## ただの添字

`open` が返すのは小さな整数です。

```c
int fd = open("data.txt", O_RDONLY);    // 3 が返ることが多い
```

この整数は、**カーネルが各プロセスごとに持っている表の添字**です。

```
プロセスのファイルディスクリプタ表
  ┌────┬──────────────────────┐
  │ 0  │ → 標準入力            │
  │ 1  │ → 標準出力            │
  │ 2  │ → 標準エラー出力       │
  │ 3  │ → data.txt のエントリ │
  └────┴──────────────────────┘
```

0、1、2 が最初から埋まっているのは、シェルがプログラムを起動するときに用意するからです。だから `open` の戻り値は 3 から始まります。

<Callout type="note" title="3 段階の構造">
  実際には表が 3 層になっています。

```
プロセスごとの fd 表  →  システム全体のオープンファイル表  →  inode / ファイルの実体
    （添字）              （読み書き位置、フラグ）              （実際のデータ）
```

  **中間の層があることが重要です。**
  `dup` で複製した fd は同じオープンファイルエントリを指すので、**読み書き位置を共有します**。
  一方、同じファイルを 2 回 `open` すると別のエントリになるので、位置は独立です。

  この違いが、リダイレクトの挙動を理解する鍵になります。
</Callout>

## すべてはファイル

Unix の設計方針として、あらゆるものが fd で扱えます。

| 対象 | 取得方法 |
| --- | --- |
| 通常のファイル | `open` |
| ディレクトリ | `open`（`O_DIRECTORY`） |
| パイプ | `pipe` |
| ソケット | `socket`, `accept` |
| 端末 | `/dev/tty` |
| デバイス | `/dev/sda`, `/dev/null` |
| **タイマ** | `timerfd_create` |
| **シグナル** | `signalfd` |
| **ファイルの変更通知** | `inotify_init` |
| **イベント通知** | `eventfd` |

後半の 4 つは Linux 独自の拡張です。本来なら別の仕組みで扱うもの（タイマ、シグナル）を、**あえて fd にしています**。

理由は、**fd なら `select` / `epoll` でまとめて待てる**からです。「ソケットの受信」と「タイマの満了」と「シグナルの到着」を、1 つのループで扱えます。統一されたインタフェースの威力です。

## リダイレクトの仕組み

```bash
./a.out > out.txt
```

プログラムは何も知らず、fd 1 に書いているだけです。シェルが `fork` と `exec` の間に細工をしています。

```c
if (fork() == 0) {
    int fd = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    dup2(fd, 1);        // fd 1 を、out.txt を指すように差し替える
    close(fd);
    execve("./a.out", argv, envp);
}
```

`dup2(fd, 1)` が核心です。「fd 1 を閉じて、fd の複製を 1 番に作る」という操作です。

**この後、fd 1 への書き込みはすべて out.txt に行きます。** プログラム側は一切変更されていません。

第 27 回で「`fork` と `exec` が分かれている理由」として挙げたのが、まさにこの隙間です。

## 2>&1 の読み方

```bash
./a.out > out.txt 2>&1
```

`2>&1` は「fd 2 を、fd 1 が指しているものと同じにする」という意味です。`dup2(1, 2)` に相当します。

**順序が重要です。**

```bash
./a.out > out.txt 2>&1     # 1 を out.txt に向けてから、2 を 1 と同じにする → 両方 out.txt
./a.out 2>&1 > out.txt     # 2 を（まだ端末の）1 と同じにしてから、1 を out.txt に向ける
                            # → 2 は端末のまま、1 だけ out.txt
```

シェルは左から順に処理します。この違いは、fd 表の構造を知っていれば当然の帰結です。

## パイプ

```bash
ls | grep foo
```

`pipe` システムコールは、**繋がった 2 つの fd** を作ります。

```c
int fds[2];
pipe(fds);
// fds[0] = 読み込み側、fds[1] = 書き込み側
```

シェルがやることは、

1. `pipe` でペアを作る
2. `fork` を 2 回して、2 つの子プロセスを作る
3. 左のプロセスでは `dup2(fds[1], 1)` として、標準出力を書き込み側に繋ぐ
4. 右のプロセスでは `dup2(fds[0], 0)` として、標準入力を読み込み側に繋ぐ
5. **両方で、使わない側の fd を閉じる**
6. それぞれ `exec` する

**5 を忘れると、パイプが終わりません。** 書き込み側の fd がどこか 1 つでも開いていると、読み込み側は EOF を受け取れず、永遠に待ちます。パイプ処理で固まる原因の多くがこれです。

パイプにはバッファがあり（Linux では既定 64KB）、いっぱいになると書き込み側がブロックします。これが**自然な流量制御**になっています。`yes | head -1` が即座に終わるのは、`head` が終了してパイプが閉じ、`yes` が SIGPIPE で殺されるからです。

## 数の上限

fd は無限には開けません。

```bash
ulimit -n              # ソフトリミット（既定 1024 のことが多い）
ulimit -Hn             # ハードリミット
cat /proc/sys/fs/file-max     # システム全体の上限
```

上限に達すると、`open` や `accept` が `EMFILE` で失敗します。

```
Too many open files
```

**サーバで最も多い障害原因の 1 つです。** 接続ごとに fd を使うので、同時接続数が上限に達するか、閉じ忘れが積み重なると発生します。

```bash
ls -l /proc/<pid>/fd | wc -l      # 現在開いている数
lsof -p <pid>                      # 何を開いているか
```

閉じ忘れの調査には、これらが使えます。`lsof` の出力に同じファイルが大量に並んでいれば、リークです。

<Callout type="warn" title="exec で引き継がれる">
  fd は `exec` を越えて引き継がれます。これがリダイレクトを可能にする一方で、
  **意図しない fd が子プロセスに渡る**という問題も生みます。
  子プロセスが、親が開いていた秘密のファイルにアクセスできてしまうかもしれません。

  対策は `FD_CLOEXEC` フラグです。これが立っている fd は `exec` 時に自動的に閉じられます。

```c
int fd = open("secret", O_RDONLY | O_CLOEXEC);    // 開くときに指定するのが安全
```
  後から `fcntl` で立てることもできますが、その間に `fork` が起きる競合があるため、
  `O_CLOEXEC` を使うべきです。
</Callout>

## 同じ fd を複数のスレッドで使う

fd 表はプロセス全体で共有されるので、全スレッドから同じ fd が見えます。便利ですが、注意点があります。

- 読み書き位置が共有されるため、複数スレッドが同じファイルを読むと位置が競合する
- 対策は `pread` / `pwrite`（位置を引数で指定し、ファイル位置を変更しない）
- `close` したときに、他のスレッドが同じ fd を使っていると危険。番号が再利用されるため、**まったく別のファイルに書き込む**事故が起きうる

## まとめ

- fd はプロセスごとの表の添字。0/1/2 はシェルが用意している
- 表は 3 層構造。中間層を共有するかどうかで、読み書き位置の共有が決まる
- ファイル、ソケット、パイプ、タイマ、シグナルまで fd で扱える。まとめて待てるのが利点
- リダイレクトは `fork` と `exec` の間で `dup2` することで実現される
- `2>&1` は順序で意味が変わる
- パイプで使わない側を閉じ忘れると終わらない
- fd の上限は有限。`EMFILE` はサーバ障害の定番
- `O_CLOEXEC` を付けて、意図しない引き継ぎを防ぐ

次は、その fd を「待つ」ときの言葉を整理します。ブロッキング、ノンブロッキング、同期、非同期。
4 つの言葉が混乱する理由から入ります。
