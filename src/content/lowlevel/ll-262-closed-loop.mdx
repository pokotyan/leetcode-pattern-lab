## 負荷をかける側も、システムの一部

第 261 回の実測では、32 人の利用者がそれぞれ応答を受け取ってから次の要求を送っていました。人気一覧をデータベースから外すと、1 秒あたりの要求数は数十倍から 200 倍余りに増えました。サーバーが速くなったので、利用者が速く次の要求を送ったからです。

この回の問いは、**負荷をかける側がどう振る舞うと、サーバーの性能はどう見えるのか**です。性能を測るとき、私たちはサーバーの側ばかりを見がちです。けれど、同じサーバーでも、負荷をかける側の送り方が違えば、スループットも応答時間も、壊れ方もまったく違って見えます。ISUCON のベンチマーカーは、どの送り方で、どんな利用者を演じているのか。本番の利用者はどれに近いのか。それを確かめます。

| 節 | 見るもの |
| --- | --- |
| 2 つの送り方 | 閉ループと開ループ。応答を待つか、待たないか |
| リトルの法則で結ぶ | 人数・スループット・応答時間・思考時間の関係 |
| ベンチマーカーの中の利用者 | ISUCON の負荷は閉ループで、利用者が増えたり去ったりする |
| 実測 | 遅くなったサーバーが、2 つの送り方の下でどう崩れるか |
| 本番の利用者 | 到着は開いていて、1 人の中は閉じている |

## 2 つの送り方

負荷をかける方法は、大きく 2 つに分かれます。Schroeder、Wierman、Harchol-Balter の論文は、これを次のように定義しています（[Open Versus Closed: A Cautionary Tale, NSDI 2006](https://www.usenix.org/conference/nsdi-06/open-versus-closed-cautionary-tale)）。

> In a closed system model, new job arrivals are only triggered by job completions (followed by think time), as in Figure 1(a). By contrast in an open system model, new jobs arrive independently of job completions, as in Figure 1(b).

（閉じた系のモデルでは、新しい仕事の到着は、仕事の完了（と、それに続く思考時間）によってのみ引き起こされる。開いた系のモデルでは、新しい仕事は仕事の完了とは無関係に到着する。）

図にすると、次のようになります。

```text
閉ループ（closed）                        開ループ（open）

  利用者 N 人                              到着（1 秒に λ 件、サーバーの状態と無関係）
  ┌──────────┐  要求                         │
  │ 考える Z │ ──────→ ┌────────┐           ▼
  │          │ ←────── │ サーバー │       ┌────────┐
  └──────────┘  応答    └────────┘       │ サーバー │ ──→ 去る
       ↑__________________|               └────────┘
   応答が来るまで次を送らない            応答を待たずに次々と届く
```

閉ループでは、系の中にいる利用者の数 N が一定です。1 人の利用者は、要求を送り、応答を待ち、少し考えて（思考時間 Z）、また送ります。サーバーが遅くなれば、利用者は応答を待つ時間が延び、そのぶん次の要求を送るのが遅れます。**負荷が自動的に弱まる**のです。

開ループでは、到着の速さ λ が一定です。利用者はサーバーの状態と関係なく現れ、要求を 1 つ送って去ります。サーバーが遅くなっても、到着は減りません。処理しきれない要求は、どこかに溜まっていきます。

負荷試験の道具 k6 の文書は、閉じたモデルの弱点を次のように書いています（[Grafana k6: Open and closed models](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)）。

> In other words, when the target system is stressed and starts to respond more slowly, a closed model load test will wait, resulting in increased iteration durations and a tapering off of the arrival rate of new VU iterations.

（つまり、対象のシステムに負荷がかかって応答が遅くなり始めると、閉じたモデルの負荷試験は待ってしまい、1 回の繰り返しにかかる時間が延び、新しい繰り返しの到着の速さが先細りになる。）

k6 は、閉じたモデルの実行方式と、到着の速さを固定する開いたモデルの実行方式（`constant-arrival-rate` など）を両方持っています。一方、よく使われる `hey` や `ab` は、同時に走らせる数（`hey` なら `-c`）を決めて、各々が応答を待ってから次を送る閉じた形です。`hey` の `-q` は「Rate limit, in queries per second (QPS) per worker」で、1 人あたりの上限を決めるだけです（[hey README](https://github.com/rakyll/hey)）。サーバーが遅くなれば、実際の送信の速さはその上限より下がります。

この「サーバーが遅いと測る側も遅くなる」性質が、測定値を歪める仕組みは、第 237 回で **coordinated omission** として見ました。1 本の接続で前の応答を待ってから次を送る道具は、サーバーが止まっている間に送るはずだった要求を送らず、したがって測らない、という話です。この回では、測定値の歪みではなく、**負荷そのものの形が違う**ことに注目します。

## リトルの法則で結ぶ

2 つの送り方を、同じ式で比べられるようにしておきます。系の中にいる数の平均を L、到着の速さ（安定していればスループットと同じ）を X、1 件が系の中にいる時間の平均を W とすると、

```text
L = X × W
```

が成り立ちます。これがリトルの法則です。導き方と意味は、読み物の <a href={`${import.meta.env.BASE_URL}reading/performance-estimation/`}>性能を勘で語らない</a> で扱いました。

閉ループに当てはめると、系の中にいるのは利用者 N 人全員で、1 人が 1 周する時間は「応答時間 R ＋ 思考時間 Z」です。したがって、

```text
N = X × (R + Z)     すなわち     X = N / (R + Z)
```

N と Z は負荷をかける側が決める定数です。サーバーが遅くなって R が延びると、X は**自動的に下がります**。サーバーが受ける負荷は、サーバー自身の速さで決まるのです。逆に、サーバーが速くなって R が縮むと、X は上がります。第 261 回で、人気一覧を速くしたら要求が増えたのは、この式のとおりです。

開ループでは、X は到着の速さ λ で外から決まります。サーバーが 1 秒に μ 件しか捌けないとき、λ が μ を下回っていれば待ち行列は落ち着きます。けれど λ が μ を上回ると、1 秒ごとに `λ − μ` 件ずつ待ち行列が伸び続け、待ち時間は時間に比例して延びていきます。**開ループの下では、処理能力を少しでも下回った瞬間に、系は安定しなくなります。**

| | 閉ループ | 開ループ |
| --- | --- | --- |
| 決まっているもの | 利用者の数 N、思考時間 Z | 到着の速さ λ |
| サーバーが遅くなると | 送信が減る。応答時間は「N 人ぶんの待ち」で頭打ち | 送信は減らない。待ち行列が伸び続ける |
| サーバーが速くなると | 送信が増える | 送信は変わらない。待ちが減るだけ |
| 系の中の要求の数 | 最大でも N | 上限がない |
| 壊れ方 | 遅くなるが、崩れにくい | ある点を越えると一気に崩れる |

## ベンチマーカーの中の利用者

ISUCON のベンチマーカーは、基本的に閉ループの利用者です。そのうえで、利用者の数そのものが、アプリケーションの振る舞いに応じて増えたり減ったりするように作られています。

### 応答を待ってから次へ進む

ISUCON11 予選の講評は、点数になる利用者の行動について「いずれかが詰まると次の行動に移るまでに時間がかかるため、スコアが伸び悩む仕組みになっていました」と書いています（[ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)）。1 人の利用者が、コンディションの確認、詳細の確認、グラフの確認を順に行い、どこかが遅ければ、その利用者が 60 秒の間に回れる回数が減ります。

ISUCON14 では、この「次の行動」の単位が時間で決まっていました。講評によれば「ベンチマーカー内に構成された世界では30msを1tickとして次の行動を制御されるようになっていました。そのため、全エンドポイントが30ms以内にレスポンスを返せていることが理想的な状態です」（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。椅子は自分の位置を送る `POST /api/chair/coordinate` が完了するまで次の移動を始めないので、この応答が遅いと椅子の移動そのものが遅れます。

閉ループの利用者にとって、応答時間は「次の行動までの待ち」です。だから、点になる行動の手前にある要求が遅いと、点になる行動の回数が減ります。第 261 回の実測で、買う人が一覧の応答を待っている間は購入できなかったのと同じです。

### 利用者が増える

ISUCON のベンチマーカーには、アプリケーションが良い振る舞いをすると、利用者が増える仕組みがよく入っています。

ISUCON11 予選では、閲覧者がトップページのトレンド（`GET /api/trend`）を見続けていました。アプリケーションマニュアルには「ISUCONDITION に興味を持っている閲覧者は、トレンドの変化に注目しています。」とあり（[ISUCONDITION アプリケーションマニュアル](https://github.com/isucon/isucon11-qualify/blob/main/docs/isucondition.md)）、講評は、トレンドの変化があると評判が良くなり利用者が増える、というベンチマーカーのシナリオを説明したうえで、こう警告しています（[ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)）。

> この改善を入れた場合、ユーザと ISU が増えリクエスト数が急増します。そのため、大量のリクエストを捌くような修正を入れないとスコアは下がります。特に、ファイルディスクリプタ数の上限を増やすなど、nginx、アプリケーション、DB の各種 limit パラメーターを緩和しないとエラーが出て fail することがあります。

ISUCON14 でも、ライドの満足度が利用者の数を動かしました。講評は「個人の評価が高いとユーザーによる招待が、地域ごとの評価の平均値が高いと口コミによるユーザー数の増加が起きるようになっていました」と書いています。

これは閉ループの式で言えば、**N そのものが、サーバーの速さに応じて増える**ということです。速くするほど R が縮んで X が上がり、さらに N が増えて X が上がります。改善が、そのまま次の負荷を呼び込みます。

### 利用者が去る

逆に、遅いと利用者は去ります。ISUCON14 では、ライドを頼んでから椅子が割り当てられるまでの時間が満足度の評価に入っていて、講評によれば、初期実装では 500 ms ごとに 1 つのライドしかマッチングしないため、他を速くしてマッチング待ちのライドが増えると「不満が溜まっていくようになっていた」とあります。

この仕組みを、ベンチマーカーのログから見つけて点数を 3 倍近くにしたのが、ISUCON14 で 3 位になったチームです。ブログによれば、スコア 8,775 の時点のログに「93.8%のライドは椅子がマッチされるまでの時間」に不満があったと出ていたことから、マッチングの間隔を 0.5 秒から 0.1 秒に短くしたところ、スコアが 25,758 になりました（[ISUCON 14に参戦して3位入賞しました](https://blog.pinkumohikan.com/entry/isucon-14)）。データベースの処理を速くしたわけではありません。**利用者が去っていく理由を一つ取り除いた**のです。

### 速くしたのに点が下がる

閉ループで利用者の行動がつながっていると、ある要求を速くしたことで、点数が下がることもあります。ISUCON11 予選を 1 位で通過した shallowverse の記録には、椅子の一覧（`GET /api/isu`）とトレンド（`GET /api/trend`）の N+1 クエリを解消したときのことが、次のように書かれています（[ISUCON11予選を1位通過した](https://www.y1r.org/posts/20210831-isucon11-qualify)）。

> GETのクエリを早くしたところ，スコアが6000まで下がりましたが，レスポンス自体は速くなっていたのでrevertはしないことにしました．

原因は記録の中では特定されていません。ただ、閉ループの式から考えられる理由はいくつかあります。速くなった要求を送る利用者が、そのぶん多くの要求を送るようになり、点になる別の処理と同じ資源を奪い合う。トレンドが速く返るようになって閲覧者の評判が上がり、利用者が増え、捌ききれない処理が増える。どちらも、サーバーの外にいる利用者の振る舞いが変わったことによるものです。このチームはその後、点になる送信の処理を速くし、最後には 150 万点まで伸ばしています。

## 実測：遅くなったサーバーは、2 つの送り方の下でどう崩れるか

2 つの送り方を、同じサーバーにかけて比べます。

サーバーは Go で書き、同時に 4 件まで処理し、1 件に 20 ms かかるものとします。処理時間は `time.Sleep` で表します。処理できるのは 1 秒に最大 `4 / 0.02 = 200` 件です。これを 40 ms に遅くすると、上限は 100 件になります。

```go
slots := make(chan struct{}, 4) // 同時に 4 件まで
http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
	slots <- struct{}{} // 空きを待つ
	time.Sleep(svc)     // 20 ms または 40 ms
	<-slots
	w.Write([]byte("ok"))
})
```

負荷をかける側も Go で書き、2 つの型を用意しました。

```go
// 閉ループ: N 人が、応答を受けてから Z 待って次を送る
for i := 0; i < n; i++ {
	go func() {
		for time.Now().Before(deadline) {
			d, ok := hit()
			res.add(d, ok)
			time.Sleep(think)
		}
	}()
}

// 開ループ: 到着間隔を指数分布で決め、応答を待たずに次の要求を出す
next := start
for next.Before(deadline) {
	time.Sleep(time.Until(next))
	sched := next
	go func() {
		_, ok := hit()
		res.add(time.Since(sched), ok) // 送るはずだった時刻から測る
	}()
	next = next.Add(time.Duration(rng.ExpFloat64() / rate * float64(time.Second)))
}
```

開ループでは、第 237 回で見た coordinated omission を避けるため、応答時間を**送るはずだった時刻から**測っています。どちらも、タイムアウトは 2 秒です。閉ループは N = 50 人、思考時間 Z = 200 ms、開ループは λ = 1 秒に 150 件の到着です。どちらも 10 秒間走らせます。

環境は Apple M1 Pro / macOS 26.2、Go 1.24.6 です。計測中は同じマシンでほかの重い処理が並行して走っていて、ロードアベレージは 40〜60 前後でした。そのぶん、`time.Sleep` は指定より 1.5〜3 ms ほど長く眠ります。

### 20 ms のとき：どちらも落ち着いている

```text
### server c=4 s=20ms
closed N=50 Z=200ms: throughput=173.1/s mean=81.8ms p50=80.1ms p99=173.5ms failed=0  X*(R+Z)=48.8
open rate=150/s: completed=155.8/s mean=44.7ms p50=38.3ms p99=121.3ms failed=0 max_inflight=24
  p50 by send second: 29 28 33 47 27 39 49 39 91 41
```

閉ループは 1 秒に 173 件、平均 82 ms でした。リトルの法則で `X × (R + Z)` を計算すると 48.8 で、利用者の数 50 とほぼ一致します（差は、`time.Sleep` の寝過ごしで思考時間が実際には 200 ms より少し長いためです）。

開ループは、1 秒に 150 件の到着に対して 155.8 件を処理しています。到着の間隔を乱数で決めているので、10 秒間の実際の到着数は 150 × 10 ちょうどにはなりません。処理能力 200 件に対して到着が 150 件なので、待ち行列は短く、同時に系の中にあった要求は最大で 24 件でした。最後の行は、送った時刻の秒ごとに応答時間の中央値を並べたもので、どの秒も 30〜90 ms に収まっています。

### 40 ms のとき：閉ループは遅くなり、開ループは崩れる

サーバーの処理時間を 40 ms にして、処理能力を 1 秒 100 件に下げます。

```text
### server c=4 s=40ms
closed N=50 Z=200ms: throughput=90.0/s mean=336.1ms p50=338.6ms p99=451.1ms failed=0  X*(R+Z)=48.3
open rate=150/s: completed=46.6/s mean=1021.2ms p50=988.5ms p99=1983.4ms failed=1092 max_inflight=344
  p50 by send second: 407 1011 1607 1950 0 0 0 0 0 0
```

閉ループは、スループットがほぼ半分（90 件）になり、平均の応答時間は 336 ms に延びました。それでも失敗は 0 です。式で確かめると、処理能力が 1 秒 100 件なら `R = N / X − Z = 50 / 100 − 0.2 = 0.3 秒` で、測った値とほぼ合っています。**サーバーが遅くなったぶん、負荷をかける側が勝手に送るのを控えた**のです。

開ループは崩れました。送った秒ごとの応答時間の中央値は 407 ms、1,011 ms、1,607 ms、1,950 ms と 1 秒ごとにおよそ 0.5〜0.6 秒ずつ延びています。到着が 150 件、処理が 100 件なので、待ち行列が 1 秒に約 50 件ずつ伸び、その待ちが 1 件ずつの応答時間に足されていきます。5 秒目以降に送った要求は、1 件も 2 秒以内に返りませんでした（0 は成功した応答が無いことを示します）。系の中の要求は最大 344 件まで積み上がり、失敗（2 秒のタイムアウト）は 1,092 件です。

ここで注目したいのは、成功した応答が **1 秒あたり 46.6 件**しかないことです。サーバーは 1 秒に 100 件を処理できるのに、利用者の役に立った応答はその半分以下でした。残りの処理能力は、**すでに利用者が待つのをやめた要求**に使われていました。負荷をかける側が 2 秒で打ち切っても、サーバーの側は待ち行列に並んだ要求を順に処理し続けるからです。

### 打ち切られた要求を捨てる、待たせすぎない

この無駄を減らす方法を 2 つ試しました。

1 つ目は、相手が接続を切った要求を、空きを待っている間に捨てる方法です。Go の `net/http` では、相手が切断すると `r.Context()` が終了するので、空きを待つ `select` でそれを見ます。

```go
select {
case slots <- struct{}{}:
case <-r.Context().Done():
	return // 相手はもう待っていない
}
```

2 つ目は、空きを一定時間（ここでは 300 ms）以上待った要求を、503 で断る方法です。

```go
t := time.NewTimer(300 * time.Millisecond)
select {
case slots <- struct{}{}:
	t.Stop()
case <-t.C:
	w.WriteHeader(http.StatusServiceUnavailable)
	return
}
```

同じ開ループ（1 秒 150 件、処理 40 ms）をかけた結果です。

```text
### s=40ms maxwait=300ms
open rate=150/s: completed=93.7/s mean=327.5ms p50=337.1ms p99=366.7ms failed=621 max_inflight=67

```

| --- | --- | --- | --- | --- |
| 待ち行列に制限なし | 46.6 件 | 1,983 ms | 1,092 件 | 344 |
| 切断された要求を捨てる | 45.0 件 | 1,991 ms | 1,108 件 | 333 |
| 300 ms 以上待たせず 503 | 93.7 件 | 367 ms | 621 件 | 67 |

切断された要求を捨てても、ほとんど改善しませんでした。理由は、捨てられるのが「2 秒待ったあと」だからです。待ち行列の先頭に残っている要求は、どれもすでに 2 秒近く待っていて、処理し終えるころには 2 秒を越えてしまいます。5 秒目以降の中央値が 2,000 ms 前後に張り付いているのは、そのためです。

300 ms で断る方は、成功が 1 秒 93.7 件と、処理能力の 100 件近くまで戻りました。成功した応答の p99 は 367 ms で、10 秒間ずっと安定しています。到着の 150 件のうち、捌けない約 50 件を早めに断り（失敗 621 件の大半は 503 です）、残りを確実に返したのです。**処理しきれない仕事を引き受けないことで、引き受けた仕事を守った**と言えます。

<Callout type="tip" title="ベンチマーカーのタイムアウトは、サーバーには伝わらない">
  ISUCON のベンチマーカーにも、要求ごとのタイムアウトがあります。ISUCON14 では初期化が 30 秒、通知の取得が 60 秒、それ以外が 10 秒でした（[ISUCON14 当日マニュアル](https://github.com/isucon/isucon14/blob/main/docs/manual.md)）。ISUCON11 予選では、椅子からの送信が 100 ms、それ以外の多くが 1 秒でした。
  ベンチマーカーが待つのをやめても、サーバーの中の処理は止まりません。第 261 回の実測で、打ち切られた購入がサーバー側で完了し、販売件数がずれて FAIL になったのは、その一例です。
  負荷が高いときにサーバーが何をしているのかを見るには、ベンチマーカーの側の数字だけでなく、サーバーの側で処理を始めた数と、終えた数と、そのうち相手がまだ待っていた数を比べる必要があります。
</Callout>

### 速くすると、利用者が増える

最後に、利用者の数が応答の速さで変わる閉ループを試します。ISUCON11 予選のトレンドや ISUCON14 の満足度の仕組みを、次の 2 つの規則に単純化しました。

- 1 秒ごとに、直前 1 秒の応答時間の p95 が 100 ms 未満なら、利用者を 10 人増やす
- 500 ms を超える応答を受けた利用者は、その場で去る

最初の利用者は 20 人、思考時間は 200 ms、30 秒間走らせます。サーバーの処理時間を 20 ms（1 秒 200 件まで）と 10 ms（1 秒 400 件まで）で比べました。

この 1 回の崩れは偶然の要素を含みますが、仕組みとしては一般的です。利用者が増える規則は「速いうちは増やす」なので、系はいつも処理能力の限界の少し手前まで押し上げられます。その状態では、一瞬の遅れが「去る」の閾値を越え、多くの利用者を一度に失います。**速くした結果、余裕のない状態で動くことになる**のです。ISUCON11 予選の講評が、トレンドの改善とセットでファイルディスクリプタの上限を緩めるよう書いているのも、増えた利用者を受け止める側の準備が要るからです。

## 本番の利用者はどちらか

本番の Web サービスの利用者は、どちらの型に近いでしょうか。

**到着は開いている。** 新しい利用者は、サーバーが遅いかどうかと無関係にやってきます。キャンペーンの告知、テレビ放送、定時のバッチ、他社のシステムからの呼び出しは、サーバーの状態を見てから送られてくるわけではありません。

**1 人の中は閉じている。** いったん訪れた利用者は、ページを開き、応答を見て、次をクリックします。1 回の訪問（セッション）の中では、応答を待ってから次へ進みます。そして、遅すぎれば去ります。

先の論文は、この中間を **partly-open** なモデルと呼び、その振る舞いが閉じたモデルと開いたモデルの間に来ることを示しています。利用者は外から到着し、要求を 1 つ終えるたびに確率 p で次の要求を送り、確率 1 − p で去ります。論文は「For a given load, when p is small, the partly-open model is more similar to an open model. For large p, the partly-open model resembles a closed model.」と書いています。1 回の訪問で送る要求が多いほど閉じたモデルに、少ないほど開いたモデルに近づくということです。

この見方から、本番の性能を考えるときの判断がいくつか出てきます。

| 場面 | 考えること |
| --- | --- |
| 負荷試験を設計する | 道具がどちらの型かを確かめる。閉ループだけで試すと、処理能力を越えたときの崩れ方が見えない。到着の速さを固定した試験を必ず入れる |
| 応答時間を報告する | 閉ループの試験で「応答時間は 300 ms で安定」と出ても、それは負荷をかける側が送るのを控えた結果かもしれない |
| リトライを設計する | 失敗したら即座に送り直すクライアントは、到着をさらに増やす。サーバーが遅いときほど負荷が増え、開ループの崩れを加速する。間隔を空ける、回数を限る |
| タイムアウトを決める | 呼び出し側が諦めた要求を、呼ばれた側が処理し続けないようにする。期限を伝えるか、待ち行列で待てる時間に上限を設ける |
| 速くしたあと | 利用者が増える、ポーリングが増える、バッチの間隔が縮むなど、速さに応じて負荷が増える経路がないかを確かめる |

<Callout type="warn" title="閉ループの試験で「限界」を測ると、楽観的になる">
  閉ループの負荷試験で同時接続数を上げていくと、ある所からスループットが伸びなくなり、応答時間だけが延びていきます。これを「限界」と呼びたくなりますが、本番の到着が開いているなら、その限界を少しでも越えた時点で、待ち行列は伸び続けます。
  閉ループで見えるのは「その人数のときにどうなるか」で、開ループで見えるのは「その到着の速さに耐えられるか」です。本番の安全性を問うなら、後者で確かめる必要があります。
</Callout>

## 次の回へ

ここまでの 2 回で、何を目的に速くするのか、負荷をかける側がどう振る舞うのかを見ました。次の第 263 回からは、実際に手を動かします。競技が始まって最初の 1 時間に、サーバーの設定とコードを手元に取り込み、変更を 1 つのコマンドで配って確かめられる状態を作るところからです。

## まとめ

- 負荷のかけ方には、応答を待ってから次を送る閉ループと、応答と無関係に到着が続く開ループがある
- 閉ループでは `N = X × (R + Z)` が成り立ち、サーバーが遅くなると負荷が自動的に弱まる。開ループでは到着が外から決まり、処理能力を越えると待ち行列が伸び続ける
- `hey` や `ab` は同時接続数を決める閉じた形、k6 には到着の速さを固定する実行方式もある。道具がどちらの型かを確かめてから結果を読む
- ISUCON のベンチマーカーは閉ループの利用者で、応答が遅いと次の行動が遅れ、点になる行動の回数が減る
- ベンチマーカーは、速いと利用者を増やし、遅いと利用者を去らせる。ISUCON11 予選のトレンド、ISUCON14 の満足度と招待がその例
- ISUCON14 で 3 位のチームは、ベンチマーカーのログから利用者の不満の理由を読み、マッチングの間隔を 0.5 秒から 0.1 秒にしてスコアを 8,775 から 25,758 にした
- 速くしたのに点が下がることがある。閉ループの外にいる利用者の振る舞いが変わるからで、サーバーだけを見ていると理由が分からない
- 実測では、処理を 20 ms から 40 ms に遅くすると、閉ループはスループットが半分になって安定し、開ループ（1 秒 150 件）は応答時間が 1 秒ごとに延びて 5 秒目以降は 1 件も 2 秒以内に返らなくなった
- 開ループで崩れたサーバーの処理能力の半分以上は、すでに相手が諦めた要求に使われていた。切断を見て捨てるだけでは足りず、300 ms 以上待たせずに断ると、成功が 1 秒 46.6 件から 93.7 件に戻った
- 速くすると利用者が増える閉ループでは、処理を 2 倍速くすると受ける負荷も約 2 倍になり、系はいつも限界の手前で動くことになる
- 本番の利用者は、到着が開いていて、1 回の訪問の中は閉じている。負荷試験では到着の速さを固定した試験を入れ、リトライとタイムアウトは負荷を増やす経路として設計する
