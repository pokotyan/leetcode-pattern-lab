## 前史：ブラウザには JavaScript しかなかった

2010 年頃、ブラウザで動く言語は JavaScript だけでした。

そこに、**C や C++ で書かれた既存の資産を動かしたい**という要求が出てきます。ゲームエンジン、画像処理、CAD、エミュレータ。数十年ぶんのコードが C で書かれていました。

素直な解は「JavaScript で書き直す」ですが、現実的ではありません。

### Emscripten

Alon Zakai が 2010 年に始めた **Emscripten** は、逆の発想を取りました。

> **C を JavaScript にコンパイルする。**

LLVM の中間表現を経由して、JavaScript を出力します。第 5 章で見たコンパイルの流れの、出力先を機械語ではなく JavaScript にしたものです。

```
C / C++  →  clang  →  LLVM IR  →  Emscripten  →  JavaScript
```

問題は、**C が前提としているものがブラウザに無い**ことでした。

| C が前提とするもの | ブラウザには |
| --- | --- |
| 連続したメモリ空間（第 4 章） | **無い** |
| ポインタ演算 | 無い |
| ファイルシステム（第 7 章） | 無い |
| `pthread` | 無い |
| `longjmp` | 無い |

Emscripten は、これらを**すべてエミュレートしました**。

- **メモリ**：巨大な `ArrayBuffer` を 1 本確保し、それを「メモリ全体」として扱う。ポインタは、そのバッファへの**インデックス**になる
- **ファイルシステム**：仮想のファイルシステムを JavaScript で実装し、`open`/`read`/`write` を受ける
- **`pthread`**：Web Workers と `SharedArrayBuffer` に対応づける
- **`longjmp` / 例外**：JavaScript の例外機構に載せる

<Callout type="tip" title="ポインタがただの整数になった">
  この「1 本の大きなバッファと、そこへのインデックス」という設計が、
  **後の WebAssembly の線形メモリそのもの**です。

  第 4 章で見た仮想メモリでは、MMU がアドレスを変換していました。
  ここでは**バッファの範囲外かどうかを検査するだけ**です。
  ハードウェアが要らず、しかも外に出られない。

  制約から生まれた設計が、そのまま安全性の根拠になりました。
</Callout>

### asm.js

Emscripten が出力する JavaScript は動きましたが、**遅かった**。JavaScript エンジンは動的型付けを前提に最適化するため、型が確定している C 由来のコードでも、実行時の型チェックが入ります。

そこで 2013 年、Mozilla が **asm.js** を提案します。

> **JavaScript の、極端に限定されたサブセットを決める。**
> **そこに当てはまるコードは、型が静的に決まるので先にコンパイルできる。**

```js
function add(x, y) {
  x = x | 0;          // 「これは 32 ビット整数」という印
  y = y | 0;
  return (x + y) | 0;
}
```

`| 0` はビット演算なので、結果は必ず 32 ビット整数です。**型注釈の代わりにビット演算を使う**という、苦肉の策でした。

重要なのは、**これは正しい JavaScript である**ことです。asm.js に対応していないブラウザでも、遅いけれど動きます。段階的に導入できる設計でした。

<Callout type="warn" title="それでも限界があった">
  asm.js は JavaScript なので、

  - **パースにテキストの解析が必要**。数十 MB のソースを読むだけで時間がかかる
  - **サイズが大きい**。圧縮しても冗長
  - **64 ビット整数が扱えない**。JavaScript の数値は倍精度浮動小数点（第 1 章）
  - 仕様ではなく、**慣習**でしかない

  「型が決まっているなら、テキストではなくバイナリで渡せばいい」という結論になります。
</Callout>

## WebAssembly

2015 年、主要ブラウザベンダが共同で **WebAssembly** を発表します。2017 年 3 月に 4 つのブラウザすべてで実装が揃い、2019 年 12 月には W3C の勧告になりました。

設計の要点です。

### スタックマシンである

Wasm の命令はスタックマシンです。

```wat
(func $add (param $a i32) (param $b i32) (result i32)
  local.get $a
  local.get $b
  i32.add)
```

**Track 2 で作ったものとまったく同じ構造**です。積んで、演算して、結果が積まれる。

なぜレジスタマシンではなくスタックマシンなのか。理由は、

- **表現が小さい**。オペランドの指定が要らない
- **検証しやすい**。各命令の前後でスタックの型が決まっているか、静的に確認できる
- **ターゲットの CPU に依存しない**。レジスタの本数を仮定しない

第 2 章で見た「ISA は契約」という話でいえば、**Wasm は特定のハードウェアを持たない ISA**です。実行時に、その機械の命令に変換されます。

### 型があり、検証できる

すべての関数、すべての命令が型を持ちます。読み込み時に、**スタックの型が整合しているかを検証します**。

検証を通らないモジュールは実行されません。**不正なコードは、実行が始まる前に弾かれます。**

### 制御フローが構造化されている

機械語なら、任意のアドレスにジャンプできます。Wasm にはそれがありません。

```wat
(block
  (loop
    ...
    (br_if 1)     ; 「2 つ外側のブロックを抜ける」という相対指定
  ))
```

**ジャンプ先は、入れ子のブロックの相対位置でしか指定できません。** 関数の途中に飛び込むことも、データをコードとして実行することもできない。

第 5 章で見た ROP（既存のコード断片を繋ぎ合わせる攻撃）が、**原理的に成立しません**。飛び先が構造として決まっているからです。

<Callout type="note" title="制御フローの完全性が、仕様の側で保証されている">
  ネイティブのコードでは、CFI（Control Flow Integrity）のような仕組みを
  **後から足して**この性質を近似します。

  Wasm は最初からそうなっています。
  「できることを制限した結果、証明できることが増えた」という設計です。
</Callout>

### 線形メモリ

メモリは、**1 本の連続したバイト列**です。

```wat
(memory 1)              ; 64KiB ページを 1 枚
i32.load offset=8       ; メモリの 8 番地から 4 バイト読む
```

ポインタは、このメモリ内の**オフセット（32 ビット整数）**です。

**ここが決定的です。**

- **Wasm のコードから到達できるのは、この線形メモリの中だけ**
- ホストのメモリを指す手段が、言語として存在しない
- 範囲外のアクセスは**トラップ**になり、その Wasm インスタンスだけが停止する

第 4 章で見た仮想メモリと比べてみます。

| | 仮想メモリ | Wasm の線形メモリ |
| --- | --- | --- |
| 分離の仕組み | MMU がページテーブルを引く | **範囲検査**（あるいはガードページ） |
| ハードウェアが必要か | **必要** | 不要 |
| 権限の粒度 | ページ単位 | メモリ全体が読み書き可 |
| 外に出られるか | 出られない | **出られない** |
| 実行可能なメモリ | ある（NX で制御） | **無い**（コードとデータが別空間） |

**コードとデータの空間が完全に分かれている**点も重要です。線形メモリに機械語を書き込んで実行する、という攻撃が成立しません。第 4 章で見た NX ビットを、**構造として持っている**形です。

### Wasm の中では、今までどおり壊れる

誤解されやすい点です。

**Wasm はホストを守りますが、Wasm の中身は守りません。**

C を Wasm にコンパイルした場合、線形メモリの中では相変わらず、

- バッファオーバーランが起きる
- 解放済みのメモリを参照できる
- スタックを壊せる

**壊れるのは線形メモリの中だけ**です。ホストのメモリには届きません。

```
ネイティブ:  バッファオーバーラン → 隣の変数を壊す → 最悪ホストを乗っ取られる
Wasm:        バッファオーバーラン → 隣の変数を壊す → そのインスタンスの中で完結する
```

第 4 章で見た「粒度が粗すぎて日常的なバグには効かない」という話が、ここでも当てはまります。**外への波及は止まるが、内側の論理的なバグは止まらない。**

<Callout type="warn" title="だから AddressSanitizer は今も必要">
  Wasm にしたからといって、メモリ安全なコードになるわけではありません。
  第 4 章で見た Sanitizer は、Wasm 向けにも用意されています。

  Wasm が保証するのは **「被害が外に出ない」** ことだけです。
</Callout>

### システムコールが無い

Wasm の命令セットには、ファイルを開く命令も、ネットワークに繋ぐ命令もありません。

**外の世界に触れるには、ホストが明示的に渡した関数を呼ぶしかありません。**

```js
// ホスト側が、何を許すかを決める
const instance = await WebAssembly.instantiate(bytes, {
  env: {
    log: (ptr, len) => console.log(readString(memory, ptr, len)),
    // ファイルもネットワークも渡さなければ、Wasm からは一切触れない
  },
})
```

第 7 章で見た「システムコールが、外の世界への唯一の窓口」という構造と同じですが、**窓口そのものをホストが決める**という点が違います。

- 通常のプロセス：**システムコールは全部使える**。使わせたくないものを seccomp で塞ぐ（引き算）
- Wasm：**何も無い**。渡したものだけが使える（足し算）

この違いが、次回のテーマになります。

## その後の進化

MVP（2017）の時点では、機能が絞られていました。その後、段階的に拡張されています。

| 機能 | 内容 | 時期 |
| --- | --- | --- |
| SIMD | 128 ビットのベクトル演算（第 2 章） | 2021 |
| スレッド | `SharedArrayBuffer` + アトミック（第 6 章） | 2021 |
| 参照型 | ホストのオブジェクトを不透明な参照として持てる | 2022 |
| 例外処理 | ゼロコスト例外。それまでは JavaScript 経由で高価だった | 2023 |
| **GC** | ホストの GC を使える。Java、Kotlin、Dart が線形メモリなしで動く | 2023 |
| 末尾呼び出し | 関数型言語に必要（Track 2 の第 8 回） | 2023 |
| memory64 | 64 ビットのアドレス空間 | 進行中 |

<Callout type="tip" title="Wasm GC が変えたこと">
  MVP では、GC を持つ言語（Java、C#、Go）を Wasm で動かすには、
  **GC のランタイムごと線形メモリの中に実装する**必要がありました。
  バイナリが大きくなり、ホストの GC と二重になります。

  Wasm GC により、**ホストの GC が管理するオブジェクトを直接扱える**ようになりました。
  線形メモリを一切使わない Wasm モジュールが書けます。

  第 4 章で見た「ポインタが 8 バイトになるとキャッシュ効率が落ちる」のと同じで、
  **メモリの持ち方が実行効率を左右する**という話です。
</Callout>

## 実際に見てみる

Wasm にはテキスト表現（WAT）があり、バイナリと相互変換できます。

```bash
# C から Wasm へ
emcc hello.c -o hello.wasm

# バイナリをテキストに
wasm2wat hello.wasm | head -40

# 逆向き
wat2wasm hello.wat -o hello.wasm
```

第 2 章で `objdump -d` を使ったのと同じ感覚で、中身を見られます。

```wat
(module
  (memory (export "memory") 1)
  (func (export "add") (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add))
```

**これを読めることが、Track 2 でスタックマシンを作った成果**です。`local.get` が `push local`、`i32.add` が `add` に対応します。

## まとめ

- Emscripten は C を JavaScript にコンパイルした。ポインタを「大きなバッファへのインデックス」にした
- asm.js は JavaScript のサブセットを定めて高速化した。テキストである限界があった
- Wasm はスタックマシン、型付き、検証可能、制御フローが構造化されている
- 線形メモリの外には到達できない。MMU を使わずに分離が成立する
- **Wasm の中では今までどおり壊れる。ただし外に出ない**
- システムコールが存在せず、ホストが渡した関数しか呼べない
- SIMD、スレッド、例外、GC と段階的に拡張されている

次は、これがブラウザの外に出た話です。**なぜ Wasm が FFI の答えになるのか**を見ます。
