## 強さは鍵だけにある

第 105 回で、ケルクホフスの原理を見ました。**鍵以外はすべて公開されてよい**、という考え方です。AES も X25519 も Ed25519 も、仕様は誰でも読めます。第 110 回で見た鍵ファイルの形式も公開されています。

すると、攻撃者と利用者を分けるものは、**鍵を知っているかどうか**だけになります。この回の問いは 2 つです。

1. その鍵は、**推測できない値**として作られているか
2. その鍵は、**持つべき者だけが使える場所**に置かれているか

AES-256 の鍵は 256 ビットですが、それを作った乱数が 15 ビット分しか散らばっていなければ、鍵の強さは 15 ビットです。アルゴリズムがどれほど強くても、**鍵の作り方と置き方で全部が決まります**。第 105〜110 回の部品はすべて、この 2 つを前提にしていました。

## 暗号用の乱数は OS からもらう

プログラムで使う「乱数」には、性質のまったく違う 2 種類があります。

| 種類 | 例 | 目的 | 出力から次を予測できるか |
| --- | --- | --- | --- |
| 統計用の擬似乱数 | Python の `random`（Mersenne Twister）、V8 の `Math.random`（xorshift128+） | シミュレーション、シャッフル | **できる**。内部状態が出力から復元できる |
| 暗号用の擬似乱数（CSPRNG） | Linux の getrandom、`/dev/urandom` | 鍵、nonce、トークン | できないように作られている |

Python のドキュメントは、`random` を「セキュリティの目的に使ってはならない」と明記し、`secrets` を使うよう求めています（[Python random](https://docs.python.org/3/library/random.html)、[Python secrets](https://docs.python.org/3/library/secrets.html)）。MDN も、`Math.random()` は暗号学的に安全な乱数を提供しないので `crypto.getRandomValues()` を使うよう書いています（[MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Math/random)）。V8 が 2015 年に採用した xorshift128+ についても、V8 自身が「暗号学的に安全ではない」と述べています（[V8 blog](https://v8.dev/blog/math-random)）。

暗号用の乱数の出どころは、**OS のカーネル**です。カーネルは割り込みの時刻の揺らぎ（第 13 回）や CPU の乱数命令など、外から予測しにくい事象を集めてプールに混ぜ、そこから CSPRNG に種を与えます。

```
割り込みの時刻、入力、CPU の乱数命令 ...
        │  混ぜる
        ▼
   エントロピーのプール ──種──▶ CSPRNG（ChaCha20 ベース）
                                    │
                    ┌───────────────┼────────────────┐
                    ▼               ▼                ▼
              getrandom(2)     /dev/urandom      /dev/random
                    │
     Python secrets / os.urandom、Go crypto/rand、OpenSSL ...
```

Linux での入口は次のとおりです。

- **getrandom(2)**: Linux 3.17 で入ったシステムコール（第 41 回）。プールが初期化される前は、`GRND_NONBLOCK` を付けない限り**ブロックします**。初期化後は、256 バイトまでの読み出しは必ず要求どおりの量を返します（[getrandom(2)](https://man7.org/linux/man-pages/man2/getrandom.2.html)）
- **/dev/urandom**: ブロックしません。そのかわり**起動の早い段階では、プールが初期化される前のデータを返すことがあります**（[random(4)](https://man7.org/linux/man-pages/man4/random.4.html)）
- **/dev/random**: Linux 5.6 以降、起動直後を除いてブロックしなくなりました。man ページは `/dev/random` を「古いインタフェース」と呼び、起動直後を除けば `/dev/urandom` で「すべての用途に十分」としています（同上）

Python の `os.urandom` と `secrets` は、Linux では getrandom をブロックするモードで使います（[Python os.urandom](https://docs.python.org/3/library/os.html#os.urandom)）。**自分で `/dev/random` を開く必要はなく、言語の暗号用 API を呼べばよい**、というのが実務での答えです。

| 言語・道具 | 暗号用 | 使ってはいけないもの |
| --- | --- | --- |
| Python | `secrets.token_bytes()`、`os.urandom()` | `random` |
| JavaScript | `crypto.getRandomValues()`、`crypto.randomUUID()` | `Math.random()` |
| Go | `crypto/rand` | `math/rand` |
| シェル | `openssl rand -hex 32` | `$RANDOM` |

<Callout type="warn" title="よくある誤解: /dev/random のほうが安全">
  かつての Linux の `/dev/random` は、カーネルが見積もった「エントロピーの残量」が減るとブロックしました。
  これが「urandom は質が落ちる、random のほうが本物」という誤解を生みました。
  実際には、いったん十分な種を得た CSPRNG の出力は、使っても「減って」弱くなるものではありません。
  Linux 5.6 でブロックするプールは取り除かれ、`/dev/random` の読み出しは flags 0 の getrandom と同じ振る舞いになりました（[LWN](https://lwn.net/Articles/808575/)）。
  **危ないのは乱数を使いすぎることではなく、種が揃う前の起動直後に鍵を作ること**です。
</Callout>

起動直後の問題は、実際に起きています。2012 年の調査では、インターネット上の **TLS ホストの 0.50%、SSH ホストの 0.03% の RSA 秘密鍵**を、公開鍵だけから計算で求められました。原因は主に、ルータやファイアウォールのような画面もキーボードもない機器が、**初回起動の直後、乱数の種が揃う前に鍵を作っていた**ことでした（[factorable.net](https://factorable.net/)）。同じ種から作られた鍵は、素数を共有してしまいます。

## 手元で: 種が小さいと、鍵は数えられる

乱数の失敗として最も有名なのが、Debian の OpenSSL の事件です（[DSA-1571](https://lists.debian.org/debian-security-announce/2008/msg00152.html)、CVE-2008-0166）。

- 2006 年 9 月 17 日に Debian の不安定版に入った 0.9.8c-1 から、2008 年 5 月 13 日の公表まで、Debian とその派生で作られた鍵が影響を受けた
- きっかけは、メモリ検査ツールの警告を消すために、OpenSSL の `md_rand.c` の `MD_Update(&m, buf, j);` という 2 行をコメントアウトしたこと。これで**乱数のプールに種がほとんど混ざらなくなり、プロセス ID だけが種として残りました**（[Debian Wiki](https://wiki.debian.org/SSLkeys)）
- プロセス ID は最大 32,767 通りです。鍵の種類・長さ・アーキテクチャごとに、**作られうる鍵がその数しかなくなりました**
- SSH の鍵、OpenVPN の鍵、DNSSEC の鍵（第 61 回）、証明書の鍵、TLS のセッション鍵が対象で、公表は「作り直すこと」を強く求めました

プロセス ID を種にした鍵を、全部の種を試して当てる模型を書いてみます。`random.Random` を使うのは、種が同じなら同じ列が出ることを見せるためです。

```python
import random, time, secrets

def make_key(seed):
    r = random.Random(seed)
    return r.getrandbits(128).to_bytes(16, "big")

victim_pid = secrets.randbelow(32768)
key = make_key(victim_pid)
print("key      =", key.hex())

t = time.perf_counter()
for pid in range(32768):
    if make_key(pid) == key:
        print("found pid =", pid, "key =", make_key(pid).hex())
        break
print(f"elapsed  = {time.perf_counter() - t:.3f}s")
```

```
key      = 446182349c1316bd89384fc6c5341d83
found pid = 14609 key = 446182349c1316bd89384fc6c5341d83
elapsed  = 0.108s
```

見かけは 128 ビットの鍵ですが、実際の選択肢は 32,768 通りしかないので、**0.1 秒で見つかります**。鍵の長さは強さを保証しません。強さを決めるのは、**その鍵が何通りの中から選ばれたか**です。

<Callout type="warn" title="よくある誤解: 時刻や PID を混ぜれば十分に推測しにくい">
  「現在時刻のミリ秒とプロセス ID を種にすれば、外からは分からない」と考えがちです。
  しかし起動時刻はおおよそ推測でき、PID の範囲は狭く、組み合わせても数十ビットにしかなりません。
  上の実験のとおり、その程度は手元の PC で数え上げられます。
  **種を自分で作らず、OS の CSPRNG をそのまま使う**のが唯一の安全な方法です。
</Callout>

## 鍵から鍵を作る: HKDF

実際のプロトコルでは、1 つの秘密から**用途の違う鍵を何本も**作ります。第 108 回の鍵交換で得られる共有秘密は 1 つですが、TLS はそこから「クライアント→サーバ」と「サーバ→クライアント」の暗号鍵、ハンドシェイク用と通信用の鍵を分けて作ります。同じ鍵を 2 方向で使うと、第 107 回で見た nonce の重複が起きやすくなるからです。

このための部品が **HKDF**（[RFC 5869](https://www.rfc-editor.org/rfc/rfc5869.html)）で、第 106 回の HMAC を 2 段で使います。

```
         salt（秘密でなくてよい）
           │
IKM ──▶ Extract = HMAC(salt, IKM) ──▶ PRK（偏りのない 32 バイト）
（鍵交換の結果など）                     │
                                          ▼
                     info="client to server" ──▶ Expand ──▶ 鍵 A
                     info="server to client" ──▶ Expand ──▶ 鍵 B
```

- **Extract** は、偏りのある入力（Diffie-Hellman の結果など）から、偏りのない固定長の鍵を取り出します。RFC は、入力が Diffie-Hellman の値なら Extract を「省略すべきでない」としています（[RFC 5869 3.3](https://www.rfc-editor.org/rfc/rfc5869.html#section-3.3)）
- **Expand** は、`info` に書いた用途ごとに別の鍵を作ります。`info` は鍵を**用途と文脈に結び付ける**ためのものです（[RFC 5869 3.2](https://www.rfc-editor.org/rfc/rfc5869.html#section-3.2)）

cryptography 48 で確かめます。

```python
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.kdf.hkdf import HKDF

shared = bytes.fromhex("4f" * 32)   # 鍵交換で得た共有秘密のつもり
salt = b"\x00" * 16
def hkdf(info):
    return HKDF(algorithm=hashes.SHA256(), length=32, salt=salt, info=info).derive(shared)
```

```
c->s   95999225b86cd2c6af24a387a53cd13065f3dc1df4fe71842bb33f6dfc09429c
s->c   5c57e26ebee4e22e07827b429575c05787c00429d8ffffa38846d6fc99a965ac
c->s   95999225b86cd2c6af24a387a53cd13065f3dc1df4fe71842bb33f6dfc09429c (もう一度)
```

同じ入力と同じ `info` からは同じ鍵が、`info` を変えると無関係に見える鍵が出ます。両端が同じ共有秘密を持っていれば、**鍵を送り合わずに同じ鍵の組を作れる**わけです。第 115 回で、TLS 1.3 の鍵スケジュールがこの HKDF を何段も重ねたものであることを見ます。

## パスワードから鍵を作るのは別の道具

HKDF の RFC は、はっきりと「HKDF はエントロピーを増やせない」と書き、パスワードのような推測しやすい入力には別の仕様（PKCS #5）を使うよう勧めています（[RFC 5869 4](https://www.rfc-editor.org/rfc/rfc5869.html#section-4)）。

違いは、**入力の散らばり**です。鍵交換の結果は 2²⁵⁶ 通りの中から選ばれますが、人が覚えられるパスワードは、辞書と規則で絞り込めます。攻撃者は候補を 1 つずつ試せばよいので、守る側にできるのは **1 回の試行を重くすること**だけです。

| 道具 | 重くするもの | 仕様 |
| --- | --- | --- |
| PBKDF2 | 反復回数（CPU の時間） | [RFC 8018](https://www.rfc-editor.org/rfc/rfc8018.html) |
| scrypt | 時間とメモリ | [RFC 7914](https://www.rfc-editor.org/rfc/rfc7914.html) |
| Argon2id | 時間とメモリ（並列度も指定） | [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html) |

メモリを要求するのは、GPU や専用回路で大量に並べて試す攻撃を高くつかせるためです。手元の Mac（Apple Silicon）で、OWASP の Password Storage Cheat Sheet が示すパラメータ（[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)）を使って 1 回あたりの時間を測りました。

```
SHA-256 1 回                      0.001 ms / 回
HKDF-SHA256                      0.005 ms / 回
PBKDF2-SHA256 600000 回         170.662 ms / 回
scrypt N=2^17 r=8 p=1         1300.100 ms / 回
Argon2id m=19MiB t=2 p=1       124.117 ms / 回
```

HKDF はパスワードの鍵導出より**数万倍速い**ことになります。鍵交換の後で使うならこの速さは長所ですが、パスワードに使えば、攻撃者にとっても数万倍速く試せるということです。

<Callout type="warn" title="よくある誤解: パスワードを SHA-256 か HKDF に通せば鍵になる">
  `key = sha256(password)` は 32 バイトの鍵の形をしていますが、選ばれうる値はパスワードの候補の数しかありません。
  第 106 回のハッシュも HKDF も**速く計算できるように作られている**ので、候補の総当たりを助けてしまいます。
  パスワードから暗号鍵を作るとき（暗号化 PKCS#8 のパスフレーズ、第 110 回）も、パスワードを保存するときも、
  使うのは PBKDF2・scrypt・Argon2id のような**わざと遅い**導出です。パスワードの保存は第 129 回で詳しく見ます。
</Callout>

## 鍵をどこに置くか

良い乱数で鍵を作っても、それをどこかに置かなければ使えません。置き場所には段階があります。

| 段階 | 例 | 鍵を取り出せるか | 誰が使えるか | 使った記録 |
| --- | --- | --- | --- | --- |
| 1. コードや設定に直書き | リポジトリの `config.yaml` | 読める人は誰でも | リポジトリに触れる全員 | なし |
| 2. 環境変数、ファイル | `.env`、権限 0600 の鍵ファイル | そのホストで読める人 | 同じ uid（第 43 回）、root | なし |
| 3. 秘密情報の管理サービス | AWS Secrets Manager、Vault | 権限があれば取り出せる | IAM やポリシーで絞る | 取り出しが残る |
| 4. KMS | AWS KMS、Cloud KMS | **取り出せない**。API で使うだけ | 鍵ポリシーで絞る | 1 回ごとの操作が残る |
| 5. 専用ハードウェア | HSM、TPM、Secure Enclave | **取り出せない**。そのチップの中で使うだけ | そのチップに届くプロセス | 機器による |

3 までは、**鍵そのものが使う側のメモリに渡ります**。4 と 5 は、鍵を渡さずに「これを暗号化して」「これに署名して」という依頼だけを受け付けます。

- AWS KMS の鍵は、FIPS 140-3 のセキュリティレベル 3 の認定を受けた HSM の外に**暗号化されずに出ることがありません**。使うには KMS の API を呼ぶしかありません（[AWS KMS](https://docs.aws.amazon.com/kms/latest/developerguide/kms-cryptography.html)）
- TPM の鍵は、TPM の外では使えないように設定でき、証明書の RSA 秘密鍵を TPM に結び付けると**エクスポートできなくなります**（[Microsoft Learn](https://learn.microsoft.com/en-us/windows/security/hardware-security/tpm/trusted-platform-module-overview)）
- Apple の Secure Enclave のハードウェア鍵は、Secure Enclave の中の OS からさえ見えないように作られています（[Apple Platform Security](https://support.apple.com/guide/security/secure-enclave-sec59b0b31ff/web)）。第 129 回のパスキーは、この仕組みの上に載っています

**取り出せないことの価値**は、侵入された後にはっきりします。鍵ファイルを盗まれたら、攻撃者はそれを持ち帰って、好きなときに好きなだけ使えます。気づいたときには、どこでいくつ署名されたか分かりません。KMS や HSM の鍵なら、攻撃者にできるのは**侵入している間に、正規の経路で使うこと**だけです。権限を止めればその場で使えなくなり、何回使われたかが記録に残ります。

<Callout type="warn" title="よくある誤解: HSM や KMS に入れれば、鍵は安全">
  取り出せないのは**鍵の値**であって、**鍵を使う権限**ではありません。
  アプリケーションの権限を奪った攻撃者は、KMS に「これを復号して」「これに署名して」と頼めます。
  鍵は盗まれていなくても、その間に作られた署名や復号されたデータは本物です。
  HSM は「漏れた鍵を回収できない」という最悪の事態を防ぐものであって、
  **誰がいつ使えるかという権限の設計と、使われ方の監視**は別に要ります。
</Callout>

## エンベロープ暗号化: 大きなデータは手元で、鍵だけを KMS で

KMS の鍵が外に出ないなら、10 GB のファイルを暗号化するには、10 GB を KMS に送る必要があるのでしょうか。実際には、AWS KMS の `Encrypt` が受け付ける平文は **4,096 バイトまで**です（[AWS KMS Encrypt](https://docs.aws.amazon.com/kms/latest/APIReference/API_Encrypt.html)）。

そこで使うのが**エンベロープ暗号化**です。データを**データ鍵**で暗号化し、そのデータ鍵を**別の鍵**で暗号化します（[AWS KMS](https://docs.aws.amazon.com/kms/latest/developerguide/kms-cryptography.html#enveloping)）。

```
        KMS の中                               アプリケーション
  ┌──────────────────┐   GenerateDataKey
  │ ルート鍵（出ない） │ ──────────────▶ 平文のデータ鍵 + 包んだデータ鍵
  └──────────────────┘                        │
                                              ├─ 平文のデータ鍵で AES-GCM ─▶ 暗号文（大きい）
                                              ├─ 平文のデータ鍵は捨てる
                                              └─ 包んだデータ鍵を暗号文の隣に保存（小さい）

  復号: 包んだデータ鍵を KMS に送る ─▶ 平文のデータ鍵が返る ─▶ 手元で暗号文を復号
```

- 重いデータの暗号化は手元の CPU（第 107 回の AES-NI）で済み、KMS には 32 バイトの鍵だけが行き来します
- 包んだデータ鍵は、**暗号文と一緒に置いてかまいません**。ルート鍵がなければ開けられないからです
- ルート鍵を替えるときも、**データを暗号化し直さず、データ鍵を包み直すだけ**で済みます
- ルート鍵だけは、どこかで暗号化されずに持っていなければなりません。それを HSM の中に置くのが KMS です

## 手元で: エンベロープ暗号化の模型

KMS の役割を、鍵を外に出さず「包む」「ほどく」だけを引き受けるクラスで真似します。包むときの AES-GCM の関連データ（第 107 回）に、何のデータの鍵かという文脈を入れます。AWS KMS の encryption context と同じ考え方で、`Encrypt` と同じ文脈を渡さないと `Decrypt` は失敗します（[AWS KMS Encrypt](https://docs.aws.amazon.com/kms/latest/APIReference/API_Encrypt.html)）。

```python
class ToyKMS:
    def __init__(self):
        self._versions = {1: AESGCM.generate_key(256)}
        self.current = 1
    def rotate(self):
        self.current += 1
        self._versions[self.current] = AESGCM.generate_key(256)
    def generate_data_key(self, context):
        dk = AESGCM.generate_key(256)
        return dk, self.wrap(dk, context)
    def wrap(self, dk, context):
        n = os.urandom(12)
        v = self.current
        return v.to_bytes(4, "big") + n + AESGCM(self._versions[v]).encrypt(n, dk, context)
    def unwrap(self, blob, context):
        v = int.from_bytes(blob[:4], "big")
        return AESGCM(self._versions[v]).decrypt(blob[4:16], blob[16:], context)
```

10 MiB のデータを暗号化し、ルート鍵を替えて包み直し、最後に別の文脈でほどこうとします。

```
暗号文         10485776 bytes  sha256 881fa5a51794d222
包んだデータ鍵 64 bytes  root key v 1
ローテーション後 64 bytes  root key v 2
暗号文は変わらない sha256 881fa5a51794d222
復号できた     True
古い包みも     True
別の文脈では  InvalidTag
```

ローテーションで動いたのは 64 バイトだけで、10 MiB の暗号文には触れていません。文脈を `column=email` から `column=phone` に変えると、第 107 回で見た AEAD の検証で弾かれます。包んだデータ鍵を**別の行や別の列にこっそり付け替える**ことを、これで防げます。

もう 1 つ、見落としやすい行があります。**古い包みも `True`** です。

## ローテーションと失効は別のこと

ローテーションは「これから使う鍵を新しくすること」で、失効は「ある鍵を使えなくすること」です。

AWS KMS の自動ローテーションは、既定で 365 日ごとに新しい鍵の材料を作ります。暗号化には新しい材料を使い、**復号には暗号化に使った古い材料を自動で選びます**。古い材料は KMS の鍵を削除するまで残ります（[AWS KMS rotate](https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html)）。そうしなければ、過去のデータが読めなくなるからです。同じページは、ローテーションは**データ鍵を替えず、データを暗号化し直さない**ので、漏れたデータ鍵の影響は軽くならない、とも明記しています。

<Callout type="warn" title="よくある誤解: 定期的にローテーションしていれば、漏洩しても安心">
  ローテーションは、1 本の鍵で暗号化する量を抑え、漏れたときに**これから先**の被害を区切るものです。
  漏れた鍵で作られた過去の暗号文や署名は、そのまま有効です。
  上の実験で古い包みがほどけたように、古い鍵が残っていれば、それを持つ者は今も読めます。
  漏れたと分かったときにするのは、ローテーションではなく**失効**（その鍵を無効にする）と、
  その鍵で守っていたデータの暗号化のし直しや、その鍵の署名を信じない手当てです。
</Callout>

署名の鍵では、失効は**検証する側**に伝えなければ効きません。公開鍵を受け取った側が、それをまだ信じているからです。

| 鍵の使われ方 | 検証する側に「もう信じるな」を伝える方法 | 詳しく見る回 |
| --- | --- | --- |
| TLS の証明書の鍵 | 証明書の失効（CRL、OCSP）、短命な証明書 | 第 114 回 |
| SSH のホスト鍵・ユーザ鍵 | known_hosts や authorized_keys から消す、証明書の期限 | 第 118、119 回 |
| JWT の署名鍵 | JWKS から外す | 第 131、139 回 |
| DNSSEC の鍵 | 親の DS を替える | 第 61 回 |

署名鍵を替える順序は、どれも同じ形になります。**新しい公開鍵を先に配り、配り終えてから新しい秘密鍵で署名し始め、古い署名が期限切れになってから古い公開鍵を外す**。順序を逆にすると、新しい鍵をまだ知らない検証側で失敗します。第 139 回で、IdP の署名鍵を実際にこの順序で替えます。

## 秘密情報はどこから漏れるか

鍵やパスワード、API トークンのような秘密情報は、アルゴリズムの弱点よりも、**置き方と扱い方**から漏れます。

**リポジトリ。** GitGuardian の 2026 年の報告では、2025 年に公開の GitHub のコミットに新たに含まれた秘密情報は 2,865 万件で、前年から 34% 増えました。2022 年に見つかって有効だった秘密情報を 2026 年 1 月に調べ直すと、**64% 以上がまだ有効**でした（[GitGuardian](https://blog.gitguardian.com/the-state-of-secrets-sprawl-2026/)）。GitHub は 2024 年 3 月から、個人アカウントの新しい公開リポジトリで、既知の形式の秘密情報を含む push を止める機能を既定で有効にしています（[GitHub Changelog](https://github.blog/changelog/2024-03-11-secret-scanning-and-push-protection-are-enabled-by-default-on-new-public-repositories/)）。

コミットしてしまった後で履歴を書き換えても、クローンやフォーク、キャッシュに残ります。GitHub のドキュメントも、**まず秘密情報を失効させるかローテーションすること**を最初の手順にしています（[GitHub Docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)）。履歴を消すのは後始末です。

**環境変数。** 設定を環境変数で渡すのは一般的ですが、環境変数は秘密を守る仕組みではありません。

- 子プロセスにそのまま受け継がれる
- Linux では `/proc/<pid>/environ` に起動時の環境が残り、ptrace で読める権限があれば読める（[proc_pid_environ(5)](https://man7.org/linux/man-pages/man5/proc_pid_environ.5.html)）
- 「設定を全部表示する」デバッグ出力やエラー報告に、まとめて載りやすい

**ログと例外。** 接続文字列に埋め込んだパスワードは、接続に失敗したときの例外メッセージに乗ってログへ流れます。

3 つをまとめて確かめます。

```python
os.environ["DB_PASSWORD"] = "hunter2-not-real"

print(subprocess.run(["sh", "-c", "env | grep DB_"], capture_output=True, text=True).stdout, end="")
logging.debug("config=%s", {k: v for k, v in os.environ.items() if k.startswith("DB_")})
try:
    connect(f"postgres://app:{os.environ['DB_PASSWORD']}@db:5432/app")
except Exception:
    print(traceback.format_exc().strip().splitlines()[-1])
```

```
DB_PASSWORD=hunter2-not-real
DEBUG config={'DB_PASSWORD': 'hunter2-not-real'}
ConnectionError: cannot connect to postgres://app:hunter2-not-real@db:5432/app
```

どれも、コードに悪意はありません。**秘密情報を普通の文字列として扱うと、普通の文字列が流れる場所すべてに流れます**。ほかにも、CI のログ、コアダンプ、クライアントアプリに埋め込んだ API キー、チャットやチケットへの貼り付けがよくある経路です。

いちばん効く対策は、**漏れても困らないほど短命な秘密にすること**です。Vault のデータベース用の機能は、サービスごとに期限付きの DB の認証情報をその場で作り、期限が来れば無効にします（[Vault](https://developer.hashicorp.com/vault/docs/secrets/databases)）。第 140 回で見るワークロード ID は、そもそも長期の秘密を持たせずに、実行環境が発行する短命なトークンをクラウドの認証情報に交換します。第 172 回の Sigstore が、署名のたびに短命な証明書を発行するのも同じ考え方です。

## 第16章の部品が、この回に何を頼っていたか

| 部品 | 何を保証するか | この回の何を前提にしているか |
| --- | --- | --- |
| ハッシュ（第 106 回） | 同じ入力から同じ要約。衝突を見つけにくい | 鍵を使わない。パスワードに使うなら遅い導出が要る |
| MAC（第 106 回） | 鍵を共有する者同士での改ざん検出 | 共有鍵が推測できないこと、両端で安全に保管されていること |
| AEAD（第 107 回） | 機密性と改ざん検出 | 鍵が乱数で作られること、nonce が重ならないこと |
| 鍵交換（第 108 回） | 盗聴者に知られずに共有秘密を作る | 一時的な秘密鍵が乱数で作られること、結果を HKDF で鍵にすること |
| 署名（第 109 回） | この鍵で署名されたこと | 秘密鍵が取り出されないこと、漏れたら失効を伝えられること |
| 鍵ファイル（第 110 回） | 鍵を運び、ペアを確かめる | ファイルを置く場所の権限、パスフレーズの導出の遅さ |

表の右の列は、どれもアルゴリズムの外にあります。**暗号の部品は、鍵の作り方と置き方が正しいという約束の上でだけ、左の列を保証します**。

そして、もう 1 つ、この章の部品がどれも答えていない問いがあります。第 108 回の鍵交換は、相手と秘密を共有しますが、**その相手が誰なのかを知りません**。第 109 回の署名は「この鍵で署名された」ことを示しますが、**その鍵が誰のものかは言いません**。この回で鍵を安全に作って置いても、見知らぬ相手の公開鍵を本物だと信じる理由は、まだどこにもありません。

## まとめ

- アルゴリズムは公開されているので、強さは鍵が推測できないことと、鍵が持つべき者だけに使えることの 2 つで決まる
- 暗号用の乱数は OS の CSPRNG からもらう。Linux では getrandom が入口で、言語の `secrets`、`crypto.getRandomValues`、`crypto/rand` がそれを使う。`random` や `Math.random` は予測できる
- `/dev/random` のほうが安全というのは誤解。危ないのは種が揃う前の起動直後で、2012 年の調査では組み込み機器の鍵が大量に計算で求められた
- Debian の OpenSSL の事件（2006〜2008）では、種がプロセス ID だけになり、作られうる鍵が 3 万通りほどに減った。鍵の長さではなく、何通りから選ばれたかが強さになる
- HKDF は、強い秘密から用途ごとの鍵を作る（Extract と Expand）。パスワードには使えず、PBKDF2・scrypt・Argon2id のような遅い導出を使う
- 鍵の置き場所は、直書き→環境変数やファイル→秘密情報の管理サービス→KMS→HSM・TPM・Secure Enclave の順に強くなる。KMS から先は鍵を取り出せず、使う権限だけを管理する
- 取り出せない鍵でも、使う権限を奪われれば使われる。権限の設計と監視が別に要る
- エンベロープ暗号化は、データをデータ鍵で暗号化し、データ鍵だけを KMS の鍵で包む。ルート鍵を替えても包み直すのは小さなデータ鍵だけで済む
- ローテーションは先の被害を区切り、失効は鍵を使えなくする。漏洩への対応は失効で、署名鍵の失効は検証する側に伝えて初めて効く
- 秘密情報はリポジトリ、環境変数、ログ、例外から漏れる。いちばん効くのは短命にすること

ここまでの部品で、秘密を守り、改ざんを見つけ、「この鍵で署名された」と言えるようになりました。しかし、どの部品も相手が誰かを知りません。次の第17章では、公開鍵と名前を結び付ける証明書から始めて、見知らぬ相手を確かめて話す仕組みを組み立てます。
