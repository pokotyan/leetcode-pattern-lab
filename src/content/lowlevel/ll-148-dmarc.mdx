## SPF も DKIM も pass しているのに

次のメールを受け取ったとします。

```
Return-Path: <x@attacker.example>
DKIM-Signature: v=1; a=rsa-sha256; d=attacker.example; s=s1; ...
From: billing@example.com
Subject: Invoice
```

送信元の IP アドレスは `attacker.example` の SPF に載っているので **SPF は pass**。署名も `attacker.example` の鍵で正しく検証できるので **DKIM も pass** です。どちらの検査も、嘘はついていません。

それでも、利用者のメールソフトに表示される差出人は `billing@example.com` です。

第 146 回で見たとおり、SPF が確かめるのは SMTP の `MAIL FROM` のドメインでした。第 147 回で見たとおり、DKIM が言えるのは「`d=` のドメインが責任を持つ」ことだけでした。**どちらも、本文の `From:` には一度も触れていません。** 攻撃者は自分のドメインで SPF と DKIM を正しく設定し、`From:` だけを他人の名前にすればよいのです。

この隙間を埋めるのが **DMARC**（Domain-based Message Authentication, Reporting, and Conformance）です。やっていることは、次の 1 文に尽きます。

**「`From:` のドメインと、認証に通ったドメインが揃っているか」を確かめ、揃っていなければ、`From:` のドメインの持ち主が決めた方針に従う。**

この回では、この「揃っている」の意味、揃っているかを判定するための「組織ドメイン」の決め方、持ち主が方針と報告先を公開する DNS のレコード、そしてそれを実際の運用に載せるまでを見ます。

## 3 つの名前

まず、1 通のメールに登場するドメインを並べます。

| 名前 | どこにあるか | 誰が確かめるか | 利用者に見えるか |
| --- | --- | --- | --- |
| `MAIL FROM` のドメイン | SMTP のエンベロープ（受信後は `Return-Path:`） | SPF（第 146 回） | ほぼ見えない |
| `d=` のドメイン | `DKIM-Signature:` ヘッダ | DKIM（第 147 回） | 見えない |
| `From:` のドメイン | 本文のヘッダ | **DMARC** | **見える** |

DMARC の仕様では、`From:` のドメインを **Author Domain**（作成者のドメイン）、SPF か DKIM で認証に通ったドメインを **Authenticated Identifier**（認証済みの識別子）と呼びます（[RFC 9989 3.2](https://www.rfc-editor.org/rfc/rfc9989.html#section-3.2)）。

DMARC は新しい暗号も新しい検査も持ち込みません。**すでにある 2 つの検査結果と、利用者が見る 1 つの名前とを突き合わせるだけ**です。だからこそ、SPF と DKIM が先に整っていないと何もできません。

```
            SPF                         DKIM
   MAIL FROM のドメインを認証     d= のドメインを認証
              │                           │
              └──────────┐   ┌────────────┘
                         ▼   ▼
               From: のドメインと揃っているか   ← DMARC
                         │
             揃っていない → From: の持ち主の方針（p=）
```

## アラインメント: 揃っているとは

「揃っている」ことを **アラインメント**（Identifier Alignment）と呼びます。判定の方法は 2 つあります（[RFC 9989 3.2.10](https://www.rfc-editor.org/rfc/rfc9989.html#section-3.2.10)）。

- **strict**: `From:` のドメインと認証済みのドメインが**完全に一致する**
- **relaxed**: 両者の**組織ドメイン**（後述。おおむね「登録したドメイン」）が一致する

既定は relaxed で、SPF 側を `aspf=`、DKIM 側を `adkim=` で個別に strict にできます。

| `From:` | 認証済みのドメイン | relaxed | strict |
| --- | --- | --- | --- |
| `example.com` | `example.com` | 揃う | 揃う |
| `example.com` | `bounce.example.com`（SPF） | 揃う | 揃わない |
| `news.example.com` | `example.com`（DKIM） | 揃う | 揃わない |
| `example.com` | `esp.example.net` | 揃わない | 揃わない |

そして判定の規則は、**どちらか 1 つが揃って pass していれば DMARC は pass** です（[RFC 9989 5.3.5](https://www.rfc-editor.org/rfc/rfc9989.html#section-5.3.5)）。

```
DMARC pass ⇔ (SPF が pass かつ MAIL FROM が From: と揃う)
             または
             (DKIM が pass かつ d= が From: と揃う)
```

<Callout type="warn" title="よくある誤解: SPF と DKIM の両方が pass しないと DMARC は pass しない">
  必要なのは「どちらか一方が、From: と揃ったうえで pass すること」です。
  逆に、両方が pass していても、どちらも From: と揃っていなければ DMARC は fail です。冒頭の例がこれです。
  「SPF は pass なのに DMARC が fail」という問い合わせの多くは、SPF が配信サービスのドメインで pass しているだけ、という状況です。
  認証の結果を見るときは、**pass かどうかと、何のドメインで pass したか**を必ず分けて読みます。
</Callout>

実際には、揃えやすいのは DKIM のほうです。SPF の `MAIL FROM` はバウンスの受け取り先でもあるので、配信サービスを使うとそのサービスのドメインになりがちです。一方 DKIM の `d=` は、公開鍵を自分のドメインに置けば自分の名前で署名してもらえます（第 151 回で、配信サービスへの委任の具体的なやり方を見ます）。さらに、後で見るとおり**転送されると SPF はほぼ必ず壊れる**ので、DKIM で揃えておくことは運用上ほぼ必須です。

## 組織ドメインをどう決めるか

relaxed の判定には「組織ドメイン」が要ります。`news.example.com` と `bounce.example.com` は同じ組織だと言いたい。では `a.github.io` と `b.github.io` はどうでしょうか。`example.co.jp` と `other.co.jp` は。

名前の形だけでは分かりません。`co.jp` や `github.io` は、その下を**別々の持ち主に貸し出す**ための名前です。こうした名前を **Public Suffix**（公開接尾辞）と呼び、その一覧が有志の管理する **Public Suffix List**（PSL、[publicsuffix.org](https://publicsuffix.org/)）です。

2015 年の最初の仕様 [RFC 7489](https://www.rfc-editor.org/rfc/rfc7489.html) は、組織ドメインを「PSL を使って、公開接尾辞の 1 つ下」と決めていました。ただし、どの PSL をどれくらいの頻度で取り直すかは決めておらず、受信側ごとに判定がずれうることを仕様自身が認めていました（[RFC 9989 4.10](https://www.rfc-editor.org/rfc/rfc9989.html#section-4.10) の経緯の説明）。

2026 年 5 月に出た新しい版 [RFC 9989](https://www.rfc-editor.org/rfc/rfc9989.html) は、これを **DNS Tree Walk** に置き換えました。外部の一覧に頼らず、**DNS そのものを上にたどって DMARC のレコードを探す**方式です。

```
From: のドメイン a.mail.example.com のとき

  _dmarc.a.mail.example.com   なし
  _dmarc.mail.example.com     なし
  _dmarc.example.com          あり  ← ここで方針が見つかる
  _dmarc.com                  なし
```

見つかったレコードのうち、**ラベルの数がいちばん少ない名前**が組織ドメインになります（[RFC 9989 4.10.2](https://www.rfc-editor.org/rfc/rfc9989.html#section-4.10.2)）。持ち主が明示したいときのために `psd=` タグがあり、`psd=n` なら「ここが組織ドメイン」、`psd=y` なら「ここは公開接尾辞なので、その 1 つ下が組織ドメイン」と宣言できます。

たどる回数には上限があります。攻撃者がラベルを何百個も並べた `From:` を送り、受信側に大量の DNS 問い合わせをさせることができるからです。RFC 9989 は、ラベルが 8 個を超える名前は途中を飛ばして **最大 8 回**の問い合わせで済むように決めています。執筆時点で使われているのは最大 7 ラベルだったので、少し余裕をみて 8 にした、と理由まで書かれています。

<Callout type="note" title="第 146 回の 10 回、ここでは 8 回">
  SPF の問い合わせ 10 回の上限と同じく、**受信側が送信側の言いなりに DNS を引かされる**ことへの歯止めです。
  メール認証の仕様には、この種の上限がいくつも出てきます。DNS を「誰でも書ける設定置き場」として使う以上、
  書かれた内容をたどる側が、どこかで打ち切らなければならないからです。
</Callout>

## 方針のレコードを読む

ドメインの持ち主は、`_dmarc.<ドメイン>` の TXT に方針を書きます（第 58 回で見たアンダースコアの慣習です）。

```
_dmarc.example.com.  IN  TXT  "v=DMARC1; p=reject; rua=mailto:dmarc@example.com"
```

RFC 9989 で使えるタグは次のとおりです（[RFC 9989 4.7](https://www.rfc-editor.org/rfc/rfc9989.html#section-4.7)）。

| タグ | 意味 | 既定 |
| --- | --- | --- |
| `v` | 版。`DMARC1` で始まらなければ無視 | 必須 |
| `p` | fail したメールの扱い: `none` / `quarantine` / `reject` | 無ければ `none` 扱い |
| `sp` | 存在するサブドメインの扱い | `p` と同じ |
| `np` | **存在しない**サブドメインの扱い（新設） | `sp`、無ければ `p` |
| `adkim` / `aspf` | DKIM / SPF のアラインメント: `r`（relaxed）/ `s`（strict） | `r` |
| `rua` | 集計報告の送り先 | なし |
| `ruf` | 失敗報告の送り先 | なし |
| `fo` | 失敗報告を出す条件 | `0` |
| `psd` | 公開接尾辞かどうか: `y` / `n` / `u`（新設） | `u` |
| `t` | テスト中: `y` / `n`（新設） | `n` |

`p` の 3 つの値は、仕様の言葉では「持ち主の評価」です。`none` は何の意思表示もしない、`quarantine` は怪しいと考える（迷惑メールのフォルダへ、など）、`reject` は明らかな失敗と考える（SMTP の段階で拒否する、など）。**あくまで受信側への依頼**である点は、後で効いてきます。

どのレコードの、どのタグが使われるかは次のように決まります（[RFC 9989 4.10.1](https://www.rfc-editor.org/rfc/rfc9989.html#section-4.10.1)）。

1. `_dmarc.<From: のドメイン>` にレコードがあれば、その `p`
2. 無ければ Tree Walk で組織ドメインのレコードを探し、`From:` のドメインが**存在すれば `sp`、存在しなければ `np`**（どちらも無ければ `p`）
3. どこにも無ければ、**DMARC は適用しない**

`np` が新設されたのは、攻撃者が `secure-login.example.com` のような**存在しない**サブドメインを `From:` に使う手口がよく見られるからです。実在するサブドメインの運用に影響を与えずに、存在しない名前だけを厳しく扱えます。

### `pct` が消えて `t` になった

RFC 7489 には `pct=` というタグがあり、fail したメールのうち何 % に方針を適用するかを 0〜100 で指定できました。段階的に厳しくするための仕組みです。

RFC 9989 はこれを**廃止**しました（[RFC 9989 付録 A.6](https://www.rfc-editor.org/rfc/rfc9989.html#appendix-A.6)）。理由は、0 と 100 以外の値が実装ごとにばらばらにしか守られなかったことです。一方で `pct=0` には、メーリングリストなどの中継者が「このドメインはこれから厳しくなるので、From: を書き換えておこう」と判断する合図として、意図しない価値が生まれていました。

そこで、**0 と 100 の 2 値だけを残して名前を変えた**のが `t=` です。`t=y` のとき、受信側は指定より 1 段階ゆるい方針を当てることが期待されます。`p=quarantine; t=y` なら `none` 相当、`p=reject; t=y` なら `quarantine` 相当です。

<Callout type="note" title="仕様の状態: Informational から Standards Track へ">
  RFC 7489（2015 年）は、IETF の標準ではなく **Informational**（情報提供）の RFC でした。事実上の標準として 10 年近く使われながら、
  IETF の合意を経た規格ではなかったのです。
  2026 年 5 月、改訂版（通称 DMARCbis）が **Standards Track** の 3 つの RFC として出ました。本体の [RFC 9989](https://www.rfc-editor.org/rfc/rfc9989.html)、
  集計報告の [RFC 9990](https://www.rfc-editor.org/rfc/rfc9990.html)、失敗報告の [RFC 9991](https://www.rfc-editor.org/rfc/rfc9991.html) です。いずれも RFC 7489 を廃止します。
  レコードは引き続き `v=DMARC1` で始まり、古い `pct=` などは無視されるだけなので、既存のレコードが壊れることはありません。
  ただし受信側の実装が新しい版に追いつくには時間がかかります。**執筆時点（2026 年 9 月）では、PSL で判定する受信側と Tree Walk で判定する受信側が混在している**と考えておくのが安全です。
</Callout>

## 報告: 持ち主に結果を返す

DMARC の名前の R は Reporting です。**受信側が、そのドメインを名乗るメールをどう判定したかを、持ち主に報告する**仕組みがあります。これが DMARC を SPF や DKIM と決定的に違うものにしています。SPF も DKIM も、失敗は受信側の中で起きて終わりでした。DMARC では、持ち主が**自分の名前がどこから、どれだけ使われているか**を知ることができます。

### 集計報告（rua）

受信側は 1 日ごとなどの単位で、送信元 IP と判定結果ごとの件数を XML にまとめ、`rua=` の宛先へ送ります（[RFC 9990](https://www.rfc-editor.org/rfc/rfc9990.html)）。仕様の例（付録 B.1）を抜粋します。

```xml
<feedback xmlns="urn:ietf:params:xml:ns:dmarc-2.0">
  <report_metadata>...</report_metadata>
  <policy_published>
    <domain>example.com</domain>
    <p>quarantine</p> <sp>none</sp> <np>none</np>
    <testing>n</testing> <discovery_method>treewalk</discovery_method>
  </policy_published>
  <record>
    <row>
      <source_ip>192.0.2.123</source_ip> <count>123</count>
      <policy_evaluated>
        <disposition>pass</disposition> <dkim>pass</dkim> <spf>fail</spf>
      </policy_evaluated>
    </row>
    <identifiers>
      <envelope_from>example.com</envelope_from> <header_from>example.com</header_from>
    </identifiers>
    <auth_results>
      <dkim><domain>example.com</domain><result>pass</result><selector>abc123</selector></dkim>
      <spf><domain>example.com</domain><result>fail</result></spf>
    </auth_results>
  </record>
</feedback>
```

読み方はこうです。`192.0.2.123` から `example.com` を名乗るメールが 123 通届いた。SPF は fail したが、DKIM が `example.com` で pass して揃ったので、DMARC としては pass し、そのまま配送した。`policy_evaluated` が DMARC から見た結果（アラインメント込み）、`auth_results` が SPF と DKIM それぞれの素の結果です。

SPF だけ fail して DKIM が pass する行は、**転送**の典型的な跡です。転送するサーバは自分の IP から送り直すので、元のドメインの SPF には載っていません。一方で本文を変えなければ DKIM の署名は残ります。新しい版では、方針をどう見つけたか（`discovery_method` が `treewalk` か `psl` か）も報告に載るようになりました。

実際の集計報告は、大手の受信側から毎日のように届き、合わせると膨大な量になります。多くの組織は、報告を受けて集計する専門の事業者に `rua` を向けています。

### 失敗報告（ruf）

失敗報告は、fail した**1 通ごとに**、ヘッダや本文の一部を送るものです（[RFC 9991](https://www.rfc-editor.org/rfc/rfc9991.html)）。原因を特定するには便利ですが、第三者が書いたメールの中身を持ち主に渡すことになります。RFC 9991 自身が、プライバシーの懸念から**多くの大規模な事業者が失敗報告を制限するか、まったく出していない**と書いており、集計報告を主な手段として勧めています。`ruf=` を書いても、ほとんど届かないと考えておくのが現実的です。

### 外部の宛先への報告の許可

`rua=mailto:d@rua.agari.com` のように、**自分のドメインの外**へ報告を送らせることもできます。ただし、何の確認もなければ、攻撃者は被害者のアドレスを `rua=` に書いたレコードを作り、fail するメールを大量に送るだけで、世界中の受信側から被害者へ報告を送りつけさせられます。

そこで受信側は、報告先の側に「受け取ることに同意している」印があるかを確かめます（[RFC 9990 4 節](https://www.rfc-editor.org/rfc/rfc9990.html#section-4)）。

```
方針を出したドメイン:  yahoo.com
報告先のホスト:        rua.agari.com
確かめる名前:          yahoo.com._report._dmarc.rua.agari.com  の TXT が v=DMARC1 で始まるか
```

実際に引くと `"v=DMARC1;"` が返ってきます（後の「手元で確かめる」）。

## p=none から reject へ

いきなり `p=reject` を書くと、自分のドメインを名乗る**正規のメール**のうち、揃っていないものがすべて拒否されます。社内のどこかの部署が勝手に契約した配信サービス、請求書を送る外部の会計システム、複合機のスキャンの送信。どこから自分のドメインのメールが出ているかを、完全に把握している組織はまずありません。

そこで、報告を使って段階的に上げるのが定石です。RFC 9989 も、少なくとも 1 か月 `p=none` で様子を見て、同じくらいの期間 `p=quarantine` を試し、結果を比べてから `reject` に進むことを勧めています（[RFC 9989 7.4](https://www.rfc-editor.org/rfc/rfc9989.html#section-7.4)）。

```
1. p=none; rua=...         報告を集める。何も起きない（監視）
2. 報告から送信元を洗い出し、SPF か DKIM で From: と揃える
3. p=quarantine; t=y       テスト。実際には none 相当
4. p=quarantine            fail したものは迷惑メールへ
5. p=reject; t=y           テスト。実際には quarantine 相当
6. p=reject                fail したものは拒否
```

`p=none` は「何もしない」方針ですが、**報告が届き始めるという意味で、最初の一歩として価値があります**。逆に、`p=none` のまま何年も放置されているドメインは、報告を誰も読んでいないことが多いのです。

### reject が向かないドメインもある

ここで、仕様自身が強い注意を書いています。メーリングリストは件名に `[list]` を付けたり、本文の末尾に案内を足したりするので、第 147 回で見たとおり DKIM の署名が壊れます。転送し直すので SPF も揃いません。すると、`p=reject` のドメインの人がメーリングリストに投稿したメールは、購読者の受信側で**全員分拒否されます**。さらに悪いことに、メーリングリストの側はその拒否を「購読者のアドレスが死んでいる」と解釈し、**無関係な購読者を自動的に退会させてしまう**ことがあります。

そのため RFC 9989 は、**メーリングリストに投稿するかもしれない一般の利用者を抱えるドメインは `p=reject` を公開すべきでない（SHOULD NOT）**と書いています。実際、`gmail.com` の方針は `p=none` です（ただし `sp=quarantine`）。一方、Google が自社の業務で使う `google.com` は `p=reject` です。**同じ会社でも、ドメインの使われ方で方針が違う**のです。

こうした中継の問題への対策として、メーリングリストの多くは `p=reject` のドメインからの投稿について `From:` を自分のアドレスに書き換えるようになり、また中継者が「受け取った時点では認証に通っていた」ことを署名つきで引き継ぐ ARC（第 147 回）が使われています。

<Callout type="warn" title="よくある誤解: p=reject と書けば、受信側は必ず拒否する">
  `p=` は持ち主から受信側への**依頼**であって、命令ではありません。
  RFC 9989 は逆に、受信側に対して「**`p=reject` だけを理由に拒否してはならない**（MUST NOT）」と書き、
  送信の実績や内容の分析など、ほかの判断材料と組み合わせるよう求めています。ほかの材料が無ければ quarantine として扱え、とも書いています（7.4 節と 8 節）。
  また、同じ節で送信側には「`p=reject` を出すなら SPF だけに頼ってはならず、DKIM で署名しなければならない（MUST）」と求めています。
  転送されれば SPF は壊れるからです。
</Callout>

## 大手の送信者要件

長いあいだ、DMARC を設定するかどうかは送信側の任意でした。流れを変えたのは、大手のメールボックス事業者が**受信の条件**として求め始めたことです。

| 事業者 | 対象 | 開始 | 主な要件 |
| --- | --- | --- | --- |
| Google（Gmail） | 個人の Gmail アカウントへ 1 日 5,000 通以上送る送信者 | 2024 年 2 月 | SPF と DKIM、DMARC（`p=none` でよい）、From: と SPF か DKIM のドメインが揃う、ワンクリックの配信停止、迷惑メール率 0.3% 未満 |
| Yahoo | 一括送信者 | 2024 年 2 月 | SPF と DKIM、DMARC（少なくとも `p=none`）で pass、From: の揃い、ワンクリックの配信停止、正引きと逆引きの一致など |
| Microsoft（Outlook.com、Hotmail、Live.com） | 1 日 5,000 通以上の送信者 | 2025 年 5 月 5 日 | SPF と DKIM がともに pass、DMARC を公開し pass（少なくとも一方が揃う） |

出典はそれぞれ、[Google の送信者ガイドライン](https://support.google.com/a/answer/81126?hl=en)、[Yahoo の送信者向けベストプラクティス](https://senders.yahooinc.com/best-practices/)、[Microsoft の発表](https://techcommunity.microsoft.com/blog/microsoftdefenderforoffice365blog/strengthening-email-ecosystem-outlook%E2%80%99s-new-requirements-for-high%E2%80%90volume-senders/4399730)と[エラー 550 5.7.515 の解説](https://support.microsoft.com/en-us/outlook/fix-ndr-error-550-5-7-515-in-outlook-com)です。

いくつかの点に注意します。

- **要求される方針は `p=none` でよい。** 求められているのは「DMARC のレコードがあり、From: と揃っていること」で、`reject` までは求めていません。
- **強制は段階的に強まっている。** Google は 2025 年 11 月から、要件を満たさないメールに**一時的・恒久的な拒否**を含む措置を取ると FAQ に書いています（[Gmail の送信者ガイドライン FAQ](https://support.google.com/mail/answer/14229414?hl=en)）。Microsoft は当初、迷惑メールのフォルダに振り分けると予告していましたが、開始直前に方針を変え、`550 5.7.515` で拒否するとしました。
- **一度一括送信者になると、ずっと一括送信者。** Google の FAQ は、一括送信者の分類に期限はないと明記しています。
- **ワンクリックの配信停止**は、`List-Unsubscribe` ヘッダと `List-Unsubscribe-Post: List-Unsubscribe=One-Click` を組み合わせ、利用者が確認の画面を経ずに POST 1 回で停止できるようにする仕組みです（[RFC 8058](https://www.rfc-editor.org/rfc/rfc8058.html)）。

事業者の要件は仕様より速く変わります。数字や日付は、**執筆時点（2026 年 9 月）での各社の公開情報**です。実際に送る前には、必ず最新の文書を確かめてください。

## BIMI: 揃っていることを利用者に見せる

DMARC が pass しても、利用者の画面は何も変わりません。そこで、**DMARC を厳しく運用しているドメインにだけ、受信側がブランドのロゴを表示する**という仕組みが作られました。**BIMI**（Brand Indicators for Message Identification）です。

```
default._bimi.paypal.com.  TXT  "v=BIMI1; l=https://.../paypal_ppe.svg; a=https://.../PPE_UK_DE_paypal_inc.pem"
```

`l=` がロゴ（SVG Tiny PS という制限つきの SVG）の場所、`a=` が**そのロゴをそのドメインが使ってよいことを示す証明書**の場所です。この証明書が第 110 回で見た X.509 の証明書で、認証局が商標の登録などを確かめて発行します。登録商標を確かめた **VMC**（Verified Mark Certificate）と、一定期間使われてきたロゴであることを確かめる **CMC**（Common Mark Certificate）の 2 種類があります。ロゴの画像そのものは、証明書の logotype 拡張（[RFC 3709](https://www.rfc-editor.org/rfc/rfc3709.html)）に埋め込まれます。

Gmail で表示されるための条件は、DMARC が `p=quarantine` か `p=reject` であることなどです。`p=none` では表示されません。VMC なら差出人の横に確認済みの印も付きますが、CMC では付きません（[Google Workspace の BIMI の設定](https://knowledge.workspace.google.com/admin/security/set-up-bimi)）。

仕様の状態には注意が要ります。BIMI は業界団体が進めてきたもので、IETF の文書としては**個人の提出による Internet-Draft** のままです（執筆時点の最新は [draft-brand-indicators-for-message-identification-14](https://datatracker.ietf.org/doc/draft-brand-indicators-for-message-identification/)、2026 年 5 月）。RFC ではありません。対応するかどうか、どう表示するかは受信側ごとに違います。

## DMARC が防がないもの

<Callout type="warn" title="よくある誤解: DMARC を reject にすれば、フィッシングは防げる">
  DMARC が守るのは **From: のドメイン部分が、そのドメインそのものである**場合だけです。次のものは防げません。

  - **似たドメイン**: `examp1e.com` や `example-support.com` は別のドメインなので、その持ち主が SPF・DKIM・DMARC を完璧に設定すれば pass します
  - **表示名の偽装**: `"Example 請求担当" <x@attacker.example>` のように、表示名だけを偽る手口。多くのメールソフトは表示名を大きく、アドレスを小さく表示します。RFC 9989 も表示名への攻撃を明示的に対象外としています（2.4 節、11.4 節）
  - **正規のアカウントの乗っ取り**: 本物のアカウントから送られたメールは、本物として pass します（第 150 回で見るとおり、メールアカウントは他のアカウントの回復の鍵でもあります）
  - **中身**: 本文が詐欺かどうかは判定しません

  DMARC は「このドメインを名乗るな」を強制する仕組みであって、「このメールは安全だ」を保証する仕組みではありません。
</Callout>

もう 1 つ見落とされがちなのは、**メールを送らないドメイン**です。使っていないドメインに DMARC が無ければ、攻撃者はそのドメインを `From:` に使えます。送らないドメインには `v=spf1 -all` と `v=DMARC1; p=reject` を置いておくのが定石です。第 143 回の null MX と組み合わせれば、「このドメインはメールを送りも受けもしない」と宣言できます。

## 組み合わせで機能する

DMARC は単独では何もしません。ここまでの部品がそろって初めて意味を持ちます。

| 部品 | DMARC の中での役割 | 欠けるとどうなるか |
| --- | --- | --- |
| DNS の TXT（第 58 回） | 方針・報告先・報告の許可の置き場 | 方針を公開できない |
| DNS のキャッシュと TTL（第 60 回） | 方針を変えたとき、いつ効くか | `reject` にした直後も古い方針が使われる |
| DNSSEC（第 61 回） | 方針のレコードの改ざんを防ぐ | 偽の応答で `_dmarc` を「無い」ことにされうる |
| SPF（第 146 回） | `MAIL FROM` のドメインを認証 | 転送に弱いので、これだけでは不十分 |
| DKIM と署名（第 147 回、第 107 回） | `d=` のドメインを認証 | 転送を越えて揃えられる手段がなくなる |
| X.509（第 110 回） | BIMI のロゴの証明書 | ロゴを出せない（DMARC 自体には不要） |
| エンベロープとヘッダの区別（第 140 回） | 利用者が見る `From:` を特定する | 何を守るのかが定まらない |

## 手元で確かめる

### 実在のドメインの方針を比べる

`dig` で主要なドメインの `_dmarc` を引きました（執筆時点）。

```
$ for d in google.com gmail.com yahoo.com outlook.com microsoft.com apple.com github.com example.com ietf.org; do
    printf "%-14s " $d; dig +short TXT _dmarc.$d | tr -d '\n'; echo
  done
google.com     "v=DMARC1; p=reject; rua=mailto:mailauth-reports@google.com"
gmail.com      "v=DMARC1; p=none; sp=quarantine; rua=mailto:mailauth-reports@google.com"
yahoo.com      "v=DMARC1; p=reject; pct=100; rua=mailto:d@rua.agari.com; ruf=mailto:d@ruf.agari.com;"
outlook.com    "v=DMARC1; p=none; sp=quarantine; pct=100; rua=mailto:rua@dmarc.microsoft; ruf=mailto:ruf@dmarc.microsoft; fo=1"
microsoft.com  "v=DMARC1; p=reject; pct=100; rua=mailto:itex-rua@microsoft.com; ruf=mailto:itex-ruf@microsoft.com; fo=1"
apple.com      "v=DMARC1; p=quarantine; sp=reject; rua=mailto:d@rua.agari.com; ruf=mailto:d@ruf.agari.com;"
github.com     "v=DMARC1; p=quarantine; sp=reject; pct=100; rua=mailto:dmarc@github.com; ruf=mailto:dmarc@github.com; fo=1"
example.com    "v=DMARC1;p=reject;sp=reject;adkim=s;aspf=s"
ietf.org       "v=DMARC1; p=none; rua=mailto:dmarc_agg@vali.email,mailto:dmarc-report@ietf.org"
```

読み取れることがいくつもあります。

- **一般の利用者が使うドメイン（`gmail.com`、`outlook.com`）は `p=none`**、会社の業務用（`google.com`、`microsoft.com`）は `p=reject`。前の節で見たメーリングリストへの配慮そのものです
- `gmail.com` と `outlook.com` は `sp=quarantine` で、**サブドメインだけを厳しく**しています。利用者はサブドメインのアドレスを持たないので、サブドメインを名乗るメールは偽物と見てよいからです
- `pct=100` が今も多く残っています。RFC 9989 では廃止されましたが、既定値と同じなので害はありません
- `example.com` は文書の例に使うための予約されたドメインで、メールを送らないので最も厳しい設定です
- IETF 自身（`ietf.org`）は、メーリングリストを運営する立場から `p=none` です

`_dmarc.mail.google.com` を引くと何も返りません。`mail.google.com` を名乗るメールには、Tree Walk で 1 つ上の `google.com` のレコードが、`sp` が無いので `p=reject` として当たります。

外部への報告の許可も引いてみます。

```
$ dig +short TXT yahoo.com._report._dmarc.rua.agari.com
"v=DMARC1;"
$ dig +short TXT nonexistent-zzq.com._report._dmarc.rua.agari.com
"v=DMARC1;"
```

2 つ目は、実在しない名前にも答えています。報告を受ける事業者は、顧客のドメインを 1 つずつ登録する代わりに、第 58 回で見た**ワイルドカード**（`*._report._dmarc.rua.agari.com`）で「誰からの報告でも受ける」と答えていることが多いのです。RFC 9990 もこの書き方を認めています。

### 判定を組み合わせる模型

最後に、SPF、DKIM、DMARC の判定を組み合わせる小さな模型を Python で動かします。Docker で mailpit を起動し、場面ごとに `MAIL FROM`、`From:`、署名するドメインを変えたメールを送り、受け取った生のメッセージから判定します。

```bash
docker run -d --name ll120 -p 18120:1025 -p 18121:8025 axllent/mailpit
python3 -m venv venv && ./venv/bin/pip install dkimpy cryptography
```

模型の要点は次のとおりです。本物の DNS は使わず、辞書で DNS の代わりをします。送信元 IP も、手元ではすべて Docker のゲートウェイから届くので、場面ごとに「受信側から見えた IP」として与えます。

```python
DNS = {
    "_dmarc.example.com": "v=DMARC1; p=reject; rua=mailto:dmarc@example.com",
    "bounce.example.com": "v=spf1 ip4:192.0.2.10 -all",
    "esp.example.net":    "v=spf1 ip4:198.51.100.7 -all",
    "list.example.org":   "v=spf1 ip4:203.0.113.5 -all",
    "attacker.example":   "v=spf1 ip4:203.0.113.66 -all",
    # s1._domainkey.<ドメイン> には、その場で作った RSA の公開鍵を入れる
}

def org_domain(domain):                        # Tree Walk の簡略版
    labels = domain.split(".")
    found = [".".join(labels[i:]) for i in range(len(labels))
             if (txt("_dmarc." + ".".join(labels[i:])) or "").startswith("v=DMARC1")]
    return min(found, key=lambda x: x.count(".")) if found else domain

def aligned(author, ident, mode):
    if ident is None:
        return False
    return author == ident if mode == "s" else org_domain(author) == org_domain(ident)

def dmarc(author, spf_res, spf_dom, dkim_res, dkim_dom, mode):
    if txt("_dmarc." + org_domain(author)) is None:   # 方針が無ければ DMARC は適用しない
        return "none"
    a_spf  = spf_res  == "pass" and aligned(author, spf_dom,  mode)
    a_dkim = dkim_res == "pass" and aligned(author, dkim_dom, mode)
    return "pass" if (a_spf or a_dkim) else "fail"
```

SPF の評価器は第 146 回の模型をさらに削った `ip4` と `-all` だけのもの、DKIM の検証は dkimpy の `verify` に、辞書を引く関数を DNS の代わりに渡しています。`MAIL FROM` は、受け取ったメッセージの `Return-Path:` から読み直しています（第 140 回）。

実行結果です。

```
場面                     Return-Path              SPF    DKIM(d=)                 relaxed  strict
自社サーバから             <b@bounce.example.com>   pass   pass(example.com)        pass     pass
配信サービス(未設定)       <b@esp.example.net>      pass   pass(esp.example.net)    fail     fail
配信サービス(DKIM委任)     <b@esp.example.net>      pass   pass(example.com)        pass     pass
単純な転送                 <b@bounce.example.com>   fail   pass(example.com)        pass     pass
MLが件名を改変             <b@list.example.org>     pass   fail(example.com)        fail     fail
なりすまし                 <x@attacker.example>     pass   pass(attacker.example)   fail     fail
サブドメインのFrom:        <b@bounce.example.com>   pass   pass(example.com)        pass     fail
```

1 行ずつ読むと、この回の話がすべて出てきます。

- **自社サーバから**: SPF は `bounce.example.com` で pass し、relaxed なら揃います。strict でも DKIM の `d=example.com` が完全に一致するので pass
- **配信サービス（未設定）**: SPF も DKIM も pass なのに、どちらも配信サービスのドメインなので **DMARC は fail**。`p=reject` なら拒否されます
- **配信サービス（DKIM 委任）**: SPF は相変わらず揃いませんが、DKIM を自分のドメインで署名してもらえば pass。**揃えるのは DKIM で十分**です
- **単純な転送**: 転送するサーバの IP は SPF に無いので fail。しかし DKIM が残っているので pass。**RFC 9989 が `p=reject` なら DKIM を必須とする理由**です
- **ML が件名を改変**: 件名を書き換えたので DKIM が壊れ、SPF はメーリングリストのドメインで pass するだけ。**正規のメールが fail** します
- **なりすまし**: 冒頭の例です。SPF も DKIM も pass しますが、DMARC が fail させます
- **サブドメインの From:**: `news.example.com` と `example.com` は、relaxed なら組織ドメインが同じで揃い、strict では揃いません

mailpit の画面（`http://localhost:18121`）で「なりすまし」の生のメッセージを開くと、冒頭に示したとおり `Return-Path:` と `d=` は攻撃者のドメイン、`From:` だけが `example.com` になっています。

終わったらコンテナを止めます。

```bash
docker stop ll120
```

## まとめ

- SPF は `MAIL FROM` を、DKIM は `d=` を認証するだけで、利用者が見る `From:` には触れない。**DMARC が初めて `From:` と認証結果を結びつける**
- 結びつけ方は**アラインメント**。strict は完全一致、relaxed は組織ドメインの一致。SPF と DKIM の**どちらか一方が揃って pass すれば** DMARC は pass
- 組織ドメインは、RFC 7489 では PSL で、2026 年 5 月の RFC 9989 では **DNS Tree Walk**（最大 8 回の問い合わせ）で決める。当面は両方の実装が混在する
- 方針は `_dmarc` の TXT に書く。`p` / `sp` / 新設の `np`、アラインメントの `adkim` / `aspf`、廃止された `pct` の代わりの `t`
- 集計報告 `rua` で、自分の名前がどこから使われているかが分かる。失敗報告 `ruf` はプライバシーの理由でほとんど届かない。外部への報告には `_report._dmarc` での許可が要る
- `p=none` で報告を集め、送信元を揃えてから `quarantine`、`reject` へ上げる。一般の利用者を抱えるドメインは、メーリングリストとの相性から `reject` を避けるべきとされ、受信側も `p=reject` だけを理由に拒否してはならない
- Google と Yahoo は 2024 年 2 月から、Microsoft は 2025 年 5 月から、大量の送信者に SPF・DKIM・DMARC（`p=none` 以上）と揃いを求めている
- BIMI は DMARC を厳しく運用しているドメインにロゴを表示する。証明書は X.509 の VMC / CMC で、仕様はまだ Internet-Draft
- DMARC は似たドメイン、表示名の偽装、正規のアカウントの乗っ取りを防がない

ここまでの SPF、DKIM、DMARC、そして第 145 回の経路の TLS は、どれも**ドメインと経路**を守る仕組みでした。中継するサーバはメールの中身をすべて読めます。次の回では、差出人の**人**が署名し、宛先の**人**だけが読めるようにする、エンドツーエンドの暗号化と署名（S/MIME と OpenPGP）を見ます。
