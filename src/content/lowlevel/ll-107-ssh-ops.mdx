## 鍵を配る仕事が残る

第 106 回で、SSH の信頼の置き方を見ました。サーバの鍵は最初の接続で覚え（known_hosts）、ユーザの鍵はサーバ側に並べておきます（authorized_keys）。どちらも**生の公開鍵を 1 本ずつ登録する**方式です。

少人数ならこれで困りません。しかし規模が大きくなると、次の仕事がすべて人手に残ります。

- **authorized_keys の配布**: 新しく入った人の公開鍵を、入ってよい全サーバに書き込む
- **退職と異動**: 辞めた人の鍵を、全サーバの authorized_keys から漏れなく消す
- **known_hosts の更新**: サーバを作り直すとホスト鍵が変わり、全員の画面に「REMOTE HOST IDENTIFICATION HAS CHANGED」が出る。利用者はやがて確かめずに消すようになる
- **秘密鍵の置き場所**: 踏み台の先に入るために、踏み台にも秘密鍵を置きたくなる

この回では、これらを順に片付けます。秘密鍵を 1 か所から動かさない **ssh-agent**、踏み台に何も預けない **ProxyJump**、生の鍵の代わりに CA の署名を信頼する **SSH 証明書**、そして証明書を **SSO と組み合わせて短命に発行する**型です。

## ssh-agent: 秘密鍵を持ち、署名だけを引き受ける

第 106 回で見たとおり、公開鍵認証でクライアントがするのは、**セッション ID を含むデータに秘密鍵で署名する**ことだけです。秘密鍵そのものをサーバに送る必要はありません。ssh-agent は、この「署名する」部分だけを別のプロセスに切り出したものです。

```
 ssh（クライアント）              ssh-agent（秘密鍵をメモリに保持）
   │  REQUEST_IDENTITIES  ──────→  │
   │  ←── 公開鍵の一覧              │
   │  SIGN_REQUEST(公開鍵, データ) →│  秘密鍵で署名
   │  ←── 署名                      │
```

やり取りは Unix ドメインソケット越しで、場所は環境変数 `SSH_AUTH_SOCK` が指します。このプロトコルは長く OpenSSH の内部文書でしか定義されていませんでしたが、執筆時点（2026 年 9 月）では [RFC 9987](https://www.rfc-editor.org/rfc/rfc9987.html)（2026 年 5 月）として標準になっています。一覧の要求が 5.5 節、署名の要求が 5.6 節です。RFC は設計の狙いを次のように書いています。

> The primary design intention of an agent is that an attacker with unprivileged access to their victim's agent should be prevented from gaining a copy of any keys that have been loaded into it.

**agent に話しかけられる者は、鍵を使えるが、鍵を持ち出せない。** これが agent の約束のすべてです。パスフレーズを解くのは `ssh-add` のときの 1 回で済み、その後は復号済みの鍵がディスクに書かれることなく agent のメモリに留まります。

手元で確かめます。普段の agent を汚さないよう、作業ディレクトリ専用の agent を別に起動します（macOS ではソケットのパスに長さの上限があり、深いディレクトリの中には作れませんでした）。

```
$ eval $(ssh-agent -a /private/tmp/claude-502/ll97.GX0r/a.sock -s)
$ ssh-add -t 1h alice
Identity added: alice (alice@laptop)
Lifetime set to 3600 seconds
Certificate added: alice-cert.pub (alice@example.com)
Lifetime set to 3600 seconds
$ ssh-add -l
256 SHA256:9DvPmAeyL89K/Za8Q127yNjkwcnPYCMLNYH7syIoZi0 alice@laptop (ED25519)
256 SHA256:9DvPmAeyL89K/Za8Q127yNjkwcnPYCMLNYH7syIoZi0 alice@laptop (ED25519-CERT)
```

`-t 1h` は、1 時間で agent から鍵を消す指定です。隣に `alice-cert.pub` があったので、後で作る証明書も一緒に読み込まれています。fingerprint（第 99 回）が同じなのは、証明書の中身が同じ公開鍵だからです。

## エージェント転送: 鍵は渡らないが、使わせてしまう

`ssh -A`（`ForwardAgent yes`）は、接続先のサーバに agent のソケットを作り、そこへの要求を SSH のチャネル越しに手元の agent へ中継します。接続先からさらに別のサーバへ入るとき、手元の鍵で署名できるようになります。

問題は、**接続先のソケットに誰が話しかけられるか**です。ソケットはファイルなので、第 43 回で見たファイルの権限で守られているだけです。そして root は権限の確認を受けません。ssh(1) のマニュアルは、`-A` の説明で次のように警告しています（[ssh(1)](https://man.openbsd.org/ssh.1)）。

> Agent forwarding should be enabled with caution. Users with the ability to bypass file permissions on the remote host (for the agent's Unix-domain socket) can access the local agent through the forwarded connection.

Docker で立てた sshd（ホスト側ポート 2297）に `-A` で入り、その間に別の端末からコンテナの root として同じソケットを使ってみます。

```
$ ssh -F ssh_config -o IdentityAgent=$SOCK -A alice@lab \
    'echo SSH_AUTH_SOCK=$SSH_AUTH_SOCK; ls -l $SSH_AUTH_SOCK; ssh-add -l; sleep 15'
SSH_AUTH_SOCK=/tmp/ssh-XXXXEDOpib/agent.49
srwxr-xr-x    1 alice    alice            0 Sep 28 10:45 /tmp/ssh-XXXXEDOpib/agent.49
256 SHA256:9DvPmAeyL89K/Za8Q127yNjkwcnPYCMLNYH7syIoZi0 alice@laptop (ED25519)
256 SHA256:9DvPmAeyL89K/Za8Q127yNjkwcnPYCMLNYH7syIoZi0 alice@laptop (ED25519-CERT)

（接続している間に、コンテナの root として）
# id -un
root
# SSH_AUTH_SOCK=/tmp/ssh-XXXXEDOpib/agent.49 ssh-add -l
256 SHA256:9DvPmAeyL89K/Za8Q127yNjkwcnPYCMLNYH7syIoZi0 alice@laptop (ED25519)
256 SHA256:9DvPmAeyL89K/Za8Q127yNjkwcnPYCMLNYH7syIoZi0 alice@laptop (ED25519-CERT)
# SSH_AUTH_SOCK=/tmp/ssh-XXXXEDOpib/agent.49 ssh alice@localhost 'echo logged-in-as-$(whoami)'
logged-in-as-alice
```

root は alice の秘密鍵ファイルを 1 バイトも読んでいません。それでも**alice として別のサーバにログインできました**。署名を頼めば、agent は頼まれたとおりに署名するからです。

<Callout type="warn" title="よくある誤解: 「秘密鍵は転送先に置かれないから、エージェント転送は安全」">
  前半は正しく、結論が誤りです。転送で渡るのは鍵ではなく**署名を頼む窓口**で、
  接続している間は、転送先の root（あるいはそのサーバを乗っ取った攻撃者）が、手元の鍵で何度でも署名させられます。
  鍵を持ち出されないので、接続を切れば止まる、という違いがあるだけです。
  RFC 9987 も 10 節で、既定で転送しないこと、完全には信頼できないホストへ転送しないことを求めています（[RFC 9987](https://www.rfc-editor.org/rfc/rfc9987.html)）。
  `ForwardAgent` の既定値は `no` です（[ssh_config(5)](https://man.openbsd.org/ssh_config.5)）。
</Callout>

どうしても転送が要るときの緩和策はいくつかあります。`ssh-add -c` は署名のたびに手元で確認を求めます。OpenSSH 8.9（2022 年 2 月）からは `ssh-add -h` で、**その鍵を使ってよい経路（どこからどこへ、どのユーザで）を agent に登録**できます（[リリースノート](https://www.openssh.org/txt/release-8.9)、[解説](https://www.openssh.org/agent-restrict.html)）。署名のたびに、経路上の各サーバのホスト鍵と結び付けて確かめるので、乗っ取られた中継サーバが別の宛先へ鍵を使うのを防げます。ただし経路上のサーバがすべてこの拡張に対応していること、ホスト鍵が known_hosts にあることが前提です。

## ProxyJump: 踏み台に何も預けない

エージェント転送を使いたくなる典型は、**踏み台（bastion）を経由して内側のサーバに入る**場面です。しかし OpenSSH 7.3（2016 年 8 月）で入った `ProxyJump`（`-J`）を使えば、転送は要りません（[リリースノート](https://www.openssh.org/txt/release-7.3)）。

```
エージェント転送で踏み台から入る           ProxyJump
                                            
 手元 ──SSH①──→ 踏み台 ──SSH②──→ 内側       手元 ──SSH①──→ 踏み台 ──TCP──→ 内側
 agent ←──転送──┘ ②の署名は踏み台で頼む      └────────── SSH②（手元から直接）──────┘
 ②の復号も踏み台で行う                       踏み台は②の暗号文を中継するだけ
```

ProxyJump は、踏み台への SSH 接続の中で**内側のサーバへの TCP 転送**だけを開き、その上で手元から内側へ**もう 1 本の SSH を直接張ります**（[ssh(1) の -J](https://man.openbsd.org/ssh.1)）。内側とのホスト鍵の確認も、鍵交換も、ユーザ認証の署名も、すべて手元で行われます。踏み台が見るのは SSH② の暗号化されたバイト列だけです。

手元の sshd を踏み台にして、その中の 127.0.0.1:22（同じ sshd）を「内側」に見立てます。

```
Host inner
  HostName 127.0.0.1
  Port 22
  ProxyJump alice@lab
  IdentityAgent none
  ...
```

```
$ ssh -v -F ssh_config alice@inner 'echo inner-ok; echo agent=${SSH_AUTH_SOCK:-none}'
debug1: Setting implicit ProxyCommand from ProxyJump: ssh -l alice -F ssh_config -v -W '[%h]:%p' lab
debug1: Host '[localhost]:2297' is known and matches the ED25519-CERT host certificate.
Authenticated to localhost ([127.0.0.1]:2297) using "publickey".
debug1: Host '127.0.0.1' is known and matches the ED25519-CERT host certificate.
Authenticated to 127.0.0.1 (via proxy) using "publickey".
inner-ok
agent=none
```

ホスト鍵の確認と認証が **2 回**、どちらも手元の ssh で行われています。内側には agent のソケットがありません（`agent=none`）。`-W` は「標準入出力を指定したホストとポートへつなぐ」指定で、ProxyJump はこれを使った ProxyCommand の略記です。

<Callout type="warn" title="よくある誤解: 「多段で入るにはエージェント転送が要る」">
  踏み台の上で `ssh` を打つ使い方をしていると、そう見えます。
  しかし踏み台から入り直す必要はなく、踏み台は TCP の中継だけをすればよいのです。
  ProxyJump なら、踏み台の root が見られるのは暗号文と接続先だけで、**署名を代行させる窓口はどこにもありません**。
  踏み台の sshd で `AllowAgentForwarding no` にしておけば、利用者が `-A` を付けても転送されません。
</Callout>

## SSH 証明書: 生の鍵ではなく、CA の署名を信頼する

agent と ProxyJump で「秘密鍵を動かさない」ことはできました。残るのは、authorized_keys と known_hosts を**配る**仕事です。

ここで第 102 回の PKI と同じ発想を持ち込みます。サーバが全員の公開鍵を覚える代わりに、**CA の公開鍵を 1 本だけ**覚え、「CA が署名した鍵なら受け入れる」ことにします。これが OpenSSH の証明書で、OpenSSH 5.4（2010 年 3 月）で入りました（[リリースノート](https://www.openssh.org/txt/release-5.4)）。形式は X.509 ではなく、OpenSSH 独自の簡素なものです（[PROTOCOL.certkeys](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL.certkeys)）。

```
ssh-ed25519-cert-v01@openssh.com
  nonce
  公開鍵（利用者の鍵、またはホスト鍵）
  serial             失効に使う番号
  type               user か host
  key id             ログに出る名前（誰に発行したか）
  valid principals   ログインしてよいユーザ名 / そのホストの名前
  valid after / before
  critical options   制限（知らない制限があれば拒否）
  extensions         許可（知らない許可は無視してよい）
  signature key      CA の公開鍵
  signature          ここまでのすべてへの CA の署名
```

第 98 回で見たとおり、署名が保証するのは「この**鍵**で署名された」ことだけでした。証明書は、その鍵に「誰の、何のための、いつまでの鍵か」を CA の署名で結び付けます。第 101 回の X.509 と役割は同じですが、**中間 CA による連鎖はありません**。署名に使う鍵が証明書であってはならない、と明記されています（同文書）。

### ユーザ証明書を発行する

CA の鍵は普通の鍵ペアです。`ssh-keygen -s` で、利用者の公開鍵に署名します。

```
$ ssh-keygen -q -t ed25519 -f user_ca -N '' -C 'user-ca'
$ ssh-keygen -s user_ca -I 'alice@example.com' -n alice,deploy -V +1h -z 1001 alice.pub
Signed user key alice-cert.pub: id "alice@example.com" serial 1001 for alice,deploy valid from 2026-09-28T19:42:00 to 2026-09-28T20:43:36
$ ssh-keygen -L -f alice-cert.pub
alice-cert.pub:
        Type: ssh-ed25519-cert-v01@openssh.com user certificate
        Public key: ED25519-CERT SHA256:9DvPmAeyL89K/Za8Q127yNjkwcnPYCMLNYH7syIoZi0
        Signing CA: ED25519 SHA256:JZirs/xQc7Uw+nyagjeOnYNfHVraU/IcSHLMus3988A (using ssh-ed25519)
        Key ID: "alice@example.com"
        Serial: 1001
        Valid: from 2026-09-28T19:42:00 to 2026-09-28T20:43:36
        Principals: 
                alice
                deploy
        Critical Options: (none)
        Extensions: 
                permit-X11-forwarding
                permit-agent-forwarding
                permit-port-forwarding
                permit-pty
                permit-user-rc
```

- `-I` は Key ID です。sshd のログに残るので、**どの人にいつ発行した証明書で入ったか**を後から追えます
- `-n` の principals は、この証明書で入ってよい**ユーザ名**です。空にすると「どのユーザでもよい」の意味になりますが（PROTOCOL.certkeys）、sshd は `TrustedUserCAKeys` 経由では principals の無い証明書を受け付けません（[sshd_config(5)](https://man.openbsd.org/sshd_config.5)）
- `-V +1h` で 1 時間だけ有効にしています。開始時刻は署名した時刻より少し前にずらされています
- 何も指定しないと、`permit-pty` などの**許可**が既定で付きます。拡張は「許可」、critical options は「制限」という分け方で、古い sshd が知らない制限を黙って無視して通してしまわないよう、知らない critical option を見たら拒否する決まりです（PROTOCOL.certkeys）

### サーバ側: CA を 1 行だけ信頼する

sshd には CA の公開鍵を置き、authorized_keys は使わない設定にしました。

```
HostKey /etc/ssh/host_key
HostCertificate /etc/ssh/host_key-cert.pub
TrustedUserCAKeys /etc/ssh/ca/user_ca.pub
AuthorizedKeysFile none
PasswordAuthentication no
```

alice にはこのサーバの authorized_keys が 1 行もありませんが、入れます。principals に無い bob としては入れません。

```
$ ssh -F ssh_config alice@lab 'id'
uid=1000(alice) gid=1000(alice) groups=1000(alice)
$ ssh -F ssh_config bob@lab true
bob@localhost: Permission denied (publickey).

（sshd のログ）
Accepted publickey for alice from 172.17.0.1 port 63764 ssh2: ED25519-CERT SHA256:9DvP... ID alice@example.com (serial 1001) CA ED25519 SHA256:JZir...
Certificate invalid: name is not a listed principal
```

期限の切れた証明書（`-V -2h:-1h` で発行）も拒否されます。ログは `Certificate invalid: expired` でした。**時計がずれていると、この判定がそのままずれます**。

principals とサーバ上のユーザ名を直接対応させたくないときは、`AuthorizedPrincipalsFile` で「このユーザには、どの principal を持つ証明書で入ってよいか」をサーバごとに書けます（[sshd_config(5)](https://man.openbsd.org/sshd_config.5)）。たとえば証明書の principals を `team-db` のような役割名にしておき、DB サーバの `deploy` ユーザだけが `team-db` を受け入れる、という形です。

### 証明書に制限を書く

critical options で、その証明書でできることを絞れます。`-O clear` で既定の許可を全部外し、実行するコマンドと接続元を固定してみます。

```
$ ssh-keygen -s user_ca -I 'alice-backup' -n alice -V +10m -O clear \
    -O force-command='echo only-backup' -O source-address=172.17.0.0/16 lim/alice.pub
$ ssh-keygen -L -f lim/alice-cert.pub | sed -n '/Critical/,$p'
        Critical Options: 
                force-command echo only-backup
                source-address 172.17.0.0/16
        Extensions: (none)
$ ssh -F ssh_config -o CertificateFile=$PWD/lim/alice-cert.pub alice@lab 'cat /etc/shadow'
only-backup
```

`cat /etc/shadow` を頼んでも、実行されたのは証明書に書かれたコマンドでした。バックアップ用の自動処理に渡す証明書などに使えます。`Extensions: (none)` なので、この証明書ではエージェント転送も pty も使えません。

### ホスト証明書と @cert-authority

同じことをサーバ側の鍵にも行います。`-h` を付けると**ホスト証明書**になり、principals にはそのホストの名前を並べます。

```
$ ssh-keygen -s host_ca -h -I 'web1' -n 'web1.internal,localhost,127.0.0.1' -V +52w host_key.pub
```

クライアントの known_hosts には、ホストごとの鍵ではなく **CA の公開鍵を、名前の範囲と一緒に**書きます。

```
@cert-authority [localhost]:2297 ssh-ed25519 AAAAC3...（host_ca.pub の中身）
@cert-authority 127.0.0.1 ssh-ed25519 AAAAC3...
```

```
$ ssh -v -F ssh_config alice@lab true
debug1: Server host certificate: ssh-ed25519-cert-v01@openssh.com SHA256:YSpV..., serial 0 ID "web1" CA ssh-ed25519 SHA256:foj... valid from 2026-09-28T19:42:00 to 2027-09-27T19:43:36
debug1: Host '[localhost]:2297' is known and matches the ED25519-CERT host certificate.
```

最初の接続でも fingerprint の確認を求められません。**TOFU（第 106 回）が、CA の公開鍵を配る 1 回の作業に置き換わりました**。サーバを作り直してホスト鍵が変わっても、新しい鍵に CA が署名していれば警告は出ません。逆に、CA が署名していても名前が principals に無ければ拒否されます。

```
$ ssh -F ssh_config -o UserKnownHostsFile=kh_any -o HostKeyAlias=db1.internal alice@lab true
Certificate invalid: name is not a listed principal
No ED25519 host key is known for db1.internal and you have requested strict checking.
Host key verification failed.
```

<Callout type="warn" title="よくある誤解: 「SSH 証明書は X.509 の証明書と同じもの」">
  考え方（CA が鍵と名前を署名で結び付ける）は同じですが、別の形式です。ASN.1 も DER も使わず、SSH の通常の符号化で書かれ、
  中間 CA の連鎖、CRL の配布点、OCSP はありません。信頼するルートも OS やブラウザのトラストストア（第 102 回）ではなく、
  `TrustedUserCAKeys` と `@cert-authority` に**自分で書いた CA だけ**です。
  そのため Web の公開 CA に SSH 証明書を発行してもらうことはできず、CA は自分たちで持ちます。
</Callout>

## 失効: 数えきれるうちは KRL、その先は短命に

長く有効な証明書を発行すれば、失効の問題が戻ってきます（第 103 回で見た、Web の証明書と同じ問題です）。OpenSSH には **KRL（Key Revocation List）** があり、serial、Key ID、公開鍵そのものの単位で失効を書けます（[ssh-keygen(1)](https://man.openbsd.org/ssh-keygen.1) の KEY REVOCATION LISTS）。

```
$ printf 'serial: 1001\n' > revoke.txt
$ ssh-keygen -k -f revoked.krl -s user_ca.pub revoke.txt
$ ssh-keygen -Q -f revoked.krl alice-cert.pub
alice-cert.pub (alice@laptop): REVOKED
（sshd_config に RevokedKeys /etc/ssh/revoked.krl を足して再読み込み）
$ ssh -F ssh_config alice@lab true
alice@localhost: Permission denied (publickey).

（sshd のログ）
Authentication key ED25519-CERT SHA256:9DvP... revoked by file /etc/ssh/revoked.krl
```

ただし KRL も**全サーバに配る**必要があり、配り損ねたサーバでは失効が効きません。authorized_keys を配る問題が、形を変えて残っています。

そこで大規模な運用では、**証明書の寿命を数時間から 1 日に縮め、失効をほぼ使わない**方向に進みました。1 日で切れる証明書なら、退職者の対処は「次から発行しない」だけで済みます。

<Callout type="warn" title="よくある誤解: 「証明書にすれば鍵の配布も失効も要らなくなる」">
  配らなくてよくなるのは**利用者ごとの公開鍵**だけです。CA の公開鍵は全サーバ（と全クライアント）に配る必要があり、
  CA を替えるときは新旧を併記して移行します。失効も、寿命が長ければ KRL の配布が要ります。
  そして **CA の秘密鍵 1 本が漏れれば、全サーバに誰としてでも入れます**。証明書は配布の手間を、
  CA の鍵を守る問題（第 100 回の KMS や HSM）に集めて置き換えるものです。
</Callout>

## SSO と組み合わせる: 短命な証明書と、鍵を配らない方式

短命な証明書を毎日手で発行するのは現実的ではありません。そこで、**会社の IdP（第 17〜18 章）でログインした人に、その場で数時間だけの証明書を発行する**仕組みが使われます。

```
 利用者 ──(1) ブラウザで SSO ログイン──→ IdP
   │   ←──(2) ID トークン（第 113 回）──┘
   │ ──(3) 公開鍵 + ID トークン ──→ SSH CA
   │                                  IdP の署名を検証し、グループから principals を決め
   │ ←──(4) 8 時間だけのユーザ証明書 ──┘ CA の秘密鍵で署名（KMS や HSM の中）
   │
   └──(5) 証明書で ssh ──→ サーバ（TrustedUserCAKeys に CA が 1 行）
```

サーバは IdP を知りません。知っているのは CA の公開鍵だけです。**誰なのか（IdP）と、どの鍵か（証明書）が、CA の署名で結び付けられ**、サーバはその署名を確かめるだけで済みます。

| 仕組み | やり方 | 出典 |
| --- | --- | --- |
| Teleport | SSO ログイン後に、数分から数時間で切れる証明書を発行 | [Teleport](https://goteleport.com/docs/reference/architecture/authentication/) |
| step-ca | OIDC のプロビジョナでユーザ証明書、ホスト証明書も発行 | [step-ca](https://smallstep.com/docs/step-ca/) |
| Vault の SSH シークレットエンジン | Vault が CA となり、短い TTL で利用者の鍵に署名 | [Vault](https://developer.hashicorp.com/vault/docs/secrets/ssh/signed-ssh-certificates) |
| Google Cloud の OS Login | Linux のアカウントを Google の ID と IAM に結び付ける。証明書の必須化や 2 段階認証も選べる | [OS Login](https://docs.cloud.google.com/compute/docs/oslogin) |
| EC2 Instance Connect | IAM で許された利用者の公開鍵を、インスタンスのメタデータに **60 秒だけ**置き、sshd の `AuthorizedKeysCommand` で引かせる | [AWS](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/connect-linux-inst-eic.html) |
| SSM Session Manager | インスタンス上のエージェントがシェルを渡し、sshd の受信ポートを開けずに済む。「受信ポート、踏み台、SSH の鍵が要らない」 | [AWS](https://docs.aws.amazon.com/systems-manager/latest/userguide/session-manager.html) |
| IAP の TCP 転送 | 外部 IP の無い VM への SSH を、IAM で許された利用者にだけトンネルで通す | [Google Cloud](https://docs.cloud.google.com/iap/docs/using-tcp-forwarding) |

上の 3 つは **SSH 証明書を短命に発行する型**、OS Login と EC2 Instance Connect は **authorized_keys の中身をクラウドの IAM から引く型**、下の 2 つは **SSH の入口そのものをクラウドの ID で守る型**です。どれも、長く生きる公開鍵をサーバに置かない点で共通しています。この組み立ては第 121 回で、構成の型の 1 つとしてもう一度見ます。

## 鍵の種類を選ぶ

利用者の鍵は、執筆時点では **Ed25519** が `ssh-keygen` の既定で（[ssh-keygen(1)](https://man.openbsd.org/ssh-keygen.1)）、短く、速く、署名に乱数を使わない（第 98 回）ので、特に理由がなければこれを選びます。RSA は古いサーバや機器との互換のために残します。

さらに一段強くするなら、OpenSSH 8.2（2020 年 2 月）で入った **FIDO の sk 鍵**（`ed25519-sk`、`ecdsa-sk`）です（[リリースノート](https://www.openssh.org/txt/release-8.2)）。

- 秘密鍵ファイルに入るのは**鍵ハンドル**だけで、本当の秘密鍵はセキュリティキーの中から出てきません。ファイルが盗まれても、キーが無ければ署名できません
- 署名のたびに**キーに触れる**ことを求めます。エージェント転送先の root が署名を頼んでも、手元で誰も触れなければ署名されません
- 証明書の critical option `verify-required` で PIN や生体認証まで求められ、逆に `no-touch-required` の拡張で自動処理用に触れる確認を外すこともできます（PROTOCOL.certkeys）

## Git のコミットにも同じ鍵で署名する

SSH の鍵は、ログイン以外にも使えます。Git 2.34（2021 年 11 月）から、GPG の代わりに SSH の鍵でコミットに署名できます（[Git 2.34 のリリースノート](https://github.com/git/git/blob/master/Documentation/RelNotes/2.34.0.adoc)）。署名の実体は `ssh-keygen -Y sign` で、検証には「どのメールアドレスにどの公開鍵を認めるか」を書いた allowed_signers ファイルを使います。

```
$ echo "alice@example.com namespaces=\"git\" $(cat alice.pub)" > allowed_signers
$ git -c gpg.format=ssh -c user.signingkey=$PWD/alice -c commit.gpgsign=true \
      commit -q --allow-empty -m first
$ git -c gpg.ssh.allowedSignersFile=$PWD/allowed_signers log --show-signature -1
commit 6a47a2e2bd3b5c6a1314564f954b0d8316baa9ae
Good "git" signature for alice@example.com with ED25519 key SHA256:9DvPmAeyL89K/Za8Q127yNjkwcnPYCMLNYH7syIoZi0
$ git cat-file -p HEAD | sed -n 4,5p
gpgsig -----BEGIN SSH SIGNATURE-----
 U1NIU0lHAAAAAQAAADMAAAALc3NoLWVkMjU1MTkAAAAgP+TvbXJm7nUAjm2aGWSPgF5ncG
```

`namespaces="git"` は、この署名が Git のためのものだと示す印で、ログイン用の署名やファイルへの署名と取り違えられないようにしています。ここでも、署名が示すのは「この鍵で署名された」ことだけで、その鍵が alice のものだと言っているのは allowed_signers という**別の仕組み**です（第 98 回）。

## この部品は何と組み合わさるか

| 部品 | 保証するもの | 保証しないもの | 組み合わせる相手 |
| --- | --- | --- | --- |
| ssh-agent | 秘密鍵を持ち出させない | 話しかけられる者に署名させないこと | ファイルの権限（第 43 回）、`ssh-add -t` `-c` `-h` |
| ProxyJump | 踏み台に鍵も平文も渡さない | 踏み台に入れる人の管理 | 内側のホスト鍵の確認（第 106 回） |
| ユーザ証明書 | この鍵が、この principals で、この期間使える | 鍵の向こうの人が誰か | CA の鍵の保管（第 100 回）、IdP（第 113 回） |
| ホスト証明書 | このホスト鍵が、この名前のもの | そのサーバの中身が安全か | `@cert-authority`、第 106 回の鍵交換と署名 |
| KRL / 短命化 | 使わせたくない証明書を止める | 配り損ねたサーバでの失効 | 構成管理、正しい時計 |

第 106 回の SSH のトランスポート（鍵交換、署名、AEAD）の上に、この回の部品が載って、初めて「大勢が、鍵を配らずに、辞めた人を締め出しながら」使える形になります。

## まとめ

- ssh-agent は秘密鍵をメモリに持ち、署名だけを引き受ける。約束は「鍵を持ち出させない」ことで、話しかけられる者は鍵を使える（RFC 9987）
- エージェント転送では鍵は渡らないが、接続中は転送先の root が署名を代行させられる。既定は `no`。必要なら `ssh-add -c` や `-h` の宛先制限で絞る
- 踏み台は ProxyJump で越える。踏み台は TCP を中継するだけで、内側との認証も暗号化も手元で完結する
- SSH 証明書は、CA が「この鍵は、この principals で、この期間」と署名したもの。サーバは `TrustedUserCAKeys`、クライアントは `@cert-authority` に CA を 1 行書けば、authorized_keys と known_hosts を配らずに済む
- critical options は制限、extensions は許可。`force-command` や `source-address` で証明書ごとにできることを絞れる
- 失効は KRL でできるが、配布の問題が残る。大規模では寿命を数時間に縮め、SSO でログインした人にその場で発行する
- クラウドには、鍵を IAM から引く型（OS Login、EC2 Instance Connect）や、SSH の入口自体を閉じる型（SSM Session Manager、IAP）もある
- 鍵は Ed25519 を基本に、より強くするなら FIDO の sk 鍵。同じ鍵で Git のコミットにも署名できる

この章では、第 15 章の部品を組み合わせて、**相手の鍵を確かめて話す**ところまで来ました。TLS ではサーバの鍵を CA の署名で、SSH ではホスト鍵を known_hosts や CA で確かめ、クライアント証明書や SSH の公開鍵認証で相手の鍵も確かめられます。しかし分かったのは、あくまで「どの鍵か」です。**その鍵の向こうにいる人は誰で、何をしてよいのか。** 第 17 章では、認証と認可を分けるところから始めます。
