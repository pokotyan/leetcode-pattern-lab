## この章で見るもの

第 31 章では、守りが効き続けていることを確かめ、証跡に残し、それを組織として回し続けるところまでを見ました。第 242 回の脅威モデリングでは「何を守るか」を DFD の上で洗い出し、第 247 回ではテナントの境界を DB の側で強制し、第 249 回では監査ログを改ざんに気づける形で残し、第 250 回ではリスクから管理策を選ぶ ISMS の仕組みを見ました。

けれど、第 31 章を通じて、ある問いには答えていません。**守る対象のうち、どれを、どこまで守らなければならないのか**。これを決めているのは、技術ではなく法律です。

- ユーザーテーブルに列を 1 つ足すとき、その列は法律上の「個人データ」になるのか
- アクセスログに残っている IP アドレスや Cookie の値は、個人情報なのか
- 分析基盤にコピーしたイベントのテーブルは、元のユーザーテーブルと同じ扱いが必要なのか
- 欧州の利用者が 1 人でもいたら、GDPR が関係してくるのか

第 32 章では、作るものと法律の接点を 9 回に分けて扱います。

## 日本の法律の地図: 定義が 8 つある

日本で個人情報の扱いを定めているのは、個人情報の保護に関する法律（平成 15 年法律第 57 号。以下「個人情報保護法」）です（[e-Gov 法令検索](https://laws.e-gov.go.jp/law/415AC0000000057)）。民間の事業者に関する部分は、主に第 4 章（第 16 条〜第 59 条）にあります。

この法律は、似た言葉をいくつも使い分けます。個人情報保護委員会のガイドラインも、わざわざ注意を促しています（[個人情報保護法ガイドライン（通則編）2-7](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)）。

> 法は、「個人情報」、「要配慮個人情報」、「個人データ」、「保有個人データ」、「個人関連情報」、「仮名加工情報」、「匿名加工情報」等の語を使い分けており、個人情報取扱事業者等に課される義務はそれぞれ異なるので、注意を要する。

まず全体を 1 枚にします。

```
              生存する個人に関する情報
  ┌───────────────────────────────────────────────────────────────┐
  │ 個人情報（第 2 条第 1 項）                                       │
  │   ・記述等で特定の個人を識別できる（容易照合を含む）             │
  │   ・個人識別符号（第 2 条第 2 項）を含む                         │
  │   ┌────────────────────────────────────────────┐                 │
  │   │ 要配慮個人情報（第 2 条第 3 項）            │  ← 性質で切る   │
  │   └────────────────────────────────────────────┘                 │
  │   ┌────────────────────────────────────────────┐                 │
  │   │ 個人データ（第 16 条第 3 項）               │  ← 置き方で切る │
  │   │  = 個人情報データベース等を構成する個人情報 │                 │
  │   │   ┌─────────────────────────────────┐       │                 │
  │   │   │ 保有個人データ（第 16 条第 4 項）│      │  ← 権限で切る   │
  │   │   └─────────────────────────────────┘       │                 │
  │   └────────────────────────────────────────────┘                 │
  ├───────────────────────────────────────────────────────────────┤
  │ 仮名加工情報（第 2 条第 5 項） 照合しない限り識別できないよう加工 │
  │ 匿名加工情報（第 2 条第 6 項） 識別できず、復元もできないよう加工 │
  ├───────────────────────────────────────────────────────────────┤
  │ 個人関連情報（第 2 条第 7 項） 上のどれにも当たらないもの         │
  └───────────────────────────────────────────────────────────────┘
```

個人情報の内側の 3 つは、切り口がそれぞれ違います。**要配慮個人情報は中身の性質**で、**個人データは置き方**（データベースに入っているか）で、**保有個人データは権限**（開示や削除に応じる権限を持つか）で決まります。そして外側の個人関連情報は、「生存する個人に関する情報」のうち、どの箱にも入らない残りです。

## 個人情報: 「特定の個人を識別できる」

第 2 条第 1 項は、個人情報を次のように定めています（[e-Gov 法令検索](https://laws.e-gov.go.jp/law/415AC0000000057)）。

> この法律において「個人情報」とは、生存する個人に関する情報であって、次の各号のいずれかに該当するものをいう。
> 一 当該情報に含まれる氏名、生年月日その他の記述等（…）により特定の個人を識別することができるもの（他の情報と容易に照合することができ、それにより特定の個人を識別することができることとなるものを含む。）
> 二 個人識別符号が含まれるもの

要素を分けると、次の 3 つです。

| 要素 | 意味 | エンジニアの言葉で言うと |
| --- | --- | --- |
| 生存する個人に関する情報 | 死者や法人の情報は原則として含まない | 対象は「生きている人の行」 |
| 特定の個人を識別できる | 「どこの誰か」が分かる | 氏名や顔写真がある行 |
| 容易照合を含む | 手元の別の情報と突き合わせれば分かる | **JOIN すれば氏名に届く行** |

ガイドラインが挙げる例には、本人の氏名、氏名と組み合わせた生年月日や連絡先、防犯カメラの映像、`kojin_ichiro@example.com` のように所属と氏名が読み取れるメールアドレスなどがあります。さらに、取得したときは識別できなかった情報でも、**後から情報が付け加えられて識別できるようになれば、その時点で個人情報になる**とも書かれています（[ガイドライン（通則編）2-1](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)）。

ここで大事なのは、**判断の単位が列ではなく、情報のまとまり**だということです。氏名の列がある行では、同じ行の購入履歴も年齢も、全体として 1 つの個人情報になります。ガイドラインや Q&A が「当該情報とあわせて全体として個人情報に該当する」という言い回しを繰り返し使うのはそのためです。

### 住所、電話番号、メールアドレスは単独でどうか

よく聞かれる問いに、Q&A は次のように答えています（[個人情報保護法ガイドラインに関する Q&A](https://www.ppc.go.jp/personalinfo/faq/APPI_QA/)）。

| 情報 | Q&A の答え（要旨） | 出典 |
| --- | --- | --- |
| 氏名だけ | 同姓同名がいても、社会通念上、特定の個人を識別できるので個人情報 | Q1-2 |
| 住所や電話番号だけ | 個別に判断。容易照合で識別できれば、全体として個人情報になりうる | Q1-3 |
| メールアドレスだけ | ユーザー名とドメインから個人が分かれば単独で個人情報。それ以外は容易照合しだい | Q1-4 |
| オンラインゲームのニックネームや ID | 通常は識別できないので個人情報ではない。ただし手元の情報と容易に照合できれば該当しうる | Q1-9 |

つまり、**同じ列でも、値の中身と、事業者が手元に何を持っているかで結論が変わります**。メールアドレスの列は、`taro.yamada@example.com` の行では単独で個人情報になりえ、`x7k2q@example.net` の行では照合の経路しだいです。列の型や名前だけを見て機械的には決められません。後の実験で、これを出力に出します。

### 容易照合性: 「JOIN できるか」の法律版

容易照合性は、この回で最も重要な概念です。ガイドラインは次のように説明しています（[ガイドライン（通則編）2-1 ※4](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)）。

> 「他の情報と容易に照合することができ」るとは、事業者の実態に即して個々の事例ごとに判断されるべきであるが、通常の業務における一般的な方法で、他の情報と容易に照合することができる状態をいい、例えば、他の事業者への照会を要する場合等であって照合が困難な状態は、一般に、容易に照合することができない状態であると解される。

Q&A は、エンジニアにとってより具体的な 2 つの答えを示しています（[Q&A Q1-18・Q1-19](https://www.ppc.go.jp/personalinfo/faq/APPI_QA/)）。

- 顧客 ID のような**共通の識別子**が割り当てられていて、事業者の内部で氏名などと一緒に参照できる場合は、容易に照合できると解されうる（Q1-19）
- 部門ごとに別々のデータベースがあっても、それだけでは足りない。**規程上・運用上、双方のデータベースを扱うことが厳格に禁止されていて**、通常の業務における一般的な方法で照合できない状態なら、容易に照合できない状態と考えられる。逆に、通常の業務で照合できる状態なら、容易に照合できる（Q1-18）

これを技術の言葉に直すと、次のようになります。

| 状態 | 容易照合性の見込み |
| --- | --- |
| `events.user_id` と `users.user_id` が同じ DB にあり、分析担当が両方に SELECT できる | 照合できる |
| 分析基盤には `user_id` だけをコピーしたが、分析担当は本番の `users` も読める | 照合できる |
| 分析基盤の担当者は本番 DB の権限を持たず、規程でも結合が禁止され、運用でも守られている | 照合できない状態と考えられる |
| 突き合わせには、広告事業者など**他社への問い合わせ**が要る | 一般に照合できない |

2 行目に注意してください。データをコピーするときに氏名を落としても、**同じ会社の誰かが日常の業務で両方を見られるなら**、コピー先も個人情報のままです。逆に、3 行目のように照合できない状態にするには、第 247 回で見た権限の分離のような技術的な仕組みと、規程と、運用の 3 つが揃っている必要があります。権限の設定は**法律上の分類を左右する設計判断**でもあるわけです。

<Callout type="note" title="判断するのは「自分の手元」で">
  個人情報保護法の容易照合性は、その情報を取り扱う事業者自身が、通常の業務で照合できるかで判断します。
  そのため、同じデータでも、渡す側では個人データ、受け取る側では個人データではない、ということが起こります。
  この「どちらの手元で判断するか」が、個人関連情報の第三者提供（第 31 条）の規律の出発点です。第 253 回で扱います。
</Callout>

## 個人識別符号: それ単体で個人情報になる符号

容易照合性の判断が要らない、例外的な類型があります。第 2 条第 2 項の**個人識別符号**です。これを含む情報は、ほかの情報と照合するまでもなく個人情報になります。

条文は 2 つの号に分かれていますが、具体的に何が当たるかは政令と委員会規則が列挙しています（[ガイドライン（通則編）2-2](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)）。

| 種類 | 例 |
| --- | --- |
| 身体の特徴を電子計算機で使うために変換した符号（第 1 号） | DNA の塩基配列、顔の容貌、虹彩、声紋、歩き方、静脈の形、指紋・掌紋から作った、本人を認証できる水準のデータ |
| 役務の利用やカードなどで割り当てられる符号（第 2 号） | 旅券の番号、基礎年金番号、運転免許証の番号、住民票コード、個人番号（マイナンバー）、各種の健康保険の被保険者番号、在留カードの番号など |

第 1 号は「顔写真」そのものではなく、顔から抽出した**認証に使える特徴量**を指します。Q&A は、録音した音声から特徴を抽出して話者認識に使えるデータに変換した場合、そのデータは個人識別符号に当たり、それ単体で個人情報になるとしています（[Q&A Q1-11](https://www.ppc.go.jp/personalinfo/faq/APPI_QA/)）。

逆に、**携帯電話番号とクレジットカード番号は個人識別符号ではありません**。Q&A は、契約形態や運用の実態がさまざまで、どんな場合でも特定の個人を識別できるとは限らないことを理由に挙げています（[Q&A Q1-25](https://www.ppc.go.jp/personalinfo/faq/APPI_QA/)）。もちろん、氏名などと容易に照合できれば個人情報です。「カード番号は個人識別符号だから特別に扱う」という整理は、法律の定義としては正しくありません（安全管理の上で特別に扱うべきかは別の話です）。

## 要配慮個人情報: 中身の性質で切る

第 2 条第 3 項の**要配慮個人情報**は、人種、信条、社会的身分、病歴、犯罪の経歴、犯罪の被害を受けた事実などが含まれる個人情報です。政令は、障害があること、健康診断の結果、医師の指導や診療・調剤を受けたこと、刑事事件や少年保護事件の手続を受けたことを加えています（[ガイドライン（通則編）2-3](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)）。

要配慮個人情報は、**取得するときに原則として本人の同意が要ります**（第 20 条第 2 項）。普通の個人情報は、利用目的を通知・公表すれば取得できるのと対照的です。エンジニアが出会うのは、問診のフォーム、福利厚生の申請、カスタマーサポートの自由記述欄などです。自由記述欄は、**設計者が想定していない要配慮個人情報が入り込む**典型的な場所です。

## 個人データと保有個人データ: 置き方と権限で切る

### 個人データ: データベースに入った個人情報

第 16 条第 1 項は、個人情報を含む情報の集まりで、特定の個人情報を**コンピュータで検索できるように体系的に構成したもの**を「個人情報データベース等」と呼びます。それを構成する個人情報が**個人データ**です（第 16 条第 3 項）。

紙の名刺の束なら議論の余地がありますが、エンジニアが扱うものは、ほぼ例外なく個人データです。ガイドラインは、ユーザー ID で整理して保管されたサービスの利用ログの電子ファイルを、ユーザー ID と個人情報を容易に照合できる場合の例として挙げ、さらに、データベースから外部の記録媒体に保存したものや、紙に出力した帳票に印字されたものも個人データだとしています（[ガイドライン（通則編）2-4・2-6](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)）。**CSV にエクスポートしても、個人データであることは変わりません**。

### 保有個人データ: 開示や削除に応じる権限があるか

個人データのうち、事業者が開示、訂正、利用停止、消去などに応じる**権限を持つもの**が**保有個人データ**です（第 16 条第 4 項）。本人からの開示や削除の請求（第 33 条以降）は、この保有個人データが対象です。

エンジニアにとって重要なのは、**SaaS として顧客企業のデータを預かっている場合**です。Q&A は、委託によって取り扱う個人データについて、特に定めがない限り委託元の保有個人データになると考えられ、委託先が自らの判断で開示等をする権限を与えられていないときは委託元の保有個人データになる、としています（[Q&A Q1-56](https://www.ppc.go.jp/personalinfo/faq/APPI_QA/)）。

つまり、B2B の SaaS が預かる顧客企業のエンドユーザーのデータは、SaaS の事業者にとって**個人データではあるが、保有個人データではない**ことが多い、ということです。エンドユーザーから直接「私のデータを消して」と言われたとき、誰が判断するのかはここで決まります。第 255 回で詳しく扱います。

### 義務はどの箱にかかるか

| 義務 | 対象 | 条 |
| --- | --- | --- |
| 利用目的の特定、目的外利用の制限 | 個人情報 | 第 17・18 条 |
| 不適正な利用の禁止、適正な取得 | 個人情報 | 第 19・20 条 |
| 取得時の利用目的の通知・公表 | 個人情報 | 第 21 条 |
| 正確性の確保、不要になったら遅滞なく消去（努力義務） | 個人データ | 第 22 条 |
| 安全管理措置、従業者と委託先の監督 | 個人データ | 第 23〜25 条 |
| 漏えい等の報告と本人への通知 | 個人データ | 第 26 条 |
| 第三者提供の制限、外国にある第三者への提供 | 個人データ | 第 27・28 条 |
| 個人関連情報の第三者提供の確認 | 個人関連情報 | 第 31 条 |
| 公表事項、開示・訂正・利用停止等の請求への対応 | 保有個人データ | 第 32〜39 条 |

（条番号は 2026 年 11 月時点の e-Gov の現行条文によります。[e-Gov 法令検索](https://laws.e-gov.go.jp/law/415AC0000000057)）

第 253 回から第 256 回は、この表の下半分を 1 回ずつ扱います。

## 個人関連情報: どの箱にも入らないもの

第 2 条第 7 項の**個人関連情報**は、「生存する個人に関する情報であって、個人情報、仮名加工情報及び匿名加工情報のいずれにも該当しないもの」です。2020 年の改正（2022 年 4 月施行）で入った定義です。

ガイドラインは、次を個人関連情報の例に挙げています（[ガイドライン（通則編）2-8](https://www.ppc.go.jp/personalinfo/legal/guidelines_tsusoku/)）。

- Cookie 等の端末識別子を通じて収集された、ある個人のウェブサイトの閲覧履歴
- メールアドレスに結び付いた、ある個人の年齢・性別・家族構成等
- ある個人の商品購買履歴・サービス利用履歴
- ある個人の位置情報
- ある個人の興味・関心を示す情報

そして同じ箇所で、位置情報も、連続的に蓄積されて特定の個人を識別できるようになれば個人情報であり、個人関連情報には当たらないと注記しています。

Cookie については、Q&A がもう一歩踏み込んでいます（[Q&A Q8-1](https://www.ppc.go.jp/personalinfo/faq/APPI_QA/)）。

> 個別の事案ごとに判断することとなりますが、Cookie等の端末識別子について、個人情報に該当しない場合には、通常、当該端末識別子に係る情報端末の利用者に関する情報として、「個人に関する情報」に該当し、個人関連情報に該当することとなると考えられます。

同じ答えは、家族で端末を共用していても通常は共用者それぞれに関する情報になること、他の情報と容易に照合できれば全体として個人情報になることも述べています。

### Cookie ID、IP アドレス、広告 ID の分かれ目

ここまでをまとめると、端末や通信の識別子は、次のように分かれます。

| 状況 | 日本法での見込み |
| --- | --- |
| Cookie ID と閲覧履歴だけを持ち、会員情報と結び付ける経路がない | 個人関連情報 |
| ログイン後の閲覧で、Cookie ID と会員 ID が同じ行に記録されている | 会員情報と容易に照合できれば、全体として個人情報 |
| 自社では誰か分からないが、提供先が会員 ID と結び付けて使う想定 | 自社にとっては個人関連情報。提供には第 31 条の確認が要る（第 253 回） |

**IP アドレス**は、ガイドラインの個人関連情報の例にも、個人識別符号の一覧にも、名前が挙がっていません。考え方は Cookie と同じで、容易照合の経路があるかどうかで決まると考えるのが自然ですが、名指しした記述は見つかりませんでした。技術的な事情としては、第 64 回で見たとおり、日本の家庭の IPv4 接続では 1 つのアドレスを複数の契約者で共有する方式も広がっており、IP アドレスだけで個人や世帯に結び付くとは限りません。一方で、ログイン中のアクセスログに会員 ID と並んで記録された IP アドレスは、その行全体が個人情報になります。

**広告 ID**（iOS の IDFA、Android の広告 ID）も、ガイドラインや Q&A で名指しされている箇所は見つかりませんでした。Q&A の言う「Cookie 等の端末識別子」と同じ考え方で扱うのが自然ですが、これは本文からの推論です。

<Callout type="note" title="ログは、思わぬ列を持っている">
  アクセスログには、IP アドレスと Cookie だけでなく、URL のクエリ文字列も残ります。
  `?email=...` のような形でメールアドレスを URL に載せるリンクや、エラーログに丸ごと出力された要求の本文は、
  **ログを個人情報の置き場に変えます**。第 249 回で監査ログに「書かないもの」を決めたのと同じ判断が、ここでも要ります。
</Callout>

## 仮名加工情報と匿名加工情報

2 つの加工情報は、第 2 条第 5 項と第 6 項で定義されています（[e-Gov 法令検索](https://laws.e-gov.go.jp/law/415AC0000000057)）。

| | 仮名加工情報 | 匿名加工情報 |
| --- | --- | --- |
| 加工の目標 | **他の情報と照合しない限り**特定の個人を識別できない | 特定の個人を識別できず、**復元もできない** |
| 代表的な加工 | 氏名を削り、会員 ID を規則性のない仮 ID に置き換える | 加えて、属性を丸め、珍しい値を削り、集団の中に埋もれさせる |
| 主な使い道 | 社内での分析（利用目的の変更がしやすくなる） | 第三者への提供（本人同意なしに提供できる） |
| 第三者提供 | 原則として禁止（第 42 条） | 公表などの手続を踏めば可能（第 44 条） |
| 作成の基準 | 委員会規則の基準（第 41 条） | 委員会規則の基準（第 43 条） |

定義の言い回しを比べると、違いが見えます。仮名加工情報は「照合しない限り」識別できないもので、**照合すれば戻せる**ことを前提にしています。作成元の手元には対応表（削除情報等）が残るため、作成元にとって仮名加工情報は、多くの場合なお個人情報です。匿名加工情報は「復元することができないようにしたもの」で、戻せないことが要件です。

どちらも、**法律の定める基準に沿って作り、作成時の義務を果たして初めて**この制度に乗ります。「ハッシュにしたから匿名だ」は、この両方の意味で成り立ちません。第 252 回で、ハッシュ化したメールアドレスを総当たりで元に戻して確かめます。

## GDPR の personal data: 「識別可能」の幅

EU の一般データ保護規則（GDPR、Regulation (EU) 2016/679）は、personal data を次のように定めています（[GDPR Art. 4(1)](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32016R0679)）。

> 'personal data' means any information relating to an identified or identifiable natural person ('data subject'); an identifiable natural person is one who can be identified, directly or indirectly, in particular by reference to an identifier such as a name, an identification number, location data, an online identifier or to one or more factors specific to the physical, physiological, genetic, mental, economic, cultural or social identity of that natural person;

識別子の例に、最初から **online identifier** が入っています。前文 30 は、それが何を指すかを具体的に書いています（[GDPR Recital 30](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32016R0679)）。

> Natural persons may be associated with online identifiers provided by their devices, applications, tools and protocols, such as internet protocol addresses, cookie identifiers or other identifiers such as radio frequency identification tags.

さらに前文 26 は、識別可能かどうかを判断するとき、管理者**または他の者**が合理的に使う見込みのあるすべての手段を考慮し、その中に **singling out**（1 人を他から選り分けること）も含めるとしています（[GDPR Recital 26](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32016R0679)）。

### 日本と EU の考え方の違い

| | 日本（個人情報保護法） | EU（GDPR） |
| --- | --- | --- |
| 中心の概念 | 特定の個人を**識別できる**情報 | 識別された、または**識別可能な**自然人に関する情報 |
| 照合の範囲 | その事業者が**通常の業務で容易に**照合できるか | 管理者または他の者が**合理的に使う見込みのある手段**（singling out を含む） |
| Cookie ID・IP アドレス | 照合の経路がなければ個人関連情報 | 定義と前文がオンライン識別子として名指し。personal data になることが多い |
| 個人に関する情報だが識別できないもの | 個人関連情報として、主に第三者提供の場面で規律 | そもそも「識別可能」の範囲に入ることが多い |
| 特別な種類 | 要配慮個人情報（取得に同意が原則必要） | Art. 9 の special categories（処理を原則禁止し、例外を列挙） |
| 仮名化 | 仮名加工情報という独自の制度 | Art. 4(5) の pseudonymisation。仮名化したデータも、原則として personal data のまま |

大まかに言えば、**日本は「誰か分かるか」で個人情報の範囲を切り、その外側の「誰かに関する情報」を個人関連情報として別に扱います。EU は「識別可能」を広く取り、Cookie ID だけのイベントログも、多くの場合 personal data の内側に入ります**。日本法で「個人関連情報だから個人データの規律はかからない」と整理したテーブルが、GDPR の下では personal data として全面的に扱う必要がある、ということは普通に起こります。

### EU の側でも「誰の手元で判断するか」が問われている

ただし、EU の「識別可能」もいつも無限に広いわけではありません。

- 2016 年の Breyer 事件で、EU 司法裁判所は、ウェブサイトの運営者が記録した動的 IP アドレスについて、運営者が接続事業者の持つ追加の情報によって利用者を識別する**法的な手段を持つ場合**には、運営者にとって personal data になると判断しました（[C-582/14 Breyer](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:62014CJ0582)）。
- 2025 年 9 月 4 日の EDPS 対 SRB 事件で、同じ裁判所は、仮名化されたデータが**すべての場合に、すべての者にとって** personal data だとみなすべきではなく、受け取った側が合理的に識別できない場合にはその者にとって personal data でないことがありうる、と判断しました。同時に、情報提供義務との関係では、識別可能性はデータを集めた時点で**管理者の立場から**判断するとしています（[C-413/23 P EDPS v SRB](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:62023CJ0413)）。

欧州委員会は 2025 年 11 月 19 日に、GDPR などを改める Digital Omnibus の規則案（COM(2025) 837）を提出しました。この案には personal data の定義を、この「誰の手元で判断するか」の方向で書き改める内容が含まれていると報じられています。2026 年 11 月時点で、EUR-Lex の手続の記録には理事会や欧州議会の立場の採択は載っておらず、**審議中**です（[EUR-Lex 手続 2025/0360(COD)](https://eur-lex.europa.eu/procedure/EN/2025_360)）。現行の Art. 4(1) は変わっていません。

## 域外適用: 海外の法律は、海外の会社だけの話ではない

### GDPR の Art. 3

GDPR は、EU 域内に拠点がない事業者にも適用されることがあります（[GDPR Art. 3(2)](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32016R0679)）。

> This Regulation applies to the processing of personal data of data subjects who are in the Union by a controller or processor not established in the Union, where the processing activities are related to:
> (a) the offering of goods or services, irrespective of whether a payment of the data subject is required, to such data subjects in the Union; or
> (b) the monitoring of their behaviour as far as their behaviour takes place within the Union.

(a) は EU の人に向けた商品やサービスの提供、(b) は EU 域内での行動の監視です。日本の会社が日本で作ったサービスでも、EU 向けに提供していれば (a) に、EU にいる人の閲覧行動を追跡してプロファイルを作れば (b) に当たる可能性があります。「EU の人がたまたまアクセスできる」ことと「EU の人に向けて提供している」ことの線引きは、言語、通貨、配送先などの事情から判断されることになり、個別の検討が要ります。

### 個人情報保護法の第 171 条

日本の法律にも同じ向きの規定があります（[個人情報保護法 第 171 条](https://laws.e-gov.go.jp/law/415AC0000000057)）。

> この法律は、個人情報取扱事業者、仮名加工情報取扱事業者、匿名加工情報取扱事業者又は個人関連情報取扱事業者が、国内にある者に対する物品又は役務の提供に関連して、国内にある者を本人とする個人情報、当該個人情報として取得されることとなる個人関連情報又は当該個人情報を用いて作成された仮名加工情報若しくは匿名加工情報を、外国において取り扱う場合についても、適用する。

日本の利用者にサービスを提供する海外の事業者も、日本の利用者の個人情報を海外で扱うときは、日本の法律の対象です。日本の会社から見ると、**海外のクラウドに置いても、海外の子会社が処理しても、日本の利用者のデータには日本の法律がついて回る**ということでもあります。外国にある第三者への提供（第 28 条）とあわせて、第 253 回で扱います。

### EU から日本への十分性認定

EU から日本へ個人データを移すときの土台が、欧州委員会の**十分性認定**です。2019 年 1 月 23 日の欧州委員会実施決定 (EU) 2019/419 は、個人情報保護法の対象となる日本の個人情報取扱事業者に移転される個人データについて、個人情報保護委員会の定めた**補完的ルール**（Supplementary Rules）とあわせて、日本が十分な水準の保護を確保していると認めています（[Commission Implementing Decision (EU) 2019/419 Art. 1](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32019D0419)）。最初の定期的な見直しの報告書は 2023 年 4 月に公表されています（[European Commission: Adequacy decisions](https://commission.europa.eu/law/law-topic/data-protection/international-dimension-data-protection/adequacy-decisions_en)）。

エンジニアにとっての含意は 2 つあります。1 つは、EU の利用者のデータを日本の個人情報取扱事業者が受け取る経路では、標準契約条項（SCC）のような追加の仕組みを使わずに済むこと。もう 1 つは、**受け取ったデータには補完的ルールがかかる**ことです。補完的ルールは、EU から受け取った個人データについて日本法より厳しい扱いを求める部分を含みます。どの部分かは第 253 回で見ます。

## 2026 年 11 月時点の改正の状況

個人情報保護法は、2020 年の改正法の附則で、施行後 3 年ごとに施行状況を検討して必要な措置を講じることになっています。これが「いわゆる 3 年ごと見直し」です。その結果として、2026 年に改正法が成立しました。状況を、施行済み・成立済み（未施行）・審議中に分けて整理します。

| --- | --- | --- |

| 施行済み | 公布の日に施行されたのは附則の一部（附則第 13 条・第 16 条）だけで、本体の条文は 2026 年 11 月時点の現行条文と変わっていない | 改正法附則第 1 条第 1 号（[e-Gov 法令検索](https://laws.e-gov.go.jp/law/415AC0000000057)） |
| 成立済み・未施行（2027 年 1 月 17 日施行） | 公布から 6 か月を経過した日に施行。個人情報データベース等の不正提供罪の加害目的への拡大と法定刑の引上げ、詐欺・暴行・不正アクセス等による個人情報の不正取得罪の新設、公示送達のデジタル化 | 改正法附則第 1 条第 3 号（同上） |

| 検討中 | 政令・委員会規則・ガイドラインは検討中。8 月 26 日に定める事項の全体像を、9 月から 10 月にかけて基本的な考え方の①〜③を委員会で決定。意見募集を経て公布・公表の予定 | [令和 8 年 改正個人情報保護法について](https://www.ppc.go.jp/personalinfo/legal/r8kaiseihogohou/) |

本体の改正の主な項目は、個人情報保護委員会の概要資料によると次のとおりです（[個人情報保護法等の一部を改正する法律について（概要）](https://www.ppc.go.jp/files/pdf/260717_kaiseihounitsuite.pdf)）。

- 統計作成等（統計作成等と整理できる AI 開発等を含む）にのみ使う場合の、第三者提供と公開されている要配慮個人情報の取得について、本人同意を不要にする
- 16 歳未満の本人について、同意や通知の相手を法定代理人とすることを明文化し、利用停止等の請求の要件を緩める
- 顔特徴データ等（改正後の条文では「特定生体個人情報」）について、一定の事項の周知を義務にし、利用停止等の請求の要件を緩め、オプトアウトによる第三者提供を禁止する
- 委託を受けた事業者の義務を見直す
- 漏えい等が起きたとき、本人の権利利益の保護に欠けるおそれが少ない場合に本人への通知義務を緩める
- 個人情報ではないが特定の個人への働きかけが可能になる情報について、不適正な利用と不正な取得を禁止する
- 重大な違反行為に対する**課徴金**制度を導入する

この回の主題である定義には、2 つの新しい言葉が加わります。改正後の第 2 条第 8 項の**連絡可能個人関連情報**は、住居などの所在地、電話番号、電子メールアドレス、電気通信設備を利用する者や設備を識別するために付された符号などで、特定の個人への連絡に利用できるものを含む個人関連情報です。概要資料は、その例として Cookie ID を挙げています。もう 1 つは、改正後の第 16 条第 5 項の**特定生体個人情報**で、本人が気づかないうちに容易に取得できる身体の特徴（顔特徴データ等）から作った個人識別符号を含む個人情報です（改正後の条文は [e-Gov 法令検索の未施行版](https://laws.e-gov.go.jp/law/415AC0000000057/20280716_508AC0000000056) で確認できます。施行日は政令で定められるため、e-Gov 上の日付は仮置きです）。

  ガイドラインや Q&A も改正に合わせて書き換えられる見込みです。この章の条番号や出典は、読む時点で最新のものと照らし合わせてください。

## 実験: テーブルの列とログの 1 行を分類する

ここまでの定義を、小さなスクリプトに落とします。目的は、**規則で決まる部分と、規則では決まらない部分を分けて見ること**です。

### 入力: サンプルのスキーマ

架空の EC サイトのテーブルを 9 つ用意しました。`domain` はテーブルが置かれている区画、`owner` は自社のデータか顧客企業から預かったデータかです。`access` は、区画どうしを通常の業務で突き合わせられるかの運用の実態で、`allowed`（できる）、`forbidden`（規程と権限で禁止されている）、`unknown`（調べていない）のどれかを書きます。

```json
{
```

### 規則

スクリプトの判定は、次の単純な規則です。

1. 列名から役割を推定する（氏名、個人識別符号、要配慮の候補、連絡先、端末・通信の識別子、照合キー、属性）
2. 氏名か個人識別符号の列を持つテーブルは「個人情報」。判断の単位はテーブルの行で、その行の他の列も全体として個人情報になる
3. 照合キー（`user_id`、`email`、`cookie_id` など）を共有するテーブルどうしを辺で結び、辺に区画どうしの `access` を付ける
4. `allowed` の辺だけで 2. のテーブルに届けば「個人情報（容易照合）」。`unknown` の辺を通らないと届かなければ「保留: 容易照合性しだい」
5. どこにも届かないが `email` の列があれば「保留: 値しだい」（Q1-4 のとおり、値の中身で変わる）
6. どこにも届かないが識別子の列があれば「個人関連情報の候補」
7. 個人情報なら個人データ。`owner` が `self` なら保有個人データ、`client` なら委託元の保有個人データ（Q1-56）
8. GDPR の欄は、識別子を持つものを personal data（またはその可能性が高いもの）とする、粗い対比

全体は 135 行です。中心の部分を示します。

```python
import json, re, sys
from collections import deque

NAME = re.compile(r"(^|_)(full_name|customer_name|name)$")
CODE = re.compile(r"passport|my_number|license_no|residence_card|face_template|fingerprint")
SENSITIVE = re.compile(r"diagnosis|medical|criminal|race|religion|disability")
ONLINE_ID = re.compile(r"cookie_id|session_id|ip_address|ad_id|idfa|gaid|device_id")
EMAIL = re.compile(r"email")
KEYS = {"user_id", "customer_no", "cookie_id", "ad_id", "email"}


def access(policy, a, b):
    if a == b:
        return "allowed"
    return policy.get(f"{a}|{b}") or policy.get(f"{b}|{a}") or "forbidden"


def build_edges(tables, policy):
    edges = {t: [] for t in tables}
    names = list(tables)
    for i, a in enumerate(names):
        for b in names[i + 1:]:
            shared = KEYS & set(tables[a]["columns"]) & set(tables[b]["columns"])
            for key in sorted(shared):
                st = access(policy, tables[a]["domain"], tables[b]["domain"])
                edges[a].append((b, key, st))
                edges[b].append((a, key, st))
    return edges


def identifying(cols):
    return any(NAME.search(c) or CODE.search(c) for c in cols)


def find_path(start, tables, edges, allow_unknown):
    ok = {"allowed", "unknown"} if allow_unknown else {"allowed"}
    seen, q = {start}, deque([(start, [])])
    while q:
        t, path = q.popleft()
        if t != start and identifying(tables[t]["columns"]):
            return path
        for nxt, key, st in edges[t]:
            if st in ok and nxt not in seen:
                seen.add(nxt)
                q.append((nxt, path + [f"{t}-[{key}:{st}]->{nxt}"]))
    return None


def classify(tables, policy):
    edges = build_edges(tables, policy)
    for t, meta in tables.items():
        cols = meta["columns"]
        if identifying(cols):
            appi, why = "個人情報", "行の中に氏名か個人識別符号がある"
        elif (p := find_path(t, tables, edges, False)) is not None:
            appi, why = "個人情報（容易照合）", " / ".join(p)
        elif (p := find_path(t, tables, edges, True)) is not None:
            appi, why = "保留: 容易照合性しだい", " / ".join(p)
        elif any(EMAIL.search(c) for c in cols):
            appi, why = "保留: 値しだい", "email の中身から個人が分かるか（Q1-4）"
        elif any(ONLINE_ID.search(c) or c in KEYS for c in cols):
            appi, why = "個人関連情報の候補", "照合の経路が見つからない"
        else:
            appi, why = "個人に関する情報ではない", "人に結び付く列がない"
```

### この実験の限界

- 列名からの推定は、命名の規約に強く依存します。`col_17` のような名前の列は見逃し、`name` という名前の商品名の列は氏名と誤認します
- 自由記述の列（問い合わせ本文など）は、中身を見ない限り、要配慮個人情報が入っているかどうか分かりません
- 判定はテーブルの単位で、行ごとの違い（ある行のメールアドレスだけ氏名を含む）は扱っていません
- `access` の値は、人が調べて書くしかありません。**ここが、規則では決まらない部分の本体です**

規則で決まる部分を機械に任せ、決まらない部分を「保留」として人の判断に回す。データカタログの分類タグや、スキーマの変更時のレビューに組み込むと、少なくとも「誰も判断していない列」を一覧にできます。

## エンジニアが判断を求められる場面

最後に、この回の定義が、実際の作業のどこに降りてくるかを並べます。

| 場面 | 問うべきこと | 関係する定義 | 詳しく扱う回 |
| --- | --- | --- | --- |
| テーブルに列を足す | その列は既存の個人情報の行に入るか。要配慮個人情報か | 個人情報、要配慮個人情報 | この回 |
| 分析基盤にデータをコピーする | コピー先の担当者は、通常の業務で元のテーブルと照合できるか | 容易照合性 | この回、第 252 回 |

| 外部の SaaS や広告事業者にデータを送る | 第三者提供か、委託か。相手の手元で個人データになるか | 個人データ、個人関連情報 | 第 253 回 |
| ページにタグを足す | 利用者の端末から、どこへ何が送られるか | 個人関連情報、外部送信規律 | 第 254 回 |

どの場面でも、最初の問いは同じです。**それは、どの箱に入る情報か**。そして、その答えの多くは、テーブルの定義だけでなく、権限の設定や運用の実態に依存しています。エンジニアが法務に相談するときに渡すべきなのは、「このテーブルは個人情報ですか」という問いではなく、**列の一覧、照合キー、誰がどこに読み取りの権限を持っているか、そのデータがどこから来てどこへ行くか**です。第 242 回で描いた DFD は、その資料としてそのまま使えます。

## まとめ

- 個人情報保護法は、個人情報・個人識別符号・要配慮個人情報・個人データ・保有個人データ・個人関連情報・仮名加工情報・匿名加工情報を使い分け、それぞれに異なる義務をかける
- 個人情報は「特定の個人を識別できる」情報。判断の単位は列ではなく情報のまとまりで、**容易照合性**（事業者が通常の業務で他の情報と照合できるか）を含む
- 容易照合性は、共通の ID と、誰が両方を見られるかで決まる。照合できない状態と言うには、権限の分離と規程と運用が揃っている必要がある（Q1-18・Q1-19）
- 個人識別符号は単体で個人情報になる。生体から作った認証用の特徴量や旅券番号などで、携帯電話番号やクレジットカード番号は含まれない
- データベースに入った個人情報が個人データ、開示や削除に応じる権限があるものが保有個人データ。預かったデータは、多くの場合、委託元の保有個人データになる
- Cookie ID と閲覧履歴は、照合の経路がなければ個人関連情報。IP アドレスや広告 ID は名指しの記述がなく、同じ考え方で判断することになる
- GDPR の personal data は「識別可能」を広く取り、オンライン識別子を名指しする。日本で個人関連情報のテーブルが、EU では personal data になることは普通に起こる
- GDPR は Art. 3 で、個人情報保護法は第 171 条で、国外の事業者にも適用されうる。EU から日本への移転には、補完的ルールつきの十分性認定がある
- 2026 年 7 月に改正法（令和 8 年法律第 56 号）が公布された。罰則の強化は 2027 年 1 月 17 日に、本体は公布から 2 年以内の政令で定める日に施行される。連絡可能個人関連情報、特定生体個人情報、課徴金などが加わり、政令・規則・ガイドラインは検討中
- 列の名前で決まる部分は機械に任せられるが、容易照合性と値の中身で決まる部分は残る。そこを「保留」として人の判断に回し、法務には列と権限とデータの流れを渡す
