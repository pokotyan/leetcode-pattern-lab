## 電源を切っても残るもの

ここまでの章で扱ってきたものは、レジスタ、キャッシュ、メモリ、プロセス。どれも **電源を切れば消えます**。

この章では、消えないものを扱います。ディスクにデータを残すということです。

第 48 回で、ページキャッシュと `fsync` を見ました。そこでは「ファイル」を、読み書きできるバイトの列として扱っていました。この章では、その **ファイルそのものが、ディスクの上でどう表現されているのか** から始めます。

## ディスクはブロックの列でしかない

ディスク（SSD でも HDD でも）が OS に見せているのは、**番号の付いた固定長のブロックの並び**だけです。

```
ブロック番号:   0      1      2      3      4      5     ...
             ┌──────┬──────┬──────┬──────┬──────┬──────┬─────
             │      │      │      │      │      │      │
             └──────┴──────┴──────┴──────┴──────┴──────┴─────
                     「3 番のブロックを読め」「5 番に書け」しか言えない
```

ディスクには、ファイルもディレクトリも名前もありません。**ファイルシステムは、このブロックの列の上に作られたデータ構造**です。第 22 回で見たヒープが、メモリという大きなバイト列の上に malloc が作ったデータ構造だったのと同じ関係です。

ファイルシステムが解くべき問題は、次の 3 つです。

- どのブロックが使用中で、どれが空いているか
- あるファイルの中身は、どのブロックに散らばっているか
- `/home/alice/memo.txt` という名前から、そのファイルにどう辿り着くか

## inode: ファイルの本体

Unix 系のファイルシステムでは、1 つのファイルに 1 つの **inode** が対応します。inode は、ファイルについての情報をまとめた、固定長の小さな構造体です。

`stat` で中身を見られます。

```
$ echo hello > a.txt
$ stat a.txt
  File: a.txt
  Size: 6         	Blocks: 8          IO Block: 4096   regular file
Device: 0,95	Inode: 354797      Links: 1
Access: (0644/-rw-r--r--)  Uid: (    0/    root)   Gid: (    0/    root)
Modify: 2026-09-24 08:42:59.240457002 +0000
Change: 2026-09-24 08:42:59.240457002 +0000
```

| inode が持っているもの | 例 |
| --- | --- |
| 種類 | 通常のファイル、ディレクトリ、シンボリックリンク、デバイス |
| 所有者と権限 | uid 0、gid 0、`rw-r--r--` |
| 大きさ | 6 バイト |
| 時刻 | 最終更新、inode の変更 |
| リンク数 | 1 |
| **中身のありか** | どのブロックにデータがあるか |

ここに **無いもの** が重要です。**ファイル名がありません。**

inode は番号（この例では 354797）で識別されます。第 42 回で見た「fd 表 → オープンファイル表 → inode」の最後の箱が、これです。`open` が返す fd は、最終的にこの番号の inode を指しています。

## ディレクトリは名前の表

では名前はどこにあるのか。**ディレクトリの中身**です。

ディレクトリも、ファイルシステムにとっては 1 つのファイルです。ただし中身が決まっていて、**「名前 → inode 番号」の対応表**が入っています。

```
ディレクトリ /tmp（inode 12）の中身
┌────────────┬──────────┐
│ 名前        │ inode 番号 │
├────────────┼──────────┤
│ .          │ 12       │  自分自身
│ ..         │ 2        │  親ディレクトリ
│ a.txt      │ 354797   │
│ d          │ 354801   │
└────────────┴──────────┘
```

`/tmp/a.txt` を開くとき、カーネルは次のように辿ります。

1. ルートディレクトリの inode（番号はファイルシステムごとに決まっている）を読む
2. その中身から `tmp` を探し、inode 12 を得る
3. inode 12 の中身から `a.txt` を探し、inode 354797 を得る
4. inode 354797 の権限を確かめて開く

**パスの `/` 1 つごとに、ディレクトリを 1 つ読んでいます。** 深いパスを大量に開くプログラムが遅くなりうるのはこのためで、カーネルはこの結果を dentry キャッシュ（後述）に覚えておきます。

<Callout type="note" title="ディレクトリのリンク数">
  空のディレクトリを作ると、リンク数は 2 になります。
  親ディレクトリにある名前と、自分自身の中の `.` の 2 つが、同じ inode を指しているからです。
  中にサブディレクトリを 2 つ作ると 4 になります。それぞれの `..` が指してくるためです。

```
$ mkdir d; stat -c %h d
2
$ mkdir d/x d/y; stat -c %h d
4
```
</Callout>

## ハードリンクとシンボリックリンク

名前と inode が分かれているので、**1 つの inode に複数の名前を付ける**ことができます。これが **ハードリンク** です。

```
$ ln a.txt b.txt        # ハードリンク
$ ln -s a.txt c.txt     # シンボリックリンク
$ ls -li a.txt b.txt c.txt
354797 -rw-r--r-- 2 root root 6 Sep 24 08:42 a.txt
354797 -rw-r--r-- 2 root root 6 Sep 24 08:42 b.txt
354800 lrwxrwxrwx 1 root root 5 Sep 24 08:42 c.txt -> a.txt
```

`a.txt` と `b.txt` は同じ inode 354797 です。**どちらが本物、ということはありません。** 同じファイルに名前が 2 つあるだけで、リンク数が 2 になっています。

`c.txt` は別の inode 354800 を持つ、別のファイルです。中身は `a.txt` という **5 バイトの文字列** で、大きさが 5 と表示されています。カーネルはパスを辿る途中でこれを見つけると、書かれたパスに置き換えて辿り直します。

| | ハードリンク | シンボリックリンク |
| --- | --- | --- |
| 実体 | ディレクトリの表の 1 行 | パスを中身に持つ小さなファイル |
| 指す先 | inode 番号 | パス（文字列） |
| 元の名前を消すと | 何も起きない。残った名前で読める | 行き先が無くなる（dangling link） |
| 別のファイルシステムへ | 張れない。inode 番号はファイルシステムごと | 張れる |
| ディレクトリに | 張れない。木構造に輪ができるため | 張れる |

## 削除は「名前を消す」こと

`rm` が呼ぶシステムコールは `unlink` です。名前のとおり、**ディレクトリの表から 1 行を消して、inode のリンク数を 1 減らす**だけです。

inode とデータのブロックが解放されるのは、次の 2 つが両方とも満たされたときです。

- リンク数が 0 になった
- **その inode を開いている fd が 1 つもない**

つまり、開いたままのファイルは、名前を消しても消えません。

```
$ exec 3<a.txt          # fd 3 で開いておく
$ rm a.txt b.txt        # 名前を 2 つとも消す
$ ls -l /proc/$$/fd/3
lr-x------ 1 root root 64 Sep 24 08:42 /proc/1/fd/3 -> /tmp/a.txt (deleted)
$ cat <&3
hello
```

名前はもうどこにもありませんが、fd 3 から中身を読めます。fd 3 を閉じた瞬間に、初めて領域が解放されます。

<Callout type="warn" title="消したのにディスクが空かない">
  ログファイルを `rm` したのにディスクの空きが増えない、という事故の正体がこれです。
  ログを書き続けているプロセスが fd を開いたままなので、inode は生きています。

```bash
lsof +L1        # リンク数が 1 未満（名前が無い）なのに開かれているファイル
```

  プロセスを再起動するか、fd 経由で中身を空にすれば（`: > /proc/<pid>/fd/<n>`）解放されます。
  ログのローテーションで「名前を変えてから、プロセスに開き直させる」のが基本になっているのは、この性質のためです。
</Callout>

逆に、この性質は便利にも使えます。一時ファイルを作ってすぐ `unlink` すれば、**プロセスが終わった時点で必ず消える** ファイルになります。実行中のプログラムのバイナリを入れ替えられるのも、古い inode が実行中のプロセスに開かれたまま残り、名前だけが新しい inode を指すようになるからです。

## rename は名前の付け替え

`rename` もまた、ディレクトリの表を書き換えるだけの操作です。データのブロックには触りません。何 GB のファイルでも一瞬で終わります。

そして、**同じファイルシステムの中の rename は原子的**です。他のプロセスからは、古いファイルか新しいファイルのどちらかが見え、「どちらも無い」瞬間や「半分だけ新しい」状態は見えません。第 48 回で「`rename` は原子的」と書いたのは、この性質のことです。

ファイルシステムをまたぐと、話が変わります。inode 番号はファイルシステムごとの番号なので、別のファイルシステムの表に書き込めません。`rename` は `EXDEV` というエラーを返し、`mv` コマンドは **コピーしてから元を消す** 動作に切り替えます。時間がかかり、原子的でもありません。

## 中身のありか: ブロックの地図

inode の最後の項目、「中身がどのブロックにあるか」の表し方は、ファイルシステムの設計で最も差が出るところです。

古い ext2 / ext3 は、**ブロック番号を 1 つずつ並べた表**を持っていました。大きなファイルでは表が収まらないので、「ブロック番号の表が入ったブロック」を指す、間接ブロックを重ねます。第 20 回で見た多段のページテーブルと同じ形です。

ext4 は **エクステント** を使います。「ファイルの何ブロック目から、ディスクの何番のブロックから、何ブロック連続しているか」を 1 組で表します。

```
ブロックを 1 つずつ（ext3）          エクステント（ext4）
  0 → 8000                           ファイル 0〜3 → ディスク 8000 から 4 ブロック
  1 → 8001
  2 → 8002
  3 → 8003
```

1 つのエクステントで、4KB のブロックなら最大 128MiB を表せます。inode の中に直接 4 つまで入り、それを超えると B 木になります（[kernel.org: ext4 High Level Design](https://docs.kernel.org/6.15/filesystems/ext4/overview.html)）。連続して置けたファイルほど地図が小さく、読むのも速い。**断片化** が性能に効く理由です。

### 穴のあいたファイル

地図が「どこに何があるか」を書いたものである以上、**どこにも対応しない範囲** を作ることもできます。

```
$ truncate -s 1G sparse.img
$ ls -lh sparse.img
-rw-r--r-- 1 root root 1.0G Sep 24 08:42 sparse.img
$ du -h sparse.img
0	sparse.img
```

大きさは 1GB ですが、使っているブロックは 0 です。読むとゼロが返ります。これを **スパースファイル** と呼びます。仮想マシンのディスクイメージや、データベースの事前確保で使われます。`ls` の大きさと `du` の使用量が一致しないのは、このためです。

## inode が尽きる

ext4 では、inode の数が **ファイルシステムを作るときに決まります**。

```bash
df -h     # 容量の使用率
df -i     # inode の使用率
```

小さなファイルを大量に作る処理（キャッシュ、メールのスプール、`node_modules`）では、容量は余っているのに inode が尽きて、`No space left on device` が出ることがあります。容量を見て「空いているのに」と悩む前に、`df -i` を見ます。

## VFS: 1 つの口で何種類も

ext4、XFS、btrfs、NFS、そしてメモリ上だけの tmpfs や、`/proc`。中身はまったく違うのに、プログラムからは同じ `open`、`read`、`write` で扱えます。

間に **VFS**（Virtual File System）という層があるからです。

```
           open / read / write / stat / rename（第 41 回のシステムコール）
                              │
                    ┌─────────┴─────────┐
                    │        VFS         │  dentry キャッシュ（名前 → inode）
                    │                    │  inode キャッシュ
                    └──┬─────┬─────┬────┬┘  ページキャッシュ（第 48 回）
                       │     │     │    │
                     ext4   XFS   NFS  procfs ...
                       │     │     │
                   ブロックデバイス  ネットワーク
```

VFS は「ファイルシステムならこの操作を用意せよ」という関数の表を決め、各ファイルシステムがそれを実装します。第 5 章の ABI や、第 63 回の world と同じく、**約束を 1 つ決めて、裏を差し替えられるようにする** 設計です。

`/proc/<pid>/fd/3` が「ファイル」として読めるのも、第 69 回で見たコンテナの overlayfs が複数のディレクトリを重ねて 1 つに見せられるのも、この層の上に作られているからです。

<Callout type="tip" title="「すべてはファイル」の正体">
  第 42 回で見た「すべてはファイル」は、VFS という共通の口があるから成り立っています。
  ディスク上のファイルでなくても、VFS の関数表を実装すれば、
  `cat` や `ls` がそのまま使えるファイルとして見せられます。
</Callout>

## まとめ

- ディスクは番号付きのブロックの列でしかない。ファイルシステムはその上のデータ構造
- inode がファイルの本体。種類、権限、大きさ、時刻、リンク数、中身のありかを持つ。**名前は持たない**
- ディレクトリは「名前 → inode 番号」の表。パスは 1 段ずつ辿る
- ハードリンクは同じ inode への別名、シンボリックリンクはパスを中身に持つ別のファイル
- 削除は `unlink`。名前が消え、リンク数も開いている fd も 0 になって初めて領域が解放される
- 同じファイルシステム内の `rename` は、表の書き換えだけで原子的
- ext4 はエクステントでブロックの地図を持つ。地図に無い範囲は穴になる
- inode の数には上限がある。`df -i` で確かめる
- VFS が共通の口を決め、ext4 から `/proc` までを同じシステムコールで扱えるようにしている

次は、`write` したデータが、実際にいつ、どこまで届いたら「保存された」と言えるのかを見ます。
