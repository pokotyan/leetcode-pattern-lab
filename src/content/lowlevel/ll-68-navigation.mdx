## この章で見るもの

ブラウザは、ここまでの章に出てきた部品を**ほぼすべて**使う、大きなプログラムです。

| 部品 | ブラウザのどこで使われるか | 既出 |
| --- | --- | --- |
| TCP、TLS、多重化 | ページとその部品を取りに行く | 第 9 章 |
| プロセスとサンドボックス | タブやサイトごとに分けて閉じ込める | 第 33 回、第 93 回 |
| 字句解析と構文解析 | HTML と CSS を木にする | 「作る」区画のコンパイラ |
| スレッドとイベントループ | 入力、スクリプト、描画を 1 本の流れに並べる | 第 34 回、第 44・45 回 |
| JIT と GC | JavaScript を速く動かし、片付ける | 第 32 回、第 26 回 |
| キャッシュの階層 | 取りに行かずに済ませる | 第 3 章 |

この章では、ページを開いてから画面に描かれ、操作に反応するまでを順に追います。最後に、その流れの**どこが遅いのか**を測る指標を見ます。

最初は、画面に何かを描くより前の段階です。**最初の 1 バイトを手に入れるまで**に、何が起きているのか。

## 1 バイト目までの往復

`https://example.com/` を開くと、HTML の最初のバイトが届くまでに、少なくとも次の手順を踏みます。

```
ブラウザ                                       サーバ
   │  ① 名前を引く（DNS）         ──────→  リゾルバ
   │                              ←──────
   │  ② TCP の接続（SYN / SYN-ACK / ACK）───→
   │                              ←──────
   │  ③ TLS のハンドシェイク       ──────→
   │                              ←──────
   │  ④ GET /                     ──────→
   │                              ←──────  最初のバイト
```

どれも**往復**です。そして往復にかかる時間（RTT）は、第 54 回で見たとおり、光の速さと経路で決まっていて、帯域を増やしても縮みません。東京から米国の西海岸まで往復 100ms かかるなら、キャッシュも接続もない初回の訪問は、HTML の 1 バイト目までに **4 往復、400ms** を払います。

**ナビゲーションの速さは、ほとんどが「往復を何回減らせるか」の話**です。以下、それぞれを順に見ます。

## ① 名前を引く: DNS

IP アドレスが分からなければ、TCP の接続は始められません。

ブラウザや OS の中にある**スタブリゾルバ**は、自分では名前を調べません。設定された**フルリゾルバ**（プロバイダや `8.8.8.8` など）に「`example.com` の A レコードを」と頼むだけです。フルリゾルバが、ルート → `.com` → `example.com` の権威サーバ、と順に問い合わせて答えを見つけます。

```
スタブ ──→ フルリゾルバ ──→ ルート       「.com はあっち」
                        ──→ .com         「example.com はあっち」
                        ──→ example.com  「203.0.113.10」
```

これを毎回やると遅いので、答えには **TTL**（何秒まで使い回してよいか）が付いていて、ブラウザ、OS、フルリゾルバの各段でキャッシュされます。第 3 章のキャッシュの階層と同じ構造です。**手前で当たれば 0 往復**、フルリゾルバで当たれば 1 往復、全部外れれば何往復もかかります。

ここでは往復の回数に関わる部分だけを見ます。ゾーンと委任の仕組み、メッセージの形、アプリの中の名前解決、偽の答えへの対策は第 10 章で扱いました。

<Callout type="note" title="TTL の長さは、速さと切り替えやすさの交換">
  TTL を長くすれば、引き直しが減って速くなります。
  代わりに、IP アドレスを変えたときに古い答えがなかなか消えません。
  移転の前に TTL を短くしておく、という運用はこのためです。
  第 97 回で見たクラスタ内の DNS も、同じ仕組みの上に乗っています。
</Callout>

## ② と ③: 接続と暗号

TCP の 3 ウェイハンドシェイクは第 53 回で見ました。1 往復です。

その上で TLS のハンドシェイクが走ります。やっていることは 2 つです。

- **鍵を決める。** 盗聴されている回線の上で、両者だけが知る鍵を作る（Diffie-Hellman 系の鍵交換）
- **相手を確かめる。** サーバが送ってきた証明書が、信頼できる認証局の署名につながっているかを検証する

TLS 1.2 まではこれに 2 往復かかっていました。TLS 1.3 は、最初のメッセージで鍵交換の材料を先に送ってしまうことで、**1 往復**に縮めました（[RFC 8446](https://datatracker.ietf.org/doc/html/rfc8446)）。

さらに、一度つないだことのあるサーバには、前回の鍵を元にした **0-RTT** で、最初のメッセージと一緒にリクエストを送れます。ただしこのデータは**リプレイ（盗んで送り直す攻撃）を防げない**と仕様に明記されています。だからブラウザは、送り直されても害のない `GET` のようなリクエストにしか 0-RTT を使いません。

| | TCP | TLS | 1 バイト目まで（DNS を除く） |
| --- | --- | --- | --- |
| TLS 1.2 | 1 往復 | 2 往復 | 3 往復 + 応答 |
| TLS 1.3 | 1 往復 | 1 往復 | 2 往復 + 応答 |
| TLS 1.3 の 0-RTT | 1 往復 | 0 往復 | 1 往復 + 応答 |
| QUIC（HTTP/3） | 接続と暗号を同時に 1 往復 | | 1 往復 + 応答 |

QUIC は、TCP と TLS を別々に積むのをやめ、**1 回のハンドシェイクで接続と鍵の両方を決めます**。第 54 回で見たとおり、ユーザ空間に作り直したからこそできた統合です。

## ④ 頼む: HTTP の版が削ってきたもの

接続ができたら、ようやく `GET` を送ります。ここで HTTP の版の違いが効いてきます。

**HTTP/1.0** は、1 回のリクエストごとに接続を閉じていました。画像が 30 枚あれば、TCP のハンドシェイクも 30 回です。

**HTTP/1.1** は、接続を閉じずに使い回す **keep-alive** を既定にしました。ただし 1 本の接続では、**前の応答が返ってくるまで次のリクエストを送れません**。そこでブラウザは、1 つのホストに対して接続を複数本張って並列にします。Chrome ではこの上限が 6 本です（[Chromium の issue](https://issues.chromium.org/issues/40329530)）。画像を複数のホスト名に分けて配る「ドメインシャーディング」は、この上限を回避するための工夫でした。

**HTTP/2** は、1 本の接続の上に複数のリクエストを**多重化**しました。ストリームという番号付きの流れに分け、応答を細かい単位で混ぜて返せます。接続は 1 本で済み、ハンドシェイクの回数も TCP のスロースタートも 1 回分になります。代わりに、第 54 回で見た **TCP の HOL ブロッキング**を 1 本にまとめて抱え込みました。

**HTTP/3** は、その下の TCP を QUIC に取り替えて、ストリームごとに独立して順序を守るようにしました。

| 版 | 接続 | 何を解決したか | 何が残ったか |
| --- | --- | --- | --- |
| HTTP/1.0 | 1 リクエスト 1 接続 | — | ハンドシェイクだらけ |
| HTTP/1.1 | 使い回す | 接続の張り直し | 1 本で 1 つずつ。並列には本数が要る |
| HTTP/2 | 1 本に多重化 | 本数の問題 | TCP の HOL ブロッキング |
| HTTP/3 | QUIC の上に多重化 | HOL ブロッキング、ハンドシェイクの往復 | UDP を通さない途中の機器 |

<Callout type="tip" title="版が変わっても、意味は変わっていない">
  `GET`、ステータスコード、ヘッダという **HTTP の意味**は、1.1 から 3 まで同じです。
  変わったのは、それを線の上にどう載せるかだけです。
  第 8 回で見た「ISA という契約は変えずに、中の実装を入れ替える」のと同じ分け方で、
  だからアプリケーションは版を意識せずに済みます。
</Callout>

## 取りに行かない: HTTP キャッシュ

往復を減らす最も強力な方法は、**そもそも取りに行かない**ことです。

応答には、どれだけ使い回してよいかを指示するヘッダを付けられます（[RFC 9111](https://www.rfc-editor.org/rfc/rfc9111)）。

```
Cache-Control: max-age=31536000, immutable     1 年間、問い合わせずに使ってよい
Cache-Control: no-cache                        保存してよいが、使う前に必ず確かめる
Cache-Control: no-store                        保存するな
```

名前が紛らわしいのが `no-cache` です。これは「キャッシュするな」ではなく、**「使う前に毎回サーバに確かめよ」**という意味です。保存そのものを禁じるのは `no-store` です（[MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)）。

「確かめる」には、中身を丸ごと取り直さずに済む仕組みがあります。サーバは最初の応答に、中身の版を表す **ETag** を付けておきます。ブラウザは次に、その値を添えて問い合わせます。

```
GET /app.css
If-None-Match: "abc123"

→ 304 Not Modified      （本文なし。手元のものを使え）
```

変わっていなければ、本文のない **304** が返ります。往復は 1 回かかりますが、転送量はほぼゼロです。

これを組み合わせた定石が、**中身のハッシュをファイル名に入れる**方式です。`app.3f9a1c.js` のように名前を変えれば、中身が変わったときには別の URL になるので、古いものを永久にキャッシュさせても困りません。HTML だけを `no-cache` にしておけば、HTML の確認 1 回で、変わった部品だけが新しく取りに行かれます。

| 段 | 当たったときのコスト | 第 3 章での対応 |
| --- | --- | --- |
| メモリ上のキャッシュ | ほぼゼロ | L1 |
| ディスク上のキャッシュ | ディスクの読み込み | L2・L3 |
| 確かめて 304 | 1 往復、本文なし | 書き戻し不要のライン |
| CDN | 近くのサーバまでの往復 | 共有された下位の段 |
| オリジンのサーバ | 遠くまでの往復と生成 | メインメモリ |

**速いものを手前に置き、外れたら奥へ**。第 14 回で見た階層の考え方が、そのままネットワークの上に広がっています。

## 先回りする

往復を減らせないなら、**早く始める**という手もあります。HTML の中にヒントを書いておくと、ブラウザは必要になる前に準備を始めます。

```html
<link rel="dns-prefetch" href="https://cdn.example.com">   <!-- 名前だけ先に引く -->
<link rel="preconnect" href="https://cdn.example.com">     <!-- 接続と TLS まで先に済ませる -->
<link rel="preload" href="/font.woff2" as="font" crossorigin>  <!-- 取得まで先に始める -->
```

どれも「後で必ず使う」と開発者が知っている情報を、ブラウザに先に渡しているだけです。第 11 回で見た CPU の**投機実行**に似ていますが、こちらは予測ではなく申告です。外れれば、無駄な接続や転送が残ります。

## 自分の環境で見る

```bash
# 各段の所要時間を分けて表示する
curl -o /dev/null -s -w \
  'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer}\n' \
  https://example.com/

# 応答のヘッダ（キャッシュの指示、HTTP の版）を見る
curl -sI https://example.com/
```

2 回続けて実行すると、2 回目は DNS の値が小さくなることが多いはずです。どこかの段のキャッシュに当たっています。

ブラウザの開発者ツールの Network タブでも、リクエストごとに「DNS Lookup」「Initial connection」「SSL」「Waiting for server response」の内訳が見られます。

## まとめ

- ブラウザは、ここまでの章の部品をほぼすべて使う大きなプログラム
- 1 バイト目までの時間は、ほとんどが往復の回数で決まる。往復は帯域では縮まない
- DNS は階層的に問い合わせ、TTL の間は各段でキャッシュされる
- TLS 1.3 はハンドシェイクを 1 往復に縮めた。0-RTT は速いが、リプレイを防げないので安全なリクエストにだけ使う
- HTTP/1.1 は接続を使い回し、HTTP/2 は 1 本に多重化し、HTTP/3 は TCP の HOL ブロッキングを QUIC で取り除いた。HTTP の意味は変わっていない
- `no-cache` は「毎回確かめよ」。確かめて変わっていなければ 304 で本文を省ける
- 中身のハッシュを名前に入れれば、部品は永久にキャッシュさせられる

次は、こうして届いたページを受け取る側、ブラウザそのものがどんなプロセスに分かれて動いているのかを見ます。
