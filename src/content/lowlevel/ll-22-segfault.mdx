## 何が起きているのか

`Segmentation fault (core dumped)` が出るまでの流れは、こうです。

1. プログラムが、ある仮想アドレスにアクセスする
2. MMU がページテーブルを引く
3. **そのページが割り当てられていない**、または **権限が足りない**
4. CPU がページフォールト例外を発生させる
5. OS が原因を調べ、「これは正常な要求ではない」と判断する
6. OS がプロセスに **SIGSEGV** シグナルを送る
7. 既定のハンドラがプロセスを終了させる

**検出しているのは MMU（ハードウェア）**、**判断しているのが OS**、**落としているのがシグナルの既定動作**です。3 者の分業になっています。

<Callout type="note" title="名前の由来">
  セグメンテーションは、ページングより古いメモリ管理方式です。
  現代の Linux はページングを使っており、セグメントはほぼ使っていません。
  それでもシグナル名が `SIGSEGV` のまま残っているのは、歴史的経緯です。
  実態は「不正なメモリアクセス」を指します。
</Callout>

## 典型的な原因

| 原因 | 例 |
| --- | --- |
| **ヌルポインタ参照** | 未初期化のポインタ、失敗した `malloc` の戻り値を確認していない |
| **解放済みメモリの参照** | `free` した後に使う（use-after-free） |
| **範囲外アクセス** | 配列の境界を越える |
| **スタックオーバーフロー** | 無限再帰、巨大な局所変数 |
| **読み取り専用領域への書き込み** | 文字列リテラルの書き換え |
| **実行不可領域の実行** | 壊れた関数ポインタへのジャンプ |

文字列リテラルの書き換えは、C でよくある罠です。

```c
char *s = "hello";      // rodata を指している
s[0] = 'H';             // 書き込み不可 → SIGSEGV

char t[] = "hello";     // これはスタック上のコピー。書き換えてよい
t[0] = 'H';             // OK
```

## 落ちないことのほうが怖い

**範囲外アクセスをしても、落ちるとは限りません。**

```c
int arr[10];
arr[15] = 42;           // 落ちないことのほうが多い
```

理由は、ページ単位でしか保護できないからです。`arr` が 4KB ページの先頭付近にあれば、`arr[15]` はまだ同じページの中です。**そのページは有効に割り当てられているので、MMU は何も言いません。**

書き込まれたのは、たまたま隣にあった別の変数かもしれません。すると、

- 無関係な変数の値がおかしくなる
- その症状が出るのは、ずっと後の別の場所
- 環境やコンパイルオプションを変えると症状が消える

という、追跡困難なバグになります。**SIGSEGV で落ちてくれるのは、実は幸運な場合**です。

<Callout type="warn" title="境界を越えても検出されない範囲">
  ページサイズは 4KB です。
  範囲外アクセスが検出されるのは、**たまたまページの境界を越えたとき**だけ。
  1 バイトの越境はまず検出されません。
  ハードウェアによる保護は、**粒度が粗すぎて日常的なバグには効かない**ということです。
</Callout>

## 道具で細かく見る

ページ単位の保護では足りないので、ソフトウェアで細かく監視する道具があります。

### AddressSanitizer

コンパイル時に検査コードを埋め込みます。

```bash
gcc -fsanitize=address -g foo.c && ./a.out
```

確保した領域の前後に「毒された」領域（レッドゾーン）を置き、そこに触れた瞬間に報告します。

```
==1234==ERROR: AddressSanitizer: heap-buffer-overflow
WRITE of size 4 at 0x602000000018 thread T0
    #0 0x4009a1 in main foo.c:7
0x602000000018 is located 0 bytes to the right of 8-byte region
```

**どこで、何バイト越えたか、その領域はどこで確保されたか**まで出ます。実行速度は 2 倍程度遅くなりますが、開発中には十分実用的です。

use-after-free も検出します。解放した領域をすぐ再利用せず、しばらく「毒された」状態で保持するためです。

### Valgrind

再コンパイル不要で、実行可能ファイルをそのまま解析します。

```bash
valgrind --leak-check=full ./a.out
```

メモリリーク、未初期化メモリの読み取り、不正な解放を検出します。速度は 10〜50 倍遅くなります。

### その他

| 道具 | 検出するもの |
| --- | --- |
| UndefinedBehaviorSanitizer (`-fsanitize=undefined`) | 整数オーバーフロー、不正なシフト、アラインメント違反 |
| ThreadSanitizer (`-fsanitize=thread`) | データ競合 |
| MemorySanitizer | 未初期化メモリの使用 |

<Callout type="tip" title="CI に組み込む">
  これらは開発中にしか使えない（遅い）ものですが、
  **テストを Sanitizer 付きで回す**のは現実的です。
  本番ビルドは通常どおりにし、CI で 1 本 Sanitizer ビルドを走らせるのが定石です。
</Callout>

## スタックカナリア

バッファオーバーランで最も危険なのは、**スタック上の戻り先アドレスを上書きされる**ことです。攻撃者が戻り先を書き換えれば、任意の場所に実行を移せます。

対策が **スタックカナリア** です。関数の入口で、戻り先アドレスの手前にランダムな値を置きます。関数から戻る直前に、その値が変わっていないか確認します。

```
[ 局所変数 ][ カナリア ][ 保存された rbp ][ 戻り先アドレス ]
              ↑ ここが壊れていたら、戻る前に異常終了させる
```

バッファを越えて書き込めば、戻り先に届く前にカナリアを踏むので検出できます。

```
*** stack smashing detected ***: terminated
```

GCC / Clang では `-fstack-protector-strong` が既定で有効なディストリビューションが多く、この保護は日常的に効いています。

<Callout type="note" title="なぜカナリアと呼ぶのか">
  炭鉱で有毒ガスを検知するためにカナリアを連れて行った、という故事に由来します。
  先に異常を示す存在、という意味です。
</Callout>

## core dump を読む

落ちたときの状態をファイルに残せます。

```bash
ulimit -c unlimited                    # core を出す設定
./a.out                                # 落ちる
gdb ./a.out core
(gdb) bt                               # バックトレース
(gdb) info registers
(gdb) frame 2
(gdb) print variable
```

`bt` で、どの関数から呼ばれてどこで落ちたかが分かります。`-g` 付きでコンパイルしてあれば、行番号まで出ます。

Linux のディストリビューションによっては `coredumpctl` で管理されます。

```bash
coredumpctl list
coredumpctl gdb <PID>
```

## 言語による違い

メモリ安全でない言語（C、C++）でのみ、この種の問題が起こります。

| 言語 | 範囲外アクセス |
| --- | --- |
| C / C++ | 未定義動作。運が良ければ SIGSEGV |
| Rust | コンパイル時に多くを排除。実行時の境界チェックでパニック |
| Java / C# / Go | 例外またはパニック |
| Python / Ruby | 例外 |

ただし、**どの言語でも FFI（外部関数呼び出し）を使えば同じ問題が起きます**。また、Go や Java でもスタックオーバーフローや、ランタイム自体のバグで SIGSEGV は起こりえます。

Rust の `unsafe` ブロックは、この保証を明示的に外す場所を限定する仕組みです。「安全でない箇所がどこか」がコード上で分かることに価値があります。

## まとめ

- SIGSEGV は、MMU が検出し、OS が判断し、シグナルの既定動作が落としている
- 検出の粒度はページ単位なので、**小さな範囲外アクセスは検出されない**
- 落ちないバグのほうが追跡は困難
- AddressSanitizer などの道具で、細かい粒度の検査ができる
- スタックカナリアは戻り先アドレスの改竄を検出する
- core dump と gdb で、落ちた瞬間の状態を復元できる

次は、ページフォールトを**積極的に利用する**仕組みを見ます。
