## 何が難しいのか

第 32 回で、JIT の一般的な仕組みを見ました。段階的なコンパイル、観測した形を前提に特殊化するインラインキャッシュ、前提が崩れたときの脱最適化。この回では、それを **JavaScript という言語** に当てはめたときに、何が特に難しく、エンジンが何を工夫しているのかを見ます。

JavaScript には、速く動かすための手がかりがほとんどありません。

| 性質 | C なら | JavaScript |
| --- | --- | --- |
| 変数の型 | 宣言で決まる | 実行するまで分からない。途中で変わる |
| オブジェクトの形 | 構造体の定義で決まる | いつでもプロパティを足せる、消せる |
| 数 | `int` と `double` を書き分ける | すべて `number`（第 4 回の倍精度浮動小数点） |
| 配列 | 同じ型の要素が隙間なく並ぶ | 何でも入る。穴も空けられる |
| プログラムの届き方 | 実行ファイルとして事前にコンパイル済み | ソースコードのまま、ネットワーク越しに毎回届く |

最後の行がブラウザ特有の事情です。ページを開くたびに、数 MB のソースコードが届き、**構文解析してからでないと 1 行も動かせません**。しかもその間、第 73 回で見たメインスレッドは他のことができません。

## 読まずに済ませる: 遅延構文解析

届いたソースコードのうち、ページの読み込み中に実際に呼ばれる関数はごく一部です。クリックされたときにだけ動く処理、特定の画面でしか使わない処理が大半を占めます。

そこでエンジンは、**関数の中身を最初は完全には解析しません**。V8 では、関数に出会うと、本来の構文解析器の代わりに **preparser** という軽い版に切り替えます（[V8 blog](https://v8.dev/blog/preparser)）。

- 構文が正しいかどうかは確かめる（誤りはすぐ報告しなければならない）
- 外側の関数を正しくコンパイルするのに必要な情報（どの変数を閉じ込めているか）だけを集める
- 抽象構文木もバイトコードも作らない

その関数が実際に呼ばれたとき、初めて完全に解析してバイトコードを作ります。第 24 回で見た**遅延割り当て**、つまり使われるまで物理メモリを割り当てない考え方と同じ発想です。

<Callout type="note" title="それでも毎回読むのは無駄">
  同じページを何度も開くなら、毎回同じソースを解析するのは無駄です。
  そこでブラウザは、解析とコンパイルの結果（バイトコード）をディスクに保存しておき、
  次回はそれを読み込みます（コードキャッシュ、[V8 blog](https://v8.dev/blog/code-caching-for-devs)）。
  第 48 回で見たページキャッシュと同じく、**2 回目以降を速くする**ための層です。
  いつ保存するかはブラウザの判断で、開発者が制御するものではありません。
</Callout>

## オブジェクトの形を、後から見つける

C の構造体では、メンバがどのオフセットにあるかをコンパイラが知っています。JavaScript のオブジェクトは、素直に作れば**名前から値を引く辞書**です。`obj.x` を読むたびに辞書を引いていては、構造体の数十倍遅くなります。

エンジンは、辞書の代わりに**形**（shape、V8 では hidden class や map と呼ぶ）という別のオブジェクトを使います（[Mathias Bynens](https://mathiasbynens.be/notes/shapes-ics)）。

```js
const a = {}      // 形 S0: プロパティなし
a.x = 1           // 形 S1: x はオフセット 0
a.y = 2           // 形 S2: x はオフセット 0、y はオフセット 1

const b = {}
b.x = 5
b.y = 6           // b も形 S2 になる。S0 → S1 → S2 の遷移を共有する
```

```
  S0 {} ──(x を足す)──→ S1 {x:0} ──(y を足す)──→ S2 {x:0, y:1}

  a ──→ [形: S2][ 1 ][ 2 ]
  b ──→ [形: S2][ 5 ][ 6 ]      値だけが並び、名前は形の側に 1 つだけ
```

**同じ順番でプロパティを足したオブジェクトは、同じ形を共有します。** オブジェクト本体には値だけが並び、「x はオフセット 0」という情報は形の側に 1 回だけ持ちます。これで、中身は第 6 回で見た構造体とほぼ同じ配置になります。

形があれば、第 32 回のインラインキャッシュが効きます。「形が S2 なら、x はオフセット 0」と覚えておけば、`obj.x` は比較 1 回と読み込み 1 回で済みます。

<Callout type="warn" title="順番が違うと、別の形になる">
  `{x, y}` の順に足したオブジェクトと、`{y, x}` の順に足したオブジェクトは、**別の形**です。
  中身が同じでも、遷移の道筋が違うからです。
  また、プロパティを `delete` したり、大量に足し引きしたりすると、
  形を維持するのをあきらめて**辞書モード**に切り替わることがあります。
  辞書モードのオブジェクトにはインラインキャッシュが効きません（[V8 blog](https://v8.dev/blog/fast-properties)）。
  コンストラクタで全部のプロパティを同じ順に初期化するのが速い、と言われるのはこのためです。
</Callout>

## 1 か所に何種類の形が来るか

インラインキャッシュは、コードの **1 か所ごと** に、そこを通った形を覚えます。その数で状態が変わります（[mrale.ph](https://mrale.ph/blog/2015/01/11/whats-up-with-monomorphism.html)）。

| 状態 | 見た形 | 読み方 |
| --- | --- | --- |
| **単相**（monomorphic） | 1 種類 | 比較 1 回で決まる。最速 |
| **多相**（polymorphic） | 数種類（V8 では 4 つまで） | 順に比較する |
| **超多相**（megamorphic） | それより多い | あきらめて、共有の表を引く |

たとえば、いろいろな形のオブジェクトを受け取る汎用の関数（ロガー、シリアライザ）は、中の `obj.x` が超多相になりがちです。**同じ関数でも、渡すものによって速さが変わる**のは、この仕組みのためです。

## 数をどう持つか

JavaScript の `number` はすべて倍精度浮動小数点です。しかし、配列の添字やループの変数のほとんどは小さな整数です。それを毎回 8 バイトの浮動小数点としてヒープに置くのは無駄です。

そこでエンジンは、**ポインタの最下位ビットを印に使います**。第 6 回で見たとおり、オブジェクトはアラインメントされて置かれるので、ポインタの下位ビットは常に 0 のはずです。そこに 1 が立っていればポインタ、0 なら**値そのものが入っている小さな整数**、と決めます。

```
  ...0110 1010  |  0   → 小さな整数（Smi）。上のビットがそのまま値
  ...1011 0000  |  1   → ヒープ上のオブジェクトへのポインタ
                   ↑
                 印のビット
```

V8 ではこれを **Smi**（small integer）と呼び、64 ビット環境でも 31 ビットの値を 32 ビットに収めています（[V8 blog](https://v8.dev/blog/pointer-compression)）。Smi の足し算は、メモリを確保せず、レジスタの上で整数として計算できます。範囲を超えたり小数になったりしたときだけ、ヒープに浮動小数点の箱を作ります。

これは第 2 回の 2 の補数、第 6 回のアラインメント、第 10 回のポインタの幅が、すべて一度に効いている設計です。

### 配列の中身の種類

配列も同じ考え方をします。V8 は、配列ごとに「中身が何か」を記録しています（[V8 blog](https://v8.dev/blog/elements-kinds)）。

```
  [1, 2, 3]            整数だけ       → 整数の配列として、隙間なく並べる
  [1, 2, 3.5]          小数が混ざった → 浮動小数点の配列に格上げ
  [1, 2, 'a']          何でも入る     → ポインタの配列に格上げ
  [1, , 3]             穴がある       → 「穴あり」に格上げ（読むたびに確かめる）
```

**格上げは一方通行です。** 一度文字列を入れた配列は、文字列を取り除いても整数の配列には戻りません。穴のある配列も、穴を埋めても「穴なし」には戻りません。`new Array(1000)` のように長さだけ先に作ると、最初から穴だらけの配列になります。

## メインスレッドを止めない GC

第 26 回で、世代別 GC と、プログラムを止めずに辿る並行 GC を見ました。ブラウザでは、この「止めない」が特に重要です。GC がメインスレッドを 50 ミリ秒止めれば、その間のクリックには反応できず、アニメーションはコマ落ちします（第 72 回の 16.7ms の予算）。

V8 の GC（Orinoco）は、仕事を 3 通りに逃がしています（[V8 blog](https://v8.dev/blog/trash-talk)）。

| 方法 | 何をするか |
| --- | --- |
| **並列** | 止めている間の仕事を、複数のスレッドで分担して短くする |
| **インクリメンタル** | 仕事を小さく刻み、JavaScript の実行と交互に進める |
| **並行** | JavaScript を動かしたまま、別のスレッドで辿る |

若い世代は、コピー方式（Scavenger）で頻繁に回収します。ほとんどのオブジェクトはすぐ死ぬので、生き残ったものだけを移せば済みます。古い世代は、並行にマークしてから、必要なら詰めます。

ブラウザならではの工夫が **アイドル時間の GC** です。1 フレームの描画を 16.7ms より早く終えたら、次のフレームまでの残り時間は何もすることがありません。そこに GC の小さな仕事を詰め込みます（[V8 blog](https://v8.dev/blog/concurrent-marking)）。第 36 回のスケジューラが空いた CPU に仕事を回すのと同じ発想を、1 つのスレッドの中の時間でやっています。

<Callout type="tip" title="メモリも、タブの数だけ要る">
  第 69 回で見たとおり、ブラウザはサイトごとにプロセスを分けます。
  JavaScript のヒープも、形の情報も、コードキャッシュも、プロセスごとに持ちます。
  エンジンが「速さ」と同じくらい「小ささ」に力を入れているのは、
  1 台のマシンで何十ものタブが同時に開かれるからです。
</Callout>

## 速い JavaScript とは

ここまでの仕組みから、エンジンが速く動かせるコードの特徴が見えてきます。どれも「言語の自由を使わない」ことです。

- オブジェクトは、同じ順番で、最初に全部のプロパティを作る
- 1 か所に来るオブジェクトの形の種類を少なくする
- `delete` でプロパティを消さない
- 配列には同じ種類の値を入れ、穴を空けない
- 整数で済む計算は整数の範囲に収める

言い換えると、**型のある言語で書いたかのように書くと速い**ということです。TypeScript の型は実行時には消えますが、型に沿って書いたコードは、結果としてエンジンが観測する形も揃います。

ただし、これらはエンジンの実装の詳細であり、版によって変わります。**最初からこれに合わせて書くのではなく、第 106 回の道具で測って、熱い部分に当たったときに思い出す**くらいがちょうどよい距離です。

## まとめ

- JavaScript には型も構造体もなく、ソースのまま毎回届く。速く動かす手がかりを、エンジンが実行中に見つける
- 関数の中身は呼ばれるまで完全には解析しない。2 回目以降はコードキャッシュを使う
- オブジェクトの形（shape / hidden class）を後から見つけ、構造体と同じ配置にする。足す順番が違えば別の形になる
- インラインキャッシュは 1 か所ごとに形を覚える。形の種類が増えると遅くなる
- 小さな整数はポインタの印のビットで区別し、ヒープに置かない。配列も中身の種類を記録し、格上げは一方通行
- GC は並列・インクリメンタル・並行に仕事を逃がし、フレームの空き時間にも詰め込む

次は、ここまでの回で見た遅さが、利用者の体験としてどう測られるのか、Web Vitals を見ます。
