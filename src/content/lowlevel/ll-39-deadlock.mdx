## 互いに待ち合う

```c
// スレッド A
lock(mutex1);
lock(mutex2);      // B が持っている。待つ

// スレッド B
lock(mutex2);
lock(mutex1);      // A が持っている。待つ
```

両方とも、相手が手放すのを待ちます。相手も同じことをしています。**どちらも永遠に進みません。**

これが **デッドロック** です。

## 成立する 4 条件

デッドロックは、次の 4 つが**すべて**成立したときにだけ起きます（Coffman の条件）。

| 条件 | 内容 |
| --- | --- |
| **相互排除** | その資源は 1 度に 1 つのスレッドしか使えない |
| **保持と待機** | 資源を持ったまま、別の資源を待つ |
| **横取り不可** | 他者から強制的に取り上げられない |
| **循環待機** | 待ちの関係が輪になっている |

**逆に言えば、1 つでも崩せば防げます。** 対策はこの表から機械的に導かれます。

### 相互排除を崩す

そもそも排他が不要にする。不変データにする、読み書きロックの読み側だけにする、ロックフリーのデータ構造を使う。

### 保持と待機を崩す

**必要なロックを全部まとめて取る。** 1 つでも取れなければ、持っているものをすべて手放してやり直す。

```c
while (true) {
    lock(mutex1);
    if (try_lock(mutex2)) break;    // 取れたら抜ける
    unlock(mutex1);                  // 取れなければ手放す
    // 少し待ってやり直す
}
```

C++ には複数のロックを安全にまとめて取る仕組みがあります。

```cpp
std::scoped_lock lk(mutex1, mutex2);    // デッドロックを避ける順序で取得する
```

### 横取り不可を崩す

**タイムアウトを設ける。** 一定時間取れなければ諦めて、持っているものを手放す。

```c
pthread_mutex_timedlock(&m, &timeout);
```

### 循環待機を崩す

**これが最も実用的です。**

> **すべてのロックに順序を決め、必ずその順序で取る。**

```c
// 規約: 常に番号の小さいほうから取る
void transfer(Account *from, Account *to) {
    Account *first  = (from->id < to->id) ? from : to;
    Account *second = (from->id < to->id) ? to : from;
    lock(&first->m);
    lock(&second->m);
    ...
}
```

全員が同じ順序で取れば、輪はできません。

<Callout type="tip" title="順序をどう決めるか">
  アドレス順、ID 順、階層の浅い順など、**一貫していれば何でも構いません**。
  重要なのは、その規約をコードベース全体で守ることです。

  Linux カーネルには **lockdep** という検証機構があり、
  実行時にロックの取得順序を記録し、**矛盾する順序を検出したら警告を出します**。
  実際にデッドロックが起きなくても、起こりうる順序があれば報告されます。
</Callout>

## 検出する

```bash
# 固まったプロセスのスタックを見る
gdb -p <pid>
(gdb) thread apply all bt

# Java
jstack <pid>            # デッドロックを自動検出して報告する

# Go
# SIGQUIT を送ると全ゴルーチンのスタックが出る
kill -QUIT <pid>
```

全スレッドのスタックを見て、**複数のスレッドがロック取得で止まっている**なら、デッドロックを疑います。

Go のランタイムは、全ゴルーチンが待ち状態になると `all goroutines are asleep - deadlock!` というパニックを起こします。

## 似ているが違うもの

### ライブロック

止まってはいないが、進んでもいない状態です。

```
A: ロックが取れない。手放してやり直そう
B: ロックが取れない。手放してやり直そう
A: ...（同じことを繰り返す）
```

廊下ですれ違おうとして、互いに同じ方向によけ続けるのに似ています。**CPU は使っているのに、仕事が進みません。**

対策は、やり直すまでの待ち時間をランダムにすることです（ランダム化バックオフ）。両者が同じタイミングで動き続けることを防ぎます。イーサネットの衝突回避や、分散システムのリトライでも同じ手法が使われます。

### 飢餓

一部のスレッドだけが、いつまでも資源を得られない状態です。

- 優先度の低いスレッドが、高いスレッドに割り込まれ続ける
- 読み書きロックで、読み手が絶え間なく来て書き手が入れない

対策は、待ち時間に応じて優先度を上げる（エイジング）、公平なロック（到着順に処理する FIFO ロック）を使う、などです。

<Callout type="note" title="公平なロックは遅い">
  到着順を厳密に守るロックは、**直前に手放したスレッドが再取得できません**。
  キャッシュが温まっているのに、わざわざ別のコアのスレッドに渡すことになります。
  スループットは下がります。

  公平さとスループットは trade-off であり、既定では不公平（barging を許す）な実装が多いです。
</Callout>

## ABA 問題

ロックフリーのアルゴリズムで CAS を使うときの罠です。

```
スレッド A: 値を読む → A
（この間にスレッド B が、A → B → A と変更する）
スレッド A: CAS する → 値は A なので成功してしまう
```

**値は同じでも、その間に別の状態を経由している**ことがあります。ポインタを扱う場合、いったん解放されたメモリが再利用されて同じアドレスになる、という形で起きます。

対策は、値にカウンタを付けて、変更のたびに増やすことです（タグ付きポインタ、バージョン番号）。値が同じでもカウンタが違えば、変更があったと分かります。

## 正しい設計が最善

デッドロックの対策を並べましたが、根本的には**ロックを使う量を減らす**のが最も効果的です。

- 共有を減らす（スレッドごとに持つ、不変にする）
- ロックを取る範囲を短くする
- ロックを持ったまま、他の関数を呼ばない（何を呼ぶか分からないので）
- ロックを持ったまま、I/O やブロッキング操作をしない
- コールバックをロック内で呼ばない（呼び出し先が何をするか分からない）

<Callout type="warn" title="ロックを持ったままコールバックを呼ばない">
  ライブラリがロックを持った状態でユーザのコールバックを呼ぶと、
  そのコールバックが同じライブラリの別の関数を呼んだ瞬間にデッドロックします。
  「持ったまま外に出ない」というのは、設計上の重要な規律です。
</Callout>

## まとめ

- デッドロックは 4 条件がすべて揃ったときにだけ起きる。1 つ崩せば防げる
- 最も実用的なのは、ロックに順序を決めて必ずその順で取ること
- lockdep、jstack、gdb のスタック確認で検出する
- ライブロックは進まないが動いている。ランダム化バックオフで対処
- 飢餓は一部が資源を得られない状態。公平さとスループットは trade-off
- ABA 問題はバージョン番号で対処する
- 最善は、ロックを使う量そのものを減らすこと
