## 順番にやると空きが出る

1 命令の実行を「フェッチ → デコード → 実行 → ライトバック」の 4 段に分けました。それぞれ別の回路が担当します。

素直に 1 命令ずつ処理すると、こうなります。

```
時刻:      1    2    3    4    5    6    7    8
命令1:    F    D    E    W
命令2:                        F    D    E    W
```

命令 1 がデコード段にいるとき、フェッチ回路は何もしていません。**4 つの回路のうち 3 つが常に遊んでいます。**

## 重ねて流す

工場の組み立てラインと同じ発想で、**前の命令が次の段に進んだら、すぐ次の命令を入れます**。

```
時刻:      1    2    3    4    5    6    7    8
命令1:    F    D    E    W
命令2:         F    D    E    W
命令3:              F    D    E    W
命令4:                   F    D    E    W
```

これが **パイプライン** です。

1 命令あたりの所要時間（レイテンシ）は 4 クロックのままですが、**1 クロックごとに 1 命令が完了する**ようになりました。スループットが 4 倍です。

段数を増やせば、1 段あたりの仕事が減るのでクロックを上げられます。Pentium 4 は 20 段以上、後期には 31 段に達しました。ただし、次に見る理由で段数を増やすと別の問題が深刻化します。

## 3 種類の詰まり

パイプラインは、常にきれいに流れるわけではありません。流れが止まる原因を **ハザード** と呼びます。

### データハザード

```asm
add  r1, r2, r3      ; r1 に結果を書く
sub  r4, r1, r5      ; その r1 を使う
```

2 番目の命令は、1 番目の結果が必要です。しかし 1 番目がライトバックを終える前に、2 番目は実行段に来てしまいます。

対策は 2 つあります。

- **フォワーディング**：ライトバックを待たず、実行段の出力を次の命令の入力に直接回す配線を追加する
- **ストール**：どうしても間に合わないときは、パイプラインを 1〜数クロック止める

多くの場合はフォワーディングで解決しますが、ロード命令の直後にその結果を使う場合は、1 クロックの待ちが避けられません。コンパイラは、この隙間に無関係な命令を挟むように並べ替えます。

### 構造ハザード

同じ回路を複数の命令が同時に使おうとする場合です。命令のフェッチとデータのロードが同時に発生すると、メモリが 1 ポートしかなければ競合します。命令用とデータ用でキャッシュを分けるのは、この対策でもあります。

### 制御ハザード

**これが最大の問題です。**

```asm
cmp  r1, r2
jne  somewhere       ; 分岐
add  ...             ; ここを実行するかどうかは、分岐が解決するまで分からない
```

分岐命令がどこへ飛ぶかは、実行段まで来ないと分かりません。しかしフェッチ段は、その 3 クロック前に「次に何を読むか」を決める必要があります。

素直にやると、分岐のたびにパイプラインが空になります。段数が深いほど損失が大きい。20 段のパイプラインなら、1 回の分岐ミスで 20 クロック近くを失います。

## 予測して、先に進む

そこで CPU は、**分岐先を予測して、当たっている前提で実行を進めます**。これを **投機実行** と呼びます。

予測が当たれば、何も損しません。外れたら、投機的に実行した結果をすべて破棄して、正しい方からやり直します。

<Callout type="note" title="予測の精度は驚くほど高い">
  現代の CPU の分岐予測は、典型的なコードで **95〜99%** 当たります。
  ループの継続はほぼ確実に当たりますし、
  過去の分岐の履歴パターンを記録して、次を予測する仕組みが入っています。
  外れたときのペナルティが 15〜20 クロックあっても、
  1% 未満の頻度なら平均コストは小さく収まります。
</Callout>

予測の仕組みは世代とともに高度化しています。

| 方式 | 内容 |
| --- | --- |
| 静的予測 | 「後ろ向きの分岐は成立する」（ループだから）と決め打ち |
| 1 ビット予測 | 前回の結果をそのまま次の予測とする |
| 2 ビット飽和カウンタ | 2 回続けて外れないと予測を変えない。ループの終わりで無駄に切り替わるのを防ぐ |
| 履歴ベース | 直近 n 回の分岐パターンをキーにして予測する |
| ニューラル方式 | パーセプトロンによる重み付き予測 |

## 予測できる分岐、できない分岐

実際に測ってみると、予測の当たりやすさが性能に直結することが分かります。

```c
// ソート済みの配列と、ランダムな配列で同じ処理をする
for (int i = 0; i < n; i++)
    if (data[i] >= 128) sum += data[i];
```

**ソート済みの配列のほうが数倍速くなります。** 前半は常に偽、後半は常に真なので、予測がほぼ全部当たるからです。ランダムな配列では 50% 外れます。

計算量はまったく同じです。差はすべて分岐予測から来ています。

<Callout type="tip" title="分岐をなくすという手">
  予測が当たらない分岐は、分岐そのものを消してしまうのが有効なことがあります。

```c
// 分岐あり
if (a > b) max = a; else max = b;

// 分岐なし（条件付き move 命令になる）
max = a > b ? a : b;
```
  x86 の `cmov`、ARM の条件付き実行命令は、分岐せずに値を選びます。
  ただし**必ず速くなるわけではありません**。予測がよく当たる分岐なら、分岐したほうが速いこともあります。
  測って決めるべき領域です。
</Callout>

## 投機実行が開けた穴

2018 年に公表された **Spectre** と **Meltdown** は、投機実行そのものを悪用する攻撃でした。

仕組みの核心はこうです。**投機実行の結果は破棄されますが、その過程でキャッシュに載ったデータは残ります。** そして「キャッシュに載っているかどうか」は、アクセス時間を測れば外から分かります。

つまり、

1. 本来アクセスできないメモリを、投機実行中に読ませる
2. その値によって異なるアドレスにアクセスさせる
3. 実行は取り消されるが、キャッシュの状態は残る
4. どのアドレスが速く読めるかを測り、値を逆算する

**アーキテクチャ上の状態は正しく巻き戻っているのに、マイクロアーキテクチャ上の副作用が情報を漏らす**、という構造です。ISA の契約は守られているのに、契約に書かれていない部分から漏れました。

対策としてカーネルとユーザ空間のページテーブルを分離する（KPTI）などの措置が取られ、いずれも性能低下を伴いました。**性能のための仕組みが、性能を犠牲にして塞がれた**わけです。

## まとめ

- パイプラインは、命令の処理を段に分けて重ねて流す仕組み
- レイテンシは変わらないが、スループットが段数倍になる
- ハザード（データ / 構造 / 制御）で流れが止まる
- 制御ハザードの対策が分岐予測と投機実行。精度は 95〜99%
- 予測しにくい分岐は、実測で数倍の差になる
- 投機実行の副作用が Spectre / Meltdown を生んだ

次は、パイプラインをさらに押し進めて、**同時に複数の命令を実行する**話です。
