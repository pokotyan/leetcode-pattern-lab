## バイト列から木へ

第 68 回で、HTML の最初のバイトが届くところまで来ました。レンダラプロセスはこれを受け取り、**DOM**（Document Object Model）という木を作ります。以降の処理はすべて、この木の上で行われます。

```
バイト列   3c 68 31 3e 48 69 3c 2f 68 31 3e
   │ ① 文字コードを決めて文字にする
文字       <h1>Hi</h1>
   │ ② 字句解析（トークナイザ）
トークン    [開始タグ h1] [文字 "Hi"] [終了タグ h1]
   │ ③ 木の構築
DOM         Document
              └ html
                  ├ head
                  └ body
                      └ h1
                          └ "Hi"
```

`<html>` も `<head>` も `<body>` も書いていないのに、木には現れています。この「書かれていないものを補う」振る舞いが、HTML のパーサの性格をよく表しています。後で詳しく見ます。

## ① 文字にする

第 5 回で見たとおり、バイト列は文字コードが決まらないと文字になりません。ブラウザは、HTTP の `Content-Type` ヘッダの `charset`、先頭のバイト順マーク、`<meta charset="utf-8">` の順に手がかりを探します。

`<meta charset>` が HTML の**先頭近くに書け**と言われるのはこのためです。途中で文字コードが判明すると、そこまで読んだ分をやり直すことになります。

## ② と ③: コンパイラと同じ 2 段

「作る」区画のコンパイラでは、<a href={`${import.meta.env.BASE_URL}build/tc-05-lexer/`}>字句解析</a>で文字列を単語に割り、<a href={`${import.meta.env.BASE_URL}build/tc-06-parser/`}>構文解析</a>で単語を木にしました。HTML のパーサも、同じ 2 段でできています（[HTML Standard: Parsing](https://html.spec.whatwg.org/multipage/parsing.html)）。

**トークナイザ**は状態機械です。「データを読んでいる」「タグ名を読んでいる」「属性の値を読んでいる」といった数十の状態を持ち、1 文字ずつ読んで状態を移り、開始タグ、終了タグ、文字、コメントといったトークンを出します。

**木の構築**は、**開いている要素のスタック**を持ちます。開始タグが来たら要素を作って今の親の子にし、スタックに積む。終了タグが来たらスタックから降ろす。スタックマシンや、括弧の対応を調べるアルゴリズムと同じ形です。

```
トークン          スタック（下が根）        木
<body>           [html, body]            body
<p>              [html, body, p]         body > p
"a"              [html, body, p]         body > p > "a"
</p>             [html, body]
```

ただし、HTML の木の構築は、この単純なスタックの操作だけでは済みません。

## 誤りで止まってはいけない

コンパイラは、文法の誤りを見つけたら**エラーを出して止まります**。誤ったプログラムを勝手に解釈して動かすほうが危険だからです。

HTML はそうはいきません。Web には、閉じ忘れ、入れ子の間違い、あり得ない位置のタグを含むページが無数にあります。ブラウザがそれを拒否すれば、ユーザは「このブラウザでは見られない」と感じて、寛容な他のブラウザに移ります。だから**どのブラウザも、壊れた HTML をなんとか表示してきました**。

問題は、その「なんとか」がブラウザごとに違っていたことです。同じ壊れた HTML から、ブラウザによって違う木ができる。これを終わらせるために、HTML の仕様は**誤りをどう回復するかまで、1 つの手順として厳密に定義しています**。パースエラーは「起きることが想定され、回復の仕方が正確に決まっているもの」として扱われます（[HTML Standard](https://html.spec.whatwg.org/multipage/parsing.html)）。

いくつか例を見ます。

**閉じ忘れを補う。** `<p>` の中で次の `<p>` が始まれば、前の `<p>` は閉じたものとみなします。`<li>` や `<td>` も同じです。

```html
<p>1 つ目<p>2 つ目
<!-- → <p>1 つ目</p><p>2 つ目</p> -->
```

**入れ子の間違いをほどく。** `<b>1<i>2</b>3</i>` のように、閉じる順番が入れ違った書式のタグは、「養子縁組」と名付けられた手順で要素を作り直して木に収めます。

**あり得ない位置のものを外に出す。** `<table>` の中に、セルに入っていない文字や要素を書くと、それは**表の外、表の直前**に移されます。

```html
<table><tr><td>A</td></tr>ここに文字</table>
<!-- → 「ここに文字」は <table> の前に置かれる -->
```

<Callout type="warn" title="書いたとおりの木になるとは限らない">
  開発者ツールの Elements パネルに出ているのは、**ソースではなく、回復後の木**です。
  「HTML には書いたのに、要素の位置が違う」ときは、この回復が働いています。
  また、サニタイザが HTML を一度解析して安全を確かめても、
  それを再び解析すると回復の結果が変わって別の木になる、という性質は、
  XSS の抜け道として実際に悪用されてきました（mutation XSS）。
  XSS そのものは<a href={`${import.meta.env.BASE_URL}reading/web-security/`}>システム設計の読み物</a>で扱っています。
</Callout>

## 読みながら組み立てる

HTML のパーサは、ファイルを最後まで受け取ってから解析するのではありません。**届いた分から順に解析し、木を伸ばしていきます**。

第 54 回で見たとおり、TCP のデータは少しずつ届きます。数 MB の HTML でも、先頭の数 KB が届いた時点で `<head>` の中身が分かり、スタイルシートや画像の取得を始められます。本文の最初の段落が届けば、残りを待たずに描き始めることもできます。

**逐次的に処理できることが、最初の表示を速くしています**。ファイル全体を受け取ってから JSON を解析する処理とは、ここが大きく違います。

## script が構文解析を止める

ところが、この逐次的な流れを止めるものがあります。`<script>` です。

`async` も `defer` も付いていない `<script>` に出会うと、パーサは**止まります**。スクリプトを取得して、実行し終わるまで、次の 1 文字を読みません。

止まらなければならない理由は、スクリプトが**これから読む HTML そのものを書き換えられる**からです。

```html
<script>
  document.write('<div>');   // パーサの入力に、文字列を差し込む
</script>
<p>この p は div の中に入る</p>
```

`document.write` は、パーサがこれから読む文字の流れに、新しい文字を差し込みます。スクリプトを実行する前に先を解析してしまうと、木の形が変わってしまいます。さらに、スクリプトはその時点までにできた DOM を読むので、どこまで木ができているかも決まっていなければなりません。

<Callout type="note" title="CSS も、間接的にパーサを止める">
  スクリプトは要素のスタイルを読むことがあります（`getComputedStyle` など）。
  そのため、ブラウザは**それより前に書かれたスタイルシートが読み終わるまで、スクリプトの実行を待たせます**。
  CSS の取得が遅ければ、スクリプトの実行が遅れ、それを待つパーサも遅れます。
  CSS 自体は、スタイルのない画面が一瞬見えるのを防ぐため、描画を止めます（render-blocking）。
</Callout>

これを避けるのが `defer` と `async` です（[MDN](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script)）。

| 書き方 | 取得 | 実行のタイミング | 実行の順序 |
| --- | --- | --- | --- |
| `<script>` | パーサを止めて取得 | 取得したらすぐ。その間パーサは止まる | 書いた順 |
| `<script defer>` | パーサと並行 | 構文解析が終わった後 | 書いた順 |
| `<script async>` | パーサと並行 | 取得できた時点ですぐ（パーサを一時止める） | 取得が終わった順。決まらない |
| `<script type="module">` | パーサと並行（依存も） | 既定では `defer` と同じ | 書いた順 |

`defer` と `async` の付いたスクリプトは、`document.write` で入力に割り込むことができません。**割り込まないと約束する代わりに、パーサを止めずに済ませてもらう**、という取引です。

## 止まっている間に、先を読む

それでも、止まる `<script>` は多くのページに残っています。パーサが止まっている間、後ろに書かれた画像やスタイルシートの取得まで止まってしまうと、第 68 回で見た往復の待ち時間が、直列に積み重なります。

そこでブラウザは、**プリロードスキャナ**という 2 つ目の簡易なパーサを持っています。本物のパーサが止まっている間に、この先の HTML をざっと読んで `<img src>`、`<link href>`、`<script src>` を見つけ、**取得だけ先に始めます**（[web.dev](https://web.dev/articles/preload-scanner)）。木は作りません。URL を拾うだけです。

```
本物のパーサ:     ────[script を待って停止]──────────→ 再開
プリロードスキャナ:      └─ 先を読む → img, css の取得を開始
```

第 12 回で見た CPU のアウトオブオーダー実行が、命令の依存で止まっている間に、依存しない後ろの命令を先に進めていたのと同じ発想です。

<Callout type="tip" title="プリロードスキャナに見えない書き方は遅い">
  JavaScript で後から `img.src = ...` を設定したり、CSS の中の `background-image` で指定したりした資源は、
  HTML の文字列の中に URL がないので、プリロードスキャナには見つけられません。
  それらは、スクリプトの実行やスタイルの計算が済むまで取得が始まりません。
  重要な資源を HTML に直接書く、あるいは `<link rel="preload">` で予告するのはこのためです。
</Callout>

## CSS も木になる

スタイルシートも、同じように字句解析と構文解析を経て、**CSSOM**（CSS Object Model）という構造になります。CSS の文法は HTML よりずっと規則的で、誤った宣言は**その宣言だけを捨てて**先へ進みます。1 つの書き損じでスタイルシート全体が無効にならないようにするためです。

DOM と CSSOM がそろって、ようやく「どの要素に、どのスタイルが当たるか」を計算できます。それが次の回の最初の段です。

## DOM は、JavaScript から見えるオブジェクト

最後に、DOM の実体について触れておきます。DOM のノードは、エンジンの中では C++ のオブジェクトです。JavaScript から `document.querySelector` で得られるのは、それを包んだ**JavaScript 側の代理のオブジェクト**です。

```
JavaScript のヒープ          エンジン（C++）のヒープ
  div の代理オブジェクト ──→  HTMLDivElement の実体
```

JavaScript から DOM を触るたびに、**2 つの言語の境界**を越えています。第 76 回で見た FFI と同じ構造で、1 回ごとのコストは小さくても、ループで大量に繰り返すと効いてきます。さらに、DOM を書き換えると次の回で見るスタイルやレイアウトの計算がやり直しになります。「DOM を触ると遅い」と言われる理由は、この 2 つが重なっていることにあります。

## 自分の環境で見る

- 開発者ツールの Elements パネルで、閉じタグを省いた HTML や、`<table>` の中に文字を書いた HTML を開き、**ソースとの違い**を確かめる
- Performance パネルで記録すると、メインスレッドに「Parse HTML」の区間が並び、`<script>` のところで途切れているのが見えます
- 表示のソース（`view-source:`）が送られてきた文字列、Elements が回復後の木です

## まとめ

- HTML のパーサは、文字コードを決め、トークナイザで単語に割り、スタックを使って木を組み立てる。コンパイラと同じ 2 段
- ただしコンパイラと違い、誤りで止まってはいけない。回復の手順まで仕様で決まっているので、どのブラウザでも同じ木になる
- パーサは届いた分から逐次的に木を伸ばす。これが最初の表示を速くする
- 普通の `<script>` は、HTML を書き換えうるのでパーサを止める。`defer` と `async` は、割り込まない代わりに止めずに済ませる約束
- パーサが止まっている間も、プリロードスキャナが先を読んで取得を始める
- CSS は CSSOM になる。誤った宣言はその宣言だけを捨てる
- DOM のノードは C++ のオブジェクトで、JavaScript から触るたびに言語の境界を越える
