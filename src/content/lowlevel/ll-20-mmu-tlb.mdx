## 変換のコスト

前回の内容をまとめると、1 回のメモリアクセスはこうなります。

```
仮想アドレス
  → 1 段目の表を読む（メモリアクセス 1 回目）
  → 2 段目の表を読む（2 回目）
  → 3 段目の表を読む（3 回目）
  → 4 段目の表を読む（4 回目）
  → 物理アドレスが確定
  → 実際のデータを読む（5 回目）
```

**データを 1 回読むために、メモリを 5 回読んでいます。** 5 倍遅くなります。これでは仮想メモリは使い物になりません。

この 4 回の表引きを **ページウォーク** と呼びます。

## 結果を覚えておく

解決策は単純です。**一度変換した結果を、小さな高速メモリに覚えておく**。

これが **TLB**（Translation Lookaside Buffer）です。MMU の中にある、仮想ページ番号から物理ページ番号への対応を記録した小さな連想メモリです。

```
仮想アドレス
  → TLB を引く
     ├─ あった（TLB ヒット）   → すぐ物理アドレスが得られる。1 サイクル
     └─ なかった（TLB ミス）   → ページウォークする。そして結果を TLB に入れる
```

TLB のエントリ数は、世代にもよりますが数十〜数千です。少ないように見えますが、局所性のおかげで**ヒット率は 99% を超える**のが普通です。

| | 容量 | ヒット時 |
| --- | --- | --- |
| L1 TLB（命令用 / データ用が別） | 各 64〜128 エントリ | 1 サイクル |
| L2 TLB（統合） | 1000〜3000 エントリ | 数サイクル |

<Callout type="note" title="TLB もキャッシュの一種">
  構造はデータキャッシュと同じです。連想度があり、追い出しのアルゴリズムがあり、
  階層になっています。違うのは、**キャッシュするのがデータではなくアドレス変換**という点だけです。
</Callout>

## TLB がカバーできる範囲

TLB のエントリ数 × ページサイズが、**TLB ミスなしでアクセスできるメモリの広さ**です。

| ページサイズ | 1500 エントリでカバーできる範囲 |
| --- | --- |
| 4KB | 6MB |
| 2MB | 3GB |
| 1GB | 1.5TB |

4KB ページでは、**わずか 6MB を超えると TLB ミスが頻発します**。数十 GB のデータを扱うデータベースやインメモリ処理では、これが深刻なボトルネックになります。

ヒュージページが効くのは、まさにこの点です。同じエントリ数で、数百倍の範囲をカバーできます。

<Callout type="tip" title="TLB ミスとキャッシュミスは別物">
  TLB ミスが起きても、ページテーブル自体がキャッシュに載っていれば、ページウォークは比較的速く終わります。
  逆に、TLB にヒットしてもデータがキャッシュになければ、メモリを待ちます。
  **両者は独立に起きる**ので、測るときも分けて見る必要があります。

```bash
perf stat -e dTLB-load-misses,dTLB-loads,cache-misses ./a.out
```
</Callout>

## プロセスを切り替えると全部無効になる

TLB のエントリは「仮想ページ 0x401 → 物理ページ 0x8A3」という形です。しかし、**どのプロセスの 0x401 なのか**が記録されていません。

素朴な実装では、プロセスを切り替えるたびに **TLB を全部捨てる**必要があります。切り替え直後はすべてのアクセスが TLB ミスになり、しばらく遅くなります。

これがコンテキストスイッチのコストの中でも大きな部分です。切り替え自体は数百サイクルでも、**その後の TLB とキャッシュの再構築に数千〜数万サイクルかかります**。

### 識別子を付ける

そこで、TLB のエントリにプロセスの識別子を持たせる仕組みが導入されました。

- x86 では **PCID**（Process Context Identifier）
- ARM では **ASID**（Address Space Identifier）

識別子が付いていれば、別プロセスのエントリと混ざる心配がないので、**切り替えても捨てる必要がありません**。戻ってきたときに、前のエントリがまだ残っています。

## 複数のコアで足並みを揃える

OS がページテーブルを書き換えたとき（メモリを解放した、権限を変えた）、TLB に残っている古い情報を消す必要があります。自分のコアだけなら `invlpg` 命令 1 つで済みます。

ところが、**同じプロセスが複数のコアで動いている場合**、他のコアの TLB にも古い情報が残っています。ハードウェアは自動では消してくれません。

そこで OS は、他のコアに割り込みを送って「このエントリを捨てろ」と指示します。これを **TLB シュートダウン** と呼びます。

コア間割り込みの往復が発生するため、非常に高価です。数千サイクルかかることもあります。

<Callout type="warn" title="munmap や mprotect が遅い理由">
  メモリの解放や権限変更は、TLB シュートダウンを伴います。
  マルチスレッドのプログラムで、**頻繁に大きな領域を確保・解放すると、
  この同期コストが支配的**になることがあります。

  メモリアロケータが解放したメモリをすぐ OS に返さず、
  自前で持ち続けるのは、この回避のためでもあります。
</Callout>

## KPTI：性能を犠牲にした対策

Meltdown への対策として導入された **KPTI**（Kernel Page Table Isolation）は、カーネル用とユーザ用でページテーブルを完全に分けるものです。

従来は、カーネル空間を各プロセスのページテーブルに含めていました（アクセスは特権レベルで拒否する）。これにより、システムコールのたびにページテーブルを切り替える必要がありませんでした。

KPTI ではこれを分離したため、**システムコールのたびにページテーブルの切り替えと TLB の破棄が発生します**。システムコールを多用するワークロードで、5〜30% の性能低下が報告されました。

PCID を持つ CPU では、この影響が緩和されます。切り替えても TLB を捨てずに済むためです。

## ハードウェアかソフトウェアか

TLB ミス時のページウォークを、誰がやるかにも方式があります。

- **ハードウェアウォーク**（x86、ARM）：MMU が自動でページテーブルを辿る。OS はテーブルの形式を守る必要がある
- **ソフトウェアウォーク**（MIPS、初期の SPARC）：TLB ミスで例外が発生し、OS がハンドラの中で変換する。テーブルの形式を自由に決められるが、遅い

現代の主要なアーキテクチャはハードウェアウォークです。

## まとめ

- 変換のたびにページウォーク（4 回のメモリ読み）が必要なので、結果を TLB に覚える
- TLB のヒット率は 99% を超えるが、エントリ数 × ページサイズを超える範囲を触ると急激に悪化する
- ヒュージページは TLB のカバー範囲を数百倍にする
- プロセス切り替えで TLB を捨てる必要があったが、PCID / ASID で回避できる
- 複数コアでのページテーブル変更は TLB シュートダウンを伴い、高価
- KPTI は Meltdown 対策だが、性能を犠牲にしている
