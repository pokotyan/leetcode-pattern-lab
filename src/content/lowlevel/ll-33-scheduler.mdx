## 誰が譲るのか

複数のプロセスで 1 つの CPU を分け合うとき、切り替えのきっかけをどう作るか。方式は 2 つです。

### 協調的マルチタスク

**各プロセスが自発的に CPU を手放す**のを待ちます。

単純で、切り替えの位置が予測できる利点があります。しかし致命的な問題があります。

> **1 つのプロセスが手放さなければ、システム全体が固まる。**

バグで無限ループに入ったプログラムがあれば、他のプロセスは二度と動けません。

Windows 3.x、Mac OS 9 まではこの方式でした。アプリケーションが 1 つ固まるとシステム全体を再起動するしかなかったのは、この設計によるものです。

### プリエンプティブ（先取り的）マルチタスク

**OS が強制的に CPU を取り上げます**。

仕組みの核心は **タイマ割り込み** です。ハードウェアのタイマが一定間隔で割り込みを発生させ、その中で OS が「このプロセスはもう十分使った」と判断すれば、別のプロセスに切り替えます。

**プロセスの協力は要りません。** 無限ループに入ったプログラムがあっても、タイマ割り込みは必ず入るので、他のプロセスは動けます。

現代の汎用 OS はすべてこの方式です。

<Callout type="note" title="プリエンプションを支えているのはハードウェア">
  「OS が強制的に」と言っても、ソフトウェアだけでは実行中のプログラムを止められません。
  **タイマ割り込みという、プログラムの意思とは無関係に発生する事象**があって初めて成立します。
  第 13 回で見た割り込みの仕組みが、ここで決定的な役割を果たしています。
</Callout>

## タイムスライス

1 回の割り当てで使える時間を **タイムスライス**（クォンタム）と呼びます。

長さの決め方には trade-off があります。

| 長さ | 利点 | 欠点 |
| --- | --- | --- |
| 短い | 応答が速い。対話的な処理が快適 | 切り替えのコストが積み上がる |
| 長い | 切り替えのコストが減る。スループットが上がる | 応答が遅くなる |

数ミリ秒程度が一般的です。Linux では固定値ではなく、実行可能なプロセス数に応じて動的に決まります。

## Linux のスケジューラ

Linux の既定は **CFS**（Completely Fair Scheduler、完全に公平なスケジューラ）です。

考え方はこうです。

> **理想的には、n 個のプロセスがそれぞれ CPU の 1/n を同時に使うべきである。**

もちろん物理的には無理なので、**実際に使った時間を記録し、最も使っていないプロセスを次に走らせます**。

この「使った時間」を **仮想実行時間**（vruntime）と呼び、赤黒木で管理します。木の最左端が、最も vruntime の小さい（＝最も使っていない）プロセスです。取り出しが O(log n) で済みます。

<Callout type="tip" title="I/O 中心のプロセスが有利になる">
  I/O 待ちのプロセスは CPU を使わないので、vruntime が増えません。
  待ちから戻ったとき、vruntime が小さいので**すぐに選ばれます**。

  これにより、キー入力への反応やネットワーク応答が速くなります。
  「対話的なプロセスを優遇する」という特別な処理を入れなくても、
  公平さの定義から自然に導かれる、という設計の妙です。
</Callout>

2023 年の Linux 6.6 では、CFS を置き換える **EEVDF**（Earliest Eligible Virtual Deadline First）が導入されました。レイテンシの要求を考慮に入れた方式です。

## 優先度

すべてのプロセスを等しく扱いたくない場合があります。

### nice 値

通常のプロセスの優先度です。-20（最優先）から +19（最も譲る）まで。既定は 0。

```bash
nice -n 10 ./batch_job          # 低い優先度で起動
renice -n 5 -p 1234            # 実行中のプロセスを変更
```

**値を上げられる（優先度を下げる）のは誰でもできますが、下げる（優先度を上げる）には root 権限が要ります。**

CFS では、nice 値が vruntime の進む速さに影響します。nice 値が低いプロセスは vruntime がゆっくり進むので、より多く選ばれます。nice 値 1 の差は、おおよそ 1.25 倍の CPU 時間の差になります。

### リアルタイム優先度

通常のプロセスより**常に優先される**クラスです。

| ポリシー | 動作 |
| --- | --- |
| `SCHED_FIFO` | 優先度が同じなら、**自分から手放すまで走り続ける** |
| `SCHED_RR` | 優先度が同じプロセス間でラウンドロビン |
| `SCHED_DEADLINE` | 「この期間内にこれだけの時間を保証する」という指定 |

```bash
chrt -f 50 ./realtime_task
```

<Callout type="warn" title="リアルタイム優先度は危険">
  `SCHED_FIFO` のプロセスが無限ループに入ると、**そのコアで通常のプロセスが一切動けなくなります**。
  シェルすら反応しなくなり、復旧が困難になります。

  Linux には保護として、リアルタイムプロセスが CPU を占有しすぎないよう制限する仕組みがあります。

```bash
cat /proc/sys/kernel/sched_rt_runtime_us    # 950000（1 秒あたり 0.95 秒まで）
```
  それでも、慎重に扱うべき機能です。
</Callout>

## 優先度の逆転

優先度が高いプロセスが、低いプロセスに待たされる現象があります。

```
低優先度のプロセス L がロックを取る
  ↓
高優先度のプロセス H が同じロックを待つ
  ↓
中優先度のプロセス M が走り始め、L を追い出す
  ↓
L が走れないのでロックが解放されない
  ↓
H はいつまでも待たされる
```

**H より優先度の低い M が、実質的に H を止めています。**

1997 年、火星探査車 Mars Pathfinder がこの問題で再起動を繰り返しました。地上から優先度継承を有効にするパッチを送って解決した、という事例が有名です。

対策は **優先度継承**（priority inheritance）です。ロックを持つプロセスの優先度を、待っている中で最も高いものに一時的に引き上げます。

## マルチコアでの配分

複数のコアがある場合、スケジューラはさらに次を考慮します。

- **負荷分散**：コア間で仕事の量を均す
- **キャッシュ親和性**：同じコアで動かし続けたほうがキャッシュが効く
- **NUMA**：メモリが近いノードのコアを選ぶ
- **電力**：使わないコアを眠らせる。性能コアと効率コアの使い分け

負荷分散とキャッシュ親和性は相反します。均すために移動させると、キャッシュが冷えます。Linux は「十分な不均衡がある場合だけ移動する」という調整をしています。

## コンテナでの制限

cgroup により、CPU の使用量を制限できます。

```bash
# cgroup v2
echo "50000 100000" > /sys/fs/cgroup/mygroup/cpu.max      # 100ms 中 50ms まで
```

Kubernetes の CPU limit はこれを使っています。

<Callout type="warn" title="CPU スロットリング">
  制限に達すると、そのプロセスは次の期間まで**完全に止められます**。
  平均 CPU 使用率が低くても、瞬間的に上限を超えると数十ミリ秒止まります。
  これが「レイテンシが時々跳ね上がる」原因になることがあります。

```bash
cat /sys/fs/cgroup/mygroup/cpu.stat | grep throttled
```
  スロットリングの発生回数を確認できます。
</Callout>

## まとめ

- 協調的は自発的に手放すのを待つ方式。1 つ固まると全部止まる
- プリエンプティブはタイマ割り込みで強制的に取り上げる。ハードウェアが前提
- Linux の CFS は「実際に使った時間が最も少ないもの」を選ぶ
- I/O 中心のプロセスは自然に優遇される
- nice 値は通常の優先度、リアルタイム優先度は常に優先されるが危険
- 優先度の逆転は優先度継承で対処する
- cgroup による CPU 制限は、スロットリングで瞬間的な停止を生む
