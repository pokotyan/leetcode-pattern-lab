## IdP と SP: ログインを外に出す

SSO の登場人物は 2 種類です。

- **IdP**（Identity Provider）: 利用者を認証する側。パスワードや多要素の確認（第 109 回）はここだけで行う。Microsoft Entra ID、Okta、Google Workspace、Keycloak など
- **SP**（Service Provider）: 利用者が使いたいサービスの側。SAML ではこう呼び、OIDC では **RP**（Relying Party、依拠する側）と呼ぶ。役割は同じ

SP は利用者のパスワードを見ません。代わりに IdP から「この利用者は、いつ、どの方法で認証された」という**署名付きの文書**を受け取り、それを信じてログインさせます。SAML ではこの文書を**アサーション**、OIDC では **ID トークン**（第 113 回）と呼びます。

**SP と IdP は直接通信しない**のが、ブラウザ向けの SSO の特徴です。文書はブラウザを経由して運ばれます。SP から IdP へは「認証してほしい」という依頼をリダイレクトで、IdP から SP へは結果をフォームの POST で届けます。SP は IdP の公開鍵（証明書）だけを事前に受け取っておけばよく、社内ネットワークの奥にある IdP に SaaS からつなぐ必要がありません。

## SSO は 2 段のセッションでできている

「1 回のログインで全部に入れる」の正体は、**2 種類のセッションの組み合わせ**です。第 110 回で見たセッションが、2 か所にあります。

```
                          ブラウザ
             ┌───────────────┼───────────────┐
             │               │               │
   Cookie(IdP のドメイン)   Cookie(SP-A)    Cookie(SP-B)
             │               │               │
             ↓               ↓               ↓
    ┌─────────────────┐  ┌────────┐     ┌────────┐
    │ IdP のセッション │  │ SP-A の │     │ SP-B の │
    │ 「alice は 9:00 に│  │セッション│     │セッション│
    │  認証済み」       │  └────────┘     └────────┘
    └─────────────────┘       ↑               ↑
             │   アサーション  │               │
             └────────────────┴───────────────┘
                 （ブラウザ経由で届ける）
```

1. 利用者が SP-A を開く。SP-A のセッションは無いので、IdP へリダイレクトする
2. IdP にもセッションが無いので、ログイン画面を出す。パスワードを確かめ、**IdP のドメインに Cookie を置いて IdP のセッションを作る**
3. IdP はアサーションを作り、ブラウザ経由で SP-A に届ける。SP-A はそれを検証し、**自分のドメインに Cookie を置いて SP-A のセッションを作る**
4. 利用者が SP-B を開く。SP-B のセッションは無いので、IdP へリダイレクトする
5. **今度は IdP のセッションがある**。ログイン画面を出さずに、そのままアサーションを作って SP-B に返す

5 の「画面を出さずに返す」が SSO の体感のすべてです。**2 回目以降のログインは、IdP の Cookie が送られることで省略されている**だけで、SP-B は SP-A と同じ手順でアサーションを受け取っています。

この構造から、SSO の性質がいくつも導けます。

- **IdP のセッションの寿命と、各 SP のセッションの寿命は別**。IdP のセッションが切れても、SP-A のセッションが生きていれば SP-A は使える。逆に SP-A のセッションが切れても、IdP のセッションが生きていれば、画面なしで入り直せる
- **ログアウトが難しい**。SP-A でログアウトしても、IdP のセッションが残っていれば次の瞬間に入り直せる。IdP でログアウトしても、SP-B の Cookie は SP-B のドメインにあり、IdP からは消せない。後で詳しく見ます
- **IdP が止まっても、すでにある SP のセッションは生きる**。止まるのは新しいログインだけ（第 119 回）

## SAML 2.0 の部品

SAML（Security Assertion Markup Language）2.0 は、2005 年 3 月に OASIS が標準にした、XML で SSO を行う仕組みです（[OASIS SAML 2.0 の仕様一式](https://docs.oasis-open.org/security/saml/v2.0/)）。仕様は層に分かれています。

| 文書 | 決めていること |
| --- | --- |
| Core | アサーションと、要求・応答のメッセージ（`AuthnRequest`、`Response`、`LogoutRequest` など）の XML の形。署名の付け方 |
| Bindings | そのメッセージを何に載せて運ぶか。HTTP-Redirect、HTTP-POST、HTTP-Artifact、SOAP |
| Profiles | 部品を組み合わせた使い方。ブラウザ向けの SSO は **Web Browser SSO Profile** |
| Metadata | IdP と SP が互いのエンドポイント URL と証明書を交換する XML |

実務の SAML は、ほぼ次の組み合わせです。**SP から IdP への `AuthnRequest` は HTTP-Redirect バインディング**（XML を DEFLATE で圧縮し、Base64 にして URL のクエリに入れる。[Bindings 3.4](https://docs.oasis-open.org/security/saml/v2.0/saml-bindings-2.0-os.pdf)）、**IdP から SP への `Response` は HTTP-POST バインディング**（Base64 にした XML を、自動で送信される HTML フォームに入れる。[Bindings 3.5](https://docs.oasis-open.org/security/saml/v2.0/saml-bindings-2.0-os.pdf)）。応答を POST で送るのは、署名付きの XML が大きく、URL に収まらないからです。

SP が応答を受け取る URL を **ACS**（Assertion Consumer Service）と呼びます。OAuth の redirect_uri（第 112 回）に当たるものです。

## 手元で確かめる: Keycloak を IdP にする

Keycloak 26.7 を Docker で起動し（ホスト側のポート 18107）、realm `ll106` に利用者 `alice` と、SAML の SP を 2 つ（`https://sp-a.example/saml` と `https://sp-b.example/saml`）登録しました。SP は実在しないので、ブラウザの代わりに Python の `requests` で Cookie を持ち回り、IdP が返す HTML からフォームの中身を取り出します。

まず IdP のメタデータを取ります。SP がこれを読み込むことで、IdP の URL と署名の検証に使う証明書が SP に伝わります。

```
$ curl -s http://localhost:18107/realms/ll106/protocol/saml/descriptor
<md:EntityDescriptor ... entityID="http://localhost:18107/realms/ll106">
  <md:IDPSSODescriptor WantAuthnRequestsSigned="true" ...>
    <md:KeyDescriptor use="signing"><ds:KeyInfo> ... <ds:X509Certificate>MIICmTCCAYEC...
```

メタデータは `WantAuthnRequestsSigned="true"` と宣言していますが、実験を簡単にするため、2 つの SP には要求への署名を求めない設定にしています。次に SP-A の立場で `AuthnRequest` を作ります。

```python
xml = (f'<samlp:AuthnRequest ... ID="{rid}" Version="2.0" IssueInstant="{now}" '
       f'Destination="{IDP}" AssertionConsumerServiceURL="https://sp-a.example/acs" '
       f'ProtocolBinding="urn:oasis:names:tc:SAML:2.0:bindings:HTTP-POST">'
       f'<saml:Issuer>https://sp-a.example/saml</saml:Issuer></samlp:AuthnRequest>')
deflated = zlib.compress(xml.encode())[2:-4]      # zlib のヘッダと末尾を外した生の DEFLATE
url = IDP + "?" + urlencode({"SAMLRequest": base64.b64encode(deflated), "RelayState": "/dashboard"})
```

`RelayState` は、ログインが済んだ後に SP のどのページへ戻すかを SP 自身が覚えておくための値で、IdP は中身を見ずにそのまま返します（80 バイト以内。[Bindings 3.4.3](https://docs.oasis-open.org/security/saml/v2.0/saml-bindings-2.0-os.pdf)）。SP-A、続けて SP-B の順にこの URL を開いた結果です（手元の実行結果）。

```
AuthnRequest ID: _81ece6f9576f4317ac06ce080352d16b  XML 468 bytes -> DEFLATE+Base64 372 chars
[sp-a] IdP returned login form (HTTP 200); cookies: ['AUTH_SESSION_ID', 'KC_AUTH_SESSION_HASH', 'KC_RESTART']
[sp-a] auto-submit form action=https://sp-a.example/acs RelayState=/dashboard
[sp-a] IdP cookies now: ['AUTH_SESSION_ID', 'KC_AUTH_SESSION_HASH', 'KEYCLOAK_IDENTITY', 'KEYCLOAK_SESSION']
AuthnRequest ID: _cfb459e640fa4bdfabc5b8dfdb09f119  XML 468 bytes -> DEFLATE+Base64 376 chars
[sp-b] IdP returned SAMLResponse immediately, no login form
[sp-b] auto-submit form action=https://sp-b.example/acs RelayState=/dashboard
```

SP-A のときはログイン画面が返り、パスワードを送った後に `KEYCLOAK_IDENTITY` と `KEYCLOAK_SESSION` という Cookie が増えました。これが **IdP のセッション**です。SP-B のときは、その Cookie が送られたので**ログイン画面が出ずに**応答が返りました。前の節の手順 5 がそのまま起きています。

IdP が返した HTML は、`action="https://sp-a.example/acs"` のフォームに `SAMLResponse`（Base64 にした XML）と `RelayState` を hidden で入れ、`window.onload` でフォームを送信するだけのページでした。利用者には一瞬の画面遷移にしか見えません。

管理 API で alice のセッションを見ると、IdP は 1 つのセッションに 2 つの SP をぶら下げて覚えていました。この一覧が、後で見るシングルログアウトの出発点になります。

```
"id": "hy9Xmf3fk86X1UAQaAetdFiP", "username": "alice",
"clients": { "6b816d26-...": "https://sp-b.example/saml",
             "2f623ebe-...": "https://sp-a.example/saml" }
```

<Callout type="note" title="Keycloak の Cookie が SameSite=None である理由">
  Keycloak の Cookie は、すべて `Secure; SameSite=None` 付きで返ってきました。
  SAML の応答は、IdP のサイトから SP のサイトへの**サイトをまたいだ POST** で届きます。
  第 110 回で見たとおり、`SameSite=Lax` の Cookie はサイトをまたいだ POST では送られません。
  SP が `AuthnRequest` の ID を Cookie に覚えておき、ACS で照合する作りにしている場合、その Cookie が Lax だと ACS に届かず、ログインが失敗します。
  ブラウザの既定が Lax になってから、SAML の SP では、ACS で使う Cookie に `SameSite=None` を明示する必要が生じました。
  なお、この実験では `http://localhost` なので、`Secure` の Cookie を `requests` に送らせるための手当てをしています。
</Callout>

## アサーションを読む

SP-A に届いた `SAMLResponse` を Base64 で戻すと、7,762 バイトの XML でした。署名と属性を省いて骨格を示します。

```xml
<samlp:Response ID="ID_f501bc6e-..." InResponseTo="_81ece6f9..." Destination="https://sp-a.example/acs">
  <saml:Issuer>http://localhost:18107/realms/ll106</saml:Issuer>
  <dsig:Signature> ... 応答全体への署名 ... </dsig:Signature>
  <samlp:Status><samlp:StatusCode Value="urn:oasis:names:tc:SAML:2.0:status:Success"/></samlp:Status>
  <saml:Assertion ID="ID_3edf27a6-...">
    <saml:Issuer>http://localhost:18107/realms/ll106</saml:Issuer>
    <dsig:Signature> ... アサーションへの署名 ... </dsig:Signature>
    <saml:Subject>
      <saml:NameID Format="urn:oasis:names:tc:SAML:1.1:nameid-format:unspecified">alice</saml:NameID>
      <saml:SubjectConfirmation Method="urn:oasis:names:tc:SAML:2.0:cm:bearer">
        <saml:SubjectConfirmationData InResponseTo="_81ece6f9..."
            NotOnOrAfter="2026-09-28T10:58:47.314Z" Recipient="https://sp-a.example/acs"/>
      </saml:SubjectConfirmation>
    </saml:Subject>
    <saml:Conditions NotBefore="2026-09-28T10:53:47.314Z" NotOnOrAfter="2026-09-28T10:54:47.314Z">
      <saml:AudienceRestriction><saml:Audience>https://sp-a.example/saml</saml:Audience></saml:AudienceRestriction>
    </saml:Conditions>
    <saml:AuthnStatement AuthnInstant="2026-09-28T10:53:49.328Z"
        SessionIndex="hy9Xmf3fk86X1UAQaAetdFiP::2f623ebe-..." SessionNotOnOrAfter="2026-09-28T20:53:49.328Z">
      ...
    </saml:AuthnStatement>
  </saml:Assertion>
</samlp:Response>
```

各部分は、第 111 回で見た JWT の登録済みクレームとほぼ一対一に対応します。

| SAML | 意味 | JWT で近いもの |
| --- | --- | --- |
| `Issuer` | 誰が発行したか | `iss` |
| `NameID` | 誰についての文書か | `sub` |
| `Audience` | どの SP に宛てたか | `aud` |
| `Conditions` の `NotBefore` / `NotOnOrAfter` | 有効な期間 | `nbf` / `exp` |
| `SubjectConfirmationData` の `InResponseTo` | どの要求への応答か | ID トークンの `nonce`（第 113 回） |
| `Recipient` | どの ACS に届けるべきか | redirect_uri の照合 |
| `AuthnStatement` | いつ、どの方法で認証したか | `auth_time`、`acr` |
| `SessionIndex` | IdP 側のどのセッションか | `sid` |

`SessionIndex` は、IdP のセッションの ID と SP-A の内部 ID を `::` でつないだものでした。

`Method="...:cm:bearer"` は、**このアサーションを持っている者を本人とみなす**という意味です。第 114 回のベアラトークンと同じ弱さを持ちます。拾った人が使えるので、仕様は SP に次の確認を**必須**としています（[Profiles 4.1.4.3](https://docs.oasis-open.org/security/saml/v2.0/saml-profiles-2.0-os.pdf)）。

- 署名を検証する
- `Recipient` が、応答を受け取った ACS の URL と一致する
- `NotOnOrAfter` が過ぎていない（IdP との時計のずれは許容する。第 140 回）
- `InResponseTo` が、自分の出した `AuthnRequest` の ID と一致する
- さらに POST バインディングでは、**アサーションは署名されていなければならず**、SP は使い終わったアサーションの ID を有効期間のあいだ覚えておき、**2 回目を拒否しなければならない**（[Profiles 4.1.4.5](https://docs.oasis-open.org/security/saml/v2.0/saml-profiles-2.0-os.pdf)）

## XML 署名: 文書の一部に署名する

アサーションの中の `dsig:Signature` を開くと、次の形をしています。

```xml
<dsig:SignedInfo>
  <dsig:CanonicalizationMethod Algorithm="http://www.w3.org/2001/10/xml-exc-c14n#"/>
  <dsig:SignatureMethod Algorithm="http://www.w3.org/2001/04/xmldsig-more#rsa-sha256"/>
  <dsig:Reference URI="#ID_3edf27a6-a8ad-4e7c-b908-4784af97d759">
    <dsig:Transforms>
      <dsig:Transform Algorithm="http://www.w3.org/2000/09/xmldsig#enveloped-signature"/>
      <dsig:Transform Algorithm="http://www.w3.org/2001/10/xml-exc-c14n#"/>
    </dsig:Transforms>
    <dsig:DigestMethod Algorithm="http://www.w3.org/2001/04/xmlenc#sha256"/>
    <dsig:DigestValue>GEoBDIMaTPRmv5XsWOtEEmni9i3PoVnSEMytzfLMcPE=</dsig:DigestValue>
  </dsig:Reference>
</dsig:SignedInfo>
<dsig:SignatureValue>QU1PfpZW3QqK...</dsig:SignatureValue>
<dsig:KeyInfo> ... <dsig:X509Certificate>MIICmTCC...
```

仕組みは第 98 回の署名と同じで、**ハッシュを 2 段にした**ものです。

1. `Reference` の `URI="#ID_..."` で、**文書の中のどの要素に署名するか**を ID で指す
2. その要素から `Signature` 自身を取り除き（enveloped-signature）、**正規化**（c14n）してから SHA-256 を取る。結果が `DigestValue`
3. `SignedInfo` 全体を正規化し、RSA-SHA256 で署名する。結果が `SignatureValue`

正規化が要るのは、XML には意味を変えずに書き方を変える自由（属性の順番、空白、名前空間の宣言の位置）があり、そのままではバイト列が一致しないからです。JWT が Base64URL にしたバイト列そのものに署名する（第 111 回）のと比べて、**XML 署名は「解釈した後の木」に署名する**ので、解釈の仕方が検証の結果を左右します。

仕様は、署名の `Reference` を**ちょうど 1 つ**にし、署名される要素（アサーションか応答）の ID を指すことを求めています（[Core 5.4.2](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf)）。

受け取った応答を、Python の signxml 5.1 で検証しました。鍵は**メタデータで事前に受け取った証明書**を使います。

```
original assertion           OK   signed NameID = alice
NameID alice -> admin        FAIL InvalidDigest: Digest mismatch for reference 0 (#ID_3edf27a6-...)
KeyInfo cert == metadata cert: True
```

NameID を 1 か所書き換えると、ダイジェストが一致しなくなります。署名が保証しているのはここまでです。

<Callout type="warn" title="よくある誤解: 応答に入っている証明書で検証すればよい">
  アサーションの `KeyInfo` には証明書が入っていますが、これは**攻撃者が自由に差し替えられる部分**です。
  自分で作った鍵で署名し、その証明書を `KeyInfo` に入れれば、「その証明書で」検証は通ります。
  第 98 回で見たとおり、署名が保証するのは「この**鍵**で署名された」ことだけで、その鍵が IdP のものかは別に確かめなければなりません。
  SAML では、それを**メタデータで事前に交換した証明書**が担います。`KeyInfo` の証明書は、どの鍵を使うかの目印にしか使ってはいけません。
  この回の実験で両者が一致したのは、本物の IdP の応答だからです。
</Callout>

## 署名は通るのに、別人でログインできる

SAML の実装で繰り返し起きてきたのが **XML 署名ラッピング**（XSW）です。原因は、**署名を検証する処理と、アサーションの中身を読む処理が、別々に文書を探している**ことです。

手元で、単純化した例を作りました。応答全体の署名が無い（アサーションだけに署名する設定は一般的です）応答を用意し、本物の署名付きアサーションを `Extensions` の中に移し、その前に**署名の無い偽のアサーション**（NameID を admin にしたもの）を置きます。そのうえで 2 つの SP の書き方を比べます。

```python
def naive_sp(root):          # 署名は「どこかに」あれば検証し、名前は「最初に見つかったもの」を読む
    ref = root.xpath("//ds:Reference/@URI", namespaces=NS)[0][1:]
    target = root.xpath(f"//*[@ID='{ref}']")[0]
    XMLVerifier().verify(to_doc(target), x509_cert=cert)
    return root.xpath("//saml:Assertion/saml:Subject/saml:NameID/text()", namespaces=NS)[0]

def careful_sp(root):        # 構造を固定し、検証した要素そのものから名前を読む
    assertions = root.xpath("saml:Assertion", namespaces=NS)
    if len(assertions) != 1:
        raise ValueError(...)
    r = XMLVerifier().verify(to_doc(assertions[0]), x509_cert=cert)
    return r.signed_xml.xpath(".//saml:NameID/text()", namespaces=NS)[0]
```

```
naive SP   -> admin
careful SP -> rejected: InvalidInput Expected to find XML element Signature in ...Assertion
```

素朴な SP では、**署名の検証は本物のアサーションに対して成功し、ログインは偽のアサーションの名前で行われました**。署名は壊れていません。壊れているのは、検証した物と使った物が同じであることを確かめなかった部分です。

2012 年の研究は、14 の SAML の実装のうち 11 に、この種の重大な脆弱性があったと報告しています（[Somorovsky ほか, USENIX Security 2012](https://www.usenix.org/conference/usenixsecurity12/technical-sessions/presentation/somorovsky)）。そしてこの問題は、今も続いています。Ruby の代表的な SAML ライブラリ ruby-saml だけでも、次のとおりです。

<Callout type="tip" title="SP を作る側の原則">
  SAML の検証を自分で書かないこと。そのうえで、使うライブラリが次を守っているかを確かめます。
  **検証した要素そのものから値を読む**、**期待する構造（Response の直下にアサーションが 1 つ）以外を拒否する**、
  **署名の鍵はメタデータのものに固定する**、**`Audience`・`Recipient`・`InResponseTo`・期限・再利用を全部確かめる**。
  そして、SAML のライブラリの CVE は、公開された当日に追うべきものとして扱います。
</Callout>

## IdP 起点のログイン

ここまでの流れは、SP が `AuthnRequest` を出すところから始まりました（**SP 起点**）。SAML にはもう 1 つ、**IdP 起点**のログインがあります。社内ポータルに並んだアプリのアイコンを押すと、IdP が要求を受けずにいきなり応答を作って SP に送る形です。仕様では「求められていない応答」（unsolicited response）と呼び、この応答は `InResponseTo` を**含んではならない**とされています（[Profiles 4.1.5](https://docs.oasis-open.org/security/saml/v2.0/saml-profiles-2.0-os.pdf)）。

Keycloak で、IdP のセッションの Cookie を持ったまま IdP 起点の URL を開くと、確かに `InResponseTo` の無い応答が返りました。

```
GET /realms/ll106/protocol/saml/clients/sp-a
200 <form name="saml-post-binding" method="post" action="https://sp-a.example/acs">
'InResponseTo' in xml: False
<saml:SubjectConfirmationData NotOnOrAfter="2026-09-28T10:59:34.359Z" Recipient="https://sp-a.example/acs"/>
```

SP の側から見ると、これは**自分が頼んでいない応答**です。`InResponseTo` を照合できないので、次のことを防ぐ手段が 1 つ減ります。

- **ログイン CSRF**: 攻撃者が自分のアカウントの正当な応答を手に入れ、それを被害者のブラウザから SP に POST させる。被害者は気づかずに**攻撃者のアカウントで**ログインし、入力したデータを攻撃者に渡してしまう（第 110 回の CSRF の、ログインへの応用）
- **盗まれた応答の持ち込み**: 有効期間内の応答を別のブラウザから送る。再利用の検出（ID を覚える）と短い `NotOnOrAfter` だけが頼りになる

OIDC には、この IdP 起点に当たる流れがありません。認可リクエストの `state` と `nonce`（第 112、113 回）で、**必ず RP が始めたやり取りに応答を結び付ける**設計になっています。IdP 起点が必要な場合でも、ポータルのアイコンを「SP のログイン開始 URL へのリンク」にしておけば、SP 起点の流れに乗せられます。

## SAML と OIDC、どちらを選ぶか

OIDC は第 113 回で見たとおり、OAuth の上に「誰がログインしたか」を載せたものです。SSO の骨格（IdP のセッション、ブラウザ経由の署名付き文書、各アプリのセッション）は同じで、違いは運び方と形式にあります。

| | SAML 2.0 | OIDC |
| --- | --- | --- |
| 文書 | XML のアサーション | JWT の ID トークン |
| 署名 | XML 署名（正規化してから署名） | JWS（バイト列にそのまま署名） |
| 鍵の配布 | メタデータの XML を事前に交換（手作業の更新が多い） | Discovery と JWKS を URL から取る（第 113 回） |
| 応答の運び方 | ブラウザのフォーム POST | 認可コードをリダイレクトで渡し、RP がトークンエンドポイントから直接受け取る |
| API の呼び出し | 決めていない | OAuth のアクセストークンがそのまま使える |
| 主な使われ方 | 企業向け SaaS への従業員の SSO | 一般向けのログイン、モバイル、SPA、API を含む構成 |

OIDC の認可コードフローでは、**ID トークンがブラウザを通らず**、RP がサーバ間の通信で受け取ります。ブラウザの中で書き換えられる機会そのものがありません。SAML の POST バインディングでは、アサーションは必ずブラウザを通り、SP は署名だけを頼りに中身を信じます。さらに、SAML は API を呼ぶためのトークンを持たないので、ログインの後に API も呼びたいアプリは結局 OAuth を別に使うことになります。

**新しく作るなら OIDC**、が一般的な答えです。それでも企業向け SaaS で SAML が残るのは、SAML が OIDC（[OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html) は 2014 年）より 9 年早く企業の IdP（Active Directory の AD FS など）に行き渡り、**顧客の IdP が話せるものに SP が合わせる**という力関係があるからです。企業向けの SaaS は、両方を受け付けるのが普通になっています。

<Callout type="warn" title="よくある誤解: SSO にすれば各アプリのセキュリティは IdP に任せられる">
  IdP が保証するのは「アサーションを発行した時点で、この利用者を認証した」ことだけです。
  その後のセッションの寿命、Cookie の属性、CSRF の対策、何をしてよいかの判定（第 115 回）は、すべて各 SP の仕事のままです。
  また、IdP でアカウントを止めても、SP のセッションや SP が発行した API トークンは生き続けます（第 117 回）。
  SSO は**認証を 1 か所に集める**仕組みであって、各アプリの責任を減らす仕組みではありません。
</Callout>

## ログアウトは 1 回では終わらない

2 段のセッションの図に戻ると、「全部からログアウトする」には、IdP のセッションと、**そのセッションから生まれたすべての SP のセッション**を消す必要があります。IdP は SP の Cookie に触れられないので、各 SP に「消してほしい」と伝えるしかありません。

SAML のシングルログアウト（SLO）は、これをブラウザのリダイレクトの連鎖で行います（[Profiles 4.4](https://docs.oasis-open.org/security/saml/v2.0/saml-profiles-2.0-os.pdf)、[Core 3.7](https://docs.oasis-open.org/security/saml/v2.0/saml-core-2.0-os.pdf)）。IdP を「セッションの権威」、各 SP を「セッションの参加者」と呼び、IdP は参加者を 1 つずつ回ります。手元で、SP-A から IdP に `LogoutRequest` を送ると、IdP はブラウザを SP-B のログアウト用 URL へ送り出しました。

```
302 Location: https://sp-b.example/slo?SAMLRequest=jZLdatwwEIVfZdG91pL...
<samlp:LogoutRequest ... Destination="https://sp-b.example/slo">
  <saml:Issuer>http://localhost:18107/realms/ll106</saml:Issuer>
  <saml:NameID ...>alice</saml:NameID>
  <samlp:SessionIndex>hy9Xmf3fk86X1UAQaAetdFiP::6b816d26-...</samlp:SessionIndex>
```

ここで SP-B は実在しないので、ブラウザは先へ進めません。この時点で管理 API を見ると、IdP のセッションは SP-A と SP-B をぶら下げたまま残っていました。**連鎖のどこか 1 つが応答しない、エラーを返す、利用者がタブを閉じる**と、そこから先の SP にも、最初に頼んだ SP-A にも、ログアウトが届きません。SLO が「動くことを期待してはいけない機能」と言われるのは、この構造のためです。

OIDC には、ログアウトを伝える仕様が 3 つあります。

| 仕様 | 伝え方 | 弱点 |
| --- | --- | --- |
| [Session Management 1.0](https://openid.net/specs/openid-connect-session-1_0.html) | RP のページに IdP の iframe を埋め、`postMessage` でセッションの変化を定期的に尋ねる | iframe から IdP の Cookie が読めないと動かない |
| [Front-Channel Logout 1.0](https://openid.net/specs/openid-connect-frontchannel-1_0.html) | IdP のログアウト画面が、各 RP のログアウト用 URL を iframe で開く | iframe の中から RP の Cookie が読めないと動かない |
| [Back-Channel Logout 1.0](https://openid.net/specs/openid-connect-backchannel-1_0.html) | IdP が各 RP に**サーバ間で** POST し、ログアウトトークン（JWT）を渡す | RP がサーバ側のセッションを `sid` や `sub` で探して消せる作りである必要がある |

バックチャネルのログアウトトークンは、ID トークンに似た JWT で、`events` に `http://schemas.openid.net/event/backchannel-logout` を持ち、`nonce` を**含んではならない**と決められています。ID トークンと取り違えて、ログインに使われないようにするためです（第 111 回の「用途を型で分ける」考え方）。**ブラウザを通らないので連鎖が途切れず、RP ごとに成否が分かる**のが強みです。ただし、JWT を Cookie に入れただけの自己完結型のセッション（第 110 回）では、サーバの側に消す対象がありません。バックチャネルのログアウトを受けるには、サーバ側にセッションの一覧を持つ必要があります。

## 第三者 Cookie の制限が壊したもの

上の表の iframe を使う 2 つは、**IdP のページの中に RP を、または RP のページの中に IdP を埋め込む**仕組みです。iframe の中のページにとって、自分の Cookie は**第三者 Cookie**になります。ブラウザがそれを送らなくなると、この仕組みは動きません。

- Safari は 2020 年 3 月に、サイトをまたぐ Cookie を既定ですべて遮断した（[WebKit](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)）
- Firefox は 2022 年 6 月に、Cookie をサイトごとに分けて保存する Total Cookie Protection を全利用者の既定にした（[Mozilla](https://blog.mozilla.org/en/mozilla/firefox-rolls-out-total-cookie-protection-by-default-to-all-users-worldwide/)）
- Chrome は第三者 Cookie の廃止を計画していたが、2025 年 4 月に、現行の設定による選択を続け、新しい確認画面も出さないと発表した（[Privacy Sandbox](https://privacysandbox.google.com/blog/privacy-sandbox-next-steps)）。執筆時点（2026 年 9 月）で、Chrome の既定では第三者 Cookie は送られる

OIDC の仕様自身も、ブラウザがサイトのデータへのアクセスを遮断し始めたことで、Session Management と Front-Channel Logout が動かなくなりうると注記しています（上の表の各仕様）。同じ理由で、SPA が iframe の中で `prompt=none` の認可リクエストを送り、画面を出さずに IdP のセッションを確かめる「サイレント認証」も、Safari や Firefox では当てにできなくなりました。**SSO の 2 段のセッションのうち、IdP のセッションを RP の画面の中から覗く手段が塞がれた**、というのがこの変化の要点です。

対策の方向は 2 つです。1 つは**ブラウザを通さない**こと。ログアウトはバックチャネルで、セッションの確認は RP のサーバ側（第 114 回の BFF）で行います。もう 1 つは、**ブラウザ自身に連携ログインを仲介させる** FedCM（Federated Credential Management）です。IdP と RP のつながりを、iframe や第三者 Cookie ではなくブラウザの API で扱うもので、Chrome 108（2022 年 11 月）で提供が始まり（[Privacy Sandbox](https://privacysandbox.google.com/blog/fedcm-shipping)）、W3C の Federated Identity Working Group で標準化が進んでいます（[W3C](https://www.w3.org/TR/fedcm/)）。

## この回の部品の組み合わせ

SAML の SSO も、単体の部品ではなく、ここまでの章の部品の組み合わせで成り立っています。

| 部品 | 担っていること | 欠けるとどうなるか |
| --- | --- | --- |
| IdP のセッション（Cookie、第 110 回） | 2 回目以降のログインを省く | 毎回パスワードを入れることになる |
| 認証（パスワード、多要素、第 109 回） | IdP での最初の確認 | アサーションが誰でも手に入る |
| XML 署名（第 98 回）とメタデータの証明書（第 101 回） | アサーションが IdP のものであり、改ざんされていない | 誰でもアサーションを作れる |
| `Audience`・`Recipient`・`InResponseTo`・期限 | 別の SP 宛て、別の要求への応答、古い応答を拒む | 他の SP のために出た応答で入られる |
| TLS（第 16 章） | ブラウザと IdP・SP の間でアサーションを盗まれない | ベアラの文書が経路で拾われる |
| SP のセッションと認可（第 110 回、第 115 回） | ログイン後に何をしてよいか | SSO はログインまでしか面倒を見ない |

## まとめ

- SSO は、認証を IdP に集め、各 SP は IdP の署名付きの文書を受け取ってログインさせる仕組み。SP は利用者のパスワードを見ない
- 実体は **IdP のセッション**と**各 SP のセッション**の 2 段。2 回目以降のログインが省かれるのは、IdP の Cookie が送られるから。寿命も消し方も別々
- SAML 2.0 は、`AuthnRequest` を HTTP-Redirect で、`Response` を HTTP-POST で、ブラウザ経由で運ぶ。アサーションは `Issuer`・`NameID`・`Audience`・期限・`InResponseTo` を持ち、JWT のクレームとほぼ対応する
- アサーションはベアラなので、SP は署名・`Recipient`・期限・`InResponseTo`・再利用を必ず確かめる。署名の鍵はメッセージ中の証明書ではなく、メタデータのものを使う
- XML 署名は文書の一部を ID で指して署名するので、**検証した物と使う物がずれる**と署名ラッピングが起きる。ruby-saml では 2024〜2025 年にも同種の脆弱性が続いた
- IdP 起点のログインは `InResponseTo` を持たず、ログイン CSRF や応答の持ち込みに弱い。OIDC にはこの流れが無い
- 新しく作るなら OIDC が一般的。SAML は、顧客の IdP に合わせる企業向け SaaS で残っている
- ログアウトは、IdP が各 SP に伝えるしかない。SAML の SLO と OIDC のフロントチャネルはブラウザの連鎖や iframe に頼るので途切れやすく、第三者 Cookie の制限でさらに壊れた。バックチャネルのログアウトと FedCM が、その代わりの方向

次の回では、SSO で「ログインできる」ようになった利用者のアカウントを、そもそも誰が各アプリに作り、退職したときに誰が消すのかを見ます。SCIM によるアカウントの配布と、email でアカウントを突き合わせることの危険です。
