## 観測する、という章

ここまでの章では、プログラムの下で何が起きているかを順に見てきました。この章では向きを変えて、**本番で動いているものを、外からどう観測するか**を扱います。

観測の難しさは、次の 3 つの条件を同時に満たさなければならないところにあります。

- 対象を止めない
- 対象を作り直さない
- 観測のせいで対象を壊さない

第 67 回のデバッガは、1 つ目で脱落します。ブレークポイントで止めてしまうからです。ログを足す方法は、2 つ目で脱落します。足すには作り直して配り直す必要があります。

この章では、この 3 つを満たすための 2 つの流れを見ます。

- **カーネルの側から見る:** 今回の eBPF
- **アプリケーションの側から見る:** 次回と次々回の OpenTelemetry と自動計装

最後に、ここまでの話を確かめるための道具をまとめます。

## 始まりは、パケットのふるい分け

eBPF の「BPF」は Berkeley Packet Filter の略です。1992 年 12 月、McCanne と Jacobson が、パケットを取り込むための新しい仕組みを論文にまとめました（[The BSD Packet Filter](https://www.tcpdump.org/papers/bpf-usenix93.pdf)）。

解きたかった問題はこうです。`tcpdump` で「ポート 80 の TCP だけ」を見たいとします。

- **素朴な方法:** 全パケットをカーネルからユーザ空間にコピーし、そこで捨てる。1 パケットごとに境界を越えるコピーが起き（第 41 回）、ほとんどは捨てるためのコピーになる。
- **論文の答え:** ふるい分けの条件を**小さなプログラム**にしてカーネルに渡し、カーネルの中で実行させる。条件に合ったものだけをユーザ空間に渡す。

```bash
tcpdump -d 'tcp port 80'     # 条件が、どんな命令列に翻訳されるかを見る
```

このプログラムを実行するのが、カーネルの中の小さな仮想機械です。レジスタは 2 本（A と X）だけで、命令は数十種類です。**後ろ向きの分岐がない**ので、必ず終わります。条件を判定するだけなら、それで十分でした。

今では、これを **cBPF**（classic BPF）と呼びます。第 77 回で見た seccomp のフィルタも、この cBPF で書かれています。システムコールの番号を「パケット」に見立てて、許すかどうかを判定しているわけです。

## 汎用の小さな機械へ

2014 年ごろ、この仮想機械は大きく作り直されました。**eBPF**（extended BPF）です（[Classic BPF vs eBPF](https://docs.kernel.org/bpf/classic_vs_extended.html)）。

| | cBPF | eBPF |
| --- | --- | --- |
| レジスタ | A と X の 2 本（32 ビット） | 汎用 10 本 + 読み取り専用のフレームポインタ（64 ビット） |
| 関数呼び出し | なし | カーネルの**ヘルパー関数**を呼べる |
| 状態 | なし | **map** に残せる |
| 用途 | パケットとシステムコールの判定 | 観測、ネットワーク、セキュリティ全般 |

レジスタの使い方には約束があります。R1〜R5 で引数を渡し、R0 で戻り値を受け取ります。これは第 31 回の呼び出し規約そのものです。**実在の CPU の呼び出し規約に素直に写せる**ように決めてあるので、後で JIT するときに変換が単純になります。

  第 61 回で、Wasm は「特定のハードウェアを持たない ISA」だと書きました。
  eBPF も同じ種類のものです。
  **カーネルの中で動くことを前提にした命令セット**で、コンパイラ（Clang / LLVM）が
  C で書いたプログラムを eBPF の機械語に落とします。
</Callout>

## 読み込む前に、すべての道筋を調べる

カーネルの中でプログラムを動かすのは危険です。無限ループすればそのコアが止まり、変なアドレスを読めばカーネルごと落ちます。第 13 回で見たとおり、カーネルの中には守ってくれる人がいません。

そこで eBPF は、**読み込む時点で**プログラムを検査します。これが **検証器**（verifier）です（[eBPF verifier](https://docs.kernel.org/bpf/verifier.html)）。検証器は、プログラムを実行する代わりに、**分岐のすべての組み合わせを机上でなぞります**。そのうえで、次のことを確かめます。

- **必ず終わること。** ループは、回数に上限があると証明できるものだけ許す。
- **範囲外を触らないこと。** ポインタを使う前に NULL を確かめたか、配列の添字は範囲内か。
- **初期化していないレジスタを読まないこと。**
- **許された関数だけを呼ぶこと。** フックの種類ごとに、呼べるヘルパーが決まっている。

証明できなければ、**読み込みそのものを拒否します**。実行してから止めるのではなく、実行させません。

制限は少しずつ緩められてきました。命令数の上限は Linux 5.2 で 4,096 から 100 万に増え、5.3 からは上限の決まったループが書けるようになりました（[LWN](https://lwn.net/Articles/794934/)、[eBPF Docs](https://docs.ebpf.io/linux/concepts/loops/)）。それでも、検証器が見るのは**すべての道筋**です。ループの 1 周ごと、分岐の組み合わせごとに数えるので、少し複雑なプログラムはすぐに上限に当たります。

<Callout type="tip" title="Wasm のサンドボックスとの違い">
  第 62 回の Wasm も、安全を保証する仕組みでした。ただし、保証の取り方が違います。

  - **Wasm:** 範囲外アクセスは実行時の境界チェックで止め、無限ループはランタイムが時間で打ち切る。**書けるプログラムの形は自由**。
  - **eBPF:** 実行前に**証明できたものだけ**を動かす。実行時には止めない（止める人がいない）。**書けるプログラムの形が狭い**。

  カーネルの中では、プログラムを途中で止めること自体が難しいので、
  「そもそも止まらないプログラムを入れさせない」側に倒しています。
</Callout>

## 機械語に直してから動かす

検証を通ったプログラムは、多くの環境で **JIT** されます。eBPF の命令列を、その CPU の機械語に変換します（第 32 回）。

- 検証器を通っているので、変換後の機械語が範囲外を触らないことは、変換前の段階で保証されている。
- 第 32 回で見た W^X の問題はカーネルの中でも同じで、書き終えたページを実行専用にしてから使う。

変換の結果は、後で見る `bpftool` で確かめられます。

```
xlated 552B  jited 464B
```

`xlated` は検証器が手を入れた後の eBPF の命令列、`jited` は変換後の機械語の大きさです。

## カーネルとユーザ空間の受け渡し: map

eBPF のプログラムは、イベントが起きるたびに一瞬だけ動いて終わります。**呼び出しをまたいで何かを覚えておく**には、**map** を使います。

map は、**カーネルの中にある表**です。eBPF のプログラムからも、ユーザ空間のプログラムからも、同じ表を読み書きできます。

```
   カーネル                                ユーザ空間
 ┌─────────────────────────┐
 │ イベント発生（open など） │
 │      ↓                  │
 │ eBPF プログラム           │
 │   count[comm] += 1  ────┼──→ ┌──────────┐ ←── 読む ──  集計ツール
 │                         │    │   map    │
 └─────────────────────────┘    └──────────┘
```

| 種類 | 形 | 使いどころ |
| --- | --- | --- |
| ハッシュ | キー → 値 | プロセスごと、接続ごとの集計 |
| 配列 | 添字 → 値 | 固定個数のカウンタ、設定値 |
| CPU ごとの配列 / ハッシュ | コアごとに別の値 | 取り合いを避けた高速な集計（第 17 回の false sharing を避ける） |
| リングバッファ | 順番に積む列 | イベントを 1 件ずつユーザ空間へ流す |

集計なら、**カーネルの中で数えてしまい、結果だけを渡す**のが基本です。イベントごとにユーザ空間へ渡すと、第 41 回のコストがイベントの数だけかかります。これは、tcpdump の論文がそもそも避けたかったことです。

1 件ずつ渡す必要があるときは、リングバッファを使います。Linux 5.8 で入ったもので、複数のコアが同時に書き込み、1 つの読み手が順に読みます（[BPF ring buffer](https://docs.kernel.org/bpf/ringbuf.html)）。

## どこに差し込むか: フック

eBPF のプログラムは、それ単体では動きません。**カーネルのどこかに取り付けて**（attach）、そこを通過したときに呼ばれます。取り付ける場所の種類によって、見えるものと、壊れにくさが違います。

| フック | どこに付くか | 安定性 |
| --- | --- | --- |
| **tracepoint** | カーネルの開発者があらかじめ置いた観測点 | 高い。名前と引数が約束として保たれる |
| **kprobe** | カーネルの**ほぼ任意の関数** | 低い。関数名や引数は版で変わり、インライン化で消える |
| **uprobe** | ユーザ空間のプログラムの任意の関数 | 低い。そのバイナリの版に依存する |
| **USDT** | ユーザ空間のプログラムに、作者が置いた観測点 | 高い。作者が約束として残したもの |
| **perf イベント** | CPU のカウンタ、タイマ | 高い。一定間隔で呼ばせるとサンプリングのプロファイラになる |
| **XDP / tc** | ネットワークの受信直後、送受信の途中 | 高い。第 55 回で見た、`sk_buff` より手前 |
| **LSM** | 権限の判定をする箇所 | 高い。アクセスを拒否することもできる |
| **cgroup** | cgroup に属するプロセスの通信、デバイスアクセス | 高い。コンテナ単位で動作を変えられる |

**安定した観測点（tracepoint、USDT）を先に探し、無ければ任意の関数（kprobe、uprobe）に付ける。** これが基本の順序です。kprobe で書いた道具は、カーネルの版を上げたときに黙って動かなくなることがあります。

### kprobe と uprobe は、書き換えたブレークポイント

kprobe と uprobe の基本の仕組みは、第 67 回のデバッガと同じです。

1. 対象の命令の先頭をブレークポイント命令に書き換える。
2. 実行がそこに来ると例外が起き、カーネルに制御が移る。
3. カーネルは、止めて人間に知らせる代わりに、**その場で eBPF のプログラムを実行し、元の命令を実行して先へ進める**。

違いは、止まらないことです。デバッガは人間が見るために止めますが、kprobe は数マイクロ秒で済ませて先へ進みます。**「止めない」という 1 つ目の条件を、ブレークポイントの仕組みのまま満たしている**わけです。

uprobe は、ファイルの**ページそのもの**に付きます。同じ実行ファイルを動かしている**全プロセスに、同時に効きます**。第 24 回で見たとおり、同じファイルのページは複数のプロセスで共有されているからです。

## カーネルの版の違いを越える: BTF と CO-RE

kprobe で関数の引数を読むとき、eBPF のプログラムは**カーネルの構造体の中身**を読むことになります。たとえば `struct task_struct` の、ある位置にあるフィールドです。

ここで、第 28 回と第 31 回の問題が出てきます。構造体のフィールドの位置（オフセット）は、**コンパイルしたときの定義で決まる**ものでした。カーネルの版が変われば、フィールドが増え、位置がずれます。設定によっても変わります。

以前は、**動かすマシンの上で、そのカーネルのヘッダを使ってコンパイルする**のが唯一の解決策でした。そのため、本番のマシンにコンパイラとカーネルのヘッダを入れる必要がありました。

**BTF** と **CO-RE**（Compile Once – Run Everywhere）が、これを変えました（[BPF CO-RE](https://nakryiko.com/posts/bpf-portability-and-co-re/)）。

- **BTF:** カーネルが**自分の型の情報**を持つようにしたもの。`/sys/kernel/btf/vmlinux` にあり、どの構造体のどのフィールドがどの位置にあるかが書かれている。
- **CO-RE:** eBPF のプログラムには「`task_struct` の `pid` を読む」という**名前での記録**を残しておく。読み込むときに、ローダがそのカーネルの BTF を引いて、**実際のオフセットに書き換える**。

これは第 30 回のローダがやっていた**再配置**と同じ発想です。アドレスを後で埋める代わりに、構造体の中の位置を後で埋めています。

## 手元で動かす

Docker Desktop の Linux VM（カーネル 6.12）の中で、特権付きのコンテナから試せます。

```bash
docker run --rm -it --privileged alpine:3.20 sh
apk add bpftrace bpftool
mount -t tracefs none /sys/kernel/tracing
```

どのプロセスが `openat` を呼んでいるかを、数秒だけ数えてみます。

```bash
bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'
```

```
@[dockerd]: 44
@[kubelet]: 83
@[containerd]: 800
@[containerd-shim]: 1277
```

コンテナの中から、**ホスト（VM）全体のプロセス**が見えています。第 68 回で見たとおり、名前空間は見える範囲を分けるだけで、カーネルは 1 つだからです。特権を渡すことの重さが、ここにも表れています。

次は kprobe です。`vfs_read` にかかった時間を、マイクロ秒単位のヒストグラムにします。入口で時刻を map に記録し、出口で差を取ります。

```bash
bpftrace -e '
  kprobe:vfs_read { @s[tid] = nsecs; }
  kretprobe:vfs_read /@s[tid]/ { @us = hist((nsecs - @s[tid]) / 1000); delete(@s[tid]); }
  END { clear(@s); }'
```

```
@us:
[0]                 8829 |@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@|
[1]                 3150 |@@@@@@@@@@@@@@@@@@                                  |
[2, 4)              2540 |@@@@@@@@@@@@@@                                      |
[4, 8)              2829 |@@@@@@@@@@@@@@@@                                    |
...
[512K, 1M)             1 |                                                    |
```

集計はすべてカーネルの中で済み、ユーザ空間に渡るのは最後のヒストグラムだけです。大半の読み込みは 1 マイクロ秒未満で終わっています（ページキャッシュに当たっている、第 48 回）。一方で、0.5 秒を超えたものが 1 件あります。**平均では見えない裾が、分布では見えます**。

いま読み込まれている eBPF のプログラムの一覧も見られます。

```bash
bpftool prog show
```

この VM では、自分で何も読み込んでいなくても、`cgroup_device` という種類のプログラムが 43 個見つかりました。cgroup v2 では、デバイスへのアクセス制御が eBPF で実装されています。第 70 回の runc がコンテナを作るたびに、「このコンテナが触ってよいデバイス」を判定する小さなプログラムを読み込んでいるのです。**eBPF は観測の道具である前に、すでにカーネルの部品として使われています**。

## できないこと、払うもの

**特権が要る。** eBPF のプログラムは、カーネルの中のデータを読めます。そのため、読み込むには強い権限が必要です。Linux 5.8 で、この権限は `CAP_SYS_ADMIN` から **`CAP_BPF`** として切り出されました（[capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html)）。一般ユーザによる利用は、カーネルの設定で既定では禁止できるようになっています（[CONFIG_BPF_UNPRIV_DEFAULT_OFF](https://cateee.net/lkddb/web-lkddb/BPF_UNPRIV_DEFAULT_OFF.html)）。

**タダではない。** kprobe は、通過するたびに例外とプログラムの実行が挟まります。1 回は小さくても、毎秒数百万回通る関数に付ければ、はっきりと遅くなります。「本番で使える」は「どこに付けても無視できる」という意味ではありません。

**書けるプログラムが狭い。** 検証器が証明できない形は書けません。任意のメモリ確保、無制限のループ、眠って待つことはできません。複雑な処理はユーザ空間に回すことになります。

**見えるのは、カーネルから見えるものだけ。** eBPF は、システムコール、関数の出入り、パケットを見られます。しかし、**「この読み込みは、どの HTTP リクエストのためのものか」という、アプリケーションの文脈**は、そのままでは見えません。

<Callout type="note" title="最後の制限が、次の話につながる">
  カーネルの側からは、何がどれだけ起きたかは見えても、
  **なぜ起きたか**（どのリクエストの処理の一部なのか）は見えません。
  その文脈を持っているのはアプリケーションです。
  次回は、アプリケーションの側から文脈を付けて記録する仕組みを見ます。
</Callout>

## まとめ

- 観測の条件は、止めない・作り直さない・壊さないこと
- BPF は、パケットのふるい分けをカーネルの中で済ませるための小さな仮想機械として始まった。seccomp も同じ cBPF を使う
- eBPF は汎用のレジスタ、ヘルパー関数、map を持つ命令セットになった
- 検証器は、すべての道筋をなぞって、必ず終わり範囲外を触らないと証明できたものだけを読み込む
- 検証を通ったプログラムは JIT され、機械語として動く
- map はカーネルとユーザ空間が共有する表。集計はカーネルの中で済ませ、結果だけを渡す
- フックは安定した観測点（tracepoint、USDT）を先に探す。kprobe と uprobe は、止まらないブレークポイント
- BTF と CO-RE は、構造体のオフセットを読み込み時に埋める。ローダの再配置と同じ発想
- 特権が要り、タダではなく、アプリケーションの文脈は見えない

次は、アプリケーションの側から「どのリクエストの処理か」という文脈を付けて記録する OpenTelemetry を見ます。
