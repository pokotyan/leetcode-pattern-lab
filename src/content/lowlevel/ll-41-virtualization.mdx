## 2 つの分離のしかた

1 台の機械で複数の環境を動かす方法は、大きく 2 つあります。

**仮想マシン**：ハードウェアごと真似る。ゲスト OS が丸ごと動く。

**コンテナ**：カーネルは共有し、見える範囲だけを分ける。

```
   仮想マシン                    コンテナ
┌─────────────────┐        ┌─────────────────┐
│ App  │ App      │        │ App  │ App      │
├──────┼──────────┤        ├──────┴──────────┤
│Guest │ Guest OS │        │                 │
│ OS   │          │        │                 │
├──────┴──────────┤        │                 │
│  ハイパーバイザ    │        │                 │
├─────────────────┤        ├─────────────────┤
│   ホスト OS       │        │   ホスト OS      │
├─────────────────┤        ├─────────────────┤
│   ハードウェア     │        │   ハードウェア    │
└─────────────────┘        └─────────────────┘
```

| | 仮想マシン | コンテナ |
| --- | --- | --- |
| カーネル | ゲストごとに別 | **ホストと共有** |
| 起動時間 | 数十秒 | **1 秒未満** |
| メモリのオーバーヘッド | 数百 MB〜 | **数 MB** |
| 分離の強さ | **強い** | 弱い |
| 別の OS を動かす | できる | **できない** |

## 仮想マシンの仕組み

ゲスト OS は、自分が物理マシンの上で動いていると思っています。特権命令を実行しようとしますが、実際にはリング 0 では動いていません。

古典的な手法は **トラップ・アンド・エミュレート** です。特権命令が例外を発生させ、ハイパーバイザがそれを捕まえて、本物のハードウェアの代わりに処理します。

ところが、x86 にはこれが機能しない命令がありました。**特権が足りなくても例外を出さず、黙って違う結果を返す**命令が 17 個ほどあったのです。このため、初期の VMware は実行時に命令列を書き換える手法（バイナリ変換）を使っていました。

その後、ハードウェア支援が導入されます。

- **Intel VT-x / AMD-V**：リング 0 の外側に新しいモード（VMX root）を作り、ゲストをそのまま動かせるようにした
- **EPT / NPT**：ゲストの仮想アドレス → ゲストの物理アドレス → ホストの物理アドレス、という**二重の変換をハードウェアで行う**

<Callout type="note" title="二重のページテーブル">
  仮想化以前は、ゲストの物理アドレスをホストの物理アドレスに変換する処理を
  ソフトウェアで行っていました（シャドウページテーブル）。
  ゲストがページテーブルを更新するたびにハイパーバイザが介入する必要があり、高価でした。

  EPT により、この 2 段階の変換がハードウェアで行われるようになりました。
  第 4 章で見たページングが、もう 1 段重なった形です。
</Callout>

### 準仮想化

ゲスト OS を改変し、「自分は仮想化されている」と分かった上で動かす方式です。特権命令を使う代わりに、ハイパーバイザに直接依頼します（hypercall）。

真似をする必要がないぶん速くなります。Xen が採用し、現在も**デバイス**の部分では広く使われています（virtio）。ディスクやネットワークのハードウェアを忠実に真似るより、専用の効率的なインタフェースを使うほうが速いためです。

## コンテナの仕組み

コンテナは、仮想化ではありません。**ただのプロセス**です。ただし、見える範囲が制限されています。

### 名前空間

「何が見えるか」を分離する仕組みです。

| 名前空間 | 分離するもの |
| --- | --- |
| PID | プロセス ID。コンテナ内では自分が PID 1 に見える |
| Mount | ファイルシステムのマウント状態 |
| Network | ネットワークインタフェース、ルーティング、ポート |
| UTS | ホスト名 |
| IPC | プロセス間通信の資源 |
| User | ユーザ ID。**コンテナ内の root をホストの一般ユーザに対応させられる** |
| cgroup | cgroup の階層 |

第 30 回で見た `clone` のフラグとして指定します。**プロセスとスレッドの違いが `clone` のフラグだったのと、まったく同じ仕組みです。**

```bash
unshare --pid --fork --mount-proc bash     # PID 名前空間を分けてシェルを起動
ps aux                                      # 自分しか見えない
```

### cgroup

「どれだけ使えるか」を制限する仕組みです。

| 対象 | 制限できるもの |
| --- | --- |
| CPU | 使用率、コアの割り当て |
| メモリ | 上限、スワップ |
| I/O | 帯域、IOPS |
| PID | プロセス数の上限 |

```bash
cat /sys/fs/cgroup/memory.max
cat /sys/fs/cgroup/cpu.max
```

### 合わせると

**コンテナ = 名前空間（見える範囲の制限）+ cgroup（使える量の制限）+ ファイルシステムの差し替え**

Docker はこれらを組み合わせ、イメージの管理と配布を加えたものです。「コンテナ」という単一の機能が OS にあるわけではありません。

<Callout type="tip" title="ホストから見える">
  コンテナ内のプロセスは、ホストから普通に見えます。

```bash
ps aux | grep <コンテナ内のプロセス>
```
  PID はホストとコンテナで違います（コンテナ内では 1 でも、ホストでは 12345）。
  **同じプロセスに 2 つの番号が付いている**という状態です。
</Callout>

## 分離の強さの違い

**コンテナはカーネルを共有しています。** カーネルに脆弱性があれば、コンテナの境界を越えられる可能性があります。

| 攻撃の起点 | 仮想マシン | コンテナ |
| --- | --- | --- |
| アプリケーションの脆弱性 | ゲスト OS 内に留まる | コンテナ内に留まる |
| **カーネルの脆弱性** | ゲスト OS 内に留まる | **ホスト全体が危険** |
| ハイパーバイザの脆弱性 | ホスト全体が危険 | — |

攻撃面の大きさが違います。ハイパーバイザのインタフェースは狭く、カーネルのシステムコールは 300 以上あります。

そのため、信頼できないコードを動かす場面（マルチテナントのクラウド、CI の実行環境）では、中間的な選択肢が使われます。

- **Firecracker**：極めて軽量な仮想マシン。AWS Lambda が使用。起動 125ms 程度
- **gVisor**：ユーザ空間でシステムコールを横取りして処理し、ホストのカーネルへの到達を減らす
- **Kata Containers**：コンテナを軽量 VM の中で動かす

## WebAssembly

さらに別方向の分離として、**WebAssembly**（Wasm）があります。

- サンドボックス内の**線形メモリ**しか触れない。ホストのメモリに到達する手段がない
- システムコールに相当する機能は、明示的にインポートしたものだけ（WASI）
- OS にもアーキテクチャにも依存しない
- 起動がマイクロ秒単位

**「何ができるか」を、能力の受け渡しとして明示的に設計している**点が、従来の方式と根本的に違います。従来は「すべてできる状態から、禁止するものを削る」という方向でした。

エッジコンピューティングやプラグイン機構で採用が進んでいます。

## どれを選ぶか

| 状況 | 適した方式 |
| --- | --- |
| 別の OS が必要 | 仮想マシン |
| 信頼できないコードを動かす | 仮想マシン、軽量 VM、Wasm |
| 同じ OS 上で環境を分けたい | コンテナ |
| 起動速度が重要 | コンテナ、Wasm |
| 密度（台あたりの数）が重要 | コンテナ、Wasm |

## まとめ

- 仮想マシンはハードウェアを真似る。コンテナはカーネルを共有し、見える範囲を制限する
- x86 には仮想化できない命令があり、ハードウェア支援（VT-x、EPT）で解決された
- 準仮想化は、ゲストが仮想化を自覚して協力する方式。デバイスでは今も主流
- コンテナは名前空間と cgroup の組み合わせ。単一の機能ではない
- カーネルを共有するため、コンテナの分離は仮想マシンより弱い
- 中間的な選択肢（Firecracker、gVisor）と、別方向の分離（Wasm）がある

最後に、ここまでの話を実際に自分の環境で確かめるための道具をまとめます。
