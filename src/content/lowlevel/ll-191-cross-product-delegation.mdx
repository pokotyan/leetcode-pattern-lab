## 同じ利用者として、隣のプロダクトを呼ぶ

ある会社に、文書を書く **docs**、数字を集計する **analytics**、メールを配る **mailer** の 3 つのプロダクトがあるとします。どれも同じ IdP でログインします（第 183 回の SSO）。そこへ、次のような要望が来ます。

- docs の画面で「この文書の閲覧数」を出したい。docs のサーバが、**ログインしている alice として** analytics の API を呼ぶ
- analytics は、集計結果を alice 宛てに配りたい。analytics が、**alice として** mailer の API を呼ぶ
- CLI からも、同じ alice として 3 つをまとめて操作したい

第 190 回の型 6 は、1 つのシステムの中のマイクロサービスの話でした。ここでは、**別々のチームが別々に作り、別々の時期に IdP とつないだプロダクト**どうしが呼び合います。登録済みのクライアントも、トークンを検証するコードも、プロダクトごとにばらばらです。そのうえで「本人として呼ぶ」ために何を渡すかを決めなければなりません。

この回では、よく使われる方式を 5 つに分け、同じ問いで比べます。基礎の部品は前の回で見ました。ID トークンとアクセストークンの違いは第 179 回、`aud` の検証とトークン交換の基本は第 181 回、スコープと権限が別の軸であることは第 182 回、受け取ったトークンを上流へそのまま流さない話は第 189 回です。ここでは、それらを**プロダクト間の連携方式の選択**という形で組み直します。

## 先に分けておく 4 つの問い

方式を比べる前に、1 回の呼び出しに乗っている問いを分けておきます。

1. **誰のためか**（利用者）: `iss` と `sub` の組。メールアドレスで本人を照合するなら、その値を誰が確かめたのかも問われる
2. **どこ宛てか**（宛先）: `aud`。このトークンを受け取ってよいのは誰か
3. **何をしてよいか**（委任の範囲と本人の権限）: スコープは「利用者がこのクライアントに任せた範囲」の上限で、「利用者がそもそも何をしてよいか」は別に判定する（第 182 回）
4. **誰が呼んでいるか**（呼び出し元のサービス）: 実際に通信してきたのがどのサーバか。mTLS やワークロードの ID で確かめる（第 188 回）

方式の違いは、ほとんどが 2 の扱い方の違いです。1 と 3 はどの方式でも必要で、4 はどの方式にも重ねられます。

もう 1 つ、守る相手を 2 つに分けておきます。

- **正当なトークンが盗まれ、別の場所で使われる**こと。宛先を狭める、寿命を短くする、鍵に縛る、まとめて止める、が効きます
- **信頼すべきでない経路の本人情報が、正当なトークンになる**こと。たとえば IdP に誰かが勝手な接続先（ソーシャルログインや別の社内 IdP）を足し、そこで作った「alice」が署名付きのトークンになる場合です。こちらは宛先をいくら狭めても防げません。IdP の設定の変更権限と監査、どの接続先の利用者をどの本人に対応付けるかで防ぎます

<Callout type="note" title="署名が正しいことは、本人が正しいことではない">
  署名が保証するのは「この IdP が発行した」ことまでです（第 149 回、第 181 回）。IdP の中で、どの経路で誰を確かめたかはトークンの外にあります。
  プロダクト間で本人として呼ぶ方式を決めるときは、トークンの形とは別に、**IdP に誰が何を登録できるか**を管理対象に入れておきます。
</Callout>

## 方式 1: ID トークンを回す

いちばん手軽に見えるのは、docs がログインで受け取った ID トークンを、そのまま analytics と mailer に送る方式です。受け手は、`aud` が「信頼するログイン元のアプリの一覧」に入っていれば受け付けます。

```
IdP ──ID トークン（aud=docs-web）──▶ docs ──同じもの──▶ analytics ──同じもの──▶ mailer
                                              aud を一覧と照合          aud を一覧と照合
```

第 179 回で見たとおり、これは使わない前提で考えます。OIDC Core は ID トークンの `aud` を、**ログインした RP の `client_id`** と定めています（[Core 2](https://openid.net/specs/openid-connect-core-1_0.html#IDToken)）。Auth0 も、第三者のクライアントが API を呼ぶ委任の場面で ID トークンを API の呼び出しに使ってはならない、と書いています（[Auth0 Blog](https://auth0.com/blog/id-token-access-token-what-is-the-difference/)）。

困る点は 3 つです。

- **宛先が無い**。`aud` は「ログインしたアプリ」で、「このトークンを受け取ってよい API」ではありません。受け手は、許可するアプリを一覧で持つしかなく、一覧に載ったどのアプリのログインで得た ID トークンでも通ります
- **範囲が無い**。ID トークンにはスコープがありません。読み取りだけ任せる、ということをトークンで表せません
- **漏れたときの範囲が広い**。一覧を共有するすべてのプロダクトで、本人として使えます

それでも現場では、移行の途中の形としてこの方式が残っていることがあります。残すなら、受け手が署名、`iss`、`aud`（一覧）、`exp`、必須のクレームを必ず確かめていること、そして**この経路には委任の範囲が無い**と全員が知っていることが最低条件です。

## 方式 2: 共通の audience を持つアクセストークンを回す

次は、社内のプロダクト全体を IdP 上で**1 つの API** として登録し、その識別子を全員の `aud` にする方式です。最初のログインで、必要なスコープをまとめて要求し、得たアクセストークンを各プロダクトへそのまま渡します。

```
            audience=https://internal.example
            scope=docs.read analytics.read mailer.read
IdP ──アクセストークン──▶ docs ──同じもの──▶ analytics ──同じもの──▶ mailer
                                   aud と scope を検証          aud と scope を検証
                                   本人の権限も判定             本人の権限も判定
```

Auth0 はこの形を**論理 API**として説明しています。別々に実装された複数の API が論理的に 1 つの API の一部なら、Dashboard で 1 つの API として表し、認可の流れを 1 つにしたまま、スコープで個々の API への権限を分けられる、というものです（[Auth0: Configure Logical API for Multiple APIs](https://auth0.com/docs/get-started/apis/set-logical-api)）。「共通 audience」という名前の機能があるわけではなく、**同じ API の識別子を全員で使う**という設計です。

この方式で大事なのは、受け手が見る条件です。

- **トークンのスコープ**: この操作に対応するスコープがあるか。これは利用者が任せた範囲の**上限**です
- **本人の業務権限**: 中央の認可基盤やプロダクト自身のデータで、この利用者が、このオブジェクトに、この操作をしてよいか（第 182 回）

両方を満たしたときだけ許します。本人が管理者でも、`mailer.read` しか無いトークンでは送信できません。逆に、トークンに `mailer.send` があっても、本人に送信の権限が無ければ送れません。**ロールや権限をトークンに写して運ぶことはしません**。写した瞬間から、権限の変更がトークンの寿命の間は反映されなくなるからです。

**利点**は単純さです。呼ぶたびに IdP と通信せず、トークンはローカルで検証でき（第 181 回）、新しいプロダクトを足しても既存の受け手の `aud` の設定は変わりません。

**欠点**は、宛先を狭めないことそのものです。RFC 9700 は、アクセストークンの宛先を**特定のリソースサーバに、それが難しければ少数のリソースサーバに**限定すべき（SHOULD）としています（[RFC 9700 2.3](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.3)）。そして、宛先を限定するのは、取られたトークンを別のリソースサーバで使い回させないためだと書いています（[4.9.3](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.9.3)）。共通 audience は、この「少数のリソースサーバ」の最も広い解釈です。analytics のログや侵害されたサーバから漏れたトークンは、mailer でもそのまま使えます。Curity も、同じトークンを共有すると、連鎖の中のすべてのサービスが受け手と同じ権限を持つことになる、と整理しています（[Curity: Token Sharing Approaches](https://curity.io/resources/learn/token-sharing/)）。

だからこの方式は、**寿命を短くすることと、まとめて止める手段**（後で見る境界時刻）と組で使います。スコープで範囲を絞っても、漏れたトークンの使える場所は絞れません。

<Callout type="warn" title="よくある誤解: スコープで絞ったので、共通 audience でも安全">
  スコープが絞るのは「何をしてよいか」で、「どこで使えるか」ではありません。`mailer.read` だけのトークンでも、mailer を含むすべての受け手で、期限まで本人として読めます。
  また、利用者が最初にまとめて許したスコープは、どのプロダクトにも等しく見えます。analytics が受け取ったトークンには、analytics と関係のない `mailer.read` も載っています。
</Callout>

## 方式 3: 呼ぶたびに、宛先別のトークンへ交換する

宛先を狭めたまま連携するには、呼ぶ側が**次の宛先専用のトークン**を手に入れます。第 181 回のトークン交換（[RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html)）です。analytics は、自分宛てに届いた alice のトークンを認可サーバに出し、mailer 宛てのトークンに取り替えます。RFC 8693 自身が、リソースサーバがクライアントの役を担い、受け取ったアクセストークンを、後ろのサービスを呼ぶのにふさわしい新しいトークンに取り替える場面を例に挙げています（[1.1](https://www.rfc-editor.org/rfc/rfc8693.html#section-1.1)）。

```
IdP ─AT(aud=docs)─▶ docs ─交換→AT(aud=analytics, act=docs)─▶ analytics ─交換→AT(aud=mailer, act=analytics)─▶ mailer
```

交換を引き受けるのが IdP か、自分たちの発行基盤かで、2 つに分かれます。

### IdP の On-Behalf-Of で交換する

主な IdP は、この交換を製品の機能として持っています。名前も要求の形も少しずつ違います。

| IdP | 名前と要求の形 | 交換できる条件 | 出てくるトークン |
| --- | --- | --- | --- |
| Microsoft Entra ID | On-Behalf-Of。`grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer` と `requested_token_use=on_behalf_of`、`assertion` に受け取ったトークン | 機密クライアントであること。`assertion` の `aud` が交換を求めるアプリ自身であること。利用者の同意を事前に済ませておく | 委任のスコープだけを持つ下流 API 用のトークン。アプリのロールは引き継がない |
| Auth0 | On-Behalf-Of Token Exchange。RFC 8693 の `grant_type`、`audience` は必須 | 受け取る API と同じ識別子に結び付けた「Custom API client」だけが交換できる。下流 API への利用者委任の許可を登録する | `sub` は利用者のまま。`act` が入れ子で連鎖を記録（5 段まで）。`azp` は外側の `act.sub` と一致 |
| Okta | On-Behalf-Of Token Exchange。RFC 8693 の形 | カスタム認可サーバと、Token Exchange を有効にしたサービスアプリ。別の認可サーバが出したトークンなら、その発行元を信頼済みに登録 | `sub` は利用者、`act` は交換を求めたサービスアプリ（5 段まで）。リフレッシュトークンと ID トークンは出ない |
| Keycloak | 標準のトークン交換（V2）。RFC 8693 の形 | 機密クライアントで、交換を求めるクライアントが元のトークンの `aud` に入っていること。クライアントごとの設定で有効にする | 同じレルムのアクセストークン。ID トークンも要求できる。`audience` は宛先を絞るためのもので、増やすことはできない |

出典は、[Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-on-behalf-of-flow)、[Auth0](https://auth0.com/docs/secure/call-apis-on-users-behalf/on-behalf-of-token-exchange)、[Okta](https://developer.okta.com/docs/guides/set-up-token-exchange/main/)、[Keycloak](https://www.keycloak.org/securing-apps/token-exchange) のドキュメント（2026 年 10 月に確認）です。

並べると、共通点がはっきりします。

- **交換するのは、自分宛てに届いたアクセストークン**です。Entra ID は、`assertion` の `aud` が交換を求めるアプリでなければならず、別のアプリ宛てのトークンは使えないと明記しています。Keycloak も同じ条件です。第 189 回で、`resource` で取ったトークンの `aud` が URL で、交換を求めたクライアント ID と一致せずに断られたのは、この条件でした
- **交換する側は、自分の資格情報で認証します**。どの製品も公開クライアントには許していません。SPA が下流を呼びたいなら、秘密を持てる中間のサーバ（BFF、第 190 回の型 2）を置き、そこで交換します。Entra ID は SPA について、アクセストークンを中間の機密クライアントに渡して OBO をさせるよう書いています
- **利用者に、その場で同意を求められません**。中間のサーバは画面を持たないからです。Entra ID は事前の同意（管理者の同意や、`knownClientApplications` による一括の同意）を、Auth0 は同意の省略を前提にしています

違いも見ておきます。Keycloak の標準のトークン交換は、元のアクセストークンを失効させても、**交換で得たアクセストークンは失効しない**と明記しています（交換で得たリフレッシュトークンは連動して失効します）。Auth0 は、元のトークンが DPoP や mTLS で鍵に縛られていても、交換後は**縛られていないベアラトークン**を出すと書いています。どちらも、交換したから安全になる、とは言えない部分です。

### 自前の発行基盤で交換する

IdP に頼らず、社内に**トークンの発行基盤**（STS、Security Token Service）を置く選択もあります。各プロダクトは、利用者のトークンと自分の身元の証（mTLS の証明書やワークロードの ID トークン）を出し、次の宛先用のトークンを受け取ります。要求の形は RFC 8693 に揃えておけば、後から IdP の機能に置き換えるのも容易です。

IdP の通信量の上限や料金、機能の制約から自由になれる代わりに、次のことを自分たちで持ちます。

- **署名鍵**の保管とローテーション（第 186 回で見た、IdP を自分で持つことと同じ重さ）
- どのプロダクトが、どの宛先へ、どのスコープで交換してよいかの**方針**
- 発行の**停止**と、失効の連動
- 発行基盤そのものの**可用性**。止まれば、プロダクト間の呼び出しがすべて止まります

### 交換の利点と欠点

**利点**は、宛先が狭いことです。analytics 宛てのトークンが漏れても、mailer では通りません。`act` で「誰が代わりに動いているか」が残るので、mailer のログには「alice のために analytics が送った」と記録できます。

**欠点**は、呼び出しの経路に IdP（または発行基盤）が入ることです。

- 呼ぶたびに 1 往復の**遅延**が増えます。Curity も、交換には Token Service への追加の要求が要り、遅延が重要な場面では問題になりうると書いています（[Curity](https://curity.io/resources/learn/token-sharing/)）。実際は、宛先ごとに期限まで**キャッシュ**します。そのため交換後のトークンも、期限まで何度でも使える普通のベアラトークンです
- IdP の**通信量の上限**を、ログインやリフレッシュと分け合います
- 設定が増えます。受け手ごとの API の登録、交換するクライアント、交換の許可の組み合わせです
- 失効は自動では連動しません（上の Keycloak の例）
- 侵害されたプロダクトは、許された範囲で**下流への交換を求められます**。交換は、侵害そのものは止めません

<Callout type="note" title="IdP の OBO を、社内連携の毎回の呼び出しに使う例は多くない">
  公開されている大規模な構成の事例（後の方式 4 の Netflix など）は、IdP との往復を呼び出しのたびに入れる形より、入口で一度変換する形を多く採っています。
  ただし、これは事例を眺めた筆者の印象で、網羅的な調査に基づくものではありません。IdP の OBO は、下流が**別の会社の API**（Microsoft Graph など）で、その IdP のトークンでしか呼べない場面で、特に強い選択肢です。
</Callout>

## 方式 4: 入口で、内部用の短命な証に作り替える

方式 2 と 3 は、どちらも IdP のトークンを社内で回し続けます。発想を変えて、**外のトークンは入口で終わらせ、社内には内部専用の証を流す**こともできます。第 190 回の型 5 を、複数のプロダクトに広げた形です。

```
クライアント ─外のトークン─▶ 入口 ─内部の証（短命、入口の鍵で署名）─▶ docs ─同じ証─▶ analytics ─▶ mailer
                              │ 外のトークンを検証、またはイントロスペクション
                              └ 外のトークンは社内に入れない
```

代表的な例を 3 つ見ます。

**Phantom Token（Curity）**: クライアントには中身の無い参照トークンだけを渡し、リバースプロキシがイントロスペクションで JWT を得て、マイクロサービスへの要求の中で**参照トークンを JWT に置き換えます**（[Curity: The Phantom Token Approach](https://curity.io/resources/learn/phantom-token-pattern/)）。外からは中身が読めず、内側は JWT をローカルで検証できます。同じ社の Split Token は、イントロスペクションの往復も省くために、JWT の署名部分だけをクライアントに渡し、残りを入口でキャッシュから組み立てます（[Split Token](https://curity.io/resources/learn/split-token-pattern/)）。

**Passport（Netflix）**: 2021 年の Netflix の記事は、Cookie や独自のプロトコル、提携先のトークンなど、多種類のトークンを**各サービスが解析し、識別子を整合性の確認なしにヘッダや URL で回していた**状態を問題にしています。そこで、認証とプロトコルの終端を入口（Zuul）に集め、要求ごとに **Passport** という内部専用の身元の構造を作りました。Passport は要求の間だけ有効で、利用者と端末の身元を持ち、protobuf で表され、HMAC で改ざんを防ぎます。後ろのサービスは外のトークンを一切扱いません（[Netflix Tech Blog（Web Archive）](https://web.archive.org/web/20240101222642/https://netflixtechblog.com/edge-authentication-and-token-agnostic-identity-propagation-514e47e0b602)）。

**Transaction Tokens（IETF のドラフト）**: この形を標準にしようとしているのが Transaction Tokens です（[draft-ietf-oauth-transaction-tokens-11](https://datatracker.ietf.org/doc/draft-ietf-oauth-transaction-tokens/)、2026 年 7 月、まだ RFC ではありません）。入口は外のアクセストークンを、信頼ドメインに 1 つの **Transaction Token Service** に RFC 8693 で出し、Txn-Token を受け取って `Txn-Token` ヘッダで後ろへ回します。

- `aud` は**信頼ドメイン**を表し、その外で受け付けてはならない
- `txn` は呼び出しの連鎖全体の識別子、`req_wl` は Txn-Token を求めたワークロード
- `scope` は発行するサービスが決め、外のトークンのスコープと一致する必要はない。`tctx` には変えてはならない取引の内容（操作、銘柄、数量など）を入れられる
- 寿命は**数分以下**を想定し、使い回しへの耐性は無いので短く保つ
- Txn-Token の中に、外から届いたアクセストークンを入れてはならない。OAuth のアクセストークンとして使ってもならない

**利点**は、後ろのプロダクトが IdP を知らなくてよいことです。外のトークンの種類が増えても、入口だけが対応します。外のトークンを失効させれば（イントロスペクションが `active=false` を返せば）、次の要求から内部の証は作られません。内部の証は短命で、社内でしか通じないので、漏れたときの範囲も時間も狭くなります。

**欠点**は、入口が**単一の大きな信頼点**になることです。入口の署名鍵を持つ者は、誰の証でも作れます。そして、後ろのサービスが入口を迂回されない保証（第 190 回の型 5 で、ヘッダ 1 行で管理者になった実験）を、mTLS や署名で必ず持たなければなりません。また、プロダクトが別々の入口を持つ会社では、**入口をどう 1 つにまとめるか**という、技術より組織の問題が先に立ちます。

## 方式 5: 信頼ドメインをまたぐ

ここまでは、全員が同じ IdP を使っている前提でした。買収した会社のプロダクトや、提携先の API のように、**別の認可サーバが守る相手**を本人として呼ぶ場合もあります。これを扱うのが Identity Chaining のドラフトです（[draft-ietf-oauth-identity-chaining-17](https://datatracker.ietf.org/doc/draft-ietf-oauth-identity-chaining/)、2026 年 7 月。承認済みで RFC Editor の作業待ち、まだ RFC 番号はありません）。

1. ドメイン A のクライアントは、手元のトークンを A の認可サーバに出し（RFC 8693）、**B の認可サーバを `aud` にした JWT の認可グラント**を受け取る
2. それを B の認可サーバに `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`（RFC 7523）で出し、B のアクセストークンを受け取る

境界を越えるたびに同じ手順を繰り返します。B の認可サーバは A の鍵を信頼しておく必要があり、どちらの側でも、利用者の識別子を相手の形に写し替えたり（`johndoe@a.example` を `doe.john@b.example` に）、渡すクレームを減らしたりできます。途中の認可グラントもベアラトークンなので、寿命を短くし、1 回だけ使え、クライアントを認証する、という対策が挙げられています。

第 189 回の ID-JAG は、この上に「企業の IdP が、同意の代わりに方針で許す」形を載せたものでした。Transaction Tokens のドラフトも、信頼ドメインをまたぐ呼び出しには Identity Chaining を使うよう勧めています。

<Callout type="note" title="GNAP は、別の委任のプロトコル">
  OAuth 2.0 とは別に、委任の手順を一から設計し直した **GNAP** が 2024 年 10 月に RFC 9635 になりました。下流のリソースサーバを呼ぶためのトークンの導き方は、2025 年 4 月の RFC 9767 にあり、受け取ったアクセストークンを使い回すより、文脈に合わせたトークンに交換するほうが安全だとしています（[RFC 9767 6.6](https://www.rfc-editor.org/rfc/rfc9767.html#section-6.6)）。
  向いている考え方は RFC 8693 と同じです。主な IdP の製品はまだ OAuth の側にあるので、この回では名前を挙げるだけにします。
</Callout>

## どの方式とも重ねる部品

ここまでの方式は、どれも「利用者のトークンをどう運ぶか」の違いでした。次の 3 つは別の軸で、どの方式にも重ねられます。

**呼び出し元のサービスを確かめる**。受け手が「alice のために」だけでなく「analytics から」も確かめれば、漏れたトークンを社外のマシンから使われても止まります。mTLS とワークロードの ID（SPIFFE、クラウドのサービスアカウント、第 188 回）で確かめ、認可で両方を見ます（第 190 回の型 6）。SPIFFE は、ワークロードがその身元の文書を使って、TLS の接続や JWT の署名と検証で他のワークロードに自分を証明すると説明しています（[SPIFFE Overview](https://spiffe.io/docs/latest/spiffe-about/overview/)）。

**トークンを鍵に縛る**。DPoP や mTLS でトークンを持ち主の鍵に縛ると（第 181 回）、盗んだ者は鍵が無い限り使えません。RFC 9700 は、盗まれたり漏れたりしたアクセストークンの悪用を防ぐため、こうした仕組みを使うべき（SHOULD）としています（[2.2.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.2.1)）。ただし、プロダクトをまたいで**同じトークンを回す**方式 1、2 とは相性が悪い点に注意します。DPoP のトークンは最初に取得したクライアントの鍵に縛られるので、次のプロダクトはそれを使えません。縛るなら、各段で新しいトークンを得る方式 3 か 4 と組み合わせます。

**認可を中央で判定する**。どの方式でも、本人の権限はトークンに載せず、受け手がその場で判定します（第 182 回の PDP と、Zanzibar 系の基盤）。

<Callout type="note" title="クラウドの「交換」は、多くが利用者の委任ではない">
  クラウドにもトークンを交換する仕組みがありますが、ほとんどは**機械の身元**のためのものです。Google Cloud の STS（`sts.googleapis.com`）は外部のワークロードの身元をフェデレーションのトークンに換え、`generateAccessToken` はサービスアカウントのトークンを出します（第 188 回）。AWS の `AssumeRole` もロールのセッションで、ロールを連鎖させるとセッションは最長 1 時間に制限されます（[AWS STS AssumeRole](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html)）。
  利用者を運ぶものもあります。AWS IAM Identity Center の trusted identity propagation は、IAM ロールに利用者の身元の文脈を付け、それを他の AWS サービスへ伝えます（[AWS](https://docs.aws.amazon.com/singlesignon/latest/userguide/trustedidentitypropagation-overview.html)）。Google Workspace のドメイン全体の委任は逆に、**利用者の同意なし**で、組織の全員のデータへのアクセスを特権管理者がアプリに許す仕組みです（[Google Workspace 管理者ヘルプ](https://knowledge.workspace.google.com/admin/apps/control-api-access-with-domain-wide-delegation)）。名前が似ていても、何を委任しているかを確かめてから使います。
</Callout>

## 手元で確かめる: 4 つの方式を 1 つの模型で

方式 1〜4 を、Python と PyJWT で 1 つのプロセスの中に組み、どこで何が止まるかを確かめます。HTTP は省き、各プロダクトの**入口の検証**だけを関数で書きました。IdP の代わりに手元で作った P-256 の鍵でトークンに ES256 で署名し、受け手は `algorithms=["ES256"]`、`issuer`、`audience` を指定し、`exp`・`iat`・`sub`・`aud` を必須にして検証します。環境は Python 3.14.0、PyJWT 2.15.1、cryptography 50.0.2 です。

中央の認可基盤の代わりに、「alice は mailer で読み取りと送信ができる、bob は読み取りだけ」という表を置きます。mailer の入口は、**スコープ**（委任の上限）と**本人の権限**の両方を見ます。

```python
def mailer_send(claims, need_scope="mailer.send", perm="send"):
    scopes = set(claims.get("scope", "").split())
    if need_scope and need_scope not in scopes:
        raise Reject(f"scope に {need_scope} がない（持っている: ...）")
    if perm not in PERMS.get((claims["sub"], "mailer"), set()):
        raise Reject(f"{claims['sub']} に mailer の {perm} 権限がない")
    return f"{perm} OK（sub={claims['sub']}）"
```

まず方式 1 と 2 です。

```
== 方式 1: ID トークンを転送する ==
  ID トークン: {'aud': 'docs-web', 'sub': 'alice', 'azp': 'docs-web', ...}
  mailer: aud を mailer として検証             -> 拒否: InvalidAudienceError: Audience doesn't match
  mailer: aud を信頼するアプリ一覧で検証       -> send OK（sub=alice）
  別アプリ wiki-web の ID トークンでも         -> send OK（sub=alice）

== 方式 2: 共通 audience のアクセストークンを転送する ==
  アクセストークン: {'aud': 'https://internal.example', 'sub': 'alice', 'scope': 'docs.read mailer.read', ...}
  analytics が受ける                           -> alice
  mailer: 送信（alice は send 権限あり）       -> 拒否: scope に mailer.send がない（持っている: docs.read mailer.read）
  mailer: 読み取り                             -> read OK（sub=alice）
  bob: scope はあるが本人に send 権限なし      -> 拒否: bob に mailer の send 権限がない
  盗んだトークンで mailer を直接               -> read OK（sub=alice）
```

ID トークンは、`aud` を mailer として確かめると当然通りません。受け手が「信頼するアプリの一覧」で通すようにすると、**一覧のどのアプリのログインで得たものでも**本人として送信できました。スコープが無いので、mailer は送信まで任されたのかどうかを知る手段がありません。

共通 audience では、同じトークンが analytics と mailer の両方で通ります。alice は送信の権限を持っていますが、トークンに `mailer.send` が無いので送信は拒否されました。bob は逆に、スコープはあっても本人の権限で止まります。**2 つの条件が別々に効いている**ことが分かります。一方で最後の行のとおり、どこかで漏れたトークンは、スコープの範囲で mailer でもそのまま使えます。

次に方式 3 です。交換の窓口は、交換を求めるクライアントの資格情報、元のトークンが**そのクライアント宛て**であること、そのクライアントに許したスコープの範囲を確かめ、寿命 60 秒で `act` 付きのトークンを出します。

```
== 方式 3: 呼ぶたびに宛先別のトークンへ交換する ==
  analytics 宛て: {'aud': 'https://analytics.example', 'sub': 'alice', 'scope': 'analytics.read', ...}
  analytics 宛てを mailer に回す               -> 拒否: InvalidAudienceError: Audience doesn't match
  交換: 資格情報が違う                         -> 拒否: invalid_client
  交換: 許されていない scope                   -> 拒否: invalid_scope: mailer.admin
  交換後: {'aud': 'https://mailer.example', 'sub': 'alice', 'scope': 'mailer.send', 'act': {'sub': 'analytics-svc'}, ...}
  交換後のトークンで mailer に送信             -> send OK（sub=alice）
  交換後のトークンを analytics に戻す          -> 拒否: InvalidAudienceError: Audience doesn't match
```

analytics 宛てのトークンは mailer で通らず、交換で得た mailer 宛てのトークンは analytics で通りません。どこかで漏れても、使える場所は 1 か所です。`sub` は alice のままで、`act` に analytics が残っています。

方式 4 では、外を流れるのは乱数の参照だけにし、入口がそれを引いて、**入口の鍵**で寿命 30 秒の内部の証（`typ: txn+jwt`、呼び出しの識別子 `txn` 付き）に署名します。

```
== 方式 4: 入口で内部用の短命な証に作り替える ==
  外を流れるトークン: stZIMlBJ3MZpHp4er5CIAw （中身のない参照）
  内部の証: {'aud': 'internal', 'sub': 'alice', 'scope': 'mailer.send', ..., 'txn': '4bf9a89b'}
  mailer: 入口の鍵で検証                       -> send OK（sub=alice）
  mailer: IdP のアクセストークンを直接         -> 拒否: typ が txn+jwt ではない
  外のトークンを取り消した後の入口             -> 拒否: introspection: active=false
```

社内のプロダクトは入口の鍵しか信じないので、IdP が正しく署名したアクセストークンを直接送っても通りません。外のトークンを取り消すと、次の要求から内部の証は作られなくなります。

| 試したこと | 方式 1 | 方式 2 | 方式 3 | 方式 4 |
| --- | --- | --- | --- | --- |
| 別のプロダクトで漏れたトークンを mailer で使う | 通る | 通る（スコープの範囲） | 止まる（`aud`） | 止まる（外のトークンは中に入らない） |
| 本人が管理者でも、任されていない操作をする | 判定できない | 止まる（スコープ） | 止まる（交換の方針とスコープ） | 止まる（入口が決めたスコープ） |
| 権限の無い本人が、広いスコープで操作する | 止まる（本人の権限） | 止まる（本人の権限） | 止まる（本人の権限） | 止まる（本人の権限） |
| 呼ぶたびに IdP や入口と通信するか | しない | しない | する（キャッシュで減らす） | 入口で 1 回 |

この模型は、HTTP、mTLS、鍵の配布、キャッシュを省いています。示しているのは、**どの条件がどの攻撃を止めるか**の対応だけです。

## まとめて止める: 境界時刻での一括失効

どの方式でも、平時の主な対策はトークンの**寿命を短くする**ことです。自己完結型のトークンは、一度出すと取り消しにくいからです（第 176 回、第 181 回）。しかし、トークンを大量に盗まれたかもしれないと分かった時点では、期限切れを待てません。

そこで、環境全体に共通の**境界時刻 T** を 1 つ置き、各プロダクトの入口が「`iat` が T 以下のトークンを拒否する」という規則を持っておく方法があります。漏れた利用者を特定しなくても、T を「今」に上げれば、それ以前に出たトークンはすべて止まり、正規の利用者は取り直せば使えます。

模型でも T を 1 分前に上げてみました。ここで、交換と組み合わせたときの落とし穴が出ます。

```
== 緊急時: iat <= T を各入口で拒否する ==
  2 分前に発行された元のトークンを analytics で   -> 拒否: iat=1793344291 <= T=1793344351（一括失効）
  入力を確かめない交換で出たトークン: {'aud': 'https://mailer.example', ..., 'iat': 1793344401}
  そのトークンを mailer で                        -> send OK（sub=alice）
  入力を確かめる交換                              -> 拒否: iat=1793344291 <= T=1793344351（一括失効）
  T より後に取り直したトークン                    -> alice
```

古いトークンから交換したトークンには、**交換した時刻の新しい `iat`** が付きます。交換の窓口が入力のトークンに T を当てていなければ、止めたはずのトークンから、T をすり抜ける新しいトークンが生まれます。RFC 8693 も、交換の元と交換後のトークンの失効が連動することを定めていません。交換を使う構成では、**交換の窓口が入力にも T を当てる**こと、そして**入力が無効になったら、それに基づくキャッシュを使わない**ことまでを、一括失効の仕様に含めます。

T の運用で決めておくことは、次のとおりです。

- **時刻の単位と比較**: JWT の `iat` と同じ UTC の秒（NumericDate）で持ち、「以下」で拒否する。通常の時刻の検証で許す誤差（第 211 回）を、境界を緩める理由にしない。T は増やすだけで、戻さない
- **配り方**: 各プロダクトが短い間隔で取りに行く（Pull）、環境変数を変えて再デプロイする、通知して取りに来させる（Push と Pull の併用）。取りに行く間隔、HTTP のキャッシュの寿命、再試行の時間を足したものが、「T を上げてから全入口で拒否されるまで」の上限になる
- **取れなかったとき**: 最後に取れた T で受け付け続ける（可用性を優先し、停止の保証を諦める）か、一定時間取れなければ受け付けを止める（停止の保証を優先し、配る側の障害で全プロダクトが止まる）か。どちらを選ぶかを先に決めておく
- **先に経路を塞ぐ**: 漏れた経路や、侵害された発行元が残っていれば、T の後に作られた新しいトークンを使われる。T は漏れた分を止める手段で、漏れ続けるのを止める手段ではない

## 方式を切り替える順序

方式 1 から 2 へ、あるいは 2 から 3 へ移るとき、全プロダクトを同時に切り替えることはできません。順序は次のとおりです。

1. **受け手を両対応にする**。新しい方式のトークンを受け付ける経路を足す。このとき、**新しい経路ではスコープの検査を同時に入れる**。受け付けだけ先に足して検査を後回しにすると、その間は範囲の無い状態になる。古い経路と新しい経路で、検証の条件（`aud` に何を期待するか）を混ぜない
2. **送り手を順に切り替える**。ログイン、リフレッシュ、定期実行のジョブ、CLI、プロダクトの間の中継のすべてが対象。スコープが足りずに拒否されたとき、**古い方式で送り直さない**。受け手も、新しい方式で拒否したものを古い方式の扱いで通し直さない
3. **古い方式の受け付けを終える**。どの送り手がまだ古い経路を使っているかを記録で確かめ、終了日と担当者を決めて止める

併用している間は、**古い経路が残っている限り、新しい方式の保証は全体の保証ではありません**。「CLI には読み取りしか任せない」と新しい方式で決めても、その CLI が古い ID トークンの経路で呼べるなら、制限は迂回できます。移行の途中であることを、保証の説明に書いておきます。

## どれを選ぶか

| 方式 | 合うユースケース | 利点 | 欠点 |
| --- | --- | --- | --- |
| 1. ID トークンを回す | 新しく選ぶ理由は無い。移行の途中の形 | 設定が要らない | 宛先も範囲も無い。一覧のどのアプリのログインでも通る |
| 2. 共通 audience | 同じ会社が持つ少数のプロダクトで、まず委任の範囲を入れたい。CLI に一度のログインで複数のプロダクトを任せたい | 呼ぶたびの通信が無い。プロダクトを足しても受け手の `aud` は変わらない | 漏れたトークンは全プロダクトで使える。短命化と一括失効が必須 |
| 3a. IdP の OBO | 下流が別の会社の API や、その IdP のトークンでしか呼べない API。呼び出しの段数が少ない | 宛先が狭い。`act` で代理が残る。鍵を自分で持たない | 遅延、通信量の上限、設定の数。失効は連動しない |
| 3b. 自前の発行基盤 | プロダクトが多く、方針を細かく決めたい。IdP の制約を避けたい | 方針を自由に決められる。IdP を入れ替えやすい | 鍵、停止、可用性を自分で持つ |
| 4. 入口で作り替える | 入口を 1 つにまとめられる。外のトークンの種類が多い | 内部は IdP を知らずに済む。内部の証は短命で社内限定 | 入口が大きな信頼点。入口の迂回を必ず塞ぐ |
| 5. ドメインをまたぐ連鎖 | 別の認可サーバが守る相手（買収先、提携先） | 相手の認可サーバが、相手の方針で判断できる | まだドラフト。両側の信頼の設定 |

実際の構成は、1 つの方式だけでは終わりません。よく見るのは、**入口での作り替え（方式 4）か宛先の制限（方式 3）を軸に、mTLS とワークロードの ID で呼び出し元を確かめ、中央の認可基盤で本人の権限を判定する**組み合わせです。方式 2 から始める場合も、その欠点を補う短命化、一括失効、呼び出し元の確認を最初から組で入れ、宛先を絞る方式へ移れる形（受け手が `aud` とスコープを別々に検査する作り）にしておきます。

## どの部品と組み合わさっているか

## まとめ

- プロダクト間で本人として API を呼ぶときは、「誰のためか」「どこ宛てか」「何を任されたか、本人は何をしてよいか」「誰が呼んでいるか」を分けて考える。方式の違いは、主に「どこ宛てか」の扱いの違い
- 守る相手は 2 つある。正当なトークンの盗難と再利用、そして信頼すべきでない経路の本人情報が正当なトークンになること。後者は宛先を絞っても防げず、IdP の設定の管理で防ぐ
- 方式 1（ID トークンを回す）は宛先も範囲も無い。模型でも、一覧に載った別のアプリの ID トークンで送信できた
- 方式 2（共通 audience）は単純で、スコープと本人の権限の両方を見れば委任の範囲は表せる。しかし漏れたトークンはすべての受け手で使える。RFC 9700 の「少数のリソースサーバ」の最も広い形で、短命化と一括失効と組で使う
- 方式 3（宛先別の交換）は、IdP の OBO（Entra ID、Auth0、Okta、Keycloak）か自前の発行基盤で行う。どれも自分宛てのトークンだけを交換でき、交換する側は機密クライアントであることが要る。遅延、通信量の上限、設定、失効の非連動が代償
- 方式 4（入口での作り替え）は、Phantom Token、Netflix の Passport、Transaction Tokens のドラフト。内部は短命な社内限定の証だけを扱い、入口が大きな信頼点になる
- 方式 5（ドメインをまたぐ連鎖）は、Identity Chaining のドラフトで、交換と JWT の認可グラントを境界ごとに繰り返す
- 呼び出し元の確認、鍵への束縛、中央での認可は、どの方式にも重ねる。DPoP は同じトークンを回す方式とは組み合わせにくい
- 境界時刻 T で `iat <= T` を一括で拒否するときは、交換の窓口も入力に T を当てる。当てないと、古いトークンから新しい `iat` のトークンが生まれ、T をすり抜けた
- 移行は、受け手の両対応（検査も同時に）、送り手の切り替え（古い方式で送り直さない）、古い方式の受け付けの終了、の順で進める

次の第 192 回では、ここまでの型が実際に崩れた事例を見ます。署名鍵の範囲の検証が欠けていた、セッショントークンが思わぬ場所に残っていた、証明書の期限を誰も見ていなかった。どれも、部品同士の境目で起きた障害と事件です。
