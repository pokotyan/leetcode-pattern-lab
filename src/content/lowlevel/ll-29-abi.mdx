## ABI とは何か

**ABI**（Application Binary Interface）は、**コンパイル済みのコード同士が噛み合うための取り決め**です。

- 関数の引数をどこで渡すか
- 戻り値をどこに置くか
- どのレジスタを壊してよいか
- スタックをどう使うか
- 構造体をメモリ上にどう並べるか
- 名前をどう修飾するか

API がソースコードレベルの取り決めであるのに対し、ABI は**バイナリレベル**の取り決めです。

ABI が同じなら、**異なる言語・異なるコンパイラで作ったコードを繋げられます**。Rust から C の関数を呼べるのも、Python が C の拡張を読み込めるのも、ABI が共通だからです。

<Callout type="warn" title="ABI が変わると再コンパイルが必要">
  ライブラリの構造体にメンバを 1 つ足すだけで、サイズとオフセットが変わります。
  ヘッダを見ずにコンパイル済みのまま使っているコードは、間違った位置を読むようになります。
  共有ライブラリのバージョン番号（`libfoo.so.1` と `libfoo.so.2`）は、
  **ABI の互換性が壊れたかどうか**を表しています。
</Callout>

## x86-64 の呼び出し規約

Linux / macOS で使われる **System V AMD64 ABI** です。

**整数・ポインタの引数は、最初の 6 個をレジスタで渡します。**

| 引数 | レジスタ |
| --- | --- |
| 第 1 | `rdi` |
| 第 2 | `rsi` |
| 第 3 | `rdx` |
| 第 4 | `rcx` |
| 第 5 | `r8` |
| 第 6 | `r9` |
| 第 7 以降 | スタック（右から左へ積む） |

**浮動小数点は `xmm0`〜`xmm7`** で渡します。

**戻り値は `rax`**（128 ビットなら `rax` と `rdx`、浮動小数点は `xmm0`）。

<Callout type="note" title="Windows は違う">
  Microsoft x64 呼び出し規約では、整数引数は `rcx`, `rdx`, `r8`, `r9` の **4 個だけ**です。
  さらに、レジスタで渡す引数のぶんもスタックに場所を空けておく必要があります（shadow space）。

  **同じ CPU でも OS が違えば ABI が違う**、という典型例です。
</Callout>

## 誰がレジスタを守るか

関数を呼ぶと、呼ばれた側がレジスタを使います。呼び出し元の値が壊れては困ります。

そこで、レジスタを 2 種類に分けます。

| 種類 | 意味 | x86-64 での該当 |
| --- | --- | --- |
| **caller-saved**（volatile） | 呼び出しで壊れてよい。**必要なら呼ぶ側が退避する** | `rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`〜`r11` |
| **callee-saved**（non-volatile） | 呼び出しの前後で保たれる。**使うなら呼ばれた側が復元する** | `rbx`, `rbp`, `r12`〜`r15` |

両方あるのは、どちらか一方では無駄が出るからです。

- 全部 caller-saved にすると、呼ぶ側が毎回全部退避することになる
- 全部 callee-saved にすると、呼ばれた側が使わないものまで保存することになる

分けておけば、「短命な値は caller-saved に、長く保持する値は callee-saved に」とコンパイラが使い分けられます。

## スタックフレーム

関数 1 回分の呼び出しに対応するスタック上の領域を **スタックフレーム** と呼びます。

```
高いアドレス
   ┌────────────────────┐
   │  呼び出し元のフレーム   │
   ├────────────────────┤
   │  第 7 以降の引数      │
   ├────────────────────┤
   │  戻り先アドレス        │  ← call 命令が push した
   ├────────────────────┤
   │  保存された rbp       │  ← 呼ばれた側が push
   ├────────────────────┤  ← rbp がここを指す
   │  局所変数             │
   │  ...                 │
   ├────────────────────┤  ← rsp がここを指す
低いアドレス
```

典型的な関数の入口と出口です。

```asm
push rbp              ; 呼び出し元の rbp を保存
mov  rbp, rsp         ; 新しいフレームの基準を設定
sub  rsp, 32          ; 局所変数のぶん確保

...                   ; 本体。局所変数は [rbp-8] のように参照

leave                 ; mov rsp, rbp; pop rbp と同じ
ret                   ; 戻り先アドレスを pop して、そこへジャンプ
```

この入口と出口の定型部分を **プロローグ** と **エピローグ** と呼びます。

<Callout type="tip" title="フレームポインタの省略">
  `rbp` を使わず、`rsp` からの相対で局所変数を参照すれば、
  レジスタを 1 本節約でき、命令も減ります（`-fomit-frame-pointer`、`-O1` 以上で既定）。

  代償は、**スタックトレースが辿りにくくなる**ことです。
  `rbp` が連鎖していれば、それを辿るだけで呼び出し履歴が復元できますが、
  省略されているとデバッグ情報（`.eh_frame`）が必要になります。
  プロファイラが正しいスタックを出せないときは、
  `-fno-omit-frame-pointer` でビルドし直すと解決することがあります。
</Callout>

## call と ret

この 2 命令が、関数呼び出しの核心です。

```
call target
  1. 次の命令のアドレスをスタックに push する
  2. target にジャンプする

ret
  1. スタックから 1 つ pop する
  2. その値のアドレスにジャンプする
```

**戻り先アドレスはスタック上にあります。** これが重要な帰結を持ちます。

局所変数のバッファを越えて書き込むと、**戻り先アドレスを書き換えられます**。関数から戻る瞬間に、攻撃者が指定した場所へジャンプします。これがバッファオーバーラン攻撃の基本形で、第 22 回で見たスタックカナリアはこれを検出するためのものです。

<Callout type="note" title="リターンアドレス予測">
  CPU は `call` / `ret` の対応を専用のスタック（Return Stack Buffer）で追跡し、
  `ret` の飛び先を予測しています。
  **`call` と `ret` を対応させずに使うと、この予測が外れて遅くなります**。
  手書きアセンブリで「`ret` の代わりに `jmp`」のような技を使うと、
  意図せず性能を落とすことがあります。
</Callout>

## 末尾呼び出し

関数の最後で別の関数を呼んで、その結果をそのまま返す形を **末尾呼び出し** と呼びます。

```c
int f(int x) {
    return g(x + 1);      // g の結果をそのまま返す
}
```

このとき、`f` のフレームはもう不要です。`g` を呼ぶ前に `f` のフレームを畳み、`call` ではなく `jmp` で `g` に飛べば、**スタックが増えません**。

これが **末尾呼び出し最適化** です。再帰をループと同じコストにできます。

```c
int fact(int n, int acc) {
    if (n <= 1) return acc;
    return fact(n - 1, n * acc);    // 末尾呼び出し
}
```

この形なら、何百万回再帰してもスタックオーバーフローしません。

ただし、**C / C++ の規格は最適化を保証していません**。GCC / Clang は `-O2` 以上で適用しますが、確実ではありません。Scheme のように規格で保証している言語もあります。

## 構造体を渡すとき

引数が構造体の場合、ABI は細かい規則を定めています。

- **小さい構造体（16 バイト以下）**：レジスタに分割して渡す
- **大きい構造体**：メモリにコピーして、そのアドレスを渡す
- **大きい戻り値**：呼び出し元が領域を用意し、そのアドレスを隠れた第 1 引数として渡す（この場合、本来の第 1 引数は `rsi` にずれる）

この規則は複雑で、浮動小数点を含むかどうかでも変わります。手書きアセンブリで C の関数を呼ぶときに事故が起きやすい箇所です。

## 実際に見る

```c
int add(int a, int b) { return a + b; }
int main(void) { return add(3, 4); }
```

```bash
gcc -O0 -S -masm=intel foo.c -o -
```

`-O0` なら、`edi` と `esi` に引数が入り、`eax` に結果が入る様子がそのまま見えます。`-O2` にすると `add` がインライン化されて消えます。最適化前後を比べると、コンパイラが何をしているかが分かります。

## まとめ

- ABI はバイナリレベルの取り決め。異なる言語やコンパイラを繋ぐ土台
- x86-64（System V）では引数の最初の 6 個をレジスタで渡す。Windows は 4 個で別規約
- caller-saved と callee-saved の 2 種類があり、使い分けで無駄を減らす
- スタックフレームは呼び出し 1 回分の領域。プロローグとエピローグで組み立てる
- 戻り先アドレスがスタック上にあることが、バッファオーバーラン攻撃の土台になっている
- 末尾呼び出しは、フレームを畳んでから `jmp` すればスタックが増えない
