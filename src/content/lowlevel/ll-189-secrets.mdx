## 消したのに、まだある

設定ファイルにアクセスキーを書いてコミットしてしまい、気づいてすぐ次のコミットで消した。手元の最新のファイルを見ても、もうキーはありません。これで済んだでしょうか。

第 111 回では、秘密情報がリポジトリ、環境変数、ログ、例外から漏れることを並べ、いちばん効く対策は短命にすることだと書きました。第 140 回では、そもそも長期の秘密を配らない方法を見ました。この回はその間を埋めます。**長期の秘密がまだ残っている現実の環境で、それがどこを通ってどこに残るのか、機械はそれをどうやって見つけるのか、見つかったら何から手を付けるのか**です。

## 漏れる道 1: Git の履歴

### 消しても、前のコミットにある

3 つのコミットを作ります。2 つ目で秘密を書いた `config.py` を追加し、3 つ目で環境変数から読む形に書き換えます。

```bash
git commit -m "init"                    # app.py だけ
git commit -m "add config"              # config.py に秘密を直書き
git commit -m "read secrets from env"   # config.py を書き換えて秘密を消す
```

最新のコミットを検索しても、何も出ません。

```bash
git grep -n "AKIA" HEAD || echo "(no match in HEAD)"
# (no match in HEAD)
```

ところが、`git log -S` で「この文字列が増えたり減ったりしたコミット」を探すと、2 つ見つかります。足したコミットと、消したコミットです。

```
$ git log --oneline -S AKIAIOSFODNN7EXAMPLE
546794c read secrets from env
34d301e add config
```

足したほうのコミットを開けば、そのまま読めます。

```
$ git show 34d301e -- config.py
+AWS_ACCESS_KEY_ID = "AKIAIOSFODNN7EXAMPLE"
+AWS_SECRET_ACCESS_KEY = "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
+GITHUB_TOKEN = "ghp_LL177FAKEtokenForLearningOnly0······"
```

（GitHub のトークンの末尾 6 文字は、この記事では伏せています。理由は後の節で説明します。）

第 81 回で見たとおり、Git はファイルの中身をハッシュで名前を付けた blob として保存し、コミットは tree を通じてその blob を指しています。3 つ目のコミットは新しい blob を指すようになっただけで、**古い blob は 2 つ目のコミットから今も指されています**。

```
$ git cat-file -p 34d301e:config.py
AWS_ACCESS_KEY_ID = "AKIAIOSFODNN7EXAMPLE"
...
```

リポジトリを push していれば、この blob はリモートにも、それを clone したすべての手元にもあります。**「消すコミット」は、秘密を消すのではなく、秘密を消したという記録を 1 つ足すだけ**です。

### 履歴を書き換えても、配った写しは変わらない

履歴そのものから消すには、過去のコミットを作り直します。GitHub のドキュメントは、そのための道具として `git filter-repo`（2.47 以上）を勧めています（[GitHub Docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)）。消したい文字列を書いたファイルを渡して、全コミットの中身を置き換えます。

```bash
# repl.txt
AKIAIOSFODNN7EXAMPLE==>REMOVED
ghp_LL177FAKEtokenForLearningOnly0······==>REMOVED

git filter-repo --replace-text ../repl.txt --force
```

```
$ git log --oneline
4e1a07b read secrets from env
66873f3 add config
0dd7edf init

$ git show HEAD~1:config.py
AWS_ACCESS_KEY_ID = "REMOVED"
AWS_SECRET_ACCESS_KEY = "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
GITHUB_TOKEN = "REMOVED"
```

2 つのことが分かります。

1 つ目は、**秘密を含むコミットより後のハッシュがすべて変わった**ことです（`34d301e` → `66873f3`、`546794c` → `4e1a07b`）。コミットのハッシュは中身と親のハッシュから計算されるので、過去の 1 か所を変えると、その子孫は全部別のコミットになります。秘密を含まない `init` だけが同じままです。

2 つ目は、**シークレットアクセスキーが残っている**ことです。`repl.txt` に書き忘れたからです。置き換えは、渡した文字列にしか効きません。漏れた値を全部把握していなければ、書き換えても漏れは残ります。

そして、書き換える前に clone しておいた別の手元では、何も変わっていません。

```
$ git log --oneline -S AKIAIOSFODNN7EXAMPLE      # 書き換え前の clone で
546794c read secrets from env
34d301e add config
```

GitHub のドキュメントも、書き換えの副作用として、他の人の clone から秘密が戻ってくる危険、フォークに残り続けること、閉じた pull request の差分表示が失われること、ハッシュが変わって自動化が壊れることを挙げ、書き換えた後は GitHub のサポートにキャッシュの削除を依頼するよう書いています（[GitHub Docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)）。**公開された秘密を、履歴の書き換えで回収することはできません**。

## 漏れる道 2: イメージの層

第 164 回で、層は差分の積み重ねで、後の層で消したファイルは whiteout で見えなくなるだけだと見ました。第 166 回では、`ARG` と `ENV` の値が config の `history` に残ると書きました。ここでは、秘密がイメージのどこに、どの形で残るかを、1 枚ずつ開いて確かめます。

わざと 3 種類の悪い渡し方をした Dockerfile です。

```dockerfile
FROM alpine:3.22
ARG NPM_TOKEN
ENV API_KEY=ll177-fake-api-key-0123456789
COPY credentials /root/.aws/credentials
RUN echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > /root/.npmrc && echo "install deps here" && rm /root/.npmrc
RUN rm /root/.aws/credentials
CMD ["sh"]
```

```bash
docker build -t ll177-leaky --build-arg NPM_TOKEN=npm_LL177FAKEnpmTokenForLearning0000 .
```

BuildKit は、この時点で警告を出します。

```
2 warnings found (use docker --debug to expand):
 - SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for sensitive data (ARG "NPM_TOKEN") (line 2)
 - SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for sensitive data (ENV "API_KEY") (line 3)
```

この検査は、`ARG` や `ENV` に秘密を置くと最終的なイメージに残るので安全でない、という理由で出ます（[Docker Docs](https://docs.docker.com/reference/build-checks/secrets-used-in-arg-or-env/)）。変数の名前で判定しているだけなので、名前が秘密らしくなければ警告は出ません。

コンテナの中から見ると、ファイルは消えています。

```
$ docker run --rm ll177-leaky sh -c 'ls -a /root; ls -la /root/.aws/; echo API_KEY=$API_KEY'
.  ..  .aws
total 8
drwxr-xr-x    1 root     root          4096 Oct  7 06:07 .
drwx------    1 root     root          4096 Oct  7 06:07 ..
API_KEY=ll177-fake-api-key-0123456789
```

`.npmrc` も `credentials` もありません。`ENV` の値は、当然ながらそのまま見えます。では、イメージの外から見るとどうでしょうか。

### history に残る `ARG`

```
$ docker history --no-trunc --format '{{.CreatedBy}}' ll177-leaky
CMD ["sh"]
RUN |1 NPM_TOKEN=npm_LL177FAKEnpmTokenForLearning0000 /bin/sh -c rm /root/.aws/credentials # buildkit
RUN |1 NPM_TOKEN=npm_LL177FAKEnpmTokenForLearning0000 /bin/sh -c echo "//registry.npmjs.org/:_authToken=${NPM_TOKEN}" > /root/.npmrc && ...
COPY credentials /root/.aws/credentials # buildkit
ENV API_KEY=ll177-fake-api-key-0123456789
ARG NPM_TOKEN=npm_LL177FAKEnpmTokenForLearning0000
...
```

`.npmrc` は同じ `RUN` の中で作って消したので、ファイルとしてはどの層にも入っていません。しかし、**その `RUN` の時点の `ARG` の値が、コマンドの記録として config に書かれています**。`ARG` を宣言した後のすべての `RUN` に `|1 NPM_TOKEN=...` が付くので、値は 3 か所に現れます。

`docker save` でイメージを tar に書き出し、config の JSON を数えると、そのとおりでした。

```
$ grep -o 'NPM_TOKEN=[A-Za-z0-9_]*' blobs/sha256/86c50748... | sort | uniq -c
   3 NPM_TOKEN=npm_LL177FAKEnpmTokenForLearning0000
$ grep -o 'API_KEY=[a-z0-9-]*' blobs/sha256/86c50748... | sort | uniq -c
   2 API_KEY=ll177-fake-api-key-0123456789
```

`API_KEY` は、`history` と、コンテナを起動するときの環境変数を並べた `Config.Env` の 2 か所です。

### 層に残る `COPY`

`manifest.json` に並ぶ層を 1 枚ずつ開きます。

```
== layer 5e35486f   （COPY credentials）
drwx------  0 0  0    0  root/
drwxr-xr-x  0 0  0    0  root/.aws/
-rw-r--r--  0 0  0  116  root/.aws/credentials
== layer 4f4fb700   （.npmrc を作って消した RUN）
== layer 1c0fa86c   （RUN rm /root/.aws/credentials）
drwx------  0 0  0    0  root/
drwxr-xr-x  0 0  0    0  root/.aws/
----------  0 0  0    0  root/.aws/.wh.credentials
```

`rm` した層には、中身のない `.wh.credentials` が 1 つあるだけです。OCI の仕様では、whiteout は「そのパスを削除したことを表す、特別な名前の空のファイル」です（[OCI Image Spec](https://github.com/opencontainers/image-spec/blob/main/layer.md)）。削除は**上に印を重ねる**ことで表すので、下の層の中身はそのままです。

```
$ tar xOf blobs/sha256/5e35486f... root/.aws/credentials
[default]
aws_access_key_id = AKIAIOSFODNN7EXAMPLE
aws_secret_access_key = wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
```

`.npmrc` の層（`4f4fb700`）が空なのは、作成と削除が同じ層の中で打ち消し合ったからです。**同じ `RUN` で消せばファイルは層に残りません。しかし、値を `ARG` で渡していれば history に残ります**。ファイルと記録は、別々の漏れ道です。

### シークレットマウントで渡す

第 166 回で見たシークレットマウントに書き換えます。`env=` を付けると、ファイルではなく環境変数として、その `RUN` の間だけ見えます（[Docker Docs](https://docs.docker.com/build/building/secrets/)）。

```dockerfile
FROM alpine:3.22
RUN --mount=type=secret,id=npm_token,env=NPM_TOKEN \
    echo "token length: ${#NPM_TOKEN}" && echo "install deps here"
RUN --mount=type=secret,id=aws,target=/root/.aws/credentials \
    head -1 /root/.aws/credentials
CMD ["sh"]
```

```bash
NPM_TOKEN=npm_LL177FAKEnpmTokenForLearning0000 docker build \
  --secret id=npm_token,env=NPM_TOKEN --secret id=aws,src=credentials -t ll177-clean .
```

```
#5 8.783 token length: 36
#6 3.526 [default]

$ docker history --no-trunc --format '{{.CreatedBy}}' ll177-clean
CMD ["sh"]
RUN /bin/sh -c head -1 /root/.aws/credentials # buildkit
RUN /bin/sh -c echo "token length: ${#NPM_TOKEN}" && echo "install deps here" # buildkit

$ docker save ll177-clean | tar x -C s2 && grep -rl "LL177FAKE\|AKIAIOSFODNN7" s2 || echo "(no secret bytes in saved image)"
(no secret bytes in saved image)
```

ビルド中には値が使えていて（長さ 36、ファイルの 1 行目）、history にも書き出したイメージのどこにも値がありません。

<Callout type="warn" title="ビルドのログは別の漏れ道">
  上の例で `echo "$NPM_TOKEN"` と書けば、シークレットマウントでも値はビルドのログに出ます。
  マウントが守るのは**イメージに残らないこと**だけで、コマンドが値をどう扱うかまでは守りません。
  CI でビルドしていれば、そのログは次の節の問題になります。
</Callout>

## 漏れる道 3: CI のログ

CI は、秘密を受け取ってコマンドを動かし、その出力をすべて記録する場所です。GitHub Actions は、登録した秘密の値がログに現れると伏せ字にします。ただし、その仕組みには限界があります。

- 伏せ字は、**登録した値と完全に一致する文字列**を探して行う。秘密を JSON や YAML にまとめて 1 つの秘密として登録すると、一致しなくなって伏せられないことがある
- 秘密から作った別の値（秘密鍵で署名した JWT、Base64 にした値など）は、それ自体を秘密として登録しなければ伏せられない
- 値の変換の仕方は無数にあるので、**自動の伏せ字は保証されない**

いずれも GitHub のドキュメントに書かれています（[GitHub Docs](https://docs.github.com/en/actions/reference/security/secure-use)）。登録されていない値は `::add-mask::VALUE` で実行中に伏せ字の対象に加えられます。また、フォークからの pull request で動くワークフローには、`GITHUB_TOKEN` 以外の秘密は渡されません（[GitHub Docs](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions)）。

伏せ字は「うっかり表示したもの」を消すための仕組みで、**秘密を外へ送ろうとするコードは止めません**。`curl` で外部に送る、1 文字ずつ区切って出力する、といったことには無力です。CI で動く依存パッケージやアクションが書き換えられたときの話は、次の第 190 回で扱います。

## 漏れる道 4: クライアントに配るコード

ブラウザやスマートフォンのアプリに入れたものは、**利用者全員に配っている**ものです。難読化しても、配った以上は取り出せます。

ビルドの道具は、環境変数をコードに埋め込む仕組みを持っています。Vite は `VITE_` で始まる変数だけを、ビルド時にクライアントのコードへ埋め込みます（[Vite](https://vite.dev/guide/env-and-mode)）。`.env` に 2 つの値を置いて確かめます。

```bash
# .env
VITE_MAPS_KEY=ll177-fake-maps-key-AAAA
DB_PASSWORD=ll177-fake-db-pass-BBBB
```

```js
// main.js
console.log("maps", import.meta.env.VITE_MAPS_KEY)
console.log("db", import.meta.env.DB_PASSWORD)
```

```
$ npx vite build
dist/assets/index-CUsKLFQj.js  0.78 kB │ gzip: 0.44 kB

$ grep -o 'll177-fake-[a-z]*-[a-z]*-[A-Z]*' -r dist
dist/assets/index-CUsKLFQj.js:ll177-fake-maps-key-AAAA
```

出力された JavaScript の末尾はこうなっていました。

```js
console.log("maps","ll177-fake-maps-key-AAAA");console.log("db",void 0);
```

接頭辞のない `DB_PASSWORD` は `void 0`（undefined）に置き換えられ、漏れていません。接頭辞は**「これは配ってよい値だ」という宣言**で、Vite のドキュメントも `VITE_` の変数に API キーのような秘密を入れてはいけないと明記しています。地図の API キーのように、ブラウザから直接呼ぶ前提で配るキーは、秘密ではなく**公開してよい識別子**として扱い、使えるオリジンや API を提供者の側で絞ります。秘密が要る呼び出しは、サーバ側を経由させます。

## 機械はどうやって秘密を見分けるか

ここからは、漏れた秘密を**見つける**側の話です。検出の道具は、文字列を前にして「これは秘密か」を判定しなければなりません。手掛かりは 3 つあります。

### 手掛かり 1: 形（正規表現）

多くのサービスの秘密は、決まった形をしています。gitleaks の既定のルールでは、AWS のアクセスキー ID はこう書かれています（[gitleaks.toml](https://github.com/gitleaks/gitleaks/blob/v8.30.1/config/gitleaks.toml)）。

```toml
[[rules]]
id = "aws-access-token"
regex = '''\b((?:A3T[A-Z0-9]|AKIA|ASIA|ABIA|ACCA)[A-Z2-7]{16})\b'''
entropy = 3
keywords = ["a3t", "akia", "asia", "abia", "acca"]
[[rules.allowlists]]
regexes = ['''.+EXAMPLE$''']
```

AWS の ID は先頭 4 文字が種類を表します。`AKIA` は長期のアクセスキー、`ASIA` は STS が発行する一時的なアクセスキーです（[AWS IAM](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_identifiers.html)）。`keywords` は、正規表現を走らせる前の絞り込みです。この文字列を含まない行は最初から見ません。

一方、シークレットアクセスキーのほうは 40 文字の英数字と記号というだけで、目印がありません。形だけでは、ハッシュ値や Base64 のデータと区別がつきません。

### 手掛かり 2: でたらめさ（エントロピー）

そこで使うのが**シャノン・エントロピー**です。文字列に現れる文字の頻度から、1 文字あたり平均何ビットの情報があるかを計算します。同じ文字ばかりなら 0、使える文字が満遍なく現れるほど大きくなります。

```python
def H(s):
    n = len(s)
    return -sum(c/n * math.log2(c/n) for c in Counter(s).values())
```

```
H     長さ  文字列
4.66   40  wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
0.00   40  aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
3.42   41  correct-horse-battery-staple-correct-hors
3.72   40  546794c64bf8121c1225d01cedcf84cb15d305de
```

最後の行は、実験のリポジトリのコミットのハッシュです。16 進数は 16 種類の文字しか使わないので、どれだけでたらめでも 1 文字あたり 4 ビット（log2 16）を超えません。大文字・小文字・数字・記号を使う秘密のほうが高く出ます。

ただし、エントロピーは**目安でしかありません**。ハッシュ、UUID、圧縮されたデータ、Base64 にした画像も高く出ます。逆に、人が決めた弱いパスワードは低く出て、見逃されます。gitleaks は、正規表現に一致したものの中から、エントロピーが閾値（上の例では 3）に満たないものを捨てる、という使い方をしています（[gitleaks](https://github.com/gitleaks/gitleaks)）。

### 手掛かり 3: 接頭辞とチェックサム

いちばん確実なのは、**発行する側が、秘密を見分けやすい形にしておく**ことです。GitHub は 2021 年にトークンの形式を変えました（[GitHub Blog](https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/)）。

```
ghp_ LL177FAKEtokenForLearningOnly0 ······
└┬─┘ └──────────────┬─────────────┘ └─┬──┘
 │                  │                 └ チェックサム 6 文字（CRC32 を base62 で）
 │                  └ でたらめな部分 30 文字
 └ 接頭辞: gh + 種類の 1 文字 + _
```

| 接頭辞 | 種類 |
| --- | --- |
| `ghp_` | 個人用アクセストークン |
| `gho_` | OAuth のアクセストークン |
| `ghu_` | GitHub App がユーザとして使うトークン |
| `ghs_` | GitHub App がアプリとして使うトークン |
| `ghr_` | リフレッシュトークン |

同じ記事によると、区切りに `_` を選んだのは、Base64 で使わない文字なので、SHA のような機械が作るでたらめな文字列と偶然一致しないようにするためです。接頭辞だけで、secret scanning の誤検知は 0.5% まで下がる見込みだとしています。

さらに末尾の 6 文字は、32 ビットのチェックサムです。記事は CRC32 を使うことと、チェックサムが「オフラインでの誤検知をほぼなくす」ことを述べています。つまり、GitHub のデータベースに問い合わせなくても、**その文字列が GitHub が発行した形のトークンかどうかを、手元の計算だけでほぼ判定できる**ということです。

記事は具体的な計算手順までは書いていません。検出ツールの CredSweeper は、接頭辞の後ろから末尾 6 文字の手前までの 30 文字の CRC32 を計算し、末尾 6 文字を base62 として読んだ値と比べる、という形で実装しています（[CredSweeper](https://credsweeper.readthedocs.io/en/v1.9.2/_modules/credsweeper/filters/value_github_check.html)）。同じ手順を Python で書き、作ったトークンで確かめます。

```python
A = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz"

def b62(n):
    s = ""
    while n:
        n, r = divmod(n, 62)
        s = A[r] + s
    return s.rjust(6, "0")

def check(token):
    body, cs = token[4:-6], token[-6:]
    return b62(zlib.crc32(body.encode())) == cs
```

32 ビットの値は最大で約 43 億、base62 の 6 文字で表せるのは 62⁶ ≈ 568 億なので、6 文字で足ります。

`check` は、比べた結果と、本体から計算したチェックサムを返すようにしました。末尾を正しい 6 文字にしたものと、`000000` にしたものを比べます（計算したチェックサムは伏せています）。

```
$ python3 tok.py check ghp_LL177FAKEtokenForLearningOnly0······
(True, '······')
$ python3 tok.py check ghp_LL177FAKEtokenForLearningOnly0000000
(False, '······')
```

でたらめな 40 文字が偶然チェックサムまで合う確率は、およそ 2³² 分の 1 です。人が「それらしく」書いたダミーの値は、ほぼ確実にここで落ちます。

<Callout type="note" title="この記事でトークンの末尾を伏せている理由">
  チェックサムまで正しいトークンは、検出の仕組みから見れば**本物と区別がつきません**。
  この記事のリポジトリを公開の場に push すれば、プッシュ保護に止められたり、
  次の節のパートナープログラムで GitHub に「漏れたトークン」として届けられたりします。
  実在しないトークンなので害はありませんが、誤報を作らないよう、本文では末尾の 6 文字を伏せました。
  同じ理由で、テストのデータに「形式どおりのトークン」を置くときは、チェックサムをわざと外しておくのが安全です。
</Callout>

## gitleaks と TruffleHog

秘密を探す道具として、よく使われる 2 つを動かします。

### gitleaks

gitleaks は、Git の履歴（`git log -p` の出力）、ディレクトリ、標準入力を、上で見たような正規表現とエントロピーのルールで調べます（[gitleaks](https://github.com/gitleaks/gitleaks)）。最初の実験のリポジトリに当てます。

```
$ gitleaks dir .            # 今のファイルだけ
INF no leaks found

$ gitleaks git . --redact=60 -v      # 履歴全体
Finding:     GITHUB_TOKEN = "ghp_LL177FAKEtok...
RuleID:      github-pat
Entropy:     4.484184
File:        config.py
Line:        3
Commit:      34d301e7648c2082df4b1368e2074f644ab6ad40
INF 3 commits scanned.
WRN leaks found: 1
```

今のファイルだけを見ると何も出ず、履歴を見ると、秘密を入れたコミットが分かります。`--redact` は、見つけた値を出力の中で伏せる指定です。

AWS のキーが出てこないのは、ルールの許可リスト `.+EXAMPLE$` に当たったからです。ドキュメントの例をそのまま使ったコードで警告が鳴り続けないようにする、という判断です。**検出器のルールには、検出の条件と同じくらい、除外の条件が書かれています**。

GitHub のトークンの規則は `ghp_[0-9a-zA-Z]{36}` という正規表現とエントロピーだけで、チェックサムは見ていません。チェックサムを壊したトークンと、同じ文字の繰り返しのトークンを並べて確かめました。

```
valid  = "ghp_....（チェックサムが正しい）"   → 検出
badsum = "ghp_....（チェックサムだけ壊した）" → 検出
lowent = "ghp_aaaa...aaaa"                    → 検出されない（エントロピーが 0）
```

### TruffleHog

TruffleHog は、800 種類を超える秘密の形を見分ける検出器を持ち、見つけた値を**実際にそのサービスの API に送って、まだ使えるかを確かめる**ことができます。結果は、使えると確かめられた verified、確かめていないか使えなかった unverified、確認中にエラーが起きた unknown の 3 種類に分かれます（[TruffleHog](https://github.com/trufflesecurity/trufflehog)）。

この実験では、偽物とはいえ値を外部へ送らないよう、`--no-verification` を付けて確認を止めました。

```bash
docker run --rm -v "$PWD/cand:/cand" trufflesecurity/trufflehog:latest \
  filesystem /cand --no-verification --no-update --json
```

4 つの候補を置いたファイルに当てた結果です。

| 候補 | TruffleHog | gitleaks |
| --- | --- | --- |
| でたらめな 30 文字 + 正しいチェックサム | 検出 | 検出 |
| 同じ 30 文字 + 壊したチェックサム | 検出 | 検出 |
| `LL177FAKEtokenForLearningOnly0` + 正しいチェックサム | **検出されない** | 検出 |
| `ghp_aaaa...aaaa` | 検出されない | 検出されない |

TruffleHog の GitHub の検出器（v2）も、正規表現で拾うだけでチェックサムは計算していません（[github.go](https://github.com/trufflesecurity/trufflehog/blob/v3.99.0/pkg/detectors/github/v2/github.go)）。3 行目が落ちたのは、TruffleHog が確認なしの結果に対して、`example`、`aaaaaa`、`00000`、`sample` などの文字列や英単語の一覧を含むものを誤検知として捨てる処理を持っているからです（[falsepositives.go](https://github.com/trufflesecurity/trufflehog/blob/v3.99.0/pkg/detectors/falsepositives.go)）。`FAKE` や `Learning` のような単語を含む値は、人が書いたダミーだろうと判断されます。最初の実験のリポジトリに当てたときも、AWS の例の値と、この偽のトークンの両方が捨てられ、検出は 0 件でした。

2 つの道具の性格の違いは、誤検知の減らし方の違いです。

| | gitleaks | TruffleHog |
| --- | --- | --- |
| 主な判定 | 正規表現 + エントロピー + 許可リスト | 正規表現 + 誤検知の単語の除外 |
| 決め手 | ルールの書き方 | 実際に API に送って確かめる（verified） |
| 向いている場所 | コミット前のフック、CI での速い検査 | 見つかったものの優先順位付け（今も使えるものから） |

<Callout type="warn" title="verified の確認は、秘密を相手に送ることでもある">
  確認のために、見つけた値をそのサービスの API に送ります。
  社内のサービスや検証用の環境の秘密を誤った宛先に送ることはありませんが、
  **確認のアクセスは相手のログに残り**、使われたことの記録にもなります。
  どこで確認を有効にするかは、運用で決めておく必要があります。
</Callout>

## GitHub の側で止める、届ける

手元の道具は、入れた人の手元でしか働きません。リポジトリを預かる側で働く仕組みが、GitHub の secret scanning です。

**secret scanning** は、すべてのブランチの Git の履歴全体に加え、issue や pull request の本文とコメント、Discussions、Wiki も調べ、見つけたものをアラートにします。公開リポジトリでは無料で動き、非公開のリポジトリでは有料の機能を有効にする必要があります（[GitHub Docs](https://docs.github.com/en/code-security/secret-scanning/introduction/about-secret-scanning)）。

**プッシュ保護**は、その手前で止めます。秘密を含む push を、リポジトリに入る**前に**拒否します。コマンドラインからの push だけでなく、Web 画面でのコミット、ファイルのアップロード、REST API での書き込みも対象です（[GitHub Docs](https://docs.github.com/en/code-security/secret-scanning/introduction/about-push-protection)）。止められたら、理由（テストで使う、誤検知、後で直す）を選んで通すこともでき、その選択はアラートとして記録されます。個人のアカウントには、公開リポジトリへの push を止める保護が既定で有効になっています。

### パートナープログラムと自動失効

公開リポジトリで見つかった秘密は、さらに先へ進みます。**secret scanning のパートナープログラム**では、サービスの提供者が自分の秘密の形を表す正規表現と、通知を受ける URL を GitHub に登録します。GitHub は公開リポジトリと公開の npm パッケージを調べ、一致したものをその URL に送ります。受け取った提供者は、失効させたり利用者に知らせたりします（[GitHub Docs](https://docs.github.com/en/code-security/secret-scanning/secret-scanning-partnership-program/secret-scanning-partner-program)）。送られる要求には GitHub の署名（ECDSA）が付いていて、提供者は本当に GitHub から来たものかを検証できます。

```
開発者 ── push ──▶ 公開リポジトリ
                       │ secret scanning が一致を見つける
                       ▼
                    GitHub ── 署名付きの POST ──▶ 提供者（AWS、Slack、…）
                                                   │ その秘密を失効・隔離し、持ち主に知らせる
```

接頭辞とチェックサムの意味は、ここで効いてきます。**公開リポジトリ全体という大量の文字列に正規表現を当てても、誤報で提供者を埋めずに済む**からです。

何をするかは提供者次第です。AWS は、公開されたことが分かった IAM ユーザーのキーに `AWSCompromisedKeyQuarantineV3` という管理ポリシーを付けます。このポリシーは、インスタンスの起動、新しいアクセスキーの作成、S3 のオブジェクトの読み取り、Bedrock のモデルの呼び出しなど、不正な課金や被害の拡大につながる操作を拒否するもので、ポリシー自体の説明に「外さずに、作成されたサポートケースの指示に従うこと」と書かれています（[AWS](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AWSCompromisedKeyQuarantineV3.html)）。**キーを失効させるのではなく、一部の操作を止める隔離**です。一覧に入っていない操作はできたままなので、これで安心してよいわけではありません。

## 漏れた後にやること

順番がすべてです。

| 順 | すること | 理由 |
| --- | --- | --- |
| 1 | **失効させる**（または入れ替える） | 漏れた値を使えなくする。これだけが被害を止める |
| 2 | 使われていないかを調べる | 漏れてから失効までの間に、誰がその値で何をしたかを、提供者の監査ログで確かめる |
| 3 | 依存しているものを新しい値に切り替える | 失効させた値を使っていたアプリや CI を直す |
| 4 | 経路を塞ぐ | なぜ漏れたか（直書き、`ARG`、ログ）を直し、検出を手前に置く |
| 5 | 必要なら履歴を書き換える | 後始末。上で見たとおり、配った写しは消せない |

GitHub のドキュメントも、まず秘密を失効させるか再生成することを最初に置き、パスワードやトークンならそれで対応が終わることもある、としています（[GitHub Docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)）。

<Callout type="warn" title="よくある誤解: 非公開リポジトリだから、履歴から消せば大丈夫">
  非公開でも、clone した全員の手元、CI のキャッシュ、バックアップ、フォークに写しがあります。
  リポジトリに読み取り権限を持つ人やツールが 1 つでも乗っ取られれば、履歴ごと持ち出されます。
  **一度コミットした秘密は、漏れたものとして扱い、失効させます**。
  第 111 回で見たとおり、ローテーションの周期を待つのでも足りません。
</Callout>

2 番目の「使われていないか」を後から確かめられるかどうかは、提供者の側に記録が残っているかで決まります。いつ見つかり、いつ失効させ、その間に何が起きたかを記録することは、第 193 回で扱う証跡そのものです。

## そもそも置かない

ここまでの経路は、どれも「長期の秘密が、普通の文字列として存在している」ことが前提でした。

| 経路 | 置かずに済ませる方法 | 回 |
| --- | --- | --- |
| リポジトリ、設定ファイル | 秘密の管理サービスから実行時に読む | 第 111 回 |
| CI からクラウドへの認証 | CI の OIDC トークンを短命な認証情報に交換する | 第 140 回 |
| Pod からクラウドへの認証 | projected service account token、IRSA、EKS Pod Identity | 第 140 回 |
| DB のパスワード | 期限付きの認証情報をその場で発行する（Vault など） | 第 111 回 |
| イメージのビルド | シークレットマウント | 第 166 回、この回 |
| 署名の鍵 | Sigstore のキーレス署名 | 第 172 回 |

第 140 回で見たとおり、ワークロード ID は長期の秘密を**条件**に置き換えます。条件は Git に入れても漏れません。漏れても困らない形に変えることが、検出よりも先に来る対策です。検出は、それでも残る秘密のための網です。

次の第 190 回は、秘密を盗む側がもっと上流を狙う話です。依存パッケージの乗っ取り、ビルド環境の侵害、CI のアクションの書き換え。この回で見た CI の伏せ字が無力だった「秘密を外へ送ろうとするコード」は、多くの場合、そうした経路から入ってきます。作ったものが配られるまでの間に改ざんされていないことを、どう示すかを見ます。

## まとめ

- 消すコミットは秘密を消さない。古い blob は前のコミットから指され続け、`git log -S` や `git show` ですぐ読める
- `git filter-repo` で書き換えると後続のハッシュがすべて変わり、置き換えは指定した文字列にしか効かない。書き換える前の clone やフォークには残る
- イメージでは、`COPY` したファイルは前の層に、`ARG` の値は config の history に、`ENV` の値は history と `Config.Env` に残る。後の層の `rm` は whiteout を足すだけ。シークレットマウントなら、どこにも残らない
- CI のログの伏せ字は完全一致に頼るので、構造化した値や変換した値は漏れうる。外へ送るコードは止めない
- クライアントに埋め込んだ値は配ったのと同じ。`VITE_` のような接頭辞は「配ってよい」の宣言
- 検出の手掛かりは、形（正規表現）、でたらめさ（エントロピー）、接頭辞とチェックサム。GitHub のトークンは `ghp_` などの接頭辞と、末尾 6 文字の CRC32 を持ち、オフラインでほぼ確実に見分けられる
- gitleaks は正規表現・エントロピー・許可リスト、TruffleHog は誤検知の単語の除外と API での確認で誤検知を減らす。今回の版では、どちらも GitHub のトークンのチェックサムは見ていなかった
- secret scanning は履歴全体と issue などを調べ、プッシュ保護は入る前に止め、パートナープログラムは提供者に届けて失効や隔離につなげる
- 漏れたら、まず失効。履歴の書き換えは最後の後始末
- いちばん効くのは置かないこと。短命な認証情報とワークロード ID へ
