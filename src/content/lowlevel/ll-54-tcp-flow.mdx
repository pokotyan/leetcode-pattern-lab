## 誰がブレーキを踏むのか

TCP の送信側は、手元のデータを好きなだけ送り出せるわけではありません。ブレーキが 2 つあります。

| ブレーキ | 守っているもの | 窓の名前 | 誰が決めるか |
| --- | --- | --- | --- |
| **フロー制御** | 相手の受信バッファを溢れさせない | 受信ウィンドウ（rwnd） | 受信側が ACK に載せて知らせる |
| **輻輳制御** | 途中のルータを溢れさせない | 輻輳ウィンドウ（cwnd） | 送信側が推測する |

送信側は、**ACK をまだもらっていないデータの量を、2 つの窓の小さいほう以下に抑えます**。

```
送ってよい未確認データの量 = min(rwnd, cwnd)
おおよその速度           = min(rwnd, cwnd) / 往復時間（RTT）
```

この式が、この回のすべてです。窓が小さいか、往復時間が長いと、回線がいくら太くても速度は出ません。

## フロー制御: 相手が読まないと止まる

前回、`write` は送信バッファにコピーした時点で返ると書きました。では、相手のアプリケーションが `read` しなかったらどうなるか。手元で試してみます。受信側は `accept` したまま何も読まず、送信側はノンブロッキングで送れるだけ送ります。

```
相手が read しないまま送れた量: 2615232
```

約 2.6MB までは `send` が成功し、そこで `EAGAIN` になりました。このときの両側のソケットを `ss -tni` で見ると、データがどこに溜まっているかが分かります（抜粋）。

```
State  Recv-Q   Send-Q   Local            Peer
ESTAB  112960   0        127.0.0.1:9000   127.0.0.1:40462    ← 受信側
ESTAB  0        2582491  127.0.0.1:40462  127.0.0.1:9000     ← 送信側
        ... rwnd_limited:4ms(100.0%) ... notsent:2502272 ...
```

- 受信側の **Recv-Q** に約 110KB。届いたが `read` されていないデータ
- 送信側の **Send-Q** に約 2.5MB。そのうち `notsent` の 2.5MB は、まだ一度も送り出されていない
- `rwnd_limited:100%`。**送信が止まっていた時間の 100% が、受信ウィンドウのせい**

受信側のバッファが埋まると、受信側は ACK で「ウィンドウ 0」を知らせます。送信側はそれ以上送れなくなり、送信バッファが埋まり、最後にアプリケーションの `write` がブロックします。**遅い読み手の影響が、TCP を通って書き手まで逆流してくる**わけです。これを **背圧**（バックプレッシャ）と呼びます。

<Callout type="tip" title="背圧は壊れていない証拠">
  サーバが遅いクライアントに大きなレスポンスを返すと、`write` が詰まります。
  これはバグではなく、TCP が正しく働いている結果です。
  問題は、**詰まった `write` がスレッドを 1 本握ったまま待ち続ける**ことです。
  第 44 回のノンブロッキング I/O と第 45 回の多重化は、この待ちを他の仕事と重ねるための道具でした。
</Callout>

## 帯域遅延積: 回線を満たすのに必要な窓

回線をフルに使うには、**往復時間のあいだ送り続けられるだけの窓**が必要です。

```
必要な窓 = 帯域 × RTT（帯域遅延積）

例: 1 Gbps、RTT 100 ms（東京 ↔ 米国西海岸くらい）
    1,000,000,000 / 8 × 0.1 = 12.5 MB
```

窓が 12.5MB に届かなければ、ACK が戻ってくるのを待つ間、回線が遊びます。

TCP のヘッダでは、ウィンドウの欄は 16 ビットしかありません。そのままでは最大 64KB です。RTT 100ms で 64KB の窓なら、速度の上限は 64KB / 0.1 秒 ≈ **5 Mbps** です。1Gbps の回線を引いても 5Mbps しか出ない。

これを解決するのが **ウィンドウスケール** オプションです。ハンドシェイクのときに「ウィンドウの値を何ビット左にずらして読むか」を取り決めます。先ほどの `ss` の出力にあった `wscale:7,7` がそれで、2⁷ = 128 倍して読むという意味です。

Linux は受信バッファの大きさを、通信の状況に応じて自動で調整します（オートチューニング）。上限は `tcp_rmem` の 3 つ目の値です。

```bash
$ cat /proc/sys/net/ipv4/tcp_rmem
4096	131072	6291456        # 最小、初期値、最大（バイト）
```

最大が 6MB なので、先ほどの例の 12.5MB には届きません。**遠い拠点間の大きな転送が思ったほど速くないとき、最初に疑うのがこの値**です。

## 再送: 届かなかったら送り直す

パケットは失われます。TCP は、ACK が返ってこないデータを送り直します。問題は、**どれだけ待ってから送り直すか**です。

**タイムアウトによる再送（RTO）。** 送信側は RTT を測り続け、その平均とばらつきから待ち時間を決めます。短すぎれば無駄な再送になり、長すぎれば回復が遅れます。Linux の下限は 200 ミリ秒で、`ss` の出力の `rto:201` がそれです。

**高速再送。** タイムアウトを待たずに済む方法があります。受信側は、順番が飛んだデータを受け取ると、**最後に順番どおり受け取った位置**を ACK し続けます。同じ ACK が 3 回重ねて届いたら、送信側はその次のパケットが失われたと判断して、すぐに送り直します。

```
送信: 1  2  3  4  5  6
受信: 1  2  ×  4  5  6
ACK:  2  3  3  3  3        ← 「3 が欲しい」が 3 回重なった → 3 をすぐ再送
```

**SACK**（選択的確認応答）を使うと、「4〜6 は受け取った」と飛び飛びの範囲を伝えられるので、失われたものだけを正確に送り直せます。

## 輻輳制御: 途中の道の混み具合を推測する

受信側のバッファは ACK で教えてもらえますが、**途中のルータがどれだけ混んでいるかは、誰も教えてくれません**。送信側は、手がかりから推測するしかありません。

**スロースタート。** 接続の最初は、cwnd を小さく始めて、ACK が返ってくるたびに増やします。1 往復ごとにほぼ倍になるので、名前に反して増え方は指数的です。初期値は長らく 2〜4 セグメントでしたが、RFC 6928 で 10 セグメント（約 14KB）に引き上げる提案がなされ、現在の Linux の既定になっています（[RFC 6928](https://www.rfc-editor.org/rfc/rfc6928.html)）。`ss` の出力の `cwnd:10` がそれです。

**輻輳回避。** 一定の値（閾値）を超えたら、増やし方を緩めます。そしてパケットの損失を検出したら、「混んでいる」と判断して cwnd を大きく減らします。**少しずつ増やし、損失で大きく減らす**。これが古典的な Reno の振る舞いです。

```
cwnd
 │         ／＼          ／＼          ／＼
 │       ／    ＼      ／    ＼      ／    ＼      ← 損失のたびに半分に
 │     ／        ＼  ／        ＼  ／
 │   ／            ＼／          ＼／
 │ ／ ← スロースタート
 └──────────────────────────────────────── 時間
```

<Callout type="tip" title="短い接続はスロースタートで終わる">
  cwnd が 10 セグメント（約 14KB）から始まるなら、100KB のレスポンスを返すのに何往復もかかります。
  **多くの Web のレスポンスは、スロースタートを抜ける前に終わってしまいます。**
  接続の使い回しが効くもう 1 つの理由がこれで、育った cwnd を次のリクエストでも使えます。

  ただし Linux は、しばらく何も送らなかった接続の cwnd を初期値に戻します（`tcp_slow_start_after_idle`、既定で 1）。
  間欠的に大きなデータを送る接続では、これを 0 にすると効くことがあります。
</Callout>

## CUBIC と BBR

Reno は、RTT が長く帯域が大きい回線では、損失の後に cwnd を元に戻すのに時間がかかりすぎます。そこで改良が重ねられてきました。

**CUBIC** は、損失からの経過時間の 3 次関数で cwnd を決めます。直前に損失が起きた値の近くでは慎重に、そこから離れると大胆に増やします。Linux では 2.6.19（2006 年）から既定です（[Wikipedia](https://en.wikipedia.org/wiki/CUBIC_TCP)）。手元の Linux でもそうなっています。

```bash
$ cat /proc/sys/net/ipv4/tcp_congestion_control
cubic
```

Reno も CUBIC も、**損失を混雑の合図**として使います。しかし、途中のルータに大きなバッファがあると、損失が起きるのはバッファが満杯になってからです。それまでの間、パケットはバッファで待たされ、遅延が大きく膨らみます（**バッファブロート**）。

**BBR** は、損失ではなく **帯域と最小 RTT を測って** 送信の速さを決めます。「これ以上送っても届く速さが上がらず、RTT だけが伸びる」点を狙い、バッファを溜めずに回線を使い切ろうとします。Google が 2016 年に発表し、自社のバックボーンを CUBIC から BBR に切り替えています（[ACM Queue](https://queue.acm.org/detail.cfm?id=3022184)）。

| 方式 | 混雑の手がかり | 苦手な状況 |
| --- | --- | --- |
| Reno | 損失 | 長い RTT、大きな帯域 |
| CUBIC | 損失 | バッファの大きな経路で遅延が膨らむ |
| BBR | 帯域と RTT の測定 | 他の方式と帯域を分け合うときの公平性 |

輻輳制御は**送信側だけで完結する**ので、サーバ側で切り替えるだけで変えられます。受信側の協力は要りません。

## 40 ミリ秒の謎

小さなリクエストを送って応答を待つ処理が、なぜか毎回 40 ミリ秒ほど遅い。よく知られた落とし穴で、2 つの善意の仕組みが噛み合って起きます。

**Nagle のアルゴリズム**（送信側）: 小さなデータを 1 つずつ送るとヘッダの割合が大きくなるので、**未確認の小さなパケットがある間は、次の小さなデータを溜めておく**。

**遅延 ACK**（受信側）: ACK を 1 パケットごとに返すと数が多いので、**少し待って、返信のデータと一緒に ACK を送る**。Linux では待ち時間の目安が 40 ミリ秒で、`ss` の出力の `ato:40` がそれです。

```
送信側                                     受信側
 write(ヘッダ部分) ── 送信 ──────────────→  受け取る。ACK は待つ（遅延 ACK）
 write(本体部分)  → 未確認があるので溜める   リクエストが揃わないので返信できない
          ……… 互いに待つ ………
                   ←──────── 40 ms 後にようやく ACK
 溜めていた本体を送信 ─────────────────────→
```

送信側は ACK を待ち、受信側はデータを待ちます。デッドロックに似た状況が、遅延 ACK のタイマ切れで解けるまで続きます（[Marc Brooker](https://brooker.co.za/blog/2024/05/09/nagle.html)）。

対策は **`TCP_NODELAY`** で Nagle を無効にすることです。多くの HTTP クライアントや RPC のライブラリは、既定でこれを付けています。そのうえで、アプリケーション側で 1 回の `write` にまとめて渡すのが正攻法です。第 41 回で見た「システムコールの回数を減らす」とも一致します。

## 1 本のパイプの限界: HOL ブロッキング

TCP は **1 本のバイト列** です。途中の 1 パケットが失われると、それより後ろのデータは、届いていても**アプリケーションに渡されません**。順番を守る約束だからです。

HTTP/2 は、1 本の TCP 接続の上に複数のリクエストを多重化しました。接続の数は減りましたが、**1 つのパケットが失われると、無関係なリクエストまで全部止まります**。これを **HOL（head-of-line）ブロッキング**と呼びます。

これは TCP の約束そのものなので、TCP の上では直せません。そこで **QUIC** は、UDP の上に、ストリームごとに独立して順序を守るトランスポートを作り直しました。あるストリームの損失は、他のストリームを止めません。QUIC は 2021 年に RFC 9000 として、その上の HTTP/3 は 2022 年に RFC 9114 として標準化されています（[RFC 9000](https://datatracker.ietf.org/doc/html/rfc9000/)）。

<Callout type="note" title="なぜ TCP を直さずに UDP の上に作ったのか">
  TCP はカーネルの中に実装されています。
  新しい機能を入れても、世界中の OS と、途中にある無数の機器（NAT、ファイアウォール）が対応するまで使えません。
  途中の機器は、見慣れない TCP のオプションを落とすことすらあります。

  UDP の上に作れば、**実装はユーザ空間のライブラリ**になり、アプリケーションと一緒に更新できます。
  暗号化も前提にしているので、途中の機器がヘッダの中身を見て干渉することもできません。
  輻輳制御も、カーネルではなくライブラリの中で動きます。
  第 41 回で見た「カーネルとユーザ空間の境界」を、あえてユーザ空間の側に引き直した設計です。
</Callout>

## 自分の環境で見る

```bash
ss -tni                                   # 接続ごとの cwnd、rtt、rto、rwnd_limited など
cat /proc/sys/net/ipv4/tcp_congestion_control
sysctl net.ipv4.tcp_rmem net.ipv4.tcp_wmem
nstat -az | grep -i retrans               # 再送の回数
```

`ss -tni` の `rwnd_limited`（相手の受信ウィンドウで止まった割合）と `sndbuf_limited`（自分の送信バッファで止まった割合）を見ると、**遅いのが相手のせいか、自分のせいか、途中の道のせいか**の見当がつきます。

## まとめ

- 送れる量は min(受信ウィンドウ, 輻輳ウィンドウ)。速度はそれを RTT で割ったもの
- 相手が読まないと受信ウィンドウが 0 になり、送信バッファが埋まり、`write` が止まる（背圧）
- 回線を満たすには帯域遅延積ぶんの窓が要る。ウィンドウスケールとバッファの上限が効く
- 損失はタイムアウトか、重複 ACK による高速再送で回復する
- 輻輳制御は途中の混雑を推測する。Linux の既定は CUBIC、損失でなく測定に基づくのが BBR
- Nagle と遅延 ACK が噛み合うと 40 ms 待たされる。`TCP_NODELAY` と、まとめた `write` で避ける
- TCP は 1 本のバイト列なので HOL ブロッキングが避けられない。QUIC は UDP の上で作り直した
