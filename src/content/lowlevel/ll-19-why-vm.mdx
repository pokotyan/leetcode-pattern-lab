## 同じアドレスが表示される

2 つのプロセスで、同じプログラムを同時に実行してみます。ポインタの値を表示させると、**両方とも同じアドレスが出ます**。

```c
int global = 42;
printf("%p\n", (void*)&global);     // 2 つ同時に実行しても同じ値
```

同じ物理的な場所を共有しているなら、片方が書き換えればもう片方にも見えるはずです。しかし、そうはなりません。

答えは単純です。**プログラムが見ているアドレスは、実在の番地ではありません。**

## 変換を挟む

CPU が `0x1000` にアクセスしようとすると、その要求は **MMU**（Memory Management Unit）というハードウェアを通ります。MMU は変換表を引き、「プロセス A の `0x1000` は物理メモリの `0x8A3000`」のように読み替えます。

```
プロセス A の 0x1000   ──MMU──▶   物理 0x8A3000
プロセス B の 0x1000   ──MMU──▶   物理 0x2F1000
```

プログラムが使うアドレスを **仮想アドレス**、実際のメモリの番地を **物理アドレス** と呼びます。変換表はプロセスごとに別なので、同じ仮想アドレスが別の場所を指します。

<Callout type="note" title="ハードウェアがやっている">
  この変換は、**メモリアクセスのたびにハードウェアが自動的に行います**。
  OS がやっているのは変換表を用意することだけで、変換そのものには介在しません。
  介在していたら、メモリアクセス 1 回ごとに OS が呼ばれることになり、到底実用になりません。
</Callout>

## 何が解決されたのか

この仕組みは 4 つの問題を同時に解決します。

### 1. プロセス間の分離

プロセス A の変換表には、A に割り当てられた物理ページしか載っていません。A が書いたアドレスが B のメモリを指すことは、**原理的にありえません**。

これは「OS がチェックしている」のではなく、「変換表に載っていないものは指せない」という構造的な保証です。ソフトウェアのバグでは破れません。

### 2. 再配置の自由

仮想メモリがなければ、プログラムは「自分がメモリのどこに置かれるか」を知って作られる必要があります。2 つのプログラムが同じ番地を要求したら、片方はリンクし直しになります。

仮想アドレスなら、**どのプログラムも「自分は 0 番地から始まる」と思い込んで構いません**。物理的にどこに置かれるかは、OS が実行時に決めます。

### 3. 断片化の解消

物理メモリに 1MB の空きが 10 箇所に散らばっているとき、連続した 10MB の領域は確保できません。

しかし仮想メモリなら、**散らばった物理ページを、仮想アドレス空間では連続して見せられます**。プログラムから見れば 10MB の連続領域です。

```
仮想:  [ 0 ][ 1 ][ 2 ][ 3 ]     連続して見える
         ↓    ↓    ↓    ↓
物理:  [ 7 ][ 2 ][ 9 ][ 4 ]     実際はばらばら
```

### 4. 物理メモリより大きく見せられる

すべての仮想ページに物理ページを割り当てる必要はありません。**使われていないページは、割り当てないでおけます**。

アクセスされた瞬間に初めて割り当てる（デマンドページング）、ディスクに退避しておいて必要になったら戻す（スワップ）、といった運用ができます。

結果として、物理メモリが 16GB でも、各プロセスが 128TB の仮想アドレス空間を持てます。

## 権限もここで決まる

変換表の各エントリには、アドレスの対応だけでなく**権限**も記録されています。

| ビット | 意味 |
| --- | --- |
| Present | 物理メモリ上にあるか |
| Writable | 書き込んでよいか |
| User | ユーザモードからアクセスしてよいか |
| NX / XD | **実行を禁止する** |

これにより、次のことが実現されます。

- プログラムのコード領域を**読み取り専用**にする（自己書き換えを防ぐ）
- データ領域を**実行不可**にする（バッファに注入したコードが動かない）
- カーネル領域をユーザモードから見えなくする

<Callout type="tip" title="NX ビットの効果">
  スタックやヒープに機械語を書き込んで、そこにジャンプする攻撃は、
  かつて最も一般的な攻撃手法でした。
  NX ビット（実行禁止）の導入により、この直接的な手法は封じられました。

  攻撃側は、既存のコードの断片を繋ぎ合わせる手法（ROP）に移行しましたが、
  難易度は大きく上がりました。**変換表に 1 ビット追加しただけ**の効果です。
</Callout>

## 代償

仮想メモリはただではありません。

- **変換表を引く分、アクセスが遅くなる**。対策が TLB（次々回）
- 変換表そのものがメモリを消費する
- プロセス切り替えのたびに変換表を切り替え、TLB を捨てる必要がある
- ページフォールトの処理に OS の介入が必要

それでも、得られる分離と柔軟性のほうが圧倒的に大きいため、汎用 OS では例外なく使われています。

<Callout type="note" title="使っていない環境もある">
  小さな組み込みシステムやリアルタイム OS では、MMU を持たない、
  あるいは使わない構成があります。
  プロセス間の分離が要らず、**アクセス時間が常に一定である**ことのほうが重要だからです。
  ページフォールトはいつ発生するか分からず、その処理時間も一定でないため、
  厳密な応答時間が求められる用途では邪魔になります。
</Callout>

## まとめ

- プログラムが扱うのは仮想アドレス。MMU が物理アドレスに変換する
- 変換表はプロセスごとに別なので、同じ仮想アドレスが別の場所を指す
- 分離、再配置の自由、断片化の解消、物理メモリ以上の見せかけを同時に実現する
- 権限（読み / 書き / 実行）もエントリに記録され、ハードウェアが強制する
- 代償は変換のコスト。それを埋めるのが TLB
