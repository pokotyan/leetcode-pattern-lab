## プラグインという難問

アプリケーションに拡張の口を用意したい。ユーザが機能を足せるようにしたい。

従来の選択肢は、どれも困ったものでした。

| 方式 | 速度 | 安全性 | 言語 | 配布 |
| --- | --- | --- | --- | --- |
| **共有ライブラリを dlopen** | 最速 | **皆無** | C ABI を出せる言語 | **OS ごとにビルド** |
| **スクリプト言語を埋め込む**（Lua など） | 遅い | そこそこ | 1 つだけ | 楽 |
| **別プロセス + IPC** | 遅い | 高い | 何でも | 楽 |
| **設定ファイルの DSL** | — | 高い | — | 楽 |

`dlopen` 方式の問題は、第 1 回で見たとおりです。**プラグインのバグが、ホストプロセス全体を落とします**。サードパーティのコードを読み込むなら、なおさら受け入れがたい。

かといって別プロセスにすると、リクエストごとに IPC が発生します。プロキシのフィルタのように**1 リクエストあたり何回も呼ばれる**用途では成立しません。

**Wasm は、この表の空白を埋めます。**

| Wasm | 速い（ネイティブの 2〜5 倍） | **高い** | 何でも | **1 ファイルでどこでも** |

## 設計で決めること

Wasm プラグインを実装するとき、判断が要る箇所は 5 つです。

### 1. ホスト ABI をどう決めるか

プラグインとホストの間の取り決めです。3 つの水準があります。

| 水準 | 内容 | 例 |
| --- | --- | --- |
| **独自 ABI** | ptr + len を自分で決める。コンポーネントモデル以前の唯一の手 | proxy-wasm |
| **汎用フレームワーク** | 既製の規約とライブラリに乗る | Extism |
| **コンポーネントモデル** | WIT で型付きの world を定義する | Zed |

### 2. 何を渡すか

前回見たケイパビリティの設計です。**渡していないものは触れません。**

```
このプラグインに渡すもの:
  - リクエストのヘッダを読む関数
  - ヘッダを書き換える関数
  - ログを出す関数

渡さないもの:
  - ファイルシステム
  - ネットワーク
  - 時刻（決定性が要るなら）
```

**ホスト関数の設計は、システムコールの設計そのもの**です（第 7 章）。粒度が細かすぎれば呼び出し回数が増え、粗すぎれば柔軟性が失われます。

### 3. リソースをどう制限するか

| 制限 | 手段 |
| --- | --- |
| 実行時間 | **fuel**（命令数を数えて上限で止める）、またはエピック割り込み |
| メモリ | 線形メモリの上限ページ数 |
| スタック | 再帰の深さ |
| 呼び出し回数 | ホスト側で数える |

**これが従来の FFI にはなかったものです。** `.so` の中で無限ループされたら、ホストには止める手段がありません。

### 4. インスタンスの寿命

| 方式 | 起動コスト | 状態 | 向く用途 |
| --- | --- | --- | --- |
| リクエストごとに作る | 高い | 毎回まっさら | 安全性重視、マルチテナント |
| **プールして使い回す** | 低い | 前回の汚染に注意 | 高頻度の呼び出し |
| 1 つを常駐 | 最低 | 共有される | 単一テナント |

インスタンス化のコストは、モジュールのコンパイル（重い）と**インスタンス生成**（軽い）に分かれます。**モジュールは 1 回コンパイルして使い回し、インスタンスだけ都度作る**のが基本形です。

前回見た「線形メモリを `mmap` のコピーオンライトで共有する」手法は、この都度生成を安くするためのものでした。

### 5. 配布をどうするか

`.wasm` は 1 ファイルなので配布は楽ですが、**バージョンと署名**の問題は残ります。多くのプロジェクトが **OCI レジストリ**（Docker イメージと同じ仕組み）を流用しています。

## 実例

### Envoy / Istio — proxy-wasm

サービスメッシュのプロキシに、HTTP フィルタを Wasm で足せます。C++、Rust、AssemblyScript、TinyGo で書けます（[Envoy Gateway](https://gateway.envoyproxy.io/docs/tasks/extensibility/wasm/)）。

**コンポーネントモデル以前の設計**なので、**proxy-wasm という独自の ABI** を定義しています。

```
ホストが提供する関数:
  proxy_get_header_map_value(type, key_ptr, key_size, ...) -> status
  proxy_set_header_map_value(...)
  proxy_log(level, msg_ptr, msg_size)

プラグインが提供する関数:
  proxy_on_request_headers(context_id, num_headers) -> action
  proxy_on_response_body(...)
```

ポインタと長さを手で渡す形です。前回見た「面倒がそのまま残る」状態ですが、**2019 年時点ではこれしか選択肢がありませんでした**。

Istio では `WasmPlugin` というリソースで宣言的に適用します（[Istio Extensibility](https://istio.io/latest/docs/concepts/extensibility/)）。認証、レート制限、独自ヘッダの付与といった用途です。

<Callout type="note" title="なぜプロキシで Wasm が効くのか">
  Envoy は C++ で書かれた高性能プロキシです。機能を足すには、
  従来は**本体を fork してビルドし直す**必要がありました。

  Wasm なら、本体を触らずに、実行時に読み込めます。
  そして**フィルタが落ちてもプロキシは落ちません**。
  リクエストが 1 本失敗するだけで済みます。

  「全リクエストが通る場所」だからこそ、分離が効きます。
</Callout>

### Zed — エディタの拡張

Zed は、拡張を **wasmtime + コンポーネントモデル + WIT** で実装しています（[Life of a Zed Extension](https://zed.dev/blog/zed-decoded-extensions)）。

```
拡張が提供できるもの:
  - 言語サポート（Tree-sitter の文法、LSP サーバの起動方法）
  - テーマ / アイコンテーマ
  - デバッガ / MCP サーバの定義
```

拡張は Rust で `zed_extension_api` に対して書き、`wasm32-wasip1` にコンパイルします。WIT と `wit-bindgen` があるので、**文字列や構造体をそのまま扱えます**。前回見た glue の自動生成が効いている例です。

エディタにとって、この分離は切実です。**拡張がクラッシュしても本体は落ちず、再起動なしで読み込み直せます**。従来のネイティブプラグイン方式のエディタでは、拡張のバグがエディタごと落とし、書きかけの内容を失わせていました。

### Kubewarden — Kubernetes のポリシー

Kubernetes の admission リクエストを検証・変更するポリシーを、Wasm モジュールとして書きます（[policy-server](https://github.com/kubewarden/policy-server)）。ポリシーは **OCI レジストリで配布**されます。

```
ポリシー = 1 つの .wasm
  入力: admission リクエスト（JSON）
  出力: allow / deny / mutate
```

ポリシーエンジンとして Rego（OPA）のような専用言語を使う代わりに、**好きな言語で書ける**のが利点です。Go（TinyGo）、Rust、AssemblyScript、Swift などの SDK があります。

TinyGo が推奨されるのは、**標準の Go コンパイラより Wasm バイナリが小さくなる**ためです。ランタイムと GC を含めるかどうかの差で、これは前回見た「コンポーネントはバイナリが大きくなる」の具体例です。

### Redpanda — ストリームの変換

Kafka 互換のストリーミング基盤で、**データの変換処理を Wasm で書ける**ようになっています。トピックからトピックへ流れる途中で、ユーザのコードが走ります。

**データが通る経路にユーザのコードを挟む**という点で、Envoy と同じ構造です。落ちてはいけない場所に、他人のコードを入れる。

### Extism — 汎用のプラグインフレームワーク

「プラグイン機構を作りたい」という要求そのものを、フレームワークにしたものです。

- ホスト側の SDK が多数の言語にある（Go、Rust、Python、Node、JVM、C、Ruby、.NET…）
- プラグイン側の **PDK**（Plugin Development Kit）も同様
- 中身のランタイムは、Go なら wazero、JVM なら wasmtime、といった具合に差し替わる

**ホスト ABI を自分で決めなくてよい**のが利点です。入出力はバイト列（多くは JSON）で、host function の登録機構が用意されています。

コンポーネントモデルより素朴ですが、**今すぐ使えて、対応言語が多い**。導入のコストが低い選択肢です。

### wazero を採用しているプロジェクト

Go の世界では、**cgo を使わずに済む**ことが決定的な利点になります。

Trivy、dapr、k6、Cilium / Tetragon、Open Policy Agent などが wazero を組み込んでいます。いずれも「単一バイナリで配布したい」「クロスコンパイルを保ちたい」という要求を持つプロジェクトです。

<Callout type="tip" title="プラグインではない使い方：C ライブラリの置き換え">
  `ncruces/go-sqlite3` は、**SQLite の C ソースを Wasm にコンパイルし、wazero で動かす**
  ことで、cgo なしの SQLite ドライバを実現しています（[go-sqlite3](https://github.com/ncruces/go-sqlite3)）。

  Go で書き直す（transpile する）方式と違い、**本家の C コードをそのまま動かす**ので、
  挙動が完全に一致します。

  第 1 回で挙げた cgo の問題——C コンパイラが必要、クロスコンパイルが難しい、
  SIGSEGV でホストが落ちる——が、まとめて消えます。
  **プラグイン機構ではなく、FFI の置き換えとしての Wasm**という使い方です。
</Callout>

## 最小の実装

Go + wazero で、プラグイン機構の骨格を作るとこうなります。

```go
ctx := context.Background()

// 1. ランタイムを作り、リソース上限を決める
runtime := wazero.NewRuntimeWithConfig(ctx,
    wazero.NewRuntimeConfig().
        WithMemoryLimitPages(64).      // 64 × 64KiB = 4MiB まで
        WithCloseOnContextDone(true),  // context のキャンセルで止める
)
defer runtime.Close(ctx)

// 2. ホスト関数を登録する。ここに書いたものだけがプラグインから見える
_, err := runtime.NewHostModuleBuilder("host").
    NewFunctionBuilder().
    WithFunc(func(ctx context.Context, m api.Module, ptr, size uint32) {
        buf, _ := m.Memory().Read(ptr, size)
        log.Println("plugin:", string(buf))
    }).
    Export("log").
    Instantiate(ctx)

// 3. モジュールは 1 回だけコンパイルする（重い）
compiled, err := runtime.CompileModule(ctx, wasmBytes)

// 4. インスタンスは呼び出しごとに作る（軽い）
instance, err := runtime.InstantiateModule(ctx, compiled,
    wazero.NewModuleConfig().WithName(""))
defer instance.Close(ctx)

// 5. タイムアウトを付けて呼ぶ
ctx, cancel := context.WithTimeout(ctx, 100*time.Millisecond)
defer cancel()
results, err := instance.ExportedFunction("handle").Call(ctx, ptr, size)
```

**ホスト関数を登録する部分が、そのままケイパビリティの設計になっています。** `log` しか登録していないので、プラグインはログを出すこと以外に外へ働きかけられません。

<Callout type="warn" title="境界をまたぐ回数を減らす">
  この例では、文字列 1 つ渡すのに線形メモリへの書き込みが要ります。

  ループの中で 1 件ずつプラグインを呼ぶと、その都度コピーと変換が走ります。
  **まとめて渡して、まとめて返す**設計にするのが定石です。

  第 7 章の「システムコールの回数を減らす」、第 1 回の「cgo の呼び出しは細かくしない」と
  同じ話が、3 回目に出てきました。**境界は、またぐ回数がコストを決めます。**
</Callout>

## 落とし穴

### 決定性を壊すもの

複数のノードで同じプラグインを走らせて、同じ結果を期待する場合、**時刻・乱数・浮動小数点**が食い違いの原因になります。

Wasm は浮動小数点の挙動を厳密に規定しているので、そこは揃います。しかし、**ホストが時刻や乱数を渡せば、そこから非決定性が入ります**。渡さないという選択肢があることを意識しておく必要があります。

### 起動コストの実態

| 処理 | おおよそ |
| --- | --- |
| モジュールのコンパイル（JIT） | 数ミリ秒〜数百ミリ秒 |
| 事前コンパイル済みの読み込み | 数百マイクロ秒 |
| **インスタンス生成** | **数十マイクロ秒** |
| 関数呼び出し | 数百ナノ秒 |

**コンパイルは必ず 1 回にまとめます。** AOT コンパイル済みのバイナリをキャッシュしておくのが定石です。

### デバッグのしにくさ

プラグインの中で起きたことは、ホストからは見えにくい。スタックトレースが取りにくく、デバッガも限定的です。**第 1 回で見た「境界でスタックトレースが途切れる」問題は、Wasm でも残ります。**

ログを出す口をホスト関数として用意しておくことが、実質的な対処になります。

### バージョニング

ホスト ABI を変えると、既存のプラグインが動かなくなります。

- 独自 ABI：自分でバージョン番号を持つ
- **コンポーネントモデル**：WIT の package にバージョンが書ける（`example:greeter@1.0.0`）

**後者のほうが、機械的に検証できるぶん安全です。** 前回「境界が長期にわたって保たれる場面で効く」と書いたのは、このことです。

## 使わないほうがよい場合

- **信頼できる自分のコードだけを動かす**：サンドボックスの代償を払う理由がない
- **呼び出しが極端に細かい**：境界のコストが支配的になる
- **数値計算が本体**：ネイティブの 2〜5 倍は致命的なことがある
- **OS の機能を深く使う**：渡す口を用意する手間が大きすぎる
- **プラグインが 1 つだけ**：設定ファイルで足りるかもしれない

## まとめ

- Wasm は「速い / 安全 / 多言語 / 1 ファイル」を同時に満たす。従来の選択肢の空白を埋める
- 設計で決めるのは 5 つ：ホスト ABI、渡すもの、リソース制限、インスタンスの寿命、配布
- **ホスト関数の設計は、システムコールの設計と同じ**。渡したものだけが使える
- Envoy / Istio は独自 ABI（proxy-wasm）、Zed はコンポーネントモデル、Extism は汎用フレームワーク
- Kubewarden は OCI レジストリで配布、Redpanda はストリームの途中に挟む
- Go では cgo を避けられることが決定的。`go-sqlite3` は FFI の置き換えとしての例
- モジュールは 1 回コンパイルし、インスタンスだけ都度作る
- **境界はまたぐ回数がコストを決める**。3 度目に出てきた同じ話

ここまでで第 8 章は終わりです。FFI の面倒から始めて、Wasm がその答えになりつつある道筋を追いました。

次の章では、もう一段視点を広げます。電源を入れてから OS が立ち上がるまで、この章で見た分離の仕組みの親戚である仮想化とコンテナ、そして全体を実際に測るための道具です。
