## データベースが軽くなった後に残るもの

前回の第 275 回では、データベースを別の台へ移し、役割ごとに台を分けました。インデックス（第 266 回）、N+1 の解消（第 267 回）、往復の削減（第 268 回）、キャッシュ（第 269〜270 回）と合わせると、多くの場合、データベースの CPU 使用率は大きく下がります。すると `top` の上位には、アプリケーションのプロセスが残ります。

ISUCON11 予選の講評は、改善を進めた段階の状況を「計測ベンチマーカーを実行し計測を行うと、CPU が主なボトルネックということがわかります。」と書き、続けて「どのプロセスが CPU を使っているかを調べるには top コマンド等でリソース使用量の傾向を見つつ、言語別のプロファイリングツール (例. Go 言語の場合 pprof) を用いて行単位の CPU 時間を確認すると良いです。」と勧めています（[ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)）。

この回の問いは、**アプリケーションの CPU を使っているのは何か、そしてそれを減らす方法は何か**です。過去の ISUCON と参加記に繰り返し現れたものを並べると、次のようになります。

| 種類 | 例 | 主な対処 |
| --- | --- | --- |
| 意図的に重い計算 | パスワードのハッシュ（bcrypt） | 台を分ける、回数を減らす。軽くはしない |
| 毎回同じ答えになる計算 | 画像のハッシュ、URL の署名 | 書き込み時に計算して保存する、前もって表にする |
| データの変換 | JSON のエンコード・デコード、テンプレート | 速いライブラリ、変換の回数と量を減らす |
| プロセスの起動 | `zip` や管理コマンドを外部コマンドで呼ぶ | ライブラリで同じことをする |
| メモリ管理 | GC | 確保を減らす、`GOGC` と `GOMEMLIMIT` |
| 自分で入れたもの | デバッグ用の検査、大量のログ | 計測して、要らなくなったら外す |

以下、この順に、どれだけの CPU を使うのかを実測しながら見ていきます。

## 実測の環境と測り方

実測には Apple M1 Pro（macOS）、Go 1.24.6 を使いました。この記事を書いている間、同じマシンでは別の重い処理が並行して動いており、ロードアベレージは 40〜120 の間を行き来していました。このような状態では、経過時間（壁時計の時間）は待たされた時間を含んで大きくぶれます。実際、同じ処理を `go test -bench` で 3 回測ると、bcrypt のコスト 6 が 15.8〜27.2 ms とばらつき、コスト 8（18.0〜24.5 ms）と区別できないほどでした。

そこで、この回の表は**1 回あたりの CPU 時間**で示します。`getrusage(2)` でプロセスが使ったユーザー時間とシステム時間を処理の前後で取り、回数で割ったものです。`GOMAXPROCS=1` にして、ランタイムのほかの仕事が混ざりにくいようにしました。CPU 時間も、ほかのプロセスとキャッシュを取り合うぶん少し膨らみますが、2 回測った値の差は概ね 10% 以内に収まりました。

```go
func cpuTime() time.Duration {
	var ru, ch syscall.Rusage
	syscall.Getrusage(syscall.RUSAGE_SELF, &ru)
	syscall.Getrusage(syscall.RUSAGE_CHILDREN, &ch) // 外部コマンドのぶん
	return time.Duration(ru.Utime.Nano() + ru.Stime.Nano() + ch.Utime.Nano() + ch.Stime.Nano())
}
```

<Callout type="note" title="CPU 時間で比べることの意味">
  本番でも、混み合ったホストの上でレイテンシだけを見て「この変更で速くなった」と判断すると、ほかの負荷の変動を自分の変更の効果と取り違えます。
  第 241 回で見たとおり、CPU プロファイルも CPU 時間の内訳です。**変更の前後を比べるときは、1 リクエストあたりの CPU 時間か、同じ量の仕事に対するプロファイルで比べる**と、混雑の影響を受けにくくなります。
</Callout>

## パスワードのハッシュ：重いのは仕様

### bcrypt のコスト

パスワードを保存するときのハッシュ関数は、わざと遅く作られています。データベースが漏れたときに、総当たりで元のパスワードを探す作業を重くするためです。bcrypt では、コストと呼ばれる整数でその重さを決めます。コストを 1 上げると、内部の鍵の準備を繰り返す回数が 2 倍になります。

Go の `golang.org/x/crypto/bcrypt` は、最小を 4、既定を 10 としています（[bcrypt package](https://pkg.go.dev/golang.org/x/crypto/bcrypt)）。

```go
const (
	MinCost     int = 4  // the minimum allowable cost as passed in to GenerateFromPassword
	MaxCost     int = 31 // the maximum allowable cost as passed in to GenerateFromPassword
	DefaultCost int = 10 // the cost that will actually be set if a cost below MinCost is passed into GenerateFromPassword
)
```

コストごとに、正しいパスワードを照合する `CompareHashAndPassword` 1 回の CPU 時間を測りました。

```text
bcrypt cost=4                n=352       cpu/op=1.13ms
bcrypt cost=6                n=96        cpu/op=4.39ms
bcrypt cost=8                n=24        cpu/op=17.33ms
bcrypt cost=10               n=6         cpu/op=69.10ms
bcrypt cost=12               n=2         cpu/op=280.23ms
```

| コスト | 1 回の CPU 時間 | 1 コアで 1 秒に照合できる回数（目安） |
| --- | --- | --- |
| 4 | 1.13 ms | 約 880 |
| 6 | 4.39 ms | 約 230 |
| 8 | 17.33 ms | 約 58 |
| 10（既定） | 69.10 ms | 約 14 |
| 12 | 280.23 ms | 約 3.6 |

コストを 2 上げるごとに、ほぼ 4 倍になっています。既定のコスト 10 では、**1 回のログインで 70 ms 近い CPU を使い、1 コアは 1 秒に十数回しかログインを処理できません**。ほかのどのエンドポイントよりも桁違いに重い処理が、ログインの 1 か所に集まっているわけです。

### ISUCON で bcrypt がどう現れたか

ISUCON9 予選の講評は、ほかの改善を終えた後について次のように書いています（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。

> 上記の対策をしてくると、最後に残るのがログイン時のbcryptの処理です。

> bcryptの処理には0.1秒ほどかかり、CPUもかなり必要とします。

そのうえで、ログインを手抜きする対策には釘を刺しています。

> そこでCPU使用率をさげるため、sleepをいれて処理を遅らせるなどの対策でログインをさぼると、人気者出品の発動に必要な人数が集まらず、スコアが上がらなくなってしまいます。

講評が示した方向は、台を使うことでした。

> 今回の予選では3台までサーバインスタンスが利用可能でしたので、ログインが他のアプリケーションの動作に影響を与えないよう、サーバインスタンスを追加してログイン処理専用とする方法も考えられたでしょう。

ISUCON13 で 3 位だった ultra_fast_gopher の参加記も、やったことの一覧に「bcrypt を余裕のあるサーバーで実行」を挙げています（[ISUCON 13 で 3 位でした(ultra_fast_gopher)](https://blog.sakamo.dev/post/isucon13/)）。ISUCON12 本選の講評は、使っている関数の名前は挙げていませんが、「問題を解いてもらうとわかるのですが、ログインがボトルネックになるように設計されています。」と書いています（[ISUCON12 本選問題の解説と講評](https://isucon.net/archives/56959385.html)）。

### 2% のリクエストが CPU の 6 割を使う

1 回の重さが、全体の中でどう見えるのかを確かめます。2 つのエンドポイントを持つ小さなサーバを作りました。

- `/login`: コスト 10 の bcrypt で照合する
- `/list`: 20 人分のユーザー情報を JSON で返す。その際、ISUCON13 の参考実装と同じく、64 KiB のアイコンの SHA-256 を毎回計算する

同じプロセスの中から 4 つのクライアントで 10 秒間リクエストを送り、**50 回に 1 回だけログイン**させながら CPU プロファイルを取りました（`GOMAXPROCS=4`）。

```text
list=5894 login=123

      flat  flat%   sum%        cum   cum%
     5.63s 52.32% 52.32%      6.23s 57.90%  golang.org/x/crypto/blowfish.encryptBlock
     2.82s 26.21% 78.53%      2.82s 26.21%  syscall.syscall
     1.14s 10.59% 89.13%      1.14s 10.59%  crypto/internal/fips140/sha256.blockSHA2
     0.61s  5.67% 94.80%      0.61s  5.67%  runtime.asyncPreempt
     0.27s  2.51% 97.30%      6.51s 60.50%  golang.org/x/crypto/blowfish.ExpandKey
```

ハンドラごとの total（`-top -cum`）は次のとおりです。

```text
         0     0%     0%      6.53s 60.69%  main.login
         0     0% 81.04%      1.17s 10.87%  main.list
```

リクエストの 2% にすぎないログインが、CPU 時間の 61% を使っています。`blowfish.encryptBlock` は bcrypt の内部で使われる暗号の関数で、関数名に bcrypt と出てこないことにも注意が要ります。ボトムアップの表示で見慣れない関数が先頭に来たら、第 241 回の `-peek` で呼び出し元をたどります。`syscall.syscall` の 26% は、同じプロセスの中のクライアントとサーバが行うソケットの読み書きです。

この表は、第 263 回のアクセスログの集計とは違う順位を示します。アクセスログで合計時間を見ると、件数の多い `/list` が上位に来るかもしれません。しかし CPU を握っているのは件数の少ない `/login` です。**合計時間の大きいエンドポイントと、CPU を使っているエンドポイントは一致するとは限らない**ので、アプリケーションの CPU が飽和しているときは、プロファイルを併せて見ます。

### 本番での判断

本番では、**ハッシュのコストを下げて速くするのは選択肢になりません**。OWASP の Password Storage Cheat Sheet は、bcrypt について「For legacy systems using bcrypt, use a work factor of 10 or more and with a password limit of 72 bytes.」と書いています（[OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)）。新しく作るなら Argon2id を第一に勧めています。

取れる手は、重さを受け入れたうえで**置き場所と回数**を変えることです。

- **ログインを別の台や別のプロセスに分ける。** ISUCON9 予選の講評の方向です。本番では、認証だけを担うサービスを別に立て、ほかの API の応答時間がログインの集中に引きずられないようにします。
- **ログインの回数を減らす。** セッションの有効期間を適切に取り、トークンの更新でパスワードの照合を繰り返さないようにします。
- **総当たりを入り口で止める。** 同じアカウントや同じ送信元からの試行回数を制限します。攻撃者が CPU を使わせる手段として、ログインのエンドポイントが狙われるからです。

## 毎回同じ答えになる計算

### 画像のハッシュ

ISUCON13 の参考実装は、ユーザーの情報を返すたびに、アイコン画像の生データからハッシュを計算していました。講評は次のように書いています（[ISUCON13 問題の解説と講評](https://isucon.net/archives/58001272.html)）。

> fillUserResponse関数(Go言語の場合)でデータベースから画像の生データを受け取り、都度SHA256の計算を行なっているところを、こちらのカラムに変更することで負荷の削減と、次の作業がしやすくなります。

「こちらのカラム」とは、問題に用意されていた `icon_hash` の列のことです。アイコンを更新したときに 1 回だけ計算して列に保存すれば、読むたびに計算する必要はありません。講評は、キャッシュを使う場合の条件として「「iconが更新されてから2秒以内にicon_hashを反映すること」という条件がありますので合わせて確認しておきましょう。」とも書いています。保存したハッシュは、第 271 回で見た `ETag` と `304 Not Modified` の材料にもなります。

SHA-256 の CPU 時間を、入力の大きさごとに測りました。

```text
sha256 1KiB                  n=1277952   cpu/op=508.4ns
sha256 16KiB                 n=65536     cpu/op=7.61µs
sha256 128KiB                n=8192      cpu/op=59.50µs
sha256 1024KiB               n=1088      cpu/op=471.00µs
```

入力の大きさにほぼ比例し、1 MiB で約 0.5 ms です。1 回だけなら軽い処理ですが、**一覧 1 回で 50 人ぶんのユーザー情報を組み立て、そのたびに 1 MiB 近い画像のハッシュを計算すれば、それだけで 20 ms を超えます**。しかも、データベースから画像の生データを毎回読み出すコストがその前に付きます。

### URL の署名

2026 年 10 月 31 日の ISUCON2026 で優勝した Typing Bears（kawasy）の参加記には、同じ形の問題が出てきます（[ISUCON2026 で優勝しました（当日編）](https://zenn.dev/luvtechno/articles/isucon2026-competition-day)）。この問題の画像の URL には、持ち主の鍵で計算した署名と有効期限が付いていました。参加記は「リファレンス実装の署名は、HMAC を1000回繰り返す重い処理でした。」と書いています。

署名を 1 回の HMAC に減らそうとしたところ、ベンチマーカーが元の方式で署名を検証していたため、点数が 0 点になりました。署名の方式は変えられません。そこで、期限を固定した署名を前もって計算し、表にしておく方式に切り替えています。

HMAC-SHA256 を 1 回と 1000 回繰り返した場合、そして前もって計算した表を引く場合を測りました。

```text
hmac rounds=1                n=1179648   cpu/op=415.3ns    allocs/op=6
hmac rounds=1000             n=768       cpu/op=444.78µs   allocs/op=6000
lookup precomputed           n=67108864  cpu/op=7.3ns      allocs/op=0
```

1000 回の HMAC は約 0.44 ms です。画像の一覧が 1 ページに 30 枚あれば、それだけで 13 ms の CPU になります。表を引けば 7 ns で、6 万倍の差です。

<Callout type="tip" title="入力が変わらない計算は、書き込みの側へ移す">
  画像のハッシュも署名も、入力（画像、鍵、期限）が同じなら答えは同じです。**読むたびに計算しているものを、書き込むときに 1 回だけ計算するように移す**のは、第 273 回で見た事前計算の一種です。
  注意するのは、入力が変わったときに作り直すことと、作り直しの猶予（ISUCON13 の 2 秒など）です。署名のように期限を含むものは、期限をどの粒度で固定してよいかを仕様で確かめます。
</Callout>

## JSON の変換

Web アプリケーションは、ほとんどのレスポンスで JSON を作ります。データベースの負荷が下がると、JSON の変換がプロファイルの上位に出てくることがよくあります。

ISUCON11 本選で優勝した fujiwara組の参加記には、改善の一覧に「echo(フレームワーク) の JSONSerializer を自作して goccy/go-json 化」があります（[ISUCON11で優勝しました](https://sfujiwara.hatenablog.com/entry/isucon11-final)）。ISUCON13 の ultra_fast_gopher の一覧にも「JSONSerializer を早くする」があります。goccy/go-json は「Fast JSON encoder/decoder compatible with encoding/json for Go」を掲げるライブラリで、`encoding/json` と同じ関数の形で置き換えられます（[goccy/go-json](https://github.com/goccy/go-json)）。

ISUCON13 のライブコメントに似た構造体を 100 件並べた配列（JSON にして 31,371 バイト）で比べました。

```go
type Livecomment struct {
	ID        int64  `json:"id"`
	User      User   `json:"user"` // ID、名前、表示名、説明、テーマ、icon_hash
	Comment   string `json:"comment"`
	Tip       int64  `json:"tip"`
	CreatedAt int64  `json:"created_at"`
}
```

```text
marshal encoding/json        n=8192      cpu/op=56.63µs    allocs/op=2    bytes/op=32793
marshal goccy/go-json        n=12288     cpu/op=39.05µs    allocs/op=2    bytes/op=32793
unmarshal encoding/json      n=1920      cpu/op=298.36µs   allocs/op=517  bytes/op=56552
unmarshal goccy/go-json      n=22528     cpu/op=51.97µs    allocs/op=103  bytes/op=59165
```

| | encoding/json | goccy/go-json | 比 |
| --- | --- | --- | --- |
| エンコード（構造体 → JSON） | 56.63 µs | 39.05 µs | 約 1.5 倍 |
| デコード（JSON → 構造体） | 298.36 µs | 51.97 µs | 約 5.7 倍 |
| デコードのメモリ確保 | 517 回 | 103 回 | |

エンコードは 1.5 倍ほど、デコードは 5 倍以上速くなりました。デコードでは確保の回数も 5 分の 1 になっていて、後で見る GC の負担も減ります。

ただし、規模の感覚も持っておく必要があります。エンコードの差は 1 回あたり約 18 µs です。毎秒 1,000 回この一覧を返しても、節約できるのは 1 コアの 2% ほどです。**JSON のライブラリの交換は、プロファイルで JSON の変換が上位に見えてから行う**ものです。それより先に、返す件数を減らす（第 273 回のページング）、同じ JSON を何度も作らない（第 269〜270 回のキャッシュ）方が効くことが多いでしょう。

<Callout type="warn" title="置き換えの前に互換性を確かめる">
  互換をうたうライブラリでも、エラーの文言、不正な UTF-8 の扱い、`map` のキーの順序、数値の精度などの細部が標準と違うことがあります。ISUCON ではベンチマーカーの整合性検査、本番ではクライアントの解釈が違いを拾います。置き換えた後は、既存のテストとベンチマーカーを通して確かめます。
  Go 自身も JSON の実装を作り直していて、Go 1.25 のリリースノートは「Go 1.25 includes a new, experimental JSON implementation, which can be enabled by setting the environment variable GOEXPERIMENT=jsonv2 at build time.」と書いています（[Go 1.25 Release Notes](https://go.dev/doc/go1.25)）。外部のライブラリを選ぶ前に、標準の新しい実装を試す余地もあります。
</Callout>

## 外部コマンドの起動

アプリケーションの中から外部コマンドを起動すると、そのたびにプロセスの生成、プログラムの読み込み、終了の待ち合わせが起きます。第 24 回の `fork` と第 30 回のローダで見た、プロセスを作って動き出させるまでの費用です。

ISUCON11 本選では、課題のファイルをまとめてダウンロードする処理が `zip` コマンドを呼んでいました。講評は次のように書いています（[ISUCON11 本選問題の解説と講評](https://isucon.net/archives/56163308.html)）。

> 課題のダウンロードに関しては、zipコマンドではなく各言語のライブラリでzipを生成すると、プロセス起動・終了のオーバーヘッドを削減できます。

> 加えて、ある程度早くなるとzip生成時のdeflateがCPU使用率の上位に上がってきます。

> 帯域には余裕があるはずなので、圧縮レベルを下げることでCPU負荷を抑えられます。

fujiwara組の参加記にも「zip生成での外部コマンド呼び出しを archive/zip 化」があり、「10分で一発実装」できたことが書かれています。後半の 2 文は、**CPU と帯域の交換**です。圧縮は CPU を使って転送量を減らす処理なので、帯域に余裕があって CPU が足りないなら、圧縮をやめるか弱める方が得になります。

何もしない `true` コマンドを `exec.Command` で起動して終了を待つ費用と、同じプロセスの中の関数呼び出しを比べました（macOS 上。CPU 時間には子プロセスのぶんを含めています）。

```text
exec true                    n=256       cpu/op=2.64ms     wall/op=8.08ms
in-process func              n=771751936 cpu/op=2.4ns      wall/op=2.7ns
```

何もしないコマンドでも、起動と終了だけで 2.6 ms の CPU を使い、混雑したマシンの上では 8 ms 待たされました。1 回目の測定では CPU 時間 4.25 ms、経過時間 128 ms で、混雑の影響を強く受けています。外部コマンドは、処理の中身より先に**起動の固定費**がかかり、その固定費が混雑に弱いということです。

ISUCON13 の問題でも、ユーザーを登録するたびに PowerDNS の管理コマンドを外部コマンドとして呼んでいました。2 位だった織時屋の参加記には、この呼び出しに気づかず時間を使ったという記録があります（[ISUCON13で2位になりました(織時屋)](https://trap.jp/post/2049/)）。

## 自分で入れたものが重い

### 消し忘れた検査

ISUCON2026 の Typing Bears の参加記には、もう 1 つの例があります。nginx を外した後に初めて取ったプロファイルについて、「asia1 の CPU 時間の約86%を JPEG のデコードが占めていました。原因はエージェント自身が入れたデバッグモードでした。」と書かれています。

参考実装は、投稿された画像を `jpeg.Decode` で最後まで読んで、正しい JPEG かを確かめていました。書き直しのときにヘッダだけを読む `jpeg.DecodeConfig` に替えたのですが、結果が変わらないかを確かめるため、両方を実行して比べるデバッグモードを有効にしたままでした。このモードを切ると、点数は 388,921 から 483,958 に上がっています。この参加記は 1 人の参加者が AI のコーディングエージェントに作業させた記録で、デバッグモードを入れたのもエージェントですが、人が作業していても同じことは起こります。

1280×960 の画像（JPEG で 226,057 バイト）で、2 つの検査の費用を比べました。

```text
jpeg.Decode                  n=160       cpu/op=9.98ms     allocs/op=6   bytes/op=1857088
jpeg.DecodeConfig            n=458752    cpu/op=1.71µs     allocs/op=2   bytes/op=13616
```

`Decode` は 1 枚に約 10 ms の CPU と 1.8 MB のメモリを使い、`DecodeConfig` は 1.7 µs で済みます。約 5,800 倍の差です。**検証のために入れた処理が、検証したかった処理の 5,800 倍重い**ということが起こります。

ヘッダだけの検査は、ヘッダが正しく本体が壊れた画像を通してしまいます。参加記も、確かめたのは「ベンチマーカーが送ってきた範囲で結果が変わらないこと」までだったと断っています。軽くした検査が仕様として許されるかは、別に確かめる必要があります。

### ログの出しすぎ

ログの出力も CPU を使います。ISUCON11 予選の講評は次のように書いています。

> アプリケーション側のログ出力を止める上記の改善を入れて top を見ると、systemd-journal が CPU 使用率の上位に来るようになります。

アプリケーションが標準出力に書いたログを、systemd のジャーナルが受け取って保存する処理が、アプリケーションとは別のプロセスとして CPU を使っていたのです。**アプリケーションのプロファイルにだけ注目していると、この CPU は見えません**。`top` で全プロセスを見るのは、こうした「自分のプロセスの外に出た費用」を拾うためでもあります。

第 278 回で見るとおり、競技の終盤にはプロファイラやスロークエリログも止めます。計測の道具も、自分で入れた処理の一部です。

## GC

Go や Java のように GC を持つ言語では、メモリを確保した量に応じて GC が働きます。第 26 回で見た GC の仕組みのうち、Go の GC が使う CPU は、主に**生きているオブジェクトをたどる量**と**GC が起きる回数**で決まります。

Go の GC ガイドは、`GOGC` の役割を「At a high level, GOGC determines the trade-off between GC CPU and memory.」と説明しています（[A Guide to the Go Garbage Collector](https://go.dev/doc/gc-guide)）。`GOGC=100` なら、前回の GC の後に生き残ったヒープと同じ量の新しい確保があったところで、次の GC を始めます。値を大きくすると GC の回数が減る代わりに、ヒープが大きくなります。Go 1.19 からは、メモリの上限を `GOMEMLIMIT` で与えることもできます。

オンメモリキャッシュ（第 269 回）として、ポインタを含む 30 万件の構造体を常に持ったまま、200 件の構造体を作って JSON にする処理を 2 万回繰り返すプログラムで、`GOGC` を変えて比べました（`GOMAXPROCS=2`）。

```text
GOMEMLIMIT= GOGC=50 elapsed=5.578s cpu=9.107s gc=105 gcCPU=33.4% heapSys=83MB maxRSS=90MB
GOMEMLIMIT= GOGC=100 elapsed=3.907s cpu=5.33s gc=46 gcCPU=18.4% heapSys=131MB maxRSS=137MB
GOMEMLIMIT= GOGC=200 elapsed=3.029s cpu=3.821s gc=22 gcCPU=9.8% heapSys=215MB maxRSS=224MB
GOMEMLIMIT= GOGC=400 elapsed=2.919s cpu=3.222s gc=12 gcCPU=6.7% heapSys=339MB maxRSS=353MB
GOMEMLIMIT=1GiB GOGC=-1 elapsed=2.936s cpu=2.747s gc=3 gcCPU=1.4% heapSys=983MB maxRSS=1011MB
```

| 設定 | GC の回数 | 使った CPU 時間 | 最大 RSS |
| --- | --- | --- | --- |
| `GOGC=50` | 105 | 9.11 秒 | 90 MB |
| `GOGC=100`（既定） | 46 | 5.33 秒 | 137 MB |
| `GOGC=200` | 22 | 3.82 秒 | 224 MB |
| `GOGC=400` | 12 | 3.22 秒 | 353 MB |
| `GOGC=off` + `GOMEMLIMIT=1GiB` | 3 | 2.75 秒 | 1,011 MB |

（`gcCPU` は `runtime.MemStats.GCCPUFraction` で、キャッシュを作る段階を含むプログラム開始からの割合）

既定の `GOGC=100` から 400 にすると、同じ仕事に使う CPU 時間は 5.33 秒から 3.22 秒へ 4 割減り、メモリは 2.6 倍になりました。GC を止めて上限だけを与えると、上限に近づいたときにだけ GC が走り、CPU 時間はさらに減ります。**生きているデータが多いほど 1 回の GC が重くなるので、オンメモリキャッシュを持つアプリケーションほど、この設定が効きます。**

本番で `GOGC` を上げる、あるいは `GOMEMLIMIT` に頼るときは、メモリの上限との距離を見ておく必要があります。コンテナのメモリ上限に近い値を `GOMEMLIMIT` にすると、上限の付近で GC が頻発して CPU を食い続ける状態になりえます。設定を変えるより先に、確保そのものを減らす（スライスを使い回す、変換の途中の文字列を作らない、デコードの確保が少ないライブラリを選ぶ）のが本筋です。

## PGO

Go 1.21 からは、プロファイルを与えてビルドする PGO（Profile-Guided Optimization）が使えます。本番で取った CPU プロファイルを `default.pgo` という名前で main パッケージに置くと、`go build` が自動で読み込み、よく呼ばれる関数を積極的に展開（インライン化）したり、インターフェース越しの呼び出しを具体的な型の呼び出しに置き換えたり（脱仮想化）します。Go の文書は効果を次のように書いています（[Profile-guided optimization](https://go.dev/doc/pgo)）。

> As of Go 1.22, benchmarks for a representative set of Go programs show that building with PGO improves performance by around 2-14%.

HTML のエスケープなど 3 つのフィルタをインターフェース越しに順に呼ぶ処理で試しました。まずベンチマークを走らせて CPU プロファイルを取り、それを与えてもう一度ビルドします。

```bash
go test -c -o nopgo.test .
./nopgo.test -test.bench Render -test.cpuprofile default.pgo
go test -c -pgo=default.pgo -o pgo.test .
```

コンパイラの判断を `-gcflags=-m` で出すと、PGO を与えたときにだけ次の行が現れました。

```text
./pgo_test.go:67:15: PGO devirtualizing interface call f.Apply to escape.Apply
./pgo_test.go:63:6: can inline render
./pgo_test.go:67:15: inlining call to escape.Apply
```

プロファイルの上で最もよく呼ばれていた `escape.Apply` について、「型が `escape` なら直接呼ぶ」という分岐を入れ、さらに展開しています。

効果を、同じ 1,500 回の処理に使ったプロセスの CPU 時間（`/usr/bin/time` の user と sys の和）で比べました。2 つのバイナリを交互に 6 回ずつ走らせています。マシンの混雑が比較的落ち着いていた時間帯（ロードアベレージ 17 前後）の結果です。

| 回 | PGO なし | PGO あり |
| --- | --- | --- |
| 1 | 1.48 秒 | 1.46 秒 |
| 2 | 1.45 秒 | 1.45 秒 |
| 3 | 1.47 秒 | 1.61 秒 |
| 4 | 1.60 秒 | 1.49 秒 |
| 5 | 1.52 秒 | 1.59 秒 |
| 6 | 1.74 秒 | 1.48 秒 |

最小値はどちらも 1.45 秒で、差は測定のばらつきに埋もれました。コンパイラは確かに脱仮想化と展開を行いましたが、この処理の時間のほとんどは `escape.Apply` の中の 1 文字ずつのループで使われていて、呼び出しそのものの費用はもともと小さかったからです。PGO が効くのは、小さな関数を大量に呼ぶ処理で、呼び出しの費用や展開による最適化の余地が全体の中で目に見える割合を占めている場合です。

PGO は、コードを書き換えずに数パーセントを得る手段です。ただし、プロファイルが本番の負荷を代表していないと効果は出ませんし、ISUCON の数時間の中で点数を何倍にもするのは、ここまでに見たような「重い処理をやめる」「回数を減らす」変更の方です。**PGO は、アルゴリズムと呼び出し回数の改善を終えた後に、残りを少しずつ削る道具**と位置づけるのがよいでしょう。

## どこから手を付けるか

ここまでの実測を、1 回あたりの CPU 時間で並べ直します。

| 処理 | 1 回の CPU 時間 |
| --- | --- |
| bcrypt の照合（コスト 10） | 69.10 ms |
| JPEG を最後までデコード（1280×960） | 9.98 ms |
| 外部コマンドの起動と終了 | 2.64 ms |
| SHA-256（1 MiB） | 471.00 µs |
| HMAC-SHA256 を 1000 回 | 444.78 µs |
| JSON のデコード（31 KB、encoding/json） | 298.36 µs |
| JSON のエンコード（31 KB、encoding/json） | 56.63 µs |
| 前もって計算した表を引く | 7.3 ns |

上の方ほど、1 回でほかの処理を何百回ぶんも上回ります。アプリケーションの CPU を減らす順序は、おおむね次のとおりです。

1. **プロファイルを取る。** 第 241 回と第 265 回の方法で、ボトムアップの表示から self の大きい関数を探します。`top` でアプリケーション以外のプロセス（ジャーナル、圧縮、外部コマンド）も見ます。
2. **やめられるものをやめる。** デバッグ用の検査、出しすぎたログ、外部コマンドの起動。
3. **毎回同じ答えになる計算を、書き込み時か起動時に移す。** ハッシュ、署名、変わらないデータの JSON。
4. **重さが仕様の処理は、置き場所を変える。** パスワードのハッシュは軽くせず、台やプロセスを分けて、ほかの処理を巻き込まないようにします。
5. **変換と確保を減らす。** 返す量を減らし、速いライブラリに替え、GC の設定を見直します。
6. **最後に PGO。**

## 次の回へ

アプリケーションの CPU まで削ると、残るのは「ベンチマーカーや利用者が、どれだけの負荷をどの間隔でかけてくるか」という、仕様の側の問題です。次の第 277 回では、負荷の強さを決めるパラメータ、ポーリングの間隔、アルゴリズムの改善の費用対効果を、仕様に合わせて詰める方法を見ます。

## まとめ

- データベースの負荷を下げると、次にアプリケーションの CPU が上位に出る。`top` で全プロセスを見て、言語のプロファイラで関数の内訳を見る
- 混雑したマシンでは経過時間がぶれる。変更の前後は、1 回あたりの CPU 時間か、同じ量の仕事のプロファイルで比べる
- bcrypt はコストを 2 上げるごとに約 4 倍重くなり、既定のコスト 10 では照合 1 回に約 70 ms の CPU を使った
- パスワードのハッシュは軽くしない。ISUCON9 予選の講評が示したように、ログインを別の台に分け、回数と試行を制限する
- 画像のハッシュや URL の署名のように入力が変わらない計算は、書き込み時に計算して保存するか、前もって表にする。1000 回の HMAC と表の参照は 6 万倍違った
- JSON のライブラリを替えると、エンコードで 1.5 倍、デコードで 5.7 倍速くなった。ただし効くのは JSON の変換がプロファイルの上位にあるときだけで、互換性の確認が要る
- 外部コマンドは、何もしなくても起動と終了で数 ms かかる。ライブラリで同じことをし、圧縮は CPU と帯域の交換として判断する
- 検証のために入れた処理や大量のログが、本来の処理より重くなることがある。JPEG の全体デコードはヘッダの読み取りの約 5,800 倍だった
- GC の CPU は生きているデータの量と GC の回数で決まる。`GOGC` を 100 から 400 にすると CPU 時間は 4 割減り、メモリは 2.6 倍になった
- PGO はプロファイルを使って展開と脱仮想化を行い、数パーセントを得る道具。今回の処理では脱仮想化は起きたが差は測れなかった。重い処理をやめる改善の後に使う
