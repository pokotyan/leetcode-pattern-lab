## 1 台の中で測る道具は、1 台の中しか見えない

前回の eBPF や、第 98 回で扱う `perf` や `strace` は、**1 台のマシンの中**で起きていることを見る道具です。

ところが、いまのサービスの多くは 1 台では完結しません。ユーザのリクエスト 1 つが、API サーバ、認証サービス、DB、キャッシュ、別のサービスへと渡っていきます。

```
ユーザ → API サーバ ─┬→ 認証サービス
                     ├→ 在庫サービス → DB
                     └→ 決済サービス → 外部 API
```

「このリクエストが 2 秒かかった」と分かっても、**どこで 2 秒使ったのか**は、どの 1 台を覗いても分かりません。各サーバは自分の分しか知らないからです。

必要なのは、**サーバをまたいで 1 つのリクエストの足取りをつなぐ**仕組みです。これを **分散トレーシング** と呼びます。

## 計装と送り先を切り離す

足取りを記録するには、プログラムのあちこちに「ここから処理が始まった」「ここで終わった」と記録するコードを埋め込む必要があります。これを **計装**（instrumentation）と呼びます。

問題は、かつて計装のコードが**送り先の製品ごとに違っていた**ことです。監視の製品を乗り換えるたびに、全サービスの計装を書き直すことになります。ライブラリの作者も、どの製品向けに計装を書けばよいのか決められません。

この問題に対して、共通の API を定めようとする計画が 2 つありました。トレースの API を定めた OpenTracing と、トレースとメトリクスのライブラリを提供した OpenCensus です。2019 年に 2 つが統合されてできたのが **OpenTelemetry** です（[Google Open Source Blog](https://opensource.googleblog.com/2019/05/opentelemetry-merger-of-opencensus-and.html)）。

考え方の中心は、第 68 回の C ABI や第 71 回の WIT と同じです。**間に共通の約束を置き、両側を独立させる**。

```
 アプリ・ライブラリ              送り先
 ┌──────────────┐           ┌─────────────┐
 │ 計装コード    │           │ 製品 A       │
 │ (共通の API)  │ ─ 共通の ─→│ 製品 B       │
 └──────────────┘  形式      │ 自前の保存先  │
                             └─────────────┘
```

計装は共通の API に向けて一度だけ書き、送り先は設定で差し替えます。

## 3 つのシグナル

OpenTelemetry は、観測のデータを 3 種類に分けて扱います。それぞれ、答えられる問いが違います。

| シグナル | 中身 | 向いている問い | 量 |
| --- | --- | --- | --- |
| **メトリクス** | 数値の集計（回数、合計、分布） | 全体として遅くなっていないか。エラー率は上がったか | 少ない。時間あたり一定 |
| **トレース** | 1 リクエストの足取り | この遅いリクエストは、どこで時間を使ったか | 多い。リクエスト数に比例 |
| **ログ** | 出来事の記録 | そのとき、何が起きていたか | 多い |

実際の調べ方は、この順に降りていくのが普通です。メトリクスで異常に気づき、トレースで遅い箇所を特定し、ログでその瞬間の詳細を読む。

3 つが**同じ識別子でつながっている**ことが重要です。ログの 1 行にトレースの ID が書いてあれば、ログからトレースへ、トレースからログへ飛べます。

## span: 足取りの 1 区間

トレースは **span** の集まりです。span は「ある処理が、いつ始まり、いつ終わったか」を表す 1 区間です。

| 項目 | 意味 |
| --- | --- |
| trace id | このリクエスト全体で共通の ID（16 バイト） |
| span id | この区間の ID（8 バイト） |
| 親の span id | この区間を呼び出した区間。最初の区間には無い |
| 名前 | `GET /orders`、`SELECT orders` など |
| 開始時刻・終了時刻 | 区間の長さ |
| 属性 | HTTP のステータス、DB の文、ユーザの種類など、キーと値の組 |
| 状態 | 成功か、エラーか |

親の ID をたどると、span は木になります。これを時間軸に並べたものが、トレースの画面でよく見る図です。

```
trace id = 4bf9...4736
┌─ GET /orders ────────────────────────────────────── 2000ms ┐
│  ┌─ 認証 ──┐                                                │
│  │  40ms   │                                                │
│  └─────────┘                                                │
│             ┌─ 在庫サービス ──────────┐                       │
│             │  ┌─ SELECT ──────────┐ │                       │
│             │  │      1500ms       │ │ ← ここが遅い           │
│             │  └───────────────────┘ │                       │
│             └────────────────────────┘                       │
│                                        ┌─ 決済 ─┐            │
│                                        │ 300ms  │            │
│                                        └────────┘            │
└──────────────────────────────────────────────────────────────┘
```

## コンテキストの伝播

span が木になるには、**子の span を作るときに、親の ID が分かっていなければなりません**。親の ID を子へ受け渡すことを **コンテキストの伝播** と呼びます。受け渡しには 2 つの場面があります。

### プロセスの中

同じプロセスの中では、「いま処理中の span」をどこかに置いておき、次の span を作るときにそれを親として使います。

置き場所は言語によって違います。

- **スレッドごとの変数に置く**: Java や Python など。第 34 回のスレッドローカル記憶域です。1 つのリクエストを 1 つのスレッドが最後まで処理するなら、これで足ります
- **引数で明示的に渡す**: Go は `context.Context` を関数の第 1 引数で受け渡す慣習があり、そこに span を入れます

<Callout type="warn" title="スレッドをまたぐと途切れる">
  スレッドごとの変数に置く方式は、処理を別のスレッドに渡した瞬間に途切れます。
  スレッドプールに仕事を投げる、コールバックが別のスレッドで呼ばれる、
  非同期の処理が別の実行単位で再開される（第 44 回）。
  このとき、コンテキストも一緒に運ぶ仕組みがないと、子の span が親を見失い、
  トレースがばらばらの木に分かれます。
</Callout>

### プロセスの間

別のサーバへ呼び出すときは、コンテキストを**通信の中身に載せて**運ぶしかありません。HTTP なら、ヘッダに書きます。

この形式を決めているのが **W3C Trace Context** で、2021 年に W3C の勧告になりました（[W3C](https://www.w3.org/TR/trace-context/)）。中心は `traceparent` という 1 行のヘッダです。

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ││ └──────── trace id ─────────────┘ └── parent id ──┘ │
             版                                                    flags
```

| 部分 | 長さ | 意味 |
| --- | --- | --- |
| 版 | 16 進 2 文字 | 現在は `00` |
| trace id | 16 進 32 文字（16 バイト） | リクエスト全体の ID |
| parent id | 16 進 16 文字（8 バイト） | 送り手の span の ID |
| flags | 16 進 2 文字 | 最下位ビットが **sampled**。送り手が記録した可能性を示す |

受け手は、このヘッダを読んで自分の span の親にし、さらに先へ呼び出すときは自分の span id を parent id に入れて送ります。**バケツリレーで ID を渡していく**だけです。

製品ごとの追加情報を運ぶために、`tracestate` という補助のヘッダもあります。

<Callout type="note" title="1 つでも中継を落とすと切れる">
  途中のサービスが 1 つでもヘッダを捨てると、そこから先は別のトレースになります。
  ロードバランサ、メッセージキュー、古いライブラリ。
  メッセージキューを通る場合は、HTTP のヘッダの代わりに**メッセージの属性**に載せて運びます。
  **全員が同じ約束を守って初めて成り立つ**仕組みです。
</Callout>

## 別々の時計で測った時刻

span には開始時刻と終了時刻が付きます。問題は、**親の span と子の span を別のマシンの時計で測っている**ことです。

第 74 回で見たとおり、マシンごとの壁時計は NTP で合わせても少しずつずれています。数ミリ秒のずれは珍しくありません。すると、次のようなことが起きます。

```
API サーバの時計で:  親 span  10:00:00.000 〜 10:00:00.050
在庫サービスの時計で: 子 span  10:00:00.048 〜 10:00:00.070   ← 親が終わった後まで続いている？
```

子の span が親より後に終わっているように見えるのは、時計のずれのせいかもしれません。

これに対する考え方は、次のとおりです。

- **1 つの span の長さは、同じマシンの単調時計で測る**。開始から終了までの長さは、壁時計のずれの影響を受けません
- **span をまたいだ時刻の比較は、目安として読む**。サーバをまたぐ数ミリ秒の前後は信用しない
- 順序は時刻ではなく**親子関係**で決まる。子の span は、時刻がどう見えても親の中で起きたことです

第 74 回の「壁時計で順番を決めない」が、ここでもそのまま当てはまります。

## API、SDK、Collector、OTLP

OpenTelemetry は、役割の違う部品に分かれています。

```
 ┌── アプリのプロセス ───────────────┐
 │  ライブラリの計装 ─→ API          │
 │                      │           │
 │                      ▼           │
 │                     SDK          │     OTLP      ┌───────────┐    ┌────────┐
 │           (集約・サンプリング・送信) │ ────────────→ │ Collector │ ─→ │ 送り先  │
 └──────────────────────────────────┘               └───────────┘    └────────┘
```

| 部品 | 役割 |
| --- | --- |
| **API** | 計装のコードが呼ぶ口。span を始める、属性を付ける、数を数える。**SDK が無ければ何もしない** |
| **SDK** | API の実体。集約、サンプリング、まとめて送る処理 |
| **OTLP** | データを送る形式と手順。Protobuf で表し、gRPC（既定のポート 4317）か HTTP（4318）で送る（[OTLP Specification](https://opentelemetry.io/docs/specs/otlp/)） |
| **Collector** | 受け取ったデータを加工して転送する独立したプロセス。間引き、属性の削除、複数の送り先への振り分け |

API と SDK が分かれているのが要点です。**ライブラリは API だけに依存します**。アプリが SDK を組み込まなければ、API の呼び出しは何もしない処理になり、コストはほぼゼロです。これで、ライブラリの作者は安心して計装を入れておけます。

<Callout type="tip" title="Collector を挟む理由">
  アプリから送り先へ直接送ることもできます。それでも間に Collector を置くのは、
  **送り先の都合をアプリから追い出す**ためです。
  認証の情報、送り先の切り替え、個人情報の削除、再送のためのバッファ。
  これらを各アプリに持たせると、変えるたびに全アプリを配り直すことになります。
</Callout>

## 全部は取れない: サンプリング

トレースは、リクエストの数に比例して増えます。秒間 1 万リクエストのサービスで、1 リクエストあたり 30 個の span ができれば、秒間 30 万個です。すべてを送って保存すると、観測のほうが本体より高くつきます。

そこで、**一部だけを残す**ことにします。これを **サンプリング** と呼び、決めるタイミングで 2 つに分かれます（[OpenTelemetry](https://opentelemetry.io/docs/concepts/sampling/)）。

| 方式 | いつ決めるか | 利点 | 欠点 |
| --- | --- | --- | --- |
| **ヘッドサンプリング** | 最初の span を作るとき | 単純で安い。捨てるものは最初から作らない | エラーになったリクエストを残せる保証がない |
| **テールサンプリング** | トレースが出揃ってから | 「エラーのもの」「遅いもの」を選んで残せる | 全 span を一旦どこかに溜める必要があり、重い |

ヘッドサンプリングの決定は、`traceparent` の sampled のビットで下流へ伝わります。上流が「記録する」と決めたリクエストは、下流も記録する。こうしないと、トレースの一部だけが残る歯抜けになります。

テールサンプリングは、同じトレースの span を**1 か所に集めてから**判断します。サーバは何十台もあるので、同じ trace id の span が同じ Collector に届くよう、trace id で振り分ける必要があります。システム設計の<a href={`${import.meta.env.BASE_URL}reading/consistent-hashing/`}>コンシステントハッシュ</a>が使われる場面です。

## メトリクスは、先に集約する

メトリクスは、トレースと違って**送る前にまとめます**。1 リクエストごとに送るのではなく、「この 10 秒で 1,532 回、合計 4.2 秒」のような集計値を送ります。量はリクエスト数ではなく、**集計の種類の数**で決まります。

遅延の分布は、平均ではなく **ヒストグラム** で持ちます。平均は極端に遅い少数を隠してしまうからです（<a href={`${import.meta.env.BASE_URL}reading/performance-estimation/`}>性能を勘で語らない</a>の p99 の話）。ヒストグラムなら、あとから p99 を概算できます。

### カーディナリティ

メトリクスには属性を付けられます。`http.method=GET`、`status=200` といった具合です。属性の値の組み合わせごとに、別の集計が作られます。

```
http_requests{method="GET",  status="200"}  1532
http_requests{method="GET",  status="500"}     4
http_requests{method="POST", status="200"}   210
```

組み合わせの数を **カーディナリティ** と呼びます。ここに**ユーザ ID やリクエスト ID** を入れると、組み合わせがユーザの数だけ増えます。10 万人なら 10 万通りの集計を、メモリに持ち、送り、保存することになります。

<Callout type="warn" title="個別の値はトレースへ、種類はメトリクスへ">
  「このユーザのリクエストが遅かった」を知りたいなら、それはトレースやログの仕事です。
  メトリクスの属性は、**取りうる値の数が小さいもの**（メソッド、ステータス、リージョン）に限ります。
  メトリクスの値段を決めているのは、データの量ではなく組み合わせの数です。
</Callout>

## まとめ

- 1 台の中を見る道具では、サーバをまたいだ 1 リクエストの足取りは見えない
- OpenTelemetry は、計装と送り先の間に共通の約束を置き、両側を独立させる
- メトリクスで気づき、トレースで場所を絞り、ログで詳細を読む。3 つは同じ ID でつながる
- span は ID と親の ID を持ち、親をたどると木になる
- コンテキストは、プロセス内ではスレッドごとの変数や引数で、プロセス間では `traceparent` ヘッダで受け渡す
- 別のマシンの span の時刻は揃わない。長さは単調時計で測り、順序は親子関係で読む
- ライブラリは API だけに依存し、SDK が無ければ計装のコストはほぼゼロ
- サンプリングは、最初に決める（安い）か、出揃ってから決める（賢いが重い）かの交換
- メトリクスの属性に個別の ID を入れると、カーディナリティが爆発する

次は、計装のコードを 1 行も書かずに span を作る、自動計装がどこに割り込んでいるのかを見ます。
