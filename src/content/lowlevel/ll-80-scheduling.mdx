## もう 1 つのスケジューラ

第 36 回で、OS のスケジューラを見ました。どのスレッドを、いつ、どのコアで動かすかを決める仕組みです。

Kubernetes のスケジューラは、同じ名前ですが、決めることが違います。

| | OS のスケジューラ（第 36 回） | kube-scheduler |
| --- | --- | --- |
| 何を置くか | スレッド | Pod |
| どこに置くか | CPU のコア | ノード（マシン） |
| どのくらいの頻度で | ミリ秒ごとに何度でも | Pod ごとに **1 回だけ** |
| 置き直すか | 常に入れ替える | 一度置いたら動かさない |

kube-scheduler は、**ノードがまだ決まっていない Pod を見つけて、置き場所を 1 回だけ決める**ものです（[Kubernetes](https://kubernetes.io/docs/concepts/overview/components/)）。決めたあと、その Pod がどれだけ CPU を使うかには関与しません。実際の CPU の配分は、ノードの上で第 36 回の CFS と第 76 回の cgroup が引き受けます。

## 箱詰めという古典問題

大きさの違う荷物を、できるだけ少ない箱に詰めたい。これは **ビンパッキング問題** と呼ばれる古典的な問題で、最適解を求めるのは NP 困難です。荷物が増えると、すべての詰め方を試すことは現実的ではなくなります。

Pod の配置は、これに次元が増えたものです。CPU とメモリという 2 つの寸法があり、さらに「この Pod はこのノードには置けない」という制約が加わります。

だから kube-scheduler は、最適解を探しません。**Pod を 1 つずつ取り出し、そのときに一番よさそうなノードに置く**という、貪欲な方法を取ります。全体として最適ではないかもしれませんが、速く、予測しやすい。

## 絞って、点数を付けて、書き込む

1 つの Pod に対して、スケジューラは 2 段階で置き場所を選びます（[Kubernetes](https://kubernetes.io/docs/concepts/scheduling-eviction/kube-scheduler/)）。

```
 全ノード（例: 500 台）
     │
     │ ① フィルタリング: 置けないノードを除く
     │    - requests を満たす空きがあるか
     │    - 指定されたラベルを持つか
     │    - taint を許容しているか
     ▼
 候補のノード（例: 120 台）── 0 台なら「置けない」として待つ
     │
     │ ② スコアリング: 候補に点数を付ける
     │    - 空きが多いか（分散させたいとき）
     │    - 同じ種類の Pod が散らばるか
     │    - イメージがすでにあるか
     ▼
 最高点のノード（同点ならランダム）
     │
     │ ③ 決定を API サーバに書き込む（Pod の nodeName を埋める）
     ▼
 そのノードの kubelet が気づいて、起動する
```

公式ドキュメントの言葉では、①で残ったノードを **feasible**（置くことが可能な）ノードと呼び、候補がなければ「その Pod はまだスケジュールできない」として、置けるようになるまで待たされます。同点のノードが複数あれば、その中から**ランダムに**選ばれます。

③に注目してください。スケジューラは kubelet に「起動せよ」と命令しません。**「この Pod はこのノード」と API サーバに書くだけ**です。kubelet は、自分のノード宛ての Pod が現れたことに watch で気づき、第 79 回の手順で起動します。第 78 回の「部品どうしは直接話さない」がここでも守られています。

<Callout type="note" title="全部を見ないこともある">
  数千台のノードがあるクラスタで、Pod のたびに全ノードに点数を付けると遅くなります。
  そこで kube-scheduler は、置けるノードが一定の割合見つかった時点でフィルタリングを打ち切り、
  その中から選びます。既定では、100 台のクラスタで 50%、5000 台で 10% になるように計算され、
  下限は 5%、そして最低でも 100 台は見ます（[Kubernetes](https://kubernetes.io/docs/concepts/scheduling-eviction/scheduler-perf-tuning/)）。
  最善ではなく「十分によい」を速く選ぶ、という判断です。
</Callout>

## 判断の根拠は、使用量ではなく申告

①のフィルタリングで「空きがあるか」を判断するとき、スケジューラが見るのは**実際の使用量ではありません**。各 Pod が申告した **requests** の合計です。

第 76 回で見たとおり、requests はコンテナの設定の一部で、ノードの上では cgroup の重み（cpu.weight）になります。スケジューラにとっては、**配置のための予約**です。

```
 ノード: CPU 4 コア

 Pod A  requests 1.0   実際の使用 0.1
 Pod B  requests 1.0   実際の使用 0.2
 Pod C  requests 1.5   実際の使用 0.1
 ─────────────────────────────────
 requests の合計 3.5 → 空きは 0.5
 実際の使用     0.4 → ほぼ空いている

 新しい Pod D（requests 1.0）は、このノードには置かれない
```

なぜ実際の使用量で判断しないのでしょうか。

- **使用量は変わる**。今は暇でも、1 分後に負荷が来るかもしれない。スケジューラは Pod を一度置いたら動かさないので、瞬間の値で判断すると、あとで溢れる
- **予測できる**。申告に基づけば、同じ入力には同じ判断が返る
- **約束になる**。requests の分は、混み合ったときにも cgroup の重みとして確保される。申告は、スケジューラとノードの両方が守る約束です

その代わり、**申告が実態とずれると無駄か事故になります**。

| 申告 | 起きること |
| --- | --- |
| requests が実際より大きい | 空いているのに置けない。マシンが無駄になる |
| requests が実際より小さい | 詰め込みすぎる。混み合うと遅くなり、メモリなら追い出される |
| requests を書かない | 予約ゼロとして、どこにでも置かれる。混んだら真っ先に追い出される（第 76 回の BestEffort） |

## 置き場所に条件を付ける

requests だけでは表せない条件もあります。

**nodeSelector と node affinity**：「GPU を持つノードに置け」「東京のゾーンのノードに置け」のように、ノードのラベルで引き寄せます。「必須」と「できれば」を区別できます。

**pod affinity と anti-affinity**：他の Pod との位置関係で決めます。「キャッシュと同じノードに置け」は affinity。「同じアプリの複製を同じノードに置くな」は anti-affinity で、1 台が落ちたときに全部が消えるのを防ぎます。

**taint と toleration**：ノードの側から Pod を**遠ざける**仕組みです（[Kubernetes](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/)）。ノードに taint（汚れ）を付けると、それを許容する toleration を持つ Pod しか置かれません。

```
 ノード gpu-1   taint: gpu=true:NoSchedule
   → 普通の Pod は置かれない
   → toleration「gpu=true を許容」を持つ Pod だけが置ける
```

affinity は「Pod がノードを選ぶ」、taint は「ノードが Pod を選ぶ」。高価な GPU のノードに関係のない Pod が居座らないようにするには、後者が向いています。

どれも、①のフィルタリングか②のスコアリングのどちらかに、条件を 1 つ足すものです。

## 拡張できる骨組み

①と②の中身は、固定されていません。kube-scheduler は **Scheduling Framework** という骨組みを持ち、決められた差し込み口（拡張点）に処理を足せるようになっています（[Kubernetes](https://kubernetes.io/docs/concepts/scheduling-eviction/scheduling-framework/)）。

| 段階 | 主な拡張点 | 役割 |
| --- | --- | --- |
| 下準備 | PreFilter | Pod の情報を前処理する。この時点で「置けない」と判定することもある |
| 絞り込み | Filter | 置けないノードを除く |
| 救済 | PostFilter | 候補が 0 台のとき。後述のプリエンプションはここで動く |
| 採点 | Score | 候補に点数を付ける |
| 予約 | Reserve | 決めたノードの資源を、書き込みが終わる前に押さえる |
| 書き込み | Bind | 決定を API サーバに書く |

Reserve が、書き込みの前に置かれている点に注目してください。Bind は非同期に行われるので、その間に次の Pod の判断が始まります。先に資源を押さえておかないと、**2 つの Pod が同じ空きを当てにしてしまう**。第 37 回で見た「片方の更新が消える」競合と同じ形の問題を、予約という形で避けています。

requests の確認、affinity、taint といった機能は、それぞれがこの骨組みの上の部品（プラグイン）として実装されています。

## 置けないときの 2 つの手段

候補のノードが 0 台だったとき、Pod はそのまま待たされます。ただし、待つ以外の手段が 2 つあります。

**プリエンプション**：Pod には優先度（PriorityClass）を付けられます。優先度の高い Pod が置けないとき、スケジューラは**優先度の低い Pod を押しのけて**場所を空けます（[Kubernetes](https://kubernetes.io/docs/concepts/scheduling-eviction/pod-priority-preemption/)）。第 36 回の優先度付きのスケジューリングと同じ考え方ですが、押しのけられた Pod は一時停止ではなく**終了**させられ、別の場所で作り直されます。

**ノードを増やす**：クラスタのノードを自動で増やす仕組みは、「置けずに待っている Pod がある」ことを合図にノードを足します。第 86 回で見ます。

<Callout type="warn" title="配置のあとで追い出されることもある">
  スケジューラは置いたら動かしませんが、ノードの側は別です。
  ノードのメモリやディスクが足りなくなると、kubelet が Pod を**追い出し**ます
  （[Kubernetes](https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/)）。
  どれを先に追い出すかは、第 76 回の QoS クラスと、requests をどれだけ超えて使っているかで決まります。
  追い出された Pod は上位のコントローラが作り直し、スケジューラがもう一度置き場所を決めます。
  **置く判断と、あとで守りきれなかったときの判断は、別の部品が別の根拠で行っている**わけです。
</Callout>

## まとめ

- kube-scheduler は、ノードの決まっていない Pod に置き場所を 1 回だけ決める。実際の CPU の配分はノードの CFS と cgroup の仕事
- 配置はビンパッキング問題の一種。最適解は探さず、1 つずつ貪欲に置く
- フィルタリングで候補を絞り、スコアリングで点数を付け、決定を API サーバに書くだけ
- 判断の根拠は実際の使用量ではなく requests という申告。予測可能で、約束として守られる
- affinity は Pod がノードを選び、taint はノードが Pod を選ぶ
- 候補がなければ待つ。優先度の高い Pod は、低い Pod を押しのけられる

次は、置かれた Pod どうしが、作り直されて IP が変わっても**同じ名前で**通信できる仕組み、Service を見ます。
