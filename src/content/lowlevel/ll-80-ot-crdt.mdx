前回は、ゲームの状態同期を見ました。そこでは**権威を持つサーバ**が 1 つの正しい状態を決め、クライアントは予測して先に動き、食い違えばサーバの答えに巻き戻しました。正解はいつもサーバの側にあります。

この回の題材は、共同で編集する文書です。ここでは巻き戻しが使えません。人が打った文字は、サーバと食い違ったからといって消してよいものではないからです。さらに、新幹線の中で 1 時間オフラインのまま書き続けた人の変更も、戻ってきたときに他の人の変更と合わせなければなりません。

この回では、複数の書き手の変更を**全員が同じ 1 つの結果に収束させる**方法として、操作を相手に合わせて直す **OT** と、どの順で合わせても同じになるようにデータの型を作る **CRDT** を、小さく実装しながら比べます。

## 何を満たせばよいのか

共同編集の仕組みには、次の 3 つが求められます。

| 要求 | 意味 |
| --- | --- |
| 手元ですぐ反映する | 打った文字は、サーバの返事を待たずに画面に出る。往復を待つと打鍵が重くなる |
| 収束する | 同じ変更の集まりを受け取った人は、受け取った順序に関係なく同じ文書を見る |
| 意図を保つ | 合わせた結果が、それぞれの人がしようとしたことから大きく外れない |

1 つめのために、各自が自分の複製を持ち、そこへ先に書き込みます。すると、同じ時刻に別々の複製へ書かれた変更が必ず生まれます。2 つめと 3 つめは、その変更をどう合わせるかの問題です。

## 手元で動かした環境

この回の実験は、すべて手元の macOS 26.2（arm64）で動かしました。自作の実装は Python 3.14.0 で書き、外部のライブラリは使っていません。既製のライブラリは Node.js 20.19.0 の上で、npm から入れた **yjs 13.6.33** と **@automerge/automerge 3.5.0** を使いました。

## 素朴な方法 1: 最後に書いた人が勝つ

いちばん簡単なのは、文書全体を 1 つの値とみなし、**最後に書いたものを残す**方法です。LWW（Last Writer Wins）と呼ばれます。

A と B が同じ版から書き始め、A が 1 段落を足し、B が誤字を 1 つ直したとします。両方が保存すると、遅く届いたほうの文書がもう一方を丸ごと上書きします。誤字の修正が勝てば、A が書いた段落は黙って消えます。収束はしますが、意図は保てません。

さらに「最後」を何で決めるかという問題があります。各端末の壁時計の時刻を使うと、時計がずれた端末の書き込みが常に勝ったり負けたりします。壁時計が進みも戻りもすることは、<a href={`${import.meta.env.BASE_URL}lowlevel/ll-161-time/`}>第 161 回</a>で見ました。

LWW が役に立つのは、上書きされても困らない小さな値です。図形の色や、フォームの 1 つの欄のように、**合わせる単位を十分に細かくすれば**、LWW は今でも広く使われています。後で見る Figma も、プロパティ単位では LWW です。

## 素朴な方法 2: 位置で送ると、ずれる

文書全体を送るのをやめ、**操作**を送ることにします。「1 文字目の後ろに X を挿入する」「0 文字目を消す」という形です。

`abc` という文書から、A は位置 1 に `X` を挿入し、B は位置 0 の `a` を消します。それぞれ自分の操作を先に適用し、相手の操作が届いたらそのまま適用します。

```
$ python3 naive_ot.py
== 位置をそのまま送る ==
A: 'abc' -> ins(1,X) -> del(0) = 'Xbc'
B: 'abc' -> del(0) -> ins(1,X) = 'bXc'
```

2 人の文書が食い違いました。B の側では、`a` が消えた時点で `b` が位置 0 に詰めて来ています。そこへ「位置 1 に挿入」を適用すると、A が意図した「`a` と `b` の間」ではなく「`b` と `c` の間」に入ります。**位置は、他人の操作によって意味が変わる**のです。

この問題に対して、2 通りの答えがあります。位置を相手の操作に合わせて**直してから**適用するのが OT、位置ではなく**変わらない名前**で場所を指すのが CRDT です。

## OT: 相手の操作に合わせて直す

OT（Operational Transformation）の中心は、**transform** と呼ばれる関数です。`T(a, b)` は、「b がすでに適用された文書に、a を適用できる形に直したもの」を返します。挿入と削除の 2 種類だけなら、組み合わせは 4 通りです。

```python
def transform(a, b):
    """a を、すでに適用された b の後に適用できる形に直す"""
    if a[0] == "ins" and b[0] == "ins":
        _, pa, ca, sa = a
        _, pb, _, sb = b
        if pa < pb or (pa == pb and sa < sb):   # 同じ位置ならサイト番号で決める
            return a
        return ("ins", pa + 1, ca, sa)
    if a[0] == "ins" and b[0] == "del":
        ...  # b が手前を消したなら、a を 1 つ前へ
    if a[0] == "del" and b[0] == "ins":
        ...  # b が手前に挿入したなら、a を 1 つ後ろへ
    if a[0] == "del" and b[0] == "del":
        ...  # 同じ文字を消していたら、a は何もしない操作になる
```

同じ位置への挿入が 2 つぶつかったときは、どちらを先にするかを決めなければなりません。ここではサイト番号の小さいほうを先にしました。どちらでもよいのですが、**全員が同じ規則で決める**ことが要ります。

A は自分の操作のあとに `T(b, a)` を、B は `T(a, b)` を適用します。

```
== transform を挟む ==
A: 'Xbc'  B: 'Xbc'
```

今度は一致しました。

## 変換の正しさ: TP1 と TP2

transform が正しいためには、2 つの条件があります。Imine らの 2003 年の論文の書き方では次のとおりです（[Imine ほか, ECSCW 2003](https://doi.org/10.1007/978-94-010-0068-0_15)。論文では C1 / C2 と呼んでいます）。

| 条件 | 式 | 意味 |
| --- | --- | --- |
| TP1（C1） | `op1 ∘ T(op2, op1) ≡ op2 ∘ T(op1, op2)` | 並行な 2 つの操作を、どちらの順で適用しても同じ文書になる |
| TP2（C2） | `T(op3, op1 ∘ T(op2, op1)) = T(op3, op2 ∘ T(op1, op2))` | 3 つめの操作を、並行な 2 つの操作に合わせて直すとき、直す順序によらず同じ操作になる |

TP1 は 2 人で、TP2 は 3 人以上で編集するときに必要になります。上の transform をランダムな文書と操作の組で試しました。

```
TP1 violations in 100000 random pairs: 0
TP2 violations in 200000 random triples: 4694
  doc='b' o1=('del', 0) o2=('ins', 1, 'y', 2) o3=('ins', 0, 'x', 3)
  via o1 then o2: ('ins', 1, 'x', 3)   via o2 then o1: ('ins', 0, 'x', 3)
  docs: 'yx' vs 'xy'
```

TP1 は 10 万組で破れませんでしたが、TP2 は 20 万組のうち 4694 組で、変換後の操作が食い違いました。上に出したのは、文書が実際に分かれる例です。`b` 1 文字の文書で、サイト 1 が `b` を消し、サイト 2 が `b` の後ろに `y` を、サイト 3 が `b` の前に `x` を挿入します。`b` が消えると、`x` と `y` はどちらも位置 0 への挿入になり、もとは `x` が前だったという情報が失われます。あとはサイト番号の比較で決まるので、直す順序によって `yx` にも `xy` にもなります。

これは手元の実装だけの誤りではありません。Imine らは、定理証明器 SPIKE で既存の transform 関数を検証しました。OT を始めた Ellis と Gibbs の関数には、挿入と削除が同じ位置でぶつかると TP1 が破れる反例が数秒で見つかりました。それを TP1 と TP2 を満たすように直したとされる Ressel の関数には、挿入・削除・挿入の 3 人で TP2 が破れる反例が見つかっています。上の transform は、論文に載っている Ressel の関数と同じ規則で、見つかった反例も同じ形です。論文は、文字列で TP2 を証明するには **123 通りの場合**を調べる必要があるとも書いています（[Imine ほか, 2003](https://doi.org/10.1007/978-94-010-0068-0_15)）。**OT は考え方は簡単でも、正しい transform を作るのが難しい**のです。

## 中央サーバで順序を決める: Jupiter と Google Docs

TP2 が要るのは、3 つ以上の並行な操作を、場所ごとに違う順序で直すからです。そこで、**サーバが 1 本の順序を決め、変換はクライアントとサーバの 2 者の間でだけ行う**という設計が生まれました。1995 年の Jupiter は、中央集権の構成を利用して、分散型の dOPT アルゴリズムを簡略化した 2 者間のアルゴリズムを示しています（[Nichols ほか, UIST 1995](https://doi.org/10.1145/215585.215706)）。

Google Docs も同じ形です。2010 年の公式ブログは、クライアントとサーバが持つものを次のように説明しています（[Google Drive Blog, 2010](https://drive.googleblog.com/2010/09/whats-different-about-new-google-docs.html)）。

| 持ち主 | 持っているもの |
| --- | --- |
| クライアント | サーバから受け取った最新の版の番号、まだ送っていない変更（pending）、送ったが確認が来ていない変更（sent）、手元の文書 |
| サーバ | 受け取ったがまだ処理していない変更、処理済みの変更の全履歴（revision log）、最新の文書 |

クライアントは**確認が返るまで次の変更を送りません**（"we never send more than one pending change at a time"）。その間に打った文字は pending に貯めます。サーバから他人の変更が届いたら、自分の pending に合わせて直してから適用します。サーバの側では、届いた変更を revision log に並べ、クライアントが知っている版からの差に合わせて直します。

この形では、サーバが順序の権威です。前回のゲームのサーバと似ていますが、違いは**食い違いを巻き戻しではなく変換で解く**ことです。手元の打鍵は消されず、位置だけが直されます。その代わり、**サーバにつながらなければ他人と合わせられません**。オフラインで長く書いた変更は、戻ってきたときに長い revision log の全部に対して変換されます。

## CRDT: 合わせ方を型に組み込む

CRDT（Conflict-free Replicated Data Type）は、発想が逆です。操作を後から直すのではなく、**どの順序で、何回受け取っても同じ結果になる**ように、データ型そのものを設計します。Shapiro らの 2011 年の報告が、2 つの流儀を整理しています（[Shapiro ほか, INRIA RR-7506](https://inria.hal.science/inria-00555588)）。

| 流儀 | 送るもの | 送り方への要求 |
| --- | --- | --- |
| 状態ベース（CvRDT） | 自分の状態の全体 | ほとんど無い。失われても、順序が入れ替わっても、重複しても、いずれ届けばよい |
| 操作ベース（CmRDT） | 個々の操作 | 因果順に、ちょうど 1 回ずつ届けること。並行な操作どうしは可換に作る |

状態ベースの条件は、状態が**半束**（join semilattice）をなし、merge がその**最小上界**になっていることです。最小上界は定義から**可換・結合・冪等**なので、merge をどの順で何回繰り返しても同じ状態に行き着きます（同報告 2.3.1 節）。冪等であることが、重複して届いても構わない理由です。

## 手で作る: カウンタ、レジスタ、集合

報告に載っている基本の型を 4 つ、Python で実装しました。

**G-Counter**（増えるだけのカウンタ）は、レプリカごとの数を持ち、merge で要素ごとの最大をとります。合計が値です。1 つの整数を持って max をとるのでは、2 人が同時に 1 足したときに 1 しか増えません。

```python
class GCounter:
    def __init__(self, rid):
        self.rid, self.p = rid, {}

    def inc(self, n=1):
        self.p[self.rid] = self.p.get(self.rid, 0) + n

    def value(self):
        return sum(self.p.values())

    def merge(self, other):
        for k, v in other.p.items():
            self.p[k] = max(self.p.get(k, 0), v)
```

**PN-Counter** は減らせるカウンタで、増やした分と減らした分の G-Counter を 2 つ持ち、差を値とします。max で合わせる以上、1 つのカウンタを減らすことはできないからです。**LWW-Register** は値に `(時刻, レプリカ ID)` を付け、大きいほうを残します。**OR-Set**（Observed-Remove Set）は、追加のたびに一意のタグを振り、削除では**自分が見たタグだけ**を墓標に入れます。

```python
class ORSet:
    def add(self, e):
        self.adds.add((e, uuid.uuid4().hex[:8]))

    def remove(self, e):
        # 自分が観測した e のタグだけを消す
        self.tombs |= {t for (x, t) in self.adds if x == e}

    def value(self):
        return {e for (e, t) in self.adds if t not in self.tombs}

    def merge(self, other):
        self.adds |= other.adds
        self.tombs |= other.tombs
```

確かめたことは 2 つです。1 つは、ランダムに操作した 3 つの状態について、merge が可換・結合・冪等かどうか（各型 2000 組）。もう 1 つは、4 つのレプリカがランダムに操作しながら、**ランダムな相手に、ランダムな古さの状態を、重複ありで**送り合い、最後に全員が同じ値になるかどうか（各型 200 回）です。

```
$ python3 crdt.py
GCounter     lattice-law violations=0  diverged runs=0/200  sample value=417
PNCounter    lattice-law violations=0  diverged runs=0/200  sample value=-12
LWWRegister  lattice-law violations=0  diverged runs=0/200  sample value=b
ORSet        lattice-law violations=0  diverged runs=0/200  sample value={'a', 'd', 'c'}
```

これは直した後の結果です。最初に書いた LWW-Register は、時刻に 1〜50 の乱数をそのまま使っていて、200 回中 7 回で値が分かれました。

```
LWWRegister  lattice-law violations=0  diverged runs=7/200  sample value=d
```

原因は、同じレプリカが同じ時刻で 2 回書くと、`(時刻, レプリカ ID)` が同じで値だけが違う状態が 2 つできることです。そうなると「大きいほうを残す」で決まらず、受け取った順序で結果が変わります。書くときの時刻を「自分がこれまでに見た最大の時刻 + 1」以上にして、組が一意になるようにしたところ、分かれなくなりました。これは Lamport 時計と同じ考え方です（[Lamport, 1978](https://doi.org/10.1145/359545.359563)）。merge の規則が正しくても、**順序の比較に使う値が一意でなければ収束しません**。

OR-Set では、A が `milk` を足し、それを受け取った B が `milk` を消し、同時に A がもう一度 `milk` を足した場合を試しました。

```
== OR-Set: 同時の add と remove ==
A: {'milk'} B: {'milk'} tombstones: 1 adds: 2
```

B が消したのは自分が見た 1 つめのタグだけなので、B が見ていない 2 つめの追加が残り、`milk` は集合に残ります。**同時の追加と削除では、追加が勝つ**のが OR-Set の意味です。逆に削除が勝つ 2P-Set もあり、どちらを選ぶかは用途で決めます（同報告 3.3 節）。

<Callout type="note" title="収束は、意図どおりを意味しない">
LWW-Register に、A が `Tokyo`、B が `Osaka` を同じ時刻 7 で書くと、両者とも `Osaka` になりました。レプリカ ID の `B` が `A` より大きいからです。全員が同じ値を見るという意味では正しく、A の書いたものが消えたという意味では誤りです。CRDT が保証するのは収束であって、誰の意図を優先するかは、型を選ぶ時点で決めた規則に任されています。
</Callout>

## 因果を追う: ベクタクロック

操作ベースの CRDT は、操作が**因果順**に届くことを前提にします。「`x` を挿入する」より前に「`x` の後ろに `y` を挿入する」が届いても、適用できないからです。

因果の前後を判定する道具が**ベクタクロック**です。各レプリカは「レプリカごとに、何番目の操作まで見たか」という表を持ちます。2 つの表を要素ごとに比べ、一方がすべての要素で他方以下なら前後関係があり、そうでなければ**並行**です。Lamport 時計の 1 つの数では、前後があることは表せても、並行であることは判定できません。

自作の文字列 CRDT（次の節）では、操作ごとに送り手のベクタクロックを付け、受け手は次の条件を満たすまで操作を保留しました。

- 送り手の要素がちょうど自分の値 + 1（送り手の操作を飛ばしていない）
- それ以外の要素がすべて自分の値以下（送り手が見ていたものは、自分も見ている）

同じ操作が 2 回届いたら、`(送り手, 番号)` で捨てます。300 回の試行での配送の内訳は次のとおりです。

```
deliveries=93576 duplicates_dropped=19129 buffered_out_of_order=15851
```

届いた操作のうち約 2 割が重複、約 17% が因果順より早く届いて保留されました。

同期の場面では、同じ表を**版ベクタ**として使います。「自分はどのレプリカの何番まで持っているか」を相手に送れば、相手は足りない分だけを返せます。Yjs はこれを state vector と呼び、更新を作るときに相手の state vector を渡すと**足りない差分だけ**を書き出します（[Yjs Docs](https://docs.yjs.dev/api/document-updates)）。

## 文字列の CRDT: 文字に名前を付ける

位置がずれる問題に対する CRDT の答えは、**文字ごとに一意の ID を振り、挿入を「ID が p の文字の後ろ」と表す**ことです。ID は他人の編集で変わりません。

自作したのは RGA（Replicated Growable Array、[Roh ほか, 2011](https://doi.org/10.1016/j.jpdc.2010.12.006)）に近いものです。

| 要素 | 内容 |
| --- | --- |
| 文字の ID | `(Lamport 時計, レプリカ ID)`。全レプリカで一意で、全順序で比べられる |
| 挿入 | `("ins", 新しい ID, 直前の文字の ID, 文字)` |
| 削除 | `("del", 消す文字の ID)`。文字は消さず、削除済みの印を付ける |

挿入を適用するには、直前の文字の後ろへ行き、そこから**自分より大きい ID の文字を飛ばしてから**入れます。

```python
pos = 0 if parent is None else self._index(parent) + 1
# 同じ場所に同時に挿入された文字のうち、ID が大きいものを先に置く
while pos < len(self.nodes) and self.nodes[pos][0] > id_:
    pos += 1
self.nodes.insert(pos, [id_, ch, False])
```

同じ文字の後ろに並行して挿入された文字は、ID の大きい順に並びます。後から来た文字の子孫は Lamport 時計の性質で必ずさらに大きい ID を持つので、この 1 つの規則でまとめて飛ばせます。

3 つのレプリカが 120 回ずつランダムに挿入と削除をし、操作を**順序を入れ替え、3 割は重複させて**配送する試行を 300 回行いました。

```
$ python3 rga.py
diverged runs: 0/300
last run: visible=26 nodes=73 tombstones=47
```

すべての試行で 3 つの文書が一致しました。飛ばす規則を外して直前の文字のすぐ後ろに入れるようにすると、300 回中 213 回で分かれました。

最後の試行の数字にも注目します。見えている文字は 26 文字なのに、内部には 73 個の節点があり、47 個は削除済みの**墓標**（tombstone）です。墓標を消せないのは、まだ届いていない操作が「その文字の後ろに挿入」を指しているかもしれないからです。

## 交錯（interleaving）

収束は保証されても、結果が読めるとは限りません。2 人が同じ場所で、同時に別の単語を打った場合を試しました。前から順に打つ場合と、各文字を先頭に挿入して後ろから打つ場合です。

```
forward  typing: ('WorldHello', 'WorldHello')
backward typing: ('WHoerllldo', 'WHoerllldo')
```

前から打てば単語はまとまりますが、後ろから打つと 1 文字ずつ混ざりました。Kleppmann らはこれを**交錯の異常**と呼び、Logoot と LSEQ は前から打っても文字が混ざりうること、RGA は前から打つ限り混ざらないが、**文書を後ろから打つと最悪の場合に文字単位で混ざる**ことを示しています（[Kleppmann ほか, PaPoC 2019](https://doi.org/10.1145/3301419.3323972)）。後ろから打つ場合、すべての文字が文書の先頭を直前の文字として持ち、並び順が時刻だけで決まるからです。

同じことを 2 つのライブラリで試しました。

| ライブラリ | 前から打つ | 後ろから打つ |
| --- | --- | --- |
| Yjs 13.6.33 | `HelloWorld` | `HelloWorld` |
| Automerge 3.5.0 | `WorldHello` | `WHoerllldo` |

Automerge の文書は、リストの下の構造を RGA だと説明しています（[Automerge](https://automerge.org/llms-full.txt)）。手元の結果も、自作の RGA と同じ混ざり方でした。Yjs のアルゴリズム YATA（[Nicolaescu ほか, GROUP 2016](https://doi.org/10.1145/2957276.2957310)）は、挿入した文字に**左隣と右隣の両方**の ID を記録します（Yjs の内部文書では `origin` と `originRight`、[INTERNALS.md](https://github.com/yjs/yjs/blob/main/INTERNALS.md)）。右隣も手がかりにするので、後ろから打った文字の列もまとまりました。

<Callout type="warn" title="収束した結果が、どちらの意図とも違うことがある">
`Hello world` を共有した状態から、A が `world` の前に `big ` を足し、B が `world` を消して `there` を打ちました。Yjs は `Hello big there` に、Automerge は `Hello therebig ` に収束しました。どちらも、2 つの挿入が同じ空白の後ろを指しているので、並び順はアルゴリズムの規則で決まります。どちらも正しく収束していますが、読める文になるかは偶然に近いものです。共同編集のエディタが他人のカーソルを表示するのは、こうした衝突を人が先に避けられるようにするためでもあります。
</Callout>

## Yjs と Automerge を動かす

上の `Hello world` の例を、送ったバイト数とともに見ます。Yjs では、相手の state vector を渡して差分を作りました（抜粋）。

```
$ node yjs.mjs
initial sync bytes: 21
A only: "Hello big world"  B only: "Hello there"
A->B bytes: 15  B->A bytes: 18
merged A: "Hello big there"  B: "Hello big there"
state vector A: {"1":15,"2":5}
structs: Item(2,0,len=5) Item(1,0,len=6) Item(1,6,len=5) Item(1,11,len=4)
delete set: [[1,[[6,5]]]]
```

state vector の `"1":15` は、クライアント 1（A）が 11 文字と 4 文字を挿入したことを表します。削除は時計を進めず、**delete set** として `(クライアント, 時計, 長さ)` の範囲で別に持たれます。ここではクライアント 1 の時計 6 から 5 文字、つまり `world` が消えています。Yjs の更新は可換・結合・冪等で、どの順で何回適用してもよいと文書にあります（[Yjs Docs](https://docs.yjs.dev/api/document-updates)）。

Automerge では、各自の最後の変更（change）の大きさを測りました。

```
$ node am.mjs
save() initial bytes: 169
merged: "Hello therebig "  other side: "Hello therebig "
```

A の変更は 111 バイト、B の変更は 155 バイトでした。B の変更を復号すると、`"elemId":"13@bbbb..."` のように、各操作が `カウンタ@アクタ ID` という ID を持っています。アクタ ID は既定で 128 ビットの乱数です（[Automerge のバイナリ形式](https://automerge.org/automerge-binary-format-spec/)）。

## メタデータの大きさと掃除

次に、2000 文字を 1 文字ずつ末尾に打ち、そのあと 3 分の 2 にあたる 1333 文字をランダムな位置から 1 文字ずつ消しました。

| | Yjs（GC あり） | Yjs（GC なし） | Automerge |
| --- | --- | --- | --- |
| 1 打鍵の更新の平均 | 11.9 バイト | 11.9 バイト | 107.8 バイト |
| 2000 文字を打った後の保存形式 | 2011 バイト | 2011 バイト | 256 バイト |
| 1333 文字を消した後（見えるのは 666 文字） | 6404 バイト | 7738 バイト | 3007 バイト |

Yjs の保存形式は `encodeStateAsUpdate`、Automerge は `save()` の大きさです。Automerge の 2000 個の変更を個別に並べると、合計 215,739 バイトでした。

数字から読めることは 3 つあります。

**連続した入力はまとまる。** Yjs は 2000 文字を打った後、内部の構造体が 1 個でした。同じクライアントが続けて挿入した文字は、時計を 1 文字ずつ進めながらも 1 つの Item にまとめます（[INTERNALS.md](https://github.com/yjs/yjs/blob/main/INTERNALS.md)）。Automerge の `save()` は、変更と操作を列ごとに並べてランレングス符号化する形式で（[Automerge のバイナリ形式](https://automerge.org/automerge-binary-format-spec/)）、個別の変更の合計 215,739 バイトが 256 バイトになりました。1 打鍵ずつ送るときの大きさと、保存したときの大きさは大きく違います。

**削除で増える。** 1333 文字を消すと、Yjs の構造体は 896 個に割れました。消えた範囲と残った範囲が交互に並び、それぞれが自分の ID と隣の ID を持つからです。見える文字は 3 分の 1 になったのに、保存形式は 2011 バイトから 6404 バイトに増えました。

**GC が捨てるのは中身だけ。** Yjs の GC を有効にすると、消えた Item の中身は捨てられ（[INTERNALS.md](https://github.com/yjs/yjs/blob/main/INTERNALS.md)）、手元でも 448 個の Item が `ContentDeleted` に置き換わりました。それでも Item そのものは残り、差は 7738 バイトと 6404 バイトでした。並び順の手がかりとして、ID と隣の情報は捨てられないのです。Automerge は**全履歴を保存する**設計で（[Automerge のバイナリ形式](https://automerge.org/automerge-binary-format-spec/)）、過去の版に戻れる代わりに、消したものも履歴に残ります。

墓標を本当に消すには、「その文字を指す操作がもう誰からも届かない」と全員が合意している必要があります。Shapiro らの報告も、メタデータが際限なく育つ型があり、その回収には弱い形の同期が要ると書いています（[Shapiro ほか, 2011](https://inria.hal.science/inria-00555588)）。CRDT は「調整なしで合わせられる」のが売りですが、**片付けには調整が要る**ということです。

## 実際の使われ方

| 例 | 方式 | 確認した出典 |
| --- | --- | --- |
| Google Docs | 中央サーバの revision log と OT。クライアントは確認待ちの変更を 1 つしか送らない | [Google Drive Blog, 2010](https://drive.googleblog.com/2010/09/whats-different-about-new-google-docs.html) |
| Figma | CRDT に着想を得たが「真の CRDT ではない」。文書を `(オブジェクト ID, プロパティ, 値)` の集まりとみなし、サーバが中央の権威で、プロパティごとに LWW、子の並び順は 0 と 1 の間の分数で表す（fractional indexing） | [Figma Blog, 2019](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/) |
| Yjs | YATA による CRDT。更新は可換・結合・冪等で、通信路を選ばない | [Yjs Docs](https://docs.yjs.dev/api/document-updates) |
| Automerge | JSON 風の文書の CRDT。全履歴を列形式で圧縮して保存する | [Automerge のバイナリ形式](https://automerge.org/automerge-binary-format-spec/) |
| Redis Software の Active-Active | 地理的に離れた複数のクラスタに同時に書ける。CRDT とベクタクロックで収束させ、集合は OR-Set の振る舞い（観測した要素だけを消し、ほかは追加が勝つ） | [Redis Docs](https://redis.io/docs/latest/operate/rs/databases/active-active/)、[Sets](https://redis.io/docs/latest/operate/rs/databases/active-active/develop/data-types/sets/) |
| Riak KV | カウンタ、集合、マップ、レジスタ、フラグを CRDT に基づくデータ型として持つ | [Riak Docs](https://docs.riak.com/riak/kv/latest/developing/data-types/index.html) |

Figma の説明は、この回の整理によく合っています。CRDT は最終的な状態を決める単一の権威がない分散システムのための設計であり、Figma はサーバが中央の権威なので、その分の仕組みを削って速く軽くできた、と書いています。オフラインの間の編集は、戻ったときに最新の文書を取り直し、その上に適用し直します（[Figma Blog](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)）。

反対の端にあるのが、Ink & Switch の**ローカルファースト**の考え方です（[Kleppmann ほか, Onward! 2019](https://doi.org/10.1145/3359591.3359737)）。論文は、待たされないこと、1 つの端末に閉じ込められないこと、ネットワークは任意であること、共同作業ができること、長く残ること、既定で安全で私的であること、利用者が最終的な所有権を持つこと、の 7 つを理想に掲げ、それを支える基盤として CRDT を挙げています。データの正本を手元に置き、サーバは複製の 1 つとして扱う、という立場です。

## どれを選ぶか

| 条件 | 向いている方式 |
| --- | --- |
| 必ずサーバを経由し、オフラインは短い | 中央サーバの OT、またはサーバを権威にした LWW と CRDT の部品（Figma の形） |
| 長いオフラインがある、端末同士で直接同期する | CRDT |
| 1 つの値を上書きすれば済む | 細かい単位の LWW |
| 数や集合を、地理的に離れた場所で同時に更新する | カウンタや OR-Set などの CRDT 型を持つデータベース |

サーバがある以上、順序をサーバに決めさせるのが最も単純です。前回のゲームの同期も、Google Docs も、Figma もその形でした。OT の transform が難しいといっても、2 者間の TP1 だけで済み、文書は必要な分しか膨らみません。

CRDT が必要になるのは、**順序を決める者がいない**ときです。端末同士で直接つながる（第 77 回、第 78 回）、何日もオフラインのまま書く、複数のデータセンタがそれぞれ書き込みを受ける、といった場面です。その代わりに次の費用を払います。

- 文字ごとの ID、墓標、全履歴などのメタデータ。手元の測定では、見える 666 文字に対して Yjs で 6404 バイトだった
- 墓標を回収するための、全員の合意
- 収束はするが、交錯や意図しない並び順のように、人が見て不自然な結果になることがある
- 権限の確認や不正な操作の拒否は、権威がいないと難しい。サーバを権威として残す形が多いのは、このためでもある

## まとめ

- 共同編集では、各自が手元の複製に先に書くので、並行な変更が必ず生まれる。求められるのは、すぐ反映すること、収束すること、意図を保つこと
- 文書全体の LWW は他人の変更を黙って消し、位置で表した操作は他人の挿入や削除でずれる
- OT は、相手の操作に合わせて位置を直す transform で合わせる。並行な 2 操作で TP1、3 操作以上で TP2 を満たす必要があり、正しい transform を作るのは難しい
- Jupiter と Google Docs は、サーバが 1 本の順序を決め、クライアントとサーバの 2 者間で変換する。クライアントは確認待ちの変更を 1 つしか送らない
- CRDT は、どの順序で何回受け取っても同じ結果になるように型を作る。状態ベースでは merge が半束の最小上界（可換・結合・冪等）、操作ベースでは因果順の配送と可換な操作が条件
- 比較に使う時刻やタグは一意でなければならない。手元の LWW-Register は、同じ `(時刻, ID)` を 2 回使っただけで 200 回中 7 回分かれた
- ベクタクロックは因果の前後と並行を判定し、版ベクタとして足りない差分を求めるのにも使える
- 文字列の CRDT は、文字に一意の ID を振り、挿入を ID で指す。削除は墓標として残る。RGA は後ろから打つと文字単位で交錯しうる（Automerge で再現、Yjs では起きなかった）
- メタデータは削除で増え、GC で捨てられるのは中身だけ。墓標を回収するには調整が要る
- 中央のサーバがあるなら、サーバに順序を決めさせるのが単純。順序を決める者がいないとき、CRDT が要る

この回で見た同期は、変更を操作の単位で知っていることが前提でした。打鍵ごとに「何をしたか」が分かれば、送るものは小さくて済みます。では、変更の記録がなく、2 つの場所に少しだけ違う大きなファイルがあるとき、違う部分だけを見つけて送るにはどうするか。次回は、rsync のローリングチェックサム、内容で区切るチャンク分割、Merkle 木を見ます。
