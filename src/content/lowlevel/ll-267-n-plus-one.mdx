## 1 本ずつは速いのに

第 266 回では、1 本のクエリを索引で速くしました。ところが、スロークエリログを合計時間で並べたとき、上位に来るのが **1 回あたり 0.1 ms もかからないクエリ** であることがあります。1 回は速いのに、回数が桁違いに多いのです。

その多くは、次の形をしています。

```go
items := query("SELECT * FROM items ORDER BY created_at DESC LIMIT 50")   // 1 回
for _, item := range items {
    seller := query("SELECT * FROM users WHERE id = ?", item.SellerID)   // 50 回
}
```

一覧を 1 回引き、その N 行それぞれについてもう 1 回ずつ引くので、合わせて N+1 回のクエリになります。これを **N+1 問題** と呼びます。1 行ごとに引くものが 2 種類あれば 2N+1 回、3 種類あれば 3N+1 回です。

コードの上では、1 行ごとのクエリは「出品者を取ってくる関数」の中に隠れていて、ループの中でクエリを流しているようには見えません。1 回分は索引で引くので、スロークエリログに 1 回ずつ記録しても遅くは見えません。それでも、1 回のリクエストの中で 151 回データベースと往復していれば、その往復の時間がそのままリクエストの時間になります。

この回では、N+1 の直し方を並べ、手元で **往復の回数** と **1 往復の時間** を変えながら測ります。

| 直し方 | クエリの数（一覧 50 件） | 考え方 |
| --- | --- | --- |
| そのまま（N+1） | 151 | 行ごとに出品者、カテゴリ、親カテゴリを 1 回ずつ引く |
| 行ごとの問い合わせを並列に | 151 | 回数はそのままで、待ち時間を重ねる |
| JOIN | 1 | 1 本の SQL で結合して引く |
| IN でまとめる + マスタを手元に | 2 | 出品者は ID を集めて 1 回で引き、カテゴリはアプリケーションの中の表から引く |

## N+1 の形

ISUCON9 予選は、椅子のフリーマーケットのアプリケーションでした。新着の商品一覧の参照実装（Go）は、商品を 1 回引いた後、次のように 1 件ずつ出品者とカテゴリを引いていました（[isucon9-qualify webapp/go/main.go](https://github.com/isucon/isucon9-qualify/blob/master/webapp/go/main.go)）。

```go
for _, item := range items {
    seller, err := getUserSimpleByID(dbx, item.SellerID)
    ...
    category, err := getCategoryByID(dbx, item.CategoryID)
    ...
}

func getCategoryByID(q sqlx.Queryer, categoryID int) (category Category, err error) {
    err = sqlx.Get(q, &category, "SELECT * FROM `categories` WHERE `id` = ?", categoryID)
    if category.ParentID != 0 {
        parentCategory, err := getCategoryByID(q, category.ParentID)
        ...
    }
    return category, err
}
```

`getCategoryByID` は、親カテゴリがあれば自分自身を呼んで親も引きます。子カテゴリの商品なら、1 件につき出品者で 1 回、カテゴリで 2 回、合わせて 3 回です。一覧の 1 回と合わせて 3N+1 回になります。講評も「初期状態ではデータベースのインデックスが不足していたり、カテゴリ、出品者、購入者とわかりやすいN+1がありました。」と書いています（[ISUCON9 予選 問題の解説と講評](https://isucon.net/archives/53789931.html)）。

ISUCON14 の講評は、近くの椅子を探す API について「各リクエストごとにすべての椅子を取得して最新のライド情報と位置情報からレスポンスに含めるかどうかをチェックするような、 2N+1回DBにクエリされる処理になっていました。」と書いています（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。こちらは N が「表示する件数」ではなく「全部の椅子」なので、データが増えるほど回数も増えます。

## 実験の環境

ISUCON9 予選の形をまねた表を作りました。

| 表 | 行数 | 内容 |
| --- | --- | --- |
| `categories` | 43 | 親カテゴリ 7、子カテゴリ 36。商品はすべて子カテゴリに属する |
| `users` | 4,000 | 出品者 |
| `items` | 50,000 | 商品。`(created_at, id)` に索引 |

| 項目 | 内容 |
| --- | --- |
| マシン | Apple M1 Pro、macOS、Docker Engine 29.4.0（VM に 8 CPU） |
| データベース | `mysql:8.4` イメージ（MySQL 8.4.13）、設定は既定のまま |
| クライアント | Go 1.24.6、go-sql-driver/mysql v1.10.1。DSN に `interpolateParams=true`（第 268 回で扱う） |
| ネットワーク | MySQL と同じ Docker のブリッジネットワークに置いたクライアントのコンテナから TCP で接続 |

同じコンテナの中、同じマシンの中では、1 往復はとても短くなります。手元では `SELECT 1` の 1 往復が中央値 0.017 ms でした。本番では、アプリケーションとデータベースは別のマシンにあり、1 往復には物理的なネットワークと、両方のマシンのカーネルを通る時間が加わります。別のゾーンやリージョンにあれば、距離の分さらに長くなります。

そこで、クライアントのコンテナのネットワークに **人工的な遅延** を足しました。Linux の `tc` コマンドで、送信するパケットを一定時間だけ遅らせる netem という仕組みを使います（[tc-netem(8)](https://man7.org/linux/man-pages/man8/tc-netem.8.html)）。

```bash
# クライアントのコンテナ（NET_ADMIN 権限付き）の中で
tc qdisc add dev eth0 root netem delay 1ms    # 送るパケットを 1 ms 遅らせる
ping -c 20 -i 0.2 -q tune-267-mysql           # 往復の時間を確かめる
tc qdisc del dev eth0 root                     # 元に戻す
```

クライアントが送るパケットだけが遅れるので、1 往復あたり、ほぼ足した遅延の分だけ長くなります。

<Callout type="warn" title="同じマシンで他の負荷が動いていた">
  計測の間、同じマシンの上で別の Docker コンテナがいくつも動いていて、ホストの load average は 30〜120 で推移していました。
  遅延を足すと、`ping` の平均が設定値より長く出る（1 ms を足して平均 1.8 ms など）ことがありました。タイマーの割り込みが混み合うと、遅らせたパケットを送り出すのも遅れるためと考えられます。
  時間の値は揺れが大きいので、中央値と最小値を並べ、桁と比率を見ます。クエリの数は MySQL の `Questions` の増分から数えていて、負荷に左右されません。
</Callout>

## 4 つの書き方

計測用のプログラムでは、同じ「新着 50 件と、その出品者・カテゴリ・親カテゴリ」を 4 通りに組み立て、結果が一致することを確かめてから時間を測りました。

**そのまま（N+1）。** ISUCON9 予選の参照実装と同じ形です。

```go
items := latestItems(n)                          // 1 回
for _, it := range items {
    v := View{Item: it}
    v.Seller = getUser(it.SellerID)              // N 回
    v.Category = getCategory(it.CategoryID)      // N 回
    v.Parent = getCategory(v.Category.ParentID)  // N 回
    out = append(out, v)
}
```

**JOIN。** 1 本の SQL で、商品、出品者、カテゴリ、親カテゴリを結合します。結合のやり方そのものは、第 102 回で見ました。ここでは、`EXPLAIN FORMAT=TREE` で見ると、オプティマイザは商品の索引 `idx_created` を逆向きに読んで新しい順に 50 行を取り、それぞれについて主キーで `categories`（2 回）と `users` を 1 行ずつ引く Nested Loop を選んでいました。中でやっていることは N+1 とほとんど同じですが、**それがデータベースの中で起きるので、ネットワークの往復は 1 回** です。

```sql
SELECT i.id, i.seller_id, i.category_id, i.name, i.price, i.created_at,
       u.id, u.account_name, c.id, c.parent_id, c.name, p.id, p.parent_id, p.name
FROM items i
JOIN users u      ON u.id = i.seller_id
JOIN categories c ON c.id = i.category_id
JOIN categories p ON p.id = c.parent_id
ORDER BY i.created_at DESC, i.id DESC LIMIT ?
```

**IN でまとめる + マスタを手元に。** 一覧を引いた後、出品者の ID を重複を除いて集め、`WHERE id IN (...)` で 1 回で引いて、ID から引ける表（Go の `map`）にします。カテゴリは 43 行しかなく、競技の間に変わらないので、起動時に全部読んでアプリケーションの中に持っておきます。クエリは一覧と出品者の 2 回です。

```go
items := latestItems(n)                       // 1 回
ids := uniqueSellerIDs(items)
q := "SELECT id, account_name FROM users WHERE id IN (?" + strings.Repeat(",?", len(ids)-1) + ")"
rows, _ := db.QueryContext(ctx, q, ids...)    // 1 回
users := map[int]User{}                        // id → User
...
for _, it := range items {
    c := masterCats[it.CategoryID]             // 起動時に読んだ表から引く。クエリなし
    out = append(out, View{Item: it, Seller: users[it.SellerID], Category: c, Parent: masterCats[c.ParentID]})
}
```

**並列に。** N+1 のまま、商品ごとの問い合わせをゴルーチンで同時に流します。クエリの数は変わりません。比較のために入れました。

N+1 の中央値をクエリの数 151 で割って、`SELECT 1` の 1 往復と並べます。

| 足した遅延 | `SELECT 1` 1 往復（中央値） | N+1 全体（中央値） | N+1 全体 ÷ 151 | JOIN（中央値） | IN + マスタ（中央値） |
| --- | --- | --- | --- | --- | --- |
| 0 | 0.017 ms | 9.95 ms | 0.066 ms | 0.43 ms | 0.39 ms |
| 0.5 ms | 1.058 ms | 220.6 ms | 1.461 ms | 2.10 ms | 2.79 ms |
| 1 ms | 2.137 ms | 415.0 ms | 2.749 ms | 2.43 ms | 3.78 ms |
| 2 ms | 2.792 ms | 448.1 ms | 2.967 ms | 2.52 ms | 4.94 ms |

読み取れることを 3 つ挙げます。

**N+1 の時間は、ほぼ「151 × 1 往復の時間」になっている。** 遅延を足した 3 つの条件で、N+1 全体を 151 で割った値は、`SELECT 1` の 1 往復の時間と同じ桁で、近い値です。1 回ずつのクエリは主キーで 1 行引くだけなので、データベースの中の仕事はほとんどありません。時間のほとんどは往復の待ちです。

**JOIN と IN は、往復の回数どおりに 1 往復、2 往復ぶんになっている。** 2 ms を足したとき、JOIN は 2.5 ms、IN は 4.9 ms で、どちらも往復の回数 × 約 2.5 ms です。JOIN と N+1 の差は、遅延 0 では 23 倍でしたが、1 ms を足すと 170 倍になりました。

**遅延が 0 でも、N+1 は 20 倍以上遅い。** 同じマシンの中でも、1 回のクエリには、ドライバがパケットを組み立て、カーネルを通って送り、MySQL がパースして実行し、結果を返して受け取る、という固定の手間がかかります。その固定の手間が 151 回かかります。

1 往復の時間は、アプリケーションのコードをいじらなくても、置き場所で変わります。手元で 0.017 ms だった往復は、別のマシンをネットワーク越しにつなげば長くなり、ゾーンをまたげばさらに長くなります。**手元では気にならなかった N+1 が、本番で急に遅くなる** のはこのためです。

### N を増やすと

遅延 1 ms のまま、一覧の件数 N を 10、50、200 と変えました。

| N | N+1 のクエリ数 | N+1（中央値） | JOIN（中央値） | IN + マスタ（中央値） |
| --- | --- | --- | --- | --- |
| 10 | 31 | 89.3 ms | 3.06 ms | 6.31 ms |
| 50 | 151 | 433.5 ms | 1.88 ms | 5.97 ms |
| 200 | 601 | 1,529.0 ms | 2.85 ms | 3.84 ms |

N+1 は N に比例して伸び、200 件で 1.5 秒になりました。JOIN と IN は、N を増やしても往復の回数が変わらないので、ほとんど変わりません。200 件の IN は、出品者 197 人の ID を 1 本の `IN` に並べています。

### 並列にすれば速くなるが

並列に流す版は、遅延を足した 3 つの条件で、N+1 のまま 15〜22 倍速くなっています。150 回の待ちを重ねて、全体の待ちを数回分に縮めたからです。ISUCON11 本選の講評にも、成績の取得で N+1 が残る部分について「AとBを並列化する程度が妥協点ではないでしょうか。」という書き方があります（[ISUCON11 本選 問題の解説と講評](https://isucon.net/archives/56163308.html)）。

しかし、並列にしても **データベースが受けるクエリの数は 151 のまま** です。そして、同時に 50 本の問い合わせを流すには、接続も同時に 50 本要ります。この実験のプログラムはプールの上限を 64 本にしていました。上限がもっと小さければ、問い合わせは空いた接続を待つことになります（第 268 回）。遅延 0 の条件では、並列にした版のほうが中央値で遅くなりました。ゴルーチンと接続の取り合いの手間が、待ちを重ねる効果を上回ったためです。

並列化は、往復の回数を減らせないとき（外部の API を 1 件ずつしか呼べないときなど）の手段です。データベースのクエリなら、先に回数を減らします。

## データベースの負担

時間のほかに、N+1 はデータベースの CPU を使います。16 個のゴルーチンから同時に一覧のリクエストを 5 秒間流し続け、1 秒あたりのリクエスト数と、MySQL が受けたクエリ数を数えました（遅延 0）。3 回測ったところ、他の負荷の影響で値は大きく揺れたので、範囲で示します。

| 書き方 | リクエスト / 秒 | クエリ / 秒 |
| --- | --- | --- |
| N+1 | 46〜402 | 6,916〜60,763 |
| N+1 を並列に | 49〜479 | 7,460〜72,359 |
| JOIN | 1,280〜5,485 | 1,280〜5,485 |
| IN + マスタ | 162〜5,151 | 325〜10,301 |

```
N+1 (3N+1)             N=50   conc=16  req/s    402.4  queries/s   60762.6
N+1 parallel           N=50   conc=16  req/s    479.2  queries/s   72359.4
JOIN                   N=50   conc=16  req/s   5485.2  queries/s    5485.4
IN + master in memory  N=50   conc=16  req/s   5150.6  queries/s   10301.4
```

上はいちばん負荷の軽かった 3 回目の出力です。N+1 は、MySQL に毎秒 6 万回のクエリを処理させて、毎秒 400 リクエストしか返せていません。JOIN は毎秒 5,500 回のクエリで、毎秒 5,500 リクエストを返しています。同じ答えを返すのに、データベースの仕事が 10 倍以上違います。

並列化した N+1 は、ここでもクエリの数が変わらないので、リクエストの数はほとんど伸びません。データベースの CPU が先に詰まる状況では、並列化は効きません。

## ISUCON での例

N+1 は、過去の問題でほぼ毎回出題されています。

- **ISUCON9 予選**（フリーマーケット）: 上で見た商品一覧。講評は直し方として、「カテゴリについては更新がありませんでしたので、ソースコードに直接書いたチームが多かったと思われます。」「出品者・購入者についてはJOINで取得するか、必要なユーザ情報をIN句を使い一気に取得してアプリケーションの中でデータを保管するなどの方法でアプローチしたチームが多かったようです。」と書いています。この回の実験の「IN + マスタ」の組み合わせです
- **ISUCON9 本選**（新幹線の予約）: 「初期実装では、列車の発着時間や料金、空席状況を1列車毎にN+1のクエリで取得しています。」。総評は「今回のアプリケーションはSQLクエリ一つ一つの実行時間は長くないものの、とにかくクエリ数が多いような問題としました。」と書いています（[ISUCON9 本選 問題の解説と講評](https://isucon.net/archives/53916974.html)）
- **ISUCON10 予選**（不動産検索）: なぞって検索で、長方形で絞った物件を 1 件ずつ多角形の中か確かめる N+1。第 266 回で見た空間インデックスで、SQL 1 回にまとめられます（[ISUCON10 予選 問題の解説と講評](https://isucon.net/archives/55025156.html)）
- **ISUCON11 本選**（履修管理）: 履修科目のループの中に講義のループがあり、その中でさらにクエリを流す、入れ子の N+1。講評は、全部を SQL にまとめるのは難しい部分を並列化で妥協する案も示しています
- **ISUCON13**（ライブ配信）: 「SQLの実行結果に対してデータを付与していく fill*Response (Go言語の場合)関数があり、何度も使われています。これらの中、さらにはそこから呼び出された関数の中でSQLが実行され、N+1 クエリとなっています。」。講評は解消の方法として、書籍「達人が教えるwebパフォーマンスチューニング: isuconから学ぶ高速化の実践」に従い、JOIN、別のクエリでのプリロード、キャッシュの 3 つを挙げています（[ISUCON13 問題の解説と講評](https://isucon.net/archives/58001272.html)）
- **ISUCON14**（ライドシェア）: 上で見た 2N+1。講評は「これらの処理はうまくクエリを構成することで1回のDB問い合わせで結果を得ることができます。」と書いています

ISUCON13 の `fill*Response` の形は、本番のコードでもよく見ます。「1 件の行を受け取って、応答の形に組み立てる関数」は、1 件の画面を作るときには自然な部品です。それを一覧の画面で行ごとに呼ぶと、組み立ての中のクエリが N 倍になります。部品の中にクエリが隠れているので、呼ぶ側からは見えません。

### 「それぞれの最新の 1 件」をまとめて引く

ISUCON14 の 2N+1 は、椅子ごとに「最新の位置」と「最新のライドの状態」を 1 回ずつ引いていました。「ある利用者の最新の注文」「ある機器の最新の記録」のように、**親ごとに子の最新の 1 件** がほしい場面は多く、ループの中で `ORDER BY created_at DESC LIMIT 1` を流す N+1 になりがちです。

講評が示した 1 回にまとめる例は、ウィンドウ関数 `row_number()` を使っています。要点だけ抜き出すと、次の形です。

```sql
-- 椅子ごとに、位置の記録を新しい順に番号を振り、1 番だけを残す
WITH near_chairs AS (
  SELECT cl.*
  FROM (
    SELECT cl.*, row_number() over (partition BY chair_id ORDER BY created_at DESC) AS rn
    FROM chair_locations cl
  ) cl
  WHERE cl.rn = 1 AND abs(cl.latitude - ?) + abs(cl.longitude - ?) < ?
),
...
SELECT chairs.*, near_chairs.latitude, near_chairs.longitude
FROM chairs
INNER JOIN near_chairs ON chairs.id = near_chairs.chair_id
...
```

`partition BY chair_id` で椅子ごとに分け、その中を `created_at` の新しい順に並べて 1、2、3 と番号を振り、1 番だけを残します。これで「椅子ごとの最新の位置」が 1 本の SQL で手に入り、椅子の表と結合できます。

ただし、この形は位置の記録の表を全部読んで番号を振るので、記録が増えるほど重くなります。講評も後半で、「各椅子ごとに最新の位置情報と総走行距離を持つテーブルを作りUPSERTだけで管理できるようになり、ここでのクエリをはじめ様々なクエリをシンプルにすることができます。」と書いています。最新の値を、書き込みのときに別の表に持っておく方向です。N+1 を 1 本の SQL にまとめるのは第一歩で、そのクエリ自体が重くなったら、第 273 回の「先に計算しておく」に移ります。

## 直し方を選ぶ

JOIN と IN は、どちらも往復を 1〜2 回にします。どちらを選ぶかは、まず結合の向きで決まります。

### 1 対多の結合では、JOIN は行が増える

商品と出品者は「多対 1」なので、JOIN しても行の数は商品の数のままです。ところが「投稿と、その投稿についたコメント全部」のような 1 対多を JOIN すると、投稿の列がコメントの数だけ繰り返されて返ってきます。コメントが 100 件ある投稿は 100 行になり、投稿の本文が 100 回送られます。

手元で確かめました。本文 2,000 バイトの投稿 1,000 件に、100 バイトのコメントを 100 件ずつ（合計 10 万件）付け、新しい投稿 50 件とそのコメント全部を取り出します。

```sql
-- JOIN: 1 往復
SELECT p.id, p.title, p.body, c.id, c.body
FROM (SELECT * FROM posts ORDER BY created_at DESC LIMIT 50) p
JOIN comments c ON c.post_id = p.id
ORDER BY p.created_at DESC, c.id;

-- 投稿を引いてから、コメントを IN で: 2 往復
SELECT id, title, body FROM posts ORDER BY created_at DESC LIMIT 50;
SELECT id, post_id, body FROM comments WHERE post_id IN (?, ?, ...) ORDER BY post_id, id;
```

MySQL がクライアントに送ったバイト数を、`Bytes_sent` の増分から数えました。

```
## delay 0
JOIN (1 query)           posts 50 comments 5000  bytes/req  10634882  median   42.259 ms
posts + IN (2 queries)   posts 50 comments 5000  bytes/req    675883  median    6.632 ms
## delay 1ms
JOIN (1 query)           posts 50 comments 5000  bytes/req  10634882  median   55.843 ms
posts + IN (2 queries)   posts 50 comments 5000  bytes/req    675883  median   16.357 ms
```

同じ 50 件の投稿と 5,000 件のコメントを受け取るのに、JOIN は 10.6 MB、IN は 0.68 MB を送っていて、16 倍違います。JOIN の 5,000 行のそれぞれに、2,000 バイトの投稿の本文が載っているからです。往復が 1 回少ないはずの JOIN のほうが、遅延 1 ms を足しても 3 倍以上遅くなりました。**往復の回数を減らすのは、送る量を増やさない範囲で** です。1 対多の関係は、親を引いてから子を IN で引き、アプリケーションで振り分けます。

### そのほかの注意

**IN は、ID の重複を除き、空のときを扱う。** 一覧の中に同じ出品者が何度も出るなら、ID の重複を除いてから並べます。一覧が空なら `IN ()` は SQL として不正なので、クエリを流さずに済ませます。`IN` に並べる数が数千を超えるなら、1 本の SQL が大きくなりすぎないよう、適当な数で分けます。分けても、往復の回数は N 回ではなく「N ÷ 1 回に並べる数」回です。

**IN は、返ってくる順番を保証しない。** `WHERE id IN (3, 1, 2)` の結果は、並べた順で返ってくるとは限りません。ID から引ける表（`map`）にしてから、元の一覧の順にたどります。

**変わらない表は、データベースに聞かない。** ISUCON9 予選のカテゴリのように、件数が少なく、動いている間に変わらない表（マスタ）は、起動時に全部読んでアプリケーションの中に持つか、ソースコードに書いてしまえます。往復は 0 回です。ただし、変わる表を手元に持つと、データベースとの食い違いを管理する必要が出ます。それは第 269 回で扱います。

**ORM を使っているなら、プリロードの機能を探す。** 多くの ORM は、関連する行を「後から 1 件ずつ」読む機能と、「まとめて先に」読む機能を持っています。前者は、関連のフィールドに触れたときに裏でクエリを流すので、N+1 がコードから見えにくくなります。後者は、この回の IN と同じことを ORM がやってくれるものです。どちらが既定なのかは、ORM ごとに確かめます。

<Callout type="tip" title="見つけるには、リクエストあたりのクエリ数を数える">
  N+1 は、1 回ずつの時間が短いので、スロークエリログを「1 回あたりの時間」で並べても上に来ません。第 264 回の pt-query-digest で **回数** の列を見て、アクセスログのリクエスト数の何倍流れているかを比べます。
  一覧のリクエストが 1,000 回に対して、`SELECT * FROM users WHERE id = ?` が 50,000 回流れていれば、1 リクエストあたり 50 回です。
  第 265 回のように SQL のコメントに呼び出し元やリクエスト ID を入れておけば、どのハンドラが何回流したのかを直接数えられます。
</Callout>

## 本番で使うとき

ISUCON では、アプリケーションとデータベースが同じマシンか、同じネットワークの隣のマシンにあります。本番では、往復の時間がもっと長くなりやすい要因がいくつもあります。

- データベースが別のゾーンにある。マネージドのデータベースでは、障害に備えてゾーンをまたぐ構成が普通です
- アプリケーションとデータベースの間に、プロキシやプーラー（第 106 回）が挟まる。1 段増えるごとに往復が長くなります
- TLS で接続を暗号化している

どれも 1 往復の時間を伸ばすので、N+1 の時間はその分だけ N 倍に伸びます。手元の開発環境で 10 ms だった画面が、本番では数百 ms になる、という形で現れます。

一方で、往復を減らすために、何でも 1 本の巨大な SQL にまとめる必要はありません。この回の実験でも、2 往復の IN と 1 往復の JOIN の差は 1〜2 ms でした。**N に比例して増える往復を、定数回にする** ことが目的で、1 回か 2 回かはたいてい問題になりません。読みやすさと、1 対多で行が増えないことを優先して選びます。

## 次の回へ

この回の実験では、プログラムの DSN に `interpolateParams=true` を付けていました。付けないと、Go の MySQL ドライバは 1 回のクエリのたびに「準備」と「実行」の 2 往復をします。N+1 を消した後にも、こうした目に見えない往復が残っています。次の第 268 回では、コネクションプール、プリペアドステートメント、参照だけのトランザクション、外部キー、ログといった、データベースとの往復と待ちに関わる設定を見ます。

## まとめ

- N+1 は、一覧を 1 回引いた後に行ごとにもう 1 回ずつ引く形。行ごとに引くものが 2 種類なら 2N+1、3 種類なら 3N+1 になる
- 1 回ずつのクエリは索引で速いので、スロークエリログを 1 回あたりの時間で並べても見つからない。回数とリクエスト数の比で見つける
- 手元の実験では、N+1 の全体の時間は「151 回 × 1 往復の時間」にほぼ一致した。遅延を 1 ms 足すと、N+1 は 415 ms、JOIN は 2.4 ms だった
- 遅延 0 でも N+1 は 20 倍以上遅い。1 回のクエリには、組み立て、送信、パース、受信の固定の手間がかかる
- N+1 の時間は N に比例し、200 件で 1.5 秒になった。JOIN と IN は N を増やしても往復の回数が変わらない
- 並列化すると待ちは重なるが、データベースが受けるクエリの数は変わらず、接続も同時に N 本要る。データベースの CPU が詰まっているときは効かない
- 同じ数のリクエストを返すのに、N+1 は JOIN の 10 倍以上のクエリをデータベースに処理させていた
- 直し方は、JOIN、IN でまとめて引いて `map` で振り分ける、変わらないマスタをアプリケーションに持つ、の 3 つ。ISUCON9 予選の講評はこの 3 つを組み合わせた解き方を挙げている
- 1 対多の JOIN は親の列がコメントの数だけ繰り返される。手元では JOIN が 10.6 MB、IN が 0.68 MB を送り、JOIN のほうが遅かった。IN は重複を除き、空の場合を扱い、返る順番に頼らない
- 本番では、ゾーンをまたぐ配置、プロキシ、TLS で 1 往復が長くなり、N+1 の時間はその N 倍で伸びる。目的は往復を N から定数回にすること
