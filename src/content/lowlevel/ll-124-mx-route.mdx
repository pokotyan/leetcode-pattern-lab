## 宛先のドメインしか知らない

前回は、SMTP の会話を 1 行ずつ手で話しました。ただし、そのとき接続先はこちらで決めていました。実際の MTA が受け取るのは、`RCPT TO` に書かれた `bob@example.net` という宛先だけです。

**`@` の右側のドメイン名から、どのホストの 25 番ポートにつなげばよいのか。** 第 58 回では、その答えが MX レコードにあることを 1 節だけ見ました。この回ではそこを掘り下げます。

見ていくのは、次の 3 つの問いです。

1. 送信側は MX の一覧を**どの順で、どこまで**試すのか。MX が無い、または「受けない」と書かれていたらどうするのか
2. 受信側は、つないできた相手が**何者か**をどう判断するのか。なぜ多くの受信側は逆引きのない IP を嫌うのか
3. なぜクラウドの仮想マシンから 25 番ポートにつなぐと、**黙って失敗する**のか

最後に、メールが通ってきた経路が `Received:` ヘッダにどう残るかを見ます。

## 接続先を決める手順

手順は [RFC 5321](https://www.rfc-editor.org/rfc/rfc5321.html) の 5.1 節に書かれています。SMTP の現行の仕様は 2008 年の RFC 5321 で、改訂版の草案（[draft-ietf-emailcore-rfc5321bis](https://datatracker.ietf.org/doc/draft-ietf-emailcore-rfc5321bis/)）は執筆時点（2026 年 9 月）でまだ RFC Editor の作業待ちです。以下は RFC 5321 に従います。

```
宛先 bob@example.net
        │
        ▼
  example.net の MX を引く
        │
        ├─ NXDOMAIN（ドメインが無い）  → エラーとして返す（5xx）
        ├─ 一時的な失敗（SERVFAIL 等）  → キューに戻して後で再試行（前回の 4xx と同じ扱い）
        ├─ MX が 1 つだけで、値が "."    → null MX。受けないドメイン（RFC 7505）
        ├─ MX が 0 個（名前はある）       → 暗黙の MX: example.net 自身を優先度 0 の MX とみなす
        └─ MX が 1 つ以上                 → 優先度の小さい順に並べ、同じ優先度はランダムに並べる
                │
                ▼
        各 MX の名前の A / AAAA を引き、アドレスの一覧を作る
                │
                ▼
        先頭から 25 番につなぐ。失敗したら次へ
```

ここで大事なのは、**DNS の失敗の種類によって扱いが分かれる**ことです。ドメインが存在しないのは確定した失敗なので送信者に返しますが、DNS サーバが一時的に答えられないだけなら、前回見た 4xx と同じくキューで待ちます。第 63 回で見た DNS の障害は、メールでは「すぐには失敗しないが、届くのが何時間も遅れる」という形で表に出ます。

### 優先度と、同じ優先度の間での分散

`gmail.com` の MX を引いてみます。

```
$ dig gmail.com MX +noall +answer
gmail.com.   2716  IN  MX  40 alt4.gmail-smtp-in.l.google.com.
gmail.com.   2716  IN  MX  10 alt1.gmail-smtp-in.l.google.com.
gmail.com.   2716  IN  MX  30 alt3.gmail-smtp-in.l.google.com.
gmail.com.   2716  IN  MX  20 alt2.gmail-smtp-in.l.google.com.
gmail.com.   2716  IN  MX  5  gmail-smtp-in.l.google.com.
```

第 58 回で引いたときとは**並び順が違います**。DNS サーバは答えの順番を毎回入れ替えて返すことがあり、並び順には意味がありません。**並べ替えるのは送信側の仕事**で、RFC 5321 5.1 は「優先度の数字が小さいほど優先」とし、並べ替えに使うことを MUST としています。

同じ優先度が複数ある場合はどうか。`yahoo.co.jp` は 4 つの MX がすべて優先度 10 です。

```
$ dig yahoo.co.jp MX +noall +answer
yahoo.co.jp.  900  IN  MX  10 mx3.mail.yahoo.co.jp.
yahoo.co.jp.  900  IN  MX  10 mx5.mail.yahoo.co.jp.
yahoo.co.jp.  900  IN  MX  10 mx1.mail.yahoo.co.jp.
yahoo.co.jp.  900  IN  MX  10 mx2.mail.yahoo.co.jp.
```

RFC 5321 は、同じ優先度の間でとくに片方を選ぶ理由がなければ、送信側は**ランダムに並べなければならない**（MUST randomize）としています。負荷を複数の MX に散らすためです。Postfix でもこれは既定の動作で、`smtp_randomize_addresses` の既定値は `yes` です（[postconf(5)](https://www.postfix.org/postconf.5.html#smtp_randomize_addresses)）。

つまり MX の優先度は、**「違う数字は予備の順番、同じ数字は負荷分散」**という 2 つの意味を持ちます。Gmail は予備の列を、Yahoo! JAPAN や iCloud（`mx01` と `mx02` がともに 10）は分散を選んでいる、と読めます。

### どこまで試すか

1 つの MX の名前が、さらに複数のアドレスを持つこともあります。`gmail-smtp-in.l.google.com` は手元で A と AAAA を 1 つずつ返しました。RFC 5321 はこれを**マルチホーム**と呼び、送信側は一覧の順に試す能力を持たなければならない（MUST）、ただし試す数には上限を設けてもよい、少なくとも 2 つは試すべき（SHOULD）、としています。

Postfix の既定値では、MX から得るアドレスは 5 つまで（`smtp_mx_address_limit = 5`）、1 回の配送で実際に SMTP のセッションを張るのは 2 つまで（`smtp_mx_session_limit = 2`）です（[postconf(5)](https://www.postfix.org/postconf.5.html#smtp_mx_address_limit)）。全部の MX に届かなければ、メールはキューに戻り、前回見た再送の間隔で後からやり直されます。

## MX が無いとき: 暗黙の MX

MX が 1 つも無いドメインにも、メールは届けられます。RFC 5321 5.1 は、MX の一覧が空なら、**そのドメイン自身を優先度 0 の MX として扱う**と決めています。これを**暗黙の MX**（implicit MX）と呼びます。

```
$ dig neverssl.com MX +noall +comments +authority
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 12906
neverssl.com.  900  IN  SOA  ns-1716.awsdns-22.co.uk. awsdns-hostmaster.amazon.com. ...

$ dig neverssl.com A +short
34.223.124.45
```

`NOERROR` で答えが空（第 60 回で見た NODATA）なので、名前はあるが MX は無い、という状態です。送信側は `neverssl.com` の A を引き、`34.223.124.45` の 25 番につなぎに行きます。

これは、MX という型が生まれる前（1986 年の [RFC 974](https://www.rfc-editor.org/rfc/rfc974.html) より前）のメールがホスト名に直接届けられていた名残です。互換のために残された規則ですが、今では困った副作用があります。

**Web サーバしか置いていないドメインにも、メールが「届けられようとする」**のです。書き間違えた宛先や、迷惑メールが差出人として勝手に使ったドメインへのバウンスが、Web サーバの 25 番に向かいます。Web サーバは 25 番で待っていないので接続は失敗しますが、送信側から見ると「相手が一時的に落ちている」のと区別がつきません。メールはキューに残り、**諦めるまで何日も再送が続きます**。送った人が「届かなかった」と知るのも、その何日か後です。

<Callout type="warn" title="よくある誤解: MX を書かなければ、メールは来ない">
  MX を書かないことは「受けない」という意味になりません。暗黙の MX の規則により、送信側は A や AAAA のアドレスに配送を試みます。
  メールを受けないドメインでは、次の null MX で**はっきり断る**のが正しい書き方です。
</Callout>

## メールを受けないと宣言する: null MX

この問題への答えが **null MX** です（[RFC 7505](https://www.rfc-editor.org/rfc/rfc7505.html), 2015 年）。優先度 0、値が `.`（長さ 0 のラベル、つまり DNS の根）の MX を **1 つだけ**置きます。

```
$ dig example.com MX +noall +answer
example.com.  300  IN  MX  0 .

$ dig example.net MX +short
0 .
```

`example.com` と `example.net`、`example.org` は、いずれも null MX を置いています。例示用のドメインなので、ここ宛てに書かれたメールが本当に送られても、どこかのサーバに届いては困るからです。

`.` はホスト名として正しくないので、普通の MX と取り違えることはありません。SRV レコードで `.` が「このサービスは無い」を意味するのにならった書き方です（RFC 7505 3 節）。null MX を置くドメインは、**ほかの MX を置いてはいけません**（MUST NOT）。

null MX を見た送信側は、キューに入れずに**その場で失敗を返せます**。RFC 7505 4.1 節は、そのときの応答として 556 と拡張ステータスコード `5.1.10`（宛先のアドレスが null MX を持つ）を使うべきだとしています。前回見た応答コードの続きで言えば、「一時的な 4xx で待つ」のではなく、「恒久的な 5xx で諦める」に一瞬で切り替わるわけです。

| 状態 | 送信側の動き | 送った人が失敗を知るまで |
| --- | --- | --- |
| MX が無く、A に 25 番が無い | 一時的な失敗として再送を続ける | 諦めるまで（数日） |
| null MX | その場で 556 `5.1.10` | すぐ |

null MX には、差出人の側の意味もあります。RFC 7505 4.1 節は、`MAIL FROM` や `From:` のドメインが null MX を持つメールを受信側が拒否してよく、そのときは 550 と `5.7.27` を使うべきだとしています。**返事の届かない差出人は、迷惑メールの典型**だからです。逆に言えば、自分が送信に使うドメインに null MX を置いてはいけません（4.2 節、SHOULD NOT）。

メールを送りも受けもしないドメインなら、null MX と、SPF の `-all`（このドメインを名乗って送ってよいサーバは無い。第 127 回）を組み合わせます。`example.com` の TXT を引くと、実際に `"v=spf1 -all"` が置かれています。

## MX の名前に CNAME を書けない

第 58 回で、「NS と MX の値に別名（CNAME）を書いてはいけない」という規則を見ました（[RFC 2181](https://www.rfc-editor.org/rfc/rfc2181.html) 10.3 節）。RFC 5321 5.1 もこれを受けて、MX の値の名前を引いたら**アドレスのレコード（A か AAAA）が返らなければならない**、CNAME が返る値は「この標準の範囲外」だ、としています。

```
example.net.       MX     10 mail.example.net.     ← 値は、A/AAAA を直接持つ名前
mail.example.net.  A      192.0.2.25               ← よい

example.net.       MX     10 mx.example.net.
mx.example.net.    CNAME  mail.provider.example.   ← 書いてはいけない
```

RFC 2181 が挙げる理由は、DNS の応答の作り方にあります。MX を問い合わせると、権威サーバは MX の値の名前の **A レコードを追加部に付けて**返します（第 57 回で見た応答の追加部）。送信側は、これで 2 回目の問い合わせを省けます。ところがこの追加の処理は CNAME をたどりません。値が別名だと、アドレスが付かずに返り、**毎回余分な問い合わせ**が発生します。管理者が一度だけ別名の先を調べて直接書けば避けられることなので、書くな、と決めてあるわけです。

もう 1 つ、MX の値はメールサーバ**自身の名前**として照合にも使われます。RFC 5321 5.1 の後半は、中継するサーバが MX の一覧から自分の名前やアドレスを探し、自分と同じかそれより劣る優先度の候補を捨てる、という手順を定めています。予備の MX が本命より劣る MX へメールを戻して、メールが行き来するのを防ぐためです。

なお、禁止されているのは **MX の値**に別名を書くことです。宛先のドメインそのものが CNAME なら、その先の名前を最初の名前として扱います（RFC 5321 5.1）。

## バックアップ MX は抜け道になる

優先度の違う MX を並べるのは、もともと**本命の MX が落ちている間、別の組織のサーバに預かってもらう**ためでした。

```
example.net.  MX  10 mx.example.net.            本命（自社）
example.net.  MX  50 backup.partner.example.     予備（取引先や ISP）
```

予備のサーバは、本命が戻るまでメールをキューに溜め、戻ったら中継します。本命が数時間止まっても、送信側から見るとメールは受け取られているので、送った人の手元でキューが詰まることはありません。

ところが、迷惑メールを送る側はここを狙います。**優先度を無視して、わざと予備の MX に送る**のです。本命の MX が迷惑メールの判定をしっかり行っていても、予備の MX は次のような事情で甘くなりがちです。

- 予備は別の組織が運用していて、本命と同じ判定の仕組みやブロックリストを持たない
- 予備は**宛先が実在するかを知らない**ことが多く、どんな宛先でも受け取ってしまう
- 本命は「予備から来たメール」を信頼して、判定を緩めることがある

2 つ目は、とくに厄介です。予備が実在しない宛先を受け取り、あとで本命に拒否されると、予備は**差出人に宛ててバウンスを送ります**。差出人は迷惑メールが偽って書いた他人のアドレスなので、無関係な人にバウンスが大量に届きます。これを**バックスキャッタ**（backscatter）と呼びます。

Postfix の設定例は、予備の MX を引き受けるなら `relay_recipient_maps` で**有効な宛先の一覧**を持たせるよう求めています。そうしないと、キューが配送不能のバウンス（`MAILER-DAEMON` のメッセージ）で埋まるからです（[Postfix Standard Configuration Examples](https://www.postfix.org/STANDARD_CONFIGURATION_README.html)）。

<Callout type="warn" title="よくある誤解: 予備の MX を置けば、それだけ安全になる">
  予備の MX は、本命と**同じ強さで判定できなければ**、防御の抜け道になります。宛先の一覧、迷惑メールの判定、ブロックリストを本命と揃える必要があります。
  そもそも、送信側の MTA は届かなければ数日は再送を続けます（前回）。本命が数時間止まるだけなら、予備が無くてもメールは失われません。今の大手の事業者が、優先度の違う予備より、**同じ優先度の MX を複数並べる**構成をとるのはこのためです。
</Callout>

## 送信側の身元: HELO の名前と逆引き

ここからは向きを変えて、**受け取る側**から見ます。受信側の MTA が知っている送信元の情報は、次の 2 つしかありません。

| 情報 | 出どころ | 信用できるか |
| --- | --- | --- |
| 接続元の IP アドレス | TCP の接続（第 53 回） | 偽れない（偽ると 3 ウェイハンドシェイクの応答が相手に届かない） |
| `EHLO` / `HELO` の名前 | 送信側が名乗った文字列 | **自己申告**で、何とでも書ける |

RFC 5321 4.1.1.1 節は、`EHLO` の引数に送信側の完全なドメイン名（FQDN）を書き、意味のある名前が無ければアドレスの表記（`[192.0.2.1]` の形）を書くよう求めています。しかし 4.1.4 節は、受信側がこの名前と IP アドレスの対応を**確かめてもよいが、合わないことを理由に受け取りを拒んではならない**（MUST NOT）としています。確かめた結果は記録や追跡のために使う、という位置づけです。

名乗った名前は信用できないので、受信側は**IP アドレスから名前を引き直します**。第 58 回で見た逆引きです。

### FCrDNS: 逆引きして、正引きで戻る

逆引きの PTR は、IP アドレスを割り当てた側が書くものなので、それだけでは不十分です。IP の持ち主は、PTR に `mail.google.com` と書くこともできてしまいます。そこで、**PTR で得た名前を正引きして、元の IP アドレスに戻るか**まで確かめます。これを **FCrDNS**（forward-confirmed reverse DNS）と呼びます。

```
接続元 209.85.220.41
   │ 逆引き（PTR）
   ▼
mail-sor-f41.google.com.       ← IP の持ち主（Google）が逆引きのゾーンに書いた名前
   │ 正引き（A）
   ▼
209.85.220.41                   ← 名前の持ち主（google.com のゾーン）が書いたアドレス
   │
   └─ 元の IP と一致 → 合格
```

逆引きのゾーンは IP アドレスの割り当てを受けた者が、正引きのゾーンはドメインの持ち主が編集します。**両方が一致するのは、両方を管理できる者が意図して揃えたときだけ**です。Authentication-Results の仕様（[RFC 8601](https://www.rfc-editor.org/rfc/rfc8601.html) 3 節）は、この検査を `iprev` という名前で定義し、「接続元の IP を I、PTR で得た名前の集合を N、N の各名前を A と AAAA で引いたアドレスの和集合を L としたとき、I が L に含まれれば合格」と書いています。

主要な事業者の送信用の IP アドレスで確かめてみます。IP アドレスは、各社が SPF で公開している送信元の範囲（Google の `_netblocks.google.com` の `209.85.128.0/17`、Microsoft の `spf.protection.outlook.com` の `40.107.0.0/16`、Amazon SES の `amazonses.com` の `54.240.0.0/18`）から選びました。

| IP アドレス | 逆引き（PTR） | その名前の正引き |
| --- | --- | --- |
| 209.85.220.41 | `mail-sor-f41.google.com.` | 209.85.220.41 |
| 40.107.22.52 | `mail-am6eur05on2052.outbound.protection.outlook.com.` | 40.107.22.52 |
| 54.240.8.1 | `a8-1.smtp-out.amazonses.com.` | 54.240.8.1 |
| 34.223.124.45 | `ec2-34-223-124-45.us-west-2.compute.amazonaws.com.` | 34.223.124.45 |

4 つとも FCrDNS は合格します。ただし最後の行は、先ほどの `neverssl.com` の IP で、Amazon EC2 が既定で付ける**機械的な名前**です。一致はしていても、名前から「メールを送るためのサーバ」だとは読み取れません。受信側の中には、名前に IP アドレスの数字が埋め込まれているような「一般的な」逆引きを、家庭の回線やクラウドの使い捨てのサーバの印として低く評価するものがあります。

### 受信側は、それをどう使うか

Gmail は、**すべての送信者**への要件として、送信元の IP に PTR があり、その名前の A または AAAA が同じ IP に戻ること、を挙げています（[Gmail の送信者のガイドライン](https://support.google.com/mail/answer/81126)、執筆時点）。

Postfix には、この検査の強さに応じて 2 つの拒否の設定があります（[postconf(5)](https://www.postfix.org/postconf.5.html#reject_unknown_client_hostname)）。

| 設定 | 拒否する条件 |
| --- | --- |
| `reject_unknown_reverse_client_hostname` | 逆引きの名前が無い |
| `reject_unknown_client_hostname` | 逆引きの名前が無い、その名前の正引きが無い、**正引きが元の IP に戻らない**、のいずれか |

どちらも既定の応答は 450 で、DNS が一時的に失敗したときは必ず 450 です。受信側の DNS が不調なだけで恒久的に断ってしまわないよう、**4xx にして送信側に再送させる**わけです。前回の「4xx は再送、5xx は諦め」がここでも効いています。

RFC 8601 自身も、この検査の信頼性には議論があり、地域によっては正引きと逆引きを揃える慣習が根づいておらず合格しにくい、と書いています。FCrDNS は決め手ではなく、**判断材料の 1 つ**です。

<Callout type="warn" title="よくある誤解: 逆引きが合っていれば、差出人は本物">
  FCrDNS が示すのは、「この IP アドレスの持ち主と、この名前のゾーンの持ち主が、対応を揃えている」ことだけです。
  迷惑メールを送る者が自分でドメインとサーバを用意すれば、FCrDNS は問題なく合格します。そして利用者が見る `From:` のドメインとは、何の関係もありません。
  `From:` と送信元を結びつけるには、第 127〜129 回の SPF、DKIM、DMARC が要ります。
</Callout>

## 25 番ポートは塞がれている

ここまでの話から、受信側が「どこから来たか」を重く見ることが分かりました。それを送信する側のネットワークの事業者から見ると、**自分の網から出ていく 25 番の通信は、自分の評判を背負っている**ということになります。

家庭の回線の PC がマルウェアに感染して迷惑メールを直接送り出すと、その ISP の IP アドレスの範囲ごとブロックリストに載ります。そこで ISP は、**利用者の回線から外部の 25 番への通信を遮断**するようになりました。日本では **OP25B**（Outbound Port 25 Blocking）と呼ばれ、JPNIC は「自ネットワークから外部ネットワークへの TCP 25 番ポートの通信を遮断することにより、spam メールや virus メールの送信を抑制しようとする技術」と説明し、代わりにサブミッションポート（587 番）などを使うよう案内しています（[JPNIC](https://www.nic.ad.jp/ja/basics/terms/OP25B.html)）。

手元の回線で確かめると、実際にそうなっていました。

```
$ python3 -c '...'   # socket.create_connection((host, port), timeout=8)
gmail-smtp-in.l.google.com 25  失敗: TimeoutError timed out
smtp.gmail.com 587             接続できた b'220 smtp.gmail.com ESMTP ... - gsmtp\r\n'
```

25 番は**拒否されるのではなく、応答が無いまま時間切れ**になります。接続を拒む RST すら返ってこないので、原因がポートの遮断だと気づきにくいのです。一方、587 番の提出用サーバには普通につながります。提出には認証が要るので（前回の AUTH）、誰が送ったかを事業者が把握できるからです。

クラウドの事業者も、同じ理由で仮想マシンからの 25 番を既定で塞いでいます（執筆時点）。

| 事業者 | 既定の扱い | 解除 |
| --- | --- | --- |
| Amazon EC2 | 25 番への通信は、プライベートな IPv4 アドレス（VPC の CIDR、RFC 1918 など）宛てだけを許し、**公開の IPv4 と IPv6 宛ては遮断**（[AWS](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-resource-limits.html#port-25-throttle)） | 申請すれば解除できる |
| Google Cloud | 宛先が VPC ネットワークの外なら、25 番への接続を**遮断**。587 番と 465 番には制限をかけない（[Google Cloud](https://docs.cloud.google.com/compute/docs/tutorials/sending-mail)） | 外部の配信サービスや、25 番以外のポートでの中継を案内 |
| Microsoft Azure | Enterprise Agreement と MCA-E の契約では遮断しない（ただし相手が受け取る保証は無い）。Enterprise Dev/Test は既定で遮断し、診断ツールで解除できる。**それ以外の契約は遮断**（[Microsoft Learn](https://learn.microsoft.com/en-us/troubleshoot/azure/virtual-network/troubleshoot-outbound-smtp-connectivity)） | 587 番の認証付き中継サービスを推奨 |

3 社とも、案内しているのは**認証付きの提出（587 番か 465 番）で、配信を専門とする事業者に渡す**ことです。自分で 25 番から直接送るのをやめて、評判を管理している配信サービスの IP から送ってもらうわけです。アプリからメールを送る実務は第 132 回で見ます。

## Received ヘッダで経路をたどる

最後に、メールが実際に通ってきた経路が、メッセージのどこに残るかを見ます。

RFC 5321 4.4 節は、メールを受け取った SMTP サーバに、**メッセージの先頭に `Received:` の行を 1 つ足す**ことを義務づけています（MUST）。その行の `from` 句には、(1) **`EHLO` で名乗られた名前**と、(2) **TCP の接続から分かった IP アドレス**の両方を入れるべきだとしています（SHOULD）。そして、すでにある `Received:` の行を**変えたり消したりしてはならず**、新しい行は必ず先頭に足す、と決めています。

中継のたびに先頭に 1 行ずつ積まれていくので、**上ほど新しく、下ほど古い**記録になります。

```
Received: from mx-out.example.org (mx-out.example.org [198.51.100.7])     ← ③ 最後に受け取った、自分の MX が付けた
        by mx.example.net with ESMTPS id ...; Mon, 28 Sep 2026 21:00:05 +0900
Received: from app01.internal (app01.internal [10.0.0.12])                ← ② 送信側の中継が付けた
        by mx-out.example.org with ESMTP id ...; Mon, 28 Sep 2026 12:00:03 +0000
Received: from [192.0.2.44] (unknown [192.0.2.44])                         ← ① 最初の提出を受けたサーバが付けた
        by submit.example.org with ESMTPSA id ...; Mon, 28 Sep 2026 12:00:01 +0000
```

経路を知るには下から上へ、①→②→③と読みます（上は説明のための例です）。行ごとに時刻を比べれば、どの区間で時間がかかったかも分かります。RFC 5321 が時刻に `+0900` のような時差を明記するよう求めているのは、この比較のためです。行の細かな書式は、次回の第 125 回で扱います。

最終的に配送した SMTP サーバは、さらに `Return-Path:` の行を先頭に足し、`MAIL FROM` のアドレスを残します（同じく 4.4 節）。第 122 回で見た、エンベロープの差出人がメッセージに現れる仕組みです。

### 信用できるのは、自分の側で付けた行だけ

`Received:` の規則には、大きな穴があります。**どの行も、その行を付けたサーバの自己申告**だということです。

- `from` 句の名前は、送信側が `EHLO` で名乗ったものにすぎない
- 自分のサーバより下の行は、送信側がメッセージの中に**あらかじめ書いておける**。ヘッダは本文と同じく、`DATA` で送られてくるデータだから

信用してよいのは、**自分の組織のサーバが付けた行**と、その中の「つないできた相手の IP アドレス」までです。上の例なら、③を付けたのが自分の MX なら、③の `198.51.100.7` は TCP の接続から得た事実です。②と①は、`198.51.100.7` の持ち主がそう書いてきた、という以上の意味を持ちません。

<Callout type="warn" title="よくある誤解: 一番下の Received を見れば、本当の送信元が分かる">
  一番下の行は、最も**偽りやすい**行です。迷惑メールの送信者は、無関係な IP アドレスを書いた `Received:` を先に入れておくことができます。
  送信元を追うときは、上から順に、自分の組織が付けた行の中で**最初に外部から受け取った行**を探し、そこに記録された接続元の IP アドレスを起点にします。
</Callout>

## MX と経路は何と組み合わさって意味を持つか

この回で見た仕組みは、どれも単独では何も保証しません。

| 仕組み | 保証すること | 保証しないこと | 組み合わさる部品 |
| --- | --- | --- | --- |
| MX | 宛先のドメインの持ち主が指定した受信サーバの名前 | 答えが途中で偽られていないこと | DNS（第 56〜60 回）、DNSSEC（第 61 回） |
| null MX | このドメインはメールを受けない | 送らないこと（それは SPF の `-all`） | SPF（第 127 回） |
| FCrDNS | IP の持ち主と名前の持ち主が対応を揃えている | `From:` の差出人が本物であること | SPF・DKIM・DMARC（第 127〜129 回） |
| `EHLO` の名前 | 何も保証しない（自己申告） | ― | FCrDNS、SPF の HELO の検査（第 127 回） |
| `Received:` | 自分のサーバが付けた行の接続元 IP | それより下の行の内容 | ログ、Authentication-Results（第 132 回） |
| 25 番の遮断 | 使い捨てのサーバから直接送らせない | 正規のアカウントからの迷惑メール | 認証付きの提出（第 123 回、第 126 回） |

とくに 1 行目は重要です。MX の答えは、DNSSEC が無ければ第 61 回で見た方法で**偽ることができます**。偽った MX に向けて送信側がつながりに行けば、メールは攻撃者のサーバに届きます。それを TLS の証明書で見破れるかというと、中継の STARTTLS では多くの場合証明書を検証しない、という事情があります。この問題は第 126 回で、MTA-STS と DANE とともに扱います。

## 手元で確かめる

### MX を引いて、接続先の順番を作る

本文で引いた `dig` に加えて、RFC 5321 5.1 の手順を、`dig` を呼ぶだけの小さな Python で書いてみます（標準ライブラリだけで動きます）。

```python
import random, subprocess, sys

def dig(name, rtype):
    out = subprocess.run(["dig", "+noall", "+comments", "+answer", name, rtype],
                         capture_output=True, text=True).stdout
    status = out.split("status: ")[1].split(",")[0]
    rows = [l.split() for l in out.splitlines() if l and not l.startswith(";")]
    return status, [r[4:] for r in rows if r[3] == rtype]

def candidates(domain):
    status, mx = dig(domain, "MX")
    if status == "NXDOMAIN":
        return "失敗: ドメインが存在しない"
    if status != "NOERROR":
        return f"一時的な失敗 ({status}): キューに戻して後で再試行"
    if [m for m in mx if m[1] == "."]:
        return "失敗: null MX。このドメインはメールを受けない (556 5.1.10)"
    if not mx:
        _, a = dig(domain, "A")
        return f"暗黙の MX: 優先度 0 の {domain} → {[x[0] for x in a]}"
    by_pref = {}
    for pref, host in mx:
        by_pref.setdefault(int(pref), []).append(host)
    order = []
    for pref in sorted(by_pref):
        hosts = by_pref[pref]
        random.shuffle(hosts)          # 同じ優先度はランダムに（RFC 5321 5.1 の MUST）
        order += [(pref, h) for h in hosts]
    return order

for d in sys.argv[1:]:
    print(d)
    r = candidates(d)
    for x in (r if isinstance(r, list) else [r]):
        print("  ", x)
```

```
$ python3 route.py gmail.com yahoo.co.jp example.com neverssl.com no-such-domain-ll115-xyz.com
gmail.com
   (5, 'gmail-smtp-in.l.google.com.')
   (10, 'alt1.gmail-smtp-in.l.google.com.')
   ...（20, 30, 40 と続く）
yahoo.co.jp
   (10, 'mx5.mail.yahoo.co.jp.')
   (10, 'mx3.mail.yahoo.co.jp.')
   (10, 'mx1.mail.yahoo.co.jp.')
   (10, 'mx2.mail.yahoo.co.jp.')
example.com
   失敗: null MX。このドメインはメールを受けない (556 5.1.10)
neverssl.com
   暗黙の MX: 優先度 0 の neverssl.com → ['34.223.124.45']
no-such-domain-ll115-xyz.com
   失敗: ドメインが存在しない
```

`gmail.com` は DNS の答えの順番にかかわらず毎回同じ順に並び、`yahoo.co.jp` は実行するたびに順番が変わります（2 回目は `mx2, mx1, mx3, mx5` でした）。本物の MTA は、この先で各名前の A と AAAA を引き、上限の数までつなぎに行きます。

### 送信元の逆引きを確かめる

```bash
ip=209.85.220.41
name=$(dig -x $ip +short)          # 逆引き
echo "$name"                        # mail-sor-f41.google.com.
dig "$name" A +short                # 正引き。元の IP に戻れば FCrDNS は合格
dig _netblocks.google.com TXT +short   # その IP が Google の送信元の範囲にあること
```

受信用の MX のアドレスも逆引きしてみると、`gmail-smtp-in.l.google.com` のアドレスは `...1e100.net.` という別の名前を返しました。逆引きが問われるのは主に送信するときで、受信専用の MX の名前と PTR は一致しなくても配送に影響しません。

### 受信側が Received に何を書くか

手元のコンテナ（mailpit）に、`EHLO` で好きな名前を名乗ってメールを送り、受信側が付けた `Received:` を見ます。送り先は手元のコンテナだけです。

```bash
docker run -d --name ll115 -p 18118:1025 axllent/mailpit
```

```python
import smtplib
from email.message import EmailMessage
m = EmailMessage()
m["From"] = "alice@example.com"; m["To"] = "bob@example.net"; m["Subject"] = "route test"
m.set_content("hello\n")
with smtplib.SMTP("127.0.0.1", 18118, local_hostname="mx.i-say-so.example") as s:
    s.send_message(m, from_addr="bounce@example.com", to_addrs=["bob@example.net"])
```

mailpit が保存した生のメッセージの先頭は、次のようになりました（Web の画面か API で取り出せます）。

```
Return-Path: <bounce@example.com>
Received: from mx.i-say-so.example (unknown [192.168.65.1])
        by ba32f683f0f6 (Mailpit) with SMTP
        for <bob@example.net>; Mon, 28 Sep 2026 12:08:36 +0000 (UTC)
From: alice@example.com
```

`from` 句に、4.4 節のとおり 2 つの情報が並んでいます。`mx.i-say-so.example` は**こちらが名乗った名前をそのまま書いたもの**で、括弧の中の `[192.168.65.1]` は、mailpit が **TCP の接続から得た**アドレス（Docker Desktop の仮想ネットワークから見たホストのアドレス）です。その前の `unknown` は、そのアドレスの逆引きが無かったことを表しています。受信側は、名乗られた名前を拒まずに記録だけし、判断には括弧の中を使うわけです。

`Return-Path:` には `MAIL FROM` の `bounce@example.com` が入り、`From:` の `alice@example.com` とは別のままです。

```bash

```

## まとめ

- 送信側は宛先のドメインの MX を引き、**優先度の小さい順**に、**同じ優先度はランダムに**並べて試す。DNS が返す並び順には意味がない
- DNS の失敗は種類で扱いが分かれる。NXDOMAIN は恒久的な失敗、一時的な失敗はキューで再送
- MX が無ければ、ドメイン自身を優先度 0 の MX とみなす（暗黙の MX）。**MX を書かないことは「受けない」ではない**
- 受けないドメインは **null MX**（`MX 0 .`）で宣言する。送信側はその場で 556 `5.1.10` を返せる。送らないことは SPF の `-all` で宣言する
- MX の値は A か AAAA を直接持つ名前でなければならず、CNAME は書けない。中継するサーバが MX の一覧から自分を見つけるため
- 予備の MX は、本命と同じ強さで判定しなければ迷惑メールの抜け道とバックスキャッタの原因になる
- `EHLO` の名前は自己申告で、受信側は IP アドレスの逆引きと、その名前の正引きが元に戻るか（FCrDNS）を見る。ただし FCrDNS は `From:` とは無関係
- ISP とクラウドは、評判を守るために外向きの 25 番を既定で塞いでいる。送るなら認証付きの提出（587 / 465）で配信サービスに渡す
- `Received:` は中継のたびに先頭に積まれ、下から上へ読む。信用できるのは自分の組織が付けた行の接続元 IP まで

次の第 125 回では、`Received:` を含むヘッダと本文そのものの形式、RFC 5322 と MIME を見ます。件名の日本語が `=?UTF-8?B?...?=` という形になる理由も、そこで分かります。
