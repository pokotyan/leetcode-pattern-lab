## 速くしただけでは終わらない

前回は、負荷の強さや通知の間隔といった仕様の側の変数を、そのとき何が律速しているかを見ながら合わせ込む方法を見ました。この回で扱うのは、その後、競技の最後の 1 時間で行う作業です。

ISUCON の点は、競技中に出した最高の値ではありません。ISUCON14 の当日の文書には、次のように書かれています（[isucon/isucon14 docs/manual.md](https://github.com/isucon/isucon14/blob/main/docs/manual.md)）。

> 競技中に最後に行った負荷走行の結果を、最終スコアとします。

さらに競技の後、主催者がサーバを再起動し、同じ点が再現するかを確かめます。つまり、終盤にやるべきことは 3 つあります。**再起動しても同じように動くことを確かめる**、**計測のために入れたものを外す**、そして**最後の 1 回をどこで止めるかを決める**です。どれも本番のサービスでの「リリースを終わらせる」作業と同じ形をしています。

| 作業 | 何を防ぐか | 本番での対応物 |
| --- | --- | --- |
| 再起動試験 | 手で起こしたプロセス、実行時に変えた設定、メモリにしかないデータが消える | 再起動、フェイルオーバー、ノードの入れ替え |
| ブラウザでの確認 | ベンチマーカーが見ない画面の崩れ | リリース後の目視確認、E2E テスト |
| 計測の停止 | ログやプロファイラの費用が残る | 計測の費用を予算として管理する |
| 最後の 1 回の判断 | ぶれの下側の値で終わる | 性能試験の繰り返しと中央値 |

## 追試で何が確かめられるか

ISUCON14 の文書は、競技後の追試の手順を具体的に定めていました（[isucon/isucon14 docs/manual.md](https://github.com/isucon/isucon14/blob/main/docs/manual.md)）。要約すると次のとおりです。

1. 3 台のサーバを再起動する。1 台でも再起動できなければ失格
2. 競技環境が指定どおりかを確かめる
3. 最終スコアを記録したサーバに負荷走行を行う。FAIL か最終スコアの 75% 以下なら再実行し、3 回目でも同じなら失格
4. もう一度 3 台を再起動する
5. 「負荷走行実行時にアプリケーションに書き込まれたデータが、再起動後に取得できるかどうかを確認します」
6. 「アプリフロントエンドにアクセスし、表示を確認します」

ISUCON2026 のレギュレーションには、複数台を使う構成に関わる一文があります（[ISUCON2026 レギュレーション](https://isucon.net/archives/59966826.html)）。

> 複数台のインスタンスが提供されており、それらを使用していたとしても、主催者がインスタンスを再起動する順序は保証しない。

同じレギュレーションは、許される変更の条件として「サーバ再起動後にすべてのアプリケーションコードが正常動作する状態を維持すること」「ベンチマーク実行時にアプリケーションに書き込まれたデータは再起動後にも取得できること」を挙げています。

ここから、再起動試験で確かめるべき性質が 3 つに分かれます。

- **自分で起動するか。** 手で起動したプロセスや、`systemctl start` しただけで `enable` していないサービスは、再起動で戻ってこない。
- **順序によらず起動するか。** データベースのサーバがアプリケーションのサーバより後に起動しても、最終的に正しくつながるか。
- **書いたものが残っているか。** 第 269 回のオンメモリのデータや、第 272 回の後回しにした書き込みが、再起動で失われないか。

## 再起動で消えるもの

### 実測：実行時に変えた設定

競技中は、MySQL の設定をその場で変えて試すことがよくあります。第 264 回で見た `long_query_time` や、接続数の上限の `max_connections` などです。この変更が再起動で残るかを、Docker の MySQL 8.4.13 で確かめます（Apple M1 Pro、macOS 26.2、Docker 29.4.0）。

```text
$ docker run -d --rm --name tune-278-mysql -e MYSQL_ROOT_PASSWORD=pw -e MYSQL_DATABASE=bench \
    -p 127.0.0.1:32780:3306 mysql:8.4
$ M(){ docker exec tune-278-mysql mysql -uroot -ppw -e "$1" 2>/dev/null; }

$ M "SET GLOBAL max_connections=1000; SET GLOBAL slow_query_log=ON; SET GLOBAL long_query_time=0;
     SET PERSIST innodb_io_capacity=2000;
     select @@GLOBAL.max_connections, @@GLOBAL.slow_query_log, @@GLOBAL.long_query_time,
            @@SESSION.long_query_time, @@GLOBAL.innodb_io_capacity"
@@GLOBAL.max_connections	@@GLOBAL.slow_query_log	@@GLOBAL.long_query_time	@@SESSION.long_query_time	@@GLOBAL.innodb_io_capacity
1000	1	0.000000	10.000000	2000
```

最後の `innodb_io_capacity` だけを `SET PERSIST` で変えています。同じ接続のセッションの `long_query_time`（`@@SESSION.long_query_time`）は 10 秒のままです。新しく接続し直すと 0 になります。

```text
$ M "select @@SESSION.long_query_time as new_session"
new_session
0.000000
```

コンテナを再起動して、もう一度見ます。

```text
$ docker restart tune-278-mysql
$ M "select @@GLOBAL.max_connections, @@GLOBAL.slow_query_log, @@GLOBAL.long_query_time,
            @@GLOBAL.innodb_io_capacity"
@@GLOBAL.max_connections	@@GLOBAL.slow_query_log	@@GLOBAL.long_query_time	@@GLOBAL.innodb_io_capacity
151	0	10.000000	2000

$ docker exec tune-278-mysql cat /var/lib/mysql/mysqld-auto.cnf
{"Version": 2, "mysql_dynamic_variables": {"innodb_io_capacity": {"Value": "2000", "Metadata": {"Host": "localhost", "User": "root", "Timestamp": 1794444130639928}}}}
```

`SET GLOBAL` で変えた 3 つは既定値に戻り、`SET PERSIST` で変えた `innodb_io_capacity` だけが残りました。残った値は、データディレクトリの `mysqld-auto.cnf` に書かれています。MySQL の文書の説明は次のとおりです（[MySQL 8.4 Reference Manual: SET Syntax for Variable Assignment](https://dev.mysql.com/doc/refman/8.4/en/set-variable.html)）。

> However, the change affects the corresponding session value only for clients that connect after the change. The global variable change does not affect the session value for any current client sessions (not even the session within which the global value change occurs). To make a global system variable setting permanent so that it applies across server restarts, you can persist it to the mysqld-auto.cnf file in the data directory.

この実験から、2 つの落とし穴が読み取れます。

- **`SET GLOBAL` は再起動で消える。** 試して効いた設定は、設定ファイル（第 262 回で git に入れた `my.cnf` など）に書き戻すか、`SET PERSIST` で残す。どちらで残したかを記録しておかないと、後で「設定ファイルには無いのに効いている値」が生まれる。
- **`SET GLOBAL` は、すでに張られた接続には効かないものがある。** `long_query_time` のようにセッションごとに値を持つ変数は、コネクションプールが握っている既存の接続には反映されない。スロークエリログを止めたつもりで、あるいは有効にしたつもりで、アプリケーションの接続が古い値のまま動いていることがある。

同じことは OS の設定にも言えます。`sysctl -w` で変えたカーネルのパラメータや、シェルで `ulimit -n` を上げただけのファイルディスクリプタの上限は、再起動や systemd からの起動では引き継がれません。前者は `/etc/sysctl.d/` に、後者はユニットファイルの `LimitNOFILE=` に書きます。

### 実測：データベースより先に起動したアプリケーション

次は起動順です。Go のアプリケーションが起動時に 1 回だけ `db.Ping()` を呼び、失敗したら終了するとします。データベースのコンテナを再起動した直後にアプリケーションを起動すると、どうなるかを見ます。

```go
db, _ := sql.Open("mysql", "root:pw@tcp(127.0.0.1:32780)/bench?timeout=1s")
for i := 1; ; i++ {
	err := db.Ping()
	if err == nil {
		break
	}
	if !*retry {
		log.Fatalf("起動失敗: %v", err)
	}
	log.Printf("ping %d 回目: %v", i, err)
	time.Sleep(time.Second)
}
```

```text
$ (docker restart tune-278-mysql >/dev/null &); sleep 1; ./boot; echo "exit=$?"
[mysql] 2026/11/12 09:49:34 connection.go:49: unexpected EOF
[mysql] 2026/11/12 09:49:34 connection.go:49: unexpected EOF
[mysql] 2026/11/12 09:49:34 connection.go:49: unexpected EOF
09:49:34.300168 起動失敗: driver: bad connection
exit=1
```

再試行する版では、次のようになりました（ドライバが出す `[mysql] ... unexpected EOF` の行と、途中の 6〜8 回目を省略しています）。

```text
$ (docker restart tune-278-mysql >/dev/null &); sleep 1; ./boot -retry
09:49:50.680274 ping 1 回目: driver: bad connection
09:49:51.761270 ping 2 回目: driver: bad connection
09:49:52.798317 ping 3 回目: driver: bad connection
09:49:53.799736 ping 4 回目: dial tcp 127.0.0.1:32780: connect: connection refused
09:49:54.847175 ping 5 回目: driver: bad connection
...
09:49:58.888984 ping 9 回目: driver: bad connection
09:50:00.079593 接続まで 9.5s、users は 10000 行。待ち受けを始める
```

接続が成立するまで 9.5 秒かかりました。`unexpected EOF` と `bad connection` は、Docker のポート転送が TCP の接続をいったん受け付けたのに、その先の MySQL がまだ応答できずに閉じたことを示しています。`connection refused` との違いは、**接続を受け付ける側が動いているかどうか**です。どちらにしても、1 回で諦めるアプリケーションは起動に失敗し、その後は誰も起こしてくれません。

systemd の `After=` を書けば済むと思いがちですが、`After=` が待つのは相手のユニットが「起動した」ことです。systemd の文書は `After=` について「the listed unit is fully started up before the configured unit is started」と書いています（[systemd.unit](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html)）。ところが、何をもって「起動した」とするかはユニットの `Type=` で決まり、既定の `Type=simple` については次のとおりです（[systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html)）。

> the service manager will consider the unit started immediately after the main service process has been forked off

プロセスが作られた時点で「起動した」とみなされるので、データベースが接続を受け付けられる状態かどうかは保証されません。そもそも、データベースが別のサーバにあれば、サーバをまたぐ順序は systemd では表せません。ISUCON2026 のレギュレーションが「再起動する順序は保証しない」と書いているのは、まさにこの状況です。

対策は 2 段構えにします。

1. **アプリケーション自身が、起動時の接続を再試行する。** 上の `-retry` の版のように、一定時間は待ち続ける。
2. **落ちても systemd が起こし直す。** ユニットに `Restart=on-failure` と `RestartSec=` を書く。ISUCON14 のマッチングを呼ぶユニット `isuride-matcher.service` にも `Restart=on-failure` と `RestartSec=5` が書かれていました（[isucon/isucon14 provisioning](https://github.com/isucon/isucon14/blob/main/provisioning/ansible/roles/webapp/files/isuride-matcher.service)）。

### 再起動試験の手順

ISUCON13 で優勝したチーム NaruseJun の参加記は、再起動試験で気をつけている点を次のように挙げています（[チーム NaruseJun の ISUCON13 参加記](https://zenn.dev/tohutohu/articles/923bdf5dcd73af)）。

> サーバー再起動してもベンチが通る アプリの再起動を挟まず連続してベンチを行っても通る&スコアが変わらない 正しくすべてのサービスが active になっているか（sudo systemctl status） 各タイミングでフロントエンドの機能が壊れていないか

（原文は箇条書きです。）実際の操作は「ベンチ → フロントチェック → サーバー再起動 → sudo systemctl status → フロントチェック → ベンチ → フロントチェック → ベンチ → フロントチェック」だと書かれています。2 つ目の「再起動を挟まずに連続して流しても通り、点が変わらない」は見落としやすい項目です。初期化の処理（`/initialize`）が前の負荷走行の痕跡を消し切れていない、オンメモリのキャッシュが前の走行のデータを持ち越している、といった不具合は、連続して流したときに初めて出ます。

ISUCON2026 で優勝した参加者の記録では、終了 40 分前に「全台の再起動を2通りの順序で確かめました。アプリは手で起動しなくても復帰し、再起動の前に書いたデータも読めました。」とあります（[ISUCON2026 競技当日の記録](https://zenn.dev/luvtechno/articles/isucon2026-competition-day)）。順序が保証されないなら、少なくとも「データベースが先」と「アプリケーションが先」の 2 通りを試しておく、という考え方です。

まとめると、再起動試験は次の順で行います。

| 手順 | 確かめること |
| --- | --- |
| 1. 負荷走行を 1 回流す | 書き込みが起きた状態を作る |
| 2. ブラウザで主な画面を操作する | 再起動前の基準を見ておく |
| 3. 全台を再起動する（順序を変えて 2 回） | 手で起動したものに頼っていないか |
| 4. `systemctl status`、`systemctl is-enabled` | すべてのサービスが active で、enable されているか |
| 5. 手順 1 で書いたデータを画面や API で読む | 書き込みが永続化されているか |
| 6. 負荷走行を 2 回続けて流す | 初期化と連続実行で点が変わらないか |
| 7. もう一度ブラウザで確認する | 表示が崩れていないか |

## ブラウザで確かめる

ベンチマーカーは、決められた API を決められた順に呼び、応答の形と値を確かめます。しかし、画面を組み立てる静的ファイルや、ベンチマーカーが呼ばない API までは見ていないことがあります。ISUCON14 の追試が最後に「アプリフロントエンドにアクセスし、表示を確認します」と定め、「構造がリファレンス実装と異なる、意図しないデータが表示されている場合」を失格としているのはそのためです。

終盤に壊れやすいのは、第 271 回で見た HTTP とプロキシの層です。nginx を外した、静的ファイルを別の場所から返すようにした、圧縮を有効にした、キャッシュのヘッダを付けた、といった変更は、ベンチマーカーの検査を通っても、ブラウザでは JavaScript が読めない、画像が古いまま、という形で壊れることがあります。ブラウザで確かめるときは、キャッシュを無効にした状態（開発者ツールの「Disable cache」）と、通常の状態の両方で開きます。

## 計測を止める

第 262〜265 回で入れた計測は、ボトルネックを探すための道具であって、最終的な構成の一部ではありません。止め忘れの例は、上位のチームにも残っています。

ISUCON9 本選で優勝したチーム（白金動物園）の参加記には、こうあります（[白金動物園 mirakui の ISUCON9 本選参加記](https://blog.mirakui.com/entry/2019/10/14/011554)）。

> あまりに便利だったので最後の最後まで使っていて、stackprof を有効にしたまま最終スコアとして提出していたことに後で気づきました……。

止めたことで点が大きく伸びた例もあります。ISUCON11 本選で優勝したチームは、最後に「今までずっと有効にしていた MySQL の slow query log を無効化して更に数字を伸ばした」と書いています（[fujiwara組の ISUCON11 本選参加記](https://sfujiwara.hatenablog.com/entry/isucon11-final)）。ISUCON13 の NaruseJun は、17 時台に 277,310 点から 468,006 点まで伸ばしていて、参加記には「後述しますが17時直後にめちゃくちゃ伸びているのは、ログを止めた結果です。」とあります。その中で、アプリケーションのアクセスログを止めたはずなのに出続けていて、調べると「元々のコードに含まれていたアクセスログ出力設定の他にpproteinで設定されていた。」という経緯も書かれています。**止めるべきものは、自分で入れたものだけとは限らない**わけです。

止めるものの一覧は、入れたときに作っておくのが確実です。

| 層 | 入れたもの（例） | 止め方 |
| --- | --- | --- |
| nginx | アクセスログ（LTSV・JSON） | `access_log off;` |
| MySQL | スロークエリログ、`long_query_time=0` | 設定ファイルから外し、再起動で反映を確かめる |
| MySQL | performance_schema の追加の計測 | 有効にした consumer や instrument を戻す |
| アプリケーション | pprof・fgprof のエンドポイント、プロファイルの自動取得 | 起動時の設定で無効にする |
| アプリケーション | フレームワークのリクエストログ、デバッグ出力 | ログの水準を上げる、ミドルウェアを外す |
| OS | 監視のエージェント、`perf` などの常駐 | サービスを停止し、`disable` する |

<Callout type="warn" title="プロファイラの口は、性能だけでなく安全の問題でもある">
  Go の `net/http/pprof` は、import するだけでハンドラを登録します。文書には「The package is typically only imported for the side effect of registering its HTTP handlers. The handled paths all begin with /debug/pprof/.」とあります（[net/http/pprof](https://pkg.go.dev/net/http/pprof)）。
  アプリケーションが `http.DefaultServeMux` をそのまま公開していると、`/debug/pprof/` 以下も外から読めます。プロファイルにはコマンドラインの引数や関数名、メモリの中身の手がかりが含まれます。競技なら点の問題で済みますが、本番では情報の漏えいになります。計測用の口は別のポートで、内側からだけ開くようにします。
</Callout>

### 実測：スロークエリログの費用

スロークエリログを `long_query_time=0` で有効にすると、どれだけ費用がかかるのかを測ります。先ほどの MySQL 8.4.13 のコンテナに 1 万行の表を作り、主キーで 1 行を引くクエリを 16 並列で 5 秒間流し続けます。クライアントは Linux 向けにビルドした Go のプログラムをコンテナの中に置いて実行し、Docker のポート転送を通らないようにしました。

```go
for time.Now().Before(stop) {
	db.QueryRow("SELECT name, score FROM users WHERE id = ?", rng.Intn(10000)+1).Scan(&name, &score)
	n.Add(1)
}
```

ログを無効にした回と、`long_query_time=0` で有効にした回を交互に 10 回ずつ流し、毎秒のクエリ数、mysqld の CPU 時間（`/proc/1/stat` の utime と stime の増分）、スロークエリログの増分を記録しました。この実験は、同じマシンで別の重い処理が並行して動いている状態で行いました（実験の前後のロードアベレージは 63 と 50）。


- 1 クエリあたりの CPU 時間は、中央値で 36.4 µs から 49.8 µs に増えました。主キーで 1 行を引くだけの軽いクエリでは、ログを書く処理の比率が大きくなります。
- ログは 1 クエリあたり 234 バイトで、5 秒間で最大 54.3 MB 増えました。この速さで 60 秒の負荷走行を流すと、数百 MB のログが残ります。ディスクの容量と書き込みの帯域も消費します。

ISUCON14 で 3 位のチームは、特別賞の点に届かせるために「データベースのCPU負荷を少しでも下げるためにスロークエリログをとめた」と書いています（[ISUCON 14に参戦して3位入賞しました](https://blog.pinkumohikan.com/entry/isucon-14)）。計測は、ボトルネックを探している間は投資ですが、探し終えた後は純粋な費用です。

## 最後の 1 回をどこで止めるか

上の実験には、もう一つの事実が出ています。**同じ設定でも、毎秒のクエリ数が 18,139 から 104,451 まで、5 倍以上ぶれた**ことです。原因は、同じマシンで動いていた別の処理です。ISUCON の環境はここまで荒れませんが、負荷走行の点にも、ネットワーク、ベンチマーカー、キャッシュの温まり具合によるぶれがあります。

ISUCON2026 で優勝した参加者の記録には、そのぶれが具体的に書かれています（[ISUCON2026 競技当日の記録](https://zenn.dev/luvtechno/articles/isucon2026-competition-day)）。

> この構成の12回の走行は 474,987〜629,638 点に散らばりました。

同じ記録は、終盤に試した手の差よりも走行ごとの差の方が大きかったことを書き残しています。この参加者は、残り時間から「あと何回走らせられるか」を計算し、その回数だけ走らせ直せる場合の期待値を閾値として、最後の走行がそれ以上なら止め、下回ればもう 1 回走らせる、という規則で最後の 1 回を決めていました。

ここから、終盤の判断について 3 つのことが言えます。

- **差がぶれより小さい変更は、1 回の比較では判断できない。** 何回か流して中央値で比べるか、採用を見送る。ISUCON11 本選で優勝したチームが「明確に数字が上がらない施策」と呼んだものの多くは、このぶれの中に埋もれている。
- **最後の走行は、試す場ではなく結果を出す場にする。** 最後の 1 回が FAIL なら最終スコアは無くなる。危険な変更は、何回か流して安定を確かめる時間が残っているうちに入れる。
- **追試の基準を知っておく。** ISUCON14 では、追試の点が最終スコアの 75% 以下なら再実行になった。ぶれの大きい構成は、それだけで追試の危険を抱えている。

本番の性能試験でも同じです。1 回の負荷試験で「5% 速くなった」と言う前に、同じ構成で何回か流したときの幅を知っておく必要があります。第 236 回で見たように、計測値はばらつくものとして扱い、比べるときは中央値やパーセンタイルの分布で比べます。

### 最後の 1 時間の進め方

ここまでの事例を時刻に並べると、上位のチームの終盤はおおむね同じ形をしています。NaruseJun（ISUCON13）は 17 時すぎに再起動試験を行い、17 時台は「基本的に再起動試験とログ周りの整理をしていた。」と書いています。ISUCON2026 の優勝者は 17 時 20 分（終了 40 分前）に終盤の確認に入りました。どちらも、終了の 40〜60 分前には新しい改善を止めています。

| 終了までの時間 | 行うこと |
| --- | --- |
| 60 分前 | 新しい改善の着手をやめる。未マージのブランチを整理し、入れるものと捨てるものを決める |
| 50 分前 | 計測を止める。止めた後に 1 回流し、ログが増えていないことと点を確かめる |
| 40 分前 | 再起動試験（順序を変えて 2 回）とブラウザでの確認 |
| 20 分前 | 仕様の変数（前回の負荷の強さや間隔）を最終の値にして、何回か流す |
| 最後 | ぶれを踏まえて、どの走行で止めるかを決める。止めた後はサーバに触らない |

この表の時間配分は目安ですが、**再起動試験と計測の停止に 30 分以上を残す**ことが共通しています。どちらも、問題が見つかったときに直してもう一度確かめる時間が要るからです。

## 事故の型

ここまでに出てきた事例を含めて、終盤に起きる事故を型として並べます。

| 型 | 事例 | 防ぎ方 |
| --- | --- | --- |
| 計測の止め忘れ | ISUCON9 本選で、プロファイラを有効にしたまま最終スコアを提出（白金動物園） | 止めるものの一覧を、入れたときに作る |
| 止めたつもりの計測が残る | ISUCON13 で、アクセスログの設定が 2 か所にあった（NaruseJun） | 止めた後に、ログが増えていないことを確かめる |
| まとめてマージして FAIL | ISUCON11 予選で、多くの変更を一度に入れて FAIL し、手作業の二分探索で原因を探した（shallowverse） | 1 変更ずつ入れて流す。壊れたら `git bisect` |
| 当日に初めての大改修 | ISUCON12 で、Redis の導入が時間内に終わらず使えなかった（NaruseJun） | 練習で一度もやっていない構成変更は、当日に始めない |
| 構成変更の後の取りこぼし | ISUCON13 で、インデックスの張り忘れとキャッシュの使い忘れを反省に挙げた（[traP の参加記](https://trap.jp/post/2049/)） | 構成を変えた後に、計測を最初から取り直す |
| 再起動で戻らない | 実行時の設定、手で起動したプロセス、起動順の依存 | 再起動試験を順序を変えて 2 回行う |

いくつかは原文で確かめておきます。ISUCON11 予選 1 位のチームの参加記には「色々一気にmergeしすぎて，複数台構成に切り替えたあたりでFAILするようになった．しんどい．」とあり、続いて「手動 git bisect の結果，getIsuConditionsFromDBの高速化に問題があることに気づきrevertする．」と書かれています（[ISUCON11 予選 1 位の参加記](https://www.y1r.org/posts/20210831-isucon11-qualify)）。同じ参加記の最後には、設定を変えていなくても「問題はないはずだが再起動試験を行っておく．」とあります。

ISUCON12 で優勝した NaruseJun のインタビューでは、当日に Redis を導入しようとしたメンバーについて、別のメンバーが「本来なら練習でやっておくべきことで、いきなり本番でやるのは無謀だと止めたんですが、結局使いきれませんでしたね笑」と振り返っています（[ISUCON12 優勝チームインタビュー](https://gihyo.jp/article/2022/10/isucon12-champinterview-narusejun)）。ここでの「本番」は競技当日のことですが、本番のサービスに置き換えても通じる話です。

ISUCON14 で 3 位のチームは、最後に「計測ツールやログ出力をとめ、最後にマッチング間隔やらポーリングやらの調整を行って最高スコアアタックして競技終了。」と書いています（[ISUCON 14に参戦して3位入賞しました](https://blog.pinkumohikan.com/entry/isucon-14)）。計測を止めてから仕様の変数を詰める、という順序は、第 277 回とこの回の内容をそのまま並べたものです。

<Callout type="tip" title="本番のサービスに持ち帰ること">
  再起動試験は、本番ではフェイルオーバーやノードの入れ替えの演習に当たります。実行時に変えた設定が構成管理（第 262 回）に戻されていないと、次にサーバを作り直したときに性能が元に戻ります。これは設定のずれと呼ばれる問題で、第 31 章で見た継続的な確認の対象でもあります。
  計測は止めるか残すかの二択ではなく、費用を見積もって残す量を決めます。本番ではスロークエリの閾値を上げる、プロファイルを一部の時間や一部の台数に限る、ログを標本化する、といった形で、探すための計測と常時の監視を分けます。
</Callout>

## この章を終えて

第 33 章では、遅い Web アプリケーションを、決められた時間の中で速くする方法を、ISUCON の過去問と上位チームの記録を題材に見てきました。

1. **何を速くするか**（第 260〜261 回）— 採点の定義が目的関数になること、整合性の検査と減点。負荷をかける側も、待たされれば離れ、速くなれば増える利用者として振る舞うこと
2. **測る**（第 262〜265 回）— 最初の 1 時間で設定とコードを手元に取り込み、ワンコマンドでデプロイできるようにする。アクセスログを合計時間で並べ、スロークエリログを指紋で束ね、リクエストとクエリとプロファイルを結び付ける
3. **データベースの仕事を減らす**（第 266〜268 回）— 並び順に合わせたインデックス、N+1 の解消、コネクションプールとプリペアドステートメントによる往復の削減
4. **持つ、まとめる、先にやる**（第 269〜273 回）— アプリケーションの中に持つキャッシュと、仕様が許す古さ。HTTP とプロキシに任せる配信。書き込みをまとめて後回しにすること、書き込み時に計算しておくこと
5. **待ちと資源の配分**（第 274〜276 回）— ロックの範囲を絞り、外部の待ちをトランザクションの外に出す。台数を役割に分けて使う。データベースの次に出てくるアプリケーションの CPU
6. **仕様に合わせ、終わらせる**（第 277 回とこの回）— 負荷の強さや間隔といった仕様の側の変数を、律速段階を見ながら合わせる。再起動試験、計測の停止、ぶれを踏まえた最後の 1 回

どの回でも、手順は同じでした。**測って、最も時間を使っている場所を見つけ、1 つ変えて、測り直す。** ISUCON の上位チームの記録が示しているのは、特別な技術よりも、この手順を 8 時間崩さずに回し続けることの強さです。そして、ここで使った道具のほとんど、つまりインデックス、キャッシュ、キュー、ロック、プロファイラ、ログは、この読み物のこれまでの章で中身を見てきたものでした。

## まとめ

- ISUCON の最終スコアは最後の負荷走行の値で、競技後には再起動を含む追試がある。終盤の作業は、再起動試験、計測の停止、最後の 1 回の判断の 3 つ
- 再起動試験で確かめるのは、自分で起動するか、順序によらず起動するか、書いたものが残っているか。順序を変えて 2 回行い、続けて 2 回流しても点が変わらないことも見る
- `SET GLOBAL` の変更は再起動で消え、`SET PERSIST` の変更は `mysqld-auto.cnf` に残る。セッションごとの変数は、すでに張られた接続には反映されない
- systemd の `After=` は相手が接続を受け付けられることまでは保証しない。アプリケーションが起動時の接続を再試行し、`Restart=on-failure` で起こし直す
- ベンチマーカーが見ない画面もあるので、ブラウザでキャッシュの有無を変えて確かめる
- 計測は探している間は投資で、探し終えたら費用。手元の実験では `long_query_time=0` で毎秒のクエリ数の中央値が約 55% になり、1 クエリあたり 234 バイトのログが出た
- 止めるものの一覧は入れたときに作り、止めた後に本当に止まったかを確かめる
- 同じ構成でも結果はぶれる。差がぶれより小さい変更は 1 回では判断せず、最後の走行は試す場にしない
- まとめてのマージ、当日に初めての大改修、構成変更の後の取りこぼしは、上位チームの記録にも繰り返し出てくる事故の型
- 第 33 章の手順は、測って、最も時間を使っている場所を見つけ、1 つ変えて、測り直すことに尽きる。その道具の中身は、低レイヤの読み物のこれまでの章にある
