## 「CPU が 100% です」と言われたら

障害の連絡で「CPU 使用率が 100% に張り付いています」と言われたとき、確かめるべきことはいくつもあります。マシン全体の値なのか、1 つのプロセスの値なのか。8 コアのうち 1 コアが 100% なのか、8 コアすべてなのか。100% のうち計算に使っているのか、カーネルの中にいるのか。そもそもそのプロセスは CPU が足りずに遅いのか、それとも別のものを待っているのか。

第 192 回では、`top` や `vmstat` の `us` / `sy` / `wa` で大まかな方向を決める、と書きました。この回ではその数字の中身に降ります。CPU 使用率は、カーネルが数えた時間を割り算した値です。**何を数えて、何で割っているのか**が分かれば、数字が直感と食い違ったときに、どちらが正しいのかを自分で判断できるようになります。

この回の実測は、Apple M1 Pro（macOS 26.2）の上の OrbStack の Linux 仮想マシン（8 vCPU、カーネル 7.0.14）で、Ubuntu 24.04 のコンテナ（procps 4.0.4、GNU time 1.9、gcc 13.3）を `docker run --rm` で動かして取りました。使ったプログラムは、指定した本数のスレッドで決まった回数の計算をする `spin`、`getppid` を繰り返し呼ぶ `sys`、4KiB 書いては `fsync` する `fsync` の 3 つです。

## 2 つの時間：経過時間と CPU 時間

プログラムの「時間」には、まったく違う 2 種類があります。

- **経過時間**（wall-clock time、実時間）: 始まってから終わるまでに、壁の時計が進んだ時間
- **CPU 時間**: そのプロセスが実際に CPU の上で命令を実行していた時間。ユーザー空間で動いていた **user** と、システムコールなどでカーネルの中にいた **sys** に分けて数える

`time` コマンドは、この 3 つを並べて見せます。GNU time の文書は、書式の `%e` を「Elapsed real time (in seconds).」、`%U` を「Total number of CPU-seconds that the process spent in user mode.」、`%S` を「Total number of CPU-seconds that the process spent in kernel mode.」と定め、`%P` を「Percentage of the CPU that this job got, computed as (%U + %S) / %E.」と定義しています（[time(1)](https://man7.org/linux/man-pages/man1/time.1.html)）。

4 つの処理を測ります。

```bash
/usr/bin/time -f "real %e user %U sys %S cpu %P" ./spin 1 1000000000
/usr/bin/time -f "real %e user %U sys %S cpu %P" ./spin 4 1000000000
/usr/bin/time -f "real %e user %U sys %S cpu %P" sleep 2
/usr/bin/time -f "real %e user %U sys %S cpu %P" ./sys 10000000
```

```text
real 2.49 user 2.29 sys 0.18 cpu 99%     # spin、1 スレッド
real 2.60 user 9.69 sys 0.23 cpu 380%    # spin、4 スレッド（各スレッドが同じ量の計算）
real 2.00 user 0.00 sys 0.00 cpu 0%      # sleep 2
real 1.27 user 0.41 sys 0.84 cpu 99%     # getppid を 1000 万回
```

| 処理 | 読み方 |
| --- | --- |
| 1 スレッドの計算 | 経過時間とほぼ同じだけ CPU を使った。`cpu 99%` は「1 コアを使い切った」 |
| 4 スレッドの計算 | 2.6 秒の間に 4 コアで同時に計算したので、**user が real の約 4 倍**になる。`%P` は 100% を超えて 380% |
| sleep | 2 秒経ったが、CPU はほぼ使っていない。遅い原因は CPU ではない |
| getppid の繰り返し | CPU は使い切っているが、時間の 3 分の 2 はカーネルの中（sys） |

1 スレッドの計算で sys が 0.18 秒出ているのは、このときの環境ではほかのコンテナも動いていたためかもしれませんが、原因は確かめていません。同じ計算を後で測り直すと `user 2.40 sys 0.00` でした。

ここから 2 つのことが言えます。

**user + sys が real に近い**なら、そのプロセスは CPU の上で走り続けていて、速くするには計算を減らすか、CPU を速くするしかありません。**user + sys が real よりずっと小さい**なら、プロセスは時間の大半を何かを待って過ごしています。ディスク、ネットワーク、ロック、あるいは CPU の順番待ちです。どれを待っているのかは別の道具で調べる必要がありますが、少なくとも「計算を速くする」は的外れです。

そして**user が real より大きい**のは、複数のスレッドが同時に走ったときだけです。CPU 時間は CPU ごとに足し合わされるので、4 コアで 1 秒走れば 4 秒になります。

<Callout type="tip" title="シェルの time と /usr/bin/time">
  bash で `time` と打つと、`/usr/bin/time` ではなく**シェルの組み込みコマンド**が動きます。出力の形は違いますが、数えているものは同じです。

```text
$ bash -c "time ./spin 4 1000000000"

real	0m2.913s
user	0m11.295s
sys	0m0.045s
```

  `-f` で書式を選びたいときや、最大メモリ使用量（`%M`）も見たいときは、`/usr/bin/time` をフルパスで呼びます。
</Callout>

## CPU 時間はどう数えられるか

CPU 時間は、カーネルが CPU ごとに「いま何をしていたか」を記録して積み上げたものです。もっとも基本的な方式は、タイマー割り込み（ティック）が来るたびに、その瞬間に CPU が何をしていたかを 1 ティックぶん足す、というものです。カーネルの設定項目の説明は、この方式を「This is the basic tick based cputime accounting that maintains statistics about user, system and idle time spent on per jiffies granularity.」と書いています（[init/Kconfig: TICK_CPU_ACCOUNTING](https://github.com/torvalds/linux/blob/master/init/Kconfig)）。ユーザー空間とカーネルの境目を越えるたびに正確な時刻で数える方式も選べますが、「時間を状態ごとの箱に振り分けて積む」という考え方は同じです。

振り分け先の箱は、プロセスの側とマシンの側の 2 つあります。

- プロセスの側: そのプロセスの utime（user）と stime（sys）。`time` や `ps` が見る値
- マシンの側: CPU ごとの user・system・idle・iowait・steal など。`top` の上の行や `vmstat` が見る値

下のシミュレーターは、4 コアのマシンで 10 ティックの間に各 CPU がどの箱に数えられるかを 1 ティックずつ進めます。状況を切り替えて、使用率、`wa` の割合、%CPU がどう変わるかを見てください。

「I/O 待ち → 横で計算」では、待っている時間は変わらないのに、途中から `wa` が消えます。「cgroup 制限」では、CPU がほとんど空いているのにプロセスが進みません。どちらもこの回の後半で実際に起こします。

## CPU 使用率は 2 回読んだ差分の割り算

マシン側の箱は、`/proc/stat` の `cpu` で始まる行に、起動してからの累計として並んでいます。proc_stat(5) は、この値の単位を「measured in units of USER_HZ (1/100ths of a second on most architectures, use sysconf(_SC_CLK_TCK) to obtain the right value)」と説明しています（[proc_stat(5)](https://man7.org/linux/man-pages/man5/proc_stat.5.html)）。今回の環境でも `getconf CLK_TCK` は `100` で、1 単位は 10ms でした。

```text
cpu  user nice system idle iowait irq softirq steal guest guest_nice
```

累計なので、1 回読んだだけでは「いま」の使用率は分かりません。**少し時間を空けて 2 回読み、差分を取って、全体に占める割合を出します。** `top` も `vmstat` も、やっていることはこれです。同じことを 10 行ほどのシェルスクリプトで書けます。

```sh
#!/bin/sh
# usage: stat.sh <command...>  /proc/stat の cpu 行を前後で取り、差分を百分率にする
a=$(head -1 /proc/stat)
"$@"
b=$(head -1 /proc/stat)
echo "$a" "$b" | awk '{
  n=split("user nice system idle iowait irq softirq steal",k," ");
  tot=0; for(i=2;i<=9;i++){d[i]=$(i+11)-$i; tot+=d[i]}
  printf "ticks=%d ", tot;
  for(i=2;i<=9;i++) printf "%s=%.1f%% ", k[i-1], 100*d[i]/tot; print ""}'
```

これで、前の節の処理を包んで測ります（表示を一部省略しています）。

```text
== idle (sleep 2)
ticks=1670 user=2.5% nice=0.0% system=2.2% idle=87.7% iowait=0.1% softirq=7.6% steal=0.0%
== spin 4 threads
ticks=2247 user=48.1% nice=0.0% system=1.6% idle=43.5% iowait=0.0% softirq=6.9% steal=0.0%
== getppid x 10M
ticks=1026 user=6.2% nice=0.0% system=9.2% idle=76.5% iowait=0.0% softirq=8.1% steal=0.0%
```

`sleep 2` の間に進んだのは 1670 単位でした。**8 CPU × 2 秒 × 100 = 1600** なので、全 CPU の時間を合計した量になっています（`sleep` の起動と終了の時間が少し乗ります）。使用率の分母は「CPU の数 × 経過時間」です。

だから、4 スレッドが 4 コアを使い切っていても、8 コアのマシン全体では **user 48.1%** にしかなりません。1 スレッドの処理が 1 コアを使い切っていれば、全体では 12.5% です。**マシン全体の使用率が低くても、1 コアが張り付いていて、そこが詰まっている**ことはよくあります。`top` で `1` を押すと CPU ごとの行に切り替わります（`mpstat -P ALL 1` でも見られます）。

<Callout type="warn" title="コンテナの中の /proc/stat は、マシン全体の値">
  今回の実測はすべてコンテナの中で `/proc/stat` を読んでいますが、見えているのは**仮想マシン全体**の値です。コンテナの CPU 数を制限しても、`/proc/stat` の行の数も中身も変わりません。

  実際、同じ VM でほかの作業のコンテナが重い処理をしていた時間帯には、`fsync` しか動かしていないのに `user=53.2%` と出ました。上の結果は、`docker stats` でほかのコンテナが静かなことを確かめてから取り直したものです。コンテナ単位の CPU 時間は、後で見る cgroup の `cpu.stat` から読みます。
</Callout>

## 内訳を読む

`top` の 2 行目は、この差分を項目ごとに並べたものです。top(1) は各項目を次のように定義しています（[top(1)](https://man7.org/linux/man-pages/man1/top.1.html)）。

| 項目 | top(1) の定義 | 増えるとき |
| --- | --- | --- |
| `us` | time running un-niced user processes | アプリケーションの計算 |
| `sy` | time running kernel processes | システムコール、ページフォールトの処理、カーネルスレッド |
| `ni` | time running niced user processes | `nice` で優先度を下げたプロセスの計算 |
| `id` | time spent in the kernel idle handler | 何も走っていない |
| `wa` | time waiting for I/O completion | 下で詳しく見る |
| `hi` | time spent servicing hardware interrupts | NIC やディスクの割り込みの処理 |
| `si` | time spent servicing software interrupts | パケットの受信処理など、割り込みの後半（第 55 回） |
| `st` | time stolen from this vm by the hypervisor | 仮想マシンが物理 CPU を待たされた |

`getppid` を繰り返すと `system` が `user` を上回りました（9.2% と 6.2%）。1 回 1 回は短いシステムコールでも、ユーザー空間とカーネルを行き来するたびにカーネル側の時間がかかることは、第 41 回で見たとおりです。`sy` が高いときは、`strace -c` や `perf` でどのシステムコールが多いかを調べます。

`ni` は、`nice` で優先度を下げたプロセスの時間です。次の節の実験で、`nice -n 19` で動かした計算が `nice=76.4%` として現れます。`us` だけを見て「CPU は空いている」と判断すると、優先度の低い処理が CPU を埋めていることを見落とします。

今回の環境では、何もしていなくても `softirq` が 7〜9% ありました。仮想マシンの中での割り込み処理の影響だと思われますが、何がこの時間を使っているかまでは確かめていません。

### iowait は I/O の量を表していない

第 192 回の表では「`wa` が高い = I/O 待ち」と書きました。高ければ I/O を待っているタスクがいるのは確かですが、逆は成り立ちません。**`wa` が低くても、I/O で詰まっていないとは言えません。**

`wa` は「CPU が暇で、かつその CPU で I/O の完了を待っているタスクがいる」時間です。CPU が I/O を待っているわけではありません。proc_stat(5) はこの項目に「This value is not reliable」と明記し、理由の 1 つ目に「The CPU will not wait for I/O to complete; iowait is the time that a task is waiting for I/O to complete.」と書いています。2 つ目の理由は、マルチコアでは待っているタスクがどの CPU の上にもいないので、CPU ごとの iowait を決めにくいことです（[proc_stat(5)](https://man7.org/linux/man-pages/man5/proc_stat.5.html)）。

実際に崩してみます。まず `fsync` を 1000 回だけ動かし、次に同じことを、優先度を下げた計算を 8 スレッド横で走らせながら行います。

```sh
./stat.sh /usr/bin/time -f "real %e user %U sys %S" ./fsync 1000
nice -n 19 ./spin 8 100000000000 &
./stat.sh /usr/bin/time -f "real %e user %U sys %S" ./fsync 1000
```

```text
== fsync x1000 alone
real 1.51 user 0.00 sys 0.54
ticks=1253 user=2.0% nice=0.0% system=4.1% idle=81.2% iowait=3.9% softirq=8.9% steal=0.0%
== fsync x1000 + nice spin 8
real 12.17 user 0.00 sys 0.91
ticks=8375 user=2.4% nice=76.4% system=2.2% idle=15.2% iowait=0.4% softirq=3.4% steal=0.0%
```

1 回目、`fsync` するプロセスは 1.51 秒のうち CPU を 0.54 秒しか使わず、残りの約 1 秒は書き込みの完了を待っていました。それでも `iowait` は **3.9%** です。待っているのは 1 本だけで、8 CPU のうち多くても 1 CPU ぶん（12.5%）にしかならないからです。

2 回目、`fsync` は 12.17 秒かかり、待ち時間はむしろ大きく増えました。それなのに `iowait` は **0.4%** に下がっています。**待っているタスクがいても、その CPU で別のタスクが走れば、その時間は `wa` ではなく `ni` や `us` に数えられる**からです。シミュレーターの「I/O 待ち → 横で計算」で見たのは、この現象です（2 回目で `fsync` 自体が 8 倍遅くなった理由は、この環境の仮想ディスクの実装が関係していると思われますが、確かめていません）。

I/O が詰まっているかどうかは、`wa` ではなく I/O の側の指標で見ます。デバイスごとの待ち時間なら `iostat -x` の `r_await` / `w_await`、プロセスごとの I/O 量なら `pidstat -d` です。I/O の完了を待って眠っているタスクの数は、次の回で見るロードアベレージにも入ってきます。

### steal は仮想マシンの外の話

`st` は、仮想マシンの vCPU が動こうとしていたのに、ハイパーバイザが物理 CPU をほかの仮想マシンに回していた時間です。仮想マシンの中からは、その間に何が起きたかは見えず、時間が抜けたことだけが分かります。

クラウドのインスタンスで `st` が継続して出ているなら、同じ物理マシンのほかの利用者と CPU を取り合っているか、CPU クレジットを使い切って性能を絞られている可能性があります。仮想マシンの中でどれだけ調べても原因は見つかりません。今回の OrbStack の仮想マシンでは、ほかのコンテナが重い処理をしている間も `st` は 0.0% のままでした。

## プロセスの %CPU が 100% を超える

マシン全体の使用率は「全 CPU の時間」で割りますが、プロセスごとの `%CPU` は**そのプロセスの CPU 時間を経過時間で割る**のが既定です。`spin` を 4 スレッドで動かしている間の `top` です。

```text
%Cpu(s): 48.1 us,  1.9 sy,  0.0 ni, 43.7 id,  0.0 wa,  0.0 hi,  6.2 si,  0.0 st

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
     55 root      20   0   35288   1248   1116 S 385.6   0.0   0:09.12 spin
```

上の行は 8 CPU 全体の 48.1%、下の行はプロセスの 385.6% です。top(1) は `%CPU` について、マルチスレッドのプロセスでは「amounts greater than 100% may be reported」と書き、続けて「if Irix mode is Off, top will operate in Solaris mode where a task's cpu usage will be divided by the total number of CPUs. You toggle Irix/Solaris modes with the ‘I’ interactive command.」と説明しています（[top(1)](https://man7.org/linux/man-pages/man1/top.1.html)）。

| 方式 | 割る数 | 4 スレッドの spin（8 CPU） | 上限 |
| --- | --- | --- | --- |
| Irix モード（top の既定） | 経過時間 | 385.6% | CPU 数 × 100% |
| Solaris モード（`I` で切り替え） | 経過時間 × CPU 数 | 385.6 ÷ 8 ≈ 48.2% | 100% |

Solaris モードにすると、上の行の `us` とほぼ同じ値になります。どちらも同じ CPU 時間を、別の数で割っているだけです。監視ツールのグラフがどちらの方式で描かれているかは、ツールごとに確かめる必要があります。「100% を超えたからおかしい」と判断するのも、「100% だから余裕がない」と判断するのも、割る数を知らないと間違えます。

<Callout type="warn" title="ps の %CPU は「起動してから」の平均">
  `ps` の `%CPU` は、`top` と同じ名前でも意味が違います。ps(1) は「Currently, it is the CPU time used divided by the time the process has been running (cputime/realtime ratio), expressed as a percentage.」と書いています（[ps(1)](https://man7.org/linux/man-pages/man1/ps.1.html)）。直近の数秒ではなく、**プロセスが起動してから今までの平均**です。

  3 秒眠ってから計算を始める bash を、起動の 6 秒後に両方で見ました。

```text
$ ps -o pid,etime,time,%cpu,comm -p 6
    PID     ELAPSED     TIME %CPU COMMAND
      6       00:06 00:00:02 48.0 bash

$ top -b -n 2 -d 1 -p 6     # 2 回目の表示
      6 root      20   0    4044   3076   2776 R  99.0   0.0   0:04.10 bash
```

  `top` は直近 1 秒の値なので、計算を始めた後の状態（99.0%）を表します。`ps` は眠っていた 3 秒も分母に入れるので、半分ほど（48.0%）に出ます。何日も動いているサーバのプロセスで、急に CPU を使い始めたものは、`ps` ではほとんど目立ちません。
</Callout>

## 使用率が低いのに遅い：CPU の上限

コンテナに CPU の上限を付けると、マシン全体の CPU が空いていても、プロセスは止められます。仕組みは第 178 回で見ました。cgroup v2 の文書は `cpu.max` を「$MAX $PERIOD」の形式とし、「the group may consume up to $MAX in each $PERIOD duration」と説明しています（[cgroup-v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)）。ここでは、それが観測の数字にどう現れるかを見ます。

同じ 1 スレッドの計算を、上限なしと `--cpus=0.5` で動かします。

```text
# 上限なし
real 2.41 user 2.40 sys 0.00 cpu 99%

# --cpus=0.5（cpu.max = 50000 100000）
real 4.80 user 2.42 sys 0.00 cpu 50%
ticks=3963 user=12.4% nice=0.0% system=1.9% idle=78.3% iowait=0.0% softirq=7.4% steal=0.0%
nr_periods 49
nr_throttled 48
throttled_usec 2363106
```

必要な CPU 時間（user）はどちらも 2.4 秒ですが、上限付きでは経過時間が倍になりました。そしてその間、**マシン全体は 78.3% が idle** です。プロセスの `%P` も 50% で、「CPU を使い切っている」ようには見えません。ホストの使用率のグラフを見ても、プロセスの `%CPU` を見ても、遅い理由は出てこない。答えは cgroup の `cpu.stat` にあります。49 回の期間のうち 48 回で予算を使い切って止められ、合計 2.36 秒待たされています。

スレッドが多いと、この止められ方はさらに激しくなります。4 スレッドの計算を `--cpus=1` で動かしました。

```text
real 12.95 user 12.51 sys 0.48 cpu 100%
usage_usec 13032096
nr_periods 133
nr_throttled 127
throttled_usec 27042838
```

4 スレッドが同時に走ると、100ms の予算を 25ms ほどで使い切り、残りの 75ms は 4 本とも止まります。上限なしなら 2.6 秒で終わる計算に 13 秒かかりました。

ここで `throttled_usec` は 27 秒で、**経過時間の 13 秒より長く**なっています。カーネルは止められていた時間を CPU ごとの実行キューの単位で記録し、止めが解けるたびにグループの合計へ足しているからです（[kernel/sched/fair.c の unthrottle_cfs_rq](https://github.com/torvalds/linux/blob/master/kernel/sched/fair.c)）。4 つの CPU で同時に止められれば、4 倍の速さで増えます。「止められていた実時間」ではなく「止められていたスレッドの延べ時間」に近い値として読みます。

<Callout type="tip" title="コンテナの中では何を見るか">
  コンテナの中で `top` を見ても、上の行はマシン全体の値です。コンテナにとっての使用率は、`/sys/fs/cgroup/cpu.stat` の `usage_usec` の差分を経過時間と `cpu.max` の上限で割って求めます。そして遅いと感じたら、まず `nr_throttled` が増えているかを見ます。cgroup v2 の文書によると、`usage_usec` / `user_usec` / `system_usec` は CPU コントローラが有効でなくても常に出ており、`nr_periods` 以降の項目はコントローラが有効なときに出ます（[cgroup-v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)）。
</Callout>

## まとめ

| 知りたいこと | 見るもの | 落とし穴 |
| --- | --- | --- |
| CPU が原因か、待ちが原因か | `time` の real と user + sys | user > real はマルチスレッドの印 |
| マシン全体の使い方 | `/proc/stat` の差分（`top`、`vmstat`） | 分母は CPU 数 × 経過時間。1 コアの張り付きが薄まる |
| I/O で詰まっているか | `iostat -x`、`pidstat -d` | `wa` は低くても I/O 待ちがないとは限らない |
| 仮想マシンの外の取り合い | `st` | 中からは原因を調べられない |
| プロセスごとの重さ | `top` の `%CPU` | 既定は経過時間で割るので 100% を超える。`ps` は起動してからの平均 |
| コンテナが遅い理由 | `cpu.stat` の `nr_throttled`、`throttled_usec` | ホストもプロセスも、使用率は低く見える |

- CPU 時間は、カーネルが CPU ごとに状態を箱に振り分けて積み上げた量。使用率も `%CPU` も、その割り算
- 使用率は累計を 2 回読んだ差分から出す。分母が「全 CPU」か「1 プロセスの経過時間」かで、同じ時間が 48% にも 385% にもなる
- `wa` は「暇な CPU」の一種で、I/O の量の指標ではない
- CPU の上限で止められているプロセスは、どの使用率にも遅さが現れない

次の第 194 回では、`top` の 1 行目に出ているもう 1 つの数字、ロードアベレージを扱います。使用率が「CPU がどれだけ埋まっていたか」なら、ロードアベレージは「どれだけのタスクが走りたがっていたか」で、ここに I/O を待って眠っているタスクも入ってきます。
