## 誰が span を作るのか

前回、span を作るには「ここから始まった」「ここで終わった」と記録するコードが要る、と書きました。素直に書けば、こうなります。

```python
def get_order(order_id):
    with tracer.start_as_current_span("get_order") as span:
        span.set_attribute("order.id", order_id)
        row = db.execute("SELECT ...", order_id)
        return row
```

これを自分で書くのが **手動計装** です。何を記録するかを細かく決められますが、すべての HTTP の受け口、すべての DB の呼び出し、すべての外部への呼び出しに書くのは現実的ではありません。

一方で、HTTP サーバや DB のドライバは、どのアプリでも**同じライブラリの同じ関数**を通ります。そこに一度だけ記録のコードを差し込めば、そのライブラリを使う全アプリで span ができます。これが **自動計装** です。

ただし、アプリのコードもライブラリのコードも書き換えないと決めた以上、**どこかに割り込むしかありません**。割り込む場所は、大きく 3 つあります。

```
 ソースコード ──→ コンパイル ──→ 実行ファイル / バイトコード ──→ 読み込み ──→ 実行中
                    ▲                                            ▲            ▲
                ② コンパイル時                              ① 読み込み時    ③ 外から
```

## ① 読み込み時に書き換える

**言語のランタイムが「コードを読み込む瞬間」に口を開けている**なら、そこで中身を差し替えられます。第 30 回のローダが実行ファイルを読み込み、第 32 回の JIT が機械語を作る、その手前です。

### Java: クラスを読み込むたびに、バイトコードを書き換える

Java には、ランタイムの仕組みとして **agent** があります。起動時に `-javaagent` で JAR を指定すると、アプリの `main` より先に、その JAR の `premain` が呼ばれます（[java.lang.instrument](https://docs.oracle.com/en/java/javase/21/docs/api/java.instrument/java/lang/instrument/package-summary.html)）。

```bash
java -javaagent:agent.jar -jar app.jar
```

`premain` は `Instrumentation` という口を受け取り、そこに **ClassFileTransformer** を登録します。以降、JVM がクラスを読み込むたびに、そのクラスのバイトコードが transformer に渡されます。transformer は、書き換えたバイトコードを返せます。

```
JVM: HttpServlet.class を読み込む
  │
  ▼
transformer(バイトコード) ──→ service() の入口に「span を開始」、出口に「span を終了」を足す
  │
  ▼
書き換え後のバイトコードを検証して、JIT へ
```

仕様は、agent について「読み込み時に任意の方法でクラスを変換できる」と明記しています。読み込み済みのクラスも、許可されていれば後から変換し直せます。

**バイトコードという中間表現がある**ことが、この方式を支えています。機械語ではなく、型と構造が残った命令列なので、「このメソッドの入口」「この呼び出しの前後」を確実に特定して書き足せます。書き足したコードは、JVM が通常どおり検証し、JIT で機械語にします。

### .NET: JIT の直前に、IL を差し替える

.NET の CLR には、**プロファイラ API** という口があります。環境変数で指定したネイティブのライブラリが、ランタイムの中に読み込まれ、モジュールの読み込みや JIT コンパイルの開始のたびに呼び出されます（[Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/framework/unmanaged-api/profiling/profiling-overview)）。

このとき、メソッドの中間表現（IL）を読み出し、書き換えたものを差し戻せます。OpenTelemetry の .NET 版の自動計装は、この口を使ってメソッドの入口と出口に計装を足し、JIT に作り直させています（[opentelemetry-dotnet-instrumentation](https://github.com/open-telemetry/opentelemetry-dotnet-instrumentation/blob/main/docs/design.md)）。

**第 32 回の JIT が、そのまま割り込み口になっている**わけです。

### Python と Node: 関数を差し替える

Python や JavaScript では、関数やクラスは**実行中に書き換えられる値**です。モジュールの属性を別の関数に置き換えるだけで、以後の呼び出しはすべて新しい関数を通ります。これを **モンキーパッチ** と呼びます。

```python
import requests

original = requests.Session.send

def traced_send(self, request, **kwargs):
    with tracer.start_as_current_span("HTTP " + request.method):
        return original(self, request, **kwargs)

requests.Session.send = traced_send     # 以後、全員がこちらを通る
```

問題は、**アプリがライブラリを使う前に差し替えを済ませる**ことです。そのため、起動の仕組みに割り込みます。

- **Python**: 自動計装の起動コマンドは、インタプリタの起動時に自動で読み込まれる `sitecustomize` モジュールが先に見つかるよう `PYTHONPATH` を調整し、アプリより先に差し替えを行います（[OpenTelemetry](https://opentelemetry.io/docs/zero-code/python/)）
- **Node**: `node --require` で先に読み込ませたモジュールが、`require()` の裏にあるモジュールの読み込み処理にフックを掛けます。対象のライブラリが読み込まれた瞬間に、その関数を包んだものに差し替えます（[OpenTelemetry](https://opentelemetry.io/docs/languages/js/libraries/)）

<Callout type="warn" title="読み込みの経路が変わると、フックが外れる">
  この方式は、**ライブラリが決まった経路で読み込まれる**ことを前提にしています。
  Node で CommonJS の `require` にだけフックを掛けていると、ES Modules の `import` では発火しません。
  ビルド時に 1 ファイルにまとめる（バンドルする）と、読み込みそのものが起きません。
  「自動計装が何もしていない」という事故の多くは、この前提が崩れたときです。
</Callout>

## ② コンパイル時に書き足す

Go や Rust、C++ のように、**機械語の実行ファイルを 1 つ作って終わり**の言語には、①の口がありません。バイトコードも無く、関数を実行中に差し替える仕組みもありません。

残る割り込み口は、**コンパイルの途中**です。第 27 回で見たコンパイルの段階のどこかで、ソースや中間表現に計装を書き足します。

Go のツールチェーンには、コンパイラなど各段階の道具を呼ぶ前に、指定したプログラムを間に挟む `-toolexec` という仕組みがあります。これを使うと、依存しているライブラリや標準ライブラリも含めて、コンパイラに渡る直前のソースを書き換えられます（[OpenTelemetry](https://opentelemetry.io/docs/zero-code/go/compile-time/)）。

```bash
go build -toolexec=<書き換えるプログラム> ./...
```

アプリのソースは変わりませんが、**ビルドの手順は変わります**。できあがったバイナリの中に、計装はすでに焼き込まれています。

## ③ 外から差し込む

最後の選択肢は、**プログラムに一切手を入れず、外から覗く**ことです。第 83 回のデバッガが、まさにこれをしていました。

第 83 回で見たとおり、ブレークポイントは命令を `int3` に書き換え、そこに来たら止めて中を覗く仕組みでした。第 103 回の **uprobe** は、同じことをカーネルがやります。ユーザ空間の関数の入口に印を付け、そこに来たら**止めずに** eBPF のプログラムを走らせます。

```
アプリのプロセス                       カーネル
┌───────────────────┐
│ http.(*Server).   │
│   ServeHTTP  ◀─── uprobe ───→ eBPF プログラム
│   ...             │           ・引数のレジスタを読む
│   ret        ◀─── 出口 ─────→ ・経過時間を計る
└───────────────────┘           ・リングバッファでユーザ空間の集計役へ
```

アプリの再起動も、再ビルドも要りません。言語も問いません。**機械語の関数であれば、どれにでも当てられます**。これが eBPF による自動計装の魅力です。

ただし、外から見るということは、**中の約束事を外から推測する**ということです。ここに限界が集中します。

## 外から見ることの限界

### 構造体の形は、バイナリの版で変わる

uprobe で分かるのは、関数に来たときの**レジスタとメモリの中身**だけです。「HTTP のメソッドとパス」を取り出すには、引数の構造体の何バイト目に何があるかを知っていなければなりません。

これは第 31 回の ABI と、第 1 章のアラインメントの話そのものです。そして、その配置は**ライブラリの版が変わるたびに変わりえます**。フィールドが 1 つ増えるだけで、すべてのオフセットがずれます。外から覗く計装は、対象の版ごとにオフセットの表を持つ必要があります。第 83 回の DWARF のようなデバッグ情報が残っていれば読み取れますが、本番のバイナリからは消されていることも多い。

### Go は独自のやり方で動いている

Go は、C とは違う独自の決まりで動いています。

- **呼び出し規約が違う**: amd64 では 1.17 から、引数を独自の規則でレジスタに載せて渡します（[Go 1.17](https://go.dev/doc/go1.17)）。C の ABI を前提にした道具では引数が読めません
- **スタックが動く**: goroutine のスタックは小さく始まり、足りなくなると**丸ごと別の場所にコピーされます**

後者は、関数の出口を捕まえる `uretprobe` と相性が最悪です。`uretprobe` は、スタック上の戻り先アドレスを自分の用意した場所に書き換えることで出口を捕まえます。その間にスタックがコピーされると、書き換えた戻り先が狂い、**観測している側がアプリを落とします**。Go に対しては `uretprobe` を使わず、関数の中の `ret` 命令に 1 つずつ uprobe を置くという回避策が取られます（[Brendan Gregg](https://www.brendangregg.com/blog/2017-01-31/golang-bcc-bpf-function-tracing.html)）。

### 暗号化の前後のどこで読むか

HTTPS の通信を観測したいとき、第 53 回のソケットを通るデータはすでに暗号化されています。ソケットで読んでも中身は分かりません。

中身を読むには、**暗号化する直前**、つまり TLS のライブラリの「平文を渡して暗号化してもらう関数」に当てる必要があります。ところが、TLS のライブラリは言語や環境ごとに違います。C のアプリは共有ライブラリの OpenSSL を使い、Go は標準ライブラリに自前の実装を静的リンクしています（第 29 回）。**どの関数に当てればよいかは、アプリの作り方次第**です。

### コンテキストを書き足せない

最も大きな壁は、前回の **コンテキストの伝播** です。

外から覗くだけなら、「この HTTP リクエストが来て、何ミリ秒かかった」は分かります。しかし、そのリクエストの処理中に**別のサービスを呼び出すとき、`traceparent` ヘッダを書き足す**ことはできません。アプリが組み立てたリクエストの中身を、外から書き換える必要があるからです。

```
サービス A ──(traceparent なし)──→ サービス B
    ▲                                  ▲
 span は作れる                     span は作れる
    └────── 親子として、つながらない ──────┘
```

結果として、**1 台ごとの span はできるが、サービスをまたいだ木にならない**、ということが起きます。これは、観測のためにアプリの外から中身を書き換えるのが本質的に難しい、ということです。第 83 回の最後で見たとおり、他人のプロセスの中身を書き換えられる権限は、安全の面でも強く制限されています。

<Callout type="note" title="それでも外から見る価値">
  1 台ごとの span だけでも、「どのサービスの、どの受け口が遅いか」は分かります。
  言語を問わず、再起動もせずに、全サービスの入口と出口の遅延が揃う。
  **最初の一歩として、何も入っていない状態よりはずっと多くが見える**ということです。
  木としてつなぐ必要が出た箇所から、①や②、手動計装を足していきます。
</Callout>

## どれを選ぶか

| 方式 | 割り込む場所 | 必要なもの | 得意 | 苦手 |
| --- | --- | --- | --- | --- |
| **読み込み時** | ランタイムの読み込み口（Java、.NET、Python、Node） | 起動オプションの追加 | コンテキストの伝播まで含めた完全なトレース | バイトコードや動的な差し替えのない言語 |
| **コンパイル時** | ビルドの途中（Go など） | ビルド手順の変更 | 静的なバイナリにも計装を焼き込める | 再ビルドが要る |
| **外から** | uprobe（eBPF） | カーネルの権限 | 再起動も再ビルドも不要、言語を問わない | 構造体の形の推測、コンテキストの伝播 |
| **手動** | 自分のコード | コードを書く | 業務上の意味（注文 ID、ユーザの種類）を記録できる | 手間 |

自動計装が作るのは、**ライブラリの境界**の span です。HTTP を受けた、DB に問い合わせた、外部を呼んだ。一方、「在庫の引き当て」「割引の計算」のような**業務の区切り**は、ライブラリからは見えません。そこは手動で書くしかありません。

実際には、**自動計装で骨組みを作り、手動計装で肉付けする**のが普通です。前回見たとおり、API は共通なので、自動で作られた span の下に、手動の span を子としてつなげられます。

## まとめ

- 自動計装は、コードを書き換えない代わりに、どこかに割り込む
- 読み込み時: Java agent はクラスの読み込みでバイトコードを、.NET は JIT の直前に IL を書き換える。Python と Node は起動時に関数を差し替える
- コンパイル時: 実行時の口がない Go などは、ビルドの途中でソースに計装を書き足す
- 外から: uprobe はデバッガのブレークポイントと同じ発想で、止めずに関数の入口と出口を覗く
- 外から見る方式は、構造体の配置、Go の独自の ABI と動くスタック、暗号化の位置、コンテキストの伝播で限界に当たる
- 自動計装はライブラリの境界を、手動計装は業務の区切りを記録する。両方を組み合わせる

最後に、手元で直接測るための道具をまとめます。
