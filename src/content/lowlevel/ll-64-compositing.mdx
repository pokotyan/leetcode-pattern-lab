## 残っている 2 つの仕事

前回のペイントの段が出力したのは、描画命令の列（表示リスト）でした。画面に出すまでには、まだ 2 つの仕事が残っています。

1. **ラスタライズ**: 描画命令を実行して、ピクセルの格子にする
2. **合成**: 複数の格子を、正しい位置・順番・透明度で重ね、1 枚の画面にする

この 2 つをまとめて扱うのが、パイプラインの最後の段です。そしてこの段は、**メインスレッドとは別のスレッドで動きます**。この回の話はほぼすべて、この一点から出てきます。

## 1 枚の絵ではなく、何枚かの層

ページ全体を 1 枚の絵として描くと、どこか 1 か所が変わっただけで全体を描き直すことになります。そこでブラウザは、ページを何枚かの **レイヤ**（層）に分けて描きます。

```
   画面に見えるもの             実際には
 ┌──────────────────┐      ┌──────────────────┐  レイヤ 3: 固定ヘッダ
 │ ヘッダ（固定）      │      └──────────────────┘
 │                    │      ┌──────────────────┐  レイヤ 2: 動くモーダル
 │   ┌──────────┐     │      │   ┌──────────┐    │  （transform で移動中）
 │   │ モーダル   │     │      │   └──────────┘    │
 │   └──────────┘     │      └──────────────────┘
 │ 本文 ……            │      ┌──────────────────┐  レイヤ 1: 本文
 └──────────────────┘      │ 本文 ……            │  （スクロールする）
                           └──────────────────┘
```

各レイヤは、一度ラスタライズすれば **GPU のメモリにテクスチャとして置いておけます**。あとは重ねるときに、位置をずらす、透明度を掛ける、拡大縮小や回転の行列を掛ける、といった操作だけで画面を作れます。これらは GPU が最も得意とする計算です。第 12 回で見た SIMD を、画素の数だけ並べた装置が GPU だと考えると分かりやすいでしょう。

**ラスタライズは重く、合成は軽い**。だから「一度描いたものを描き直さず、重ね方だけを変える」ことが、速さの鍵になります。

## 合成だけで済むプロパティ

前回の表を思い出してください。`transform` と `opacity` だけは、**レイアウトもペイントもやり直さず、合成の段だけで**反映できました。

理由は、この 2 つが「レイヤの中身」ではなく「レイヤの重ね方」を変えるものだからです。

- `transform: translateX(100px)`: レイヤのテクスチャをそのまま 100px ずらして重ねる
- `opacity: 0.5`: レイヤのテクスチャに 0.5 を掛けて重ねる

中身の画素は 1 つも変わらないので、描き直す必要がありません。web.dev も、合成だけで扱えるプロパティは今のところ `transform` と `opacity` の 2 つだと書いています（[web.dev](https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count)）。

対して `left` や `width` を動かすと、要素の位置や大きさが変わるので、レイアウトからやり直しです。見た目が同じアニメーションでも、1 フレームあたりの仕事の量が桁違いになります。

## メインスレッドを待たない

ここで、合成の段が別のスレッドで動くことが効いてきます。

Chrome の構成では、メインスレッドがペイントまでを済ませると、その結果（表示リストと、各レイヤの位置関係を表す木）を **コンポジタスレッド**に渡します。これを commit と呼びます。以降のラスタライズと合成は、コンポジタスレッドと GPU の側で進みます（[RenderingNG のアーキテクチャ](https://developer.chrome.com/docs/chromium/renderingng-architecture)）。

```
メインスレッド   ─ JS ─ style ─ layout ─ paint ─┐commit ─ JS（重い処理）──────────
                                               ▼
コンポジタスレッド ────────────────────────── raster ─ 合成 ─ 合成 ─ 合成 ─ 合成 ─
                                                     フレーム フレーム フレーム フレーム
```

一度 commit が済めば、**メインスレッドが JavaScript で塞がっていても、コンポジタスレッドは合成を続けられます**。

- スクロール: レイヤの表示位置をずらすだけなので、コンポジタスレッドだけで進められる
- `transform` と `opacity` のアニメーション: 開始時に動かし方（時刻ごとの値）を渡しておけば、コンポジタスレッドが毎フレーム値を進める

RenderingNG の文書は、レイアウト・ペイントを省ける視覚効果なら「完全にコンポジタスレッドで実行でき、メインスレッドを飛ばせる」と書いています（[RenderingNG のアーキテクチャ](https://developer.chrome.com/docs/chromium/renderingng-architecture)）。重い JavaScript の最中でもページがスクロールでき、ローディングのくるくるが回り続けるのはこのためです。

<Callout type="note" title="GPU を触るのは別のプロセス">
  実際に GPU に命令を出すのは、レンダラのプロセスではなく **GPU プロセス**です。
  第 61 回で見たとおり、レンダラはサンドボックスの中にあり、GPU のドライバを直接触らせるのは危険だからです。
  コンポジタスレッドは合成の指示（どのテクスチャをどこに描くか）を作り、GPU プロセスがそれをまとめて実行します。
</Callout>

## 入力も、メインスレッドを待たずに済むとは限らない

スクロールがコンポジタスレッドだけで進むのは、**スクロールを止める JavaScript がない**と分かっているときに限ります。

`wheel` や `touchstart` のリスナーは、`event.preventDefault()` でスクロールを取り消せます。リスナーが付いている領域でスクロールが始まると、コンポジタスレッドは「取り消されるかもしれない」ので、**メインスレッドがリスナーを実行し終えるまで待たなければなりません**。Chrome はこの領域を「ファストスクロールできない領域」として記録しています（[Inside look at modern web browser, part 4](https://developer.chrome.com/blog/inside-browser-part4)）。

```js
// document 全体に付けると、ページ全体でスクロールがメインスレッド待ちになる
document.addEventListener('touchstart', onTouch)

// passive: true は「preventDefault しない」という約束。コンポジタは待たずに進める
document.addEventListener('touchstart', onTouch, { passive: true })
```

`passive: true` は、第 45 回で見たノンブロッキングの考え方に似ています。**待つ必要がないことを宣言して、待ちをなくす**のです。

## 1 フレームの締め切り

画面は、決まった間隔で書き換わります。60Hz のディスプレイなら 1 秒に 60 回、つまり約 16.7ms ごとです。この区切りの合図を **vsync** と呼びます。

HTML の仕様も、ブラウザが 60Hz の更新を目指すなら、描画の機会は最大で 60 分の 1 秒（約 16.7ms）ごとに来ると書いています。維持できなければ、ときどきフレームを落とすより、安定して保てる 1 秒 30 回に落とすこともある、としています（[HTML Living Standard](https://html.spec.whatwg.org/multipage/webappapis.html#rendering-opportunity)）。

| ディスプレイ | 1 フレームの長さ |
| --- | --- |
| 60Hz | 約 16.7ms |
| 120Hz | 約 8.3ms |
| 144Hz | 約 6.9ms |

この時間の中に、JavaScript、スタイル、レイアウト、ペイント、そして合成までを収めなければなりません。実際にはブラウザ自身の仕事もあるので、アプリケーションに使える時間はもっと短くなります。

**間に合わなかったフレームは、次の vsync まで前の絵のまま**になります。アニメーションが一瞬止まって跳ぶ、スクロールが引っかかる。これを **ジャンク**（jank）と呼びます。

<Callout type="tip" title="締め切りのあるスケジューリング">
  第 36 回で見た OS のスケジューラは、公平に CPU を配ることを目標にしていました。
  ブラウザの描画は違います。**16.7ms ごとに必ず 1 枚出す**という締め切りがあり、
  1ms 遅れても 16.7ms 遅れても、そのフレームを落としたことに変わりはありません。
  実時間システムの考え方に近く、平均の速さより**最悪の 1 フレーム**が体験を決めます。
  第 74 回で見たとおり、タイマで「16ms 後に起こして」と頼んでも正確には起きないので、
  描画の合図は vsync という外からの信号に揃えられています。
</Callout>

## レイヤを増やせば速くなる、わけではない

合成だけで済むなら、すべての要素を別々のレイヤにすればよいように見えます。`will-change: transform` を付けると、ブラウザはその要素を最初から専用のレイヤに分けてくれます。

しかし、レイヤにはコストがあります。

- **メモリ**: レイヤごとにテクスチャを持つ。画面いっぱいのレイヤなら、1 枚で幅 × 高さ × 4 バイト（RGBA）。高解像度の画面では 1 枚で十数 MB になる
- **転送**: テクスチャは GPU に送らなければならず、CPU と GPU の間の帯域と、GPU のメモリを食う
- **管理**: 重なりの順番や、どのレイヤがどのレイヤの上にあるかの計算が増える

web.dev は「レイヤを作るたびにメモリと管理が必要で、それはタダではない」と書き、不要な昇格をしないよう勧めています（[web.dev](https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count)）。第 16 回のキャッシュと同じで、**速い層は小さく保たなければ速くない**のです。

## 開発者ツールで見る

- **Layers パネル**: ページがどのレイヤに分かれ、各レイヤがどれだけのメモリを使っているかを 3D で見られる
- **Rendering タブの Paint flashing**: 描き直された領域が緑に光る。`transform` のアニメーション中に何も光らなければ、合成だけで済んでいる
- **Performance パネルの Frames**: フレームごとに、間に合ったか落としたかが並ぶ

アニメーションが重いときは、まず「光っているか」を見ます。光っていれば、合成の前の段から毎フレームやり直しています。

## まとめ

- パイプラインの最後の段は、描画命令をピクセルにするラスタライズと、層を重ねる合成
- ページは複数のレイヤに分けて描かれ、各レイヤは GPU のテクスチャとして保持される。描き直しは重く、重ね直しは軽い
- `transform` と `opacity` はレイヤの重ね方だけを変えるので、合成だけで済む
- 合成はコンポジタスレッドで動くため、メインスレッドが塞がっていてもスクロールや合成だけのアニメーションは進む
- スクロールを取り消せるリスナーがあると、コンポジタはメインスレッドを待つ。`passive: true` で待ちをなくせる
- 60Hz なら 1 フレーム約 16.7ms。間に合わなければフレームが落ちてジャンクになる
- レイヤはメモリと転送のコストを持つ。増やせば速くなるわけではない

次は、メインスレッドの側に戻ります。JavaScript、イベント、そして描画の段が、1 本のスレッドの上でどういう順番で回っているのか、ブラウザのイベントループを見ます。
