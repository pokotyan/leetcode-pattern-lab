## 書き込みは、読み出しのようには逃がせない

前回までの 3 回は、読み出しを速くする方法でした。アプリの中に持つ、許される古さの範囲で使い回す、HTTP とプロキシに任せる。どれも「同じ答えを何度も計算しない」ための工夫です。

書き込みには、この手が使えません。届いたデータはどこかに残さなければならず、キャッシュで返事をしても、データベースの中身は変わりません。そこでこの回では、書き込みの **回数** を減らす方法を見ます。

| 方法 | 何をまとめるか | 代わりに受け入れるもの |
| --- | --- | --- |
| 1 つのトランザクションに入れる | コミット（ディスクへの書き出しの待ち） | 途中で失敗したときの巻き戻しが大きくなる |
| 複数行の `VALUES` で 1 文にする | 往復と解析とコミット | 文の大きさの上限 |
| リクエストをまたいでメモリに溜め、一定間隔で書く | 複数のリクエストの書き込み | 反映の遅れと、落ちたときに消える危険 |
| 応答を先に返し、処理を後回しにする | 遅い処理そのもの | 失敗を後から扱う仕組みが要る |

下に行くほど速くなり、引き換えに諦めるものが大きくなります。どこまで進んでよいかを決めるのは、仕様に書かれた「どれだけ遅れてよいか」「どれだけ失ってよいか」です。

## 1 行の INSERT は何に時間を使うのか

MySQL のリファレンスは、1 行を挿入するのにかかる時間の内訳を、おおよその比で示しています（[MySQL 8.4 Reference Manual: Optimizing INSERT Statements](https://dev.mysql.com/doc/refman/8.4/en/insert-optimization.html)）。

| 段階 | 比 |
| --- | --- |
| 接続 | 3 |
| クエリをサーバに送る | 2 |
| クエリを解析する | 2 |
| 行を挿入する | 1 × 行の大きさ |
| インデックスを挿入する | 1 × インデックスの数 |
| 閉じる | 1 |

行そのものを書く部分は、全体のごく一部です。同じ節は冒頭で「To optimize insert speed, combine many small operations into a single large operation.」（挿入を速くするには、小さな操作をたくさん行う代わりに、まとめて 1 つの大きな操作にする）と書いています。

この表には、もう 1 つの大きな費用が出てきません。**コミット** です。第 99 回で見たとおり、コミットはログをディスクに書き出し、`fsync` が終わるのを待ってから成功を返します。autocommit のまま 1 行ずつ INSERT すると、1 行ごとにこの待ちが入ります。リファレンスの InnoDB への一括読み込みの節も、「When importing data into InnoDB, turn off autocommit mode, because it performs a log flush to disk for every insert.」（InnoDB にデータを取り込むときは autocommit を切ること。autocommit では挿入のたびにログをディスクへ書き出すため）と書いています（[MySQL 8.4 Reference Manual: Bulk Data Loading for InnoDB Tables](https://dev.mysql.com/doc/refman/8.4/en/optimizing-innodb-bulk-data-loading.html)）。

まとめると、1 行の INSERT には次の費用が付いてきます。

```
 アプリ                         MySQL
   │── INSERT ... (1 行) ──────→│  解析
   │                             │  行とインデックスを書く（ここは小さい）
   │                             │  コミット: redo log を書き出して fsync を待つ
   │←───────────── OK ───────────│
   │   ネットワークの往復 1 回
```

1 万行を書くなら、これが 1 万回です。まとめる方法は、どの費用を何回に減らすかで分けられます。

| 書き方 | 往復 | 解析 | コミット |
| --- | --- | --- | --- |
| 1 行ずつ、autocommit | 行数 | 行数 | 行数 |
| 1 行ずつ、1 つのトランザクション | 行数 | 行数 | 1 |
| 100 行ずつの複数行 `VALUES`、autocommit | 行数 / 100 | 行数 / 100 | 行数 / 100 |
| 全行を 1 文 | 1 | 1 | 1 |

複数行の `VALUES` は次の形です。リファレンスは、同じクライアントから多数の行を同時に挿入するならこの形を使うよう勧め、「This is considerably faster (many times faster in some cases) than using separate single-row INSERT statements.」（1 行ずつの INSERT 文よりかなり速く、場合によっては何倍も速い）と書いています（[Optimizing INSERT Statements](https://dev.mysql.com/doc/refman/8.4/en/insert-optimization.html)）。

```sql
INSERT INTO cond (isu_id, ts, is_sitting, message) VALUES
  (1, '2020-09-13 12:26:40', 0, 'condition message 0'),
  (2, '2020-09-13 12:26:41', 1, 'condition message 1'),
  (3, '2020-09-13 12:26:42', 0, 'condition message 2');
```

ファイルから読み込むなら `LOAD DATA` があり、同じ節は INSERT 文を使うより「通常 20 倍速い」としています。ただし、アプリが受け取ったリクエストを書く場面では、ファイルを経由するより複数行の `VALUES` を組み立てる方が自然です。

## 手元で確かめる：1 万行の入れ方

Go で 5 通りの書き方を比べました。表には主キーのほかに `(isu_id, ts)` のインデックスを 1 つ張っています。コネクションは 1 本だけ使います。

```go
// 1 行ずつ（autocommit）
for i := 0; i < N; i++ {
	db.Exec("INSERT INTO cond (isu_id, ts, is_sitting, message) VALUES (?, ?, ?, ?)", row(i)...)
}

// per 行ずつの複数行 VALUES
for start := 0; start < N; start += per {
	ph, args := ...                     // "(?, ?, ?, ?)" を per 個と、その引数
	db.Exec("INSERT INTO cond (...) VALUES "+strings.Join(ph, ","), args...)
}
```

環境は次のとおりです。

- Apple M1 Pro、macOS。Docker（OrbStack）の `mysql:8.4`（8.4.13）を既定の設定のまま起動
- Go 1.24.6、github.com/go-sql-driver/mysql v1.8.1
- 既定でバイナリログが有効（`log_bin=1`、`sync_binlog=1`）、`innodb_flush_log_at_trx_commit=1`

<Callout type="warn" title="この回の数値は、混んだマシンで測っています">
  測定中、同じマシンでは他の実験も動いていて、ロードアベレージは 50〜130 ほどでした。
  そのため、絶対値は静かなマシンより何倍も遅く、同じ測定を繰り返すと数倍ぶれます
  （1 回目の測定では autocommit の 1 行ずつが 31 行/秒、2 回目は 11 行/秒でした）。
  読み取ってほしいのは、書き方ごとの **桁の違いと順序** です。これは繰り返しても変わりませんでした。
</Callout>

`innodb_flush_log_at_trx_commit` を既定の 1 と、2 に変えた場合の両方で測りました。2 は第 99 回で見たとおり、コミットのたびにログを OS に渡すだけで、`fsync` は約 1 秒ごとにまとめて行う設定です。autocommit の 1 行ずつだけは時間がかかりすぎるので 1,000 行、他は 10,000 行です。

```text
innodb_flush_log_at_trx_commit=1
1 行ずつ（autocommit）              1000 行    92822 ms        11 行/秒  INSERT 文  1000  redo fsync  2198
1 行ずつ（1 トランザクション）             10000 行    12724 ms       786 行/秒  INSERT 文 10000  redo fsync  2194
100 行ずつ                       10000 行     1390 ms      7197 行/秒  INSERT 文   100  redo fsync   248
1000 行ずつ                      10000 行      270 ms     37100 行/秒  INSERT 文    10  redo fsync    90
10000 行を 1 文                  10000 行      303 ms     32960 行/秒  INSERT 文     1  redo fsync    66
innodb_flush_log_at_trx_commit=2
1 行ずつ（autocommit）              1000 行    11361 ms        88 行/秒  INSERT 文  1000  redo fsync    26
1 行ずつ（1 トランザクション）             10000 行    10669 ms       937 行/秒  INSERT 文 10000  redo fsync    27
100 行ずつ                       10000 行     1455 ms      6873 行/秒  INSERT 文   100  redo fsync     5
1000 行ずつ                      10000 行      424 ms     23591 行/秒  INSERT 文    10  redo fsync     4
10000 行を 1 文                  10000 行      928 ms     10777 行/秒  INSERT 文     1  redo fsync     5
```

`INSERT 文` は `Com_insert`、`redo fsync` は `Innodb_os_log_fsyncs` の増分です（[MySQL 8.4 Reference Manual: Server Status Variables](https://dev.mysql.com/doc/refman/8.4/en/server-status-variables.html)）。読み取れることを整理します。

| 比べたもの | 結果 | 何が効いたか |
| --- | --- | --- |
| autocommit → 1 トランザクション（設定 1） | 11 → 786 行/秒 | コミットの待ちが 1 回になった |
| autocommit、設定 1 → 2 | 11 → 88 行/秒、fsync 2198 → 26 回 | コミットの `fsync` を待たなくなった |
| 1 トランザクション → 100 行ずつ | 786 → 7197 行/秒 | 往復と解析が 1/100 になった |
| 100 行ずつ → 1000 行ずつ | 7197 → 37100 行/秒 | 往復と解析がさらに 1/10 |
| 1000 行ずつ → 1 文 | 頭打ち、またはやや遅い | 往復はもう支配的でない。巨大な文の組み立てと解析が効き始める |

設定 1 の autocommit では、1 行あたりおよそ 2 回の redo log の `fsync` が数えられました。この環境ではバイナリログも有効なので、コミットは InnoDB とバイナリログの両方を揃える手順を通ります。1 回のコミットで redo log の書き出しが 1 回で済まないのは、そのためだと考えられます。設定 1 の他の行でも `fsync` の回数が多いのは、この計数がサーバ全体のもので、コミットを待たずに裏で行われる書き出しも含むためと見られます。いずれにせよ、設定を 2 にすると回数は 1/100 近くまで減り、autocommit の 1 行ずつが 8 倍速くなりました。

まとめる単位は、**数百〜千行で効果のほとんどが得られ**、それ以上大きくしても速くはなりませんでした。往復とコミットの費用が十分に薄まれば、残るのは本当に行を書く費用だからです。

<Callout type="note" title="1 文の大きさには上限がある">
  1 つの SQL 文は 1 つの通信パケットとして送られ、その大きさは `max_allowed_packet` を超えられません。
  超えると `ER_NET_PACKET_TOO_LARGE` のエラーになり、接続が切られます
  （[MySQL 8.4 Reference Manual: Packet Too Large](https://dev.mysql.com/doc/refman/8.4/en/packet-too-large.html)）。
  この実験の環境では 64 MB（`67108864`）でした。
  プリペアドステートメントのプレースホルダの数にも上限があり、超えると
  `ER_PS_MANY_PARAM`（Prepared statement contains too many placeholders）になります
  （[MySQL 8.4 Error Reference](https://dev.mysql.com/doc/mysql-errors/8.4/en/server-error-reference.html)）。
  「全部を 1 文で」ではなく、**数百〜千行ごとに区切る** のが安全です。
</Callout>

## ISUCON での現れ方

書き込みをまとめる改善は、ISUCON で繰り返し出題されています。

**一括で取り込む。** ISUCON11 予選（ISUCONDITION）では、椅子（ISU）が自分の状態（コンディション）を定期的に POST してきます。1 回の POST には複数のコンディションが含まれ、参考実装はそれを 1 件ずつ INSERT していました。公式の解説は、このエンドポイントについて「このエンドポイントによる INSERT が DB の CPU 負荷の多くを占めます。」と書き、続けて「ここのクエリは一度発行するだけで十分なので、bulk (batch) insert をするようにしましょう。」と勧めています（[ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)）。

ISUCON12 予選（ISUPORTS）では、初期データの移行に同じ問題が現れました。SQLite の初期データを MySQL に移そうとすると、付属の変換スクリプトが「1行につき1つのINSERT文が記述された形式」を出力し、スコアの表には全テナントで約 370 万行あったため、取り込みに非常に時間がかかった、と解説にあります（[ISUCON12 予選問題の解説と講評](https://isucon.net/archives/56850281.html)）。このときの解決策は行そのものを減らすことでした。次回で扱います。

**リクエストをまたいでまとめる。** ISUCON11 予選の解説は、一括挿入のさらに先として、次のように書いています。

> さらなる改善として、アプリケーションマニュアルの記載から、コンディションの反映が遅れることをベンチマーカーは許容しているため、POST されたコンディションをキューに詰めるなどして、複数リクエストを跨いで纏めたコンディションを一定間隔で INSERT するとさらに速くなります。

ISUCON14（ISURIDE）でも、椅子の現在位置を送る `POST /api/chair/coordinate` について、解説が「POST /api/chair/coordinateについては他に利用されるエンドポイントも3秒の反映猶予があるため、非同期化・バルクインサート化が可能でした。」と書いています（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。

**遅い処理を後回しにする。** ISUCON9 本選（ISUXPRESS）では、予約のキャンセルのたびに外部の決済 API を呼び、それに 1 秒かかっていました。ベンチマーカーの仕様には、負荷走行の後に 5 秒以上待ってから整合性を確かめる、と書かれていました。解説は、このことから「キャンセル処理はバックグラウンドで実行しても良いことがわかります」とし、「決済のキャンセルは5秒以内毎にバッチ処理でバルクキャンセルするという実装を行い、レスポンスを早く返すことができるようになります。」と書いています（[ISUCON9 本選問題の解説と講評](https://isucon.net/archives/53916974.html)）。

3 つに共通しているのは、どれも **仕様に「遅れてよい」根拠が書かれていた** ことです。反映の猶予は 3 秒、整合性の確認は 5 秒後。後回しの改善は、この数字を読んでから始まります。

## リクエストをまたいでまとめる

1 回のリクエストの中で行をまとめても、リクエストが細かく大量に来るなら、INSERT の回数はリクエストの数だけ残ります。そこで、受け取ったデータをメモリに溜めておき、別のゴルーチンが一定間隔でまとめて書き出します。

```go
var (
	mu  sync.Mutex
	buf []cond
)

// リクエストを処理する側: 溜めるだけで、すぐ成功を返す
func postCondition(rows []cond) {
	mu.Lock()
	buf = append(buf, rows...)
	mu.Unlock()
}

// 書き出す側: 100 ms ごとに、溜まった分を取り出して複数行の INSERT にする
func flusher() {
	for range time.Tick(100 * time.Millisecond) {
		mu.Lock()
		rows := buf
		buf = nil
		mu.Unlock()
		if len(rows) > 0 {
			insertRows(rows) // 1000 行ずつに区切って INSERT
		}
	}
}
```

ロックを持つのは、スライスを付け替える一瞬だけです。データベースへの書き込みはロックの外で行うので、書いている間もリクエストは溜め続けられます。

### 時間と件数の両方で区切る

一定間隔だけで書き出すと、届く量が急に増えたとき、1 回の書き出しが巨大になります。逆に、件数だけで区切ると、量が少ない時間帯にはいつまでも書き出されません。実際の実装では、**どちらか早い方** で書き出すのが普通です。

```go
const (
	maxRows  = 1000                    // これだけ溜まったら、時間を待たずに書く
	maxDelay = 100 * time.Millisecond  // これだけ経ったら、件数が少なくても書く
)

func postCondition(rows []cond) {
	mu.Lock()
	buf = append(buf, rows...)
	full := len(buf) >= maxRows
	mu.Unlock()
	if full {
		select {
		case kick <- struct{}{}: // 書き出し役を起こす。すでに起こしてあれば何もしない
		default:
		}
	}
}

func flusher() {
	t := time.NewTicker(maxDelay)
	for {
		select {
		case <-t.C:
		case <-kick:
		}
		flushOnce()
	}
}
```

`kick` は容量 1 のチャネルです。ハンドラは書き出し役を起こすだけで、自分では書きません。書き出し役を 1 つに限っておけば、同じ行の書き込みの順序が入れ替わる心配もありません。

この 2 つの値が、そのまま **反映の遅れの上限と、1 文の大きさの上限** になります。前の節で見たとおり、1 文の行数は千行程度で効果が頭打ちになるので、`maxRows` を大きくしても速くはなりません。`maxDelay` は、後の節で見る「許される遅れ」から逆算して決めます。

### 重複を吸収できる形にしておく

後で見るように、まとめた書き込みは失敗したときに再試行することになります。再試行で同じ行が 2 回届いても困らないよう、行を一意に決めるキーを主キーか一意索引にしておくと安全です。ISUCON11 予選のコンディションには、同じ椅子で時刻が重複しないという保証がマニュアルにあり、解説も `(jia_isu_uuid, timestamp)` を複合主キーにすることに触れています。

```sql
-- 同じ椅子・同じ時刻の行がすでにあれば、何もしない
INSERT IGNORE INTO isu_condition (jia_isu_uuid, timestamp, ...) VALUES (...), (...), ...;
```

`INSERT IGNORE` は重複以外のエラーも警告に変えてしまうので、`INSERT ... ON DUPLICATE KEY UPDATE` で重複のときだけ同じ値を書き直す形の方が、誤りに気付きやすくなります。どちらにしても、**再試行してよい書き込みにしておくこと** が、まとめ書きを安全に使う前提です。

### 手元で確かめる：3 つの書き方の比較

32 のクライアントが、1 回あたり 10 行のコンディションを送り続ける状況を作りました。各クライアントは応答を受け取ってから 100 ms 待って次を送ります。したがって、受け付け側が限りなく速ければ、毎秒 320 件の要求、3,200 行が届きます。HTTP は挟まず、ハンドラに当たる関数を直接呼んでいます。コネクションプールの上限は 32 本です。

- `single`: 10 行を 1 行ずつ、autocommit で INSERT する（参考実装の形）
- `sync`: 10 行を 1 文の複数行 INSERT にする（一括挿入）
- `async`: メモリに溜めてすぐ返し、100 ms ごとに書き出す

```text
single 要求    419 件 (    38 件/秒)  行    4190  INSERT 文   4190  応答 p50  834.88 ms p99 1571.71 ms
sync   要求   1632 件 (   161 件/秒)  行   16320  INSERT 文   1632  応答 p50   78.18 ms p99  291.72 ms
async  要求   3136 件 (   313 件/秒)  行   31360  INSERT 文     90  応答 p50    0.00 ms p99    0.09 ms  反映までの遅れ p50  131.1 ms p99  400.0 ms max  400.7 ms
```

10 秒間の結果です。

| | 処理できた要求 | INSERT 文 | 応答時間 p50 | データベースに入るまで |
| --- | --- | --- | --- | --- |
| 1 行ずつ | 38 件/秒 | 4,190 | 835 ms | 応答と同時 |
| 1 要求を 1 文 | 161 件/秒 | 1,632 | 78 ms | 応答と同時 |
| 溜めて 100 ms ごと | 313 件/秒 | 90 | 0.00 ms | p50 131 ms、最大 401 ms |

溜める方式は、届いた要求をほぼすべて処理しました（上限は毎秒 320 件）。INSERT は 10 秒で 90 回、つまり書き出しの間隔ごとにほぼ 1 回です。要求の数がどれだけ増えても、INSERT の回数は **時間で決まる** ようになります。

その代わり、「成功」を返した時点では、データはまだデータベースにありません。最後の列がその遅れで、中央値で 131 ms、最大で 401 ms でした。100 ms の間隔より長いのは、書き出しそのものにも時間がかかり、その間に届いた分は次の回に回るからです。**反映の遅れは、書き出しの間隔に、書き出しにかかる時間を足したもの** になります。

## 反映の遅れを誰が許すのか

溜める方式を入れると、システムの外から見える振る舞いが変わります。

- POST した直後に GET すると、いま送ったデータが見えない
- 件数や合計の表示が、少し前の値になる
- 別のサーバや別のプロセスから見ると、さらに見え方がずれる

これを受け入れてよいかは、技術では決まりません。ISUCON では、マニュアルや解説に、3 秒の反映猶予、負荷走行の後 5 秒以上待ってから整合性を確かめる、と数字で書かれていました。本番のサービスでは、この数字を決めるのは仕様を持つ人です。第 270 回で見た「許される古さ」と同じく、**書き込み側にも許される遅れがあり、それを先に確かめる** のが出発点です。

自分の書き込みだけは直後に見せたい、という要件もよくあります。その場合は、読み出しのときにバッファの中身も見て結果に混ぜるか、書いた本人の要求だけは同期で書く、という折衷が取れます。ただし、バッファを読む処理はプロセスの中でしか働きません。アプリのサーバが複数台あれば、別の台に届いた読み出しには見えません。

## 落ちたら何が消えるのか

もう 1 つの代償は、**成功を返したのにデータベースに入っていない行** が、常にメモリの中にあることです。

### 手元で確かめる：受け付けの最中に終了させる

先ほどの溜める方式で、開始から約 3 秒後に、後始末をせずにプロセスを終了させました（`os.Exit(1)`）。終了の直前に、成功を返した行の数、テーブルにある行の数、書き出しの途中の行の数、バッファに残っている行の数を記録し、終了した後にテーブルの行数を数え直しています。3 回行いました。

```text
異常終了の直前: 成功を返した行 9920 / テーブルにある行 7360 / 書き込み中の行 960 / バッファに残った行 1600
8320
異常終了の直前: 成功を返した行 9920 / テーブルにある行 9530 / 書き込み中の行 320 / バッファに残った行 70
9850
異常終了の直前: 成功を返した行 9920 / テーブルにある行 8640 / 書き込み中の行 640 / バッファに残った行 640
9280
```

| 回 | 成功を返した行 | 終了後にテーブルにあった行 | 失われた行 |
| --- | --- | --- | --- |
| 1 | 9,920 | 8,320 | 1,600 |
| 2 | 9,920 | 9,850 | 70 |
| 3 | 9,920 | 9,280 | 640 |

書き出しの途中だった行は、INSERT 文がサーバに届いていたので、終了の後にコミットされていました。失われたのは、バッファに残っていた行です。どれだけ失うかは、終了がどの瞬間に来たかで 70 行から 1,600 行まで変わりました。

これに対して、終了の合図を受けたら新しい受け付けを止め、バッファを最後まで書き出してから終わるようにすると、失われる行はありませんでした。

```text
graceful=true 受け付けた行 9340 / テーブルにある行 9340 / 書き込み中の行 0 / バッファに残った行 0
```

### 失うことへの備え

溜める方式で失われうるものと、その対策を整理します。

| 起きること | 結果 | 対策 |
| --- | --- | --- |
| 再起動やデプロイでの停止 | バッファの中身が消える | 停止の合図（SIGTERM）を受けて受け付けを止め、書き出してから終わる。systemd の `TimeoutStopSec` などの猶予に収める |
| プロセスの異常終了、OOM、マシンの停止 | バッファの中身が消える | 避けられない。失ってよいデータにだけ使うか、先に耐久性のある場所に書く |
| 書き出しの INSERT が失敗する | まとめた全行が入らない | 再試行する。重複しても困らないよう、一意キーと `INSERT IGNORE` や UPSERT で冪等にする |
| 書き出しが追いつかない | バッファが膨らみ続ける | 次の節 |

ISUCON11 予選のマニュアルには「ユーザはコンディションのデータ欠損を許容しますが、理想的には全てのコンディションのデータが保存されることを期待しています。」とあります（[ISUCONDITION アプリケーションマニュアル](https://github.com/isucon/isucon11-qualify/blob/main/docs/isucondition.md)）。センサーの値のように、数件欠けても意味が変わらないデータだから、メモリに溜める方式が許されていたわけです。

注文や決済のように 1 件も失えないデータでは、メモリに溜めてはいけません。その場合は「失わない場所に先に書き、重い処理だけを後回しにする」形になります。第 116 回で見た、業務の更新と同じトランザクションでジョブの行を書く方式や、トランザクショナル outbox がそれです。ISUCON9 本選の決済キャンセルの後回しも、本番で作るなら「キャンセル待ち」の行をデータベースに書いてから応答し、ワーカーが拾って外部 API を呼ぶ形にするのが筋です。

<Callout type="tip" title="「先に書く場所」は、速い必要がある">
  耐久性のある場所に先に書くなら、その書き込み自体が速くなければ意味がありません。
  追記だけのログファイル、Redis の AOF、Kafka のようなログ型のキューは、
  どれもファイルの途中を書き換えず、末尾に追記していく形で速さを出しています。
  ディスクへの書き出しをどの間隔で確定させるかは、それぞれ設定で選べます（Redis の AOF なら `appendfsync`）。
  第 99 回の WAL と同じ考え方で、データベースが自分の中でやっていることを、外側で繰り返していることになります。
</Callout>

## 書き出しが追いつかないとき

溜める方式は、書き出しの速さが届く量を上回っている間だけ成り立ちます。先ほどの実験で、クライアントの待ち時間を 100 ms から 5 ms に縮め、届く量を十数倍にしてみました。

```text
async  要求  42364 件 (  4235 件/秒)  行  423640  INSERT 文    426  応答 p50    0.00 ms p99    0.01 ms  反映までの遅れ p50 24832.0 ms p99 43453.0 ms max 43536.3 ms
```

受け付けは毎秒 4,235 件の要求、4 万行あまりを即座に返し続けましたが、反映までの遅れは中央値で 25 秒、最大で 44 秒になりました。10 秒間の負荷を止めた後も、溜まった 42 万行を書き終えるまでさらに 30 秒以上かかっています。応答時間だけを見ていると、この状態には気付けません。

**バッファに上限のない後回しは、遅れの上限もありません。** 本番で使うなら、次のどれかを決めておきます。

- バッファの長さ、または最も古い行の待ち時間を計測し、監視する
- 上限を超えたら、受け付けを同期の書き込みに切り替えるか、`503` や `429` で断る（第 114 回の再試行と組み合わせる）
- 書き出しを複数のゴルーチンに分けて並列に書く。ただし、同じ行への書き込みの順序が問題になる場合は、キーごとに担当を分ける

ISUCON11 予選の参考実装は、この判断をコードに書いていました。`POST /api/condition` の先頭で `dropProbability := 0.9` の確率で要求を捨て、何も書かずに `202 Accepted` を返しています。コメントには「一定割合リクエストを落としてしのぐようにしたが、本来は全量さばけるようにすべき」とあります（[isucon11-qualify webapp/go/main.go](https://github.com/isucon/isucon11-qualify/blob/main/webapp/go/main.go)）。解説は、改善で CPU に余裕が生まれてからこの値を下げると、保存されるコンディションが増えて加点が大きくなる、と説明しています。受け付けられる量を超えてまで受け取らない、という判断も含めて、性能の調整です。

## 本番で使うときの判断

| 問い | まとめてよい方向 | まとめない方がよい方向 |
| --- | --- | --- |
| 書いた直後に読む人がいるか | いない、または数秒遅れてよい | 書いた本人がすぐ確認する |
| 失ってよいか | 数件欠けても意味が変わらない（計測値、ログ、閲覧履歴） | 1 件も失えない（注文、決済、在庫） |
| 書き込みの量 | 細かい書き込みが大量に来る | まばらで、1 件ずつ重い |
| アプリの台数 | 1 台、または書き手を 1 つに集められる | 多数の台が同じ行を更新する |

迷ったら、次の順に試すのが安全です。後ろに行くほど、得られる速さに対して受け入れるものが大きくなります。

1. 1 つのリクエストの中の書き込みを、複数行の `VALUES` にまとめる（振る舞いは変わらない）
2. 関係する書き込みを 1 つのトランザクションに入れる（整合性はむしろ良くなる）
3. 失ってよいデータに限って、リクエストをまたいでメモリに溜める（停止時の書き出しと、上限の監視を付ける）
4. 失えないデータの遅い処理は、先に耐久性のある場所に書いてから後回しにする

`innodb_flush_log_at_trx_commit=2` で `fsync` を減らす設定も、効果は大きく、コードを変えずに済みます。ただし、これは **データベース全体の書き込みについて直前の 1 秒ほどは失ってよい、と決める** ことです。第 99 回で見たとおり、失われるのは最後の数件で、データが壊れるわけではありません。それでも、どのデータにとって許されるかを、アプリの書き方を変える場合と同じ問いで確かめる必要があります。

次回は、書き込みの「回数」ではなく「中身」に手を入れます。読むたびに計算していたものを書き込みのときに計算しておく、そもそも要らない行を持たない、という方向です。

## まとめ

- 1 行の INSERT の時間の大半は、行を書くことではなく、往復、解析、コミットの待ちにある
- autocommit をやめて 1 つのトランザクションに入れるとコミットの待ちが 1 回になり、複数行の `VALUES` にすると往復と解析も減る
- 手元の MySQL 8.4 では、1 行ずつの autocommit が 11 行/秒、1 トランザクションで 786 行/秒、1,000 行ずつの複数行 INSERT で 37,100 行/秒だった。効果は数百〜千行で頭打ちになる
- 1 文の大きさには `max_allowed_packet` とプレースホルダの数の上限がある。数百〜千行ごとに区切る
- リクエストをまたいでメモリに溜め、一定間隔で書くと、INSERT の回数が要求の数ではなく時間で決まる。手元では要求の処理量が 161 件/秒から 313 件/秒に上がり、INSERT は 10 秒で 90 回になった
- その代わり、反映が遅れる。遅れは書き出しの間隔に書き出しの時間を足したもの。ISUCON では、仕様に書かれた 3 秒の反映猶予や、5 秒待ってからの整合性の確認が根拠だった
- 成功を返した行がメモリにしかない時間がある。後始末なしで終了させると、手元では 70〜1,600 行が失われた。停止の合図を受けて書き出してから終われば失われなかった
- 失ってよいデータにだけメモリに溜める方式を使う。失えないデータは、先に耐久性のある場所に書いてから重い処理を後回しにする（第 116 回）
- 書き出しが追いつかないとバッファも遅れも際限なく伸びる。手元では反映の遅れが最大 44 秒になった。長さを監視し、上限を決めて断るか同期に戻す
- `innodb_flush_log_at_trx_commit=2` などの設定は、データベース全体について「直前の少しは失ってよい」と決めることになる
