## 動画は絵の列

ここまでの回では、canvas に絵を 1 枚ずつ描いてきました。動画も、中身は**決まった間隔で並んだ絵の列**です。1 枚 1 枚をフレームと呼びます。

まず、圧縮していないフレームの大きさを数えます。第 99 回で見たとおり、canvas のピクセルは 1 画素あたり RGBA の 4 バイトです。

| 解像度 | 1 フレーム（RGBA） | 30fps で 1 秒 | 1 フレーム（YUV 4:2:0） | 30fps で 1 秒 |
| --- | --- | --- | --- | --- |
| 1280 × 720 | 3,686,400 バイト | 約 111MB | 1,382,400 バイト | 約 41MB |
| 1920 × 1080 | 8,294,400 バイト | 約 249MB | 3,110,400 バイト | 約 93MB |

1080p の RGBA を 30fps で流すと、1 秒に約 249MB、ビットに直すと約 2Gbit/s です。家庭の回線にも、ディスクにも、そのままでは載りません。

右の 2 列の **YUV 4:2:0** は、動画で標準的に使われる画素の並べ方です。明るさ（輝度、Y）は画素ごとに持ち、色（色差、U と V）は縦横 2 画素ずつの 4 画素で 1 組だけ持ちます。人の目は明るさの細かい変化には敏感で、色の細かい変化には鈍いので、色の情報を 4 分の 1 に間引いても見た目はほとんど変わりません。MDN は、4:2:0 は 1 行おきの色の情報を輝度の画像に当てはめる方式だと説明しています（[MDN: Digital video concepts](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Video_concepts)）。1 画素あたりは、Y の 1 バイトと、4 画素で共有する U と V の 2 バイトを 4 で割った 0.5 バイトで、**1.5 バイト**になります。

```
RGBA（4 バイト / 画素）           YUV 4:2:0（1.5 バイト / 画素）
┌──┬──┬──┬──┐                  Y  ┌──┬──┬──┬──┐   U  ┌──┬──┐   V  ┌──┬──┐
│RG│RG│RG│RG│                     │Y │Y │Y │Y │      │U │U │      │V │V │
│BA│BA│BA│BA│                     ├──┼──┼──┼──┤      └──┴──┘      └──┴──┘
├──┼──┼──┼──┤                     │Y │Y │Y │Y │      2×2 画素で 1 つ
│RG│RG│RG│RG│                     └──┴──┴──┴──┘
│BA│BA│BA│BA│
└──┴──┴──┴──┘
```

WebCodecs が扱うフレームの形式にも、この並べ方がそのまま出てきます。`I420` は Y・U・V の 3 枚の面を順に並べた形、`NV12` は Y の面と、U と V を交互に詰めた面の 2 枚にした形です（[MDN: VideoFrame.format](https://developer.mozilla.org/en-US/docs/Web/API/VideoFrame/format)）。どちらも 1 画素 1.5 バイトで、違うのはメモリ上の並べ方だけです。

## 差分で縮める

YUV にしても、1080p で 1 秒 93MB です。ここからさらに 100 分の 1 以下にするのが、H.264、VP9、AV1 といった**動画のコーデック**の仕事です。

鍵になるのは、**隣り合うフレームはほとんど同じ**という性質です。MDN は、動画の圧縮はフレームを比べて違う場所を見つけ、前のフレームを次のフレームに近づけるのに十分な情報だけを記録する、と説明しています（[MDN: Web video codec guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Video_codecs)）。

```
時刻 →
┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
│ key │ │delta│ │delta│ │delta│ │ key │ │delta│ …
│全体  │ │差分  │ │差分  │ │差分  │ │全体  │ │差分  │
└─────┘ └─────┘ └─────┘ └─────┘ └─────┘ └─────┘
   ▲       └ 直前までのフレームが無いと復号できない
   └ これだけで復号できる。シークの起点になる
```

- **キーフレーム**: 他のフレームに頼らずに復号できるフレーム。WebCodecs の仕様は、Key Chunk を「復号するのに他のどのフレームにも依存しない符号化されたチャンク」と定義しています（[WebCodecs §1](https://www.w3.org/TR/webcodecs/#key-chunk)）
- **差分フレーム**（delta）: 前のフレームとの違いだけを持つ。小さいが、単独では絵にならない

差分を積み重ねると誤差も積み重なるので、ときどきキーフレームを挟んで画をリセットします。シークしたときも、直前のキーフレームから復号し直します（[MDN: Web video codec guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Video_codecs)）。

もう 1 つ、第 129 回で見た DEFLATE や Brotli と違い、動画のコーデックの多くは**非可逆**です。MDN は、ほとんどの動画のコーデックは復号した映像が元と正確には一致しない非可逆の方式で、縮めるほど細部が失われる、と書いています（[MDN: Web video codec guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Video_codecs)）。テキストは 1 ビットでも変われば壊れますが、映像は目に分からない範囲なら捨ててよい。だから桁違いに縮められます。

符号化と復号は計算が重いので、多くの機械は専用の回路（ハードウェアのエンコーダとデコーダ）を持っています。第 48 回の DMA と同じく、CPU は指示を出すだけで、実際の仕事は別の装置が行います。

## video 要素を canvas に描く

ブラウザで動画を扱う最も簡単な方法は、`<video>` に再生させて、その時点のフレームを canvas に描くことです。`drawImage()` は `<video>` をそのまま受け取ります。

```js
ctx.drawImage(video, 0, 0)   // いま表示されているフレームを 1 枚描く
```

問題は**いつ描くか**です。`requestAnimationFrame`（rAF）は画面の更新ごとに呼ばれますが、動画のフレームが変わる間隔とは関係ありません。60Hz の画面で 30fps の動画を描けば、2 回に 1 回は同じフレームを描き直すことになります。

`requestVideoFrameCallback`（rVFC）は、**動画の新しいフレームがコンポジタに渡されたとき**に呼ばれます。仕様は、次にフレームがコンポジタに提示されたときに呼ばれるコールバックを登録するもの、としています（[WICG: HTMLVideoElement.requestVideoFrameCallback()](https://wicg.github.io/video-rvfc/)）。呼ばれる頻度は、動画のフレームレートとブラウザの描画のレートの低い方で、25fps の動画を 60Hz で再生すれば約 25Hz になります（同）。

```js
function onFrame(now, meta) {
  ctx.drawImage(video, 0, 0)
  // meta.mediaTime: そのフレームの動画の中での時刻（秒）
  // meta.presentedFrames: これまでに合成に出したフレームの数。飛びがあれば落ちたと分かる
  video.requestVideoFrameCallback(onFrame)
}
video.requestVideoFrameCallback(onFrame)
```

### 手元で確かめる（1）: rAF と rVFC の回数

ヘッドレスの Chrome 155（macOS、Apple M1 Pro。以下の実験はすべてこの環境）で、canvas のアニメーションを `MediaRecorder` で 30fps の WebM（VP9）に 4 秒録り、それを `<video>` で再生しながら、2 秒間に rAF と rVFC が何回呼ばれるかを数えました。

```
rAF  : 106 回 / 2 秒
rVFC :  53 回 / 2 秒
最初の 3 回のメタデータ:
  mediaTime=0       presentedFrames=1  640x360
  mediaTime=0.038   presentedFrames=2
  mediaTime=0.155   presentedFrames=3
```

ヘッドレスの rAF は約 53 回 / 秒、rVFC は約 26.5 回 / 秒で、**rVFC は動画のフレームの数だけ呼ばれました**。rAF で描くと、半分は同じ絵の描き直しです。3 回目の `mediaTime` が 0.038 から 0.155 に跳んでいるのは、再生の開始直後にフレームが間に合わなかったためと考えられます。仕様も、メインスレッドが重いと毎フレーム呼ばれるとは限らず、厳密なタイミングの保証はない、と書いています（[WICG: rVFC](https://wicg.github.io/video-rvfc/)）。

## フレームを 1 枚ずつ扱う: WebCodecs

`<video>` は便利ですが、中で何が起きているかに手を出せません。読み込み、分解、復号、表示までがひとかたまりです。WebRTC（第 79 回）も同じで、符号化と送信をブラウザが一括で引き受けます。

Chrome の解説は、こうした既存の API では、ウェブの開発者が映像のストリームの個々の部品を扱えないことを、WebCodecs の動機に挙げています（[Chrome for Developers: WebCodecs](https://developer.chrome.com/docs/web-platform/best-practices/webcodecs)）。WebCodecs は、その部品のうち**コーデックだけ**を取り出した API です。

```
           VideoFrame                 EncodedVideoChunk
canvas ─▶ ┌──────────┐  VideoEncoder  ┌────────────────┐   mux    ┌──────────┐
カメラ     │ 生の画素   │ ─────────────▶ │ key / delta    │ ───────▶ │ MP4/WebM │
video     │ (NV12 等)  │ ◀───────────── │ 符号化された列   │ ◀─────── │ ネットワーク│
          └──────────┘  VideoDecoder  └────────────────┘  demux   └──────────┘
               │                                         ▲
               ▼                                         └ ここは WebCodecs の外
       drawImage / WebGL / WebGPU
```

部品は 3 種類です。

- **`VideoFrame`**: 生のフレーム 1 枚。canvas、`<video>`、`ImageBitmap`、配列のバイト列から作れる
- **`VideoEncoder` / `VideoDecoder`**: `VideoFrame` と `EncodedVideoChunk` を相互に変換する
- **`EncodedVideoChunk`**: 符号化されたフレーム 1 枚分のバイト列。`type` が `key` か `delta` かを持つ

図の右端の **mux / demux**（コンテナへの詰め込みと取り出し）は WebCodecs に含まれません。仕様は、この仕様では符号化されたメディアはコンテナに入っていない、と書いています（[WebCodecs §7.4](https://www.w3.org/TR/webcodecs/#codec-string)）。MP4 や WebM のファイルを読むには、ファイルを解析してチャンクを取り出す処理を自分で用意します（たとえば [mp4box.js](https://github.com/gpac/mp4box.js) のような JavaScript のライブラリ）。

### 何を使えるかを先に聞く

コーデックの対応は、ブラウザと OS とハードウェアの組み合わせで変わります。仕様は `configure()` の前に `isConfigSupported()` で確かめるよう勧めています（[WebCodecs §4.5](https://www.w3.org/TR/webcodecs/#videodecoder-methods)）。

```js
const { supported } = await VideoEncoder.isConfigSupported({
  codec: 'avc1.42001f',              // H.264 Baseline, level 3.1
  width: 1280, height: 720, bitrate: 2_000_000, framerate: 30,
  hardwareAcceleration: 'prefer-hardware',
})
```

`hardwareAcceleration` は `no-preference`、`prefer-hardware`、`prefer-software` の 3 つで、仕様上は**ヒント**です（[WebCodecs §7.9](https://www.w3.org/TR/webcodecs/#hardware-acceleration)）。仕様は `prefer-hardware` を使う例として、WebAssembly で自前のソフトウェアの代替を用意する場合を挙げています（同）。

## 手元で確かめる（3）: 300 枚を符号化する

`OffscreenCanvas`（第 99 回）に 1280 × 720 のアニメーション（色の変わるグラデーションの上を、円が 20 個動く）を描き、1 枚ごとに `VideoFrame` にして符号化しました。300 枚（30fps で 10 秒分）、目標 2Mbps、150 枚ごとにキーフレームを要求しています。

```js
const enc = new VideoEncoder({
  output: (chunk, meta) => chunks.push(chunk),   // meta.decoderConfig に復号の設定が来る
  error: e => console.error(e),
})
enc.configure({ codec, width: 1280, height: 720, bitrate: 2_000_000, framerate: 30, hardwareAcceleration })
for (let i = 0; i < 300; i++) {
  paint(i)                                                   // OffscreenCanvas に描く
  const frame = new VideoFrame(canvas, { timestamp: i * 33333 })   // マイクロ秒
  enc.encode(frame, { keyFrame: i % 150 === 0 })
  frame.close()                                              // 渡したらすぐ閉じる
  if (enc.encodeQueueSize > 10) await new Promise(r => enc.addEventListener('dequeue', r, { once: true }))
}
await enc.flush()
```

最後の `if` は背圧です。`encode()` はすぐに戻り、仕事は待ち行列に積まれます。積んだ数は `encodeQueueSize` で見え、減ると `dequeue` イベントが来ます（[WebCodecs §4.4](https://www.w3.org/TR/webcodecs/#videodecoder-event-summary)）。待たずに積み続けると、未処理のフレームがメモリにたまります。第 56 回の中継で、書けない間も読み続けると背圧が切れたのと同じです。

```
コーデック          加速        符号化 fps  合計バイト   キー平均   差分平均   RGBA 比   I420 比
H.264 avc1.42001f  hardware      76     2,525,138   14,353    8,377     438 倍    164 倍
H.264 avc1.42001f  software      52     2,480,036   16,500    8,212     446 倍    167 倍
VP9                software     181     1,913,418   16,017    6,313     578 倍    217 倍
AV1                software     152     1,828,325   10,054    6,068     605 倍    227 倍
```

300 枚の RGBA は 1,105,920,000 バイト（約 1.1GB）です。それが 2MB 前後になりました。H.264 の合計がほぼ 2.5MB なのは、目標の 2Mbps × 10 秒 = 2.5MB に**エンコーダが合わせた**からです。圧縮率は映像の性質より、指定したビットレートで決まっています。VP9 と AV1 は目標を下回りました。

符号化の速さは、描画とフレームの生成を含めたループ全体の値です。この条件では、ハードウェアの H.264 がソフトウェアの VP9 より遅く出ました。ハードウェアのエンコーダは 1 枚ごとの往復の待ちがあり、待ち行列を 10 枚で止めているこのループではそれが効いたと考えられます。ハードウェアなら速い、とは限りません。

キーフレームと差分の差が 2 倍程度しかないのは、この映像では毎フレーム画面全体の色が変わるからです。そこで、**ほとんど動かない映像**（単色の背景に、フレームの番号の文字だけが変わる）でも同じことをしました。

```
コーデック          加速        合計バイト   キー平均   差分平均
H.264              hardware     199,498     5,447      633
H.264              software     333,120     5,231    1,083
VP9                software     368,018     3,266    1,213
AV1                software     230,184     2,459      756
```

今度は目標の 2.5MB に届かず、ハードウェアの H.264 では**差分フレームがキーフレームの 9 分の 1**（633 バイト）になりました。変わったのは文字の部分だけなので、差分にはそこしか載りません。画面共有やスライドの録画が、同じビットレートでもカメラの映像よりずっと鮮明なのはこのためです。

## 手元で確かめる（4）: 復号する

符号化の最初の出力には、`meta.decoderConfig` として**復号に要る設定**が付いてきます。H.264 では、ここに `description` が入っていました。H.264 の登録文書は、`description` を ISO/IEC 14496-15 の AVCDecoderConfigurationRecord（MP4 の avcC の箱の中身）とみなすと定めています（[AVC (H.264) WebCodecs Registration](https://www.w3.org/TR/webcodecs-avc-codec-registration/)）。VP9 と AV1 には入っていません。コンテナを使うときは、この設定をファイルのヘッダに書き、読むときに取り出して `VideoDecoder.configure()` に渡します。

```js
const dec = new VideoDecoder({ output: frame => { draw(frame); frame.close() }, error: console.error })
dec.configure(decoderConfig)
for (const c of chunks) dec.decode(c)
await dec.flush()
```

```
コーデック   加速       復号 fps   出てきた形式   coded の大きさ   visibleRect   allocationSize
H.264       hardware    1,345     NV12          1280x720        1280x720      1,382,400
H.264       software      794     I420          1280x738        1280x720      1,382,400
VP9         software    1,514     NV12          1280x720        1280x720      1,382,400
AV1         software      388     I420          1280x720        1280x720      1,382,400
```

3 つのことが見えます。

1. **出てくる形式は実装しだい**です。同じ H.264 でも、ハードウェアからは NV12、ソフトウェアからは I420 が出ました。受け取る側は `format` を見て分岐するか、`copyTo()` で RGBA に変換させる必要があります
2. **coded の大きさと見える大きさは違う**ことがあります。ソフトウェアの H.264 は、縦 738 の領域に復号し、そのうち 720 行を `visibleRect` として示しました。描くときは `visibleRect` を使います
3. `allocationSize()` は見える領域の 1280 × 720 × 1.5 = 1,382,400 バイトで、最初に計算した YUV 4:2:0 の大きさと一致します

復号は 1 秒に数百から千数百枚で、再生に要る 30 枚 / 秒を大きく上回ります。AV1 のソフトウェア復号だけが目立って遅く、専用の回路が無い機械で AV1 を高解像度で再生する重さが表れています。

## close() を呼ぶ理由

`VideoFrame` は JavaScript のオブジェクトですが、中身の画素は JavaScript のヒープの外にあります。復号したフレームなら、**デコーダの持っているバッファ**、ハードウェアの復号なら GPU のメモリそのものかもしれません。

仕様は、出力された `VideoFrame` が要らなくなったらすぐ `close()` を呼ぶよう勧め、その理由を、元のメディアの資源は `VideoDecoder` が持っており、解放しなかったり GC を待ったりすると**復号が止まりうる**から、と書いています（[WebCodecs §4.5 decode()](https://www.w3.org/TR/webcodecs/#dom-videodecoder-decode)）。CPU のメモリ、GPU のメモリ、ハードウェアへの排他的なハンドルといったコーデックの資源は、すぐに使い尽くされうるので、使い終わったらすぐ解放すべきだ、とも定めています（[WebCodecs §1 Codec System Resources](https://www.w3.org/TR/webcodecs/#system-resources)）。

GC に任せられないのは、GC が見ているのは JavaScript のヒープの大きさだけだからです（第 26 回）。`VideoFrame` のオブジェクト自体は数十バイトなので、GC から見ると急いで回収する理由がありません。その裏で 1 枚 3MB のバッファが握られたままになります。

### 手元で確かめる（5）: 閉じずに溜める

1920 × 1080 の 900 枚（30 秒分）を復号し、出てきた `VideoFrame` を閉じずに配列に溜めたまま 4 秒待ち、それから全部閉じました。Chrome のすべてのプロセスの RSS（物理メモリの使用量）を外から `ps` で測っています。

```
                             溜めている間     全部 close() した後
ハードウェア H.264（NV12）      953 MB          895 MB
ソフトウェア VP9（NV12）       1,937 MB         916 MB
ソフトウェア VP9、毎回 close   1,216 MB        1,036 MB
```

ソフトウェアの復号では、溜めている間に RSS が**約 1GB 多く**、`close()` で戻りました。900 枚 × 3,110,400 バイトは約 2.8GB なので、RSS はその全部を数えてはいませんが、閉じないフレームがメモリを握り続けていることは見えます。ハードウェアの復号では RSS がほとんど動きませんでした。フレームの実体は GPU 側の面（macOS では IOSurface）にあり、プロセスの RSS には現れていないと考えられます。

この環境では、900 枚を溜めても**復号は止まりませんでした**。300 枚の 720p でも同じで、`decodeQueueSize` は 0 まで減り、`flush()` も完了しています。

<Callout type="warn" title="よくある誤解: 「手元で止まらなかったので close() は要らない」">
  止まるかどうかは、デコーダの実装と、ハードウェアが持つバッファの数で決まります。
  仕様が「止まりうる」と書いているのは、資源をデコーダが持っているからです（[WebCodecs §4.5](https://www.w3.org/TR/webcodecs/#dom-videodecoder-decode)）。
  出力先のバッファの数に限りがある実装では、それを全部アプリに握られると、次のフレームを書く場所がなくなります。
  手元の Chrome と M1 Pro で止まらなかったのは、その環境での 1 つの結果にすぎません。
  別の OS や GPU では止まりえますし、止まらなくても、上の表のようにメモリは握られ続けます。
  **描いたらすぐ閉じる。後で使うなら `clone()` して、それも閉じる**のが原則です。
</Callout>

仕様は、コピーを避けるために `clone()` と `close()` による参照の数え上げを定めています（[WebCodecs §9.1 Memory Model](https://www.w3.org/TR/webcodecs/#raw-media-memory-model)）。`clone()` は画素を複製せず、同じ資源への参照を 1 つ増やします。すべての参照が `close()` されたときに、資源が解放されます。

## コピーせずに GPU へ渡す

`VideoFrame` は `CanvasImageSource` の一種で、`drawImage()` に渡せます（[WebCodecs §9.4](https://www.w3.org/TR/webcodecs/#videoframe-interface)）。Chrome の解説も、`drawImage()` や WebGL の `texImage2D()` で使えると書いています（[Chrome for Developers: WebCodecs](https://developer.chrome.com/docs/web-platform/best-practices/webcodecs)）。

ここで気になるのは**コピーの回数**です。ハードウェアで復号したフレームは、もともと GPU のメモリにあります。それを CPU に読み出して RGBA に直し、また GPU に送るのは、第 14 回で見たメモリ階層を往復する無駄です。

WebGPU には、そのための専用の入口 `importExternalTexture()` があります（第 101 回）。仕様は `GPUExternalTexture` を、外部の映像のフレームを包んだ、サンプリングできる 2D テクスチャとし、**取り込んだ元をコピーせずに実装できる**（ただし実装の事情による）と書いています（[WebGPU §6.4](https://www.w3.org/TR/webgpu/#gpuexternaltexture)）。中身は RGBA とは限らず、Y と UV のような最大 3 枚の面と、色空間を変換するための情報を持ちうる、とも書いています（同）。WGSL の側では `texture_external` という型で受け、`textureSampleBaseClampToEdge` などで読みます（同）。YUV から RGB への変換は、シェーダがサンプリングするときに行われます。

```wgsl
@group(0) @binding(0) var video: texture_external;
@group(0) @binding(1) var samp: sampler;
@fragment fn fs(@location(0) uv: vec2f) -> @location(0) vec4f {
  return textureSampleBaseClampToEdge(video, samp, uv);   // NV12 でも RGBA が返る
}
```

### 手元で確かめる（6）: 取り込みの手間と、閉じた後

再生中の `<video>`（ソフトウェアで復号した VP9、640 × 360）から `new VideoFrame(video)` を作り、いくつかの入口に渡しました。

```
VideoFrame の形式                     I420A（WebM の VP9 がアルファを持っていた）
allocationSize()（そのままの形式）       576,000 バイト    = 640 × 360 × 2.5
copyTo(buf, { format: 'RGBA' })       921,600 バイト    = 640 × 360 × 4、stride 2560
WebGL texImage2D を 100 回 + finish     9.1 ms
WebGPU importExternalTexture を 100 回  0.9 ms
close() の後に importExternalTexture    OperationError: ... video frame that doesn't have back resource
```

`copyTo()` に `format: 'RGBA'` を渡すと、ブラウザが変換して詰めてくれます。大きさは 1.6 倍になります。`importExternalTexture()` は 1 回 0.01ms 以下で、画素を動かしていないことがうかがえます。ただし、この 0.9ms はテクスチャを取り込む手続きだけの時間で、GPU がサンプリングする時間は含みません。このフレームはソフトウェアで復号したものなので、どこかで GPU への転送は起きています。

`close()` の後で取り込もうとすると、**元の資源が無い**という例外になりました。`GPUExternalTexture` は、元の `VideoFrame` が生きている間だけ使える借り物です。

## カメラのフレームを横から取る

カメラの映像は `getUserMedia()` で `MediaStreamTrack` として得られ、普段は `<video>` に映すか、WebRTC で送ります。その途中でフレームを 1 枚ずつ取り出し、加工して戻すための API が、MediaStreamTrack の Insertable Streams です。

- **`MediaStreamTrackProcessor`**: トラックを流れるメディアを `ReadableStream` として取り出す。映像なら、チャンクは `VideoFrame`（[Media Capture Transform §2.1](https://www.w3.org/TR/mediacapture-transform/#track-processor)）
- **`VideoTrackGenerator`**: `VideoFrame` のストリームから、新しい映像のトラックを作る（[同 §2.2](https://www.w3.org/TR/mediacapture-transform/#video-track-generator)）

```
カメラ ─▶ MediaStreamTrack ─▶ Processor ─▶ VideoFrame ─▶ WebGPU で背景をぼかす ─▶ VideoFrame
                                                                                  │
                         RTCPeerConnection（第 79 回）◀── 新しいトラック ◀── Generator ┘
```

ビデオ会議の背景ぼかしは、この形で作れます。第 79 回の WebRTC は送受信を一括で引き受けてくれますが、その手前に自分の処理を挟みたいときに、この API と WebCodecs を組み合わせます。

仕様の作業部会は、この 2 つを専用の Worker に公開することでは合意していますが、Window にも公開するかは合意していません（[Media Capture Transform §2.1.1](https://www.w3.org/TR/mediacapture-transform/#track-processor-interface)）。名前も揺れていて、以前の提案の `MediaStreamTrackGenerator` が現在の `VideoTrackGenerator` に置き換わりました（[同 §6](https://www.w3.org/TR/mediacapture-transform/#backwards-compatibility)）。

手元の Chrome 155 では、仕様の合意と逆の状態でした。

```
               MediaStreamTrackProcessor   VideoTrackGenerator   MediaStreamTrackGenerator
Window         function                    undefined             function
Worker         undefined                   undefined             undefined
```

canvas の `captureStream(30)` のトラックを `MediaStreamTrackProcessor` で読むと、`BGRA 320x180` の `VideoFrame` が約 33ms 間隔のタイムスタンプ（0、32132、64558 マイクロ秒…）で取れました。**実装と仕様がずれている API** なので、使う前に、対象のブラウザで名前と公開先を確かめてください。

## 組み合わせで見る

動画のフレームを扱う道をまとめます。

| やりたいこと | 道 | 注意 |
| --- | --- | --- |
| 動画を再生して、上に絵を重ねる | `<video>` ＋ rVFC ＋ `drawImage` | rAF でなく rVFC で描けば、同じフレームを描き直さない |
| 動画に効果を掛けて表示する | `<video>` か `VideoDecoder` → `importExternalTexture` → WebGPU | 取り込んだテクスチャは元のフレームが生きている間だけ使える |
| ブラウザの中で動画を書き出す | canvas → `VideoFrame` → `VideoEncoder` → mux | コンテナは自分で用意する。`encodeQueueSize` で背圧を掛ける |
| 動画のファイルを 1 枚ずつ解析する | demux → `VideoDecoder` → `copyTo` | 出てくる形式は実装しだい。`format` と `visibleRect` を見る |
| カメラの映像を加工して送る | Processor → 加工 → Generator → WebRTC | 公開先と名前がブラウザで違う |
| どの方法でも | `VideoFrame.close()` | 描いたらすぐ閉じる。GC は外のメモリを見ていない |

## まとめ

- 動画は絵の列。1080p の RGBA を 30fps で流すと 1 秒に約 249MB。YUV 4:2:0 は色を 4 画素で共有し、1 画素 1.5 バイトにする
- コーデックは、他に頼らないキーフレームと、前との違いだけの差分フレームで縮める。多くは非可逆。動かない映像では、差分はキーフレームの 9 分の 1 になった
- `<video>` を canvas に描くなら、動画のフレームごとに呼ばれる `requestVideoFrameCallback` を使う。手元では rAF の半分の回数で呼ばれた
- WebCodecs は、`VideoFrame`・`VideoEncoder` / `VideoDecoder`・`EncodedVideoChunk` で、コーデックだけを取り出した API。コンテナの読み書きは含まない
- 対応するコーデックとハードウェアの有無は環境しだい。`isConfigSupported()` で毎回聞く。同じ H.264 でも、ハードウェアは NV12、ソフトウェアは I420 を出した
- `VideoFrame` の画素は JavaScript のヒープの外にある。`close()` しないとメモリを握り続け、仕様上は復号が止まりうる。手元では止まらなかったが、ソフトウェアの復号で約 1GB が握られた
- WebGPU の `importExternalTexture` は、映像のフレームをコピーせずにテクスチャとして扱える入口。YUV から RGB への変換はサンプリングのときに行われる
- カメラのフレームは `MediaStreamTrackProcessor` で取り出し、`VideoTrackGenerator` で戻す。仕様と実装の名前・公開先がずれている

ここまでで第 15 章は終わりです。DOM に任せる描き方から始め、Canvas 2D、WebGL、WebGPU、DOM を canvas に描き込む HTML-in-Canvas、そして動画のフレームまで、ブラウザの中で自分で画素を作る道を一通り見ました。どの回にも、**描いた画素を読み戻せるか**という問いが付いて回りました。別のオリジンの画像を描いた canvas が汚染されて `getImageData()` を拒むこと、HTML-in-Canvas が読み戻してよい描画だけを描くこと、汚染された（origin-clean でない）画像や動画から `VideoFrame` を作ろうとすると `SecurityError` になること（[WebCodecs §9.4.2](https://www.w3.org/TR/webcodecs/#videoframe-constructors)）は、どれも同じ規則の現れです。次の第 16 章では、その規則の大元を見ます。ブラウザは、**互いに信用しない多数のサイトのコードを同時に動かしています**。どのサイトがどのサイトのデータを読めるのか、まず第 104 回で、境界を決める 2 本の物差し、オリジンとサイトから始めます。
