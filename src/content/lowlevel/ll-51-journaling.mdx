## 1 つの操作は、1 回の書き込みではない

第 49 回で見たとおり、ファイルシステムはディスク上にいくつもの構造を持っています。ファイルに 4KB 追記するだけでも、書き換わる場所は 1 か所ではありません。

| 書き換える場所 | 内容 |
| --- | --- |
| ブロックの空き状況（ビットマップ） | 新しいブロックを「使用中」にする |
| inode | ファイルサイズと、ブロックの位置を更新する |
| データブロック | 追記した 4KB そのもの |

ディスクは、この 3 つを**まとめて 1 回で書く**ことができません。順番に書きます。そして、どの順番であっても、**途中で電源が落ちる**可能性があります。

```
 ビットマップ ✓   inode ✗   データ ✗     → ブロックが「使用中」なのに誰も指していない（漏れ）
 ビットマップ ✗   inode ✓   データ ✗     → inode が、他のファイルにも割り当たりうるブロックを指す（最悪）
 ビットマップ ✗   inode ✗   データ ✓     → データは書けたが、誰も知らない（無害だが消えた）
 ビットマップ ✓   inode ✓   データ ✗     → ファイルの末尾に、前に使っていた誰かのゴミが見える
```

どの組み合わせも、「全部書けた」でも「何も書かなかった」でもない中途半端な状態です。これを**クラッシュ整合性**の問題と呼びます。

前回の `fsync` は「いつ書き終わったかを知る」ための道具でした。今回は「**書いている途中で落ちても、構造が壊れない**」ための仕組みを見ます。

## 起動時に全部調べる: fsck

最も素朴な対策は、**起動時にディスク全体を検査する**ことです。これが `fsck`（file system check）です。

- すべての inode を読み、指しているブロックを集める
- ビットマップと突き合わせ、食い違いを直す
- どのディレクトリからも指されていない inode を `lost+found` に移す

問題は時間です。検査の量は**ディスクの大きさに比例**します。容量が数 TB になると、1 回の起動に何十分もかかります。しかも、壊れたのは直前の数個の操作だけなのに、全部を調べることになります。

さらに、fsck が直せるのは「構造の矛盾」だけです。上の表の最後の行のように、構造は正しいが**中身がゴミ**という状態は、見つけられません。

## 先に予定を書いておく: ジャーナリング

発想を変えます。本来の場所を書き換える前に、**これから何を書くかを、別の場所にまとめて書いておく**。この別の場所がジャーナル（日誌）です。

```
 1. ジャーナルに「ビットマップ・inode・データをこう書き換える」と書く
 2. 最後に「ここまでで 1 まとまり」という印（コミットレコード）を書く
 3. 本来の場所に書く（チェックポイント）
 4. ジャーナルの該当部分を捨てる
```

落ちた場所によって、起動時にやることが決まります。

| 落ちたタイミング | 起動時の処理 |
| --- | --- |
| 2 より前 | コミットレコードが無い。**その操作は無かったことにする** |
| 2 と 3 の間 | コミットレコードがある。**ジャーナルから本来の場所へ書き直す**（リプレイ） |
| 3 の途中 | 同じく、リプレイで書き直す。何度書いても結果は同じ |

操作は「全部起きた」か「何も起きなかった」のどちらかになります。起動時に調べるのは**ジャーナルだけ**なので、ディスクがどれだけ大きくても数秒で終わります。

<Callout type="tip" title="コミットレコードは 1 セクタに収める">
  この仕組みは、「コミットレコードの書き込みそのものは、途中で切れない」ことを前提にしています。
  そこで、コミットレコードは**ディスクが一度に書ける最小単位（セクタ）に収まる大きさ**にします。
  さらに ext4 はジャーナルの各ブロックにチェックサムを付け、
  中途半端に書かれたまとまりを検出できるようにしています（[Linux カーネルのドキュメント](https://www.kernel.org/doc/html/latest/filesystems/ext4/journal.html)）。
</Callout>

## 何をジャーナルに書くか

ジャーナリングには代償があります。**同じデータを 2 回書く**ことです。一度ジャーナルに、もう一度本来の場所に。データの量が多いと、これは重くなります。

そこで、多くのファイルシステムは**メタデータ（ビットマップ、inode、ディレクトリ）だけ**をジャーナルに書きます。ext4 には 3 つのモードがあります（[ext4 のドキュメント](https://www.kernel.org/doc/html/v6.0/admin-guide/ext4.html)）。

| モード | ジャーナルに書くもの | 保証 |
| --- | --- | --- |
| `data=journal` | メタデータとデータ | 最も安全。データも 2 回書くので遅い |
| `data=ordered`（既定） | メタデータだけ。ただし**関連するデータを先にディスクに書いてから**メタデータをコミットする | inode が、まだ書かれていないブロックを指すことはない |
| `data=writeback` | メタデータだけ。データとの順序は保証しない | 速いが、クラッシュ後にファイルの末尾に古いゴミが見えうる |

既定の `data=ordered` の要点は、**順序**です。データを先に、メタデータを後に書く。こうすれば、最悪でも「データは書けたがメタデータが古い」、つまり**変更が無かったことになる**だけで済みます。冒頭の表の最後の行（中身がゴミ）は起きません。

<Callout type="warn" title="ジャーナリングは、アプリのデータを守らない">
  ジャーナリングが守るのは**ファイルシステムの構造**です。
  アプリが `write` した内容が、クラッシュ後に残っている保証ではありません。

  たとえば、既存ファイルの途中を上書きしている最中に落ちれば、
  `data=ordered` でも**新旧が混ざった内容**が残りえます。
  ファイルシステムは壊れていないが、アプリのデータは壊れている。
  前回の「書いて `fsync` して `rename`」は、この問題をアプリ側で解くための手順でした。
</Callout>

## 上書きしないという選択: コピーオンライト

ジャーナリングは「上書きする前に予定を書く」方法でした。もう 1 つの方法は、**そもそも上書きしない**ことです。

ZFS や btrfs は、ブロックを書き換えるとき、**新しい場所に書き、指している親を更新する**という手順を取ります。親も上書きせず、新しい場所に書きます。これを根まで繰り返します。

```
 変更前                          変更後

      [根 v1]                      [根 v1]      [根 v2]  ← 最後に、根の位置だけを切り替える
      /     \                      /     \      /     \
   [A]      [B]                 [A]      [B]  [A]    [B']
   / \      / \                 / \      / \          / \
  1   2    3   4               1   2    3   4        3   4'   ← 4 を 4' として新しい場所に書く
```

最後に「今の根はここ」という 1 か所だけを書き換えます。この 1 回の書き込みが、操作全体のコミットになります。

- 根を切り替える前に落ちたら、古い根から辿れる**古い状態がそのまま残っている**
- 切り替えた後なら、新しい状態になっている

ジャーナルは要りません。**中途半端な状態が、そもそも辿れる場所に存在しない**からです。第 24 回で見た copy-on-write と同じ発想を、ディスクの上でやっています。

<Callout type="note" title="スナップショットがほぼ無料になる">
  古い根を捨てずに取っておけば、それが**その時点の完全なファイルシステム**になります。
  変更されていないブロックは新旧で共有されているので、コピーは発生しません。
  ZFS や btrfs のスナップショットが一瞬で取れるのは、この構造の副産物です。
</Callout>

代償もあります。

| 観点 | ジャーナリング（ext4 など） | コピーオンライト（ZFS、btrfs） |
| --- | --- | --- |
| 1 回の変更で書く量 | データ + ジャーナル | データ + 根までの親すべて |
| ファイルの配置 | 上書きなので、連続した配置が保たれる | 書くたびに場所が変わり、**断片化しやすい** |
| スナップショット | 別の仕組みが要る | 構造から自然に得られる |
| データのチェックサム | 通常は無い | 親がチェックサムを持てるので、**ビットの腐敗を検出できる** |

## ディスクが書く単位より大きい書き込み

ここまでは「1 セクタの書き込みは途中で切れない」を前提にしていました。しかし、上のソフトウェアが一度に書きたい単位は、たいていそれより大きいものです。

データベースのページは 8KB や 16KB です（第 56 回）。ディスクの原子的な書き込みの単位が 4KB なら、16KB のページを書いている途中で落ちると、**前半が新しく後半が古い**ページが残ります。これを **torn write**（ちぎれた書き込み）と呼びます。

データベースは、これを自分で防いでいます。

- **PostgreSQL**: チェックポイント後にページを初めて変更するとき、**ページ全体をログに書く**（`full_page_writes`）。ページがちぎれても、ログにある完全なページから復元できる（[PostgreSQL のドキュメント](https://www.postgresql.org/docs/current/runtime-config-wal.html)）
- **MySQL（InnoDB）**: ページを本来の場所に書く前に、**別の領域に一度書く**（doublewrite buffer）。本来の場所がちぎれたら、そちらから戻す（[MySQL のドキュメント](https://dev.mysql.com/doc/refman/8.4/en/innodb-doublewrite-buffer.html)）

どちらも「2 回書いて、どちらかが無事なら直せる」という構造です。**ファイルシステムのジャーナリングを、データベースがページの単位でもう一度やっている**と見ることができます。

## データベースのログは、同じ発想

ここまでの話は、ファイルシステムに限りません。

| ファイルシステム | データベース |
| --- | --- |
| ジャーナル | WAL（Write-Ahead Log） |
| コミットレコード | コミットのログレコード |
| チェックポイント | チェックポイント（ダーティページを書き出し、古いログを捨てる） |
| リプレイ | クラッシュリカバリ（redo） |
| コピーオンライト | LMDB のようなコピーオンライトの B+tree |

第 48 回で「WAL はランダムな書き込みの代わりに、順次書き込みのログだけを `fsync` する」と書きました。その裏にあるのが、今回の**先に予定を書き、印を書いたら確定**という構造です。第 58 回で、データベースの側から改めて見ます。

<Callout type="warn" title="二重のジャーナリング">
  データベースは自分で WAL を持ち、その下のファイルシステムもジャーナルを持っています。
  さらに下の SSD も、内部で書き込みの記録を持っています（次回）。
  **同じ「書いた」を、層ごとに何度も記録している**わけです。

  データベースが `O_DIRECT` を使ったり、ファイルシステムのモードを選んだりするのは、
  この重複をどこかで減らすためです。
</Callout>

## 手元で確かめる

```bash
# マウントオプション（data= の指定が無ければ ordered）
findmnt -o TARGET,FSTYPE,OPTIONS /

# ext4 のジャーナルの情報
sudo dumpe2fs -h /dev/<デバイス> | grep -i journal

# ジャーナルを書いているカーネルスレッド（jbd2）
ps aux | grep jbd2
```

`jbd2/sda1-8` のようなスレッドが見えるはずです。これが ext4 のジャーナルを書いています。`iotop` で見ると、`fsync` の多いプログラムを動かしたときに、このスレッドの書き込みが増えるのが分かります。

## まとめ

- ファイルへの 1 回の変更は、ディスク上では複数か所の書き込みになる。途中で落ちると構造が矛盾する
- fsck はディスク全体を調べて直す。大きいディスクでは遅く、中身のゴミは見つけられない
- ジャーナリングは、先に予定を書き、コミットレコードを書いたら確定とする。起動時はジャーナルだけ見ればよい
- ext4 の既定 `data=ordered` は、メタデータだけをジャーナルに書き、データを先に書く順序で守る
- ジャーナリングが守るのはファイルシステムの構造で、アプリのデータではない
- コピーオンライトの FS は上書きせず、根の切り替えだけで確定する。スナップショットとチェックサムが副産物
- データベースは、ページのちぎれを full page writes や doublewrite で自分で防ぐ。WAL はジャーナルと同じ構造
