## どのサービスにも、同じコードが要る

サービスが数十に分かれると、**どのサービスにも同じ種類のコード**が必要になります。

| 面倒 | なぜ要るか |
| --- | --- |
| タイムアウト | 相手が詰まったとき、こちらまで道連れで止まらないため |
| 再試行 | 一時的な失敗（Pod の入れ替え中など）を吸収するため |
| 流量の遮断 | 壊れた相手に送り続けて、傷を広げないため |
| リクエスト単位の振り分け | 前回見たとおり、Service は接続単位でしか散らさないため |
| 暗号化と相手の確認 | クラスタ内の通信を盗み見や成りすましから守るため |
| 観測 | どの呼び出しが遅いのか、どこで失敗したのかを知るため |

これをライブラリとして各サービスに組み込む方法は、昔からあります。ただし、サービスが Go、Java、Python、Node で書かれていれば、**同じ振る舞いを 4 つの言語で書き、4 つの版を揃え続ける**ことになります。どれか 1 つのライブラリにバグがあれば、そのサービスだけが違う振る舞いをします。

## 第 9 章で一度、同じことをしている

これは、実は初めて出てくる問題ではありません。

第 54 回で見たとおり、TCP は、**再送、順序の保証、流量の制御**を、アプリから取り上げてカーネルに移したものでした。アプリは `send` するだけで、パケットが落ちても自分で送り直す必要はありません。すべてのアプリが同じ再送の実装を持つ代わりに、1 か所で正しく実装する、という判断です。

サービスメッシュは、**その 1 段上で同じ判断をします**。タイムアウトや再試行や暗号化といった L7（リクエスト単位）の面倒を、アプリから取り上げて、**アプリの横で動くプロキシ**に移します。

```
 ライブラリ方式                     メッシュ方式
 ┌────────────────────┐            ┌────────────┐  ┌──────────┐
 │ アプリ               │            │ アプリ       │→ │ プロキシ   │→ 相手
 │  + 再試行            │→ 相手       │ （素の HTTP）│  │ 再試行     │
 │  + タイムアウト       │            └────────────┘  │ 暗号化     │
 │  + 暗号化・観測       │                             │ 観測       │
 └────────────────────┘                             └──────────┘
 言語ごとに実装が要る                  プロキシは 1 種類で済む
```

プロキシは言語を問いません。アプリはただ `http://api/` に平文で送るだけで、その先はプロキシが引き受けます。

## アプリに気づかれずに、プロキシを挟む

問題は、**アプリのコードを変えずに**、どうやって通信をプロキシへ通すかです。アプリは `api:80` に繋いでいるつもりで、プロキシの存在を知りません。

ここで効いてくるのが、第 87 回で見た **Pod の中のコンテナは Network 名前空間を共有する**という性質です。同じ Pod にプロキシのコンテナを入れれば（サイドカー）、アプリとプロキシは同じ `localhost`、同じネットワークインタフェース、同じ **netfilter の規則**を共有します。

そこで、Pod の起動時に、Pod の Network 名前空間の中へ次のような規則を入れます。

```
 この Pod から出ていく TCP は、宛先がどこであっても
   → 同じ名前空間のプロキシの待ち受けポートへ REDIRECT する
 （ただし、プロキシ自身が出す通信は除く。除かないと無限に回る）
```

前回、Service の仮想 IP は、カーネルが宛先を書き換えることで成り立っていました。これも同じ仕組みです。ただし今度の書き換え先は Pod ではなく、**同じ Pod の中のプロキシ**です。

```
 アプリ: connect(api の ClusterIP:80)
    │  netfilter が宛先を localhost のプロキシへ書き換える
    ▼
 プロキシ: accept() した接続の、本来の宛先は？
    │  getsockopt(SO_ORIGINAL_DST) で書き換え前の宛先を取り出す
    ▼
 プロキシ: 本来の宛先に向けて、自分で接続し直す
```

書き換えると、プロキシが受け取った接続は「プロキシ宛て」に見えてしまい、アプリが本当はどこに繋ぎたかったのかが分かりません。そこで Linux は、conntrack（前回）が覚えている書き換え前の宛先を、**`SO_ORIGINAL_DST` というソケットオプション**で読み出せるようにしています。Envoy の文書にも、書き換えられた接続の本来の宛先をこのオプションで読むと書かれています（[Envoy Docs](https://www.envoyproxy.io/docs/envoy/latest/configuration/listeners/listener_filters/original_dst_filter)）。

**アプリから見れば、ただ `api` に繋いだだけ**です。第 42 回で見た「プログラム側を一切変えずに、fd の向き先を差し替える」リダイレクトと、発想が同じです。

<Callout type="note" title="規則を入れるのは誰か">
  netfilter の規則を書き換えるには、第 85 回で見た `CAP_NET_ADMIN` が要ります。
  アプリの Pod にこの権限を持たせたくないので、
  権限を持つ init コンテナに一度だけ規則を入れさせてから終了させる方式や、
  CNI プラグイン（前回）の段階で規則を入れてしまう方式が取られます。
  第 95 回の eBPF で、ソケットの段階で向き先を差し替える実装もあります。
</Callout>

## 誰がプロキシに指示を出すのか

プロキシが 1 つだけなら、設定ファイルを手で書けば済みます。しかし Pod が 500 個あれば、プロキシも 500 個です。そして、それぞれが「`api` の実体の Pod は今どれか」「`api` への再試行は何回か」を知っていなければなりません。

そこで、サービスメッシュは 2 つの層に分かれます（[Istio Docs](https://istio.io/latest/docs/ops/deployment/architecture/)）。

| 層 | 役割 | 動く頻度 |
| --- | --- | --- |
| **データプレーン** | 実際にリクエストを受け取り、振り分け、暗号化し、記録するプロキシ群 | リクエストごと |
| **コントロールプレーン** | Kubernetes の API を watch し、各プロキシに設定と証明書を配る | 変化があったときだけ |

この分け方は、第 86 回で見た Kubernetes 自身の構造と同じです。**速い経路（リクエスト）には判断を持ち込まず、遅い経路（設定）で判断してから配る**。第 55 回で、1 パケットに使える時間がわずかしかないので、パケットごとの経路からできるだけ仕事を追い出したのと同じ考え方です。

コントロールプレーンが止まっても、プロキシは**最後に受け取った設定のまま**動き続けます。新しい Pod への振り分けは反映されなくなりますが、既存の通信は止まりません。

## 暗号化と、相手が誰かの確認

クラスタの中の通信は、同じ組織の中とはいえ、ノードをまたげば共有の網を通ります。メッシュは、プロキシ同士の通信を **mTLS**（双方が証明書を出し合う TLS）で包むことで、これを守ります。

ここで問題になるのが、**証明書に何を書くか**です。普通の TLS なら、証明書にはホスト名を書きます。しかし Pod の IP はすぐ変わり（前回）、同じ IP が次の瞬間には別のサービスの Pod に割り当てられるかもしれません。**IP では、相手が誰かを表せません。**

そこで、IP ではなく**そのワークロードが何者か**を証明書に書きます。よく使われるのが **SPIFFE** という形式で、ID は次のような URI になります（[SPIFFE](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/)）。

```
spiffe://cluster.local/ns/shop/sa/api
         └ 信頼の範囲  └ 名前空間 └ サービスアカウント
```

コントロールプレーンは認証局の役を担い、各プロキシに**寿命の短い証明書**を配り、期限が来る前に取り替え続けます。アプリは証明書の存在すら知りません。

これで、「`shop` 名前空間の `web` からの呼び出しだけを `api` に通す」という規則を、IP ではなく**名前で**書けるようになります。第 85 回で見たコンテナの権限の絞り方を、ネットワークの上の呼び出しにまで広げたものです。

## 再試行は、掛け算になる

メッシュを入れると、再試行を 1 行の設定で足せます。便利ですが、ここに典型的な事故があります。

```
 web ──→ api ──→ db
  再試行 3 回   再試行 3 回
```

`db` が一時的に詰まると、`api` のプロキシは 1 回のリクエストにつき最大 3 回送ります。`web` のプロキシも、`api` が失敗を返すたびに 3 回送り直します。**`db` には、元の 1 回が 9 回になって届きます**。段が 3 つなら 27 回です。

詰まっているところに、詰まっているからこそ大量のリクエストを送り込み、回復を妨げる。これを **リトライストーム** と呼びます。

<Callout type="warn" title="再試行を足すときに確かめること">
  - **その操作は、2 回行われても安全か。** 支払いのような操作は、再試行で二重に実行されうる。
    第 93 回で見る冪等性と同じ問題
  - **どの段で再試行するか。** 全段で再試行すると掛け算になる。1 か所に寄せる
  - **全体の時間の上限。** 再試行の合計が、呼び出し元のタイムアウトを超えないようにする

  第 54 回の TCP は、再送の間隔を指数的に広げ、輻輳を検出すると送る量そのものを減らしました。
  再試行を足すなら、同じだけの慎重さが要ります。
</Callout>

## プロキシをどこに置くか

ここまでは、Pod ごとにプロキシを入れる **サイドカー方式**で説明しました。最も素直な形ですが、代償もはっきりしています。

| 観点 | サイドカー方式 | ノード単位の方式 |
| --- | --- | --- |
| プロキシの数 | Pod の数だけ | ノードの数だけ（L7 の処理は必要な分だけ別に置く） |
| メモリ | Pod ごとに消費する。小さな Pod が多いと割合が大きい | ノードで共有する |
| 障害の範囲 | その Pod だけ | そのノードの全 Pod |
| プロキシの更新 | すべての Pod を作り直す必要がある | ノード上のプロキシだけ入れ替える |
| 起動の順番 | アプリより先にプロキシが準備できていないと、最初の通信が失敗する | Pod の起動とは独立 |

ノード単位の方式の例として、Istio の ambient モードは、**ノードごとの L4 のプロキシ**で mTLS と L4 の認可を行い、HTTP を理解する処理が必要なときだけ **Pod の外に別の L7 のプロキシ**を置きます（[Istio Docs](https://istio.io/latest/docs/ambient/overview/)）。暗号化だけが目的なら、L7 のプロキシは要りません。

どちらが正しいというより、**何を共有し、何を分けるか**の選択です。第 76 回で、仮想マシンとコンテナの違いを「何を共有するか」で整理したのと同じ構図です。共有すれば軽くなり、分ければ障害の範囲が狭くなります。

<Callout type="tip" title="サイドカーの起動と終了の順番">
  サイドカー方式では、プロキシがアプリより**先に起動し、後に終了する**必要があります。
  プロキシが先に止まると、終了処理中のアプリが最後のリクエストに応答できません。
  Kubernetes は、init コンテナに `restartPolicy: Always` を付けたものを「サイドカー」として扱い、
  通常のコンテナより先に起動し、後に止める仕組みを持つようになりました
  （[Kubernetes Docs](https://kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/)）。
  終了の順番の話は、次回の入れ替えの中でもう一度出てきます。
</Callout>

## 払うもの

メッシュは、全サービスに同じ振る舞いを配れる一方で、次のものを払います。

**1 回の呼び出しに、プロキシが 2 つ挟まる。** 送り手の横のプロキシと、受け手の横のプロキシです。それぞれが接続を受け、解析し、暗号化し、送り直します。1 段ごとの遅延は小さくても、呼び出しが何段も連なるほど積み重なります。

**失敗の形が増える。** アプリが正しくても、プロキシの設定の誤りで通信が止まります。コントロールプレーンが配った 1 つの誤った設定が、**全 Pod に同時に**行き渡ります。

**調べる対象が増える。** 「なぜ繋がらないのか」を調べるとき、アプリ、プロキシ、書き換え規則、証明書、コントロールプレーンのどこで止まっているかを切り分けることになります。

このため、サービスが少なく、言語も揃っているなら、ライブラリで足りることも多くあります。メッシュが本当に効くのは、**サービスの数と言語の種類が増え、全体で振る舞いを揃えることの価値が、この代償を上回ったとき**です。

## まとめ

- タイムアウト、再試行、暗号化、観測は、どのサービスにも要る。ライブラリだと言語ごとに実装が要る
- メッシュは、それをアプリの横のプロキシに移す。TCP が再送をアプリからカーネルに移したのと同じ判断
- プロキシは、Pod の Network 名前空間の中の netfilter の規則で透過的に挟まれる。本来の宛先は `SO_ORIGINAL_DST` で取り出す
- データプレーンはリクエストを処理し、コントロールプレーンは watch して設定と証明書を配る
- mTLS の相手は IP ではなくワークロードの ID で表す。SPIFFE の URI と、寿命の短い証明書
- 再試行は段の数だけ掛け算になる。冪等性と、再試行する段を 1 か所に寄せることが要る
- サイドカーかノード単位かは、何を共有し何を分けるかの選択

次は、Pod を入れ替えるときに、この通信の経路の中で何が起きているのか。止めずに入れ替えるための仕組みを見ます。
