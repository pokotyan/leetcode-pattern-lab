## 読むだけでは見えないものを確かめる

第 187 回の SAST と SCA は、どちらも**動かさずに読む**道具でした。この回では、残りの 3 つを扱います。

| 道具 | 何を相手にするか | 何を確かめるか |
| --- | --- | --- |
| **DAST**（Dynamic Application Security Testing） | 動いている Web アプリ | 外から要求を送り、応答に問題が表れるか |
| **IaC の検査** | Terraform などのインフラのコード | これから作る設定が基準に反していないか |
| **CSPM**（Cloud Security Posture Management） | クラウドの今の設定 | 実際に存在するリソースが基準に反していないか |

3 つは、見ている時点が違います。IaC の検査は**作る前**の設定を、DAST と CSPM は**動いている間**の状態を見ます。第 186 回で、作った時点の正しさと動いている間の正しさは別物であり、その差を**ドリフト**と呼びました。この回の後半では、そのドリフトが IaC の検査からは見えず、CSPM にしか見えないことを確かめます。

| Checkov | 3.3.24（`bridgecrew/checkov` イメージ） |
| Conftest | v0.71.1（OPA 1.21.1、`openpolicyagent/conftest` イメージ） |

DAST の実験は、自分で作った Docker のネットワーク `ll176-net` の中だけで行いました。検査対象のアプリ（`ll176-app`）も ZAP も、そのネットワークの外には要求を送っていません。Terraform は `plan` までで止め、`apply` はしていません。クラウドのアカウントは使っておらず、ダミーの認証情報で plan を作っています。CSPM の部分は、手で作った JSON を使った**模擬**です。

## DAST: 外から要求を送る

DAST の道具は、ブラウザと同じ立場でアプリに HTTP の要求を送り、返ってきた応答を調べます。ソースコードは見ません。代表的なオープンソースの道具が **ZAP** です。

ZAP の動きは、大きく 3 段に分かれます。

```
① 探索（spider）       リンクやフォームをたどって、URL とパラメータの一覧を作る
        │
② パッシブスキャン      探索で流れた要求と応答を、横から眺めるだけで調べる
        │                （ヘッダの欠落、Cookie の属性、情報の漏れ）
③ アクティブスキャン    パラメータに攻撃用の値を入れて要求を送り直し、
                         応答の変化から脆弱性を判定する
```

②と③の違いが重要です。パッシブスキャンは、**アプリに余計な要求を送りません**。探索のときに流れた通信を読むだけです。アクティブスキャンは、**実際に攻撃に相当する要求を送ります**。

ZAP はこの 2 つを、コンテナで動かすためのスクリプトとして用意しています。

| スクリプト | すること | 向いている場面 |
| --- | --- | --- |
| `zap-baseline.py` | 既定で 1 分間探索し、パッシブスキャンだけを行う。実際の攻撃はしない | CI、本番環境 |
| `zap-full-scan.py` | 時間制限なしで探索し、その後にアクティブスキャンを行う。実際の攻撃をするため長時間かかりうる | 許可を得た検証環境 |

baseline は「実際の"攻撃"は行わず、比較的短い時間で終わる」と説明されています（[ZAP](https://www.zaproxy.org/docs/docker/baseline-scan/)）。full scan は「実際の"攻撃"を行い、長時間かかる可能性がある」とされています（[ZAP](https://www.zaproxy.org/docs/docker/full-scan/)）。

<Callout type="warn" title="アクティブスキャンは許可された相手にだけ">
  アクティブスキャンが送るのは、SQL インジェクションやパス・トラバーサルを試す値そのものです。
  相手から見れば攻撃と区別がつきません。データを書き換える機能があれば、実際に書き換わることもあります。
  **自分が管理し、検査の許可を得た環境にだけ**当ててください。この回の実験も、手元の Docker ネットワークの中だけで行っています。
</Callout>

## 手元で確かめる: ZAP をローカルのアプリに当てる

検査の対象として、わざと問題を入れた小さなアプリを用意しました。トップページで Cookie を発行し、`/search` では受け取った `q` をそのまま HTML に埋め込みます。第 100 回で見た反射型 XSS の形です。

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
from urllib.parse import urlparse, parse_qs

class H(BaseHTTPRequestHandler):
    def do_GET(self):
        u = urlparse(self.path)
        if u.path == "/":
            body = '<html><head><title>ll176</title></head><body><a href="/search?q=hello">search</a></body></html>'
            self.send_response(200)
            self.send_header("Set-Cookie", "session=abc123; Path=/")
        elif u.path == "/search":
            q = parse_qs(u.query).get("q", [""])[0]
            body = f"<html><body><p>results for {q}</p></body></html>"
            self.send_response(200)
        else:
            body = "not found"
            self.send_response(404)
        data = body.encode()
        self.send_header("Content-Type", "text/html")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

HTTPServer(("0.0.0.0", 8000), H).serve_forever()
```

これを専用のネットワークで起動し、同じネットワークに ZAP のコンテナを入れます。

```bash
docker network create ll176-net
docker run -d --rm --name ll176-app --network ll176-net \
  -v "$PWD":/app -w /app python:3.13-alpine python app.py

docker run --rm --network ll176-net -v "$PWD/zap":/zap/wrk:rw \
  zaproxy/zap-stable zap-baseline.py -t http://ll176-app:8000/ -J baseline.json -I
```

`-I` は、警告だけなら終了コードを失敗にしない指定です。

### full scan の結果

同じアプリに full scan を当てました（探索は 1 分に制限）。2 分 36 秒かかり、警告は 12 種類になりました。baseline に無かったものだけを抜き出します。

```

	http://ll176-app:8000/search?q=%3C%2Fp%3E%3CscrIpt%3Ealert%281%29%3B%3C%2FscRipt%3E%3Cp%3E (200 OK)

	http://ll176-app:8000/search?q=%3Cscript%3Ealert(5397)%3C/script%3E (200 OK)
WARN-NEW: Source Code Disclosure - File Inclusion [43] x 1
	http://ll176-app:8000/search?q=hello (200 OK)
```

反射型 XSS の判定では、ZAP は `</p><scrIpt>alert(1);</scRipt><p>` という値を `q` に入れ、**同じ文字列が応答にそのまま現れた**ことを証拠（evidence）として記録していました。直前の `<p>` を閉じてから `<script>` を挿し込む値になっているのは、埋め込まれる位置の文脈に合わせて値を選んでいるためです。

このとき、アプリが受け取った要求は約 560 件でした。`/search` に届いた値の一部を並べると、アクティブスキャンが何をしているかが分かります。

```
/search?q=c%3A%2FWindows%2Fsystem.ini
/search?q=..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2FWindows%2Fsystem.ini
/search?q=%2Fetc%2Fpasswd
/search?q=..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2F..%2Fetc%2Fpasswd
```

検索語を受け取るだけのパラメータにも、パス・トラバーサルやファイルの読み出しを試す値が順に送られています。**アプリの中身を知らないので、あり得る攻撃を片端から試す**わけです。

### 誤検知も出る

3 つ目の `Source Code Disclosure - File Inclusion` は誤検知です。このアプリはファイルを読んでいません。ZAP の記録には、判定の理由が次のように書かれていました。

```
The output for the source code filename [search] differs sufficiently from that of
the random parameter [nqqenuhzpmlicikewlcggcwenidoskdhguzfzw], at [65%],
compared to a threshold of [75%]
```

`q` に `search` を入れた応答と、でたらめな文字列を入れた応答を比べ、似ている度合いが閾値を下回ったので「ファイル名を渡すと違う中身が返る」と推測しています。このアプリは入力をそのまま返すので、入力が違えば応答も違います。DAST は**応答の差から推測する**ため、こうした判定の誤りは避けられません。第 187 回で SAST の誤検知の扱いを見ましたが、DAST でも同じく、**ルールごとに無視・警告・失敗を設定ファイルで決めておく**のが普通です（`zap-baseline.py` の `-c` で渡します）。

## 認証の奥をどう検査するか

実際のアプリでは、重要な機能のほとんどがログインの後ろにあります。ZAP の文書も、アプリが認証を使うなら ZAP にそれを扱う設定をしないと、保護された機能には一切到達できない、と述べています（[ZAP](https://www.zaproxy.org/docs/authentication/)）。

扱い方は、だいたい次のどれかです。

| 方法 | 内容 | 注意点 |
| --- | --- | --- |
| ログインの手順を教える | フォームの送信先と項目、ログイン済みかを判定する文字列を設定する | ログアウトの URL を探索で踏むと、以降は未ログインのまま検査が続く |
| トークンを渡す | 事前に取得したセッションの Cookie や `Authorization` ヘッダを、すべての要求に付ける | トークンの有効期限が検査の途中で切れることがある |
| ブラウザで記録する | ブラウザを使った認証の手順を記録し、再生させる | 多要素認証や CAPTCHA は、検査用の環境で外しておく必要がある |

**検査用のユーザは、本番のデータに触れない環境で、権限ごとに用意します**。一般ユーザと管理者の両方で検査すると、第 135 回で見た認可の誤り（一般ユーザで管理者の機能が呼べる）にも近づけます。ただし、「ユーザ A が ユーザ B のデータを読める」という越境は、ZAP のような汎用の道具には意味が分かりません。これは第 191 回で、テストとして書く方法を見ます。

## SAST と DAST の守備範囲

同じ反射型 XSS は、第 187 回の taint 解析でも見つけられます。`request` から来た値（source）が、エスケープ（sanitizer）を通らずに HTML（sink）に流れているからです。では、2 つは何が違うのでしょうか。

| 観点 | SAST | DAST |
| --- | --- | --- |
| 必要なもの | ソースコード | 動いているアプリ |
| 言語やフレームワーク | 対応したものだけ | 関係ない（HTTP さえ話せばよい） |
| 指摘の場所 | ファイルと行 | URL とパラメータ |
| 得意なもの | 値の流れの誤り。まだ到達できない経路も読める | ヘッダ、Cookie、TLS、エラー画面など、**設定と環境**の問題 |
| 苦手なもの | 実行時の設定、プロキシや CDN が付け足す・消すもの | 探索で見つからない画面、認証の奥、業務上の意味 |
| 検査にかかる時間 | 分の単位。変更のたびに回せる | 今回の小さなアプリでも 2 分以上。大きなアプリでは時間単位 |

baseline で見つかったヘッダの欠落は、アプリのコードではなく、前に立つ Web サーバや CDN の設定で直すこともよくあります。**コードには何も書かれていないので、SAST にはそもそも見えません**。逆に、管理画面の奥の、まだどこからもリンクされていない機能の脆弱性は、DAST には見えず SAST には見えます。2 つは置き換えではなく、補い合う関係です。

## IaC の検査: 作る前の設定を読む

ここからはインフラの話です。Terraform のようなインフラのコード（IaC）は、それ自体が「これから作る設定」の記述です。だから、**作る前に読んで基準と比べる**ことができます。仕組みは SAST に近く、対象がアプリのコードからインフラのコードに変わっただけです。

検査用に、わざと悪い設定を並べた Terraform を書きました。

```hcl
resource "aws_s3_bucket" "reports" {
  bucket = "ll176-reports"
}

resource "aws_s3_bucket_public_access_block" "reports" {
  bucket                  = aws_s3_bucket.reports.id
  block_public_acls       = false
  block_public_policy     = false
  ignore_public_acls      = false
  restrict_public_buckets = false
}

resource "aws_security_group" "web" {
  name        = "ll176-web"
  description = "web"

  ingress {
    description = "ssh"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_db_instance" "main" {
  identifier          = "ll176-db"
  engine              = "postgres"
  instance_class      = "db.t4g.micro"
  allocated_storage   = 20
  username            = "app"
  password            = "change-me-please"
  storage_encrypted   = false
  publicly_accessible = true
  skip_final_snapshot = true
}
```

公開を止める設定をすべて外した S3 のバケット、SSH をインターネット全体に開けたセキュリティグループ、暗号化せず外部から到達できる RDS です。

`CKV2_` で始まるものが、グラフを使うチェックです。`CKV2_AWS_5` は「このセキュリティグループはどのリソースにも付いていない」という指摘で、1 つのリソースだけを見ていては判定できません。

2 つの道具を比べると、**件数がまるで違います**（Trivy は 14 件、Checkov は 24 件）。Checkov は、クロスリージョンのレプリケーション、イベント通知、ライフサイクルの設定、Multi-AZ のような、セキュリティというより運用の推奨に近いものまで指摘しています。どの道具も「何を悪いとみなすか」の一覧を持っており、その一覧が違えば結果も違います。**道具の既定の一覧をそのまま合格の基準にせず、自分たちの基準に合わせて取捨する**必要があります。

もう一つ、平文で書いたデータベースのパスワード `change-me-please` は、今回の指定ではどちらの失敗の一覧にも出てきませんでした。設定の誤りの検査と、秘密の検出は別の仕事です。秘密の検出は第 189 回で扱います。

## plan を読む

`.tf` のファイルを読む検査には限界があります。変数、モジュール、`count` や `for_each` で作られるリソースは、**値が決まるまで何ができるか分かりません**。そこで、Terraform が実際に作ろうとしているものを書き出した **plan** を読む方法があります。

```bash
terraform init
terraform plan -out=tfplan
terraform show -json tfplan > plan.json
```

```
Plan: 4 to add, 0 to change, 0 to destroy.
```

plan の JSON には、リソースごとの変更が `resource_changes` として並びます。`change.actions` が何をするか（`create`、`update`、`delete` など）、`change.after` が変更後の値です（[HashiCorp Developer](https://developer.hashicorp.com/terraform/internals/json-format)）。今回のセキュリティグループは次のようになっていました。

```json
{
  "address": "aws_security_group.web",
  "type": "aws_security_group",
  "change": {
    "actions": ["create"],
    "after": {
      "ingress": [
        { "cidr_blocks": ["0.0.0.0/0"], "description": "ssh",
          "from_port": 22, "to_port": 22, "protocol": "tcp", ... }
      ]
    }
  }
}
```

（一部の項目を省略しています）

**変数もモジュールも展開済みの、完成した値**です。Checkov も plan の JSON を `-f` で読めて、その方が依存関係や文脈の情報が多い、と説明しています（[Checkov](https://www.checkov.io/7.Scan%20Examples/Terraform%20Plan%20Scanning.html)）。

<Callout type="warn" title="plan のファイルには秘密がそのまま入る">
  `terraform plan` の画面では、パスワードは `(sensitive value)` と伏せられていました。
  ところが JSON を見ると、今回の plan では次のようになっていました。

  ```
  after.password           = change-me-please
  after_sensitive.password = True
  ```

  `after_sensitive` は「この値は機密」という印を付けるだけで、値そのものは `after` に残っています。
  Terraform の文書も、`sensitive` を付けた値は state と plan の両方のファイルに保存され、
  そのファイルを読める人なら誰でも値を読める、と明記しています（[HashiCorp Developer](https://developer.hashicorp.com/terraform/language/manage-sensitive-data)）。
  plan の JSON を CI の成果物として保存したり、外部の検査サービスに送ったりするときは、この点に注意が要ります。
</Callout>

## policy as code: 自分たちの基準を書く

道具の既定のチェックは便利ですが、組織ごとの決まりは入っていません。「管理用のポートは社内の範囲からだけ」「本番のデータベースは外から到達できない」といった**自分たちの基準を、コードとして書いて機械で判定する**のが **policy as code** です。

よく使われるのが、OPA（Open Policy Agent）の **Rego** という言語です。Rego は、望むルールや判断をコードとして表現するための宣言的な言語で、JSON のような入れ子になったデータへの問い合わせを書きます（[OPA](https://www.openpolicyagent.org/docs/policy-language)）。**Conftest** は、その Rego で書いたポリシーを設定ファイルに当てる道具で、既定では `main` という名前空間の `deny`、`warn`、`violation` という名前のルールを探します（[Conftest](https://www.conftest.dev/)）。

先ほどの plan の JSON に当てるポリシーを書きました。

```rego
package main

import rego.v1

admin_ports := {22, 3389}

deny contains msg if {
	rc := input.resource_changes[_]
	rc.type == "aws_security_group"
	not "delete" in rc.change.actions
	rule := rc.change.after.ingress[_]
	"0.0.0.0/0" in rule.cidr_blocks
	some port in admin_ports
	rule.from_port <= port
	port <= rule.to_port
	msg := sprintf("%s: port %d is open to 0.0.0.0/0", [rc.address, port])
}

deny contains msg if {
	rc := input.resource_changes[_]
	rc.type == "aws_db_instance"
	rc.change.after.publicly_accessible == true
	msg := sprintf("%s: publicly_accessible must be false", [rc.address])
}

warn contains msg if {
	rc := input.resource_changes[_]
	rc.type == "aws_db_instance"
	rc.change.after.storage_encrypted != true
	msg := sprintf("%s: storage is not encrypted", [rc.address])
}
```

Rego では、ルールの本体に並べた条件が**すべて成り立つときだけ**、`msg` が集合に加わります。最初のルールは「作成または変更されるセキュリティグループの、受信の規則のうち、`0.0.0.0/0` を許し、ポートの範囲が 22 か 3389 を含むもの」を探しています。`from_port` と `to_port` の範囲で判定しているので、`0` から `65535` まで開けるような書き方も捕まえます。

```bash
docker run --rm -v "$PWD":/project openpolicyagent/conftest test plan.json
```

```
WARN - plan.json - main - aws_db_instance.main: storage is not encrypted
FAIL - plan.json - main - aws_db_instance.main: publicly_accessible must be false
FAIL - plan.json - main - aws_security_group.web: port 22 is open to 0.0.0.0/0

3 tests, 0 passed, 1 warning, 2 failures, 0 exceptions
```

終了コードは 1 でした。CI で plan の後にこれを実行すれば、**`deny` に当たる変更は apply まで進めない**、という関所になります。`warn` は止めずに知らせるだけです。どの基準を止める側に置くかを、レビューできるコードとして残せるのが、手順書に書いた決まりとの違いです。

<Callout type="tip" title="同じ Rego を別の場所でも使う">
  Rego は Terraform 専用ではありません。Conftest は Kubernetes のマニフェストや Dockerfile なども読めますし、
  OPA を Kubernetes のアドミッションの段階に置けば、第 173 回で見た API サーバへの書き込みそのものを止められます。
  **同じ基準を、作る前（CI）と入る瞬間（アドミッション）の両方に置ける**のが、ポリシーをコードにする利点の一つです。
</Callout>

## IaC の検査では見えないもの

ここまでの検査は、すべて**コードと plan**を読んでいました。言い換えると、Terraform を通らずに起きた変更は見えません。

| ドリフトの生まれ方 | 例 |
| --- | --- |
| コンソールでの手作業 | 障害対応で、セキュリティグループに一時的に穴を開けて閉じ忘れる |
| CLI やスクリプト | 調査のために `aws` コマンドでバケットの設定を変える |
| 別の IaC やツール | 別のチームの Terraform や、運用ツールが同じリソースを書き換える |
| IaC の管理外のリソース | 最初から手で作られ、どのコードにも書かれていないリソース |
| クラウド側の変化 | 新しい機能が追加され、その既定値が基準に合わない。基準そのものが更新される |

Terraform 自身も、plan や apply のたびに state と実際のインフラを比べ、Terraform の外で行われた変更を検出します。`terraform plan -refresh-only` を使えば、state を書き換えずに差分だけを確かめられます（[HashiCorp Developer](https://developer.hashicorp.com/terraform/tutorials/state/resource-drift)）。plan の JSON にも、この差分が `resource_drift` として入ります。ただし、これは**Terraform が管理しているリソースについて、誰かが plan を実行したとき**にしか分かりません。管理外のリソースは比較の対象にすら入りません。

## CSPM: 今の設定を集めて基準と比べる

**CSPM** は、コードではなくクラウドそのものを見ます。仕組みは次のとおりです。

```
① 収集    クラウドの API（Describe 系、List 系）を呼び、リソースと設定を集める
           変更のイベントを受けて、変わったものだけ集め直すこともある
② 記録    集めた設定を、リソースごとの履歴として保存する
③ 評価    設定を基準のルールと比べ、違反しているリソースを指摘する
④ 通知    違反を通知し、必要なら自動で直す
```

AWS では、①と②を **AWS Config** が担います。AWS Config は、アカウントの中のリソースの設定と、それが過去にどう変わったかを記録し、Config のルールに反するリソースを「非準拠」として通知します。評価は、リソースが作成・変更・削除されるたびに続けて行われます（[AWS Config](https://docs.aws.amazon.com/config/latest/developerguide/WhatIsConfig.html)）。

③の基準を束ねて提供するのが **AWS Security Hub CSPM** です。たとえば第 186 回で触れた **CIS AWS Foundations Benchmark** を有効にすると、その要件に対応したコントロールで評価されます。v5.0.0 の一覧には、今回の Terraform で作ろうとした設定にそのまま当たるものが並んでいます（[AWS](https://docs.aws.amazon.com/securityhub/latest/userguide/cis-aws-foundations-benchmark.html)）。

| コントロール | 内容 |
| --- | --- |
| EC2.53 | セキュリティグループは、`0.0.0.0/0` からリモート管理用のポートへの受信を許可しない |
| RDS.2 | RDS の DB インスタンスは、PubliclyAccessible の設定で公開を禁止する |
| RDS.3 | RDS の DB インスタンスは、保存時の暗号化を有効にする |
| S3.1 / S3.8 | S3 のバケットは、パブリックアクセスのブロックを有効にする |

評価の時機は、コントロールごとに**変更をきっかけにするもの**と**定期的なもの**に分かれます。定期的なものは前回から 12 時間か 24 時間以内に実行され、変更をきっかけにするものは、AWS Config がリソースの状態の変化を記録したときに実行されます。それでも、取りこぼしを防ぐために少なくとも 24 時間に 1 回は確かめると説明されています（[AWS](https://docs.aws.amazon.com/securityhub/latest/userguide/securityhub-standards-schedule.html)）。

ほかのクラウドにも同じ役割の仕組みがあり（Google Cloud の Security Command Center、Microsoft Defender for Cloud など）、複数のクラウドをまとめて見る製品もあります。どれも、**API で今の設定を集め、基準と比べる**という骨組みは同じです。

### 手元で模擬する: コードと今の設定を突き合わせる

ここではクラウドのアカウントを使わないので、CSPM の動きを**模擬**します。以下の `current-sg.json` は、AWS の `DescribeSecurityGroups` の応答に似せて**手で書いた JSON** で、実際のクラウドから取得したものではありません。障害対応のときに、誰かがコンソールから PostgreSQL のポートを開けて、閉じ忘れたという想定です。

```json
{
  "SecurityGroups": [
    {
      "GroupName": "ll176-web",
      "GroupId": "sg-0123456789abcdef0",
      "IpPermissions": [
        {"IpProtocol": "tcp", "FromPort": 22, "ToPort": 22,
         "IpRanges": [{"CidrIp": "0.0.0.0/0", "Description": "ssh"}]},
        {"IpProtocol": "tcp", "FromPort": 5432, "ToPort": 5432,
         "IpRanges": [{"CidrIp": "0.0.0.0/0", "Description": "temporary debug"}]}
      ]
    }
  ]
}
```

これを、先ほどの plan の JSON（あるべき状態）と突き合わせる小さなスクリプトを書きました。規則を（グループ名、プロトコル、ポートの範囲、CIDR）の組にそろえて集合の差を取る部分がドリフトの検出、今の設定だけを見て危ないポートの公開を探す部分が CSPM の評価に当たります。

```python
import json, sys

plan = json.load(open(sys.argv[1]))
current = json.load(open(sys.argv[2]))

def desired_rules():
    for r in plan["planned_values"]["root_module"]["resources"]:
        if r["type"] == "aws_security_group":
            name = r["values"]["name"]
            for i in r["values"]["ingress"]:
                for cidr in i["cidr_blocks"]:
                    yield (name, i["protocol"], i["from_port"], i["to_port"], cidr)

def current_rules():
    for g in current["SecurityGroups"]:
        for p in g["IpPermissions"]:
            for ip in p["IpRanges"]:
                yield (g["GroupName"], p["IpProtocol"], p["FromPort"], p["ToPort"], ip["CidrIp"])

want, have = set(desired_rules()), set(current_rules())
for r in sorted(have - want):
    print("drift: exists but not in code ", r)
for r in sorted(want - have):
    print("drift: in code but missing    ", r)

SENSITIVE = {22, 3389, 3306, 5432, 6379}
for name, proto, lo, hi, cidr in sorted(have):
    hit = [p for p in SENSITIVE if lo <= p <= hi]
    if cidr == "0.0.0.0/0" and hit:
        print("posture: open to internet    ", name, hit)
```

```
drift: exists but not in code  ('ll176-web', 'tcp', 5432, 5432, '0.0.0.0/0')
posture: open to internet     ll176-web [22]
posture: open to internet     ll176-web [5432]
```

5432 番の規則は、コードに無いのに存在するドリフトとして見つかり、さらに基準にも反しています。先ほどの Conftest の結果と比べてください。**plan を読んだ Conftest は 22 番しか指摘していません**。plan には 5432 番がどこにも書かれていないからです。

本物の CSPM は、これを全リソース種別、全アカウント、全リージョンについて、変更のたびか定期的に行っています。そして、IaC で管理していないリソースも、API から見えさえすれば同じように評価されます。**コードを持っていなくても評価できる**ことが、IaC の検査との一番大きな違いです。

<Callout type="note" title="見つけた後、どちらに合わせるか">
  ドリフトを見つけたら、直し方は 2 通りあります。
  実際の環境をコードに合わせる（手で開けた穴を閉じる）か、コードを実際の環境に合わせる（その変更が正しいなら Terraform に書き足す）かです。
  第 173 回の Kubernetes のコントローラは、前者を自動で続ける仕組みでした。
  クラウドの設定でも、AWS Config には違反したリソースを自動で修復する機能があります。
  ただし自動で戻すと、障害対応のために意図して開けた穴まで閉じてしまうことがあるので、どの違反を自動で戻すかは慎重に選びます。
</Callout>

## 3 つをどこに置くか

この回と前回の道具を、開発の流れの上に並べると次のようになります。

| いつ | 道具 | 見ているもの | 見えないもの |
| --- | --- | --- | --- |
| コードの変更のたび | SAST、SCA（第 187 回） | アプリのコード、依存の一覧 | 実行時の設定、環境 |
| インフラの変更のたび（plan の後） | IaC の検査、policy as code | これから作るインフラの設定 | Terraform の外で起きた変更 |
| 検証環境へのデプロイ後 | DAST（baseline は毎回、アクティブスキャンは定期的に） | 外から見たアプリの振る舞い | 探索で届かない機能、業務上の意味 |
| 常に | CSPM | クラウドの今の設定 | アプリの中の欠陥 |

**どれか 1 つで全部を見ることはできません**。それぞれの「見えないもの」の列を、別の行の道具が埋める形になっています。そして、表の下の行ほど「動いている間の正しさ」を見ています。第 186 回で、作った時点の正しさは時間とともに崩れると書きました。だから、下の 2 行は一度通せば終わりではなく、続けて回すことに意味があります。

ここまでで、確かめる道具は一通り見ました。次の第 189 回では、どの道具にも共通して引っかかりやすい、具体的な攻撃面の一つ目を扱います。この回でも、plan の JSON にパスワードが平文で入り、どちらの IaC の検査の失敗の一覧にも現れませんでした。**秘密の情報が、どんな経路で漏れ、どう見つけ、漏れた後に何をするか**です。

## まとめ

- DAST は動いているアプリに外から要求を送って確かめる。ZAP の baseline は探索とパッシブスキャンだけで攻撃はせず、full scan はアクティブスキャンで攻撃に相当する要求を送る
- 手元の実験では、baseline は 5 件の要求でヘッダと Cookie の欠落を 9 種類見つけたが、XSS は見つけられなかった。full scan は約 560 件の要求で反射型 XSS を見つけ、誤検知も 1 件出した
- 認証の奥を検査するには、ログインの手順かトークンを ZAP に教える。検査用の環境と、権限ごとのユーザを用意する
- SAST はコードの値の流れを、DAST は設定と環境を含めた振る舞いを見る。両者は補い合う
- IaC の検査はインフラのコードを読み、作る前に設定の誤りを指摘する。Trivy は 14 件、Checkov は 24 件と、道具によって基準の一覧が違う
- plan の JSON は変数やモジュールを展開した完成した値を持つので、検査の対象に向いている。ただし `sensitive` の値も平文で入る
- policy as code は、自分たちの基準を Rego などで書き、Conftest で plan に当てて CI の関所にする
- CSPM はクラウドの API から今の設定を集めて基準と比べる。AWS では AWS Config が記録し、Security Hub CSPM が CIS などの基準で評価する
- 手作業などで生まれたドリフトは、コードや plan を読む検査には見えず、今の設定を見る CSPM にしか見えない
