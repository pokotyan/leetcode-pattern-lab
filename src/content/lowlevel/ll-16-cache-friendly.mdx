## 二重ループの順番を入れ替えるだけ

同じ計算をする 2 つのループです。

```c
// A: 行優先で走査
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        sum += a[i][j];

// B: 列優先で走査
for (int j = 0; j < N; j++)
    for (int i = 0; i < N; i++)
        sum += a[i][j];
```

**A のほうが、N が大きいと数倍から十数倍速くなります。**

理由はメモリ上の配置です。C の二次元配列は、行が連続して並びます。

```
a[0][0] a[0][1] a[0][2] ... a[1][0] a[1][1] ...
└────── 連続 ──────┘
```

A は連続したアドレスを順に読むので、1 回のキャッシュミスで 16 要素ぶんが載ります。B は毎回 N 要素ぶん飛ぶので、**1 要素読むたびにキャッシュミス**します。しかも読み込んだラインの残り 15 要素は使わずに捨てられます。

<Callout type="warn" title="言語によって「連続する向き」が違う">
  C、C++、Python の NumPy（既定）は**行優先**。
  Fortran、MATLAB、R、Julia は**列優先**です。
  同じ「内側のループを速い向きに」という原則でも、書く順番が逆になります。
  NumPy は `order='F'` で列優先にもできるため、ライブラリをまたぐときは確認が必要です。
</Callout>

## データ構造を横に倒す

オブジェクトの配列を扱うとき、2 つの持ち方があります。

```c
// AoS (Array of Structures): 構造体の配列
struct Particle { float x, y, z; float vx, vy, vz; int id; };
struct Particle particles[10000];

// SoA (Structure of Arrays): 配列の構造体
struct Particles {
    float x[10000], y[10000], z[10000];
    float vx[10000], vy[10000], vz[10000];
    int   id[10000];
};
```

**x 座標だけを全要素ぶん処理したい**とします。

AoS では、`particles[i].x` を読むたびに 28 バイトの構造体全体がキャッシュに載り、そのうち 4 バイトしか使いません。**キャッシュの 85% が無駄**です。

SoA では、`x[i]` が連続しているので、載ったライン 64 バイトすべてが使われます。さらに、連続していることで SIMD 命令も適用しやすくなります。

| | AoS | SoA |
| --- | --- | --- |
| 1 要素の全メンバを使う処理 | 有利 | 不利 |
| 特定のメンバだけを全要素で使う処理 | 不利 | **有利** |
| コードの読みやすさ | 有利 | 不利 |
| SIMD 適用 | 難しい | 容易 |

ゲームエンジンや数値計算で SoA が使われるのは、**後者の処理が支配的**だからです。すべてを SoA にする必要はなく、ホットな部分だけ倒す（ハイブリッド）のが実務的です。

## ポインタを辿る構造は遅い

連結リストと配列で、同じ要素数を全走査する場合を考えます。

配列は連続しているので、プリフェッチャも効き、ほぼ最速で流れます。

連結リストは、次のノードのアドレスが**そのノードを読むまで分かりません**。つまり、

```
ノードを読む → 200 サイクル待つ → 次のアドレスが分かる → また 200 サイクル待つ → ...
```

**待ち時間を重ねることができません**。これを**ポインタ追跡**と呼び、メモリ階層にとって最悪のパターンです。

同じことが、木構造、ハッシュテーブルのチェイン、グラフの隣接リストにも当てはまります。

<Callout type="tip" title="計算量が同じでも実測は大きく違う">
  「連結リストの挿入は O(1)、配列は O(n)」は正しい。
  しかし実測では、**数千要素程度までは配列のほうが速い**ことがよくあります。
  memmove は連続メモリを高速に動かせるのに対し、
  連結リストは挿入位置を探す時点でポインタ追跡が発生するからです。

  C++ の `std::vector` が `std::list` より広く使われているのは、この事情によります。
</Callout>

改善策としては、ノードをメモリプールから連続的に確保する、木をノードの配列として表現する（インデックスで参照する）、といった方法があります。

## false sharing

マルチスレッドで、最も見つけにくい性能問題です。

```c
struct Counter { long value; };
struct Counter counters[8];      // 8 スレッドがそれぞれ 1 個ずつ使う

// スレッド i は counters[i].value だけを更新する
```

論理的には、スレッド同士はまったく干渉しません。**別々の変数を触っているからです。**

ところが `long` は 8 バイトなので、`counters[0]` から `counters[7]` までの 64 バイトが**すべて同じキャッシュラインに収まります**。

キャッシュのやり取りはライン単位です。スレッド 0 が `counters[0]` に書くと、そのラインを持つ他の全コアのキャッシュが無効化されます。スレッド 1 が `counters[1]` を読もうとすると、無効化されているので取り直しになります。

**8 スレッドが 1 本のラインを奪い合い、コア間の通信が延々と発生します。** シングルスレッドより遅くなることすらあります。

論理的には共有していないのに、ハードウェアの都合で共有しているように振る舞う。だから **false sharing**（偽の共有）と呼ばれます。

対策は、**各要素をキャッシュラインサイズに広げる**ことです。

```c
struct Counter {
    long value;
    char padding[56];        // 64 バイトに揃える
};

// C++17 以降
struct alignas(std::hardware_destructive_interference_size) Counter { long value; };
```

メモリを 8 倍使いますが、それで数倍速くなるなら見合います。

<Callout type="warn" title="見つけ方">
  false sharing は、コードを読んでも分かりません。測るしかありません。

```bash
perf c2c record ./a.out      # Linux。キャッシュラインの競合を検出する専用モード
perf c2c report
```
  「スレッドを増やしたのにスケールしない」「むしろ遅くなる」ときの
  容疑者リストに必ず入れるべき現象です。
</Callout>

## 構造体を小さくする

キャッシュに載る要素数は、構造体のサイズに反比例します。したがって、

- 第 1 章で見たように、メンバを大きい順に並べてパディングを減らす
- 使わないメンバを削る
- `int64_t` で足りるところを `int32_t` にする、フラグを 1 バイトにまとめる
- ポインタの代わりに配列のインデックス（`uint32_t`）を持つ

64 バイトの構造体を 32 バイトにできれば、キャッシュに載る個数が倍になります。**アルゴリズムを変えずに、ミス率が半分になる**ということです。

## まずは測る

ここまでの話はすべて、**実測なしにやるべきではありません**。

```bash
# キャッシュミスの回数を見る
perf stat -e cache-references,cache-misses,L1-dcache-load-misses ./a.out

# どの行でミスしているか
perf record -e cache-misses ./a.out
perf report
```

macOS なら Instruments、Windows なら VTune が同等のことをします。

キャッシュミス率が低いなら、ここで挙げた最適化をしても意味がありません。**ボトルネックがどこかを確かめてから手を入れる**、という順序は崩さないことです。

## まとめ

- 走査の向きを内側の連続方向に合わせる。言語によって連続の向きが違う
- 特定のメンバだけを大量に処理するなら SoA を検討する
- ポインタ追跡は待ち時間を重ねられないので極端に遅い
- false sharing は論理的に無関係な変数が同じラインに載ることで起きる。パディングで分離する
- 構造体を小さくすれば、それだけでミス率が下がる
- すべて実測してから手を入れる
