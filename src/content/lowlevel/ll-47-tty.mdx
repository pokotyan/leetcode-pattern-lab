## 端末は、かつて機械だった

TTY という名前は **teletypewriter**（テレタイプ端末）から来ています。キーボードと紙に印字する装置を備えた機械で、シリアル回線でコンピュータにつながっていました。1 台のコンピュータに何台もの端末がつながり、それぞれに人が座っていました。

カーネルは、この回線の先にいる人のために、次の仕事を引き受けていました。

- 打った文字を画面（紙）に送り返す（エコー）
- 打ち間違いを消す（Backspace）
- 1 行打ち終わるまで溜めておき、Enter でまとめてプログラムに渡す
- 特定の文字（Ctrl+C など）を、プログラムへの合図に変える

機械としての端末はなくなりましたが、**この仕事を担うカーネルの部品は今も残っていて、毎日使われています**。

## 疑似端末: 両端がソフトウェアの端末

いま使っているのは、ウィンドウの中で動く **端末エミュレータ**（Terminal.app、iTerm2、GNOME Terminal など）です。本物の回線はないので、カーネルは **疑似端末**（pty）という、両端がソフトウェアになった回線を用意します。

```
 キーボード                                             シェル（bash）
    │                                                    ▲ │
    ▼                                           fd 0,1,2 │ ▼
 端末エミュレータ ──── master ──[ line discipline ]── slave（/dev/pts/0）
    ▲                                    │
    │                                    └ エコー、行の編集、Ctrl+C の変換
 画面に描く
```

pty は **master** と **slave** の 2 つの端点を持つ対です。端末エミュレータが master を持ち、シェルは slave を fd 0、1、2 として持ちます。

```bash
$ tty
/dev/pts/0
$ ls -l /proc/self/fd/0
lrwx------ 1 root root 64 ... /proc/self/fd/0 -> /dev/pts/0
```

第 42 回で見た「すべてはファイル」がここにも現れています。シェルにとって、端末はただの fd です。

pty を作るのは端末エミュレータだけではありません。`ssh` でログインすると、サーバ側の sshd が pty を作り、master の側をネットワークにつなぎます。`tmux` や `screen` も、`docker run -t` も、中で pty を作っています。

## line discipline: カーネルの中の行エディタ

master と slave の間にいるのが **line discipline** です。既定の **カノニカルモード** では、これが小さな行エディタとして働きます。

- 打った文字を master 側に送り返す。**画面に文字が出るのは、カーネルがエコーしているから**
- Backspace で 1 文字、Ctrl+U で 1 行、Ctrl+W で 1 語を消す
- Enter が来るまで溜めておき、**1 行まとめて**プログラムの `read` に返す

つまり、`cat` を起動して文字を打つとき、Backspace を処理しているのは `cat` ではなくカーネルです。`cat` のコードには行編集の機能は 1 行もありません。

設定は `stty` で見られます。

```bash
$ stty -a
speed 38400 baud; rows 0; columns 0; line = 0;
intr = ^C; quit = ^\; erase = ^?; kill = ^U; eof = ^D; eol = <undef>;
eol2 = <undef>; swtch = <undef>; start = ^Q; stop = ^S; susp = ^Z; rprnt = ^R;
werase = ^W; lnext = ^V; discard = ^O; min = 1; time = 0;
```

`speed 38400 baud` は、存在しないシリアル回線の速度です。機械の時代の設定項目が、そのまま残っています。

`intr = ^C` などが、line discipline が特別扱いする文字の一覧です。

| 文字 | 設定名 | line discipline がすること |
| --- | --- | --- |
| Ctrl+C | `intr` | フォアグラウンドのプロセスグループに **SIGINT** を送る |
| Ctrl+\\ | `quit` | **SIGQUIT** を送る（既定の動作はコアダンプして終了） |
| Ctrl+Z | `susp` | **SIGTSTP** を送る（一時停止） |
| Ctrl+D | `eof` | 溜めている行をそのまま `read` に返す |
| Ctrl+S / Ctrl+Q | `stop` / `start` | 出力を止める / 再開する |

第 46 回で「端末ドライバが Ctrl+C を検出して SIGINT を送る」と書いたのは、この表の 1 行目のことです。

<Callout type="tip" title="Ctrl+D はシグナルではない">
  Ctrl+D は、プログラムに何かを「送る」わけではありません。
  **溜まっている分をそのまま `read` に返させる**だけです。

  行の先頭で押すと、溜まっているのは 0 バイトです。
  `read` が 0 を返すので、プログラムは「ファイルの終わり（EOF）に達した」と判断して終了します。
  行の途中で押すと、それまで打った文字が改行なしで返るだけで、終了しません。
  **EOF は、`read` が 0 を返すことそのもの**です。

  ちなみに、うっかり Ctrl+S を押して端末が固まったように見えたら、Ctrl+Q で戻ります。
  出力を止める機能が、機械の時代から残っているためです。
</Callout>

### raw モード

`vim` や `less`、`top` は、キーを 1 つ押すたびに反応します。Enter を待っていません。これらのプログラムは起動時に line discipline を **raw モード**（非カノニカル）に切り替えています。

raw モードでは、エコーも行編集も特殊文字の変換も止まり、打ったバイトがそのまま 1 つずつ `read` に届きます。`vim` の中で Ctrl+C を押してもプログラムが終了しないのは、SIGINT に変換されず、ただのバイト `0x03` として `vim` に届いているからです。

プログラムが異常終了して raw モードのまま戻ってこないと、打った文字が画面に出ない、改行がおかしい、といった壊れた状態が残ります。`reset` や `stty sane` で既定の設定に戻せます。

bash や zsh の行編集（矢印キーで履歴を辿るなど）も、実は raw に近いモードでシェル自身がやっています。カーネルの行エディタは Backspace 程度しかできないので、高機能な編集はプログラムが自前で持つことになります。

## 画面の色やカーソルは、ただのバイト

プログラムが文字に色を付けたり、カーソルを動かしたりするときも、特別な仕組みは使いません。**エスケープシーケンス**という決まったバイト列を、普通に書き込むだけです。

```bash
printf '\033[31m赤い文字\033[0m\n'     # ESC [ 31 m で赤、ESC [ 0 m で元に戻す
printf '\033[2J\033[H'                  # 画面を消し、カーソルを左上へ
```

これを解釈して画面を描き分けているのは、master の向こうにいる端末エミュレータです。カーネルは中身を見ずに素通りさせます。

端末の大きさだけは、カーネルが管理しています。端末エミュレータはウィンドウの大きさが変わると `ioctl` でカーネルに伝え、カーネルはフォアグラウンドのプロセスに **SIGWINCH** を送ります。`vim` がウィンドウの大きさに合わせて描き直せるのはこのためです。上の `stty -a` が `rows 0; columns 0` になっていたのは、大きさを伝える端末エミュレータがいないコンテナの中で実行したからです。

## セッション、プロセスグループ、ジョブ制御

Ctrl+C の SIGINT は「フォアグラウンドのプロセスグループ」に届きます。ここで出てくる単位を整理します。

```
 セッション（ログイン 1 回ぶん。端末 1 つと結びつく）
 ├─ プロセスグループ: bash                  ← セッションリーダー
 ├─ プロセスグループ: sleep 100 | cat &      ← バックグラウンドのジョブ
 └─ プロセスグループ: vim                    ← フォアグラウンドのジョブ
                                               （Ctrl+C はここだけに届く）
```

- **セッション**: 1 つの端末（**制御端末**）と結びついた、プロセスグループの集まり。ログインしたシェルが `setsid` で作る
- **プロセスグループ**: シェルが 1 つのコマンドライン（パイプラインを含む）ごとに作る。**ジョブ**の実体
- **フォアグラウンドのプロセスグループ**: 端末に 1 つだけ。シェルが `tcsetpgrp` でカーネルに登録する

```bash
$ sleep 100 | cat &
$ ps -o pid,pgid,sid,tpgid,tty,comm
  PID  PGID   SID TPGID TT       COMMAND
  100   100   100   130 pts/0    bash
  120   120   100   130 pts/0    sleep
  121   120   100   130 pts/0    cat          ← sleep と同じグループ
  130   130   100   130 pts/0    ps           ← いまのフォアグラウンド
```

`TPGID` が、その端末のフォアグラウンドのプロセスグループです。

これで **ジョブ制御** の動きが説明できます。

1. Ctrl+Z を押すと、line discipline がフォアグラウンドのグループに SIGTSTP を送り、ジョブが止まる
2. シェルは子の停止を `waitpid` で知り、自分をフォアグラウンドに戻してプロンプトを出す
3. `bg` は、止まったグループに SIGCONT を送る。フォアグラウンドはシェルのまま
4. `fg` は、`tcsetpgrp` でそのグループをフォアグラウンドにしてから SIGCONT を送る

バックグラウンドのジョブが端末から読もうとすると、カーネルは **SIGTTIN** を送ってそのジョブを止めます。端末の入力を奪い合わないように、読めるのはフォアグラウンドだけ、という規則です。

## SIGHUP: 回線が切れた

`HUP` は **hang up**、電話を切ることです。モデムの回線が切れたとき、その端末で動いていたプログラムに知らせるためのシグナルでした。

いまでも、端末のウィンドウを閉じたり、ssh の接続が切れたりすると、pty の master が閉じられます。するとカーネルは、その端末を制御端末とするセッションのリーダー（シェル）に SIGHUP を送り、シェルは自分のジョブに SIGHUP を送ります。既定の動作は終了なので、**ssh が切れると、そこで動かしていたプログラムも止まります**。

| 方法 | 何をしているか |
| --- | --- |
| `nohup cmd &` | SIGHUP を無視する設定にしてから実行する |
| `disown` | シェルのジョブ一覧から外し、シェルが SIGHUP を送らないようにする |
| `setsid cmd` | 新しいセッションを作り、制御端末を持たずに実行する |
| `tmux` / `screen` | pty の master を、切れない別のプロセス（tmux のサーバ）が持つ |

`tmux` で作業していると ssh が切れても生き残るのは、master を持っているのが ssh ではなく tmux のサーバだからです。再接続すると、新しい端末から同じ master にもう一度つなぎ直します。

デーモンが SIGHUP を「設定ファイルを読み直せ」という合図に使う慣習は、デーモンには制御端末がなく、本来の意味で SIGHUP が届くことがないので、空いている番号を転用したものです。

## 端末かどうかで、出力が変わる

プログラムは、出力先が端末かどうかを `isatty` で調べられます。調べ方は、その fd に端末用の `ioctl` を発行して、成功するかどうかを見るだけです。

多くのプログラムが、この結果で振る舞いを変えます。

| プログラム | 端末のとき | パイプやファイルのとき |
| --- | --- | --- |
| `ls` | 横に並べ、色を付ける | 1 行に 1 つ、色なし |
| `grep --color=auto` | 一致箇所に色を付ける | 色を付けない |
| `git log` | ページャ（`less`）を起動する | そのまま出力する |
| C の `printf` | 改行ごとに書き出す | バッファが溜まるまで書き出さない |

最後の行が、実務でいちばん困る違いです。

C の標準入出力ライブラリは、`printf` のたびに `write` を呼ぶと遅いので、ユーザ空間のバッファに溜めてからまとめて `write` します。第 41 回で見たとおり、システムコールには固定のコストがあるからです。問題は、溜める量が出力先によって違うことです。

- 端末につながっているときは **行バッファ**: 改行が来たら書き出す
- それ以外（パイプ、ファイル）では **完全バッファ**: 数 KB 溜まるまで書き出さない

この規則は glibc のマニュアルに明記されています（[GNU C Library: Buffering Concepts](https://www.gnu.org/software/libc/manual/html_node/Buffering-Concepts.html)）。

```bash
./progress                 # 1 秒ごとに 1 行出る
./progress | tee log.txt   # しばらく何も出ず、後でまとめて出る
```

プログラムは同じで、出力先が端末からパイプに変わっただけです。Python も同じ考え方で標準出力をバッファします。

<Callout type="warn" title="コンテナのログが出てこない">
  `docker run` を `-t` なしで実行すると、コンテナの標準出力は端末ではなくパイプになります。
  そのため、手元では 1 行ずつ出ていたログが、コンテナでは**しばらく何も出ず、まとめて出る**ことがあります。
  異常終了すると、バッファに残っていた分は**出ないまま消えます**。

  対策は、出力先に関係なく書き出させることです。

  - C: `setvbuf(stdout, NULL, _IOLBF, 0)` で行バッファに固定する
  - Python: 環境変数 `PYTHONUNBUFFERED=1`、または `python -u`
  - 外から変える: `stdbuf -oL ./progress`（glibc の標準入出力を使うプログラムに限る）

  `docker run -t` は pty を用意して、コンテナの標準出力を端末にします。
  `-i` は標準入力を開いたままにするオプションで、これとは別物です。
</Callout>

## まとめ

- TTY は機械の端末の名残。エコー、行編集、特殊文字の変換はカーネルの line discipline がやっている
- 端末エミュレータ、ssh、tmux、`docker run -t` は pty を作る。シェルから見れば、端末はただの fd
- カノニカルモードでは 1 行ずつ `read` に返る。`vim` などは raw モードに切り替えて 1 バイトずつ受け取る
- Ctrl+C は SIGINT、Ctrl+Z は SIGTSTP、Ctrl+D はシグナルではなく「溜まった分を返す」。行頭なら 0 バイトになり、EOF として扱われる
- 色やカーソル移動はエスケープシーケンスというただのバイト列。解釈するのは端末エミュレータ
- シェルはコマンドラインごとにプロセスグループを作り、フォアグラウンドを 1 つ決める。ジョブ制御はその切り替え
- 端末が切れると SIGHUP。nohup、setsid、tmux はそれぞれ別の方法でこれを避ける
- 出力先が端末かどうかで、標準出力のバッファリングが変わる。パイプにつなぐとログが遅れる理由
