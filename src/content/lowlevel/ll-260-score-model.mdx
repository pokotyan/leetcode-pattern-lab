## この章で見るもの

第 32 章では、作るものが動いている法律の層を見ました。第 33 章では、もう一度コンピュータの側へ戻ります。テーマは**遅い Web アプリケーションを、決められた時間の中で速くすること**です。

第 30 章では、本番を観測する道具を見ました。第 236 回で「まず測る。測ってから直す」と書き、第 237 回でパーセンタイルの集め方、第 238 回で CPU 時間の内訳、第 241 回でプロファイルの読み方を扱いました。けれど、道具の使い方を知っていても、実際の Web アプリケーションを前にしたときに次の問いへ答えるのは別の技能です。

- どこから測り始めるのか。何を最初に見るのか
- 見つけたボトルネックのうち、どれから直すのか
- 直したのに速くならないのはなぜか。速くなったのに、なぜ利用者の役に立っていないのか
- 何をどこまで変えてよいのか。変えてはいけないものは何か

この章では、これらを ISUCON という競技の過去の問題と、上位チームが公開した記録を手がかりに見ていきます。

### ISUCON とは

ISUCON は、公式サイトの説明では「お題となるWebサービスを決められたレギュレーションの中で限界まで高速化を図るチューニングバトル」です（[ISUCON 公式 Blog](https://isucon.net/)）。2011 年に始まり（[ISUCON2026 イベントレポート](https://isucon.net/archives/isucon2026-event-report.html)）、2026 年 10 月 31 日に開催された ISUCON2026 には 856 チーム、1,596 名が参加しました（[ISUCON2026 まとめ](https://isucon.net/archives/60124520.html)）。

競技の形は毎回ほぼ同じです。ISUCON2026 のレギュレーションから要点を拾うと、次のとおりです（[ISUCON2026 レギュレーション](https://isucon.net/archives/59966826.html)）。

- チームは 1〜3 名。競技時間は 10:00〜18:00 の 8 時間
- 主催者が Web アプリケーション（問題）と、Go、Perl、PHP、Python、Ruby、Rust、Node.js の初期実装を用意する
- URI、レスポンスの構造、JavaScript・CSS・画像などは変えてはいけない。それ以外は「各サーバにおけるソフトウェアの入れ替え、設定の変更、アプリケーションコードの変更および入れ替えなどは一切禁止しない」
- 点数は、主催者の用意した負荷をかける道具（**ベンチマーカー**）が付ける。「採点は採点条件をクリアしたチームの間における、性能値（スコア）の高さによって行う」
- 競技の後で主催者が再起動を含めて計測をやり直し、動かない、または点数が再現しない場合は失格

つまり、**決められた利用者（ベンチマーカー）が決められた時間だけ使ったときに、どれだけの価値を生み出せたか**を競います。インデックスを張っても、キャッシュを足しても、データベースを替えても、言語ごと書き直してもかまいません。

### なぜ題材にするのか

性能改善の知識を学ぶ題材として、ISUCON には本番のサービスにはない性質があります。

**問題とベンチマーカーが公開されている。** ISUCON9 予選の講評は、問題のリポジトリについて「アプリケーション、ベンチマーカーを起動する手順もありますので、手元で挑戦することもできるかと思います」と書いています（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。本番の障害は二度と同じ形では起きませんが、過去の問題は何度でも同じ条件で解き直せます。

**出題者が「どこに何を仕込んだか」を説明している。** 毎回の講評には、初期状態のボトルネック、想定した直し方、直したときの点数の目安が書かれています。ISUCON12 予選の講評は、問題の作り方を次のように説明しています（[ISUCON12 予選問題の解説と講評](https://isucon.net/archives/56850281.html)）。

> ISUCONの問題には、解消するべきボトルネックとなる要素が複数(意図的に作り込まれて)存在しています。基本的にはその時点で最大のボトルネックになっている要素を解消することでスコアが上がっていき、多くのボトルネックを解消するほどスコアが向上します。

**参加者が記録を公開している。** 上位のチームは、何時に何をして点数がいくつになったかを書き残します。ある変更で点数が下がった、ある設定で FAIL した、という失敗も含めてです。性能改善の判断が、時刻と数字つきで残っている資料はほかにあまりありません。

**同じ型が繰り返し現れる。** インデックスの不足、N+1 クエリ、外部サービスの待ち、書き込みの集中、キャッシュできるのにしていない計算。どの回にも現れる型は、本番の Web アプリケーションで遅さの原因になるものとほぼ同じです。

一方で、競技と本番の違いも意識しておく必要があります。ISUCON11 本選で優勝した fujiwara 氏は、どの手を打っても点数が明確に上がらない時間帯について書いたあとで、こう続けています（[ISUCON11で優勝しました](https://sfujiwara.hatenablog.com/entry/isucon11-final)）。

> リアルでのパフォーマンスチューニングでは、明確に数字が上がらない施策を無闇に入れるのは避けるべきですよね。

競技では 8 時間後に捨てるコードでも、本番では何年も保守します。ISUCON12 本選で優勝した NaruseJun の sekai 氏は、競技の性格を「ISUCONで出てくる課題は今っぽくない、昔ながらのパフォーマンスチューニングが問題の肝となっています」と表現しています（[gihyo.jp のインタビュー](https://gihyo.jp/article/2022/10/isucon12-champinterview-narusejun)）。この章では、競技に特有の判断と、本番でもそのまま使える判断を分けながら進めます。

## 速さは目的ではない

この回の問いに戻ります。**何を速くすれば点になるのか。**

「応答時間を短くすればよい」と答えたくなりますが、それは半分しか正しくありません。速くするのは手段で、目的は別にあります。目的が何かによって、速くするべき場所も、速くしてはいけない場所も変わります。

最適化の言葉で言えば、最初に決めるのは**目的関数**です。何を最大（または最小）にするのか。そして**制約**です。何を守らなければならないのか。ISUCON の採点の決まりは、この 2 つを明文化したものになっています。本番の性能改善でこれに当たるのが、ビジネスの指標と SLO（サービスレベル目標）ですが、それは後で見ます。

## 採点の決まり方

ISUCON の採点は、どの回でもおおむね次の 4 つの部品でできています。

| 部品 | 中身 |
| --- | --- |
| 加点 | 何ができたら点になるか。回ごとに違う |
| 減点 | 誤ったレスポンスやタイムアウトで、点がどれだけ引かれるか |
| FAIL | どんな誤りで、その負荷走行が 0 点になるか |
| 追試 | 競技の後で、何を確かめられるか |

### 加点：要求の数から、利用者が生んだ価値へ

古い回の ISUCON では、点数は捌いたリクエストの数から計算されていました。それが変わったのが ISUCON9 予選です。講評は次のように書いています（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。

> 今回のISUCONでは、例年と違い、スコアはリクエスト数から計算されるものではなく、取引が完了した椅子の価格の合計をベースに次の計算式でスコアとしています。

式は「取引が完了した商品（椅子）の価格の合計（ｲｽｺｲﾝ） - 減点 = スコア（ｲｽｺｲﾝ）」です。問題は椅子のフリーマーケット「ISUCARI」で、ベンチマーカーは出品し、一覧を回遊し、購入します。講評はその狙いを「アプリケーションが速くなり、いつでも快適に使えるだけではなく、ユーザが求めているものを調べ、ビジネスをより成功させるというのもISUCONの中に含められないかと考えました」と説明しています。

実際、この問題では初期データで利用者が買うカテゴリを偏らせてあり、新着一覧をその利用者が買うカテゴリに合わせて返すと「数%ですが、スコアがあがるようになってます」とも書かれています。応答時間とは関係のない、**利用者の求めるものを返す**という改善にも点が付くわけです。

その後の回でも、点数は利用者が生んだ価値で定義されています。

| 回 | 題材 | 点数の定義（要約） |
| --- | --- | --- |
| ISUCON9 予選 | 椅子のフリーマーケット | 取引が完了した商品の価格の合計 − 減点 |
| ISUCON11 予選 | 椅子の状態を記録する IoT サービス | 初期点 1,000 点 ＋ 利用者がコンディションとグラフを確認したことによる加点 − 減点 |
| ISUCON13 | ライブ配信サービス | Tips（投げ銭）の投稿の合計 |
| ISUCON14 | 椅子の配車サービス | 移動距離とライド完了数から計算 |

ISUCON14 の当日マニュアルは、点数を次の 3 つの合計と定めています（[ISUCON14 当日マニュアル](https://github.com/isucon/isucon14/blob/main/docs/manual.md)）。

```text
椅子がライドとマッチした位置から乗車位置までの移動距離の合計 * 0.1
椅子の乗車位置から目的地までの移動距離の合計
ライド完了数 * 5
```

講評は、この式から読み取れることを「空車のときと人を乗せているときではスコアに10倍の差があるので、椅子が移動する際にはできるだけ人を乗せている状態、つまり椅子と乗車位置が近いライドに割り当てることも必要になっていました」と解説しています（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。どの椅子をどの利用者に割り当てるかという、応答時間ではない部分にも点数が依存しているのです。

### 点にならないリクエスト

点数が利用者の生んだ価値で決まると、**すべてのリクエストが点に結び付くわけではない**ことになります。ISUCON13 の講評は次のように書いています（[ISUCON13 問題の解説と講評](https://isucon.net/archives/58001272.html)）。

> ISUCON13のスコアは、リクエストを処理した回数ではなく、Tipsの投稿の合計です。ベンチマーカーはいくつものシナリオを同時に走らせていますが、そのうちTipsの投稿に辿り着くシナリオは限られており、HTTPリクエストの最適化がスコアに結びつきにくい場面もありました。

ISUCON11 予選も同じ構造です。ベンチマーカーは、椅子としてコンディションを送り続ける役、利用者として椅子の状態を確認する役、トップページのトレンドを見続ける閲覧者の役の 3 つを演じていました。講評は「直接の加点は 2 のユーザの行動で行っており、いずれかが詰まると次の行動に移るまでに時間がかかるため、スコアが伸び悩む仕組みになっていました」と書いています（[ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)）。椅子からの送信は量が最も多いのに、それ自体は点になりません。

点にならないリクエストを速くすることに意味がないわけではありません。点になるリクエストと**同じ資源を奪い合っている**なら、それを軽くすることは点になるリクエストを速くすることと同じです。どの資源を奪い合っているかは、後の実測で確かめます。

### 負荷の量をアプリケーションが選ぶ

もう一つ、点数の定義と切り離せない仕掛けがあります。**どれだけの負荷を受けるかを、アプリケーションの側が選べる**回があることです。

ISUCON9 予選では、初期化のエンドポイント `/initialize` の応答に `campaign` という値を返すことで、キャンペーン機能を有効にできました。講評は「数字は0から4までとなり、数字が大きくなると同時にアクセスするユーザも増えていきます」と説明し、高い点数を出すには「キャンペーン機能を最大まで上げて同時アクセス数を増やし」と書いています（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。

ISUCON11 予選では、椅子から届くコンディションをどの割合で捨てるかを `dropProbability` という値で決められました。講評によれば、初期状態では捨てる割合を下げてもアプリケーションが負荷に耐えられず点数が伸びず、ほかの改善で CPU に余裕ができてから下げると、グラフの確認による加点を大きくできました（[ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)）。

どちらも、**受け入れる仕事の量を増やすほど点の上限は上がるが、捌ききれなければ点が下がる**という形をしています。速くすることと、速くなったぶんだけ多くの仕事を引き受けることは、別の判断です。この調整は第 277 回で扱います。

### 減点と FAIL

点を増やす方向と同じくらい重要なのが、点を失う方向です。ISUCON11 予選の当日マニュアルは、減点と即時失敗（fail）を次のように定めていました（[ISUCON11 予選 当日マニュアル](https://github.com/isucon/isucon11-qualify/blob/main/docs/manual.md)）。

| 誤り | 扱い |
| --- | --- |
| 初期化処理、アプリケーション互換性チェックの失敗 | 1 回以上で fail |
| HTTP ステータスコードやレスポンス内容などの誤り | 1 回あたり減点 1 点、100 回の失敗時点で fail |
| リクエストのタイムアウト | 10 回あたり減点 1 点、fail は発生しない |

マニュアルには「fail となった場合スコアは 0 点となります」とあります。タイムアウトは 1 秒で、10 回で 1 点しか引かれません。一方で、内容の誤りは 100 回で 0 点になります。**遅いことより、間違えることの方がはるかに重く扱われている**のです。

ISUCON14 ではさらに厳しく、負荷走行を打ち切って FAIL にする条件として、「負荷走行の実行中にクリティカルエラーが発生する」「負荷走行の実行中に200件以上のワーニングが発生する」などが並んでいます（[ISUCON14 当日マニュアル](https://github.com/isucon/isucon14/blob/main/docs/manual.md)）。クリティカルエラーには「ライドが長時間マッチングされませんでした」「決済サーバーに誤った支払いがリクエストされました」などがあり、1 回でも起きれば 0 点です。

ISUCON9 予選の外部決済サービスも、同じ商品を 2 回購入すると「クリティカルなエラー扱いになり、一度発生しただけでベンチマークが失敗するようになっていました」（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。購入処理を速くしようとしてロックを外し、二重に売ってしまえば、その時点で終わりです。

### 整合性の検査

ベンチマーカーは、負荷をかけるだけでなく、アプリケーションが正しく動いているかも調べます。ISUCON14 の負荷走行は、初期化、アプリケーション整合性チェック、60 秒の負荷テスト、最終チェックの順で進み、マニュアルは「初期化処理もしくはアプリケーション整合性チェックに失敗すると、負荷走行は即時失敗（FAIL）になります」と定めています。負荷テストの終了時点で進行中だった決済は 5 秒以内に終わる必要があり、終わらなければ「ベンチマーカーの期待する決済金額と一致せずFAILになります」。

ISUCON12 予選の講評には、データの移行中に別の参照が割り込むと「中途半端なデータが返ります。アプリケーション的には不正な状態となるため、ベンチマーカーがfailします」という説明があります（[ISUCON12 予選問題の解説と講評](https://isucon.net/archives/56850281.html)）。

ここから分かるのは、ISUCON の採点が「速さ」と「正しさ」を同じ天秤には載せていないことです。正しさは**制約**で、満たさなければ速さに関係なく 0 点になります。

### 最終スコアと追試

最後の部品が、競技の後の確認です。どの負荷走行の点数が最終スコアになるかは回によって違います。ISUCON14 では「競技中に最後に行った負荷走行の結果を、最終スコアとします」と定められていました。ISUCON11 予選では「競技終了後、主催者は 全サーバーの再起動後に負荷走行を実施 します。その際のスコアを最終スコアとします」でした。

どちらの場合も、その後に追試があります。ISUCON2026 のレギュレーションは次のように書いています（[ISUCON2026 レギュレーション](https://isucon.net/archives/59966826.html)）。

> 追試は再起動後にベンチマーカーを動作させて行い、正常にベンチマークが完了しない、あるいは競技時間中に登録されたスコアに近い結果が再現されない場合、また、ベンチマークの結果に捏造があると判断される場合には、判断基準の公開と共にそのチームは失格とする。

レギュレーションには「サーバ再起動後にすべてのアプリケーションコードが正常動作する状態を維持すること」「ベンチマーク実行時にアプリケーションに書き込まれたデータは再起動後にも取得できること」という留意事項もあります。メモリにだけ持ったデータが再起動で消える、手で起動したプロセスが再起動後に立ち上がらない、といった作りは、どれほど速くても失格です。この扱いは第 278 回で詳しく見ます。

### 点にならない要素：ブラフ

問題の中には、手を付けても点数に響かない要素もあります。作問者が意図して置いたもの、意図せずそうなったものの両方があり、参加者の間では**ブラフ**と呼ばれます。

ISUCON14 には、決済サービスの `Idempotency-Key` ヘッダという要素がありました。講評によれば、作問者はこれを改善の対象にするつもりで入れたものの「うまくボトルネックとして絡めることができませんでした」。そしてドキュメントに記載が残ったため、「かなりのブラフになってしまったのですがこれに囚われていた人はあまりいなかったようで安心しています」と書かれています（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。

ISUCON11 予選の講評には、「点数が上がるまでチューニングポイントとなり得ない箇所」という見出しまであります。画像を持つ `isu` テーブルは、利用者が増えない限り 100 件ほどしかなく、負荷になっていませんでした。そして出題の意図として「典型的なボトルネックだからと むやみに改善を行ってもスコアが伸びない問題設計にしていました」と書いています（[ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)）。

ブラフに時間を取られる原因は、ほとんどの場合「見るからに遅そう」「典型的に悪い」という推測です。第 236 回の言葉で言えば、推測しないで測る、です。

## 実測：要求の数と点数は別のもの

ここまでの話を、手元で小さく再現します。題材は次のような店です。

- 利用者には 2 種類いる。**買う人**（16 人）は、商品一覧を見て（`GET /items`）、1 つ買う（`POST /buy`）を繰り返す。**眺める人**（16 人）は、人気一覧（`GET /popular`）を見続けるだけで買わない
- 点数は、購入が成立した金額の合計（1 件 100）からエラーの件数を引いたもの。エラーが 100 件に達したら 0 点（FAIL）
- 負荷走行の最後に、ベンチマーカーが数えた購入件数とアプリケーションが記録した販売件数を突き合わせ、一致しなければ FAIL
- タイムアウトは 1 秒

アプリケーション側は、3 つのエンドポイントがどれもデータベースに 1 回問い合わせます。データベースは同時に 4 件までしか処理できないものとし、問い合わせの時間は `time.Sleep` で表します。

```go
var db = make(chan struct{}, 4) // 同時に処理できる問い合わせは 4 件まで

func query(ms int) {
	db <- struct{}{}                                // 空きを待つ
	time.Sleep(time.Duration(ms) * time.Millisecond) // 問い合わせにかかる時間
	<-db
}

// GET /items: query(40)   商品一覧
// GET /popular: query(60) 人気一覧（点にならない）
// POST /buy: query(20)    購入（点になる）
```

ベンチマーカーは Go で書き、32 人がそれぞれ応答を受け取ってから次の要求を送ります（この送り方の意味は第 261 回で扱います）。

```go
for time.Now().Before(deadline) { // 買う人
	if !do("GET", "/items") {
		continue
	}
	if do("POST", "/buy") {
		purchases.Add(1)
		revenue.Add(100)
	}
}
```

環境は Apple M1 Pro / macOS 26.2、Go 1.24.6 です。負荷走行は 1 回 15 秒です。計測した時間帯は、同じマシンでほかの重い処理が並行して走っていて、ロードアベレージが 60〜140 ありました。`time.Sleep` の実際の待ち時間が指定より 1.5〜3 ms ほど長くなることを別に確かめています。そのため、同じ条件を 3 回ずつ走らせて比べます。

### まず、どこに時間がかかっているか

初期状態（A）で 1 回走らせたときの、エンドポイントごとの件数と合計時間です。アプリケーションの中で、リクエストを受けてから返すまでを測っています。

```text
POST /buy    count=   351 sum= 120.24s avg=342.56ms
GET /items   count=   351 sum= 125.49s avg=357.51ms
GET /popular count=   651 sum= 243.33s avg=373.78ms
sold=351
requests=1353 (90 req/s) errors=0 purchases=351 revenue=35100 score=35100 PASS
```

問い合わせ自体は 20〜60 ms なのに、平均の応答時間はどれも 340〜370 ms です。32 人に対してデータベースの空きが 4 つしかないので、ほとんどの時間は空きを待っています。合計時間は `GET /popular` が最も大きく、点にならない要求が全体の時間の半分を占めていました。

### 4 つの手を比べる

次の 5 通りを、それぞれ 3 回走らせました。

| | 変更 | 1 秒あたりの要求数 | 点数 |
| --- | --- | --- | --- |
| A | 初期状態 | 88〜91 | 33,800〜35,100（PASS ×3） |
| F | 購入の問い合わせを 20 → 4 ms | 93〜97 | 36,600〜38,300（PASS ×3） |
| C | 商品一覧の問い合わせを 40 → 10 ms | 96〜109 | 37,800〜43,200（PASS ×3） |
| G | 人気一覧の問い合わせを 60 → 30 ms | 114〜125 | 46,300〜47,100（PASS ×2）、FAIL ×1 |
| B | 人気一覧をメモリから返す（データベースに行かない） | 5,539〜19,018 | 87,600〜96,000（PASS ×3） |
| D | 人気一覧に 503 を返して断る | 5,580〜10,617 | 0（FAIL ×3） |

いくつかのことが読み取れます。

**点になる処理そのものを速くしても、ほとんど点は増えない。** F は購入の問い合わせを 5 分の 1 にしましたが、点数は数 % しか増えていません。

**点にならない処理を軽くした方が、点が増える。** G で人気一覧の問い合わせを半分にすると、点数は約 1.3 倍になりました。B でデータベースから外すと約 2.7 倍です。眺める人が奪っていたデータベースの空きが、買う人に回ったからです。

**要求の数は点数ではない。** B では 1 秒あたりの要求数が A の約 60〜210 倍になりましたが、点数は 2.7 倍です。増えた要求のほとんどは、データベースに行かなくなった人気一覧を眺める人が、速くなったぶん余計に送ったものです。要求の数のばらつき（5,539〜19,018）が大きいのは、この要求が CPU だけで捌かれていて、同じマシンで走っていたほかの処理の影響を直接受けたためです。点数のばらつきはそれよりずっと小さく収まっています。

**断れば軽くなるが、0 点になる。** D は人気一覧を 503 で断り、データベースを買う人だけに使わせました。購入は 839〜897 件と B に近い数まで伸びましたが、503 はベンチマーカーにとってエラーで、エラーが 100 件を超えた時点で FAIL です。

**正しさの検査は、遅さからも壊れる。** G の 3 回のうち 1 回は、次のように終わりました。

```text
requests=1710 (114 req/s) errors=18 purchases=423 revenue=42300 score=42282 FAIL (sold mismatch)
```

18 件の要求が 1 秒のタイムアウトに達しています。ベンチマーカーは応答を待つのをやめましたが、アプリケーションは購入の処理を最後まで続け、販売件数に数えました。その結果、ベンチマーカーの購入件数とアプリケーションの販売件数がずれ、突き合わせで FAIL になりました。タイムアウト自体の減点は 18 点でしかないのに、それが整合性の検査を通じて 0 点に変わったのです。ISUCON14 の決済の「5 秒以内に完了しなかった場合、ベンチマーカーの期待する決済金額と一致せずFAILになります」という規則が守ろうとしているのも、この種のずれです。

### 数字の理由

この結果は簡単な式で説明できます。32 人がそれぞれ 1 件ずつ要求を出して待っていて、データベースは空きを待つ順に 4 件ずつ処理します。すると、全員が 1 回ずつ処理を受けるのにかかる時間（1 巡）は、全員の問い合わせ時間の合計を 4 で割ったものになります。

```text
1 巡の時間 = (買う人 16 人の 1 回あたりの問い合わせ時間の合計 + 眺める人 16 人の合計) / 4
A: (16 × (40 + 20) / 2 + 16 × 60) / 4 = 360 ms
```

買う人は 1 回の購入に 2 巡（一覧と購入）を使うので、15 秒間の購入件数は `16 × 15 / (2 × 0.36) ≈ 333` です。平均の応答時間 340〜370 ms がこの 1 巡の時間とほぼ一致しているのも、この見方が当たっていることを示しています。同じ式で各案を見積もると、次のようになりました。

| | 1 巡の時間 | 見積もった購入件数 | 測った購入件数 |
| --- | --- | --- | --- |
| A | 360 ms | 333 | 338〜351 |
| F | 328 ms | 366 | 366〜383 |
| C | 300 ms | 400 | 378〜432 |
| G | 240 ms | 500 | 423〜471 |
| B | 120 ms | 1,000 | 876〜960 |

この店では、データベースの時間を誰が使っていても、全員の待ち時間が同じだけ延びます。だから**合計時間の大きいものから減らすと、点になる処理も含めて全員が速くなる**のです。アクセスログを合計時間で並べる理由は第 263 回で改めて見ますが、その根拠の一つはこの構造にあります。

一方で、合計時間の順位は「どれを直せば点になるか」の候補を示すだけです。点になる処理と資源を共有していなければ、どれほど合計時間の大きい処理を軽くしても点数は動きません。G で FAIL が出たように、速くしたことで別の検査に引っかかることもあります。**順位を決めるのは計測で、良し悪しを決めるのは点数（目的関数）**です。

<Callout type="tip" title="点数の決まりを最初に読む">
  ISUCON の上位チームの参加記には、マニュアルの点数の節を読み直して方針を変えた話がよく出てきます。
  ISUCON11 予選を 1 位で通過した shallowverse は、午後になってから「点の付け方を読み直す（2回目）」と書き、コンディションの送信が多いほどグラフの点の倍率が上がることに気づいています（[ISUCON11予選を1位通過した](https://www.y1r.org/posts/20210831-isucon11-qualify)）。
  本番でも同じで、改善を始める前に「何が増えれば成功なのか」を文章で確かめておくと、手を付ける順番が変わります。
</Callout>

## 本番での目的関数

ISUCON の採点の決まりは、本番のサービスで性能を考えるときの枠組みとほとんど同じ形をしています。

Google の SRE 本は、サービスの水準を表す指標と目標を次のように定義しています（[Site Reliability Engineering, Chapter 4 - Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)）。

> An SLI is a service level indicator—a carefully defined quantitative measure of some aspect of the level of service that is provided.

> An SLO is a service level objective: a target value or range of values for a service level that is measured by an SLI.

（SLI は、提供しているサービスの水準のある側面を、注意深く定義して数量で表したもの。SLO は、SLI で測ったサービスの水準について、目標とする値またはその範囲。）

そして、指標の選び方について次のように勧めています。

> Start by thinking about (or finding out!) what your users care about, not what you can measure.

（測れるものからではなく、利用者が何を気にしているかから考え始める。）

ISUCON の採点を本番の言葉に置き換えると、次のようになります。

| ISUCON | 本番 |
| --- | --- |
| 点数（取引額、Tips の合計、移動距離） | ビジネスの指標（売上、成約数、継続率）と、それに効く SLI |
| 点にならないリクエスト | 利用者の成果に直接つながらない処理。ただし資源を共有していれば間接的に効く |
| タイムアウトによる減点 | レイテンシの SLO 違反、エラーバジェットの消費 |
| 内容の誤りで FAIL | データの不整合、二重課金、誤った在庫。速さと交換してはならないもの |
| 追試（再起動後の再計測） | 再起動、デプロイ、障害からの復旧の後も同じ性能と正しさが保たれること |
| ブラフ | 仕様には書かれているが、実際の負荷にほとんど効かない機能 |

本番で目的関数を決めるときに、ISUCON から持ち帰れることが 3 つあります。

**要求の数は目的にならない。** 1 秒あたりのリクエスト数は、測りやすく、増えれば速くなったように見えます。けれど実測の B のように、要求の数は利用者の成果と無関係に増減します。ポーリングの間隔を短くしただけ、リトライが増えただけでも要求の数は増えます。

**正しさは制約として別に持つ。** 速さと正しさを一つの点数に混ぜてしまうと、「少し間違えても速い方が得」という判断が生まれます。ISUCON の採点が誤りに対して非対称に重いのは、それを防ぐためです。本番でも、整合性を壊す変更は性能の改善量に関係なく受け入れない、という線を先に引いておきます。

**資源の共有関係を地図にする。** 点になる処理と点にならない処理が何を奪い合っているかが分かれば、どちらを直すべきかが決まります。データベースの接続、CPU、ロック、外部 API の同時実行数。第 263〜265 回で、その地図を計測から描く方法を見ます。

<Callout type="warn" title="断ることは、本番では正当な手段になりうる">
  実測の D は、要求を 503 で断ってデータベースを空けました。ISUCON では、ベンチマーカーが正当な利用者を演じているので、これは誤りとして数えられます。
  本番では、過負荷のときに一部の要求を断る**負荷の切り離し（load shedding）**は、全体が倒れるのを防ぐ正当な設計です。
  違いは、断ることを目的関数の上で決めているかどうかです。どの要求を、どの条件で、どの程度まで断ってよいのかを、SLO やビジネス上の優先度として先に定めておく必要があります。
  ISUCON10 予選では、bot からの要求を 503 で断ることが想定された解法の一つでした。講評は「実際には bot のリクエストは椅子購入や物件資料請求といったコンバージョンにつながらないので、503エラーで弾いても問題ないことが当日のマニュアルに記載されています」と書いています（[ISUCON10 予選問題の解説と講評](https://isucon.net/archives/55025156.html)）。断ってよい相手が、仕様に書かれていたのです。
</Callout>

## 次の回へ

この回の実測では、ベンチマーカーの 32 人は応答を受け取ってから次の要求を送っていました。だから、アプリケーションが遅くなると、ベンチマーカーも勝手に遅くなります。眺める人を速くしたら要求が数十倍から 200 倍余りに増えたのも、この送り方のせいです。次の第 261 回では、負荷をかける側がどう振る舞うのかを、閉ループと開ループという 2 つの型で比べます。

## まとめ

- ISUCON は、決められたベンチマーカーが決められた時間だけ使ったときの点数を競う。問題・ベンチマーカー・講評・参加記が公開されていて、同じ条件で何度でも再現できる
- 競技と本番は違う。8 時間で捨てるコードと何年も保守するコードでは、同じ改善でも費用の重みが違う
- 性能改善は、何を最大にするか（目的関数）と、何を守るか（制約）を決めるところから始まる
- ISUCON9 予選から、点数はリクエストの数ではなく、利用者が生んだ価値（取引額、Tips の合計、移動距離）で定義されるようになった
- 点にならないリクエストもある。ただし点になる処理と資源を共有していれば、それを軽くすることが点になる
- タイムアウトの減点は軽く、内容の誤りは重い。クリティカルな誤りは 1 回で 0 点になる。正しさは速さと交換できない制約として扱われる
- 整合性の検査は遅さからも壊れる。タイムアウトで打ち切られた処理がサーバー側で完了すると、記録がずれて FAIL になりうる
- 最終スコアは追試で確かめられる。再起動後に動くこと、書き込んだデータが残ることも採点の条件に含まれる
- 手を付けても点にならない要素（ブラフ）がある。見るからに遅そうという推測ではなく、計測で選ぶ
- 実測では、点になる購入の問い合わせを 5 分の 1 にしても点数は数 % しか増えず、点にならない人気一覧をデータベースから外すと約 2.7 倍になった。要求の数は約 60〜210 倍になったが、それは点数ではない
- 本番では、点数がビジネスの指標と SLI・SLO に、減点がエラーバジェットに、FAIL がデータの不整合に、追試が再起動やデプロイ後の確認に当たる
