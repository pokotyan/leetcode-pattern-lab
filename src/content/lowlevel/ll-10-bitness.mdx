## 「64 ビット」が指しているもの

この言葉はいくつかのものを同時に指していて、混乱の元になっています。整理します。

| 何のビット幅か | 意味 |
| --- | --- |
| **アドレスの幅** | 指せるメモリの範囲。**これが主役** |
| レジスタの幅 | 一度に扱える整数の大きさ |
| データバスの幅 | 一度にメモリとやり取りするバイト数 |
| 命令長 | 命令 1 個のビット数（無関係。ARM64 の命令は 32 ビット） |

「64 ビット CPU」と言うとき、通常は **アドレスとレジスタが 64 ビット幅**であることを指します。

<Callout type="warn" title="命令長とは無関係">
  ARM64 は 64 ビット CPU ですが、**命令は 32 ビット固定長**です。
  「64 ビット CPU だから命令も 64 ビット」ではありません。
  ここは混同しやすい箇所です。
</Callout>

## 4GB の壁

32 ビットのアドレスで指せる範囲は 2³² バイト = **4GB** です。これが 32 ビット時代の上限でした。

しかも実際に使えるのは 4GB より少なくなります。理由は、アドレス空間の一部が OS 自身や周辺機器の領域に予約されるためです。

| 区分 | 32 ビット Windows の典型 |
| --- | --- |
| ユーザ空間 | 2GB（設定で 3GB にできる） |
| カーネル空間 | 2GB |

さらに、グラフィックカードなどのメモリがアドレス空間にマップされるため、「8GB 積んだのに 3.2GB しか認識されない」という現象が起きました。**物理メモリが足りないのではなく、番地が足りない**という状況です。

<Callout type="note" title="延命策としての PAE">
  32 ビットのまま 4GB を超えるために、**PAE**（Physical Address Extension）という仕組みがありました。
  物理アドレスを 36 ビットに拡張し、64GB まで扱えるようにするものです。
  ただし、**1 つのプロセスが見られる範囲は 4GB のまま**です。
  複数のプロセスで合計 64GB を使えるだけで、根本的な解決ではありませんでした。
</Callout>

## 64 ビットで何が変わったか

**1. アドレス空間が実質的に無制限になった。**

2⁶⁴ = 約 1844 京バイト（16EB）です。現実の実装では全部は使いません。x86-64 では当初 48 ビット（256TB）、現在は 57 ビット（128PB）まで拡張されています。それでも当面は足ります。

<Callout type="tip" title="正準アドレスという規則">
  x86-64 で 48 ビットしか使わない場合、残りの上位 16 ビットは
  **48 ビット目と同じ値で埋めなければならない**という規則があります（正準形式）。
  これに反するアドレスを使うと例外が発生します。
  将来アドレス幅を拡張したときに、上位ビットを勝手に使っていたプログラムが壊れるのを防ぐためです。
</Callout>

**2. レジスタが増えた。**

x86 では 8 本から 16 本に倍増しました。これは地味に見えて、実際の性能に大きく効きます。レジスタが足りずにメモリへ退避する（スピル）回数が減るからです。

**3. 64 ビット整数が 1 命令で扱えるようになった。**

32 ビット時代は、64 ビットの加算に複数命令が必要でした。

**4. 呼び出し規約が改善された。**

32 ビットの x86 では、関数の引数をスタック経由で渡すのが一般的でした。x86-64 では**最初の 6 個をレジスタで渡します**。メモリアクセスが減り、関数呼び出しが速くなりました。

**5. SSE2 が必須になった。**

浮動小数点演算が、古い x87 スタック方式から SSE レジスタ方式に移行しました。

## 代償

**ポインタが 2 倍のサイズになりました。** 8 バイトです。

ポインタを大量に含むデータ構造（連結リスト、木、ハッシュテーブル）では、メモリ使用量が目に見えて増えます。そしてメモリ使用量が増えるということは、**キャッシュに乗る要素数が減る**ということです。

このため、64 ビット化直後は「メモリを多く使う代わりに遅くなる」ケースが実際にありました。JVM には **圧縮 OOP** という仕組みがあり、ヒープが 32GB 以下ならポインタを 32 ビットで持つことで、この損失を避けています。

<Callout type="note" title="x32 ABI">
  「64 ビットのレジスタと命令は使いたいが、ポインタは 32 ビットのままにしたい」
  という要求に応えたのが **x32 ABI** です。
  4GB 以下で動くプログラムなら、メモリ効率と性能を両立できます。
  ただし普及せず、Linux でも縮小の方向にあります。
</Callout>

## 型のサイズが処理系で違う

64 ビット化に際して、C の型のサイズをどうするかで判断が分かれました。

| モデル | `int` | `long` | ポインタ | 採用 |
| --- | --- | --- | --- | --- |
| **LP64** | 32 | **64** | 64 | Linux, macOS, BSD |
| **LLP64** | 32 | **32** | 64 | **Windows** |
| ILP32 | 32 | 32 | 32 | 32 ビット環境 |

**Windows だけ `long` が 32 ビットのまま**です。既存の Windows のコードが `long` を 32 ビットと仮定して大量に書かれていたためです。

この差は、移植時に必ず問題になります。

```c
long x = ...;               // Linux では 64 ビット、Windows では 32 ビット
printf("%ld\n", x);         // 書式指定子も食い違う
```

対策は、**サイズを明示した型を使う**ことです。

```c
#include <stdint.h>
int64_t  x;      // どこでも 64 ビット
uintptr_t p;     // ポインタを入れられる整数
size_t   n;      // サイズを表す。64 ビット環境では 64 ビット
```

<Callout type="warn" title="ポインタを int に入れない">
  32 ビット時代には `int` にポインタを入れるコードが書けてしまいました。
  64 ビットでは上位 32 ビットが失われます。
  ポインタを整数として持つ必要があるなら `uintptr_t` を使います。
</Callout>

## 確認する方法

```bash
uname -m            # x86_64 / aarch64 / i686
getconf LONG_BIT    # 64
file ./a.out        # ELF 64-bit LSB executable, x86-64
```

C で確かめるならこうです。

```c
printf("%zu %zu %zu\n", sizeof(int), sizeof(long), sizeof(void*));
```

## まとめ

- 「64 ビット」の主役はアドレス幅。次いでレジスタ幅
- 32 ビットでは 1 プロセスあたり 4GB が上限で、実際はもっと少ない
- 64 ビット化で、アドレス空間・レジスタ数・呼び出し規約が同時に改善された
- 代償はポインタが 8 バイトになること。キャッシュ効率が落ちる
- `long` のサイズは Linux と Windows で違う。`int64_t` などを使う

次は、現代の CPU が 1 命令ずつ順番に実行してはいない、という話に入ります。
