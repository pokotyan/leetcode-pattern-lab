## 定時バッチが 2 回走った

毎晩 3 時に売上を集計して、結果をファイルに書き出すバッチがあるとします。1 台のサーバの cron で動かしていましたが、そのサーバが落ちた夜に集計が抜けました。そこで同じ設定のサーバをもう 1 台用意し、両方の cron に同じ行を書きました。翌朝、集計は 2 回走っていて、取引先へのメールも 2 通ずつ届いていました。

前回は、データベースをキューにして、仕事を 1 件ずつ取り出す方法を見ました。そこでは、期限を書いた行が「いまこのジョブを持っているのは誰か」を表し、期限が切れた後に戻ってきた元のワーカーが、他人の処理中のジョブを完了にしてしまう危うさにも触れました。今回は、それをジョブ 1 件から役割に広げます。問題は、キューから仕事を取り出すさらに手前にあります。**同じ仕事を、誰か 1 人だけに始めさせたい。** 冗長にするために台数を増やすと、何もしなければ全員が動きます。かといって 1 台に戻せば、その 1 台が落ちたときに誰も動きません。

求めているものを言葉にすると、こうなります。

- **いま動いてよいのは 1 人だけ**（安全性）
- **その 1 人が落ちたら、いずれ別の誰かが動ける**（活性）

第 37 回で見たミューテックスは、1 台の中ではこの両方を満たしていました。ハードウェアが CAS を分割不可能に実行してくれ、ロックを持ったスレッドが死ねばプロセスごと消えるからです。マシンをまたぐと、どちらも自明ではなくなります。この回では、部品を 3 つ順に足していきます。**比較して交換する書き込み**、**期限付きのロック（リース）**、そして**書き込み先が古い持ち主を拒む仕組み（フェンシング）**です。

## 比較して交換する

### 2 人が同時に「無ければ作る」

いちばん素朴なロックは、「`locks/nightly` というファイルが無ければ作る。あったら諦める」です。ところが、「あるか見る」と「作る」を別々の要求にすると、2 台が同時に「無い」と見て、2 台とも作ってしまいます。第 37 回で見た、読んでから書くまでの間に割り込まれる競合と同じ形です。

必要なのは、**確認と書き込みを 1 回の要求にまとめ、その間に誰も割り込めないことを書き込み先が保証する**ことです。1 台の中ではこれが CAS（compare-and-swap、比較して一致したら交換する）命令でした。マシンをまたぐ場合は、書き込み先のサーバが同じことを引き受けます。

### HTTP の条件付きリクエスト

HTTP には、この形の要求が仕様として用意されています。RFC 9110 の**条件付きリクエスト**です（[RFC 9110 13.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1)）。

| ヘッダ | 意味 | 外れたとき |
| --- | --- | --- |
| `If-Match: "etag"` | いまの版の識別子（ETag）がこの値なら実行する | 412 Precondition Failed |
| `If-None-Match: *` | まだ何も無いときだけ実行する | 412 Precondition Failed |

RFC は `If-Match` の用途を、複数の利用者が同じ資源を並行して扱うときの意図しない上書き、つまり **lost update（失われた更新）** を防ぐことだと説明しています（[RFC 9110 13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)）。`If-None-Match: *` についても、複数の利用者が最初の版を作ろうとしたときに起きる lost update の変形を防ぐ、と書いています（[RFC 9110 13.1.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2)）。条件が外れたときの **412** は、要求に付けた条件が偽だったことを表す状態コードです（[RFC 9110 15.5.13](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.13)）。

`If-None-Match` は、本来はキャッシュの確認に使われるヘッダです。次の章の第 117 回では、ブラウザが手元の ETag を添えて GET し、変わっていなければ 304 が返る使い方が出てきます。同じヘッダに `*` を付けて PUT に添えると、「無ければ作る」になります。

```
 クライアント A                    サーバ                    クライアント B
  PUT /locks/nightly ──────────→                ←────────── PUT /locks/nightly
  If-None-Match: *                │ まだ無い？                If-None-Match: *
                                  │ 判定と書き込みを 1 つずつ順に
  ←── 200 OK（作った）              │
                                  └─────────────────────→ 412（もうある）
```

### データベースの version 列

データベースの行でも、同じことを列 1 つで作れます。行に `version` 列を持たせ、更新の条件に「読んだときの version のままなら」を入れます。

```sql
-- 読む: version = 7 だった
UPDATE settings SET value = 'new', version = version + 1
 WHERE id = 1 AND version = 7;
-- 更新件数が 0 なら、誰かが先に書いた。読み直してやり直す
```

これを**楽観ロック**（楽観的並行性制御）と呼びます。第 100 回で見た `SELECT ... FOR UPDATE` は、読む時点で行にロックを掛け、相手を待たせる**悲観ロック**でした。楽観ロックは誰も待たせず、書く瞬間にぶつかったかどうかだけを確かめます。ぶつかることがまれなら速く、ロックを持ったまま落ちる人もいません。その代わり、ぶつかったら読み直してやり直す処理を自分で書く必要があります。第 223 回と第 230 回で扱う Kubernetes の `resourceVersion` も、API の単位で同じことをしています。

### オブジェクトストレージの CAS

オブジェクトストレージも、条件付きの書き込みを持つようになりました。

| 書き込み先 | 「無ければ作る」 | 「この版のままなら書く」 | 外れたとき |
| --- | --- | --- | --- |
| HTTP（RFC 9110） | `If-None-Match: *` | `If-Match: ETag` | 412 |
| Amazon S3 | `If-None-Match: *`（2024 年 8 月〜） | `If-Match: ETag`（2024 年 11 月〜） | 412 |
| Google Cloud Storage | `ifGenerationMatch=0` | `ifGenerationMatch=generation` | 412 |
| etcd | `create_revision == 0` を比較する txn | `mod_revision == n` を比較する txn | txn が失敗側に分岐 |
| データベースの行 | 一意制約付きの `INSERT` | `WHERE version = n` | 一意制約違反 / 更新 0 件 |

S3 の文書は、同じキーに複数の条件付き書き込みが来た場合は**先に終わった 1 つが成功し、残りは 412** になると書いています（[Amazon S3: Conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html)）。`If-None-Match` は 2024 年 8 月（[What's New](https://aws.amazon.com/about-aws/whats-new/2024/08/amazon-s3-conditional-writes/)）、`If-Match` は 2024 年 11 月（[What's New](https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-s3-functionality-conditional-writes/)）に使えるようになりました。GCS ではオブジェクトの版の番号である generation を前提条件に使い、`0` は「まだ存在しなければ」を表す特別な値です（[GCS: Request preconditions](https://docs.cloud.google.com/storage/docs/request-preconditions)）。

これが入ったことで、**ロックのためだけに別のデータベースを用意する必要が減りました。** Terraform の S3 バックエンドは、状態ファイルを同時に書き換えないためのロックを、以前は DynamoDB の表で取っていました。Terraform 1.10 で S3 の条件付き書き込みによるロックファイル（`use_lockfile`）が入り、1.11 で正式な機能になり、DynamoDB による方式は非推奨になりました（[Terraform 1.11 CHANGELOG](https://github.com/hashicorp/terraform/blob/v1.11/CHANGELOG.md)、[S3 backend](https://developer.hashicorp.com/terraform/language/backend/s3)）。

Iceberg や Delta Lake のようなテーブル形式も、「最新版はこれ」という 1 つのポインタを条件付きで差し替えることで、ファイルの集合の入れ替えを原子的に見せています。この話と、MinIO で `If-None-Match` と `If-Match` を 1 回ずつ試した実験は、読み物の<a href={`${import.meta.env.BASE_URL}reading/lake-storage/`}>データの置き場所</a>にあります。この回の実験では、**同時に**ぶつけたときに本当に 1 人だけが勝つかを見ます。

## ロックには期限が要る

「無ければ作る」でロックを取れるようになりました。ところが、このロックには致命的な弱点があります。**取った人が、外す前に落ちたら、永遠に外れません。** 第 37 回のミューテックスでは、持ち主のスレッドが死ねばプロセスごと消えました。ネットワークの向こうのロックファイルは、持ち主が電源ごと消えても残り続けます。翌晩のバッチは、誰も持っていないロックを待ち続けます。

そこで、ロックに**期限**を付けます。期限付きのロックを**リース**（lease、賃借）と呼びます。持ち主は期限が来る前に**更新**（ハートビート）し続け、更新が途絶えれば、期限が来た時点で他の人が取ってよいことにします。持ち主が落ちても、待つのは期限の長さまでで済みます。

```
  持ち主 A:  取得 ─ 更新 ─ 更新 ─ 更新 ─ ✕（落ちた）
  期限:      |─────10s─────|
                   |─────10s─────|
                         |─────10s─────|
                               |─────10s─────|  ← ここで切れる
  B:                                          取得
```

期限を誰が測るかで、作り方が 2 つに分かれます。

**書き込み先が測る。** etcd のリースがこれです。クライアントは `LeaseGrant` で TTL（秒）付きのリースをもらい、キーをそのリースに結び付けます。etcd が TTL の間に更新（`LeaseKeepAlive`）を受け取らなければリースは切れ、**結び付いたキーはすべて削除されます**（[etcd API](https://etcd.io/docs/v3.5/learning/api/)）。Redis の `SET key value NX PX 30000`（無ければ作り、30 秒で消える）も同じ形です（[Redis: Distributed Locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)）。

**自分たちで測る。** S3 や GCS のオブジェクトには、こうした「一定時間で消える」機能がありません（ライフサイクル規則は日単位の後片付けで、ロックの期限には使えません）。そこで、期限をロックの**中身に書き**、読む側が自分で判定します。

```
 locks/nightly.json の中身:  {"holder": "host-a", "expires_at": 1792838511}

 B の手順:
   1. GET して中身と ETag を読む
   2. expires_at が過ぎていなければ諦める
   3. 過ぎていれば、自分の中身を If-Match: <読んだ ETag> で PUT する
      → 同じことを考えた C と同時になっても、勝つのは 1 人（他は 412）
```

ここに時計の問題が入り込みます。`expires_at` を書いたのは A の壁時計で、それを判定するのは B の壁時計です。第 211 回で詳しく扱いますが、別のマシンの時計は完全には揃わず、NTP の step で戻ることもあります。B の時計が進んでいれば、まだ有効なロックを奪ってしまいます。

より安全なのは、**相手の時刻を信用せず、自分の単調時計で測る**ことです。「同じ ETag のまま、自分の時計で期限の長さだけ変化が無かったら奪う」とすれば、比べるのは自分の時計の経過時間だけになります。後で見る Kubernetes の leaderelection は、まさにこのやり方をしています。

## 期限付きにした途端に起きること

リースで「落ちた持ち主」の問題は解けました。代わりに、もっと厄介な問題が生まれます。**持ち主は落ちていないのに、期限が切れることがある**のです。

```
 時刻  A                              ロック              B
  0s   リースを取る（期限 10s）       A
  1s   書き込みの準備 ─┐
       ……GC で停止……   │                                   
 10s                    │             期限切れ
 11s                    │             B                    リースを取る
 12s                    │                                  書き込む
 15s   停止から戻る ←──┘
 15s   書き込む  ← A は自分がまだ持ち主だと思っている
```

A が止まる理由はいくらでもあります。

- 第 26 回で見た GC の **Stop the World**。ヒープが大きければ秒単位になることもある
- 仮想マシンの一時停止やライブマイグレーション、スワップアウトされたページの読み戻し
- `SIGSTOP`、デバッガ、コンテナの CPU 制限による長い絞り込み
- 要求がネットワークのどこかで遅れ、期限が切れた後に届く
- 壁時計の巻き戻しや進みすぎで、期限の判定そのものがずれる

「書く直前に、まだ期限内か確かめればよい」と思うかもしれません。しかし、確かめた直後に止まれば同じことです。Martin Kleppmann は、GC はスレッドを**どの時点でも**止めうるので、この確認では防げないと指摘しています（[How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)）。**止まっている本人には、止まっていたことが分かりません。** 戻ってきた A にとっては、1 行前の続きを実行しているだけです。

Google の Chubby の論文も、同じ問題を正面から書いています。ロック L を持つプロセスが要求 R を出してから落ち、別のプロセスが L を取って何かした後に R が届けば、R は L の保護なしに、しかも食い違ったデータの上で実行されうる（[Burrows, OSDI 2006](https://storage.googleapis.com/gweb-research2023-media/pubtools/4444.pdf)）。

## フェンシングトークン

問題の核心は、**ロックを判定する場所と、書き込みが実行される場所が別**であることです。ロックのサービスがどれだけ正しくても、書き込み先が「この書き込みは今の持ち主からか」を知らなければ、古い持ち主の書き込みは通ってしまいます。

そこで、ロックを取るたびに**単調に増える番号**を配り、書き込みにその番号を添えさせます。書き込み先は、これまでに受け付けた最大の番号を覚えておき、**それより小さい番号の書き込みを拒否します**。これが **フェンシングトークン**です。Kleppmann の例では、A がトークン 33 を得て止まり、B が 34 を得て書き、戻ってきた A の 33 の書き込みは、34 を見たことのある書き込み先に拒否されます（[Kleppmann](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)）。

```
 ロックサービス                  書き込み先（最大トークン を覚える）
  A に token 33 ─→ A ……停止……
  B に token 34 ─→ B ── 書く(34) ──→  受理。max = 34
                   A ── 書く(33) ──→  33 < 34 なので拒否
```

同じ役割の番号は、あちこちに既にあります。

| 仕組み | 単調に増える番号 | 誰が検査するか |
| --- | --- | --- |
| Chubby | sequencer（ロック名、モード、ロックの世代番号） | 要求を受けたサーバ |
| etcd | revision（キー空間が変わるたびに増える、クラスタ全体のカウンタ） | `Txn` の比較 |
| Kubernetes | `resourceVersion` | API サーバ（409 Conflict） |
| Raft | 任期（term） | 各ノード（古い任期の leader の要求を拒む） |
| オブジェクトストレージ | ETag / generation | ストレージ（412） |

**Chubby** は、ロックを持つ人が **sequencer** という不透明なバイト列を受け取り、ロックで守りたい要求に添えてサーバに渡す仕組みを持っています。受け取ったサーバは、それがまだ有効か確かめ、有効でなければ拒否することになっています（[Burrows, OSDI 2006](https://storage.googleapis.com/gweb-research2023-media/pubtools/4444.pdf)）。sequencer に対応できないサーバのために、持ち主が落ちて外れたロックを一定時間（**lock-delay**、上限 1 分）誰にも取らせない仕組みも用意されています。論文自身が「不完全だが」と断っている保険です。

**etcd** の文書には、ロックとリースの使い方について率直な注意書きがあります。リースの TTL はサーバとクライアントがそれぞれ自分の時計で測る物理時間なので、サーバがリースを取り消した後もクライアントが持っているつもりでいる状況が起こりうる。だからリースそのものは相互排除を保証しない。そのうえで、Chubby の sequencer は etcd の revision とリース ID の組み合わせにほぼ相当し、Kleppmann のフェンシングトークンは etcd では revision に当たる、と書いています。そして、**etcd の外の資源を守りたいなら、その資源自身が版の番号を検査できなければならない**とも（[etcd: Notes on the usage of lock and lease](https://etcd.io/docs/v3.5/learning/why/#notes-on-the-usage-of-lock-and-lease)）。

<Callout type="warn" title="書き込み先が検査しなければ、トークンは飾り">
  フェンシングトークンは、配るだけでは何も守りません。
  書き込み先が「最大の番号」を覚え、比較して拒否して初めて効きます。
  ファイルサーバ、外部の API、メール送信のように、番号を検査できない相手に対しては、トークンでは防げません。
  その場合は、書き込み先の側の条件付き書き込み（読んだ ETag や version のままなら書く）を使うか、
  二重に実行されても結果が変わらないように作る（冪等にする）ことになります。
</Callout>

### Redlock をめぐる議論

Redis の文書は、5 台の独立した Redis に同じキーを `SET NX PX` で書き、過半数で取れて、かつ取るのにかかった時間が期限より十分短ければロックを得たとみなす **Redlock** というアルゴリズムを載せています（[Redis: Distributed Locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)）。

2016 年に Kleppmann はこれを分析し、2 つの点を挙げました。Redlock は**フェンシングトークンを生成しない**こと、そして安全性が**同期的なシステムモデル**、つまりネットワークの遅延、プロセスの停止、時計のずれに上限があるという仮定に依存し、それらが期限と同じくらいの大きさになると破れることです。そのうえで、効率のため（たまに二重に動いても困らない）なら Redis 1 台で十分、正しさのためなら合意に基づくシステムとフェンシングを使うべきだ、と勧めています（[Kleppmann](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html)）。Redis の作者 antirez は反論を公開しており、Redis の文書は両方へのリンクを並べています。

いま Redis の文書の側にも、一貫性を気にするなら**フェンシングトークンを実装すべき**こと、Redis の TTL は**単調時計を使っておらず**、壁時計がずれると複数のプロセスがロックを得うることが、注意として書かれています（[Redis: Distributed Locks](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)）。どちらの立場を取るにしても、実務で持ち帰るべき点は同じです。**ロックを「効率のため」に使うのか「正しさのため」に使うのかを決め、正しさのためなら、書き込み先で古い持ち主を拒む仕組みを用意する。**

## リーダー選出は、リースの取り合い

「1 人だけが動く」を長い時間続けたいとき、それを**リーダー選出**と呼びます。言葉は大きいですが、中身はここまでと同じで、**リースを取り合い、取れた人が更新し続ける**だけです。

etcd には選出の API があり、`etcdctl elect` で試せます。候補はそれぞれ自分のリース付きのキーを作り、作られた順（create_revision の小さい順）で最初の 1 人がリーダーになります。ロック（`etcdctl lock`）も同じ作りで、Go のクライアントの実装は、「自分のキーの create_revision が 0（まだ無い）なら作る」という `Txn` を投げ、プレフィックスの中で最も古いキーの持ち主をロックの持ち主としています（[concurrency/mutex.go](https://github.com/etcd-io/etcd/blob/main/client/v3/concurrency/mutex.go)）。

Kubernetes では、`coordination.k8s.io` の **Lease** オブジェクトがこの役を担います（[Kubernetes: Leases](https://kubernetes.io/docs/concepts/architecture/leases/)）。HA 構成の `kube-controller-manager` や `kube-scheduler` は、Lease を取れた 1 つだけが動き、残りは待機します。第 230 回で、自作のコントローラを冗長にするときに使うのもこれです。Lease の `spec` には次のフィールドがあります（[Lease v1](https://kubernetes.io/docs/reference/kubernetes-api/cluster-resources/lease-v1/)）。

| フィールド | 意味 |
| --- | --- |
| `holderIdentity` | いまの持ち主 |
| `leaseDurationSeconds` | 他の候補が、最後に見た `renewTime` から待たなければならない時間 |
| `acquireTime` | いまの持ち主が取った時刻 |
| `renewTime` | いまの持ち主が最後に更新した時刻 |
| `leaseTransitions` | 持ち主が交代した回数 |

同じ Lease は、ノードの生存確認にも使われています。ノードごとに `kube-node-lease` 名前空間に同名の Lease があり、kubelet のハートビートは、その `renewTime` を書き換える更新要求です（[Kubernetes: Leases](https://kubernetes.io/docs/concepts/architecture/leases/)）。

Go のクライアントの `leaderelection` パッケージには、時計についての興味深い設計があります（[client-go leaderelection](https://pkg.go.dev/k8s.io/client-go/tools/leaderelection)）。

- 待っている候補は、Lease に書かれた `renewTime` を**自分の時計と比べません**。他のマシンの時計で書かれた値かもしれないからです。代わりに、Lease の中身が変わったことを**自分の時計で観測した時刻**を覚え、そこから `leaseDurationSeconds` の間変化が無ければ期限切れとみなします。そのため、時計の**ずれ**にはいくらでも耐えますが、時計の**進む速さの違い**には耐えない、と文書は書いています
- 既定値は `LeaseDuration` 15 秒、`RenewDeadline` 10 秒、`RetryPeriod` 2 秒です。持ち主は 10 秒以内に更新できなければリーダーを降り、候補は 2 秒ごとに取得を試みます
- Lease の更新は、読んだときの Lease をそのまま書き戻す `Update` なので、`resourceVersion` による楽観ロックがかかり、2 人が同時に奪おうとしても片方は拒否されます（[resourcelock/leaselock.go](https://github.com/kubernetes/client-go/blob/master/tools/leaderelection/resourcelock/leaselock.go)）
- そしてパッケージの冒頭には、**この実装は、同時にリーダーとして振る舞うクライアントが 1 つだけであることを保証しない（フェンシング）**と明記されています

つまり Kubernetes のリーダー選出も、期限切れに気付かない元リーダーの問題からは自由ではありません。組み込みのコントローラがそれでも成り立つのは、書き込み先の API サーバが `resourceVersion` で衝突を拒み、調整ループが「最新の状態を読んで差を埋める」作りなので、二重に動いても結果が壊れにくいからです（第 223 回で扱います）。

<Callout type="note" title="リースの長さは、何と何の交換か">
  リースを短くすれば、リーダーが落ちてから次が動き出すまでが短くなります。
  そのかわり、GC やネットワークの一時的な遅れで更新が間に合わず、生きているリーダーが降ろされることが増えます。
  長くすれば逆です。client-go の文書は、リーダーの交代の頻度を監視し、安定するまで `RetryPeriod` と `LeaseDuration` を伸ばすよう勧めています。
  <a href={`${import.meta.env.BASE_URL}reading/consensus/`}>分散合意</a>で見た Raft の選挙のタイムアウトにも、同じ交換があります。
</Callout>

## 手元で確かめる

### 実験の環境

docker の 1 つのネットワークに、次のコンテナを置きました。ホストへのポート公開はしていません。

| 役割 | イメージ | 版 |
| --- | --- | --- |
| S3 互換ストレージ | `pgsty/minio`（MinIO のコミュニティ派生版） | `RELEASE.2026-08-04T00-00-00Z` |
| etcd | `quay.io/coreos/etcd:v3.6.5` | etcd 3.6.5（1 台構成） |
| クライアント | `python:3.12-slim` | boto3 1.43.118、etcdctl 3.6.5 |
| データベース | `postgres:17` | PostgreSQL 17.11 |

MinIO は S3 そのものではなく、同じ API を話すローカルの代替です。MinIO での結果は、S3 での動作の証明にはなりません。

### (1) 8 プロセスが同時に「無ければ作る」

8 個のプロセスを `multiprocessing.Barrier` で揃えて同時に走らせ、同じキーに `put_object(..., IfNoneMatch="*")` を送ります。まず比較のため、条件を付けずに同じことをします。

```
条件なし PUT: [200, 200, 200, 200, 200, 200, 200, 200]
中身: {"holder": "w6"}
```

全員が成功し、最後に書いた w6 の中身だけが残りました。全員が「自分がロックを取った」と思っています。次に `If-None-Match: *` を付けます。キーを変えて 50 回繰り返しました。

```
--- (a) 無ければ作る: 8 プロセスが同時に If-None-Match: * ---
  w0: 412
  w1: 412
  w2: 412
  w3: 412
  w4: 200
  w5: 412
  w6: 412
  w7: 412
  中身: {"holder": "w4", "expires_at": 1792838534.882602}
  50 回のうち、勝者がちょうど 1 人だった回: 50  勝者の数の分布: {1: 50}
```

50 回すべてで、勝者はちょうど 1 人でした。残りの 7 人は 412 を受け取り、自分が負けたことを知ります。

### (2) 期限切れのロックを同時に奪う

次に、`expires_at` が過去になったロックを置き、その ETag を 8 人が同時に `If-Match` に指定して書き換えます。「期限切れを見つけた複数の人が、同時に奪いに来た」状況です。

```
  いまのロック: {"holder": "old", "expires_at": 1792838496.0463135} ETag "d9bbaca19b64d0fa889b03ab5619e2d9"
  w0: 412
  w1: 412
  w2: 412
  w3: 412
  w4: 412
  w5: 412
  w6: 412
  w7: 200
  中身: {"holder": "w7", "expires_at": 1792838527.0842566} ETag "d8105e5d6435c191c795d6d4a9d47820"
```

勝ったのは w7 だけで、ETag が新しい値に変わりました。他の 7 人が持っている ETag はもう古いので、何度送っても 412 です。期限の判定（`expires_at` が過ぎたか）は各自の時計で行っていますが、**奪い合いの決着は書き込み先の CAS が付けている**ことに注意してください。

### (3) etcd のリースは、更新しなければ消える

TTL 5 秒のリースを作り、そのリースに結び付けてキーを書きます。更新はしません。

```
$ etcdctl lease grant 5
lease 694da16d7fb46d05 granted with TTL(5s)
$ etcdctl put --lease=... jobs/nightly/owner worker-a
OK
header.revision 2 create_revision 2 mod_revision 2 version 1 lease 7587898438855191813
lease 694da16d7fb46d05 granted with TTL(5s), remaining(4s)
(更新せずに 6 秒待つ)
lease 694da16d7fb46d05 already expired
get の結果の件数: 0 header.revision 3
```

期限が来るとリースは切れ、キーは消えました。revision が 2 から 3 に進んでいます。**期限切れによる削除も、キー空間の 1 回の変更として revision を 1 つ進めます。** 誰かがこのキーの変化を watch していれば、削除のイベントとして受け取れます。

### (4) etcdctl lock の持ち主を止める

`etcdctl lock --ttl=5 nightly` を 2 つ起動します。先に起動した A がロックを取り、B は待ちます。そこで A を `SIGSTOP` で止めます。止められた A はリースを更新できません。

```
[  1.00s] A: nightly/694da16d7fb46d0b
[  2.02s] B は待っている。出力: ''
   header.revision 5
    nightly/694da16d7fb46d0b create_revision 4
    nightly/694da16d7fb46d0f create_revision 5
[  2.05s] A を SIGSTOP
[  7.52s] B: nightly/694da16d7fb46d0f
   header.revision 6
    nightly/694da16d7fb46d0f create_revision 5
[  7.54s] A を SIGCONT
[ 10.56s] A の出力:
   nightly/694da16d7fb46d0b
   
   Error: session expired
   A のプロセス: 終了
```

ロックの実体は、`nightly/` の下の、リース ID を名前に持つキーです。A のキー（create_revision 4）と B のキー（create_revision 5）が並び、古い A が持ち主でした。A を止めてから約 5.5 秒後、A のリースが切れてキーが消え、B が持ち主になりました。

注目してほしいのは最後です。A は、**止めている間は何も知らず、再開されてから初めて**「session expired」に気付いて終了しました。etcdctl は気付いた時点で止まってくれますが、A が自前のプログラムで、再開直後に書き込みを始めるような作りなら、気付く前に書いてしまいます。それを次の (6) で作ります。

### (5) etcdctl elect は既定で 60 秒待つ

`etcdctl elect batch-leader worker-a` と `worker-b` を起動し、リーダーの A を止めます。

```
A: batch-leader/694da16d7fb46d1b worker-a
B: ''
$ etcdctl elect -l batch-leader
batch-leader/694da16d7fb46d1b
worker-a
    batch-leader/694da16d7fb46d1b = worker-a create_revision 8
    batch-leader/694da16d7fb46d20 = worker-b create_revision 9
A を止めてから B が leader になるまで 56.77s
B: batch-leader/694da16d7fb46d20 worker-b
A: batch-leader/694da16d7fb46d1b worker-a Error: elect: session expired
```

今度は B が引き継ぐまでに 57 秒かかりました。この版の `etcdctl elect` には TTL を指定するオプションが無く、Go のクライアントのセッションの既定の TTL である 60 秒（[concurrency/session.go](https://github.com/etcd-io/etcd/blob/main/client/v3/concurrency/session.go)）がそのまま使われるためです。リーダーが落ちてから最大でこれだけの間、誰も動きません。リースの長さが、そのまま引き継ぎの遅さになることが分かります。

### (6) 止まっていたワーカーが書き込む

最後に、この回の中心の状況を作ります。小さな Python で、次の 2 つを用意しました。

- **ワーカー**: etcd の HTTP の入り口（gRPC gateway）を叩いて TTL 3 秒のリースを取り、「ロックのキーの create_revision が 0 なら、自分のリース付きで作る」という `Txn` でロックを取る。成功したときの応答の revision を、フェンシングトークンとして持つ。別スレッドで 1 秒ごとにリースを更新し、少し仕事をしてから、書き込み先に `token` と結果を PUT する
- **書き込み先**: 結果を 1 つだけ持つ小さな HTTP サーバ。`naive` では何でも受け付け、`fencing` ではこれまでの最大トークンより小さい書き込みを 409 で拒否する

A を起動し、ロックを取った直後に `SIGSTOP` で止め、B を起動します。B が書き終えたら A を `SIGCONT` で再開します。

```
=== 書き込み先: naive ===
[  0.05s] A: ロックを取った。lease=694da16d7fb46d5d token(revision)=20
[ 0.50s] (A を SIGSTOP)
[  3.61s] B: ロックを取った。lease=694da16d7fb46d60 token(revision)=22
[storage] 受理 token=22 value=B の集計結果
[  4.12s] B: 書き込み成功: B の集計結果
(A を SIGCONT)
[storage] 受理 token=20 value=A の集計結果
[  4.14s] A: 書き込み成功: A の集計結果
最終状態: {"value": "A の集計結果", "max_token": 22}
```

A のリースが切れて B がロックを取り、正しく書きました。その 20 ミリ秒後、再開した A が、**自分がまだ持ち主だと思ったまま**古い結果を書き、B の結果を上書きしました。A のリース更新のスレッドが失敗に気付くより先に、書き込みが終わっています。書き込み先を `fencing` にして同じことをします。

```
=== 書き込み先: fencing ===
[  0.29s] A: ロックを取った。lease=694da16d7fb46d74 token(revision)=24
[ 0.50s] (A を SIGSTOP)
[  3.77s] B: ロックを取った。lease=694da16d7fb46d77 token(revision)=26
[storage] 受理 token=26 value=B の集計結果
[  4.27s] B: 書き込み成功: B の集計結果
(A を SIGCONT)
[storage] 拒否 token=24 < max_token=26 (A の集計結果)
[  4.29s] A: 書き込み拒否: HTTP 409
最終状態: {"value": "B の集計結果", "max_token": 26}
```

A の書き込みは、トークン 24 が既に見た 26 より小さいので拒否され、B の結果が残りました。**A は相変わらず自分が持ち主だと思っていますが、書き込み先がそれを認めません。** ロックのサービスを何も変えず、書き込み先に比較を 1 つ足しただけで、壊れ方が変わりました。

トークンが 24 から 26 に 2 つ飛んでいるのは、(3) で見たとおり、A のリースが切れてキーが消えたこと自体が revision を 1 つ使ったからです。トークンに必要なのは**増えること**だけで、連番である必要はありません。

### (7) PostgreSQL: 一意制約と勧告ロック

データベースがすでにあるなら、データベースで済ませる方法もあります。まず、実行記録の表に「ジョブ名と予定時刻」の一意制約を付けます。

```
host-a: INSERT 成功
host-b: ERROR:  duplicate key value violates unique constraint "job_runs_pkey"
host-b: DETAIL:  Key (job, scheduled_for)=(nightly-report, 2026-10-23 18:00:00+00) already exists.
```

これは「無ければ作る」をデータベースの一意制約でやっているもので、**同じ回を 2 度始めない**ことを確実に守れます。ただし、host-a が途中で落ちた回をどう扱うかは、別に決める必要があります。

次に、第 115 回でキーごとの直列化に使った**勧告ロック**を、ここでは「1 人だけ」のために使います。番号 42 について、A がセッション単位のロックを取り、B が取ろうとします。

```
A: pg_try_advisory_lock -> true
B: pg_try_advisory_lock -> false
(A の psql を SIGSTOP して 5 秒待つ)
B: pg_try_advisory_lock -> false
pg_locks: locktype=advisory objid=42 pid=82 granted=true
FATAL:  terminating connection due to administrator command
(A のバックエンドを終了させる)
server closed the connection unexpectedly
	This probably means the server terminated abnormally
	before or while processing the request.
connection to server was lost
B: pg_try_advisory_lock -> true
```

`FATAL` の行と、`server closed` から始まる 4 行は、バックエンドを終了させられた A の psql が出したものです。A のクライアントを止めても、ロックは外れませんでした。第 115 回で見たとおり、セッション単位の勧告ロックは、明示的に外すか**セッションが終わるまで**持たれ続けます（[PostgreSQL 文書](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS)）。期限が無いので、止まった A のせいで B が二重に動くことはありません。その代わり、接続が生きたまま固まった A は、誰かが接続を切るまでロックを握り続けます。接続が切れればサーバが自動で片付けるので、A のプロセスが死んだ場合は外れます。期限の代わりに、**接続の生死**を使っているわけです。第 105 回で見たとおり、transaction モードのプーラーを挟むとセッション単位の勧告ロックは使えません。

## 定時バッチの二重起動をどう防ぐか

ここまでの部品で、最初の問題に戻ります。

| 方法 | 「1 人だけ」を決める場所 | 持ち主が落ちたとき | 止まった持ち主の書き込み |
| --- | --- | --- | --- |
| 一意制約（ジョブ名 + 予定時刻） | データベース | 行は残る。やり直すかどうかは別に決める | 同じ回は 2 度始まらない |
| 勧告ロック（セッション単位） | データベースの接続 | 接続が切れれば外れる | 接続が生きている間は誰も取れない |
| オブジェクトストレージのロックファイル | 条件付き書き込み + 中身の期限 | 期限を過ぎたら奪える | 防げない。書き込み先での検査が要る |
| etcd / Kubernetes Lease | 合意で複製された KV | TTL で切れる | 防げない。revision / resourceVersion で検査 |

選び方の目安を挙げます。

- **データベースが 1 つあるなら、まずデータベースで済ませる。** 一意制約は「同じ回を 2 度始めない」を最も確実に守り、実行の記録としても残る。勧告ロックは期限の問題を持たない
- **リースを使うなら、止まった持ち主が書きに来ることを前提にする。** 書き込み先が版の番号や ETag を検査できるなら、それを使う
- **書き込み先が検査できないもの（メール送信、外部 API）は、ロックだけに頼らない。** 送信ごとに一意のキーを付けて、相手の側で重複を捨ててもらう。これは第 113 回の冪等性キーの考え方そのもの
- **ロックが効率のためだけなら、そこまでしなくてよい。** たまに二重に動いても結果が同じになる処理なら、Redis 1 台の `SET NX PX` で十分なことも多い

<Callout type="tip" title="最初の失敗に、何を足せばよかったか">
  冒頭の売上集計なら、こう組めます。
  まず実行記録の表に「ジョブ名 + 予定時刻」の一意制約を付け、INSERT に成功した方だけが集計を始める。
  集計結果のファイルは、予定時刻を名前に含めて `If-None-Match: *` で書き、2 度目の書き込みが 412 になるようにする。
  取引先へのメールには「ジョブ名 + 予定時刻」から作った冪等性キーを付ける。
  どこか 1 か所が破れても、次の層が二重の結果を止めます。
</Callout>

## まとめ

- 冗長化のために台数を増やすと、何もしなければ全員が動く。求めるのは「動くのは 1 人だけ」と「その 1 人が落ちたら誰かが動ける」の両方
- 確認と書き込みを 1 回にまとめ、書き込み先に判定させる。HTTP の `If-None-Match: *` と `If-Match`（412）、S3（2024 年〜）と GCS の条件付き書き込み、etcd の `Txn`、データベースの version 列はすべて同じ CAS
- 期限の無いロックは、持ち主が落ちると永遠に外れない。だからリース（期限付きロック）と更新。etcd はサーバが期限を測ってキーを消す。オブジェクトストレージには TTL が無いので、期限を中身に書き、自分で判定する
- 期限付きにすると、GC、一時停止、ネットワークの遅れ、時計のずれで、期限切れに気付かない元の持ち主が書き込む。書く直前の確認では防げない
- フェンシングトークンは、ロックのたびに増える番号を書き込み先が検査する仕組み。Chubby の sequencer、etcd の revision、Kubernetes の `resourceVersion`、Raft の任期が同じ役割を持つ
- Redlock をめぐっては、時間の仮定とフェンシングの欠如が論点になった。ロックが効率のためか正しさのためかを先に決める
- リーダー選出はリースの取り合い。Kubernetes の Lease と client-go は、相手の時刻を信用せず自分の時計で変化を測る。既定は 15 秒 / 10 秒 / 2 秒。そして、フェンシングは保証しないと明記している
- 実験では、8 プロセスの同時の「無ければ作る」は 50 回すべてで勝者 1 人。止めたワーカーは再開後に古い結果で上書きし、トークンを検査する書き込み先ではそれが拒否された

ここまでで第 16 章は終わりです。失敗するネットワークの上で、同じ要求をもう一度送ってよいか、仕事をどう並べて渡すか、そしてそれを 1 人だけに実行させるにはどうするかを見てきました。どの回でも、最後に頼りになったのは、書き込み先が 1 回の比較で決着を付けることでした。次の章では、ここまでの部品をほぼすべて使う大きなプログラムである**ブラウザ**の中に入ります。
