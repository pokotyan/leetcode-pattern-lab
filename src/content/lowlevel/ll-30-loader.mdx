## main は最初ではない

C のプログラムは `main` から始まる、と教わります。実際には、`main` が呼ばれるまでに相当なことが起きています。

全体の流れです。

```
シェルが fork する
  └─ 子プロセスが execve("./a.out", argv, envp) を呼ぶ
       └─ カーネル
            ├─ ELF ヘッダを読み、形式を確認する
            ├─ 現在のアドレス空間を捨てる
            ├─ セグメントを新しいアドレス空間にマップする
            ├─ 動的リンカが必要なら、それもマップする
            └─ 動的リンカ（または本体）のエントリポイントにジャンプする
                 └─ 動的リンカ
                      ├─ 必要な共有ライブラリを読み込む
                      ├─ シンボルを解決する
                      ├─ 各ライブラリの初期化処理を実行する
                      └─ 本体の _start へ
                           └─ _start（libc）
                                ├─ libc を初期化する
                                ├─ 環境変数と引数を整える
                                └─ main(argc, argv, envp) を呼ぶ
                                     └─ main が return したら exit() を呼ぶ
```

## execve が何をするか

`execve` は、**現在のプロセスを別のプログラムで上書きする**システムコールです。新しいプロセスは作りません。

```c
execve("/bin/ls", argv, envp);
// 成功した場合、この行には戻ってこない
```

やっていることは、

1. ファイルを開き、先頭を読んで形式を判別する
2. 現在のアドレス空間（text、data、heap、stack すべて）を破棄する
3. 新しいプログラムのセグメントをマップする
4. スタックを作り、そこに `argv` と `envp` を配置する
5. エントリポイントにジャンプする

**ファイルディスクリプタは引き継がれます**（`FD_CLOEXEC` が付いていなければ）。シェルのリダイレクトが機能するのは、この性質によります。第 7 章で詳しく扱います。

<Callout type="note" title="fork と exec が分かれている理由">
  一見、「プロセスを作って別のプログラムを実行する」を 1 つの呼び出しにすればよさそうです。
  Windows の `CreateProcess` はそうなっています。

  Unix が分けているのは、**fork と exec の間に何かをする余地**を作るためです。
  ファイルディスクリプタをつなぎ替える、権限を落とす、環境変数を変える。
  シェルのリダイレクトとパイプは、この隙間で実現されています。

```c
if (fork() == 0) {
    close(1);              // 標準出力を閉じて
    open("out.txt", ...);  // ファイルを開く（fd 1 になる）
    execve("/bin/ls", ...);// ls は何も知らずに fd 1 に書く
}
```
</Callout>

## シェバンもここで処理される

`execve` はファイルの先頭を見て形式を判別します。ELF なら `0x7F ELF`。

先頭が `#!` なら、**スクリプト**として扱われます。

```bash
#!/usr/bin/env python3
```

カーネルは `#!` の後ろを読み取り、そのプログラムを、元のファイル名を引数にして実行します。

```
execve("./script.py", ...)
  → カーネルが #! を見つける
  → 実際には execve("/usr/bin/env", ["env", "python3", "./script.py"], ...) を実行する
```

**シェバンはシェルの機能ではなく、カーネルの機能です。** だから `execve` を直接呼ぶプログラムからでもスクリプトが実行できます。

## 動的リンカの仕事

ELF ヘッダには、`INTERP` というセグメントがあります。動的リンクされたプログラムでは、ここに動的リンカのパスが入っています。

```bash
readelf -l ./a.out | grep -A1 INTERP
#     [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]
```

カーネルは本体ではなく、**まず動的リンカにジャンプします**。動的リンカは通常の共有ライブラリのように見えますが、それ自身は静的リンクされており、自分で自分を再配置できます。

動的リンカの仕事です。

1. `DT_NEEDED` に列挙されたライブラリを読み込む（それらの依存も再帰的に）
2. 各ライブラリを、空いているアドレスにマップする
3. シンボルを解決し、GOT を埋める（Full RELRO なら全部、遅延なら最小限）
4. 各ライブラリの初期化関数（`.init_array`）を呼ぶ
5. 本体のエントリポイントにジャンプする

C++ のグローバルオブジェクトのコンストラクタは、ここ（4 の段階）で実行されます。

<Callout type="warn" title="静的初期化順序の問題">
  異なる翻訳単位にあるグローバルオブジェクトの初期化順序は、**規定されていません**。
  ある翻訳単位のグローバルオブジェクトが、別の翻訳単位のグローバルオブジェクトに依存していると、
  リンク順によって動いたり動かなかったりします。

  対策は、グローバルオブジェクトを使わないか、
  関数内の `static` 変数にして初回アクセス時に初期化させる方法です。
</Callout>

## _start と main

本体のエントリポイントは `main` ではなく `_start` です。

```bash
readelf -h ./a.out | grep Entry
#   Entry point address: 0x1040
nm ./a.out | grep -i ' t _start'
```

`_start` は libc（正確には `crt1.o`）が提供します。やることは、

1. スタックから `argc`、`argv`、`envp` を取り出す
2. libc の初期化（`__libc_start_main`）を呼ぶ
3. その中で、標準入出力のバッファ設定、ロケール、TLS の準備などを行う
4. `main(argc, argv, envp)` を呼ぶ
5. `main` の戻り値を持って `exit()` を呼ぶ

**`main` から `return` すると、`exit()` が呼ばれます。** `exit()` は `atexit` で登録された関数と、グローバルオブジェクトのデストラクタを実行してから、`_exit` システムコールでプロセスを終了させます。

<Callout type="tip" title="_start を自分で書いてみる">
```c
// nostdlib.c
void _start(void) {
    const char msg[] = "hi\n";
    __asm__ volatile ("syscall" :: "a"(1), "D"(1), "S"(msg), "d"(3));
    __asm__ volatile ("syscall" :: "a"(60), "D"(0));
}
```
```bash
gcc -nostdlib -static nostdlib.c -o hi && ./hi
```
  libc なしで、システムコールを直接呼ぶだけのプログラムです。
  **`main` が特別なのは C の規約であって、OS の都合ではない**ことが分かります。
</Callout>

## 起動を観察する

```bash
strace -f ./a.out 2>&1 | head -40
```

`execve` から始まり、`openat` でライブラリを開き、`mmap` でマップし、`mprotect` で権限を設定していく様子が見えます。**プログラム本体の処理に入るまでに、数十回のシステムコールが発生しています。**

```bash
LD_DEBUG=all ./a.out 2>&1 | head -50       # 動的リンカの詳細
LD_DEBUG=statistics ./a.out                 # 解決にかかった時間
```

起動が遅いプログラムでは、ここに原因があることがあります。依存ライブラリが多いほど、解決に時間がかかります。

## まとめ

- `execve` は現在のプロセスを別のプログラムで上書きする
- `fork` と `exec` が分かれているから、その隙間でリダイレクトができる
- シェバン（`#!`）はカーネルが解釈する
- 動的リンクされたプログラムでは、まず動的リンカに制御が渡る
- 動的リンカがライブラリを読み込み、シンボルを解決し、初期化を実行する
- `_start` は libc のもの。`main` は C の規約であって OS の都合ではない
- `strace` と `LD_DEBUG` で起動の過程を観察できる

次は、関数を呼ぶときの取り決めを見ます。ここが分かると、逆アセンブルが読めるようになります。
