第 120 回で見たとおり、OAuth 2.0 は**委任**の仕組みです。利用者が「このアプリに、私の予定表を読むことを許す」と決め、その結果としてアプリはアクセストークンを受け取ります。

では、「Google でログイン」ボタンは何をしているのでしょうか。アプリが知りたいのは予定表の中身ではなく、**いまブラウザの前にいるのが誰か**です。OAuth のアクセストークンを受け取った時点で、それは分かったことになるのでしょうか。

答えは「分からない」です。この回では、その欠けていた部分を OpenID Connect（以下 OIDC）がどう埋めたのかを、部品ごとに見ていきます。

## OAuth だけでログインを作ると何が欠けるか

アクセストークンは、**リソースサーバ（API）に見せるための札**です。受け取ったクライアントが中身を読むことは想定されていません（第 120 回で見たとおり、形式すら規定されていません）。OAuth の解説サイトは、この点を最初に断っています。「OAuth 2.0 is not an authentication protocol.」（[oauth.net: End User Authentication with OAuth 2.0](https://oauth.net/articles/authentication/)）。

それでも OAuth だけで「ログイン」を作ろうとすると、よくある形はこうなります。

```
クライアント                     認可サーバ / API
    |  アクセストークンを受け取る         |
    |---- GET /me  (Bearer AT) --------->|
    |<--- { "id": "12345", ... } --------|
    |  「id=12345 がログインした」と判断   |
```

これには 2 つの穴があります。

**1. そのトークンが自分宛てに発行されたか分からない。** `/me` は、トークンが有効なら誰が持ってきても答えます。攻撃者が自分の作った別のアプリに被害者をログインさせ、そこで得たアクセストークンを、正規のアプリのログイン処理に差し出したとします。正規のアプリは `/me` を呼び、被害者の ID を得て、攻撃者を被害者としてログインさせてしまいます。自分に向けられたのではない権限で動かされるので、**混乱した代理人（confused deputy）** と呼ばれる型の攻撃です（[oauth.net](https://oauth.net/articles/authentication/) の「Injection of access tokens」「Lack of audience restriction」）。

**2. その流れの中で利用者が本当に認証されたか分からない。** アクセストークンは、利用者がその場にいなくてもリフレッシュトークンで作り直せます。持っていることは「かつて誰かが委任した」ことしか意味しません。

RFC 9700（OAuth 2.0 Security BCP、2025 年 1 月）も、この種の差し込みは「純粋な OAuth のフローでは検出する方法がない」と書いています（[RFC 9700 4.6.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.6.1)）。

<Callout type="warn" title="よくある誤解: アクセストークンを取れたら、ログインできた">
  アクセストークンは「API を呼んでよい」という札で、**宛先は API**です。クライアントは、それが自分に宛てて発行されたのか、別のアプリに発行されたものを持ち込まれたのかを見分けられません。
  この誤解が生まれるのは、「ログインしないとトークンはもらえない」という一方向の事実を、逆向きに「トークンがある、だからログインした」と読んでしまうからです。
  ログインの判定には、**クライアント自身に宛てた、署名付きの認証結果**が要ります。それが ID トークンです。
</Callout>

## OIDC が足したもの

OIDC は OAuth を置き換えるのではなく、**OAuth のフローの上に、認証の結果を運ぶ部品をいくつか足した**ものです。中心は OpenID Connect Core 1.0 で、現行版は errata set 2（2023 年 12 月）です（[OpenID Connect Core 1.0](https://openid.net/specs/openid-connect-core-1_0.html)）。2024 年には同じ内容が ISO/IEC 26131:2024 として国際規格にもなりました（[ISO](https://www.iso.org/standard/89056.html)）。

| 足したもの | 役割 |
| --- | --- |
| `openid` スコープ | 「これは OIDC の要求だ」という印。OIDC の要求は必ず含む（MUST。[Core 3.1.2.1](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)） |
| ID トークン | 誰が、いつ、どの IdP で認証され、**どのクライアントに宛てて**発行されたかを書いた JWT |
| `nonce` | 認可リクエストと ID トークンを 1 対 1 に結ぶ使い捨ての値 |
| `at_hash` | 一緒に発行されたアクセストークンのハッシュ。トークンの組を結ぶ |
| UserInfo エンドポイント | アクセストークンで利用者の属性を引く API |
| Discovery | IdP の設定を `/.well-known/openid-configuration` で公開する |
| JWKS | ID トークンを検証する公開鍵の一覧（第 119 回） |

OIDC の用語では、認可サーバを **OP**（OpenID Provider）、クライアントを **RP**（Relying Party、認証結果を信頼する側）と呼びます。この回では IdP と RP という呼び方も混ぜて使います。

ここで、この章までの部品がどう組み合わさっているかを並べておきます。**OIDC 単体では何も保証できず、下の部品が揃って初めてログインになります。**

| 部品 | どこで見たか | OIDC の中での役目 |
| --- | --- | --- |
| OAuth のコードフロー + PKCE | 第 120 回 | ブラウザを経由して、IdP から RP に結果を渡す道 |
| JWT（JWS） | 第 119 回 | ID トークンの形式 |
| 署名（RS256 / ES256） | 第 106 回 | ID トークンが IdP の出したものであることの保証 |
| JWK / JWKS | 第 107 回、第 119 回 | 署名を確かめる公開鍵をどう手に入れるか |
| TLS と証明書 | 第 17 章 | Discovery と JWKS を取りに行く先が本物の IdP であること |
| ハッシュ | 第 103 回 | PKCE の `S256`、`at_hash` |
| セッションと Cookie | 第 118 回 | ID トークンを確かめた後、RP 自身のログイン状態を保つ |

最後の行は見落とされがちです。**ID トークンはログインの「証拠」であって、ログイン状態そのものではありません。** RP は ID トークンを確かめたら、自分のセッションを作り、以後は Cookie で利用者を識別します。

## 手元で: Keycloak を立てる

ここからは、オープンソースの IdP である Keycloak を Docker で動かし、curl だけでログインの流れを通します。公式の手順と同じく、開発用の `start-dev` で起動します（[Keycloak: Getting started with Docker](https://www.keycloak.org/getting-started/getting-started-docker)）。

```
$ docker run -d --name kc-ll103 -p 18103:8080 \
    -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
    quay.io/keycloak/keycloak:latest start-dev
$ docker logs kc-ll103 | tail -1
... Keycloak 26.7.4 on JVM (powered by Quarkus 3.33.3.2) started in 16.675s. Listening on: http://0.0.0.0:8080
```

管理 API で、realm（IdP の中の独立した区画）`demo`、機密クライアント `webapp`、利用者 `alice` を作ります。

```
$ T=$(curl -s -d grant_type=password -d client_id=admin-cli -d username=admin -d password=admin \
      http://localhost:18103/realms/master/protocol/openid-connect/token | jq -r .access_token)
$ curl -H "Authorization: Bearer $T" -H 'Content-Type: application/json' \
    http://localhost:18103/admin/realms -d '{"realm":"demo","enabled":true}'
$ curl ... /admin/realms/demo/clients -d '{"clientId":"webapp","secret":"s3cret",
    "redirectUris":["http://localhost:9999/callback"],
    "attributes":{"pkce.code.challenge.method":"S256"}}'
$ curl ... /admin/realms/demo/users -d '{"username":"alice","email":"alice@example.com",
    "emailVerified":true,"firstName":"Alice","lastName":"Liddell","enabled":true,
    "credentials":[{"type":"password","value":"alice-pass","temporary":false}]}'
```

`pkce.code.challenge.method` を `S256` にすると、このクライアントは PKCE なしの要求を受け付けなくなります。`localhost:9999` には何も待ち受けていません。ブラウザの代わりに curl でリダイレクト先の URL を読むだけなので、それで足ります。

## Discovery を読む

RP が最初にするのは、IdP の設定を読むことです。**発行者識別子（issuer）** の URL の後ろに `/.well-known/openid-configuration` を付けて取ります。

```
$ curl -s http://localhost:18103/realms/demo/.well-known/openid-configuration | jq
issuer                  "http://localhost:18103/realms/demo"
authorization_endpoint  ".../realms/demo/protocol/openid-connect/auth"
token_endpoint          ".../realms/demo/protocol/openid-connect/token"
userinfo_endpoint       ".../realms/demo/protocol/openid-connect/userinfo"
jwks_uri                ".../realms/demo/protocol/openid-connect/certs"
id_token_signing_alg_values_supported ["PS384","RS384","EdDSA","ES384","HS256",...,"RS256",...]
code_challenge_methods_supported      ["plain","S256"]
response_types_supported ["code","none","id_token","token","id_token token","code id_token",...]
```

（抜粋。実物は 56 項目ありました）

Discovery の仕様は、**返ってきた `issuer` が、取りに行った URL の前半と完全に一致しなければならず、ID トークンの `iss` とも一致しなければならない**と定めています（[OpenID Connect Discovery 1.0 4.3](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderConfigurationValidation)）。これで「設定文書を取った先」と「トークンを出した者」が同じだと言えます。その前提は、TLS でこの URL の持ち主を確かめられることです（第 110 回）。この回の手元の例は HTTP ですが、本番では必ず HTTPS です。

`jwks_uri` の先には公開鍵が並びます。

```
$ curl -s http://localhost:18103/realms/demo/protocol/openid-connect/certs | jq '.keys[] | {kid,kty,alg,use}'
{ "kid": "i6OZQ-BFYPxzXvxk_65cJ0JDH1YgPN6QaYQYLKlY6Ao", "kty": "RSA", "alg": "RS256",    "use": "sig" }
{ "kid": "uoUsQoFXufMQNdw39SJA3tT6jpYiwxdbnNlbSVBWM5w", "kty": "RSA", "alg": "RSA-OAEP", "use": "enc" }
```

署名用（`use: sig`）と暗号化用（`use: enc`）の鍵が別にあります。第 107 回で見た JWK の形そのものです。

比べるために、公開されている IdP の Discovery も見ておきます。

```
$ curl -s https://accounts.google.com/.well-known/openid-configuration | jq
issuer                                "https://accounts.google.com"
jwks_uri                              "https://www.googleapis.com/oauth2/v3/certs"
id_token_signing_alg_values_supported ["RS256"]
```

項目の名前は同じです。**RP のライブラリが「issuer の URL を 1 つ設定するだけ」で動くのは、この文書があるから**です。

<Callout type="note" title="対応していることと、使ってよいことは別">
  Keycloak も Google も、`response_types_supported` に `token` や `id_token token`（トークンをリダイレクトの URL に載せて返す implicit フロー）を並べています。
  しかし RFC 9700 は、implicit フローを使わないよう求めています（SHOULD NOT。[RFC 9700 2.1.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.2)）。
  Discovery の一覧は「この IdP が話せること」で、推奨ではありません。**基本は認可コードフロー + PKCE** です。
</Callout>

## curl だけでコードフロー + PKCE を通す

第 120 回で見た認可コードフローに、OIDC の `openid` スコープと `nonce` を足します。作業ファイルの `flow.sh` の要点です。

```bash
KC=http://localhost:18103/realms/demo/protocol/openid-connect
REDIRECT=http://localhost:9999/callback
VERIFIER=$(openssl rand -base64 48 | tr '+/' '-_' | tr -d '=\n')
CHALLENGE=$(printf %s "$VERIFIER" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')
STATE=$(openssl rand -hex 16); NONCE=$(openssl rand -hex 16)

# 1. 認可リクエスト（ブラウザが開く URL）。ログイン画面の HTML が返る
AUTHZ="$KC/auth?response_type=code&client_id=webapp&redirect_uri=$REDIRECT\
&scope=openid%20email%20profile&state=$STATE&nonce=$NONCE\
&code_challenge=$CHALLENGE&code_challenge_method=S256"
PAGE=$(curl -s -c jar.txt -b jar.txt "$AUTHZ")
ACTION=$(... フォームの action 属性を取り出す ...)

# 2. 利用者がパスワードを入れて送信する。IdP は 302 で RP に戻す
LOC=$(curl -s -c jar.txt -b jar.txt -o /dev/null -w '%{redirect_url}' \
        -d username=alice -d password=alice-pass "$ACTION")

# 3. RP のサーバがトークンエンドポイントで code を交換する
curl -s -u webapp:s3cret -d grant_type=authorization_code -d code="$CODE" \
     -d redirect_uri=$REDIRECT -d code_verifier="$VERIFIER" $KC/token > tokens.json
```

実行すると、手順 2 のリダイレクト先はこうなりました。

```
redirect: http://localhost:9999/callback?state=865c10db6561d4e6e447eba9fec15a1b
          &session_state=3hIZ5Mc9Jp555W4gBQeIHK6s
          &iss=http%3A%2F%2Flocalhost%3A18103%2Frealms%2Fdemo
          &code=f8393284-dc3e-52f9-8d2a-2e01abeadbc0.3hIZ5Mc9...
state ok
```

`state` は送った値と一致しています。`iss` が付いているのは RFC 9207（2022）の仕組みで、RP が複数の IdP を使うとき、**どの IdP から戻ってきた応答か**を取り違えないためのものです（[RFC 9207](https://www.rfc-editor.org/rfc/rfc9207.html)）。

手順 3 の応答には、アクセストークンと並んで `id_token` が入っています。

```
{ "access_token": "eyJhbGciOiJSUzI1NiIs...", "expires_in": 300,
  "refresh_token": "eyJhbGciOiJIUzUxMiIs...", "token_type": "Bearer",
  "id_token": "eyJhbGciOiJSUzI1NiIs...", "scope": "openid profile email", ... }
```

PKCE が効いていることも確かめておきます。同じ流れで `code_verifier` だけを変えると、交換は拒まれます。

```
code_verifier が違う  → {"error":"invalid_grant","error_description":"PKCE verification failed: Code mismatch"}
code_verifier が無い  → {"error":"invalid_grant","error_description":"PKCE code verifier not specified"}
```

## ID トークンの中身

第 119 回と同じく、ピリオドで区切って Base64URL を戻せば中身が読めます。**ID トークンも署名されているだけで、暗号化されていません。**

```
header:  {"alg": "RS256", "typ": "JWT", "kid": "i6OZQ-BFYPxzXvxk_65cJ0JDH1YgPN6QaYQYLKlY6Ao"}
payload: {
 "exp": 1790592594, "iat": 1790592294, "auth_time": 1790592293,
 "iss": "http://localhost:18103/realms/demo",
 "aud": "webapp",
 "sub": "5fb1bf7c-5146-49bd-b5fe-9cd8b254e592",
 "typ": "ID",
 "azp": "webapp",
 "nonce": "b9a1d6045569300147d3c583563b4f53",
 "sid": "3hIZ5Mc9Jp555W4gBQeIHK6s",
 "at_hash": "U6wOFA7h05XgCn74zGe0tQ",
 "acr": "1",
 "email_verified": true, "name": "Alice Liddell", "preferred_username": "alice",
 "email": "alice@example.com", ...
}
```

`kid` は、さきほど JWKS に並んでいた署名用の鍵と同じです。主なクレームの意味は次のとおりです（[Core 2](https://openid.net/specs/openid-connect-core-1_0.html#IDToken)）。

| クレーム | 意味 |
| --- | --- |
| `iss` | 発行した IdP。Discovery の `issuer` と一致する |
| `sub` | その IdP の中で利用者を指す識別子。**使い回されない** |
| `aud` | **宛先のクライアント**。ここでは `webapp` |
| `exp` / `iat` | 有効期限と発行時刻（ここでは 300 秒） |
| `auth_time` | 利用者が実際に認証した時刻 |
| `nonce` | 認可リクエストで RP が送った値がそのまま入る |
| `at_hash` | 同時に発行されたアクセストークンのハッシュの左半分 |
| `acr` | 認証の強さの区分（第 122 回のステップアップ認証で使う） |
| `azp` | 発行を受けたクライアント。仕様は拡張を使わない限り気にしなくてよいとしている |

`typ: "ID"` と `sid` は Keycloak が独自に足したものです。

## ID トークンとアクセストークンは宛先が違う

同じ応答に入っていたアクセストークンも、Keycloak では JWT です。並べると違いがはっきりします。

```
access_token payload: {
 "iss": "http://localhost:18103/realms/demo",
 "aud": "account",
 "sub": "5fb1bf7c-5146-49bd-b5fe-9cd8b254e592",
 "typ": "Bearer",
 "azp": "webapp",
 "scope": "openid profile email",
 "realm_access": { "roles": ["offline_access", "default-roles-demo", "uma_authorization"] },
 ...
}
```

`aud` が `webapp` ではなく `account`（Keycloak の利用者向け API）になっています。**アクセストークンは API に宛てたもの、ID トークンはクライアントに宛てたもの**です。

| | ID トークン | アクセストークン |
| --- | --- | --- |
| 宛先（`aud`） | RP（クライアント自身） | リソースサーバ（API） |
| 読むのは | RP | API。RP は中身を読まない前提 |
| 伝えること | 誰が、いつ、どう認証されたか | 何をしてよいか（スコープ、委任された権限） |
| 形式 | 必ず JWT | 規定なし（不透明な文字列でも JWT でもよい） |
| 送る先 | どこにも送らない | API の `Authorization: Bearer` |

<Callout type="warn" title="よくある誤解: ID トークンを API に送ればよい">
  ID トークンは JWT で、署名があり、`sub` も入っています。API に送れば「誰のリクエストか」を確かめられそうに見えるので、この誤解はよく起きます。
  しかし ID トークンの `aud` は RP で、API ではありません。**API が「自分宛てではないトークン」を受け付ける**ようになると、同じ IdP を使う別のアプリの ID トークンでも API が通ってしまいます。
  また ID トークンにはスコープがなく、何を許すかの情報もありません。API には、その API を宛先にしたアクセストークンを送ります。
</Callout>

Keycloak はこの区別を強制しています。UserInfo に ID トークンを差し出すと拒まれ、サーバのログには理由が残ります。

```
$ curl -si -H "Authorization: Bearer $ID_TOKEN" .../userinfo
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="demo", error="invalid_token", error_description="Token verification failed"

(docker logs) reason="Token type is incorrect. Expected '[Bearer, DPoP]' but was 'ID'"
```

## 手元で: ID トークンを検証する

検証の手順は Core 3.1.3.7 に番号付きで並んでいます。コードフローで使う主なものは、**`iss` が一致する、`aud` に自分の `client_id` が入っている、決めたアルゴリズムで署名を確かめる、`exp` が過ぎていない、送った `nonce` と一致する**、です（[Core 3.1.3.7](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)）。第 119 回の手順に、`nonce` が加わった形です。

作業ディレクトリの venv に PyJWT 2.15.0 と cryptography を入れ、次のように書きました（`verify.py` の要点）。

```python
disco = requests.get(ISS + "/.well-known/openid-configuration").json()
assert disco["issuer"] == ISS
jwks = jwt.PyJWKClient(disco["jwks_uri"])
key = jwks.get_signing_key_from_jwt(tok["id_token"])       # kid で JWKS から鍵を選ぶ
claims = jwt.decode(tok["id_token"], key, algorithms=["RS256"],
                    audience="webapp", issuer=ISS, leeway=30)
assert claims["nonce"] == nonce, "nonce mismatch"

digest = hashlib.sha256(tok["access_token"].encode("ascii")).digest()
at_hash = base64.urlsafe_b64encode(digest[:16]).rstrip(b"=").decode()
print("user =", (claims["iss"], claims["sub"]))
```

`algorithms` を固定し、`aud` と `iss` を必ず渡すのが第 119 回の教訓です。`leeway=30` は時計のずれ（第 149 回）の許容です。

```
at_hash expected U6wOFA7h05XgCn74zGe0tQ got U6wOFA7h05XgCn74zGe0tQ True
user = ('http://localhost:18103/realms/demo', '5fb1bf7c-5146-49bd-b5fe-9cd8b254e592')
aud=other-api            -> InvalidAudienceError Audience doesn't match
iss=evil                 -> InvalidIssuerError Invalid issuer
access_token as id_token -> InvalidAudienceError Audience doesn't match
nonce を別の値にすると      -> AssertionError: nonce mismatch
```

最後から 2 行目は、アクセストークンを ID トークンとして検証させた結果です。**署名は同じ鍵で正しく付いているのに、`aud` で落ちます。** 署名の検証だけで済ませると、ここを通してしまいます。

`at_hash` は、アクセストークンを ID トークンの `alg` に対応するハッシュ（RS256 なら SHA-256）にかけ、その左半分（ここでは 16 バイト）を Base64URL にしたものです（[Core 3.1.3.6](https://openid.net/specs/openid-connect-core-1_0.html#CodeIDToken)）。ブラウザを経由してトークンが届く流れでは、アクセストークンの差し替えを見抜くために使います（[RFC 9700 4.6.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.6.1)）。コードフローでは、トークンは RP のサーバが直接受け取るので、確かめるかどうかは任意（MAY）です（[Core 3.1.3.8](https://openid.net/specs/openid-connect-core-1_0.html#CodeFlowTokenValidation)）。

## state、nonce、PKCE は何を防ぐのか

似た使い捨ての値が 3 つ出てきました。どれも「**この応答は、このブラウザで始めた、この要求への応答か**」を確かめるためのものですが、確かめる場所が違います。

| 値 | 誰が作る | どこで照合する | 主に防ぐもの |
| --- | --- | --- | --- |
| `state` | RP | リダイレクトで戻ってきたとき、RP が | 攻撃者の応答を踏ませる CSRF |
| `code_challenge` / `code_verifier` | RP | トークンエンドポイントで、IdP が | 盗んだ code を別の場所で使うこと、code の差し込み |
| `nonce` | RP | ID トークンを受け取った後、RP が | ID トークンの使い回し、code の差し込み |

RFC 9700 は、PKCE をサポートする IdP なら PKCE を CSRF 対策にしてよいとし、OIDC では `nonce` も CSRF 対策になると書いています。また、機密クライアントの OIDC なら、条件付きで PKCE の代わりに `nonce` を使ってよいとしています（[RFC 9700 2.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1)、[2.1.1](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.1.1)）。ただしどちらを使う場合も、**値は要求ごとに作り、始めたブラウザに結びつける**ことが前提です。`nonce` による防御は、**ID トークンの `nonce` を確かめ終わるまで、発行されたトークンを何も使わない**ときにだけ効きます（[RFC 9700 4.5.3.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.5.3.2)）。

`nonce` の必須かどうかはフローで違い、コードフローでは任意、implicit フローでは必須です（[Core 3.1.2.1](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest)、[3.2.2.1](https://openid.net/specs/openid-connect-core-1_0.html#ImplicitAuthRequest)）。任意でも、付けて確かめない理由はありません。

code そのものの使い回しも試しておきます。同じ code でもう一度トークンを取りに行くと、拒まれるだけでは済みませんでした。

```
== userinfo（1 回目の交換で得たアクセストークン）
{"sub":"5fb1bf7c-...","email_verified":true,"name":"Alice Liddell",...}
== 同じ code を 2 回目
{"error":"invalid_grant","error_description":"Code not valid"}
== userinfo（同じアクセストークンで再度）
WWW-Authenticate: Bearer realm="demo", error="invalid_token", error_description="user_session_not_found"
```

2 回目の交換で、**1 回目に発行したトークンまで使えなくなっています。** RFC 6749 は、code が 2 回使われたら拒否しなければならず、その code から発行したトークンも可能なら取り消すべきだと定めています（[RFC 6749 4.1.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2)）。2 回目が来たということは、どちらかが盗まれた code だからです。

## UserInfo と、ID トークンとの照合

UserInfo は、アクセストークンを見せて利用者の属性を引く API です。

```
$ curl -s -H "Authorization: Bearer $ACCESS_TOKEN" .../userinfo
{"sub":"5fb1bf7c-5146-49bd-b5fe-9cd8b254e592","email_verified":true,"name":"Alice Liddell",
 "preferred_username":"alice","given_name":"Alice","family_name":"Liddell","email":"alice@example.com"}
```

ここで大事なのは、UserInfo は**アクセストークンで呼ぶ普通の OAuth の API** だということです。つまり、先に見た「OAuth だけでログイン」と同じ弱さを抱えています。そのため Core は、**UserInfo の `sub` が ID トークンの `sub` と完全に一致することを確かめ、一致しなければ応答を使ってはならない**と定めています（[Core 5.3.2](https://openid.net/specs/openid-connect-core-1_0.html#UserInfoResponse)）。理由として挙げているのが、トークンを別のセッションのものと入れ替える**トークンの差し替え**（Token Substitution、[Core 16.11](https://openid.net/specs/openid-connect-core-1_0.html#TokenSubstitution)）です。

**ログインの判定の根拠は ID トークンで、UserInfo はその補足**です。順序を逆にすると、OAuth だけのログインに戻ってしまいます。

## 利用者を指すのは iss と sub の組

ID トークンには `email` も `preferred_username` も入っています。RP のデータベースで利用者を探すとき、どれを鍵にすればよいのでしょうか。

Core 5.7 の答えははっきりしています。**安定した識別子として頼ってよいのは `iss` と `sub` の組だけ**です。IdP は同じ email を時期を変えて別の利用者に割り当ててよく、利用者の email は変わりうる。だから `email`、`phone_number`、`preferred_username`、`name` を一意な識別子に使ってはならない（MUST NOT）、と書いています（[Core 5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)）。

```
RP の利用者テーブル（よい例）
  iss                                  sub                                    user_id
  http://localhost:18103/realms/demo   5fb1bf7c-5146-49bd-b5fe-9cd8b254e592   42
  https://accounts.google.com          1098...                                42
```

`sub` は「その IdP の中で」一意なだけなので、**必ず `iss` と組にします**。IdP が 2 つあれば、偶然同じ `sub` が現れても別人です。

<Callout type="warn" title="よくある誤解: email は一意だから、email で利用者を紐付ければよい">
  社内の常識では email は 1 人に 1 つなので、鍵にしたくなります。しかし RP が受け取る email は、**その IdP が「この人の email はこれだ」と言っている値**にすぎません。
  利用者が自分で自由に email を設定できる IdP や、検証していない email を返す IdP があれば、他人の email を名乗って、その人の既存アカウントに入り込めます。
  `email_verified` が `true` でも、それは「その IdP が確かめた」という意味で、別の IdP のアカウントと同一人物だという保証ではありません。複数の IdP をまたぐ突き合わせの事故は、第 125 回で詳しく見ます。
</Callout>

## OIDC が保証しないもの

最後に、OIDC の範囲の外にあるものを確かめておきます。

- **何をしてよいか。** ID トークンは「誰か」を伝えるだけです。その人に何を許すかは、RP 自身の認可の仕組みです（第 123 回）
- **RP のログイン状態。** ID トークンの `exp` は 300 秒でしたが、RP のセッションはそれとは別に RP が決めます。IdP でログアウトしても、RP のセッションは自動的には消えません（第 124 回）
- **IdP そのものの正しさ。** RP は IdP を信頼する前提です。署名鍵が漏れれば、偽の ID トークンが検証を通ります。鍵の管理とローテーションは第 127 回で見ます
- **TLS の代わり。** Discovery と JWKS の取得先が偽物なら、偽の鍵で検証してしまいます。署名の検証は、鍵の入手経路が安全であって初めて意味を持ちます

## まとめ

- OAuth のアクセストークンは API に宛てた札で、クライアントはそれが自分宛てかを見分けられない。OAuth だけでログインを作ると、他のアプリのトークンを持ち込まれる（混乱した代理人）
- OIDC は OAuth の上に、`openid` スコープ、ID トークン、`nonce`、`at_hash`、UserInfo、Discovery を足した。署名は第 106 回、形式は第 119 回の JWT、鍵は JWKS、取得経路は TLS に頼る
- ID トークンの `aud` は RP、アクセストークンの `aud` は API。**ID トークンは API に送らない。アクセストークンでログインを判断しない**
- ID トークンの検証は、アルゴリズムを固定して署名、`iss`、`aud`、`exp`、`nonce`。署名が正しくても `aud` で落ちるトークンがある
- `state` は RP が戻りで、PKCE は IdP がトークンエンドポイントで、`nonce` は RP が ID トークンで照合する。いずれも要求ごとに作り、ブラウザに結びつける
- code を 2 回使うと拒否され、Keycloak は 1 回目に発行したトークンも取り消した（RFC 6749 4.1.2）
- UserInfo の `sub` は ID トークンの `sub` と照合する。利用者の識別子は `iss` と `sub` の組で、email ではない
- 基本のフローは認可コード + PKCE。Discovery に implicit が並んでいても、推奨ではない

RP は ID トークンで「誰か」を知り、API にはアクセストークンを送るようになりました。次の第 122 回では、そのアクセストークンを受け取った API の側が、何を確かめなければならないかを見ます。
