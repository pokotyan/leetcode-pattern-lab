## ページの中の、もう 1 つの窓

`<img>` は画像を 1 枚、`<script>` はコードを 1 本、ページに取り込みます。取り込まれたものは、ページの一部として扱われます。

`<iframe>` は違います。iframe の中には**別の文書**が読み込まれ、その文書は自分の `Window` を持ち、自分のオリジンを持ち、自分の履歴を持ち、別のサイトであれば別のプロセスで動きます。iframe は部品を取り込む仕組みではなく、**ページの中にもう 1 つのブラウザの窓を開く**仕組みです。

この章では、iframe に関わる部品をすでに多く見てきました。ただ、どれも別々の回に分かれています。

- 第 87 回: 別のサイトの iframe は、別のプロセスで描かれる
- 第 94 回、第 95 回: 別のオリジンの iframe の DOM は読めない。`sandbox` を付けるとオリジンが `null` になる。`postMessage` で境界を越える
- 第 97 回、第 98 回: iframe の中の Cookie は第三者の Cookie になり、ストレージはトップレベルのサイトごとに分けられる
- 第 100 回: `frame-ancestors` で、自分のページを他人の iframe に入れさせない
- 第 101 回: 分離したページは、iframe の中の文書にも COEP を求める

この回では、これらを **1 つの iframe に掛かる問い**として並べ直します。あわせて、これまでの回で扱わなかった問い（中の文書のオリジンが URL だけでは決まらないこと、フレームどうしの移動の規則、埋め込む側の CSP、遅延読み込み、Fenced Frames）を手元で確かめます。

## 1 つの iframe に掛かる問い

```
 トップレベルの文書  https://news.example/          ← 親
 ┌─────────────────────────────────────────────┐
 │  <iframe src="https://widget.example/chat"   │
 │          sandbox="..." allow="...">          │
 │  ┌───────────────────────────────────────┐   │
 │  │ 中の文書  https://widget.example/chat  │   │ ← 子
 │  │   自分の Window、オリジン、履歴、       │   │
 │  │   Cookie の文脈、（別サイトなら）プロセス │   │
 │  └───────────────────────────────────────┘   │
 └─────────────────────────────────────────────┘
```

| 問い | 決める者 | 使う物差し | 仕組み | 回 |
| --- | --- | --- | --- | --- |
| 中の文書のオリジンは何か | ブラウザ（URL と属性から） | オリジン | `src`、`srcdoc`、`sandbox` | 第 94 回、この回 |
| 親と子は互いに何を読めるか | ブラウザ | オリジン | 同一オリジンポリシー、`postMessage` | 第 94 回、第 95 回 |
| この iframe を置いてよいか | 親 | URL | CSP の `frame-src` | この回 |
| このページを埋め込ませてよいか | 子 | 祖先のオリジン | `frame-ancestors`、`X-Frame-Options` | 第 100 回 |
| 中のページに何を許すか | 親 | — | `sandbox`、`allow`、`credentialless` | 第 95 回、第 100 回、第 101 回 |
| 誰が誰を移動させられるか | ブラウザ | オリジンと利用者の操作 | フレームのナビゲーションの規則 | この回 |
| 読み込みの要求に何が付くか | ブラウザ | サイト | Cookie、`Sec-Fetch-*`、`Referer` | 第 97 回、第 99 回 |
| 中の状態はどこに保存されるか | ブラウザ | トップレベルのサイト | ストレージの分割、CHIPS、Storage Access API | 第 97 回 |
| どのプロセスで動くか | ブラウザ | サイト | サイト分離、COEP | 第 87 回、第 101 回 |

表の 3 行目と 4 行目に注目してください。iframe には**置く側と置かれる側の 2 者がいて、どちらも拒否できる**ことが、iframe を扱う仕組みの多くに共通する形です。

## 手元の環境

Python の `http.server` に、受け取った要求のヘッダを記録する処理を足したサーバを 127.0.0.1 の 18301 番と 18302 番で立て、Playwright から手元にインストールされた Chrome 154 をヘッドレスで、毎回まっさらな一時プロファイルで動かしました。

ホスト名には `top.localhost`、`widget.localhost`、`other.localhost`、`evil.localhost` を使いました。Chrome は `*.localhost` をループバックに解決し、**安全な文脈**（secure context）として扱うので、HTTP のままでも `Sec-Fetch-*` のヘッダが送られます。`localhost` は Public Suffix List に無いので、第 94 回の規則どおり最後のラベルが公開接尾辞とみなされ、`top.localhost` と `widget.localhost` は**別のサイト**になります。実際に、後で見る `Sec-Fetch-Site` は `cross-site` でした。

## 中の文書のオリジンは、URL だけでは決まらない

`top.localhost:18301` のページに、さまざまな作り方の iframe を入れ、中の文書の `self.origin` と、親から中の DOM を読めるか、中で `localStorage` を使えるかを調べました。

```
作り方                                       中の self.origin          location          親から DOM   localStorage
src= 別のサイト                              http://widget.localhost:18301   …/report.html  SecurityError  ok
src= 同じサイトの別ポート                     http://top.localhost:18302      …/report.html  SecurityError  ok
src= 同じオリジン                             http://top.localhost:18301      …/report.html  読める         ok
src なし（about:blank）                       http://top.localhost:18301      about:blank    読める         ok
srcdoc                                       http://top.localhost:18301      about:srcdoc   読める         ok
srcdoc ＋ sandbox="allow-scripts"            null                            about:srcdoc   SecurityError  SecurityError
src= 同じオリジン ＋ sandbox="allow-scripts"  null                            …/report.html  SecurityError  SecurityError
src= data: の URL                            null                            data:text/…    SecurityError  SecurityError
src= 親が作った blob: の URL                  http://top.localhost:18301      blob:http://…  読める         ok
```

上の 3 行は第 94 回で見たとおりで、オリジンは URL のスキーム・ホスト・ポートで決まります。残りの行は、**URL を見てもオリジンが分からない**例です。

HTML Standard は、新しい文書のオリジンを次の順で決めます（[HTML Standard: determining the origin](https://html.spec.whatwg.org/#determining-the-origin)）。

1. sandbox のフラグ（オリジンを分けるもの）が立っていれば、**新しい不透明なオリジン**
2. URL が `about:srcdoc` なら、**作った側のオリジン**
3. URL が `about:blank` で、作った側のオリジンがあれば、**作った側のオリジン**
4. それ以外は URL のオリジン

1 番めが先頭にあるので、同じオリジンの `src` でも、`srcdoc` でも、`sandbox` を付ければ `null` になります。`data:` の URL は 4 番めに当たり、`data:` の URL のオリジンは不透明なので `null` です。`blob:` の URL は、作った文書のオリジンを URL の中に持っているので、4 番めで作った側のオリジンになります。

### srcdoc は「別の文書」だが「別のオリジン」ではない

`srcdoc` は、HTML を属性に直接書いて iframe に表示する仕組みです。中身は別の文書として解析されるので、外側のページの CSS は効かず、外側の DOM の一部にもなりません。見た目は分離されています。

しかしオリジンは親と同じです。上の実験でも、`srcdoc` の中の文書は `http://top.localhost:18301` を名乗り、親からも中からも互いの DOM を読めました。中で動くスクリプトは、親の `document.cookie`（HttpOnly でないもの）にも、親と同じ `localStorage` にも触れます。

<Callout type="warn" title="よくある誤解: 「利用者の HTML は srcdoc に入れれば隔離できる」">
  `srcdoc` だけでは、利用者が書いた `<script>` が**自分のオリジンで**動きます。XSS（第 100 回）をそのまま招き入れる形です。
  HTML Standard は、ブログのコメント欄の例で `<iframe sandbox srcdoc="...">` と、**`sandbox` を組み合わせて**使う形を示しています（[HTML Standard: an iframe srcdoc document](https://html.spec.whatwg.org/#an-iframe-srcdoc-document)）。
  スクリプトを動かす必要があるなら `sandbox="allow-scripts"` までにとどめ、`allow-same-origin` は付けません。第 95 回で見たとおり、同じオリジンの内容に `allow-scripts` と `allow-same-origin` を両方付けると、中から `sandbox` を外せます。より強く分けたいなら、第 104 回の「サンドボックス用のドメイン」のように、**別のサイトから配信**します。
</Callout>

### about:blank は作った側を引き継ぐ

`src` を付けずに作った iframe や、`window.open()` で URL を指定せずに開いた窓は、`about:blank` の文書を持ち、作った側のオリジンを引き継ぎます。親のスクリプトはこの中に自由に書き込めます。広告やウィジェットの読み込みでは、空の iframe を作ってから中に `<script>` を書き込む作り方がよく使われてきました。中で動くコードは、**親と同じオリジンで、親と同じ権限を持つ**ことを意識しておく必要があります。

## 親と子が互いに触れるもの

オリジンが同じなら、親と子は互いの DOM、変数、ストレージにすべて触れます。オリジンが違えば、第 95 回で見たとおり、別のオリジンの `Window` で許されるのは `postMessage()`、`length`、`frames`、`parent`、`top` など少数のものと、`location` への**書き込み**だけです。

親から別のオリジンの子の `location` を読み、続けて書き込むと、次のとおりでした。

```
親 → 別のオリジンの子  location.href を読む  → SecurityError
親 → 別のオリジンの子  location に代入する   → ok（子は親が指定した URL へ移動した）
```

**中は読めないが、移動はさせられる**。この非対称が、次の節の話につながります。

## 誰が誰を移動させられるか

1 枚のページの中に複数のフレームがあると、どのフレームが、どのフレームの URL を変えてよいかが問題になります。どこへでも移動させられるなら、広告の iframe が、隣の決済の iframe を偽物に差し替えられてしまいます。

手元の Chrome で、3 つの組み合わせを試しました。トップは `top.localhost`、子は `widget.localhost` と `other.localhost` です。

```
移動させる側                     移動させられる側             結果
親（top）                        子（widget）                 移動した
子（other）                      兄弟の子（widget）            SecurityError
子（widget）、利用者の操作なし     トップ（top）                 SecurityError
子（widget）、ボタンを押した中で   トップ（top）                 移動した（evil.localhost へ）
同じオリジンの子、操作なし          トップ（top）                 移動した
```

兄弟の移動が拒否されたとき、コンソールには次の 1 行が出ました。

```
Unsafe attempt to initiate navigation for frame with origin 'http://top.localhost:18301'
from frame with URL 'http://widget.localhost:18301/autotop.html?to=...'
```

### 兄弟は移動させられない

兄弟の移動を止めているのは、**移動させる側が、相手のフレームか、その祖先のどれかと同じオリジンでなければならない**という規則です。親は子の祖先なので、子を移動させられます。`other.localhost` は、`widget.localhost` とも、その祖先の `top.localhost` とも同じオリジンではないので、移動させられません。

この規則は、2008 年の Barth、Jackson、Mitchell の論文が、当時のブラウザでフレームを差し替える攻撃を示したうえで提案したものです。Chromium の実装には、この論文を参照したコメントが残っています（[Chromium: LocalFrame::CanNavigate](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/frame/local_frame.cc)、[Securing Frame Communication in Browsers](http://www.adambarth.com/papers/2008/barth-jackson-mitchell.pdf)）。

HTML Standard では、同じ形の規則が、名前で窓を探すとき（`window.open(url, "pay")` や `target="pay"`）の判定 **familiar with** に書かれています（[HTML Standard: familiar with](https://html.spec.whatwg.org/#familiar-with)）。一方、移動そのものの判定である「allowed by sandboxing to navigate」は、主に `sandbox` のフラグを見る内容です（[HTML Standard: allowed by sandboxing to navigate](https://html.spec.whatwg.org/#allowed-to-navigate)）。`location` への代入で兄弟を止める挙動は、この回では Chrome でしか確かめていません。

### 子がトップを移動させるには、利用者の操作が要る

`top.location = ...` は、別のオリジンの子にも許された書き込みです。広告の iframe がこれを使うと、利用者が読んでいたページを丸ごと別のサイトへ移動させられます。

Chrome は 2016 年に、**トップと同じオリジンでない iframe がトップを移動させるのは、利用者の操作（クリックなど）を処理している間に限る**という制限を提案しました。提案は、悪意のある内容がこの手口で利用者を強制的に移動させていることを理由に挙げています（[Intent to Deprecate and Remove: Cross-origin top navigation without a user gesture](https://groups.google.com/a/chromium.org/g/Blink-dev/c/Xi8-y4ySjA4/m/D80epeAMAAAJ)）。実験の 3 行めと 4 行めのとおり、手元の Chrome 154 でもこの制限が働いていました。

ただし、Chromium のテストのコメントは、この制限を「非標準で、仕様に書かれていない動作」としています（[Chromium: framebusting_browsertest.cc](https://chromium.googlesource.com/chromium/src/+/lkgr/content/browser/framebusting_browsertest.cc)）。仕様で決まっているのは、埋め込む側が `sandbox` で明示的に削る方法です。

```
sandbox 属性                                                トップの移動（実験）
sandbox="allow-scripts"                                    クリックしても SecurityError
sandbox="allow-scripts allow-top-navigation-by-user-activation"
                                                           クリックの中なら移動した、操作なしは SecurityError
sandbox="allow-scripts allow-top-navigation"               制限しない
```

`allow-top-navigation-by-user-activation` は、HTML Standard の **sandboxed top-level navigation without user activation** のフラグに当たり、利用者の操作が無いときだけトップの移動を禁じます（[HTML Standard](https://html.spec.whatwg.org/#sandboxed-top-level-navigation-without-user-activation-browsing-context-flag)）。広告を `sandbox` に入れるときは、`allow-top-navigation` ではなくこちらを使えば、「広告をクリックしたら広告主のサイトへ移る」という本来の動作だけを残せます。

### フレームバスティングは守りにならない

逆向きの使い方もあります。昔は、自分のページが他人の iframe に入れられたら抜け出すために、ページに次のようなスクリプトを置くことがありました。これを**フレームバスティング**（framebusting）と呼びます。

```js
if (top !== self) top.location = self.location
```

<Callout type="warn" title="よくある誤解: 「フレームバスティングのスクリプトでクリックジャッキングを防げる」">
  このスクリプトを止めるのは、埋め込む側にとって簡単です。`sandbox="allow-forms"` のように `allow-scripts` を付けずに入れればスクリプトが動かず、`allow-scripts` を付けても `allow-top-navigation` を付けなければトップを移動できません。
  上で見た Chrome の制限も、利用者の操作が無ければ、別のオリジンの子からのトップの移動を止めます。つまり、守る側のフレームバスティングも同じように止まります。
  埋め込ませないための仕組みは、**ブラウザが応答のヘッダで判断する** `frame-ancestors`（第 100 回）です。中のスクリプトに頼りません。
</Callout>

## 置く側と置かれる側: frame-src と frame-ancestors

iframe を拒否できるのは、置かれる側だけではありません。**置く側**も、自分のページに入れてよい iframe を CSP の `frame-src` で制限できます。CSP Level 3 では、`frame-src` が無ければ `child-src` を、それも無ければ `default-src` を使います（[CSP Level 3](https://w3c.github.io/webappsec-csp/#directive-frame-src)）。

親のページ（`top.localhost`）と子のページ（`widget.localhost`）に、それぞれ CSP を付けて読み込みました。

```
親の CSP                                子の CSP                 子のサーバに要求が届いたか   iframe の中身
なし                                    なし                     届いた                      表示された
frame-src 'self'                        なし                     届かない                    エラーのページ
なし                                    frame-ancestors 'none'   届いた                      表示されない
frame-src http://widget.localhost:18301 なし                     届いた                      表示された
```

2 つの拒否は、**拒否する時期が違います**。

- `frame-src` は親のページに書かれているので、ブラウザは**要求を送る前に**止められます。子のサーバには何も届きません
- `frame-ancestors` は子の応答に書かれているので、ブラウザは**要求を送り、応答を受け取ってから**表示を止めます。子のサーバは要求を受け取り、その要求には SameSite の条件を満たす Cookie も付きます

後者から分かるのは、`frame-ancestors` で埋め込みを拒否しても、**GET の要求に副作用があれば、それは起きてしまう**ということです。状態を変える処理を GET で受けてはいけない理由が、ここにも 1 つあります。

| 指定 | 書く場所 | 守るもの | 止める時期 |
| --- | --- | --- | --- |
| `frame-src` | 置く側の応答 | 自分のページに、知らない相手の iframe を入れさせない（XSS で差し込まれた iframe など） | 要求の前 |
| `frame-ancestors` | 置かれる側の応答 | 自分のページを、知らない相手の iframe に入れさせない（クリックジャッキング） | 応答の後 |

## 読み込みの要求に付くもの

iframe の中の文書を読み込む要求は、ブラウザから見ると**ナビゲーション**です。サーバのログには次のように記録されました。

```
同じオリジンの iframe   Sec-Fetch-Dest: iframe  Sec-Fetch-Site: same-origin  Sec-Fetch-Mode: navigate
                        Referer: http://top.localhost:18301/blank.html
別のサイトの iframe     Sec-Fetch-Dest: iframe  Sec-Fetch-Site: cross-site   Sec-Fetch-Mode: navigate
                        Referer: http://top.localhost:18301/
```

- `Sec-Fetch-Dest: iframe` は、**この要求が iframe の中に表示されるためのもの**だとサーバに伝えます。第 99 回で見た Fetch Metadata を使えば、埋め込ませたくないページは、ここを見て応答の本文を作る前に断れます
- `Referer` は、別のサイトに対してはオリジンだけに削られています。第 99 回で見た既定の `strict-origin-when-cross-origin` のとおりです

Cookie は、子のサイト（`widget.localhost`）に、トップレベルで訪れたときに `SameSite=None; Secure` と `SameSite=Lax` の 2 つを置いてから、`top.localhost` の中に iframe で入れて調べました。

```
普通の iframe              Cookie: sid=1      （SameSite=None は付き、Lax は付かない）
credentialless の iframe   Cookie なし
```

`SameSite=None` の Cookie が付いたのは、Chrome が執筆時点で第三者 Cookie を既定では遮断していないからです。Safari と Firefox では、同じ構成でもこの Cookie は付かないか、トップレベルのサイトごとに分けられます（第 97 回、第 98 回）。

## 中のページに何を許すか

置く側は、中のページの能力を 3 つの方向から調整できます。

| 属性 | 向き | 例 | 回 |
| --- | --- | --- | --- |
| `sandbox` | **削る**。スクリプト、フォーム、ポップアップ、トップの移動、オリジンをまとめて禁じ、キーワードで 1 つずつ戻す | `sandbox="allow-scripts allow-forms"` | 第 95 回 |
| `allow` | **与える**。カメラ、位置情報、決済などの強い機能を、ページの `Permissions-Policy` が許す範囲で中に渡す | `allow="payment; geolocation"` | 第 100 回 |
| `credentialless` | **資格情報を外す**。中を、その時だけの空の Cookie とストレージで動かす | `<iframe credentialless>` | 第 101 回 |

`credentialless` は、実験でも Cookie が付かず、中の `document.cookie` も空でした。中の `localStorage` は使えますが、トップレベルの文書が続く間だけの一時的な領域です。MDN は、この仕組みが本来のオリジンの Cookie やストレージに触れない代わりに、COEP を付けたページでも COEP の無い第三者の文書を埋め込めるようにするものだと説明しています（[MDN: IFrame credentialless](https://developer.mozilla.org/en-US/docs/Web/Security/IFrame_credentialless)）。MDN はこの機能を、主要なブラウザの一部で動かないとして Baseline に入れていません。ログインが要る埋め込み（決済、利用者ごとのウィジェット）には使えません。

## 読み込みの時期: loading="lazy"

iframe はそれ自体が 1 つのページなので、読み込みは重い処理です。`loading="lazy"` を付けると、画面に近づくまで読み込みを遅らせます。

実験では、5000 ピクセルの空白の下に `loading="lazy"` の iframe を置きました。ページを読み込んだ時点では、普通の iframe と `credentialless` の iframe の要求だけがサーバに届き、遅延の iframe の要求は**下までスクロールした後**に初めて届きました。

MDN は、遅延読み込みが**スクリプトが有効なときに限られる**と書いています。スクリプトを無効にしたブラウザで遅延読み込みが働くと、サーバは iframe の要求の時期から利用者のスクロールの位置を知ることができ、スクリプトを無効にした意味が失われるからです（[MDN: iframe の loading 属性](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#loading)）。**要求の時期そのものが情報になる**という点は、第 95 回の XS-Leaks と同じ形です。

対応は、画像と iframe をまとめた数字で Chrome 77、Firefox 121、Safari 16.4 からです（[Can I use](https://caniuse.com/loading-lazy-attr)）。

## 消えつつある枠: Fenced Frames

広告のために、iframe よりさらに強く親と切り離す枠として、Chrome は **Fenced Frames**（`<fencedframe>`）を出荷しました。親と中が `postMessage` も含めて通信できず、中がどのサイトに埋め込まれたかを知ることもできない枠で、Privacy Sandbox の広告の API（Protected Audience など）と組み合わせて使う前提でした。

しかし Google は、第三者 Cookie を廃止しないと決めた後、2025 年 10 月にPrivacy Sandbox の技術の大半を引き上げると発表しました（[Update on Plans for Privacy Sandbox Technologies](https://privacysandbox.google.com/blog/update-on-plans-for-privacy-sandbox-technologies)）。それを受けて 2026 年 8 月、Fenced Frames の要素と `window.fence` の API を取り除く提案が出されています。提案では、Chrome 154 で `window.fence` を取り除いて要素を中身の無い形だけ残し、155 から要素自体の削除を段階的に進める予定です（[Intent to Ship: Remove FencedFrame element and window.fence APIs](https://groups.google.com/a/chromium.org/g/blink-dev/c/c9w5uH3eSuo/m/KcvocvF1DQAJ)）。手元の Chrome 154 でも、`HTMLFencedFrameElement` はまだ存在していました。

Fenced Frames は、**埋め込みを使った追跡を、枠の側で断つ**という発想でした。第三者 Cookie が残ることになり、その前提が無くなったので、iframe とストレージの分割（第 97 回）が引き続き埋め込みの基本の形です。

## 用途別の組み合わせ

ここまでの部品を、iframe を使う場面ごとに組み合わせると次のようになります。

| 場面 | 置く側でやること | 置かれる側でやること |
| --- | --- | --- |
| 利用者が書いた HTML を表示する | **別のサイト**から配信し、`sandbox="allow-scripts"`（`allow-same-origin` は付けない）。`srcdoc` だけで済ませない | 配信用のドメインに CSP を付ける（第 100 回） |
| 決済や地図など、第三者の部品を埋め込む | `frame-src` で相手を限る。`sandbox` と `allow` は必要な分だけ。`postMessage` の `event.origin` を完全一致で確かめる（第 95 回） | 親が期待どおりのオリジンかを `event.origin` で確かめる |
| 広告を埋め込む | `sandbox` に `allow-top-navigation-by-user-activation` を使い、`allow-top-navigation` は付けない | — |
| 自分のページを他社のサイトに埋め込んでもらう（ウィジェット） | — | `frame-ancestors` で相手を限る。Cookie は CHIPS や Storage Access API（第 97 回、第 104 回）。`postMessage` の送り先を指定する |
| どこにも埋め込ませない | — | `frame-ancestors 'none'`（古いブラウザ向けに `X-Frame-Options: DENY`）。`Sec-Fetch-Dest: iframe` の要求を断る |
| 分離したページに第三者の部品を入れる | `credentialless`、または相手に CORP と COEP を付けてもらう（第 101 回） | COEP を付ける（`credentialless` でない場合） |

## ブラウザごとの違い

この回の実験は、ヘッドレスの Chrome 154 だけで行いました。違いが出やすいのは次の点です（執筆時点、2026 年 10 月）。

- 中の文書のオリジンの決め方（`srcdoc`、`about:blank`、`sandbox`、`data:`）は HTML Standard で決まっていて、主要なブラウザで共通する部分
- **利用者の操作の無いトップの移動を止める制限**は、Chromium のテストが非標準と明記している動作。他のブラウザでの挙動は確かめていない
- **兄弟のフレームを `location` への代入で移動させる**のを止める判定も、この回で確かめたのは Chrome だけ
- `credentialless` は Baseline に入っていない
- `loading="lazy"` の iframe は、Firefox が 121、Safari が 16.4 から
- Fenced Frames は Chrome が削除を進めている
- 第三者の iframe に Cookie が付くかは、Chrome、Safari、Firefox で大きく違う（第 98 回）

## まとめ

- iframe は部品を取り込む仕組みではなく、ページの中に**もう 1 つの窓**を開く仕組み。中の文書は自分のオリジン、`Window`、履歴、Cookie の文脈、場合によってはプロセスを持つ
- 中の文書のオリジンは URL だけでは決まらない。`sandbox` は何であれ `null` にし、`srcdoc` と `about:blank` と `blob:` は作った側のオリジンを引き継ぎ、`data:` は `null` になる
- `srcdoc` は見た目を分けるが、オリジンは親と同じ。利用者の HTML を入れるなら `sandbox` を組み合わせ、できれば別のサイトから配信する
- 別のオリジンの子は読めないが、移動はさせられる。Chrome では、相手かその祖先と同じオリジンでなければ兄弟を移動させられず、別のオリジンの子がトップを移動させるには利用者の操作が要った
- 置く側は `frame-src` で要求の前に、置かれる側は `frame-ancestors` で応答の後に拒否する。後者では要求は届くので、GET に副作用を持たせない
- iframe の要求は `Sec-Fetch-Dest: iframe` のナビゲーションで、別のサイトへの `Referer` はオリジンだけになる。`credentialless` の iframe には Cookie が付かない
- 置く側は `sandbox` で削り、`allow` で与え、`credentialless` で資格情報を外す
- フレームバスティングのスクリプトは守りにならない。埋め込ませない仕組みは `frame-ancestors`

次は、ブラウザとサーバの間に挟まる共有のキャッシュを扱います。この回までの境界は、ブラウザが「この応答は誰のものか」を知っていることを前提にしていました。CDN やリバースプロキシのキャッシュは、その前提を持たずに、1 人のために作られた応答を次の人へ返します。
