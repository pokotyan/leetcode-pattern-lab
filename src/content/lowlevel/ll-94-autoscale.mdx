## 台数を決め打ちにすると

アクセスは一定ではありません。昼に多く夜に少ない、月末だけ跳ねる、宣伝した瞬間に 10 倍になる。

台数を固定すると、どちらかを諦めることになります。

- **最大に合わせる**と、ほとんどの時間、機械が遊んでいる
- **平均に合わせる**と、山のときに溢れる。第 91 回で見たとおり、溢れた Pod は準備完了から外れ、残りにさらに負荷が集まる

そこで、**負荷を測り、それに合わせて台数を変える**。やっていることは、第 86 回の調整ループと同じです。違うのは、あるべき姿を人間が書くのではなく、**測定値から計算する**ことだけです。

## 3 つの方向

増減させられるものは 3 つあります。

| 何を | 仕組み | かかる時間 |
| --- | --- | --- |
| Pod の数 | HorizontalPodAutoscaler（HPA） | 秒〜数十秒 |
| Pod 1 つの大きさ（requests） | 縦方向の自動調整 | Pod の作り直しが要ることが多い |
| ノードの数 | ノードの自動増減 | 分単位（仮想マシンの起動） |

この回では、最もよく使われる Pod の数とノードの数を見ます。

## HPA: 比例で台数を決める

HPA のコントローラは、既定で 15 秒ごとに測定値を読み、次の式で台数を決めます（[Kubernetes](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/)）。

```
必要な台数 = ceil( 今の台数 × 今の測定値 ÷ 目標値 )
```

CPU 使用率の目標を 60% にしていて、4 台の平均が 90% なら、

```
ceil( 4 × 90 ÷ 60 ) = ceil( 6.0 ) = 6 台
```

負荷が台数に比例して分散する、という仮定の下では、6 台にすれば平均が 60% に戻る計算です。

ここで「CPU 使用率」は、**requests に対する割合**です。第 84 回で見た requests が書かれていない Pod は、分母が無いので使用率を計算できず、HPA はその指標では何もしません。**requests は、スケジューラの詰め込みだけでなく、自動増減の物差しにもなっている**ということです。

### 少しの差では動かない

測定値は常に揺れています。目標 60% に対して 61% になるたびに台数を変えていては落ち着きません。そこで、比が **1 から 10% 以内**のずれなら何もしない、という許容幅が既定で設けられています。

### まだ準備ができていない Pod は数えない

起動したばかりの Pod は、JIT のウォームアップ（第 32 回）やキャッシュの暖機で、一時的に CPU を多く使います。これを数えると「まだ足りない」と判断して、さらに増やしてしまいます。HPA は、準備完了になっていない Pod や測定値の欠けた Pod を、**増やしすぎない側に倒して**扱います。

## 遅れが、行き過ぎと振動を生む

調整ループには、どうしても**遅れ**があります。

```
負荷が増える
  │  測定値に現れるまで（集計の間隔）      数十秒
  │  HPA が気づくまで（15 秒ごと）          〜15 秒
  │  Pod が作られ、イメージが届くまで        数秒〜数十秒（第 77 回の層の取得）
  │  起動して準備完了になるまで              数秒〜数十秒
  ↓
やっと処理能力が増える
```

この間も、負荷は増え続けているかもしれません。HPA は「まだ足りない」と判断して、さらに台数を積み増します。やっと全員が立ち上がったときには、**必要以上の台数**になっています。

すると今度は、平均の使用率が目標を大きく下回り、台数を減らします。減らしすぎれば、また足りなくなる。**増やしすぎと減らしすぎを繰り返す**のが**振動**です。

```
台数
 ▲       ╱╲        ╱╲
 │      ╱  ╲      ╱  ╲
 │ ────╱    ╲    ╱    ╲──── 本当に必要な台数
 │           ╲  ╱
 │            ╲╱
 └──────────────────────────→ 時間
```

これは Kubernetes に固有の問題ではありません。エアコンの温度制御でも、第 54 回で見た TCP の輻輳制御でも、**測定から反映までに遅れがある制御は、放っておくと振動します**。対策も昔から同じです。

**増やすのは速く、減らすのはゆっくり。** 足りないときの損失（遅延、エラー）は大きく、多すぎるときの損失（費用）は小さいからです。HPA は既定で、増やす判断は即座に使い、減らす判断は**過去 5 分間の計算結果のうち最も大きい台数**を採用します。これを**安定化ウィンドウ**と呼びます。一瞬負荷が下がっただけでは減らしません。

<Callout type="tip" title="エアコンと同じ仕掛け">
  エアコンが設定温度ちょうどで入ったり切れたりを繰り返さないのは、
  「25 度で冷房を止め、27 度で再開する」のように幅を持たせているからです。
  HPA の許容幅と安定化ウィンドウは、これと同じ**不感帯**と**ためらい**の仕掛けです。
</Callout>

## CPU 使用率が正しい物差しとは限らない

比例の式は、「測定値が台数に反比例して下がる」ことを前提にしています。この前提が崩れる場面があります。

**スロットリングされている。** 第 84 回で見たとおり、CPU の limits に当たっているコンテナは、平均の使用率が低く見えたまま遅くなります。HPA から見ると「まだ余裕がある」ように見えます。

**CPU ではなく待ちで詰まっている。** データベースの応答待ちで詰まっている Pod は、CPU をほとんど使いません。台数を増やしても速くならず、むしろデータベースへの接続が増えて悪化することがあります。第 40 回で見た「並列にしても速くならない壁」と同じ話です。

**負荷の単位が違う。** キューから仕事を取り出す作業者なら、CPU よりも**キューに溜まった件数**のほうが直接的な物差しです。

そのため HPA は、CPU やメモリ以外の任意の測定値（1 秒あたりのリクエスト数、キューの長さ）も目標にできます。**何を測るかの選択が、自動増減の質を決めます。**

## ノードを増やす

Pod を増やしても、置く場所が無ければ始まりません。第 88 回で見たとおり、どのノードにも requests が収まらない Pod は **Pending** のまま待ちます。

ノードの自動増減は、この **Pending の Pod** を合図にします。「既存のノードに置けない Pod があるなら、それが収まるノードを新しく足す」。逆に、Pod を他のノードに寄せればノードを 1 台空けられるなら、そのノードを消します（[Kubernetes](https://kubernetes.io/docs/concepts/cluster-administration/node-autoscaling/)）。

重要なのは、この判断が**実際の使用量ではなく requests だけを見る**ことです。ノードの自動増減は、スケジューラと同じ帳簿で「置けるか、置けないか」を判断しています。使用量に応じて増やしたいなら、HPA が Pod を増やし、その Pod が置けないことをノードの増減が拾う、という 2 段の連携で実現します。

```
負荷が増える
  → HPA が Pod を増やす
    → 置き場所が無い Pod が Pending になる
      → ノードを足す（数分）
        → スケジューラが Pending の Pod を新しいノードに置く
```

ノードの起動は仮想マシンの起動なので、**分単位**かかります。その間、増やしたはずの Pod は動いていません。

<Callout type="note" title="あらかじめ席を取っておく">
  この遅れを隠す定番の手が、**優先度の低いダミーの Pod で席を確保しておく**方法です。
  本物の Pod が来ると、スケジューラは優先度の低いダミーを追い出して席を譲ります（第 88 回の追い出し）。
  追い出されたダミーが Pending になり、それを合図にノードが足される。
  **ノードの起動を、本物の Pod が待たずに済む**ようにする仕掛けです。
  その代わり、ダミーの分の費用を常に払います。
</Callout>

## ゼロまで減らす

夜間はまったくリクエストが来ないサービスもあります。1 台でも動かしておけば費用がかかります。**ゼロ台まで減らせれば、使っていない時間の費用はゼロ**です。

しかし、ゼロ台から最初のリクエストが来たとき、それを受ける Pod はまだありません。

1. 誰かがリクエストを**いったん預かる**（Pod の代わりに受け付けて待たせる）
2. Pod を起動する
3. 準備ができたら、預かっていたリクエストを渡す

この最初のリクエストだけが遅くなる現象を**コールドスタート**と呼びます。遅さの中身は、ここまでの章で見てきたものの足し算です。

| 段階 | 関係する回 |
| --- | --- |
| 実行環境の用意（コンテナ、または軽量な仮想マシン） | 第 76 回、第 78 回 |
| イメージや実行ファイルの取得 | 第 77 回 |
| プロセスの起動、ライブラリの読み込み | 第 30 回 |
| ランタイムの初期化、JIT のウォームアップ | 第 32 回 |
| 接続の確立（データベース、TLS） | 第 53 回 |

Kubernetes の HPA でも、ゼロまで減らす機能が整えられてきています（[Kubernetes Blog](https://kubernetes.io/blog/2026/09/02/kubernetes-v1-37-hpa-scale-to-zero-beta/)）。ただし、上の「預かる」役は別に用意する必要があります。

### サーバレスという極端

この考え方を突き詰めたのが**サーバレス**です。利用者は台数を一切考えず、**リクエストが来たら、その分だけ実行環境が用意される**。

複数の利用者のコードを同じ物理マシンで動かすので、分離が重要になります。第 76 回で見た **Firecracker** は、この用途のために作られた軽量な仮想マシンで、Linux カーネルを 125 ミリ秒未満で起動できることが論文で示されています（[Firecracker](https://firecracker-microvm.github.io/)）。コンテナの手軽さと、仮想マシンの分離の強さの間を取った選択です。

さらに、**起動済みの状態を丸ごと保存しておき、そこから再開する**ことで、起動と初期化の段階を飛ばす工夫も使われます。第 24 回で見た copy-on-write の考え方を使えば、1 つの保存状態から多数の実行環境を、ページを共有したまま素早く作れます。

## まとめ

- 自動増減も調整ループ。あるべき台数を、人間ではなく測定値から計算する
- HPA は「今の台数 × 測定値 ÷ 目標値」で台数を決める。CPU 使用率は requests に対する割合
- 測定から反映までの遅れが、行き過ぎと振動を生む。遅れのある制御に共通の問題
- 対策は不感帯（許容幅）と、減らすときのためらい（安定化ウィンドウ）。増やすのは速く、減らすのはゆっくり
- CPU 使用率が正しい物差しとは限らない。スロットリング、待ち、キューの長さ
- ノードの増減は Pending の Pod を合図にし、requests だけを見る。起動は分単位
- ゼロまで減らすとコールドスタートが生じる。その中身はここまでの章の足し算
- サーバレスは、軽量な仮想マシンと保存状態からの再開で、その遅れを削っている

ここまでで第 15 章は終わりです。宣言して近づけ続けるという 1 つの考え方が、Pod の配置、通信、更新、状態、拡張、そして台数の増減まで、すべてを貫いていました。次の章では、こうして大量に動いているものを、**止めずに外から観測する**方法に入ります。カーネルの中に小さなプログラムを差し込む eBPF から始めます。
