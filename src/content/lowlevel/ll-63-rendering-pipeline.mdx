## 木から絵へ

前回で、ブラウザは HTML から **DOM** を、CSS から **CSSOM** を組み立てました。どちらも木です。しかし画面に出せるのはピクセルの格子だけです。木を格子に変えるまでの工程を、**レンダリングパイプライン**と呼びます。

工程は段に分かれていて、各段は前の段の出力だけを入力にします。第 11 回で見た CPU のパイプラインと同じ考え方です。

```
 DOM + CSSOM
     │
     ▼
 ① スタイル   各要素に効く CSS を決める          → 計算済みスタイル
     │
     ▼
 ② レイアウト 位置と大きさを決める              → レイアウトの木（箱の配置）
     │
     ▼
 ③ ペイント   何をどの順で描くかを書き出す      → 表示リスト（描画命令の列）
     │
     ▼
 ④ 合成       層に分けてラスタライズし、重ねる  → 画面のフレーム
```

Chrome の実装はこれをさらに細かい段に分けていますが（[RenderingNG のアーキテクチャ](https://developer.chrome.com/docs/chromium/renderingng-architecture)）、骨格はこの 4 段です。④ は次回に回し、この回では ①〜③ を見ます。

## ① スタイル: 誰にどの規則が効くのか

最初の段は、要素ごとに **計算済みスタイル**（computed style）を決めることです。

CSS の規則はセレクタで対象を選び、複数の規則が同じ要素に当たることがあります。ブラウザは、当たる規則を集め、詳細度と出現順で優先を決め、親から継承する値を埋め、`em` や `%` のような相対値を解決します。結果として、すべての要素がすべてのプロパティについて具体的な値を持ちます。

<Callout type="note" title="セレクタは右から照合する">
  `.menu li a` という規則を、ブラウザは「`.menu` の中の `li` の中の `a` を探す」とは処理しません。
  **要素ごとに**、その要素が規則に当たるかを判定します。
  そのため右端の `a` から見て、祖先を遡って `li`、`.menu` があるかを調べます。
  右端が絞り込めていない規則（`* ` や `div` だけで終わるもの）ほど、照合する要素が増えます。
</Callout>

## ② レイアウト: 箱の位置と大きさ

次に、**各要素の箱がどこに、どの大きさで置かれるか**を計算します。

レイアウトの難しさは、**ある箱の大きさが他の箱に依存する**ことです。

- 親の幅が決まらないと、子の幅（`width: 50%`）が決まらない
- 子の中身の高さが決まらないと、親の高さ（`height: auto`）が決まらない
- 前の兄弟の高さが決まらないと、自分の縦位置が決まらない

幅は親から子へ下りながら、高さは子から親へ上りながら決まります。木を下りて上る、アルゴリズムの区画で扱った木の再帰そのものです。

そして、1 つの要素の大きさが変わると、この依存を辿って**兄弟、親、さらにその外側まで**計算し直しになります。web.dev は「レイアウトはほぼ常に文書全体が対象になる」と書いています（[web.dev](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)）。要素の数がそのままレイアウトの重さになります。

## ③ ペイント: 描く順番を書き出す

ペイントの段は、実はまだピクセルを塗りません。作るのは **表示リスト**（display list）、つまり「この位置にこの色の矩形」「ここにこの文字列」「ここにこの画像」という**描画命令の列**です。

```
表示リスト（概念図）
  drawRect(0, 0, 1280, 800, #ffffff)        背景
  drawRect(16, 16, 400, 120, #f5f5f5)       カードの背景
  drawText(32, 48, "見出し", 20px bold)
  drawImage(32, 80, 64, 64, logo.png)
  ...
```

命令の順番は、重なりの順番（z-index や、後に書いた要素が上になる規則）で決まります。実際にピクセルに変えるのは次回の合成の段で、ここでは「何を描くか」の記録だけです。

描くことと、ピクセルに変えることを分けておくと、同じ表示リストを別のスレッドや GPU でラスタライズできます。第 48 回で見た DMA が、CPU は転送の内容を書き出すだけで実際の転送は別の装置に任せていたのと同じ考え方です。

## 何を変えると、どこからやり直しか

パイプラインの重要な性質は、**変更の種類によって、やり直しの開始地点が違う**ことです。

| 変えたもの | 例 | やり直す段 |
| --- | --- | --- |
| 幾何（大きさ・位置） | `width`、`height`、`top`、`font-size`、要素の追加や削除 | ① → ② → ③ → ④ |
| 見た目だけ | `color`、`background-color`、`box-shadow` | ① → ③ → ④ |
| 合成だけで済むもの | `transform`、`opacity` | ④ だけ |

① から ② を通るやり直しを **リフロー**（reflow、レイアウトのやり直し）、③ からのやり直しを **リペイント**と呼びます。

同じ「右に 100px 動かす」でも、`left: 100px` はリフローを起こし、`transform: translateX(100px)` は合成だけで済みます。この差が次回の主題です。

<Callout type="tip" title="DOM を触ると遅い、の中身">
  「DOM 操作は遅い」とよく言われますが、遅いのは JavaScript から DOM のオブジェクトを書き換える瞬間ではありません。
  **書き換えた結果、① と ② をやり直すこと**が重いのです。
  フレームワークが仮想 DOM で差分を取り、実際の DOM への書き込みをまとめるのは、このやり直しの回数を減らすためです。
  仕組みはシステム設計の読み物
  <a href={`${import.meta.env.BASE_URL}reading/browser-internals/`}>ブラウザの中の差分と制御</a>
  で扱っています。
</Callout>

## 後回しにする: ダーティフラグ

変更のたびにパイプラインを回していたら、どれだけ速くても間に合いません。そこでブラウザは、**変更があったことを記録するだけにして、計算は後回しにします**。

```js
el.style.width = '100px'   // 「el のスタイルが古い」と印を付けるだけ
el.style.height = '50px'   // 同じ印がもう付いている
el.style.color = 'red'     // 同じ
// …… スクリプトが終わる
// 次に描画するときに、印の付いた部分だけを 1 回だけ計算する
```

この印を **ダーティフラグ**と呼びます。第 15 回で見たキャッシュのライトバックと同じ発想で、書き込みはすぐには反映させず、必要になったときにまとめて片付けます。

いつ「必要になる」のかというと、普通は**次の描画のタイミング**です。これは第 65 回で見るイベントループの中に、決まった位置として組み込まれています。

## 読むと、その場で計算させてしまう

ところが、後回しが効かない場合があります。**スクリプトがレイアウトの結果を読んだとき**です。

```js
box.classList.add('super-big')
console.log(box.offsetHeight)   // ← ここでレイアウトが走る
```

`offsetHeight` は「今の高さ」を返さなければなりません。しかし直前にクラスを変えているので、印の付いたまま計算が終わっていません。ブラウザは**その場でスタイルとレイアウトを実行してから**値を返します。これを **強制同期レイアウト**（forced synchronous layout）と呼びます（[web.dev](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)）。

1 回なら問題になりません。問題は、書き込みと読み込みを**交互に**繰り返したときです。

```js
// 悪い例: 1 周ごとに読んで、書く
for (const p of paragraphs) {
  p.style.width = `${box.offsetWidth}px`   // 読む → 書く → 次の周で読むと、また計算
}

// 良い例: 先にすべて読み、それからすべて書く
const w = box.offsetWidth
for (const p of paragraphs) {
  p.style.width = `${w}px`
}
```

悪い例では、段落が 1000 個あればレイアウトが 1000 回走ります。この状態を **レイアウトスラッシング**と呼びます。第 17 回の false sharing と同じく、コードの見た目には何の問題もないのに、下の層で同じ仕事が繰り返されています。

<Callout type="warn" title="レイアウトを強制するプロパティは多い">
  `offsetWidth` / `offsetHeight` / `offsetTop`、`clientWidth`、`scrollTop`、
  `getBoundingClientRect()`、`getComputedStyle()` の一部の値など、
  **レイアウトの結果に依存する値**を読むものはすべて該当します。
  `scrollTop` に値を代入する、`focus()` を呼ぶといった操作も、位置を確定させる必要があるため同じことが起きます。
  「読み」をまとめて先に済ませる、というのが唯一の一般的な対策です。
</Callout>

## 開発者ツールで見る

ブラウザの開発者ツールの Performance パネルで記録すると、1 フレームの中の各段がそのまま並んで見えます。

```
Main ─┬─ Task ───────────────────────────────────────┬──
      │  Evaluate Script   Recalculate Style   Layout │ Paint
      │  ███████████████   ████                ██████ │ ██
```

JavaScript の中に紫色の Layout が何度も挟まっていれば、そこがレイアウトスラッシングです。スクリプトの後に 1 回だけ Layout が来ているのが正常な形です。

第 98 回で「推測せず、測ってから直す」と書いたのは、ブラウザでも変わりません。**何が遅いかは、段ごとの時間を見れば分かります。**

## まとめ

- レンダリングパイプラインは、DOM と CSSOM をピクセルに変える工程。スタイル → レイアウト → ペイント → 合成
- スタイルは各要素の計算済みスタイルを決め、レイアウトは箱の位置と大きさを決める。レイアウトは依存を辿って文書全体に波及する
- ペイントは描画命令の列（表示リスト）を作るだけで、ピクセルにはしない
- 変更の種類で、やり直しの開始地点が違う。幾何を変えるとリフロー、見た目だけならリペイント、`transform` と `opacity` は合成だけ
- 変更は印を付けて後回しにされるが、レイアウトの値を読むとその場で計算させてしまう。読み書きを交互にするとレイアウトスラッシングになる

次は、パイプラインの最後の段、合成と GPU を見ます。なぜ `transform` のアニメーションだけが、メインスレッドが忙しくても滑らかに動くのか。
