## その鍵は、どこに置くのか

ここまでの 3 回は、ブラウザの前に座った**人**がログインする話でした。しかし実際にクラウドの API を呼んでいるのは、多くの場合、人ではありません。CI のジョブがイメージをレジストリに押し込み、Pod がオブジェクトストレージからファイルを読み、夜間のバッチがデータベースの控えを取ります。

機械にはパスワードを覚える頭も、パスキーを持つ指もありません。そこで昔から使われてきたのが、**長期のアクセスキーをどこかに置く**方法です。CI の秘密情報の欄に AWS のアクセスキーを貼る。Kubernetes の Secret にサービスアカウントの鍵ファイルを入れる。

この回の問いは、**機械は、長く生きる秘密を持たずに、自分が誰かを示せるか**です。答えは「示せる。ただし、秘密を置いていた場所に、代わりに**条件**を書くことになる」です。その条件を書き損なうと、鍵を公開したのと同じことが起きます。

## 長期の秘密は、何が困るのか

第 124 回で、API キーは多くの場合「どの契約に結びつけるか」の値で、誰が使っているかを示さないと見ました。第 128 回の client credentials の `client_secret` も、漏れれば誰でもそのクライアントになりすませる長期の秘密でした。第 108 回では、秘密がリポジトリ、環境変数、ログを通って漏れる経路を並べました。

長期の秘密の困るところは、まとめると次の 3 つです。

| 性質 | 何が起きるか |
| --- | --- |
| **期限がない（か、とても長い）** | 漏れてから気づくまでの間、ずっと使える。ローテーションは人の作業になり、後回しにされる |
| **ベアラ型** | 持っている者が本人とみなされる。コピーされたかどうかを、使われる側は区別できない |
| **置き場所が増える** | CI、開発者の手元、コンテナのイメージ、バックアップ。どこか 1 か所から漏れれば足りる |

第 108 回の結論は、**漏れても困らないほど短命な秘密にする**ことでした。この回の仕組みはその先で、**そもそも長期の秘密を配らない**ことを目指します。

## 発想: 実行環境に身元を証明してもらう

機械は自分の秘密を持っていません。しかし、機械を**動かしている環境**は、その機械が何者かを知っています。GitHub Actions は、いま動いているジョブがどのリポジトリの、どのブランチの、どのワークフローかを知っています。Kubernetes は、この Pod がどの名前空間の、どのサービスアカウントで動いているかを知っています。

そこで実行環境に、**「このジョブ（この Pod）はこれです」という署名付きの文書**を発行してもらいます。形式は第 127 回の JWT で、中身は第 129 回の ID トークンとほぼ同じです。クラウドの側はそれを受け取り、署名を確かめ、条件に合えば**短命な認証情報**を返します。これを**ワークロード ID フェデレーション**と呼びます。

```
 実行環境（IdP の役）             ワークロード                 クラウドの STS
 GitHub / Kubernetes                                          （トークンを交換する窓口）
       │                              │                              │
       │ ① OIDC トークンを発行        │                              │
       │   iss, sub, aud, exp に署名  │                              │
       ├─────────────────────────────→│                              │
       │                              │ ② トークンを差し出す         │
       │                              ├─────────────────────────────→│
       │ ③ Discovery と JWKS を取得   │                              │
       │←────────────────────────────────────────────────────────────┤
       │                              │   ④ 署名、iss、aud、exp を検証
       │                              │      信頼ポリシーの条件と照合
       │                              │ ⑤ 短命な認証情報（1 時間など）│
       │                              │←─────────────────────────────┤
```

第 129 回の OIDC と比べると、登場人物の役がずれています。**IdP は GitHub や Kubernetes のクラスタ**で、**RP はクラウド**です。利用者はいません。ブラウザもリダイレクトもなく、ワークロードは発行されたトークンをそのまま差し出します。

秘密が消えたわけではありません。**署名鍵は実行環境の側にあり**、それを守るのは GitHub やクラウド事業者（あるいは自分のクラスタ）の仕事になります。ワークロードの手元に残るのは、数分から 1 時間で期限が切れるトークンだけです。

## GitHub Actions が発行するトークン

GitHub Actions では、ジョブに `id-token: write` の権限を与えると、OIDC トークンを要求できるようになります（[GitHub Docs: OpenID Connect reference](https://docs.github.com/en/actions/reference/security/oidc)）。ジョブの中には `ACTIONS_ID_TOKEN_REQUEST_URL` と `ACTIONS_ID_TOKEN_REQUEST_TOKEN` の 2 つの環境変数が入り、後者をベアラトークンにして前者へ要求すると、OIDC トークンが返ります。`audience` はこの要求の引数で指定します。

公式の例を抜粋すると、トークンの中身は次のとおりです（[GitHub Docs: OpenID Connect](https://docs.github.com/en/actions/concepts/security/openid-connect)）。

```json
{
  "sub": "repo:octo-org/octo-repo:environment:prod",
  "aud": "https://github.com/octo-org",
  "iss": "https://token.actions.githubusercontent.com",
  "repository": "octo-org/octo-repo",
  "repository_owner": "octo-org",
  "repository_id": "74",
  "ref": "refs/heads/main",
  "environment": "prod",
  "event_name": "workflow_dispatch",
  "job_workflow_ref": "octo-org/octo-automation/.github/workflows/oidc.yml@refs/heads/main",
  "runner_environment": "github-hosted",
  "nbf": 1632492967, "iat": 1632493567, "exp": 1632493867
}
```

第 127 回で見た登録済みクレーム（`iss`、`sub`、`aud`、`exp`）に、リポジトリやブランチやイベントの種類が足されています。この例では `iat` から `exp` までが 300 秒です。

中心になるのは `sub` です。既定の形は、ジョブがどういう状況で動いたかで変わります（[GitHub Docs: OpenID Connect reference](https://docs.github.com/en/actions/reference/security/oidc)）。

| 状況 | `sub` の形 |
| --- | --- |
| ジョブが環境（environment）を参照している | `repo:ORG/REPO:environment:NAME` |
| プルリクエストのイベント（環境を参照しない場合） | `repo:ORG/REPO:pull_request` |
| ブランチやタグへの push など | `repo:ORG/REPO:ref:refs/heads/BRANCH`、`repo:ORG/REPO:ref:refs/tags/TAG` |

### 手元で: GitHub の Discovery を読む

発行者の公開情報は、クラウドのアカウントがなくても読めます。第 129 回の Keycloak と同じ `/.well-known/openid-configuration` です。

```
$ curl -s https://token.actions.githubusercontent.com/.well-known/openid-configuration
{
  "issuer": "https://token.actions.githubusercontent.com",
  "jwks_uri": "https://token.actions.githubusercontent.com/.well-known/jwks",
  "subject_types_supported": ["public", "pairwise"],
  "response_types_supported": ["id_token"],
  "claims_supported": ["sub", "aud", "exp", "iat", "iss", "jti", "nbf", "ref", "sha",
    "repository", "repository_id", "repository_owner", "repository_owner_id", ...],
  ...
}

$ curl -s https://token.actions.githubusercontent.com/.well-known/jwks \
    | python3 -c "import json,sys; [print(k['kty'], k['alg'], k['kid'][:20]) for k in json.load(sys.stdin)['keys']]"
RSA RS256 cc413527-173f-5a05-9
RSA RS256 38826b17-6a30-5f9b-b
RSA RS256 38E9B30B3A023A1B7230
RSA RS256 4F3E9AD8C9A6F5EB3173
```

執筆時点（2026 年 9 月）で、JWKS には RSA の公開鍵が 4 本並んでいました。第 135 回で見たとおり、ローテーションの途中では新旧の鍵を同時に載せておくので、複数あるのが普通です。クラウドの STS は、トークンのヘッダの `kid` でこの中から 1 本を選んで署名を確かめます。

<Callout type="note" title="名前は使い回される: 変わらない sub へ">
  OIDC の仕様は、`sub` が発行者の中で一意で、別の主体に割り当て直されないことを求めています。
  ところが従来の既定の `sub` は組織名とリポジトリ名だけでできていたので、組織やリポジトリを消した後に**同じ名前を別の誰かが取れば、同じ `sub` を作れました**。
  GitHub は、2026 年 7 月 15 日より後に作られたリポジトリで、所有者とリポジトリの **ID** を含む形を既定にしました。
  例は `repo:octo-org@123456/octo-repo@456789:ref:refs/heads/main` です。それ以前のリポジトリは、明示的に切り替えない限り従来の形のままです（[GitHub Docs: Immutable subject claims](https://docs.github.com/en/actions/reference/security/oidc#immutable-subject-claims)）。
  第 129 回で、利用者を指すのは `iss` と `sub` の組で、email ではないと見ました。同じ理由で、**変わりうる名前より、変わらない ID に結びつける**のが安全です。
  Google Cloud のドキュメントも、`repository` や `repository_owner` のような名前の欄を条件に使うと、名前の乗っ取りの危険が増すと注意しています（[Google Cloud: deployment pipelines](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)）。
</Callout>

## クラウドの側: トークンを交換する

**AWS** では、STS の `AssumeRoleWithWebIdentity` にこのトークンを渡します。この呼び出しには **AWS の認証情報が要りません**。呼び出し元の身元は、渡したトークンで確かめるからです。返ってくるのはアクセスキー ID、シークレットアクセスキー、セッショントークンの 3 つ組で、既定の寿命は 1 時間、`DurationSeconds` で 900 秒からロールの上限（1〜12 時間）までの範囲で変えられます。受け付けるトークンの署名は RS256/384/512 か ES256/384/512 です（[AWS STS API Reference](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRoleWithWebIdentity.html)）。

どのトークンを受け入れるかは、ロールの**信頼ポリシー**に書きます。GitHub の手順の例です（[GitHub Docs: Configuring OpenID Connect in AWS](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)、[AWS IAM](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-idp_oidc.html#idp_oidc_Create_GitHub)）。

```json
{
  "Effect": "Allow",
  "Principal": {
    "Federated": "arn:aws:iam::012345678910:oidc-provider/token.actions.githubusercontent.com"
  },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
      "token.actions.githubusercontent.com:sub": "repo:octo-org/octo-repo:ref:refs/heads/main"
    }
  }
}
```

`Principal` が「どの発行者を信じるか」（`iss`）、`aud` の条件が「この STS 宛てに発行されたトークンか」、`sub` の条件が「**どのジョブに**このロールを渡すか」です。AWS 公式のアクションを使う場合、`aud` は `sts.amazonaws.com` にします。

**Google Cloud** の Workload Identity Federation も骨格は同じです。発行者ごとに「プロバイダ」を登録し、トークンのクレームを Google 側の属性に写す**属性の対応づけ**（例: `google.subject=assertion.sub`）と、受け入れるかを決める **CEL の条件式**を書きます。ワークロードはトークンを STS に渡し、グラントタイプ `urn:ietf:params:oauth:grant-type:token-exchange` で交換します（[Google Cloud STS API](https://docs.cloud.google.com/iam/docs/reference/sts/rest/v1/TopLevel/token)）。これは第 130 回で見た RFC 8693 のトークン交換の形です。

## `sub` の条件は、秘密の代わりになった

ここで、冒頭の答えの後半に戻ります。長期のアクセスキーを使っていたときは、**キーを知っていること**がロールを使える条件でした。フェデレーションでは、**信頼ポリシーの条件に合うトークンを持っていること**が条件です。

そして GitHub の発行者 `https://token.actions.githubusercontent.com` は、**世界中の GitHub のリポジトリで共通**です。誰でも自分のリポジトリにワークフローを書けば、この発行者の正しい署名が付いたトークンを手に入れられます。署名が確かめるのは「GitHub が発行した」ことまでで、「**自分の**組織のジョブだ」ことは `sub` などの条件でしか確かめられません。

<Callout type="warn" title="誤解 1: OIDC にしたから、鍵が漏れる心配はなくなった">
  長期の鍵は消えましたが、**信頼ポリシーが新しい秘密の役**を担っています。
  `sub` の条件がなければ、ロールの ARN を知った誰かが、自分のリポジトリのワークフローからそのロールを引き受けられます。
  2023 年に複数の研究者がこの設定漏れを見つけ、同じ問題は GitHub 以外の CI や SaaS の連携にもあったと報告されています（[Wiz](https://www.wiz.io/blog/avoiding-mistakes-with-aws-oidc-integration-conditions)）。
  AWS は、GitHub のような**複数の組織で共有される発行者**について、信頼ポリシーに所定のクレームの条件（GitHub なら `token.actions.githubusercontent.com:sub`）がないロールの作成や更新を拒否するようになりました。
  値が `*` や `?` だけのものも拒否されます（[AWS IAM: Identity-provider controls](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_oidc_secure-by-default.html)）。
  ただし、この検査が対象にするのは作成と更新の時点で、**既存のロールには遡って適用されません**（同じページ）。
  Google Cloud も、GitHub、GitLab SaaS、HCP Terraform については、自分の組織に絞る属性の条件を**必ず**書くよう求めています（[Google Cloud](https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines)）。
</Callout>

AWS の検査が拒むのは「条件がない」「全部を許す」という明白な場合だけです。**広すぎる**条件は通ります。

### 手元で: ワイルドカードは何を通すか

AWS の `StringLike` は、`*`（任意の文字列）と `?`（任意の 1 文字）を使える、大文字小文字を区別する照合です（[AWS IAM: Condition operators](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_condition_operators.html)）。Python の `fnmatch.fnmatchcase` は `*` と `?` を同じ意味で扱うので、この 2 つだけを使う範囲で、どの `sub` がどの条件を通るかを手元で並べられます。

```python
from fnmatch import fnmatchcase
subs = [
    "repo:octo-org/deploy:ref:refs/heads/main",
    "repo:octo-org/deploy:ref:refs/heads/feature-x",
    "repo:octo-org/deploy:pull_request",
    "repo:octo-org/deploy:environment:prod",
    "repo:octo-org/sandbox:ref:refs/heads/main",
    "repo:octo-org-evil/deploy:ref:refs/heads/main",
]
for p in ["repo:octo-org/deploy:environment:prod", "repo:octo-org/deploy:ref:refs/heads/main",
          "repo:octo-org/deploy:*", "repo:octo-org/*", "repo:octo-org*"]:
    print(p)
    for s in subs:
        if fnmatchcase(s, p): print("   通る:", s)
```

```
repo:octo-org/deploy:environment:prod
   通る: repo:octo-org/deploy:environment:prod
repo:octo-org/deploy:ref:refs/heads/main
   通る: repo:octo-org/deploy:ref:refs/heads/main
repo:octo-org/deploy:*
   通る: repo:octo-org/deploy:ref:refs/heads/main
   通る: repo:octo-org/deploy:ref:refs/heads/feature-x
   通る: repo:octo-org/deploy:pull_request
   通る: repo:octo-org/deploy:environment:prod
repo:octo-org/*
   （上の 4 つ）
   通る: repo:octo-org/sandbox:ref:refs/heads/main
repo:octo-org*
   （上の 5 つ）
   通る: repo:octo-org-evil/deploy:ref:refs/heads/main
```

読み取れることは 3 つです。

- `repo:octo-org/deploy:*` は、**どのブランチの push も、プルリクエストのジョブも**通します。本番のロールをこれで渡すと、レビュー前のブランチに書いたワークフローから本番に触れます。ブランチの保護やレビューの手順を、クラウドの側で迂回されることになります
- `repo:octo-org/*` は組織の**全リポジトリ**を通します。試験用のリポジトリに書き込める人は、本番のロールも使えます
- `repo:octo-org*` は `/` を忘れただけですが、**別の組織** `octo-org-evil` まで通します。組織名は誰でも取れるので、これは条件がないのとほとんど変わりません

本番に触るロールは、**環境（environment）で絞る**のが基本です。AWS のドキュメントも、環境を使う場合は GitHub 側で保護ルールを付け、どのブランチやタグから配備できるかを制限するよう勧めています（[AWS IAM](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_create_for-idp_oidc.html#idp_oidc_Create_GitHub)）。クラウドの条件（どの環境か）と GitHub の保護ルール（誰がその環境に配備できるか）が、**組み合わさって初めて**「承認されたジョブだけが本番に触れる」が成り立ちます。

## Kubernetes の Pod が持つトークン

Kubernetes も、Pod に同じ種類の JWT を配ります。v1.22 以降、Pod のサービスアカウントのトークンは TokenRequest API で取得された**短命な**もので、projected volume としてマウントされ、kubelet が自動で取り替えます。v1.24 以降は、Secret に入った長期のトークンが自動では作られなくなりました（[Kubernetes: Service Accounts](https://kubernetes.io/docs/concepts/security/service-accounts/)）。

Pod の定義で、**宛先（audience）と寿命**を指定したトークンを追加でマウントできます。

```yaml
  volumes:
  - name: cloud-token
    projected:
      sources:
      - serviceAccountToken:
          audience: sts.amazonaws.com
          expirationSeconds: 3600
          path: token
```

kubelet は、トークンが寿命の 80% を過ぎるか 24 時間を超えると、新しいものに取り替えます。取り替わったファイルを読み直すのはアプリの責任で、公式の説明は「5 分に 1 回読み直す程度で多くの場合は足りる」としています（[Kubernetes: Configure Service Accounts for Pods](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/#serviceaccount-token-volume-projection)）。

### 手元で: k3s のトークンを読み、検証する

Docker の中で k3s（v1.33.4+k3s1）を 1 ノードだけ起動し、名前空間 `shop` にサービスアカウント `api` と、上の volume を持つ Pod `api-0` を作りました。Pod の中のトークンを取り出して、第 127 回の手順で Base64URL をほどきます。

```
$ docker run -d --privileged --name ll109-k3s rancher/k3s:v1.33.4-k3s1 server --disable=traefik,metrics-server,local-storage
$ docker exec ll109-k3s kubectl -n shop exec api-0 -- cat /var/run/secrets/cloud/token > cloud.jwt
$ python3 dec.py cloud.jwt
cloud.jwt {"alg": "RS256", "kid": "3RjL32ly2RSSOwNmwKchOA3xtspEClCNZ9pawzq_2j8"}
{
  "aud": ["sts.amazonaws.com"],
  "exp": 1790596606,
  "iat": 1790593006,
  "iss": "https://kubernetes.default.svc.cluster.local",
  "kubernetes.io": {
    "namespace": "shop",
    "node": { "name": "c0deefbfcc1a", "uid": "3d6f67eb-..." },
    "pod": { "name": "api-0", "uid": "54828651-..." },
    "serviceaccount": { "name": "api", "uid": "19627406-..." }

  "sub": "system:serviceaccount:shop:api"

```

`sub` は `system:serviceaccount:名前空間:名前` の形で、`aud` は指定したとおり、`exp - iat` はちょうど 3600 秒です。トークンは Pod とノードの UID まで抱えています。

同じ Pod に既定でマウントされるトークン（`/var/run/secrets/kubernetes.io/serviceaccount/token`）も読み比べると、違いがありました。

```
  "aud": ["https://kubernetes.default.svc.cluster.local", "k3s"],
  "exp": 1822129006,
  "iat": 1790593006,
  "kubernetes.io": { ..., "warnafter": 1790596613 },
```

`exp - iat` は 31,536,000 秒、つまり **1 年**です。kube-apiserver の `--service-account-extend-token-expiration`（既定で有効）は、古い長期トークンからの移行で壊れないよう、自動で差し込まれるトークンの期限を最大 1 年まで延ばします（[kube-apiserver](https://kubernetes.io/docs/reference/command-line-tools-reference/kube-apiserver/)）。代わりに `warnafter`（ここでは発行の約 1 時間後）を過ぎたトークンが使われると、API サーバが警告を記録できるようになっています。**「Pod のトークンは短命」は、宛先と寿命を自分で指定した projected token についての話**だと分かります。

寿命の下限も確かめました。

```
$ kubectl -n shop create token api --audience sts.amazonaws.com --duration 5m
error: failed to create token: ... spec.expirationSeconds: Invalid value: 300:
       may not specify a duration less than 10 minutes
```

### クラスタも OIDC の発行者になる

外のクラウドがこのトークンを信じるには、公開鍵が要ります。Kubernetes の API サーバは、`/.well-known/openid-configuration` と `/openid/v1/jwks` を公開します。中身は OIDC と互換になるよう作られていますが、トークンの検証に必要な項目だけを載せたものです（[Kubernetes: Service account issuer discovery](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/#service-account-issuer-discovery)）。

```
$ kubectl get --raw /.well-known/openid-configuration
{"issuer":"https://kubernetes.default.svc.cluster.local",
 "jwks_uri":"https://172.17.0.30:6443/openid/v1/jwks",
 "response_types_supported":["id_token"],"subject_types_supported":["public"],
 "id_token_signing_alg_values_supported":["RS256"]}
```

手元の k3s の `jwks_uri` は、Docker の内部アドレスを指しています。外のクラウドはここに届きません。実際に使うときは、`--service-account-issuer` と `--service-account-jwks-uri` を**外から届く https の URL**に設定し、そこに JWKS を置きます（同じページ）。EKS はクラスタごとに公開の Discovery を用意し、署名用の秘密鍵を 7 日ごとにローテーションしています（[Amazon EKS: IRSA](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html)）。

この JWKS を使って、STS の役をする 30 行ほどの模型を Python（cryptography 48）で書きました。署名、`iss`、`exp`、`aud` を確かめ、`sub` を信頼ポリシーの条件と照合します。

```python
POLICY = {
    "iss": "https://kubernetes.default.svc.cluster.local",
    "StringEquals": {"aud": "sts.amazonaws.com"},
    "StringLike":   {"sub": "system:serviceaccount:shop:api"},
}
# kid で JWKS から鍵を選び、RSA PKCS#1 v1.5 + SHA-256 で検証 → iss → exp → aud → sub
```

```
$ python3 sts.py cloud.jwt default.jwt forged.jwt
cloud.jwt    -> OK: system:serviceaccount:shop:api に短命な認証情報を発行（exp まで 3551 秒）
default.jwt  -> NG: aud=['https://kubernetes.default.svc.cluster.local', 'k3s']
forged.jwt   -> NG: 署名
```

既定のトークンは、同じ鍵で正しく署名されていても `aud` で落ちます。**クラスタの API 宛てのトークンを、クラウドに持ち込ませない**ための仕切りです。`forged.jwt` は、`sub` を `system:serviceaccount:shop:admin` に書き換えたもので、署名で落ちました。

<Callout type="warn" title="誤解 2: Pod を消せば、そのトークンは使えなくなる">
  Kubernetes のドキュメントは、projected token は Pod かサービスアカウントが消えると**API に対して**無効になると書いています（[Kubernetes](https://kubernetes.io/docs/tasks/configure-pod-container/configure-service-account/#serviceaccount-token-volume-projection)）。
  手元で、Pod を消す前後に TokenReview でトークンを API サーバに問い合わせると、たしかに結果が変わりました。

  ```
  消す前:   authenticated=true
  消した後: authenticated=  error=[invalid bearer token, service account token has been invalidated]
  ```

  ところが、同じトークンを上の STS の模型に渡すと、Pod を消した後も `OK` が返りました。
  模型は第 130 回でいう**ローカルでの検証**をしていて、署名と期限しか見ないからです。
  API サーバは Pod の UID をトークンと照らし合わせられますが、外の検証者はクラスタの中の状態を知りません。
  外のクラウドにとって、トークンを無効にする手段は**期限が来ること**だけです。寿命を短く指定する意味はここにあります。
</Callout>

## EKS と GKE での形

同じ仕組みの上に、各クラウドは使いやすい形を用意しています。

**IRSA（IAM roles for service accounts）** は、上の模型そのままの形です。クラスタの OIDC 発行者を IAM に登録し、サービスアカウントに `eks.amazonaws.com/role-arn` の注釈を付けると、Webhook が Pod に環境変数 `AWS_ROLE_ARN` と `AWS_WEB_IDENTITY_TOKEN_FILE`（`/var/run/secrets/eks.amazonaws.com/serviceaccount/token`）を差し込みます。AWS SDK はこのファイルを読み、自分で `AssumeRoleWithWebIdentity` を呼びます（[Amazon EKS: Configure Pods](https://docs.aws.amazon.com/eks/latest/userguide/pod-configuration.html)）。信頼ポリシーには、クラスタごとの発行者と `sub`（`system:serviceaccount:NS:SA`）を書きます。

**EKS Pod Identity** は、クラスタごとに OIDC の発行者を IAM に登録する手間をなくしたものです。ロールの信頼ポリシーには `pods.eks.amazonaws.com` というサービスの主体を 1 つ書くだけで済み、どのサービスアカウントにどのロールを渡すかは EKS の側の「関連づけ」で管理します。Pod には宛先 `pods.eks.amazonaws.com`、寿命 24 時間の projected token が入り、各ノードのエージェント（`169.254.170.23`）がそれを使って EKS Auth API の `AssumeRoleForPodIdentity` を呼び、SDK に認証情報を渡します（[Amazon EKS: How Pod Identity works](https://docs.aws.amazon.com/eks/latest/userguide/pod-id-how-it-works.html)、[Pod Identities](https://docs.aws.amazon.com/eks/latest/userguide/pod-identities.html)）。

**GKE の Workload Identity Federation** は、`PROJECT_ID.svc.id.goog` という形のプールを使い、各ノードの GKE メタデータサーバがワークロードの要求を仲介します。IAM の許可には `principal://iam.googleapis.com/projects/番号/locations/global/workloadIdentityPools/PROJECT_ID.svc.id.goog/subject/ns/名前空間/sa/名前` の形で主体を書きます。注意点として、**同じプロジェクトの別のクラスタで、同じ名前空間と同じ名前のサービスアカウントは、IAM から見て同じ主体**になります（[Google Cloud: About Workload Identity Federation for GKE](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity)）。信頼できないクラスタを同じプロジェクトに置くと、そのクラスタから本番の権限を得られます。前の節の `sub` の広すぎる条件と、同じ種類の問題です。

## インスタンスメタデータと IMDSv2

もっと前からある「機械の ID」が、仮想マシンの**インスタンスメタデータサービス**（IMDS）です。EC2 のインスタンスに IAM ロールを付けると、インスタンスの中から `169.254.169.254` にある HTTP のサービスに尋ねるだけで、そのロールの一時的な認証情報がもらえます。ここにも長期の秘密はありません。**「このマシンの中から尋ねた」ことが身元の証明**になっているわけです。

この前提は、**マシンの中から尋ねたのが本当にそのアプリか**を確かめていません。2019 年 7 月に発覚した Capital One の侵害では、設定を誤った Web アプリケーションファイアウォールが入口になりました（[米司法省](https://www.justice.gov/usao-wdwa/pr/former-seattle-tech-worker-convicted-wire-fraud-and-computer-intrusions)）。報道や分析によれば、攻撃者はファイアウォールに外からの要求を中継させる SSRF（サーバ側リクエストの偽造。サーバに、攻撃者の指定した宛先へ要求を送らせる攻撃）でメタデータサービスに届き、ファイアウォールのロールの認証情報を得ました。そのロールには権限が付きすぎており、S3 のバケットの一覧と読み出しができました（[Krebs on Security](https://krebsonsecurity.com/2019/08/what-we-can-learn-from-the-capital-one-hack/)）。

AWS は同じ年の 11 月に **IMDSv2** を発表しました（[AWS Security Blog, 2019-11-19](https://aws.amazon.com/blogs/security/defense-in-depth-open-firewalls-reverse-proxies-ssrf-vulnerabilities-ec2-instance-metadata-service/)）。

```
# まず PUT でセッショントークンをもらう（寿命は最大 6 時間）
TOKEN=$(curl -X PUT http://169.254.169.254/latest/api/token \
  -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
# 以後の要求にはトークンをヘッダで付ける
curl http://169.254.169.254/latest/meta-data/ -H "X-aws-ec2-metadata-token: $TOKEN"
```

同じ記事は、設定の甘いファイアウォール、リバースプロキシ、SSRF、外に開いた L3 のファイアウォールや NAT の 4 つに対して、次の工夫を挙げています。

- **PUT で始める**: PUT は Web サイトやブラウザではあまり使われない種類の要求で、外からの要求を中継してしまう機器でも通りにくい
- **以後の要求に秘密のトークンを要求する**: PUT で始めてトークンをヘッダで求める組み合わせは、URL しか操れない SSRF に対して、v1 より常に強い
- **X-Forwarded-For が付いた要求にはトークンを発行しない**: リバースプロキシを経由した要求を断る
- **応答の IP パケットの TTL（ホップ数の上限）を 1 にできる**: トークンがインスタンスの外へ転送されない

<Callout type="warn" title="誤解 3: IMDSv2 はメタデータの認証の仕組みだ">
  IMDSv2 のトークンは、**要求がインスタンスの中から、直接来たこと**を確かめる手間を増やすものです。
  インスタンスの中で動くプロセスなら、どれでも PUT を送ってトークンをもらえます。**どのプロセスかは区別しません**。
  SSRF のような「他人に要求を送らせる」攻撃を難しくする対策であって、中に入り込まれた後の防御ではありません。
  同じ理由で、EKS のノードで IMDS への経路を絞らないと、Pod がノードの IAM ロールの認証情報を取れてしまい、同じノードの他の Pod のロールに届く可能性もあります（[Amazon EKS: IRSA](https://docs.aws.amazon.com/eks/latest/userguide/iam-roles-for-service-accounts.html)）。
  IRSA や Pod Identity を入れても、**ノードのロールへの経路は自動では閉じない**ので、別に塞ぎます。
</Callout>

## SPIFFE と SPIRE: 環境をまたぐ共通の形

ここまでの仕組みは、発行者がクラウドや CI ごとに違い、`sub` の形もばらばらでした。**SPIFFE** は、ワークロードの身元の表し方と配り方を、環境によらず揃えるための仕様です（[SPIFFE Concepts](https://spiffe.io/docs/latest/spiffe-about/spiffe-concepts/)）。

- **SPIFFE ID**: `spiffe://信頼ドメイン/ワークロードの識別子` の形の URI。第 173 回のメッシュで出てくる `spiffe://cluster.local/ns/shop/sa/api` がこれ
- **SVID**: SPIFFE ID を証明する文書で、**X.509 の証明書**（X.509-SVID）と **JWT**（JWT-SVID）の 2 形式がある。JWT-SVID はリプレイ攻撃を受けやすいので、仕様は可能な限り X.509-SVID を使うよう勧めている
- **Workload API**: ワークロードが SVID を受け取る窓口。呼び出す側は**自分の身元を知る必要も、認証トークンを持つ必要もない**

最後の点が要です。SVID をもらうのに秘密が要るなら、その秘密をどう配るかという元の問題に戻ってしまいます。実装の **SPIRE** は、これを**証明（アテステーション）**で解きます（[SPIRE Concepts](https://spiffe.io/docs/latest/spire-about/spire-concepts/)）。

```
ノードの証明:         SPIRE Agent が起動時に、自分のノードが何者かをサーバに示す
                      （AWS のインスタンス識別文書、Kubernetes のサービスアカウントトークンなど）
ワークロードの証明:   Workload API を呼んだプロセスについて、Agent がカーネルや kubelet に尋ねて属性を集める
                      （Unix の uid/gid、Kubernetes の名前空間やサービスアカウントなど）
                      → 登録済みのセレクタと一致すれば、その SPIFFE ID の SVID を渡す
```

IMDS との違いがはっきりします。IMDS は「このマシンの中から来た」までしか確かめませんでした。SPIRE は、**どのプロセスが**尋ねたかを、プロセスの側の申告ではなくカーネルや kubelet に確かめます。X.509-SVID は第 109 回の証明書そのもので、第 113 回の mTLS にそのまま使えます。メッシュが各プロキシに配っていた短命な証明書は、この形です。

## Sigstore: 署名の鍵も持たない

第 168 回では、Sigstore がコンテナのイメージに「鍵を持たずに」署名する話が出てきます。その仕組みはこの回の組み合わせです。認証局の **Fulcio** は、CI の OIDC トークンなどの身元を確かめ、その身元を SAN（第 109 回）に、発行者を拡張に書いた**有効期間 10 分**の証明書を発行します。署名に使う秘密鍵はその場で作って捨てます（[Sigstore: Fulcio](https://docs.sigstore.dev/certificate_authority/overview/)）。

```
GitHub の OIDC トークン（このリポジトリのこのワークフロー）
  → Fulcio が 10 分の証明書を発行（公開鍵 ＋ 身元）
  → その場で作った秘密鍵でイメージの digest に署名（第 106 回）→ 秘密鍵は捨てる
  → 署名と証明書を透明性ログに記録（第 111 回の CT と同じ考え方）
```

検証する側は、「この鍵で署名された」ではなく「**このリポジトリのこのワークフローが**署名した」を確かめます。ここでも、検証の条件に書く身元（どのリポジトリ、どのワークフローか）を広く書けば、意味が薄れます。

## どの部品と組み合わさっているか

| 部品 | ここでの役 | 前の回 |
| --- | --- | --- |
| JWT | 実行環境が発行する身元の文書の形式 | 第 127 回 |
| 署名（RS256 など） | 文書を発行者が書いたことの保証。改ざんした `sub` は落ちる | 第 106 回 |
| Discovery と JWKS | 発行者の公開鍵をクラウドに配る。ローテーション中は複数の鍵が並ぶ | 第 129 回、第 135 回 |
| TLS とトラストストア | JWKS を取りに行く経路が本物の発行者につながっていることの保証 | 第 110 回 |
| `aud` | クラスタ宛て、別のクラウド宛てのトークンの持ち込みを防ぐ | 第 127 回、第 130 回 |
| 信頼ポリシーの `sub` の条件 | **どの**ジョブ、どの Pod にロールを渡すか。秘密の代わりの役 | 第 131 回 |
| 短命な認証情報 | 漏れたときの被害を時間で区切る。外の検証者にとって唯一の失効手段 | 第 108 回 |
| X.509-SVID と mTLS | 通信の相手がどのワークロードかを確かめる | 第 109 回、第 113 回、第 173 回 |

この表の中で**保証を何もしないもの**に気づくことが大切です。署名は「GitHub が発行した」ことしか言いません。自分の組織のジョブかどうか、本番に触ってよいジョブかどうかは、条件の書き方だけで決まります。

## まとめ

- 長期のアクセスキーは、期限がなく、ベアラ型で、置き場所が増える。ワークロード ID フェデレーションは、実行環境が発行する OIDC トークンをクラウドの短命な認証情報に交換し、長期の秘密を配らない
- 役はずれている。IdP は GitHub や Kubernetes のクラスタで、RP はクラウドの STS。検証の手順は第 127 回、第 129 回と同じで、署名、`iss`、`aud`、`exp`
- GitHub の発行者は全リポジトリで共通なので、**署名が正しいことは自分の組織のジョブであることを意味しない**。信頼ポリシーの `sub` の条件が秘密の代わりになる。`repo:org/repo:*` はプルリクエストや任意のブランチを、`repo:org*` は別の組織まで通す
- AWS は共有の発行者で `sub` の条件がないロールを作成時に拒むが、広すぎる条件と既存のロールは救わない。名前は使い回されるので、GitHub は ID を含む `sub` に移りつつある
- Kubernetes の projected token は宛先と寿命を指定でき、寿命の下限は 10 分。既定でマウントされるトークンは移行のため 1 年まで延ばされていた。Pod を消すと API サーバでは無効になるが、外の検証者には期限まで有効に見える
- IMDSv2 は PUT とヘッダのトークンで SSRF を難しくする対策で、どのプロセスかは区別しない。IRSA や Pod Identity を入れても、ノードのロールへの経路は別に塞ぐ
- SPIFFE は身元を URI と X.509/JWT の SVID で揃え、SPIRE はカーネルや kubelet に尋ねる証明で「どのプロセスか」まで確かめる。Sigstore は同じ OIDC の身元から 10 分の証明書を作り、署名の鍵すら持たない

次の第 137 回は、この 4 章の総まとめです。ここまでの部品を組み合わせた構成の型を並べ、それぞれで**どの部品が何を保証し、どこが弱いのか**を 1 枚の表に集めます。
