## 同じ Cookie が、どちらにもなる

`widget.example` というチャットのサービスがあるとします。利用者が `widget.example` を直接開いてログインすると、ブラウザは `widget.example` の Cookie を覚えます。この Cookie は、そのとき**ファーストパーティ Cookie**（第一者 Cookie）です。

次に利用者が `news.example` を開き、そのページに `widget.example` のチャットが iframe で埋め込まれていたとします。iframe の読み込みに付いていくのは、**さっきと同じ Cookie** です。しかしこの場面では、同じ Cookie が**サードパーティ Cookie**（第三者 Cookie。第 118 回ではこちらの表記を使います）と呼ばれます。

Cookie の値も属性も変わっていません。変わったのは、**利用者がいま見ているページ**だけです。この回の出発点はここです。

- 第一者か第三者かは、Cookie そのものの性質ではなく、**その Cookie が使われる文脈**で決まる
- ブラウザが制限してきたのは第三者の文脈での使用で、その止め方は「遮断」「分けて保存」「許可制」の 3 通りがある
- Cookie だけ止めても、localStorage や HTTP キャッシュが残っていれば同じことができるので、**ストレージ全体を分ける**流れになった

## 第一者と第三者を決めるもの

「第一者」は、利用者が訪れているサイトそのものです。アドレスバーに出ているページ（**トップレベル**のページ）のサイトがそれにあたります。「第三者」は、利用者と訪問先の二者の間に、利用者の意図とは別に入り込む三番目の当事者です。広告や計測の配信元がその典型で、呼び名はここから来ています。

MDN の定義は、この関係を Cookie に当てはめたものです（[MDN: Third-party cookies](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Third-party_cookies)）。

- Cookie のドメインとスキームが、アドレスバーに出ているページと一致すれば、そのページと同じサイトの Cookie で、**ファーストパーティ Cookie** と呼ぶ
- 違えば、**サードパーティ Cookie** と呼ぶ

ここでの「サイト」は第 93 回で見たとおり、スキームと登録可能ドメイン（eTLD+1）の組です。オリジンではありません。冒頭の例を表にすると、次のようになります。

| 利用者が見ているページ | 読み込まれる資源 | `widget.example` の Cookie は |
| --- | --- | --- |
| `https://widget.example/` | そのページ自身 | 第一者 |
| `https://news.example/` | `https://widget.example/chat` の iframe | **第三者** |
| `https://news.example/` | `https://widget.example/pixel.gif` の画像 | **第三者** |
| `https://app.widget.example/` | `https://widget.example/api` への fetch | 第一者（同じサイト） |

最後の行は、オリジンは違いますが同じサイトなので第一者です。第 95 回の CORS はオリジンの単位でかかるので、この場合も CORS の設定は要ります。**CORS の「クロスオリジン」と、第三者 Cookie の「クロスサイト」は別の物差し**です。

Cookie の仕様の改訂版 RFC 6265bis も、第三者 Cookie を「利用者が見ている主な資源（ふつうは Web ページ）とは別のサーバから取得される、埋め込まれた内容に結び付いた Cookie」と説明しています。そのうえで、多くのブラウザが第三者 Cookie をさまざまな方法で制限していること、遮断するもの、第一者の文脈ごとに分けるもの、設定で決めるものがあることを述べ、**互換性が許す限り制限的な方針を採るよう推奨**しています（[RFC 6265bis-22 7.1](https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-7.1)）。仕様は特定のやり方を決めておらず、**ブラウザごとに違う**ことが前提になっています。

<Callout type="warn" title="よくある誤解: 「Domain 属性に別のドメインを書いた Cookie が第三者 Cookie」">
  `Domain` 属性は「どのホストに送るか」を決めるだけで、第一者か第三者かとは関係ありません。
  そもそも `news.example` の応答が `Domain=widget.example` の Cookie を設定することはできず、ブラウザが拒否します（[RFC 6265 5.3](https://www.rfc-editor.org/rfc/rfc6265.html#section-5.3)）。
  第三者 Cookie は「よそのドメインの Cookie を作ること」ではなく、**`widget.example` が自分で設定した自分の Cookie を、よそのサイトのページの中で使うこと**です。
  だから同じ Cookie が、トップレベルが `widget.example` なら第一者、`news.example` なら第三者になります。
</Callout>

### 入れ子の iframe では、祖先もすべて見る

トップレベルだけを比べればよいわけではありません。RFC 6265bis は、Cookie の判定に使う「site for cookies」を次のように決めています。入れ子の文書では、**トップレベルのオリジンが、その文書と、そのすべての祖先の文書と同じサイトであるとき**に限ってトップレベルのオリジンを使い、そうでなければ中身のないオリジン（opaque origin）にする（[RFC 6265bis-22 5.2.1](https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-5.2.1)）。

```
トップレベル  a.example
  └ iframe    b.example        ← a.example と別のサイト
      └ iframe a.example       ← トップと同じサイトだが、途中に b.example が挟まる
```

一番下の iframe はトップと同じサイトですが、途中に別のサイトが挟まっているので、**第三者の文脈として扱われます**。間の `b.example` が、自分の中に `a.example` を埋め込んで利用者の Cookie 付きで操作する、という抜け道を塞ぐためです。

## どこで使われてきたか

第三者 Cookie は、広告のためだけの仕組みではありません。止めると何が困るかを知るために、用途を分けておきます。

| 用途 | 仕組み | 第三者 Cookie が要る理由 |
| --- | --- | --- |
| 広告の配信とサイトをまたぐ追跡 | 多くのサイトに同じ配信元の画像や script を埋め込む | 配信元が**どのサイトでも同じ ID** を受け取り、利用者の閲覧を結び付ける |
| 埋め込みのウィジェット（チャット、コメント欄、動画） | iframe で自社のページを埋め込む | 埋め込まれた先でも、利用者のログインや設定を使いたい |
| 埋め込み型の SSO や決済 | IdP や決済事業者の iframe を置く | iframe の中で「IdP にログイン済みか」を確かめたい（第 124 回） |
| 分析の計測 | 計測用の script をページに入れる | 計測の事業者のドメインで Cookie を持てば、サイトをまたいで同じ人と数えられる |

分析の計測は、多くの場合すでに**ページ側のドメインの Cookie**（計測用の script が `document.cookie` で書く、第一者 Cookie）で動いています。そのため、第三者 Cookie の制限で失われるのは主に「サイトをまたいで同じ人と数えること」です。ただし第一者 Cookie にも寿命などの制限がかかるブラウザがあり、それは第 97 回で見ます。

表の 1 行目と 2〜3 行目は、ブラウザから見ると**同じ形**をしています。どちらも「よそのサイトの中で、自分の Cookie を使う」ことです。ブラウザは要求の目的を区別できないので、追跡だけを止めることはできません。以下で見る CHIPS と Storage Access API は、**2〜3 行目の正当な用途を、追跡に使えない形で残す**ための仕組みです。

## SameSite とは別の話

第三者 Cookie の制限は、SameSite 属性（第 118 回で詳しく見ます）と混同されがちです。どちらも同じ「サイト」の物差しを使いますが、**決める人と目的が違います**。

| | SameSite 属性 | 第三者 Cookie の制限 |
| --- | --- | --- |
| 決める人 | Cookie を設定する**サイト** | **ブラウザ**（と利用者の設定） |
| 目的 | サイトを守る（CSRF などで、よそから始まった要求に Cookie を付けさせない） | **利用者を守る**（サイトをまたいで追跡させない） |
| 見るもの | その要求がどこから始まったか | トップレベルのサイトと、その Cookie のサイトが違うか |
| 緩める方法 | `SameSite=None; Secure` を書く | 書いても緩まない。CHIPS か Storage Access API を使う |

2 つは重ねてかかります。第三者の文脈に Cookie を出したいなら、まずサイト側が `SameSite=None; Secure` を書いて「よその文脈でも送ってよい」と宣言し、そのうえで**ブラウザがそれを許すか**が問われます。

<Callout type="warn" title="よくある誤解: 「SameSite=None にすれば、埋め込み先でも Cookie が届く」">
  `SameSite=None` は、サイトが自分の Cookie について「よそからの要求にも付けてよい」と言っているだけです。
  第三者 Cookie を遮断しているブラウザ（Safari など）では、`SameSite=None; Secure` の Cookie でも iframe の中には届きません。後の実験の WebKit がそうなりました。
  SameSite は**必要条件**であって、十分条件ではありません。
</Callout>

## 分けて保存する: CHIPS

追跡に使われるのは、第三者 Cookie が**どのトップレベルのサイトの中でも同じ値**だからです。`news.example` の中の `widget.example` と、`shop.example` の中の `widget.example` が同じ Cookie を受け取るので、両方の閲覧を同じ人に結び付けられます。

それなら、**トップレベルのサイトごとに別の Cookie 置き場を用意すれば**、埋め込みの中での状態は保ちつつ、サイトをまたいだ結び付けはできなくなります。これが **CHIPS**（Cookies Having Independent Partitioned State）で、Cookie に `Partitioned` 属性を付けて使います。

```
Set-Cookie: __Host-chat=34d8g; SameSite=None; Secure; Path=/; Partitioned
```

`Partitioned` の Cookie は、設定したサイトと、そのときのトップレベルのサイトの**2 つを鍵にして**保存されます（[MDN: CHIPS](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Privacy_sandbox/Partitioned_cookies)）。この 2 つめの鍵を**パーティションキー**と呼び、スキームを含むトップレベルのサイトから作ります。`Secure` は必須で、サブドメインと共有しないなら `__Host-` 接頭辞を付けることが勧められています。

```
Cookie の置き場（ブラウザの中）

  パーティションキーなし（従来）      Partitioned
  ┌──────────────────────┐          ┌───────────────────────────────────┐
  │ widget.example       │          │ (widget.example, news.example)    │ chat=A
  │   chat=X             │          │ (widget.example, shop.example)    │ chat=B
  │  どのトップでも同じ  │          │ (widget.example, widget.example)  │ chat=C
  └──────────────────────┘          └───────────────────────────────────┘
```

`news.example` の中のチャットは `chat=A` だけを、`shop.example` の中のチャットは `chat=B` だけを見ます。`widget.example` を直接開いたときも、別の置き場です。**同じ人だと結び付ける材料が、置き場の外に出ない**ので、埋め込みの状態は保てても追跡には使えません。

対応は、執筆時点（2026 年 9 月）で次のとおりです。

| ブラウザ | CHIPS |
| --- | --- |
| Chrome | 114 から既定で有効（[Privacy Sandbox: CHIPS](https://privacysandbox.google.com/cookies/chips)）。1 つのパーティションに 180 個まで、埋め込まれたサイトごとに 10 KB までの上限がある |
| Firefox | 141 で再び有効化（[Firefox 141 リリースノート](https://www.firefox.com/en-US/firefox/141.0/releasenotes/)） |
| Safari | 18.4 で対応（[WebKit Features in Safari 18.4](https://webkit.org/blog/16574/webkit-features-in-safari-18-4/)） |

MDN は、2025 年 12 月から主要なブラウザの最新版で使える機能（Baseline 2025）としています。

CHIPS は、**サイトが自分から「分けてよい」と宣言する**仕組みです。チャットの未読の状態や、埋め込み先ごとの設定のように、トップレベルのサイトごとに別々でかまわない状態に向いています。逆に「`widget.example` に一度ログインしたら、どこに埋め込まれても同じログインでいたい」という用途には使えません。置き場が分かれているので、`widget.example` を直接開いてログインした Cookie は、`news.example` の中からは見えないからです。

## 許可を求める: Storage Access API

分けずに、**従来の（パーティションキーのない）Cookie を埋め込みの中で使いたい**場合の手段が **Storage Access API** です（[MDN: Storage Access API](https://developer.mozilla.org/en-US/docs/Web/API/Storage_Access_API)）。iframe の中の文書が、ブラウザに「この埋め込みで、自分のサイトの Cookie を使わせてほしい」と頼みます。

```js
// widget.example の iframe の中
if (!(await document.hasStorageAccess())) {
  button.onclick = async () => {
    await document.requestStorageAccess()   // クリックの中で呼ぶ
    location.reload()                        // 以後の要求に Cookie が付く
  }
}
```

- `document.hasStorageAccess()` は、いまこの文書が第三者 Cookie を使えるかを返す
- `document.requestStorageAccess()` は、許可を求める。**クリックやタップなどの利用者の操作の中で呼ぶ必要がある**。埋め込みが利用者に確認を連発できないようにするためで、同じトップレベルのサイトと埋め込みのサイトの組にすでに許可があれば不要
- 許可された後の要求には、**パーティションキーのない Cookie** が付く

MDN も書いているとおり、このAPIが必要なのは**分割されていない第三者 Cookie を使いたいときだけ**です。CHIPS の Cookie には許可は要りません。Safari 18.4 の解説も、分割された Cookie と分割されていない Cookie の両方が要るなら、後者のために Storage Access API を使い続けるよう述べています。

条件の細部はブラウザで違います。Chrome は 119 でこの API を出荷し、次の条件を課しています（[Privacy Sandbox: Storage Access API](https://privacysandbox.google.com/cookies/storage-access-api)）。

- 利用者が過去に、その埋め込みのサイトを**トップレベルで訪れている**こと（知らないサイトに許可を求めさせない）
- 対象の Cookie が `SameSite=None` と `Secure` を持っていること
- 一度許可すると 30 日は確認を出さず、iframe を操作するたびにさらに 30 日延びる

Firefox と Safari も、許可を 30 日で失効させます（MDN）。Safari では、第三者 Cookie を使える経路は Storage Access API と、ポップアップのための一時的な互換の措置に限られるとしています（[WebKit: Tracking Prevention](https://webkit.org/tracking-prevention/)）。

<Callout type="note" title="Related Website Sets の行方">
  Chrome は、同じ組織が持つ複数のドメイン（`brand.example` と `brand-cdn.example` など）を「関連するサイトの組」として登録すれば、その間では確認なしに Cookie を使わせる **Related Website Sets**（旧名 First-Party Sets）と、それを使う `requestStorageAccessFor` を用意していました。
  しかし 2025 年 10 月 17 日、Google は第三者 Cookie について現行の方式（利用者が設定で選ぶ）を続けることを前提に、Related Website Sets を含む Privacy Sandbox の多くの技術を廃止すると発表しました。同じ発表で、CHIPS と FedCM は他のブラウザも対応して広く使われているので維持するとしています（[Privacy Sandbox: Update on plans](https://privacysandbox.google.com/blog/update-on-plans-for-privacy-sandbox-technologies)）。
  執筆時点（2026 年 9 月）の Chrome 153 のリリースノートでも、両者は「廃止と削除」の項に挙がっています（[Chrome 153 release notes](https://developer.chrome.com/release-notes/153)）。**他のブラウザにはもともと無く、新しく頼る仕組みではありません**。
</Callout>

## Cookie 以外も分ける: ストレージの分割

Cookie だけを止めても、追跡の材料は他にも残ります。iframe の中の `widget.example` は、localStorage に ID を書いておけば、別のサイトに埋め込まれたときにそれを読めます。HTTP キャッシュにも ID を仕込めますし、キャッシュに特定の資源があるかどうかの時間差から、閲覧の履歴を推測することもできます（[Chrome: HTTP cache partitioning](https://developer.chrome.com/blog/http-cache-partitioning)）。

そこでブラウザは、**Cookie に限らず、状態を持つものをトップレベルのサイトで分ける**方向に進みました。これを**ストレージの分割**（state partitioning、storage partitioning）と呼びます。CHIPS がサイトの宣言で分けるのに対し、こちらは**ブラウザが既定で**分けます。

| ブラウザ | 分けているもの（執筆時点、2026 年 9 月） |
| --- | --- |
| Chrome | HTTP キャッシュを 86 から、トップレベルのサイトとフレームのサイトと URL の組で分ける（[Chrome Developers](https://developer.chrome.com/blog/http-cache-partitioning)）。localStorage、sessionStorage、IndexedDB、Cache Storage、Origin Private File System、BroadcastChannel、SharedWorker、Web Locks、Service Worker などを 115 から全利用者で分ける。Blob URL は 137 から（[Privacy Sandbox: Storage partitioning](https://privacysandbox.google.com/cookies/storage-partitioning)） |
| Firefox | HTTP キャッシュ、画像やフォントのキャッシュ、接続のプール、DNS、HSTS、TLS のセッション識別子、CORS のプリフライトのキャッシュなどのネットワークの状態を 85 から、localStorage や IndexedDB などを含む状態の分割を 103 から既定で分ける（[MDN: State Partitioning](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/State_Partitioning)） |
| Safari | 第三者の localStorage と IndexedDB をトップレベルのサイトごとに分けたうえで一時的なものにし、第三者の Service Worker と HTTP キャッシュも分ける（[WebKit: Tracking Prevention](https://webkit.org/tracking-prevention/)） |

Chrome の分割のキーは、トップレベルのサイトと現在のフレームのオリジンに加えて、**途中に別のサイトが挟まっているかを示す 1 ビット**（ancestor bit）を持ちます。前の節の入れ子の iframe の問題を、ストレージの側でも同じように扱うためです。

Firefox の表に**接続のプール**が入っていることに注目してください。第 85 回で見たとおり、ブラウザは HTTP の接続を使い回しますが、`news.example` の中で開いた `widget.example` への接続を `shop.example` の中でも使い回すと、「同じ接続から来た」ことが同じ人の手がかりになります。**キャッシュも接続も、共有すれば速く、分ければ追跡されにくい**。ストレージの分割は、この交換で後者を選んだものです。分けた分だけ、同じ資源を別々に取得することになります。

<Callout type="warn" title="よくある誤解: 「Chrome は第三者 Cookie を止めていないので、埋め込みの状態の扱いは昔のまま」">
  Chrome は執筆時点（2026 年 9 月）で、第三者 Cookie を既定では遮断していません。遮断するのはシークレットモードと、利用者が設定で選んだ場合です（[MDN](https://developer.mozilla.org/en-US/docs/Web/Privacy/Guides/Third-party_cookies)）。
  しかし localStorage や IndexedDB は 115 から、HTTP キャッシュは 86 から、トップレベルのサイトで分けています。
  そのため、iframe の中で localStorage に書いた値を、その埋め込みのサイトを直接開いたときに読む、といった作りは **Chrome でも動きません**。次の実験でそうなりました。
</Callout>

## 手元で確かめる

2 つのサイトに同じ埋め込みを置き、iframe の中に Cookie が届くか、`Partitioned` を付けるとどうなるか、localStorage は分かれるかを、3 つのエンジンで比べます。

### 準備

Python の `http.server` を TLS で包んだサーバを 127.0.0.1 の 2 つのポートで動かします。`Secure` と `Partitioned` を平文の http で試すとブラウザごとの扱いの差が混ざるので、自己署名の証明書で HTTPS にし、ブラウザには証明書の誤りを無視させます。

- **トップレベル**: `https://news.localhost:18188/embed` と `https://shop.localhost:18188/embed`。どちらも `https://127.0.0.1:18189/frame` を iframe で埋め込むだけのページ。`*.localhost` はブラウザが 127.0.0.1 に向ける
- **埋め込み（ウィジェット）**: `127.0.0.1:18189`
  - `/set`: トップレベルで開くページ。`w_none`（`SameSite=None; Secure`）と `w_lax`（`SameSite=Lax`）を設定し、localStorage に `first-party` と書く
  - `/frame`: iframe の中のページ。届いた `Cookie` ヘッダ、`document.cookie`、localStorage の値、`document.hasStorageAccess()` の結果を返す。`?set=news` を付けると、iframe の中から `w_part`（`Partitioned` 付き）と `w_3p`（`Partitioned` なし）を設定し、localStorage に `from-news-frame` と書く

`news.localhost`、`shop.localhost`、`127.0.0.1` は互いに別のサイトです。ブラウザも実際にそう扱い、Chrome の Cookie の一覧では `w_part` のパーティションキーが `https://news.localhost` になりました。

手順は、(1) ウィジェットをトップレベルで開く、(2) news の中の iframe を見る、(3) news の中で `Partitioned` の Cookie を設定してから見直す、(4) shop の中の iframe を見る、(5) ウィジェットをもう一度トップレベルで開く、です。操作は Playwright（Python 版 1.63.0、作業ディレクトリの venv に入れたもの）で、利用者の普段のブラウザとは別の、使い捨てのプロファイルで行いました。

<Callout type="warn" title="テスト用の自動化ツールは、ブラウザの既定を変えている">
  最初の実行では、Chrome でも Firefox でも localStorage が分かれず、Firefox では第三者 Cookie もそのまま届きました。
  調べると、Playwright は Chromium を `--disable-features=...,ThirdPartyStoragePartitioning,...` 付きで起動し、Firefox には `network.cookie.cookieBehavior` を 4、`network.cookie.CHIPS.enabled` を false にした設定を渡していました（手元の Playwright 1.63.0 の同梱ファイルで確認）。
  以下の結果は、Chromium では `--disable-features` を上書きして分割を戻し、Firefox では `cookieBehavior` を既定の Total Cookie Protection にあたる 5 にして CHIPS を有効にしたものです。
  **自動テストで「動いた」埋め込みが、利用者のブラウザでは動かない**ことがあるのは、このためです。E2E テストでこの種の挙動を確かめるときは、起動の設定を確認してください。
</Callout>

### 結果

各段階で iframe（または (5) のトップレベルのページ）が受け取ったものです。Cookie はサーバに届いた `Cookie` ヘッダ、ls は localStorage の `w` の値です。

```
===== chromium 153.0.8010.12（Playwright の disable-features を上書き）
1 top-level 127.0.0.1/set  jar: ['w_lax', 'w_none']
2 news iframe           {'server-received': 'w_none=1', 'ls': None, 'hasSA': True}
3 news iframe (again)   {'server-received': 'w_none=1; w_part=news; w_3p=1', 'ls': 'from-news-frame'}
4 shop iframe           {'server-received': 'w_none=1; w_3p=1', 'ls': None}
5 top-level 127.0.0.1   {'server-received': 'w_none=1; w_lax=1; w_3p=1', 'ls': 'first-party'}

===== firefox 155.0（cookieBehavior=5 + CHIPS）
2 news iframe           {'server-received': '', 'ls': None, 'hasSA': False}
3 news iframe (again)   {'server-received': 'w_part=news; w_3p=1', 'ls': 'from-news-frame'}
4 shop iframe           {'server-received': '', 'ls': None}
5 top-level 127.0.0.1   {'server-received': 'w_none=1; w_lax=1', 'ls': 'first-party'}

===== webkit 26.6
2 news iframe           {'server-received': '', 'ls': 'first-party', 'hasSA': False}
3 news iframe (again)   {'server-received': 'w_part=news', 'ls': 'from-news-frame'}
4 shop iframe           {'server-received': '', 'ls': 'from-news-frame'}
5 top-level 127.0.0.1   {'server-received': 'w_lax=1; w_none=1', 'ls': 'from-news-frame'}
```

（`docCookie` など一部の項目を省いています。）サーバのログでは、iframe の要求はどれも `Sec-Fetch-Site: cross-site` でした。まとめると次のようになります。

| | Chromium（既定） | Firefox（TCP） | WebKit |
| --- | --- | --- | --- |
| (2) トップレベルで設定した `SameSite=None` の Cookie が iframe に届く | **届く** | 届かない | 届かない |
| (3) iframe の中で設定した `Partitioned` の Cookie | news の中だけで届く | news の中だけで届く | news の中だけで届く |
| (3)(4) iframe の中で設定した `Partitioned` なしの Cookie | どこでも届く（トップレベルにも） | **news の中だけ**で届く | 保存されない |
| (4)(5) iframe の中で書いた localStorage | news の中だけ | news の中だけ | 分かれなかった |

読み取れることは 4 つです。

- **Chrome は第三者 Cookie を既定で通す**。`w_none` はどの iframe にも届き、iframe の中で設定した `w_3p` はトップレベルの (5) にまで届いた。**同じ Cookie が文脈によって第三者にも第一者にもなる**ことが、そのまま見える
- **Firefox は遮断ではなく、分ける**。`Partitioned` を付けていない `w_3p` も、news の置き場に入り、news の中でだけ届いた。Total Cookie Protection は**すべての第三者 Cookie を CHIPS のように扱う**
- **WebKit は遮断する**。`SameSite=None; Secure` の `w_none` も、iframe の中で設定した `w_3p` も使えず、`Partitioned` を付けた `w_part` だけが news の中で使えた。CHIPS が**「遮断するブラウザで、埋め込みの状態を持つための手段」**になっている
- **`Partitioned` の Cookie の結果は 3 つとも同じ**だった。ブラウザごとに方針が違っても、CHIPS を使えば挙動をそろえられる

Storage Access API も試しました。WebKit では、shop の中の iframe のボタンをクリックして `requestStorageAccess()` を呼ぶと許可され、その後の fetch には (1) で設定した分割されていない `w_none=1` が付きました。ただし自動化の環境で確認の画面がどう扱われたかは見えておらず、Chrome は `NotAllowedError` で拒否、Firefox は応答が返らず時間切れになりました。**実際の利用者が見る確認の流れまでは再現できていません**。

WebKit で localStorage が分かれなかった点は、WebKit の公式の説明（第三者の localStorage はトップレベルのサイトごとに分ける）と食い違います。Playwright の WebKit のビルドや設定によるものか、ここでは確かめきれていません。Safari 本体での挙動としては読まないでください。また、Chrome で利用者が第三者 Cookie の遮断を選んだ状態も、プロファイルの設定と CDP の `Network.setCookieControls` で再現を試みましたが、この手元の環境では遮断されませんでした。

## 組み合わせで決まる

埋め込みで Cookie が使えるかどうかは、1 つの部品では決まりません。

| 部品 | 決めていること | 回 |
| --- | --- | --- |
| サイト（eTLD+1） | 第一者か第三者かの物差し。Public Suffix List で決まる | 第 93 回 |
| CORS | よそのオリジンの応答を読ませるか。Cookie を付けた fetch では `Access-Control-Allow-Credentials` も要る | 第 95 回 |
| SameSite | サイトが、よそから始まった要求に Cookie を付けてよいと宣言するか | 第 118 回 |
| 第三者 Cookie の制限 | ブラウザが、第三者の文脈で Cookie を遮断するか、分けるか、通すか | この回、第 97 回 |
| CHIPS | サイトが「分けてよい」と宣言し、分けた置き場で使う | この回 |
| Storage Access API | 利用者の操作を条件に、分けていない Cookie を使う許可を得る | この回 |
| Fetch Metadata | サーバが、要求が第三者の文脈から来たかを `Sec-Fetch-Site` で知る | 第 98 回 |

たとえば、`app.example` のページから `api.widget.example` へ Cookie 付きの fetch を送るには、(1) CORS で資格情報を許し、(2) Cookie に `SameSite=None; Secure` を付け、(3) ブラウザが第三者 Cookie を通す、の 3 つがそろう必要があります。(3) はサイトの側では決められないので、Safari では (1) と (2) を正しく書いても届きません。フロントと API をどこに置けばこの問題を避けられるかは、章の最後の第 101 回で構成の型として整理します。

## まとめ

- 第一者か第三者かは Cookie の性質ではなく、**トップレベルのサイト（と入れ子の祖先すべて）と、その Cookie のサイトが同じか**で決まる。同じ Cookie が文脈によってどちらにもなる
- `Domain` 属性は送り先を決めるだけで、第三者かどうかとは関係ない。CORS のクロスオリジンと、第三者のクロスサイトも別の物差し
- SameSite はサイトが自分を守るために選ぶもの、第三者 Cookie の制限はブラウザが利用者のためにかけるもの。`SameSite=None` は必要条件にすぎない
- **CHIPS**（`Partitioned`）は、トップレベルのサイトごとに分けた置き場で Cookie を使う。Chrome 114、Firefox 141、Safari 18.4 が対応し、どのブラウザでも挙動をそろえられる
- **Storage Access API** は、利用者の操作を条件に、分けていない Cookie を埋め込みの中で使う許可を得る。Chrome の Related Website Sets は廃止に向かっている
- Cookie だけでなく localStorage、HTTP キャッシュ、接続のプールまでトップレベルのサイトで分ける**ストレージの分割**が進んでおり、Chrome も第三者 Cookie を通したまま分割はしている
- 手元の実験では、Chrome は通す、Firefox は分ける、WebKit は遮断する、と方針が分かれた。自動テストのツールがこの既定を変えていることにも注意する

次の回では、ブラウザごとの違いをもう一段掘り下げます。Safari の ITP が第三者 Cookie の遮断に至るまでに何を変えてきたか、そして**第一者 Cookie にまで**かかる制限、Firefox と Chrome の経緯、リダイレクトを使って一瞬だけ第一者になる手口への対策を見ます。
