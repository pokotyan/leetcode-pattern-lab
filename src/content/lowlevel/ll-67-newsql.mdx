## 1 台に収まらなくなったら

ここまでの 3 回は、1 台のマシンの中の話でした。ページ、インデックス、WAL、MVCC。どれも、**1 つのバッファプールと 1 本の WAL** を前提にしています。

データや書き込みが 1 台の限界を超えたとき、昔から取られてきた手は 2 つです。

**読み取りレプリカを足す。** 前回見たとおり、WAL を別のマシンに送れば、同じ内容のデータベースが増えます。読み取りは分散できます。ただし、**書き込みは相変わらず 1 台**です。

**手作業でシャーディングする。** ユーザ ID の範囲などで、データを複数のデータベースに分けます。書き込みも分散できますが、その代償をすべてアプリが払うことになります。

- どのデータがどのシャードにあるかを、アプリが知っている必要がある
- シャードをまたぐ JOIN が書けない
- シャードをまたぐトランザクションが書けない（システムデザインの読み物の<a href={`${import.meta.env.BASE_URL}reading/distributed-transaction/`}>分散トランザクション</a>で見た、あの問題）
- 1 つのシャードが膨らんだら、止めずに分け直すのが極めて難しい

**NewSQL** は、この手作業をデータベースの内側に取り込んだものです。アプリからは 1 台の SQL データベースに見え、トランザクションも使えます。その下で、データは自動的に何十台にも分かれています。Google の Spanner（[OSDI 2012 の論文](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf)）と、それに影響を受けた CockroachDB、TiDB、YugabyteDB などがこの系統です。

## 5 つの層

製品ごとに細部は違いますが、構造はおおむね同じ層に分かれます。

```
 ┌───────────────────────────────────────────┐
 │ SQL 層：構文解析、実行計画                    │  どのノードに来ても同じ SQL が通る
 ├───────────────────────────────────────────┤
 │ トランザクション層：MVCC、2PC、時刻           │  複数の range にまたがる更新
 ├───────────────────────────────────────────┤
 │ 分散 KV 層：キー範囲（range）への分割と配置     │  どのキーがどのノードにあるか
 ├───────────────────────────────────────────┤
 │ 複製層：range ごとの Raft                     │  1 つの range を 3 台で持つ
 ├───────────────────────────────────────────┤
 │ ストレージエンジン：LSM-tree の KV            │  各ノードのディスク
 └───────────────────────────────────────────┘
```

一番下は、多くの場合 **LSM-tree** です（<a href={`${import.meta.env.BASE_URL}reading/db-index/`}>データベースの索引</a>の読み物で見た構造）。TiDB のストレージである TiKV は RocksDB を使い、CockroachDB は RocksDB から、Go で書き直した互換エンジンの **Pebble** に移りました。Pebble は v20.2 で既定になっています（[Cockroach Labs](https://www.cockroachlabs.com/blog/pebble-rocksdb-kv-store/)）。

<Callout type="note" title="Pebble に移った理由の 1 つは FFI">
  CockroachDB は Go で書かれていて、RocksDB は C++ です。
  RocksDB を呼ぶたびに cgo の境界を越えることになり、
  第 76 回で見た「境界をまたぐ呼び出しのコスト」と「言語をまたいだデバッグの難しさ」を抱えていました。
  Cockroach Labs は Pebble の利点として、この cgo の境界を越えずに済むことを挙げています（[Cockroach Labs](https://www.cockroachlabs.com/blog/pebble-rocksdb-kv-store/)）。
</Callout>

## テーブルを 1 本のキー空間に並べる

分散 KV 層が扱うのは、**バイト列のキーと値の組**だけです。そこで、テーブルの行もインデックスも、すべてキーと値に変換してから載せます。TiDB の変換規則は次のとおりです（[TiDB 文書](https://docs.pingcap.com/tidb/stable/tidb-computing)）。

| 何を | キー | 値 |
| --- | --- | --- |
| 行 | `t{テーブル ID}_r{行 ID}` | 列の値の並び |
| ユニークインデックス | `t{テーブル ID}_i{インデックス ID}_{列の値}` | 行 ID |
| ユニークでないインデックス | `t{テーブル ID}_i{インデックス ID}_{列の値}_{行 ID}` | なし |

たとえば `users(id, email)` で `email` にインデックスがあれば、1 行につき 2 つのキーができます。

```
 t42_r1001                  → (1001, 'a@example.com')     ← 行そのもの
 t42_i1_a@example.com       → 1001                        ← インデックス
```

見覚えのある形のはずです。第 65 回で見た InnoDB のセカンダリインデックスは、**葉に主キーを持ち、それを使ってもう一度クラスタ化インデックスを引く**二段引きでした。ここでもまったく同じで、`email` で検索すると、まずインデックスのキーを引いて行 ID を得て、次に行のキーを引きます。違うのは、**2 つのキーが別々のマシンにあるかもしれない**ことです。

キーはバイト列として**辞書順に並びます**。同じテーブルの行は `t42_r` で始まるキーとして連続し、同じインデックスの項目も連続します。つまり、この巨大なキー空間は、**テーブルごと、インデックスごとに区切られた、1 本のソート済みの列**になっています。B+tree の葉を横に並べたものを、そのままクラスタ全体に広げた形です。

## 範囲で切る

この 1 本のキー空間を、連続した範囲ごとに切り分けます。CockroachDB では **range**、TiDB では **Region** と呼びます。

```
 キー空間（辞書順）
 ├──── range 1 ────┼──── range 2 ────┼──── range 3 ────┼─ …
 t42_r0000        t42_r5000        t42_i1_a…        t43_r…
      ↓                  ↓                  ↓
   ノード A, B, C     ノード B, C, D     ノード A, C, D   （それぞれ 3 台に複製）
```

1 つの range の大きさには上限があり、超えると 2 つに分割されます。既定の上限は CockroachDB で 512MiB（[Cockroach Labs](https://www.cockroachlabs.com/glossary/distributed-db/range-shard/)）、TiKV で 256MiB です。TiKV は v8.4.0 で 96MiB から引き上げました（[TiDB 文書](https://docs.pingcap.com/tidb/stable/tune-region-performance/)）。小さすぎると range の数が増えて管理の負担が増え、大きすぎるとノード間で移すのに時間がかかります。

分割も移動も、データベースが自動でやります。あるノードに range が偏れば、別のノードへ移します。手作業のシャーディングで最も辛かった「分け直し」が、**range の分割と移動という小さな操作の繰り返し**に置き換わっています。

### 連番の主キーが、1 台に書き込みを集める

範囲で切ることには、はっきりした弱点があります。

主キーが連番だと、新しい行のキーは常に**キー空間の末尾**に来ます。末尾を担当しているのは、最後の 1 つの range だけです。どれだけノードを足しても、**挿入はすべてその 1 つの range、つまり 1 組の 3 台に集中します**。分割されても、新しい末尾の range に集中が移るだけです（[TiDB 文書](https://docs.pingcap.com/tidb/stable/troubleshoot-hot-spot-issues/)）。これを **ホットスポット** と呼びます。

1 台のデータベースでは、連番に近い主キーは B+tree の右端に追記されるので、ページ分割が少なく好まれました（第 65 回）。**分散すると、同じ性質が裏目に出ます。** 対策として、TiDB は主キーの上位ビットをランダムにする `AUTO_RANDOM` を用意しており、CockroachDB ではランダムな UUID を主キーにするのが定石です。

## range ごとに合意する

各 range は、複数のノード（普通は 3 台）に複製されます。そして **range ごとに 1 つの Raft グループ** を作り、その range への書き込みを合意します。Raft そのものは、システムデザインの読み物の<a href={`${import.meta.env.BASE_URL}reading/consensus/`}>分散合意</a>で見たとおりです。

ここで、前回の WAL が別の形で現れます。Raft がノード間で揃えているのは **ログ** です。range への書き込みは Raft のログに追記され、過半数のノードがそれをディスクに書いた時点で確定します。**1 台のデータベースで「WAL を `fsync` したらコミット」だったものが、「Raft のログを過半数が `fsync` したらコミット」になった**わけです。1 台の故障では、コミット済みのデータは消えません。

CockroachDB では、1 つのノードが数十万の Raft グループに参加していることもあります（[Cockroach Labs](https://www.cockroachlabs.com/blog/scaling-raft/)）。そのため、ハートビートをまとめて送るなど、Raft を大量に動かすための工夫が重ねられています。

<Callout type="tip" title="読み取りは合意しない">
  書き込みのたびに合意するのは仕方がないとして、読み取りのたびに過半数へ問い合わせていては遅すぎます。
  そこで、range ごとに一定期間「この range の読み取りは自分が答える」という**リース**を 1 台に持たせます。
  CockroachDB はこれを leaseholder と呼びます。
  リースを持つノードは、他のノードに聞かずに手元の最新状態から答えられます。
</Callout>

## 範囲をまたぐトランザクション

1 行だけの更新なら、1 つの range の Raft で完結します。問題は、**複数の range にまたがる** トランザクションです。先ほどの `users` への 1 行の挿入ですら、行のキーとインデックスのキーが別の range にあれば、2 つの range をまたぎます。

ここで使われるのは、結局 **2PC** です。<a href={`${import.meta.env.BASE_URL}reading/distributed-transaction/`}>分散トランザクション</a>の読み物では、2PC は調整役が落ちるとロックを握ったまま止まるので、マイクロサービス間ではほとんど使われない、と書きました。そして、使われるのは「1 つのデータベースクラスタの内部」に限られる、とも。**NewSQL は、まさにその内部です。**

止まる問題を避けられるのは、**参加者も、調整役の決定も、Raft で複製されている**からです。1 台が落ちても、その range の他の 2 台が状態を引き継げます。「調整役が落ちたのか、遅いだけなのか分からない」という 2PC の根本的な弱点が、合意の層によって埋められています。

TiDB が採用している **Percolator**（Google が 2010 年に発表した方式）では、トランザクションが触るキーのうち 1 つを **primary** に選びます（[TiKV](https://tikv.org/deep-dive/distributed-transaction/percolator/)）。

1. **prewrite**：すべてのキーに、仮の値とロックを書く。各ロックには「primary はどのキーか」を記す
2. **commit**：primary のロックを外し、コミット記録を書く。**この 1 つの書き込みが、トランザクション全体の成否を決める**
3. 残りのキーのロックは、後から非同期に外す

途中で調整役が落ちても、ロックの残ったキーに出会った人は、primary を見に行けば分かります。primary がコミット済みなら確定させ、そうでなければ取り消します。**成否の判定を、1 つのキーの 1 回の書き込みに集約する**ことで、調整役がいなくても誰でも後始末ができる仕組みです。

## 時刻をどう揃えるか

前回の MVCC は、「どの版が見えるか」をトランザクションの順序で決めていました。1 台なら、トランザクション ID を 1 つずつ増やせば順序が付きます。何十台もあるとき、**誰がその番号を振るのか**が問題になります。

製品ごとに、答えがはっきり分かれています。

| 方式 | 採用例 | 仕組み | 代償 |
| --- | --- | --- | --- |
| **中央で振る** | TiDB（PD の TSO） | 1 つのサービスが単調増加するタイムスタンプを配る | 毎回そこに聞きに行く。地理的に遠いと遅い |
| **誤差込みの原子時計** | Spanner（TrueTime） | GPS と原子時計で、現在時刻を「この区間のどこか」として返す | 誤差の分だけコミットを待つ |
| **HLC** | CockroachDB、YugabyteDB | 物理時刻と論理カウンタを組み合わせる | 時計のずれの上限を仮定し、その範囲内の読み取りはやり直す |

**TiDB** は、PD（Placement Driver）という管理サービスが **TSO**（Timestamp Oracle）としてタイムスタンプを配ります（[TiDB 文書](https://docs.pingcap.com/tidbcloud/tso/)）。最も単純で、順序が確実に付きます。

**Spanner** の TrueTime は、時刻を 1 点ではなく**区間**で返します。Google の環境では、その誤差 ε はおおむね 1〜7 ミリ秒の間で変動すると論文にあります（[Spanner 論文](https://www.usenix.org/system/files/conference/osdi12/osdi12-final-16.pdf)）。Spanner はコミットのタイムスタンプを決めた後、**その時刻が確実に過去になるまで待ってから**コミットを完了させます（commit wait）。待つ時間は誤差の大きさで決まるので、Google は時計の精度そのものにお金をかけて、この待ち時間を縮めています。

**CockroachDB** は特殊なハードウェアを仮定せず、NTP で揃えた普通の時計を使います。その代わり、ノード間の時計のずれに上限（既定で 500 ミリ秒）を仮定します。読み取りの時刻より少しだけ新しい版を見つけたとき、それが本当に未来の書き込みなのか、時計のずれでそう見えているだけなのか区別できません。この **不確実な区間** に入った場合は、読み取りの時刻を進めてやり直します。そして、あるノードの時計のずれが上限の 80% を超えたと判断すると、そのノードは自ら停止します（[Cockroach Labs](https://www.cockroachlabs.com/blog/clock-management-cockroachdb/)）。**仮定が破れたまま動き続けるより、止まるほうを選ぶ**設計です。

時計そのものの話（NTP による補正や、時刻が巻き戻る問題）は、第 82 回で扱います。

## 何を払っているのか

NewSQL は、1 台のデータベースの便利さを保ったまま、台数で伸ばすことを可能にしました。ただし、タダではありません。

- **書き込みのたびに、ネットワークの往復が入る。** Raft の過半数に届けるための往復、複数の range なら 2PC の往復。1 台のデータベースの `fsync` 1 回と比べると、1 件あたりの遅延は大きい
- **レプリカの置き場所が遅延を決める。** 3 台を別々の大陸に置けば、1 回の合意ごとに大陸間の往復がかかる。耐障害性と遅延の交換
- **キーの設計が性能を決める。** 連番の主キーによるホットスポットのように、1 台では問題にならなかった設計が効いてくる
- **時計に依存する。** 時計が仮定より大きくずれれば、性能が落ちるか、ノードが止まる

<Callout type="tip" title="結局、同じ部品の組み合わせ">
  NewSQL の各層を並べると、この章と前の章で見た部品がそのまま出てきます。
  辞書順に並んだキー（B+tree の葉）、ログを先に書くこと（WAL）、古い版を残すこと（MVCC）、
  LSM-tree、そしてその下のページキャッシュと `fsync`。
  **新しいのは、それらを合意と時計で束ねたこと**です。
  1 台のデータベースの中身を知っていれば、分散データベースの挙動の多くは説明できます。
</Callout>

## まとめ

- 読み取りレプリカでは書き込みが伸びず、手作業のシャーディングでは JOIN、トランザクション、分け直しが辛い
- NewSQL は SQL 層、トランザクション層、分散 KV、range ごとの Raft、LSM-tree の層に分かれる
- 行もインデックスもキーと値に変換され、辞書順の 1 本のキー空間に並ぶ。セカンダリインデックスは二段引き
- キー空間を range に切り、自動で分割・移動する。連番の主キーは末尾の range にホットスポットを作る
- range ごとの Raft が、1 台のときの「WAL を fsync したらコミット」を「過半数がログを書いたらコミット」に置き換える
- 範囲をまたぐ更新は 2PC。参加者が Raft で複製されているので止まらない。Percolator は成否を primary の 1 キーに集約する
- MVCC の順序を付ける時刻の答えは 3 つ。中央の TSO、TrueTime と commit wait、HLC と不確実な区間

ここまでで第 11 章は終わりです。1 台の中のページから始めて、何十台に分かれたデータベースまで来ました。次の章では、ここまでの部品をほぼすべて使う身近な大きなプログラム、**ブラウザ**の中に入ります。
