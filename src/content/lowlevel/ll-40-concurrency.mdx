## 2 つの言葉は違うものを指す

日常会話では混ざりますが、意味が違います。

> **並行（concurrency）**：複数の仕事を、**同時に扱う**。
> **並列（parallelism）**：複数の仕事を、**同時に動かす**。

1 コアの CPU を考えてください。第 6 章で見たとおり、OS は高速に切り替えて複数のプロセスを動かしているように見せます。**同時に動いてはいません。** しかし、複数の仕事を同時に扱っています。これが並行です。

コアが 4 つあれば、4 つの仕事が物理的に同時に進みます。これが並列です。

| | 並行 | 並列 |
| --- | --- | --- |
| 何の話か | **構造**。仕事の組み立て方 | **実行**。物理的に同時か |
| 1 コアでも成立するか | **する** | しない |
| 目的 | 応答性、資源の有効活用 | 速度 |
| 例 | イベントループ、コルーチン | マルチコア、SIMD、GPU |

<Callout type="tip" title="並行は並列の前提になる">
  並列に動かすには、まず**仕事を独立した単位に分けておく**必要があります。
  その「分け方」が並行の設計です。

  逆は成立しません。並行に設計しても、コアが 1 つなら並列にはなりません。
  そして、**並行に設計しただけで速くなると思い込むのが、最も多い誤解**です。
</Callout>

## 並行だけで得られるもの

コアが 1 つでも、並行にする価値があります。

**待ち時間を埋められる。** 第 7 章で見たとおり、I/O 待ちの間 CPU は何もしていません。その間に別の仕事を進められれば、全体の所要時間が縮みます。

```
逐次:   [計算][─── I/O 待ち ───][計算][─── I/O 待ち ───]
並行:   [計算][─── I/O 待ち ───]
              [計算][─── I/O 待ち ───]
```

**応答性が上がる。** 重い処理の最中でも、ユーザの操作に反応できます。画面が固まらない。

**構造が自然になる。** 「接続ごとに 1 つの流れ」と書けるほうが、状態機械を手で書くより読みやすい。

## 並列にしても速くならない場合

コアを増やせば増やすほど速くなる、とはなりません。

### アムダールの法則

プログラムのうち、**並列化できない部分の割合を `s`** とします。コアを `n` 個にしたときの速度向上の上限は、

```
speedup = 1 / (s + (1 - s) / n)
```

`n` を無限に大きくしても、

```
speedup → 1 / s
```

**逐次部分の割合だけで上限が決まります。**

| 逐次部分 | コア無限大での上限 | 16 コアでの実際 |
| --- | --- | --- |
| 1% | **100 倍** | 13.9 倍 |
| 5% | **20 倍** | 9.1 倍 |
| 10% | **10 倍** | 6.4 倍 |
| 25% | **4 倍** | 3.4 倍 |
| 50% | **2 倍** | 1.9 倍 |

**5% が逐次的なだけで、どれだけコアを積んでも 20 倍が上限です。**

<Callout type="warn" title="逐次部分は思ったより多い">
  初期化、結果の集約、ログ出力、ロックを取っている区間、メモリの確保。
  これらはすべて逐次部分です。

  さらに、並列化そのもののコスト（スレッドの生成、タスクの分配、同期）が加わります。
  **小さな仕事を並列化すると、コストのほうが大きくなって遅くなります。**
</Callout>

### グスタフソンの法則

アムダールの法則には前提があります。**問題の大きさが固定されている**ことです。

現実には、コアが増えたらより大きな問題を解こうとします。多くの場合、**問題を大きくすると並列化できる部分の割合が増えます**（逐次部分は初期化などで、あまり増えない）。

```
scaled speedup = n - s × (n - 1)
```

この見方では、コアを増やした分だけ「同じ時間でより多くを処理できる」ことになります。

**どちらが正しいかではなく、何を問うているかが違います。**

- アムダール：**同じ仕事**をどれだけ速く終えられるか（強スケーリング）
- グスタフソン：**同じ時間**でどれだけ多くを処理できるか（弱スケーリング）

### それ以前の壁

理論上限に達する前に、別の要因で頭打ちになります。

| 要因 | 内容 | 出てきた章 |
| --- | --- | --- |
| **メモリ帯域** | コアが増えてもメモリは 1 つ。取り合いになる | 第 3 章 |
| **キャッシュの奪い合い** | L3 は共有。他のコアがデータを追い出す | 第 3 章 |
| **false sharing** | 論理的に無関係でも、同じラインなら干渉する | 第 3 章 |
| **ロック競合** | 排他区間は逐次的。待ち時間が増える | 第 6 章 |
| **NUMA** | 遠いノードのメモリは 2 倍遅い | 第 3 章 |
| **コンテキストスイッチ** | スレッドが多すぎると切り替えだけで消耗 | 第 6 章 |

**「スレッドを増やしたら遅くなった」は、珍しいことではありません。**

## 2 種類の並列性

並列化の対象には、大きく 2 つの型があります。

### タスク並列

**違う仕事**を同時に行います。

```
スレッド 1: ネットワークからデータを受け取る
スレッド 2: 受け取ったデータを変換する
スレッド 3: 変換結果をディスクに書く
```

パイプライン型です。各段が独立しているので分けやすい。第 2 章で見た CPU のパイプラインと同じ構造です。

### データ並列

**同じ処理を、違うデータに**適用します。

```
100 万個の要素すべてに、同じ変換をかける
```

分割が単純で、スケールしやすい。効かせる手段が何段階もあります。

| 手段 | 粒度 | 出てきた章 |
| --- | --- | --- |
| **SIMD** | 1 命令で 4〜16 要素 | 第 2 章 |
| **マルチコア** | コアごとに範囲を分ける | 第 6 章 |
| **GPU** | 数千の演算器で一斉に | — |
| **分散処理** | 複数のマシンに分ける | — |

**GPU** は、データ並列に特化した設計です。制御回路を削り、演算器を大量に並べています。分岐が少なく、同じ処理を大量のデータに繰り返すものにしか向きませんが、その条件に合えば桁違いに速い。

<Callout type="tip" title="MapReduce も同じ形">
  「各要素に同じ処理をする（map）→ 結果をまとめる（reduce）」という構造は、
  データ並列そのものです。

  分割できる部分が map、逐次的な部分が reduce。
  **アムダールの法則でいう `s` が reduce の側にある**、という見方ができます。
</Callout>

## 並行の設計モデル

「複数の仕事をどう組み立てるか」には、いくつかの型があります。

### 共有メモリ + ロック

最も基本的な形です。第 6 章で扱いました。

```c
pthread_mutex_lock(&m);
shared_state++;
pthread_mutex_unlock(&m);
```

**速いが、間違えやすい。** データ競合、デッドロック、優先度の逆転。すべてここで起きます。

### メッセージパッシング

**共有しない。** 各実行単位が自分のデータだけを持ち、やり取りはメッセージのコピーで行います。

```
スレッド A ──[メッセージ]──▶ スレッド B
```

競合が原理的に起きません。**共有していないものは壊せない**からです。

代表的な 2 系統があります。

**アクターモデル**（Erlang、Elixir、Akka）

- 各アクターが**自分専用のメールボックス**を持つ
- メッセージを 1 つずつ順に処理する
- アクターの中は常にシングルスレッド

「誰に送るか」を指定します。受け手が主体です。

**CSP**（Go、Occam）

- **チャネル**という通路を介してやり取りする
- 送り手と受け手は互いを知らない

「どのチャネルに流すか」を指定します。通路が主体です。

```go
ch := make(chan int)
go func() { ch <- compute() }()     // 送る
result := <-ch                       // 受け取る
```

<Callout type="note" title="Go の標語">
  > Do not communicate by sharing memory; instead, share memory by communicating.
  > （メモリを共有して通信するな。通信によってメモリを共有せよ）

  共有を前提に排他を足すのではなく、**そもそも共有しない**設計にする。
  第 6 章の最後で「最善の対策は共有しないこと」と書いたのは、この方向です。
</Callout>

### async / await

**1 つのスレッドの中で**、待ちが発生したら別の仕事に切り替えます。

```ts
async function handle(req: Request) {
  const data = await fetch(url)      // 待っている間、他の仕事が進む
  return process(data)
}
```

- 切り替えは**明示的**（`await` の位置でだけ起きる）
- OS を介さないので極めて軽い
- **並行だが、並列ではない**（1 スレッドで動く場合）

`await` の位置でしか切り替わらないので、その間は排他が保証されます。ロックが要らない場面が多い。

**その代わり、CPU を使い続ける処理には無力です。** `await` に到達しなければ、他の仕事は一切進みません。

<Callout type="warn" title="関数の色の問題">
  `async` な関数は、`async` な関数からしか `await` できません。
  ある関数を非同期にすると、**その呼び出し元も連鎖的に非同期にする必要があります**。

  これを「関数に色が付く」と表現します。
  Go の goroutine や Java の仮想スレッドが**色を付けない**設計を選んだのは、
  この伝播を避けるためです。
</Callout>

### 比較

| モデル | 競合の起きやすさ | 速度 | 代表 |
| --- | --- | --- | --- |
| 共有メモリ + ロック | **高い** | 速い | C、C++、Java |
| アクター | 低い | 中 | Erlang、Akka |
| CSP | 低い | 中 | Go |
| async / await | 低い（単一スレッドなら） | 速い | JavaScript、Rust、Python |
| データ並列 | **無い**（要素が独立なら） | 非常に速い | SIMD、GPU、MapReduce |
| 不変データ | **無い** | 中 | Haskell、Clojure |

## 何を選ぶか

判断の順序です。

**1. そもそも並行にする必要があるか。** 逐次で十分なら、それが最も安全で速い。

**2. 何が目的か。**

| 目的 | 向くもの |
| --- | --- |
| I/O 待ちを埋めたい | async、軽量スレッド |
| 計算を速くしたい | データ並列、マルチコア |
| 応答性を保ちたい | 並行（ワーカーに逃がす） |
| 障害を分離したい | プロセス、アクター |

**3. 状態を共有せずに済む形はあるか。** 分割できるなら分割する。不変にできるなら不変にする。

**4. どうしても共有が必要な部分だけ、最小の範囲でロックする。**

<Callout type="tip" title="測ってから並列化する">
  計測の回（第 78 回）で扱うとおりです。
  **並列化は、ボトルネックがそこにあると確かめてから**行うべきです。

  I/O 律速の処理をマルチコア化しても、1 ミリ秒も速くなりません。
  そして、コードは確実に読みにくくなり、バグが入る余地が増えます。

```bash
perf stat -e task-clock,cycles ./a.out    # CPU をどれだけ使っているか
perf stat -e cache-misses ./a.out         # メモリ律速か
```
</Callout>

## スケールしているかを測る

並列化した後は、**実際にスケールしているか**を確認します。

```
効率 = (1 コアでの時間) / (n コアでの時間 × n)
```

理想は 1.0 です。0.5 なら、コアの半分が無駄になっています。

```bash
# スレッド数を変えながら測る
for n in 1 2 4 8 16; do
  THREADS=$n /usr/bin/time -f "$n threads: %e sec" ./a.out
done
```

**コア数を倍にして時間が半分にならないなら、どこかに壁があります。** アムダールの逐次部分か、メモリ帯域か、ロック競合か。ここから第 78 回の計測の道具に戻ることになります。

## まとめ

- **並行は構造、並列は実行**。1 コアでも並行は成立する
- アムダールの法則：逐次部分が 5% あれば、上限は 20 倍
- 理論上限の前に、メモリ帯域・キャッシュ・ロック競合で頭打ちになる
- タスク並列（違う仕事）とデータ並列（同じ処理を違うデータに）
- 共有メモリ + ロックは速いが危険。メッセージパッシングは共有しないので競合が起きない
- async / await は軽いが、関数に色が付き、CPU 律速には効かない
- **測ってから並列化し、並列化した後もスケールしているか測る**

これで第 6 章は終わりです。次の章では、ここまでの実行単位が**外の世界に触れる**ための唯一の窓口を見ます。
