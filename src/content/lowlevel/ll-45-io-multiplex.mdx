## 1 つの流れで 1 つしか待てない

前回見たとおり、ブロッキングな `read` は、データが来るまで戻りません。
書き方は自然ですが、**1 つの実行の流れで 1 つの fd しか待てません**。

接続が 1 万本あるサーバでは、これが直接の壁になります。

## 素朴な解決とその限界

### 接続ごとにプロセス

```c
while (1) {
    int client = accept(listen_fd, ...);
    if (fork() == 0) { handle(client); exit(0); }
}
```

分かりやすく、片方がクラッシュしても他に影響しません。しかし、1 接続あたり数 MB のメモリと、生成コストがかかります。1 万接続は現実的ではありません。

### 接続ごとにスレッド

プロセスよりは軽いですが、スタックが 1 本あたり数 MB（仮想領域）、切り替えのコストも積み上がります。1 万スレッドは厳しく、数万は無理です。

**この「1 万接続を捌けるか」という問題が、1999 年に C10K 問題として提起されました。**

## 1 つの流れで複数を待つ

発想を変えます。

> **複数の fd を渡して、「どれかが準備できたら教えて」と頼む。**

これが **I/O 多重化** です。1 つのスレッドで何千もの接続を扱えます。

### select

最も古い方式です。

```c
fd_set readfds;
FD_ZERO(&readfds);
FD_SET(fd1, &readfds);
FD_SET(fd2, &readfds);
select(maxfd + 1, &readfds, NULL, NULL, &timeout);
// 戻ってきたら、FD_ISSET で誰が準備できたかを調べる
```

問題が 3 つあります。

1. **fd の上限が 1024**（`FD_SETSIZE`）。ビットマップが固定長のため
2. **呼ぶたびに全 fd の集合を渡し直す**。カーネルへのコピーが毎回発生する
3. **戻ってきた後、全 fd を線形に調べる**必要がある。O(n)

### poll

配列を使うことで、上限の問題は解消しました。

```c
struct pollfd fds[N];
fds[0].fd = fd1; fds[0].events = POLLIN;
poll(fds, N, timeout);
```

しかし、**毎回全部を渡し直し、戻ってきたら全部走査する**という構造は同じです。接続が 1 万本あって、そのうち動きがあるのが 10 本でも、1 万本ぶんの処理が毎回発生します。

### epoll

Linux の **epoll** は、この構造を根本から変えました。

```c
int ep = epoll_create1(0);

struct epoll_event ev = { .events = EPOLLIN, .data.fd = client_fd };
epoll_ctl(ep, EPOLL_CTL_ADD, client_fd, &ev);     // 登録は 1 回だけ

struct epoll_event events[64];
int n = epoll_wait(ep, events, 64, -1);            // 準備できたものだけ返る
for (int i = 0; i < n; i++) { handle(events[i].data.fd); }
```

違いは決定的です。

| | select / poll | epoll |
| --- | --- | --- |
| fd の登録 | 毎回全部渡す | **1 回だけ** |
| 戻り値 | 全 fd の状態 | **準備できたものだけ** |
| 計算量 | O(n) | **O(準備できた数)** |

カーネル側が fd のリストを保持し、準備ができたものを内部のリストに繋いでいくため、この効率が実現されます。

**1 万接続のうち 10 本だけ動きがあるなら、10 本ぶんの処理で済みます。**

<Callout type="note" title="OS ごとの実装">
  | OS | 仕組み |
  | --- | --- |
  | Linux | epoll |
  | BSD, macOS | kqueue |
  | Solaris | /dev/poll, event ports |
  | Windows | IOCP（設計思想が異なる） |

  移植性のため、libevent、libev、libuv といった抽象化ライブラリが使われます。
  Node.js が使っているのは libuv です。
</Callout>

## レベルトリガとエッジトリガ

epoll には 2 つの通知方式があります。

**レベルトリガ**（既定）：**データがある限り**、毎回通知される。

**エッジトリガ**（`EPOLLET`）：**状態が変化した瞬間だけ**通知される。

エッジトリガは通知回数が減るので効率的ですが、扱いが難しくなります。

```c
// エッジトリガでは、EAGAIN が返るまで読み切らなければならない
while (1) {
    ssize_t n = read(fd, buf, size);
    if (n == -1 && errno == EAGAIN) break;    // 読み切った
    if (n <= 0) break;
    process(buf, n);
}
```

**途中でやめると、残りのデータがあっても次の通知が来ません**。接続がハングしたように見えます。

さらに、エッジトリガでは fd をノンブロッキングにしておく必要があります。そうしないと、最後の `read` でブロックしてしまいます。

## ノンブロッキング

fd をノンブロッキングモードにすると、`read` は待たずにすぐ返ります。

```c
fcntl(fd, F_SETFL, O_NONBLOCK);

ssize_t n = read(fd, buf, size);
if (n == -1 && (errno == EAGAIN || errno == EWOULDBLOCK)) {
    // まだデータがない。エラーではない
}
```

**`EAGAIN` はエラーではありません。** 「今はまだ」という意味です。多重化と組み合わせて使うのが基本です。

## イベントループ

多重化を中心に組んだ構造が **イベントループ** です。

```
while (1) {
    events = epoll_wait(...)           // 準備できたものを取る
    for (ev in events) {
        callback = handlers[ev.fd]     // 対応する処理を呼ぶ
        callback(ev)
    }
}
```

Node.js、nginx、Redis、Python の asyncio、Go のランタイムは、すべてこの構造を持っています。

<Callout type="warn" title="コールバックで長い処理をしてはいけない">
  イベントループは 1 つのスレッドで回っています。
  あるコールバックが 100ms かかると、**その間すべての接続が待たされます**。

  「Node.js でブロッキングな処理を書くな」と言われるのは、この構造によるものです。
  重い処理はワーカースレッドに逃がすか、細かく分割する必要があります。
</Callout>

## それでも残る問題

多重化は**ソケットには効きますが、通常のファイルには効きません**。

ローカルのファイルは「常に読み込み可能」と判定されるため、`epoll` に登録しても意味がありません。実際の `read` で、ディスクの読み込みが完了するまでブロックします。

このため、ファイル I/O を含む非同期処理では、

- **スレッドプールに逃がす**（libuv、Node.js の方式）
- **非同期 I/O の仕組みを使う**（Linux AIO、io_uring）

という対応が必要です。

**io_uring** は、この問題も含めて統一的に扱える仕組みとして設計されました。ファイル、ソケット、その他の操作を、同じリングバッファに投入できます。

## 方式の使い分け

| 方式 | 向いている場面 |
| --- | --- |
| ブロッキング + スレッド | 接続数が数百程度。コードが素直に書ける |
| 多重化 + イベントループ | 接続数が多く、各接続の処理が軽い |
| 軽量スレッド（Go、Java 21+） | **両方の利点**。ブロッキングに書けて、ランタイムが多重化する |

現代的な選択肢としては、軽量スレッドが有力です。ブロッキングのように素直に書けて、ランタイムが内部で epoll を使って多重化してくれます。コールバックの入れ子から解放されつつ、性能も得られます。

## 計測する

```bash
ss -s                          # ソケットの統計
ss -tan state established | wc -l
cat /proc/net/sockstat
```

接続数が増えてきたら、fd の上限（`ulimit -n`）、ポートの範囲（`net.ipv4.ip_local_port_range`）、TIME_WAIT の数なども確認が必要になります。

## まとめ

- ブロッキング I/O は 1 つの流れで 1 つの fd しか待てない
- 接続ごとのプロセス / スレッドは、数千を超えると成立しない（C10K 問題）
- 多重化は、1 つの流れで複数の fd を待つ仕組み
- select / poll は毎回全 fd を渡して全部走査するため O(n)
- epoll は登録が 1 回で、準備できたものだけ返る
- エッジトリガは効率的だが、読み切る責任が生じる
- イベントループのコールバックで長い処理をすると全体が止まる
- 通常のファイルには多重化が効かない。スレッドプールか io_uring を使う

次は、fd を使わない、もう 1 つの通知の仕組みを見ます。
