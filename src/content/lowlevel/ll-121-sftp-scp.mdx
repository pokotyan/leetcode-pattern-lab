## 同じ SSH の上の、別々のプロトコル

前回の第 120 回では、別のプロトコルを暗号化された通信路に載せる型を 4 つに分けました。最後の型が、**SSH のチャネルの中に載せる**ものでした。この回は、その型の代表であるファイル転送を見ます。

`scp`、`sftp`、`rsync -e ssh` は、どれも `ssh` と同じ鍵で認証し、同じ暗号で守られます。利用者から見れば「SSH でファイルを送る」という同じ操作です。しかし、第 118 回で見たチャネルを開いた後に**サーバに何を頼み、チャネルの中でどんなバイト列をやり取りしているか**は、3 つとも違います。

| 道具 | チャネルで頼むもの | サーバで動くもの | チャネルの中身 |
| --- | --- | --- | --- |
| `scp -O`（旧来の方式） | `exec`（コマンドの実行） | `scp -f` / `scp -t`（利用者のシェル経由） | rcp 由来の 1 行の命令とファイルの中身 |
| `scp`（OpenSSH 9.0 以降の既定）、`sftp` | `subsystem "sftp"` | `sftp-server` または sshd 内蔵の `internal-sftp` | SFTP のパケット |
| `rsync -e ssh` | `exec` | `rsync --server ...` | rsync のプロトコル（第 81 回） |

この違いが、ファイル名の解釈、壊れ方、速さ、サーバ側でどこまで絞れるかの違いになって表れます。順に確かめていきます。

## 実験の環境

第 118 回と同じく、Alpine の openssh-server を Docker で動かし、手元の macOS から接続しました。利用者は、普通にログインできる `alice` と、ファイル転送だけを許す `bob` の 2 人です。

| --- | --- |
| サーバ | Alpine Linux 3.22.6、OpenSSH_10.0p2（openssh-server、openssh-sftp-server）、rsync 3.5.0 |
| クライアント | macOS の OpenSSH_10.0p2（LibreSSL 3.3.6）、openrsync（プロトコル 29）、Python 3 |

```

$ docker exec ll117-sshd sshd -V
OpenSSH_10.0p2, OpenSSL 3.5.8 25 Aug 2026
```

接続には第 118 回と同じように専用の設定ファイル `cfg` を使い、`lab` で `alice`、`bob` で `bob` につながるようにしています。

## SCP: rcp から受け継いだ作り

### チャネルの中で何が起きているか

まず、旧来の方式を `-O` で明示して使います。

```
$ scp -O -v -F cfg lab:hello.txt dl/
Executing: program /usr/bin/ssh host lab, user (unspecified), command scp -v -f hello.txt
debug1: Sending command: scp -v -f hello.txt
Sink: C0644 12 hello.txt
Transferred: sent 3620, received 4300 bytes, in 0.0 seconds
```

手元の `scp` は `ssh` を起動し、**サーバ上で `scp -f hello.txt` というコマンドを実行させています**。`-f`（from）は「このファイルを送り出せ」、`-t`（to）は「受け取れ」という、利用者が打つことのない内部用のオプションです。つまり旧来の SCP には、サーバ側の専用のデーモンも、サブシステムもありません。**サーバにも `scp` の実行ファイルが入っていることが前提**です。実際、最初に試したときのコンテナには `scp` が入っておらず、次のように失敗しました。

```
$ scp -O -F cfg lab:hello.txt dl/
sh: scp: not found
```

`Sink: C0644 12 hello.txt` は、送り手の `scp -f` が送ってきた 1 行です。`C` の後ろにパーミッション、大きさ、ファイル名が並び、その後ろにファイルの中身が続きます。受け手は区切りごとに 0 の 1 バイトを返して先へ進めます。

この作りは、BSD の `rcp` をそのまま SSH の上に移したものです。CVE の記述にも「scp の実装は 1983 年の rcp から派生しており、どのファイルやディレクトリを送るかはサーバが決める」とあります（[CVE-2019-6111](https://www.cve.org/CVERecord?id=CVE-2019-6111)）。

### ファイル名をサーバのシェルが読む

`exec` で渡したコマンド行は、第 118 回で見たとおり**サーバ側の利用者のシェル**が解釈します。そのため、リモート側のファイル名はシェルの文法に従って読まれます。空白を含む名前、`$HOME`、ワイルドカード、コマンド置換を、旧来の方式と既定の方式で比べました。

```
$ scp -O -F cfg 'lab:my file.txt' dl2/          # 旧来: 空白で 2 つに割れる
scp: my: No such file or directory
scp: file.txt: No such file or directory
$ scp -F cfg 'lab:my file.txt' dl2/             # 既定（SFTP）: 1 つの名前のまま

$ scp -O -F cfg 'lab:$HOME/*.log' dl2/          # 旧来: サーバのシェルが展開して成功
$ scp -F cfg 'lab:$HOME/*.log' dl2/             # 既定: $HOME は展開されない
scp: remote readdir("$HOME/"): No such file or directory
scp: $HOME/*.log: No such file or directory
$ scp -F cfg 'lab:*.log' dl2/                   # 既定: * はクライアント側で展開される

$ scp -O -F cfg hello0 'lab:/tmp/$(id -un)-x'   # 旧来: 置き先の名前の中のコマンドが実行される
$ scp -F cfg hello0 'lab:/tmp/$(id -un)-y'
$ docker exec ll117-sshd ls /tmp
$(id -un)-y
alice-x
```

最後の例では、旧来の方式で送ったファイルは `alice-x` という名前になりました。サーバのシェルが `$(id -un)` を**実行して**その結果を名前に埋め込んだということです。既定の方式では、書いたとおりの `$(id -un)-y` という名前のファイルができています。

<Callout type="note" title="CVE-2020-15778 は「仕様どおり」とされた">
  置き先の引数にバッククォートを書くとサーバでコマンドが実行される件は、[CVE-2020-15778](https://www.cve.org/CVERecord?id=CVE-2020-15778) として登録されましたが、
  **disputed**（異議あり）の印が付いています。記述によれば、OpenSSH 側は既存の使い方を壊すおそれが大きいとして、この種の検証を意図的に入れていません。
  普通の SSH の利用者はもともと任意のコマンドを実行できるので、新たに増える権限はありません。
  問題になるのは、**「scp だけを許す」つもりで利用者を制限しているサーバ**です。scp の引数がシェルを通る以上、その制限は簡単に越えられます。
  ファイル転送だけを許したいなら、後で見る SFTP の `internal-sftp` を使うのが筋です。
</Callout>

### 送ってくるファイル名を、誰が確かめるのか

サーバのシェルがワイルドカードを展開するということは、**どのファイルを返すかを決めるのがサーバ**だということです。`scp -O host:a.txt .` と頼んでも、悪意のあるサーバ（または中間者）は別の名前のファイルを送り返せます。2019 年に公表された一連の問題は、この構造を突いたものでした。

| CVE | 内容（[cve.org](https://www.cve.org/) の記述の要約） |
| --- | --- |
| [CVE-2018-20685](https://www.cve.org/CVERecord?id=CVE-2018-20685) | `.` や空のファイル名を送り、クライアント側の置き先ディレクトリのパーミッションを書き換える |
| [CVE-2019-6111](https://www.cve.org/CVERecord?id=CVE-2019-6111) | 要求と違う名前のファイルを送り、置き先ディレクトリの任意のファイルを上書きする。`-r` なら下のディレクトリも操作でき、`.ssh/authorized_keys` の上書きもありうる |
| [CVE-2019-6109](https://www.cve.org/CVERecord?id=CVE-2019-6109) / [CVE-2019-6110](https://www.cve.org/CVERecord?id=CVE-2019-6110) | 進み具合の表示や標準エラーに端末の制御文字を混ぜ、余分なファイルが送られたことを隠す |

OpenSSH 8.0（2019-04-17）は、**サーバが送ってきたファイル名がコマンド行の要求と合っているかをクライアントで確かめる**ようにしました。ただしリリースノートは、ワイルドカードの展開をサーバのシェルに頼っている以上、**確実な確認の方法はない**とも書いています（[OpenSSH 8.0](https://www.openssh.org/txt/release-8.0)）。

これを手元で確かめます。サーバの `PATH` で先に見つかる `/usr/local/bin/scp` に、何を頼まれても `evil.txt` を送り返す偽物を置きました。

```sh
#!/bin/sh
head -c1 >/dev/null            # 受け手の「始めてよい」を待つ
printf 'C0644 5 evil.txt\n'    # 頼まれていない名前を名乗る
head -c1 >/dev/null
printf 'pwned\0'
head -c1 >/dev/null
```

```
$ scp -O -F ../cfg lab:hello.txt .
protocol error: filename does not match request
$ echo $?
1

$ scp -O -F ../cfg 'lab:*.txt' .
$ ls
evil.txt
```

`hello.txt` を頼んだときは、名前が合わないので拒否されました。しかし `*.txt` を頼むと、`evil.txt` は `*.txt` に当てはまるので受け入れられます。**クライアントにできるのは「頼んだパターンに合うか」までで、サーバがそのパターンを正しく展開したかは分からない**のです。リリースノートが言う「確実な方法はない」とは、この残りの部分です。

### OpenSSH 9.0 で既定が SFTP に

OpenSSH 9.0（2022-04-08）で、`scp` は**既定で SFTP のプロトコルを使う**ようになりました。互換性の問題があるときは `-O` で旧来の方式に戻せます（[OpenSSH 9.0](https://www.openssh.org/txt/release-9.0)）。

```
$ scp -v -F cfg lab:hello.txt dl/
Executing: program /usr/bin/ssh host lab, user (unspecified), command sftp
debug1: Sending subsystem: sftp
```

ここで `command sftp` と出ているのはサブシステムの名前で、次の行のとおり `exec` ではなく `subsystem` として要求しています。リリースノートは、互換性が変わる点として次を挙げています（同上）。

- 旧来の方式は、リモートのファイル名のワイルドカードを**サーバのシェルで**展開していた。その副作用で、ファイル名に含まれるシェルの特殊文字は二重に引用しなければならなかった。SFTP ではその必要がない
- SFTP には `~user` の形のパスを展開する仕組みがない。OpenSSH 8.7 以降の `sftp-server` は、そのための拡張 `expand-path@openssh.com` を持つ

上の実験で `$HOME` が展開されなくなったのは、この変化そのものです。コマンド名は `scp` のままでも、中身は次に見る SFTP のクライアントに入れ替わっています。

## SFTP: サブシステムとして始まる

### subsystem 要求

`sftp` や既定の `scp` は、チャネルを開いた後に `subsystem` 要求を送ります（[RFC 4254 6.5](https://www.rfc-editor.org/rfc/rfc4254.html#section-6.5)）。`sftp -vvv` では次のように見えます。

```
debug1: Sending subsystem: sftp
debug2: channel 0: request subsystem confirm 1
debug3: send packet: type 98                     CHANNEL_REQUEST
debug3: receive packet: type 99                  CHANNEL_SUCCESS
debug2: subsystem request accepted on channel 0
```

サーバ側では、`sshd_config` の `Subsystem` に書いた名前とコマンドの対応で、何を起動するかが決まります。

```
Subsystem sftp /usr/lib/ssh/sftp-server
```

`exec` との違いは、**クライアントがコマンド行を送らない**ことです。クライアントは `sftp` という名前を送るだけで、実際に何を実行するかはサーバの管理者が決めます。ファイル名はこの後、SFTP のパケットの中の文字列として運ばれ、シェルを通りません。

ただし RFC 4254 は、サブシステムも**通常は利用者のシェルを使って起動される**ので、シェルの初期化スクリプトが出力した余計な文字列と区別できるよう、プロトコルの最初に目印を置くのがよい、と書いています（同上）。手元で、サブシステムの前に 1 行出力するように設定を変えると、確かに壊れました。

```
Subsystem sftp echo Welcome; exec /usr/lib/ssh/sftp-server
```

```
$ sftp -F cfg -b <(echo pwd) lab
Received message too long 1466264675
Ensure the remote shell produces no output for non-interactive sessions.
$ python3 -c 'print(bytes.fromhex("%08x" % 1466264675))'
b'Welc'
```

クライアントは、最初の 4 バイトを SFTP のパケットの長さとして読みます。そこに `Welc` が来たので、約 1.4 GB のパケットが来ると解釈して諦めたわけです。`.bashrc` などで非対話のときにも何かを表示していると、この「Received message too long」に出会います。

### 仕様の状態: 20 年以上ドラフトのまま

SFTP には RFC がありません。IETF の secsh 作業部会でドラフトが書かれましたが、RFC にならないまま期限切れになっています。

| 文書 | 日付 | プロトコルの版 | 状態 |
| --- | --- | --- | --- |
| [draft-ietf-secsh-filexfer-02](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02) | 2001 年 10 月 | 3 | 期限切れ |
| [draft-ietf-secsh-filexfer-13](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-13) | 2006 年 7 月 | 6 | 期限切れ |
| [draft-spaghetti-sshm-filexfer-00](https://datatracker.ietf.org/doc/draft-spaghetti-sshm-filexfer/) | 2025 年 7 月 | — | 個人提出のドラフト。期限切れ |

OpenSSH の `sftp` と `sftp-server` は、**02 の版 3 を実装**し、それより新しい版の機能は必要なものだけを拡張として足しています（[OpenSSH の PROTOCOL 文書](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL)）。手元でも、`sftp> version` は `SFTP protocol version 3` と答えました。広く使われているのが OpenSSH である以上、**事実上の標準は 2001 年のドラフトの版 3 と OpenSSH の拡張**です。

IETF の SSHM（Secure Shell Maintenance）作業部会は、OpenSSH の証明書やエージェントのプロトコルと並んで、SFTP を**今実装されているとおりに文書にする**ことを目標に挙げています（[SSHM の憲章](https://datatracker.ietf.org/wg/sshm/about/)）。2025 年 7 月に出た上の表の 3 行目のドラフトはその流れのものですが、執筆時点（2026 年 10 月）の Datatracker では、改版のないまま期限切れの個人提出のドラフトとして表示されています。

### パケットの形

SFTP のパケットは、第 118 回の SSH のパケットと同じく、**長さが先頭にある**形です。32 ビットの長さ、8 ビットの種類、そのあとにデータが続きます（[draft-02 3](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02#section-3)）。最初の INIT 以外の要求には、32 ビットの**request-id** が入ります。

```
uint32   length
byte     type
uint32   request-id     （INIT と VERSION にはない）
...      種類ごとのデータ
```

| クライアントから | 番号 | サーバから | 番号 |
| --- | --- | --- | --- |
| INIT | 1 | VERSION | 2 |
| OPEN / CLOSE | 3 / 4 | STATUS | 101 |
| READ / WRITE | 5 / 6 | HANDLE | 102 |
| LSTAT / FSTAT / SETSTAT / FSETSTAT | 7〜10 | DATA | 103 |
| OPENDIR / READDIR | 11 / 12 | NAME | 104 |
| REMOVE / MKDIR / RMDIR | 13〜15 | ATTRS | 105 |
| REALPATH / STAT / RENAME / READLINK / SYMLINK | 16〜20 | EXTENDED_REPLY | 201 |
| EXTENDED | 200 | | |

（[draft-02 3](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02#section-3)）。見てのとおり、これは「ファイルを送る」プロトコルというより、**open、read、write、close、stat をネットワーク越しに呼ぶ**プロトコルです。第 41 回のシステムコールを、番号付きの要求にして送っていると考えると分かりやすいでしょう。

### 手で話してみる

`ssh -s lab sftp` はサブシステムを要求して、チャネルの中身を標準入出力につなぎます。Python からこれを起動し、パケットを手で組んで送りました。`>>` が送ったバイト列、`<<` が受け取ったバイト列（長いものは先頭だけ）です。

```
>> 00 00 00 05 01 00 00 00 03
<< 00 00 01 3e 02 00 00 00 03 00 00 00 18 70 6f 73 69 78 2d 72 65 6e 61 6d 65 40 6f 70 65 6e 73 73 68 2e 63 6f 6d ...
   type 2 version 3
>> 00 00 00 1a 03 00 00 00 01 00 00 00 09 68 65 6c 6c 6f 2e 74 78 74 00 00 00 01 00 00 00 00
<< 00 00 00 0d 66 00 00 00 01 00 00 00 04 00 00 00 00
   type 102 id 1 handle b'\x00\x00\x00\x00'
```

- 1 行目は INIT です。長さ 5、種類 1、版 3。request-id はありません
- 返ってきた VERSION は 318 バイトあり、版 3 の後ろに `posix-rename@openssh.com` などの**拡張の名前と版の組**が並んでいます
- 次は OPEN（3）です。request-id 1、長さ 9 の `hello.txt`、開き方のフラグ `0x00000001`（READ）、属性なし
- HANDLE（`0x66` = 102）が request-id 1 への返事として返り、ハンドルは 4 バイトの `00 00 00 00` でした

ハンドルは、サーバが開いたファイルにつけた名札です。クライアントは**中身を解釈してはならず**、長さは 256 バイトまでと決められています（[draft-02 6.2](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02#section-6.2)）。OpenSSH の `sftp-server` は、内部の表の添字をそのまま入れているようです。

続けて、**返事を待たずに** READ を 3 つ送りました。request-id は 10、11、12 で、オフセットはそれぞれ 0、6、100、長さはどれも 6 バイトです。

```
>> 00 00 00 19 05 00 00 00 0a 00 00 00 04 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 06
>> 00 00 00 19 05 00 00 00 0b 00 00 00 04 00 00 00 00 00 00 00 00 00 00 00 06 00 00 00 06
>> 00 00 00 19 05 00 00 00 0c 00 00 00 04 00 00 00 00 00 00 00 00 00 00 00 64 00 00 00 06
<< 00 00 00 0f 67 00 00 00 0a 00 00 00 06 68 65 6c 6c 6f 2c
   DATA id 10 b'hello,'
<< 00 00 00 0f 67 00 00 00 0b 00 00 00 06 20 73 66 74 70 0a
   DATA id 11 b' sftp\n'
<< 00 00 00 1c 65 00 00 00 0c 00 00 00 01 00 00 00 0b 45 6e 64 20 6f 66 20 66 69 6c 65 00 00 00 00
   STATUS id 12 code 1
>> 00 00 00 0d 04 00 00 00 14 00 00 00 04 00 00 00 00
<< 00 00 00 18 65 00 00 00 14 00 00 00 00 00 00 00 07 53 75 63 63 65 73 73 00 00 00 00
   type 101 id 20 code 0
```

12 バイトのファイルの 100 バイト目からの READ には、DATA ではなく STATUS のコード 1（`SSH_FX_EOF`）と `End of file` の文字列が返りました。最後の CLOSE（4、request-id 20）には STATUS のコード 0（`SSH_FX_OK`）が返っています。

### request-id が多重化を可能にする

この 3 つの READ のように、クライアントは返事を待たずにいくつでも要求を送ってよく、**未応答の要求の数に上限はありません**。サーバは要求と違う順番で返事をしてもよく、どの返事がどの要求に対応するかは request-id で突き合わせます。ただし、**同じファイルに関する要求は受け取った順に処理しなければなりません**（[draft-02 3](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02#section-3)、[6.1](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02#section-6.1)）。

第 65 回の HTTP/2 がストリーム番号で 1 本の接続に何本ものやり取りを重ねたのと同じ発想が、SSH のチャネルの**さらに内側**で、もう一度使われているわけです。この多重化が、後で見る速さを左右します。

## 拡張と、実際の要求の並び

### VERSION に並ぶ拡張

`sftp -vvv` は、VERSION に並んでいた拡張を読み取って表示します。

```
debug2: Remote version: 3
debug2: Server supports extension "posix-rename@openssh.com" revision 1
debug2: Server supports extension "statvfs@openssh.com" revision 2
debug2: Server supports extension "fstatvfs@openssh.com" revision 2
debug2: Server supports extension "hardlink@openssh.com" revision 1
debug2: Server supports extension "fsync@openssh.com" revision 1
debug2: Server supports extension "lsetstat@openssh.com" revision 1
debug2: Server supports extension "limits@openssh.com" revision 1
debug2: Server supports extension "expand-path@openssh.com" revision 1
debug2: Server supports extension "copy-data" revision 1
debug2: Unrecognised server extension "home-directory"
debug2: Server supports extension "users-groups-by-id@openssh.com" revision 1
debug3: Sent message limits@openssh.com I:1
debug3: Received limits reply T:201 I:1
debug3: server upload/download buffer sizes 261120 / 261120; using 261120 / 261120
debug3: server handle limit 1048571; using 64
```

拡張の多くは、版 3 に足りない POSIX の操作を補うものです。たとえば版 3 の RENAME は置き先が既にあると失敗するので、`rename(2)` と同じく上書きする `posix-rename@openssh.com` があり、`fsync@openssh.com` は書いた内容をディスクに確定させます（[OpenSSH の PROTOCOL 文書](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL) 4.3〜4.12）。`home-directory` だけが「Unrecognised」になっているのは、クライアントが同じ働きの `expand-path@openssh.com` を使うからだと考えられます。

速さに関わるのは **`limits@openssh.com`** です。クライアントが EXTENDED（200）で問い合わせると、サーバは次の 4 つを返します（同 4.8）。

| 項目 | 意味 | 文書が求める最小値 |
| --- | --- | --- |
| max-packet-length | 1 つの SFTP パケットの最大のバイト数 | 34000 |
| max-read-length | READ で頼める最大の長さ | 32768 |
| max-write-length | WRITE で受け付ける最大の長さ | 32768 |
| max-open-handles | 同時に開けるハンドルの数 | — |

上の出力では、サーバが 1 回の READ / WRITE で 261120 バイトまで受け付けると答え、クライアントはそれを使っています。`sftp` の `-B`（1 回の要求の大きさ）の説明には「既定は 32768 バイト」とありますが（[sftp(1)](https://man.openbsd.org/sftp)）、この拡張に答えるサーバに対しては、OpenSSH のクライアントはサーバの上限まで大きくしていることが分かります。この拡張がない版 3 では、クライアントはサーバがどこまで受け付けるかを知る方法がなく、安全な小さい値を使うしかありませんでした。

### put と get の並び

1 MiB のファイルを送って、受け取りました。クライアント側（`sftp -vvv`）の抜粋です。

```
sftp> put one.bin
```

OPEN のフラグ `0x001a` は、WRITE（0x02）、CREAT（0x08）、TRUNC（0x10）の組み合わせです（[draft-02 6.3](https://datatracker.ietf.org/doc/html/draft-ietf-secsh-filexfer-02#section-6.3)）。送るときは最初の WRITE の返事を確かめてから残りの 4 つを続けて送り、受け取るときは返事が届くたびに、同時に出しておく READ の数を 1、2、3 と増やしています。ファイルの大きさより先（1305599 まで）を頼んでいるのは、終わりが EOF の STATUS で分かるからです。

サーバ側の様子は、`sftp-server` に `-l DEBUG3` を付け、標準エラーに出させる `-e` を付けて、ファイルに書き出させて見ました（`Subsystem` のコマンドはシェルを通るので、`2>>` でつなげます）。

```

debug1: request 1: limits
debug3: request 2: realpath
realpath "."
debug3: request 4: open flags 26
open "/home/alice/x.bin" flags WRITE,CREATE,TRUNCATE mode 0644
debug1: request 4: sent handle 0
debug1: request 6: write "/home/alice/x.bin" (handle 0) off 0 len 261120
debug3: request 6: sent status 0
...
debug3: request 5: close handle 0
close "/home/alice/x.bin" bytes read 0 written 1048576
```

request-id 5 の CLOSE が、6 以降の WRITE より後に処理されています。クライアントは CLOSE 用の番号を先に確保しておき、最後に使っているわけです。番号は突き合わせのための名札で、順番の意味は持たないことがよく分かります。

## 速さは「同時にいくつ待つか」で決まる

SFTP は要求と返事のプロトコルなので、要求を 1 つずつ出して返事を待つと、**1 往復ごとに 1 つ分のデータ**しか運べません。往復時間を RTT、1 回の要求の大きさを B、同時に出しておく要求の数を R とすると、速さはおよそ R × B / RTT が上限になります。第 54 回で見た TCP の窓と同じ、帯域遅延積の話です。

手元の Docker への接続は RTT がほとんどないので、差が出ません。そこで、片道 10 ミリ秒の遅れを足すだけの小さな TCP 中継を Python で書き、その中継を通して 16 MiB のファイルを取得しました。`-B 32768` で要求を小さく固定し、`-R`（同時に出しておく要求の数。既定は 64、[sftp(1)](https://man.openbsd.org/sftp)）を変えています。各 3 回の所要時間（秒）で、接続と認証の時間を含みます。

```
$ sftp -R 1 -B 32768 -F cfg -b <(echo 'get mid.bin /dev/null') slow
```

| 条件 | 1 回目 | 2 回目 | 3 回目 |
| --- | --- | --- | --- |
| 遅れなし、`-R 1` | 1.02 | 1.25 | 0.89 |
| 遅れなし、`-R 64` | 0.64 | 0.54 | 0.56 |
| 往復 20 ミリ秒、`-R 1` | 15.65 | 21.97 | 15.48 |
| 往復 20 ミリ秒、`-R 4` | 9.28 | 7.80 | 6.44 |
| 往復 20 ミリ秒、`-R 16` | 2.81 | 6.20 | 8.35 |
| 往復 20 ミリ秒、`-R 64` | 1.19 | 1.59 | 1.67 |
| 往復 20 ミリ秒、既定（`-R 64`、`-B` は limits の値） | 1.38 | 1.08 | 1.31 |

16 MiB を 32 KiB ずつ取ると 512 回の要求になります。`-R 1` では 512 回の往復を待つことになり、20 ミリ秒の往復なら待ち時間だけで 10 秒を超えます。中継が Python の素朴なものなので値のばらつきは大きいのですが、**同時に出す数を増やせば往復の待ちが重なって消える**という傾向ははっきり出ています。遅れのない手元では、`-R 1` でも 1 秒前後で終わり、この差はほとんど見えません。

<Callout type="tip" title="遠くのサーバへの転送が遅いとき">
  SFTP の速さを決めるのは、回線の帯域だけではありません。同時に出せる要求の数と大きさ（`-R` と `-B`、またはサーバが `limits@openssh.com` で答える上限）、
  それに SSH のチャネルの窓（第 118 回の `rcvd adjust 2097152` のように、OpenSSH は 2 MiB 程度ずつ窓を開けていました）も上限になります。
  往復時間の長い経路で遅いときは、まず「往復 1 回あたりに何バイト運べているか」を計算してみると、どこが詰まっているかの見当がつきます。
  自作や古い SFTP のライブラリには、要求を 1 つずつしか出さないものがあり、その場合は回線を太くしても速くなりません。
</Callout>

## サーバ側: ファイル転送だけの利用者を作る

取引先にファイルを置いてもらう、といった用途では、「SFTP でファイルを読み書きできるが、シェルは使えず、決まったディレクトリの外は見えない」利用者が欲しくなります。OpenSSH では、次の設定で作れます。

```
Subsystem sftp /usr/lib/ssh/sftp-server

Match User bob
  ChrootDirectory /srv/sftp/%u
  ForceCommand internal-sftp
  AllowTcpForwarding no
  X11Forwarding no
  PermitTTY no
```

| 設定 | 役割（[sshd_config(5)](https://man.openbsd.org/sshd_config)） |
| --- | --- |
| `internal-sftp` | sshd の中に組み込まれた SFTP サーバ。`sftp-server` と同じ引数を受け付ける。`ChrootDirectory` と組み合わせるとき、chroot の中に補助のファイルを置かなくてよい |
| `ForceCommand internal-sftp` | 利用者が `exec` や `shell` で何を頼んでも、`internal-sftp` を動かす |
| `ChrootDirectory` | 認証の後、そのディレクトリを `/` にする。`%u` は利用者名に置き換わる。**経路のすべての要素が root の所有で、グループや他人が書き込めない**ことが条件 |

外部の `sftp-server` を使うと、chroot の中に実行ファイルや共有ライブラリを置く必要があります。`internal-sftp` は sshd 自身の中で動くので、その手間がありません。

### 確かめる

```
$ sftp -F cfg -b b3 bob
sftp> -cd ..
sftp> pwd
Remote working directory: /
sftp> put hello0 upload/report.csv
sftp> -put hello0 top.csv
dest open "/top.csv": Permission denied
sftp> ls -l upload
-rw-r--r--    ? 1001     1001            2 Oct  8 14:15 upload/report.csv

$ ssh -F cfg bob 'cat /etc/passwd'
This service allows sftp connections only.
```

- `cd ..` をしても `/` のままで、`/srv/sftp/bob` の外には出られません。`ls -la` で見える `/` の中身は、`upload` だけでした
- chroot の根（`/srv/sftp/bob`）は root の所有なので、bob はそこに書けません。書き込める場所として、bob の所有の `upload` を中に作っておく必要があります。これは不便に見えますが、根を利用者に書き換えさせないための条件そのものです
- 所有者の欄が名前でなく `?` と数字になっているのは、chroot の中に `/etc/passwd` がないからです
- コマンドの実行を頼んでも、`ForceCommand` により SFTP しか動きません

試しに chroot の根を bob の所有に変えると、ログインした直後に切られ、サーバのログに理由が残りました。

```
$ docker exec ll117-sshd chown bob /srv/sftp/bob
$ sftp -F cfg -b b3 bob
Connection to 127.0.0.1 closed by remote host.
Connection closed
$ docker logs ll117-sshd | tail -1
bad ownership or modes for chroot directory "/srv/sftp/bob"
```

`ForceCommand` が置き換えるのは、`exec` と `shell` の要求で動くコマンドだけです。第 118 回で見たポートフォワーディングは別の種類のチャネル（`direct-tcpip`）なので、`ForceCommand` の対象になりません。設定から `AllowTcpForwarding no` の行を消して bob で `-L` を試すと、サーバの内側の 22 番に届きました。行を戻すと、転送は拒否されます。

```
$ ssh -F cfg -N -L 22118:127.0.0.1:22 bob &
$ nc -w1 127.0.0.1 22118 </dev/null | head -1
SSH-2.0-OpenSSH_10.0                                                  （AllowTcpForwarding no がないとき）
channel 2: open failed: administratively prohibited: open failed     （あるとき）
```

<Callout type="warn" title="よくある誤解: ForceCommand で SFTP だけにしたので、他には何もできない">
  `ForceCommand internal-sftp` は、**コマンドを SFTP に差し替えるだけ**で、ポートフォワーディングは止めません。
  転送を止めておかないと、SFTP 専用のつもりの利用者が、**サーバが届く範囲すべてへの踏み台**になりえます。
  `AllowTcpForwarding no`、`X11Forwarding no`、`PermitTTY no` を一緒に書くか、`authorized_keys` 側で `restrict` を付けて、転送も止めておきます。
</Callout>

## rsync over SSH と sshfs

### rsync は exec で自分をもう 1 つ起動する

`rsync -e ssh` は、SFTP を使いません。`ssh -v` を挟んでみると、サーバで実行させているコマンドが見えます。

```
$ rsync -e "ssh -v -F cfg" hello0 lab:r.txt 2>&1 | grep 'Sending command'
debug1: Sending command: rsync --server . r.txt
```

旧来の SCP と同じく `exec` で、サーバ側にも `rsync` が入っていることが前提です。チャネルの中では、両端の rsync が第 81 回で見たブロックの指紋と差分をやり取りします。**SSH は暗号化された 1 本のパイプを用意しているだけ**で、その上のプロトコルは rsync のものです。macOS に入っている `rsync` は、rsync 本家ではない openrsync（プロトコル 29）でした。相手のサーバと話せたのは、rsync のプロトコルに版の取り決めがあるからです。

`exec` で動く以上、旧来の SCP と同じく、引数は利用者のシェルを通り、`ForceCommand internal-sftp` の利用者には使えません。rsync を許しつつ範囲を絞りたいときは、`authorized_keys` の `command=` で受け側のコマンドを固定するのが一般的です（第 123 回で `command=` の強制を扱います）。

### sshfs は SFTP の上のファイルシステム

sshfs は、SFTP で遠くのファイルシステムを手元にマウントします。多くの SSH サーバは SFTP を既定で有効にしているので、サーバ側に何も入れなくてよい、というのが利点です（[libfuse/sshfs](https://github.com/libfuse/sshfs)）。SFTP がもともと open、read、write、stat を番号付きの要求で送るプロトコルなので、FUSE（ユーザ空間のファイルシステム）の各操作をそのまま要求に翻訳できるわけです。

ただし、ファイルを開くたび、属性を調べるたびに往復が発生するので、往復時間の長い経路では、ファイル数の多いディレクトリに `ls -l` や `grep -r` をかけると極端に遅くなります。また同じ README は、sshfs には現在、定常的に開発する貢献者がおらず、保守者も影響の大きい問題への対応しかできない、と書いています（同上）。手元の macOS には sshfs が入っていないので、この回では動かしていません。

## 3 つを並べる

| | 旧来の SCP（`scp -O`） | SFTP（`sftp`、既定の `scp`） | rsync over SSH |
| --- | --- | --- | --- |
| チャネルで頼むもの | `exec` | `subsystem` | `exec` |
| サーバに必要なもの | `scp` の実行ファイル | `sftp-server` または `internal-sftp` | `rsync` の実行ファイル |
| ファイル名の解釈 | サーバのシェル | SFTP のパケットの文字列（シェルを通らない） | サーバのシェル |
| 仕様 | 文書化された標準なし | 2001 年のドラフトの版 3 と OpenSSH の拡張 | rsync の実装 |
| できること | 一方向のコピー | 一覧、削除、名前の変更、属性の変更、途中からの読み書き | 差分だけの同期 |
| 遠い経路での速さ | ストリームで流すので往復に左右されにくい | 同時に出す要求の数で決まる | 差分が小さければ最も少なく運ぶ |
| 利用者を絞る方法 | 確実な方法がない | `ForceCommand internal-sftp` と `ChrootDirectory` | `command=` で固定する |

SFTP を選ぶ理由は、速さよりも、**シェルを通らないことと、サーバ側で権限を絞れること**にあります。旧来の SCP は、`-O` が残っている限り使えますが、信頼できないサーバからファイルを受け取る用途には向きません。

この回で見た 3 つは、どれも SSH が作った 1 本の暗号化された通信路の中で完結していました。SSH が使えない相手とファイルをやり取りする場面では、今も FTP と、それを TLS で包んだ FTPS が使われています。次の第 122 回では、制御とデータで**接続を 2 本使う** FTP が、NAT やファイアウォール、TLS とどう噛み合わないのかを見て、SFTP と並べます。

## まとめ

- `scp -O`、`sftp`、`rsync -e ssh` はどれも SSH の上で動くが、チャネルで頼むもの（`exec` か `subsystem`）と、中で話すプロトコルが違う
- 旧来の SCP は rcp 由来で、サーバで `scp -f` / `scp -t` を `exec` する。リモートのファイル名はサーバのシェルが解釈し、空白、`$HOME`、ワイルドカード、コマンド置換がすべて効く
- どのファイルを返すかはサーバが決めるので、悪意のあるサーバは別の名前のファイルを送れる（CVE-2019-6111 など）。OpenSSH 8.0 から名前を確かめるが、ワイルドカードで頼めばパターンに合う別のファイルは通る
- OpenSSH 9.0 から `scp` の既定は SFTP。`-O` で旧来の方式に戻せる
- SFTP は `subsystem "sftp"` で始まる。シェルの初期化が何かを出力すると「Received message too long」で壊れる
- SFTP に RFC はなく、事実上の標準は 2001 年のドラフト（draft-ietf-secsh-filexfer-02）の版 3 と OpenSSH の拡張。SSHM 作業部会が文書化を目標にしている
- パケットは長さ、種類、request-id の順。open、read、write、close をハンドルで呼ぶ形で、request-id によって返事を待たずに何本も要求を重ねられる
- 速さは、同時に出す要求の数と大きさで決まる。`limits@openssh.com` でサーバの上限を知り、OpenSSH は既定で 64 本を重ねる
- ファイル転送だけの利用者は `ForceCommand internal-sftp` と `ChrootDirectory` で作る。chroot の経路は root の所有でなければならず、転送の禁止（`AllowTcpForwarding no`）は別に書く
- rsync over SSH は `exec` で `rsync --server` を起動し、第 81 回の差分のプロトコルを運ぶ。sshfs は SFTP の要求をファイルシステムの操作に対応させる
