## 「もう使わない」を誰が決めるか

前回の `malloc` の世界では、いつ `free` するかをプログラマが決めていました。早すぎれば use-after-free、2 回呼べば double free、忘れればリークです。

**ガベージコレクション**（GC）は、この判断をランタイムに任せる仕組みです。ただしランタイムは、プログラマの意図を知りません。「この先このオブジェクトを使うか」は、一般には判定できない問いです。

そこで、判定できる問いに置き換えます。

> **もう辿り着けないオブジェクトは、もう使えない。**

プログラムがオブジェクトに触るには、ポインタを辿るしかありません。辿り始める場所は決まっています。

- スタック上の局所変数（第 22 回）
- CPU のレジスタ
- グローバル変数

これらを **ルート** と呼びます。ルートからポインタを辿って届くオブジェクトは **生きている** 可能性があり、どこからも届かないものは確実に **ゴミ** です。GC は、このゴミを見つけて回収します。

「辿り着けるが二度と使わない」オブジェクトは回収されません。GC のある言語でもメモリリークが起きるのはこのためです。捨て忘れたキャッシュのマップに入ったままのオブジェクトは、ルートから辿れる限り生き続けます。

見つけ方には、大きく 2 つの系統があります。**数える**か、**辿る**かです。

## 数える: 参照カウント

各オブジェクトに「自分を指しているポインタの数」を持たせます。ポインタを代入すれば増やし、外せば減らし、0 になったらその場で解放します。

```
a = Obj()      # Obj の参照数 1
b = a          # 2
del a          # 1
del b          # 0 → その場で解放
```

利点ははっきりしています。

- **ゴミになった瞬間に回収される。** まとめて止まる時間がない
- ファイルやソケットのような資源も、使い終わった瞬間に閉じられる

Python（CPython）、Swift、Objective-C の ARC、C++ の `shared_ptr`、Rust の `Rc` / `Arc` が、この方式です。

欠点も 2 つあります。

**代入のたびにコストがかかる。** ポインタをコピーするだけで、カウンタの書き換えが起きます。マルチスレッドなら、そのカウンタの更新は第 37 回のアトミック操作でなければなりません。さらに、同じオブジェクトを複数のスレッドが触ると、カウンタの入ったキャッシュラインを奪い合います（第 17 回の false sharing と同じ構図です）。Rust が `Rc`（スレッド間で共有しない、普通の加算）と `Arc`（アトミック）を分けているのは、このコストを払うかどうかを選ばせるためです。

**循環を回収できない。**

```
a.next = b
b.next = a
del a, b       # a も b も、互いに指し合っているので参照数は 1 のまま
```

どこからも辿れないのに、カウントは 0 になりません。CPython は、参照カウントとは別に **循環を探すための GC** を持っていて、定期的に動かしています。

## 辿る: マーク&スイープ

もう 1 つの系統は、定義どおりに辿る方式です。

```
1. マーク:   ルートから辿れるオブジェクトに印を付ける
2. スイープ: ヒープ全体を眺め、印の無いものを解放する
```

```
 ルート ──→ [A] ──→ [B]          [D] ──→ [E]
             │                     ↑       │
             └──→ [C]              └───────┘
 マーク後:  A B C に印。D と E は循環しているが、ルートから届かない
 スイープ:  D と E を解放
```

循環は自然に回収されます。代入のたびのコストもありません。

代わりに、**辿っている最中にポインタを書き換えられると困ります**。印を付け終えた A に、まだ見ていないオブジェクトへのポインタが新しく書き込まれたら、そのオブジェクトは印が無いまま回収されてしまいます。最も単純な解決は、GC の間 **プログラムを止める** ことです。これを **Stop the World**（STW）と呼びます。

ヒープが大きいほど辿る量が増え、止まる時間が長くなります。数 GB のヒープで数百ミリ秒止まれば、ウェブサーバの応答時間にそのまま出ます。

## 動かす: コピーとコンパクション

マーク&スイープで空いた場所は、ヒープのあちこちに散らばります。前回見た **断片化** がそのまま起きます。

そこで、生きているオブジェクトを **移動して詰める** 方式があります。

**コピー GC** は、ヒープを 2 つに分け、片方だけを使います。GC のときに、生きているオブジェクトだけをもう片方へ詰めてコピーし、元の側はまるごと空きにします。

```
 GC 前（使用中の側）          GC 後（もう片方）
 ┌─┬───┬─┬──┬─┬────┐         ┌─┬─┬─┬──────────────┐
 │A│ × │C│× │E│ ×  │  ────→  │A│C│E│    空き       │
 └─┴───┴─┴──┴─┴────┘         └─┴─┴─┴──────────────┘
```

利点が 2 つあります。

- **断片化しない。** 空きは常に 1 つの連続した領域になる
- **割り当てが極端に速い。** 空きの先頭を指すポインタを、要求された大きさだけ進めるだけで済む（**バンプアロケーション**）。前回のフリーリストを探す手間がない

コストは、**生きているオブジェクトの量**に比例します。ゴミがどれだけあっても、コピーしないので関係ありません。ゴミが多いほど得な方式です。

<Callout type="warn" title="動かすと、外に渡したポインタが無効になる">
  オブジェクトを移動すると、そのアドレスを指していたポインタを全部書き換える必要があります。
  ランタイムの管理下にあるポインタは書き換えられますが、
  **第 76 回の FFI で C の側に渡したアドレス**は、ランタイムには見えません。
  移動した後に C がそのアドレスを使えば、別のオブジェクトか、空きを読みます。
  Java の JNI、C# の `fixed`、Go の cgo のポインタ規則が
  「渡している間は動かさない（ピン留め）」を要求するのは、このためです。
</Callout>

## ほとんどのオブジェクトは若くして死ぬ

多くのプログラムで観察される経験則があります。

> **ほとんどのオブジェクトは、作られてすぐに不要になる。長く生き残ったものは、その後も長く生きる。**

関数の中の一時的な文字列、リクエストごとのオブジェクト、ループの中の中間結果。これらはすぐにゴミになります。一方、設定やキャッシュは、プログラムの終わりまで生きます。

これを **世代別仮説** と呼び、これを利用したのが **世代別 GC** です。

```
 若い世代（小さい）         古い世代（大きい）
 ┌──────────────┐  生き残ったら  ┌──────────────────────────┐
 │ 新しく作られた  │  ─────────→  │ 何度も生き残ったもの          │
 │ ものは全部ここ  │   昇格        │                            │
 └──────────────┘               └──────────────────────────┘
   頻繁に GC（コピー）             たまに GC（マーク&スイープ など）
```

若い世代はほぼゴミなので、コピー GC で回収すると、コピーする量がごくわずかで済みます。古い世代は滅多に見ません。**ヒープ全体を辿る回数が大きく減ります。**

ただし、1 つ問題があります。若い世代だけを GC するとき、ルートは局所変数だけではありません。**古い世代のオブジェクトが若いオブジェクトを指している**なら、それも生きています。これを見落とさないために、古い世代を全部辿っていては意味がありません。

そこで、**ポインタの書き込みを監視**します。古いオブジェクトに若いオブジェクトへのポインタが書き込まれたら、その場所を記録しておく。若い世代の GC では、この記録（**カードテーブル**や **remembered set**）もルートとして扱います。

ポインタの書き込みのたびに、この記録のための数命令が差し込まれます。これを **ライトバリア** と呼びます。コンパイラが自動で挿入するので、プログラマには見えません。第 37 回で見たメモリバリアとは別物です。名前が似ているので注意が必要です。

## 止めずに辿る

世代別にしても、古い世代の GC ではヒープの大部分を辿ります。そこで、**プログラムを動かしたまま辿る**方式（並行 GC）が作られてきました。

問題は、さきほどの「辿っている最中の書き換え」です。これもライトバリアで解決します。GC が動いている間は、ポインタの書き込みのたびに「このポインタの先は、まだ見ていないかもしれない」と GC に知らせます。辿り終えたと思った後でも、知らされたものは追加で辿ります。

完全に止まらないわけではありません。ルートの読み取りや、最後の確認のために短い停止が入ります。ただし、その時間はヒープの大きさにあまり依存しなくなります。

代わりに払うものがあります。

| 払うもの | 理由 |
| --- | --- |
| CPU 時間 | GC のスレッドがプログラムと並んで動く。ライトバリアの分、プログラム自体も遅くなる |
| メモリ | GC が終わる前に、プログラムは新しいオブジェクトを作り続ける。その分の余裕が要る |

**停止時間、スループット、メモリ使用量**の 3 つは同時には良くできません。どの GC も、この三角形のどこに立つかを選んでいます。

## 実例

**Go** は、移動しない（コピーしない）並行マーク&スイープです。世代別ではありません。前回の話でいえば、ヒープの管理は tcmalloc を下敷きにしたサイズクラスのアロケータで、GC はその上で印を付けて回収します。`GOGC`（既定 100）は「前回の GC 後に生きていた量の何 % 増えたら次の GC を始めるか」で、メモリと CPU の交換を直接指定する値です。Go 1.26 では、オブジェクトを 1 つずつ辿る代わりに、8KiB のスパンをアドレス順に処理してキャッシュの局所性を高めた新しい実装（Green Tea）が既定になりました（[Go 1.26 リリースノート](https://go.dev/doc/go1.26)、[Go Blog](https://go.dev/blog/greenteagc)）。第 3 章の話が、GC の設計にそのまま効いている例です。

**Java**（HotSpot）は複数の GC を選べます。既定は G1 で、ヒープを小さな領域に分け、ゴミの多い領域から優先的にコピーして回収します。停止時間を極端に短くしたい用途には ZGC があり、JDK 21 で世代別モードが入り、JDK 23 でそれが既定に、JDK 24 で世代別でないモードが削除されました（[JEP 490](https://openjdk.org/jeps/490)）。世代別仮説が、停止時間の短い GC にも有効だったということです。

**Python**（CPython）は、参照カウントに、循環を回収する世代別の GC を組み合わせています。Python 3.14.0 では、停止時間を短くするために循環 GC を **インクリメンタル**（少しずつ進める方式）に変えましたが、本番環境でメモリ使用量が大きく増えるという報告が相次ぎ、3.14.5 で元の方式に戻されました（[What's New in Python 3.14](https://docs.python.org/3/whatsnew/3.14.html)）。停止時間を削った分、ゴミが回収されるまでの時間が延び、メモリが溜まったわけです。**さきほどの三角形が、実際の言語で動いた例**です。

<Callout type="tip" title="GC とコンテナのメモリ上限">
  GC は「どこまでメモリが使えるか」を知らないと、上限まで余裕があると思ってゴミを溜め、
  第 92 回の OOM kill に当たります。
  Go の `GOMEMLIMIT`、Java の `-XX:MaxRAMPercentage` は、
  **GC に上限を教えて、そこに近づいたら積極的に回収させる**ための設定です。
</Callout>

## まとめ

- GC は「使わないか」ではなく「ルートから辿れないか」で判定する。辿れるものが残るリークは防げない
- 参照カウントは即座に回収できるが、代入のたびにコストがかかり、循環を回収できない
- マーク&スイープは循環も回収できるが、辿る間の書き換えを防ぐために止まる
- コピー GC は生きている量だけに比例し、断片化せず、割り当てが速い。ただし FFI に渡したポインタが問題になる
- 世代別 GC は「ほとんどのオブジェクトは若くして死ぬ」を利用する。古いものから若いものへのポインタはライトバリアで記録する
- 停止時間、スループット、メモリの 3 つは同時に良くできない

ここまでで第 4 章は終わりです。次は、プログラムがそもそもどうやって実行可能な形になり、メモリに載るのかを見ます。
