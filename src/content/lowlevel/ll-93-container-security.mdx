## コンテナの root は誰か

コンテナの中で `id` を実行すると、多くの場合 root と表示されます。

```bash
docker run --rm alpine sh -c 'id; cat /proc/self/uid_map'
```

```
uid=0(root) gid=0(root) ...
         0          0 4294967295
```

`uid_map` は、第 84 回で見た**ユーザ名前空間**の対応表です。「コンテナの中の 0 から始まる 4294967295 個の ID を、外の 0 から始まる ID に対応させる」と読みます。つまり**何も変換していません**。コンテナの root は、カーネルから見てホストの uid 0 そのものです。

それでもホストを自由にできないのは、**root の権限が削られている**からです。この回では、その削り方を順に見ます。そして最後に、中で動かす**イメージそのもの**を信用してよいかという、別の方向の話をします。

## root の権限を分割する: capabilities

Unix の伝統では、権限は「uid 0 か、それ以外か」の 2 択でした。root なら何でもでき、そうでなければほとんど何もできない。

Linux は root の権限を約 40 個の **capabilities** に分割しています。

| capability | できること |
| --- | --- |
| `CAP_NET_BIND_SERVICE` | 1024 未満のポートで待ち受ける |
| `CAP_CHOWN` | ファイルの所有者を変える |
| `CAP_KILL` | 他のユーザのプロセスにシグナルを送る |
| `CAP_NET_ADMIN` | ネットワークの設定を変える |
| `CAP_SYS_PTRACE` | 他のプロセスをデバッグする |
| `CAP_SYS_ADMIN` | マウントなど、他に分類されなかった大量の操作 |

Docker は、必要なものだけを残して他をすべて落とした状態でコンテナを起動します（[Docker Docs](https://docs.docker.com/engine/security/)）。手元で確かめると、残っているのは 14 個でした。

```bash
docker run --rm alpine grep CapEff /proc/self/status
# CapEff: 00000000a80425fb
```

このビット列を読むと、`CHOWN`、`DAC_OVERRIDE`、`FOWNER`、`FSETID`、`KILL`、`SETGID`、`SETUID`、`SETPCAP`、`NET_BIND_SERVICE`、`NET_RAW`、`SYS_CHROOT`、`MKNOD`、`AUDIT_WRITE`、`SETFCAP` です。**`CAP_SYS_ADMIN` が無い**ので、コンテナの中の root でも `mount` はできません。

```bash
docker run --rm alpine mount -t tmpfs none /mnt
# mount: permission denied (are you root?)
```

さらに絞れます。多くの Web アプリケーションは、1 つも要りません。

```bash
docker run --rm --cap-drop ALL alpine sh -c 'grep CapEff /proc/self/status; chown nobody /tmp'
# CapEff: 0000000000000000
# chown: /tmp: Operation not permitted
```

<Callout type="warn" title="--privileged は全部を戻す">
  `--privileged` を付けると、capabilities をすべて与え、seccomp と AppArmor を外し、
  ホストのデバイスもすべて見せます。**ホストの root とほぼ同じ**です。
  「動かないから付けた」で済ませてよいものではありません。
  必要な capability だけを `--cap-add` で足すのが正しい対応です。
</Callout>

## システムコールを絞る: seccomp

capabilities は「root の特権操作」を分けるものでした。**seccomp** はもっと手前で、**呼べるシステムコールそのもの**を制限します。

第 41 回で見たとおり、ユーザ空間からカーネルに触る窓口はシステムコールだけです。第 84 回では、コンテナの弱点はカーネルを共有していることで、システムコールは 300 以上あると書きました。**窓口を減らせば、カーネルの脆弱性に届く道も減ります**。

seccomp は、プロセスがシステムコールを呼ぶたびに、カーネルの中で小さなフィルタ（BPF のプログラム）を実行し、許可するか拒否するかを決めます。

```
アプリケーション
    │ syscall 命令
    ▼
seccomp のフィルタ ──── 許可リストに無い → EPERM を返す
    │ 許可
    ▼
カーネルの本来の処理
```

Docker の既定のプロファイルは**許可リスト**です。既定の動作を「拒否」にし、許可するシステムコールを列挙しています。結果として、300 以上のうち約 44 個が使えなくなります（[Docker Docs](https://docs.docker.com/engine/security/seccomp/)）。

| 拒否される例 | 理由 |
| --- | --- |
| `reboot` | ホストを再起動させない |
| `kexec_load` | 別のカーネルを読み込ませない |
| `init_module` / `delete_module` | カーネルモジュールを操作させない |
| `mount` / `umount2` | ファイルシステムの構成を変えさせない（`CAP_SYS_ADMIN` があれば許可） |
| `unshare` / `clone` の一部 | 新しい名前空間を作らせない |
| `ptrace` | Linux 4.8 より前のカーネルでは seccomp を回避できたため（新しいカーネルでは許可） |

コンテナの中から、フィルタが掛かっているかを確かめられます。

```bash
docker run --rm alpine grep Seccomp: /proc/self/status
# Seccomp: 2          ← フィルタが有効

docker run --rm --security-opt seccomp=unconfined alpine grep Seccomp: /proc/self/status
# Seccomp: 0          ← 無効
```

<Callout type="note" title="許可リストと、Wasm のケイパビリティ">
  第 78 回で、「全部できる状態から禁止を足す」アクセス制御と、
  「何もできない状態から許可を渡す」ケイパビリティを比べました。
  seccomp の許可リストは、**カーネルが全部できる状態を前提に、後から窓口を塞ぐ**ものです。
  塞ぎ忘れがあればそこから届きます。
  Wasm は、そもそも窓口を持たないところから始めます。同じ「分離」でも出発点が逆です。
</Callout>

## さらに重ねる

capabilities と seccomp のほかにも、独立した仕組みを重ねられます。どれか 1 つが破られても、次で止めるためです。

| 仕組み | 何を制限するか |
| --- | --- |
| **AppArmor** / **SELinux** | ファイルのパスやラベルごとに、読み書きや実行を許可する。Docker は既定のプロファイルを当てる |
| **`--read-only`** | ルートファイルシステムを読み取り専用にする。書く必要のある場所だけ tmpfs やボリュームにする |
| **`--security-opt no-new-privileges`** | setuid のファイルを実行しても権限が上がらないようにする |
| **`USER`**（Dockerfile） | そもそも root で動かさない |

```bash
docker run --rm --read-only alpine touch /x
# touch: /x: Read-only file system
```

読み取り専用にしておくと、侵入されても**実行ファイルを置き換えたり、ツールを持ち込んだりしにくく**なります。

## root を root でなくする: ユーザ名前空間と rootless

ここまでは、uid 0 のまま権限を削る方法でした。根本的な対策は、**コンテナの root をホストの一般ユーザに対応させる**ことです。第 84 回で見たユーザ名前空間の、本来の使い方です（[Docker Docs](https://docs.docker.com/engine/security/)）。

```
         コンテナの中         ホスト
uid_map:  0              →  100000
          1              →  100001
          ...
```

こうすると、コンテナから抜け出せたとしても、ホストでは uid 100000 の一般ユーザでしかありません。

さらに進めたのが **rootless** です。Docker の rootless モードや Podman では、**コンテナを管理するデーモン自体を一般ユーザで動かします**。第 86 回で見た dockerd、containerd、runc の連鎖全体が root ではなくなります。

| 方式 | コンテナの root | デーモン |
| --- | --- | --- |
| 通常の Docker | ホストの uid 0（権限は削られている） | root |
| `userns-remap` | ホストの一般ユーザ | root |
| rootless Docker / Podman | ホストの一般ユーザ | 一般ユーザ |

rootless では、1024 未満のポートを開けない、一部のネットワークの機能が遅い、cgroup の制限に systemd の設定が要るといった制約があります。それでも、**デーモンが root で動いていること**そのものが大きな危険なので、選ぶ価値があります。次の節がその理由です。

## docker.sock を渡すということ

CI やコンテナの監視ツールで、次のような設定を見かけます。

```bash
docker run -v /var/run/docker.sock:/var/run/docker.sock some-tool
```

コンテナの中から Docker を操作するためのものです。しかし、この socket の先にいるのは **root で動いている dockerd** です。socket に書き込める者は、dockerd に何でも頼めます。

```bash
# docker.sock を渡されたコンテナの中から
docker run -v /:/host --privileged alpine chroot /host
```

**ホストの `/` をマウントした特権コンテナを作り、その中でホストのファイルシステムに入る**。これで、ホストの root と同じことができます。Docker のドキュメントも、ホストの `/` をマウントしたコンテナが制限なくホストを書き換えられることを明記しています（[Docker Docs](https://docs.docker.com/engine/security/)）。

<Callout type="warn" title="docker グループも同じ">
  一般ユーザを `docker` グループに入れて `sudo` なしで `docker` を使えるようにするのも、
  **その人に root を渡す**のと同じ意味です。socket の権限が `docker` グループに与えられているだけだからです。
  docker.sock のマウントも docker グループも、**root の権限を渡す操作**として扱ってください。
</Callout>

## 中身を信用できるか

ここまでは、**動いているコンテナを閉じ込める**話でした。もう一つの問題は、**そもそも動かすイメージが本物か、何が入っているか**です。

### digest で固定する

```dockerfile
FROM node:22                     # タグ。指す先は後から変わりうる
FROM node:22@sha256:9a3b...      # digest。中身が 1 ビットでも違えば一致しない
```

第 85 回で見たとおり、digest は中身のハッシュです。タグは書き換えられますが、digest は書き換えられません。レジストリが乗っ取られても、**同じ digest で違う中身を返すことはできません**。

### 脆弱性を走査する

**Trivy** や **Docker Scout** は、イメージの層を開いて、OS のパッケージや言語のライブラリの版を調べ、既知の脆弱性の一覧と突き合わせます。

```bash
trivy image my-app:latest
docker scout cves my-app:latest
```

### 部品表と出どころを添付する

前回見た **SBOM** は、Buildpacks だけのものではありません。BuildKit は、ビルドしたイメージに次の 2 種類の**証明**（attestation）を付けられます（[Docker Docs](https://docs.docker.com/build/metadata/attestations/)）。

| 証明 | 中身 | 既定 |
| --- | --- | --- |
| **SBOM** | イメージに入っているソフトウェアの一覧 | `--sbom=true` で付ける |
| **provenance** | どのソースから、どの手順で、どこでビルドしたか | 最小限（`mode=min`）が既定で付く |

provenance は **SLSA**（Supply-chain Levels for Software Artifacts）という枠組みの形式で書かれます。「このイメージは、このリポジトリのこのコミットから、この CI でビルドされた」という記録です。

### 署名する

最後に、**誰が作ったか**を証明します。**cosign**（Sigstore）は、イメージの digest に署名し、その署名をレジストリに一緒に置きます。

```bash
cosign sign my-registry/my-app@sha256:...
cosign verify my-registry/my-app@sha256:... --certificate-identity=... --certificate-oidc-issuer=...
```

Sigstore では、長期間保管する秘密鍵を持たずに、CI の OIDC の身元（「この GitHub リポジトリのこのワークフロー」）から短命な証明書を発行して署名できます。署名の記録は公開の透明性ログに残ります。

```
ソースのコミット
   │ ビルド（provenance: どこで、何から）
   ▼
イメージ（digest）── SBOM（何が入っているか）
   │ 署名（誰が）
   ▼
実行する側で検証してから動かす
```

**閉じ込める**対策と、**中身を確かめる**対策は、守る方向が違います。前者は「中身が悪くても被害を広げない」、後者は「悪い中身を動かさない」。両方が要ります。

## まとめ

- ユーザ名前空間を使わない限り、コンテナの root はホストの uid 0。権限を削ることで守っている
- capabilities は root の権限の分割。Docker は 14 個だけ残す。`--cap-drop ALL` でさらに絞れる
- seccomp は呼べるシステムコールの許可リスト。既定で約 44 個を塞ぐ
- AppArmor / SELinux、読み取り専用のルート、no-new-privileges、`USER` を重ねる
- ユーザ名前空間と rootless は、root を root でなくする根本的な対策
- docker.sock と docker グループは、ホストの root を渡すのと同じ
- digest で固定し、脆弱性を走査し、SBOM と provenance を付け、署名して検証する

ここまでで第 15 章は終わりです。1 台のマシンでコンテナを作り、動かし、絞るところまで来ました。次の章では、それを**何百台ものマシンに配り、宣言したとおりの状態を保ち続ける**仕組みに入ります。
