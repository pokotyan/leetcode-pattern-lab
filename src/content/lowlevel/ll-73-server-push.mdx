## この章で見るもの

第 11 章では、HTTP/2 のフレーム（第 65 回）、HTTP/3 と QUIC（第 66 回）、その上の gRPC（第 69〜72 回）を見ました。どれも、**呼び出した側が要求を送り、相手が応答を返す**形です。gRPC のサーバストリーミングでさえ、ストリームを開くのはクライアントです。

ところが、この形に収まらない通信があります。

- チャットの新しい発言や、在庫の変化を、起きた瞬間に画面へ出したい
- 回線が細く、電池も少ない機器に、必要なときだけ知らせたい
- 端末同士で、サーバを経由せずに音声や映像をやり取りしたい
- ゲームのように、少し遅れて届いた情報には意味がない
- 複数人が同じ文書を同時に書き換え、最後に同じ内容へ揃えたい

第 12 章では、こうした通信を 8 回に分けて扱います。最初のこの回は、いちばん身近な問題、**HTTP の上でサーバから送る**ための手段です。ポーリング、ロングポーリング、SSE、WebSocket の 4 つを順に見て、手元でハンドシェイクとフレームを読み、運用で起きることを再現します。

## 実験の環境

この回の実験は、次の環境で行いました。サーバは Node の標準モジュールだけで書き、WebSocket のハンドシェイクとフレームの処理も手で実装しています。ライブラリが隠している部分を見るためです。

| 項目 | バージョン |
| --- | --- |
| OS | macOS（Darwin 25.2.0、arm64） |
| Node | 手元は v20.19.0、コンテナの中は v22.23.3（`node:22-alpine`） |
| Python | 3.14.0（生の TCP でつなぐクライアント） |

| nginx | 1.29.8（`nginx:1.29-alpine`） |

サーバは 1 秒ごとに番号付きのイベントを 1 つ作り、直近の 100 件を覚えておきます。これを 4 つの方法で配ります。

## 聞きに行く: ポーリング

HTTP の枠の中でいちばん素直なのは、**クライアントが定期的に聞きに行く**ことです。「前回もらった番号より後に何かあるか」を、たとえば 5 秒ごとに尋ねます。

```
$ curl -s -w '  (%{time_total}s)\n' 'http://127.0.0.1:8080/poll?since=431'
[]  (0.002032s)
```

何も無ければ空の配列がすぐ返ります。仕組みは単純で、どのプロキシもキャッシュも問題なく通ります。その代わりに、2 つの費用があります。

- **遅れ**: 変化が起きてから次に聞きに来るまで、最大で間隔 1 回分待たされる
- **無駄な往復**: 何も起きていなくても、間隔ごとに要求と応答が往復する

間隔を縮めれば遅れは減りますが、無駄な往復が増えます。1 万台のクライアントが 1 秒ごとに聞けば、変化が無くても毎秒 1 万件の要求をさばくことになります。

## 応答を待たせる: ロングポーリング

**ロングポーリング**は、サーバが**新しいものが出るまで応答を返さない**ようにする工夫です。クライアントは応答を受け取ったらすぐ次の要求を出します。手元のサーバで、最新の番号（ここでは 423）を渡して 3 回続けて待たせると次のようになりました。

```
$ for i in 1 2 3; do curl -s -w '  (%{time_total}s)\n' "http://127.0.0.1:8080/poll?since=$last&wait=1"; last=$((last+1)); done
[{"id":424,"data":"{\"n\":424,\"t\":\"07:35:08\"}"}]  (0.512092s)
[{"id":425,"data":"{\"n\":425,\"t\":\"07:35:09\"}"}]  (0.972105s)
[{"id":426,"data":"{\"n\":426,\"t\":\"07:35:10\"}"}]  (0.968464s)
```

応答はイベントが作られた直後に返り、何も無い間は往復が起きません。ただし、RFC 6202 がまとめているとおり、弱点も残ります（[RFC 6202 2.2](https://www.rfc-editor.org/rfc/rfc6202.html#section-2.2)）。

- 1 件届けるたびに、要求と応答のヘッダが 1 往復ずつ流れる
- 応答を返してから次の要求が届くまでの間に起きたことは、次の要求で拾うしかない。**どこまで受け取ったかをクライアントが送る**（上の `since`）必要がある
- 待たせている要求は、途中のプロキシから見れば「応答が遅いサーバ」である。プロキシのタイムアウトより早く、空の応答を返して張り直す必要がある

最後の 2 点は、この回の後半で SSE と WebSocket にもそのまま出てきます。

## 応答を終わらせない: SSE

ロングポーリングで 1 件返すたびに応答を閉じていたのを、**閉じずに書き足し続ける**ことにしたのが **SSE（Server-Sent Events）**です。仕様は WHATWG の HTML Standard の 9.2 節にあり、ブラウザでは `EventSource` として使えます（[HTML Standard 9.2](https://html.spec.whatwg.org/multipage/server-sent-events.html)）。

curl で取得すると、応答の中身がそのまま見えます。

```
$ curl -sN -i http://127.0.0.1:8080/events
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Transfer-Encoding: chunked

retry: 3000

id: 4
event: tick
data: {"n":4,"t":"07:24:33"}

id: 5
event: tick
data: {"n":5,"t":"07:24:34"}
```

ただの HTTP の応答です。`Content-Type` が **`text/event-stream`** で、本文が終わらないだけです。本文は UTF-8 のテキストで、1 行が 1 つのフィールド、**空行が 1 つのイベントの区切り**です（[HTML Standard 9.2.5](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream)、[9.2.6](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation)）。

| 行 | 意味 |
| --- | --- |
| `data: …` | イベントの中身。複数行あれば改行でつないで 1 つにする |
| `event: …` | イベントの種類。省略すると `message` |
| `id: …` | このイベントの ID。クライアントが覚えておき、再接続のときに送り返す |
| `retry: …` | 再接続までの待ち時間（ミリ秒）。数字だけのときに採用される |
| `: …`（コロンで始まる行） | コメント。無視される |

SSE が向いているのは、**サーバからクライアントへの一方向**の流れです。クライアントから送りたいことがあれば、別に普通の HTTP の要求を出します。

### 再接続と Last-Event-ID

SSE の価値の半分は、**切れたときの振る舞いが仕様で決まっている**ことにあります。接続が切れると、ブラウザは `retry:` で指定された時間だけ待ってから同じ URL に要求を出し直し、最後に受け取った `id:` の値を **`Last-Event-ID`** ヘッダに入れて送ります（[HTML Standard 9.2.3](https://html.spec.whatwg.org/multipage/server-sent-events.html#sse-processing-model)）。

これを確かめるため、サーバに「イベントを 3 つ送ったら TCP の接続を壊す」動作を足し、Node 22 の `EventSource`（`--experimental-eventsource` で有効になる実験的な実装）でつなぎました。

```
  0.04 open
  0.85 tick id=12 data={"n":12,"t":"07:26:54"}
  1.83 tick id=13 data={"n":13,"t":"07:26:55"}
  2.85 error readyState=0
  5.88 open
  5.88 tick id=14 data={"n":14,"t":"07:26:56"}
  5.88 tick id=15 data={"n":15,"t":"07:26:57"}
  5.88 tick id=16 data={"n":16,"t":"07:26:58"}
  5.88 tick id=17 data={"n":17,"t":"07:26:59"}
  6.83 tick id=18 data={"n":18,"t":"07:27:00"}
```

サーバの側のログは次のとおりです。

```
[sse] connect from 57121 Last-Event-ID=-
[sse] dropping 57121 after 3 events
[sse] connect from 57148 Last-Event-ID=13
```

3 つの点が読み取れます。

- 切れてから再接続まで **約 3 秒**。最初に送った `retry: 3000` のとおり
- 再接続の要求には `Last-Event-ID: 13` が付いた。サーバはそれを見て、14 から 17 を**まとめて再送**した
- サーバは id=14 を「3 つ目」として書き込んだ直後に接続を壊したが、**クライアントには届いていなかった**。`write` が成功しても届いたとは限らないこと（第 53 回）が、ここでも起きている。それでも、届いた最後の番号をクライアントが申告するので、取りこぼさずに済んだ

一方で、サーバが覚えている範囲より古い番号を申告されたら、再送はできません。手元のサーバは直近 100 件しか持たないので、100 秒以上たってから `Last-Event-ID: 7` を送ると、欠けた範囲を知らせるイベントを返すようにしてあります。

```
$ curl -sN -H 'Last-Event-ID: 7' http://127.0.0.1:8080/events
retry: 3000

event: reset
data: gap 8..19 lost

id: 20
event: tick
data: {"n":20,"t":"07:24:49"}
```

**再開位置はクライアントが持ち、再送できる範囲はサーバが持つ**、という分担です。範囲を外れたときにどうするか（全体を取り直させる、など）は、アプリケーションが決める必要があります。

<Callout type="note" title="再接続をやめさせる方法">
  `EventSource` は、接続が切れれば何度でも再接続します。
  止めたいときは、サーバが **204 No Content** を返します（[HTML Standard 9.2.1](https://html.spec.whatwg.org/multipage/server-sent-events.html#server-sent-events-intro)）。
  ステータスが 200 以外、あるいは `Content-Type` が `text/event-stream` でない応答も、再接続しない「失敗」として扱われます（[9.2.2](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-eventsource-interface)）。
  認証が切れたときに 401 を返せば、ブラウザは再接続を繰り返さずに止まります。
</Callout>

### HTTP/1.1 では 6 本まで

SSE の接続は、1 本の HTTP の要求を開いたままにします。HTTP/1.1 では 1 本の TCP 接続で同時に 1 つの要求しか扱えないので、**SSE 1 本につき TCP 接続を 1 本占有**します。ブラウザは同じ相手への HTTP/1.1 の接続数を絞っていて、MDN によればその上限は**ブラウザ全体で、ドメインごとに 6 本**です（[MDN: EventSource](https://developer.mozilla.org/en-US/docs/Web/API/EventSource)）。タブを 6 つ開けば、7 つ目のタブは SSE どころか画像 1 枚も読めなくなります。Chrome と Firefox はこの問題を「修正しない」としています（同上）。

HTTP/2 ではこの問題が消えます。SSE はストリームの 1 つにすぎず、1 本の TCP 接続の中に多数を同時に開けます（第 65 回）。同時に開けるストリームの数は `SETTINGS_MAX_CONCURRENT_STREAMS` で相手が決め、RFC 9113 は 100 を下回らない値を勧めています（[RFC 9113 6.5.2](https://www.rfc-editor.org/rfc/rfc9113.html#section-6.5.2)）。**SSE を使うなら、ブラウザとの間は HTTP/2 以上にする**のが前提と考えてよいでしょう。

## 接続を別のものに変える: WebSocket

SSE は一方向です。チャットやゲームのように、**両方向から好きなときに送りたい**場合は WebSocket を使います。仕様は RFC 6455 です（[RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html)）。

WebSocket は、HTTP の要求で始まり、途中で **HTTP であることをやめます**。最初の要求で「この TCP 接続を WebSocket に切り替えたい」と申し出て、サーバが応じたら、以後はまったく別の形式のフレームが流れます。

### Upgrade を手で打つ

Python で TCP の接続を開き、要求を手で書いて送りました。`Sec-WebSocket-Key` には、RFC 6455 の 1.3 節の例と同じ値を使っています。

```
GET /chat HTTP/1.1
Host: localhost:8080
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

返ってきた応答は次のとおりです。

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

**101 Switching Protocols** が「この接続はここから HTTP ではない」という宣言です。`Sec-WebSocket-Version` は 13 でなければなりません（[RFC 6455 4.1](https://www.rfc-editor.org/rfc/rfc6455.html#section-4.1)）。

`Sec-WebSocket-Accept` は、クライアントが送った鍵に固定の GUID `258EAFA5-E914-47DA-95CA-C5AB0DC85B11` をつなげ、SHA-1 を取って Base64 にした値です（[RFC 6455 1.3](https://www.rfc-editor.org/rfc/rfc6455.html#section-1.3)）。手元の OpenSSL で計算すると、同じ値になります。

```
$ printf '%s' 'dGhlIHNhbXBsZSBub25jZQ==258EAFA5-E914-47DA-95CA-C5AB0DC85B11' \
    | openssl sha1 -binary | base64
s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

この計算は、秘密を守るためのものではありません。鍵は要求に平文で書かれていて、誰でも同じ計算ができます。目的は、**相手が WebSocket を理解するサーバであることを確かめる**ことです。WebSocket を知らない HTTP サーバは、この値を返せません。また、ブラウザのスクリプトは `fetch` や `XMLHttpRequest` で `Sec-` で始まるヘッダを付けられないので（[Fetch Standard: forbidden request-header](https://fetch.spec.whatwg.org/#forbidden-request-header)）、普通の HTTP の要求を WebSocket の要求に見せかけることもできません。

curl でも、`-H` で同じ 4 つのヘッダを付ければ同じ 101 の応答が返ります。ただし手元の curl 8.7.1 はその先のフレームを扱わないので、応答を表示したまま止まります。

<Callout type="warn" title="Origin を確かめる">
  ブラウザは WebSocket の要求に `Origin` ヘッダを付けます（[RFC 6455 4.1](https://www.rfc-editor.org/rfc/rfc6455.html#section-4.1)）。
  WebSocket には CORS のような事前の確認が無く、別のサイトのページからでも接続を開けます。
  Cookie で認証しているなら、**サーバが `Origin` を見て、許した相手以外を拒否しなければなりません**（[RFC 6455 10.2](https://www.rfc-editor.org/rfc/rfc6455.html#section-10.2)）。
</Callout>

### フレームをバイト列で読む

101 の後は、**フレーム**が流れます。形式は次のとおりです（[RFC 6455 5.2](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.2)）。

```
 1 バイト目: FIN(1) RSV1-3(3) opcode(4)
 2 バイト目: MASK(1) 長さ(7)            0〜125 はそのまま長さ
                                        126 なら続く 2 バイトが長さ
                                        127 なら続く 8 バイトが長さ
 （MASK=1 なら）マスク鍵 4 バイト
 中身
```

| opcode | 意味 |
| --- | --- |
| 0x0 | 継続（分割したメッセージの 2 つ目以降） |
| 0x1 | テキスト（UTF-8） |
| 0x2 | バイナリ |
| 0x8 | close |
| 0x9 | ping |
| 0xA | pong |

手元のクライアントから、マスク鍵 `37 fa 21 3d` で `Hello` を送りました。サーバは受け取った文字列を大文字にして返します。

```
send: 81 85 37 fa 21 3d 7f 9f 4d 51 58
recv: 81 05 48 45 4c 4c 4f b'HELLO'
```

| バイト | 読み方 |
| --- | --- |
| `81` | FIN=1（これで完結）、opcode=0x1（テキスト） |
| `85` | MASK=1、長さ 5 |
| `37 fa 21 3d` | マスク鍵 |
| `7f 9f 4d 51 58` | `Hello` の各バイトを、鍵の 4 バイトと順に XOR したもの。`0x48 ^ 0x37 = 0x7f` |

この 11 バイトは、RFC 6455 の 5.7 節に例として載っているバイト列と一致します（[RFC 6455 5.7](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.7)）。サーバからの応答（`81 05 …`）には MASK のビットも鍵もなく、中身がそのまま見えています。

HTTP の 1 往復ではヘッダだけで数百バイトになることもありますが、WebSocket のフレームの見出しは、短いメッセージなら**サーバからは 2 バイト、クライアントからは 6 バイト**です。

### なぜクライアントだけがマスクするのか

**クライアントからサーバへのフレームは必ずマスクし、サーバからのフレームはマスクしてはならない**と決まっています。マスクの無いフレームを受け取ったサーバは、接続を閉じなければなりません（[RFC 6455 5.1](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.1)）。手元のサーバもそう作ってあり、マスクせずに `Hello` を送ると、close コード 1002（プロトコル違反）で閉じられました。

```
send: 81 05 48 65 6c 6c 6f
recv: 88 02 03 ea            ← close、コード 0x03ea = 1002
```

暗号化でもないのに、なぜこんな手間をかけるのでしょうか。理由は**途中の機器を守るため**です（[RFC 6455 10.3](https://www.rfc-editor.org/rfc/rfc6455.html#section-10.3)）。

WebSocket を作っている最中に、Huang らは次の攻撃を示しました。攻撃者のページがブラウザに、攻撃者のサーバとの WebSocket を開かせます。そして、送るデータの中身に `GET /script.js HTTP/1.1` `Host: 被害者のサイト` のような HTTP の要求そっくりのバイト列を入れます。Upgrade を理解しない透過プロキシは、この接続をまだ HTTP だと思っているので、中身を**新しい要求**として解釈し、攻撃者のサーバが返す偽の応答を被害者のサイトの内容としてキャッシュしてしまいます。

マスクは、これを防ぎます。**鍵はブラウザがフレームごとに予測できない値を選ぶ**ので、ページのスクリプトは、線の上に流れるバイト列を思いどおりに作れません。サーバからの向きをマスクしないのは、攻撃者が流すバイト列を制御できるのは**ブラウザの中のスクリプト**の側だからです。

### ping、pong、close

**ping と pong** は、接続が生きているかを確かめるための制御フレームです。ping を受け取った側は、**同じ中身**の pong を返さなければなりません（[RFC 6455 5.5.3](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.5.3)）。制御フレームは中身が 125 バイト以下で、分割してはなりません（[RFC 6455 5.5](https://www.rfc-editor.org/rfc/rfc6455.html#section-5.5)）。

```
ping sent: 89 83 ac f3 29 9a cd 91 4a     ← opcode 0x9、中身 "abc"（マスク済み）
pong recv: 8a 03 61 62 63                 ← opcode 0xA、中身 "abc"
```

ブラウザの `WebSocket` API には ping を送るメソッドがありません。ping は**サーバから送り、ブラウザが自動で pong を返す**のが普通の使い方です。

**close** は、閉じる理由を 2 バイトのコードで伝えます（[RFC 6455 7.4.1](https://www.rfc-editor.org/rfc/rfc6455.html#section-7.4.1)）。

```
close sent: 88 85 ac dc ba c4 af 34 d8 bd c9   ← コード 1000 + 理由 "bye"（マスク済み）
close recv: 88 02 03 e8                        ← コード 1000 を返す
after close recv: b''                          ← その後、サーバが TCP を閉じた
```

| コード | 意味 |
| --- | --- |
| 1000 | 正常な終了 |
| 1001 | 去る（サーバの停止、ページの移動） |
| 1002 | プロトコル違反 |
| 1003 | 受け付けられない種類のデータ |
| 1007 | 中身がその種類として正しくない（テキストが UTF-8 でない、など） |
| 1008 | ポリシー違反 |
| 1009 | メッセージが大きすぎる |
| 1011 | サーバの予期しない問題 |
| 1005 | （送らない）コードが付いていなかった |
| 1006 | （送らない）close フレーム無しに接続が切れた |

1005 と 1006 は、**フレームに入れて送ってはならない**コードです（[RFC 6455 7.4.1](https://www.rfc-editor.org/rfc/rfc6455.html#section-7.4.1)）。受け取った側のアプリケーションに状況を伝えるために、ライブラリが作り出す値です。運用で最もよく見るのは **1006** で、後で見るプロキシのタイムアウトのように、TCP が黙って切られたときに出ます。

## HTTP/2 と HTTP/3 の上の WebSocket

ここまでの WebSocket は、**HTTP/1.1 の TCP 接続を 1 本まるごと乗っ取る**仕組みでした。HTTP/2 には Upgrade の仕組みがないので、そのままでは使えません。HTTP/2 の 1 つのストリームの上で WebSocket を始める方法を定めたのが RFC 8441 です（[RFC 8441](https://www.rfc-editor.org/rfc/rfc8441.html)）。

仕組みは **拡張 CONNECT** と呼ばれます。

1. サーバが SETTINGS で `SETTINGS_ENABLE_CONNECT_PROTOCOL`（0x8）を 1 にして、使えることを知らせる（[RFC 8441 3](https://www.rfc-editor.org/rfc/rfc8441.html#section-3)）
2. クライアントは `:method` が `CONNECT`、新しい擬似ヘッダ **`:protocol` が `websocket`** の要求を、新しいストリームで送る（[RFC 8441 4](https://www.rfc-editor.org/rfc/rfc8441.html#section-4)）
3. サーバは **200** を返す。以後、そのストリームの DATA フレームの中を WebSocket のフレームが流れる

`Upgrade`、`Connection`、`Sec-WebSocket-Key`、`Sec-WebSocket-Accept` は使いません。鍵の役割は `:protocol` が引き継ぎました（[RFC 8441 5](https://www.rfc-editor.org/rfc/rfc8441.html#section-5)）。WebSocket の close に続く TCP の正常な切断は END_STREAM に、TCP の RST は `CANCEL` の RST_STREAM に置き換わります。

Node の `http2` モジュールは、この設定に対応しています。サーバで `enableConnectProtocol: true` を指定し、クライアントから拡張 CONNECT を送って、先ほどと同じ `Hello` のフレームを流しました。

```
client sees SETTINGS enableConnectProtocol = true
server got headers: {":method":"CONNECT",":protocol":"websocket",":path":"/chat",
                     ":scheme":"http",":authority":"localhost:8443","sec-websocket-version":"13"}
client got response: {":status":200,...} stream id 1
server got frame bytes: 818537fa213d7f9f4d5158
client got frame bytes: 810548454c4c4f "HELLO"
server: END_STREAM from client
```

ストリームの中を流れるフレームのバイト列は、HTTP/1.1 のときとまったく同じです。変わったのは**始め方と終わらせ方**だけです。

これにより、1 本の TCP 接続の上で、通常の要求と複数の WebSocket を同時に扱えます。その代わり、第 65 回で見た **TCP の HOL ブロッキング**も一緒に背負います。1 つのパケットが失われると、同じ接続の上のすべての WebSocket が止まります。

HTTP/3 に同じ仕組みを持ち込んだのが RFC 9220（2022 年 6 月）です（[RFC 9220](https://www.rfc-editor.org/rfc/rfc9220.html)）。設定の番号は同じ 0x08 で、正常な終了は QUIC のストリームの FIN、異常な終了は `H3_REQUEST_CANCELLED` のストリームエラーになります。こちらは QUIC のストリームの上なので、HOL ブロッキングは WebSocket ごとに分かれます（第 66 回）。

<Callout type="note" title="実際に使われているか">
  RFC 8441 を前提に作っても、途中のプロキシが対応していなければ使われません。
  サーバが `SETTINGS_ENABLE_CONNECT_PROTOCOL` を送らなければ、クライアントは拡張 CONNECT を使えず、HTTP/1.1 で別の接続を張ります。
  たとえば nginx が RFC 8441 を受けて裏へ HTTP/1.1 の Upgrade として渡す機能は、要望の ticket が 2020 年から開いたままです（[nginx trac #1992](https://trac.nginx.org/nginx/ticket/1992)）。
  RFC 9220 については、2026 年 10 月の執筆時点で、主要なブラウザが既定で有効にしているという確かな情報は見つけられませんでした。
</Callout>

## 運用で起きること

ここからは、**長く開いたままの接続**が、途中の機器や再起動とどうぶつかるかを見ます。第 72 回で gRPC について見た問題と、根は同じです。

### 途中の機器に切られる

ロードバランサやリバースプロキシは、**一定時間データが流れない接続を切ります**。AWS の Application Load Balancer は既定で 60 秒です（[AWS: Connection idle timeout](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html#connection-idle-timeout)）。nginx が裏のサーバからの読み取りを待つ `proxy_read_timeout` も既定で 60 秒で、これは応答全体ではなく**2 回の読み取りの間隔**にかかります（[nginx: proxy_read_timeout](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout)）。

nginx 1.29.8 をサーバの前に置き、`proxy_read_timeout` を 5 秒にして再現しました。

```nginx
location /events {
  proxy_pass http://app;
  proxy_buffering off;
  proxy_read_timeout 5s;
}
location /chat {
  proxy_pass http://app;
  proxy_set_header Upgrade $http_upgrade;
  proxy_set_header Connection $connection_upgrade;
  proxy_read_timeout 5s;
}
```

まず、何も送らない SSE です。

```
$ curl -sN 'http://127.0.0.1:18080/events?quiet=1' -o /dev/null -w 'http=%{http_code} total=%{time_total}s\n'
http=200 total=5.008468s        （curl の終了コード 18: 本文が途中で終わった）
```

nginx のエラーログには、次の行が残りました。

```
[error] 29#29: *1 upstream timed out (110: Operation timed out) while reading upstream, ...
```

サーバに 2 秒ごとにコメント行 `: hb` を送らせると（`?hb=2`）、12 秒たっても切れず、curl 側のタイムアウトで終わりました。SSE の仕様も、古いプロキシ対策として **15 秒程度ごとにコメント行を送る**ことを勧めています（[HTML Standard 9.2.7](https://html.spec.whatwg.org/multipage/server-sent-events.html#authoring-notes)）。

WebSocket でも同じです。何も流れない接続は 5 秒で、**close フレーム無しに** TCP が切られました。ブラウザなら close コード 1006 として見える切れ方です。

```
== via nginx, idle
 0.02s HTTP/1.1 101 Switching Protocols
 5.01s TCP closed by peer (no close frame)
== via nginx, server ping every 2s
 0.06s HTTP/1.1 101 Switching Protocols
 2.07s frame op=0x9 payload=b'hb'
 4.07s frame op=0x9 payload=b'hb'
 ...
10.08s still open, client stops
```

サーバから 2 秒ごとに ping を送れば切れません。nginx の文書も、`proxy_read_timeout` を延ばすか、サーバから ping を送るよう案内しています（[nginx: WebSocket proxying](https://nginx.org/en/docs/http/websocket.html)）。

第 72 回で、ALB は HTTP/2 の PING フレームをアイドルタイムアウトの計算に入れないと見ました（[AWS 同上](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html#connection-idle-timeout)）。WebSocket の ping や SSE のコメント行は、途中の機器から見れば**普通のデータ**なので、この問題は起きません。

<Callout type="warn" title="Upgrade はプロキシで消える">
  `Upgrade` と `Connection` は、1 区間ごとに消費される hop-by-hop のヘッダです。
  nginx は明示しない限り、裏のサーバへ転送しません（[nginx: WebSocket proxying](https://nginx.org/en/docs/http/websocket.html)）。
  上の `proxy_set_header` を書かない location に同じ要求を送ると、サーバには `upgrade=- connection=-` の普通の GET が届き、426 が返りました。
  なお、nginx 1.29.7 から `proxy_http_version` の既定値が 1.0 から 1.1 に変わりました（[nginx: proxy_http_version](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_http_version)）。それより前の版では、`proxy_http_version 1.1;` も必要です。
</Callout>

途中の機器が**溜め込む**問題もあります。手元の nginx 1.29.8 では、`proxy_buffering` を既定の on にしたままでも、SSE のイベントは 1 秒ごとに遅れずに届きました。ところが、`gzip on; gzip_types text/event-stream;` を足すと、**40 秒待ってもヘッダすら届きません**でした。圧縮は、ある程度の量が溜まるまで出力しないからです。SSE の経路では、圧縮や応答のバッファリングをする層がどこかに無いかを確かめる必要があります。

### デプロイで全員が一斉に戻ってくる

サーバを入れ替えると、そのサーバが持っていた接続はすべて切れます。WebSocket なら close コード 1001 を送り、SSE なら応答を終わらせて、行儀よく切ることはできます。問題はその後です。**切られたクライアントは、一斉に再接続してきます**。

1 万台のクライアントが同時に切られたとして、再接続の時刻の散らし方ごとに、100 ミリ秒あたりに集中する接続数を計算しました（Python で乱数を振った試算）。

```
全員が 3 秒後（retry: 3000 のまま）    100ms あたりの最大 10000 本  （= 100000 本/秒）
3 秒 ± 10%                             100ms あたりの最大  1696 本  （=  16960 本/秒）
0〜3 秒で一様（full jitter）           100ms あたりの最大   365 本  （=   3650 本/秒）
0〜30 秒で一様                         100ms あたりの最大    52 本  （=    520 本/秒）
```

固定の待ち時間では、1 万本が同じ瞬間に戻ってきます。新しい接続ごとに TLS のハンドシェイク、認証、取りこぼしの再送が走るので、入れ替わったばかりのサーバにとっては最も重い瞬間です。ここで失敗したクライアントがまた同じ間隔で再試行すれば、同じ山が繰り返されます。

対策は、第 72 回の gRPC と同じく、**待ち時間に揺らぎ（ジッタ）を入れ、失敗が続けば指数的に延ばす**ことです（[AWS Architecture Blog: Exponential Backoff And Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)）。SSE の仕様も、前回の再接続が失敗していれば、ブラウザが指数的なバックオフを入れてよいとしています（[HTML Standard 9.2.3](https://html.spec.whatwg.org/multipage/server-sent-events.html#sse-processing-model)）。ただし、どれだけ延ばすかはブラウザ次第です。確実に散らしたいなら、方法は 2 つあります。

- WebSocket では、再接続の処理はアプリケーションが書くので、揺らぎもそこで入れる
- SSE では、サーバが止まる前に、**接続ごとにばらばらの `retry:`** を送ってから応答を終わらせる。`retry:` はストリームごとの値なので、こうすればサーバの側から散らせる

加えて、全台を同時に入れ替えないこと（第 174 回のローリングアップデート）、止める台が接続を手放すまでの猶予を取ることも効きます。

### 取りこぼしを取り戻す: 再開位置を誰が持つか

接続が切れている間に起きたことは、何もしなければ失われます。SSE では、仕様が `id:` と `Last-Event-ID` という**置き場所**を用意してくれていました。WebSocket には、それに当たるものがありません。メッセージの番号を付け、再接続のときに「どこまで受け取ったか」をクライアントから送る仕組みを、アプリケーションが作る必要があります。

どちらの場合も、決めることは同じです。

| 決めること | 選択肢の例 |
| --- | --- |
| 再開位置を誰が覚えるか | クライアントが最後の番号を覚えて申告する（SSE の方式）/ サーバが利用者ごとに既読の位置を持つ |
| 番号を誰が振るか | 1 台のサーバが連番を振る / 裏の記録（ログやストリーム）の位置をそのまま使う |
| どこまで遡れるか | 直近 N 件 / 直近 T 時間。外れたら「全体を取り直せ」と伝える |
| 重複をどう扱うか | 再送と新着が重なりうるので、クライアントが番号で捨てる |

サーバが複数台ある場合、**番号は 1 台のサーバのものであってはなりません**。別のサーバにつながり直したときに意味が通じないからです。番号は、次に見る裏の共有の記録の側で振るのが筋です。

### 送る速さより相手が遅いとき: 背圧

WebSocket や SSE では、**サーバが送りたいときに送る**ことができます。では、相手が読むのが遅いときはどうなるのでしょうか。第 54 回で見たとおり、TCP は受信側が読まなければ窓を閉じ、送信側のカーネルの送信バッファが埋まります。その先は、**アプリケーションがどうするか**です。

手元のサーバで、64 KiB のバイナリフレームを送り続ける処理を 2 通り書きました。相手はハンドシェイクの後、何も読まないクライアントです。サーバのコンテナはメモリを 256 MiB に制限しています。

1 つ目は、Node の `socket.write()` が `false`（バッファが上限を超えた）を返しても**無視して書き続ける**版です。

```
[flood:ignore] t=0.1s sent=14.0MiB writableLength=13.9MiB rss=70MiB write()=false x224
[flood:ignore] t=0.2s sent=39.0MiB writableLength=38.9MiB rss=98MiB write()=false x624
[flood:ignore] t=0.3s sent=74.0MiB writableLength=73.9MiB rss=137MiB write()=false x1184
[flood:ignore] t=0.4s sent=121.0MiB writableLength=121.0MiB rss=188MiB write()=false x1936
[flood:ignore] t=0.5s sent=175.0MiB writableLength=175.0MiB rss=247MiB write()=false x2800
$ docker inspect ... → running=false oom=true exit=137
```

`writableLength` は、カーネルにも渡せずにプロセスの中に溜まっている量です。0.5 秒で 175 MiB に達し、コンテナは **OOM で強制終了**されました。読まないクライアントが 1 つあるだけで、同じプロセスが持つ他の全員の接続も道連れになります。

2 つ目は、`false` が返ったら書くのをやめ、`drain` イベント（バッファが空いた）を待つ版です。

```
[flood:respect] t=1.0s sent=0.5MiB writableLength=0.1MiB rss=55MiB write()=false x3
...
[flood:respect] t=5.0s sent=0.5MiB writableLength=0.1MiB rss=55MiB write()=false x3
```

約 0.5 MiB（カーネルの送受信バッファに収まった分）を送ったところで止まり、メモリは増えません。これが**背圧**（バックプレッシャ）を受け止めるということです。

止めた後に、来るデータをどうするかは用途で決めます。

- **間引く**: 株価や位置情報のように、最新の値だけに意味があるものは、古い値を捨てて最新だけを残す
- **切る**: 一定量を超えて溜まったら、その接続を閉じる（close コード 1008 など）。クライアントは再接続し、再開位置から取り直す
- **待たせる**: 発生源の側を止められるなら止める。多くのクライアントに配る場面では、1 人の遅さで全員を止めることになるので使いにくい

ブラウザの側では、`WebSocket` の `bufferedAmount` が、送ったがまだ線に出ていない量を表します（[WHATWG WebSockets Standard](https://websockets.spec.whatwg.org/#dom-websocket-bufferedamount)）。送る側がブラウザでも、見るべき値は同じです。

### サーバが複数台のときのファンアウト

長く開いた接続は、**特定のサーバにつながっています**。利用者 A はサーバ 1 に、利用者 B はサーバ 2 につながっているとします。A の発言をサーバ 1 が受け取っても、サーバ 1 は B の接続を持っていません。

```
              ┌──────────────┐
  A ──WS──→  │  サーバ 1     │ ──publish("room:42", msg)──┐
              └──────────────┘                              ↓
                                                  ┌─────────────────┐
                                                  │ pub/sub の中継   │
                                                  └─────────────────┘
              ┌──────────────┐                              │
  B ←─WS───  │  サーバ 2     │ ←─subscribe("room:42")─────┘
              └──────────────┘
```

そこで、**サーバの裏に pub/sub の中継を置き**、各サーバは自分の接続が関心を持つトピックを購読します。受け取ったメッセージはまず中継に出し、中継から全サーバへ配られたものを、各サーバが自分の接続へ配ります。サーバ自身は状態を持たない形になり、台数を増やしても、どのサーバにつながってもよくなります。

中継の選び方は、前の節の「取りこぼし」と直結します。

- Redis の Pub/Sub は、**その瞬間に購読している相手にだけ**届け、記録を残しません（at-most-once）（[Redis: Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)）。サーバの再起動中に流れたメッセージは消えるので、`Last-Event-ID` で遡る元にはなりません
- Redis Streams や Kafka のように**記録を残し、位置を指定して読み直せる**中継なら、その位置を再開位置として使える

**配るだけの中継と、遡れる記録は別の役割**です。両方が要るなら、記録に書いたうえで、新着の通知だけを pub/sub で流す構成もよく取られます。次回の MQTT は、この「ブローカが配る」形をプロトコルそのものにしたものです。

## どれを選ぶか

ここまでの手段を、判断に使う軸で並べます。gRPC のサーバストリーミング（第 69 回）も比較に入れました。

| 軸 | ポーリング | ロングポーリング | SSE | WebSocket | gRPC サーバストリーミング |
| --- | --- | --- | --- | --- | --- |
| 向き | クライアント → サーバの問い合わせ | 同左 | サーバ → クライアント | 双方向 | サーバ → クライアント（双方向ストリーミングもある） |
| 遅れ | 間隔 1 回分 | 小さい | 小さい | 小さい | 小さい |
| 中身 | 任意 | 任意 | UTF-8 のテキスト | テキストとバイナリ | Protobuf |
| 再接続と再開 | 不要 | `since` を自作 | ブラウザが自動。`Last-Event-ID` | すべて自作 | 自作。gRPC の自動再試行は、応答ヘッダを受け取った後は働かない（[gRFC A6](https://github.com/grpc/proposal/blob/master/A6-client-retries.md)） |
| 途中の機器との相性 | 最もよい | タイムアウトに注意 | 普通の HTTP。圧縮・バッファリングに注意 | Upgrade の転送設定が要る | HTTP/2 を裏まで通す必要がある |
| ブラウザから | そのまま | そのまま | `EventSource` | `WebSocket` | gRPC-Web 経由。サーバストリーミングは `grpcwebtext` モードでだけ使える（[grpc-web](https://github.com/grpc/grpc-web)） |
| サーバの費用 | 要求の数に比例 | 待たせている要求の数 | 開いている接続の数 | 開いている接続の数 | 開いているストリームの数 |

選び方の目安は次のとおりです。

- **変化がまれで、数十秒の遅れが許される**なら、ポーリングで足ります。いちばん壊れにくい方法です
- **サーバからの通知が主で、クライアントからの送信はたまに**なら、SSE が第一の候補です。再接続と再開位置が仕様に入っていて、HTTP/2 の上なら接続数の問題もありません。生成 AI の応答を少しずつ表示する用途も、この形です
- **両方向から頻繁に、低い遅れで送る**なら、WebSocket です。その代わり、再開、背圧、keepalive を自分で作ります
- **サービス間の通信**で、すでに gRPC を使っているなら、サーバストリーミングが自然です。型が付き、デッドラインやフロー制御も gRPC の仕組みに乗れます。ブラウザに直接出す用途には向きません

どの手段でも、**長く開いた接続を前提にした瞬間に、アイドルタイムアウト、再接続の集中、取りこぼし、背圧、ファンアウトの 5 つ**を引き受けることになります。手段の選択より、この 5 つにどう答えるかの方が、運用の手間を大きく左右します。

## まとめ

- HTTP は要求した側にしか応答を返さない。サーバから送るには、要求を先に出させておくか、接続を HTTP 以外のものに変える
- ポーリングは単純で壊れにくいが、遅れと無駄な往復の板挟みになる。ロングポーリングは応答を待たせることで両方を減らす
- SSE は終わらない HTTP の応答。`text/event-stream` の行の形式で、`id:` と `Last-Event-ID` による再開、`retry:` による再接続の間隔が仕様で決まっている。HTTP/1.1 ではブラウザの接続数の上限に当たるので、HTTP/2 で使う
- WebSocket は 101 で HTTP をやめる。`Sec-WebSocket-Accept` は鍵と固定の GUID の SHA-1 で、相手が WebSocket を理解することを確かめる。フレームの見出しは 2〜14 バイト
- クライアントからのフレームだけをマスクするのは、ブラウザのスクリプトが線の上のバイト列を制御できないようにして、途中のプロキシを守るため
- RFC 8441 と RFC 9220 は、拡張 CONNECT で HTTP/2 と HTTP/3 のストリームの上に WebSocket を載せる。フレームは同じで、始め方と終わらせ方だけが違う
- 途中の機器は、何も流れない接続を黙って切る。SSE のコメント行や WebSocket の ping を、タイムアウトより短い間隔で流す
- 再接続には揺らぎを入れる。取りこぼしは、再開位置と遡れる範囲を決めて取り戻す。読まない相手には背圧をかけ、間引くか切る
- サーバが複数台なら、裏に pub/sub を置いてファンアウトする。配るだけの中継と、遡れる記録は役割が違う

次回は、HTTP から離れて、細い回線と小さな機器のために作られた pub/sub のプロトコル **MQTT** を見ます。この回の最後に裏方として置いたブローカが、そこでは主役になります。トピック、QoS 0/1/2、retain、Will、セッションが、切れやすい回線の上で何を保証するのかを確かめます。
