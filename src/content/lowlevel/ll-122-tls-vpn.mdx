## 接続を守る仕組みで、網をつなぐ

前回は、データベースや中間層のプロトコルが、自分の会話の途中で TLS に切り替える様子を見ました。そこでは、TLS を話すのはクライアントとサーバのプログラム自身でした。PostgreSQL のドライバが TLS を知らなければ、暗号化はできません。

では、**TLS を知らないプログラムの通信を、外から TLS で包む**ことはできるでしょうか。さらに進めて、1 本の接続ではなく、**手元の端末から出る IP パケットをまとめて**どこかの網まで運ぶことはできるでしょうか。後者がいわゆる VPN です。

答えはどちらも「できる」ですが、包む単位が大きくなるにつれて、TLS の性質がそのままでは合わなくなります。TLS は第 113 回で見たとおり、**順序どおりに確実に届くバイト列**（TCP）を前提に作られています。一方、IP パケットは、失われても並べ替わってもよいものとして運ばれます。この食い違いを、製品ごとにどう扱っているかがこの回の主題です。

## 包む単位で 3 つに分ける

| 包む単位 | 代表例 | 利用者から見えるもの | 中身の宛先を決めるのは |
| --- | --- | --- | --- |
| 1 本の TCP 接続 | stunnel | 手元の決まったポート | 設定ファイル（固定） |
| 接続ごとに宛先を選べる TCP | HTTP CONNECT、SSH の `-D`（第 120 回） | プロキシ | 接続ごとの要求 |
| IP パケット | OpenVPN、SSTP、OpenConnect、MASQUE の CONNECT-IP（第 75 回） | 仮想のネットワークインタフェース | 端末の経路表 |

上の 2 段は、プログラムの**接続**を中継します。最後の段は、OS に `tun0` のような**仮想のインタフェース**を作り、そこへ経路表で振り向けられた IP パケットを、まるごとトンネルに入れます（tun はカーネルとユーザ空間のプログラムの間で IP パケットをやり取りする仕組みです）。プログラムは自分が VPN を通っていることを知りません。

## stunnel: 1 本の TCP を TLS で包む

stunnel は、マニュアルの冒頭で「リモートのクライアントとローカルのサーバの間の TLS 暗号化の包み紙」として作られたと説明されています（[stunnel manual](https://www.stunnel.org/manual.html)）。平文しか話せないサービスの前に置き、外からの TLS を受け止めて、中身を平文で後ろに渡します。逆向きに、クライアント側に置いて、平文の接続を TLS にして送り出すこともできます。

```
  クライアント側コンテナ                         サーバ側コンテナ
 ┌──────────────────────────┐               ┌──────────────────────────────┐
 │ curl ─平文─▶ stunnel     │ ══TLS 8443══▶ │ stunnel ─平文─▶ httpd         │
 │      127.0.0.1:8080      │               │          127.0.0.1:8080      │
 └──────────────────────────┘               └──────────────────────────────┘
```

サーバ側の設定です。8443 番で TLS を受け、平文の `httpd` へつなぎます。

```ini
[web]
accept  = 0.0.0.0:8443
connect = 127.0.0.1:8080
cert    = /pki/server.crt
key     = /pki/server.key
```

クライアント側の設定です。`client = yes` で向きが逆になり、手元の 8080 番で平文を受けて、TLS でサーバへ送ります。

```ini
[web]
client  = yes
accept  = 127.0.0.1:8080
connect = server.example.com:8443
CAfile  = /pki/ca.crt
verifyChain = yes
checkHost = server.example.com
```

クライアント側のコンテナで、平文の HTTP として `curl` を打ちます。

```
$ docker exec ll121-cli curl -s http://127.0.0.1:8080/
hello from the plaintext service
```

`curl` は TLS のことを何も知りません。クライアント側の stunnel のログには、その裏で起きたことが出ています。

```
LOG5[0]: Service [web] accepted connection from 127.0.0.1:40178
LOG5[0]: s_connect: connected 172.24.0.2:8443
LOG6[0]: SNI: sending servername: server.example.com
LOG6[0]: Certificate accepted at depth=1: CN=ll121 lab CA
LOG6[0]: CERT: Host name "server.example.com" matched with "server.example.com"
LOG5[0]: Certificate accepted at depth=0: CN=server.example.com
LOG6[0]: TLS connected: new session negotiated
LOG6[0]: TLSv1.3 ciphersuite: TLS_AES_256_GCM_SHA384 (256-bit encryption)
LOG6[0]: Peer temporary key: X25519, 253 bits
LOG5[0]: Connection closed: 78 byte(s) sent to TLS, 242 byte(s) sent to socket
```

第 113 回で見た TLS 1.3 のハンドシェイクが、そのまま行われています。CA の署名をたどり（depth=1 が CA、depth=0 がサーバの証明書）、名前を照合してから、データを流しています。

### 線の上では何が見えるか

サーバ側のコンテナで、TLS の 8443 番と、平文の 8080 番の両方を同時に記録しました（ACK だけのパケットは省いています）。

```
 4  172.24.0.3:44490 → 172.24.0.2:8443  TLSv1.2  Client Hello (SNI=server.example.com)
 6  172.24.0.2:8443 → 172.24.0.3:44490  TLSv1.3  Server Hello, Change Cipher Spec, Application Data, ...
 8  172.24.0.3:44490 → 172.24.0.2:8443  TLSv1.3  Change Cipher Spec, Application Data
 9  172.24.0.2:8443 → 172.24.0.3:44490  TLSv1.3  Application Data
10  127.0.0.1:50334 → 127.0.0.1:8080    TCP      [SYN]
13  172.24.0.3:44490 → 172.24.0.2:8443  TLSv1.3  Application Data
14  127.0.0.1:50334 → 127.0.0.1:8080    HTTP     GET / HTTP/1.1
19  127.0.0.1:8080 → 127.0.0.1:50334    HTTP     HTTP/1.1 200 OK  (text/html)
```

読み取れることが 3 つあります。

- **ネットワークに出る区間（172.24.0.x）は TLS だけ**で、`GET /` が平文で見えるのはサーバの中のループバック（127.0.0.1）だけです。最初の ClientHello が `TLSv1.2` と表示されるのは、TLS 1.3 でも互換のためにレコードの版を 1.2 と書く決まりのためです（第 113 回）
- サーバ側の stunnel が後ろの `httpd` に接続する（10 番の SYN）のは、**TLS のハンドシェイクが終わった後**です。stunnel の既定では、TLS が成立しない接続は後ろのサービスに届きません
- `httpd` から見た接続の相手は `127.0.0.1` です。**本当のクライアントの IP アドレスは、後ろのサービスからは見えなくなります**。第 114 回の「TLS を終えた後ろに何を渡すか」と同じ問題で、stunnel にも PROXY protocol を足す設定などがあります

この型は、**TLS を話せない古いサービスに、プログラムを書き換えずに TLS を足す**ときに今も使われます。前回の PostgreSQL のように途中で切り替える型ではなく、接続の最初から TLS なので、第 117 回の分類では「暗黙の TLS」の側に入ります。なお、stunnel には `protocol = smtp` や `pgsql` のように、途中で切り替える型のプロトコルに合わせて最初のやり取りを代行する設定もあります（[stunnel manual](https://www.stunnel.org/manual.html)）。

### クライアント側は、既定では何も確かめない

stunnel のマニュアルによれば、`verifyChain` の既定は `no` です。さらに、チェーンを確かめる場合でも、**サーバの確認には `checkHost` か `checkIP` で特定の証明書を求めることが欠かせない**と書かれています（[stunnel manual](https://www.stunnel.org/manual.html)）。

これを確かめるために、同じ名前 `server.example.com` で自己署名した証明書を持つ偽のサーバを、別のコンテナ（`evil.example.com`）に立てました。クライアント側には、確かめる設定（`strict`）と、何も書かない設定（`lax`）の 2 つのサービスを並べました。

```ini
[strict]
client  = yes
accept  = 127.0.0.1:8081
connect = evil.example.com:8443
CAfile  = /pki/ca.crt
verifyChain = yes
checkHost = server.example.com

[lax]
client  = yes
accept  = 127.0.0.1:8082
connect = evil.example.com:8443
```

```
$ docker exec ll121-cli2 curl -sS http://127.0.0.1:8081/
curl: (56) Recv failure: Connection reset by peer
$ docker exec ll121-cli2 curl -sS http://127.0.0.1:8082/
this is NOT the real server
```

`lax` のほうは、偽のサーバの中身を何の問題もなく返しました。ログを見ると違いがはっきりします。

```
LOG4[ui]: Service [lax] needs authentication to prevent MITM attacks
...
LOG4[0]: CERT: Pre-verification error: certificate not found in local repository: self-signed certificate
LOG4[0]: Rejected by CERT at depth=0: CN=server.example.com
LOG3[0]: SSL_connect: ... error:0A000086:SSL routines::certificate verify failed
...
LOG6[1]: Peer certificate not required
LOG6[1]: CERT: Certificate verification disabled
LOG5[1]: Connection closed: 78 byte(s) sent to TLS, 237 byte(s) sent to socket
```

stunnel は起動時に「`lax` には中間者を防ぐための認証が要る」と警告していますが、**警告を出すだけで、接続は通します**。一方、`strict` で拒否されたとき、`curl` に返ったのは「接続がリセットされた」だけでした。**包まれている側のプログラムには、証明書の検証に失敗したという事情が伝わりません**。原因を調べるには、stunnel のログを見るしかありません。

<Callout type="warn" title="よくある誤解: stunnel で包んだので、経路は守られている">
  確かめない TLS が防ぐのは、経路を**眺めているだけ**の盗聴者です。経路に割り込める相手には、自分の証明書を出されて終わりです。
  これは第 145 回で見た、証明書を確かめない日和見の STARTTLS と同じ性質です。
  クライアント側の stunnel を置くときは、`CAfile`（または `CApath`）、`verifyChain = yes`、`checkHost` を必ずそろえます。
  自前の CA でよいので、**「どの名前の、どの CA の証明書なら受け入れるか」を書き下すまでが TLS の設定**です。
</Callout>

## HTTP CONNECT: 宛先を接続ごとに選ぶ

stunnel は宛先が設定ファイルで固定されていました。宛先を接続ごとに選びたいときに使われるのが、HTTP の `CONNECT` メソッドです。クライアントはプロキシに次のように頼みます（[RFC 9110 9.3.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.6)）。

```
CONNECT server.example.com:443 HTTP/1.1
Host: server.example.com:443

HTTP/1.1 200 OK
（ここから先、プロキシは両方向のバイト列をそのまま中継する）
```

2xx が返った後、プロキシは**中身を解釈せずにバイト列を流すだけ**になります。ブラウザが社内のプロキシ越しに HTTPS のサイトを開くときは、この上でサイトとの TLS を張るので、プロキシには宛先のホスト名とポートしか分かりません。プロキシとの間も HTTPS にすれば、**TLS の中に TLS が入る**形になります。

CONNECT が運べるのは TCP だけです。これを UDP と IP パケットに広げたのが、第 75 回で見た MASQUE の CONNECT-UDP（[RFC 9298](https://www.rfc-editor.org/rfc/rfc9298.html)）と CONNECT-IP（[RFC 9484](https://www.rfc-editor.org/rfc/rfc9484.html)）です。CONNECT-IP まで来ると、もう VPN そのものです。

## IP パケットを運ぶと、TCP が二重になる

ここから VPN の話に入ります。VPN は IP パケットを運ぶので、トンネルの中には利用者のアプリの TCP がそのまま入っています。トンネル自体も TCP（たとえば TCP の上の TLS）で作ると、**TCP の上に TCP が載る**ことになります。

第 120 回で見たとおり、この形では、外側の TCP が失われたパケットを再送している間に、内側の TCP も「届いていない」と判断して自分でも再送を始め、両方のタイマーが互いを悪化させます。IPsec を TCP で包む方式を定めた RFC 9329 も、TCP の中で TCP を動かすことは勧められないとし、**UDP が塞がれているときだけ TCP で包む**ことを推奨しています（[RFC 9329](https://www.rfc-editor.org/rfc/rfc9329.html)）。

そのため、TLS を使う VPN の多くは、次の 2 つのどちらかを選んでいます。

- **TLS は鍵を決めるためだけに使い、IP パケットは UDP の上の独自の形式で運ぶ**（OpenVPN）
- **TLS の接続と並べて、UDP の上の DTLS（第 77 回）の通り道を開き、使えるならそちらで運ぶ**（OpenConnect / AnyConnect）

そして、どちらも UDP が通らない網のために、TCP（多くは 443 番）で動く道を残しています。

## OpenVPN: TLS を鍵の取り決めにだけ使う

OpenVPN は IETF で標準化されたプロトコルではなく、仕様はプロジェクトのソースと付属の文書で示されています（IETF の datatracker には `openvpn` を名前に含む文書がありません）。以下は、OpenVPN のソースに付いた文書（[Network protocol](https://build.openvpn.net/doxygen/network_protocol.html)）と、2.6 のマニュアル（[OpenVPN 2.6 manual](https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html)）に基づきます。

### 2 つのチャネル

OpenVPN の 1 本のトンネルの中には、性質の違う 2 つのチャネルがあります。

```
            ┌──────────────── 制御チャネル（確実に届ける） ────────────────┐
            │  TLS のハンドシェイクと、TLS の中で送る設定の受け渡し         │
            │  → 双方向の暗号の鍵の材料を決める                          │
            │  P_CONTROL_* / P_ACK_V1   独自の確認応答と再送               │
            └────────────────────────────────────────────────────────────┘
                                 │ 鍵
                                 ▼
            ┌──────────────── データチャネル（届かなくてもよい） ──────────┐
            │  tun から読んだ IP パケットを、TLS とは別の鍵で暗号化して運ぶ  │
            │  P_DATA_V2                再送しない                        │
            └────────────────────────────────────────────────────────────┘
                         どちらも同じ UDP 1194 番（または TCP）の上
```

OpenVPN の文書は、TLS の通り道は「双方向の暗号と HMAC の鍵のための乱数の材料を交換する」ために使われると書いています（[Network protocol](https://build.openvpn.net/doxygen/network_protocol.html)）。**IP パケットそのものは TLS のレコードには入りません**。TLS で決めた鍵を使って、OpenVPN 自身の形式で 1 パケットずつ暗号化し、UDP のデータグラム 1 つに 1 つ入れて送ります。こうすれば、1 つのパケットが失われても後ろのパケットは待たされず、TCP が二重になる問題も起きません。

### パケットの先頭 1 バイト

すべてのパケットの先頭（TCP で運ぶときは、長さ 16 ビットの後ろ）には、上位 5 ビットの種類（opcode）と、下位 3 ビットの `key_id` が入った 1 バイトがあります（[Network protocol](https://build.openvpn.net/doxygen/network_protocol.html)）。`key_id` は、どの TLS のセッションで決めた鍵かを示し、鍵を作り直している途中でも古い鍵と新しい鍵を区別できるようにしています。opcode の値はソースで次のように定義されています（[ssl_pkt.h](https://build.openvpn.net/doxygen/ssl__pkt_8h_source.html)）。

| 値 | 名前 | 意味 |
| --- | --- | --- |
| 7 | `P_CONTROL_HARD_RESET_CLIENT_V2` | クライアントからの最初のパケット。以前の状態を捨てる |
| 8 | `P_CONTROL_HARD_RESET_SERVER_V2` | サーバからの最初のパケット |
| 10 | `P_CONTROL_HARD_RESET_CLIENT_V3` | 上と同じだが、クライアントごとの tls-crypt の鍵（後述の v2）を伴う |
| 3 | `P_CONTROL_SOFT_RESET_V1` | 新しい鍵への切り替え。古い鍵から順に移る |
| 4 | `P_CONTROL_V1` | 制御チャネルのパケット。中身はたいてい TLS の暗号文 |
| 5 | `P_ACK_V1` | 制御チャネルのパケットへの確認応答 |
| 9 | `P_DATA_V2` | データチャネルのパケット。peer-id 付き |

このほかに 1 と 2（鍵の取り決め方が古い V1 の最初のパケット）も定義されていますが、ソースのコメントでは V1 の opcode は無効と見なすとされています。6 の `P_DATA_V1` は、peer-id を持たない古い形式のデータチャネルのパケットです（同上）。

### UDP の上に、自前の再送の層を持つ理由

ここで、`P_ACK_V1` が目に付きます。TLS のハンドシェイクは、ClientHello から Finished まで**1 バイトも欠けず、順番どおりに届く**ことを前提にしています。UDP はそれを保証しないので、OpenVPN は制御チャネルにだけ、**確認応答と再送による単純な信頼性の層**を自前で持っています（[Network protocol](https://build.openvpn.net/doxygen/network_protocol.html)）。TLS のレコードを小さく切って `P_CONTROL_V1` に入れ、番号を振り、`P_ACK_V1` が返らなければ送り直します。

一方、データチャネルにはこの層を通しません。文書は、制御チャネルとデータチャネルが**別々の packet-id の系列**を使う理由を、「データチャネルは信頼性のないチャネルで、制御チャネルは信頼性のあるチャネルだから」と説明しています（同上）。データチャネルの packet-id は、再送のためではなく、**同じパケットを送り直されて受け入れてしまう（リプレイ）こと**を防ぐために使われます。

まとめると、OpenVPN は「確実に届けたいもの（鍵の取り決め）」と「届かなくてもよいもの（利用者の IP パケット）」を分け、前者にだけ TCP の代わりを自前で用意している、ということです。DTLS（第 77 回）が TLS の側に同じ工夫を入れたのに対し、OpenVPN は TLS の外側でそれを行っています。

### データチャネルの暗号

データチャネルで使う暗号は、OpenVPN 2.6 の `--data-ciphers` の既定で、ChaCha20-Poly1305 が使えるときは `AES-256-GCM:AES-128-GCM:CHACHA20-POLY1305` です（[OpenVPN 2.6 manual](https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html)）。いずれも第 105 回の AEAD です。

データチャネルの処理は、本来はユーザ空間の `openvpn` プロセスが行います。パケットごとにカーネルとユーザ空間を行き来するので、速度が出にくいことが弱点でした。これをカーネルに移す **DCO**（Data Channel Offload）のドライバ `ovpn` が、Linux 6.16 で取り込まれました（[Phoronix: Linux 6.16 Networking](https://www.phoronix.com/news/Linux-6.16-Networking)）。鍵の取り決め（TLS）はユーザ空間に残し、決まった鍵でパケットを暗号化する部分だけをカーネルが受け持つ形で、2 つのチャネルを分けた設計がそのまま役割の分担になっています。

### サーバの証明書を確かめる設定

OpenVPN の典型的な構成では、1 つの CA がサーバの証明書と、利用者ごとのクライアント証明書の両方を発行します。ここに落とし穴があります。クライアントが「この CA の署名がある証明書なら受け入れる」とだけ確かめていると、**別の利用者のクライアント証明書を持った人が、サーバのふりをできてしまいます**。

そのため、クライアントの設定には次の 2 行を入れるのが定石です。

```
remote-cert-tls server
verify-x509-name server.example.com name
```

`--remote-cert-tls server` は、相手の証明書に TLS のサーバ用の鍵用途（第 110 回の Extended Key Usage の `serverAuth`）があることを求めます。マニュアルは、これを**中間者攻撃を防ぐための重要な予防策**としています。`--verify-x509-name` は、相手の X.509 の名前が指定したものと等しいときだけ接続を受け入れます（[OpenVPN 2.6 manual](https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html)）。stunnel の `checkHost` と同じく、**CA の署名に加えて、名前と用途まで確かめて初めて相手を特定したことになる**という話です。

### tls-auth、tls-crypt、tls-crypt-v2

OpenVPN には、TLS のハンドシェイクの**外側**にもう 1 枚かぶせる設定があります。TLS を始める前の段階から、共有の鍵で制御チャネルのパケットを守るものです。

| 設定 | 何をするか | 鍵 |
| --- | --- | --- |
| `--tls-auth` | 制御チャネルのすべてのパケットに HMAC を付け、合わないものを TLS の処理に入る前に捨てる。「HMAC ファイアウォール」。暗号化はしない | 全員で共有する 1 つの鍵 |
| `--tls-crypt` | 制御チャネルのすべてのパケットを暗号化し、認証する。TLS で使う**証明書も外から見えなくなる** | 全員で共有する 1 つの鍵 |
| `--tls-crypt-v2` | tls-crypt と同じことを、**クライアントごとに別の鍵**で行う | クライアントごとの鍵（サーバの鍵で包んで配る） |

（[OpenVPN 2.6 manual](https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html)）。マニュアルは、サーバでサービス妨害（DoS）に最もよく耐えるには、UDP を使い、`--tls-auth` か `--tls-crypt` を併用するよう勧めています（同上）。鍵を知らない相手のパケットは、**重い TLS の処理（証明書の解析や署名の検証）に入る前に**捨てられるからです。TLS の実装に脆弱性が見つかったときも、鍵を持たない相手はそこまで届きません。

ただし、tls-auth と tls-crypt の鍵は**全員で共有**しています。tls-crypt-v2 の設計文書は、どれか 1 台のクライアントかサーバが侵害されれば、攻撃者はこの共有の鍵を手に入れる、と問題を述べ、クライアントごとに固有の鍵を持たせるのが v2 の目的だとしています（[tls-crypt-v2.txt](https://github.com/OpenVPN/openvpn/blob/master/doc/tls-crypt-v2.txt)）。opcode 10 の `P_CONTROL_HARD_RESET_CLIENT_V3` は、この v2 のために足されたものです。

<Callout type="note" title="手元では動かせなかった実験">
  OpenVPN をコンテナ同士で張り、UDP 1194 番を tshark で記録して、`P_CONTROL_HARD_RESET_CLIENT_V2` から始まる制御チャネルの中に TLS の ClientHello が切り分けて入っている様子と、
  接続後の ping が `P_DATA_V2` として流れる様子を見る予定でした。OpenVPN は tun を作るので、コンテナに `NET_ADMIN` の権限と `/dev/net/tun` を渡す必要があります。
  今回の作業環境では、その権限を付けてコンテナを起動する操作が許可されなかったため、この節は OpenVPN の文書とソースに基づく説明に留めています。
  試すときは、tls-crypt なしの状態では制御チャネルの中に TLS のハンドシェイク（証明書を含む）が見え、`--tls-crypt` を付けると見えなくなることを比べると、上の表の違いがよく分かります。
</Callout>

## SSL VPN 製品の型

企業向けの VPN 製品には、「SSL VPN」と呼ばれるものが多くあります。名前の SSL は TLS のことで、共通点は **HTTPS と同じ 443 番の TLS で接続を始める**ことです。ホテルや空港の網、社内のプロキシは、443 番の TLS ならほぼ必ず通すからです。ここでは仕様が公開されている 2 つを見ます。

### SSTP: HTTPS の上に PPP を載せる

SSTP（Secure Socket Tunneling Protocol）は Microsoft の方式で、**PPP のフレームを HTTPS の上に載せる**ものです（[MS-SSTP Overview](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-sstp/70adc1df-c4fe-4b02-8872-f1d8b9ad806a)）。PPP は電話回線の時代からある、2 点間で IP パケットを運ぶためのデータリンク層のプロトコルです。仕様の概要は、PPTP や L2TP/IPsec がホテルなどの網で通らないことを動機に挙げ、HTTPS を使えばたいていのファイアウォールと Web プロキシを越えられると書いています（同上）。

層の重なりは仕様に次のように書かれています（同上）。

```
アプリのデータ
  └ TCP / UDP（アプリの）
      └ IP（アプリの）
          └ PPP
              └ SSTP
                  └ TLS
                      └ TCP 443 番
                          └ IP
```

TLS が成立した後、クライアントは次のような HTTP の要求を送ります。メソッドは `SSTP_DUPLEX_POST`、URI は `/sra_{BA195980-CD49-458b-9E23-C84EE0ADCD75}/` で、Content-Length には 64 ビットの最大値 `18446744073709551615` を書きます（[MS-SSTP 3.2.4.1](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-sstp/60a4676f-7eec-495e-926f-af7b22a72a40)）。**「終わらない 1 つの要求の本体」として、その後のすべてのパケットを流す**わけです。サーバが 200 を返すと、以降はこの接続の上で SSTP のパケットをやり取りします。

見ての通り、SSTP は**アプリの TCP を、外側の TCP の上で運ぶ**形です。前の節の TCP の二重化を、そのまま抱えています。

SSTP にはもう 1 つ、**暗号の結び付け**（crypto binding）という仕組みがあります。PPP の認証で得た鍵の材料を使って、TLS のサーバ証明書のハッシュなどを結び付け、中間者が PPP のフレームを別の TLS 接続へ中継できないようにします（[MS-SSTP Overview](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-sstp/70adc1df-c4fe-4b02-8872-f1d8b9ad806a)）。第 115 回の SSH で、公開鍵認証の署名にセッション ID を入れてその接続でしか通用しないようにしていたのと、同じ発想です。**上の層の認証を、下の層の TLS の接続に縛り付ける**ことで、TLS を偽のサーバとの間で張られても、認証の結果を本物へ持ち込めないようにしています。

### OpenConnect / AnyConnect: TLS と DTLS を並べる

OpenConnect は、Cisco の AnyConnect と互換と考えられるプロトコルとして、個人の Internet-Draft にまとめられています（[draft-mavrogiannopoulos-openconnect-04](https://datatracker.ietf.org/doc/html/draft-mavrogiannopoulos-openconnect-04)）。2023 年 7 月に出た版が最新で、執筆時点（2026 年 10 月）では**期限切れのドラフト**であり、IETF が承認した仕様ではありません（同上）。

流れは次のとおりです（同上）。

1. クライアントは、通常 443 番で TLS を張る
2. HTTP の `CONNECT` 要求でトンネルを開く。これが主の通り道（CSTP）になる
3. 任意で、UDP の上に DTLS の通り道を開く。DTLS の鍵は、ヘッダで送るのではなく、**TLS の鍵の書き出し（exporter）の仕組みで、両者が別々に同じ値を導く**（ラベルは `EXPORTER-openconnect-psk`）
4. DTLS が使えればそちらでパケットを運び、UDP が通らなければ TCP の上の TLS に戻る

ドラフトは、DTLS の通り道を「TCP の上で TCP をトンネルする欠点を避けたい」人のためのものだと説明しています（同上）。認証や設定の受け渡しは確実に届く TLS の側で済ませ、利用者のパケットは再送しない DTLS の側で運ぶ、という分け方は、OpenVPN の 2 つのチャネルとよく似ています。違いは、OpenVPN が TLS の外で信頼性の層を自作したのに対し、OpenConnect は**信頼できる通り道として本物の TCP の上の TLS を、信頼できない通り道として DTLS を**、それぞれ既製の部品で並べている点です。

CSTP の側では、パケットごとに `S` `T` `F` の 3 文字で始まる 8 バイトのヘッダを付け、その後ろに長さと種類（データ、キープアライブなど）を書いて、TLS のレコードに入れます（同上）。TLS は区切りのないバイト列なので、**その上で IP パケットの切れ目を示すのは、上の層の仕事**です。SSTP が PPP のフレームを区切るのも同じ理由です。

<Callout type="warn" title="インターネットに面した SSL VPN 機器は、真っ先に狙われる">
  SSL VPN の機器は、社外から誰でも届く 443 番で待ち受け、認証の前に HTTP の要求を解釈します。
  つまり、**認証より前にある Web アプリ**です。ここに脆弱性があれば、ID もパスワードもなしに、社内ネットワークへの入口を取られます。
  2024 年には、Ivanti Connect Secure の CVE-2023-46805、CVE-2024-21887、CVE-2024-21893 が実際に悪用され、CISA などが共同で注意喚起を出しました。
  組み合わせると認証を迂回して高い権限で任意のコマンドを実行でき、CISA の検証では工場出荷状態に戻しても root の足場が残りうることが示されています（[CISA AA24-060B](https://www.cisa.gov/news-events/cybersecurity-advisories/aa24-060b)）。
  VPN は「中に入れば信頼される」入口なので（第 138 回）、その入口の機器自体の更新と監視が、TLS の設定以上に重要になります。
</Callout>

## TLS を使わない VPN との比べ方

ここまでの VPN は、TLS のハンドシェイクと PKI（証明書）を相手の確認に使っていました。これに対し、TLS を使わない VPN も広く使われています。

### WireGuard

WireGuard は、相手の確認と鍵交換に Noise という枠組みを使います。正確な構成名は `Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s` で、使う暗号が名前の中で固定されています。**すべてのパケットは UDP で送られ**、認証されていないクライアントには**一切応答しない**と説明されています（[WireGuard Protocol](https://www.wireguard.com/protocol/)）。

TLS を使う VPN と違う点は次のとおりです。

- **証明書がない**: 相手は公開鍵そのもので指定する。第 115 回の SSH の `authorized_keys` に近く、誰がどの鍵かの対応は設定で配る
- **方式の交渉がない**: TLS のように一覧から選ぶ段階がなく、ダウングレードの余地もない。代わりに、暗号を入れ替えるには版を上げるしかない
- **TCP では動かない**: WireGuard は TCP の上のトンネルを明示的にサポートせず、TCP に変換するのは別の難読化の層の仕事だとしています。DPI（通信の中身による識別）を避けることも目的にしていません（[WireGuard Known Limitations](https://www.wireguard.com/known-limitations/)）

### IPsec と IKEv2

IPsec は IP の層そのものを暗号化する標準で、鍵の取り決めには IKEv2（[RFC 7296](https://www.rfc-editor.org/rfc/rfc7296.html)）を使います。認証には証明書も事前共有鍵も使えます。データは ESP として運ばれ、NAT を越えるときは UDP の 4500 番に包みます（[RFC 3948](https://www.rfc-editor.org/rfc/rfc3948.html)）。UDP が塞がれた網のために、IKE と ESP を TCP で包む方式も標準化されていて、TCP の 4500 番が必須です。この RFC は、TCP の上で TCP を動かすことは勧めず、**UDP が塞がれているときだけ**使うよう推奨しています（[RFC 9329](https://www.rfc-editor.org/rfc/rfc9329.html)）。

### 並べる

| | OpenVPN | SSTP | OpenConnect / AnyConnect | WireGuard | IPsec（IKEv2） |
| --- | --- | --- | --- | --- | --- |
| 相手の確認 | TLS（証明書） | TLS（証明書）＋ PPP の認証 | TLS（証明書）＋ HTTP の認証 | Noise（公開鍵を設定で配る） | IKEv2（証明書か事前共有鍵） |
| データの運び方 | 独自の形式、UDP（TCP も可） | PPP を TLS に入れて TCP 443 | DTLS（UDP）、使えなければ TLS | UDP のみ | ESP（UDP 4500 に包むことも） |
| TCP の二重化 | TCP を選んだときだけ | 常に | DTLS が使えないときだけ | 起きない（TCP 非対応） | TCP で包んだときだけ |
| 443 番の TLS に紛れられるか | TCP 443 番で動かせば近い形になる | そのもの | そのもの | できない | できない（RFC 9329 は TLS 1.2 を併用する余地を残す） |
| 標準 | 実装が仕様 | Microsoft の公開仕様 | 期限切れの個人ドラフト | 論文と公開仕様 | IETF の RFC |

選ぶ基準は、おおむね次の 2 つの引っ張り合いです。

- **通りやすさ**: 制限の厳しい網から使うなら、443 番の TLS に見える SSTP や OpenConnect、TCP で動かした OpenVPN が通る。その代わり、TCP の二重化と、認証の前に HTTP を解釈する大きな入口を抱える
- **単純さと速さ**: 網を自分で選べるなら、UDP だけで交渉もない WireGuard は設定も攻撃面も小さい。IPsec は機器同士（拠点間）の接続で、相互接続性が求められるときに選ばれる

どれを選んでも、VPN が保証するのは**「この端末が、この網に入ってよい鍵を持っている」**ところまでです。入った後にどこへ届くかは、第 138 回で見た VPN とゼロトラストの議論に戻ります。

## 次回へ

この回で見た TLS は、どれも**IP の上で、つながった後に**使われていました。ところが、IP アドレスをもらう前、つまり Wi-Fi に参加してよいかを決める段階でも TLS は使われています。次の第 123 回では、802.1X と EAP-TLS のように IP が使えない段階で TLS を運ぶ方法、古い RADIUS を TLS で守る RadSec、時刻の問い合わせを守る NTS など、目立たない裏方を守っている TLS を見ていきます。

## まとめ

- TLS で包む単位は 3 段階ある。1 本の TCP（stunnel）、接続ごとに宛先を選べる TCP（HTTP CONNECT）、IP パケット（VPN）
- stunnel は TLS を知らないプログラムに TLS を足せるが、クライアント側の `verifyChain` の既定は `no`。`CAfile`、`verifyChain`、`checkHost` をそろえないと、偽のサーバに黙ってつながる。包まれたプログラムには検証の失敗の理由が届かない
- VPN を TCP の上の TLS で作ると、アプリの TCP が外側の TCP の上に載り、再送が二重になる。だから TLS を使う VPN の多くは、データを UDP で運ぶ道を持つ
- OpenVPN は TLS を**鍵の取り決め**にだけ使い、IP パケットは TLS とは別の鍵で、独自の形式で UDP に載せる。TLS のための確認応答と再送の層を、制御チャネルにだけ自前で持つ
- OpenVPN のクライアントは `remote-cert-tls server` と `verify-x509-name` で、同じ CA の別の証明書によるなりすましを防ぐ。`tls-auth` / `tls-crypt` は TLS の手前で鍵のないパケットを捨て、`tls-crypt-v2` はその鍵をクライアントごとに分ける
- SSTP は PPP を `SSTP_DUPLEX_POST` の終わらない要求の本体として HTTPS に流す。crypto binding で PPP の認証を TLS の接続に縛り付ける
- OpenConnect / AnyConnect は TLS で認証と設定を済ませ、TLS から導いた鍵で DTLS の通り道を開いてパケットを運ぶ。仕様は期限切れの個人ドラフト
- SSL VPN の機器は、認証の前に HTTP を解釈する、インターネットに面した入口であり、実際に悪用が繰り返されている
- WireGuard（Noise、UDP のみ、交渉なし）と IPsec（IKEv2、ESP）は TLS を使わない。通りやすさを取るか、単純さと速さを取るかで選ぶ
