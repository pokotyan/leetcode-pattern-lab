## malloc は OS ではない

第 22 回で、`malloc` はシステムコールではなくライブラリの関数だと書きました。OS から大きな領域をまとめてもらい、それを細かく切り分けて渡している、と。第 24 回では、もらった領域も触るまでは物理メモリが割り当てられないことを見ました。

この回は、その「切り分けて渡す」部分の中身です。

`malloc` がやっていることは、突き詰めると 2 つの帳簿付けです。

- 渡した領域がそれぞれ **何バイトだったか**（`free` はサイズを受け取らないので、自分で覚えておく必要がある）
- 返してもらった領域のうち **どこが空いているか**（次の `malloc` で再利用するため）

この帳簿をどこに、どういう形で持つかが、アロケータの設計のすべてです。ここでは Linux の標準である glibc の実装（ptmalloc）を中心に見ます。

## 返されたアドレスの手前

次のプログラムを Linux（glibc）で動かしてみます。

```c
void *a = malloc(24), *b = malloc(24);
printf("a=%p b=%p diff=%ld\n", a, b, (char *)b - (char *)a);
printf("hdr(a)=%#lx\n", ((size_t *)a)[-1]);   // 返されたアドレスの 8 バイト手前
```

```
a=0xa9182a0 b=0xa9182c0 diff=32
hdr(a)=0x21
```

24 バイトを 2 回頼んだのに、アドレスは **32 バイト**離れています。そして返されたアドレスのすぐ手前に、`0x21` という値が書かれています。

これが帳簿の 1 つ目です。glibc は、渡す領域の直前に **ヘッダ** を置き、そこにサイズを書きます。ヘッダとデータを合わせた単位を **チャンク** と呼びます。

```
            ヘッダ（8 バイト）         ユーザに渡す領域
          ┌──────────────────┬──────────────────────────┐
  チャンク │ サイズ 32 | フラグ │  24 バイト + 余り          │
          └──────────────────┴──────────────────────────┘
                              ↑
                         malloc が返すアドレス
```

**なぜ 32 か。** 24 バイトのデータにヘッダ 8 バイトを足すと 32 バイト。そしてチャンクは **16 バイト境界** に揃えられます。第 6 回で見たアラインメントの要求のうち最も厳しいもの（`long double` や SIMD 用の型）に合わせるためで、`malloc` が返すアドレスは、どんな型を置いても大丈夫なように揃っていなければなりません。

**なぜ 0x21 か。** サイズは必ず 16 の倍数なので、下位 4 ビットは常に 0 です。そこを **フラグ** に使っています。`0x21` は「サイズ 0x20（32）」に、最下位ビットの「直前のチャンクは使用中」という印が立ったものです。空いたビットを使い回すのは、第 1 回で見たビット演算の典型的な使い方です。

つまり、**小さい割り当てほど無駄が大きい**ということです。1 バイトを頼んでも、最小のチャンク（64 ビットでは 32 バイト）が使われます。小さなオブジェクトを大量に作るプログラムでは、この差が効いてきます。

## 大きさで経路が変わる

同じプログラムに、100KB と 200KB の割り当てを足して `strace` で見ます。

```
brk(NULL)                = 0xa918000
brk(0xa939000)           = 0xa939000        ← ヒープの上端を 132KB 伸ばす
mmap(NULL, 208896, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) = 0xffff8989d000
a=0xa9182a0
c=0xa9182e0              ← 100KB はヒープから
d=0xffff8989d010         ← 200KB は mmap で別の場所から
```

小さい割り当ては、第 22 回の `brk` で伸ばしたヒープから切り出されます。一方、200KB は **その割り当てのためだけに `mmap` が呼ばれ**、ヒープとはまったく別のアドレスに置かれています。

境目は **mmap しきい値** と呼ばれ、glibc の初期値は 128KiB です（[glibc マニュアル](https://www.sourceware.org/glibc/manual/latest/html_node/Malloc-Tunable-Parameters.html)）。ただし固定ではなく、しきい値より大きいブロックが解放されると、しきい値がそのサイズまで引き上げられます。「大きいものを確保しては解放する」パターンのプログラムで、毎回 `mmap` と `munmap` が走るのを避けるためです。

なぜ分けるのか。理由は **返し方** にあります。

- `mmap` で取った領域は、`free` の時点で `munmap` すればすぐ OS に返せる
- `brk` のヒープは **上端を動かすことでしか縮められない**。途中に空きができても、その上に使用中のチャンクが 1 つでもあれば返せない

大きな領域をヒープに混ぜると、解放しても OS に返せない穴になりやすい。だから大きいものは最初から別枠にしておきます。

## 空いた場所を覚えておく

`free` されたチャンクは、OS には返されずに **フリーリスト** へ入ります。次の `malloc` は、まずここから合うものを探します。

```c
free(a);
void *e = malloc(24);
printf("e=%p (a reused? %d)\n", e, e == a);
```

```
e=0xa9182a0 (a reused? 1)
```

解放した直後に同じ大きさを頼むと、**まったく同じアドレス**が返ってきます。

空いたチャンクは、ユーザが使っていた領域そのものに次の空きへのポインタを書き込み、リストとして繋ぎます。**空いている間は、中身をアロケータの帳簿として使う**わけです。別に帳簿用のメモリを用意しなくて済みます。

リストが 1 本だと、探すのに時間がかかります。そこで、**大きさごとに別々のリスト**を持ちます。

| 仕組み | 何をするか |
| --- | --- |
| **サイズクラス**（bin） | 32、48、64… と大きさの区分ごとにリストを分ける。頼まれた大きさの区分を見れば、探さずに見つかる |
| **結合**（coalescing） | 隣り合う空きチャンクを 1 つにまとめる。細切れのままだと大きい要求に応えられない |
| **分割**（splitting） | 大きい空きから必要な分だけ切り出し、残りを空きとして戻す |

ヘッダの「直前のチャンクは使用中」というフラグは、結合のためにあります。`free` のとき、前のチャンクが空いていれば 1 つにまとめられます。

## スレッドごとに持つ

複数のスレッドが同時に `malloc` を呼ぶと、帳簿は 1 つなので、第 37 回のロックが必要になります。`malloc` はプログラムの中で最も頻繁に呼ばれる関数の 1 つなので、ここが取り合いになると全体が遅くなります。

glibc は 2 段の対策を取っています。

**tcache。** スレッドごとに、小さいチャンクを少数だけ溜めておく箱です。glibc 2.26 から既定で有効です（[glibc マニュアル](https://www.sourceware.org/glibc/manual/latest/html_node/Memory-Allocation-Tunables.html)）。自分の箱から取るだけなので、ロックが要りません。さきほど同じアドレスが返ってきたのも、`free` したチャンクが tcache に入り、次の `malloc` がそれを最初に取ったからです。

**arena。** ヒープそのものを複数用意し、スレッドを振り分けます。64 ビットでは、既定で CPU コア数の 8 倍まで増えます（[glibc マニュアル](https://www.sourceware.org/glibc/manual/latest/html_node/Memory-Allocation-Tunables.html)）。

<Callout type="warn" title="arena がメモリを食う">
  arena ごとに空き領域を抱えるので、スレッドが多いプログラムでは、
  **実際に使っている量よりずっと多くのメモリ**を確保したままになることがあります。
  コンテナのメモリ上限（第 76 回）に当たって初めて気づく、という形で表に出がちです。
  環境変数 `MALLOC_ARENA_MAX=2` のように arena の数を絞ると、速度と引き換えに使用量が減ります。
</Callout>

## free しても減らない

「メモリを解放したのに、プロセスのメモリ使用量（RSS）が減らない」というのは、よくある疑問です。ここまでの話で説明がつきます。

- `free` はチャンクをフリーリストに戻すだけで、OS には返さない
- ヒープは上端からしか縮められない。途中の空きは返せない
- arena や tcache も空きを抱えている

使用中と空きが入り混じり、空きの合計は十分あるのに、**大きな連続した領域が取れない**、あるいは **OS に返せない** 状態を **断片化** と呼びます。

| 種類 | 何が起きているか |
| --- | --- |
| **内部断片化** | チャンクの中の使われていない部分。24 バイトの要求に 32 バイトを使う、など |
| **外部断片化** | チャンクとチャンクの間の、小さすぎて使えない空き |

長時間動くサーバで、負荷は一定なのにメモリだけがじわじわ増える場合、リークではなく断片化であることも少なくありません。glibc の `malloc_trim` は、ヒープの途中の空きページも `madvise` で OS に返そうとします。

## アロケータは差し替えられる

`malloc` はただのライブラリ関数なので、別の実装に取り替えられます。第 29 回で見た動的リンクの仕組みを使えば、再コンパイルすら要りません。

```bash
LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2 ./server
```

`LD_PRELOAD` で指定したライブラリは、libc より先に探されます。同じ名前の `malloc` があれば、そちらが使われます。

代表的な実装は、どれも **サイズクラス** と **スレッドごとのキャッシュ** を軸にしています。

| 実装 | 出自 | 特徴 |
| --- | --- | --- |
| **ptmalloc** | glibc の標準 | チャンクの直前にヘッダ。汎用 |
| **jemalloc** | FreeBSD、のちに Meta | ページ単位の領域をサイズクラスごとに分け、断片化に強い |
| **tcmalloc** | Google | スレッドごとのキャッシュを先駆けて導入 |
| **mimalloc** | Microsoft | ページごとに空きリストを持ち、局所性を重視 |

言語のランタイムが自前のアロケータを持つことも多く、たとえば Go のランタイムのアロケータは tcmalloc の設計を下敷きにしています。

<Callout type="tip" title="ヘッダを持たない設計">
  jemalloc や mimalloc の多くの割り当ては、チャンクの手前にヘッダを置きません。
  **同じサイズクラスのものだけを 1 つのページにまとめ**、
  「このページは 32 バイト用」とページの側に書いておきます。
  アドレスからページが分かれば、サイズも分かります。
  小さい割り当ての無駄が減り、同じ大きさのものが隣に並ぶので第 3 章のキャッシュにも優しくなります。
</Callout>

## 帳簿が壊れると何が起きるか

glibc のアロケータは、帳簿の一部を **ユーザのデータのすぐ隣** に置いています。空きチャンクでは、ユーザが使っていた領域にポインタを書いています。ここから、C のメモリバグが厄介な理由が見えてきます。

**ヒープのバッファオーバーフロー。** 確保した領域の終わりを越えて書くと、**次のチャンクのヘッダ**を書き潰します。その場ではクラッシュせず、しばらく後の `malloc` や `free` が壊れた帳簿を読んで落ちます。原因と症状が離れているので、追うのが難しくなります。

**use-after-free。** 解放した領域に書き込むと、そこはもう **フリーリストのポインタ** です。次の `malloc` が、その書き換えられたポインタを辿ります。攻撃者が値を選べれば、任意の場所を `malloc` に返させることができ、これが多くの攻撃の足がかりになってきました。

**double free。** 同じチャンクを 2 回 `free` すると、フリーリストに同じチャンクが 2 回入ります。すると、後の 2 回の `malloc` が **同じ領域を別々の持ち主に渡します**。

最近の glibc は、よくある壊れ方を検出するとその場で止めます。

```
free(): double free detected in tcache 2
Aborted
```

終了コードは 134 です。シグナルで死んだプロセスの終了コードは、シェルでは 128 にシグナル番号を足した値になり、ここでは SIGABRT（6）で止められたことを表しています。シグナルそのものは第 46 回で見たとおりです。

ただし、検出できるのはごく一部です。確実に見つけたいなら、第 23 回の AddressSanitizer を使います。ASan は解放した領域をすぐには再利用せず、アクセスを監視することで、これらを発生した場所で捕まえます。

## まとめ

- `malloc` の仕事は帳簿付け。渡したサイズと、空いている場所を覚えておく
- glibc はデータの直前にヘッダを置く。24 バイトの要求は、ヘッダと 16 バイト境界で 32 バイトになる
- 小さい割り当ては `brk` のヒープから、大きい割り当て（初期値 128KiB 以上）は `mmap` で別枠から
- 空きはサイズクラスごとのフリーリストで管理し、隣り合う空きは結合する
- スレッドの取り合いを避けるため、tcache と arena を持つ。その分メモリを多く抱える
- `free` しても OS には返らないことが多い。断片化で RSS が減らない
- `LD_PRELOAD` で jemalloc や mimalloc に差し替えられる
- 帳簿がデータの隣にあるので、オーバーフロー、use-after-free、double free は帳簿を壊す

ここまでは、いつ `free` するかをプログラマが決める世界でした。次は、それをランタイムに任せるガベージコレクションです。
