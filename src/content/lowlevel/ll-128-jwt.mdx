## その文字列は何を保証しているのか

`eyJ` で始まり、ピリオドで 3 つに区切られた長い文字列。API の `Authorization: Bearer` ヘッダや、OpenID Connect の ID トークンとして毎日のように目にします。そして「JWT で認証しています」という言い方もよく聞きます。

しかし JWT は、**「JSON で書いた主張（クレーム）の集まりに、署名か暗号化を掛けて URL に載る形にしたもの」という形式**にすぎません。誰が作ったか、誰に向けたものか、いつまで有効か、を**確かめる手順は受け取った側に任されています**。手順を 1 つ飛ばせば、形式としては正しい偽物がそのまま通ります。

この回では、JWT を手で割って中身を読み、署名がどこに掛かっているか、受け取った側は何をどの順で確かめるべきか、過去にどこで壊れたか、を順に見ます。最後に、ブラウザでトークンをどこに置くかという、よく議論になる問題を脅威モデルから分解します。

## JOSE: 5 つの仕様の分担

JWT は単独の仕様ではなく、**JOSE**（JSON Object Signing and Encryption）と呼ばれる一群の仕様の上に立っています。

| 仕様 | 名前 | 決めていること |
| --- | --- | --- |
| [RFC 7515](https://www.rfc-editor.org/rfc/rfc7515.html) | JWS（JSON Web Signature） | 任意のバイト列に**署名か MAC** を付ける形式 |
| [RFC 7516](https://www.rfc-editor.org/rfc/rfc7516.html) | JWE（JSON Web Encryption） | 任意のバイト列を**暗号化**する形式 |
| [RFC 7517](https://www.rfc-editor.org/rfc/rfc7517.html) | JWK（JSON Web Key） | 鍵を JSON で表す形式と、その集まり JWKS |
| [RFC 7518](https://www.rfc-editor.org/rfc/rfc7518.html) | JWA（JSON Web Algorithms） | `ES256` や `HS256` といったアルゴリズムの名前と中身 |
| [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html) | JWT（JSON Web Token） | JWS か JWE の中身を「クレームの JSON」にしたもの |

つまり**JWT は JWS か JWE の特別な使い方**です。実際に出回っている JWT のほとんどは JWS、つまり**署名されているだけ**のものです。JWK は第 108 回で鍵の形式の 1 つとして見ました。この回では、その JWK が「公開鍵を配る」という役目で働くところを見ます。

## 3 つに割って読む

JWS には JSON で表す形式もありますが、JWT で使うのは**コンパクト形式**と呼ばれる 1 行の形です（[RFC 7515 7.1](https://www.rfc-editor.org/rfc/rfc7515.html#section-7.1)）。

```
BASE64URL(ヘッダ) . BASE64URL(ペイロード) . BASE64URL(署名)
```

**Base64URL** は、Base64 の `+` と `/` を URL で意味を持たない `-` と `_` に置き換え、末尾の `=` を取り除いたものです（[RFC 7515 2](https://www.rfc-editor.org/rfc/rfc7515.html#section-2)）。Base64 は 3 バイトを 6 ビットずつ 4 文字に写す**符号化**であって、鍵も何も使いません。誰でも元に戻せます。

手元で作った ES256 の JWT（作り方は後の「手元で確かめる」で見ます）を、シェルだけで戻してみます。`=` を補い、`-_` を `+/` に戻して、普通の `base64 -d` に渡すだけです。

```bash
b64url_decode() {
  local s=$(printf %s "$1" | tr '_-' '/+')
  while [ $(( ${#s} % 4 )) -ne 0 ]; do s="$s="; done
  printf %s "$s" | base64 -d
}
T=$(cat token.txt)
b64url_decode "$(echo $T | cut -d. -f1)"
b64url_decode "$(echo $T | cut -d. -f2)"
b64url_decode "$(echo $T | cut -d. -f3)" | xxd | head -2
```

```
{"alg":"ES256","typ":"JWT","kid":"g8AALhxsWTnQ7IglMEmHgeboVP6uqcC5XpgJnlfoVXA"}
{"iss":"https://idp.example","sub":"user-42","aud":"https://api.example","iat":1790592365,"nbf":1790592365,"exp":1790592665,"jti":"a1b2c3","role":"viewer"}
00000000: 3212 23af 28a5 f172 493c c8b3 19af b519  2.#.(..rI<......
00000010: f912 636b 03fc de0b b9f3 1e45 1a41 f0d2  ..ck.......E.A..
```

1 つめが**ヘッダ**（JOSE ヘッダ）で、どのアルゴリズムで、どの鍵で署名したかを書きます。2 つめが**ペイロード**（クレームの集まり）です。3 つめは署名の生のバイト列で、ES256 なら 64 バイトです。

<Callout type="warn" title="よくある誤解: 署名されているから中身は見えない">
  上のとおり、**JWS のペイロードは鍵なしで誰でも読めます**。署名が保証するのは「この鍵の持ち主が作ってから書き換えられていない」ことだけで（第 107 回）、機密性は何も約束しません（第 103 回の 4 つの性質の区別）。
  `eyJ` という見慣れない文字列が暗号文のように見えるのが誤解の元です。`eyJ` は `{"` を Base64 にしたものにすぎません。
  したがって、**パスワード、個人情報、内部のシステム構成などをペイロードに入れてはいけません**。ブラウザの開発者ツール、プロキシのログ、エラー報告のサービスなど、トークンが通る場所すべてで読まれます。
  中身も隠したいなら JWE を使いますが、それなら「そもそもトークンに書く必要があるのか」を先に考えるほうが多くの場合は正解です。
</Callout>

## 署名はどこに掛かっているのか

署名の対象（**署名入力**）は、JSON そのものではなく、**Base64URL にした後のヘッダとペイロードをピリオドでつないだ ASCII 文字列**です（[RFC 7515 5.1](https://www.rfc-editor.org/rfc/rfc7515.html#section-5.1)）。

```
署名入力 = "eyJhbGciOi...In0" + "." + "eyJpc3Mi...In0"
署名     = ES256(秘密鍵, SHA-256(署名入力))
```

こうしておくと、検証する側は JSON を解釈し直さずに、受け取った文字列のまま署名を確かめられます。JSON はキーの順序や空白の入れ方が自由なので、「同じ意味の JSON」を毎回同じバイト列に直す正規化は難しいのです。**ヘッダも署名の範囲に入っている**ことにも注意してください。`alg` や `kid` を書き換えれば、署名は合わなくなります（ただし後で見るとおり、検証する側がヘッダを信じて鍵やアルゴリズムを選んでしまうと、この守りは意味を失います）。

もう 1 つ、細かいが実務で引っかかる点があります。第 107 回で見た ECDSA の署名は、ライブラリの多くが **DER**（ASN.1）で表した `r` と `s` の組を返します。JWS はこれを使わず、**`r` と `s` をそれぞれ 32 バイトに揃えて並べた 64 バイト**を署名とします（[RFC 7518 3.4](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.4)）。手元で作ったときの長さはこうでした。

```
DER signature bytes: 71  JWS signature bytes: 64
```

汎用の暗号ライブラリで JWT を自作すると、DER のまま入れてしまい、他の実装で検証できないという事故が起きます。

## 登録済みクレーム

ペイロードには好きなクレームを書けますが、意味が決まっている名前が 7 つあります（[RFC 7519 4.1](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1)）。どれも**任意**で、何を必須にするかは JWT を使う側の仕様（OpenID Connect など）が決めます。

| クレーム | 意味 | 受け取った側が確かめること |
| --- | --- | --- |
| `iss` | 発行者 | 自分が信頼する発行者か。**その発行者の鍵で署名されているか** |
| `sub` | 主体（誰についてのトークンか） | 発行者の中で一意な識別子。`iss` と組にして使う |
| `aud` | 受け取り手 | **自分が含まれているか**。含まれていなければ拒否しなければならない |
| `exp` | 有効期限（UNIX 時刻の秒） | 現在時刻がこれより前か |
| `nbf` | これより前は無効 | 現在時刻がこれ以降か |
| `iat` | 発行時刻 | 古すぎないか（使う側の方針次第） |
| `jti` | トークンの一意な ID | 使い回し（リプレイ）の検出に使える |

`aud` については RFC 7519 が「処理する側が `aud` の値の中に自分を見つけられなければ、その JWT は**拒否しなければならない**（MUST）」と書いています（[4.1.3](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.3)）。`exp` については、時計のずれを見込んで「**通常は数分以内**の小さな猶予」を認めてよいとしています（[4.1.4](https://www.rfc-editor.org/rfc/rfc7519.html#section-4.1.4)）。時計がどうずれるかは第 158 回で見ます。

## 検証の手順

受け取った側がすることを順に並べます。[RFC 7519 7.2](https://www.rfc-editor.org/rfc/rfc7519.html#section-7.2) の形式上の手順に、[RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html)（JWT の現在の最良の慣行、BCP 225）の勧めを重ねたものです。

1. **受け付けるアルゴリズムを、自分の側で先に決めておく**。ヘッダの `alg` はそれと照らし合わせるだけで、選ぶためには使わない。RFC 8725 は「ライブラリは、呼び出し側が指定したアルゴリズムだけを使わなければならない」としています（[3.1](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.1)）
2. **鍵を、自分が信頼する経路で手に入れたものの中から選ぶ**。`kid` は「どれか」を指す目印として使い、鍵そのものをトークンから受け取らない（後述）
3. **署名を確かめる**。ここまで済むまで、ペイロードのどの値も信じない
4. **`iss` を確かめ、その鍵が本当にその発行者のものかを確かめる**（[RFC 8725 3.8](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.8)）。複数の発行者を受け付けるときに特に効く
5. **`aud` に自分が含まれているかを確かめる**（[RFC 8725 3.9](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.9)）
6. **`exp` と `nbf` を、小さな猶予を付けて確かめる**
7. 用途が混ざりうるなら **`typ` で種類を確かめる**。たとえばアクセストークン用の JWT には `typ: at+jwt` を付ける決まりがあります（[RFC 9068 2.1](https://www.rfc-editor.org/rfc/rfc9068.html#section-2.1)）。ID トークンをアクセストークンとして受け取ってしまう取り違えを防ぐためです（[RFC 8725 3.11](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.11)）
8. ここまで通って初めて、`sub` やその他のクレームを使って**何を許すか**を決める。これは JWT の仕事ではなく、第 132 回で見る認可の仕事です

手順 1 から 7 は、ほぼすべてライブラリが引き受けてくれます。ただし**何を期待するか（アルゴリズム、発行者、受け取り手）を渡すのは呼び出す側**です。渡さなければ確かめられません。

## 手元で確かめる

Python の cryptography（50.0）だけで ES256 の JWT を組み立て、検証は PyJWT（2.15）で行います。どちらも作業ディレクトリの venv に入れました。まず P-256 の鍵を作り、公開鍵を JWK にして、RFC 7638 の thumbprint（後述）を `kid` にします。

```python
key = ec.generate_private_key(ec.SECP256R1())
nums = key.public_key().public_numbers()
jwk = {"crv": "P-256", "kty": "EC",
       "x": b64url(nums.x.to_bytes(32, "big")), "y": b64url(nums.y.to_bytes(32, "big"))}
kid = b64url(hashlib.sha256(json.dumps(jwk, separators=(",", ":"), sort_keys=True).encode()).digest())

header  = {"alg": "ES256", "typ": "JWT", "kid": kid}
payload = {"iss": "https://idp.example", "sub": "user-42", "aud": "https://api.example",
           "iat": now, "nbf": now, "exp": now + 300, "jti": "a1b2c3", "role": "viewer"}
signing_input = b64url(json_bytes(header)) + "." + b64url(json_bytes(payload))
r, s = decode_dss_signature(key.sign(signing_input.encode(), ec.ECDSA(hashes.SHA256())))
token = signing_input + "." + b64url(r.to_bytes(32, "big") + s.to_bytes(32, "big"))
```

できたトークンは 401 文字でした。これを、アルゴリズムを `ES256` に固定し、`aud` と `iss` を指定し、猶予を 30 秒にして検証します。ペイロードの `role` を書き換えたもの、別の API として検証したもの、期限切れのもの、`alg: none` にしたものも試します。

```python
jwt.decode(tok, key, algorithms=["ES256"], audience="https://api.example",
           issuer="https://idp.example", leeway=30)
```

```
正しいトークン                 OK   sub=user-42 role=viewer
role を書き換え                FAIL InvalidSignatureError: Signature verification failed
aud が違う API で検証          FAIL InvalidAudienceError: Audience doesn't match
exp が 10 秒前（許容 30 秒）   OK   sub=user-42 role=viewer
exp が 60 秒前（許容 30 秒）   FAIL ExpiredSignatureError: Signature has expired
alg: none                      FAIL InvalidAlgorithmError: The specified alg value is not allowed
algorithms を渡さない          FAIL DecodeError: It is required that you pass in a value for the "algorithms" argument when calling decode().
```

`role` の書き換えは、ペイロードが 1 文字でも変われば署名入力が変わるので失敗します。`aud` 違いは、**署名は正しい**のに拒否されています。同じ発行者が別の API 向けに出した正しいトークンを、こちらで使わせないためです。最後の行のとおり、PyJWT は 2.0 からアルゴリズムの指定を必須にしています。手順 1 をライブラリが強制している例です。

## 有名な壊れ方

2015 年、Tim McLean は複数の言語の主要な JWT ライブラリに、検証を素通りさせる 2 種類の欠陥を報告しました（[Auth0 のブログ](https://auth0.com/blog/critical-vulnerabilities-in-json-web-token-libraries/)）。どちらも、**トークン自身が書いたヘッダを信じて検証の方法を決めた**ことが原因です。

### alg: none

JWS には、署名なしを表す `none` というアルゴリズムが定義されています（[RFC 7518 3.6](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.6)）。署名の部分は空文字列です。

```
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJpc3MiOi...In0.
```

ヘッダの `alg` を見て検証の関数を選ぶライブラリは、これを受け取ると「署名なしなので検証すべきものはない」として成功を返していました。**攻撃者は好きなペイロードを書いて、署名なしで送るだけ**です。RFC 8725 は、`none` は JWT が別の手段で暗号的に守られている場合にだけ使ってよいとしています（[3.2](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.2)）。

### RS256 と HS256 の取り違え

もう 1 つはもっと巧妙です。サーバが RS256 や ES256（公開鍵で検証する）を使っているとき、攻撃者はヘッダを `HS256`（共通鍵の HMAC、第 104 回）に書き換え、**サーバの公開鍵そのものを HMAC の鍵として**ペイロードに MAC を付けます。公開鍵は誰でも入手できます。

検証する側が「`alg` を見て、設定された鍵で検証する」だけだと、設定された鍵（公開鍵の PEM のバイト列）を HMAC の鍵として MAC を計算し、一致してしまいます（[RFC 8725 2.1](https://www.rfc-editor.org/rfc/rfc8725.html#section-2.1)）。手元で、ヘッダの `alg` を信じる悪い検証を 15 行ほどで書いて試しました。

```
悪い検証: True
PyJWT: InvalidKeyError The specified key is an asymmetric key or x509 certificate and should not be used as an HMAC secret.
PyJWT (ES256 に固定): InvalidAlgorithmError The specified alg value is not allowed
```

PyJWT は、HS256 を許しても**公開鍵を HMAC の鍵にすることを拒む**よう作られていますが、根本の対策は 3 行目のとおりアルゴリズムを固定することです。第 107 回で見たとおり、署名と MAC は「誰が作れるか」がまったく違う道具です。**その 2 つを 1 つの `alg` 欄で切り替えられる**ことが、この事故の構造です。

<Callout type="warn" title="よくある誤解: 署名を検証しているから大丈夫">
  上の 2 つは、どちらも「署名の検証」はしていました。問題は**何で検証するかをトークンに決めさせた**ことです。
  署名が守るのは、正しい鍵で正しいアルゴリズムを使って確かめた場合だけです。
  鍵、アルゴリズム、発行者、受け取り手は、**すべて検証する側があらかじめ知っている値**と突き合わせる。トークンに書かれた値は、突き合わせる相手であって、根拠ではありません。
</Callout>

### ヘッダから鍵を取ってくる: kid、jku、x5u、jwk

同じ構造の問題は、鍵を指すヘッダにもあります（[RFC 7515 4.1](https://www.rfc-editor.org/rfc/rfc7515.html#section-4.1)）。

| ヘッダ | 中身 | 信じたときに起きること |
| --- | --- | --- |
| `kid` | 鍵の ID（任意の文字列） | ファイルのパスや SQL にそのまま埋め込むと、パスの注入や SQL の注入になる |
| `jku` | JWKS の URL | 攻撃者が自分のサーバの JWKS を指し、自分の鍵で署名したトークンを通す。サーバから任意の URL へ取りに行かせる SSRF にもなる |
| `x5u` | 証明書チェーンの URL | `jku` と同じ |
| `jwk` | 公開鍵そのものを埋め込む | 攻撃者が自分の公開鍵を埋め込み、それで検証させる |

RFC 8725 は `kid` による注入と、`jku`/`x5u` による SSRF を名指しで挙げています（[3.10](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.10)）。OWASP の JWT Cheat Sheet も、検証の鍵は**トークンの外で確立した信頼**（固定した鍵や、設定した `jwks_uri`）から得るよう勧めています（[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)）。`kid` は使ってよいのですが、**信頼できる JWKS の中から 1 つを選ぶための目印**としてだけ使います。

<Callout type="note" title="RFC 8725 の改訂">
  執筆時点（2026 年 9 月）で、RFC 8725 を置き換える改訂版 draft-ietf-oauth-rfc8725bis が第 10 版まで進み、RFC 化の手前の段階にあります（[IETF Datatracker](https://datatracker.ietf.org/doc/draft-ietf-oauth-rfc8725bis/)）。
  暗号化と署名の取り違え、JWE の圧縮や PBES2 の反復回数による資源の枯渇などへの対策が加わっています。
</Callout>

## JWKS: 公開鍵をどう配るか

署名を公開鍵で検証するなら、受け取る側は発行者の公開鍵を知っていなければなりません。第 107 回で見たとおり、**署名が保証するのは「この鍵で署名された」ことだけ**で、その鍵が誰のものかは別の仕組みが要ります。TLS では証明書でした（第 110 回）。JWT では多くの場合、発行者が **JWKS**（JWK Set）を HTTPS の URL で公開します。

```json
{
  "keys": [
    {
      "crv": "P-256", "kty": "EC", "alg": "ES256", "use": "sig",
      "kid": "g8AALhxsWTnQ7IglMEmHgeboVP6uqcC5XpgJnlfoVXA",
      "x": "MtOO16DhYjUfHZ1PNCRph5iFexGEWe7OF6x9ohG_SNA",
      "y": "LvAhmIsoVRaYmoHaTLKw0RbDc1CALJxrxfJrHVRoaiw"
    }
  ]
}
```

ここで**信頼の根拠は TLS に移っています**。JWKS の URL は受け取る側の設定に書いておき（OpenID Connect なら Discovery 文書の `jwks_uri`、第 130 回）、その URL の TLS 証明書（第 17 章）で「本物の発行者のサーバから取った」ことを確かめます。

`kid` の値には何を使ってもよいのですが、上では **JWK Thumbprint**（[RFC 7638](https://www.rfc-editor.org/rfc/rfc7638.html)）を使いました。鍵の必須の要素だけを、辞書順に並べ、空白なしの JSON にして SHA-256 を取ったものです。同じ鍵からは誰が計算しても同じ値になるので、第 108 回で見た「鍵がペアかどうか」を確かめる材料にもなります。

鍵を入れ替える（ローテーションする）ときは、順番が大事です。

```
1. 新しい鍵を JWKS に足す（まだ署名には使わない）
2. 受け取る側のキャッシュが入れ替わるのを待つ（キャッシュの寿命以上）
3. 新しい鍵で署名し始める
4. 古い鍵で署名したトークンがすべて期限切れになるのを待つ
5. 古い鍵を JWKS から外す
```

受け取る側は JWKS をキャッシュします。知らない `kid` が来たら取り直すのが普通ですが、**取り直しの回数は制限します**。でたらめな `kid` を大量に送られると、発行者のサーバへの問い合わせを代わりに増やしてしまうからです。手順 1 と 3 の順を逆にすると、キャッシュの古い受け取り側がすべて検証に失敗します。この事故は第 136 回と第 139 回でもう一度見ます。

## JWT をセッションの代わりにしてよいか

第 127 回で、サーバ側のセッション（ID だけを渡し、状態はサーバに置く）と、自己完結型のトークン（状態をトークンに書いて署名する）を比べました。JWT は後者の代表です。

| 観点 | サーバ側セッション | JWT をセッションに使う |
| --- | --- | --- |
| 検証に要るもの | 保存先への問い合わせ | 公開鍵だけ（問い合わせ不要） |
| ログアウト、強制的な無効化 | 保存先から消せば即座に効く | **期限まで有効なまま**。止めるには拒否リストが要る |
| 権限の変更 | 次のリクエストから反映 | トークンを出し直すまで古い権限のまま |
| 大きさ | 数十バイトの ID | 数百バイト〜数 KB。毎回送る |
| 中身の見え方 | 利用者からは見えない | 誰でも読める |

問い合わせなしで検証できるのは、サービスが多数あり、発行者と受け取り手が別の組織やシステムであるときに大きな利点です。ここに JWT の本来の居場所があります。1 つのアプリが自分で発行して自分で受け取るだけなら、その利点はほとんど活きず、**失効できない**という弱点だけが残ります。

<Callout type="warn" title="よくある誤解: JWT はステートレスだからスケールしてセキュア">
  JWT をセッションに使って無効化もしたくなると、「無効にしたトークンの一覧」をどこかに持つことになります。
  毎回その一覧を引くなら、それはサーバ側のセッションと同じ問い合わせで、ステートレスの利点はなくなります。OWASP も同じ指摘をしています（[JWT Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)）。
  実務で落ち着きやすい形は、**寿命の短い JWT（数分）＋失効できるリフレッシュトークンやサーバ側のセッション**の組み合わせです。
  JWT は「認証方式」ではなく、認証の結果を運ぶための**形式**です。どう認証したか（第 126 回）、何を許すか（第 132 回）は、JWT の外で決まります。
</Callout>

## トークンをブラウザのどこに置くか

「JWT は localStorage に置くな」という助言はよく聞きます。結論だけが独り歩きしがちなので、ここでは**攻撃者が何をできるか**から分解します。以後の回（第 131 回の DPoP と BFF、第 138 回の構成の型）は、この節の整理を前提にします。

### XSS が起きたら攻撃者は何ができるか

置き場所の議論で想定する攻撃は、ほぼ **XSS**（攻撃者のスクリプトが、正規のページと同じオリジンで動くこと。第 86 回）です。OAuth 2.0 for Browser-Based Applications（[RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html)、2026 年 8 月に BCP 212 として発行）は、そのとき攻撃者ができることを 4 つに分けています（[5.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-5.1)）。

| 攻撃 | 何をするか | 置き場所で防げるか |
| --- | --- | --- |
| 1 回の窃取（5.1.1） | その時点のトークンを読んで外へ送る | JavaScript から読めない場所なら防げる |
| 継続的な窃取（5.1.2） | 新しいトークンが出るたびに外へ送る | 同上 |
| 新しいトークンの取得（5.1.3） | 利用者の IdP とのセッションを使い、自分で認可の流れを始めて新しいトークンを得る | **防げない**。どこに置いたかと無関係 |
| 利用者のブラウザ経由の代理（5.1.4） | 盗まずに、そのページの中から API を呼ぶ | **防げない** |

5.1.4 は「ブラウザが自分の Cookie やトークンをリクエストに付けるので、攻撃者はトークンを手に入れる必要すらない」と書いています。つまり**置き場所で左右できるのは「持ち出せるか」だけ**で、「その場で悪用されるか」は変えられません。

持ち出しを防ぐ価値は、**攻撃者がトークンを使える場所と期間**にあります。持ち出されたトークンは、攻撃者の手元から、利用者がページを閉じた後も期限まで使えます。リフレッシュトークンなら、さらに長く使えます。持ち出せなければ、攻撃はその利用者がページを開いている間、そのブラウザの中からに限られます。

### 置き場所の比較

| 置き場所 | XSS で読んで持ち出せるか | XSS でその場で使えるか | CSRF の対策 | リロード、タブ間 | サブドメインとの共有 |
| --- | --- | --- | --- | --- | --- |
| localStorage | 読める | 使える | 不要（自動では送られない） | 残る。同じオリジンの全タブで共有 | しない（オリジン単位） |
| sessionStorage | 読める | 使える | 不要 | リロードでは残る。タブごと | しない |
| IndexedDB | 読める | 使える | 不要 | 残る。全タブで共有 | しない |
| JavaScript の変数、クロージャ | 難しくなるが、`fetch` などを先に差し替えられると送る瞬間に横取りされる | 使える | 不要 | リロードで消える。タブごと | しない |
| Web Worker の中のメモリ | ページ側からは直接読めない | Worker に頼めば使える | 不要 | リロードで消える | しない |
| HttpOnly Cookie | 読めない | 使える（ブラウザが自動で付ける） | **必要** | 期限まで残る。全タブで共有 | `Domain` 属性を付けると共有される |
| BFF（トークンはサーバ側、ブラウザはセッション Cookie だけ） | ブラウザにトークンがない | BFF 経由で使える | **必要** | セッション Cookie 次第 | `__Host-` 接頭辞で閉じられる |

表の「その場で使えるか」の列がすべて「使える」になっていることが、この節の要点です。**XSS を防げていなければ、どこに置いても悪用はされます**。置き場所の選択は、その上で「盗まれたトークンが外で使える量」を減らすためのものです。

OWASP の HTML5 Security Cheat Sheet が「セッションの識別子を localStorage に置かない。データは常に JavaScript から読めるからだ」と書き、HttpOnly の Cookie を代わりに挙げているのも、この「持ち出し」の観点です（[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html)）。RFC 10017 も、localStorage のようにどこからでも触れる場所は、Web Worker のように隔離された場所より悪意あるスクリプトから触りやすい、としています（[8](https://www.rfc-editor.org/rfc/rfc10017.html#section-8)）。

<Callout type="warn" title="よくある誤解: HttpOnly Cookie なら XSS に安全">
  半分だけ正しい言い方です。HttpOnly の Cookie は JavaScript から**読めない**ので、持ち出しは防げます。
  しかし XSS のスクリプトは、同じオリジンから `fetch('/api/transfer', { credentials: 'include' })` を送れます。ブラウザは Cookie を自動で付けるので、**リクエストは正規のものとして通ります**。
  守れるのは「攻撃者の手元に渡らない」ことだけで、ページを開いている間の悪用は止まりません。
</Callout>

<Callout type="warn" title="よくある誤解: localStorage は危険、Cookie は安全の二択">
  Cookie に移すと、今度は**ブラウザが勝手に送る**ことによる CSRF（第 127 回）の対策が要ります。localStorage のトークンは自分で付けない限り送られないので、CSRF は起きません。
  つまり 2 つは「危険と安全」ではなく、**持ち出しに弱いか、勝手に送られることに弱いか**の違いです。どちらを選んでも、XSS そのものを防ぐこと（出力のエスケープ、Content Security Policy）が先にあります。
</Callout>

### Cookie に JWT を入れるなら

- **大きさ**: ブラウザが保証する 1 つの Cookie の大きさは、名前と値と属性の合計で少なくとも 4,096 バイトです（[RFC 6265 6.1](https://www.rfc-editor.org/rfc/rfc6265.html#section-6.1)）。手元の最小の JWT でも 401 文字で、クレームやグループを足すとすぐ数 KB になります。超えると黙って捨てられることがあり、分割する実装も出てきます
- **属性**: `Secure`、`HttpOnly`、`SameSite`、`Domain` を付けない `__Host-` 接頭辞（第 127 回）。RFC 10017 は BFF の Cookie について、`Secure` と `HttpOnly` を必須、`SameSite=Strict` と接頭辞を推奨としています（[6.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1)）
- **CSRF**: `SameSite` だけに頼らず、状態を変える API には CSRF トークンや独自ヘッダの要求を組み合わせる（第 127 回）

### よく使われる折衷と、その限界

よく勧められるのは次の組み合わせです。

```
アクセストークン     寿命は数分。JavaScript のメモリ（または Web Worker）に置く
リフレッシュトークン HttpOnly Cookie。Path をトークンの更新用のエンドポイントに絞る
                     使うたびに新しいものに取り替える（ローテーション）
```

持ち出されうるのは寿命の短いアクセストークンだけになり、リフレッシュトークンは読めず、他の API への通信にも付きません。ローテーションしておけば、盗まれたリフレッシュトークンが 2 回使われたことを発行者が検知できます（第 129 回）。

ただし限界もはっきりしています。XSS のスクリプトは**更新用のエンドポイントを自分で呼べば**、Cookie が付いて新しいアクセストークンを受け取れます。これは表の 5.1.3 と同じ構図で、置き場所では防げません。この折衷が縮めるのは「外で使える期間」であって、攻撃の入口ではありません。

### 推奨の順番

RFC 10017 は、ブラウザで動くアプリの構成を 3 つ挙げ、この順に安全性が下がるとしています（[6](https://www.rfc-editor.org/rfc/rfc10017.html#section-6)）。

1. **BFF**（[6.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1)）: OAuth の処理もトークンもすべてサーバ側。ブラウザは BFF とのセッション Cookie だけを持つ。業務用や個人データを扱うアプリには「強く推奨」
2. **トークン仲介バックエンド**（[6.2](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.2)）: トークンの取得はサーバ側で行い、アクセストークンだけをブラウザに渡して API を直接呼ぶ
3. **ブラウザだけの OAuth クライアント**（[6.3](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.3)）: すべてをブラウザの中で行う

BFF でも、悪意あるスクリプトは同じオリジンから BFF へリクエストを送れる、と RFC 自身が書いています（6.1 の安全性の考察）。BFF が消すのは「持ち出し」で、「代理」ではありません。上の表と同じ結論です。

### 盗まれても使えなくする方向

置き場所で持ち出しを防ぐ代わりに、**持ち出されたトークンを別の場所では使えなくする**という考え方もあります。DPoP（[RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html)）は、トークンを利用者の手元の鍵に結び付け、リクエストのたびにその鍵で署名を付けさせます。WebCrypto で `extractable: false`（取り出し不可）の鍵を作り IndexedDB に保存すれば、XSS のスクリプトでも**鍵の中身は持ち出せません**。RFC 10017 もこの組み合わせに触れています。ただしここでも、ページの中から鍵を「使う」ことはできます。詳しくは第 131 回で見ます。

### ブラウザでなければ

ネイティブのモバイルアプリやデスクトップアプリなら、OS が用意する保管場所（iOS や macOS の Keychain、Android の Keystore）にトークンを置きます。アプリごとに隔離され、鍵をハードウェアの中に閉じ込めて取り出せなくすることもできます（第 109 回の「取り出せない」ことの価値）。同じ画面の中で他人のスクリプトが動く、というブラウザ特有の問題がないので、議論の前提がそもそも違います。

## JWT は何と組み合わさって意味を持つか

JWT 単体は、署名付きの JSON にすぎません。安全に使えるのは、ここまでの部品が揃ったときです。

| 部品 | 役目 | 見た回 |
| --- | --- | --- |
| 署名（ES256、RS256、EdDSA）か MAC（HS256） | 書き換えられていないこと | 第 104 回、第 107 回 |
| JWK と JWKS | 公開鍵を配り、`kid` で選ぶ | 第 108 回、この回 |
| TLS と証明書 | JWKS を本物の発行者から取ったこと | 第 110〜114 回 |
| 時計 | `exp` と `nbf` の判定 | 第 158 回 |
| 発行する仕組み | 誰を、どう認証して発行したか | 第 129 回、第 130 回 |
| 認可 | `sub` に何を許すか | 第 132 回 |

どれか 1 つが欠けると、形式としては正しい JWT が、何も保証しない文字列になります。

## まとめ

- JWT は JOSE（JWS、JWE、JWK、JWA）の上に乗った**形式**で、認証方式ではない。出回る JWT の多くは JWS で、**署名されているだけで中身は誰でも読める**
- 署名は Base64URL にしたヘッダとペイロードに掛かる。ES256 の署名は DER ではなく `r` と `s` を並べた 64 バイト
- 検証では、**アルゴリズム、鍵、発行者、受け取り手をすべて検証する側が先に決めておき**、トークンに書かれた値はそれと突き合わせるだけにする。`alg: none`、RS256 と HS256 の取り違え、`kid`・`jku`・`jwk` の悪用は、すべてトークンに検証の方法を決めさせたことで起きた
- 公開鍵は JWKS で配り、信頼の根拠は TLS に移る。ローテーションは「足す、待つ、切り替える、待つ、外す」の順
- JWT をセッションに使うと失効できない。寿命の短い JWT と失効できる仕組みを組み合わせる
- ブラウザでの置き場所が左右するのは**持ち出せるかどうか**だけで、XSS がその場で悪用することは防げない。BFF、トークン仲介、ブラウザだけの順に安全で、盗まれても使えなくするには DPoP と取り出せない鍵を使う

次の第 129 回では、この JWT がアクセストークンとして運ばれることの多い OAuth 2.0 が、実際には何を決めている仕組みなのかを見ます。OAuth は認証の仕組みではない、というところから始めます。
