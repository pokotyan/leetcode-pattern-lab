## 平文はどこにあるのか

第 104 回では、TLS 1.3 のハンドシェイクを 1 メッセージずつ読みました。そこでは話し手が 2 人しかいませんでした。クライアントと、サーバです。

本番の構成では、その間に何台も挟まります。CDN、ロードバランサ、Ingress、サイドカーのプロキシ。ブラウザのアドレスバーに鍵のマークが出ていても、それが保証するのは**ブラウザと、最初に TLS を受け止めた機械との間**だけです。その先で通信が平文に戻っているのか、別の TLS で包み直されているのかは、ブラウザからは見えません。

そこでこの回では、3 つの問いを立てて構成を読みます。

1. **誰が平文を見るか**（TLS を終える＝復号する機械はどれか）
2. **証明書と秘密鍵を誰が持つか**（秘密鍵が置かれる機械はどれか）
3. **終えた後ろに、クライアントの情報をどう渡すか**（IP アドレス、クライアント証明書）

TLS を「終える（終端する）」とは、そこでハンドシェイクの相手役を務め、暗号文を平文に戻すことです。第 104 回で見た CertificateVerify に署名できるのは秘密鍵を持つ者だけなので、**TLS を終える機械には、必ず秘密鍵がある**。この事実が、以下のすべての型の前提です。

## 構成の型

### 型 1: ロードバランサで終える（L7）

```
クライアント ══TLS══▶ LB ──平文 HTTP──▶ アプリ
                     ↑ 秘密鍵はここ
                     ↑ HTTP を読んで、パスやヘッダで振り分ける
```

最も多い型です。LB が HTTP を読めるので、パスによる振り分け、ヘッダの付与、圧縮、WAF などができます。証明書の更新も LB の 1 か所で済みます（第 103 回の自動更新の置き場所になります）。

代わりに、**LB から後ろは平文**です。同じ網の中にいる誰か（あるいは第 163 回で見るような計装）がそれを読めます。

### 型 2: 終えて、もう一度暗号化する

```
クライアント ══TLS①══▶ LB ══TLS②══▶ アプリ
                      ↑ 平文はここで一度だけ現れる
```

LB は HTTP を読みつつ、後ろには別の TLS 接続を張ります。TLS① と TLS② は**別のハンドシェイク、別の鍵**です。平文は LB のメモリの中にだけ現れます。

ただし、**TLS② で LB がアプリの証明書を検証しているとは限りません**。たとえば AWS の Application Load Balancer は、ターゲットの証明書を検証しないと明記しており、自己署名や期限切れの証明書でも通ります。その代わり VPC の中の通信はパケットの層で認証されているので中間者の心配はない、という説明です（[AWS ELB ドキュメント: Target groups](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-target-groups.html#target-group-routing-configuration)）。つまりこの区間の相手確認は、TLS ではなくクラウドの網が担っています。

### 型 3: パススルー（L4）

```
クライアント ══════════TLS══════════▶ アプリ
                 ↑ LB は ClientHello の SNI だけ見て振り分ける
                 ↑ 秘密鍵はアプリにある
```

LB は TLS を終えず、TCP のバイト列をそのまま流します。どこへ送るかは、ClientHello に平文で入っている SNI（第 104 回）で決めます。Kubernetes の Gateway API では、リスナの TLS モードに `Terminate` と `Passthrough` があり、後者ではゲートウェイで TLS を終えず暗号化されたまま通します（[Gateway API: TLS](https://gateway-api.sigs.k8s.io/guides/tls/)）。

平文を見るのはアプリだけで、秘密鍵もアプリだけが持ちます。代わりに LB は HTTP を読めないので、パスでの振り分けも、HTTP のヘッダの付与もできません。第 72 回で見た「L4 の振り分けは接続単位で、呼び出し単位ではない」という制約もそのまま残ります。なお、第 62 回の ECH を使うと本当の SNI も暗号化されるので、SNI による振り分けは ECH を解ける機械でしかできなくなります。

### 型 4: サイドカーやメッシュで終える

```
[Pod A: アプリ ─平文(localhost)─ プロキシ] ══mTLS══ [プロキシ ─平文(localhost)─ アプリ :Pod B]
```

第 156 回で見たサービスメッシュです。TLS を終えるのは同じ Pod の中のプロキシで、平文が流れるのは Pod の中の localhost だけです。秘密鍵は各プロキシが持ち、寿命の短い証明書として自動で配られます。

### 4 つの型を並べる

| 型 | 平文を見る機械 | 秘密鍵がある機械 | LB が HTTP を読めるか |
| --- | --- | --- | --- |
| LB で終える | LB と、LB からアプリまでの経路 | LB | 読める |
| 終えて再暗号化 | LB（メモリの中） | LB とアプリの両方 | 読める |
| パススルー | アプリだけ | アプリ | 読めない（SNI だけ） |
| メッシュ | 各 Pod の中（localhost） | 各プロキシ | プロキシが読める |

<Callout type="warn" title="よくある誤解: 「HTTPS にしたので、通信はずっと暗号化されている」">
鍵のマークは、**最初に TLS を終えた機械まで**の話です。CDN や LB で終えていれば、その先は別の区間で、平文のこともあります。しかも、TLS を終える機械は秘密鍵を持つので、CDN 事業者は**あなたの名前で TLS を話せる**立場にいます。「HTTPS かどうか」ではなく、「何区間あって、それぞれ誰が終えているか」を数えるのが正しい問いです。
</Callout>

## 終えた後ろに、何を渡すか

TLS を終えると、後ろのアプリから見た接続の相手は LB になります。**クライアントの IP アドレスも、クライアントが出した証明書も、アプリからは見えなくなります**。そこで、LB が情報を書き足して後ろへ渡します。

### IP アドレス: ヘッダか、PROXY protocol か

HTTP を読める型（1, 2）では、LB がヘッダを足します。慣習として広く使われているのが `X-Forwarded-For` で、同じ目的を標準化したのが `Forwarded` ヘッダです（[RFC 7239](https://www.rfc-editor.org/rfc/rfc7239.html)）。

HTTP を読めないパススルー（型 3）では、ヘッダを足せません。そこで、TCP 接続の**先頭に 1 行差し込む**のが PROXY protocol です。HAProxy が定めた仕様で、v1 は次のような人の読める 1 行です（[PROXY protocol](https://www.haproxy.org/download/1.8/doc/proxy-protocol.txt)）。

```
PROXY TCP4 192.168.0.1 192.168.0.11 56324 443\r\n
（この直後から、クライアントの ClientHello がそのまま続く）
```

v2 はバイナリ形式で、TLV という追加の欄にクライアント証明書の CN などの TLS の情報も載せられます（同上）。

### クライアント証明書: XFCC

LB やプロキシでクライアント証明書を確かめた場合（次の節の mTLS）は、その結果を後ろへヘッダで渡します。Envoy は `x-forwarded-client-cert`（XFCC）というヘッダに、証明書のハッシュ、Subject、URI 型の SAN などを `;` 区切りで書きます（[Envoy: HTTP header manipulation](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_conn_man/headers#x-forwarded-client-cert)）。

```
By=http://frontend.lyft.com;Hash=468ed33b...;Subject="/C=US/.../CN=Test Client";URI=http://testclient.lyft.com
```

AWS の ALB では、確かめた結果を `X-Amzn-Mtls-Clientcert-Subject` や `X-Amzn-Mtls-Clientcert-Leaf` などのヘッダで渡します。検証を ALB でせずに証明書チェーンだけを渡す「パススルー」モードもあり、その場合はアプリが自分で検証する必要があります（[AWS ELB: Mutual authentication with TLS](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/mutual-authentication.html)）。

<Callout type="warn" title="よくある誤解: 「ヘッダに書いてあるのだから、LB が確かめた値だ」">
ヘッダは、**誰でも書けます**。アプリに LB を通らず直接届く経路があれば、`curl -H 'X-Forwarded-For: 10.0.0.1'` や偽の XFCC で、別人のふりができます。PROXY protocol の仕様も、受け手は信頼できるプロキシからの接続にだけこれを許すよう求めています（[PROXY protocol](https://www.haproxy.org/download/1.8/doc/proxy-protocol.txt)）。Envoy は設定しなければ、外から来た XFCC を消す（sanitize する）のが既定です（[Envoy](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_conn_man/headers#x-forwarded-client-cert)）。

守るべきことは 2 つです。**LB は外から来た同名のヘッダを捨ててから書き直す**こと。**アプリは LB からしか届かない**ように網を閉じること。ヘッダによる受け渡しは、この 2 つが揃って初めて意味を持ちます（第 114 回の「ゲートウェイで検証してヘッダで渡す型」も同じ前提です）。
</Callout>

## mTLS: クライアントも証明書を出す

普通の TLS では、証明書を出すのはサーバだけです。クライアントが誰なのかは、TLS の上で、パスワードやトークンで確かめます。

**mTLS**（相互 TLS）では、クライアントも証明書を出します。仕組みは第 104 回のハンドシェイクに 1 通足すだけです。

```
クライアント                                     サーバ
ClientHello  ─────────────────────────────▶
             ◀───────────────────────────── ServerHello
                                            EncryptedExtensions
                                            CertificateRequest   ← これが増える
                                            Certificate
                                            CertificateVerify
                                            Finished
Certificate          ← クライアントの証明書
CertificateVerify    ← ハンドシェイクへの署名（秘密鍵を持つ証明）
Finished     ─────────────────────────────▶
```

サーバは EncryptedExtensions の後に CertificateRequest を送ります（[RFC 8446 4.3.2](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.3.2)）。その中の `certificate_authorities` 拡張で、受け入れる CA の名前を示すこともできます（[RFC 8446 4.2.4](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2.4)）。クライアントは、サーバと同じく Certificate と CertificateVerify を返します。CertificateVerify は第 98 回の署名なので、**証明書を盗み見ただけでは mTLS は通りません**。秘密鍵が要ります。

クライアントが証明書を出さなかった場合、サーバはクライアントを確かめないまま続けてもよいし、`certificate_required` のアラートで打ち切ってもよい、とされています（[RFC 8446 4.4.2.4](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.2.4)）。**どちらにするかはサーバの設定次第**です。

用途は主に 3 つです。

- **サービス間の通信**: 第 156 回のメッシュ。証明書には SPIFFE ID（第 120 回）のような「ワークロードの名前」を書く
- **デバイス**: IoT の機器や社用端末に、工場や MDM で証明書を入れておく
- **ゼロトラスト**: 社内網にいることではなく、「会社が発行した端末証明書を持つこと」を接続の条件にする（第 121 回で構成として見ます）

<Callout type="warn" title="よくある誤解: 「mTLS にすれば、アクセス制御もできている」">
mTLS が確かめるのは、**相手が、信頼する CA の発行した証明書と、その秘密鍵を持っている**ことだけです。その相手に何を許すかは、何も決めていません。

同じ社内 CA が全サービスに証明書を配っているなら、`billing` の証明書を持つサービスも、`logging` の証明書を持つサービスも、同じように mTLS を通ります。「`logging` には決済 API を呼ばせない」は、**証明書の中の名前（SAN の URI など）を見て判定する認可の規則**を別に書いて初めて実現します（第 115 回）。メッシュの認可ポリシーは、まさにこの部分です。さらに、利用者の代わりに動いているなら、利用者が誰かは mTLS では分かりません。それはトークンで運びます（第 114 回、第 121 回）。
</Callout>

mTLS は単体でも使えますが、**トークンと組み合わせる**と、もう 1 つの役割を持ちます。アクセストークンを「この証明書を出したクライアントにしか使えない」と縛る方式（RFC 8705）で、盗まれたトークンを使えなくします。これは第 114 回で詳しく見ます。

## 手元で確かめる: mTLS のサーバに 3 通りでつなぐ

openssl で 2 つの CA（A と B）を作り、A からサーバ証明書と `alice` のクライアント証明書を、B から `mallory` のクライアント証明書を発行します（作り方は第 102 回と同じなので省きます）。サーバは Python の `ssl` で、**CA A の発行したクライアント証明書だけを受け入れる**ように設定します。

```python
ctx = ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER)
ctx.minimum_version = ssl.TLSVersion.TLSv1_3
ctx.load_cert_chain("server.crt", "server.key")
ctx.load_verify_locations("caA.crt")          # クライアント証明書を検証する CA
ctx.verify_mode = ssl.CERT_REQUIRED           # 出さないクライアントは拒む

srv = http.server.HTTPServer(("127.0.0.1", 18095), H)
srv.socket = ctx.wrap_socket(srv.socket, server_side=True)
```

ハンドラは `self.connection.getpeercert()` で相手の証明書の CN を取り出して返します。curl（macOS 付属の 8.7.1、LibreSSL 3.3.6）で 4 通り試しました。

```
$ curl --cacert caA.crt --cert alice.crt --key alice.key https://api.local:18095/
hello, alice

$ curl --cacert caA.crt https://api.local:18095/
curl: (56) LibreSSL SSL_read: ... error:1404C45C:SSL routines:ST_OK:reason(1116), errno 0

$ curl --cacert caA.crt --cert mallory.crt --key mallory.key https://api.local:18095/
curl: (56) LibreSSL SSL_read: ... error:1404C418:SSL routines:ST_OK:tlsv1 alert unknown ca, errno 0

$ curl --cert alice.crt --key alice.key https://api.local:18095/
curl: (60) SSL certificate problem: self signed certificate in certificate chain
```

（`api.local` は `--resolve api.local:18095:127.0.0.1` で手元に向けています。）

2 番目と 3 番目がサーバに拒まれた例です。`reason(1116)` は、この LibreSSL がアラートの名前を知らず番号だけ出したもので、1000 を引いた **116 が `certificate_required`** です（[RFC 8446 6](https://www.rfc-editor.org/rfc/rfc8446.html#section-6)）。3 番目の `unknown ca` はアラート 48 で、「その CA は知らない」という意味です。4 番目は向きが逆で、**クライアントがサーバを信用していない**（CA A を渡していないので、OS のトラストストアで検証して失敗した）例です。

OpenSSL 3.6 の `s_client` で同じことをすると、名前がはっきり出ます。

```
$ openssl s_client -connect 127.0.0.1:18095 -servername api.local -CAfile caA.crt
...
No client certificate CA names sent
...
Verification: OK
...
error:0A00045C:SSL routines:ssl3_read_bytes:tlsv13 alert certificate required:...:SSL alert number 116
```

ここから読み取れることが 2 つあります。

- **エラーの番号が 35（接続時の失敗）ではなく 56（受信時の失敗）** です。TLS 1.3 では、クライアントは Certificate と Finished を送った時点でハンドシェイクを終えたと考え、サーバの拒否は**その後の読み込みで**届きます。サーバの証明書の検証は `Verification: OK` なので、ログの見かけは「つながった後に切られた」になります。mTLS の拒否を探すときは、ハンドシェイクのエラーだけでなく、読み込み時のエラーも見る必要があります
- `No client certificate CA names sent` は、このサーバが `certificate_authorities` を送っていないことを示します。クライアントが証明書を複数持っている場合、手がかりが無いので正しい 1 枚を選べないことがあります。ALB がこの一覧の送信を設定で選べるようにしているのは、この問題のためです（[AWS ELB](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/mutual-authentication.html#advertise-ca-subject)）

最後に、サーバ側を `ssl.CERT_OPTIONAL` に変えて、証明書なしでつないでみます。

```
$ curl --cacert caA.crt https://api.local:18095/
hello, (no cert)
```

**通ってしまいます**。「出されたら検証する、出されなければ匿名として通す」という設定で、RFC 8446 4.4.2.4 が許す前者の振る舞いです。この設定にするなら、「証明書が無ければ断る」はアプリが判定しなければなりません。mTLS が認可ではないことの、小さな実例です。

## ブラウザに「HTTPS 以外で来るな」と覚えさせる: HSTS

ユーザがアドレスバーに `example.com` とだけ打つと、ブラウザは最初に平文の `http://` でつなぎに行くことがあります。そこで中間者がリダイレクトを握りつぶせば、TLS は一度も始まりません。

**HSTS**（HTTP Strict Transport Security）は、サーバが `Strict-Transport-Security` ヘッダで「以後この名前には HTTPS でしか来るな」とブラウザに覚えさせる仕組みです（[RFC 6797](https://www.rfc-editor.org/rfc/rfc6797.html)）。覚えたブラウザは、`http://` の URL も内部で `https://` に書き換え、さらに**証明書のエラーを利用者が無視して進むことを許しません**（[RFC 6797 12.1](https://www.rfc-editor.org/rfc/rfc6797.html#section-12.1)）。このヘッダは HTTPS の応答で受け取ったときだけ有効です（[RFC 6797 8.1](https://www.rfc-editor.org/rfc/rfc6797.html#section-8.1)）。

それでも「最初の 1 回」は守れません。そこで、ブラウザにあらかじめ名前の一覧を組み込むのが**プリロード**です。hstspreload.org への登録には、`max-age` が 1 年（31536000 秒）以上で、`includeSubDomains` と `preload` を付けることが条件で、**一覧からの削除は遅く、苦痛を伴う**とはっきり書かれています（[hstspreload.org](https://hstspreload.org/)）。すべてのサブドメインで長期に HTTPS を出せる確信が無いうちは登録しない、というのが公式の注意です。

HSTS は TLS の暗号を強くするものではありません。**TLS を必ず始めさせる**ためのもので、第 102 回の証明書検証と組み合わさって初めて意味を持ちます。

## 証明書のピン留めが廃れた理由

「CA が誤発行しても騙されないよう、このサイトの公開鍵をブラウザに覚えさせる」のが**ピン留め**です。Web では HPKP（[RFC 7469](https://www.rfc-editor.org/rfc/rfc7469.html)）というヘッダで実現されていました。

しかし Chrome は 72 で HPKP を削除しました。理由は、採用がごく少なく、誤発行への防御になる一方で、**サービス妨害と悪意あるピン留めの危険**を生むからです（[Chrome 72 の非推奨と削除](https://developer.chrome.com/blog/chrome-72-deps-rems)）。

- **鍵を失うと、サイトが自分で自分を締め出す**。ピンした鍵を紛失したり、CA を乗り換えたりすると、覚えたブラウザからは `max-age` の間ずっと到達できない
- **乗っ取られると、攻撃者がピンを置いていく**。一時的にサーバを握った攻撃者が自分の鍵をピンすれば、持ち主が取り戻した後も利用者が入れない

誤発行への対策は、第 103 回の Certificate Transparency と CAA レコード（第 58 回）が担う形に移りました。モバイルアプリでは今もピン留めが使われますが、Android の公式文書も、**予備の鍵を必ず含めよ、さもなければ鍵の交換のたびにアプリの更新が要る**と注意しています（[Android: Network security configuration](https://developer.android.com/privacy-and-security/security-config)）。

<Callout type="warn" title="よくある誤解: 「ピン留めすれば、それだけ安全になる」">
ピン留めは、**鍵を替える自由と引き換え**に誤発行を防ぐものです。第 103 回で見たように、証明書の有効期間は短くなり、自動更新が当たり前になりました。自動更新は鍵ごと替えることも多く、ピン留めとは相性が最悪です。ピンした鍵の寿命と、証明書の運用の寿命を揃えられない限り、安全を増やすより障害を増やします。
</Callout>

## つながらないとき: エラーメッセージで切り分ける

TLS の障害の多くは、**第 102 回の検証の手順（署名、期限、名前、用途、失効）のどこで落ちたか**に対応します。手元の Python（3.14、OpenSSL 3.6）のクライアントで、よくある 6 つを作って、実際のメッセージを集めました。

```
[期限切れ]        certificate verify failed: certificate has expired
[まだ有効でない]  certificate verify failed: certificate is not yet valid or the system clock is incorrect
[名前が違う]      certificate verify failed: Hostname mismatch, certificate is not valid for 'www.example.com'.
[中間を送らない]  certificate verify failed: unable to get local issuer certificate
[版の不一致]      [SSL: TLSV1_ALERT_PROTOCOL_VERSION] tlsv1 alert protocol version
[SNI を送らない]  (s_client) Verify return code: 62 (hostname mismatch)  ← 既定の証明書が返ってきた
```

| 症状 | 原因の候補 | 確かめ方 |
| --- | --- | --- |
| `certificate has expired` | 証明書の期限切れ。更新したのに古い証明書を読み込んだまま | `openssl s_client ... \| openssl x509 -noout -dates` で、**実際に返ってくる**証明書の期限を見る |
| `not yet valid` | **クライアントの時計が遅れている**（第 140 回）。発行直後の証明書と、時計のずれた端末の組み合わせ | 失敗する端末の `date` を見る。起動直後の NTP 未同期の機器で多い |
| `Hostname mismatch` | SAN に無い名前でつないだ（第 101 回）。IP で直接つないだ | `openssl x509 -noout -ext subjectAltName` |
| `unable to get local issuer certificate` | サーバが中間証明書を送っていない。**または**クライアントのトラストストアにルートが無い | `s_client -showcerts` で送られてくる枚数を数える。1 枚だけなら前者 |
| `alert protocol version` / `handshake failure` | TLS の版や暗号スイートの共通部分が無い（古いクライアントと新しいサーバ、またはその逆） | `s_client -tls1_2` などで版を指定して試す |
| 名前が合わない（特定のクライアントだけ） | クライアントが SNI を送らず、サーバが既定の証明書を返した | `s_client -noservername` と `-servername 名前` で返る証明書を比べる |
| mTLS で `certificate required` / `unknown ca` | クライアント証明書を出していない／別の CA の証明書を出した | 前の節のとおり。読み込み時のエラーとして出る |
| 手元では通るのにコンテナだけ失敗 | コンテナのトラストストアが古い、または入っていない（第 145 回の `ca-certificates`） | コンテナの中で `ls /etc/ssl/certs` |

いくつか補足します。

**中間証明書の送り忘れ**は、ブラウザでは気づきにくい障害です。第 102 回で見たとおり、ブラウザは AIA から中間を取りに行ったり、以前に見た中間を覚えていたりして補うので、ブラウザでは正常に見え、curl や他の言語だけが失敗します。上の実験でも、葉の証明書だけを返すサーバは失敗し、`cat leaf.crt inter.crt > fullchain.crt` で連結したものを読ませると通りました。**サーバには、葉と中間を連結したファイルを渡す**のが原則です。

**SNI を送らないクライアント**は、今では珍しくなりましたが、IP アドレスで直接つなぐと必ず起きます。SNI の `HostName` には IP アドレスを入れてはいけない決まりだからです（[RFC 6066 3](https://www.rfc-editor.org/rfc/rfc6066.html#section-3)）。1 つの IP で多数の名前を出しているサーバは、SNI が無いと既定の証明書を返すしかありません。上の実験では、SNI で証明書を選ぶサーバに `-noservername` でつなぐと `default.invalid` の証明書が返り、名前の不一致になりました。

**版の不一致と同じメッセージが、まったく別の原因で出る**こともあります。この回の実験の途中、`localhost` に向けた curl が `alert protocol version` で失敗しました。調べると `localhost` が IPv6 の `::1` に解決され、同じ番号のポートで待っていた**別のサーバ**につながっていました。**エラーの中身より先に、つながっている相手が想定どおりかを確かめる**のも、切り分けの 1 歩目です（`curl -v` の `Connected to` の行で分かります）。

**鍵と証明書の取り違え**（証明書と秘密鍵のペアが違うためにサーバが起動しない）は、第 99 回で見たとおり、公開鍵を取り出して比べれば分かります。

<Callout type="tip" title="「検証を切れば通る」は、原因の切り分けにだけ使う">
`curl -k` や `verify=False` で通るなら、「TCP と TLS の版は問題なく、証明書の検証で落ちている」ところまでは分かります。切り分けの道具としては便利です。しかし、そのまま本番のコードに残すと、第 97 回で見た中間者に対して無防備になります。検証を切った状態の TLS は、**暗号化はされていても、相手が誰か分からない**通信です。
</Callout>

## どの部品と組み合わさっているか

この回の話は、どれも単独では働きません。

| やりたいこと | 組み合わせる部品 |
| --- | --- |
| LB で TLS を終える | 証明書と秘密鍵（第 99、101 回）＋自動更新（第 103 回）＋後ろへの受け渡し（ヘッダ、PROXY protocol）＋網を閉じること |
| mTLS でクライアントを確かめる | TLS 1.3 のハンドシェイク（第 104 回）＋署名（第 98 回）＋クライアント用の CA とトラストストア（第 102 回）＋**認可の規則**（第 115 回） |
| 盗まれたトークンを使えなくする | mTLS ＋アクセストークン（第 114 回、RFC 8705） |
| TLS を必ず始めさせる | HSTS ＋プリロード＋証明書の検証（第 102 回） |
| 誤発行を見つける | Certificate Transparency ＋ CAA（第 103 回、第 58 回）。ピン留めではなく |

## まとめ

- TLS を終える機械は必ず秘密鍵を持ち、そこで平文が現れる。構成は「誰が平文を見るか」「誰が秘密鍵を持つか」「後ろへ何をどう渡すか」の 3 つで読む
- 型は、LB で終える（L7）、終えて再暗号化、パススルー（L4、SNI で振り分け）、メッシュ。再暗号化しても、LB が後ろの証明書を検証しているとは限らない
- 終えた後ろには、クライアントの IP を `X-Forwarded-For` / `Forwarded` や PROXY protocol で、クライアント証明書を XFCC などで渡す。ヘッダは誰でも書けるので、LB で書き直し、アプリに直接届く経路を閉じる
- mTLS はサーバが CertificateRequest を送り、クライアントも Certificate と CertificateVerify を返す。確かめるのは「信頼する CA の証明書と秘密鍵を持つこと」だけで、何を許すかは別の認可の規則が決める
- TLS 1.3 の mTLS の拒否は、ハンドシェイクの後の読み込み時のエラーとして現れる
- HSTS は TLS を必ず始めさせる仕組み。プリロードは取り消しが難しい。HPKP は自分を締め出す危険のため Chrome 72 で削除され、誤発行への対策は CT と CAA に移った
- 障害は検証の手順のどこで落ちたかで切り分ける。期限、時計のずれ、名前、中間の送り忘れ、版の不一致、SNI、古いトラストストア

次の回からは、同じ部品（鍵交換、署名、AEAD）を使いながら、**CA を置かずに相手を信じる**別の道を見ます。最初の接続で相手の鍵を覚える SSH です。
