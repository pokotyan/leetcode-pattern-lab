## 読むたびに同じ計算をしていないか

前回は、書き込みの回数を減らしました。この回では、計算を **読むときから書くときへ移す** 方法を見ます。

Web アプリでは、多くの場合、読み出しの回数が書き込みの回数を大きく上回ります。椅子の位置は 1 回記録されるだけですが、その椅子の総走行距離は、オーナーが画面を開くたびに計算されます。成績は科目の終了時に確定しますが、成績の一覧は学生がアクセスするたびに集計されます。**読むたびに同じ答えを計算しているなら、答えが変わる瞬間（書き込み）に 1 回だけ計算して保存しておけば、読み出しは保存した値を返すだけになります。**

第 270 回、第 271 回のキャッシュも「同じ計算を繰り返さない」工夫でした。違いは置き場所と寿命です。

| | キャッシュ（第 269・270 回） | 事前計算（この回） |
| --- | --- | --- |
| 置き場所 | アプリのメモリ、Redis など | データベースの列や表 |
| 正しさの基準 | 元のデータ。古くなってよい範囲が決まっている | 計算した値そのものが正。元のデータと常に一致させる |
| 消えたら | 作り直せば済む | 元のデータから再計算しない限り戻らない |
| 更新のきっかけ | 期限切れ、無効化 | 元のデータの書き込みと同時 |

この回で扱うのは、次の 5 つの形です。

| 形 | 何を先に計算するか | ISUCON での例 |
| --- | --- | --- |
| 書き込み時に計算した列 | 行ごとに決まる派生値 | ISUCON11 予選の `condition_level` |
| 累計の UPSERT | 行が増えるたびに変わる合計 | ISUCON14 の総走行距離 |
| 確定した時点で 1 回だけ計算 | ある時点で変わらなくなる集計 | ISUCON12 予選の課金、ISUCON11 本選の総合点 |
| 不要な行の削減 | 実際に使われる行だけを残す | ISUCON12 予選の `player_score`、`visit_history` |
| キー基準のページング | 読み飛ばす位置を、件数ではなくキーで持つ | ISUCON11 本選のお知らせ一覧 |

## 書き込み時に計算した列

ISUCON11 予選（ISUCONDITION）では、椅子（ISU）から送られるコンディションが `is_dirty=true,is_overweight=false,is_broken=false` のような文字列で保存されていました。3 つのうち `true` の数で、`info`・`warning`・`critical` の 3 段階の **コンディションレベル** が決まります（[ISUCONDITION アプリケーションマニュアル](https://github.com/isucon/isucon11-qualify/blob/main/docs/isucondition.md)）。

コンディションの一覧の API は、レベルで絞り込んで最新の何件かを返します。ところがレベルは文字列から計算しないと分からないので、参考実装は椅子のコンディションを全件読み、アプリの中でレベルを計算して絞り込んでいました。公式の解説はこう書いています（[ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)）。

> POST /api/condition/:jia_isu_uuid で INSERT するタイミングで condition_level を計算し、WHERE で filter をかけられるようにすると、LIMIT をかけることができるようになります。

続けて、問題の本質がどこにあったかも書かれています。

> condition_level が正規化されていない CSV 形式だったため、とりあえず改善しようとしたチームも多かったと思います。しかし速度の観点における問題点は正規化されていないこと自体ではなく、正規化されていないことにより上述のように LIMIT を取れないことでした。

データベースが `WHERE` で絞れない値は、インデックスにも載せられず、`LIMIT` も効きません。**アプリで計算している値は、データベースから見ると存在しない** のです。

### 手元で確かめる：レベルで絞って 20 件

椅子 100 台、1 台あたり 5,000 件、合計 50 万件のコンディションを作りました。3 つのフラグはそれぞれ約 1/3 の確率で `true` にしてあり、`critical`（3 つとも `true`）は全体の約 3.7% です。椅子 1 台から `critical` を新しい順に 20 件取り出します。

環境は Apple M1 Pro、Docker（OrbStack）の `mysql:8.4`（8.4.13）、Go 1.24.6 と github.com/go-sql-driver/mysql v1.8.1 です。時間は 5 回の中央値、「読んだ行」はセッションの `Handler_read_%` の合計で、ストレージエンジンから行を取り出した回数です（[MySQL 8.4 Reference Manual: Server Status Variables](https://dev.mysql.com/doc/refman/8.4/en/server-status-variables.html)）。一時表からの読み出しも含みます。

```sql
-- 元の形: 椅子の全件を新しい順に読み、アプリでレベルを計算して 20 件集める
SELECT id, ts, `condition` FROM isu_condition WHERE isu_id = 42 ORDER BY ts DESC;

-- 書き込み時に condition_level を計算して保存し、(isu_id, condition_level, ts) の索引を張る
SELECT id, ts, `condition` FROM isu_condition
WHERE isu_id = 42 AND condition_level = 'critical' ORDER BY ts DESC LIMIT 20;
```

```text
  全件を読んでアプリで絞る（SQL 部分）                         34.22 ms  読んだ行     5001  返した行 5000
  condition_level で絞って LIMIT 20                 1.65 ms  読んだ行       20  返した行 20
```

元の形は 5,000 行を読んでアプリに送り、アプリはさらにその 5,000 件の文字列を解析します。列を足した形は 20 行だけを読んで終わりました。第 267 回で見たとおり、`(isu_id, condition_level, ts)` の索引では、等号の 2 列で範囲が決まり、その中が `ts` の順に並んでいるので、先頭から 20 件取れば終わりです。

<Callout type="tip" title="データベースに計算させる：生成列">
  派生値の計算をアプリの INSERT に書き足す代わりに、MySQL の生成列（generated column）を使う方法もあります。
  `STORED` の生成列は、行の挿入や更新のときに式を評価して値を保存し、通常の列と同じようにインデックスを張れます
  （[MySQL 8.4 Reference Manual: CREATE TABLE and Generated Columns](https://dev.mysql.com/doc/refman/8.4/en/create-table-generated-columns.html)）。
  計算の式がデータベースの定義に 1 か所だけ置かれるので、書き込みの経路が複数あっても計算を忘れません。
  第 267 回の、降順の並びを生成列で作る方法も同じ発想です。
</Callout>

## 累計を UPSERT で持つ

ISUCON14（ISURIDE）では、椅子が数秒ごとに現在位置を送り、それが `chair_locations` に 1 行ずつ溜まっていきます。椅子のオーナー向けの画面は、自分の椅子それぞれの **総走行距離** を表示します。参考実装は、表示のたびに次のクエリで計算していました（[isucon14 webapp/go/owner_handlers.go](https://github.com/isucon/isucon14/blob/main/webapp/go/owner_handlers.go)）。

```sql
SELECT ... IFNULL(total_distance, 0) AS total_distance
FROM chairs
       LEFT JOIN (SELECT chair_id,
                          SUM(IFNULL(distance, 0)) AS total_distance,
                          MAX(created_at)          AS total_distance_updated_at
                   FROM (SELECT chair_id,
                                created_at,
                                ABS(latitude - LAG(latitude) OVER (PARTITION BY chair_id ORDER BY created_at)) +
                                ABS(longitude - LAG(longitude) OVER (PARTITION BY chair_id ORDER BY created_at)) AS distance
                         FROM chair_locations) tmp
                   GROUP BY chair_id) distance_table ON distance_table.chair_id = chairs.id
WHERE owner_id = ?
```

ウィンドウ関数の `LAG` で 1 つ前の位置を取り出し、差の絶対値（マンハッタン距離）を足し合わせています。問題は、内側の派生表が **全椅子の全位置** を対象にしていることです。オーナーが持つ椅子が 10 台でも、全椅子の距離を計算してから JOIN します。

公式の解説は、まずクエリを組み替えるだけでも軽くできると書いたうえで、次のように続けています（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。

> また、最新以外のchair_locationsはここでのtotal_distanceを計算することにしか使われないことと、新しく椅子の位置情報が記録されるとき次のtotal_distanceは1つ前の位置情報とそれまでの total_distanceから計算できることに気がつけると、各椅子ごとに最新の位置情報と総走行距離を持つテーブルを作りUPSERTだけで管理できるようになり、ここでのクエリをはじめ様々なクエリをシンプルにすることができます。

累計は、**直前の値と新しい 1 件から次の値が決まる** 種類の集計です。合計、件数、最大、最小、最新の値がこれに当たります。こうした集計は、行が増えるたびに 1 回の更新で追いかけられます。

MySQL では `INSERT ... ON DUPLICATE KEY UPDATE` で書けます。行が無ければ挿入し、主キーか一意キーが重複したら更新します。新しい行の値は、MySQL 8.0.19 以降の行の別名（`AS new`）で参照します。以前の `VALUES()` 関数による参照は 8.0.20 から非推奨です（[MySQL 8.0 Reference Manual: INSERT ... ON DUPLICATE KEY UPDATE](https://dev.mysql.com/doc/refman/8.0/en/insert-on-duplicate.html)）。

```sql
CREATE TABLE chair_total (
  chair_id INT PRIMARY KEY,
  total_distance BIGINT NOT NULL,
  latitude INT NOT NULL,      -- 直前の位置
  longitude INT NOT NULL,
  updated_at DATETIME(6) NOT NULL);

-- 位置を記録するたびに、chair_locations への INSERT と同じトランザクションで
INSERT INTO chair_total (chair_id, total_distance, latitude, longitude, updated_at)
VALUES (?, 0, ?, ?, ?) AS new
ON DUPLICATE KEY UPDATE
  total_distance = chair_total.total_distance
                 + ABS(new.latitude - chair_total.latitude)
                 + ABS(new.longitude - chair_total.longitude),
  latitude = new.latitude, longitude = new.longitude, updated_at = new.updated_at;
```

代入の順序に意味があります。MySQL では、単一表の `UPDATE` の代入は概ね左から順に評価され、後ろの代入は前の代入で変わった値を見ます。標準 SQL とは異なる振る舞いだと、リファレンス自身が書いています（[MySQL 8.4 Reference Manual: UPDATE Statement](https://dev.mysql.com/doc/refman/8.4/en/update.html)）。ここでは `total_distance` の計算を先に書いているので、その時点の `chair_total.latitude` はまだ直前の位置です。順序を逆にすると、新しい位置どうしの差（0）を足すことになります。この形で累計が正しく保たれることは、後で元のクエリと突き合わせて確かめます。

### 手元で確かめる：総走行距離

椅子 1,000 台、1 台あたり 300 件、合計 30 万件の位置を作りました。オーナー 1 人が 10 台を持ちます。

```text
== 累計の UPSERT: 椅子 1,000 台 × 位置 300 件、オーナー 1 人あたり椅子 10 台
  全椅子を集計してから JOIN（元の形）                        732.43 ms  読んだ行  3294036  返した行 10
  オーナーの椅子に絞ってから集計                              24.55 ms  読んだ行    32994  返した行 10
  累計の表を JOIN                                   14.83 ms  読んだ行       21  返した行 10
```

| 書き方 | 時間 | 読んだ行 |
| --- | --- | --- |
| 全椅子を集計してから JOIN（元の形） | 732 ms | 3,294,036 |
| 派生表の中でオーナーの椅子に絞る | 24.6 ms | 32,994 |
| 累計の表を JOIN | 14.8 ms | 21 |

元の形は、30 万行の位置を読むだけでなく、ウィンドウ関数と集計のための一時表を何度も読み書きしており、読んだ行は 300 万を超えました。派生表の中に `WHERE chair_id IN (SELECT id FROM chairs WHERE owner_id = ?)` を入れるだけで 1/100 になります。これが解説の言う「クエリを組み替える」改善です。累計の表にすると、読むのはオーナーの椅子 10 行と累計 10 行だけで、**位置の件数がいくら増えても変わりません**。組み替えた形は、椅子 1 台あたりの位置の件数に比例して遅くなり続けます。

累計の表に 14.8 ms かかっているのは、測定中のマシンが混んでいたためです（同じマシンで他の実験も動いており、ロードアベレージは 40〜70 でした）。読んだ行の数で比べてください。

書き込み側の費用も測りました。位置 2,000 件を 1 つのトランザクションで記録し、UPSERT を足す場合と足さない場合を交互に 3 回ずつ行っています。

```text
== 書き込みの側の費用: 位置 2,000 件を 1 トランザクションで記録（交互に 3 回ずつ）
  upsert=false INSERT 1 文あたり 1.077 ms
  upsert=true  INSERT 1 文あたり 1.275 ms  UPSERT 1 文あたり 1.359 ms
  upsert=false INSERT 1 文あたり 3.551 ms
  upsert=true  INSERT 1 文あたり 2.657 ms  UPSERT 1 文あたり 2.791 ms
  upsert=false INSERT 1 文あたり 3.371 ms
  upsert=true  INSERT 1 文あたり 3.729 ms  UPSERT 1 文あたり 3.982 ms
```

混雑のために回ごとのぶれは大きいものの、UPSERT 1 文の費用は、同じ回の INSERT 1 文とほぼ同じでした。どちらも主キーで 1 行に届く操作で、費用の大半は往復だからです。**書き込みのたびに 1 文増やす代わりに、読み出しのたびに 30 万行を読む処理が消えます。**

最後に、累計の表が正しく保たれているかを確かめました。位置を 2,000 件追加した後、元の形のクエリで全椅子を計算し直して累計の表と比べています。

```text
  位置を 2,000 件足した後、集計と累計の表が食い違う椅子: 0 台
```

<Callout type="warn" title="累計は、元のデータと同じトランザクションで更新する">
  `chair_locations` への INSERT と `chair_total` の UPSERT を別々のトランザクションにすると、片方だけが成功したときに累計がずれます。
  ずれた累計は、元の行から計算し直さない限り直りません。
  また、同じ椅子の位置が 2 つのリクエストから同時に届くと、どちらの「直前の位置」から差を取るかで結果が変わります。
  UPSERT は対象の行をロックして 1 件ずつ適用されるので累計は壊れませんが、届いた順と記録の時刻の順が逆になると、距離の計算が実際と変わります。
  ISUCON14 では椅子ごとの送信が順に届く前提でしたが、本番では「順序が入れ替わったらどうするか」を先に決めておきます。
</Callout>

### 件数のカウンタ：読んでから書かない

累計の最も単純な形は件数です。「いいね」の数、未読の数、在庫の数。`SELECT COUNT(*)` を毎回走らせる代わりに、カウンタの列を持ちます。このとき、次の 2 つの書き方は結果が違います。

```sql
-- (A) アプリで読んでから書く
SELECT like_count FROM posts WHERE id = 1;          -- 10 を得る
UPDATE posts SET like_count = 11 WHERE id = 1;      -- アプリで 10 + 1 を計算して書く

-- (B) データベースの中で足す
UPDATE posts SET like_count = like_count + 1 WHERE id = 1;
```

(A) では、2 人が同時に 10 を読み、2 人とも 11 を書くと、1 回分の「いいね」が消えます。第 99 回で見たロストアップデート（更新の消失）です。REPEATABLE READ でも、`SELECT` がロックを取らない普通の読み出しである限り防げません。(B) は、`UPDATE` が行に排他ロックを取ってから最新の値に 1 を足すので、同時に来ても順に適用されます。この回の UPSERT も (B) の形で、`chair_total.total_distance` を読む操作と書く操作が 1 つの文の中にあります。

事前計算の値を更新するときは、**アプリに値を持ち帰らず、差分をデータベースに渡す** 形にしておくと、同時実行の問題の多くを避けられます。1 つの行に書き込みが集中して待ちが増える場合の扱いは、次回で見ます。

<Callout type="note" title="件数を毎回数える代わりに">
  ページングの画面には、全件数や総ページ数を表示することがよくあります。`SELECT COUNT(*)` は条件に合う行をすべて数えるので、
  件数が多い表では、後で見る OFFSET と同じく重くなります。
  件数をカウンタとして別の表に持つか、「1,000 件以上」のように上限で打ち切って表示するのが定番です。
</Callout>

## 確定した時点で 1 回だけ計算する

累計のように少しずつ追いかけられない集計もあります。偏差値、順位、全体の平均を使う計算は、1 件増えるたびに全員の値が変わります。こうした集計では、**値が変わらなくなる時点** に注目します。

ISUCON12 予選（ISUPORTS）の課金は、大会ごとに、スコアを登録した参加者 1 人につき 100 円、ランキングを閲覧しただけの参加者 1 人につき 10 円で計算されます（[isucon12-qualify webapp/go/isuports.go](https://github.com/isucon/isucon12-qualify/blob/main/webapp/go/isuports.go)）。参考実装は、課金の画面が開かれるたびに、MySQL の閲覧記録と SQLite のスコアを読んでこれを計算していました。解説の論点の一覧にはこうあります（[ISUCON12 予選問題の解説と講評](https://isucon.net/archives/56850281.html)）。

> 正しい課金情報を返す必要があるのは大会が完了(finish)した後だけなので、その時点で確定値を計算して保存できる。アクセスのたびに都度計算する必要はない

本文では、大会が終了するまでは課金は常に 0 で、終了した時点で確定し、その後は変わらないことから、終了の API が呼ばれたときに「1回だけ課金情報を計算してMySQLのテーブルに保存するようなチューニングが可能となっていました。」と書かれています。

ISUCON11 本選（ISUCHOLAR）の成績の画面も同じ構造でした。学生ごとに、履修した科目それぞれの総合点の一覧を集計していて、科目が増えるほど重くなります。解説は「すでに終了している科目では更新されないことに気づけば永続的にキャッシュして良いことが分かります」と書いています（[ISUCON11 本選問題の解説と講評](https://isucon.net/archives/56163308.html)）。

どちらも、仕様に **状態の遷移**（大会の終了、科目の終了）があり、その後は値が動かないことが根拠です。確定した後の値は、キャッシュというより記録です。消えても元のデータから計算し直せますが、計算し直す必要がそもそも無くなります。

| 集計の性質 | 適した方法 |
| --- | --- |
| 直前の値と新しい 1 件で次の値が決まる（合計、件数、最大、最新） | 書き込みごとに UPSERT で累計する |
| ある時点から変わらなくなる（締めた月の売上、終わった大会の順位） | 確定の時点で 1 回計算して保存する |
| 常に全体に依存して変わる（現在の順位、全体の偏差値） | 一定間隔で計算し直し、許される古さの範囲で使う（第 271 回） |

## 行そのものを減らす

計算の結果を保存するより手前に、**そもそも使われない行を持っている** ことがあります。

ISUCON12 予選の `player_score` 表は、CSV のアップロードでスコアを登録します。CSV には同じ参加者の行が何度も現れ、仕様上は最後の行だけが有効でした。ところが参考実装はすべての行を保存し、読むときに最後の行を選んでいました。解説は、CSV を読みながら参加者ごとに最後の 1 行だけを覚えて INSERT するように変えられること、初期データも同じ考えで作り直せることを示し、次のように書いています（[ISUCON12 予選問題の解説と講評](https://isucon.net/archives/56850281.html)）。

> この処理を行うことで、player_score テーブルは初期状態の全テナント合計370万行から、18万行程度に削減されます。

閲覧の記録 `visit_history` も同様です。課金の計算は参加者ごとの最初の閲覧の時刻（`MIN(created_at)`）しか使っておらず、解説は「各テナント/大会/参加者につき、最初のアクセス時に作成される1行のみが必要」と指摘しています。最初の 1 行だけを残すと、320 万行が 20 万行になり、以後は 2 回目以降の閲覧で INSERT する必要もなくなります。

行の削減は、他の改善の前提になりました。解説は、`player_score` の削減に気付いたチームの多くが SQLite から MySQL への移行に成功し、気付かずに全データを移そうとしたチームは成功が難しかったと書き、「このデータ削減が行えたかどうか、がMySQL移行を成功させられたかどうかの分岐点となったようです。」としています。

ISUCON12 本選（ISU CONQUEST）では、別の形の削減が出題されました。プレゼントの表には、受け取り前のプレゼントと受け取り済みの履歴が同居していました。解説は、受け取り済みの行は以後変更されないことを指摘し、「受け取り前のプレゼントテーブルと、受け取り済みのプレゼント履歴テーブルにわけ、テーブルのデータ件数を減らした上で、水平分割することを想定していました。」と書いています（[ISUCON12 本選問題の解説と講評](https://isucon.net/archives/56959385.html)）。消すのではなく、**よく読む表から、読まない行を追い出す** 削減です。

| 削減の形 | 例 | 本番での注意 |
| --- | --- | --- |
| 最後の 1 行だけ持つ | 参加者ごとの最新のスコア | 履歴を後から見たい要件が無いかを確かめる |
| 最初の 1 行だけ持つ | 参加者ごとの最初の閲覧 | 同じく、回数や時刻の一覧が要らないか |
| 現役と履歴を分ける | 受け取り前のプレゼントと履歴 | 移す処理と、両方を読む画面の扱い |

本番のサービスでは、捨てた行は戻りません。監査や分析で履歴が必要になることもあります。履歴は別の表や分析用の基盤に流し、**よく読む表を小さく保つ** 形にしておけば、両方の要件を満たせます。

## OFFSET からキー基準へ

ページングの `OFFSET` も、読むたびに同じ作業を繰り返す例です。`ORDER BY id DESC LIMIT 20 OFFSET 100000` は、索引をたどって 100,000 件を数えて読み捨て、その次の 20 件を返します。ページが深くなるほど読み捨てが増えます。

ISUCON11 本選の解説は、お知らせの一覧について次のように書いています（[ISUCON11 本選問題の解説と講評](https://isucon.net/archives/56163308.html)）。

> また、参考実装では一覧取得のページングがOFFSETとLIMITの組み合わせで実現されています。OFFSETを使用するとオフセット数分のrowを頭から数える必要があるため、レコード数の増加に応じてパフォーマンスが劣化します。今回はページング用のリンクヘッダを介して、リクエスト時のクエリパラメーターを指定していたため、ページ数ではなく前回の最初・最後のレコードのIDを使用することでseek方式のページングに差し替えることが可能でした。

**キー基準**（seek 方式、keyset ページング）では、前のページの最後の行のキーを覚えておき、「それより小さいものを 20 件」と問い合わせます。索引の上でその位置に直接降り、20 件読めば終わります。

```sql
-- OFFSET: 読み捨てる件数がページの深さに比例する
SELECT id, title FROM announcements ORDER BY id DESC LIMIT 20 OFFSET 100000;

-- キー基準: 前のページの最後の id を受け取る
SELECT id, title FROM announcements WHERE id < 900001 ORDER BY id DESC LIMIT 20;
```

### 手元で確かめる：100 万件のお知らせ

お知らせを 100 万件作り、同じページを 2 つの方法で取り出しました。

```text
== OFFSET とキー基準: お知らせ 100 万件、1 ページ 20 件
  OFFSET 0                                      3.55 ms  読んだ行       21  返した行 20
  WHERE id < 1000001                            5.49 ms  読んだ行       20  返した行 20
  OFFSET 1000                                   6.57 ms  読んだ行     1021  返した行 20
  WHERE id < 999001                            10.85 ms  読んだ行       20  返した行 20
  OFFSET 100000                                70.81 ms  読んだ行   100021  返した行 20
  WHERE id < 900001                            18.02 ms  読んだ行       20  返した行 20
  OFFSET 900000                              1334.16 ms  読んだ行   900021  返した行 20
  WHERE id < 100001                            18.16 ms  読んだ行       20  返した行 20
```

| ページの位置 | OFFSET の読んだ行 | OFFSET の時間 | キー基準の読んだ行 | キー基準の時間 |
| --- | --- | --- | --- | --- |
| 先頭 | 21 | 3.6 ms | 20 | 5.5 ms |
| 1,000 件目 | 1,021 | 6.6 ms | 20 | 10.9 ms |
| 10 万件目 | 100,021 | 70.8 ms | 20 | 18.0 ms |
| 90 万件目 | 900,021 | 1,334 ms | 20 | 18.2 ms |

OFFSET の読んだ行は、ページの位置に比例して増えました。キー基準は、どの位置でも 20 行です。浅いページでキー基準の時間がやや長いのは、混んだマシンでの測定のぶれで、読んだ行の数には差がありません。

キー基準には、別の利点もあります。OFFSET では、1 ページ目を読んだ後に新しい行が先頭に追加されると、2 ページ目の先頭に 1 ページ目の最後の行がもう一度現れます。キー基準は「この id より前」を指定するので、間に行が増えても重複も抜けも起きません。

代わりに、キー基準では「37 ページ目へ飛ぶ」ができません。次と前にだけ進めます。並び替えのキーが一意でないとき（作成日時など）は、`(created_at, id)` のように一意になる列を足し、`WHERE (created_at, id) < (?, ?)` の形で比べます。この形で索引が使われるかは、第 101 回の要領で `EXPLAIN` を見て確かめます。

## 本番で使うときの判断

事前計算は、読み出しを速くする代わりに、**同じ事実をデータベースの中に 2 か所持つ** ことになります。これが非正規化です。正規化された形では、1 つの事実は 1 か所にしかないので、矛盾が起きようがありません。非正規化した瞬間から、2 か所を揃え続ける責任が書き込み側に移ります。

| 問い | 事前計算が向く | 向かない |
| --- | --- | --- |
| 読み書きの比 | 読み出しが書き込みよりずっと多い | 書いた値をほとんど読まない |
| 計算の形 | 直前の値と新しい 1 件で決まる、またはある時点で確定する | 常に全体に依存する |
| 書き込みの経路 | 1 か所、またはデータベースの定義（生成列、トリガ）で強制できる | 多数のサービスやバッチが同じ表を書く |
| ずれたときの直し方 | 元のデータから再計算できる | 元のデータを捨ててしまった |

運用で効いてくるのは最後の行です。累計や確定値を持つなら、**元のデータからすべてを計算し直すバッチ** を用意し、定期的に突き合わせるか、少なくとも必要なときに走らせられるようにしておきます。この回の実験で行った「集計と累計の表を突き合わせて、食い違う行を数える」クエリが、そのまま監視になります。

ISUCON の解説が繰り返し指摘しているのは、こうした事前計算の根拠が **仕様の中にある** ことでした。過去の位置は総走行距離にしか使われない、課金は終了後にしか確定しない、スコアは最後の行だけが有効、受け取り済みのプレゼントは変更されない。どれもコードを速く書き直す技術ではなく、仕様を読んで「この値はいつ変わるのか」「この行は誰が読むのか」を確かめた結果です。

次回は、書き込みどうしがぶつかる場面を扱います。ロックをどの範囲で取るか、ロックを持ったまま外部の API を待つと何が起きるか、ID の採番をどこで行うか、です。

## まとめ

- 読むたびに同じ答えを計算しているなら、答えが変わる書き込みの時点で 1 回だけ計算して保存できる
- アプリで計算している値はデータベースから見えないので、`WHERE` も索引も `LIMIT` も効かない。書き込み時に列として保存すると、手元では 5,000 行の読み出しが 20 行になった
- 直前の値と新しい 1 件で決まる集計（合計、件数、最新）は、書き込みごとの UPSERT で累計できる。総走行距離の計算は、読んだ行が 329 万から 21 になった
- UPSERT 1 文の費用は INSERT 1 文とほぼ同じだった。累計は元のデータと同じトランザクションで更新し、`UPDATE` 句の代入の順序に気を付ける
- ある時点から変わらなくなる集計は、確定の時点で 1 回だけ計算する（ISUCON12 予選の課金、ISUCON11 本選の終了した科目）
- 使われない行を持たないことが、他の改善の前提になる。ISUCON12 予選では 370 万行が 18 万行、320 万行が 20 万行になり、MySQL への移行ができるかどうかを分けた
- 現役の行と履歴を別の表に分ければ、履歴を捨てずに、よく読む表を小さく保てる
- OFFSET はページの位置に比例して読み捨てる。手元では 90 万件目で 90 万行を読み 1.3 秒かかった。キー基準ならどの位置でも 20 行で、行の追加による重複や抜けも起きない
- 事前計算は非正規化であり、2 か所を揃える責任が書き込み側に移る。元のデータから再計算する手段を残しておく
- 事前計算の根拠は仕様の中にある。「この値はいつ変わるのか」「この行は誰が読むのか」を先に確かめる
