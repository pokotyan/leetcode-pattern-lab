## その鍵のマークは、どこまでを守っているのか

Web メールの画面は HTTPS で開かれ、メールクライアントの設定画面には「SSL/TLS を使う」という項目があります。だから、メールは暗号化されて届いている、と感じるのは自然です。

しかし、第 123 回で見たとおり、メールは **MUA → MSA → MTA → … → MTA → MDA** と何段も受け渡されます。利用者が設定で選べるのは、最初の 1 区間（自分のクライアントから自分の送信サーバまで）だけです。**その先の MTA 同士の区間を暗号化するかどうかは、送る側と受ける側のサーバが、その場で相談して決めています**。そして、その相談は長いあいだ、誰でも口を挟める形で行われてきました。

この回では、提出と中継の 2 つの区間で事情がどう違うかを見てから、中継の区間の弱さ（証明書を確かめない、暗号化の申し出を消される）と、それを補う 3 つの仕組み（MTA-STS、DANE、TLS-RPT）を順に見ます。

## 2 つの区間、2 つの事情

```
  利用者              自分の事業者                        相手の事業者
 ┌─────┐  提出   ┌─────┐   中継（インターネット）   ┌─────┐       ┌─────┐
 │ MUA │ ──────▶ │ MSA │ ─▶ MTA ─────────────────▶ │ MTA │ ────▶ │ MDA │
 └─────┘ 465/587 └─────┘         25 番             └─────┘       └─────┘
   接続先の名前は利用者が設定する       接続先の名前は MX を引いて決まる
   認証（パスワード、OAuth）がある       認証はない。誰からでも受け取る
```

| | 提出（MUA → MSA） | 中継（MTA → MTA） |
| --- | --- | --- |
| ポート | 465（暗黙の TLS）、587（STARTTLS） | 25（STARTTLS） |
| 接続先の名前 | 利用者が設定した名前（`smtp.gmail.com` など） | 宛先ドメインの MX を DNS で引いた結果 |
| TLS を断られたら | 送らない（パスワードを平文で流せない） | 既定では**平文で送る** |
| 証明書の検証 | する。普通の HTTPS と同じ | 既定では**しないことが多い** |
| 決めている仕様 | [RFC 8314](https://www.rfc-editor.org/rfc/rfc8314.html)、[RFC 7817](https://www.rfc-editor.org/rfc/rfc7817.html) | [RFC 3207](https://www.rfc-editor.org/rfc/rfc3207.html)、MTA-STS、DANE |

違いを生んでいるのは、**「どの名前を確かめればよいか」を誰が知っているか**です。提出の区間では、利用者が接続先の名前を自分で書き込んでいます。RFC 7817 は、メールクライアントが証明書と照合する名前を「利用者が設定したホスト名」とし、安全でない DNS から導いた名前を使ってはならないとしています。これは第 102 回で見た、ブラウザが URL のホスト名を証明書と照合するのと同じ構図です。

中継の区間では、送る側の MTA が知っているのは宛先のドメイン（`example.com`）だけで、接続先のホスト名は MX を引いて初めて分かります。その MX の答えが偽物なら（第 61 回）、偽の名前と、その名前の正しい証明書がそろってしまいます。**照合すべき名前そのものが、守られていない経路から来る**。これが中継の暗号化を難しくしている根っこです。

## 提出: 465 番と 587 番

提出の区間には、TLS を始める方法が 2 通りあります。

- **暗黙の TLS（465 番）**: 接続した直後に TLS のハンドシェイクを始める。SMTP の最初の挨拶（220）も TLS の中で届く。HTTPS と同じ形
- **STARTTLS（587 番）**: まず平文で SMTP を話し始め、EHLO の応答に `STARTTLS` があれば、`STARTTLS` コマンドを送ってから TLS に切り替える

465 番は、一時 `smtps` として登録されたものの取り消されて別のサービスに割り当て直されたという経緯があり（RFC 8314 7.3）、長く「非標準」と扱われてきました。それを 2018 年に正式な提出のポートとして認め直したのが RFC 8314 です。RFC 8314 は要旨で、接続の最初から TLS を始める方式のほうが「より成功裏に展開されてきた」と述べ、移行期間中はクライアントもサーバも **587 番の STARTTLS と 465 番の暗黙の TLS の両方を実装すべき（SHOULD）**としつつ、暗黙の TLS を優先するよう勧めています（[RFC 8314](https://www.rfc-editor.org/rfc/rfc8314.html) 3.3）。なお RFC 8314 自身が、**MTA 同士の中継は対象外**だと明記しています。

なぜ暗黙の TLS のほうがよいのか。STARTTLS には、平文から暗号文へ**途中で切り替える**という構造上の弱さがあるからです。これは次の中継の節で具体的に見ます。

<Callout type="warn" title="「587 番なら暗号化されている」とは限らない">
  587 番は提出用のポートという意味で、TLS を使うことまでは意味しません。
  クライアントの設定が「STARTTLS が使えれば使う」になっていると、応答から `STARTTLS` が消されたとき、平文のまま AUTH に進む実装がありえます。
  提出の区間では、TLS を**必須**にする設定（465 番の暗黙の TLS か、STARTTLS を必須にする設定）を選びます。
  多くのサーバが、TLS の前には AUTH を広告しない（後の実験で見ます）のは、この事故を防ぐためです。
</Callout>

## 中継: 「相手が言えば使う」暗号化

MTA 同士の区間の STARTTLS は、2002 年の [RFC 3207](https://www.rfc-editor.org/rfc/rfc3207.html) で決まりました。流れは次のとおりです。

```
S: 220 mx.example.com ESMTP
C: EHLO sender.example.net
S: 250-mx.example.com
S: 250-PIPELINING
S: 250 STARTTLS                ← 「TLS も話せます」という申し出（平文）
C: STARTTLS
S: 220 2.0.0 Ready to start TLS
   ======== ここから TLS のハンドシェイク（第 104 回） ========
C: EHLO sender.example.net     ← TLS の中で最初からやり直す
S: 250-mx.example.com
...
C: MAIL FROM:<alice@example.net>
```

RFC 3207 は、TLS が始まったら**それまでに得た情報（EHLO の応答など）をすべて捨て**、クライアントは最初のコマンドとして EHLO を送り直すよう求めています。平文の間に聞いたことは信用できないからです。

そして、同じ RFC 3207 にはもう 1 つ重要な規則があります。**インターネットに公開された SMTP サーバは、ローカル宛てのメールを受け取る条件として STARTTLS を要求してはならない（MUST NOT）**。TLS を話せない相手からのメールも受け取れ、という相互運用のための規則です。

この結果、中継の STARTTLS は **日和見の暗号化**（opportunistic encryption）になりました。相手が申し出れば暗号化し、申し出がなければ平文で送る。TLS のハンドシェイクが失敗しても平文で送り直す。Postfix の送信側の設定 `smtp_tls_security_level` の `may` がまさにこの動作で、公式の説明は「送信が平文でも許される以上、既定より強い TLS を求めても相互運用性を下げるだけだ」とまで書いています。この既定値は **Postfix 3.11 から `may`、それより前は空（TLS を使わない）** です（[Postfix の postconf(5)](https://www.postfix.org/postconf.5.html#smtp_tls_security_level)）。

日和見の暗号化で守れるものと守れないものを分けると、次のようになります。

| 攻撃者 | 日和見の STARTTLS で防げるか |
| --- | --- |
| 回線を**見ているだけ**の盗聴者 | 防げる。TLS の中身は読めない |
| 応答を**書き換えられる**中間者（STARTTLS を消す） | 防げない。平文に落とされる |
| DNS を偽って**別のサーバに誘導**する攻撃者 | 防げない。偽のサーバとも TLS を張ってしまう |
| 自分の証明書を出す中間者 | 防げない。証明書を確かめていない |

つまり、**日和見の STARTTLS が防ぐのは受け身の盗聴だけ**です。それでも、全部の通信を黙って集める大規模な盗聴を割に合わなくするという意味で、価値はあります。能動的な攻撃者が狙った相手には効かない、というだけです。

## 証明書を確かめないのはなぜか

中継の MTA が証明書を確かめないのは、怠慢というより、**確かめても意味のある答えが出ない**からです。

仮に送る側の MTA が、`mx.example.com` の証明書を Web と同じ手順で検証するとします。

1. `example.com` の MX を引いて `mx.example.com` を得る
2. `mx.example.com` に接続し、証明書の SAN が `mx.example.com` であることを確かめる

攻撃者が DNS を偽れるなら、1 の答えを `mx.attacker.test` に変えられます。攻撃者は `mx.attacker.test` の正規の証明書を認証局から普通に取得できるので、2 は通ってしまいます。**MX の答えが守られていない限り、MX の名前と照合することに意味がない**。RFC 7672 もこの点を、サーバの名前が MX を通して間接的に得られ、DNSSEC がなければ MX の問い合わせが中間者攻撃に弱い、と説明しています（[RFC 7672](https://www.rfc-editor.org/rfc/rfc7672.html) 1.3.2）。

では、宛先のドメイン `example.com` と照合すればよいかというと、大手の事業者は多数の顧客ドメインのメールを同じ MX で受けているので、すべての顧客ドメインを載せた証明書は用意できません。加えて、受信側の多くが自己署名の証明書や期限切れの証明書を使っていた歴史があり、検証を必須にすると届かなくなるメールが大量に出ました。

こうして、「何と照合するか」が決められないまま、**確かめずに暗号化だけする**運用が標準になりました。この穴をふさぐには、照合すべき名前（または鍵）を、MX とは別の守られた経路で手に入れる必要があります。MTA-STS と DANE は、その「別の経路」を何にするかの違いです。

## STARTTLS を消す攻撃と、実装の脆弱性

STARTTLS の申し出は平文で届きます。途中の機器が `250 STARTTLS` の行を別の文字列に書き換えれば、送る側は「この相手は TLS を話せない」と判断し、平文で送ります。これを **STARTTLS の除去**（STARTTLS stripping）と呼びます。RFC 3207 自身が、中間者は `250 STARTTLS` を消すことで攻撃できる、と認めています。

これは理屈の上の話ではありません。2014 年 11 月、米国とタイのインターネット接続事業者が利用者の通信に手を入れ、SMTP の応答から STARTTLS の申し出を取り除いていたことが報告されました（[EFF, 2014](https://www.eff.org/deeplinks/2014/11/starttls-downgrade-attacks)）。途中の機器にとってこの書き換えは簡単で、送る側からは「相手が TLS を話さない」という正常な状況と見分けがつきません。

もう 1 つの弱点は、平文から TLS へ切り替える**境目**です。2021 年の USENIX Security で発表された研究「Why TLS is better without STARTTLS」は、SMTP、POP3、IMAP の STARTTLS を 100 以上のテストで調べ、**40 件以上の脆弱性**を報告しました。調べた 28 のメールクライアントのうち問題がなかったのは 3 つだけで、インターネット全体では約 32 万台のメールサーバがコマンド注入の影響を受けると見積もっています（[Poddebniak ほか, USENIX Security 2021](https://www.usenix.org/conference/usenixsecurity21/presentation/poddebniak)）。

コマンド注入の典型は、次のような形です。

```
C: STARTTLS\r\nRSET\r\n          ← 攻撃者が平文の段階で 2 行分を 1 度に送り込む
S: 220 Ready to start TLS
   ======== TLS 開始 ========
   （サーバが「RSET」を TLS の中で届いたコマンドとして処理してしまう）
```

サーバが平文の段階で読み込んだ受信バッファを、TLS に切り替えるときに**捨てずに持ち越す**と、平文で送り込まれた残りの行が、暗号化された会話の一部として扱われます。第 125 回で見たパイプライン（PIPELINING）で、複数の行をまとめて受け取れるのが普通であるため、この境目の処理を誤りやすいのです。RFC 3207 の「TLS の後は状態を捨てよ」という規則は、実装では守り切れていませんでした。

この研究の結論が表題のとおり、**提出と受信（IMAP、POP3）では STARTTLS をやめて暗黙の TLS を使うべき**、というものです。RFC 8314 の推奨と同じ向きです。一方、MTA 同士の 25 番には暗黙の TLS のポートがないので、中継は STARTTLS を使い続けるしかありません。そこで、STARTTLS を「消されたら気づける」「偽のサーバなら気づける」ようにする仕組みが必要になります。

## MTA-STS: HTTPS で方針を配る

**MTA-STS**（SMTP MTA Strict Transport Security、[RFC 8461](https://www.rfc-editor.org/rfc/rfc8461.html)、2018 年）は、受信側のドメインが「うちの MX はこの名前で、必ず TLS を話し、正規の証明書を出す」という方針を、**HTTPS で配る**仕組みです。名前のとおり、Web の HSTS に似た考え方です。

置くものは 2 つです。

```
; 1. DNS: 方針があること、方針の版
_mta-sts.example.com.  IN  TXT  "v=STSv1; id=20260928T000000Z;"

; 2. HTTPS: 方針そのもの
https://mta-sts.example.com/.well-known/mta-sts.txt
  version: STSv1
  mode: enforce
  mx: mx1.example.com
  mx: *.mx.example.com
  max_age: 604800
```

送る側の MTA は、次の順で動きます。

1. `_mta-sts.<宛先ドメイン>` の TXT を引き、`id` が手元のキャッシュと違えば方針を取り直す
2. `https://mta-sts.<宛先ドメイン>/.well-known/mta-sts.txt` を取得する。このとき **`mta-sts.<宛先ドメイン>` の証明書を Web PKI で検証し**、リダイレクトには従わない
3. MX を引き、方針の `mx:` の型に合う MX だけを使う（ワイルドカードは左端の 1 ラベルにだけ当たる）
4. 接続した MX で STARTTLS を必ず使い、**証明書が Web PKI でたどれ、SAN がその MX の名前に合う**ことを確かめる

`mode` には 3 つの値があります。

| mode | 失敗したとき |
| --- | --- |
| `enforce` | 方針に合わない MX、証明書の検証に失敗した MX、STARTTLS を話さない MX には**送らない** |
| `testing` | 報告だけして（TLS-RPT）、送ってしまってよい |
| `none` | 方針がないものとして扱う（方針を取り下げるときに使う） |

`enforce` で送れなかったメールは、すぐに諦めてはいけません。RFC 8461 は、恒久的な失敗にする前に DNS で新しい方針が出ていないかを確かめるよう求めています。

鍵になるのは 2 と 4 の組み合わせです。**攻撃者が DNS の MX を偽っても、偽の MX の名前は HTTPS で取った方針の `mx:` に載っていない**。方針そのものは HTTPS で運ばれ、`mta-sts.example.com` の正規の証明書がなければ偽れません。照合すべき名前を、**DNS ではなく Web PKI（第 102 回）で守られた経路で**手に入れたことになります。STARTTLS を消す攻撃も、方針が「必ず TLS」と言っている以上、送る側が気づいて送信をやめます。

<Callout type="warn" title="MTA-STS は初めての相手を守れない">
  MTA-STS の方針は、キャッシュして初めて効きます。
  送る側がまだ方針を持っていない最初の配送で、攻撃者が `_mta-sts` の TXT を消し、HTTPS の取得を妨げれば、送る側は「方針のないドメイン」として日和見の配送に戻ります。
  RFC 8461 自身が、送る側が**以前に方針を取得してキャッシュしている場合にしか**この攻撃は防げない、と書いています。
  HSTS の最初のアクセスと同じ、初回を信じる（TOFU、Trust On First Use）方式の限界です。
  `max_age`（最大 31557600 秒、約 1 年）を長めにとり、送る側が期限の前に取り直すことで、隙間を小さくします。
</Callout>

もう 1 つ、運用側の注意があります。方針は長くキャッシュされるので、**MX を変えるときは方針の更新が先**です。新しい MX を `mx:` に足さずに MX を切り替えると、`enforce` の方針をキャッシュしている送り手は、`max_age` が切れるまで新しい MX に送ってくれません。Microsoft の手順書も、MX を移すときはまず `mode` を `testing` にして `id` を変え、古い `max_age` が過ぎるのを待つよう指示しています（[Microsoft Learn: How SMTP DANE works](https://learn.microsoft.com/en-us/purview/how-smtp-dane-works)）。

## DANE for SMTP: DNSSEC で鍵を固定する

**DANE for SMTP**（[RFC 7672](https://www.rfc-editor.org/rfc/rfc7672.html)、2015 年）は、別の道を選びました。**MX の答えそのものを DNSSEC で守り**、そのうえで MX ホストの証明書（または鍵）を DNS の **TLSA レコード**に載せて固定します。

```
; 1. MX の答えが DNSSEC で検証できる（第 61 回）
example.com.                   IN  MX    10 mx1.example.com.

; 2. MX ホストの 25 番の TLS で使う鍵を、TLSA で宣言する
_25._tcp.mx1.example.com.      IN  TLSA  3 1 1 8593BDFC8CCC...（SHA-256）
```

TLSA の 3 つの数字は、何をどう照合するかを表します。

| 欄 | 値 | 意味 |
| --- | --- | --- |
| 証明書の使い方 | 3（DANE-EE） | サーバ自身の証明書（の鍵）と直接照合する。**認証局も有効期限も見ない** |
| | 2（DANE-TA） | このレコードの鍵を信頼の起点にして、チェーンをたどる |
| | 0、1（PKIX-TA、PKIX-EE） | Web PKI の検証と組み合わせる。**SMTP では使わない（SHOULD NOT）** |
| 照合する対象 | 1（SPKI） | 証明書全体ではなく公開鍵の部分（SubjectPublicKeyInfo。第 99 回） |
| 照合の方法 | 1（SHA2-256） | その SHA-256 |

RFC 7672 が推奨するのは `3 1 1`（DANE-EE、SPKI、SHA-256）で、次点が `2 0 1` です。0 と 1 を使わない理由は、MTA が Web ブラウザのような広い認証局の一覧を持つことを期待できないからだ、とされています。`3 1 1` を公開鍵に対して載せておけば、証明書を更新しても**鍵を変えない限り TLSA は書き換えなくてよい**のも利点です。

DANE の規則は強く、TLSA が DNSSEC で検証できる形で存在するのに、認証された TLS 接続が張れなかった場合は、**次の MX に移るか、配送を遅らせる**ことになっています（平文には戻らない）。TLSA があること自体が「必ず TLS」という方針の宣言になっているので、STARTTLS を消されても送る側は気づけます。そして TLSA の存在や中身を攻撃者が消したり偽ったりしても、DNSSEC の署名で見破れます。

MTA-STS と違って**初回から守れる**のが DANE の強みで、その代償は、宛先ドメインと MX ホストのゾーンがどちらも DNSSEC で署名され、送る側が DNSSEC を検証するリゾルバを使っている必要があることです。第 61 回で見たとおり、DNSSEC の普及には偏りがあります。

## 2 つの比較

| | MTA-STS | DANE for SMTP |
| --- | --- | --- |
| 仕様 | RFC 8461（2018） | RFC 7672（2015） |
| 信頼の根 | **Web PKI**（認証局と HTTPS） | **DNSSEC**（ルートゾーンの鍵） |
| 方針の置き場所 | `_mta-sts` の TXT と HTTPS の方針文書 | MX ホストごとの TLSA |
| 初回の配送 | 守れない（TOFU） | 守れる |
| 必要な準備 | Web サーバと証明書を 1 つ用意する | 宛先と MX のゾーンの DNSSEC、送信側の検証 |
| MX の証明書 | 認証局の証明書が要る | 自己署名でもよい（DANE-EE） |
| 変更の反映 | `max_age` の間キャッシュされる | TTL に従う |
| 失敗の報告 | TLS-RPT | TLS-RPT |

両方を置いてもかまいません。RFC 8461 は、両方を実装する送り手は **MTA-STS の検証で、失敗した DANE の検証を覆してはならない**（MUST NOT）と定めています（RFC 8461 2 節）。事業者によって選択が分かれていて、後の実験で見るとおり、Google、Microsoft（outlook.com）、Yahoo は MTA-STS を公開し、ドイツの posteo.de や mailbox.org は MTA-STS と DANE の両方を置いています。Microsoft の Exchange Online は、送信側の DANE の検証を全顧客に既定で有効にしており、受信側の DANE はドメインごとに有効にする方式で提供しています（[Microsoft Learn](https://learn.microsoft.com/en-us/purview/how-smtp-dane-works)、受信側の一般提供は [2024 年の告知](https://techcommunity.microsoft.com/blog/exchange/announcing-general-availability-of-inbound-smtp-dane-with-dnssec-for-exchange-on/4281292)）。

## TLS-RPT: 失敗を知らせてもらう

`enforce` や DANE で「送らない」と決めると、今度は**設定の誤りでメールが届かなくなったことに、受信側が気づけない**という問題が出ます。証明書の期限切れ、新しい MX の書き忘れ、TLSA の更新漏れは、受信側からは「メールが来なくなった」としか見えません。

**TLS-RPT**（SMTP TLS Reporting、[RFC 8460](https://www.rfc-editor.org/rfc/rfc8460.html)、2018 年）は、送る側に失敗の集計を送ってもらう仕組みです。

```
_smtp._tls.example.com.  IN  TXT  "v=TLSRPTv1; rua=mailto:tlsrpt@example.com"
```

送る側は、1 日（UTC の 0 時から 24 時）分を JSON にまとめ、`rua` の宛先へメールか HTTPS で送ります。報告の結果の種類には、`starttls-not-supported`、`certificate-host-mismatch`、`certificate-expired`、`validation-failure`（ここまでが TLS の交渉の失敗）、`sts-policy-fetch-error`、`dane-required`（方針に関わる失敗）などがあります。

導入の順番は、DMARC（第 131 回）と同じく段階的です。まず TLS-RPT を置き、MTA-STS を `testing` で公開して報告を読み、失敗がないことを確かめてから `enforce` に上げます。

## 経路の TLS はエンドツーエンドではない

ここまでの仕組みがすべて完璧に働いても、守られるのは**サーバとサーバの間の回線**だけです。

```
 MUA ═TLS═▶ MSA [平文] ═TLS═▶ MTA [平文] ═TLS═▶ MTA [平文] ─▶ メールボックス
            ↑                  ↑                 ↑
         各サーバの中では、メールは平文でディスクのキューに置かれる
```

| 守れるもの | 守れないもの |
| --- | --- |
| 回線上の盗聴 | 中継するサーバの管理者（や、そこへ侵入した者）が読むこと |
| （MTA-STS / DANE なら）偽のサーバへの誘導 | メールボックスに保存された中身 |
| （MTA-STS / DANE なら）STARTTLS の除去 | 中継の途中で中身を書き換えること（それは DKIM の仕事。第 130 回） |
| | 送信者が本物かどうか（SPF、DKIM、DMARC の仕事。第 129〜131 回） |

さらに、TLS を使うかどうかは**区間ごと**に決まります。自分の事業者と相手の事業者の間が TLS でも、相手が社内の別のサーバへ転送する区間が平文なら、そこで読めます。送る側が「全区間で TLS を使え」と指示する **REQUIRETLS**（[RFC 8689](https://www.rfc-editor.org/rfc/rfc8689.html)、2019 年）という拡張もありますが、MAIL FROM に付けるこの指示を、途中のすべての MTA が理解していなければ意味がありません。

<Callout type="warn" title="「TLS で送ったから、機密のメールも安全」ではない">
  経路の TLS は、封筒を運ぶトラックに鍵をかけるようなものです。
  集配所（各 MTA）では封筒は開いた状態で棚に並びます。
  中継するサーバにも読ませたくない中身は、メッセージ自体を暗号化する S/MIME や OpenPGP で守る必要があります。第 132 回で扱います。
</Callout>

## 手元で確かめる

作業は `scratchpad/work/ll-128-mail-tls/` で行いました。

### 25 番は届かない

執筆に使った回線では、外部の 25 番への接続が通りませんでした（`nc -vz gmail-smtp-in.l.google.com 25` がタイムアウトし、587 番と 465 番にはつながる）。家庭用やクラウドの回線の多くが外向きの 25 番を塞いでいるためです（第 126 回）。そこで、MX の代わりに**提出のサーバ**で STARTTLS と証明書を見ます。認証もメールの送信もせず、EHLO と STARTTLS だけで切り上げます。

### 平文の EHLO と、TLS の後の EHLO

Python の `socket` で 587 番に EHLO だけ送ると、応答はこうでした。

```
S: 220 smtp.gmail.com ESMTP ... - gsmtp
C: EHLO client.example
S: 250-smtp.gmail.com at your service, [2404:...]
S: 250-SIZE 35882577
S: 250-8BITMIME
S: 250-STARTTLS
S: 250-ENHANCEDSTATUSCODES
S: 250-PIPELINING
S: 250-CHUNKING
S: 250 SMTPUTF8
```

**`STARTTLS` はあるのに、`AUTH` がありません。** `smtplib` で STARTTLS してから EHLO し直すと、拡張の一覧が変わります。

```
before: ['8bitmime', 'chunking', 'enhancedstatuscodes', 'pipelining', 'size', 'smtputf8', 'starttls']
after:  ['8bitmime', 'auth', 'chunking', 'enhancedstatuscodes', 'pipelining', 'size', 'smtputf8']
auth:  LOGIN PLAIN XOAUTH2 PLAIN-CLIENTTOKEN OAUTHBEARER XOAUTH
TLSv1.3 TLS_AES_256_GCM_SHA384
```

TLS の後は `starttls` が消え、`auth` が現れました。平文の間はパスワードを受け付けない、という先ほどの Callout の実例です。`XOAUTH2` と `OAUTHBEARER` は第 133 回で扱う OAuth での認証です。

### 証明書を名前で確かめる

`openssl s_client` の `-starttls smtp` は、EHLO と STARTTLS を代わりにやってから TLS を始めます。

```
$ openssl s_client -starttls smtp -connect smtp.gmail.com:587 \
    -servername smtp.gmail.com -verify_return_error
depth=2 C=US, O=Google Trust Services LLC, CN=GTS Root R1
depth=1 C=US, O=Google Trust Services, CN=WR2
depth=0 CN=smtp.gmail.com
...
Negotiated TLS1.3 group: X25519MLKEM768
Verification: OK
```

チェーンの読み方は第 102 回と同じです。鍵交換に耐量子の `X25519MLKEM768` が使われているのも Web と同じです。ここで**照合する名前を別のものにする**と、検証は失敗します。

```
$ openssl s_client -starttls smtp -connect smtp.gmail.com:587 \
    -verify_hostname mail.example.com -verify_return_error
depth=0 CN=smtp.gmail.com
verify error:num=62:hostname mismatch
```

証明書はどの名前と照合するかを外から与えて初めて意味を持つ、ということです。中継の MTA が困っているのは、この `-verify_hostname` に何を渡すか決められないことでした。465 番では `-starttls` なしで、接続した直後に TLS が始まります（`openssl s_client -connect smtp.gmail.com:465`）。

### 主要なドメインの MTA-STS と TLSA

```
$ dig +short TXT _mta-sts.gmail.com
"v=STSv1; id=20190429T010101;"
$ curl -s https://mta-sts.gmail.com/.well-known/mta-sts.txt
version: STSv1
mode: enforce
mx: smtp.google.com
mx: gmail-smtp-in.l.google.com
mx: *.gmail-smtp-in.l.google.com
max_age: 86400
```

執筆時点（2026 年 9 月）で、いくつかのドメインを引いた結果を並べます。

| ドメイン | MTA-STS の mode | max_age | TLS-RPT の宛先 | MX の TLSA |
| --- | --- | --- | --- | --- |
| gmail.com | enforce | 86400（1 日） | `mailto:` | なし（NXDOMAIN） |
| outlook.com | enforce | 604800（7 日） | `https://` | なし |
| yahoo.com | **testing** | 86400 | `mailto:` | なし |
| posteo.de | enforce | 1209600（14 日） | `mailto:` | `3 1 1` が 5 件 |
| mailbox.org | enforce | 2419200（28 日） | `mailto:` | `3 1 1` |

yahoo.com が `testing` のままなのは、方針を公開していても、失敗したときに送信を止めてはいない、ということです。posteo.de の TLSA は DNSSEC で検証でき、応答に `ad`（検証済み）の印が付いています。

```
$ dig @1.1.1.1 +dnssec TLSA _25._tcp.mx01.posteo.de
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 6, ...
_25._tcp.mx01.posteo.de. 900 IN TLSA 3 1 1 13815B2C03F7BD63C54869706428442EDAB706D5B018A27575CA9891 29A196D5
...（3 1 1 がほかに 4 件と、その RRSIG）
```

1 つの MX に 5 件の TLSA があるのは、**鍵の入れ替えのために、新旧の鍵を並べて載せておく**ためと読めます（第 100 回のローテーションの考え方）。一方 gmail.com の MX の応答には `ad` がなく、DNSSEC で署名されていないので、Google の MX に DANE は使えません。Google が MTA-STS を選んだのと整合します。

### 手元で、日和見の STARTTLS と除去を再現する

最後に、手元だけで閉じた実験をします。自前の CA で `mx.ll117.test` の証明書を作り、STARTTLS を話す小さな SMTP サーバ（Python 標準ライブラリだけで 40 行ほど）と、その前に挟む**`250 STARTTLS` の行を書き換えるだけの中継**をローカルに立てます。送る側は `smtplib` で、「STARTTLS があれば使い、証明書は確かめない」という日和見の MTA の動きをまねます。（Docker の mailpit を使う予定でしたが、割り当てのポートが別の作業で使われていたため、コンテナを使わずに 1 つのスクリプトの中で完結させました。）

中継がすることは、サーバからの応答のうち `250 STARTTLS` で始まる行を `250 X-NOTHING` に置き換えるだけです。実行結果です。

```
== 1. 日和見の STARTTLS
直接つなぐ: TLS（証明書は未検証）
== 2. 途中で STARTTLS を消す
中継を挟む: 平文のまま
  サーバが受けた会話 1: 平文 ehlo sender.ll117.test / 平文 STARTTLS / TLS ehlo sender.ll117.test /
                        TLS mail from:<alice@sender.ll117.test> / TLS rcpt to:<bob@ll117.test> / TLS quit
  サーバが受けた会話 2: 平文 ehlo sender.ll117.test / 平文 mail from:<alice@sender.ll117.test> /
                        平文 rcpt to:<bob@ll117.test> / 平文 quit
== 3. 名前を決めて検証する
正しい名前: 検証成功 (mx.ll117.test)
違う名前: 検証失敗 (mx.attacker.test): Hostname mismatch, certificate is not valid for 'mx.attacker.test'.
== 4. TLSA 3 1 1 を計算して照合する
  DNS に載せる値:  _25._tcp.mx.ll117.test. IN TLSA 3 1 1 8593BDFC8CCC7941183B7BED927622CF...
  相手が出した鍵: 8593BDFC8CCC7941183B7BED927622CF... 一致
```

2 の結果が要点です。**サーバは STARTTLS を申し出ていて、送る側も TLS を使う気があったのに、1 行の書き換えだけで全部が平文になりました**。送る側からは、「この相手は TLS を話さない」という正常な状況と区別できません。サーバ側のログにも、平文の相手が来たとしか残りません。

3 は、照合する名前が決まっていれば偽物を見破れることを示しています。MTA-STS は `mx:` の一覧で、DANE は DNSSEC で守った MX で、この「決まった名前」を与えます。

4 は DANE-EE の検証そのものです。TLSA の `3 1 1` の値は、証明書から公開鍵（SPKI）を取り出して SHA-256 を取るだけで、`openssl` でも同じ値になります。

```
$ openssl x509 -in mx.crt -noout -pubkey | openssl pkey -pubin -outform DER | openssl dgst -sha256
SHA2-256(stdin)= 8593bdfc8ccc7941183b7bed927622cff57935f774b0faa1e009c0c5e1da798a
```

認証局の署名も有効期限も見ていません。**DNSSEC で守られた DNS に載っている鍵と同じ鍵か**、だけを確かめます。自己署名の証明書でも DANE なら認証できる、というのはこの意味です。

## 何と組み合わさって機能するか

| 部品 | この回での役割 | 呼び戻す回 |
| --- | --- | --- |
| TLS 1.3 | STARTTLS の後に張る暗号化の本体 | 第 104 回 |
| X.509 と信頼の連鎖 | 提出のサーバと MTA-STS の方針の配信元の検証 | 第 101 回、第 102 回 |
| 公開鍵の形式（SPKI） | TLSA `3 1 1` が照合する対象 | 第 99 回 |
| DNS の MX | 中継の接続先を決める。守られていないと名前の照合が無意味になる | 第 58 回、第 126 回 |
| DNSSEC | DANE の信頼の根。MX と TLSA の答えを守る | 第 61 回 |
| HTTPS（Web PKI） | MTA-STS の信頼の根。方針を守る | 第 102 回、第 105 回 |
| 鍵のローテーション | TLSA を新旧並べる、MTA-STS の `id` と `max_age` | 第 100 回 |
| TLS-RPT | 失敗を受信側に知らせる。これがないと enforce に上げられない | この回 |

経路の暗号化は、TLS という部品 1 つでは完結しません。**「どの相手と TLS を張るべきか」を守る別の部品**（Web PKI か DNSSEC）と組み合わさって、初めて能動的な攻撃者に耐えます。

## まとめ

- メールの暗号化は区間ごとに決まる。**提出（MUA → MSA）と中継（MTA → MTA）で事情がまったく違う**
- 提出は、利用者が接続先の名前を設定するので、Web と同じく証明書を名前で検証できる。RFC 8314 は 465 番の**暗黙の TLS**を勧める
- 中継の STARTTLS は**日和見の暗号化**で、相手が申し出れば使い、なければ平文で送る。公開された MX は STARTTLS を要求してはならない。Postfix の既定は 3.11 から `may`
- 中継の MTA が証明書を確かめないのは、照合すべき MX の名前自体が守られていない DNS から来るため。**日和見の STARTTLS が防ぐのは受け身の盗聴だけ**
- `250 STARTTLS` を消せば平文に落ちる（stripping）。平文から TLS への境目では、2021 年の研究が 40 件以上の実装の脆弱性（コマンド注入など）を報告した
- **MTA-STS** は Web PKI を信頼の根に、HTTPS で「MX の名前と、必ず TLS」という方針を配る。初回は守れない（TOFU）。MX を変えるときは方針が先
- **DANE** は DNSSEC を信頼の根に、TLSA で MX の鍵を固定する。初回から守れるが、DNSSEC が前提。SMTP では `3 1 1` が推奨
- **TLS-RPT** で失敗を報告してもらい、`testing` から `enforce` へ段階的に上げる
- どれも守るのは回線だけで、**経路の TLS はエンドツーエンドではない**。各 MTA の中ではメールは平文

ここまでで、メールを「盗み見られずに運ぶ」ことは見ました。しかし、運ばれてきたメールの差出人が本物かどうかは、まだ何も確かめていません。次の第 129 回では、その最初の手がかりである SPF が、実は利用者の見る From: ではなく、エンベロープの MAIL FROM しか見ていないことから始めます。
