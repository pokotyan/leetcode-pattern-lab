## CPU に運ばせない

ディスクから 1MB 読むとき、CPU が 1 バイトずつレジスタ経由でメモリに移していては、その間ずっと CPU が占有されます。

そこで **DMA**（Direct Memory Access）という仕組みがあります。専用のコントローラが、**CPU を介さずにデバイスとメモリの間でデータを転送します**。

```
1. CPU が DMA コントローラに指示する
   「デバイス X から、メモリの 0x1000 番地に、4096 バイト転送せよ」
2. CPU は別の仕事をする
3. DMA コントローラが転送する
4. 完了したら、DMA コントローラが割り込みを発生させる
5. CPU が割り込みハンドラで後始末をする
```

CPU が関わるのは 1 と 5 だけです。転送中は他の仕事ができます。

<Callout type="note" title="DMA とキャッシュの整合性">
  DMA はメモリを直接書き換えるため、**CPU のキャッシュには反映されません**。
  古い値がキャッシュに残っていると、転送されたデータが見えないことがあります。

  x86 ではハードウェアが整合性を保ちますが（cache-coherent DMA）、
  ARM などでは OS がキャッシュを明示的に無効化する必要があります。
  デバイスドライバを書くときに必ず出てくる注意点です。
</Callout>

## ページキャッシュ

ファイルを読むと、その内容はメモリ上の **ページキャッシュ** に保持されます。同じ場所を再び読むときは、ディスクに行きません。

```c
read(fd, buf, size);
```

1 回目はディスクから読み、ページキャッシュに載せ、そこからユーザのバッファにコピーします。2 回目はコピーだけです。数万倍速くなります。

```bash
free -h
#               total   used   free   shared  buff/cache   available
# Mem:           16Gi   4Gi    1Gi     0.5Gi       11Gi        11Gi
```

`buff/cache` がページキャッシュです。**「メモリが減っている」ように見えても問題ありません。** 必要になればすぐ解放されるので、`available` が実質的な空きです。

書き込みも同様で、まずページキャッシュに書かれ、後でまとめてディスクに書き出されます（ライトバック）。だから `write` はすぐ返ります。

<Callout type="warn" title="write が返っても、ディスクには書かれていない">
  `write` の成功は「カーネルが受け取った」という意味で、
  「ディスクに記録された」という意味ではありません。
  この時点で電源が落ちれば、データは失われます。
</Callout>

## 確実に書く

永続化を保証するには、明示的に指示する必要があります。

```c
fsync(fd);         // ファイルのデータとメタデータをディスクに書き出す
fdatasync(fd);     // データだけ（サイズが変わらないなら、こちらのほうが速い）
```

**データベースが遅く見える大きな理由がこれです。** トランザクションのコミットごとに `fsync` を呼ぶ必要があり、これは数ミリ秒かかります（SSD でも数百マイクロ秒）。

`fsync` を減らすための工夫が、各所で行われています。

- **グループコミット**：複数のトランザクションをまとめて 1 回の `fsync` で永続化する
- **WAL**（Write-Ahead Log）：ランダムな書き込みの代わりに、順次書き込みのログだけを `fsync` する
- 耐久性を緩める設定（MySQL の `innodb_flush_log_at_trx_commit=2` など）

<Callout type="warn" title="fsync の失敗を無視してはいけない">
  Linux では、`fsync` が失敗したときにページの dirty フラグがクリアされ、
  **再試行しても成功してしまう**という挙動が長らく問題になっていました
  （PostgreSQL の開発者が 2018 年に指摘し、fsyncgate と呼ばれました）。

  `fsync` がエラーを返したら、そのデータは失われたものとして扱い、
  安易に再試行せず、より上位のレベルで対処する必要があります。
</Callout>

## ディレクトリも同期が要る

ファイルを新規作成した場合、ファイルの内容を `fsync` しても、**ディレクトリのエントリはまだ書かれていない**ことがあります。

```c
int fd = open("data.tmp", O_CREAT | O_WRONLY, 0644);
write(fd, data, len);
fsync(fd);
close(fd);
rename("data.tmp", "data.txt");

int dfd = open(".", O_RDONLY);
fsync(dfd);              // ← これが必要
close(dfd);
```

`rename` を使うのは、**アトミックな置き換え**のためです。同じファイルシステム内なら、`rename` は原子的に行われます。書き込み途中のファイルが見えることがありません。「一時ファイルに書いて `rename`」というパターンは、この性質に依存しています。

## コピーを減らす

通常、ファイルをネットワークに送るときは 4 回のコピーが発生します。

```
ディスク ──DMA──▶ ページキャッシュ ──CPU──▶ ユーザのバッファ
                                              │ CPU
                                              ▼
ネットワーク ◀──DMA── ソケットバッファ ◀────────
```

**CPU によるコピーが 2 回**あります。データを加工しないなら、これは無駄です。

`sendfile` を使うと、ユーザ空間を経由せずに転送できます。

```c
sendfile(out_fd, in_fd, &offset, count);
```

さらに、対応したネットワークカードでは、ページキャッシュから直接 DMA で送出でき、**CPU のコピーが 0 回**になります。これが **ゼロコピー** です。

| 方式 | CPU コピー | コンテキストスイッチ |
| --- | --- | --- |
| `read` + `write` | 2 回 | 4 回 |
| `mmap` + `write` | 1 回 | 4 回 |
| `sendfile` | 0〜1 回 | 2 回 |
| `splice` | 0 回 | 2 回 |

nginx の静的ファイル配信、Kafka のログ転送などで使われており、スループットに大きく効きます。

## キャッシュを迂回する

大きなファイルを 1 回だけ読む場合、ページキャッシュに載せても再利用されません。それどころか、**本来キャッシュしておきたい他のデータを追い出します**。

```c
// ヒントを与える
posix_fadvise(fd, 0, 0, POSIX_FADV_DONTNEED);    // もう使わない
posix_fadvise(fd, 0, 0, POSIX_FADV_SEQUENTIAL);  // 順次読むので先読みして

// キャッシュを完全に迂回する
int fd = open("file", O_RDONLY | O_DIRECT);
```

**ダイレクト I/O**（`O_DIRECT`）は、ページキャッシュを経由せず、デバイスとユーザのバッファを直接やり取りします。

データベースが使うことがあります。自前でバッファプールを管理しているので、OS のキャッシュと二重に持つのが無駄だからです。

ただし制約が厳しく、**バッファのアドレスと転送サイズをブロックサイズに揃える**必要があります。守らないとエラーになります。

## ブロックデバイスの階層

```
アプリケーション
    ↓  read / write
ページキャッシュ
    ↓
ファイルシステム（ext4, XFS, Btrfs）
    ↓
ブロックレイヤ（I/O スケジューラ、マージ、並べ替え）
    ↓
デバイスドライバ
    ↓  DMA
物理デバイス
```

**I/O スケジューラ**は、要求を並べ替えたり結合したりします。HDD では、シーク距離を減らすための並べ替えが大きな効果を持ちました。

SSD にはシークがないため、複雑な並べ替えは不要です。むしろオーバーヘッドになります。

```bash
cat /sys/block/nvme0n1/queue/scheduler
# [none] mq-deadline kyber bfq
```

NVMe SSD では `none`（何もしない）が既定です。**ハードウェアが変わると、最適なソフトウェアの構造も変わる**という例です。

## 計測する

```bash
iostat -x 1                # デバイスごとの利用率と待ち時間
iotop                      # プロセスごとの I/O
biolatency                 # I/O のレイテンシ分布（bcc / eBPF）

# ページキャッシュの効き具合
vmstat 1                   # bi / bo が実際のディスク I/O
```

`iostat` の `%util` が 100% に近ければ、デバイスが飽和しています。`await`（平均待ち時間）が大きければ、キューが詰まっています。

## まとめ

- DMA により、CPU を介さずにデバイスとメモリの間で転送できる
- ページキャッシュが読み書きを高速化する。`buff/cache` は実質的な空き
- `write` の成功は永続化を意味しない。`fsync` が必要
- 新規作成ではディレクトリも `fsync` する。`rename` は原子的
- `sendfile` / `splice` でコピー回数を減らせる（ゼロコピー）
- `O_DIRECT` はページキャッシュを迂回する。自前でキャッシュする場合に使う
- I/O スケジューラは HDD では有効だったが、NVMe では不要
