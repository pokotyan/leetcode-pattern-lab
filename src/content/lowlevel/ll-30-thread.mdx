## 実行の流れだけを増やす

プロセスは重い。メモリ空間が丸ごと別で、情報のやり取りに手間がかかります。

**同じメモリ空間を共有したまま、実行の流れだけを増やしたい。** それがスレッドです。

「実行の流れ」に最低限必要なものは何か。

- **プログラムカウンタ**（今どこを実行しているか）
- **レジスタ**（計算の途中経過）
- **スタック**（関数の呼び出し履歴と局所変数）

これだけです。そして、それ以外はすべて共有できます。

## 共有するものと、しないもの

| スレッドごとに別 | 全スレッドで共有 |
| --- | --- |
| **スタック** | **ヒープ** |
| レジスタ、プログラムカウンタ | グローバル変数、静的変数 |
| スレッド ID | コード（text） |
| シグナルマスク | ファイルディスクリプタ |
| errno（TLS として実装） | 現在のディレクトリ |
| スレッドローカル変数 | ページテーブル（アドレス空間そのもの） |

**この表が、スレッドに関するほぼすべての性質の源です。**

- 局所変数はスタックにあるので、スレッドごとに別。安全
- グローバル変数とヒープ上のデータは共有。**同時に触ると壊れる**
- ファイルディスクリプタが共有されるので、1 つのソケットを複数スレッドから使える
- 1 つのスレッドが不正なメモリアクセスをすると、**プロセス全体が落ちる**

<Callout type="warn" title="共有は利点であり危険">
  プロセス間通信が不要になるのは大きな利点です。ポインタを渡すだけで済みます。
  同時に、**片方が壊したデータをもう片方が読む**ことも簡単に起きます。
  分離がないということは、保護もないということです。
</Callout>

## Linux では両者は同じもの

Linux のカーネルから見ると、プロセスとスレッドの区別はありません。どちらも `task_struct` です。

違いは、`clone` システムコールを呼ぶときに**何を共有すると指定したか**だけです。

```c
// プロセスを作る（何も共有しない）
clone(..., SIGCHLD);

// スレッドを作る（メモリ、ファイル、シグナルハンドラを共有）
clone(..., CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND | CLONE_THREAD);
```

`fork` も `pthread_create` も、内部では `clone` を呼んでいます。**共有の度合いを選べる連続体**であり、プロセスとスレッドはその両端に付けられた名前にすぎません。

この設計により、「メモリは共有しないがファイルディスクリプタは共有する」のような中間も作れます。コンテナの名前空間分離も、同じ `clone` のフラグで実現されています。

## コストの比較

| 操作 | おおよそのコスト |
| --- | --- |
| プロセスの生成（fork + exec） | 数百マイクロ秒〜数ミリ秒 |
| スレッドの生成 | 数十マイクロ秒 |
| プロセス間のコンテキストスイッチ | 数マイクロ秒（TLB の破棄を含む） |
| スレッド間のコンテキストスイッチ | 1 マイクロ秒程度（アドレス空間が同じ） |
| 関数呼び出し | 数ナノ秒 |

スレッドのほうが軽いとはいえ、**関数呼び出しに比べれば桁違いに重い**ことに注意が必要です。

## スレッドローカルストレージ

グローバル変数を、スレッドごとに別の実体にしたいことがあります。

```c
__thread int counter;              // GCC 拡張
thread_local int counter;          // C11 / C++11
```

代表例が `errno` です。グローバル変数に見えますが、実際にはスレッドごとに別の場所を指すマクロとして実装されています。共有されていたら、あるスレッドのエラーコードを別のスレッドが上書きしてしまいます。

実装としては、スレッドごとに専用の領域を確保し、専用のレジスタ（x86-64 では `fs` セグメントレジスタ）がそこを指します。アクセスは `fs:[offset]` の形になり、通常のグローバル変数とほぼ同じ速さです。

## 何個作ればよいか

スレッドを増やせば速くなる、という単純な話ではありません。

| 処理の性質 | 適切な数 |
| --- | --- |
| **CPU 律速**（計算が中心） | コア数と同じくらい |
| **I/O 律速**（待ちが中心） | コア数より多くてよい |

CPU 律速の処理でコア数を超えてスレッドを作っても、切り替えのコストが増えるだけです。

I/O 律速なら、待っている間に他のスレッドが動けるので、多めにしても意味があります。ただし、スレッドごとにスタック（既定で 8MB の仮想領域）が必要なので、数万スレッドは現実的ではありません。

<Callout type="tip" title="スレッドプール">
  タスクごとにスレッドを作ると、生成と破棄のコストが積み重なります。
  あらかじめ一定数のスレッドを作っておき、キューからタスクを取って処理させる方式が
  **スレッドプール**です。

  ほとんどの言語・フレームワークが標準で持っています
  （Java の `ExecutorService`、.NET の `ThreadPool`、Python の `concurrent.futures`）。
</Callout>

## 軽量スレッド

OS のスレッドは、生成にも切り替えにもカーネルの介入が必要です。もっと軽いものが欲しい。

そこで、**ランタイムが自前で管理する実行の流れ**が使われます。

| 呼び名 | 例 |
| --- | --- |
| グリーンスレッド、ゴルーチン | Go の goroutine |
| 仮想スレッド | Java 21 以降 |
| コルーチン | Kotlin、Python の async |
| 軽量プロセス | Erlang、Elixir |

数百万個作れます。スタックが小さく（Go の goroutine は初期 2KB で必要に応じて伸びる）、切り替えがユーザ空間で完結するためです。

多数の軽量スレッドを、少数の OS スレッドの上で動かす方式を **M:N モデル** と呼びます。

<Callout type="warn" title="軽量スレッドがブロックされると困る">
  軽量スレッドが OS レベルでブロックするシステムコール（同期的なファイル読み込みなど）を呼ぶと、
  **それを載せている OS スレッドごと止まります**。
  他の軽量スレッドも巻き添えになります。

  Go のランタイムはこれを検出して別の OS スレッドを用意します。
  Node.js が「ブロッキングな処理をイベントループ上で書くな」と警告するのも同じ理由です。
</Callout>

## GIL

Python（CPython）と Ruby（MRI）には、**GIL**（Global Interpreter Lock）があります。

これは「インタプリタの内部状態を触れるスレッドは、同時に 1 つだけ」という排他ロックです。結果として、**マルチスレッドにしても CPU 律速の処理は速くなりません**。

| 処理 | GIL の影響 |
| --- | --- |
| CPU 律速（計算） | **並列化されない**。マルチプロセスを使う必要がある |
| I/O 律速 | I/O 中は GIL を手放すので、**並列化される** |
| C 拡張 | 明示的に GIL を手放せば並列化される（NumPy など） |

GIL があるのは、インタプリタの実装が単純になり、シングルスレッドの性能が上がり、C 拡張が書きやすくなるからです。歴史的な選択であり、今も議論が続いています（Python 3.13 で GIL を無効にできるビルドが試験的に導入されました）。

Python で CPU 律速の処理を並列化するなら、`multiprocessing` でプロセスを分けるのが定石です。

## まとめ

- スレッドはスタック・レジスタ・PC だけを別に持ち、それ以外を共有する
- この共有が、利点（やり取りが楽）と危険（壊し合う）の両方の源
- Linux では、プロセスもスレッドも `clone` の共有フラグの違いでしかない
- スレッドローカル変数は、専用レジスタが指す領域で実現される
- CPU 律速ならコア数程度、I/O 律速なら多めでよい
- 軽量スレッドはランタイムが管理し、数百万個作れる
- Python / Ruby の GIL により、CPU 律速の処理はスレッドでは並列化されない
