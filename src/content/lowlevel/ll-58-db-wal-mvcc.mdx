## コミットの瞬間に、何を書けばよいのか

`COMMIT` が返ってきたら、その変更は電源が落ちても消えてはいけません。第 50 回で見たとおり、そのためには `fsync` でディスクまで届けるしかありません。

では、何を `fsync` すればよいのでしょうか。素直に考えると、**書き換えたページそのもの**です。しかし、これは現実的ではありません。

- 1 つのトランザクションが、テーブルのページ、主キーのインデックスのページ、セカンダリインデックスのページと、**ディスク上に散らばった何枚ものページ**を書き換える
- 1 行（100 バイト）を変えただけでも、書き出す単位はページ（PostgreSQL なら 8KB、InnoDB なら 16KB）
- 同じページを何度も書き換えるなら、そのたびに書き出すのは無駄。第 56 回のバッファプールは、まさにそれを避けるためにある

ランダムな位置に何枚ものページを書き、それぞれ `fsync` を待つ。これをコミットのたびにやっていたら、1 秒に数百件もさばけません。

## 先にログを書く

そこで、ページではなく**変更の記録**だけを書きます。

> ページをディスクに書き出す前に、そのページへの変更を記したログが、必ず先にディスクに届いていること

これが **WAL**（Write-Ahead Logging、先行書き込みログ）の約束です。コミットとは「そのトランザクションのログを末尾に追記し、`fsync` すること」になります。ページそのものは、バッファプールの中でダーティのまま置いておいて構いません。

```
      バッファプール（メモリ）                 ディスク
 ┌─────────────────────────────┐
 │ ページ 17（ダーティ）          │ ─── 後でゆっくり ──→  データファイル
 │ ページ 203（ダーティ）         │                       （ランダム書き込み）
 └─────────────────────────────┘
          │ 変更のたびに記録
          ▼
 ┌─────────────────────────────┐
 │ WAL バッファ                  │ ─── COMMIT で fsync ─→  WAL ファイル
 └─────────────────────────────┘                       （末尾への追記だけ）
```

これで 2 つのことが同時に手に入ります。

**コミットが速い。** 書くのは、末尾への短い追記だけです。ディスクは、散らばった位置への書き込みより、順番に並んだ書き込みのほうがずっと得意です（HDD ならシークが要らず、SSD でも書き込み増幅が小さい。第 52 回）。

**落ちても戻せる。** 再起動したら WAL を先頭から読み直し、データファイルに反映されていなかった変更を当て直します。データファイルがどれだけ古くても、WAL さえ残っていれば、コミット済みの状態を作り直せます。

ログの各レコードには、**LSN**（Log Sequence Number）という通し番号が付きます。各ページのヘッダには「このページに最後に反映したログの LSN」が書かれていて、回復時にはそれを見て、当て直す必要があるかを判断します。第 51 回のファイルシステムのジャーナルと、発想はまったく同じです。

## redo と undo

WAL に何を書くかは、「ページをいつ書き出してよいか」の方針で決まります。方針は 2 つの軸で表されます。

| 軸 | 選択 | 意味 |
| --- | --- | --- |
| **steal** | する | コミット前の変更を含むダーティページを、書き出してもよい |
| **force** | しない | コミット時に、変更したページを書き出さなくてもよい |

バッファプールを自由に使うには、**steal する、force しない**の組み合わせが最も都合がよい。ただしその代わりに、次の 2 種類の情報が必要になります。

- **force しない** ので、コミット済みなのにデータファイルに反映されていない変更がありうる。それを当て直すための **redo**（やり直し）情報
- **steal する** ので、未コミットの変更がデータファイルに書かれてしまっていることがある。それを取り消すための **undo**（取り消し）情報

この組み合わせで回復する方式を体系化したのが、1992 年に IBM の Mohan らが発表した **ARIES** です。多くのデータベースの回復処理は、この論文の「解析 → redo → undo」の 3 段階を下敷きにしています。

PostgreSQL と InnoDB は、ここで道が分かれます。

- **InnoDB** は **redo log** と **undo log** の両方を持つ
- **PostgreSQL** の WAL は、基本的に redo だけ。未コミットの変更がデータファイルに書かれていても、その行は「未コミットのトランザクションが作った版」として無視されるだけなので、消しに行く必要がない

なぜ PostgreSQL は undo なしで済むのか。答えは後半の MVCC にあります。

## fsync をまとめる: グループコミット

WAL で書き込みは軽くなりましたが、**コミットごとに `fsync` を 1 回**という制約は残っています。`fsync` は SSD でも数百マイクロ秒、ディスクによっては数ミリ秒かかります。1 件ずつ待っていたら、コミットの上限は 1 秒あたり数千件で頭打ちです。

そこで、同じ瞬間にコミットしようとしているトランザクションをまとめて、**1 回の `fsync` で全員分を確定させます**。これを **グループコミット** と呼びます。

```
 T1: COMMIT ─┐
 T2: COMMIT ─┼─→ WAL に 3 件ぶん追記 ─→ fsync 1 回 ─→ 3 件とも完了を返す
 T3: COMMIT ─┘
```

同時に来るコミットが多いほど、1 回の `fsync` あたりの件数が増えます。**負荷が高いときほど効率が上がる**、という珍しい性質です。

もっと速くしたければ、耐久性を少しだけ手放す設定もあります。

| 設定 | 何を諦めるか |
| --- | --- |
| PostgreSQL の `synchronous_commit = off` | `fsync` を待たずに成功を返す。落ちると**直前のごく一部のコミットが消える**が、データが壊れることはない |
| InnoDB の `innodb_flush_log_at_trx_commit = 2` | ログを OS には渡すが `fsync` は約 1 秒ごと。OS ごと落ちると最大 1 秒ぶん消える |

<Callout type="warn" title="消えることと、壊れることは違う">
  これらの設定で失われるのは「最後の数件」だけで、**データベースが矛盾した状態になるわけではありません**。
  WAL の約束（ページより先にログ）は守られたままだからです。
  一方、ディスクやファイルシステムが `fsync` に嘘をつく場合は話が別で、
  こちらは**壊れます**（第 50 回）。
</Callout>

## 半分だけ書かれたページ

WAL にはもう 1 つ落とし穴があります。**ページの書き出しそのものが、途中で止まる**場合です。

PostgreSQL のページは 8KB ですが、ファイルシステムやディスクが一度に書ける単位は 4KB であることが多い。8KB を書いている途中で電源が落ちると、**前半が新しく後半が古い**ページが残ります。これを **torn page**（破れたページ）と呼びます（[Percona](https://www.percona.com/blog/a-tale-of-two-databases-how-postgresql-and-mysql-handle-torn-pages/)）。

redo のログは「このページのこの位置をこう変えた」という差分なので、土台のページが壊れていると当て直せません。2 つのデータベースは別々の方法でこれを防ぎます。

**PostgreSQL の full page writes。** チェックポイントの後、あるページを**初めて**変更するときは、差分ではなく**ページ全体**を WAL に書きます。破れたページがあっても、WAL の中の完全なページから作り直せます。

**InnoDB の doublewrite buffer。** ダーティページをデータファイルの本来の位置に書く前に、まず専用の領域にまとめて順番に書き、`fsync` します。本来の位置への書き込みが途中で止まっても、その控えから戻せます。

どちらも「完全な写しを別の場所に 1 つ持っておく」という点で同じです。PostgreSQL はそれを WAL、つまりコミットの経路に置き、InnoDB は裏のページ書き出しの経路に置いています。

## チェックポイント: WAL を短く保つ

WAL を先頭から全部当て直すのでは、何ヶ月も動いたデータベースの再起動が終わりません。そこで定期的に **チェックポイント** を取ります。

1. その時点のダーティページを、すべてデータファイルに書き出す
2. 「この LSN より前の変更は、すべてデータファイルに反映済み」と記録する

回復は、最後のチェックポイントから始めればよくなります。それより古い WAL は、レプリケーションやバックアップに使わないなら捨てられます。

チェックポイントの間隔は、**回復時間と、平常時の書き込み量の交換**です。間隔を詰めれば回復は速いが、ダーティページを頻繁に書き出すことになり、full page writes も増えます。第 56 回で見たダーティページの書き出しと、ここで繋がります。

<Callout type="tip" title="レプリケーションも WAL でできている">
  WAL は「データベースに起きた変更の、順序付きの完全な記録」です。
  これを別のマシンに送り、同じように当て直せば、同じ状態のデータベースがもう 1 台できます。
  PostgreSQL のストリーミングレプリケーションは、まさにこれです。
  次回の NewSQL では、この「ログを複数台で揃える」ところに合意アルゴリズムが入ってきます。
</Callout>

## 読む人を待たせない: MVCC

ここからは、耐久性ではなく**同時実行**の話です。

第 37 回のロックを素直に使うなら、ある行を書き換えている間、その行を読みたい人は待つことになります。集計のような長い読み取りが走ると、その間の書き込みがすべて止まります。

**MVCC**（Multi-Version Concurrency Control、多版同時実行制御）は、これを **行の古い版を残す** ことで解決します。

- 書き込む人は、行を上書きせず**新しい版**を作る
- 読む人は、トランザクション開始時点（あるいは文の開始時点）の **スナップショット** に見えるべき版を選んで読む
- 読む人は書く人を待たず、書く人も読む人を待たない

「古い版をどこに置くか」で、実装が 2 つに分かれます。

### PostgreSQL: 行を丸ごと増やす

PostgreSQL の各行（タプル）には、隠れた列が付いています。

| 列 | 意味 |
| --- | --- |
| `xmin` | この版を作ったトランザクション ID |
| `xmax` | この版を消した（あるいは更新した）トランザクション ID。まだ生きていれば 0 |
| `ctid` | この版の物理的な位置（ページ番号, ページ内の番号） |

`UPDATE` は、**古い版の `xmax` に自分の ID を書き、新しい版を別の場所に挿入する**操作です。

```
UPDATE t SET v = 'b' WHERE id = 1;   -- トランザクション 101 が実行

 ページ 0
 ┌──────────────────────────────────────────┐
 │ (0,1)  xmin=100 xmax=101  id=1 v='a'  │ ← 古い版。101 より前のスナップショットにはまだ見える
 │ (0,2)  xmin=101 xmax=0    id=1 v='b'  │ ← 新しい版
 └──────────────────────────────────────────┘
```

どの版が見えるかは、スナップショットと `xmin` / `xmax` を突き合わせて決まります。未コミットのトランザクションが作った版は、単に見えないだけです。**だから undo が要りません。** 中断したトランザクションの版は、誰にも見えないゴミとして残るだけです。

その代わり、ゴミは誰かが片付けなければなりません。それが **VACUUM** です。どのスナップショットからも見えなくなった古い版を回収し、ページの空きとして再利用できるようにします。第 57 回で見た HOT 更新や、インデックスがヒープの位置（`ctid`）を指す構造は、この「更新するたびに行が引っ越す」性質と表裏一体です。

<Callout type="warn" title="トランザクション ID の周回">
  PostgreSQL のトランザクション ID は 32 ビットで、約 40 億で一周します。
  古い版の `xmin` を「凍結」してこの周回の影響を受けないようにするのも VACUUM の仕事で、
  これが滞ると、**データベースが新しい書き込みを拒否して止まる**ところまで行きます
  （[PostgreSQL 文書](https://www.postgresql.org/docs/current/routine-vacuuming.html)）。
  autovacuum を止めてはいけない理由の 1 つです。
</Callout>

### InnoDB: 古い版は undo log に

InnoDB は逆の方針を取ります。

- 行は**その場で**書き換える。クラスタ化インデックス（第 57 回）の葉にある行そのものが、常に最新版
- 書き換える前の値は **undo log** に書き、行からそこへのポインタ（roll pointer）を張る
- 古いスナップショットで読む人は、ポインタを辿って undo log から古い版を**組み立て直して**読む

```
 クラスタ化インデックスの葉              undo log
 ┌──────────────────────────┐      ┌──────────────────┐
 │ id=1 v='c'  roll_ptr ────┼────→ │ v='b' に戻す情報   │ ──→ │ v='a' に戻す情報 │
 └──────────────────────────┘      └──────────────────┘
```

undo log は、先ほどの「steal のための undo」と同じものです。**中断の取り消しと、古い版の読み出しに、同じ記録を使い回している**わけです。どのスナップショットからも不要になった undo は、purge という裏の処理が片付けます。

| | PostgreSQL | InnoDB |
| --- | --- | --- |
| 最新版の場所 | ヒープのどこか（更新のたびに新しい場所） | クラスタ化インデックスの葉（その場で更新） |
| 古い版の場所 | ヒープの中に並んで残る | undo log |
| 古い版を読むコスト | そのまま読める | undo を辿って組み立てる |
| 片付け | VACUUM | purge |
| 片付けが遅れると | テーブルとインデックスが膨らむ | undo が溜まり、古い版の組み立てが長くなる |

<Callout type="tip" title="長いトランザクションが、全員を遅くする">
  どちらの方式でも、古い版は「それを必要とするスナップショットが 1 つでもある限り」消せません。
  `BEGIN` したまま放置された接続や、何時間も走る分析クエリがあると、
  その間に作られた古い版がすべて溜まり続けます。
  PostgreSQL ではテーブルが膨らみ、InnoDB では undo が伸びて読み取りが遅くなります。
  **トランザクションを短く保つ**ことが、MVCC のデータベースでは性能の問題でもあります。
</Callout>

## 分離レベル: 何が見えてしまうのか

MVCC とロックを組み合わせて、データベースは **分離レベル** を提供します。レベルが低いほど速く、代わりに「他のトランザクションの影響が見えてしまう」現象が起きます。

| 現象 | 何が起きるか |
| --- | --- |
| ダーティリード | 他のトランザクションの**未コミット**の変更が見える |
| ノンリピータブルリード | 同じ行を 2 回読むと、間に他人がコミットした変更で値が変わる |
| ファントム | 同じ条件で 2 回検索すると、行が増えたり減ったりする |
| ロストアップデート | 2 人が同じ値を読んで書き戻し、片方の更新が消える |
| write skew | 2 人が別々の行を書くが、**2 人とも同じ前提を読んで判断した**ために、合わせると制約が壊れる |

既定のレベルは製品によって違います。PostgreSQL は Read Committed、InnoDB は Repeatable Read です（[PostgreSQL 文書](https://www.postgresql.org/docs/current/transaction-iso.html)、[MySQL 文書](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)）。同じ「Repeatable Read」という名前でも、中身の実装が違うので、防げる現象も完全には一致しません。

最後の write skew は、スナップショットで読むことそのものから生まれます。

```
 当直の医師が 2 人いる。「最低 1 人は当直に残る」という決まりがある。

 医師 A: SELECT count(*) FROM oncall;  → 2 人いる。自分が抜けても大丈夫
 医師 B: SELECT count(*) FROM oncall;  → 2 人いる。自分が抜けても大丈夫
 医師 A: DELETE FROM oncall WHERE name = 'A'; COMMIT;
 医師 B: DELETE FROM oncall WHERE name = 'B'; COMMIT;

 → 当直が 0 人になる
```

2 人は別々の行を消しているので、行ロックはぶつかりません。どちらも自分のスナップショットの中では正しく判断しています。これを防ぐには、**読んだものが後で変わっていないか**まで検査する Serializable が必要です。PostgreSQL は、この検査をロックではなく読み書きの依存関係の追跡で行う **SSI**（Serializable Snapshot Isolation）で Serializable を実装しています。衝突を検出したら、片方のトランザクションを失敗させて、アプリにやり直させます。

<Callout type="note" title="ロックがなくなったわけではない">
  MVCC で消えたのは「読む人と書く人の待ち合わせ」です。
  **同じ行を 2 人が書く**ときは、今でも行ロックで順番に並びます。
  `SELECT ... FOR UPDATE` は、読み取りの段階でその行ロックを先に取っておく書き方です。
  第 39 回のデッドロックは、ここでも普通に起きます。
</Callout>

## まとめ

- コミットごとにページを書き出すのは遅すぎる。代わりに、変更の記録（WAL）を末尾に追記して `fsync` する
- 約束は 1 つ。「ページをディスクに書く前に、その変更のログが先にディスクにある」
- steal / no-force の方針から、redo と undo の 2 種類の情報が必要になる。PostgreSQL は MVCC のおかげで undo を持たない
- グループコミットで、複数のコミットを 1 回の `fsync` にまとめる
- torn page は、完全なページの写しを別に持って防ぐ（full page writes / doublewrite buffer）
- チェックポイントで、回復に必要な WAL の範囲を区切る
- MVCC は古い版を残し、読む人と書く人が互いを待たないようにする。PostgreSQL はヒープに、InnoDB は undo log に古い版を置く
- 古い版は、それを見るスナップショットが消えるまで片付けられない。長いトランザクションは全員の敵
- スナップショットで読むだけでは write skew を防げない。防ぐには Serializable が要る

次は、ここまでのページ、インデックス、WAL、MVCC を **何十台ものマシンに分けて持つ** NewSQL を見ます。
