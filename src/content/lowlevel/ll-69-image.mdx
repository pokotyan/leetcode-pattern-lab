## 名前空間の中に、何を見せるのか

第 68 回で、コンテナは **名前空間 + cgroup + ファイルシステムの差し替え** だと書きました。前の 2 つはカーネルの機能で、第 68 回で中身を見ました。残るのは 3 つ目です。

Mount 名前空間を分けると、コンテナの中から見える `/` を、ホストとは別のディレクトリにできます。では、その別のディレクトリの中身はどこから来るのか。**それがイメージです。**

`/bin/sh` も `/etc/passwd` も `/usr/lib/libc.so` も、コンテナの中で見えるファイルはすべて、イメージの中に入っていたものです。カーネルだけはホストのものを使うので、イメージにカーネルは入っていません。

この回では、イメージを実際にほどいて、中に何が入っているのかを確かめます。

## イメージをほどく

`docker save` は、イメージを 1 つの tar ファイルに書き出します。手元の Docker Desktop（Docker Engine 29）で `alpine:3.20` を書き出して、展開してみます。

```bash
docker pull alpine:3.20
docker save alpine:3.20 -o alpine.tar
mkdir alpine && tar -xf alpine.tar -C alpine
```

```
alpine/
├── oci-layout
├── index.json
├── manifest.json
└── blobs/sha256/
    ├── 45e09956dc66...   JSON    1026 バイト
    ├── ab3fe4defd29...   JSON     628 バイト
    ├── 3f26bc2dec0b...   gzip  4092319 バイト
    └── ...
```

ファイル名がすべて `sha256` のハッシュ値になっています。中身は、数個の小さな JSON と、1 つの大きな gzip です。**イメージとは、これだけのものです。**

## 3 種類の部品

この構造は **OCI Image Spec**（Open Container Initiative が定めたイメージの仕様）で決まっています。Docker 以外のツール（Podman、containerd、Kubernetes）も同じ形式を読み書きします。

部品は 3 種類です。

```
  manifest（目次）
  ├── config  ─→  実行時の設定と、層の一覧
  └── layers
      ├── layer 0  ─→  tar.gz（ファイルの差分）
      ├── layer 1  ─→  tar.gz
      └── ...
```

**manifest** は目次です。展開したものを読むと、こうなっています。

```json
{
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "digest": "sha256:ab3fe4defd29ba62...",
    "size": 628
  },
  "layers": [
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "digest": "sha256:3f26bc2dec0b515f...",
      "size": 4092319
    }
  ]
}
```

中身そのものは持たず、**他の部品のハッシュ値とサイズだけ**を持っています。

**config** は、コンテナをどう起動するかの設定です。

```json
{
  "architecture": "arm64",
  "os": "linux",
  "config": {
    "Env": ["PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"],
    "Cmd": ["/bin/sh"],
    "WorkingDir": "/"
  },
  "rootfs": {
    "type": "layers",
    "diff_ids": ["sha256:88b4fba61c4c714a..."]
  },
  "history": [
    { "created_by": "ADD alpine-minirootfs-3.20.10-aarch64.tar.gz / # buildkit" },
    { "created_by": "CMD [\"/bin/sh\"]", "empty_layer": true }
  ]
}
```

環境変数、起動するコマンド、作業ディレクトリ。そして `architecture: arm64` とあります。**このイメージは arm64 の機械語が入った、arm64 専用のもの**です。この話は第 72 回で掘り下げます。

**layer** は、ファイルシステムの中身を tar でまとめ、gzip で圧縮したものです。

```bash
$ tar -tzf blobs/sha256/3f26bc2dec0b... | head
bin/
bin/arch
bin/ash
bin/busybox
bin/cat
...
```

普通の tar です。特別な形式ではありません。

## ハッシュ値が名前になっている

どの部品も、**中身の sha256 ハッシュ値**で呼ばれます。これを **digest** と呼び、`sha256:3f26bc...` のように書きます。OCI の仕様では、digest は部品のバイト列そのものに対して計算すると定められています（[OCI Image Spec: Descriptors](https://github.com/opencontainers/image-spec/blob/main/descriptor.md)）。

確かめます。

```bash
$ shasum -a 256 blobs/sha256/3f26bc2dec0b...
3f26bc2dec0b515f1c2818f6e13a8f1da1f88179a008445d4e587233386bff78

$ gunzip -c blobs/sha256/3f26bc2dec0b... | shasum -a 256
88b4fba61c4c714a2fc173ddf7e9324a257304696830bf41ad28ecc58c11c95f
```

1 つ目は、ファイル名と同じ値になりました。2 つ目の、**展開した tar のハッシュ値**は、config の `diff_ids` と同じです。manifest は圧縮後の値で層を指し、config は圧縮前の値で層を指しています。圧縮方式を変えても、中身が同じであることを確かめられるようにするためです。

名前が中身から決まる仕組みを **内容アドレス**（content addressable）と呼びます。これには 3 つの効果があります。

| 効果 | 理由 |
| --- | --- |
| **改ざんが分かる** | 取得したバイト列のハッシュ値を計算し、名前と一致しなければ壊れている |
| **重複が消える** | 中身が同じなら名前も同じ。同じベースイメージを使う 10 個のイメージでも、ベースの層は 1 つしか保存しない |
| **目次ごと固定できる** | manifest は各部品の digest を持つので、manifest の digest が同じなら、全部品が同じだと保証される |

Git がコミットやファイルをハッシュ値で管理しているのと、同じ発想です。

## タグは書き換えられる

`alpine:3.20` の `3.20` は **タグ** です。タグは、digest に付けた別名にすぎず、**あとから別の digest に付け替えられます**。実際、Alpine は 3.20 系の修正版を出すたびに、`3.20` タグを新しいイメージへ付け替えています。

```
alpine:3.20        ─→ sha256:d9e853e8...   （今日）
alpine:3.20        ─→ sha256:????????...   （来月のセキュリティ修正後）
alpine@sha256:d9e853e8...  ─→ 永遠にこの中身
```

したがって、**同じ `FROM alpine:3.20` でも、ビルドした日によって中身が違う**ことがあります。確実に同じ中身を使いたいときは、digest で指定します。

```dockerfile
FROM alpine:3.20@sha256:d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc
```

<Callout type="note" title="latest は「最新」を意味しない">
  `latest` は、タグを省略したときに補われる名前にすぎません。
  自動で最新版を指すわけではなく、誰かが `latest` という名前で push したものを指します。
  本番環境の設定で `latest` を使うと、いつ何が動いているのか分からなくなります。
</Callout>

## 1 つのタグ、複数のイメージ

`docker save` で展開した中には、JSON がもう少し多く入っていました。`index.json` から辿ると、manifest の手前に、もう 1 段の目次があります。

```bash
$ docker buildx imagetools inspect alpine:3.20
MediaType: application/vnd.oci.image.index.v1+json
Manifests:
  Platform:    linux/amd64
  Platform:    linux/arm/v6
  Platform:    linux/arm/v7
  Platform:    linux/arm64/v8
  Platform:    linux/386
  Platform:    linux/ppc64le
  Platform:    linux/riscv64
  Platform:    linux/s390x
  ...
```

**image index** と呼ばれる、manifest の一覧です。`alpine:3.20` というタグは、CPU アーキテクチャごとに別々のイメージを束ねた、この一覧を指しています。`docker pull` は、この一覧から自分の CPU に合うものを選んでいます。この仕組みは第 72 回で詳しく見ます。

## 層を重ねて 1 つに見せる

イメージの層は、それぞれが **前の層からの差分**です。Dockerfile の 1 命令が、だいたい 1 層になります。

```dockerfile
FROM alpine:3.20
RUN rm /etc/motd && echo hi > /hello
```

これをビルドして層の中身を見ると、2 つ目の層にはファイルが 3 つしかありません。

```bash
$ tar -tzvf <2 つ目の層>
drwxr-xr-x  0 0  0  0  etc/
----------  0 0  0  0  etc/.wh.motd
-rw-r--r--  0 0  0  3  hello
```

`/hello` を追加したことは、ファイルそのものが入っているので分かります。では、`/etc/motd` を消したことはどう表すのか。tar には「消した」を表す方法がありません。そこで、**`.wh.` で始まる空のファイル**を置いて「この名前は消えた」と記録します。これを **whiteout** と呼びます。

コンテナを起動するとき、これらの層を下から順に重ねて、1 つのディレクトリに見せます。Linux では **overlayfs** というファイルシステムがこれを担います。

```
  コンテナから見える /  （merged）
  ┌──────────────────────────────────────────┐
  │ /bin/sh  /etc/...  /hello   （motd はない）│
  └──────────────────────────────────────────┘
          ↑ 上から順に探し、最初に見つかったものを見せる
  ┌──────────────────────────────────────────┐
  │ upperdir: コンテナの書き込み層（最初は空） │  書ける
  ├──────────────────────────────────────────┤
  │ lowerdir: 層 1  /hello, /etc/.wh.motd      │  読み取り専用
  ├──────────────────────────────────────────┤
  │ lowerdir: 層 0  /bin, /etc/motd, ...       │  読み取り専用
  └──────────────────────────────────────────┘
```

実際に動いているコンテナの中で、`/` のマウント情報を見ると、この構造がそのまま出てきます。

```bash
$ docker run --rm alpine:3.20 grep " / " /proc/self/mountinfo
... / / rw,relatime - overlay overlay rw,
    lowerdir=/var/lib/.../snapshots/543/fs:/var/lib/.../snapshots/526/fs,
    upperdir=/var/lib/.../snapshots/.../fs, workdir=...
```

`lowerdir` にコロン区切りで層が並び、`upperdir` が 1 つあります。

## 書くときだけコピーする

イメージの層は読み取り専用です。では、コンテナの中で `/etc/hosts` を書き換えるとどうなるのか。

1. `/etc/hosts` は lowerdir にある
2. 書き込もうとした瞬間、overlayfs がファイルを **upperdir にまるごとコピー** する
3. 以降の読み書きは、upperdir のコピーに対して行われる

**第 24 回で見た copy-on-write と同じ発想**です。fork した親子がページを共有し、書いた瞬間にだけコピーしたのと同じように、コンテナは層を共有し、書いたファイルだけをコピーします。

この仕組みのおかげで、同じイメージから 100 個のコンテナを起動しても、層のファイルは 1 組しかディスクにありません。**起動が速いのも、ディスクをほとんど使わないのも、コピーしていないから**です。

一方で、単位がページではなく **ファイル** である点に注意が必要です。

<Callout type="warn" title="大きなファイルへの小さな書き込み">
  lowerdir にある 1GB のファイルの末尾に 1 バイト書くだけで、1GB のコピーが走ります。
  データベースのファイルやログのように、書き込みが多いものをコンテナの書き込み層に置くと、
  遅いうえに、コンテナを消すと一緒に消えます。
  こうしたデータは、overlayfs を通らない **ボリューム** に置きます（第 73 回）。
</Callout>

## コンテナ = イメージ + 書き込み層

ここまでをまとめると、イメージとコンテナの関係がはっきりします。

| | イメージ | コンテナ |
| --- | --- | --- |
| 実体 | 読み取り専用の層の積み重ね + config | イメージ + 書き込み層 1 枚 + 実行中のプロセス |
| 変更 | できない（digest が変わってしまう） | 書き込み層にだけ書ける |
| 共有 | 複数のコンテナで共有する | 書き込み層はコンテナごと |
| 消すと | 層が消える | 書き込み層が消える。イメージは残る |

**プログラム（実行ファイル）とプロセスの関係**に似ています。1 つの実行ファイルから複数のプロセスを起動できるように、1 つのイメージから複数のコンテナを起動できます。

<Callout type="tip" title="層は消しても小さくならない">
  層は差分の積み重ねなので、ある層で追加したファイルを、次の層で消しても、
  **最初の層にファイルは残ったまま**です。whiteout で見えなくなるだけです。

```dockerfile
RUN curl -o /tmp/big.tar.gz https://...   # 500MB の層ができる
RUN rm /tmp/big.tar.gz                    # whiteout の層が増えるだけ
```
  イメージは 500MB のままです。取得・展開・削除を 1 つの `RUN` にまとめるか、
  次回のマルチステージビルドを使います。
</Callout>

## 手元で確かめる

```bash
# 層の digest と設定を見る
docker image inspect alpine:3.20 --format '{{json .RootFS}}'
docker image inspect alpine:3.20 --format '{{json .Config}}'

# 層ごとの大きさと、どの命令で作られたか
docker history alpine:3.20

# レジストリ上の index / manifest を、pull せずに見る
docker buildx imagetools inspect alpine:3.20
docker buildx imagetools inspect alpine:3.20 --raw

# 別のツールでも同じものが見える
crane manifest alpine:3.20          # go-containerregistry
skopeo inspect docker://alpine:3.20
```

`docker save` で書き出して展開し、JSON を 1 つずつ読んでみるのが一番の近道です。数分で読み切れる量しかありません。

## まとめ

- イメージは、tar.gz の層と、それを指す JSON（manifest、config）でできている。形式は OCI Image Spec で決まっている
- 部品はすべて中身の sha256（digest）で呼ばれる。改ざん検知、重複排除、目次ごとの固定が同時に手に入る
- タグは digest に付けた別名で、付け替えられる。中身を固定したいなら digest で指定する
- 1 つのタグが、CPU アーキテクチャごとのイメージを束ねた image index を指していることが多い
- 層は差分で、削除は whiteout で表す。overlayfs が層を重ねて 1 つの `/` に見せる
- コンテナの書き込みは、ファイル単位の copy-on-write で書き込み層に入る

次は、この層を `/` に据えて、プロセスが実際に動き出すまでに、誰が何をしているのかを見ます。
