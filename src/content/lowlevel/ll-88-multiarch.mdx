## コンテナは CPU を隠さない

コンテナについては「一度作ればどこでも動く」とよく言われます。これは半分だけ正しい説明です。

第 84 回で見たとおり、コンテナは **ホストのカーネルの上で動くただのプロセス**です。仮想マシンと違い、CPU を真似る層はありません。コンテナの中のプログラムは、ホストの CPU が直接実行します。

すると、イメージに入っている実行ファイルは、**ホストの CPU が解釈できる機械語**でなければなりません。第 8 回で見たとおり、x86-64 と ARM64 は命令セットが違い、同じバイト列でも意味が通じません。

| コンテナが隠すもの | コンテナが隠さないもの |
| --- | --- |
| ファイルシステム（ライブラリ、設定） | CPU の命令セット |
| プロセス ID、ネットワーク、ホスト名 | カーネル（システムコールの番号と意味） |
| 使える CPU 時間やメモリの量 | ABI（呼び出し規約、構造体の配置） |

「どこでも動く」の「どこでも」は、**同じ CPU アーキテクチャで、Linux カーネルが動いている場所**という意味です。

## 実行ファイルの先頭を見る

同じ Alpine Linux のイメージを、アーキテクチャを指定して 2 回起動し、`/bin/busybox` の先頭 20 バイトを見てみます。

```bash
docker run --rm --platform linux/amd64 alpine:3.20 sh -c 'head -c 20 /bin/busybox | od -An -tx1'
#  7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
#  03 00 3e 00

docker run --rm --platform linux/arm64 alpine:3.20 sh -c 'head -c 20 /bin/busybox | od -An -tx1'
#  7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
#  03 00 b7 00
```

先頭の `7f 45 4c 46` は、第 30 回で見た ELF の目印（`0x7F` と `ELF`）です。その次の `02` は 64 ビット、`01` はリトルエンディアンを表します（第 3 回、第 10 回）。

違うのは最後の 2 バイトです。ここは ELF ヘッダの `e_machine` で、**この機械語がどの CPU 向けか**を表します。

| `e_machine` | CPU |
| --- | --- |
| `0x3e` | x86-64 |
| `0xb7` | AArch64（ARM64） |

名前もタグも同じ `alpine:3.20` なのに、中身は別の機械語です。この仕組みを見ていきます。

## platform という 3 つ組

イメージがどの環境向けかは、**platform** という文字列で表します。

```
linux/amd64
linux/arm64
linux/arm/v7
└┬──┘ └┬┘ └┬┘
 os   arch variant
```

| 要素 | 意味 | 例 |
| --- | --- | --- |
| os | カーネルの種類 | `linux`、`windows` |
| arch | 命令セット | `amd64`（x86-64）、`arm64`、`riscv64`、`s390x` |
| variant | 同じ arch の中の世代の違い | `arm/v6`、`arm/v7`、`amd64/v3` |

variant は、第 8 回で見た「命令セットは拡張されていく」という話に対応します。32 ビット ARM の v6 と v7 では使える命令が違い、x86-64 も v2、v3 と世代ごとに使える命令（SIMD など）が増えています。新しい命令を使うように作ったバイナリは、古い CPU では不正な命令として止まります。

## 1 つの名前に、複数の中身をぶら下げる

では `alpine:3.20` という 1 つの名前で、どうやって別々の中身を配っているのか。答えは、第 85 回で見たマニフェストの **もう 1 段上** にあります。

```
alpine:3.20
   │
   ▼
image index（どの platform 向けのマニフェストがあるかの一覧）
   ├── linux/amd64   → マニフェスト → config + レイヤ
   ├── linux/arm64   → マニフェスト → config + レイヤ
   ├── linux/arm/v7  → マニフェスト → config + レイヤ
   └── ...
```

この一覧を OCI では **image index**、Docker の古い形式では **manifest list** と呼びます。中身を覗くと、次のようになっています。

```bash
docker buildx imagetools inspect alpine:3.20
# Name:      docker.io/library/alpine:3.20
# MediaType: application/vnd.oci.image.index.v1+json
#
# Manifests:
#   Name:      docker.io/library/alpine:3.20@sha256:c64c...
#   MediaType: application/vnd.oci.image.manifest.v1+json
#   Platform:  linux/amd64
#
#   Name:      docker.io/library/alpine:3.20@sha256:3775...
#   Platform:  linux/arm/v6
#   ...
```

`docker pull` は、次の順で動きます。

1. タグを引いて、image index を取ってくる
2. **自分が動いているマシンの platform** に一致するマニフェストを選ぶ
3. そのマニフェストが指す config とレイヤだけを取ってくる

利用者は何も指定しなくても、自分の CPU に合った中身が届きます。`--platform` を付けると、2 の選択を上書きできます。

<Callout type="note" title="platform が unknown/unknown のマニフェスト">
  実際の一覧には、`Platform: unknown/unknown` のエントリも混ざっています。
  これはイメージではなく、**そのイメージがどう作られたか**（SBOM や来歴の証明）を記録した添付物です。
  image index は「platform ごとのイメージの一覧」であると同時に、
  関連する成果物をまとめてぶら下げる入れ物としても使われています。
</Callout>

index を持たず、1 つの platform 向けのマニフェストだけを持つイメージもあります。自分の手元で `docker build` しただけのイメージは、通常こちらです。

## exec format error の正体

別の CPU 向けのイメージを動かそうとすると、次のエラーに出会います。

```
exec /usr/local/bin/app: exec format error
```

これはカーネルが返すエラー `ENOEXEC` です。第 30 回で見たとおり、`execve` はファイルの先頭を見て、実行できる形式かどうかを判断します。ELF であっても、`e_machine` が自分の CPU と違えば実行できません。

典型的に起きるのは、次のような場面です。

- Apple Silicon の Mac で作ったイメージを、x86-64 のサーバに持っていった
- x86-64 でしか配布されていないイメージを、ARM のサーバ（AWS Graviton など）で動かした
- image index がなく、1 つの platform しか持たないイメージを pull した

イメージの pull 自体は成功し、**実行した瞬間に初めて失敗する**のが厄介なところです。

## 別の CPU の機械語を動かす: binfmt_misc と QEMU

では、x86-64 のマシンで ARM64 のイメージを動かす手段はないのか。あります。第 30 回で、`#!` で始まるファイルは、カーネルが別のプログラム（インタプリタ）に渡して実行すると書きました。Linux には、これを一般化した **binfmt_misc** という仕組みがあります。

```
「先頭がこのバイト列のファイルは、このプログラムに渡して実行せよ」
という規則を、カーネルに登録できる

  先頭が 7f 45 4c 46 ... b7 00（ARM64 の ELF）
    → /usr/bin/qemu-aarch64 に渡す
```

**QEMU のユーザモード**は、ARM64 の機械語を 1 命令ずつ読み、x86-64 の機械語に変換しながら実行します。第 84 回の仮想マシンとは違い、OS 全体ではなく**1 つのプロセスだけ**を翻訳します。システムコールは、引数を変換したうえでホストのカーネルにそのまま渡します。

binfmt_misc に QEMU を登録しておくと、`exec format error` になるはずだったファイルが、QEMU 経由で動くようになります。Docker Desktop はこの設定を最初から持っています（[Docker Docs](https://docs.docker.com/build/building/multi-platform/)）。Linux のサーバでは、`tonistiigi/binfmt` などのイメージを一度実行して登録するのが一般的です。

```bash
docker run --privileged --rm tonistiigi/binfmt --install all
```

<Callout type="warn" title="エミュレーションは遅い">
  命令を 1 つずつ翻訳するので、ネイティブ実行より大幅に遅くなります。
  特にコンパイルや圧縮のような計算の重い処理では、
  ビルド時間が数倍から十倍以上に延びることも珍しくありません。
  **動くことと、実用的な速度で動くことは別**です。
</Callout>

### Apple Silicon と Rosetta

Apple Silicon の Mac では、Docker Desktop が Linux の VM を動かし、その中でコンテナを動かしています。この VM の中で amd64 のバイナリを動かすとき、QEMU の代わりに Apple の **Rosetta** を使う設定があります（[Docker Blog](https://www.docker.com/blog/docker-desktop-4-25/)）。Rosetta は QEMU より大幅に速く動きます。

それでも翻訳であることに変わりはなく、次のような罠があります。

- 性能を測ると、本番の x86-64 サーバとまったく違う数字が出る
- CPU 固有の命令拡張を前提にしたバイナリは、翻訳側が対応していなければ落ちる
- `uname -m` は `x86_64` を返すが、実際に計算しているのは ARM の CPU

手元の Mac で「amd64 でも動いた」ことは、本番で同じように動く保証にはなりません。

## 複数の platform 向けにビルドする

配る側は、1 回のビルドで複数の platform 向けのイメージを作り、image index にまとめて push します。これを担うのが **buildx**（BuildKit のフロントエンド）です。

```bash
docker buildx build --platform linux/amd64,linux/arm64 -t example/app:1.0 --push .
```

中でどう作るかには、3 つの方法があります（[Docker Docs](https://docs.docker.com/build/building/multi-platform/)）。

| 方法 | やり方 | 速さ |
| --- | --- | --- |
| エミュレーション | 相手の platform の環境を QEMU で丸ごと動かしてビルドする | 遅い |
| 複数のネイティブノード | amd64 のマシンと arm64 のマシンを 1 つのビルダーとして束ねる | 速いが、マシンが要る |
| クロスコンパイル | 自分の CPU のまま、相手の CPU 向けの機械語を出力する | 速い |

### クロスコンパイルを Dockerfile に書く

コンパイラが出力する機械語の CPU は、コンパイラ自身が動いている CPU と同じである必要はありません。第 27 回で見たコンパイルの段階のうち、最後にどの命令セットのアセンブリを出すかを切り替えるだけです。これを **クロスコンパイル** と呼び、Go や Rust では特に簡単です。これを Dockerfile に組み込むと、エミュレーションを避けられます。

BuildKit は、ビルド中に次の変数を自動で与えます。

| 変数 | 意味 | 例 |
| --- | --- | --- |
| `BUILDPLATFORM` | ビルドしているマシンの platform | `linux/arm64` |
| `TARGETPLATFORM` | いま作っているイメージの platform | `linux/amd64` |
| `TARGETOS` / `TARGETARCH` | `TARGETPLATFORM` の各要素 | `linux` / `amd64` |

```dockerfile
# ビルド用のステージは、ビルドするマシンの CPU でネイティブに動かす
FROM --platform=$BUILDPLATFORM golang:1.25 AS build
ARG TARGETOS TARGETARCH
WORKDIR /src
COPY . .
# コンパイラには、作りたいイメージの CPU 向けに出力させる
RUN GOOS=$TARGETOS GOARCH=$TARGETARCH CGO_ENABLED=0 go build -o /out/app .

# 実行用のステージは、作りたいイメージの platform のものを使う
FROM gcr.io/distroless/static
COPY --from=build /out/app /app
ENTRYPOINT ["/app"]
```

ポイントは、**ステージごとに platform が違う**ことです。

```
--platform linux/amd64,linux/arm64 でビルドすると:

  build ステージ   … どちらの場合も linux/arm64（手元の Mac）でネイティブに動く
                     GOARCH だけが amd64 / arm64 と変わる
  最終ステージ     … linux/amd64 と linux/arm64 の 2 つを作る
                     COPY するだけなので、エミュレーションの負担はほぼない
```

重い処理（コンパイル）はすべてネイティブで走り、相手の platform では何も実行しません。

<Callout type="tip" title="CGO_ENABLED=0 の意味">
  Go でも C のライブラリを呼ぶ（cgo を使う）と、C のクロスコンパイラと、
  相手の CPU 向けの C ライブラリが必要になります。
  第 76 回で見た FFI の境界が、ここでも手間を増やします。
  C への依存を切って静的リンクすれば（第 29 回）、Go のコンパイラだけで完結します。
</Callout>

### CI でネイティブに作る

クロスコンパイルが難しい言語（C の拡張を多く含む Python や Ruby など）では、それぞれの CPU のマシンでネイティブにビルドする方が確実です。GitHub Actions では、公開リポジトリ向けに ARM64 の Linux ランナー（`ubuntu-24.04-arm`）が 2025 年 8 月に正式に提供されました（[GitHub Changelog](https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/)）。amd64 と arm64 のジョブを並べて走らせ、最後に image index にまとめる、という構成が取れます。

## Compose で platform を固定する

Compose でも、サービスごとに platform を指定できます。

```yaml
services:
  legacy-db:
    image: example/old-db:5.7
    platform: linux/amd64   # arm64 版が配布されていない
```

amd64 版しかないイメージを Apple Silicon で使うときに必要になります。ただし前述のとおり、中身はエミュレーションで動いています。遅い、あるいは不可解に落ちるときは、**まず platform を疑う**のが近道です。

```bash
# いま動いているコンテナが、どの platform のイメージか
docker inspect --format '{{.Platform}}' <コンテナ>
docker image inspect --format '{{.Os}}/{{.Architecture}}' <イメージ>
```

## まとめ

- コンテナはカーネルと CPU を隠さない。イメージの中身はホストの CPU が直接実行する機械語
- ELF ヘッダの `e_machine` が、どの CPU 向けかを表す
- platform は os / arch / variant の 3 つ組
- image index が platform ごとのマニフェストを束ね、pull 時に自分の platform のものが選ばれる
- `exec format error` は、`execve` が知らない形式を拒否したときのエラー
- binfmt_misc と QEMU で別の CPU の機械語も動くが、遅い。Rosetta は速いが本番と同じではない
- 複数 platform のビルドは、エミュレーション、ネイティブノード、クロスコンパイルの 3 通り
- `FROM --platform=$BUILDPLATFORM` と `TARGETARCH` で、重い処理をネイティブのまま済ませる
