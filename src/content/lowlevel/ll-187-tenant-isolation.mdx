## 境界を越えると、別の会社のデータ

SaaS では、1 つのシステムが何百、何千という顧客企業（**テナント**）を同時に相手にします。利用者 A が利用者 B の文書を読めてしまうのは認可の不具合ですが、**テナント A の利用者がテナント B の行を読めてしまう**のは、それより一段重い事故です。漏れた先は別の会社で、契約と法令の問題になります。

第 131 回では、認可の判定を作る部品の 1 つとして PostgreSQL の行単位のセキュリティ（RLS）を短く見ました。この回は、テナントの境界そのものを主題にします。

1. そもそもテナントをどう分けるか（silo / pool / bridge）
2. 境界はどこで越えられるか（DB の `WHERE` だけではない）
3. DB 側で強制する RLS を、本番で**効き続ける**形にするには何に気をつけるか
4. 越境を、人の注意ではなくテストで見つけるにはどうするか

## 分け方: silo / pool / bridge

AWS の SaaS Lens は、テナントの分け方を 3 つに分類しています（[AWS Well-Architected SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html)）。

| 型 | 何を分けるか | 境界を守るもの | 主な代償 |
| --- | --- | --- | --- |
| **silo** | テナントごとに専用の資源（DB、場合によってはアカウントやクラスタごと） | 接続先そのもの。別の DB には `WHERE` を書き忘れても届かない | テナント数に比例して運用と費用が増える。スキーマ変更を全テナントに配る仕組みが要る |
| **pool** | すべての資源を共有し、行やキーに `tenant_id` を持たせる | アプリの条件付けと、DB の RLS などの強制 | 境界が**コードと設定**にしかない。1 か所の書き忘れが全テナントに効く |
| **bridge** | サービスや層ごとに silo と pool を混ぜる | 層ごとに上のどちらか | どの層がどちらかを把握し続ける必要がある |

silo は境界が物理的なので強く、pool は安く速く育てられます。現実の SaaS は、規制の厳しい顧客や大口の顧客だけ silo にし、それ以外を pool にする bridge 型が多くなります。

この回の後半は、境界が最も壊れやすい **pool 型**を前提にします。silo でも、識別基盤や運用ツール、集計基盤は共有されていることが多く、そこでは同じ問題が起きます。

## 越境が起きる場所

「`WHERE tenant_id = ?` を付ける」だけで済むなら話は簡単です。実際には、テナントの区別が**抜け落ちうる場所**は DB のクエリの外にもたくさんあります。OWASP の Multi Tenant Security Cheat Sheet も、キャッシュ、キュー、ログ、ファイルの置き場所をそれぞれ取り上げています（[OWASP Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)）。

| 場所 | 越境の形 | 典型的な原因 |
| --- | --- | --- |
| API の ID 指定 | `GET /orders/201` で他社の注文が返る（**IDOR / BOLA**） | ID で引いた後、持ち主のテナントを確かめていない |
| キャッシュ | テナント A の結果がテナント B に返る | キャッシュのキーが `orders:list:page1` のようにテナントを含まない |
| 検索インデックス | 全文検索で他社の文書がヒットする | DB とは別の索引で、クエリにテナントの絞り込みを付け忘れる |
| 非同期ジョブ | ジョブが別のテナントの文脈で動く | キューのメッセージにテナントを入れていない、またはワーカーが前のジョブの文脈を引き継ぐ |
| 集計・分析 | ダッシュボードの合計に他社の数字が混ざる | 集計用のビューやバッチが特権ロールで動く |
| ログ・エラー通知 | 他社の個人情報が、別の顧客向けのサポート画面やエラー通知に出る | ログにテナントの区別がない、または共有の画面に生のログを出す |
| ファイルの置き場所 | 署名付き URL や推測可能なパスで他社のファイルが取れる | オブジェクトのキーにテナントを含めず、URL を発行する前に認可していない |

OWASP API Security Top 10 の API1（BOLA）は、オブジェクトの ID を書き換えるだけで他人のデータに届く問題を、一覧の 1 番目に挙げています。対策として「**すべての関数で**、ログインした利用者がその記録に対する操作を行えるかを確かめる」ことを求めています（[OWASP API1:2023](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization)）。

キャッシュについては、Cheat Sheet が「値や認可がテナントで変わるキャッシュのキーには、すべてテナントの識別子を含める」と書いています。キューについては、受け取ったワーカーが**テナントの文脈を張り直し、改めて認可する**ことを求めています。どちらも、「上流で確かめたから下流は大丈夫」という前提を捨てる、という同じ考え方です。

<Callout type="note" title="テナント ID は利用者から受け取らない">
  第 131 回の原則 3 のとおり、テナント ID はリクエストの本文やクエリ文字列ではなく、
  検証済みのトークンやセッションから取ります。`?tenant=2` や `X-Tenant-Id` ヘッダを信じると、
  どれほど DB 側で強制しても、**強制に使う値そのもの**を相手が選べることになります。
</Callout>

## 実験の環境

この回の実験は、次の環境で行いました。

| 項目 | バージョン |
| --- | --- |
| OS | macOS（Darwin 25.2.0、arm64） |
| Docker | 29.4.0 |
| PostgreSQL | 17.11（`postgres:17`、コンテナ名 `ll179-pg`） |
| Node | v22.23.3（`node:22-alpine`） |
| node-postgres（`pg`） | 8.23.1 |

ロールを 3 つ作ります。役割ごとにロールを分けることが、この後の話の前提になります。

| ロール | 役割 | 属性 |
| --- | --- | --- |
| `owner_role` | テーブルを作る（マイグレーション用） | 一般 |
| `app` | アプリケーションが接続に使う | 一般 |
| `ops` | 運用・調査用 | `BYPASSRLS` |

```sql
CREATE ROLE owner_role LOGIN PASSWORD 'pw';
CREATE ROLE app LOGIN PASSWORD 'pw';
CREATE ROLE ops LOGIN PASSWORD 'pw' BYPASSRLS;
GRANT CREATE ON SCHEMA public TO owner_role;

SET ROLE owner_role;
CREATE TABLE tenants (id int PRIMARY KEY, name text NOT NULL);
CREATE TABLE orders (
  id int PRIMARY KEY,
  tenant_id int NOT NULL REFERENCES tenants(id),
  item text NOT NULL,
  amount int NOT NULL
);
INSERT INTO tenants VALUES (1, 'acme'), (2, 'globex');
INSERT INTO orders VALUES
  (101, 1, 'ねじ', 1200),
  (102, 1, 'ばね', 800),
  (201, 2, '歯車', 50000);
GRANT SELECT, INSERT, UPDATE, DELETE ON orders, tenants TO app, ops;
```

acme（テナント 1）に 2 件、globex（テナント 2）に 1 件の注文があります。

## 手元で確かめる 1: WHERE を書き忘れると

まず RLS を付けない状態で、アプリのロール `app` から読みます。

```
SELECT id, tenant_id, item, amount FROM orders WHERE tenant_id = 1;
 id  | tenant_id | item | amount
-----+-----------+------+--------
 101 |         1 | ねじ |   1200
 102 |         1 | ばね |    800
(2 rows)

SELECT sum(amount) FROM orders;
  sum
-------
 52000
(1 row)

SELECT id, tenant_id, item FROM orders WHERE id = 201;
 id  | tenant_id | item
-----+-----------+------
 201 |         2 | 歯車
(1 row)
```

1 つ目は正しく書いた一覧です。2 つ目は、集計の画面で `WHERE` を書き忘れた例で、acme の画面に **globex の 50000 円が足された合計**が出ます。3 つ目は ID を直接指定した例で、ID さえ分かれば他社の行が返ります。

どちらも、SQL としては何も間違っていません。**DB は、このクエリがどのテナントのためのものかを知らない**からです。境界がアプリのコードにしかない限り、書き忘れはそのまま漏洩になります。

## DB に境界を教える: Row Level Security

PostgreSQL の RLS は、テーブルにポリシーを付け、条件に合う行だけを読み書きの対象にします。テナント ID は、**接続ごとの設定変数**（`app.tenant_id` のような独自の名前の設定）に入れてポリシーから読みます。

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::int)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::int);
```

`USING` は**見える行**（`SELECT`、`UPDATE` と `DELETE` の対象）を、`WITH CHECK` は**書き込める行**（`INSERT` や `UPDATE` の後の値）を決めます。テナントを設定して、さっきと同じことを試します。

```
SET app.tenant_id = '1';

SELECT id, tenant_id, item FROM orders;
 id  | tenant_id | item
-----+-----------+------
 101 |         1 | ねじ
 102 |         1 | ばね
(2 rows)

SELECT sum(amount) FROM orders;
 sum
------
 2000
(1 row)

SELECT id, item FROM orders WHERE id = 201;
(0 rows)

UPDATE orders SET amount = 0 WHERE id = 201;
UPDATE 0

INSERT INTO orders VALUES (202, 2, '紛れ込み', 1);
ERROR:  new row violates row-level security policy for table "orders"

UPDATE orders SET tenant_id = 2 WHERE id = 101;
ERROR:  new row violates row-level security policy for table "orders"
```

`WHERE` を書かない集計も 2000 円になり、ID を直接指定しても 0 行です。他社の行の更新は `UPDATE 0` で、エラーにすらなりません（見えない行は、存在しないのと同じ扱いです）。他社の ID で行を作ることも、自社の行を他社へ移すことも、`WITH CHECK` が拒みます。

### 計画にポリシーが足されている

RLS は特別な検査をしているわけではありません。**クエリの計画に、ポリシーの式が条件として足されている**だけです。`EXPLAIN` で見えます。

```
EXPLAIN (COSTS OFF) SELECT id, item FROM orders WHERE id = 201;
                                            QUERY PLAN
---------------------------------------------------------------------------------------------------
 Index Scan using orders_pkey on orders
   Index Cond: (id = 201)
   Filter: (tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::integer)

EXPLAIN (COSTS OFF) SELECT sum(amount) FROM orders;
                                               QUERY PLAN
---------------------------------------------------------------------------------------------------------
 Aggregate
   ->  Seq Scan on orders
         Filter: (tenant_id = (NULLIF(current_setting('app.tenant_id'::text, true), ''::text))::integer)
```

（式の形は、次の節で書き換えた後のポリシーのものです。）同じ集計を、RLS の対象外のスーパーユーザで `EXPLAIN` すると `Filter` の行がありません。

```
 Aggregate
   ->  Seq Scan on orders
```

ここから 2 つのことが分かります。1 つは、**性能の考え方は普通の `WHERE` と同じ**だということです。`tenant_id` を先頭に含む索引がなければ、テナントで絞る条件は第 82 回で見た索引を使えず、テーブル全体を読みます。pool 型では、主キー以外の索引も `(tenant_id, ...)` の形にするのが基本です。もう 1 つは、ポリシーの式の中で使う関数は、行ごとに評価されうるということです。重い副問い合わせをポリシーに書くと、すべてのクエリが重くなります。

## テナントが設定されていないとき

アプリがテナントを設定し忘れたら、何が起きるべきでしょうか。最初のポリシーのまま、新しい接続で試します。

```
SELECT count(*) FROM orders;
ERROR:  unrecognized configuration parameter "app.tenant_id"
```

`current_setting` は、設定が存在しなければエラーにします。第 2 引数の `missing_ok` を `true` にすると、代わりに NULL を返します（[PostgreSQL System Administration Functions](https://www.postgresql.org/docs/current/functions-admin.html)）。

ここで落とし穴が 1 つあります。**一度その接続で設定したことがあると、設定は「存在しない」ではなく「空文字列」になります**。

```
BEGIN;
SET LOCAL app.tenant_id = '1';
SELECT count(*) FROM orders;      → 2
COMMIT;

SELECT current_setting('app.tenant_id', true) IS NULL AS is_null,
       quote_literal(current_setting('app.tenant_id', true)) AS value;
 is_null | value
---------+-------
 f       | ''

SELECT count(*) FROM orders;
ERROR:  invalid input syntax for type integer: ""
```

トランザクションが終わって `SET LOCAL` の値は消えましたが、変数そのものは空文字列として残り、`::int` の変換で失敗しています。未設定の状態が「NULL」と「空文字列」の 2 通りあるわけです。両方を NULL に揃えて、**どちらでも 0 行**になるようにポリシーを書き直します。

```sql
DROP POLICY tenant_isolation ON orders;
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::int)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::int);
```

```
SELECT count(*) FROM orders;            → 0   （一度も設定していない接続）
BEGIN; SET LOCAL app.tenant_id = '1';
SELECT count(*) FROM orders;            → 2
COMMIT;
SELECT count(*) FROM orders;            → 0   （空文字列が残った接続）
```

`tenant_id = NULL` は真にならないので、行は 1 つも見えません。

<Callout type="tip" title="エラーにするか、0 行にするか">
  どちらも**閉じた側に倒れて**いるので、他社の行は漏れません。違いは気づきやすさです。
  エラーなら設定し忘れがすぐ表に出ますが、空文字列の扱いのように意図しない形で失敗することがあります。
  0 行なら安定しますが、「なぜか一覧が空」という不具合として静かに現れます。
  0 行にする場合は、アプリ側で「テナント未設定のままクエリを発行した」ことをログや計測に出しておくと、両方の利点を得られます。
  いずれにしても、未設定のときに**全行が見える**書き方（`OR current_setting(...) IS NULL` のような逃げ道）だけは避けてください。
</Callout>

## 手元で確かめる 2: 誰には効かないのか

RLS を有効にしても、すべてのロールに効くわけではありません。PostgreSQL の文書は、**スーパーユーザと `BYPASSRLS` 属性を持つロールは常に RLS を迂回し、テーブルの所有者も通常は迂回する**と書いています（[PostgreSQL 5.9](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)）。3 つとも確かめます。

まず、テーブルを作った `owner_role` です。テナントを設定していないのに全件が見えます。

```
SELECT current_user, count(*) FROM orders;
 current_user | count
--------------+-------
 owner_role   |     3

ALTER TABLE orders FORCE ROW LEVEL SECURITY;

SELECT current_user, count(*) FROM orders;
 current_user | count
--------------+-------
 owner_role   |     0

SET app.tenant_id = '2';
SELECT current_user, count(*) FROM orders;
 current_user | count
--------------+-------
 owner_role   |     1
```

`FORCE ROW LEVEL SECURITY` を付けると、所有者にもポリシーが掛かります。マイグレーションで使ったロールのままアプリを動かしている構成では、**`ENABLE` だけではポリシーが 1 行も効いていない**ことになります。

次に、`BYPASSRLS` を持つ `ops` と、スーパーユーザの `postgres` です。`FORCE` を付けた後でも全件が見えます。

```
SELECT current_user, count(*) FROM orders;
 current_user | count
--------------+-------
 ops          |     3

SELECT current_user, count(*) FROM orders;
 current_user | count
--------------+-------
 postgres     |     3

SELECT rolname, rolsuper, rolbypassrls FROM pg_roles
 WHERE rolname IN ('postgres','owner_role','app','ops') ORDER BY rolname;
  rolname   | rolsuper | rolbypassrls
------------+----------+--------------
 app        | f        | f
 ops        | f        | t
 owner_role | f        | f
 postgres   | t        | t
```

`FORCE` は所有者のためのもので、`BYPASSRLS` とスーパーユーザには関係しません。

| 接続に使うロール | `ENABLE` のみ | `ENABLE` + `FORCE` |
| --- | --- | --- |
| 一般のロール（`app`） | 効く | 効く |
| テーブルの所有者（`owner_role`） | **効かない** | 効く |
| `BYPASSRLS`（`ops`） | **効かない** | **効かない** |
| スーパーユーザ（`postgres`） | **効かない** | **効かない** |

### 迂回していることに気づく: row_security = off

`BYPASSRLS` のロールでも、**意図せず迂回している**ことに気づきたい場面があります。設定 `row_security` を `off` にすると、迂回する権限のないロールでは、ポリシーで結果が絞られるクエリが**エラーになります**（[PostgreSQL 5.9](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)）。

```
-- app で
SET row_security = off;
SELECT count(*) FROM orders;
ERROR:  query would be affected by row-level security policy for table "orders"

-- postgres で
SET row_security = off;
SELECT count(*) FROM orders;   → 3
```

バックアップや全テナントにまたがる移行のように「全行を見るつもり」の処理で `row_security = off` を付けておくと、誤って一般のロールで動いたときに、黙って一部の行だけを処理する代わりに止まります。

### ビューは所有者の権限で読む

もう 1 つ、見落とされやすい迂回路があります。**ビュー**です。既定では、ビューが参照するテーブルへのアクセスは**ビューの所有者**の権限で判定され、RLS もビューの所有者のポリシーが適用されます（[PostgreSQL CREATE VIEW](https://www.postgresql.org/docs/current/sql-createview.html)）。

集計用のビューをスーパーユーザで作り、`app` に読ませます。

```sql
-- postgres で
CREATE VIEW order_summary AS
  SELECT tenant_id, count(*) AS n, sum(amount) AS total FROM orders GROUP BY tenant_id;
GRANT SELECT ON order_summary TO app;
```

```
-- app で
SET app.tenant_id = '1';
SELECT * FROM order_summary ORDER BY tenant_id;
 tenant_id | n | total
-----------+---+-------
         1 | 2 |  2000
         2 | 1 | 50000
```

acme の画面で globex の集計が見えています。PostgreSQL 15 以降は、ビューに `security_invoker` を付けると、**クエリを実行した利用者**の権限とポリシーで読むようになります。

```
-- postgres で
ALTER VIEW order_summary SET (security_invoker = true);

-- app で
SET app.tenant_id = '1';
SELECT * FROM order_summary ORDER BY tenant_id;
 tenant_id | n | total
-----------+---+-------
         1 | 2 |  2000
```

前の節の表で「集計・分析」を越境の起きる場所に挙げたのは、このためです。**テーブルに RLS を付けても、その手前に別の権限で読む層があれば、そこが穴になります**。同じことは `SECURITY DEFINER` の関数にも言えます。

### 制約は RLS を迂回する

最後に、RLS では隠しきれないものがあります。テナント 1 として、他社の注文と同じ ID で行を作ってみます。

```
SET app.tenant_id = '1';
INSERT INTO orders VALUES (201, 1, '探り', 1);
ERROR:  duplicate key value violates unique constraint "orders_pkey"

SELECT id FROM orders WHERE id = 201;
(0 rows)
```

`SELECT` では見えない 201 番が、主キーの重複というエラーで**存在することだけは分かります**。PostgreSQL の文書も、一意制約や主キー、外部キーの検査は整合性を保つために常に RLS を迂回するので、**この経路での情報の漏れ**（covert channel）に注意するよう書いています（[PostgreSQL 5.9](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)）。

漏れるのは中身ではなく存在だけですが、連番の ID ならテナント全体の注文数の推測に使えます。外から決められる ID を主キーにしない、ID を推測しにくい値（UUID など）にする、一意制約を `(tenant_id, 外部の番号)` の組にする、といった設計で狭められます。

## 接続プールと、残る設定

ここまでは `psql` で 1 回ずつ接続していました。実際のアプリは**接続プール**を使い、1 本の DB 接続を多くのリクエストで使い回します。そして `SET` で入れた値は、第 83 回で見たトランザクションとは関係なく、**接続（セッション）が続く限り残ります**。PostgreSQL の文書のとおり、`SET`（`SET SESSION`）はトランザクションがコミットされればセッションの終わりまで有効で、`SET LOCAL` は**コミットしてもしなくても、トランザクションの終わりまで**しか効きません（[PostgreSQL SET](https://www.postgresql.org/docs/current/sql-set.html)）。

これを、Node の `pg` のプールで確かめます。プールの大きさを 1 にして、2 つのリクエストが必ず同じ接続を使うようにします。

```js
const pool = new pg.Pool({ host: 'll179-pg', user: 'app', password: 'pw', database: 'postgres', max: 1 })

async function handleBad(tenantId) {
  const c = await pool.connect()
  try {
    if (tenantId !== null) await c.query(`SET app.tenant_id = '${tenantId}'`)
    const r = await c.query('SELECT pg_backend_pid() AS pid, count(*)::int AS n, array_agg(id ORDER BY id) AS ids FROM orders')
    return r.rows[0]
  } finally {
    c.release()
  }
}
```

リクエスト 1 はテナント 2 として処理し、リクエスト 2 はテナントを設定せずに処理します（ログイン前の画面や、テナントを設定し忘れた非同期ジョブを想定しています）。リクエスト 2 は 0 行になるはずです。

```
[bad] request 1 (tenant 2): { pid: 168, n: 1, ids: [ 201 ] }
[bad] request 2 (tenant unset): { pid: 168, n: 1, ids: [ 201 ] }
```

`pid` が同じなので、同じ DB 接続です。リクエスト 2 は、**前のリクエストのテナント 2 として**globex の注文を読んでいます。RLS は正しく動いています。正しく動いた結果、前の利用者の身元で行を返しているのです。

`SET LOCAL` に相当する `set_config(..., true)` を、トランザクションの中で使うように直します。

```js
async function handleGood(tenantId) {
  const c = await pool.connect()
  try {
    await c.query('BEGIN')
    if (tenantId !== null) await c.query("SELECT set_config('app.tenant_id', $1, true)", [String(tenantId)])
    const r = await c.query('SELECT pg_backend_pid() AS pid, count(*)::int AS n, array_agg(id ORDER BY id) AS ids FROM orders')
    await c.query('COMMIT')
    return r.rows[0]
  } catch (e) {
    await c.query('ROLLBACK')
    throw e
  } finally {
    c.release()
  }
}
```

```
[good] request 1 (tenant 2): { pid: 170, n: 1, ids: [ 201 ] }
[good] request 2 (tenant unset): { pid: 170, n: 0, ids: null }
```

同じ接続でも、リクエスト 2 は 0 行になりました。値はトランザクションと一緒に消え、残った空文字列は前の節のポリシーで NULL として扱われます。

`set_config` を使う理由はもう 1 つあります。`SET` の値の位置にはバインド変数（`$1`）を書けないので、`handleBad` のように文字列を組み立てることになり、テナント ID の出どころによっては SQL インジェクションの入口になります。`set_config(name, value, is_local)` は普通の関数なので値をパラメータで渡せ、第 3 引数を `true` にすれば現在のトランザクションの中だけで効きます（[PostgreSQL System Administration Functions](https://www.postgresql.org/docs/current/functions-admin.html)）。

<Callout type="warn" title="プールの種類で、残り方が変わる">
  アプリの中のプール（node-postgres など）は、接続を返すときに何も初期化しないものが多く、上の実験のとおり `SET` が残ります。
  PgBouncer のセッションモードは、接続を次のクライアントに渡す前に `server_reset_query`（既定は `DISCARD ALL`）を送ります。
  一方、トランザクションモードではこのクエリは送られず、トランザクションが終わるたびに接続がプールに戻ります
  （[PgBouncer config](https://www.pgbouncer.org/config.html)）。PgBouncer の機能表も、トランザクションモードでは `SET` / `RESET` を使えないとしています（[PgBouncer features](https://www.pgbouncer.org/features.html)）。
  つまりトランザクションモードでは、**自分の `SET` が他のクライアントのトランザクションに残る**ことがありえます。
  どのプールでも安全なのは、**テナントの設定を必ずトランザクションの中で `SET LOCAL` / `set_config(..., true)` で行い、そのトランザクションの中だけでクエリを発行する**形です。
</Callout>

この形にすると、副作用として「テナントを設定せずにクエリを発行できる経路」をコードの構造で減らせます。たとえば、DB へのアクセスを `withTenant(tenantId, async (tx) => { ... })` のような関数からしか行えないようにし、その中で `BEGIN` と `set_config` と `COMMIT` を済ませます。テナントを渡さずに DB を触る方法そのものを用意しない、という考え方です。

## 層を重ねる

RLS は強力ですが、最後の網です。テナントの境界は、何枚かを重ねて守るのが普通です。

| 層 | 何を守るか | 破れる原因 |
| --- | --- | --- |
| トークンからテナントを取る（第 130 回） | 強制に使う値が正しいこと | 利用者の入力からテナントを取る |
| アプリの条件付け（`WHERE tenant_id = ?`、リポジトリ層で必ず付ける） | クエリの意図。索引も効く | 書き忘れ、生 SQL、集計 |
| DB の RLS | 書き忘れても行が漏れない | 所有者・`BYPASSRLS`・スーパーユーザで接続、ビュー、設定の残り |
| DB 以外の資源のキー（キャッシュ、索引、オブジェクトのパス） | DB の外の越境 | キーにテナントがない。RLS はここまで届かない |
| テナントごとの暗号鍵（第 108 回） | 万一読まれても復号できない | 鍵の選択をアプリが誤る |

2 番目と 3 番目は、片方があれば十分に見えて、実は**役割が違います**。アプリの `WHERE` は意図を表し、索引を効かせます。RLS は、意図を書き忘れたときの保険です。RLS だけに頼ると、アプリのコードを読んでもテナントの絞り込みが見えず、DB の外の資源（キャッシュのキーなど）を作るときに考慮が抜けやすくなります。

## 越境を検出するテスト

境界が**効き続けている**ことは、レビューの注意ではなく機械で確かめます。OWASP API1 も、認可の仕組みを評価するテストを書き、それが失敗する変更をデプロイしないよう求めています（[OWASP API1:2023](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization)）。テストは大きく 3 種類に分けられます。

### 1. 2 つのテナントで、相手のものを触る

テストのデータには、必ず**テナントを 2 つ以上**用意します。1 テナントだけのテストでは、`WHERE` を書き忘れても結果が変わらないので、越境を見つけられません。

```
テナント A の利用者で:
  一覧の API          → B の ID が 1 つも含まれない
  B の ID で取得      → 404（403 ではなく。存在を教えない）
  B の ID で更新・削除 → 404 で、B の行は変わっていない
  本文の tenant_id を B にして作成 → 拒否、または A として作られる
  集計・検索・エクスポート → B の値が混ざらない
```

API の一覧からエンドポイントを列挙し、すべてに対して「他テナントの ID を差し込む」テストを自動で作ると、新しいエンドポイントの追加でも抜けにくくなります。

### 2. 同じ接続で、テナントを切り替える

この回の接続プールの実験そのものです。プールの大きさを 1 にし、テナント A のリクエスト、テナント未設定のリクエスト、テナント B のリクエストを順に流して、それぞれが自分の行だけを見ることを確かめます。非同期ジョブのワーカーにも同じテストを書きます。

### 3. スキーマを検査する

テーブルを追加したときに RLS を付け忘れる問題は、DB のカタログを読めば見つかります。`tenant_id` 列を持つのに RLS が無効、`FORCE` が付いていない、ポリシーがない、のいずれかに当てはまるテーブルを列挙します。手元で、RLS を付けずに `invoices` を足して確かめました。

```sql
SELECT c.relname, c.relrowsecurity AS rls, c.relforcerowsecurity AS force,
       (SELECT count(*) FROM pg_policy p WHERE p.polrelid = c.oid) AS policies
FROM pg_class c
JOIN pg_attribute a ON a.attrelid = c.oid AND a.attname = 'tenant_id' AND NOT a.attisdropped
JOIN pg_namespace n ON n.oid = c.relnamespace AND n.nspname = 'public'
WHERE c.relkind IN ('r', 'p')
ORDER BY c.relname;
```

```
 relname  | rls | force | policies
----------+-----+-------+----------
 invoices | f   | f     |        0
 orders   | t   | t     |        1
```

この結果に `rls = f` の行が 1 つでもあれば CI を失敗させます。同じように、アプリの接続に使うロールが `rolsuper` でも `rolbypassrls` でもなく、どのテーブルの所有者でもないこと、ビューに `security_invoker` が付いていることも、カタログへの問い合わせで検査できます。第 184 回で見た「設定を基準と比べ続ける」考え方を、DB のスキーマに当てはめたものです。

<Callout type="note" title="バックアップと復元も境界をまたぐ">
  OWASP の Cheat Sheet は、2 つのテナントを含むバックアップから 1 テナントだけを復元し、
  もう一方の記録やオブジェクトが含まれていないことを確かめるテストを挙げています（[OWASP Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)）。
  「テナントの解約時にデータを消す」「1 テナントの分だけ書き出す」といった運用の処理も、
  多くは特権ロールで動くので、RLS には守られていません。
</Callout>

実験が終わったら、コンテナを止めます。

```bash
docker stop ll179-pg
```

次の回は、境界のもう 1 つの典型である**ファイル**を扱います。利用者がアップロードしたファイルを受け取り、加工し、配り返す処理には、パスの解決、圧縮、XML、外部の URL からの取り込みと、ここまでとは違う形の越境が潜んでいます。

## まとめ

- テナントの分け方には silo（専用の資源）、pool（共有して `tenant_id` で区別）、bridge（混在）がある。pool では境界がコードと設定にしかない
- 越境は DB の `WHERE` だけでなく、ID の直接指定（BOLA）、キャッシュのキー、検索インデックス、非同期ジョブ、集計、ログ、ファイルの置き場所で起きる。テナント ID は検証済みのトークンから取る
- PostgreSQL の RLS は、ポリシーの式をクエリの条件として足す。`USING` で見える行を、`WITH CHECK` で書ける行を決める。`tenant_id` を先頭にした索引が要る
- 未設定の変数は「存在しない」と「空文字列」の 2 通りがある。`NULLIF(current_setting(..., true), '')` で揃え、未設定なら 0 行にする。全行を見せる逃げ道は書かない
- テーブルの所有者は `FORCE ROW LEVEL SECURITY` を付けるまで迂回する。`BYPASSRLS` とスーパーユーザは常に迂回する。既定のビューは所有者の権限で読むので `security_invoker` を付ける。一意制約や外部キーの検査は RLS を迂回し、存在が漏れる
- `SET` はセッションに残り、接続プールで次のリクエストに引き継がれる。トランザクションの中で `SET LOCAL` / `set_config(..., true)` を使い、値はパラメータで渡す
- 越境は、2 テナントで相手のものを触るテスト、同じ接続でテナントを切り替えるテスト、カタログを読んで RLS の付け忘れや特権ロールを見つける検査で、継続的に確かめる
