## 信用できないプログラムを、毎日実行している

ページを開くたびに、ブラウザは**どこの誰が書いたか分からない JavaScript** を実行します。広告の枠にも、埋め込まれた動画にも、それぞれ別の誰かのコードが入っています。

しかもそのコードを解釈するのは、HTML、CSS、画像、フォント、動画を扱う、数千万行の C++ でできたエンジンです。どこかにメモリ破壊のバグが残っている、と考えるのが現実的です。第 23 回で見たとおり、C や C++ のメモリ破壊は、攻撃者にとっては任意のコードを動かす入口になります。

つまりブラウザは、

- **互いに信用しない多数のプログラム**を同時に動かし
- それぞれが**落ちても、乗っ取られても**、他と OS 全体を守る

必要があります。これは OS がプロセスに対してやっていることと同じ問題です。そしてブラウザは、実際に **OS の道具をそのまま使って**これを解いています。

## 1 つのプロセスだった頃

初期のブラウザは、すべてのタブを 1 つのプロセスで動かしていました。

- 1 つのタブがクラッシュすると、**全部のタブが道連れ**になる
- 1 つのタブが重い処理を始めると、他のタブも固まる
- エンジンのバグを突いて乗っ取られると、**ブラウザの権限で**ファイルもネットワークも自由に触れる

2008 年に登場した Chrome は、最初から**複数のプロセス**に分ける設計を取りました。OS と直接やり取りする「ブラウザカーネル」と、制限された権限でサンドボックスの中で動く「レンダリングエンジン」を、別の保護領域に置くという考え方です（[Multi-process Architecture](https://www.chromium.org/developers/design-documents/multi-process-architecture/)）。

## プロセスの役割分担

現在の Chromium 系のブラウザでは、おおよそ次のように分かれています。

```
┌──────────────────── ブラウザプロセス ────────────────────┐
│  UI（タブ、アドレスバー）、全体の管理、権限を持つ唯一の場所     │
└───┬───────────────┬────────────────┬────────────────┬────┘
    │ IPC           │ IPC            │ IPC            │ IPC
┌───┴────┐    ┌─────┴─────┐    ┌─────┴─────┐    ┌─────┴─────┐
│レンダラ   │    │ レンダラ    │    │  GPU      │    │ネットワーク │
│site A   │    │ site B    │    │ プロセス    │    │サービス    │
│HTML/CSS │    │ HTML/CSS  │    │ 描画命令を │    │ 接続と     │
│JS       │    │ JS        │    │ GPU に渡す │    │ キャッシュ │
└─────────┘    └───────────┘    └───────────┘    └───────────┘
  サンドボックス    サンドボックス
```

| プロセス | 何をするか | 権限 |
| --- | --- | --- |
| ブラウザ | UI、タブとプロセスの管理、ファイルや Cookie の管理 | 強い。ユーザの権限で動く |
| レンダラ | HTML と CSS の解析、レイアウト、JavaScript の実行 | 最も弱い。ほぼ何もできない |
| GPU | 描画命令を GPU のドライバに渡す | ドライバに触れる分だけ |
| ネットワーク | 接続、TLS、HTTP キャッシュ | ネットワークに触れる分だけ |

**最も危険なもの（外から来たデータを解析し、外から来たコードを動かすもの）に、最も弱い権限を与える**。これが分け方の原則です。第 43 回で見た「必要な権限だけを持たせる」を、プロセスの単位で徹底しています。

GPU のドライバやネットワークの処理を分けているのも同じ理由です。GPU のドライバはクラッシュしやすく、それでブラウザ全体が落ちるのは困ります。

## レンダラを閉じ込める

プロセスを分けただけでは、乗っ取られたレンダラが自分で `open` を呼べば、ファイルは読めてしまいます。第 33 回で見たとおり、プロセスはユーザの権限をそのまま持つからです。

そこでレンダラは、**サンドボックス**の中で起動されます。Linux の Chromium では、仕組みを重ねて使っています（[Linux Sandboxing](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/linux/sandboxing.md)）。

- **名前空間**で、ファイルシステムや他のプロセスを見えなくする（第 84 回）
- **seccomp-bpf** で、呼べるシステムコールを絞る（第 93 回）。レンダラには Chrome 23 から使われている

第 93 回のコンテナの安全で見た道具と、ほぼ同じ組み合わせです。**ブラウザのタブは、とても厳しく絞られたコンテナのようなもの**だと言えます。

では、レンダラが画像を読み込みたいときはどうするのか。自分では取りに行けないので、**ブラウザプロセスに頼みます**。

```
レンダラ:  「この URL の画像がほしい」 ──IPC──→  ブラウザ / ネットワーク
                                                  権限を確かめて取得
レンダラ:  ←──IPC── バイト列だけ受け取る
```

レンダラが持っているのは、頼むための**通信路**だけです。頼まれた側が「このサイトにこれを渡してよいか」を判断します。第 78 回で見た Wasm のケイパビリティ（渡されたものしか触れない）と同じ設計で、**危険な部分と判断する部分を別のプロセスに置く**ことで、判断を乗っ取られにくくしています。

<Callout type="note" title="プロセス間通信は、共有しない並行">
  ブラウザの各プロセスは、メモリを共有せず、メッセージを送り合って協調します。
  第 40 回で見た「共有しない」並行の、大規模な実例です。
  大きな画像や描画結果のように、コピーすると重いものだけは、
  共有メモリの領域を作ってそこに置き、場所だけをメッセージで渡します。
</Callout>

## Spectre が変えたこと: サイト分離

ここまでの分離は、「乗っ取られても OS を守る」ためのものでした。しかし 2018 年、別の種類の脅威がはっきりします。

第 11 回で見た **Spectre** です。投機実行の痕跡をキャッシュの時間差で読むことで、**同じプロセスのアドレス空間にあるデータなら、プログラムの境界を無視して読み出せる**可能性があります。JavaScript から、しかもバグを突く必要すらなく。

それまでのブラウザは、ページの中の iframe や、同じタブで開いた別のサイトを、**同じレンダラプロセス**に入れることがありました。サイト間の境界（同一オリジンポリシー）は、レンダラの中のプログラムが守っていたのです。Spectre は、その境界がプロセスの中では当てにならないことを示しました。

答えは、**サイトが違えばプロセスを分ける**ことでした。これを **サイト分離** と呼びます。

- 別のサイトへ移動すると、タブのレンダラプロセスが切り替わる
- 別のサイトの iframe は、親のページとは**別のプロセス**で描く（アウトオブプロセス iframe）

Chrome はデスクトップでこれを Chrome 67（2018 年）から既定にしました（[Site Isolation](https://www.chromium.org/Home/chromium-security/site-isolation/)）。Firefox も 2021 年から同じ方向の分離を進めています（[Mozilla Security Blog](https://blog.mozilla.org/security/2021/05/18/introducing-site-isolation-in-firefox/)）。

**アドレス空間が別なら、投機実行でも読めない**。第 19 回で見た仮想メモリの分離が、最後の防壁として働いています。

<Callout type="warn" title="プロセスを増やすと、メモリが増える">
  サイトごとにプロセスを分ければ、レンダラの数だけエンジンの実行環境が必要になります。
  サイト分離はメモリの使用量を増やしました。
  メモリの少ない端末では、分離の範囲を絞ったり、プロセスの数に上限を設けたりしています。
  **分離の強さとメモリは交換の関係**です。第 84 回で見た、仮想マシンとコンテナの間の交換と同じ形です。
</Callout>

## 時計を粗くする: クロスオリジン分離

Spectre のような攻撃には、**細かい時計**が必要です。キャッシュに当たったかどうかの差は、ナノ秒の単位だからです。

そこでブラウザは、`performance.now()` のような時計の精度を落とし、スレッド間で共有できる `SharedArrayBuffer`（これを使うと自作の細かい時計が作れる）を一時期無効にしました。

いまは、ページが「他のオリジンのものを、相手の許可なく自分のプロセスに取り込まない」と宣言したとき（COOP と COEP という 2 つのヘッダ）に限って、`SharedArrayBuffer` と細かい時計を使わせています。デスクトップの Chrome では 92 からこの条件が必須になりました（[Chrome for Developers](https://developer.chrome.com/blog/enabling-shared-array-buffer)）。

**強い道具は、隔離を約束した者にだけ渡す**。これも権限の分割の一種です。

## 自分の環境で見る

- Chrome のタスクマネージャ（メニューの「その他のツール」→「タスク マネージャ」）を開くと、タブ、拡張機能、GPU、ネットワークなどが**別々のプロセス**として並び、それぞれのメモリと CPU が見えます
- 別のサイトの iframe を含むページを開くと、その iframe が別のプロセスとして表示されます

```bash
# Linux / macOS で、ブラウザのプロセスの数を数える
ps aux | grep -c '[C]hrome'
ps aux | grep '[C]hrome' | grep -o -- '--type=[a-z-]*' | sort | uniq -c
```

`--type=renderer`、`--type=gpu-process`、`--type=utility` といった起動引数で、役割ごとに別のプロセスになっていることが分かります。

## まとめ

- ブラウザは、互いに信用しない多数のプログラムを同時に動かす。OS と同じ問題を、OS の道具で解いている
- ブラウザ、レンダラ、GPU、ネットワークのプロセスに分け、最も危険なレンダラに最も弱い権限を与える
- レンダラは名前空間と seccomp-bpf で閉じ込められ、外の資源はブラウザプロセスに頼んで受け取る
- プロセスどうしはメモリを共有せず、メッセージで協調する
- Spectre は、プロセスの中の境界が当てにならないことを示した。サイト分離は、サイトごとにアドレス空間を分けて守る
- 細かい時計と `SharedArrayBuffer` は、クロスオリジン分離を約束したページにだけ許される
- 分離を強めるほどメモリが増える。ここにも交換がある
