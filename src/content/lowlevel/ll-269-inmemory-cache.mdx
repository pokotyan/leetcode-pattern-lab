## 往復を減らす、その先

第 268 回では、データベースとの往復そのものを安くしました。接続を使い回し、プリペアドステートメントの往復を減らし、要らないトランザクションを外しました。それでも往復は往復で、1 回ごとにネットワークとデータベースの CPU を使います。

この回では、**往復をしない**という選択肢を見ます。変わらないデータ、めったに変わらないデータを、アプリケーションのプロセスのメモリに持っておき、データベースに問い合わせずに返します。

第 15 回では CPU のキャッシュを見ました。小さく速い場所に、遠くて遅い場所の写しを置くという考え方は同じです。そして CPU のキャッシュが複数のコアの間で写しを一致させるために無効化の通信をしていたのと同じく、アプリケーションのキャッシュにも、**写しが複数あると一致させる仕事が要る**という問題がついて回ります。CPU はそれをハードウェアがやってくれますが、アプリケーションでは自分で書きます。

| 節 | 問い |
| --- | --- |
| 何を持つか | どんなデータならメモリに持ってよいか |
| 実測（1） | マスタの参照をメモリに移すと何が変わるか |
| 並行に読む | 複数のゴルーチンから安全に読む方法と、その費用 |
| 捨てる | 変わったときにどう捨てるか。バージョンをキーに入れる |
| 実測（2） | 2 つのプロセスで、片方の更新がもう片方に見えるか |
| 再起動と /initialize | メモリの中身はいつ消え、いつ消さなければならないか |

## 何をメモリに持つか

ISUCON の講評に繰り返し出てくるのは、次のようなデータです。

| 種類 | 例 | 変わるとき |
| --- | --- | --- |
| 定数に近いマスタ | ISUCON9 予選のカテゴリ（43 件） | 変わらない |
| 運用で変わるマスタ | ISUCON12 本選のゲームのマスタ | 管理者の更新のとき |
| 一度書いたら変わらない行 | 終了した科目の総合点、作成後のアイコン | 変わらない |
| 頻繁に読まれる小さな表 | ISUCON13 の users、themes | 利用者の操作のとき |

ISUCON9 予選の講評は、カテゴリについて次のように書いています（[講評](https://isucon.net/archives/53789931.html)）。

> カテゴリについては更新がありませんでしたので、ソースコードに直接書いたチームが多かったと思われます。

更新が無いと分かっているなら、データベースから読むことさえやめて、コードに書いてしまえます。起動時に一度読み込んでも同じことです。

ISUCON9 本選では、優勝した白金動物園の rosylilly が、時刻の記録に「マスタテーブルから引いてるデータ取得をメモリ取得に」と書いています（[参加記](https://rosylilly.hatenablog.com/entry/2019/10/07/020627)）。一方でこの回の講評は、何でもメモリに載せられるわけではないことを強調しています（[講評](https://isucon.net/archives/53916974.html)）。

> 今回は競技用マシンに搭載されているメモリが1GBと低めに設定されているため、何も考えず全部メモリに載せると容易に搭載されているメモリを食い潰してしまうため、力技で解決することは難しいのも特徴です。

> 変動しない情報はメモリに載せることもしつつ、全ては乗り切らないのでメモリだけでは解決しません。

メモリに持つ候補を選ぶときの基準をまとめておきます。

- **読まれる回数に比べて、変わる回数が十分少ない。** 変わるたびに捨てる仕事が発生するので、書き込みが多いものは割に合いません。
- **小さい。** 全件を持っても、プロセスのメモリとガベージコレクタ（第 26 回）の負担が許容できる大きさです。
- **変わったことを、自分が知る手段がある。** 更新が自分のプロセスを通るか、どこかに更新の印が残ります。これが無いものは、第 270 回の「古くてよい時間」の考え方で扱います。

## 手元で確かめる（1）：マスタの参照をメモリに移す

ISUCON9 予選の一覧ページを小さくした形で比べます。商品 5 万件、カテゴリ 43 件（親 6 件、子 37 件）の表を MySQL に作り、新着 48 件を取って、各商品にカテゴリ名と親カテゴリ名を付けて返します。

環境は Apple M1 Pro / macOS 26.2、Docker 29.4.0 の上の MySQL 8.0.46、Go 1.24.6、go-sql-driver/mysql v1.9.3 です。Docker Desktop のポート転送は 1 回の往復に数ミリ秒かかることがあったため、負荷をかけるプログラムは Linux 向けにビルドし、MySQL のコンテナとネットワークを共有するコンテナの中から `127.0.0.1:3306` に接続しました。

3 つの書き方を比べます。

| 名前 | 書き方 | 1 ページあたりのクエリ |
| --- | --- | --- |
| `db` | 商品を 1 回で取り、各商品のカテゴリと親カテゴリを 1 件ずつ引く | 1 ＋ 48 × 2 = 97 |
| `join` | カテゴリの表を 2 回 JOIN して 1 回で取る | 1 |
| `mem` | 起動時にカテゴリを map に読み込み、商品だけ 1 回で取る | 1 |

`mem` の要点は次のとおりです。

```go
cats := map[int]category{}
rows, _ := db.Query("SELECT id, parent_id, name FROM categories")
for rows.Next() {
	var c category
	rows.Scan(&c.ID, &c.ParentID, &c.Name)
	cats[c.ID] = c
}
// 以後、カテゴリは cats[id] で引く。起動後に書き換えないので、ロックは要らない
```

1 本の接続で 5 秒ずつ、3 周測りました。`queries/page` は、MySQL の `Questions`（受け付けた文の数）の増分をページ数で割ったものです。

```text

mode=join c=1 pages=6360 pages/s=1272 p50=0.54ms p99=4.60ms  queries/page=1.0
mode=mem  c=1 pages=9893 pages/s=1979 p50=0.37ms p99=2.53ms  queries/page=1.0
mode=db   c=1 pages=556  pages/s=111  p50=7.66ms p99=25.15ms queries/page=97.0
mode=join c=1 pages=8459 pages/s=1692 p50=0.44ms p99=3.22ms  queries/page=1.0
mode=mem  c=1 pages=6240 pages/s=1248 p50=0.47ms p99=5.32ms  queries/page=1.0
mode=db   c=1 pages=467  pages/s=93   p50=7.81ms p99=72.32ms queries/page=97.0
mode=join c=1 pages=7168 pages/s=1434 p50=0.50ms p99=3.79ms  queries/page=1.0
mode=mem  c=1 pages=9118 pages/s=1824 p50=0.41ms p99=2.91ms  queries/page=1.0
```

- `db` は 1 ページに 97 回の往復をし、中央値で 7.5〜7.8 ミリ秒かかっています。往復 1 回あたり約 80 マイクロ秒で、同じマシンの中の通信でもこれだけ積み上がります。
- `join` と `mem` はどちらも 1 回の往復で、中央値は 0.4〜0.5 ミリ秒です。`db` の約 15 倍の速さです。
- `join` と `mem` の差は、3 周のうち 2 周で `mem` が速いものの、1 周では逆転しており、この負荷では揺れの範囲です。

この実験から言えるのは、**効いたのは「往復が 97 回から 1 回になったこと」で、それは JOIN でもメモリでも得られる**ということです。メモリに持つことの追加の利点は、データベースが JOIN をしなくて済むことと、カテゴリの表を読むためのバッファプールやロックに関わらなくなることです。データベースの CPU が詰まっている場面（ISUCON ではよくあります）では、この差が効いてきます。

同じ実験を 16 並列でも 3 周しました。

```text

mode=join c=16 pages=1991  pages/s=398  p50=6.27ms   p99=1308.52ms
mode=mem  c=16 pages=11966 pages/s=2393 p50=4.34ms   p99=40.47ms
mode=db   c=16 pages=526   pages/s=105  p50=129.42ms p99=548.79ms
```

この時間帯は同じマシンで他の負荷も動いており（`uptime` の load average が 60〜130）、数字は大きく揺れました。それでも、`db` が最も遅く最も揺れること、`mem` が 3 周とも毎秒 1,600 ページ以上を保ったことは読み取れます。往復の多い書き方ほど、混んだ環境で悪化しやすいということです。

<Callout type="note" title="N+1 の消し方との関係">
  `db` の書き方は、第 267 回で見た N+1 そのものです。第 267 回では JOIN と IN でまとめる方法を見ました。
  マスタのように小さく変わらない表なら、まとめる代わりにメモリに持つという選択肢が加わります。
  JOIN をやめて表を分けて読むと、片方だけをメモリから引けるようになります。
  ISUCON13 で 2 位になった織時屋（traP）は、JOIN していたクエリをばらして users のキャッシュを効かせたと書いています（[参加記](https://trap.jp/post/2049/)）。
</Callout>

## 複数のゴルーチンから読む

Web アプリケーションは、要求ごとに別のゴルーチン（やスレッド）で動きます。同じ map を複数のゴルーチンから読み書きするなら、同期が要ります。Go の map は、読むだけなら複数のゴルーチンから同時に読めますが、**誰か 1 人でも書くなら、すべての読み書きを同期させなければなりません**。

起動時に読み込んで二度と書き換えないなら、同期は不要です。上の `mem` がこれにあたります。問題は、**読みながら書き換える**場合です。選択肢は 4 つあります。

| 方式 | 読み | 書き |
| --- | --- | --- |
| `map` ＋ `sync.Mutex` | 毎回ロックを取る。読む人同士も待ち合う | ロックを取って書く |
| `map` ＋ `sync.RWMutex` | 読み用のロック。読む人同士は待ち合わない | 書き用のロック。全員の読みが終わるのを待つ |
| `sync.Map` | ロックを取らずに読める作り | 内部で調整 |
| 丸ごと差し替え（コピーオンライト） | `atomic.Pointer` から今の map を取り、ロックなしで読む | map を丸ごと複製して書き換え、ポインタを差し替える |

`sync.Map` の説明は、どんな場面向けかを明記しています（[sync.Map](https://pkg.go.dev/sync#Map)）。

> The Map type is optimized for two common use cases: (1) when the entry for a given key is only ever written once but read many times, as in caches that only grow, or (2) when multiple goroutines read, write, and overwrite entries for disjoint sets of keys. In these two cases, use of a Map may significantly reduce lock contention compared to a Go map paired with a separate [Mutex] or [RWMutex].

（Map は 2 つのよくある使い方に向けて最適化されている。(1) あるキーの値が一度だけ書かれ、何度も読まれる場合。大きくなる一方のキャッシュがこれにあたる。(2) 複数のゴルーチンが、互いに重ならないキーの集まりを読み書きする場合。この 2 つでは、Map を使うと、map と Mutex や RWMutex の組み合わせに比べてロックの競合を大きく減らせることがある。）

ISUCON11 本選で優勝した fujiwara組の参加記には、「1行だけ DB を引くような部分をオンメモリキャッシュ化 (メモリになければDBを見てメモリ(sync.Map)に載せる」という作業が挙がっています（[参加記](https://sfujiwara.hatenablog.com/entry/isucon11-final)）。無ければ読んで載せる、という使い方は、説明の (1) に当てはまります。

なお、Go 1.24 で `sync.Map` の実装は入れ替わっています。リリースノートは次のように書いています（[Go 1.24 Release Notes](https://go.dev/doc/go1.24)）。

> The implementation of sync.Map has been changed, improving performance, particularly for map modifications.

### 4 つの方式を測る

1,000 件の利用者を入れた 4 種類のキャッシュに対し、`b.RunParallel` で並行に読みました。読むだけの場合と、100 回に 1 回書く場合の 2 通りです。`-cpu 1,8` で、1 コアと 8 コアのそれぞれで 3 回ずつ測っています。数値は 1 回の操作あたりの時間です（短いほど速い）。

```text
BenchmarkReadOnly/Mutex-8           129.0 ns/op   132.3 ns/op   138.6 ns/op
BenchmarkReadOnly/RWMutex-8          47.79 ns/op   43.20 ns/op   41.23 ns/op
BenchmarkReadOnly/SyncMap-8           5.856 ns/op   6.340 ns/op   4.301 ns/op
BenchmarkReadOnly/CopyOnWrite-8       3.155 ns/op   3.094 ns/op   3.267 ns/op
BenchmarkWrite1pct/Mutex-8          110.1 ns/op   111.4 ns/op   103.0 ns/op
BenchmarkWrite1pct/RWMutex-8         39.99 ns/op   39.38 ns/op   38.84 ns/op
BenchmarkWrite1pct/SyncMap-8         11.71 ns/op   10.52 ns/op   12.60 ns/op
BenchmarkWrite1pct/CopyOnWrite-8    394.4 ns/op   366.6 ns/op   848.4 ns/op
```

（3 回分を 1 行に並べ直しています。）1 コアの結果は、読むだけで Mutex が 57〜64 ns、RWMutex が 51〜95 ns、sync.Map が 20〜55 ns、丸ごと差し替えが 7.8〜10.7 ns でした。同じマシンで他の負荷が動いていたため、1 コアの値は大きく揺れています。

- **8 コアで読むだけなら、ロックを取らない 2 つが桁違いに速い。** Mutex は 1 コアのときより遅くなっています。8 つのコアが 1 つのロックを取り合い、ロックの入ったキャッシュラインがコアの間を行き来するからです（第 15 回の無効化の通信）。RWMutex も、読み用のロックの計数を書き換えるので、同じ問題を小さく抱えています。
- **100 回に 1 回書くと、丸ごと差し替えは最も遅くなる。** 書くたびに 1,000 件の map を複製するからです。読むだけなら最速だった方式が、書き込みが 1% 混ざるだけで逆転します。
- **sync.Map は、どちらの場合も安定して速い。** 書き込みが混ざっても 10〜13 ns に収まりました。

ただし、この差が問題になるのは 1 回の要求でキャッシュを数千回引くような場合です。1 回の要求で数回引くだけなら、Mutex の 130 ns も、データベースへの 1 往復（上の実験で約 80 マイクロ秒）の 600 分の 1 にすぎません。**最初は読みやすい `map` ＋ `RWMutex` で書き、プロファイル（第 265 回）でロックが上位に出たら替える**、で十分です。

<Callout type="warn" title="キャッシュから取り出したものを書き換えない">
  map の値にポインタやスライスを入れていると、取り出した側がその中身を書き換えたとき、
  他のゴルーチンが読んでいる最中のデータが変わります。ロックが守るのは map の構造だけです。
  キャッシュに入れたものは書き換えない約束にするか、取り出すときに複製します。
  Go なら `go test -race` や `go build -race` で、この種の競合を見つけられます。
</Callout>

## 変わったときに捨てる

運用で変わるマスタは、変わったときに捨てなければなりません。ISUCON12 本選では、ベンチマークの途中で 1 回だけ管理者がマスタを更新するシナリオがありました。講評は、マスタの扱いについて次のように書いています（[講評](https://isucon.net/archives/56959385.html)）。

> 改善ポイントとしては、マスターテーブルのデータは、全てキャッシュに入れる想定でした。

> しかし、マスター更新処理が実際には発生するので、パージ処理をきちんと作る必要があります。

> いくつか方法がありますが、キャッシューのキーにマスターバージョンのプレフィックスをつけてキャッシュする手法が、パージ漏れを無くす意味でも、有効な手法だと考えています。

捨て方には大きく 2 つあります。

| 方式 | やり方 | 漏れの起きやすさ |
| --- | --- | --- |
| 個別に消す | 更新した処理が、関係するキーを `Delete` する | 関係するキーを 1 つでも書き忘れると古いまま |
| バージョンをキーに入れる | 更新のたびにバージョンを上げ、キーを `版:id` にする | 古い版のキーは二度と引かれない |

バージョンをキーに入れる方式は、**消さない**ことで漏れを無くします。更新のたびにバージョンが変わるので、古いエントリは誰にも引かれなくなります。消す処理を書かなくてよいので、どのキーが関係するかを考えなくて済みます。そのかわり、古い版のエントリはメモリに残り続けるので、版が上がったときにまとめて捨てるか、大きさに上限を付けます。

そして、この方式にはもう 1 つの利点があります。バージョンを**共有の場所**に置けば、**他のプロセスの更新**にも気づけることです。次の実験で確かめます。

## 手元で確かめる（2）：2 つのプロセス

同じプログラムを 2 つ起動し（A と B）、同じ MySQL を見させます。利用者の名前を `sync.Map` にキャッシュし、無ければデータベースから読んで載せます。名前の更新は A に送ります。

素朴な実装（`naive`）では、更新した A は自分のキャッシュからそのキーを消します。

```go
tx.Exec("UPDATE users SET name = ? WHERE id = ?", name, id)
tx.Commit()
cache.Delete(strconv.Itoa(id))
```

結果は次のとおりです。応答の末尾は、どのキーで引いたか、メモリとデータベースのどちらから返したかです。

```text
$ curl -s 'A/user?id=42'
user-42 key=42 (db)
$ curl -s 'B/user?id=42'
user-42 key=42 (db)
$ curl -s 'B/user?id=42'
user-42 key=42 (memory)
$ curl -s -X POST 'A/user?id=42&name=alice'
updated
$ curl -s 'A/user?id=42'
alice key=42 (db)
$ curl -s 'B/user?id=42'
user-42 key=42 (memory)
```

A は自分のキャッシュを消したので新しい名前を返しますが、B は古い名前を返し続けます。B は更新があったことを知る手段を持っていません。**このまま放っておけば、B は再起動するまで古い名前を返します。**

次に、バージョンをキーに入れる実装（`versioned`）です。更新と同じトランザクションで `master_version` の値を 1 つ上げ、読むときは毎回その値を引いてキーにします。

```go
func cacheKey(id int) string {
	var v int
	db.QueryRow("SELECT v FROM master_version WHERE id = 1").Scan(&v)
	return fmt.Sprintf("%d:%d", v, id)
}
```

```text
$ curl -s 'A/user?id=42'
user-42 key=1:42 (db)
$ curl -s 'B/user?id=42'
user-42 key=1:42 (db)
$ curl -s 'B/user?id=42'
user-42 key=1:42 (memory)
$ curl -s -X POST 'A/user?id=42&name=alice'
updated
$ curl -s 'A/user?id=42'
alice key=2:42 (db)
$ curl -s 'B/user?id=42'
alice key=2:42 (db)
```

B も、版が 2 に上がったことに気づき、データベースから新しい名前を読みました。

代わりに、読むたびにバージョンを引く往復が 1 回増えます。それでも、1 ページで多くのマスタを引く場面では、往復が「マスタの件数ぶん」から「1 回」になります。ISUCON12 本選の講評は、マスタの版が上がると利用者がログイン画面に戻される仕様だったと説明しています。版を確かめる処理がもともとあるアプリケーションなら、その値をキーに使えます。版の値そのものを数百ミリ秒だけキャッシュする（第 270 回の考え方）こともできますが、そのぶん他のプロセスの更新に気づくのが遅れます。

## 再起動と /initialize

メモリのキャッシュは、プロセスが止まれば消えます。消えること自体は問題ではありません。データベースが正であれば、次に読んだときに作り直されるだけです。**問題になるのは、メモリにしか無いデータを作ったとき**と、**データベースの方が巻き戻ったのに、メモリが巻き戻らないとき**です。

ISUCON のベンチマーカーは、走るたびに最初に `/initialize` を呼びます。ISUCON12 予選の講評は次のように説明しています（[講評](https://isucon.net/archives/56850281.html)）。

> 更にISUCON特有の事情として、ベンチマーク開始時に /initialize というエンドポイントにアクセスが行われ、そこで初期状態(アプリケーション外部から観測できる状態)にデータを復元する必要があります。また、このエンドポイントは30秒以内に処理を終える必要もあります。

`/initialize` はデータベースを初期状態に戻します。このとき、メモリのキャッシュも捨てるか、初期状態から作り直さなければなりません。さらに、プロセスが複数あるなら、**`/initialize` を受け取ったプロセス以外のキャッシュ**も捨てる必要があります。

上の `versioned` の実験を続けて、A に `/initialize` を送り、その後もう一度名前を変えました。`/initialize` はデータベースの名前を初期値に戻し、版を 1 に戻し、A のキャッシュを空にします。

```text
$ curl -s -X POST 'A/initialize'
initialized
$ curl -s -X POST 'A/user?id=42&name=bob'
updated
$ curl -s 'A/user?id=42'
bob key=2:42 (db)
$ curl -s 'B/user?id=42'
alice key=2:42 (memory)
```

B は `alice` を返しました。`/initialize` で版を 1 に戻したため、次の更新で版は再び 2 になり、B のメモリに残っていた**前の走行の「版 2」**のエントリに当たったのです。版の番号は、データベースを初期化しても**巻き戻してはいけません**。巻き戻すなら、すべてのプロセスのキャッシュを確実に捨てます。

ISUCON に限らず、本番でもデータベースを復元したり、管理画面から直接データを直したりすると、同じことが起きます。データを外から書き換える手段があるなら、キャッシュを捨てる手段も一緒に用意します。

<Callout type="tip" title="起動直後の作り直しを軽くする">
  キャッシュを空にした直後は、すべての要求がデータベースに向かいます。
  マスタのように全件が小さいものは、起動時や /initialize の中で全件を読み込んでおくと、
  走り始めの負荷の山を避けられます。/initialize に時間制限がある場合は、その範囲に収まるかを確かめます。
  空のキャッシュに要求が一斉に来たときの振る舞いは、第 270 回で測ります。
</Callout>

## 本番で使うときの判断

### 台数を増やすときに足かせになる

メモリのキャッシュは、そのプロセスの中でしか見えません。ISUCON13 で 2 位になった織時屋（traP）の参加記は、自分たちのキャッシュ用のライブラリを説明したうえで、次のように書いています（[参加記](https://trap.jp/post/2049/)）。

> ただし、単純なオンメモリキャッシュのため、キャッシュしたテーブルに関する処理は複数サーバーに分けづらくなってしまう。

そして反省として、次の一文を挙げています。

> @eiya: でもオンメモリキャッシュしてるからapp二台に分けられないしな...で思考止まってしまっていた（nginxの負荷だけでも分散させれば良かった）

メモリのキャッシュを入れると、そのデータを書き換える処理は、キャッシュを持つプロセスを必ず通るようにしなければなりません。アプリケーションを複数台にするときは、次のどれかを選びます。

| 方法 | 内容 | 代償 |
| --- | --- | --- |
| 書き込みを 1 台に集める | 書き換える処理だけを 1 台に振り分ける | その 1 台が詰まる |
| バージョンや更新時刻を共有の場所に置く | 上の実験の `versioned` | 読むたびに 1 往復 |
| 更新を他のプロセスに知らせる | Redis の Pub/Sub などで「このキーを捨てて」と伝える | 知らせが届く前の古さ、届かなかったときの扱い |
| 古くてよい時間を決める | 第 270 回の TTL | その時間だけ古い |
| 共有のキャッシュに移す | Redis や memcached に置く | 往復が 1 回に戻る |

台数の分け方は第 275 回で扱います。キャッシュを入れる前に、そのデータを書き換えるのがどこかを確かめておくと、後で台数を増やすときに困りません。

### 大きさとガベージコレクタ

メモリに持つ量が増えると、ガベージコレクタが調べる量も増えます（第 26 回）。ポインタを多く含む構造を大量に持つと、GC の時間が要求の処理を圧迫します。件数に上限が無いデータ（利用者ごと、要求ごとに増えるもの）をキャッシュするなら、LRU などで大きさに上限を付けます。

### 正はどこにあるか

メモリのキャッシュは写しです。正はデータベースにある、という前提を崩さないようにします。メモリにだけ書いてデータベースに書かない、という作りにすると、それはキャッシュではなく、データベースを 1 つ増やしたことになります。再起動で消え、複数台で食い違い、後で見つけにくい不整合になります。第 272 回で扱う「書き込みを後回しにする」は、この境界を意識して踏み越える技術です。

次の第 270 回では、変わり続けるデータを、仕様が許す古さの範囲でキャッシュします。捨てる手段の無いデータを、時間で捨てる方法です。

## まとめ

- 変わらないデータ、めったに変わらないデータは、アプリケーションのメモリに持つとデータベースとの往復が無くなる。ISUCON9 予選のカテゴリのように変わらないものは、コードに書いてもよい
- 実測では、1 ページ 97 回の往復を 1 回にすると、中央値が 7.5 ミリ秒から 0.4〜0.5 ミリ秒になった。効いたのは往復の回数で、JOIN でもメモリでも同じだけ減る
- メモリに持つ利点は、往復に加えて、混んだデータベースに仕事をさせないこと。並列の実験では、往復の多い書き方ほど大きく揺れた
- 読むだけなら同期は要らない。読みながら書くなら、Mutex、RWMutex、sync.Map、丸ごと差し替えのどれかで守る
- 8 コアで読むだけなら、sync.Map と丸ごと差し替えは Mutex の 20〜40 倍速かった。書き込みが 1% 混ざると、丸ごと差し替えは最も遅くなった
- その差が効くのは 1 要求でキャッシュを数千回引くとき。最初は map と RWMutex で書き、プロファイルで上位に出たら替える
- 変わるマスタは、個別に消すより、バージョンをキーに入れる方が消し漏れが起きない（ISUCON12 本選の講評）
- 自分のプロセスのキャッシュを消すだけでは、他のプロセスは古いままになる。バージョンを共有の場所に置けば、他のプロセスの更新にも気づける
- /initialize ではメモリのキャッシュも初期化する。複数のプロセスがあるならすべて。版の番号は巻き戻さない
- メモリのキャッシュは、台数を増やすときの足かせになる。書き換える処理がどこを通るかを先に決めておく
