## コンテナは自分だけのネットワークを持つ

第 76 回で、名前空間の 1 つとして **Network 名前空間** を挙げました。コンテナを起動すると、ランタイムは新しい Network 名前空間を作り、その中でプロセスを動かします（第 78 回）。

新しい Network 名前空間の中には、最初は **ループバック（`lo`）しかありません**。ネットワークインタフェース、ルーティング表、ファイアウォールの規則、使用中のポート番号の表。これらはすべて名前空間ごとに別々です。

実際にコンテナの中から見てみます。

```bash
docker run --rm alpine:3.20 ip addr
# 1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 ...
#     inet 127.0.0.1/8 scope host lo
# ...
# 11: eth0@if228: <BROADCAST,MULTICAST,UP,LOWER_UP> ...
#     inet 172.17.0.24/16 brd 172.17.255.255 scope global eth0
```

`lo` と `eth0` が見えます。`lo` は名前空間が最初から持っているもの、`eth0` は Docker が後から差し込んだものです。

ここから重要な帰結が 1 つ出てきます。

<Callout type="warn" title="コンテナの中の localhost は、コンテナ自身">
  コンテナの中で `localhost:5432` に接続すると、届く先は**そのコンテナ自身の `lo`** です。
  ホストで動いている PostgreSQL には届きません。
  ループバックも名前空間ごとに別物だからです。
  「ホストでは繋がるのに、コンテナからは繋がらない」の多くはこれが原因です。
</Callout>

## veth ペアとブリッジ

名前空間の外と繋ぐには、**veth ペア** を使います。veth は、両端を持つ仮想のケーブルのようなものです。片方の端から入れたパケットが、もう片方の端から出てきます。

```
 ┌── コンテナ A の名前空間 ──┐   ┌── コンテナ B の名前空間 ──┐
 │   eth0  172.17.0.2         │   │   eth0  172.17.0.3         │
 └─────┬──────────────────────┘   └─────┬──────────────────────┘
       │ veth ペア                        │ veth ペア
 ┌─────┴──────────────────────────────────┴───────────────────┐
 │  vethXXXX            docker0（ブリッジ）172.17.0.1   vethYYYY │   ホストの名前空間
 └───────────────────────────┬────────────────────────────────┘
                             │ NAT
                          eth0（ホストの実際の NIC）
```

- veth の片端を **コンテナの名前空間に移し**、`eth0` という名前を付ける
- もう片端はホストの名前空間に残し、**ブリッジ**（`docker0`）に繋ぐ

ブリッジは、ソフトウェアで作ったスイッチングハブです。同じブリッジに繋がったコンテナ同士は、同じ LAN にいるのと同じように直接通信できます。

先ほどの出力の `eth0@if228` は、「この `eth0` の相方は、別の名前空間にあるインタフェース番号 228 だ」という意味です。ホスト側で `ip link` を見ると、228 番の `veth...` が見つかります。

## 外に出る: NAT

`172.17.0.0/16` はコンテナ用の私的なアドレスで、外の世界はこのアドレスへの戻り道を知りません。そこで、コンテナから外に出るパケットは、ホストの NIC を通るときに **送信元アドレスをホストのアドレスに書き換えます**（NAT、正確には MASQUERADE）。家庭のルータが、家の中の機器のアドレスを 1 つのグローバルアドレスに書き換えるのと同じです。

この書き換えを行っているのは、Linux カーネルのパケット処理の仕組み（netfilter）です。Docker は、コンテナを作るたびに **iptables** の規則を追加して、NAT とフィルタを設定しています。

```bash
# ホストで（Linux の場合）
sudo iptables -t nat -L -n
# Chain POSTROUTING
# MASQUERADE  all  --  172.17.0.0/16  0.0.0.0/0
```

iptables は、Linux のディストリビューションで後継の nftables への置き換えが進んでいます。Docker Engine 29 では、iptables を介さずに nftables の規則を直接書く方式が試験的に入りました（[Docker Docs](https://docs.docker.com/engine/network/firewall-nftables/)）。いずれ既定になる予定ですが、現時点ではまだ試験的な扱いです。

## 中に入る: ポートの公開

外から来るパケットをコンテナに届けるには、逆向きの書き換えが要ります。これが `-p`（ポートの公開）です。

```bash
docker run -p 8080:80 nginx
```

これで、**ホストの 8080 番に来たパケットの宛先を、コンテナの `172.17.0.2:80` に書き換える**規則（DNAT）が追加されます。

```
クライアント → ホスト:8080
                 │  netfilter が宛先を書き換える
                 ▼
            172.17.0.2:80（コンテナの nginx）
```

<Callout type="note" title="docker-proxy というプロセス">
  ポートを公開すると、ホストに `docker-proxy` というプロセスが現れることがあります。
  ホスト自身から `localhost:8080` に繋ぐ場合、パケットはループバックを通りますが、
  カーネルはループバック宛てのパケットを通常の NAT の経路に乗せません。
  そこで、ユーザ空間のプロセスが実際に 8080 番を listen し、
  受け取った通信をコンテナへ中継します（`dockerd` の `--userland-proxy`、既定で有効）
  （[Docker Docs](https://docs.docker.com/reference/cli/dockerd/)）。
  パケットの書き換えだけでは届かない経路を、第 42 回のソケットで地道に埋めている、ということです。
</Callout>

<Callout type="warn" title="公開したポートはファイアウォールを素通りすることがある">
  Docker が追加する規則は、ホストのファイアウォール（ufw など）の規則より先に評価されることがあります。
  `-p 5432:5432` と書くと、ホストのすべてのインタフェースで公開され、
  ファイアウォールで閉じたつもりのポートが外から見えることがあります。
  手元でだけ使うなら `-p 127.0.0.1:5432:5432` のように、待ち受けるアドレスを明示します。
</Callout>

## 名前で繋ぐ: 組み込み DNS

コンテナの IP アドレスは起動のたびに変わります。そのため、コンテナ同士は名前で繋ぐのが普通です。これを担うのが、Docker の **組み込み DNS サーバ** です。

2 つの場合の `/etc/resolv.conf` を比べると違いが分かります。

```bash
# 既定のブリッジ（docker0）
docker run --rm alpine:3.20 cat /etc/resolv.conf
# nameserver 192.168.65.7        ← ホストの DNS をそのまま使う

# 自分で作ったネットワーク
docker network create demo-net
docker run --rm --network demo-net alpine:3.20 cat /etc/resolv.conf
# nameserver 127.0.0.11          ← 組み込み DNS
```

自分で作ったネットワーク（ユーザ定義ネットワーク）では、コンテナ内の `127.0.0.11` で DNS サーバが応答します。このアドレスはコンテナの `lo` の中にありますが、実際に答えているのは `dockerd` です。**コンテナ名やサービス名を引くと、そのコンテナの IP アドレスが返り**、知らない名前はホストの DNS に転送されます。

既定のブリッジではこの仕組みが働かず、コンテナ同士を名前で引けません。**名前で繋ぎたいなら、ネットワークを自分で作る**のが原則です。次回の Compose は、これを自動でやってくれます。

## その他のネットワークの形

| モード | 何をするか | 使いどころ |
| --- | --- | --- |
| `bridge`（既定） | 上で見た veth + ブリッジ + NAT | ほとんどの場合 |
| `host` | Network 名前空間を**作らない**。ホストのネットワークをそのまま使う | NAT の手間を省きたい、大量のポートを使う |
| `none` | `lo` だけ。外と繋がない | ネットワーク不要な処理 |
| `container:<名前>` | 他のコンテナの Network 名前空間に**相乗りする** | サイドカー |

`host` モードでは、コンテナの中の `localhost` がホストの `localhost` と同じものになります。分離が 1 つ減るので、ポートの衝突にも注意が必要です。

`container:` モードでは、2 つのコンテナが 1 つのネットワークを共有し、互いに `localhost` で通信できます。Kubernetes の Pod は、この形を標準にしたものです。

### ホストに繋ぐ

コンテナからホストのサービスに繋ぎたいときは、`host.docker.internal` という名前を使います。Docker Desktop では最初から使えます。Linux の Docker Engine では自動では用意されないため、`--add-host=host.docker.internal:host-gateway` を付けて、ブリッジのゲートウェイ（ホスト側のアドレス）を登録します（[Docker Docs](https://docs.docker.com/desktop/features/networking/)）。

## ファイル: コンテナの中に書いたものは消える

第 77 回で見たとおり、コンテナのファイルシステムは、読み取り専用のイメージのレイヤの上に、**書き込み用のレイヤを 1 枚重ねたもの**です。コンテナを削除すると、この書き込み用のレイヤも一緒に消えます。

データベースのファイルのように残したいものは、この重ね合わせの外に置く必要があります。そのための手段が 3 つあります。

| 方式 | 実体 | 特徴 |
| --- | --- | --- |
| **ボリューム** | Docker が管理する領域（`/var/lib/docker/volumes/...`） | コンテナを消しても残る。場所を Docker が決める |
| **バインドマウント** | ホストの任意のディレクトリ | ホストのファイルをそのまま見せる。開発中のソースコードなど |
| **tmpfs** | メモリ上 | コンテナを止めると消える。秘密情報の一時置き場など |

どれも、第 76 回で見た **Mount 名前空間** の中で、コンテナのルートファイルシステムの一部に別の場所を重ねて見せているだけです。バインドマウントは、Linux の `mount --bind` そのものです。

```bash
docker run -v mydata:/var/lib/postgresql/data postgres   # ボリューム
docker run -v "$PWD":/app node:22 node /app/index.js     # バインドマウント
docker run --tmpfs /run/secrets alpine                   # tmpfs
```

## 権限で揉める理由

バインドマウントでよく起きるのが、次のような問題です。

- コンテナが作ったファイルが、ホストで `root` の持ち物になっていて消せない
- ホストのファイルを、コンテナの中のプロセスが読めない、書けない

原因は、**ファイルの持ち主はユーザ名ではなく数値（UID）で記録されている**ことです。

```
ホスト:     tomo = UID 501
コンテナ:   root = UID 0、node = UID 1000

コンテナの root が書いたファイル → ディスクには「UID 0」と記録される
                                → ホストから見ると root の持ち物
```

カーネルが権限を判定するときに見るのは UID の数字だけで、名前は `/etc/passwd` が付けている表示上のラベルにすぎません。コンテナとホストは、それぞれ別の `/etc/passwd` を持っています。だから**同じ UID が別の名前に見え、同じ名前が別の UID を指す**ことが起きます。

対策は主に 2 つです。

- コンテナを実行するユーザの UID をホストのユーザに合わせる（`--user "$(id -u):$(id -g)"`）
- User 名前空間を使い、コンテナ内の UID をホストの別の UID に対応させる（第 85 回）

## Docker Desktop は VM の中にある

ここまでの話は、Linux の上で直接 Docker Engine が動いている場合のものです。macOS や Windows の Docker Desktop では、**Docker Engine は Linux の VM の中で動いています**。macOS のカーネルには名前空間も cgroup もないからです。

```
 macOS ────────────────────────────────────────────────┐
 │  docker CLI                                          │
 │     │ ソケット                                        │
 │  ┌──┴─── Linux VM ───────────────────────────────┐  │
 │  │  dockerd → containerd → runc → コンテナ          │  │
 │  │  docker0、veth、iptables はすべてこの中           │  │
 │  └────────────────────────────────────────────────┘  │
 └──────────────────────────────────────────────────────┘
```

そのため、2 つの違いが出ます。

**ネットワーク。** `docker0` や veth は VM の中にあり、macOS からは見えません。`-p` で公開したポートは、Docker Desktop が VM の外まで中継しています。コンテナの IP アドレス（`172.17.0.2` など）に macOS から直接繋ぐことはできません。

**バインドマウントが遅い。** macOS のディレクトリを見せると、ファイルへのアクセスは VM の境界を越える **ファイル共有**（VirtioFS など）を通ります。ファイルを 1 つ開くたびに VM の外に問い合わせが飛ぶので、`node_modules` のように小さなファイルが大量にある場合は特に遅くなります。Docker Desktop は、VM の中にファイルの写しを持って同期する方式（Synchronized file shares）も用意しています（[Docker Docs](https://docs.docker.com/desktop/features/synchronized-file-sharing/)）。

<Callout type="tip" title="遅いときの定番の逃がし方">
  依存パッケージのディレクトリだけを名前付きボリュームにして、バインドマウントから外します。

```yaml
volumes:
  - .:/app
  - node_modules:/app/node_modules   # VM の中に置き、ファイル共有を通さない
```
  ソースコードはホストと共有しつつ、小さなファイルが大量にある部分は VM の中に閉じ込める、という分け方です。
</Callout>

## まとめ

- コンテナは自分の Network 名前空間を持つ。中の `localhost` はコンテナ自身
- veth ペアで名前空間の外と繋ぎ、ブリッジで同じホストのコンテナを繋ぐ
- 外に出るときは NAT で送信元を、`-p` で公開したポートは宛先を書き換える。担うのは netfilter
- ループバック経由の接続は NAT に乗らないので、docker-proxy がユーザ空間で中継する
- ユーザ定義ネットワークでは、127.0.0.11 の組み込み DNS でコンテナ名を引ける
- ボリューム、バインドマウント、tmpfs は、Mount 名前空間の中で別の場所を重ねて見せているだけ
- 権限の問題は、ファイルの持ち主が UID の数値で記録されることから起きる
- Docker Desktop は VM の中で動く。ネットワークの見え方とバインドマウントの速さが Linux と違う
