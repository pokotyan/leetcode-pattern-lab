## canvas に描くと失うもの

第 124 回から第 126 回まで、canvas に自分で描く方法を見てきました。Canvas 2D でも WebGL でも WebGPU でも、canvas の中身は**ピクセルの格子**でしかありません。ブラウザから見ると、そこには文字も、ボタンも、段落もありません。

そのため、DOM なら黙っていてもブラウザがしてくれていた仕事を、canvas では全部自分で引き受けることになります。

| DOM ならブラウザがすること | canvas に描いたとき |
| --- | --- |
| 段落の折り返し、禁則、行の高さ | `fillText` は 1 行を置くだけ。折り返しは自分で計算する |
| アラビア語やヘブライ語の右から左の並び、縦書き | 双方向テキストのアルゴリズムや縦書きの組版を自分で書く |
| 入力欄、キャレット、選択、IME | すべて自作。IME の変換中の表示も含む |
| スクリーンリーダーへの公開 | 何も伝わらない。別に DOM を用意して同期させる |
| クリックの当たり判定 | 座標から「何を押したか」を自分で引く |

HTML-in-Canvas の提案書は、この状況を「複雑なレイアウトの文字やその他の内容を canvas に描く簡単な Web API がない。その結果、canvas を使った内容は、アクセシビリティ、国際化、性能、品質の面で苦しんでいる」と書いています（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。

グラフの凡例や軸、デザインツールのテキストボックス、ゲームのメニューのように、canvas の中に「普通の UI」を置きたい場面はたくさんあります。

## これまでの回避策

この問題は昔からあり、3 つの回避策が使われてきました。

**1. DOM を canvas の上に重ねる。** 文字や入力欄だけ普通の要素にして、`position: absolute` で canvas の上に置きます。もっとも素直ですが、DOM と canvas は別々に描かれるので、canvas 側の変形（3D の面に貼る、シェーダで歪ませる）を DOM に掛けることはできません。重ね順も「canvas の上か下か」しか選べません。

**2. SVG の `foreignObject` で画像にする。** HTML を SVG の `foreignObject` に包み、画像として読み込んで `drawImage` で描きます。手元の Chrome 155 で、`foreignObject` に `div` と `input` を入れた SVG を data URL の画像にして描くと、ピクセルは描かれ、`getImageData` で読み出すこともできました。ただし、できあがるのは**ただの画像**です。中の入力欄に文字は打てず、外部の画像やフォントの読み込みにも制限があり、描き直すたびに SVG を作り直して画像として読み込み直すことになります。

**3. CSS を自前で解釈して描き直す。** html2canvas のようなライブラリは、DOM と各要素のスタイルを読み、canvas の命令で描き直します。README は、これは実際のスクリーンショットではなくページの情報から組み立てたものなので正確とは限らず、「CSS のプロパティは 1 つずつ手で実装しなければならないので、まだ対応していないものが多くある」と書いています（[html2canvas](https://github.com/niklasvh/html2canvas)）。ブラウザのレンダリングエンジンを JavaScript で作り直しているようなものです。

どれも、**ブラウザがすでに持っているレイアウトとペイントの仕組みを使えない**ことが根にあります。

## 発想: ブラウザにレイアウトさせ、その絵を借りる

HTML-in-Canvas の考え方は単純です。

1. canvas の子として、**本物の DOM** を置く
2. ブラウザはその DOM を普段どおりにスタイル計算・レイアウト・ペイントする。ただし画面には直接出さない
3. ペイントの結果（第 115 回で見た表示リスト）を**スナップショット**として取っておく
4. 開発者は、そのスナップショットを好きな位置・好きな変形で canvas やテクスチャに描く

```
  canvas の子の DOM              ブラウザ                    開発者のコード
 ┌─────────────────┐   style / layout / paint   ┌──────────────┐
 │ <form drawable>   │ ───────────────────────▶ │ スナップショット │
 │   <label> <input> │                          └──────┬───────┘
 └─────────────────┘                                 │ paint イベント
          ▲                                          ▼
          │ クリック・入力・読み上げは       ctx.drawElementImage(form, x, y)
          │ 本物の DOM が受ける            gl.texElementSubImage2D(...)
          └──────────── 描いた位置を伝える ─ updateElementGeometry
```

文字の組版も、入力欄も、キャレットも、DOM が本物なのでブラウザの実装がそのまま効きます。開発者がするのは「どこに、どう描くか」だけです。

<Callout type="warn" title="2026 年 10 月時点で、実験中の API です">
  HTML-in-Canvas は WICG（標準化の前段の議論の場）の提案で、Web の標準ではありません。実装は Chromium だけです。
  Chrome では Origin Trial（期間を区切って本番のサイトで試せる仕組み）として提供されており、Chrome 160 まで延長されています（[Chrome for Developers](https://developer.chrome.com/blog/html-in-canvas-ot-changes)）。
  API の名前は**すでに何度も変わっています**。Chrome 155 で `layoutsubtree` 属性が `content="drawable"` に、`texElementImage2D` が `texElementSubImage2D` に、`copyElementImageToTexture` が `drawElementImageToTexture` に改められました（同じ記事）。
  この回の名前とふるまいは、手元の Chrome Canary 158 で確かめたものです。今後も変わる前提で読んでください。
</Callout>

## 5 つの部品

提案書は、この仕組みを 5 つの部品に分けています（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。

| 部品 | 役割 |
| --- | --- |
| canvas の `content` 属性 | `fallback`（既定）なら子は従来どおりの代替内容。`drawable` にすると子をレイアウトの対象にする |
| 子の `drawable` 属性 | 描く対象の要素に付ける。`isolation: isolate` が掛かり、子孫の包含ブロックになる |
| `paint` イベントと `requestPaint()` | スナップショットが更新されたことを知らせる。`requestPaint()` は変化がなくても次の描画機会に 1 回発火させる |
| `drawElementImage()` ほか | スナップショットを描く。2D は `drawElementImage`、WebGL は `texElementSubImage2D`、WebGPU は `drawElementImageToTexture` |
| `updateElementGeometry()` | 描いた位置を DOM に伝え、当たり判定とアクセシビリティの位置を合わせる |

最小の例は次のとおりです。提案書の例をもとにしています。

```html
<canvas id="c" content="drawable" style="width: 400px; height: 200px">
  <form id="form" drawable>
    <label for="name">name:</label>
    <input id="name">
  </form>
</canvas>
<script>
  const c = document.getElementById('c')
  const ctx = c.getContext('2d')
  c.onpaint = () => {
    ctx.reset()
    ctx.drawElementImage(form, 100, 0)   // スナップショットを (100, 0) に描く
  }
</script>
```

`content="drawable"` の canvas の直下の子は、ブロックとして通常の流れでレイアウトされます。提案書によると、子はアクセシビリティの上では普通の DOM と同じように扱われますが、最初は当たり判定の対象になりません（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。描いて位置を伝えるまで、どこにあるか決まっていないからです。

## 手元で確かめる（1）: どのブラウザで使えるか

Playwright からヘッドレスの Chrome を起動し、関係するプロパティがあるかを調べました。

```
                                   drawElementImage  content 属性  layoutSubtree  texElementSubImage2D  texElementImage2D
Chrome 155（安定版、フラグなし）       なし              なし          なし           なし                   なし
Chrome 155（安定版、フラグあり）       あり              なし          あり           あり                   あり
Chrome Canary 158（フラグなし）        あり              あり          なし           あり                   なし
```

フラグは `--enable-features=CanvasDrawElement` か `--enable-experimental-web-platform-features` のどちらか一方で効きました。

食い違いが 1 つあります。Chrome のブログは改名を Chrome 155 としていますが、手元の安定版 155.0.8059.84 では、フラグを有効にしても**古い名前**のままでした。`content="drawable"` の canvas で `drawElementImage` を呼ぶと、例外の文言は次のとおりです。

```
InvalidStateError: ... DrawElementImage requires the canvas to have the layoutsubtree attribute.
```

逆に Canary 158 で `layoutsubtree` を使うと「content=drawable attribute が要る」という例外になり、新しい名前でだけ動きました。WebGL の古い名前 `texElementImage2D` も、安定版 155 にはまだ残っていて、Canary 158 では消えていました。**同じ番号のブラウザでも、どちらの名前が通るかは揃っていません**。試すときは、まず機能の有無を調べるところから始めるのが安全です。

また、Canary 158 ではフラグなしで有効でした。Canary の既定の設定によるもので、安定版の利用者の環境とは違います。以降の実験はすべて Canary 158 で行っています。

## 手元で確かめる（2）: 文字と入力欄を描く

日本語の段落、太字、アラビア語（右から左）、縦書きの見出し、入力欄を 1 つの `div` に入れ、`drawElementImage` で canvas に描きました。

```html
<canvas id="c" width="400" height="240" content="drawable">
  <div id="card" drawable style="width: 360px">
    <div style="writing-mode: vertical-rl; float: right">縦書きの見出し</div>
    <p>日本語と <b>太字</b> と <span dir="rtl">مرحبا بالعالم</span> の混在。折り返しもブラウザが行います。</p>
    <label>名前: <input id="name"></label>
  </div>
</canvas>
```

スクリーンショットでは、段落が幅 360px で折り返され、アラビア語は右から左に、見出しは縦に組まれていました。`fillText` だけでこれを書くのは大仕事です。`getImageData` で canvas を読み出すと、不透明なピクセルが 45,120 個あり、絵は canvas のビットマップに確かに入っていました。

入力欄にフォーカスを当てて `abc` と打つと、値は `abc` になり、canvas に描かれた入力欄にも `abc` とフォーカスの枠が出ました。**入力を受けているのは本物の `input`** で、canvas はその姿を描き写しているだけです。

### paint イベントはいつ来るか

`paint` イベントの回数を数えました。

```
読み込み直後                           1 回
そのあと 1 秒、何もしない                1 回のまま
入力欄にフォーカスを当てる                +1
3 文字打つ（100ms 間隔）                  +4
打ち終えて 1.5 秒待つ                     +4（約 500ms ごと）
```

何も変わらなければ、イベントは来ません。提案書も、スナップショットが変わらないときには発火を避けるべきだとしています（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。打ち終えたあとに約 500ms ごとに来ているのは、**キャレットの点滅**です。キャレットが消えるたび、出るたびに、見た目が変わるのでスナップショットが更新されます。

このことは、点滅の間隔がページから測れることを意味します。提案書のセキュリティとプライバシーの質問票も、操作できる見た目のために、フォーム部品の描画やスクロールバー、テキストの選択、そして「キャレットの点滅の速さ」が見えるようになると認めています（[Security and Privacy Questionnaire](https://github.com/WICG/html-in-canvas/blob/main/security-privacy-questionnaire.md)）。

### スナップショットがないと描けない

例外になる場面も確かめました。

```
スクリプトの冒頭（最初の paint の前）に描く
  -> InvalidStateError: No cached paint record for element.
drawable 属性のない子を描く
  -> InvalidStateError: Descendants passed to DrawElementImage must have the 'drawable' attribute.
paint イベントの中で描く                          -> 成功
paint の後の requestAnimationFrame の中で描く     -> 成功
```

描けるのは、**一度ペイントされてスナップショットが記録された後**です。記録された後なら、`paint` イベントの外でも直近のスナップショットを描けました。

もう 1 つ、つまずいた点があります。`drawable` の子に幅を指定しないと、canvas の幅いっぱいには広がらず、中身の幅に縮みました。`auto` という文字だけの `div` は幅 28px で、`getElementImageDefaultSize()` も幅 27.5 を返しました。中身のない `div` なら幅は 0 で、何も描かれません。

## paint イベントは、レンダリングの更新のどこで来るか

第 117 回で、イベントループの 1 周の中で描画の機会が来ると、requestAnimationFrame、スタイルとレイアウト、ResizeObserver と IntersectionObserver、そしてペイントの順に進むことを見ました（[HTML Living Standard](https://html.spec.whatwg.org/multipage/webappapis.html#update-the-rendering)）。`paint` イベントをこのどこに入れるかが、この提案のいちばん難しい設計でした。

提案書は 3 つの案を比べ、**ペイントの直後に 1 回だけ発火する**案（Option C）を選んでいます（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。

```
描画の機会
  ├─ requestAnimationFrame
  ├─ スタイル・レイアウト
  ├─ ResizeObserver
  ├─ IntersectionObserver
  ├─ ペイント（drawable の子のスナップショットを記録）
  ├─ paint イベント      ← ここで canvas に描いた内容は、このフレームに出る
  └─ 合成へ渡す（第 116 回の commit）
                          ← ここで DOM を変えても、反映は次のフレーム
```

ペイントより前（ResizeObserver と同じ位置）で発火させると、イベントの中で DOM が書き換えられたときに、レイアウトからやり直すループが要ります。提案書は、WebGL の多くの API は命令の流し込みを同期で待つので、スナップショットを後から差し込む方式では行き詰まる、とも書いています。そこで、**ペイントが終わった時点で内容を確定させ、例外は canvas に描く内容だけ**、という形にしました。`paint` の中での DOM の変更は、次のレンダリングの更新に回ります。

これを確かめました。最初の `paint` の中で、描いた直後に子の背景を赤から青に変えます。

```
rAF#1             canvas=0,0,0
paint#1 (frame 1) drew 255,0,0      <- 赤で描く
  -> paint の中で背景を青に変更
rAF#2             canvas=255,0,0    <- まだ赤
paint#2 (frame 2) drew 0,0,255      <- 次のフレームで青のスナップショットが来る
rAF#3             canvas=0,0,255
```

各フレームで requestAnimationFrame が先、`paint` が後に来ていること、`paint` の中の変更は次のフレームの `paint` で初めて反映されることが分かります。

<Callout type="note" title="スクロールとアニメーションは、まだメインスレッド待ち">
  第 116 回で、スクロールや transform のアニメーションは、コンポジタスレッドだけで進められると見ました。
  canvas に描いた DOM は違います。描くのは `paint` イベントの JavaScript なので、メインスレッドが塞がると止まります。
  Chrome のブログは、現状の制限として、スクロールとアニメーションが JavaScript から独立して更新できないことを挙げています（[Chrome for Developers](https://developer.chrome.com/blog/html-in-canvas-origin-trial)）。
  提案書には、描画の命令を canvas に保持させ、スクロールやアニメーションのたびにブラウザが再生し直す「自動で更新される canvas」という将来の案が書かれています。
</Callout>

## 描いた位置を DOM に伝える

canvas に描いた入力欄は、描いた場所でクリックできなければ意味がありません。ところが、子の DOM が実際にレイアウトされた場所と、canvas に描いた場所は一致しません。回転させたり、3D の面に貼ったりもできるからです。

そこで、**描いた場所を変換行列として DOM に伝える**のが `updateElementGeometry()` です。2D の `drawElementImage` は、既定でこれを自動で呼びます。そのときの canvas の変換（`translate` や `rotate`）が、そのまま要素の変換として記録されます（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。

ボタンを canvas の中央に 45 度回して描き、当たり判定を調べました。

```js
c.onpaint = () => {
  ctx.reset()
  ctx.translate(200, 150); ctx.rotate(Math.PI / 4)
  ctx.drawElementImage(btn, -60, -20)                                 // 自動で位置を伝える
  // ctx.drawElementImage(btn, -60, -20, { preserveElementGeometry: true })  // 伝えない
}
```

```
                       自動（既定）                                preserveElementGeometry: true
getElementTransform    [0.707, 0.707, -0.707, 0.707, 171.7, 93.4]   単位行列
getBoundingClientRect  x=143.4 y=93.4 幅 113.1 高さ 113.1           x=0 y=0 幅 120 高さ 40
elementFromPoint(200,150)  button                                  canvas
(200,150) と (60,20) をクリック  onclick 1 回                         0 回
```

自動のときは、`getBoundingClientRect` が回転したボタンを囲む正方形（120×40 を 45 度回した外接矩形）になり、**描いた場所をクリックするとボタンが押されました**。DOM 上の元の位置（左上）をクリックしても反応しません。位置を伝えないと、ボタンはどこにも当たらず、canvas が受けました。

WebGL と WebGPU では、テクスチャがどの面にどう貼られたかを canvas の API は知りません。そのため、提案書は 3D の文脈では `updateElementGeometry` を自分で呼ぶ必要があるとしています（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。

アクセシビリティも同じ仕組みに乗っています。`drawable` の子は読み上げの木にそのまま現れますが、位置が伝えられていないうちは、位置の情報なしで公開されます（同じ提案書）。スクリーンリーダーは中身を読めますが、画面のどこにあるかは描いた後に分かります。描かなくなった子は、DOM から外すか `aria-hidden` で隠しておかないと、見えない UI が読み上げられます。

## 手元で確かめる（3）: 何が描かれないか

canvas は、描いた後に `getImageData` でピクセルを読めます。WebGL と WebGPU では、テクスチャの読み出しは常にできます。ということは、DOM のスナップショットに**ページが知ってはいけない情報**が写っていたら、それはそのまま漏れます。

第 124 回で見たとおり、Canvas 2D は別オリジンの画像を描くと canvas を汚染（tainted）し、それ以降の読み出しを禁じて守っていました。HTML-in-Canvas は別の方法を取ります。**そもそも危ないものを描かない**のです。提案書はこれを read-back-allowed rendering（読み出してよい描画）と呼び、描画にも `paint` の発火の有無にも、機微な情報を含めないと定めています（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。描かれない情報として挙げられているのは次のものです。

- 埋め込まれた別オリジンの内容（`iframe`、`img`）、`background-image` などの URL 参照、汚染された canvas、SVG の `use` などの参照
- システムの色、テーマ、設定
- スペルチェックと文法の下線
- 訪問済みリンクの情報
- JavaScript から見えない、自動入力の候補の表示
- サブピクセルのアンチエイリアス
- 字幕と動画のコントロール
- IME のポップアップと、IME 特有の文字の装飾

Python の `http.server` で同じ内容のサーバを 127.0.0.1:18501 と 127.0.0.1:18502 に立てました。ページは `http://127.0.0.1:18501/` から、別オリジンの画像は `http://localhost:18502/` から配ります。`drawable` の `div` の中に、同一オリジンの赤い画像、別オリジンの赤い画像、`:visited` で赤くなるリンクを置きました。リンク先には、あらかじめこのページのリンクから一度移動しています。比べるため、同じリンクを canvas の外にも置きました。

```
                                            読み出したピクセル    画面
同一オリジンの画像                             255,0,0（赤）       赤
別オリジンの画像（読み込みは成功、幅 60）        255,255,255（白）   描かれない
訪問済みリンク（canvas の中に描いたもの）       0,0,255（青）       青（未訪問の色）
訪問済みリンク（canvas の外の普通の DOM）       ―                  赤（訪問済みの色）
canvas の getImageData                       成功（汚染されない）
同じ別オリジンの画像を普通の drawImage で描く   SecurityError（汚染される）
```

別オリジンの画像は、画像そのものは読み込まれているのに、スナップショットからは抜け落ちていました。訪問済みのリンクは、外では訪問済みの赤で表示されるのに、canvas の中では未訪問の青で描かれました。どちらも canvas は汚染されず、読み出しは成功しています。

Canvas 2D の `drawImage` は「描いてから、読ませない」、HTML-in-Canvas は「読ませてよいものだけを描く」という対になった守り方です。後者は読み出しを止めないので、WebGL や WebGPU にもそのまま使えます。代わりに、別オリジンの `iframe` の中身は描けません。Chrome のブログも、この API は別オリジンの iframe の内容では動かないことを制限に挙げています（[Chrome for Developers](https://developer.chrome.com/blog/html-in-canvas-origin-trial)）。次の章の第 130 回で見る「埋め込めるが、中身は読めない」という境界を、描画の側でも守っているわけです。

<Callout type="warn" title="よくある誤解: 「DOM を canvas に描けるなら、スクリーンショットが撮れる」">
  撮れるのは、**そのページがもともと JavaScript で知りうる内容だけ**です。
  別オリジンの画像や iframe、訪問履歴、システムの配色、スペルチェックの結果は写りません。
  提案書の質問票も、新しいセキュリティ上の情報を一切出さないことを設計の要件にしていると書いています（[Security and Privacy Questionnaire](https://github.com/WICG/html-in-canvas/blob/main/security-privacy-questionnaire.md)）。
  第 137 回で見る iframe の境界を、この API で越えることはできません。
</Callout>

## 手元で確かめる（4）: Worker と GPU に渡す

### ElementImage を Worker に送る

`captureElementImage()` は、直近のスナップショットを `ElementImage` という転送可能なオブジェクトとして取り出します。これを Worker に送れば、第 124 回で見た OffscreenCanvas の上で描けます（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。

```js
const off = c.transferControlToOffscreen()
worker.postMessage({ canvas: off }, [off])
c.onpaint = () => {
  const img = c.captureElementImage(form)    // ElementImage
  worker.postMessage({ img }, [img])         // 転送する
}
c.onelementgeometryupdate = (e) => { /* Worker で描いた位置が DOM に反映された */ }

// Worker の中
ctx.reset(); ctx.drawElementImage(e.data.img, 50, 30)
```

Worker の中で `(50, 30)` に描くと、緑の `div` のピクセルが Worker の OffscreenCanvas から読めました。少し遅れてメインスレッドに `elementgeometryupdate` イベントが届き、要素の `getBoundingClientRect` は `(58, 38)` になりました。canvas が body の余白 8px の位置にあるので、描いた位置と一致しています。

Worker は DOM に触れません（第 117 回）。そのため Worker からの位置の更新はまとめてメインスレッドに送られ、反映し終えたところでイベントが来る、という非同期の形になっています（同じ提案書）。

### WebGL と WebGPU のテクスチャに描く

WebGL では `texElementSubImage2D`、WebGPU では `GPUQueue` の `drawElementImageToTexture` で、スナップショットをテクスチャに写します。

```js
// WebGL 2: 先にテクスチャの領域を確保してから写す
gl.texStorage2D(gl.TEXTURE_2D, 1, gl.RGBA8, 200, 100)
c.onpaint = () => gl.texElementSubImage2D(gl.TEXTURE_2D, 0, 0, 0, el)

// WebGPU: canvas に webgpu のコンテキストを設定しておく
g.getContext('webgpu').configure({ device, format: navigator.gpu.getPreferredCanvasFormat() })
g.onpaint = () => device.queue.drawElementImageToTexture({ source: q }, { texture: t })
```

青い `div` を WebGL のテクスチャに写し、テクスチャを framebuffer につないで `readPixels` で読むと `0,128,255`、橙の `div` を WebGPU のテクスチャに写して `copyTextureToBuffer` で読むと `255,128,0` が返りました。どちらも元の背景色そのものです。シェーダを通せば、このテクスチャを 3D の面に貼ることも、歪ませることもできます（第 97・99 回）。

つまずいた点が 2 つあります。

- WebGL で `texStorage2D` を呼ばずに写すと、`GL_INVALID_OPERATION: ... The destination level of the destination texture must be defined.` になりました。Chrome のブログにある「写す先のテクスチャの領域を自動では確保しなくなった」という変更のとおりです（[Chrome for Developers](https://developer.chrome.com/blog/html-in-canvas-ot-changes)）。
- WebGPU で canvas にコンテキストを設定しないまま呼ぶと、`containing canvas does not have a rendering context.` という TypeError になりました。写す先は別のテクスチャでも、元の要素を子に持つ canvas に WebGPU のコンテキストが要ります。

## 何に使うのか、何に使わないのか

提案書が挙げる用途は、canvas の中のスタイル付きの文字（グラフの凡例や軸、ゲームのメニュー）、アクセシビリティの改善、HTML に WebGL のシェーダを掛けること、3D の場面の中の 2D の内容、そして HTML を画像や動画として書き出すことです（[WICG/html-in-canvas](https://github.com/WICG/html-in-canvas)）。

逆に、普通のページの効果に使うものではありません。

- CSS の `filter`、`transform`、View Transitions で足りるなら、そちらはコンポジタスレッドで動き、メインスレッドを待ちません（第 116 回）
- 描き写すたびに、スナップショットのラスタライズとテクスチャへの転送が起きます
- Chromium だけの、名前の変わり続けている API です。Origin Trial のトークンは期限があり、更新を忘れると機能が消えます（[Chrome for Developers](https://developer.chrome.com/blog/html-in-canvas-ot-changes)）

本番で使うなら、機能の有無を調べて、ないときは従来の方法（DOM を重ねる）に戻れるようにしておく必要があります。

## まとめ

- canvas の中身はピクセルでしかなく、折り返し、双方向テキスト、縦書き、入力、読み上げ、当たり判定を失う。DOM を重ねる、`foreignObject` で画像にする、CSS を自前で解釈する、という回避策はどれもブラウザのレイアウトを使えない
- HTML-in-Canvas は、canvas の子に置いた本物の DOM をブラウザにレイアウト・ペイントさせ、そのスナップショットを canvas やテクスチャに描く
- 部品は `content="drawable"`、`drawable`、`paint` イベントと `requestPaint()`、`drawElementImage` / `texElementSubImage2D` / `drawElementImageToTexture`、`updateElementGeometry`
- `paint` イベントはペイントの直後に 1 回発火し、その中で canvas に描いた内容はそのフレームに出る。DOM の変更は次のフレームに回る
- 2D の `drawElementImage` は描いた変換を DOM に伝え、回転して描いたボタンも描いた場所でクリックできる。3D では自分で `updateElementGeometry` を呼ぶ
- 別オリジンの画像、訪問済みリンクの色、システムの配色などは描かれない。汚染で読み出しを止めるのではなく、読ませてよいものだけを描く
- 2026 年 10 月時点で Chromium だけの実験中の API。Chrome 155 の安定版と Canary 158 では通る名前が違った。機能の有無を調べてから使う

ここまでで、ブラウザの中で描く手段を一通り見ました。残るのは、**自分では描かない絵**、つまり動画です。動画の 1 フレームは、デコーダが GPU のメモリに作った画像で、canvas にも WebGL にも WebGPU にも渡せます。次の第 128 回では、`video` 要素から canvas に写す方法と、WebCodecs でフレームを 1 枚ずつ扱う方法、そしてそのときのコピーとメモリの扱いを見ます。
