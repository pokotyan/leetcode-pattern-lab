## 4 つの言葉

この 4 語は、説明する人によって定義が食い違います。まずは、広く使われている整理から始めます。

| 用語 | 待ちが発生したとき |
| --- | --- |
| **ブロッキング** | **待つ**。その処理が終わってから次へ |
| **ノンブロッキング** | 待たずに次へ。**終わったかどうかは自分で確認しに行く** |
| **同期** | **待つ**。その処理が終わってから次へ |
| **非同期** | 待たずに次へ。**終わったら通知が来る** |

この整理は実用的で、多くの場面で通用します。ただし、**よく見ると問題があります**。

> **「ブロッキング」と「同期」の説明が、一字一句同じです。**

つまり、この 2 つを「独立した 2 軸」として 4 象限に並べようとすると、片側が重なって成立しません。実態は **1 本の軸に 3 つの状態がある**、と見たほうが正確です。

## 3 つの状態として見る

```
① 待つ                      ブロッキング / 同期
② 待たない・自分で確認する      ノンブロッキング（ポーリング）
③ 待たない・通知が来る         非同期
```

具体的なコードで並べます。

### ① 待つ

```c
ssize_t n = read(fd, buf, size);     // データが来るまで戻らない
process(buf, n);
```

書き方が最も素直です。上から下に読めます。

**代わりに、その間このスレッドは何もできません。** 第 6 章で見たとおり、OS はこのスレッドを待機状態にして、CPU を他へ回します。CPU は無駄になりませんが、**このスレッドの仕事は止まります**。

### ② 待たない・自分で確認する

```c
fcntl(fd, F_SETFL, O_NONBLOCK);      // ノンブロッキングにする

while (1) {
    ssize_t n = read(fd, buf, size);
    if (n == -1 && errno == EAGAIN) {
        do_other_work();              // まだ来ていない。別の仕事をする
        continue;
    }
    process(buf, n);
    break;
}
```

`read` はすぐ戻ります。データがなければ `EAGAIN` を返します。**エラーではなく「今はまだ」という意味です。**

**問題は、いつ確認しに行くかです。**

- 頻繁に確認すれば、CPU を無駄に焼く（ビジーループ）
- 間隔を空ければ、検出が遅れる

対象が 1 つならまだしも、**1 万本の接続を全部確認して回る**のは論外です。第 7 章の C10K 問題そのものです。

### ③ 待たない・通知が来る

```c
// 依頼だけして、すぐ戻る
aio_read(&control_block);

do_other_work();

// 完了するとシグナルやコールバックで知らされる
```

自分で確認する必要がありません。**完了したことを向こうから教えてくれます。**

## 通知にも 2 種類ある

ここが、最も混乱が生まれる部分です。「通知が来る」と言っても、**何を通知するのか**が 2 通りあります。

| 方式 | 通知の内容 | やることが残るか |
| --- | --- | --- |
| **準備完了通知** | 「**読める状態になった**」 | **残る**（自分で `read` する） |
| **完了通知** | 「**読み終わった**。バッファに入っている」 | 残らない |

**epoll は準備完了通知です。**

```c
int n = epoll_wait(ep, events, 64, -1);   // 「読める」と教えてくれる
for (int i = 0; i < n; i++) {
    read(events[i].data.fd, buf, size);    // ← 実際の読み込みは自分でやる
}
```

**io_uring / Windows の IOCP / POSIX AIO は完了通知です。**

```c
// リクエストを投げておく
io_uring_submit(&ring);

// 完了したものを受け取る。データはもうバッファにある
io_uring_wait_cqe(&ring, &cqe);
```

前者を **リアクタ**（reactor）パターン、後者を **プロアクタ**（proactor）パターンと呼びます。

<Callout type="warn" title="epoll は「非同期 I/O」ではない">
  epoll を使ったサーバは「非同期サーバ」と呼ばれることが多いですが、
  **実際の読み書きは同期的にブロッキングで行われます**（準備ができているので待たされないだけ）。

  厳密な用語では、epoll は **I/O 多重化**（I/O multiplexing）という
  独立した分類になります。
</Callout>

## 規格上の定義では軸が違う

POSIX や、Stevens の『UNIX Network Programming』の分類では、2 つの軸の意味がまったく違います。

| 軸 | 何を問うているか |
| --- | --- |
| **ブロッキング / ノンブロッキング** | **呼び出しがすぐ戻るか** |
| **同期 / 非同期** | **データのコピー中に、プロセスが止まるか** |

この定義だと、I/O モデルは 5 つに分かれます。

| モデル | 呼び出し | データのコピー中 | 分類 |
| --- | --- | --- | --- |
| ブロッキング I/O | 戻らない | 止まる | **同期** |
| ノンブロッキング I/O | すぐ戻る | 止まる | **同期** |
| I/O 多重化（select / epoll） | 戻らない | 止まる | **同期** |
| シグナル駆動 I/O | すぐ戻る | 止まる | **同期** |
| **非同期 I/O（aio、io_uring）** | すぐ戻る | **止まらない** | **非同期** |

<Callout type="warn" title="この定義では、最初の 4 つは全部「同期」">
  epoll も、ノンブロッキング + ポーリングも、**規格上は同期 I/O** です。

  「非同期」と呼べるのは、**カーネルがデータのコピーまで済ませて、
  完了を知らせてくれる方式だけ**です。

  最初に挙げた実用的な整理では、epoll は「通知が来るから非同期」の側に入ります。
  **同じものが、定義によって別の分類になります。**
  だから話が噛み合わなくなります。
</Callout>

## 言葉が指すものを確認する

議論が噛み合わないときは、**どのレベルの話をしているか**を確認するのが早い。

| レベル | 「非同期」が指すもの | 例 |
| --- | --- | --- |
| **API の書き方** | 戻り値が即座に返り、後で結果を受け取る形 | `Promise`、`Future`、コールバック |
| **プログラミングモデル** | 待っている間に他の仕事が進む構造 | `async` / `await`、goroutine |
| **システムコール** | カーネルがコピーまで済ませる方式 | `io_uring`、IOCP、`aio_*` |
| **ハードウェア** | 転送を DMA に任せ、完了を割り込みで知る | 第 7 章の DMA |

**この 4 つは独立しています。** どれか 1 つが非同期でも、他が同期であることは普通にあります。

## 見た目と実装が一致しない例

### Node.js のファイル I/O

```js
const data = await fs.promises.readFile('big.txt')
```

API は非同期です。しかし、**Linux では内部でスレッドプールが使われ、
各スレッドの中では普通のブロッキング `read` が呼ばれています**。

第 7 章で触れたとおり、通常のファイルには epoll が効きません（常に「読み込み可能」と判定される）。だから、**別スレッドに逃がしてブロックさせる**という実装になっています。

```
呼び出し側から見ると:  非同期
実際にやっていること:  別スレッドでブロッキング read
```

<Callout type="tip" title="だからスレッドプールのサイズが効いてくる">
  Node.js の `UV_THREADPOOL_SIZE` は既定で 4 です。
  ファイル I/O を大量に並行させると、**ここが上限になります**。

  「非同期なのに並列度が上がらない」場合、この値を疑う価値があります。
  API の見た目からは想像しにくい制約です。
</Callout>

### async / await と、スレッド

```ts
async function handler() {
  const data = await fetch(url)     // ここで他の仕事に切り替わる
  return heavyComputation(data)      // ここは切り替わらない
}
```

`await` の位置でだけ切り替わります。**CPU を使い続ける処理の途中では切り替わりません。**

第 6 章の言葉でいえば、これは **協調的マルチタスク**です。自分から手放さなければ、他は動けません。

OS のスレッドはプリエンプティブなので、この問題がありません。代わりに切り替えのコストが高い。**軽さと安全性の交換**です。

### ブロッキングに見えて非同期

Go の goroutine は、見た目がブロッキングです。

```go
n, err := conn.Read(buf)     // ブロッキングに見える
```

しかし、実際にはランタイムがこの goroutine を待機列に移し、**別の goroutine を同じ OS スレッドで動かします**。内部では epoll が使われています。

**書き方は同期、実行は非同期。** Java 21 の仮想スレッドも同じ方向です。

<Callout type="note" title="これが async/await への批判の背景">
  第 6 章で触れた「関数の色」の問題です。
  `async` を付けると、呼び出し元にも連鎖的に `async` が必要になります。

  Go や仮想スレッドは、**言語の見た目を同期のままにして、
  ランタイムが非同期に実行する**という道を選びました。
  色が付かないので、既存のコードをそのまま使えます。
</Callout>

## どれを選ぶか

| 状況 | 向いているもの |
| --- | --- |
| 接続数が数百まで | **ブロッキング + スレッド**。素直に書ける |
| 接続数が数千〜数万 | **I/O 多重化**（epoll / kqueue） |
| 極めて高いスループットが要る | **完了通知**（io_uring / IOCP） |
| 通常のファイル I/O | スレッドプール、または io_uring |
| 書きやすさを優先 | **軽量スレッド**（goroutine、仮想スレッド） |

**まずブロッキングで書く**のが正解であることは多い。第 8 章で書いたとおり、測って足りないと分かってから複雑な方式に移るべきです。

非同期化は、**コードの読みやすさとデバッグのしやすさを確実に犠牲にします**。スタックトレースが途切れ、処理の流れが追いにくくなります。それに見合う効果があるかは、実測でしか分かりません。

## 確かめる

```bash
# どのシステムコールで待っているか
strace -T -e trace=read,epoll_wait,io_uring_enter ./a.out

# スレッドが何をしているか
cat /proc/<pid>/task/*/stat | awk '{print $2, $3}'   # 状態（S=待機, R=実行中）

# Node.js のスレッドプールを増やす
UV_THREADPOOL_SIZE=16 node app.js
```

`strace -T` は各システムコールの所要時間を出します。**`read` に 3 秒かかっていれば、そこでブロックしています。**

## まとめ

- よく見る 4 分類は、**「ブロッキング」と「同期」の説明が同一**なので 2 軸としては成立しない
- **3 つの状態**として見ると整理しやすい：待つ / 待たず自分で確認 / 待たず通知
- 通知にも 2 種類ある：**準備完了通知**（epoll。読むのは自分）と**完了通知**（io_uring。もう読み終わっている）
- 規格上の定義では、epoll も「同期 I/O」に分類される。**定義が違えば分類も変わる**
- API の見た目と実装は一致しない（Node.js のファイル I/O は裏でブロッキング）
- Go や仮想スレッドは「書き方は同期、実行は非同期」という道を選んだ
- まずブロッキングで書き、測ってから複雑にする
