## 鍵を共有しない相手に、改ざんがないことを示せるか

第 95 回の MAC は、「このメッセージは、鍵を知っている誰かが作り、途中で変わっていない」ことを確かめる道具でした。ただし**確かめる側も同じ鍵を持っている**必要があります。受け取った人は自分で同じ MAC を作れるので、第三者に「これは送り主が作ったものだ」と示すことはできません。

ソフトウェアの配布を考えると、これでは困ります。1 つの配布元が作ったものを、世界中の見知らぬ利用者が確かめたい。利用者全員に MAC の鍵を配れば、その全員が偽物を作れてしまいます。

第 97 回で、公開鍵暗号によって「公開してよい鍵」と「自分だけが持つ鍵」を分けられるようになりました。これを確認に使うのが**デジタル署名**です。

- **署名**は、秘密鍵を持つ者だけが作れる
- **検証**は、公開鍵を持つ誰にでもできる

この回では、署名の中で何が計算されているのかを 3 つの方式で見て、**検証に成功したとき何が確かめられたのか**を正確に言い分けます。

## よくある説明と、その誤り

<Callout type="warn" title="よくある誤解: 署名とは、秘密鍵で暗号化することだ">
  教科書や解説記事でよく見る説明です。「公開鍵で暗号化したものは秘密鍵で戻せる。
  逆に、秘密鍵で暗号化したものは公開鍵で戻せるので、戻せたら本人が作った証拠になる」。
  これは**教科書的な RSA にだけ当てはまる偶然**で、署名一般の説明としては誤りです。
</Callout>

教科書的な RSA では、暗号化と署名は同じ形の計算です（第 97 回）。

```
暗号化:  c = m^e mod n     復号:  m = c^d mod n
署名:    s = m^d mod n     検証:  m = s^e mod n    ← e と d を入れ替えただけに見える
```

RSA の計算は、e と d のどちらで先に累乗しても、もう一方で元に戻る置換になっています。この性質のおかげで、暗号化と署名が「向きを逆にしただけ」に見えます。

しかし、この対称性は RSA に固有です。

- **ECDSA や Ed25519 には「秘密鍵で暗号化する」操作がそもそも無い。** 署名は 2 つの数の組で、検証は「この式が成り立つか」を確かめるだけです。署名から元のメッセージやハッシュを取り出すことはできません
- **RSA でも、実際の署名と暗号化は別の手順になっている。** 暗号化の OAEP と署名の PSS は、パディングの作り方も目的も違います（[RFC 8017](https://www.rfc-editor.org/rfc/rfc8017.html)）
- **署名するのはメッセージそのものではなく、そのハッシュ**です。n より長いメッセージは直接累乗できませんし、教科書的な RSA の署名は掛け算に対して性質を保つので（2 つの署名を掛けると、2 つのメッセージの積の署名になる）、パディングなしでは偽造できてしまいます

より正確な言い方は次のとおりです。

```
署名:  sig = Sign(秘密鍵, メッセージ)     中でハッシュを取り、秘密鍵を使った演算をする
検証:  Verify(公開鍵, メッセージ, sig) → 正しい / 正しくない
```

検証の出力は**真か偽の 1 ビット**です。「復号して比べる」という形をしているのは RSA の実装上の都合にすぎません。

## RSA の署名: PKCS#1 v1.5 と PSS

RSA の署名には 2 つの方式があります（[RFC 8017 8](https://www.rfc-editor.org/rfc/rfc8017.html#section-8)）。

| 方式 | 累乗する前の値の作り方 | 同じメッセージを 2 回署名すると |
| --- | --- | --- |
| **RSASSA-PKCS1-v1_5** | `00 01 FF FF ... FF 00` + ハッシュの種類 + ハッシュ値 | 同じ署名になる |
| **RSASSA-PSS** | ハッシュ値と乱数（ソルト）を混ぜて、マスクをかける | 毎回違う署名になる |

RFC 8017 は「新しいアプリケーションでは RSASSA-PSS が必須であり、RSASSA-PKCS1-v1_5 は既存のアプリケーションとの互換性のためだけに含める」と書いています。それでも v1.5 は、証明書や JWT の RS256 などでいまも広く使われています。

TLS 1.3 は線引きをはっきりさせました。ハンドシェイクの中の署名（CertificateVerify、第 104 回）で RSA を使うなら **PSS でなければならず**、v1.5 は**証明書の中の署名にだけ**使ってよいとしています（[RFC 8446 4.2.3](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2.3)）。

v1.5 の形は、手元で公開鍵の累乗だけをして見ることができます（後の「手元で確かめる」節で作った鍵です）。

```
$ openssl pkeyutl -verifyrecover -pubin -inkey rsa.pub -in rsa15.sig -pkeyopt rsa_padding_mode:none | xxd
00000000: 0001 ffff ffff ffff ffff ffff ffff ffff  ................
...
000000c0: ffff ffff ffff ffff ffff ffff 0030 3130  .............010
000000d0: 0d06 0960 8648 0165 0304 0201 0500 0420  ...`.H.e.......
000000e0: 8399 3cfe a2b7 2238 9959 c871 6399 40f5  ..<..."8.Y.qc.@.
000000f0: 6c3e 6947 a3c4 3d07 692d 95a8 6954 60c1  l>iG..=.i-..iT`.
$ openssl dgst -sha256 msg.txt
SHA2-256(msg.txt)= 83993cfea2b722389959c871639940f56c3e6947a3c43d07692d95a8695460c1
```

`00 01`、`FF` の並び、区切りの `00`、`30 31 30 0d 06 09 60 86 48 01 65 03 04 02 01 ...`（SHA-256 を表す ASN.1 の DigestInfo）、そして末尾 32 バイトがメッセージの SHA-256 と一致しています。ハッシュの種類を埋め込むのは、別のハッシュ関数にすり替える攻撃を防ぐためです（[RFC 8017 9.2](https://www.rfc-editor.org/rfc/rfc8017.html#section-9.2)）。

<Callout type="note" title="検証を手抜きすると偽造できる">
  2006 年、OpenSSL は PKCS#1 v1.5 のパディングの後ろに余分なデータが付いていないかを確かめていなかったため、
  公開指数 e = 3 の鍵に対する署名を偽造できる脆弱性を修正しました（[OpenSSL Security Advisory 2006-09-05](https://openssl-library.org/news/secadv/20060905.txt)、CVE-2006-4339）。
  「先頭がそれらしく、中にハッシュが見つかれば良し」とする検証は壊れます。
  **検証する側は、期待する形を丸ごと作って完全一致で比べる**必要があります。
</Callout>

## ECDSA: 毎回の乱数 k が命綱

ECDSA は楕円曲線の上の署名です。秘密鍵は数 d、公開鍵は曲線上の点 Q = dG（G は曲線ごとに決まった基点）です。第 97 回の X25519 と同じく、Q から d を求めるのが難しいことに安全性を頼っています。

署名の手順は次のとおりです（n は基点 G の位数、z はメッセージのハッシュ）。

```
1. 署名のたびに、秘密の乱数 k を選ぶ（nonce）
2. 点 kG を計算し、その x 座標を r とする
3. s = k^-1 (z + r*d) mod n
4. 署名は (r, s) の組
```

検証する側は d も k も知りませんが、公開鍵 Q と (r, s) と z から点を作り直し、その x 座標が r と一致するかを確かめられます。

ここで**k の扱いが致命的に重要**です。同じ秘密鍵で、2 つの違うメッセージ z1、z2 に**同じ k** を使ったとします。k が同じなら r も同じなので、外から見ても使い回しが分かります。そして 2 つの式を引き算すると、

```
s1 - s2 = k^-1 (z1 - z2)            ← d が消える
k = (z1 - z2) / (s1 - s2) mod n     ← 公開されている値だけで k が求まる
d = (s1*k - z1) / r mod n           ← k が分かれば秘密鍵が求まる
```

**公開されている署名 2 つから、秘密鍵が計算できてしまいます。**

これが現実に起きたのが、2010 年 12 月の 27C3 で fail0verflow が発表した PlayStation 3 の事例です（[Console Hacking 2010: PS3 Epic Fail](https://media.ccc.de/v/27c3-4087-en-console_hacking_2010)）。Sony はソフトウェアの署名で、**毎回同じ k** を使っていました。署名された 2 つのファイルがあれば、Sony の署名用の秘密鍵が求まる状態だったのです。

k は**同じでなければ良い**わけでもありません。k の一部のビットが偏っているだけでも、署名を多数集めれば秘密鍵を復元できます。2024 年には、PuTTY が NIST P-521 の ECDSA で k を 512 ビットのハッシュ値から作っていたため、k の上位 9 ビットが常に 0 になり、約 60 個の署名から秘密鍵を復元できることが分かりました（[PuTTY vuln-p521-bias](https://www.chiark.greenend.org.uk/~sgtatham/putty/wishlist/vuln-p521-bias.html)、CVE-2024-31497、0.81 で修正）。

<Callout type="tip" title="決定的な ECDSA">
  RFC 6979 は、k を乱数生成器からではなく、**秘密鍵とメッセージのハッシュから HMAC_DRBG で導出**する方法を定めています（[RFC 6979](https://www.rfc-editor.org/rfc/rfc6979.html)）。
  同じメッセージなら同じ k、違うメッセージなら（事実上）違う k になり、良い乱数源が無くても使い回しが起きません。
  作られる署名は通常の ECDSA と区別できないので、検証側は何も変える必要がありません。
</Callout>

## Ed25519: 乱数に頼らない設計

Ed25519 は、EdDSA という署名方式を Curve25519 と同じ系統の曲線で具体化したものです（[RFC 8032](https://www.rfc-editor.org/rfc/rfc8032.html)）。ECDSA の失敗を踏まえて、最初から**決定的**に作られています。

```
秘密鍵: 32 バイトのシード
  SHA-512(シード) → 前半 32 バイト → 数 s（署名に使う秘密の値）、公開鍵 A = sB
                   → 後半 32 バイト → prefix（nonce を作る材料）

署名:  r = SHA-512(prefix || M)       ← nonce はメッセージと秘密から決まる
       R = rB
       S = r + SHA-512(R || A || M) * s  mod L
       署名 = R || S（64 バイト）
```

RFC 8032 は「署名ごとに一意の乱数を使う必要がない」ことを利点に挙げ、「EdDSA の署名は決定的であり、悪い乱数で署名したことに起因する攻撃を防ぐ。その影響はアルゴリズムによっては秘密鍵の完全な漏洩にまで及ぶ」と書いています（[RFC 8032 8.2](https://www.rfc-editor.org/rfc/rfc8032.html#section-8.2)）。

ほかにも使う側にとっての利点があります。

- **ハッシュ関数を選ばなくてよい。** 中で SHA-512 を使うと決まっているので、「SHA-1 で署名してしまう」といった組み合わせの誤りが起きません
- **鍵も署名も短い。** 公開鍵 32 バイト、署名 64 バイト
- **形が一定。** ECDSA の署名は DER の整数の長さで 70〜72 バイトに揺れますが、Ed25519 は常に 64 バイトです

NIST も 2023 年 2 月の FIPS 186-5 で EdDSA を承認された署名方式に加えました（[FIPS 186-5](https://csrc.nist.gov/pubs/fips/186-5/final)）。新しく鍵を作るなら、相手が対応している限り Ed25519 を選ぶのが無難です。対応していない相手（古い HSM や一部のクラウドの鍵管理サービスなど）のために、ECDSA P-256 と RSA が残っています。

3 方式を並べるとこうなります。

| | RSA（PKCS#1 v1.5） | RSA-PSS | ECDSA（P-256） | Ed25519 |
| --- | --- | --- | --- | --- |
| 署名の長さ | 鍵長と同じ（2048 ビットなら 256 バイト） | 同左 | 70〜72 バイト（DER） | 64 バイト |
| 同じメッセージの再署名 | 同じ | 毎回違う（ソルト） | 毎回違う（RFC 6979 なら同じ） | 同じ |
| 乱数が悪いと | 影響なし | 秘密鍵の漏洩には結びつかない | **秘密鍵が漏れる** | 署名時は乱数を使わない |
| 主な用途 | 証明書、JWT の RS256 | TLS 1.3 のハンドシェイク、PS256 | 証明書、JWT の ES256、DNSSEC（アルゴリズム 13） | SSH、Git、JWT の EdDSA |

耐量子の署名としては、2024 年 8 月に ML-DSA が FIPS 204 として標準化されました（[FIPS 204](https://csrc.nist.gov/pubs/fips/204/final)）。第 97 回で見た鍵交換と違い、署名は「今収集して後で解読」の対象になりにくい（過去の署名を後から偽造しても、検証はもう終わっている）ため、移行は鍵交換ほど急がれていません。

## 署名は何を保証するのか

検証に成功したとき、確かめられたのは次の 2 つだけです。

1. **このメッセージは、署名されてから 1 ビットも変わっていない**（完全性）
2. **この公開鍵に対応する秘密鍵で署名された**（第 94 回の真正性のうち、「鍵」についての部分）

<Callout type="warn" title="よくある誤解: 検証に通ったので、送り主は〇〇さんだ">
  署名が示すのは「**この鍵で**署名された」ことだけで、「**その鍵が〇〇さんのもの**」であることは示しません。
  攻撃者が自分の鍵ペアを作り、自分の秘密鍵で署名し、自分の公開鍵を「〇〇さんの公開鍵です」と添えて送れば、
  検証は完璧に成功します（次の節で実演します）。
  **公開鍵と持ち主を結びつける仕組み**が別に要ります。
</Callout>

その「結びつける仕組み」は、場面ごとに違います。

| 場面 | 公開鍵を誰のものと信じる根拠 |
| --- | --- |
| TLS のサーバ | CA が署名した証明書（第 101、102 回） |
| SSH のサーバ | 初回接続で覚えた known_hosts（第 106 回） |
| SSH のユーザ | サーバの authorized_keys に登録された公開鍵 |
| JWT、ID トークン | IdP が TLS 越しに公開する JWKS（第 111、113 回） |
| DNSSEC | 親ゾーンの DS をたどったルートのトラストアンカー（第 61 回） |
| Git のコミット | GitHub などに登録した鍵、または allowed_signers ファイル |

どれも、**すでに信じている何か**から、新しい公開鍵へ信頼を引き継いでいます。証明書は「CA の公開鍵を信じているなら、この CA が署名したこの公開鍵も信じられる」という、署名を使った引き継ぎの仕組みです。

<Callout type="warn" title="よくある誤解: 署名したので、中身は守られている">
  署名は**中身を隠しません**。署名付きのメッセージは誰でも読めます。第 111 回で見る JWT（JWS）が典型で、
  署名されたトークンの中身は Base64URL をデコードするだけで読めます。
  秘密にしたいなら、第 96 回の AEAD で暗号化するという別の部品が要ります。
</Callout>

署名はもう 1 つ、**新しさ**も保証しません。昨日盗み見た署名付きメッセージは、今日送り直しても検証に通ります（第 94 回のリプレイ）。そのため署名を使うプロトコルは、署名の対象に「この場限りの値」を入れます。

- TLS 1.3 の CertificateVerify は、**そのハンドシェイクで交わしたメッセージ全体のハッシュ**に署名する。前に空白（0x20）を 64 個、続けて「TLS 1.3, server CertificateVerify」という文脈を示す文字列を置くので、別のプロトコルや別の役割の署名に流用できない（[RFC 8446 4.4.3](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.3)）
- JWT は `exp`（期限）や `jti`（一意の ID）を入れる
- SSH のユーザ認証は、接続ごとに違うセッション ID に署名する（第 106 回）

**何に署名させるか**を決めるのはプロトコルの側です。署名方式がどれほど強くても、署名の対象に文脈と新しさが入っていなければ、正しい署名が間違った場所で使われます。

## MAC と署名の使い分け

| | MAC（HMAC など） | 署名 |
| --- | --- | --- |
| 鍵 | 作る側と確かめる側が同じ鍵を共有 | 作る側は秘密鍵、確かめる側は公開鍵 |
| 第三者に示せるか | できない（確かめる側も作れる） | できる（否認防止の土台） |
| 確かめる側が増えると | 全員に秘密の鍵を配る必要がある | 公開鍵を配るだけ |
| 速さ・大きさ | 速い、32 バイト程度 | 遅い、64〜512 バイト |

判断の基準は、**確かめる側を信じてよいか**です。

- 作る側と確かめる側が**同じ組織の同じシステム**なら MAC で足ります。サーバが自分で発行して自分で受け取る Cookie の改ざん防止や、TLS の中の各レコード（AEAD の認証タグ）がこれです
- 確かめる側が**多数で、そのどれにも偽物を作らせたくない**なら署名です。IdP が発行した ID トークンを多数のサービスが確かめる、配布元のパッケージを利用者全員が確かめる、といった場面です

実際のプロトコルは両方を使います。TLS はハンドシェイクで 1 回だけ署名して相手の鍵を確かめ、その後の大量のデータには共通鍵の AEAD を使います。**署名は高価なので、信頼の出発点にだけ使う**という分担です。

## 署名はどこで使われているか

| 使われる場所 | 何に署名するか | 詳しく見る回 |
| --- | --- | --- |
| TLS のハンドシェイク | そのハンドシェイクのメッセージ全体のハッシュ | 第 104 回 |
| X.509 証明書 | 「この公開鍵はこの名前のもの」という文書 | 第 101、102 回 |
| SSH | サーバはハンドシェイクに、ユーザはセッション ID に | 第 106、107 回 |
| JWT、ID トークン | ヘッダとペイロード | 第 111、113 回 |
| WebAuthn、パスキー | サーバからの challenge と origin | 第 109 回 |
| DNSSEC | RRset | 第 61 回 |
| コンテナイメージ、コード署名 | 成果物のダイジェスト（Sigstore） | 第 152 回 |
| Git のコミットとタグ | コミットオブジェクト | Git 2.34 から SSH 鍵でも署名できる（[GitHub Blog](https://github.blog/open-source/git/highlights-from-git-2-34/)） |
| OS のパッケージ | パッケージや、パッケージ一覧のハッシュ | apt、rpm など |

どの行も、署名だけでは成り立っていません。**ハッシュ**（第 95 回）で対象を固定長にし、**署名**で鍵を確かめ、**証明書や JWKS や known_hosts** で鍵と持ち主を結びつけ、機密が要るなら **AEAD**（第 96 回）を、共通鍵が要るなら**鍵交換**（第 97 回）を足します。

## 手元で確かめる

openssl 3.6 で、Ed25519、ECDSA、RSA の署名を作って検証します。

```
$ printf 'pay 100 yen to alice\n' > msg.txt
$ printf 'pay 900 yen to alice\n' > msg2.txt
```

### Ed25519

```
$ openssl genpkey -algorithm ed25519 -out ed.key
$ openssl pkey -in ed.key -pubout -out ed.pub
$ openssl pkeyutl -sign -rawin -inkey ed.key -in msg.txt -out msg.ed.sig
$ wc -c msg.ed.sig
      64 msg.ed.sig
$ openssl pkeyutl -verify -rawin -pubin -inkey ed.pub -in msg.txt -sigfile msg.ed.sig
Signature Verified Successfully
```

Ed25519 は中で SHA-512 を使うので、`-rawin` でメッセージをそのまま渡します。金額を書き換えたメッセージで検証すると失敗します。

```
$ openssl pkeyutl -verify -rawin -pubin -inkey ed.pub -in msg2.txt -sigfile msg.ed.sig
Signature Verification Failure
```

署名の先頭 1 バイトを書き換えても失敗します。そして、同じメッセージにもう一度署名すると、**まったく同じ 64 バイト**になります。決定的な署名だからです。

```
$ openssl pkeyutl -sign -rawin -inkey ed.key -in msg.txt -out again.sig
$ cmp msg.ed.sig again.sig && echo same
same
```

### ECDSA（P-256）

```
$ openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out ec.key
$ openssl pkey -in ec.key -pubout -out ec.pub
$ openssl dgst -sha256 -sign ec.key -out msg.ec.sig msg.txt
$ openssl dgst -sha256 -sign ec.key -out again.ec.sig msg.txt
$ cmp -s msg.ec.sig again.ec.sig && echo same || echo differ
differ
$ openssl dgst -sha256 -verify ec.pub -signature msg.ec.sig msg.txt
Verified OK
$ openssl dgst -sha256 -verify ec.pub -signature again.ec.sig msg.txt
Verified OK
```

同じメッセージの署名が毎回違い、それでもどちらも検証に通ります。k が毎回違うからです。署名の中身は、r と s の 2 つの整数を並べた DER です。

```
$ openssl asn1parse -inform DER -in msg.ec.sig
    0:d=0  hl=2 l=  68 cons: SEQUENCE
    2:d=1  hl=2 l=  32 prim: INTEGER           :68C70BC108B57620C12FA0C25C8DD0B8D4F9008BCB317FDDF4C2EFB1A2921960
   36:d=1  hl=2 l=  32 prim: INTEGER           :390EF56BD81BAF07BE17525CE4249C6B90A1996469CC372ABF8A1BB3B3B70143
```

6 回署名して長さを数えると、70、71、72 バイトが混ざりました。DER の整数は、先頭のビットが 1 だと符号のために 00 を 1 バイト足すので、r と s の値によって長さが揺れます。

### RSA（PKCS#1 v1.5 と PSS）

```
$ openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out rsa.key
$ openssl pkey -in rsa.key -pubout -out rsa.pub
$ openssl dgst -sha256 -sign rsa.key -out rsa15.sig msg.txt                        # v1.5
$ openssl dgst -sha256 -sign rsa.key -sigopt rsa_padding_mode:pss -out pss1.sig msg.txt
$ openssl dgst -sha256 -sign rsa.key -sigopt rsa_padding_mode:pss -out pss2.sig msg.txt
$ cmp -s pss1.sig pss2.sig && echo same || echo differ
differ
$ openssl dgst -sha256 -verify rsa.pub -sigopt rsa_padding_mode:pss -signature pss1.sig msg.txt
Verified OK
```

v1.5 は 2 回署名しても同じ値に、PSS はソルトのぶん毎回違う値になりました。v1.5 の署名を公開鍵で累乗した中身は、前の「RSA の署名」節で見たとおりです。

### 署名は「この鍵で」しか言わない

最後に、攻撃者が自分の鍵で偽のメッセージに署名した場合です。

```
$ openssl genpkey -algorithm ed25519 -out eve.key
$ openssl pkey -in eve.key -pubout -out eve.pub
$ openssl pkeyutl -sign -rawin -inkey eve.key -in msg2.txt -out msg2.eve.sig

$ openssl pkeyutl -verify -rawin -pubin -inkey eve.pub -in msg2.txt -sigfile msg2.eve.sig
Signature Verified Successfully          ← 添えられた公開鍵で確かめれば、正しい署名
$ openssl pkeyutl -verify -rawin -pubin -inkey ed.pub -in msg2.txt -sigfile msg2.eve.sig
Signature Verification Failure           ← 本当の送り主の公開鍵で確かめると、失敗
```

1 つ目の検証は完全に正しく成功しています。**どちらの公開鍵で確かめるべきか**は、署名の計算からは決まりません。それを決めるのが、証明書や known_hosts や JWKS です。

## まとめ

- 「署名は秘密鍵で暗号化すること」は教科書的な RSA にだけ当てはまる偶然。ECDSA や Ed25519 には暗号化の操作が無く、RSA でも署名と暗号化は別の手順
- 署名はハッシュと秘密鍵による演算、検証は公開鍵による真偽の判定。検証の出力は 1 ビット
- RSA は PKCS#1 v1.5（互換用）と PSS（新規はこちら）。TLS 1.3 のハンドシェイクでは PSS が必須。検証はパディングまで完全一致で比べる
- ECDSA は署名ごとの k が命綱。同じ k を 2 回使えば、公開された署名 2 つから秘密鍵が求まる（PS3、2010）。偏りだけでも漏れる（PuTTY、2024）
- Ed25519 は nonce をメッセージと秘密から決める決定的な署名で、乱数の失敗が起きない。新しく選ぶならこれ
- 署名が保証するのは「変わっていない」と「この鍵で署名された」まで。鍵が誰のものか、中身の機密、新しさは保証しない
- 確かめる側を信じてよければ MAC、多数の第三者に確かめさせるなら署名。実際のプロトコルは両方を組み合わせる

署名で鍵を確かめる仕組みはそろいましたが、その鍵は結局ファイルとして手元に置かれます。次の回では、`BEGIN PRIVATE KEY` や `ssh-ed25519 AAAA...` といった鍵ファイルの形式を読み分け、秘密鍵と公開鍵が本当にペアかどうかを確かめる方法を見ます。
