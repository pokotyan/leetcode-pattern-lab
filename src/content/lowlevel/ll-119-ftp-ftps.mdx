## 1 回の転送に接続が 2 本

前回の第 118 回では、SSH の 1 本の接続の中でファイルを運ぶ SFTP を見ました。要求も応答もファイルの中身も、同じ接続の上のチャネルを流れます。

FTP は、その正反対の設計です。1985 年の [RFC 959](https://www.rfc-editor.org/rfc/rfc959.html) は、コマンドと応答をやり取りする**制御接続**と、ファイルの中身を運ぶ**データ接続**を、別々の TCP 接続として定めています（[RFC 959 2.2](https://www.rfc-editor.org/rfc/rfc959.html#section-2)）。しかもデータ接続は転送のたびに張り直され、**どちらの向きに、どのポートへ張るか**を、制御接続の中の文字列で決めます。

この「接続の宛先が通信の中身に書かれている」という性質が、FTP をめぐるほとんどの問題の根になっています。NAT は中身のアドレスを書き換えられず、ファイアウォールは次にどのポートが使われるかを知りません。そこで、制御接続の中身を読んで穴を開ける**ALG**（Application Level Gateway）という仕掛けが生まれました。そして FTP に TLS をかけると（FTPS）、今度はその ALG が中身を読めなくなります。

この回では、まず平文の FTP で 2 本の接続の向きを確かめ、次に第 117 回の型 2（途中で TLS に切り替える）にあたる FTPS を立て、最後にファイアウォール役のコンテナを挟んで、ALG が FTP では働き FTPS では働かない様子を見ます。

3 台とも、受動モードのデータ接続に使うポートを 30000〜30009 に絞っています（理由は後で見ます）。平文の設定の要点は次のとおりです。

```
listen=YES
local_enable=YES
pasv_min_port=30000
pasv_max_port=30009
log_ftp_protocol=YES
```

明示的な FTPS では、これに次を足します。

```
ssl_enable=YES

```

## 平文の FTP: 制御接続でデータ接続の宛先を決める

### 受動モード: PASV と EPSV

まず、Python の `socket` だけで制御接続を張り、コマンドを 1 行ずつ送ります。`C:` が送ったもの、`S:` がサーバの応答です。

```
S: 220 (vsFTPd 3.0.5)
C: USER alice
S: 331 Please specify the password.
C: PASS correct-horse
S: 230 Login successful.
C: TYPE I
S: 200 Switching to Binary mode.
C: PASV
S: 227 Entering Passive Mode (172,21,0,2,117,52).
   -> data: 172.21.0.2:30004  (117*256+52)
C: RETR hello.txt
S: 150 Opening BINARY mode data connection for hello.txt (15 bytes).
DATA: b'hello from ftp\n'
S: 226 Transfer complete.
C: EPSV
S: 229 Entering Extended Passive Mode (|||30000|)
C: LIST
S: 150 Here comes the directory listing.
DATA: -rw-r--r--    1 1000     1000           15 Oct 08 05:13 hello.txt
S: 226 Directory send OK.
```

読み取れることを順に挙げます。

- `PASV` は、サーバに「データ用のポートで待ち受けて、その場所を教えてくれ」と頼むコマンドです（[RFC 959 4.1.2](https://www.rfc-editor.org/rfc/rfc959.html#section-4)）。応答の `227` には、**IPv4 アドレスの 4 バイトとポート番号の上位・下位の 2 バイト**が、10 進数をカンマで区切った形で入っています。`117*256+52 = 30004` が、サーバが待ち受けたポートです
- クライアントは、その場所へ**2 本目の TCP 接続**を自分から張り、そこでファイルの中身を受け取ります。制御接続には `150` と `226` という「始めた」「終わった」だけが流れます
- `EPSV` は、IPv6 と NAT のために 1998 年に足された拡張です（[RFC 2428](https://www.rfc-editor.org/rfc/rfc2428.html)）。応答の `229` には**ポート番号しか入っていません**。データ接続の宛先は制御接続と同じアドレスと決められているので（[RFC 2428 3](https://www.rfc-editor.org/rfc/rfc2428.html#section-3)）、32 ビットのアドレスを書く場所が要らず、IPv6 でもそのまま使えます

<Callout type="note" title="227 に書かれるアドレスは、サーバが自分で思っているアドレス">
  `227` の `172,21,0,2` は、サーバが「自分のアドレス」として書いたものです。vsftpd は既定で、制御接続を受けたソケットのアドレスをそのまま書きます。
  サーバが NAT の内側にいると、ここに外から届かない内側のアドレスが入ってしまいます。そのために vsftpd には、応答に書くアドレスを上書きする `pasv_address` があります（[vsftpd.conf(5)](https://security.appspot.com/vsftpd/vsftpd_conf.html)）。
  `229` にはアドレスがないので、この問題は起きません。curl も、受動モードでは `EPSV` を先に試し、だめなら `PASV` に戻ります（[curl(1)](https://curl.se/docs/manpage.html)）。
</Callout>

### 能動モード: PORT と EPRT

もう一方のやり方では、**クライアントが待ち受け、サーバがそこへ接続してきます**。RFC 959 の元々の既定はこちらで、データ接続はサーバの側から張るものとして書かれています（[RFC 959 3.2](https://www.rfc-editor.org/rfc/rfc959.html#section-3)）。curl では `--ftp-port -`（`-P -`）で能動モードになります。

```
$ curl -v --ftp-port - -u alice:correct-horse ftp://ll118-ftp/hello.txt
> EPRT |1|172.21.0.5|38275|
< 200 EPRT command successful. Consider using EPSV.
> RETR hello.txt
* Connection accepted from server
* Connected 2nd connection to 172.21.0.2 port 38491
< 150 Opening BINARY mode data connection for hello.txt (15 bytes).

$ curl -v --disable-eprt --ftp-port - -u alice:correct-horse ftp://ll118-ftp/hello.txt
> PORT 172,21,0,5,192,21
< 200 PORT command successful. Consider using PASV.
```

`EPRT |1|172.21.0.5|38275|` の `1` は IPv4 の意味です（[RFC 2428 2](https://www.rfc-editor.org/rfc/rfc2428.html#section-2)）。`PORT` は `227` と同じ 6 つの数の形で、`192*256+21 = 49173` 番で待っていると伝えています。tcpdump で SYN だけを抜き出すと、**2 本目の接続の SYN がサーバ（172.21.0.2）から出ている**ことが分かります。

```
172.21.0.5.38744 > 172.21.0.2.21:    Flags [S]     ← 制御接続: クライアントから
172.21.0.2.21 > 172.21.0.5.38744:    Flags [S.]
172.21.0.2.38491 > 172.21.0.5.38275: Flags [S]     ← データ接続: サーバから
172.21.0.5.38275 > 172.21.0.2.38491: Flags [S.]
```

RFC 959 では、サーバ側のデータ用の既定のポートは「制御のポートの 1 つ下」（L-1）、つまり 20 番です（[RFC 959 3.2](https://www.rfc-editor.org/rfc/rfc959.html#section-3)）。手元の vsftpd は 38491 番から接続してきました。vsftpd の `connect_from_port_20` は既定で `NO` で、20 番という特権ポートを使わないほうが少ない権限で動ける、と説明されています（[vsftpd.conf(5)](https://security.appspot.com/vsftpd/vsftpd_conf.html)）。

2 つのモードを並べます。

| | 受動（PASV / EPSV） | 能動（PORT / EPRT） |
| --- | --- | --- |
| 待ち受けるのは | サーバ | クライアント |
| データ接続の SYN を送るのは | クライアント | サーバ |
| 宛先を伝えるのは | サーバの応答（`227` / `229`） | クライアントのコマンド |
| クライアントが NAT の内側にいると | そのまま通る（外向きの接続だから） | サーバからの接続が内側に届かない |
| サーバ側のファイアウォールで開けるもの | 21 番と、受動用のポート範囲 | 21 番だけ（外向きの接続を許す） |

第 76 回で見たとおり、家庭やオフィスの NAT は**外から内への新しい接続を通しません**。能動モードは、まさにその「外から内への接続」を要求します。RFC 2428 も、ファイアウォールは一般に内向きの接続を通さないという理由で、受動モードを勧める文書（RFC 1579）を引いています。今日のクライアントの既定がほぼ受動モードなのはこのためです。

### パスワードもファイルも、そのまま流れる

この平文の FTP の通信を tcpdump で記録し、中身を文字として表示すると、次の行が見えました。

```
172.21.0.5.38744 > 172.21.0.2.21: ... length 12: FTP: USER alice
172.21.0.5.38744 > 172.21.0.2.21: ... length 20: FTP: PASS correct-horse
172.21.0.5.38744 > 172.21.0.2.21: ... length 27: FTP: EPRT |1|172.21.0.5|38275|
B.....".hello from ftp
```

利用者名、パスワード、データ接続の宛先、ファイルの中身がすべて読めます。RFC 2577（FTP のセキュリティの考慮点）も、FTP は `PASS` コマンドでパスワードを平文で送る、と明記しています（[RFC 2577 5](https://www.rfc-editor.org/rfc/rfc2577.html)）。

## 宛先を中身に書くことの帰結 1: バウンス攻撃

能動モードでは、**クライアントが「この宛先に接続してくれ」とサーバに頼みます**。その宛先が自分自身である保証はありません。`PORT` に第三者のアドレスとポートを書けば、サーバはそこへ接続し、指示されたファイルを送り込みます。サーバを踏み台にして、攻撃者自身のアドレスを隠したまま、別のホストのサービスに接続させられるわけです。これを **FTP バウンス攻撃**と呼びます（[RFC 2577 2〜3](https://www.rfc-editor.org/rfc/rfc2577.html)）。

元々 RFC 959 は、クライアントが 2 台のサーバに制御接続を張り、**サーバ同士の間で直接**データを運ばせる使い方を想定していました（[RFC 959 2.3](https://www.rfc-editor.org/rfc/rfc959.html#section-2)）。宛先を自由に書けるのは仕様どおりの機能で、それが攻撃に転用されたのです。

RFC 2577 の対策の提案は、1024 番より下のポートへのデータ接続を開かない（`504` で断る）ことと、受動モードだけで済ませることでした。ただ、それでも 1024 番以上のサービスは狙えると、RFC 自身が認めています（[RFC 2577 3](https://www.rfc-editor.org/rfc/rfc2577.html)）。今日の実装は、さらに強く**データ接続の宛先は制御接続の相手と同じアドレスに限る**という確認をしています。vsftpd では `port_promiscuous=NO`（既定）がこの確認です（[vsftpd.conf(5)](https://security.appspot.com/vsftpd/vsftpd_conf.html)）。

この確認は、後で NAT を挟んだときにはっきり見えます。内側のクライアント（10.118.0.3）が NAT 越しに `PORT` を送ると、サーバから見た制御接続の相手は NAT の外側のアドレスなので、次のように拒否されました。

```
> EPRT |1|10.118.0.3|47705|
< 500 Illegal EPRT command.
> PORT 10,118,0,3,156,71
< 500 Illegal PORT command.
```

<Callout type="note" title="受動モードの側の確認と、ポートの横取り">
  受動モードにも似た問題があります。サーバが待ち受けたデータ用のポートに、**本来のクライアントより先に別の誰かが接続すれば**、その人がファイルを受け取ってしまいます。
  RFC 2577 は、ポート番号を順番に割り当てる OS では次の番号を予想されやすいとして、データ接続のポートを乱数で選ぶよう勧めています（[RFC 2577 8](https://www.rfc-editor.org/rfc/rfc2577.html)）。
  vsftpd の `pasv_promiscuous=NO`（既定）は、データ接続の送信元が制御接続と同じアドレスであることを確かめます（[vsftpd.conf(5)](https://security.appspot.com/vsftpd/vsftpd_conf.html)）。
  ただし、同じ NAT の内側にいる別の利用者は、外から見て同じアドレスです。アドレスの確認だけでは区別できません。この穴は、後で見る FTPS のセッション再開で塞がります。
</Callout>

## 宛先を中身に書くことの帰結 2: ファイアウォールが中身を読む

ファイアウォールの規則を「21 番への新しい接続だけを通す」と書くと、データ接続は通りません。データ接続のポートは、制御接続の中で毎回決まるからです。かといって 1024〜65535 番をすべて開けるのでは、ファイアウォールの意味がありません。

そこで、ファイアウォールや NAT の機器が**制御接続の中身を読み**、`227` や `PORT` の行からアドレスとポートを取り出して、**そのデータ接続だけを一時的に通す**仕組みが作られました。一般に ALG と呼ばれ、Linux では conntrack の**ヘルパ**がこれを担います。ヘルパは「次にこの 5 つ組の接続が来るはずだ」という**期待**（expectation）を登録し、実際に来た接続を `RELATED` として扱います。NAT をしている場合は、`PORT` の行に書かれた内側のアドレスを外側のアドレスに**書き換え**もします。

### 手元で: ファイアウォール役のコンテナを挟む

クライアントとサーバの間に、NAT とファイアウォールを兼ねたコンテナ `ll118-fw` を置きました。

```
ll118-inner (10.118.0.3) ── eth0 [ll118-fw] eth1 (172.21.0.7) ── ll118-ftp (172.21.0.2)
                                  MASQUERADE                    ll118-ftps (172.21.0.3)
```

規則は「戻りの通信と、21 番への新しい接続だけを通す」です。

```
iptables -t nat -A POSTROUTING -o eth1 -j MASQUERADE
iptables -P FORWARD DROP
iptables -A FORWARD -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A FORWARD -i eth0 -o eth1 -p tcp --dport 21 -m conntrack --ctstate NEW -j ACCEPT
```

まずヘルパなしで、平文の FTP を受動モードで取得します。

```
$ curl -v --connect-timeout 4 -u alice:correct-horse ftp://172.21.0.2/hello.txt
> EPSV
< 229 Entering Extended Passive Mode (|||30006|)
*   Trying 172.21.0.2:30006...
> PASV
< 227 Entering Passive Mode (172,21,0,2,117,49).
curl: (28) Connection time-out
```

ログインまでは進みますが、30006 番への新しい接続が FORWARD で捨てられ、時間切れになりました。

### ヘルパを付ける

ここで 1 つ予定外のことがありました。Docker Desktop の Linux カーネルでは、FTP のヘルパが組み込まれていません。

```
$ zcat /proc/config.gz | grep -E "CONNTRACK_FTP|NF_CT_NETLINK_HELPER"
# CONFIG_NF_CONNTRACK_FTP is not set
CONFIG_NF_CT_NETLINK_HELPER=y
```

代わりに、ヘルパの処理をユーザ空間で行う conntrack-tools の `conntrackd` を使いました。カーネルは対象のパケットをキュー経由で `conntrackd` に渡し、`conntrackd` の FTP ヘルパが中身を読んで期待を登録します。ヘルパを付ける対象は、raw テーブルの `CT` ターゲットで明示します。

```
nfct add helper ftp inet tcp
conntrackd -d -C /etc/conntrackd.conf        # Helper { Type ftp inet tcp { QueueNum 5 ... } }
iptables -t raw -A PREROUTING -i eth0 -p tcp --dport 21 -j CT --helper ftp
```

`conntrack -E expect` で期待の登録を見張りながら、`PASV` で取得しました（`--disable-epsv`）。

```
$ curl -sS --disable-epsv -u alice:correct-horse ftp://172.21.0.2/hello.txt
hello from ftp

    [NEW] 300 proto=6 src=10.118.0.3 dst=172.21.0.2 sport=0 dport=30002 ... master-src=10.118.0.3 master-dst=172.21.0.2 sport=51654 dport=21 class=0 helper=ftp
[DESTROY] 299 proto=6 src=10.118.0.3 dst=172.21.0.2 sport=0 dport=30002 ... helper=ftp
```

`227` の応答を読んだヘルパが、「10.118.0.3 から 172.21.0.2 の 30002 番への接続」を期待として登録し（`NEW`、有効期限 300 秒）、実際の接続が来た時点で使い終えています（`DESTROY`）。**21 番しか開けていないのに、データ接続が通りました**。

能動モードでも試しました。クライアントが送った `PORT` と、サーバのログに残った `PORT` を並べます。

```
クライアントが送った:  PORT 10,118,0,3,151,155
サーバが受け取った:    PORT 172,21,0,7,204,209      （vsftpd のログ）
```

ヘルパが、制御接続の中の**内側のアドレスを NAT の外側のアドレス（172.21.0.7）に書き換え**、ポートも NAT が割り当てた番号に差し替えています。サーバは `200 PORT command successful` と受け入れました。これが「ALG は中身を読むだけでなく書き換える」ということです。ただ、この構成では、その後のサーバからの接続を内側のクライアントへ届けるところまでは動かず、`425 Failed to establish connection.` で終わりました。期待は外側のアドレス宛てに登録されていたので、戻りの接続を内側へ振り向ける NAT の設定が、ユーザ空間のヘルパでは整わなかったと見ています。

<Callout type="warn" title="手元で見えた、ユーザ空間のヘルパの限界">
  同じ構成で curl の既定どおり `EPSV` から始めると、`229` の応答に対して期待は登録されず、データ接続は時間切れになりました（2 回試して同じでした）。
  conntrack-tools 1.4.8 の FTP ヘルパのソースには `229 ` を探す処理があるので、原因は追い切れていません。
  ALG は「仕様の上ではこう読めるはずの文字列」を、実装ごとの癖を持って読みます。**ALG を前提にした構成は、ALG の実装に依存する**という一例として記しておきます。
</Callout>

### ヘルパは「信頼できない文字列を読んで穴を開ける」仕組み

ヘルパは、利用者やサーバが送ってきた文字列を解釈して、ファイアウォールに穴を開けます。攻撃者が FTP の制御接続らしく見えるものを作れれば、意図しない穴を開けさせられるかもしれません。このため Linux は、以前は 21 番の通信に自動で FTP のヘルパを付けていましたが、カーネル 4.7 からこの自動の割り当てを既定で止めました（[firewalld: Automatic Helper Assignment](https://firewalld.org/2016/10/automatic-helper-assignment)）。netfilter の開発者たちの文書は、上で使ったように **`CT` ターゲットで、ヘルパを付ける通信を明示的に絞る**ことと、`RELATED` を通す規則もヘルパの種類やポートの範囲で絞ることを勧めています（[Secure use of iptables and connection tracking helpers](https://home.regit.org/netfilter-en/secure-use-of-helpers/)）。

## FTPS: FTP の上に TLS をかける

### 明示的な FTPS（AUTH TLS）

FTP に TLS をかける標準は [RFC 4217](https://www.rfc-editor.org/rfc/rfc4217.html) です。その土台は、1997 年に FTP の認証と保護の枠組みを定めた [RFC 2228](https://www.rfc-editor.org/rfc/rfc2228.html) で、`AUTH`、`PBSZ`、`PROT`、`CCC` といったコマンドはそこで定義されました。RFC 4217 は、この枠組みの「保護の方式」に TLS を当てはめたものです。

制御接続は平文の 21 番で始まり、`AUTH TLS` で TLS に切り替えます（[RFC 4217 4](https://www.rfc-editor.org/rfc/rfc4217.html)）。第 117 回の型 2 で、第 145 回のメールの STARTTLS と同じ構造です。`ll118-ftps` に TLS なしでログインしようとすると、パスワードを送る前に断られます。

```
< 220 (vsFTPd 3.0.5)
> USER alice
< 530 Non-anonymous sessions must use encryption.
curl: (67) Access denied: 530
```

curl に `--ssl-reqd`（TLS が使えなければ失敗する）を付けて取得します。TLS のハンドシェイクの細かい行は省きました。

```
$ curl -v --ssl-reqd --cacert ca.crt -u alice:correct-horse ftp://ll118-ftps/hello.txt
* Connected to ll118-ftps (172.21.0.3) port 21
< 220 (vsFTPd 3.0.5)
> AUTH SSL
< 234 Proceed with negotiation.
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 / secp256r1 / id-ecPublicKey
*  subjectAltName: host "ll118-ftps" matched cert's "ll118-ftps"
*  SSL certificate verify ok.
> USER alice
< 331 Please specify the password.
> PASS correct-horse
< 230 Login successful.
> PBSZ 0
< 200 PBSZ set to 0.
> PROT P
< 200 PROT now Private.
> EPSV
< 229 Entering Extended Passive Mode (|||30004|)
* SSL reusing session with ALPN '-'
> RETR hello.txt
< 150 Opening BINARY mode data connection for hello.txt (15 bytes).
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 / secp256r1 / UNDEF
* Connected 2nd connection to 172.21.0.3 port 30004
hello from ftp
```

curl が送ったのは `AUTH TLS` ではなく `AUTH SSL` でした。RFC 4217 の時点の名前は `AUTH TLS` ですが、古いクライアントのために `AUTH SSL` も同じ意味で受け付けるサーバが多く、Microsoft の IIS の仕様にも、両者を区別せず受け付けると書かれています（[MS-FTPS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-ftps/dbdd0923-8c29-4984-a95e-58dd6b0aff44)）。`openssl s_client -starttls ftp` でも同じサーバに入れました。

```
$ openssl s_client -starttls ftp -connect ll118-ftps:21 -CAfile ca.crt -verify_hostname ll118-ftps -ign_eof
Verification: OK
Protocol: TLSv1.3
331 Please specify the password.
230 Login successful.
200 PBSZ set to 0.
200 PROT now Clear.
200 PROT now Private.
```

（標準入力から `USER`、`PASS`、`PBSZ 0`、`PROT C`、`PROT P` を流し、応答の行だけを抜き出しています。）

### PBSZ と PROT: データ接続の保護は別に頼む

`AUTH TLS` が守るのは**制御接続だけ**です。データ接続をどう守るかは、`PROT` で別に決めます。RFC 2228 の `PROT` には C（Clear、保護なし）、S（Safe、完全性のみ）、E（Confidential、機密性のみ）、P（Private、両方）の 4 段階がありますが、TLS で使うのは **C と P だけ**です（[RFC 4217 9](https://www.rfc-editor.org/rfc/rfc4217.html)）。

- データ接続の最初の状態は **Clear でなければならない**（MUST）と決められています（[RFC 4217 9](https://www.rfc-editor.org/rfc/rfc4217.html)）。つまり `AUTH TLS` だけで止めたクライアントは、パスワードは守れても**ファイルの中身は平文で送ります**
- `PROT` の前には必ず `PBSZ` を送り、TLS の場合の値は `0` です（同）。`PBSZ` は RFC 2228 の枠組みで保護用のバッファの大きさを伝えるコマンドで、TLS には意味がありませんが、手順として残っています

上の `openssl s_client` の例のとおり、vsftpd は `PROT C` を受け付けました。ただ、`force_local_data_ssl=YES` の設定では、実際のデータ転送の段階で断ります。Python の `ftplib.FTP_TLS` で、`prot_c()` にしてファイルの一覧を取ろうとした結果です。

```
prot_c -> error_perm 522 Data connections must be encrypted.
```

<Callout type="warn" title="よくある誤解: FTPS にしたから、ファイルは暗号化されている">
  明示的な FTPS では、**制御接続とデータ接続の保護は別々**です。クライアントが `PROT P` を送らなければ、データ接続は平文のままです。
  サーバの側で「データ接続も TLS 必須」（vsftpd なら `force_local_data_ssl`）にしておかないと、クライアントの設定次第でファイルの中身が平文で流れます。
  tcpdump で確かめるなら、制御接続（21 番）だけでなく、**受動モードのポート範囲のほう**を見ます。
</Callout>

### tcpdump で見ると

明示的な FTPS の通信を記録し、21 番の中で文字として読める行を探すと、次の 3 行だけでした。

```
172.21.0.3.21 > 172.21.0.5.50082: ... length 20: FTP: 220 (vsFTPd 3.0.5)
172.21.0.5.50082 > 172.21.0.3.21: ... length 10: FTP: AUTH SSL
172.21.0.3.21 > 172.21.0.5.50082: ... length 31: FTP: 234 Proceed with negotiation.
```

この後ろはすべて TLS のレコードで、`PASS`、`correct-horse`、`hello from` のどれを探しても 0 件でした。平文の段階に残るのは、挨拶と切り替えの合図だけです。この平文の段階を狙う攻撃（切り替えの申し出を消す、境目にコマンドを紛れ込ませる）は、第 117 回で見たとおりです。

## データ接続にセッションの再開を求める理由

curl の出力に `SSL reusing session` という行がありました。データ接続の TLS のハンドシェイクで、**制御接続で確立した TLS のセッションを再開している**という意味です。vsftpd の `require_ssl_reuse=YES` は、これを必須にする設定で、説明には「データ接続が制御接続と同じマスターシークレットを知っていることを証明させる」とあります（[vsftpd.conf(5)](https://security.appspot.com/vsftpd/vsftpd_conf.html)）。

なぜ必要なのか。先ほどの Callout で見た**データ用のポートの横取り**を思い出してください。受動モードで待ち受けたポートに、本来のクライアントより先に誰かが接続し、そのまま TLS のハンドシェイクをすれば、その人がファイルを受け取るか、送り込むことができます。データ接続は新しい TCP 接続で、新しい TLS のハンドシェイクなので、**制御接続の相手と同じ人である保証がありません**。送信元のアドレスの確認は、同じ NAT の内側にいる人や、経路の途中の人を区別できません。

セッションを再開できるのは、制御接続の TLS で共有した秘密を持っている者だけです（TLS 1.3 では、第 113 回の PSK による再開です）。**再開を必須にすれば、データ接続の相手が制御接続の相手と同じだと暗号の上で確かめられます**。RFC 4217 も、サーバがデータ接続にキャッシュ済みのセッションの使用を求めるのは妥当だと書いています（[RFC 4217 10.2](https://www.rfc-editor.org/rfc/rfc4217.html)）。

curl の `--no-sessionid` で再開を止めると、次のようになりました。

```
$ curl -v --no-sessionid --ssl-reqd --cacert ca.crt -u alice:correct-horse ftp://ll118-ftps/hello.txt
> PROT P
< 200 PROT now Private.
> EPSV
< 229 Entering Extended Passive Mode (|||30007|)
> RETR hello.txt
< 150 Opening BINARY mode data connection for hello.txt (15 bytes).
curl: (18) transfer closed with 15 bytes remaining to read
```

サーバのログには、理由がはっきり残っていました。

```
[alice] DEBUG: Client "172.21.0.5", "No SSL session reuse on data channel."
[alice] FTP response: Client "172.21.0.5", "522 SSL connection failed: session reuse required"
```

Python の `ftplib.FTP_TLS` は、**再開をしないクライアント**の実例です。手元の Python 3.12.15 の `ntransfercmd` は、データ接続を新しいセッションとして TLS で包むだけでした。

```python
def ntransfercmd(self, cmd, rest=None):
    conn, size = super().ntransfercmd(cmd, rest)
    if self._prot_p:
        conn = self.context.wrap_socket(conn,
                                        server_hostname=self.host)
    return conn, size
```

```
prot_p -> error_perm 522 SSL connection failed: session reuse required
```

ログインも `PROT P` も通るのに、ファイルの一覧を取る段階で失敗します。クライアント側で再開を行う機能を足す要望は、2026 年 10 月の時点でも未解決のままです（[python/cpython#63699](https://github.com/python/cpython/issues/63699)）。vsftpd の説明自身も、`require_ssl_reuse` は安全な既定値だが多くのクライアントを動かなくするので、無効にしたくなるかもしれない、と認めています（[vsftpd.conf(5)](https://security.appspot.com/vsftpd/vsftpd_conf.html)）。**「つながらないから `require_ssl_reuse=NO` にする」は、データ接続の乗っ取りへの守りを外すこと**だと理解したうえで判断します。

<Callout type="tip" title="データ接続の証明書も同じものを">
  RFC 4217 は、データ接続でサーバが示す証明書を、対応する制御接続のものと同じにすることを強く勧めています（[RFC 4217 15.1.1](https://www.rfc-editor.org/rfc/rfc4217.html)）。
  クライアントは制御接続でしか名前を確かめていないことが多いので、データ接続で別の証明書が出てきても気づきにくいからです。セッションの再開は、この点でも制御接続とデータ接続を結び付けます。
</Callout>

## TLS をかけると ALG が読めなくなる

ここで、ファイアウォール役のコンテナに戻ります。FTP のヘルパを付けたまま、今度は明示的な FTPS のサーバ（172.21.0.3）に `PASV` で接続しました。

```
$ curl -v --connect-timeout 5 --disable-epsv --ssl-reqd -k -u alice:correct-horse ftp://172.21.0.3/hello.txt
> AUTH SSL
< 234 Proceed with negotiation.
> PASV
< 227 Entering Passive Mode (172,21,0,3,117,49).
*   Trying 172.21.0.3:30001...
curl: (28) Failed to connect to 172.21.0.3 port 21 after 5003 ms: Could not connect to server
-- expect events:
（何も出ない）
```

（この実験では、ファイアウォールの挙動だけを見るために `-k` で証明書の確認を省いています。）

curl の画面には `227` が見えていますが、それは**TLS を解いた後の**クライアントの中の話です。ファイアウォールを通るのは TLS のレコードで、ヘルパには `227` の文字列が見えません。期待は 1 件も登録されず、データ接続は捨てられました。

解決策は、**受動モードのポート範囲を固定して、その範囲をファイアウォールで開けておく**ことです。サーバ側で `pasv_min_port` / `pasv_max_port` を 30000〜30009 にしていたのは、このためです（vsftpd の説明にも「ファイアウォールの設定を助けるために狭い範囲を指定できる」とあります。[vsftpd.conf(5)](https://security.appspot.com/vsftpd/vsftpd_conf.html)）。

```
iptables -A FORWARD -i eth0 -o eth1 -p tcp --dport 30000:30009 -m conntrack --ctstate NEW -j ACCEPT
```

```
> PASV
< 227 Entering Passive Mode (172,21,0,3,117,51).
> RETR hello.txt
< 150 Opening BINARY mode data connection for hello.txt (15 bytes).
hello from ftp
< 226 Transfer complete.
```

マネージドのサービスも同じ形を取っています。AWS Transfer Family は、FTP と FTPS のデータ接続に 8192〜8200 番の範囲を使うと明記しています（[AWS Transfer Family](https://docs.aws.amazon.com/transfer/latest/userguide/what-is-aws-transfer-family.html)）。

| | 平文の FTP | FTPS |
| --- | --- | --- |
| ALG が `227` / `PORT` を読めるか | 読める | 読めない |
| データ用のポートを開ける方法 | ヘルパの期待（その接続だけ一時的に） | 受動ポートの範囲を常に開けておく |
| NAT の内側のサーバ | ALG が `227` のアドレスを書き換えることもある | `pasv_address` などで外側のアドレスを書かせる |
| 能動モード（クライアントが NAT の内側） | ALG が `PORT` を書き換えれば通ることもある | ALG が `PORT` を読めないので通らない |

### CCC: 制御接続を平文に戻す

もう 1 つの逃げ道として、RFC 2228 には **CCC**（Clear Command Channel）があります。ログインが済んだ後で制御接続の TLS をやめ、平文に戻すコマンドです。RFC 4217 は、これが使われるのは多くの場合 NAT やファイアウォールといった**境界の機器の制約のため**だと書き（[RFC 4217 5](https://www.rfc-editor.org/rfc/rfc4217.html)）、同時に CCC はセキュリティ上の問題を生みうると警告しています（[RFC 4217 15.3](https://www.rfc-editor.org/rfc/rfc4217.html)）。curl にも `--ftp-ssl-ccc` があり、説明は「認証の後で TLS の層を止める。残りの制御チャネルの通信は暗号化されない」です（[curl(1)](https://curl.se/docs/manpage.html)）。

パスワードは守れますが、その後のコマンド（どのファイルを取ったか、消したか）は読めますし、書き換えもできます。**ALG を働かせるために、守りの一部を自分から外す**取引です。ポートの範囲を開けられるなら、そちらを選びます。

## 暗黙の FTPS: 990 番と、標準にならなかった経緯

もう 1 つの形が、**接続の最初から TLS を話す**暗黙の FTPS です。第 117 回の型 1 にあたり、HTTPS や IMAPS と同じです。

```
$ printf "" | nc -w 2 ll118-ftpsi 990 | head -c 20 | xxd
（何も返らない）
$ printf "QUIT\r\n" | nc -w 2 ll118-ftps 21
220 (vsFTPd 3.0.5)
221 Goodbye.
$ printf "QUIT\r\n" | openssl s_client -connect ll118-ftpsi:990 -CAfile ca.crt -quiet
depth=0 CN=ftp.example.com
verify return:1
220 (vsFTPd 3.0.5)
```

21 番は TCP がつながった瞬間に平文の `220` を送ってきますが、990 番は黙って ClientHello を待ちます。TLS を張った後で、初めて `220` が届きます。curl では URL を `ftps://` にすると暗黙の FTPS になります。

```
$ curl -v --cacert ca.crt -u alice:correct-horse ftps://ll118-ftpsi/hello.txt
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384 / secp256r1 / id-ecPublicKey
* Connected to ll118-ftpsi (172.21.0.6) port 990
< 220 (vsFTPd 3.0.5)
> USER alice
< 331 Please specify the password.
> PASS correct-horse
< 230 Login successful.
> PBSZ 0
< 200 PBSZ set to 0.
> PROT P
```

暗黙の FTPS は、**どの RFC にも書かれていません**。IANA の登録簿には 990 番が `ftps`（"ftp protocol, control, over TLS/SSL"）として載っていますが、参照する文書の欄は空です（[IANA: Service Name and Transport Protocol Port Number Registry](https://www.iana.org/assignments/service-names-port-numbers/service-names-port-numbers.xhtml?search=990)）。RFC 4217 が定めているのは、21 番で `AUTH` から始める明示的な方式だけです。

Microsoft の IIS の仕様（MS-FTPS）は、暗黙の FTPS は元々、すでに失効した**ドラフト**に書かれていたと説明しています。さらに、990 番を使う暗黙の FTPS を拡張として残している理由を、**古いファイアウォールのパケットフィルタが、暗号化された通信と平文の通信の混在に混乱し、FTP の接続を切ることがあるので、別のポートに分けるため**だとしています（[MS-FTPS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-ftps/dbdd0923-8c29-4984-a95e-58dd6b0aff44)）。前の節で見た「ALG が TLS の途中で読めなくなる」問題への、実装側の回避策だったわけです。同じ文書によれば、暗黙の FTPS では TLS が張れた時点で `PBSZ 0` と `PROT P` を受け取ったものとみなし、データ接続も既定で保護します。

vsftpd は、`implicit_ssl=YES` にすると「すべての接続で最初に TLS のハンドシェイクを期待する」動きになり、明示的な方式や平文も受けたいなら別の待ち受けのプロセスを立てるよう書いています（[vsftpd.conf(5)](https://security.appspot.com/vsftpd/vsftpd_conf.html)）。今回 `ll118-ftpsi` を別のコンテナにしたのはこのためです。

第 117 回で見たとおり、メールでは RFC 8314 が「最初から TLS」を推奨し直しました。FTP にはそのような文書はなく、**標準は明示的な方式、実際には両方が使われている**という状態が続いています。

## SFTP と FTPS を並べる

名前は似ていますが、第 118 回の SFTP と FTPS は、土台からまったく別のプロトコルです。

| | SFTP（第 118 回） | FTPS（明示的） | FTPS（暗黙） |
| --- | --- | --- | --- |
| 土台 | SSH のサブシステム | FTP + TLS（RFC 4217） | FTP + TLS（標準なし） |
| TCP 接続の数 | 1 本（チャネルで多重化） | 制御 1 本 + 転送ごとにデータ 1 本 | 同左 |
| 使うポート | 22 | 21 と、受動用の範囲 | 990 と、受動用の範囲 |
| サーバの確認 | ホスト鍵（`known_hosts`、SSH 証明書） | X.509 の証明書（第 111 回） | 同左 |
| 利用者の認証 | SSH の公開鍵、パスワードなど（第 115 回） | `USER` / `PASS`、クライアント証明書 | 同左 |
| データ接続の保護 | 接続全体が常に暗号化 | `PROT P` を送ったときだけ | 既定で保護 |
| NAT とファイアウォール | 22 番を 1 つ通せばよい | ポートの範囲を開ける。ALG は働かない | 同左 |
| データ接続の乗っ取りへの守り | 不要（別の接続がない） | TLS セッションの再開を必須に | 同左 |

運用の手間だけを見れば、SFTP のほうがはるかに単純です。それでも FTPS が残っているのは、**相手の側が FTP を前提にしている**からです。取引先の業務システムが FTP のクライアントを組み込んでいる、X.509 の証明書で相手を確かめる運用がすでにある、といった事情です。AWS Transfer Family が SFTP、FTPS、FTP、AS2 を並べて提供し、「顧客や取引先の側の認証、アクセス、ファイアウォールの設定を変えずに移行できる」ことを売りにしているのは、こうした相手を抱えた利用者が多いことの表れでしょう。同じページは、ファイル転送のプロトコルが金融、医療、広告、小売といった業種でのデータ交換に使われているとも書いています（[AWS Transfer Family](https://docs.aws.amazon.com/transfer/latest/userguide/what-is-aws-transfer-family.html)）。何を基準に選ぶかは、第 124 回でまとめます。

<Callout type="note" title="同じ証明書を共有する FTP サーバ">
  FTPS のサーバが Web サーバと同じワイルドカード証明書を持っていると、HTTPS の要求を FTP のサーバへ付け替える攻撃（ALPACA）の踏み台になりえます。
  FTP のサーバは、知らないコマンドに「500 Unknown command」と返しながら、次の行を読み続けるからです。第 124 回で手元で再現します。
</Callout>

## 何と組み合わさって機能するか

| 部品 | この回での役割 | 呼び戻す回 |
| --- | --- | --- |

| NAT と conntrack | 外から内への接続を通さない。ヘルパが期待を登録し、`PORT` を書き換える | 第 76 回 |

## まとめ

- FTP は、コマンドの**制御接続**とファイルの**データ接続**を別の TCP 接続にする（RFC 959）。データ接続の宛先は、制御接続の中の文字列で毎回決まる
- 受動モード（`PASV` / `EPSV`）はサーバが待ち受けてクライアントが接続し、能動モード（`PORT` / `EPRT`）はその逆。NAT の内側のクライアントでは受動モードしか素直に通らない。`EPSV` の `229` はポートだけを返すので、IPv6 や NAT と相性がよい（RFC 2428）
- 宛先を自由に書けることは、**バウンス攻撃**（他人のサービスにサーバから接続させる）とデータ用のポートの横取りを生んだ。今日のサーバはデータ接続の相手を制御接続の相手と同じアドレスに限る
- ファイアウォールや NAT の **ALG**（Linux では conntrack のヘルパ）は、制御接続の中身を読んで期待を登録し、`PORT` のアドレスを書き換える。信頼できない文字列で穴を開ける仕組みなので、Linux はカーネル 4.7 から自動の割り当てをやめ、`CT` ターゲットでの明示を求める
- 明示的な FTPS は 21 番で `AUTH TLS` から始める（RFC 4217）。データ接続は既定で Clear で、`PBSZ 0` と `PROT P` を送って初めて暗号化される。サーバ側でデータ接続の TLS を必須にしておく
- データ接続に**制御接続の TLS セッションの再開**を求めると、データ接続の相手が制御接続の相手と同じだと確かめられる（vsftpd の `require_ssl_reuse`）。再開しないクライアント（Python の `ftplib` など）はここで `522` になる
- TLS をかけると ALG は中身を読めない。**受動ポートの範囲を固定して開ける**のが正攻法で、CCC で制御接続を平文に戻すのは守りを外す取引
- 暗黙の FTPS（990 番）は IANA に登録はあるが、RFC はない。失効したドラフトに由来し、ALG の混乱を避けるために実装が残してきた
- SFTP は 1 本の接続で済み、運用は単純。FTPS は相手の側が FTP を前提にしているときに選ばれる

この回では、TLS の上に載せたせいでネットワークの機器が中身を読めなくなる、という問題を見ました。次の第 120 回では、逆に SSH の中に**別の通信をまるごと通す**使い方を見ます。`-L`、`-R`、`-D` のポート転送の実際と危険、`ProxyCommand` の正体である標準入出力の転送、L3 の VPN になる `-w`、そして SSH の上で動く Git と、SSH で起動して UDP に移る Mosh です。
