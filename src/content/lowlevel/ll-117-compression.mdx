## 読める者は、縮められる

第 116 回で、LB が TLS を終えて平文を読めるので、振り分けやヘッダの付与とともに**圧縮**もできる、と一言だけ触れました。この回は、その圧縮を正面から見ます。

圧縮は、低レイヤのどの層にも顔を出します。第 57 回の DNS は同じ名前を圧縮ポインタで指し直し、第 65 回の HTTP/2 はヘッダを HPACK で縮め、第 69 回の gRPC はメッセージ本体を gzip で包み、第 164 回のコンテナイメージは層を tar.gz で固めていました。やっていることは、どれも同じ 1 つの発想です。**繰り返しを見つけて、短く言い換える。**

ただ、この章（相手を確かめて話す）に圧縮を置くのには理由があります。圧縮は、暗号化と組み合わさると**事故を起こす**からです。第 107 回で見たとおり、AEAD は中身を隠しますが、**長さは隠しません**。縮んだか縮まなかったかという 1 ビットが、暗号文の外から観測できてしまう。これが CRIME と BREACH で、TLS 1.3 が圧縮の機能を削除した理由でもあります。

この回では、3 つの問いで圧縮を読みます。

1. **何を縮めるのか**（圧縮は何を手がかりに縮めているか）
2. **どこで縮めるのか**（HTTP のどの層、どの機械で縮むか）
3. **縮めると何が漏れるか**（長さから何が分かってしまうか）

## 何を縮めるのか: 繰り返しと偏り

圧縮が食べているのは**冗長性**、つまり「前にも出てきた」と「どれも同じくらいの頻度では出てこない」の 2 つです。可逆圧縮の多くは、この 2 つにそれぞれ道具を当てます。

```
元データ ─▶ [ LZ77 ]  前に出た並びを「n バイト前のものを m バイト」と後方参照に置き換える
         ─▶ [ ハフマン等 ]  よく出る記号に短いビット列、まれな記号に長いビット列を割り当てる
         ─▶ 圧縮後
```

前者が **LZ77**（辞書式。少し前に出たバイト列への後方参照）、後者が**エントロピー符号化**（ハフマン符号や算術符号）です。この 2 段を組んだのが **DEFLATE** で、[RFC 1951](https://www.rfc-editor.org/rfc/rfc1951) が形式を定めています。よく聞く名前は、DEFLATE そのものではなく、その**包み**の違いです。

| 名前 | 中身 | 仕様 |
| --- | --- | --- |
| DEFLATE | LZ77 ＋ ハフマン。圧縮の本体 | [RFC 1951](https://www.rfc-editor.org/rfc/rfc1951) |
| zlib | DEFLATE に 2 バイトのヘッダと Adler-32 のチェックを付けた包み | [RFC 1950](https://www.rfc-editor.org/rfc/rfc1950) |
| gzip | DEFLATE に別のヘッダ（元ファイル名・時刻など）と CRC-32 を付けた包み | [RFC 1952](https://www.rfc-editor.org/rfc/rfc1952) |

つまり「gzip も zlib も、中身は同じ DEFLATE の別のラッパー」です。後から出た方式は、この 2 段を改良しました。**Brotli** は LZ77 とハフマンに加えて、Web のテキストでよく出る語をあらかじめ収めた**静的辞書**を持ちます（[RFC 7932](https://www.rfc-editor.org/rfc/rfc7932)）。**Zstandard**（zstd）は、圧縮レベルを広く取り、外部辞書を使え、展開が非常に速いのが特徴です（[RFC 8878](https://www.rfc-editor.org/rfc/rfc8878)）。

<Callout type="warn" title="よくある誤解: 「圧縮すれば、どんなデータも小さくなる」">
  圧縮が食べるのは冗長性です。**冗長性の無いデータは縮みません。** むしろラッパーの分だけ数バイト増えます。
  乱数の列、暗号化済みのデータ、そして JPEG や動画のように**すでに圧縮されているデータ**がこれに当たります。
  だから「暗号化の後で圧縮する」構成はほぼ無意味で、順序は必ず**圧縮してから暗号化**です（この順序が別の問題を生むことは後で見ます）。
  後の実験で、JPEG が 98%、乱数が 100%（わずかに増加）までしか縮まないことを確かめます。
</Callout>

## どこで縮めるのか: HTTP の 2 つの層

HTTP で「圧縮する」と言うとき、実は別の 2 つの場所があります。

```
                Content-Encoding            Transfer-Encoding
意味            表現そのものの符号化        転送のためのその場の符号化
効く範囲        端から端まで（end-to-end）  1 ホップずつ（hop-by-hop）
キャッシュ      表現の一部。Vary が要る     転送の都合。表現ではない
実務            gzip / br / zstd はほぼこちら  chunked がほぼ唯一の実用
```

**Content-Encoding** は「この表現は gzip で符号化してある」という、表現自体の性質です（[RFC 9110 8.4](https://www.rfc-editor.org/rfc/rfc9110#section-8.4)）。クライアントは受け取れる方式を **Accept-Encoding** で申告し（[RFC 9110 12.5.3](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.3)）、サーバがその中から選びます。符号化によって応答の中身が変わるので、キャッシュに対しては **`Vary: Accept-Encoding`** を付けて「この応答は Accept-Encoding ごとに別物だ」と知らせる必要があります（[RFC 9110 12.5.5](https://www.rfc-editor.org/rfc/rfc9110#section-12.5.5)）。この Vary を忘れると、gzip を受け取れない相手に gzip 済みの応答がキャッシュから返る事故が起きます（CDN での扱いは第 103 回）。

**Transfer-Encoding** は 1 ホップ区間だけの符号化で、HTTP/1.1 では主に `chunked` が使われます（[RFC 9112 6.1](https://www.rfc-editor.org/rfc/rfc9112#section-6.1)）。圧縮の文脈で実際に使うのはほぼ Content-Encoding の方です。

縮める機械も 1 か所とは限りません。第 116 回で見たように LB やリバースプロキシが TLS を終えて平文を読めるなら、そこで圧縮してから後ろへ渡すことも、アプリが圧縮した応答をそのまま通すこともできます（LB の置き方は第 73 回）。どの機械が縮めるかは、CPU をどこで使うか、そして次に見る漏れをどの範囲で抱えるか、の設計になります。

圧縮が効くのは HTTP 本文だけではありません。場所ごとに、使う道具も狙いも違います。

| どこ | 何を縮める | 方式 | 回 |
| --- | --- | --- | --- |
| HTTP 本文 | 応答（と要求）の本文 | gzip / Brotli / zstd（Content-Encoding） | この回 |
| HTTP ヘッダ | 繰り返されるヘッダ | HPACK / QPACK（DEFLATE では**ない**） | 第 65 回、第 66 回 |
| gRPC | メッセージ本体 | `grpc-encoding`（gzip など） | 第 69 回 |
| DNS | メッセージ内の重複する名前 | 圧縮ポインタ | 第 57 回 |
| コンテナ | イメージの各層 | tar + gzip / zstd | 第 164 回 |
| TLS | （記録層の圧縮） | **TLS 1.3 で削除** | 第 115 回 |

ヘッダ圧縮が DEFLATE ではなく専用の HPACK なのは、まさにこの回のテーマである漏れが理由です。第 65 回で見たとおり、SPDY がヘッダを DEFLATE で縮めたところ **CRIME** に突かれ、HPACK は「値全体でしか一致を取らない」設計で 1 文字ずつの推測を封じました。

## 手元で確かめる: 何が、どれだけ、どの速さで縮むか

まず素材ごとの縮み方を測ります。macOS 26.2 / Apple M1 Pro、uv で立てた Python 3.12.12（zlib 1.2.12、brotli 1.2.0、zstandard 0.25.0 / libzstd 1.5.7）です。素材は HTML（RFC 9110 の HTML 版、約 1.19 MB）、JSON（`package-lock.json`、約 294 KB）、JPEG 画像（約 273 KB）、乱数 1 MB です。

HTML（テキスト）の結果です。比率は「圧縮後 / 元」です。

```
method          size  ratio  comp MB/s  decomp MB/s
gzip -1       269267  22.7%        184         1114
gzip -6       212848  17.9%         56         1499
gzip -9       209516  17.6%         31         1415
brotli 4      194860  16.4%        170          798
brotli 11     152518  12.8%          1          616
zstd 1        227833  19.2%        416         1707
zstd 3        208825  17.6%        459         1647
zstd 19       163688  13.8%          3         1858
```

読み取れることが 3 つあります。**縮みは方式とレベルで大きく変わる**（gzip -6 の 17.9% に対し brotli 11 は 12.8%）。**最高の縮みは猛烈に遅い**（brotli 11 は 1 MB/s。gzip -6 の 56 分の 1）。そして **zstd は、同じ比率をはるかに速く出す**（zstd -3 は gzip -6 とほぼ同じ 17.6% を約 8 倍の速さで）。JSON でも傾向は同じでした（gzip -6 で 21.7%、brotli 11 で 18.7%）。

展開の速さも押さえておきます。どの方式も圧縮より展開の方がはるかに速く、zstd は特に速い（上の表で 1600〜1900 MB/s、JPEG では 3 万 MB/s を超える場面も）。**圧縮は 1 回、展開は配った回数だけ起きる**ので、配信では展開の速さが効きます。

次に、縮まないデータです。

```
photo.jpg (273 KB)   gzip -6  98.4%    brotli 11  97.7%    zstd 19  98.4%
random.bin (1 MB)    gzip -6 100.0%    brotli 11 100.0%    zstd 19 100.0%
```

**すでに圧縮された JPEG は、どの方式でもほとんど縮みません。** 乱数に至っては 100%、わずかに増えます。先の誤解の Callout のとおりで、暗号化済みのデータも同じです。だから CPU を使って JPEG を gzip で包み直すのは、ほぼ無駄です。

### 誰が何を返しているか

実在の公開サイトに、`Accept-Encoding` を変えて読み取り専用で `HEAD`/`GET` し、`Content-Encoding` を見ました（curl 8.7.1、本文は破棄）。

```
サイト                         要求した Accept-Encoding        返ってきた Content-Encoding
www.wikipedia.org              gzip                            gzip
www.wikipedia.org              br / zstd のみ                  （無し＝identity）
developer.mozilla.org          gzip, deflate, br, zstd         br
www.cloudflare.com             gzip, deflate, br, zstd         br
www.instagram.com              gzip, deflate, br, zstd         zstd
```

**同じ URL でも、クライアントが申告した方式でサーバの返し方が変わります。** Wikipedia は gzip だけに応じ、br や zstd しか受け取れないと言うと無圧縮で返しました。多くのサイトが `Vary: Accept-Encoding` を付けており、「この応答は Accept-Encoding ごとに別物」とキャッシュに知らせています。br を返したサイト（MDN、Cloudflare）は、あらかじめ最高レベルで圧縮したものを置いている（precompressed）典型です。brotli 11 は上で見たとおり遅いので、静的な資産を事前に 1 回縮めておき、動的な応答には速い zstd や gzip を使う、という組み合わせになります。

## 縮めると何が漏れるか: 長さは隠れない

ここからが、この回を TLS の章に置いた理由です。

第 107 回で、AEAD は中身を隠すが長さは隠さない、と見ました。圧縮は、その**長さを中身に依存させます**。「よく出る並びほど短くなる」のだから、暗号文の長さを見れば「平文にどれだけ繰り返しがあったか」が分かる。**秘密と、攻撃者が選べる文字列が、同じ圧縮の文脈に入ると、長さが秘密を漏らすオラクルになります。**

これが **CRIME**（2012、[Qualys の解説](https://blog.qualys.com/ssllabs/2012/09/14/crime-information-leakage-attack-against-ssltls)）と **BREACH**（2013、[breachattack.com](https://breachattack.com/)）です。CRIME は TLS 記録層の圧縮を、BREACH は HTTP 応答本文の圧縮を狙います。BREACH の論文は、根本の原因を「秘密（CSRF トークンなど）と利用者の入力が同じ応答に入り、同じ圧縮の文脈を共有することが非常に多い」と述べ、TLS がこれを防げないのは「プロトコルの設計時、中間者が被害者のブラウザ経由で任意の平文を送れるという脅威が想定されていなかったから」だと説明しています（[BREACH 論文](https://css.csail.mit.edu/6.566/2018/readings/breach.pdf)）。

### 手元で再現する

防御を理解するために、127.0.0.1 の中だけで長さのオラクルを再現します。自己署名証明書で実際の TLS を張り、**秘密のトークンと、攻撃者が選べるクエリ `q` を同じページに入れて gzip した応答**を返すサーバを立てます。攻撃側は `q` に「トークンはこれで始まるのでは」という推測を入れ、**TLS で流れてきたバイト数**を数えるだけです。推測がトークンの続きと一致すると、その分が後方参照として縮み、応答が短くなります。

トークンの 7 文字目を当てる場面の、推測ごとのバイト数です（26 文字＋`_` のうち抜粋）。

```
推測        TLS で受け取った総バイト数
TOKEN_U:    209 bytes
TOKEN_V:    208 bytes   <= 最小
TOKEN_W:    209 bytes
...（V 以外はすべて 209）
```

**正しい 1 文字だけが 1 バイト短い。** この 1 バイトを手がかりに頭から順に当てると、6 文字の秘密 `TOKEN_VLRACE` を、1 文字につき 1 回の推測だけで完全に復元できました。TLS で暗号化されていても、記録のバイト数は外から数えられるので、暗号化は何の助けにもなりません。

### 止める: 長さをぼかすか、秘密を毎回変えるか

BREACH の論文は、対策として「圧縮の無効化」「秘密と利用者の入力を分ける」「秘密をリクエストごとに変える」「秘密のマスキング」「長さを隠す」などを挙げています（[BREACH 論文](https://css.csail.mit.edu/6.566/2018/readings/breach.pdf)）。圧縮を切るのは確実ですが、転送量の代償が大きくなります。そこで、手元で 2 つの対策を比べました。

- **長さをぼかす**: 応答ごとに、秘密の前へ長さがランダムな詰め物（2〜16 文字）を足す。秘密そのものは毎回同じ文字列のまま応答に入る
- **マスキング**: 応答ごとにランダムなバイト列 `m` を作り、`m` と「秘密と `m` の XOR」を並べて埋め込む。受け取った側は XOR し直せば秘密に戻せるが、**応答の中に秘密の文字列そのものは現れない**

同じ攻撃を、1 つの推測あたり 1 回と 30 回（最も短かった値を採る）で行いました（別の実行で、秘密は `TOKEN_RRLZVQ`）。

```
対策           1 推測あたり   復元した文字列    一致
なし            1 回          TOKEN_RRLZVQ      一致
長さをぼかす    1 回          TOKEN_BGAAAK      不一致
長さをぼかす   30 回          TOKEN_RRLZVQ      一致
マスキング      1 回          TOKEN_DBPERS      不一致
マスキング     30 回          TOKEN_FSBHBA      不一致
```

**長さをぼかすだけでは、試行を増やせば破られます。** 詰め物の長さはランダムでも、推測が当たったときに縮む 1 バイトは毎回同じだけ効くので、何度も測って最小値を取れば信号が浮かび上がります。BREACH の論文も、長さを隠す対策は試行を増やせば平均で打ち消せると指摘しています。

**マスキングは、試行を増やしても破れませんでした。** 推測と一致する並びが、そもそも応答の中に無いからです。CSRF トークンをリクエストごとにマスクして埋め込むのは、この性質を使った対策です。実務では、さらに「秘密と攻撃者の入力を同じ応答に入れない」ことと、SameSite の Cookie（第 130 回）を組み合わせます。攻撃者のサイトから送らせた要求に Cookie が付かなければ、その応答には利用者の秘密がそもそも入らないからです。

<Callout type="warn" title="よくある誤解: 「HTTPS なら圧縮しても安全」">
  暗号化が隠すのは**中身**で、**長さ**ではありません。圧縮は長さを中身に依存させるので、
  **攻撃者が一部を選べる応答を、秘密ごと圧縮すると、長さから秘密が漏れます**。
  これは実装のバグではなく、圧縮と暗号化を素直に重ねたときに原理的に生じます。
  だから「秘密を含む応答の、攻撃者が制御できる部分」は圧縮の文脈から外すか、秘密をリクエストごとに変えます。
  なお、マスキングが守るのはマスクした値だけで、同じ応答の他の秘密は守りません（[Karakostas と Zindros, 2016](https://www.blackhat.com/docs/eu-16/materials/eu-16-Karakostas-Ctx-Eliminating-BREACH-With-Context-Hiding-wp.pdf)）。
</Callout>

### だから TLS 1.3 は圧縮をやめた

CRIME の直接の対策は TLS 記録層の圧縮を無効にすることでした。TLS 1.3 はこれを恒久化し、**プロトコルから圧縮の機能そのものを削除**しました（[RFC 9846](https://www.rfc-editor.org/rfc/rfc9846)。2026 年 7 月に RFC 8446 を置き換えた TLS 1.3 の仕様）。第 115 回の表で「再ネゴシエーション、圧縮：TLS 1.2 はあり、1.3 はなし」と並んでいたのは、これです。HTTP 本文の圧縮（Content-Encoding）はアプリの層に残り続けるので、BREACH への対策はアプリの側で続ける必要があります。

## もう一度、縮まないものと展開爆弾

縮まないデータの話には、裏側があります。**繰り返しだらけのデータは、極端に縮む。** 第 192 回の **zip bomb（展開爆弾）**がこれで、受け取った側が何も考えずに展開すると、送られた量の何千倍ものメモリやディスクを使わされます。

1 GiB のゼロを、メモリに全部載せずに流し込みながら圧縮しました。

```
gzip -9:  1,073,741,824 bytes of zeros -> 1,043,656 bytes   約 1028:1
zstd 19:  1,073,741,824 bytes of zeros ->    32,785 bytes   約 32751:1
```

**1 GiB が、gzip で約 1 MB、zstd で約 32 KB になります。** 逆に言えば、この小さなデータを受け取って素直に展開すると 1 GiB に膨らみます。`Content-Encoding` 付きのリクエストを受け付けるサーバや、アップロードされたアーカイブを展開するサーバは、これに晒されます。守りは第 192 回と同じで、**ヘッダが申告する展開後の大きさを信用せず、展開しながら数えて上限で止める**ことです。

## 実装ごとの違い

| 方式 | 得意なところ | 使いどころ |
| --- | --- | --- |
| gzip / DEFLATE | どこでも通じる。ほどほどに速くほどほどに縮む | 既定の無難な選択。古い相手にも通じる |
| Brotli | 静的辞書で Web テキストがよく縮む。最高レベルは非常に遅い | 静的資産を事前に最高レベルで圧縮して配る |
| Zstandard | レベルの幅が広く、低レベルが速い。外部辞書が使える | 動的な応答、ログ、大量データ。速さと比率の両取り |

**比率と速さは引き換え**で、どこで時間をかけられるかで選びます。1 回作って何度も配る静的ファイルには時間をかけて brotli 11、毎回その場で作る動的な応答には速い zstd の低〜中レベル、という使い分けです。

新しい動きとして、**Compression Dictionary Transport**（[RFC 9842](https://www.rfc-editor.org/rfc/rfc9842)、2025 年 9 月、Proposed Standard）があります。以前に配った応答（たとえば前のバージョンの JS）を**辞書**に指定し、次の応答を Brotli や Zstandard でその辞書を使って圧縮する仕組みで、版の差分だけを送るのに近い縮みが得られます。Chrome が出荷済みと報告されていますが、対応バージョンの正確な範囲はこの回では確認していません。

## まとめ

- 圧縮は冗長性（繰り返しと偏り）を食べる。LZ77 の後方参照とハフマン等のエントロピー符号化を組んだのが DEFLATE で、gzip も zlib もその別のラッパー。Brotli は静的辞書、zstd はレベルの幅と外部辞書と速さ
- HTTP では Content-Encoding（表現の符号化、end-to-end、Vary が要る）と Transfer-Encoding（転送の都合、hop-by-hop）が別物。gzip / br / zstd はほぼ前者。実在サイトは Accept-Encoding を見て返し方を変える
- すでに圧縮されたデータ（JPEG、暗号文、乱数）は縮まない。だから順序は必ず圧縮してから暗号化
- 暗号化は中身を隠すが長さを隠さない。圧縮は長さを中身に依存させるので、秘密と攻撃者の入力を同じ文脈で圧縮すると長さから秘密が漏れる（CRIME、BREACH）。手元で 1 バイトの差からトークンを復元できた。長さをぼかすだけでは試行を増やすと破られ、リクエストごとのマスキングでは止まった
- ヘッダ圧縮が DEFLATE でなく HPACK なのも、TLS 1.3 が圧縮を削除したのも、この漏れが理由
- 繰り返しだらけのデータは極端に縮む。1 GiB のゼロが zstd で約 32 KB。展開する側は宣言された大きさを信用せず、数えて止める

ここまでの章では、CA が署名した証明書を鎖でたどって相手を信じてきました。次の回からは、CA を置かずに相手を信じる別の道を見ます。**最初の接続で相手の鍵を覚え、次からはその鍵と一致するかだけを確かめる SSH** です。
