## 宛先が、動き続ける

第 88 回で見たとおり、Pod はどのノードに置かれるか分かりません。ノードが落ちれば別のノードに作り直され、更新のたびに新しい Pod に入れ替わります。**Pod の IP アドレスは、作り直されるたびに変わります。**

一方、Pod に繋ぎに行く側は、宛先を知っていなければなりません。

```
web（3 個）  ──→  api（5 個）  ──→  db
                   10.244.1.7
                   10.244.2.3     ← どれに送る？ 次の瞬間に消えるかもしれない
                   10.244.1.12
                   ...
```

この回では、この問題を 2 段に分けて見ます。

1. どのノードにいる Pod とも、IP で直接話せるようにする（**Pod ネットワーク**）
2. 入れ替わり続ける Pod の集まりに、**変わらない 1 つの宛先**を与える（**Service**）

## 1 段目: どの Pod とも、NAT なしで話せる

第 81 回で見た Docker の既定のネットワークでは、コンテナの IP はホストの中でしか意味を持たず、外へ出るときは NAT でホストのアドレスに書き換えられていました。

Kubernetes は、これと違う約束を置いています（[Kubernetes Docs](https://kubernetes.io/docs/concepts/services-networking/)）。

> Each pod in a cluster gets its own unique cluster-wide IP address.
>
> All pods can communicate with all other pods, whether they are on the same node or on different nodes. Pods can communicate with each other directly, without the use of proxies or address translation (NAT).

**クラスタ全体で一意な IP を、Pod ごとに 1 つ**。そして**アドレスを書き換えずに**、どのノードの Pod とも話せる。Pod の中のプロセスから見ると、自分の IP と、相手から見た自分の IP が一致します。

ただし、Kubernetes 自体はこの約束を**実現しません**。約束だけを決め、実現は **CNI**（Container Network Interface）のプラグインに任せています。

### CNI: 名前空間ができたら呼ばれる実行ファイル

第 87 回で見たとおり、Pod を作るとき、コンテナランタイムはまず Network 名前空間を用意します。その直後に、ランタイムは **CNI プラグインという実行ファイルを起動します**。

仕様はとても単純です（[CNI Specification](https://github.com/containernetworking/cni/blob/main/SPEC.md)）。

- 操作の種類（`ADD`、`DEL`、`CHECK` など）を環境変数 `CNI_COMMAND` で渡す
- 対象の Network 名前空間を `CNI_NETNS` で渡す
- 設定を JSON で標準入力に渡し、結果を JSON で標準出力に受け取る

```bash
CNI_COMMAND=ADD CNI_NETNS=/var/run/netns/pod-abc CNI_IFNAME=eth0 ... \
  /opt/cni/bin/bridge < net.conf
# → {"ips": [{"address": "10.244.1.7/24", ...}], ...}
```

API サーバも gRPC も出てきません。**実行ファイルを起動し、標準入出力で JSON をやり取りする**という、第 30 回のローダと第 42 回の fd の上にそのまま乗った取り決めです。だから、どんな言語でも、どんな方式でもプラグインを書けます。

プラグインが `ADD` で行うことは、第 81 回で見た Docker の作業とほとんど同じです。

```
 ノード A（10.0.0.1）                        ノード B（10.0.0.2）
 ┌──────────────────────────┐              ┌──────────────────────────┐
 │ Pod 10.244.1.7           │              │ Pod 10.244.2.3           │
 │   eth0 ═══ veth ═══┐     │              │     ┌═══ veth ═══ eth0   │
 │                    ブリッジ│              │ブリッジ                    │
 │   経路: 10.244.2.0/24    │   ─────────→ │                          │
 │         → 10.0.0.2 へ    │  ノード間の網 │                          │
 └──────────────────────────┘              └──────────────────────────┘
```

違うのは最後の 1 行です。**別のノードの Pod のアドレス範囲を、そのノードへ届ける経路**が必要になります。その実現方法がプラグインごとに違います。

| 方式 | やり方 | 代償 |
| --- | --- | --- |
| 経路を配る | 各ノードに「10.244.2.0/24 は 10.0.0.2 へ」と経路を足す | ノード間の網が Pod のアドレスを通せる必要がある |
| 包んで運ぶ（オーバーレイ） | Pod 宛てのパケットを、ノード宛ての UDP パケットに包む（VXLAN など） | ヘッダが増えて MTU が減る（第 55 回）。包む・剥がすコスト |
| クラウドの網に乗る | クラウドの仮想ネットワークから Pod に直接アドレスを割り当てる | クラウドの仕組みに依存する |

## 2 段目: どこにも存在しない IP

Pod 同士が IP で話せても、相手の IP は変わり続けます。そこで **Service** を作ります。

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api
spec:
  selector:
    app: api          # このラベルの Pod を束ねる
  ports:
    - port: 80
      targetPort: 8080
```

Service を作ると、**ClusterIP** という仮想 IP が 1 つ割り当てられます。たとえば `10.96.0.42` です。以後、`api` に繋ぎたい側は、この IP の 80 番に送ればよくなります。Pod が何回入れ替わっても、この IP は変わりません。

不思議なのは、**このアドレスを持っているインタフェースが、クラスタのどこにも存在しない**ことです。iptables や nftables のモードでは、どのノードで `ip addr` を見ても `10.96.0.42` は出てきませんし、ping にも応答しません。それでも、TCP で繋ぐと Pod に届きます。

届く理由は、第 81 回の `-p 8080:80` と同じです。**パケットがノードを通るときに、宛先を書き換えている**のです。

### 誰が、何に書き換えるのか

仕組みは 3 つの部品でできています。

```
 ① Service（selector: app=api）
        │  EndpointSlice コントローラがラベルの合う Pod を探し続ける
        ▼
 ② EndpointSlice: 10.96.0.42:80 の実体は
        10.244.1.7:8080（ready）
        10.244.2.3:8080（ready）
        10.244.1.12:8080（not ready）
        │  各ノードの kube-proxy が watch している
        ▼
 ③ 各ノードのカーネルのパケット書き換え規則
        宛先 10.96.0.42:80 → ready な 2 つのどれかに DNAT
```

① と ② は、第 86 回で見た調整ループそのものです。EndpointSlice のコントローラは、Service の selector に合い、かつ **ready**（第 91 回で見る readiness probe に通っている）な Pod を探して、その一覧を API サーバに書き続けます。

③ を担うのが、各ノードで動く **kube-proxy** です。名前に proxy と付いていますが、今の kube-proxy は**通信を中継しません**。EndpointSlice の変化を watch して、カーネルの書き換え規則を更新するだけです。パケットそのものは、第 55 回で見たカーネルの受信経路の中で、netfilter が書き換えます。

```bash
# iptables モードのノードで（抜粋）
sudo iptables -t nat -L KUBE-SERVICES -n
# KUBE-SVC-XXXX  tcp  --  0.0.0.0/0  10.96.0.42  tcp dpt:80
sudo iptables -t nat -L KUBE-SVC-XXXX -n
# KUBE-SEP-AAAA  statistic mode random probability 0.50000
# KUBE-SEP-BBBB
```

`statistic mode random probability 0.5` は、**半分の確率でこちらの Pod を選べ**という規則です。Pod が 3 つなら 1/3、残りの 1/2、残り全部、と確率を積み重ねて、均等に振り分けます。

### 規則の書き方は 3 通り

Linux では、書き換え規則の表現方法を選べます（[Kubernetes Docs](https://kubernetes.io/docs/reference/networking/virtual-ips/)）。

| モード | 仕組み | 状況 |
| --- | --- | --- |
| iptables | netfilter の規則を Service と Pod の数だけ並べる | 長く既定だった方式 |
| IPVS | カーネルの L4 ロードバランサを使う。ClusterIP をダミーのインタフェースに付ける | 1.35 で非推奨になった（[KEP-5495](https://github.com/kubernetes/enhancements/blob/master/keps/sig-network/5495-deprecate-ipvs-mode-in-kube-proxy/README.md)） |
| nftables | iptables の後継の仕組みで規則を書く | 1.33 で GA。将来の既定として推奨されている |

iptables の規則は上から順に照合されるため、Service が数千になると、規則の更新にも照合にも時間がかかるようになりました。nftables は集合（map）で引けるので、この問題が小さくなります。

さらに、第 95 回の eBPF を使う CNI プラグインの中には、kube-proxy を置かず、**ソケットを作る段階で宛先を実体の Pod に差し替えてしまう**ものもあります。パケットごとに書き換える必要がなくなります。

どの方式でも、**仮想 IP で待ち受けているプロセスはどこにもいない**という点は同じです。届く前に、カーネルが宛先を差し替えています。

## 書き換えは、接続の最初の 1 回だけ

第 53 回で、TCP の接続は両端のアドレスとポートの組で識別されると見ました。途中で宛先が書き換わるなら、**同じ接続の 2 つ目以降のパケットも、同じ Pod に書き換えられ**なければ困ります。応答のパケットも、元の `10.96.0.42` から来たように書き戻さなければなりません。

これを覚えているのが、カーネルの **conntrack**（接続追跡）です。最初のパケットで振り分け先を決めると、その対応を表に記録し、以後の同じ接続のパケットは表を引いて同じように書き換えます。

```bash
sudo conntrack -L -d 10.96.0.42
# tcp 6 86390 ESTABLISHED src=10.244.1.20 dst=10.96.0.42 dport=80
#       src=10.244.2.3 dst=10.244.1.20 sport=8080 ...   ← 実際の相手
```

このことから、実務でよく当たる性質が 1 つ出てきます。

<Callout type="warn" title="長く生きる接続は、振り分け直されない">
  振り分けを決めるのは**接続の最初**だけです。
  HTTP/2 や gRPC のように、1 本の TCP 接続を長く使い回して多数のリクエストを流す通信では、
  すべてのリクエストが最初に選ばれた 1 つの Pod に行き続けます。
  Pod を 5 個に増やしても、既存の接続は新しい Pod に一切流れません。

  Service の振り分けは **L4（接続単位）** であって、**L7（リクエスト単位）ではない**ということです。
  リクエスト単位で散らしたければ、クライアント側で複数の接続を張って自分で振り分けるか、
  HTTP を理解するプロキシを間に置く必要があります。
  後者を仕組みとして全体に行き渡らせたものが、次回のサービスメッシュです。
</Callout>

## 名前で引く

`10.96.0.42` を設定ファイルに書くのは不便なので、**クラスタ内 DNS** があります。Service を作ると、次の形の名前が引けるようになります（[Kubernetes Docs](https://kubernetes.io/docs/concepts/services-networking/dns-pod-service/)）。

```
api.shop.svc.cluster.local   →  10.96.0.42
 │    │    │   └ クラスタのドメイン
 │    │    └ Service であること
 │    └ 名前空間（Kubernetes の、第 76 回とは別物の名前空間）
 └ Service 名
```

Pod の `/etc/resolv.conf` は、kubelet が次のように書き込みます。

```
nameserver 10.96.0.10
search shop.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

`search` があるので、同じ名前空間の中なら `api` とだけ書けば引けます。第 81 回で、Docker のユーザ定義ネットワークでは `127.0.0.11` の組み込み DNS がサービス名を解決していたのと、同じ発想です。

<Callout type="note" title="ndots:5 の副作用">
  `ndots:5` は、「ドットが 5 個未満の名前は、まず search の候補を順に付けて引いてみる」という指定です。
  `api.example.com`（ドット 2 個）を引くと、
  `api.example.com.shop.svc.cluster.local`、`api.example.com.svc.cluster.local`、……と
  存在しない名前を順に問い合わせてから、最後に本来の名前を引きます。
  外部の名前を大量に引くアプリでは、DNS の問い合わせが数倍に増えます。
  末尾にドットを付けて `api.example.com.` と書けば、最初から絶対名として引かれます。
</Callout>

Service には、ClusterIP を持たない **headless** という形もあります。この場合、DNS は ready な Pod の IP をそのまま全部返します。振り分けはクライアントに任せ、Pod を 1 つずつ区別したい場合（第 92 回）に使います。

## クラスタの外から入る

ClusterIP は、クラスタの中でしか意味を持ちません。外から入れるには、段階があります。

| 方法 | 仕組み |
| --- | --- |
| **NodePort** | すべてのノードの同じポート（既定の範囲は 30000〜32767）に来たパケットを、Service へ書き換える |
| **LoadBalancer** | NodePort に加えて、クラウドのロードバランサを作り、各ノードの NodePort へ振り分けさせる |
| **Gateway / Ingress** | HTTP を理解するプロキシを入口に置き、ホスト名やパスで Service を選ぶ |

NodePort は、**どのノードに来ても**受け付けます。そのノードに目的の Pod がいなければ、別のノードの Pod へ転送します。ここでもう一度アドレスの書き換えが起き、Pod から見た送信元がクライアントではなくノードになります。

HTTP の入口については、古くからの **Ingress** の API は凍結され、Kubernetes のプロジェクトは後継の **Gateway API** を勧めています（[Kubernetes Docs](https://kubernetes.io/docs/concepts/services-networking/ingress/)）。どちらも、Kubernetes 自身はプロキシを持たず、**「こういう振り分けをしてほしい」という宣言だけを受け付け**、実際のプロキシは別の実装が担う、という形は同じです。CNI と同じ分業です。

## まとめ

- Pod ごとにクラスタ全体で一意な IP を持ち、NAT なしで直接話せる、という約束を Kubernetes が決める
- 約束の実現は CNI プラグインが担う。名前空間ができたら起動され、JSON を標準入出力でやり取りする実行ファイル
- Service の ClusterIP は、どのインタフェースにも存在しない仮想 IP。各ノードのカーネルが宛先を書き換えて届ける
- kube-proxy は中継しない。EndpointSlice を watch して、iptables / nftables の規則を書き換えるだけ
- 振り分けは conntrack により接続の最初の 1 回だけ。長く生きる接続は、Pod を増やしても散らない
- 名前は `<Service>.<名前空間>.svc.cluster.local`。`ndots:5` は外部名の問い合わせを増やす
- 外からの入口は NodePort、LoadBalancer、Gateway の段階がある

次は、L4 の Service では届かない「リクエスト単位の制御」を、アプリの外側にまとめて引き受けるサービスメッシュを見ます。
