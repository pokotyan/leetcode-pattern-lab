## カーネルは名前を知らない

`ls -l` を実行すると、ファイルの持ち主が `alice` のように名前で表示されます。しかしカーネルの中に `alice` という文字列はありません。カーネルが知っているのは **uid**（ユーザ ID）と **gid**（グループ ID）という**番号だけ**です。

```bash
$ id
uid=1000(alice) gid=1000(alice) groups=1000(alice),27(sudo)
```

番号と名前の対応は、`/etc/passwd` と `/etc/group` という**ただのテキストファイル**に書かれています。`ls` や `id` は、カーネルから番号を受け取ったあと、このファイルを自分で読んで名前に直して表示しているだけです。

```
alice:x:1000:1000:Alice:/home/alice:/bin/bash
  │       │    │                        └ ログインシェル
  │       │    └ 主グループの gid
  │       └ uid
  └ 名前
```

<Callout type="warn" title="番号がずれると、別人の持ち物になる">
  カーネルは番号で判定するので、あるマシンで uid 1000 の alice が作ったファイルを、
  別のマシンに持っていくと、**そのマシンの uid 1000 の誰か**の持ち物になります。
  NFS でファイルを共有したとき、コンテナにホストのディレクトリを見せたとき（第 73 回）に
  権限で揉めるのは、名前ではなく番号が一致していないからです。
</Callout>

## プロセスは誰として動いているか

第 33 回で、プロセスには実行中のプログラムに付随する状態の集まりが付いてくると書きました。その 1 つが **資格情報**（credentials）です。

| 項目 | 意味 |
| --- | --- |
| **実 uid**（real） | 誰がこのプロセスを起動したか |
| **実効 uid**（effective） | 権限の判定に使う uid |
| **保存 uid**（saved） | 一時的に手放した権限を取り戻すための控え |
| gid とその 3 種類 | uid と同じ構造 |
| 補助グループ | 所属している他のグループの一覧 |

普段は 3 つの uid がすべて同じ値です。`/proc/self/status` で見られます。

```bash
$ grep ^Uid /proc/self/status
Uid:	1000	1000	1000	1000
#       実     実効   保存   ファイルシステム用
```

**権限の判定に使われるのは実効 uid** です。3 つが分かれている理由は、後で setuid を見るとわかります。

資格情報は `fork` で子にそのまま引き継がれ、`exec` をしても基本的には変わりません。ログインした時点のシェルの uid が、そこから起動したすべてのプロセスに受け継がれていきます。

## 9 ビットの読み方

ファイルの側には、**持ち主の uid**、**グループの gid**、そして **モード**（12 ビット）が inode に記録されています。モードのうち下位 9 ビットが、おなじみの `rwx` です。

```
-rw-r-----  1 alice staff  ...  report.txt
 └┬┘└┬┘└┬┘
  │  │  └ その他（other）   --- = 0
  │  └ グループ（group）     r-- = 4
  └ 持ち主（user）          rw- = 6     → 8 進数で 640
```

各桁は 3 ビットで、`r` = 4、`w` = 2、`x` = 1 です。`chmod 640` の数字は、この 3 ビットを 3 組並べたものを 8 進数で書いたものです。8 進数が使われるのは、**3 ビットがちょうど 8 進数 1 桁になる**からです。第 1 回で見た「4 ビットが 16 進数 1 桁」と同じ理屈です。

カーネルの判定手順は次のとおりです。

1. 実効 uid が 0（root）なら、ほぼすべて許可する
2. 実効 uid がファイルの持ち主と一致すれば、**持ち主の 3 ビットだけ**を見る
3. そうでなく、ファイルのグループが自分のグループのどれかと一致すれば、**グループの 3 ビットだけ**を見る
4. どれでもなければ、**その他の 3 ビット**を見る

**最初に当てはまった区分だけを見て、そこで判定が終わる**点が重要です。

```bash
$ ls -l g
----r--rwx 1 alice root 3 ... g
$ cat g            # alice として実行
cat: g: Permission denied
```

「その他」には `rwx` がすべて付いていますが、alice は持ち主なので持ち主の `---` だけが見られ、拒否されます。**権限は足し算ではありません**。

## ディレクトリの r、w、x

ディレクトリにも同じ 9 ビットがありますが、意味が変わります。第 49 回で詳しく見ますが、ディレクトリの中身は **名前と inode 番号の対応表**です。3 つのビットは、この表に対する操作を表します。

| ビット | ディレクトリでの意味 |
| --- | --- |
| `r` | 表を読む（中の名前の一覧を取る） |
| `w` | 表を書き換える（名前を追加・削除・変更する） |
| `x` | 表を**通り抜ける**（名前から inode を引き、その先に進む） |

ここから、直感に反する挙動がいくつも出てきます。

```bash
$ ls -ld /srv/x
drwx--x--x 2 root root ... /srv/x     # 711: 他人は x だけ
$ ls /srv/x                           # alice として
ls: cannot open directory '/srv/x': Permission denied
$ cat /srv/x/f                        # 名前を知っていれば読める
hi
```

**一覧は取れないのに、名前を知っていれば中のファイルを開けます**。`x` だけがあると、表は読めないが引くことはできるからです。ホームディレクトリを 711 にして、公開したいファイルだけ名前を教える、という使い方はこの性質を利用しています。

もう 1 つ重要なのが、**ファイルの削除はディレクトリへの書き込み**だということです。削除とは、ディレクトリの表から名前を消す操作だからです。

- 読み取り専用のファイルでも、ディレクトリに `w` があれば削除できる
- 自分が書き込めるファイルでも、ディレクトリに `w` がなければ削除できない

パスの途中のディレクトリすべてに `x` が必要な点も見落とされがちです。`/home/alice/public/index.html` を開くには、`/`、`/home`、`/home/alice`、`/home/alice/public` のすべてに `x` が要ります。Web サーバが「ファイルのパーミッションは正しいのに 403 になる」原因の多くはこれです。

## 判定は open のときだけ

権限の判定は、**`open` の時点で 1 回だけ**行われます。一度 fd を取得すれば、あとからファイルのパーミッションが変わっても、その fd では読み書きを続けられます。

```bash
$ exec 3<secret         # fd 3 で開いておく
$ chmod 000 secret
$ cat secret
cat: secret: Permission denied
$ cat <&3               # 開いてある fd からは読める
top-secret
```

第 42 回で見たとおり、fd は「開いたファイルの記述」への添字です。権限の確認は、その記述を作るときに済んでいます。`read` や `write` のたびにパーミッションを調べ直したりはしません。

これは、権限を持つプロセスが開いた fd を、権限のないプロセスに渡すという設計を可能にします。特権の必要なポートを root で開いてから、一般ユーザに切り替えて待ち受けるサーバが、その例です。

## umask: 作るときの既定値

新しいファイルを作るとき、プログラムは `open` にモードを渡します。多くのプログラムはファイルに 666、ディレクトリに 777 を指定します。それでも実際にできるファイルが 644 になるのは、**umask** が引かれるからです。

```
  要求されたモード     666   rw-rw-rw-
  umask               022   ----w--w-
  ─────────────────────────────────
  実際のモード         644   rw-r--r--      （666 AND NOT 022）
```

umask はプロセスの属性で、`fork` で子に引き継がれます。シェルで `umask 077` を実行すると、そのシェルから起動したプログラムが作るファイルはすべて持ち主以外に見えなくなります。

## setuid: 他人として実行する

一般ユーザは自分のパスワードを変えられます。しかしパスワードのハッシュが入った `/etc/shadow` は、root しか書き込めません。

```bash
$ ls -l /etc/shadow /usr/bin/passwd
-rw-r-----  1 root shadow  ... /etc/shadow
-rwsr-xr-x  1 root root    ... /usr/bin/passwd
```

`passwd` の持ち主の `x` の位置に `s` があります。これが **setuid ビット**で、モードの上位 3 ビットの 1 つです。

setuid ビットの付いたファイルを `exec` すると、カーネルは**実効 uid をファイルの持ち主の uid に変えます**。実 uid は元のままです。

```bash
$ id
uid=1000(alice) gid=1000(alice) groups=1000(alice)
$ ./sid            # id をコピーして root の持ち物にし、setuid を付けたもの
uid=1000(alice) gid=1000(alice) euid=0(root) groups=1000(alice)
```

`passwd` は実効 uid が root なので `/etc/shadow` を書き換えられます。同時に、実 uid を見れば「起動したのは alice だ」とわかるので、**alice のパスワードだけ**を変えるように自分で制限しています。

ここで 3 つの uid が分かれている理由がわかります。

- **実 uid** は「本当は誰なのか」を覚えておくため
- **実効 uid** は、いま権限の判定に使う値
- **保存 uid** は、実効 uid を一時的に一般ユーザに戻したあと、また root に戻れるようにするための控え

特権が必要な処理の間だけ実効 uid を root にし、それ以外は手放しておく。この切り替えのために 3 つが必要です。

<Callout type="warn" title="setuid のプログラムは、攻撃者の入力で動く">
  setuid root のプログラムは、**一般ユーザが用意した環境で root として動きます**。
  環境変数、引数、カレントディレクトリ、開いたままの fd、シグナル。すべて攻撃者が選べます。

  そのため、カーネルやライブラリは setuid のプログラムを特別扱いします。
  第 29 回で見た `LD_PRELOAD` は、setuid のプログラムでは無効になります。
  bash は、実 uid と実効 uid が違うことに気づくと、自分から権限を捨てます（`-p` を付けたときだけ保持する）。
  それでも、setuid のプログラムの脆弱性は、長く権限昇格の定番であり続けました。
</Callout>

ほかの上位ビットも見ておきます。

| ビット | ファイルに付けたとき | ディレクトリに付けたとき |
| --- | --- | --- |
| **setuid**（4000） | 実効 uid を持ち主にして実行 | （Linux では無視） |
| **setgid**（2000） | 実効 gid をグループにして実行 | 中に作ったファイルが、ディレクトリのグループを継ぐ |
| **sticky**（1000） | （現在は無視） | 中のファイルは、**持ち主しか削除・改名できない** |

sticky bit は `/tmp` に付いています。

```bash
$ ls -ld /tmp
drwxrwxrwt  ... /tmp          # 最後の t が sticky
```

`/tmp` は誰でも書き込めるディレクトリです。前に見たとおり、ディレクトリに `w` があればその中の名前を消せるので、そのままでは**他人のファイルも削除できてしまいます**。sticky bit はこの規則に「ただし持ち主だけ」という条件を足すものです。

```bash
# alice が作り、誰でも書ける 666 にしたファイルを、bob が操作する
$ echo b >> /tmp/a          # 書き込みはできる
$ rm /tmp/a
rm: cannot remove '/tmp/a': Operation not permitted
```

## root という例外を分割する

ここまでの仕組みは、「実効 uid が 0 なら、ほぼすべて許可」という例外を抱えています。ファイルを読むためだけに root が必要なプログラムも、ポート 80 で待ち受けたいだけのプログラムも、**root になった瞬間にすべての権限を持ちます**。

Linux は 2.2 から、この root の権限を **capabilities** という単位に分割しました（[capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html)）。

| capability | 例外として許すこと |
| --- | --- |
| `CAP_DAC_OVERRIDE` | ファイルのパーミッションを無視する |
| `CAP_CHOWN` | 所有者を変える |
| `CAP_SETUID` | uid を自由に変える |
| `CAP_NET_BIND_SERVICE` | 1024 未満のポートで待ち受ける |
| `CAP_KILL` | 他のユーザのプロセスにシグナルを送る |

上の手順の「root ならほぼすべて許可」は、正確には「**`CAP_DAC_OVERRIDE` を持っていれば、パーミッションの判定を飛ばす**」です。root がパーミッション 000 のファイルを読めるのは、root が偉いからではなく、このビットが立っているからです。

capabilities はプロセスだけでなく、**実行ファイルにも付けられます**。setuid root の代わりに、必要な capability だけをファイルに付けておけば、`exec` したときにその権限だけを持って動きます。

```bash
setcap cap_net_bind_service=+ep ./server    # root にせず、ポート 80 だけ許す
getcap ./server
```

コンテナが root で動いていても「本物の root」ではない理由の 1 つは、Docker がこの capabilities を 14 個だけ残して配っていることでした（第 77 回）。

<Callout type="note" title="9 ビットで足りないとき: ACL">
  9 ビットで表せるのは「持ち主、1 つのグループ、その他」の 3 区分だけです。
  「alice と bob には読ませたいが、同じグループの carol には見せたくない」は表現できません。
  そのために **ACL**（アクセス制御リスト）があり、ユーザやグループごとに権限を足せます。

```bash
setfacl -m u:bob:r report.txt
getfacl report.txt
```

  ACL が付いたファイルは、`ls -l` のモードの末尾に `+` が付きます。
</Callout>

## まとめ

- カーネルは uid と gid という番号だけを扱う。名前との対応は `/etc/passwd` にあるただのテキスト
- プロセスは実・実効・保存の 3 つの uid を持ち、判定には実効 uid を使う
- 判定は持ち主 → グループ → その他の順で、**最初に当てはまった 3 ビットだけ**を見る
- ディレクトリの `r` は一覧、`w` は名前の追加と削除、`x` は通り抜け。削除はディレクトリへの書き込み
- 権限の判定は `open` のときだけ。fd を持っていれば、あとからの `chmod` の影響を受けない
- setuid は実効 uid をファイルの持ち主に変える。攻撃者の用意した環境で動くので特別扱いされる
- sticky bit は、誰でも書けるディレクトリで他人のファイルを消せないようにする
- root の特権は capabilities に分割されている。root がパーミッションを無視できるのも capability のおかげ

次は、その fd を「待つ」ときの言葉を整理します。ブロッキング、ノンブロッキング、同期、非同期。4 つの言葉が混乱する理由から入ります。
