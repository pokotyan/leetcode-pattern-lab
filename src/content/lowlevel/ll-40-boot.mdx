## 最初の 1 命令

電源が入った瞬間、メモリ（DRAM）は空です。初期化すらされていません。では CPU は何を実行するのか。

答えは、**CPU がリセット時に読みに行くアドレスが、ハードウェアとして決まっている**ことです。

- x86 では `0xFFFFFFF0`
- ARM では実装依存（多くは 0 番地、またはブート ROM）
- 6502 では `$FFFC` に書かれたアドレス（第 13 回で見たリセットベクタ）

このアドレスには、マザーボード上の **フラッシュ ROM**（不揮発性メモリ）がマップされています。そこに入っているのが **ファームウェア** です。

**第 13 回で見た割り込みベクタの仕組みが、ここでも使われています。** 「電源投入」も一種のリセット割り込みとして扱われます。

## ファームウェア

### BIOS（旧方式）

1981 年の IBM PC から続く方式です。

1. **POST**（Power-On Self Test）：CPU、メモリ、周辺機器を検査する
2. 起動デバイスを順に調べる
3. ディスクの**先頭 512 バイト**（MBR）を読み、メモリの `0x7C00` に置く
4. そこにジャンプする

**512 バイト**しかありません。しかも末尾 2 バイトは識別用の印（`0x55AA`）、64 バイトはパーティション表です。ブートローダが使えるのは 446 バイト。

この中に OS を読み込む処理を全部書くのは不可能なので、**もっと大きな第 2 段階を読み込むだけ**のコードが入っています。多段階になっているのはこの制約によります。

<Callout type="note" title="16 ビットのまま起動する">
  BIOS は互換性のため、CPU を **リアルモード**（16 ビット、1MB までしかアクセスできない）で起動します。
  2003 年の 64 ビット CPU でも、電源投入直後は 1978 年の 8086 と同じ状態です。
  ブートローダが、16 ビット → 32 ビット（プロテクトモード）→ 64 ビット（ロングモード）と
  段階的に切り替えていきます。
</Callout>

### UEFI（現行方式）

BIOS の制約を解消した仕様です。

| | BIOS | UEFI |
| --- | --- | --- |
| 起動時のモード | 16 ビット | 32 / 64 ビット |
| ブートローダの置き場所 | MBR の 446 バイト | **ファイルシステム上の実行可能ファイル** |
| ディスクの上限 | 2TB（MBR の制約） | GPT により実質無制限 |
| 起動の指定 | デバイス単位 | NVRAM の変数で管理 |
| セキュアブート | なし | 署名検証ができる |

UEFI では、**FAT でフォーマットされた ESP**（EFI System Partition）に、`.efi` という実行可能ファイルを置きます。ファームウェアがファイルシステムを読めるので、512 バイト制限がありません。

```bash
efibootmgr -v          # 起動エントリの一覧
ls /boot/efi/EFI/      # ESP の中身
```

**セキュアブート**は、署名されたブートローダしか実行しない仕組みです。ブートキット（OS より先に動くマルウェア）を防ぎます。一方、署名されていない独自 OS の起動を妨げるため、無効化が必要になることもあります。

## ブートローダ

代表的なものが **GRUB** です。仕事は、

1. 設定ファイルを読み、起動メニューを表示する
2. **カーネルのイメージ**をメモリに読み込む
3. **initramfs** を読み込む
4. カーネルにパラメータを渡し、制御を移す

```bash
cat /proc/cmdline      # カーネルに渡されたパラメータ
# BOOT_IMAGE=/vmlinuz-6.5.0 root=/dev/sda2 ro quiet splash
```

`root=` でルートファイルシステムの場所を指定しています。

## initramfs

ここに循環があります。

> **ルートファイルシステムをマウントするには、そのディスクのドライバが必要。**
> **ドライバはルートファイルシステムの中にある。**

解決策が **initramfs**（初期 RAM ファイルシステム）です。

必要最小限のドライバとツールを詰めた小さなファイルシステムを、ブートローダがメモリ上に展開します。カーネルはまずこれをルートとして起動し、必要なドライバを読み込んで本物のルートをマウントし、そちらに切り替えます（`pivot_root`）。

```bash
lsinitramfs /boot/initrd.img-$(uname -r) | head
```

暗号化されたディスク、RAID、LVM、ネットワーク越しのルートなど、複雑な構成に対応するために不可欠な仕組みです。

## カーネルの起動

カーネルが制御を受け取ってからの流れです。

1. CPU を適切なモードに切り替え、ページングを有効にする
2. メモリマップを取得し、物理メモリの管理を初期化する
3. 割り込みベクタテーブルを設定する
4. スケジューラ、メモリ管理、ファイルシステムなどのサブシステムを初期化する
5. デバイスを検出し、ドライバを初期化する
6. ルートファイルシステムをマウントする
7. **最初のユーザプロセス（PID 1）を起動する**

```bash
dmesg | head -50       # 起動時のカーネルメッセージ
```

7 の時点で、初めてユーザ空間のコードが動き始めます。

## PID 1

最初のユーザプロセスには、2 つの特別な役割があります。

- **孤児プロセスの引き取り先**：親が死んだプロセスの新しい親になり、ゾンビを回収する
- **他のすべてのプロセスの祖先**：システムのサービスを起動する

現代の Linux では **systemd** が使われます。

従来の SysV init は、シェルスクリプトを番号順に逐次実行していました。systemd は、

- サービス間の依存関係を宣言し、**並列に起動する**
- ソケットを先に作っておき、必要になったときにサービスを起動する（socket activation）
- cgroup でサービスごとのリソースを管理する
- ログを一元管理する（journald）

```bash
systemd-analyze                  # 起動時間の内訳
systemd-analyze blame            # 時間がかかったサービスの一覧
systemd-analyze critical-chain   # 依存関係の連鎖
systemctl status
```

<Callout type="tip" title="起動が遅いときの調べ方">
  `systemd-analyze blame` で時間のかかっているサービスが分かります。
  ただし、並列に起動しているので、**単に時間がかかっているだけのサービスは全体に影響しません**。
  実際のボトルネックは `critical-chain` で、依存の連鎖として見る必要があります。
</Callout>

## 全体の流れ

```
電源投入
  → CPU がリセットベクタから実行を開始
  → ファームウェア（BIOS / UEFI）が POST とデバイス初期化
  → ブートローダ（GRUB）がカーネルと initramfs を読み込む
  → カーネルが自身を初期化し、ドライバを読み込む
  → ルートファイルシステムをマウント
  → PID 1（systemd）を起動
  → サービスが並列に起動
  → ログイン画面
```

各段階が、次の段階を読み込んで制御を渡す、という連鎖です。段階ごとに「使えるものが増えていく」構造になっています。

## 組み込みとファミコンの場合

小さなシステムでは、この階層が大幅に簡略化されます。

ファミコンの場合、

1. 電源投入
2. 6502 が `$FFFC`（リセットベクタ）から 2 バイト読む
3. そのアドレスへジャンプする
4. **そこがゲームのプログラムの先頭**

OS もブートローダもありません。カートリッジの ROM が、そのままアドレス空間にマップされています。

Track 3 の NES エミュレータでは、この 4 手をそのまま実装することになります。「起動」が具体的に何を指すのかが、最も単純な形で見えます。

## まとめ

- CPU はリセット時に読むアドレスがハードウェアで決まっている
- BIOS は 512 バイトの MBR から起動し、16 ビットモードで始まる
- UEFI はファイルシステム上の実行可能ファイルを起動する。GPT とセキュアブートを含む
- ブートローダがカーネルと initramfs を読み込む
- initramfs は「ドライバを読むためのドライバ」という循環を解く
- PID 1 は孤児の引き取り先であり、すべてのプロセスの祖先
- systemd は依存関係に基づいて並列起動する
