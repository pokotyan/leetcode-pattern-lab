## 発行する側に回る

第 183 回から第 186 回までは、ブラウザの前に座った人が IdP でログインする話でした。けれども、自分のサービスに API を付けると、すぐに別の依頼が来ます。「夜間のバッチから注文の一覧を取りたいので、**API キーを発行してほしい**」。相手はブラウザもリダイレクトも持たないプログラムで、毎回の要求に何かの文字列を付けて送ってきます。

API キーは古くからある、いちばん単純な仕組みです。それでも、発行する側に回ると決めることは意外に多くあります。

- どんな文字列にするのか。長さは、文字の種類は、見分ける目印は
- データベースに何を保存するのか。パスワードと同じように bcrypt を通すべきか
- 届いたキーをどう照合するのか。比べ方で情報が漏れないか
- 1 本のキーに何を許すのか。いつまで有効にするのか
- 入れ替えるとき、漏れたときにどうするのか

この回は、これらを一般的な設計と実在のサービスの文書で確かめ、手元で 1 つずつ動かします。最後に、キーそのものを毎回送る方式の限界と、キーで要求に**署名する**方式（AWS Signature Version 4、RFC 9421）を見ます。

## API キーは何を表しているのか

先に、API キーが何の証拠なのかを確かめておきます。第 173 回で、API キーは多くの場合「どの契約やプロジェクトに結びつけるか」を決める値で、誰が使っているかを示さないと見ました。OWASP の API Security Top 10 も「API keys should not be used for user authentication. They should only be used for API clients authentication.」と書いています（[OWASP API2:2023](https://api-security.owasp.org/editions/2023/en/0xa2-broken-authentication)）。API キーが示すのは、**このキーを発行された利用者（クライアント）からの要求である**ことまでです。

そして第 181 回で見たベアラトークンと同じく、**持っている者が使える**値です。違いは寿命です。OAuth のアクセストークンは数分から 1 時間で切れますが、API キーは発行者が期限を付けない限り、何年でも生きます。この回の設計は、ほとんどがこの 2 つの性質（ベアラ型で、長く生きる）から来ています。

## どんな文字列を作るか

### でたらめさは CSPRNG から

キーの強さは、攻撃者が当てずっぽうで当てられないことだけで決まります。人が覚える必要はないので、パスワードと違って**長く、完全にでたらめ**にできます。

でたらめさは、暗号論的に安全な乱数生成器（CSPRNG）から取ります。Python なら `random` ではなく `secrets` を使います。`secrets` の文書は、総当たりに耐えるには十分なでたらめさが必要で、2015 年の時点では 32 バイト（256 ビット）あれば典型的な用途には十分と考えられている、と書いています（[Python secrets](https://docs.python.org/3/library/secrets.html)）。NIST SP 800-63B-4 も、認証に使う乱数は承認された乱数生成器で、少なくとも 112 ビットの強さを持つものから作るよう求めています（[SP 800-63B-4 3.2.12](https://pages.nist.gov/800-63-4/sp800-63b.html)）。目安としては **128〜256 ビット**です。

### 文字にする: base62 と base32

乱数のバイト列は、そのままでは HTTP のヘッダや設定ファイルに書けないので、文字に直します。

| 符号化 | 使う文字 | 1 文字あたり | 向いている場面 |
| --- | --- | --- | --- |
| 16 進 | `0-9a-f` | 4 ビット | 長くなる。ハッシュ値と見分けがつかない |
| base32 | 英大文字と数字 2〜7 | 5 ビット | 大文字小文字を区別しない場所、読み上げ |
| base62 | 英大小文字と数字 | 約 5.95 ビット | ダブルクリックで全体を選べる。URL でも安全 |
| base64 | 上に `+` `/`（または `-` `_`）と `=` | 6 ビット | 記号が区切り文字とぶつかりやすい |

GitHub と Stripe はどちらも英数字の並びを使っています。base62 の 32 文字なら、32 × log2(62) ≈ **190 ビット**になります。

### 接頭辞: 種類と環境を名札にする

GitHub は 2021 年にトークンの形式を `ghp_` のような接頭辞付きに変え、secret scanning の誤検知が大きく減る見込みだと述べています（[GitHub Blog](https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/)）。検出する側から見た話は第 244 回で扱います。発行する側から見ると、接頭辞の役目は検知だけではありません。

Stripe のキーは、接頭辞で種類と環境が分かります（[Stripe: API keys](https://docs.stripe.com/keys)）。

| 接頭辞 | 種類 | 公開してよいか |
| --- | --- | --- |
| `pk_test_` / `pk_live_` | 公開可能キー。ブラウザやアプリに埋め込む | はい |
| `rk_test_` / `rk_live_` | 制限付きキー。権限を絞れる | いいえ |
| `sk_test_` / `sk_live_` | シークレットキー。全 API に無制限 | いいえ |

接頭辞があると、次のことが文字列を見ただけで分かります。

- **どの環境のキーか**: `sk_test_` を本番の設定に入れた、`sk_live_` を開発者の手元に置いた、という取り違えに、人もレビューのツールも気づける
- **公開してよい種類か**: `pk_` がフロントエンドにあるのは正常で、`sk_` があれば事故
- **漏れたときに、どこへ届ければよいか**: GitHub の secret scanning のパートナープログラム（第 244 回）は、この形を正規表現で登録して成り立っている

### チェックサム: 問い合わせる前に弾く

GitHub の新しい形式は、末尾 6 文字に 32 ビットのチェックサム（CRC32 を base62 にしたもの）を持ちます（[GitHub Blog](https://github.blog/engineering/platform-security/behind-githubs-new-authentication-token-formats/)）。検出する側がこれを使って誤検知を減らす様子は、第 244 回で見ます。

発行する側にとっての利点は、**データベースに問い合わせる前に、打ち間違いやコピーの欠けを弾ける**ことです。でたらめな文字列を大量に送りつけられても、チェックサムが合わないものは DB に届きません。CRC32 は鍵を持たない誤り検出の符号で、**改ざんや偽造を防ぐものではない**点には注意が要ります。チェックサムを正しく計算した偽のキーは誰でも作れます。防ぐのは、あくまで次に見る秘密の部分の照合です。

### ID と秘密を分ける

もう 1 つ決めておくのが、キーを **ID の部分と秘密の部分**に分けるかどうかです。

```
lab_live_9f9wsr1hPbC6_SQRM92DHV4Dk2PGXw76PDY7ekcELobLq3xo4lM
└──┬───┘ └────┬─────┘ └──────────────┬───────────────┘└─┬──┘
   │          │                      │                  └ チェックサム 6 文字（CRC32 を base62 で）
   │          │                      └ 秘密 32 文字（base62、約 190 ビット）
   │          └ キー ID 12 文字（秘密ではない。DB を引く鍵）
   └ 接頭辞（サービス名 + 環境）
```

ID があると、DB を主キーで引いてから、その行のハッシュと比べられます。ログや管理画面には ID だけを出せば、どのキーが使われたかを秘密を見せずに示せます。後で見るとおり、パスワード向けの遅いハッシュを使う場合は、ID が無いと照合そのものが成り立ちません。

### 手元で確かめる: 形式を決め、1 文字の誤りを弾く

上の形式で発行し、照合の前にチェックサムで弾く関数を Python 3.14 で書きました。チェックサムは GitHub の形にならい、CRC32 を base62 の 6 文字にしています。

```python
def issue(env="live"):
    key_id = rand62(12)                      # secrets.choice で 1 文字ずつ選ぶ
    secret = rand62(32)
    body = f"lab_{env}_{key_id}_{secret}"
    return body + b62(zlib.crc32(body.encode()), 6)

def parse(key):
    if not key.startswith(("lab_live_", "lab_test_")) or len(key) != 60:
        return None, "形が違う"
    body, cs = key[:-6], key[-6:]
    if b62(zlib.crc32(body.encode()), 6) != cs:
        return None, "チェックサムが合わない"
    env, key_id, secret = body.split("_")[1:]
    return (env, key_id, secret), "OK"
```

```
発行: lab_live_9f9wsr1hPbC6_SQRM92DHV4Dk2PGXw76PDY7ekcELobLq3xo4lM 60 文字
秘密部分のエントロピー: 32 × log2(62) = 190.5 ビット
1 文字変更: lab_live_9f9wsr1hPbC6_SQRM92DHa4Dk2PGXw76PDY7ekcELobLq3xo4lM チェックサムが合わない
隣を入れ替え: チェックサムが合わない
1 文字の置き換え 3111 通りのうち、チェックサムを通ったもの: 0
でたらめな 1,000,000 本のうち、チェックサムを通ったもの: 0
```

チェックサムより前の各位置（区切りの `_` を除く 51 か所）を、ほかの 61 文字に置き換えた 3,111 通りは、すべて形かチェックサムで落ちました。CRC32 は 32 ビット以内に収まる連続した誤りを必ず見つけるので、1 文字の置き換えや隣どうしの入れ替えは原理的に通りません。でたらめな 100 万本も 0 本でした。偶然に通る確率は約 2^32 分の 1（約 43 億分の 1）です。

<Callout type="warn" title="チェックサムの付いた本物そっくりの値を、テストやドキュメントに置かない">
  チェックサムまで正しい値は、検出の仕組みから見れば本物と区別がつきません（第 244 回で扱います）。
  ドキュメントの例やテストのデータには、チェックサムをわざと外した値を使うと、誤報を作らずに済みます。
  この回の `lab_live_` は架空の接頭辞なので、どのスキャナにも登録されていません。
</Callout>

## 何を保存するか

### 平文では持たない

発行したキーを、そのままデータベースに入れてはいけません。DB のバックアップ、レプリカ、ログ、管理者の画面、どこか 1 か所から漏れれば、全利用者のキーがそのまま使えてしまいます。第 174 回のパスワードと同じく、**一方向の関数を通した値だけを持ち**、届いたキーに同じ関数を通して比べます。

そのため、キーの全体を利用者に見せられるのは**作った直後の 1 回だけ**になります。Stripe も、本番のシークレットキーは作成時に 1 回だけ表示し、後から再表示はできず、失くしたらローテーションか削除をして作り直すよう案内しています（[Stripe: API keys](https://docs.stripe.com/keys)）。管理画面でどのキーかを見分けるには、作成時に**末尾の数文字**（ここでは 4 文字）を別に保存しておき、`…3xo4lM` のように見せます。末尾 4 文字が漏れても、残りの約 180 ビットは変わらず当てられません。

### 遅いハッシュは要らない

ここで第 174 回を思い出すと、bcrypt や Argon2id のようなパスワード用の遅い関数を使うべきに見えます。結論から言うと、**十分に長くでたらめな API キーには要りません**。SHA-256 で足ります。

第 174 回で遅い関数が必要だったのは、パスワードの**候補が少ない**からでした。人が覚えられる長さの文字列は、総当たりで手が届く数しかありません。そこで 1 回の計算を 10 万倍遅くして、届かない数に押し戻していました。API キーは最初から 2^190 通りあり、押し戻す必要がそもそもありません。

NIST SP 800-63B-4 にも、似た性質の秘密について同じ区別があります。印刷して配る回復用コードのような「look-up secret」は、すべて承認されたハッシュ関数で保存しなければならず、**112 ビットに満たないものに限って**、ソルト付きのパスワードハッシュで保存しなければならない、としています（[SP 800-63B-4 3.1.2.2](https://pages.nist.gov/800-63-4/sp800-63b.html)）。NIST の分類に API キーという項目はありませんが、「CSPRNG で作った十分に長い秘密は、速いハッシュで保存してよい」という考え方は、この規定と同じです。

**サーバの秘密で HMAC を取る**形もあります。保存するのは `HMAC-SHA256(サーバの秘密, キーの秘密部分)` で、サーバの秘密は DB とは別の場所（第 151 回の秘密情報の管理サービスなど）に置きます。DB だけが漏れた場合、攻撃者は手元にあるキーの候補がどの行に当たるかを確かめることすらできません。第 174 回のペッパーと同じ考え方で、追加の層です。その代わり、サーバの秘密を失うと全キーが照合できなくなるので、その秘密の保管と入れ替えの手順が別に要ります。

### 手元で確かめる: 照合 1 回の値段

照合 1 回にかかる時間を、手元の Mac（Apple M1 Pro、Python 3.14.0、bcrypt 5.0.0、argon2-cffi 25.1.0）で測りました。Argon2id は第 174 回と同じ OWASP の最低限の設定（m=19 MiB、t=2、p=1）です。

```
SHA-256                                  0.0004 ms/回      2,281,706 回/秒
HMAC-SHA256(サーバの秘密)                 0.0014 ms/回        712,960 回/秒
bcrypt cost=12                         250.4233 ms/回              4 回/秒
Argon2id m=19MiB t=2 p=1                23.7823 ms/回             42 回/秒

bcrypt は SHA-256 の 571,392 倍遅い = 約 19.1 ビット分
argon は SHA-256 の 54,264 倍遅い = 約 15.7 ビット分
```

Argon2id の値は第 174 回の測定（127 ms）と違いますが、あちらは別のライブラリでの測定です。どちらにしても桁は同じです。

遅い関数が稼ぐのは、bcrypt の cost 12 で**約 19 ビット**です。これを、総当たりに要る手間と並べます。攻撃者は SHA-256 を 1 秒に 1 兆回（10^12 回）試せる、と相手に有利に置き、bcrypt はそこから上の実測の倍率（57 万倍）だけ遅くなるとしました。候補の半分を試すまでの時間です。

```
API キー 32 文字 base62: 190.5 ビット  SHA-256 1.14e+45 秒 = 3.60e+37 年  bcrypt 6.49e+50 秒 = 7.51e+45 日
パスワード 英小文字+数字 8 文字: 41.4 ビット  SHA-256 1.41e+00 秒 = 4.47e-08 年  bcrypt 8.06e+05 秒 = 9.33e+00 日
```

8 文字のパスワードは、SHA-256 なら 1.4 秒で半分を試せます。bcrypt にすると約 9 日になり、遅い関数が意味を持ちます。API キーは、SHA-256 のままでも 10^37 年の桁です。ここに 19 ビットを足しても、0 が 6 つ増えるだけで、何も変わりません。

逆に、遅い関数の値段は**正しい利用者が毎回払います**。パスワードの照合はログインの 1 回だけですが、API キーは**すべての要求で**照合します。bcrypt の cost 12 なら、CPU の 1 コアが 1 秒に処理できる要求は 4 件です。でたらめなキーを送りつけるだけで、サーバの CPU を使い切らせることもできます。

## どう照合するか

### ID で引いて、ハッシュを比べる

照合の手順は次のとおりです。

```
届いたキー
  │ ① 接頭辞と長さ        → 違えば 401（DB に触れない）
  │ ② チェックサム        → 違えば 401（DB に触れない）
  │ ③ キー ID で 1 行を引く（主キーの索引）
  │ ④ SHA-256(秘密部分) と保存したハッシュを定数時間で比べる
  │ ⑤ 失効していないか、期限内か
  │ ⑥ 要求の操作がスコープに入っているか → 入っていなければ 403
  ▼
 通す（最終使用日時を記録）
```

ID を持たない形式でも、ハッシュ値そのものに索引を張れば 1 行を引けます。SHA-256 は同じ入力に同じ値を返すからです。これは**ソルトを付けない速いハッシュだからできる**ことで、bcrypt や Argon2id は行ごとに別のソルトを使うため、ハッシュで引けません。ID なしで bcrypt を使うと、届いたキーを全行のハッシュと 1 つずつ比べることになります。下の実験の 100 万行なら、250 ms × 100 万 ≈ 69 時間です。

### 手元で確かめる: PostgreSQL で照合する

`postgres:17`（17.11）に表を作り、100 万行のダミーのキーを入れました。

```sql
CREATE TABLE api_keys (
  key_id       text PRIMARY KEY,      -- キー ID（秘密ではない）
  prefix       text NOT NULL,         -- lab_live_ / lab_test_
  secret_hash  bytea NOT NULL,        -- SHA-256(秘密部分)
  last4        text NOT NULL,         -- 画面に出す末尾 4 文字
  owner_id     bigint NOT NULL,
  scopes       text[] NOT NULL,
  expires_at   timestamptz,
  revoked_at   timestamptz,
  last_used_at timestamptz,
  created_at   timestamptz NOT NULL DEFAULT now()
);
```

照合する API は、同じ Docker ネットワークに置いた Python のコンテナ（Python 3.13、psycopg 3.3.6）から呼びます。上の手順をそのまま書いたものです。

```python
def verify(key, need_scope):
    ...                                   # ① ② 形とチェックサム（上の parse と同じ）
    _, env, key_id, secret = body.split("_")
    row = conn.execute(
        "SELECT secret_hash, scopes, expires_at < now(), revoked_at IS NOT NULL,"
        "       last_used_at IS NULL OR last_used_at < now() - interval '1 minute'"
        "  FROM api_keys WHERE key_id = %s", (key_id,)).fetchone()
    given = hashlib.sha256(secret.encode()).digest()
    if row is None:
        hmac.compare_digest(given, given)  # 無い場合もおおむね同じ手間をかける
        return "401 不明なキー"
    stored, scopes, expired, revoked, stale = row
    if not hmac.compare_digest(given, stored):
        return "401 秘密が違う"
    if revoked:  return "401 失効済み"
    if expired:  return "401 期限切れ"
    if need_scope not in scopes:
        return "403 スコープ不足"
    if stale:    # 最終使用日時の書き込みは 1 分に 1 回まで
        conn.execute("UPDATE api_keys SET last_used_at = now() WHERE key_id = %s", (key_id,))
    return "200 OK"
```

```
正しいキー             200 OK
スコープ外             403 スコープ不足
1 文字違い             401 チェックサム
ID は本物、秘密は偽物   401 秘密が違う
期限切れ               401 期限切れ
失効済み               401 失効済み
('6dSjAYrJ50mA', 'lab_live_', '08ccd259…5b7f2b',  # ハッシュは途中を省略
  'FVS6', ['orders:read'], datetime.date(2027, 1, 22), True)
verify 5000 回: 中央値 0.036 ms, p99 0.285 ms
うち SHA-256 1 回: 0.40 µs
```

「ID は本物、秘密は偽物」は、キー ID を知った誰かがチェックサムを正しく計算し直して作った偽のキーです。形とチェックサムは通り、秘密の照合で落ちます。チェックサムが守りではないことの確認です。最後の行が DB に残る中身で、秘密そのものはどこにもありません。

`last_used_at` の更新を 1 分に 1 回に絞っているのは、すべての要求で UPDATE を発行すると、読むだけの API が書き込みの負荷と WAL を生むからです。最終使用日時は分単位で分かれば足ります。

照合 1 回は中央値 0.036 ms で、そのほとんどが DB との往復です。SHA-256 の計算（0.4 µs）は誤差の範囲です。索引の効き方を `EXPLAIN (ANALYZE, BUFFERS)` で比べました（出力は抜粋）。

```
-- キー ID で引く（主キーの索引）
Index Scan using api_keys_pkey on api_keys (actual time=0.050..0.050 rows=1 loops=1)
  Buffers: shared hit=4
Execution Time: 0.090 ms

-- ハッシュで引く（索引なし）
Parallel Seq Scan on api_keys (actual time=31.232..31.233 rows=0 loops=3)
  Rows Removed by Filter: 333334
Execution Time: 41.337 ms

-- ハッシュに UNIQUE 索引を張った後
Index Scan using api_keys_secret_hash on api_keys (actual time=0.034..0.034 rows=1 loops=1)
Execution Time: 0.053 ms
```

主キーで引けば 4 ページを読むだけで、0.09 ms です。ハッシュで引く形でも、索引を張れば同じ速さになります（索引の大きさは 100 万行で 56 MB）。索引が無いと 100 万行を全部なめて 41 ms かかります。キーの照合は**すべての要求の手前**に入るので、ここの 41 ms はそのまま API 全体の遅さになります。

### 手元で確かめる: `==` と `compare_digest`

④ で `==` を使わないのは、第 146 回のタイミング攻撃のためです。`==` は違うバイトを見つけた時点で止まるので、先頭が合っているほど少し遅くなります。どれくらいの差なのかを、手元で測りました（Python 3.14.0、各 20 万回の平均を 31 回測った中央値）。

```
--- 32 バイト（ns/回）
==              先頭で違う    43.8   末尾で違う    48.9   一致    44.4
compare_digest  先頭で違う    47.0   末尾で違う    43.7   一致    43.8
--- 4096 バイト（ns/回）
==              先頭で違う    36.1   末尾で違う   176.7   一致   173.8
compare_digest  先頭で違う  2141.5   末尾で違う  2154.3   一致  2102.0
```

4096 バイトでは、`==` が先頭で違うと 36 ns、末尾で違うと 177 ns で、どこまで一致したかが時間にはっきり出ます。`compare_digest` は位置によらず約 2.1 µs で、全バイトを比べている分だけ遅くなります。

32 バイトでは、`==` の差は 5〜10 ns でした。3 回測り直すと、末尾で違うほうが遅い向きはどの回も同じでしたが、値そのものは回ごとに数 ns 揺れました。`compare_digest` の側は、位置による向きがそろいませんでした。この手元の計測で読み取れるのはそこまでです。ネットワーク越しに、この差から何バイト目まで合っているかを当てられるかは、雑音と試行回数の兼ね合いで、ここからは言えません。

もう 1 つ、ここで比べているのは**キーそのものではなくハッシュ値**です。攻撃者は「ハッシュの先頭 1 バイトが合うキー」を狙って作れないので（原像耐性、第 146 回）、1 バイトずつ当てていく攻撃はそもそも組み立てにくくなります。それでも、秘密に関わる比較は理屈を考えずに `compare_digest` にしておく、と決めておくのが安全です。

## 何を許すか

キーが漏れたときの被害は、そのキーに何が許されていたかで決まります。発行する側が用意しておきたい制限を並べます。

| 制限 | 何を減らすか | 例 |
| --- | --- | --- |
| スコープ | できる操作。読み取りだけのキーは、漏れても書き換えられない | 上の実験の `orders:read` |
| 制限付きキー | 全権のキーを配らない | Stripe の `rk_`。Stripe は全権の `sk_` を新しい用途に使うことを勧めず、既存の利用も制限付きキーへ移すよう案内している（[Stripe](https://docs.stripe.com/keys)） |
| テスト用と本番用 | 開発の手元から本番のデータに触れない | Stripe の `_test_` と `_live_`。各環境が専用のキーを持ち、互いのオブジェクトに触れない |
| 送信元の制限 | 盗んだ場所から使えない | Stripe はキーごとのアクセスポリシーで、IP アドレスや CIDR、ASN、国で制限でき、合わない要求を拒んで通知する |
| 有効期限 | 漏れてから使える期間 | OWASP は可能な限り期限を付け、信頼する前に有効かを確かめるよう求めている（[OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)） |
| 最終使用日時 | 使われていないキーを見つけて消す | Stripe は 180 日以上、送金や支払いの作成に使われていないキーの権限を制限することがある |

最終使用日時は地味ですが、効き目の大きい欄です。誰も使っていないキーは消せますし、使われていないはずのキーが使われたら、それは漏洩の兆候です。OWASP も、秘密が**いつ、誰（何）に使われたか**と、期限切れの秘密を使おうとした試みを監査ログに残すよう挙げています（[OWASP Secrets Management 2.6](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)）。

<Callout type="note" title="公開可能キーは秘密ではない">
  Stripe の `pk_` は、ブラウザやアプリに埋め込む前提のキーで、支払い情報からトークンを作るような限られた操作しかできません（[Stripe](https://docs.stripe.com/keys)）。
  「キー」という名前でも、**漏れることを前提に権限を設計した識別子**です。第 173 回で見た「API キーはプロジェクトの識別」に近い使い方です。
  自分のサービスで同じ種類を作るなら、接頭辞で秘密のキーとはっきり分け、できることを最小にします。
</Callout>

## 入れ替える、止める

### 2 本を同時に有効にする

長く生きる秘密は、いつか入れ替える必要があります。理由は、定期的な方針、担当者の退職、漏洩の疑いなどです。問題は、キーを使うプログラムが**1 か所とは限らない**ことです。古いキーを止めた瞬間に、更新し忘れた 1 台が落ちます。

そこで、**新旧の 2 本が同時に有効な期間**を設けます。第 186 回の署名鍵のローテーションで、新しい鍵を先に配ってから切り替えたのと同じ発想です。

```
  時間 →
  新しいキー  [ 発行 ]──── 有効 ──────────────────────────────────────
  古いキー    ──── 有効 ─────────────[ 期限 ]
                  ↑ 利用側を順に新しいキーへ   ↑ 古いキーの last_used_at が止まったのを確かめてから
```

Stripe のダッシュボードでローテーションすると、古いキーと新しいキーの両方が**最長 7 日間**使え、それより長く要るなら新しいキーを手動で作って移行し、終わってから古いキーを無効にするよう案内しています。古いキーを止める前に要求のログを見て、数時間から数日にわたって要求がゼロになっていることを確かめる、とも書いています（[Stripe](https://docs.stripe.com/keys)）。上の表の最終使用日時が、ここで使われます。

1 つの利用者が複数のキーを持てるようにしておけば、この手順はどのサービスでも組めます。キーが利用者に 1 本しか持てない設計だと、入れ替えは必ず停止を伴います。

### 漏れたら、すぐに止める

漏洩したときは猶予を置きません。**即時に失効させ、持ち主に知らせます**。Stripe も、侵害されたキーは悪意のある要求を止めるために取り消す必要があるとして、有効期限に「今すぐ」を選べるようにしています（[Stripe](https://docs.stripe.com/keys)）。OWASP も、不要になったか漏れた可能性のある秘密は失効させなければならないと書き、アプリを再起動しても盗まれた認証情報は失効しないと注意しています（[OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)）。

自分で発行するキーが公開のリポジトリに漏れたことを知る手段として、GitHub の secret scanning のパートナープログラムがあります。接頭辞の付いた形式を正規表現で登録しておくと、公開リポジトリで見つかったときに GitHub から通知が届き、発行者が失効させられます。仕組みと、漏れた後の手順の順番は第 244 回で詳しく見ます。接頭辞とチェックサムを最初から付けておくことが、この仕組みに参加する前提になります。

## キーを送る方式と、キーで署名する方式

### ベアラ型の限界

ここまでのキーは、**要求のたびにキーそのものを送る**方式でした。TLS の中を通るとはいえ、キーはサーバに届き、途中のロードバランサやプロキシ、サーバのログ、アプリのメモリを通ります。どこか 1 か所で書き留められれば、そのキーは期限まで何にでも使えます。第 181 回のベアラトークンと同じ弱さで、しかも寿命が長い分だけ重くなります。

第 181 回では、DPoP や mTLS でトークンを持ち主の鍵に縛る方法を見ました。共通鍵の API キーでも、似たことができます。**キーを送らず、キーで要求に署名して送る**のです。

### AWS Signature Version 4

AWS の API は、アクセスキー ID とシークレットアクセスキーの組を使いますが、シークレットアクセスキーを送りません。要求の中身を決まった形に並べた**正規化した要求**を作り、そのハッシュを含む文字列に、シークレットアクセスキーから**派生させた鍵**で HMAC-SHA256 を掛けます（[AWS IAM: Create a signed AWS API request](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv-create-signed-request.html)）。

```
DateKey              = HMAC-SHA256("AWS4" + シークレットアクセスキー, "YYYYMMDD")
DateRegionKey        = HMAC-SHA256(DateKey, リージョン)
DateRegionServiceKey = HMAC-SHA256(DateRegionKey, サービス)
SigningKey           = HMAC-SHA256(DateRegionServiceKey, "aws4_request")
署名                  = HMAC-SHA256(SigningKey, 署名する文字列)
```

AWS は署名の目的を 3 つ挙げています。要求者の身元を確かめること、途中での改ざんを防ぐこと、そして再送への対策です。最後については「In most cases, a request must reach AWS within five minutes of the time stamp in the request.」とあります（[AWS IAM: Signing AWS API requests](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_sigv.html)）。

### 手元で確かめる: 文書の例を手で計算する

AWS の文書には、署名の途中の値まで載った例があります。Amazon Glacier の Create Vault の要求で、文書の例示用のシークレットアクセスキー `wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY` を使ったものです（[Amazon Glacier: Signing Requests](https://docs.aws.amazon.com/amazonglacier/latest/dev/amazon-glacier-signing-requests.html)）。Python の `hmac` と `hashlib` だけで計算します。

```python
canonical = "\n".join([
    "PUT", "/-/vaults/examplevault", "",
    "host:glacier.us-east-1.amazonaws.com",
    "x-amz-date:20120525T002453Z",
    "x-amz-glacier-version:2012-06-01", "",
    "host;x-amz-date;x-amz-glacier-version",
    hashlib.sha256(b"").hexdigest(),          # 本文が空なので空文字列のハッシュ
])
sts = "\n".join(["AWS4-HMAC-SHA256", "20120525T002453Z",
                 "20120525/us-east-1/glacier/aws4_request",
                 hashlib.sha256(canonical.encode()).hexdigest()])
k_date    = h(("AWS4" + secret).encode(), "20120525")
k_region  = h(k_date, "us-east-1")
k_service = h(k_region, "glacier")
k_signing = h(k_service, "aws4_request")
sig = hmac.new(k_signing, sts.encode(), hashlib.sha256).hexdigest()
```

```
正規化した要求の SHA-256: 5f1da1a2d0feb614dd03d71e87928b8e449ac87614479332aced3a701f916743
kDate     a50f8303268ea3b2dfdb45f592eac539817bb8833a300af0649c7544e67c7bcb
kRegion   1e75aac55f1490464a5d5924615c7a7487e21c65bb6eca012336e1a0e49d2591
kService  2b351c7e59890f9cc44bba9270e5860bb1187c199b7a9adcba675f6560eb4b96
kSigning  75fb39ae89095e144a7b5b520c6761dcedc4fe3acf1fc6e51fee65489bfacf74
署名: 3ce5b2f2fffac9262b4da9256f8d086b4aaf42eba5f111c21681a65a127b7c2a
文書の値と一致: True
20120526 us-east-1  kSigning 442466d9cbf99cf4 ...
20120525 us-west-2  kSigning 0f6e00f74b036bcb ...
```

正規化した要求のハッシュ（`5f1da1a2…`）も、最後の署名（`3ce5b2f2…`）も、文書の値と一致しました。文書は派生鍵の途中の値までは載せていないので、`kDate` から `kSigning` は手元の計算の値です。

最後の 2 行は、日付を 1 日ずらしたものと、リージョンを変えたものの `kSigning` です。まったく別の値になります。この形から、次のことが読み取れます。

- **シークレットアクセスキーは要求に載らない**。届くのはアクセスキー ID、日付、リージョン、サービス、署名だけ。途中で要求が記録されても、そこからシークレットは得られない（HMAC の鍵は出力から戻せない。第 146 回）
- **派生鍵は 1 日、1 リージョン、1 サービスに限られる**。署名する側が `kSigning` だけを持つ構成にすれば、それが漏れても別の日、別のリージョン、別のサービスの要求には使えない
- **署名は要求の中身に掛かる**。メソッド、パス、署名するヘッダ、本文のハッシュを書き換えると署名が合わない。ベアラ型のキーは、盗めばどの要求にも付けられた
- **時刻の窓で再送を絞る**。要求の時刻から 5 分を過ぎたものは拒まれる。逆に、文書が述べているのは時刻の窓だけで、**窓の中で同じ要求をもう一度送ること**は署名だけでは区別できない。利用者側の時計が 5 分以上ずれると、正しい要求も拒まれる

<Callout type="warn" title="よくある誤解: 署名する方式なら、サーバに秘密を預けなくてよい">
  SigV4 は HMAC、つまり共通鍵の MAC です。署名を確かめる AWS の側も、同じシークレットアクセスキー（または派生鍵を作れるもの）を持っていなければなりません。
  そのため、この回の前半の「サーバは秘密のハッシュだけを持つ」設計とは両立しません。**サーバは秘密そのものを、取り出せる形で守る**必要があります（第 151 回の KMS や HSM）。
  守っているのは**通り道**です。キーが要求に載らないので、ログ、プロキシ、メモリの写しから漏れる経路が消えます。
  サーバの側からも漏らしたくないなら、第 181 回の DPoP や mTLS のように、利用者が秘密鍵を持ち、サーバは公開鍵だけを持つ非対称の署名を使います。
</Callout>

### HTTP Message Signatures（RFC 9421）

AWS の方式はその会社だけの形式です。HTTP の要求に署名する形を標準にしたのが、2024 年 2 月の **RFC 9421（HTTP Message Signatures）**です。要求のどの部分に署名したかと署名の付帯情報を `Signature-Input` ヘッダに、署名の値を `Signature` ヘッダに入れます（[RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html)）。

```
Signature-Input: sig1=("@method" "@authority" "@path" "content-digest");created=...;keyid="...";nonce="..."
Signature: sig1=:（署名の値を Base64 にしたもの）:
```

`@method` や `@path` は要求から取り出す派生コンポーネントで、本文は直接ではなく、RFC 9530 の `Content-Digest` ヘッダ（本文のハッシュ）を署名に含めることで覆います。付帯情報には `created`（作成時刻）、`expires`（期限）、`nonce`、`alg`、`keyid` があり、アルゴリズムは HMAC-SHA256 のような共通鍵の方式も、Ed25519 や ECDSA のような公開鍵の方式も選べます。

再送について、RFC 9421 は SigV4 よりはっきり書いています。署名が要求の一部しか覆わないと、別の要求に同じ署名を付けて再送できること、それを防ぐにはまず要求を見分けられるだけの部分を覆い、`nonce` で署名ごとに一意の値を入れれば検証者が繰り返しを検出できること、作成時刻と期限で盗んだ署名の使い道を狭められること、を挙げています（[RFC 9421 7.2.2](https://www.rfc-editor.org/rfc/rfc9421.html#section-7.2.2)）。`nonce` で再送を検出するには、検証する側が使用済みの値を覚えておく必要があります。

### それぞれ何から守るか

| 脅威 | ベアラ型の API キー | SigV4（共通鍵の署名） | RFC 9421 + 公開鍵 |
| --- | --- | --- | --- |
| 要求のログやプロキシからキーが漏れる | 漏れる | 秘密は要求に載らない | 秘密は要求に載らない |
| 盗んだ要求を書き換えて送る | 防げない | 署名した範囲は防ぐ | 署名した範囲は防ぐ |
| 盗んだ要求をそのまま再送する | 防げない | 5 分の窓の外は防ぐ | 期限の外は防ぐ。nonce を覚えれば窓の中も |
| サーバの DB からキーが漏れる | ハッシュで持てば防げる | サーバが秘密を持つので守る必要がある | サーバは公開鍵だけ |
| 利用者の手元からキーが漏れる | 防げない | 防げない | 防げない（取り出せない鍵なら第 181 回の範囲で狭まる） |
| 実装の手間 | 最小 | 正規化を 1 文字でも誤ると署名が合わない | 同左。ライブラリの成熟度を確かめる |

どの方式でも、**利用者の手元にある長期の秘密が盗まれたら防げない**という最後の行は変わりません。署名にすると通り道は守れますが、秘密が長く生き続けること自体は同じです。

## まとめ

- API キーはクライアントの識別で、利用者の認証ではない。ベアラ型で長く生きることが、設計のほとんどを決める
- 生成は CSPRNG で 128〜256 ビット。base62 の 32 文字で約 190 ビット。接頭辞で種類と環境（`sk_live_`、`rk_test_` など）を示し、末尾の CRC32 のチェックサムで打ち間違いを DB に届く前に弾く。チェックサムは誰でも計算できるので、守りにはならない
- キー ID と秘密に分けると、主キーで 1 行を引いてから照合でき、ログには ID だけを出せる
- 保存するのはハッシュだけ。全体を見せるのは作成時の 1 回で、管理画面には末尾 4 文字を見せる
- 十分に長くでたらめなキーには、遅いハッシュは要らない。手元で bcrypt（cost 12）は SHA-256 の 57 万倍遅かったが、稼ぐのは約 19 ビットで、190 ビットのキーには意味がない。むしろ全要求で 250 ms を払うことになる。NIST も 112 ビット以上の look-up secret には承認されたハッシュ関数を、それ未満にパスワードハッシュを求めている
- ハッシュの比較は `compare_digest` で。手元では 4096 バイトで `==` の時間差がはっきり出た（36 ns と 177 ns）。32 バイトでは 5〜10 ns の差で、ネットワーク越しに読めるかはこの計測からは言えない
- 100 万行の表でも、主キーで引けば照合は 0.09 ms。索引が無いと 41 ms で、全要求の手前に乗る
- スコープ、制限付きキー、テスト用と本番用、送信元の制限、有効期限、最終使用日時で、漏れたときの被害を絞る
- 入れ替えは新旧 2 本が有効な期間を置き、古いキーの使用が止まってから無効にする。漏れたら即時に失効させる
- キーそのものを送る代わりに署名する方式では、秘密は要求に載らない。AWS SigV4 は日付・リージョン・サービスで派生させた鍵で HMAC を掛け、5 分の時刻の窓を持つ。文書の例を手で計算すると署名が一致した。RFC 9421 は同じ考え方の標準で、nonce と期限で再送を扱う

API キーは、どれだけ丁寧に作っても**長く生きる秘密**であることに変わりはありません。次の第 188 回では、CI のジョブや Pod のような機械について、この長期の秘密そのものを配らずに済ませる仕組みを見ます。
