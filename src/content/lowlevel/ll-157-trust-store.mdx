## ブラウザは守られたのに、なぜ他のプログラムは守られないのか

2026 年 10 月 17 日、インドの認証局 eMudhra の中間証明書 8 枚について、**秘密鍵が誰にでも計算できる**ことが Mozilla に報告されました。鍵生成の不具合で、秘密鍵が 256 未満の小さな整数になっていたのです（[Mozilla Bugzilla 2083449](https://bugzilla.mozilla.org/show_bug.cgi?id=2083449)）。鍵を計算できれば、誰でもこの中間 CA になりすまして、どの名前の証明書でも作れます。第 155 回の言葉で言えば、「ルートを 1 枚信じることは、その持ち主にあらゆる名前の証明書を作る力を渡すこと」が、悪い形で現実になりました。

Mozilla は同じ日のうちに、Firefox がこの 8 枚を信頼しないようにしました。ブラウザと OS の各社も、それぞれの経路で対策を進めました。それでも、多くの会社の情報システム部門は開発者に「Docker のベースイメージと `ca-certificates` を更新して」「Python の `certifi` を上げて」「Go のバイナリを作り直して」と依頼することになりました。

ブラウザが守られたのに、なぜ curl や Python や Java は守られないのでしょうか。第 155 回で、トラストストアはプログラムごとに違うことを表で見ました。この回では一歩進めて、次の 3 つを問います。

1. その一覧は**誰が作り、どの経路で**手元に届くのか
2. 「Java の cacerts は OS の一覧へのリンク」とは、何がどこを指しているのか
3. 一覧が更新されてから、**動いているプログラムが実際に新しい一覧で検証する**までに、何が要るのか

## 源流はほとんど 1 つ

公開の Web で使われるルートの一覧を、自分で審査して決めている組織は多くありません。Mozilla、Apple、Microsoft、Google（Chrome Root Store）の 4 つの**ルートプログラム**が、CA の監査報告を読み、事故の対応を見て、一覧に入れるか外すかを決めています。

このうち、Linux の世界の一覧のほとんどは **Mozilla の一覧**から作られています。Mozilla の一覧は、Firefox の暗号ライブラリ NSS のソースコードの中にある `certdata.txt` というファイルです。

```
Mozilla の certdata.txt（NSS）
├── Debian / Ubuntu の ca-certificates パッケージ
├── Fedora / RHEL / Amazon Linux の ca-certificates パッケージ
├── curl のサイトが配る cacert.pem
│     └── Homebrew の ca-certificates（macOS のキーチェーンの分と合わせる）
├── Python の certifi
├── Node.js のバイナリに埋め込まれた一覧
└── uv などの、一覧を同梱するツール
```

requests の文書にも、certifi より前は「Mozilla の一覧から取ったルートを同梱し、Requests の版ごとに 1 回だけ更新していた」と書かれています（[Requests: CA Certificates](https://requests.readthedocs.io/en/latest/user/advanced/#ca-certificates)）。curl の `cacert.pem` の先頭にも、`certdata.txt` から抜き出したと書かれています（[curl: CA Extract](https://curl.se/docs/caextract.html)）。

源流は 1 つでも、**手元に届くまでの経路と速さは別々**です。Mozilla が一覧を変えた日に、Debian のパッケージ、certifi、Node.js の新しい版がそろって出るわけではありません。経路ごとに、作る人、作り直す日、配る仕組みが違います。

## ブラウザだけが持っている、もう 1 本の経路

ブラウザが先に守られたのは、**ルートの一覧とは別の経路**を持っているからです。

| ブラウザ | 一覧とは別に配っているもの |
| --- | --- |
| Firefox | **OneCRL**。信頼しない中間 CA の一覧を、ブラウザの更新とは別に、数時間単位で配る。今回は 10 月 17 日 22:59 UTC に配信を終えた（[Bugzilla 2083449](https://bugzilla.mozilla.org/show_bug.cgi?id=2083449)） |
| Chrome | **CRLSets**（第 156 回）と、自前の Chrome Root Store。Chrome は 10 月 27 日の Chrome Root Store v43 で対応すると予告した |

今回の問題は、ルートではなく**中間**の鍵が漏れたことでした。ブラウザなら、その中間 8 枚だけを名指しで止められます。ところが curl や各言語のライブラリには、中間を名指しで止める仕組みがありません。持っているのは**ルートの一覧だけ**です。第 156 回で見たとおり、失効も既定では確かめません。

すると、ブラウザ以外が取れる手は 2 つに限られます。

- **ルートごと外す**。そのルートの下で正しく発行された証明書も、一緒に信頼しなくなる
- **プログラムの側に、止める鍵を書き込む**。Go は 10 月 19 日の 1.27.3 と 1.26.10 で、`crypto/x509` のセキュリティ修正を出しました（[Go Release History](https://go.dev/doc/devel/release)）。報道によれば、問題の鍵 8 個を検証から外す処理です。版を上げてビルドし直さないと効きません

Mozilla は今回、`emSign ECC Root CA - G3` を緊急に外すと決めました。鍵を計算した人の一部がその鍵を公開したからです。逆に言えば、同じ eMudhra の他のルートは一覧に残ります。

<Callout type="note" title="一覧は「信じる」「信じない」しか表せない">
  Mozilla の一覧の中には、「このルートは、ある日付より後に発行されたサーバ証明書については信頼しない」という条件付きの印（distrust-after）も書けます。第 155 回の Entrust の段階的な退場は、この形でした。
  ところが、多くのプログラムが読むのは、証明書を並べただけの PEM ファイルです。PEM には条件を書く場所がありません。Amazon Linux の `update-ca-trust` の説明にも、PEM の束は不信の情報を表せないので、その証明書は束に入れないと書かれています（[update-ca-trust(8)](https://www.mankier.com/8/update-ca-trust)）。
  条件付きの信頼は、一覧を PEM に落とす段階で「入れる」か「消す」かのどちらかに丸められます。ブラウザと同じ細かさでは守れません。
</Callout>

## OS の一覧は、元の一覧と、作られた束に分かれている

「OS の証明書ストア」と呼ばれるものは、どの OS でも 2 層になっています。**元の一覧**と、そこから**プログラムが読みやすい形に作った束**です。プログラムが読むのは後者です。

### macOS

macOS のルートは、`/System/Library/Keychains/SystemRootCertificates.keychain` というキーチェーンに入っています。このマシン（macOS 26.2）では 156 枚でした。OS の更新でだけ変わり、利用者が書き換えることはできません。社内のルートを足すときは、別のキーチェーン（System や login）に入れ、「常に信頼」の設定を付けます。

このキーチェーンを読むのは、**Apple の API（Security フレームワーク）で検証するプログラム**だけです。Safari、macOS の上の Go、Node.js の `--use-system-ca` がこれにあたります。Homebrew の OpenSSL にリンクした Python や curl は、キーチェーンを直接は読みません。読むのは Homebrew が作った `/opt/homebrew/etc/ca-certificates/cert.pem` です。

Homebrew は、この束を作るときに、キーチェーンにある証明書と curl の配る束を合わせます（[Homebrew の ca-certificates](https://github.com/Homebrew/homebrew-core/blob/main/Formula/c/ca-certificates.rb)）。その作り方の中に、こんな行があります。

```bash
# Exclude AAA Certificate Services and the emSign G3 roots by their public keys.
```

10 月 22 日の時点で、このマシンの `SystemRootCertificates.keychain` には `emSign ECC Root CA - G3` がまだ入っていました。macOS が G3 をどう扱っているかは、このファイルを見ても分かりません。ただ、**キーチェーンの中身をそのまま写し取る**と、G3 も一緒に写ってしまいます。Homebrew は、それを公開鍵の指紋で名指しして外しているわけです。束を作る人が、元の一覧に入っていない判断を自分で足すこともある、という例です。

### Debian と Ubuntu

Debian 系では、`ca-certificates` パッケージが元の一覧を `/usr/share/ca-certificates/mozilla/` に置き、`update-ca-certificates` が束を作ります（[update-ca-certificates(8)](https://manpages.debian.org/bookworm/ca-certificates/update-ca-certificates.8.en.html)）。

```
元の一覧                                    作られるもの
/usr/share/ca-certificates/mozilla/*.crt ─┐
/usr/local/share/ca-certificates/*.crt ───┼─ update-ca-certificates ─┬→ /etc/ssl/certs/*.pem とハッシュ名のリンク
/etc/ca-certificates.conf（! で無効化） ──┘                           ├→ /etc/ssl/certs/ca-certificates.crt（1 本の束）
                                                                      └→ /etc/ca-certificates/update.d/ のフックを実行
```

最後のフックが Java への橋渡しです。`ca-certificates-java` パッケージが置くフック `jks-keystore` が、追加と削除の一覧を受け取り、`/etc/ssl/certs/java/cacerts` を作り直します。Debian の OpenJDK の `cacerts` は、そこへのリンクです。

```
$ ls -l /usr/lib/jvm/java-17-openjdk-arm64/lib/security/cacerts
lrwxrwxrwx ... cacerts -> /etc/ssl/certs/java/cacerts
```

### Amazon Linux、Fedora、RHEL

Amazon Linux 2023 は Fedora の仕組みを使っています。元の一覧は p11-kit の形式で 2 か所に置かれ、`update-ca-trust` がそこから**用途ごとの束を一度に**作ります（[update-ca-trust(8)](https://www.mankier.com/8/update-ca-trust)）。

```
元の一覧（優先度: 低）  /usr/share/pki/ca-trust-source/      ← ca-certificates の RPM が置く
元の一覧（優先度: 高）  /etc/pki/ca-trust/source/anchors/   ← 管理者が足す（あらゆる用途で信頼）
                        /etc/pki/ca-trust/source/blocklist/ ← 管理者が外す（あらゆる用途で不信）
            │
            └─ update-ca-trust ─┬→ extracted/pem/tls-ca-bundle.pem      OpenSSL・curl・Python・Go 向け
                                ├→ extracted/pem/directory-hash/         ハッシュ名のディレクトリ
                                ├→ extracted/openssl/ca-bundle.trust.crt 信頼の印つきの OpenSSL 形式
                                ├→ extracted/java/cacerts                Java のキーストア形式
                                └→ extracted/edk2/cacerts.bin            UEFI 向け
```

そして、昔からあるパスは、すべて作られた束への**シンボリックリンク**になっています。

```
$ ls -l /etc/pki/tls/certs/ca-bundle.crt /etc/ssl/certs /etc/pki/java/cacerts
/etc/pki/tls/certs/ca-bundle.crt -> /etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem
/etc/ssl/certs                   -> /etc/pki/ca-trust/extracted/pem/directory-hash
/etc/pki/java/cacerts            -> /etc/pki/ca-trust/extracted/java/cacerts
```

Go が Linux で探すファイルの一覧にも、`/etc/pki/tls/certs/ca-bundle.crt` と `/etc/pki/ca-trust/extracted/pem/tls-ca-bundle.pem` が入っています（[crypto/x509 root_linux.go](https://go.dev/src/crypto/x509/root_linux.go)）。どの名前で開いても、たどり着くのは `update-ca-trust` が作った同じファイルです。

## 「Java の cacerts は OS の一覧へのリンク」をたどる

Amazon Linux 2023 に Amazon Corretto 21 を入れ、Java が読むファイルを端までたどりました。

```
$ ls -l /usr/lib/jvm/java-21-amazon-corretto.aarch64/lib/security/cacerts
... cacerts -> ../../../../../../../../../../etc/pki/java/cacerts
$ readlink -f /usr/lib/jvm/java-21-amazon-corretto.aarch64/lib/security/cacerts
/etc/pki/ca-trust/extracted/java/cacerts
```

3 段のリンクです。

```
$JAVA_HOME/lib/security/cacerts
  → /etc/pki/java/cacerts
    → /etc/pki/ca-trust/extracted/java/cacerts   ← update-ca-trust が作る実体
```

Java は、自分が OS の一覧を読んでいることを知りません。いつもどおり `$JAVA_HOME/lib/security/cacerts` を開くだけです。その先のファイルを、OS の側が作り直しています。

では、「Amazon が `ca-certificates` を更新したあとに作り直してデプロイすれば、Java 側にも反映される」の「作り直す」は、何を作り直すのでしょうか。`ca-certificates` の RPM に入っているインストール後の処理を見ると、答えが書いてあります。

```
$ rpm -q --scripts ca-certificates
postinstall scriptlet (using /bin/sh):
if [ -x /usr/bin/ln ]; then
/usr/bin/ca-legacy install
/usr/bin/update-ca-trust
fi
```

**パッケージを入れたり更新したりすると、そのたびに `update-ca-trust` が走り、`extracted/` の下の束がすべて作り直されます。** Java のキーストアもその 1 つです。だから、元の一覧（RPM）が新しくなれば、リンクの先の実体も新しくなり、Java もその実体を読みます。

この理屈が成り立つには、3 つの条件がそろう必要があります。

1. **そのファイルシステムの中で**、RPM が実際に更新されること。コンテナなら、イメージをビルドし直すこと
2. 更新の後に `update-ca-trust` が走ること。RPM の更新なら自動で走る。手で anchors に置いたときは自分で走らせる
3. Java のプロセスが**起動し直す**こと。Java はキーストアを起動時に読み、その後は読み直さない（後で確かめます）

「作り直してデプロイ」は、1 と 3 を同時に満たす操作です。新しいイメージをビルドすると 1 と 2 が起き、デプロイでプロセスが入れ替わると 3 が起きます。

<Callout type="warn" title="誤解: Java の cacerts は、どの環境でも OS の一覧へのリンクになっている">
  リンクにしているのは、OS のパッケージとして配られる Java です（Amazon Linux の Corretto の RPM、`amazoncorretto` のイメージ、Debian の OpenJDK）。
  Docker Hub の `eclipse-temurin:21-jre` では、`cacerts` は JDK に同梱された普通のファイルで、118 枚の JDK 独自の一覧でした。OS の `ca-certificates` を更新しても、この一覧は変わりません。
  Temurin のイメージは、環境変数 `USE_SYSTEM_CA_CERTS` を付けて起動したときだけ、OS の証明書を取り込んだキーストアを作ります。自分の環境の `cacerts` がどちらなのかは、`ls -l $JAVA_HOME/lib/security/cacerts` で、リンクかどうかを見れば分かります。
</Callout>

## 言語ごとに、どこから、いつ読むか

第 155 回の表を、「一覧がどこから来て、何をすれば更新されるのか」で並べ直すと、次のようになります。

| プログラム | 一覧の出どころ | 更新するには | 読むタイミング |
| --- | --- | --- | --- |
| curl、OpenSSL を使う C のプログラム | OpenSSL の既定の場所（`openssl version -d` で分かる）。Linux では OS の束 | OS のパッケージ | 実行のたび |
| Python の標準 `ssl` | リンクしている OpenSSL の既定の場所。`SSL_CERT_FILE` で上書きできる | OS のパッケージ（Homebrew なら Homebrew の） | `create_default_context()` のたび |
| Python の requests | **certifi**（Mozilla の一覧を抜き出した Python パッケージ） | `pip install -U certifi`。`REQUESTS_CA_BUNDLE` で OS の束を指すこともできる | 接続を作るとき |
| pip | 24.2 から、certifi と OS の一覧の**両方**（[pip: HTTPS Certificates](https://pip.pypa.io/en/stable/topics/https-certificates/)） | pip と certifi を上げる | 実行のたび |
| uv | 同梱した Mozilla の一覧。`--system-certs` で OS の検証器を使う（[uv: TLS certificates](https://docs.astral.sh/uv/concepts/authentication/certificates/)） | uv を上げる | 実行のたび |
| Node.js（公式のバイナリ） | **バイナリに埋め込んだ**一覧。「リリース時点で固定された Mozilla の一覧のスナップショット」（[Node.js CLI](https://nodejs.org/api/cli.html#--use-bundled-ca---use-openssl-ca)） | Node.js の版を上げる。`--use-system-ca` か `NODE_EXTRA_CA_CERTS` で OS の分を足す | 起動時 |
| Go | Linux では OS の束のファイル。macOS と Windows では OS の検証器 | OS のパッケージ。止める鍵の書き込みは Go の版を上げてビルドし直す | 最初の検証で 1 回 |
| Java | `$JAVA_HOME/lib/security/cacerts`。OS のリンクか、JDK 同梱か | リンクなら OS のパッケージ。同梱なら JDK を上げる | 起動時 |

表の右の 2 列が、今回の依頼の中身にそのまま対応しています。

- 「`ca-certificates` を更新して」は、OS の束を読むもの（curl、Python の `ssl`、Go、リンクになっている Java）のため
- 「`certifi`、`pip`、`uv` を上げて」は、OS の束を読まず、**自分で一覧を持っている**もののため
- 「Go のバイナリを作り直して」は、OS の束とは関係のない、Go の中に書き込まれた止める鍵のため
- 「ルート証明書を独自に同梱している CLI や SDK を確かめて」は、この表に載らない、残りすべてのため

Node.js の 10 月のセキュリティリリース（22.23.4、24.22.1、26.12.1）にも、依存の更新として「ca-cert (eMudhra Intermediate CA Compromise)」が入っています（[Node.js October 2026 Security Releases](https://nodejs.org/en/blog/vulnerability/october-2026-security-releases)）。埋め込みの一覧を持つプログラムは、**本体の版を上げることが、一覧を更新すること**です。

## コンテナの中では、一覧はビルドした日に止まる

コンテナのイメージは、ビルドした時点のファイルシステムをそのまま固めたものです（第 215 回）。`/etc/pki/ca-trust/extracted/` の束も、certifi の束も、ビルドした日の中身で固まります。Amazon Linux のリポジトリで `ca-certificates` が更新されても、**動いているコンテナの中のファイルは 1 バイトも変わりません**。

しかも、Dockerfile を変えずにビルドし直しても、更新されないことがあります。次の Dockerfile を 2 回ビルドしました。

```dockerfile
FROM amazonlinux:2023
RUN dnf -y -q upgrade ca-certificates && rpm -q ca-certificates
```

```
#4 [1/2] FROM docker.io/library/amazonlinux:2023@sha256:eb81ff44...
#5 [2/2] RUN dnf -y -q upgrade ca-certificates && rpm -q ca-certificates
#5 CACHED
```

2 回目の `RUN` は `CACHED` で、実行されていません。BuildKit は、命令の文字列と、その前の層が同じなら、前回の層を使い回します。リポジトリに新しいパッケージが出ていても、それを知る機会がありません。`FROM` も、手元にあるタグの古いイメージをそのまま使います。

取り直すには、`--pull` でベースイメージを取り直し、`--no-cache`（あるいは更新したい層より前の何かを変える）で `RUN` を実行させます。そのうえで、新しいイメージでプロセスを起動し直すまでがデプロイです。

distroless や `scratch` に Go のバイナリだけを置く構成では、ビルド用のステージから `/etc/ssl/certs` を写すのが定番です。このときイメージに入るのは、**ビルド用のステージを作った日の束**です。ビルド用のステージのベースイメージも、同じように取り直す必要があります。

<Callout type="warn" title="誤解: OS を更新すれば、全部のプログラムの一覧が新しくなる">
  OS のパッケージで更新されるのは、OS の束と、それへのリンクだけです。certifi、uv、公式の Node.js、JDK 同梱の cacerts、ルートを同梱した CLI や SDK は、それぞれ**自分の配布物の版**で一覧が決まります。
  逆に、certifi を上げても、curl や Go は何も変わりません。「どれを更新すれば、どれに効くか」は、上の表の「一覧の出どころ」の列で決まります。
</Callout>

## 一覧の変更が、プログラムに届くまで

ここまでの話を、1 手ずつ動かして確かめます。「ホストに社内のルートを足す」では、ファイルを置く・束を作り直す・プロセスを起動し直す、の 3 段がそれぞれ別の操作であることを見ます。「コンテナでルートを外す」では、今回の依頼の順に、どの操作でどのプログラムが新しい一覧に移るかを見ます。

## 手元で確かめる

Amazon Linux 2023（`amazonlinux:2023`、2026 年 10 月 22 日に取得、`ca-certificates-2025.2.76-1.0.amzn2023.0.3`）のコンテナの中で、自前の CA（第 155 回と同じ作り方）が発行した `lab.test` の証明書を返す HTTPS サーバを立て、各言語から接続しました。

### 束を作り直す前と後

```
== 1. 何もしていない
  curl           : NG
  python ssl     : NG
  python requests: NG
  node           : NG UNABLE_TO_VERIFY_LEAF_SIGNATURE
  go             : NG ... x509: certificate signed by unknown authority
  java           : NG SSLHandshakeException
== 2. anchors に置いただけ（update-ca-trust はまだ）
  （すべて NG のまま）
== 3. update-ca-trust の後
  curl           : ok
  python ssl     : ok
  python requests: NG
  node           : ok
  go             : ok
  java           : ok
```

2 で何も変わらないのは、`source/anchors/` が**元の一覧**の置き場所で、プログラムが読むのは `extracted/` の束だからです。3 で `extracted/java/cacerts` と `extracted/pem/tls-ca-bundle.pem` のタイムスタンプが同じ時刻に変わり、Java も Go もそろって通りました。

requests だけは 3 の後も失敗します。読んでいるのが `/usr/local/lib/python3.9/site-packages/certifi/cacert.pem` で、OS の束ではないからです。

node が 3 で通ったのは、Amazon Linux のリポジトリの Node.js 18 が、OS の OpenSSL にリンクして作られているからです（`process.config.variables.node_shared_openssl` が `true`）。公式サイトの Node.js 24.11.0 のバイナリを同じコンテナで動かすと、結果が変わりました。

```
upstream node                      : NG UNABLE_TO_VERIFY_LEAF_SIGNATURE
upstream node --use-system-ca      : ok
upstream node NODE_EXTRA_CA_CERTS  : ok
```

**同じ「Node.js」でも、誰がビルドしたかで読む一覧が違います**。OS のパッケージの Node.js と、公式のバイナリや `node` の公式イメージとでは、同じ操作の結果が変わります。

### 動いているプロセスは読み直さない

Java、Go、Python で、3 秒おきに 3 回接続するプログラムを先に起動しておき、途中で `update-ca-trust` を走らせました。

```
java try0 NG SSLHandshakeException
go   try 0 false
java try1 NG SSLHandshakeException
go   try 1 false
--- update-ca-trust done
java try2 NG SSLHandshakeException
go   try 2 false
py   try 0 False
py   try 1 False
py   try 2 True
java new process: java try0 ok
```

束は作り直されたのに、動き続けている Java と Go は 3 回目も失敗しました。Java は起動時にキーストアを読み、Go は最初の検証で束を読んで、どちらもその後は読み直しません。Python の `urllib` は接続のたびに新しいコンテキストを作り、そのたびに束を読むので、3 回目で通りました。Java を起動し直すと、1 回目から通ります。Node.js の文書にも、`NODE_EXTRA_CA_CERTS` は「プロセスの起動時にだけ読む」とあります（[Node.js CLI](https://nodejs.org/api/cli.html#node_extra_ca_certsfile)）。

ルートを**外す**ときも同じです。OS の束から G3 を消しても、動き続けているサーバのプロセスは、起動したときに読んだ G3 入りの一覧で検証し続けます。

### 同じ日の、いくつもの一覧

2026 年 10 月 22 日に、手に入る一覧の中の emSign のルートを数えました。

| 一覧 | 版 | 全体の枚数 | 入っている emSign のルート |
| --- | --- | --- | --- |
| Amazon Linux 2023 の TLS 用の束 | ca-certificates 2025.2.76 | 147 | G1、G3、C1、C3 |
| Debian bookworm の束 | ca-certificates 20250419~deb12u2 | 152 | G1、C1、C3 |
| curl の配る cacert.pem | 2026-10-20 | 118 | G1 |
| Node.js 24.22.1 の埋め込み | 24.22.1 | 118 | G1 |
| certifi | 2026.4.22 | 120 | G1、G3、C1、C3 |
| certifi | 2026.10.18 | 117 | なし |
| certifi | 2026.10.19 | 120 | G1、C1、C3 |
| Homebrew の cert.pem | 2026-10-20 | 189 | G1 |
| macOS 26.2 の SystemRootCertificates.keychain | — | 156 | G1、G3 |

Amazon Linux の束に入っていた 4 枚は、`trust list` でも、Corretto の `keytool -list -cacerts` でも同じ 4 枚でした。リンクの先が同じファイルなので、当然そろいます。リポジトリにはまだ `ca-certificates` の新しい版が出ておらず、`dnf check-update ca-certificates` は何も返しませんでした。この状態で、いくらイメージをビルドし直しても G3 は残ります。

certifi は、10 月 18 日の版で emSign をすべて外し、翌日の版で G3 以外を戻しています。一覧の作り手の判断も、数日のうちに動きます。そして、**どの一覧が今どうなっているかは、その一覧ごとに見るしかありません**。

## 自分のアプリの接続先は、どのルートにたどり着くか

一覧からルートが外れて困るのは、**そのルートにたどり着く証明書を使っている接続先**につなぐときだけです。手元の Node.js 24.16.0 と 24.22.1 の埋め込みの一覧を比べると、145 枚から 118 枚に減っていました。外れたのは DigiCert Global Root CA、DigiCert High Assurance EV Root CA、Entrust の 3 枚、COMODO Certification Authority、AffirmTrust の 4 枚、Trustwave の 3 枚、GTS Root R2、emSign の G3・C1・C3 など 31 枚です。加わったのは SECOM と Telia の新しいルート 4 枚です。

Node.js の版を上げる前に知りたいのは、「自分のアプリの接続先のうち、外れた 31 枚のどれかにたどり着くものはあるか」です。この節では、その問いの意味と調べ方を見ます。

### 影響を受けるのは、自分が検証する接続だけ

一覧を使うのは、**相手の証明書を検証する側**です。

- アプリから外へ出る HTTPS の接続（外部の API、Webhook の送信、クラウドや SaaS の SDK）は、アプリの Node.js の一覧で検証します。影響を受けるのはここです
- アプリが受ける接続は、つないできた側（ブラウザや相手のサーバ）が、相手の一覧で検証します。アプリの Node.js の一覧は使われません
- `ca` オプションで CA を渡している接続は、埋め込みの一覧を使いません。Node.js の文書には、`ca` を指定すると既定の一覧は「連結されるのではなく、完全に置き換えられる」とあります（[Node.js TLS](https://nodejs.org/api/tls.html#tlscreatesecurecontextoptions)）。データベースの CA を渡している接続（第 167 回）がこれにあたります

### ルートは、サーバから送られてこない

第 155 回で見たとおり、サーバが送るのはサーバ証明書と中間証明書までで、ルートはクライアントの一覧の中にあります。クライアントは、サーバ証明書から発行者をたどり、**自分の一覧にある証明書に行き着いたところで**検証を終えます。つまり、どのルートにたどり着くかは、サーバが送る証明書と、クライアントの一覧の**両方**で決まります。

github.com に、Node.js 24.22.1 の一覧を PEM に書き出したもの（作り方は後述）を渡してつなぐと、次のようになりました（2026 年 10 月 23 日）。

```
$ openssl s_client -connect github.com:443 -servername github.com -CAfile node-24.22.1.pem -showcerts
Certificate chain
 0 s:CN=github.com
   i:C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication CA DV E36
 1 s:C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication CA DV E36
   i:C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication Root E46
 2 s:C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication Root E46
   i:C=US, ST=New Jersey, L=Jersey City, O=The USERTRUST Network, CN=USERTrust ECC Certification Authority
```

サーバは 3 枚を送っています。3 枚目は、Sectigo の新しいルート E46 を、古いルート USERTrust ECC が署名したクロス署名の証明書です（第 155 回）。送られてきた最後の証明書の発行者だけを読むと、「USERTrust ECC にたどり着く」と答えたくなります。

ところが、検証で実際に組まれた経路は違いました。`s_client` が標準エラーに出す `depth=` の行が、検証で組まれた経路です。

```
depth=2 C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication Root E46
depth=1 C=GB, O=Sectigo Limited, CN=Sectigo Public Server Authentication CA DV E36
depth=0 CN=github.com
Verify return code: 0 (ok)
```

E46 そのものが Node.js の一覧に入っているので、OpenSSL はそこで止まります。OpenSSL は 1.1.0 から、発行者を探すたびに、送られてきた証明書より先に一覧を見るからです。

一覧から E46 を抜くと、経路は延びます。抜いた一覧を `-CAfile` に渡すと、送られてきたクロス署名の証明書を通って USERTrust ECC にたどり着き、検証は通りました。E46 と USERTrust ECC の両方を抜くと、初めて失敗しました。

```
一覧から抜いたもの           たどり着いたルート     Node.js の結果
なし                         E46                    ok
E46                          USERTrust ECC          ok
E46 と USERTrust ECC         なし                   NG UNABLE_TO_GET_ISSUER_CERT_LOCALLY
```

ルートが外れても、クロス署名で別のルートへの道が残っていれば、接続は切れません。逆に言えば、「どのルートにたどり着くか」は接続先だけを見ても決まらず、**検証に使う一覧を使って経路を組ませてみる**しかありません。

<Callout type="warn" title="誤解: getPeerCertificate(true) の先頭が、検証に使われたルート">
  Node.js の `tlsSocket.getPeerCertificate(true)` で `issuerCertificate` をたどると、**サーバが送った証明書**を並べ、その最後の証明書の発行者を一覧から探して付け足したものが返ります。検証で組まれた経路ではありません。
  www.amazon.com では、たどった先は「Amazon Root CA 1 ← Starfield Services Root Certificate Authority - G2」となり、Starfield が最後に来ました。同じ一覧で `s_client` を使うと、経路は Amazon Root CA 1 で止まっていました。どのルートにたどり着くかを見るときは、`s_client` の `depth=` の行を読みます。
</Callout>

### 調べ方

#### 1. 接続先を洗い出す

最初に、アプリがどこへつないでいるかの一覧を作ります。コードだけでは足りません。

- コードと設定にある URL とホスト名。環境変数やシークレットに入っているものも含む
- SDK が内部でつなぐ先。SDK を使うと、ホスト名がコードに現れない
- 実行時にしか決まらない接続先。利用者が登録した Webhook の送り先などは、データベースの中にある
- 実際に出ていった通信の記録。DNS の問い合わせのログや、外向きのプロキシのログ

利用者が登録する Webhook の送り先のように、事前に一覧にできない接続先もあります。それについては、後述のとおり、失敗したときにエラーの種類が分かるようにしておくことになります。

#### 2. 新しい一覧で経路を組ませる

公式の Node.js の一覧は、`tls.rootCertificates` で PEM の文字列として取り出せます。これをファイルに書き出し、`openssl s_client` に渡します。

```bash
node -p "require('tls').rootCertificates.join('\n')" > node-24.22.1.pem

openssl s_client -connect api.example.com:443 -servername api.example.com \
  -CAfile node-24.22.1.pem </dev/null 2>&1 | grep -E '^depth|Verify return'
```

最も大きい `depth=` の行が、たどり着いたルートです。`Verify return code: 0 (ok)` でなければ、新しい Node.js では失敗します。版を上げる前と後の一覧で 1 回ずつ実行すれば、ルートが変わる接続先と、失敗する接続先が分かります。

#### 3. 新しい版の Node.js で、実際につなぐ

最後の決め手は、デプロイする版の Node.js で、実際に接続してみることです。`openssl` のコマンドと Node.js とで、リンクしている OpenSSL の版も設定も違いうるので、同じ結果になるとは限りません。

```js
// try.js
const tls = require('tls');
const host = process.argv[2];
const s = tls.connect({ host, port: 443, servername: host }, () => {
  console.log(process.version, host, 'ok');
  s.end();
});
s.on('error', e => console.log(process.version, host, 'NG', e.code));
```

```bash
while read h; do
  ~/.asdf/installs/nodejs/24.16.0/bin/node try.js "$h"
  ~/.asdf/installs/nodejs/24.22.1/bin/node try.js "$h"
done < hosts.txt
```

```
v24.16.0 github.com ok
v24.22.1 github.com ok
v24.16.0 www.amazon.com ok
v24.22.1 www.amazon.com ok
...
```

2026 年 10 月 23 日に、国内外の銀行、SaaS、クラウド、報道機関などの 45 の Web サイトで試したところ、24.16.0 と 24.22.1 の結果はすべて `ok` で同じでした。たどり着いたルートは、DigiCert Global Root G2 と G3、Amazon Root CA 1、ISRG Root X2、Sectigo の R46 と E46、GlobalSign の R46 と E46、SECOM の Security Communication RootCA2 などで、外れた 31 枚は 1 つもありませんでした。公開の Web サイトの多くは、外されることが前もって知らされていたルートから、すでに移っています。古いルートに残っていやすいのは、長く更新されていない社内のシステム、取引先の古い API、機器の管理画面などです。

### 調べた結果は、調べた日の結果

この確認は、**調べた日の証明書**についての答えです。

- 証明書は数か月ごとに更新されます。更新のときに、中間証明書や、たどり着くルートが変わることがあります（第 155 回の Let's Encrypt の例）
- 同じホスト名でも、つないだ先のサーバや拠点、クライアントが対応する署名の方式によって、送られる証明書が違うことがあります

そのため、一度調べて終わりにせず、デプロイする版の Node.js で実際の接続先につなぐ確認を、ステージングや CI に組み込むのが確実です。

失敗したときのエラーも、見分けられるようにしておきます。自前の CA で、一覧に無いルートにたどり着くサーバを立てて Node.js 24.22.1 でつなぐと、サーバが中間証明書まで送るときは `UNABLE_TO_GET_ISSUER_CERT_LOCALLY`、サーバ証明書だけを送るときは `UNABLE_TO_VERIFY_LEAF_SIGNATURE` になりました。後者は、サーバが中間証明書を送り忘れたとき（第 159 回）と同じエラーです。ログにエラーの種類と接続先を残しておけば、`s_client -showcerts` で送られてくる証明書を数え、ルートの側の問題か、送り忘れかを切り分けられます。

## この部品は何と組み合わさるか

| 層 | 誰が決めるか | 変わったことがどう届くか |
| --- | --- | --- |
| ルートプログラム（Mozilla、Apple、Microsoft、Chrome） | 監査と事故の対応を見て、入れる・外す | 一覧のソースの変更として公開される |
| ブラウザの別経路（OneCRL、CRLSets） | ブラウザの開発元 | ブラウザの更新とは別に、数時間単位で配られる |
| OS のパッケージ（ca-certificates） | ディストリビューション | パッケージの更新。インストール時に束を作り直す（`update-ca-certificates`、`update-ca-trust`） |
| 自分で一覧を持つ配布物（certifi、Node.js、uv、JDK 同梱の cacerts） | それぞれの開発元 | その配布物の版を上げる |
| イメージ（第 215 回） | 自分たち | ビルドし直す。キャッシュを使わずに |
| プロセス | 自分たち | 起動し直す |

ブラウザ以外のプログラムが新しい一覧で検証するには、表の下の 3 層を、自分たちで動かす必要があります。情報システム部門からの依頼が「更新して」「ビルドし直して」「デプロイして」の 3 つになっているのは、この層の数に対応しています。

## まとめ

- 公開の Web のルートの一覧は、4 つのルートプログラムが決めている。Linux の世界の一覧の多くは、Mozilla の `certdata.txt` から作られている
- ブラウザは、ルートの一覧とは別に、中間 CA を名指しで止める経路（OneCRL、CRLSets）を持つ。他のプログラムが持つのはルートの一覧だけで、取れる手は「ルートごと外す」か「プログラムに止める鍵を書き込む」になる
- PEM の束は「信じる」「信じない」しか表せない。条件付きの信頼は、束に落とすときに丸められる
- OS の証明書ストアは、元の一覧と、そこから作った束の 2 層。Debian は `update-ca-certificates`、Amazon Linux と RHEL は `update-ca-trust` が束を作る。プログラムが読むのは束のほう
- Amazon Linux の Corretto の `cacerts` は、`/etc/pki/java/cacerts` を経て `update-ca-trust` が作るキーストアへの、3 段のリンク。RPM を更新すると後処理で束が作り直されるので、Java にも届く。Temurin の公式イメージは同梱のファイルで、リンクではない
- certifi、uv、公式の Node.js、JDK 同梱の cacerts は、自分の版で一覧が決まる。OS を更新しても変わらない
- コンテナでは、一覧はビルドした日に固まる。同じ Dockerfile のビルドはキャッシュで更新を素通りするので、`--pull` と `--no-cache` で取り直す
- Java と Go は一覧を起動時か最初の検証で読み、その後は読み直さない。束を作り直したら、プロセスを起動し直すまでが更新
- 一覧の変更が効くのは、自分が検証する側の接続（外へ出る HTTPS）だけ。`ca` オプションで CA を渡している接続は埋め込みの一覧を使わない
- どのルートにたどり着くかは、サーバが送る証明書と、クライアントの一覧の両方で決まる。送られてきた最後の証明書の発行者や `getPeerCertificate(true)` ではなく、新しい一覧を渡した `s_client` の `depth=` の行と、デプロイする版の Node.js で実際につないだ結果で確かめる。証明書は更新で変わるので、確認は継続して行う

これで、証明書の中身、連鎖、発行と失効、そして信頼する一覧の配られ方が揃いました。次の回では、その証明書が TLS 1.3 のハンドシェイクの中でどう使われるのかを、1 メッセージずつ読みます。
