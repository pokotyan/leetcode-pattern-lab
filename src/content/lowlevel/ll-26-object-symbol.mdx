## ELF という入れ物

Linux の実行可能ファイル、オブジェクトファイル、共有ライブラリは、すべて **ELF**（Executable and Linkable Format）という形式です。

| OS | 形式 |
| --- | --- |
| Linux, BSD | ELF |
| macOS | Mach-O |
| Windows | PE / COFF |

形式は違いますが、**入っているものはほぼ同じ**です。コード、データ、シンボルの一覧、再配置情報。

ファイルの先頭 4 バイトを見れば判別できます。

```bash
xxd -l 16 ./a.out
# 00000000: 7f45 4c46 0201 0100 ...     .ELF....
```

`0x7F` に続いて `ELF` の 3 文字。これが**マジックナンバー**です。`file` コマンドはこれを見ています。

## セクション

ELF の中身は **セクション**に分かれています。

```bash
readelf -S ./foo.o
```

主なものです。

| セクション | 中身 |
| --- | --- |
| `.text` | 機械語のコード |
| `.data` | 初期値ありの変数 |
| `.bss` | 初期値なしの変数（**サイズだけ記録。中身はない**） |
| `.rodata` | 定数、文字列リテラル |
| `.symtab` | シンボルテーブル |
| `.strtab` | シンボル名の文字列 |
| `.rela.text` | `.text` に対する再配置情報 |
| `.debug_*` | デバッグ情報（`-g` を付けたとき） |

**リンカは、同じ名前のセクションを連結します。** 10 個の `.o` の `.text` が繋がって、1 つの大きな `.text` になります。

<Callout type="note" title="セクションとセグメント">
  - **セクション**：リンカ向けの区分。細かい
  - **セグメント**：ローダ向けの区分。粗い。権限（読み / 書き / 実行）が同じものをまとめる

  リンク時に、複数のセクションが 1 つのセグメントにまとめられます。
  `.text` と `.rodata` は両方とも「読み取り + 実行可能」なので同じセグメントに入ります。

```bash
readelf -l ./a.out       # セグメント（プログラムヘッダ）を見る
```
</Callout>

## シンボルテーブル

**シンボル**とは、名前の付いた場所のことです。関数名、グローバル変数名。

```bash
nm foo.o
```

```
0000000000000000 T main
                 U printf
0000000000000004 C counter
0000000000000000 D initialized
0000000000000000 b hidden_static
```

左が値（多くの場合オフセット）、中央 1 文字が種類、右が名前です。

| 記号 | 意味 |
| --- | --- |
| **T** | `.text` にある。外部から見える（大文字 = global） |
| **t** | `.text` にある。このファイル内のみ（小文字 = local、`static`） |
| **D** | 初期値ありのデータ |
| **B** | `.bss` にある |
| **U** | **未定義**。他のファイルで定義されているはず |
| **W** | 弱いシンボル。他に定義があればそちらが優先される |

**`U` が付いているものが、リンクで解決すべき相手です。** `undefined reference` エラーは、リンクが終わっても `U` のまま残ったものについて出ます。

```bash
nm -u ./foo.o           # 未定義シンボルだけ表示
nm -D ./libfoo.so       # 共有ライブラリの動的シンボル
nm -C ./a.out           # C++ の名前を復元して表示
```

## 再配置情報

アセンブラが残した「ここを後で直してほしい」というメモです。

```bash
readelf -r foo.o
```

```
Relocation section '.rela.text':
  Offset          Info           Type           Sym. Name + Addend
000000000015  000a00000004 R_X86_64_PLT32    printf - 4
```

「`.text` の先頭から 0x15 バイト目を、`printf` のアドレスで書き換えよ」という指示です。

**型**（`R_X86_64_PLT32` など）が、書き換え方を決めます。絶対アドレスを入れるのか、現在位置からの相対値を入れるのか、といった違いです。

実際の機械語を見ると、その場所が 0 で埋まっています。

```bash
objdump -d foo.o
```

```
  10:  bf 00 00 00 00        mov    $0x0,%edi        # 0 が埋まっている
  15:  e8 00 00 00 00        call   1a <main+0x1a>   # ここも 0
```

リンク後に同じ場所を見ると、実際のアドレスが入っています。**リンクとは、この穴埋め作業**です。

## デバッグ情報

`-g` を付けると、`.debug_*` セクションに情報が入ります。

- どの機械語が、ソースの何行目に対応するか
- 変数名と、その型、格納場所
- 構造体や関数の定義

これがあるから、gdb で行番号が出て、変数名で値を見られます。

**デバッグ情報はかなり大きい**です。実行可能ファイルのサイズが数倍になることも珍しくありません。

```bash
strip ./a.out                    # デバッグ情報とシンボルを削除
objcopy --only-keep-debug a.out a.out.debug    # 別ファイルに分離する方法もある
```

配布用には strip し、デバッグ情報は別に保管しておくのが実務的なやり方です。クラッシュ時のスタックトレースは、後から突き合わせられます。

<Callout type="warn" title="strip すると解析しにくくなる">
  `strip` 済みのバイナリでは、`nm` にシンボルが出ず、
  スタックトレースが `??` だらけになります。
  本番で問題が起きたときに困るので、**デバッグ情報を捨てるのではなく分離する**ほうが安全です。
</Callout>

## 実際に開いてみる

```bash
cat > foo.c <<'END'
#include <stdio.h>
int counter;
int initialized = 42;
static int hidden = 7;
int main(void) { printf("%d\n", counter + initialized + hidden); return 0; }
END

gcc -c foo.c -o foo.o
readelf -S foo.o | head -20      # セクション一覧
nm foo.o                          # シンボル
readelf -r foo.o                  # 再配置情報
objdump -d -M intel foo.o         # 逆アセンブル
```

`counter` が `.bss`、`initialized` が `.data`、`hidden` が小文字（local）で出ることを確認できます。

## サイズの内訳を見る

```bash
size ./a.out
#    text    data     bss     dec     hex filename
#    1234     560       8    1802     70a a.out
```

`bss` がファイルサイズに含まれていないことが、この表からも分かります。`dec` は実行時に必要なメモリの合計です。

## まとめ

- ELF はセクションの集まり。リンカは同名セクションを連結する
- シンボルは名前の付いた場所。`U` は未定義で、リンクで解決すべきもの
- 再配置情報は「この位置をこのシンボルのアドレスで埋めよ」という指示
- リンクとは、この穴埋め作業のこと
- デバッグ情報は大きい。捨てるより分離する
- `nm`、`readelf`、`objdump`、`size` で中身を確認できる
