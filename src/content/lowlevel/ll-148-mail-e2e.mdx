## 経路を守っても、中身は誰が読めるのか

第 144 回では、MTA-STS や DANE を使って、サーバとサーバの間の TLS を「なりすましたサーバに繋がない」ところまで固めました。第 145〜147 回では、SPF・DKIM・DMARC で「このドメインが出したメールか」を確かめました。

それでも残る問題があります。**メールは、途中のサーバに一度置かれてから次へ渡される**仕組みだという点です。

```
Alice の MUA ──TLS──▶ 提出サーバ ──TLS──▶ 中継 ──TLS──▶ 受信 MX ──▶ メールボックス ──TLS──▶ Bob の MUA
                      [平文で置く]       [平文]        [平文]       [平文で保存]
```

TLS が守るのは矢印の上だけです。四角の中、つまり**各サーバのキューやメールボックスでは、本文はそのまま読めます**。サーバの管理者、サーバに侵入した攻撃者、保存されたメールを開示するよう求められた事業者は、中身を読めます。

ここを守るには、**送る人が暗号化し、受け取る人だけが復号する**しかありません。途中のサーバは、意味の分からないバイト列を運ぶだけになります。これを**エンドツーエンド暗号化**と呼びます。メールでこれを実現する標準は 2 つあり、**S/MIME** と **OpenPGP** です。この回では、両者が何を守り、何を守らないのかを、手元で署名と暗号化を掛けて確かめながら見ていきます。

## 3 つの守りの違い

最初に、この章で出てきた守りを並べておきます。似た言葉で呼ばれますが、守る範囲がまったく違います。

| 守り | 誰が掛けるか | 守る範囲 | 保証すること | 見た回 |
| --- | --- | --- | --- | --- |
| 経路の TLS | 隣り合うサーバ同士 | 1 区間の通信路 | その区間で盗み見・改ざんされない | 第 144 回 |
| DKIM | 送信ドメインのサーバ | ヘッダの一部と本文 | `d=` のドメインが責任を持つ | 第 146 回 |
| S/MIME・OpenPGP | 送る人の MUA | 本文（ヘッダは原則守らない） | **この人が書いた**、**この人しか読めない** | この回 |

DKIM とこの回の署名は、どちらも第 106 回のデジタル署名を使いますが、**鍵を持っている主体が違います**。DKIM の鍵はドメインの送信サーバが持ち、社員の誰が送っても同じ鍵で署名します。S/MIME や OpenPGP の鍵は**個人**が持ち、その人の端末の中で署名します。

## S/MIME と OpenPGP

2 つの方式は、暗号の部品はほぼ同じで、**鍵を誰がどう保証するか**が違います。

| | S/MIME | OpenPGP |
| --- | --- | --- |
| 現行の仕様 | [RFC 8551](https://www.rfc-editor.org/rfc/rfc8551.html)（S/MIME 4.0、2019 年）、証明書の扱いは [RFC 8550](https://www.rfc-editor.org/rfc/rfc8550.html) | [RFC 9580](https://www.rfc-editor.org/rfc/rfc9580.html)（2024 年。RFC 4880 を置き換え） |
| 中身の形式 | CMS（[RFC 5652](https://www.rfc-editor.org/rfc/rfc5652.html)）、ASN.1 の DER | 独自のパケット列 |
| 公開鍵の入れ物 | X.509 の証明書（第 109 回） | OpenPGP の公開鍵（利用者 ID と自己署名つき） |
| 誰が保証するか | 認証局（第 110 回の信頼の連鎖） | 利用者同士の署名、または配布する場所 |
| 主な利用者 | 企業、官公庁 | 開発者、報道、オープンソースの配布物 |

どちらも、**本文を共通鍵で暗号化し、その共通鍵を受け取る人の公開鍵で包む**という構成です（第 105 回のハイブリッド暗号）。受け取る人が 3 人なら、共通鍵を 3 人分それぞれの公開鍵で包んで添えます。本文の暗号文は 1 つで済みます。

## S/MIME: 証明書で人を結びつける

S/MIME は、第 109 回の X.509 証明書を**メールアドレスに対して**発行します。`subjectAltName` にメールアドレスを、拡張鍵用途（EKU）に `emailProtection` を入れます。

公的に信頼される S/MIME 証明書については、CA/Browser Forum が 2023 年 9 月から [S/MIME Baseline Requirements](https://cabforum.org/working-groups/smime/requirements/) を適用しています（執筆時点の最新は 2026 年 7 月の 1.0.15 版）。そこでは、確認の強さに応じて 4 つの種類が決められています。

| 種類 | 認証局が確かめること |
| --- | --- |
| Mailbox-validated | そのメールアドレスを受け取れること |
| Organization-validated | 組織が実在すること |
| Sponsor-validated | 組織と、その組織に属する個人 |
| Individual-validated | 個人の身元 |

最も手軽な Mailbox-validated が確かめるのは、第 133 回で見たドメインの所有確認と同じく「**そのアドレス宛てのメールを受け取れる**」ことだけです。証明書に書かれた名前の人が本当にその人かは、上の種類を選ばない限り分かりません。

### 証明書を配る難しさ

S/MIME の暗号化で一番困るのは、**暗号化して送る前に、相手の証明書を手に入れておく必要がある**ことです。Web の TLS なら、サーバが接続のたびに証明書を送ってくれます。メールでは相手はその場にいません。

実際には次のどれかで手に入れます。

- 相手から**署名つきのメール**を一度もらう。署名には証明書が同梱されるので、MUA がそれを覚える
- 組織のアドレス帳（ディレクトリ）に社員の証明書を載せておき、MUA がそこから引く
- 証明書のファイルを別の手段で受け取る

1 つめの方法だと、**最初の 1 通は暗号化できません**。2 つめの方法は、同じ組織の中では働きますが、取引先には届きません。S/MIME が企業の中で使われ、企業の外にはあまり広がらなかった理由の 1 つがここにあります。証明書には有効期限があり、第 111 回で見た更新と失効の手間も、利用者の数だけ発生します。

## 手元で確かめる: S/MIME の署名

OpenSSL 3.6.2 の `openssl cms` で、自前の CA、Alice と Bob の証明書を作り、署名と暗号化を掛けてみます。証明書は第 110 回と同じ手順で作り、`extendedKeyUsage=emailProtection` と `subjectAltName=email:alice@example.com` を入れました。

本文は MIME の 1 部分として用意し、署名します。

```bash
printf 'Content-Type: text/plain; charset=utf-8\r\n\r\nMeeting moved to 15:00. Budget draft attached later.\r\n' > body.txt
openssl cms -sign -in body.txt -signer alice.crt -inkey alice.key \
  -from alice@example.com -to bob@example.com -subject "Q3 budget" -out signed.eml
```

できたメッセージの先頭はこうなります。

```
To: bob@example.com
From: alice@example.com
Subject: Q3 budget
MIME-Version: 1.0
Content-Type: multipart/signed; protocol="application/pkcs7-signature"; micalg="sha-256"; boundary="----8093833A78786FE9EB04E7EA69FBA743"

This is an S/MIME signed message

------8093833A78786FE9EB04E7EA69FBA743
Content-Type: text/plain; charset=utf-8

Meeting moved to 15:00. Budget draft attached later.

------8093833A78786FE9EB04E7EA69FBA743
Content-Type: application/pkcs7-signature; name="smime.p7s"
Content-Transfer-Encoding: base64

MIIFCAYJKoZIhvcNAQcCoIIE+TCCBPUCAQExDTALBglghkgBZQMEAgEwCwYJKoZI ...
```

第 143 回の MIME の形そのものです。**multipart/signed** の 1 つめの部分が本文で、平文のまま読めます。2 つめの `smime.p7s` が CMS の SignedData で、中には署名の値、Alice の証明書、署名した時刻、本文のハッシュが入っています。本文を平文で残しておくのは、S/MIME に対応していない MUA でも本文だけは読めるようにするためです。

検証を、本文を変えた場合、ヘッダを変えた場合、信頼していない CA で確かめた場合で試しました。

```
そのまま                        CMS Verification successful
本文の 15:00 を 17:00 に変更    CMS Verification failure (CMS_SignerInfo_verify_content:verification failure)
Subject と From: を書き換え     CMS Verification successful
別の CA を信頼の根にして検証    CMS Verification failure (unable to get local issuer certificate)
```

本文の書き換えと、知らない CA が出した証明書は検出されます。しかし 3 つめのとおり、**件名と `From:` を書き換えても署名は正しいまま**です。署名が掛かっているのは本文の MIME 部分だけで、その外側のヘッダは範囲に入っていないからです。

<Callout type="warn" title="よくある誤解: 署名が正しければ差出人も正しい">
  上の実験では、`From:` を別人に書き換えても `openssl cms -verify` は成功しました。
  署名が言えるのは「**この証明書の持ち主が、この本文を書いた**」ことだけです（第 106 回の「署名はこの鍵で、としか言わない」）。
  差出人との結びつけは、受け取った MUA の仕事です。RFC 8550 は、受け取る側は `From:` か `Sender:` のアドレスが署名者の証明書にあるアドレスと一致するかを確かめなければならない（MUST）としています（[RFC 8550 3](https://www.rfc-editor.org/rfc/rfc8550.html#section-3)）。
  DMARC が DKIM の `d=` と `From:` を結びつけた（第 147 回）のと同じ構図で、**結びつける手順を飛ばせば、正しい署名が偽の差出人を飾ります**。
</Callout>

## 手元で確かめる: 暗号化と、送った本人が読めない問題

次に Bob 宛てに暗号化します。S/MIME 4.0 が加えた AEAD の形式（**AuthEnvelopedData**、AES-GCM）と、従来の形式（**EnvelopedData**、AES-CBC）の 2 つを作りました。

```bash
openssl cms -encrypt -aes-256-gcm -in body.txt -recip bob.crt \
  -from alice@example.com -to bob@example.com -subject "Q3 budget" -out enc-gcm.eml
```

```
To: bob@example.com
From: alice@example.com
Subject: Q3 budget
MIME-Version: 1.0
Content-Disposition: attachment; filename="smime.p7m"
Content-Type: application/pkcs7-mime; smime-type=authEnveloped-data; name="smime.p7m"
Content-Transfer-Encoding: base64
```

今度は本文全体が **application/pkcs7-mime** の 1 つの塊になり、中身は読めません。構造を `openssl cms -cmsout -print` で見ると、次の部品が入っていました。

```
contentType: id-smime-ct-authEnvelopedData
  d.issuerAndSerialNumber:            ← どの証明書の鍵で包んだか（Bob）
    keyEncryptionAlgorithm: rsaEncryption
  encryptedContentInfo:
    algorithm: aes-256-gcm             ← 本文を暗号化した共通鍵の方式
    encryptedContent: ...
```

受け取る人を「どの CA の何番の証明書か」で指し、その公開鍵で包んだ共通鍵を添える、という前の節の構成がそのまま見えます。Bob の鍵では復号でき、Alice の鍵では復号できません。

```
== Bob の鍵で復号
Meeting moved to 15:00. Budget draft attached later.
== Alice の鍵で復号
Error decrypting CMS using private key
```

**送った本人も、自分の送信済みのメールを読めません**。宛先に自分の証明書も加えれば読めるようになり、実際の MUA はそうしています。`openssl cms -encrypt ... bob.crt alice.crt` で作ると、包んだ鍵が 2 人分入り、Alice の鍵でも復号できました。

署名と暗号化を両方掛けるときは、**署名してから暗号化**し、multipart/signed をまるごと AuthEnvelopedData に入れます。97 バイトの本文が、署名つきで 2373 バイト（証明書を同梱するため）、暗号化のみで 977 バイト、両方で 4032 バイトになりました。

<Callout type="warn" title="よくある誤解: 秘密鍵は、なくしたら作り直せばよい">
  署名用の鍵なら、なくしても新しい鍵で署名し直せば済みます。
  しかし**暗号化用の秘密鍵をなくすと、その鍵宛てに届いた過去のメールは二度と読めません**。メールボックスには暗号文のまま残っているからです。
  TLS の鍵は通信が終われば捨ててよい（第 112 回の前方秘匿性）のに対し、メールの暗号化の鍵は**何年も保管し続ける必要があります**。
  企業が S/MIME を配るときに、暗号化用の鍵だけを組織で預かる（鍵の寄託）ことがあるのはこのためです。逆に言えば、預かった側はいつでも読めるので、「本人しか読めない」という性質は弱まります。
</Callout>

## 暗号化だけでは改ざんを防げない: EFAIL

2018 年 5 月、S/MIME と OpenPGP の両方で、**暗号化されたメールの平文を攻撃者に送らせる**攻撃が公表されました。**EFAIL** です（[efail.de](https://efail.de/)、CVE-2017-17688 と CVE-2017-17689）。第 104 回で見た「暗号化だけでは、改ざんを防げない」が、実際のメールで起きた例です。

### CBC の暗号文は書き換えられる

S/MIME の従来の EnvelopedData は、AES-CBC で本文を暗号化し、**改ざんを検出する仕組みを持っていません**。第 104 回で見たとおり、CBC の復号は次の形でした。

```
P[i] = Decrypt(C[i]) XOR C[i-1]      （C[0] は IV）
```

平文の先頭 16 バイトが分かっていれば、IV に「分かっている平文 XOR 入れたい平文」を XOR するだけで、先頭のブロックを好きな 16 バイトに変えられます。MIME の本文は `Content-Type: te` のように始まることが多く、**先頭は推測できます**。

手元で、さきほどの AES-CBC の暗号文に対して、IV を書き換えて先頭を `X-Note: forged\r\n` に変え、3 つめの暗号文ブロックの 1 バイトを変えて 4 つめのブロックの `15` を `19` に変えました。鍵は使っていません。

```python
known  = b"Content-Type: te"
wanted = b"X-Note: forged\r\n"
for i in range(16):
    cbc[IV + i] ^= known[i] ^ wanted[i]
cbc[CT + 16*2 + 13] ^= ord("5") ^ ord("9")
```

Bob の鍵で復号した結果です。

```
CBC: exit=0
b'X-Note: forged\r\nxt/plain; charse%\xb2\xe3M\xde\xbe\x8ce\xf6\xa0\xfdd:\xa0\xd5\xc7ng moved to 19:00. Budget draft attached later.\r\n'
```

**復号は成功扱い**で、先頭は狙いどおりに、会議の時刻は 19:00 に変わりました。書き換えた直後のブロックだけが意味のないバイト列になりますが、それを知らせる仕組みはありません。

EFAIL の「CBC/CFB ガジェット攻撃」は、この性質を使って、**暗号文の前後に HTML の画像タグの断片を平文として作り込み**ます。受け取った MUA が復号して HTML として表示すると、画像を取りにいく URL の中に、復号された平文が入ってしまいます。攻撃者は、以前に盗み取っておいた暗号文を改変して本人に送り直すだけで、本人の MUA に平文を送らせられます。もう 1 つの「直接の持ち出し」は暗号の弱さではなく、**暗号化された部分と平文の部分を 1 つの HTML としてつなげて表示する** MUA の実装を突いたものでした。

### AEAD でも、確かめる前の平文を使えば同じこと

同じ書き換えを AES-GCM の暗号文に掛けると、今度は検出されます。ただし、手元の `openssl cms` では次のようになりました。

```
$ openssl cms -decrypt -inform DER -in gcm-bad.der -recip bob.crt -inkey bob.key -out out.txt
Error decrypting CMS structure
exit=4
$ cat out.txt
Content-Type: text/plain; charset=utf-8

Meiting moved to 15:00. Budget draft attached later.
```

終了コードは失敗を返していますが、**改ざんされた平文（`Meeting` が `Meiting` になったもの）が出力ファイルに書かれています**。GCM の認証タグは暗号文の最後にあるので、流しながら復号する実装は、タグを確かめる前に平文を書き出してしまうのです。呼び出す側が終了コードを見ずに出力を使えば、AEAD にした意味がなくなります。

EFAIL の当時、OpenPGP の実装 GnuPG も、完全性の検査（MDC）に失敗したときに警告を出すだけで平文は出力しており、MUA がその平文を表示していました。GnuPG は 2018 年 6 月の 2.2.8 で、MDC のないメッセージの復号を**警告ではなく失敗**に変えています（[GnuPG 2.2.8 の告知](https://lists.gnu.org/archive/html/info-gnu/2018-06/msg00005.html)）。RFC 9580 は、AEAD による新しい暗号化の形式（SEIPD の v2）を加えました。

<Callout type="warn" title="よくある誤解: 暗号化してあれば、中身は書き換えられない">
  暗号化が約束するのは機密性だけで、完全性は別の性質です（第 102 回）。
  CBC や CFB だけの暗号文は、鍵を知らなくても狙った位置を書き換えられ、復号は成功します。
  AEAD にしても、**タグを確かめる前の平文を画面やファイルに出せば、同じ穴が開きます**。
  EFAIL の教訓は、方式を AEAD に替えることと、**確かめに失敗したら 1 バイトも使わない**ことの両方が要る、という点でした。
</Callout>

## OpenPGP: 鍵をどう配るか

OpenPGP の公開鍵には、認証局の署名の代わりに、**利用者 ID（名前とメールアドレス）と、それを鍵自身が署名した自己署名**が入っています。形式は 2024 年の [RFC 9580](https://www.rfc-editor.org/rfc/rfc9580.html) で改訂され、RFC 4880 は廃止されました。

S/MIME では認証局が「この鍵はこのアドレスのもの」と保証しましたが、OpenPGP では**その保証を誰に頼るか**を利用者が選びます。そのため、鍵の配り方がいくつもあります。

| 配り方 | 仕組み | 何を信頼の根にするか | 弱いところ |
| --- | --- | --- | --- |
| 信頼の網 | 会って確かめた人が、相手の鍵に署名する。署名をたどって見知らぬ人の鍵を信じる | 知り合いの判断 | 使い方が難しく、広がらなかった |
| 鍵サーバ | 誰でも鍵を登録・検索できるサーバ | なし（登録は誰でもできた） | 他人の名前で鍵を登録できる。第三者の署名を大量に付けて鍵を使えなくする嫌がらせも起きた |
| 確認つきの鍵サーバ | 登録したアドレスに確認のメールを送り、応答があったものだけ公開する（[keys.openpgp.org](https://keys.openpgp.org/about/faq)） | そのアドレスを受け取れること | Mailbox-validated の S/MIME と同じ強さ |
| WKD | ドメインの Web サーバが、そのドメインの利用者の鍵を置く | そのドメインの HTTPS（第 109〜113 回） | ドメインの運営者が対応している必要がある |
| Autocrypt | 送るメールのヘッダに自分の公開鍵を載せ、受け取った側が覚える | 最初の 1 通（TOFU） | 能動的な攻撃者には弱い |

keys.openpgp.org は、**第三者の署名を既定では配らない**方針を取っています。その理由として FAQ は、第三者の署名は誰の鍵にも任意のデータを付けられる仕組みで、スパムの温床になることを挙げています。信頼の網の土台だった第三者の署名が、公開の鍵サーバでは攻撃の道具になったわけです。

**Autocrypt** は、鍵を配る問題を「最初のメールで一緒に送る」ことで片付けようとする取り組みです。仕様は自らの守備範囲を「**受動的なデータ収集の攻撃だけを防ぐ**」と明記しています（[Autocrypt Level 1](https://docs.autocrypt.org/level1.html)）。経路の途中で鍵を差し替える攻撃者には効かない、と最初から言っているわけで、第 144 回の STARTTLS と同じく、**何もしないよりは良い日和見の暗号化**という位置づけです。

## 手元で確かめる: WKD から鍵を引く

手元に gpg は入っていなかったので、OpenPGP の署名や暗号化は試さず、**鍵の配り方**だけを確かめます。WKD の仕様（[draft-koch-openpgp-webkey-service](https://datatracker.ietf.org/doc/draft-koch-openpgp-webkey-service/)。執筆時点で RFC ではなく個人の Internet-Draft）は、メールアドレスのローカル部を小文字にして SHA-1 に掛け、z-base-32 という 32 文字の符号で表したものを URL にします。

```python
ZB32 = "ybndrfg8ejkmcpqxot1uwisza345h769"
def zbase32(b):
    bits = "".join(f"{x:08b}" for x in b)
    return "".join(ZB32[int(bits[i:i+5], 2)] for i in range(0, len(bits), 5))
h = zbase32(hashlib.sha1(local.lower().encode()).digest())
```

URL には、`openpgpkey.` というサブドメインを使う方式と、ドメインそのものに置く方式の 2 つがあります。仕様はこのハッシュについて、安全のためではなく、ローカル部を固定長の文字列に写すためだけのものだと書いています。

kernel.org は開発者の鍵を WKD で公開しています。手元で計算した URL の 2 つのうち、`openpgpkey.kernel.org` は名前が引けず、ドメインそのものに置く方式で 1621 バイトの鍵が返ってきました。

```
$ python3 wkd.py torvalds@kernel.org
advanced: https://openpgpkey.kernel.org/.well-known/openpgpkey/kernel.org/hu/pf113mfnx1f3eb1yiwhsipa91xfc7o4x?l=torvalds
direct:   https://kernel.org/.well-known/openpgpkey/hu/pf113mfnx1f3eb1yiwhsipa91xfc7o4x?l=torvalds
$ curl -sS -o torv.pgp -w '%{http_code} %{size_download}\n' "<direct の URL>"
200 1621
```

返ってきたバイト列を、RFC 9580 のパケットの見出し（先頭の 1 バイトで種類、続く数バイトで長さ）だけを読む 30 行ほどの Python で並べました。

```
Public-Key       269 bytes  v4 created=2011-09-20 algo=1
User ID           36 bytes  Linus Torvalds <torvalds@kernel.org>
Signature        334 bytes  v4 type=0x13 pubalgo=1 hash=8
User ID           46 bytes  Linus Torvalds <torvalds@linux-foundation.org>
Signature        338 bytes  v4 type=0x13 pubalgo=1 hash=10
Public-Subkey    269 bytes  v4 created=2011-09-20 algo=1
Signature        310 bytes  v4 type=0x18 pubalgo=1 hash=10
```

主鍵（algo=1 は RSA）の後に、利用者 ID と、それを主鍵が署名した自己署名（type 0x13）が組になって並び、最後に暗号化などに使う副鍵と、それを主鍵に結びつける署名（type 0x18）が続きます。X.509 では認証局が 1 つの署名で「鍵と名前」を結びましたが、OpenPGP では**鍵の持ち主自身が、名前ごとに結びつきを宣言している**のが見て取れます。WKD で取ってきた鍵を信じてよい根拠は、この自己署名ではなく、**kernel.org の HTTPS から取ってきたこと**です。

## ヘッダは守られない

S/MIME でも OpenPGP でも、暗号化されるのは本文の MIME 部分です。さきほど暗号化したメッセージでも、先頭の `To:`、`From:`、`Subject:` は平文のままでした。

宛先と差出人を隠せないのは、仕組み上しかたがありません。第 139 回のエンベロープ（`MAIL FROM` と `RCPT TO`）がなければ、中継するサーバはどこへ運べばよいか分からないからです。しかし件名は運ぶのに必要ありません。それでも、多くの MUA は件名を平文で送ってきました。「**本文は暗号化したが、件名に要件を全部書いてしまった**」というのは、よくある失敗です。

誰が、誰と、いつ、どのくらいの頻度でやり取りしたかという**メタデータ**も、中継するサーバとメールボックスの事業者からは見えます。中身を読めなくても、このメタデータだけで分かることは多くあります。

この穴を埋めるため、2025 年に [RFC 9788](https://www.rfc-editor.org/rfc/rfc9788.html)（Header Protection for Cryptographically Protected Email）が出ました。ヘッダの写しを暗号化・署名の内側に入れ、外側の件名を `[...]` のような無意味な値に置き換える方式です。対応していない MUA でも読めるよう、本文の先頭にヘッダを表示用に書き込む工夫も含まれています。ただし、**外側に残る宛先と差出人は、この仕組みでも隠せません**。

<Callout type="warn" title="よくある誤解: エンドツーエンドで暗号化すれば、何も漏れない">
  守られるのは本文だけです。宛先、差出人、日時、大きさは中継するサーバから見え、件名も多くの MUA では平文です。
  「誰と連絡を取っているか」自体が秘密なら、メールの暗号化では守れません。
</Callout>

## DKIM の署名と、人の署名

第 146 回の DKIM と、この回の署名を並べると、違いがはっきりします。

| | DKIM | S/MIME・OpenPGP の署名 |
| --- | --- | --- |
| 鍵の持ち主 | 送信ドメインのサーバ | 個人 |
| 公開鍵の置き場所 | DNS の `_domainkey` | 証明書、鍵サーバ、WKD など |
| 範囲 | `h=` に挙げたヘッダと本文 | 本文の MIME 部分（ヘッダは RFC 9788 まで範囲外） |
| 利用者から見えるか | 見えない。受信サーバが判定し、DMARC に使う | MUA が署名者を表示する |
| 言えること | このドメインが責任を持って送った | この人がこの本文を書いた |

両者は置き換え合うものではありません。DKIM は、ドメインの信用を受信サーバに伝えて迷惑メールの判定に使うための仕組みで、人の署名は、その人が書いたことを受け取った人に伝えるための仕組みです。1 通のメールに両方が付いていることは珍しくありません。

## 使い続けると困ること

仕組みが正しく動いても、エンドツーエンド暗号化はメールの他の部品とぶつかります。

| ぶつかる相手 | 何が起きるか |
| --- | --- |
| 迷惑メールとウイルスの判定 | 受信サーバが本文と添付を検査できない。暗号化したメールはフィルタを素通りする |
| 検索 | サーバ側の全文検索が使えない。端末で復号してから探すしかない |
| 複数の端末、Web メール | 秘密鍵を全部の端末に持たせる必要がある。ブラウザで読むなら、鍵をどこに置くかが第 127 回の置き場所の問題と同じになる |
| 保存と監査 | 組織が法令のためにメールを保存・検査する義務と衝突する。鍵の寄託が必要になる |
| 鍵の更新 | 古い鍵は、過去のメールを読むために捨てられない |
| 転送、メーリングリスト | 暗号化したメールは、鍵を持たない人に転送しても読めない |

## 代わりに何が使われているか

実務で「暗号化メール」と呼ばれているものの多くは、エンドツーエンドではありません。

**ポータル型**では、本文を送らず、閲覧用の Web ページの URL だけをメールで送ります。受け取った人はそのページにログインして読みます。中身は事業者のサーバにあり、事業者は読めますが、取り消しや閲覧の記録ができます。**ファイル共有の URL を送る**方式も同じ考え方です。

日本で長く使われてきたのが、**パスワード付きの ZIP を添付し、パスワードを別のメールで送る**慣習です。頭文字から PPAP と呼ばれます。これは、この回の基準で見ると何も守っていません。

- パスワードは**同じ経路で、多くの場合は数分後に自動で**送られる。1 通目を読める立場の人は 2 通目も読める
- 誤送信の対策としても、宛先を間違えればパスワードも同じ相手に届く
- 暗号化された添付は、受信サーバのウイルス検査を通り抜ける

最後の点は、攻撃に実際に使われました。JPCERT/CC は 2020 年 9 月、マルウェア Emotet が**パスワード付きの ZIP を添付し、パスワードを本文に書いて**送られている例を報告し、メール配信経路のセキュリティ製品による検知や検疫をすり抜けることが想定されると注意を呼びかけています（[JPCERT/CC](https://www.jpcert.or.jp/newsflash/2020090401.html)）。

同じ 2020 年の 11 月、平井卓也デジタル改革担当大臣（当時）は、内閣府と内閣官房でパスワード付き ZIP の利用を 11 月 26 日から廃止すると発表し、その理由を「セキュリティ対策の観点からも、受け取る側の利便性の観点からも、適切なものではない」と述べています（[内閣府の記者会見要旨、2020 年 11 月 24 日](https://www.cao.go.jp/minister/2009_t_hirai/kaiken/20201124kaiken.html)）。

<Callout type="note" title="別送は、経路が別のときにだけ意味がある">
  秘密を 2 つに分けて送る考え方自体は間違っていません。意味を持つのは、**2 つが本当に別の経路を通るとき**です。
  電話で伝える、事前に決めておく、といった方法なら、メールを読める立場の人がパスワードまで知ることはありません。
  同じメールサーバを通る 2 通目は、別の経路ではありません。
</Callout>

## 何と組み合わさって意味を持つか

エンドツーエンド暗号化も、単独では何も保証しません。

| 部品 | 役目 | 見た回 |
| --- | --- | --- |
| 公開鍵暗号とハイブリッド暗号 | 共通鍵を受け取る人の公開鍵で包む | 第 105 回 |
| AEAD | 本文の書き換えを検出する。確かめる前の平文を使わない | 第 104 回 |
| 署名 | この人が本文を書いたこと | 第 106 回 |
| X.509 と信頼の連鎖 | S/MIME で鍵とアドレスを結びつける | 第 109 回、第 110 回 |
| 証明書の更新と失効 | 利用者ごとの証明書を保ち続ける | 第 111 回 |
| HTTPS | WKD で取ってきた鍵を信じる根拠 | 第 112 回 |
| 鍵の保管 | 暗号化の鍵を何年も失わない | 第 108 回 |
| MUA の実装 | `From:` と署名者を突き合わせる。HTML の表示で平文を漏らさない | この回 |
| 経路の TLS | メタデータとヘッダを、少なくとも経路の上では守る | 第 144 回 |

## まとめ

- 経路の TLS が守るのはサーバとサーバの間だけで、**各サーバのキューとメールボックスでは本文が読める**。そこまで守るには、送る人が暗号化し受け取る人だけが復号する、エンドツーエンド暗号化が要る
- S/MIME（RFC 8551）は X.509 の証明書で鍵とアドレスを結びつけ、OpenPGP（RFC 9580）は鍵の保証を利用者に任せる。どちらも**相手の鍵を先に手に入れる**ことが一番の壁
- 署名が言えるのは「この鍵の持ち主が本文を書いた」ことだけで、`From:` との一致は MUA が確かめる。手元では、`From:` と件名を書き換えても署名の検証は成功した
- 暗号化の秘密鍵をなくすと過去のメールは読めない。送った本人も、自分を宛先に加えなければ読めない
- EFAIL は、CBC の暗号文が鍵なしで書き換えられることと、MUA が平文を HTML としてつなげて表示することを突いた。AEAD にしても、**タグを確かめる前の平文を使えば同じ**
- 宛先、差出人、日時は隠せず、件名も多くの MUA では平文。RFC 9788 が件名などのヘッダを内側に移す方式を定めた
- エンドツーエンド暗号化は、迷惑メールの判定、検索、複数の端末、保存の義務とぶつかり、普及しなかった。代わりにポータル型や共有の URL が使われる。同じ経路でパスワードを送る PPAP は何も守らず、攻撃の隠れみのにもなった

次の第 149 回では、届いたメールを利用者が読みにいく側、IMAP と JMAP を見ます。そこでは、メールクライアントの認証がパスワードから OAuth へ移りつつあることと、メールのアカウントが他のすべてのアカウントを取り戻す鍵になっている構造を扱います。
