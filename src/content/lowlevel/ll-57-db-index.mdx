## 葉に何を置くか

B+tree の形そのもの、つまり 1 ノードを 1 ページにして分岐を増やし、段数を減らす話は、システムデザインの区画の <a href={`${import.meta.env.BASE_URL}reading/db-index/`}>データベースの索引（B-tree と LSM-tree）</a> で扱いました。100 分岐なら 1 億件が 4 段、という話です。

ここで見るのは、その **葉に何を置くか** です。前回見たページの上に B+tree を載せると、葉のページには「キー」と「何か」が並びます。この「何か」には 2 つの選び方があります。

```
 (A) 葉に行そのものを置く           (B) 葉に行の在りかを置く

  [ 10 | 20 | 30 ]                  [ 10 | 20 | 30 ]
     ↓                                 ↓
  ┌──────────────────┐             ┌──────────────┐        テーブル本体
  │ 10: 山田, 34, ... │             │ 10 → (0,1)   │ ──→  (0,1): 山田, 34, ...
  │ 11: 佐藤, 27, ... │             │ 11 → (5,3)   │ ──→  (5,3): 佐藤, 27, ...
  └──────────────────┘             └──────────────┘
```

(A) は、索引とテーブルが一体になっています。(B) は、索引とテーブルが別々にあり、索引は行の住所だけを持っています。

主キーの索引とそれ以外の索引の違い、そして MySQL と PostgreSQL の性質の違いは、ほとんどがこの選択から説明できます。

## InnoDB：テーブルそのものが主キーの B+tree

MySQL の InnoDB は、主キーの索引に (A) を採ります。これを **クラスタ化インデックス** と呼びます。

**テーブルという独立した入れ物はありません。** 主キーの B+tree の葉に、行のすべての列が並んでいます。行は主キーの順に並んで格納され、葉のページどうしは横につながっています。

主キーを定義しなかった場合でも、この構造は変わりません。適当な一意の索引が無ければ、InnoDB は隠れた行番号の列を作り、それでクラスタ化インデックス（`GEN_CLUST_INDEX`）を作ります（[MySQL 8.4 リファレンス](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)）。**InnoDB の行は、必ず何かの B+tree の葉に住んでいる** のです。

主キーでの検索は、B+tree を 1 回たどれば行が手に入ります。主キーの範囲検索は、葉を横にたどるだけなので、ページを順番に読むことになります。

## セカンダリインデックスは、主キーを持つ

主キー以外の列に作る索引を **セカンダリインデックス** と呼びます。InnoDB のセカンダリインデックスは (B) の形ですが、葉に置く「住所」が特徴的です。**物理的な位置ではなく、主キーの値** を置きます。

```
 セカンダリ（email）                   クラスタ化（id）
 ┌──────────────────────┐             ┌──────────────────────┐
 │ a@x → id=42          │ ──────────→ │ 42: a@x, 山田, 34, ... │
 │ b@x → id=7           │   B+tree を  │  7: b@x, 佐藤, 27, ... │
 └──────────────────────┘  もう 1 回    └──────────────────────┘
```

`WHERE email = 'a@x'` は、次の 2 段階になります。

1. email の B+tree をたどり、主キー `42` を得る
2. **主キーの B+tree をもう一度たどり**、行を得る

1 回で済む主キー検索に比べて、たどる段数が倍になります。

なぜ物理的な位置を持たないのか。クラスタ化インデックスでは、行が主キーの順に並んでいるので、**行が挿入されてページが分割されると、行の物理的な位置が変わります**。もしセカンダリインデックスが位置を持っていたら、ページが分割されるたびに、そのページに載っていた行を指すすべてのセカンダリインデックスを書き換えることになります。主キーの値なら、行がどこに動いても変わりません。前回のスロット付きページと同じく、**動くものを直接指さない** ための間接参照です。

その代償として、**すべてのセカンダリインデックスの葉に、主キーのコピーが入ります**。MySQL のリファレンスも、主キーが長いとセカンダリインデックスが大きくなるので、短い主キーが有利だと明記しています。

## PostgreSQL：テーブルはヒープ、索引はすべて対等

PostgreSQL は、すべての索引に (B) を採ります。テーブル本体は **ヒープ** と呼ばれ、行は主キーの順ではなく、空いている場所に置かれます。主キーの索引も、それ以外の索引も、葉には前回見た `ctid`（ページ番号と行ポインタの番号の組）が並びます。

**主キーも、ただの一意な索引の 1 つです。** セカンダリインデックスから引いても、索引を 1 回たどって `ctid` を得たら、そのページを直接読むだけです。InnoDB のような 2 段階はありません。

では PostgreSQL のほうが有利かというと、更新のときに代償が出ます。PostgreSQL は、行を更新すると **古い行をその場で書き換えず、新しい版の行を別に作ります**（理由は第 58 回で見ます）。新しい版は別の場所に置かれるので、`ctid` が変わります。

```sql
SELECT ctid FROM t WHERE id = 1;       -- (0,1)
UPDATE t SET name = 'renamed' WHERE id = 1;
SELECT ctid FROM t WHERE id = 1;       -- (635,155)
```

最初のページに空きが無かったので、新しい版はテーブルの最後のページ（635 番）に置かれました。**行の住所が変わった以上、この行を指すすべての索引に、新しい住所の項目を足す必要があります**。更新したのが `name` 列だけで、索引が `id` にしか無くても、です。

### HOT：同じページに収まれば索引に触らない

この問題を和らげるのが **HOT**（Heap-Only Tuple）です。次の 2 つを満たす更新では、索引を一切書き換えません（[PostgreSQL ドキュメント](https://www.postgresql.org/docs/current/storage-hot.html)）。

- 索引が張られている列を変更していない
- 古い行と **同じページに**、新しい版を置く空きがある

新しい版は同じページ内に置かれ、古い版から新しい版へ鎖がつながります。索引は古い行ポインタを指したままで、たどると鎖を伝って新しい版に行き着きます。ページの外から見た住所が変わらないので、索引を直す必要がないのです。

空きを残すには、テーブルの **fillfactor** を下げます。

```sql
CREATE TABLE h (id int PRIMARY KEY, counter int) WITH (fillfactor = 90);
-- 1000 行入れてから
UPDATE h SET counter = counter + 1 WHERE id = 1;
SELECT ctid FROM h WHERE id = 1;    -- (0,1) → (0,205)。同じ 0 番のページ
SELECT n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables WHERE relname = 'h';
--  n_tup_upd | n_tup_hot_upd
--          1 |             1
```

ページの 10% を空けておいたので、新しい版は同じページに収まり、HOT 更新として数えられています。

| | InnoDB | PostgreSQL |
| --- | --- | --- |
| テーブル本体 | 主キーの B+tree（クラスタ化） | ヒープ（順序なし） |
| セカンダリの葉 | キー + 主キーの値 | キー + `ctid` |
| セカンダリからの検索 | B+tree を 2 回たどる | 1 回たどってページを読む |
| 主キーの範囲検索 | 葉を順に読むだけ | 行はヒープ上に散らばりうる |
| 索引列以外の更新 | セカンダリは触らない | HOT が効かなければ全索引に項目を追加 |

どちらが優れているかではなく、**読みと更新のどちらに手間を寄せたか** の違いです。

## 主キーの選び方とページ分割

B+tree の葉のページが満杯のところにキーを挿入すると、ページを 2 つに分けて半分ずつ移します。これが **ページ分割** です。

キーを挿入する位置は、キーの値で決まります。ここで、主キーの選び方が効いてきます。

**連番のキー**（自動採番など）は、常に最大値より大きいので、**必ず右端の葉に追記されます**。右端のページが埋まったら新しいページを右に足すだけで、既存のページは分割されません。

**ランダムなキー**（UUIDv4 など）は、葉のどこに入るか分かりません。あちこちのページで分割が起き、**分割されたページは半分しか埋まっていない** 状態から再出発します。

InnoDB のリファレンスは、この差を具体的に書いています。順番に挿入すると葉のページは約 15/16 まで埋まり、ランダムな順で挿入すると 1/2 から 15/16 の間になる（[MySQL 8.4 リファレンス](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)）。

手元の PostgreSQL 18 で、100 万件の UUID を主キーにして比べました。

```sql
CREATE TABLE u4 (id uuid PRIMARY KEY);   -- gen_random_uuid()（UUIDv4、完全にランダム）
CREATE TABLE u7 (id uuid PRIMARY KEY);   -- uuidv7()（時刻順）
-- それぞれ 100 万件挿入して、pgstattuple 拡張で索引を調べる
--  k  | size  | avg_leaf_density
--  v4 | 38 MB |            71.13
--  v7 | 30 MB |            89.98
```

同じ件数、同じ 16 バイトのキーで、**ランダムなほうが 3 割近く大きく、葉は 7 割しか埋まっていません**。

大きさ以上に効くのが、前回見たバッファプールです。連番なら、挿入のたびに触るのは右端の数ページだけで、それはずっとメモリに載っています。ランダムなら、**索引全体がまんべんなく触られる** ので、索引がバッファプールに収まらなくなった瞬間から、挿入のたびにディスクを読むことになります。

<Callout type="tip" title="UUIDv7：一意なまま、時刻順に並ぶ">
  UUIDv7 は 2024 年 5 月の RFC 9562 で標準化された形式で、先頭の 48 ビットにミリ秒単位の時刻を置き、残りを乱数で埋めます
  （[RFC 9562](https://www.rfc-editor.org/rfc/rfc9562)）。
  **生成した順にほぼ昇順に並ぶ** ので、B+tree から見ると連番に近い挙動になります。
  PostgreSQL 18 では `uuidv7()` 関数が標準で使えます（[PostgreSQL 18 リリースノート](https://www.postgresql.org/docs/release/18.0/)）。

  InnoDB ではこの差がさらに大きく出ます。クラスタ化インデックスなので、**ランダムな主キーはテーブル本体そのものを散らかし**、
  しかも 16 バイトの主キーがすべてのセカンダリインデックスにコピーされるからです。
</Callout>

<Callout type="warn" title="連番にも弱点がある">
  連番は 1 台のデータベースでは理想的ですが、**全員が右端の同じページに書き込む** ことになります。
  1 台なら、そのページがメモリに載り続けるので利点です。
  しかし、データをキーの範囲で複数のマシンに分けるデータベースでは、**最新のキーを持つ 1 台に書き込みが集中** します。
  第 59 回で、この問題に戻ってきます。
</Callout>

## 索引だけで答える

索引の葉に、クエリが必要とする列がすべて入っていれば、テーブル本体を読む必要がありません。このような索引を **カバリングインデックス** と呼びます。

InnoDB では、セカンダリインデックスの葉に主キーが必ず入っているので、「索引の列と主キーだけを返すクエリ」は、2 段階目を省略できます。

PostgreSQL では、検索には使わないが葉に載せておきたい列を `INCLUDE` で指定できます。

```sql
CREATE INDEX t_age ON t (age) INCLUDE (name);
VACUUM t;
EXPLAIN (ANALYZE, BUFFERS) SELECT age, name FROM t WHERE age = 30;
--  Index Only Scan using t_age on t (actual rows=1250.00 loops=1)
--    Index Cond: (age = 30)
--    Heap Fetches: 2
```

`Index Only Scan` は、索引だけで答えたという意味です。ただし `Heap Fetches: 2` と、ヒープを 2 回読んでいます。

これは PostgreSQL の索引の葉が、**その行がいまのトランザクションから見えるかどうか** の情報を持っていないためです。行の新旧の版を見分ける情報はヒープの行にしかありません。そこで PostgreSQL は、ページごとに「このページの行はすべて誰からでも見える」という 1 ビットを **可視性マップ** に持ち、そのビットが立っているページは読まずに済ませます（[PostgreSQL ドキュメント](https://www.postgresql.org/docs/current/indexes-index-only-scans.html)）。ビットを立てるのは `VACUUM` です。更新が多いテーブルでは、ビットが立っていないページが増え、index-only scan の利点が消えていきます。

## 複合インデックスは左から

複数の列をまとめた索引（`(last_name, first_name)` など）では、葉は **1 つ目の列で並べ、同じ値の中を 2 つ目の列で並べた** 順になります。電話帳が名字で並び、同じ名字の中を名前で並べているのと同じです。

| 条件 | 索引の使い方 |
| --- | --- |
| `last_name = '山田'` | 使える。先頭の列で範囲が決まる |
| `last_name = '山田' AND first_name = '花子'` | 使える。1 点に絞れる |
| `first_name = '花子'` だけ | 基本的に使えない。「花子」は各名字の中に散らばっている |

電話帳で名前だけから人を探せないのと同じ理由です。これが「複合インデックスは左端から一致させる」という経験則の正体です。

ただし、先頭の列の種類が少なければ、**先頭の値ごとに小さな範囲検索を繰り返す** という手が使えます。名字が 5 種類しか無ければ、「山田の花子」「佐藤の花子」…と 5 回探せば済むからです。これを **skip scan** と呼び、MySQL は 8.0.13 から（[MySQL 8.4 リファレンス](https://dev.mysql.com/doc/refman/8.4/en/range-optimization.html)）、PostgreSQL は 18 から対応しています（[PostgreSQL 18 リリースノート](https://www.postgresql.org/docs/release/18.0/)）。

なお、先ほどの `INCLUDE` で載せた列は、葉に置かれているだけで並び順には関わりません。

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT age, name FROM t WHERE name = 'user30';
--  Seq Scan on t (actual rows=1.00 loops=1)
--    Filter: (name = 'user30'::text)
--    Rows Removed by Filter: 99999
--    Buffers: shared hit=636
```

`name` は索引に載っていても検索には使えず、テーブルの全 636 ページを読んでいます。

## まとめ

- 同じ B+tree でも、葉に行そのものを置くか、行の在りかを置くかで性質が変わる
- InnoDB はテーブル本体が主キーの B+tree（クラスタ化インデックス）。セカンダリは主キーの値を持ち、2 段階でたどる
- 主キーを住所にするのは、ページ分割で行が動いても索引を直さずに済むため。代わりに主キーが全セカンダリにコピーされる
- PostgreSQL はテーブルがヒープで、全索引が `ctid` を持つ。更新で行が動くと全索引を直すが、同じページに収まれば HOT で避けられる
- ランダムな主キーはページ分割を招き、索引を大きくし、バッファプールに収まりにくくする。UUIDv7 は時刻順に並ぶ
- 必要な列が葉に揃えば索引だけで答えられる。PostgreSQL では可視性マップと VACUUM が前提になる
- 複合インデックスは先頭の列から並ぶ。先頭の種類が少なければ skip scan が使える
