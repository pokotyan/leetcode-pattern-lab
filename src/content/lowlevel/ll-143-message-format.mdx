## DATA の後ろに何を書いているのか

第 141 回では、SMTP の会話を手で打ち、`DATA` と答えてから `.` だけの行までの間に「メッセージ」を流し込みました。SMTP はその中身をほとんど見ません。1 行が長すぎないこと、`.` で始まる行をドット詰めすることくらいしか気にせず、バイト列として次のサーバへ渡します。

では、その中身はどんな形をしているのでしょうか。件名の日本語、HTML の本文、PDF の添付は、どういうバイト列になって運ばれているのでしょうか。

答えを先に言うと、メッセージの形式は **「7 ビットの ASCII で、1 行が短いテキスト」という古い器を壊さずに、中身だけを継ぎ足してきた結果**です。日本語も画像も、いったん ASCII の文字列に変換して器に収めています。この回では、その変換の規則を上から順に見て、最後に Python で組み立てたメッセージを手で戻します。

## ヘッダと本文: 空行 1 つで分かれる

メッセージの形式を決めているのは [RFC 5322](https://www.rfc-editor.org/rfc/rfc5322.html)（2008 年、RFC 2822 を置き換え、[RFC 6854](https://www.rfc-editor.org/info/rfc6854) で一部更新）です。形は単純で、**ヘッダの並び、空行 1 つ、本文**です。

```
From: Taro Yamada <taro@example.com>        ← ヘッダ（名前: 値）
To: hanako@example.net
Subject: Meeting next week
Date: Mon, 21 Sep 2026 23:13:20 +0900
Message-ID: <20260928.1@example.com>
                                            ← 空行（CRLF だけの行）
Hanako,                                     ← 本文
See you next week.
```

行の区切りは CRLF です。1 行の長さには 2 つの上限があり、**998 文字を超えてはならず（MUST）、78 文字以下にすべき（SHOULD）** と定められています（[RFC 5322 2.1.1](https://www.rfc-editor.org/rfc/rfc5322.html#section-2.1.1)）。998 は、SMTP が 1 行を CRLF 込みで 1000 オクテットまでと決めていること（[RFC 5321 4.5.3.1.6](https://www.rfc-editor.org/rfc/rfc5321.html#section-4.5.3.1.6)）から CRLF の 2 つを引いた数です。78 は、80 桁の端末で読めるようにするための目安です。

長いヘッダは、途中に CRLF と空白を入れて**折り返せます**。次の行が空白で始まっていれば、前の行の続きとして読みます。

```
Subject: This is a very long subject line
 that continues here
```

## 主なヘッダの役割

RFC 5322 は、各ヘッダが 1 通のメッセージに何回現れてよいかを表にしています（[3.6](https://www.rfc-editor.org/rfc/rfc5322.html#section-3.6)）。**必須なのは `Date` と `From` の 2 つだけ**です。

| ヘッダ | 回数 | 意味 |
| --- | --- | --- |
| `Date` | 必ず 1 | 書き手がメッセージを送り出した時刻 |
| `From` | 必ず 1 | 書き手（複数人も可） |
| `Sender` | 0〜1 | 実際に送り出した人。`From` が複数なら必須 |
| `Reply-To` | 0〜1 | 返信の宛先。無ければ `From` へ返す |
| `To` / `Cc` / `Bcc` | 各 0〜1 | 宛先の**表示**。1 つのヘッダに複数のアドレスを並べる |
| `Message-ID` | 0〜1（SHOULD） | このメッセージを世界で一意に指す識別子 |
| `In-Reply-To` / `References` | 0〜1（SHOULD） | 何への返信か。スレッドを組むのに使う |
| `Subject` | 0〜1 | 件名 |

`From`、`Sender`、`Reply-To` の 3 つは紛らわしいので区別しておきます。秘書が上司の名前でメールを出すなら、`From` は上司、`Sender` は秘書です（RFC 5322 3.6.2 の例と同じ考え方）。メーリングリストが「返信はリストへ」としたいときに使うのが `Reply-To` です。

大事なのは、これらが**すべて書き手が自由に書ける文字列**だということです。第 139 回で見たとおり、配送先を決めるのはエンベロープの `RCPT TO` で、`To:` ではありません。`Bcc:` の宛先が他の受信者に見えないのも、そもそも `Bcc:` の行を送る前に消すか書き換えるからで（RFC 5322 3.6.3 がいくつかの扱い方を挙げています）、配送は `RCPT TO` だけで成り立ちます。

<Callout type="warn" title="「From: が正しく表示されているから本人」ではない">
  `From:` は、SMTP の `MAIL FROM` とも、接続元の IP アドレスとも無関係に、書き手が好きに書ける行です。
  特に**表示名**（`<...>` の前の部分）は何を書いてもよく、表示名に別人のメールアドレスそのものを書くこともできます。
  多くのメールクライアントは表示名だけを大きく見せるので、利用者が見ている差出人は、形式の上では何の保証もありません。
  `From:` のドメインを初めて検証に結びつけるのは第 147 回の DMARC で、それでも表示名は守られません。
</Callout>

### Date の書き方

`Date` は `Mon, 21 Sep 2026 23:13:20 +0900` のように、曜日、日、月、年、時刻、UTC からのずれを並べます（[RFC 5322 3.3](https://www.rfc-editor.org/rfc/rfc5322.html#section-3.3)）。ずれを `-0000` と書くと「UTC での時刻だが、書き手の地域の時差は分からない」という意味になり、`+0000` とは区別されます。後の「手元で確かめる」で Python が出力する `-0000` はこれです。

`Date` は**書き手の時計**で、受け取った時刻ではありません。送信側の時計が狂っていれば未来の日付にもなります（時計の話は第 157 回）。受け取った時刻は、後で見る `Received:` のほうに残ります。

## Message-ID とスレッド

`Message-ID` は `<20260928.1@example.com>` のように、`@` を挟んだ山括弧の文字列です。一意性を保証するのは**生成した側の責任**で、右側に自分のドメイン名、左側に時刻や乱数を入れるのが普通です（[RFC 5322 3.6.4](https://www.rfc-editor.org/rfc/rfc5322.html#section-3.6.4)）。

返信を作るときは、この識別子を使って親子関係を書きます。規則は次のとおりです。

- `In-Reply-To:` には、親の `Message-ID` を書く
- `References:` には、**親の `References:` の中身の後ろに、親の `Message-ID` を足したもの**を書く

```
A  Message-ID: <a@example.com>
B  Message-ID: <b@example.net>   In-Reply-To: <a@example.com>
                                 References:  <a@example.com>
C  Message-ID: <c@example.com>   In-Reply-To: <b@example.net>
                                 References:  <a@example.com> <b@example.net>
```

`References:` は根から親までの道のりを全部持つので、途中の 1 通が手元に無くても木を組み直せます。メールクライアントのスレッド表示は、基本的にこの 2 つのヘッダを頼りにしています。件名の `Re:` が揃っているかどうかで推測するクライアントもありますが、それは補助です。**`Message-ID` を付けずに送るアプリからの通知は、返信されてもスレッドにならない**のはこのためです。

## MIME: ASCII の器に何でも入れる

RFC 5322 の本文は、ASCII のテキストしか想定していません。日本語も、画像も、複数の部品もありません。これを、**器の形はそのままに、ヘッダを数本足すだけ**で拡張したのが MIME です。1996 年の 5 つの RFC に分かれており、本文のヘッダを [RFC 2045](https://www.rfc-editor.org/rfc/rfc2045.html)、メディア型と multipart を [RFC 2046](https://www.rfc-editor.org/rfc/rfc2046.html)、**ヘッダの中の** ASCII 以外の文字を [RFC 2047](https://www.rfc-editor.org/rfc/rfc2047.html) が決め、残る RFC 2048 と [RFC 2049](https://www.rfc-editor.org/rfc/rfc2049.html) が登録の手続きと適合の条件を扱います。

MIME を使うメッセージは `MIME-Version: 1.0` を書き、`Content-Type` で中身の種類を、`Content-Transfer-Encoding` で ASCII への変換方法を示します。

### multipart: 1 通に複数の部品を入れる

`Content-Type: multipart/...` の本文は、**境界文字列**で区切られた部品の並びです（[RFC 2046 5.1](https://www.rfc-editor.org/rfc/rfc2046.html#section-5.1)）。

```
Content-Type: multipart/mixed; boundary="XYZ"

ここ（最初の境界より前）はプリアンブル。読み飛ばされる
--XYZ
Content-Type: text/plain; charset="utf-8"

本文
--XYZ
Content-Type: application/pdf
Content-Disposition: attachment; filename="report.pdf"
Content-Transfer-Encoding: base64

JVBERi0xLjcK...
--XYZ--
ここ（最後の境界より後）はエピローグ。これも読み飛ばされる
```

- 区切りの行は `--` と境界文字列。**最後だけ後ろにも `--` を付ける**
- 境界文字列は 1〜70 文字で、**部品の中身に現れてはならない**。だからライブラリは長い乱数を使う
- 各部品は、それ自体がヘッダと空行と本文を持つ小さなメッセージで、**入れ子にできる**

よく使う multipart の種類は 3 つです。

| 型 | 意味 | 典型 |
| --- | --- | --- |
| `multipart/mixed` | 独立した部品を順に並べる | 本文と添付 |
| `multipart/alternative` | **同じ内容の別表現**。受け手が 1 つを選ぶ | テキスト版と HTML 版 |
| `multipart/related` | 組み合わせて 1 つになる部品（[RFC 2387](https://www.rfc-editor.org/info/rfc2387)） | HTML と、そこから `cid:` で参照する画像 |

`multipart/alternative` には順番の決まりがあり、**元の内容に忠実でないものから順に並べ、受け手は表示できる最後のものを選ぶ**（RFC 2046 5.1.4）ことになっています。テキスト版を先、HTML 版を後に置くのはこのためです。

HTML メールに画像を埋め込み、さらにファイルを添付すると、入れ子は 3 段になります。

```
multipart/mixed
├── multipart/alternative
│   ├── text/plain                    ← HTML を表示できない受け手向け
│   └── multipart/related
│       ├── text/html                 ← <img src="cid:logo@example.com">
│       └── image/png                 ← Content-ID: <logo@example.com>
└── application/pdf                   ← 添付
```

添付ファイルの名前は `Content-Disposition` ヘッダ（[RFC 2183](https://www.rfc-editor.org/info/rfc2183)、1997 年）の `filename` で渡します。`attachment` なら添付として、`inline` なら本文の中に表示されることを期待します。

## Content-Transfer-Encoding: バイト列を ASCII にする

中身が画像のように任意のバイト列だったり、UTF-8 の日本語だったりすると、7 ビットの器には入りません。そこで**運ぶ前に ASCII の文字列へ変換し、その方法を `Content-Transfer-Encoding` に書きます**（[RFC 2045 6](https://www.rfc-editor.org/rfc/rfc2045.html#section-6)）。

| 値 | 変換 | 中身の条件 |
| --- | --- | --- |
| `7bit` | しない | ASCII だけで、1 行 998 オクテット以下 |
| `8bit` | しない | 8 ビット目が立ったバイトもあるが、行の形は保つ |
| `binary` | しない | 何でもよい（SMTP ではほぼ通らない） |
| `quoted-printable` | 一部だけ `=XX` にする | ほぼ ASCII のテキスト向け |
| `base64` | 3 バイトを 4 文字にする | 任意のバイト列向け |

上の 3 つは「変換していない」という宣言で、**中身がその条件を満たしていると主張しているだけ**です（RFC 2045 6.2）。`8bit` を SMTP で運ぶには、途中のサーバがすべて `8BITMIME` 拡張（[RFC 6152](https://www.rfc-editor.org/info/rfc6152)、第 141 回の EHLO の一覧に出てきたもの）を話す必要があります。

**quoted-printable** は、印字できる ASCII はそのまま残し、それ以外のバイトを `=` と 16 進数 2 桁で表します。`=` 自身も `=3D` になり、1 行は 76 文字までで、超えるときは行末に `=` を置いて折り返します（RFC 2045 6.7）。英文にたまに記号が混じる程度なら人間にもほぼ読めますが、日本語には向きません。

```
Price: 100 yen = 1 coffee
→ Price: 100 yen =3D 1 coffee

来週の打ち合わせ（UTF-8 で 24 バイト）
→ =E6=9D=A5=E9=80=B1=E3=81=AE=E6=89=93=E3=81=A1=E5=90=88=E3=82=8F=E3=81=9B（72 文字）
```

**base64** は、入力の 24 ビット（3 バイト）を 6 ビットずつ 4 つに分け、64 種類の文字の 1 つずつに写します（RFC 2045 6.8）。第 127 回の Base64URL の元になった符号化です。出力は 76 文字ごとに改行します。

<Callout type="note" title="添付は約 4/3 倍、改行込みでもう少し大きくなる">
  3 バイトが 4 文字になるので、base64 にした添付は元の **4/3 倍**になります。さらに 76 文字ごとに CRLF の 2 バイトが入るので、実際には約 1.37 倍です。
  SMTP の `SIZE` 拡張（第 141 回）で受け手が示す上限は、変換後のメッセージ全体のオクテット数です（[RFC 1870](https://www.rfc-editor.org/rfc/rfc1870.html)）。上限が 10 MB なら、元のファイルは 7 MB 程度までしか添付できません。
</Callout>

## ヘッダの日本語: encoded-word

本文は `Content-Type` の `charset` と `Content-Transfer-Encoding` で何とでもなりました。しかし**ヘッダには、この 2 つを書く場所がありません**。件名や差出人の表示名に日本語を入れるために作られたのが **encoded-word** です（[RFC 2047](https://www.rfc-editor.org/rfc/rfc2047.html)）。

```
=?charset?encoding?encoded-text?=

Subject: =?utf-8?b?5p2l6YCx44Gu5omT44Gh5ZCI44KP44Gb44Gr44Gk44GE44Gm?=
           ↑文字コード  ↑B = base64、Q なら quoted-printable に似た形
```

`=?` と `?=` で囲まれた部分を、受け手が文字コードと符号化の指定に従って戻します。規則のうち、実務で効くものは次の 3 つです。

- **1 つの encoded-word は 75 文字まで**。長い件名は複数の encoded-word に分け、折り返して並べる。隣り合う encoded-word の間の空白は、戻すときに捨てる
- **アドレスの部分（`taro@example.com`）には使えない**。使えるのは表示名や件名など、人が読むための部分だけ
- **引用符で囲んだ文字列の中では使えない**。`"=?utf-8?b?...?="` と引用符で囲むと、仕様上はただの文字列になる

2 つ目と 3 つ目は MUST NOT の規則ですが、受け取る側の実装は寛容に作られがちです。たとえば手元の Python 3.14.0 の email パッケージは、`From: "=?utf-8?b?5bGx55Sw?=" <a@example.com>` の表示名を「山田」と戻しました。**同じメッセージでも、クライアントによって表示が変わりうる**のが、ヘッダの日本語の厄介なところです。

### ファイル名はもう 1 つ別の規則

添付の `filename` はヘッダの中の**パラメータ**なので、RFC 2047 の encoded-word は使えないことになっています。パラメータのためには別に [RFC 2231](https://www.rfc-editor.org/rfc/rfc2231.html) があり、`*` を付けたパラメータ名で文字コードを指定し、値を `%XX` で書きます。

```
Content-Disposition: attachment; filename*=utf-8''%E8%B3%87%E6%96%99.bin
```

ところが、RFC 2231 を理解しないメールクライアントが長く残ったため、`filename="=?utf-8?b?...?="` という**仕様外の書き方**も広く使われてきました。受け取る側もそれに合わせており、手元の Python 3.14.0 はこの書き方のファイル名も「資料.bin」と戻しました。添付ファイルの名前が化けるときは、この 2 つの書き方の食い違いをまず疑います。

## ISO-2022-JP と文字化け

日本語のメールは、長い間 **ISO-2022-JP** で書くのが作法でした。1993 年の [RFC 1468](https://www.rfc-editor.org/info/rfc1468) が、JUNET で使われていた符号化をこの名前で定めたものです。

ISO-2022-JP は、第 5 回で見た文字コードの中でも独特で、**エスケープシーケンスで文字集合を切り替えながら、全体を 7 ビットに収めます**。

```
"来週" を ISO-2022-JP で
1B 24 42 | 4D 68 3D 35 | 1B 28 42
ESC $ B  | 来    週    | ESC ( B
（ここから JIS X 0208） （ASCII に戻す）
```

どのバイトも 0x80 未満なので、**8 ビットを通さないサーバも無傷で通れます**。8BITMIME が広まる前の経路でも壊れない、というのが、日本で長くこの符号化が使われてきた理由です。件名は `=?iso-2022-jp?b?GyRCTWg9NSROQkckQTlnJG8kOxsoQg==?=` のように、エスケープシーケンスごと base64 にします。

その代わり、文字化けの原因もいくつか抱えています。

| 症状 | 原因 |
| --- | --- |
| `$BMh=5(B` のような記号の列 | ESC（0x1B）が途中で落ちた。切り替えが効かず、2 バイト文字が ASCII として見える |
| 丸数字（①）や一部の旧字体が `?` になる | JIS X 0208 に無い文字。Shift_JIS の Windows 版（CP932）にはあるので、送り手の画面では書けてしまう |
| 波ダッシュ（〜）が別の文字になる | 同じ JIS のコードを、Unicode のどの文字に対応させるかが変換表ごとに違う |
| `譚･騾ｱ` のような漢字の列 | UTF-8 のバイト列を Shift_JIS として読んだ。`charset` の書き忘れや書き間違い |

3 つ目は具体的に見ておく価値があります。JIS X 0208 の 0x2141（Shift_JIS では 0x8160）を、Python の `shift_jis` は U+301C（WAVE DASH）に、`cp932` は U+FF5E（FULLWIDTH TILDE）に対応させます。**同じバイト列が、読む側の変換表によって別の Unicode の文字になる**ので、往復させると元に戻らないことがあります。

現在は、主要なメールクライアントの多くが UTF-8 で送るようになり、ISO-2022-JP を選ぶ理由は減っています。ただし、古い業務システムからの通知や、それを受け取る古いクライアントは今も残っています。

## SMTPUTF8: ヘッダにも UTF-8 をそのまま書く

encoded-word は表示名と件名しか救えません。**メールアドレスそのもの**に日本語を使いたいとき（`太郎@例え.jp`）は、器のほうを変えるしかありません。それが次の 2 つです。

- [RFC 6531](https://www.rfc-editor.org/info/rfc6531)（2012 年）: SMTP の `SMTPUTF8` 拡張。EHLO で受け手が対応を表明し、送り手は `MAIL FROM` に `SMTPUTF8` を付ける
- [RFC 6532](https://www.rfc-editor.org/info/rfc6532)（2012 年）: ヘッダに UTF-8 を**そのまま**書いてよい。1 行の上限は 998「文字」ではなく 998「オクテット」と読み替える

つまり国際化メールアドレスは、**経路上のすべての SMTP サーバと、宛先のメールボックスまでが対応して初めて**届きます。途中に 1 台でも対応しないサーバがあれば、送り手はエラーを返されます。encoded-word で逃げることはできません。

<Callout type="warn" title="「ヘッダは UTF-8 で書けばよい」は、SMTPUTF8 が通るときだけ">
  RFC 6532 がある今でも、SMTPUTF8 を表明しない相手に UTF-8 の生のヘッダを送ってよいわけではありません。
  普通のメッセージでは、ヘッダは ASCII で、日本語は encoded-word にするのが今も基本です。
  ライブラリもこの 2 つを使い分けます。後で見るように、Python の email パッケージも出力の方針（policy）を変えるだけで、同じ件名を encoded-word にしたり生の UTF-8 で書いたりします。
</Callout>

## Received: 下から上へ読む

最後に、メッセージの先頭に積み重なっていく `Received:` を読みます。どの経路を通ったかは第 142 回で見たので、ここでは**形式と読み方**だけを扱います。

SMTP サーバはメッセージを受け取るたびに、**先頭に** `Received:` を 1 行足し、既にある `Received:` には手を触れません（[RFC 5321 4.4](https://www.rfc-editor.org/rfc/rfc5321.html#section-4.4)、[RFC 5322 3.6.7](https://www.rfc-editor.org/rfc/rfc5322.html#section-3.6.7)）。だから、**いちばん上が最後の中継、いちばん下が最初の中継**です。

次は、この章の設定に合わせて作った架空の例です。

```
Received: from mx.example.net (mx.example.net [192.0.2.25])        ③
        by store.example.net (Dovecot) with LMTP id 8f3a
        for <hanako@example.net>; Mon, 21 Sep 2026 23:13:27 +0900
Received: from submit.example.com (submit.example.com [198.51.100.7])  ②
        by mx.example.net (Postfix) with ESMTPS id 4XyZ1
        for <hanako@example.net>; Mon, 21 Sep 2026 23:13:25 +0900
Received: from [192.168.1.20] (unknown [203.0.113.50])             ①
        by submit.example.com (Postfix) with ESMTPSA id 9AbC2
        for <hanako@example.net>; Mon, 21 Sep 2026 23:13:21 +0900
From: 山田 太郎 ...
```

| 句 | 意味 |
| --- | --- |
| `from A (B [C])` | A は相手が HELO で**名乗った**名前、B は受け手が逆引きで得た名前、C は実際の接続元の IP アドレス |
| `by` | この行を書いたサーバ自身 |
| `with` | 使ったプロトコル。`ESMTPS` は STARTTLS あり、`ESMTPSA` は STARTTLS と認証あり（[RFC 3848](https://www.rfc-editor.org/rfc/rfc3848.html)） |
| `id` | そのサーバのキューの ID。ログを追うときの手がかり |
| `for` | この回の受け取りでの宛先（`RCPT TO`） |
| 末尾の時刻 | そのサーバが受け取った時刻 |

下から読むと、① 利用者の端末（家庭のルータの内側 `192.168.1.20`、外から見た IP は `203.0.113.50`）が認証つきで提出し、② 送信側のサーバが受信側の MX へ TLS で中継し、③ MX がメールボックスのサーバへ LMTP で渡した、と分かります。各行の時刻の差を見れば、**どこで時間が掛かったか**も分かります（各サーバの時計が合っていれば、ですが）。

`from` の括弧の中身が重要です。**名乗った名前（A）は相手が言ったことにすぎず、信頼できるのは受け手が自分で確かめた IP アドレス（C）のほう**です。

<Callout type="warn" title="下のほうの Received は偽物かもしれない">
  `Received:` は受け取ったサーバが書く行ですが、送り手が最初からメッセージに `Received:` を書き込んでおくこともできます。
  各サーバは既存の行に触れないので、偽の行はそのまま下に残ります。
  **信頼できるのは、自分の組織のサーバが書いた行と、そのすぐ下の 1 行（自分のサーバが直接確かめた接続元）まで**です。それより下は、相手の申告として読みます。
</Callout>

## 手元で確かめる

Python 3.14 の標準ライブラリの email パッケージで、日本語の差出人・件名、テキストと HTML の本文、日本語の名前の添付を持つメッセージを組み立て、生のバイト列を見ます。外部のパッケージは使いません。

```python
from email.message import EmailMessage
from email.utils import formatdate
from email import policy

msg = EmailMessage(policy=policy.SMTP)          # 改行は CRLF
msg["From"] = "山田 太郎 <taro@example.com>"
msg["To"] = "hanako@example.net"
msg["Subject"] = "来週の打ち合わせについて"
msg["Date"] = formatdate(1790000000)
msg["Message-ID"] = "<20260928.1@example.com>"
msg.set_content("花子さん\n\n来週の打ち合わせの資料を添付します。\n")
msg.add_alternative("<p>花子さん</p><p>来週の打ち合わせの資料を<b>添付</b>します。</p>\n",
                    subtype="html")
msg.add_attachment(bytes(range(256)) * 12,      # 3072 バイト
                   maintype="application", subtype="octet-stream", filename="資料.bin")
open("msg.eml", "wb").write(msg.as_bytes())
```

```
From: =?utf-8?b?5aSq6YOO?=@=?utf-8?b?5L6L44GI?=.jp
```

## 何と組み合わさって意味を持つか

メッセージの形式は、それだけでは「こういう形をしている」としか言いません。何かを保証するのは、ほかの部品と組み合わさったときです。

| 部品 | 形式との関係 | 見る回 |
| --- | --- | --- |
| 文字コード | `charset` と encoded-word が指す先。取り違えれば化ける | 第 5 回 |
| SMTP の拡張 | `8bit` には 8BITMIME、生の UTF-8 には SMTPUTF8 が経路全体で必要 | 第 141 回 |
| MX と経路 | `Received:` に残る経路の記録 | 第 142 回 |
| DMARC | 誰でも書ける `From:` のドメインを、初めて検証に結びつける | 第 147 回 |
| DKIM | ヘッダと本文のバイト列に署名する。**折り返しや `Content-Transfer-Encoding` の変換で壊れる**ので、署名する前に 7 ビットに変換しておくべき（[RFC 6376 5.3](https://www.rfc-editor.org/rfc/rfc6376.html#section-5.3)） | 第 146 回 |
| S/MIME と OpenPGP | `multipart/signed` などの MIME の型で、本文だけを署名・暗号化する。ヘッダは守らない | 第 148 回 |
| 署名 | 「このバイト列に署名した」としか言わない、という性質がそのまま DKIM に効く | 第 106 回 |

DKIM の行は特に重要です。途中のサーバが 8BITMIME に対応しない次の相手のために `8bit` の本文を quoted-printable に変換するのは、RFC 6152 の上では正当な振る舞いです。しかし署名されたバイト列は変わるので、DKIM の検証は失敗します。**形式の上では同じ内容でも、バイト列が違えば署名は別物**です。

## まとめ

- メッセージは「ヘッダ、空行、本文」。1 行は 998 文字まで（78 文字以下が望ましい）で、長いヘッダは空白で始まる行に折り返す
- 必須のヘッダは `Date` と `From` だけ。`From`、`Sender`、`Reply-To`、`To` はどれも書き手が自由に書く文字列で、配送はエンベロープが決める
- スレッドは `Message-ID`、`In-Reply-To`、`References` で組む。`References` は親の `References` に親の `Message-ID` を足したもの
- MIME はヘッダを数本足して器を拡張した。`multipart` は境界文字列で部品を区切り、`alternative` は後ろほど忠実な表現を置く
- `Content-Transfer-Encoding` はバイト列を ASCII にする方法。base64 は約 4/3 倍、quoted-printable は日本語だと約 3 倍になる。`8bit` は経路の 8BITMIME が前提
- ヘッダの日本語は encoded-word（75 文字まで、アドレスや引用符の中には使えない）、添付の名前は RFC 2231。ISO-2022-JP は 7 ビットで通るために長く使われ、ESC の欠落、JIS X 0208 に無い文字、変換表の違いで化けた
- 日本語のアドレスそのものは SMTPUTF8 と RFC 6532 の世界で、経路全体の対応が要る
- `Received:` は先頭に積まれるので下から上へ読む。信頼できるのは自分の組織が書いた行と、その直下の接続元まで

ここまでで、メールが**どこを通り、どんな形で運ばれるか**が揃いました。次の第 144 回では、その経路を暗号化する話に移ります。提出と中継で事情がまったく違い、中継の STARTTLS は既定では証明書を確かめない、というところから始めます。
