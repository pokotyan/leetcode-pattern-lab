## 素直な方法と、その問題

8 ビットで負の数を表したいとします。いちばん素直な発想は、**先頭 1 ビットを符号に使う**ことです。

```
0 0000101  →  +5
1 0000101  →  -5
```

これを **符号付き絶対値表現** と呼びます。人間には読みやすい。しかし 2 つ困ったことが起きます。

**1 つめ。0 が 2 つある。** `00000000` が +0、`10000000` が -0 です。値の比較をするたびに「両方 0 かもしれない」と気にする必要があります。

**2 つめ。足し算の回路が使えない。** +5 と -5 を単純に足すと `00000101 + 10000101 = 10001010` で、これは -10 です。正しくは 0 です。つまり、符号を見て場合分けし、大小を比べ、引き算をする専用の回路が必要になります。回路が増えるのは、面積と遅延がそのまま増えることを意味します。

## 発想の転換：時計のように一周させる

別の考え方をします。3 時間前を知りたいとき、時計の針を反時計回りに 3 つ戻す代わりに、**時計回りに 9 つ進めても同じ場所に着きます**（12 時間で一周するから）。

```
-3  ≡  +9   （12 で割った余りが同じ）
```

引き算を、足し算で代用できたわけです。

同じことをビットでやります。8 ビットの値は 256 種類なので、256 で一周します。つまり **-1 は 255 と同じ場所**です。

```
-1  →  255  →  11111111
-2  →  254  →  11111110
-5  →  251  →  11111011
```

この決め方を **2 の補数 (two's complement)** と呼びます。

確かめます。5 + (-5) を、ただの足し算としてやってみます。

```
  00000101   (5)
+ 11111011   (-5, つまり 251)
-----------
 100000000   (256)
```

9 桁になりました。しかし 8 ビットしか保持できないので、はみ出した 1 は捨てられます。残るのは `00000000`、つまり 0 です。**正解です。**

<Callout type="tip" title="これが決定的に重要な理由">
  2 の補数を使うと、**符号付きの足し算・引き算に、符号なしとまったく同じ回路が使えます**。
  CPU は加算器を 1 つ持っていればよく、「これは符号付きか」を気にする必要がありません。
  気にするのは、結果を人間向けに表示するときと、大小比較のときだけです。
</Callout>

## 符号を反転する手順

ある値の 2 の補数（符号を反転した値）は、次の 2 手で求まります。

1. **全ビットを反転する**（0 と 1 を入れ替える。これを 1 の補数と呼ぶ）
2. **1 を足す**

5 → -5 でやってみます。

```
  00000101   5
  11111010   全ビット反転
+        1
-----------
  11111011   -5
```

なぜこれで合うのか。全ビット反転は「255 から引く」ことと同じです（`11111111 - x`）。そこに 1 を足すので、結果は `256 - x`。これはさっき決めた「-x を 256-x として表す」という約束そのものです。

<Callout type="note" title="頭の中でやるときの近道">
  右端から見ていって、**最初に現れる 1 まではそのまま、それより左を全部反転する**。
  `00101000` なら、右の 3 つの 0 と最初の 1（つまり `1000`）はそのままで、左の `0010` を反転して `1101`。
  結果は `11011000` です。手で書くときはこちらが速いです。
</Callout>

## MSB は符号ビットとして読める

2 の補数では、**最上位ビットが 1 なら負、0 なら正**になります。これは偶然ではなく、負の数を「上半分」に割り当てた結果です。

8 ビットの場合、値の割り当てはこうなります。

| ビットパターン | 符号なしとして | 符号付きとして |
| --- | --- | --- |
| 00000000 | 0 | 0 |
| 01111111 | 127 | 127 |
| 10000000 | 128 | **-128** |
| 11111111 | 255 | -1 |

**同じビット列が、解釈によって別の数になります。** ビット列そのものには符号の情報は入っていません。「これを符号付きとして読む」という約束が、型として別のところに書かれているだけです。

```c
unsigned char a = 200;
signed char   b = a;      // ビットは同じ。b は -56 になる
```

## 範囲が非対称なことの後始末

8 ビットの符号付き整数の範囲は **-128 〜 +127** です。負のほうが 1 つ多い。0 が正の側に 1 つ席を取っているためです。

この非対称さは、実際に事故を起こします。

```c
signed char x = -128;
signed char y = -x;      // +128 は表せない。結果は -128 のまま
```

絶対値を取っただけなのに負のまま、ということが起こります。`INT_MIN` に対する `abs()` は、C の規格上は未定義動作です。

<Callout type="warn" title="実際にあった事故">
  この非対称性は、割り算でも出ます。`INT_MIN / -1` は数学的には `+2147483648` ですが、
  32 ビット符号付き整数では表せません。x86 ではこの演算が**ゼロ除算と同じ例外を発生させ、プロセスが落ちます**。
  「割る数が 0 でないことは確認した」だけでは足りない、という珍しい例です。
</Callout>

## オーバーフローで何が起きるか

表せる範囲を超えると、値は一周して反対側に出ます。

```
  01111111   127
+        1
-----------
  10000000   -128
```

127 に 1 を足したら -128 になりました。**エラーは出ません。** CPU は淡々と足し算をしただけです。

ただし CPU は、これが起きたことを**フラグ**として記録しています。

| フラグ | 意味 |
| --- | --- |
| **C**（Carry） | 符号なしとして見たときに桁あふれした |
| **V / O**（Overflow） | 符号付きとして見たときに符号が壊れた |
| **Z**（Zero） | 結果が 0 だった |
| **N / S**（Negative / Sign） | 結果の MSB が 1 だった |

使うかどうかは、そのあとの命令次第です。C 言語の `int` の加算はこれらを無視するので、オーバーフローは静かに通り過ぎます（規格上は未定義動作で、最適化がそれを前提に働くことすらあります）。一方 Rust の debug ビルドは、このフラグを見てパニックします。**同じ CPU の同じ演算に対する、言語側の態度の違い**です。

<Callout type="tip" title="2038 年問題もこれ">
  Unix 時刻を 32 ビット符号付き整数で持つと、2038 年 1 月 19 日に +2147483647 を超えます。
  次の秒で -2147483648、つまり 1901 年に飛びます。原因は特別な何かではなく、
  ここで見た「一周して反対側に出る」という挙動そのものです。
</Callout>

## シフト演算に 2 種類ある理由

ビットを左右にずらす操作は、2 倍・1/2 倍に対応します。

左シフトは単純です。右端に 0 を詰めればよい。

右シフトが問題です。左端に何を詰めるか。

- **論理右シフト**：常に 0 を詰める。符号なしの値に使う
- **算術右シフト**：**元の MSB と同じ値**を詰める。符号付きの値に使う

`-8`（`11111000`）を 2 で割りたいとします。

```
論理右シフト: 01111100  →  124   間違い
算術右シフト: 11111100  →  -4    正しい
```

負の数では符号ビットを引き伸ばす必要があります。だから CPU には右シフト命令が 2 種類あり、多くの言語では型（符号付きか否か）でどちらを使うかが決まります。JavaScript のように `>>` と `>>>` で明示的に書き分ける言語もあります。

## まとめ

- 2 の補数は「負の数を上半分に割り当てる」約束。引き算のための専用回路が要らなくなる
- 符号を反転するには、全ビット反転して 1 を足す
- ビット列そのものに符号の情報はない。解釈する側の約束
- 範囲は非対称（-128 〜 +127）。最小値の絶対値は取れない
- オーバーフローしてもエラーにはならない。フラグに残るだけで、使うかは言語次第
