## 鍵をどうやって渡すのか

第 105 回の AES-GCM は、同じ鍵を持つ 2 人の間なら、機密性と完全性をまとめて守ってくれました。ただし前提があります。**2 人が同じ鍵を、あらかじめ持っている**ことです。

ブラウザが初めて訪れるサイトと、そんな鍵を共有しているはずがありません。鍵をそのまま送れば、経路の途中で盗聴している人（第 103 回の攻撃者のモデル）にも届きます。鍵を暗号化して送ろうにも、そのための鍵がありません。これが**鍵配送問題**です。

1976 年、Whitfield Diffie と Martin Hellman は、**盗聴されている経路だけを使って、2 人が共通の秘密を作る**方法を示しました（[New Directions in Cryptography](https://ee.stanford.edu/~hellman/publications/24.pdf)）。翌年には Rivest、Shamir、Adleman が、公開してよい鍵で暗号化し、自分だけが持つ鍵で復号する方式を発表します（[RSA の論文](https://people.csail.mit.edu/rivest/Rsapaper.pdf)）。

この回では、この 2 系統を見ます。そして、実際のプロトコルがどちらをどう使っているか、使わなくなったのはなぜかを見ます。

## 鍵を 2 つに分ける

共通鍵暗号では、暗号化と復号に同じ鍵を使いました。公開鍵暗号では、鍵が**ペア**になります。

| 鍵 | 誰が持つか | 何に使うか |
| --- | --- | --- |
| 公開鍵 | 誰に配ってもよい | 暗号化する、鍵交換の相手に渡す、署名を検証する |
| 秘密鍵 | 持ち主だけ | 復号する、鍵交換で共有秘密を計算する、署名する |

ペアの間には数学的な関係がありますが、**公開鍵から秘密鍵を計算するのは現実的な時間ではできない**。公開鍵暗号の安全性はすべて、この「一方向には簡単で、逆向きは難しい」計算に乗っています。何を難しさの根拠にするかで、方式が分かれます。

| 方式 | 難しさの根拠 |
| --- | --- |
| RSA | 大きな合成数の素因数分解 |
| Diffie-Hellman（有限体） | 離散対数問題 |
| 楕円曲線（ECDH、X25519、ECDSA、Ed25519） | 楕円曲線上の離散対数問題 |
| ML-KEM | 格子の問題（Module-LWE） |

## RSA の仕組み

RSA の鍵は、次のように作ります。

```
1. 大きな素数 p と q を選ぶ（それぞれ 1024 ビットなど）
2. n = p × q                     … 公開する
3. φ(n) = (p-1)(q-1)             … 秘密
4. e を決める（ほぼ常に 65537）    … 公開する
5. e × d ≡ 1 (mod φ(n)) となる d … 秘密鍵

暗号化: c = m^e mod n
復号:   m = c^d mod n
```

公開鍵は `(n, e)`、秘密鍵は `d` です。`d` を求めるには `φ(n)` が要り、`φ(n)` を求めるには `n` を `p` と `q` に分解する必要があります。**n が 2048 ビットもあると、この分解が現実的な時間で終わらない**。これが RSA の安全性の根拠です。

小さな数で動かすと、仕組みそのものは数行です。

```python
p, q = 61, 53
n = p * q
phi = (p - 1) * (q - 1)
e = 17
d = pow(e, -1, phi)

m = 65
c = pow(m, e, n)
```

```
n=3233 phi=3120 e=17 d=2753
m=65 -> c=2790 -> m'=65
```

`d` の計算に使った `phi` は、`p` と `q` を知っている人にしか作れません。

## 教科書どおりの RSA は危ない

上のように、平文の数をそのまま `m^e mod n` にするものを**教科書的 RSA**（textbook RSA）と呼びます。これを実際に使うと、少なくとも 3 つの問題が起きます。

**同じ平文は同じ暗号文になる。** 計算に乱数が入っていないからです。公開鍵は誰でも持っているので、攻撃者は「yes」「no」を自分で暗号化して、盗聴した暗号文と見比べるだけで中身が分かります。第 105 回の ECB と同じ種類の弱さです。

**暗号文をいじると、平文が予測どおりに変わる。** `c` に `2^e` を掛けると、復号結果は `2m` になります。

```python
c2 = (c * pow(2, e, n)) % n
pow(c2, d, n)   # → 130 （= 65 × 2）
```

秘密鍵を知らなくても、平文を狙った値に変えられます。暗号化は改ざんを防がない、という第 105 回の話がここでも当てはまります。

**短い平文は、そのまま根を取れば戻る。** `e = 3` で `m` が小さく `m^3 < n` なら、`mod n` がまったく効かず、`c` の 3 乗根がそのまま `m` です。

そこで、実際には平文に**乱数を混ぜた詰め物（パディング）**をしてから計算します。現在の推奨は **OAEP** です（[RFC 8017 7.1](https://www.rfc-editor.org/rfc/rfc8017.html#section-7.1)）。ハッシュ関数（第 104 回）と乱数で平文を包み、毎回違う暗号文にし、改ざんされた暗号文は復号の段階で弾きます。

古い方式の **PKCS#1 v1.5** のパディングは、形式が合っているかどうかの応答の違いから平文を少しずつ割り出される攻撃が 1998 年に Bleichenbacher によって示されました。2017 年の ROBOT は、同じ攻撃が当時も多くの HTTPS サーバで通ることを示し、**`TLS_RSA` で始まる暗号スイートを無効にするしかない**と結論しています（[ROBOT](https://robotattack.org/)）。

<Callout type="warn" title="よくある誤解: 「RSA で暗号化すれば、あとは安全」">
  RSA の安全性は、素因数分解の難しさだけでは決まりません。
  **パディングを付けない、または古いパディングを使う**だけで、平文が推測されたり、暗号文から平文が割り出されたりします。
  計算式が正しくても、組み合わせ方で壊れるという第 103 回の「自分で暗号を組むな」の典型です。
  ライブラリを使うときも、`padding=None` のような選択肢が残っていないかを確かめてください。
</Callout>

## RSA で大きなデータは運べない

OAEP には、もう 1 つ見逃せない性質があります。**一度に暗号化できる長さが、鍵の大きさで決まる**ことです。2048 ビット（256 バイト）の鍵で SHA-256 の OAEP を使うと、平文は最大 `256 - 2×32 - 2 = 190` バイトです（[RFC 8017 7.1.1](https://www.rfc-editor.org/rfc/rfc8017.html#section-7.1.1)）。

Python の cryptography で確かめます。

```python
from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes

key = rsa.generate_private_key(public_exponent=65537, key_size=2048)
pub = key.public_key()
oaep = padding.OAEP(mgf=padding.MGF1(hashes.SHA256()), algorithm=hashes.SHA256(), label=None)

msg = b"attack at dawn"
c1 = pub.encrypt(msg, oaep)
c2 = pub.encrypt(msg, oaep)
```

```
暗号文の長さ: 256 バイト
同じ平文の 2 回の暗号文は同じか: False
復号: b'attack at dawn'
190 バイト: OK
191 バイト: Encryption failed
```

同じ平文でも暗号文は毎回変わり、191 バイトは暗号化できません。しかも RSA の秘密鍵の演算は、AES に比べて桁違いに遅い処理です。**RSA で運べるのは、せいぜい共通鍵 1 つ分**です。

## Diffie-Hellman: 送らずに共有する

Diffie-Hellman（DH）は、何かを暗号化して送る方式ではありません。**2 人がそれぞれ公開値を送り合い、各自の手元で同じ秘密を計算する**方式です。

小さな数でたどります。公開の約束として、素数 `p = 23` と `g = 5` を決めておきます。

```
Alice                                   Bob
秘密 a = 6 を選ぶ                        秘密 b = 15 を選ぶ
A = 5^6 mod 23 = 8                      B = 5^15 mod 23 = 19
          ──────── A = 8 を送る ────────→
          ←────── B = 19 を送る ────────
B^a = 19^6 mod 23 = 2                   A^b = 8^15 mod 23 = 2
```

どちらも `g^(ab) mod p` を計算しているので、同じ値 2 になります。盗聴者に見えるのは `p`、`g`、`A`、`B` だけです。そこから `a` か `b` を求めるのが**離散対数問題**で、`p` が十分大きいと現実的な時間では解けません。

**楕円曲線 DH（ECDH）** は、同じ考え方を「数のべき乗」から「楕円曲線上の点を何倍かする」計算に置き換えたものです。秘密は数 `a`、公開値は基点 `G` を `a` 倍した点 `aG`。相手の公開値を自分の秘密で何倍かすると、どちらも `abG` に着きます。同じ強度を、有限体の DH よりずっと短い鍵で得られます。

今いちばん広く使われているのが **X25519**（Curve25519 上の ECDH）です（[RFC 7748](https://www.rfc-editor.org/rfc/rfc7748.html)、2016 年）。秘密も公開値も **32 バイト**。RFC 7748 は、計算結果が全部 0 になっていないかを確かめて、0 なら中止してよいと定めています（[RFC 7748 6.1](https://www.rfc-editor.org/rfc/rfc7748.html#section-6.1)）。相手が細工した公開値を送ってきた場合の備えです。

<Callout type="note" title="X25519 の鍵で署名はできない">
  X25519 は鍵交換専用です。同じ Curve25519 の仲間でも、署名に使うのは Ed25519 で、鍵の形式も別です。
  鍵ファイルの種類と用途の対応は、第 108 回で詳しく見ます。
</Callout>

## 手元で確かめる: X25519 で同じ秘密に着く

Python の cryptography で、Alice と Bob の 2 人分の鍵を作り、公開値だけを交換して同じ秘密になるかを見ます。最後に、その秘密から HKDF（第 109 回）で AES-GCM の鍵を作り、第 105 回の暗号化につなげます。

```python
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.hazmat.primitives.serialization import Encoding, PublicFormat
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
from cryptography.hazmat.primitives import hashes
import os

def raw(pub):
    return pub.public_bytes(Encoding.Raw, PublicFormat.Raw)

alice = X25519PrivateKey.generate()
bob = X25519PrivateKey.generate()
A, B = alice.public_key(), bob.public_key()

s_alice = alice.exchange(B)   # Alice は自分の秘密と Bob の公開値だけを使う
s_bob = bob.exchange(A)       # Bob も同様

def derive(secret):
    return HKDF(algorithm=hashes.SHA256(), length=32, salt=None, info=b"demo v1").derive(secret)

nonce = os.urandom(12)
ct = AESGCM(derive(s_alice)).encrypt(nonce, b"hello bob", None)
print(AESGCM(derive(s_bob)).decrypt(nonce, ct, None))
```

```
Alice が送る公開値: f77c612f4f9fb6cfd3b7407921951ef90c3d881f97dadb197753ce92ec5b977f
Bob   が送る公開値: 1927cc6e78842f0c810341df2bc27cd7956d8b4c1e0ab3ebd0848d8d84e5bf0b
Alice の共有秘密:   4e71a17394eb11db9f02db0d2f74869d73dae6872e1beb6ae9415bdfd4c55759
Bob   の共有秘密:   4e71a17394eb11db9f02db0d2f74869d73dae6872e1beb6ae9415bdfd4c55759
一致: True
Bob が復号: b'hello bob'
```

線の上を流れたのは 32 バイトの公開値 2 つだけです。共有秘密そのものは、一度も送られていません。

共有秘密をそのまま AES の鍵にせず HKDF を通しているのは、X25519 の出力が一様な乱数ではない（曲線の点の座標である）ためと、1 つの秘密から用途ごとに別の鍵を作りたいためです。TLS 1.3 も同じく、鍵交換の結果を HKDF の鍵スケジュールに入れています（第 113 回）。

## 実際のプロトコルは、公開鍵で本文を暗号化しない

ここまでで、公開鍵暗号の役目がはっきりします。RSA は短いものしか運べず遅い。DH はそもそも何も運ばない。だから実際のプロトコルは、**公開鍵の仕組みで共通鍵を用意し、本文は共通鍵の AEAD で暗号化する**という 2 段構えにしています。これを**ハイブリッド暗号**と呼びます。

```
          公開鍵の仕組み                      共通鍵の仕組み
  ┌───────────────────────┐   共有秘密   ┌───────┐   鍵   ┌──────────────────────┐
  │ 鍵交換（X25519 など）   │ ──────────→ │ HKDF  │ ────→ │ AEAD（AES-GCM など）   │ ← 本文はここ
  │ または RSA で鍵を包む   │              └───────┘        └──────────────────────┘
  └───────────────────────┘
      数十〜数千バイト、1 回だけ                          何ギガバイトでも、高速に
```

TLS、SSH（第 115 回）、QUIC（第 66 回）、Signal、age、PGP、どれもこの形です。PGP や S/MIME のように「公開鍵で暗号化する」と説明される方式も、実際に公開鍵で暗号化しているのは、本文を暗号化した**使い捨ての共通鍵**のほうです。

<Callout type="warn" title="よくある誤解: 「HTTPS はサーバの公開鍵で通信を暗号化している」">
  広く流布している説明ですが、正確ではありません。
  TLS 1.2 以前の RSA 鍵交換でも、サーバの公開鍵で暗号化していたのは**プリマスタシークレット**という 48 バイトの値だけでした（[RFC 5246 7.4.7.1](https://www.rfc-editor.org/rfc/rfc5246.html#section-7.4.7.1)）。
  本文は、そこから導いた共通鍵で暗号化されます。
  そして TLS 1.3 では、サーバの公開鍵は**暗号化にまったく使われません**。鍵は ECDHE で作り、サーバの鍵は「ハンドシェイクに署名する」ためだけに使われます（第 107 回、第 113 回）。
  「証明書の公開鍵で暗号化している」という理解のままだと、次の節の前方秘匿性が分からなくなります。
</Callout>

## 前方秘匿性: 秘密鍵が後から漏れたら

RSA で鍵を包む方式と、DH で鍵を作る方式は、普段の通信では同じように働きます。違いが出るのは、**何年も後にサーバの秘密鍵が漏れたとき**です。

```
TLS 1.2 の RSA 鍵交換
  クライアント ── サーバの公開鍵で包んだプリマスタシークレット ──→ サーバ
  攻撃者: 暗号化された通信を全部録っておく
  （数年後）サーバの秘密鍵が漏れる
  攻撃者: 録っておいたプリマスタシークレットを復号 → 共通鍵を再計算 → 過去の通信を全部読む

ECDHE（接続ごとに使い捨ての鍵で DH）
  クライアント ── 使い捨ての公開値 ──→ サーバ（使い捨ての秘密は接続後に捨てる）
  （数年後）サーバの秘密鍵が漏れる
  攻撃者: 漏れたのは署名用の鍵だけ。録った通信の共有秘密は、もう誰も計算できない
```

**過去の通信が、後からの秘密鍵の漏洩に巻き込まれない**性質を、**前方秘匿性**（forward secrecy）と呼びます。鍵交換の秘密（ECDHE の E は ephemeral、使い捨ての意味）を接続ごとに作って捨てるから成り立ちます。

TLS 1.2 では、ECDHE と RSA 鍵交換のどちらも選べました。TLS 1.3 は RSA 鍵交換と静的な DH を削除し、「公開鍵による鍵交換は、すべて前方秘匿性を持つ」と明記しています（[RFC 8446 1.2](https://www.rfc-editor.org/rfc/rfc8446.html#section-1.2)）。先ほどの ROBOT も、「録っておいた通信を後から復号できる」のが RSA 鍵交換を捨てる大きな理由でした。

<Callout type="warn" title="よくある誤解: 「秘密鍵が漏れても、鍵を替えればそれで済む」">
  前方秘匿性のない方式では、鍵を替えても**すでに録られた過去の通信**は守れません。
  逆に、前方秘匿性のある方式で漏れた秘密鍵は、主に「そのサーバになりすます」ために使われます。
  漏れたときに何を失うかは、鍵交換の方式で決まります。
  なお TLS 1.3 でも、セッション再開用のチケットを暗号化する鍵を長く使い回すと、その鍵の漏洩で再開した通信が読まれうるので、前方秘匿性は構成次第で薄まります（第 113 回）。
</Callout>

## 鍵交換は、相手が誰かを教えてくれない

DH は、盗聴するだけの攻撃者には破れません。しかし**途中で公開値を差し替えられる攻撃者**には無力です。Mallory が Alice と Bob の間に入り、両方に自分の公開値を渡したらどうなるかを確かめます。

```python
alice, bob, mallory = (X25519PrivateKey.generate() for _ in range(3))
M = mallory.public_key()

alice_side = alice.exchange(M)   # Alice は Bob の公開値だと思って M を使う
bob_side = bob.exchange(M)       # Bob も Alice の公開値だと思って M を使う
```

```
Alice と Bob の秘密は一致: False
Mallory は Alice 側の秘密を持つ: True
Mallory は Bob 側の秘密を持つ:   True
```

Alice と Bob はそれぞれ「鍵交換に成功した」と思っていますが、実際には 2 本の別々の暗号化通信が Mallory のところで終わっています。Mallory は Alice から届いたものを復号して読み、書き換え、Bob 向けに暗号化し直せます。これが**中間者攻撃**です。

```
Alice ═══ 暗号化 ═══ Mallory ═══ 暗号化 ═══ Bob
         鍵 K1      （全部読める）    鍵 K2
```

鍵交換が保証するのは「**この公開値の持ち主**と秘密を共有した」ことだけです。その公開値が本当に Bob のものかは、鍵交換の中には何も書かれていません。

これを塞ぐには、Bob が「この公開値は私が送った」ことを示す必要があります。そのための道具が**署名**（第 107 回）で、署名に使う鍵が本当に Bob のものかを第三者が保証するのが**証明書**（第 17 章、第 110 回から）です。TLS 1.3 の CertificateVerify は、まさに鍵交換を含むハンドシェイク全体への署名です。

<Callout type="warn" title="よくある誤解: 「暗号化されていれば、正しい相手と話している」">
  鍵交換と AEAD がそろっていても、相手の確認がなければ、**暗号化された通信を攻撃者と結んでいる**だけかもしれません。
  `curl -k` や `verify=False` で証明書の検証を切ると、暗号化は続いたまま、この節の Mallory を素通りさせます。
  暗号化（機密性）と、相手の確認（真正性）は、第 103 回で分けたとおり別の性質で、別の部品が担います。
</Callout>

## 量子コンピュータと「今収集して後で解読」

RSA も DH も楕円曲線も、十分に大きな量子コンピュータがあれば、Shor のアルゴリズムで効率よく解けることが 1994 年に示されています（[Shor](https://arxiv.org/abs/quant-ph/9508027)）。そうした量子コンピュータは、執筆時点（2026 年 9 月）でまだ存在しません。

それでも鍵交換の移行が急がれているのは、**今録られた通信は、将来解読できるようになる**からです。NIST は、攻撃者が暗号化されたデータを今集めておき、量子技術が成熟してから解読する「harvest now, decrypt later」の脅威を、移行を急ぐ理由として挙げています（[NIST IR 8547 初期公開草案](https://csrc.nist.gov/pubs/ir/8547/ipd)、2024 年 11 月）。同じ草案は、112 ビット相当の強度の RSA や楕円曲線（RSA-2048、P-256 など）を 2030 年以降は非推奨、2035 年以降は不許可とする案を示しています。

前方秘匿性は、この脅威には効きません。使い捨ての秘密を捨てても、**録られた公開値から量子コンピュータで秘密を計算し直せる**からです。

### ML-KEM

NIST は 2024 年 8 月 13 日、格子の問題に基づく **ML-KEM** を FIPS 203 として標準化しました（[FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)）。パラメータは ML-KEM-512、768、1024 の 3 種類です。

ML-KEM は DH とは形が違う **KEM**（鍵カプセル化方式）です。

```
受け手: 鍵ペアを作り、カプセル化鍵（公開鍵）を送る
送り手: カプセル化鍵に対して encapsulate → (暗号文, 共有秘密) が出てくる。暗号文を送る
受け手: 自分の秘密鍵で decapsulate → 同じ共有秘密が出てくる
```

送り手が値を選んで包む点は RSA の鍵輸送に似ていますが、受け手が**接続ごとに鍵ペアを作り直す**使い方をすれば、前方秘匿性も保てます。TLS ではクライアントが毎回新しい鍵ペアを作ります。

openssl 3.6 で試すと、大きさの違いが分かります。

```
$ openssl genpkey -algorithm ML-KEM-768 -out kem.pem
$ openssl pkey -in kem.pem -pubout -out kem.pub
$ openssl pkeyutl -encap -pubin -inkey kem.pub -out ct.bin -secret ss_sender.bin
$ openssl pkeyutl -decap -inkey kem.pem -in ct.bin -secret ss_recv.bin
$ wc -c ct.bin ss_sender.bin
    1088 ct.bin
      32 ss_sender.bin
$ cmp ss_sender.bin ss_recv.bin && echo same
same
```

共有秘密は X25519 と同じ 32 バイトですが、線の上を流れる暗号文は 1088 バイトです。X25519 の 32 バイトに比べて桁が 2 つ違います。

### 2 つを重ねる: X25519MLKEM768

ML-KEM はまだ新しく、実装の不具合や未知の弱点がないとは言い切れません。そこで TLS では、**X25519 と ML-KEM-768 を両方行い、2 つの共有秘密を連結して鍵スケジュールに入れる**ハイブリッドが使われています。どちらか一方が破られても、もう一方が残っていれば秘密は守られます。

この方式は 2026 年に RFC 10024 として標準化されました（[RFC 10024](https://www.rfc-editor.org/info/rfc10024)）。名前付きグループの番号は `0x11EC` で、クライアントの鍵共有はカプセル化鍵 1184 バイトと X25519 の 32 バイトを連結した 1216 バイト、サーバの応答は暗号文 1088 バイトと X25519 の 32 バイトで 1120 バイトです（[draft-ietf-tls-ecdhe-mlkem](https://datatracker.ietf.org/doc/draft-ietf-tls-ecdhe-mlkem/)）。

執筆時点（2026 年 9 月）で、主要なブラウザはこれを既定で使っています。

| ブラウザ / OS | 既定になった版 | 出典 |
| --- | --- | --- |
| Chrome | 131（2024 年 11 月。それまでの Kyber 版 `0x6399` から切り替え） | [Google Security Blog](https://security.googleblog.com/2024/09/a-new-path-for-kyber-on-web.html) |
| Firefox | デスクトップ 132、Android 145 | [Cloudflare](https://developers.cloudflare.com/ssl/post-quantum-cryptography/pqc-support/) |
| Safari / Apple の OS | iOS 26、macOS Tahoe 26 など。URLSession と Network framework でも既定 | [Apple](https://support.apple.com/en-us/122756) |

手元の openssl 3.6 も、グループを指定しなければ X25519MLKEM768 を提案に含めます。実際に接続して、何が選ばれたかを見ます。

```
$ echo | openssl s_client -connect www.cloudflare.com:443 -servername www.cloudflare.com 2>/dev/null \
    | grep -E "Negotiated|Protocol"
Negotiated TLS1.3 group: X25519MLKEM768
Protocol: TLSv1.3

$ echo | openssl s_client -connect www.cloudflare.com:443 -servername www.cloudflare.com -groups x25519 2>/dev/null \
    | grep "Temp Key"
Peer Temp Key: X25519, 253 bits
```

X25519 だけを提案すれば、X25519 だけで接続します。耐量子の鍵交換は、両端が対応していて初めて使われます。

<Callout type="note" title="署名の移行は後回し">
  ここで耐量子になったのは**鍵交換だけ**です。サーバの確認に使う署名と証明書は、執筆時点でも RSA や ECDSA のままです。
  過去の署名を後から偽造できても、その接続の検証はもう終わっているので、「今収集して後で解読」の対象になりにくいからです。
  署名側の耐量子方式（ML-DSA）は第 107 回で触れます。
</Callout>

## 部品の組み合わせで見る

この回の部品は、単体では何も守りません。組み合わさって初めて意味を持ちます。

| 部品 | 担うもの | 足りないもの | 補う部品 |
| --- | --- | --- | --- |
| 鍵交換（ECDHE、X25519MLKEM768） | 盗聴者に知られない共有秘密 | 相手が誰か | 署名（第 107 回）＋ 証明書（第 110 回） |
| 共有秘密 | 32 バイトの秘密 | そのまま鍵にするには偏りがある、用途ごとに分けたい | HKDF（第 109 回） |
| HKDF が出した鍵 | 共通鍵 | 本文の保護そのもの | AEAD（第 105 回） |
| 署名 | 公開値を送ったのが鍵の持ち主であること | 鍵が誰のものか | 証明書、known_hosts（第 115 回） |

TLS 1.3 のハンドシェイクは、この表の行をすべて 1 往復に詰め込んだものです（第 113 回）。

## まとめ

- 鍵配送問題: 共通鍵暗号は、鍵をあらかじめ共有していないと使えない。公開鍵暗号は鍵を公開鍵と秘密鍵に分けて、これを解く
- RSA は素因数分解の難しさに頼る。教科書的 RSA は決定的で改ざんに弱く、OAEP のパディングが要る。PKCS#1 v1.5 の暗号化は Bleichenbacher 攻撃と ROBOT で問題になった
- RSA で運べるのは鍵 1 つ分程度。2048 ビットの OAEP（SHA-256）で最大 190 バイト
- Diffie-Hellman は何も送らずに、公開値の交換だけで同じ秘密を作る。X25519 は 32 バイトの鍵で行う楕円曲線 DH
- 実際のプロトコルは公開鍵で本文を暗号化しない。鍵交換 → HKDF → AEAD のハイブリッド
- 接続ごとの使い捨ての鍵交換は前方秘匿性を持つ。TLS 1.3 は RSA 鍵交換を廃止し、前方秘匿性のある鍵交換だけにした
- 鍵交換だけでは中間者を防げない。相手の確認には署名と証明書が要る
- 「今収集して後で解読」に備え、鍵交換は ML-KEM（FIPS 203）と X25519 のハイブリッド X25519MLKEM768 に移りつつあり、主要ブラウザでは既定になっている

鍵交換で共通の秘密は作れましたが、送られてきた公開値が本当に相手のものかは、まだ分かりません。次の第 107 回では、「この鍵の持ち主が作った」ことを示すデジタル署名を見ます。
