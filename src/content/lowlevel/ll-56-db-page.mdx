## この章で見るもの

データベースは、ここまでの章で見てきたものの集大成です。ファイルシステムの上にファイルを置き、ページキャッシュと付き合い、`fsync` で永続化を確かめ、複数のスレッドで同時に読み書きし、ネットワーク越しに問い合わせを受けます。

システムデザインの区画には、データベースを **選ぶ側** から見た読み物があります。

| 読み物 | 扱っていること |
| --- | --- |
| <a href={`${import.meta.env.BASE_URL}reading/db-index/`}>データベースの索引（B-tree と LSM-tree）</a> | 索引の構造と、読み書きのどちらを犠牲にするか |
| <a href={`${import.meta.env.BASE_URL}reading/consensus/`}>分散合意（CAP・Quorum・Raft）</a> | 複数のノードで 1 つの値を決める方法 |
| <a href={`${import.meta.env.BASE_URL}reading/distributed-transaction/`}>分散トランザクション（2PC と Saga）</a> | 複数の場所にまたがる更新を揃える方法 |

この章は、その **下** で何が起きているかを見ます。B-tree がディスクの上で実際にどう置かれているのか、主キーとそれ以外の索引は何が違うのか、コミットしたデータがなぜ消えないのか、そしてそれを何台ものマシンに広げると何が変わるのか。

最初は、すべての土台になる **ページ** です。

## ファイルを固定長に切る

データベースは、テーブルや索引を 1 つ（または複数）のファイルとして持ちます。ただし、そのファイルを行ごとに読み書きするわけではありません。**ファイルを固定長の「ページ」の並びとして扱います**。

| 製品 | ページの大きさ |
| --- | --- |
| PostgreSQL | 8KB（[ドキュメント](https://www.postgresql.org/docs/current/storage-page-layout.html)） |
| MySQL（InnoDB） | 16KB（既定。`innodb_page_size` で変更可） |
| SQLite | 4KB（既定。[ドキュメント](https://www.sqlite.org/pragma.html#pragma_page_size)） |

固定長にする理由は、第 4 章のページングとまったく同じです。

- **番号で場所が決まる。** ページ番号 × 8KB がファイル内の位置になる。探す必要がない
- **読み書きの単位が揃う。** ディスクもページキャッシュも、ブロック単位でしか動かない。1 行だけ読みたくても、実際に動くのはブロックである
- **キャッシュの単位になる。** メモリ上でも、ページを 1 枚ずつ置いたり追い出したりできる

1 行が 100 バイトでも、ディスクとの間を行き来するのは常に 8KB です。第 15 回で見た「1 バイト欲しくても 64 バイト持ってくる」キャッシュラインの話が、桁を変えてもう一度出てきます。

## ページの中身：スロット付きページ

ページの中に行をどう並べるかにも工夫があります。PostgreSQL のページは、次のような形をしています。

```
 0                                                        8192
 ┌────────┬──────────────────┬──────────┬──────────────────┐
 │ ヘッダ  │ 行ポインタ 1,2,3… → │  空き領域  │ ← … 行 3 行 2 行 1 │
 └────────┴──────────────────┴──────────┴──────────────────┘
          ↑ lower                        ↑ upper
```

- **行ポインタ**（1 つ 4 バイト）は、先頭から後ろへ向かって増える。中身は「行がページ内のどこから何バイトあるか」
- **行そのもの** は、末尾から前へ向かって詰める
- 両者の間が空き領域。`lower` と `upper` がぶつかったら満杯

手元の PostgreSQL 18 で、10 万行のテーブルの最初のページを覗くと、この通りになっています（`pageinspect` 拡張を使用）。

```sql
SELECT lower, upper, pagesize FROM page_header(get_raw_page('t', 0));
--  lower | upper | pagesize
--    764 |   832 |     8192

SELECT lp, lp_off, lp_len FROM heap_page_items(get_raw_page('t', 0)) LIMIT 3;
--  lp | lp_off | lp_len
--   2 |   8152 |     40
--   3 |   8112 |     40
```

ヘッダが 24 バイト、行ポインタが 185 個で 24 + 185 × 4 = 764。行は末尾の 8192 から 40 バイトずつ前に詰められています。

### なぜ 1 段挟むのか

行を指すときは、**ページ番号と行ポインタの番号の組** を使います。PostgreSQL ではこれを `ctid` と呼び、SQL から見えます。

```sql
SELECT ctid, * FROM t ORDER BY id LIMIT 3;
--  ctid  | id | name
--  (0,1) |  1 | user1
--  (0,2) |  2 | user2
--  (0,3) |  3 | user3
```

`(0,2)` は「0 番のページの、2 番の行ポインタ」です。行の実際の位置（ページ内のオフセット 8152）ではありません。

1 段挟んでおくと、**ページの中で行を動かしても、外からの呼び名は変わりません**。行を削除して隙間ができたら、残りの行を詰め直し、行ポインタの中身だけ書き換えればよい。索引は `(0,2)` を持ち続けられます。

<Callout type="tip" title="同じ間接参照を、何度も見てきた">
  第 4 章の仮想アドレスは、物理メモリの場所を動かしてもプログラムから見たアドレスが変わらないようにする間接参照でした。
  第 42 回のファイルディスクリプタも、カーネル内の実体を指す番号でした。
  **「番号で呼び、表で引く」ことで、実体を動かす自由を得る**。スロット付きページも同じ設計です。
</Callout>

## なぜ自前でキャッシュを持つのか

第 48 回で見たとおり、ファイルを読めば OS がページキャッシュに載せてくれます。それでもデータベースは、**バッファプール** という自前のキャッシュを持ちます。第 14 回の表に 1 行だけ登場した「データベース / バッファプール / テーブルファイル」がこれです。

OS に任せきりにしない理由は、データベースにしか分からないことがあるからです。

| データベースが知っていること | OS には分からない理由 |
| --- | --- |
| このページは **いま使用中** で、追い出されては困る（ピン留め） | OS はプロセスがメモリ上のどこを参照中か知らない |
| このページは **全件走査で 1 回通るだけ**。残しても無駄 | OS から見れば普通の読み込み |
| このページを書き出す前に、**ログを先に書く必要がある** | OS はダーティなページを好きな順に書き戻す |

特に 3 つ目が決定的です。データベースは「変更内容をログに書き、それが確実にディスクに載ってから、データのページを書く」という順序を守ることで、クラッシュしても壊れないことを保証しています（第 58 回で詳しく見ます）。**書き出しの順序を OS に委ねると、この保証が成り立ちません**。

## 二重に持つ問題

自前でキャッシュを持つと、今度は OS のページキャッシュと **同じページを 2 回持つ** 問題が出ます。

```
 ディスク ──→ OS のページキャッシュ ──→ バッファプール ──→ クエリ
              （8KB の写し）           （同じ 8KB の写し）
```

ここで、製品によって方針が分かれます。

**MySQL（InnoDB）は、OS のキャッシュを迂回します。** データファイルを `O_DIRECT` 付きで開くと、読み書きがページキャッシュを通らず、ディスクとバッファプールの間で直接行われます。MySQL 8.4 から、Linux ではこれが既定になりました（[MySQL 8.4 リファレンス](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html)）。その代わり、キャッシュはバッファプールだけなので、メモリの大半をバッファプールに割り当てるのが普通です。

**PostgreSQL は、OS のキャッシュを使います。** 通常の `read` / `write` でファイルにアクセスし、バッファプール（`shared_buffers`）から追い出したページも、しばらく OS のページキャッシュに残ります。**OS のキャッシュを 2 段目のキャッシュとして当てにする設計** です。そのため `shared_buffers` はメモリの 25% 程度に抑え、残りを OS に任せるのが定番の目安になっています。

| | InnoDB | PostgreSQL |
| --- | --- | --- |
| ファイルの開き方 | `O_DIRECT`（8.4 以降の既定） | 通常の読み書き |
| キャッシュ | バッファプールだけ | バッファプール + OS のページキャッシュ |
| バッファプールの大きさ | メモリの大半 | メモリの 25% 程度が目安 |
| 二重持ち | 起きない | 起きる（代わりに OS の先読みなどが効く） |

<Callout type="note" title="非同期 I/O も自前で持ち始めた">
  OS のキャッシュを使う方式でも、読み込みを待つ間は止まってしまいます（第 44 回）。
  PostgreSQL 18 では、複数の読み込みをまとめて発行する **非同期 I/O** が入りました。
  専用のワーカープロセスに任せる方式が既定で、Linux の `io_uring` を使う方式も選べます
  （[PostgreSQL 18 リリースノート](https://www.postgresql.org/docs/release/18.0/)）。
  第 45 回で見た「待つ仕組みの進化」が、データベースの内側でも起きています。
</Callout>

## 何を追い出すか

バッファプールが満杯になったら、どれかのページを追い出す必要があります。第 15 回の CPU キャッシュと同じく、素朴に考えれば LRU（最後に使われてから最も時間が経ったもの）です。

しかし、データベースでは素朴な LRU が大きく外れる場面があります。**全件走査** です。

大きなテーブルを 1 回だけ頭から読むと、そのページが次々と「最近使ったもの」として先頭に並び、**何度も使われていた大事なページがすべて追い出されます**。しかも、走査で読んだページは二度と使われません。

各製品はこれを避ける工夫をしています。

**InnoDB：途中に差し込む。** 新しく読んだページを LRU リストの先頭ではなく、**末尾から 3/8 の位置** に差し込みます。そこから末尾までは「古い」区画で、追い出しの候補です。古い区画のページは、最初のアクセスから 1 秒（`innodb_old_blocks_time` の既定値）以上経ってから再び使われたときに、初めて先頭に移ります（[MySQL 8.4 リファレンス](https://dev.mysql.com/doc/refman/8.4/en/innodb-performance-midpoint_insertion.html)）。全件走査は短時間に連続して読むだけなので、古い区画を素通りして消えていきます。

**PostgreSQL：時計の針を回す。** バッファごとに使用回数（`usage_count`）を持ち、アクセスされるたびに増やします。追い出すときは、時計の針のようにバッファを順に見ていき、使用回数が 0 なら追い出し、0 でなければ 1 減らして次へ進みます。これが **clock-sweep** で、LRU の近似です。使用回数の上限は 5 に抑えられています（[buf_internals.h](https://github.com/postgres/postgres/blob/master/src/include/storage/buf_internals.h)）。上限を大きくすると LRU に近づきますが、追い出す相手を見つけるまでに針が何周もする必要が出るためです。

```
       ┌──→ [usage 2] → 1 に減らして次へ
  針 ──┤    [usage 0] → これを追い出す
       └──  [usage 5] ...
```

さらに、大きなテーブルの全件走査では、共有のバッファプールを使わず、**小さな専用の区画を使い回す** ようになっています（[バッファ管理の README](https://github.com/postgres/postgres/blob/master/src/backend/storage/buffer/README)）。

<Callout type="tip" title="LRU の近似は、CPU もデータベースも同じ">
  第 15 回で、厳密な LRU は回路が大きくなるため CPU は近似を使うと書きました。
  データベースでも事情は同じで、アクセスのたびにリストを並べ替えると、
  それ自体が多数のスレッドの奪い合い（第 37 回）になります。
  **1 ビットや数ビットのカウンタで「最近使ったか」だけを覚える** という近似が、どの階層でも選ばれています。
</Callout>

## 書き込みは後回しにする

行を更新すると、バッファプール上のページが書き換わります。**この時点ではディスクに書きません**。ページに「変更された」という印を付けるだけです。これを **ダーティページ** と呼びます。

第 15 回のライトバック方式のキャッシュと同じ構造です。同じページを何度も更新しても、ディスクへの書き込みは最後の 1 回で済みます。

では、コミットしたのにデータのページがまだディスクに無い状態で電源が落ちたらどうなるのか。ここで先ほどのログが効きます。**変更内容はログに書かれ、ログは `fsync` 済み** なので、再起動時にログから復元できます。データのページは後でゆっくり書けばよいのです。

ただし、いつまでも書かずにいると、復元に必要なログが際限なく伸びます。そこで定期的に **チェックポイント** を取ります。

1. その時点のダーティページをすべてディスクに書き出す
2. 書き出しが終わったら「ここまでのログはもう不要」と記録する

チェックポイントの瞬間には大量の書き込みが集中します。**定期的に書き込みが詰まってレイテンシが跳ねる** 現象の典型的な原因です。各製品は、チェックポイントの書き出しを時間をかけて少しずつ行う仕組みを持っています。

<Callout type="warn" title="8KB は一度に書けるとは限らない">
  データベースのページは 8KB や 16KB ですが、OS やディスクが **途中で止まらずに書ける単位** はそれより小さいことがあります。
  書いている途中で電源が落ちると、**前半だけ新しく後半は古いページ**（torn page、ちぎれたページ）ができます。

  PostgreSQL はチェックポイント後に初めて変更するページの全体をログに書き（`full_page_writes`）、
  InnoDB はデータファイルに書く前に別の領域にも書いておく（doublewrite buffer）ことで、これに備えています。
  ディスクの書き込みの単位と原子性は、第 50 回と第 52 回で扱った話です。
</Callout>

## 手元で確かめる

PostgreSQL なら、1 つのクエリが何枚のページに触ったかを `EXPLAIN` で見られます。

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM t WHERE id = 50000;
--  Index Scan using t_pkey on t
--    Index Cond: (id = 50000)
--    Buffers: shared hit=3
```

`shared hit=3` は、バッファプールで 3 ページ見つかったという意味です（`read` と出れば、バッファプールに無くてファイルから読んだ）。10 万行の中から 1 行を取り出すのに、**索引の 2 ページとテーブルの 1 ページ** で済んでいます。

```sql
CREATE EXTENSION pg_buffercache;
SELECT count(*) FROM pg_buffercache b
  JOIN pg_class c ON b.relfilenode = pg_relation_filenode(c.oid)
  WHERE c.relname = 't';
```

こちらは、テーブル `t` のページがいまバッファプールに何枚載っているかを数えます。

性能の議論で「このクエリは遅い」と言うとき、見るべきは多くの場合 **触ったページの枚数と、そのうち何枚がメモリに無かったか** です。第 14 回の桁の表のとおり、メモリに無いページを 1 枚読むだけで、メモリ上の処理の何百倍もかかるからです。

## まとめ

- データベースはファイルを固定長のページ（PostgreSQL は 8KB、InnoDB は 16KB）の並びとして扱う
- ページの中は、先頭から伸びる行ポインタと、末尾から詰める行。行はページ番号と行ポインタの番号の組で呼ぶ
- 間接参照を挟むので、ページの中で行を動かしても外からの呼び名は変わらない
- 書き出しの順序と追い出す相手を自分で決めるために、バッファプールを持つ
- InnoDB は `O_DIRECT` で OS のキャッシュを迂回し、PostgreSQL は OS のキャッシュを 2 段目として使う
- 全件走査に強い置き換え方式（途中への差し込み、clock-sweep）が使われる
- 変更はダーティページとして溜め、ログで守り、チェックポイントで書き出す

次は、このページの上に B+tree を載せたとき、**主キーの索引とそれ以外の索引で何が違うのか** を見ます。
