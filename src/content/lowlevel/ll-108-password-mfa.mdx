## 知っていることは、本人の証拠になるか

第 107 回で、認証の要素には知識・所有・生体の 3 種類があると見ました。いちばん古く、いまも最も多く使われているのが**知識**、つまりパスワードです。

パスワードによる認証が示しているのは、厳密には「**この文字列を知っている誰かが、いま入力した**」ということだけです。本人しか知らないはずだ、という前提の上に成り立っています。この前提は、次の 3 つの経路で崩れます。

- **サーバから漏れる。** 保存してあったパスワードのデータベースが盗まれる
- **ほかのサイトから漏れる。** 同じパスワードを使い回していれば、どこか 1 つの漏洩が全部に効く
- **利用者から聞き出される。** 偽のログイン画面に入力させる（フィッシング）

この回では、1 つ目をパスワードの保存方法で、2 つ目を漏洩パスワードの照合で、3 つ目を多要素認証で防ごうとした歴史を順に見ます。そして、**3 つ目を本当に防げたのは、第 97 回の署名と第 77 回のオリジンを組み合わせた WebAuthn だけだった**ことを確かめます。

## パスワードをどう保存するか

サーバは、利用者が入力したパスワードが登録時と同じかどうかを確かめられればよく、**パスワードそのものを持っている必要はありません**。そこで、一方向の関数を通した値だけを保存し、ログインのたびに同じ関数を通して比べます。

ここで第 94 回のハッシュ関数を思い出すと、SHA-256 を使えばよさそうに見えます。原像耐性があるので、ハッシュ値からパスワードは戻せません。しかし、これは**パスワードの保存には使えません**。理由は 2 つあります。

1 つ目は、**同じパスワードが同じ値になる**ことです。`password123` の SHA-256 は、どのサイトで計算しても同じです。よく使われるパスワードのハッシュ値を前もって計算した表を作っておけば、盗んだデータベースを表と突き合わせるだけで済みます。そこで利用者ごとに異なる乱数（**ソルト**）を混ぜてから計算し、ソルトはハッシュ値と一緒に保存します。ソルトは秘密ではありません。役目は、**前もって作った表を使えなくし、1 人ずつ別々に総当たりさせること**です。

2 つ目が本質的な問題で、**SHA-256 は速すぎる**ことです。ハッシュ関数は大きなファイルを素早く処理するために設計されています。パスワードは人間が覚えられる程度の長さしかなく、候補の数は限られています。攻撃者は盗んだソルトとハッシュ値を手元に持ち帰り、自分の計算機で好きなだけ試せます（オフライン攻撃）。1 回の計算が速いほど、1 秒あたりに試せる候補が増えます。

手元の Mac（Python 3.14、cryptography 48）で、1 回の計算にかかる時間を比べました。

```
SHA-256                                0.0004 ms/回       2,456,912 回/秒
PBKDF2-HMAC-SHA256 600,000            76.0703 ms/回              13 回/秒
scrypt N=2^17 r=8 p=1                352.4710 ms/回               3 回/秒
Argon2id m=19MiB t=2 p=1             127.6729 ms/回               8 回/秒
```

SHA-256 は CPU の 1 コアで毎秒 200 万回を超えます。GPU を使えばさらに桁が上がります。一方、下の 3 つは**わざと遅くした**関数で、1 回に 0.1 秒前後かかります。ログインする本人にとっては気にならない待ち時間ですが、総当たりする側にとっては 10 万倍以上の差になります。

### 遅いだけでなく、メモリも食う関数

計算を遅くするだけなら、SHA-256 を何十万回も繰り返せば足ります。PBKDF2 はその考え方で、HMAC を指定した回数だけ繰り返します。しかし、繰り返すだけの計算は GPU や専用回路（ASIC）で**並列に**安く実行できます。

そこで scrypt と Argon2 は、計算の途中で**大きなメモリを確保して、あちこち読み書きする**ように作られています。1 回の計算に数十 MiB が要ると、GPU の数千のコアを同時に動かすだけのメモリが足りなくなり、並列化の利点が薄れます。これを**メモリハード**と呼びます。

OWASP の Password Storage Cheat Sheet は、執筆時点（2026 年 9 月）で次の設定を最低限として挙げています（[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)）。

| 方式 | 推奨の設定（どれか 1 つ） | 備考 |
| --- | --- | --- |
| **Argon2id**（第一の選択） | m=19 MiB, t=2, p=1 など 5 通り | m（メモリ）と t（繰り返し）の交換で同等の強さ |
| scrypt | N=2^17（128 MiB）, r=8, p=1 など | Argon2id が使えないとき |
| bcrypt | 作業係数（cost）10 以上 | **入力は 72 バイトまで** |
| PBKDF2 | HMAC-SHA256 で 600,000 回、HMAC-SHA512 で 220,000 回 | FIPS 140 の認定が必要なとき |

Argon2id の結果は、方式・版・パラメータ・ソルト・ハッシュ値を 1 行にまとめた文字列（PHC 形式）で保存するのが普通です。

```
$argon2id$v=19$m=19456,t=2,p=1$tlXGjd9NOC1tTN2bgDqSKw$nK+wBVUbbcU8MWzyI436kbdz5JvkJIx2wYpFGKt7je0
```

パラメータが値の中に書いてあるので、後で強い設定に変えても、古い利用者の値はそのまま検証でき、次のログインのときに新しい設定で作り直せます。

第 99 回で見た鍵導出と同じ関数（PBKDF2、scrypt、Argon2）が出てきますが、用途が違います。第 99 回ではパスワードから**暗号の鍵を作る**ために使い、ここでは**パスワードを確かめるための値を保存する**ために使っています。どちらも「推測しやすい入力から、総当たりしにくい出力を作る」点が共通しています。

<Callout type="warn" title="よくある誤解: 「パスワードは暗号化して保存している」">
  暗号化は、鍵があれば元に戻せる変換です（第 95 回）。パスワードを暗号化して保存すると、
  **データベースと鍵が一緒に盗まれた時点で全員分の平文が戻ります**。鍵は同じサーバの設定やメモリにあることが多く、別々に守るのは困難です。
  逆に「ハッシュ化しているから安全」も不十分で、SHA-256 を 1 回通しただけなら、上で見たとおり毎秒数百万回の総当たりを許します。
  正しくは「**利用者ごとのソルトを付けて、遅くメモリを食うパスワード用の関数で**ハッシュ化する」です。
  NIST も、ソルトを 32 ビット以上とし、適切なパスワードハッシュ方式で保存することを求めています（[SP 800-63B-4 3.1.1.2](https://pages.nist.gov/800-63-4/sp800-63b.html)）。
</Callout>

### bcrypt の 72 バイト

bcrypt は 1999 年からある方式で、いまも広く使われていますが、**入力の 73 バイト目以降を無視する**という制限があります。長いパスワードの末尾を変えても、同じ値になります。

これはパスワードの保存以外の用途で事故になりました。Okta は、AD/LDAP 連携の認証結果のキャッシュのキーを「ユーザ ID + ユーザ名 + パスワード」を連結した文字列の bcrypt で作っていました。ユーザ名が 52 文字以上あると、パスワードの部分が 72 バイトの外にはみ出し、**以前に成功した認証のキャッシュを使って、パスワードを確かめずにログインできる**場合がありました（2024 年 7 月〜10 月、[Okta のセキュリティ勧告](https://trust.okta.com/security-advisories/okta-ad-ldap-delegated-authentication-username/)）。修正で、方式は PBKDF2 に替えられています。

最近のライブラリは黙って切り捨てなくなっています。Python の bcrypt 5.0.0 で 72 バイトを超える入力を渡すと、例外になりました（[pyca/bcrypt](https://github.com/pyca/bcrypt)）。

```
ValueError: password cannot be longer than 72 bytes, truncate manually if necessary (e.g. my_password[:72])
```

UTF-8 の日本語は 1 文字 3 バイトなので、24 文字で上限に届きます。新しく作るなら Argon2id を選べば、この制限を気にする必要はありません。

<Callout type="note" title="ペッパー">
  ソルトに加えて、全利用者で共通の秘密の値（**ペッパー**）を混ぜる方法もあります。ペッパーはデータベースとは別の場所（秘密情報の管理サービスや HSM、第 99 回）に置きます。
  データベースだけが盗まれた場合には、総当たりの出発点すら与えません（[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)）。
  その代わり、ペッパーを失うと全員のパスワードが検証できなくなり、替えるのも簡単ではありません。
</Callout>

## 利用者に何を求めるか: NIST SP 800-63B-4

保存方法はサーバの側の話でした。では、利用者にどんなパスワードを作らせるべきでしょうか。米国の NIST が認証の指針として出している SP 800-63B は、2025 年 7 月に第 4 版（**SP 800-63B-4**）が最終版になり、2020 年の版を置き換えました（[NIST CSRC](https://csrc.nist.gov/pubs/sp/800/63/b/4/final)）。パスワードについての要点は次のとおりです（[SP 800-63B-4 3.1.1.2](https://pages.nist.gov/800-63-4/sp800-63b.html)）。

| 項目 | SP 800-63B-4 の要求 |
| --- | --- |
| 最小の長さ | パスワードだけで認証するなら 15 文字、多要素の一部なら 8 文字 |
| 最大の長さ | 少なくとも 64 文字まで受け付けるべき（SHOULD） |
| 文字種の組み合わせ | 「英大文字・数字・記号を含めること」のような規則を**課してはならない**（SHALL NOT） |
| 定期的な変更 | **強制してはならない**。漏洩の証拠があるときだけ変更させる |
| 禁止リスト | よく使われるもの、推測しやすいもの、**漏洩したもの**の一覧と照合しなければならない（SHALL） |
| ヒントや秘密の質問 | 使わせてはならない |
| 試行回数 | 連続した失敗は 100 回までに制限する（3.2.2） |

<Callout type="warn" title="よくある誤解: 記号を必須にし、90 日ごとに変えさせると強くなる">
  直感に反しますが、NIST はどちらも禁止しています。
  文字種の規則を課すと、利用者は `Password1!` のような予測しやすい形に落ち着きます。定期変更を強制すると、`Password2!`、`Password3!` と末尾だけ変えます。
  攻撃者はこの癖を知っているので、候補の順番をそれに合わせるだけです。
  **強さを決めるのは長さと、既知の一覧に載っていないこと**であり、そのために長さの下限と禁止リストとの照合が求められています。
</Callout>

## 使い回しを突かれる: クレデンシャルスタッフィング

保存を正しくしても、利用者が**ほかのサイトと同じパスワード**を使っていれば、そのサイトからの漏洩で破られます。どこかで漏れたユーザ名とパスワードの組を、別のサイトのログイン画面に機械的に試していく攻撃を**クレデンシャルスタッフィング**と呼びます（[OWASP Credential Stuffing Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet.html)）。1 つのアカウントに多数の候補を試す総当たりとは違い、1 アカウントあたり 1 回しか試さないので、試行回数の制限にかかりません。

この攻撃に対して、パスワードの保存方法は何の役にも立ちません。**攻撃者はすでに正しいパスワードを持っている**からです。防ぐ手段は、NIST の禁止リストのように漏洩済みのパスワードを登録させないことと、パスワード以外の要素を足すことです。

漏洩済みかどうかの照合を、パスワードを外部に渡さずに行う方法があります。Have I Been Pwned の Pwned Passwords は、パスワードの SHA-1 の**先頭 5 文字だけ**を受け取り、その 5 文字で始まるハッシュ値の残りの部分と出現回数を全部返します（[HIBP API v3](https://haveibeenpwned.com/API/v3)）。一致するかどうかは手元で判定するので、サービス側にはどのパスワードを調べたかが分かりません。これを **k-匿名性**と呼びます。

```python
h = hashlib.sha1(pw.encode()).hexdigest().upper()
prefix, suffix = h[:5], h[5:]
body = urlopen(f"https://api.pwnedpasswords.com/range/{prefix}").read().decode()
```

```
password123                   CBFDA 1972 件の候補 -> 2266543 回
correct horse battery staple  ABF7A 2012 件の候補 -> 391 回
```

執筆時点の値です。2 つ目は漫画で「長くて覚えやすいパスワード」の例として有名になった文字列で、有名になったこと自体によって一覧に載っています。**長さは必要条件であって、十分条件ではありません**。

## 2 つ目の要素: ワンタイムパスワード

パスワードだけでは使い回しとフィッシングに弱いので、「**持っているもの**」を足すのが多要素認証です。最も広く使われているのが、スマートフォンの認証アプリが表示する 6 桁の数字、**TOTP**（Time-based One-Time Password）です。

### HOTP: カウンタの HMAC

TOTP の土台は **HOTP**（[RFC 4226](https://www.rfc-editor.org/rfc/rfc4226.html)）で、中身は第 94 回の HMAC そのものです。

```
登録時: サーバと端末が秘密の鍵 K を共有する（QR コードで渡す）

HOTP(K, C):
  mac    = HMAC-SHA1(K, C を 8 バイトのビッグエンディアンにしたもの)   ← 20 バイト
  offset = mac の最後のバイトの下位 4 ビット                           ← 0〜15
  code   = mac[offset .. offset+3] を整数にし、最上位ビットを落とす       ← 31 ビット
  結果   = code mod 10^6                                              ← 6 桁
```

offset で 4 バイトを選ぶ手順を「動的な切り詰め」と呼びます（[RFC 4226 5.3](https://www.rfc-editor.org/rfc/rfc4226.html#section-5.3)）。20 バイトの MAC を、人が打ち込める 6 桁に縮めるためのものです。

### TOTP: カウンタの代わりに時刻

HOTP のカウンタ C は、押すたびに 1 増やします。端末とサーバで数がずれると困るので、**TOTP は C を時刻から計算します**（[RFC 6238 4](https://www.rfc-editor.org/rfc/rfc6238.html#section-4)）。

```
C = floor((現在の Unix 時刻 − T0) / X)      T0 = 0、X = 30 秒が既定
```

30 秒ごとに C が 1 つ進み、数字が変わります。第 139 回で詳しく見る**時計のずれ**が、そのまま認証の失敗になります。RFC は、ネットワークの遅延を考えて**1 つ前の時間枠まで**受け付けることを勧めています（[RFC 6238 5.2](https://www.rfc-editor.org/rfc/rfc6238.html#section-5.2)）。

### 手元で確かめる: TOTP を 15 行で

```python
import hmac, hashlib, struct

def hotp(key: bytes, counter: int, digits: int = 6, algo=hashlib.sha1) -> str:
    mac = hmac.new(key, struct.pack(">Q", counter), algo).digest()
    offset = mac[-1] & 0x0F
    code = struct.unpack(">I", mac[offset:offset + 4])[0] & 0x7FFFFFFF
    return str(code % 10**digits).zfill(digits)

def totp(key: bytes, t: float, step: int = 30, digits: int = 6, algo=hashlib.sha1) -> str:
    return hotp(key, int(t) // step, digits, algo)
```

RFC 6238 の付録 B にあるテストベクタ（鍵は ASCII の `12345678901234567890`、8 桁、SHA-1）と照合します。

```
          59  94287082  OK
  1111111109  07081804  OK
  1111111111  14050471  OK
  1234567890  89005924  OK
  2000000000  69279037  OK
 20000000000  65353130  OK
```

認証アプリが読む QR コードの中の鍵は Base32 で書かれています。同じ鍵を Base32 にして、OATH Toolkit 2.6.12 の `oathtool` と同じ時刻で比べると、一致しました。`-w 1` は次の時間枠の値も出す指定です。

```
$ oathtool --totp -b --now="..." -w 1 GEZDGNBVGY3TQOJQGEZDGNBVGY3TQOJQ
662172
165451
$ python3 -c "import totp; ..."      # 同じ時刻と 30 秒後
662172
165451
```

### TOTP が保証しないもの

TOTP は HMAC なので、第 94 回で見た MAC の性質をそのまま引き継ぎます。

- **サーバも同じ鍵 K を持っている。** パスワードと違って一方向の関数では保存できません。検証のたびに HMAC を計算するので、K を取り出せる形で持つ必要があります。サーバから K が漏れれば、攻撃者は好きなときに正しい数字を作れます
- **6 桁は 100 万通りしかない。** 試行回数を制限しなければ当てられます（[RFC 4226 7.3](https://www.rfc-editor.org/rfc/rfc4226.html#section-7.3)）
- **数字はどのサイトに入力されたかを知らない。** これが最大の弱点です

## 多要素でも破られる: 中継されるフィッシング

TOTP の数字は 30 秒ほどで使えなくなります。盗んでも後から使えないので、フィッシングに強いように見えます。しかし、攻撃者が**その場で中継**すれば 30 秒で十分です。

```
利用者 ──→ 偽サイト（攻撃者のプロキシ） ──→ 本物のサイト
  ID/パスワード入力  ─────────→ そのまま転送
  TOTP の 6 桁入力   ─────────→ そのまま転送   → ログイン成功
                    ←───────── セッション Cookie を受け取り、攻撃者が保持
```

偽サイトは本物のログイン画面をそのまま中継して見せるので、利用者には区別がつきません。本物のサイトから見れば、**正しいパスワードと正しい 6 桁が届いた**だけです。攻撃者はログイン後のセッション Cookie（第 109 回）を手に入れ、以後は認証を飛ばしてアカウントを使えます。Microsoft は 2022 年に、この「中間者型（AiTM）」のフィッシングで 1 万以上の組織が狙われたと報告しており、中継を自動化する道具も公開されています（[Microsoft Security Blog](https://www.microsoft.com/en-us/security/blog/2022/07/12/from-cookie-theft-to-bec-attackers-use-aitm-phishing-sites-as-entry-point-to-further-financial-fraud/)）。

ほかの方式も同じ構造の弱さを持っています。

- **SMS で届くコード。** 中継されるのは TOTP と同じです。加えて、電話番号そのものが奪われることがあります。NIST は電話網（PSTN）による方式を「制限付き」とし、SIM の交換や番号の移転などの兆候を確かめるよう求めています（[SP 800-63B-4 3.1.3.3](https://pages.nist.gov/800-63-4/sp800-63b.html)）
- **プッシュ通知で「承認」を押す方式。** 攻撃者がパスワードを入手していれば、承認の通知を何十回も送りつけ、利用者がうっかり、あるいはうるさくなって押すのを待てます（**MFA 疲労攻撃**）。米国の CISA は、画面の数字をアプリに打ち込ませる**番号照合**を、フィッシング耐性のある方式に移行するまでの暫定策として勧めています（[CISA](https://www.cisa.gov/sites/default/files/publications/fact-sheet-implement-number-matching-in-mfa-applications-508c.pdf)）

<Callout type="warn" title="よくある誤解: 多要素認証を入れればフィッシングは防げる">
  多要素認証が防ぐのは、主に**パスワードだけが漏れた場合**、つまり使い回しやデータベースの漏洩です。
  利用者がその場で偽サイトにパスワードと 6 桁を入力するなら、要素がいくつあっても中継されます。
  NIST は、手で打ち込む方式（OTP や SMS のコード）は**フィッシング耐性があるとみなしてはならない**と明記しています（[SP 800-63B-4 3.2.5](https://pages.nist.gov/800-63-4/sp800-63b.html)）。
  足りないのは要素の数ではなく、**認証の応答が「どのサイトに向けたものか」を含んでいること**です。
</Callout>

## フィッシング耐性: WebAuthn

中継に負けない方式は、利用者の注意力に頼らず、**認証の応答そのものに相手の名前を結びつける**必要があります。NIST はこれをフィッシング耐性の定義としています（同 3.2.5）。この条件を満たし、広く使えるのが W3C の **WebAuthn** と、FIDO Alliance の CTAP を合わせた **FIDO2** です。WebAuthn は 2026 年 8 月 25 日に Level 3 が W3C 勧告になりました（[W3C](https://www.w3.org/news/2026/web-authentication-an-api-for-accessing-public-key-credentials-level-3-is-now-a-w3c-recommendation/)）。

仕組みは、第 97 回の署名です。

- **登録。** 端末（認証器）が、そのサイト専用の鍵ペアを新しく作ります。公開鍵だけをサイトに登録し、秘密鍵は端末に残します。鍵ペアは **RP ID**（通常はサイトのドメイン名、例: `example.com`）に結びつけて保管されます
- **ログイン。** サイトが乱数の challenge を送り、端末が秘密鍵で署名して返します。サイトは登録済みの公開鍵で検証します

署名される中身が要点です（[WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/)）。

```
clientDataJSON（ブラウザが作る）
  {"type":"webauthn.get", "challenge":"...", "origin":"https://example.com", ...}

authenticatorData（認証器が作る）
  rpIdHash (32 バイト = SHA-256("example.com")) | flags (UP, UV, BE, BS ...) | signCount

署名 = Sign(秘密鍵, authenticatorData ‖ SHA-256(clientDataJSON))
```

**origin を書き込むのはブラウザ**で、ページの JavaScript ではありません。第 77 回で見たとおり、オリジンはブラウザがページごとに管理している値で、ページが偽ることはできません。さらにブラウザは、ページのオリジンが名乗れる RP ID を制限します。`https://examp1e.com` のページは、RP ID に `example.com` を指定できません（Level 3 には、所有者が明示的に許した別ドメインにだけ例外を認める仕組みがあります）。

中継を試みる偽サイトで何が起きるかを並べます。

| 偽サイトの試み | 結果 |
| --- | --- |
| 自分の RP ID `examp1e.com` で署名を頼む | その RP ID の鍵は端末にない。署名そのものが作られない |
| 本物の RP ID `example.com` を指定する | ブラウザが拒否する。オリジンと RP ID が合わない |
| 本物のサイトから取った challenge を見せる | origin に `https://examp1e.com` が書かれ、本物のサイトの検証で落ちる |
| 署名後に origin を書き換える | 署名が合わなくなる |

TOTP との違いは、**秘密が利用者の目と手を通らない**ことです。利用者が偽サイトに気づかなくても、ブラウザと認証器が機械的に相手を確かめます。

### 手元で確かめる: WebAuthn の模型

ブラウザと認証器とサイトを 1 つの Python ファイルに縮めた模型を作りました（cryptography 48 の ECDSA P-256）。本物の WebAuthn は CBOR という形式で符号化し、attestation などの手順もありますが、署名の対象と検証の順番は仕様のとおりにしています。要所だけ抜き出します。

```python
def browser_get(authn, page_origin, rp_id, challenge, allow_ids):
    host = page_origin.split("://")[1]
    if not (host == rp_id or host.endswith("." + rp_id)):
        raise PermissionError(f"origin {page_origin} は rpId {rp_id} を名乗れない")
    client_data = json.dumps({"type": "webauthn.get",
                              "challenge": challenge.hex(), "origin": page_origin}).encode()
    return (client_data, *authn.get_assertion(rp_id, allow_ids,
                                              hashlib.sha256(client_data).digest()))

def rp_verify(pub, expected_origin, rp_id, challenge, client_data, auth_data, sig):
    cd = json.loads(client_data)
    assert cd["challenge"] == challenge.hex(), "challenge が違う"
    assert cd["origin"] == expected_origin, f"origin が違う: {cd['origin']}"
    assert auth_data[:32] == hashlib.sha256(rp_id.encode()).digest(), "rpIdHash が違う"
    pub.verify(sig, auth_data + hashlib.sha256(client_data).digest(), ec.ECDSA(hashes.SHA256()))
    return "OK"
```

```
1. 本物のサイト              -> OK
2. 偽サイトが自分の rpId で   -> LookupError rpId=examp1e.com の鍵はない
3. 偽サイトが本物の rpId で   -> PermissionError origin https://examp1e.com は rpId example.com を名乗れない
4. clientDataJSON の origin を書き換え -> InvalidSignature
```

認証器の側は、RP ID ごとに鍵を引くだけです。**どのサイトかを判断しているのは人ではなく、ブラウザと鍵の表**だということが分かります。

### 部品の組み合わせ

WebAuthn は新しい暗号を発明していません。前の回までの部品を組み合わせたものです。

| 部品 | 担う役割 | 回 |
| --- | --- | --- |
| 署名（ECDSA、Ed25519） | 秘密鍵を持っていることを示す。サーバには公開鍵しか置かないので、漏れても困らない | 第 97 回 |
| ハッシュ | clientDataJSON と RP ID を固定長にして署名に含める | 第 94 回 |
| 暗号用の乱数 | challenge を毎回変え、署名の使い回し（リプレイ）を防ぐ | 第 99 回 |
| オリジン | 「どのサイトに向けた署名か」をブラウザが保証する | 第 77 回 |
| TLS | そのオリジンが本当にそのドメインであることを保証する | 第 16 章 |

最後の行が欠けると全体が崩れます。オリジン `https://example.com` が意味を持つのは、TLS と証明書（第 100〜103 回）がそのドメインの持ち主を確かめているからです。WebAuthn が安全な文脈（HTTPS）でしか使えないのはこのためです。

## パスキー: 同期する鍵と、しない鍵

**パスキー**は、WebAuthn の鍵ペアのうち、パスワードの代わりに単独でログインできるように作られたものの呼び名です。FIDO Alliance は 2 種類を区別しています（[FIDO Alliance](https://fidoalliance.org/passkeys/)）。

| 種類 | 秘密鍵の置き場所 | 利点 | 引き換えにするもの |
| --- | --- | --- | --- |
| 同期パスキー | クラウドの鍵管理（OS やパスワードマネージャ）を通じて利用者の端末間で同期 | 端末を替えても失わない | 秘密鍵が端末の外に出る。同期先のアカウントの強さに依存する |
| デバイス固定のパスキー | セキュリティキーなど 1 台の中から出ない | 秘密鍵を取り出せない（第 99 回の価値） | 紛失すると使えない。予備の登録が要る |

どちらもフィッシング耐性は同じです。署名の対象に origin が入る仕組みは、鍵の置き場所に関係しないからです。違いは**鍵そのものを盗まれる経路**のほうにあります。authenticatorData の BE（バックアップ可能）と BS（バックアップ済み）のフラグで、サイトはその鍵が同期される種類かどうかを知ることができます（[WebAuthn Level 3 6.1.3](https://www.w3.org/TR/webauthn-3/)）。NIST は、秘密鍵を書き出せる同期型の認証器を最も高い保証レベル AAL3 には使ってはならないとしています（[SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)）。

<Callout type="warn" title="よくある誤解: 顔や指紋がサーバに送られている">
  パスキーでログインするとき、指紋や顔で確かめるのは**端末の中だけ**です。
  生体情報は端末のロックを解き、秘密鍵を使ってよいかを決めるために使われ、サイトには「本人確認をした」という UV フラグが署名付きで届くだけです。
  サイトが受け取るのは署名であって、生体情報ではありません。
  逆に言えば、サイトから見て保証されているのは「**その鍵を持つ端末で、利用者が操作した**」ことまでで、誰の指だったかは分かりません。
</Callout>

## アカウント回復が最も弱い経路になる

ログインをパスキーにしても、アカウントの強さは**いちばん弱い入口**で決まります。端末をなくした利用者のために、メールや SMS に届くリンクだけでアカウントを取り戻せるようにしてあれば、攻撃者はパスキーを迂回してその経路を使います。

NIST の SP 800-63B-4 は、回復の方法を 4 つ（保存しておく回復コード、送付する回復コード、回復の連絡先、身元確認のやり直し）に分けて要件を定めています。たとえば保存用の回復コードは 64 ビット以上の乱数で作り、パスワードと同様にハッシュ化して保存し、使ったら無効にします。SMS で送るコードの有効期間は 10 分までです。そして、**回復が行われたら必ず利用者に通知する**ことを求めています。不正な回復に本人が気づけるようにするためです（[SP 800-63B-4 Account Recovery](https://pages.nist.gov/800-63-4/sp800-63b.html)）。

設計するときは、ログインの方式と回復の方式を**同じ表に並べて**、どちらが弱いかを確かめるのが確実です。パスキーと、秘密の質問で回復できる仕組みを併用していれば、そのアカウントの強さは秘密の質問と同じです。

## 認証の結果は、どこに残るか

ここまでの方式はすべて、**ログインの瞬間**に本人を確かめるものでした。第 107 回で見たとおり、HTTP はステートレスなので、その結果をセッション Cookie やトークンに残さないと、次のリクエストでは誰だか分からなくなります。

中継型のフィッシングが最終的に盗んでいたのは、このセッション Cookie でした。WebAuthn は中継そのものを失敗させるので、この経路は塞がります。しかし、利用者の端末に入り込んだマルウェアがブラウザから Cookie を直接盗む場合は、ログインの方式が何であっても防げません。**認証の強さと、認証の結果を運ぶものの強さは別の問題**で、後者は次の回で扱います。

## まとめ

- パスワードで示せるのは「この文字列を知っている誰かが入力した」ことだけ。サーバからの漏洩、使い回し、フィッシングの 3 つの経路で破られる
- パスワードは暗号化せず、利用者ごとのソルトを付けて、遅くメモリを食う関数（Argon2id を第一に、scrypt、bcrypt、PBKDF2）でハッシュ化して保存する。SHA-256 を 1 回通すだけでは速すぎる
- bcrypt は入力を 72 バイトまでしか見ない。パスワード以外の用途に流用して事故になった例がある
- NIST SP 800-63B-4（2025）は、文字種の規則と定期変更の強制を禁じ、長さの下限と漏洩パスワードとの照合を求める
- HOTP / TOTP は HMAC に 8 バイトのカウンタ（TOTP は 30 秒ごとの時刻）を入れて 6 桁に切り詰めたもの。サーバも鍵を持ち、時計のずれに弱い
- OTP、SMS、プッシュ通知は、その場で中継されるフィッシングに負ける。応答がどのサイトに向けたものかを含んでいないから
- WebAuthn は、サイトごとの鍵ペアで challenge と origin と RP ID に署名する。origin はブラウザが書き込み、TLS がその意味を支える。これがフィッシング耐性の中身
- パスキーには同期型とデバイス固定型があり、フィッシング耐性は同じで、鍵が盗まれる経路が違う
- アカウントの強さは最も弱い入口で決まる。回復の経路を必ず並べて確かめる

ログインの瞬間に本人を確かめても、その結果を覚えておく仕組みが弱ければ意味がありません。次の第 109 回では、認証の結果を運ぶセッションと Cookie を見ます。
