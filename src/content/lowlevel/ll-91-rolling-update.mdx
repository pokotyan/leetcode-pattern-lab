## 入れ替えの最中も、リクエストは来る

`api` の Pod が 4 個動いていて、新しい版に入れ替えたいとします。いちばん単純なのは、4 個を全部止めてから新しい 4 個を立てることです。その間、`api` は応答できません。

止めずに入れ替えるには、**古いものを少しずつ減らし、新しいものを少しずつ増やす**しかありません。

```
時間 →
古い版  ■■■■  ■■■□  ■■□□  ■□□□  □□□□
新しい版 □□□□  ■□□□  ■■□□  ■■■□  ■■■■
```

言葉にすると単純ですが、これを安全に行うには 3 つの問いに答える必要があります。

1. 新しい Pod は、**いつ**リクエストを受けてよいのか
2. 古い Pod は、**どういう順番で**止めればリクエストを落とさないのか
3. 一度に**何個まで**止めてよいのか

## Deployment は、2 つの ReplicaSet の数を調整する

入れ替えを行うのは Deployment のコントローラです。仕組みは第 86 回の調整ループそのものです。

Deployment は、Pod を直接は作りません。**ReplicaSet**（「このテンプレートの Pod を n 個」という宣言）を作り、その数を調整します。テンプレートを書き換えると、新しいテンプレートの ReplicaSet がもう 1 つ作られ、コントローラは 2 つの数を少しずつ動かします。

```
Deployment api（あるべき数 4、テンプレート v2）
   ├── ReplicaSet api-v1  4 → 3 → 2 → 1 → 0
   └── ReplicaSet api-v2  0 → 1 → 2 → 3 → 4
```

どれだけ速く動かすかは、2 つの値で決まります。どちらも既定は 25% です（[Kubernetes Docs](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/)）。

| 値 | 意味 | 4 個のとき |
| --- | --- | --- |
| `maxUnavailable` | あるべき数から、同時に何個まで欠けてよいか | 1 個まで欠けてよい（最低 3 個） |
| `maxSurge` | あるべき数を、同時に何個まで超えてよいか | 1 個まで多くてよい（最大 5 個） |

`maxSurge` を大きくすれば、先に新しい Pod を立ててから古いものを消すので、欠けずに済みます。ただし一時的に余分な資源（第 88 回の requests の分）が要ります。`maxUnavailable` を大きくすれば資源は要りませんが、その間は処理できる量が減ります。

古い ReplicaSet は、数を 0 にしたまま残ります。**戻すときは、古い ReplicaSet の数を増やし直すだけ**です。イメージを作り直す必要はありません。

ここで重要なのは、コントローラが「新しい Pod が 1 個増えた」と数えるのは、**Pod が作られたときではない**ということです。

## 準備ができたことを、誰が判定するのか

第 82 回で、Compose の `depends_on` は「プロセスを起動した」ことしか意味せず、「仕事を受けられる」ことは healthcheck で別に判定する必要がある、と見ました。Kubernetes でも同じ区別をします。判定の仕組みを **probe** と呼び、3 種類あります（[Kubernetes Docs](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)）。

| probe | 問い | 失敗したら |
| --- | --- | --- |
| **readiness** | いま、リクエストを受けてよいか | EndpointSlice から外される。コンテナは殺さない |
| **liveness** | このプロセスは、まだ生きていると言えるか | コンテナを再起動する |
| **startup** | 起動は終わったか | 終わるまで liveness を始めない。一定時間内に終わらなければ再起動 |

判定の手段は、コンテナの中でコマンドを実行する、HTTP の GET を送る、TCP で接続できるか試す、gRPC のヘルスチェックを呼ぶ、のいずれかです。いずれも実行するのは各ノードの kubelet です。

**readiness** が、前回の Service と直結しています。EndpointSlice に載るのは ready な Pod だけでした。つまり、**readiness に通るまでは、kube-proxy の書き換え規則の振り分け先に入らない**。そして Deployment のコントローラも、ready になった Pod だけを「使える 1 個」と数えます。新しい版が起動に失敗し続ければ、ready な Pod が増えないので、コントローラは古い Pod を減らしません。入れ替えは、そこで止まります。

<Callout type="warn" title="liveness で、相手の様子を調べてはいけない">
  liveness の失敗は**再起動**を意味します。
  「データベースに繋がるか」を liveness に入れると、データベースが 1 分止まっただけで、
  **それに繋ぐすべての Pod が一斉に再起動**します。再起動しても、データベースは直りません。
  それどころか、再起動の嵐がデータベースの回復を妨げます。前回のリトライストームと同じ形です。

  liveness が答えるべきなのは「**このプロセス自身が**詰まっていないか」だけです。
  第 39 回で見たデッドロックのように、外から見て動いているのに二度と応答しない状態を検出するのが本来の用途です。
  外部の依存が使えないなら、readiness で「今は受けられない」と答えます。
</Callout>

## 止め方の順番

新しい Pod の側は、readiness で守られています。問題は古い Pod の側です。

Pod を消すとき、何が起きるのかを順に追います。Kubernetes の文書に書かれている流れは次のとおりです（[Kubernetes Docs](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/#pod-termination-flow)）。

1. API サーバ上で、Pod に「終了中」の印と猶予期間が付く
2. その Pod のノードの kubelet が印に気づき、`preStop` フックがあれば実行する
3. kubelet がコンテナランタイムに、各コンテナの **PID 1 へ TERM シグナル**を送らせる
4. 猶予期間（`terminationGracePeriodSeconds`、既定 30 秒）が過ぎても残っていれば、KILL シグナルを送る

そして、文書にはもう 1 つ、見落とされやすい一文があります。

> At the same time as the kubelet is starting graceful shutdown of the Pod, the control plane evaluates whether to remove that shutting-down Pod from EndpointSlice objects

**kubelet が終了処理を始めるのと同時に**、コントロールプレーンは、この Pod を EndpointSlice から外す作業を始めます。2 つは**並行**です。順番の保証はありません。

### 並行であることの帰結

前回見たとおり、EndpointSlice から外されても、それだけでは何も起きません。**すべてのノードの kube-proxy が変化に気づき、それぞれのカーネルの規則を書き換え終わって**、初めて新しい接続がこの Pod に来なくなります。その時刻はノードごとにばらばらです。

```
時刻 →
Pod:        TERM を受ける → listen ソケットを閉じる → 終了
ノード A:   ───────── 規則を更新（もう来ない）
ノード B:   ──────────────────────── 規則を更新
                          ↑
            この間、ノード B からの新しい接続は、閉じたソケットに届く
            → 接続拒否（RST）
```

第 46 回のグレースフルシャットダウンの手順は、「TERM を受けたら、まず新しい接続の受付をやめる」でした。1 台のサーバならそれで正しいのですが、ここでは**受付をやめた後にも、まだ新しい接続が届きうる**のです。

対策は、**TERM を受けても、しばらくは普通に受け付け続ける**ことです。いちばん簡単なのは、`preStop` で数秒待つことです。

```yaml
lifecycle:
  preStop:
    sleep:
      seconds: 5     # この間に、各ノードの規則が更新されるのを待つ
```

`preStop` は TERM より前に実行されるので、この 5 秒の間、アプリは何も知らずに受け付け続けます。その間に振り分け先から外れ、5 秒後に TERM が届いたときには、新しい接続はもう来ません。`sleep` の動作は kubelet 自身が実行するので、第 79 回の distroless のようにシェルも `sleep` コマンドも入っていないイメージでも使えます（[Kubernetes Docs](https://kubernetes.io/docs/concepts/containers/container-lifecycle-hooks/)）。

`preStop` の時間も猶予期間に含まれることに注意します。`preStop` で 5 秒、処理中のリクエストを終えるのに 20 秒かかるなら、猶予期間はそれより長くなければなりません。

<Callout type="warn" title="TERM が、そもそも届いていない">
  入れ替えのたびに Pod がきっかり 30 秒かかって消えるなら、TERM が無視されている疑いがあります。
  第 78 回で見たとおり、PID 1 は既定の動作が効かない特別なプロセスで、
  shell 形式の `CMD` ではシェルが PID 1 になり、TERM をアプリに渡さないことがあります。
  kubelet は猶予期間いっぱい待ち、最後に KILL を送ります。
  処理中のリクエストは、後始末の機会なく切られます。
</Callout>

### 長く生きる接続を、閉じてもらう

もう 1 つの落とし穴は、前回見た**長く生きる接続**です。HTTP/2 や keep-alive の接続は、振り分け先から外れた後も、すでに張られている限りこの Pod に届き続けます。規則の書き換えは、新しい接続にしか効かないからです。

終了処理の中で、サーバは既存の接続に対して「この接続にはもう新しいリクエストを送らないでほしい」と伝える必要があります。HTTP/2 なら GOAWAY を送り、HTTP/1.1 なら応答に `Connection: close` を付けて閉じます。クライアントは次のリクエストのために接続を張り直し、そのときには新しい振り分けが効きます。

## 一度に、何個まで止めてよいか

ここまでは、Deployment が自分で入れ替える場合でした。しかし Pod が止まる理由は、ほかにもあります。

Kubernetes は、Pod の中断を 2 種類に分けます（[Kubernetes Docs](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/)）。

| 種類 | 例 | 防げるか |
| --- | --- | --- |
| **非自発的な中断** | ノードの故障、カーネルのパニック、ノードの資源不足による追い出し | 防げない。数を多めに持ち、別のノードに散らす |
| **自発的な中断** | ノードの保守のための退避（drain）、ノードの削減 | 誰かの操作なので、ペースを制御できる |

ノードの OS を更新するために、管理者がノードから Pod を退避させるとします。そのノードに `api` の Pod が 3 個とも載っていれば、`api` は全滅します。

これを防ぐのが **PodDisruptionBudget** です。「`app: api` の Pod は、自発的な中断で**最低 3 個は残すこと**」のように宣言します。

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api
spec:
  minAvailable: 3
  selector:
    matchLabels:
      app: api
```

ノードの退避は、Pod を直接消すのではなく、**Eviction API** を通して「この Pod を追い出してよいか」を API サーバに尋ねます。予算を割り込むなら、API サーバは断ります。退避の道具は待って再試行し、別のノードで新しい Pod が ready になって予算に余裕ができてから、次を追い出します。

ただし、この守りが効くのは Eviction API を通る操作だけです。文書にも、Deployment や Pod を直接消す操作は予算を無視すると書かれています。**PodDisruptionBudget は、他人の保守作業に対する約束**であって、自分の削除を止める仕組みではありません。

## 3 つの問いへの答え

冒頭の 3 つの問いに戻ります。

| 問い | 答えている仕組み |
| --- | --- |
| 新しい Pod は、いつ受けてよいか | readiness probe。通るまで EndpointSlice に載らず、Deployment も数えない |
| 古い Pod は、どういう順番で止めるか | EndpointSlice からの削除と終了処理は並行。preStop で待ち、TERM で既存の接続を閉じてもらう |
| 一度に何個まで止めてよいか | 自分の入れ替えは maxUnavailable / maxSurge、他人の保守は PodDisruptionBudget |

どれも、**「状態が変わったことが、分散した全員に行き渡るまでには時間がかかる」**という前提の上に立っています。1 台のサーバの終了処理にはなかった難しさは、すべてここから来ています。

## まとめ

- Deployment は、新旧 2 つの ReplicaSet の数を少しずつ動かして入れ替える。戻すときは古い方を増やし直すだけ
- 速さは maxUnavailable と maxSurge（既定はどちらも 25%）で決まる
- readiness は振り分け先に入れるか、liveness は再起動するか、startup は起動を待つか。liveness で外部の依存を調べない
- Pod の削除では、EndpointSlice からの削除と kubelet の終了処理が並行に進む。規則の更新はノードごとにばらばら
- preStop で数秒待ってから TERM を受けると、閉じたソケットに新しい接続が届く競合を避けられる
- 長く生きる接続は、GOAWAY や `Connection: close` で張り直してもらう
- PodDisruptionBudget は、Eviction API を通る自発的な中断にだけ効く

ここまでの Pod は、どれも入れ替えのきく、中に状態を持たないものでした。次は、入れ替えのきかない**状態を持つもの**を、どうやってこの仕組みに載せるのかを見ます。
