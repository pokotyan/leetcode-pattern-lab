## SPF は何を確かめているのか

第 58 回で、TXT レコードの用途の 1 つとして SPF を「このドメインを名乗ってメールを送ってよいサーバ」と紹介しました。この説明は間違いではありませんが、**「名乗る」とはどこで名乗ることなのか**を省いています。

第 139 回で見たとおり、1 通のメールには差出人が少なくとも 2 か所に書かれます。

```
SMTP の会話（エンベロープ）      MAIL FROM:<bounce-42@mailer.example.net>
メッセージのヘッダ              From: Example Bank <support@example.com>
```

利用者のメールソフトが表示するのは下の `From:` です。**SPF が確かめるのは上の MAIL FROM（と HELO）のドメイン**で、`From:` には一切触れません（[RFC 7208 2.2〜2.4](https://www.rfc-editor.org/rfc/rfc7208.html#section-2.2)）。これが SPF についての最大の誤解の出発点です。

なぜ `From:` を見ないのか。理由は設計の順番にあります。RFC 7208 は、SPF の検査を **MAIL コマンドを受け取った時点**で行うことを想定しています（[2.5](https://www.rfc-editor.org/rfc/rfc7208.html#section-2.5)）。第 141 回の会話で言えば、`MAIL FROM` の直後、`DATA` より前です。この時点では、受信側はまだ本文もヘッダも受け取っていません。**見ようにも `From:` がまだ届いていない**のです。

その代わり、SPF には「受け取る前に断れる」という利点があります。`MAIL FROM` の段階で `550` を返せば、本文を 1 バイトも受け取らずに済みます。

この回では、SPF の書式と評価の規則を読み、小さな評価器を書いて、何が pass になり何が壊れるのかを確かめます。

## 入力は 3 つだけ

SPF の評価は `check_host()` という関数として定義されています（[RFC 7208 4](https://www.rfc-editor.org/rfc/rfc7208.html#section-4)）。入力は次の 3 つです。

| 引数 | 中身 | どこから来るか |
| --- | --- | --- |
| `ip` | 接続してきた相手の IP アドレス | TCP の接続そのもの（第 53 回） |
| `domain` | SPF を引くドメイン | MAIL FROM の `@` より後ろ（または HELO の名前） |
| `sender` | MAIL FROM の全体 | マクロで使う（後述） |

注目してほしいのは `ip` です。MAIL FROM も HELO も、送信側が好きな文字列を書けます。しかし IP アドレスは、**TCP の 3 ウェイハンドシェイクを終えた相手のもの**です。偽の送信元アドレスでパケットを送ることはできても、SYN-ACK を受け取れなければ接続は確立しません。RFC 7208 も「接続元の IP は正しいと仮定する。現代の正しく構成されたシステムでは、これが崩れる危険は無いに等しい」としています（[11.3](https://www.rfc-editor.org/rfc/rfc7208.html#section-11.3)）。SPF はこの「偽りにくい 1 つの値」を、偽りやすい名前と突き合わせる仕組みです。

```
送信側が自由に書ける               偽りにくい
MAIL FROM: <x@example.com>   ×   接続元 IP 198.51.100.7
        │                                │
        └── example.com の TXT を引く ──→ この IP は一覧にあるか？
```

HELO についても、RFC 7208 は検査することを推奨しています（[2.3](https://www.rfc-editor.org/rfc/rfc7208.html#section-2.3)）。特に、第 141 回で見たバウンスの `MAIL FROM:<>` のように送信者が空のときは、`postmaster@<HELO の名前>` を MAIL FROM とみなして評価します（[2.4](https://www.rfc-editor.org/rfc/rfc7208.html#section-2.4)）。

## 書式: 項目を左から順に読む

SPF レコードは `v=spf1` で始まる TXT で、空白で区切った **項目**（term）を並べたものです。

```
example.com.  TXT  "v=spf1 ip4:192.0.2.0/24 include:_spf.mailer.example -all"
                    版     ─── 機構 ────  ─────── 機構 ──────────  機構
```

項目には 2 種類あります。**機構**（mechanism）は「この IP は当てはまるか」を判定するもので、**修飾子**（modifier）は `名前=値` の形で評価の仕方を変えるものです（[4.6.1](https://www.rfc-editor.org/rfc/rfc7208.html#section-4.6.1)）。

| 機構 | 当てはまる条件 | DNS を引くか |
| --- | --- | --- |
| `all` | 常に当てはまる | 引かない |
| `ip4:192.0.2.0/24` | IP がこの範囲にある | 引かない |
| `ip6:2001:db8::/32` | IP がこの範囲にある | 引かない |
| `a` / `a:host` | IP がそのドメイン（またはホスト）の A / AAAA のどれか | 引く |
| `mx` / `mx:host` | IP がそのドメインの MX のホストのアドレスのどれか | 引く（MX と、各ホストの A / AAAA） |
| `include:d` | `d` の SPF を評価した結果が pass | 引く |
| `exists:d` | `d` に A レコードが 1 つでもある | 引く |
| `ptr` | 逆引きが一致する | 引く。**使わない**（[5.5](https://www.rfc-editor.org/rfc/rfc7208.html#section-5.5) の見出しに「do not use」とある） |

| 修飾子 | 意味 |
| --- | --- |
| `redirect=d` | どの機構にも当てはまらなければ、`d` の SPF の結果をそのまま使う |
| `exp=d` | fail のときに相手へ返す説明文を `d` の TXT から取る |

評価は**左から順に行い、最初に当てはまった機構で終わります**。当てはまった機構の前に付いた記号が **限定子**（qualifier）で、これが結果を決めます（[4.6.2](https://www.rfc-editor.org/rfc/rfc7208.html#section-4.6.2)）。

| 限定子 | 結果 | 省略したとき |
| --- | --- | --- |
| `+` | pass | 限定子を書かなければ `+` |
| `-` | fail | |
| `~` | softfail | |
| `?` | neutral | |

最後に置く `-all` や `~all` は、「ここまでのどれにも当てはまらなかったら」という既定の答えです。`all` は常に当てはまるので、**`all` より右に書いた機構は評価されません**。どの機構にも当てはまらず `redirect` もなければ、結果は neutral です（[4.7](https://www.rfc-editor.org/rfc/rfc7208.html#section-4.7)）。

<Callout type="note" title="exists とマクロ">
  `exists:` はマクロと組み合わせて使います。たとえば `exists:%{i}._spf.corp.example` は、接続元の IP を名前に埋め込んで A を引きます。
  答えがあれば当てはまるので、許可する IP の一覧を DNS サーバの側で動的に持てます。
  執筆時点（2026 年 9 月）で、`salesforce.com` の SPF はこの形の `exists:` を使っています。
  便利な反面、M3AAWG はマクロと `exists` を「専門家以外は避けるべき」としています（[Best Practices for Managing SPF Records, 2017](https://www.m3aawg.org/documents/en/m3aawg-best-practices-for-managing-spf-records) 4.1）。
</Callout>

## 7 つの結果

`check_host()` が返す結果は 7 つです（[2.6](https://www.rfc-editor.org/rfc/rfc7208.html#section-2.6)）。

| 結果 | 意味 | RFC が示す扱い（[8](https://www.rfc-editor.org/rfc/rfc7208.html#section-8)） |
| --- | --- | --- |
| pass | このドメインを名乗ってよいと明示された | 評判の上で、このドメインが送信の責任を持つとみなせる |
| fail | 名乗ってはいけないと明示された | 断るなら `550 5.7.1` |
| softfail | 「たぶん許可していない」という弱い表明 | これだけを理由に断るべきではない（SHOULD NOT） |
| neutral | 許可するともしないとも言わない | none と**まったく同じに**扱わなければならない（MUST） |
| none | SPF が無い、またはドメインが取り出せない | |
| temperror | DNS の一時的な失敗 | 後で再試行すれば変わりうる。断るなら `451 4.4.3` |
| permerror | レコードが解釈できない | DNS の管理者が直すまで変わらない。断るなら `550 5.5.2` |

大事なのは、RFC 7208 が**結果ごとの扱いを義務として決めていない**ことです。2.6 は「特定の結果の扱いについて規範的な要求は定めない」と書き、fail の扱いも「受信側の方針の問題」としています（[8.4](https://www.rfc-editor.org/rfc/rfc7208.html#section-8.4)）。SPF は「送信側の表明」を受信側に届ける仕組みで、それをどう使うかは受信側が決めます。

## include は「貼り込み」ではない

`include:` という名前からは、相手のレコードの中身をその場に貼り込むように見えます。実際の動きは違います（[5.2](https://www.rfc-editor.org/rfc/rfc7208.html#section-5.2)）。

```
example.com          v=spf1 ip4:192.0.2.0/24 include:_spf.mailer.example -all
_spf.mailer.example  v=spf1 ip4:198.51.100.0/24 -all
```

IP が `203.0.113.5` のとき、`include:_spf.mailer.example` の先を評価すると、`-all` に当たって fail になります。しかし、この fail で全体が終わるわけでは**ありません**。include の先の結果は、次の表のとおり「当てはまった / 当てはまらなかった」に読み替えられるだけです。

| include 先の結果 | include という機構は |
| --- | --- |
| pass | 当てはまる |
| fail、softfail、neutral | 当てはまらない（次の項目へ進む） |
| temperror | temperror を返す |
| permerror | permerror を返す |
| none | **permerror** を返す |

RFC 自身が「振り返れば include という名前はまずい選び方だった。if-match や on-match のほうがよかった」と書いています。include の先の `-all` は、「私の一覧に無い」と言っているだけです。

最後の行にも注意してください。**include 先に SPF が無いと、自分のドメインの評価全体が permerror になります**。契約をやめた配信サービスの SPF が消えたのに、自分の include を消し忘れると、そこから先のすべてのメールの評価が壊れます。

`redirect=` は、include と違って「どこにも当てはまらなければ、あちらの結果をそのまま自分の結果にする」ものです。同じ組織の中で複数のドメインに同じ方針を当てるためにあります（[6.1](https://www.rfc-editor.org/rfc/rfc7208.html#section-6.1)）。`gmail.com` の SPF は `v=spf1 redirect=_spf.google.com` の 1 項目だけです。

<Callout type="warn" title="よくある誤解: SPF が pass なら差出人は本物">
  SPF の pass が言っているのは、「MAIL FROM に書かれたドメインの管理者が、この IP を許可している」ことだけです。
  攻撃者が自分で `attacker.example` を取り、自分のサーバを SPF に書き、`MAIL FROM:<x@attacker.example>` で送れば、SPF は **pass** になります。
  そのうえで本文のヘッダに `From: support@example.com` と書いても、SPF はそれを見ません。
  RFC 7208 もこの点を明記し、「利用者やメールソフトが、認証された名前と `From:` が違うことに気づかなければ、誤った安心感を与えうる」としています（[11.2](https://www.rfc-editor.org/rfc/rfc7208.html#section-11.2)）。
  2 つを結びつけるのは SPF ではなく、第 147 回の DMARC です。
</Callout>

## DNS の問い合わせ 10 回の上限

第 58 回の Callout で触れた上限を、正確に読んでおきます（[4.6.4](https://www.rfc-editor.org/rfc/rfc7208.html#section-4.6.4)）。

- `include`、`a`、`mx`、`ptr`、`exists`、`redirect` の **6 種類の項目**を、評価全体で**合計 10 個まで**に制限しなければならない（MUST）。超えたら permerror
- `all`、`ip4`、`ip6`、`exp` は数えない
- `mx` は、それとは別に、1 つの `mx` から引く A / AAAA が 10 個を超えたら permerror
- 答えが空だった問い合わせ（名前はあるがレコードが無い、または名前が存在しない）を **void lookup** と呼び、**2 回まで**にすべき（SHOULD）。超えたら permerror

数えるのは「問い合わせの回数」というより「DNS を使う項目の数」です。そして、**include の先で使われた項目も合算されます**。自分のレコードには include が 3 つしかなくても、その先がさらに include を持っていれば、数は増えていきます。

なぜこんなに小さな数なのか。RFC 7208 は、SPF の検査が **DNS の増幅攻撃の道具**になることを理由に挙げています（[11.1](https://www.rfc-editor.org/rfc/rfc7208.html#section-11.1)）。攻撃者が自分のドメインに `a:victim.example a:foo.victim.example ...` と並べた SPF を置き、その MAIL FROM で世界中のメールサーバに送れば、受信側の検査がいっせいに被害者の DNS へ問い合わせます。名前が存在しなくても攻撃は成り立つので、void lookup にも別の上限が要ります。数 KB の SMTP で何十倍もの DNS の負荷を生めないように、上限は「1 台のサーバとしては妥当に見える値より、かなり低く」決められています。

<Callout type="warn" title="よくある誤解: SPF レコードを 2 つに分ければ上限を回避できる">
  1 つのドメインに `v=spf1` で始まる TXT が 2 つあると、評価は **permerror** になります（[4.5](https://www.rfc-editor.org/rfc/rfc7208.html#section-4.5)）。
  足し合わされることはありません。配信サービスごとの手順書に従って「SPF を追加」した結果、2 行目の `v=spf1` ができてしまう事故はよくあります。
  1 行が 255 バイトを超えるなら、1 つの TXT の中に文字列を複数並べます。受信側は**空白を入れずに**連結します（[3.3](https://www.rfc-editor.org/rfc/rfc7208.html#section-3.3)）。
</Callout>

## 手元で確かめる: SPF の評価器の模型

ここまでの規則を Python で書いてみます。`ptr`、マクロの大半（`%{i}` と `%{d}` 以外）、`a` と `mx` の `/24` のような範囲指定は省きました。DNS の引き方は関数として外から渡すので、偽のゾーンでも本物の DNS でも同じ評価器が使えます。

```python
import ipaddress

class PermError(Exception): pass
class TempError(Exception): pass

QUAL = {'+': 'pass', '-': 'fail', '~': 'softfail', '?': 'neutral'}

class Checker:
    def __init__(self, lookup):
        self.lookup = lookup          # (名前, 型) -> 文字列のリスト。無ければ []
        self.terms = 0                # DNS を使った項目の数
        self.voids = 0                # 答えが空だった問い合わせの数

    def count(self, term):
        self.terms += 1
        if self.terms > 10:
            raise PermError('DNS を使う項目が 10 を超えた')

    def dns(self, name, rtype):
        ans = self.lookup(name, rtype)
        if not ans:
            self.voids += 1
            if self.voids > 2:
                raise PermError('void lookup が 2 を超えた')
        return ans

    def check_host(self, ip, domain):
        recs = [r for r in self.lookup(domain, 'TXT')
                if r == 'v=spf1' or r.startswith('v=spf1 ')]
        if not recs:
            return 'none'
        if len(recs) > 1:
            raise PermError(f'{domain} に SPF が 2 つある')
        redirect = None
        for t in recs[0].split()[1:]:
            if t.startswith('redirect='):
                redirect = t[len('redirect='):]
                continue
            if '=' in t:              # exp= など、評価に関わらない修飾子
                continue
            q = t[0] if t[0] in QUAL else '+'
            if self.match(ip, domain, t.lstrip('+-~?')):
                return QUAL[q]
        if redirect:
            self.count(f'redirect={redirect}')
            r = self.check_host(ip, redirect)
            if r == 'none':
                raise PermError(f'redirect 先 {redirect} に SPF が無い')
            return r
        return 'neutral'

    def match(self, ip, domain, term):
        name, _, arg = term.partition(':')
        if name == 'all':
            return True
        if name in ('ip4', 'ip6'):
            return ip in ipaddress.ip_network(arg, strict=False)
        if name == 'include':
            self.count(term)
            r = self.check_host(ip, arg)
            if r == 'none':
                raise PermError(f'include 先 {arg} に SPF が無い')
            return r == 'pass'
        if name == 'a':
            self.count(term)
            return ip in self.addrs(arg or domain, ip)
        if name == 'mx':
            self.count(term)
            hosts = self.dns(arg or domain, 'MX')
            if len(hosts) > 10:
                raise PermError('MX が 10 を超えた')
            return any(ip in self.addrs(h, ip) for h in hosts)
        if name == 'exists':
            self.count(term)
            target = arg.replace('%{i}', str(ip)).replace('%{d}', domain)
            return bool(self.dns(target, 'A'))
        raise PermError(f'この模型が扱わない項目: {term}')

    def addrs(self, host, ip):
        rtype = 'A' if ip.version == 4 else 'AAAA'
        return [ipaddress.ip_address(x) for x in self.dns(host, rtype)]
```

include の先で起きた permerror や temperror は、例外としてそのまま外へ伝わります。include の表の下 3 行は、この書き方で自然に満たされます。

### 偽のゾーンで 11 通り

まず、辞書で作った偽のゾーン（アドレスは文書用の `192.0.2.0/24` などを使います）で、結果を 1 つずつ出してみます。ゾーンの中身は次のとおりです。

```
example.com          v=spf1 ip4:192.0.2.0/24 include:_spf.mailer.example -all
_spf.mailer.example  v=spf1 ip4:198.51.100.0/24 -all
soft.example         v=spf1 ip4:192.0.2.0/24 ~all
two.example          v=spf1 ip4:192.0.2.0/24 -all   と   v=spf1 -all   の 2 つ
broken.example       v=spf1 include:gone.example -all        （gone.example には何も無い）
void.example         v=spf1 a:x.void.example a:y.void.example a:z.void.example -all
deep.example         v=spf1 include:i1.example -all          （i1 → i2 → … → i11 と入れ子）
forwarder.example    v=spf1 ip4:203.0.113.0/24 -all
```

実行結果です。

```
192.0.2.10    example.com        項目  0  void 0  pass  # 自社のサーバ
198.51.100.7  example.com        項目  1  void 0  pass  # 配信サービス（include 先）
203.0.113.5   example.com        項目  1  void 0  fail  # 無関係なサーバ
203.0.113.5   soft.example       項目  0  void 0  softfail  # ~all のドメイン
203.0.113.5   nospf.example      項目  0  void 0  none  # SPF が無いドメイン
192.0.2.10    two.example        項目  0  void 0  permerror（two.example に SPF が 2 つある）  # SPF が 2 つ
192.0.2.10    broken.example     項目  1  void 0  permerror（include 先 gone.example に SPF が無い）  # include 先が消えた
192.0.2.10    void.example       項目  3  void 3  permerror（void lookup が 2 を超えた）  # 存在しない名前を 3 回
192.0.2.10    deep.example       項目 11  void 0  permerror（DNS を使う項目が 10 を超えた）  # include の入れ子 11 段
203.0.113.99  example.com        項目  1  void 0  fail  # 転送（MAIL FROM はそのまま）
203.0.113.99  forwarder.example  項目  0  void 0  pass  # 転送（SRS で MAIL FROM を書き換え）
```

いくつか読み取れることがあります。

- 1 行目は DNS を使う項目を 1 つも数えていません。`ip4` で先に当たれば、後ろの include は評価されないからです。**安い項目を左に置く**と、上限にも問い合わせの時間にも効きます（RFC 7208 [10.1.1](https://www.rfc-editor.org/rfc/rfc7208.html#section-10.1.1) も同じことを勧めています）
- 3 行目で、include 先の `-all` は全体を終わらせず、外側の `-all` が fail を出しています
- `broken.example` と `deep.example` は、**IP が正しくても permerror** です。レコードの誤りは、正規のメールも巻き込みます
- 最後の 2 行は後の「転送」の節で使います

### 本物の DNS で数える

次に、同じ評価器に dnspython（作業ディレクトリの venv に入れた 2.8.0）で引いた本物の答えを渡します。`lookup` の中身を差し替えるだけで、TXT が複数の文字列に分かれていれば `b''.join(r.strings)` で空白なしに連結します。NXDOMAIN と「答えが空」は `[]`、タイムアウトは `TempError` にしました。

執筆時点（2026 年 9 月）の `github.com` の SPF は次のとおりです。

```
$ dig TXT github.com +noall +answer | grep spf1
github.com. 300 IN TXT "v=spf1 ip4:192.30.252.0/22 include:spf.protection.outlook.com
  include:_netblocks.google.com include:_netblocks2.google.com include:mail.zendesk.com
  include:_spf.salesforce.com include:servers.mcsv.net include:mktomail.com
  include:sendgrid.net ip4:62.253.2" "27.114 ip4:166.78.69.169 ... ~all"
```

（読みやすさのために折り返しました。）2 つの文字列の境目が `ip4:62.253.2" "27.114` と、**IP アドレスの途中**にあります。空白を入れて連結する実装では `ip4:62.253.2` と `27.114` に割れて、壊れたレコードとして読まれます。3.3 の「空白を入れずに」が効いている実例です。

どこにも当てはまらない IP（`203.0.113.5`）で評価すると、すべての項目をたどることになります。入れ子の深さを字下げで示すと、次のようになりました。

```
 1 include:spf.protection.outlook.com
 2 include:_netblocks.google.com
 3 include:_netblocks2.google.com
 4 include:mail.zendesk.com
 5 include:_spf.salesforce.com
 6   exists:%{i}._spf.mta.salesforce.com
 7 include:servers.mcsv.net
 8 include:mktomail.com
 9 include:sendgrid.net
10   include:ab.sendgrid.net
=> softfail  (DNS を使った項目 10, void 1)
```

**ちょうど 10 です**。`github.com` 自身が書いた include は 8 つですが、Salesforce の先の `exists` と、SendGrid の先の `include:ab.sendgrid.net` で 2 つ増えています。void の 1 回は、`203.0.113.5._spf.mta.salesforce.com` が存在しなかった分です。

ここで大事なのは、この 10 が **github.com の管理者の手の外で変わりうる**ことです。SendGrid や Salesforce が自分のレコードに include を 1 つ足せば、github.com は何も変えていないのに 11 になり、末尾まで評価が進む IP については permerror になります。同じ評価器で `microsoft.com` は 7、`salesforce.com` は 4、`gmail.com` は `redirect` の 1 でした。

<Callout type="note" title="上限はレコードの全体ではなく、たどった道筋で数える">
  RFC 7208 の上限は、実際の評価で使った項目の数です。`192.30.252.1` で評価すると、先頭の `ip4` で pass になり、数は 0 のままでした。
  つまり上限を超えたレコードでも、**左のほうで当たる送信元だけは pass し続けます**。自社のサーバでは問題が見えず、特定の配信サービスから送ったメールだけが permerror になる、という分かりにくい壊れ方をします。
  SPF の検査サービスの多くが、すべての include を先まで数えて警告するのはこのためです。
</Callout>

## 上限を超えたら: フラット化の是非

上限の対策としてよく勧められるのが **SPF のフラット化**です。include の先を事前にすべてたどって IP アドレスの一覧にし、`ip4:` と `ip6:` だけのレコードに書き直します。`ip4` と `ip6` は数えないので、上限の問題は消えます。

しかし、失うものがあります。RFC 7208 は include を「管理の境界を越えるためのもの」と説明しています（[5.2](https://www.rfc-editor.org/rfc/rfc7208.html#section-5.2)）。include を使うのは、**配信サービスの IP アドレスの一覧を、配信サービス自身に管理させる**ためです。フラット化すると、その一覧の写しを自分が持つことになります。

| | include のまま | フラット化 |
| --- | --- | --- |
| 上限 | 相手の構成次第で超える | 超えない |
| 相手が IP を足したとき | 自動で反映される | 写しを更新するまで、新しい IP からのメールが fail |
| 相手が IP を手放したとき | 自動で外れる | 写しに残り、その IP の次の持ち主に許可を与え続ける |
| 問い合わせの回数 | 多い | 少ない |
| レコードの大きさ | 小さい | 大きくなり、255 バイトの分割や 512 バイトの目安（[3.4](https://www.rfc-editor.org/rfc/rfc7208.html#section-3.4)）に近づく |

フラット化した写しを定期的に自動で作り直す仕組みを持てるなら、選択肢になります。持てないなら、先に次の手を考えるほうが安全です。

- **使っていない include を消す。** 契約が終わったサービスの include は、上限を食うだけでなく、そのサービスの利用者全員に自分のドメインを名乗らせる穴になります
- **送信の用途ごとにサブドメインを分ける。** 配信サービスが MAIL FROM に `bounce.example.com` のような専用のドメインを使えるなら、SPF はそのドメインごとに別々に数えられます（第 150 回で扱います）
- **`a` と `mx` を `ip4` と `ip6` に置き換える。** M3AAWG は、`a` と `mx` を必要がない限り使わないよう勧めています（[2017](https://www.m3aawg.org/documents/en/m3aawg-best-practices-for-managing-spf-records) 4.1）

最後に、1 行目の穴の話を補っておきます。M3AAWG は、大きな共有の基盤を include するときには「その基盤の利用者全員に、自分のドメインを名乗る許可を与えてしまいうる」と注意しています（同 4.1）。SPF の pass は「その IP から来た」ことしか言わないので、同じ IP を他の顧客と共有していれば、区別はできません。

## 転送で SPF が壊れる理由と SRS

`alice@example.com` が `bob@school.example` にメールを送り、bob がそれを `bob@home.example` へ自動転送しているとします。

```
[example.com のサーバ]  ──→  [school.example]  ──→  [home.example]
 IP 192.0.2.10                 IP 203.0.113.99        SPF を検査する
 MAIL FROM:<alice@example.com>  MAIL FROM:<alice@example.com>  ← そのまま
```

home.example が見る接続元は、転送した school.example の `203.0.113.99` です。しかし MAIL FROM は alice のまま `example.com` なので、example.com の SPF を引き、そこに `203.0.113.99` は無いので **fail** になります。偽のゾーンの 10 行目がこれでした。

これは SPF の欠陥というより、**SPF の定義どおりの結果**です。school.example は example.com の許可を得ずに、example.com を名乗って送っています。第 139 回で見たとおり、転送ではエンベロープの宛先だけが書き換わり、送信者はそのまま残るのが普通でした。

RFC 7208 の付録 D は、転送する側（mediator）の対策として、**MAIL FROM を自分のドメインに書き換える**ことを挙げています（[D.2](https://www.rfc-editor.org/rfc/rfc7208.html#appendix-D.2)）。そうすれば、検査されるのは転送する側の SPF になります。偽のゾーンの 11 行目がこれで、pass になりました。

ただし書き換えると、転送の先で届かなかったときのバウンスが元の送信者に戻らなくなります。そこで、**元の送信者を書き換えた後のアドレスに埋め込み、バウンスが来たら取り出して戻す**方式が作られました。これが **SRS**（Sender Rewriting Scheme）です。SRS は RFC ではなく、2004 年に Shevek が公開した文書と実装（[The Sender Rewriting Scheme](https://www.libsrs2.net/srs/srs.pdf)）が元になっています。

Microsoft 365 は外部への自動転送で SRS を使っており、書き換えの例を公開しています（[Microsoft Learn](https://learn.microsoft.com/en-us/exchange/reference/sender-rewriting-scheme)）。

| | 元のメール | 転送されたメール |
| --- | --- | --- |
| MAIL FROM | `bob@fabrikam.com` | `john.work+SRS=44ldt=IX=fabrikam.com=bob@contoso.com` |
| From: | `bob@fabrikam.com` | `bob@fabrikam.com` |

`44ldt` はハッシュ、`IX` は時刻で、第三者が勝手に SRS のアドレスを作って転送する側を踏み台にできないようにしています。同じページは、**SRS で SPF は pass しても、DMARC は pass しない**と注意しています。`From:` は `fabrikam.com` のままで、SPF で認証されたのは `contoso.com` だからです。転送で DMARC を通すには、`From:` のドメインの DKIM 署名が壊れずに届く必要があります（第 146 回、第 147 回）。

## -all と ~all は結局どちらがよいのか

`-all`（fail）のほうが強く、`~all`（softfail）は弱い、と言われます。RFC 7208 の定義としてはそのとおりです。しかし実際の扱いは、受信側と、次の DMARC との組み合わせで決まります。

M3AAWG は「ほとんどの受信側は `~all` と `-all` を同じように扱うが、`-all` のときに認証されないメールを断りやすい受信側もある」と書いています（[2017](https://www.m3aawg.org/documents/en/m3aawg-best-practices-for-managing-spf-records) 3）。

さらに、2026 年 5 月に RFC 7489 を置き換えて標準化の道に乗った DMARC の新しい仕様 [RFC 9989](https://www.rfc-editor.org/rfc/rfc9989.html) は、`-all` の副作用を具体的に書いています（[7.1](https://www.rfc-editor.org/rfc/rfc9989.html#section-7.1)）。

- SPF は SMTP の早い段階で評価されるので、DMARC を評価する前に SPF の fail だけで断る受信側がありうる
- そうなると、SPF は fail でも、**揃った DKIM で DMARC を pass できたはずのメール**（たとえば上の転送されたメール）まで断られる
- `MAIL FROM` の段階で断られたメールは `DATA` に進まないので、`From:` のドメインが分からず、**DMARC の集計報告にも現れない**

<Callout type="warn" title="よくある誤解: -all にすれば、なりすましは確実に断られる">
  `-all` は「断ってよい」という送信側の表明で、断るかどうかは受信側が決めます（RFC 7208 8.4）。
  そして SPF が守っているのは MAIL FROM だけなので、`-all` にしても `From:` の偽装は止まりません。
  逆に、`-all` は転送された正規のメールを DMARC の評価より前に落とし、その事実を報告からも消すことがあります。
  利用者が見る差出人を守りたいなら、効くのは SPF の最後の 1 文字ではなく、DKIM を揃えたうえでの DMARC の方針です。
</Callout>

メールを一切送らないドメインには、`v=spf1 -all` だけを置くのが定石です（[RFC 7208 10.1.2](https://www.rfc-editor.org/rfc/rfc7208.html#section-10.1.2)）。送信に使われない `www.example.com` やキャンペーン用のドメインを、MAIL FROM に使われにくくできます。

受信側は SPF の結果を `Received-SPF` や `Authentication-Results` のヘッダに書き残します（[RFC 7208 9](https://www.rfc-editor.org/rfc/rfc7208.html#section-9)）。そこには `envelope-from=` や `smtp.mailfrom=` と書かれ、**ヘッダ自身が、検査したのは `From:` ではないと言っています**。読み方は第 150 回でまとめて扱います。

## SPF は何と組み合わさって意味を持つか

| 部品 | 役目 | 見た回 |
| --- | --- | --- |
| TCP の接続 | 接続元 IP が偽りにくいこと | 第 53 回 |
| SMTP のエンベロープ | MAIL FROM と HELO という、検査される名前 | 第 139 回、第 141 回 |
| DNS の TXT | 許可の一覧を置く場所 | 第 58 回 |
| DNS のキャッシュと TTL | include 先の変更がいつ効くか | 第 60 回 |
| DNSSEC | 一覧そのものが偽られていないこと。無ければ偽の答えで pass を作れる（[RFC 7208 11.3](https://www.rfc-editor.org/rfc/rfc7208.html#section-11.3)） | 第 61 回 |
| DKIM | 転送で壊れにくい、もう 1 つの認証 | 第 146 回 |
| DMARC | 認証されたドメインと `From:` を結びつける | 第 147 回 |

SPF 単体は、「このドメインの管理者は、この IP を知っている」としか言いません。利用者が見る差出人を守る話になるのは、DMARC と組み合わさったときです。

## まとめ

- SPF が確かめるのは **MAIL FROM（と HELO）のドメイン**で、利用者が見る `From:` ではない。検査は `DATA` より前に行う想定なので、そもそも `From:` はまだ届いていない
- 入力は接続元 IP、ドメイン、送信者の 3 つ。偽りにくい IP を、偽りやすい名前と突き合わせる
- 項目は左から評価し、最初に当たった機構の限定子（`+ - ~ ?`）が結果になる。結果は pass、fail、softfail、neutral、none、temperror、permerror の 7 つで、扱いは受信側が決める
- include は貼り込みではなく「先が pass なら当たる」。先の `-all` は全体を終わらせないが、先に SPF が無いと permerror
- DNS を使う項目は include の先も含めて合計 10 個まで、void lookup は 2 回まで。DNS の増幅攻撃を防ぐための低い上限で、**配信サービスの側の変更で自分のレコードが上限を超える**ことがある
- フラット化は上限を消すが、配信サービスの IP の管理を自分が引き受けることになる。まず不要な include を消し、送信用のサブドメインを分ける
- 転送では MAIL FROM が元のままなので SPF は fail する。SRS で書き換えれば SPF は pass するが、DMARC は `From:` と揃わないので pass しない
- `-all` と `~all` の実際の差は小さく、`-all` は DMARC より前に正規の転送メールを落とすことがある

SPF は「どこから来たか」を確かめる仕組みで、転送のように経路が変わると壊れます。次の第 146 回では、経路ではなく**メッセージそのものに署名を付ける** DKIM を見ます。署名が保証するのは何で、`From:` とはどう関係するのでしょうか。
