## 1 行が 3 命令

2 つのスレッドが、共有のカウンタを 100 万回ずつ増やします。

```c
counter++;
```

結果は 200 万になるはずです。実際にやると、190 万や 150 万といった値になります。

理由は、この 1 行が機械語では 3 命令だからです。

```asm
mov  eax, [counter]      ; 読む
add  eax, 1              ; 足す
mov  [counter], eax      ; 書く
```

2 つのスレッドがこう並ぶと、

```
スレッド A: 読む (10)
スレッド B: 読む (10)
スレッド A: 足す (11)
スレッド B: 足す (11)
スレッド A: 書く (11)
スレッド B: 書く (11)     ← 2 回増やしたのに 11
```

**片方の更新が消えます。** これが **データ競合** です。

複数のスレッドが同じデータにアクセスし、少なくとも一方が書き込みで、同期が取られていない。この 3 条件が揃うと競合が起きます。

<Callout type="warn" title="再現しないのが最悪の性質">
  タイミング次第なので、100 万回に 1 回しか起きないことがあります。
  テストでは通り、本番の高負荷時にだけ壊れる。
  デバッガを付けると再現しない（タイミングが変わるため）。
  **最も追いにくいバグの類型**です。
</Callout>

## アトミック操作

「読んで、足して、書く」を**分割不可能な 1 つの操作**として実行できれば、割り込まれません。CPU にはそのための命令があります。

```asm
lock add [counter], 1        ; x86。lock プレフィックスで排他を保証する
```

高級言語からも使えます。

```c
// C11
#include <stdatomic.h>
atomic_int counter;
atomic_fetch_add(&counter, 1);

// C++
std::atomic<int> counter;
counter++;
```

代表的なアトミック操作です。

| 操作 | 内容 |
| --- | --- |
| `fetch_add` | 読んで足して書く。元の値を返す |
| `exchange` | 値を入れ替える。元の値を返す |
| **`compare_exchange`（CAS）** | **「期待値と一致したら書き換える」を分割不可能に行う** |

**CAS**（Compare-And-Swap）が最も重要です。これがあれば、任意の更新処理をロックなしで書けます。

```c
int old, new;
do {
    old = atomic_load(&value);
    new = f(old);                    // 好きな計算
} while (!atomic_compare_exchange_weak(&value, &old, new));
```

「読んで、計算して、その間に誰も変えていなければ書く。変わっていたらやり直す」というループです。**楽観的並行制御**の基本形で、データベースの実装にも同じ構造が出てきます。

<Callout type="note" title="アトミックでも安くはない">
  `lock` 付き命令は、キャッシュラインを排他的に確保する必要があるため、
  通常の命令の数十倍のコストがかかります（20〜100 サイクル程度）。
  さらに複数のコアが同じ変数を更新すると、キャッシュラインの奪い合いになり、
  **スレッドを増やすほど遅くなる**ことがあります。

  カウンタをスレッドごとに分散し、読むときだけ合計する（シャーディング）のが定石です。
</Callout>

## ミューテックス

アトミック操作で守れるのは、1 つの変数への単純な操作だけです。複数の変数にまたがる処理には、**排他区間**が必要です。

```c
pthread_mutex_lock(&m);
    // ここは 1 つのスレッドしか入れない
    balance_a -= 100;
    balance_b += 100;
pthread_mutex_unlock(&m);
```

実装は、素朴には「アトミックにフラグを立てられたら入る、立てられなければ待つ」です。

待ち方が問題になります。

- **スピン**：ひたすら確認し続ける。短い待ちなら速いが、長いと CPU を無駄にする
- **休止**：OS に「この条件が満たされたら起こして」と頼んで寝る。切り替えのコストがかかる

Linux の **futex**（fast userspace mutex）は、両方を組み合わせます。

> **競合がないときはユーザ空間だけで完結し、システムコールを呼ばない。**
> **競合したときだけカーネルに入って待つ。**

ロックが空いていれば、アトミック命令 1 つで取得できます。ほとんどの場合は競合しないので、これで大半のコストが消えます。

## ロックの種類

| 種類 | 用途 |
| --- | --- |
| **ミューテックス** | 基本の排他 |
| **再帰ミューテックス** | 同じスレッドが多重に取れる |
| **読み書きロック** | 読みは同時に複数可、書きは排他 |
| **スピンロック** | 極めて短い区間。カーネル内部で使われる |
| **セマフォ** | n 個まで同時に入れる |
| **条件変数** | 「ある条件が成立するまで待つ」 |

**読み書きロック**は、読みが圧倒的に多い場合に有効です。ただし、書き手が飢える（読み手が絶えず来ると書けない）問題や、状態の管理コストが増える問題があり、常に得とは限りません。

**条件変数**は、ミューテックスと組で使います。

```c
pthread_mutex_lock(&m);
while (!condition) {                       // if ではなく while
    pthread_cond_wait(&cond, &m);          // ロックを解放して待つ。起きたら再取得
}
// condition が成立している
pthread_mutex_unlock(&m);
```

`while` を使うのは、**偽の起床**（spurious wakeup）があるためです。条件が成立していないのに起こされることがあるので、起きたら必ず再確認します。

## メモリの見え方

ここからが本当に厄介な部分です。

第 12 回で見たとおり、CPU は命令の順番を入れ替えます。コンパイラも最適化で入れ替えます。シングルスレッドでは辻褄が合うように調整されますが、**他のスレッドからは入れ替わって見えます**。

```c
// スレッド A
data = 42;
ready = 1;

// スレッド B
if (ready) {
    print(data);       // 42 とは限らない
}
```

`data` への書き込みと `ready` への書き込みは無関係なので、順番が入れ替わることがあります。B から見ると、`ready` が 1 なのに `data` がまだ古い、という状態がありえます。

<Callout type="warn" title="volatile では解決しない">
  C / C++ の `volatile` は「最適化で読み書きを消すな」という指示であって、
  **順序の保証でも、アトミック性の保証でもありません**。
  マルチスレッドの同期に `volatile` を使うのは誤りです。
  （Java の `volatile` は別物で、こちらは順序の保証を含みます。）
</Callout>

## メモリバリア

順序を強制する命令が **メモリバリア**（メモリフェンス）です。

```c
data = 42;
atomic_thread_fence(memory_order_release);    // これより前の書き込みを先に見せる
ready = 1;
```

実際には、アトミック変数に順序指定を付けるのが一般的です。

| 順序指定 | 意味 |
| --- | --- |
| `relaxed` | アトミック性だけ。順序の保証なし |
| `acquire` | これ以降の読み書きが、これより前に移動しない |
| `release` | これより前の読み書きが、これ以降に移動しない |
| `acq_rel` | 両方 |
| `seq_cst` | 全スレッドで一貫した順序。最も強く、最も高価。**既定値** |

`release` で書き、`acquire` で読む組み合わせが基本です。書いた側の「それ以前のすべての書き込み」が、読んだ側から見えることが保証されます。

<Callout type="tip" title="既定のままで大抵よい">
  `seq_cst` は最も遅いですが、最も直感に合います。
  ここを緩めて得られる性能は、正しく使えた場合でも限定的で、
  **間違えたときの結果は極めて追いにくい**。
  プロファイルで明確にボトルネックだと分かるまで、既定のままにしておくのが賢明です。
</Callout>

## アーキテクチャによる差

メモリの順序をどこまで保証するかは、CPU によって違います。

| アーキテクチャ | 順序の強さ |
| --- | --- |
| **x86 / x86-64** | 強い（TSO）。書き込み後の読み込みの入れ替えだけが起きる |
| **ARM / RISC-V / POWER** | 弱い。ほぼ自由に入れ替わる |

**これが移植時の罠になります。** x86 で動いていた同期のバグが、ARM で顕在化する。Apple Silicon への移行時に、この種の問題が数多く報告されました。

「x86 で動いたから正しい」とは言えません。規格が保証する範囲で書く必要があります。

## 検出する

```bash
gcc -fsanitize=thread -g foo.c && ./a.out
```

ThreadSanitizer は、実行時にメモリアクセスを監視し、同期なしの共有アクセスを検出します。実際に競合が起きなくても、**起こりうる**ことを検出できます。

```
WARNING: ThreadSanitizer: data race
  Write of size 4 at 0x... by thread T2:
  Previous read of size 4 at 0x... by thread T1:
```

速度は 5〜15 倍遅くなりますが、この種のバグを見つける手段としては最も確実です。

## 最善の対策

競合を安全に扱う技術を学ぶことも大事ですが、より効果的なのは**そもそも共有しない**ことです。

- **不変にする**：書き換えなければ競合しない
- **所有権を明確にする**：あるデータは 1 つのスレッドだけが触る
- **メッセージで渡す**：共有せず、コピーを送る（Go のチャネル、Erlang のメッセージ）
- **スレッドローカルにする**：各スレッドが自分のぶんを持ち、最後に集計する

Rust の型システムは、この方針をコンパイル時に強制します。所有権と借用の規則により、**データ競合はコンパイルエラーになります**。

## まとめ

- `counter++` は 3 命令。割り込まれると更新が消える
- アトミック操作は分割不可能。CAS があれば任意の更新をロックなしで書ける
- アトミックも安くない。キャッシュラインの奪い合いになる
- ミューテックスは排他区間を作る。futex は競合しないときシステムコールを避ける
- CPU とコンパイラは順序を入れ替える。他スレッドからは見える
- `volatile` は同期の道具ではない。メモリ順序の指定を使う
- x86 は順序が強く、ARM は弱い。移植で顕在化する
- 最善の対策は共有しないこと
