## 部品は揃った。では、どう組まれているのか

第 94 回から、部品を 1 つずつ開いてきました。署名、証明書、TLS、SSH、セッション、JWT、OAuth、OIDC、IdP、ワークロードの ID。どの回でも「この部品は単独では何を保証しないか」を確かめました。

実際のシステムでは、これらは**必ず複数が組み合わさって**使われます。そして事故の多くは、部品そのものではなく、**ある部品が保証していると思い込んでいたことを、実は別の部品が（あるいは誰も）保証していなかった**ところで起きます。

この回では、よく見る構成を 10 の型に分け、それぞれを同じ 3 つの問いで読みます。

1. **誰の、何を確かめているか**。サーバの鍵か、クライアントの鍵か、利用者か、委任された権限か
2. **証はどこにあるか**。ログインの結果を表すもの（セッション ID、トークン、証明書）が、どの機械のどこに置かれ、盗まれたら何ができるか
3. **境界はどこか**。どこから先を「検証済み」として信じているか。その前提が崩れる経路はあるか

各型には、図と「部品と保証」の表と、弱点を置きます。読むときは、区別を 2 つ意識してください。**相手の鍵と相手の人は別**です。TLS や SSH のホスト鍵が確かめるのは「この秘密鍵を持つ者がいる」ことまでです（第 105 回、第 106 回）。そして**機械の ID と利用者の ID も別**です。サービス間の 1 つのリクエストには、「どのサービスが」（第 120 回）と「誰のために」の 2 つが同時に乗ります。

## 型 1: 従来型の Web アプリ（サーバ側セッション + OIDC）

```
ブラウザ ──(1) /login──▶ アプリ ──(2) 認可リクエスト（リダイレクト）──▶ IdP
   │                        ▲                                             │
   │                        └──(3) code ──(4) code + client 認証 ──▶ ID トークン
   │
   └──(5) 以後は Cookie: sid=... だけを送る
             アプリは sid → セッションの保存先（利用者 = iss + sub）を引く
```

サーバが HTML を組み立てる、最も古くからある型です。ログインのときだけ OIDC（第 113 回）で IdP に利用者を確かめてもらい、**その結果をアプリ自身のセッションに写し取って**、以後は第 110 回のサーバ側セッションで動きます。

| 部品 | 何を保証しているか | 回 |
| --- | --- | --- |
| TLS とサーバ証明書 | ブラウザが話しているのが本物のアプリであること | 第 104 回 |
| 認可コード + state + PKCE | 戻ってきた code が、このブラウザが始めたログインのものであること | 第 112 回 |
| ID トークン（署名、iss、aud、nonce） | IdP がこのアプリ宛てに「この利用者がログインした」と言ったこと | 第 113 回 |
| セッション Cookie（`__Host-`、HttpOnly、Secure、SameSite） | 以後のリクエストが、そのログインをしたブラウザから来ていること | 第 110 回 |
| サーバ側のセッションの保存先 | セッションをいつでも取り消せること | 第 110 回 |
| アプリの認可 | その利用者に、そのデータを見せてよいこと | 第 115 回 |

**弱点**は、第 110 回で見た Cookie の弱点そのものです。CSRF（SameSite と CSRF トークンで防ぐ）、XSS による「その場での悪用」、セッション固定。一方で、トークンはブラウザに一切出ないので、持ち出される対象はセッション ID だけで、それもサーバ側ですぐ取り消せます。**この型は古いのではなく、ブラウザで一番守りやすい形**です。次の型 2 は、SPA にこの性質を取り戻すためのものです。

<Callout type="warn" title="よくある誤解: ID トークンの期限がセッションの期限">
  ID トークンは「ログインした瞬間」の証明で、アプリはそれを検証したらセッションに写して役目を終えます。
  ID トークンの `exp` が 5 分でも、アプリのセッションは 8 時間続くことがありますし、その逆もあります。**セッションの寿命はアプリが自分で決めて持つ**もので（第 110 回のアイドルタイムアウトと絶対タイムアウト）、IdP 側のセッションとも別です。
  この「IdP とのセッション」と「アプリとのセッション」の 2 段が、SSO のログアウトを難しくしている原因でした（第 116 回）。
</Callout>

## 型 2: SPA + BFF

```
ブラウザ（SPA） ──Cookie: sid──▶ BFF ──Authorization: Bearer AT──▶ API
                                   │
                                   └── OAuth の機密クライアント。AT と RT はここに置く
```

画面は JavaScript の SPA でも、**OAuth の処理とトークンの保管はサーバ側の BFF（Backend for Frontend）が行う**型です。ブラウザが持つのは BFF とのセッション Cookie だけで、BFF はリクエストを受けるたびにセッションからアクセストークンを取り出し、API へ中継します（[RFC 10017 6.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1)）。形の上では、**型 1 のサーバ側セッションを、API の中継役に置き直したもの**です。

| 部品 | 何を保証しているか | 回 |
| --- | --- | --- |
| BFF の機密クライアントとしての認証 | トークンを受け取るのが登録された BFF であること | 第 112 回 |
| セッション Cookie（HttpOnly、`__Host-`、SameSite=Strict） | ブラウザからトークンが読めないこと。セッションの取り消し | 第 110 回、第 111 回 |
| CSRF 対策（独自ヘッダの要求など） | 状態を変えるリクエストが、自分の画面から来たこと | 第 110 回 |
| アクセストークンの `aud` | そのトークンがこの API 宛てであること | 第 114 回 |

保存場所の比較は第 111 回で済ませたので、結論だけ呼び戻します。**置き場所で変えられるのは「持ち出せるか」だけ**で、XSS のスクリプトが同じオリジンから BFF を呼ぶ「代理」は止まりません。RFC 10017 も、BFF の構成で攻撃者が利用者のブラウザから BFF へリクエストを送れることを認めています（[6.1](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.1)）。

**弱点**は、BFF が全部のトークンを持つ機械になることです。BFF のセッションの保存先が漏れれば、全利用者のアクセストークンとリフレッシュトークンが漏れます。保存先を暗号化し（第 100 回のエンベロープ暗号化）、BFF から API への経路も TLS で守ります。

## 型 3: SPA が直接トークンを持つ

```
ブラウザ（SPA） ──認可コード + PKCE──▶ IdP
      │  AT（と RT）は JavaScript が持つ
      └──Authorization: Bearer AT──▶ API（別オリジン。CORS）
```

サーバ側の部品を持たずに、SPA 自身が公開クライアント（第 112 回）として OAuth を行い、トークンを持って API を直接呼ぶ型です。RFC 10017 はこれを 3 つの構成のうち最も安全性が低いものとして最後に置き、XSS が起きれば攻撃者はアクセストークンもリフレッシュトークンも手に入れられるとしています（[6.3](https://www.rfc-editor.org/rfc/rfc10017.html#section-6.3)）。

| 部品 | 何を保証しているか | 回 |
| --- | --- | --- |
| PKCE | 盗んだ code をトークンに引き換えさせないこと | 第 112 回 |
| redirect_uri の完全一致 | code が登録済みの戻り先にしか届かないこと | 第 112 回 |
| 短い寿命と RT のローテーション | 持ち出されたトークンの使える期間を縮めること | 第 111 回、第 112 回 |
| DPoP と取り出せない WebCrypto 鍵 | 持ち出されたトークンを、別の場所で使わせないこと | 第 114 回 |

**弱点**ははっきりしています。この型では、**XSS がそのままトークンの持ち出しにつながります**。OAuth 2.0 Security BCP は、公開クライアントのリフレッシュトークンには送信者への結び付けかローテーションを必須としています（[RFC 9700 2.2.2](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.2.2)）。それでも「持ち出されてから次のローテーションまで」は使えるので、扱うデータが重いなら型 2 に寄せるのが素直です。

<Callout type="warn" title="よくある誤解: PKCE を入れたので、SPA がトークンを持っても安全">
  PKCE が守るのは**トークンを受け取る瞬間**、つまり code の横取りです。受け取った後のトークンがどこに置かれ、誰に読まれるかには何も言いません。
  型 3 の危険は、ログインの流れではなく**ログインの後**にあります。PKCE は必要条件で、十分条件ではありません。
</Callout>

## 型 4: モバイル / デスクトップアプリ

```
アプリ ──(1) システムブラウザを開く──▶ IdP のログイン画面（利用者はここにパスワードを入れる）
  ▲                                         │
  └──(2) 戻り先 URI で code を受け取る ◀────┘
  │     カスタムスキーム / https のユニバーサルリンク / 127.0.0.1 のループバック
  └──(3) code + PKCE の verifier ──▶ トークン。OS の Keychain / Keystore に置く
```

ネイティブアプリは配布されたバイナリなので、埋め込んだ秘密は取り出せます。つまり**必ず公開クライアント**です。RFC 8252 は、ネイティブアプリの公開クライアントに PKCE の実装を必須とし（[8.1](https://www.rfc-editor.org/rfc/rfc8252.html#section-8.1)）、認可リクエストに**アプリに埋め込んだ WebView を使ってはならない**としています（[8.12](https://www.rfc-editor.org/rfc/rfc8252.html#section-8.12)）。埋め込みのブラウザでは、アプリがログイン画面の入力を読めてしまい、利用者はそれが本物の IdP かを URL で確かめられないからです。

戻り先には 3 つの方式があります。独自のスキーム（[7.1](https://www.rfc-editor.org/rfc/rfc8252.html#section-7.1)）、アプリに結び付けた https の URL（[7.2](https://www.rfc-editor.org/rfc/rfc8252.html#section-7.2)）、デスクトップ向けの 127.0.0.1 のループバック（[7.3](https://www.rfc-editor.org/rfc/rfc8252.html#section-7.3)）です。独自のスキームは**別のアプリが同じ名前を登録できる**ので、code が悪意あるアプリに届くことがあります。PKCE はまさにこの横取りへの対策として作られました（第 112 回）。

| 部品 | 何を保証しているか | 回 |
| --- | --- | --- |
| システムブラウザ | パスワードがアプリに渡らないこと。IdP の URL と証明書を利用者が見られること。IdP とのセッションの共有 | 第 104 回、第 116 回 |
| PKCE | 横取りされた code を使わせないこと | 第 112 回 |
| https の戻り先（ドメインとアプリの結び付け） | code がそのドメインを持つアプリにだけ届くこと | 第 58 回、第 101 回 |
| OS の保管場所（Keychain、Keystore） | 他のアプリからトークンを読めないこと | 第 100 回、第 111 回 |

**弱点**は、ブラウザと違ってアプリを後から直せないことです。古い版のアプリは何年も動き続けるので、IdP 側の設定（戻り先、スコープ、リフレッシュトークンの寿命）で守れる部分を厚くします。

## 型 5: API ゲートウェイで検証して、後ろへ ID を渡す

```
クライアント ──Bearer AT──▶ ゲートウェイ ──X-User-Sub: alice──▶ サービス A
                            │ 署名、iss、aud、exp を検証      サービス B
                            │ 受け取った X-User-* は捨てる     （ヘッダを読むだけ）
                            └ JWKS をキャッシュ
```

アクセストークンの検証（第 114 回）を入口の 1 か所に集め、後ろのサービスには**検証済みの結果だけをヘッダで渡す**型です。後ろのサービスは JWT のライブラリも JWKS も持たずに済みます。

この型の保証は、**後ろのサービスがゲートウェイ以外から届かない**という 1 点に懸かっています。ヘッダは誰でも書けるので、ゲートウェイを迂回できる者は `X-User-Sub: admin` と書くだけで管理者になれます（第 105 回で見た `X-Forwarded-For` と同じ構図です）。

クラウドの製品は、この弱点を**ヘッダ自体に署名する**ことで補っています。AWS の Application Load Balancer は、OIDC でログインさせた後、利用者のクレームを `x-amzn-oidc-data` ヘッダに ES256 で署名した JWT として渡し、アプリには署名と、JWT のヘッダの `signer` がその LB の ARN であることを検証するよう求めています。同時に渡す `x-amzn-oidc-identity` などは署名のない、互換性のためのヘッダだと明記しています（[AWS ELB ドキュメント](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-authenticate-users.html#user-claims-encoding)）。

| 部品 | 何を保証しているか | 回 |
| --- | --- | --- |
| ゲートウェイでの JWT 検証（アルゴリズム固定、iss、aud、exp） | 入ってきたトークンが、信頼する IdP がこの API 宛てに発行した有効なものであること | 第 111 回、第 114 回 |
| 受信ヘッダの削除と作り直し | 後ろへ渡る ID が、クライアントの書いたものではないこと | 第 105 回 |
| ネットワークの制限、mTLS、ゲートウェイの署名 | 後ろのサービスに届いたリクエストが、ゲートウェイを通ったものであること | 第 105 回、第 156 回 |
| サービスごとの認可 | その利用者に、そのオブジェクトを触らせてよいこと | 第 115 回 |

**弱点**は 2 つあります。1 つは上の迂回です。もう 1 つは、ゲートウェイが確かめるのが「有効なトークンか」までだということです。BOLA（第 108 回）のような**オブジェクトごとの認可**は、データを知っている後ろのサービスにしかできません。

<Callout type="warn" title="よくある誤解: ゲートウェイで検証したので、後ろは何も確かめなくてよい">
  後ろのサービスが確かめなくてよいのは「トークンの署名と期限」だけで、それも**ゲートウェイ以外の経路が本当に無い**ときに限ります。
  同じクラスタの別の Pod、デバッグ用のポートフォワード、設定を誤った内部 LB。どれか 1 つでも経路があれば、ヘッダを信じるサービスは誰にでもなりすまされます。
  迂回できないことを網の設定だけで保証できないなら、ALB の例のように**ヘッダに署名させて後ろで検証する**か、ゲートウェイと後ろの間を mTLS にして相手がゲートウェイであることを確かめます。
</Callout>

## 手元で確かめる: 小さな BFF とゲートウェイ

型 2 と型 5 を、Python の標準ライブラリの HTTP サーバと PyJWT で組み、どこで何が止まるかを確かめます。登場するのは 3 つのプロセスです。

```
curl ──Cookie: sid──▶ BFF :18110 ──Bearer AT──▶ ゲートウェイ :18111 ──ヘッダ──▶ バックエンド :18112
                       sid → AT を引く           ES256 の JWT を検証        X-User-Sub を読む
                                                 X-User-Sub を作り直す       （STRICT=1 なら、ゲートウェイの
                                                 自分の鍵で短い JWT に署名    署名付き JWT を検証する）
```

IdP の代わりに、手元で作った P-256 の鍵でアクセストークン（`iss`、`sub`、`aud=orders-api`、寿命 5 分）に署名し、公開鍵は JWKS のファイルでゲートウェイに渡します。本物の構成では、ゲートウェイは Discovery の `jwks_uri` から TLS で取ります（第 111 回、第 113 回）。ゲートウェイは PyJWT の `jwt.decode` に `algorithms=["ES256"]`、`issuer`、`audience`、`leeway=30` を渡し、`exp`・`iss`・`aud`・`sub` を必須にして検証します。`kid` は手元の JWKS の中から選ぶだけで、トークンに鍵の在りかを決めさせません（第 111 回の「検証する側が先に決めておく」）。環境は Python 3.14、PyJWT 2.15.0、cryptography 50.0.1 です。

venv に `pyjwt[crypto]` を入れ、`lab.py mkkeys` で IdP とゲートウェイの鍵と JWKS を作り、3 つのサーバを起動しておきます。まず BFF にログインします（ここでは IdP とのやり取りを省き、BFF が alice のトークンを受け取ったことにしています）。

```
$ curl -si -c jar.txt http://127.0.0.1:18110/login
HTTP/1.0 200 OK
Set-Cookie: sid=RRJzeiz9WawcC8L-u2B4XWBBRmZ0MRwnKnL0hW7Cy2E; HttpOnly; SameSite=Strict; Path=/
{"logged_in": "alice"}

$ grep HttpOnly_ jar.txt
#HttpOnly_127.0.0.1	FALSE	/	FALSE	0	sid	RRJzeiz9WawcC8L-u2B4XWBBRmZ0MRwnKnL0hW7Cy2E
```

ブラウザの代わりの cookie jar にあるのは、意味を持たない乱数の `sid` だけです。JWT はどこにもありません。本番なら名前を `__Host-sid` にして `Secure` を付けますが、この実験は平文の HTTP なので省いています。

```
$ curl -s -b jar.txt -H 'X-Requested-With: fetch' http://127.0.0.1:18110/api/orders/42
{"path": "/orders/42", "user": "alice"}

$ curl -s -b jar.txt http://127.0.0.1:18110/api/orders/42
{"error": "missing CSRF header"}
```

BFF はセッションからトークンを取り出してゲートウェイへ中継し、バックエンドは alice として応答しました。独自ヘッダの無いリクエストを BFF が拒むのは、第 110 回の CSRF 対策です（別サイトのフォームは独自ヘッダを付けられません）。次に、ゲートウェイを直接叩きます。比べるためのトークンを、同じ IdP の鍵で作っておきます。

```
$ TOK=$(.venv/bin/python lab.py issue alice)                  # 正しいもの
$ TOK_BILLING=$(.venv/bin/python lab.py issue alice billing-api)  # aud が別の API
$ TOK_EXPIRED=$(.venv/bin/python -c "import lab; print(lab.issue('alice', ttl=-120))")
$ TOK_ADMIN=$(.venv/bin/python lab.py issue admin)            # 後で使う

$ curl -si -H 'X-User-Sub: admin' http://127.0.0.1:18111/orders/42
HTTP/1.0 401 Unauthorized
WWW-Authenticate: Bearer realm="orders"

$ curl -s -H "Authorization: Bearer $TOK_BILLING" http://127.0.0.1:18111/orders/42
{"error": "invalid_token", "why": "Audience doesn't match"}

$ curl -s -H "Authorization: Bearer $TOK_EXPIRED" http://127.0.0.1:18111/orders/42
{"error": "invalid_token", "why": "Signature has expired"}

$ curl -s -H "Authorization: Bearer $TOK" -H 'X-User-Sub: admin' http://127.0.0.1:18111/orders/42
{"path": "/orders/42", "user": "alice"}
```

トークンが無ければ 401（第 108 回の `WWW-Authenticate`）、同じ IdP の正しい署名でも `aud=billing-api` なら拒否、期限切れも拒否。最後の行が大事で、**正しいトークンと一緒に偽のヘッダを送っても、ゲートウェイはそれを捨てて作り直す**ので alice のままです。ところが、バックエンドに直接届く経路があると話が変わります。

```
$ curl -s -H 'X-User-Sub: admin' http://127.0.0.1:18112/orders/42
{"path": "/orders/42", "user": "admin"}
```

ヘッダ 1 行で管理者になりました。型 5 の弱点そのものです。そこで、バックエンドを `STRICT=1` で起動し直し、ゲートウェイが自分の鍵で署名した寿命 60 秒の JWT（`iss=gateway`、`aud=orders-backend`）を `X-Gateway-Assertion` で受け取って検証させます。ALB の `x-amzn-oidc-data` と同じ考え方です。

```
$ curl -s -H 'X-User-Sub: admin' http://127.0.0.1:18112/orders/42
{"error": "bad gateway assertion", "why": "Not enough segments"}

$ curl -s -H 'X-User-Sub: admin' -H "X-Gateway-Assertion: $TOK_ADMIN" http://127.0.0.1:18112/orders/42
{"error": "bad gateway assertion", "why": "unknown kid 'idp-2026-09'"}

$ curl -s -b jar.txt -H 'X-Requested-With: fetch' http://127.0.0.1:18110/api/orders/42
{"path": "/orders/42", "user": "alice"}
```

2 つ目は、IdP が正しく署名した admin のアクセストークンを差し込んだ場合です。**バックエンドはゲートウェイの鍵しか信じない**ので、IdP のトークンでは通りません。利用者向けのトークンと、ゲートウェイからバックエンドへの証を、別の鍵と別の `aud` で分けておいたことが効いています。正規の経路（BFF 経由）はそのまま通ります。

| 試したこと | 止めた部品 |
| --- | --- |
| ブラウザ側からトークンを読む | BFF（トークンをサーバ側に置く） |
| 別サイトからの自動送信 | BFF の独自ヘッダの要求（CSRF 対策） |
| トークンなし、別の API 宛て、期限切れ | ゲートウェイの JWT 検証（署名、aud、exp） |
| 正しいトークン + 偽のヘッダ | ゲートウェイでのヘッダの作り直し |
| ゲートウェイの迂回 | **何も止めない**（STRICT=0）。署名付きの証を後ろで検証して初めて止まる |

逆に、この実験が止めていないものもあります。署名付きの証も、60 秒の間に盗み見られれば使い回せます。本番ではゲートウェイとバックエンドの間を mTLS にして、盗聴と相手の取り違えを同時に塞ぎます。それが次の型 6 です。

## 型 6: マイクロサービス間（2 つの ID を別々に運ぶ）

```
                ワークロードの ID: mTLS の証明書（SPIFFE ID）
            ┌──────────────────────────────────────────┐
[注文サービス] ══mTLS══▶ [在庫サービス] ══mTLS══▶ [決済サービス]
   │  Bearer: 利用者のトークン（aud=在庫）   │  Bearer: トークン交換で作り直したもの（aud=決済, act=在庫）
   └──────────────────────────────────────────┘
                利用者の ID: JWT
```

サービスメッシュ（第 156 回）では、各サービスのプロキシが短命な証明書で mTLS を張ります。SPIFFE の X.509-SVID は、ワークロードの ID を `spiffe://` で始まる URI として証明書の SAN に 1 つだけ入れます（[SPIFFE X.509-SVID](https://github.com/spiffe/spiffe/blob/main/standards/X509-SVID.md)）。これで「**どのサービスが**呼んでいるか」が分かります。

しかし mTLS は、「**誰のために**」呼んでいるかを知りません。そこで利用者の ID は、リクエストのヘッダに乗せた JWT で別に運びます。Istio の認可ポリシーはこの 2 つを別の欄で扱っていて、`principals` はピアの証明書から得た ID（例 `cluster.local/ns/default/sa/productpage`）で mTLS が要り、`requestPrincipals` は JWT から得た `iss/sub` で RequestAuthentication が要る、と書かれています（[Istio: Authorization Policy](https://istio.io/latest/docs/reference/config/security/authorization-policy/)）。

利用者のトークンを下流へそのまま回すと、`aud` を広くせざるを得ず、途中の 1 つのサービスが盗まれれば全サービスで使えるトークンが漏れます。そこで、サービスの境界ごとに**トークン交換**（[RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html)）で、次の宛先だけに通じるトークンに作り直します。RFC 8693 は、A が B に**完全になりすます**場合（impersonation）と、A が B の代理であることを保ったまま動く場合（delegation）を分け、後者では `act` クレームで「実際に動いている者」を示します（[1.1](https://www.rfc-editor.org/rfc/rfc8693.html#section-1.1)、[4.1](https://www.rfc-editor.org/rfc/rfc8693.html#section-4.1)）。詳しくは第 114 回で見ました。

| 部品 | 何を保証しているか | 回 |
| --- | --- | --- |
| mTLS + 短命な証明書（SPIFFE ID） | 通信の相手がどのワークロードか。区間の盗聴と改ざんの防止 | 第 105 回、第 120 回、第 156 回 |
| 利用者の JWT（iss、sub、aud） | このリクエストが誰のためのものか | 第 111 回、第 114 回 |
| トークン交換（aud の付け替え、`act`） | 下流へ渡すトークンが、その宛先でしか使えないこと。誰が代理しているか | 第 114 回 |
| 認可ポリシー（`principals` と `requestPrincipals` の両方） | 「このサービスから、この利用者のために」の組み合わせを許すか | 第 115 回 |

**弱点**は、2 つの ID のどちらか一方しか見ない認可です。「在庫サービスからの呼び出しなら何でも許す」と書けば、在庫サービスを乗っ取った者は全利用者のデータを読めます。逆に利用者の JWT だけを見れば、どのサービスからでも同じトークンで呼べます。

<Callout type="warn" title="よくある誤解: メッシュで mTLS を有効にしたので、認証は済んでいる">
  mTLS が確かめたのは**サービスの鍵**で、利用者ではありません（第 105 回）。さらに、JWT の検証を足す設定にも落とし穴があります。
  Istio の RequestAuthentication は、無効なトークンは拒否しますが、**トークンを含まないリクエストは受け入れ**、ただ認証済みの ID を持たないものとして扱います。認証済みのリクエストだけに絞るには、認可の規則を組み合わせるよう明記されています（[Istio: RequestAuthentication](https://istio.io/latest/docs/reference/config/security/request_authentication/)）。
  「検証する」と「要求する」は別の設定です。
</Callout>

## 型 7: ゼロトラスト / IAP（ネットワークの位置を信じない）

```
従来: 社外 ──VPN──▶ [社内ネットワーク: 中に入れば社内アプリに届く]

IAP:  利用者 + 管理された端末 ══TLS══▶ アクセスプロキシ ──署名付きヘッダ──▶ 社内アプリ
                                        │ 毎回: IdP のセッション、端末の状態、ポリシー
                                        └ アプリはプロキシ以外から届かない
```

VPN の型は、「社内ネットワークに入れたこと」を信頼の根拠にします。一度入れば、中のアプリにはネットワークの上で届きます。Google の BeyondCorp の論文（2014）は、境界が破られると攻撃者が特権的な社内ネットワークに比較的容易に入れてしまうことを問題とし、特権的なイントラネットをなくして社内アプリをインターネットに置き、アクセスを**利用者と端末の認証情報だけ**で決める方式を示しました（[Google Research](https://research.google/pubs/beyondcorp-a-new-approach-to-enterprise-security/)、[USENIX ;login:](https://www.usenix.org/publications/login/dec14/ward)）。NIST SP 800-207（2020 年 8 月）も、ゼロトラストを「物理的・ネットワーク上の位置や資産の所有だけを根拠に、暗黙の信頼を与えない」ことと定義しています（[NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/final)）。

実装の中心は**アクセスプロキシ**です。Google Cloud の Identity-Aware Proxy は、確かめた利用者を `x-goog-iap-jwt-assertion` ヘッダの ES256 の JWT でアプリに渡します。`aud` はバックエンドごとに決まった値（例 `/projects/番号/global/backendServices/ID`）で、アプリはこれを検証するよう求められています。理由として、IAP を迂回した攻撃者は署名のない `x-goog-authenticated-user-email` などを偽造できるから、と書かれています（[Google Cloud: IAP の署名付きヘッダ](https://docs.cloud.google.com/iap/docs/signed-headers-howto)）。**型 5 と全く同じ構図**で、入口で確かめ、署名付きの証を渡し、後ろで検証します。

| 部品 | 何を保証しているか | 回 |
| --- | --- | --- |
| IdP + 多要素（できればパスキー） | 利用者が本人であること | 第 109 回、第 113 回 |
| 端末の証明書、端末の管理情報 | 管理された、条件を満たす端末からであること | 第 101 回、第 105 回 |
| アクセスプロキシのポリシー | この利用者とこの端末に、このアプリを許すか（毎回） | 第 115 回 |
| 署名付きヘッダ（aud をアプリごとに） | アプリに届いた ID がプロキシの確かめたものであること | 第 111 回 |

**弱点**は、IdP とプロキシが単一の入口になることです。IdP が止まれば全部の社内アプリに入れなくなり（第 119 回）、IdP のセッションが盗まれれば全部に入られます。「ゼロトラスト」は何も信じないという意味ではなく、**信頼の根拠を、ネットワークの位置から、毎回確かめる利用者と端末へ移した**という意味です。

## 型 8: CI/CD からクラウドへ（長期の鍵を置かない）

```
GitHub Actions のジョブ ──(1) OIDC トークンを要求（permissions: id-token: write）
        │                    iss = https://token.actions.githubusercontent.com
        │                    sub = repo:org/app:ref:refs/heads/main,  aud = sts.amazonaws.com
        └──(2) AssumeRoleWithWebIdentity ──▶ AWS STS ──(3) 短命な一時的認証情報
                                               │ 信頼ポリシーの条件: aud と sub が一致するか
```

第 120 回で見たワークロード ID フェデレーションです。CI のジョブは、実行環境が発行した OIDC トークンを、クラウドの短命な認証情報に交換します。**リポジトリの秘密情報にクラウドのアクセスキーを置かない**ことが、この型の価値です。GitHub の手順では、AWS の信頼ポリシーに `token.actions.githubusercontent.com:aud` が `sts.amazonaws.com`、`:sub` が `repo:octo-org/octo-repo:ref:refs/heads/octo-branch` と一致する条件を書く例を示し、`sub` の条件を評価するよう勧めています（[GitHub Docs: AWS での OIDC](https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments/oidc-in-aws)）。

| 部品 | 何を保証しているか | 回 |
| --- | --- | --- |
| CI の OIDC トークン（署名、iss、aud） | GitHub が「このリポジトリのこのジョブだ」と言ったこと | 第 113 回、第 120 回 |
| JWKS と TLS | その署名鍵が本物の GitHub のものであること | 第 102 回、第 111 回 |
| 信頼ポリシーの `sub` の条件 | **どの**リポジトリ、ブランチ、環境のジョブにロールを渡すか | 第 115 回、第 120 回 |
| 短命な一時的認証情報 | 漏れても使える期間が短いこと | 第 100 回 |

**弱点**は、ほぼすべて `sub` の条件の書き方にあります。`StringLike` で `repo:org/app:*` と書けば、main 以外のどのブランチのジョブも、プルリクエストで動くジョブも、本番のロールを受け取れます。トークンの署名は完璧でも、**「誰に渡すか」の規則が広すぎれば、署名は広すぎる相手を正しく証明するだけ**です。

## 型 9: 人のサーバアクセス（IdP から短命な SSH 証明書へ）

```
利用者 ──(1) IdP でログイン（SSO + MFA）──▶ SSH の CA
   ▲                                          │ principals = [alice, deploy], 有効 8 時間
   └──(2) ユーザ証明書（自分の公開鍵に CA が署名）◀─┘
   │
   └──(3) ssh ──▶ sshd（TrustedUserCAKeys で CA の公開鍵だけを信じる）
                  クライアントも @cert-authority でホスト証明書を検証する
```

第 107 回の型です。`authorized_keys` と `known_hosts` を何千台に配る代わりに、**サーバには CA の公開鍵を 1 つだけ置き**、利用者には IdP でのログインと引き換えに数時間だけ有効な証明書を発行します。

| 部品 | 何を保証しているか | 回 |
| --- | --- | --- |
| IdP の SSO と MFA | 証明書を受け取るのが本人であること | 第 109 回、第 116 回 |
| SSH のユーザ証明書（principals、期限） | この公開鍵が、どのログイン名で、いつまで使えるか | 第 107 回 |
| SSH の公開鍵認証（セッション ID への署名） | 接続しているのがその秘密鍵の持ち主であること | 第 106 回 |
| ホスト証明書 | 接続先のサーバが本物であること（TOFU を置き換える） | 第 106 回、第 107 回 |

**弱点**は CA の秘密鍵です。これを持つ者は、どのサーバのどのアカウントにも入れる証明書を作れます。KMS や HSM に置いて取り出せなくし（第 100 回）、発行を IdP の認証と監査ログに結び付けます。その代わり、退職者の対応は「証明書を発行しない」だけで済み、数時間後には全サーバで自然に入れなくなります。期限を短くすることが、失効の仕組みの代わりになっています（第 103 回の短命な証明書と同じ考え方）。

## 型 10: 企業 SSO（IdP + SAML/OIDC + SCIM）

```
             SCIM: POST /Users, PATCH, DELETE（アカウントを配る・消す）
    IdP ─────────────────────────────────────────────▶ SaaS / 社内アプリ
     │   SAML アサーション or ID トークン（ログインのたび）      │
     └──────────────────────────────────────────────────▶ アプリのセッション
     IdP とのセッション                                        （アプリごと）
```

会社の IdP 1 つで、何十の SaaS と社内アプリにログインさせる型です（どの IdP を選ぶかは第 118 回）。**ログイン**は SAML か OIDC で（第 116 回）、**アカウントの作成と削除**は SCIM で（第 117 回）行います。SCIM は HTTP の上で `/Users` や `/Groups` を POST、PUT、PATCH、DELETE する取り決めです（[RFC 7644 3.2](https://www.rfc-editor.org/rfc/rfc7644.html#section-3.2)）。

| 部品 | 何を保証しているか | 回 |
| --- | --- | --- |
| IdP の認証（MFA、パスキー） | 利用者が本人であること | 第 109 回 |
| SAML の XML 署名 / ID トークンの署名 | アサーションが IdP のもので、このアプリ宛てであること | 第 113 回、第 116 回 |
| iss + sub（SAML なら NameID）による突き合わせ | ログインした人と、アプリ側のアカウントが同じ人であること | 第 113 回、第 117 回 |
| SCIM | アカウントとグループが IdP と一致していること。退職時の削除 | 第 117 回 |
| アプリの認可（グループからロールへの対応） | そのアプリの中で何をしてよいか | 第 115 回 |

**弱点**は、SSO が「ログインの入口」を 1 つにするだけで、**ログインの後に残るもの**を消さないことです。IdP でアカウントを止めても、アプリとのセッション、発行済みの API トークン、SSO を通らないローカルアカウントは残ります（第 117 回）。IdP が止められるのは**次のログイン**だけです。SCIM による無効化をアプリが受け取ってセッションを消すか、バックチャネルログアウト（第 116 回）に対応していて、初めて退職の処理が終わります。

## 10 の型に共通すること

型を並べると、同じ形が何度も出てきます。

- **入口で確かめて、証を後ろへ渡す**。型 1 のセッション、型 2 の BFF、型 5 のゲートウェイ、型 7 の IAP、型 9 の SSH 証明書。どれも、重い確認（IdP、MFA、JWT の検証）を 1 か所で行い、以後は軽い証で済ませる。その代わり、**証を受け取る側が「入口を通ったものしか届かない」ことを確かめられるか**が要になる
- **宛先を狭める**。`aud`（型 2、5、6、7、8）、トークン交換（型 6）、`sub` の条件（型 8）、principals（型 9）。署名が正しいことより、**誰に宛てた証か**を確かめ忘れる事故のほうが多い
- **短くして、失効の代わりにする**。短命なアクセストークン、ゲートウェイの 60 秒の証、CI の一時的な認証情報、8 時間の SSH 証明書、メッシュの証明書。取り消せない自己完結型の証（第 110 回の trade-off）は、寿命で被害を縛る
- **鍵の相手と人を分ける**。TLS、mTLS、SSH のホスト鍵は鍵を確かめ、ID トークン、SAML、JWT は人を運ぶ。型 6 のように両方が乗るときは、認可で**両方**を見る

## どの層で、誰を確かめるか

最後に、この 4 章の部品を「何を確かめるか」で 1 枚にまとめます。

| 層 | 確かめるもの | 答える部品 | 答えないこと |
| --- | --- | --- | --- |
| TLS | サーバの**鍵**と名前の結び付き | 鍵交換、署名（CertificateVerify）、証明書とチェーン | そのサーバを運用しているのが誰で、信頼してよいか |
| mTLS / SPIFFE | クライアントの**鍵**（どのワークロードか） | クライアント証明書、短命な SVID | そのワークロードが誰のために動いているか、何をしてよいか |
| SSH | サーバのホスト鍵と、利用者の鍵 | 署名、known_hosts / SSH 証明書 | その鍵で何をしてよいか（sudo、principals の外） |
| ID トークン / SAML アサーション | **利用者**がログインしたこと（RP 宛て） | IdP、署名、JWKS、nonce、aud | API を呼んでよいこと。ログインの後も有効かどうか |
| セッション Cookie | 以後のリクエストが、ログインしたブラウザからであること | サーバ側セッション、Cookie の属性 | XSS がそのブラウザの中で使うこと |
| アクセストークン | **委任された権限**（このクライアントに、この範囲、この宛先） | OAuth、aud、scope、DPoP / mTLS での結び付け | 利用者がそのオブジェクトを触ってよいか |
| 認可 | **何をしてよいか**（この主体が、このオブジェクトに、この操作を） | RBAC / ABAC / ReBAC、ポリシーエンジン | 相手が本物かどうか（上の層が済ませている前提） |

表を上から下へ読むと、**確かめる対象が「鍵」から「人」へ、そして「行為」へと移っていく**のが分かります。下の層の部品は、上の層が済ませたことを前提にしています。そして上の層は、下の層が答えないことに答えません。どこか 1 段が「上か下の誰かがやっているはず」と思い込んだとき、構成全体が崩れます。

## まとめ

- 構成は「誰の何を確かめるか」「証はどこにあるか」「どこから先を検証済みと信じるか」の 3 つで読む。事故は、ある部品が保証していると思い込んだことを、実は誰も保証していないところで起きる
- 型 1（サーバ側セッション + OIDC）はブラウザで最も守りやすい。ID トークンはログインの瞬間の証明で、セッションの寿命はアプリが持つ
- 型 2（BFF）はトークンをサーバ側に置き、ブラウザは Cookie だけを持つ。消せるのは持ち出しで、XSS による代理は残る。型 3（SPA が直接持つ）は XSS がそのまま持ち出しになり、PKCE はそれを防がない
- 型 4（ネイティブアプリ）は必ず公開クライアント。システムブラウザ、PKCE、戻り先の 3 方式（RFC 8252）
- 型 5（ゲートウェイ）は、受け取ったヘッダを捨てて作り直し、後ろに迂回経路が無いことが前提。無いと言い切れなければ、ALB や IAP のようにヘッダに署名して後ろで検証する。手元の実験でも、迂回したヘッダ 1 行で管理者になれた
- 型 6（サービス間）は、ワークロードの ID を mTLS で、利用者の ID を JWT で別々に運び、トークン交換で宛先を狭める。認可は両方を見る。「検証する」と「要求する」は別の設定
- 型 7（IAP）は信頼の根拠をネットワークの位置から、毎回確かめる利用者と端末に移す。型 8（CI の OIDC）は長期の鍵をなくし、安全性は `sub` の条件の狭さで決まる
- 型 9（短命な SSH 証明書）と型 10（企業 SSO + SCIM）は、入口を IdP にまとめる。入口を止めても、ログインの後に残るもの（セッション、トークン、ローカルアカウント）は別に消す
- 層ごとに確かめる対象は、鍵、人、委任された権限、行為へと移る。各層は、他の層の答えないことに答えない

次の第 122 回では、この回の型が実際に崩れた事例を見ます。署名鍵の範囲の検証が欠けていた、セッショントークンが思わぬ場所に残っていた、証明書の期限を誰も見ていなかった。どれも、部品同士の境目で起きた障害と事件です。
