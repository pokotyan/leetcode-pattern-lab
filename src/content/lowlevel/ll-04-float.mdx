## まず、有名な現象から

どの言語でも同じことが起きます。

```python
>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False
```

これは言語のバグではありません。CPU の浮動小数点演算がそうなっているからで、**Python でも JavaScript でも C でも Java でも同じ結果**になります。

理由は 1 行で言えます。

> **0.1 は 2 進数で正確に表せない。**

## 10 進数でも同じことが起きている

10 進数で 1/3 を書こうとすると `0.3333...` と無限に続きます。どこかで打ち切るしかありません。打ち切った時点で誤差が生まれます。

2 進数では、分母が 2 の冪でない分数がこうなります。1/10 は 2 の冪ではないので、

```
0.1 (10進) = 0.0001100110011001100...(2進)  ← 1100 が無限に続く
```

無限に続くので、有限のビット数では必ず打ち切られます。**0.1 をコードに書いた瞬間、それは 0.1 ではない何か**になっています。

一方 0.5、0.25、0.75 は 2 の冪の和なので正確に表せます。

```python
>>> 0.5 + 0.25 == 0.75
True
```

## ビットの並び

**IEEE 754** という規格で、ビットの使い方が決まっています。倍精度（double、64 ビット）の内訳です。

```
 ┌─┬───────────┬──────────────────────────────────────────────────┐
 │S│  指数部    │                   仮数部                          │
 └─┴───────────┴──────────────────────────────────────────────────┘
  1     11 bit                        52 bit
```

| 部分 | ビット数 | 役割 |
| --- | --- | --- |
| 符号 (S) | 1 | 0 なら正、1 なら負 |
| 指数部 | 11 | 小数点の位置。2 の何乗か |
| 仮数部 | 52 | 有効数字の中身 |

値は次の形になります。

```
(-1)^S × 1.仮数部 × 2^(指数部 - 1023)
```

10 進数で `1.234 × 10³` と書くのと同じ形（科学的記数法）です。違うのは、底が 10 ではなく 2 であることだけです。

<Callout type="tip" title="仮数部の先頭 1 は書かれていない">
  正規化した 2 進数は必ず `1.xxxx` の形になります（先頭が 0 なら、その分だけ指数を減らせばよい）。
  先頭が必ず 1 なら、保存する必要はありません。この「**ケチ表現**」により、
  52 ビットで 53 ビットぶんの精度が得られています。
</Callout>

指数部から 1023 を引くのは、負の指数を表すためです。2 の補数を使わず**ゲタを履かせる**（バイアスを足す）方式にしたのは、こうすると**ビット列をそのまま符号なし整数として比較しても大小関係が保たれる**からです。浮動小数点数の比較回路が単純になります。

## 精度はどれくらいか

| 型 | 全体 | 仮数部 | 10 進の有効桁 |
| --- | --- | --- | --- |
| `float`（単精度） | 32 bit | 23 bit | 約 7 桁 |
| `double`（倍精度） | 64 bit | 52 bit | 約 15〜16 桁 |

「約 15 桁」というのは、2⁵³ ≈ 9.0 × 10¹⁵ から来ています。

重要なのは、**精度が「桁数」で決まっていて「絶対的な細かさ」では決まっていない**ことです。値が大きくなるほど、隣の表現可能な数との間隔が広がります。

```python
>>> 2.0**53
9007199254740992.0
>>> 2.0**53 + 1
9007199254740992.0      # 増えない
```

2⁵³ を超えると、整数ですら 1 刻みで表せなくなります。JavaScript の `Number.MAX_SAFE_INTEGER` が 9007199254740991 なのはこのためです。**JavaScript で 64 ビット整数の ID を扱うと壊れる**のは、この境界を越えるからです。

## どう付き合うか

**比較は差の大きさで行う。**

```python
abs(a - b) < 1e-9
```

ただし、比べる値が大きいときはこの閾値では足りません。相対誤差で見るほうが安全です。

```python
import math
math.isclose(a, b, rel_tol=1e-9)
```

**金額は浮動小数点で持たない。** 誤差が積み上がり、帳尻が合わなくなります。選択肢は 2 つです。

- **整数で最小単位を持つ**（円ではなく銭、ドルではなくセント）
- **10 進小数型を使う**（Python の `decimal`、SQL の `NUMERIC` / `DECIMAL`）

<Callout type="warn" title="足す順番で結果が変わる">
  浮動小数点の加算は**結合法則を満たしません**。
  `(a + b) + c` と `a + (b + c)` が違う値になることがあります。
  大きな値と小さな値を混ぜて足すと、小さいほうが丸めで消えるからです。
  合計を取るときは、**小さい値から順に足す**か、Kahan の補正加算のような手法を使うと誤差が減ります。
  この性質は、並列化した集計の結果が実行のたびに微妙に変わる原因にもなります。
</Callout>

## 特殊な値

指数部を全部 1 にしたビットパターンは、通常の数ではなく特殊な意味に割り当てられています。

| 値 | 意味 | 生まれ方 |
| --- | --- | --- |
| `+Inf` / `-Inf` | 無限大 | `1.0 / 0.0`、範囲を超えた計算 |
| `NaN` | Not a Number | `0.0 / 0.0`、`sqrt(-1)`、`Inf - Inf` |

**NaN には厄介な性質があります。自分自身と等しくありません。**

```python
>>> float('nan') == float('nan')
False
>>> x = float('nan')
>>> x == x
False
```

規格でそう定められています。「比較できない値」だからです。結果として、次のことが起こります。

- `NaN` を含む配列のソート結果は、比較関数の実装次第で壊れる
- `x != x` が真なら `x` は NaN、という判定イディオムが成立する
- 集合や辞書のキーにすると、入れたのに見つからないことがある

判定には専用の関数を使います（Python の `math.isnan`、JavaScript の `Number.isNaN`）。

<Callout type="note" title="0 も 2 つある">
  符号ビットが別なので、`+0.0` と `-0.0` が存在します。比較では等しくなりますが、
  `1/+0.0` は `+Inf`、`1/-0.0` は `-Inf` です。符号が残っているのは、
  極限の方向を保ちたい数値計算の要求によるものです。
</Callout>

## 非正規化数

指数部が最小のとき、先頭の暗黙の 1 を外した表現に切り替わります。これを **非正規化数**（subnormal / denormal）と呼びます。0 のすぐ近くを、精度を落としながら細かく表すための仕組みです。

これがないと、表せる最小の正の数と 0 の間に急な段差ができ、`a != b` なのに `a - b == 0` という状況が起こります。非正規化数はその段差を埋めます。

ただし、**多くの CPU で非正規化数の演算は極端に遅くなります**。通常の演算の数十倍かかることがあり、音声処理などで「値が小さくなっていくと突然 CPU 使用率が跳ね上がる」という現象の原因になります。対策として、非正規化数を 0 に丸めるモード（FTZ / DAZ）が用意されています。

## まとめ

- 0.1 は 2 進数で無限小数になるため、格納した時点で誤差がある
- IEEE 754 は「符号 + 指数部 + 仮数部」で、科学的記数法の 2 進数版
- 精度は相対的。値が大きいほど、表せる数の間隔が広がる
- 金額は整数か 10 進小数型で持つ
- NaN は自分自身と等しくない
- 加算に結合法則がないので、足す順番で結果が変わる
