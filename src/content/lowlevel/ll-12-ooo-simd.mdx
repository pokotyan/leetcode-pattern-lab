## 実行ユニットを増やす

パイプラインは「1 クロックに 1 命令完了」まで来ました。次の一手は、**実行回路そのものを複数用意する**ことです。

整数の加算器を 4 つ、乗算器を 2 つ、ロード / ストアユニットを 3 つ、といった具合に並べます。これらが同時に動けば、1 クロックに複数の命令が完了します。これを **スーパースカラ** と呼びます。

現代の高性能 CPU は、1 クロックに 4〜8 命令を完了できます。

ただし、命令を順番通りに投入すると、この能力は活かせません。

```asm
load  r1, [r2]       ; メモリ待ち。200 クロックかかるかもしれない
add   r3, r1, r4     ; r1 が要る。待つしかない
add   r5, r6, r7     ; これは r1 と無関係。今すぐできる
```

3 番目の命令は、1 番目の完了を待つ必要がありません。しかし順番通りなら、2 番目で詰まっている間ずっと止まります。

## 順番を入れ替える

そこで、**依存関係さえ守れば、命令の順番を入れ替えてよい**ことにします。これが **アウトオブオーダー実行** です。

CPU は次のように動きます。

1. 命令をデコードし、**リザベーションステーション**という待合室に入れる
2. 入力が揃った命令から、空いている実行ユニットに送る
3. 結果は **リオーダバッファ** に貯める
4. **元の順番通りに**、結果を確定させる（リタイア）

投入と実行は順不同、**完了の確定だけは元の順番**です。こうしないと、例外が発生したときにどこまで実行済みかが説明できなくなります。

<Callout type="note" title="外から見えるかどうかがすべて">
  プログラムから観測できる状態（レジスタとメモリの内容）が、
  順番通りに実行した場合と一致していれば、内部で何をしようと構いません。
  ISA という契約が守られていればよい、という考え方です。
  ただし**マルチスレッドではこれが破れます**。別のスレッドからは順番の入れ替えが観測できるためで、
  第 6 章の同期の話につながります。
</Callout>

## 名前の衝突を消す

順番を入れ替えようとすると、本来は無関係なのにレジスタ名が同じせいで依存しているように見えるケースが出ます。

```asm
add  r1, r2, r3     ; r1 に書く
mov  r4, r1         ; r1 を読む
add  r1, r5, r6     ; 別の計算。たまたま r1 を使い回している
```

3 番目は 1 番目とは無関係ですが、同じ r1 に書くので順番を守らなければならないように見えます。レジスタが 16 本しかないため、こういう使い回しは頻繁に起きます。

対策が **レジスタリネーミング** です。CPU は内部に、ISA で見えるよりずっと多くの物理レジスタを持っています（100〜300 本程度）。命令ごとに別の物理レジスタを割り当て、名前の衝突を消します。

```
add  p10, p2, p3     ; r1 → p10
mov  p11, p10
add  p12, p5, p6     ; r1 → p12 （別物になった）
```

これで 3 番目は 1 番目と独立になり、並行して実行できます。

## 1 命令で複数のデータを処理する

別方向の並列化もあります。**SIMD**（Single Instruction, Multiple Data）です。

256 ビットのレジスタに 32 ビット整数を 8 個詰め、1 命令で 8 個まとめて足します。

```
[ a0 | a1 | a2 | a3 | a4 | a5 | a6 | a7 ]
+
[ b0 | b1 | b2 | b3 | b4 | b5 | b6 | b7 ]
=
[ c0 | c1 | c2 | c3 | c4 | c5 | c6 | c7 ]     1 命令
```

| 拡張 | レジスタ幅 | 32 ビット整数の個数 |
| --- | --- | --- |
| SSE | 128 bit | 4 |
| AVX / AVX2 | 256 bit | 8 |
| AVX-512 | 512 bit | 16 |
| ARM NEON | 128 bit | 4 |
| ARM SVE | 可変長 | 実装依存 |

画像処理、音声処理、行列計算、文字列検索など、**同じ処理を大量のデータに繰り返す**場面で効きます。

使い方は 3 段階あります。

| 方法 | 手間 | 制御 |
| --- | --- | --- |
| コンパイラの自動ベクトル化 | なし | 効くかどうかは運次第 |
| 組み込み関数（intrinsics） | 中 | 命令を直接指定できる |
| アセンブリ | 大 | 完全 |

自動ベクトル化を効かせるには、ループの形が単純で、要素間に依存がなく、境界が明確である必要があります。`-O3 -march=native` を付け、`-fopt-info-vec` で効いたかどうかを確認するのが実務的な手順です。

<Callout type="warn" title="AVX-512 は周波数を下げることがある">
  幅の広い SIMD 命令は消費電力が大きく、一部の Intel の世代では
  **AVX-512 を使うとコア全体のクロックが下がります**。
  SIMD 部分は速くなっても、他の処理が遅くなり、全体では損をすることがあります。
  必ず全体のスループットで測る必要があります。
</Callout>

## 1 つのコアに 2 つのスレッドを載せる

アウトオブオーダー実行をもってしても、実行ユニットには空きが出ます。メモリ待ちが長いときは特にそうです。

そこで、**1 つのコアに独立した命令の流れを 2 本流す**という手があります。**SMT**（Simultaneous Multithreading）、Intel の呼称では**ハイパースレッディング**です。

レジスタと PC を 2 組持ち、実行ユニットは共有します。片方がメモリ待ちで止まっている間、もう片方が実行ユニットを使えます。

効果は処理の性質によります。

| 状況 | 効果 |
| --- | --- |
| メモリ待ちが多い処理 | 30〜40% 向上することもある |
| 実行ユニットを使い切っている処理 | ほぼ効果なし、または悪化 |
| キャッシュを奪い合う処理 | **遅くなる** |

「8 コア 16 スレッド」の 16 は、物理的な 8 コアの上に論理的な 16 本が見えるという意味です。**16 コアぶんの性能ではありません。**

<Callout type="warn" title="セキュリティ上の理由で無効化されることがある">
  同じコアを共有するため、キャッシュや実行ユニットの使用状況から
  隣のスレッドの情報が漏れる攻撃（L1TF、MDS など）が報告されました。
  クラウド事業者や一部の OS では、SMT を無効にする選択が取られています。
</Callout>

## 書いた順に実行されているという前提

ここまでを踏まえると、次のことが言えます。

- 命令の実行順は、書いた順とは違う
- 複数の命令が同時に実行されている
- 予測に基づいて、まだ確定していない命令が先に走っている
- メモリへの書き込みも、順番が入れ替わることがある

シングルスレッドのプログラムからは、これらは見えません。CPU が辻褄を合わせるからです。

**しかし、複数のスレッドが同じメモリを触ると、この辻褄合わせは効きません。** あるスレッドから見た書き込み順が、別のスレッドからは違って見えます。第 6 章で扱う**メモリモデル**と**メモリバリア**は、この問題に対処するためのものです。

## まとめ

- スーパースカラ：実行ユニットを複数持ち、同時に複数命令を完了させる
- アウトオブオーダー実行：依存関係を守る範囲で順番を入れ替える。確定だけは順番通り
- レジスタリネーミング：名前の使い回しによる偽の依存を消す
- SIMD：1 命令で複数のデータを処理する。データ並列に効く
- SMT：1 コアに 2 つの命令の流れを載せ、空いた実行ユニットを埋める
- 順序の入れ替えは、マルチスレッドでは観測できてしまう

次は、この流れを外から止める仕組みです。
