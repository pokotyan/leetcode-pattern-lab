## SSH の入口は、ネットワークの入口でもある

前回の第 122 回では、FTP が制御とデータの 2 本の接続を使うために、暗号化するとファイアウォールが中身を読めなくなる事情を見ました。この回は向きが逆です。**SSH の接続は 1 本なのに、その中を何でも通せてしまう**ことを扱います。

第 118 回の最後に、ポートフォワーディングの 3 つのオプション（`-L`、`-R`、`-D`）を表で並べ、「SSH で入れる人は、そのサーバが届く範囲すべてに手が届く」と書きました。この回はその先を見ます。

- 3 つのオプションは、それぞれ**どちら側に、どのアドレスで入口を開ける**のか
- 標準入出力を通す `-W`、IP パケットを通す `-w` は何が違うのか
- サーバの管理者は、どこまで絞れるのか。絞ったつもりで絞れていないのはどこか
- TCP の上に TCP を載せると何が起きるのか
- SSH の上に載っている代表的なプロトコル、Git と Mosh は、SSH の何を使っているのか

どれも第 118 回で見た**チャネル**の使い方の違いです。シェルの代わりに、TCP のバイト列、IP パケット、あるいは別のプログラムの標準入出力を運んでいるだけです。

## 実験の環境

コンテナを 3 つ用意し、ネットワークを 2 つに分けました。`ll119-in` は Docker の `--internal` で作ったので、外へ出られず、`client` からも直接は届きません。`gw` だけが両方につながっています。

```
          ll119-out (172.22.0.0/16)              ll119-in (172.23.0.0/16, internal)
 client ─────────────────────────────── gw ─────────────────────────────── inner
 172.22.0.3                 172.22.0.2 | 172.23.0.2                        172.23.0.3
 ssh クライアント                       sshd                                HTTP :8080 / sshd
```

| 項目 | バージョン |
| --- | --- |
| ホスト | macOS（Darwin 25.2.0、arm64）、Docker 29.2.1（カーネル 6.12.72-linuxkit） |
| コンテナ | `alpine:3.22`（中身は 3.22.6） |
| OpenSSH | 10.0p2（クライアント、サーバとも） |
| Git | 2.49.1 |
| Mosh | 1.4.0 |
| curl | 8.14.1 |
| Python（HTTP サーバ） | 3.12.15 |
| tcpdump | 4.99.5 |

`gw` と `client` は、tun デバイスを使う実験のために `--cap-add NET_ADMIN --device /dev/net/tun` を付けて起動しています。`inner` は `python3 -m http.server 8080` で 1 行の HTML を返します。

```
$ docker exec ll119-client curl -s -m 3 http://ll119-inner:8080/ || echo "(direct: unreachable)"
(direct: unreachable)
```

## -L: 手元に入口を開け、向こう側の宛先へつなぐ

### Alpine の sshd は、既定で転送を断る

まず `-L` で、手元の 18080 番を `inner` の 8080 番へつなごうとしました。

```
$ ssh -N -L 18080:ll119-inner:8080 gw &
$ curl -s -m 3 http://127.0.0.1:18080/; echo curl_rc=$?
curl_rc=56
channel 2: open failed: administratively prohibited: open failed
```

`gw` のログには `refused local port forward: originator 127.0.0.1 port 37816, target ll119-inner port 8080` と残っていました。Alpine の openssh-server は、設定ファイルに `AllowTcpForwarding no` を書いて配っています。OpenSSH 自体の既定値は `yes` です（[sshd_config(5)](https://man.openbsd.org/sshd_config.5)）。

注目したいのは、**`ssh` の起動そのものは成功している**ことです。`-L` の要求は、待ち受けを手元で開くだけで、サーバには何も聞きません。手元の 18080 番に接続が来たときに初めて `direct-tcpip` のチャネルを開こうとし（[RFC 4254 7.2](https://www.rfc-editor.org/rfc/rfc4254.html#section-7.2)）、そこで断られます。`-f -o ExitOnForwardFailure=yes` を付けて起動しても、`ssh` は終了コード 0 で裏に回り、そのまま動き続けました。この設定が拾うのは待ち受けを開けなかった失敗で、後からチャネルを断られる失敗ではありません。

### 許可すると、宛先には gw から接続が来る

`/etc/ssh/sshd_config.d/` に `AllowTcpForwarding yes` を置いて sshd に HUP を送ると、つながりました。

```
$ ssh -f -N -o ExitOnForwardFailure=yes -L 18080:ll119-inner:8080 gw
$ curl -s http://127.0.0.1:18080/
hello from inner
$ ss -ltnp | grep 18080
LISTEN 0  128   127.0.0.1:18080   0.0.0.0:*   users:(("ssh",pid=65,fd=5))
LISTEN 0  128       [::1]:18080      [::]:*   users:(("ssh",pid=65,fd=4))

(inner の HTTP サーバのログ)
172.23.0.2 - - [08/Oct/2026 05:14:59] "GET / HTTP/1.1" 200 -
```

`inner` から見ると、接続してきたのは `172.23.0.2`、つまり `gw` です。手元の `curl` の TCP は手元の `ssh` で終わり、`gw` の sshd が**新しい TCP 接続**を `inner` へ張っています。運ばれているのは TCP のパケットではなく、**バイト列だけ**です。この点は後の「TCP の上に TCP」で効いてきます。

### 手元の入口を誰に開くか

`-L` の待ち受けは、既定で手元のループバックだけです。`-L 0.0.0.0:18081:...` のように待ち受けるアドレスを書くと、そのとおりに開きます。

```
$ ssh -f -N -L 0.0.0.0:18081:ll119-inner:8080 gw
$ ss -ltn | grep 18081
LISTEN 0  128     0.0.0.0:18081   0.0.0.0:*
```

こうすると、**手元のマシンに届く誰もが、`inner` に届く**ようになります。会議の Wi-Fi に `0.0.0.0` で開いた転送を持ち込めば、同じ Wi-Fi にいる人が社内の管理画面に触れます。手元のマシンが入口になる、という意味で、`-L` は手元の管理者の責任です。

## -D: 宛先を接続ごとに決める

`-D` は手元に SOCKS のプロキシを開きます。宛先は固定せず、SOCKS の要求で接続ごとに受け取ります。

```
$ ssh -v -f -N -D 1080 gw
$ curl -s --socks5-hostname 127.0.0.1:1080 http://ll119-inner:8080/
hello from inner
debug1: Connection to port 1080 forwarding to socks port 0 requested.
debug1: channel 2: new dynamic-tcpip [dynamic-tcpip] (inactive timeout: 0)
debug1: channel 2: free: direct-tcpip: listening port 1080 for ll119-inner port 8080, ...
```

最初は `dynamic-tcpip` という仮のチャネルとして受け、SOCKS の要求を読んで宛先が分かった時点で、`-L` と同じ `direct-tcpip` になっています。プロトコル上は `-L` と何も変わりません。

ここで、`--socks5` と `--socks5-hostname` の違いがはっきり出ます。

```
$ curl -sS -m3 --socks5 127.0.0.1:1080 http://ll119-inner:8080/
curl: (97) Could not resolve proxy: 127.0.0.1
$ getent hosts ll119-inner; echo getent=$?
getent=2
```

curl のメッセージは紛らわしいのですが、起きているのは、`client` で `ll119-inner` を名前解決しようとして失敗したことです。SOCKS5 の要求には、宛先を IPv4、IPv6、**ドメイン名**のどれで渡すかの種類があります（[RFC 1928 4](https://www.rfc-editor.org/rfc/rfc1928.html#section-4)）。`--socks5` は手元で名前を引いて IP アドレスを渡し、`--socks5-hostname` は名前のまま渡して、**名前解決も向こう側（sshd）に任せます**。

内側にしかない名前は、向こうで引かなければ解決できません。逆に、「通信は SSH の中に通したのに、名前の問い合わせは手元のネットワークに出ていた」ということも起こります。ブラウザを `-D` に向けるときも、名前解決をプロキシ側でする設定かどうかを確かめます。

## -R: 向こう側に入口を開け、手元の宛先へつなぐ

`-R` は向きが逆で、**サーバ側で待ち受け**、届いた接続をチャネルで手元に戻します。クライアントは `tcpip-forward` という全体要求を送り、接続が来るたびにサーバから `forwarded-tcpip` のチャネルが開かれます（[RFC 4254 7.1, 7.2](https://www.rfc-editor.org/rfc/rfc4254.html#section-7.1)）。

`client` に、ループバックだけで待ち受ける「管理画面」を置き、`gw` 側へ出してみます。

```
(client で)  python3 -m http.server 9000 --bind 127.0.0.1
$ ssh -f -N -o ExitOnForwardFailure=yes -R 19000:127.0.0.1:9000 gw
$ ssh -f -N -o ExitOnForwardFailure=yes -R 0.0.0.0:19001:127.0.0.1:9000 gw

(gw で)
$ ss -ltn | grep -E "1900[01]"
LISTEN 0  128   127.0.0.1:19001   0.0.0.0:*
LISTEN 0  128   127.0.0.1:19000   0.0.0.0:*
LISTEN 0  128       [::1]:19000      [::]:*
LISTEN 0  128       [::1]:19001      [::]:*
$ curl -s http://127.0.0.1:19000/
secret dashboard on client (127.0.0.1 only)

(inner から gw の 19001 へ)
$ curl -s -m3 http://172.23.0.2:19001/; echo inner_rc=$?
inner_rc=7
```

`0.0.0.0` を指定したのに、`gw` は 127.0.0.1 で待ち受けました。sshd の `GatewayPorts` が既定の `no` だからです。sshd_config(5) は、`no` ならリモート転送をループバックに縛り、`yes` ならワイルドカードアドレスに、`clientspecified` ならクライアントの指定どおりに開く、と定めています（[sshd_config(5)](https://man.openbsd.org/sshd_config.5)）。`clientspecified` にして同じことをすると、こうなります。

```
(gw で)
$ ss -ltn | grep 19001
LISTEN 0  128     0.0.0.0:19001   0.0.0.0:*

(inner から)
$ curl -s -m3 http://172.23.0.2:19001/; echo inner_rc=$?
secret dashboard on client (127.0.0.1 only)
inner_rc=0
```

`client` の中でループバックにしか開いていなかったものが、**別のネットワークにいる `inner` から読めました**。

<Callout type="warn" title="リバーストンネルは、内側から外へ穴を開ける">
  `-R` の典型的な使い方は、NAT やファイアウォールの内側にあるマシンから、外のサーバへ SSH をつなぎ、外から内側に入れるようにすることです。
  ファイアウォールが見ているのは「内側から外の 22 番への通常の接続」だけなので、**受信を禁じる規則を素通りします**。
  外のサーバが `GatewayPorts yes` なら、その穴はインターネット全体に開きます。
  守る側から見ると、内側の端末から外への SSH を許すことは、外から内側への入口を作る権限を渡すことと同じです。
  外のサーバの管理者は `PermitListen` や `authorized_keys` の `permitlisten=` で待ち受けを絞れますが（[sshd(8)](https://man.openbsd.org/sshd.8)）、
  内側の組織からは、どの外部サーバがどう設定されているかは見えません。
</Callout>

`-R` の宛先を省いて `-R 1080` とだけ書くと、**サーバ側に SOCKS のプロキシ**が開きます（[ssh(1)](https://man.openbsd.org/ssh.1)）。サーバに入った人が、手元のネットワークを足場に好きな宛先へつなげる形で、`-D` の向きを逆にしたものです。

## サーバの側で絞る

### 鍵ごとに絞る: permitopen と command=

`authorized_keys` の行に、オプションを付けられます。`restrict` は転送、エージェント転送、X11 転送、pty の割り当てなどを一括で禁止し、`port-forwarding` でポートの転送だけを戻し、`permitopen` で行き先を 1 つに絞ります（[sshd(8)](https://man.openbsd.org/sshd.8)）。

```
command="/bin/echo tunnel-only",restrict,port-forwarding,permitopen="ll119-inner:8080" ssh-ed25519 AAAA...
```

```
$ ssh gw id
tunnel-only
$ ssh -f -N -L 18080:ll119-inner:8080 -L 18022:127.0.0.1:22 gw
$ curl -s http://127.0.0.1:18080/
hello from inner
(18022 番へ接続すると)
channel 4: open failed: administratively prohibited: open failed

(gw のログ)
Received request from 172.22.0.3 port 36096 to connect to host 127.0.0.1 port 22, but the request was denied.
```

`command=` を付ける前は、`restrict` を付けていても `ssh gw id` はそのまま実行されました。`restrict` が止めるのは転送や pty で、**コマンドの実行は止めません**。「この鍵はトンネル専用」にするには、`command=` でシェルを取り上げる必要があります。なお `permitopen` のホスト名は文字どおりに比べられ、名前解決もパターンの照合もしません（[sshd(8)](https://man.openbsd.org/sshd.8)）。`ll119-inner:8080` で許可した状態で、同じ `inner` を IP アドレス（`-L 18083:172.23.0.3:8080`）で頼むと、`administratively prohibited` で断られました。

### AllowTcpForwarding no だけでは絞れない

逆に、シェルを渡したまま `AllowTcpForwarding no` にした場合を見ます。`inner` でも sshd を動かし、`gw` 越しに入ります。

```
$ ssh -o ProxyCommand="ssh -W %h:%p gw" alice@ll119-inner hostname; echo "via -W rc=$?"
channel 0: open failed: administratively prohibited: open failed
stdio forwarding failed
Connection closed by UNKNOWN port 65535
via -W rc=255

$ ssh -o ProxyCommand="ssh gw nc %h %p" alice@ll119-inner hostname; echo "via nc rc=$?"
inner
via nc rc=0
```

1 つ目は SSH の転送機能を使うので断られます。2 つ目は `gw` で `nc` を**普通のコマンドとして実行**し、その標準入出力をつないでいるだけなので、転送の設定は関係ありません。sshd_config(5) の `AllowTcpForwarding` の項にも、「利用者がシェルを使える限り、転送を禁止してもセキュリティは上がらない。利用者はいつでも自分で転送役を置けるからだ」という趣旨の注記があります（[sshd_config(5)](https://man.openbsd.org/sshd_config.5)）。

**転送を止めたいなら、シェルも止める**（`command=`、`ForceCommand`、あるいは転送専用のアカウント）。シェルを渡すなら、そのサーバが届く範囲すべてを渡したと考えます。`DisableForwarding yes` は X11、エージェント、TCP、Unix ソケットの転送をまとめて止める設定ですが（同上）、同じ限界があります。

## -W と ProxyCommand: 標準入出力を穴に通す

`-W host:port` は、待ち受けを開かずに、**手元の `ssh` の標準入出力そのもの**を、向こうの `host:port` への `direct-tcpip` チャネルにつなぎます（[ssh(1)](https://man.openbsd.org/ssh.1)）。

```
$ echo | ssh -W ll119-inner:22 gw | head -c 40 | od -c | head -3
0000000   S   S   H   -   2   .   0   -   O   p   e   n   S   S   H   _
0000020   1   0   .   0  \r  \n   I   n   v   a   l   i   d       S   S
0000040   H       i   d   e   n   t   i
```

標準出力に、`inner` の sshd のバージョン文字列（第 118 回）がそのまま出てきました。送った空行には `Invalid SSH identification` と返しています。

`ProxyCommand` は、「TCP の代わりに、このコマンドの標準入出力を使って SSH を話せ」という指定です（[ssh_config(5)](https://man.openbsd.org/ssh_config.5)）。`-W` と組み合わせると、`gw` 越しに `inner` へ入れます。

```
$ ssh -v -o ProxyCommand="ssh -W %h:%p gw" alice@ll119-inner hostname
debug1: Executing proxy command: exec ssh -W ll119-inner:22 gw
debug1: Remote protocol version 2.0, remote software version OpenSSH_10.0
debug1: kex: algorithm: mlkem768x25519-sha256
Authenticated to ll119-inner (via proxy) using "publickey".
inner
```

第 119 回の `ProxyJump` は、これの略記です。`-W` 以前は、上の実験のように踏み台で `nc` を動かすのが定番でした。`ProxyCommand` に渡すのは標準入出力を持つものなら何でもよく、ssh_config(5) には、`nc -X connect -x` で HTTP プロキシの `CONNECT` を越える例も載っています（[ssh_config(5)](https://man.openbsd.org/ssh_config.5)）。**SSH から見ると、下が TCP でも、別の SSH のチャネルでも、HTTP プロキシでも同じ**です。

## -w: IP パケットを運ぶ

ここまでの転送は、どれも TCP の**中身のバイト列**を運んでいました。`-w` は違います。両端に **tun デバイス**（第 3 層の仮想インターフェース）を作り、その間で **IP パケットそのもの**を運びます（[ssh(1)](https://man.openbsd.org/ssh.1)）。OpenSSH はこれを `tun@openssh.com` という独自のチャネルで実装していて、1 つのデータの先頭に 4 バイトのアドレスファミリ（IPv4 は 2、IPv6 は 24）を付けて送ります（[OpenSSH の PROTOCOL 文書](https://github.com/openssh/openssh-portable/blob/master/PROTOCOL)）。

サーバには `PermitTunnel`（既定は `no`）を設定します。tun デバイスを作るには特権が要るので、ここでは `gw` の root で入りました。

```
(gw の sshd_config.d)
PermitTunnel point-to-point
PermitRootLogin prohibit-password

$ ssh -f -o ExitOnForwardFailure=yes -w 0:0 root@ll119-gw \
    "ip addr add 192.0.2.2/30 dev tun0 && ip link set tun0 up && sleep 1800"
$ ip addr add 192.0.2.1/30 dev tun0 && ip link set tun0 up
$ ip -d link show tun0 | head -3
12: tun0: <POINTOPOINT,MULTICAST,NOARP,UP,LOWER_UP> mtu 1500 qdisc pfifo_fast state UNKNOWN ...
    link/none  promiscuity 0 allmulti 0 minmtu 68 maxmtu 65535
    tun type tun pi off vnet_hdr off persist off ...
$ ping -c 3 192.0.2.2
64 bytes from 192.0.2.2: icmp_seq=1 ttl=64 time=1.06 ms
64 bytes from 192.0.2.2: icmp_seq=2 ttl=64 time=0.377 ms
64 bytes from 192.0.2.2: icmp_seq=3 ttl=64 time=2.02 ms
```

TCP ではない ICMP が通りました。`gw` で、tun0 と eth0 を同時に覗きます。

```
(tun0)
05:17:03.122175 IP 192.0.2.1 > 192.0.2.2: ICMP echo request, id 39562, seq 1, length 64
05:17:03.122242 IP 192.0.2.2 > 192.0.2.1: ICMP echo reply, id 39562, seq 1, length 64

(eth0)
05:17:03.121999 IP 172.22.0.3.33280 > 172.22.0.2.22: Flags [P.], seq 801077529:801077653, ..., length 124
05:17:03.122022 IP 172.22.0.2.22 > 172.22.0.3.33280: Flags [.], ack 124, ..., length 0
05:17:03.122311 IP 172.22.0.2.22 > 172.22.0.3.33280: Flags [P.], seq 1:125, ack 124, ..., length 124
```

経路の上に見えるのは、22 番への TCP だけです。84 バイトの IP パケット（IP ヘッダ 20 + ICMP 8 + データ 56）が、124 バイトの SSH のデータになっています。内訳は次のように計算でき、観測した値と合います。

```
  84  IP パケット
+  4  アドレスファミリ（tun@openssh.com）
+  9  CHANNEL_DATA の種類 1、チャネル番号 4、データ長 4
+  7  padding_length 1、パディング 6（第 118 回の形。長さの欄を除いて 8 の倍数に揃える）
+  4  packet_length
+ 16  Poly1305 のタグ（chacha20-poly1305）
= 124
```

`-w` を使えば、経路を足すだけで `gw` の向こうのネットワーク全体に届く、**簡易な VPN** になります。ただし ssh(1) 自身が、SSH を使った構成はオーバーヘッドが大きいので一時的な用途に向く、と書いています（[ssh(1)](https://man.openbsd.org/ssh.1) の SSH-BASED VIRTUAL PRIVATE NETWORKS）。理由の 1 つが次の節です。恒常的な VPN は第 125 回と第 141 回で扱います。

## TCP の上に TCP を載せる

`-w` の中を流れる TCP は、**TCP（SSH）の上の TCP** になります。この組み合わせの問題は、Olaf Titz の文書（最終更新は 2001 年）でよく知られています（[Why TCP Over TCP Is A Bad Idea](https://wiretapped.mirrorservice.org/network-security/cipe/docs/tcp-tcp.html)）。要点は次のとおりです。

- 外側の TCP は、損失が起きると再送し、再送タイマを伸ばす（第 54 回の RTO）
- 内側の TCP からは、損失は見えず、**ただ ACK が遅れる**ように見える。内側のタイマがまだ短ければ、内側も再送を始める
- 外側は配送を保証しているので、内側の再送はすべて無駄で、外側の待ち行列を伸ばすだけになる。Titz はこれを「内部の崩壊（meltdown）」と呼んだ

`gw` の eth0 に `tc qdisc add dev eth0 root netem delay 40ms loss 3%` で遅延と損失を足し、30 MB のファイルを、tun の中（`192.0.2.2:8000`）と外（`172.22.0.2:8001`）から 1 回ずつ取りました。転送中、`gw` で毎秒 `ss -tin` を取っています。

```
tunnel: 30000000 bytes in 141.128760s
direct: 30000000 bytes in 114.667488s
```

```
(内側の TCP: 192.0.2.2:8000 → 192.0.2.1、転送の終盤)
rto:17895 rtt:9978.74/126.97 ... bytes_retrans:1448 ... retrans:0/1 dsack_dups:1 ... minrtt:41.723

(外側の TCP: SSH の 22 番、同じ時刻)
rto:243 rtt:42.063/1.351 ... bytes_retrans:291164 ... retrans:1/206 lost:2 ... minrtt:40
```

読み取れることは次のとおりです。

- 損失を取り戻しているのは外側です。外側は 206 回再送し、RTT は 42 ミリ秒のままです
- 内側は 1 回しか再送しておらず、しかも `dsack_dups:1`（受け手から「その分はもう届いている」と知らされた）なので、**その 1 回は無駄な再送**でした
- 内側の RTT は、最小で 41.7 ミリ秒なのに、平均では **約 10 秒**に膨らみ、RTO は約 18 秒になっています。外側の TCP の送信バッファに、内側のデータが溜まって待たされているからです
- 時間は外より約 23% 長くかかりました

この実験では、Titz の書いた「崩壊」までは起きませんでした。内側の RTT の見積もりが待ち行列ごと膨らんだので、内側のタイマが外側より先に切れる状況にならなかったのです。代わりに見えたのは、**内側の TCP が経路の状態を正しく測れなくなる**ことです。内側の輻輳制御は 10 秒の RTT を前提に動き、外側の待ち行列はさらに伸び、内側を流れる対話的な通信（SSH の上の SSH など）は、その待ち行列の後ろに並びます。損失がもっと多い、あるいは一時的に途切れる回線では、内側のタイマが切れて再送が重なる場面も起こり得ます。1 回の実験なので、数字はこの条件での一例として読んでください。

<Callout type="warn" title="よくある誤解: SSH のポートフォワーディングは、どれも TCP over TCP">
  `-L`、`-R`、`-D`、`-W` は、手元と sshd で TCP を**終わらせ**、中身のバイト列だけをチャネルで運びます。
  宛先への TCP は sshd が新しく張り直すので（`inner` のログの送り元は `gw` でした）、TCP の再送や輻輳制御が二重に動くことはありません。
  二重になるのは、`-w` のように **IP パケットごと**運ぶときだけです。
  ただし、バイト列を運ぶ転送にも別の弱点はあります。複数の転送が 1 本の SSH の TCP を共有するので、1 つのパケットの損失が全チャネルを止めます（第 54 回の HOL ブロッキング）。
  UDP を運べないのも同じ理由です。トンネルの下に UDP を使う VPN が多いのは、この 2 つを避けるためです（第 125 回）。
</Callout>

実験の後、netem は外しました。

## ControlMaster: 1 本の接続を使い回す

チャネルを多重化できるなら、**認証済みの 1 本の SSH 接続**を、後から起動した別の `ssh` とも共有できるはずです。それが `ControlMaster` です。最初の `ssh` が Unix ソケットで待ち受け、後の `ssh` はそこへチャネルを開く要求を出すだけになります（[ssh_config(5)](https://man.openbsd.org/ssh_config.5)）。

```
$ time (for i in $(seq 10); do ssh gw true; done)
real	0m1.680s

$ ssh -o ControlMaster=auto -o ControlPath=/tmp/cm-%C -o ControlPersist=60 gw true
$ ssh -o ControlPath=/tmp/cm-%C -O check gw
Master running (pid=255)
$ time (for i in $(seq 10); do ssh -o ControlPath=/tmp/cm-%C gw true; done)
real	0m0.157s

$ ssh -v -o ControlPath=/tmp/cm-%C gw hostname 2>&1 | grep -E "mux|Authenticated|kex"
debug1: mux_client_request_session: master session id: 2
```

10 回の接続が 1.68 秒から 0.157 秒になりました。2 回目以降は、`kex:` も `Authenticated` も出ていません。鍵交換も認証もせず、既存の接続にチャネルを足しているだけだからです。`gw` 側の `ss` でも、確立済みの 22 番の接続は 1 本だけでした。Ansible の SSH 接続の既定の引数が `-C -o ControlMaster=auto -o ControlPersist=60s` になっているのはこのためです（[Ansible の ssh connection](https://docs.ansible.com/ansible/latest/collections/ansible/builtin/ssh_connection.html)）。

裏返すと、**制御ソケットに話しかけられる者は、認証なしにそのサーバでコマンドを実行できます**。手元のソケットは `srw-------`（所有者だけ）で作られていましたが、第 119 回のエージェント転送と同じく、守りはファイルの権限だけです。共有のマシンでは `ControlPath` を他人の書けないディレクトリに置き、`ControlPersist` を必要以上に長くしないことです。また、多重化された `ssh` に付けたオプションの一部（たとえば別の鍵）は、既存の接続には効きません。認証をやり直したいときは `-O exit` で親を閉じます。

## X11 転送とエージェント転送

チャネルで運べるものには、ほかに X11 の画面とエージェントがあります。

- **X11 転送**（`-X`、`-Y`）は、サーバ上の GUI アプリケーションの描画を手元の X サーバに送ります（[RFC 4254 6.3](https://www.rfc-editor.org/rfc/rfc4254.html#section-6.3)）。ssh(1) は、リモート側でファイルの権限を越えられる者が転送を通じて手元の画面に触れ、キー入力の監視などができてしまう、と警告しています（[ssh(1)](https://man.openbsd.org/ssh.1)）。sshd の `X11Forwarding` の既定は `no` です（[sshd_config(5)](https://man.openbsd.org/sshd_config.5)）
- **エージェント転送**（`-A`）は、第 119 回で実際に root から署名を代行させました。構図は X11 と同じで、**手元の資源への窓口を、相手のサーバに置く**転送です

`-L` が「相手側のネットワークへの入口を手元に置く」のに対し、X11、エージェント、`-R` は「手元への入口を相手側に置く」転送です。**相手のサーバをどこまで信頼するか**で、使ってよいかが決まります。

## Git over SSH: 2 つのコマンドを exec する

### git は ssh にコマンドを 1 行渡すだけ

Git の SSH の転送は、サーバで `git-upload-pack`（取得用）か `git-receive-pack`（送信用）を `exec` で起動し、その標準入出力で Git のプロトコルを話すだけです（[gitprotocol-pack](https://git-scm.com/docs/gitprotocol-pack)）。`gw` に `git` というユーザと空のリポジトリ `/srv/git/demo.git` を用意し、push してみます。

```
$ GIT_SSH_COMMAND="ssh -v" git push origin main
debug1: Sending command: git-receive-pack 'demo.git'
 * [new branch]      main -> main
```

`git@host:path` の形の URL は、パスがホームディレクトリからの相対になり、リポジトリのパスは必ず単引用符で囲まれます（[gitprotocol-pack](https://git-scm.com/docs/gitprotocol-pack)）。SSH から見ると、`ssh gw "git-receive-pack 'demo.git'"` と何も変わりません。第 118 回の `session` チャネルと `exec` 要求です。

### プロトコル v2 は、環境変数で頼む

取得のときの様子を `GIT_TRACE_PACKET` で見ます。git が起動する `ssh` のコマンド行は次のとおりでした。

```
$ GIT_TRACE=1 git ls-remote git@ll119-gw:demo.git
trace: run_command: unset GIT_PREFIX; GIT_PROTOCOL=version=2 ssh -o SendEnv=GIT_PROTOCOL git@ll119-gw 'git-upload-pack '\''demo.git'\'''
```

Git は、**`GIT_PROTOCOL=version=2` という環境変数を SSH で送る**ことで、v2 を話したいと伝えます。gitprotocol-v2 は、ssh:// では `GIT_PROTOCOL` に `version=2` を入れる必要があり、サーバ側でこの変数を通す設定が要る場合がある、と書いています（[gitprotocol-v2](https://git-scm.com/docs/gitprotocol-v2)）。SSH には、`env` 要求で環境変数を渡す仕組みがありますが、sshd は `AcceptEnv` に書かれた名前しか受け取りません（[sshd_config(5)](https://man.openbsd.org/sshd_config.5)）。Alpine の sshd には書かれていないので、最初の clone はこうなりました。

```
(AcceptEnv なし)
packet:  clone< 329682f4944b0792190ef112c9cf6a8c173d503e HEAD\0multi_ack thin-pack side-band ...
packet:  clone< 329682f4944b0792190ef112c9cf6a8c173d503e refs/heads/main
packet:  clone< 0000
packet:  clone> want 329682f4944b0792190ef112c9cf6a8c173d503e multi_ack_detailed side-band-64k ...
packet:  clone> done
packet:  clone< NAK
```

サーバは接続するなり**すべての ref** を広告する、v0 の動きです。`AcceptEnv GIT_PROTOCOL` を足すと、同じ clone がこう変わりました。

```
(AcceptEnv GIT_PROTOCOL)
packet:  clone< version 2
packet:  clone< agent=git/2.49.1-Linux
packet:  clone< ls-refs=unborn
packet:  clone< fetch=shallow wait-for-done
packet:  clone< server-option
packet:  clone< object-format=sha1
packet:  clone< 0000
packet:  clone> command=ls-refs
packet:  clone> agent=git/2.49.1-Linux
packet:  clone> object-format=sha1
packet:  clone> 0001
packet:  clone> peel
packet:  clone> symrefs
packet:  clone> unborn
packet:  clone> ref-prefix refs/heads/
packet:  clone> ref-prefix refs/tags/
packet:  clone> ref-prefix HEAD
packet:  clone> 0000
packet:  clone< 329682f4944b0792190ef112c9cf6a8c173d503e HEAD symref-target:refs/heads/main
```

v2 では、サーバはまず**できること（capability）**だけを伝え、クライアントが `ls-refs` で欲しい ref の接頭辞を指定してから一覧が返ります。ref が何十万もあるリポジトリでは、この違いが大きく効きます。各行の先頭（トレースでは省かれています）には 4 桁の 16 進数で長さが付き、`0000` は区切り（flush-pkt）、`0001` は引数との区切り（delim-pkt）です（[gitprotocol-v2](https://git-scm.com/docs/gitprotocol-v2)）。第 118 回の SSH のパケット、第 65 回の HTTP/2 のフレームと同じく、**長さが先にある形**です。

v2 を既定にしたのは Git 2.26 で（[2.26.0 のリリースノート](https://github.com/git/git/blob/master/Documentation/RelNotes/2.26.0.adoc)）、不具合のため 2.27 でいったん既定から外され（[2.27.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.27.0.adoc)）、2.29 で再び既定になりました（[2.29.0](https://github.com/git/git/blob/master/Documentation/RelNotes/2.29.0.adoc)）。なお、push のときは、`AcceptEnv` を足した後でも `GIT_PROTOCOL` は空で届き、`git-receive-pack` は v0 の形で ref を広告しました。

<Callout type="tip" title="自分のサーバで v2 が効いているか">
  `GIT_TRACE_PACKET=1 git ls-remote <URL> 2>&1 | head` で、最初の行が `version 2` かどうかを見れば分かります。
  SSH で運用している Git サーバで v0 になっていたら、sshd の `AcceptEnv` を確かめます。
  `GIT_TRACE` には、ssh に渡したコマンド行がそのまま出るので、パスの書き方の確認にも使えます。
</Callout>

### 鍵 1 本で利用者を決める

GitHub などでは、誰もが `git@github.com` という**同じユーザ名**で入ります。それでも誰が来たかが分かるのは、**どの鍵で認証したか**から利用者を決めているからです。`ssh -T git@github.com` を打つと `Hi USERNAME! You've successfully authenticated, but GitHub does not provide shell access.` と返ります（[GitHub Docs](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/testing-your-ssh-connection)）。GitHub の内部の実装は公開されていませんが、同じ振る舞いは、第 119 回の `authorized_keys` と `command=` で作れます。

```
command="/usr/local/bin/gitshell alice",restrict ssh-ed25519 AAAA... alice@client
command="/usr/local/bin/gitshell bob",restrict ssh-ed25519 AAAA... bob@client
```

`command=` を付けた鍵で認証すると、クライアントが頼んだコマンドの代わりにそのコマンドが実行され、頼んだコマンドは `SSH_ORIGINAL_COMMAND` という環境変数で渡されます（[sshd(8)](https://man.openbsd.org/sshd.8)）。`gitshell` は、引数で受けた利用者名と `SSH_ORIGINAL_COMMAND` を見て、`git-upload-pack '...'` か `git-receive-pack '...'` の形のときだけ、決めたディレクトリの下のリポジトリで `exec` するシェルスクリプトです。

```
$ ssh -T git@ll119-gw
Hi alice! You've authenticated, but this server does not provide shell access.
$ ssh -T -i ~/.ssh/id_bob -o IdentitiesOnly=yes git@ll119-gw
Hi bob! You've authenticated, but this server does not provide shell access.
$ ssh git@ll119-gw "cat /etc/passwd"
command not allowed

(gitshell のログ)
05:23:54 user=alice cmd=[git-receive-pack 'demo.git'] GIT_PROTOCOL=[]
05:24:06 user=alice cmd=[git-upload-pack 'demo.git'] GIT_PROTOCOL=[version=2]
```

この形には、次の帰結があります。

- **1 本の鍵は 1 人の利用者にしか結び付けられません**。GitHub でも、別のアカウントや別のリポジトリにすでに登録した鍵を追加しようとすると `Key is already in use` になり、デプロイキーは 1 つのリポジトリにしか使えません（[GitHub Docs](https://docs.github.com/en/authentication/troubleshooting-ssh/error-key-already-in-use)）
- 認証（どの鍵か）は sshd がし、**認可（そのリポジトリに push してよいか）は `command=` の先のプログラムの仕事**です。sshd はリポジトリのことを何も知りません。第 19 章の「認証と認可を分ける」の小さな実例です
- `SSH_ORIGINAL_COMMAND` は**利用者が自由に書ける文字列**です。シェルに渡して評価すれば、コマンドの注入になります。決まった形にだけ一致させ、パスに `..` や `/` を許さず、`exec` に引数として渡すのが基本です

Git には、この役を受け持つ制限付きのシェル `git-shell` も付いていて、Git の送受信のコマンドだけを実行させられます（[git-shell](https://git-scm.com/docs/git-shell)）。

## Mosh: SSH は最初の鍵渡しにだけ使う

Mosh は、SSH とは逆の発想のリモートシェルです。**SSH は起動と鍵の受け渡しにだけ使い**、その後の通信は UDP の上の独自プロトコル SSP（State Synchronization Protocol）に任せます（[mosh.org](https://mosh.org/)、[Winstein と Balakrishnan, USENIX ATC 2012](https://www.usenix.org/conference/atc12/technical-sessions/presentation/winstein)）。

### SSH の上で何が起きているか

`mosh` は、まず SSH でサーバに入り、`mosh-server` を起動します。手で同じことをすると、こう返ります。

```
$ ssh -v gw -- "LANG=C.UTF-8 mosh-server new -s -l LANG=C.UTF-8"
debug1: Sending command: LANG=C.UTF-8 mosh-server new -s -l LANG=C.UTF-8
MOSH CONNECT 60001 CoLPsgjKwGnSedxjZpwq7w
mosh-server (mosh 1.4.0) [build mosh 1.4.0]
[mosh-server detached, pid = 583]

(gw で、SSH が閉じた後)
alice   583  ...  mosh-server new -s -l LANG=C.UTF-8
UNCONN 0  0   172.22.0.2:60001   0.0.0.0:*
```

`MOSH CONNECT` の行が、UDP のポート番号と、22 文字のセッション鍵です（[mosh.org](https://mosh.org/)）。この行は**SSH の暗号化された `exec` チャネルの出力として**クライアントに届きます。`mosh-server` は自分を切り離して残り、SSH の接続は閉じます。データグラムは、この鍵を使って AES-128 の OCB3 モード（第 107 回の AEAD の 1 つ）で暗号化と認証をされます（[mosh.org](https://mosh.org/)）。

つまり Mosh の信頼の根は、**最初の SSH 接続**にあります。サーバを確かめたのは SSH のホスト鍵（第 118 回）、利用者を確かめたのは SSH の公開鍵認証で、Mosh 自身はサーバの鍵も利用者の鍵も持ちません。「SSH で安全に渡した使い捨ての共通鍵で、別の通信路を守る」という形です。

実際に `mosh gw` を動かし、`gw` の eth0 を見ました（`client` はコンテナなので、`script` で擬似端末を用意して起動しています）。

```
05:25:02.411789 IP 172.22.0.3.55664 > 172.22.0.2.22: Flags [S], ...   SSH の開始
05:25:02.500686 IP 172.22.0.3.55664 > 172.22.0.2.22: Flags [.], ...   SSH の終わり
05:25:02.508023 IP 172.22.0.3.39967 > 172.22.0.2.60001: UDP, length 81
05:25:02.511387 IP 172.22.0.2.60001 > 172.22.0.3.39967: UDP, length 68
05:25:02.759429 IP 172.22.0.2.60001 > 172.22.0.3.39967: UDP, length 109
```

SSH が使われたのは最初の約 0.1 秒だけで、その直後から UDP に切り替わっています。

### 送り元が変わっても続く

Mosh のサーバは、**認証の通った最新のデータグラムの送り元**へ返事を送ります。`client` で 2 秒ごとに時刻を表示させ、途中で `client` の送り元アドレスを変えてみました（`ip addr add 172.22.0.100/16` と、経路の `src` の書き換え。Wi-Fi から携帯の回線へ移ったのに相当します）。

```
05:25:45 172.22.0.2.60001 > 172.22.0.3.36536
05:25:45 172.22.0.3.36536 > 172.22.0.2.60001
05:25:47 172.22.0.2.60001 > 172.22.0.3.36536      ← まだ古いアドレスへ
05:25:47 172.22.0.100.36536 > 172.22.0.2.60001    ← 新しいアドレスから
05:25:49 172.22.0.2.60001 > 172.22.0.100.36536    ← 以後は新しいアドレスへ
05:25:49 172.22.0.100.36536 > 172.22.0.2.60001

(client の画面に出た時刻)
05:25:38 05:25:40 05:25:42 05:25:44 05:25:46 05:25:49 05:25:51 05:25:53 05:25:55 05:25:57 05:25:59 05:26:01
```

サーバはすぐに新しいアドレスへ返事を送り始め、画面の表示も途切れずに続きました。TCP の上の SSH なら、送り元のアドレスが変わった時点でその接続は使えなくなります（第 53 回の 4 つ組）。Mosh は「接続」を持たず、**鍵で認証できたデータグラムなら、どこから来ても同じセッション**と見なすので、こうなります。第 76 回の QUIC の接続移行と同じ考え方です。

### 代わりに失うもの

SSP が同期するのは**端末の画面の状態**で、バイト列ではありません。最新の画面だけを送ればよいので、途中の出力を飛ばせますし、遅い回線ではキー入力を予測して先に表示できます。これは第 79 回のゲームの状態同期と同じ発想です。その代わり、mosh.org によれば、同期されるのは見えている画面だけで、スクロールバックは残りません（[mosh.org](https://mosh.org/)）。運用の面では、SSH の 22 番に加えて **UDP の 60000〜61000 番**を開ける必要があり（同上）、`mosh-server` は SSH が閉じた後も利用者の権限で動き続けます。

| `-L` | TCP のバイト列 | `direct-tcpip` | `AllowTcpForwarding`、`PermitOpen` | 手元 |
| `-D` | TCP のバイト列（宛先は SOCKS で） | `direct-tcpip` | 同上 | 手元 |
| `-R` | TCP のバイト列 | `tcpip-forward` と `forwarded-tcpip` | 同上、`GatewayPorts`、`PermitListen` | サーバ |
| `-W` / ProxyCommand | 標準入出力 | `direct-tcpip` | `AllowTcpForwarding` | なし |
| `-w` | IP パケット | `tun@openssh.com` | `PermitTunnel` | 両端の tun |
| ControlMaster | 後から来た ssh のチャネル | 既存の接続を共有 | （クライアント側） | 手元の Unix ソケット |
| Git | Git のプロトコル | `exec` と `env` | `AcceptEnv`、`command=` | なし |
| Mosh | 起動と鍵の受け渡しだけ | `exec` | （UDP のポートを開ける） | サーバの UDP |

どの行も、第 118 回で見たチャネルを、違う相手につないでいるだけです。そして、どの行についても「シェルを渡した利用者は、自分で同じものを作れる」ことは変わりません。**SSH で入れることを許すとき、許しているのはシェルだけではない**、と考えるのが出発点です。

次の第 124 回では、SSH から TLS に戻り、PostgreSQL や MySQL のようなデータベースが、平文で始まった接続をどう TLS に切り替えるのか、そして接続の設定の既定値が中間者に対して何を守り、何を守らないのかを見ます。

## まとめ

- `-L`、`-D`、`-W` は `direct-tcpip`、`-R` は `tcpip-forward` と `forwarded-tcpip` のチャネルで、どれも TCP を両端で終わらせ、**中身のバイト列だけ**を運ぶ。宛先から見た送り元は sshd のマシン
- `-L` の待ち受けを `0.0.0.0` にすると手元が入口になる。`-R` の待ち受けはサーバの `GatewayPorts`（既定 `no`）でループバックに縛られ、`clientspecified` や `yes` にすると内側のサービスが外に出る
- `-D` は SOCKS のプロキシ。宛先を名前のまま渡すかどうかで、名前解決をする場所が変わる
- `restrict`、`permitopen`、`permitlisten`、`command=` で鍵ごとに絞れる。**シェルを渡したまま `AllowTcpForwarding no` にしても、`nc` で同じことができる**
- `ProxyCommand` は SSH の下を任意の標準入出力に差し替える仕組みで、`-W` と組み合わせたものの略記が `ProxyJump`
- `-w` は tun デバイスの間で IP パケットを運ぶ簡易な VPN。中の TCP は TCP の上の TCP になり、手元の実験では内側の RTT が最小 42 ミリ秒から平均約 10 秒に膨らみ、無駄な再送も出た
- ControlMaster は認証済みの接続を共有する。速くなる代わりに、制御ソケットに触れる者は認証なしでコマンドを実行できる
- Git over SSH は `git-upload-pack` / `git-receive-pack` を `exec` するだけ。v2 は `GIT_PROTOCOL` 環境変数で頼み、サーバの `AcceptEnv` がないと v0 になる。GitHub 型のサーバは鍵から利用者を決め、`command=` の先で認可する
- Mosh は SSH で `mosh-server` を起動して鍵を受け取り、以後は UDP の SSP（AES-128 OCB3）で画面の状態を同期する。信頼の根は最初の SSH にあり、送り元のアドレスが変わってもセッションが続く
