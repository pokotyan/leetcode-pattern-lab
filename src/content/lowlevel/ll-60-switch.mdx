## 第 9 章から第 10 章へ

## Ethernet フレームの形

2 層目で運ばれるデータの単位を**フレーム**と呼びます。有線 LAN の Ethernet のフレームは次の形をしています。

```
+-----------+-----------+-----------+------------------------+-----+
| 宛先 MAC  | 送信元 MAC | EtherType | ペイロード              | FCS |
|  6 バイト |  6 バイト  |  2 バイト | 46〜1500 バイト         | 4   |
+-----------+-----------+-----------+------------------------+-----+
```

- **宛先 MAC アドレス**：誰に届けるか。先頭に置かれているので、受け取った機械は最初の 6 バイトを読んだ時点で自分宛てかどうかが分かる
- **送信元 MAC アドレス**：誰が送ったか。後で見るとおり、スイッチはここを読んで学習する
- **EtherType**：ペイロードの中身が何か。`0x0800` なら IPv4、`0x86DD` なら IPv6、`0x0806` なら ARP
- **FCS**（Frame Check Sequence）：途中でビットが化けていないかを確かめる CRC。化けていたフレームは黙って捨てられる

ペイロードの最大の 1500 バイトが、第 68 回で見る **MTU** の正体です。最小が 46 バイトなのは、ヘッダと FCS を足したフレーム全体が 64 バイトを下回らないようにするためで、足りない分は詰め物（パディング）で埋めます。

後の実測で `tcpdump` が ARP のフレームを `length 42` と表示します。これはヘッダ 14 バイトと ARP の本体 28 バイトの和で、パディングと FCS を含みません。実験に使う仮想的なリンク（veth）は電線を通らないので、パディングも FCS も付けずに受け渡しています。

## MAC アドレスの中身

MAC アドレスは 48 ビット（6 バイト）の識別子で、`02:00:00:00:00:01` のように 16 進数で書きます。製造時にネットワークカードに書き込まれるものは、先頭 3 バイトが製造元を表す OUI（Organizationally Unique Identifier）で、IEEE から割り当てられます。残りを製造元が重ならないように振るので、世界で一意になります。

先頭のバイトの下位 2 ビットには特別な意味があります。IEEE 802 のアドレスの扱いを IETF の側からまとめた RFC 9542 は、最下位のビット（M ビット）を「This bit is frequently referred to as the "group" or "multicast" bit. If it is zero, the MAC address is unicast. If it is a one, the address is groupcast (multicast or broadcast).」と説明しています（[RFC 9542 2.1](https://www.rfc-editor.org/rfc/rfc9542.html#section-2.1)）。その 1 つ上のビット（X ビット）は「universal/local」ビットで、0 なら IEEE から割り当てられた接頭辞の持ち主が管理する世界で一意のアドレス、1 ならそのネットワークの管理者が自分で決めたアドレスです。

| 先頭のバイト | M ビット | X ビット | 意味 |
| --- | --- | --- | --- |
| `00` | 0 | 0 | 世界で一意のユニキャスト（製造時のアドレス） |
| `02` | 0 | 1 | 管理者が決めたユニキャスト |
| `01` | 1 | 0 | マルチキャスト（例: IPv4 マルチキャストは `01:00:5e:...`） |
| `ff`（全部 1） | 1 | 1 | ブロードキャスト `ff:ff:ff:ff:ff:ff`。全員宛て |

この回の実験では、端末に `02:00:00:00:00:01` から `02:00:00:00:00:04` を手で付けます。X ビットが 1 なので、どこかの製品のアドレスと衝突することはありません。

<Callout type="note" title="スマートフォンの MAC アドレスは毎回違う">
  最近のスマートフォンや PC は、Wi-Fi に接続するときに、製造時のアドレスではなく**ランダムに作ったアドレス**を使います。作ったアドレスは X ビットが 1 です。製造時のアドレスを使い続けると、どこの Wi-Fi に現れたかで持ち主を追跡できてしまうためです。第 56 回で見た Bluetooth のアドレスのランダム化と同じ考え方です。
</Callout>

## ハブ、ブリッジ、スイッチ

複数の機械を 1 つの L2 ネットワークにまとめる箱は、時代とともに賢くなってきました。

**ハブ**は、あるポートに届いた信号を、ほかの全ポートにそのまま流します。宛先を読みません。つながった全員が同じ線を共有しているのと同じなので、2 台が同時に送ると信号がぶつかります（衝突）。ぶつかる範囲を**コリジョンドメイン**と呼び、ハブにつながった全員が 1 つのコリジョンドメインに入ります。初期の Ethernet は、送る前に線が空いているかを聞き、ぶつかったら待ってやり直す方式（CSMA/CD）でこれに対処していました。第 55 回の Wi-Fi が今もやっている CSMA/CA と同じ発想です。

**ブリッジ**は、宛先 MAC アドレスを読み、必要な側にだけフレームを渡す箱です。もともとは 2 つの線をつなぐ 2 ポートの装置でした。

**スイッチ**は、ポートの多いブリッジです。仕組みはブリッジと同じで、Linux のカーネル文書も、IEEE 802.1Q（ブリッジの標準）を引いて「The purpose of a bridge is to filter and forward frames between different segments based on the destination MAC (Media Access Control) address.」と説明しています（[Linux kernel: Ethernet Bridging](https://docs.kernel.org/networking/bridge.html)）。

今のスイッチは、ポートごとに機械が 1 台だけつながり、送る線と受ける線が別になっています（**全二重**）。こうすると、ぶつかる相手がいないので衝突が起きません。コリジョンドメインはポートごとに分かれ、実質的に消えます。

## 送信元で覚えて、宛先で選ぶ

スイッチは、どのポートの先に誰がいるのかを、設定されなくても自分で覚えます。覚えた内容を **MAC アドレステーブル**（Linux では FDB、Forwarding Database）と呼びます。規則は 4 つだけです。

1. **学習**：フレームが届いたら、**送信元**の MAC アドレスと、届いたポートの組を覚える
2. **転送**：**宛先**の MAC アドレスがテーブルにあれば、そのポートだけへ送る
3. **フラッディング**：宛先がテーブルに無い、またはブロードキャスト・マルチキャストなら、届いたポート以外の全ポートへ複製して送る
4. **エージング**：一定時間その送信元を見なかったら、テーブルから消す

学習に使うのは送信元だけ、という点が要です。宛先がどこにいるかは、その宛先が**何かを送ってきたとき**に初めて分かります。だから、まだ一度も声を出していない相手への最初のフレームは、全ポートに流れます。

下の SIM で、端末 A〜E とスイッチの間を流れるフレームを 1 つずつ進めてみてください。E は D と同じハブの先にいて、スイッチからはどちらもポート 4 に見えます。

<SwitchLearning client:visible />

「知らない宛先」では、A から B への最初のフレームが C・D・E にも届きます。B が返事をした時点で、スイッチは B の居場所を覚え、2 回目からは B だけに届きます。「ハブの先」では、D から E へのフレームはポート 4 に届き、宛先もポート 4 の先にいるので、スイッチはどこにも送りません。E へはハブが直接届けています。

Linux のカーネルの bridge は、この規則をそのままコードにしています。フレームを受け取る関数の後半は、宛先を FDB で引いて、見つかればそのポートへ、見つからなければ全ポートへ流す、という形です（[net/bridge/br_input.c](https://github.com/torvalds/linux/blob/v6.12/net/bridge/br_input.c)、v6.12 から抜粋）。

```c

		dst = br_fdb_find_rcu(br, eth_hdr(skb)->h_dest, vid);
		break;
	...
	if (dst) {
		...
		br_forward(dst->dst, skb, local_rcv, false);
	} else {
		if (!mcast_hit)
			br_flood(br, skb, pkt_type, local_rcv, false, vid);
```

エージングの既定値は、同じソースの `br_private.h` に `#define BR_DEFAULT_AGEING_TIME	(300 * HZ)` とあり、300 秒です。

## 手元で確かめる: 4 つの端末を Linux bridge につなぐ

Linux の network namespace を使うと、1 台のマシンの中に、ネットワークの設定を別々に持つ「端末」をいくつも作れます。これを 4 つ作って、Linux bridge という仮想のスイッチにつなぎます。

実験の環境は Apple M1 Pro の macOS 26.2 上の OrbStack の Linux VM（カーネル 7.0.14）、その上の Alpine Linux 3.20 のコンテナ（`--privileged`）です。道具は iproute2 6.9.0 と tcpdump 4.99.4 です。

```sh
ip link add br0 type bridge ageing_time 1000   # この値の単位は後の囲みで説明する
ip link set br0 up
for h in A B C D; do                            # A=1, B=2, C=3, D=4
  ip netns add $h
  ip link add veth$h type veth peer name eth0 netns $h   # 端末と bridge をつなぐ仮想の線
  ip link set veth$h master br0 up
  ip -n $h link set eth0 address 02:00:00:00:00:0$i
  ip -n $h addr add 10.0.0.$i/24 dev eth0
  ip -n $h link set eth0 up
done
```

ここで 1 つ準備が要ります。最初の試行では、何も送っていないうちから bridge が 4 台すべてを学習していました。リンクを上げた直後に、各端末の IPv6 が近隣の確認やルーターを探すフレームを自分から送るためです（第 64 回で見ます）。純粋な学習の様子を見るため、各端末の IPv6 を止めてからやり直しました。

### 知らない宛先へのフレームは全員に届く

A には B の MAC アドレスを手で教えておき（ARP を省くため）、B はまだ何も送っていない状態で、A から B へ ping を 2 回送ります。B・C・D の 3 台で、届いたフレームを tcpdump で見ます。

```text
### 1. 通信前の FDB
(学習した項目なし)
--- B が受け取ったフレーム
02:00:00:00:00:01 > 02:00:00:00:00:02, ethertype IPv4 (0x0800), length 98: 10.0.0.1 > 10.0.0.2: ICMP echo request, id 64, seq 1, length 64
02:00:00:00:00:02 > 02:00:00:00:00:01, ethertype IPv4 (0x0800), length 98: 10.0.0.2 > 10.0.0.1: ICMP echo reply, id 64, seq 1, length 64
02:00:00:00:00:01 > 02:00:00:00:00:02, ethertype IPv4 (0x0800), length 98: 10.0.0.1 > 10.0.0.2: ICMP echo request, id 64, seq 2, length 64
02:00:00:00:00:02 > 02:00:00:00:00:01, ethertype IPv4 (0x0800), length 98: 10.0.0.2 > 10.0.0.1: ICMP echo reply, id 64, seq 2, length 64
--- C が受け取ったフレーム
02:00:00:00:00:01 > 02:00:00:00:00:02, ethertype IPv4 (0x0800), length 98: 10.0.0.1 > 10.0.0.2: ICMP echo request, id 64, seq 1, length 64
--- D が受け取ったフレーム
02:00:00:00:00:01 > 02:00:00:00:00:02, ethertype IPv4 (0x0800), length 98: 10.0.0.1 > 10.0.0.2: ICMP echo request, id 64, seq 1, length 64

02:00:00:00:00:01 dev vethA used 2/2 master br0
02:00:00:00:00:02 dev vethB used 2/2 master br0
```

1 回目の要求（`seq 1`）は、宛先が B なのに C と D にも届いています。B の居場所をまだ知らないので、bridge が全ポートへ流したからです。B が返事をすると bridge は B を `vethB` の先にいると覚え、2 回目の要求（`seq 2`）は B にしか届いていません。C と D の行には `seq 2` がありません。

C と D は、自分宛てでないフレームを受け取っても、宛先 MAC アドレスが自分のものでないので捨てます。tcpdump はネットワークカードを「自分宛て以外も受け取る」モード（プロミスキャスモード）にして見ているので、捨てられる前のフレームが見えています。

### 覚えたことは忘れる

`ageing_time 1000` にした bridge で、そのまま 12 秒待ちます。

```text
### 3. 学習が消えるまで 12 秒待つ（ageing_time 10 秒）
(学習した項目なし)
```

10 秒間 A も B も何も送らなかったので、項目が消えました。この後に A が B へ送れば、また全ポートに流れます。エージングがあるので、端末を別のポートにつなぎ替えても、しばらくすれば新しい場所を覚え直します。実際には、つなぎ替えた端末が何か 1 つ送った時点で、学習の規則によりすぐに上書きされます。

<Callout type="warn" title="ageing_time の単位は秒ではない">
  `ip-link(8)` の man ページは、`ageing_time` を「the number of seconds a MAC address will be kept in the FDB」と説明しています（[ip-link(8)](https://man7.org/linux/man-pages/man8/ip-link.8.html)）。しかし、上の実験で `1000` を指定すると、項目は約 10 秒で消えました。既定値を表示させると `ageing_time 30000` で、既定の 300 秒とも合いません。

  カーネルの側では、この値を受け取る `br_set_ageing_time` が引数を `clock_t` で受け、`clock_t_to_jiffies(ageing_time)` で変換しています（[net/bridge/br_stp.c](https://github.com/torvalds/linux/blob/v6.12/net/bridge/br_stp.c)）。`clock_t` は 1/100 秒が単位なので、`ip link` で渡す値は **1/100 秒単位**です。300 秒にしたければ `30000` を渡します。
</Callout>

## ARP: IP アドレスから MAC アドレスを引く

ここまでは、A が B の MAC アドレスを手で教えられていました。普通の端末は、相手の **IP アドレス**しか知りません。`ping 10.0.0.2` と打っても、Ethernet のフレームを作るには宛先の MAC アドレスが要ります。この対応を調べるのが **ARP**（Address Resolution Protocol）です。

1982 年の [RFC 826](https://www.rfc-editor.org/rfc/rfc826.html) は、目的を「A protocol is needed to dynamically distribute the correspondences between a &lt;protocol, address&gt; pair and a 48.bit Ethernet address.」と書いています。手順は次のとおりです。

1. A は「10.0.0.2 を持っている人は、10.0.0.1 の私に MAC アドレスを教えて」という ARP 要求を、**ブロードキャスト**で送る
2. 全員がそれを受け取り、10.0.0.2 を持っている B だけが答える。答えは A 宛ての**ユニキャスト**で送る
3. A は答えを **ARP キャッシュ**に覚え、以後しばらくは問い合わせずに使う

RFC 826 も、B が答えを「sends the packet directly (not broadcast) to EA(X)」、つまり問い合わせた本人に直接返すと書いています。

`ARP から始める` のプリセットと同じことを、C から D への ping で確かめます。今度は ARP キャッシュを手で入れていません。

```text
--- B が受け取ったフレーム
02:00:00:00:00:03 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 10.0.0.4 tell 10.0.0.3, length 28
--- D が受け取ったフレーム
02:00:00:00:00:03 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 10.0.0.4 tell 10.0.0.3, length 28
02:00:00:00:00:04 > 02:00:00:00:00:03, ethertype ARP (0x0806), length 42: Reply 10.0.0.4 is-at 02:00:00:00:00:04, length 28
02:00:00:00:00:03 > 02:00:00:00:00:04, ethertype IPv4 (0x0800), length 98: 10.0.0.3 > 10.0.0.4: ICMP echo request, id 80, seq 1, length 64
02:00:00:00:00:04 > 02:00:00:00:00:03, ethertype IPv4 (0x0800), length 98: 10.0.0.4 > 10.0.0.3: ICMP echo reply, id 80, seq 1, length 64
--- C と D の ARP キャッシュ
10.0.0.4 dev eth0 lladdr 02:00:00:00:00:04 REACHABLE
10.0.0.3 dev eth0 lladdr 02:00:00:00:00:03 DELAY
```

無関係な B に届いたのは、宛先が `ff:ff:ff:ff:ff:ff` の ARP 要求だけです。D の答えは C 宛てで、その後の ping も C と D の間だけを流れています。D の側にも C の対応が残っているのは、RFC 826 の手順どおり、要求を受け取った側も送信元の対応を覚えるからです。

ブロードキャストは、L2 ネットワーク全体の全員に届きます。端末が何千台もある 1 つの L2 ネットワークでは、ARP 要求だけで全員の手を煩わせることになります。L2 ネットワークをあまり大きくしない理由の 1 つで、次の第 61 回の VLAN はこれを分ける道具です。

## 誰でも「それは自分だ」と言える

ARP には、答えが本物かどうかを確かめる仕組みがありません。そして、聞かれていない答えも受け入れます。

自分の IP アドレスを、聞かれる前に周りへ知らせる ARP を **Gratuitous ARP** と呼びます。アドレスの重複を検出する手順を定めた [RFC 5227](https://www.rfc-editor.org/rfc/rfc5227.html) は、これを ARP Announcement と呼び、送信元と宛先の両方の IP アドレス欄に自分のアドレスを入れた ARP 要求で、「It conveys a stronger statement than an ARP Probe, namely, "This is the address I am now using."」と説明しています。正当な用途は、IP アドレスを付け替えたときや、冗長構成で待機系が主系の IP アドレスを引き継いだときに、周りの ARP キャッシュをすぐに書き換えさせることです。

Linux がこれを受け取ったときの動きは、カーネルの文書の `arp_accept` の項に書かれています。この設定は「Define behavior for accepting gratuitous ARP (garp) frames from devices that are not already present in the ARP table」で、既定の 0 なら新しい項目は作りません。ただし「If the ARP table already contains the IP address of the gratuitous arp frame, the arp table will be updated regardless if this setting is on or off.」とあります（[ip-sysctl](https://docs.kernel.org/networking/ip-sysctl.html)）。**すでに知っている相手の対応は、設定に関係なく上書きされる**ということです。

これを、悪意のある D に試させます。C が A（10.0.0.1）と通信した後で、D が「10.0.0.1 は自分（02:..:04）だ」という Gratuitous ARP を流します。

```text
C の arp_accept: 0
### C の ARP キャッシュ（本物）
10.0.0.1 dev eth0 lladdr 02:00:00:00:00:01 REACHABLE
### D が「10.0.0.1 は自分（02:..:04）だ」と Gratuitous ARP を流す
02:00:00:00:00:04 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 10.0.0.1 (ff:ff:ff:ff:ff:ff) tell 10.0.0.1, length 28
### C の ARP キャッシュ（上書き後）
10.0.0.1 dev eth0 lladdr 02:00:00:00:00:04 STALE
### C から 10.0.0.1 への ping はどこへ行くか（A と D で受信を数える）
A が受けた ICMP: 0  D が受けた ICMP: 2
```

`arp_accept` は 0 のままでしたが、C の ARP キャッシュは D の MAC アドレスに書き換わり、C が A に送ったつもりの ping は 2 回とも D に届きました。これが **ARP スプーフィング**（ARP キャッシュの汚染）です。D が受け取ったフレームを本物の A へ転送し直せば、C と A の通信の間に気付かれずに割り込めます。スイッチは送信元の MAC アドレスを学習しているだけなので、この偽りには関与しません。

同じ L2 ネットワークにいる相手は、この程度のことができる、と考えておく必要があります。対策は層によって分かれます。

- **スイッチの側**：DHCP で配った IP アドレスと MAC アドレスとポートの対応を記録しておき、それに合わない ARP を捨てる機能（Dynamic ARP Inspection などと呼ばれます）
- **端末の側**：重要な相手の対応を静的に登録する。ただし数が増えると管理できない
- **上の層**：そもそも L2 を信用しない。第 20 章の TLS で相手を確かめていれば、割り込まれても中身は読めず、書き換えれば気付ける

公衆 Wi-Fi で TLS が欠かせない理由の 1 つは、同じアクセスポイントにつながった見知らぬ誰かが、まさにこの位置にいるからです。

## L2 スイッチと L3 スイッチ、箱と回路

ここまでの規則だけで動くスイッチを **L2 スイッチ**と呼びます。IP アドレスは読みません。これに、次の第 62 回で見るルーターの機能（IP アドレスで宛先を選ぶ）を足したものが **L3 スイッチ**で、社内のネットワークで部署ごとの L2 ネットワークをつなぐのによく使われます。

業務用のスイッチは、ポートが数十あり、それぞれが毎秒数千万のフレームを受け取ります。第 68 回で計算するとおり、1 パケットあたりに使える時間はマイクロ秒を切ります。そのため、宛先 MAC アドレスから出口のポートを引く処理は、CPU のソフトウェアではなく、専用の回路（ASIC）と、内容から位置を一度に引ける連想メモリ（CAM。経路の最長一致などを扱う 3 値のものは TCAM）で行います。テーブルの大きさは回路で決まっているので、それを超える数の MAC アドレスを送り付けられると覚えきれず、知らない宛先として全ポートに流してしまいます。これを悪用して他人宛てのフレームを盗み見る攻撃が **MAC フラッディング**で、スイッチの側ではポートごとに覚える数の上限を設けて防ぎます。

この実験の Linux bridge は、同じ仕組みをカーネルのソフトウェアで実行しています。仮想マシンやコンテナを同じ L2 ネットワークにつなぐのは、たいていこの bridge です。第 65 回では、クラウドがこの「仮想のスイッチ」をどう広げているのかを見ます。

## まとめ

- 同じ L2 ネットワークの中では、フレームは宛先 MAC アドレスで届けられる。フレームは宛先・送信元・EtherType・ペイロード・FCS からなり、ペイロードの上限 1500 バイトが MTU になる
- MAC アドレスの先頭のバイトの最下位ビットは「全員宛てか」、その次のビットは「管理者が決めたものか」を表す
- スイッチは送信元から学習し、宛先で出口を選ぶ。知らない宛先とブロードキャストは全ポートに流し、しばらく見ない送信元は忘れる
- 実測では、まだ声を出していない B への最初のフレームが C と D にも届き、B が返事をした後は B にだけ届いた。Linux bridge の `ageing_time` は 1/100 秒単位で、既定は 300 秒
- ARP は、IP アドレスに対応する MAC アドレスをブロードキャストで尋ね、ユニキャストで答える。答えの真偽を確かめる仕組みは無く、Gratuitous ARP で既存の対応を上書きできる
- 同じ L2 ネットワークにいる相手は通信に割り込める。上の層で相手を確かめることが最後の守りになる

次の第 61 回では、1 台のスイッチを論理的に複数の L2 ネットワークに分ける VLAN と、スイッチをループ状につないだときに起きるブロードキャストの嵐、それを防ぐスパニングツリーを見ます。
