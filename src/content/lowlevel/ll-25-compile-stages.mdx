## 1 つのコマンドの中身

```bash
gcc foo.c -o foo
```

この 1 行で、実際には 4 つの処理が順番に走っています。

```
foo.c  ──プリプロセス──▶  foo.i  ──コンパイル──▶  foo.s
                                                    │
                                                 アセンブル
                                                    ▼
       foo  ◀──リンク──  foo.o  ◀────────────────
```

それぞれ別のプログラムで、個別に実行できます。

```bash
gcc -E foo.c -o foo.i      # プリプロセスだけ
gcc -S foo.i -o foo.s      # コンパイルだけ
gcc -c foo.s -o foo.o      # アセンブルだけ
gcc foo.o -o foo           # リンクだけ
```

エラーがどの段階で出たのかを切り分けられると、原因の特定がはるかに速くなります。

## 1. プリプロセス

**テキストを加工するだけ**の処理です。C 言語の文法をまったく理解していません。

やることは 3 つです。

| 指令 | 動作 |
| --- | --- |
| `#include` | **そのファイルの中身を、その場に貼り付ける** |
| `#define` | 文字列を置き換える |
| `#if` / `#ifdef` | 条件を満たさない部分を削除する |

`#include <stdio.h>` は、`stdio.h` の中身を丸ごとその位置に展開します。展開結果は驚くほど大きくなります。

```bash
gcc -E hello.c | wc -l
# 800 行以上になることがある。元は 5 行でも
```

<Callout type="warn" title="マクロは関数ではない">
```c
#define SQUARE(x) x * x
SQUARE(1 + 2)          // → 1 + 2 * 1 + 2  = 5。7 ではない
```
  単なる文字列の置き換えなので、優先順位を考慮しません。
  括弧で囲めば回避できますが（`#define SQUARE(x) ((x) * (x))`）、
  それでも `SQUARE(i++)` のように引数が 2 回評価される問題は残ります。
  C++ では `inline` 関数や `constexpr`、C でも `static inline` を使うほうが安全です。
</Callout>

**インクルードガード**が必要な理由もここにあります。同じヘッダを 2 回展開すると、同じ定義が 2 つ並んでエラーになります。

```c
#ifndef FOO_H
#define FOO_H
// 中身
#endif
```

`#pragma once` はコンパイラ独自拡張ですが、事実上どこでも使えます。

## 2. コンパイル

ここが本体です。C のソースを読み、アセンブリを出力します。内部はさらに細かく分かれます。

| 段階 | 仕事 |
| --- | --- |
| **字句解析** | 文字列をトークン（単語）に切り分ける |
| **構文解析** | トークンから構文木を組み立てる |
| **意味解析** | 型の検査、宣言と使用の照合 |
| **中間表現への変換** | 機種に依存しない形にする |
| **最適化** | 中間表現を変形する |
| **コード生成** | 対象の機種の命令列にする |

この一連の流れは、Track 2 で実際に作ることになります。

<Callout type="tip" title="最適化レベル">
  | オプション | 内容 |
  | --- | --- |
  | `-O0` | 最適化なし。デバッグ向き。ソースと機械語が素直に対応する |
  | `-O1` | 基本的な最適化 |
  | `-O2` | 実用上の標準 |
  | `-O3` | 積極的。ループ展開、自動ベクトル化。コードサイズが増える |
  | `-Os` | サイズ優先 |
  | `-Ofast` | 規格を一部無視して速度優先（浮動小数点の再結合など） |

  `-O2` 以上では、変数が消えたり行の順序が入れ替わったりするため、
  デバッガで追うと「この変数は最適化により消えています」と言われます。
</Callout>

## 3. アセンブル

アセンブリを機械語に変換し、**オブジェクトファイル**（`.o`）を作ります。

この変換はほぼ機械的です。ただし、この段階では**まだ決められないこと**があります。

```asm
call  printf          ; printf のアドレスは、まだ分からない
mov   eax, [counter]  ; counter がどこに置かれるかも、まだ分からない
```

他のファイルで定義されている関数や変数のアドレスは、このファイルだけを見ても決まりません。

そこでアセンブラは、その部分を仮の値（0 など）で埋めておき、「ここは後で `printf` のアドレスに直してほしい」という**メモ**を残します。これが **再配置情報** です。

## 4. リンク

複数のオブジェクトファイルとライブラリを 1 つにまとめ、**仮の値を実際のアドレスに書き換えます**。

```bash
gcc a.o b.o -lm -o prog
```

リンカがやることは 3 つです。

1. 各オブジェクトファイルのセクション（コード、データ）を種類ごとに連結する
2. 連結後の位置に基づいて、各シンボルの最終的なアドレスを決める
3. 再配置情報に従って、仮の値を実際のアドレスに書き換える

リンクエラーの 2 大メッセージは、この工程を知ると読み解けます。

| メッセージ | 意味 |
| --- | --- |
| `undefined reference to 'foo'` | `foo` を使っているが、**どこにも定義がない** |
| `multiple definition of 'foo'` | `foo` の定義が **2 つ以上ある** |

前者は、ライブラリの指定漏れ（`-lm` を忘れた）か、実装ファイルをコンパイル対象に入れ忘れたときに出ます。

<Callout type="warn" title="宣言と定義">
  - **宣言**：「そういう名前のものがある」と知らせる。ヘッダに書く
  - **定義**：実体を作る。`.c` に書く

  コンパイルは宣言さえあれば通ります。**定義がないことはリンクまで分かりません**。
  「コンパイルは通るのにリンクで落ちる」のは、この分業によるものです。
</Callout>

## 翻訳単位

プリプロセス後の 1 つの `.c` ファイルを **翻訳単位** と呼びます。コンパイラは、**1 翻訳単位ずつ独立に処理します**。

このことから、いくつかの帰結が生まれます。

- 他のファイルの中身を知らないので、ファイルをまたいだ最適化（インライン化など）ができない
- 同じヘッダが複数の `.c` から include されると、同じ内容が何度もコンパイルされる
- 1 ファイルだけ変更したら、そのファイルだけ再コンパイルすればよい（差分ビルドが成立する）

**LTO**（Link Time Optimization）は、この制約を外す仕組みです。オブジェクトファイルに中間表現を残しておき、リンク時にまとめて最適化します。

```bash
gcc -flto -O2 a.c b.c -o prog
```

ファイルをまたいだインライン化や不要コードの削除ができるようになりますが、リンクに時間がかかります。

## C++ での追加の複雑さ

C++ ではさらに 2 つの事情が加わります。

**名前修飾**（name mangling）。オーバーロードのため、関数名に引数の型情報が埋め込まれます。

```
void f(int)      →  _Z1fi
void f(double)   →  _Z1fd
```

エラーメッセージに出る暗号のような名前は、これです。`c++filt` で元に戻せます。

```bash
echo '_Z1fi' | c++filt          # → f(int)
```

C の関数を C++ から使うときに `extern "C"` が必要なのは、修飾を止めさせるためです。

**テンプレート**。使われた型ごとに実体が生成されるため、複数の翻訳単位で同じ実体ができます。リンカはこれを重複エラーにせず、1 つにまとめる特別な扱いをします。

## まとめ

- プリプロセス（テキスト加工）→ コンパイル（アセンブリ生成）→ アセンブル（機械語化）→ リンク（結合とアドレス確定）
- `#include` は中身の貼り付け。マクロは文字列置換であって関数ではない
- オブジェクトファイルには、未解決のアドレスを直すためのメモ（再配置情報）が入る
- `undefined reference` は定義がない、`multiple definition` は定義が重複している
- 翻訳単位は独立に処理される。だから差分ビルドが成立し、LTO が必要になる
