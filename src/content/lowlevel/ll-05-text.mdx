## 文字も結局は数

メモリに入るのは数だけです。だから文字を扱うには、**文字と数の対応表**を決めるしかありません。

最初に広く使われた対応表が **ASCII** です。7 ビット、128 文字。

| 範囲 | 中身 |
| --- | --- |
| 0x00〜0x1F | 制御文字（改行、タブ、ベル） |
| 0x20 | 空白 |
| 0x30〜0x39 | `0`〜`9` |
| 0x41〜0x5A | `A`〜`Z` |
| 0x61〜0x7A | `a`〜`z` |

この配置には意図があります。

- 数字の文字コードから `0x30` を引けば数値になる
- 大文字と小文字の差はちょうど `0x20`（ビット 5 を立てるかどうかだけ）

```c
c | 0x20     // 小文字にする
c & ~0x20    // 大文字にする
```

現代のライブラリはもっと複雑なことをしますが、この性質は今も生きています。

## 各国語の混乱

128 文字では、英語以外がまったく入りません。8 ビット目の空きを使って 128 文字を追加する方式が各地で作られました（ISO-8859-1 など）。

日本語は文字数が桁違いなので、**1 文字に複数バイトを使う**方式が必要でした。Shift_JIS、EUC-JP、ISO-2022-JP がそれぞれ別の対応表を持ち、同じバイト列が方式によって別の文字になりました。これが **文字化け** の正体です。

<Callout type="warn" title="Shift_JIS が残した傷">
  Shift_JIS では、2 バイト文字の 2 バイト目に `0x5C`（ASCII のバックスラッシュ）が現れます。
  「ソ」「表」「能」などがこれに当たります。バイト単位で `\` を探すプログラムは、
  文字の途中を誤検出します。「**ダメ文字**」と呼ばれ、パス処理やエスケープ処理で長く事故を起こし続けました。
  1 バイトずつ見てよいかどうかは、符号化方式に依存する、という教訓です。
</Callout>

## Unicode：番号を世界で統一する

**Unicode** は「世界中の文字に一意の番号を振る」という取り組みです。この番号を **コードポイント** と呼び、`U+3042`（あ）のように書きます。

重要なのは、Unicode が決めているのは**番号だけ**だという点です。その番号をバイト列にどう落とすかは、別の話です。この「落とし方」が **符号化方式**（エンコーディング）で、UTF-8、UTF-16、UTF-32 があります。

| 方式 | 1 文字のバイト数 | 特徴 |
| --- | --- | --- |
| UTF-32 | 常に 4 | 単純。ただし英語主体だと 4 倍に膨らむ |
| UTF-16 | 2 または 4 | Windows と Java、JavaScript の内部表現 |
| UTF-8 | 1〜4 | ASCII と互換。ウェブの事実上の標準 |

## UTF-8 の設計が上手い

UTF-8 のバイト列の作り方です。

| コードポイント | バイト列 |
| --- | --- |
| U+0000〜U+007F | `0xxxxxxx` |
| U+0080〜U+07FF | `110xxxxx 10xxxxxx` |
| U+0800〜U+FFFF | `1110xxxx 10xxxxxx 10xxxxxx` |
| U+10000〜U+10FFFF | `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx` |

ここには、よく効く性質が 3 つ仕込まれています。

**1. ASCII がそのまま通る。** 0x00〜0x7F は 1 バイトで、ASCII と同じ値です。既存の英語のファイルは、何もしなくても正しい UTF-8 です。

**2. 途中のバイトを見分けられる。** 2 バイト目以降は必ず `10` で始まります。先頭バイトは `0`、`110`、`1110`、`11110` のいずれかです。**バイト列の途中に飛び込んでも、文字の境界まで戻れます**。Shift_JIS にはできなかったことです。

**3. ASCII の文字が途中に紛れない。** 多バイト文字を構成するバイトは必ず MSB が 1 なので、`0x5C`（`\`）や `0x2F`（`/`）が文字の途中に出てくることがありません。バイト単位の検索がそのまま使えます。

<Callout type="tip" title="ゼロから設計するなら UTF-8 一択">
  ファイル、ネットワーク、データベース、ソースコード。迷う場面はほぼありません。
  BOM（先頭に付ける印）も UTF-8 では不要で、付いていると逆に問題を起こすことがあります。
</Callout>

## UTF-16 とサロゲートペア

UTF-16 は「2 バイトあれば世界中の文字が入るだろう」という前提で設計されました。この前提は 1996 年に崩れました。文字が 65,536 個を超えたのです。

対応として、**2 個の 16 ビット値を組にして 1 文字を表す**仕組みが追加されました。これが **サロゲートペア** です。

この後付けが、JavaScript と Java に今も残る歪みを生んでいます。

```javascript
"𠮷".length          // 2   （1 文字なのに）
"𠮷".charAt(0)       // 壊れた半分
[..."𠮷"].length     // 1   （イテレータはコードポイント単位）
```

`String.length` が返すのは**文字数ではなく UTF-16 の単位数**です。絵文字や一部の漢字で食い違います。

## 「文字数」という曖昧な言葉

さらにややこしいことに、「1 文字」の定義が 3 つあります。

```
"が"  →  U+304C            1 コードポイント
"が"  →  U+304B U+3099     2 コードポイント（か + 濁点）
```

見た目は同じですが、中身が違います。前者を **合成済み**、後者を **結合文字列** と呼びます。

絵文字ではもっと極端になります。

```
👨‍👩‍👧‍👦  →  6 コードポイント（4 人 + 結合子 3 つ）
```

したがって、数え方は文脈によって変わります。

| 数えたいもの | 単位 | 例（`👨‍👩‍👧‍👦`） |
| --- | --- | --- |
| ストレージの容量 | バイト | 25 |
| UTF-16 の配列長 | コードユニット | 11 |
| Unicode の文字番号の数 | コードポイント | 7 |
| **人間が見る文字の数** | **書記素クラスタ** | **1** |

入力欄の「140 文字まで」のようなものは、書記素クラスタで数えるのが正しい。ほとんどの言語では標準では扱えず、専用のライブラリが必要です。

<Callout type="warn" title="正規化を忘れると検索が当たらない">
  「が」を合成済みで登録し、結合文字列で検索すると、バイト列が違うので一致しません。
  macOS のファイルシステムは歴史的に分解形（NFD）を使うため、
  Mac で作ったファイル名を Linux で検索して見つからない、という事故が起きます。
  比較の前に **正規化**（NFC / NFD）を揃えるのが基本です。
</Callout>

## 実際に見る

```bash
printf 'あ' | xxd
# 00000000: e381 82                                  ...
```

`E3 81 82` の 3 バイトです。先頭が `1110` で始まっているので 3 バイト文字、と読めます。

```python
>>> 'あ'.encode('utf-8')
b'\xe3\x81\x82'
>>> 'あ'.encode('utf-16le')
b'B0'
>>> ord('あ')
12354                       # U+3042
```

## まとめ

- 文字コードは「文字と数の対応表」。Unicode は番号、UTF-8 は番号のバイト化
- UTF-8 は ASCII 互換で、バイト列の途中から境界を復元できる
- UTF-16 のサロゲートペアが、JavaScript / Java の `length` を文字数と食い違わせている
- 「文字数」はバイト / コードユニット / コードポイント / 書記素クラスタの 4 通りある
- 比較の前に正規化を揃える

次は、値そのものではなく**置き場所**の話です。構造体のサイズが、メンバの合計と一致しない理由を見ます。
