## ログインの結果は、どこに残るのか

第 125 回で見たとおり、HTTP はステートレスです。パスワードとパスキー（第 126 回）で本人を確かめても、**その結果は、そのリクエストが終わった時点で消えます**。次のリクエストは、同じ人から来たのか、別の人から来たのか、HTTP の層では区別できません。

だから、認証の結果を**リクエストをまたいで持ち運ぶ仕組み**が要ります。ブラウザでは、その運び役はほぼ決まって **Cookie** です。この回では、次の 3 つを分けて見ます。

| 部品 | 決めていること | 決めていないこと |
| --- | --- | --- |
| Cookie | ブラウザが値を覚え、条件に合うリクエストに自動で付けて送る | 値の意味。値が正しいかどうか |
| セッション（サーバ側） | 値は ID だけ。「誰か」はサーバの保存先に書く | 保存先をどう共有し、いつ消すか |
| 自己完結型トークン | 値そのものに「誰か」を書き、署名（または MAC）で改ざんを防ぐ | 発行した後に取り消す方法 |

**Cookie は運び方で、セッションとトークンは中身の作り方**です。この 2 つを混ぜて考えると、「Cookie は古い、トークンは新しい」という比べられないものの比較になります。

## Cookie の仕組み

Cookie は、サーバが応答の `Set-Cookie` ヘッダで値を渡し、ブラウザが以後のリクエストの `Cookie` ヘッダで送り返す、という約束です（[RFC 6265](https://www.rfc-editor.org/rfc/rfc6265.html)）。改訂版の [RFC 6265bis](https://datatracker.ietf.org/doc/draft-ietf-httpbis-rfc6265bis/) は、執筆時点（2026 年 9 月）で第 22 版が RFC Editor の最終確認の段階にあり、SameSite や接頭辞はこちらで定義されています。

```
HTTP/1.1 200 OK
Set-Cookie: sid=V39jXiOj...; Path=/; HttpOnly; Secure; SameSite=Lax

GET /me HTTP/1.1
Cookie: sid=V39jXiOj...
```

送り返すときに付くのは `名前=値` だけで、属性は付きません。**属性はブラウザへの指示**で、「どこへ送るか」「誰に見せるか」を決めます。

| 属性 | 意味 |
| --- | --- |
| `Domain` | 省略すると、設定したホストだけに送る（host-only）。`Domain=example.com` と書くと、`www.example.com` などのサブドメインにも送る（[RFC 6265 4.1.2.3](https://www.rfc-editor.org/rfc/rfc6265.html#section-4.1.2.3)、[5.3](https://www.rfc-editor.org/rfc/rfc6265.html#section-5.3)） |
| `Path` | そのパスの下へのリクエストだけに送る。**安全のための境界ではない**（同じオリジンの別のパスのページから読める） |
| `Expires` / `Max-Age` | 期限。無ければブラウザを閉じるまで。6265bis は上限を 400 日以下にするよう求めている（[5.5](https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-5.5)） |
| `Secure` | HTTPS のリクエストにだけ送る |
| `HttpOnly` | JavaScript の `document.cookie` から見えなくする。HTTP のリクエストには付く |
| `SameSite` | 別のサイトから始まったリクエストに付けるかどうか（後述） |

見落とされやすいのが、**Cookie の境界はオリジンではない**ことです。同一オリジンはスキーム・ホスト・ポートの組ですが（オリジンとサイトの違いは第 93 回）、Cookie は**ポートで分かれません**（[RFC 6265 8.5](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.5)）。さらに、`foo.example.com` は `Domain=example.com` の Cookie を設定でき、兄弟の `bar.example.com` の Cookie を上書きできます（[8.6](https://www.rfc-editor.org/rfc/rfc6265.html#section-8.6)）。

これを塞ぐのが**接頭辞**です。名前が `__Host-` で始まる Cookie は、`Secure` 付き、`Path=/`、`Domain` なしでなければブラウザが受け付けません（[6265bis 4.1.3.2](https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-4.1.3.2)）。つまり**そのホストが HTTPS で設定したものに限られ、サブドメインから押し込めません**。セッションの Cookie には `__Host-sid` のような名前を付けるのが、いまの定石です。

## 手元で確かめる（1）: curl で Set-Cookie を見る

Python の `http.server` で小さなサーバを書き、127.0.0.1:18100 で動かします。`/login` で次の 6 つの Cookie を返します。

- `sid`: サーバ側セッションの ID（`secrets.token_urlsafe(32)`、256 ビットの乱数）
- `tok`: 自己完結型トークン。`{"user": ..., "exp": ...}` を Base64URL にし、第 104 回の HMAC-SHA256 を付けたもの
- `c_strict`、`c_lax`、`c_default`（SameSite なし）、`c_none`（`SameSite=None; Secure`）: SameSite の比較用

`/me` は `sid` と `tok` のそれぞれで「誰か」を答え、`/show` は届いた Cookie の名前を返します。curl の `-c` で Cookie を保存し、`-b` で送ります（手元の実行結果）。

```
$ curl -si -c jar.txt 'http://127.0.0.1:18100/login?user=alice' | grep -i set-cookie
Set-Cookie: sid=V39jXiOj7wCcvHA-vyr6l2ug_Pse3AdDmblW0ON4UHc; Path=/; HttpOnly; SameSite=Lax
Set-Cookie: tok=eyJ1c2VyIjogImFsaWNlIiwgImV4cCI6IDE3OTA1OTU5MzR9.Irk8Q_qBj8M4tAfFfVxLLHfTA9hzWN2oXcKJyvyI6z4; Path=/; HttpOnly; SameSite=Lax
Set-Cookie: c_strict=1; Path=/; SameSite=Strict
...
$ cat jar.txt
127.0.0.1	FALSE	/	TRUE	0	c_none	1
127.0.0.1	FALSE	/	FALSE	0	c_strict	1
#HttpOnly_127.0.0.1	FALSE	/	FALSE	0	sid	V39jXiOj7wCcvHA-vyr6l2ug_Pse3AdDmblW0ON4UHc
...
$ curl -s -b jar.txt http://127.0.0.1:18100/me
session: alice  token: alice
```

保存ファイルの列は、ドメイン、サブドメインにも送るか（`FALSE` = host-only）、パス、Secure か、期限（0 = セッション Cookie）、名前、値です。

2 つ気づくことがあります。1 つは、`tok` の前半は**暗号化されていない**ことです。Base64URL を戻せば誰でも読めます。

```
$ echo eyJ1c2VyIjogImFsaWNlIiwgImV4cCI6IDE3OTA1OTU5MzR9 | base64 -d
{"user": "alice", "exp": 1790595934}
```

**MAC（や署名）が守るのは改ざんで、中身の秘密ではありません**（第 103 回の区別）。もう 1 つは、curl は `SameSite=Strict` の Cookie も区別せず送ることです。**SameSite も HttpOnly もブラウザが守る約束で、サーバが強制しているものではありません**。攻撃者が自分の curl で送る分には、何の制限にもなりません。

<Callout type="note" title="curl が Secure の Cookie を平文の http で送った理由">
  上の `c_none` は `Secure` 付きなのに、`http://127.0.0.1` への要求にも付きました。
  curl（手元は 8.7.1）は localhost や 127.0.0.1 を安全な宛先として扱うためです。
  ブラウザも同じく、`http://localhost` などを「安全な文脈」とみなします。本番のホスト名では、平文の http には送られません。
</Callout>

## サーバ側セッションと自己完結型トークン

Cookie に何を入れるかで、設計は 2 つに分かれます。

```
サーバ側セッション                         自己完結型トークン
  Cookie: sid=ランダムな ID                  Cookie: tok=本文.MAC（または署名）
          │                                           │
          ↓                                           ↓
  保存先（メモリ、Redis、DB）を引く          鍵で MAC を検証し、本文を信じる
  sid → {user: alice, 最終アクセス: ...}     保存先は引かない
```

| | サーバ側セッション | 自己完結型トークン |
| --- | --- | --- |
| 値の中身 | 意味のない乱数 | 利用者の情報と期限 |
| 検証 | 保存先を引く（1 回の問い合わせ） | 鍵の計算だけ |
| 複数台のサーバ | 保存先を共有する必要がある | 鍵を共有すればよい |
| 大きさ | 数十バイト | 中身に比例して大きくなる |
| **取り消し** | **保存先から消せば即座に効く** | **期限が来るまで有効のまま** |

最後の行が本質です。サーバ側セッションは、検証のたびに「いまも有効か」を保存先に聞いているので、消せばその瞬間に無効になります。自己完結型トークンは、**保存先を引かずに済むことが利点であり、そのまま取り消せないことの原因**です。取り消したければ、失効リストを保存先に置いて毎回引くことになり、結局サーバ側セッションと同じ問い合わせが戻ってきます。

実験のサーバで確かめます。ログアウトの前に `sid` と `tok` の値を控えておき、ログアウトの後で、その値を手で送り直します。

```
$ curl -si -b jar.txt -c jar.txt -X POST http://127.0.0.1:18100/logout | grep -i set-cookie
Set-Cookie: sid=; Path=/; Max-Age=0
Set-Cookie: tok=; Path=/; Max-Age=0

$ curl -s -H "Cookie: sid=$SID; tok=$TOK" http://127.0.0.1:18100/me
session: None  token: alice
```

`Max-Age=0` でブラウザ（ここでは curl）の手元からは両方とも消えました。しかし**控えておいた値を送れば、トークンはまだ通ります**。サーバ側セッションのほうは保存先から消したので通りません。一方、本文を `"user": "admin"` に書き換えたトークンは、MAC が合わずに拒否されました。

```
$ curl -s -H "Cookie: tok=<書き換えた本文>.<元の MAC>" http://127.0.0.1:18100/me
session: None  token: None
```

<Callout type="warn" title="よくある誤解: 「ログアウトしたから、そのトークンはもう使えない」">
  ログアウトの `Set-Cookie: ...; Max-Age=0` は、**ブラウザに「手元の値を捨てて」と頼むだけ**です。
  値がすでに盗まれていれば、盗んだ側の手元には残っています。
  ログアウトを「サーバ側でそのセッションを無効にすること」と定義し、保存先から消すまでがログアウトです（[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)）。
  自己完結型トークンでは、これができないか、失効リストを別に持つことになります。
  JWT をセッションの代わりに使うときの問題はここから始まり、第 128 回で詳しく見ます。
</Callout>

## セッションの寿命

サーバ側セッションには、2 つの時計を付けます。

- **アイドルタイムアウト**: 最後のアクセスから一定時間で無効にする。OWASP は、重要なアプリで 2〜5 分、リスクの低いアプリで 15〜30 分を一般的な範囲として挙げています
- **絶対タイムアウト**: 使い続けていても、ログインから一定時間で無効にする。1 日中使う業務アプリなら 4〜8 時間が目安とされています

（いずれも [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)）。アイドルタイムアウトは「席を離れた端末」を、絶対タイムアウトは「盗まれた ID が使われ続けること」を縛ります。どちらも**サーバが時刻を記録している**から効くもので、Cookie の `Expires` はブラウザの都合でしか働きません。

セッション ID そのものは、推測されないことが条件です。OWASP は**少なくとも 64 ビットのエントロピー**を求めています。連番や時刻から作った ID は、第 109 回で見た暗号用の乱数に置き換えます。

## セッション固定

**セッション固定**は、攻撃者が**自分の知っている ID を被害者に使わせる**攻撃です。攻撃者はあらかじめ ID を用意し、何らかの方法（兄弟のサブドメインからの Cookie の設定など）で被害者のブラウザに入れておきます。被害者がその ID のままログインすると、サーバはその ID に被害者の身元を結び付け、攻撃者は同じ ID でログイン後の状態に入れます。

実験のサーバに、「ログイン時に、送られてきた `sid` があればそれを使い回す」危険な動作を切り替えで入れて比べました。

```
== 使い回す実装
$ curl -si -H 'Cookie: sid=attacker-chosen-id' 'http://127.0.0.1:18100/login?user=alice' | grep 'sid='
Set-Cookie: sid=attacker-chosen-id; Path=/; HttpOnly; SameSite=Lax
$ curl -s -H 'Cookie: sid=attacker-chosen-id' http://127.0.0.1:18100/me
session: alice  token: None                ← 攻撃者の ID が alice になった

== ログイン時に作り直す実装
Set-Cookie: sid=0j9jL3MCFixUJxnfqvFaJ3Otrj9i8cKfClacfHC15zY; Path=/; HttpOnly; SameSite=Lax
session: None  token: None
```

対策は 1 行で、**ログインや権限の昇格のたびに、ID を新しく作り直す**ことです（[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)）。`__Host-` 接頭辞は、サブドメインから ID を押し込む経路のほうを塞ぎます。

## CSRF: ブラウザが勝手に Cookie を付けること

Cookie の便利さは、**ブラウザが条件に合うリクエストへ自動で付ける**ことにあります。そしてこれが、そのまま弱点になります。

別のサイト `evil.example` のページに、次のフォームがあるとします。

```html
<form method="POST" action="https://bank.example/transfer">
  <input name="to" value="mallory">
</form>
<script>document.forms[0].submit()</script>
```

被害者が `bank.example` にログインしたまま `evil.example` を開くと、ブラウザは `bank.example` への POST を送り、**`bank.example` の Cookie を付けます**。サーバから見れば、正しいセッションの付いた正規の送金依頼です。これが **CSRF**（クロスサイトリクエストフォージェリ）です。攻撃者は Cookie の値を知りませんし、応答も読めません。**読まずに、送らせるだけ**で成立します。

### SameSite

SameSite は、この「別のサイトから始まったリクエストにも Cookie を付ける」を止める属性です（[6265bis 5.6.7](https://www.ietf.org/archive/id/draft-ietf-httpbis-rfc6265bis-22.html#section-5.6.7)）。ここでの**サイト**は、スキームと登録可能なドメイン（`example.co.jp` や `example.com` のような、組織が登録する単位）の組で、**オリジンより広い**単位です。`a.example.com` と `b.example.com` は別オリジンですが同じサイトです。

| 値 | 別のサイトから始まったリクエストに付くか |
| --- | --- |
| `Strict` | 付かない。リンクで移動してきた最初のページ表示にも付かない |
| `Lax` | トップレベルの移動（リンクのクリック、GET）にだけ付く。POST、iframe、fetch には付かない |
| `None` | 付く。`Secure` が必須 |

Chrome は 80（2020 年 2 月）から段階的に、**SameSite を書いていない Cookie を Lax として扱う**ようにし、2020 年 8 月に全利用者への展開を終えました（[Chromium: SameSite Updates](https://www.chromium.org/updates/same-site/)）。同時に、`SameSite=None` には `Secure` が必須になりました。既存のサイトを壊しすぎないよう、SameSite を書いていない Cookie に限って、**設定から 2 分以内ならトップレベルの POST にも付ける**一時的な例外（Lax+POST）が入っています。

### 手元で確かめる（2）: ブラウザで SameSite を見る

SameSite はブラウザでなければ確かめられません。Playwright で操作するヘッドレスの Chrome（153、独立したプロファイル）で、`http://127.0.0.1:18100/login` を開いてから、**別のサイト**として `http://localhost:18100/evil` を開き、そこから 127.0.0.1 へのフォームの POST と、リンクでの移動を起こしました。`127.0.0.1` と `localhost` はホスト名が違うので、ポートが同じでも別のサイトです。サーバのログに、届いた Cookie と `Sec-Fetch-Site` ヘッダ（後述）を出しています。

```
127.0.0.1 GET  /show      Cookie: sid=...; tok=...; c_strict=1; c_lax=1; c_default=1; c_none=1   Sec-Fetch-Site: none
127.0.0.1 POST /transfer  Cookie: c_default=1; c_none=1                                        Sec-Fetch-Site: cross-site
127.0.0.1 GET  /show      Cookie: sid=...; tok=...; c_lax=1; c_default=1; c_none=1               Sec-Fetch-Site: cross-site
（2 分以上たってから、もう一度 POST）
127.0.0.1 POST /transfer  Cookie: c_none=1                                                     Sec-Fetch-Site: cross-site
```

- 別のサイトからの POST には、**Lax の `sid` も `tok` も付かなかった**。サーバから見れば「ログインしていない人の送金依頼」で、CSRF は成立しない
- 付いたのは `None` と、SameSite を書いていない `c_default` だけ。`c_default` はログインから 2 分以内だったので Lax+POST の例外で付き、2 分を過ぎると付かなくなった
- リンクでの移動（GET）には Lax が付き、Strict だけが付かなかった。**Strict にすると、別のサイトのリンクから来た利用者は、最初の 1 画面だけログインしていないように見える**

<Callout type="warn" title="よくある誤解: 「SameSite=Lax があるので CSRF 対策は要らない」">
  SameSite の境界は**サイト**です。同じ登録可能なドメインの下の別のサブドメイン（利用者が投稿できる `user.example.com` や、乗っ取られた古いサブドメイン）から来た要求は「同じサイト」なので、Strict でも止まりません。
  また、`GET` で状態を変える作りは Lax のトップレベル移動で素通りします。SameSite を書き忘れた Cookie には 2 分の例外があり、既定を Lax にしていないブラウザもあります。
  OWASP も、SameSite は**多層防御の一段**であって、本来の CSRF 対策の代わりにはならないとしています（[OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)）。
</Callout>

### トークンと Fetch Metadata

本来の対策は、**攻撃者のページが知り得ない値を、要求に含めさせる**ことです（同じ Cheat Sheet）。

- **同期トークン**: サーバがセッションに結び付けた乱数をフォームに埋め込み、POST で送り返させて照合する。攻撃者は相手のページを読めない（同一オリジンポリシー、第 86 回）ので、この値を知りようがない
- **署名付きの二重送信 Cookie**: 保存先を持たない場合に、セッションに結び付けた値を HMAC で署名して Cookie とフォームの両方に入れる。署名しない素朴な形は、兄弟のサブドメインから Cookie を押し込まれると破られる
- **Fetch Metadata**: ブラウザが付ける `Sec-Fetch-Site`（`same-origin` / `same-site` / `cross-site` / `none`）を見て、状態を変える要求で `cross-site` を拒否する。上のログにもこのヘッダが出ている
- そもそも **GET で状態を変えない**

**どれも、要求が「どこから来たか」をブラウザの協力で確かめている**点に注意してください。CSRF はブラウザの自動送信を悪用する攻撃なので、対策もブラウザの仕組み（同一オリジンポリシー、SameSite、Fetch Metadata）と組み合わさって初めて効きます。

## XSS: Cookie を盗まれる経路、盗まれなくても使われる経路

**XSS**（クロスサイトスクリプティング）は、攻撃者の JavaScript が**被害者のページのオリジンで**動いてしまうことです。こうなると、CSRF の対策の前提（攻撃者は相手のページを読めない）が崩れます。OWASP も、XSS があれば CSRF の対策は迂回されうるとしています。

HttpOnly が防ぐのは、その中の 1 つの経路だけです。実験のブラウザで、127.0.0.1 のページの中から JavaScript を実行しました。

```
> document.cookie
"c_strict=1; c_lax=1; c_default=1; c_none=1"            ← HttpOnly の sid と tok は見えない

> await (await fetch('/transfer', {method: 'POST', body: 'to=mallory'})).text()
"transfer by alice cookies seen: ['c_default', 'c_lax', 'c_none', 'c_strict', 'sid', 'tok']"
```

| XSS でできること | HttpOnly で防げるか |
| --- | --- |
| Cookie の値を読み、攻撃者のサーバへ送って、後で別の場所から使う | **防げる**（`document.cookie` に出ない） |
| そのページの中から、同じオリジンへ要求を送る（ブラウザが Cookie を付ける） | **防げない** |

<Callout type="warn" title="よくある誤解: 「HttpOnly にしたので XSS されても大丈夫」">
  HttpOnly の Cookie は XSS で**盗めません**が、XSS のスクリプトは**その場で**同じオリジンからリクエストを送れ、ブラウザはそこに Cookie を付けます。
  SameSite もこれを止めません。同じサイトからの要求だからです。上の `fetch` は、HttpOnly で Lax の `sid` を付けたまま送金を通しました。
  HttpOnly が変えるのは「値を持ち出して、被害者がページを閉じた後も別の場所から使う」ことができなくなる点で、被害の広がりを縮めるものです。XSS そのものを防ぐ手段（出力のエスケープ、Content-Security-Policy）の代わりにはなりません。
</Callout>

では、トークンを Cookie ではなく `localStorage` に置いたらどうなるか。`localStorage` は同じオリジンの JavaScript からいつでも読めるので、**XSS のスクリプトはトークンを読んで持ち出せます**。一方、ブラウザが自動では送らないので、CSRF の心配は減ります。つまり、HttpOnly の Cookie と `localStorage` は**守る相手が入れ替わる**関係です。どこに置くかの判断は、JWT と一緒に第 128 回で詳しく見ます。

## 第三者 Cookie の制限

ここまでの「別のサイト」とは逆向きに、**別のサイトのページに埋め込まれたときに送る Cookie** を**第三者 Cookie**と呼びます。`news.example` のページが `ads.example` の画像や iframe を読み込んだとき、`ads.example` の Cookie がそれです。広告の追跡に使われてきたため、ブラウザは制限を強めてきました。第三者かどうかの決まり方、CHIPS や Storage Access API は第 96 回で、Safari の ITP をはじめとするブラウザごとの違いは第 97 回で詳しく見ました。ここでは要点だけを並べます。

| ブラウザ | 執筆時点（2026 年 9 月）の既定 |
| --- | --- |
| Safari | 2020 年 3 月から、別のサイトの資源への Cookie を既定ですべて遮断（[WebKit](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)） |
| Firefox | 2022 年 6 月から、Total Cookie Protection でサイトごとに Cookie を分けて保存（[Mozilla](https://blog.mozilla.org/en/mozilla/firefox-rolls-out-total-cookie-protection-by-default-to-all-users-worldwide/)） |
| Chrome | 廃止の計画を撤回し、2025 年 4 月に、既存の設定で利用者が選ぶ形を続けると発表（[Privacy Sandbox](https://privacysandbox.google.com/blog/privacy-sandbox-next-steps)） |

これは広告だけの話ではありません。**SSO の一部は第三者 Cookie に頼っていました**。たとえば、アプリのページに IdP の iframe を隠して埋め込み、「IdP とのセッションがまだ生きているか」を確かめる方式は、iframe の中の IdP の Cookie が第三者 Cookie になるため、Safari や Firefox では動かなくなりました。SSO が「IdP とのセッション」と「各アプリとのセッション」の 2 段でできていること、そしてこの制限への対応は、第 133 回で見ます。

## まとめ

- HTTP はステートレスなので、認証の結果は Cookie などで持ち運ぶ。**Cookie は運び方、セッションとトークンは中身の作り方**で、別の軸
- Cookie の属性はブラウザへの指示。Cookie はポートで分かれず、兄弟のサブドメインから上書きされうる。`__Host-` 接頭辞で、そのホストが HTTPS で設定したものに限れる
- サーバ側セッションは保存先を引くので即座に取り消せる。自己完結型トークンは保存先を引かない代わりに取り消せない。これが両者の本質的な trade-off
- ログアウトは、ブラウザの Cookie を消すことではなく、サーバ側でセッションを無効にすること。アイドルタイムアウトと絶対タイムアウトもサーバの時計で持つ
- セッション固定は、ログインのたびに ID を作り直して防ぐ
- CSRF は、ブラウザが Cookie を自動で付けることを悪用する。SameSite は多層防御の一段で、同期トークンや Fetch Metadata と組み合わせる
- HttpOnly の Cookie は XSS で盗めないが、XSS はその場で同じオリジンから要求を送れるので悪用はできる
- 第三者 Cookie の制限は、iframe に頼る SSO のセッション確認を壊した

次の回では、自己完結型トークンの代表である **JWT** を分解します。中身は誰でも読めること、何を検証しなければならないか、そしてこの回で見た「取り消せない」問題を抱えたまま、セッションの代わりに使ってよいのかを考えます。
