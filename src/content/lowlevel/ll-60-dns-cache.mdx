## 書き換えたのに切り替わらない

サーバを移すために、A レコードを新しい IP アドレスに書き換えたとします。権威サーバに問い合わせれば、もう新しい答えが返ります。それなのに、古いサーバのアクセスログにはリクエストが届き続けます。

**権威サーバの答えが変わっても、その答えを覚えている場所が途中にいくつもある**からです。第 68 回では「TTL の間は各段でキャッシュされる」と 1 行で済ませました。この回では、その各段が何を、どれだけの間、どんな規則で覚えているのかを見ます。

## TTL は「受け取ってから何秒」

レコードには必ず **TTL**（Time To Live）が付いています。**受け取ってから何秒のあいだ、問い合わせ直さずに使ってよいか**を表す秒数で、32 ビットの欄に入り、上限は 2<sup>31</sup> − 1 秒です（[RFC 2181](https://datatracker.ietf.org/doc/html/rfc2181#section-8)）。

大事なのは、TTL が**期限の時刻ではなく残り時間**だということです。フルリゾルバは受け取った時点から数え始め、クライアントに答えを返すときには**残りの秒数**に書き換えて渡します。受け取った側はそこからまた数え始めます。

手元で確かめると、その様子が見えます（値は実行した時点のもの）。

```
$ dig @elliott.ns.cloudflare.com +noall +answer example.com A    ← 権威サーバ
example.com.   300   IN  A  104.20.23.154

$ dig @8.8.8.8 +noall +answer example.com A                      ← フルリゾルバ
example.com.   147   IN  A  104.20.23.154

$ dig @8.8.8.8 +noall +answer example.com A                      ← 数秒後
example.com.   136   IN  A  104.20.23.154
```

権威サーバはいつ聞いても 300 と答えます。フルリゾルバは「あと 147 秒」「あと 136 秒」と、手元の残り時間を答えています。0 になれば捨てて、権威サーバに聞き直します。

## 覚えている場所は何段もある

アプリケーションから権威サーバまでの間には、キャッシュが何段も重なっています。

```
アプリ ─→ 言語のランタイム ─→ OS ─→ 家庭のルータ ─→ フルリゾルバ ─→ 権威サーバ
         （JVM など）       （systemd-resolved   （組み込みの    （プロバイダ、
          ブラウザ            mDNSResponder）     フォワーダ）     8.8.8.8 など）
```

| 段 | 何が覚えているか | 期限の決め方 |
| --- | --- | --- |
| ブラウザ | Chrome のホストキャッシュ | OS に任せたときは TTL が分からないので 60 秒（[Eric Lawrence](https://textslashplain.com/2022/03/31/chromiums-dns-cache/)） |
| 言語のランタイム | JVM の `InetAddress` のキャッシュ | 設定値。TTL を見ない（後述） |
| OS | systemd-resolved、macOS の mDNSResponder など | レコードの TTL |
| フルリゾルバ | 利用者全員で共有するキャッシュ | TTL。ただし上限や下限を自分で設けることがある |

第 59 回で見たとおり、`getaddrinfo` が返すのはアドレスの一覧だけで、**TTL は返しません**。そのため、`getaddrinfo` の上に自前のキャッシュを作る段（ブラウザや JVM）は、TTL を知らないまま**自分で決めた秒数**で覚えるしかありません。glibc の `getaddrinfo` 自体はキャッシュを持たないので、Linux で systemd-resolved も nscd も動いていなければ、OS の段は素通りになります。

第 3 章のキャッシュの階層と同じ形ですが、大きな違いが 1 つあります。**CPU のキャッシュには、書き換えを他の段に知らせる仕組み（コヒーレンス）がありました。DNS にはありません。** 権威サーバは、誰が自分の答えを覚えているのかを知らず、「もう古い」と伝える手段も持ちません。各段は TTL が切れるまで、古い答えを正しいと信じて使い続けます。

## 「無い」という答えも覚える

存在しない名前を聞かれたときの答え（NXDOMAIN）や、名前はあるがその種類のレコードが無いという答え（NODATA）も、キャッシュされます。これが**ネガティブキャッシュ**です（[RFC 2308](https://datatracker.ietf.org/doc/html/rfc2308)）。

「無い」ことにはレコードが無いので、TTL を付ける場所がありません。そこで権威サーバは、応答の権威部（authority section）にそのゾーンの **SOA レコード**を添えます。RFC 2308 は、ネガティブキャッシュの期限を **SOA 自身の TTL と、SOA の最後の欄（MINIMUM）の小さいほう**と定めています。

```
$ dig @a.iana-servers.net +noall +comments +authority nosuch.iana.org A
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 17505
iana.org.  3600  IN  SOA  sns.dns.icann.org. noc.dns.icann.org. 2026092401 7200 3600 1209600 3600
                                                                                          ^^^^
                                                                          MINIMUM（ネガティブキャッシュの秒数）
```

MINIMUM という名前は、昔「ゾーン内のレコードの TTL の最小値」という意味だったころの名残です。RFC 2308 がこれをネガティブキャッシュの秒数に読み替えました。推奨は **1〜3 時間**で、1 日を超える値は問題を起こしてきた、と書かれています。

同じ問い合わせを `8.8.8.8` に投げると、手元では TTL が 1800 で返ってきました。**フルリゾルバは、ネガティブキャッシュに独自の上限を設けることがある**ためです。たとえば CoreDNS のキャッシュは、既定で成功した答えを最大 3600 秒、「無い」という答えを最大 1800 秒までしか覚えません（[CoreDNS](https://coredns.io/plugins/cache/)）。

<Callout type="warn" title="作る前に引くと、作ってからも引けない">
  新しいサブドメインを作る作業の途中で、まだレコードを登録していない名前を `dig` や `curl` で試すと、
  その「無い」という答えがフルリゾルバに覚えられます。
  その直後にレコードを登録しても、**ネガティブキャッシュが切れるまで、そのフルリゾルバを使う人には「無い」と返り続けます**。
  証明書の発行で DNS による所有確認を待っているときに、これで数十分足止めされることがあります。
  レコードを登録してから引く、という順番を守るのが一番の予防です。
</Callout>

## TTL を先に下げてから移す

キャッシュを外から消す手段が無い以上、IP アドレスを切り替えるときは **TTL を使って段取りを組む**しかありません。定石は次の手順です。

```
時刻      やること                               キャッシュの状態
───────────────────────────────────────────────────────────────────────
T0        TTL を 86400 → 300 に下げる          まだ TTL 86400 の答えを持つ段がある
T0+1 日   （旧 TTL の 86400 秒が過ぎるのを待つ）  すべての段が TTL 300 の答えに入れ替わった
          A レコードを新しい IP に書き換える
T0+1 日   （300 秒 + 余裕を待つ）                 新しい答えに入れ替わった
+数分     旧サーバへの流入が止まったのを確かめる
後日      TTL を元の長さに戻す
```

ポイントは最初の待ち時間です。**TTL を下げた直後に書き換えても意味がありません。** 下げる直前に答えを受け取った段は、古い TTL（この例では 1 日）の間それを持ち続けるからです。**待つべき時間は、新しい TTL ではなく古い TTL** です。

そして、手順どおりに進めても、旧サーバへのアクセスはすぐには止まりません。

- **TTL を守らない段がある。** JVM やブラウザのように自分の秒数で覚える段は、レコードの TTL を見ていません
- **一度張った接続は DNS を引き直さない。** HTTP の keep-alive や DB のコネクションプールは、第 53 回で見たソケットを使い回しています。接続が生きている限り、相手は古い IP のままです

だから、**旧サーバはしばらく動かしたままにして、流入がゼロになったのを見てから止めます**。

## JVM のキャッシュ

TTL を見ない段の代表が JVM です。Java は `InetAddress` の中に独自の名前解決キャッシュを持ち、期限を**セキュリティプロパティ** `networkaddress.cache.ttl` で決めます（[Oracle](https://docs.oracle.com/en/java/javase/21/core/java-networking.html)）。

| プロパティ | 意味 | 既定 |
| --- | --- | --- |
| `networkaddress.cache.ttl` | 成功した答えを覚える秒数。負なら永久、0 なら覚えない | セキュリティマネージャが有効なら **永久（-1）**。無効なら実装依存で、OpenJDK は **30 秒** |
| `networkaddress.cache.negative.ttl` | 失敗した答えを覚える秒数 | 10 秒 |
| `networkaddress.cache.stale.ttl` | DNS が応答しないとき、期限切れの答えを使い続けてよい秒数 | 0（使わない）。JDK 21 で追加（[JDK-8306653](https://bugs.openjdk.org/browse/JDK-8306653)） |

OpenJDK の既定値は、`java.security` の注釈に「この実装の既定では 30 秒」と書かれています（[OpenJDK](https://github.com/openjdk/jdk/blob/master/src/java.base/share/conf/security/java.security)）。

**セキュリティマネージャが有効なときに「永久」になる**のは、DNS の答えが変わると、接続先ごとに与えた権限の判断が崩れるからです。一度許可したホスト名の IP アドレスを後から差し替えられると、許可していない相手につながせることができてしまいます。安全のために、答えを固定したのです。その結果、この設定の JVM は**再起動するまで DNS の変更に気づきません**。

セキュリティマネージャは JDK 24 で有効にできなくなったので（[JEP 486](https://openjdk.org/jeps/486)）、新しい JDK ではこの罠は消えつつあります。それでも 30 秒は、TTL が 5 秒のレコードにとっては長すぎます。AWS は SDK の文書で、JVM の TTL を 5 秒にするよう勧めています（[AWS](https://docs.aws.amazon.com/sdk-for-java/v1/developer-guide/jvm-ttl-dns.html)）。

```java
// 最初の名前解決より前に設定する。システムプロパティではないので -D では効かない
java.security.Security.setProperty("networkaddress.cache.ttl", "5");
```

## 期限切れの答えを使い続ける: serve-stale

TTL はふつう「切れたら捨てる」ものですが、あえて**切れた答えを返す**仕組みもあります。**serve-stale** です（[RFC 8767](https://datatracker.ietf.org/doc/html/rfc8767)）。

権威サーバが落ちたり、DDoS で応答できなくなったりすると、TTL の切れたフルリゾルバから順に名前が引けなくなります。サーバ本体は動いていても、名前が引けなければ誰もたどり着けません。serve-stale は、**聞き直しに失敗したときに限って**、手元の期限切れの答えを返します。

| RFC 8767 の目安 | 値 |
| --- | --- |
| 権威サーバの応答を待つのを諦めて古い答えを返すまで | 1.8 秒（よくある 2 秒のタイムアウトの少し手前） |
| 古い答えに付けて返す TTL | 30 秒 |
| 期限切れの答えを保持しておく最大の期間 | 1〜3 日 |
| 応答しない権威サーバに聞き直す間隔 | 30 秒以上空ける |

古い答えに 30 秒という短い TTL を付けるのは、受け取った側が長く覚え込まないようにするためです。BIND、Unbound、CoreDNS などのフルリゾルバが、設定で有効にできる形で実装しています。

**可用性と鮮度の交換**であることは、第 68 回で見た TTL そのものと変わりません。権威サーバが落ちている間は、古い答えでも無いよりはまし、という判断です。

## 答えを変えて配る: ラウンドロビンと GeoDNS

DNS は、名前を引かせる段階で**どのサーバに行かせるか**を決める道具としても使われます。

**DNS ラウンドロビン**は、1 つの名前に複数の A レコードを登録し、順番を入れ替えて返す方式です。上の `example.com` も 2 つのアドレスを返していました。クライアントの多くは先頭のアドレスから使うので、順番を回せば負荷が散ります。

**GeoDNS** は、問い合わせてきた相手の場所に応じて、近いサーバのアドレスを返す方式です。CDN の多くがこれで利用者を近くの拠点へ振り分けています。

ここで問題になるのが、**権威サーバから見えるのは利用者ではなく、フルリゾルバだ**という点です。東京の利用者が米国にある公開リゾルバを使っていれば、権威サーバには米国からの問い合わせに見えます。

これを補うのが **EDNS Client Subnet（ECS）** です（[RFC 7871](https://datatracker.ietf.org/doc/html/rfc7871)）。フルリゾルバが、問い合わせに**利用者の IP アドレスの上位ビット**を添えて権威サーバに送ります。

```
利用者 198.51.100.23 ─→ フルリゾルバ ─→ 権威サーバ
                        「198.51.100.0/24 の人が聞いている」
                                        ←─ 「その範囲には 203.0.113.10 を。/24 の範囲で使い回してよい」
```

アドレスを丸ごと渡さず、IPv4 は 24 ビット、IPv6 は 56 ビットに切り詰めることが強く勧められています。プライバシーのためです。

ECS には代償があります。**答えが利用者の範囲ごとに変わるので、フルリゾルバのキャッシュも範囲ごとに分けなければならず、当たる率が下がります。** RFC 7871 自身が、範囲ごとのキャッシュを実装しなければ、当たる率の低下で ECS の利点がほぼ打ち消されると書いています。そして、送るかどうかはフルリゾルバ次第です。Cloudflare の `1.1.1.1` は、プライバシーを理由に利用者の IP の情報を権威サーバに送りません（[Cloudflare](https://developers.cloudflare.com/1.1.1.1/faq/)）。Google Public DNS は、ECS に対応していると判定した権威サーバにだけ送ります（[Google](https://developers.google.com/speed/public-dns/docs/ecs)）。

<Callout type="note" title="DNS による振り分けは即座には効かない">
  DNS で振り分ける方式は、どれもこの回で見たキャッシュの上に乗っています。
  あるサーバが落ちて答えから外しても、**その答えを覚えている段と、すでに張られた接続は、TTL が切れるまで・接続が閉じるまで古い行き先を使い続けます**。
  TTL を短くすれば切り替えは速くなりますが、問い合わせが増えて、名前解決の往復も増えます。
  秒単位で切り替えたいなら、DNS ではなく、第 97 回で見た Service のような
  **1 つの宛先の後ろで振り分ける仕組み**（ロードバランサ）の出番です。
</Callout>

## 自分の環境で見る

```bash
# 権威サーバとフルリゾルバで TTL を比べる（権威サーバ名は dig NS で調べる）
dig NS example.com +short
dig @<権威サーバ> +noall +answer example.com A
dig @8.8.8.8 +noall +answer example.com A     # 2 回続けて、残り秒数が減るのを見る

# ネガティブキャッシュの秒数（SOA の最後の欄と、SOA の TTL の小さいほう）
dig +noall +comments +authority no-such-name.example.org A

# OS のキャッシュ（systemd-resolved の場合）
resolvectl statistics        # キャッシュの件数と当たった回数
resolvectl flush-caches      # 消す

# macOS
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
```

Chrome なら `about://net-internals/#dns` でホストキャッシュを消せます。ただし、消せるのは**自分の手元の段だけ**です。フルリゾルバのキャッシュは、運営者以外には消せません。

## まとめ

- TTL は「受け取ってから何秒使ってよいか」。各段は残り秒数を数え、下流には残りを渡す
- キャッシュは ブラウザ、ランタイム、OS、フルリゾルバと何段もある。`getaddrinfo` は TTL を返さないので、その上の段は自分の秒数で覚える
- DNS には書き換えを知らせる仕組みがない。各段は TTL が切れるまで古い答えを使う
- 「無い」という答えもキャッシュされる。期限は SOA の TTL と MINIMUM の小さいほう（RFC 2308）
- IP アドレスを移すときは、TTL を先に下げ、**古い TTL の分だけ待ってから**書き換える。旧サーバは流入が止まるまで残す
- JVM は `networkaddress.cache.ttl` で独自に覚える。セキュリティマネージャ有効時は永久、OpenJDK の既定は 30 秒
- serve-stale は、権威サーバが応答しないときに限り期限切れの答えを返す（RFC 8767）
- GeoDNS と ECS は利用者に近いサーバを返すが、キャッシュの当たる率を下げ、キャッシュと接続の保持のために即座には切り替わらない

次は、キャッシュに入った答えがそもそも**本物かどうか**を問います。偽の答えをキャッシュに入れる攻撃と、それを防ぐ DNSSEC を見ます。
