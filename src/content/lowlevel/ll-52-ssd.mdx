## ディスクのふりをしている装置

OS から見ると、SSD は HDD と同じ**ブロックデバイス**です。「論理ブロック番号 N に 4KB 書く」「N から 4KB 読む」という命令を受け付け、同じ番号に何度でも書き直せます。

しかし、中にある NAND フラッシュは、そういう性質をまったく持っていません。**SSD の中身は、上書きができない記憶素子を、上書きできるように見せかける小さなコンピュータ**です。今回はその見せかけの仕組みと、それが上の層にどう漏れてくるかを見ます。

## NAND フラッシュの 3 つの操作

NAND フラッシュのセルは、絶縁された領域に閉じ込めた電荷の量で値を表します。電荷は電源を切っても残るので、不揮発です。

できる操作は 3 つで、**単位がそれぞれ違います**（[flashdba](https://flashdba.com/2014/06/20/understanding-flash-blocks-pages-and-program-erases/)）。

| 操作 | 単位 | 典型的な大きさ | 内容 |
| --- | --- | --- | --- |
| 読み出し | ページ | 4〜16KB | 電荷の量を読む |
| 書き込み（プログラム） | ページ | 4〜16KB | 電荷を入れる。**消去済みのページにしか書けない** |
| 消去 | ブロック | 数 MB（数百ページ） | ブロック内の全ページの電荷を抜く |

問題は 2 行目と 3 行目の組み合わせです。

- 一度書いたページには、**消去するまで書けない**
- 消去は、**数百ページをまとめて**しかできない

つまり、1 ページだけ書き直したいとき、素直にやると「ブロックの有効なページをすべて退避 → ブロックを消去 → 全部書き戻す」ことになります。4KB を書き換えるために数 MB を動かすのは論外です。

<Callout type="note" title="消去には寿命がある">
  消去と書き込みを繰り返すと、絶縁膜が劣化し、やがて電荷を保てなくなります。
  1 つのブロックが耐えられる回数（P/E サイクル）には上限があり、
  **1 セルに詰めるビット数が多いほど少なくなります**（[TechTarget](https://www.techtarget.com/searchstorage/definition/P-E-cycle)）。
  1 セル 1 ビットの SLC、2 ビットの MLC、3 ビットの TLC、4 ビットの QLC と、
  容量あたりの値段が下がるのと引き換えに、寿命と書き込み速度が落ちていきます。
</Callout>

## 上書きの代わりに、別の場所に書く: FTL

そこで SSD は、上書きを**しません**。

「論理ブロック N を書き換える」という命令が来たら、**空いている別のページ**に新しい内容を書き、「N は今こちらにある」と対応表を書き換えます。古いページは「無効」の印を付けて放っておきます。

```
 論理ブロック番号         対応表            物理ページ
                                         ┌─────────── ブロック 7 ───────────┐
      N  ───────────→  N → 7-3 に変更 ──→ │ 7-0 有効 │ 7-1 有効 │ 7-2 無効 │ 7-3 新しい N │
                                         └──────────────────────────────────┘
                                         ┌─────────── ブロック 2 ───────────┐
                        （古い N は 2-5）   │ ... │ 2-5 無効（古い N） │ ... │
                                         └──────────────────────────────────┘
```

この変換を行う層を **FTL**（Flash Translation Layer）と呼びます。SSD のコントローラの上で動くファームウェアです。

どこかで見た構造です。

- 第 20 回のページングは、仮想アドレスから物理アドレスへの対応表だった
- 前回のコピーオンライト FS は、上書きせず新しい場所に書いて親を付け替えた

FTL は、その両方を**ディスクの内側で**やっています。OS から見える論理ブロック番号は、仮想メモリの仮想アドレスと同じく、実在の場所ではありません。

<Callout type="tip" title="対応表はどこに置くか">
  4KB ごとに 4 バイトの対応表を持つと、容量の約 0.1%、**1TB あたり約 1GB** になります。
  SSD に DRAM が載っているのは、主にこの表を置くためです。
  DRAM を載せない安価な SSD は、NVMe の HMB（Host Memory Buffer）という仕組みで
  **ホストのメモリを少し借りて**、表の一部を置きます（[The SSD Review](https://www.thessdreview.com/ssd-guides/learning-to-run-with-flash-2-0/understanding-dram-vs-dram-less-ssds-and-making-the-right-purchase-choice/)）。
  表が載りきらない分は NAND から読むことになり、ランダムアクセスが遅くなります。
</Callout>

## 無効なページを回収する: ガベージコレクション

別の場所に書き続ければ、いずれ空きページが尽きます。無効なページは、ブロックごと消去しない限り再利用できません。

そこで FTL は、裏で**ガベージコレクション**を行います。

```
 1. 無効なページが多いブロックを選ぶ
 2. そのブロックに残っている有効なページを、別のブロックにコピーする
 3. 対応表を書き換える
 4. 元のブロックを消去し、空きブロックに戻す
```

第 26 回で見たコピー方式の GC と、ほぼ同じ手順です。そして同じ弱点を持ちます。**生きているデータが多いほど、コピーの量が増える**。

## 書き込み増幅

ホストが 1 ページ書いただけでも、ガベージコレクションで有効なページが移動するので、NAND への実際の書き込みはそれより多くなります。この比を**書き込み増幅**（write amplification）と呼びます。

```
書き込み増幅 = NAND に実際に書いた量 / ホストが書いた量
```

これが大きいと、2 つのことが起きます。

- **遅くなる**: ガベージコレクションが、ホストの書き込みと帯域を取り合う。SSD がほぼ満杯の状態でランダムに書き続けると、ある時点から急に遅くなる
- **寿命が縮む**: P/E サイクルを余計に消費する

書き込み増幅は、**空きの多さ**で大きく変わります。空きが多ければ、「ほぼ全部が無効」なブロックを選べるので、コピーが少なくて済みます。そのため SSD は、表示容量より多くの NAND を積み、ユーザから見えない予備領域として確保しています。これを**オーバープロビジョニング**と呼びます。

<Callout type="warn" title="層ごとに増幅が掛け算になる">
  SSD の書き込み増幅は、上の層の増幅と**掛け算**で効きます。

  - データベースの WAL とページで 2 回（前回）
  - ファイルシステムのジャーナルでさらに（前回）
  - LSM-tree の compaction で同じデータを何度も書き直す（<a href={`${import.meta.env.BASE_URL}reading/db-index/`}>データベースの索引</a>）
  - そして SSD の内部のガベージコレクション

  アプリが 1GB 書いたつもりでも、NAND には何倍も書かれています。
  書き込みの多いシステムで SSD の寿命を見積もるときは、この積で考える必要があります。
</Callout>

## 使っていないと教える: TRIM

FTL には、根本的な情報不足があります。**ファイルが削除されたことを知らない**のです。

第 49 回で見たとおり、ファイルの削除はファイルシステムのメタデータを書き換えるだけで、データのブロックには触りません。SSD から見ると、そのブロックは相変わらず「有効なデータが入っている」ように見えます。ガベージコレクションのたびに、**もう誰も読まないデータを律儀にコピーし続ける**ことになります。

そこで、ファイルシステムが SSD に「この範囲はもう使っていない」と伝える命令があります。ATA では **TRIM**、NVMe では **Deallocate**、Linux の中では **discard** と呼ばれます。

```bash
# 未使用領域をまとめて SSD に通知する
sudo fstrim -v /

# 多くのディストリビューションでは定期実行されている
systemctl status fstrim.timer
```

TRIM を受けた SSD は、そのページを無効として扱えます。空きが増え、書き込み増幅が下がります。

<Callout type="note" title="削除したデータは読めなくなるのか">
  TRIM の後に同じ範囲を読むと、多くの SSD はゼロを返します。
  逆に言えば、TRIM されていない削除済みの領域は、NAND の上に**しばらく残っている**ことがあります。
  完全に消したいときに「上書きすれば消える」が HDD ほど確実でないのは、
  上書きが**別の場所に書かれる**からです。
</Callout>

## 書き込みを散らす: 摩耗平準化

ブロックごとに消去の回数に上限がある以上、特定のブロックに書き込みが集中すると、そこだけ先に壊れます。

ファイルシステムのメタデータのように、同じ論理ブロックが頻繁に書き換えられる場所はあります。しかし FTL は上書きをしないので、同じ論理ブロックへの書き込みでも、物理的には毎回違うページに行きます。ここまでは自然に分散します。

厄介なのは逆側です。**一度書いたきり変わらないデータ**（OS のファイル、昔の写真）が載ったブロックは、消去されません。書き換えの多いデータは、残りの少ないブロックを回り続けることになります。

そこで FTL は、ときどき**変わらないデータもわざと移動**させ、消去回数の少ないブロックを書き換えの多い側に回します。これが**摩耗平準化**（wear leveling）です。寿命のために、あえて書き込み増幅を少し増やしているわけです。

```bash
# SSD の健康状態（残り寿命、書き込み総量）
sudo smartctl -a /dev/nvme0
```

`Percentage Used` や `Data Units Written` が、ここまでの話の結果として見える数字です。

## 並列に動く装置と、NVMe

SSD は 1 つの NAND チップではありません。数個から数十個のチップが並び、それぞれが独立に動けます。**並列に命令を投げるほど速くなる**装置です。

HDD の時代のインタフェース（SATA の AHCI）は、この性質に合っていませんでした。命令の待ち行列は 1 本で、深さは 32 です。HDD にはヘッドが 1 つしかないので、それで十分だったのです。

NVMe は、SSD のために作り直されたインタフェースです（[NVM Express の資料](https://nvmexpress.org/wp-content/uploads/2013/04/NVM_whitepaper.pdf)）。

| | AHCI（SATA） | NVMe |
| --- | --- | --- |
| 待ち行列の数 | 1 | 最大 65,535 |
| 1 本あたりの深さ | 32 | 最大 65,536 |
| 接続 | SATA コントローラ経由 | PCIe に直結 |

Linux は、**CPU コアごとに待ち行列を割り当てます**。各コアが自分の待ち行列に命令を積み、ロックを取り合わずに済みます。完了は割り込み（第 13 回）で知らされ、その割り込みも発行したコアに返すよう設定できます。

第 48 回で、NVMe では I/O スケジューラが `none`（何もしない）が既定だと書きました。シークの無い装置に、並べ替えは要りません。**並列に投げて、あとは装置に任せる**のが最善だからです。

## 電源が落ちたとき

最後に、第 50 回の `fsync` の話に戻ります。

SSD のコントローラも、受け取ったデータをいったん内部の DRAM に溜めます。`fsync` の最後に OS は「キャッシュを NAND に書き出せ」という命令（flush）を送り、SSD はそれが終わってから完了を返します。これが `fsync` が遅い理由の一部です。

データセンター向けの SSD の多くは、**コンデンサ**を積んでいます。電源が落ちても、蓄えた電力で DRAM の中身を NAND に書き切れるので、flush をほぼ即座に完了できます。コンシューマ向けの SSD にはこれが無いことが多く、**同じ `fsync` の速さが桁で違う**ことがあります。

<Callout type="warn" title="flush を無視する装置">
  中には、flush を受け取っても実際には書き出さず、すぐ完了を返す装置があります。
  ベンチマークでは速く見えますが、電源断で**`fsync` が成功したはずのデータが消えます**。
  データベースを置くストレージを選ぶときは、速さだけでなく、
  電源断に対する保護（power loss protection）の有無を確かめる必要があります。
</Callout>

## FTL を上に出すという方向

FTL は、上書きできない装置を上書きできるように見せるための層でした。しかし上の層、たとえば LSM-tree やコピーオンライト FS は、**もともと上書きをしない**書き方をしています。上書きしない書き方を、上書きできるように見せかけた装置の上で、さらに上書きしないように使っている。無駄があります。

そこで、SSD の内側の構造を OS に見せる規格があります。NVMe の **ZNS**（Zoned Namespaces）は、SSD を「先頭から順にしか書けないゾーン」の集まりとして見せます。ホストが順に書くことを約束する代わりに、SSD は複雑な FTL を持たずに済み、書き込み増幅、予備領域、DRAM を減らせます（[NVM Express](https://nvmexpress.org/specification/nvme-zoned-namespaces-zns-command-set-specification/)）。

**抽象化が隠していた制約を、あえて上に見せる**。性能が限界まで求められる場所では、層の境界の引き直しが起きます。

## まとめ

- NAND はページ単位で読み書きし、ブロック単位でしか消せない。書いたページは消すまで書けない
- FTL は上書きの代わりに別の場所に書き、対応表を更新する。ページングやコピーオンライトと同じ構造
- 無効なページはガベージコレクションで回収する。空きが少ないほど書き込み増幅が大きくなる
- 書き込み増幅は、DB・FS・LSM・SSD の各層で掛け算になる
- TRIM は、削除されたことを SSD に伝える。伝えないと、死んだデータをコピーし続ける
- 摩耗平準化は、変わらないデータもわざと動かして寿命を揃える
- NVMe は多数の待ち行列で、並列に動く SSD の性質に合わせた
- `fsync` の速さは、電源断に備えたコンデンサの有無で桁が変わる

ここまでで第 8 章は終わりです。ファイルの構造から、確実に残す手順、クラッシュへの備え、そして一番下の装置まで降りてきました。次の章では、データを**別のマシンに届ける**側、ネットワークの下で何が起きているかを見ます。
