## 2 つの問い

プログラムが時刻を知りたい理由は、大きく 2 つに分かれます。

- **いま何時か。** ログに記録する、有効期限と比べる、画面に表示する
- **どれだけ経ったか。** 処理時間を測る、タイムアウトを判定する、一定間隔で何かをする

この 2 つは、同じ時計で答えてはいけません。次のコードは、よくある間違いです。

```python
start = time.time()          # いま何時か、を聞いている
do_something()
elapsed = time.time() - start   # 経過時間のつもり
```

`time.time()` が返すのは **壁時計**（wall clock）の時刻です。壁に掛かった時計と同じで、ずれていれば誰かが針を合わせ直します。`do_something()` の最中に針が 5 秒戻されれば、`elapsed` は負になります。

経過時間を測るには、**針を合わせ直されることのない時計**を使います。

```python
start = time.monotonic()
do_something()
elapsed = time.monotonic() - start
```

なぜ時計が 2 種類必要なのかを、ハードウェアから順に見ていきます。

## 時を刻む部品

コンピュータの中には、時間に関わる部品がいくつかあります。

| 部品 | 何をするか | 特徴 |
| --- | --- | --- |
| **RTC**（リアルタイムクロック） | 電源が切れていても日時を数え続ける | ボタン電池で動く。精度は低い |
| **水晶発振器** | 一定の周波数で振動する | すべての時計の元。温度で周波数が変わる |
| **タイマ** | 一定間隔で割り込みを発生させる | 第 36 回で見たプリエンプションの元 |
| **TSC**（Time Stamp Counter） | x86 の CPU が持つカウンタ。一定の速さで増え続ける | 読むのが非常に速い |

電源を入れると、カーネルはまず RTC から日時を読み、それを起点にします（第 81 回で見た起動の途中です）。その後は RTC を使わず、**起点からどれだけ経ったか**をカウンタで数えて、現在時刻を計算します。

```
現在時刻 = 起動時に RTC から読んだ時刻 + (カウンタの現在値 - 起動時の値) / カウンタの周波数
```

カウンタには TSC がよく使われます。昔の TSC は CPU の周波数が変わると増える速さも変わってしまい、時計には使えませんでした。現在の CPU の TSC は周波数に関係なく一定の速さで増える（invariant TSC）ので、時計の元として使えます。

どのカウンタを使っているかは、ファイルで確かめられます。

```bash
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
# x86 なら tsc、ARM64 なら arch_sys_counter
cat /sys/devices/system/clocksource/clocksource0/available_clocksource
```

ARM64 では、TSC の代わりに CPU のアーキテクチャが定める汎用タイマのカウンタ（`arch_sys_counter`）が使われます。名前は違っても、**一定の速さで増えるカウンタを読んで時刻を計算する**という構造は同じです。

## カーネルが持つ時計

カーネルは、このカウンタを元に複数の時計を用意しています。`clock_gettime` に渡す ID で選びます。

| 時計 | 起点 | 合わせ直されるか | 用途 |
| --- | --- | --- | --- |
| `CLOCK_REALTIME` | 1970-01-01 00:00:00 UTC | **される**。戻ることもある | いま何時か |
| `CLOCK_MONOTONIC` | 起動時（のような任意の点） | 戻らない。進む速さだけ補正される | 経過時間 |
| `CLOCK_MONOTONIC_RAW` | 同上 | 補正もされない。カウンタそのまま | 補正の影響を避けて測りたいとき |
| `CLOCK_BOOTTIME` | 同上 | 戻らない。**スリープ中も進む** | スリープをまたぐ経過時間 |

`CLOCK_MONOTONIC` の値そのものには意味がありません。「起動してから何秒か」に近い値ですが、**2 回読んだ差だけが意味を持ちます**。そのかわり、絶対に戻りません。

これらは第 41 回で見た vDSO の中で実装されているので、カーネルに入らずに数十ナノ秒で読めます。時刻の取得は、プログラムの中で最も頻繁に呼ばれる操作の 1 つだからです。

<Callout type="tip" title="言語ごとの対応">
  | 言語 | 壁時計 | 単調時計 |
  | --- | --- | --- |
  | C | `clock_gettime(CLOCK_REALTIME)` | `clock_gettime(CLOCK_MONOTONIC)` |
  | Python | `time.time()` | `time.monotonic()`、`time.perf_counter()` |
  | Java | `System.currentTimeMillis()` | `System.nanoTime()` |
  | JavaScript | `Date.now()` | `performance.now()` |
  | Go | `time.Now()` の壁時計部分 | `time.Now()` の単調部分（`Sub` で自動的に使われる） |

  Go は、`time.Now()` が両方の値を持ち、差を取るときは単調時計の側を使います。
  間違えようのない設計にした例です。
</Callout>

## 時計はずれる

水晶発振器の周波数は、個体差と温度で少しずつ違います。ずれは ppm（100 万分の 1）で表します。

20 ppm のずれは、1 日で約 1.7 秒（86,400 秒 × 20 / 1,000,000）です。放っておけば、1 ヶ月で 1 分近くずれます。

そこで **NTP**（Network Time Protocol）で、正確な時刻を持つサーバに問い合わせて合わせ直します。合わせ方は 2 通りあります。

**slew（徐々に寄せる）。** 時計の進む速さを少しだけ変えて、時間をかけて正しい時刻に近づけます。1 秒進みすぎていれば、しばらく少しだけゆっくり進めます。時刻は連続したままで、**戻りません**。ntpd では、速さの変更は最大 500 ppm に制限されています。1 秒のずれを直すのに 2,000 秒ほどかかる計算です（[ntpd のドキュメント](https://docs.ntpsec.org/latest/ntpd.html)）。

**step（跳ばす）。** 時刻を一気に正しい値に書き換えます。速いが、**時刻が不連続になります**。進んでいた時計を直せば、時刻が戻ります。ntpd は、ずれが 128 ms を超える状態が続いたときにこちらを使います（同上）。

```
         slew                              step
  時刻 ↑      ／                     時刻 ↑    ／
      │    ／  ← 傾きが少し緩む          │  ／│
      │  ／                              │／  │ ← ここで戻る
      │／                                │    ／
      └──────────→ 実際の時間             └──────────→ 実際の時間
```

`CLOCK_REALTIME` は slew も step も受けます。`CLOCK_MONOTONIC` は slew だけを受け、step では動きません。`CLOCK_MONOTONIC_RAW` はどちらも受けません。

## 時刻が戻ると何が壊れるか

壁時計を経過時間に使うと、step のたびに事故が起きます。

- **タイムアウト。** 「10 秒後の時刻」を壁時計で計算して待つと、途中で時刻が 1 分戻れば 70 秒待つことになる
- **レート制限。** 「前回から 1 秒経ったか」の判定が狂い、一時的に無制限になったり、ずっと拒否されたりする
- **ログの順序。** 後に起きた出来事のほうが、古い時刻で記録される

さらに厄介なのは、**別のマシンの時計どうしは、NTP で合わせても完全には一致しない**ことです。数ミリ秒のずれは普通にあります。2 台のマシンのログを時刻で並べても、それが本当に起きた順番とは限りません。

<Callout type="warn" title="壁時計で順番を決めない">
  複数のマシンにまたがる出来事の前後関係を、壁時計の時刻だけで決めることはできません。
  分散データベースは、この問題に正面から取り組んでいます。
  時計の誤差の上限を測って、その分だけ待つ方式と、
  壁時計と論理的なカウンタを組み合わせる方式です。
  第 67 回で見ます。
</Callout>

## うるう秒

時刻の基準にも 2 種類あります。

- **TAI**（国際原子時）: 原子時計で刻む。1 秒の長さは一定で、ずれない
- **UT1**: 地球の自転に基づく。自転の速さは一定ではないので、TAI と少しずつずれる

私たちが普段使っている **UTC** は、TAI と同じ速さで進みながら、UT1 との差が 0.9 秒を超えないように、ときどき 1 秒を足します。これが **うるう秒** です。足される日は、UTC で 23:59:59 の次が 23:59:60 になります。

ところが、Unix の時刻（1970 年からの秒数）には **23:59:60 を表す方法がありません**。1 日は必ず 86,400 秒と数えるからです。そこでカーネルは、うるう秒の瞬間に時刻を 1 秒戻すような処理をします。NTP の step とは別の、**もう 1 つの「時刻が戻る」原因**です。

これは実際に大きな障害を起こしました。2012 年 6 月 30 日のうるう秒では、Linux カーネルがうるう秒を挿入したときに高精度タイマの側へ時刻の変更を知らせていなかったため、短いタイムアウトで待つプログラムが空回りし、MySQL や Java のプロセスが CPU を使い切る事象が各地で起きました（[LWN.net](https://lwn.net/Articles/504779/)）。

対策として広まったのが **leap smear** です。うるう秒の前後に時計の速さをわずかに変え、1 秒を少しずつ吸収します。Google は、正午から正午までの 24 時間で線形に吸収する方式を公開しています。速さの変化は約 11.6 ppm で、NTP の slew の上限よりずっと小さく、時刻は一度も戻りません（[Google Public NTP](https://developers.google.com/time/smear)）。

<Callout type="note" title="うるう秒は廃止に向かっている">
  2022 年の国際度量衡総会で、UT1 と UTC の差の許容幅を 2035 年までに広げること、
  つまり事実上うるう秒を挿入しないことが決議されました
  （[BIPM, Resolution 4 of the 27th CGPM](https://www.bipm.org/en/cgpm-2022/resolution-4)）。
  ソフトウェアにとって扱いにくいことが、廃止の理由の 1 つです。
</Callout>

## 1970 年からの秒数と、2038 年

Unix の時刻は、1970-01-01 00:00:00 UTC からの秒数です。これを符号付き 32 ビット整数（`time_t`）で持っていると、表せる最大値は 2<sup>31</sup> − 1 = 2,147,483,647 秒で、2038-01-19 03:14:07 UTC に達します。

その 1 秒後、第 2 回で見たとおり、符号付き整数は最大値から **最小の負の数** に回り込みます。時刻は 1901 年 12 月に飛びます。これが **2038 年問題** です。

64 ビットの環境では `time_t` は 64 ビットなので問題になりません（第 10 回）。残るのは、32 ビットの組み込み機器と、**時刻を 32 ビットの列に保存しているファイル形式やデータベース**です。プログラムを 64 ビットに移しても、保存されたデータの形式は変わらないからです。

## タイムゾーンは表示の問題

カーネルの時計は、すべて UTC で動いています。日本時間は、表示するときに 9 時間を足しているだけです。

**タイムゾーンは、時刻の問題ではなく表示の問題です。** 保存と計算は UTC で行い、人に見せる直前に変換するのが原則です。

<Callout type="warn" title="タイムゾーンは法律で変わる">
  夏時間の有無や時差は、各国の法律で決まり、ときどき変わります。
  変換の規則は IANA の tz データベース（`/usr/share/zoneinfo`）にまとめられていて、
  OS やランタイムの更新で配られます。
  「+09:00」という固定の差ではなく「Asia/Tokyo」という名前で持つのは、
  この変更に追従するためです。

  夏時間のある地域では、ある日の 1:30 が 2 回来たり、2:30 が存在しなかったりします。
  地方時で「毎日 2:30 に実行する」と書いたジョブは、年に 2 回、おかしな動きをします。
</Callout>

## 眠ったぶんだけ正確に起きるわけではない

`sleep(0.001)` と書いても、ちょうど 1 ms 後に起きるとは限りません。

**タイマの粒度。** 起きる時刻を決めるのはタイマ割り込みです。現在の Linux は高精度タイマ（hrtimer）を持つので、マイクロ秒単位で起こせます。一方、OS によっては既定の粒度が粗いものもあります。

**タイマスラック。** Linux は、近い時刻に起きるタイマをまとめて起こすために、わざと少し遅らせます。CPU を眠りから起こす回数を減らして、電力を節約するためです。この遅らせ幅は既定で 50 マイクロ秒で、`nanosleep`、`epoll_wait`、`futex` などの待ちに効きます（[PR_SET_TIMERSLACK(2const)](https://man7.org/linux/man-pages/man2/pr_set_timerslack.2const.html)）。

**スケジューラ。** タイマが時間どおりに鳴っても、そのスレッドが CPU を割り当てられるのは、第 36 回で見たスケジューラの判断しだいです。CPU が混んでいれば、さらに遅れます。

したがって、「1 ms ごとに処理する」ループを `sleep(0.001)` で書くと、遅れが毎回積み重なります。一定間隔で動かしたいなら、**次に起きる時刻を単調時計で計算し、その時刻まで眠る**ようにします。

```c
struct timespec next;
clock_gettime(CLOCK_MONOTONIC, &next);
for (;;) {
    do_work();
    next.tv_nsec += 1000000;                         // 1 ms 後
    if (next.tv_nsec >= 1000000000) { next.tv_sec++; next.tv_nsec -= 1000000000; }
    clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME, &next, NULL);   // その時刻まで眠る
}
```

「どれだけ眠るか」ではなく「いつまで眠るか」を指定するので、1 回の遅れが次に持ち越されません。

## まとめ

- 「いま何時か」は壁時計、「どれだけ経ったか」は単調時計。混ぜると、時刻が戻ったときに壊れる
- 時計の元は一定の速さで増えるカウンタ（x86 の TSC、ARM64 の汎用タイマ）。起動時に RTC から読んだ時刻に足していく
- 時計は ppm 単位でずれ、NTP が slew（速さを変える）か step（跳ばす）で直す。step では壁時計が戻る
- 別のマシンの時計は完全には一致しない。前後関係を壁時計だけで決めない
- うるう秒は Unix の時刻では表せず、障害の原因になってきた。smear で吸収し、制度としても廃止に向かっている
- 32 ビットの `time_t` は 2038 年に負に回り込む
- タイムゾーンは表示の問題。保存と計算は UTC
- sleep は指定した時間ちょうどには起きない。一定間隔なら、単調時計で起きる時刻を指定する
