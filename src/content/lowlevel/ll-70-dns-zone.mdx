## 1 台の台帳では持たない

DNS の前身は、`HOSTS.TXT` という 1 つのファイルでした。全ホストの名前とアドレスを 1 か所で管理し、各マシンが定期的に取りに行く方式です。ホストが増えるにつれて、更新の集中と、名前の衝突と、配布の手間で行き詰まりました。

DNS はこれを、**名前の階層に沿って管理を分ける**ことで解決しました（[RFC 1034](https://datatracker.ietf.org/doc/html/rfc1034)）。

```
                         .（ルート）
          ┌───────────────┼───────────────┐
         com             jp              org
       ┌──┴──┐         ┌──┴──┐
    example google    co     ac
       │                │
      www            example
```

名前は右から読みます。`www.example.com` は、ルートの下の `com` の下の `example` の下の `www` です。正式には末尾にルートを表す `.` が付いて `www.example.com.` と書きます。普段は省略されていますが、この点が「すべての名前はルートから始まる」ことを表しています。

## ゾーンと委任

木全体を 1 つの組織が管理するわけではありません。木のどこかに**切れ目**を入れ、切れ目の下を別の組織に任せます。切れ目で区切られた、つながった範囲の 1 つ 1 つを **ゾーン** と呼びます。RFC 1034 は「すべての切れ目を入れたあと、つながった名前空間の 1 つ 1 つが別々のゾーンになる」と説明しています。

```
  ┌──────────── ルートゾーン ────────────┐
  │  .    「com は Verisign のサーバへ」     │
  │       「jp は JPRS のサーバへ」          │
  └──────┬──────────────────┬──────────┘
  ┌──────┴── com ゾーン ──┐  ┌─ jp ゾーン ─┐
  │ 「example.com は      │  │    ...      │
  │   あのサーバへ」        │  └─────────────┘
  └──────┬───────────────┘
  ┌──────┴── example.com ゾーン ──┐
  │  www   A   203.0.113.10         │  ← ここに答えが書いてある
  └─────────────────────────────┘
```

親のゾーンが子のゾーンに管理を任せることを **委任** といいます。委任の実体は驚くほど単純で、**親のゾーンに、子の名前の NS レコード（そのゾーンを持っているサーバの名前）を書いておくだけ**です（[RFC 9499](https://datatracker.ietf.org/doc/html/rfc9499)）。

ここで大事なのは、**親は子の中身を知らない**ことです。`com` のサーバは `example.com` の NS を知っていますが、`www.example.com` の IP アドレスは知りません。知っているのは「誰に聞けばよいか」だけです。

あるゾーンの中身を自分の手元のデータとして持ち、他に聞かずに答えられるサーバを **権威サーバ** と呼びます。ルートゾーンの権威サーバが**ルートサーバ**、`com` や `jp` のような最上位のゾーンが **TLD**（トップレベルドメイン）です。

<Callout type="tip" title="ディレクトリとマウントに似ている">
  ファイルシステムで、別のディスクを `/home` にマウントすると、`/` のディスクは `/home` の中身を知りません。
  知っているのは「ここから先は別のディスク」という印だけです。
  委任はこれと同じで、NS レコードがマウントポイントの印にあたります。
  第 49 回で見たパス名の解決が、ディレクトリを 1 段ずつ降りていくのとも似ています。
</Callout>

## 誰がたどるのか: フルリゾルバの反復問い合わせ

木をたどって答えを見つける役を担うのが **フルリゾルバ**（キャッシュを持つ再帰リゾルバ）です。アプリの側にあるスタブリゾルバは、フルリゾルバに「最後まで調べてきて」と頼むだけです。

この 2 種類の頼み方は、RFC 1034 では**再帰**と**非再帰**として区別されています。

- **再帰の問い合わせ**: 「答えか、エラーを返して。途中の案内は要らない」。スタブからフルリゾルバへの頼み方
- **非再帰の問い合わせ**: 「手元の情報だけで答えて」。返ってくるのは、答えか、エラーか、**別のサーバへの案内**（リファーラル）のどれか。フルリゾルバから権威サーバへの頼み方

頼む側は、問い合わせの **RD**（再帰を望む）ビットでどちらかを示し、答える側は **RA**（再帰に対応する）ビットで応じられるかを示します。ビットの位置は第 71 回で見ます。

フルリゾルバは、非再帰の問い合わせを繰り返し、案内をたどっていきます。これを **反復解決** と呼びます。

```
スタブ ──RD=1──→ フルリゾルバ
                    │ ① www.example.com の A は？ ──→ ルートサーバ
                    │    ←── 「知らない。com はこのサーバたちへ」（リファーラル）
                    │ ② www.example.com の A は？ ──→ com のサーバ
                    │    ←── 「知らない。example.com はこのサーバたちへ」
                    │ ③ www.example.com の A は？ ──→ example.com のサーバ
                    │    ←── 「203.0.113.10」（権威のある答え）
スタブ ←─答え──── フルリゾルバ
```

リファーラルと本当の答えは、応答の中で区別されます。権威サーバが自分のゾーンの答えを返すときは **AA**（権威のある答え）ビットを立て、リファーラルでは立てません。

<Callout type="note" title="全部を毎回聞いているわけではない">
  ルートや `com` のサーバの一覧も、答えと同じく TTL 付きでキャッシュされます。
  `com` の NS レコードは 2 日（172800 秒）の TTL で配られているので、
  いったん聞けば、しばらくは ① を飛ばして ② から始められます。
  実際にルートまで問い合わせが届くのは、キャッシュが空のときや、見たことのない TLD を引くときです。
  キャッシュの話は第 74 回で扱います。
</Callout>

図では、どのサーバにも `www.example.com` という名前をそのまま送っています。ルートは `com` のことしか答えないのに、完全な名前を見せる必要はありません。そこで、各段には必要な部分（ルートには `com`、`com` のサーバには `example.com`）だけを聞く **QNAME minimisation** という方法が標準化されています（[RFC 9156](https://datatracker.ietf.org/doc/html/rfc9156)）。問い合わせ先に余計な情報を見せない工夫で、第 76 回の「誰に何が見えるか」の話につながります。

## ルートサーバは 13 の名前

反復解決は必ずルートから始まります。では、フルリゾルバはルートサーバの IP アドレスをどうやって知るのでしょうか。DNS で引こうにも、引くにはルートが必要です。

答えは、**最初から設定ファイルに書いてある**、です。IANA が公開している **ルートヒント**（`named.root`）というファイルに、ルートサーバの名前とアドレスが載っていて、フルリゾルバのソフトウェアはこれを同梱しています。起動時にはその中のどれかに「ルートの NS は？」と聞いて、最新の一覧を取り直します。これを **プライミング** といいます（[RFC 9609](https://datatracker.ietf.org/doc/html/rfc9609)）。

ルートサーバには `a.root-servers.net` から `m.root-servers.net` までの **13 の名前**があり、12 の組織が運用しています（[IANA](https://www.iana.org/domains/root/servers)）。

| 名前 | 運用者 | 名前 | 運用者 |
| --- | --- | --- | --- |
| a | Verisign | h | US Army（Research Lab） |
| b | 南カリフォルニア大学 ISI | i | Netnod |
| c | Cogent Communications | j | Verisign |
| d | メリーランド大学 | k | RIPE NCC |
| e | NASA（Ames Research Center） | l | ICANN |
| f | Internet Systems Consortium | m | WIDE Project |
| g | 米国国防総省（NIC） | | |

なぜ 13 なのか。理由は**パケットの大きさ**です。当時の DNS は UDP の上で 512 バイトまでしか送れないと決められていて（[RFC 1035](https://datatracker.ietf.org/doc/html/rfc1035)）、プライミングの応答に名前と IPv4 アドレスを詰め込める上限が 13 でした（[ICANN RSSAC FAQ](https://www.icann.org/en/rssac/faq)）。512 バイトの制限と、それを広げる EDNS0 は第 71 回で見ます。

<Callout type="warn" title="「世界にルートサーバは 13 台」ではない">
  13 というのは**名前**（とそれに対応する IP アドレス）の数で、機械の台数ではありません。
  各運用者は、同じ IP アドレスを世界中の多数の拠点から広告する **anycast** で運用しています（[RFC 4786](https://datatracker.ietf.org/doc/html/rfc4786)）。
  ルーティングの仕組みにより、問い合わせはネットワーク上で最も近い拠点に届きます。
  2002 年に ISC（F の運用者）が最初に導入し（[ICANN RSSAC FAQ](https://www.icann.org/en/rssac/faq)）、
  本稿執筆時点で拠点の総数は 2000 を超えています（[root-servers.org](https://root-servers.org/)）。
</Callout>

anycast は、TCP より UDP の短いやり取りと相性がよい方式です。1 往復で終わる問い合わせなら、途中で経路が変わって別の拠点に届いても困りません。どの拠点が答えたかは、CHAOS クラスの特別な問い合わせで確かめられます（[RFC 4892](https://datatracker.ietf.org/doc/html/rfc4892)）。

```bash
$ dig +short hostname.bind CH TXT @k.root-servers.net
"ns1.jp-tyo.k.ripe.net"          # 例: 東京の拠点が答えている
```

## グルーレコード: 鶏と卵を断ち切る

委任には 1 つ落とし穴があります。`google.com` の権威サーバは `ns1.google.com` です。`ns1.google.com` の IP アドレスを知るには、`google.com` の権威サーバに聞く必要があります。**聞きたい相手のアドレスを、その相手に聞かないと分からない**。

これを断ち切るのが **グルーレコード** です。親の `com` ゾーンに、NS レコードと一緒に `ns1.google.com` の A / AAAA レコードも置いておき、リファーラルの応答に添えて返します。RFC 1034 は、グルーを「ゾーンの権威あるデータではなく、サーバのアドレスのレコード」であり、「サーバの名前が切れ目の下にある場合にだけ必要」と説明しています。

```
com のサーバからのリファーラル
  AUTHORITY:   google.com.      NS    ns1.google.com.    ← 委任（誰に聞くか）
  ADDITIONAL:  ns1.google.com.  A     216.239.32.10      ← グルー（その人の居場所）
```

グルーは親が「預かっている」写しで、本物は子のゾーンにあります。だから、子のゾーンでサーバのアドレスを変えたのに親のグルーを直し忘れると、古いアドレスに案内され続けます。レジストラの管理画面でネームサーバの「ホスト登録」を求められるのは、このグルーを親に書いてもらうためです。

リファーラルにグルーを必ず載せるべきかは長らく曖昧でしたが、2023 年の [RFC 9471](https://datatracker.ietf.org/doc/html/rfc9471) で、委任先の内側にあるサーバのグルーは**すべて載せなければならず、載せきれないなら TC ビット（切り詰めた印）を立てなければならない**と定められました。

## 手元で確かめる: `dig +trace`

`dig +trace` は、`dig` 自身がフルリゾルバの役を演じて、ルートから順に非再帰の問い合わせを送り、各段の応答を表示します。最初の「ルートの NS は？」だけは手元の設定のリゾルバに聞き、そこから先は自分でたどります。

```bash
$ dig +trace www.example.com
```

出力は次のような形になります（RRSIG などの署名の行は省略しています。値は実行した時点のものです）。

```
.                   82111   IN  NS  a.root-servers.net.     ← ① ルートの一覧
.                   82111   IN  NS  b.root-servers.net.
  ...（m まで 13 行）
;; Received 1097 bytes from 192.0.2.1#53(192.0.2.1) in 19 ms

com.                172800  IN  NS  a.gtld-servers.net.     ← ② ルートからの案内
  ...（m まで 13 行）
;; Received 1175 bytes from 170.247.170.2#53(b.root-servers.net) in 83 ms

example.com.        172800  IN  NS  hera.ns.cloudflare.com. ← ③ com からの案内
example.com.        172800  IN  NS  elliott.ns.cloudflare.com.
;; Received 510 bytes from 2001:501:b1f9::30#53(m.gtld-servers.net) in 127 ms

www.example.com.    300     IN  A   104.20.23.154            ← ④ 権威のある答え
;; Received 183 bytes from 172.64.35.228#53(elliott.ns.cloudflare.com) in 14 ms
```

読みどころは 3 つです。

- **各段の `from` を見る。** 答えを返したのが、ルート、`com`、`example.com` の権威サーバと、1 段ずつ下りていく
- **TTL を見る。** 委任の NS は 2 日と長く、最後の A は 300 秒と短い。上の段ほど変わらないので長くキャッシュさせている
- **時間を見る。** 遠い拠点ほど往復が長い。キャッシュが空なら、この合計がそのまま名前解決の待ち時間になる

1 段ずつ手で聞くこともできます。`+norec` で RD ビットを落とすと、フルリゾルバではなく権威サーバとして答えてもらえます。

```bash
$ dig @a.gtld-servers.net google.com NS +norec
;; flags: qr; QUERY: 1, ANSWER: 0, AUTHORITY: 4, ADDITIONAL: 9   ← aa が無い = リファーラル
;; AUTHORITY SECTION:
google.com.      172800  IN  NS    ns1.google.com.
;; ADDITIONAL SECTION:
ns1.google.com.  172800  IN  A     216.239.32.10                   ← グルー

$ dig @ns1.google.com www.google.com A +norec
;; flags: qr aa; QUERY: 1, ANSWER: 8, AUTHORITY: 0, ADDITIONAL: 1   ← aa = 権威のある答え
```

ANSWER が 0 で AUTHORITY に NS が並ぶのがリファーラル、`aa` が立って ANSWER に値が入るのが最終的な答えです。

## 公開接尾辞、apex、サブドメイン

ゾーンと委任が分かると、ドメインの話で混ざりやすい言葉を区別できます。`news.example.co.jp` を例に並べます。

| 言葉 | 何で決まるか | `news.example.co.jp` の場合 |
| --- | --- | --- |
| 公開接尾辞（public suffix） | 登録の方針。その下を第三者が登録できるか | `co.jp` |
| 登録可能なドメイン（eTLD+1） | 公開接尾辞に 1 ラベル足したもの。レジストラで登録する単位 | `example.co.jp` |
| apex（ゾーンの頂点） | DNS の構造。SOA と NS が置かれた、ゾーンの切れ目の位置 | 通常は `example.co.jp`。`news` を別のゾーンに委任していれば `news.example.co.jp` |
| サブドメイン | 名前の包含関係。右側のラベルが一致するか | `example.co.jp` のサブドメインであり、`co.jp` や `jp` のサブドメインでもある |

**サブドメインは、名前の種類ではなく 2 つの名前の関係です。** RFC 1034 は「あるドメインに含まれるドメインは、そのドメインのサブドメインである。名前の末尾が、含む側の名前で終わるかで判定できる」と定義しています（[RFC 9499](https://datatracker.ietf.org/doc/html/rfc9499) による引用）。比較はラベル単位なので、`ooo.example.com` は `oo.example.com` のサブドメインではありません。この定義では `example.com` も `com` のサブドメインです。普段の会話で「サブドメイン」と言うときは、たいてい「登録可能なドメインのサブドメイン」を指しています。

**apex は DNS の構造で決まります。** RFC 9499 は apex を「SOA と、それに対応する権威のある NS の組を持つ、木の上の位置」と定義し、zone apex とも呼ぶとしています。前の節の言葉でいえば、**切れ目の子の側の名前**です。どこに切れ目を入れるかはゾーンの持ち主が委任で決めるので、`dig` で問い合わせれば確かめられます。

**公開接尾辞は DNS の外で決まります。** RFC 9499 は、ドメイン名のどこにも公開接尾辞かどうかを示す情報はなく、外部の手段でしか判定できない、と書いています。その外部の手段が、有志が管理する Public Suffix List（PSL）です。PSL の中身と、ブラウザがそれをどう使うかは第 134 回で見ます。

どれも**ドットの数では決まりません**。`news.example.com` と `example.co.jp` はどちらもドットが 2 つですが、前者は登録可能なドメイン `example.com` のサブドメインで、後者は登録可能なドメインそのものです。

<Callout type="note" title="「apex ドメイン」「ルートドメイン」という呼び方">
  ホスティングや DNS 事業者の画面と文書では、**レジストラで登録した（購入した）ドメインそのもの**を「apex ドメイン」と呼ぶのが一般的です。
  たとえば GitHub Pages の文書は、カスタムドメインを `www.example.com` のようなサブドメインと、`example.com` のような apex ドメインの 2 種類に分けています（[GitHub Docs](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/about-custom-domains-and-github-pages)）。
  同じものを「ルートドメイン」「ネイキッドドメイン」と呼ぶこともあります。
  登録したドメインにゾーンを 1 つ作るのが普通なので、この使い方は DNS の apex（ゾーンの頂点）と同じ名前を指すことがほとんどです。
  ただし、厳密には指すものが違います。サブドメインを別のゾーンに委任すると、DNS の apex はそのサブドメインに移りますが、apex ドメインと呼ばれる登録したドメインは変わりません。
  また、DNS で「ルート」といえば木の頂上の `.` のことなので、「ルートドメイン」は DNS の文脈では紛らわしい言い方です。
  この連載では、ゾーンの頂点を apex、レジストラで登録する単位を登録可能なドメインと呼び分けます。
</Callout>

### 普段は重なり、ときどき分かれる

多くの組織は、登録したドメインに対して DNS 事業者でゾーンを 1 つ作り（Route 53 ならホストゾーン）、サブドメインのレコードもすべてそこに書きます。この場合、登録可能なドメインと apex は同じ名前になります。2 つが分かれるのは、次のような場合です。

- **サブドメインを別のゾーンに委任している**: apex が下にずれる。登録可能なドメインは変わらない
- **公開接尾辞がゾーンになっていない**: 公開接尾辞かどうかは登録の方針で決まり、ゾーンの切れ目とは関係がない
- **PSL の私的な区画**: 企業が利用者ごとのサブドメインを公開接尾辞として登録していても、ゾーンはその企業が 1 つで持っていることがある

### 手元で確かめる: SOA で apex を探す

ある名前がどのゾーンに属するかは、その名前の SOA を問い合わせると分かります。その名前が apex なら ANSWER に SOA が返り、apex でなければ「その型のレコードは無い」という応答の AUTHORITY に、属するゾーンの SOA が添えられて返ってきます。公開接尾辞と登録可能なドメインは、第 134 回の 30 行ほどの Python で PSL（2026-10-20 版）から計算しました。2026 年 10 月 23 日に実行した結果です。

```bash
$ dig +noall +answer +authority SOA ec2.amazonaws.com
ec2.amazonaws.com.  900  IN  SOA  ns-15.awsdns-01.com. awsdns-hostmaster.amazon.com. 1 7200 900 1209600 900
```

```
名前                  公開接尾辞    登録可能なドメイン     apex（SOA の持ち主）
www.example.com       com          example.com          example.com
www.jprs.co.jp        co.jp        jprs.co.jp           jprs.co.jp
co.jp                 co.jp        （なし）              jp
mail.google.com       com          google.com           google.com
ec2.amazonaws.com     com          amazonaws.com        ec2.amazonaws.com
pokotyan.github.io    github.io    pokotyan.github.io   github.io
```

上の 3 つの分かれ方が、それぞれ現れています。

**`ec2.amazonaws.com` は、委任されたサブドメインです。** `amazonaws.com` の権威サーバに聞くと、`aa` の無いリファーラルが返ります。

```bash
$ dig @ns-27.awsdns-03.com ec2.amazonaws.com NS +norec +noall +authority
ec2.amazonaws.com.  7200  IN  NS  ns-1026.awsdns-00.org.
ec2.amazonaws.com.  7200  IN  NS  ns-15.awsdns-01.com.
ec2.amazonaws.com.  7200  IN  NS  ns-1813.awsdns-34.co.uk.
ec2.amazonaws.com.  7200  IN  NS  ns-817.awsdns-38.net.
```

`amazonaws.com` のゾーンは、`ec2` から下を別のゾーンに任せています。PSL には `ec2.amazonaws.com` が載っていないので、登録可能なドメインは `amazonaws.com` のままです。

**`co.jp` は、`jp` のゾーンの中の名前です。** `jp` の権威サーバは、`co.jp` について `aa` を立てて自分で答え、`jprs.co.jp` については直接リファーラルを返します。

```bash
$ dig @a.dns.jp co.jp NS +norec +noall +comments +authority
;; flags: qr aa; QUERY: 1, ANSWER: 0, AUTHORITY: 1, ADDITIONAL: 1
jp.          900    IN  SOA  z.dns.jp. root.dns.jp. 1792735203 3600 900 1814400 900

$ dig @a.dns.jp jprs.co.jp NS +norec +noall +comments +authority
;; flags: qr; QUERY: 1, ANSWER: 0, AUTHORITY: 4, ADDITIONAL: 9
jprs.co.jp.  86400  IN  NS   ns1.jprs.co.jp.
```

`co.jp` は PSL では公開接尾辞ですが、DNS の上では切れ目のない、ただの名前です。

**`pokotyan.github.io` は、私的な区画です。** `github.io` が PSL に載っているので、ブラウザは `pokotyan.github.io` を 1 つのサイトとして扱います。一方、ゾーンは GitHub が `github.io` で 1 つ持っています。

<Callout type="warn" title="この方法の注意点">
  調べる名前が CNAME だと、フルリゾルバが CNAME の先を引くので、**転送先のゾーンの SOA** が返ります。
  たとえば CDN に向けた名前を調べると、CDN 事業者のゾーンが出てきます。
  CNAME を置いた名前は apex ではないので、CNAME が返ってきた時点で apex でないことは分かります。
</Callout>

### どの場面で、どれを意識するか

| 場面 | 効く言葉 | 何が起きるか | 回 |
| --- | --- | --- | --- |
| DNS のレコードをどこに書くか | apex | 名前を含む、いちばん下のゾーンに書く。サブドメインが委任されていれば、親のゾーンに書いても親はリファーラルを返すだけで、そのレコードは使われない | 第 70 回（この回） |
| apex に CNAME を置けない | apex | apex には SOA と NS があるので、CNAME と同居できない。apex でない `www` には置ける | 第 72 回 |
| 使わなくなったサブドメインの委任 | apex（委任） | 親に NS が残ったままだと、サブドメインから下を丸ごと乗っ取られる | 第 78 回 |
| ワイルドカード証明書 | サブドメイン（1 ラベル） | `*.example.com` は `www.example.com` に一致し、`example.com` にも `a.b.example.com` にも一致しない | 第 154 回 |
| Cookie の `Domain` 属性、SameSite、サイト分離 | 公開接尾辞、登録可能なドメイン | 同じ登録可能なドメインのサブドメインどうしは同じサイトになる。公開接尾辞には Cookie を置けない | 第 134 回、第 176 回 |
| WebAuthn の RP ID | 登録可能なドメイン | 自分のホストから登録可能なドメインまでの名前しか名乗れない | 第 174 回 |
| DMARC の relaxed アラインメント | 組織ドメイン | おおむね登録可能なドメインにあたる。`news.example.com` と `example.com` は揃っているとみなされる | 第 200 回 |
| 用途ごとに送信用のサブドメインを分ける | サブドメイン | SPF は名前ごとに別々に評価され、DMARC は組織ドメインで束ねられる | 第 198 回、第 203 回 |

DNS の運用（レコードをどこに書くか、委任をどう片付けるか）では apex を、ブラウザやメールの「同じ持ち主か」という判定では公開接尾辞と登録可能なドメインを見ます。問題が起きたとき、どちらの話をしているのかを最初に分けると、原因を探しやすくなります。

## まとめ

- DNS は名前と IP アドレスの対応を 1 か所に置かず、名前の階層に沿って管理を分ける
- 切れ目で区切った範囲がゾーン。親のゾーンに子の NS レコードを書くことが委任で、親は子の中身を知らない
- ゾーンの中身を手元に持って答えるのが権威サーバ。ルートゾーンの権威サーバがルートサーバ、最上位のゾーンが TLD
- スタブはフルリゾルバに再帰で頼み、フルリゾルバは権威サーバに非再帰で聞いてリファーラルをたどる。本当の答えには AA ビットが立つ
- ルートサーバの場所はルートヒントとして最初から持っていて、プライミングで最新にする
- ルートサーバは 13 の名前で、12 の組織が運用する。13 は 512 バイトに収まる上限。実体は anycast で世界中に 2000 を超える拠点がある
- サーバの名前が委任先の内側にあるときは、親がグルーレコードでアドレスを添える
- `dig +trace` で各段の案内が、`+norec` で権威サーバの生の応答が見える
- apex はゾーンの切れ目で決まる DNS の言葉で、公開接尾辞と登録可能なドメインは PSL で決まる登録の言葉。サブドメインは名前どうしの包含関係。普段は登録可能なドメインと apex が重なるが、委任や PSL の私的な区画で分かれる

次は、ここで行き交っていた問い合わせと応答を、**バイト列として**見ます。Python のソケットだけで DNS のメッセージを組み立ててフルリゾルバに送り、返ってきた応答を読み解きます。
