## そのリクエストは、届いていたのか

フロントエンドの開発で、次のようなエラーを見たことがあると思います。

```
Access to fetch at 'http://127.0.0.1:18187/data' from origin 'http://127.0.0.1:18186'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present
on the requested resource.
```

「ブロックされた」と書いてあるので、リクエストが止められたように読めます。しかし、この回の実験のサーバのログには、**このリクエストがきちんと届いて、200 で応答した記録**が残っています。止められたのは、**応答をページの JavaScript に渡すこと**のほうです。

第 85 回と第 86 回で見たとおり、同一オリジンポリシーは主に「**読むこと**」を制限し、「送ること」の多くは許しています。CORS（Cross-Origin Resource Sharing）は、その読み出しの制限を、**サーバが自分の資源について緩める**ための約束です。この回では、次の区別を軸に見ていきます。

| CORS がすること | CORS がしないこと |
| --- | --- |
| 別のオリジンのページに、応答を読ませてよいかをサーバが答える | サーバへのリクエストを止める（単純なリクエストはそのまま届く） |
| 単純でないリクエストの前に、サーバが CORS を理解しているかを確かめる（プリフライト） | サーバを攻撃から守る。curl やサーバ間の通信を制限する |
| 資格情報（Cookie など）つきの応答を読ませるかを、別に確かめる | Cookie を付けるかどうかを決める（それは SameSite と第三者 Cookie の制限。第 110 回、第 88 回） |

## CORS は、ブラウザとサーバの間の約束

CORS の仕様は、いまは WHATWG の [Fetch Standard の 3.3 節「CORS protocol」](https://fetch.spec.whatwg.org/#http-cors-protocol)にあります。冒頭の 1 文が、この仕組みの性格をよく表しています。

> The CORS protocol consists of a set of headers that indicates whether a response can be shared cross-origin.

つまり CORS は「**応答を別のオリジンと共有してよいか**」を示すヘッダの集まりです。判定するのはブラウザで、サーバはヘッダで答えるだけです。

```
ページ (http://127.0.0.1:18186)      ブラウザ                     API (http://127.0.0.1:18187)
  fetch('http://...:18187/data') ─→  Origin: http://...:18186 ─→  処理して応答する
                                     を付けて送る                   Access-Control-Allow-Origin: ?
                                  ←─ 応答を受け取る            ←─
                                     ヘッダを見て判定
       ←── 読ませる / TypeError ───
```

大事なのは、**判定が応答の後にある**ことです。サーバはリクエストを受け取り、処理を終え、応答を返しています。ブラウザが最後に「このページには見せない」と決めるだけです。

では、なぜこれで安全が保たれるのか。攻撃者のページが別のオリジンの API を呼ぶとき、ブラウザは**利用者の Cookie** や、利用者の端末からしか届かない**社内ネットワーク**への経路を使えます。攻撃者が自分の curl で同じ URL を呼んでも、その Cookie もその経路もありません。**CORS が守っているのは、利用者のブラウザが持つ権限を、別のオリジンのページに勝手に使わせて、その結果を読まれることです。**

## 単純なリクエストと、プリフライト

ブラウザは、別のオリジンへのリクエストを 2 種類に分けます。

**単純なリクエスト**は、いきなり本番のリクエストを送ります。条件は次のとおりです（[CORS-safelisted method](https://fetch.spec.whatwg.org/#cors-safelisted-method)、[CORS-safelisted request-header](https://fetch.spec.whatwg.org/#cors-safelisted-request-header)）。

| 項目 | 許される範囲 |
| --- | --- |
| メソッド | `GET`、`HEAD`、`POST` |
| ヘッダ | `Accept`、`Accept-Language`、`Content-Language`、`Content-Type`（ほかに `Range` の一部）。値は 128 バイト以下 |
| `Content-Type` | `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain` のいずれか |

この範囲は、でたらめに決まったものではありません。**HTML の `form` 要素でも昔から送れたもの**です。フォームはオリジンをまたいで POST できる（第 86 回、CSRF の根）ので、fetch で同じものを送れるようにしても、新しい危険は増えません。仕様も、プリフライトが要るのは「HTML の form 要素でできることより込み入ったリクエスト」だと書いています（[3.3.1](https://fetch.spec.whatwg.org/#http-cors-protocol)）。

それを超えるリクエスト、たとえば `Content-Type: application/json` の POST、`PUT` や `DELETE`、`Authorization` や独自のヘッダを付けたものは、**先に `OPTIONS` で問い合わせます**。これが**プリフライト**です。

```
OPTIONS /transfer HTTP/1.1
Origin: http://127.0.0.1:18186
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type
```

サーバが「そのオリジンから、そのメソッドとヘッダで来てよい」と答えたときだけ、ブラウザは本番のリクエストを送ります。プリフライトは、**CORS を知らない古いサーバに、フォームでは届かなかった種類のリクエストを突然届けない**ための確認です。プリフライトには Cookie などの資格情報は付きません（[3.3.5](https://fetch.spec.whatwg.org/#cors-protocol-and-credentials)）。

## 応答のヘッダ

サーバが返すヘッダは次のとおりです（[3.3.3 HTTP responses](https://fetch.spec.whatwg.org/#http-responses)）。

| ヘッダ | どの応答に | 意味 |
| --- | --- | --- |
| `Access-Control-Allow-Origin` | 両方 | 読ませてよいオリジン。リクエストの `Origin` の値そのもの（`null` もありうる）か `*` |
| `Access-Control-Allow-Credentials` | 両方 | 資格情報つきのリクエストでも読ませてよいか。値は小文字の `true` だけ |
| `Access-Control-Allow-Methods` | プリフライト | 許すメソッド |
| `Access-Control-Allow-Headers` | プリフライト | 許すリクエストヘッダ |
| `Access-Control-Max-Age` | プリフライト | 上の 2 つを何秒キャッシュしてよいか。**既定は 5 秒** |
| `Access-Control-Expose-Headers` | 本番の応答 | JavaScript に見せてよい応答ヘッダ |

`Access-Control-Allow-Origin` に書けるのは、**1 つのオリジンか `*` だけ**です（[3.3.4 の ABNF](https://fetch.spec.whatwg.org/#http-new-header-syntax)）。カンマで複数並べることはできません。複数のオリジンを許したいサーバは、届いた `Origin` を許可リストと照らし、一致したものだけを書き返します。オリジンは末尾に `/` を付けない形で比べられるので、`https://example.com/` と書くと一致しません。

`Access-Control-Expose-Headers` が無いとき JavaScript から読める応答ヘッダは、`Cache-Control`、`Content-Language`、`Content-Length`、`Content-Type`、`Expires`、`Last-Modified`、`Pragma` だけです（[CORS-safelisted response-header name](https://fetch.spec.whatwg.org/#cors-safelisted-response-header-name)）。独自の `X-Request-Id` やページ送りの `Link` を読ませたいなら、明示して並べます。

## 資格情報と、ワイルドカードが使えない理由

fetch には**資格情報モード**（credentials mode）があります（[Fetch Standard](https://fetch.spec.whatwg.org/#concept-request-credentials-mode)）。

| モード | Cookie や HTTP 認証を付けるか |
| --- | --- |
| `omit` | 付けない |
| `same-origin`（fetch の既定） | 同じオリジンへのリクエストにだけ付ける |
| `include` | 別のオリジンへのリクエストにも付ける |

`include` にすると、CORS の判定が厳しくなります。仕様の 3.3.5 節の表を要約すると次のとおりです（[CORS protocol and credentials](https://fetch.spec.whatwg.org/#cors-protocol-and-credentials)）。

| 資格情報モード | `Allow-Origin` | `Allow-Credentials` | 読めるか |
| --- | --- | --- | --- |
| `omit` | `*` | なし | 読める |
| `omit` | `*` | `true` | 読める（`Allow-Credentials` は無視される） |
| `include` | `*` | `true` | **読めない**。`include` のとき `*` は使えない |
| `include` | `https://rabbit.invalid` | `true` | 読める |
| `include` | `https://rabbit.invalid` | `True` | 読めない。`true` は大文字小文字を区別する |

同じく、`Allow-Headers`、`Allow-Methods`、`Expose-Headers` の `*` も、`include` のときはワイルドカードとして働きません。さらに、`Allow-Headers: *` を書いても **`Authorization` はワイルドカードに含まれません**（[CORS non-wildcard request-header name](https://fetch.spec.whatwg.org/#cors-non-wildcard-request-header-name)）。認証のヘッダは、名前で明示して許す必要があります。

なぜ `*` と資格情報を組み合わせられないのか。仕様は `*` の意味をこう説明しています（[Basic safe CORS protocol setup](https://fetch.spec.whatwg.org/#basic-safe-cors-protocol-setup)）。

> It will share the resource with APIs such as XMLHttpRequest, much like it is already shared with curl and wget.

**`*` は「curl や wget で誰でも取れるものを、ブラウザからも取らせる」という宣言**です。利用者の Cookie で中身が変わる応答は、curl では取れません。そういう応答を「誰にでも」見せる設定は、宣言として成り立たないので、仕様は組み合わせを禁じ、サーバに**どのオリジンに見せるかを 1 つずつ名指しさせます**。仕様はこの判断について、資格情報つきで応答を共有するのは「rather unsafe」で、confused deputy（権限を持つ者が、他人の頼みで権限を使ってしまうこと）を避けるよう細心の注意が要る、とも書いています。

同じ節の「Basic safe CORS protocol setup」には、もう 1 つ重要な注意があります。**IP アドレスやファイアウォールで守られた資源に CORS を使うのは安全ではない**、CORS が発明された理由はそこにある、というものです。社内からしか届かない API に `*` を付けると、社員のブラウザが開いた外部のページから、その API の応答が読まれます。この問題は、後の Local Network Access の節で戻ってきます。

## 手元で確かめる（1）: 送れるが、読めない

Python の `http.server` で 2 つのサーバを 1 つのプロセスで立てます。

- `http://127.0.0.1:18186`: 何もしないページを返す（アプリの側）
- `http://127.0.0.1:18187`: API。クエリの `mode` で `Access-Control-Allow-Origin` の出し方を切り替える（`none` = 出さない、`star` = `*`、`fixed` = `http://127.0.0.1:18186` 固定、`reflect` = 届いた `Origin` をそのまま返す）。`cred=1` で `Allow-Credentials: true`、`pf=ok` でプリフライトに `Allow-Methods` と `Allow-Headers` を返す。受けたリクエストはすべてログに書く

ポートが違うので**別オリジン**ですが、ホストが同じ `127.0.0.1` なので**同じサイト**です（第 85 回）。ログの `Sec-Fetch-Site: same-site` がそれを示しています。ブラウザは、playwright-core から起動したヘッドレスの Chrome 153（独立した一時プロファイル）で、ページの中から fetch を実行しました。以下は手元の実行結果の抜粋です。

まず、`Allow-Origin` を出さない API に、単純な GET と、`text/plain` の POST を送ります。

```
fetch('http://127.0.0.1:18187/data?mode=none')
  → TypeError: Failed to fetch
fetch('http://127.0.0.1:18187/transfer?mode=none', {method: 'POST', body: 'to=mallory&amount=100'})
  → TypeError: Failed to fetch
```

サーバのログにはこう残りました。

```
18187 GET     /data?mode=none      | Origin: http://127.0.0.1:18186 | Sec-Fetch-Mode: cors | Sec-Fetch-Site: same-site
18187 POST    /transfer?mode=none  | Origin: http://127.0.0.1:18186 | Content-Type: text/plain;charset=UTF-8 | ...

$ curl -s http://127.0.0.1:18187/transfers
transfers: ['to=mallory&amount=100', ...]
```

**ページの側はエラーでも、POST はサーバに届き、送金の記録まで残っています。** CORS はこの POST を止めていません。止めたのは応答の本文を読むことだけです。

次に、`Content-Type: application/json` で同じ POST を送ります。

```
== プリフライトに CORS のヘッダを返さない場合
18187 OPTIONS /transfer?mode=none  | Origin: ... | Access-Control-Request-Method: POST | Access-Control-Request-Headers: content-type
  （POST は来ない）
== プリフライトで許した場合
18187 OPTIONS /transfer?mode=fixed&pf=ok | ... | Access-Control-Request-Method: POST | Access-Control-Request-Headers: content-type
18187 POST    /transfer?mode=fixed&pf=ok | Origin: ... | Content-Type: application/json
```

こちらは、**プリフライトが通らなければ本番の POST は送られません**。単純なリクエストとプリフライトが要るリクエストで、サーバから見える結果がまったく違うことが分かります。

<Callout type="warn" title="よくある誤解: 「CORS エラーなら、リクエストはサーバに届いていない」">
  届いているかどうかは、**単純なリクエストかどうか**で決まります。
  単純なリクエスト（GET、フォームと同じ形の POST）は、CORS の判定より前にサーバに届き、処理されています。上の実験では送金の記録まで残りました。
  届かないのは、プリフライトが要るリクエストでプリフライトが失敗した場合だけです。
  仕様も、共有されない応答でも**サーバがした処理はタイミングなどの副作用から漏れうる**と注意しています（[3.3.3](https://fetch.spec.whatwg.org/#http-responses)）。
</Callout>

<Callout type="warn" title="よくある誤解: 「CORS はサーバを攻撃から守る」">
  CORS は**ブラウザの中の読み出しの制限を、サーバが緩める仕組み**です。サーバに対する防御は何も足しません。
  状態を変える API を守るのは、CSRF の対策（同期トークン、SameSite、Fetch Metadata。第 110 回、第 90 回）と、認証と認可です。
  「`Content-Type: application/json` しか受け付けないので、プリフライトが必ず起きて安全」という考え方もありますが、サーバが `text/plain` で届いた JSON も受け付けてしまう実装だと、この前提は崩れます。**受け付ける `Content-Type` を厳密に確かめて初めて**、プリフライトは防御の一段になります。
</Callout>

## 手元で確かめる（2）: 資格情報とワイルドカード

先に API のオリジンで `/login` を開き、`sid=alice-session; HttpOnly; Secure; SameSite=None` の Cookie を受け取ってから、ページに戻って fetch します。API は Cookie があれば `"user": "alice"` を、無ければ `"anonymous"` を返します。

| リクエスト | 応答のヘッダ | 結果 | サーバに Cookie は届いたか |
| --- | --- | --- | --- |
| 既定（`same-origin`） | `Allow-Origin: *` | 読めた。`"user": "anonymous"` | 届かない |
| `credentials: 'include'` | `Allow-Origin: *` | 読めない | **届いた** |
| `include` | `*` と `Allow-Credentials: true` | 読めない | **届いた** |
| `include` | `http://127.0.0.1:18186`、`Allow-Credentials` なし | 読めない | **届いた** |
| `include` | `http://127.0.0.1:18186` と `Allow-Credentials: true` | 読めた。`"user": "alice"` | 届いた |

Chrome のコンソールには、判定の理由がそのまま出ます。

```
... The value of the 'Access-Control-Allow-Origin' header in the response must not be
the wildcard '*' when the request's credentials mode is 'include'.
... The value of the 'Access-Control-Allow-Credentials' header in the response is ''
which must be 'true' when the request's credentials mode is 'include'.
```

表の右の列に注目してください。**読めなかった 3 つでも、Cookie はサーバに届いています。** Cookie を付けるかどうかは、SameSite と第三者 Cookie の扱い（第 110 回、第 88 回）が決めることで、CORS は付けた後の応答を読ませるかどうかしか決めません。ここではページと API が同じサイトなので、`SameSite=Lax` でも Cookie は届きます。

`Access-Control-Expose-Headers` も確かめました。API は毎回 `X-Request-Id` を返していますが、`response.headers.get('x-request-id')` は `Expose-Headers: X-Request-Id` を付けた応答でだけ `req-11` を返し、付けない応答では `null` でした。

## 手元で確かめる（3）: Origin の反射と null

設定を手早く済ませようとして、**届いた `Origin` をそのまま `Allow-Origin` に書き返し、`Allow-Credentials: true` を付ける**実装を見かけます。これを `mode=reflect&cred=1` として、**別のサイト**のページ（`http://localhost:18186`。ホスト名が違うので 127.0.0.1 とは別サイト）から呼びました。

```
18187 GET /data?mode=reflect&cred=1 | Origin: http://localhost:18186 | Cookie: sid=alice-session | Sec-Fetch-Site: cross-site
  → 読めた: {"user": "alice", "secret": "balance=1000000"}
18187 GET /data?mode=fixed&cred=1   | Origin: http://localhost:18186 | Cookie: sid=alice-session | Sec-Fetch-Site: cross-site
  → TypeError: Failed to fetch
```

反射する実装では、**別のサイトのページが、alice としてログインした状態の応答を読めました**。許可リストで固定した実装では読めません。ここで Cookie がクロスサイトの fetch に付いたのは、執筆時点（2026 年 9 月）の Chrome が第三者 Cookie を既定で止めていないためで、Safari や Firefox では既定の設定で扱いが変わります（第 88 回、第 89 回）。ブラウザの既定に頼って安全になっている設定は、設定と呼べません。

もう 1 つは `null` です。`sandbox` 属性の付いた iframe（第 86 回）や、一部のリダイレクトを経たリクエストでは、`Origin` が `null` になります。実験では、`sandbox="allow-scripts"` の iframe の中から fetch しました。

```
18187 GET /data?mode=reflect&cred=1 | Origin: null | Cookie: sid=alice-session | Sec-Fetch-Site: cross-site
iframe から親へ: read: {"user": "alice", "secret": "balance=1000000"}
```

`null` は**どこの誰のページでも作れる**オリジンです。攻撃者は自分のページに sandbox の iframe を置くだけで `Origin: null` を名乗れます。

<Callout type="warn" title="よくある誤解: 「Origin を反射すれば手軽に CORS を通せる」">
  資格情報なしの反射は `*` とほぼ同じ意味ですが、**資格情報つきの反射は「すべてのオリジンに、利用者としてのアクセスを読ませる」**という設定になります。仕様が `include` で `*` を禁じた意味を、自分で打ち消しています。
  許可リストの照合も、前方一致や部分一致（`example.com` を含むかどうか）で書くと、`example.com.evil.example` のようなオリジンが通ります。スキーム・ホスト・ポートを完全一致で比べてください。
  `null` を許可リストに入れてはいけません。上の実験のとおり、誰でも名乗れます（[PortSwigger Web Security Academy: CORS](https://portswigger.net/web-security/cors)）。
</Callout>

<Callout type="warn" title="よくある誤解: 「サーバ間の通信や curl にも CORS がかかる」">
  CORS はブラウザが自分に課している制限です。curl に `-H 'Origin: https://evil.example'` を付けても、`Allow-Origin` の無い応答がそのまま読めます（下の実行例）。
  サーバから API を呼ぶ場合、Node の `fetch` も CORS の判定をしません。「CORS を設定したので、この API は他から呼ばれない」は成り立ちません。
</Callout>

```
$ curl -s -i -H 'Origin: https://evil.example' 'http://127.0.0.1:18187/data?mode=none'
HTTP/1.0 200 OK
X-Request-Id: req-21
Content-Type: application/json

{"user": "anonymous", "secret": "balance=1000000"}
```

## Vary: Origin と、キャッシュが壊す CORS

`Allow-Origin` を**リクエストによって変える**サーバは、応答に `Vary: Origin` を付ける必要があります。仕様の「CORS protocol and HTTP caches」がこの場面を説明しています（[Fetch Standard](https://fetch.spec.whatwg.org/#cors-protocol-and-http-caches)）。

1. サーバは、`Origin` の付いたリクエストにだけ `Allow-Origin` を返す
2. 利用者が先にその URL を**アドレスバーで開く**（移動には `Origin` が付かない）。`Allow-Origin` の無い応答がキャッシュに入る
3. 後でページが同じ URL を fetch すると、キャッシュの応答が使われ、`Allow-Origin` が無いので CORS で失敗する

実験の API に `/cached` を用意しました。`Cache-Control: max-age=300` を付け、`Origin` があればそれを `Allow-Origin` に書き返します。`vary=1` のときだけ `Vary: Origin` を付けます。

```
== Vary なし
18187 GET /cached?vary=0 | Sec-Fetch-Mode: navigate     ← アドレスバーで開く
（ページから fetch → サーバにリクエストは来ない。キャッシュから返り、TypeError）

== Vary: Origin あり
18187 GET /cached?vary=1 | Sec-Fetch-Mode: navigate
18187 GET /cached?vary=1 | Origin: http://127.0.0.1:18186 | Sec-Fetch-Mode: cors
（ページから fetch → 取り直され、"response #19" が読めた）
```

`Vary: Origin` があると、ブラウザは「`Origin` の値が違えば別の応答」と扱い、取り直します。

ブラウザのキャッシュなら壊れるのは 1 人の利用者ですが、**CDN やリバースプロキシのような共有キャッシュ**では影響が全員に広がります。`https://a.example` からの要求で作られた `Allow-Origin: https://a.example` の応答が CDN に入ると、`https://b.example` のページにも同じ応答が返り、b ではすべて CORS で失敗します。逆に、どのオリジンにも同じ値を返すなら、仕様は**常に同じ `Allow-Origin` を返し、`Vary` は使わない**よう勧めています。

実務では、`Vary` を尊重しない、または `Vary` の値の種類が多いとキャッシュしない CDN もあります。CDN の設定で、キャッシュのキーに `Origin` を含めるかを確かめてください（CDN ごとに違うので、ここでは一般論にとどめます）。

## プリフライトのキャッシュ

プリフライトは往復が 1 回増えるので、ブラウザは結果をキャッシュします（[4.9 CORS-preflight cache](https://fetch.spec.whatwg.org/#cors-preflight-cache)）。キャッシュの項目は、ネットワークの分割のキー、オリジン、URL、資格情報の有無、メソッドかヘッダ名、の組で持たれます。**URL ごと**なので、`/items/1` と `/items/2` は別々にプリフライトします。

`Access-Control-Max-Age` が無ければ 5 秒です（[4.8 CORS-preflight fetch](https://fetch.spec.whatwg.org/#cors-preflight-fetch)）。大きな値を書いても、ブラウザは自分の上限で切り詰めます。

| ブラウザ | 上限 | 出典 |
| --- | --- | --- |
| Chrome（Chromium 76 以降） | 2 時間 | [MDN](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Access-Control-Max-Age) |
| Firefox | 24 時間 | MDN、[Firefox のソース](https://github.com/mozilla-firefox/firefox/blob/main/netwerk/protocol/http/nsCORSListenerProxy.cpp)（`std::min(age, 86400U)`） |
| Safari（WebKit） | 600 秒 | [WebKit のソース](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/loader/CrossOriginPreflightResultCache.cpp)（`maxPreflightCacheTimeout = 600_s`） |

実験で、同じ URL への `PUT`（JSON）を 0 秒、1 秒、7 秒の時点で 3 回送りました。

```
== Max-Age なし（既定の 5 秒）
OPTIONS /item?...&k=a
PUT     /item?...&k=a      ← 0 秒
PUT     /item?...&k=a      ← 1 秒: キャッシュが効いてプリフライトなし
OPTIONS /item?...&k=a      ← 7 秒: 5 秒を過ぎたので、もう一度
PUT     /item?...&k=a
== Max-Age: 600
OPTIONS /item?...&k=b
PUT     /item?...&k=b
PUT     /item?...&k=b
PUT     /item?...&k=b      ← 7 秒後もプリフライトなし
```

WebKit のソースのコメントは、上限を短くしている理由を「安全なネットワークに切り替えた後に、汚染されたキャッシュを使う危険を小さくするため」と書いています。プリフライトの結果も、**キャッシュされる以上、古くなる**ものです。許可を取り消したとき、最大で Max-Age の間は古い許可が使われることを見込んでおきます。

## 公開サイトから社内と localhost へ: Local Network Access

「Basic safe CORS protocol setup」の注意を思い出してください。CORS は「ファイアウォールの内側にあること」を権限として扱えません。そして単純なリクエストはそのまま届くので、公開サイトのページは、利用者のブラウザを踏み台にして、**家庭のルータや社内の管理画面、`localhost` で動く開発用のサーバに、フォームと同じ形のリクエストを送れます**。読めなくても、送るだけで設定を変えられる機器は少なくありません。

Chrome はこれを塞ぐ取り組みを続けてきました。

| 時期 | 内容 | 出典 |
| --- | --- | --- |
| 以前 | **Private Network Access**: 私的なアドレスへのリクエストの前にプリフライトを送り、機器の側に許可させる方式を試した。のちに保留 | [Chrome for Developers](https://developer.chrome.com/blog/local-network-access) |
| Chrome 142（2025 年 10 月） | **Local Network Access**: 公開サイトから私的なアドレスや loopback への要求、社内サイトから loopback への要求を、**利用者の許可のプロンプト**で制限。安全な文脈（HTTPS）でだけ許可を求められる | 同上、[Chrome Platform Status](https://chromestatus.com/feature/5152728072060928) |
| Chrome 145 | 許可を `local-network`（私的なアドレス）と `loopback-network`（`localhost` など）の 2 つに分けた。旧名の `local-network-access` は別名として残る | [Chrome Platform Status](https://chromestatus.com/feature/5068298146414592) |

Local Network Access は、**機器の側が CORS を正しく実装することを当てにしない**方向への転換です。プリフライトの方式は、世の中の古いルータがプリフライトに答えられないため、機器の側の対応を待つ必要がありました。許可のプロンプトは、判断を利用者に移します。許可されたリクエストは、私的なアドレスの機器が公的に信頼される証明書を持ちにくいことを考慮して、混在コンテンツの制限も緩められます。iframe の中から使う場合は Permissions-Policy で委ねます（第 91 回）。

他のブラウザについて、Chrome Platform Status は執筆時点（2026 年 9 月）で Firefox を「Shipped/Shipping」、Safari を「No signal」としています。Firefox 側の説明は [Mozilla のサポート記事](https://support.mozilla.org/en-US/kb/control-personal-device-local-network-permissions-firefox)にあります。変化の速い領域なので、使う前に各ブラウザの最新の説明を確かめてください。

## CORS は何と組み合わさって意味を持つか

CORS 単独では、守れるものがほとんどありません。どの部品と組み合わさるかを表にします。

| 組み合わせる部品 | 役割の分担 | 回 |
| --- | --- | --- |
| 同一オリジンポリシー | 既定で読み出しを禁じる。CORS はその例外を作る | 第 85 回、第 86 回 |
| SameSite と第三者 Cookie の制限 | Cookie を**付けるか**を決める。CORS は付けた後に**読ませるか**を決める | 第 110 回、第 88 回、第 89 回 |
| CSRF トークン、Fetch Metadata | 単純なリクエストで**届いてしまう**書き込みを、サーバの側で拒む | 第 110 回、第 90 回 |
| CSP の `connect-src` | 自分のページが**どこへ** fetch してよいかを、ページの側で絞る | 第 91 回 |
| CORP、ORB、COEP | `img` や `script` の埋め込みのように、CORS を通らない読み込みがプロセスのメモリに載るのを制限する | 第 92 回 |
| HTTP キャッシュと CDN | `Vary: Origin` を付けないと、正しい CORS の設定がキャッシュで壊れる | 第 77 回 |
| Local Network Access | ファイアウォールの内側を、CORS では守れない権限として扱う | この回 |

なかでも見落とされやすいのが 3 行目です。**CORS の設定をどれだけ厳しくしても、単純なリクエストで状態を変える API は守れません。** 読ませないことと、書かせないことは、別の部品が受け持っています。

## まとめ

- CORS は、同一オリジンポリシーの読み出しの制限を、サーバがヘッダで緩める仕組み。判定はブラウザが**応答の後で**行う（Fetch Standard 3.3 節）
- 単純なリクエスト（フォームで送れた範囲）はそのまま届き、処理される。それを超えるものは `OPTIONS` のプリフライトで先に確かめ、通らなければ本番は送られない
- `credentials: 'include'` のときは `Allow-Origin: *` が使えず、オリジンの名指しと `Allow-Credentials: true` が要る。`*` は「curl で誰でも取れるもの」という宣言だから
- CORS で読めなくても、Cookie は付いて届いている。Cookie を付けるかは SameSite と第三者 Cookie の扱いが決める
- `Origin` の反射と資格情報の組み合わせ、`null` の許可は、どのサイトにも利用者としての応答を読ませる
- `Allow-Origin` を変えるなら `Vary: Origin`。共有キャッシュでは全員が壊れる
- プリフライトの結果は既定 5 秒、ブラウザごとの上限（Chrome 2 時間、Firefox 24 時間、Safari 600 秒）までキャッシュされる
- ファイアウォールの内側は CORS で守れない。Chrome は Local Network Access で、公開サイトから社内や localhost への要求を利用者の許可制にした

次の回では、この回で何度も「第 88 回」と送ってきた、**ファーストパーティ Cookie とサードパーティ Cookie**を正面から扱います。同じ Cookie が、どのページの中で使われるかによって第一者にも第三者にもなる、という点から始めます。
