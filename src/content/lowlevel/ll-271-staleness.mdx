## 変わらないものから、変わるものへ

第 270 回では、マスタデータのように**ほとんど変わらないもの**をアプリケーションのメモリに持ちました。変わったときに確実に捨てられるなら、そのキャッシュは古いものを返しません。

この回で扱うのは、**変わり続けるもの**です。ランキング、集計値、他の利用者の状態などは、書き込みがあるたびに変わります。書き込みのたびにキャッシュを捨てていると、書き込みの多い場面ではほとんど当たりません。かといって捨てなければ古いものを返し続けます。

その間を埋めるのが、**どれだけ古くてもよいか**という約束です。仕様が「更新から 1 秒以内に反映されていればよい」と決めているなら、その 1 秒の間は同じ応答を何人に返しても構いません。この回では、その猶予の使い方と、使い方を誤ったときに起きることを見ます。

| 節 | 問い |
| --- | --- |
| 鮮度の猶予 | 仕様は何秒の古さを許しているか |
| TTL の数え方 | 期限はどの時刻から数えるのか |
| Thundering Herd | 期限が切れた瞬間に何が起きるか |
| 合流 | 同時に来た同じ要求を 1 回にまとめると何が変わるか |
| 裏で作り直す | 利用者を待たせずに新しくするには |
| 実測 | 5 通りの実装で、重い処理の呼ばれた回数と古さを数える |

## 仕様が決める鮮度の猶予

ISUCON の問題は、多くの回で「この情報は何秒まで古くてよい」と明記しています。講評から拾うと次のとおりです。

| 回 | 対象 | 許された古さ | 出典 |
| --- | --- | --- | --- |
| ISUCON10 本選 | 観戦者向けのダッシュボード | 最大 1 秒 | [講評](https://isucon.net/archives/55140539.html) |
| ISUCON12 予選 | 参加者の情報（失格処理の後） | 3 秒 | [講評](https://isucon.net/archives/56850281.html) |
| ISUCON13 | アイコン画像のハッシュ値 | 更新から 2 秒以内 | [講評](https://isucon.net/archives/58001272.html) |
| ISUCON14 | 椅子の座標 | 過去 3 秒以内 | [講評](https://isucon.net/archives/58869617.html) |

ISUCON10 本選の講評は、ダッシュボードについて次のように書いています。

> ダッシュボードにアクセスするのは仮想選手と仮想オーディエンスなのですが、仮想オーディエンス向けダッシュボードのみ、最大 1 秒のキャッシュが許可されていました。

ISUCON12 予選の講評は、キャッシュしてよい条件を箇条書きで並べ、その最後に猶予を挙げています。

> レギュレーション上、更新が行われるイベントが発生してから実際の情報が更新されるまでに3秒の猶予がある

猶予は、何をキャッシュしてよいかの範囲も決めます。ISUCON14 の講評は、椅子の座標に 3 秒の猶予があるからといって応答全体をキャッシュできるわけではなかったと書いています。

> ドキュメントでこのエンドポイントで返される椅子の座標は過去3秒以内に送られた POST /api/chair/coordinateであれば良いという記述がありますが、猶予されるのは位置情報のみで椅子が割り当て可能かは即時に反映される必要があったためサクッとレスポンス全体を3秒キャッシュみたいなことはできない様になっていたと思います。

1 つの応答の中に、古くてよい部分と、すぐ反映しなければならない部分が混ざっていることがあります。キャッシュする単位は応答ではなく、**猶予が同じ値のまとまり**です。

本番のサービスには、このような猶予が仕様書に書かれていないことがほとんどです。それでも「ランキングは 10 秒遅れてよいか」「在庫数は 1 秒遅れてよいか」は、決めれば決まる問いです。決めないままキャッシュを入れると、どこまで古くてよいかを実装者が暗黙に決めたことになります。

<Callout type="tip" title="猶予が無いなら、仕様を問い直す">
  猶予が書かれていない値でも、利用者がその値を見て何をするかを考えると、許される古さが見えてくることがあります。
  ランキングの順位は数秒遅れても困る人は少なく、残り 1 個の在庫は 1 秒遅れると売り越しが起きます。
  前者は猶予を決めて合意し、後者はキャッシュせずに書き込みの側で正しさを守ります（第 275 回）。
</Callout>

## TTL の数え方

猶予を使う最も単純な方法は、TTL（有効期限）付きのキャッシュです。値を作ったら時刻と一緒に持っておき、期限内ならそれを返し、過ぎていたら作り直します。

```go
if b, ok := load(); ok && time.Since(b.storedAt) < ttl {
	return b
}
b := buildBoard()
store(b)
return b
```

ここで、`storedAt` を**キャッシュに入れた時刻**にするのが素朴な実装です。ところが、利用者から見た古さは、キャッシュに入れた時刻ではなく、**集計がデータを読んだ時刻**から数えます。集計に 50 ミリ秒かかるなら、キャッシュに入った瞬間にその値はすでに 50 ミリ秒古く、TTL を 1 秒にすると、最後に返す応答は約 1.05 秒古くなります。

ISUCON10 本選の講評は、まさにこの点を指摘しています。

> この 1 秒の判定はシビアで、単に1秒キャッシュをしているだけだと、アプリケーションが詰まり始めたときに「仮想負荷走行の結果が 1 秒以内にダッシュボードのレスポンスに反映されている」が達成できなくなる場合があったかと思います。

アプリケーションが詰まると、集計の待ち時間が延び、その分だけ古さが猶予を超えます。対策は 2 つです。期限をデータを読んだ時刻から数えるか、TTL を猶予より十分短くするかです。講評に載っている作問チーム（白金動物園）の解答例では、`Cache-Control: public, max-age=1` を付けたうえで、手前の Varnish の TTL を `ttl=0.5s, grace=0.2s` にしています。合計しても 1 秒に届かない値です。

## 期限が切れた瞬間に起きること

TTL 付きのキャッシュには、もう 1 つ落とし穴があります。期限が切れた瞬間に来ていた要求は、**全員が「キャッシュに無い」と判断し、全員が作り直しを始める**ことです。

```
時刻 →        期限切れ
               │
要求 1 ────────┼─ 無い → 集計 ──────────┐
要求 2 ────────┼─ 無い → 集計 ──────────┤  データベースには
要求 3 ────────┼─ 無い → 集計 ──────────┤  同じ集計が N 本並ぶ
  ⋮            │                        │
要求 N ────────┼─ 無い → 集計 ──────────┘
```

この現象は Thundering Herd（群れが一斉に押し寄せる）や、キャッシュスタンピードと呼ばれます。集計が重いほど作り直しにかかる時間が長くなり、その間に来た要求もまた作り直しを始めるので、被害が広がります。データベースの CPU が 4 つしかなければ、5 本目以降の集計は順番待ちになり、待ちがさらに作り直しの時間を延ばします。

ISUCON10 本選の講評は、ダッシュボードのキャッシュについて次のように続けています。

> 仮想オーディエンス向けダッシュボードのキャッシュについては、アプリケーションに対して同時に複数のキャッシュ更新（Thundering Herd）が走らないようにしたり、非同期でキャッシュ更新を走らせるようにしたりするのが効果的だったかと思います。たとえば Go の singleflight や Varnish を使うことでこういった制御をする事が可能です。

ここには 2 つの対策が書かれています。**作り直しを 1 本に絞る**ことと、**作り直しを利用者の要求から切り離す**ことです。順に見ます。

## 同じ要求を 1 回にまとめる

作り直しを 1 本に絞る道具が、Go の [golang.org/x/sync/singleflight](https://pkg.go.dev/golang.org/x/sync/singleflight) です。`Do` の説明は次のとおりです。

> Do executes and returns the results of the given function, making sure that only one execution is in-flight for a given key at a time. If a duplicate comes in, the duplicate caller waits for the original to complete and receives the same results.

（与えられた関数を実行して結果を返す。同じキーの実行は同時に 1 つだけになるようにする。重複した呼び出しが来たら、その呼び出しは最初の実行が終わるのを待ち、同じ結果を受け取る。）

TTL のキャッシュと組み合わせると、期限切れのときだけ `Do` を通るようにします。

```go
var group singleflight.Group

func get() board {
	if b, ok := load(); ok && time.Since(b.storedAt) < ttl {
		return b
	}
	v, _, _ := group.Do("board", func() (any, error) {
		b := buildBoard()
		store(b)
		return b, nil
	})
	return v.(board)
}
```

期限が切れた瞬間に 100 本の要求が来ても、集計を走らせるのは最初の 1 本だけで、残りの 99 本はその結果を待って受け取ります。

この仕組みは、キャッシュが無くても使えます。キャッシュせずに `Do` だけを通すと、**同時に処理中の同じ要求**だけがまとまります。これをリクエストの合流（coalescing）と呼びます。ISUCON11 本選の講評は、GPA の一覧を取るクエリについて、科目が終了したとき以外は結果が変わらないので呼び出しを使い回せると書き、次のようにまとめています（[講評](https://isucon.net/archives/56163308.html)）。

> 当日はN+1の改善とGPA一覧取得のcoalescingの2つが達成できていれば、上位入賞を狙えたように思います。

この回で優勝したチームの参加記にも、作業の一覧に「GetGrades の SingleFlight 化」が挙がっています（[fujiwara組の参加記](https://sfujiwara.hatenablog.com/entry/isucon11-final)）。

### 合流にも古さがある

合流は「キャッシュしないので古くならない」と思われがちですが、そうではありません。途中から合流した要求は、**自分が来るより前に始まった集計の結果**を受け取ります。集計に 50 ミリ秒かかるなら、最大で約 50 ミリ秒古い結果です。

さらに、利用者が自分で書き込んだ直後に読むと、書き込みより前に始まった集計に合流して、**自分の書き込みが反映されていない結果**を受け取ることがあります。書いたものがすぐ読めること（read-your-writes）が求められる場面では、合流させてはいけません。

Go のキャッシュライブラリ [motoki317/sc](https://github.com/motoki317/sc) は、この違いを選べるようにしています。README の機能一覧は、合流と、より厳しい合流を分けて書いています。

> **Single Flight Execution:** Ensures only one goroutine is launched per key to fetch the value, preventing redundant work.

> **Strict Request Coalescing:** Offers an option (`EnableStrictCoalescing()`) to ensure all callers receive fresh data, suitable for specific use-cases.

## 利用者を待たせずに作り直す

singleflight で作り直しを 1 本に絞っても、期限が切れた瞬間に来た要求は、その 1 本が終わるまで待たされます。集計が 50 ミリ秒なら 50 ミリ秒です。

これを避けるには、**期限が切れる前に作り直す**か、**期限切れの値を返しながら裏で作り直す**かします。

| 方式 | 作り直しのきっかけ | 利用者の待ち | 古さの上限 |
| --- | --- | --- | --- |
| TTL のみ | 期限切れを見つけた要求 | 作り直しの時間（全員が自分で作る） | TTL ＋ 集計の時間 |
| TTL ＋ singleflight | 期限切れを見つけた最初の要求 | 作り直しの時間（1 本を待つ） | TTL ＋ 集計の時間 |
| 古いものを返しつつ裏で作り直す | 一定の古さを超えた最初の要求 | なし | 作り直しの間隔 ＋ 集計の時間 |
| 定期的に作り直す | タイマー | なし | 間隔 ＋ 集計の時間 |
| 書き込み時に作り直す | 書き込み | なし | 集計の時間 |

3 つ目は、HTTP の世界では `stale-while-revalidate`（[RFC 5861](https://www.rfc-editor.org/rfc/rfc5861)）と呼ばれる動きです。第 144 回では、Varnish が既定でこの動き（grace）をすることを確かめました。nginx では `proxy_cache_background_update` と `proxy_cache_use_stale updating` の組み合わせで同じことができます。nginx の文書は `proxy_cache_background_update` を次のように説明しています（[ngx_http_proxy_module](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache_background_update)）。

> Allows starting a background subrequest to update an expired cache item, while a stale cached response is returned to the client. Note that it is necessary to allow the usage of a stale cached response when it is being updated.

nginx には singleflight にあたる指定もあります。`proxy_cache_lock` です。

> When enabled, only one request at a time will be allowed to populate a new cache element identified according to the proxy_cache_key directive by passing a request to a proxied server. Other requests of the same cache element will either wait for a response to appear in the cache or the cache lock for this element to be released, up to the time set by the proxy_cache_lock_timeout directive.

4 つ目の「定期的に作り直す」は、ISUCON11 予選の講評がトレンドのページについて勧めた方法です（[講評](https://isucon.net/archives/56044867.html)）。

> 一度レスポンスを計算したら、そのデータをキャッシュしておき、全てのリクエストに対してそのデータを返すことができます。

> ただし、閲覧者は変化に注目しているので、常に同じものを返すことはユーザの増加に繋がりません。定期的に更新するような処理を入れると良いでしょう。

定期的な作り直しは、誰も見ていない間も集計を回し続けます。対象のキーが少なく、どれもよく読まれるなら適しています。キーが多く、ほとんど読まれないものが混ざるなら、読まれたときに作り直す方式の方が無駄がありません。

## 手元で確かめる

5 通りの実装を Go で作り、同じ負荷をかけて比べました。環境は Apple M1 Pro（8 コア）/ macOS 26.2、Go 1.24.6、golang.org/x/sync v0.16.0、負荷をかける側は hey 0.1.4 です。サーバと hey は同じマシンで動かしています。実験の間、同じマシンでは別の作業も動いており、毎秒の要求数は回によって 2 倍近く揺れました。以下では、揺れにくい「重い処理が呼ばれた回数」と「返した応答の古さ」を主に見ます。

### 実験の作り

重い集計の代わりに、50 ミリ秒眠る関数を置きました。データベースの CPU が 4 つしかない状況を表すため、この関数は**同時に 4 本までしか実行できない**ようにしています。5 本目からは順番待ちです。

```go
var dbSlots = make(chan struct{}, 4)

func buildBoard() board {
	backendCalls.Add(1)
	dbSlots <- struct{}{}
	snapshot := time.Now() // 集計が読んだデータは、クエリを始めた時点のもの
	time.Sleep(50 * time.Millisecond)
	<-dbSlots
	return board{builtAt: snapshot, body: "leaderboard"}
}
```

応答を返すたびに `time.Since(b.builtAt)`、つまり**その応答に含まれるデータが何ミリ秒前のものか**を測り、最大値を記録します。TTL は 1 秒にしました。比べた実装は次の 5 つです。

| 名前 | 実装 |
| --- | --- |
| `nocache` | 毎回集計する |
| `ttl` | TTL 1 秒。期限切れなら自分で集計する |
| `ttl-sf` | TTL 1 秒。期限切れなら singleflight を通して集計する |
| `sf` | キャッシュせず、singleflight で同時の要求だけ合流させる |
| `swr` | TTL の半分（0.5 秒）を過ぎたら古い値を返しつつ、裏で 1 本だけ作り直す |

負荷は `hey -c 100 -z 10s` です。100 本の接続が、応答を受け取るたびに次の要求を送ります（第 262 回の閉ループ）。

読み取れることを並べます。

- **キャッシュが無いと、集計の枠がそのまま上限になります。** `nocache` は毎秒約 75 件で、中央値でも 1.3 秒待っています。4 本 × 1 秒あたり 20 回で、理論上の上限は毎秒 80 回です。
- **TTL だけでは、期限切れのたびに 40〜50 本の集計が走ります。** 10 秒間に期限切れは約 10 回なので、`ttl` の 399〜500 回は、1 回の期限切れあたり 40〜50 本です。`ttl-sf` は 3 周とも 10 回、つまり期限切れ 1 回につき 1 本でした。
- **古さの最大値は、どちらも 1 秒を超えています。** `ttl` は 1059〜1080 ミリ秒、`ttl-sf` は 1060〜1065 ミリ秒です。期限をキャッシュに入れた時刻から数えているので、集計の 50 ミリ秒と順番待ちの分だけ猶予を超えます。前の節で見た ISUCON10 本選の指摘が、そのまま再現しています。
- **合流だけでも、集計の回数は 5 分の 1 になります。** `sf` は 179〜185 回で、`nocache` の約 850 回より大幅に少なく、毎秒の要求数は約 24 倍です。古さは最大 60〜76 ミリ秒で、集計 1 回分の時間に収まっています。
- **裏で作り直す方式は、集計の回数が少ないまま古さが小さくなります。** `swr` は 18〜19 回で、古さの最大は 659〜695 ミリ秒でした。作り直しを 0.5 秒ごとにしているので、`ttl-sf` より集計は多く、古さは小さくなります。

### p99 では見えない、期限切れの瞬間

`ttl` と `ttl-sf` の p99 は、3 周のうち 2 周で `ttl` の方が悪かったものの、差ははっきりしません。Thundering Herd は期限切れの瞬間にだけ起きるので、全体の 1% より少ない要求にしか現れないからです。3 周目の応答時間の分布を見ると違いが分かります。

`ttl` では、0.146 秒を超えた要求が 529 件あり、最も遅いものは 1.46 秒待っています。期限切れのたびに 40〜50 本の集計が 4 本の枠に並び、最後尾は 50 ミリ秒 × 約 12 回分を待つからです。`ttl-sf` は最も遅いものでも 0.13 秒でした。平均や p99 だけを見ていると、この**期限切れのたびに一部の利用者が 1 秒以上待たされる**現象を見落とします。

### 冷えた状態に一斉に来る

キャッシュが空の状態に要求が一斉に届く場面は、再起動の直後やデプロイの直後に起きます。サーバを起動した直後に、200 本の要求を同時に送りました（`hey -n 200 -c 200`）。

```text
ttl    mode=ttl backend_calls=200 max_age_ms=65.7  Slowest: 2.6853 secs  Fastest: 0.0573 secs  50% in 1.3988 secs
ttl-sf mode=ttl-sf backend_calls=1 max_age_ms=53.9  Slowest: 0.0670 secs  Fastest: 0.0552 secs  50% in 0.0612 secs
```

`ttl` は 200 本すべてが集計を走らせ、最後の要求は 2.69 秒待ちました。`ttl-sf` は集計 1 回で、全員が 67 ミリ秒以内に応答を受け取っています。

### 並列度を変える

`ttl` の 1 回の期限切れあたりの集計の数は、同時に来ている要求の数で決まります。並列度を変えて測りました。

```text
c=10  mode=ttl    backend_calls=85
c=10  mode=ttl-sf backend_calls=10
c=300 mode=ttl    backend_calls=600
c=300 mode=ttl-sf backend_calls=10
```

`ttl` は負荷が増えるほど集計が増え、`ttl-sf` は負荷によらず 10 回です。**速くして利用者が増えるほど、TTL だけのキャッシュはデータベースへの負荷を増やします。** 第 262 回で見た「速くすると負荷が増える」現象と組み合わさると、キャッシュを入れたのに、ある負荷を超えたところで急に詰まるという形で現れます。

### 期限をデータの時刻から数える

最後に、期限を `storedAt`（キャッシュに入れた時刻）ではなく `builtAt`（集計がデータを読んだ時刻）から数えるように変えて、`ttl-sf` と `swr` を測り直しました。

```text
c=100 mode=ttl-sf backend_calls=10 max_age_ms=1000.0
c=100 mode=swr    backend_calls=20 max_age_ms=625.4
```

`ttl-sf` の古さの最大は 1000.0 ミリ秒になり、1 秒の猶予の内側に収まりました。期限ちょうどの値なので、本当に 1 秒以内を守るなら TTL をもう少し短くします。

## 本番で使うときの判断

### どの方式を選ぶか

実測から、方式ごとの性質を整理します。

| 状況 | 向く方式 |
| --- | --- |
| 同じ重い処理が同時に何本も走っている | まず合流（singleflight）。キャッシュを入れなくても回数が減る |
| 猶予があり、読まれる頻度が高い | TTL ＋ singleflight。TTL は猶予から集計の時間を引いた値以下に |
| 期限切れの瞬間の待ちも許したくない | 古いものを返しつつ裏で作り直す。古さの上限は作り直しの間隔で決まる |
| 対象のキーが少なく、常に読まれる | 定期的に作り直す |
| 書き込みの回数が読み込みよりずっと少ない | 書き込み時に作り直す（第 274 回） |
| 自分の書き込みがすぐ見えないと困る | 合流もキャッシュもしない。または書いた本人だけ別の経路で読む |

### キーの粒度

singleflight の効果は、**同時に同じキーが来る**ことが前提です。利用者ごとに違うキーで呼ぶなら、同時に同じキーが来ることは少なく、合流はほとんど起きません。ISUCON11 本選の GPA のように引数が定数のクエリや、全員に同じものを返すランキングで効きます。

### エラーと遅い 1 本

合流させると、最初の 1 本の失敗や遅れが、合流した全員に伝わります。最初の 1 本が 30 秒かかれば、合流した要求もすべて 30 秒待ちます。singleflight には `Forget` があり、キーを忘れさせて次の呼び出しを新しく始めさせられます。集計にはタイムアウトを付け、失敗した結果はキャッシュに入れないようにします。

### 複数台のとき

この回の実装は、どれも 1 つのプロセスの中で完結しています。アプリケーションが 3 台に分かれていれば、期限切れのたびに最大 3 本の集計が走り、3 台が返す値の古さもそれぞれ違います。台数が少ないなら、これで足りることがほとんどです。台数が多いなら、手前のリバースプロキシでまとめる（`proxy_cache_lock`、Varnish）か、Redis などの共有の場所に結果を置きます。ISUCON10 本選の講評に載った解答例も、観戦者向けのダッシュボードをアプリケーションの中ではなく、手前の Varnish でキャッシュしています。

HTTP のキャッシュの規則に乗せてしまえば、作り直しの制御はプロキシやブラウザに任せられます。次の第 272 回では、その HTTP とプロキシの層を見ます。

## まとめ

- 「何秒以内に反映すればよい」という仕様は、その時間だけ同じ応答を使い回してよいという許可でもある。本番では、決まっていない猶予を決めるところから始める
- 猶予は値ごとに違う。1 つの応答に猶予の違う値が混ざるなら、キャッシュする単位を分ける（ISUCON14 の座標と割り当て可否）
- 古さは、データを読んだ時刻から数える。キャッシュに入れた時刻から数えると、集計の時間と待ちの分だけ猶予を超える。実測では TTL 1 秒で最大 1.08 秒古い応答を返した
- TTL だけのキャッシュは、期限切れの瞬間に全員が作り直しを始める（Thundering Herd）。実測では 1 回の期限切れで 40〜50 本の集計が走り、一部の要求が 1.46 秒待った
- singleflight で作り直しを 1 本に絞ると、負荷の大きさによらず期限切れ 1 回につき 1 本になる。冷えた状態に 200 本が一斉に来ても集計は 1 回だった
- 合流（coalescing）はキャッシュが無くても効く。実測では集計の回数が約 5 分の 1、毎秒の要求数は約 24 倍になった
- 合流した要求は、自分が来る前に始まった集計の結果を受け取る。自分の書き込みがすぐ見える必要がある場面では使わない
- 古いものを返しつつ裏で作り直す方式は、利用者を待たせずに古さの上限を下げる。HTTP では stale-while-revalidate、nginx では proxy_cache_background_update にあたる
- Thundering Herd は期限切れの瞬間にだけ起きるので、平均や p99 では見えにくい。応答時間の分布と最大値を見る
- 速くして利用者が増えるほど、TTL だけのキャッシュは裏への負荷を増やす
