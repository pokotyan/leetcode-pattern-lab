## デバッガはただのプロセス

gdb や lldb は、何か特別な権限で動いているように見えます。他のプログラムを好きな場所で止め、変数の値を読み、書き換え、1 行ずつ進められるからです。

しかし、デバッガ自体は **普通のユーザプロセス** です。カーネルに 1 つだけ頼みごとをしています。「あのプロセスを止めて、中を読み書きさせてくれ」。それが **ptrace** というシステムコールです。

第 41 回で見た `strace` も、同じ ptrace を使っています。strace は「システムコールのたびに止めて」と頼み、デバッガは「この命令に来たら止めて」と頼む。違いはそれだけです。

## ptrace: 他人のプロセスを止めて覗く

ptrace で追跡する側を **tracer**、追跡される側を **tracee** と呼びます。関係の作り方は 2 通りあります。

- **自分で起動する。** fork した子が `PTRACE_TRACEME` を呼んでから exec する。`gdb ./a.out` はこちら
- **動いているものに取り付く。** `PTRACE_ATTACH`（または `PTRACE_SEIZE`）で、既存のプロセスを捕まえる。`gdb -p <PID>` はこちら

関係ができると、tracee は **シグナルを受け取るたびに止まり、tracer に知らせます**。第 46 回で見たシグナルが、デバッガへの通知の経路として使われています。tracer は `waitpid` でその停止を待ち、止まっている間に次の操作をします。

| 操作 | 何をするか |
| --- | --- |
| `PTRACE_PEEKDATA` / `PEEKTEXT` | tracee のメモリを 1 ワード読む |
| `PTRACE_POKEDATA` / `POKETEXT` | tracee のメモリに 1 ワード書く |
| `PTRACE_GETREGS` / `SETREGS` | tracee のレジスタをまとめて読む / 書く |
| `PTRACE_CONT` | 再開する |
| `PTRACE_SINGLESTEP` | 1 命令だけ実行して、また止める |
| `PTRACE_SYSCALL` | 次のシステムコールの出入りで止める（strace が使う） |

デバッガの機能は、すべてこの組み合わせで作られています。変数の値を表示するのは PEEK、変数を書き換えるのは POKE、「ここで止まる」はこの後で見るブレークポイントです。

## ブレークポイントは命令の書き換え

「この関数に来たら止めて」という機能は、CPU に専用の仕組みがあるわけではありません。**止めたい場所の命令を、止まる命令に書き換えています**。

x86 には `int3` という 1 バイトの命令（`0xCC`）があります。実行すると、第 13 回で見た **トラップ** が起き、カーネルがそのプロセスに `SIGTRAP` を送ります。tracee は止まり、tracer に知らせが届きます。

1 バイトであることが重要です。どんなに短い命令の先頭にも置けるので、隣の命令を壊しません。

手順は次のとおりです。

```
1. 止めたいアドレスの元の 1 バイトを PEEK で読んで保存する
      55  48 89 e5 ...        (push rbp; mov rbp, rsp; ...)
2. そこに 0xCC を POKE で書く
      CC  48 89 e5 ...
3. CONT で再開する
4. CPU が 0xCC を実行 → トラップ → SIGTRAP → tracee が止まる
   このとき命令ポインタは、トラップの性質上「次の命令」= 元のアドレス + 1 を指している
5. 元のバイト 55 を書き戻し、命令ポインタを 1 戻す
6. ユーザが「続行」したら、1 命令だけ SINGLESTEP で実行し、
   もう一度 0xCC を書いてから CONT する（次に来たときも止まるように）
```

手順 4 の「+1」は、第 13 回で見たフォールトとトラップの違いそのものです。トラップの戻り先は次の命令なので、デバッガが 1 つ戻してやる必要があります。

最小のデバッガは、次のような骨組みになります（x86-64 の Linux、エラー処理は省略）。

```c
pid_t pid = fork();
if (pid == 0) {
    ptrace(PTRACE_TRACEME, 0, NULL, NULL);
    execl("./target", "target", NULL);        // exec の直後に SIGTRAP で止まる
}
int status;
waitpid(pid, &status, 0);

long orig = ptrace(PTRACE_PEEKTEXT, pid, addr, NULL);
ptrace(PTRACE_POKETEXT, pid, addr, (orig & ~0xffL) | 0xcc);   // 下位 1 バイトを int3 に
ptrace(PTRACE_CONT, pid, NULL, NULL);
waitpid(pid, &status, 0);                     // ブレークポイントで止まった

struct user_regs_struct regs;
ptrace(PTRACE_GETREGS, pid, NULL, &regs);     // regs.rip == addr + 1
ptrace(PTRACE_POKETEXT, pid, addr, orig);     // 元に戻す
regs.rip = addr;
ptrace(PTRACE_SETREGS, pid, NULL, &regs);     // 1 つ戻す
```

`addr` は、`nm target` で調べた関数のアドレスです（第 28 回）。PIE でビルドされていれば、読み込まれた先頭アドレスを `/proc/<PID>/maps` から足す必要があります。

<Callout type="note" title="読み取り専用のコードに、どうやって書くのか">
  コードのページは読み取り専用で、しかも同じ実行ファイルを動かしている
  他のプロセスと共有されています。そこに 0xCC を書いてよいのでしょうか。

  ptrace の書き込みは、カーネルが保護を越えて行います。そのとき、
  第 24 回で見た **copy-on-write** が働き、tracee のページだけが複製されてから書き換わります。
  ディスク上のファイルも、同じプログラムを動かしている他のプロセスも影響を受けません。
</Callout>

ARM64 では、`int3` の代わりに `brk` 命令を使います。命令の長さは 4 バイト固定で、止まったときの命令ポインタは `brk` 自身を指したままです。**仕組みは同じで、細部だけが命令セットによって違います**。

## 1 命令ずつ進める

gdb の `stepi` は、1 命令だけ実行して止まります。これには CPU の機能を使います。

x86 のフラグレジスタには **TF**（トラップフラグ）があります。これを立てると、CPU は **1 命令実行するたびにデバッグ例外を起こします**。`PTRACE_SINGLESTEP` は、カーネルがこのフラグを立ててから tracee を再開する操作です。

ソースの 1 行ずつ進む `step` や `next` は、その上に作られています。

- `step`: 行が変わるまで、1 命令ずつ進める
- `next`: 関数呼び出しに入ったら、戻り先のアドレスに一時的なブレークポイントを置いて CONT する。関数の中を 1 命令ずつ進むと遅すぎるからです

「どこからどこまでが 1 行か」をデバッガが知っているのは、この後で見るデバッグ情報のおかげです。

## ハードウェアのブレークポイント

命令の書き換えでは止められないものがあります。「**この変数が書き換えられたら止めて**」という **ウォッチポイント** です。どの命令が書くのか、事前には分からないからです。

素朴にやるなら、1 命令ずつ実行して、毎回その変数の値を比べます。これは数百倍遅くなります。

そこで CPU が専用のレジスタを持っています。x86 では **DR0〜DR3** に監視したいアドレスを、**DR7** に「実行か、書き込みか、読み書きか」と監視する長さを設定します。条件に一致するアクセスが起きると、CPU がデバッグ例外を起こします（[x86 debug register - Wikipedia](https://en.wikipedia.org/wiki/X86_debug_register)）。

アドレスを入れるレジスタは 4 本しかないので、**同時に使えるハードウェアウォッチポイントは 4 つまで**です。gdb で `watch` を 5 つ以上置くと、残りは遅いソフトウェア方式に落ちます。

| 方式 | 仕組み | 速さ | 個数 |
| --- | --- | --- | --- |
| ソフトウェアブレークポイント | 命令を 0xCC に書き換え | 止まるまでは等速 | 実質無制限 |
| ハードウェアブレークポイント | DR0〜DR3 に実行アドレス | 等速 | 4 |
| ハードウェアウォッチポイント | DR0〜DR3 にデータのアドレス | 等速 | 4 |
| ソフトウェアウォッチポイント | 1 命令ごとに値を比較 | **極端に遅い** | 実質無制限 |

ハードウェアブレークポイントは、コードを書き換えられない場所（ROM や、まだ読み込まれていない共有ライブラリ）でも使えます。

## 機械語とソースを結ぶ DWARF

ここまでの操作はすべて、**アドレスとレジスタ**の世界の話です。しかし私たちは「`main.c` の 42 行目で止めて」「`user->name` を表示して」と頼みます。この変換に使うのが **デバッグ情報** です。

`-g` を付けてコンパイルすると、第 28 回で見た `.debug_*` セクションに **DWARF** という形式の情報が入ります。

| セクション | 中身 | デバッガが使う場面 |
| --- | --- | --- |
| `.debug_line` | 機械語のアドレスとソースの行の対応表 | 「42 行目で止めて」「いまどの行か」 |
| `.debug_info` | 型、変数、関数の情報。変数が **どこにあるか**（どのレジスタか、フレームの何バイト目か） | 「`user->name` を表示して」 |
| `.debug_frame` / `.eh_frame` | 各アドレスで、呼び出し元のフレームをどう復元するか | バックトレース |

変数の居場所は、アドレスによって変わります。最適化されたコードでは、ある変数が前半はレジスタに、後半はスタックにあり、途中で消えることもあります。gdb が `<optimized out>` と表示するのは、**その地点ではもう値がどこにも無い**という意味です。

<Callout type="tip" title="デバッグ情報は後から取ってこられる">
  ディストリビューションのパッケージは、サイズを抑えるためにデバッグ情報を取り除いて配られます。
  取り除く前の実行ファイルとデバッグ情報は、**Build ID** という一意の値で結びついています。

  **debuginfod** は、この Build ID を鍵にして、デバッグ情報とソースコードを HTTP で配るサーバです。
  Fedora では gdb や perf などが既定でこれを使い、手元にないデバッグ情報を自動で取ってきます
  （[LWN.net](https://lwn.net/Articles/852416/)）。

```bash
readelf -n /usr/bin/ls | grep "Build ID"
debuginfod-find debuginfo <Build ID>
```
</Callout>

## スタックを遡る

`bt`（バックトレース）は、「いまの関数を誰が呼び、その関数を誰が呼んだか」を遡ります。やり方は 2 つあります。

**フレームポインタを辿る。** 第 31 回で見たとおり、`rbp` を保存して連鎖させていれば、`rbp` → 呼び出し元の `rbp` → さらにその呼び出し元、と辿るだけで履歴が復元できます。単純で速い。

**CFI を読む。** フレームポインタが省略されていると、この連鎖は途中で切れます。そこで `.eh_frame` の **CFI**（Call Frame Information）を読みます。「このアドレスにいるとき、戻り先は `rsp + 24` にある」といった規則が、アドレスの範囲ごとに書かれています。正確ですが、読むのに手間がかかります。

`.eh_frame` はデバッグ情報を取り除いても残ります。C++ の例外が発生したとき、呼び出し元へ遡って `catch` を探す処理にも同じ情報が使われるからです。

<Callout type="note" title="フレームポインタが戻ってきた">
  フレームポインタはレジスタを 1 本使うため、長く省略されるのが普通でした。
  しかし、本番環境でのプロファイリング（第 81 回）で正しいスタックが取れない問題が大きくなり、
  Fedora 38 はパッケージの既定のビルドオプションに `-fno-omit-frame-pointer` を加えました
  （[Fedora Project Wiki](https://fedoraproject.org/wiki/Changes/fno-omit-frame-pointer)）。
  Ubuntu 24.04 も 64 ビットの全プラットフォームで同じ方針を取っています
  （[Brendan Gregg](https://www.brendangregg.com/blog/2024-03-17/the-return-of-the-frame-pointers.html)）。
  わずかな性能と引き換えに、観測しやすさを取った判断です。
</Callout>

## コアダンプはプロセスの写真

第 23 回で、落ちたプログラムのコアダンプを gdb で読みました。コアダンプの中身は、**止まった瞬間のプロセスをそのまま ELF ファイルにしたもの**です。

```bash
readelf -h core | grep Type        # Type: CORE (Core file)
readelf -l core                     # PT_NOTE と、たくさんの PT_LOAD
```

- **PT_LOAD**: プロセスのメモリの各領域。スタック、ヒープ、データ
- **PT_NOTE**: スレッドごとのレジスタ、受け取ったシグナル、どのファイルがどのアドレスにマップされていたか

実行ファイルと同じ形式なので、gdb はコアダンプを「止まったままのプロセス」として扱えます。レジスタもメモリもあるので、変数を表示し、バックトレースを取れます。ただし **動いているプロセスではない**ので、再開はできません。

落ちていないプロセスのコアダンプも取れます。`gcore <PID>` は、ptrace で取り付いてメモリとレジスタを読み、ファイルに書いてから離れます。本番で固まっているプロセスを、止めずに持ち帰って調べられます。

## 誰でも覗けるわけではない

ptrace でできることは、「そのプロセスとして何でもできる」ことと同じです。メモリの中の秘密鍵を読むことも、任意のコードを実行させることもできます。そのため、取り付ける権限は制限されています。

基本の規則は「**同じユーザのプロセスにだけ取り付ける**」です。setuid のプログラムのように途中で権限が変わったプロセスには取り付けられません。

多くのディストリビューションは、さらに **Yama** というセキュリティモジュールで制限しています（[Yama - The Linux Kernel documentation](https://docs.kernel.org/admin-guide/LSM/Yama.html)）。

| `ptrace_scope` | 意味 |
| --- | --- |
| 0 | 同じユーザのプロセスなら取り付けられる（従来の規則） |
| 1 | **自分の子孫にだけ**取り付けられる。`gdb ./a.out` はできるが、`gdb -p` は原則できない |
| 2 | `CAP_SYS_PTRACE` を持つプロセスだけ |
| 3 | 誰も取り付けられない。一度設定すると戻せない |

```bash
cat /proc/sys/kernel/yama/ptrace_scope
```

`gdb -p` が「Operation not permitted」で失敗したら、まずこの値を疑います。コンテナの中でデバッガが動かないときは、`CAP_SYS_PTRACE` が落とされていないか（第 77 回）を確かめます。

## まとめ

- デバッガはただのプロセス。ptrace で他のプロセスを止め、メモリとレジスタを読み書きする
- ソフトウェアブレークポイントは、命令の先頭を 1 バイトの `int3`（0xCC）に書き換えるだけ。トラップなので、止まったあと命令ポインタを 1 戻す
- シングルステップは CPU のトラップフラグ、ウォッチポイントは CPU のデバッグレジスタ（x86 では 4 本）を使う
- ソースの行や変数の名前は、DWARF がアドレスとレジスタに翻訳している
- バックトレースはフレームポインタか CFI で遡る。観測のためにフレームポインタを戻す動きがある
- コアダンプは止まった瞬間のプロセスを ELF にしたもの。`gcore` なら止めずに取れる
- ptrace は強力なので、Yama や capabilities で取り付けられる相手が制限されている
