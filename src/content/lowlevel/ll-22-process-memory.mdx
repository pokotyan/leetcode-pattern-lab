## 全体図

64 ビット Linux でのプロセスの仮想アドレス空間は、おおむねこうなっています。

```
   0xFFFFFFFFFFFFFFFF ┌──────────────────┐
                      │   カーネル空間     │  ユーザモードからは触れない
   0xFFFF800000000000 ├──────────────────┤
                      │    （未使用）      │  正準アドレスの穴
   0x00007FFFFFFFFFFF ├──────────────────┤
                      │     スタック       │  ↓ 下に伸びる
                      ├──────────────────┤
                      │                  │
                      │      （空き）      │
                      │                  │
                      ├──────────────────┤
                      │   共有ライブラリ    │  mmap 領域
                      ├──────────────────┤
                      │                  │
                      ├──────────────────┤
                      │      ヒープ        │  ↑ 上に伸びる
                      ├──────────────────┤
                      │       bss         │  初期値なしの静的変数
                      ├──────────────────┤
                      │      data         │  初期値ありの静的変数
                      ├──────────────────┤
                      │      text         │  機械語のコード
   0x0000000000400000 └──────────────────┘
                      （0 番地付近は意図的に未割り当て）
```

## それぞれの区画

### text（コード）

機械語の命令が入ります。権限は **読み取り + 実行、書き込み不可**。

書き込みを禁止することで、プログラムが自分のコードを書き換える攻撃を防ぎます。また、読み取り専用なので、**同じプログラムを複数起動しても物理メモリを共有できます**。

### data

初期値を持つ静的変数・グローバル変数が入ります。

```c
int counter = 100;              // data
static char msg[] = "hello";    // data
```

実行可能ファイルの中に初期値がそのまま格納されており、起動時にメモリへ読み込まれます。

### bss

**初期値を持たない**（あるいは 0 で初期化される）静的変数が入ります。

```c
int table[1000000];             // bss。4MB
static int flag;                // bss
```

重要なのは、**bss は実行可能ファイルの中で場所を取らない**ことです。「ここから 4MB ぶんを 0 で埋めてほしい」というサイズの情報だけが記録されています。

だから、100 万要素の配列を宣言しても、実行可能ファイルのサイズはほとんど増えません。一方、初期値を書くと data に入るので、ファイルが 4MB 大きくなります。

<Callout type="note" title="bss の由来">
  Block Started by Symbol の略で、1950 年代のアセンブラの擬似命令名が語源です。
  意味を考えても仕方がない名前の代表格です。
</Callout>

### ヒープ

実行時に動的に確保される領域です。`malloc` / `new` が返すのはここです。

**低いアドレスから高いアドレスへ**伸びます。

拡張の方法は 2 通りあります。

- **`brk` / `sbrk`**：ヒープの上端を動かす、古典的な方法
- **`mmap`**：まとまった領域を新しく確保する。大きな要求（glibc では既定で 128KB 以上）ではこちらが使われる

`malloc` はシステムコールではなく、**ライブラリの関数**です。OS からまとめて大きな領域をもらい、その中を細かく切り分けて管理します。毎回システムコールを呼んでいては遅すぎるからです。

### スタック

関数の呼び出しごとに積まれる領域です。局所変数、引数、戻り先アドレスが入ります。

**高いアドレスから低いアドレスへ**伸びます。ヒープと逆向きです。

なぜ逆向きか。仮想アドレス空間の両端から中央に向かって伸ばすことで、**どちらがどれだけ大きくなっても、空き領域を融通できる**からです。

スタックにはサイズの上限があります（Linux の既定で 8MB）。超えると **スタックオーバーフロー** で、通常はセグメンテーションフォールトになります。

```bash
ulimit -s          # 8192 (KB)
```

深い再帰や、巨大な局所変数の宣言が原因になります。

```c
void f() {
    char buf[10 * 1024 * 1024];     // 10MB。この時点で落ちる
}
```

<Callout type="tip" title="スレッドごとにスタックがある">
  スタックは**実行の流れごとに必要**です。したがって、スレッドを作ると
  そのスレッド用のスタックが別に確保されます（既定で 8MB の仮想領域）。
  数千スレッドを作るとアドレス空間を圧迫するのは、このためです。
  一方、実際に触ったページだけが物理メモリを消費するので、
  物理メモリが即座に 8MB × スレッド数になるわけではありません。
</Callout>

## 実際に見る

Linux では、プロセスのメモリ配置をそのまま読めます。

```bash
cat /proc/self/maps
```

```
555555554000-555555555000 r--p  ...  /usr/bin/cat      # text の前の読み取り専用部
555555555000-55555555a000 r-xp  ...  /usr/bin/cat      # text
55555555a000-55555555d000 r--p  ...  /usr/bin/cat      # rodata
55555555e000-55555555f000 rw-p  ...  /usr/bin/cat      # data
55555555f000-555555580000 rw-p  ...  [heap]
7ffff7d8b000-7ffff7db1000 r--p  ...  /lib/libc.so.6
7ffffffde000-7ffffffff000 rw-p  ...  [stack]
```

`r-xp` のような表記が権限です。`r` 読み、`w` 書き、`x` 実行、`p` プライベート（`s` なら共有）。

**text が `r-x` で `w` がないこと**、**data が `rw-` で `x` がないこと**を確認できます。これが第 18 回で触れた NX ビットの実際の姿です。

サイズの内訳は `pmap` や `/proc/self/smaps` で見られます。

## ASLR：毎回場所を変える

上のダンプをもう一度実行すると、**アドレスが変わっています**。

これは **ASLR**（Address Space Layout Randomization）によるものです。起動のたびに、スタック、ヒープ、共有ライブラリ、（PIE なら）実行ファイル本体の配置をランダムにずらします。

目的は攻撃の難化です。攻撃コードが「この関数はこのアドレスにある」と決め打ちできなくなります。

```bash
cat /proc/sys/kernel/randomize_va_space     # 2 = 全面的に有効
setarch -R ./a.out                          # ASLR を無効にして実行（デバッグ用）
```

デバッグでアドレスを固定したいときは無効化できますが、本番では必ず有効にします。

<Callout type="warn" title="ASLR は万能ではない">
  アドレスがどこかから 1 つでも漏れると（ログ、エラーメッセージ、フォーマット文字列の脆弱性）、
  そこを基準に他のアドレスを計算できてしまうことがあります。
  ASLR は攻撃を**難しくする**ものであって、**不可能にする**ものではありません。
  NX、スタックカナリア、RELRO といった他の防御と組み合わせて初めて意味を持ちます。
</Callout>

## 0 番地が空けてある理由

アドレス空間の先頭付近は、意図的に未割り当てにされています。

これにより、**ヌルポインタの参照が必ずページフォールトになります**。もし 0 番地が有効なメモリだったら、`*(int*)0 = 1` が静かに成功してしまい、バグが見つかりません。

「ヌルポインタを踏むと落ちる」という、デバッグ上ありがたい挙動は、この配置によって成立しています。

## まとめ

- text（コード、読み + 実行）、data（初期値あり）、bss（初期値なし）、heap（上向き）、stack（下向き）
- bss は実行可能ファイルの中で場所を取らない
- `malloc` はシステムコールではなくライブラリ関数。OS からまとめてもらって切り分ける
- スタックとヒープが逆向きに伸びるのは、空き領域を融通するため
- `/proc/self/maps` で実際の配置と権限が見られる
- ASLR は起動ごとに配置をずらす。他の防御と組み合わせて効く
- 0 番地が空いているおかげで、ヌルポインタ参照が検出できる
