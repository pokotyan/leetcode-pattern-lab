## 単位を決める

仮想アドレスから物理アドレスへの対応表を作りたい。しかし、**1 バイトごとに対応を記録したら、表そのものがメモリより大きくなります**。

そこで、ある程度のまとまりごとに対応させます。この単位が **ページ** です。標準的なサイズは **4KB** です。

```
仮想アドレス (64 bit の下位 48 bit を使う場合)
┌──────────────────────────────┬──────────────┐
│       ページ番号               │  オフセット    │
│         36 bit                │   12 bit     │
└──────────────────────────────┴──────────────┘
                                 2^12 = 4096
```

下位 12 ビットは **ページ内の位置** で、変換されずそのまま通ります。上位のページ番号だけが変換の対象です。

```
仮想 0x00401234
  ページ番号 = 0x401、オフセット = 0x234
  ページ 0x401 が物理ページ 0x8A3 に対応していれば
  物理アドレス = 0x8A3234
```

<Callout type="note" title="なぜ 4KB なのか">
  小さくすると、表のエントリ数が増えて表が巨大になります。
  大きくすると、少ししか使わないのに 1 ページ丸ごと割り当てることになり無駄が出ます（内部断片化）。
  4KB は 1970 年代に選ばれた妥協点で、今も既定値として残っています。
  現代のメモリ容量から見ると小さすぎるという議論はあり、
  そのための仕組みが後述のヒュージページです。
</Callout>

## 表が大きすぎる

48 ビットの仮想アドレス空間、4KB ページなら、ページ数は 2³⁶ = 約 687 億個です。

1 エントリ 8 バイトとすると、**表だけで 512GB**。1 プロセスあたり、です。成立しません。

問題の核心は、**アドレス空間のほとんどが使われていない**のに、全部のエントリを用意していることです。

## 多段にする

そこで、表を木構造にします。x86-64 では 4 段（最近は 5 段も）です。

```
仮想アドレス
┌────────┬────────┬────────┬────────┬───────────┐
│  9 bit │  9 bit │  9 bit │  9 bit │  12 bit   │
│ PML4   │  PDPT  │   PD   │   PT   │ オフセット  │
└────────┴────────┴────────┴────────┴───────────┘
```

各段の表は 512 エントリ（2⁹）× 8 バイト = ちょうど 4KB、つまり 1 ページに収まります。

変換の手順はこうです。

1. CPU のレジスタ（x86 では **CR3**）が、最上位の表の物理アドレスを持っている
2. 仮想アドレスの上位 9 ビットで、その表を引く → 次の段の表のアドレス
3. 次の 9 ビットで引く → さらに次の段
4. これを 4 回繰り返すと、目的の物理ページ番号が得られる
5. オフセットを足して物理アドレスが完成

**多段にすると何が得か。** 使われていない領域については、**途中の段のエントリを空にしておける**のです。その先の表を作る必要がありません。

小さなプロセスなら、実際に必要な表は数ページで済みます。512GB が数十 KB になりました。

<Callout type="warn" title="代償は 4 回のメモリアクセス">
  1 回のメモリアクセスのために、**変換だけで 4 回メモリを読む**ことになります。
  実際のデータを含めて 5 回。これでは実用になりません。
  だから次の記事で扱う **TLB** が必須になります。
</Callout>

## エントリの中身

各エントリには、物理ページ番号のほかにフラグが入っています。

| フラグ | 意味 |
| --- | --- |
| **P**（Present） | 物理メモリ上にあるか。0 ならページフォールト |
| **R/W** | 書き込み可能か |
| **U/S** | ユーザモードからアクセスできるか |
| **A**（Accessed） | アクセスされたか。**CPU が自動で立てる** |
| **D**（Dirty） | 書き込まれたか。**CPU が自動で立てる** |
| **NX** | 実行禁止 |

**A と D は CPU が勝手に立てます。** OS はこれを使って、

- どのページが最近使われたか（追い出す候補を選ぶため）
- どのページが変更されたか（追い出すときに書き戻す必要があるか）

を判断します。**OS が全アクセスを監視することなく、統計を得られる**仕組みです。

## ページフォールト

Present ビットが 0 のページにアクセスすると、CPU は **ページフォールト**という例外を発生させ、OS に制御を移します。

OS は原因を調べて対処します。

| 原因 | OS の対応 |
| --- | --- |
| まだ物理ページを割り当てていない | 空きページを割り当てて、エントリを埋める |
| スワップアウトされている | ディスクから読み戻す |
| ファイルをマップした領域への初回アクセス | ファイルから読み込む |
| コピーオンライトのページへの書き込み | 複製を作って書き込み可能にする |
| **本当に不正なアクセス** | **SIGSEGV を送る** |

前の 4 つは正常な動作の一部です。**ページフォールトはエラーではありません。** 最後のケースだけがエラーです。

<Callout type="tip" title="マイナーフォールトとメジャーフォールト">
  - **マイナーフォールト**：ディスクアクセスが不要。すでにメモリ上にあるページを対応づけるだけ。速い
  - **メジャーフォールト**：ディスクから読む必要がある。遅い

```bash
/usr/bin/time -v ./a.out
# Major (requiring I/O) page faults: 0
# Minor (reclaiming a frame) page faults: 1523
```
  メジャーフォールトが多いなら、メモリが足りていません。
</Callout>

## 表を切り替える

プロセスを切り替えるとき、OS は CR3 に新しいプロセスの最上位の表のアドレスを書きます。**これだけで、アドレス空間全体が入れ替わります。**

ただし、TLB に残っている古い変換結果は無効になるため、捨てる必要があります。これがプロセス切り替えのコストの大きな部分を占めます（次の記事で詳述）。

## ページを大きくする

4KB では、大きなメモリを扱うときにエントリ数が膨大になります。1GB を扱うと 26 万エントリです。TLB に入りきらず、変換のコストが支配的になります。

そこで、**ヒュージページ**（x86-64 では 2MB と 1GB）が用意されています。段を 1 つ省略し、そこで変換を終わらせる仕組みです。

| ページサイズ | 1GB あたりのエントリ数 |
| --- | --- |
| 4KB | 262,144 |
| 2MB | 512 |
| 1GB | 1 |

データベースや仮想マシンのように、大きな連続メモリを扱う用途では効果が大きく、10〜30% の性能向上が報告されることもあります。

代償は、メモリの無駄（少ししか使わなくても 2MB 確保される）と、連続した物理領域の確保が必要になることです。

```bash
cat /proc/meminfo | grep -i huge
cat /sys/kernel/mm/transparent_hugepage/enabled
```

Linux には、OS が自動的にヒュージページを使う **THP**（Transparent Huge Pages）があります。ただし、断片化した状況ではページの確保に時間がかかり、**予期しないレイテンシの急増**を招くことがあります。データベース製品が THP の無効化を推奨するのはこのためです。

## まとめ

- ページは変換の単位。標準は 4KB
- 全エントリを持つと表が巨大になるので、多段の木にする
- 使っていない領域は、途中の段を空にしておける
- 変換に 4 回のメモリアクセスが必要。TLB で埋める
- Accessed / Dirty ビットは CPU が自動で立てる。OS の判断材料になる
- ページフォールトは正常動作の一部。不正アクセスだけがエラー
- ヒュージページは大きなメモリを扱うときに効くが、副作用もある
