## 誰が答えたのか

第 57 回で、DNS の問い合わせは UDP のパケット 1 つで送り、答えもパケット 1 つで返ってくるのを見ました。TCP のような 3 ウェイハンドシェイクはありません。

ここで問題になるのは、**UDP では送信元のアドレスを偽れる**ことです。第 53 回で見たとおり、TCP は初期シーケンス番号を往復で確かめ合うので、経路の外から偽のパケットを差し込むのは難しくなります。UDP にはその手順がありません。パケットに書かれた送信元 IP は、送った本人が好きに書いた値です。

すると、フルリゾルバが権威サーバに問い合わせを送ったあと、**本物より先に、権威サーバを名乗る偽の答えが届く**ことがありえます。フルリゾルバがそれを受け入れてしまえば、偽の答えがキャッシュに入り、第 60 回で見た TTL の間、そのリゾルバを使う全員に配られます。

この回では、偽の答えを受け入れないための工夫を 2 種類見ます。**当て物を難しくする**対策と、**署名で確かめる** DNSSEC です。

## 答えを受け入れる条件

フルリゾルバは、届いた応答が自分の送った問い合わせへの答えかどうかを、次の値で照らし合わせます。

```
問い合わせ（リゾルバ → 権威）            応答（権威 → リゾルバ）として受け入れる条件
  送信元 192.0.2.53 : 50123     ──→      宛先が 192.0.2.53 : 50123 であること
  宛先   198.51.100.1 : 53                送信元が 198.51.100.1 : 53 であること
  ID     0x3a7f                           ID が 0x3a7f であること
  質問   www.example.com A                質問部が同じであること
```

経路の外にいる攻撃者は、問い合わせのパケットを見られません。宛先の権威サーバの IP とポート 53、質問の内容は推測できるので、**分からないのは ID とリゾルバ側のポート番号**だけです。

ID は 16 ビットで、とりうる値は 65,536 通りです（[RFC 1035](https://datatracker.ietf.org/doc/html/rfc1035)）。かつての実装の多くは、問い合わせの送信元ポートを固定していました。そうなると、攻撃者が当てるべきものは 16 ビットの ID だけです。RFC 5452 の言い方では、**平均 32,768 回の試行**で当たります（[RFC 5452](https://datatracker.ietf.org/doc/html/rfc5452)）。

## キャッシュポイズニング

偽の答えをキャッシュに入れる攻撃を、**キャッシュポイズニング**と呼びます。手順は競走です。

```
攻撃者 ──① www.example.com を引いて ──→ フルリゾルバ ──② 問い合わせ ──→ 権威サーバ
攻撃者 ──③ 偽の答え（ID を変えて大量に）──→ フルリゾルバ
                                          ←────── ④ 本物の答え ──────
```

攻撃者は①で自分からリゾルバに問い合わせを投げ、リゾルバが権威サーバに問い合わせる瞬間を作ります。本物の答え④が届くまでの数十ミリ秒の間に、ID を変えた偽の答えを何百通も送り込みます。1 つでも ID が合えば、リゾルバはそれを受け入れ、あとから届く本物は捨てられます。

それでも 2008 年までは、これは深刻とは見なされていませんでした。**外れたら、次の挑戦まで TTL の分だけ待たされる**からです。本物の答えがキャッシュに入ってしまえば、TTL が切れるまでリゾルバは権威サーバに問い合わせません。1 日に数回しか挑戦できないなら、65,536 分の数百を当てるのに何か月もかかります。

## Kaminsky 攻撃（2008）

2008 年、Dan Kaminsky が、この「TTL の分だけ待たされる」制約を外す方法を示しました（[CERT VU#800113](https://www.kb.cert.org/vuls/id/800113)、CVE-2008-1447）。

発想は、**毎回、存在しない別の名前を引かせる**ことです。

```
1 回目: a1.example.com を引かせる → 偽の答えを送る → 外れ
2 回目: a2.example.com を引かせる → 偽の答えを送る → 外れ
3 回目: a3.example.com を引かせる → ...
         ↑ どれもキャッシュに無いので、リゾルバは毎回すぐ権威に問い合わせる
```

名前が毎回違うので、キャッシュが挑戦を止めてくれません。攻撃者は待たずに何度でも競走に参加できます。

そして偽の答えの中身が巧妙です。`a3.example.com` の A レコードだけでなく、**「`example.com` の権威サーバは `ns.attacker.example` だ」という NS レコードとそのアドレス**を一緒に載せます。第 56 回で見た委任の情報です。これが受け入れられると、`a3` だけでなく **`example.com` 以下の全部の名前**が攻撃者の権威サーバに問い合わせられるようになります。

発表は、主要な DNS 実装の開発元が足並みをそろえて修正版を出したあとに行われました。修正の中身は、次の節の送信元ポートのランダム化です。

## 当て物の桁を増やす

ID が 16 ビットしかないなら、**照らし合わせる値を増やせばよい**。プロトコルを変えずにできる対策が 2 つ使われています。

| 対策 | 何を乱数にするか | 増える当て物 |
| --- | --- | --- |
| **送信元ポートのランダム化** | 問い合わせごとにリゾルバ側の UDP ポートを変える | 1024 未満を除く最大 64,512 通り。ID と掛け合わせて約 42 億通り（[RFC 5452](https://datatracker.ietf.org/doc/html/rfc5452)） |
| **0x20** | 質問の名前の英字を、大文字と小文字でランダムに混ぜる | 名前の英字 1 文字あたり 1 ビット |

送信元ポートのランダム化は、Kaminsky の発表に合わせて各実装に入りました。今のフルリゾルバは、問い合わせのたびに別のポートから送ります。

**0x20** は、DNS の名前比較が大文字と小文字を区別しないことを利用した工夫です（[draft-vixie-dnsext-dns0x20](https://datatracker.ietf.org/doc/html/draft-vixie-dnsext-dns0x20-00)、2008 年）。ASCII の英字は、0x20 のビットだけが大文字と小文字の違いです。`www.example.com` を `wWw.ExAMpLe.cOm` と送れば、権威サーバは質問部をそのまま写して返すので、写し方が一致しない答えは偽物だと分かります。英字 10 文字なら 10 ビット分、当て物が増えます。

<Callout type="note" title="ランダム化は確率を下げるだけ">
  どちらの対策も、偽の答えを**見分ける**のではなく、**当てにくくする**だけです。
  2020 年に発表された SAD DNS は、OS が ICMP の送信数を全体で制限していることを手がかりに、
  リゾルバが今どのポートを開けているかを外から探り当て、ポートのランダム化を実質的に無効にしました（[SAD DNS](https://www.saddns.net/)、CVE-2020-25705）。
  カーネルの修正で塞がれましたが、「乱数の桁を増やす」対策には、こうした抜け道がありえます。
</Callout>

## 署名で確かめる: DNSSEC

当て物の桁をいくら増やしても、経路の途中にいる攻撃者（パケットを見られる者）には効きません。ID もポートも見えているからです。

**DNSSEC** は、発想を変えます。答えを受け取る経路を信じるのをやめ、**答えそのものにゾーンの持ち主が署名する**。受け取った側は、誰から届いたかに関係なく、署名を検証して本物かどうかを決めます（[RFC 4033](https://datatracker.ietf.org/doc/html/rfc4033)、[RFC 4034](https://datatracker.ietf.org/doc/html/rfc4034)、[RFC 4035](https://datatracker.ietf.org/doc/html/rfc4035)）。

新しいレコードが 3 種類加わります。

| レコード | 置き場所 | 中身 |
| --- | --- | --- |
| **RRSIG** | 署名されるレコードと同じゾーン | 同じ名前・同じ型のレコードの集まり（RRset）に対する署名 |
| **DNSKEY** | ゾーンの頂点 | そのゾーンの公開鍵 |
| **DS** | **親**ゾーン | 子ゾーンの DNSKEY のハッシュ |

`example.com` の A レコードの RRSIG は、`example.com` の DNSKEY で検証できます。では、その DNSKEY が本物だとどうして言えるのか。そこで **DS** が効きます。DS は親の `.com` ゾーンに置かれ、`.com` の鍵で署名されています。**親が「子の鍵のハッシュはこれだ」と署名付きで保証する**わけです。これを上にたどると、最後はルートに行き着きます。

```
ルート（.）   DNSKEY key id 20326 ← これだけは検証する側が最初から持っている（トラストアンカー）
   │           └ 署名 → .  の DNSKEY 一式 → その中の ZSK が署名 → com の DS
   ▼
com          DS 19718 ── ハッシュが一致 ── com の DNSKEY（KSK 19718）
   │           └ 署名 → com の DNSKEY 一式 → ZSK が署名 → example.com の DS
   ▼
example.com  DS 2371  ── ハッシュが一致 ── example.com の DNSKEY（KSK 2371）
               └ 署名 → example.com の DNSKEY 一式 → ZSK 34505 が署名 → A レコード
```

図の key id は、2026 年 9 月に `dig` で実際に引いた値です。これが**信頼の連鎖**です。検証する側は、ルートの鍵 1 つだけを信じれば、そこから下のすべての署名を確かめられます。ルートゾーンは 2010 年 7 月 15 日に署名されました（[IANA](https://www.iana.org/archive/root-dnssec-launch/launch-status-updates)）。

### 鍵を 2 段に分ける理由

上の図で、各ゾーンの鍵が **KSK**（鍵署名鍵）と **ZSK**（ゾーン署名鍵）の 2 種類に分かれています。DNSKEY の flags が 257 なら KSK、256 なら ZSK として扱うのが慣例です。

- **KSK** は DNSKEY の集まりだけに署名する。親の DS が指しているのはこの鍵
- **ZSK** はゾーンの残りのレコードすべてに署名する

分ける理由は、**親との手続きを減らすため**です。DS は親のゾーンにあるので、変えるには親（`.com` ならレジストリ）に依頼が要ります。頻繁に使って頻繁に替えたい鍵は ZSK にして、KSK は長く据え置く。ZSK を替えても、KSK がそれに署名し直すだけで親に触れずに済みます。

<Callout type="tip" title="ルートの鍵も交代する">
  ルートの KSK は 2018 年 10 月 11 日から key id 20326（KSK-2017）が使われてきました。
  後継の KSK-2024（key id 38696）は 2025 年 1 月からルートゾーンに載り、
  2026 年 10 月 11 日に署名の役目を引き継ぐ計画です（[IANA](https://www.iana.org/dnssec/files)）。
  交代の前後には、`dig . DNSKEY` で flags 257 の鍵が 2 つ並ぶ期間があります。
  トラストアンカーを手で書き込んだまま更新していない検証リゾルバは、交代を境にすべての名前を引けなくなります。
</Callout>

## 無いことを証明する

署名は、**あるもの**が本物だと示せます。では「その名前は存在しない」（NXDOMAIN）という答えはどう守るのか。攻撃者が本物の名前に対して「存在しない」と偽の答えを返せば、署名が無いので検証できません。

**NSEC** は、ゾーンの名前を並べたときの**すき間**に署名します。

```
ゾーン内の名前を順に並べる:  api.example.com  <すき間>  www.example.com

NSEC: api.example.com の次は www.example.com（署名付き）
  → 「その間に名前は無い」ことの証明
  → foo.example.com を問われたら、この NSEC を返せば不在を示せる
```

すき間の両端は事前に署名しておけるので、署名の鍵を権威サーバに置かずに済みます。ただし副作用があります。NSEC を順にたどれば、**ゾーンの名前がすべて列挙できてしまう**のです。

**NSEC3** は、名前そのものではなく名前のハッシュを並べて、列挙を難しくしました（[RFC 5155](https://datatracker.ietf.org/doc/html/rfc5155)）。ハッシュを何回繰り返すかを設定できますが、繰り返しても辞書攻撃への効果は薄く、検証側の負担だけが増えるので、今は**繰り返し 0 回、ソルトなし**が推奨です（[RFC 9276](https://datatracker.ietf.org/doc/html/rfc9276)）。

最近は第 3 の方法も広まっています。応答のたびにその場で署名するサーバなら、「その名前は**存在するが、問われた型のレコードは無い**」という、ちょうどその名前だけを覆う NSEC を作れます（[RFC 9824](https://datatracker.ietf.org/doc/html/rfc9824)）。列挙のしようがなく、応答も小さくなります。`example.com` の存在しない名前を引くと、その形が見えます。

```
nosuchname-xyz.example.com. 1800 IN NSEC \000.nosuchname-xyz.example.com. RRSIG NSEC TYPE128
```

次の名前が「自分の直後」で、型の一覧にあるのは NXNAME（型番号 128）という「実は存在しない」ことを示す印だけです。

## 検証の失敗は名前解決の失敗になる

DNSSEC の検証に失敗したとき、フルリゾルバは偽の答えを返しません。**SERVFAIL（RCODE 2）を返します**（[RFC 4035 §5.5](https://datatracker.ietf.org/doc/html/rfc4035#section-5.5)）。アプリから見ると、単に「名前が引けない」です。

これは攻撃を防いだ結果であると同時に、**運用の失敗がそのまま障害になる**ということでもあります。

- 署名の有効期限が切れた（RRSIG には期限がある）
- 鍵を替えたのに、親の DS を古いまま残した
- 権威サーバが不在証明を正しく作れていなかった

2021 年 9 月、Slack は DNSSEC を有効にした際、権威 DNS がワイルドカードのある名前に対して不完全な NSEC を返していたため、一部の検証リゾルバから `slack.com` のサブドメインが引けなくなりました。慌てて DS を消しても、`.com` ゾーンの DS は TTL が 24 時間で、リゾルバにキャッシュされた古い DS がすぐには消えず、元に戻すのに時間がかかりました（[Slack Engineering](https://slack.engineering/what-happened-during-slacks-dnssec-rollout/)）。

<Callout type="warn" title="検証そのものが攻撃の的になる">
  検証リゾルバは、届いた鍵と署名の組み合わせを計算で確かめます。
  2024 年 2 月に公表された KeyTrap は、鍵と署名を大量に並べたゾーンを用意し、
  その組み合わせをすべて試させることで、**応答 1 つで検証リゾルバの CPU を長時間占有**させるものでした（[ISC](https://kb.isc.org/docs/cve-2023-50387)、CVE-2023-50387）。
  RFC 4033 自身も、DNSSEC は暗号の計算を使うぶん新しい種類のサービス妨害を招くと書いています。
</Callout>

問い合わせに **CD ビット**（Checking Disabled）を立てると、リゾルバは検証を省いて答えをそのまま返します。検証の失敗なのか、そもそも権威が応答していないのかを切り分けるのに使います。逆に、リゾルバが検証に成功した答えには **AD ビット**（Authentic Data）が立ちます（[RFC 4035 §3.2](https://datatracker.ietf.org/doc/html/rfc4035#section-3.2)）。

## 手元で確かめる

`dig` に `+dnssec` を付けると、署名も一緒に返ってきます（出力は 2026 年 9 月に `1.1.1.1` へ問い合わせたもの。値は時期によって変わります）。

```
$ dig +dnssec example.com A @1.1.1.1
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 3, AUTHORITY: 0, ADDITIONAL: 1
; EDNS: version: 0, flags: do; udp: 1232
example.com.   293 IN A     104.20.23.154
example.com.   293 IN RRSIG A 13 2 300 20260926065104 20260924045104 34505 example.com. NDfV...
```

`flags` の `ad` が「リゾルバが検証した」の印です。RRSIG の `13` はアルゴリズム（ECDSA P-256）、`20260926...` と `20260924...` は署名の有効期限と開始、`34505` は署名した鍵の key id です。

わざと署名を壊してある検証用のドメインを引くと、違いがはっきりします。

```
$ dig dnssec-failed.org A @1.1.1.1
;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL
$ dig +cd dnssec-failed.org A @1.1.1.1
;; ->>HEADER<<- opcode: QUERY, status: NOERROR
;; flags: qr rd ra cd; QUERY: 1, ANSWER: 1
```

`+cd` で検証を止めると答えが返ってきます。**権威は応答していて、検証だけが落ちている**と分かります。

`delv` は、リゾルバの判定を信じずに、手元で信頼の連鎖を検証する道具です。`+rtrace` を付けると、たどった順が見えます（macOS 付属の `delv` は暗号機能なしでビルドされていて動かないので、`docker run --rm alpine sh -c 'apk add bind-tools && delv ...'` で試しました）。

```
$ delv @1.1.1.1 +rtrace example.com A
;; fetch: example.com/A
;; fetch: example.com/DNSKEY
;; fetch: example.com/DS
;; fetch: com/DNSKEY
;; fetch: com/DS
;; fetch: ./DNSKEY
; fully validated
example.com.   300 IN A 104.20.23.154

$ delv @1.1.1.1 github.com A
; unsigned answer

$ delv @1.1.1.1 dnssec-failed.org A
;; resolution failed: failure
```

`example.com` から上へ、DNSKEY と DS を交互にたどってルートの鍵に着いています。`github.com` のように署名していないゾーンは `unsigned answer` です。DNSSEC は、署名したゾーンしか守れません。

## DNSSEC が守らないもの

DNSSEC が保証するのは、**答えが改ざんされていないこと**と、**ゾーンの持ち主が出したものであること**だけです。

- **盗み見は防がない。** 問い合わせも答えも平文のままです。RFC 4033 は「意図的な設計の選択として、DNSSEC は機密性を提供しない」と明記しています（[RFC 4033](https://datatracker.ietf.org/doc/html/rfc4033)）
- **手元とリゾルバの間は守らない。** 検証するのはたいていフルリゾルバで、スタブリゾルバは AD ビットを信じるだけです。その AD ビット自体は、平文の UDP で届きます
- **サービス妨害は防がない。** むしろ検証の失敗や計算の負荷が、新しい止まり方を増やします

## まとめ

- UDP は送信元を偽れる。フルリゾルバは宛先ポートと 16 ビットの ID と質問部で応答を照らし合わせるが、ポートが固定なら当て物は 16 ビットしかない
- キャッシュポイズニングは、本物より先に偽の答えを届ける競走。かつては外れると TTL の分だけ待たされた
- Kaminsky 攻撃（2008）は、存在しない名前を毎回引かせて待ち時間を消し、NS レコードでゾーンごと乗っ取った
- 送信元ポートのランダム化と 0x20 は、当て物の桁を増やす。偽物を見分けるわけではない
- DNSSEC は答えに署名する。RRSIG を DNSKEY で、DNSKEY を親の DS で確かめ、ルートのトラストアンカーまでつなぐ
- KSK と ZSK に分けるのは、親の DS に触れずに鍵を替えるため。ルートの KSK は 2026 年 10 月 11 日に替わる予定
- 不在は NSEC / NSEC3 / その場で作る NSEC で証明する。NSEC はゾーンの列挙を許す
- 検証に失敗すると SERVFAIL になる。運用の失敗がそのまま名前解決の障害になる
