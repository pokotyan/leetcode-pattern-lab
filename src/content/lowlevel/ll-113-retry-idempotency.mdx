## この章で見るもの

ここまでの章は、ほとんどの場面で「1 つの要求が、1 回、相手に届く」ことを前提にしてきました。実際のネットワークはそうではありません。接続は途中で切れ、相手のプロセスは落ち、応答は戻る途中で失われます。そして送り手が送り直せば、**同じ要求が二度届きます**。

この章では、そうした失敗の上で**仕事を一度だけ、確実に渡す**ための部品を順に見ます。

| 回 | 部品 | 解いている問題 |
| --- | --- | --- |
| 第 113 回（この回） | リトライ、冪等性キー、期限 | 結果の分からない要求を、送り直してよいか |

## タイムアウトした要求は、届いたのか

クライアントが `POST /charges` を送り、1 秒待っても応答が来なかったとします。このとき、サーバの側では次のどれかが起きています。

| | 何が起きたか | サーバの状態 | クライアントから見えるもの |
| --- | --- | --- | --- |
| 1 | **送れなかった**。接続が張れない、要求が出ていない | 変わっていない | `ECONNREFUSED`、名前が引けない、接続のタイムアウト |
| 2 | **届いたが、処理されなかった**。処理の前に落ちた、断られた | 変わっていない | 接続が切れた（FIN / RST）、または応答が来ない |
| 3 | **処理されたが、応答が消えた**。処理の後に落ちた、応答が途中で失われた | **変わった** | 接続が切れた（FIN / RST）、または応答が来ない |

1 は、まだ何も始まっていないので、送り直して構いません。第 66 回で見たとおり、誰も待ち受けていないポートへの SYN には RST が返り、クライアントは `connect` の段階で `ECONNREFUSED` を受け取ります。要求のバイトは 1 つも出ていません。

問題は 2 と 3 です。要求を書き終えたあとに接続が切れた、あるいは応答が来ないままタイムアウトした、という観測は、**2 と 3 のどちらでも同じ**です。RST は「この接続はもう無い」と言っているだけで、要求を処理したかどうかは何も言いません。タイムアウトに至っては、相手が処理中なのか、落ちたのか、応答がネットワークのどこかで止まっているのか（第 67 回の再送が続いているのか）すら分かりません。第 84 回で見た gRPC の `DEADLINE_EXCEEDED` に「状態を変える操作では、成功していてもこのコードが返りうる」という注意書きがあったのは、この事情によります。

後の実験で、処理前に切る、処理後に FIN で切る、処理後に RST で切る、処理後に黙る、の 4 通りのサーバを作り、クライアントに何が見えるかを並べます。**処理前に切ったときと処理後に切ったときで、クライアントが受け取る例外はまったく同じ**です。

結果が分からない要求に対して、クライアントにできることは 3 つしかありません。

- 送り直さずに失敗として扱う。3 だった場合、相手の状態と食い違う
- 送り直す。3 だった場合、**同じ仕事が二度行われる**
- 送り直しても二度行われないように、要求と受け手の側を作っておく

この回は、3 つ目をどう作るかの話です。

## HTTP の約束: 安全なメソッドと冪等なメソッド

HTTP は、メソッドごとに「送り直してよいか」の手がかりを決めています（[RFC 9110 9.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2)）。

**安全**（safe）なメソッドは、定義上ほぼ読み取り専用で、クライアントがサーバの状態の変更を求めないものです。`GET`、`HEAD`、`OPTIONS`、`TRACE` が安全です。アクセスログを書くような副作用があっても、クライアントが求めたものではないので安全と見なされます。

**冪等**（idempotent）なメソッドは、「同じ要求を何回送っても、サーバに意図された効果が 1 回送ったときと同じ」ものです。安全なメソッドに加えて、`PUT` と `DELETE` が冪等です（[RFC 9110 9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)）。`PUT /users/42` は「42 番をこの内容にせよ」なので、2 回当てても結果は同じです。`DELETE` も、2 回目は消すものが無いだけです（応答のステータスは変わりえますが、効果は同じです）。

`POST` と `PATCH` は冪等ではありません。`POST /charges` は「新しい課金を 1 つ作れ」という意味で、2 回送れば 2 つ作るのが正しい解釈だからです。

RFC 9110 は、この区別をそのまま自動の再送の条件にしています。

> Idempotent methods are distinguished because the request can be repeated automatically if a communication failure occurs before the client is able to read the server's response.

そして、冪等でないメソッドについては次のように書いています（同上）。

- クライアントは、冪等でないメソッドの要求を自動で再送すべきでない（SHOULD NOT）。例外は、メソッドにかかわらず要求の意味が実際には冪等だと知る手段があるか、元の要求が適用されなかったことを検出する手段がある場合
- ただし「もっと危うい方法を取るクライアントもある」として、応答の一部も受け取る前に下の接続が閉じた場合、**とくにアイドルだった持続的接続を使った場合**に `POST` を自動で再送する例を挙げている
- **プロキシは、冪等でない要求を自動で再送してはならない**（MUST NOT）
- 自動で再送したものが失敗したら、それをさらに自動で再送すべきでない

アイドルな持続的接続がわざわざ挙がっているのは、そこが典型的な落とし穴だからです。HTTP/1.1 のクライアントは接続を使い回しますが、サーバはアイドルな接続をいつでも閉じられます。クライアントがちょうど要求を書いた瞬間に、サーバ側のアイドルタイムアウトが来て接続が閉じられることがあります。この場合、サーバは要求を読んでいない可能性が高いのですが、**クライアントからは「書いた直後に切られた」としか見えません**。HTTP/1.1 の仕様（[RFC 9112 9.3.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3.1)）も、接続はいつ閉じられてもおかしくないので回復を考えておけ、と書いたうえで、再送の条件は RFC 9110 の 9.2.2 に委ねています。

### Go の net/http は何を見て再送しているか

実際のクライアントがこの約束をどう実装しているかを、Go の標準ライブラリで見てみます。`Transport` が再送を判断する関数は、おおむね次の順に条件を見ています（[transport.go の shouldRetryRequest](https://github.com/golang/go/blob/master/src/net/http/transport.go)）。

1. **新しく張った接続での失敗は再送しない。** 新しい接続でいきなり切られたなら、サーバが要求を嫌っている可能性があり、再送すると無限に繰り返しかねない
2. **使い回した接続で、何も書かずに失敗したなら再送する。** 本体を巻き戻せる場合に限る
3. **要求が再送できる（replayable）ものでなければ再送しない**
4. 再送できるものなら、最初の応答バイトを読む段階での失敗や、サーバがアイドルな接続を閉じたことによる失敗を再送する

3 の判定（[request.go の isReplayable](https://github.com/golang/go/blob/master/src/net/http/request.go)）は、本体が無いか巻き戻せる要求について、メソッドが `GET`、`HEAD`、`OPTIONS`、`TRACE`（執筆時点の master では `QUERY` も）のどれかなら真です。そしてもう 1 つ、**要求に `Idempotency-Key` か `X-Idempotency-Key` のヘッダが付いていれば、`POST` でも真**になります。ソースのコメントは、このヘッダは標準ではないが、`POST` などが冪等であることを示すのに広く使われている、と書いています。次の節の冪等性キーは、ライブラリの再送の判断にまで入り込んでいるわけです。

### HTTP/2 は「処理していない」を言える

HTTP/1.1 では、切れた要求が処理されたかどうかをクライアントが知る手段はありません。HTTP/2 は、これを言うための仕組みを 2 つ持っています（[RFC 9113 8.7](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.7)）。

- **GOAWAY** フレームは、処理したかもしれないストリームの最大の番号を伝える。それより大きい番号のストリームの要求は、安全に再送できる
- **RST_STREAM** に `REFUSED_STREAM` のエラーコードを付けると、そのストリームを何も処理せずに閉じたことを伝えられる

RFC 9113 は、処理されていない要求は失敗していないので、**冪等でないメソッドでも自動で再送してよい**と書いています。その代わりサーバは、保証できない限り「処理していない」と伝えてはなりません。第 86 回で見た gRPC の透過的な再試行は、この 2 つを使って、サーバのアプリが見ていないことが確実な要求だけを送り直す仕組みでした。

つまり、表の 1 と 2 の一部は、プロトコルが「送り直して安全」と教えてくれます。残るのは、**届いたかもしれない、処理されたかもしれない**要求です。

## 冪等性キー: 送り直しに名前を付ける

`POST /charges` を冪等にする方法は、要求そのものに**一意な名前**を付けることです。クライアントは操作ごとに一意なキーを作り、送り直すときには同じキーを付けます。サーバはキーごとに「処理したか、どう応えたか」を覚えておき、同じキーが来たら、処理し直さずに前回の応答を返します。

これをヘッダとして標準にしようとしているのが、IETF の httpapi ワーキンググループの「The Idempotency-Key HTTP Header Field」です。執筆時点の最新は 2026 年 10 月 22 日付けの第 08 版で、まだ RFC になっていないインターネットドラフトです（[datatracker](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)）。以下はこの第 08 版の内容です（[draft-ietf-httpapi-idempotency-key-header-08](https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-08.html)）。

ヘッダは構造化フィールド（Structured Field）の Item で、値は String です。つまり**二重引用符で囲む**形になります。手元で、ヘッダを付けた `POST` を生のソケットで受けると、線の上にはこう流れていました。

```
POST /charges HTTP/1.1
Host: 127.0.0.1:8010
Accept-Encoding: identity
Content-Length: 27
Content-Type: application/json
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"

{"order": 7, "amount": 100}
```

ドラフトは、キーに UUID のような乱数の識別子を使うことを推奨し、キーは一意でなければならず、**中身の違う別の要求に使い回してはならない**としています。キーと一緒に、要求の本体のチェックサムなどの**フィンガープリント**を使って、同じ要求かどうかを判定してもよい、とも書いています。なお、Stripe の API は同じ名前のヘッダを引用符なしの値で受け付けています（[Stripe: Idempotent requests](https://docs.stripe.com/api/idempotent_requests)）。ドラフトより前から使われてきた形です。

### サーバが区別する状況

キーを受け取ったサーバが区別しなければならない状況は、次のとおりです。応答のコードはドラフトの第 08 版によるものです。

| 状況 | サーバの応答 |
| --- | --- |
| キーが必要な操作なのに、キーが無い | `400`（説明の文書へのリンクを付ける） |
| 初めて見るキー | 処理して、キーと応答を保存する |
| 処理を終えたキーが、同じ中身で来た | **処理せず、保存した応答を返す** |
| 処理を終えたキーが、**違う中身**で来た | `422`（キーの使い回し） |
| **処理中の**キーが来た | `409`（競合） |
| 保存期間を過ぎたキーが来た | 新しい要求として処理される |

保存期間についてドラフトは、期限を定めるなら文書で公開すべきだ、とだけ書いています。

Stripe の文書は、実際の運用での細部を書いています（[Stripe: Idempotent requests](https://docs.stripe.com/api/idempotent_requests)）。API v1 では、

- 保存するのは、エンドポイントの**実行が始まったあと**の、最初の要求のステータスコードと本体。**`500` のエラーも保存され**、同じキーの再送には同じ `500` が返る
- 入力の検証で失敗した要求や、同じキーで並行して実行中の要求と競合した要求は、実行が始まっていないので保存しない。これらは送り直してよい
- キーは最長 255 文字。少なくとも 24 時間たったキーは消されうる。消されたあとに同じキーが来れば、新しい要求として扱う
- 受け取った引数を最初の要求と比べ、違えばエラーにする
- `GET` と `DELETE` には意味がないので付けない。定義上冪等だから

`500` まで保存するのは、`500` を返すまでの間に何が書かれたか分からないからです。処理し直すと、半分書いたものの上にもう一度書くことになりかねません。

### キーはどこに保存するか

冪等性キーの記録を本体の更新と同じトランザクションに入れること、存在確認ではなく一意制約で競合を防ぐこと、保存期間を決めること。この 3 点は、システムデザインの読み物の<a href={`${import.meta.env.BASE_URL}reading/messaging/`}>メッセージングの現実</a>で扱いました。ここでは、それを PostgreSQL の上に実際に置いたとき、**並行に同じキーが来た瞬間に何が起きるのか**を、第 99 回と第 100 回の部品で見ます。

表は 2 つです。

```sql
CREATE TABLE idempotency_keys (
  key           text PRIMARY KEY,        -- 一意制約が、同時に来た 2 本の片方を止める
  request_hash  bytea NOT NULL,          -- 本体の SHA-256。違えば 422
  state         text NOT NULL CHECK (state IN ('processing','done')),
  response_code int,
  response_body text,
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE charges (id bigserial PRIMARY KEY, order_no int, amount int);
```

置き方は 2 通りあります。

**置き方 A: 1 つのトランザクションに全部入れる。**

```
BEGIN;
  INSERT INTO idempotency_keys (key, request_hash, state)
       VALUES ($1, $2, 'processing')
  ON CONFLICT (key) DO NOTHING RETURNING key;
  -- 1 行返った → 初めてのキー。本体を処理する
  INSERT INTO charges ...;
  UPDATE idempotency_keys SET state = 'done', response_code = 201, response_body = ... ;
  -- 返らなかった → 既存のキー。SELECT して 422 / 保存した応答を返す
COMMIT;
```

キーの行と `charges` の行は、第 99 回の WAL の 1 つのコミットで同時に見えるようになるか、どちらも見えないかのどちらかです。処理の途中でプロセスが落ちても、キーだけが残ることはありません。

では、同じキーの要求が 2 本、ほぼ同時に来たらどうなるか。1 本目の `INSERT` はまだコミットされていないので、2 本目からはキーの行が見えません。ところが PostgreSQL は、一意インデックスに同じ値を入れようとした 2 本目を、**1 本目のトランザクションの結末が決まるまで待たせます**。1 本目がコミットすれば、2 本目の `ON CONFLICT DO NOTHING` は何も挿入せずに返り、続く `SELECT` で 1 本目が保存した応答を読めます。1 本目がロールバックすれば、2 本目の挿入が通ります。実験では、待っている 2 本目のバックエンドの待ち事象が `Lock / transactionid`、つまり**相手のトランザクション ID に対するロック待ち**として見えました。第 100 回で見た「行ロックは行そのものに書く」PostgreSQL が、一意性の確認でも相手のトランザクションの終わりを待つ形です。

この置き方では、`state = 'processing'` が他のトランザクションから見えることはありません。`409` を返す場面がなく、後から来た方は待たされて、最初の応答を受け取ります。

**置き方 B: 「処理中」を先にコミットする。**

置き方 A が使えるのは、処理がすべて同じデータベースの中で終わる場合だけです。カード会社の決済 API を呼ぶ、メールを送る、といった**外部への副作用**は、トランザクションをロールバックしても取り消せません。そうした処理を長いトランザクションの中で行えば、外部 API の応答を待つ間ずっとロックと接続を握ることにもなります。

そこで、キーの行を `processing` で挿入して**先にコミット**し、外部の処理を行い、最後に結果を書くトランザクションを別に開きます。今度は `processing` が他の要求から見えるので、同じキーで来た 2 本目には、待たせずに `409` を返せます。

代わりに、新しい失敗の形が生まれます。外部の処理の途中でプロセスが落ちると、**キーは `processing` のまま残り**、そのキーの再送は永遠に `409` になります。Stripe 風の冪等性キーを PostgreSQL で実装する方法を詳しく書いた brandur の記事（[Implementing Stripe-like Idempotency Keys in Postgres](https://brandur.org/idempotency-keys)）は、キーの行に `locked_at`（いつから処理中か）と `recovery_point`（どの段階まで終えたか）を持たせ、ロックが一定時間を過ぎたら別の要求が引き継げるようにし、途中で止まった要求を最後まで進める completer と、古いキーを消す reaper という裏方のプロセスを置く設計を示しています。同じ記事は、保存期間として 72 時間程度を勧めています。週末をまたいでも、修正をデプロイして再処理する余裕を残すためです。

| | 置き方 A（1 トランザクション） | 置き方 B（処理中を先にコミット） |
| --- | --- | --- |
| 使える処理 | 同じデータベースの中で完結するもの | 外部への副作用を含むもの |
| 同じキーが並行に来たとき | 2 本目は一意インデックスで待たされ、最初の応答を受け取る | 2 本目はすぐ `409` |
| 途中で落ちたとき | 全部ロールバック。キーも残らない | キーが `processing` で残る。引き継ぎの仕組みが要る |
| ロックを握る時間 | 処理の間ずっと | 短いトランザクション 2 回分 |

<Callout type="warn" title="キーを別のストアに置くと、どちらの置き方も崩れる">
  キーを Redis に、本体を PostgreSQL に置くと、「本体は書けたがキーは書けなかった」「キーは書けたが本体は書けなかった」の両方が起こりえます。
  置き方 A の原子性は、キーと本体が**同じ WAL の同じコミット**に乗ることに頼っています。
  外部 API のように同じトランザクションに入れられない相手には、その相手自身の冪等性キーを渡すのが基本です。
  決済 API に自分の注文 ID から作ったキーを付けて呼べば、置き方 B で途中から再開したときに同じ課金をもう一度呼んでも、相手の側で 1 回にまとめられます。
</Callout>

## 待ち方: 指数バックオフとジッター

送り直してよいことが分かったとして、次は**いつ**送り直すかです。失敗の原因が相手の過負荷なら、すぐに送り直すのは火に油を注ぐことになります。そこで、試すたびに待ち時間を倍々に伸ばします。これが **指数バックオフ** です。

指数バックオフだけでは、まだ問題が残ります。相手が一瞬止まり、100 台のクライアントが**同じ瞬間に**失敗したとします。全員が同じ規則で待てば、全員が 1 秒後、3 秒後、7 秒後に、**そろって**送り直します。待ち時間をいくら伸ばしても、山の高さは 100 のままです。そこで、待ち時間に乱数を混ぜて、送り直す時刻をばらします。これが **ジッター** です。

AWS の Marc Brooker の記事（[Exponential Backoff And Jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/)、2015 年）は、ジッターの付け方を 3 つ比べています。式は、記事が公開しているシミュレータのソース（[aws-arch-backoff-simulator](https://github.com/awslabs/aws-arch-backoff-simulator/blob/master/src/backoff_simulator.py)）から取りました。`n` は何回目の再試行か、`v = min(cap, base × 2^n)` は指数バックオフの待ち時間です。

| 方式 | n 回目の待ち時間 | 特徴 |
| --- | --- | --- |
| ジッターなし | `v` | 全員が同じ時刻に送り直す |
| Full Jitter | `uniform(0, v)` | 0 から `v` までのどこか。ばらつきは最大 |
| Equal Jitter | `v/2 + uniform(0, v/2)` | 半分は必ず待ち、残り半分をばらす |
| Decorrelated Jitter | `min(cap, uniform(base, 前回の待ち × 3))` | 前回の待ち時間から次を決める |

記事は 100 台のクライアントが競合する場面で比べ、ジッターなしを「明らかな負け」、ジッターを付けた中では Equal Jitter を負けとし、Full Jitter と Decorrelated Jitter の優劣ははっきりしない（Full Jitter は仕事が少なく、時間はやや長い）と結論しています。そして、ジッター付きのバックオフは実装の手間に対する見返りが非常に大きい、と書いています。後の実験で、同じ式を使って到着の山を数えます。

AWS の Builders' Library の記事（[Timeouts, retries, and backoff with jitter](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)）は、ジッターは再試行だけのものではないとして、タイマー、定期ジョブ、その他の遅らせて行う仕事のすべてにジッターを足すことを検討する、と書いています。毎時 0 分に全台が走る cron も、同じ山を作るからです。第 86 回で見た gRPC の `retryPolicy` も、待ち時間に 0.8〜1.2 倍の揺らぎを掛けていました。

## 再試行は段の数だけ掛け算になる

1 つのクライアントと 1 つのサーバなら、再試行の上限を 3 回にすれば、最悪でも負荷は 3 倍です。呼び出しが何段にも重なると、話が変わります。

```
 利用者 ──→ A ──→ B ──→ C（詰まっている）
 3 回試す   3 回試す  3 回試す
```

C が失敗を返すと、B は C を 3 回呼びます。B の失敗を見た A は B を 3 回呼び、そのたびに B は C を 3 回呼びます。利用者も A を 3 回呼びます。**C には、元の 1 回が 3 × 3 × 3 = 27 回になって届きます**。第 227 回のサービスメッシュの回で改めて扱う**リトライストーム**です。上の図の「3 回試す」が「1 回目のあとに 3 回再試行する」なら、4 × 4 × 4 = 64 回です。AWS の記事は 5 段のスタックで各段が独立に再試行すれば、データベースへの負荷は 243 倍（3 の 5 乗）になり、回復の見込みはほぼ無くなる、と書いています（[AWS Builders' Library](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)）。

この掛け算を止める手は、大きく 3 つあります。

**再試行する段を 1 か所にする。** AWS の記事は、スタックの 1 か所でだけ再試行するのを推奨しています。Google の SRE 本（[Handling Overload](https://sre.google/sre-book/handling-overload/)）は、**要求を断った層の直上の層でだけ**再試行すべきだとし、それより上へは「過負荷なので再試行するな」という種類のエラーを返して、組み合わせ的な再試行の爆発を避ける、と書いています。第 84 回で、下流の `UNAVAILABLE` をそのまま上流に返すと掛け算になる、と書いたのと同じ考え方です。

**再試行に予算を付ける。** SRE 本は、要求ごとの上限（最大 3 回の試行）に加えて、**クライアントごとの予算**を置いています。要求全体に占める再試行の割合を数え、それが 10% を下回っている間だけ再試行します（同上）。相手が全面的に落ちたとき、負荷は 3 倍近くまで膨らむ代わりに、約 1.1 倍に収まります。同じ本の別の章（[Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/)）は、プロセス全体で 1 分あたり 60 回まで、のようなサーバ全体の再試行の予算も挙げています。

**トークンバケットで絞る。** AWS の記事は、ローカルのトークンバケットで再試行を制限し、トークンがある間はすべての呼び出しが再試行でき、尽きたら一定の速さでしか再試行しない、という方式を紹介しています。第 86 回で見た gRPC の `retryThrottling` も同じ形で、失敗で 1 減り、成功で `tokenRatio` 増え、半分を切ったら再試行をやめます。

それでも相手が失敗し続けるなら、呼ぶこと自体をしばらくやめるのが Circuit Breaker です。その状態遷移は、<a href={`${import.meta.env.BASE_URL}reading/messaging/`}>メッセージングの現実</a>で扱いました。

## 期限を下流へ渡す

掛け算の問題には、もう 1 つの顔があります。利用者が 1 秒で諦めたあとも、下流の仕事は続いているかもしれないのです。

各段が「下流への呼び出しは 1 秒でタイムアウト、3 回まで試す」と**独立に**決めているとします。A が B を呼び、B が C を 1 秒待ってタイムアウトし、もう一度 C を呼ぶ。その間に A も B を待ちきれずにタイムアウトし、B をもう一度呼ぶ。最初の B はそれを知らず、まだ C を呼び続けています。利用者はとっくに画面を閉じているのに、C には**誰も待っていない仕事**が積まれていきます。

これを防ぐのが **期限の伝播** です。SRE 本は、下流を呼ぶときに期限を新しく作るのではなく、上流から受け取った期限を引き継ぐべきだとし、期限を過ぎた要求の処理に資源を使うのは無駄であること、取り消しの伝播も同じく無駄な仕事を減らすことを書いています（[Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/)）。

期限を線の上で運ぶ形は、gRPC が具体的に決めています（[gRPC over HTTP2](https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md)）。

```
grpc-timeout = TimeoutValue TimeoutUnit
  TimeoutValue: 最大 8 桁の正の整数（ASCII）
  TimeoutUnit : H（時） M（分） S（秒） m（ミリ秒） u（マイクロ秒） n（ナノ秒）

例: grpc-timeout: 1S
    grpc-timeout: 850m
```

ヘッダが無ければ、サーバは無限の期限と見なします。運ぶのが**時刻ではなく残り時間**であることに意味があります。2 台のサーバの時計が合っている保証はないので、gRPC は期限を、すでに経過した時間を差し引いた残り時間に直して送ります（[gRPC: Deadlines](https://grpc.io/docs/guides/deadlines/)）。受けた側は、受け取った時刻に残り時間を足して自分の時計での期限を作り、下流を呼ぶときはそこからまた残り時間を計算して渡します。言語ごとに伝播が既定かどうかが違うことは、第 86 回で見ました。

同じ文書は、期限が切れるとサーバ側の呼び出しは自動で取り消されるが、アプリが始めた長い処理は、**呼び出しが取り消されたかを定期的に確かめて、自分で止める**必要がある、と書いています。期限は、呼び出し元が諦める時刻であると同時に、受け手が仕事を捨ててよい時刻でもあります。

HTTP には、残り時間を運ぶ標準のヘッダはありません。HTTP の上で同じことをするなら、gRPC と同じ考え方（残り時間を渡す、各段で差し引く、切れたら下流を呼ばない、仕事を止める）で、自分たちのヘッダを決めることになります。後の実験ではそうしています。

<Callout type="tip" title="タイムアウトの値は、どこから決めるか">
  AWS の記事は、タイムアウトを決める手順として、まず許容できる「誤ったタイムアウト」の割合（たとえば 0.1%）を決め、
  下流のサービスの遅延のうちそれに対応するパーセンタイル（この例では p99.9）を見る、という方法を書いています
  （[AWS Builders' Library](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter)）。
  平均値から決めると、裾の遅い要求のかなりの部分が「失敗」になり、それが再試行を呼んで負荷を増やします。
  パーセンタイルをどう集めるかは第 236 回で扱います。
</Callout>

## 手元で確かめる

### 実験の環境

ホストは Apple Silicon の macOS で、コンテナは aarch64 で動いています。サーバもクライアントも Python の標準ライブラリ（`http.server` の `ThreadingHTTPServer` と `http.client`）で書きました。

| 役割 | イメージ | 版 |
| --- | --- | --- |
| データベース | `postgres:17` | 17.11 |
| サーバとクライアント（PostgreSQL の接続は psycopg） | `python:3.13-alpine` | Python 3.13、psycopg 3.3.6 |
| Docker | Docker Engine | 29.4.0 |

Python のコンテナは `--network container:ll-113-pg` で PostgreSQL と同じネットワーク名前空間に入れ、`127.0.0.1` で互いに話しています。ホストへのポートの公開はしていません。

### 失敗の見え方

クライアントは `timeout=1.0` で `POST` を送ります。サーバは、パスによって振る舞いを変えます。「処理した」は、サーバが要求を記録したかどうかです。

```
誰も待ち受けていない   | ConnectionRefusedError: [Errno 111] Connection refused              | 0.00s | サーバが処理した数 0
処理せず FIN で閉じる  | RemoteDisconnected: Remote end closed connection without response | 0.00s | サーバが処理した数 0
処理後に FIN で閉じる  | RemoteDisconnected: Remote end closed connection without response | 0.00s | サーバが処理した数 1
処理後に RST で閉じる  | ConnectionResetError: [Errno 104] Connection reset by peer        | 0.00s | サーバが処理した数 1
処理後 3 秒黙る        | TimeoutError: timed out                                           | 1.00s | サーバが処理した数 1
```

RST は、閉じる前に `SO_LINGER` を 0 秒に設定して作りました。1 行目だけが、要求のバイトを送る前の失敗です。2 行目と 3 行目は、**クライアントから見るとまったく同じ例外**ですが、サーバの状態は違います。最初の表の 2 と 3 を、クライアントが区別できないことの実物です。

### 素朴な再試行で、二重に処理される

サーバを「3 回に 1 回、処理したあとで応答を返さずに FIN で接続を閉じる」ようにし、クライアントは 30 件の注文を、失敗したら最大 3 回まで送り直します。冪等性キーは付けません。

```
注文 30 件 / 送信 45 回 / 成功応答 30 / サーバが処理した数 45 / 重複した注文 15
```

クライアントから見ると、30 件すべてが成功しています。サーバでは 45 件が処理され、15 件の注文が二重になりました。**再試行は、クライアントの見かけの成功率を上げる代わりに、相手の状態を壊しています。**

### 冪等性キーを PostgreSQL に置く

同じサーバに、前の節の置き方 A（1 つのトランザクション）で冪等性キーを入れました。クライアントは注文ごとに UUID を作り、送り直すときは同じキーを付けます。応答を落とすのは、キーと本体をコミットしたあとです。

```
[one-tx] 注文 30 件 / 送信 45 回 / 成功応答 30 / charges の行 30 / キーの行 30
```

送信は 45 回のままですが、`charges` は 30 行で、重複はありません（`GROUP BY order_no HAVING count(*) > 1` は 0 行）。キーの表には、送り直しに返す応答がそのまま入っています。

```
   key    |   hash   | state | response_code |  response_body   | created_at
----------+----------+-------+---------------+------------------+------------
 264d1841 | b35aca4d | done  |           201 | {"charge_id": 2} | 10:44:21
 8efa9c8b | 985ce771 | done  |           201 | {"charge_id": 3} | 10:44:21
 c0d0a609 | 1567ee1e | done  |           201 | {"charge_id": 1} | 10:44:21
```

同じキーで、同じ本体を 2 回、続けて金額だけ変えた本体を 1 回送りました。

```
(201, '{"charge_id": 1}')
(201, '{"charge_id": 1}')                                  ← 処理せず、保存した応答を返した
(422, '{"error":"key reused with different payload"}')     ← 本体の SHA-256 が違う
```

### 同じキーを並行に 2 本送る

本体の処理に 1 秒かかるようにし、同じキーの要求を 0.2 秒ずらして 2 本送りました。0.5 秒の時点で、別の接続から `pg_stat_activity` とキーの行を見ています。

置き方 A（1 つのトランザクション）:

```
[one-tx] 0.5 秒時点: 別の接続から見たキーの状態 = None
  待っているバックエンド: (127, 'Lock', 'transactionid', 'INSERT INTO idempotency_keys(key, reques')
  A: HTTP 201 {"charge_id": 1} (1.01s)
  B: HTTP 201 {"charge_id": 1} (1.02s)
  charges の行 1
```

1 本目のキーの行はコミット前なので、別の接続からは見えません（`None`）。2 本目の `INSERT` は、1 本目のトランザクション ID に対するロックを待っています。1 本目が 1.01 秒でコミットすると、2 本目は直後に同じ応答を受け取りました。

置き方 B（処理中を先にコミット）:

```
[two-step] 0.5 秒時点: 別の接続から見たキーの状態 = ('processing',)
  A: HTTP 201 {"charge_id": 1} (1.01s)
  B: HTTP 409 {"error":"request with this key is in progress"} (0.2s)
  charges の行 1
```

`processing` が見えているので、2 本目は待たずに `409` を受け取りました。どちらの置き方でも、`charges` は 1 行です。違うのは、2 本目のクライアントが**待たされて答えを得る**か、**すぐ断られて、あとで送り直す**かです。

### 100 台が同時に失敗したとき、いつ送り直すか

前の節の 4 つの方式で、100 台のクライアントが時刻 0 に同時に失敗し、それぞれ 6 回再試行する時刻をシミュレーションしました。相手は落ちたままで、再試行はすべて失敗します。`base` は 1 秒、`cap` は 32 秒、乱数の種は 1 です。表は 1 秒ごとの到着数（再試行の数）です。

| 秒 | ジッターなし | Full | Equal | Decorrelated |
| --- | --- | --- | --- | --- |
| 0〜1 | 0 | 124 | 100 | 0 |
| 1〜2 | **100** | 70 | 22 | 45 |
| 2〜3 | 0 | 48 | 78 | 58 |
| 3〜4 | **100** | 29 | 2 | 20 |
| 4〜5 | 0 | 33 | 34 | 28 |
| 5〜6 | 0 | 23 | 46 | 25 |
| 6〜7 | 0 | 21 | 18 | 26 |
| 7〜8 | **100** | 17 | 0 | 30 |
| 8〜9 | 0 | 18 | 6 | 18 |
| 9〜10 | 0 | 22 | 14 | 20 |
| 10〜15 | 0 | 51 | 80 | 80 |
| 15〜16 | **100** | 10 | 0 | 12 |
| 16〜31 | 0 | 84 | 100 | 108 |
| 31〜32 | **100** | 6 | 0 | 4 |
| 1 秒あたりの最大 | 100 | 124 | 100 | 58 |
| **100 ミリ秒あたりの最大** | **100** | 22 | 25 | 12 |
| 最後の到着（秒） | 63 | 52 | 57 | 117 |

1 秒ごとに数えると、Full Jitter の最初の 1 秒（124）はジッターなしより高く見えます。Full Jitter の 1 回目の待ちは 0〜1 秒の一様分布なので、最初の再試行と、一部の 2 回目がそこに入るからです。しかし、ジッターなしの 100 は**同じ瞬間の** 100 です。100 ミリ秒の幅で数えると、ジッターなしは 100 のまま、Full は 22、Decorrelated は 12 まで下がります。Decorrelated は前回の待ちの 3 倍までを上限にするので、`cap` に張り付いた後も長く散らばり、最後の到着が 117 秒まで延びています。

次に、相手が 100 ミリ秒に 2 件（毎秒 20 件）まで捌けるとして、100 台が全員成功するまでを数えました。容量を超えた要求は失敗し、同じ規則で送り直します。種を 1〜20 に変えた 20 回の平均です。

| 方式 | 呼び出しの総数 | 全員が終わる時刻 |
| --- | --- | --- |
| ジッターなし | 2550 回 | 1439.0 秒 |
| Full Jitter | 354 回 | 13.9 秒 |
| Equal Jitter | 369 回 | 19.5 秒 |
| Decorrelated Jitter | 268 回 | 15.3 秒 |

ジッターなしでは、毎回 100 台がそろって同じ 100 ミリ秒に来るので、そのたびに 2 台しか通りません。待ちが `cap` の 32 秒に張り付いてからは、32 秒ごとに 2 台ずつしか減らず、全員が終わるまで 24 分かかりました。ジッターを付けると、同じ容量の相手に対して 15 秒前後で終わります。ここでも Full と Decorrelated の優劣は、何を重く見るか（時間か、呼び出しの数か）で入れ替わり、Brooker の記事の結論と同じ傾向でした。容量の数え方を 100 ミリ秒の枠にした単純なモデルなので、数値そのものより、桁の違いを見てください。

### 3 段の再試行を数える

`利用者 → A → B → C` の 3 段の HTTP サーバを 1 つのプロセスの中に立て、C は常に `503` を返すようにしました。各段は `5xx` かタイムアウトのとき、決めた回数まで試します。

```
リトライなし: 利用者の要求 1 件 → C に届いた 1 回（1.00 倍）
2 段（A, B）が 3 回ずつ試す: 利用者の要求 1 件 → C に届いた 9 回（9.00 倍）
3 段（利用者, A, B）が 3 回ずつ試す: 利用者の要求 1 件 → C に届いた 27 回（27.00 倍）
3 段が 1 + 3 回ずつ試す: 利用者の要求 1 件 → C に届いた 64 回（64.00 倍）
B だけが 3 回試す: 利用者の要求 1 件 → C に届いた 3 回（3.00 倍）
```

計算どおり、掛け算になりました。C の直上の B だけが再試行すれば、3 倍で済みます。

次に、利用者の要求を 100 件にし、各段に gRPC の `retryThrottling` と同じ規則のトークンバケット（`maxTokens` 10、`tokenRatio` 0.1）を段ごとに 1 つ持たせました。

```
各段 3 回試す、予算なし: 利用者の要求 100 件 → C に届いた 2700 回（27.00 倍）
各段 3 回試す、トークンバケット: 利用者の要求 100 件 → C に届いた 109 回（1.09 倍）
```

最初の数回の失敗でトークンが半分を切り、あとは各段が再試行をやめて失敗をそのまま返しました。C が落ちている間の負荷は、ほぼ「再試行しない」ときと同じになります。

### 期限を渡すか、各段で決めるか

最後に、C を「1.5 秒かけて処理してから `200` を返す」ようにし、利用者は 1 秒で諦めることにしました。A と B は 3 回まで試します。比べたのは 2 通りです。

- **各段が独立に 1 秒のタイムアウト**: A も B も、下流を 1 秒待って諦め、送り直す
- **残り時間を下流へ渡す**: 利用者が `X-Deadline-Ms: 1000` を付け、各段は受け取った時刻から自分の期限を作り、下流には残り時間を渡す。残りが無ければ下流を呼ばずに `504` を返す。C は 10 ミリ秒ごとに期限を確かめ、切れたら仕事をやめる

8 秒待ってから、C の記録を数えました。

```
各段が独立に 1 秒のタイムアウト: C に届いた 9 回 / うち利用者が諦めた後に始まった 8 回 / C が働いた合計 13.7s / C の最後の仕事が終わった時刻 5.5s
残り時間を下流へ渡す: C に届いた 1 回 / うち利用者が諦めた後に始まった 0 回 / C が働いた合計 1.0s / C の最後の仕事が終わった時刻 1.0s
```

独立のタイムアウトでは、利用者が 1 秒で去ったあとに C で 8 回の仕事が始まり、C は合計 13.7 秒、**誰も待っていない仕事**をしました。B は A がタイムアウトしたことを知らずに C を呼び続け、A は B を待ちきれずに新しい B を呼んだからです。期限を渡すと、C の仕事は 1 回、1 秒で打ち切られました。

## まとめ

- 結果の分からない要求は「送れなかった」「届いたが処理されなかった」「処理されたが応答が消えた」のどれか。後の 2 つは、FIN でも RST でもタイムアウトでも、クライアントからは区別できない
- RFC 9110 は `GET`、`HEAD`、`OPTIONS`、`TRACE` を安全、それに `PUT`、`DELETE` を加えたものを冪等と定め、冪等でない要求の自動再送を戒め、プロキシには禁じている。HTTP/2 の `GOAWAY` と `REFUSED_STREAM` は「処理していない」を伝えられる
- Go の net/http は、使い回した接続での失敗だけを、再送できる要求に限って送り直す。`Idempotency-Key` ヘッダの付いた `POST` も再送できるものとして扱う
- 冪等性キーは、送り直しを見分けるための名前。サーバはキーごとに状態と応答を保存し、同じ中身なら保存した応答を、違う中身なら `422` を、処理中なら `409` を返す。IETF のドラフトは執筆時点で第 08 版
- キーを本体と同じトランザクションに入れると、並行の 2 本目は一意インデックスで相手のコミットを待つ。外部への副作用があるなら「処理中」を先にコミットし、途中で落ちたキーを引き継ぐ仕組みを持つ
- 待ち時間は指数で伸ばし、ジッターで時刻をばらす。ジッターが無いと、待ちをいくら伸ばしても同じ瞬間に全員が来る
- 再試行は段の数だけ掛け算になる。再試行する段を 1 か所にし、予算やトークンバケットで絞る
- 期限は時刻ではなく残り時間として下流へ渡し、切れたら下流を呼ばず、仕事も止める

送り直しても二重にならない受け手と、送り直し方の作法がそろいました。次の回は、送り手と受け手の間に仕事を置いておく**キュー**の中身、ログとオフセットと可視性タイムアウトを見ます。
