## 数値しか渡せない

Core Wasm（コンポーネントモデル以前の Wasm）の関数が扱える型は、たった 4 つです。

```
i32  i64  f32  f64
```

文字列も、構造体も、配列も、**言語として存在しません**。

`greet(name: string) -> string` を実装しようとすると、こうなります。

```wat
(func (export "greet") (param i32 i32) (result i32))
;;                      ptr  len        結果の ptr
```

そして呼ぶ側は、

1. ホスト側の文字列を UTF-8 にする
2. Wasm 側の `malloc` を呼んで、線形メモリに場所を確保する
3. そこにバイト列をコピーする
4. ポインタと長さを渡して関数を呼ぶ
5. 戻ってきたポインタから、長さを読み、バイト列をコピーして取り出す
6. **Wasm 側の `free` を呼んで解放する**

**第 1 回で見た FFI の面倒が、そのまま残っています。** 構造体のレイアウトを合わせ、文字列の表現を変換し、誰が解放するかを決める。安全になったのは「壊れても外に出ない」ことだけで、**手間は減っていません**。

<Callout type="warn" title="しかも言語ごとに流儀が違う">
  Rust の `wasm-bindgen`、AssemblyScript、TinyGo、Emscripten。
  それぞれが独自の「文字列の渡し方」を持っています。

  **Rust で書いた Wasm と、Go で書いた Wasm を直接繋ぐことができない。**
  同じ Wasm なのに、境界の規約が違うからです。

  第 1 回で「C ABI が共通語」と書いたのと同じ問題が、Wasm の中でもう一度起きました。
</Callout>

## コンポーネントモデル

答えは、**Core Wasm の上に、型のある層をもう 1 枚乗せる**ことでした。

```
┌─────────────────────────────────────┐
│  コンポーネント                        │
│   ├─ 型付きのインタフェース（WIT）       │
│   ├─ 変換の規約（canonical ABI）       │
│   └─ core module（今までの Wasm）      │
└─────────────────────────────────────┘
```

**コンポーネントは、core module を包んだもの**です。中身は今までの Wasm のままで、外側に「この関数は文字列を受け取って文字列を返す」という情報と、その変換方法が付きます。

第 5 章で見た ELF とセクションの関係に似ています。実体は機械語だが、外側に「何が入っているか」を記述した層がある。

## WIT：インタフェースを書く

**WIT**（Wasm Interface Type）は、境界を記述するための小さな言語です。

```wit
package example:greeter@1.0.0;

interface greet {
  record person {
    name: string,
    age: u32,
  }

  variant salutation {
    formal,
    casual,
    custom(string),
  }

  hello: func(who: person, style: salutation) -> string;
}
```

使える型です。

| 分類 | 型 |
| --- | --- |
| 基本 | `bool` `u8`〜`u64` `s8`〜`s64` `f32` `f64` `char` `string` |
| 集合 | `list<T>` `tuple<A, B>` |
| 構造 | `record`（構造体） `variant`（タグ付き共用体） `enum` `flags` |
| 特殊 | `option<T>` `result<T, E>` |
| 参照 | **`resource`**（後述） |

**`option` と `result` があることが重要です。** 第 1 回で「例外は境界を越えられない」と書きました。コンポーネントモデルでは、エラーは**型として表現されます**。

```wit
read-file: func(path: string) -> result<list<u8>, error-code>;
```

呼ぶ側は、成功か失敗かを必ず扱うことになります。エラーコードを返して `errno` を見る、という規約を人間が覚える必要がありません。

## world：契約の単位

`interface` は関数のまとまりです。**`world` は「1 つのコンポーネントが何を import し、何を export するか」**を宣言します。

```wit
world greeter {
  // ホストから受け取るもの
  import wasi:cli/environment@0.2.0;
  import log: func(msg: string);

  // 外に提供するもの
  export greet;
}
```

**これが契約書そのものです。**

- `import` = このコンポーネントが動くためにホストが用意しなければならないもの
- `export` = ホストが呼べるもの

第 2 章で「ISA はソフトウェアとハードウェアの契約」と書きました。world は、**ホストとコンポーネントの契約**です。そして機械可読なので、**ツールが検証できます**。

<Callout type="tip" title="import が「渡されるもの」の一覧になっている">
  前回見たケイパビリティの考え方が、ここで形になっています。

  world の `import` に書かれていないものは、そのコンポーネントから触れません。
  **契約書を読めば、そのコンポーネントが何をしうるかが分かる。**

  「このプラグインはネットワークに繋ぐか」を、コードを読まずに判定できます。
  第 7 章の seccomp では、こうはいきませんでした。
</Callout>

## resource：所有権を型で書く

第 1 回で最も事故が多い箇所として挙げたのが、**所有権**でした。誰が確保し、誰が解放するのか。

WIT には、そのための型があります。

```wit
resource file {
  constructor(path: string);
  read: func(len: u32) -> result<list<u8>, error-code>;
  write: func(data: list<u8>) -> result<u32, error-code>;
}
```

`resource` は、**ホスト側が持っている実体への不透明なハンドル**です。

- 中身のアドレスは見えない。**ポインタではない**
- 整数のハンドルとして渡るが、その値に意味はない
- **解放のタイミングは、所有権の移動として型に書かれる**
- 別のコンポーネントに渡すことも、借用させることもできる

第 7 章で見たファイルディスクリプタと同じ構造です。fd は「プロセスごとの表の添字」であって、実体を指すポインタではありませんでした。だから安全に渡せる。

**resource は、その考え方を言語の型として一般化したもの**です。

## canonical ABI：高水準の型を数値に落とす

WIT で書いた `string` は、最終的には Core Wasm の数値になります。その変換規則が **canonical ABI** です。

```
WIT:        hello: func(who: person) -> string

canonical ABI が決める:
  - person をどうメモリに並べるか（フィールドの順、アラインメント）
  - string を UTF-8 で線形メモリのどこに置くか
  - 誰が確保し、誰が解放するか
  - 戻り値が大きいときの返し方
```

**第 1 章で見たアラインメントとパディングの話**が、ここで仕様として固定されています。人間が合わせるのではなく、**規格が決めて、ツールが生成する**。

生成は各言語のツールが行います。

| 言語 | ツール |
| --- | --- |
| Rust | `cargo component` / `wit-bindgen` |
| JavaScript / TypeScript | `jco` |
| Python | `componentize-py` |
| Go | `wit-bindgen-go`（TinyGo） |
| C / C++ | `wit-bindgen c` |

```bash
# WIT から Rust の束縛を生成し、コンポーネントとしてビルドする
cargo component build --release

# 中身を確認する
wasm-tools component wit target/wasm32-wasip1/release/greeter.wasm
```

<Callout type="note" title="第 5 章のリンカと同じ役割">
  リンカは、オブジェクトファイルの未解決シンボルを実アドレスで埋めました。
  コンポーネントモデルのツールは、**WIT の型を canonical ABI の数値操作に展開します**。

  どちらも「人間が書いた抽象を、機械のレベルに落とす」作業です。
  違いは、リンカが扱うのがアドレスだけだったのに対し、
  こちらは**型の変換まで含む**点です。
</Callout>

## 合成：コンポーネントをつなぐ

コンポーネントの `import` を、別のコンポーネントの `export` で埋められます。

```
┌──────────────┐        ┌──────────────┐
│ アプリ         │ import │ ログ実装       │
│  import: log ─┼───────▶│  export: log │
│  export: run  │        └──────────────┘
└──────────────┘
        │
        ▼  合成すると
┌──────────────────────────────┐
│ 1 つのコンポーネント             │
│   export: run                 │
└──────────────────────────────┘
```

```bash
wac plug app.wasm --plug logger.wasm -o composed.wasm
```

**静的リンクとまったく同じ発想です**（第 5 章）。違うのは、

- 繋ぐ相手が**別の言語で書かれていてよい**
- 繋いだ後も、**それぞれの線形メモリは分離されたまま**

Rust で書いたコンポーネントと Python で書いたコンポーネントを合成できて、しかも片方が壊れてももう片方のメモリは無事、という状態が作れます。

<Callout type="tip" title="これが「言語をまたぐリンカ」">
  第 1 回の冒頭に戻ります。FFI の共通語が C ABI だったのは、
  **それが最も小さい共通部分**だったからでした。機能を削って共通化した。

  コンポーネントモデルは逆の方向です。
  **共通の型システムを新しく定義して、各言語をそこに合わせさせる。**

  代償は、対応するツールチェーンが必要になることです。
  利点は、削らずに済むことです。
</Callout>

## WASI も world として定義されている

前回見た WASI は、**WIT で書かれた world の集まり**です。

```wit
// コマンドラインプログラムの world
world command {
  import wasi:filesystem/types@0.2.0;
  import wasi:sockets/tcp@0.2.0;
  import wasi:cli/stdin@0.2.0;
  ...
  export wasi:cli/run@0.2.0;
}
```

```wit
// HTTP サーバの world
world proxy {
  import wasi:http/outgoing-handler@0.2.0;
  export wasi:http/incoming-handler@0.2.0;
}
```

**「どの world を満たすか」が、そのコンポーネントの実行環境を決めます。** `command` を満たすならコマンドラインで動き、`proxy` を満たすなら HTTP サーバとして動く。

| 版 | 時期 | 内容 |
| --- | --- | --- |
| WASI 0.1（Preview 1） | 2019 | 関数を並べただけ。型は数値のみ |
| **WASI 0.2** | 2024 | **コンポーネントモデル採用**。string / record / resource が使える |
| **WASI 0.3** | 2026 年 6 月 | **非同期がモデル本体に**。`future<T>` と `stream<T>` |
| WASI 1.0 | 2026〜2027 予定 | 安定版 |

WASI 0.3 の非同期は、第 7 章で見た議論そのものです。`future` は「完了したら値が来る」、`stream` は「連続して流れてくる」。**準備完了通知と完了通知の区別が、言語をまたぐインタフェースの型として現れました**（[WASI 0.3](https://wasi.dev/releases/wasi-p3)）。

## 3 つの境界を並べる

| | C ABI | Core Wasm | コンポーネントモデル |
| --- | --- | --- | --- |
| 扱える型 | 数値とポインタ | **数値 4 種のみ** | 文字列・構造体・列挙・resource |
| 所有権 | **ドキュメント頼み** | ドキュメント頼み | **型に書かれる** |
| エラー | 戻り値 + `errno` | 数値 | **`result<T, E>`** |
| メモリ | 共有 | インスタンスごとに分離 | 分離 + 自動変換 |
| 壊れたとき | **ホストごと落ちる** | インスタンス内で完結 | インスタンス内で完結 |
| 言語をまたぐ | できる（面倒） | **流儀が食い違う** | できる |
| 変換のコード | 人が書く | 人が書く | **生成される** |
| 必要なもの | C コンパイラ | Wasm ツールチェーン | + コンポーネント対応ツール |

## 代償

きれいな話ばかりではありません。

**1. バイナリが大きくなる。** 型変換の glue と、言語ランタイムがコンポーネントの中に入ります。「Hello, world」が数百 KB になることがあります。

**2. 変換のコストがある。** 文字列や構造体は、境界を越えるたびに**コピーと変換**が発生します。前回書いた「境界をまたぐ回数を減らす」は、ここでも変わりません。

**3. ツールチェーンが動いている。** 0.2 と 0.3 で仕様が変わり、言語ごとの対応度にも差があります。Rust が最も進んでいて、他は追いかけている状況です。

**4. 学ぶことが増える。** WIT の文法、world の考え方、生成ツールの使い方。単に `dlopen` するより理解すべきことが多い。

<Callout type="warn" title="小さく始められるかを確認する">
  **既存の C ライブラリを 1 つ呼びたいだけ**なら、コンポーネントモデルは重すぎます。
  Core Wasm + 自前の薄い ABI で足ります。

  効いてくるのは、**境界が長期にわたって保たれる場面**です。
  プラグインの API、複数チームで分担する境界、サードパーティに公開するインタフェース。
  「後から型を足せない」ことのコストが大きい場所が向いています。
</Callout>

## まとめ

- Core Wasm が扱える型は数値 4 種だけ。文字列は ptr + len に手で分解する必要があった
- 言語ごとに渡し方の流儀が違い、Wasm 同士でも直接繋がらなかった
- コンポーネントモデルは、core module を包んで型のある層を乗せる
- **WIT** が型とインタフェースを記述し、**world** が import / export の契約を宣言する
- **`resource`** が所有権を型として表す。ファイルディスクリプタの考え方の一般化
- **canonical ABI** が高水準の型を数値に落とす規則。生成ツールがコードを書く
- コンポーネント同士を合成できる。言語をまたぐリンカに相当する
- WASI 自体が world として定義されている。0.2 で型が、0.3 で非同期が入った
- 代償はサイズ、変換コスト、ツールチェーンの成熟度

次は、これが**実際にどう使われているか**を見ます。Wasm をプラグイン機構として採用した OSS を、設計の判断ごとに並べます。
