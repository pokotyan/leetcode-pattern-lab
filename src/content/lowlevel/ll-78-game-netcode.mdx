前回は、WebRTC がブラウザ同士をつなぎ、音声と映像を RTP で流し、DataChannel で任意のデータを運ぶ仕組みを見ました。その前の 2 回では、QUIC の DATAGRAM（第 75 回）と NAT 越え（第 76 回）を扱っています。ここまでの 3 回で見てきたのは、**どう運ぶか**でした。

この回は、**何を運ぶか**を考えます。題材は対戦ゲームです。回線には数十ミリ秒の遅延があり、その長さは揺らぎ、パケットはときどき失われます。それでも、画面の前の全員が**同じ世界を見ているように見せたい**。そのために、何を、どの頻度で送り、受け取った側は何を画面に出すのかを順に見ていきます。

## 全員が少しずつ違う時刻にいる

最初に、問題の形をはっきりさせます。片道 50ms の回線でつながった 2 人がいるとします。

- 自分の操作がサーバに届くのは 50ms 後。その結果が返ってくるのは、早くても 100ms 後
- 相手について届く情報は、どれも 50ms 以上前のもの
- 相手から見た自分も、50ms 以上前の自分

つまり、**全員が少しずつ違う時刻の世界を見ています**。これは回線を速くしても 0 にはなりません。設計で決めることは、次の 3 つに分けられます。

| 問い | 選択肢の例 |
| --- | --- |
| 何が正しいかを誰が決めるか | サーバ、全員が同じ計算をする、各自が自分の分を決める |
| 何を送るか | 入力だけ、状態の全体、状態の差分 |
| 画面に何を出すか | 届いた最新の状態、少し過去を補間したもの、自分で予測した未来 |

## 権威をどこに置くか

**権威**（authority）とは、「本当はどうなったか」を決める立場のことです。

**クライアント・サーバ型**では、サーバが世界を動かし、クライアントは入力を送って結果を受け取ります。Gabriel Gambetta の解説は、これを**権威サーバ**（authoritative server）と呼び、不正への対策として最も重要なのは「プレイヤーを信用しないこと」だと書いています（[Gambetta, Fast-Paced Multiplayer Part I](https://www.gabrielgambetta.com/client-server-game-architecture.html)）。クライアントが「自分は今ここにいる」「この敵を倒した」と申告する形にすると、申告を書き換えるだけで不正ができます。入力だけを受け取り、結果はサーバが計算すれば、少なくとも壁を抜けるような申告は通りません。

**P2P 型**では、サーバを置かずに端末同士が直接やり取りします。誰か 1 人を権威に選ぶ方法もありますが、多くの RTS や格闘ゲームが使ってきたのは、**全員が同じ入力から同じ計算をする**方法です。次の節のロックステップと、後半のロールバックがこれに当たります。

| | クライアント・サーバ（権威サーバ） | P2P（全員が同じ計算） |
| --- | --- | --- |
| サーバの費用 | 要る | 要らない（第 76 回の NAT 越えは要る） |
| 結果の改ざん | サーバが計算するので難しい | 全員が同じ計算をするので、食い違えば検出できる |
| 情報の漏れ | 見えるべきものだけを送れる | 全員が世界の全体を持つので、隠れた情報も手元にある |
| 遅延 | 往復の分だけ操作の反映が遅れる | 一番遅い相手との片道や往復に引きずられる |

最後の 2 行が、この回の残りの話の出発点です。

## 決定論的ロックステップ

### 入力だけを送る

Age of Empires の開発者は、最低の動作環境を 28.8kbps のモデムとして、数百のユニットが動く対戦を作りました。ユニットの座標や状態を送る方式では、動かせるユニットは 250 ほどが限度だったと書いています。そこで選んだのが、**全員が同じシミュレーションを走らせ、送るのはコマンドだけ**にする方式です（[Bettner, Terrano, 2001](https://www.gamedeveloper.com/programming/1500-archers-on-a-28-8-network-programming-in-age-of-empires-and-beyond)）。

- 時間を**通信ターン**に区切る。ターンの長さは通常 200ms
- ターン 1000 に出したコマンドは、**ターン 1002 に実行する**と決めて送る。2 ターン先なので、相手に届くまでの猶予がある
- 全員のコマンドがそろうまで、次のターンには進まない

ユニットが何千あっても、送るのは「この 10 体をここへ動かせ」というコマンドだけです。実行を 2 ターン遅らせれば、プレイヤーには 200〜400ms の遅れが生じます。同じ記事は、RTS では 250ms のコマンドの遅れは気付かれず、250〜500ms は十分遊べ、500ms を超えると気付かれ始めたと書いています。**遅れに強いジャンルだから選べた方式**です。

### 一番遅い人に合わせて全員が待つ

全員の入力がそろわなければ進めない以上、**ゲームは一番遅い参加者の速さでしか進みません**。Age of Empires は、各端末の処理の速さと回線の遅れを測り、ターンの長さそのものを調整していました（同記事）。

手元のシミュレータで確かめます（実験の道具立ては後の節で説明します）。60fps で 3600 フレームを進める 2 人の端末を、片道の遅延、±8ms のジッタ、2% の損失がある仮想の回線でつなぎました。各フレームでは**相手のそのフレームの入力が届くまで待ちます**。入力は失われる前提で、毎回直近 16 フレーム分をまとめて送り直しています。自分の入力を何フレーム先の分として出すか（入力遅延）を変えて、待たされた回数を数えました。

```
one-way delay stall_ticks slowdown  same
   16ms     0        5576     2.55x  True
   16ms     2          57     1.02x  True
   40ms     0       10626     3.95x  True
   40ms     2        1236     1.34x  True
   40ms     4           6     1.00x  True
   70ms     0       17138     5.76x  True
   70ms     2        3427     1.95x  True
   70ms     4         717     1.20x  True
   70ms     6           8     1.00x  True
```

入力遅延が 0 だと、片道 16ms でも 2.55 倍の時間がかかっています。**入力遅延を片道の遅延より長くとって初めて、待たずに進めます**。片道 70ms（約 4.2 フレーム）では、4 フレームでは足りず、6 フレームでほぼ止まらなくなりました。ロックステップの設計とは、この「操作してから反映されるまでの遅れ」を払うことで、待ち時間を消す設計です。`same` の列は、最後のフレームで 2 台の状態が一致したかどうかです。

Glenn Fiedler は、入力を TCP で送ると、失われた入力の再送を待つ間シミュレーションが止まると指摘しています。入力は小さいので、UDP で**届いたと確認されていない入力をすべて毎回送る**ほうがよい、という結論です（[Fiedler, Deterministic Lockstep, 2014](https://gafferongames.com/post/deterministic_lockstep/)）。第 54 回の TCP の HOL ブロッキングが、ここでも問題になります。

### 決定論は難しい

この方式は、**同じ初期状態と同じ入力から、ビット単位で同じ結果が出る**ことに全面的に依存しています（同記事）。1 ビットでもずれれば、その差は積み重なって、いずれ片方の画面ではユニットが生きていて、もう片方では死んでいる、という食い違い（**デシンク**）になります。

ずれの源として、まず浮動小数点があります。第 4 回で見たとおり、浮動小数点の加算は結合法則を満たしません。手元の Python 3.14.0 で確かめると、こうなります。

```
(0.1+0.2)+0.3 = 0.6000000000000001  0.1+(0.2+0.3) = 0.6
```

数式として同じでも、計算の順序が変われば最後のビットが変わります。そして、ゲームの物理のように小さな差を増幅する計算では、それが大きな差に育ちます。数学的に等しい 2 つの式 `r*x*(1-x)` と `r*x - r*x*x` で、ロジスティック写像（r = 3.9）を 100 回まわしました。

```
step   1: A=0.97499999999999998 B=0.97499999999999998 diff=0.000e+00
step  10: A=0.10400971326746830 B=0.10400971326746822 diff=8.327e-17
step  30: A=0.97284343951089769 B=0.97284343950992280 diff=9.749e-13
step  50: A=0.24135511240702046 B=0.24135522619998495 diff=1.138e-07
step  60: A=0.41278216690125880 B=0.41282060341521687 diff=3.844e-05
step  76: A=0.46337641516608319 B=0.25716102300675914 diff=2.062e-01
```

10 回目で最後の 1 ビットほどだった差が、76 回目には値の 2 割を超えました。コンパイラが式を並べ替える、別の命令（FMA など）を使う、という違いだけで、2 台の計算はこのように分かれます。Fiedler の別の記事は、同じコンパイラと同じ命令セットに固定すれば浮動小数点でも決定論的にできるが、コンパイラや CPU の構成が違えば、デバッグビルドとリリースビルドの間ですら結果が変わりうるとまとめています。寄せられた経験談の中には、AMD と Intel で超越関数（sin、cos など）の結果がわずかに違ったという報告もあります（[Fiedler, Floating Point Determinism, 2010](https://gafferongames.com/post/floating_point_determinism/)）。整数か固定小数点で計算する、という選択が昔から好まれるのはこのためです。

もう 1 つの源が**乱数**です。全員が同じ種から始め、乱数生成器の状態もゲームの状態の一部として扱う必要があります。Age of Empires も擬似乱数の種を保存し直して全端末でそろえていました（[Bettner, Terrano](https://www.gamedeveloper.com/programming/1500-archers-on-a-28-8-network-programming-in-age-of-empires-and-beyond)）。他にも、壁時計の時刻、ハッシュ表を走査する順序、初期化していないメモリなど、**入力以外から結果に入り込むもの**はすべてずれの源になります。

<Callout type="tip" title="デシンクは検出できるようにしておく">
  決定論が崩れても、その場では何も起きません。差はしばらく見えないまま育ちます。
  そこで、各端末が一定間隔でゲームの状態のチェックサムを計算して交換し、食い違ったらその時点で知らせる仕組みを入れておくのが一般的です。
  食い違いが見つかった最初のフレームが分かれば、原因の追跡がずっと楽になります。
</Callout>

## 実験の道具立て

ここからは、権威サーバ型の技法を順に見ていきます。比べるために、Python 3.14.0（macOS 上）で小さなシミュレータを書きました。外部のライブラリは使っていません。

- 世界は 1 次元。プレイヤーは入力（-1、0、+1）に応じて 5 単位/秒で動く。入力は乱数で決めた台本で、10〜60 ティックごとに変わる
- サーバは 60Hz でティックを進め、20Hz（3 ティックに 1 回）でスナップショットを送る
- 回線は上りと下りを別々に模擬し、片道の遅延、一様分布のジッタ、損失率を指定する。ジッタがあるのでパケットの順序も入れ替わる
- クライアントは毎ティック入力にシーケンス番号を付け、サーバが受け取ったと確認していない入力を最大 30 個まとめて送る
- 位置 -3〜3 の区間には、**サーバだけが知っている**外力（+2 単位/秒）がある。他のプレイヤーに押される、動く床に乗る、といった、クライアントが予測できない出来事の代わり
- 別にもう 1 人、サーバ上で動くプレイヤー（以下「相手」）を置く

記録は 60 秒（3600 ティック）です。以下では、断りがなければ片道 50ms、ジッタ ±15ms、損失 5% の条件で測っています。実際に失われた割合は、上りが 4.9%、下りが 4.8% でした。

## スナップショットと補間

### 描く時刻を過去にずらす

権威サーバ型の基本は、サーバが世界の**スナップショット**を一定の間隔で撮って配ることです。Valve の Source エンジンの解説では、サーバは 1 ティック 15ms（約 66.7 ティック/秒）で世界を進め、クライアントが受け取るスナップショットは既定で毎秒 20 個（`cl_updaterate 20`）です（[Valve, Source Multiplayer Networking](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)）。

毎秒 20 個では、届いた位置をそのまま描くとカクつきます。そこで Source は、**描く時刻をわざと過去にずらし**、受け取った 2 つのスナップショットの間を補間します。既定の補間期間は 100ms（`cl_interp 0.1`）で、50ms ごとに届くスナップショットが 1 つ失われても、補間に使える 2 つがまだ手元に残る長さです。それでも足りなくなったときは直線で外挿しますが、外挿は 0.25 秒まで（`cl_extrapolate_amount`）に限られます（同ページ）。補間期間は次の式で決まります。

```
補間期間 = max( cl_interp, cl_interp_ratio / cl_updaterate )
```

Fiedler は、2〜5% の損失なら、パケット 2 つを続けて失っても補間先が残るように**送信間隔の 3 倍**、さらにジッタの分を足した遅れが要るという経験則を挙げています。毎秒 10 パケットなら 300ms に 50ms を足して 350ms です（[Fiedler, Snapshot Interpolation, 2014](https://gafferongames.com/post/snapshot_interpolation/)）。

### 実験: 補間の遅れを変える

相手の位置の出し方を 4 通りに変えて比べました。`latest` は届いた最新のスナップショットの位置をそのまま出します。それ以外は、推定したサーバの現在時刻から補間遅延を引いた時刻を描きます。サーバの時刻は、直近 1 秒に受け取ったスナップショットの「受信時刻 − 送信時刻」の最小値をずれとして推定しました。

```
interp   stale_ms err_past  err_now jump_max still% underrun%
latest         77    0.000    0.235    0.750   79.9       0.0
50ms          100    0.005    0.306    0.500   39.2      14.1
100ms         150    0.002    0.450    0.250   36.8       0.6
150ms         200    0.002    0.593    0.083   36.9       0.2
```

| 列 | 意味 |
| --- | --- |
| `stale_ms` | 画面に出している相手が、平均で何 ms 前の姿か |
| `err_past` | 描いている時刻での、サーバ上の本当の位置との差 |
| `err_now` | 今この瞬間の、サーバ上の位置との差 |
| `jump_max` | 1 フレームで表示が跳んだ最大の距離（1 フレームに正しく進む距離は約 0.083） |
| `still%` | 表示が止まっていたフレームの割合。相手が本当に止まっている割合は 36.8% |
| `underrun%` | 描く時刻の先のスナップショットがまだ無く、補間できなかったフレームの割合 |

`latest` は一番新しい姿を出していますが、**8 割のフレームで止まり、届くたびに最大 0.75 跳んでいます**。毎秒 20 回の階段です。補間 50ms は、スナップショットの間隔とちょうど同じ長さなので、遅れやジッタがあると 14% のフレームで次が届いておらず、足りません。100ms にすると、補間できないフレームは 0.6% になり、止まっている割合は相手が本当に止まっている割合とほぼ同じになりました。150ms にすれば 1 フレームの跳びは正しい速さの 0.083 と一致し、完全に滑らかになります。

代わりに払っているのが `stale_ms` と `err_now` です。**滑らかさは、見ている過去の深さと引き換え**です。片道 100ms、ジッタ ±30ms、損失 10% に悪化させると、補間 50ms では 41% のフレームが補間できず、100ms でも 3.8% になりました。

### デルタ圧縮: 確認済みの基準からの差分

スナップショットを毎回丸ごと送ると帯域が足りません。Fiedler の例では、901 個の立方体の状態を 60Hz で送ると約 17.38Mbps になりました（[Fiedler, Snapshot Compression, 2015](https://gafferongames.com/post/snapshot_compression/)）。

そこで、**相手が受け取ったと確認できたスナップショットを基準**（ベースライン）にして、そこからの差分だけを送ります。「スナップショット 110 を、100 を基準に符号化した」という形です。変わっていない物体は「変化なし」の 1 ビットで済みます。基準は**必ず相手が受け取ったものでなければなりません**。受け取っていないものを基準にすると、相手は復号できないからです。受信側は最新の受信番号を ACK で返し続け、送信側はそれを見て基準を新しくします。定常状態では、基準はおよそ 1 往復前のスナップショットになります（同記事）。

Source もスナップショットを、**最後に確認された更新からの差分**で送っています。差分でない完全なスナップショットを送るのは、ゲームの開始時と、数秒間ひどい損失が続いたときだけです（[Valve](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)）。

TCP の再送とは考え方が逆なことに注意してください。**失われたスナップショットは送り直しません**。次のスナップショットが、もっと新しい状態を、まだ有効な基準からの差分として運ぶからです。

### 優先度と関心管理

物体が多い世界では、すべてを毎回送ることはできません。そこで、**大事なものを多く、そうでないものを少なく**送ります。

Fiedler の**優先度アキュムレータ**は、物体ごとに数値を 1 つ持ち、毎フレームその物体の優先度を足していきます。値の大きい順に、パケットに入るだけ詰めて送り、送れた物体の値は 0 に戻します。入らなかった物体は値が残るので、次のパケットで先頭に来ます（[Fiedler, State Synchronization, 2015](https://gafferongames.com/post/state_synchronization/)）。帯域の上限（記事の例では 256kbit/s）を動的に変えれば、回線が苦しいときに送る量を絞れます。

優先度の決め方として一番素直なのは、**プレイヤーの近くにあるもの、視界に入っているものを高くする**ことです。さらに進めて、見えないもの・関係ないものは**そもそも送らない**のが関心管理（interest management）です。帯域が減るだけでなく、権威サーバの表の「情報の漏れ」の行にも効きます。壁の向こうの敵の位置をクライアントに送らなければ、クライアントを改造しても見えません。

## クライアント側の予測と照合

### 自分の操作だけは待たない

補間は**他人**を滑らかに見せる技法でした。**自分**の操作に同じことをすると、キーを押してから自分が動くまでに往復と補間の分だけ待たされます。Valve の解説の例では、遅延 150ms のプレイヤーが前進キーを押すと、自分が歩き出すのが見えるのは 150ms 後です（[Valve](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)）。

そこで、**クライアントがサーバと同じコードで自分の入力を先に計算し、その結果を出します**。これがクライアント側予測です。ただし、権威はあくまでサーバにあります。サーバの結果が届いて予測と違っていたら、クライアントは自分の位置を直さなければなりません。

### 照合: 確定した状態から、未確認の入力を積み直す

直し方が肝心です。サーバから届く位置は、往復の分だけ過去のものです。素直にそれで上書きすると、その間に押した入力の分だけ**引き戻されます**。

Gambetta が解説する方法は、**入力にシーケンス番号を振り、サーバは「どの番号まで処理したか」を状態と一緒に返す**ものです（[Gambetta, Part II](https://www.gabrielgambetta.com/client-side-prediction-server-reconciliation.html)）。クライアントは、確認された番号以前の入力を捨て、サーバの位置を出発点に、**まだ確認されていない入力を自分で計算し直します**。Half-Life のネットワークを設計した Yahn Bernier も、2001 年の論文で同じ手順を示しています。最後に確認されたコマンドの後の状態から始め、それ以降のコマンドを順に走らせます（[Bernier, Latency Compensating Methods, 2001](https://developer.valvesoftware.com/wiki/Latency_Compensating_Methods_in_Client/Server_In-game_Protocol_Design_and_Optimization)）。

シミュレータの照合の部分は次のとおりです。

```python
# スナップショットを受け取ったとき
unacked = [(s, i) for s, i in unacked if s > snap["ack"]]   # 確認済みの入力を捨てる
before = pred
pred = snap["x"]                       # サーバが確定した位置から
for _, i in unacked[:-1]:              # まだ確認されていない入力を積み直す
    pred = step_client(pred, i)        # （最後の 1 つはこの後のティックで通常どおり適用する）
corrections.append(abs(before - pred)) # 照合で動いた量 = 予測の外れ
```

### 実験: 予測なし、予測だけ、上書き、照合

自分の位置の出し方を 4 通りに変えました。

- `none`: 予測しない。届いた最新のスナップショットの位置を出す
- `predict_only`: 予測だけして、サーバの結果を一切見ない
- `naive`: 予測し、スナップショットが届くたびにその位置で上書きする（積み直さない）
- `reconcile`: 予測し、上で見た方法で照合する

誤差は、遅延が無かった場合（入力をその場でサーバの物理で計算した場合）の位置との差です。反応は、向きを変えてから画面上の自分がその向きに動き出すまでの時間の中央値です。

```
mode          err_mean  err_p95 react_ms corr_n corr_mean corr_max
none             0.392    0.833      167      0     0.000    0.000
predict_only     6.820   12.667       17      0     0.000    0.000
naive            0.287    0.583       17    635     0.145    0.667
reconcile        0.044    0.300       17    188     0.102    0.267
```

`none` は、操作してから動くまで 167ms かかっています。往復の 100ms に、次のスナップショットを待つ時間とティックの刻みが加わった値です。予測をすると、どの方式でも 1 フレーム（17ms）で反応します。

違いは、その後です。`predict_only` は、サーバだけが知っている外力を知らないので、外力の区間を通るたびにずれが積み重なり、平均で 6.8 も外れました。**予測は権威に照らして直さなければ、ずれ続けます**。

`naive` は、新しいスナップショットを反映した 1142 回のうち 635 回で位置を直され、1 回で最大 0.667 戻されています。速さ 5 単位/秒で約 133ms 分です。往復の間に進んだ分を毎回引き戻されるので、動いている間ずっとガクガクと引っ張られる、いわゆるラバーバンドになります。

`reconcile` は、直された回数が 188 回で、ほぼ外力の区間を通ったときだけです。平均誤差は `naive` の 6 分の 1 以下でした。**照合をすれば、補正が起きるのは予測が本当に外れたときだけになります**。片道 100ms、損失 10% に悪化させても、`reconcile` の平均誤差は 0.075、`naive` は 0.540、`none` は 0.659 で、反応は `none` だけが 267ms に延びました。

<Callout type="warn" title="積み直しで同じ効果を何度も出さない">
  照合では、同じ入力を何度も計算し直します。Bernier の論文は、その計算の中で足音などの効果音や画面効果を出すと、積み直すたびに鳴ってしまうと注意しています。
  クライアントは、各コマンドを初めて計算したときだけ効果を出すよう印を付けておきます（[Bernier](https://developer.valvesoftware.com/wiki/Latency_Compensating_Methods_in_Client/Server_In-game_Protocol_Design_and_Optimization)）。
  照合で位置が跳ぶ見た目は、Source のように短い時間をかけて滑らかに寄せる（`cl_smoothtime`）ことで目立たなくできます（[Valve](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)）。
</Callout>

予測できるのは、自分と、自分の入力だけで決まるものに限られます。**他人の入力は、届くまで分からない**からです（同ページ）。そのため、権威サーバ型のゲームの画面には、**予測した少し未来の自分**と、**補間した少し過去の他人**が同時に映っています。

## ラグ補償: 撃った瞬間に巻き戻す

この食い違いが一番問題になるのが、撃ち合いです。画面の相手は 100ms 以上前の姿です。そこに照準を合わせて撃っても、命令がサーバに届く頃には、相手はもうそこにいません。

Source のサーバは、全プレイヤーの直近 1 秒の位置を記録しておき、撃つ命令が届くと、その命令が作られた時刻を次の式で見積もります（[Valve](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)）。

```
命令の実行時刻 = サーバの現在時刻 − 回線の遅延 − クライアントの補間遅延
```

そして、**他のプレイヤーだけを**その時刻の位置に戻し、当たり判定をしてから元に戻します。これがラグ補償です。式に補間遅延が入っていることに注目してください。クライアントが過去を見せていることを、サーバが知っていて差し引いています。

### 実験: 巻き戻すかどうか

シミュレータのクライアントに、0.5 秒ごとに**画面上の相手の位置に正確に**撃たせました。命令には、クライアントが描いていた時刻を付けます。サーバは、巻き戻さずに今の位置で判定した場合と、その時刻に巻き戻して判定した場合の両方を数えます。当たりの幅は ±0.4、補間遅延は 100ms です。`rewind_limit` は巻き戻してよい時間の上限です。

まず、これまでと同じ片道 50ms、ジッタ ±15ms、損失 5% の結果です。

```
rewind_limit=1000ms shots=113 hit_no_rewind=39 hit_rewind=113 target_moved_since_mean=0.59 max=1.00
```

次に、片道 150ms、ジッタ ±20ms、損失 2% のプレイヤーの結果です。

```
rewind_limit=1000ms shots=116 hit_no_rewind=30 hit_rewind=116 target_moved_since_mean=1.10 max=2.00
rewind_limit=200ms shots=116 hit_no_rewind=30 hit_rewind=46 target_moved_since_mean=0.30 max=0.92
```

巻き戻さなければ、正確に狙っても当たるのは 3 割ほど（113 発中 39 発）です。当たったものも、たまたま相手が止まっていたか、こちらへ向かっていたものです。巻き戻せば全弾当たります。

`target_moved_since` は、当たった瞬間に、撃たれた側が**サーバの現在ではすでにどれだけ離れていたか**です。片道 150ms では平均 1.10、最大 2.00 で、速さ 5 単位/秒の相手が 0.4 秒前にいた場所で撃たれています。撃たれた側から見れば、**もう物陰に入ったのに撃たれた**ことになります。

Bernier の論文はこの逆説を正面から書いています。遅延の大きいプレイヤーが遅延の小さいプレイヤーを撃つと、撃たれた側には「角の向こうから撃たれた」ように見えることがある。それでも Half-Life では、各プレイヤーが自分の武器を即座に、思ったとおりに扱えることを選んだ。これはゲームデザインの判断だ、という結論です（[Bernier](https://developer.valvesoftware.com/wiki/Latency_Compensating_Methods_in_Client/Server_In-game_Protocol_Design_and_Optimization)）。撃つ側に有利に判定するこの考え方は、"favor the shooter" と呼ばれます。

得と失は、次のように分かれます。

| | 得をする人 | 損をする人 |
| --- | --- | --- |
| ラグ補償あり | 撃つ側。見えたとおりに当たる | 撃たれる側。隠れた後に撃たれる。遅延の大きい相手ほどひどい |
| ラグ補償なし | 撃たれる側 | 撃つ側。相手の動きを読んで先を狙う必要があり、その量は自分の遅延で変わる |

そのため、**どこまで巻き戻すかに上限を設けます**。Riot Games は VALORANT について、上限が無ければ 500ms の遅延のプレイヤーが、物陰に入って半秒後のあなたを倒せてしまうので、悪用を防ぎつつ各地域の大半のプレイヤーがほぼ完全な当たり判定で遊べるよう上限を調整している、と書いています（[Riot Games, Peeking into VALORANT's Netcode, 2020](https://www.riotgames.com/en/news/peeking-valorants-netcode)）。上の実験で上限を 200ms にすると、片道 150ms のプレイヤーの命中は 116 発中 46 発に落ち、撃たれた側が離れていた距離は最大 0.92 に縮みました。**遅延の大きいプレイヤーに、自分の遅延の分を自分で払わせる**線引きです。

## ロールバック: 予測して進め、外れたら巻き戻す

格闘ゲームは、ロックステップとも権威サーバとも相性がよくありません。1 フレーム（約 17ms）の入力遅延にも気付くプレイヤーがいるので、ロックステップのように入力を何フレームも遅らせられません。1 対 1 で対称なので、片方に権威を置くのも不公平です。

GGPO は、ここで**ロールバック**を使います。相手の入力がまだ届いていないフレームは、相手の入力を予測して先に進めます。後から本物の入力が届き、予測と違っていたら、**そのフレームの状態を読み戻し、現在まで計算し直します**（[GGPO](https://github.com/pond3r/ggpo)）。予測は単純で、相手は直前と同じボタンを押し続けているものとします。格闘ゲームの入力は、60fps で見ればほとんどのフレームで前のフレームと同じなので、たいてい当たります。

ゲームの側には、次の 3 つの機能が求められます（[GGPO Developer Guide](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md)）。

- `save_game_state`: 今の状態を丸ごと保存する
- `load_game_state`: 保存した状態に戻す
- `advance_frame`: 描画せずに 1 フレームだけ進める

前提はロックステップと同じで、**シミュレーションが完全に決定論的であること**です。乱数の種を両者でそろえ、乱数生成器の状態をゲームの状態に含めておけば、何度巻き戻しても同じ乱数が出ます（同ガイド）。また、**1 フレームの巻き戻しを毎フレーム行い、1 回目と 2 回目の状態を比べる**検査用のセッション（sync test）が用意されていて、決定論の崩れを開発中に見つけられます。

### 入力遅延と巻き戻しの深さの兼ね合い

GGPO は、ロックステップの入力遅延とロールバックを**組み合わせて**使います。開発者が入力遅延のフレーム数を決め、パケットが届くのにそれより長くかかる分だけを予測で隠します（同ガイド）。

ガイドの勧めは、ゲームの質を損なわない範囲で入力遅延をできるだけ大きくすることです。格闘ゲームでは 1 を超える入力遅延に中級者のほとんどが気付くが、パズルゲームなら 4〜5 まで上げられる、と書かれています。入力遅延を大きくすれば巻き戻しが浅くなり、予測が外れていた数フレームの間だけ出ていた表示（たとえば 2 フレームだけの画面の明滅）が、巻き戻しで消えてしまうことが減ります。また、予測で進めてよいのは 8 フレームまで（`GGPO_MAX_PREDICTION_FRAMES`）で、それを超えると進めずに待ちます（[ggponet.h](https://github.com/pond3r/ggpo/blob/master/src/include/ggponet.h)）。

### 実験: 巻き戻しは何回、何フレームか

ロックステップの実験と同じ回線で、相手の入力を予測して進め、外れたら巻き戻す方式にしました。入力は 16 通りのボタンの組み合わせで、4〜30 フレームごとに変わります。状態は整数だけで計算し、乱数生成器の状態も含めています。予測の上限は GGPO と同じ 8 フレームです。片方の端末で数えた値です。

```
one-way delay rollbacks  resim resim/frame depth_mean depth_max stalls  same
   16ms     0       194    286        0.08        1.5         3      0  True
   16ms     1        91     92        0.03        1.0         2      0  True
   16ms     2         1      1        0.00        1.0         1      0  True
   40ms     0       194    566        0.16        2.9         4      0  True
   40ms     2       177    179        0.05        1.0         2      0  True
   40ms     3         2      2        0.00        1.0         1      0  True
   70ms     0       194    908        0.25        4.7         6      0  True
   70ms     3       193    328        0.09        1.7         3      0  True
  120ms     0       194   1463        0.41        7.5         8     71  True
  120ms     3       193    907        0.25        4.7         6      0  True
```

| 列 | 意味 |
| --- | --- |
| `rollbacks` | 巻き戻した回数 |
| `resim` | 計算し直したフレームの合計 |
| `resim/frame` | 3600 フレームあたりの、1 フレームの追加の計算量 |
| `depth_mean` / `depth_max` | 1 回の巻き戻しで戻ったフレーム数 |
| `stalls` | 予測の上限に達して待ったティック数 |

巻き戻しの回数（約 194 回）は、ほぼ**相手が入力を変えた回数**です。予測が外れるのは入力が変わった瞬間だけだからです。変わるのは遅延のほうで、**1 回にどれだけ戻るか**は片道の遅延から入力遅延を引いた分になっています。片道 70ms・入力遅延 0 では平均 4.7 フレーム戻り、入力遅延を 3 にすると 1.7 フレームに縮みました。片道 16ms なら入力遅延 2 で、40ms なら 3 で巻き戻しはほとんど起きなくなります。この 2 つは、**ロールバックが入力遅延を払って消えていく**様子です。

片道 120ms・入力遅延 0 では、戻りが上限の 8 フレームに達し、71 ティック待たされました。予測で隠せる遅延には上限があります。

費用は `resim/frame` です。片道 120ms では、1 フレームあたり平均 0.41 フレーム分を余計に計算しています。ただし平均は当てになりません。巻き戻しは入力が変わった瞬間にまとめて起こり、**最悪の場合、予測の上限の 8 フレーム分の計算を 1 フレームの時間（17ms）に収めなければなりません**。ロールバックを採るゲームは、1 フレームの計算を、描画を除いて数分の 1 の時間で終えられるように作る必要があります。状態の保存も毎フレーム行うので、状態は小さく、丸ごとコピーできる形にしておくのが有利です。

`same` の列は、最後に 2 台の状態が一致したことを示しています。予測が何度外れても、正しい入力がそろえば、決定論によって同じ結果に収束します。

## 調整する値: ティックレート、送信レート、入力遅延

ここまで出てきた数値は、どれもゲームごとに選ぶ値です。

| 値 | 上げると | 下げると | 例 |
| --- | --- | --- | --- |
| ティックレート（サーバが世界を進める頻度） | 判定が細かく、待ち時間が減る。CPU を食う | 安い。動きの速いものの判定が粗くなる | Source は既定で 1 ティック 15ms。CS:S や TF2 は 66（[Valve](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)）。VALORANT は 128（[Riot](https://www.riotgames.com/en/news/peeking-valorants-netcode)） |
| スナップショットの送信レート | 補間遅延を短くできる。帯域を食う | 帯域が減る。補間遅延が延びる | Source のクライアントは既定で毎秒 20 個を要求し、ティックレートを超えては届かない |
| 入力の送信レート | 自分の操作が早く届く。上りの帯域を食う | 1 パケットに複数の入力をまとめる | Source は毎秒 30 パケット程度で、1 パケットに 2 つ以上の入力が入る |
| 補間遅延 | 損失とジッタに強くなる。過去を見る深さが増す | 新しい姿が見える。カクつきやすい | Source は 100ms。Fiedler の例では 350ms |
| 入力遅延 | 巻き戻しや待ちが減る | 操作の手応えが良くなる | GGPO は格闘ゲームで 1 以下、パズルなら 4〜5 |

Valve の解説によれば、Source のサーバをティックレート 100 で動かすと、既定の 66 のときの約 1.5 倍の CPU を使います（[Valve](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking)）。また、補間遅延は動いている側をわずかに有利にします。相手を少し早く見られるからです。両者とも動いていれば差は消えます（同ページ）。Riot Games は、曲がり角から飛び出す側が待ち構える側より有利になる「ピーカーズアドバンテージ」を式で示しています。待ち構える側が生き残るには、飛び出す側より、自分とサーバの往復の遅延と、両側で受信したデータを処理まで溜めておく時間の分だけ速く反応しなければなりません。この溜めておく時間はティックレートと描画のフレームレートで決まるため、128 ティックのサーバと遅延の削減によって、有利さの約 28% に当たる約 40ms を縮めたと書いています（[Riot](https://www.riotgames.com/en/news/peeking-valorants-netcode)）。

Overwatch の GDC 2017 の講演は、権威サーバ型のシューターでも決定論を活用して応答性と精度を両立させる設計を扱っています（[Ford, 'Overwatch' Gameplay Architecture and Netcode, GDC 2017](https://gdcvault.com/play/1024001/-Overwatch-Gameplay-Architecture-and)）。ここで見た技法は、1 つを選ぶものではなく、ゲームの中で**ものごとに使い分ける**ものです。

## 確実に届けるものと、届かなくてよいもの

最後に、第 75 回の話に戻ります。ゲームが送るものを、届かなかったときにどうするかで分けてみます。

| 送るもの | 失われたら | 向いている運び方 |
| --- | --- | --- |
| 位置のスナップショット | 送り直さない。次の新しいスナップショットが上書きする | 順序も再送も無い経路 |
| 入力（予測・ロックステップ・ロールバック） | 送り直す価値はあるが、再送を待ちたくない | 確認されていない入力を毎回まとめて送る。運び方は順序も再送も無い経路 |
| チャット、アイテムの購入、試合の結果 | 必ず届けなければならない。順序も大事 | 再送と順序のある経路 |

スナップショットを TCP や QUIC のストリームで送ると、1 つの失われたパケットのために、もっと新しいスナップショットまで待たされます（第 54 回、第 66 回）。古いスナップショットの再送は、**届いた時点ですでに要りません**。逆に、購入の要求が消えるのは困ります。

QUIC の DATAGRAM 拡張は、この 2 つを 1 本の接続に同居させるための仕組みです。DATAGRAM フレームは損失が検出されても再送されません。それでいて ACK を求めるので、送った側は届いたかどうかを知ることはできます（[RFC 9221 5.2](https://www.rfc-editor.org/rfc/rfc9221.html#section-5.2)）。そして、**ストリームと同じ輻輳制御に従います**（[RFC 9221 5.4](https://www.rfc-editor.org/rfc/rfc9221.html#section-5.4)）。チャットと購入はストリームで、位置と入力は DATAGRAM で送れば、暗号化と輻輳制御を 1 つにまとめたまま、それぞれに合った届け方を選べます。前回の WebRTC の DataChannel で、順序なし・再送なしのチャネルと、確実なチャネルを並べて開くのも同じ考え方です。

<Callout type="warn" title="確実な経路でも、二重に処理されない作りにしておく">
  購入の要求を確実な経路で送っていても、接続が切れて張り直したときに、クライアントは「さっきの要求は届いたのか」が分かりません。
  要求に一意な ID を付け、サーバが同じ ID を二度処理しないようにしておけば、安心して送り直せます。
  入力にシーケンス番号を振ったのと同じ発想です。
</Callout>

## まとめ

- 遅延がある以上、参加者は全員少しずつ違う時刻の世界を見ている。設計とは、誰が正しさを決め、何を送り、画面に何を出すかを選ぶこと
- 権威サーバは結果をサーバが計算するので改ざんに強く、見せるべきものだけを送れる。P2P で全員が同じ計算をする方式はサーバが要らないが、全員が世界の全体を持つ
- 決定論的ロックステップは入力だけを送り、全員の入力がそろうまで待つ。帯域は小さいが、一番遅い参加者に合わせて全員が待つ。入力遅延を片道の遅延より長くとれば待ちは消える。浮動小数点の計算順序、乱数の種、入力以外の情報源がデシンクを生む
- スナップショット方式では、他人を少し過去に描いて補間する。補間遅延を延ばすほど損失とジッタに強く滑らかになるが、見ている過去が深くなる。差分は相手が確認した基準から取り、失われたものは送り直さない
- 自分の操作はクライアントで予測し、サーバの確定状態に未確認の入力を積み直して照合する。照合しなければ予測はずれ続け、積み直さずに上書きすると引き戻される
- ラグ補償はサーバが撃った瞬間の過去に巻き戻して判定する。撃つ側は見えたとおりに当たるが、撃たれた側は隠れた後に撃たれる。巻き戻しには上限を設ける
- ロールバックは相手の入力を予測して進め、外れたら状態を読み戻して計算し直す。巻き戻しの深さは片道の遅延から入力遅延を引いた分で、深いほど計算の費用と見た目の破綻が増える
- 位置は再送しない経路で、購入やチャットは確実な経路で送る。QUIC ではストリームと DATAGRAM を 1 本の接続で使い分けられる

この回の参加者は、それぞれ自分の世界を持ちながら、権威やロールバックで最後には 1 つの正しい状態にそろえていました。次回は、複数の人が**同じ文書を同時に書き換える**場合を扱います。ゲームと違って、どちらの書き込みも捨てずに 1 つの結果へ合わせる必要があります。そのための 2 つの方法、OT と CRDT を見ます。
