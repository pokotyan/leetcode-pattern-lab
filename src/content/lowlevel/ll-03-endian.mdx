## 問題の所在

メモリのアドレスは 1 バイトごとに振られています。では、4 バイトの値をメモリに置くとき、どの順番で並べるのか。

`0x12345678` という値を、アドレス 100 番地から置くとします。候補は 2 つです。

```
ビッグエンディアン        リトルエンディアン
100: 12                  100: 78
101: 34                  101: 56
102: 56                  102: 34
103: 78                  103: 12
```

**ビッグエンディアン**は、上位バイト（big end）を小さいアドレスに置きます。人間が数字を書く順番と同じです。

**リトルエンディアン**は、下位バイト（little end）を小さいアドレスに置きます。逆順に見えます。

<Callout type="note" title="名前の由来">
  ガリヴァー旅行記に出てくる、ゆで卵をどちらの端から割るかで争う 2 つの派閥から取られています。
  1980 年に Danny Cohen が書いた記事でこの比喩が使われ、そのまま定着しました。
  「どちらでもいいことで延々と争っている」という含意が込められています。
</Callout>

## どちらにも言い分がある

**ビッグエンディアンの利点。** メモリダンプがそのまま読めます。`12 34 56 78` と並んでいれば `0x12345678` です。また、数値の大小比較を先頭バイトから順に見ていけるので、文字列比較と同じ関数で数値も比較できます。

**リトルエンディアンの利点。** 型を変えるときにアドレスが変わりません。

```
100: 78 56 34 12

ここを 1 バイトとして読むと   0x78
ここを 2 バイトとして読むと   0x5678
ここを 4 バイトとして読むと   0x12345678
```

**どの幅で読んでも、開始アドレスは同じ 100 番地です。** ビッグエンディアンだと、1 バイトとして読みたいなら 103 番地を指す必要があり、幅によって計算が変わります。

また、多倍長の足し算を下の桁から処理していくとき、アドレスを昇順にたどるだけで済みます。初期の 8 ビット CPU では、この単純さが実装コストに直結しました。

## 現実の分布

| 環境 | バイトオーダー |
| --- | --- |
| x86 / x86-64 | リトルエンディアン |
| ARM | 切り替え可能だが、実質リトルエンディアン |
| RISC-V | リトルエンディアン |
| 6502（ファミコン） | リトルエンディアン |
| 68000、SPARC、PowerPC（従来） | ビッグエンディアン |
| TCP/IP のヘッダ | **ビッグエンディアン** |
| JPEG、PNG のヘッダ | ビッグエンディアン |
| BMP、WAV | リトルエンディアン |

CPU はほぼリトルエンディアンで統一されつつあります。一方で、**ネットワークとファイル形式にはビッグエンディアンが残っています**。

ネットワークのほうを **ネットワークバイトオーダー** と呼びます。TCP/IP が設計された時代の主要な機種がビッグエンディアンだったため、そのまま規格になりました。今も変わっていません。

## つまり、変換が必要になる

x86 のマシンでネットワークに 16 ビットのポート番号を送るとき、そのまま書き出すと逆順になります。だから変換関数があります。

```c
#include <arpa/inet.h>

uint16_t port = 8080;
uint16_t on_wire = htons(port);   // host to network, short
```

| 関数 | 意味 |
| --- | --- |
| `htons` | host to network, 16 ビット |
| `htonl` | host to network, 32 ビット |
| `ntohs` | network to host, 16 ビット |
| `ntohl` | network to host, 32 ビット |

ビッグエンディアンのマシンでは、これらは何もしない関数になります。だから**自分の環境がどちらでも、常に呼んでおくのが正解**です。「うちは x86 だから」と省略したコードは、移植した瞬間に壊れます。

<Callout type="warn" title="バイナリファイルを自作するときの落とし穴">
  構造体をそのまま `write()` してファイルにするコードは、書いた機械と読む機械のエンディアンが違うと壊れます。
  さらに次回に出てくる**パディング**のせいで、コンパイラやオプションが違うだけでも壊れます。
  独自のバイナリ形式を作るなら、バイトオーダーとレイアウトを明示的に決めて、1 バイトずつ組み立てるべきです。
</Callout>

## 自分の環境を確かめる

C なら、共用体（union）を使うのが定番です。

```c
#include <stdio.h>

int main(void) {
    union { unsigned int i; unsigned char c[4]; } u = { .i = 0x12345678 };
    printf("%02x %02x %02x %02x\n", u.c[0], u.c[1], u.c[2], u.c[3]);
    return 0;
}
```

x86 で実行すると `78 56 34 12` と出ます。

コマンドラインなら、こちらのほうが手軽です。

```bash
printf '\x12\x34\x56\x78' | xxd -e -g4
# リトルエンディアン環境では 78563412 と表示される（-e は little-endian 表示）
```

Python では `struct` モジュールで明示的に指定できます。

```python
import struct
struct.pack('>I', 0x12345678)   # b'\x124Vx'      ビッグエンディアン
struct.pack('<I', 0x12345678)   # b'xV4\x12'      リトルエンディアン
struct.pack('=I', 0x12345678)   # 実行環境に従う
```

`>` と `<` を明示する癖をつけておくと、後で悩まずに済みます。

## ビット順はどうなのか

「エンディアンがあるならビットにも順番があるのでは」と思うところですが、**普通のプログラムからビットの順番は見えません**。メモリはバイト単位でしか読み書きできず、1 バイトの中でどちらが MSB かは CPU の中で一貫しているからです。

ビット順が問題になるのは、シリアル通信のように**線 1 本で 1 ビットずつ送る**場面です。UART は LSB から送り、I²C は MSB から送ります。ここではハードウェアの仕様として明記されています。

また、C のビットフィールドの並び順は処理系定義です。

```c
struct { unsigned a : 3; unsigned b : 5; } x;
```

`a` が上位 3 ビットになるか下位 3 ビットになるかは、コンパイラ次第です。**ビットフィールドでハードウェアのレジスタを表現するのは危険**で、シフトとマスクで明示的に書くほうが確実です。

## 中間のもの

歴史上は変わり種もありました。PDP-11 は 32 ビット値を「16 ビット単位ではビッグエンディアン、その中ではリトルエンディアン」という順（`34 12 78 56`）で並べました。**ミドルエンディアン**あるいは PDP エンディアンと呼ばれます。今は資料の中でしか見ません。

## まとめ

- エンディアンは「複数バイトの値をメモリに並べる順番」の約束
- リトルエンディアンは「幅を変えてもアドレスが同じ」、ビッグエンディアンは「ダンプが読める」
- CPU はほぼリトルエンディアンに収束、ネットワークと一部のファイル形式はビッグエンディアン
- 変換関数は、自分の環境がどちらでも常に呼ぶ
- 構造体をそのままファイルやネットワークに流さない

次は小数です。ここには、エンディアンよりもはるかに多くの人がつまずく罠があります。
