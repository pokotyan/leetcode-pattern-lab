## 1 台で足りなくなったら

前回の第 275 回では、ロックの範囲を絞り、トランザクションの中で外部の応答を待たないようにしました。ここまでの回で扱ってきたのは、すべて**1 台の中の**無駄を減らす改善です。それでも CPU が使い切られているなら、残る手段は台数を使うことです。

ISUCON では、多くの回で複数台のサーバが与えられますが、初期状態ではアプリケーション、データベース、nginx がすべて 1 台目で動いています。ISUCON9 予選の講評は、この点を次のように書いています（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。

> 1台よりも多くのインスタンスを使う場合は、最初の1台からリクエストを振り分ける必要があり、どうサーバを使い分けるかも問題を解く上で重要になります。

この回の問いは 3 つです。

1. **何を単位に分けるのか**（役割、エンドポイント、データ）
2. **どこから分けるのか**（どの資源が足りていないかで決まる）
3. **分けると何を払うのか**（ネットワークの往復、整合性、運用）

第 87 回ではロードバランサを、第 112 回ではシャーディングを、それぞれ仕組みとして扱いました。この回では、それらを「限られた台数をどう配るか」という判断の側から見ます。

## 分け方の種類

台数の使い方は、何を単位に分けるかで 4 つに整理できます。

| 単位 | 例 | 分けやすさ | 効くとき |
| --- | --- | --- | --- |
| 役割 | アプリと DB を別の台に、DNS と その DB を別の台に | 設定の変更だけで済むことが多い | 役割ごとの CPU の使い方が偏っているとき |
| 同じ役割の複製 | アプリを 2 台に置き、nginx から振り分ける | アプリが状態を持たなければ容易 | アプリの CPU が足りないとき |
| エンドポイント | ログイン専用の台、書き込み専用の台 | nginx の振り分けで済む | 特定のエンドポイントが重いとき |
| データ | テーブルごとに別の DB、ユーザーごとに別の DB | アプリの改修が要る | DB の CPU や書き込みが 1 台に収まらないとき |

上の行ほど手間が少なく、下の行ほど効果の上限が高い傾向があります。役割で分けるのは設定ファイルの接続先を書き換えるだけで済みますが、得られるのは「取り合いがなくなる」ぶんまでです。データで分けると、データベースの負荷そのものを複数台に割れますが、アプリケーションがどのデータをどの台に置いたかを知っている必要があります。

## どこから分けるか

### 足りない資源の側に台数を寄せる

分け方を決める前に、**どの資源が足りていないか**を見ます。`top` や `dstat` でプロセスごとの CPU を見れば、1 台目で何が CPU を使っているかが分かります。

ISUCON10 予選の講評は、データベースが足りない問題で、アプリケーションではなくデータベースに台数を寄せるよう勧めています（[ISUCON10 予選問題の解説と講評](https://isucon.net/archives/55025156.html)）。

> 今回の問題は DB の CPU が100%に張り付くケースが多いです。しかも1台分のスペックはそこまで強くありません。3台構成の際に App x2 / DB x1 にするのではなく、 App x1 / DB x2 にすることで負荷分散ができます。

データベースを 2 台にする方法として、講評はテーブルの単位で分けることを挙げています。

> 特に chair テーブルと estate テーブル間に JOIN が存在しないため、2つのデータベースに分割して、検索処理を分散させることが可能です。

ISUCON12 本選では、5 台のうち 4 台をデータベースに使う構成が想定されていました（[ISUCON12 本選問題の解説と講評](https://isucon.net/archives/56959385.html)）。

> アプリケーションの動作としては、Write heavyな仕組みです。

> それを踏まえると、サーバー構成は、App 1台、DB 4台が良いバランスだと思います。

書き込みはレプリカを足しても減らないので（第 107 回）、書き込みが多いならデータを分けるしかありません。講評は「４台でDBを水平分割すると、その効果が顕著に出ることを想定していました。」と続けています。

逆に、アプリケーションの CPU が足りない問題では、アプリケーションを複製します。ISUCON11 予選の講評は、1 台での改善を一通り終えた後に「1 台では限界があるため、複数台のサーバーを活用するようにします。」と書き、「一番変更が簡単な構成は、DB が 1 台でアプリケーションが 2 台の構成です。」と続けています（[ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)）。この問題では、椅子からの状態の送信を受けるエンドポイントだけを別の台に向けられる仕掛け（登録時の `target_base_url`）があり、講評は書き込みを受ける台とそれ以外の台に分ける方法を簡単なものとして挙げています。

### エンドポイントで分ける

特定のエンドポイントだけが重いなら、そのエンドポイントだけを別の台に送る方法があります。nginx の `location` ごとに `proxy_pass` の行き先を変えるだけで実現できます。

ISUCON9 予選では、ログインのパスワード照合（bcrypt）が最後まで重く残りました。講評は「ログインが他のアプリケーションの動作に影響を与えないよう、サーバインスタンスを追加してログイン処理専用とする方法も考えられたでしょう。」と書いています。ISUCON11 本選の講評も、3 台目の使い方の例として、お知らせ関連のエンドポイントの処理を 3 台目に切り出す構成を挙げ、「分かりやすく効果の高い改善だと想定していました。」としています（[ISUCON11 本選問題の解説と講評](https://isucon.net/archives/56163308.html)）。

エンドポイントで分けると、重い処理がほかの処理の CPU を奪わなくなります。全体の処理能力が同じでも、**軽いエンドポイントの応答時間が重いエンドポイントに引きずられなくなる**のが利点です。重い処理が何かは、次の第 277 回で扱います。

### 振り分けの設定

役割やエンドポイントで分けるときの入り口は、1 台目の nginx です。たとえばログインだけを 3 台目に送り、それ以外を 1 台目と 2 台目のアプリケーションに 1 対 2 の割合で送るなら、設定はおおよそ次のようになります。

```nginx
upstream app {
    server 127.0.0.1:8080 weight=1;
    server 192.168.0.12:8080 weight=2;  # CPU に余裕のある台に多く送る
    keepalive 32;
}

upstream login_only {
    server 192.168.0.13:8080;
    keepalive 8;
}

server {
    listen 80;

    location = /api/login {
        proxy_pass http://login_only;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }

    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
    }
}
```

`weight` は第 87 回で見た重み付きの振り分けです。`keepalive` と、`proxy_http_version 1.1` および空の `Connection` ヘッダの組は、nginx とアプリケーションの間の接続を使い回すための設定で、台を分けて通信がネットワークを通るようになると効き目が大きくなります（第 272 回）。

データベースを別の台に移すときは、アプリケーション側の接続先を書き換えるだけでなく、データベースの側でも外からの接続を受け付ける必要があります。配布された設定ファイルによっては、MySQL の `bind-address` が `127.0.0.1` に限られていたり、アプリケーション用のユーザーが `'isucon'@'localhost'` のように同じ台からの接続だけを許可されていたりします。移した後にアプリケーションが接続できずにエラーを返し続けると、ベンチマーカーの整合性検査で失敗するので、移す前に 1 台目から `mysql -h` で接続できることを確かめておきます。

### 参加記に見る順序

上位チームの参加記を見ると、台数を使う変更は、インデックスや N+1 の解消をある程度終えた中盤に入っていることが多いようです。

ISUCON13 で 2 位だった織時屋の参加記は、時刻ごとの点数と構成を記録しています（[ISUCON13で2位になりました(織時屋)](https://trap.jp/post/2049/)）。12:27 の 14,491 点から、アプリケーションのデータベースを 2 台目に移して 12:59 に 23,657 点になりました。その後、1 台目の CPU がまだ重いことから DNS と nginx・アプリケーションを分ける作業に入り、15:37 には「nginx+dns+db(isudns)/db(isupipe)/app構成」で 160,819 点（直前の基準は 14:31 の 78,472 点）を記録しています。ISUCON13 の講評自身も、DNS とその DB、nginx とアプリケーション、アプリケーションの DB を分ける 3 台構成の例を示しています（[ISUCON13 問題の解説と講評](https://isucon.net/archives/58001272.html)）。

ISUCON14 で 4 位だったチームの参加記では、スコアの推移の中に「10221: DBを別インスタンスに逃がす (0gajun)」という行があり、直前の 5,578 点からほぼ倍になっています（[ISUCON14 に「都営三田線~」で参加し4位になりました](https://zenn.dev/layerx/articles/3bd55b77e047c4)）。データベースに負荷が集中し続けると見て、早めに別の台へ移したと書かれています。

ISUCON11 本選の講評も、「実際の競技では、序盤から中盤にかけてアプリケーションとDBの2台構成に移行し、その後3台構成に移行したチームが多いと思います。」と振り返っています。

## 手元で確かめる：同じ台に置くか、分けるか

役割を分けると何が変わるのかを、Docker のコンテナで確かめました。`--cpuset-cpus` でコンテナが使える CPU を指定し、「同じ台に置く」を「同じ CPU を共有する」、「別の台に置く」を「別の CPU を使う」で模しています。

### 構成

アプリケーションは Go 1.24.6 で書いた小さな HTTP サーバです。1 リクエストごとに次の 2 つを行います。

- アプリケーションの CPU を使う処理として、SHA-256 を 25 万回繰り返す
- データベースの CPU を使う処理として、インデックスのない列で絞り込んで集計するクエリ（20 万行の表を全件走査する）を 2 回投げる

```go
b := appWork(work) // SHA-256 を work 回
for i := 0; i < scan; i++ {
	g := (int(b) + int(cnt.Add(1)) + i) % 1000
	conn := db
	if g%2 == 1 {
		conn = db2 // -dsn2 を与えたときだけ別の DB になる
	}
	conn.QueryRow("SELECT SUM(v) FROM items WHERE grp = ?", g).Scan(&c)
}
```

データベースは MySQL 8.4 です。負荷は、別の CPU に置いたコンテナから 8 並列で 15 秒間かけ続ける閉ループ（第 262 回）で与えました。比べた構成は次の 3 つです。

| 構成 | アプリ | DB | DB2 | 模しているもの |
| --- | --- | --- | --- | --- |
| A | CPU 0 | CPU 0 | なし | 1 台に全部載っている |
| B | CPU 0 | CPU 1 | なし | DB を別の台へ移した |
| C | CPU 0 | CPU 1 | CPU 2 | DB を 2 台にし、データを半分ずつ持たせた |

C の 2 台のデータベースには同じ表を入れ、集計の対象のグループの番号が偶数か奇数かで行き先を変えています。ISUCON10 予選のテーブル単位の分割や、第 112 回のシャーディングと同じく、「どのデータをどの台に聞くか」をアプリケーションが決める形です。

環境は Apple M1 Pro / macOS、Docker 29.4.0（OrbStack、Linux カーネル 7.0.14、仮想マシンの CPU は 8 個）です。この記事を書いている間、同じマシンでは別の重い処理が並行して動いていて、ロードアベレージは 15〜35 程度でした。`--cpuset-cpus` で CPU を指定しても、ほかのプロセスが同じ CPU に載ってくることは防げません。そこで A、B、C を順に 1 回ずつ走らせる組を繰り返しました。最初の 1 組は、直前の実験のコンテナが同じ名前で残っていて振り分けが混ざったため除き、残りの 5 組を載せます。

### 結果

```text
== A same-cpu r4
tune-275-app-A4 30.41% tune-275-db 72.38% tune-275-db2 0.47%
ok=285 err=0 rps=19.0 p50=417.58ms p90=504.82ms p99=703.52ms
== B split r4
tune-275-app-B4 57.48% tune-275-db 84.03% tune-275-db2 4.55%
ok=248 err=0 rps=16.5 p50=411.95ms p90=794.6ms p99=1.02863s
== C split+2db r4
tune-275-app-C4 67.98% tune-275-db 82.11% tune-275-db2 63.76%
ok=608 err=0 rps=40.5 p50=188.62ms p90=283.29ms p99=355.86ms
```

（1 行目は実験の途中で `docker stats` が示した CPU 使用率で、100% が CPU 1 個分。2 行目が負荷をかけた側の集計）

5 組の毎秒リクエスト数を並べます。

| 組 | A（同じ台） | B（DB を分離） | C（DB を 2 台） | B ÷ A | C ÷ A |
| --- | --- | --- | --- | --- | --- |
| 1 | 12.4 | 7.0 | 23.3 | 0.56 | 1.88 |
| 2 | 12.2 | 14.5 | 26.6 | 1.19 | 2.18 |
| 3 | 19.0 | 16.5 | 40.5 | 0.87 | 2.13 |
| 4 | 13.6 | 17.1 | 28.3 | 1.26 | 2.08 |
| 5 | 20.5 | 28.1 | 44.3 | 1.37 | 2.16 |

絶対値は組ごとに倍近く揺れていますが、同じ組の中の比は安定していました。**C は 5 組とも A の約 2 倍**になりました。一方、**B は A より速い組も遅い組もあり、はっきりした差になりませんでした。**

### なぜ DB を別の台に移しただけでは伸びなかったのか

構成 A の CPU 使用率を見ると、理由が分かります。1 個の CPU を共有したアプリケーションとデータベースの使用率は、どの組でもおおよそアプリケーションが 24〜34%、データベースが 66〜79% で、合わせて 100% 前後でした。**この処理では、CPU の 7 割をデータベースが使っていた**ということです。

データベースを別の CPU へ移すと、データベースが使える CPU は 1 個まるごとになります。ただ、取り戻せるのはアプリケーションが使っていた 3 割だけです。理屈の上で伸びるのは 1 ÷ 0.7 で約 1.4 倍が上限で、しかもその上限は、移した先の CPU にほかの負荷が乗らない場合の話です。構成 B のデータベースは 84〜102% と CPU を使い切っていて、アプリケーションは 30〜57% で余っていました。**ボトルネックはデータベースのまま**です。

構成 C でデータベースを 2 台にすると、それぞれの使用率は 64〜91% に分かれ、アプリケーションの使用率が 65〜74% に上がりました。データベース側の仕事が 2 台に割れたことで、ようやく全体の処理量が増えたのです。

<Callout type="note" title="分ける前に、比率を見る">
  役割を分けて得られる伸びは、**分けた相手が使っていた CPU の割合**で頭打ちになります。アプリケーションとデータベースが 3 対 7 で CPU を使っているなら、データベースを移すだけでは最大でも約 1.4 倍、アプリケーションを移すだけなら約 1.1 倍です。
  ISUCON10 予選の講評が「App x2 / DB x1」ではなく「App x1 / DB x2」を勧めたのは、データベースの CPU が張り付いている問題で、アプリケーションを増やしても足りない側の資源は増えないからです。
</Callout>

## 手元で確かめる：ネットワーク越しになるコスト

データベースを別の台に移すと、アプリケーションとデータベースの間の通信は、同じ台の中のループバックではなく、ネットワークを通るようになります。1 回のクエリにつき 1 往復以上の時間が必ずかかり、その時間は**クエリの回数に比例して**積み上がります。

これを確かめるために、アプリケーションのコンテナのネットワークインターフェースに `tc qdisc ... netem delay` で送信の遅延を足し、往復時間を人工的に延ばしました。1 リクエストで主キーによる検索を 0、1、10、50 回行い、並列度 1 で応答時間の中央値を測っています。

```bash
docker exec tune-275-app tc qdisc add dev eth0 root netem delay 5ms
```

遅延はアプリケーションの送信側だけに足しているので、データベースへの問い合わせ 1 往復ごとに 1 回加わります。ただし、負荷をかける側への HTTP の応答もこのインターフェースから出ていくため、各リクエストに 1 回ぶん余計に加わります。表の「検索 0 回」の行がその分です。

同時に、接続文字列だけを変えたアプリケーションをもう 1 つ動かしました。go-sql-driver/mysql の `interpolateParams=true` です。ドライバの README は、この設定について次のように説明しています（[go-sql-driver/mysql](https://github.com/go-sql-driver/mysql)）。

> If `interpolateParams` is true, placeholders (`?`) in calls to `db.Query()` and `db.Exec()` are interpolated into a single query string with given parameters. This reduces the number of roundtrips, since the driver has to prepare a statement, execute it with given parameters and close the statement again with `interpolateParams=false`.

既定の設定では、プレースホルダを含むクエリ 1 回ごとに、準備と実行の 2 往復がかかるということです。この設定の中身は第 269 回で扱いました。

### 結果

`ping` で測った往復時間は、遅延を足す前が平均 0.284 ms（最小 0.039 ms）、2 ms を足すと平均 2.516 ms、5 ms を足すと平均 6.516 ms でした。

```text
== app delay=5ms pk=50
ok=10 err=0 rps=1.7 p50=638.08ms p90=666.42ms p99=666.42ms
== appip delay=5ms pk=50
ok=18 err=0 rps=3.0 p50=346.22ms p90=384.88ms p99=411.6ms
```

応答時間の中央値をまとめます（「既定」は `interpolateParams=false`、「補間」は `true`）。

| 1 リクエストの検索回数 | 遅延なし・既定 | 遅延なし・補間 | +2 ms・既定 | +2 ms・補間 | +5 ms・既定 | +5 ms・補間 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | 0.21 ms | 0.83 ms | 3.05 ms | 3.54 ms | 7.78 ms | 6.48 ms |
| 1 | 2.09 ms | 0.65 ms | 10.74 ms | 6.58 ms | 21.35 ms | 14.65 ms |
| 10 | 6.98 ms | 3.92 ms | 101.98 ms | 71.64 ms | 175.58 ms | 79.29 ms |
| 50 | 45.48 ms | 10.07 ms | 468.75 ms | 269.56 ms | 638.08 ms | 346.22 ms |

5 ms を足した列で、検索 50 回の行から検索 0 回の行を引いて 50 で割ると、検索 1 回あたりの増分が出ます。補間では (346.22 − 6.48) ÷ 50 ≈ 6.8 ms で、`ping` の往復時間とほぼ同じ、つまり 1 往復です。既定では (638.08 − 7.78) ÷ 50 ≈ 12.6 ms で、2 往復ぶんになっています。

遅延を足していない列でも、検索 50 回の既定と補間で 4.5 倍の差が出ています。混雑したマシンの上では、往復のたびにスレッドの起床を待たされる時間が乗るからです。遅延の小さい環境でも、**往復の回数そのものが応答時間を決める**ことが分かります。

<Callout type="warn" title="同じ台の中では見えなかった N+1 が、分けた後に効いてくる">
  データベースが同じ台にあるうちは、1 往復は 0.1 ms 以下で済み、検索 50 回の N+1 も数 ms で終わります。データベースを別の台に移した途端、同じコードの応答時間が往復時間の 50 倍、既定の設定ならその 2 倍ずつ延びます。
  **台を分ける前に、往復の回数を減らしておく**（第 268 回の N+1 の解消、第 269 回の往復の削減）のが順序として安全です。分けた後に点数が下がったら、まずリクエストあたりのクエリの回数を疑います。
</Callout>

同じ理由で、台どうしの距離も重要です。ISUCON2026 で優勝した Typing Bears の参加記には、競技の開始直後に「10:10 にはリージョン間の RTT が約 100ms で、asia1 と asia2 の間だけ 0.4ms であることを測りました。」とあります（[ISUCON2026 で優勝しました（当日編）](https://zenn.dev/luvtechno/articles/isucon2026-competition-day)）。往復時間が 250 倍違う台が混ざっているなら、頻繁に通信する役割どうしは近い台に置く必要があります。**台を配る前に、台どうしの往復時間を測っておく**ということです。

## データで分ける

### テーブルの単位で分ける

ISUCON10 予選の chair と estate のように、**互いに JOIN しないテーブル**は、別のデータベースに置いてもアプリケーションの変更が小さくて済みます。接続を 2 つ持ち、テーブルごとに使う接続を選ぶだけです。上の実験の構成 C は、これを模したものでした。

第 112 回でいう垂直分割です。分けた後は、2 つのテーブルをまたぐトランザクションが張れなくなります。両方を同時に更新する処理があるなら、その処理の整合性をどう保つかを先に決めておく必要があります。

ISUCON11 本選の講評は、分けなかった場合の改善にも触れています。「DBを複数台に分割しなかった場合でも、JOIN相当の処理をアプリケーション側で行うことでDBの負荷を下げるなどの改善が可能です。」JOIN をアプリケーションに移すと、データベースの CPU をアプリケーションの CPU に付け替えることになり、台数を増やせるアプリケーションの側に負荷を寄せられます。

### ユーザーの単位で分ける

1 つのテーブルが 1 台に収まらないときは、行をユーザーやテナントの単位で複数のデータベースに分けます。第 112 回でいう水平分割（シャーディング）です。ISUCON12 本選の講評は、テーブルの設計そのものを水平分割しやすい形にしていたと書いています。

> 今回のテーブルも、水平分割がしやすい様なテーブル設計にしていました。

水平分割で問題になるのが、第 112 回でも見た ID の採番です。データベースごとに `AUTO_INCREMENT` で採番すると、別のデータベースと値が重なります。講評は、アプリケーションの側で採番することを想定していたうえで、次の注意を付けています。

> ただし、SnowflakeIDをそのまま利用すると、除算した余りで水平分割したDBを決める、というロジックと相性が悪いです。

Snowflake 形式の ID は上位の桁に時刻を、下位の桁に同じ時刻の中での連番を持ちます。生成の頻度が低いと連番はほとんど 0 のままなので、下位の桁の余りで振り分けると特定のデータベースに寄ってしまいます。講評は「そのため、振り分けに使用する桁（下一桁）は、乱数で生成するなど工夫が必要になります。」と続けています。

ISUCON12 予選も、テナントごとに SQLite のファイルを持つ構成で、データの単位で分ける問題でした。講評は「SQLiteのままで複数台に分散するためには、リクエストをテナント単位でそのテナントのデータベースファイルが存在しているホストに適切に振り分ける必要があります。」と書き、多くのチームが取った方法として MySQL への移行を挙げています。「MySQLへの移行に成功すると、アプリケーションサーバー2台とMySQLサーバー1台など、複数台構成によって性能を伸ばすことが容易になります。」（[ISUCON12 予選問題の解説と講評](https://isucon.net/archives/56850281.html)）。データをどの台に置いたかをアプリケーションが知っていなければならない構成から、置き場所を 1 か所に集める構成に戻したことで、アプリケーションを自由に複製できるようになった、という見方ができます。

## 台ごとに性能が違う

ここまでは、どの台も同じ性能だという前提で話してきました。ISUCON10 本選では、この前提が崩されていました（[ISUCON10 本選問題の解説と講評](https://isucon.net/archives/55140539.html)）。

> 実選手に対して、特にスペックはアナウンスしませんでしたが、実はこの3台はそれぞれ異なるスペックを有していました。

講評によれば、3 台はそれぞれ「1 GB RAM, 2 vCPUs」「2 GB RAM, 2 vCPUs」「1 GB RAM, 4 vCPUs」でした。メモリの多い台にはデータベース、CPU の多い台には計算の重いアプリケーション、というように、役割と台の特性を合わせる必要があります。講評に載っている作問者側の解答例も、2 GB の台に MySQL と Redis を、4 vCPU の台にスコアに寄与する処理を置いています。

本番のクラウドでも、台ごとの性能が揃っているとは限りません。インスタンスの種類を混ぜて使うとき、同じ種類でも世代が違うとき、別の利用者と物理的な資源を共有しているときには、同じ設定の台でも処理能力が変わります。**最初に `nproc` と `free` で各台の資源を確かめ、ベンチマークで台ごとの処理能力を測ってから配る**のが確実です。

## 本番で台数を使うときに考えること

ISUCON の台数の使い方は、本番のスケールアウトとそのまま重なる部分と、本番では別の考慮が要る部分があります。

| 論点 | ISUCON | 本番 |
| --- | --- | --- |
| 分ける動機 | 決まった台数の中で CPU を使い切る | 負荷の増加、障害の影響範囲、チームの分担 |
| 状態の置き場所 | オンメモリキャッシュやファイルを 1 台に寄せてもよい | アプリケーションの台は使い捨てにし、状態は共有の場所へ置く |
| 台が止まったとき | 再起動試験で戻ればよい | 1 台が止まっても続けられる冗長性が要る |
| 往復時間 | 同じネットワークの中で数百 µs 程度 | AZ やリージョンをまたぐと桁が変わり、通信量に料金がかかることもある |
| 分ける手間 | 数時間で戻せないなら分けない | 移行の計画、データの分け直し（第 112 回）、監視の追加 |

特に、**アプリケーションが状態を持っているかどうか**は、台数を使う前に確かめておく必要があります。第 270 回で見たオンメモリキャッシュ、ローカルのファイルに書いた画像、プロセスの中に持ったセッションは、アプリケーションを 2 台にした途端に台ごとに食い違います。ISUCON でも、キャッシュを入れた後でアプリケーションを複製すると、片方の台の更新がもう片方に届かずに整合性の検査で失敗します。状態を持つ処理だけを 1 台に集める（エンドポイントで分ける）、共有のキャッシュサーバに移す、のどちらかを選びます。

台数を増やすことは、壊れうる部品を増やすことでもあります。第 87 回で見たヘルスチェックと切り離しの仕組みがないと、1 台の障害が全体の障害になります。台を分けるのは、**1 台の中の無駄を減らし、往復の回数を減らし、状態の置き場所を決めた後**にするのが、ISUCON でも本番でも安全な順序です。

データベースを分け、台数を使い切ると、多くの場合ボトルネックはアプリケーションの CPU に移ります。次の第 277 回では、パスワードのハッシュ、毎回計算している署名、JSON の変換、外部コマンドの起動、GC など、アプリケーションの CPU を使っているものを実測し、どこから削るかを見ます。

## まとめ

- 1 台の中の改善を終えた後の手段が台数を使うこと。分ける単位は、役割、同じ役割の複製、エンドポイント、データの 4 つ
- 分け方は、足りない資源の側に台数を寄せて決める。DB の CPU が張り付くなら、アプリではなく DB を増やす（ISUCON10 予選の App x1 / DB x2、ISUCON12 本選の App 1 台 / DB 4 台）
- 役割を分けて得られる伸びは、分けた相手が使っていた CPU の割合で頭打ちになる。実測では DB が CPU の 7 割を使っていたため、DB を別の CPU に移すだけでははっきり伸びず、DB を 2 台にすると約 2 倍になった
- 特定のエンドポイントが重いなら、そのエンドポイントだけを別の台に送る。軽いエンドポイントの応答時間が守られる
- DB を別の台に移すと、クエリ 1 回ごとに往復時間がかかる。実測では、往復時間を約 6.5 ms にした状態で、検索 1 回あたりの増分は補間ありで約 6.8 ms、既定の設定では約 12.6 ms（2 往復）だった
- 台を分ける前に N+1 と往復の回数を減らしておく。台どうしの往復時間も先に測る
- JOIN しないテーブルはテーブルの単位で別の DB に分けやすい。行をユーザーの単位で分けるときは、ID の採番と振り分けの桁に注意する
- 台ごとの性能が違うことがある。資源を確かめ、役割と台の特性を合わせて配る
- アプリケーションを複製する前に、状態（オンメモリキャッシュ、ファイル、セッション）の置き場所を決める
