## 書き込みは、すぐには届かない

入れ替わりの一番大きな原因は、第 12 回のアウトオブオーダ実行そのものより、**store buffer** という小さな待ち行列です。

```
      コア 0                      コア 1
 ┌──────────────┐           ┌──────────────┐
 │  実行ユニット   │           │  実行ユニット   │
 │      │ 書く    │           │      │ 書く    │
 │      ▼        │           │      ▼        │
 │ store buffer  │           │ store buffer  │
 │  [x = 1]      │           │  [y = 1]      │
 │      │ あとで   │           │      │ あとで   │
 └──────┼───────┘           └──────┼───────┘
        ▼                          ▼
 ┌─────────────────────────────────────────┐
 │  L1 / L2 / L3（コヒーレンシで一致している） │
 └─────────────────────────────────────────┘
```

書き込み命令は、値をいきなりキャッシュに書くのではなく、まず自分のコアの store buffer に積みます。キャッシュラインの所有権を取ってくる（第 15 回の MESI で、他のコアの写しを無効化する）には時間がかかるので、**それを待たずに次の命令へ進む**ためです。

store buffer の中身は、**自分のコアからは見えますが、他のコアからはまだ見えません**。キャッシュに書き出されて初めて、コヒーレンシの世界に入ります。

これだけで、直感に反する結果が生まれます。

## 実験: 2 つのスレッドが、両方 0 を読む

次のプログラムを考えます。`x` と `y` は最初 0 です。

```c
// スレッド 1           // スレッド 2
x = 1;                  y = 1;
r1 = y;                 r2 = x;
```

どう並べて実行しても、`r1` と `r2` の少なくとも片方は 1 になるはずです。先に走った側の書き込みを、後の側が読むからです。

ところが、**両方 0** になることがあります。

1. スレッド 1 が `x = 1` を store buffer に積む。まだ誰にも見えない
2. スレッド 2 が `y = 1` を store buffer に積む。まだ誰にも見えない
3. スレッド 1 が `y` を読む。キャッシュには 0 しかない
4. スレッド 2 が `x` を読む。キャッシュには 0 しかない

書き込みの後の読み込みが、**書き込みより先に済んでしまった**のと同じ結果です。

実際に試しました。C11 のアトミック変数で上のコードを書き、100 万回繰り返して「両方 0」の回数を数えています（Apple Silicon 上の Docker、arm64 の Linux）。

| 順序指定 | 両方 0 になった回数 |
| --- | --- |
| `memory_order_relaxed` | 995,094 / 1,000,000 |
| `memory_order_seq_cst` | 0 / 1,000,000 |

`relaxed` では、ほぼ毎回起きています。割合は環境やタイミングで大きく変わりますが、**起きるかどうか**は変わりません。`seq_cst` にすると、ぴたりと止まります。

<Callout type="note" title="この入れ替わりは x86 でも起きる">
  x86 は順序が強いと第 37 回で書きましたが、この例（書き込みの後の読み込み）だけは x86 でも起きます。
  store buffer は x86 にもあるからです。
  x86 が禁じているのは、それ以外の入れ替わりです。
</Callout>

## 4 種類の入れ替わり

メモリ操作の組み合わせは 4 通りあります。「前の操作」が「後の操作」より後に見えてよいか、で整理できます。

| 前 → 後 | x86-64（TSO） | ARM64 / RISC-V（弱い） |
| --- | --- | --- |
| 読み → 読み | 入れ替わらない | 入れ替わりうる |
| 読み → 書き | 入れ替わらない | 入れ替わりうる |
| 書き → 書き | 入れ替わらない | 入れ替わりうる |
| 書き → 読み | **入れ替わりうる** | 入れ替わりうる |

x86 のモデルは **TSO**（Total Store Order）と呼ばれます。「書き込みはすべてのコアから同じ順番で見える。ただし自分の store buffer の分だけ遅れる」というモデルで、ほぼ上の図そのものです。

ARM は、4 通りすべてを許します。store buffer に加えて、読み込みの先回りや、書き込みを別々のキャッシュラインへ順不同で出すことも許しているためです。その代わり、回路を単純にでき、電力も抑えられます。

もう 1 つの典型例を見ます。

```c
// スレッド 1           // スレッド 2
data = 1;               r1 = flag;
flag = 1;               r2 = data;
```

`r1 == 1 && r2 == 0`（旗は見えたのにデータが古い）は、x86 では起きません。ARM では**許されています**。書き → 書き、または読み → 読みのどちらかが入れ替われば起きるからです。

<Callout type="warn" title="起きなかったことは、保証ではない">
  同じ環境でこちらも 100 万回試しましたが、`relaxed` でも 1 回も起きませんでした。
  ARM のアーキテクチャが許していても、特定の CPU の実装がたまたまそうしないことはあります。
  **テストで出ないことは、正しいことの証明になりません**。
  次の世代の CPU、別のメーカーの ARM、あるいはコンパイラの最適化で、突然出るようになります。
</Callout>

<Callout type="tip" title="Apple Silicon は x86 のふりができる">
  Apple の M シリーズには、スレッド単位で TSO に切り替える仕組みがあります。
  Rosetta 2 は x86 のプログラムをこのモードで動かすことで、
  変換した機械語にバリアを大量に挟まずに済ませています（[ScienceDirect](https://www.sciencedirect.com/science/article/pii/S1383762124000390)）。
  同じ論文では、TSO で動かすと平均で約 9% 遅くなったと報告されています。
  順序の強さは、タダではありません。
</Callout>

## 言語が間に立つ

ハードウェアのモデルは CPU ごとに違い、しかも**コンパイラも**入れ替えます。プログラマがその両方を意識して書くのは無理です。

そこで、各言語は自分の **メモリモデル** を定め、「このルールで書けば、どの CPU でも同じ意味になる」と約束します。C / C++ は C11 / C++11 で、Java は Java 5（JSR-133）で、Go は 2022 年の改訂でそれを明文化しました。

その中心にある約束が **DRF-SC** です。

> データ競合（data race）のないプログラムは、逐次一貫（sequentially consistent）に振る舞う。

逐次一貫とは、「すべてのスレッドの操作を、何らかの 1 本の順番に並べて、その順に実行したのと同じ結果になる」ということです。入れ替わりが一切ない、直感どおりの世界です。

つまり、**データ競合さえ無くせば、store buffer も ARM の弱さも考えなくてよい**。Go の改訂でも、この形の保証を C、C++、Java、JavaScript、Rust、Swift と揃えることが明記されています（[The Go Memory Model](https://go.dev/ref/mem)、[Russ Cox による解説](https://research.swtch.com/gomm)）。

### データ競合とは

2 つのスレッドが**同じ場所**に触り、少なくとも一方が**書き込み**で、その 2 つの間に **happens-before の関係がない**こと。ただし、アトミック変数への操作は競合に数えません。

### happens-before

「A が B より前に起きたと保証される」という関係です。次の 2 つから作られ、推移的につながります。

- **同じスレッドの中**では、プログラムに書いた順
- **`release` の書き込みを、`acquire` の読み込みが読んだ**とき、その書き込みはその読み込みより前（これを synchronizes-with と呼びます）

```
スレッド 1                         スレッド 2
data = 42;          ─┐
                     │ プログラム順
flag.store(1, release) ──synchronizes-with──▶ flag.load(acquire) == 1
                                                     │ プログラム順
                                               print(data);   // 必ず 42
```

`data = 42` から `print(data)` まで、矢印をたどって行けます。だから競合ではなく、42 が見えることが保証されます。第 37 回の「`release` で書き、`acquire` で読む」は、この矢印を 1 本張る操作だったわけです。

ミューテックスも同じです。`unlock` は release、次の `lock` は acquire として働き、ロックで守った区間どうしの間に矢印を張ります。

## データ競合があると、何が起きるか

言語によって扱いが違います。

| 言語 | データ競合があるとき |
| --- | --- |
| C / C++ | **未定義動作**。何が起きても規格違反ではない |
| Java | 型安全は守られる。ただし、見える値の順番はほとんど保証されない |
| Go | 1 ワードの値なら、どれかの書き込みの値が見える。複数ワードの値（インタフェース、スライス、文字列、マップ）は、（ポインタ、長さ）の組が食い違って**任意のメモリ破壊**に至りうる（[The Go Memory Model](https://go.dev/ref/mem)） |

C / C++ の「未定義動作」は、脅しではありません。コンパイラは「データ競合は無い」と仮定して最適化します。

```c
bool stop = false;          // アトミックではない

void worker(void) {
    while (!stop) {         // ループの中で stop を書き換える人はいない
        do_work();          // （と、コンパイラには見える）
    }
}
```

別のスレッドが `stop = true` を書いても、このループは止まらないことがあります。コンパイラが「ループの中で `stop` は変わらない」と判断し、**読み込みをループの外に出して 1 回だけにする**ことが許されるからです。ハードウェアの入れ替わり以前の問題です。`atomic_bool` にすれば、毎回読むことが保証されます。

## 機械語に落とすと

順序指定が、実際にどの命令になるかを見ます。GCC（`-O2`）で同じ C のコードを 2 つのアーキテクチャ向けにコンパイルした結果です。

| 操作 | x86-64 | ARM64 |
| --- | --- | --- |
| 書き込み `relaxed` | `mov` | `str` |
| 書き込み `release` | `mov` | `stlr` |
| 書き込み `seq_cst` | **`xchg`** | `stlr` |
| 読み込み `acquire` | `mov` | `ldar` |
| 読み込み `seq_cst` | `mov` | `ldar` |

いくつか読み取れることがあります。

**x86 では、release と acquire がタダです。** TSO がもともと書き → 書き、読み → 読みの順序を守っているので、普通の `mov` で足ります。

**x86 の `seq_cst` の書き込みだけが高い。** x86 で唯一許されている入れ替わり（書き → 読み）を止めるには、store buffer を空にする必要があります。`xchg` はそのための命令で、先ほどの「両方 0」の実験が止まったのはこれのおかげです。

**ARM では専用の命令を使います。** `stlr`（store-release）と `ldar`（load-acquire）は、ARMv8 がこの用途のために用意した命令で、全体を止めるフェンス（`dmb`）より軽く済みます。

この対応表は、各アーキテクチャについて研究者がまとめたものが公開されています（[C/C++11 mappings to processors](https://www.cl.cam.ac.uk/~pes20/cpp/cpp0xmappings.html)）。

<Callout type="note" title="x86 で動いたコードが ARM で壊れる理由">
  x86 では `relaxed` と `release` が同じ `mov` になります。
  つまり、`release` にすべきところを `relaxed` と書き間違えても、**x86 では何も変わりません**。
  同じコードを ARM でビルドすると、`stlr` になるべき命令が `str` になり、初めて差が出ます。
  第 37 回で触れた「Apple Silicon への移行で見つかったバグ」の多くは、この形です。
</Callout>

## 古典的な罠: double-checked locking

遅延初期化を速くしようとして、ロックを取る前に一度確認する書き方です。

```c
Singleton *instance = NULL;          // アトミックではない

Singleton *get(void) {
    if (instance == NULL) {          // (1) ロックなしで確認
        lock(&m);
        if (instance == NULL) {
            instance = new_singleton();   // (2) 確保 + 初期化 + 代入
        }
        unlock(&m);
    }
    return instance;
}
```

(1) の読み込みは、ロックの外にあるので (2) の書き込みと happens-before の関係がありません。データ競合です。

実際の失敗の形は、「`instance` への代入が、初期化の書き込みより先に他のスレッドに見える」ことです。別のスレッドは `NULL` でない `instance` を受け取り、**まだ初期化されていないメモリ**を読みます。前の節の「旗は見えたのにデータが古い」と同じ形です。

直し方は 2 つあります。

- `instance` をアトミックにして、代入を `release`、(1) の読み込みを `acquire` にする
- 言語が用意している一度だけの初期化（C の `call_once`、Go の `sync.Once`、C++ の関数内 `static`）を使う

普通は後者を選びます。**同期の部品を自作しない**のが、この回のいちばん実用的な結論です。

## まとめ

- 入れ替わりの主因は store buffer。書き込みは自分のコアにしか見えない時間がある
- 書き込みの後の読み込みは、x86 でも入れ替わる。実測で 100 万回中 99 万回起きた
- ARM は 4 通りの入れ替わりをすべて許す。テストで出ないことは保証ではない
- 言語のメモリモデルは DRF-SC を約束する。データ競合を無くせば、直感どおりに動く
- happens-before は、プログラム順と「release を acquire が読む」の 2 種類の矢印でできている
- C / C++ のデータ競合は未定義動作。コンパイラは読み込みを消したり移したりする
- x86 の release / acquire はタダで、seq_cst の書き込みだけ `xchg` が要る。ARM は `stlr` / `ldar`
- double-checked locking は競合。一度だけの初期化は言語の部品を使う
