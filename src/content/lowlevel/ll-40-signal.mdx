## 番号だけが届く

**シグナル**は、プロセスに対する非同期の通知です。届くのは**番号だけ**で、データは付いていません。

```bash
kill -TERM 1234        # プロセス 1234 に SIGTERM を送る
kill -9 1234           # SIGKILL（番号 9）
kill -l                # 一覧
```

プロセスは、シグナルごとに次のいずれかを設定できます。

- **既定の動作に任せる**（多くは終了）
- **無視する**
- **ハンドラを登録して、独自の処理をする**

シグナルが届くと、実行中の処理が**どこであっても中断され**、ハンドラが呼ばれます。終わったら元の場所に戻ります。第 13 回で見た割り込みの、ソフトウェア版と考えられます。

## 主なシグナル

| 番号 | 名前 | 既定動作 | 発生する場面 |
| --- | --- | --- | --- |
| 2 | **SIGINT** | 終了 | Ctrl+C |
| 3 | SIGQUIT | 終了 + core | Ctrl+\\ |
| 9 | **SIGKILL** | 終了 | **捕捉も無視もできない** |
| 11 | **SIGSEGV** | 終了 + core | 不正なメモリアクセス |
| 13 | **SIGPIPE** | 終了 | 読み手のいないパイプへの書き込み |
| 15 | **SIGTERM** | 終了 | `kill` の既定。終了の要請 |
| 17 | SIGCHLD | 無視 | 子プロセスの状態変化 |
| 18/19 | SIGCONT / SIGSTOP | 再開 / 停止 | Ctrl+Z は SIGTSTP |

**SIGKILL と SIGSTOP だけは、捕捉も無視もできません。** これがあるから、どんなプログラムでも確実に止められます（第 29 回で触れた D 状態は例外で、カーネル内で中断できないため SIGKILL も効きません）。

<Callout type="tip" title="SIGTERM と SIGKILL の使い分け">
  **SIGTERM が先です。**
  プログラムに後始末（ファイルを閉じる、バッファを書き出す、接続を切る）の機会を与えます。

  応答がない場合の最終手段が SIGKILL です。カーネルが強制的に終了させるため、
  **後始末は一切行われません**。データの破損につながる可能性があります。

  Docker の `docker stop` や Kubernetes の Pod 終了も、
  SIGTERM を送って一定時間待ち、それでも終わらなければ SIGKILL、という手順です。
</Callout>

## Ctrl+C が効く仕組み

端末で Ctrl+C を押すと、端末ドライバがそれを検出し、**フォアグラウンドのプロセスグループ全体**に SIGINT を送ります。

「プロセスグループ」が単位であることが重要です。パイプで繋いだ複数のコマンドが同時に止まるのは、これらが同じプロセスグループに属しているからです。

```bash
ps -o pid,pgid,comm
```

## SIGPIPE の罠

読み手のいないパイプやソケットに書き込むと、**SIGPIPE が届いてプロセスが終了します**。

```bash
yes | head -1
# head が終了 → yes が書き込む → SIGPIPE → yes が終了
```

コマンドラインではこれが望ましい動作です。しかしサーバでは困ります。クライアントが切断しただけでサーバが落ちてしまいます。

対策は 2 つです。

```c
signal(SIGPIPE, SIG_IGN);            // 無視する。write が EPIPE を返すようになる
send(fd, buf, len, MSG_NOSIGNAL);    // この送信だけシグナルを出さない
```

多くのネットワークライブラリは、初期化時に SIGPIPE を無視に設定しています。

## ハンドラの中でできること

これがシグナルの最も厄介な点です。

**ハンドラは、実行中のどの命令の直後にでも割り込みます。** `malloc` の途中かもしれません。`printf` がバッファを操作している最中かもしれません。

そこでハンドラが `malloc` を呼ぶと、**内部のデータ構造が中途半端な状態で再度触られ、壊れます**。デッドロックすることもあります。

したがって、ハンドラの中で呼んでよい関数は **async-signal-safe** と定められたものだけです。

| 呼んでよい | 呼んではいけない |
| --- | --- |
| `write` | **`printf`** |
| `_exit` | `exit` |
| `signal` | **`malloc` / `free`** |
| `kill` | `pthread_mutex_lock` |
| `sigaction` | ほぼすべての標準ライブラリ関数 |

```bash
man 7 signal-safety        # 完全な一覧
```

<Callout type="warn" title="printf をハンドラで呼んではいけない">
  デバッグのために書きたくなりますが、`printf` は内部でバッファとロックを使います。
  通常の `printf` の途中で割り込むと、そのロックを二重に取ろうとしてデッドロックします。
  **稀にしか起きないので、テストでは見つかりません。**

  どうしても出力したいなら `write(2, "msg\n", 4)` を使います。
</Callout>

## 安全な書き方

### フラグを立てるだけ

ハンドラでは変数を 1 つ立てるだけにし、実際の処理はメインループで行います。

```c
volatile sig_atomic_t should_stop = 0;

void handler(int sig) { should_stop = 1; }    // これだけ

int main(void) {
    signal(SIGTERM, handler);
    while (!should_stop) { do_work(); }
    cleanup();                                  // 安全な場所で後始末
}
```

`sig_atomic_t` は、中断されない単位で読み書きできることが保証された型です。`volatile` は、最適化でループ内の読み込みが消えるのを防ぎます。

### self-pipe

より汎用的な方法です。ハンドラでパイプに 1 バイト書き、メインループの `epoll` でそれを検出します。

```c
void handler(int sig) { write(pipe_fd[1], "x", 1); }    // write は安全
```

これにより、**シグナルをイベントループに統合できます**。

### signalfd

Linux では、シグナルを fd として受け取れます。

```c
sigset_t mask;
sigemptyset(&mask);
sigaddset(&mask, SIGTERM);
sigprocmask(SIG_BLOCK, &mask, NULL);    // 通常の配送をブロックする

int sfd = signalfd(-1, &mask, 0);
// sfd を epoll に登録すれば、他の fd と同じように扱える
```

**ハンドラがそもそも呼ばれないので、安全でない関数の問題が消えます。** 第 36 回で触れた「何でも fd にする」方針の恩恵です。

## マルチスレッドでの配送

プロセスに送られたシグナルは、**ブロックしていないスレッドのうち任意の 1 つ**に配送されます。どれが受け取るかは決まっていません。

実用的な定石は、

1. メインスレッドで、扱いたいシグナルを全スレッドでブロックする
2. 専用のスレッドを 1 つ用意し、`sigwait` で待つ
3. そのスレッドだけがシグナルを処理する

これで配送先が確定します。Go のランタイムは同様のことを内部で行い、`signal.Notify` でチャネル経由の受信として提供しています。

## グレースフルシャットダウン

サーバでの実用的な終了処理です。

```c
// SIGTERM を受けたら
1. 新しい接続の受付をやめる（listen ソケットを閉じる）
2. 処理中のリクエストが終わるのを待つ（タイムアウト付き）
3. 接続を閉じ、バッファを書き出す
4. 終了する
```

Kubernetes では、この間に `preStop` フックとロードバランサからの切り離しが行われます。SIGTERM から SIGKILL までの猶予は `terminationGracePeriodSeconds`（既定 30 秒）で指定します。

**この猶予内に終わらないと、SIGKILL で強制終了されます。** 長時間のリクエストを扱うサービスでは、猶予期間の設定を見直す必要があります。

## まとめ

- シグナルは番号だけの非同期通知。ハンドラはどの命令の直後にでも割り込む
- SIGKILL と SIGSTOP は捕捉も無視もできない
- SIGTERM は終了の要請、SIGKILL は強制終了。後始末の有無が違う
- SIGPIPE はサーバでは無視するのが基本
- ハンドラで呼んでよいのは async-signal-safe な関数だけ。`printf` は不可
- フラグを立てるだけ、self-pipe、signalfd のいずれかで安全に扱う
- マルチスレッドでは専用スレッドで `sigwait` するのが定石
