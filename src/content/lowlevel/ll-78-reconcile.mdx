## この章で見るもの

第 13 章では、コンテナを 1 台のマシンで作って動かすところまで来ました。第 74 回の最後で、Compose がやらないこととして次の 3 つを挙げました。

- 複数のマシンにコンテナを振り分ける
- マシンが落ちたら、別のマシンで立て直す
- 負荷に応じて数を増減させる

この章では、これを引き受ける仕組みを見ます。題材には Kubernetes を使いますが、目的は機能を覚えることではありません。**何百台ものマシンの上で、何千ものコンテナを「書いたとおり」に保ち続ける**には何が要るのか。そして、それがこれまでの章の何の上に乗っているのかを見ます。

「クラウドネイティブ」という言葉は幅が広く、定義も一定しません。この章では、**使い捨てられる小さな単位を、宣言した状態に向けて機械が保ち続ける**という設計の考え方、という意味で使います。

## 命令するか、宣言するか

3 つのコンテナを動かしたいとします。やり方は 2 つあります。

**命令型**：「コンテナを 3 つ起動せよ」という手順を実行する。

**宣言型**：「コンテナが 3 つ動いている」という状態を書いておく。

1 回だけ実行するなら、どちらでも結果は同じです。違いが出るのは、**そのあと何かが起きたとき**です。

| 起きたこと | 命令型 | 宣言型 |
| --- | --- | --- |
| 1 つがクラッシュした | 誰かが気づいて、もう一度起動を命令する | 「3 つのはずが 2 つ」という差が生まれ、機械が 1 つ足す |
| 同じ命令を 2 回実行した | 6 つになる | 3 つのまま |
| 途中でネットワークが切れた | どこまで実行されたか分からない | 次に見たときの差を埋めればよい |

命令は**変化**を伝えます。宣言は**結果**を伝えます。変化の列は、1 つでも取りこぼすと後の状態がすべてずれます。結果は、何度見直しても同じものを指します。

「同じ操作を何度繰り返しても結果が変わらない」という性質を **冪等性** と呼びます。宣言型の操作は、もともと冪等です。

## 調整ループ

宣言しただけでは何も動きません。書かれた状態と現実を見比べ、差を埋める誰かが要ります。この「誰か」を **コントローラ** と呼び、それがやっている繰り返しを **調整ループ**（reconcile loop）と呼びます。

```
         ┌───────────────────────────────┐
         │                               │
         ▼                               │
  あるべき状態を読む                       │
         │                               │
  現在の状態を観察する                     │
         │                               │
  差はあるか ── ない ──→ 待つ ─────────────┤
         │                               │
        ある                              │
         │                               │
  差を縮める操作を 1 つ行う ─────────────────┘
```

Kubernetes の公式ドキュメントは、これを **サーモスタット** にたとえています（[Kubernetes](https://kubernetes.io/docs/concepts/architecture/controller/)）。

> 温度を設定することは、サーモスタットに**あるべき状態**を伝えることです。実際の室温が**現在の状態**です。サーモスタットは、機器を入れたり切ったりして、現在の状態をあるべき状態に近づけます。

ポイントは、サーモスタットが「何度上げろ」という命令を受け取らないことです。設定温度と室温だけを見て、そのとき必要な操作を決めます。窓が開いていようが、誰かがストーブを持ち込もうが、やることは同じです。

同じドキュメントは、さらに踏み込んだことを書いています。**クラスタは安定した状態に到達しないかもしれないが、コントローラが動いて有用な変更を加えられる限り、それは問題ではない**。障害は常に起きるものとして、それを修正し続けること自体を仕組みにしているわけです。

<Callout type="note" title="制御工学の言葉">
  あるべき値と測った値の差（偏差）を見て操作量を決める仕組みは、
  制御工学で **フィードバック制御** と呼ばれてきたものです。
  エアコン、自動車の速度制御、CPU の周波数制御と同じ構造です。
  第 86 回で見る自動の増減では、
  この「制御」としての性質（遅れ、行き過ぎ、振動）がそのまま問題になります。
</Callout>

## 変化を追うか、状態を見るか

調整ループの性質を、もう少し正確に言います。

第 45 回で、epoll の通知には 2 種類あると書きました。

- **レベルトリガ**：データがある限り、毎回通知される
- **エッジトリガ**：状態が変わった瞬間だけ通知される

エッジトリガは効率がよい代わりに、通知を 1 回取りこぼすと二度と気づけません。

コントローラの設計にも同じ区別があります。「Pod が 1 つ消えた」というイベント（エッジ）に反応して 1 つ足すのか、「今 2 つしかない」という状態（レベル）を見て 1 つ足すのか。

Kubernetes のコントローラは、**レベルで判断する**ように作られています。コントローラの設計指針は、シェルスクリプトと同じで、コントローラは**いつ止まっていて、いつ再開するか分からない**ものとして書け、と述べています（[kubernetes/community](https://github.com/kubernetes/community/blob/master/contributors/devel/sig-api-machinery/controllers.md)）。

止まっていた間のイベントは失われます。しかし状態は残っています。再開したときに状態を見直せば、やるべきことは分かります。

イベントは「そろそろ見直したほうがよい」という**合図**としてだけ使い、判断は必ず最新の状態から行う。これが、取りこぼしに強い理由です。さらに念のため、変化がなくても定期的に全体を見直す仕組み（resync）も用意されています。

## 状態を 1 か所に置く

調整ループが回るには、「あるべき状態」がどこかに書かれていなければなりません。Kubernetes では、それを **etcd** に置きます。公式ドキュメントの説明は「API サーバのすべてのデータを置く、一貫性があり可用性の高いキーバリューストア」です（[Kubernetes](https://kubernetes.io/docs/concepts/overview/components/)）。

なぜ 1 か所なのか。数十のコントローラ、数百のノードが、それぞれ別の記憶を持っていたら、誰の言う「あるべき状態」が正しいのか決められなくなります。**正しい答えは 1 つ、置き場所も 1 つ** にしておけば、全員がそこを見ればよい。

ただし、1 台のマシンに置けば、そのマシンが落ちたときにクラスタ全体が止まります。そこで etcd は、3 台や 5 台で同じデータを持ち、**Raft** で合意を取りながら書き込みます。過半数が生きていれば動き続けます。Raft の仕組みはシステム設計の読み物の
<a href={`${import.meta.env.BASE_URL}reading/consensus/`}>分散合意</a>で扱いました。

第 10 章で見たデータベースと、構造がよく似ています。第 59 回の NewSQL も、範囲ごとに Raft で合意を取っていました。**失ってはいけない、全員が同じものを見るべき状態**は、どこでも同じ道具で守られています。

<Callout type="warn" title="etcd は大きなデータベースではない">
  etcd に置くのは、クラスタの**設定と状態**です。
  アプリケーションのデータを置く場所ではありません。
  全ノードで合意を取りながら書くので、書き込みは速くありません。
  1 つの値の大きさや全体の容量にも上限があります。
  アプリケーションのデータベースは、別に用意します。
</Callout>

## 誰が何をしているか

状態の置き場所が 1 つに決まると、役割をきれいに分けられます。

```
            ┌──────────────┐
  kubectl ─→│ kube-apiserver│←─── 全員がここだけを通る
            └──────┬───────┘
                   │
                ┌──┴──┐
                │ etcd │  状態の置き場所（ここに直接触るのは API サーバだけ）
                └─────┘

   コントローラ群          スケジューラ           各ノードの kubelet
  「数が足りない」         「この Pod を         「自分に割り当てられた
    → Pod を作る           どのノードに」         Pod を実際に起動する」
```

| 部品 | 見ているもの | やること |
| --- | --- | --- |
| **kube-apiserver** | — | 読み書きの唯一の窓口。認証、検証、etcd への保存 |
| **コントローラ** | 「3 つのはず」と「今いくつ」 | 足りない Pod を作る、余った Pod を消す |
| **スケジューラ** | ノードが決まっていない Pod | どのノードに置くかを決め、書き込む |
| **kubelet** | 自分のノードに割り当てられた Pod | コンテナを実際に起動し、状態を報告する |

注目すべきは、**部品どうしが直接話さない**ことです。コントローラはスケジューラを呼びません。スケジューラは kubelet に命令しません。全員が API サーバを通して状態を読み、状態を書くだけです。

公式ドキュメントの Job コントローラの説明がそれをよく表しています。Job コントローラは自分では Pod もコンテナも動かさない。**API サーバに Pod を作れ、消せと伝えるだけ**だ、と（[Kubernetes](https://kubernetes.io/docs/concepts/architecture/controller/)）。

1 つの部品が落ちても、他の部品は動き続けます。戻ってきたら、状態を読み直して続きをやればよい。これは第 70 回で見た containerd と shim の分離と同じ発想の、もう一段大きな版です。

## 見張り続けるための仕組み: watch

コントローラは状態を「見る」と言いましたが、1 秒ごとに全 Pod の一覧を API サーバに問い合わせていたら、何千のコントローラとノードで API サーバが潰れます。

そこで **watch** という仕組みがあります。HTTP の GET に `?watch` を付けると、API サーバは応答を閉じずに、**変化があるたびに流し続けます**（[Kubernetes](https://kubernetes.io/docs/reference/using-api/api-concepts/)）。

```
GET /api/v1/namespaces/default/pods?watch=1&resourceVersion=10245

← {"type":"ADDED",    "object":{... "resourceVersion":"10246" ...}}
← {"type":"MODIFIED", "object":{... "resourceVersion":"10250" ...}}
← {"type":"DELETED",  "object":{... "resourceVersion":"10257" ...}}
   （接続は開いたまま）
```

**resourceVersion** は、状態の版番号です。「10245 より後の変化をくれ」と言えば、途中から続きを受け取れます。

実際のコントローラは、この仕組みの上に次のような層を重ねています。

1. 起動時に一覧を 1 回取る（list）
2. その版番号から watch を始め、手元のキャッシュを更新し続ける
3. 変化があった対象の名前を、作業の待ち行列に入れる
4. 待ち行列から取り出し、**キャッシュから最新の状態を読んで**調整する

4 番目が大事です。イベントの中身をそのまま使うのではなく、名前だけを受け取って、判断は最新の状態から行う。前の節の「イベントは合図、判断は状態から」を、そのまま実装しています。

第 45 回で見たとおり、「状態が変わったら知らせてもらう」のは、全部を見て回るより桁違いに安くなります。epoll が 1 万本のソケットで効いたのと同じ理由で、watch は何千のコントローラで効きます。

## 同時に書いたらどうなるか

API サーバには、多くの書き手がいます。コントローラ、スケジューラ、kubelet、人間。2 人が同じオブジェクトを同時に書き換えたらどうなるでしょうか。

第 37 回で見たロックを使う方法もありますが、クラスタ全体でロックを取り合うと遅くなり、ロックを持ったまま落ちたプロセスが全体を止めます。

Kubernetes は **楽観的並行性制御** を使います。

1. オブジェクトを読む。このとき resourceVersion も受け取る
2. 手元で書き換える
3. 「resourceVersion が 10250 のままなら、これで更新してくれ」と送る
4. 誰かが先に書き換えていて版が変わっていれば、**更新は拒否される**（409 Conflict）
5. 拒否されたら、読み直してやり直す

第 37 回の CAS（比較して交換）と同じ考え方です。「読んだときから変わっていなければ書く、変わっていたらやり直す」。衝突がまれなら、ロックより速く、誰かが落ちても全体が止まりません。

そして、調整ループはもともと「最新の状態を読んで差を埋める」ものなので、**やり直しても害がありません**。冪等性が、ここでも効いています。

## まとめ

- 命令は変化を、宣言は結果を伝える。宣言は冪等で、取りこぼしに強い
- コントローラは、あるべき状態と現在の状態の差を埋め続ける調整ループ
- イベントは合図にだけ使い、判断は最新の状態から行う（レベルトリガ）。止まっていても再開すれば追いつく
- 状態は etcd の 1 か所に置き、Raft で複製する。アプリのデータの置き場所ではない
- 部品どうしは直接話さず、API サーバを通して状態を読み書きするだけ
- watch と resourceVersion で、変化だけを受け取る。同時の書き込みは楽観的並行性制御で扱う

次は、この仕組みが扱う最小の単位を見ます。Kubernetes は、なぜコンテナを直接扱わず、Pod という単位を挟むのでしょうか。
