## 指紋は何を約束するのか

第 103 回で、暗号の部品が約束する性質を 4 つに分けました。機密性、完全性、真正性、否認防止です。この回はそのうち**完全性**（途中で書き換わっていないこと）と、**真正性**（確かにあの相手が出したこと）の入口を扱います。

使う部品は 2 つです。

- **ハッシュ関数**: 任意の長さのデータから、固定長の短い値（ダイジェスト）を作る。鍵を使わない
- **MAC**（Message Authentication Code、メッセージ認証符号）: **鍵**とデータから固定長の値（タグ）を作る。同じ鍵を持つ者だけが作れ、確かめられる

ダウンロードページに並ぶ `SHA256: 2cf24d...` も、API の要求に付ける `X-Signature: 98e7ff...` も、見た目は同じ 16 進の文字列です。しかし前者はハッシュ、後者はたいてい MAC で、**約束していることがまったく違います**。この回の目標は、その違いを言葉にできるようにすることです。

## ハッシュ関数の手触り

まず、実物を見ます。`hello` と、最後の 1 文字を 1 ビットだけ変えた `helln`（`o` は 0x6f、`n` は 0x6e）です。

```
$ printf 'hello' | openssl dgst -sha256
SHA2-256(stdin)= 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
$ printf 'helln' | openssl dgst -sha256
SHA2-256(stdin)= d1dd3e4f53afb65be5774853d60b74fa12c10b769c262165562c5287e6816e15
```

Python で違うビットを数えると、256 ビットのうち 128 ビット、ちょうど半分が変わっていました。

```
$ python3 avalanche.py
入力の違い: 1 ビット / 出力 256 ビット中 128 ビットが違う
```

入力のわずかな違いが出力全体に広がり、出力からは入力の手がかりが読み取れない。**良いハッシュ関数は、出力が乱数と見分けのつかないように振る舞います**。ただし乱数ではなく、同じ入力からは必ず同じ出力が出ます。この「決まっているのに予測できない」性質が、以下のすべての用途の土台です。

## 3 つの強さを分ける

「ハッシュが安全」と一口に言いますが、中身は 3 つの別々の要求です。出力を n ビットとします。

| 性質 | 攻撃者の課題 | 総当たりで要る手間 |
| --- | --- | --- |
| **原像耐性** | ダイジェスト h だけを見て、h になる入力を見つける | 約 2^n |
| **第 2 原像耐性** | 入力 m を与えられ、同じダイジェストになる**別の** m' を見つける | 約 2^n |
| **衝突耐性** | 同じダイジェストになる入力の組を、**何でもよいので 1 組**見つける | 約 2^(n/2) |

原像と第 2 原像は「狙った 1 つの値」に当てる課題です。衝突は、2 つとも自分で自由に選べます。この自由の差が、手間を **2^n から 2^(n/2) へ**、指数の半分まで下げます。

### 誕生日のパラドックス

理由は、クラスの中に誕生日が同じ 2 人がいる確率と同じです。**特定の日**が誕生日の人を探すには大勢が要りますが、**誰でもよいから 2 人が一致する**のは、23 人いれば確率が 5 割を超えます。人数 k に対して「組」の数は k(k-1)/2 と、2 乗で増えるからです。

ハッシュに当てはめると、ダイジェストを 2^(n/2) 個ほど集めれば、その中のどこかの 2 つが一致する見込みが高くなります。手元で、SHA-256 を 32 ビットに切り詰めた「弱いハッシュ」で確かめます。

```python
# birthday.py
import hashlib, os
def h32(data):
    return hashlib.sha256(data).digest()[:4]   # 32 ビットに切り詰める
seen = {}
tries = 0
while True:
    m = os.urandom(16)
    tries += 1
    d = h32(m)
    if d in seen and seen[d] != m:
        print(f"{tries} 個目で衝突: {seen[d].hex()} と {m.hex()} → {d.hex()}")
        break
    seen[d] = m
```

```
$ python3 birthday.py
123733 個目で衝突: 226602cc51f9cb61f7611398da629fd5 と c8ecdd843bcf7e4e44e18f41a99e8b75 → 83e66d8f
$ python3 birthday.py
114516 個目で衝突: a4cbc0d3ff3a8d542b999cb0e26654d8 と 39169d423fd99e462528417c006862e1 → d94442f5
$ python3 birthday.py
73272 個目で衝突: 8a51ee4b590b88f3c1a9163b88977401 と 1bcc9e2935164dedb43c756ad13f719b → e70646e9
```

32 ビットは約 43 億通りですが、衝突は 2^16 = 65,536 の数倍で見つかります。24 ビットに縮めて、「`hello` と同じ値になる別の入力」（第 2 原像）と比べると、差がはっきりします。

```
24 ビットの第 2 原像: 24290639 回     ← 2^24 ≒ 1,677 万の程度
24 ビットの衝突: 5327 回              ← 2^12 = 4,096 の程度
```

**強度は出力長の半分**、というのはこの意味です。SHA-256 の衝突耐性は 128 ビット相当で、これが「256 ビットの出力が要る」理由です。HMAC の仕様も、タグを切り詰めるなら**ハッシュの出力長の半分以上、かつ 80 ビット以上**にするよう勧めています（[RFC 2104 5](https://www.rfc-editor.org/rfc/rfc2104.html#section-5)）。

### 衝突が破れると何が困るのか

「狙った値に当てられないなら、衝突くらい見つかってもよいのでは」と思えます。困るのは、**署名がダイジェストに対して行われる**ときです（第 107 回で見ます）。攻撃者が「無害な文書」と「有害な文書」の衝突する組を作り、無害な方に署名をもらえば、その署名は有害な方にもそのまま通ります。

## MD5 と SHA-1 はどう破れたか

| 関数 | 出力 | 状況 |
| --- | --- | --- |
| MD5 | 128 ビット | 2004 年に衝突の組が発表された。今はノート PC で数秒〜1 分で衝突が作れる（[RFC 6151](https://www.rfc-editor.org/rfc/rfc6151.html)） |
| SHA-1 | 160 ビット | 2017 年に実際の衝突（SHAttered）。2020 年に選択プレフィックス衝突（SHA-1 is a Shambles） |
| SHA-2 | 224〜512 ビット | 実用的な攻撃は知られていない |

**SHAttered** は、2017 年 2 月 23 日に CWI Amsterdam と Google が公表した、SHA-1 の初めての実際の衝突です。約 900 京回（9×10^18）の SHA-1 計算、6,500 CPU 年と 110 GPU 年に相当する計算で、中身の違う 2 つの PDF を作りました（[shattered.io](https://shattered.io/)）。

2020 年の **SHA-1 is a Shambles** はさらに進んで、**選択プレフィックス衝突**を実現しました。先頭部分をそれぞれ自由に選んだ 2 つのデータの後ろに、細工したブロックを付けて衝突させるもので、GPU を借りて約 7.5 万ドルで計算し、PGP の信頼の網で他人の名前の鍵に第三者の署名を移し替えられることを示しました（[SHA-1 is a Shambles](https://sha-mbles.github.io/)）。

NIST は SHA-1 を 2030 年 12 月 31 日までに、残っているすべての用途から外すと発表し、できるだけ早く SHA-2 か SHA-3 に移るよう勧めています（[NIST 2022](https://www.nist.gov/news-events/news/2022/12/nist-retires-sha-1-cryptographic-algorithm)）。

### 手元で確かめる: SHAttered の 2 つの PDF

公開されている 2 つの PDF を落として比べます。

```
$ curl -sSfLO https://shattered.io/static/shattered-1.pdf
$ curl -sSfLO https://shattered.io/static/shattered-2.pdf
$ openssl dgst -sha1 shattered-*.pdf
SHA1(shattered-1.pdf)= 38762cf7f55934b34d179ae6a4c80cadccbb7f0a
SHA1(shattered-2.pdf)= 38762cf7f55934b34d179ae6a4c80cadccbb7f0a
$ openssl dgst -sha256 shattered-*.pdf
SHA2-256(shattered-1.pdf)= 2bb787a73e37352f92383abe7e2902936d1059ad9f1ba6daaa9c1e58ee6970d0
SHA2-256(shattered-2.pdf)= d4488775d29bdef7993367d541064dbdda50d383f89f0aa13a6ff2e0894ba5ff
$ cmp -l shattered-1.pdf shattered-2.pdf | wc -l
      62
```

大きさは同じ 422,435 バイトで、違うのは 193 バイト目から始まる 62 バイトだけです。SHA-1 は一致し、SHA-256 はまったく違います。

<Callout type="warn" title="よくある誤解: MD5 が破られたのだから HMAC-MD5 も破られた">
  破られたのは**衝突耐性**です。衝突は攻撃者が 2 つの入力を自由に選べるときの課題で、
  鍵を知らない攻撃者が HMAC のタグを作る課題とは別物です。
  RFC 6151 も、HMAC-MD5 について MAC としての実用的な脆弱性は示されていないとしつつ、
  **新しいプロトコルには入れるべきではない**と書いています（[RFC 6151 2.3](https://www.rfc-editor.org/rfc/rfc6151.html#section-2.3)）。
  逆に言えば、「衝突が見つかった」というニュースだけでは、どの用途が壊れたかは分かりません。
  壊れたのが 3 つの強さのどれかを、用途ごとに確かめる必要があります。
</Callout>

## 今使うハッシュ関数

| 名前 | 規格 | 内部の形 | 特徴 |
| --- | --- | --- | --- |
| **SHA-256 / SHA-384 / SHA-512** | FIPS 180-4 | Merkle–Damgård | 最も広く使われる。多くの CPU に専用命令がある |
| **SHA-512/256** など | FIPS 180-4 | 同上（出力を切り詰め） | SHA-512 の内部で計算し、出力の一部だけを出す |
| **SHA3-256** など、SHAKE128/256 | FIPS 202（2015 年 8 月） | スポンジ | 公募で選ばれた Keccak。SHAKE は出力長を自由に選べる |
| **BLAKE2b / BLAKE2s** | RFC 7693 | Merkle–Damgård の改良（最終ブロックに印を付ける） | 高速。鍵付きの MAC モードを内蔵 |
| **BLAKE3** | 公開仕様 | 内部が Merkle 木 | 並列化しやすく非常に速い。MAC・鍵導出のモードも持つ |

SHA-2 は [FIPS 180-4](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)、SHA-3 は [FIPS 202](https://csrc.nist.gov/pubs/fips/202/final)、BLAKE2 は [RFC 7693](https://www.rfc-editor.org/rfc/rfc7693.html) で定められています。BLAKE3 は、内部が Merkle 木なので、任意の数のスレッドと SIMD のレーンに仕事を分けられると説明しています（[BLAKE3](https://github.com/BLAKE3-team/BLAKE3)）。第 12 回で見た SIMD が、ここで効きます。

迷ったら **SHA-256** で十分です。互換性が最も高く、衝突耐性 128 ビットは現在の計算量では届きません。

## ハッシュは改ざんを防がない

ここからが、この回の本題です。

<Callout type="warn" title="よくある誤解: ハッシュ値を添えれば、改ざんに気づける">
  ファイルと一緒に SHA-256 の値を送れば、受け取った側は計算し直して一致を確かめられます。
  しかし経路の途中にいる攻撃者は、**ファイルを書き換えたうえで、ハッシュ値も計算し直して差し替えられます**。
  ハッシュ関数には鍵が無いので、誰でも正しいダイジェストを作れるからです。
  ハッシュ値が役に立つのは、**ファイルとは別の、信頼できる経路でハッシュ値が届いたとき**だけです
  （公式サイトの HTTPS のページ、署名されたリリースノート、ロックファイルに書き込まれた値など）。
  つまりハッシュは完全性の問題を「大きなデータを守る」問題から「短い値を守る」問題に縮めるだけで、
  その短い値を守るのは別の部品（TLS、署名）の仕事です。
</Callout>

同じ考え方は、ほかの回にも出てきます。第 61 回の DNSSEC の DS レコードは子ゾーンの鍵のハッシュで、**親ゾーンの署名で守られている**から意味を持ちました。コンテナイメージの `sha256:` で始まるダイジェストも、それを書いた設定ファイルが信頼できて初めて「このイメージで間違いない」と言えます。

では、別の経路が無いときはどうするか。攻撃者が作れない値、つまり**鍵が要る値**を添えます。これが MAC です。

## 鍵を混ぜればよい、のか

最初に思いつくのは、送り手と受け手だけが知る鍵 K を、本文の前に付けてハッシュすることです。

```
tag = SHA-256(K || 本文)       ← || は連結
```

鍵を知らなければ正しいタグは作れないように見えます。しかし **SHA-256 ではこれが破れます**。原因はハッシュ関数の内部の形にあります。

### Merkle–Damgård の形

SHA-256 は入力を 64 バイトのブロックに区切り、32 バイトの**内部状態**を 1 ブロックずつ更新していきます。最後のブロックの後に、`0x80`、0 の並び、元の長さ（ビット数）を 8 バイトで付けた**詰め物**を足して、64 バイトの倍数にそろえます（[FIPS 180-4 5.1.1](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)）。

```
    初期値 ─▶[圧縮]─▶[圧縮]─▶[圧縮]─▶ 内部状態 = ダイジェスト
               ▲        ▲        ▲
            ブロック1  ブロック2  ブロック3（詰め物を含む）
```

問題は最後の矢印です。**SHA-256 のダイジェストは、最後の内部状態そのもの**です。ダイジェストを知っている者は、そこから圧縮を続けられます。

### 長さ拡張攻撃

攻撃者が `本文` とそのタグ `SHA-256(K || 本文)` を見たとします。K は知りませんが、次のものは作れます。

1. 鍵の長さを推測し（数通り試せば当たる）、`K || 本文` に付く詰め物 P を計算する
2. タグを内部状態として圧縮を再開し、好きな続き X を入れる
3. 得られた値は `SHA-256(K || 本文 || P || X)` そのもの

受け手が `本文 || P || X` を受け取って、K を前に付けてハッシュすると、攻撃者の作ったタグと一致します。**鍵を知らないまま、後ろを書き足した本文に正しいタグが付けられる**わけです。

詰め物の計算に鍵は要りません。長さだけで決まります。手元で、鍵が 16 バイトと推測した場合の詰め物を作ってみます（詰め物を作るだけで、攻撃そのものは実装していません）。

```python
# pad.py
import struct
def sha256_padding(total_len):
    pad = b"\x80" + b"\x00" * ((55 - total_len) % 64)
    return pad + struct.pack(">Q", total_len * 8)

key_len = 16
msg = b"user=alice&role=user"
p = sha256_padding(key_len + len(msg))
print("詰め物:", p.hex(" "))
print("偽の本文:", msg + p + b"&role=admin")
```

```
$ python3 pad.py
鍵+本文の長さ: 36 バイト
詰め物: 80 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 01 20
偽の本文: b'user=alice&role=user\x80\x00...\x00\x01 &role=admin'
```

末尾の `01 20` は 0x120 = 288 ビット = 36 バイトです。受け手のパーサが途中の制御文字を読み飛ばし、`role` の最後の値を採用するなら、`role=admin` として通ってしまいます。

これは机上の話ではありません。2009 年、Thai Duong と Juliano Rizzo は、Flickr の API がパラメータを並べて共有の秘密の後ろに連結し、MD5 をとったものを署名としていたため、秘密を知らずに別の要求の署名を偽造できることを示しました（[Duong & Rizzo 2009](https://vnhacker.blogspot.com/2009/09/flickrs-api-signature-forgery.html)）。

<Callout type="warn" title="よくある誤解: MD5 をやめて SHA-256 にすれば直る">
  長さ拡張は、衝突耐性の弱さではなく **Merkle–Damgård という形の性質**です。
  MD5、SHA-1、SHA-256、SHA-512 のどれでも同じように起きます。
  ハッシュ関数を強いものに替えても、`hash(鍵 || 本文)` という**組み立て方**が間違っている限り直りません。
  第 103 回の「自分で暗号を組むな」は、まさにこういう意味です。部品は正しくても、組み合わせ方で壊れます。
</Callout>

内部状態をすべては出力しない関数では、この攻撃は成り立ちません。SHA-512/256 や SHA-384（内部状態を切り詰めて出す）、SHA-3（スポンジの内部状態の一部しか出さない）、BLAKE2・BLAKE3 がそうです。BLAKE3 は「SHA-2 と違って長さ拡張に対して安全」と明記しています（[BLAKE3](https://github.com/BLAKE3-team/BLAKE3)）。それでも、**鍵付きのハッシュが欲しいときは、専用に設計された MAC を使う**のが正解です。

## HMAC

**HMAC** は、どんなハッシュ関数からでも安全な MAC を作る組み立て方です（[RFC 2104](https://www.rfc-editor.org/rfc/rfc2104.html)、1997 年。NIST の FIPS 198-1 も同じもの）。

```
HMAC(K, m) = H( (K ⊕ opad) || H( (K ⊕ ipad) || m ) )

  B    = ハッシュのブロック長（SHA-256 なら 64 バイト）
  K    = 鍵を B バイトまで 0 で埋めたもの（B より長い鍵は先に H でハッシュする）
  ipad = 0x36 を B 回
  opad = 0x5c を B 回
```

ハッシュを 2 回、入れ子にかけます。内側のハッシュの結果は外側のハッシュに**鍵と一緒に**入れ直されるので、外に出るダイジェストから内側の計算を続けることはできません。長さ拡張は、ここで止まります。ipad と opad で鍵を 2 通りに変えるのは、内側と外側に別々の鍵を使ったのと同じ効果を得るためです。

RFC 2104 は、鍵の長さを**ハッシュの出力長（SHA-256 なら 32 バイト）以上**にするよう勧め、それより短い鍵は強く勧めないとしています（[RFC 2104 3](https://www.rfc-editor.org/rfc/rfc2104.html#section-3)）。

### 手元で確かめる: HMAC を手で組む

定義のとおりに組んだものと、標準ライブラリの `hmac` と、openssl を比べます。

```python
# hmac_by_hand.py
import hashlib, hmac
key = b"secret-key"
msg = b"hello"
B = 64
k = key.ljust(B, b"\x00")
ipad = bytes(x ^ 0x36 for x in k)
opad = bytes(x ^ 0x5c for x in k)
inner = hashlib.sha256(ipad + msg).digest()
mine = hashlib.sha256(opad + inner).hexdigest()
lib = hmac.new(key, msg, hashlib.sha256).hexdigest()
print("手で計算:", mine)
print("hmac    :", lib)
print("一致    :", hmac.compare_digest(mine, lib))
print("sha256(key||msg):", hashlib.sha256(key + msg).hexdigest())
```

```
$ python3 hmac_by_hand.py
手で計算: 98e7ffb964bb5a3f902db1fc101a5baa98b6f2cd56858210c9d70f26ac762fc7
hmac    : 98e7ffb964bb5a3f902db1fc101a5baa98b6f2cd56858210c9d70f26ac762fc7
一致    : True
sha256(key||msg): 1a00ab9a8be939984e33c46b65e6634f471783862970a94df4497080071fbc8a

$ printf 'hello' | openssl dgst -sha256 -hmac 'secret-key'
HMAC-SHA2-256(stdin)= 98e7ffb964bb5a3f902db1fc101a5baa98b6f2cd56858210c9d70f26ac762fc7
```

3 つが一致し、単純な連結とは別の値になります。BLAKE2 は鍵を引数に取る MAC のモードを内蔵しているので、HMAC で包まずに `hashlib.blake2b(msg, key=key)` と書けます。SHA-3 にも KMAC という専用の MAC があります（[NIST SP 800-185](https://csrc.nist.gov/pubs/sp/800/185/final)）。

### HMAC が使われている場所

HMAC は、この先の回に何度も出てきます。

| 使われる場所 | 回 |
| --- | --- |
| Webhook や API の要求への署名（`X-Hub-Signature-256` など） | ― |
| JWT の `HS256`（HMAC-SHA256） | 第 128 回 |
| 鍵導出の HKDF（HMAC を組み合わせて鍵を作る） | 第 109 回 |
| TLS 1.3 の Finished メッセージと鍵スケジュール | 第 113 回 |
| ワンタイムパスワードの HOTP / TOTP | 第 126 回 |

## MAC は第三者に何も証明しない

MAC で分かるのは、「**同じ鍵を持つ誰か**が、このタグを作った」ことです。鍵を持つのが自分と相手の 2 者だけなら、自分が作っていない以上、相手が作ったと分かります。これが真正性です。

しかし、このタグを**第三者に見せて**「相手がこれを送った」と主張することはできません。鍵を持つ自分にも同じタグが作れるからです。第三者から見れば、どちらが作ったのか区別がつきません。

```
          鍵 K を持つ          タグを作れる     第三者に「相手が作った」と示せる
MAC       送り手と受け手        両方             できない
署名      送り手（秘密鍵）だけ   送り手だけ        できる（公開鍵で誰でも検証）
```

第 103 回の 4 つの性質で言えば、**MAC は否認防止を持ちません**。否認防止が要るとき、あるいは検証する人が大勢いて全員に鍵を配れないときは、第 107 回の署名を使います。逆に、2 者の間で速く確かめたいだけなら、MAC のほうが桁違いに安く、鍵も短くて済みます。

<Callout type="note" title="鍵の共有は別の問題">
  MAC は「2 者がすでに同じ鍵を持っている」ことを前提にしています。
  その鍵をどう安全に共有するかは MAC の外の話で、第 106 回の鍵交換が答えます。
  TLS は鍵交換で共有した秘密から HKDF で MAC と暗号の鍵を作っており、
  HMAC は単体ではなく**鍵交換と組み合わさって**初めて使える部品になっています。
</Callout>

## 比べ方で漏れる: タイミング攻撃

受け手はタグを計算し直し、届いたタグと比べます。この**比べ方**にも落とし穴があります。

多くの言語の `==` は、先頭から 1 バイトずつ比べ、**違うバイトが見つかった時点で止まります**。すると、先頭の 1 バイトが合っているタグは、合っていないタグよりわずかに長く比較に時間がかかります。攻撃者が何度も要求を送って応答時間を測れば、1 バイト目を 256 通り試して一番遅いものを選び、次に 2 バイト目を……と、**鍵を知らずに正しいタグを 1 バイトずつ当てていける**可能性があります。1 つのタグを当てる手間が、2^256 から 256 × 32 程度まで下がります。

対策は、**中身にかかわらず、常に全バイトを比べる**比較関数を使うことです。

```python
import hmac
hmac.compare_digest(expected, received)   # == の代わりに
```

Python の文書は、この関数が「内容に基づく途中打ち切りを避け、タイミング解析を防ぐよう設計されている」とし、外から与えられたダイジェストとの比較には `==` の代わりにこれを使うよう勧めています。長さが違う場合は長さの情報は漏れうるが、値は漏れないとも書いています（[Python hmac](https://docs.python.org/3/library/hmac.html#hmac.compare_digest)）。Go の `crypto/subtle.ConstantTimeCompare`、Node の `crypto.timingSafeEqual` も同じ目的の関数です。

ネットワーク越しの時間差は小さく、雑音にも埋もれます。それでも測定を繰り返せば雑音は平均で消せるので、「遅延が大きいから大丈夫」とは言えません。**秘密に関わる値の比較は、いつも定数時間で**、と決めておくのが安全です。

## パスワードの保存は別の話

最後に、ハッシュの最も有名な誤用に触れておきます。パスワードを SHA-256 でハッシュして保存するのは、**やってはいけません**。

この回で見たハッシュ関数は、**速い**ことが長所です。しかしパスワードの保存では、DB が漏れたあとに攻撃者が候補を片っ端から試す速さが、そのまま弱さになります。パスワードには、わざと遅く、大量のメモリを使うように作った専用の関数（Argon2id、scrypt、bcrypt）とソルトを使います。詳しくは第 126 回で見ます。

## まとめ

- ハッシュ関数は鍵を使わず、任意のデータから固定長のダイジェストを作る。1 ビットの違いで出力の約半分が変わる
- 強さは 3 つに分かれる。原像耐性と第 2 原像耐性は約 2^n、衝突耐性は誕生日のパラドックスで約 2^(n/2)。出力長の半分が衝突に対する強度
- MD5 は 2004 年、SHA-1 は 2017 年の SHAttered で衝突が実証された。NIST は SHA-1 を 2030 年末までに退役させる。今は SHA-256 を基本に、SHA-3、BLAKE2・3 も使える
- **ハッシュ値は、別の信頼できる経路で届いたときだけ改ざんの検出に使える**。同じ経路なら攻撃者は両方を差し替える
- `SHA-256(鍵 || 本文)` は長さ拡張攻撃で破れる。関数を強くしても直らない、組み立て方の問題
- HMAC は鍵を 2 通りに変えてハッシュを入れ子にかけ、どのハッシュ関数からでも安全な MAC を作る
- MAC は同じ鍵を持つ者同士の確認で、第三者には証明できない（否認防止がない）。そこが署名との違い
- タグの比較は `==` ではなく定数時間の関数で。パスワードの保存には専用の遅い関数を使う（第 126 回）

MAC で改ざんには気づけるようになりましたが、中身は丸見えのままです。次の回では、中身を隠す共通鍵暗号を見ます。そして、**暗号化だけでは改ざんを防げない**ことを確かめ、この回の MAC と暗号を 1 つにまとめた AEAD にたどり着きます。
