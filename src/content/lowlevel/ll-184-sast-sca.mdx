## 動かさずに見つける

第 183 回で、この章の流れを設計・実装・検査・証跡の 4 段に分けました。この回から検査の段に入ります。最初に扱うのは、**プログラムを動かさずに、ファイルを読むだけで問題を見つける**道具です。

読む対象は 2 つあります。

| 道具 | 読むもの | 探すもの |
| --- | --- | --- |
| **SAST**（Static Application Security Testing） | 自分たちが書いたソースコード | SQL インジェクションのような、書き方の誤り |
| **SCA**（Software Composition Analysis） | 依存関係の一覧（ロックファイル） | 使っているライブラリの版に、既知の脆弱性があるか |

SAST は「**自分たちのコードに、まだ誰も知らない欠陥があるか**」を探し、SCA は「**他人のコードに、すでに公表された欠陥があるか**」を探します。前者は推論で、後者は照合です。この違いが、どちらの道具の長所と短所にもそのまま表れます。

この回では、まず SAST が「危ない書き方」をどう見分けているかを 3 段階で見て、手元で Semgrep を動かし、**誤検知と見逃しがどこから生まれるか**を確かめます。後半では SCA が何を照合しているかを、npm audit と osv-scanner、そして呼び出しの有無まで調べる govulncheck で確かめます。

## SAST の 3 段階

SAST が欠陥を見つけるやり方は、精度の低い順に 3 段階あります。

### 1. 文字列で探す

いちばん素朴なのは、`grep` のように**文字列の並び**で探すことです。`execute(` と `+` が同じ行にあれば怪しい、という具合です。速くて簡単ですが、空白や改行の入れ方、変数への代入を挟むだけで外れます。文字列の中やコメントの中にある `execute(` にも反応します。

### 2. 構文木で探す

コードを**抽象構文木（AST）**に変換してから探すと、書式の揺れが消えます。`db.execute("SELECT " + name)` という 1 行を Semgrep に読ませ、`semgrep --dump-ast -l python` で内部の構文木を出させてみます。

```
Pr(
  [ExprStmt(
     Call(
       DotAccess(
         N(
           Id(("db", ()), ...)), (),
         FN(
           Id(("execute", ()), ...))),
       [Arg(
          Call(Special((Op(Plus), ())),
            [Arg(L(String(("SELECT ", ()))));
             Arg(
               N(
                 Id(("name", ()), ...)))]))]),
     ())])
```

（識別子ごとに付く型情報などの付帯情報は `...` で省略しています。）

「`db` の `execute` を呼ぶ（`Call`）。引数は、文字列リテラル（`L(String ...)`）と変数 `name`（`N(Id ...)`）の足し算（`Op(Plus)`）」という木になっています。空白や改行や括弧の付け方がどうであっても、同じ木になります。**パターンは文字列ではなく、この木の形に対して当てる**ので、書式の揺れでは外れません。Semgrep のルールに書く `$DB.execute("..." + $X)` は、この木の形を表したものです。

ただし、構文木は**値がどこから来たか**を知りません。`name` が利用者の入力なのか、プログラムに埋め込んだ定数なのかは、この木を見ても分かりません。

### 3. 値の流れを追う

そこで、**値がどこで生まれ、どこを通って、どこに届くか**を追います。これを**データフロー解析**と呼び、その中でもセキュリティの検査に使う形を **taint 解析**（汚染の追跡）と呼びます。taint 解析は、次の 3 つを決めて動きます。

| 用語 | 意味 | 例 |
| --- | --- | --- |
| **source** | 信用できない値が入ってくる場所 | HTTP のクエリ文字列、リクエストの本文、ヘッダ |
| **sink** | 信用できない値が届くと危ない場所 | SQL を実行する関数、シェルを起動する関数、HTML への出力 |
| **sanitizer** | 値を無害にする処理 | 整数への変換、エスケープ、許可リストとの照合 |

source から出た値に「汚れている」という印を付け、代入や連結を通るたびに印を引き継ぎます。sanitizer を通ると印が消えます。**印が付いたまま sink に届いたら報告する**、というのが taint 解析です。Semgrep の文書もこの 3 語で説明しています（[Semgrep Docs](https://docs.semgrep.dev/writing-rules/data-flow/taint-mode)）。

CodeQL の文書は、taint 解析をデータフロー解析の拡張として位置づけています。通常のデータフロー解析は値そのものが保たれる経路だけを追いますが、taint 解析は `y = x + 1` のように**値は変わっても、信用できない値から導かれたもの**も追います（[CodeQL](https://codeql.github.com/docs/writing-codeql-queries/about-data-flow-analysis/)）。文字列の連結で SQL を組み立てる場合は、まさにこの「値は変わったが、中身は入力由来」の形です。

## 手元で比べる: パターン一致と taint 解析

実際に、同じコードへ 2 種類のルールを当てて違いを見ます。対象は、Flask で書いた小さな Web アプリケーションです。関数ごとに、性質の違う SQL の組み立て方を 7 通り並べました。

```python
import sqlite3
from flask import Flask, request, abort

app = Flask(__name__)
db = sqlite3.connect(":memory:", check_same_thread=False)
pending = {}

@app.route("/a")
def a():
    name = request.args.get("name")
    q = "SELECT * FROM users WHERE name = '" + name + "'"
    return str(db.execute(q).fetchall())                        # 13 行目

@app.route("/b")
def b():
    q = "SELECT * FROM users WHERE name = '" + "admin" + "'"
    return str(db.execute(q).fetchall())                        # 19 行目

@app.route("/c")
def c():
    n = int(request.args.get("id"))
    q = "SELECT * FROM users WHERE id = " + str(n)
    return str(db.execute(q).fetchall())                        # 26 行目

@app.route("/d")
def d():
    name = request.args.get("name")
    return str(db.execute(f"SELECT * FROM users WHERE name = '{name}'").fetchall())  # 32 行目

@app.route("/e")
def e():
    name = request.args.get("name")
    if not name.isalnum():
        abort(400)
    q = "SELECT * FROM users WHERE name = '" + name + "'"
    return str(db.execute(q).fetchall())                        # 41 行目

@app.route("/f1")
def f1():
    pending["name"] = request.args.get("name")
    return "ok"

@app.route("/f2")
def f2():
    q = "SELECT * FROM users WHERE name = '" + pending["name"] + "'"
    return str(db.execute(q).fetchall())                        # 53 行目

@app.route("/g")
def g():
    name = request.args.get("name")
    return str(db.execute("SELECT * FROM users WHERE name = ?", (name,)).fetchall())
```

（行番号のコメントは説明のために付けたもので、解析したファイルには付いていません。）

人が読めば、`a`（入力を連結）、`d`（入力を f 文字列で埋め込む）、`f1` → `f2`（入力をグローバルな辞書に置き、別の関数で連結）が脆弱で、`b`（定数どうし）、`c`（整数に変換済み）、`e`（英数字だけかを検査済み）、`g`（プレースホルダ）は安全です。

SQL インジェクションは CWE-89「Improper Neutralization of Special Elements used in an SQL Command」という分類です（[CWE](https://cwe.mitre.org/data/definitions/89.html)）。正しい直し方は `g` のように**プレースホルダで値を渡す**ことで、SQL の構文と値がデータベースに別々に届くため、値が構文として解釈されることがありません。

### ルール 1: 形だけで探す

まず、「文字列リテラルとの連結で作った変数を `execute` に渡している」という形だけを探すルールを書きます。

```yaml
rules:
  - id: sql-string-concat
    languages: [python]
    severity: WARNING
    message: SQL を文字列の連結で組み立てている
    patterns:
      - pattern: $DB.execute($Q)
      - pattern-either:
          - pattern-inside: |
              $Q = "..." + $X
              ...
          - pattern-inside: |
              $Q = "..." + $X + "..."
              ...
```

`$DB` や `$Q` は**メタ変数**で、構文木のどんな部分にも一致し、同じ名前は同じものを指します。`pattern-inside` は「この形の内側にあるもの」に絞る指定で、`...` は「間に何があってもよい」を表します。

```bash
docker run --rm --name ll175-semgrep -v "$PWD:/src" -w /src semgrep/semgrep \
  semgrep scan --metrics=off --config pattern.yml app.py
```

```
│ 5 Code Findings │
    ❯❱ sql-string-concat
          SQL を文字列の連結で組み立てている

           13┆ return str(db.execute(q).fetchall())
            ⋮┆----------------------------------------
           19┆ return str(db.execute(q).fetchall())
            ⋮┆----------------------------------------
           26┆ return str(db.execute(q).fetchall())
            ⋮┆----------------------------------------
           41┆ return str(db.execute(q).fetchall())
            ⋮┆----------------------------------------
           53┆ return str(db.execute(q).fetchall())
```

（枠線や空行を詰めています。）

13（`a`）と 53（`f2`）は正しく拾えました。しかし、19（`b`）と 26（`c`）は**安全なのに報告**しています（誤検知）。形は同じでも、値が定数だったり整数に変換済みだったりすることを、このルールは知りません。そして、32 行目の `d` を**見逃して**います。f 文字列は `+` による連結とは別の構文木になるため、形が一致しないのです。

<Callout type="note" title="ルールの書き方でも結果は揺れる">
  実は最初に `"..." + $X + ...` という 1 つの形で書いたところ、`c` の
  `"..." + str(n)`（項が 2 つだけの連結）に一致しませんでした。
  `a + b + c` は `(a + b) + c` という入れ子の木になるので、項の数が違う連結は、別の形として書き分ける必要がありました。
  パターン一致のルールは、**書いた人が想定した形しか拾わない**ことを、ルールを書く側が意識しておく必要があります。
</Callout>

### ルール 2: 値の流れで探す

次に、同じ欠陥を taint 解析のルールで書きます。

```yaml
rules:
  - id: sql-injection-taint
    languages: [python]
    severity: ERROR
    message: リクエストの値が SQL に届いている
    mode: taint
    pattern-sources:
      - pattern: request.args.get(...)
    pattern-sanitizers:
      - pattern: int(...)
    pattern-sinks:
      - patterns:
          - pattern: $DB.execute($Q, ...)
          - focus-metavariable: $Q
```

source はクエリ文字列の取得、sanitizer は整数への変換、sink は `execute` の**第 1 引数**です。`focus-metavariable` で第 1 引数に絞っているので、`g` のように第 2 引数のタプルで値を渡す書き方は sink に当たりません。`--dataflow-traces` を付けると、値がどこを通ったかも表示されます。

```bash
docker run --rm --name ll175-semgrep -v "$PWD:/src" -w /src semgrep/semgrep \
  semgrep scan --metrics=off --config taint.yml --dataflow-traces app.py
```

```
│ 3 Code Findings │
   ❯❯❱ sql-injection-taint
          リクエストの値が SQL に届いている

           13┆ return str(db.execute(q).fetchall())


          Taint comes from:
           11┆ name = request.args.get("name")

          Taint flows through these intermediate variables:
           11┆ name = request.args.get("name")
           12┆ q = "SELECT * FROM users WHERE name = '" + name + "'"

                This is how taint reaches the sink:
           13┆ return str(db.execute(q).fetchall())

            ⋮┆----------------------------------------
           32┆ return str(db.execute(f"SELECT * FROM users WHERE name = '{name}'").fetchall())
          ...
            ⋮┆----------------------------------------
           41┆ return str(db.execute(q).fetchall())
          ...
```

（枠線や空行を詰め、2 件目以降の経路の表示を省略しています。）

**11 行目で生まれた値が、12 行目の連結を通って、13 行目の sink に届いた**、という経路がそのまま示されています。報告を受け取った人は、この経路を読めば、どこで直せばよいかが分かります。

### 2 つのルールを並べる

結果を表にまとめます。

| 関数 | 書き方 | 人の判定 | ルール 1（形） | ルール 2（taint） |
| --- | --- | --- | --- | --- |
| `a` | 入力を `+` で連結 | 脆弱 | 報告 | 報告 |
| `b` | 定数どうしを連結 | 安全 | **報告（誤検知）** | 報告なし |
| `c` | `int()` してから連結 | 安全 | **報告（誤検知）** | 報告なし |
| `d` | f 文字列に埋め込む | 脆弱 | **見逃し** | 報告 |
| `e` | 英数字か検査してから連結 | 安全 | **報告（誤検知）** | **報告（誤検知）** |
| `f1` → `f2` | グローバル経由で別関数へ | 脆弱 | 報告 | **見逃し** |
| `g` | プレースホルダ | 安全 | 報告なし | 報告なし |

taint 解析は、`b`・`c` の誤検知と `d` の見逃しを解消しました。値の出どころを知っているからです。それでも、2 か所で外れています。

**`e` の誤検知。** `isalnum()` で英数字だけかを確かめ、そうでなければ `abort(400)` で打ち切っています。人が読めば安全ですが、ルールは `isalnum()` による分岐を sanitizer として知りません。**ルールに書かれていない無害化は、無害化として扱われません。** 自分たちのコードに検証用の関数があるなら、それを sanitizer としてルールに加えることで、この種の誤検知は消せます。

**`f2` の見逃し。** 値は `f1` でグローバルな辞書 `pending` に入り、別の HTTP リクエストで呼ばれる `f2` で SQL に入ります。関数をまたぐ経路です。Semgrep の文書は、Community Edition の taint 解析が**関数の内側だけで動く**こと、関数をまたぐ解析は有償の Semgrep Pro の機能であることを明記しています（[Semgrep Docs](https://docs.semgrep.dev/writing-rules/data-flow/taint-mode)）。さらにこの例は、2 回の別々のリクエストにまたがって状態を経由しているので、関数をまたぐ解析ができる道具でも、追えるかどうかは解析の作り次第です。

<Callout type="warn" title="「指摘ゼロ」は「欠陥ゼロ」ではない">
  SAST が何も報告しないのは、**ルールに書かれた経路が見つからなかった**というだけです。
  ルールが知らない source（独自のメッセージキューから読む値など）、知らない sink（社内の SQL ヘルパ）、
  解析の届かない経路（関数・ファイル・リクエストをまたぐ流れ）は、最初から対象の外にあります。
  SAST は、**よくある形の欠陥を、人がレビューする前に機械的に潰すための網**として使うのが適切です。
</Callout>

## 誤検知と見逃しは、どちらも減らしきれない

ここまでの実験で、誤検知も見逃しも、ルールと解析の作りから生まれることが見えました。原理的にも、任意のプログラムについて「この値が実行時にこの関数へ届くか」を常に正しく判定する方法はありません。そこで SAST の道具は、**疑わしいものを全部報告して見逃しを減らす**か、**確かなものだけ報告して誤検知を減らす**かの、どちらかに寄せて妥協します。

現場で問題になりやすいのは前者です。誤検知の多い道具は、指摘を「また誤検知だろう」と読み飛ばす習慣を作り、本物の指摘まで埋もれさせます。導入の初めは確度の高いルールに絞り、プルリクエストの差分に関わる指摘だけを見せる、といった運用で、読まれる量に抑えるのが現実的です。

誤検知に対しては、次の順で対処します。

1. **ルールを直す。** 自分たちの検証関数を sanitizer に加える。誤検知の大半は、ルールがコードの事情を知らないことから来ます
2. **コードを直す。** `e` のように検査してから連結するより、`g` のようにプレースホルダを使えば、SAST にも人にも安全が一目で分かります
3. **その箇所だけ抑止する。** Semgrep なら行末の `# nosemgrep: ルール ID` のように、抑止した理由とともに記録します。抑止の一覧は、後で見直す対象になります

## Semgrep と CodeQL

代表的な SAST の道具である Semgrep と CodeQL は、同じ taint 解析を行いますが、作りが違います。

| | Semgrep | CodeQL |
| --- | --- | --- |
| 入力 | ソースファイルをそのまま構文解析する | コードから**データベース**を作る。コンパイルする言語ではビルドの過程を監視して抽出する |
| ルールの書き方 | 対象の言語に似たパターンを YAML に書く | QL というクエリ言語で、データベースに問い合わせる |
| ビルド | 要らない | コンパイルする言語では必要 |
| 得意なこと | 速さ、ルールの書きやすさ、組織固有の規則 | 関数やファイルをまたぐ深いデータフロー |

CodeQL は、コンパイルする言語では**通常のビルドを監視して**コードの関係をデータベースに抽出し、そのデータベースにクエリを実行します（[CodeQL](https://codeql.github.com/docs/codeql-overview/about-codeql/)）。CodeQL の文書は、データフローを関数の内側だけの**ローカル**なものと、関数やオブジェクトのプロパティをまたいでプログラム全体で計算する**グローバル**なものに分け、前者は速く、後者はより多くの計算を要すると説明しています（[CodeQL](https://codeql.github.com/docs/writing-codeql-queries/about-data-flow-analysis/)）。

どちらを選ぶかより、**どこで動かすか**のほうが効果を左右します。プルリクエストごとに差分に対して動かし、指摘をレビューの画面に出すのが基本の形です。CWE の番号付きで指摘が出るので、第 183 回で見た OWASP Top 10 の分類とも結び付けられます。

## SCA: 他人のコードの既知の欠陥

ここからは後半です。現代のアプリケーションでは、自分たちが書いたコードより、依存しているライブラリのコードのほうがはるかに多くなります。そのライブラリに脆弱性が公表されたとき、**自分たちのどのアプリが、どの版を使っているか**をすぐに答えられるかどうかが SCA の目的です。

SCA がやっていることは、次の照合です。

```
ロックファイル                         脆弱性データベース
（何を、どの版で使っているか）         （どのパッケージの、どの版の範囲に、どの欠陥があるか）
        │                                       │
        └──────────────── 突き合わせる ─────────┘
                              │
                     該当する版の一覧と、直る版
```

### ロックファイルを読む

照合の片側は**ロックファイル**です。`package.json` に書くのは `"express": "^4.17.1"` のような**範囲**ですが、実際に入る版は、インストールした日によって変わりえます。npm の `package-lock.json` は、**実際に生成された依存の木そのもの**を記録し、次のインストールで同じ木を再現できるようにするためのファイルです（[npm Docs](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json)）。SCA は、実際に入る版が確定しているロックファイルを読みます。

手元で、古い版を固定した小さなプロジェクトを作ります。

```json
{
  "name": "ll175-sca",
  "version": "1.0.0",
  "private": true,
  "dependencies": {
    "lodash": "4.17.20",
    "express": "4.17.1"
  }
}
```

```bash
npm install --package-lock-only --ignore-scripts
```

`--package-lock-only` はロックファイルだけを作り、パッケージの中身は取得しません。`--ignore-scripts` はインストール時のスクリプトを動かさない指定です。直接書いたのは 2 つだけですが、ロックファイルには 51 個のパッケージが、それぞれ `"version": "6.7.0"` のような確定した版と、取得元の URL、中身のハッシュ（`integrity`）付きで並びました。その中の 1 つ `qs` は、自分では一度も書いていないパッケージです。どこから来たのかは `npm ls` で分かります。

```bash
npm ls qs --package-lock-only
```

```
ll175-sca@1.0.0 /…/scratchpad/ll175/sca
└─┬ express@4.17.1
  ├─┬ body-parser@1.19.0
  │ └── qs@6.7.0 deduped
  └── qs@6.7.0
```

express が直接、そして express が使う body-parser も `qs` を使っています。このように、**依存の依存**として入ってくるものを**推移的依存**と呼びます。49 個は推移的依存です。脆弱性の多くはこちら側で見つかり、しかも自分では版を直接選んでいないため、気づきにくく、直しにくい場所です。

### npm audit

npm には SCA の機能が組み込まれています。`npm audit` は、プロジェクトの依存関係の記述をレジストリに送り、既知の脆弱性の報告を求めるコマンドです（[npm Docs](https://docs.npmjs.com/cli/v11/commands/npm-audit)）。


読み方の要点は 3 つです。

- 見出しの `body-parser  <=1.20.5` は「この**範囲**の版に脆弱性がある」という意味で、手元の版そのものではありません
- `express` は、自身の欠陥に加えて「**脆弱な版の body-parser や qs に依存している**」ことで報告されています。推移的依存の欠陥が、直接の依存の名前で表に出てくる形です
- 末尾の `8 vulnerabilities` は**パッケージ単位**の数え方です。lodash 1 つに 5 件の勧告が付いていても、1 と数えています

`Will install express@4.22.3, which is outside the stated dependency range` は、`package.json` に書いた版の指定を越えて上げないと直らない、という意味です。`--force` を付けると上げてくれますが、互換性の確認は自分で行う必要があります。

### CVE、GHSA、OSV

脆弱性には、発行する側ごとに別々の ID が付きます。製品をまたいで使われる **CVE**（`CVE-2021-23337`）、GitHub Advisory Database の **GHSA**（`GHSA-35jh-r3h4-6jhm`）、Go の脆弱性データベースの **GO**（`GO-2022-1059`）などです。GHSA の ID は `GHSA-xxxx-xxxx-xxxx` の形で、`x` には `23456789cfghjmpqrvwx` の文字が入ります。GitHub Advisory Database の勧告は、すべて OSV の形式の JSON として公開されています（[GitHub Docs](https://docs.github.com/en/code-security/security-advisories/working-with-global-security-advisories-from-the-github-advisory-database/about-the-github-advisory-database)）。

**OSV** は、これらを機械で読める共通の形式にまとめたものです。lodash の勧告を OSV の API から取ってみます。

`curl -s https://api.osv.dev/v1/vulns/GHSA-35jh-r3h4-6jhm` の結果から、必要な部分だけを抜き出すと次のとおりです。

```
id:      GHSA-35jh-r3h4-6jhm
aliases: ['CVE-2021-23337', 'CVE-2026-4800', 'GHSA-r5fr-rjxr-66jc']

package: {"name": "lodash", "ecosystem": "npm", "purl": "pkg:npm/lodash"}
ranges:  [{"type": "SEMVER", "events": [{"introduced": "0"}, {"fixed": "4.17.21"}]}]

package: {"name": "lodash.template", "ecosystem": "npm", "purl": "pkg:npm/lodash.template"}
ranges:  [{"type": "SEMVER", "events": [{"introduced": "0"}, {"last_affected": "4.5.0"}]}]
```

`aliases` は、**他のデータベースで同じ脆弱性に付けられた ID の一覧**です（[OSV Schema](https://ossf.github.io/osv-schema/)）。`GHSA-r5fr-rjxr-66jc` はこの勧告の別名として載っているので、osv-scanner は 2 つを同じまとまりとして表示していたわけです。一方、npm audit は 2 つを別々の行として出していました。**同じ脆弱性が、道具によって 1 件にも 2 件にも数えられる**ことは、件数を指標にするときに注意が要ります。

`ranges` の `events` は、版の並びに沿って「`introduced`（ここから脆弱）」「`fixed`（ここで直った）」「`last_affected`（直った版が無く、ここまでが脆弱）」を並べたものです（[OSV Schema](https://ossf.github.io/osv-schema/)）。lodash 本体は `0` から `4.17.21` の手前まで、`lodash.template` は直った版が無く `4.5.0` までが脆弱、と読めます。GitHub の勧告のページも、lodash の `template` 関数による Command Injection で、4.17.21 で直ったと記しています（[GitHub Advisory](https://github.com/advisories/GHSA-35jh-r3h4-6jhm)）。

照合は、ロックファイルの `(エコシステム, 名前, 版)` が、この範囲に入るかどうかを調べるだけです。範囲の比較の仕方（`SEMVER` か、エコシステム独自の順序か）も、`type` で指定されています。

## 入っていることと、使っていることは違う

ここまでの照合には、大きな前提があります。**ロックファイルに入っていれば、使っているとみなす**という前提です。

lodash の Command Injection は `template` 関数の欠陥です。アプリケーションが `template` を一度も呼んでいなければ、この欠陥を突く道はありません。それでも npm audit も osv-scanner も、版が範囲に入っている以上は報告します。SCA の報告には、**この意味での誤検知が少なくありません**。

これを減らすのが**到達可能性解析**です。脆弱性の情報に「どの関数が脆弱か」を含めておき、アプリケーションのコードからその関数への**呼び出しの経路**があるかを静的に調べます。SAST の taint 解析と同じく、プログラムの構造を読む解析です。

Go の公式の道具 govulncheck は、これを標準で行います。Go の文書は、govulncheck が依存関係の既知の脆弱性を調べたうえで、**コードからその脆弱性への直接・間接の呼び出しを特定する**、ノイズの少ない道具だと説明しています（[Go Docs](https://go.dev/doc/tutorial/govulncheck)）。

### 手元で確かめる

脆弱性のある `golang.org/x/text v0.3.7` を `go.mod` で指定し、同じ `golang.org/x/text/language` パッケージを使う 2 つのプログラムを用意します。

```go
// calls/main.go: 脆弱な関数を呼ぶ

	fmt.Println(tags, err)

func main() {
	fmt.Println(language.Japanese)
```

## 直す流れを自動にする: Dependabot と Renovate

SCA は、第 183 回で見たとおり、**コードが変わっていなくても結果が変わる**検査です。昨日公表された脆弱性は、昨日までのスキャンには現れません。そのため、変更のたびに加えて定期的に動かし、見つかったら直す流れまで自動にしておくのが普通です。

**Dependabot** のセキュリティ更新は、依存に脆弱性が見つかると、**修正を含む最小の版**に上げるプルリクエストを自動で作ります（[GitHub Docs](https://docs.github.com/en/code-security/dependabot/dependabot-security-updates/about-dependabot-security-updates)）。**Renovate** も、複数のプラットフォームと言語に対応した、依存の自動更新の道具です（[Renovate Docs](https://docs.renovatebot.com/)）。どちらも、プルリクエストの CI でテストが通るかを見てから取り込む形になります。

自動更新を回すうえで効くのは、次の点です。

- **普段から版を新しく保つ。** 長く上げていない依存は、上げるときの差分が大きく、脆弱性が出たときに急いで上げられません。osv-scanner の結果では `qs 6.7.0` に 4 件が当たり、直る版は `6.7.3` から `6.16.0` まで散らばっていました。古いまま放置するほど、直すために越える版の幅が広がります
- **テストを持つ。** 更新のプルリクエストを安心して取り込めるかは、テストがどれだけ挙動を押さえているかで決まります
- **推移的依存は上流を上げる。** `qs` を直すには、多くの場合 `express` を上げます。npm の `overrides` のように推移的依存の版だけを差し替える仕組みもありますが、上流が想定していない組み合わせになることを承知で使います

ロックファイルに何が入っているかを一覧にしたものは、第 187 回で見る **SBOM** になります。SCA が照合の片側に使っていた「何を、どの版で使っているか」を、配布物に添えて第三者にも渡せる形にしたものです。

## 読むだけでは見えないもの

SAST と SCA は、どちらも**動かさずに読む**道具です。そのため、動いているアプリが実際にどう応答するか、設定やデプロイの環境が正しいかは見えません。たとえば、SQL の組み立ては正しくても、本番の Web サーバの設定でエラーの詳細が外に漏れている、といった問題は、コードを読んでも分かりません。

次の第 185 回では、視点を反対側に移します。**動いているアプリに外から要求を送って確かめる** DAST と、インフラの**設定を読んで確かめる** IaC の検査、そしてクラウドの**今の設定を集めて基準と比べる** CSPM です。この回の SAST と DAST がどう補い合うかも、そこで見ます。

## まとめ

- SAST は自分たちのコードの未知の欠陥を、SCA は依存しているライブラリの既知の欠陥を探す。前者は推論、後者は照合
- SAST の精度は、文字列 → 構文木の形 → 値の流れ（taint 解析：source・sink・sanitizer）の順に上がる
- 手元の実験では、形だけのルールは定数や整数化した値を誤検知し、f 文字列を見逃した。taint 解析はそれを解消したが、ルールに無い検証は誤検知し、関数をまたぐ経路は見逃した
- 指摘ゼロは欠陥ゼロではない。誤検知は、ルールを直す・コードを直す・理由付きで抑止する、の順に対処する
- Semgrep はソースを直接読み、ルールが書きやすい。CodeQL はコードをデータベースにして、関数をまたぐ深いデータフローを問い合わせる
- SCA はロックファイルの（エコシステム、名前、版）を、OSV などの版の範囲と突き合わせる。推移的依存も同じように照合される。CVE・GHSA・GO の ID は `aliases` で結ばれ、道具によって件数の数え方が違う
- 到達可能性解析は、脆弱な関数への呼び出しがあるかまで調べ、SCA の誤検知を減らす。govulncheck は同じ版でも呼ぶ側だけを影響ありと判定した
- SCA は、データベースの更新だけで結果が変わる。定期的に動かし、Dependabot や Renovate で更新のプルリクエストまで自動にする
