## 部品は揃った。では、どう組むのか

第 85 回では、TLS 1.3 のハンドシェイクを「1 往復」という数だけで見ました。第 66 回では、QUIC がそのハンドシェイクのメッセージを CRYPTO フレームに載せて運ぶのを見ました。どちらも、**中で何が起きているか**には立ち入りませんでした。

一方で第 16 章では、部品を 1 つずつ見てきました。鍵交換（第 105 回）、署名（第 106 回）、AEAD（第 104 回）、ハッシュと MAC（第 103 回）、鍵の導出（第 108 回）。そしてこの章の第 109〜111 回で、証明書とその連鎖、発行と失効を見ました。

この回の問いは、**見知らぬサーバとの間に、盗聴も改ざんもなりすましもされない通路を、なぜ 1 往復で作れるのか**です。答えは「部品の組み合わせ方」にあります。ハンドシェイクを 1 通ずつ読み、最後に、手元で鍵を書き出して**サーバの暗号化されたメッセージを自分で復号し、署名と MAC を自分で検証**します。

なお、TLS 1.3 の仕様は 2026 年 7 月に [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.html) として改訂され、RFC 8446 を置き換えました。バージョン番号は同じ 1.3 のままで、互換性のある小さな改訂です（[RFC 9846 1.2](https://www.rfc-editor.org/rfc/rfc9846.html#section-1.2)）。以下の節番号は RFC 9846 のものです。

## 全体の流れ

先に全体を示します（[RFC 9846 2](https://www.rfc-editor.org/rfc/rfc9846.html#section-2) の図を簡略化したもの）。`{ }` はハンドシェイク用の鍵で、`[ ]` はアプリケーション用の鍵で暗号化されることを表します。

```
クライアント                                         サーバ

ClientHello
  + supported_versions, key_share,
  + signature_algorithms, server_name, alpn  ────→
                                                     ServerHello
                                                       + supported_versions, key_share
                                                  ── ここから暗号化 ──
                                                     {EncryptedExtensions}   alpn など
                                                     {Certificate}           証明書の連鎖
                                                     {CertificateVerify}     ここまでへの署名
                                              ←────  {Finished}              ここまでへの MAC
{Finished}                                   ────→
[アプリケーションデータ]                      ←───→  [アプリケーションデータ]
```

1 往復で済む理由は、**クライアントが最初のメッセージで鍵交換の材料（key_share）まで送ってしまう**からです。サーバは ServerHello を返した時点で共有の秘密を計算でき、その直後から暗号化して話せます。クライアントは、サーバの 1 回の応答を受け取れば、Finished の直後からリクエストを送れます。

## 手元のサーバに話しかける

まず実物を見ます。自己署名の P-256 証明書を作り、openssl 3.6 の `s_server` をポート 18094 で起動して、`s_client -trace` でハンドシェイクを表示しました。

```
$ openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
    -keyout server.key -out server.crt -days 30 -subj "/CN=localhost" \
    -addext "subjectAltName=DNS:localhost"
$ openssl s_server -accept 18094 -cert server.crt -key server.key -tls1_3 -alpn h2,http/1.1 -www
$ openssl s_client -connect 127.0.0.1:18094 -servername localhost -alpn h2 -tls1_3 \
    -trace -CAfile server.crt
```

`-msg` にすると、メッセージの並びだけが見えます（抜粋）。

```
>>> TLS 1.3, Handshake [length 05bf], ClientHello
<<< TLS 1.3, Handshake [length 04ba], ServerHello
<<< TLS 1.3, ChangeCipherSpec [length 0001]
<<< TLS 1.3, Handshake [length 000f], EncryptedExtensions
<<< TLS 1.3, Handshake [length 01a3], Certificate
<<< TLS 1.3, Handshake [length 004f], CertificateVerify
<<< TLS 1.3, Handshake [length 0034], Finished
>>> TLS 1.3, ChangeCipherSpec [length 0001]
>>> TLS 1.3, Handshake [length 0034], Finished
Negotiated TLS1.3 group: X25519MLKEM768
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
ALPN protocol: h2
```

上の図のとおりの順番です。ChangeCipherSpec という見慣れないものが混ざっていますが、これは後で説明します。

## ClientHello: 候補を全部並べる

ClientHello は「私はこれらを使えます」という一覧です。`-trace` の出力から主要な部分を抜き出します。

```
ClientHello, Length=1467
  client_version=0x303 (TLS 1.2)
  Random: ...（32 バイト）
  session_id (len=32): 502AC401...
  cipher_suites (len=6)
    {0x13, 0x02} TLS_AES_256_GCM_SHA384
    {0x13, 0x03} TLS_CHACHA20_POLY1305_SHA256
    {0x13, 0x01} TLS_AES_128_GCM_SHA256
  extensions
    server_name(0)                 localhost
    supported_groups(10)           X25519MLKEM768, ecdh_x25519, secp256r1, ...
    application_layer_protocol_negotiation(16)   h2
    signature_algorithms(13)       mldsa65, ..., ecdsa_secp256r1_sha256, ..., ed25519,
                                   ..., rsa_pss_rsae_sha256, ..., rsa_pkcs1_sha256, ...
    supported_versions(43)         TLS 1.3 (772)
    psk_key_exchange_modes(45)     psk_dhe_ke
    key_share(51)
      NamedGroup: X25519MLKEM768 (4588)   key_exchange (len=1216)
      NamedGroup: ecdh_x25519 (29)        key_exchange (len=32)
```

1 つずつ見ます（[RFC 9846 4.2.2](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.2.2)）。

| 欄 | 役割 | 対応する部品 |
| --- | --- | --- |
| client_version = 0x0303 | **TLS 1.2 のふり**。本当のバージョンは supported_versions で伝える | ― |
| random | 32 バイトの乱数。鍵の導出に混ぜ、毎回違う鍵になるようにする | 乱数（第 108 回） |
| cipher_suites | **AEAD とハッシュの組**だけを並べる | AEAD（第 104 回）、ハッシュ（第 103 回） |
| server_name（SNI） | どのサイトの証明書を出してほしいか。**平文** | 第 62 回 |
| alpn | 上で何を話すか（第 65 回の h2） | ― |
| supported_groups | 使える鍵交換の方式の一覧 | 鍵交換（第 105 回） |
| key_share | そのうち**いくつかの公開鍵を先に送る** | 鍵交換（第 105 回） |
| signature_algorithms | サーバに使ってほしい署名の方式 | 署名（第 106 回） |

**key_share が 2 つ**入っている点に注目してください。openssl 3.5 以降は、既定で X25519MLKEM768 と X25519 の 2 つの鍵を送ります（[OpenSSL 3.5 のリリースノート](https://openssl-library.org/news/openssl-3.5-notes/)）。X25519MLKEM768 は、第 105 回で見た耐量子の ML-KEM-768 と X25519 を組み合わせたもので、2026 年 8 月に [RFC 10024](https://www.rfc-editor.org/rfc/rfc10024.html) になりました。1216 バイトという大きさは、**ML-KEM の鍵 1184 バイトと X25519 の 32 バイトをつなげたもの**です（[RFC 10024 4.1](https://www.rfc-editor.org/rfc/rfc10024.html#section-4.1)）。

サーバがどちらも受け付けなければ、1 往復を足して「この方式で送り直して」と頼むことになります。これが後で見る HelloRetryRequest です。**候補を当てずっぽうで先に送る**ことで、たいていの場合に 1 往復を節約しているわけです。

<Callout type="note" title="なぜ TLS 1.2 のふりをするのか">
  TLS 1.2 までは、ClientHello の先頭のバージョン欄で最大のバージョンを伝えていました。ところが、知らないバージョン番号を見ると接続を切ってしまう実装が多く、番号を上げられなくなっていました。
  TLS 1.3 はこの欄を 0x0303（TLS 1.2）に固定し、本当に話せるバージョンを **supported_versions 拡張の一覧**で伝えます（[RFC 9846 4.3.1](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.3.1)）。
  中身のない session_id を 32 バイト送り、サーバが ChangeCipherSpec を 1 つ挟むのも同じ理由です。TLS 1.2 のように見せないと通さない中継装置があったため、「中間装置との互換モード」として残されました（[RFC 9846 E.4](https://www.rfc-editor.org/rfc/rfc9846.html#appendix-E.4)）。ChangeCipherSpec は中身のない飾りで、受け取った側は読み捨てます。
</Callout>

## ServerHello: 1 つずつ選び、鍵を返す

サーバは各候補から 1 つずつ選びます。

```
ServerHello, Length=1206
  server_version=0x303 (TLS 1.2)
  session_id (len=32): 502AC401...        クライアントの値をそのまま返す
  cipher_suite {0x13, 0x02} TLS_AES_256_GCM_SHA384
  extensions
    supported_versions(43)   TLS 1.3 (772)
    key_share(51)
      NamedGroup: X25519MLKEM768 (4588)  key_exchange (len=1120)
```

サーバの key_share は 1120 バイトで、ML-KEM の暗号文 1088 バイトと X25519 の公開鍵 32 バイトです。**ここで両者は同じ共有の秘密を持ちます**。X25519 の部分は第 105 回で見た Diffie-Hellman で、ML-KEM の部分はクライアントの鍵で包んだ秘密をサーバが送る方式です。2 つの秘密をつなげたもの（ML-KEM の秘密が先）が、鍵スケジュールの入力になります（[RFC 10024 4.3](https://www.rfc-editor.org/rfc/rfc10024.html#section-4.3)）。

ServerHello の後ろには、**署名の方式も、ALPN の結果も、証明書もありません**。それらはすべて、この後の暗号化された部分に移されました。

## ここから暗号化される

ServerHello より後ろのハンドシェイクのメッセージは、すべてハンドシェイク用の鍵で暗号化されます（[RFC 9846 1.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-1.3)）。**経路上の観測者には、サーバがどの証明書を出したかすら見えません**。TLS 1.2 では、証明書は平文で流れていました。

### EncryptedExtensions

鍵交換に関係しない拡張の返事です。今回は ALPN の `h2` だけが入っていました（[RFC 9846 4.4.1](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.4.1)）。

### Certificate

第 109 回で読んだ X.509 証明書の連鎖です。中間証明書があれば、サーバ証明書の後ろに続けます（第 110 回）。今回は自己署名なので 1 枚だけです。

### CertificateVerify: 「秘密鍵を持っている」ことを示す

ここが認証の要です。**証明書そのものは誰でも送れます**。公開されている文書だからです。サーバが本物であることを示すには、証明書の中の公開鍵に対応する**秘密鍵を持っていることを、その場で示す**必要があります。

CertificateVerify は、**ClientHello から Certificate までの全メッセージのハッシュ（トランスクリプトハッシュ）への署名**です。署名の対象は次の 4 つをつなげたものです（[RFC 9846 4.5.2](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.5.2)）。

```
0x20 を 64 バイト
"TLS 1.3, server CertificateVerify"     文脈の文字列
0x00
Transcript-Hash(ClientHello ... Certificate)
```

トランスクリプトにはクライアントの乱数と key_share も入っているので、**この署名はこの接続でしか作れません**。録画した署名を別の接続で使い回すことはできません。そして、key_share が署名の対象に入っていることで、**中間者が鍵交換の値をすり替えると署名の検証が失敗します**。第 105 回で「鍵交換だけでは相手が誰か分からない」と述べた穴は、ここで塞がれます。

文脈の文字列は、同じ鍵で作った署名を別の用途に流用されないためのものです。

### Finished: ここまでを鍵で確かめる

Finished は、ここまでの全メッセージへの **HMAC**（第 103 回）です（[RFC 9846 4.5.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.5.3)）。

```
finished_key = HKDF-Expand-Label(server_handshake_traffic_secret, "finished", "", Hash.length)
verify_data  = HMAC(finished_key, Transcript-Hash(ClientHello ... CertificateVerify))
```

CertificateVerify が「この鍵の持ち主が話している」ことを示すのに対し、Finished は**「両者が同じメッセージを見て、同じ鍵を導いた」**ことを確かめます。途中で誰かが候補の一覧を書き換えていれば（たとえば弱い暗号スイートだけを残していれば）、両者のトランスクリプトが食い違い、Finished が一致しません。クライアントも同じ形で自分の Finished を返し、ここでハンドシェイクが終わります。

<Callout type="warn" title="よくある誤解 1: 「証明書を送ればサーバが本物だと証明できる」">
  証明書は公開の文書で、Web サイトに接続すれば誰でも手に入ります。偽のサーバも、本物の証明書をそのまま送れます。
  サーバが本物であることを示しているのは、**証明書の公開鍵に対応する秘密鍵で、この接続のトランスクリプトに署名した CertificateVerify** です。
  証明書は「この公開鍵はこの名前のものだ」と言うだけで（第 109 回）、その鍵をいま相手が持っているかは言いません。**証明書と署名は、組み合わさって初めて相手の確認になります**。
  逆に言えば、秘密鍵が漏れれば、証明書が正しくても偽のサーバが作れます。第 111 回の失効や短命な証明書が要るのはこのためです。
</Callout>

## 鍵スケジュール: HKDF で鍵を段階的に作る

共有の秘密から、いくつもの鍵を作ります。道具は第 108 回で見た **HKDF** で、TLS 1.3 はこれに「tls13 」で始まるラベルを付けて使います（[RFC 9846 7.1](https://www.rfc-editor.org/rfc/rfc9846.html#section-7.1)）。

```
             0
             │
   PSK ──→ HKDF-Extract = Early Secret ──→ 0-RTT 用の鍵、binder 用の鍵
             │
       Derive-Secret(., "derived", "")
             │
共有の秘密 ─→ HKDF-Extract = Handshake Secret
             ├─→ "c hs traffic" + Hash(CH..SH) = client_handshake_traffic_secret
             ├─→ "s hs traffic" + Hash(CH..SH) = server_handshake_traffic_secret
             │
       Derive-Secret(., "derived", "")
             │
       0 ──→ HKDF-Extract = Main Secret
             ├─→ "c ap traffic" + Hash(CH..サーバ Finished) = client_application_traffic_secret_0
             ├─→ "s ap traffic" + Hash(CH..サーバ Finished) = server_application_traffic_secret_0
             ├─→ "exp master"  エクスポータ用
             └─→ "res master"  次回の再開用（チケットのもと）
```

読みどころは 3 つです。

- **段階ごとに材料を足していく**。Early Secret には PSK を、Handshake Secret には鍵交換の秘密を混ぜます。PSK を使わないときも、同じ段を 0 で通ります
- **トランスクリプトのハッシュを混ぜる**。鍵は「この接続のこの時点までのやり取り」に結び付きます
- **向きと用途ごとに別の鍵**。クライアント→サーバとサーバ→クライアント、ハンドシェイク用とアプリケーション用で、すべて別の秘密になります。1 つが漏れても、他は導けません

各秘密からは、さらに `HKDF-Expand-Label(secret, "key", "", 鍵長)` と `"iv"` で、AEAD の鍵と IV を作ります（[RFC 9846 7.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-7.3)）。各レコードの nonce は、**IV と 64 ビットのレコード番号の XOR** です（[5.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-5.3)）。番号は毎回増えるので、第 104 回で見た「nonce の再利用」は構造上起きません。

## 第 16 章の部品との対応

ここまでをまとめると、TLS 1.3 のハンドシェイクは次のように部品を組み合わせています。

| 部品 | 使われている場所 | 担う性質 | 回 |
| --- | --- | --- | --- |
| 乱数 | ClientHello / ServerHello の random、鍵の生成 | 毎回違う鍵になる | 第 108 回 |
| 鍵交換（X25519、ML-KEM） | key_share | 盗聴者の知らない共有の秘密。前方秘匿性 | 第 105 回 |
| ハッシュ（SHA-256/384） | トランスクリプトハッシュ | やり取り全体を短い値に固定する | 第 103 回 |
| 署名（ECDSA、RSA-PSS、Ed25519） | CertificateVerify | サーバがその公開鍵の秘密鍵を持っている | 第 106 回 |
| 証明書と連鎖 | Certificate | その公開鍵がその名前のものだ | 第 109、110 回 |
| HMAC | Finished | 両者が同じやり取りを見て同じ鍵を持っている | 第 103 回 |
| HKDF | 鍵スケジュール | 1 つの秘密から用途別の鍵を安全に作る | 第 108 回 |
| AEAD（AES-GCM、ChaCha20-Poly1305） | ServerHello より後ろのすべてのレコード | 機密性と改ざんの検出 | 第 104 回 |

**どれか 1 つを抜くと、TLS は成り立ちません**。鍵交換だけなら中間者に割り込まれ、署名だけなら通信は暗号化されず、証明書だけなら誰でも名乗れ、AEAD だけなら鍵を渡す手段がありません。

<Callout type="warn" title="よくある誤解 2: 「TLS の通信はサーバの公開鍵で暗号化されている」">
  TLS 1.3 では、**証明書の公開鍵は署名の検証にしか使いません**。通信を暗号化しているのは、key_share で毎回作る使い捨ての鍵から HKDF で導いた、AEAD の共通鍵です。
  TLS 1.2 以前の RSA 鍵交換では、クライアントが秘密を証明書の公開鍵で暗号化して送っていました。そのため、**後からサーバの秘密鍵が漏れると、録っておいた過去の通信がすべて読めました**。TLS 1.3 はこの方式と静的な DH を取り除き、すべての鍵交換が前方秘匿性を持つようにしました（[RFC 9846 1.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-1.3)）。
  ですから、秘密鍵を渡して復号させる、という TLS 1.2 時代の監視装置の方式は TLS 1.3 では使えません。
</Callout>

## 手元で確かめる: 鍵ログで復号し、署名と MAC を検証する

接続の鍵を外に書き出す仕組みがあります。**SSLKEYLOGFILE** の形式で、各行に「ラベル、ClientHello の random、秘密」を書きます。2026 年 7 月に [RFC 9850](https://www.rfc-editor.org/rfc/rfc9850.html) として文書化されました。ブラウザや curl（OpenSSL 版）は環境変数 `SSLKEYLOGFILE` で、`openssl s_client` は `-keylogfile` で、Python の ssl は `SSLContext.keylog_filename` で書き出せます。

```
SERVER_HANDSHAKE_TRAFFIC_SECRET 53d914b8...  （random）  （秘密）
CLIENT_HANDSHAKE_TRAFFIC_SECRET 53d914b8...
SERVER_TRAFFIC_SECRET_0 ...
CLIENT_TRAFFIC_SECRET_0 ...
EXPORTER_SECRET ...
```

上の鍵スケジュールの図の秘密が、そのまま並んでいます。Wireshark や tshark にこのファイルを渡すと、パケットを復号して表示できます。手元には tshark が無かったので、**同じことを Python で直接やりました**。Python の ssl を `MemoryBIO` で使うと、ソケットに流れるバイト列をすべて手元で受け取れます。それを TLS のレコードに切り分け、鍵ログの秘密から鍵を作って復号します。要となる部分だけを示します。

```python
def label(secret, name, context, length, h):                # HKDF-Expand-Label
    info = struct.pack("!H", length) + bytes([len(b"tls13 " + name)]) + b"tls13 " + name
    info += bytes([len(context)]) + context
    out, t, n = b"", b"", 1
    while len(out) < length:                                   # HKDF-Expand（RFC 5869）
        t = hmac.new(secret, t + info + bytes([n]), h).digest()
        out, n = out + t, n + 1
    return out[:length]

s_hs = secrets["SERVER_HANDSHAKE_TRAFFIC_SECRET"]
key = label(s_hs, b"key", b"", 32, hashlib.sha384)           # AES-256-GCM の鍵
iv  = label(s_hs, b"iv",  b"", 12, hashlib.sha384)

nonce = bytes(a ^ b for a, b in zip(iv, b"\0" * 4 + struct.pack("!Q", seq)))
inner = AESGCM(key).decrypt(nonce, body, record_header)       # 5 バイトのレコードヘッダが関連データ

# CertificateVerify: 証明書の公開鍵で、トランスクリプトへの署名を検証
signed = b" " * 64 + b"TLS 1.3, server CertificateVerify" + b"\0" + sha384(CH..Certificate)
cert.public_key().verify(sig, signed, ec.ECDSA(hashes.SHA256()))

# Finished: 自分で HMAC を計算して比べる
fk = label(s_hs, b"finished", b"", 48, hashlib.sha384)
mine = hmac.new(fk, sha384(CH..CertificateVerify), hashlib.sha384).digest()
```

実行結果です（手元の出力）。

```
cipher: TLS_AES_256_GCM_SHA384  alpn: h2
server handshake key: 54095bb6eba374d655d8cae36ff94aa2... iv: 088e26905abe8874fc434a02
plain     type=22 len=1210 -> ServerHello
plain     type=20 len=   1 -> ChangeCipherSpec (互換用のダミー)

   CertificateVerify: 証明書の公開鍵で検証 OK
   文脈文字列を client に変えると NG

```

読みどころは次のとおりです。

- 暗号化されたレコードの外側の型は、すべて **23（application_data）** です。本当の型（22 = handshake）は**暗号文の中の末尾の 1 バイト**に入っています（[RFC 9846 5.2](https://www.rfc-editor.org/rfc/rfc9846.html#section-5.2)）。外からは、ハンドシェイクなのかアプリケーションのデータなのかも区別できません
- 暗号文を 1 ビット反転させると、復号は `InvalidTag` で失敗しました。第 104 回で見た AEAD の改ざん検出です
- CertificateVerify は、**自分で組み立てた署名対象**で検証が通りました。文脈の文字列を 1 語変えるだけで失敗します
- Finished は、**自分で計算した HMAC と一致**しました。鍵ログの秘密と、自分で持っているトランスクリプトだけで再現できたことになります

<Callout type="warn" title="鍵ログは本番で使わない">
  鍵ログのファイルがあれば、その接続は誰でも復号できます。RFC 9850 は、この仕組みを**本番のシステムで使ってはならない（MUST NOT）**と書いています。
  環境変数 `SSLKEYLOGFILE` を読むライブラリは多く、コンテナの設定に残ったまま本番へ出ると、すべての通信の鍵がファイルに書き続けられます。
  なお、鍵ログがあっても、ハンドシェイク用の鍵から ML-KEM や X25519 の秘密を逆に求めることはできません。書き出しているのは HKDF の下流の秘密だけです。
</Callout>

## TLS 1.2 から何が変わったか

[RFC 9846 1.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-1.3) の一覧のうち、主なものを整理します。

| 項目 | TLS 1.2 | TLS 1.3 |
| --- | --- | --- |
| 往復数 | 2 往復 | 1 往復（再開なら 0-RTT も可） |
| 鍵交換 | RSA 鍵交換、静的 DH、ECDHE など | **(EC)DHE と PSK だけ**。すべて前方秘匿性あり |
| 暗号スイート | 鍵交換・認証・暗号・MAC の組（`TLS_ECDHE_RSA_WITH_AES_128_CBC_SHA` など）で数百 | **AEAD とハッシュの組だけ**。定義は 3 つ（[B.4](https://www.rfc-editor.org/rfc/rfc9846.html#appendix-B.4)） |
| 暗号方式 | CBC + MAC、RC4 なども | **AEAD だけ** |
| 証明書 | 平文で流れる | 暗号化される |
| 鍵の導出 | 独自の PRF | HKDF |
| RSA の署名 | PKCS#1 v1.5 | ハンドシェイクでは **RSA-PSS** |
| 再ネゴシエーション、圧縮 | あり | なし |

暗号スイートが短くなったのは、**鍵交換と署名を別の拡張（supported_groups と signature_algorithms）に切り出した**からです。組み合わせの数だけ名前を作る必要がなくなりました。

### ダウングレードを防ぐ

攻撃者が ClientHello の supported_versions を消して、両者を TLS 1.2 で話させようとしたらどうなるでしょうか。TLS 1.3 を話せるサーバは、やむを得ず TLS 1.2 で応じるとき、**ServerHello.random の最後の 8 バイトを `DOWNGRD` と 0x01 にする**決まりです（[RFC 9846 4.2.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.2.3)）。手元で `-tls1_2` を付けて接続すると、そのとおりでした。

```
ServerHello, Length=59
  server_version=0x303 (TLS 1.2)
  random_bytes (len=28): F59F3378842504404EC1B960BCB549EF4538205B444F574E47524401
                                                                 D O W N G R D \1
```

両者の random は、TLS 1.2 でも ECDHE の署名と Finished の対象に入るので、攻撃者はこの 8 バイトを書き換えられません。TLS 1.3 を話せるクライアントは、これを見たら接続を中止します。

## 送り直し: HelloRetryRequest

クライアントが送った key_share を、サーバが 1 つも受け付けない場合があります。サーバを `-groups P-256` で起動し直して接続すると、ClientHello が 2 回送られました。

```
ClientHello, Length=1458    key_share: X25519MLKEM768, ecdh_x25519
ServerHello, Length=84      random: CF21AD74E59A6111BE1D8C021E65B891C2A211167ABB8C5E079E09E2C8A8339C
                            key_share: secp256r1（「この方式で」という指定だけ）
ClientHello, Length=271     key_share: secp256r1
ServerHello, Length=151     key_share: secp256r1
EncryptedExtensions ...
```

1 回目の ServerHello が **HelloRetryRequest** です。形は ServerHello と同じで、random に **SHA-256("HelloRetryRequest") という固定の値**が入っていることで区別します（[RFC 9846 4.2.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.2.3)、[4.2.4](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.2.4)）。1 往復増えるので、クライアントは**相手が受け付けそうな方式を先に送っておく**ことが大事です。2 つ目の ClientHello が小さいのは、ML-KEM の 1216 バイトが無くなったためです。

## 再開と 0-RTT

### PSK による再開

ハンドシェイクが終わると、サーバは **NewSessionTicket** を送ります（[RFC 9846 4.7.1](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.7.1)）。チケットは、鍵スケジュールの `res master` から導いた PSK（事前共有鍵）に結び付いています。次の接続で ClientHello に `pre_shared_key` 拡張としてチケットを入れると、証明書の検証を省いて再開できます。

```
ClientHello, Length=1553     ... key_share(51), psk(41)
ServerHello, Length=1212     ... key_share(51), psk(41)
EncryptedExtensions, Length=2
Finished, Length=48          ← Certificate と CertificateVerify が無い
Finished, Length=48
Reused, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
```

ClientHello の `psk_key_exchange_modes` が `psk_dhe_ke` だったので、再開でも **key_share による鍵交換を併用**しています。PSK だけで鍵を作る `psk_ke` もありますが、その場合は前方秘匿性がありません（[RFC 9846 4.3.9](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.3.9)）。

### 0-RTT: 速さと引き換えに失うもの

PSK があれば、クライアントは ClientHello と**同時に**、PSK から導いた鍵（Early Secret の段の `c e traffic`）でリクエストを暗号化して送れます。これが 0-RTT（early data）です。`-early_data` を付けて試しました。同じチケットで 2 回続けて試しています。

```
---- 1 回目
>>> ClientHello
<<< ServerHello, EncryptedExtensions, Finished
>>> EndOfEarlyData, Finished
Reused, TLSv1.3 ...
Early data was accepted            サーバ側: Early data received: GET / HTTP/1.0
---- 2 回目（同じチケット）
>>> ClientHello
<<< ServerHello, EncryptedExtensions, Certificate, CertificateVerify, Finished
Early data was rejected
```

2 回目は 0-RTT が拒まれ、証明書付きの完全なハンドシェイクに戻りました。openssl の `s_server` は、early data を有効にすると**チケットを 1 回しか受け付けない**からです。これは RFC の挙げるリプレイ対策の 1 つ（使い捨てのチケット）です（[RFC 9846 8.1](https://www.rfc-editor.org/rfc/rfc9846.html#section-8.1)）。

<Callout type="warn" title="よくある誤解 3: 「0-RTT のデータも、通常のデータと同じく守られている」">
  0-RTT のデータは、サーバがまだ一言も返していない段階で送られます。そのため、**経路上の誰かがそれを録っておき、サーバに送り直す**のを TLS だけでは防げません（[RFC 9846 2.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-2.3)、[8](https://www.rfc-editor.org/rfc/rfc9846.html#section-8)）。
  使い捨てのチケットは 1 台のサーバの中では効きますが、複数のサーバやデータセンタに分かれていると、全台で使用済みの記録を共有しない限り抜けがあります。また、0-RTT のデータは PSK だけで暗号化されるので、前方秘匿性もありません。
  だから第 66 回で見たとおり、HTTP では **GET のような安全なメソッドだけ**を 0-RTT で送り、サーバは危ないものを `425 Too Early` で断ります（[RFC 8470](https://www.rfc-editor.org/rfc/rfc8470.html)）。
</Callout>

## それでも平文で残るもの: SNI と ECH

ここまでで、ServerHello より後ろはすべて暗号化されました。しかし、**ClientHello は平文**です。鍵交換の前なので、暗号化する鍵がまだありません。第 62 回で見たとおり、SNI（接続先のホスト名）と ALPN の一覧は経路上から読めます。

これを塞ぐのが第 62 回の **ECH**（[RFC 9849](https://www.rfc-editor.org/rfc/rfc9849.html)、2026 年 3 月）です。サーバの公開鍵を DNS の HTTPS レコード（第 58 回）で事前に配り、本当の ClientHello をその鍵で暗号化して、外側の当たり障りのない ClientHello に包んで送ります。ここでも**「事前に相手の公開鍵をどこかで知る」**という部品が要ることになります。

## 保証すること、しないこと

| TLS 1.3 のハンドシェイクが保証する | 保証しない |
| --- | --- |
| 通信の中身が盗み見られない（機密性） | 接続先の IP、SNI（ECH が無ければ）、通信量と時刻 |
| 改ざんを検出できる（AEAD、Finished） | 相手のサーバが善良であること。**証明書は名前を確かめるだけ** |
| 相手が、証明書の名前の秘密鍵を持っている | クライアントが誰か（それは第 113 回の mTLS や第 18 章の認証） |
| 後から秘密鍵が漏れても過去の通信は読めない | 0-RTT のデータのリプレイ |
| 候補の書き換えやダウングレードを検出できる | 通信の端（サーバの中）で平文がどう扱われるか |

特に、**TLS が確かめるのは「接続した名前の鍵を持つ相手」であって、その相手の中身ではない**ことは押さえておいてください。フィッシングサイトも、自分のドメインの正しい証明書を持てば TLS は問題なく成立します。

## まとめ

- TLS 1.3 は、ClientHello で鍵交換の公開鍵（key_share）まで先に送ることで、1 往復で鍵を決める。仕様は 2026 年 7 月から RFC 9846
- ClientHello は TLS 1.2 のふりをし、本当のバージョンは supported_versions で伝える。暗号スイートは AEAD とハッシュの組だけで、鍵交換と署名は別の拡張で選ぶ
- ServerHello より後ろ（EncryptedExtensions、Certificate、CertificateVerify、Finished）はすべて暗号化される
- CertificateVerify は、トランスクリプトへの署名で**秘密鍵を持っていること**を示す。key_share も署名の対象なので、中間者の割り込みを検出できる
- Finished は、トランスクリプトへの HMAC で**両者が同じやり取りを見て同じ鍵を持つこと**を確かめる
- 鍵は HKDF で段階的に導き、トランスクリプトに結び付け、向きと用途ごとに分ける。nonce は IV とレコード番号の XOR
- 鍵交換、署名、証明書、ハッシュ、HMAC、HKDF、AEAD の**どれが欠けても成り立たない**
- 受け付けられない key_share には HelloRetryRequest で 1 往復足す。TLS 1.2 へ落とされたら random の `DOWNGRD` で気づく
- PSK による再開は証明書を省き、0-RTT は往復を 0 にするが、リプレイを防げず前方秘匿性も無い
- 鍵ログ（SSLKEYLOGFILE、RFC 9850）で観察できるが、本番で使ってはならない。ClientHello の SNI は ECH が無ければ平文

次の回では、この TLS を**どこで終えるか**を見ます。ロードバランサで終えるのか、サーバまで通すのか。誰が平文を見て、誰が秘密鍵を持つのか。そして、今回サーバだけが送った Certificate と CertificateVerify を、クライアントも送る mTLS に進みます。
