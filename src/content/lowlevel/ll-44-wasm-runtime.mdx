## ブラウザの外へ

前回見たとおり、Wasm には**システムコールがありません**。ホストが渡した関数しか呼べない。

ブラウザでは、ホストが JavaScript なのでそれでよかった。しかし、サーバやコマンドラインで動かすなら、ファイルもネットワークも要ります。

そこで 2019 年、**WASI**（WebAssembly System Interface）が提案されます。

> **標準的な「ホストが渡す関数」の一覧を決める。**

ファイルを開く、読む、書く、時刻を取る、乱数を得る。POSIX に近い一式が定義されました。

<Callout type="note" title="Docker の作者の言葉">
  WASI が発表された日、Docker の創業者 Solomon Hykes はこう書きました。

  > If WASM+WASI existed in 2008, we wouldn't have needed to create Docker.
  > （WASM と WASI が 2008 年にあったなら、Docker を作る必要はなかった）

  誇張はありますが、指している構造は正確です。
  第 9 章で見るコンテナは「OS の機能を使って見える範囲を制限する」もの、
  Wasm は「**そもそも何も見えないところに、必要なものだけ渡す**」ものです。
</Callout>

## ケイパビリティという考え方

WASI の設計で最も重要なのは、**渡し方**です。

```bash
# このディレクトリだけを見せる
wasmtime run --dir=/tmp/sandbox app.wasm
```

Wasm 側は「ファイルシステム全体」を見られません。**ホストが渡したディレクトリのハンドルから辿れる範囲だけ**です。

`open("/etc/passwd")` に相当する操作が、そもそもできない。パスを絶対パスで指定する手段が無いからです。

| 方式 | 考え方 | 例 |
| --- | --- | --- |
| **アクセス制御リスト** | 全部できる状態から、禁止を足す | Unix の権限、seccomp、SELinux |
| **ケイパビリティ** | **何もできない状態から、許可を渡す** | WASI、Capsicum、ブラウザの権限 |

第 7 章で見た seccomp は前者でした。**システムコールは全部呼べるが、フィルタで塞ぐ**。塞ぎ忘れがあれば抜けられます。

WASI は後者です。**渡していないものは、存在しないのと同じ**。塞ぎ忘れという概念がありません。

<Callout type="tip" title="混乱しやすい用語の整理">
  「ケイパビリティ」は Linux では別の意味でも使われます（`CAP_NET_ADMIN` など、
  root の権限を細分化したもの）。こちらは**アクセス制御リストの側**です。

  ここで言うケイパビリティは、**「持っていることが権限そのものである券」**という意味です。
  ファイルディスクリプタ（第 7 章）が、実はこれに近い性質を持っています。
  fd を持っていれば読める。持っていなければ、パスを知っていても開き直す必要がある。
</Callout>

## ランタイムの選択肢

Wasm を実行する処理系は複数あります。**同じバイトコードを、どう機械語にするか**が違います。

| ランタイム | 実装 | 実行方式 | 特徴 |
| --- | --- | --- | --- |
| **Wasmtime** | Rust | JIT（Cranelift）+ Winch | Bytecode Alliance の標準実装。コンポーネントモデル対応 |
| **Wasmer** | Rust | JIT（LLVM / Cranelift / Singlepass） | 組み込みやすさ重視。WASIX という独自拡張 |
| **WasmEdge** | C++ | AOT | CNCF プロジェクト。エッジ向け |
| **WAMR** | C | インタプリタ / AOT | 組み込み向け。極小のフットプリント |
| **wazero** | **Go** | インタプリタ / コンパイラ | **cgo に依存しない**。Go から使うときの定番 |

速度の目安です。2026 年の計測では、ネイティブを 1 としたとき、

| ランタイム | ネイティブ比 |
| --- | --- |
| WAMR（AOT） | 約 1.6 倍 |
| Wasmtime（JIT） | 約 2.4 倍 |
| wazero | 約 4.7 倍 |

（[Performance of WebAssembly runtimes in 2026](https://00f.net/2026/06/23/webassembly-runtimes-2026/)）

<Callout type="warn" title="wazero が遅いのには理由がある">
  wazero は **Pure Go** です。cgo を使わないので、
  第 1 回で見た「C コンパイラが必要」「クロスコンパイルが難しい」という問題が消えます。

  その代わり、コード生成を Go だけで書く必要があり、
  LLVM や Cranelift ほどの最適化はできません。

  **FFI の面倒を避けるために、速度を差し出している。**
  この連載で何度も出てきた交換が、ここにも現れています。
</Callout>

## Wasm を FFI として使う

ここが本題です。

第 1 回で見たとおり、FFI の根本的な問題は、

> **C 側で SIGSEGV が起きると、ホストプロセス全体が落ちる。**

Wasm を使うと、この前提が変わります。

```
従来の FFI:
  ホストプロセス
    └─ dlopen した .so  ← ここで壊れると全部死ぬ

Wasm による FFI:
  ホストプロセス
    └─ Wasm ランタイム
         └─ Wasm インスタンス  ← ここで壊れても、トラップして戻ってくるだけ
```

得られるものを並べます。

| | 従来の FFI | Wasm 経由 |
| --- | --- | --- |
| クラッシュの波及 | **プロセス全体** | インスタンスだけ |
| ホストのメモリを壊せるか | **壊せる** | 壊せない |
| システムコール | 全部使える | **渡したものだけ** |
| 実行時間の制限 | できない | **できる**（fuel / 燃料計測） |
| メモリ使用量の制限 | できない | できる |
| C コンパイラ | **必要** | 不要（配布時） |
| クロスコンパイル | 難しい | **同じ .wasm がどこでも動く** |
| 速度 | ネイティブ | **2〜5 倍遅い** |
| 境界でのデータ受け渡し | ポインタを渡すだけ | **線形メモリへのコピーが要る** |

<Callout type="tip" title="fuel（燃料）による実行時間の制限">
  Wasm ランタイムの多くは、**実行した命令数を数えて、上限で止める**機能を持ちます。

  無限ループするプラグインを読み込んでも、ホストは止まりません。
  従来の FFI では、C 側が固まったらホストも固まります。

  第 6 章で見たプリエンプションを、**ランタイムがソフトウェアで実現している**形です。
</Callout>

### 代償：境界でのコピー

Wasm の線形メモリは、ホストのメモリとは別の領域です。

```
ホスト側のバッファ  ──[コピー]──▶  線形メモリ  ──▶  Wasm の関数
                                      │
ホスト側の結果      ◀──[コピー]──────┘
```

**ポインタを渡すだけでは済みません。** 大きなデータをやり取りすると、このコピーが支配的になります。

第 7 章で見たゼロコピーの話と、ちょうど逆です。安全のために、コピーを 1 回増やしています。

## 実例：Go における FFI の変遷

Go は、この問題が最も分かりやすく現れる言語です。

**cgo の課題**は、第 1 回で見たものがすべて当てはまります。C コンパイラが必要でクロスコンパイルが難しく、C 側の SIGSEGV でホストが落ち、呼び出しのたびにスタック切り替えのコストがかかる。

そこで、**C のライブラリを Wasm にコンパイルして、wazero で動かす**というアプローチが試みられています。安全性とクロスコンパイルの問題は解決しますが、**性能が大きく落ちます**。

さらに進んだ手法として、**Wasm を Go のソースコードに変換してしまう**（wasm2go のような方式）という試みもあります。Wasm の命令を Go のコードに 1 対 1 で書き下し、Go のコンパイラに最適化させる。ランタイムの解釈コストが消えるので速くなります。

ただし、ここでも新しい問題が出ます。

- **生成コードが Wasm の 6〜20 倍に膨らむ**。ビルド時間とメモリ使用量が問題になる
- **インスタンスごとに独立した線形メモリが必要**。同じデータが複製され、メモリを食う

2 つめへの対策が興味深い。**`mmap(MAP_PRIVATE)` でコピーオンライトを使う**、というものです。

第 4 章で見たとおり、`MAP_PRIVATE` なページは書き込むまで物理メモリを共有します。同じ Wasm モジュールの複数インスタンスは、**初期状態のデータを共有したまま、書き換えた部分だけが分かれます**。これにより、同じメモリ量で扱えるインスタンス数が大きく増えます。

（[Go における FFI のこれまでとこれから](https://speakerdeck.com/goccy/go-niokeru-ffi-no-kore-madeto-korekara) — Masaaki Goshima）

<Callout type="note" title="第 4 章の CoW が、ここで効いている">
  `fork` を実用的にした仕組みが、Wasm のインスタンスを大量に並べるためにも使われる。

  **同じ構造の問題には、同じ解が効きます。**
  「初期状態が同じものを大量に作る」という形が同じだからです。
</Callout>

## 型を持った境界へ

線形メモリを使った FFI には、まだ不便な点があります。**受け渡せるのは数値だけ**です。

```wat
(func (export "greet") (param i32 i32) (result i32))
;;                      ptr  len        ptr（文字列は自分で組み立てる）
```

文字列も構造体も、**ポインタと長さに分解して、線形メモリに手で書く**必要があります。第 1 回で見た FFI の面倒が、そのまま残っています。

これを解決するのが **コンポーネントモデル** と、インタフェース記述言語の **WIT** です。次回まるごと扱います。

## 使いどころ

Wasm を FFI として使うべき場面と、そうでない場面があります。

| 状況 | 向いているか |
| --- | --- |
| **信頼できないコードを動かす**（プラグイン、ユーザ定義関数） | **非常に向く** |
| クロスコンパイルを保ちたい | 向く |
| ライブラリのクラッシュで落ちたくない | 向く |
| 呼び出しが粗い（1 回で大きな仕事） | 向く |
| **計算そのものが最速でなければならない** | **向かない**（2〜5 倍遅い） |
| 大きなデータを頻繁にやり取りする | 向かない（コピーが効く） |
| 呼び出しが細かい（ループで何百万回） | 向かない |
| OS の機能を深く使う | 向かない |

**プラグイン機構が最も分かりやすい用途です。**

サードパーティのコードを自分のプロセスに読み込むのは、従来なら受け入れがたいリスクでした。Wasm なら、メモリも、システムコールも、実行時間も制限した上で読み込めます。

データベースのユーザ定義関数、エディタの拡張、CDN のエッジ関数、Kubernetes 上のワークロード。**「他人のコードを、安全に、速く動かす」**という要求がある場所に広がっています。

<Callout type="warn" title="万能ではない">
  Wasm を使えば FFI の問題が全部消えるわけではありません。

  - **Wasm の中身は相変わらず壊れる**（前回）。外に出ないだけ
  - **速度は確実に落ちる**
  - **境界の設計は自分でやる**。何を渡し、何を渡さないか
  - **エコシステムがまだ動いている**。WASI 0.2 と 0.3 で仕様が変わり続けている

  「速度重視ならネイティブ、安全性と配布のしやすさ重視なら Wasm」という、
  いつもの交換です。
</Callout>

## 分離の仕組みの系譜

この連載で見てきた「壊れたときに波及させない」仕組みを、並べ直してみます。

| 仕組み | 境界 | 強制するもの | 章 |
| --- | --- | --- | --- |
| **特権レベル（リング）** | ユーザ / カーネル | CPU | 第 2 章 |
| **仮想メモリ** | プロセス間 | MMU | 第 4 章 |
| **プロセス分離** | プロセス間 | OS | 第 6 章 |
| **seccomp** | システムコール | カーネル（引き算） | 第 7 章 |
| **コンテナ** | 名前空間 + cgroup | カーネル | 第 9 章 |
| **仮想マシン** | ゲスト OS | ハイパーバイザ + VT-x | 第 9 章 |
| **Wasm** | 線形メモリ | **仕様と検証（足し算）** | この章 |

**下に行くほど、ハードウェアへの依存が減り、粒度が細かくなっています。**

リングと MMU は、CPU の機能そのものでした。コンテナはカーネルの機能。Wasm は**仕様とその検証**だけで分離を成立させています。だから、MMU を持たない機械でも、ブラウザの中でも、同じ保証が得られます。

そして方向が逆転しています。第 7 章の seccomp が「全部できる状態から塞ぐ」だったのに対し、Wasm は「**何もできない状態から渡す**」。塞ぎ忘れという失敗の形が、そもそも存在しません。

## まとめ

- WASI は「ホストが渡す関数」の標準を決めたもの。ブラウザの外で Wasm を動かすための土台
- 権限は**ケイパビリティ**として渡される。渡していないものは存在しない
- ランタイムは複数あり、速度と可搬性が交換関係にある（WAMR 1.6 倍 / Wasmtime 2.4 倍 / wazero 4.7 倍）
- **Wasm を FFI に使うと、クラッシュが波及せず、システムコールも実行時間も制限できる**
- 代償は速度と、境界でのデータコピー
- Go では cgo → Wasm ランタイム → Wasm の Go コードへの変換、という試行が続いている
- コンポーネントモデルと WIT が、文字列や構造体を型として扱えるようにした。WASI 0.3（2026 年 6 月）で非同期も言語機構に入った
- 分離の仕組みは、ハードウェア依存から仕様ベースへ、引き算から足し算へと移ってきている

次は、この「受け渡せるのは数値だけ」という制約をどう外したかを見ます。
