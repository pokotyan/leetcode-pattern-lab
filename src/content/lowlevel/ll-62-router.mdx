## 道のりを知っている人はいない

前の 2 回では、同じ線の上（同じブロードキャストドメインの中）でフレームを届ける仕組みを見ました。スイッチは MAC アドレスを覚えて、正しいポートにだけフレームを出します。しかしスイッチが扱えるのは、自分の配下にいる相手までです。別のネットワークにいる相手へは、**ルーター**がパケットを渡していきます。

インターネットで東京から海外のサーバへパケットを送ると、途中で 10 台を超えるルーターを通ることも珍しくありません。それでも、出発点から終点までの道のりを全部知っている機械は、どこにもありません。各ルーターが知っているのは、**この宛先なら、次は隣のどのルーターに渡せばよいか**だけです。パケットは、この「次の 1 手」の判断を積み重ねて目的地に着きます。

この回では、その判断を 3 つの段に分けて見ていきます。

1. 送る側の端末が、相手に直接届けるのか、ルーターに預けるのかを決める
2. ルーターが、経路表を引いて次の渡し先を決める
3. その経路表を、人が書くのか、ルーター同士に作らせるのか

実験には、Docker の Linux コンテナ（OrbStack の VM、カーネル 7.0.14、Alpine Linux 3.20、iproute2 6.9.0、tcpdump 4.99.4）の中に作った 4 つのネットワーク名前空間（netns）を使います。netns はカーネルの中に独立したネットワークの部品一式（インターフェース、経路表、ARP の表）を作る仕組みで、1 つが 1 台の機械のように振る舞います。

```
  h1 ──────────── r1 ──────────────── r2 ──────────── h2
  10.0.1.10   10.0.1.1  10.0.12.1   10.0.12.2  10.0.2.1   10.0.2.10
     （10.0.1.0/24）       （10.0.12.0/24）       （10.0.2.0/24）
```

`h1` と `h2` が端末、`r1` と `r2` がルーターです。どこもプライベートアドレス（[RFC 1918](https://www.rfc-editor.org/rfc/rfc1918.html) の `10.0.0.0/8`）で、どの MAC アドレスも、読みやすいように手で決めた値に固定しました（`02:00:00:00:01:10` なら「10.0.1.0/24 の線にいる .10」）。

## アドレスの左と右: プレフィックス長

IPv4 のアドレスは 32 ビットの数です。`10.0.2.10` は 8 ビットずつ区切って 10 進で書いたもので、2 進ではこうなります。

```
10.0.2.10  = 00001010 00000000 00000010 00001010
```

このうち**左から何ビットまでが「どのネットワークか」を表すか**を、スラッシュの後ろの数で示します。`10.0.2.0/24` は「左の 24 ビットが `00001010 00000000 00000010` であるアドレスの集まり」で、残り 8 ビットがそのネットワークの中の個々の機械を区別します。左側をネットワーク部（プレフィックス）、右側をホスト部と呼び、スラッシュの数を**プレフィックス長**と呼びます。

昔の IPv4 は、アドレスの先頭のビットでネットワーク部の長さが 8・16・24 のどれかに決まっていました（クラス A・B・C）。これでは大きさが 256 倍ずつしか選べず、アドレスが無駄になります。そこで長さを自由に書けるようにしたのが **CIDR**（Classless Inter-Domain Routing）で、今の表記はすべてこの形です（[RFC 4632](https://www.rfc-editor.org/rfc/rfc4632.html)）。`/24` を `255.255.255.0` と書く**サブネットマスク**は、同じことを「1 が並ぶ部分がネットワーク部」というビット列で表したものです。

## 端末が最初に決めること: 直接か、ゲートウェイか

`h1` が持っている経路表は、起動した時点でこれだけです。

```
$ ip route        # h1
10.0.1.0/24 dev h1-eth0 proto kernel scope link src 10.0.1.10
```

自分のインターフェースにアドレス `10.0.1.10/24` を付けたので、カーネルが「`10.0.1.0/24` はこの線に直接つながっている」という経路を自動で入れました（`proto kernel scope link`）。この状態で `h2` に ping を打つと、パケットは 1 つも出ていきません。

```
$ ping 10.0.2.10    # h1
ping: connect: Network unreachable
```

`10.0.2.10` は `10.0.1.0/24` に入らないので、どの線に出せばよいかが分からないからです。そこで**デフォルトゲートウェイ**を足します。「どこにも当てはまらない宛先は `10.0.1.1`（r1）に預ける」という経路です。

```
$ ip route add default via 10.0.1.1      # h1
```

端末の判断はこれで全部です。**宛先が自分のつながっている線の中にいれば、その相手の MAC アドレスを ARP で調べて直接送る。いなければ、ゲートウェイの MAC アドレスを調べて、ゲートウェイ宛てのフレームに入れて送る。** どちらの場合も、IP ヘッダの宛先は最終的な相手のままです。違うのは、フレームの宛先 MAC アドレスだけです。ARP の仕組みは第 60 回で見ました。

## ルーターは宛先を見て、表を引いて、渡す

ゲートウェイを足しても、まだ届きません。

```
$ ping -c1 10.0.2.10    # h1
From 10.0.1.1 icmp_seq=1 Destination Net Unreachable
```

今度はパケットが `r1` まで届き、`r1` が「その宛先への道を知らない」と返してきました。`r1` の経路表には、自分が直接つながっている 2 本の線しかありません。

```
$ ip route        # r1
10.0.1.0/24 dev r1-eth0 proto kernel scope link src 10.0.1.1
10.0.12.0/24 dev r1-eth1 proto kernel scope link src 10.0.12.1
```

`r1` と `r2` に、相手の向こう側のネットワークへの経路を 1 行ずつ書き足します。

```
$ ip route add 10.0.2.0/24 via 10.0.12.2    # r1: 10.0.2.0/24 へは r2 に渡す
$ ip route add 10.0.1.0/24 via 10.0.12.1    # r2: 10.0.1.0/24 へは r1 に渡す
```

```
$ ping -c2 10.0.2.10    # h1
64 bytes from 10.0.2.10: icmp_seq=1 ttl=62 time=1.12 ms
64 bytes from 10.0.2.10: icmp_seq=2 ttl=62 time=0.047 ms
```

届きました。ここで `r1` と `r2` がしたことは、どちらも同じです。**受け取ったパケットの宛先 IP で自分の経路表を引き、一致した行の次ホップへ渡す。** `r1` は `h2` の居場所を知りません。知っているのは「`10.0.2.0/24` なら `10.0.12.2` へ」という 1 行だけです。そして `r2` は、`r1` がどう判断したかを一切受け取らずに、自分の表を引き直します。

なお、Linux は既定ではパケットを転送しません。ルーター役の 2 つの netns では `net.ipv4.ip_forward=1` を設定してあります。これを 0 にすると、自分宛てでないパケットは捨てられ、どんな経路を書いても届きません。

## 表を引く規則: 最長一致

経路表の行どうしが重なることがあります。`r1` に、`10.0.2.0/24` のうち後ろ半分の `10.0.2.128/25` だけは別の場所へ送る行と、どれにも当てはまらないときの既定経路 `0.0.0.0/0` を足しました。

```
$ ip route        # r1
default via 10.0.12.2 dev r1-eth1
10.0.1.0/24 dev r1-eth0 proto kernel scope link src 10.0.1.1
10.0.2.0/24 via 10.0.12.2 dev r1-eth1
10.0.2.128/25 via 10.0.1.10 dev r1-eth0
10.0.12.0/24 dev r1-eth1 proto kernel scope link src 10.0.12.1
```

`10.0.2.200` は `0.0.0.0/0` にも `10.0.2.0/24` にも `10.0.2.128/25` にも入ります。カーネルにどの行を使うかを聞くと、こうなります。

```
$ ip route get 10.0.2.10
10.0.2.10 via 10.0.12.2 dev r1-eth1 src 10.0.12.1 uid 0
$ ip route get 10.0.2.200
10.0.2.200 via 10.0.1.10 dev r1-eth0 src 10.0.1.1 uid 0
$ ip route get 8.8.8.8
8.8.8.8 via 10.0.12.2 dev r1-eth1 src 10.0.12.1 uid 0
```

`10.0.2.200` には `/25` が、`10.0.2.10` には `/24` が、どちらにも入らない `8.8.8.8` には既定経路が選ばれました。**一致する行のうち、プレフィックス長がいちばん長いもの**を使う、という規則です。これを**最長一致**（longest match）と呼びます。CIDR の RFC は、これを最初の規則として掲げています。

> 1.  Forwarding in the Internet is done on a longest-match basis.
>
> （[RFC 4632 5.1](https://www.rfc-editor.org/rfc/rfc4632.html#section-5.1)）

ルーターの要件をまとめた RFC 1812 は、手順を 2 段に分けて書いています。まず宛先と上位ビットが一致しない行を捨て（Basic Match）、残った中から最も長いものを選びます（Longest Match）。例として挙げているのは、宛先 `10.144.2.5` に対して `10.144.2.0/24`、`10.144.0.0/16`、`10.0.0.0/8` が残る場合で、「this rule would keep only the first (10.144.2.0/24) because its prefix length is longest（この規則は、プレフィックス長が最も長いので最初のもの（10.144.2.0/24）だけを残す）」と述べています（[RFC 1812 5.2.4.3](https://www.rfc-editor.org/rfc/rfc1812.html#section-5.2.4.3)）。

既定経路 `0.0.0.0/0` は、比べるビットが 0 本なので、どの宛先とも一致します。そして長さが 0 なので、ほかに一致する行が 1 本でもあれば必ず負けます。「最後の受け皿」として振る舞うのは、特別扱いされているからではなく、この規則から自然に出てくる性質です。既定経路を消して `8.8.8.8` を引くと、一致する行がなくなります。

```
$ ip route get 8.8.8.8      # 既定経路を消した r1
RTNETLINK answers: Network unreachable
```

下のシミュレーターで、宛先と各行を 2 進で並べて比べる様子を 1 手ずつ追えます。行の並び順を変えても結果が変わらないことも確かめられます。

## 渡すたびに書き換わるもの、書き換わらないもの

`h1` から `h2` への 1 つのパケットを、3 本の線の上でそれぞれ捕まえました（`tcpdump -e` でイーサネットのヘッダも出しています。行頭の時刻は省いています）。

```
--- h1 と r1 の間
02:00:00:00:01:10 > 02:00:00:00:01:01, ethertype IPv4 (0x0800), length 98: (tos 0x0, ttl 64, id 61722, offset 0, flags [DF], proto ICMP (1), length 84)
    10.0.1.10 > 10.0.2.10: ICMP echo request, id 56, seq 1, length 64
--- r1 と r2 の間
02:00:00:00:12:01 > 02:00:00:00:12:02, ethertype IPv4 (0x0800), length 98: (tos 0x0, ttl 63, id 61722, offset 0, flags [DF], proto ICMP (1), length 84)
    10.0.1.10 > 10.0.2.10: ICMP echo request, id 56, seq 1, length 64
--- r2 と h2 の間
02:00:00:00:02:01 > 02:00:00:00:02:10, ethertype IPv4 (0x0800), length 98: (tos 0x0, ttl 62, id 61722, offset 0, flags [DF], proto ICMP (1), length 84)
    10.0.1.10 > 10.0.2.10: ICMP echo request, id 56, seq 1, length 64
```

同じパケットであることは、IP ヘッダの `id 61722` が 3 つとも同じことから分かります。そのうえで、次のことが読み取れます。

- **イーサネットの送信元と宛先は、線ごとに全部違う。** どの線でも「その線の上の送り手」から「その線の上の次の受け手」宛てになっている
- **IP の送信元と宛先は、最初から最後まで `10.0.1.10 > 10.0.2.10` のまま**
- **TTL だけが 64、63、62 と 1 つずつ減っている**

ルーターは、受け取ったフレームの外側（イーサネットのヘッダ）を外し、中の IP パケットの宛先で表を引き、次ホップの MAC アドレスを ARP の表から引いて、新しい外側を付けて送り出しています。`r1` の ARP の表に載っているのは、隣にいる `r2`（`10.0.12.2`）と `h1` だけです。遠くにいる `h2` の MAC アドレスを `r1` が知る必要はありません。

```
$ ip neigh        # r1
10.0.12.2 dev r1-eth1 lladdr 02:00:00:00:12:02 REACHABLE
10.0.1.10 dev r1-eth0 lladdr 02:00:00:00:01:10 DELAY
```

### TTL: 迷子のパケットを消すための数

TTL（Time to Live）は、IP ヘッダの 8 ビットの欄です。もともとは秒の単位で、IP の仕様は「every module that processes a datagram must decrease the TTL by at least one even if it process the datagram in less than a second（データグラムを処理するどの部分も、処理が 1 秒未満で終わったとしても TTL を少なくとも 1 減らさなければならない）」と定めています（[RFC 791 3.1](https://www.rfc-editor.org/rfc/rfc791.html#section-3.1)）。実際には 1 秒も保持するルーターはまずないので、ルーターの要件の RFC は「the TTL is effectively a hop count limit（TTL は実質的にホップ数の上限である）」と書いています（[RFC 1812 5.3.1](https://www.rfc-editor.org/rfc/rfc1812.html#section-5.3.1)）。

なぜ減らすのかというと、経路表の設定を誤ると、2 台のルーターがお互いを次ホップにしてパケットを投げ合うループができるからです。TTL がなければ、そのパケットは永遠に回り続けて回線を埋めます。TTL が 0 になったパケットは捨てられ、同じ RFC は、そのとき送信元へ ICMP の Time Exceeded（コード 0、TTL Exceeded in Transit）を返すよう求めています。実験で TTL を 1 にして送ると、`r1` がそれを返してきます。

```
$ ping -c1 -t1 10.0.2.10    # h1
From 10.0.1.1 icmp_seq=1 Time to live exceeded
```

### TTL を変えると、チェックサムも変わる

IP ヘッダには、ヘッダ自身が壊れていないかを確かめる 16 ビットのチェックサムがあります。TTL はヘッダの一部なので、TTL を書き換えればチェックサムも計算し直さなければなりません。同じ ping を 3 か所で捕まえ、`tcpdump -x` が出した 16 進のうち IP ヘッダの先頭 20 バイトだけを並べました。

```
r1 が受けたもの:  4500 0054 f590 4000 4001 2e05 0a00 010a 0a00 020a
r2 が受けたもの:  4500 0054 f590 4000 3f01 2f05 0a00 010a 0a00 020a
h2 が受けたもの:  4500 0054 f590 4000 3e01 3005 0a00 010a 0a00 020a
                                      ^^   ^^^^
                                     TTL  チェックサム
```

5 つ目の 16 ビット語の上位バイトが TTL（`40` = 64、`3f` = 63、`3e` = 62）、下位バイトの `01` がプロトコル番号（ICMP）、その次がチェックサムです。TTL が 1 減るたびに、チェックサムが `0x0100` ずつ増えています。

IP のチェックサムは、ヘッダを 16 ビットずつ 1 の補数で足し合わせ、その結果のビットを反転したものです。TTL を 1 減らすとその語は `0x0100` 小さくなり、和も `0x0100` 小さくなり、反転したチェックサムは `0x0100` 大きくなります。ヘッダ全体を足し直さなくても、変わった語の差分だけで新しい値を出せるわけです。RFC 1812 は、TTL だけを変えるときにこの差分による更新を使ってよいとしており（[RFC 1812 4.2.2.5](https://www.rfc-editor.org/rfc/rfc1812.html#section-4.2.2.5)）、その計算方法は [RFC 1624](https://www.rfc-editor.org/rfc/rfc1624.html) にまとめられています。上の 3 つの値は、ヘッダを全部足し直して計算した値とも一致しました。

```
$ python3 checksum.py      # チェックサム欄を 0 にしたヘッダから計算し直す
TTL 0x40 -> 0x2e05
TTL 0x3f -> 0x2f05
TTL 0x3e -> 0x3005
```

なお IPv6 のヘッダにはチェックサムがありません。TTL にあたる欄は Hop Limit と呼ばれ、減らすのは同じですが、計算し直すものがない分だけルーターの仕事が軽くなっています（第 64 回）。

## traceroute は TTL を使って途中を覗く

ICMP の Time Exceeded は、**TTL が尽きた場所のルーターのアドレスから**返ってきます。これを逆手に取ったのが `traceroute` です。TTL を 1 にしたパケット、2 にしたパケット、3 にしたパケット、と順に送り、それぞれに Time Exceeded を返してきたのが誰かを並べれば、途中のルーターが 1 台ずつ分かります。

```
$ traceroute -n -q1 10.0.2.10    # h1
 1  10.0.1.1  0.025 ms
 2  10.0.12.2  0.649 ms
 3  10.0.2.10  0.013 ms
```

このとき `h1` の線の上で起きていたことです（Linux の `traceroute` は既定で UDP を、宛先ポート 33434 から 1 つずつ増やしながら送ります）。`tcpdump -v` の出力から、時刻と、TTL とプロトコル以外の IP ヘッダの欄、ICMP の中に入っている元のパケットの表示を省いて載せています。

```
IP (ttl 1, proto UDP) 10.0.1.10.49555 > 10.0.2.10.33434: UDP, length 32
IP (ttl 64, proto ICMP) 10.0.1.1 > 10.0.1.10: ICMP time exceeded in-transit, length 68
IP (ttl 2, proto UDP) 10.0.1.10.47780 > 10.0.2.10.33435: UDP, length 32
IP (ttl 63, proto ICMP) 10.0.12.2 > 10.0.1.10: ICMP time exceeded in-transit, length 68
IP (ttl 3, proto UDP) 10.0.1.10.40120 > 10.0.2.10.33436: UDP, length 32
IP (ttl 62, proto ICMP) 10.0.2.10 > 10.0.1.10: ICMP 10.0.2.10 udp port 33436 unreachable, length 68
```

TTL 1 は `r1` で、TTL 2 は `r2` で尽きて、それぞれが Time Exceeded を返しています。TTL 3 は `h2` まで届き、`h2` ではそのポートで誰も待っていないので Port Unreachable が返りました。これが「着いた」の合図です。返ってきた ICMP 自身の TTL が 64、63、62 と減っているのも、それぞれが何ホップ先から戻ってきたかを表しています。

`traceroute` が、どの ICMP がどのプローブへの返事なのかを区別できるのは、ICMP のエラーが**引き金になった元のパケットの先頭を中に入れて返す**からです。ICMP の元の仕様は、元の IP ヘッダと「the first 64 bits of the original datagram's data（元のデータグラムのデータの最初の 64 ビット）」を含めるとしていました（[RFC 792](https://www.rfc-editor.org/rfc/rfc792.html)）。8 バイトあれば UDP のポート番号が入ります。ルーターの要件はこれを広げ、「the ICMP datagram SHOULD contain as much of the original datagram as possible without the length of the ICMP datagram exceeding 576 bytes（ICMP データグラムは、長さが 576 バイトを超えない範囲で、元のデータグラムをできるだけ多く含めるべきである）」としています（[RFC 1812 4.3.2.3](https://www.rfc-editor.org/rfc/rfc1812.html#section-4.3.2.3)）。実際に `r1` が返した Time Exceeded は 88 バイトで、IP ヘッダ 20 バイトと ICMP ヘッダ 8 バイトのあとに、元の UDP のパケット 60 バイトが丸ごと入っていました。

<Callout type="note" title="traceroute で * * * が並ぶとき">
  途中のルーターが ICMP を返さない設定になっていたり、返す数を絞っていたりすると、その段は `* * *` になります。後ろの段が普通に返ってくるなら、その経路は通っています。
  また、行きと帰りが別の道を通ることもあります。`traceroute` が見せるのは**行きの道だけ**です。
  同じ ICMP を途中で捨てられると困るのが、第 68 回で見た経路 MTU 探索です。大きすぎるパケットを捨てたルーターが返す ICMP（Destination Unreachable の Fragmentation Needed）で送信元は経路の MTU を知るので（[RFC 1191](https://www.rfc-editor.org/rfc/rfc1191.html)）、ICMP をまとめて遮断すると、大きなパケットだけが黙って消えます。
</Callout>

## 経路表を誰が書くのか

ここまでは、経路を `ip route add` で人が書きました。これを**静的経路**と呼びます。2 台なら困りませんが、ルーターが数十台あって、どこかの線が切れたら迂回させたい、となると手では追いつきません。そこで、ルーター同士が知っていることを交換し合い、経路表を自動で作る**ルーティングプロトコル**を使います。代表的な考え方が 2 つあります。

### 距離ベクトル: 隣から聞いた距離を信じる

**距離ベクトル**型では、各ルーターが「自分から各ネットワークまで何ホップか」の一覧を、隣のルーターにだけ定期的に送ります。受け取った側は、隣の距離に 1 を足し、今知っているより近ければ採用します。全体の地図を持たず、隣の言うことを信じて足し算を繰り返すだけです。

古くからある **RIP** がこの型です。単純な分、困った性質もあります。ある線が切れたとき、隣同士が「自分はあっち経由で行ける」とお互いを指し合い、距離を 1 ずつ増やしながら投げ合ってしまうことがあります。RIP はこれを、距離の上限を決めて打ち切ることで止めています。仕様の言葉では「In the existing implementation of RIP, 16 is used.  This value is normally referred to as "infinity"（既存の RIP の実装では 16 が使われる。この値は普通「無限大」と呼ばれる）」です（[RFC 2453 3.4.1](https://www.rfc-editor.org/rfc/rfc2453.html#section-3.4.1)）。つまり RIP では 15 ホップより遠いネットワークは扱えません。

### リンクステート: 全員が同じ地図を持って、各自で最短路を計算する

**リンクステート**型では、各ルーターが「自分にはどんな線がつながっていて、その先に誰がいるか」だけを、ネットワーク全体に配ります。全員がそれを集めると、全員が同じ地図を持つことになります。OSPF の仕様は、こう説明しています。

> In a link-state routing protocol, each router maintains a database describing the Autonomous System's topology.  This database is referred to as the link-state database. Each participating router has an identical database.
>
> （リンクステート型のルーティングプロトコルでは、各ルーターが自律システムのトポロジーを記述したデータベースを保持する。このデータベースをリンクステートデータベースと呼ぶ。参加するすべてのルーターが同一のデータベースを持つ。）
>
> （[RFC 2328 1.1](https://www.rfc-editor.org/rfc/rfc2328.html#section-1.1)）

地図がそろえば、各ルーターは自分を始点にして、各ネットワークまでの最短路を計算します。OSPF はこの計算にダイクストラ法を使います（[RFC 2328 16.1](https://www.rfc-editor.org/rfc/rfc2328.html#section-16.1)）。重み付きグラフの最短路を 1 点から求める、<a href={`${import.meta.env.BASE_URL}articles/dijkstra/`}>ダイクストラ法</a>そのものです。重みは線ごとの「コスト」で、帯域の大きい線ほど小さくするのが普通です。

### 手元で OSPF に経路表を作らせる

同じ 4 つの netns で、今度は静的経路を書かずに、`r1` と `r2` で FRRouting 10.0 の `ospfd` を動かしました。設定は、どのネットワークを OSPF に載せるかだけです。

```
router ospf
 ospf router-id 1.1.1.1
 network 10.0.1.0/24 area 0
 network 10.0.12.0/24 area 0
```

起動直後の `r1` の経路表は直結の 2 行だけで、`h1` からの ping は Destination Net Unreachable になります。待っていると、`r1` に OSPF が学んだ行が入りました。

```
$ ip route        # r1
10.0.1.0/24 dev r1-eth0 proto kernel scope link src 10.0.1.1
10.0.2.0/24 nhid 14 via 10.0.12.2 dev r1-eth1 proto ospf metric 20
10.0.12.0/24 dev r1-eth1 proto kernel scope link src 10.0.12.1
```

`proto ospf` が、人ではなく OSPF が書いた行であることを示しています。行が入るまでの時間は、設定を少し変えながら 3 回動かして 16 秒、20 秒、38 秒とばらつきました。OSPF のルーターは隣を見つけるための Hello を一定間隔（FRR の既定では 10 秒。[FRR: OSPFv2](https://docs.frrouting.org/en/latest/ospfd.html)）で送り、隣と地図を交換し終えてから経路を計算するので、起動のタイミングによってこの程度の差が出ます。FRR の側から見た `r1` の地図と経路はこうです。

```
       OSPF Router with ID (1.1.1.1)

                Router Link States (Area 0.0.0.0)

Link ID         ADV Router      Age  Seq#       CkSum  Link count
1.1.1.1        1.1.1.1            6 0x80000006 0x10d8 2
2.2.2.2        2.2.2.2            7 0x80000005 0x439c 2

O>* 10.0.2.0/24 [110/20] via 10.0.12.2, r1-eth1, weight 1, 00:00:07
```

リンクステートデータベースに、`r1`（1.1.1.1）と `r2`（2.2.2.2）がそれぞれ自分のリンクを広告した記録が並んでいます。`r1` はこの 2 件から、`10.0.2.0/24` には `r2` 経由で行けると計算しました。

次に、`r2` の `h2` 側の線を落としました。`r2` が地図の更新を配り、`r1` の経路表から `10.0.2.0/24` の行は 2 秒以内に消えました。人が何もしなくても、つながらなくなった宛先は表から消え、別の道があればそちらに切り替わります。これが動的ルーティングを使う理由です。

### 同じ宛先に、出どころの違う経路があるとき

上の `[110/20]` の 2 つの数は、どの経路を経路表に採るかの比べ方を表しています。

- **20** は**メトリック**で、同じプロトコルの中での距離です。OSPF なら通る線のコストの合計で、ここでは `r1` の線（コスト 10）と `r2` の先の線（コスト 10）の和です
- **110** は**管理距離**（administrative distance）で、**どのプロトコルが教えた経路をより信じるか**の順位です。同じ宛先を静的経路と OSPF と BGP がそれぞれ教えてきたら、メトリックは単位が違って比べられないので、まずこちらで決めます

FRR の文書は、管理距離を「The lowest Admin Distance is the route selected.（管理距離が最も小さい経路が選ばれる）」とし、直結 0、静的 1、外部 BGP 20、OSPF 110、RIP 120、内部 BGP 200 などの値を表にしています。そして、この並びは「care has been taken to choose the same distances that other routing suites have chosen（他のルーティングソフトウェアが選んできたのと同じ値を選ぶよう配慮した）」ものだと書いています（[FRR: Administrative Distance](https://docs.frrouting.org/en/latest/zebra.html#administrative-distance)）。管理距離は規格で決まった値ではなく、実装の慣習です。

まぎらわしいのは、Linux の経路表に出ている `metric 20` です。これは OSPF のコストの 20 とたまたま同じ値ですが、別物です。FRR は自分が選んだ経路をカーネルに入れるとき、一律に 20 を付けると説明しており、「the kernel’s metric value bears no resemblance to FRR’s RIB metric or admin distance（カーネルのメトリックの値は、FRR の RIB のメトリックや管理距離とは何の関係もない）」と断っています（[FRR: Route Replace Semantics](https://docs.frrouting.org/en/latest/zebra.html#route-replace-semantics)）。

この回では 1 つの組織の中の経路の交換だけを扱いました。組織同士がインターネット全体の経路を交換する仕組みは、設計の考え方がまったく違います。それが次の第 63 回の BGP です。

## 家庭のルーターがしていること: NAPT

家庭用の「ルーター」は、ここまで見たルーターの仕事に加えて、もう 1 つ大きな仕事をしています。内側の端末はプライベートアドレス（`192.168.x.x` など）を持っていますが、これはインターネット上では使えません。そこで、内側から外へ出ていくパケットの送信元を、ルーターが外側に持っている 1 つのグローバルアドレスと、ルーターが選んだポート番号に書き換えます。戻ってきたパケットは、覚えておいた対応表を使って宛先を元に戻します。

アドレスだけでなくポートも書き換えるので、正確には **NAPT**（Network Address Port Translation）と呼びます。RFC 3022 は、NAPT が「(local IP addresses, local TU port number)」の組を「(registered IP address, assigned TU port number)」の組に対応させるものだとし、「This model fits the requirements of most Small Office Home Office (SOHO) groups（このモデルは、ほとんどの SOHO の要件に合う）」と述べています（[RFC 3022 2.2](https://www.rfc-editor.org/rfc/rfc3022.html#section-2.2)）。

ここで注意したいのは、**NAPT はこの回の意味でのルーティングとは別の仕事**だということです。ルーターは本来、IP の送信元と宛先を書き換えません。上の実験でも 3 本の線の上で IP アドレスは同じでした。NAPT は、それをあえて書き換えています。対応表に行が無ければ外から入ってくるパケットを渡す先が分からないこと、それを越えて端末同士をつなぐ方法は、第 91 回で詳しく見ます。

## 箱の中の話: L3 スイッチと、速く引くための表

### L3 スイッチ

前回の VLAN で分けたネットワークどうしも、互いに通信するにはルーターを通らなければなりません。これを VLAN 間ルーティングと呼びます。VLAN ごとにルーターへ線を引くのは手間なので、スイッチの中にルーターの機能を入れた機器がよく使われます。**L3 スイッチ**と呼ばれるもので、VLAN ごとに仮想的なインターフェース（SVI）を作ってそれぞれに IP アドレスを付け、その間をスイッチの中で転送します。やっていることは、この回の最長一致と MAC の書き換えそのものです。

### 経路表を速く引く

経路表を上から 1 行ずつ比べていては、行が増えるほど遅くなります。インターネットの経路は数十万行ありますし、第 68 回で見たとおり、10Gbps の線ではパケット 1 つに使える時間は 1 マイクロ秒ほどしかありません。

そこで、実際の転送には、経路表から作った転送専用の表（**FIB**、Forwarding Information Base）を使います。経路を選ぶための情報を持つのが経路表（RIB）、選ばれた結果を速く引けるように並べ直したのが FIB です。Linux のカーネルは、IPv4 の FIB を LC-trie という木で持っています（[Linux: LC-trie implementation notes](https://docs.kernel.org/networking/fib_trie.html)）。宛先のビットを上から順に見て枝を下りていく、<a href={`${import.meta.env.BASE_URL}articles/trie/`}>トライ木</a>の一種です。途中で通ったプレフィックスのうち最も深いものが最長一致になるので、行の数ではなくビットの長さに比例した手間で引けます。

専用のハードウェアで転送するルーターやスイッチでは、**TCAM**（Ternary Content-Addressable Memory）という特殊なメモリを使う方式が広く知られています。各行に「0・1・どちらでもよい」の 3 値でプレフィックスを書いておき、宛先を入れると全行と同時に比べて、一致した中で最も優先度の高い行（長いプレフィックスを先に並べておく）を 1 回の検索で返します。速い代わりに容量が小さく、電力も食うので、何行入るかが機器の性能表に書かれる項目になっています。

## まとめ

- IP アドレスは「どのネットワークか」の左側と「その中の誰か」の右側に分かれ、境目をプレフィックス長で示す（CIDR）
- 端末は、相手が自分の線の中にいれば直接、いなければデフォルトゲートウェイに渡す。違うのはフレームの宛先 MAC だけで、IP の宛先は最終的な相手のまま
- ルーターは受け取るたびに宛先 IP で経路表を引き直し、一致する行のうち最も長いプレフィックスの次ホップへ渡す（最長一致）。既定経路は長さ 0 の、いつも負ける行
- 渡すたびにイーサネットのヘッダは付け替えられ、IP のアドレスは変わらず、TTL が 1 減ってチェックサムが差分で更新される
- TTL が尽きると Time Exceeded が返る。traceroute はそれを使って途中のルーターを 1 台ずつ知る
- 経路表は人が書く（静的経路）か、ルーター同士に作らせる。RIP は隣の距離を信じる距離ベクトル型、OSPF は全員が同じ地図を持ってダイクストラ法で計算するリンクステート型
- 出どころの違う経路は管理距離で、同じプロトコルの中ではメトリックで比べる
- 家庭のルーターの NAPT は、ルーティングとは別に、送信元のアドレスとポートを書き換える仕事
- 転送は経路表から作った FIB で行う。ソフトウェアでは木（Linux は LC-trie）、ハードウェアでは TCAM で最長一致を速く引く

次の第 63 回では、組織同士がインターネット全体の経路を交換する BGP を見ます。この回のルーティングプロトコルが「最短の道」を探すのに対し、BGP が探すのは「方針に合う道」です。
