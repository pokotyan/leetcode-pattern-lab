## ローダの仕事を、実行中にやる

第 30 回で見たローダは、実行ファイルの中の機械語を `mmap` でメモリに載せ、`mprotect` で実行可能にしてから、そこへジャンプしました。

**JIT**（Just-In-Time コンパイラ）がやっていることは、これとほとんど同じです。違うのは、機械語がファイルから来るのではなく、**実行中のプログラムが自分で組み立てる**という点だけです。

```
ローダ:  ファイルの機械語 ──mmap──▶ メモリ ──mprotect(実行可)──▶ ジャンプ
JIT:     自分で作った機械語 ──書き込み──▶ メモリ ──mprotect(実行可)──▶ ジャンプ
```

JavaScript、Java、C#、Wasm のランタイム（第 62 回の Wasmtime など）、正規表現エンジン、データベースの式評価。実行時に機械語を作るプログラムは、思ったより身近にあります。

## 最小の JIT

「42 を返す関数」を、実行中に作って呼び出します。

```c
#include <stdio.h>
#include <string.h>
#include <sys/mman.h>
#include <stdint.h>

int main(void) {
#if defined(__aarch64__)
    uint32_t code[] = { 0x52800540, 0xd65f03c0 };    // mov w0, #42 ; ret
#elif defined(__x86_64__)
    uint8_t code[] = { 0xb8, 0x2a, 0, 0, 0, 0xc3 };  // mov eax, 42 ; ret
#endif
    // 1. 読み書きできるページを確保する
    void *p = mmap(NULL, 4096, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    // 2. 機械語を書き込む
    memcpy(p, code, sizeof code);
    // 3. 命令キャッシュとの食い違いを解消する（後述）
    __builtin___clear_cache((char *)p, (char *)p + sizeof code);
    // 4. 書き込み不可・実行可に切り替える
    mprotect(p, 4096, PROT_READ | PROT_EXEC);
    // 5. 関数ポインタとして呼ぶ
    int (*f)(void) = (int (*)(void))p;
    printf("%d\n", f());
}
```

arm64 の Linux で実行すると、`42` が表示されました。

この数バイトが関数として動くのは、第 31 回の **ABI** に従っているからです。呼び出し規約では、戻り値は ARM64 なら `w0`（`x0` の下位 32 ビット）、x86-64 なら `eax` に置くことになっています。そこに 42 を入れて `ret` すれば、C の側からは普通の関数と区別がつきません。本物の JIT も、呼び出し規約を守った機械語を出すことで、ランタイムの C / C++ のコードと相互に呼び合っています。

## なぜ、書きながら実行しないのか

上のコードは、書き込むときは `PROT_READ | PROT_WRITE`、実行するときは `PROT_READ | PROT_EXEC` と、わざわざ切り替えています。最初から 3 つとも付けた `PROT_READ | PROT_WRITE | PROT_EXEC`（RWX）で確保すれば、1 回で済むはずです。

それをしないのは、第 19 回で見た **NX ビット**の意味がなくなるからです。書き込めて実行もできるページがあれば、攻撃者はバッファオーバーランでそこに機械語を書き込み、ジャンプするだけで済みます。NX が封じた攻撃が、そのまま復活します。

そこで、**書き込み可能と実行可能を同時に許さない**という原則が生まれました。**W^X**（Write XOR Execute）と呼ばれます。OS によっては RWX のページを作ること自体を拒否します。

問題は、切り替えのコストです。

<Callout type="warn" title="mprotect は安くない">
  第 21 回で見たとおり、権限の変更は **TLB シュートダウン**を伴います。
  マルチスレッドの JIT が、関数を 1 つ作るたびに `mprotect` を 2 回呼ぶと、
  そのたびに他のコアの TLB を無効化して回ることになります。
</Callout>

実際の JIT は、いくつかの方法でこれを避けています。

| 方式 | やり方 | 特徴 |
| --- | --- | --- |
| 権限の切り替え | 書くときだけ RW、終わったら RX | 素直。切り替えのたびに TLB シュートダウン |
| 二重マッピング | 同じ物理ページを、RW のアドレスと RX のアドレスの 2 か所にマップする | 切り替え不要。書く側のアドレスが漏れると危ない |
| スレッド単位の切り替え | CPU の機能で、スレッドごとに「いまは書く / いまは実行する」を切り替える | 速い。ハードウェアの支援が要る |

二重マッピングは、第 24 回の共有マッピングの応用です。同じファイル（あるいは無名の共有メモリ）を 2 回 `mmap` すれば、同じ物理ページに 2 つの仮想アドレスが付きます。片方は書けるが実行できない、もう片方は実行できるが書けない。W^X の「同じアドレスでは」という条件は満たします。

### Apple Silicon の場合

Apple Silicon の macOS は、3 つ目の方式を OS として用意しています。`mmap` に `MAP_JIT` を付けて確保した領域は、**スレッドごとに**書き込み可能か実行可能かのどちらかになり、`pthread_jit_write_protect_np` で切り替えます（[Apple Developer](https://developer.apple.com/documentation/apple-silicon/porting-just-in-time-compilers-to-apple-silicon)）。

```c
void *p = mmap(NULL, size, PROT_READ | PROT_WRITE | PROT_EXEC,
               MAP_PRIVATE | MAP_ANONYMOUS | MAP_JIT, -1, 0);

pthread_jit_write_protect_np(0);   // このスレッドから見て RW にする
memcpy(p, code, len);
pthread_jit_write_protect_np(1);   // このスレッドから見て RX に戻す
sys_icache_invalidate(p, len);
```

ページの権限としては RWX を指定していますが、あるスレッドが同時に両方を使えることはありません。しかも切り替えは**そのスレッドだけ**の話なので、他のコアの TLB を無効化する必要がありません。Apple Silicon では、この「同時には両方できない」保護が Hardened Runtime の採用の有無にかかわらず全アプリにかかります。Hardened Runtime を有効にしたアプリが JIT をするには、`com.apple.security.cs.allow-jit` という許可（entitlement）の宣言も必要です（[Apple Developer](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.allow-jit)）。

## 命令キャッシュを忘れる

最小の JIT に戻ると、3 番目の `__builtin___clear_cache` がまだ説明されていません。

第 16 回で見たとおり、L1 キャッシュは**命令用とデータ用に分かれています**。JIT が `memcpy` で書いた機械語は、データとして書き込まれたので、**L1 データキャッシュ**に入ります。一方、CPU が命令を取り出すのは **L1 命令キャッシュ**からです。

```
  memcpy で書く ──▶ L1 データキャッシュ  [新しい機械語]
                            │
                            │  （自動では伝わらないことがある）
                            ▼
  命令を取り出す ◀── L1 命令キャッシュ   [同じアドレスの古い中身]
```

同じアドレスに以前別の機械語が入っていた場合、命令キャッシュには古い中身が残っているかもしれません。そのまま実行すると、**書いたはずのない命令**が走ります。

- **x86** は、この食い違いをハードウェアが検出して解消します。自己書き換えコードを持つ古いプログラムとの互換性のためです。その代わり、検出したときにパイプラインを捨て直すので遅くなります
- **ARM** は、ソフトウェアに明示的な指示を求めます

`__builtin___clear_cache` を arm64 でコンパイルして中身を逆アセンブルすると、次の命令が並んでいました。

```
dc   cvau, x2     // データキャッシュの内容を、命令側からも見える段まで書き出す
dsb  ish          // それが終わるのを待つ
ic   ivau, x0     // 命令キャッシュの該当ラインを無効化する
dsb  ish          // それが終わるのを待つ
```

データキャッシュから書き出し、命令キャッシュを捨てる。キャッシュの段と、命令とデータの分離という第 3 章の話が、JIT を書く人にとっては正しさの問題として現れます。

## 全部はコンパイルしない

機械語の作り方が分かったところで、次の問題は**何を、いつ**コンパイルするかです。

コンパイルは時間がかかります。事前コンパイルなら、その時間はビルドのときに払えば済みました。JIT では、**コンパイルにかかる時間もプログラムの実行時間**です。一度しか呼ばれない関数を丁寧に最適化するのは、損でしかありません。

そこで、ほとんどの JIT は段階を踏みます。

1. まずインタプリタで動かし、関数やループごとに**何回実行されたか**を数える
2. 回数が閾値を超えたものだけを、手早くコンパイルする
3. さらに熱いものだけを、時間をかけて最適化する

V8（Chrome や Node.js の JavaScript エンジン）は 4 段です（[V8 blog](https://v8.dev/blog/maglev)）。

| 段 | 種類 | 役割 |
| --- | --- | --- |
| Ignition | インタプリタ | すべてのコードはまずここ。実行しながら型の情報を集める |
| Sparkplug | 最適化しないコンパイラ | バイトコードをほぼそのまま機械語に置き換える |
| Maglev | 手早い最適化コンパイラ | 2023 年に追加。TurboFan より約 10 倍速くコンパイルできる |
| TurboFan | 本格的な最適化コンパイラ | 最も熱い部分だけ |

Java の HotSpot も、インタプリタ（レベル 0）、C1 コンパイラ（レベル 1〜3）、C2 コンパイラ（レベル 4）の段階を持ちます（[Microsoft for Java Developers](https://devblogs.microsoft.com/java/how-tiered-compilation-works-in-openjdk/)）。CPython も 3.13 で実験的な JIT を入れました。あらかじめ用意した機械語の断片を貼り合わせる copy-and-patch という方式です（[PEP 744](https://peps.python.org/pep-0744/)）。

<Callout type="tip" title="ベンチマークのウォームアップが必要な理由">
  JIT を持つ言語では、最初の数百回と、その後とで**別のプログラムが動いています**。
  第 90 回で「ウォームアップしてから測る」と書いたのは、このためです。
  逆に、起動直後の応答時間が問題になる用途（コマンドラインツール、サーバレス）では、
  JIT が温まる前に処理が終わってしまうことがあります。
</Callout>

## 推測して特殊化する

JIT が事前コンパイルより速くなりうる理由は、「作る」の Track 2 で<a href={`${import.meta.env.BASE_URL}build/tc-09-interpreter/`}>インタプリタを書く回</a>に触れたとおり、**実行時の情報を使える**ことです。代表的な仕掛けを 1 つ見ます。

JavaScript で `obj.x` と書いたとき、`obj` がどんな形のオブジェクトかは実行するまで分かりません。素直に実装すると、毎回「`x` という名前のプロパティはどこにあるか」を辞書で引くことになります。

しかし実際のプログラムでは、ある 1 行を通るオブジェクトは、ほとんど毎回**同じ形**をしています。そこで JIT は、観測した形を前提にした機械語を出します。

```
// obj.x に対して JIT が出す機械語のイメージ
if (obj->shape != 観測した形 S)     // ガード: 前提が成り立っているか
    goto slow_path;                // 外れたら、一般的な処理へ
value = *(obj + 16);                // 形 S なら、x は必ずオフセット 16 にある
```

辞書を引く処理が、比較 1 回と、決まったオフセットからの読み込み 1 回になりました。第 6 回で見た、構造体のメンバを決まったオフセットで読むのと同じ速さです。これを **インラインキャッシュ** と呼びます。

最適化コンパイラは、この種の前提をさらに積み重ねます。「この変数は常に整数」「この呼び出し先は常に同じ関数」と仮定して、インライン展開や型の検査の省略を行います。

前提が崩れたらどうするか。ガードが外れた時点で、**最適化された機械語の実行を中断し、インタプリタに戻します**。これを **脱最適化**（deoptimization）と呼びます。

<Callout type="note" title="脱最適化は、スタックフレームの作り直し">
  脱最適化は、見た目よりずっと難しい処理です。
  最適化されたコードでは、変数はレジスタに置かれ、関数はインライン展開で消えています。
  それを、インタプリタが期待する形のスタックフレーム（第 31 回）に**組み直す**必要があります。
  そのため JIT は、機械語の各地点について「どのレジスタが、元のどの変数だったか」という対応表を一緒に作っておきます。
  デバッガがデバッグ情報を使ってやっていることと、よく似ています。
</Callout>

## JIT の代償

JIT は速さと引き換えに、いくつかのものを払っています。

| 代償 | 内容 |
| --- | --- |
| メモリ | 生成した機械語を置く領域（コードキャッシュ）と、型の情報の記録 |
| 起動の遅さ | 温まるまでは遅い。ウォームアップが要る |
| 予測しにくさ | 脱最適化で突然遅くなることがある |
| 攻撃面 | 実行可能なメモリに書き込む仕組みそのものが、攻撃の足がかりになる |

最後の点は深刻です。JIT のコンパイラにバグがあれば、それは**任意の機械語を実行できるバグ**になりがちです。型の前提を誤って検査を省けば、第 23 回で見たような範囲外アクセスが、機械語のレベルで発生します。ブラウザの脆弱性で JIT 由来のものが繰り返し見つかっているのは、このためです。

Wasm が事前に検証できる形式を採り、ランタイムが生成する機械語の範囲を狭くしている（第 61 回）のは、JIT の速さを取りながらこの危険を小さくするための設計でもあります。

## まとめ

- JIT は、ローダの仕事（機械語をメモリに置き、実行可能にしてジャンプする）を実行中に自分でやる
- 呼び出し規約を守った機械語なら、関数ポインタとして普通に呼べる
- W^X: 書き込みと実行を同時に許さない。NX の意味を保つため
- 権限の切り替えは TLB シュートダウンを伴う。二重マッピングやスレッド単位の切り替え（Apple の `MAP_JIT`）で避ける
- 書いた機械語はデータキャッシュに入る。ARM では命令キャッシュとの同期を明示する
- コンパイル時間も実行時間。熱い部分だけを段階的に最適化する
- 観測した型を前提に特殊化し、外れたら脱最適化で戻る

ここまでで第 5 章は終わりです。プログラムが実行可能な形になり、メモリに載り、関数が呼ばれ、さらに実行中に機械語が作られる仕組みまでが揃いました。
次の章では、**それが複数同時に走る**とどうなるかを見ます。
