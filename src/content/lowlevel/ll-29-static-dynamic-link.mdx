## 2 つの方式

ライブラリの関数を使うとき、その機械語をどう調達するか。

**静的リンク**：リンク時に、ライブラリの中身を実行ファイルにコピーする。

**動的リンク**：実行ファイルには「このライブラリのこの関数を使う」という記録だけを残し、**実行時に読み込む**。

| | 静的（`.a`） | 動的（`.so` / `.dll` / `.dylib`） |
| --- | --- | --- |
| 実行ファイルのサイズ | 大きい | 小さい |
| 起動速度 | 速い | やや遅い（読み込みと解決がある） |
| メモリ（複数プロセス） | 各自が持つ | **1 つを共有** |
| ライブラリの更新 | 再リンクが必要 | **差し替えるだけ** |
| 実行環境への依存 | 少ない | ライブラリが必要 |

Linux では動的リンクが既定です。

## メモリを共有できる

動的リンクの最大の利点は、**複数のプロセスが同じライブラリの物理メモリを共有できる**ことです。

libc はほぼすべてのプロセスが使います。静的リンクなら、100 個のプロセスが libc のコピーを 100 個持ちます。動的リンクなら、物理メモリ上のコードは 1 つで済みます。

共有できるのは、**コードが読み取り専用で、どのプロセスでも同じ内容**だからです。データ部分はプロセスごとに別です（コピーオンライトで分離されます）。

## どこに置かれるか分からない問題

共有ライブラリは、プロセスによって違うアドレスに読み込まれます。ASLR もあり、起動のたびに変わります。

すると困ります。ライブラリのコードの中に「グローバル変数 `x` はアドレス 0x1000 にある」と書き込んでしまうと、別の場所に読み込まれた瞬間に壊れます。

読み込み時に全部書き換えれば動きますが、書き換えたページは**共有できなくなります**（コピーオンライトで複製される）。共有という利点が消えます。

## 位置独立コード

解決策が **PIC**（Position Independent Code）です。**絶対アドレスをコードに埋め込まない**ように書きます。

具体的には、

- 分岐は、現在位置からの**相対**で書く
- グローバル変数やほかの関数のアドレスは、**表を経由して参照する**

この表が **GOT**（Global Offset Table）です。GOT はデータ領域にあり、プロセスごとに別です。**コードは書き換えず、GOT だけを書き換えれば済みます。**

```
コード（共有、書き換えなし）          GOT（プロセスごと、書き換える）
  mov rax, [rip + GOT_offset]  ──▶   [ printf の実アドレス ]
  call rax                            [ malloc の実アドレス ]
```

共有ライブラリは `-fPIC` を付けてコンパイルする必要があります。

```bash
gcc -fPIC -c foo.c -o foo.o
gcc -shared foo.o -o libfoo.so
```

<Callout type="note" title="PIE">
  実行ファイル本体も位置独立にしたものが **PIE**（Position Independent Executable）です。
  これにより、実行ファイル自体のアドレスも ASLR の対象になります。
  現代のディストリビューションでは既定で有効です。
  `file` コマンドで `LSB pie executable` と出るのがそれです。
</Callout>

## 遅延束縛と PLT

ライブラリの関数は数千あります。起動時に全部のアドレスを解決すると、起動が遅くなります。**実際に呼ばれない関数まで解決するのは無駄です。**

そこで、**最初に呼ばれたときに初めて解決する**という仕組みがあります。遅延束縛（lazy binding）です。

その仕掛けが **PLT**（Procedure Linkage Table）です。

```
1 回目の printf 呼び出し
  call printf@plt
    → PLT のエントリへ
    → GOT を見る。まだ解決されていないので、動的リンカへ飛ぶ
    → 動的リンカが printf の実アドレスを探し、GOT に書き込む
    → printf へジャンプ

2 回目以降
  call printf@plt
    → PLT のエントリへ
    → GOT を見る。実アドレスが入っている
    → そのままジャンプ
```

1 回目だけ余分なコストがかかり、2 回目以降はほぼ直接呼び出しと同じです。

<Callout type="warn" title="GOT は攻撃対象になる">
  GOT は書き換え可能なメモリ上にあり、関数のアドレスが並んでいます。
  ここを書き換えられると、任意のコードに実行を移されます。

  対策が **RELRO**（RELocation Read-Only）です。
  `-Wl,-z,relro,-z,now` を付けると、起動時に全シンボルを解決してから
  **GOT を読み取り専用にします**（Full RELRO）。
  遅延束縛の利点は失われますが、安全性が上がります。
  現代のディストリビューションでは既定で有効なことが多いです。
</Callout>

## 依存関係を見る

```bash
ldd ./a.out
```

```
linux-vdso.so.1 (0x00007ffd8...)
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f8...)
/lib64/ld-linux-x86-64.so.2 (0x00007f8...)
```

`ld-linux-*.so` が**動的リンカ**そのもので、他のライブラリを読み込む役目を担います。

`linux-vdso.so.1` はディスク上に存在しません。カーネルが各プロセスのアドレス空間にマップする特別な領域で、`gettimeofday` のような軽いシステムコールを、**カーネルに入らずに済ませる**ための仕組みです。

<Callout type="warn" title="ldd を信頼できないファイルに使わない">
  `ldd` は実装によっては対象を実際にロードします。
  信頼できないバイナリに対しては `objdump -p ./a.out | grep NEEDED` を使うべきです。
</Callout>

## 探索の順番

動的リンカがライブラリを探す順序です。

1. `LD_PRELOAD` で指定されたもの
2. 実行ファイルに埋め込まれた `RPATH`（`DT_RPATH`）
3. `LD_LIBRARY_PATH` 環境変数
4. 実行ファイルに埋め込まれた `RUNPATH`（`DT_RUNPATH`）
5. `/etc/ld.so.cache`（`ldconfig` が作る）
6. `/lib`、`/usr/lib`

```bash
LD_DEBUG=libs ./a.out        # 探索の様子を表示する
```

「ライブラリが見つからない」ときは、この順序に沿って確認します。

## LD_PRELOAD

**既存のライブラリより先に、自分のライブラリを読み込ませる**仕組みです。同じ名前の関数があれば、そちらが使われます。

```c
// mymalloc.c
#include <stdio.h>
#include <dlfcn.h>

void *malloc(size_t size) {
    static void *(*real)(size_t) = NULL;
    if (!real) real = dlsym(RTLD_NEXT, "malloc");
    void *p = real(size);
    fprintf(stderr, "malloc(%zu) = %p\n", size, p);
    return p;
}
```

```bash
gcc -shared -fPIC mymalloc.c -o mymalloc.so -ldl
LD_PRELOAD=./mymalloc.so ls
```

**ソースコードも再コンパイルもなしに、既存プログラムの関数呼び出しを差し替えられます。**

用途は広く、メモリリークの検出、性能測定、動作の記録、テスト用のモック、互換性の後付けなどに使われます。

一方、マルウェアの常套手段でもあるため、setuid されたプログラムでは無効化されます。

## 静的リンクを選ぶとき

動的リンクが既定ですが、静的リンクが適する場面もあります。

- **配布の単純さ**：1 ファイルで動く。Go が既定で静的リンクなのはこれが理由
- **コンテナの軽量化**：ライブラリを含めないイメージが作れる
- **glibc のバージョン差の回避**：新しい環境でビルドしたバイナリが古い環境で動かない問題

```bash
gcc -static foo.c -o foo
```

ただし glibc の静的リンクには注意が必要です。`getaddrinfo` などが内部で動的読み込みを行うため、完全に独立しません。完全な静的リンクを目指すなら musl libc が使われます。

## まとめ

- 静的リンクは埋め込み、動的リンクは実行時に読み込む
- 動的リンクの利点は、複数プロセスでのメモリ共有とライブラリの差し替え
- PIC は絶対アドレスを埋め込まない書き方。GOT を経由する
- PLT は遅延束縛の仕掛け。初回だけ解決し、以降は直接呼ぶ
- GOT は攻撃対象になるので RELRO で読み取り専用にする
- `LD_PRELOAD` で既存の関数を差し替えられる

次は、この実行ファイルが実際にメモリへ載るまでを見ます。
