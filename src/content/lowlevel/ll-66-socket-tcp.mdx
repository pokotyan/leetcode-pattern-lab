## この章で見るもの

第 7 章では、ソケットを「fd の一種」として扱いました。`read` と `write` ができて、`epoll` でまとめて待てるもの。第 45 回では、それを 1 万本捌く話をしました。

しかし、fd の向こう側で何が起きているのかは見ていません。

- `connect` は、なぜ時間がかかるのか
- `accept` を呼ぶ前に届いた接続は、どこにいるのか
- `write` が成功したデータは、もう相手に届いたのか
- ネットワークカードに届いたパケットは、どうやってソケットにたどり着くのか

この章では、カーネルの中の **TCP/IP スタック** に入ります。3 回に分けて、**接続の始まりと終わり**、**速度の決め方**、**パケットが NIC を通る道筋** を見ます。

## ソケットはカーネルの中の構造体

`socket()` を呼ぶと、カーネルの中に接続 1 本分の状態が作られ、その番号が fd として返ります。第 42 回で見たとおり、fd は表の添字にすぎません。実体はカーネルの中にあります。

TCP のソケットが持っている主なものは次のとおりです。

| 持っているもの | 中身 |
| --- | --- |
| 4 つ組 | 自分の IP とポート、相手の IP とポート。接続を一意に決める |
| 状態 | LISTEN、ESTABLISHED、TIME_WAIT など（後述） |
| 送信バッファ | `write` されたが、まだ相手に確認されていないデータ |
| 受信バッファ | 届いたが、まだ `read` されていないデータ |
| シーケンス番号 | 何バイト目まで送ったか、何バイト目まで受け取ったか |
| タイマ | 再送、遅延 ACK、keepalive、TIME_WAIT |

**`write` はこの送信バッファにコピーした時点で返ります。** 相手に届いたかどうかは関係ありません。第 48 回で、ファイルへの `write` がページキャッシュに書いた時点で返るのを見ましたが、構造は同じです。

<Callout type="warn" title="write が成功しても届いたとは限らない">
  `write` が 100 バイト成功を返しても、それは「カーネルが預かった」という意味です。
  直後に相手のマシンの電源が落ちれば、そのデータは届きません。
  **届いたことを知る唯一の確かな方法は、相手からアプリケーションとしての応答をもらうこと**です。
  HTTP のレスポンスや、DB の COMMIT の返事がそれにあたります。
</Callout>

## サーバ側の準備

サーバは 4 つのシステムコールで待ち受けます。

```c
int s = socket(AF_INET, SOCK_STREAM, 0);   // 箱を作る
bind(s, &addr, sizeof addr);               // ポート番号を決める
listen(s, 128);                            // 待ち受け状態にする。128 は backlog
int c = accept(s, NULL, NULL);             // 1 本取り出す。新しい fd が返る
```

ここで重要なのは、**`listen` した時点で、カーネルは接続を受け付け始める**ということです。`accept` は「接続を受け付ける」操作ではなく、**カーネルがすでに確立させた接続を 1 本取り出す**操作です。

## 3 ウェイハンドシェイク

クライアントが `connect` を呼ぶと、3 つのパケットが行き交います。

```
クライアント                                 サーバ
 SYN_SENT    ── SYN（seq = x）────────────→    （SYN キューへ）  SYN_RECV
             ←── SYN + ACK（seq = y, ack = x+1）
ESTABLISHED  ── ACK（ack = y+1）───────────→   （accept キューへ）ESTABLISHED
                                                    ↓
                                              accept() で取り出す
```

なぜ 3 回なのか。**双方が、自分の初期シーケンス番号を相手が受け取ったと確認する**必要があるからです。SYN で自分の番号を送り、相手の ACK でそれが届いたと分かります。これを両方向でやると 4 回になりますが、サーバの SYN と ACK を 1 つのパケットにまとめて 3 回で済ませています。

初期シーケンス番号は 0 から始まりません。推測されにくいように、乱数を混ぜて決めます。古い接続のパケットが迷い込んだり、第三者が偽のパケットを差し込んだりするのを防ぐためです。

<Callout type="tip" title="connect は往復 1 回分待つ">
  `connect` が返るのは、SYN + ACK が戻ってきたときです。
  東京とロンドンの間なら、それだけで 200 ミリ秒以上かかります。
  データを 1 バイトも送る前にです。
  TLS を載せればさらに往復が増えます。
  **接続を使い回す**（keep-alive、コネクションプール）ことが効くのは、この往復を毎回払わずに済むからです。
</Callout>

## accept を呼ぶ前の接続はどこにいるのか

`listen` したソケットの裏には、2 つの待ち行列があります。

| 行列 | 入っているもの | 大きさを決めるもの |
| --- | --- | --- |
| **SYN キュー** | SYN を受け取り、SYN + ACK を返したが、最後の ACK がまだの接続 | `net.ipv4.tcp_max_syn_backlog` |
| **accept キュー** | ハンドシェイクが終わり、`accept` されるのを待っている接続 | `listen` の backlog と `net.core.somaxconn` の小さいほう |

アプリケーションが `accept` を呼ぶのが遅れると、accept キューが埋まります。埋まると、Linux は**新しい SYN に応えず、最後の ACK を受け取っても接続を accept キューに移さずに捨てます**。RST を返して断るのではなく、黙って捨てるのが既定です（`net.ipv4.tcp_abort_on_overflow` が 0）。クライアントから見ると応答が来ないので、SYN の再送を繰り返しながら待たされます。再送の間隔は 1 秒、2 秒、4 秒と倍々に伸びるので、**取りこぼされた接続は数秒単位で遅れます**。

手元で試すと、その様子がそのまま見えます。backlog を 1 にして、`accept` を呼ばずに 4 本の接続を張ってみます（Linux 上で `/proc/net/tcp` を読んで状態を表示）。

```
backlog 1 に 4 本:
  9000->58932 ESTABLISHED    ← accept キューに入った
  9000->58934 ESTABLISHED    ← accept キューに入った
  58940->9000 SYN_SENT       ← 応答がもらえず、待たされている
  58946->9000 SYN_SENT
```

backlog 1 で 2 本入っているのは、Linux が「backlog + 1 本」まで受け入れる実装になっているためです。残りの 2 本は、クライアント側で SYN_SENT のまま止まっています。

`somaxconn` の既定値は長らく 128 でしたが、Linux 5.4 で 4096 に引き上げられました（[glibc のメーリングリスト](https://sourceware.org/legacy-ml/libc-alpha/2019-11/msg01013.html)）。古い既定値のままの環境では、瞬間的に接続が集中すると、アプリケーションに余力があってもここで取りこぼします。

```bash
ss -ltn        # LISTEN 中のソケット。Recv-Q が accept キューの現在の長さ、Send-Q が上限
nstat -az TcpExtListenOverflows TcpExtListenDrops    # 溢れて捨てた回数
```

<Callout type="note" title="SYN flood と SYN cookie">
  SYN キューは、最後の ACK を待つ間メモリを使います。
  送信元を偽った SYN を大量に送りつけると、SYN キューが埋まり、正規の接続が入れなくなります。これが **SYN flood** です。
  Linux は、SYN キューが溢れそうになると **SYN cookie** に切り替えます。
  状態を覚えておく代わりに、必要な情報を暗号的に計算してシーケンス番号 y に埋め込み、
  返ってきた ACK の番号から復元します。**状態を持たなければ、埋められることもない**という発想です。
</Callout>

## 状態遷移の全体

TCP の接続は、11 個の状態のどれかにいます。全部を覚える必要はありませんが、`ss` や `netstat` で見かける状態が、どこにいるのかは把握しておく価値があります。

```
                 始まり                           終わり（先に close した側）
  CLOSED ─connect→ SYN_SENT                ESTABLISHED ─close→ FIN_WAIT1
                     │ SYN+ACK 受信                               │ ACK 受信
  LISTEN ─SYN 受信→ SYN_RECV                               FIN_WAIT2
                     │ ACK 受信                                   │ FIN 受信
                 ESTABLISHED                               TIME_WAIT ─2MSL→ CLOSED

                                         終わり（後から close した側）
                                           ESTABLISHED ─FIN 受信→ CLOSE_WAIT
                                                                  │ close
                                                               LAST_ACK ─ACK 受信→ CLOSED
```

終わりが非対称なのがポイントです。**先に `close` した側が TIME_WAIT に入り、後から `close` した側は CLOSE_WAIT を通ります。**

手元で、クライアントを先に閉じてみると、この通りになります。

```
接続中:              9000->58930 ESTABLISHED   58930->9000 ESTABLISHED
クライアントが close: 9000->58930 CLOSE_WAIT    58930->9000 FIN_WAIT2
サーバも close:                                58930->9000 TIME_WAIT
```

<Callout type="warn" title="CLOSE_WAIT が溜まるのはアプリケーションのバグ">
  CLOSE_WAIT は「相手はもう閉じたが、こちらがまだ `close` していない」状態です。
  カーネルは相手の FIN を受け取った時点で、あとはアプリケーションが `close` するのを待っています。
  **CLOSE_WAIT が何千本も溜まっているなら、どこかで fd を閉じ忘れています。**
  TIME_WAIT と違い、時間が経っても自然には消えません。
  いずれ fd の上限（`ulimit -n`）に達して、新しい接続を受けられなくなります。
</Callout>

## TIME_WAIT はなぜ残るのか

先に閉じた側は、接続を閉じたあとも **2MSL**（MSL はパケットがネットワークに残りうる最大時間）のあいだ TIME_WAIT に留まります。Linux ではこの時間が 60 秒に固定されています（[Vincent Bernat](https://vincent.bernat.ch/en/blog/2014-tcp-time-wait-state-linux)）。

無駄に見えますが、理由が 2 つあります。

**1. 最後の ACK が失われたときに、再送に応えるため。** 相手（LAST_ACK にいる側）は、自分の FIN に対する ACK が来なければ、FIN を再送します。こちらが状態を完全に消していたら、その FIN に RST で応えることになり、相手はエラーとして扱います。

**2. 遅れて届いた古いパケットを、新しい接続と混同しないため。** 同じ 4 つ組で直後に新しい接続を張ると、前の接続のパケットが遅れて届いたとき、新しい接続のデータとして受け取ってしまう可能性があります。TIME_WAIT の間はその 4 つ組を使わせないことで、古いパケットがネットワークから消えるのを待ちます。

<Callout type="note" title="TIME_WAIT が問題になる場面">
  TIME_WAIT はソケット 1 つあたりわずかなメモリしか使わないので、数万本あっても通常は問題になりません。
  問題になるのは、**同じ相手に短い接続を大量に張るクライアント**です。
  4 つ組のうち、相手の IP とポート、自分の IP が固定なので、残るのは自分のポートだけです。
  ポートの範囲（`net.ipv4.ip_local_port_range`、既定で約 2 万 8 千個）を
  TIME_WAIT が使い切ると、新しい接続が張れなくなります。

  対策の本筋は、**接続を使い回して、そもそも短い接続を大量に作らない**ことです。
  かつて使われた `tcp_tw_recycle` は、NAT の内側から来る接続を壊す副作用があり、
  Linux 4.12 で削除されました（[linux-man](https://www.spinics.net/lists/linux-man/msg11931.html)）。
  クライアント側で TIME_WAIT のポートを再利用する `tcp_tw_reuse` は、タイムスタンプを使って安全を確かめる仕組みで、こちらは残っています。
</Callout>

## RST: 話を打ち切る

FIN による終了は「送るものはもう無い」という丁寧な終わり方です。これに対し、**RST** は「この接続は存在しない。以上」という一方的な打ち切りです。

RST が送られる典型的な場面:

| 場面 | 何が起きているか |
| --- | --- |
| 誰も LISTEN していないポートに SYN が来た | 「そんな接続は受け付けていない」。クライアントは `ECONNREFUSED` |
| 受信バッファに未読のデータを残したまま `close` した | 相手の送ったデータが捨てられたことを、黙っていないで知らせる |
| 知らない接続のパケットが来た | 相手が再起動した後など。相手は `ECONNRESET` |
| `SO_LINGER` を 0 秒にして `close` した | TIME_WAIT を経ずに即座に消す。意図的に使う |

RST を受け取った接続に `write` すると、`EPIPE` が返り、さらに **SIGPIPE** が送られます。第 46 回で見たとおり、SIGPIPE の既定の動作はプロセスの終了です。サーバが相手に切断されただけで落ちるのを防ぐため、ネットワークのサーバは SIGPIPE を無視するか、`send` に `MSG_NOSIGNAL` を付けるのが普通です。

## 同じポートで待ち受ける

サーバを再起動すると、`bind` が `EADDRINUSE` で失敗することがあります。直前のプロセスが持っていた接続が TIME_WAIT に残っていて、そのポートがまだ使用中とみなされるからです。

**`SO_REUSEADDR`** を付けると、TIME_WAIT の接続が残っていても `bind` できます。待ち受けるサーバのほとんどが、これを付けています。

**`SO_REUSEPORT`** は別物で、**複数のソケットが同じポートで同時に LISTEN できる**ようにします。Linux 3.9 で入りました（[LWN](https://lwn.net/Articles/542629/)）。カーネルが新しい接続を 4 つ組のハッシュでソケットに振り分けるので、ワーカープロセスごとに独立した accept キューを持てます。

```
SO_REUSEPORT なし                         SO_REUSEPORT あり
  1 つの accept キュー                      ワーカーごとの accept キュー
  ┌──────────┐                            ┌────┐ ┌────┐ ┌────┐
  │ ○○○○○○  │ ← 全ワーカーが取り合う      │ ○○ │ │ ○○ │ │ ○○ │
  └──────────┘                            └────┘ └────┘ └────┘
   ↑  ↑  ↑                                   ↑      ↑      ↑
  w1 w2 w3                                  w1     w2     w3
```

1 つのキューを複数のワーカーが取り合うと、第 37 回で見たロックの競合と同じ問題が起きます。キューを分ければ、それが消えます。nginx などが複数コアで accept を分散させるのに使っています。

## 自分の環境で見る

```bash
ss -tan                              # すべての TCP ソケットと状態
ss -tan state time-wait | wc -l      # TIME_WAIT の数
ss -tan state close-wait             # 閉じ忘れの疑い
ss -ltn                              # LISTEN と accept キュー
nstat -az | grep -i listen           # accept キューから溢れた回数
sudo tcpdump -i any -nn port 8080    # SYN、ACK、FIN、RST が実際に流れる様子
```

`tcpdump` の出力で、`[S]` が SYN、`[S.]` が SYN + ACK、`[.]` が ACK、`[F.]` が FIN、`[R]` が RST です。`curl` を 1 回実行して眺めるだけで、この回の内容がすべて見えます。

## まとめ

- ソケットはカーネルの中の構造体。`write` は送信バッファにコピーした時点で返り、相手に届いたことは保証しない
- `connect` は 3 ウェイハンドシェイクで往復 1 回分待つ。接続の使い回しが効くのはこのため
- `listen` した時点でカーネルは接続を確立し始める。`accept` は accept キューから 1 本取り出すだけ
- accept キューが溢れると接続は黙って捨てられる。`somaxconn` は Linux 5.4 で 4096 になった
- 先に閉じた側が TIME_WAIT に 60 秒残る。最後の ACK の再送と、古いパケットの混入に備えるため
- CLOSE_WAIT が溜まるのは、アプリケーションの閉じ忘れ
- RST は一方的な打ち切り。切られた接続への `write` は SIGPIPE を招く
- `SO_REUSEADDR` は再起動のため、`SO_REUSEPORT` は accept キューを分けるため

次は、接続が確立したあと、TCP が**どれだけの速さで送るか**をどう決めているのかを見ます。
