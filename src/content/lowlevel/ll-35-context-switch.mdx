## 何を保存するのか

CPU は 1 つのコアで 1 つの命令の流れしか実行できません。複数のプロセスが同時に動いているように見えるのは、**高速に切り替えている**からです。

切り替えのとき、OS は今のプロセスの状態を保存し、次のプロセスの状態を復元します。

保存するもの：

| 対象 | 内容 |
| --- | --- |
| 汎用レジスタ | すべて |
| プログラムカウンタ | 次に実行する命令 |
| スタックポインタ | |
| フラグレジスタ | |
| 浮動小数点 / SIMD レジスタ | 大きい。x86-64 で AVX-512 まで含めると 2KB を超える |
| ページテーブルのポインタ | プロセスをまたぐ場合のみ |

これらを PCB に書き込み、次のプロセスの PCB から読み出して復元します。

<Callout type="tip" title="FPU の状態は遅延して保存する">
  浮動小数点と SIMD のレジスタは大きく、保存に時間がかかります。
  しかし、多くのプロセスはこれらを使いません。

  そこで、**切り替え時には保存せず、新しいプロセスが最初に FPU を使おうとしたときに
  例外を発生させて、そこで初めて保存する**という最適化があります（lazy FPU switching）。

  ただし、この仕組みは投機実行を悪用した情報漏洩（LazyFP）の対象になり、
  現在は無効化される方向にあります。**性能のための最適化が、また塞がれた**例です。
</Callout>

## 保存より高いもの

レジスタの保存と復元そのものは、数百ナノ秒程度です。しかし、**実際のコストはその数倍から数十倍**になります。

理由は、切り替えた後に**キャッシュと TLB が冷えている**ことです。

```
プロセス A が動いている間
  L1/L2/L3 キャッシュには A のデータが載っている
  TLB には A のアドレス変換が載っている

プロセス B に切り替わる
  キャッシュにはまだ A のデータが残っているが、B には無関係
  B のデータを読むたびにキャッシュミス
  B のアドレス変換のたびに TLB ミス（PCID がなければ TLB は全破棄）

しばらく動くと、キャッシュと TLB が B のもので埋まる
  → ようやく本来の速度が出る

そしてまた A に切り替わると、A のデータは追い出されている
```

この「温まるまでの時間」が、切り替えの本当のコストです。作業セットが大きいほど長くなります。

| 内訳 | おおよそ |
| --- | --- |
| レジスタの保存と復元 | 0.2〜1 マイクロ秒 |
| TLB の再構築 | 数マイクロ秒 |
| キャッシュの再構築 | 数マイクロ秒〜数十マイクロ秒 |

<Callout type="warn" title="測りにくい">
  レジスタの保存時間は測れますが、キャッシュが冷えたことによる影響は
  「その後のプログラムが遅くなる」という形で分散して現れます。
  マイクロベンチマークでは過小評価されがちです。
</Callout>

## 切り替えが起きるきっかけ

**自発的**（voluntary）：プロセス自身が CPU を手放す。

- I/O 待ちに入った（`read` がブロックした）
- ロックの取得を待つ
- `sleep` した
- 明示的に `sched_yield` を呼んだ

**非自発的**（involuntary）：OS に取り上げられる。

- タイムスライスを使い切った
- より優先度の高いプロセスが実行可能になった
- 割り込みの処理からの復帰時に、別のプロセスが選ばれた

```bash
cat /proc/<pid>/status | grep ctxt
# voluntary_ctxt_switches:     1234
# nonvoluntary_ctxt_switches:  56
```

**この 2 つの比率が、性能問題の切り分けに役立ちます。**

- 自発的が多い → I/O やロック待ちが多い。並行度を上げるか、待ちを減らす
- 非自発的が多い → CPU を奪い合っている。プロセス数を減らすか、コアを増やす

```bash
vmstat 1               # cs 列が 1 秒あたりの切り替え回数
pidstat -w 1           # プロセスごとの内訳
perf stat ./a.out      # context-switches
```

## 減らす方法

### スレッド数を適正にする

コア数より大幅に多いスレッドを走らせると、切り替えが増えるだけです。CPU 律速の処理では、コア数程度に抑えます。

### CPU に固定する

特定のプロセスを特定のコアに固定すると、そのコアのキャッシュが保たれやすくなります。

```bash
taskset -c 0,1 ./a.out           # コア 0 と 1 だけで動かす
numactl --cpunodebind=0 ./a.out  # NUMA ノードごと固定
```

さらに、そのコアを OS のスケジューラから外して専有させることもできます（`isolcpus` カーネルパラメータ）。低レイテンシが要求される用途で使われます。

### 待ちの方法を変える

短い待ちなら、コンテキストスイッチを起こすより**その場で回って待つ**ほうが安いことがあります。これが **スピンロック** です。

```
ロックが空くまで、ひたすらループして確認し続ける
```

待ち時間が切り替えのコスト（数マイクロ秒）より短ければ、スピンのほうが得です。長ければ、CPU を無駄に焼くだけで損です。

現実の実装は両方を組み合わせます（**アダプティブロック**）。しばらくスピンして、それでも取れなければ寝る。Linux の futex や、多くの言語のミューテックスがこの方式です。

### バッチ処理にする

1 件ずつ処理して待つのではなく、まとめて処理してからまとめて待つ。切り替えの回数そのものが減ります。ネットワークやディスクの I/O で特に効きます。

## 割り込みとの関係

ハードウェア割り込みが入ると、そのコアで動いていた処理は中断されます。割り込み処理が終わった後、**元のプロセスに戻るとは限りません**。スケジューラが別のプロセスを選ぶことがあります。

ネットワークの負荷が高いと、割り込みが頻発してコンテキストスイッチが増えます。対策として、

- **割り込み結合**（interrupt coalescing）：複数のパケットをまとめて 1 回の割り込みにする
- **ポーリングモード**：割り込みを止めて、定期的に見に行く方式に切り替える（Linux の NAPI、DPDK）

高スループットのネットワーク処理で「割り込みを使わない」選択が取られるのは、この事情です。

## まとめ

- コンテキストスイッチはレジスタの保存と復元だが、本当のコストはキャッシュと TLB が冷えること
- 自発的（自分から手放す）と非自発的（取り上げられる）の比率が、問題の切り分けに使える
- スレッド数をコア数程度に抑える、CPU に固定する、待ち方を変える、バッチ化する
- 短い待ちにはスピン、長い待ちには休止。実装は両方を組み合わせる
- 割り込みが多いと切り替えも増える。ポーリングに切り替える手法がある
