## なぜ WebGL を拡張しなかったのか

前回の WebGL は、OpenGL ES をそのまま JavaScript に写した API でした。WebGPU の explainer は、まずその点を問題として挙げています。WebGL 1.0 と 2.0 はそれぞれ OpenGL ES 2.0 と 3.0 を JavaScript に投影したもので、そのため「WebGL は今の GPU の設計に合っていない」と書いています（[WebGPU Explainer §1.3](https://gpuweb.github.io/gpuweb/explainer/#why-not-webgl3)）。

ずれているのは、主に次の 2 点です。

- **状態の持ち方**: OpenGL は、1 つの大きな状態を少しずつ書き換え、`draw` の瞬間にその状態全体を使う。状態の組み合わせが正しいかどうか、シェーダをどう組み合わせるかは、**draw のたびに**確かめるしかない
- **命令の送り方**: 命令は 1 つずつ即座に発行され、結果を知りたければ同期的に問い合わせる（`getError` や `readPixels`）

1990 年代の OpenGL の設計は、GPU が固定機能の装置だった時代のものです。2014 年から 2016 年にかけて出た Vulkan、Metal、Direct3D 12 は、どれも逆の方針を取りました。**状態の組み合わせは前もって 1 つのオブジェクトに固め、命令はバッファに溜めてまとめて送る**。WebGPU の目標の 1 つは、この 3 つのネイティブ API の上に実装できることです（[WebGPU Explainer §1.2](https://gpuweb.github.io/gpuweb/explainer/#goals)）。

explainer によると、WebGL 2.0 にコンピュートシェーダを足す試み（WebGL 2.0 Compute）もありましたが、ネイティブ API との食い違いのために難航し、関わっていた人たちは WebGPU に力を移しました（[§1.3](https://gpuweb.github.io/gpuweb/explainer/#why-not-webgl3)）。

## ブラウザの中での位置

第 88 回で見たとおり、GPU のドライバを触るのはレンダラではなく GPU プロセスです。WebGPU はこの構成を前提に設計されています。explainer は、ドライバを持つ GPU プロセスはレンダラより緩いサンドボックスで動き、**複数のオリジンで共有される**ので、受け取ったメッセージはすべて GPU プロセスの側で検証しなければならない、と書いています（[§2.1](https://gpuweb.github.io/gpuweb/explainer/#gpu-process)）。

```
 レンダラのプロセス                          GPU プロセス
┌──────────────────────┐             ┌──────────────────────────────────┐
│ JavaScript             │  IPC        │ Dawn（WebGPU の実装）            │
│  device.createBuffer() │ ─────────▶ │  検証 → Metal / D3D12 / Vulkan   │
│  queue.submit()        │  命令の列    │  Tint: WGSL → MSL / HLSL / SPIR-V│
│  ↑ 返るのは「取っ手」だけ│ ◀───────── │  エラー、mapAsync の完了の通知    │
└──────────────────────┘  非同期の返事 └──────────────────────────────────┘
```

Chrome の実装は **Dawn** です。Dawn の README は、自分を WebGPU 標準の実装と位置付け、ネイティブの側では D3D12・Metal・Vulkan・OpenGL を使うと書いています。シェーダ言語 WGSL のコンパイラは **Tint** です（[Dawn README](https://dawn.googlesource.com/dawn/+/HEAD/README.md)）。Firefox は wgpu という別の実装を使っています（[Chrome for Developers](https://developer.chrome.com/blog/webgpu-release)）。

この「呼び出しはレンダラ、実行と検証は別のプロセス」という配置が、この回で見る API の形をほぼすべて決めています。

## 対応状況と、安全なコンテキスト

web.dev の 2025 年 11 月の記事では、各ブラウザの対応は次のとおりです（[web.dev](https://web.dev/blog/webgpu-supported-major-browsers)）。

| ブラウザ | 対応 |
| --- | --- |
| Chrome / Edge | 113 から Windows（Direct3D 12）、macOS、ChromeOS。Android は 121 から（Android 12 以降、Qualcomm / ARM の GPU）。Linux は対応中 |
| Firefox | 141 から Windows。145 から Apple シリコンの macOS Tahoe 26。Linux、Android、Intel の Mac は対応中 |
| Safari | macOS Tahoe 26、iOS 26、iPadOS 26、visionOS 26 |

仕様は 2026 年 9 月 15 日付けの W3C の勧告候補草案です（[WebGPU](https://www.w3.org/TR/webgpu/)）。インタフェースにはすべて `SecureContext` が付いていて、**安全なコンテキストにしか現れません**。手元の Chrome 155 で、同じページを 3 つのオリジンから開いて確かめました。`gpu.example.test` は `--host-resolver-rules` で 127.0.0.1 に向けています。

```
origin                             isSecureContext   typeof navigator.gpu
http://127.0.0.1:18431             true              object
http://localhost:18431             true              object
http://gpu.example.test:18431      false             undefined
```

HTTP でも、ループバックのアドレスは安全とみなされるので使えます。ローカル以外の HTTP では、`navigator.gpu` そのものがありません。機能の検出は `if (!navigator.gpu)` で行い、その場合はたいてい「HTTPS で配っていない」ことが原因です。

## オブジェクトの関係

WebGPU のオブジェクトは、上から順に作っていきます。

```
navigator.gpu
  └─ requestAdapter()    GPUAdapter    物理的な GPU（とドライバ）の 1 つ。features と limits を持つ
       └─ requestDevice() GPUDevice     論理的な接続。ここからすべてを作る
            ├─ createBuffer / createTexture / createSampler      資源
            ├─ createShaderModule({ code: WGSL })                 シェーダ
            ├─ createBindGroupLayout → createPipelineLayout        「どの番号に何を挿すか」の型
            ├─ createRenderPipeline / createComputePipeline        状態を固めた実行の単位
            ├─ createBindGroup(layout, 資源)                        型に合わせて資源を束ねたもの
            ├─ createCommandEncoder → beginRenderPass / beginComputePass
            │     setPipeline, setBindGroup, draw / dispatchWorkgroups, end
            │   → finish() で GPUCommandBuffer
            └─ queue.submit([commandBuffer])                       ここで初めて GPU に渡る
```

WebGL との違いが一番大きいのは、**パイプライン**と**バインドグループ**です。

- **パイプライン**は、シェーダ、頂点の形式、ブレンドの方法、出力の形式など、draw に必要な状態の組み合わせを**1 つの変更できないオブジェクト**にしたものです。作るときに検証とコンパイルを済ませるので、draw のたびに確かめる必要がありません
- **バインドグループ**は、シェーダの `@group(0) @binding(0)` のような番号に、どのバッファやテクスチャを挿すかをまとめたものです。これもレイアウト（型）に対して作るときに検証されます

WebGL では「今どのプログラムが使われているか、どのテクスチャユニットに何が入っているか」が、コンテキストに付いた 1 つの大きな状態でした。WebGPU では、それが**明示的に渡すオブジェクト**に変わります。第 12 回で見た CPU が、命令を先読みしても正しい結果になるよう依存関係を調べていたのと逆で、WebGPU では依存関係を**書く側が先に宣言**します。

## アダプタとデバイスの limits

手元の環境は、Apple M1 Pro の MacBook Pro、macOS、Chrome 155（ヘッドレス）です。アダプタを取ると、次の情報が返りました。

```js
const adapter = await navigator.gpu.requestAdapter()
adapter.info          // { vendor: "apple", architecture: "metal-3", device: "", description: "" }
navigator.gpu.getPreferredCanvasFormat()   // "bgra8unorm"
```

`device` と `description` は空でした。ハードウェアをどこまで細かく見せるかはブラウザが決めてよく、仕様は、実際の上限を見せる義務はなく、少数の区分にまとめて**フィンガープリント**（端末の識別）を減らす方法もある、と書いています（[WebGPU §2.2](https://www.w3.org/TR/webgpu/#privacy-considerations)）。

面白いのは limits です。アダプタが言う上限と、何も指定せずに作ったデバイスの上限を並べます。

```
                                      adapter.limits   device.limits（既定）
maxBufferSize                         4294967292       268435456   (256 MiB)
maxStorageBufferBindingSize           4294967292       134217728   (128 MiB)
maxComputeInvocationsPerWorkgroup     1024             256
maxComputeWorkgroupSizeX              1024             256
maxComputeWorkgroupStorageSize        32768            16384
maxTextureDimension2D                 16384            8192
maxBindGroups                         4                4
```

**デバイスは、要求しない限りアダプタの上限ではなく仕様の既定値で作られます**。仕様の表にある既定値（`maxStorageBufferBindingSize` は 128 MiB、`maxComputeInvocationsPerWorkgroup` は 256）とそのまま一致しました（[WebGPU §3.6.2](https://www.w3.org/TR/webgpu/#limits)）。仕様は、既定値は「多くのアプリが上限を要求せずに動く程度には高く」取ってあると書いています（[§2.2](https://www.w3.org/TR/webgpu/#privacy-considerations)）。

この仕組みのおかげで、**既定値の範囲で書いたコードは、どの端末でも同じように動く**ことが保証されます。大きなバッファが要るなら、`requestDevice({ requiredLimits: { maxBufferSize: adapter.limits.maxBufferSize } })` のように明示して要求し、アダプタが応じられなければ `requestDevice` が失敗します。機能（`features`）も同じで、`shader-f16` や `timestamp-query` は `requiredFeatures` に書いたときだけ使えます。仕様は、要求したものと「ちょうど同じ」集合だけが検証で許されると書いています（[§4.3.1](https://www.w3.org/TR/webgpu/#gpudevicedescriptor)）。

## コマンドを溜めて、まとめて送る

描画の最小の例です。頂点バッファすら使わず、頂点の番号から三角形の座標を作ります。

```js
const ctx = canvas.getContext('webgpu')
const format = navigator.gpu.getPreferredCanvasFormat()
ctx.configure({ device, format })

const module = device.createShaderModule({ code: `
  @vertex fn vs(@builtin(vertex_index) i: u32) -> @builtin(position) vec4f {
    var p = array(vec2f(0.0, 0.8), vec2f(-0.8, -0.8), vec2f(0.8, -0.8));
    return vec4f(p[i], 0.0, 1.0);
  }
  @fragment fn fs() -> @location(0) vec4f { return vec4f(1.0, 0.4, 0.1, 1.0); }` })

const pipeline = device.createRenderPipeline({
  layout: 'auto',
  vertex: { module },
  fragment: { module, targets: [{ format }] },
})

function frame() {
  const enc = device.createCommandEncoder()
  const pass = enc.beginRenderPass({ colorAttachments: [{
    view: ctx.getCurrentTexture().createView(),
    clearValue: [0.1, 0.1, 0.15, 1], loadOp: 'clear', storeOp: 'store',
  }] })
  pass.setPipeline(pipeline)
  pass.draw(3)
  pass.end()
  device.queue.submit([enc.finish()])
}
```

`setPipeline` も `draw` も、この時点では何も実行しません。**エンコーダに命令を書き込んでいるだけ**です。`finish()` で `GPUCommandBuffer` になり、`queue.submit()` で初めて GPU プロセスに渡ります。仕様は、コマンドバッファは 1 回しか送れず、送ると無効になると定めています。同じ命令を繰り返し送りたいなら、`GPURenderBundle` に記録しておきます（[§12](https://www.w3.org/TR/webgpu/#command-buffers)）。

キャンバスへの出力は `getCurrentTexture()` で取るテクスチャです。手元で確かめると、同じタスクの中で 2 回呼ぶと同じオブジェクトが返り、`requestAnimationFrame` を挟むと別のオブジェクトが返りました。中央と隅の画素を読むと、三角形の色 `(255, 102, 26)` と消去の色 `(26, 26, 38)` でした。キャンバスの中身は、第 91 回で見た合成の段に、1 枚のレイヤとして渡されます。

第 48 回の DMA（CPU は指示を書くだけで、転送は別の装置に任せる）や、第 45 回の io_uring（操作をリングバッファに溜めて渡す）と同じ形です。**仕事の内容を先に全部書き出してから、1 回の通知で渡す**。1 つ渡すたびに境界を越えるより、まとめて越えるほうが安くなります。

## エラーは後から届く

WebGL では、間違った呼び出しをすると `gl.getError()` でその場で確かめられました。WebGPU にはこれがありません。explainer は、JavaScript の例外で同期的にエラーを返すのが理想だとしたうえで、マルチプロセスの実装では「法外に高くつく」と書いています（[§3.3](https://gpuweb.github.io/gpuweb/explainer/#errors)）。検証は GPU プロセスで行われるので、結果を待てば IPC の往復を待つことになるからです。

代わりの仕組みが、**無効なオブジェクトの伝染**と**エラースコープ**です。

- 検証に失敗した呼び出しは、例外を投げずに**無効なオブジェクト**を返す。無効なオブジェクトを使って作ったものも無効になる。explainer はこれを「伝染する」と呼んでいる（[§3.2.1](https://gpuweb.github.io/gpuweb/explainer/#error-monad)）
- エラーが起きた呼び出しは、エラーの報告以外は何もしない
- `pushErrorScope()` と `popErrorScope()` で挟んだ区間のエラーを、`Promise` で受け取れる。区間の中の処理が終わって報告が返ってきてから解決する（[§3.3.2](https://gpuweb.github.io/gpuweb/explainer/#errors-errorscopes)）
- どのスコープにも捕まらなかったエラーは、デバイスの `uncapturederror` イベントに届く

わざと間違えてみます。`STORAGE` の用途を付けずに作ったバッファを、ストレージバッファの場所に挿します。

```js
const wrong = device.createBuffer({ size: 256, usage: GPUBufferUsage.UNIFORM })

device.pushErrorScope('validation')
const bind = device.createBindGroup({
  layout: pipeline.getBindGroupLayout(0),
  entries: [{ binding: 0, resource: { buffer: wrong } }],
})
const err = await device.popErrorScope()
```

時刻（ページの読み込みからの経過）を付けて記録すると、こうなりました。

```
 54.4ms  createBindGroup が返った: 例外なし、オブジェクトは GPUBindGroup
 54.4ms  popErrorScope を呼んだ（Promise は未解決）
145.5ms  スコープが解決: GPUValidationError:
         Binding usage (BufferUsage::Uniform) of [Buffer (unlabeled)] doesn't match
         expected usage (BufferUsage::Storage).
          - While validating entries[0] against { binding: 0, visibility: ShaderStage::Compute,
            buffer: {type: BufferBindingType::Storage, minBindingSize: 4, hasDynamicOffset: 0} }.
145.7ms  submit が返った
147.9ms  uncapturederror: [Invalid BindGroup (unlabeled)] is invalid due to a previous error.
148.0ms  uncapturederror: [Invalid CommandBuffer] is invalid due to a previous error.
```

`createBindGroup` は**何事もなかったように** `GPUBindGroup` を返しました。誤りが分かったのは約 90ms 後で、この間には直前のパイプラインのコンパイルの待ちも含まれています。その無効なバインドグループを使ってコマンドを作って送ると、スコープの外なので `uncapturederror` に 2 件届きました。バインドグループが無効で、それを使ったコマンドバッファも無効、という**伝染**がそのまま見えます。送ったコマンドは何も実行されていません。

Chrome は、捕まらなかったエラーを開発者ツールのコンソールにも出します。メッセージは Dawn のもので、どのオブジェクトのどの呼び出しで起きたかを「While ...」の連なりで示します。オブジェクトに `label` を付けておくと、`(unlabeled)` の部分がその名前になり、どこで間違えたかを追いやすくなります。

シェーダのコンパイルエラーは `getCompilationInfo()` で行と列まで取れます。

```
error 1:58 cannot assign to 'let x'
info  1:58 'let' variables are immutable
info  1:46 'let x' declared here
```

### 同期の問い合わせは何が高いのか

比べるために、WebGL の `getError()` を 1000 回呼んでみました。

```
gl.getError() を 1000 回       89.4ms
gl.uniform1f() を 1000 回       0.1ms
```

`uniform1f` は命令を溜めるだけなので速く、`getError` は**GPU プロセスまで問い合わせて返事を待つ**ので、1 回あたり約 0.09ms かかります。1 フレームが 16.7ms（第 91 回）なら、毎フレーム 200 回呼ぶだけで予算を使い切ります。WebGL の実装も裏では命令を溜めて送っていますが、同期の問い合わせのたびにそれを吐き出して待つことになります。WebGPU が同期の問い合わせを API から外したのは、このためです。

<Callout type="warn" title="よくある誤解: 「WebGPU はエラーを投げないので、間違いに気づけない」">
  気づけますが、**どこで聞くかを決めておく**必要があります。
  開発中は `uncapturederror` を拾ってログに出し、確かめたい区間は `pushErrorScope` で挟みます。
  `popErrorScope` の `Promise` を毎フレーム待つと、それ自体が往復の待ちになるので、本番の描画の途中には入れません。
  なお、`createComputePipelineAsync` のような非同期版は、失敗するとエラースコープではなく、返した `Promise` が拒否されます（[§10](https://www.w3.org/TR/webgpu/#pipelines)）。
</Callout>

## パイプラインのコンパイルはどこで払うか

パイプラインを作るときにシェーダのコンパイルが走ります。`sin` と `cos` を 400 行並べた重いコンピュートシェーダで、同期版と非同期版を比べました。毎回シェーダに違う定数を混ぜて、キャッシュに当たらないようにしています。

```
                           呼び出しが返るまで   使える状態になるまで   最初の dispatch の完了まで
createComputePipeline        0ms                  0ms（すぐ返る）      222.4 / 130.0 / 128.0ms
createComputePipelineAsync   0〜0.1ms             145.0 / 137.6 / 141.4ms   146.3 / 138.6 / 142.3ms
同じシェーダをもう一度（同期版）   0ms                  0ms                  1.0ms
```

Chrome では、**同期版の呼び出しもメインスレッドを止めませんでした**。オブジェクトはすぐに返り、コンパイルは GPU プロセスの側で進みます。ただし、そのパイプラインを使ったコマンドは、コンパイルが終わるまで実行されません。同期版は「待ち」が最初の dispatch に移っているだけです。

非同期版は、**準備ができた時点を `Promise` で教えてくれる**ところが違います。仕様は、非同期版を「可能な限り使うことを勧める」とし、理由をキューの処理がパイプラインのコンパイルで止まるのを防ぐためだと書いています（[§10](https://www.w3.org/TR/webgpu/#pipelines)）。読み込み中にパイプラインを非同期で作り揃えておけば、最初のフレームで 100ms 以上止まることを避けられます。

同じシェーダでもう一度作ると約 1ms で済みました。Dawn がコンパイル結果をキャッシュしているためです。ゲームが「シェーダのコンパイル中」と表示するのは、この 100ms 単位のコストを、プレイ中に払わないためです。

## コンピュートシェーダ: 描かない GPU

WebGPU では、描画とは無関係な計算にも GPU を使えます。シェーダの処理は**インボケーション**（1 回の実行）に分かれ、それが**ワークグループ**という単位にまとまります。WGSL の仕様は、同じワークグループのインボケーションは `workgroup` アドレス空間の変数を共有すると書いています（[WGSL §1.1](https://www.w3.org/TR/WGSL/#overview)）。

```
dispatchWorkgroups(64, 64)          ← ワークグループを 64×64 個
  └─ @workgroup_size(16, 16)       ← 1 つのワークグループに 16×16 のインボケーション
       └─ global_invocation_id     ← 全体で 1024×1024 のどこを担当するか
```

1024×1024 の行列の積を書きます。1 つのインボケーションが、出力の 1 要素を担当します。

```wgsl
@group(0) @binding(0) var<storage, read> a: array<f32>;
@group(0) @binding(1) var<storage, read> b: array<f32>;
@group(0) @binding(2) var<storage, read_write> c: array<f32>;
const N = 1024u;

@compute @workgroup_size(16, 16)
fn main(@builtin(global_invocation_id) id: vec3u) {
  let row = id.y; let col = id.x;
  var sum = 0.0;
  for (var k = 0u; k < N; k++) { sum += a[row * N + k] * b[k * N + col]; }
  c[row * N + col] = sum;
}
```

GPU の結果を CPU で読むには、`MAP_READ` の用途を持つバッファに写してから `mapAsync` します。仕様は、`mapAsync` の `Promise` が解決すると `getMappedRange()` で中身を読めるようになると定めています（[§5.2](https://www.w3.org/TR/webgpu/#buffer-mapping)）。map している間は、そのバッファを GPU から使えません。explainer はこれを、CPU と GPU の間での**所有権の移動**として説明しています（[§3.5.1](https://gpuweb.github.io/gpuweb/explainer/#buffer-mapping-ownership)）。

```js
device.queue.writeBuffer(bufA, 0, A)          // CPU → GPU
device.queue.writeBuffer(bufB, 0, B)
const enc = device.createCommandEncoder()
const pass = enc.beginComputePass({ timestampWrites: { querySet, beginningOfPassWriteIndex: 0, endOfPassWriteIndex: 1 } })
pass.setPipeline(pipeline); pass.setBindGroup(0, bindGroup)
pass.dispatchWorkgroups(1024 / 16, 1024 / 16)
pass.end()
enc.copyBufferToBuffer(bufC, 0, readBuf, 0, bytes)   // 結果を読み出し用へ
device.queue.submit([enc.finish()])
await readBuf.mapAsync(GPUMapMode.READ)              // GPU → CPU
const C = new Float32Array(readBuf.getMappedRange().slice(0))
readBuf.unmap()
```

`timestamp-query` の機能を要求すると、パスの開始と終了の時刻を GPU 自身に記録させられます。これで、**カーネルだけの時間**と、**書き込みから読み出しまでの全体の時間**を分けて測れます。同じ環境（M1 Pro、Chrome 155）で、JavaScript の 3 重ループ（キャッシュに優しい i-k-j の順、第 17 回）と比べました。

```
JavaScript（Float32Array、i-k-j）           1507.2ms        1.42 GFLOPS
WebGPU 1 回目  全体  46.7ms   カーネル 14.81ms
WebGPU 2〜6 回目 全体 10.7〜12.0ms   カーネル 6.55〜8.00ms   最速で 327.9 GFLOPS
パイプラインの作成（非同期）                  106.0ms
結果の差（997 要素おきに比較）                   0
```

カーネルだけなら JavaScript の約 200 倍、転送を含めても 100 倍以上です。`queue.submit()` の呼び出し自体は 0.1ms 未満で返りました。行列の積は、要素数 N² のデータに対して N³ 回の掛け算と足し算をする、**データあたりの計算が多い**仕事です。

### 速くならない計算

同じ方法で、`c[i] = a[i] * 2 + b[i]` という単純な計算を比べます。5 回の中央値です。

```
要素数          JavaScript    WebGPU（書き込み〜読み出しの全体）
1,024             0.1ms         0.4ms
1,048,576         2.4ms         4.9ms
16,777,216       27.1ms        50.5ms
```

**どの大きさでも、GPU のほうが遅くなりました**。1 要素あたりの計算が掛け算と足し算の 1 回ずつしかないので、時間のほとんどは CPU と GPU の間でデータを運ぶことと、往復の待ちに使われています。第 14 回のメモリ階層と同じで、**計算の速さより、データを運ぶ速さが上限を決めます**。

GPU に任せて得をするのは、次のどちらかを満たすときです。

- データあたりの計算が多い（行列の積、畳み込み、物理シミュレーション、機械学習の推論）
- データが**もともと GPU の上にある**（描画に使うテクスチャや頂点、前のパスの出力）。往復しなければ転送のコストを払わない

<Callout type="note" title="時刻の精度はわざと落としてある">
  上の時刻は、`performance.now()` も `timestamp-query` も、精度を落とされた値です。
  仕様は、セキュリティとプライバシーへの懸念を減らすために、タイムスタンプの値は低い精度に揃えると書いています。
  さらに、GPU の処理は複数のオリジンが共有するプロセスで動くので、COOP / COEP によるクロスオリジン分離（第 111 回）があっても、GPU 側の時計は分離されないと注意しています（[§2.1.7](https://www.w3.org/TR/webgpu/#security-timing)）。
  0.1ms 単位の数字は、そのつもりで読んでください。
</Callout>

## WebGL と WebGPU を並べる

| | WebGL | WebGPU |
| --- | --- | --- |
| 元になった API | OpenGL ES 2.0 / 3.0 | Vulkan・Metal・Direct3D 12 の世代 |
| シェーダ言語 | GLSL ES | WGSL |
| 状態 | コンテキストに付いた 1 つの大きな状態を書き換える | パイプラインとバインドグループを前もって作り、渡す |
| 検証 | draw のたびに | オブジェクトを作るとき。draw では軽い確認だけ |
| 命令の送り方 | 呼び出しごと（実装が裏で溜める） | エンコーダに溜めて `submit` |
| エラー | `getError()` で同期的に（往復の待ち） | エラースコープと `uncapturederror` で非同期に |
| 読み出し | `readPixels`（同期） | `mapAsync`（非同期） |
| 汎用の計算 | 描画の形に無理に当てはめる | コンピュートシェーダ、ストレージバッファ |
| 使える場所 | HTTP でも可 | 安全なコンテキストだけ |
| 対応状況 | ほぼすべてのブラウザ | 主要なブラウザで対応。Linux などはまだ途中 |

WebGL が遅いわけではありません。数百の draw で済む画面なら、WebGL で十分に速く、対応する端末も多いままです。Three.js や Babylon.js のように両方の上で動くライブラリもあります。WebGPU を選ぶ理由は、**draw の数が多く CPU 側の負担が効いてくるとき**と、**GPU で計算したいとき**です。

## まとめ

- WebGPU は、WebGL が写した OpenGL ES の設計（1 つの大きな状態、即時の命令、同期の問い合わせ）を捨て、Vulkan・Metal・Direct3D 12 の世代に合わせて作り直した API
- Chrome の実装は Dawn で、GPU プロセスの中で検証してから Metal・D3D12・Vulkan に渡す。WGSL は Tint がコンパイルする
- 安全なコンテキストでしか `navigator.gpu` は現れない。ループバックなら HTTP でもよい
- アダプタ → デバイス → 資源・シェーダ・パイプライン・バインドグループ、の順に作る。デバイスは要求しない限り**仕様の既定の limits** で作られるので、既定の範囲で書けばどの端末でも動く
- 状態はパイプラインに固め、資源はバインドグループで渡す。検証は作るときに済ませ、命令はエンコーダに溜めて `submit` で送る
- エラーは同期的に返らない。無効なオブジェクトが伝染し、エラースコープか `uncapturederror` で後から届く。手元では約 90ms 後に届いた。WebGL の `getError` は 1 回約 0.09ms の往復だった
- パイプラインのコンパイルは 100ms 単位。Chrome では同期版も呼び出しは止まらないが、待ちが最初の dispatch に移るだけ。非同期版で前もって作っておく
- コンピュートシェーダは、データあたりの計算が多い仕事でだけ速い。1024×1024 の行列の積はカーネルで JavaScript の約 200 倍、単純な足し算は転送のせいで GPU のほうが遅かった

ここまでの 3 回で、canvas に描く手段を CPU から GPU まで見てきました。どれも、文字の折り返し、フォームの入力、スクリーンリーダーへの対応といった、DOM なら当たり前にできることを自分で作り直す必要がありました。次の第 102 回では、その溝を埋めようとしている新しい提案、HTML-in-Canvas を見ます。DOM の要素をブラウザにレイアウトさせたまま、その見た目を canvas、WebGL、WebGPU のテクスチャに描き込む仕組みです。
