## 速くした後に残る変数

前回は、データベースの次に CPU を使い始めるアプリケーション自身の処理（パスワードのハッシュ、JSON のエンコード、自分で入れた検査など）を見ました。ここまでの回で扱ったのは、どれも「同じ仕事をより少ない資源で行う」改善です。

ところが、インデックスを張り、N+1 を消し、キャッシュを入れ、台数を使い切った後でも、点がまだ大きく動くことがあります。動かしているのは、コードの速さではなく**仕様の側にある変数**です。

- 負荷をかける側に「どれだけ強く来てよいか」を伝えるパラメータ
- 状態の変化を確かめに来る間隔（ポーリングの間隔）
- 溜まった仕事を処理する間隔（マッチングやバッチの間隔）
- 待たされた利用者が離れるまでの時間と、その離脱が点に与える影響

これらは第 261 回で見た「何を速くすれば点になるか」と、第 262 回で見た「負荷をかける側も利用者として振る舞う」ことの帰結です。この回では、こうした変数がどの条件で効き、どの条件で効かないのかを、ISUCON の事例と手元の実験で確かめます。

| 節 | 問い |
| --- | --- |
| 負荷の強さを選べる仕様 | 負荷を上げると点が上がるのはどういうときか |
| 通知をどう待たせるか | 確かめに来る間隔は、遅れと負荷をどう交換するか |
| 待ち行列を回す間隔 | 処理の間隔と割り当て方は、どちらがいつ効くか |
| アルゴリズムの改善と費用対効果 | 正しい方向の改善が点にならないのはなぜか |
| ベンチマーカーのログを読む | 何が不満なのかを、どこから知るか |
| ブラフに時間を使わない | 文書にあるが効かない要素をどう見分けるか |

## 負荷の強さを選べる仕様

ISUCON では、参加者が負荷の強さを自分で選べる仕組みが繰り返し出題されています。

ISUCON9 予選（椅子のフリマ「ISUCARI」）では、初期化のエンドポイントが返す値で負荷の強さを決めました。講評には次のように書かれています（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。

> アプリケーションの初期化エンドポイントである /initialize で campaign というキーの値で 0 よりも大きな数字を返すことで、キャンペーン機能を有効にすることができます。数字は0から4までとなり、数字が大きくなると同時にアクセスするユーザも増えていきます。

参照実装の Go のコードでは、この値は `Campaign: 0` に固定されていました（[isucon/isucon9-qualify webapp/go/main.go](https://github.com/isucon/isucon9-qualify/blob/master/webapp/go/main.go)）。講評は、上位に行くには「キャンペーン機能を最大まで上げて同時アクセス数を増やし、さらに人気者出品で発生する１つの商品の負荷の集中を緩和して、出品される商品の単価をあげていく必要がありました」と書いています。

ISUCON11 予選（時系列データの「ISUCONDITION」）では、逆向きの変数がコードに埋め込まれていました。センサーから届くデータを受け取るハンドラは、初期状態で 9 割のリクエストを読み捨てます（[isucon/isucon11-qualify webapp/go/main.go](https://github.com/isucon/isucon11-qualify/blob/main/webapp/go/main.go)）。

```go
// ISUからのコンディションを受け取る
func postIsuCondition(c echo.Context) error {
	// TODO: 一定割合リクエストを落としてしのぐようにしたが、本来は全量さばけるようにすべき
	dropProbability := 0.9
	if rand.Float64() <= dropProbability {
		c.Logger().Warnf("drop post isu condition request")
		return c.NoContent(http.StatusAccepted)
	}
```

講評は、この値を下げるとデータが増えてグラフの確認による加点が大きくなる一方で、「初期状態では dropProbability を下げてもアプリケーションが負荷に耐えきれず、GET の処理をする余裕がないため得点が伸びませんでした」と説明しています（[ISUCON11 予選問題の解説と講評](https://isucon.net/archives/56044867.html)）。同じ講評は、反対方向の調整にも触れています。

> 状況に応じて、trendの更新頻度を下げたり、dropProbabilityを上げたりすることで負荷を絞り、レスポンスタイムを速くすることも得点を稼ぐためには重要でした。

予選 1 位のチーム shallowverse の参加記では、この変数の扱いが時間とともに変わっています（[ISUCON11 予選 1 位の参加記](https://www.y1r.org/posts/20210831-isucon11-qualify)）。15 時半ごろには「dropProbalibityをいじったが，スコアが下がったりFAILしたりするので，とりあえず放置する．」と判断し、他の改善を進めた後の最後に「0.9だった dropProbalibity を0.4に調整すると150万点が出た」と書かれています（参加記の表記のまま引用しています）。

ここから分かるのは、**負荷を強める変数は、システムに余力があるときにだけ点になる**ということです。余力がないまま強めれば、応答が遅れ、時間切れや整合性のエラーで減点されます。だから、この種の変数は最初に触るものではなく、他の改善で余力を作った後に、少しずつ上げて確かめるものです。

| 大会 | 変数 | 置き場所 | 強めると |
| --- | --- | --- | --- |
| ISUCON9 予選 | `campaign`（0〜4） | `/initialize` の応答 | 同時に来る利用者が増える |
| ISUCON11 予選 | `dropProbability`（初期値 0.9） | ハンドラのコード | 受け取るデータが増え、グラフの加点が増える |
| ISUCON11 予選 | trend の更新頻度 | アプリケーションの実装 | 閲覧者の評判が上がり利用者が増える |
| ISUCON14 | `ISUCON_MATCHING_INTERVAL`（初期値 0.5 秒） | `/home/isucon/env.sh` | 配車の待ちが短くなる |
| ISUCON14 | `retry_after_ms`（初期値 30） | 通知の応答 | 通知を確かめに来る頻度が上がる |

### つまみを回す手順

この種の変数は、1 回の負荷走行で最適な値が分かるものではありません。余力の大きさは他の改善とともに変わるので、改善を入れるたびに最適な値も動きます。shallowverse の参加記には、終盤の作業として「パラメータチューニングしやすいように定数まとめたり」と書かれ、それが「終盤のベンチ & チューニングの時間短縮につながった．」とあります（[ISUCON11 予選 1 位の参加記](https://www.y1r.org/posts/20210831-isucon11-qualify)）。

手順としては、次のようにします。

1. **変数を 1 か所に集める。** コードに散らばった定数、環境変数、設定ファイルの値を、変えるたびにデプロイし直さなくて済む場所に置く。ISUCON14 の `env.sh` のように、最初から外に出ている変数もある
2. **1 回に 1 つだけ動かす。** 2 つの変数を同時に動かすと、どちらが効いたのか分からない
3. **値と結果を表に残す。** 値、点、エラーの数、主な応答時間を、走行ごとに記録する
4. **他の改善を入れたら、もう一度振る。** 前に下げて失敗した値が、余力ができた後には効くことがある。shallowverse の `dropProbability` がまさにその例だった

ISUCON2026 の優勝者の記録には、この表の実例があります（[ISUCON2026 競技当日の記録](https://zenn.dev/luvtechno/articles/isucon2026-competition-day)）。投稿数の上限を超えたら応答を 2 秒遅らせるという調整で、上限を「なし、162、54、36、27」と変えたときの点が「505,000、509,132、546,385、538,787、506,261」でした。記録には「1回ずつの結果なので、後で触れるスコアのばらつきを含んでいました。」と添えられています。山の形は見えますが、隣り合う値の差がぶれより小さいかどうかは、1 回ずつの結果からは判断できません。この点は次回、最後の 1 回の判断として扱います。

本番のサービスにも同じ種類の変数があります。ログやトレースのサンプリング率、クライアントのポーリング間隔、バッチの実行間隔、レート制限の上限、キャッシュの有効期限は、どれも「負荷」と「価値（鮮度、精度、受け付ける量）」を交換するつまみです。ISUCON との違いは、本番では価値の側を測る指標を自分で決めなければならないことで、それが第 261 回で見た SLO やビジネス指標の役割です。

## 通知をどう待たせるか

### ISUCON14 の通知

ISUCON14（ライドシェアの「ISURIDE」）では、利用者と椅子が配車の状態の変化を知るための通知エンドポイントが 2 つありました。当日の文書は、2 通りの実装を認めています（[isucon/isucon14 docs/ISURIDE.md](https://github.com/isucon/isucon14/blob/main/docs/ISURIDE.md)）。

> どちらの実装においても、状態が変更されてから3秒以内に通知されていることが期待されます。

JSON を返す方式では、「クライアントはレスポンスの `retry_after_ms` で指定された時間(ms)が経過した後に再度リクエストを送信します。」とあり、参照実装の値は 30 ms でした。もう一つの方式は、第 88 回で見た SSE（Server-Sent Events）で、接続を張ったままサーバから変化を送ります。同じ文書は、通知の順序について「どちらの通知も発生したすべての状態遷移を、発生した順序通りに、少なくとも1回以上（at least once）返す必要があります。」とも定めていました。

講評は、30 ms という値の由来を説明しています（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。

> 初期状態では30ms間隔という超頻度でポーリングされるようになっていました。これはベンチマーカー内の世界が30msを1tickとして動いていることに由来します。retry_after_msプロパティで頻度を制御することが可能ですが、頻度を下げるとユーザーや椅子が状態変化に気づくまでの時間が長くなり、満足度が下がるような仕組みになっていました。

つまり、間隔を延ばせばリクエストが減って他の処理に余力が回り、延ばしすぎれば利用者の満足度が下がります。4 位のチーム（LayerX）の参加記には、この調整が 2 段階で現れます（[ISUCON14 参加記](https://zenn.dev/layerx/articles/3bd55b77e047c4)）。マッチングの改善と同時に「通知のリクエスト間隔を 100ms -> 300ms に伸ばす」ことで 30,936 点、終盤に「通知をまとめて返し、通知間隔を 300ms -> 1000ms に」することで 39,027 点になっています。後者は、間隔を延ばした分だけ溜まる複数の状態遷移を 1 回の応答でまとめて返すことで、「すべての状態遷移を順に返す」という条件を満たしたまま回数を減らしたものです。

### 押し出せば解決するとは限らない

ポーリングをやめてサーバから押し出せば、遅れもリクエストも減るように見えます。ところが、ISUCON10 本選では、それで点が下がったという報告が多くありました。この問題のベンチマーカーは Web Push のサーバを内蔵していて、通知を Web Push に切り替えられるようになっていました。講評はこう書いています（[ISUCON10 本選問題の解説と講評](https://isucon.net/archives/55140539.html)）。

> 参加者の多くは実装しなかった、あるいは実装したけどスコアが下がったのでポーリング方式に切り戻した、というご意見が多かったような印象です。実は、単にすべての状態の変化を即時に仮想選手に Web Push 通知するだけだと、仮想選手達は同時かつ即時に次のリクエストを送ってきていわゆる Thundering Herd 問題が発生し、より瞬間的な負荷が高まってしまうという状況が予想されるからです。

全員に同時に届く通知は、全員を同時に動かします。ポーリングの間隔には、リクエストの時刻を自然にばらけさせる働きもあったわけです。想定解の一つは、全員に送る通知はポーリングのまま残し、個別の通知だけを押し出す、という使い分けでした。

ISUCON14 の講評も、SSE への移行について同じ趣旨のことを書いています。

> 移行するか否かについては「ドキュメントに書いてあるからとりあえず移行してみよう」ではなくこちらからステータスの変更を迅速に送ることができるなどの移行によるメリットや移行のためのコストなどを勘案して移行するかの判断をすることが必要だったのではないかと思います。

### 実測：ポーリングの間隔と通知の遅れ

間隔を変えると、リクエストの数と通知の遅れがどう変わるのかを手元で測ります。Go で 1 つのプロセスの中に HTTP サーバと 200 個のクライアントを立てました。

- サーバは利用者ごとの状態の版番号を持ち、平均して 1 秒に 1 回、各利用者の状態をどこかで 1 つ進める（全体で毎秒約 200 回の変化）
- クライアントは自分の版番号を付けて問い合わせ、応答の `retry_after_ms` だけ待って次を送る
- 比較のために、変化があるまで応答を保留するロングポーリング（最大 2 秒）も用意する
- 5 秒間の、毎秒のリクエスト数、起きた変化の数、クライアントが気づいた変化の数、変化から気づくまでの遅れを数える

サーバの中心は次のとおりです。

```go
func handler(w http.ResponseWriter, r *http.Request) {
	reqs.Add(1)
	id, _ := strconv.Atoi(r.URL.Query().Get("id"))
	seen, _ := strconv.Atoi(r.URL.Query().Get("v"))
	st.mu.Lock()
	v := st.version[id]
	if longPoll && v == seen {
		// 変化があるまで（最大 2 秒）応答を保留する
		ch := make(chan struct{})
		st.waiters[id] = append(st.waiters[id], ch)
		st.mu.Unlock()
		select {
		case <-ch:
		case <-time.After(2 * time.Second):
		}
		st.mu.Lock()
		v = st.version[id]
	}
	st.mu.Unlock()
	json.NewEncoder(w).Encode(map[string]int{"v": v, "retry_after_ms": retryMs})
}
```

環境は Apple M1 Pro、macOS 26.2、Go 1.24.6 です。

```text
$ for r in 30 100 300 1000; do ./poll -retry $r; done; ./poll -long
poll   30ms  req/s=  6014  changes= 807 seen= 803  req/seen= 37.4  delay mean=  17.2ms p99=  51.4ms
poll  100ms  req/s=  2000  changes= 892 seen= 874  req/seen= 11.4  delay mean=  50.9ms p99= 100.4ms
poll  300ms  req/s=   680  changes= 856 seen= 787  req/seen=  4.3  delay mean= 143.4ms p99= 298.4ms
poll 1000ms  req/s=   200  changes= 798 seen= 540  req/seen=  1.9  delay mean= 429.9ms p99= 987.3ms
long-poll    req/s=   202  changes= 855 seen= 855  req/seen=  1.2  delay mean=   0.3ms p99=   2.2ms
```

読み取れることを並べます。

- **リクエストの数は間隔に反比例する。** 200 クライアントが 30 ms ごとに来れば、理論上は毎秒約 6,667 回です。実測の 6,014 回との差は、応答を待つ時間の分です。100 ms では 2,000 回、1,000 ms では 200 回でした。
- **遅れの平均は間隔の約半分、最悪は間隔とほぼ同じになる。** 変化はポーリングの合間のどこかで起きるので、平均すると間隔の半分だけ待たされます。30 ms で平均 17.2 ms、300 ms で 143.4 ms でした。
- **1 回気づくための問い合わせの数が大きく違う。** 30 ms では、1 つの変化に気づくまでに 37.4 回問い合わせています。そのほとんどは「変化なし」を返すだけのリクエストです。
- **間隔が長いと、変化がまとまって見える。** 1,000 ms では 798 回の変化のうち、クライアントが別々に気づいたのは 540 回でした。残りは、前の問い合わせと次の問い合わせの間に 2 回以上起きた変化が 1 回分として見えたものです。この実験は最新の版番号だけを返しているので変化が消えていますが、ISUCON14 のように「すべての状態遷移を順に返す」仕様なら、サーバは未送信の遷移を溜めておき、まとめて返す必要があります。LayerX が間隔を延ばすときに「通知をまとめて返し」たのは、この条件を守るためです。
- **ロングポーリングは、リクエストの数を 1,000 ms のポーリング並みに抑えたまま、遅れをほぼ 0 にする。** その代わり、保留している間のコネクションとゴルーチンをサーバが抱えます。SSE も同じで、接続を張り続ける費用と引き換えに即時性を得ます。

なお、この実験はサーバとクライアントが同じプロセスにあり、リクエストあたりの処理もほぼ空です。本番の通知エンドポイントがデータベースを引くなら、1 回の問い合わせの費用はこの何倍にもなり、「変化なし」を返すだけのリクエストの割合がそのまま無駄になります。

<Callout type="note" title="間隔をサーバが決めるという設計">
  `retry_after_ms` のように、次に来るまでの時間を応答に含める設計は、負荷が高いときにサーバ側から間隔を延ばせるという利点があります。HTTP にも、503 などの応答で、次の要求まで待つべき時間を示す `Retry-After` ヘッダがあります（[RFC 9110: 10.2.3. Retry-After](https://www.rfc-editor.org/rfc/rfc9110#section-10.2.3)）。
  クライアントの側に固定の間隔を埋め込んでしまうと、配布済みのアプリケーションの振る舞いを後から変えられません。第 16 章で見たリトライの間隔と同じく、間隔の決定権をどちらに置くかは、障害の時にも効いてきます。
</Callout>

## 待ち行列を回す間隔

### ISUCON14 のマッチング

ISUCON14 では、配車の要求と空いている椅子を結び付ける処理（マッチング）が、別のサービスから一定間隔で呼ばれていました。文書には「初期状態では `isuride-matcher` というsystemdサービスがアプリケーションの `GET /api/internal/matching` を500msごとにポーリングすることで、ライドと椅子のマッチングを行う処理を起動しています。」とあり、間隔は `env.sh` の `ISUCON_MATCHING_INTERVAL` で変えられました（[isucon/isucon14 docs/ISURIDE.md](https://github.com/isucon/isucon14/blob/main/docs/ISURIDE.md)）。参照実装のマッチングは、最も長く待っている要求を 1 件取り出し、空いている椅子を `ORDER BY RAND()` で 1 台選ぶものでした（[isucon/isucon14 webapp/go/internal_handlers.go](https://github.com/isucon/isucon14/blob/main/webapp/go/internal_handlers.go)）。

講評は、出題側の想定と実際の結果の違いを率直に書いています（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。

> 作問時点では上位入賞には、マッチングアルゴリズム自体の改善とバルク化が必須だと考えていましたが、アルゴリズムはそのままでマッチング頻度を上げるだけで上位入賞を果たしているチームもありました。

3 位のチームの参加記には、その場面が具体的に残っています（[ISUCON 14に参戦して3位入賞しました](https://blog.pinkumohikan.com/entry/isucon-14)）。8,775 点の時点のベンチマーカーのログから「マッチングまでの時間が長いため満足度が下がって離脱が増えていると推測しました。」と考え、間隔を 0.5 秒から 0.1 秒に縮めたところ 25,758 点になっています。

一方、同じチームは、その後に乗車位置に最も近い椅子を割り当てる改善に取り組み、乗車位置までの時間への不満は 86.7% から 43.6% に下がったものの、点は伸びませんでした。参加記には「合計4時間？くらい費やしたが残り1.5hほどとなったので渋々諦め」とあります。4 位の LayerX は、ランダムをやめて「空いてる chair のうち最も近いものを選ぶようにする」改善を同じ時期の N+1 の解消と一緒に入れ、21,372 点に上げています。

同じ方向の改善が、片方では点になり、片方ではならなかった。その理由を考えるために、手元で単純化したモデルを動かします。

### 実測：マッチングの間隔と割り当て方

次のシミュレーションは、ISURIDE を大きく単純化したものです。実時間ではなく、1 ms 刻みの離散時間で 600 秒分を計算します。

- 100 × 100 の格子の上に椅子が 30 台ある。椅子は 1 ms に 0.01 進む（1 秒に 10）
- 配車の要求は平均して毎秒 `rate` 件、ランダムな乗車位置と目的地で届く
- 要求は 3 秒以内にマッチングされなければ離脱する
- マッチングは `interval` ms ごとに動き、待っている要求を 1 件だけ（参照実装と同じ）か、全件（`-all`）処理する
- 椅子の選び方は、空いている椅子からランダム（参照実装と同じ）か、乗車位置に最も近い椅子（`-nearest`）
- 点は ISUCON14 の定義に合わせ、「乗車位置までの距離 × 0.1 + 乗車位置から目的地までの距離 + 完了数 × 5」とする

ISUCON14 の点の定義は、当日の文書のとおりです（[isucon/isucon14 docs/manual.md](https://github.com/isucon/isucon14/blob/main/docs/manual.md)）。

マッチングの中心部分の要点を抜き出すと次のとおりです（説明のために一部を関数に分けて簡略化しています）。

```go
for matched < n && len(queue) > 0 {
	r := queue[0]
	free := freeChairs(t)
	if len(free) == 0 {
		break // 空いている椅子がなければ次の回まで待つ
	}
	ci := free[rng.Intn(len(free))]
	if *nearest {
		ci = nearestTo(free, r.pickup)
	}
	assign(ci, r, t)
	queue = queue[1:]
	matched++
}
```

まず、間隔の効き方です。

- 500 ms ごとに 1 件しか処理しないと、処理できるのは最大で毎秒 2 件です。毎秒 1.5 件の到着に対しては足りていますが、到着の偏りで行列ができ、マッチングまでの平均の待ちは 743 ms でした。間隔を 100 ms にすると 57 ms に下がり、離脱が 0 になりました。
- 500 ms のまま全件を処理しても、離脱は 0 になります。**間隔を縮めることと、1 回で全件を処理することは、どちらも処理能力を上げる手段**です。
- 椅子が足りない条件では、間隔を縮めると完了数は 1,150 件から 1,320 件に増えますが、全件処理を足しても 1,319 件で頭打ちです。ここでは、マッチングの処理能力ではなく**椅子の台数**が限界になっています。

次に、近い椅子を選ぶ効き方です。

- 椅子に余裕がある条件では、近い椅子を選ぶと乗車位置までの時間が 6,604 ms から 2,168 ms へ 3 分の 1 になりました。ところが完了数はほとんど変わらず、点はむしろ 67,043 から 63,517 に下がりました。このモデルでは、要求の数が外から決まっているので、早く運んでも完了数は増えません。そのうえ点の定義には「乗車位置までの距離 × 0.1」が含まれるので、迎えの距離を縮めるとその分の点が減ります。
- 椅子が足りない条件では、近い椅子を選んでも乗車位置までの時間は 6,633 ms から 6,220 ms にしか縮みません。空いた椅子が出るたびに待っている要求へすぐ割り当てるので、**選べる椅子が 1 台か 2 台しかない**からです。完了数は 1,320 件から 1,369 件へ、約 4% 増えました。

この単純なモデルは、ISUCON14 のベンチマーカーを再現していません。ISUCON14 では、満足度が上がると利用者や椅子が増える仕組みがあり、早く運ぶことが次の需要を生みます。このモデルにはその仕組みがないので、近い椅子を選ぶ改善の効果は小さく出ます。それでも、次のことは言えます。

**同じ改善でも、そのとき何が律速しているかによって、効いたり効かなかったりする。** 待ちが長いことが律速なら間隔や一括処理が効き、椅子の台数が律速なら割り当て方は小さくしか効かず、需要が律速なら運ぶ速さは点にならない。3 位のチームの参加記には、後から振り返って「改善は上手く行っていてマッチング間隔にネックが戻っていましたね。。。」と書かれています。律速が別の場所に移っていたために、正しい方向の改善が点に現れなかったと読めます。

## アルゴリズムの改善と費用対効果

ISUCON14 の講評は、マッチングのさらなる改善について、出題側は乗車位置に近い椅子を割り当てる貪欲法を想定していたこと、ある時点での割り当ての移動距離の最小化は二部マッチング問題として解けることを紹介しています（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。理屈の上では、貪欲法より二部マッチングの方が全体の移動距離は短くなります。

ただ、競技の 8 時間でも、本番の開発でも、問うべきは「より良いアルゴリズムか」ではなく「**その改善が、いま律速している量を動かすか**」です。上の実験で言えば、椅子が足りない条件で割り当てを最適化しても、選べる椅子が 1〜2 台しかない以上、改善の余地はほとんどありません。

| 状況 | 先に効くもの | 後回しでよいもの |
| --- | --- | --- |
| 待ち行列が伸びて離脱が出ている | 処理の間隔、1 回の処理量、処理そのものの速さ | 割り当ての質 |
| 処理する資源（椅子、ワーカー、コネクション）が足りない | 資源を増やす、1 件あたりの占有時間を縮める | 待ちの短縮 |
| 資源に余裕があり、1 件あたりの質が点になる | 割り当ての質（近さ、優先度） | 間隔の短縮 |
| 需要が外から決まっていて伸びない | （速度の改善は点にならない。目的関数を見直す） | ほぼすべて |

ISUCON11 本選で優勝したチームの参加記には、点に明確に響かない手を打ち続ける苦しさと並べて、次の一文があります（[fujiwara組の ISUCON11 本選参加記](https://sfujiwara.hatenablog.com/entry/isucon11-final)）。

> リアルでのパフォーマンスチューニングでは、明確に数字が上がらない施策を無闇に入れるのは避けるべきですよね。

本番では、アルゴリズムの改善はコードの複雑さと保守の費用を伴います。改善を入れる前に「どの指標がどれだけ動くはずか」を書き、入れた後にその指標が動いたかを確かめる。動かなかったら、律速が別の場所にある可能性をまず疑い、改善を取り下げることも選択肢に入れます。

## ベンチマーカーのログを読む

アクセスログやプロファイルは、システムの中で何が起きているかを教えてくれます。しかし、**利用者が何に不満を持っているか**は、システムの中からは見えません。ISUCON では、その情報がベンチマーカーの出力に含まれていることがあります。

ISUCON14 の 3 位のチームは、ベンチマーカーのログに出ていた次の行を手がかりにしました（[ISUCON 14に参戦して3位入賞しました](https://blog.pinkumohikan.com/entry/isucon-14)）。

> 93.8%のライドは椅子がマッチされるまでの時間、95.9%のライドはマッチされた椅子が乗車地点までに掛かる時間、20.6%のライドは椅子の実移動時間に不満がありました

3 つの段階のどこに不満が集中しているかが分かれば、改善の順序が決まります。ここではマッチングまでの時間への不満が最も多かったので、間隔の短縮が最初の手になりました。

ベンチマーカーのエラーも、仕様を知る材料です。ISUCON13 で優勝したチームの参加記には、処理を速くしすぎて失敗した例があります（[チーム NaruseJun の ISUCON13 参加記](https://zenn.dev/tohutohu/articles/923bdf5dcd73af)）。NG ワードを追加したときの削除処理を効率化したところ、「期待されたHTTPステータスコードが確認できませんでした (expected:400, actual:201)」というエラーが増えたので、500 ms 待つようにし、終盤にはその待ち時間を増やすと点が上がったので最終的に 1 秒待つことにした、と書かれています。ベンチマーカーは、NG ワードの追加が反映された後に投稿されたコメントが拒否されることを確かめていて、反映の時刻とベンチマーカーの期待がずれると、それが整合性のエラーとして数えられたと考えられます。

ISUCON2026 で優勝した参加者の記録には、さらに進んだ例があります（[ISUCON2026 競技当日の記録](https://zenn.dev/luvtechno/articles/isucon2026-competition-day)）。サーバの CPU に余裕があるのに毎秒のリクエスト数が伸びなくなったことから、律速はベンチマーカー側の処理能力だと判断し（記録には「原因が確定したわけではなく、実測値からの判断です。」と添えられています）、点の倍率が低い地域への応答を意図的に遅らせて、倍率の高い地域へ処理能力を回すことで点を上げています。この大会は 1 人の参加者が AI のエージェントに競技を任せた事例なので、人の判断の参考としては扱いに注意が要りますが、**負荷をかける側の限界も、律速段階の一つになりうる**ことを示しています。

<Callout type="warn" title="応答を遅らせる調整は競技の外に持ち出さない">
  ベンチマーカーの期待に合わせて応答を遅らせる、利用者を増やさないために一部の応答を遅らせる、といった調整は、点の定義が固定された競技だから成り立つものです。
  本番で同じ目的を果たすのは、レート制限、優先度付きの待ち行列、混雑時に機能を絞る設計（劣化運転）です。いずれも、遅らせることを利用者に説明でき、監視できる形で入れます。
</Callout>

本番で「ベンチマーカーのログ」に当たるのは、利用者の側から見た指標です。ブラウザで測った Web Vitals（第 17 章）、クライアントの再試行の回数、問い合わせの内容、途中で離脱した利用者の割合などです。サーバのログだけを見ていると、「サーバは速いのに利用者は待っている」状態（クライアントのポーリング間隔が長い、モバイル回線の往復が多い）を見落とします。

## ブラフに時間を使わない

ISUCON の文書には、存在はするが改善しても点にならない要素が含まれていることがあります。ISUCON14 の決済の再試行がその例です。決済のマイクロサービスは `Idempotency-Key` ヘッダ（第 16 章で見た冪等性キー）に対応していて、これを使えば失敗時の確認 API の呼び出しを省けました。しかし、講評は次のように書いています（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。

> 要素としては存在するのでドキュメントにも記載したので、かなりのブラフになってしまったのですがこれに囚われていた人はあまりいなかったようで安心しています。

ブラフに見えるものが、実は後から効く場合もあります。ISUCON10 本選のダッシュボードの集計は、69 行の SQL 1 本で書かれていました。講評によれば、このクエリは「データ量（仮想負荷走行の実行回数）の少ない初期状態ではスロークエリではないですがチューニングが進むと重くなっていく」ものでした（[ISUCON10 本選問題の解説と講評](https://isucon.net/archives/55140539.html)）。最初の計測で目立たないからといって無関係とは限らず、他の改善で負荷が増えると前に出てきます。

見分けるための規則は単純です。

1. **計測に出ていないものは、まだ触らない。** 文書に書いてあるから、見た目が怪しいから、という理由では着手しない。
2. **他の改善を入れるたびに計測を取り直す。** 69 行の SQL のように、律速が移ってきたときに初めて手を付ける。
3. **入れた改善が点を動かさなかったら、時間を区切って引き返す。** 3 位のチームが 4 時間を費やしたマッチングの改善のように、方向が正しくても律速でなければ点にならない。

本番の開発でも事情は同じです。設計書やレビューで「ここが遅そう」と指摘された箇所が、実際のトラフィックでは呼ばれていないことはよくあります。指摘を記録しておき、計測でその箇所が上位に出てきたときに着手するのが、限られた時間の使い方として合理的です。

## 次に向けて

ここまでで、遅い Web アプリケーションを速くするための手段は一通り揃いました。次回は最終回として、積み上げた変更を「終わらせる」ための作業を扱います。再起動しても同じように動くか、計測のために入れたものを外したか、最後の 1 回のスコアがどれだけぶれるのかを確かめます。

## まとめ

- ボトルネックを片付けた後も、負荷の強さ、確かめに来る間隔、溜まった仕事を処理する間隔という仕様の側の変数が点を大きく動かす
- 負荷を強める変数（`campaign`、`dropProbability`）は、余力があるときにだけ点になる。他の改善で余力を作ってから、少しずつ上げて確かめる
- ポーリングのリクエスト数は間隔に反比例し、通知の遅れの平均は間隔の約半分になる。手元の実験では 30 ms で毎秒 6,014 回、1 回気づくのに 37.4 回の問い合わせだった
- 間隔を延ばすと変化がまとまって見える。すべての遷移を返す仕様なら、サーバ側で溜めてまとめて返す
- ロングポーリングや SSE は、接続を保つ費用と引き換えに遅れとリクエスト数を同時に減らす。ただし全員への同時通知は Thundering Herd を生むので、ポーリングと使い分ける
- 待ち行列の処理能力は、間隔を縮めても 1 回の処理量を増やしても上がる。資源（椅子）が足りなくなると、どちらも頭打ちになる
- 割り当ての質（近い椅子を選ぶ）は、資源に余裕があり、その質が点や価値に結び付くときにだけ効く
- 同じ改善が効くかどうかは、そのとき何が律速しているかで決まる。改善の前に動くはずの指標を書き、動かなければ引き返す
- 利用者の不満はシステムの中からは見えない。ISUCON ではベンチマーカーのログ、本番では利用者側の指標から読む
- 文書にあるが計測に出ない要素（ブラフ）には手を付けない。ただし、負荷が増えると前に出てくるものもあるので、改善のたびに計測を取り直す
