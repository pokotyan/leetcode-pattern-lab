前回は、MQTT がブローカを挟んだ pub/sub で、細く不安定な回線の上でも QoS とセッションを使ってメッセージを届けることを見ました。MQTT は TCP の上に載っています。TCP の上にいる限り、1 つのパケットが失われると後ろのメッセージはすべて待たされ、端末のアドレスが変われば接続を張り直すしかありません。

第 66 回では、QUIC が HTTP/2 の HOL ブロッキングを取り除くために、ストリーム、パケット番号、接続 ID、TLS 1.3 を UDP の上にまとめ直したことを見ました。そこでの QUIC は **HTTP/3 の運び手**でした。この回では、HTTP を外して **QUIC を汎用のトランスポートとして使う**ことを考えます。ストリームに加えて「再送しないデータグラム」を持てるようになると、ゲームや音声、トンネルのように、これまで素の UDP で自作していた通信を QUIC に載せられます。そのとき何が手に入り、何に困るのかを、手元で損失と遅延を入れて確かめ、最後にゲームでの採用事例と突き合わせます。

## QUIC を部品として見る

リアルタイム性の高い通信を作るとき、従来の選択肢は 2 つでした。素の UDP の上に必要なものを自作するか、TCP と UDP を併用して、確実に届けたいものを TCP に、遅れるくらいなら捨てたいものを UDP に流すかです。QUIC はこの 2 つの間に、もう 1 つの選択肢を作りました。

| 欲しいもの | 素の UDP で自作 | TCP と UDP を併用 | QUIC |
| --- | --- | --- | --- |
| 確実に順序どおり届ける | 再送と並べ替えを自作 | TCP が持つ | ストリーム |
| 遅れたら捨ててよいデータ | そのまま送る | UDP 側で送る | DATAGRAM 拡張 |
| 種類の違うデータが互いを待たない | 自作 | 2 本の接続に分ければ待たない。TCP の中では待つ | ストリームごと、DATAGRAM は待たない |
| 暗号化と認証 | DTLS などを別に組み込む | TLS と DTLS を別々に | 1 回の TLS 1.3 のハンドシェイクで両方 |
| 輻輳制御 | 自作するか、しない | 2 本が別々に帯域を取り合う | 接続全体で 1 つ |
| アドレスが変わっても続ける | 自前のセッション ID | TCP は張り直し | 接続 ID と経路検証 |

QUIC を選ぶと、**信頼できるストリームと信頼性のないデータグラムが、1 つの暗号化された接続と 1 つの輻輳制御の下に同居します**。TCP と UDP の併用では、暗号化の鍵もタイムアウトも輻輳への反応も 2 系統あり、片方だけ切れたときの扱いをアプリケーションが決める必要がありました。素の UDP の自作では、これらをすべて自分で作ることになります。

代わりに払うものは、第 66 回で見たとおりです。QUIC はユーザ空間で動くので CPU を多く使い、UDP が途中で塞がれる環境では TCP に戻る道を用意しておく必要があります。

## DATAGRAM 拡張（RFC 9221）

QUIC の本体（RFC 9000）には、信頼性のないデータを送る手段がありません。それを足したのが **DATAGRAM 拡張**です（[RFC 9221](https://www.rfc-editor.org/rfc/rfc9221.html)）。

使うには、両側がトランスポートパラメータ `max_datagram_frame_size`（0x20）で、受け取れる DATAGRAM フレームの最大の大きさを宣言します。既定値は 0 で、0 より大きい値を送ってきた相手にだけ DATAGRAM を送れます（[RFC 9221 3](https://www.rfc-editor.org/rfc/rfc9221.html#section-3)）。フレームの形はごく単純です（[RFC 9221 4](https://www.rfc-editor.org/rfc/rfc9221.html#section-4)）。

```
DATAGRAM Frame {
  Type (i) = 0x30..0x31,     最下位ビット（LEN）が 1 なら Length 欄がある
  [Length (i)],              無ければパケットの残り全部がデータ
  Datagram Data (..),
}
```

STREAM フレームと比べると、**ストリーム ID もオフセットも無い**ことが分かります。どのデータグラムが何の用途なのかを区別したければ、アプリケーションが先頭に識別子を入れます。RFC 9221 は、先頭に可変長整数を置く形を勧めています（[RFC 9221 5.1](https://www.rfc-editor.org/rfc/rfc9221.html#section-5.1)）。

### 再送しないが、ACK は返り、輻輳制御も受ける

DATAGRAM の振る舞いは、「UDP をそのまま QUIC に通したもの」とは違います。RFC 9221 の 5 節を順に読むと、次のようになっています。

| 性質 | 内容 | 出典 |
| --- | --- | --- |
| 再送 | 失われたと判断しても**送り直さない** | [5.2](https://www.rfc-editor.org/rfc/rfc9221.html#section-5.2) |
| ACK | **ack-eliciting**（受け取った側に ACK を返させる）。失われたか届いたかを、実装はアプリケーションに知らせてよい（MAY） | [5.2](https://www.rfc-editor.org/rfc/rfc9221.html#section-5.2) |
| 輻輳制御 | 接続の輻輳制御に従う。送れないときは、待たせるか、送らずに捨てる | [5.4](https://www.rfc-editor.org/rfc/rfc9221.html#section-5.4) |
| フロー制御 | 無い。受け取った側は、処理しきれなければ捨ててよい | [5.3](https://www.rfc-editor.org/rfc/rfc9221.html#section-5.3) |
| 大きさ | 分割できない。1 つのパケットに収まらないものは送れない | [5](https://www.rfc-editor.org/rfc/rfc9221.html#section-5) |
| 暗号化 | STREAM と同じく 0-RTT か 1-RTT の鍵で保護する | [5](https://www.rfc-editor.org/rfc/rfc9221.html#section-5) |

**再送しないのに ACK が返る**のが要点です。QUIC の ACK は「どのパケット番号を受け取ったか」を返すもので、中身が STREAM か DATAGRAM かは区別しません。送る側は ACK から損失と RTT を知り、それを輻輳制御に使います。DATAGRAM だけを送っていても、経路が詰まれば送る速さは絞られます。素の UDP のように、詰まった経路へ同じ速さで送り続けることはありません。

裏返すと、**アプリケーションが「捨ててよい」と言ったデータにも、ACK の分のパケットが逆向きに流れます**。そして、輻輳制御が送信を止めた瞬間には、DATAGRAM は待たされるか捨てられます。「送れば即座に出ていく」という UDP の感覚とは、ここが違います。

### ストリームとの使い分け

| | ストリーム | DATAGRAM |
| --- | --- | --- |
| 届くか | 届くまで再送する | 届かないことがある |
| 順序 | ストリームの中で守る | 守らない |
| 損失したとき | そのストリームの後続が待つ（第 66 回） | 何も待たない |
| 大きさ | 任意。分割して送る | 1 パケットに収まる大きさまで |
| 向いているもの | ログイン、購入、チャット、マップの読み込み | 位置や向きの更新、音声のフレーム、トンネルの中身 |

判断の軸は「**遅れて届いたものに価値が残るか**」です。10ms ごとに送るキャラクターの位置は、40ms 遅れて届いた時点で次の位置に追い越されていて、使い道がありません。購入の確定は、遅れても必ず届かなければなりません。

## 手元で確かめる

DATAGRAM とストリームを両方使う小さなサーバとクライアントを Go の [quic-go](https://github.com/quic-go/quic-go) で書き、Docker のコンテナ 2 つの間で動かしました。

- 環境: Apple Silicon の Mac 上の Docker Desktop（Docker Engine 29.2.1、Linux カーネル 6.12.72-linuxkit）、`debian:bookworm-slim` に iproute2 6.1.0
- 実装: quic-go v0.63.0、Go 1.26.0。`EnableDatagrams: true` を指定し、qlog を書き出す
- 送り方: クライアントが 10ms ごとに 100 バイトのメッセージを 500 個送る。各メッセージは番号と送信時刻を持ち、DATAGRAM と 1 本の双方向ストリームの**両方に同じものを**流す。サーバは受け取った時刻との差を遅延として記録する（2 つのコンテナは同じカーネルの時計を使う）
- 経路: `tc qdisc add dev eth0 root netem` で、クライアントからサーバへ 20ms、サーバからクライアントへ 20ms の遅延を入れる（往復 40ms）。損失を入れる回は、クライアントからサーバへの向きにだけ `loss 5%` を足す

クライアントの送信部分は次のとおりです（抜粋）。

```go
conn, _ := tr.Dial(ctx, raddr, tlsConf, &quic.Config{
	EnableDatagrams: true,
	Tracer:          qlog.DefaultConnectionTracer, // $QLOGDIR に qlog を書く
})
s, _ := conn.OpenStreamSync(ctx)
for i := 0; i < 500; i++ {
	conn.SendDatagram(encode(i)) // 再送されない
	s.Write(encode(i))           // 再送される
	time.Sleep(10 * time.Millisecond)
}
```

比較のために、同じメッセージを素の UDP で送るだけのプログラムも用意しました。

### 損失を入れたときの遅延と欠落

クライアントからサーバへの向きに 5% の損失を入れた結果です（遅延は送信から受信まで、片道）。

| 実行 | 受け取った数 | p50 | p90 | p99 | 最大 |
| --- | --- | --- | --- | --- | --- |
| DATAGRAM（1 回目） | 474 / 500 | 21.2ms | 23.1ms | 32.2ms | 41.6ms |
| ストリーム（1 回目） | 500 / 500 | 21.3ms | 59.8ms | 79.2ms | 96.9ms |
| DATAGRAM（2 回目） | 468 / 500 | 21.3ms | 27.1ms | 83.3ms | 537.6ms |
| ストリーム（2 回目） | 500 / 500 | 22.0ms | 77.8ms | 137.8ms | 537.4ms |
| DATAGRAM だけを送った回 | 472 / 500 | 21.1ms | 22.8ms | 28.5ms | 38.4ms |
| 素の UDP | 474 / 500 | 21.4ms | 24.4ms | 32.3ms | 47.3ms |

**DATAGRAM は約 5% を失い、届いたものの遅延は素の UDP と変わりません。ストリームはすべて届きますが、p90 が 60〜80ms に伸びています。**片道 20ms のところに、損失の検出と再送で往復 1 回強が足されたものです。損失したメッセージだけでなく、その後ろに続いたメッセージも、再送が届くまでアプリケーションに渡されません。第 66 回で「同じストリームの中では TCP と同じく待たされる」と書いたことが、そのまま数字に出ています。

2 回目は、DATAGRAM とストリームの両方に 500ms 前後の値が 1 つずつ出ています。両方が同じ時刻に遅れているので、損失ではなく Docker Desktop の仮想マシンの処理が一時的に止まったものと考えられます。損失を入れない回でも、ときどき 100ms を超える遅延が 1〜2 個出ていました。手元の仮想環境での測定は、この程度の揺れを含みます。

もう 1 つ気づくことがあります。DATAGRAM とストリームを両方流した回では、クライアントが送った 1-RTT パケットは約 510 個で、1000 個ではありません。quic-go は、同じ時刻に出た DATAGRAM フレームと STREAM フレームを **1 つのパケットにまとめていました**。まとめれば ACK もパケットの数も減りますが、そのパケットが失われると、DATAGRAM とストリームが同時に損失を受けます。

### 送ったパケットと ACK を数える

次に、損失を入れずに、両側の qlog から 1-RTT パケットの数を数えました。「ACK だけのパケット」は、ACK フレーム（と PADDING）しか含まないものです。

| 送ったもの | クライアントが送ったパケット | サーバが送ったパケット | うち ACK だけ |
| --- | --- | --- | --- |
| 素の UDP で 500 個 | 500 | 0 | — |
| DATAGRAM で 500 個 | 522 | 257 | 239 |
| ストリームで 500 個 | 510 | 258 | 240 |
| 両方で 500 個ずつ | 508 | 259 | 241 |

素の UDP では、500 個送れば線の上を流れるのは 500 個です。QUIC の DATAGRAM で送ると、**逆向きに ACK が約 250 個流れ、合わせて約 1.5 倍**になります。DATAGRAM でもストリームでも、ACK の数はほぼ同じでした。受け取る側は、パケットの中身が何であれ、ack-eliciting なパケットを 2 つ受け取るごとに 1 回 ACK を返しています。

1 つのパケットの大きさも見ておきます。100 バイトのデータを入れた DATAGRAM のパケットは、qlog の記録で 126 バイトでした。ショートヘッダ、接続 ID（この実装では 4 バイト）、パケット番号、フレームの種類と長さ、AEAD の認証タグ 16 バイトで、26 バイトが足されています。これに IPv4 と UDP のヘッダ 28 バイトが付きます。

サーバのパケットには、ACK に混じって PING フレームが 16 回入っていました。ACK だけのパケットは ack-eliciting ではないので、送りっぱなしにすると相手から ACK が返ってきません。RFC 9000 は、そういう側が**ときどき ack-eliciting なフレームを足して**相手に ACK を返させてよいとしています（[RFC 9000 13.2.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-13.2.1)）。

## ACK の量

ACK を返す頻度は、RFC 9000 では受け取る側が決めます。

- ack-eliciting なパケットを **少なくとも 2 つ受け取ったら ACK を送るべき**（SHOULD）。TCP の遅延 ACK の勧めと揃えたもの（[RFC 9000 13.2.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-13.2.2)）
- ACK を遅らせてよい上限は、受け取る側が `max_ack_delay` で宣言する。既定値は 25ms（[RFC 9000 18.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-18.2)）
- 番号が飛んだとき（損失の疑い）や、ECN の CE 印が付いたときは、遅らせずにすぐ ACK を返すべき（[RFC 9000 13.2.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-13.2.1)）
- ACK だけのパケットは輻輳制御の対象ではない。その代わり、ack-eliciting なパケット 1 つに対して ACK だけのパケットを 2 つ以上返してはならない（[RFC 9000 13.2.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-13.2.1)）

RFC 9221 は、DATAGRAM だけを含むパケットについては、受け取る側が `max_ack_delay` の範囲で ACK を遅らせる機能を持つべきだと書いています（SHOULD）。送る側は、それらのパケットが一時的に ACK されなくても何もしないからです（[RFC 9221 5.2](https://www.rfc-editor.org/rfc/rfc9221.html#section-5.2)）。

10ms ごとに小さなメッセージを送るゲームのような通信では、2 パケットごとの ACK は少なくない量です。第 66 回で見た Fastly の測定でも、ACK の頻度を下げることが CPU の費用を下げる手段の 1 つでした。ただし、受け取る側は送る側の事情を知りません。送る側から「このくらいの間隔で ACK してほしい」と頼むための拡張が、**ACK Frequency** です（[draft-ietf-quic-ack-frequency](https://datatracker.ietf.org/doc/draft-ietf-quic-ack-frequency/)）。

| 要素 | 内容 |
| --- | --- |
| `min_ack_delay`（トランスポートパラメータ） | 受け取る側が「ACK をこれ以上は遅らせられる」下限をマイクロ秒で宣言する。これを送ってきた相手にだけ、次のフレームを送れる |
| ACK_FREQUENCY フレーム（0xaf） | Ack-Eliciting Threshold（ACK を返さずに受け取ってよい ack-eliciting なパケットの数）、Requested Max Ack Delay（遅らせてよい時間）、Reordering Threshold（どれだけ順序が乱れたらすぐ ACK するか）を指定する |
| IMMEDIATE_ACK フレーム（0x1f） | 受け取ったらすぐに ACK を返すよう求める |

執筆時点（2026 年 10 月）で、これはまだ **IETF のドラフト**です。最新の版は 2026 年 2 月の -14 で、QUIC WG の状態は「WG Consensus: Waiting for Write-Up」（WG としての合意は済み、IESG に送る文書待ち）、版としては期限が切れた扱いになっています（[datatracker](https://datatracker.ietf.org/doc/draft-ietf-quic-ack-frequency/)）。

この拡張でできるのは、ACK の**間隔を広げる**ことです。ACK を**止める**ことはできません。損失の検出も輻輳制御も ACK を前提にしているので、DATAGRAM だけを流す接続でも、ACK を完全に無くすことは QUIC の設計の外にあります。

## 接続移行の実際

第 66 回では、QUIC が接続を 4 つ組ではなく接続 ID で識別し、アドレスが変わっても接続を続けられること、新しい経路は PATH_CHALLENGE と PATH_RESPONSE で確かめることを見ました。ここでは、それが実際にどう動き、どこで困るのかを見ます。

アドレスが変わる経緯は 2 種類あります（[RFC 9000 9](https://www.rfc-editor.org/rfc/rfc9000.html#section-9)）。

- **能動的な移行**: クライアント自身が新しいアドレス（Wi-Fi からモバイル回線へ、など）から送り始める。先に新しい経路を PATH_CHALLENGE で試してから移ってよい
- **NAT の張り替え**: クライアントは何もしていないのに、途中の NAT が外側のポートやアドレスを付け替える。クライアントは気づかず、サーバだけが「送信元が変わった」と知る

どちらの場合も、サーバは新しいアドレスを確かめるまで、そこへ送る量を制限します。送信元を偽ったパケットで、他人に大量のデータを送り付けさせる攻撃を防ぐためです（[RFC 9000 9.3](https://www.rfc-editor.org/rfc/rfc9000.html#section-9.3)）。PATH_CHALLENGE を含むデータグラムは 1200 バイト以上に広げ、新しい経路がその大きさを通せることも同時に確かめます（[RFC 9000 8.2.1](https://www.rfc-editor.org/rfc/rfc9000.html#section-8.2.1)）。確かめ終わったら、輻輳制御と RTT の推定は初期値に戻します。ただし、ポート番号だけが変わった場合は NAT の張り替えであることが多いので、元の値を使い続けてもよいとされています（[RFC 9000 9.4](https://www.rfc-editor.org/rfc/rfc9000.html#section-9.4)）。

### 3 つの移行を起こす

先ほどの実験に、3 種類のアドレスの変化を加えました（損失なし、往復 40ms）。

**1. 能動的な移行。** 250 個目のメッセージの前で、クライアントが新しい UDP ソケットを作り、quic-go の `AddPath`、`Probe`、`Switch` で移りました。

```
probe ok in 42ms, switching [::]:42593 -> [::]:47649            （クライアント）
peer address changed: 172.30.0.20:42593 -> 172.30.0.20:47649   （サーバ）
```

qlog では、クライアントが新しい経路に PATH_CHALLENGE だけを入れた 1200 バイトのパケットを、それまでとは別の接続 ID で送り、サーバは自分の PATH_CHALLENGE と PATH_RESPONSE を 1 つの 1200 バイトのパケットで返していました。経路の確認に往復 1 回（42ms）かかり、500 個のメッセージはすべて届きました。確認の直後、**両側の輻輳制御が slow start に戻っていました**。変わったのはポートだけで、RFC 上は元の状態を引き継いでもよい場面ですが、quic-go は初期値に戻すほうを選んでいます。

**2. NAT の張り替えに近い変化。** 送信の途中で、クライアントのコンテナに 2 つ目のアドレス 172.30.0.21 を足し、経路表の送信元をそちらに書き換えました。ソケットはそのままで、**クライアントのプログラムは何も知りません**。

```
peer address changed: 172.30.0.20:52733 -> 172.30.0.21:52733   （サーバ）
```

サーバは送信元の変化に気づき、1200 バイトの PATH_CHALLENGE を送り、クライアントの QUIC の実装が PATH_RESPONSE を返しました。サーバの qlog の上で、送ってから応答を受け取るまで約 84ms でした。クライアントは移行したと思っていないので、それまでと同じ接続 ID を使い続けていました（[RFC 9000 9.5](https://www.rfc-editor.org/rfc/rfc9000.html#section-9.5) も、アドレスの変化を意図しない場合は ID が変わらないことがあると書いています）。600 個のメッセージはすべて届きました。

<Callout type="note" title="PATH_RESPONSE の大きさ">
  RFC 9000 8.2.2 は、PATH_RESPONSE を含むデータグラムも、増幅攻撃の制限にかからない限り 1200 バイトに広げるよう求めています。
  手元の qlog では、クライアントの PATH_RESPONSE を含むパケットは 1 と 2 のどちらでも 42〜43 バイトで、広げられていませんでした。
  PATH_CHALLENGE を送ったサーバの側は、これを受け取って経路を有効と判断しています。実装ごとに細部が違うことの一例です。
</Callout>

**3. アドレスが消える。** 最初の試みでは、新しいアドレスを足したあとに元のアドレスを消しました。Linux では、同じサブネットの最初のアドレス（primary）を消すと、後から足したアドレス（secondary）も一緒に消えます。結果として、コンテナからサーバへの経路そのものが無くなりました。

```
send datagram 272: write udp [::]:43964->172.30.0.10:4433: sendmsg: network is unreachable
```

`sendmsg` が `ENETUNREACH` を返した時点で、**クライアントの quic-go は接続をその場で閉じました**（qlog の `connection_closed` は `initiator: local`）。サーバには何も届かないので、サーバは 10 秒のアイドルタイムアウトを待ってから接続を捨てています。届いたのは 600 個中 239 個でした。

経路がしばらく無くなるのは、エレベーターに乗ったスマートフォンでは珍しくありません。RFC 9000 は「送れる経路が無いときは接続の状態を捨ててよい（MAY）。移行できる実装は、新しい経路が現れるのを待ってから捨ててもよい」と書いているだけで、**書き込みのエラーにどう反応するかは実装に任されています**（[RFC 9000 9](https://www.rfc-editor.org/rfc/rfc9000.html#section-9)）。そのエラーが OS ごとに何として返ってくるかも、同じではありません。

### ネットワークの切り替えを知る手段は OS ごとに違う

NAT の張り替えは QUIC が自動で吸収しますが、Wi-Fi からモバイル回線への切り替えのような能動的な移行は、**クライアントが「ネットワークが変わった」と知って新しいソケットを作らない限り起きません**。その「知る」手段は、OS ごとに別々です。

| OS | 手段の例 |
| --- | --- |
| Linux | netlink でアドレスや経路の変化を受け取る（[rtnetlink(7)](https://man7.org/linux/man-pages/man7/rtnetlink.7.html)） |
| iOS / macOS | Network フレームワークの `NWPathMonitor`（[Apple](https://developer.apple.com/documentation/network/nwpathmonitor)） |
| Android | `ConnectivityManager.NetworkCallback`（[Android Developers](https://developer.android.com/reference/android/net/ConnectivityManager.NetworkCallback)） |
| Windows | `NotifyIpInterfaceChange` などの IP Helper の通知（[Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-notifyipinterfacechange)） |

通知の粒度もタイミングも揃っていません。さらに、IPv4 と IPv6 のどちらで出ていくか、途中に IPv4 を IPv6 で運ぶ仕組み（DS-Lite や MAP-E、464XLAT）があるかで、移行の前後で経路の性質が大きく変わります。**QUIC の仕様が保証するのは「移行してもよい仕組み」までで、いつ、どの経路へ移るかを決めるのはアプリケーションの仕事**です。

## 使われている場所

HTTP/3 以外で QUIC を使う代表的なものを並べます。

| 用途 | 仕様 | 状態（2026 年 10 月） | QUIC の使い方 |
| --- | --- | --- | --- |
| DNS over QUIC（DoQ） | [RFC 9250](https://www.rfc-editor.org/rfc/rfc9250.html) | RFC | 問い合わせ 1 つにストリーム 1 本 |
| SMB over QUIC | [Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-over-quic) | 製品の機能 | ファイル共有を UDP 443 番で |
| MASQUE（CONNECT-UDP / CONNECT-IP） | [RFC 9298](https://www.rfc-editor.org/rfc/rfc9298.html) / [RFC 9484](https://www.rfc-editor.org/rfc/rfc9484.html) | RFC | HTTP/3 の上で UDP や IP を中継する。中身は DATAGRAM で運ぶ |
| WebTransport | [W3C](https://www.w3.org/TR/webtransport/) / [IETF ドラフト](https://datatracker.ietf.org/doc/draft-ietf-webtrans-http3/) | W3C は勧告候補、IETF はドラフト | ブラウザからストリームとデータグラムを使う |
| Media over QUIC（MoQT） | [IETF ドラフト](https://datatracker.ietf.org/doc/draft-ietf-moq-transport/) | ドラフト | 中継を挟む pub/sub。ストリームとデータグラムの両方 |

### DNS over QUIC

第 62 回で見たとおり、DoQ は UDP の 853 番を使い、ALPN は `doq` です。クライアントは**問い合わせごとに別のストリーム**を使い、各ストリームの中身は「1 つの問い合わせだけを扱う TCP 接続」と同じ形になります（[RFC 9250 4.2](https://www.rfc-editor.org/rfc/rfc9250.html#section-4.2)）。1 本の TCP 接続で複数の問い合わせを流すと、1 つのパケットの損失が無関係な応答まで止めますが、DoQ ではストリームが分かれているので止まりません。DATAGRAM は使っていません。

### SMB over QUIC

Windows のファイル共有（SMB）を、TCP の 445 番ではなく UDP の 443 番の QUIC で運びます。Microsoft は、TLS 1.3 で暗号化されたトンネルを作り、認証も含めた SMB の通信がその外に出ないことから、これを「SMB VPN」と呼んでいます。サーバは Windows Server 2022 Datacenter: Azure Edition と、Windows Server 2025 以降のすべてのエディション、クライアントは Windows 11 です。管理者が明示的に有効にする必要があり、Windows のクライアントは既定では**まず TCP を試し、失敗したときに QUIC を試します**（[Microsoft Learn](https://learn.microsoft.com/en-us/windows-server/storage/file-server/smb-over-quic)）。

### MASQUE: HTTP/3 の上で UDP と IP を中継する

HTTP には、プロキシに TCP のトンネルを張らせる `CONNECT` がありました。MASQUE は、これを **UDP と IP に広げたもの**です。

- **HTTP Datagrams**（[RFC 9297](https://www.rfc-editor.org/rfc/rfc9297.html)）: HTTP のリクエストに結び付いたデータグラム。HTTP/3 では QUIC の DATAGRAM フレームの先頭に **Quarter Stream ID**（リクエストのストリーム ID を 4 で割った値）を置いて、どのリクエストのものかを示す。DATAGRAM が使えない経路では、ストリームの中に Capsule という形で入れて送る
- **CONNECT-UDP**（[RFC 9298](https://www.rfc-editor.org/rfc/rfc9298.html)）: `connect-udp` という upgrade トークンで、`https://example.org/.well-known/masque/udp/{target_host}/{target_port}/` のような URI テンプレートを使って宛先を指定する。中継する UDP のペイロードは、Context ID 0 の HTTP Datagram に入れる
- **CONNECT-IP**（[RFC 9484](https://www.rfc-editor.org/rfc/rfc9484.html)）: `connect-ip` で IP パケットそのものを中継する。アドレスの割り当て（ADDRESS_ASSIGN）や経路の通知（ROUTE_ADVERTISEMENT）を Capsule で送るので、VPN として使える

中継する中身が QUIC なら、**QUIC の中に QUIC が入る**ことになります。RFC 9298 はこの場合、輻輳制御が 2 重に掛かることを指摘したうえで、外側の接続の輻輳制御を、内側が輻輳制御をしていると確実に分かる場合を除いて無効にしてはならないとしています。また、外側が TCP だと再送も 2 重になり、同じデータを両方が送り直すことがあるので、HTTP/3 の上で DATAGRAM を使って中継するよう勧めています（[RFC 9298 6](https://www.rfc-editor.org/rfc/rfc9298.html#section-6)）。中身を再送しない DATAGRAM が、トンネルに向いている理由です。

Apple の iCloud Private Relay は、利用者の通信を運営者の異なる 2 つの中継を通して、どちらか一方だけでは「誰が」と「どこへ」を結び付けられないようにしています（[Apple](https://developer.apple.com/support/prepare-your-network-for-icloud-private-relay/)）。Apple は WWDC23 で、MASQUE の中継を Private Relay の中核の技術と説明し、QUIC と HTTP/3 で多数の接続を 1 本のトンネルに多重化すること、QUIC が塞がれたネットワークでは HTTP/2 に戻ることを述べています（[WWDC23 "Ready, set, relay"](https://developer.apple.com/videos/play/wwdc2023/10002/)）。

### WebTransport

ブラウザの JavaScript から使える双方向の通信は、長く WebSocket（第 73 回）だけでした。WebSocket は TCP の上にあり、1 本のバイト列しか持てません。WebTransport は、HTTP/3 の接続の上に、**複数のストリームとデータグラム**を JavaScript から開けるようにする API です。データグラムは、先ほどの HTTP Datagrams で運ばれます。

API は W3C が、プロトコルは IETF の WebTrans WG が決めています。執筆時点で、W3C の仕様は 2026 年 7 月 30 日付けの勧告候補（Candidate Recommendation Snapshot）です（[W3C](https://www.w3.org/TR/webtransport/)）。IETF の WebTransport over HTTP/3 はまだ**ドラフト**で、最新は 2026 年 7 月の -16、WG の最終確認（WG Last Call）の段階です（[datatracker](https://datatracker.ietf.org/doc/draft-ietf-webtrans-http3/)）。ブラウザの対応は、MDN の互換性データで Chrome 97、Firefox 114、Safari 26.4 からとなっています（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport)）。

### Media over QUIC

Media over QUIC Transport（MoQT）は、映像や音声の配信を想定した **pub/sub のプロトコル**で、QUIC か WebTransport の上で動き、途中に中継（relay）を挟んで多数の受信者に配ります。名前に Media とありますが、中身の種類には依存しないと書かれています。データはストリームとデータグラムのどちらでも運べ、遅れたものを捨てる部分的な信頼性を前提にしています。執筆時点では **IETF のドラフト**で、最新は 2026 年 10 月 1 日の -22 です（[datatracker](https://datatracker.ietf.org/doc/draft-ietf-moq-transport/)）。前回の MQTT と同じく中継を挟む pub/sub ですが、TCP の上の 1 本の列ではなく、QUIC のストリームとデータグラムに載せる点が違います。

## 事例: ゲームの通信に QUIC を入れる

ゲームのリアルタイム通信は、これまで素の UDP の上に再送や順序の仕組みを自作したもの（いわゆる Reliable UDP）が主流でした。セガは CEDEC 2025 で、2 つの内製ライブラリに QUIC を導入した経験を発表しています（[CEDEC 2025「ゲームにおけるリアルタイム通信への QUIC 導入事例の紹介」](https://speakerdeck.com/segadevtech/cedec-2025-gemuniokeruriarutaimutong-xin-heno-quicdao-ru-shi-li-noshao-jie)）。以下は発表資料に書かれていることの要約です。

**対象。** 1 つは『Sonic Rumble』で、最大 32 人の対戦、Unity で作られ、PC とモバイル向けにグローバルに展開する、サーバとクライアント型のゲームです。通信には内製の Nemofiller（C#、netstandard2.1 準拠、Unity と .NET で動く）を使っています。もう 1 つは、約 20 年使われてきた内製のリアルタイム通信ライブラリ SPHINGO（C/C++、SCTP を元にした独自プロトコルを TCP か UDP の上で使う）です。どちらも QUIC の実装には Cloudflare の quiche（Rust）を使っています。Nemofiller では、quiche を呼ぶ部分を C++ で書き、C# と C++ の行き来を減らしています。

**採用の理由。** TCP には HOL ブロッキングがあり、IP アドレスが変わるとハンドシェイクからやり直しになります。素の UDP では、順序の保証や暗号化を足すなら自作で、標準のプロトコルが無く、多くの場合 TCP を併用して実装が複雑になります。SPHINGO の側には、接続移行を手軽に入れたいこと、独自プロトコルの維持の手間を減らすため標準のプロトコルを選択肢に加えたいことがありました。

この回で見た仕組みと、発表で報告された結果を並べます。

| この回で見たこと | 発表で報告されたこと |
| --- | --- |
| 信頼性の要るものはストリーム、遅れたら要らないものは DATAGRAM | Sonic Rumble は信頼性が必要な通信に STREAM、不要な通信に DATAGRAM を使った |
| DATAGRAM にも ACK が返り、線の上のパケットが増える | 切断と判定される接続が一定の割合で出た。通信量の割にパケットの数が多く、経路上の機器でパケットが捨てられていると推測し、DATAGRAM の部分を**暫定的に素の UDP に戻したところ切断の判定が減った**。DATAGRAM に戻すことを検討中 |
| ACK の間隔は受け取る側が決め、送る側から変えるには ACK Frequency（ドラフト）が要る | 「UDP と同じ感覚で投げるとパケット数が増える点は留意」。ACK の ON/OFF や頻度を制御する機能が欲しい。SPHINGO の互換機能では、信頼性の無い通信なのに ACK があることが冗長だった |
| 接続ができてしまえば、データを送るのに余分な往復は要らない | 128 バイトのメッセージで測った RTT は、QUIC と UDP が ping の値とほぼ同じで、TCP は大きく離れた |
| UDP が通らない環境では TCP に戻る | QUIC で接続できず TCP に切り替えた割合は平均 0.014%。TCP への切り替えは将来なくしてもよいかもしれない、という評価 |
| 移行は仕組みがあるだけで、いつ移るかはアプリケーションが決める | QUIC は「経路の切り替えに配慮のあるプロトコル（というだけ）」で、実装は想定していたものの結構面倒だった |
| 書き込みエラーへの反応は実装次第 | 切り替え先がすでにあるときの書き込みエラーの挙動が、Winsock 系と BSD ソケット由来の実装で違う |
| ネットワークの変化を知る手段は OS ごとに違う | 統一したインタフェースが無く、OS の通知を使える環境とポーリングが必要な環境がある |
| 移行の前後で経路の性質が変わる | Wi-Fi、キャリア回線、有線 LAN と、DS-Lite、MAP-E、464XLAT のような移行技術の組み合わせで試験が膨らむ。移行に時間がかかると送受信のバッファがあふれて切断に至る |

SPHINGO を採用したタイトルでは、1 日あたり 17561 接続のうち 331 件（約 1.9%）で接続移行が起きていました。100 クライアントが 30 秒ごとに接続と切断を繰り返す負荷試験では、CPU とメモリの使用量は既存の実装に近い値でした。

手元の実験で見た「ACK が逆向きに約半分の数だけ流れる」ことは、現場では経路上の機器でのパケットの取りこぼしとして現れ、いったん素の UDP に戻す判断につながっています。ACK を減らす拡張がまだドラフトであることも、ここで効いています。一方、HOL ブロッキングの回避、標準の暗号化、TCP への切り替えがほとんど要らないことは、期待どおりに働いています。

## どれを選ぶか

| 条件 | 向いているもの |
| --- | --- |
| 確実に届けばよく、往復の遅れも気にならない | TCP。ブラウザからなら WebSocket（第 73 回） |
| 遅れたら捨てるデータが中心で、暗号化も移行も要らない（閉じた網の中など） | 素の UDP |
| 確実に届けるものと捨ててよいものが混ざり、暗号化が要り、モバイルでアドレスが変わる | QUIC のストリームと DATAGRAM |
| 上と同じことをブラウザから | WebTransport |
| 端末同士を直接つなぎたい。音声や映像を扱いたい | WebRTC（第 76 回と第 77 回） |

QUIC を選ぶときは、次の 3 つを先に確かめておきます。

- **パケットの数**: DATAGRAM でも ACK が返る。小さなメッセージを高い頻度で送るなら、アプリケーションの側でまとめる、送る頻度を下げる、ACK Frequency に対応した実装を選ぶ、のどれかが要る
- **UDP が通らない場合**: TCP に戻る経路を残すか。残すなら、DATAGRAM で送っていたものを TCP の上でどう扱うかも決める
- **移行の担い手**: ネットワークの変化をどの OS の手段で知り、いつ新しい経路を試すか。書き込みエラーで実装が接続を閉じてしまわないか

WebRTC も、内部では信頼性のあるデータとないデータを 1 つの暗号化された関係の上で扱います。ただし、UDP の上に DTLS、SRTP、SCTP を組み合わせた別の積み方で、端末同士で直接つなぐことを前提にしています。QUIC との違いは第 77 回で比べます。

## まとめ

- QUIC を汎用のトランスポートとして使うと、信頼できるストリームと信頼性のない DATAGRAM が、1 つの暗号化された接続と 1 つの輻輳制御の下に同居する。素の UDP の自作や TCP との併用で別々に用意していたものが 1 つにまとまる
- DATAGRAM 拡張（RFC 9221）は再送しないが ack-eliciting で、輻輳制御も受ける。フロー制御は無く、1 パケットに収まらないものは送れない
- 手元の実験では、5% の損失で DATAGRAM は約 5% を失い遅延は素の UDP と同じ、ストリームはすべて届くが p90 が 60〜80ms に伸びた。DATAGRAM でも逆向きに約半分の数の ACK が流れ、線の上のパケットは素の UDP の約 1.5 倍になった
- ACK の頻度は受け取る側が決める。送る側から間隔を広げる ACK Frequency は、執筆時点でまだ IETF のドラフト。ACK を止めることはできない
- 接続移行には、クライアントが自分で移る場合と NAT の張り替えがある。どちらも経路検証の後に輻輳制御を初期値に戻すのが基本。いつ移るか、書き込みエラーをどう扱うかは実装とアプリケーションに任されていて、OS ごとの差がそこに出る
- HTTP/3 以外では、DoQ、SMB over QUIC、MASQUE（iCloud Private Relay など）、WebTransport、MoQT が QUIC を使っている。WebTransport と MoQT は、IETF の仕様がまだドラフト
- セガの事例では、HOL ブロッキングの回避と TCP への切り替えの少なさは期待どおりで、DATAGRAM のパケット数と ACK、接続移行の実装の手間が課題として報告された

QUIC の接続移行は、クライアントからサーバへの経路が変わっても続ける仕組みでした。では、サーバを持たずに、NAT の内側にいる端末同士を直接つなぐにはどうすればよいのでしょうか。次回は、NAT の振る舞いの分類から始めて、ホールパンチング、STUN、TURN、ICE を見ます。
