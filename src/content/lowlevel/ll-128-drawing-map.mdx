## 前の章では、絵を描いていたのはブラウザだった

第 17 章では、HTML と CSS が画面のピクセルになるまでを追いました。DOM からスタイルを決め、レイアウトで位置を決め、ペイントで描画命令の列（表示リスト）を作り、ラスタライズと合成で画面に出す（第 90・91 回）。この流れの中で、**何をどこに描くかを決めていたのは、すべてブラウザ**でした。開発者は「こういう文書です」と宣言するだけで、どの画素を何色にするかには関わりません。

この章では逆に、**開発者が自分で画素を作る**手段を見ます。グラフ、地図、ゲーム、デザインツール、動画編集。DOM の要素として並べるには数が多すぎるもの、あるいは CSS では表せない見た目のものです。

ブラウザには、そのための手段がいくつも用意されています。

- DOM と CSS（`transform`、アニメーション、View Transitions）
- SVG
- Canvas 2D と OffscreenCanvas
- WebGL
- WebGPU
- HTML-in-Canvas（DOM を canvas に描き込む、実験段階の提案）
- WebCodecs（動画のフレームを扱う）

ばらばらに見えるこれらを並べる軸は、1 つです。**描いている場面を、誰が覚えているか**。

## 保持モードと即時モード

グラフィックスの API は、昔から 2 つの型に分けて説明されます。Microsoft の Win32 の解説が簡潔なので引きます（[Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/learnwin32/retained-mode-versus-immediate-mode)）。

- **保持モード**（retained mode）の API は宣言的で、アプリケーションが図形を組み合わせて場面を作ると、**ライブラリがその場面のモデルをメモリに持ち続ける**。場面を変えたいときは、図形を足す・消すといった更新を伝えるだけで、描き直しはライブラリの責任になる
- **即時モード**（immediate mode）の API は手続き的で、アプリケーションが**フレームのたびに描画命令を直接出す**。ライブラリはフレームの間に場面を覚えておらず、場面を追うのはアプリケーションの側になる

同じ文書は、保持モードは仕事を肩代わりしてくれるぶん使いやすいが、自分の場面のモデルを押し付けるので柔軟さに欠け、汎用のモデルを持つぶんメモリを食う、即時モードなら目的に合わせた最適化ができる、と続けています。

ブラウザにあてはめると、きれいに 2 つに分かれます。

```
保持モード（ブラウザが場面を覚えている）       即時モード（自分が場面を覚えている）
┌──────────────────────────────┐        ┌──────────────────────────────┐
│ DOM / CSS                    │        │ Canvas 2D                    │
│ SVG                          │        │ WebGL                        │
│                              │        │ WebGPU                       │
│ 場面 = DOM の木               │        │ 場面 = 自分の配列や構造体       │
│ 変える = 属性やスタイルを書く   │        │ 変える = 全部描き直す           │
│ 描き直し = ブラウザが判断       │        │ 描き直し = 自分で判断           │
└──────────────────────────────┘        └──────────────────────────────┘
```

DOM の木は、ブラウザが持つ巨大なシーングラフです。`<circle>` の `cx` を書き換えると、ブラウザはその要素だけが変わったことを知っており、必要な段（第 120 回の style、layout、paint）だけをやり直します。

Canvas は違います。HTML Standard は `canvas` 要素を、スクリプトに**解像度に依存したビットマップのキャンバス**を与えるもの、と定義しています（[HTML Standard](https://html.spec.whatwg.org/multipage/canvas.html#the-canvas-element)）。`ctx.arc()` で円を描いた瞬間に、それは画素に溶けて消えます。ブラウザに残るのは「何色の画素が並んでいるか」だけで、「そこに円がある」という事実はどこにも残りません。円を動かしたければ、消して、別の場所に描き直すしかありません。

## パイプラインのどこにいるか

第 90・91 回のパイプラインの上に、それぞれの手段を置いてみます。

```
            JS ─ style ─ layout ─ paint ─ raster ─ 合成
DOM/CSS     ●     ●       ●        ●       ●       ●     要素ごとにブラウザが全段を回す
transform   ●                                      ●     合成だけで済む（第 121 回）
SVG         ●     ●       ●        ●       ●       ●     中身は DOM。要素が増えれば全段が重くなる
Canvas 2D   ●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●  →  ●     画素は自分で作る。ブラウザから見れば 1 つの画像
WebGL       ●（命令を積む）──── GPU が描く ──────  →  ●     画素を作るのは GPU。JS は命令と数値を渡すだけ
WebGPU      ●（命令を積む）──── GPU が描く ──────  →  ●     同上。計算だけに使うこともできる
```

ポイントは、**canvas 要素そのものはページの中で 1 つの箱**だということです。HTML Standard の分類では、`canvas` は画像や動画と同じ埋め込みコンテンツで、レイアウトから見ると決まった大きさの四角形にすぎません。中身がどれだけ複雑でも、ブラウザの style と layout が扱うのは「800×600 の箱が 1 つ」だけです。

その箱の中身の画素を、誰がどこで作るかが、Canvas 2D と WebGL・WebGPU の違いです。

- **Canvas 2D** は、JavaScript から「この円を塗れ」という命令を 1 つずつ出す。Chrome は 2D の命令も GPU で実行できますが（第 129 回で見ます）、命令を作る仕事はメインスレッドの JavaScript に残る
- **WebGL・WebGPU** は、頂点の座標の配列とシェーダ（GPU で動く小さなプログラム）を渡し、「これで 10 万個描け」と 1 回だけ頼める。画素ごと・頂点ごとの計算は GPU が並列にやる。第 12 回の SIMD を数千本並べた装置が GPU でした

どちらの場合も、実際に GPU のドライバに命令を出すのは**GPU プロセス**です（第 118 回）。レンダラの中の WebGL の呼び出しは、命令の列としてまとめられ、GPU プロセスに送られて実行されます。この「別プロセスに命令を送る」構造が、第 130 回の WebGL と第 131 回の WebGPU の設計の違いを理解する鍵になります。

<Callout type="note" title="CSS のアニメーションも View Transitions も保持モードの側">
  `transform` と `opacity` のアニメーションが軽いのは、ブラウザがレイヤという場面を覚えていて、重ね方だけを変えればよいからでした（第 121 回）。
  View Transitions も同じ発想です。MDN の説明では、`::view-transition-old()` は遷移前の**静止したスナップショット**、`::view-transition-new()` は遷移後の**生きた表示**で、
  それらが画面の上に重ねた疑似要素の木の中でアニメーションします（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API)）。
  JavaScript から同じ仕組みを操作する Web Animations API（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Web_Animations_API)）も含めて、
  どれも「ブラウザが場面を覚えている」ことを前提に、変化だけを伝える手段です。
</Callout>

## 即時モードで失うもの

即時モードは速さと自由を手に入れる代わりに、ブラウザが場面を覚えていたからこそできていたことを、すべて手放します。

| 機能 | DOM / SVG | Canvas / WebGL / WebGPU |
| --- | --- | --- |
| どこをクリックされたか（ヒットテスト） | ブラウザが要素を返す | 座標しか分からない。自分で判定する |
| 文字のレイアウト（折り返し、双方向、合字） | ブラウザがやる | `fillText` は 1 行を置くだけ。折り返しは自前 |
| スクリーンリーダー（アクセシビリティツリー） | 要素と文字が載る | 何も載らない。代わりの DOM を自分で用意する |
| ページ内検索、テキストの選択とコピー | できる | できない |
| フォーカスとキーボード操作 | ブラウザがやる | 自前 |
| 描き直しの判断 | ブラウザが変わった所だけ | 毎フレーム全部、または自分で差分を管理する |

HTML Standard 自身が、canvas の使いどころを強く制限しています。**より適した要素があるときに canvas を使ってはならない**とし、たとえばページの見出しを canvas で描くのは不適切だと書いています（[HTML Standard](https://html.spec.whatwg.org/multipage/canvas.html#the-canvas-element)）。canvas を使うなら、同じ機能を伝える代替の内容（canvas 要素の子要素）を用意しなければならず、操作できる領域にはその代替の内容の中のフォーカスできる要素を 1 対 1 で対応させるべきだ、とも定めています。

文字の入力欄はさらに深刻です。仕様は、**canvas で文字の編集を実装することは避けるべき**とし、再実装しなければならないものを列挙しています（[HTML Standard](https://html.spec.whatwg.org/multipage/canvas.html#best-practices)）。キャレットのマウスとキーボードでの移動、スクロール、コピーと貼り付け、スペルチェック、ドラッグ＆ドロップ、ページ全体の文字検索、双方向の文字の編集、すべての言語での行の折り返し、文字の選択、プラットフォームのショートカット、IME、元に戻すとやり直し、キャレットに追従する拡大表示。日本語を入力する人にとって、IME が動かない入力欄は使い物になりません。

<Callout type="warn" title="よくある誤解: 「canvas に描いた文字も、ブラウザは文字として扱っている」">
  `fillText` で描いた文字は、描いた瞬間に画素になります。ブラウザは、そこに「支払いへ進む」と書いてあることを知りません。
  ページ内検索にも、スクリーンリーダーにも、翻訳機能にも見えません。下の実験で確かめます。
  この問題を正面から解こうとしているのが、DOM をレイアウトさせたまま canvas に描き込む HTML-in-Canvas の提案です（第 132 回）。
</Callout>

## それでも canvas に描く理由

失うものがこれだけあっても、大きなアプリケーションはあえて canvas 側に移ってきました。

- **Figma** は、HTML と SVG は余計な荷物が多く、DOM へのアクセスのせいで 2D canvas の API よりずっと遅いことが多いとして、描画をすべて WebGL で一から実装しました。エディタ本体は C++ で書き、emscripten で JavaScript（asm.js）にコンパイルしています（[Figma のブログ](https://www.figma.com/blog/building-a-professional-design-tool-on-the-web/)）。いまなら Wasm（第 204 回）の役割です
- **Google ドキュメント**は 2021 年に、HTML による描画から canvas による描画へ実装を移すと告知しました。理由は、性能と、プラットフォームの違いによる見え方のずれを減らすことでした（[Google Workspace Updates](https://workspaceupdates.googleblog.com/2021/05/Google-Docs-Canvas-Based-Rendering-Update.html)）
- **Skia** は Chrome、Android、Flutter などの描画エンジンになっている 2D グラフィックスのライブラリです（[Skia](https://skia.org/)）。この Skia を Wasm にコンパイルした CanvasKit も公開されていて、WebGL のコンテキストを Skia の描画先として HTML の canvas に直接描けます（[Skia: CanvasKit](https://skia.org/docs/user/modules/canvaskit/)）。ブラウザの中に、もう 1 つ描画エンジンを持ち込む形です

共通しているのは、**場面の数が多く、見た目をすべて自分で決めたい**ことです。そして、失ったもの（文字の入力、アクセシビリティ）は、canvas の上に透明な DOM を重ねるなどして、自分で補っています。

ライブラリの行に注目してください。[Three.js](https://threejs.org/) や [PixiJS](https://pixijs.com/) は、即時モードの WebGL の上に、**シーングラフという保持モードをもう一度作り直す**ものです。シーンにメッシュやスプライトを足し、位置を変えると、ライブラリが毎フレーム全部を描き直します。保持モードを捨てたのは、ブラウザ汎用の場面のモデルが重かったからで、場面そのものが要らなかったわけではありません。**自分の用途に合った軽い場面を、自分の側に持ち直す**のです。

## 確かめる: 同じ粒子を 3 つの方式で動かす

同じ数の点（半径 2px の円）を毎フレーム動かし、SVG、Canvas 2D、WebGL で描きます。環境は Apple M1 Pro の Mac、Playwright から起動したヘッドレスの Chrome 155 です。WebGL は ANGLE の Metal バックエンドで動いていました（`WEBGL_debug_renderer_info` で `ANGLE Metal Renderer: Apple M1 Pro`）。

粒子の位置と速度は 3 方式で共通の `Float32Array` に持ち、描く部分だけを差し替えます。

```js
// 共通: 位置を進めて、壁で跳ね返す
function update() {
  for (let i = 0; i < N; i++) {
    x[i] += vx[i]; y[i] += vy[i]
    if (x[i] < 0 || x[i] > W) vx[i] = -vx[i]
    if (y[i] < 0 || y[i] > H) vy[i] = -vy[i]
  }
}

// SVG: 要素を N 個作っておき、属性を書き換える（場面はブラウザが持つ）
render = () => { for (let i = 0; i < N; i++) { cs[i].setAttribute('cx', x[i]); cs[i].setAttribute('cy', y[i]) } }

// Canvas 2D: 消して、1 本のパスに N 個の円を足して塗る（場面は配列だけ）
render = () => {
  ctx.clearRect(0, 0, W, H); ctx.beginPath()
  for (let i = 0; i < N; i++) { ctx.moveTo(x[i] + R, y[i]); ctx.arc(x[i], y[i], R, 0, Math.PI * 2) }
  ctx.fill()
}

// WebGL: 座標を 1 本のバッファに詰めて GPU に送り、1 回の drawArrays(POINTS) で描く
render = () => {
  for (let i = 0; i < N; i++) { xy[i * 2] = x[i]; xy[i * 2 + 1] = y[i] }
  gl.bufferSubData(gl.ARRAY_BUFFER, 0, xy)
  gl.clear(gl.COLOR_BUFFER_BIT); gl.drawArrays(gl.POINTS, 0, N)
}
```

WebGL の側の円は、頂点シェーダで点の大きさを決め、フラグメントシェーダで中心からの距離が半径を超える画素を捨てて作っています（第 130 回で詳しく見ます）。

`requestAnimationFrame` の中で `update()` と `render()` にかかった時間（JS の時間）と、コールバックの呼ばれる間隔（フレームの間隔）を 120 フレーム測り、最初の 10 フレームを捨てた中央値を出しました。60Hz なら間隔は 16.7ms が上限で、それより長ければフレームを落としています。

```
方式      点の数      JS の時間（中央値）   フレームの間隔（中央値）   p95
svg        1,000          1.3ms              16.7ms                 16.8ms
svg        3,000          3.2ms              16.7ms                 16.8ms
svg       10,000         10.8〜11.1ms         16.7〜33.3ms            66.6〜83.2ms
svg      100,000        128.7ms             266.7ms                400.0ms
canvas     1,000          0.2ms              16.7ms                 16.7ms
canvas    10,000          1.5ms              16.7ms                 16.7ms
canvas   100,000         15.6ms              16.7ms                 16.8ms
canvas   300,000         46.6ms              50.0ms                 50.1ms
canvas 1,000,000        152.0ms             150.0ms                183.3ms
webgl      1,000          0.0ms              16.7ms                 16.7ms
webgl    100,000          0.6ms              16.7ms                 16.7ms
webgl    300,000          1.6ms              16.7ms                 16.7ms
webgl  1,000,000          5.1ms              16.7ms                 16.7ms
```

SVG の 1 万個は、何度か測ると中央値が 16.7ms の回と 33.3ms の回があり、ちょうど締め切りの境目でした。

崩れ方が 3 者 3 様です。

- **SVG は 1 万個あたりで崩れ始める**。しかも JS の時間（11ms）よりフレームの間隔（33ms）がずっと長い。JavaScript の後に、ブラウザの仕事が残っている
- **Canvas 2D は 10 万個で締め切りぎりぎり**、30 万個で 1 秒 20 フレームに落ちる。JS の時間とフレームの間隔がほぼ等しい。重さのほとんどが JavaScript で命令を出す部分にある
- **WebGL は 100 万個でもフレームを落とさない**。JS の 5.1ms は、ほぼ座標を詰め直すループの時間で、描画そのものは GPU が担っている

### 時間はどこに消えたのか

SVG の「JS の後に残っている仕事」を、Long Animation Frames API で分けます。この API は、描画の更新が 50ms より遅れたフレーム（長いアニメーションフレーム）について、`renderStart`（`requestAnimationFrame` のコールバックを含むレンダリングの開始）と、`styleAndLayoutStart`（style と layout の計算の開始）の時刻を記録します（[Chrome for Developers](https://developer.chrome.com/docs/web-platform/long-animation-frames)）。`styleAndLayoutStart` からフレームの終わりまでを「style と layout 以降」として取り出しました。

```
方式      点の数     フレーム全体   style と layout 以降   （JS の時間）
svg       30,000      58.4ms         25.8ms              32.7ms
svg      100,000     216.6ms         88.1ms             127.4ms
canvas   300,000      51.5ms          0.1ms              46.9ms
```

SVG では、`setAttribute` を呼ぶ JavaScript の時間に加えて、**ブラウザが 3 万個の要素の style と layout をやり直す時間**が 4 割ほど乗っています。保持モードの代償です。ブラウザは要素ごとに、変わったかどうか、どの段からやり直すかを管理しています。それが便利さの源で、同時に要素の数に比例する重さでもあります。

Canvas 2D の 30 万個では、style と layout は 0.1ms でした。ブラウザから見れば、800×600 の箱が 1 つあるだけだからです。そのかわり、30 万回の `arc()` を呼ぶ JavaScript がまるごと残ります。

要素の数も見ておきます。SVG で 10 万個を描いたページは `document.getElementsByTagName('*')` が 100,008 個、canvas と WebGL のページは 8 個でした。

<Callout type="tip" title="この数字の読み方">
  これはヘッドレスの Chrome の、点の描画という最も単純な場面での目安です。
  `requestAnimationFrame` は vsync に揃うので（第 121 回）、間隔は 16.7ms の倍数に張り付きます。
  WebGL の JS の時間は「命令を積んだ時間」であって、GPU が描き終えた時間ではありません。GPU の側が詰まれば、フレームの間隔に表れます。
  場面が変われば崩れる場所も変わります。自分の場面で、自分の端末で測ってください（第 233 回）。
</Callout>

## 確かめる: canvas に描いた文字はどこにもない

もう 1 つ、即時モードで失うものを確かめます。同じページに、SVG のボタン（`<rect>` と `<text>` で「注文を確定する」）と、canvas に `fillRect` と `fillText` で描いたボタン（「支払いへ進む」）を並べました。

```js
const hit = (x, y) => { const e = document.elementFromPoint(x, y); return e.id || e.tagName }
window.__result = {
  svgHit: hit(50, 20), canvasHit: hit(50, 120),          // その座標に何があるか
  findSvg: window.find('注文を確定する'),                  // ページ内検索
  findCanvas: window.find('支払いへ進む'),
  textContent: document.body.innerText.replace(/\s+/g, ' ').trim(),
}
```

結果です。アクセシビリティツリーは、Chrome DevTools Protocol の `Accessibility.getFullAXTree` で取りました。

```
ヒットテスト        SVG: text            canvas: c（canvas 要素そのもの）
ページ内検索        SVG: true            canvas: false
innerText          "注文を確定する"（canvas の文字は含まれない）
アクセシビリティ     RootWebArea | SvgRoot | Canvas | StaticText:注文を確定する | InlineTextBox:注文を確定する
```

SVG の文字は、どこを押されたか、検索、アクセシビリティツリーのすべてに現れました。canvas の「支払いへ進む」は、どこにも現れません。アクセシビリティツリーには `Canvas` という空の箱が 1 つあるだけです。スクリーンリーダーの利用者には、このボタンは存在しません。

## どれを選ぶか

ここまでを、選ぶときの問いに直します。

```
文字の入力やアクセシビリティが中心か？
├─ はい → DOM と CSS。動きは transform / opacity と View Transitions で
└─ いいえ（または補える）
    │
    ├─ 要素は数千まで、1 つずつにイベントを付けたい → SVG
    ├─ 数万〜十万、毎フレーム全部が動く → Canvas 2D（重ければ OffscreenCanvas で Worker へ）
    ├─ 十万以上、または 3D、シェーダの効果 → WebGL（対応の広さ）/ WebGPU（新しい機能）
    └─ GPU で計算したい（物理、画像処理、推論） → WebGPU のコンピュートシェーダ

canvas の中に、ちゃんとした文字や入力欄を置きたい → HTML-in-Canvas（実験段階）
動画のフレームを加工したい → WebCodecs と、上のどれか
```

実際には 1 つに決める必要はありません。地図のアプリなら、地図本体は WebGL、地名のラベルとボタンは DOM、というように**層ごとに使い分けて重ねる**のが普通です。canvas も 1 つの要素なので、DOM の上にも下にも置けます。合成の段（第 121 回）が、それらを 1 枚の画面にまとめます。

<Callout type="note" title="なぜ選択肢がこれほど多いのか">
  WebGL は OpenGL ES を、WebGPU は Vulkan・Metal・Direct3D 12 の世代の GPU を、それぞれウェブに持ち込んだものです。
  MDN は、WebGPU を WebGL の後継と位置付け、OpenGL（したがって WebGL）には今後の更新が予定されていない、と書いています（[MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API)）。
  手段の数は、その時代ごとの GPU の形を写してきた結果です。古い手段が消えないのは、ウェブが後方互換を守るからです。
</Callout>

## まとめ

- ブラウザで描く手段を分ける軸は、**場面を誰が覚えているか**。DOM・CSS・SVG はブラウザが覚える**保持モード**、Canvas 2D・WebGL・WebGPU は自分が覚える**即時モード**
- canvas 要素は、レイアウトから見れば 1 つの箱。中身の画素は自分で作る。Canvas 2D は JavaScript が命令を 1 つずつ出し、WebGL・WebGPU は配列とシェーダを渡して GPU に一括で描かせる
- 即時モードは、ヒットテスト、文字のレイアウト、アクセシビリティ、ページ内検索、選択、IME を失う。HTML Standard は、より適した要素があるなら canvas を使わず、文字の編集を canvas で作らないよう求めている
- Figma や Google ドキュメントは、それでも性能と見え方の一貫性のために canvas へ移った。Three.js や PixiJS は、WebGL の上に自分用の軽い保持モードを作り直す
- 手元の Chrome 155（M1 Pro、ヘッドレス）では、毎フレーム動く点は、SVG が 1 万個前後、Canvas 2D が 10 万個前後で 16.7ms を超え、WebGL は 100 万個でも落ちなかった
- SVG は JavaScript に加えて style と layout の時間が乗り、Canvas 2D はほぼ JavaScript だけが重い。重さがどこにあるかが違う
- canvas に描いた文字は、ヒットテストにも検索にもアクセシビリティツリーにも現れない
- 実際のアプリは、層ごとに手段を使い分けて重ね、合成で 1 枚にする

次の回では、即時モードのいちばん手前にある Canvas 2D を見ます。ビットマップの大きさと表示の大きさの違い、`devicePixelRatio` でぼやける理由、状態のスタック、`getImageData` で画素を読み出すと何が起きるのか、そして描画をメインスレッドから Worker へ移す OffscreenCanvas です。
