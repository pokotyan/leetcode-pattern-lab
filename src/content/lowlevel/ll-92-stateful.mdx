## Pod は家畜として扱われる

ここまでの回で見てきた仕組みは、すべて 1 つの前提に立っています。**Pod はいつ消えてもよい**、という前提です。

- ノードが落ちれば、Pod は別のノードに作り直される（第 86 回の調整ループ）
- 更新のたびに、古い Pod は消され、新しい Pod が作られる（第 91 回）
- 資源が足りなければ、優先度の低い Pod は追い出される（第 88 回）

作り直された Pod は、**名前も IP アドレスも違う別物**です。そして第 77 回で見たとおり、コンテナの中に書いたファイルは書き込み層にあり、コンテナと一緒に消えます。

この扱いは「ペットではなく家畜」と表現されます。1 匹ずつ名前を付けて世話をするのではなく、群れとして数だけを管理する。**区別する必要がないから、壊れたら取り替えればよい。**

これが成り立つのは、Pod が**状態を持たない**ときだけです。

| | 状態を持たない（ステートレス） | 状態を持つ（ステートフル） |
| --- | --- | --- |
| 例 | Web サーバ、API サーバ | データベース、メッセージキュー |
| 消えたら | 別の Pod が同じ仕事をする | **データが失われる** |
| 増やすには | 数を変えるだけ | データの分け方と複製を考える必要がある |
| どの Pod に届いてもよいか | よい | よくない（主はどれか、どのデータを持つか） |

## 状態を外に追い出す

最も簡単な解決は、**状態を Pod の外に置く**ことです。

アプリケーションのサーバは状態を持たず、セッションはキャッシュのサーバに、データはデータベースに置く。アプリケーションの Pod は何台でも増減でき、消えても何も失いません。多くのシステムはこの形を取ります。

しかし、これは問題を移しただけです。**状態を引き受けたデータベースは、どこかで動いていなければなりません。** それもクラスタに載せるなら、「消えてもよい」という前提と正面からぶつかります。

## ボリューム: 消えないディスクを後から付ける

コンテナの外にデータを置く仕組みが**ボリューム**です。第 81 回で見た Docker のボリュームと同じく、コンテナのファイルシステムの一部に、別の記憶領域をマウントします。

Kubernetes では、この記憶領域を 2 つの物に分けて扱います（[Kubernetes](https://kubernetes.io/docs/concepts/storage/persistent-volumes/)）。

| 物 | 意味 | 誰が用意するか |
| --- | --- | --- |
| **PersistentVolume**（PV） | 実在する記憶領域。クラウドのディスク、NFS のパスなど | 管理者、または自動 |
| **PersistentVolumeClaim**（PVC） | 「10GB、読み書きできるもの」という要求 | アプリケーションの利用者 |

公式の文書は、この関係を Pod とノードにたとえています。**Pod がノードの資源を消費するように、PVC は PV の資源を消費する。**

```
 アプリの Pod ──使う──→ PVC「10GB ください」
                          │ 結び付ける
                          ↓
                         PV（実在するディスク）
                          │
                          ↓
                 クラウドのブロックストレージ
```

なぜ 1 段挟むのか。**アプリケーションの定義に、インフラの詳細を書かせないため**です。

アプリケーションの利用者は「どれだけ、どういう使い方で」だけを書きます。それがどのクラウドのどの種類のディスクなのかは知りません。同じ定義を別のクラスタに持っていけば、そこにあるディスクと結び付きます。第 31 回の ABI や第 41 回のシステムコールと同じく、**約束の面を 1 つ決めて、両側を独立させる**という発想です。

### 要求されてから作る

事前に PV を並べておくのは手間です。そこで、PVC が来たら**その場で PV を作る**ことができます。これが**動的プロビジョニング**です。

どういうディスクを作るかは **StorageClass** に書いておきます。「SSD で、ゾーンをまたいで複製するもの」といった品目の定義です。PVC は品目の名前を指定し、それに合う PV が自動的に作られて結び付けられます。

### 使い方の制約

ディスクには、**同時に何か所から使えるか**という物理的な制約があります。これを**アクセスモード**として宣言します。

| モード | 意味 |
| --- | --- |
| ReadWriteOnce | 1 つのノードから読み書きできる |
| ReadOnlyMany | 複数のノードから読み取りだけできる |
| ReadWriteMany | 複数のノードから読み書きできる |
| ReadWriteOncePod | 1 つの Pod からだけ読み書きできる |

クラウドのブロックストレージの多くは ReadWriteOnce です。1 台のマシンにしか接続できない、SSD を 1 台のマシンに挿すのと同じ性質だからです。

<Callout type="warn" title="複数から書けるディスクは、書く側が気をつける必要がある">
  ReadWriteMany のネットワークファイルシステムに、複数の Pod が同じファイルを書けば、
  第 37 回で見た競合がネットワーク越しに起きます。
  さらに、第 50 回で見た `fsync` の保証が、ネットワークファイルシステムでは弱まることがあります。
  **「複数から書ける」はファイルシステムが調停してくれるという意味ではありません。**
</Callout>

## CSI: ストレージの差し込み口

ディスクの作り方、ノードへの接続のしかた、マウントのしかたは、ストレージの種類ごとに違います。以前はこれらのドライバが Kubernetes の本体のコードに含まれていて、新しいストレージに対応するには本体を変える必要がありました。

そこで、ストレージとの間の約束を外に切り出したのが **CSI**（Container Storage Interface）です（[CSI spec](https://github.com/container-storage-interface/spec)）。ボリュームを作る、ノードに付ける、マウントする、といった操作を gRPC のインタフェースとして定め、各ストレージの業者はそのインタフェースを実装したドライバを配ります。

第 78 回で見た CRI（コンテナの実行）と、第 89 回で見た CNI（ネットワーク）と並んで、**Kubernetes は外部の実装と「インタフェースの約束」で繋がる**という形を一貫して取っています。

## StatefulSet: 取り替えのきかない Pod

ボリュームで「データを残す」ことはできました。しかし、データベースのクラスタにはそれだけでは足りません。

3 台で複製を組むデータベースを考えます。

- 3 台はそれぞれ**自分のディスク**を持つ。共有ではない
- 互いに**名前で**呼び合って複製する。「1 号機は主、2 号機と 3 号機は従」
- 起動には**順序**がある。主が立ち上がってから従が参加する

普通の Pod の集まり（Deployment）は、これを満たせません。Pod の名前はランダムに生成され、作り直すたびに変わります。どの Pod がどのディスクを使うかも決まっていません。

**StatefulSet** は、これを保証するための仕組みです（[Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/)）。

| 保証 | 中身 |
| --- | --- |
| 安定した名前 | Pod に 0 から順の番号が付く。`db-0`、`db-1`、`db-2`。作り直しても同じ名前 |
| 安定したディスク | 番号ごとに PVC が作られる。`db-1` は作り直されても、必ず `db-1` のディスクに付く |
| 順序 | 0 から順に起動し、逆順に停止する。前の番号が準備完了になるまで次を作らない |

名前で呼び合うには、**headless Service** を使います。第 89 回で見た Service は、仮想 IP を 1 つ持って後ろの Pod に振り分けるものでした。headless Service は仮想 IP を持たず、DNS で Pod を 1 台ずつ引けるようにします。

```
db-0.db.default.svc.cluster.local   →  1 号機の IP
db-1.db.default.svc.cluster.local   →  2 号機の IP
```

IP アドレスは作り直すたびに変わりますが、**名前は変わりません**。複製の設定には、この名前を書きます。

<Callout type="note" title="消しても、ディスクは消えない">
  StatefulSet を削除したり、台数を減らしたりしても、**ボリュームは自動では削除されません**。
  公式の文書は、データの安全のほうが、関連する資源を自動で片付けることより価値が高いから、
  と説明しています。
  「Pod は家畜」の世界で、ディスクだけはペットとして扱われている、ということです。
</Callout>

## それでも、データベースは難しい

StatefulSet は名前とディスクと順序を与えます。しかし、**データベースの正しさまでは面倒を見ません**。

Kubernetes が知っているのは「Pod が動いているか」「準備完了か」だけです。データベースの中で何が起きているかは知りません。

**主が落ちたとき。** Kubernetes は `db-0` を作り直します。しかし、その間に従を主に昇格させるべきか、作り直した `db-0` を主に戻すべきか、そのとき複製が追いついていないデータをどう扱うか。**これはデータベースの知識がないと判断できません。** 第 59 回で見たように、NewSQL は Raft を内蔵してこれを自分で解いています。そうでないデータベースでは、誰かが判断しなければなりません。

**2 台が同時に主になったとき。** ノードがネットワークから切り離されると、Kubernetes はそのノードの Pod が死んだのか、生きているが通信できないだけなのかを区別できません。代わりの Pod を作った瞬間、**古い主と新しい主が同時に書き込む**可能性があります。StatefulSet が「同じ名前の Pod はクラスタ全体で同時に 1 台まで」を保証し、到達できなくなったノードの Pod を自動では消さないのは、このためです。消すのはノードが復帰したとき、ノード自体が削除されたとき、または人が強制的に消したときだけで、強制削除はこの保証を破りうると明記されています（[Kubernetes](https://kubernetes.io/docs/tasks/run-application/force-delete-stateful-set-pod/)）。<a href={`${import.meta.env.BASE_URL}reading/consensus/`}>分散合意</a>で見た問題が、ここにそのまま現れます。

**ディスクの性能。** ネットワーク越しのブロックストレージは、1 回の書き込みにネットワークの往復がかかります。第 58 回で見た WAL の `fsync` は、コミットのたびにこの往復を待ちます。

**バックアップ、バージョンアップ、容量の拡張。** どれもデータベースごとに手順が違い、順序を間違えるとデータを失います。

<Callout type="tip" title="ここを自動化するのが次の回">
  「主が落ちたら、どの従を昇格させるか」「バージョンを上げるときは、従から 1 台ずつ」。
  こうした**人間の運用手順を、調整ループとして書く**のが Operator です。
  StatefulSet が与える土台の上に、データベース固有の知識を載せる形になります。
</Callout>

## 選び方

| 状況 | 向く選択 |
| --- | --- |
| アプリケーションのサーバ | 状態を持たせない。Deployment |
| 状態は必要だが、運用の手間を減らしたい | クラウドのマネージドなデータベースを外に置く |
| クラスタの中で動かしたい | StatefulSet と、そのデータベース用の Operator |
| そもそも分散を前提に作られたデータベース | 第 59 回の NewSQL のように、自分で合意を取るもの |

状態を持つものをクラスタに載せられるかどうかは、Kubernetes の機能よりも、**そのソフトウェア自身が、ノードの喪失と作り直しを前提に作られているか**で決まります。

## まとめ

- Kubernetes の多くの仕組みは「Pod はいつ消えてもよい」を前提にしている
- 最も簡単な解決は、状態を Pod の外に追い出すこと。ただし引き受けた側はどこかで動く必要がある
- PV は実在する記憶領域、PVC はその要求。1 段挟むことで、アプリの定義からインフラの詳細を外す
- StorageClass で品目を定義し、要求に応じて作る。アクセスモードは物理的な制約の宣言
- CSI は CRI、CNI と並ぶ差し込み口。外部の実装とインタフェースで繋がる
- StatefulSet は安定した名前、番号ごとのディスク、起動の順序を保証する
- ただし、データベースの正しさ（昇格、二重の主、複製の遅れ）までは面倒を見ない

次は、この「データベースの正しさ」のような固有の知識を、自分でコントローラとして書いて Kubernetes に教える方法、Operator を見ます。
