## 暗号化すれば、それで済むのか

第 93 回で、暗号が約束しうる性質を機密性・完全性・真正性・否認防止の 4 つに分けました。第 94 回のハッシュと MAC は、そのうち**完全性と真正性**を受け持つ部品でした。この回は残る**機密性**、つまり「中身を読まれない」ことを受け持つ部品を見ます。

送る側と受け取る側が**同じ鍵**を持っているとき、その鍵で中身を隠す方式を**共通鍵暗号**（対称鍵暗号）と呼びます。通信でも保存でも、大量のデータを実際に暗号化しているのはほぼすべてこれです。第 96 回で見る公開鍵暗号は、この共通鍵を 2 人の間で用意するために使われます。

ここで最初に問いを立てておきます。**暗号化したデータは、途中で書き換えられないのでしょうか。** 読めないものは、狙って書き換えることもできない、と考えたくなります。この回の中ほどで、それが成り立たないことを手元で確かめます。

## 2 つの作り方: ブロック暗号とストリーム暗号

共通鍵暗号の部品には、大きく 2 つの作り方があります。

| 種類 | 何をするか | 代表 |
| --- | --- | --- |
| **ブロック暗号** | 決まった長さのブロックを、鍵で決まる別のブロックに置き換える | AES |
| **ストリーム暗号** | 鍵から、平文と同じ長さの乱数のような列（**鍵ストリーム**）を作り、平文と XOR する | ChaCha20 |

**AES** は 2001 年に [FIPS 197](https://csrc.nist.gov/pubs/fips/197/final) として定められたブロック暗号です（2023 年に編集上の改訂）。ブロックの長さは **128 ビット（16 バイト）** で固定、鍵の長さは 128・192・256 ビットの 3 種類があり、それぞれ AES-128・AES-192・AES-256 と呼びます。中では、バイトの置き換え・並べ替え・混ぜ合わせ・鍵との XOR を 1 ラウンドとして、鍵の長さに応じて 10・12・14 ラウンド繰り返します。

```
鍵 K（16 / 24 / 32 バイト）
          │
          ↓
  16 バイト ──→ [ AES_K ] ──→ 16 バイト        鍵ごとに決まる、16 バイトの置き換え表
  （平文）                     （暗号文）      同じ鍵なら、同じ入力は必ず同じ出力
```

大事なのは、**AES そのものは「16 バイトを 16 バイトに置き換える」ことしかしない**という点です。17 バイト以上のデータをどう分けて AES に通すか、は AES の外で決める必要があります。これが後で見る**利用モード**です。

**ChaCha20** は [RFC 8439](https://www.rfc-editor.org/rfc/rfc8439.html) で定められたストリーム暗号です。256 ビットの鍵、96 ビットの **nonce**（1 回だけ使う値）、32 ビットのカウンタから、1 回に 64 バイトずつ鍵ストリームを作ります（[2.3〜2.4 節](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.3)）。足し算・ビット回転・XOR だけでできているので、専用の命令がない CPU でも速く、処理時間がデータに依存しにくいのが特徴です。

```
(鍵, nonce, カウンタ) ──→ [ ChaCha20 ] ──→ 鍵ストリーム  k1 k2 k3 k4 ...
                                                  XOR
                                      平文        p1 p2 p3 p4 ...
                                                   ＝
                                      暗号文      c1 c2 c3 c4 ...
```

## ブロック暗号をどう並べるか: 利用モード

長いデータを AES で暗号化する並べ方を**利用モード**と呼びます。代表的なものは NIST の [SP 800-38A](https://csrc.nist.gov/pubs/sp/800/38/a/final) にまとまっています。

### ECB: 素直に 16 バイトずつ

最も素直なのは、16 バイトずつ区切って、それぞれを独立に AES に通す方法です。これを **ECB**（Electronic Codebook）と呼びます。しかし前の図のとおり、**同じ鍵なら同じ入力は同じ出力**になります。手元で、同じ 16 バイトを 2 回含む平文を ECB で暗号化しました（Python の cryptography 48、手元の実行結果）。

```
b'ATTACK AT DAWN!!' b7f65944fc5ceb48d521a37d50067810
b'ATTACK AT DAWN!!' b7f65944fc5ceb48d521a37d50067810   ← 1 行目とまったく同じ
b'ATTACK AT DUSK!!' 64838e00af3d52ecf04a5cac1a3826a2
```

中身は読めなくても、**「1 ブロック目と 2 ブロック目は同じ」ことは漏れています**。画像のように同じ色が広い範囲で続くデータでは、この漏れが目に見えます。Linux のマスコットのペンギンの画像を ECB で暗号化すると、色はでたらめになるのに**輪郭がそのまま残る**という例がよく知られています（[Wikipedia: Block cipher mode of operation](https://en.wikipedia.org/wiki/Block_cipher_mode_of_operation)）。

<Callout type="warn" title="よくある誤解: AES-256 を使っているから安全">
  暗号の強さを鍵の長さで語る説明は多いのですが、**ECB で使えば AES-256 でもパターンは漏れます**。
  鍵が 128 ビットでも 256 ビットでも、同じブロックが同じ暗号文になる性質は変わりません。
  第 93 回で見た「自分で暗号を組むな」の中身の 1 つがこれで、
  **壊れるのはアルゴリズムではなく、その使い方（モード、nonce、組み合わせ）**であることがほとんどです。
  ライブラリの API で `mode=ECB` を既定にしているものもあるので、既定値を確かめずに使わないことです。
</Callout>

### CBC: 前のブロックを混ぜる

**CBC**（Cipher Block Chaining）は、平文のブロックを AES に通す前に、**1 つ前の暗号文ブロックと XOR** します。最初のブロックには前がないので、代わりに **IV**（初期化ベクトル、16 バイト）を使います。

```
        IV          C1          C2
         │           │           │
  P1 ──→ XOR   P2 ──→ XOR   P3 ──→ XOR
         ↓           ↓           ↓
       AES_K       AES_K       AES_K
         ↓           ↓           ↓
         C1          C2          C3
```

同じ平文を CBC で暗号化すると、1 ブロック目と 2 ブロック目の暗号文は別物になりました。

```
b'ATTACK AT DAWN!!' 08d4d7a834e16f7c24cf5e0986ca5569
b'ATTACK AT DAWN!!' 7f5e1b4aaceca462dedb0957d6985cc9   ← もう同じにならない
b'ATTACK AT DUSK!!' 09af272cf86d6e5d4d5aff1c812ef561
```

IV は暗号文と一緒に送ってよい値で、秘密にする必要はありません。ただし CBC では、**暗号化のたびに予測できない値**でなければなりません（SP 800-38A の付録 C）。固定の IV では、同じ平文の先頭が同じ暗号文になり、ECB と同じ漏れ方をします。

CBC にはもう 1 つ、**平文の長さを 16 バイトの倍数に揃える必要がある**という制約があります。そのための詰め物が**パディング**です。よく使われる PKCS#7 の方式では、足りないバイト数 n の値を n 個並べます。5 バイトの `hello` は、`0b`（11）を 11 個足して 16 バイトになります。

```
68 65 6c 6c 6f 0b 0b 0b 0b 0b 0b 0b 0b 0b 0b 0b
 h  e  l  l  o  └──────── 11 が 11 個 ────────┘
```

復号する側は、最後のバイトを見て、その数だけ詰め物があるかを確かめてから取り除きます。この「確かめる」が、次の攻撃の入口になります。

### CTR: AES で鍵ストリームを作る

**CTR**（Counter）モードは、AES をストリーム暗号として使います。nonce とカウンタを並べた 16 バイトを AES に通し、出てきた 16 バイトを鍵ストリームとして平文と XOR します。

```
  nonce‖0     nonce‖1     nonce‖2
     ↓           ↓           ↓
   AES_K       AES_K       AES_K
     ↓           ↓           ↓
    K0          K1          K2        ← 鍵ストリーム
     ⊕           ⊕           ⊕
    P0          P1          P2
     ↓           ↓           ↓
    C0          C1          C2
```

パディングが要らず（最後は必要な長さだけ XOR する）、各ブロックが独立なので**並列に計算でき**、復号にも AES の暗号化の向きしか使いません。現在よく使われるモードは、ほぼこの CTR が土台です。

## パディングの確認が、秘密を漏らす

CBC の復号では、1 つ前の暗号文ブロックを XOR して平文を取り出します。つまり、**前の暗号文ブロックの 1 ビットを反転させると、次の平文ブロックの同じ位置の 1 ビットが反転します**。

攻撃者は、この性質を使って暗号文を少しずつ書き換えて送りつけ、受け取った側が「パディングが正しい」と判断したか「正しくない」と判断したかを観察します。応答のエラーの種類、あるいは処理時間の差で、その 1 ビットの情報が漏れるなら、**鍵を知らないまま平文を 1 バイトずつ当てられます**。この「パディングが正しいかを教えてくれる相手」を**パディングオラクル**と呼び、2002 年に Vaudenay が SSL、IPsec、WTLS への応用とともに示しました（[Vaudenay, EUROCRYPT 2002](https://link.springer.com/chapter/10.1007/3-540-46035-7_35)）。

実際の TLS でも、この形の攻撃が繰り返し見つかりました。

| 名前 | 年 | 何が起きたか |
| --- | --- | --- |
| **POODLE** | 2014 | SSL 3.0 の CBC のパディングの検証の甘さを突き、古いプロトコルへの格下げと組み合わせて平文を取り出す（[Google Online Security Blog](https://security.googleblog.com/2014/10/this-poodle-bites-exploiting-ssl-30.html)） |
| **Lucky 13** | 2013 | TLS 1.1/1.2 と DTLS の CBC + HMAC で、パディングの長さによって MAC の計算時間がわずかに変わることを観測して平文を取り出す（[AlFardan と Paterson](http://www.isg.rhul.ac.uk/tls/Lucky13.html)） |

どちらも根は同じで、**復号して、パディングを確かめて、それから MAC を確かめる**という順序（MAC-then-encrypt）にあります。改ざんされた暗号文を、改ざんを見抜く前に処理してしまうので、その処理の結果が外に漏れるわけです。TLS には後から、先に MAC を確かめる encrypt-then-MAC の拡張（[RFC 7366](https://www.rfc-editor.org/rfc/rfc7366.html)）も足されましたが、最終的な答えは、次の節から見る **AEAD** への置き換えでした。

## 暗号化だけでは、改ざんを防げない

CTR モードに戻ります。暗号文は `C = P ⊕ K`（平文と鍵ストリームの XOR）でした。ここで攻撃者が暗号文に何かの値 Δ を XOR すると、復号の結果は次のようになります。

```
(C ⊕ Δ) ⊕ K = (P ⊕ K ⊕ Δ) ⊕ K = P ⊕ Δ
```

**鍵を知らなくても、平文の狙った位置を狙ったとおりに書き換えられます**。攻撃者に必要なのは、平文の形式（どこに何が書いてあるか）の見当だけです。送金の依頼 `to=alice&amount=00100` を AES-128-CTR で暗号化し、`amount=99999` に変えることを試しました。Δ は「元の平文と、変えたい平文の XOR」です。

```python
msg  = b"to=alice&amount=00100"
want = b"to=alice&amount=99999"
delta  = bytes(a ^ b for a, b in zip(msg, want))
forged = bytes(c ^ d for c, d in zip(ct, delta))     # 暗号文にだけ手を加える。鍵は使わない
```

```
ct       820e0c03ac8d96134ae875bf99f68544ce9e241468
forged   820e0c03ac8d96134ae875bf99f68544c7972c1d61   ← 末尾の 5 バイトだけ変わった
decrypt  b'to=alice&amount=99999'
```

受け取った側は、何の異常も検出できずに `99999` を読みます。CTR が特別に弱いのではありません。ChaCha20 でも同じことが起き、CBC でも（前のブロックが壊れる代わりに）狙った 1 ブロックを書き換えられます。**暗号化は機密性しか約束しておらず、完全性は別の部品の仕事**です。

<Callout type="warn" title="よくある誤解: 暗号化してあれば書き換えられない">
  「読めないものは狙って書き換えられない」は直感的ですが、上のとおり成り立ちません。
  暗号化が約束するのは、**鍵を持たない者に中身を読ませないこと**だけです。
  Cookie やトークンの中身を「暗号化してあるから改ざんされない」と考えて MAC を付けない実装は、
  ユーザ ID や権限の欄を書き換えられる危険があります。
  完全性が欲しいなら、第 94 回の MAC を組み合わせるか、最初から両方を持つ AEAD を使います。
</Callout>

## AEAD: 暗号化と改ざん検出を 1 つにする

暗号化と MAC を別々に組み合わせると、順序や鍵の分け方を間違える余地が残ります（前の節のパディングオラクルがその例でした）。そこで、**暗号化と改ざん検出を 1 つの操作として定義したもの**が使われるようになりました。これを **AEAD**（Authenticated Encryption with Associated Data、関連データ付き認証付き暗号）と呼びます。

AEAD の使い方は、どの方式でも同じ形をしています。

```
暗号化: (鍵, nonce, 平文, 関連データ) → 暗号文 ‖ タグ
復号:   (鍵, nonce, 暗号文 ‖ タグ, 関連データ) → 平文  または  失敗
```

- **タグ**は、暗号文と関連データの全体に対する MAC のような値で、16 バイトが一般的です
- **関連データ**（AAD）は、**暗号化はしないが、改ざんは検出したい**データです。TLS ならレコードのヘッダ、データベースなら「この暗号文は users テーブルの id=42 の行のもの」という情報を入れます。後者を入れておくと、別の行の暗号文をそのまま貼り替える攻撃も検出できます
- **復号は、タグが合わなければ平文を 1 バイトも返さない**。改ざんされたデータを処理してしまう、というパディングオラクルの前提がここで消えます

代表は 2 つです。

| 方式 | 中身 | 定義 |
| --- | --- | --- |
| **AES-GCM** | AES の CTR モードで暗号化し、GHASH（GF(2¹²⁸) 上の多項式の評価）でタグを作る。nonce は 96 ビットが標準 | [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final)（2007） |
| **ChaCha20-Poly1305** | ChaCha20 で暗号化し、Poly1305 でタグを作る。Poly1305 の鍵は、nonce ごとに ChaCha20 で使い捨てのものを作る | [RFC 8439 2.8](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.8) |

TLS 1.3 は、共通鍵暗号をこの AEAD だけに絞りました。RFC は、残したものが「すべて AEAD のアルゴリズム」だと書いています（[RFC 8446 1.2](https://www.rfc-editor.org/rfc/rfc8446.html#section-1.2)）。TLS 1.3 の暗号スイートが `TLS_AES_128_GCM_SHA256` や `TLS_CHACHA20_POLY1305_SHA256` のような短い名前になっているのはこのためで、詳しくは第 103 回で見ます。

さきほどの改ざんを、AES-128-GCM で試しました。

```python
g = AESGCM(AESGCM.generate_key(bit_length=128))
n = os.urandom(12)                                   # 96 ビットの nonce
ct = g.encrypt(n, msg, b"user_id=42")                # 関連データを付ける
forged = bytes(c ^ d for c, d in zip(ct, delta)) + ct[len(msg):]
g.decrypt(n, forged, b"user_id=42")                  # 暗号文を書き換えた
g.decrypt(n, ct, b"user_id=43")                      # 暗号文はそのまま、関連データだけ違う
```

```
len msg 21 len ct 37                  ← 21 バイトの平文 + 16 バイトのタグ
ok      b'to=alice&amount=00100'
tampered ciphertext -> InvalidTag
different AAD       -> InvalidTag
```

暗号文の中の書き換えは CTR のときとまったく同じ操作ですが、今度は**タグが合わず、復号そのものが失敗**しました。関連データを 1 文字変えただけでも同じです。ChaCha20-Poly1305 でも、同じ API で同じ結果になります。

## nonce を 2 回使うと、何が漏れるか

AEAD の約束には、1 つだけ利用者が守る条件があります。**同じ鍵で、同じ nonce を 2 回使わないこと**です。nonce は秘密にする必要はなく、暗号文と一緒に送ってかまいません。守るべきなのは**一意であること**だけです。

<Callout type="warn" title="よくある誤解: IV や nonce は秘密にしなければならない">
  IV や nonce を鍵と同じように隠そうとする実装がありますが、その必要はありません。
  TLS でも暗号文の横に置かれるか、双方が数えている番号から作られます。
  逆に、**秘密かどうかより、使い回さないことの方がはるかに重要**です。
  CBC の IV は「予測できないこと」、CTR や GCM の nonce は「二度と使わないこと」が条件で、
  モードによって求められる性質も違います。
</Callout>

守らなかったとき、まず**機密性**が壊れます。GCM の暗号化は CTR なので、nonce が同じなら鍵ストリームも同じです。2 つの暗号文を XOR すると、鍵ストリームが打ち消し合って**平文同士の XOR** が残ります。

```python
c1 = g.encrypt(n, b"to=alice&amount=00100", None)
c2 = g.encrypt(n, b"to=bob&amount=0000500", None)   # 同じ nonce をもう一度
x = xor(c1, c2)
```

```
c1^c2 == m1^m2: True
m2 from m1: b'to=bob&amount=0000500'       ← 一方の平文を知っていれば、もう一方がそのまま読める
```

一方の平文が分かっている（あるいは推測できる）だけで、もう一方が読めてしまいます。RFC 8439 も ChaCha20-Poly1305 について同じことを警告しています（[RFC 8439 4](https://www.rfc-editor.org/rfc/rfc8439.html#section-4)）。

GCM ではさらに**完全性**も壊れます。GCM のタグは、鍵から作られる**認証鍵 H** を変数とする多項式の値です。同じ nonce で作られた 2 つのタグを組み合わせると、H の多項式の方程式が得られ、それを解くと H の候補が絞り込めます。H が分かれば、攻撃者は**任意の暗号文に正しいタグを付けられる**ようになります。この攻撃は Joux が GCM の標準化の段階で NIST に指摘したもので（[Joux, Authentication Failures in NIST version of GCM](https://csrc.nist.gov/csrc/media/projects/block-cipher-techniques/documents/bcm/comments/800-38-series-drafts/gcm/joux_comments.pdf)）、2016 年には、インターネット上で nonce を繰り返している HTTPS サーバが 184 台見つかり、暗号化された通信に偽の内容を差し込めることが実証されました（[Böck ほか, WOOT 2016](https://eprint.iacr.org/2016/475)）。

つまり GCM での nonce の使い回しは、「少し弱くなる」のではなく、**機密性と完全性の両方が崩れる**失敗です（[RFC 8452 1](https://www.rfc-editor.org/rfc/rfc8452.html#section-1) は、これを「破滅的」と書いています）。対策は 3 通りあります。

| 対策 | 中身 |
| --- | --- |
| **数える** | nonce を送信のたびに 1 ずつ増やす。TLS 1.3 は、鍵と一緒に導出した固定の値とレコードの通し番号を XOR して nonce を作り、nonce そのものは送らない（[RFC 8446 5.3](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.3)） |
| **乱数にして、回数を抑える** | 96 ビットの乱数の nonce は、同じ鍵で約 2³² 回を超えると衝突の確率が無視できなくなる。NIST は、乱数の IV を使う場合の暗号化の回数を 2³² 回までに制限している（SP 800-38D 8.3）。超える前に鍵を替える |
| **使い回しに強い方式を選ぶ** | AES-GCM-SIV（[RFC 8452](https://www.rfc-editor.org/rfc/rfc8452.html)）は、nonce を使い回しても「2 つの平文が同じかどうか」しか漏れない |

複数のサーバやプロセスが同じ鍵で暗号化する構成では、「数える」がそのままでは成り立たない点に注意が要ります。カウンタを共有しない限り、2 台が同じ番号を使いかねないからです。そのような場面では、乱数の nonce と鍵の定期的な交換（第 99 回の鍵の管理）を組み合わせるか、使い回しに強い方式を選びます。

## 128 ビットのブロックと、データの量

ブロックの長さも、安全性に直接かかわります。第 94 回の誕生日のパラドックスを思い出すと、n ビットのブロックでは、およそ 2^(n/2) 個のブロックを暗号化したあたりで、同じ暗号文ブロックの組が現れ始めます。CBC ではその組から平文同士の XOR が漏れます。

AES より前の 3DES や Blowfish はブロックが 64 ビットでした。2^32 ブロックは 32 GB にすぎず、長く続く 1 本の接続なら現実に届く量です。2016 年の **Sweet32** は、785 GB ほどの通信を観測して、HTTPS の Cookie を取り出せることを示しました（[sweet32.info](https://sweet32.info/)、CVE-2016-2183）。AES が 128 ビットのブロックを持つのは、この上限を実用上届かない所まで押し上げるためです。

## CPU の命令で速くする

AES をソフトウェアで速く実装するには、ラウンドの処理をまとめた大きな表を引くのが定番でした。しかし表の引き方は鍵とデータによって変わるので、キャッシュに当たるか外れるかの時間差から、鍵の情報が漏れる危険があります。

そこで CPU に AES 専用の命令が入りました。Intel は 2010 年の Westmere 世代から **AES-NI** と呼ぶ 6 つの命令（1 ラウンドを実行する `AESENC`、最後のラウンドの `AESENCLAST`、鍵の展開を助ける `AESKEYGENASSIST` など）を載せ、GCM の GHASH に使う繰り上がりのない掛け算 `PCLMULQDQ` も加えました（[Intel の解説](https://www.intel.com/content/dam/doc/white-paper/advanced-encryption-standard-new-instructions-set-paper.pdf)）。第 12 回で見た SIMD のレジスタ（128 ビット）に 1 ブロックがちょうど収まり、1 命令で 1 ラウンドが進みます。Arm も ARMv8 で同じ役割の命令を持っています。**速くなるだけでなく、表を引かないので時間差が生まれにくい**のも利点です。

手元の Apple M1 Pro（`hw.optional.arm.FEAT_AES: 1`）で、OpenSSL 3.6 の速度を測りました。`OPENSSL_armcap=0` は、OpenSSL に CPU の拡張命令を使わせないための環境変数です。

```
$ openssl speed -evp aes-128-gcm -bytes 16384 -seconds 2
AES-128-GCM        7356189.14k        ← 約 7.4 GB/s
$ OPENSSL_armcap=0 openssl speed -evp aes-128-gcm -bytes 16384 -seconds 2
AES-128-GCM         156032.67k        ← 約 0.16 GB/s（約 47 分の 1）

$ openssl speed -evp chacha20-poly1305 -bytes 16384 -seconds 2
ChaCha20-Poly1305  1684471.10k        ← 約 1.7 GB/s
$ OPENSSL_armcap=0 openssl speed -evp chacha20-poly1305 -bytes 16384 -seconds 2
ChaCha20-Poly1305   528022.03k        ← 約 0.53 GB/s
```

専用命令があれば AES-GCM が大きく勝ち、なければ ChaCha20-Poly1305 の方が 3 倍以上速い、という関係が見えます（ChaCha20 の側も、NEON という汎用の SIMD 命令を止めた分だけ遅くなっています）。RFC 8439 も、AES の命令を持たない CPU では ChaCha20 の方が速いことを動機に挙げています（[RFC 8439 1](https://www.rfc-editor.org/rfc/rfc8439.html#section-1)）。TLS 1.3 の暗号スイートにも、AES-GCM と並んで ChaCha20-Poly1305 が入っています。

## 手元で確かめる

この回の実験は、Python 3.14 と cryptography 48 の 1 本のスクリプトで再現できます。要点だけを並べます。

```python
import os
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.primitives.ciphers.aead import AESGCM, ChaCha20Poly1305
from cryptography.exceptions import InvalidTag

key = os.urandom(16)
msg = b"to=alice&amount=00100"

# 1. ECB: 同じブロックは同じ暗号文
enc = Cipher(algorithms.AES(key), modes.ECB()).encryptor()
print(enc.update(b"ATTACK AT DAWN!!" * 2).hex())

# 2. CTR: 鍵を使わずに平文を書き換える
nonce = os.urandom(16)
enc = Cipher(algorithms.AES(key), modes.CTR(nonce)).encryptor()
ct = enc.update(msg) + enc.finalize()
delta = bytes(a ^ b for a, b in zip(msg, b"to=alice&amount=99999"))
forged = bytes(c ^ d for c, d in zip(ct, delta))
dec = Cipher(algorithms.AES(key), modes.CTR(nonce)).decryptor()
print(dec.update(forged) + dec.finalize())           # b'to=alice&amount=99999'

# 3. AES-GCM: 同じ書き換えは InvalidTag になる
g = AESGCM(AESGCM.generate_key(bit_length=128))
n = os.urandom(12)
ct = g.encrypt(n, msg, b"user_id=42")
try:
    g.decrypt(n, bytes(c ^ d for c, d in zip(ct, delta)) + ct[len(msg):], b"user_id=42")
except InvalidTag:
    print("InvalidTag")
```

<Callout type="tip" title="openssl enc では AEAD を使えない">
  コマンドラインでファイルを暗号化する `openssl enc` は、AEAD に対応していません。
  `openssl enc -aes-128-gcm ...` を実行すると、`enc: AEAD ciphers not supported` と表示されて止まります（手元の OpenSSL 3.6.2）。
  つまり `openssl enc` で作れるのは、この回で見た「改ざんを検出しない」暗号文だけです。
  ファイルを暗号化するなら、AEAD を使う専用の道具やライブラリを選びます。
</Callout>

## 何と組み合わさって意味を持つか

共通鍵暗号は、単体では役に立ちません。この回の部品が働くには、周りに次の部品が要ります。

| 足りないもの | 埋める部品 | 回 |
| --- | --- | --- |
| 改ざんの検出 | MAC、または最初から AEAD | 第 94 回、この回 |
| 2 人が同じ鍵を持つこと | 鍵交換（ECDHE） | 第 96 回 |
| 鍵交換の相手が本物であること | 署名と証明書 | 第 97 回、第 100〜101 回 |
| 鍵交換の結果から、向きごと・用途ごとの鍵を作ること | 鍵導出（HKDF） | 第 99 回 |
| 予測できない鍵と nonce | 暗号用の乱数 | 第 99 回 |

TLS 1.3 は、この表を 1 本のプロトコルにまとめたものです。ECDHE で共通の秘密を作り、HKDF で送信用と受信用の鍵と IV を導出し、レコードの通し番号から nonce を作って、AEAD でレコードを暗号化します。第 103 回で、そのハンドシェイクを 1 メッセージずつ読みます。

## まとめ

- 共通鍵暗号は、同じ鍵を持つ者同士で**機密性**を守る部品。ブロック暗号（AES: 128 ビットのブロック、鍵 128/192/256 ビット）とストリーム暗号（ChaCha20）がある
- AES は 16 バイトを置き換えるだけで、長いデータへの使い方は**利用モード**が決める。ECB は同じブロックが同じ暗号文になり、パターンが漏れる。CBC は IV とパディングが要り、CTR は AES で鍵ストリームを作る
- 復号してからパディングや MAC を確かめる作りは、**パディングオラクル**（POODLE、Lucky 13）で平文を漏らした
- **暗号化だけでは改ざんを防げない**。CTR では、鍵を知らずに暗号文を XOR するだけで平文を狙いどおりに書き換えられる
- **AEAD**（AES-GCM、ChaCha20-Poly1305）は暗号化と改ざん検出を 1 つにし、タグが合わなければ平文を返さない。関連データで、暗号化しない文脈も守れる。TLS 1.3 は AEAD だけを使う
- nonce は秘密でなくてよいが、**同じ鍵で二度使ってはいけない**。GCM で使い回すと平文の XOR が漏れ、認証鍵 H も求められて偽造できるようになる
- 64 ビットのブロックは誕生日の上限に届く（Sweet32）。AES-NI などの専用命令は、AES を速くし、時間差による漏れも減らす

この回の部品は「2 人が同じ鍵を持っている」ことを前提にしていました。次の第 96 回では、一度も会ったことのない 2 人が、盗聴されている通信路の上でその共通の鍵を作る方法、公開鍵暗号と鍵交換を見ます。
