## この章で見るもの

ここまでの章で、守りの部品をたくさん見てきました。第 93〜101 回ではブラウザが引くオリジンの境界を、第 102〜108 回では暗号と鍵を、第 116〜123 回では認証と認可を、第 160 回ではコンテナの権限の絞り方を見ました。第 64 回では、消し忘れた DNS のレコードが乗っ取りの入口になることも確かめました。第 25 章では、動いているシステムの中を観測する道具を扱いました。

どれも、**1 つの部品として正しく使えば効く**ものです。けれど、実際のシステムを前にすると、別の問いが残ります。

- そもそも、このシステムで何を守るべきかを、誰がどう決めたのか
- 「正しく作った」と言うとき、何と比べて正しいのか
- 作った日に正しかった設定が、半年後も正しいままだと、どうして言えるのか
- それを、社外の人に信じてもらうには何を見せればよいのか

第 26 章では、この問いを 8 回に分けて扱います。

| 回 | 見るもの |
| --- | --- |
| 第 174 回（この回） | 守りの地図。脅威モデリング、基準、確かめ続けること、証跡 |
| 第 175 回 | コードを読んで見つける。SAST と SCA |
| 第 176 回 | 動いているものと設定を確かめる。DAST、IaC の検査、CSPM |
| 第 177 回 | 秘密が漏れる道。シークレットの検出と、漏れた後の対応 |
| 第 178 回 | 作ってから配るまで。サプライチェーン、SLSA、SBOM、署名 |
| 第 179 回 | テナントの境界。マルチテナントの越境と、DB 側での強制 |
| 第 180 回 | ファイルを受け取る、返す。Zip Slip、XXE、SSRF など |
| 第 181 回 | 証跡に残す。監査ログ、SIEM、継続的な統制の監視、SOC 2 |

この回では個々の技術には深入りせず、**8 回がそれぞれ全体のどこを受け持つのか**を描きます。

## 守りを 4 つの段に分ける

セキュリティの活動は、ばらばらに見えて、実は順番を持っています。この章では次の 4 つの段に分けて考えます。

```
④ 証跡に残す          監査ログ、SIEM、統制の監視、SOC 2       （第 181 回）
      ▲ 確かめた結果を、第三者が検証できる形で残す
③ 確かめ続ける        アプリ: SAST / SCA / DAST              （第 175・176 回）
                      インフラ: IaC の検査 / CSPM            （第 176 回）
                      配布: SLSA / SBOM / 来歴               （第 178 回）
      ▲ 基準どおりに作られ、今もそのままかを機械で見る
② 基準に照らして作る  アプリ: OWASP Top 10 / ASVS / CWE
                      インフラ: CIS Benchmarks / CIS Controls
      ▲ 何を満たせば「守れている」と言えるかの物差し
① リスクを洗い出す    脅威モデリング（STRIDE、攻撃ツリー）、OCTAVE
```

下の段は上の段の前提です。①で何を守るかが決まっていなければ、②でどの基準を採るかを選べません。②の物差しがなければ、③の検査は何を合格とすればよいか分かりません。③で確かめた記録がなければ、④で見せるものがありません。

逆向きの流れもあります。④の監査で見つかった不足や、③の検査で繰り返し出る指摘は、①の脅威モデルや②の基準の選び方を見直すきっかけになります。**一周して終わりではなく、回り続ける**ものです。

この 4 段のうち、第 177・179・180 回は少し性格が違います。シークレット、テナントの境界、ファイルの取扱いという**具体的な攻撃面**を 1 つずつ取り上げ、そこに 4 段を当てはめる回です。最後にまとめて対応表を示します。

## 「統制」という言葉

この章では**統制**（control、コントロール）という言葉を何度も使います。NIST の用語集は、セキュリティの統制を次のように定義しています（[NIST CSRC Glossary](https://csrc.nist.gov/glossary/term/security_control)）。

> A safeguard or countermeasure prescribed for an information system or an organization designed to protect the confidentiality, integrity, and availability of its information and to meet a set of defined security requirements.

要するに、**決められた要件を満たすために置く、具体的な対策**のことです。「root ユーザーにアクセスキーを作らない」「本番の DB には公開のアドレスを付けない」「依存関係の既知の脆弱性を 30 日以内に直す」といった 1 つ 1 つが統制です。技術的なもの（設定やコード）だけでなく、手続き（承認の手順、定期的な見直し）も含みます。

統制には、必ず次の 3 つが対になってついて回ります。

| 項目 | 例 |
| --- | --- |
| 統制（何をするか） | root ユーザーのアクセスキーを持たない |
| 確かめ方（どう見るか） | アカウントの設定を API で読み、キーの有無を調べる |
| 証拠（何が残るか） | 調べた日時と結果の記録 |

第 175〜180 回は主に「確かめ方」を、第 181 回は「証拠」を扱います。この回の残りでは、その手前の「何を統制にするか」を決める 2 つの段を見ます。

## リスクを洗い出す: 脅威モデリング

### 4 つの問い

脅威モデリングは、設計の段階で「このシステムに何が起こりうるか」を体系的に洗い出す作業です。やり方は流派によって違いますが、共通する骨格は次の 4 つの問いにまとめられています（[Threat Modeling Manifesto](https://www.threatmodelingmanifesto.org/)）。

1. What are we working on?（何を作っているのか）
2. What can go wrong?（何がまずくなりうるか）
3. What are we going to do about it?（それにどう対処するか）
4. Did we do a good enough job?（十分にできたか）

1 つ目の問いに答えるために図を描き、2 つ目の問いに答えるために分類の枠を当てる。これが次に見る DFD と STRIDE の役割です。

### DFD と信頼境界

**DFD**（Data Flow Diagram、データフロー図）は、システムを「データがどこから来て、どこで処理され、どこに置かれるか」で描く図です。Microsoft の脅威モデリングの解説では、DFD を 4 種類の要素と、脅威モデリングのために足す 1 つの線で描きます（[MSDN Magazine 2006](https://learn.microsoft.com/en-us/archive/msdn-magazine/2006/november/uncover-security-design-flaws-using-the-stride-approach)）。

| 要素 | 意味 | 例 |
| --- | --- | --- |
| 外部の相手（interactor） | システムの外にいる、データの出し手や受け手 | 利用者、外部の API、IdP |
| プロセス | データを処理する計算 | Web API、バッチ処理のワーカー |
| データの置き場（data store） | データが留まる場所 | DB、オブジェクトストレージ、設定ファイル |
| データの流れ（data flow） | 要素の間を動くデータ | HTTPS の要求、キューのメッセージ |
| 信頼境界（trust boundary） | 信頼してよい側と、してはいけない側の境目 | インターネットとアプリの間、テナントとテナントの間 |

同じ解説は、信頼境界を「すべての中でいちばん主観的なもの」と書いています。どこに線を引くかは設計の判断で、ここを誤ると、境界を越えるデータの流れを見落とします。**脅威の多くは、信頼境界を横切る矢印の上で起こります**。

### STRIDE: 何がまずくなりうるかの分類

DFD を描いたら、要素ごとに「何がまずくなりうるか」を考えます。手がかりなしに考えると、その場で思いついたことしか挙がりません。そこで Microsoft は、脅威を 6 つに分類した **STRIDE** を使います（[Microsoft Learn](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-threats)）。それぞれの脅威は、守りたい性質の 1 つを破るものとして整理されています。

| 脅威 | 意味 | 破られる性質 |
| --- | --- | --- |
| **S**poofing（なりすまし） | 他人の認証情報を使って、別の誰かとして振る舞う | 認証 |
| **T**ampering（改ざん） | 保存中や転送中のデータを書き換える | 完全性 |
| **R**epudiation（否認） | 行った操作を「やっていない」と言い逃れる | 否認防止 |
| **I**nformation disclosure（情報の漏えい） | 見てはいけない人に情報が見える | 機密性 |
| **D**enial of service（サービス妨害） | 正当な利用者が使えなくなる | 可用性 |
| **E**levation of privilege（権限の昇格） | 権限のない者が、より強い権限を得る | 認可 |

性質の側は、第 102 回で見た機密性・完全性・真正性・否認防止と、第 116 回で見た認証と認可に、可用性を足したものです。STRIDE は新しい概念というより、**これまでの章で見た性質を、破る側から言い直した一覧**だと考えると覚えやすくなります。

### 要素ごとに当てはまる脅威は決まっている

前掲の MSDN の解説には、DFD の要素の種類ごとに、どの脅威が当てはまるかの表があります。これを **STRIDE per element** と呼びます。

| 要素 | S | T | R | I | D | E |
| --- | --- | --- | --- | --- | --- | --- |
| データの流れ | | ✓ | | ✓ | ✓ | |
| データの置き場 | | ✓ | | ✓ | ✓ | |
| プロセス | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 外部の相手 | ✓ | | ✓ | | | |

なりすましができるのは「誰か」として振る舞う主体（プロセスと外部の相手）だけで、ただのデータの流れになりすますことはできません。逆に、外部の相手は自分たちの管理の外にいるので、改ざんや漏えいを防ぐ対象にはなりません。**表を使うと、要素の数 × 当てはまる脅威の数だけ、考えるべき問いが機械的に出てきます**。思いつきに頼らずに、抜けを減らせるのがこの方法の利点です。

<Callout type="note" title="データの置き場と否認">
  表では、データの置き場に否認（R）の印がありません。ただし、置き場が**監査ログ**であれば話は別で、
  ログが書き換えられると「誰が何をしたか」を示せなくなります。
  表は出発点であって、要素の役割によって足し引きします。ログの守り方は第 181 回で扱います。
</Callout>

### 小さな例で当ててみる

具体的なシステムで試します。次のような、小さな SaaS を考えます。

- 利用者はブラウザでログインし（ログインは外部の IdP に任せる）、CSV のファイルをアップロードする
- Web API はファイルをオブジェクトストレージに置き、取り込みの仕事をキューに積む
- ワーカーがキューから仕事を取り出し、CSV を読んで DB に書く
- 1 つのアプリを、複数の会社（テナント）が共有している

DFD にすると、次のようになります。点線が信頼境界です。

```
  インターネット側             ┆   アプリ側
                               ┆
 [利用者]──(1) HTTPS 要求────────→ (Web API) ──(3) 書き込み──→ ═オブジェクトストレージ═
                               ┆      │  ↑                              │
 [IdP]───(2) ID トークン─────────→    │  └─(4) 読み書き── ═DB═           │
                               ┆      │                     ↑            │
                               ┆      └─(5) 仕事を積む→ ═キュー═         │
                               ┆                            │            │
                               ┆                      (ワーカー)←─(6) 読む┘
                               ┆                            └─(7) 書き込み→ ═DB═
  ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄
   テナント A のデータ ┆ テナント B のデータ   （DB とストレージの中にも境界がある）
```

この図の要素に STRIDE per element の表を当て、いくつかの行を書き出すと次のようになります。

| 要素 | 脅威 | 起こりうること | 対策の候補 | 扱う回 |
| --- | --- | --- | --- | --- |
| 利用者（外部の相手） | S | 盗んだセッションで本人になりすます | MFA、セッションの管理 | 第 117・118 回 |
| (2) ID トークン | T | 署名を検証せずに中身を信じる | 署名・発行者・宛先の検証 | 第 122 回 |
| Web API | E | URL の ID を変えると、他テナントのデータが見える | 認可の検査、DB 側での強制 | 第 179 回 |
| Web API | I | エラーの応答に接続文字列が出る | 例外の扱い、シークレットを置かない | 第 177 回 |
| (1) アップロード | T | 細工した zip のパスで、置き場の外に書かせる | パスの正規化 | 第 180 回 |
| ワーカー | E | CSV の中の URL を取りに行き、内部のメタデータに届く | 宛先の制限 | 第 180 回 |
| ワーカー | D | 展開すると巨大になる zip で、ディスクとメモリを食い尽くす | 展開後の大きさの上限 | 第 180 回 |
| キュー | I | 仕事にテナント ID を載せ忘れ、別テナントの文脈で処理する | 仕事の中身にテナントを必ず持たせる | 第 179 回 |
| ワーカー | R | 誰の依頼で取り込んだかが残らない | 監査ログ | 第 181 回 |
| DB | I | バックアップのスナップショットが公開設定になっている | 設定の継続的な検査 | 第 176 回 |
| Web API の依存 | T | 依存パッケージに悪意のある版が混ざる | 依存の固定、来歴の検証 | 第 175・178 回 |

表のすべての行を埋める必要はありません。ここで大事なのは 2 点です。1 つは、**図の要素から機械的に問いを出したので、テナントの境界やワーカーのような「表から見えにくい場所」も漏れずに挙がった**こと。もう 1 つは、挙がった脅威の多くが、この章の後続の回にそのままつながることです。脅威モデルは、**どの検査と統制が必要かを決める入力**になります。

### 攻撃ツリー: 1 つの目標を分解する

STRIDE が「要素ごとに、脅威を網羅する」方法だとすると、**攻撃ツリー**は「1 つの目標に至る道を、深く分解する」方法です。Schneier は、攻撃の目標を根に置き、その目標に至る方法を枝と葉で表す木として説明しました（[Schneier 1999](https://www.schneier.com/academic/archives/1999/12/attack_trees.html)）。枝の分かれ方には 2 種類あります。

- **OR**: 子のどれか 1 つが成り立てば、親が成り立つ（別々の手段）
- **AND**: 子のすべてが成り立って初めて、親が成り立つ（組み合わせが要る手段）

上の SaaS で「他テナントの CSV を読む」を根に置くと、たとえば次のように分解できます。

```
他テナントの CSV を読む（OR）
├─ API の認可を回避する（OR）
│   ├─ URL のファイル ID を書き換える ............ 認可の検査が無ければ成立
│   └─ キャッシュのキーにテナントが入っていない応答を受け取る
├─ ストレージから直接読む（AND）
│   ├─ オブジェクトのキー（パス）を知る
│   └─ そのキーに対して有効な署名付き URL を得る
├─ 権限の強い認証情報を手に入れる（OR）
│   ├─ Git の履歴に残ったアクセスキーを拾う
│   └─ CI のログに出力されたトークンを拾う
└─ 正規の運用者として見る
    └─ 運用者の権限が広すぎ、操作の記録も残らない
```

AND の枝は、子のどれか 1 つを確実に止めれば枝全体が止まります。OR の枝は、すべての子を止めなければなりません。葉に「実行の難しさ」や「必要な費用」を振れば、どの葉を最初に塞ぐべきかの優先順位も付けられます。Schneier の解説でも、ノードに費用や実現性などの値を割り当てて、最も現実的な攻撃を見つける使い方が示されています。

### OCTAVE: 組織の資産から始める

STRIDE と攻撃ツリーは、どちらも**設計図（DFD）や攻撃の目標**から出発します。開発者が自分の作るシステムを点検するのに向いた道具です。

これとは出発点の違う方法として、カーネギーメロン大学の SEI が作った **OCTAVE**（Operationally Critical Threat, Asset, and Vulnerability Evaluation）があります。2003 年の解説では、大きな組織向けの OCTAVE Method と、小さな組織向けの OCTAVE-S が示されています（[SEI](https://www.sei.cmu.edu/library/introduction-to-the-octave-approach/)）。2007 年には、より少ない時間と人手で評価できるようにした **OCTAVE Allegro** が出ました。その要約は、評価の対象を次のように説明しています（[SEI](https://www.sei.cmu.edu/library/introducing-octave-allegro-improving-the-information-security-risk-assessment-process/)）。

> It leads the organization to consider people, technology, and facilities in the context of their relationship to information and the business processes and services they support.

つまり、**守るべき情報と、それが支える業務**をまず決め、その情報がどの人・技術・施設の中に置かれているかをたどってリスクを評価します。STRIDE が「この API のこの矢印に何が起こるか」を問うのに対して、OCTAVE は「この会社にとって、顧客の請求データが漏れたら何が困るか、それはどこに置かれているか」を問います。

| | STRIDE（と攻撃ツリー） | OCTAVE |
| --- | --- | --- |
| 出発点 | システムの設計図（DFD）、攻撃の目標 | 組織にとって重要な情報と業務 |
| 単位 | 要素（プロセス、データの流れなど） | 情報資産と、それを入れている人・技術・施設 |
| 主な問い | この要素に、どの種類の脅威があるか | この資産が損なわれたら、業務に何が起きるか |
| 主な担い手 | 設計者、開発者 | 業務と IT の両方を知る組織の人 |
| 得られるもの | 設計上の対策の一覧 | リスクの評価と、組織としての対応の方針 |

2 つは競合するものではありません。OCTAVE のような評価で「この情報が最重要で、この業務が止まると困る」という優先度を決め、その情報を扱うシステムを STRIDE で細かく点検する、という組み合わせ方ができます。

## 基準に照らして作る: アプリの辞書とインフラの辞書

脅威モデリングで挙がった脅威に、毎回ゼロから対策を考えるのは大変です。また、自分たちで考えた対策だけでは、抜けがあるかどうかを外から判断できません。そこで、**「こう作れば、この種類の脅威は防げる」をまとめた共通の基準**を使います。

基準は、大きく 2 つの系統に分かれます。**アプリと API の作り方を扱う OWASP の系統**と、**OS やクラウドの設定を扱う CIS の系統**です。対象が違うので、同じ「ログを残す」でも、書いてある中身が違います。

### アプリの側: OWASP Top 10、ASVS、CWE

**OWASP Top 10** は、Web アプリケーションで重大なリスクの分類を 10 個並べたものです。2025 年版は次のとおりです（[OWASP Top 10:2025](https://top10.owasp.org/2025)）。

| ID | 分類 | この章との関係 |
| --- | --- | --- |

Top 10 は**分類の一覧**であって、1 つずつ合否を判定できる要件の形にはなっていません。「Broken Access Control が無いこと」を確かめる方法は書かれていないのです。

合否を判定できる形にしたのが **ASVS**（Application Security Verification Standard）です。2025 年 5 月に 5.0.0 が出ました（[OWASP ASVS](https://github.com/OWASP/ASVS/tree/v5.0.0)）。ASVS は要件を「章.節.要件」の番号で識別し、認証、セッション、認可、ファイルの取扱い、ログなどの章に分けて並べています。5.0 の文書は、要件を 3 つの水準に分けています（[ASVS 5.0「What is the ASVS」](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x03-What-is-the-ASVS.md)）。

| 水準 | 位置づけ | 要件の割合 |
| --- | --- | --- |
| L1 | 最低限の出発点。前提条件なしに悪用される攻撃への、最初の防御 | 約 20% |
| L2 | ほとんどのアプリケーションが目指すべき水準 | L1 と合わせて約 70% |
| L3 | 最高水準のセキュリティを示したいアプリケーション向け。多層防御など | 残りの約 30% |

ASVS 5.0 には、要件の一部を「決めたことを文書にしておく」形にしたものがあります。たとえば「アップロードを許すファイルの種類」は、アプリによって答えが違うので、ASVS は正解を決めず、**組織が決めて文書に残すこと**を要件にし、実装が文書どおりかを別の要件で確かめます。脅威モデリングの結果が、ここで基準とつながります。

3 つ目の **CWE**（Common Weakness Enumeration）は、ソフトウェアとハードウェアの**弱点の種類**に番号を振った一覧です（[MITRE CWE](https://cwe.mitre.org/about/index.html)）。

> A 'weakness' is a condition in a software, firmware, hardware, or service component that, under certain circumstances, could contribute to the introduction of vulnerabilities.

CVE が「この製品のこの版にある、この 1 件の脆弱性」に振られる番号であるのに対して、CWE は「SQL インジェクション」「パスの検証不備」のような**種類**に振られる番号です。第 175 回で見る SAST の指摘には、多くの場合 CWE の番号が付きます。Top 10 の各分類にも、対応づけられた CWE の一覧があります。A01:2025 には、パストラバーサル（CWE-22）や認可の欠落（CWE-862）など 40 個が並んでいます（[OWASP Top 10:2025 A01](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control/)）。**Top 10 が見出し、ASVS が要件、CWE が個々の欠陥の名前**、という関係です。

### インフラの側: CIS Benchmarks と CIS Controls

インフラの基準として広く使われているのが、CIS（Center for Internet Security）の 2 つの文書です。

**CIS Benchmarks** は、製品ごとの**安全な設定の推奨値**を集めたものです。25 以上の製品群について、クラウド（AWS、Azure、Google Cloud）、OS、データベース、ネットワーク機器などの文書があります（[CIS Benchmarks](https://www.cisecurity.org/cis-benchmarks)）。たとえば AWS 向けの文書には、「root ユーザーのアクセスキーを持たない」「CloudTrail のログファイルの検証を有効にする」「S3 のパブリックアクセスをブロックする」といった項目が並びます。項目の多くは、**API で設定を読めば合否が決まる**形をしています。

**CIS Controls** は、製品ではなく**組織が取るべき対策の優先順位**を示した文書です。現行の v8.1 は 18 の統制からなり、資産の棚卸し、ソフトウェアの棚卸し、データの保護、安全な設定、アカウント管理、継続的な脆弱性管理、監査ログの管理、アプリケーションのセキュリティ、インシデント対応などが並びます（[CIS Controls List](https://www.cisecurity.org/controls/cis-controls-list)）。各統制はさらに具体的な対策（Safeguard、全部で 153 個）に分かれ、組織の規模や成熟度に応じた 3 つの実装グループ（IG1〜IG3）に振り分けられています。IG1 は「essential cyber hygiene」と呼ばれ、どの組織もまずここから始めるよう勧められています（[CIS Implementation Groups](https://www.cisecurity.org/controls/implementation-groups)）。

### 2 つの辞書を並べる

| | OWASP（Top 10 / ASVS） | CIS（Benchmarks / Controls） |
| --- | --- | --- |
| 主な対象 | アプリケーション、API | OS、クラウド、ミドルウェア、組織の運用 |
| 書いてあること | コードと設計が満たすべき要件 | 設定の推奨値と、組織の対策の優先順位 |
| 例 | 「オブジェクトへのアクセスごとに認可を検査する」 | 「root ユーザーのアクセスキーを持たない」 |
| 主に確かめる道具 | SAST、SCA、DAST、手動の検査 | IaC の検査、CSPM、構成の監査 |
| この章の回 | 第 175・176・179・180 回 | 第 176 回 |

2 つの辞書の境目にも注意が要ります。たとえば ASVS は、DNS の設定のように**アプリケーションの責任の外にある設定は対象外**だと明記しています（[ASVS 5.0「What is the ASVS」](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x03-What-is-the-ASVS.md)）。第 64 回で見たダングリング DNS は、ASVS だけを見ていると拾えません。逆に CIS Benchmarks は、アプリの中の認可の検査には触れません。**どちらか一方だけでは、システム全体を覆えない**ということです。

<Callout type="warn" title="基準を満たすことは、守れていることと同じではない">
  基準は「多くのシステムに共通する脅威」への対策の集まりです。
  自分たちのシステムに固有の脅威、たとえば業務の手順を悪用されるような脅威は、基準の中にはありません。
  それを見つけるのが脅威モデリングの役目です。①を飛ばして②だけを満たしても、
  「基準には合格しているが、肝心のところが守れていない」状態になりえます。
</Callout>

## 作ったときの正しさと、動いている間の正しさ

基準に沿って作り、リリースの前に検査も通した。それで終わりにできないのは、**正しさが時間とともに崩れる**からです。崩れ方には、少なくとも 3 つの型があります。

| 崩れ方 | 例 | 何が変わったか |
| --- | --- | --- |
| 設定のずれ（ドリフト） | 障害対応のために、コンソールからセキュリティグループに穴を開けて、閉じ忘れる | 動いている環境 |
| 知識の更新 | リリース時には無かった脆弱性が、使っている依存パッケージで公表される | 世の中の知識 |
| 基準の更新 | 基準の新しい版で、新しい項目が増える | 物差し |

1 つ目の**ドリフト**は、コードやテンプレートに書いた「あるべき状態」と、実際の環境とが食い違うことです。Terraform の解説では、手で変更したリソースについて、状態ファイルが実際のインフラと同期しなくなること（"drift"）と説明しています（[HashiCorp Developer](https://developer.hashicorp.com/terraform/tutorials/state/resource-drift)）。第 161 回で見た Kubernetes のコントローラは、宣言された状態に近づけ続けることでドリフトを打ち消していました。けれど、すべての設定がそうした仕組みの下にあるわけではありません。

2 つ目は、**コードは何も変わっていないのに、評価が変わる**場合です。昨日まで問題の無かった依存パッケージが、今日の脆弱性の公表で「直すべきもの」になります。第 175 回の SCA は、この変化を拾うために繰り返し動かす必要があります。

3 つ目は、物差しの側の変化です。たとえば AWS Security Hub が対応している CIS AWS Foundations Benchmark は v5.0.0 までですが（[AWS Security Hub](https://docs.aws.amazon.com/securityhub/latest/userguide/cis-aws-foundations-benchmark.html)）、CIS 自身のページでは 7.1.0 が最新として掲げられています（[CIS](https://www.cisecurity.org/benchmark/amazon_web_services)）。道具が見ている物差しが、いつの版なのかも確かめる対象です。

ここから、**一度の検査では足りず、確かめ続ける仕組みが要る**という結論が出ます。NIST SP 800-137 は、この考え方を情報セキュリティの継続的モニタリング（ISCM）として、組織の資産の可視化、脅威と脆弱性の把握、そして**導入した統制が有効に働いているかの可視化**を続けるものと位置づけています（[NIST SP 800-137](https://csrc.nist.gov/pubs/sp/800/137/final)）。

## 確かめ続ける: 3 つの系統

確かめる道具は、何を見るかで 3 つの系統に分かれます。

```
                       見るもの                      主な道具            照らす基準
アプリの系統   ──→   ソースコード                   SAST               ASVS / CWE
                      依存関係（ロックファイル）     SCA                脆弱性 DB（CVE、GHSA、OSV）
                      動いているアプリ               DAST               ASVS / Top 10
インフラの系統 ──→   インフラのコード（Terraform）  IaC の検査          CIS Benchmarks
                      動いているクラウドの設定       CSPM               CIS Benchmarks
配布の系統     ──→   ビルドと成果物                 来歴の検証、署名     SLSA
                      成果物の中身                   SBOM               脆弱性 DB
```

| 系統 | 道具 | いつ動かすか | 扱う回 |
| --- | --- | --- | --- |
| アプリ | SAST（コードの静的解析） | 変更のたび（プルリクエスト） | 第 175 回 |
| アプリ | SCA（依存関係の解析） | 変更のたび、加えて定期的に | 第 175 回 |
| アプリ | DAST（動いているアプリへの検査） | ステージング環境で定期的に | 第 176 回 |
| インフラ | IaC の検査 | 変更のたび（plan の段階） | 第 176 回 |
| インフラ | CSPM（クラウドの設定の検査） | 常時、または短い間隔で | 第 176 回 |
| 配布 | SLSA、来歴、署名、SBOM | ビルドのたび、配布と取り込みのたび | 第 178 回 |

この表で、**IaC の検査と CSPM の関係**が、前の節の「作ったときの正しさ」と「動いている間の正しさ」にそのまま対応しています。IaC の検査は、テンプレートに書いた「あるべき状態」を見ます。CSPM は、クラウドの API を呼んで「今の状態」を見ます。コンソールでの手作業によるドリフトは、前者には見えず、後者にしか見えません。

基準と道具のつながりの具体例として、AWS Security Hub の CIS AWS Foundations Benchmark への対応表を見ると、たとえば CIS v5.0.0 の要件 1.3 が「[IAM.4] IAM root user access key should not exist」という自動の検査に対応づけられています。一方で、同じ表には「Not supported – manual check」と書かれた要件もあります（[AWS Security Hub](https://docs.aws.amazon.com/securityhub/latest/userguide/cis-aws-foundations-benchmark.html)）。**基準の項目のすべてが機械で確かめられるわけではなく、残りは人の手で確かめて記録を残す**ことになります。この線引きは第 181 回の証跡にもかかわります。

## 証跡に残す

最後の段は、確かめた結果を**第三者が検証できる形で残す**ことです。社内のチームが「守れています」と言うだけでは、顧客や取引先は判断できません。

この段には 3 つの部品があります。第 181 回でまとめて扱います。

- **監査ログと SIEM**: 誰が、いつ、何を、どこから行い、結果がどうだったかを集め、改ざんを検知できる形で保管し、相関させて異常を見つける
- **継続的な統制の監視**: 統制ごとに、それが働いていることを示す証拠（設定の読み取り結果、検査の結果、承認の記録）を API で集め続ける
- **第三者による評価**: SOC 2 のように、独立した監査人が統制の設計と運用を評価し、報告書を出す（[AICPA](https://www.aicpa-cima.com/topic/audit-assurance/audit-and-assurance-greater-than-soc-2)）

前の節の 3 系統の道具は、ここで**証拠の出どころ**になります。CSPM の検査結果は「クラウドの設定が基準どおりである」ことの証拠に、SCA の結果と修正の記録は「脆弱性を決めた期間内に直している」ことの証拠になります。**検査を回すことと、その記録を残すことは、別々の作業**として設計しておく必要があります。

## 攻撃面に当てはめる

第 177・179・180 回は、4 つの段のどれか 1 つではなく、**特定の攻撃面に 4 つの段をすべて当てはめる**回です。それぞれの回で、段ごとに何をするかを先に並べておきます。

| | ① リスクを洗い出す | ② 基準 | ③ 確かめ続ける | ④ 証跡 |
| --- | --- | --- | --- | --- |
| 第 177 回 シークレット | 秘密がどこを通り、どこに残るか | ASVS の V13.3（Secret Management）、CIS Controls のアカウント管理 | Git の履歴とプッシュの検査 | 失効と入れ替えの記録 |
| 第 179 回 テナントの境界 | テナント ID が届かない経路はどこか | Top 10 の A01、ASVS の認可の要件 | 越境を検出するテスト | テナントをまたいだアクセスの記録 |
| 第 180 回 ファイルの取扱い | ファイルの中身とパスと URL を、どこまで信じているか | ASVS のファイルの取扱いの章 | 展開や取り込みの検査とテスト | 取り込みの記録 |

## 段と回の対応

ここまでの話を、1 つの表にまとめます。

| 段 | 中身 | 主な基準・道具 | 回 |
| --- | --- | --- | --- |
| ① リスクを洗い出す | 何を守るか、何が起こりうるか | DFD、STRIDE、攻撃ツリー、OCTAVE | 第 174 回 |

| ③ 確かめ続ける（アプリ） | コード、依存、動いているアプリ | SAST、SCA、DAST | 第 175・176 回 |

## まとめ

- この章は、守りを 4 つの段で考える。リスクを洗い出す、基準に照らして作る、確かめ続ける、証跡に残す。下の段が上の段の前提で、上の段の結果は下の段の見直しに戻る
- 統制とは、決められた要件を満たすために置く具体的な対策のこと。統制には、確かめ方と証拠が対になる
- 脅威モデリングは 4 つの問い（何を作っているか、何がまずくなりうるか、どう対処するか、十分だったか）に答える作業。DFD で要素と信頼境界を描き、STRIDE で脅威を分類する
- STRIDE per element は、要素の種類ごとに当てはまる脅威を決めておき、問いを機械的に出す方法。攻撃ツリーは、1 つの目標を OR と AND で分解し、どこを塞げば止まるかを見る方法
- OCTAVE は、設計図ではなく組織にとって重要な情報と業務から出発してリスクを評価する。STRIDE と組み合わせて、優先度の高い情報を扱うシステムを細かく点検する使い方ができる
- 基準はアプリとインフラで辞書が分かれる。アプリは OWASP（Top 10 が分類、ASVS が検証できる要件、CWE が欠陥の種類の名前）、インフラは CIS（Benchmarks が製品ごとの設定、Controls が組織の対策の優先順位）
- 作ったときの正しさは、ドリフト、新しい脆弱性の公表、基準の更新によって崩れる。だから一度の検査ではなく、確かめ続ける仕組みが要る
- 確かめる道具は、アプリ（SAST、SCA、DAST）、インフラ（IaC の検査、CSPM）、配布（SLSA、SBOM、来歴）の 3 系統。IaC の検査はあるべき状態を、CSPM は今の状態を見る
- 基準の項目のすべてが機械で確かめられるわけではない。確かめた結果は、第三者が検証できる証跡として別に残す
