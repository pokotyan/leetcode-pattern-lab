## すべてが 1 本のスレッドに乗っている

前回、合成はコンポジタスレッドで動くと書きました。裏を返せば、それ以外はほぼすべて **メインスレッド**という 1 本のスレッドの上で動いています。

- JavaScript の実行
- クリックやキー入力のイベント処理
- DOM の書き換え
- スタイル、レイアウト、ペイント（第 71 回の ①〜③）

なぜ 1 本なのか。DOM は、複数のスレッドから同時に触ることを前提に作られていないからです。第 37 回で見たとおり、共有するものを複数のスレッドから書き換えるにはロックが必要で、それは遅く、間違えやすい。ブラウザは「DOM に触れるのは 1 本のスレッドだけ」と決めることで、この問題をまるごと避けました。

代わりに、そのスレッドの上で**誰がいつ動くのか**を決める仕組みが必要になります。それがイベントループです。

## 形は第 45 回と同じ

第 45 回で見たイベントループは、こういう形でした。

```
while (1) {
    events = epoll_wait(...)       // 準備できたものを取る
    for (ev in events) handlers[ev.fd](ev)
}
```

ブラウザのイベントループも骨格は同じです。違うのは、**描画という特別な仕事が、ループの中の決まった位置に組み込まれている**ことです。HTML の仕様が定めている処理の流れを、要点だけ抜き出すとこうなります（[HTML Living Standard](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model)）。

```
while (true) {
    task = いずれかのタスクキューから、最も古い実行可能なタスク
    task を実行する                         // 例: クリックのハンドラ、setTimeout のコールバック
    マイクロタスクキューが空になるまで実行する  // Promise の then など

    if (描画の機会が来ていれば) {
        resize / scroll のイベント、メディアクエリ、アニメーションを進める
        requestAnimationFrame のコールバックを実行する
        スタイルとレイアウトを計算する
        ResizeObserver、IntersectionObserver に通知する
        描画を更新する（ペイントして、合成に渡す）
    }
}
```

**1 周で実行するタスクは 1 つだけ**。そのあとマイクロタスクを全部片付け、描画の機会が来ていれば描画する。これが基本の形です。

<Callout type="note" title="どのキューから取るかは、ブラウザが決める">
  タスクキューは 1 本ではありません。入力イベント、タイマ、ネットワーク、といった発生源ごとに分かれていて、
  仕様は「どのキューから取るかは実装が決める」としています。
  ブラウザはこれを使って、**入力のキューを優先する**といった調整をしています。
  第 36 回で見た、対話的な処理を待たせないためのスケジューラの工夫と同じ方向の考え方です。
</Callout>

## タスクとマイクロタスク

キューには 2 種類あります。

| | タスク（マクロタスク） | マイクロタスク |
| --- | --- | --- |
| 例 | イベントハンドラ、`setTimeout`、`setInterval`、`postMessage` の受信 | `Promise` の `then` / `await` の続き、`queueMicrotask`、`MutationObserver` |
| 1 周で実行する数 | **1 つ** | **キューが空になるまで全部** |
| 描画を挟めるか | タスクとタスクの間で描画できる | マイクロタスクの途中では描画されない |

違いは実行の順番に現れます。

```js
console.log('1')
setTimeout(() => console.log('4'), 0)
Promise.resolve().then(() => console.log('3'))
console.log('2')
// 出力: 1 2 3 4
```

スクリプト全体が 1 つのタスクです。`1` と `2` を出し終えてタスクが終わると、マイクロタスクの `3` が**すぐに**実行されます。`setTimeout` の `4` は別のタスクなので、次の周（場合によっては描画を挟んだ後）まで待ちます。遅延 0 を指定しても、今のタスクの中には割り込めません。

<Callout type="warn" title="マイクロタスクは描画を止められる">
  マイクロタスクは「空になるまで全部」実行されます。マイクロタスクの中で次のマイクロタスクを積み続けると、
  ループは描画の段に進めず、**ページが固まります**。

  ```js
  function loop() { Promise.resolve().then(loop) }   // 描画も入力も永遠に来ない
  loop()
  ```

  同じことを `setTimeout(loop, 0)` で書けば、1 周ごとに描画や入力を挟めるので固まりません。
  **処理を分割するなら、マイクロタスクではなくタスクで区切る**必要があります。
</Callout>

## requestAnimationFrame: 描画の直前に呼んでもらう

アニメーションを JavaScript で動かすとき、`setTimeout(step, 16)` で 16ms ごとに呼ぶ方法は、うまくいきません。

- 第 82 回で見たとおり、タイマは指定どおりの時刻には起きない。少しずつずれる
- ずれた結果、1 フレームに 2 回呼ばれたり、1 回も呼ばれなかったりする
- 画面が見えていないタブでも動き続けて、電力を無駄にする

`requestAnimationFrame(step)` は、「**次の描画の直前**に呼んでほしい」という依頼です。上の疑似コードのとおり、描画の機会が来たときに、スタイルとレイアウトの計算より前に実行されます。

```js
function step(timestamp) {
  box.style.transform = `translateX(${(timestamp / 10) % 500}px)`
  requestAnimationFrame(step)
}
requestAnimationFrame(step)
```

こうすれば、1 フレームに 1 回、ちょうど描画に間に合う位置で DOM を書き換えられます。書き換えた結果は、すぐ後のスタイルとレイアウトでまとめて計算されるので、第 71 回のダーティフラグとも噛み合います。タブが見えていなければ、呼び出しの頻度は大きく下げられます。

## 長いタスクが、入力を止める

イベントループは 1 周に 1 タスクです。つまり、**実行中のタスクが終わるまで、次のタスクも描画も始まりません**。

クリックのハンドラが 300ms かかる処理をしていると、その間に来たキー入力はキューで待たされ、画面も更新されません。利用者から見ると、ページが固まっています。

```
時間 →
メイン │■■■■■■■■■■■■■■■■■■■■■■■■■■■■│ クリック処理（300ms）
入力   │   ↑キー入力が届く（待たされる）              │→ ここでやっと処理
描画   │    ×     ×     ×     ×     ×     ×          │→ ここでやっと描画
            （16.7ms ごとの描画の機会をすべて逃す）
```

W3C の Long Tasks の仕様は、**50ms を超えるもの**を長いタスクと定義しています（[Long Tasks API](https://w3c.github.io/longtasks/)）。根拠として、利用者の入力には 100ms 以内に応答すべきだという目安を挙げています。入力が来たとき実行中のタスクが最大 50ms、入力の処理自体に 50ms、合わせて 100ms に収める、という計算です。

対策は 2 つしかありません。

1. **分割する**: 長い処理を小さな塊に分け、塊の間でタスクとして区切る（`setTimeout` などで次の周に回す）。その隙間に入力と描画が入れる
2. **よそに逃がす**: メインスレッドから別のスレッドへ移す。次の Web Worker

第 45 回で「イベントループのコールバックで長い処理をしてはいけない」と書いたのと、まったく同じ話です。サーバでは待たされるのが他の接続、ブラウザでは待たされるのが利用者の指です。

## Web Worker: DOM に触れない別のスレッド

**Web Worker** は、メインスレッドとは別のスレッドで JavaScript を動かす仕組みです。Worker は自分専用のイベントループを持ちます。

ただし、Worker からは **DOM に触れません**。DOM に触れるのはメインスレッドだけ、という決まりを守るためです。やり取りは `postMessage` によるメッセージだけです。

```js
// メインスレッド
const worker = new Worker('heavy.js')
worker.postMessage({ data: bigArray })
worker.onmessage = (e) => render(e.data)   // 結果だけ受け取って、DOM はこちらで触る

// heavy.js（Worker）
onmessage = (e) => postMessage(compute(e.data))
```

`postMessage` で渡した値は、既定では**複製**されます（structured clone）。送り手と受け手が同じオブジェクトを共有しないので、ロックが要りません。第 40 回で見た「共有せず、メッセージで渡す」設計そのものです。

大きなデータで複製が重いときは、`ArrayBuffer` を**移譲**できます。所有権ごと相手に渡し、送り手の側では使えなくなります。コピーは起きません。

<Callout type="note" title="SharedArrayBuffer と Spectre">
  本当にメモリを共有したい場合のために `SharedArrayBuffer` があります。
  `Atomics` と組み合わせれば、第 37・38 回で見たアトミック操作とメモリモデルの世界をブラウザで使えます。

  ただし、共有メモリは高精度のタイマとしても使えるため、2018 年初めに Spectre を受けて事実上無効化されました。
  現在は、ページが **クロスオリジン分離**（COOP と COEP のヘッダで、他のオリジンの資源と同じプロセスに載らないことを保証した状態）
  になっているときだけ使えます（[MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)）。
  第 69 回のサイト分離と同じ脅威への、もう 1 つの対策です。
</Callout>

## 開発者ツールで見る

Performance パネルで記録すると、メインスレッドの各タスクが横に並び、50ms を超えたタスクの右上には赤い三角の印が付きます。

- 赤い印の付いたタスクの中身を展開すれば、どの関数が時間を使ったかが分かる
- タスクの後ろに Recalculate Style と Layout が何度も挟まっていれば、第 71 回のレイアウトスラッシング
- 入力のイベントが、前のタスクの終わりまで待たされていれば、分割か Worker への移動が必要

## まとめ

- DOM に触れるのはメインスレッドだけ。JavaScript、イベント、スタイル・レイアウト・ペイントは 1 本のスレッドを取り合う
- イベントループは 1 周に 1 タスクを実行し、マイクロタスクを空になるまで実行し、描画の機会が来ていれば描画する
- `Promise` の続きはマイクロタスク、`setTimeout` やイベントはタスク。マイクロタスクを積み続けると描画が止まる
- `requestAnimationFrame` は、次の描画の直前に呼ばれる。アニメーションはタイマではなくこちらで動かす
- 50ms を超えるタスクは長いタスク。その間、入力も描画も待たされる。分割するか、Worker に逃がす
- Worker は DOM に触れず、メッセージの複製や移譲でやり取りする。共有メモリはクロスオリジン分離のときだけ使える
