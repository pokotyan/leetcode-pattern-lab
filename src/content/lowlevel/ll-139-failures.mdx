## 壊れたのはどの部品か

第 103 回から第 138 回まで、部品を 1 つずつ取り出し、何を保証し何を保証しないかを分けてきました。最後の回では逆向きに、**実際に起きた障害と事件**から部品を眺めます。

先に結論を言うと、ここで取り上げる事例のほとんどで、**AES も ECDSA も SHA-256 も破られていません**。壊れたのは、次のようなつなぎ目です。

- 暗号ライブラリの中の、長さを 1 つ確かめ忘れたコード
- 証明書を更新する手順と、それを本番に届ける手順の間
- 検証する側の時計と、発行する側の時計の間
- 鍵を公開する側と、それをキャッシュする側の間
- 鍵と、その鍵が署名してよい範囲の間
- 多要素認証と、その結果を持ち越すセッションの間

各事例について、**何が起きたか**、**どの部品とどの部品の組み合わせで起きたか**、**教訓**の順で書きます。出典は事後報告、公式の発表、CVE、米国の Cyber Safety Review Board（CSRB）の報告書など、当事者か公的機関の一次資料に限りました。確かめられなかった数字や経緯は書いていません。

| 事例 | 年 | 壊れたつなぎ目 | 呼び戻す回 |
| --- | --- | --- | --- |
| Heartbleed | 2014 | TLS の拡張 × C のメモリ × 秘密鍵 | 第 106、110、112、113 回 |
| Azure Storage の証明書切れ | 2013 | 証明書の更新 × 配備の優先順位 | 第 110、112 回 |
| Ericsson の SGSN-MME | 2018 | 製品に埋め込まれた証明書 × 期限 | 第 110 回 |
| 時計のずれ（手元で再現） | ― | 時計 × exp / nbf / notBefore | 第 110、128、158 回 |
| Azure AD の認証停止 | 2021 | 鍵の削除 × メタデータのキャッシュ | 第 128、130、136 回 |
| Storm-0558 | 2023 | 盗まれた署名鍵 × 鍵の範囲の検証漏れ | 第 107、109、128、130 回 |
| Psychic Signatures | 2022 | 署名の検証の実装 | 第 107、128 回 |
| CircleCI、Okta | 2023 | 多要素認証 × 盗めるセッション | 第 126、127、131 回 |

## Heartbleed（2014）: 長さの確認 1 つが秘密鍵を漏らした

### 何が起きたか

2014 年 4 月 7 日、OpenSSL は TLS の heartbeat 拡張の処理に境界の確認が欠けていたことを公表しました（[OpenSSL Security Advisory](https://openssl-library.org/news/secadv/20140407.txt)、[CVE-2014-0160](https://nvd.nist.gov/vuln/detail/CVE-2014-0160)）。heartbeat は「このバイト列をそのまま返して」と頼んで接続が生きているかを確かめる仕組みで、要求には**返してほしい長さ**と**中身**が入っています。OpenSSL は、書かれた長さが実際の中身より長くても確かめずに、その長さの分だけメモリを写して返していました。

```
要求:  長さ = 65535、中身 = "A"（1 バイト）
応答:  "A" + その後ろにあったメモリ 65534 バイト
```

勧告によれば、1 回で**最大 64KB のメモリ**が、接続した相手（クライアントでもサーバでもよい）に漏れます。影響したのは OpenSSL 1.0.1 から 1.0.1f と 1.0.2-beta で、1.0.1g で直りました。発見者のサイトは、欠陥が 2012 年 3 月の 1.0.1 から 2 年あまり出荷されていたこと、そして**悪用してもログに異常が残らない**ことを書いています（[heartbleed.com](https://heartbleed.com/)）。

漏れるメモリに何が入っているかは運次第です。そこで Cloudflare は、脆弱な版の OpenSSL を使う nginx のサーバを公開し、秘密鍵を取り出せるか試してもらいました。公開したその日のうちに、外部の人が**サーバの秘密鍵を取り出す**ことに成功しています（[Cloudflare](https://blog.cloudflare.com/the-results-of-the-cloudflare-challenge/)）。

### どの部品の組み合わせで起きたか

暗号のアルゴリズムは何も破られていません。壊れたのは、次の組み合わせです。

- **C で書かれたライブラリ**が、相手の書いた長さを信じてメモリを読んだ
- そのプロセスのメモリに、**TLS の秘密鍵**（第 110 回で見た、証明書と対になる鍵）、利用者のパスワード、セッションの Cookie が同居していた
- 秘密鍵が漏れれば、攻撃者はそのサーバになりすませる。さらに、**RSA 鍵交換**（第 106 回）で結んだ過去の通信を記録していれば、それも復号できる。ECDHE で前方秘匿性があれば、過去の通信は守られる

修正版に入れ替えるだけでは終わりません。heartbleed.com が挙げる後始末は、鍵の失効と証明書の再発行、パスワードの変更、セッションと Cookie の無効化です。ここで第 112 回の問題が出てきます。**失効させた証明書を、クライアントがきちんと確かめてくれるとは限らない**のでした。

### 教訓

- 暗号ライブラリの**メモリ安全性**は、暗号の強さと同じくらい重要。秘密鍵を同じプロセスのメモリに置いている限り、そのプロセスのどこかの欠陥が鍵の漏洩になる。第 109 回の「取り出せない場所（HSM、KMS）に鍵を置く」価値はここにある
- 前方秘匿性は、鍵が漏れたときの被害を「これから」に限る。TLS 1.3 が ECDHE だけにした理由の 1 つ（第 113 回）
- 秘密鍵が漏れたかもしれないときの手順（失効、再発行、全セッションの無効化）は、事前に決めておかないと、その日に決めることになる

## 証明書の期限切れ: 通知は届いていた

### Azure Storage（2013）

2013 年 2 月 22 日、Windows Azure Storage の HTTPS が世界中で使えなくなりました。blob、queue、table の 3 種類のワイルドカード証明書が、**全リージョン共通で、3 分ほどの間に相次いで**期限を迎えたためです。事後報告は、直接の原因は期限切れだが、**根本原因は証明書を保守し監視する手順の破綻**だったと書いています（[Windows Azure Blog の事後報告（アーカイブ）](https://web.archive.org/web/2013/http://blogs.msdn.com/b/windowsazure/archive/2013/03/01/details-of-the-february-22nd-2013-windows-azure-storage-disruption.aspx)）。

経緯は、どこにでもありそうなものです。

```
180 日前から    秘密情報の保管サービスが、期限の接近をチームに通知
1 月 7 日       チームは新しい証明書を保管サービスに登録し、次のリリースに含めた
               ─ ただし、そのリリースに「証明書の更新を含む」印を付け忘れた
その後          リリースは、優先度の高い他の更新の後ろに回された
               ─ 保管サービス上はすでに更新済みなので、追加の警告は出なかった
2 月 22 日      古い証明書のまま期限を迎える
```

**更新した**という記録と、**本番で使われている**という事実が分かれていました。監視は保管サービスの中身を見ていて、実際に客に提示されている証明書を見ていなかったわけです。3 種類の証明書が全リージョンで同じで、期限も数分しか違わなかったことも、報告書は単一障害点として挙げています。

### Ericsson の SGSN-MME（2018）

2018 年 12 月 6 日、Ericsson は、移動体通信のコアネットワークの装置 SGSN-MME の特定の 2 つのソフトウェア版で障害が起き、複数の国の顧客に影響したと発表しました。初期の原因分析は、**ソフトウェアに入っていた証明書の期限切れ**です（[Ericsson](https://www.ericsson.com/en/press-releases/2018/12/update-on-software-issue-impacting-certain-customers)）。証明書は Web サーバだけのものではなく、**製品の中に埋め込まれて出荷され、誰も期限を覚えていない**ことがあります。

### Let's Encrypt のルート（2021）

第 111 回で見た DST Root CA X3 の期限切れも、この系列です。ただし性質は違います。期限は何年も前から告知されていて、Let's Encrypt も手を打っていました。それでも失敗したのは、**クライアントのトラストストアとチェーン組み立ての実装**（OpenSSL 1.0.2 など）という、サーバの運用者からは見えない部品の差でした。

### 教訓

- 監視するのは「更新したか」ではなく、**外から接続して実際に提示される証明書の期限**
- 全部の場所で同じ証明書・同じ期限にしない。更新の失敗が全体の停止になる
- 更新を自動化し（第 112 回の ACME）、**期間を短くして頻繁に更新する**ほうが、手順は錆びない。年に 1 回の手作業は、毎回初めての作業になる

<Callout type="warn" title="よくある誤解: 期限は分かっているのだから、証明書切れは防げる">
  上の 3 件とも、期限そのものは事前に分かっていました。Azure の事例では通知も届いていました。
  防げなかったのは、**更新した証明書が、実際に使われる場所まで届いたか**を誰も確かめていなかったからです。
  期限を知っていることと、期限切れを防げることの間には、配備と監視という別の部品が挟まっています。
</Callout>

## 時計がずれると、正しいものが拒まれる

証明書の notBefore / notAfter（第 110 回）も、JWT の `exp` / `nbf` / `iat`（第 128 回）も、TOTP の 30 秒の窓（第 126 回）も、**検証する側の時計**で判定します。時計はずれます（第 158 回で詳しく見ます）。起動直後に NTP で合わせる前の機器、仮想マシンの復帰直後、電池の切れた装置の時計は、何年も前を指していることがあります。

これは特定の事件というより、**毎日どこかで起きている障害の型**です。手元で再現します。

### 手元で確かめる 1: 証明書

自前の CA で、今この瞬間から 90 日間有効なサーバ証明書を作り、`openssl verify -attime` で検証する側の時計をずらします（OpenSSL 3.6.2）。

```
$ openssl x509 -in srv.crt -noout -dates
notBefore=Sep 28 10:56:12 2026 GMT
notAfter=Dec 27 10:56:12 2026 GMT

$ openssl verify -CAfile ca.crt srv.crt
srv.crt: OK

$ openssl verify -CAfile ca.crt -attime $((now-300)) srv.crt      # 時計が 5 分遅れている
error 9 at 0 depth lookup: certificate is not yet valid or the system clock is incorrect

$ openssl verify -CAfile ca.crt -attime $((now+91*86400)) srv.crt  # 時計が 91 日進んでいる
error 10 at 0 depth lookup: certificate has expired
```

**発行した直後の証明書**と、**時計が数分遅れた端末**の組み合わせで、正しい証明書が拒まれます。OpenSSL のメッセージが「or the system clock is incorrect」と添えているのは、この組み合わせがそれほどよくあるからです。第 114 回の切り分けの表で、`not yet valid` を見たら端末の `date` を見る、としたのはこのためです。

### 手元で確かめる 2: JWT

PyJWT 2.15 で、発行する側（IdP）の時計だけをずらして 5 分有効のトークンを作り、正しい時計の受け取り側で `leeway`（許容するずれ）を変えて検証しました。

```
IdP の時計が 2 分進んでいる   leeway=0    ImmatureSignatureError: The token is not yet valid (iat)
IdP の時計が 2 分進んでいる   leeway=30   ImmatureSignatureError: The token is not yet valid (iat)
IdP の時計が 2 分進んでいる   leeway=180  OK
IdP の時計が 7 分遅れている   leeway=0    ExpiredSignatureError: Signature has expired
IdP の時計が 7 分遅れている   leeway=30   ExpiredSignatureError: Signature has expired
IdP の時計が 7 分遅れている   leeway=180  OK
```

署名は正しく、`iss` も `aud` も合っています。それでも**時刻の判定だけで**拒まれます。`leeway` を広げれば通りますが、それは期限切れのトークンを長く受け入れることでもあります。RFC 7519 が猶予を「通常は数分以内」としているのは、この取引の落としどころです（第 128 回）。

### 教訓

- 時刻を使う検証（証明書、JWT、TOTP、Kerberos、SAML の NotOnOrAfter）は、**発行側と検証側の時計の一致**という、暗号の外の前提に立っている
- 時計の同期（NTP、第 158 回）は、認証基盤の依存関係の一部として監視する
- 許容するずれは小さく保ち、エラーメッセージで「期限」と「時計」を見分けられるようにしておく

## 鍵を消す順番を誤る: Azure AD（2021）

### 何が起きたか

2021 年 3 月 15 日 19:00 UTC ごろから、Azure AD に認証を頼るマイクロソフトと他社のアプリで、認証のエラーが続きました。マイクロソフトの初期の分析によれば、原因は **OpenID Connect などで使う署名鍵のローテーションの誤り**です（[Microsoft Q&A の公式通知](https://learn.microsoft.com/en-us/answers/questions/315440/notification-authentication-errors-across-multiple)）。

- 使われなくなった鍵は、自動化された仕組みが時間の予定に沿って削除する
- ある鍵は、クラウドをまたぐ移行のために、通常より長く **「保持（retain）」の印**が付けられていた
- 自動化の不具合で、その印が無視され、**まだ使われている鍵が削除された**

鍵のメタデータは 21:05 UTC に元へ戻されました。しかし通知は、**アプリが戻されたメタデータを取り込み、キャッシュを正しい内容で更新する必要がある**と書き、復旧までの時間はキャッシュの扱いの違いでアプリごとに異なったとしています。Azure Storage の一部では古いメタデータのキャッシュを強制的に無効にする更新を配り、残った影響の解消を宣言したのは翌 16 日の 09:25 UTC でした。

### どの部品の組み合わせで起きたか

第 128 回で見た JWKS のローテーションの手順を思い出してください。

```
1. 新しい鍵を JWKS に足す  2. キャッシュが入れ替わるのを待つ  3. 新しい鍵で署名し始める
4. 古い鍵のトークンが期限切れになるのを待つ                   5. 古い鍵を JWKS から外す
```

この事故は、手順 5 を**まだ署名に使っている鍵に対して**行ってしまったものです。そして、戻すときにも**受け取る側のキャッシュ**が効いてきます。鍵を外したときの JWKS をキャッシュした受け取り側は、発行者が元に戻しても、キャッシュが切れるまで失敗し続けます。

### 手元で確かめる 3: JWKS のキャッシュ

発行者（IdP）と、JWKS をキャッシュする 2 つの受け取り側（RP）の模型を PyJWT で作りました。RP-A はある時点で JWKS を取り直し、RP-B は最初に取った JWKS を持ち続けます。

```
[0] 平常時
  RP-A: OK (kid=k1)
  RP-B: OK (kid=k1)
[1] 使用中の k1 を JWKS から外す（署名は k1 のまま）
  RP-A: 失敗 (kid=k1 がキャッシュに無い) ← JWKS を取り直した RP
  RP-B: OK (kid=k1) ← 古いキャッシュを持つ RP
[2] JWKS を元に戻す
  RP-A: 失敗 (kid=k1 がキャッシュに無い) ← [1] の JWKS をキャッシュしたまま
  RP-A: OK (kid=k1) ← キャッシュを捨てて取り直した後
[3] 順序を誤ったローテーション: k2 を公開する前に k2 で署名し始める
  RP-B: 失敗 (kid=k2 がキャッシュに無い)
  RP-B: 失敗 (kid=k2 がキャッシュに無い) ← k2 を公開した後も、キャッシュが古いまま
```

同じ変更でも、**いつ JWKS を取ったか**によって RP ごとに結果が分かれます。[1] では取り直した RP だけが壊れ、[2] では元に戻したのに壊れたままです。障害の最中に「うちでは再現しない」「戻したのに直らない」という報告が入り交じるのは、このためです。

実際の RP の多くは、知らない `kid` が来たら JWKS を取り直します。[3] はそれで救えますが、[1] のように**鍵が JWKS から消えた**場合は、取り直しても救えません。取り直しの回数に上限を設けるべきことも、第 128 回で見ました。

### 教訓

- 鍵のローテーションは、発行者だけで完結しない。**受け取る側のキャッシュの寿命**を含めた分散した手順として設計する
- 「消す」操作は最も危険な段階。消してよい条件（その鍵で署名されたトークンがもう残っていない）を、印ではなく実際の使用状況で確かめる
- IdP が止まると、それに頼る全部のアプリのログインが止まる。第 136 回で見た「IdP を自分で持つと引き受けるもの」の中で、可用性はこの規模で効いてくる

## Storm-0558（2023）: 鍵は本物、範囲の確認が抜けていた

### 何が起きたか

2023 年 6 月、米国務省のセキュリティ担当者が、Exchange Online のメールボックスへのアクセスを記録するログ（MailItemsAccessed）に基づく独自の警告規則で、異常なアクセスに気づき、16 日にマイクロソフトへ知らせました。調べると、攻撃者は**マイクロソフトの署名鍵で自分でトークンを作って**いました。CSRB の報告書によれば、その鍵は次のようなものでした（[CSRB 報告書](https://www.cisa.gov/sites/default/files/2025-03/CSRBReviewOfTheSummer2023MEOIntrusion508.pdf)、[CISA](https://www.cisa.gov/resources-tools/resources/CSRB-Review-Summer-2023-MEO-Intrusion)）。

- **2016 年に作られた、一般消費者向けアカウント（MSA）の署名鍵**だった
- この鍵は、消費者向けの Outlook のトークンにしか署名できないはずで、**企業向けの Exchange Online では使えないはず**だった
- 2021 年 3 月に廃止される予定だったが、消費者向けの鍵の仕組みを堅くする作業が難航して遅れていた
- 消費者向けの鍵は手作業でまれにしか交換されず、2021 年に**手作業のローテーションに関連した大規模なクラウド障害**が起きたあと、交換そのものが止まっていた。有効な鍵の古さを知らせる警告も無かった

攻撃者は、この鍵で作ったトークンで、22 の組織のメールアカウントと、503 の個人アカウントにアクセスしました。

**なぜ企業向けのメールが、消費者向けの鍵で署名されたトークンを受け入れたのか。** マイクロソフトの 2023 年 9 月の報告によれば、2018 年 9 月に、消費者向けと企業向けの両方の鍵をまとめて公開する**共通の鍵メタデータのエンドポイント**を用意しました。ところが、どの鍵をどの種類のアカウントに使うべきかを確かめる検証ライブラリは、その範囲の確認を自動で行うように更新されませんでした。メールの開発者は**ライブラリが完全な検証をしてくれると思い込み**、発行者と範囲の確認を自分で足していませんでした（[MSRC](https://www.microsoft.com/en-us/msrc/blog/2023/09/results-of-major-technical-investigations-for-storm-0558-key-acquisition)）。CSRB も、SDK が共通のエンドポイントの中で消費者向けと企業向けの鍵を区別するよう十分に更新されていなかったと書いています。

**鍵がどう盗まれたのか**は、分かっていません。マイクロソフトは 2023 年 9 月の報告で、クラッシュダンプに紛れ込んだ鍵が持ち出された可能性が最も高いとしましたが、2024 年 3 月 12 日にこの記述を改め、鍵を含むクラッシュダンプそのものは見つかっていないと認めています。CSRB は、報告書をまとめた時点でもマイクロソフトは鍵の入手経路を示せていないと書き、この侵入は**防げたはずのもので、一連のセキュリティの失敗の連鎖**によるものだと結論づけました。

### どの部品の組み合わせで起きたか

```
署名鍵（第 107 回）   ── 2016 年の消費者用の鍵が、何年も交換されずに生きていた（第 109 回）
      ×
JWKS / Discovery    ── 消費者用と企業用の鍵を 1 つの場所で公開した（第 128、130 回）
      ×
検証の実装          ── 「JWKS のどれかの鍵で署名が通ればよい」で止まり、
                       その鍵がこの発行者・この用途の鍵かを確かめなかった
```

**署名の検証は成功していました**。第 107 回で強調したとおり、署名が保証するのは「この鍵で署名された」ことだけで、**その鍵がこのトークンを発行してよい者の鍵か**は別に確かめなければなりません。第 130 回で見た「利用者は `iss` と `sub` の組で指す」という原則も、`iss` がその鍵の持ち主と結び付いていて初めて意味を持ちます。

### 手元で確かめる 4: 鍵の範囲を確かめない検証

仕組みを単純化した模型で、この構造を再現します。共通の JWKS に、消費者用の鍵 `c-2016` と企業用の鍵 `e-2023` を載せます（鍵ごとの `owner` という欄は、説明のために作った架空のものです）。攻撃者は `c-2016` の秘密鍵を持っていて、企業テナントの発行者を名乗るトークンを作ります。

```
署名が JWKS のどれかで通れば良しとする: 受理: sub=alice@corp.example iss=https://login.example/tenant-123
鍵とその持ち主（発行者）を突き合わせる:   拒否: 鍵 c-2016 は consumer 用で、企業テナントの発行者 https://login.example/tenant-123 の鍵ではない
```

署名の検算も `aud` も `exp` も正しく通ります。欠けているのは**鍵と発行者の対応**だけです。第 128 回の「鍵、アルゴリズム、発行者、受け取り手は、すべて検証する側があらかじめ知っている値と突き合わせる」の、「鍵」と「発行者」を別々に突き合わせて、その**組**を突き合わせていない状態です。

### 教訓

- 検証は「署名が正しいか」と「その鍵がこの用途に許されているか」の 2 段。後者は、ライブラリがしてくれると思い込みやすい
- 信頼の範囲が違う鍵を、同じ入れ物（JWKS、トラストストア）に入れると、範囲の区別は検証する側の実装に押し付けられる。第 111 回の Name Constraints は、証明書の世界でこの範囲を鍵の側に書く仕組みだった
- 署名鍵は交換してこそ被害が限られる（第 109 回）。「前回の交換で障害が起きたから止める」は、次の事故の種になる。Azure AD の事例とこの事例は、同じ年に交換の難しさの両面を見せている

<Callout type="warn" title="よくある誤解: 署名の検証に成功したのだから、トークンは本物だ">
  Storm-0558 のトークンは、マイクロソフトの本物の鍵で署名されていました。検証は正しく成功しています。
  それでも偽物だったのは、**その鍵がそのトークンを発行する権限を持っていなかった**からです。
  「本物の鍵で署名された」と「正当な発行者が発行した」は、鍵と発行者と用途の対応を確かめて初めて同じ意味になります。
</Callout>

## 検証の実装そのものが壊れる: Psychic Signatures（2022）

Storm-0558 は「検証は正しいが、確かめる範囲が足りなかった」事例でした。検証の実装そのものが壊れていた例もあります。

2022 年 4 月、Neil Madden は、Java 15 から 18 の ECDSA の署名検証が、**r と s がどちらも 0 の署名**を、どんな公開鍵・どんなメッセージに対しても有効と判定することを公表しました（[Neil Madden](https://neilmadden.blog/2022/04/19/psychic-signatures-in-java/)、CVE-2022-21449）。ECDSA の検証（第 107 回）では、最初に r と s が 1 以上であることを確かめる決まりですが、それが抜けていました。2022 年 4 月の Oracle の定例の修正で直されています（[Oracle CPU April 2022](https://www.oracle.com/security-alerts/cpuapr2022.html)）。

影響の範囲として挙げられているのは、TLS の証明書とハンドシェイク、署名付き JWT、SAML のアサーション、OIDC の ID トークン、WebAuthn の認証メッセージです。**第 17〜20 章のほとんどの部品**が、この 1 つの関数に乗っていたことになります。

原因は、Java 15 で楕円曲線のコードを**ネイティブの C++ から Java に書き直した**ことでした。第 128 回の `alg: none` や RS256 と HS256 の取り違えが「トークンに検証の方法を決めさせた」誤りだったのに対し、こちらは**正しい方法を選んでも、その実装が間違っていた**誤りです。

教訓は、暗号の実装はまれな入力（0、無限遠点、長さ 0、範囲外の値）で壊れるということ、そして**検証を通るべきでない入力で検証が失敗することを確かめるテスト**が、通るべき入力のテストと同じくらい必要だということです。第 107 回の手元の節で、改ざんした署名が失敗するのを確かめたのは、この種の確認でした。

## 盗まれたセッションは、多要素認証を素通りする

第 126 回で、多要素認証は**ログインの瞬間**を守るものだと見ました。ログインの結果は、第 127 回のセッションや第 128 回のトークンとして持ち越されます。その持ち越された結果を盗まれると、多要素認証はもう関係ありません。

### CircleCI（2023）

CircleCI の事後報告によれば、2022 年 12 月 16 日、従業員のノート PC にマルウェアが入り、ウイルス対策ソフトは検知しませんでした。マルウェアは**セッション Cookie を盗み**、攻撃者は別の場所からその従業員になりすまして本番の一部に入りました。報告は、盗まれたのが **2FA で守られた SSO のセッション**だったと明記しています。攻撃者は顧客の環境変数、トークン、鍵を含むデータを持ち出し、保存時には暗号化されていたものの、**動いているプロセスから暗号鍵を取り出して**いました。顧客からの GitHub の OAuth に関する不審な動きの通報で 12 月 29 日に気づき、報告は顧客にすべての秘密情報の交換を求めました（[CircleCI](https://circleci.com/blog/jan-4-2023-incident-report/)）。

### Okta のサポートシステム（2023）

Okta の根本原因の報告によれば、2023 年 9 月 28 日から 10 月 17 日にかけて、攻撃者は Okta の顧客サポートのシステムに入り、134 の顧客に関係するファイルにアクセスしました。その一部は **HAR ファイル**（ブラウザの開発者ツールが書き出す、通信の記録）で、**セッショントークン**が含まれていました。攻撃者はそれを使い、5 つの顧客の正規のセッションを乗っ取りました。侵入に使われたのはサポートシステムのサービスアカウントの認証情報で、従業員が会社の PC の Chrome で個人の Google プロファイルにログインしていたため、その認証情報が個人のアカウント側に保存されていたとされます。Okta は対策の 1 つとして、**管理者のセッショントークンをネットワークの位置に結び付ける**仕組みを入れました（[Okta](https://sec.okta.com/articles/2023/11/unauthorized-access-oktas-support-case-management-system-root-cause)）。

### どの部品の組み合わせで起きたか

```
多要素認証（第 126 回）    ── ログインの瞬間だけを守る
      ×
セッション / トークン（第 127、128 回）── ベアラ: 持っている人が使える（第 131 回）
      ×
トークンが置かれた場所    ── 端末のブラウザ、障害調査のために顧客が送った HAR ファイル
```

HAR ファイルの事例は、トークンの置き場所が「ブラウザのどこか」だけでは済まないことを示しています。調査のために通信を記録すれば、その記録にも Cookie や `Authorization` ヘッダが入ります。第 109 回で見た「秘密情報はログから漏れる」の、利用者の側で起きた形です。

### 教訓

- ベアラトークンとセッション Cookie は、**盗まれた時点で本人になれる**。第 131 回の DPoP や mTLS による束縛、Okta が入れたネットワークの位置への束縛は、盗まれたものを別の場所で使えなくする工夫
- セッションの寿命（第 127 回）と、重要な操作の前のステップアップ認証（第 131 回）は、盗まれた後の被害の時間と範囲を縛る
- 通信の記録（HAR、トレース、ログ）は秘密情報を含む前提で扱う。提出前にトークンを消す、受け取った側は保存しない
- 保存時の暗号化は、**鍵が同じ場所で動いているプロセスの中にあれば**、そのプロセスに入った攻撃者を止めない（第 109 回のエンベロープ暗号化と KMS の意味）

<Callout type="warn" title="よくある誤解: 多要素認証を入れたので、アカウントは乗っ取られない">
  CircleCI の事例で盗まれたのは、2FA で守られた SSO のセッションでした。多要素認証は正しく働いていて、ログインの瞬間は本人でした。
  多要素認証が守るのは**認証の瞬間**です。その結果を運ぶセッションやトークンは別の部品で、盗まれれば多要素認証を通り直す必要はありません。
  第 126 回のフィッシング耐性のある認証（パスキー）も、ログイン後に盗まれたセッションは守りません。
</Callout>

## 事例を横に並べる

| 事例 | 正しく動いていた部品 | 前提にしていたこと | 実際 |
| --- | --- | --- | --- |
| Heartbleed | TLS の暗号、証明書 | ライブラリが秘密鍵をメモリの外に漏らさない | 境界の確認 1 つで漏れた |
| Azure Storage | 保管サービス、通知 | 更新した証明書は本番に届いている | 配備が後回しにされていた |
| 時計のずれ | 署名、証明書 | 検証側と発行側の時計が合っている | 起動直後や復帰直後はずれる |
| Azure AD | 署名、JWKS の配布 | 消す鍵は使われていない。戻せばすぐ直る | 印が無視された。キャッシュが古い答えを持ち続けた |
| Storm-0558 | 署名の検証 | ライブラリが鍵の範囲も確かめる | 確かめていなかった。鍵も交換されていなかった |
| Psychic Signatures | ECDSA のアルゴリズム | 検証の実装が規格どおり | r と s の範囲の確認が抜けていた |
| CircleCI、Okta | 多要素認証 | 多要素を通った人だけがセッションを使う | セッションは持っている人が使えた |

右の 2 列を見ると、共通点が浮かびます。どの事故も、**ある部品が、隣の部品について置いていた前提**が崩れたところで起きています。部品の中身だけを見ていては見つからず、第 138 回で並べた「どの部品が何を保証しているか」の表の、**行と行の間**を見なければ見つかりません。

## 4 章を閉じる

第 16 章では、暗号の部品がそれぞれ 1 つの性質しか約束しないことを見ました。暗号化は改ざんを防がず、ハッシュは発信元を示さず、署名は鍵の持ち主を教えません。第 17 章では、証明書と信頼の連鎖で「その鍵は誰のものか」を答え、TLS と SSH でそれを組み立てました。第 19 章では、相手の鍵ではなく**その向こうの利用者**が誰で、何をしてよいのかを扱い、第 20 章でそれを多くのアプリにまたがらせました。

この回の事例は、その積み上げのどこでも、**1 つの部品が単独で責任を負えない**ことを示しています。

- 署名は正しくても、鍵の範囲の確認が抜ければ偽のトークンが通る（Storm-0558）
- 鍵の配布が正しくても、消す順番とキャッシュを誤れば全部のログインが止まる（Azure AD）
- 多要素認証が正しくても、結果を運ぶセッションが盗まれれば素通りされる（CircleCI、Okta）
- 暗号が正しくても、それを実装したコードのメモリの扱い 1 つで鍵が漏れる（Heartbleed）

部品ごとに「何を保証し、何を保証しないか」を知っていれば、事故の報告を読んだときに、**どの前提が崩れたのか**を言葉にできます。それがこの 4 章で目指したことでした。

## まとめ

- ここで見た事例の多くで、暗号のアルゴリズムは破られていない。壊れたのは部品同士のつなぎ目
- Heartbleed（2014、CVE-2014-0160）は、heartbeat の長さを確かめ忘れた C のコードが、同じプロセスにある秘密鍵や Cookie を最大 64KB ずつ漏らした。前方秘匿性の有無が過去の通信の被害を分ける
- 証明書の期限切れは、期限を知っていても起きる。Azure Storage（2013）は更新した証明書の配備が後回しにされ、監視は保管サービスの中身しか見ていなかった
- 時計のずれは、正しい証明書や JWT を拒ませる。発行直後の証明書と遅れた時計、進んだ IdP の時計と `iat` の組み合わせを手元で再現した
- Azure AD（2021）は、保持の印を無視して使用中の署名鍵を消し、戻した後も受け取り側のキャッシュが古いメタデータを持ち続けた。ローテーションはキャッシュを含めた分散した手順
- Storm-0558（2023）は、2016 年の消費者用の署名鍵で作ったトークンを企業向けのメールが受け入れた。共通の鍵の公開場所と、鍵の範囲を確かめない検証の組み合わせ。鍵の入手経路は CSRB の報告書の時点でも分かっていない
- Psychic Signatures（2022、CVE-2022-21449）は、Java の ECDSA 検証が r = s = 0 を通した。JWT、SAML、TLS、WebAuthn がまとめて影響を受けた
- CircleCI と Okta（2023）は、多要素認証の後に持ち越されたセッションを盗まれた。ベアラトークンの束縛、寿命の短縮、通信の記録の扱いが対策になる

ここまでの 4 章で、暗号の部品、TLS と SSH、認証と認可、SSO がそろいました。次の第 21 章では、これらを**すべて継ぎ足して使っている最も古い仕組み**、メールを見ます。SMTP は誰でも差出人を名乗れる設計で始まり、DNS の MX と TXT、STARTTLS と証明書、DKIM の署名、そして差出人のドメインを確かめる DMARC が、後から 1 つずつ足されてきました。
