前回は、共同編集のように**変更の操作そのもの**を送り合い、OT や CRDT で順序の違いを吸収して両端を同じ状態に揃える方法を見ました。操作が手元に残っていれば、それを送るのがいちばん小さく済みます。

しかし、操作の記録が残っていないことはよくあります。昨日のバックアップと今日のディスク、配布済みのバージョン 1.4 とこれから配る 1.5、2 台のレプリカに溜まったデータ。どちらの側にも**大きなデータがあり、中身はほぼ同じ**ですが、どこが変わったのかは誰も覚えていません。この回では、そこから**違う部分だけを見つけて送る**方法を見ます。第 12 章の最後の回です。

## 何が分かっていて、何が分かっていないのか

差分の作り方は、誰が何を知っているかで大きく変わります。

| 状況 | 例 | 使う方法 |
| --- | --- | --- |
| 片方が古い版と新しい版の両方を持っている | ソフトウェアの更新を配る | バイナリ差分（bsdiff、xdelta） |
| 両端が別々の版を 1 つずつ持ち、相手の中身を知らない | ファイルを別のマシンへ同期する | rsync のアルゴリズム |
| 多数の版を、まとめて 1 か所に貯める | バックアップ | 内容で区切るチャンク分割と重複排除 |
| 大量のデータのうち、どこが食い違っているかを知りたい | レプリカ同士の突き合わせ | Merkle 木 |

2 行目がいちばん難しい状況です。相手のデータを読めないのに、相手のデータとの差分を作らなければなりません。ここから順に見ていきます。

この回の実験は、macOS 上の Python 3.14.0 と、Docker Desktop の Alpine Linux 3.22（aarch64）に入れた rsync 3.5.0（プロトコル 32）、restic 0.18.0、Borg 1.4.3、xdelta3 3.1.0 で行いました。

## 素朴な方法とその弱点

いちばん単純なのは**全部送る**ことです。確実ですが、64 MiB のうち 1 バイトしか変わっていなくても 64 MiB を送ります。

次に思いつくのは、**固定の長さで切ってハッシュを比べる**方法です。受け手がデータを 8 KiB ずつに切り、それぞれのハッシュ（第 106 回）を送り手に送ります。送り手は自分のデータも同じように切り、ハッシュが一致しない塊だけを送ります。

これは**書き換え**には強いのですが、**挿入と削除**に弱いという欠点があります。先頭に 1 バイト挿入すると、それより後ろのすべての塊の中身が 1 バイトずつずれ、すべてのハッシュが変わります。

```
古い:   [ABCDEFGH][IJKLMNOP][QRSTUVWX]
新しい: [xABCDEFG][HIJKLMNO][PQRSTUVW][X]     先頭に x を挿入
        すべての塊の中身が変わる
```

8 MiB の乱数のデータで確かめます。古いデータと新しいデータをそれぞれ 8 KiB ずつに切り、新しいデータの塊のうち、古いデータにも同じ塊があったものの割合を数えました（後で出てくる 2 つの方式の結果も並べています）。

```
[fixed 8KiB] 先頭に 1 バイト挿入: reused 0.00% of bytes (0/1025 chunks)
[fixed 8KiB] 中央に 1 バイト挿入: reused 50.00% of bytes (512/1025 chunks)
[fixed 8KiB] 中央の 1 バイトを書き換え: reused 99.90% of bytes (1023/1024 chunks)
```

1 バイトの書き換えなら塊 1 つを送るだけで済みますが、先頭に 1 バイト挿入しただけで**再利用できる塊は 0 個**になります。中央に挿入すると、前半だけが助かります。文書やログ、アーカイブのように、途中に何かが挿入されるデータでは、この方法はほとんど役に立ちません。

ずれを吸収する方法は 2 つあります。**一方の側だけが固定の位置で切り、もう一方の側があらゆる位置で探す**か（rsync）、**切る位置を位置ではなく中身で決める**か（CDC）です。

## rsync: 受け手が指紋を送り、送り手が 1 バイトずつ探す

rsync のアルゴリズムは、Andrew Tridgell と Paul Mackerras が 1996 年の技術報告で示したものです（[The rsync algorithm](https://rsync.samba.org/tech_report/)）。古いファイル B を持つ受け手を β、新しいファイル A を持つ送り手を α とすると、手順は次のとおりです（[同 2 節](https://rsync.samba.org/tech_report/node2.html)）。

1. β は B を、重ならない S バイトのブロックに切る
2. β は各ブロックについて、**弱い 32 ビットのローリングチェックサム**と**強い 128 ビットの MD4 チェックサム**を計算し、α に送る
3. α は A の**すべての位置**について、長さ S の範囲の弱いチェックサムを計算し、B のブロックと一致するものを探す。弱いチェックサムが一致したら、強いチェックサムも確かめる
4. α は「B のブロック k をここに置け」という参照と、どのブロックにも一致しなかった部分の生のデータを順に β に送る

```
β（古い B）: [b0][b1][b2][b3]  → 各ブロックの (弱, 強) を α へ

α（新しい A）: x b0 b1 b2 b3
              ↑ 位置 0 から 1 バイトずつ窓をずらして照合
              位置 0: 弱が一致しない → 1 バイト進む
              位置 1: b0 と一致 → 「b0」を送り、S バイト進む
              ...
α → β: 生データ "x", 参照 b0, 参照 b1, 参照 b2, 参照 b3
```

固定長の方法との違いは、**受け手は固定の位置で切るが、送り手はあらゆる位置で照合する**という非対称性です。挿入によってデータがずれても、送り手の窓はずれた先でブロックを見つけます。

問題は計算量です。ファイルの長さを n とすると、照合の位置は n 通りあります。位置ごとに S バイトのハッシュを計算し直すと O(nS) かかり、S が数 KB なら現実的ではありません。そこで、**窓を 1 バイトずらしたときの値を、前の値から O(1) で求められる**チェックサムを使います。

### 窓を 1 バイトずらす計算

rsync の弱いチェックサムは、範囲 X_k … X_l（バイト列）について次のように定義されています（[同 3 節](https://rsync.samba.org/tech_report/node3.html)）。

```
a(k,l) = ( X_k + X_(k+1) + … + X_l )                 mod M
b(k,l) = ( (l-k+1)·X_k + (l-k)·X_(k+1) + … + 1·X_l )  mod M
s(k,l) = a(k,l) + 2^16 · b(k,l)                      M = 2^16
```

a は単純な総和、b は「後ろから数えた位置」で重み付けした総和です。窓を 1 バイト右にずらすと、出ていくのは X_k、入ってくるのは X_(l+1) です。

```
a(k+1,l+1) = ( a(k,l) - X_k + X_(l+1) )               mod M
b(k+1,l+1) = ( b(k,l) - (l-k+1)·X_k + a(k+1,l+1) )    mod M
```

a は、出ていくバイトを引いて入ってくるバイトを足すだけです。b のほうは、窓がずれると残ったバイトの重みが**すべて 1 ずつ減ります**。重みが 1 ずつ減った分の合計は、残ったバイトの総和そのものです。一方で、新しく入った X_(l+1) には重み 1 が付きます。この 2 つを合わせると「新しい a を足す」ことになり、出ていった X_k の重み (l-k+1) の分だけを引けば済みます。**窓の長さ S によらず、足し算と引き算が数回**です。

これは、<a href={`${import.meta.env.BASE_URL}articles/string-matching/`}>文字列照合</a>で見たローリングハッシュと同じ考え方です。形は zlib の Adler-32（[RFC 1950](https://www.rfc-editor.org/rfc/rfc1950.html)）に似ていますが、Adler-32 は 65521 という素数を法とし、a の初期値を 1 にしています。rsync は 2^16 を法としているので、余りの計算がビットの切り捨てで済みます。

Python で書いて、窓を 1000 回ずらしながら、毎回最初から計算した値と一致することを確かめました。

```python
M = 1 << 16

def roll(a, b, out_byte, in_byte, n):
    a = (a - out_byte + in_byte) % M
    b = (b - n * out_byte + a) % M
    return a, b
```

```
rolling == direct for 1000 shifts (window 16)
```

### 弱いハッシュと強いハッシュの 2 段

32 ビットの弱いチェックサムは、計算が速い代わりに衝突します。そこで、弱いチェックサムが一致した位置でだけ、強いハッシュを計算して確かめます。弱いほうは**候補を絞るためのふるい**で、本当に同じかどうかは強いほうで判断します。

どのくらい衝突するのかを見るため、8 MiB の乱数のファイルと、別の種から作った 8 MiB の乱数のファイルを照合しました。一致するブロックは 1 つもないはずです。

```
[weak] unrelated file: matched=0 literal=8388608 weak_hits=18 weak_only=18
```

約 838 万の位置で照合し、弱いチェックサムが偶然一致した位置が 18 か所ありました。どれも強いハッシュで弾かれています。32 ビットの値が一様に散らばるなら、2896 個のブロックに対して約 5.7 回と見積もれるところなので、それよりは多く衝突しています。総和に基づくチェックサムの値は一様には散らばらないためと考えられます。いずれにしても、強いハッシュを計算する位置は全体のごく一部で済みます。

## Python で照合を書いて試す

照合の全体を Python で書き、8 MiB の乱数のファイルに 3 種類の変更を加えて試しました。ブロックの長さは、後で見る rsync の決め方に合わせて 2896 バイトにしています。各行の末尾にあった実行時間の表示は省いています。

```
[rsync] 先頭に 1 バイト挿入: matched=8386816 literal=1793 weak_hits=2896 weak_only=0
[rsync] 中央に 1 バイト挿入: matched=8383920 literal=4689 weak_hits=2895 weak_only=0
[rsync] 中央の 1 バイトを書き換え: matched=8383920 literal=4688 weak_hits=2895 weak_only=0
```

先頭に挿入した場合、送り手は位置 0 では何も見つけられず、挿入された 1 バイトを生データとして送り、位置 1 から先はすべてのブロックを見つけています。中央に挿入した場合は、挿入された位置を含むブロック 1 つ（2896 バイト）と挿入された 1 バイトが生データになりました。どの場合にも含まれる 1792 バイトは、ファイルの末尾の S に満たない端数です。この実装は端数のブロックを照合の対象にしていないので生データとして送っていますが、本物の rsync は端数のブロックも照合します。

固定長の方法では 0% だった先頭への挿入が、ここではほぼ全量の再利用になりました。

## 本物の rsync で確かめる

64 MiB の乱数のファイルを用意し、先頭に 1 バイト挿入したもの、中央（32 MiB の位置）に 1 バイト挿入したもの、11 か所の 1 バイトを書き換えたものを作りました。古いファイルを受け手の場所に置き、`--stats` で転送の内訳を出します。

まず、何も指定せずに実行した結果です。

```
== head default
Literal data: 67,108,865 bytes
Matched data: 0 bytes
Total bytes sent: 67,125,351
```

**全部送っています。**rsync は、送り元と送り先の両方がローカルのパスのとき、差分転送を使わずにファイル全体をコピーするのが既定です（[rsync(1)](https://download.samba.org/pub/rsync/rsync.1) の `--whole-file`）。同じマシンの中なら、ディスクを読んで比べるより全部コピーするほうが速いからです。差分転送を強制するには `--no-whole-file` を付けます。`--debug=deltasum2` で、受け手がブロックをどう切ったかも表示させました。

```
== head --no-whole-file
count=8192 rem=0 blength=8192 s2length=3 flength=67108864
Literal data: 1 bytes
Matched data: 67,108,864 bytes
Total bytes sent: 32,875
Total bytes received: 57,537

== mid --no-whole-file
Literal data: 1 bytes
Matched data: 67,108,864 bytes
Total bytes sent: 32,873

== ten --no-whole-file
Literal data: 90,112 bytes
Matched data: 67,018,752 bytes
Total bytes sent: 122,989
```

`Literal data` は一致しなかったので送り手が送ったデータの量、`Matched data` は受け手が手元の古いファイルから取り出したデータの量です（[rsync(1)](https://download.samba.org/pub/rsync/rsync.1)）。どの場合も、受け取ったファイルが新しいファイルと一致することを `cmp` で確かめています。

- **挿入は、挿入した 1 バイトだけ**が生データになりました。中央の場合も 1 バイトだけなのは、32 MiB がブロックの長さ 8192 のちょうど倍数で、挿入がブロックの境目に当たったためです
- **11 か所の書き換え**は、11 × 8192 = 90,112 バイトです。書き換わった 1 バイトを含むブロックが、まるごと生データになります
- 送り手が受け取った 57,537 バイトは、受け手から届いたブロックの指紋です。8192 個のブロックについて、弱いチェックサム 4 バイトと強いハッシュ 3 バイトの合計 7 バイトずつで、8192 × 7 = 57,344 バイトになります

ブロックの長さ `blength=8192` は、ファイルの長さのおおよその平方根を 8 の倍数に切り下げた値です。rsync のソースでは、長さが 700 × 700 バイト以下のファイルは 700 バイト（`BLOCK_SIZE`）、それより大きいファイルは平方根を 8 の倍数で求め、上限を 2^17 バイト（`MAX_BLOCK_SIZE`）としています（[generator.c](https://github.com/RsyncProject/rsync/blob/master/generator.c) の `sum_sizes_sqroot`、[rsync.h](https://github.com/RsyncProject/rsync/blob/master/rsync.h)）。64 MiB の平方根はちょうど 8192 です。ブロックを短くすると変更 1 か所あたりの生データは減りますが、送る指紋の数が増えます。平方根は、この 2 つの釣り合いを取る目安です。

### 強いハッシュは 3 バイトしか送っていない

`s2length=3` は、強いハッシュを**先頭の 3 バイトだけ**送ったという意味です。技術報告では 128 ビットの MD4 でしたが、現在の rsync は、ファイルとブロックの長さから、偶然の一致が起きにくい程度の長さを計算して、それだけを送ります（[generator.c](https://github.com/RsyncProject/rsync/blob/master/generator.c) の `s2length` の計算）。強いハッシュの種類も、両端が対応するものから強い順に選びます。今回の rsync 3.5.0 は `xxh128 xxh3 xxh64 md5 md4` に対応していました（`rsync --version` の `Checksum list`）。

3 バイトに切り詰めれば、偶然の一致はありえます。その備えとして、rsync はファイル全体のチェックサムも送り、組み立てたファイルと照合します。合わなければ、強いハッシュを完全な長さにして、そのファイルをもう一度送り直します（[receiver.c](https://github.com/RsyncProject/rsync/blob/master/receiver.c) の `redoing`、`failed verification` のメッセージ）。**普段は短く送って、まれな失敗はやり直しで拾う**という設計です。

<Callout type="note" title="rsync のハッシュは敵を想定していない">
  ここでの強いハッシュは、偶然の一致を見分けるためのものです。悪意のある相手が狙って衝突を作ることは想定していません。第 106 回で見たように、MD4 や MD5 はすでに衝突を作れます。差分転送の正しさと、相手が本物かどうかの確認は別の問題で、後者は SSH などの下の層（第 118 回）で守ります。
</Callout>

## 内容で区切る

rsync は、1 対 1 の同期にはよく合います。しかし、**受け手が毎回、古いファイル全体を読んで指紋を作る**必要があります。バックアップのように、何十もの版を 1 か所に貯めて、どの版とも重複を省きたい場合には向きません。

そこで、**切る位置をデータの中身で決める**方法が使われます。これを**内容で区切るチャンク分割**（content-defined chunking、CDC）と呼びます。データの上に短い窓を滑らせ、窓の中身のハッシュが**特定の条件を満たした位置**で切ります。

```
古い:   …[ABCDE|FGHIJKLM|NOPQRS|TUV…        | は「窓のハッシュの下位 13 ビットが 0」の位置
新しい: …[ABCDE|FGHIxJKLM|NOPQRS|TUV…       x を挿入
                └─ この塊だけが変わる
```

境界は「そこにどんなバイトが並んでいるか」だけで決まるので、前に何バイト挿入されても**同じ中身の場所に同じ境界が現れます**。挿入を含む塊だけが変わり、その後ろは元の塊に戻ります。どちらの側も、相手のデータを見ずに独立に切れるのが rsync との大きな違いです。

塊にはハッシュで名前を付け、**同じハッシュの塊は 1 回だけ保存する**、または相手がすでに持っていれば送らない、とすれば重複排除になります。

### Rabin フィンガープリントと LBFS

ハッシュが条件を満たす確率を 2^-13 にすれば、境界は平均 8192 バイトに 1 回現れます。2001 年の LBFS（低帯域のネットワーク向けのファイルシステム）は、この方法で、ファイルの重なり合うすべての 48 バイトの範囲について **Rabin フィンガープリント**を計算し、下位 13 ビットが決めた値に一致した位置を境界にしました（[Muthitacharoen ほか, SOSP 2001](https://pdos.csail.mit.edu/papers/lbfs:sosp01/lbfs.pdf) 3.1 節）。Rabin フィンガープリントは、バイト列を GF(2) の多項式と見て、決めた既約多項式で割った余りです。ローリングハッシュとして計算できます。

条件だけで切ると、同じバイトが続くデータでは境界が現れず、逆に短い塊が続くこともあります。そのため LBFS は、境界の後 2 KB 以内では次の境界を作らず、64 KB まで境界が現れなければ強制的に切るという**最小と最大**を設けています（同 3.1 節）。

### Gear ハッシュと FastCDC

Rabin フィンガープリントは、1 バイトごとに多項式の剰余を更新するので、それなりに重い計算です。**Gear ハッシュ**は、各バイトの値に対応する 64 ビットの乱数を表（Gear）から引き、次のように更新するだけです（[Xia ほか, USENIX ATC 2016](https://www.usenix.org/system/files/conference/atc16/atc16-paper-xia.pdf)）。

```
fp = (fp << 1) + Gear[b]
```

1 ビット左にずらすたびに、古いバイトの影響は上の桁へ押し出され、64 回ずらすと消えます。**引き算をしなくても、勝手に窓が前に進む**ローリングハッシュです。その代わり、fp の下位 k ビットには直近の k バイトの影響しか入っていません。下位 13 ビットで判定すると、実質 13 バイトの窓で境界を決めることになります。

FastCDC はこれを 3 つの工夫で改良しました（同論文）。

- **判定に使うビットを上位に散らす**: マスクの 1 のビットを上位側に広げ、判定に関わるバイトを増やす
- **最小の長さの手前は判定しない**: どうせ切らない範囲のハッシュ計算を飛ばす
- **正規化したチャンク分割**: 目標の長さより手前では 1 のビットが多いマスク（切りにくい）、先では少ないマスク（切りやすい）を使い、長さを目標の近くに集める。8 KB を目標とする例では、15 ビットと 11 ビットのマスクを使っている

論文は、Rabin に基づく CDC の約 10 倍、Gear に基づく CDC の約 3 倍の速さで、重複排除の率はほぼ同じだったと報告しています（[USENIX ATC 2016](https://www.usenix.org/conference/atc16/technical-sessions/presentation/xia)）。

### 手元で比べる

Gear ハッシュによる CDC を Python で書き、LBFS と同じく平均 8 KiB（13 ビット）、最小 2 KiB、最大 64 KiB に設定しました。正規化したものは、FastCDC の例と同じく 15 ビットと 11 ビットのマスクを切り替えます。まず、古いデータを切った結果の長さの分布です。

```
[fixed 8KiB] chunks=1024 mean=8192 stdev=0 min=8192 max=8192
[gear] chunks=852 mean=9846 stdev=7796 min=2056 max=53126
[gear+normalized] chunks=880 mean=9533 stdev=2789 min=2057 max=23323
```

平均が 8192 より長いのは、最小の 2 KiB を飛ばしてから判定を始めるためです。正規化すると、標準偏差が 7796 から 2789 に縮み、最大も 53126 から 23323 に下がりました。長さが目標の近くに集まっています。

次に、先ほどと同じ 3 種類の変更を加え、再利用できた割合を比べます。

```
[fixed 8KiB] 先頭に 1 バイト挿入: reused 0.00% of bytes (0/1025 chunks)
[gear] 先頭に 1 バイト挿入: reused 99.79% of bytes (851/852 chunks)
[gear+normalized] 先頭に 1 バイト挿入: reused 99.93% of bytes (879/880 chunks)
[fixed 8KiB] 中央に 1 バイト挿入: reused 50.00% of bytes (512/1025 chunks)
[gear] 中央に 1 バイト挿入: reused 99.92% of bytes (851/852 chunks)
[gear+normalized] 中央に 1 バイト挿入: reused 99.90% of bytes (879/880 chunks)
[fixed 8KiB] 中央の 1 バイトを書き換え: reused 99.90% of bytes (1023/1024 chunks)
[gear] 中央の 1 バイトを書き換え: reused 99.92% of bytes (851/852 chunks)
[gear+normalized] 中央の 1 バイトを書き換え: reused 99.90% of bytes (879/880 chunks)
```

CDC では、どの変更でも**変わった塊は 1 つだけ**でした。新しいデータの塊の数が古いデータと同じなのは、挿入された塊が元の塊と同じ位置で終わり、後ろの境界がすべて元どおりに戻ったことを示しています。

### 平均の長さをどう決めるか

平均の長さを短くすると、1 か所の変更で失う量が減り、重複も細かく見つかります。その代わり、塊の数が増え、塊ごとに持つハッシュと索引が増えます。32 バイトのハッシュで 1 TiB を 8 KiB ずつに切ると、塊は約 1.3 億個、ハッシュだけで約 4 GiB です。バックアップの道具は、長めの塊を選んでいます。

| 道具 | 方式 | 塊の長さ |
| --- | --- | --- |
| restic | Rabin フィンガープリント、64 バイトの窓。多項式はリポジトリごとに無作為に選ぶ | 平均 1 MiB、512 KiB〜8 MiB（[restic](https://restic.readthedocs.io/en/stable/100_references.html)） |
| Borg | buzhash。表をリポジトリごとの乱数の種と XOR する | 既定で目標 2 MiB（2^21）、512 KiB〜8 MiB（[Borg](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html)） |

どちらも、境界の決め方をリポジトリごとの秘密の値で変えています。境界が誰にとっても同じだと、塊の長さの並びから、どのファイルが保存されているかを外から推測される恐れがあるためです（Borg の文書はこの目的を明記しています）。

64 MiB の乱数のファイルを、restic と Borg でそれぞれ 1 回バックアップし、その後に先ほどの 3 種類の変更を加えたものを順にバックアップしました。

```
== restic backup (base)
Added to the repository: 64.003 MiB (64.007 MiB stored)
== restic backup (head)
Added to the repository: 3.421 MiB (3.420 MiB stored)
== restic backup (mid)
Added to the repository: 3.255 MiB (3.254 MiB stored)
== restic backup (ten)
Added to the repository: 24.338 MiB (24.338 MiB stored)
```

Borg の `--stats` の 3 つの列は、元の大きさ、圧縮後の大きさ、重複を省いた後に新しく保存した大きさです（乱数なので圧縮は効いていません）。

```
== borg create (base)
This archive:               67.11 MB             67.11 MB             67.11 MB
== borg create (head)
This archive:               67.11 MB             67.11 MB              2.65 MB
== borg create (mid)
This archive:               67.11 MB             67.11 MB              3.97 MB
== borg create (ten)
This archive:               67.11 MB             67.11 MB             42.47 MB
```

1 バイトの挿入では、どちらも 2〜4 MB を新しく保存しただけで済んでいます。しかし 11 か所の書き換えでは、restic が 24 MiB、Borg が 42 MB を新しく保存しました。1 か所の変更で、その位置を含む**数 MB の塊がまるごと**新しくなるからです。同じ変更で rsync が送った生データは 90 KB でした。restic の 4 回分のバックアップは、合わせて 256 MiB に対して保存した量が 95.0 MiB です（`restic stats --mode raw-data`）。

**長い塊は、散らばった小さな変更に弱い。**バックアップの道具は、変わらないファイルが大半を占める状況を前提に、索引の小ささを優先しています。

## 両方を知っている側が作る差分

ソフトウェアの更新を配る場合は、事情が違います。配る側は**古い版と新しい版の両方**を持っています。相手が古い版を持っていることも分かっています。この場合は、手元で 2 つを好きなだけ比べて、いちばん小さい差分を作れます。

**xdelta** は、差分の形式として **VCDIFF**（[RFC 3284](https://www.rfc-editor.org/rfc/rfc3284.html)）を使います。VCDIFF の差分は、古いデータのどこかを写す COPY、新しいバイトを書き足す ADD、同じバイトを繰り返す RUN という命令の並びです。先ほどの 64 MiB のファイルで差分を作りました。

```
head delta=262 bytes
mid delta=261 bytes
ten delta=396 bytes
```

rsync がブロックの単位で送った 90 KB に対し、11 か所の書き換えが 396 バイトになりました。xdelta はバイト単位で一致する範囲を探せるので、書き換わった 1 バイトだけを ADD で送れます。差分のファイルの先頭は、RFC 3284 が定める `d6 c3 c4 00`（「VCD」の各バイトの最上位ビットを立てたものと、版の 0）で始まっていました。

```
0000000 d6 c3 c4 00 05 02 13 68 65 61 64 2e 62 69 6e 2f
```

**bsdiff** は、Colin Percival が実行ファイルの差分のために作った道具です（[bsdiff](https://www.daemonology.net/bsdiff/)）。接尾辞の整列で一致する範囲を探し、完全には一致しないがほぼ同じ範囲も「引き算した差」として記録します。差の大半は 0 になるので、圧縮がよく効きます。作者は、xdelta より 50〜80% 小さい差分を作れるとしています。今回は手元で bsdiff を動かしていません。

### 実行ファイルの差分はなぜ大きいのか

ソースを 1 行変えて再コンパイルすると、その後ろのコードの位置がずれ、**そこを指すアドレスがすべて変わります**。Chromium の文書によれば、Chrome の実行ファイルにはおよそ 50 万個の内部のポインタがあり、小さな変更でもその多くの値が変わります（[Software Updates: Courgette](https://www.chromium.org/developers/design-documents/software-updates-courgette/)）。

Courgette は、実行ファイルを**逆アセンブルし、ポインタを記号に置き換えた形**にしてから bsdiff をかけます。アドレスのずれが記号の対応表に吸収されるので、差分が小さくなります。同じ文書の例では、ある更新の差分が、全体 10,385,920 バイト、bsdiff 704,512 バイト、Courgette 78,848 バイトでした。その後継として、同じ考え方で PE、ELF、DEX などの形式を扱う **Zucchini** が作られ、Chromium のソースに含まれています（[Zucchini](https://chromium.googlesource.com/chromium/src/+/HEAD/components/zucchini/README.md)、[導入時のレビュー](https://codereview.chromium.org/2922273002)）。データの**形式を知っていれば**、バイトの並びの差分より小さく書けるという例です。

## 違う場所を木で探す

ここまでは、データ全体について指紋を送るか、差分を作るかでした。データがもっと大きく、**ほとんど同じで違いはまれ**なら、もう一段減らせます。

**Merkle 木**は、ブロックのハッシュを葉とし、子のハッシュを連結したもののハッシュを親とする木です。根が一致すれば、その下はすべて一致しています。一致しなければ子を比べ、食い違う枝だけを下りていきます。

```
            根 ≠
          /      \
       左 =      右 ≠           左の下は見なくてよい
                /    \
              =       ≠          …葉まで下りて違うブロックを特定する
```

8 MiB のデータを 4 KiB ずつの葉（2048 枚）に分け、1〜300 か所の 1 バイトを書き換えたものと比べました。下りていく段ごとに 1 往復かかるとして、往復の回数と、やり取りしたハッシュの数を数えます。比較のため、葉のハッシュを全部いっぺんに送る方法（1 往復）も並べます。

```
[merkle] leaves=2048 changes=1 fanout=2: rounds=12 hashes=23 diff_leaves=1
[merkle] leaves=2048 changes=1 fanout=16: rounds=4 hashes=41 diff_leaves=1
[flat]   leaves=2048 changes=1: rounds=1 hashes=2048
[merkle] leaves=2048 changes=30 fanout=2: rounds=12 hashes=373 diff_leaves=30
[merkle] leaves=2048 changes=30 fanout=16: rounds=4 hashes=553 diff_leaves=30
[flat]   leaves=2048 changes=30: rounds=1 hashes=2048
[merkle] leaves=2048 changes=300 fanout=2: rounds=12 hashes=1837 diff_leaves=277
[merkle] leaves=2048 changes=300 fanout=16: rounds=4 hashes=2057 diff_leaves=277
[flat]   leaves=2048 changes=300: rounds=1 hashes=2048
```

変更が 1 か所なら、2 分木で 23 個のハッシュを比べるだけで、違う葉を特定できました。全部送る方法の 1/90 です。その代わり**12 往復**かかります。枝分かれを 16 にすると、往復は 4 回に減り、ハッシュは 41 個に増えます。変更が 300 か所（違う葉は 277 枚）になると、木で探しても全部送るのと同じくらいのハッシュが必要になり、往復が多いぶん損です。

**往復の回数と送るバイト数は交換できる**、というのがこの実験の結論です。第 54 回で見たように RTT が大きい回線では往復が高くつくので、枝分かれを増やすか、違いが多いと分かっていれば最初から葉を全部送ります。

### Merkle 木を使っているもの

**Dynamo と Cassandra。** Amazon の Dynamo は、レプリカ同士の食い違いを見つける anti-entropy に Merkle 木を使いました。各ノードは担当するキーの範囲ごとに Merkle 木を持ち、同じ範囲を持つノード同士が根から比べていきます。論文は、この方法がディスクの読み出しと送るデータを減らす一方、ノードの参加や離脱でキーの範囲が変わると木を作り直さなければならないことを欠点に挙げています（[DeCandia ほか, SOSP 2007](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf) 4.7 節）。Cassandra の repair も、Merkle 木でデータを比べます（[Cassandra](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/repair.html)）。木の計算に使うメモリには上限の設定（`repair_session_space`）があり（[cassandra.yaml](https://cassandra.apache.org/doc/latest/cassandra/managing/configuration/cass_yaml_file.html)）、葉の数を無制限には増やせません。1 枚の葉が広い範囲を受け持つほど、その中の 1 行の食い違いのために範囲全体を送ることになります。

**git。** git のオブジェクトは、中身のハッシュで名前が付きます。ディレクトリを表す tree オブジェクトは、中のファイル（blob）とサブディレクトリ（tree）のハッシュを並べたものなので、コミットの下は Merkle 木になっています（[Pro Git 10.2](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)）。`src/main.c` だけを変えた 2 つのコミットを比べると、こうなります（git 2.52.0）。

```
== HEAD~1
040000 tree 2e81171448eb9f2ee3821e3d447aa6b2fe3ddba1	docs
040000 tree 5ec86921817e46af5fefe09e0ea2e151002218f7	src
== HEAD
040000 tree 2e81171448eb9f2ee3821e3d447aa6b2fe3ddba1	docs
040000 tree 58b278c11190be245ff8c30dba5ebe4e2a23c68c	src
```

`docs` の tree のハッシュは同じなので、その下を見る必要はありません。`src` の下では、`util.c` の blob は同じハッシュのまま、`main.c` だけが変わっています。fetch のときは、クライアントが手元にあるコミットを `have` として伝え、サーバはそこから届く範囲のオブジェクトを送らずに済ませます（[gitprotocol-pack](https://git-scm.com/docs/gitprotocol-pack)）。

**ZFS の send。** 第 51 回で見たように、ZFS はブロックを書き換えるとき新しい場所に書き、根まで親を書き直します。各ブロックへのポインタには、そのブロックが書かれたトランザクショングループの番号（birth time）が入っています。2 つのスナップショットの差分を送る `zfs send -i` は、木をたどりながら、古いスナップショットより前に書かれたブロックの下を飛ばします（[OpenZFS: ZfsSend](https://openzfs.org/wiki/Documentation/ZfsSend)）。**ハッシュを比べるのではなく、書いた時刻で枝を刈る**ので、相手と往復する必要もありません。相手が古いスナップショットを持っていることさえ分かっていれば、送る側だけで差分が決まります。

## 方法を並べる

| 方法 | 往復 | 送るもの | 前提 |
| --- | --- | --- | --- |
| 全部送る | 0 | データ全体 | なし |
| rsync | 1 | 受け手からブロックの指紋、送り手から参照と生データ | 送り手が自分のデータを全部読む |
| CDC と重複排除 | 1（持っている塊を尋ねる） | 相手が持っていない塊 | 両端が同じ切り方をする |
| バイナリ差分 | 0 | 差分 | 送り手が相手の版を知っている |
| Merkle 木 | 木の深さの分 | 食い違った枝のハッシュと、違う葉 | 両端が同じ木を維持している |

前回の操作の転送も、この表に並べられます。**操作の記録があればそれを送るのがいちばん小さく、記録がなければ、往復の回数と、計算と、送る量のどれかを払って違いを見つける**ことになります。

## まとめ

- 固定の長さで切ってハッシュを比べる方法は、書き換えには強いが、挿入や削除でずれると後ろがすべて変わる
- rsync は、受け手が固定の位置で切ったブロックの指紋を送り、送り手があらゆる位置で照合する。弱いチェックサムは窓を 1 バイトずらすごとに O(1) で更新でき、一致した位置だけ強いハッシュで確かめる
- rsync のブロックの長さはファイルの長さのおおよその平方根。強いハッシュは必要な長さだけ送り、ファイル全体の照合が合わなければやり直す。ローカル同士では既定で差分転送を使わない
- CDC は窓のハッシュが条件を満たす位置で切るので、挿入があっても同じ中身の場所に同じ境界が現れる。Gear ハッシュと FastCDC は判定を速くし、正規化で長さのばらつきを抑える
- 塊の平均の長さは、変更 1 か所で失う量と、索引の大きさの釣り合いで決める。restic や Borg は MB 単位の塊を使う
- 両方の版を持つ側は、bsdiff や xdelta（VCDIFF）でバイト単位の差分を作れる。実行ファイルは、Courgette や Zucchini のように形式を解釈すると差分がさらに小さくなる
- Merkle 木は、違う枝だけを下りて食い違いを探す。往復の回数と送るハッシュの数は、枝分かれの数と変更の多さで交換条件になる

この章では、データをネットワーク越しに届け、揃えることを見てきました。揃えたデータは、最後にはどこかに保存されます。次の第 13 章「データベースの中身」では、データベースがディスクの上でデータをどう持っているのかを見ます。最初は、データベースがディスクを読み書きする単位である**ページ**と、ページをメモリに置いておく**バッファプール**です。この回で見た「固定の長さで切る」「ハッシュで指す」「新しい場所に書いて親を書き直す」という考え方は、そこでも形を変えて現れます。
