## 1 つのプロセスでは足りないとき

第 70 回で、コンテナの中では最初のプロセスが PID 1 になり、それが終わればコンテナも終わる、と見ました。コンテナは**プロセス 1 つ分**の入れ物として設計されています。

しかし、実際のアプリケーションは 1 つのプロセスでは完結しないことがあります。

- Web サーバと、そのログを集めて外に送るプロセス
- アプリケーションと、その通信を暗号化して中継するプロキシ
- アプリケーションと、設定ファイルの変更を見張って書き換えるプロセス

これらは**別のプログラム**です。別の言語で書かれ、別の人が保守し、別々に更新したい。だから 1 つのコンテナに押し込めるのは筋が悪い。

一方で、これらは**離れて動くと意味がありません**。ログを集めるプロセスは、Web サーバと同じファイルが見えなければならない。プロキシは、アプリケーションと `localhost` で話せなければならない。そして、同じマシンに置かれなければならない。

つまり、**別々のコンテナでありながら、一部の名前空間を共有し、必ず一緒に配置される組**が欲しい。これが **Pod** です。

## Pod は「共有された名前空間」の組

公式ドキュメントは、Pod を次のように定義しています（[Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/)）。

> Pod は、1 つ以上のコンテナの組で、ストレージとネットワークの資源を共有し、コンテナの動かし方の指定を持つ。

そして、その「共有された文脈」の正体を、はっきり書いています。

> Pod の共有された文脈とは、Linux の名前空間、cgroup、場合によってはその他の分離の仕組みの集まりであり、コンテナを分離しているのと同じものである。

第 68 回で見たとおり、コンテナは名前空間と cgroup の組み合わせでした。Pod はそれを **1 段外側にもう 1 つ作ったもの** です。

```
        Pod（Network、IPC、UTS 名前空間を共有）
  ┌─────────────────────────────────────────────┐
  │  IP アドレス 10.1.2.3、ホスト名 web-7f9c       │
  │                                             │
  │   ┌────────────┐  ┌────────────┐            │
  │   │ コンテナ A  │  │ コンテナ B  │             │
  │   │ （アプリ）  │  │ （ログ転送）│             │
  │   │ Mount 名前空間│ │ Mount 名前空間│ ← 別々   │
  │   │ PID 名前空間 │  │ PID 名前空間 │ ← 既定は別々│
  │   └─────┬──────┘  └─────┬──────┘            │
  │         └──── 共有ボリューム ─┘               │
  └─────────────────────────────────────────────┘
```

| 名前空間 | Pod の中で | 結果 |
| --- | --- | --- |
| Network | **共有** | 同じ IP、同じポート空間。`localhost` で話せる。同じポートは 2 つで使えない |
| IPC | **共有** | 共有メモリやセマフォを使える |
| UTS | **共有** | 同じホスト名 |
| Mount | 別々 | それぞれ自分のイメージのファイルを見る。ボリュームだけを共有する |
| PID | 既定は別々 | 設定で共有にできる（互いのプロセスが見え、シグナルを送れる） |

第 74 回の Compose で、`network_mode: service:x` を使うと別のコンテナの Network 名前空間に相乗りできる、と見ました。Pod は、それを**最初から組として定義したもの**です。

## 何もしないコンテナ: pause

名前空間を共有するには、その名前空間を**誰かが持っていなければなりません**。

第 68 回で見たとおり、名前空間はプロセスに付いています。その名前空間に属するプロセスがすべて終わると、名前空間も消えます。もしアプリのコンテナが Network 名前空間を作り、ログ転送のコンテナがそこに相乗りしていたら、アプリが再起動した瞬間に名前空間が消え、IP アドレスも失われ、ログ転送のコンテナは宙に浮きます。

そこで Kubernetes（のランタイム）は、Pod を作るとき、アプリより先に **pause** という小さなコンテナを起動します。

- pause が Network、IPC などの名前空間を作って持ち続ける
- アプリのコンテナは、その名前空間に**参加する**形で起動される
- アプリが何度再起動しても、pause が生きている限り名前空間と IP は残る
- pause が終われば、Pod は終わったものとみなされる

pause 自身は、ほとんど何もしません。シグナルを待って眠るだけです。何もしないから落ちない。**落ちない者に、壊れてはいけないものを持たせる**という設計です（[sklar.rocks](https://sklar.rocks/what-is-a-pod-sandbox/)）。

<Callout type="tip" title="pause は PID 1 の役も引き受けられる">
  Pod の中で PID 名前空間を共有する設定にすると、pause がその中の PID 1 になります。
  第 70 回で見た「PID 1 は孤児を引き取ってゾンビを回収しなければならない」という役目を、
  pause が引き受けます。アプリのコンテナ側に tini を入れなくて済むわけです。
</Callout>

## kubelet がランタイムに頼むこと

各ノードで Pod を実際に動かすのは **kubelet** です。第 78 回で見たとおり、kubelet も調整ループの 1 つで、「このノードに割り当てられた Pod」と「実際に動いているコンテナ」の差を埋め続けます。

ただし kubelet は、自分でコンテナを作りません。第 70 回で見た containerd のようなランタイムに頼みます。頼み方を決めているのが **CRI**（Container Runtime Interface）です。

公式ドキュメントによると、CRI は kubelet とコンテナランタイムの間の gRPC のプロトコルで、kubelet がクライアントになります。これにより、クラスタの部品を作り直さずに、いろいろなランタイムを使えます（[Kubernetes](https://kubernetes.io/docs/concepts/architecture/cri/)）。

CRI の呼び出しには、Pod という単位がそのまま現れています。

```
kubelet                               containerd（CRI の実装）
   │                                        │
   │── RunPodSandbox ──────────────────────→│  pause を起動し、名前空間を作る
   │                                        │  （このとき CNI でネットワークを設定）
   │── PullImage ──────────────────────────→│  イメージを取ってくる（第 69 回）
   │── CreateContainer（サンドボックス ID）─→│  サンドボックスの名前空間に参加する
   │── StartContainer ─────────────────────→│  shim → runc → 起動（第 70 回）
   │                                        │
   │── ContainerStatus（定期的に）─────────→│  状態を API サーバへ報告する
```

最初に作るのは、コンテナではなく **サンドボックス** です。サンドボックスとは、pause が持っている名前空間の組のことです。個々のコンテナは、その中に入れる形で作られます。

第 70 回の図と並べると、層の積み重なりが見えます。

```
kubelet ─(CRI / gRPC)→ containerd ─→ shim ─→ runc ─→ clone + 名前空間 + cgroup（第 68 回）
```

Docker の CLI が dockerd を経由して containerd に頼んでいたところを、Kubernetes では kubelet が直接 containerd に頼みます。Kubernetes は以前、Docker を経由するための変換層（dockershim）を持っていましたが、v1.24 で取り除かれました（[Kubernetes Blog](https://kubernetes.io/blog/2022/02/17/dockershim-faq/)）。

## サイドカー

Pod の中の「アプリではない方」のコンテナを、**サイドカー** と呼びます。オートバイの横に付ける側車から来た言葉です。

| よくある役割 | 共有しているもの | 例 |
| --- | --- | --- |
| ログの転送 | ボリューム | アプリがファイルに書いたログを読んで外へ送る |
| 通信の中継 | Network 名前空間 | アプリの出入りする通信を横取りして暗号化・計測する |
| 設定の同期 | ボリューム | 設定を外から取ってきてファイルに書き、アプリに読ませる |

どれも、アプリのコードを 1 行も変えずに機能を足しています。**名前空間とボリュームを共有しているから、アプリからは「自分のマシンの中にある何か」にしか見えない**。通信の中継を突き詰めたものが、第 82 回のサービスメッシュです。

### 起動と終了の順番

サイドカーには長い間、厄介な問題がありました。Pod の中のコンテナは**同時に**起動され、**同時に**止められます。

- アプリがプロキシより先に起動すると、最初の通信が失敗する
- 処理が終わったら止まるはずの Pod（Job）で、サイドカーがいつまでも動き続け、Pod が終わらない
- 止めるとき、ログ転送が先に止まると、アプリの最後のログが失われる

そこで、**init コンテナ** の仕組みが拡張されました。init コンテナは、本体のコンテナより前に**1 つずつ順番に**動き、終わってから次へ進むコンテナです。データベースの準備を待つ、設定ファイルを生成する、といった「起動前の下ごしらえ」に使われてきました。

この init コンテナに `restartPolicy: Always` を付けると、**終わらずに動き続ける init コンテナ**、つまりサイドカーになります。本体より先に起動し、Pod の生存中ずっと動き、本体が終わってから止められます。v1.28 で入り、v1.33 で安定版になりました（[Kubernetes](https://www.kubernetes.io/docs/concepts/workloads/pods/sidecar-containers/)、[Kubernetes Blog](https://kubernetes.io/blog/2023/08/25/native-sidecar-containers/)）。

```yaml
spec:
  initContainers:
    - name: log-shipper
      image: log-shipper:1.0
      restartPolicy: Always     # ← これでサイドカーになる
  containers:
    - name: app
      image: app:2.3
```

起動と終了の順番は、第 70 回で見た PID 1 とシグナルの問題の、Pod 版です。**複数のプロセスをまとめて扱うと、必ず順番の問題が出る**。

## Pod は使い捨て

最後に、Pod のもう 1 つの性質です。公式ドキュメントは、Pod を「比較的短命で、使い捨ての存在」として設計した、と書いています（[Kubernetes](https://kubernetes.io/docs/concepts/workloads/pods/)）。

- Pod が載っているノードが落ちれば、その Pod は消える。**同じ Pod が別のノードで復活することはない**
- 代わりに、上位のコントローラが**新しい Pod** を作る。名前も IP アドレスも変わる
- だから、Pod を直接作ることはまれで、Deployment や Job のような上位の仕組みを通して作る

第 78 回の調整ループは、ここで効きます。「3 つのはず」を覚えているのはコントローラで、Pod ではありません。Pod は、その「3 つ」を満たすための交換可能な部品です。

<Callout type="warn" title="IP アドレスに頼らない">
  Pod の IP アドレスは、作り直されるたびに変わります。
  別の Pod の IP を設定ファイルに書くと、相手が作り直された瞬間に繋がらなくなります。
  変わらない名前で相手を指す仕組みが、第 81 回の Service です。
  状態を持つものに安定した名前を与える仕組みは、第 84 回で見ます。
</Callout>

## まとめ

- Pod は、名前空間の一部（Network、IPC、UTS）を共有し、必ず一緒に配置されるコンテナの組
- 共有する名前空間は、何もしない pause コンテナが持ち続ける。アプリが再起動しても IP は残る
- kubelet は CRI（gRPC）で containerd に頼む。最初にサンドボックスを作り、その中にコンテナを入れる
- サイドカーは、名前空間とボリュームの共有によって、アプリを変えずに機能を足す
- `restartPolicy: Always` の init コンテナで、サイドカーの起動と終了の順番を保証できる
- Pod は使い捨て。数を覚えているのはコントローラで、作り直すたびに名前も IP も変わる
