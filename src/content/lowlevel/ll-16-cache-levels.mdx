## 番号に上限はない

L1、L2、L3 という番号は、**CPU コアから数えて何番目か**を表しているだけです。規格で「3 段まで」と決まっているわけではありません。

- L1 が外れたら L2 を見る
- L2 が外れたら L3 を見る
- 最後の段が外れたら、メインメモリに取りに行く

最後の段のことを、番号にかかわらず **LLC**（Last Level Cache、最終段キャッシュ）と呼びます。多くの CPU では L3 が LLC ですが、L2 までしかない CPU では L2 が LLC です。

現在のパソコンやサーバ向け CPU は、ほとんどが **3 段**です。4 段目を持つ CPU も過去にあり、逆にコア側に新しい段を足して番号を振り直した例もあります。それぞれ後で見ます。まず、なぜ 3 段あたりに落ち着くのかを考えます。

## なぜ 1 段で済ませないのか

前々回、SRAM は速いが面積が大きい、と書きました。実は同じ SRAM でも、**大きくするほど遅くなります**。

- 容量が大きいと、回路の端から端までの配線が長くなり、信号が届くまでに時間がかかる
- 連想度を上げると、比較するタグが増える
- 大きいほど、1 回の読み出しで動かす回路が増え、電力を食う

つまり「32MB で 4 サイクル」のキャッシュは作れません。作れるのは、「32KB で 4 サイクル」か「32MB で 40 サイクル」のどちらかです。

そこで、**段ごとに役割を変えます**。

| 段 | 何を優先するか | 典型的な容量 | 典型的なレイテンシ |
| --- | --- | --- | --- |
| L1 | とにかく速さ。パイプラインを止めない | 32〜64KB | 4〜5 サイクル |
| L2 | L1 から溢れたものを、そこそこ速く拾う | 1〜3MB | 12〜16 サイクル |
| L3 | メモリに行く回数を減らす。容量が主役 | 数十 MB | 40〜70 サイクル |

L1 は **ヒットしたときの速さ** を、L3 は **ミスしないこと** を最優先に設計されます。1 つのキャッシュで両方を満たすことはできないので、段に分けています。

## なぜ無限に増やさないのか

段を増やすと、間を細かく埋められます。それでも 3 段程度で止まるのは、**段を足すこと自体にコストがある**からです。

**外れたときに遅くなる。** L1 から L3 まで順に外れて、ようやくメモリに行きます。段が多いほど、メモリに行くまでに「ないことを確かめる時間」が積み重なります。

```
L1 を見る → ない → L2 を見る → ない → L3 を見る → ない → メモリへ
  4 サイクル       12 サイクル        40 サイクル        +200 サイクル
```

新しい段を足すなら、それで減らせるメモリアクセスの分が、**全員が余計に払う確認の時間**を上回らなければなりません。

**面積と電力を食う。** キャッシュは、今でも CPU のダイ面積の大きな割合を占めています。その面積はコアや演算器に回すこともできます。

**一致させる手間が増える。** 前回のコヒーレンシは、段ごとに写しを持つほど複雑になります。

結果として、**速さ重視の小さい段、中間の段、容量重視の大きい段** の 3 つに分けたあたりが、多くの設計で釣り合う点になっています。ただしこれは経験則で、条件が変われば段の数も変わります。

## コアごとか、みんなで共有か

段の数と同じくらい重要なのが、**その段を誰が使うか**です。典型的なデスクトップ向け CPU では、次のようになっています。

```
 ┌────────── コア 0 ──────────┐   ┌────────── コア 1 ──────────┐
 │  L1 命令 32KB  L1 データ 48KB │   │  L1 命令 32KB  L1 データ 48KB │  ...
 │        L2 2MB（専有）        │   │        L2 2MB（専有）        │
 └─────────────┬──────────────┘   └─────────────┬──────────────┘
               └──────────────┬──────────────────┘
                     L3 数十 MB（全コアで共有）
                              │
                         メインメモリ
```

**L1 は、命令用とデータ用に分かれています。** 命令の取り出しとデータの読み書きは、パイプラインの別の段で同時に起きます。1 つのキャッシュで両方を受けると取り合いになるので、入口を分けます。L2 以降は、命令もデータも区別せずに持ちます。

**L1 と L2 は、多くの場合コアごとの専有です。** 近くに置けるので速く、他のコアに邪魔されません。

**L3 は、全コアで共有します。** 容量が大きいので、コアごとに分けると使い切れないコアと足りないコアが出ます。共有にすれば、忙しいコアが多く使えます。また、あるコアが書いたデータを別のコアが読むとき、メモリまで降りずに L3 で受け渡せます。

<Callout type="note" title="共有の単位は製品によって違う">
  「L3 は全コアで共有」は典型例で、例外がいくつもあります。

  - AMD Ryzen は、8 コアをまとめた単位（CCD）ごとに L3 を持つ。16 コアの製品では L3 が 2 つに分かれ、**別の CCD の L3 は直接には使えない**
  - Intel の省電力コア（E コア）は、4 コアで 1 つの L2 を共有する
  - Apple M シリーズは、コアのまとまり（クラスタ）ごとに大きな L2 を共有し、その外側に後述の SLC を置く

  スレッドをどのコアに置くかで性能が変わることがあるのは、このためです。
</Callout>

共有の L3 は、物理的には 1 つの塊ではありません。コアの数だけ **スライス** に分けて並べ、リング状や網目状の配線で繋いでいます。アドレスによってどのスライスに載るかが決まるので、**同じ L3 でも、近いスライスは速く、遠いスライスは遅い**ということが起きます。

## 上の段の中身は、下の段にもあるのか

段が複数あると、「L1 にあるデータは L2 や L3 にも入っているのか」という問題が生じます。設計は 3 通りあります。

| 方式 | 下の段の中身 | 利点 | 欠点 |
| --- | --- | --- | --- |
| **包含**（inclusive） | 上の段の中身をすべて含む | 下の段を見れば、上の段にあるかどうか分かる | 同じデータを二重に持つので、実質の容量が減る |
| **排他**（exclusive） | 上の段の中身を含まない | 合計した容量をまるごと使える | 段の間でデータを移し替える手間がかかる |
| **非包含**（non-inclusive） | 含むとも含まないとも決めない | 両者の中間 | 「どこにあるか」を別の仕組みで管理する必要がある |

包含の利点は、コヒーレンシで効きます。他のコアがあるアドレスを書き換えたとき、L3 を見て「持っていない」と分かれば、そのコアの L1 や L2 を調べなくて済みます。

一方、L2 を大きくすると、包含では L3 の多くが L2 の写しで埋まってしまいます。実際、Intel はサーバ向けの Skylake-SP で L2 を 1MB に増やしたのと同時に、L3 を包含から非包含に変えました（[ServeTheHome](https://www.servethehome.com/intel-xeon-scalable-processor-family-microarchitecture-overview/intel-skylake-sp-microarchitecture-l3-cache-inclusive-v-non-inclusive/)）。

非包含や排他の L3 は、多くの場合 **ビクティムキャッシュ** として動きます。メモリから読んだデータはまず L2 に入り、L2 から追い出されたもの（ビクティム）だけが L3 に入ります。L3 は「L2 に入りきらなかったものの控え」になります。

## 4 段目は存在する

では L4 はないのかというと、あります。ただし、**SRAM ではない**ことが多いのが特徴です。

**Intel の eDRAM。** Haswell や Broadwell の一部の製品は、CPU の横に 128MB の eDRAM（ロジックと同じ工程で作る DRAM）を別のチップとして載せ、L4 として使いました（[WikiChip](https://en.wikichip.org/wiki/intel/crystal_well)）。主な目的は内蔵 GPU の帯域を補うことでしたが、CPU からも使えます。L3 から追い出されたデータを受け取るビクティムキャッシュでした（[Chips and Cheese](https://chipsandcheese.com/p/broadwells-edram-vcache-before-vcache)）。

**Apple の SLC。** Apple M シリーズでは、CPU のクラスタ、GPU、その他の処理装置がすべて共有する **SLC**（System Level Cache）がメモリの手前にあります（[Chips and Cheese](https://chipsandcheese.com/p/igpu-cache-setups-compared-including-m1)）。CPU から見れば L2 の次の段なので、L3 と呼ぶこともできます。番号で呼ばず「システム全体のキャッシュ」と名付けているのは、CPU 専用ではないからです。

**IBM のメインフレーム。** IBM Telum は、コアごとに 32MB という巨大な L2 を持ち、あるコアが使っていない L2 の空きを、他のコアの **仮想的な L3**（チップ内で最大 256MB）や **仮想的な L4**（筐体内で最大 2GB）として貸し出します（[IBM Telum - Wikipedia](https://en.wikipedia.org/wiki/IBM_Telum)）。専用の L3 や L4 の回路を持たず、段の境界を固定しない設計です。

<Callout type="tip" title="段を増やす代わりに、1 段を厚くする">
  AMD の 3D V-Cache は、L3 の上にもう 1 枚の SRAM を積み重ね、
  L3 の容量を 32MB から 96MB に増やします。
  新しい段は作りません。**段を足すと外れたときに遅くなる**という問題を避け、
  既存の段を大きくする方を選んでいます。
</Callout>

## 番号は振り直される

逆に、コアの内側に段が足されることもあります。

Intel の Lion Cove コアは、従来の L1 データキャッシュの位置に 48KB の **L0** を置き、その後ろに 192KB の **L1** を新設しました。L2 は最大 3MB で、その先に共有の L3 が続きます（[Chips and Cheese](https://chipsandcheese.com/p/lion-cove-intels-p-core-roars)）。

| 段 | 容量 | レイテンシ |
| --- | --- | --- |
| L0 | 48KB | 4 サイクル |
| L1 | 192KB | 9 サイクル |

従来なら「L1 と L2 の間に 1 段足した」と表現するところを、名前をずらして 0 から数え直しています。**番号は「コアから何番目か」でしかない**ことがよく分かる例です。

## 自分のマシンで確かめる

前々回のコマンドで、段ごとの容量に加えて、共有の単位も確認できます。

```bash
# Linux: index0〜3 がそれぞれ L1 データ、L1 命令、L2、L3
grep . /sys/devices/system/cpu/cpu0/cache/index*/{level,type,size,shared_cpu_list}

# 段と共有関係を図で表示する（hwloc パッケージ）
lstopo --no-io

# macOS: perflevel0 が高性能コア、perflevel1 が省電力コア
sysctl hw.perflevel0 hw.perflevel1 | grep -i cache
```

`shared_cpu_list` を見ると、その段がどのコア（論理 CPU）の間で共有されているかが分かります。L1 と L2 では自分と同じ物理コアのハイパースレッドだけ、L3 では全コアが並ぶ、という形が典型です。

## まとめ

- L1、L2、L3 の番号は、コアから何番目かを表すだけ。最後の段を LLC と呼ぶ
- SRAM は大きくするほど遅くなる。だから速さ重視の段と容量重視の段に分ける
- 段を足すと、外れたときの確認時間が全員に上乗せされる。多くの設計が 3 段で釣り合う
- L1 は命令とデータに分かれる。L1 と L2 はコアごと、L3 は共有が典型
- 下の段が上の段の中身を含むかどうかで、包含・排他・非包含がある
- L4 は存在する。eDRAM、SoC 全体で共有する SLC、他のコアの L2 を借りる仮想 L4 など、形はさまざま
