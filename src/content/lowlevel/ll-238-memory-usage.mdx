## 「メモリが足りない」と言われたら

監視画面で free が 1 割を切っている。コンテナが前触れなく再起動を繰り返す。プロセスの RSS を全部足したら、搭載量を超えていた。どれも「メモリが足りないのでは」という相談の入口としてよく出てきますが、本当に足りないのはこのうち一部だけです。

第 24 回で、`malloc` は約束をするだけで、触ったときに初めて物理ページが割り当てられることを見ました。第 220 回では、コンテナの `--memory` が cgroup の `memory.max` になり、超えると殺されることを見ました。この回では、それらの仕組みが**数字としてどこに現れるか**を読む側に回ります。調べる順番は、次の 3 つの問いです。

1. マシン全体で、まだ使える量はどれだけあるか（`free` の `available`）
2. 誰が使っているのか（プロセスの RSS と PSS、cgroup の `memory.stat`）
3. 上限はどこにあり、超えたら誰が殺されるのか（`memory.max` と OOM killer）

下のシミュレーターは、16 GiB のマシンでファイルの読み込み、`malloc`、書き込み、`fork`、別プロセスの確保を順に行い、最後に OOM killer が動くまでを 1 手ずつ追います。`free` の各列と、プロセスごとの数字がどこで動き、どこで動かないかに注目してください。

この回の実測は、Apple M1 Pro の上の OrbStack が動かす Linux VM（カーネル 7.0.14、メモリ 16 GiB、スワップ 17 GiB、cgroup v2）で、Debian trixie のコンテナ（procps-ng 4.0.4）を `docker run --rm` で起動して行いました。VM の中では他のコンテナも動いているので、`used` の値には自分以外の分も含まれています。

## free の 6 つの列

`free` は `/proc/meminfo` を読んで整形しているだけです。man ページは、各列の出どころを次のように書いています（[free(1)](https://man7.org/linux/man-pages/man1/free.1.html)）。

| 列 | man ページの説明 | `/proc/meminfo` の欄 |
| --- | --- | --- |
| total | Total usable memory | `MemTotal` |
| used | Used or unavailable memory (calculated as total - available) | （計算値） |
| free | Unused memory | `MemFree` |
| shared | Memory used (mostly) by tmpfs | `Shmem` |
| buff/cache | Sum of buffers and cache | `Buffers` + `Cached` + `SReclaimable` |
| available | Estimation of how much memory is available for starting new applications, without swapping | `MemAvailable` |

大事なのは、**free は「何にも使われていないページ」であって、「これから使える量」ではない**ことです。第 48 回で見たとおり、カーネルは読み書きしたファイルの内容をページキャッシュとして残します。空いているメモリを遊ばせておく理由が無いからです。ページキャッシュは中身がディスクにあるので、必要になれば捨てて別の用途に回せます。

実際に 1 GiB のファイルを読んで確かめます。先にページキャッシュを捨ててから（`drop_caches` は VM 全体に効くので `--privileged` が要ります）、ファイルを読む前後で `free -m` を取りました。

```bash
dd if=/dev/urandom of=/tmp/big bs=1M count=1024 status=none; sync
echo 3 > /proc/sys/vm/drop_caches
free -m
cat /tmp/big > /dev/null
free -m
```

```text
## drop 後
               total        used        free      shared  buff/cache   available
Mem:           16040        5045       10880         137         497       10994
Swap:          17064           0       17064
## 1 GiB を読んだ後
               total        used        free      shared  buff/cache   available
Mem:           16040        5032        9808         137        1582       11008
Swap:          17064           0       17064
```

free は 1,072 MiB 減り、buff/cache が 1,085 MiB 増えました。一方で available と used はほとんど動いていません。**ファイルを読むと free は減るが、使える量は減らない**のです。同じファイルをもう一度読むと、ディスクに行かずに済むので速くなります。

```text
## もう一度読む（時間）
real	0m0.147s
## キャッシュを捨てて読む（時間）
real	0m0.285s
```

used の計算式にも注意が要ります。手元の procps-ng 4.0.4 では、上の表のとおり `total - available` です。drop 後の行で確かめると、16040 − 10994 = 5046 で、表示の 5045 とは丸めの差しかありません。`free` の版によって used の計算式が違うことがあるので、別の環境の数字と比べるときは、その環境の `man free` を確かめてください。

### available は推定値である

`MemAvailable` の欄は、2014 年にカーネル 3.14 で入りました。それまでは、利用者が `free` と `cached` を足して「使える量」を見積もるのが普通でした。この欄を足したコミットは、その見積もりが外れる理由をこう説明しています（[34e431b0ae39](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/commit/?id=34e431b0ae398fc54ea69ff85ec700722c9da773)）。

> It is wrong because Cached includes memory that is not freeable as page cache, for example shared memory segments, tmpfs, and ramfs, and it does not include reclaimable slab memory, which can take up a large fraction of system memory on mostly idle systems with lots of files.

`Cached` には、tmpfs や共有メモリのように捨てられないものが含まれます。逆に、ファイルシステムが持っている dentry や inode のキャッシュ（回収できるスラブ、`SReclaimable`）は含まれません。そこでカーネル自身が推定して出すことにした、というのがこの欄です。カーネルの文書は、推定の材料を次のように書いています（[The /proc Filesystem](https://docs.kernel.org/filesystems/proc.html)）。

> Calculated from MemFree, SReclaimable, the size of the file LRU lists, and the low watermarks in each zone.

watermark は、カーネルが回収を始める目安として空けておく量です。つまり available は、「空いている量に、捨てられるキャッシュを足し、カーネルが常に空けておきたい分を引いたもの」の推定値で、上のシミュレーターのような単純な足し算より控えめに出ます。それでも、**新しく何かを動かす余地を知りたいなら、見る列は available** です。`free` が 0 に近くても、available に余裕があれば問題ありません。

## プロセスが使っている量

次に、誰が使っているのかを見ます。第 24 回で、`ps` や `top` に出る VSZ（約束した仮想アドレス空間の広さ）と RSS（実際に物理メモリに載っている量）の違いを見ました。この差は、確保した瞬間と書き込んだ瞬間を分けて測るとはっきりします。

```c
size_t n = 512UL << 20;
show("起動直後");
char *p = malloc(n);
show("malloc(512 MiB) 後");
memset(p, 1, n / 2);
show("前半 256 MiB に書いた");
memset(p, 1, n);
show("全部に書いた");
```

`show` は `/proc/self/status` の `VmSize`（VSZ）と `VmRSS`、`/proc/meminfo` の `Committed_AS` を表示する関数です。

```text
起動直後            VmSize:	    2280 kB  VmRSS:	    1320 kB  Committed_AS:   15817052 kB
malloc(512 MiB) 後     VmSize:	  526572 kB  VmRSS:	    1324 kB  Committed_AS:   16341344 kB
前半 256 MiB に書いた  VmSize:	  526572 kB  VmRSS:	  263468 kB  Committed_AS:   16353124 kB
全部に書いた      VmSize:	  526572 kB  VmRSS:	  525612 kB  Committed_AS:   16341564 kB
```

`malloc` の直後、VSZ は 512 MiB 増えましたが、RSS は 4 kB しか増えていません。書いたぶんだけ RSS が増え、全部に書いて初めて 512 MiB になります。

もう 1 つ動いた数字が `Committed_AS` です。`malloc` の時点で約 512 MiB 増えています。man ページは、この欄を「The amount of memory presently allocated on the system.」と説明し、触っていないぶんも含めた**約束の総量**だとしています（[proc_meminfo(5)](https://man7.org/linux/man-pages/man5/proc_meminfo.5.html)）。マシン全体で約束の総量が物理メモリを超えていても、全員が一度に使わなければ問題は起きません。

### オーバーコミットの 3 つのモード

約束をどこまで許すかは、`vm.overcommit_memory` で決まります。カーネルの文書は 3 つのモードを定めています（[Overcommit Accounting](https://docs.kernel.org/mm/overcommit-accounting.html)）。

| 値 | 文書での名前 | 振る舞い |
| --- | --- | --- |
| 0 | Heuristic overcommit handling | 明らかに無理な確保だけを拒否する。文書には「This is the default.」とある |
| 1 | Always overcommit | 確保を拒否しない |
| 2 | Don't overcommit | 約束の総量を「スワップ + 物理メモリの一定割合（既定 50%）」までに抑える |

モード 2 では、上限は `/proc/meminfo` の `CommitLimit` に出ます。上限を超える `malloc` は NULL を返すので、**殺される代わりに確保が失敗する**ようになります。文書はこれを「in most situations this means a process will not be killed while accessing pages but will receive errors on memory allocation as appropriate.」と書いています。ただし、多くのプログラムは確保の失敗を想定して作られていないので、モード 2 にすれば安全というわけではありません。

今回の VM では `cat /proc/sys/vm/overcommit_memory` が `1` でした。既定の 0 ではありません。OrbStack の VM がこう設定しているためで、**手元の環境の設定は、配布物の既定と同じとは限りません**。

### 共有されたページと PSS

RSS には、他のプロセスと共有しているページも全部入ります。第 234 回で触れたとおり、全プロセスの RSS を足すと物理メモリを超えることがあります。これを実際に起こしてみます。

親が 256 MiB を確保して全部に書き、`fork` で子を 3 つ作ります。どの子も書き込まずに止まっているので、第 24 回のコピーオンライトにより、4 つのプロセスが同じ物理ページを共有します。その後、子 1 だけに 256 MiB 全部を書かせます。それぞれの時点で、4 プロセスの `/proc/<pid>/smaps_rollup` と `free -m` を取りました。

```text
## 確保前
Mem:           16040        5053       10330         142        1043       10986
## fork で 3 つ増やした直後（どれも書いていない）
pid 1  Rss:  257 MiB  Pss:   64 MiB  Shared_Dirty:  256 MiB  Private_Dirty:    0 MiB
pid 14  Rss:  256 MiB  Pss:   64 MiB  Shared_Dirty:  256 MiB  Private_Dirty:    0 MiB
pid 15  Rss:  256 MiB  Pss:   64 MiB  Shared_Dirty:  256 MiB  Private_Dirty:    0 MiB
pid 16  Rss:  256 MiB  Pss:   64 MiB  Shared_Dirty:  256 MiB  Private_Dirty:    0 MiB
               total        used        free      shared  buff/cache   available
Mem:           16040        5317       10064         142        1046       10723
## 子 1 だけが 256 MiB 全部に書いた後
pid 1  Rss:  257 MiB  Pss:   85 MiB  Shared_Dirty:  256 MiB  Private_Dirty:    0 MiB
pid 14  Rss:  256 MiB  Pss:  256 MiB  Shared_Dirty:    0 MiB  Private_Dirty:  256 MiB
pid 15  Rss:  256 MiB  Pss:   85 MiB  Shared_Dirty:  256 MiB  Private_Dirty:    0 MiB
pid 16  Rss:  256 MiB  Pss:   85 MiB  Shared_Dirty:  256 MiB  Private_Dirty:    0 MiB
               total        used        free      shared  buff/cache   available
Mem:           16040        5585        9770         142        1072       10454
```

fork の直後、RSS の合計は約 1 GiB ですが、used は確保前から 264 MiB しか増えていません。実際に使っているのは 256 MiB ぶんです。PSS の合計は 64 × 4 = 256 MiB で、こちらは実際の量に合います。

PSS（Proportional Set Size）は、カーネルの文書で次のように定義されています（[The /proc Filesystem](https://docs.kernel.org/filesystems/proc.html)）。

> The "proportional set size" (PSS) of a process is the count of pages it has in memory, where each page is divided by the number of processes sharing it.

子 1 が書くと、その子の分だけページが複製されます。子 1 の 256 MiB はすべて `Private_Dirty`（自分だけが持つ、書き換えたページ）になり、PSS も 256 MiB です。残りの 3 プロセスは元のページを 3 で割って 85 MiB ずつになりました。used は 268 MiB 増えています。**RSS は 4 行とも 256 MiB のまま変わっていない**ので、RSS だけを見ていると、この 268 MiB がどこから来たのか分かりません。

`smaps_rollup` で見られる欄のうち、よく使うのは次の 4 つです。

| 欄・呼び名 | 意味 | 何に使うか |
| --- | --- | --- |
| Rss | 物理メモリに載っているページの数。共有ページも 1 枚として数える | `top` や `ps` に出る値。OOM killer の計算にも使われる |
| Pss | 共有ページを、共有しているプロセスの数で割って足したもの | プロセスごとの実質的な消費。全プロセスの合計が実際の量に近くなる |
| Private_Clean + Private_Dirty | そのプロセスだけが持つページ | **そのプロセスを殺したら戻ってくる量** |
| Swap | スワップに追い出されたページ | 物理メモリには載っていないが、使っている量 |

3 行目は USS（Unique Set Size）と呼ばれることがあります。カーネルの欄の名前ではなく、`smem` という道具が使う呼び名で、man ページは「Unshared memory is reported as the USS (Unique Set Size).」と書いています（[smem(8)](https://man7.org/linux/man-pages/man8/smem.8.html)）。PostgreSQL や Apache のように、同じプログラムを `fork` して何十個も並べるサーバでは、RSS の合計は大きく出ます。1 プロセス増やすといくら増えるのかを見積もるなら PSS、1 プロセス止めたらいくら空くのかを知りたいなら USS を見ます。

## スワップ: si と so

物理メモリが足りなくなると、カーネルはまずページキャッシュを捨て、それでも足りなければ匿名メモリ（ヒープやスタックのように、裏にファイルが無いページ）をスワップに追い出します（第 24 回）。この動きは `vmstat` の `si`（swap in、スワップから読み戻した量）と `so`（swap out、スワップへ書き出した量）に出ます。単位は 1 秒あたりの KiB です。

VM 全体を追い詰めると他のコンテナに迷惑がかかるので、cgroup の中だけで起こします。`--memory=128m --memory-swap=512m` は、物理メモリ 128 MiB と、スワップを合わせて 512 MiB まで使えるという指定です。その中で 300 MiB を確保して書き込み、横で `vmstat 1` を取りました。

```text
memory.max=128MiB memory.swap.max=384MiB

 6  0      0 10519876    172 1174152    0    0  6773   118 3108    6  4  2 94  0  0  0
 6  0      0 10514272    172 1180708    0    0  5528     0 14372 16747 50 10 40  0  0  0
12  0 179368 10359692    172 1168068  176 179560 31776 179864 14962 19717 50 14 36  0  0  0
 4  0 179360 10349580    172 1173292   24    0  3960  1348 16766 21948 51 11 37  1  0  0
 4  0 179360 10347072    172 1175792    0    0  2500     0 12150 15855 50 10 40  0  0  0

memory.current=127MiB memory.swap.current=178MiB
VmRSS:	  124524 kB
VmSwap:	  183248 kB
```

3 行目で `so` が約 175 MiB/秒になり、`swpd`（スワップに出ている総量）が 179,368 KiB に増えました。上限の 128 MiB を超えた分がスワップに出され、プロセスの `VmRSS` は 122 MiB、`VmSwap` は 179 MiB です。VM 全体の `free` は 10 GiB 近く残っているのに、**cgroup の上限に当たったプロセスだけがスワップしています**。

`vmstat` の読み方は次のとおりです。

- `swpd` が大きいこと自体は問題ではありません。一度追い出されて、その後使われていないページが溜まっているだけかもしれません。
- `so` が続いているときは、メモリが足りなくて追い出し続けています。
- `si` と `so` が両方とも続いているときは、追い出したページをすぐに読み戻し、また追い出しています。第 24 回のスラッシングで、性能が壊れている状態です。

## コンテナの中の free は、ホストの数字を出す

上の実験で、`free` は 10 GiB 近い空きを示していました。コンテナの中で `free` を実行すると、何が出るのでしょうか。`--memory=128m` のコンテナで試しました。

```text
memory.max=134217728
## コンテナの中の free（ホスト VM 全体の値が出る）
               total        used        free      shared  buff/cache   available
Mem:           16040        5236        9906         142        1285       10804
```

total は 16 GiB のままです。`/proc/meminfo` は名前空間で分けられていないので、**コンテナの中の `free` や `top` には、VM 全体の値が出ます**。このコンテナが使えるのは 128 MiB なのに、available は 10 GiB と表示されます。第 220 回の「ランタイムが制限に気づかない」と同じ問題で、`free` を見てメモリに余裕があると判断してはいけません。

コンテナの使用量は、cgroup のファイルで見ます。同じコンテナで 512 MiB のファイルを書いてから読み、`memory.stat` の `anon` と `file`、`memory.current` を取りました。

```text
## 起動直後
anon=0MiB file=0MiB current=0MiB
## 512 MiB のファイルを書いた後
anon=0MiB file=126MiB current=127MiB
## それを読んだ後
anon=0MiB file=126MiB current=127MiB
max 4323
oom 0
oom_kill 0
```

cgroup v2 の文書は、`anon` を「Amount of memory used in anonymous mappings such as brk(), sbrk(), and mmap(MAP_ANONYMOUS).」、`file` を「Amount of memory used to cache filesystem data, including tmpfs and shared memory.」と説明しています（[Control Group v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)）。

このコンテナはプロセスとしては何も確保していないのに、`memory.current` は上限ぎりぎりの 127 MiB です。全部がページキャッシュ（`file`）です。第 220 回で「ページキャッシュも数えられる」と書いたのは、この状態のことです。

それでも殺されてはいません。`memory.events` の 3 つの欄の意味は、文書によると次のとおりです。

| 欄 | 文書の説明 |
| --- | --- |
| max | The number of times the cgroup's memory usage was about to go over the max boundary.  If direct reclaim fails to bring it down, the cgroup goes to OOM state. |
| oom | The number of time the cgroup's memory usage was reached the limit and allocation was about to fail. |
| oom_kill | The number of processes belonging to this cgroup killed by any kind of OOM killer. |

`max` は 4,323 回、上限を超えそうになったことを示しています。そのたびにカーネルは自分のページキャッシュを捨て（direct reclaim）、上限の中に収めました。`oom` と `oom_kill` が 0 なので、OOM には至っていません。**`memory.current` が上限に張り付いていても、`file` が大半なら問題は起きていない**と読みます。監視の閾値を `memory.current` に置くと、ファイルを読み書きするだけのコンテナで誤報が出ます。`anon` を見るか、`memory.events` の `oom_kill` の増加を見るのが確実です。

## OOM killer は誰を選ぶのか

回収できるものが尽きると、OOM killer が動きます。第 24 回では「たいてい、最もメモリを使っているプロセスが選ばれる」と書きました。どう比べているのかを、カーネルのソースで確かめます。選ぶときの点数を計算する関数 `oom_badness` は、次のとおりです（[mm/oom_kill.c](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/mm/oom_kill.c)）。

```c
	/*
	 * The baseline for the badness score is the proportion of RAM that each
	 * task's rss, pagetable and swap space use.
	 */
	points = get_mm_rss_sum(p->mm) + get_mm_counter_sum(p->mm, MM_SWAPENTS) +
		mm_pgtables_bytes(p->mm) / PAGE_SIZE;
	task_unlock(p);

	/* Normalize to oom_score_adj units */
	adj *= totalpages / 1000;
	points += adj;
```

点数は、**RSS とスワップに出ている量とページテーブルの大きさの合計**に、`oom_score_adj` を足したものです。`oom_score_adj` は −1000 から +1000 で、`totalpages / 1000` 倍されてから足されます。`totalpages` は使ってよいメモリの総量なので、adj を +500 にすると「使ってよい量の半分を余計に使っている」扱いになります。また、この関数の前半には、`oom_score_adj` が −1000（`OOM_SCORE_ADJ_MIN`）なら候補から外す処理があります。

ここで RSS を使っていることに注意してください。前の節の `fork` の実験のように、共有しているページは**共有しているプロセス全員に、まるごと数えられます**。PSS ではありません。

### totalpages は、どこで足りなくなったかで変わる

`totalpages` が何を指すかは、OOM が起きた場所で変わります。カーネルの文書は次のように書いています（[The /proc Filesystem](https://docs.kernel.org/filesystems/proc.html)）。

> If it is due to a memory limit (or swap limit) being reached, the allowed memory is that configured limit.  Finally, if it is due to the entire system being out of memory, the allowed memory represents all allocatable resources.

ソースでも、cgroup の上限に当たった場合は `oc->totalpages = mem_cgroup_get_max(oc->memcg)` と、上限の値を使っています。

ところが、`/proc/<pid>/oom_score` で見える値は、**常にマシン全体を分母にして計算されています**。`fs/proc/base.c` の該当部分です（[fs/proc/base.c](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/fs/proc/base.c)）。

```c
	unsigned long totalpages = totalram_pages() + total_swap_pages;
	...
	if (badness != LONG_MIN)
		points = (1000 + badness * 1000 / (long)totalpages) * 2 / 3;
```

`--memory=512m` のコンテナで、200 MiB と 50 MiB を書いて止まるプロセスを並べ、`oom_score` を見ました。

```text
memory.max=512MiB
## そのまま
pid 11   RSS  201 MiB  oom_score_adj     0  oom_score  670
pid 12   RSS   51 MiB  oom_score_adj     0  oom_score  667
## 小さい方に oom_score_adj=1000
pid 11   RSS  201 MiB  oom_score_adj     0  oom_score  670
pid 12   RSS   51 MiB  oom_score_adj  1000  oom_score 1334
## 小さい方に oom_score_adj=-1000
pid 11   RSS  201 MiB  oom_score_adj     0  oom_score  670
pid 12   RSS   51 MiB  oom_score_adj -1000  oom_score    0
```

RSS が 4 倍違うのに、点数は 670 と 667 でほとんど同じです。上の式で計算すると理由が分かります。分母の `totalpages` は物理メモリ 16,040 MiB とスワップ 17,064 MiB の合計で、約 33 GiB です。201 MiB はその 0.6% なので `badness * 1000 / totalpages` は 6、51 MiB なら 1 です。(1000 + 6) × 2 / 3 = 670、(1000 + 1) × 2 / 3 = 667 になります。adj を 1000 にすると `badness` に `totalpages` がそのまま足されるので (1000 + 1000 + 1) × 2 / 3 = 1334、−1000 なら候補外として 0 です。

実際にこのコンテナで OOM が起きれば、分母は 512 MiB になり、201 MiB のプロセスは約 39%、51 MiB のプロセスは約 10% として比べられます。**`oom_score` の数字の大きさは、コンテナの中での危なさを表していません**。順位を比べる材料としてだけ使ってください。

### OOM kill の記録を読む

最後に、実際に殺させて記録を読みます。`--memory=128m --memory-swap=128m`（スワップなし）のコンテナで、16 MiB ずつ確保して書き込むプログラムを動かしました。

```text
96 MiB 書いた
112 MiB 書いた
終了コード: 137
max 5084
oom 1
oom_kill 1
```

112 MiB まで書いたところで殺され、終了コードは 137（128 + `SIGKILL` の 9、第 220 回）でした。`memory.events` の `oom` と `oom_kill` が 1 ずつ増えています。カーネルのログ（`dmesg`）には、次の 2 行が残りました。1 行目は長いので、cgroup のパスを途中で省いています。

```text
[955919.765017] oom-kill:constraint=CONSTRAINT_MEMCG,nodemask=(null),cpuset=424effdacfd8…,mems_allowed=0,oom_memcg=/scon/container/…/docker/424effdacfd8…,task_memcg=/scon/container/…/docker/424effdacfd8…,task=grow,pid=3227256,uid=0
[955919.765115] Memory cgroup out of memory: Killed process 3227256 (grow) total-vm:133384kB, anon-rss:130608kB, file-rss:1192kB, shmem-rss:0kB, UID:0 pgtables:300kB oom_score_adj:0
```

読むところは次のとおりです。

| 項目 | この例の値 | 読み方 |
| --- | --- | --- |
| `constraint` | `CONSTRAINT_MEMCG` | cgroup の上限に当たった。マシン全体が足りないなら `CONSTRAINT_NONE` |
| `oom_memcg` | コンテナの cgroup | どの cgroup の上限に当たったか |
| `task_memcg`、`task`、`pid` | 同じ cgroup の `grow` | 殺されたプロセスと、その所属 |
| `total-vm` | 133,384 kB | VSZ |
| `anon-rss` / `file-rss` / `shmem-rss` | 130,608 / 1,192 / 0 kB | 殺された時点の RSS の内訳。ほぼ全部が匿名メモリ |
| `pgtables` | 300 kB | ページテーブルの大きさ。点数に足される |
| `oom_score_adj` | 0 | 調整値 |

`oom_memcg` と `task_memcg` が同じなので、**自分の上限に当たって、自分の中から 1 つ選ばれた**と分かります。`constraint=CONSTRAINT_NONE` で、殺されたのが自分のコンテナだった場合は、マシン全体が足りなくなり、たまたま自分が最も点数が高かったということです。前者なら自分の上限を見直し、後者ならマシン全体の詰め込みすぎを疑います。

## リークか、断片化か、キャッシュか

メモリが増え続ける、という相談の多くは、次の 3 つのどれかです。どれかによって、次に使う道具が違います。

| 見えている形 | 疑うもの | 次にやること |
| --- | --- | --- |
| `memory.current` や buff/cache が高いが、`anon` や RSS は低い | ページキャッシュ。問題ではない | available と `memory.events` の `oom_kill` を確かめて終わる |
| 負荷が一定なのに、RSS が時間とともに単調に増える | メモリリーク。解放し忘れた確保が溜まっている | ヒープのプロファイラで、どこで確保されたものが残っているかを見る（第 234 回の `heaptrack`、`valgrind`） |
| 負荷の山で RSS が増え、山が過ぎても下がらないが、それ以上は増えない | アロケータが解放されたメモリを OS に返していない、あるいは断片化（第 25 回） | アロケータの統計（glibc なら `malloc_stats`）でヒープの使用中の量と RSS の差を見る |
| GC のある言語で、上限に近づいてから OOM kill される | GC が上限を知らず、ゴミを溜めている（第 26 回） | ランタイムのヒープ統計を見て、`GOMEMLIMIT` や `-XX:MaxRAMPercentage` で上限を教える |

見分ける鍵は、**時間をかけて RSS を記録し、その形を見ること**です。1 回の `top` では、どの形なのか分かりません。`/proc/<pid>/smaps_rollup` の `Rss` と `Pss` を数分おきに記録するだけでも、増え続けているのか、上がって止まっているのかは分かります。

## 調べる順番

ここまでを、メモリの相談を受けたときの手順にまとめます。

1. `free -m` の **available** を見る。free や used は見ない。コンテナの中なら `free` は使わず、`/sys/fs/cgroup/memory.current` と `memory.max` を見る
2. 足りていないなら、`memory.stat` の `anon` と `file` で、プロセスが確保した量とページキャッシュを分ける
3. 誰が使っているかは、`ps aux --sort=-rss` で当たりを付け、同じプログラムが何個も動いているなら `smaps_rollup` の PSS で比べる
4. `vmstat 1` の `si` と `so` が続いていないかを見る
5. プロセスが消えたなら、終了コード 137、`memory.events` の `oom_kill`、`dmesg` の `Killed process` の行を探し、`constraint` と `oom_memcg` でどこの上限に当たったかを読む
6. 増え続けているなら、RSS を時間で記録して形を見る

## まとめ

- `free` の free は「何にも使われていないページ」。ファイルを読めば減るが、ページキャッシュは捨てられるので、使える量は減らない。見るべきは available
- available はカーネルが `MemAvailable` として出す推定値。free と cached を足す昔の見積もりは、tmpfs を含み、回収できるスラブを含まないので外れる
- `malloc` は VSZ と `Committed_AS` を増やすだけで、書き込むまで RSS は増えない。約束をどこまで許すかは `vm.overcommit_memory` で決まる
- RSS は共有ページを全員に数える。プロセスごとの実質的な消費は PSS、そのプロセスを止めたら空く量は USS（Private_Clean + Private_Dirty）
- `vmstat` の so が続けば追い出し続けている。si と so が両方続けばスラッシング
- コンテナの中の `free` はホストの値を出す。使用量は `memory.current` と `memory.stat` で見る。上限に張り付いていても、大半が `file` なら回収されるだけで殺されない
- OOM killer の点数は RSS + スワップ + ページテーブルに `oom_score_adj` を足したもの。`/proc/<pid>/oom_score` はマシン全体を分母にした値で、cgroup の中での危なさは表さない
- OOM のログの `constraint` と `oom_memcg` で、自分の上限に当たったのか、マシン全体が足りなかったのかを分ける
