## 自分のコードの外側

第 175 回と第 176 回では、自分たちが書いたコードと設定に問題がないかを機械で確かめました。しかし、本番で動いているものの大部分は、自分たちが書いたものではありません。

```
ソースのコミット ── 依存パッケージ ── CI の道具（Action など）
        │               │                  │
        └───────────────┴─── ビルド ───────┘
                              │
                     成果物（イメージ、tarball）
                              │ 公開
                         レジストリ
                              │ 取得
                       本番で動かす
```

矢印の 1 本 1 本が、中身をすり替えられる場所です。第 175 回の SCA は「**既知の脆弱性を持つ版**を使っていないか」を調べるものでした。この回で扱うのは、**悪意をもって差し込まれた中身**です。脆弱性のデータベースには、まだ載っていません。

第 160 回では、イメージを digest で固定し、BuildKit で SBOM と provenance を付け、cosign で署名するところまでを短く見ました。この回では、その一つ一つが**何を記録し、何を証明し、何を証明しないのか**を、実物の JSON を開いて確かめます。

## 攻撃の型

サプライチェーン攻撃は、どこに差し込むかでいくつかの型に分けられます。実際に起きた例と並べます。

| 型 | 何をするか | 実例 |
| --- | --- | --- |
| **typosquatting** | 人気のパッケージに似た名前で公開し、打ち間違いを待つ | 2017 年、npm の `crossenv`（本物は `cross-env`）など約 40 個が、環境変数を外部に送っていた（[The Register](https://www.theregister.com/2017/08/02/typosquatting_npm/)） |
| **依存の乗っ取り** | 正規のパッケージの保守権限を手に入れ、悪意ある版を出す | 2018 年、`event-stream` の保守を引き継いだ人物が `flatmap-stream` を依存に加え、特定の暗号資産ウォレットの鍵を狙った（[npm Blog](https://blog.npmjs.org/post/180565383195/details-about-the-event-stream-incident)） |
| **dependency confusion** | 社内だけで使うパッケージと同じ名前を公開レジストリに登録し、ビルドに公開側を選ばせる | 2021 年、研究者が 35 社以上の社内ビルドに自作のパッケージを取り込ませた（[BleepingComputer](https://www.bleepingcomputer.com/news/security/researcher-hacks-over-35-tech-firms-in-novel-supply-chain-attack/)） |
| **配布物だけの改ざん** | リポジトリには無いコードを、配布用の tarball にだけ入れる | 2024 年、xz-utils 5.6.0 以降の tarball に、ビルド時にバックドアを組み込む仕掛けが入っていた（[NVD CVE-2024-3094](https://nvd.nist.gov/vuln/detail/CVE-2024-3094)） |
| **ビルド環境の侵害** | ビルドの途中で成果物に手を加える | 2020 年、SolarWinds Orion の DLL が改ざんされ、**正規のコード署名証明書で署名されて**配布された（[CISA AA20-352A](https://www.cisa.gov/news-events/cybersecurity-advisories/aa20-352a)） |
| **CI の道具の書き換え** | CI が取得するスクリプトや Action を書き換え、CI の中のシークレットを盗む | 2021 年、Codecov の Bash Uploader が書き換えられ、CI の環境変数が送られた（[Codecov](https://about.codecov.io/security-update/)）。2025 年、`tj-actions/changed-files` のタグが悪意あるコミットに付け替えられ、シークレットがログに出た（[NVD CVE-2025-30066](https://nvd.nist.gov/vuln/detail/CVE-2025-30066)） |

いくつか、細部が重要な例があります。

xz-utils では、改ざんに使われた行が「配布された tarball にだけ」あり、上流の Git リポジトリには無かったことが報告されています（[oss-security](https://www.openwall.com/lists/oss-security/2024/03/29/4)）。**リポジトリのコードを読んでも見つからない**ということです。配布物が、どのソースから、どの手順で作られたかを確かめる手段が要ります。

SolarWinds では、改ざんされた DLL に正規の署名が付いていました。ビルドの途中で差し込まれたので、署名の工程はいつもどおり動いたからです。**署名は「誰が出したか」を証明しますが、「中身が意図したとおりに作られたか」は証明しません**。

Codecov では、Docker イメージを作る手順の誤りから、スクリプトを書き換えるための認証情報が抜き取られました（[Codecov](https://about.codecov.io/security-update/)）。CI の道具の 1 つが、それを使うすべての利用者の CI に届く入口になっていました。

### それぞれへの対策

| 型 | 主な対策 |
| --- | --- |
| typosquatting | 追加する依存を人が確かめる。SCA や専用の検査でよく似た名前を警告する |
| 依存の乗っ取り | ロックファイルで版とハッシュを固定し、更新を差分として確認する。provenance で「どのリポジトリから作られたか」を確かめる |
| dependency confusion | 社内パッケージにはスコープ（`@社名/`）や名前空間を使い、取得先のレジストリを 1 つに固定する |
| 配布物だけの改ざん | 配布物に provenance を付け、ソースのコミットとビルド基盤に結び付ける |
| ビルド環境の侵害 | ビルドを隔離された基盤で行い、その基盤が provenance を書いて署名する（SLSA Build L3） |
| CI の道具の書き換え | Action やスクリプトを内容のハッシュで固定する。CI に渡すシークレットを短命にする |

ロックファイルの `integrity`（第 103 回のハッシュ）は、「前回取得したものと同じ中身か」を確かめます。依存の乗っ取りでは、悪意ある**新しい版**に更新した時点でロックファイルも書き換わるので、ハッシュは更新を止めません。ハッシュで固定するのは、**中身が勝手に変わらないようにし、変わるときを差分として見えるようにする**ためです。

## Action を SHA で固定する理由

GitHub Actions のワークフローは、`uses: owner/repo@v4` のように Action を参照します。この `v4` は Git のタグか枝で、**持ち主が後から別のコミットに付け替えられます**。`tj-actions/changed-files` では、`v1` から `v45.0.7` までのタグがすべて悪意あるコミットを指すように付け替えられました（[NVD CVE-2025-30066](https://nvd.nist.gov/vuln/detail/CVE-2025-30066)）。タグで参照していたワークフローは、次の実行から何も変えずにその中身を動かしました。

GitHub のドキュメントは、完全な長さのコミット SHA に固定することを「Action を不変のリリースとして使う現時点で唯一の方法」としています（[GitHub Docs](https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions)）。

```yaml
- uses: actions/checkout@v4                                       # 付け替えられる
- uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2 付け替えられない
```

第 160 回のイメージのタグと digest と同じ関係です。SHA は Git のオブジェクトの中身のハッシュなので、同じ SHA で違う中身を指すことはできません。ただし、次の点に注意が要ります。

- SHA が**本家のリポジトリのもの**で、フォークのものではないことを確かめる（同じドキュメントが注意している）
- 固定した Action の中で、別の Action をタグで呼んでいれば、その先は固定されない
- 固定したままでは修正も届かない。Dependabot や Renovate に、SHA と版のコメントを一緒に更新させる

<Callout type="warn" title="固定は改ざんを防ぐが、悪い版を選ぶのは防がない">
  SHA で固定すると、**固定した時点の中身から変わらない**ことは保証されます。
  固定した時点ですでに悪い中身だった場合や、更新の PR で悪い版に上げてしまった場合は防げません。
  更新の差分を読むこと、CI に渡すシークレットを最小にして短命にすること（第 128 回、第 177 回）と組み合わせます。
</Callout>

## SLSA: 何をどこまで保証するか

**SLSA**（Supply-chain Levels for Software Artifacts）は、成果物が**どこで、何から、どう作られたか**の記録（provenance）と、その記録をどこまで信用できるかを段階で定めた枠組みです。v1.0 の Build トラックは、次の 4 段です（[SLSA v1.0 Levels](https://slsa.dev/spec/v1.0/levels)）。

| レベル | 要件 | 防げるもの |
| --- | --- | --- |
| Build L0 | なし | なし |
| Build L1 | ビルドの手順が一貫していて、provenance が作られ、配られる。**署名は無くてもよい** | リリース作業の誤り（上流に無いコミットからビルドした、など） |
| Build L2 | L1 に加えて、**ホストされたビルド基盤**が provenance を作り、**署名する** | ビルドの**後**の改ざん。署名があるので、provenance や成果物を後から差し替えると検証に落ちる |
| Build L3 | L2 に加えて、ビルドどうしが互いに影響できず、**署名に使う秘密をユーザが定義したビルドの手順から触れない** | ビルドの**途中**の改ざん。ビルドの手順を乗っ取っても、偽の provenance に署名できない |

L3 の要件が要です。L2 では、ビルドの手順（たとえば `npm install` で走る依存のスクリプト）が署名の鍵に届くなら、改ざんした成果物に「正しく作られた」という provenance を付けて署名できてしまいます。L3 は、**provenance を書いて署名するのはビルド基盤であり、ビルドされる側のコードではない**という分離を求めます。

SLSA が保証するのは、あくまで**記録の正しさ**です。「このコミットから、このワークフローで作られた」ことは確かめられますが、そのコミットに悪いコードが含まれていないことは保証しません。xz-utils の例で言えば、リポジトリに無いファイルを含む tarball は、そのリポジトリのコミットを指す provenance と食い違うはずなので、**検証する側がそれを求めていれば**見つけられます。乗っ取られた保守者が正規の手順でリポジトリに悪いコードを入れた場合は、provenance は正しく作られます。

## provenance の形: in-toto の attestation

provenance は、**in-toto の attestation** という入れ子の形式で書きます（[in-toto Attestation Framework](https://github.com/in-toto/attestation/blob/main/spec/README.md)）。

```
Envelope（DSSE）        署名と、署名した中身の型
  └ Statement           どの成果物（subject: 名前と digest）についての主張か
      └ Predicate       主張の中身。predicateType で種類を示す
                         （SLSA provenance、SPDX の SBOM、など）
```

**Statement** が成果物を digest で名指しし、**Predicate** に中身を書きます。同じ枠に provenance も SBOM も入るので、検証する側は「この digest について、どんな主張が、誰の署名で付いているか」を同じ方法で扱えます。

**DSSE**（Dead Simple Signing Envelope）は、中身の型（`payloadType`）と中身のバイト列を連結したものに署名します（[DSSE](https://github.com/secure-systems-lab/dsse)）。JSON を正規化してから署名する方式をやめ、**受け取ったバイト列そのものを検証する**ことで、正規化の実装の違いを突く攻撃をなくしています。

### BuildKit の provenance を開く

上のイメージを、provenance を詳しく残す `mode=max` と SBOM を付けてビルドし、手元のレジストリに送りました。

```bash
docker buildx build --provenance=mode=max --sbom=true \
  -t localhost:5178/ll178-app:1 --push .
```

レジストリから、タグが指すイメージインデックスを取り出します。

```bash
curl -s -H 'Accept: application/vnd.oci.image.index.v1+json' \
  http://localhost:5178/v2/ll178-app/manifests/1
```

```json
{ "mediaType": "application/vnd.oci.image.index.v1+json",
  "manifests": [
    { "digest": "sha256:386daa03...", "platform": { "architecture": "arm64", "os": "linux" } },
    { "digest": "sha256:499a4bb5...", "platform": { "architecture": "unknown", "os": "unknown" },
      "annotations": { "vnd.docker.reference.digest": "sha256:386daa03...",
                       "vnd.docker.reference.type": "attestation-manifest" } } ] }
```

（digest を短縮し、`mediaType` と `size` の一部を省略）

第 152 回で見たインデックスに、2 つ目の項目として**証明のためのマニフェスト**が加わっています。プラットフォームを `unknown/unknown` にしているのは、ランタイムがこれを誤って取得して動かさないようにするためです（[Docker Docs](https://docs.docker.com/build/metadata/attestations/attestation-storage/)）。その中を開くと、層が 2 つあります。

```
層 1  application/vnd.in-toto+json   88478 バイト   predicate-type: https://spdx.dev/Document
層 2  application/vnd.in-toto+json    6063 バイト   predicate-type: https://slsa.dev/provenance/v1
subject: sha256:386daa03...（イメージのマニフェスト）
```

SBOM と provenance が、どちらも in-toto の Statement として入っています。provenance の方を抜粋します。

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "predicateType": "https://slsa.dev/provenance/v1",
  "subject": [
    { "name": "pkg:docker/localhost%3A5178/ll178-app@1?platform=linux%2Farm64",
      "digest": { "sha256": "386daa0305bf22b5830d41c6d5b955fb872332cd8c8748e9975d66940fe48e17" } }
  ],
  "predicate": {
    "buildDefinition": {
      "buildType": "https://github.com/moby/buildkit/blob/master/docs/attestations/slsa-definitions.md",
      "resolvedDependencies": [
        { "uri": "pkg:docker/docker/buildkit-syft-scanner@stable-1?platform=linux%2Farm64",
          "digest": { "sha256": "ae4f3b55..." } },
        { "uri": "pkg:docker/alpine@3.20?platform=linux%2Farm64",
          "digest": { "sha256": "d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc" } }
      ],
      "externalParameters": {
        "configSource": { "path": "Dockerfile" },
        "request": { "frontend": "dockerfile.v0", ... }
      },
      "internalParameters": { "buildConfig": { "llbDefinition": [ ...6 つの手順... ] }, ... }
    },
    "runDetails": {
      "builder": { "id": "" },
      "metadata": {
        "startedOn": "2026-10-07T05:59:06.278938841Z",
        "buildkit_completeness": { "request": true, "resolvedDependencies": false }, ... }
    }
  }
}
```

フィールドの意味は SLSA の provenance の仕様が定めています（[SLSA v1.0 Provenance](https://slsa.dev/spec/v1.0/provenance)）。

| フィールド | 意味 | この実験で読み取れること |
| --- | --- | --- |
| `subject` | この provenance が述べている成果物 | イメージのマニフェストの digest |
| `externalParameters` | ビルドを頼んだ側が指定したもの。検証する側が期待と照らし合わせる | Dockerfile のパスと、使ったフロントエンド |
| `internalParameters` | ビルド基盤が内部で決めたもの | `mode=max` では、ビルドの全手順（LLB）と Dockerfile 本体の base64 まで入る |
| `resolvedDependencies` | ビルドが取り込んだもの | `FROM alpine:3.20` の**タグが digest に解決されて**記録されている |
| `runDetails.builder.id` | ビルドした基盤 | 空。手元のビルダーには、検証者が信用できる名前が無い |

ここから、3 つのことが分かります。

1 つ目は、**タグで書いたベースイメージも、実際に使った digest で記録される**ことです。後から `alpine:3.20` が別の中身に付け替えられても、このイメージが何から作られたかは追えます。

2 つ目は、`buildkit_completeness` の `resolvedDependencies: false` です。BuildKit は、`RUN apk add jq` が**ネットワークから取ってきたもの**を把握していません。provenance に載るのは、ビルドの仕組みが自分で取得したものだけです。`RUN` の中で取得したものは、SBOM の側（後で見ます）で中身から推定するしかありません。

3 つ目は、この JSON が**どこにも署名されていない**ことです。DSSE の封筒が無く、Statement がそのまま層として置かれています。レジストリに書き込める者なら、別の provenance に差し替えられます。SLSA で言えば L1 の状態です。L2 以上にするには、ビルド基盤がこれに署名する必要があります。

<Callout type="warn" title="mode=max はビルド引数の値も載せる">
  `mode=max` は、ビルド引数の値を provenance に含めます。
  ビルド引数で認証情報を渡していれば、それがイメージと一緒に配られます。
  Docker のドキュメントは、秘密はシークレットのマウントで渡すよう求めています（[Docker Docs](https://docs.docker.com/build/metadata/attestations/slsa-provenance/)）。
  既定の `mode=min` は、ビルド環境の情報を漏らさない最小限の内容です。
</Callout>

## Sigstore: 鍵を持たずに署名し、記録を公開する

第 128 回で、Sigstore の認証局 **Fulcio** が、CI の OIDC トークンの身元を書いた有効期間 10 分の証明書を発行する仕組みを見ました。ここでは、その証明書で作った署名を**後から誰がどう検証するのか**を、公開されている npm パッケージで確かめます。

### npm audit signatures

npm は、GitHub Actions などで公開したパッケージに provenance を付けられます（[npm Docs](https://docs.npmjs.com/generating-provenance-statements)）。Sigstore 自身の JavaScript 実装である `@sigstore/bundle` と、`ms` を入れて、`npm audit signatures` を実行しました。

```
$ npm ls --all
├─┬ @sigstore/bundle@4.0.0
│ └── @sigstore/protobuf-specs@0.5.2
└── ms@2.1.3

$ npm audit signatures
audited 3 packages in 1s

3 packages have verified registry signatures

2 packages have verified attestations
```

2 種類の検証が行われています。

- **レジストリの署名**: npm のレジストリが、公開されたパッケージに付けている署名。3 つすべてにある。「レジストリから受け取ったものが、レジストリが配ったものと同じ」ことを確かめる（[npm Docs](https://docs.npmjs.com/verifying-registry-signatures)）
- **attestation**: provenance が付いているのは `@sigstore/*` の 2 つだけで、`ms` には無い

レジストリの署名は、レジストリが乗っ取られたり、公開者のトークンが盗まれたりした場合には何も言いません。盗んだトークンで公開した版にも、レジストリは同じように署名するからです。**どこで作られたか**を言えるのは provenance の方です。

### attestation の中身

npm のレジストリから、この版の attestation を取り出しました。2 つ入っています。

```
$ curl -s 'https://registry.npmjs.org/-/npm/v1/attestations/@sigstore%2fbundle@4.0.0' \
  | jq '.attestations | map({predicateType, mt: .bundle.mediaType})'
[
  { "predicateType": "https://github.com/npm/attestation/tree/main/specs/publish/v0.1",
    "mt": "application/vnd.dev.sigstore.bundle+json;version=0.2" },
  { "predicateType": "https://slsa.dev/provenance/v1",
    "mt": "application/vnd.dev.sigstore.bundle.v0.3+json" }
]
```

1 つ目はレジストリが公開時に作る**公開の証明**、2 つ目が CI が作った **provenance** です（[npm Docs](https://docs.npmjs.com/generating-provenance-statements)）。どちらも **Sigstore の bundle** という形で、DSSE の封筒、証明書、透明性ログの記録をひとまとめにしています。provenance の封筒の中身を base64 から戻すと、次の Statement でした。

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [ { "name": "pkg:npm/%40sigstore/bundle@4.0.0",
                 "digest": { "sha512": "3700a5e58d15e838...292413f8" } } ],
  "predicateType": "https://slsa.dev/provenance/v1",
  "predicate": {
    "buildDefinition": {
      "buildType": "https://slsa-framework.github.io/github-actions-buildtypes/workflow/v1",
      "externalParameters": { "workflow": { "ref": "refs/heads/main",
        "repository": "https://github.com/sigstore/sigstore-js", "path": ".github/workflows/release.yml" } },
      "resolvedDependencies": [ { "uri": "git+https://github.com/sigstore/sigstore-js@refs/heads/main",
        "digest": { "gitCommit": "21dd66d041593ad5d9fc2fe461131d8db868ad6f" } } ] },
    "runDetails": {
      "builder": { "id": "https://github.com/actions/runner/github-hosted" },
      "metadata": { "invocationId": "https://github.com/sigstore/sigstore-js/actions/runs/16609504990/attempts/1" }

```

（`internalParameters` を省略し、digest を短縮）

手元のビルドと比べると、`builder.id` に GitHub がホストするランナーが入り、`resolvedDependencies` にソースのコミットが入っています。**どのリポジトリの、どのコミットから、どのワークフローで**作られたかが分かります。

`subject` の digest が、手元に落ちてきた tarball と同じものかを確かめます。npm のロックファイルの `integrity` は、tarball の SHA-512 を base64 で書いたものです。

```
$ jq -r '.packages["node_modules/@sigstore/bundle"].integrity' package-lock.json

$ echo -n 3700a5e58d15e838...292413f8 | xxd -r -p | base64
NwCl5Y0V6Di0NexvkTqdoVfmjTaQwoLM236r89KEojGmq/jMls8S+zb7yOwAPdXvbwfKDlP+lmXgAL4vKSQT+A==
```

一致しました。provenance は、**手元にあるこの tarball**について述べています。

### 証明書に書かれた身元

bundle に入っている証明書を OpenSSL で開きました。

```
$ openssl x509 -inform der -in cert.der -noout -subject -issuer -dates -ext subjectAltName
subject=
issuer=O=sigstore.dev, CN=sigstore-intermediate
notBefore=Jul 29 23:16:46 2025 GMT
notAfter=Jul 29 23:26:46 2025 GMT
X509v3 Subject Alternative Name: critical
    URI:https://github.com/sigstore/sigstore-js/.github/workflows/release.yml@refs/heads/main
```

有効期間はちょうど 10 分です。subject は空で、身元は SAN に**ワークフローのファイルの URI**として書かれています。第 109 回の証明書がドメイン名を SAN に書いたのと同じ場所に、「このリポジトリのこのワークフロー」が入っています。

拡張の欄には、Sigstore 独自の OID で、さらに細かい身元が入っていました（[Fulcio OID info](https://github.com/sigstore/fulcio/blob/main/docs/oid-info.md)）。

| OID（`1.3.6.1.4.1.57264.1.` に続く番号） | 名前 | 値 |
| --- | --- | --- |
| 8 | Issuer | `https://token.actions.githubusercontent.com` |
| 9 | Build Signer URI | `https://github.com/sigstore/sigstore-js/.github/workflows/release.yml@refs/heads/main` |
| 12 | Source Repository URI | `https://github.com/sigstore/sigstore-js` |
| 14 | Source Repository Ref | `refs/heads/main` |
| 21 | Run Invocation URI | `https://github.com/sigstore/sigstore-js/actions/runs/16609504990/attempts/1` |

provenance の中身（ビルド基盤が書いた主張）と、証明書の身元（Fulcio が OIDC トークンから確かめた事実）が、同じリポジトリ、同じワークフロー、同じ実行を指しています。検証する側は、この**両方**が期待どおりかを確かめます。

### 透明性ログ: 期限の切れた証明書をどう信じるか

証明書は 2025 年 7 月 29 日 23:26:46 に失効しています。それなのに今日の検証で通るのは、**署名がその 10 分の間に行われたことを、別の誰かが記録している**からです。それが透明性ログ **Rekor** です（[Sigstore Docs](https://docs.sigstore.dev/logging/overview/)）。bundle の中の記録を抜粋します。

```json
{
  "logIndex": "327695167",
  "kindVersion": { "kind": "dsse", "version": "0.0.1" },
  "integratedTime": "1753831006",
  "inclusionProof": {
    "rootHash": "lqGd7Ll+LOodM+mvsVNONCEur81F5L3YN050DRmpIZI=",
    "treeSize": "205790921",
    "checkpoint": { "envelope": "rekor.sigstore.dev - 1193050959916656506\n205790921\nlqGd7Ll+...\n\n— rekor.sigstore.dev wNI9ajBFAiEA..." }
  }
}
```

`integratedTime` の 1753831006 は、2025 年 7 月 29 日 23:16:46（UTC）です。証明書の `notBefore` と同じ秒で、有効期間の中に収まっています。`inclusionProof` は、第 111 回の Certificate Transparency と同じ Merkle 木の包含証明で、署名済みの木の根（checkpoint）に、この記録が含まれていることを示します。

同じ記録を、Rekor の公開 API からも読み出しました（読み取りだけです）。

```
$ curl -s 'https://rekor.sigstore.dev/api/v1/log/entries?logIndex=327695167' \
  | jq -r 'to_entries[0].value.body' | base64 -d | jq '.spec.payloadHash'
{ "algorithm": "sha256", "value": "4938e6292bbc5a38b76ed7214a071659898578fe06d806546f183c66791ecf96" }

$ jq -r '.attestations[] | select(.predicateType=="https://slsa.dev/provenance/v1")
         | .bundle.dsseEnvelope.payload' att.json | base64 -d | shasum -a 256
4938e6292bbc5a38b76ed7214a071659898578fe06d806546f183c66791ecf96  -
```

公開のログに記録された中身のハッシュと、npm から受け取った provenance のハッシュが一致しました。

透明性ログには、もう 1 つの役割があります。第 111 回で、ドメインの持ち主が CT のログを見張って、自分の知らない証明書を見つけられると書きました。同じように、リポジトリの持ち主は Rekor を見張り、**自分のワークフローの名前で、自分の知らない署名が作られていないか**を確かめられます。鍵を持たない署名は、記録を公開することで成り立っています。

<Callout type="note" title="公開のリポジトリと非公開のリポジトリ">
  Rekor の公開インスタンスに載せた記録は、誰でも読めます。リポジトリの名前やワークフローの名前も載ります。
  GitHub の artifact attestations は、公開リポジトリでは Sigstore の公開インスタンスを、
  非公開リポジトリでは GitHub が運用する Sigstore のインスタンスを使います（[GitHub Docs](https://docs.github.com/en/actions/concepts/security/artifact-attestations)）。
</Callout>

## 署名を手元で試す

公開のインスタンスに記録を残さないように、手元では**鍵を作って**署名しました。最初に作ったイメージの digest に cosign で署名し、手元のレジストリに置きます（透明性ログへの記録は止めています）。

```bash
cosign generate-key-pair
cosign sign --key cosign.key --use-signing-config=false --tlog-upload=false \
  localhost:5000/ll178-app@sha256:e89766b525fc183c087a48a9e55b185b1a079181e49bfd5075df172e6b34f13a
```

署名がどこに置かれたかを、レジストリのタグの一覧で確かめます。

```
$ curl -s localhost:5178/v2/ll178-app/tags/list
{"name":"ll178-app","tags":["sha256-e89766b525fc183c087a48a9e55b185b1a079181e49bfd5075df172e6b34f13a","1"]}
```

`sha256-<digest>` という名前のタグが増えています。その中身はインデックスで、`artifactType` が `application/vnd.dev.sigstore.bundle.v0.3+json` のマニフェストを 1 つ指していました。OCI の配布の仕様は、成果物に関係するもの（署名や SBOM）を引く **Referrers API** を定めていて、対応していないレジストリでは、このタグの名前の規則で代わりに置くことになっています（[OCI Distribution Spec](https://github.com/opencontainers/distribution-spec/blob/main/spec.md)）。手元の `registry:2` は Referrers API に 404 を返したので、こちらが使われました。

検証します。

```
$ cosign verify --key cosign.pub --insecure-ignore-tlog=true localhost:5000/ll178-app:1
Verification for localhost:5000/ll178-app:1 --
[{"critical":{"identity":{"docker-reference":"localhost:5000/ll178-app:1"},
  "image":{"docker-manifest-digest":"sha256:e89766b525fc183c087a48a9e55b185b1a079181e49bfd5075df172e6b34f13a"}, ...}]
```

（抜粋）

次に、別の Dockerfile でビルドしたイメージを、**同じタグ `1` に上書き**しました。

```
$ cosign verify --key cosign.pub --insecure-ignore-tlog=true localhost:5000/ll178-app:1
Error: no signatures found
```

タグは新しい digest を指すようになり、その digest には署名がありません。署名は**タグではなく digest に付いている**ので、タグを付け替えても署名は付いてきません。

この実験の検証の条件は「この公開鍵で署名されたか」だけです。キーレス署名では、第 160 回の `--certificate-identity` と `--certificate-oidc-issuer` で、上の表の SAN と Issuer を指定します。**どのリポジトリの、どのワークフローの、どの枝か**まで書かなければ、同じ CI を使う誰の署名でも通ってしまいます。

### GitHub artifact attestations

GitHub Actions には、ビルドした成果物に provenance を付けて Sigstore で署名する仕組みがあります（[GitHub Docs](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)）。

ワークフローに `id-token: write`（Fulcio に渡す OIDC トークン）と `attestations: write` の権限を与え、`actions/attest` のステップで成果物のパスを渡します。使う側は `gh attestation verify <成果物> -R <組織>/<リポジトリ>` で、そのリポジトリのワークフローが作ったものかを確かめます。

GitHub はこれだけで SLSA v1.0 Build L2 になり、組織で共有する再利用可能なワークフローでビルドすれば L3 に届くとしています（[GitHub Docs](https://docs.github.com/en/actions/concepts/security/artifact-attestations)）。L3 の「ビルドの手順から署名の秘密に触れない」を、呼び出す側のリポジトリが書き換えられないワークフローで実現する、という考え方です。

npm の **trusted publishing** も、同じ考え方で長期のトークンをなくします。CI の OIDC トークンで公開し、GitHub Actions と GitLab CI/CD から公開した場合は provenance が自動で付きます（[npm Docs](https://docs.npmjs.com/trusted-publishers)）。盗まれて使い回されるトークンが無くなるので、第 177 回の漏洩の経路が 1 つ減ります。

## SBOM: 何が入っているか

provenance が「どう作られたか」の記録なら、**SBOM**（Software Bill of Materials）は「何が入っているか」の記録です。広く使われている形式は 2 つです。

| 形式 | 出自 | 特徴 |
| --- | --- | --- |
| **SPDX** | Linux Foundation。ライセンスの管理から始まった | 要素どうしの関係（`CONTAINS`、`DEPENDENCY_OF` など）を明示的に書く。2.3 が広く使われている（[SPDX 2.3](https://spdx.github.io/spdx-spec/v2.3.1/)） |
| **CycloneDX** | OWASP。セキュリティの用途から始まった | 部品と依存の木を簡潔に書く。脆弱性や VEX も同じ形式で書ける。ECMA-424 として標準化された（[CycloneDX](https://cyclonedx.org/specification/overview/)） |

どちらも、部品を **purl**（Package URL）で名指しします（[purl spec](https://github.com/package-url/purl-spec)）。`pkg:種類/名前空間/名前@版?修飾子` という形で、エコシステムを問わず同じ書き方で部品を指せるので、SBOM と脆弱性のデータベースをつなぐ鍵になります。

### Syft で SBOM を作る

上のイメージを、Syft で 2 つの形式に書き出しました。

```bash

```

```

...
jq                      1.7.1-r0     apk

...

```

（17 行のうち一部）

SPDX で `jq` を見ると、こうなっています。

```json
{
  "name": "jq",
  "SPDXID": "SPDXRef-Package-apk-jq-b205586c099249e6",
  "versionInfo": "1.7.1-r0",
  "downloadLocation": "https://jqlang.github.io/jq/",
  "sourceInfo": "acquired package info from APK DB: /lib/apk/db/installed",
  "licenseDeclared": "MIT",

    { "referenceType": "cpe23Type", "referenceLocator": "cpe:2.3:a:jq:jq:1.7.1-r0:*:*:*:*:*:*:*" },
```

```json
  { "ref": "pkg:apk/alpine/jq@1.7.1-r0?...",
    "dependsOn": [ "pkg:apk/alpine/musl@1.2.5-r3?...", "pkg:apk/alpine/oniguruma@6.9.9-r0?..." ] }, ... ]
```

`sourceInfo` が示すとおり、Syft は `apk` のデータベース（`/lib/apk/db/installed`）を読んで部品を数えています。`RUN apk add jq` で入ったものは、provenance には載りませんでしたが、SBOM には載りました。**イメージの中身から推定する**からです。

### SBOM は「見えたもの」の一覧

一覧には、`package.json` に書いた依存の `ms` がありません。イメージに入れたのはロックファイルだけで、`node_modules` には何も入れていないからです。同じディレクトリを Syft に読ませると、ロックファイルから `ms` が見つかります。

```
$ syft dir:/src
NAME       VERSION  TYPE
ll178-app  1.0.0    npm
ms         2.1.3    npm
```

イメージを調べたときは**入っているもの**を、ソースを調べたときは**宣言されたもの**を数えています。どちらも正しく、意味が違います。ほかにも、次のものは SBOM から漏れやすいところです。

- 静的にリンクされたライブラリや、ソースから直接ビルドして置いたバイナリ（パッケージマネージャの記録が無い）
- マルチステージビルドの途中の段で使った道具。BuildKit の SBOM は、既定では**最後の段だけ**を調べる（[Docker Docs](https://docs.docker.com/build/metadata/attestations/sbom/)）
- ビルドのときにだけ使い、成果物に残らないもの（コンパイラ、ビルドのスクリプトが取得したもの）

BuildKit が付けた SBOM（provenance と並んでいたもう 1 つの層）も、作ったのは Syft でした。`creators` に `Tool: syft-v1.51.0` と `Tool: buildkit-v0.33.1` が並び、部品の一覧は手元の Syft とほぼ同じでした。

### VEX: 入っているが影響しない

SBOM と脆弱性のデータベースを突き合わせると、警告が大量に出ます。その多くは、第 175 回で見たように、脆弱な関数を呼んでいない、設定で無効になっている、といった理由で実際には影響しません。**VEX**（Vulnerability Exploitability eXchange）は、作った側が「この製品は、この脆弱性の影響を受けるか」を機械が読める形で述べるための文書です（[CISA](https://www.cisa.gov/resources-tools/resources/minimum-requirements-vulnerability-exploitability-exchange-vex)）。

OpenVEX の仕様では、状態は `not_affected`（影響しない）、`affected`（影響する）、`fixed`（この版で直っている）、`under_investigation`（調査中）の 4 つです。`not_affected` と述べるときは、次の 5 つから理由を必ず選びます（[OpenVEX](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md)）。

| `not_affected` の理由 | 意味 |
| --- | --- |
| `component_not_present` | その部品が入っていない |
| `vulnerable_code_not_present` | 部品はあるが、脆弱なコードが含まれていない |
| `vulnerable_code_not_in_execute_path` | 脆弱なコードは実行される経路に無い |
| `vulnerable_code_cannot_be_controlled_by_adversary` | 攻撃者がそのコードに届く入力を制御できない |
| `inline_mitigations_already_exist` | 別の仕組みで悪用が防がれている |

SBOM が「何が入っているか」、VEX が「そのうちどれが問題か」です。走査の道具が VEX を読めば、作った側が調べ済みの警告を除いて、残りに集中できます。CycloneDX は、VEX を同じ形式の中で書けます。

## 全体をつなぐ

ここまでの部品を、最初の図に重ねます。

```
ソースのコミット ── 依存（ロックファイルのハッシュ、スコープ、取得先の固定）
        │           CI の道具（Action を SHA で固定）
        ▼
     ビルド（隔離された基盤が provenance を書き、署名する: SLSA Build L2/L3）
        │
        ▼
     成果物（digest）── provenance: どこで、何から    ─┐
        │              SBOM: 何が入っているか          ├─ in-toto の attestation
        │              VEX: どれが問題か               ─┘  Sigstore で署名し、Rekor に記録
        ▼
     取得して動かす前に検証する
       ・digest に署名があるか
       ・署名した身元が期待どおりか（リポジトリ、ワークフロー、枝）
       ・provenance のソースとビルド基盤が期待どおりか
```

どれも、**記録を作るだけでは何も防ぎません**。provenance も SBOM も署名も、使う側が検証して、合わないものを止めて初めて意味を持ちます。Kubernetes ならアドミッションの段階で、CI なら取得の直後で、検証に落ちたものを止める場所を決めておく必要があります。そして、その検証が**今も動いているか**を確かめ続けることが、この章の主題です。

ここまでは、ソフトウェアが外から入ってくる道を見てきました。次の第 179 回では、視点を自分たちのサービスの内側に移します。1 つのシステムに多くの顧客のデータが同居するとき、ある顧客の要求が別の顧客のデータに届かないことを、アプリケーションとデータベースのどこで、どう保証するかを見ます。

## まとめ

- サプライチェーン攻撃は、typosquatting、依存の乗っ取り、dependency confusion、配布物だけの改ざん、ビルド環境の侵害、CI の道具の書き換えに分けられる。どれも、自分のコードを読んでも見つからない
- 署名は「誰が出したか」を証明するが、「意図したとおりに作られたか」は証明しない。SolarWinds の改ざんされた DLL には正規の署名が付いていた
- Action のタグは付け替えられる。完全なコミット SHA で固定するのが、不変の参照にする唯一の方法。本家の SHA であることと、更新の差分を確かめる
- SLSA の Build トラックは、provenance があるか（L1）、ホストされた基盤が署名するか（L2）、ビルドの手順から署名の秘密に触れないか（L3）で段階を分ける。保証するのは記録の正しさで、ソースの正しさではない
- provenance は in-toto の attestation（DSSE の封筒、Statement、Predicate）で書く。BuildKit の provenance はタグを digest に解決して記録するが、`RUN` の中で取得したものは載らず、手元のビルドでは署名もされない
- Sigstore は、10 分の証明書で署名し、Rekor に記録することで、証明書が切れた後も「有効期間内に署名された」ことを示す。npm の provenance では、tarball の digest、ソースのコミット、ワークフローの身元が一致することを確かめられた
- 署名は digest に付く。タグを付け替えると検証に落ちる。キーレス署名の検証では、身元（リポジトリ、ワークフロー、枝）と発行者を狭く指定する
- SBOM（SPDX / CycloneDX）は purl で部品を名指しする。イメージからは「入っているもの」、ソースからは「宣言されたもの」が見え、どちらからも漏れるものがある
- VEX は、作った側が「どの脆弱性が影響しないか、なぜか」を述べる文書。SBOM と組み合わせて警告を絞る
- 記録は検証して初めて効く。取得して動かす前に止める場所を決める
