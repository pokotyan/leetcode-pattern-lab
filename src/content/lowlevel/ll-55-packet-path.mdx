## 1 パケットに使える時間

10Gbps の回線に、1500 バイトのパケットが隙間なく流れてくるとします。イーサネットのヘッダや隙間の分を含めて 1 パケット約 1538 バイトなので、

```
10,000,000,000 / 8 / 1538 ≈ 81 万パケット / 秒
1 パケットあたり ≈ 1.2 マイクロ秒
3 GHz の CPU なら ≈ 3700 サイクル
```

3700 サイクルは、第 14 回の表でいえば**メインメモリへのアクセス十数回分**です。その間に、パケットを受け取り、宛先を調べ、TCP の状態を更新し、ソケットに届けなければなりません。1 パケットごとに割り込みを受けて、1 パケットごとにメモリを確保していては、とても間に合いません。

この回は、カーネルがこの予算の中でどうやり繰りしているかを、受信の道筋に沿って見ます。

## まず大きさの上限: MTU

リンクが一度に運べるパケットの大きさの上限を **MTU** と呼びます。イーサネットでは 1500 バイトが標準です。

TCP が 1 パケットに載せるデータの量 **MSS** は、そこから IP と TCP のヘッダを引いた値です。

```
MTU 1500 − IP ヘッダ 20 − TCP ヘッダ 20 = MSS 1460 バイト
```

MSS はハンドシェイクのときに互いに知らせ合います。

<Callout type="warn" title="小さいパケットは通るのに、大きいデータだけ止まる">
  経路の途中に MTU の小さいリンク（VPN やトンネルなど）があると、1500 バイトのパケットは通れません。
  送信側は IP ヘッダに「分割するな」の印を付けて送り、
  途中のルータが「大きすぎる」という ICMP のメッセージを返すことで、経路の MTU を知ります（**経路 MTU 探索**）。

  ところが、途中のファイアウォールが ICMP をまとめて捨てていると、この知らせが届きません。
  送信側は大きなパケットを送り続け、それが黙って捨てられ続けます。
  **ハンドシェイクや小さなリクエストは通るのに、大きなレスポンスだけが止まる**のが典型的な症状です
  （[Cloudflare](https://blog.cloudflare.com/path-mtu-discovery-in-practice/)）。
  対策は ICMP を通すか、途中の機器でハンドシェイクの MSS を書き換える（**MSS クランプ**）ことです。

  第 89 回で見たコンテナのネットワークを、複数のホストにまたがって張るオーバーレイでも同じことが起きます。
  パケットを別のパケットで包む分だけ、中の MTU が小さくなるからです。
</Callout>

## 受信の道筋

パケットが NIC に届いてから、`read` で読まれるまでの全体像です。

```
  NIC ── DMA ──→ リングバッファ（メモリ上）
   │
   └─ 割り込み ──→ ドライバ: 割り込みを止め、NAPI のポーリングを予約
                        │
                   softirq でまとめて取り出す（最大 budget 個）
                        │  sk_buff を作る
                        │  GRO: 同じ接続のパケットを 1 つにまとめる
                        ▼
                   IP 層:  宛先の判定、netfilter（iptables / nftables）
                        ▼
                   TCP 層: シーケンス番号の確認、ACK、ソケットを探す
                        ▼
                   ソケットの受信バッファに積む → 待っているスレッドを起こす（epoll）
                        ▼
                   アプリケーションの read: ユーザ空間にコピー
```

1 段ずつ見ていきます。

## リングバッファと DMA

NIC は、受け取ったパケットを CPU に 1 バイトずつ渡したりはしません。第 48 回で見た **DMA** で、メモリに直接書き込みます。

書き込む場所は、ドライバが前もって用意した **リングバッファ** です。空きバッファのアドレスを並べた記述子（ディスクリプタ）の輪で、NIC は届いたパケットを次の空きに書き、記述子に「使用済み」の印を付けます。

```
            ドライバが取り出す位置
                   ↓
  ┌───┬───┬───┬───┬───┬───┬───┬───┐
  │ 空 │ 空 │ 済 │ 済 │ 済 │ 空 │ 空 │ 空 │ ← 輪になっている
  └───┴───┴───┴───┴───┴───┴───┴───┘
                               ↑
                          NIC が次に書く位置
```

ドライバの取り出しが追いつかず、輪が一周して空きがなくなると、NIC は新しいパケットを捨てます。これは **カーネルが何も知らないうちに起きる損失**なので、TCP の統計には出ず、NIC の統計にだけ現れます。

```bash
ethtool -g eth0              # リングバッファの大きさ（現在値と上限）
ethtool -S eth0 | grep -i drop    # NIC で捨てた数。名前はドライバによって違う
```

## 割り込みを止める: NAPI

パケットが届いたことは、第 13 回で見た**割り込み**で CPU に知らせます。しかし、81 万パケット / 秒で毎回割り込まれたら、CPU は割り込みの出入りだけで手一杯になります。

Linux の答えが **NAPI** です（[カーネルのドキュメント](https://docs.kernel.org/networking/napi.html)）。

1. 最初のパケットで割り込みが来る
2. ドライバは**それ以降の割り込みを止め**、ポーリングを予約して、すぐに割り込み処理を終える
3. softirq（割り込みの後始末を後回しにして実行する仕組み）の中で、リングバッファからパケットをまとめて取り出す。1 回に取り出す上限（budget）がある
4. リングが空になったら、割り込みを再び有効にする

**暇なときは割り込みで素早く反応し、忙しいときはポーリングでまとめて処理する。** 第 44 回の「待ち方」の議論が、ハードウェアとの境界でも同じ形で現れています。

処理が追いつかないと、softirq の予算を使い切ったまま次の回に持ち越されます。その回数は `/proc/net/softnet_stat` に出ます。

```bash
cat /proc/net/softnet_stat   # CPU ごとの行。2 列目が捨てた数、3 列目が予算切れで持ち越した回数（16 進数）
```

## まとめて運ぶ: TSO / GSO / GRO

1 パケットごとにかかる固定費を減らすいちばん効く方法は、**パケットの数そのものを減らす**ことです。ただし、回線の上を流れるパケットの大きさは MTU で決まっています。そこで、**カーネルの中だけ大きなパケットとして扱う**仕組みがあります（[カーネルのドキュメント](https://docs.kernel.org/networking/segmentation-offloads.html)）。

| 仕組み | 方向 | 何をするか |
| --- | --- | --- |
| **TSO** | 送信 | カーネルは MSS よりずっと大きな塊（典型的には最大 64KB）を 1 つとして NIC に渡し、**NIC が MSS ごとに切り分けて**ヘッダを付ける |
| **GSO** | 送信 | NIC が TSO に対応していなくても、切り分けをドライバに渡す直前まで遅らせる。上の層は大きな塊のまま扱える |
| **GRO** | 受信 | 同じ接続の連続したパケットを、上の層に渡す前に 1 つの大きなパケットにまとめる |

TCP 層から見ると、1500 バイトのパケットが 40 個届く代わりに、60KB のパケットが 1 個届きます。**TCP の処理もソケットを探す処理も、40 回が 1 回になります。**

```bash
ethtool -k eth0 | grep -E 'segmentation|receive-offload'   # 各 offload の有効・無効
```

<Callout type="note" title="tcpdump で MTU より大きいパケットが見える理由">
  自分のマシンで `tcpdump` を取ると、1500 バイトを超える巨大なパケットが記録されていることがあります。
  回線の上を本当にそのサイズで流れたわけではありません。
  `tcpdump` はカーネルの中でパケットを見ているので、**送信では TSO / GSO で切られる前、受信では GRO でまとめられた後**の姿が見えるのです。
</Callout>

## コアに振り分ける: RSS

1 つのコアでは処理が追いつかないなら、複数のコアで分けます。ただし、同じ接続のパケットを別々のコアで処理すると、順番が入れ替わったり、TCP の状態を取り合ったりします。

**RSS** は、NIC に複数の受信キュー（リングバッファ）を持たせ、**4 つ組のハッシュ**でキューを選びます（[カーネルのドキュメント](https://docs.kernel.org/networking/scaling.html)）。各キューの割り込みを別のコアに割り当てれば、**同じ接続は常に同じコアで、違う接続は違うコアで**処理されます。前々回の `SO_REUSEPORT` と同じ発想を、ハードウェアでやっているわけです。

NIC が複数のキューを持たない場合は、同じことをソフトウェアでやる **RPS** があります。さらに **RFS** は、その接続を `read` しているスレッドが動いているコアへパケットを寄せます。第 16 回で見たとおり、L1 と L2 はコアごとにあるので、**パケットを処理したコアと、データを読むコアが同じなら、キャッシュに載ったまま渡せる**からです。

```bash
ethtool -l eth0          # 受信キューの数
grep eth0 /proc/interrupts   # キューごとの割り込みが、どのコアで何回起きたか
```

## 送信の側と、コピーの回数

送信も逆向きに同じ段を通ります。`write` でユーザ空間から送信バッファにコピーされ、TCP がセグメントを作り、qdisc（送信の待ち行列と帯域制御）を通り、ドライバが送信用のリングバッファに記述子を置き、NIC が DMA で読み出して送ります。送り終わると、NIC は割り込みで完了を知らせ、バッファが解放されます。

このうち CPU がデータそのものをコピーするのは、ユーザ空間とカーネルの間の 1 回です。第 48 回で見た **`sendfile`** は、ファイルを送るときにこの 1 回すら省き、ページキャッシュから直接 NIC に DMA させるものでした。静的なファイルを配る Web サーバが速いのは、このためです。

## カーネルを通らない道

ここまでの工夫をすべてしても、汎用のネットワークスタックには、1 パケットごとの固定費が残ります。`sk_buff` の確保、netfilter の規則の評価、ソケットの検索、ユーザ空間へのコピー。特定の処理だけを極端に速くしたい場合、**カーネルの一部または全部を飛ばす**という選択肢があります。

**XDP** は、ドライバがパケットを受け取った直後、**`sk_buff` を作るより前**に、eBPF のプログラムを実行させる仕組みです。Linux 4.8 で入りました（[Wikipedia](https://en.wikipedia.org/wiki/Express_Data_Path)）。プログラムは、パケットごとに「捨てる」「そのまま通す」「別の NIC から送り返す」「ユーザ空間に渡す」を選べます。DDoS 攻撃のパケットを、スタックに入る前に最も安く捨てる、という使い方が代表的です。第 103 回で見た eBPF を、観測ではなくパケット処理に使う形です。

**DPDK** は、さらに徹底して、**NIC をカーネルから切り離し、ユーザ空間のドライバが直接操作**します。受信キューをひたすらポーリングし続け、割り込みを使いません（[DPDK のドキュメント](https://doc.dpdk.org/guides/prog_guide/ethdev/ethdev.html)）。システムコールも、カーネルとの間のコピーも発生しません。

| 道 | TCP/IP スタック | 失うもの |
| --- | --- | --- |
| 通常 | カーネルのものを使う | — |
| XDP | 必要なパケットだけ通常の道に戻せる | eBPF で書ける範囲の処理に限られる |
| DPDK | 使えない。自前で持つ | カーネルの道具（`ss`、`tcpdump`、iptables）がそのままでは使えない。CPU のコアを 1 つ以上ポーリングで占有する |

<Callout type="tip" title="待たずに回し続けるという選択">
  DPDK がコアを占有してポーリングし続けるのは、一見無駄に見えます。
  しかし、1 パケットあたり数千サイクルしか使えないとき、割り込みとコンテキストスイッチの数千サイクルは払えません。
  **待つ仕組みそのものが高すぎるなら、待たない。** 第 37 回のスピンロックと同じ判断です。
  NAPI は、その判断を負荷に応じて自動で切り替える中間の解でした。
</Callout>

## まとめ

- 10Gbps で 1 パケットに使えるのは約 1.2 マイクロ秒。1 パケットごとの固定費との戦いになる
- MTU は 1 パケットの上限。経路 MTU 探索が ICMP の遮断で壊れると、大きなデータだけが止まる
- NIC は DMA でリングバッファに書く。取り出しが追いつかないと、NIC で黙って捨てられる
- NAPI は、最初の割り込みのあと割り込みを止め、ポーリングでまとめて処理する
- TSO / GSO / GRO は、カーネルの中だけパケットを大きくして、処理の回数を減らす
- RSS は 4 つ組のハッシュで接続をコアに振り分ける。RFS は読むスレッドのコアに寄せる
- XDP は `sk_buff` の前で eBPF を動かし、DPDK はカーネルを丸ごと飛ばす

ここまでで第 9 章は終わりです。第 8 章でデータをディスクに確実に残す方法を、この章でデータを確実に相手に届ける方法を見ました。次の章では、その通信のほぼすべてが最初に行っている手順、**名前を引く**ことを見ます。
