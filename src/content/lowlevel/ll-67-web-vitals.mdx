## 何を「速い」と呼ぶのか

ここまでの回で、ブラウザの中にある遅さの源をいくつも見てきました。接続とハンドシェイク、構文解析を止める script、レイアウトのやり直し、メインスレッドを塞ぐ長いタスク、GC。

では、「このページは速いか」と聞かれたら、どれを測ればよいのでしょうか。サーバの応答時間でしょうか。`load` イベントまでの時間でしょうか。

どちらも、利用者の体験とはずれています。サーバが 50ms で返しても、画面に何も出なければ遅く感じます。`load` イベントの後に大きな画像が差し込まれて画面が跳ねれば、それも不快です。

**Web Vitals** は、この問いに「利用者が感じることを、3 つに分けて測る」と答えた指標の組です（[web.dev](https://web.dev/articles/vitals)）。

| 指標 | 問い | 「良い」の目安 |
| --- | --- | --- |
| **LCP**（Largest Contentful Paint） | 主な中身は、いつ見えたか | 2.5 秒以内 |
| **INP**（Interaction to Next Paint） | 操作に、すぐ反応したか | 200 ミリ秒以内 |
| **CLS**（Cumulative Layout Shift） | 見ている途中で、画面が跳ねなかったか | 0.1 以下 |

目安の値は、実際の利用者のページ表示の **75 パーセンタイル** で判定します（[web.dev](https://web.dev/articles/defining-core-web-vitals-thresholds)）。平均ではなく、「4 人に 3 人がこの値より良い体験をしているか」を見ます。平均では、遅い回線や古い端末の利用者が隠れてしまうからです。

<Callout type="note" title="指標は入れ替わる">
  反応の速さは、かつて FID（最初の操作だけの待ち時間）で測っていました。
  2024 年 3 月に INP へ置き換わっています（[web.dev](https://web.dev/blog/inp-cwv-march-12)）。
  指標の名前や目安の値は、これからも見直される可能性があります。
  この回では、名前よりも**それぞれが何を測っているのか**に注目します。
  中身が分かっていれば、指標が変わっても何を直せばよいかは変わりません。
</Callout>

## LCP: 主な中身が見えるまで

LCP は、画面の中で**最も大きな画像か文字の塊**が描画された時刻です。「ページの主役が見えた瞬間」の代わりに使っています。

LCP の時間は、この章の前半で見た段の足し算に分解できます（[web.dev](https://web.dev/articles/optimize-lcp)）。

```
 ナビゲーション開始
 │
 ├─ ① TTFB ─────────┤                      HTML の最初のバイトが届くまで（第 60 回）
                     ├─ ② 読み込み開始の遅れ ─┤    その画像を取りに行くと決めるまで（第 62 回）
                                             ├─ ③ 読み込み時間 ─┤   画像そのものの転送（第 54 回）
                                                                 ├─ ④ 描画の遅れ ─┤  届いてから描かれるまで
                                                                                  LCP
```

| 区間 | どの回の話か | よくある原因 |
| --- | --- | --- |
| ① TTFB | 第 60 回 | DNS、接続、TLS、サーバの処理、リダイレクト |
| ② 読み込み開始の遅れ | 第 62 回 | 画像が CSS や JavaScript の中にあり、先読みで見つけられない |
| ③ 読み込み時間 | 第 54 回 | 画像が大きい、帯域を他の資源と取り合う |
| ④ 描画の遅れ | 第 63 回、第 65 回 | 構文解析を止める script、長いタスクがメインスレッドを塞ぐ |

**LCP を改善するとは、この 4 区間のどれが長いかを見つけることです。** 画像を圧縮しても、実際には ② が長いなら効きません。第 98 回で「推測しない」と書いたのと同じ話です。

## INP: 操作から、次の描画まで

INP は、ページを開いている間の**すべての**クリック、タップ、キー入力について、操作してから画面が次に描き変わるまでの時間を測り、そのうち**ほぼ最悪の値**を報告します（[web.dev](https://web.dev/articles/optimize-inp)）。1 回目の操作だけでなく、ずっと見ています。

1 回の操作の時間は、3 つの区間に分かれます。

```
 クリック
 │
 ├─ ① 入力の遅れ ─┤                         他のタスクが終わるのを待つ
                  ├─ ② 処理 ─┤                イベントハンドラが動く
                             ├─ ③ 表示の遅れ ─┤   style → layout → paint → 合成
                                              次のフレーム
```

これは第 65 回で見たイベントループの 1 周そのものです。

- **① 入力の遅れ**: クリックした瞬間に、メインスレッドが別の長いタスクを実行していれば、それが終わるまでハンドラは動けません。第 44 回で見た、ブロックしている間は他のことができない、という性質です
- **② 処理**: ハンドラ自身の重さ。第 66 回の遅延構文解析があるので、初めて呼ばれる関数はここで解析とコンパイルの時間も払います
- **③ 表示の遅れ**: ハンドラが DOM を書き換えた結果を描くまで。第 63 回の、どの段からやり直しになるかがここに効きます

<Callout type="tip" title="長いタスクを切る">
  ① と ② の多くは、**50 ミリ秒を超えて続くタスク**（長いタスク）が原因です。
  1 つの大きな処理を小さく刻み、合間にイベントループへ制御を返せば、
  その隙間でクリックを処理できます。
  第 36 回で見た、プリエンプションのない協調的マルチタスクで「自分から手放す」のと同じ構図です。
  ブラウザのメインスレッドは、OS のスケジューラに割り込まれない、協調的な世界です。
</Callout>

## CLS: 画面が跳ねた量

CLS は、**見えている要素が予告なく動いた量**を足し合わせたものです（[web.dev](https://web.dev/articles/cls)）。記事を読んでいる途中で広告が差し込まれ、本文が下にずれる。押そうとしたボタンが直前に動き、別のものを押してしまう。そういう体験を数字にしています。

1 回のずれの大きさは、「画面のどれだけの面積が影響を受けたか」と「どれだけの距離を動いたか」の積です。ページを長く開いているほど足し合わせが大きくならないよう、**1 秒以内に続いたずれを 1 つの塊**（最大 5 秒）とみなし、最も大きい塊の値を使います（[web.dev](https://web.dev/blog/evolving-cls)）。

ずれの原因のほとんどは、第 63 回の **layout のやり直し**です。

| 原因 | 何が起きているか | 対策 |
| --- | --- | --- |
| 大きさを指定しない画像 | 読み込むまで高さ 0 で配置され、届いた瞬間に周りを押しのける | `width` と `height`（縦横比）を指定し、先に場所を取る |
| 後から差し込む要素 | 広告、通知、埋め込み | 場所を予約しておく |
| Web フォントの差し替え | 代わりのフォントで配置した後、幅の違うフォントに替わる | 大きさの近い代わりのフォントを選ぶ |

利用者の操作の直後に起きたずれは、数えません。クリックして何かが開くのは、予告されたずれだからです。

## 2 つの測り方

指標の値は、どこで測るかで大きく変わります。

| | 実験室の計測 | 実際の利用者の計測（RUM） |
| --- | --- | --- |
| どこで | 決まった端末と回線を模擬して、1 回読み込む | 利用者のブラウザで、本物の閲覧のたびに |
| 長所 | 再現できる。変更の前後を比べられる | 本当の体験が分かる。端末、回線、操作の偏りまで含む |
| 短所 | 1 つの条件でしかない。操作がないので INP は測れない | ばらつく。原因を突き止めにくい |

**実験室の値が良くても、実際の利用者の値が悪いことはよくあります。** 開発者のマシンは速く、回線も速いからです。第 98 回の「環境を揃える」の裏返しで、実際の利用者の環境は揃っていないという前提で見る必要があります。

実際の利用者の計測は、ブラウザが用意している API で行います。

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log(entry.entryType, entry.startTime, entry)
  }
}).observe({ type: 'largest-contentful-paint', buffered: true })

// 'layout-shift'（CLS の材料）、'event'（INP の材料）、'longtask' なども同じ形で受け取れる
```

ブラウザは、描画やイベントの処理のたびに内部で時刻を記録しており、それをこの API で受け取れます。受け取った値をサーバに送って集計すれば、75 パーセンタイルを自分で計算できます。第 16 章で見る OpenTelemetry のような仕組みで、サーバ側のトレースと同じ場所に集める使い方もあります。

<Callout type="warn" title="指標を上げることが目的ではない">
  指標は、体験の一部を数字にした近似です。
  たとえば、LCP の候補になる大きな画像を小さく分割すれば、LCP の値は良くなるかもしれませんが、
  利用者の体験は何も変わりません。
  **数字が悪いときは、パイプラインのどの段が遅いのかを探す手がかりとして使う**のが本来の使い方です。
</Callout>

## この章の部品を、もう一度並べる

最後に、3 つの指標と、この章の回の対応を並べます。

| 回 | LCP | INP | CLS |
| --- | --- | --- | --- |
| 第 60 回 URL から最初のバイト | ① TTFB | | |
| 第 61 回 プロセス構成 | | 入力がどのプロセスに届くか | |
| 第 62 回 HTML から DOM へ | ② 読み込み開始の遅れ | | |
| 第 63 回 パイプライン | ④ 描画の遅れ | ③ 表示の遅れ | layout のやり直し |
| 第 64 回 合成と GPU | | 合成だけで済む変化は軽い | transform で動かせば layout は起きない |
| 第 65 回 イベントループ | ④（長いタスク） | ① 入力の遅れ | |
| 第 66 回 JavaScript エンジン | 構文解析とコンパイル | ② 処理、GC の停止 | |

3 つの指標はばらばらに見えますが、どれも**メインスレッドとレンダリングパイプラインの詰まり**を、別の角度から見ています。

## まとめ

- Web Vitals は、読み込み（LCP）、反応（INP）、安定（CLS）を、実際の利用者の 75 パーセンタイルで測る
- LCP は、TTFB・読み込み開始の遅れ・読み込み時間・描画の遅れの 4 区間に分解できる
- INP は、入力の遅れ・処理・表示の遅れの 3 区間で、イベントループの 1 周そのもの。長いタスクを切るのが基本
- CLS の多くは layout のやり直し。大きさを先に予約すれば防げる
- 実験室の計測は再現性、実際の利用者の計測は本当の体験。両方を使う
- 指標の名前は変わりうる。何を測っているかを押さえ、遅い段を探す手がかりとして使う

ここまでで第 11 章は終わりです。ブラウザは、ネットワーク、プロセスとサンドボックス、パーサ、GPU、イベントループ、JIT と GC という、ここまでの章の部品をほぼすべて使う大きなプログラムでした。次の章では、**別の言語で書かれたコードを、同じプロセスの中で呼ぶ**という話に入ります。その答えの 1 つとして使われ始めた WebAssembly は、もともとこのブラウザの中で、JavaScript だけでは足りない速さを補うために生まれたものです。
