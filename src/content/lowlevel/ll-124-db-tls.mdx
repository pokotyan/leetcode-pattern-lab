## 誰も鍵のマークを見ない区間

前回の第 123 回では、SSH のチャネルに TCP を通して、手元から内側のサービスへ穴を通しました。データベースにつなぐときによく使われる方法の 1 つです。この回では、もう 1 つの方法、**データベースのプロトコルそのものに TLS を載せる**ほうを見ます。

ブラウザなら、TLS がつながらなければ警告の画面が出ます。利用者は鍵のマークを見て、少なくとも「つながった相手の証明書は確かめられた」と知ることができます。アプリケーションサーバからデータベースへの接続には、その画面がありません。接続文字列に何を書いたか、ドライバの既定値が何か、サーバが何を許しているかで、次の 3 つのどれになるかが決まります。

1. 暗号化されていない
2. 暗号化されているが、相手が本物かは確かめていない
3. 暗号化され、相手が本物だと確かめている

どれになっても、アプリは普通に動きます。**違いが表に出るのは、経路に中間者がいたときだけ**です。この回では、PostgreSQL を中心に、偽のサーバと、応答を書き換える中間者を手元に立てて、設定ごとに何が起きるかを確かめます。後半では MySQL、Redis、MongoDB、Kafka、AMQP の載せ方を比べ、最後にコネクションプーラーのような中間層で区間が分かれる話をします。

## PostgreSQL: 8 バイトで「TLS を話せますか」と聞く

第 120 回で分けた型でいえば、PostgreSQL は**平文で始めて途中で切り替える**型です。ポートは 5432 の 1 つで、平文の接続も TLS の接続も同じポートで受けます。

### SSLRequest と 1 バイトの返事

クライアントは、通常の起動メッセージ（StartupMessage）の代わりに、まず **SSLRequest** を送ります。サーバは `S`（TLS を話せる）か `N`（話せない）の **1 バイト**で答え、`S` なら TLS のハンドシェイクに進み、その後の起動メッセージ以降はすべて TLS の中を通ります。`N` なら、クライアントは平文のまま起動メッセージを送って続けてもよいし、そこで接続を切ってもよい、とされています（[PostgreSQL: 54.2.10 SSL Session Encryption](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-FLOW-SSL)）。

サーバのコンテナのネットワークに tcpdump を付けて、`sslmode=prefer`（既定）で psql をつないだときの最初の 3 つのパケットを取りました。

```
172.25.0.3.43202 > 172.25.0.2.5432: Flags [P.], length 8
	0x0030:  e6b1 6480 0000 0008 04d2 162f            ..d......../
172.25.0.2.5432 > 172.25.0.3.43202: Flags [P.], length 1
	0x0030:  a186 c2ff 53                             ....S
172.25.0.3.43202 > 172.25.0.2.5432: Flags [P.], length 1573
	0x0030:  e6b1 6484 1603 0106 2001 0006 1c03 03ac  ..d.............
	...
	0x00d0:  6462 2e65 7861 6d70 6c65 2e63 6f6d 000b  db.example.com..
```

- 1 つ目がクライアントの SSLRequest です。`00000008` は長さ 8、`04d2162f` は 10 進で 80877103 で、上位 16 ビットが 1234、下位が 5679 という、通常のプロトコル番号とは決して重ならない値です
- 2 つ目がサーバの返事 `53`、つまり ASCII の `S` です
- 3 つ目は `16 03 01` で始まる TLS のレコード、第 115 回の ClientHello です。SNI に `db.example.com` が入っているのも見えます。libpq は既定で SNI を送ります（[libpq: sslsni](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-SSLSNI)）

この 1 往復は**平文**で、どちらの方向も認証されていません。第 120 回で見た途中で切り替える型の弱点は、すべてここに集まっています。

### 切り替えの境目に残るバイト

第 120 回では、SMTP の STARTTLS で、切り替える前に送り込まれたバイトが切り替えた後のものとして処理されるコマンド注入（CVE-2011-0411 系）を見ました。PostgreSQL にも、まったく同じ形の脆弱性が 2021 年に見つかっています。

- [CVE-2021-23214](https://www.postgresql.org/support/security/CVE-2021-23214/): サーバ側。`cert` 認証などを使う設定で、中間者が接続の最初に任意の SQL を差し込めた。説明文自身が「CVE-2011-0411 に似ている」と書いています
- [CVE-2021-23222](https://www.postgresql.org/support/security/CVE-2021-23222/): クライアント（libpq）側。中間者が最初のいくつかの問い合わせに偽の応答を差し込めた

どちらも 9.6〜14 が対象で、2021-11-11 のマイナーリリースで直りました。プロトコルの文書には今、**サーバは `S` の 1 バイトだけを送って待つはずなので、その時点で読めるバイトが余っていたら中間者による詰め込みを疑え、クライアントはちょうど 1 バイトだけ読んでから TLS ライブラリにソケットを渡すか、余りを読んだらプロトコル違反として扱え**、と書かれています（[PostgreSQL: 54.2.10](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-FLOW-SSL)）。同じ節には、SSLRequest への応答としてエラーメッセージが返ってきた場合も、**サーバがまだ認証されていないのでその内容を利用者に見せるな**という注意もあります（CVE-2024-10977）。平文の段階で受け取ったものは、1 バイトたりとも信用しない、というのが共通の教訓です。

## sslmode: 6 つの段階

libpq（psql や多くのドライバの土台）で、TLS をどこまで求めるかを決めるのが `sslmode` です。公式の文書は、各モードが何から守るかを表にしています（[libpq: 32.19.3](https://www.postgresql.org/docs/current/libpq-ssl.html#LIBPQ-SSL-PROTECTION)）。

| `sslmode` | 動き | 盗聴から守るか | 中間者から守るか |
| --- | --- | --- | --- |
| `disable` | 平文だけを試す | いいえ | いいえ |
| `allow` | まず平文、失敗したら TLS | 場合による | いいえ |
| `prefer`（既定） | まず TLS、失敗したら平文 | 場合による | いいえ |
| `require` | TLS だけ。証明書は確かめない | はい | いいえ |
| `verify-ca` | TLS だけ。信頼する CA の発行かを確かめる | はい | CA の運用次第 |
| `verify-full` | TLS だけ。CA と、ホスト名が証明書に合うかを確かめる | はい | はい |

`require` の行の説明は、文書の言葉では「**ネットワークが、常に自分の望むサーバにつないでくれると信じる**」です。そして既定の `prefer` については、**セキュリティの観点からは意味がなく、後方互換のためだけに既定になっている**とまで書かれています（[libpq: 32.19.3](https://www.postgresql.org/docs/current/libpq-ssl.html#LIBPQ-SSL-PROTECTION)）。

### 本物のサーバに 6 通りでつなぐ

サーバの `pg_hba.conf` は、平文の接続も TLS の接続も受け付ける `host` の行にしておき、`pg_stat_ssl` で自分の接続が TLS かどうかを問い合わせました。

```
$ psql "host=db.example.com user=app dbname=app sslmode=disable" \
    -Atc "select ssl, version from pg_stat_ssl where pid=pg_backend_pid()"
f|
（allow も f|。prefer、require、verify-ca、verify-full はすべて t|TLSv1.3）
```

`allow` が平文になるのは、平文を先に試し、それが通ったからです。相手が本物である限り、`prefer` 以上はすべて TLS 1.3 になり、**見た目の違いはありません**。違いが出るのは、名前の確かめ方を変えたときです。

```
$ psql "host=172.25.0.2 ... sslmode=verify-ca sslrootcert=caA.crt"     → t|TLSv1.3
$ psql "host=172.25.0.2 ... sslmode=verify-full sslrootcert=caA.crt"
psql: error: connection to server at "172.25.0.2", port 5432 failed:
  server certificate for "db.example.com" (and 1 other name) does not match host name "172.25.0.2"
```

IP アドレスでつなぐと、`verify-ca` は通り、`verify-full` は名前の不一致で止まります。`verify-ca` が確かめるのは「CA A が発行した証明書か」だけで、**CA A が発行した別のサーバの証明書でも通る**ということです。

CA の証明書を渡さずに `verify-full` を指定すると、libpq は既定の場所 `~/.postgresql/root.crt` を探し、無ければ止まります。

```
psql: error: ... root certificate file "/root/.postgresql/root.crt" does not exist
Either provide the file, use the system's trusted roots with sslrootcert=system,
or change sslmode to disable server certificate verification.
```

`sslrootcert=system` は OS のトラストストアを使う指定で、この値を使うと `sslmode` の既定が `verify-full` に変わり、それより弱い指定はエラーになります。誰でも自分の持つ名前に対して公的な CA の証明書を取れる以上、公的な CA を信頼しながら名前を確かめない `verify-ca` は役に立たないからです（[libpq: sslrootcert](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-SSLROOTCERT)）。今回の証明書は手元の CA A の発行なので、`sslrootcert=system` では `certificate verify failed` になりました。

### 偽のサーバに向けたとき

次に、CA B の証明書を持つ**偽のサーバ**を別のコンテナで立てました。名前は同じ `db.example.com` を名乗っています。DNS を偽られた状況を、`hostaddr` で偽のサーバの IP を直接指定して再現します（`host` は証明書の照合に使う名前、`hostaddr` は実際につなぐ先です）。

まず、CA の証明書を渡さない場合です。

```
$ psql "host=db.example.com hostaddr=172.25.0.4 ... sslmode=prefer"   → t|TLSv1.3
$ psql "host=db.example.com hostaddr=172.25.0.4 ... sslmode=require"  → t|TLSv1.3
$ psql "host=db.example.com hostaddr=172.25.0.4 ... sslmode=verify-ca"
psql: error: ... root certificate file "/root/.postgresql/root.crt" does not exist
```

**`prefer` と `require` は、偽のサーバに何の問題もなくつながりました**。暗号化はされています。ただし、暗号化の相手が偽物です。アプリが続けて送るパスワードの認証や SQL、受け取る結果は、すべて偽のサーバとの間でやり取りされます。

続いて、`sslrootcert=caA.crt` を渡した場合です。

```
== sslmode=prefer
f|
== sslmode=require
psql: error: ... SSL error: certificate verify failed
== sslmode=verify-ca
psql: error: ... SSL error: certificate verify failed
== sslmode=verify-full
psql: error: ... SSL error: certificate verify failed
```

ここで 2 つ、意外な結果が出ます。

- **`require` が検証で落ちた**。文書によれば、後方互換のため、**ルート CA のファイルが存在すると `require` は `verify-ca` と同じ動きになる**からです。ただし、文書はこの振る舞いに頼るなとも書いています（[libpq: 32.19.1](https://www.postgresql.org/docs/current/libpq-ssl.html#LIBQ-SSL-CERTIFICATES)）。同じ `require` が、`~/.postgresql/root.crt` があるかどうかで意味を変えるということです
- **`prefer` は、検証に失敗したあと、平文でつなぎ直して成功した**（`f|`）。`prefer` の定義は「まず TLS、失敗したら平文」で、証明書の検証の失敗も「失敗」に含まれます。偽のサーバの `pg_hba.conf` が平文を許していれば、そのまま平文の接続が成立します。偽のサーバの設定を決めるのは攻撃者なので、当然許しています

<Callout type="warn" title="よくある誤解: 「sslrootcert を渡したから、prefer でも検証されている」">
  上の実験のとおり、`prefer` は検証に失敗すると**平文に落ちて接続を続けます**。CA の証明書を渡しても、`prefer` である限り、中間者に対しては何も守りません。
  検証を確実に効かせるには、`sslmode` そのものを `verify-full` にします。`require` に CA ファイルの有無で意味が変わる振る舞いがあるのも、
  設定を読んだだけでは結果が分からないという意味で避けるべき理由になります。
</Callout>

### 返事を `N` に書き換える中間者

偽のサーバより安上がりな攻撃もあります。本物のサーバとの間に立って、**SSLRequest への返事を `N` に書き換える**だけの中間者です。Python で 50 行ほどのプロキシを書きました。クライアントの SSLRequest には `N` と答え、その後クライアントから平文で届くものを表示しながら、本物のサーバへそのまま中継します。

```python
SSL_REQUEST = struct.pack(">II", 8, 80877103)

def handle(client):
    if recv_exact(client, 8) == SSL_REQUEST:
        print("client sent SSLRequest -> answering 'N'", flush=True)
        client.sendall(b"N")
    upstream = socket.create_connection(("db.example.com", 5432))
    # 本物のサーバへは平文で中継し、クライアントから届いたバイトを表示する
    threading.Thread(target=pump, args=(upstream, client, None), daemon=True).start()
    pump(client, upstream, "C->S plaintext:")
```

`sslmode=prefer` でこのプロキシにつなぎ、問い合わせを 1 つ送りました。

```
$ psql "host=db.example.com hostaddr=172.25.0.5 user=app dbname=app sslmode=prefer" \
    -Atc "select 'card=4111-1111-1111-1111' as secret, (select ssl from pg_stat_ssl where pid=pg_backend_pid())"
card=4111-1111-1111-1111|f
```

プロキシの側には、次のように出ました。

```
client sent SSLRequest -> answering 'N'
C->S plaintext: ...5....user.app.database.app.application_name.psql..
C->S plaintext: p...6SCRAM-SHA-256.... n,,n=,r=eHwbjpJXxpmnQV59AQHhCacY
C->S plaintext: p...lc=biws,r=eHwbjpJXxpmnQV59AQHhCacYQ23movTV3aCBt1DWvCrVDPfC,p=ypleRU5wcwyK/jqp+HjMYffLIGn1V4/lwRrGrJxldKM=
C->S plaintext: Q...jselect 'card=4111-1111-1111-1111' as secret, (select ssl from pg_stat_ssl where pid=pg_backend_pid()).
C->S plaintext: X....
```

**クライアントは何の警告も出さずに平文で接続し、利用者名、データベース名、SQL の全文が中間者に読まれました**。応答の行も同じように読めます。`sslmode=require` で同じプロキシにつなぐと、`N` を受け取った時点で止まります。

```
psql: error: ... server does not support SSL, but SSL was required
```

これは第 120 回の STARTTLS の除去と同じ構図で、第 148 回で見たメールの日和見の暗号化とも同じ弱さです。ただし、メールの中継には「TLS を話せない相手にも届けなければならない」という事情がありました。**データベースの接続には、そういう事情はほとんどありません**。接続先は自分たちで管理しているサーバだからです。

### パスワードは漏れていないが、なりすましは通った

上の出力で、パスワードそのものは流れていません。この実験のサーバが使っている認証方式 SCRAM-SHA-256 は、サーバが選んだ乱数とパスワードを混ぜた値（`p=...`）を送るだけで、この値を後の別の接続で使い回すことはできません。しかし文書は、**チャネルバインディングなしの SCRAM は、本物のサーバとクライアントの間に立つ偽のサーバが、本物の乱数を素通しして認証を成功させることを防がない**とはっきり書いています（[PostgreSQL: 54.3.1 SCRAM-SHA-256](https://www.postgresql.org/docs/current/sasl-authentication.html#SASL-SCRAM-SHA-256)）。上のプロキシがやったのはまさにそれです。

**チャネルバインディング**は、この隙間をふさぐ仕組みです。SCRAM の計算に、TLS の接続でサーバが出した証明書のハッシュ（`tls-server-end-point`）を混ぜます。中間者は本物の証明書を見せることはできても、その秘密鍵を持たないので、同じ証明書で TLS を終えることができません。名前は `SCRAM-SHA-256-PLUS` です（同上）。上の出力の `n,,` は SCRAM の先頭の欄で、`n` は「クライアントはチャネルバインディングを使わない」という意味です（[RFC 5802 7](https://www.rfc-editor.org/rfc/rfc5802.html#section-7)）。TLS が無いのでバインドする先がなく、こうなります。

libpq の `channel_binding` は既定が `prefer` で、`require` にするとチャネルバインディングが使えない接続を拒みます（[libpq: channel_binding](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-CHANNEL-BINDING)）。同じプロキシに `channel_binding=require` を付けてつなぐと、こうなりました。

```
$ psql "host=db.example.com hostaddr=172.25.0.5 ... sslmode=prefer channel_binding=require" -Atc ...
psql: error: ... channel binding required, but SSL not in use
```

ちなみに、プロキシを最初に書いたときは、本物のサーバへの区間だけを TLS にしていました。すると psql は `server offered SCRAM-SHA-256-PLUS authentication over a non-SSL connection` と言って止まりました。サーバは自分の側の TLS を見て `-PLUS` を提示し、クライアントは自分の側が平文なのにそれが来たことを矛盾として検出したわけです。攻撃者が上流も平文にすれば、この検出はすり抜けられます。**`channel_binding=require` は、`sslmode=verify-full` ほどではないものの、サーバの証明書の秘密鍵を持つ相手と認証したことをパスワードの側から保証する**、もう 1 本の防御線です。

## 直接 TLS を始める: sslnegotiation=direct

PostgreSQL 17 で、SSLRequest の往復を省き、**TCP がつながった直後から TLS のハンドシェイクを始める**方式が入りました。クライアントの接続パラメータ `sslnegotiation=direct` で使います（[PostgreSQL 17 リリースノート](https://www.postgresql.org/docs/release/17.0/)）。第 120 回の型でいえば、途中で切り替える型から、**暗黙の TLS の型**へ移る選択肢です。サーバは同じポートで、SSLRequest で始まる接続と、いきなり ClientHello で始まる接続の両方を受け付けます。

```
$ psql "host=db.example.com ... sslmode=require sslnegotiation=direct"      → t|TLSv1.3
$ psql "host=db.example.com ... sslmode=verify-full sslrootcert=caA.crt sslnegotiation=direct" → t|TLSv1.3
$ psql "host=db.example.com ... sslmode=prefer sslnegotiation=direct"
psql: error: weak sslmode "prefer" may not be used with sslnegotiation=direct (use "require", "verify-ca", or "verify-full")
```

`prefer` と組み合わせられないのは、サーバが直接の TLS に対応していなかったときに、平文の認証へ意図せず落ちるのを避けるためだと文書は説明しています（[libpq: sslnegotiation](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-SSLNEGOTIATION)）。**直接の TLS を選ぶなら、平文に落ちる道は最初から無い**という設計です。

パケットを取って TShark で読むと、クライアントが最初に送るバイトから ClientHello で、ALPN に `postgresql` が入っていました。

```
$ tshark -r direct.pcap -Y "tls.handshake.type==1" -T fields \
    -e frame.number -e tcp.stream -e tls.handshake.extensions_server_name -e tls.handshake.extensions_alpn_str
4	0	db.example.com	postgresql
25	1	db.example.com	postgresql
$ tshark -r direct.pcap -Y "tcp.len>0 && tcp.dstport==5432" -T fields -e tcp.stream -e tcp.len -e tcp.payload
0	1573	16030106200100061c0303cb4d754711439f2dc2103f95e14c277a78f9735ce948af9f3d2...
```

ALPN（第 115 回）は、直接の TLS では**必須**です。プロトコルの文書は、プロトコルの取り違え（protocol confusion）の攻撃を防ぐために ALPN を使うことをクライアントに求め、IANA に登録された `postgresql` という名前を指定しています（[PostgreSQL: 54.2.10](https://www.postgresql.org/docs/current/protocol-flow.html#PROTOCOL-FLOW-SSL)）。取り違えの攻撃は第 127 回の ALPACA で詳しく見ます。`openssl s_client` で ALPN を付けずに直接つなぐと、TLS のハンドシェイク自体は終わりますが、サーバは次のログを残して接続を閉じました。

```
LOG:  received direct SSL connection request without ALPN protocol negotiation extension
```

`-alpn postgresql` を付けると `ALPN protocol: postgresql` と表示されます。従来の方式は `openssl s_client -starttls postgres` で確かめられ、こちらは `No ALPN negotiated` でした。

直接の TLS の利点は、往復が 1 回減ることのほかに、**普通の TLS を話す道具がそのまま使える**ことです。第 116 回で見た SNI で振り分けるパススルーのロードバランサは、SSLRequest を知らなければ PostgreSQL の接続を振り分けられません。libpq の文書も、SNI を見て振り分けるプロキシは、PostgreSQL のハンドシェイクを知っているのでなければ `sslnegotiation=direct` を必要とする、と書いています（[libpq: sslsni](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-SSLSNI)）。代わりに、サーバもクライアントも 17 以上である必要があります。

## サーバ側で強制する: pg_hba.conf

ここまではクライアントの設定でした。クライアントが何を指定してきても、**サーバの側で平文を断る**こともできます。`pg_hba.conf` の行の種類のうち、`hostssl` は TLS の接続にだけ、`hostnossl` は TLS でない接続にだけ当てはまります（[PostgreSQL: 20.1](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html)）。`host` の行を消して `hostssl` だけにすれば、平文で来た接続はどの行にも当たらず拒否されます。

ただし、サーバの側で強制しても、**クライアントがサーバを確かめているかどうかは変わりません**。上の「返事を `N` に書き換える中間者」は、本物のサーバへは TLS でつなげば `hostssl` の行も通ります。サーバの強制は「平文の接続をうっかり作らない」ためのもので、中間者への備えは、クライアントの `verify-full` が担います。

### クライアント証明書で利用者を確かめる

逆向き、つまりサーバがクライアントを証明書で確かめるのが、第 116 回の mTLS です。PostgreSQL では 2 通りの書き方があります。

- 認証方式 `cert`: クライアント証明書だけで認証する。証明書の CN が、要求された利用者名と一致すればログインを許す（[PostgreSQL: 20.12](https://www.postgresql.org/docs/current/auth-cert.html)）
- オプション `clientcert=verify-ca` / `verify-full`: パスワードなど別の認証方式に、クライアント証明書の確認を**足す**。`verify-full` は CN と利用者名の一致まで確かめる（[PostgreSQL: 20.1](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html)）

文書は、`cert` 認証は**実質的に `trust` に `clientcert=verify-full` を付けたもの**だと説明しています（[PostgreSQL: 20.12](https://www.postgresql.org/docs/current/auth-cert.html)）。サーバの `ssl_ca_file` に CA A を置き、次の `pg_hba.conf` で試しました。

```
local   all  all                 trust
hostssl all  alice  0.0.0.0/0    cert
host    all  all    0.0.0.0/0    scram-sha-256
```

```
== alice with alice.crt
alice|/CN=alice
== alice without cert
psql: error: ... FATAL:  connection requires a valid client certificate
== alice with mallory.crt (CA B, CN=alice)
psql: error: ... SSL error: tlsv1 alert unknown ca
== app with alice.crt
app|/CN=alice
```

（2 列目は `pg_stat_ssl` の `client_dn` です。）CA B が発行した、CN が `alice` の証明書は、ハンドシェイクの段階で `unknown ca` として拒まれました。サーバのログには、確かめられなかった証明書の Subject と発行者が残ります。

```
LOG:  could not accept SSL connection: certificate verify failed
DETAIL:  Client certificate verification failed at depth 0: unable to get local issuer certificate.
	Failed certificate data (unverified): subject "/CN=alice", serial number 6912...618, issuer "/CN=Lab DB CA B".
```

最後の行が示しているのは、第 116 回の「mTLS は認可ではない」と同じことです。利用者 `app` で `alice` の証明書を出すと、TLS の段階では CA A の証明書として検証が通り、認証は `host` の行のパスワード認証で行われました。**証明書が誰のものかと、どの利用者として入ったかは、`pg_hba.conf` の行が結び付けたときにだけ一致します**。

## MySQL: 能力フラグで切り替える

MySQL も、1 つのポート（3306）で平文から TLS に切り替える型です。ただし、最初に話すのが**サーバ**である点が PostgreSQL と違います。

```
サーバ  ─▶  Server Greeting（版、乱数、能力フラグ。CLIENT_SSL が立っていれば TLS を話せる）
クライアント ─▶  SSLRequest（32 バイト。CLIENT_SSL を立てた能力フラグなど。利用者名の手前で切れている）
          ======== ここから TLS のハンドシェイク ========
クライアント ─▶  HandshakeResponse（利用者名、認証データ）を TLS の中で送り直す
```

SSLRequest は、通常の HandshakeResponse を**利用者名の欄の直前で打ち切ったもの**で、能力フラグに CLIENT_SSL を立てて送ります（[MySQL: Protocol::SSLRequest](https://dev.mysql.com/doc/dev/mysql-server/latest/page_protocol_connection_phase_packets_protocol_ssl_request.html)）。CLIENT_SSL の値は 2048（`0x0800`）です（[MySQL: Capabilities Flags](https://dev.mysql.com/doc/dev/mysql-server/latest/group__group__cs__capabilities__flags.html)）。手元で取ったパケットでは次のとおりでした。

```
$ tshark -r mysql.pcap -Y "tcp.stream==1 && tcp.len>0" -T fields -e tcp.srcport -e tcp.len -e tcp.payload
3306	78	4a0000000a382e342e313100...        Server Greeting（"8.4.11"）
34982	36	2000000185aabf190000000108000000000000000000000000000000000000000000000
34982	340	160301014f0100014b0303...          ClientHello
```

2 行目の先頭 4 バイト `20 00 00 01` はパケットの長さ 32 と通し番号 1、続く `85 aa bf 19` がリトルエンディアンの能力フラグ `0x19bfaa85` で、`0x0800` のビットが立っています。TShark の解析でも `Switch to SSL after handshake: Set` と表示されました。その後ろはほぼ 0 の埋め草で、**利用者名はまだ送られていません**。

### --ssl-mode と、平文を断るサーバ

MySQL のクライアントの `--ssl-mode` は、PostgreSQL の `sslmode` とほぼ対応する 5 段階です（[MySQL 8.4: --ssl-mode](https://dev.mysql.com/doc/refman/8.4/en/connection-options.html#option_general_ssl-mode)）。

| `--ssl-mode` | 動き | PostgreSQL で近いもの |
| --- | --- | --- |
| `DISABLED` | 平文 | `disable` |
| `PREFERRED`（既定） | TLS を試し、できなければ平文 | `prefer` |
| `REQUIRED` | TLS が必須。証明書は確かめない | `require` |
| `VERIFY_CA` | CA を確かめる | `verify-ca` |
| `VERIFY_IDENTITY` | CA とホスト名を確かめる | `verify-full` |

文書自身が、既定の `PREFERRED` は高度な中間者攻撃を防げないので `VERIFY_CA` か `VERIFY_IDENTITY` のほうがよい、と注意しています（同上）。手元の 8.4.11 で試すと、次のようになりました。

```
== --ssl-mode=DISABLED
ERROR 2061 (HY000): Authentication plugin 'caching_sha2_password' reported error: Authentication requires secure connection.
== --ssl-mode=PREFERRED
Ssl_version	TLSv1.3
== --ssl-mode=REQUIRED
Ssl_version	TLSv1.3
== --ssl-mode=VERIFY_CA
ERROR 2026 (HY000): SSL connection error: CA certificate is required if ssl-mode is VERIFY_CA or VERIFY_IDENTITY
== --ssl-mode=VERIFY_CA --ssl-ca=/tmp/ca.pem
Ssl_version	TLSv1.3
== --ssl-mode=VERIFY_IDENTITY --ssl-ca=/tmp/ca.pem
ERROR 2026 (HY000): SSL connection error: error:0A000086:SSL routines::certificate verify failed
```

読み取れることが 3 つあります。

- **`DISABLED` が認証で失敗した**。既定の認証方式 `caching_sha2_password` は、サーバ側にまだ照合の結果が無いとき、パスワードを安全に渡せる経路を要求します。TLS が無い場合は RSA の公開鍵で包む方法があり、`--get-server-public-key` を付けると平文の接続でも通りました（`Ssl_version` が空）。ただし、その公開鍵自体を平文で受け取っているので、中間者に差し替えられれば意味がありません
- **サーバは起動時に証明書を自分で作っていた**。MySQL のサーバは、データディレクトリに `ca.pem`、`server-cert.pem`、`server-key.pem` があれば TLS を有効にし、OpenSSL で作られたサーバは足りないものを起動時に自動で作れます（[MySQL 8.4: 8.3.1](https://dev.mysql.com/doc/refman/8.4/en/using-encrypted-connections.html#using-encrypted-connections-server-side-startup-configuration)）。何も設定しなくても `PREFERRED` で TLS になったのはこのためです
- **自動で作られた証明書では `VERIFY_IDENTITY` が通らない**。中身を見ると、`subject=CN=MySQL_Server_8.4.11_Auto_Generated_Server_Certificate` で、SAN の拡張はありません（`No extensions in certificate`）。CA も自動生成の自己署名です。名前を確かめたいなら、サーバの名前を書いた証明書を自分で発行して入れる必要があります

サーバの側で平文を断るのが `require_secure_transport` です。有効にすると、TCP/IP の接続は TLS を使うものだけが許されます（Unix ドメインソケットなどは別扱い）（[MySQL 8.4: Configuring Encrypted Connections as Mandatory](https://dev.mysql.com/doc/refman/8.4/en/using-encrypted-connections.html#mandatory-encrypted-connections)）。

```
mysql> SET PERSIST require_secure_transport=ON;
== after require_secure_transport=ON, DISABLED
ERROR 3159 (HY000): Connections using insecure transport are prohibited while --require_secure_transport=ON.
```

パケットを見ると、この拒否が届くのは `Login Request user=root` の**後**でした。平文の接続では、利用者名と認証の応答が送られてから断られます。サーバの強制は、クライアントが最初から平文で話しかけることまでは止められません。

<Callout type="note" title="--ssl が「TLS を必須にする」ではなかった時代: BACKRONYM（2015）">
  MySQL 5.7.2 以前のクライアントライブラリでは、`--ssl` オプションが TLS を**任意**にするだけで、中間者が平文に落とせました
  （[CVE-2015-3152](https://nvd.nist.gov/vuln/detail/CVE-2015-3152)）。
  いまの `--ssl-mode=REQUIRED` 以上はこの反省の上にあります。オプションの名前から「強制される」と読み取れても、
  実際の意味は文書で確かめる必要がある、という例です。
</Callout>

## そのほかのデータストアとメッセージング

PostgreSQL と MySQL は「途中で切り替える」型でした。ほかのよく使われるものは、多くが**TLS 用のポートやリスナーを別に持つ**型です。

| 対象 | 載せ方 | 平文との関係 | クライアント証明書 |
| --- | --- | --- | --- |
| PostgreSQL | SSLRequest で切り替え。17 からは直接の TLS も | 同じポート。`pg_hba.conf` で区別 | `cert` / `clientcert`（任意） |
| MySQL | 能力フラグ CLIENT_SSL で切り替え | 同じポート。`require_secure_transport` | `REQUIRE X509` など（任意） |
| Redis（6.0 以降） | `tls-port` で TLS 専用のポートを開く | `port` と並べて開ける。`port 0` で平文を閉じる | **既定で必須**。`tls-auth-clients no` で外す |
| MongoDB | 同じポートで TLS を受ける | `net.tls.mode` の `allowTLS` / `preferTLS` で混在、`requireTLS` で TLS だけ | X.509 認証（任意） |
| Kafka | リスナーごとに `SSL` / `SASL_SSL` を割り当てる | `PLAINTEXT` / `SASL_PLAINTEXT` のリスナーと別 | `ssl.client.auth` |
| MQTT | TLS の上に載せる（8883） | 平文は 1883 | 端末の識別によく使う（第 75 回） |
| AMQP（RabbitMQ） | TLS 専用のリスナー（例: 5671） | 平文は 5672 | `verify_peer` と `fail_if_no_peer_cert` |

いくつか補足します。

**Redis** は 6 から TLS に対応しましたが、ビルド時に `BUILD_TLS=yes` で有効にする任意の機能です。`tls-port` は平文の `port` に**加えて**開くもので、`port 0` にしないと平文の口も残ります。クライアント証明書は既定で必須で、レプリカから主への接続には `tls-replication yes`、クラスタのノード間には `tls-cluster yes` が別に要ります（[Redis: TLS](https://redis.io/docs/latest/operate/oss_and_stack/management/security/encryption/)）。**クライアントとの区間だけを TLS にして、レプリケーションやクラスタのバスが平文のまま**、という構成になりやすいので注意が要ります。

**MongoDB** の `net.tls.mode` は、`allowTLS` ならサーバ間は TLS を使わず受け付けは両方、`preferTLS` ならサーバ間は TLS で受け付けは両方、`requireTLS` なら TLS だけです（[MongoDB: net.tls.mode](https://www.mongodb.com/docs/manual/reference/configuration-options/#mongodb-setting-net.tls.mode)）。混在の段階は、移行の途中に使うためのものです。

**Kafka** は、リスナーごとに `PLAINTEXT`、`SSL`、`SASL_PLAINTEXT`、`SASL_SSL` のどれかを割り当てます（[Kafka: Listener Configuration](https://kafka.apache.org/42/security/listener-configuration/)）。`SASL_SSL` は、TLS の上で SASL による利用者の認証を行う組み合わせです。クライアントは 2.0.0 から**サーバのホスト名の確認が既定で有効**で、`ssl.endpoint.identification.algorithm` を空にすると外れます（[Kafka: Encryption and Authentication using SSL](https://kafka.apache.org/42/security/encryption-and-authentication-using-ssl/)）。つまり、Kafka は既定の側が安全で、外すのに明示の操作が要る、という珍しい例です。

**RabbitMQ** は、TLS のリスナーを平文とは別のポートで開きます。クライアントライブラリの側の既定は言語ごとに違い、たとえば Java のクライアントには検証なしで TLS を使う `useTlsWithNoVerification()` があり、本番では使うなと書かれています。ホスト名の確認は `enableHostnameVerification()` を別に呼ぶ必要があります（[RabbitMQ: TLS Support](https://www.rabbitmq.com/docs/ssl)）。

## ドライバの既定値はばらばら

ここまでで、同じ「TLS を使う」という指定でも、何を確かめるかはクライアントの実装が決めていることが分かりました。困るのは、**同じ文字列が、ドライバによって違う意味になる**ことです。PostgreSQL の接続文字列 `sslmode=require` を例にとります。

| クライアント | 既定 | `sslmode=require` の意味 |
| --- | --- | --- |
| libpq（psql、多くの言語のラッパー） | `prefer`（検証なし、平文に落ちる） | 検証しない。ただし CA ファイルがあれば `verify-ca` と同じ（[libpq](https://www.postgresql.org/docs/current/libpq-connect.html#LIBPQ-CONNECT-SSLMODE)） |
| Go の lib/pq | `require`（libpq の既定と違う） | TLS 必須、検証はしない（[lib/pq](https://pkg.go.dev/github.com/lib/pq)） |
| Node.js の node-postgres（pg-connection-string） | （接続文字列の `sslmode` を `ssl` の設定に読み替える） | 既定では `ssl: true` になり、Node.js の既定どおり**証明書を検証する**。libpq と同じ意味にするには `uselibpqcompat=true` を付ける（[pg-connection-string](https://github.com/brianc/node-postgres/blob/master/packages/pg-connection-string/README.md)） |

libpq に合わせて書いた接続文字列を Node.js に持っていくと検証が**厳しく**なり、自己署名の証明書でつながらなくなります。そこで `ssl: { rejectUnauthorized: false }` を足して「直す」、という流れは、多くのプロジェクトで見かけます。逆に Node.js で `verify-full` 相当だった設定を libpq の世界に持っていけば、検証は**ゆるく**なります。

<Callout type="warn" title="よくある誤解: 「接続文字列に ssl と書いたので、安全につながっている」">
  `sslmode=require`、`--ssl-mode=REQUIRED`、`ssl=true`、`tls=true` のどれも、**暗号化を求めているだけで、相手を確かめているとは限りません**。
  上の実験の偽のサーバには、`prefer` と `require`（CA ファイルなし）が問題なくつながりました。
  確かめるべきことは 3 つです。**CA を渡しているか**（どのファイルか、OS のトラストストアか）、**ホスト名を照合しているか**（`verify-full`、`VERIFY_IDENTITY`）、
  **失敗したときに平文に落ちないか**（`prefer`、`PREFERRED`）。手元で確かめる一番簡単な方法は、この回の実験のように、別の CA の証明書を持つサーバに向けてみることです。
  つながってしまったら、その設定は中間者を通します。
</Callout>

クラウドのマネージドなデータベースでは、事業者が CA の証明書の束を配布しており、それを `sslrootcert` に渡して `verify-full` で接続するのが基本の形です。CA が更新される時期には証明書の束の入れ替えが要るので、第 114 回の証明書の寿命の話がここでも効いてきます。

## 中間層: プーラーとプロキシで区間が分かれる

データベースの前には、コネクションプーラーやプロキシが挟まることがよくあります。第 116 回で HTTPS について立てた問い「**何区間あって、それぞれ誰が終えているか**」が、そのまま当てはまります。

```
アプリ ══TLS①══▶ PgBouncer ══TLS②══▶ PostgreSQL
         ↑ client_tls_*         ↑ server_tls_*
```

PgBouncer は PostgreSQL のプロトコルを理解するプロキシなので、TLS をいったん終え、後ろへ別の接続を張ります。2 つの区間の設定は別々で、既定値は次のとおりです（[PgBouncer: Configuration](https://www.pgbouncer.org/config.html)）。

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| `client_tls_sslmode`（アプリ → PgBouncer） | `disable` | 平文。クライアントが TLS を求めても**無視する** |
| `server_tls_sslmode`（PgBouncer → PostgreSQL） | `prefer` | TLS を求め、断られたら平文。**サーバの証明書は検証しない** |

何も設定しなければ、アプリから PgBouncer までは平文、PgBouncer から PostgreSQL までは中間者に無防備な TLS です。PostgreSQL 本体を `hostssl` と `verify-full` で固めても、間に挟んだ 1 台の既定値で両方の区間が崩れます。PgBouncer の `client_tls_sslmode` の `verify-ca` と `verify-full` は「クライアント証明書を確かめる」という意味で、libpq の同じ名前とは向きが逆なのも、取り違えやすい点です（同上）。

中間層を挟むと、もう 1 つ失うものがあります。前の節のチャネルバインディングは、**クライアントと、TLS を終えた相手との間**で効く仕組みです。プーラーが TLS を終えるなら、アプリのチャネルバインディングが確かめられるのはプーラーの証明書までで、その先の PostgreSQL ではありません。第 116 回で見たとおり、TLS を終える機械は必ず秘密鍵を持ち、そこで平文が現れます。プーラーやプロキシは、データベースの全部の問い合わせと結果を平文で見る機械として扱う必要があります。

## 何と組み合わさって機能するか

| やりたいこと | 組み合わせる部品 |
| --- | --- |
| DB への接続を盗聴から守る | TLS（第 115 回）＋クライアントの `require` 以上＋サーバの `hostssl` / `require_secure_transport` |
| DB への接続を中間者から守る | 上に加えて、CA の証明書の配布（第 113 回）＋ `verify-full` / `VERIFY_IDENTITY` |
| パスワードの認証を中間者から守る | SCRAM ＋チャネルバインディング（`channel_binding=require`） |
| 切り替えの境目を無くす | `sslnegotiation=direct` ＋ ALPN `postgresql`（第 120 回の暗黙の TLS の型） |
| DB の利用者を証明書で確かめる | mTLS（第 116 回）＋ `cert` / `clientcert` ＋利用者名との対応づけ |
| プーラーを挟んでも守る | 区間ごとの `client_tls_*` / `server_tls_*` の設定＋プーラーを平文を見る機械として扱うこと |
| TLS に対応しない DB に届く | 第 123 回の SSH の `-L`、または次の第 125 回の stunnel |

次の第 125 回では、プロトコルそのものに TLS を載せるのではなく、**TLS で通り道を作り、その中に別のものを流す**方法を見ます。任意の TCP を TLS で包む stunnel、TLS を鍵の交換にだけ使ってデータは独自の形式で運ぶ OpenVPN、そして HTTPS の上に PPP を載せる SSL VPN の製品です。

## まとめ

- アプリからデータベースへの区間には、TLS の失敗を利用者に知らせる画面が無い。「暗号化なし」「暗号化だけ」「暗号化と相手の確認」のどれになっても、アプリは同じように動く
- PostgreSQL は 8 バイトの SSLRequest と 1 バイトの `S` / `N` で TLS に切り替える。この平文の 1 往復が、除去（`N` への書き換え）と、境目に残るバイトの注入（CVE-2021-23214 / 23222）の舞台になる
- libpq の既定の `sslmode=prefer` は中間者に対して何も守らない。手元の実験では、`N` に書き換える中間者に SQL の全文を読まれ、証明書の検証に失敗したときも平文でつなぎ直した。`require` は偽のサーバにつながる。CA ファイルがあると `require` が `verify-ca` になる互換の振る舞いもある
- 中間者に備えるのは `verify-full`（MySQL なら `VERIFY_IDENTITY`）。`sslrootcert=system` は既定を `verify-full` にする。SCRAM のチャネルバインディング（`channel_binding=require`）は、パスワードの側からサーバの証明書の秘密鍵を持つ相手だと保証する
- PostgreSQL 17 の `sslnegotiation=direct` は最初から TLS を始め、ALPN `postgresql` を必須にする。`prefer` とは組み合わせられず、平文に落ちる道が無い
- サーバ側の `hostssl` や `require_secure_transport` は平文の接続を断るが、クライアントがサーバを確かめているかどうかは変えない。`cert` 認証は実質 `trust` ＋ `clientcert=verify-full`
- MySQL は Server Greeting の後、CLIENT_SSL（2048）を立てた利用者名の手前までの SSLRequest で切り替える。自動生成の証明書には名前が無く、`VERIFY_IDENTITY` が通らない
- Redis、Kafka、AMQP、MQTT は TLS 用のポートやリスナーを別に持つ型が多い。Redis はレプリケーションとクラスタのバスに別の設定が要る。Kafka はホスト名の確認が既定で有効
- 同じ `sslmode=require` でも、libpq、lib/pq、node-postgres で意味が違う。PgBouncer の既定は、アプリ側が平文、DB 側が検証しない `prefer`。中間層を挟むと区間が分かれ、そこで平文が現れる
