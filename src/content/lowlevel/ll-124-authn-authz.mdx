## この章で見るもの

しかし、アプリケーションが本当に知りたいのは、鍵のことではありません。**このリクエストを送ってきたのは誰か**、そして**その人にこの操作を許してよいか**です。第 123 回の最後に置いた問いを、この章で引き受けます。

## 4 つの段階

ログインしてファイルを開く、という 1 つの操作の中には、性質の違う 4 つの段階があります。

```
  識別 (identification)   「私は alice です」と名乗る
        │                  → 主張にすぎない。誰でも名乗れる
        ▼
  認証 (authentication)   その主張が本当かを確かめる
        │                  → パスワード、署名、OTP などの証拠を検証する
        ▼
  認可 (authorization)    alice にこの操作を許すかを決める
        │                  → 規則（ロール、所有者、ポリシー）と照らし合わせる
        ▼
  監査 (audit)            誰が何をしたか、許されたか拒まれたかを残す
                           → 後から確かめるため
```

RFC 4949（インターネットのセキュリティ用語集）は、認証を「システムの主体について主張された身元を検証する過程」と定義し、それを**名乗る段階（identification step）**と**確かめる段階（verification step）**の 2 つに分けています。認可は「システムの主体に、システムへのアクセスの承認を与える過程」で、読み・書き・実行のような操作の種類ごとに決まるものとしています（[RFC 4949](https://www.rfc-editor.org/rfc/rfc4949.html)）。

大事なのは、**認証は「誰か」に答え、認可は「何をしてよいか」に答える**ことで、2 つは別々に失敗しうるということです。

| 段階 | 答える問い | 失敗すると | 典型的な置き場所 |
| --- | --- | --- | --- |
| 識別 | 誰だと言っているか | ― | ユーザ名、`sub`、uid |
| 認証 | 本当にその人か | なりすまし | ログイン画面、IdP、トークンの検証 |
| 認可 | それをしてよいか | 権限を越えた操作 | アプリの各処理、ゲートウェイ、ポリシーエンジン |
| 監査 | 何が起きたか | 事後に追えない | ログ、監査証跡 |

この分け方は OS にもあります。第 43 回で見たとおり、`login` がパスワードを確かめたあと、プロセスには **uid という番号**が付くだけです。ファイルを開くたびに、カーネルはその uid とファイルの rwx を照らし合わせます。**認証は 1 回、認可はシステムコールのたび**に行われているわけです。Web アプリでも構造は同じで、違うのは uid の代わりに何を持ち回るかだけです。

## 401 と 403 の本来の意味

HTTP には、この区別に対応するステータスコードが 2 つあります。

**401 Unauthorized** は、「このリソースに対する**有効な認証情報がない**ので、リクエストを処理しなかった」という意味です。401 を返すサーバは、**`WWW-Authenticate` ヘッダで少なくとも 1 つのチャレンジ**（どの方式で認証してほしいか）を送らなければなりません（[RFC 9110 15.5.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.2)）。クライアントは、それを見て認証情報を付け直せます。

**403 Forbidden** は、「サーバはリクエストを理解したが、実行を拒む」という意味です。認証情報が付いていたなら、サーバは**それでは足りない**と判断しています。クライアントは**同じ認証情報で自動的に再試行すべきではありません**（[RFC 9110 15.5.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4)）。

```
401: あなたが誰か分からない（または証拠が無効）。認証し直せば通るかもしれない
403: あなたが誰かは関係なく、あるいは分かったうえで、これは許さない
```

<Callout type="warn" title="よくある誤解: 401 は「認可されていない」の意味だ">
  名前が Unauthorized なので、「認可に失敗したら 401」と実装されがちです。
  しかし定義を読むと、401 が扱うのは**認証情報が欠けているか無効なこと**で、
  返すときは必ず `WWW-Authenticate` を付けます。名前と中身がずれているのは歴史的な経緯で、RFC 9110 でも名前は変わっていません。
  OAuth のベアラトークンの仕様も、この区別に従っています。トークンが期限切れや偽物なら `invalid_token` で **401**、
  トークンは有効だが権限（スコープ）が足りなければ `insufficient_scope` で **403** です（[RFC 6750 3.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-3.1)）。
  401 はクライアントに「トークンを取り直せ」と伝え、403 は「取り直しても無駄だ」と伝えます。取り違えると、
  クライアントがログイン画面へ飛ばし続けたり、逆に期限切れのトークンで失敗し続けたりします。
</Callout>

もう 1 つ、**404 で隠す**という選択肢があります。RFC 9110 は、禁じられたリソースの**存在そのものを隠したい**サーバが、403 の代わりに 404 を返してよいとしています（[RFC 9110 15.5.4](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.4)）。他人の注文番号を試したときに 403 が返れば、「その番号の注文は存在する」と分かってしまいます。404 なら、存在しないのか見せてもらえないのか区別できません。

実際のサービスでは、この 3 つの使い分けはかなりばらばらです。**クライアントを書く側は、401 を「認証をやり直す合図」、403 を「やり直しても変わらない合図」として扱い、それ以外の意味を期待しない**のが無難です。

## 認証の要素と多要素

「本当にその人か」を確かめる証拠は、昔から 3 種類に分けられます。NIST SP 800-63B（米国立標準技術研究所の、デジタル ID の認証に関する指針。執筆時点の最新版は 2025 年 7 月に確定した Rev.4）の用語集は、認証の要素を**知っているもの（something you know）、持っているもの（something you have）、その人自身であるもの（something you are）**の 3 つとしています（[NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)）。

| 要素 | 例 | 弱点 |
| --- | --- | --- |
| 知識 | パスワード、PIN | 推測される、使い回される、偽サイトで入力させられる |
| 所有 | 端末に入った秘密鍵、TOTP の鍵、セキュリティキー | 盗まれる、なくす |
| 生体 | 指紋、顔 | **秘密ではない**。取り替えられない |

**多要素認証**は、**種類の違う**要素を 2 つ以上使うことです。パスワードを 2 つ聞いても、知識が 2 つあるだけで多要素にはなりません。種類を分ける意味は、**1 つの攻撃で全部を奪われにくくする**ことにあります。偽サイトはパスワードを盗めても、手元のセキュリティキーの中の秘密鍵は盗めません。

生体について、同じ指針は「生体の特徴は秘密ではない」と明記し、**生体は物理的な認証器（持っているもの）と組み合わせた多要素認証の一部としてだけ使う**よう求めています（[NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)）。スマートフォンの指紋認証も、実際には「その端末の中の秘密鍵を使ってよいか」を指紋で許可しているのであって、指紋そのものをサーバに送っているわけではありません。この組み合わせが、第 125 回のパスキーの形です。

## 認証の結果は、持ち越さないと消える

ここで、見落とされやすい性質があります。**HTTP はステートレス**です。RFC 9110 は、各リクエストの意味はそれ単体で理解できるものと定義し、同じ接続の上の 2 つのリクエストが同じクライアントから来たとサーバが仮定してはならない、としています（[RFC 9110 3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-3.3)）。HTTP の認証の枠組みについても、「リクエストを認証するのに必要な情報は、すべてそのリクエストの中になければならない」と書いています（[RFC 9110 16.4.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-16.4.2)）。

つまり、ログイン画面でパスワードを確かめても、**その結果は次のリクエストには何も残っていません**。毎回パスワードを送らせるのでなければ、「この人は認証済みだ」という事実を何かに書いて、クライアントに持たせる必要があります。

```
  1. POST /login  (alice, パスワード)
                    ─────────────→  サーバ: パスワードを検証   ← 認証はここだけ
                    ←─────────────  「認証済み」の証を渡す
  2. GET /docs/1  + 証
                    ─────────────→  サーバ: 証を検証 → alice だと分かる → 認可
  3. GET /docs/2  + 証
                    ─────────────→  サーバ: 証を検証 → alice だと分かる → 認可
```

2 回目以降、サーバが確かめているのは**パスワードではなく証のほう**です。証を盗まれれば、パスワードを知らなくても alice になれます。多要素認証をいくら固くしても、**ログイン後に渡す証が弱ければそこから崩れる**わけです。

証の持たせ方は大きく 2 つに分かれます。

| 方式 | クライアントが持つもの | 状態の置き場所 | 詳しくは |
| --- | --- | --- | --- |
| サーバ側セッション | 意味のない ID（Cookie） | サーバの保存先 | 第 126 回 |
| 自己完結型トークン | 中身と署名（JWT など） | トークンそのもの | 第 127 回 |

どちらにも、「取り消しやすさ」と「サーバが覚えておく量」の間の trade-off があります。それは第 126 回で扱います。

## TLS の相手確認と、利用者の認証は別の層

第17章で確かめたものと、この章で確かめるものは、**層が違います**。

```
  ┌─────────────────────────────────────────────┐
  │ アプリケーション: 利用者は alice か。          │ ← この章（パスワード、ID トークン、セッション）
  │   alice は /docs/2 を読んでよいか             │ ← 認可（第 131 回）
  ├─────────────────────────────────────────────┤
  │ TLS: サーバは example.com の鍵を持っているか    │ ← 第 109〜113 回（証明書）
  │      （mTLS なら）クライアントはこの鍵を持つか   │
  └─────────────────────────────────────────────┘
```

TLS が保証するのは、**接続の向こうに、その証明書の秘密鍵を持つ者がいる**ことだけです。ブラウザがサーバを確かめても、サーバはブラウザの向こうの人が誰かをまだ知りません。逆に、利用者が正しいパスワードを入れても、その送り先が本物のサーバでなければ意味がありません。**ログインの仕組みは、TLS でサーバが確かめられていることを前提に成り立っています**。2 つは置き換えではなく、積み重ねです。

mTLS でクライアントの鍵を確かめた場合も、第 113 回で見たとおり、分かるのは「どの鍵か」までです。その鍵を持つサービスに何を許すかは、やはり認可の仕事として残ります。

## 「誰の代わりに」動くのか

ここまでは、本人が自分で操作する場面でした。しかし実際には、**別のプログラムが利用者の代わりに動く**場面がたくさんあります。

- 写真の印刷サービスが、利用者のクラウドストレージから写真を読む
- CI が、開発者の代わりにリポジトリへコメントを書く
- フロントのサービスが、利用者の代わりに後ろのサービスを呼ぶ

このとき、印刷サービスに利用者のパスワードを渡すのは最悪の方法です。印刷サービスは写真だけでなくメールも読めるようになり、パスワードを変えない限り取り消せず、ストレージ側から見ると本人と区別がつきません。

必要なのは、**「この利用者が、このクライアントに、この範囲の操作を、この期間だけ許した」という証**です。これを**委任**と呼びます。委任では、登場人物が 1 人増えます。

```
  利用者 (alice) ──許可──→ クライアント (印刷サービス) ──証──→ リソース (ストレージ)
                             「alice に代わって、写真を読む」
```

リソースの側で行う認可は、「alice は写真を読めるか」と「alice はこのクライアントに写真を読むことを許したか」の**両方**になります。この委任の証を発行する仕組みが、第 128 回の OAuth 2.0 です。

## よくある誤解

ここまでの区別を使うと、この分野でよく聞く 4 つの言い方が、それぞれどこで層を取り違えているかが見えます。

<Callout type="warn" title="誤解 1: OAuth はログインの仕組みだ">
  「Google で OAuth ログイン」という言い方が広まっているので、OAuth を認証の仕組みだと思いがちです。
  しかし OAuth 2.0 が決めているのは**委任**で、アクセストークンは「このクライアントに、この範囲のアクセスを許した」ことを
  **リソースサーバに**示すための物です。oauth.net の解説は「OAuth 2.0 は認証のプロトコルではない」と明言し、
  クライアントはアクセストークンの宛先ではなく、それを提示する役にすぎないと説明しています（[oauth.net: User Authentication with OAuth 2.0](https://oauth.net/articles/authentication/)）。
  アクセストークンを受け取ったことを「ログインした」とみなすと、別のアプリ向けに発行されたトークンを差し込まれても気づけません。
  「誰がログインしたか」を伝える層を OAuth の上に足したのが OpenID Connect（第 129 回）です。
</Callout>

<Callout type="warn" title="誤解 2: JWT は認証方式だ">
  「JWT 認証」という言い方もよく聞きます。しかし JWT は、クレーム（主張）を JSON で表し、
  署名などを付けて運ぶための**形式**です（[RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html)）。
  郵便でいえば封筒の規格で、中の手紙を誰が書いたか、誰宛てか、いつまで有効かは、中身と検証の手順が決めます。
  同じ JWT の形をしていても、ID トークン（誰がログインしたか）、アクセストークン（何を委任されたか）、
  ワークロードの身元（第 136 回）では、意味も、検証すべき項目も違います。「JWT だから安全」も「JWT だから認証済み」も成り立ちません。第 127 回で中身を読みます。
</Callout>

<Callout type="warn" title="誤解 3: API キーがあれば認証として十分だ">
  API キーは、多くの場合**リクエストをどの契約やプロジェクトに結びつけるか**を決めるための値です。
  Google Cloud のドキュメントは、標準の API キーは**主体（プリンシパル）を認証しない**と書いています。
  API キーは請求と使用量の割り当てのためにリクエストをプロジェクトに結びつけるだけで、
  主体が分からないので IAM で呼び出し元に権限があるかを確かめられない、という説明です（[Google Cloud: Manage API keys](https://docs.cloud.google.com/docs/authentication/api-keys)）。
  API キーには、**誰が使っているか（人か、どの端末か）が分からない**、**期限がなく長く生きる**、**ベアラ型なので拾った人も使える**という性質があります。
  公開してよい用途（地図の表示のように、使用量の管理が主目的のもの）と、利用者のデータに触れる用途を分けて考えます。
  機械の身元をより確かに示す方法は第 136 回で見ます。
</Callout>

4 つめは、認証と認可の取り違えそのものです。節を改めて、手を動かして確かめます。

## 誤解 4: ログインできれば何でもできる

**認証を通ったことを、認可を通ったことと同じに扱う**。これが最もよく起きる事故です。OWASP の API Security Top 10（2023 年版）の 1 位は **Broken Object Level Authorization（BOLA）**で、API がオブジェクトの識別子を受け取る処理を多く持つため、オブジェクト単位のアクセス制御の不備が広い攻撃面になる、と説明されています（[OWASP API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10)）。以前から IDOR（Insecure Direct Object Reference）と呼ばれてきたものと同じ種類の問題です。2 位は Broken Authentication、5 位は Broken Function Level Authorization（管理者向けの機能を一般の利用者が呼べる）で、**上位の多くが「認可の抜け」**です。

形はいつも同じです。

```
GET /api/orders/1001   Authorization: Bearer <alice のトークン>
  → サーバ: トークンは有効。alice だ（認証 OK）
  → サーバ: 注文 1001 を DB から取って返す    ← 1001 が alice のものかを見ていない
```

alice は正しくログインしています。トークンも本物です。**認証には何の問題もありません**。問題は、URL の数字を 1002 に書き換えたときに、他人の注文が返ってくることです。

### 手元で確かめる

Python の標準ライブラリだけで、小さな文書 API を作ります。トークンから利用者を引く部分（認証）と、操作を許すかを決める部分（認可）を分けて書き、起動時の引数で「所有者を確かめない版」と「確かめる版」を切り替えます。

```python
TOKENS = {"tok-alice": "alice", "tok-bob": "bob"}
ROLES = {"alice": {"reader"}, "bob": {"reader", "admin"}}
DOCS = {"1": {"owner": "alice", "body": "alice の下書き"},
        "2": {"owner": "bob", "body": "bob の給与明細"}}
CHECK_OWNER = sys.argv[1] == "fixed"

    def authenticate(self):
        h = self.headers.get("Authorization", "")
        if not h.startswith("Bearer "):
            self.send(401, {"error": "login required"},
                      [("WWW-Authenticate", 'Bearer realm="docs"')])
            return None
        user = TOKENS.get(h[len("Bearer "):])
        if user is None:
            self.send(401, {"error": "invalid_token"},
                      [("WWW-Authenticate", 'Bearer realm="docs", error="invalid_token"')])
        return user

    def do_GET(self):
        user = self.authenticate()
        if user is None:
            return
        doc = DOCS.get(self.path.removeprefix("/docs/"))
        if doc is None or (CHECK_OWNER and doc["owner"] != user):
            return self.send(404, {"error": "not found"})
        self.send(200, {"user": user, "doc": doc["body"]})

    def do_DELETE(self):
        user = self.authenticate()
        if user is None:
            return
        if "admin" not in ROLES[user]:
            return self.send(403, {"error": "admin only"})
        self.send(200, {"deleted": self.path, "by": user})
```

`python3 server.py vuln 8098` と `python3 server.py fixed 8099` で 2 つ起動し、curl で叩きます（出力は `Server` などのヘッダを省いて抜粋）。

まず認証の失敗です。トークンなしと、偽のトークンは、どちらも 401 で、`WWW-Authenticate` が付きます。

```
$ curl -si http://127.0.0.1:8098/docs/1
HTTP/1.0 401 Unauthorized
WWW-Authenticate: Bearer realm="docs"

{"error": "login required"}

$ curl -si -H 'Authorization: Bearer tok-mallory' http://127.0.0.1:8098/docs/1
HTTP/1.0 401 Unauthorized
WWW-Authenticate: Bearer realm="docs", error="invalid_token"
```

次に、所有者を確かめない版で、alice が自分の文書と bob の文書を読みます。

```
$ curl -si -H 'Authorization: Bearer tok-alice' http://127.0.0.1:8098/docs/1
HTTP/1.0 200 OK

{"user": "alice", "doc": "alice の下書き"}

$ curl -si -H 'Authorization: Bearer tok-alice' http://127.0.0.1:8098/docs/2
HTTP/1.0 200 OK

{"user": "alice", "doc": "bob の給与明細"}
```

**2 つ目が BOLA です**。サーバは応答に `"user": "alice"` と書いていて、alice だと正しく分かっています。それでも bob の給与明細を返しました。認証は完璧に動いていて、認可が 1 行も書かれていなかっただけです。

所有者を確かめる版では、同じリクエストが 404 になります。403 ではなく 404 にしているのは、前の節で見たとおり、**文書 2 が存在すること自体を alice に教えない**ためです。

```
$ curl -si -H 'Authorization: Bearer tok-alice' http://127.0.0.1:8099/docs/2
HTTP/1.0 404 Not Found

{"error": "not found"}
```

最後に、機能単位の認可です。削除は admin のロールを持つ人だけに許しています。

```
$ curl -si -X DELETE -H 'Authorization: Bearer tok-alice' http://127.0.0.1:8099/docs/1
HTTP/1.0 403 Forbidden

{"error": "admin only"}

$ curl -si -X DELETE -H 'Authorization: Bearer tok-bob' http://127.0.0.1:8099/docs/1
HTTP/1.0 200 OK

{"deleted": "/docs/1", "by": "bob"}
```

alice は誰なのか分かっていて、トークンを取り直しても結果は変わらないので 403 です。401 と 403 と 404 が、それぞれ別の段階の失敗を表していることが見えます。

<Callout type="note" title="「本人の ID と比べる」だけでは足りない">
  上の修正は、文書の所有者とトークンの利用者を比べるだけの単純なものでした。
  OWASP は、セッション（たとえば JWT から取り出した値）の利用者 ID と、リクエストの ID を比べるだけでは
  BOLA の解決として十分ではないと書いています（[OWASP API1:2023](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization)）。
  共有された文書、チームの文書、管理者による代理操作のように、「読んでよい人」は所有者だけではないからです。
  同じページは、**クライアントから受け取った値でレコードに触れるすべての処理で**、ログインした利用者にその操作が許されるかを確かめるよう勧めています。
  その規則をどう表し、どこで判定するかが第 131 回の主題です。
</Callout>

ID を連番でなくランダムな値にするのも、OWASP が挙げる対策の 1 つです。ただしそれは**当てにくくする**だけで、URL が漏れれば読まれます。第 61 回で見た DNS の「当て物の桁を増やす」対策と同じで、確かめる代わりにはなりません。

## この章の部品の関係

最後に、この章で扱う部品がどう組み合わさるかを 1 枚にしておきます。

```
          ┌────────── 本人を確かめる（第 125 回）──────────┐
          │ パスワード + ハッシュ（第 103 回）                 │
          │ TOTP = HMAC（第 103 回）+ 時刻                    │
          │ パスキー = 署名（第 106 回）+ オリジン（第 86 回）   │
          └───────────────────┬──────────────────────────┘
                              │ 認証の結果
                              ▼
          ┌────────── 結果を持ち越す ─────────────────────┐
          │ セッション ID + Cookie（第 126 回）              │
          │ JWT = JSON + 署名（第 106 回）+ JWKS（第 107 回）   │ ← 第 127 回
          └───────────────────┬──────────────────────────┘
                              │
          ┌────────── 他人の代わりに動く ──────────────────┐
          │ OAuth 2.0: 委任の証 = アクセストークン（第 128 回）│
          │ OIDC: OAuth + ID トークン(JWT) = 誰がログインしたか │ ← 第 129 回
          │ 受け取った側の検証、トークンを鍵や接続に縛る       │ ← 第 130 回
          └───────────────────┬──────────────────────────┘
                              ▼
          ┌────────── 何を許すか（第 131 回）──────────────┐
          │ スコープ ≠ 権限。RBAC / ABAC / ReBAC。          │
          │ オブジェクトごとに確かめる                       │
          └─────────────────────────────────────────────┘
      下敷き: TLS でサーバの鍵を確かめる（第 109〜113 回）。これがないと上の全部が偽サイトに流れる
```

どの部品も、単体では何かが欠けています。パスワードは証を渡さなければ 1 回で終わり、証は認可がなければ何でも通し、OAuth は OIDC がなければ誰がログインしたかを言わず、すべては TLS がなければ偽の相手に渡ります。**この章は、それぞれの部品が「何を保証し、何を保証しないか」を 1 つずつ確かめていく章**です。

## まとめ

- 識別は名乗ること、認証はそれを確かめること、認可は何を許すかを決めること、監査はそれを記録すること。認証と認可は別々に失敗する
- 401 は「有効な認証情報がない」で、`WWW-Authenticate` が必須。403 は「分かったうえで許さない」。存在を隠したいときは 404 でもよい
- ベアラトークンでは、無効なトークンが 401（`invalid_token`）、スコープ不足が 403（`insufficient_scope`）
- 認証の要素は知識・所有・生体。多要素は**種類の違う**要素を組み合わせる。生体は秘密ではなく、所有と組み合わせて使う
- HTTP はステートレスなので、認証の結果は証（セッションかトークン）として持ち越す。以後は証を盗まれれば本人になれる
- TLS の相手確認と利用者の認証は別の層で、積み重なって初めて意味を持つ
- 利用者の代わりに別のプログラムが動くには、パスワードではなく範囲と期限のある委任の証が要る
- OAuth は委任、JWT は形式、API キーは多くの場合プロジェクトの識別。どれもそれだけでは「利用者の認証」にならない
- 認証が完璧でも、オブジェクトごとの認可がなければ他人のデータが読める（BOLA）

次の回では、この章の入口である「本人を確かめる」部分に戻り、パスワードをどう保存するか、多要素のうちどれが偽サイトに強いのか、パスキーがなぜフィッシングに耐えるのかを見ます。
