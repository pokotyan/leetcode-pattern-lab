## 1 人なら速いのに、同時に来ると遅い

前回までの改善は、1 つのリクエストがする仕事を減らすものでした。往復を減らし、行を減らし、計算を前に移しました。この回は、**リクエストどうしが待ち合う時間** を扱います。

1 つのリクエストを単独で走らせれば 0.2 秒で終わる処理が、64 人が同時に来ると 1 人あたり 2 秒かかる。こういうとき、CPU もディスクも余っていることがよくあります。誰も働いていないのに、全員が誰かを待っているのです。

待ちの原因は、大きく 3 つに分かれます。

| 原因 | 何が起きているか | この回で見る例 |
| --- | --- | --- |
| ロックの範囲が広い | 関係の無いもの同士が同じロックを取り合う | 出品者の行、列車ごとの予約、全体で 1 つの mutex |
| ロックを持ったまま待つ | 外部 API や遅い処理の間、他の人を止め続ける | 購入のトランザクション中の決済 API |
| 全員が 1 か所を更新する | 1 つのカウンタや 1 行に書き込みが集中する | ID 採番の表 |

ロックそのものの仕組み、つまり InnoDB がどの行やすき間に何のロックを掛けるのかは第 100 回で、デッドロックが起きる条件と防ぎ方は第 39 回で見ました。この回では、それを **性能の問題として** 見ます。

## ロックを持ったまま外部 API を待つ

ISUCON9 予選（ISUCARI）は、椅子のフリーマーケットのサービスでした。商品の購入では、外部の配送サービスと決済サービスの API を呼びます。公式の解説は、購入処理の問題を次のように書いています（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。

> 購入には上で説明したキャンペーン機能により多くのユーザが、1つの商品に対して一挙に押し寄せます。さらに購入時にはトランザクション中に２つの外部サービス、配送サービスAPIと決済サービスAPIに対してリクエストを送るようになっていました。

参考実装の購入処理（[isucon9-qualify webapp/go/main.go](https://github.com/isucon/isucon9-qualify/blob/master/webapp/go/main.go) の `postBuy`）を要約すると、次の順になっています。

```go
tx := dbx.MustBegin()
tx.Get(&targetItem, "SELECT * FROM `items` WHERE `id` = ? FOR UPDATE", rb.ItemID)
// 出品中か、自分の商品でないか、などを確かめる
tx.Get(&seller, "SELECT * FROM `users` WHERE `id` = ? FOR UPDATE", targetItem.SellerID)
// 取引の行を INSERT し、商品を「取引中」に UPDATE する
APIShipmentCreate(...)   // 配送 API
APIPaymentToken(...)     // 決済 API
// 配送の行を INSERT する
tx.Commit()
```

`FOR UPDATE` で、商品の行と **出品者の行** に排他ロックを掛け、その後で外部 API を 2 回呼び、最後にコミットしています。ロックはコミットまで外れません。つまり、外部 API の応答を待っている間、

- 同じ商品を買おうとする人は全員、商品の行のロックを待つ
- **同じ出品者の別の商品** を買おうとする人も全員、出品者の行のロックを待つ

ことになります。解説は、この結果「ロック待ちが多く発生し、エラーやタイムアウトが多く発生し、単価の上昇がなくなったり、ベンチマーク自体が失敗になるなどの状況が生まれます。」と書いています。

### 手元で確かめる：外部 API をトランザクションの中で呼ぶか、外で呼ぶか

同じ形を再現しました。出品者 10 人、商品 5,000 点（出品者 1 人あたり 500 点）を用意し、64 人の買い手がそれぞれ、ランダムに選んだ商品を買い続けます。外部 API は、同じプロセスの中に立てた HTTP サーバで、指定の時間だけ待ってから応答します。1 回の購入で 2 回呼びます。

環境は Apple M1 Pro、Docker（OrbStack）の `mysql:8.4`（8.4.13）、Go 1.24.6、github.com/go-sql-driver/mysql v1.8.1 です。分離レベルは既定の REPEATABLE READ のままです。

**中で呼ぶ形**（参考実装と同じ）:

```go
tx.QueryRow("SELECT seller_id, status FROM items WHERE id = ? FOR UPDATE", item)
tx.QueryRow("SELECT num_sell_items FROM users WHERE id = ? FOR UPDATE", seller)
call() // 配送 API
call() // 決済 API
tx.Exec("UPDATE items SET buyer_id = ?, status = 'sold_out' WHERE id = ?", buyer, item)
tx.Exec("UPDATE users SET num_sell_items = num_sell_items + 1 WHERE id = ?", seller)
tx.Commit()
```

**外で呼ぶ形**: 商品を押さえる操作を、条件付きの UPDATE 1 文にして先にコミットします。外部 API はロックを何も持たない状態で呼び、最後に短いトランザクションで確定します。

```go
// 1. 押さえる: 出品中のときだけ「取引中」にする。0 行なら他の人が先に押さえた
res, _ := db.Exec("UPDATE items SET buyer_id = ?, status = 'trading' WHERE id = ? AND status = 'on_sale'", buyer, item)
if n, _ := res.RowsAffected(); n == 0 {
	return errSold
}
// 2. ロックを何も持たずに外部 API を呼ぶ
call()
call()
// 3. 確定する: 短いトランザクション
tx.Exec("UPDATE items SET status = 'sold_out' WHERE id = ?", item)
tx.Exec("UPDATE users SET num_sell_items = num_sell_items + 1 WHERE id = (SELECT seller_id FROM items WHERE id = ?)", item)
tx.Commit()
```

外部 API の応答を 100 ms にした場合と、ISUCON9 予選の配送 API がベンチマーク中に返していた 0.8 秒にした場合の結果です。

```text
inside  API 100ms 購入成功   246 (  32.5 件/秒)  応答 p50  1385.0 ms p99  3230.0 ms  売り切れ 8  ロック待ちタイムアウト 0
outside API 100ms 購入成功   785 ( 148.8 件/秒)  応答 p50   358.1 ms p99   971.0 ms  売り切れ 62  ロック待ちタイムアウト 0
inside  API 800ms 購入成功   114 (   3.9 件/秒)  応答 p50  9553.8 ms p99 20205.8 ms  売り切れ 1  ロック待ちタイムアウト 0
outside API 800ms 購入成功   375 (  31.6 件/秒)  応答 p50  1877.5 ms p99  2638.9 ms  売り切れ 18  ロック待ちタイムアウト 0
```

測定は 5〜10 秒間で、その時点で処理中だった購入も最後まで待っています。

| 外部 API | 形 | 購入成功 | 応答時間 p50 | p99 |
| --- | --- | --- | --- | --- |
| 100 ms | 中で呼ぶ | 32.5 件/秒 | 1,385 ms | 3,230 ms |
| 100 ms | 外で呼ぶ | 148.8 件/秒 | 358 ms | 971 ms |
| 800 ms | 中で呼ぶ | 3.9 件/秒 | 9,554 ms | 20,206 ms |
| 800 ms | 外で呼ぶ | 31.6 件/秒 | 1,878 ms | 2,639 ms |

外部 API が 800 ms のとき、中で呼ぶ形は応答の中央値が 9.6 秒、遅いものは 20 秒になりました。外部 API を 2 回呼ぶだけなら 1.6 秒で済むはずの処理です。

なぜこうなるのかは、上限を計算すると分かります。中で呼ぶ形では、出品者の行のロックを外部 API 2 回分の間ずっと持っています。出品者は 10 人なので、同時に進められる購入は最大 10 件、1 件あたり 2 × 0.8 = 1.6 秒です。上限は 10 / 1.6 = 6.25 件/秒で、測った 3.9 件/秒はその手前です。買い手が 64 人いても、出品者が 10 人なら 10 人分しか進みません。**買い手の数ではなく、ロックの数が上限を決めています**。

外で呼ぶ形では、外部 API を待っている間に何のロックも持たないので、64 人の買い手がそれぞれ並行に外部 API を待てます。上限は 64 / 1.6 = 40 件/秒で、測った 31.6 件/秒はその近くです。

<Callout type="warn" title="この回の数値は、混んだマシンで測っています">
  測定中、同じマシンでは他の実験も動いていて、ロードアベレージは 25〜50 ほどでした。
  そのため、データベースの 1 回の往復やコミットが静かなマシンより遅く、外で呼ぶ形でも p50 が理論値（200 ms、1,600 ms）より長くなっています。
  同じ測定を繰り返すと絶対値は数割ぶれましたが、2 つの形の差の大きさは変わりませんでした。
</Callout>

### 誰が何を待っているのかを見る

中で呼ぶ形を走らせている最中に、1.5 秒ごとに InnoDB の状態を覗きました。`information_schema.innodb_trx` で実行中のトランザクションとロック待ちの数を、`performance_schema.data_lock_waits` でどの表のどの索引で待っているかを数えています（[MySQL 8.4 Reference Manual: The data_lock_waits Table](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-data-lock-waits-table.html)）。

```sql
SELECT COUNT(*), SUM(trx_state = 'LOCK WAIT') FROM information_schema.innodb_trx;
SELECT r.OBJECT_NAME, r.INDEX_NAME, COUNT(*)
FROM performance_schema.data_lock_waits w
JOIN performance_schema.data_locks r ON r.ENGINE_LOCK_ID = w.REQUESTING_ENGINE_LOCK_ID
GROUP BY 1, 2;
```

```text
trx=64 lock_wait=54
users	PRIMARY	199
---
trx=64 lock_wait=54
users	PRIMARY	253
---
trx=64 lock_wait=54
users	PRIMARY	314
```

64 のトランザクションのうち 54 がロック待ちで、待っている先はすべて `users` の主キー、つまり出品者の行でした。動いているのは 10、ちょうど出品者の数です。最後の列が 54 より大きいのは、`data_lock_waits` が「待っている側と、それを止めている側」の組を 1 行ずつ数えるためで、列の後ろの方にいる人は前にいる全員に止められています。

このとき、MySQL もアプリのプロセスもほとんど働いていません。全員が外部 API の応答と、その応答を待っている誰かを待っています。**CPU 使用率が低いのに遅い** ときは、こうした待ちを疑います。第 265 回で触れた off-CPU のプロファイルや、MySQL の待ちの統計が手掛かりになります。

### トランザクションの外に出すときに考えること

外で呼ぶ形は、1 つのトランザクションを 3 段に分けています。速くなる代わりに、段と段の間で失敗したときのことを自分で決めなければなりません。

| 失敗する場所 | 状態 | 対応 |
| --- | --- | --- |
| 1 の後、外部 API が失敗した | 商品が「取引中」のまま | 「出品中」に戻す（補償処理） |
| 外部 API が成功し、3 の前にプロセスが落ちた | 外部では決済済み、こちらは「取引中」 | 「取引中」のまま古くなった行を拾い、外部の状態を問い合わせて確定させるか取り消す |
| 外部 API の応答がタイムアウトした | 外部で処理されたか分からない | 冪等キーを付けて再試行するか、外部に問い合わせる（第 114 回） |

1 つのトランザクションに入れていれば、データベースの中は全部か無しかでした。外部 API はもともとトランザクションの外にあるので、中で呼んでいても、外部で決済した後に自分のコミットが失敗すれば同じ食い違いが起きます。**中で呼んでも、外部との整合は守られていなかった** のです。外に出すことで、その事実が状態（「取引中」）として表に出て、扱えるようになります。

ISUCON9 予選の解説が示した対策は、少し違う形でした。

> 対策としては、mutexやflockによる排他制御が考えられます。1つの商品につき1つのトランザクションのみが開始されるようアプリケーションにて制御を行い、ロックが解放された直後のトランザクション開始前に商品が購入できるステータスにあるかどうかをチェックすると、データベースに負荷がかからず素早くレスポンスが可能となるかと思います。

同じ商品への購入が殺到するとき、データベースのロックの列に並ばせる前に、アプリの中で商品ごとに 1 人だけを通し、残りは「もう売れたか」を確かめてすぐ返す、という方法です。外で呼ぶ形の条件付き UPDATE も、2 人目以降に 0 行の更新を返して即座に断るので、効果は近いものになります。どちらも、**負けが決まっている人を長く待たせない** 工夫です。

## 排他の粒度

ロックの範囲が広すぎる問題は、外部 API が無くても起きます。

ISUCON9 本選（ISUXPRESS）は、新幹線の座席予約でした。参考実装は、予約のたびに `SELECT * FROM reservations WHERE date=? AND train_class=? AND train_name=? FOR UPDATE` で、その列車の予約をすべてロックしていました（[isucon9-final webapp/go/main.go](https://github.com/isucon/isucon9-final/blob/master/webapp/go/main.go)）。しかも `reservations` 表には、この条件に合う索引がありませんでした（[01_schema.sql](https://github.com/isucon/isucon9-final/blob/master/webapp/sql/01_schema.sql)）。第 100 回で見たとおり、InnoDB のロックは索引に掛かるので、索引の無い条件で `FOR UPDATE` すると、走査したすべての行がロックされます。列車ごとのつもりのロックが、表全体のロックになっていたわけです。公式の解説は「DBをロックしている範囲も広いため、ロックは車両毎にかけ、できるだけロック範囲を限定することで予約重複を避けつつ座席検索が可能になります。」と書いています（[ISUCON9 本選問題の解説と講評](https://isucon.net/archives/53916974.html)）。

アプリの中で mutex を使う場合も、粒度の考え方は同じです。

### 手元で確かめる：mutex の粒度

64 のゴルーチンが、1,000 個のキーからランダムに 1 つを選び、そのキーの mutex を取って 2 ms の処理（`time.Sleep`）をして離す、という作業を 2 秒間繰り返しました。データベースは使っていません。

```go
// 全体で 1 つ
var global sync.Mutex

// キーごと: 初めて使うキーの mutex を作って共有する
var per sync.Map
m, _ := per.LoadOrStore(k, &sync.Mutex{})
m.(*sync.Mutex).Lock()
```

```text
全体で 1 つの mutex               273 件/秒
キーごとの mutex                13710 件/秒
キーごと（配列）、10 キーに集中           2139 件/秒
```

| 粒度 | 処理できた量 | 上限の見積もり |
| --- | --- | --- |
| 全体で 1 つ | 273 件/秒 | 1 / 2 ms = 500 件/秒 |
| キーごと（1,000 キーに分散） | 13,710 件/秒 | 64 / 2 ms = 32,000 件/秒（ゴルーチンの数で頭打ち） |
| キーごと、ただし 10 キーに集中 | 2,139 件/秒 | 10 / 2 ms = 5,000 件/秒 |

見積もりより低いのは、`time.Sleep` が混んだマシンでは 2 ms より長く眠るためです。差の大きさは見積もりどおりで、**同時に進められる数は、ロックの数と、アクセスがロックにどう散らばるかで決まります**。キーごとにしても、アクセスが一部のキーに集中すれば、その数で頭打ちになります。ISUCON9 予選のキャンペーンのように 1 つの商品に人が殺到する場面では、商品ごとのロックにしても、その 1 商品の購入は 1 件ずつしか進みません。だからこそ、待つ人を早く帰す工夫が要ったのです。

<Callout type="note" title="アプリの mutex は、1 つのプロセスの中でしか効かない">
  `sync.Mutex` で守れるのは、同じプロセスの中のゴルーチンどうしだけです。
  アプリのサーバを 2 台にすると、それぞれのプロセスが自分の mutex を持つので、排他になりません。
  ファイルの `flock` も、同じマシンの中のプロセスどうしでしか効きません。
  複数の台で排他が要るなら、データベースの行ロック、MySQL の `GET_LOCK()`、Redis などの共有の場所にロックを置きます。
  第 275 回で台数を増やすときに、この前提が崩れていないかを確かめることになります。
</Callout>

## ファイルロックをトランザクションに置き換える

ISUCON12 予選（ISUPORTS）では、アプリ全体がテナントごとのファイルロックで守られていました。解説はこう説明しています（[ISUCON12 予選問題の解説と講評](https://isucon.net/archives/56850281.html)）。

> このアプリケーションはなぜか実装者にトランザクションの知識がない(という設定の)ため、データの整合性を保つためにアプリケーション上で排他ロックを行っています。排他ロックの実装は、大昔のWebアプリケーションを知っている方には懐かしの flock です。

参考実装は `flockByTenantID` という関数で、テナントごとのロックファイルに `flock` を掛けていました（[isucon12-qualify webapp/go/isuports.go](https://github.com/isucon/isucon12-qualify/blob/main/webapp/go/isuports.go)）。スコアの CSV を取り込む処理は、表の行を DELETE してから CSV の内容を 1 行ずつ INSERT するもので、その途中を他のリクエストに見せないために、ランキングの **参照** でも同じロックを取っていました。テナントの中では、読み出しも書き込みも 1 列に並んでいたことになります。

解説の答えは「DELETEとINSERTを1トランザクションで実行すれば、排他のための flock を丸ごとなくすことができます。」でした。第 99 回の MVCC により、トランザクションの途中の状態は他の読み手から見えません。読み手は、書き手のコミット前の版を待たずに読めます。**データベースがすでに持っている仕組みを、アプリが自前のロックで作り直していた** のです。

| | flock | トランザクション |
| --- | --- | --- |
| 読み手は書き手を待つか | 待つ（同じロックを取る） | 待たない（コミット前の版を読む） |
| 書き手どうし | テナント単位で 1 列 | 触る行が重なるときだけ待つ |
| 効く範囲 | 同じマシンのプロセスだけ | データベースにつながる全員 |
| 途中で落ちたら | 書きかけのデータが残る | 巻き戻る |

## 外部 API を並列に呼び、打ち切る

ロックを持たずに外部 API を待つようにしても、1 つのリクエストの中で外部 API を順に何回も呼んでいれば、そのリクエストは遅いままです。ISUCON9 予選の取引一覧は、表示する取引ごとに配送 API で状態を問い合わせていました。解説によれば、この API はベンチマーク中「0.8秒かかるようにしてあります」とされ、対策として「必要な回数のAPI呼び出しを非同期・並列で行うことでかかる時間を短くする方法が考えられます。」と書かれています（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。同じ段落は、ドキュメントを読むと実はほとんどの呼び出しが不要だったことも指摘しています。呼ばずに済むなら、それが最善です。

### 手元で確かめる：順に、並列に、打ち切り付きで

100 ms で応答する API を 10 回呼びました。2 つ目の場面では、10 回のうち 1 回だけ 3 秒かかるようにしています。並列化には `golang.org/x/sync/errgroup`（v0.10.0）を、打ち切りには `context.WithTimeout` を使いました（[pkg.go.dev: context](https://pkg.go.dev/context)、[pkg.go.dev: errgroup](https://pkg.go.dev/golang.org/x/sync/errgroup)）。

```go
ctx, cancel := context.WithTimeout(context.Background(), 300*time.Millisecond)
defer cancel()
var g errgroup.Group
for i := 0; i < 10; i++ {
	g.Go(func() error {
		req, _ := http.NewRequestWithContext(ctx, "GET", url(i), nil)
		res, err := http.DefaultClient.Do(req) // 期限を過ぎると err が返る
		...
	})
}
g.Wait()
```

```text
順に 10 回                1096 ms
並列に 10 回               109 ms
-- 10 回のうち 1 回だけ 3 秒かかる場合
並列に 10 回              3015 ms
並列 + 300 ms で打ち切り   302 ms（打ち切られた呼び出し 1）
```

並列にすると、時間は合計ではなく **最も遅い 1 回** で決まります。全部が 100 ms なら 109 ms になりますが、1 回でも 3 秒かかれば 3 秒です。並列化は、遅い呼び出しの影響を消すのではなく、最も遅いものに揃えるだけです。

そこで打ち切りを組み合わせます。300 ms を過ぎたら待つのをやめ、得られた結果だけで応答します。打ち切った呼び出しの分をどう扱うかは、仕様で決めます。

- 表示の一部なら、「状態を取得できませんでした」と出すか、前回の値（第 270 回の許される古さ）を出す
- 処理に必須なら、全体を失敗として返し、利用者に再試行してもらう
- 書き込みを伴う呼び出しなら、外部で処理されたかどうかが分からない状態になる。冪等キーを付けておき、後で確認する

<Callout type="warn" title="既定ではタイムアウトしない">
  Go の `http.DefaultClient` には全体のタイムアウトが設定されていません（`http.Client` の `Timeout` は 0 で、0 は「タイムアウトしない」を意味します。
  [pkg.go.dev: net/http](https://pkg.go.dev/net/http#Client)）。
  外部 API が応答を返さなくなると、それを呼んだリクエストは永久に待ち、そのリクエストが持っていたロックやコネクションも返ってきません。
  外部 API を呼ぶ箇所には、必ず期限を付けます。
</Callout>

## ID の採番に全員が並ぶ

最後は、全員が同じ 1 か所を更新する場合です。

ISUCON12 予選の参考実装は、システム全体で一意な ID を、MySQL の 1 行の表で採番していました。解説は論点として「システム内で一意のIDを発行するために、MySQLのauto_incrementが設定されたテーブルに更新を掛けてIDを採番している」「IDは文字列型なので、UUIDやULID、他にも一意になるような文字列であれば代用できる」と挙げています。採番の関数は次の形で、**デッドロックで失敗したら最大 100 回まで再試行する** 作りになっていました（[isucon12-qualify webapp/go/isuports.go](https://github.com/isucon/isucon12-qualify/blob/main/webapp/go/isuports.go)）。

```go
// id_generator: id BIGINT AUTO_INCREMENT PRIMARY KEY, stub CHAR(1) UNIQUE
for i := 0; i < 100; i++ {
	ret, err := adminDB.ExecContext(ctx, "REPLACE INTO id_generator (stub) VALUES (?);", "a")
	if err != nil {
		if merr, ok := err.(*mysql.MySQLError); ok && merr.Number == 1213 { // deadlock
			continue
		}
		...
	}
	id, err = ret.LastInsertId()
	break
}
```

`REPLACE` は、一意キー `stub` が `'a'` の行を消して入れ直し、そのたびに `AUTO_INCREMENT` で新しい `id` を得ます。表には常に 1 行しかなく、全員がその 1 行を消しては入れ直します。

### 手元で確かめる：並行数を増やすと

同じ表を作り、並行数 1、8、32 で 5 秒ずつ採番を続けました。比べるために、普通の `AUTO_INCREMENT` の表への INSERT も同じように測っています。どちらも autocommit です。

```text
INSERT INTO plain（比較）  並行  1:      50 個/秒  デッドロック      0 回（採番 1 個あたり 0.00 回）
INSERT INTO plain（比較）  並行  8:     163 個/秒  デッドロック      0 回（採番 1 個あたり 0.00 回）
INSERT INTO plain（比較）  並行 32:     265 個/秒  デッドロック      0 回（採番 1 個あたり 0.00 回）
REPLACE INTO id_generator  並行  1:      77 個/秒  デッドロック      0 回（採番 1 個あたり 0.00 回）
REPLACE INTO id_generator  並行  8:      61 個/秒  デッドロック    173 回（採番 1 個あたり 0.54 回）
REPLACE INTO id_generator  並行 32:      54 個/秒  デッドロック    745 回（採番 1 個あたり 2.58 回）
```

| 並行数 | 普通の INSERT | `REPLACE INTO id_generator` | 採番 1 個あたりのデッドロック |
| --- | --- | --- | --- |
| 1 | 50 個/秒 | 77 個/秒 | 0 |
| 8 | 163 個/秒 | 61 個/秒 | 0.54 回 |
| 32 | 265 個/秒 | 54 個/秒 | 2.58 回 |

普通の INSERT は、並行数を増やすと処理量が増えました。第 99 回のグループコミットで、同時に来たコミットの `fsync` がまとめられるからです。`id_generator` は逆に、並行数を増やすと **減りました**。並行数 32 では、ID を 1 つ得るまでに平均 2.58 回デッドロックで失敗し、やり直しています。この直前に行った 1 回目の測定では、並行数 1、8、32 で 69、21、9 個/秒、デッドロックは 1 個あたり 0、0.62、3.58 回で、混雑の影響で絶対値は違いますが、傾向は同じでした。

なぜ 1 行の表でデッドロックが起きるのか。`SHOW ENGINE INNODB STATUS` の最後のデッドロックの記録を抜粋します。

```text
*** (1) TRANSACTION:
REPLACE INTO id_generator (stub) VALUES ('a')
*** (1) HOLDS THE LOCK(S):
RECORD LOCKS ... index stub of table `bench`.`id_generator` trx id 15441 lock_mode X locks gap before rec
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index stub of table `bench`.`id_generator` trx id 15441 lock_mode X waiting
*** (2) TRANSACTION:
REPLACE INTO id_generator (stub) VALUES ('a')
*** (2) HOLDS THE LOCK(S):
RECORD LOCKS ... index stub of table `bench`.`id_generator` trx id 15429 lock_mode X
*** (2) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index stub of table `bench`.`id_generator` trx id 15429 lock_mode X locks gap before rec insert intention waiting
*** WE ROLL BACK TRANSACTION (1)
```

舞台は一意索引 `stub` です。`REPLACE` は、重複する行を見つけてロックし、消し、新しい行を挿入します。消された行は削除の印が付いたまま索引に残るので、一意索引の上には `'a'` の古い版がいくつも並びます。一方のトランザクションはそのすき間のロック（`locks gap before rec`）を持ったまま行のロックを待ち、もう一方は行のロックを持ったまま同じすき間への挿入インテンションロックを待っています。第 100 回で見たギャップロックと挿入インテンションロックが、1 行を全員で取り合う形で循環待ちになったのです。

対策は、**採番を 1 か所に集めない** ことです。

| 方法 | 採番の場所 | 注意 |
| --- | --- | --- |
| 対象の表の `AUTO_INCREMENT` | その表への INSERT | ID を INSERT の前に知る必要があるときは使いにくい |
| UUID（v4、v7）、ULID | アプリの中 | 主キーにするなら時刻順の v7 や ULID（第 97 回） |
| Snowflake 型の ID | アプリの中（台ごとの番号を埋め込む） | 台の番号の割り当てと時計の巻き戻り |

ISUCON12 本選（ISU CONQUEST）でも、ID の採番が改善の論点に挙がり、解説は Snowflake ID のようなアプリ側での採番を想定していたと書いています。データベースを水平分割するなら、どの台でも重ならない ID をアプリで作れることが前提になります（[ISUCON12 本選問題の解説と講評](https://isucon.net/archives/56959385.html)）。

## 本番で使うときの判断

| 症状 | 疑うこと | 確かめ方 |
| --- | --- | --- |
| 同時アクセスが増えると応答時間が伸びるが、CPU は余っている | ロック待ち、外部 API 待ち | `innodb_trx` の `LOCK WAIT`、`data_lock_waits`、外部 API の呼び出し時間の計測 |
| 特定の商品やユーザーにアクセスが集まると遅い | ロックの範囲が、アクセスの集まる単位と一致している | 待っている行の主キーの分布 |
| 並行数を増やすと処理量が減る、デッドロックが頻発する | 全員が同じ行やすき間を更新している | `SHOW ENGINE INNODB STATUS` の最後のデッドロック |
| たまに 50 秒近くかかって失敗する | ロック待ちのタイムアウト | `innodb_lock_wait_timeout`（既定 50 秒）と、エラー 1205 の発生数 |

最後の行の 50 秒は、InnoDB が行ロックを待つ時間の既定値です（[MySQL 8.4 Reference Manual: InnoDB Startup Options and System Variables](https://dev.mysql.com/doc/refman/8.4/en/innodb-parameters.html)）。Web のリクエストとしては長すぎるので、利用者はとっくに諦めているのに、データベースの中では待ち続けている、ということが起きます。すぐに断ってよい処理なら、第 116 回で見た `NOWAIT` や `SKIP LOCKED` で待たない選択もできます。

ロックの改善は、次の順に考えます。

1. **ロックを持ったまま待たない**。外部 API、ファイルの読み書き、重い計算は、トランザクションの外に出す
2. **ロックの範囲を、実際にぶつかる単位まで狭める**。全体より列車、列車より車両。索引が無いと範囲が勝手に広がる
3. **負けが決まっている人を早く帰す**。条件付きの UPDATE、`NOWAIT`、アプリでの事前の確認
4. **全員が 1 か所を更新する形をやめる**。採番、カウンタ、合計は分散させるか、まとめて更新する（第 272 回）

どれも、仕様が許す範囲で行います。ロックを狭めすぎれば、二重の予約や二重の購入が起きます。ISUCON の多くの問題で、ベンチマーカーは負荷をかけながら整合性も確かめていて、ロックを外しすぎると失格になります。速さと正しさの境目は、「同時に起きてはいけないことは何か」を仕様から書き出して、それを守る最小の範囲で決めます。

次回は、ここまで 1 台のサーバの中で行ってきた改善から一歩出て、複数の台に役割を分けて使う方法を見ます。

## まとめ

- 単独なら速いのに同時に来ると遅いとき、多くは誰かが誰かを待っている。CPU が余っていても遅いのはその兆候
- 行ロックを持ったまま外部 API を待つと、そのロックを必要とする全員が外部 API の応答を待つことになる
- 手元の再現では、出品者の行を押さえたまま 0.8 秒の API を 2 回呼ぶ形は 3.9 件/秒、応答の中央値 9.6 秒。外に出すと 31.6 件/秒、1.9 秒になった
- 中で呼ぶ形の上限は、買い手の数ではなくロックの数（出品者 10 人）で決まっていた。実行中の 64 トランザクションのうち 54 が出品者の行を待っていた
- トランザクションの外に出すと、段の間で失敗したときの補償処理が要る。ただし中で呼んでいても、外部との整合はもともと守られていなかった
- 排他の粒度は、同時に進められる数を決める。全体で 1 つの mutex と、キーごとの mutex では 50 倍の差が出た。キーごとでも、アクセスが集中すればその数で頭打ちになる
- 索引の無い条件で `FOR UPDATE` すると、走査した行がすべてロックされる（ISUCON9 本選）
- アプリの `flock` や mutex でデータベースの整合を守るのは、MVCC とトランザクションの作り直しになっていることが多い（ISUCON12 予選）
- 外部 API の呼び出しは並列にし、期限を付けて打ち切る。並列化だけでは、最も遅い 1 回に揃うだけ
- 1 行の表で全員が採番すると、並行数を増やすほど遅くなり、手元では採番 1 個あたり 2.58 回のデッドロックが起きた。採番はアプリ側や対象の表に分散させる
