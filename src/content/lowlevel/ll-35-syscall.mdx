## 自分では何もできない

ユーザ空間のプログラムは、次のことが**一切できません**。

- ディスクに読み書きする
- ネットワークにパケットを送る
- 画面に文字を出す
- メモリを新しく確保する
- プロセスを作る

すべてカーネルに頼む必要があります。その頼み方が **システムコール** です。

## 関数呼び出しとは違う

`printf` は関数呼び出しです。`write` はシステムコールです。見た目は似ていますが、中身はまったく違います。

| | 関数呼び出し | システムコール |
| --- | --- | --- |
| 命令 | `call` | `syscall`（x86-64）、`svc`（ARM64） |
| 特権レベル | 変わらない | **リング 3 → リング 0** |
| 飛び先 | 指定できる | **カーネルが決めている。指定できない** |
| スタック | 同じものを使う | **カーネル用のスタックに切り替わる** |
| コスト | 数ナノ秒 | **数百ナノ秒〜数マイクロ秒** |

<Callout type="note" title="飛び先を指定できないことが安全性の根拠">
  もしユーザが飛び先を指定できたら、カーネルの好きな場所に特権付きで飛び込めてしまいます。
  `syscall` 命令の飛び先は、起動時にカーネルが特別なレジスタ（x86-64 では `MSR_LSTAR`）に
  登録したアドレスに固定されています。**ユーザ空間からは変更できません。**

  つまり、「入口は 1 つだけ、そこに門番がいる」という構造です。
</Callout>

## 呼び出しの手順

x86-64 Linux では、レジスタに番号と引数を入れて `syscall` を実行します。

| レジスタ | 内容 |
| --- | --- |
| `rax` | システムコール番号 |
| `rdi`, `rsi`, `rdx`, `r10`, `r8`, `r9` | 引数（最大 6 個） |
| `rax`（戻り時） | 戻り値。負の値はエラー |

```asm
mov  rax, 1          ; 1 = write
mov  rdi, 1          ; fd = 1（標準出力）
mov  rsi, msg        ; バッファのアドレス
mov  rdx, 13         ; 長さ
syscall
```

**引数レジスタが、関数呼び出し規約と微妙に違う**ことに注意してください。第 4 引数が `rcx` ではなく `r10` です。`syscall` 命令が `rcx` を戻り先アドレスの保存に使うためです。

カーネル側では、

1. ユーザのレジスタをカーネルスタックに保存する
2. `rax` の番号でシステムコール表を引く
3. 引数を検証する（**ポインタが本当にそのプロセスのものか**など）
4. 実際の処理を行う
5. 戻り値を `rax` に入れ、ユーザモードに戻る

**3 の検証が極めて重要です。** ユーザが渡したポインタをそのまま信用してカーネル空間に書き込んだら、任意のメモリを破壊できてしまいます。カーネルは専用の関数（`copy_from_user` / `copy_to_user`）を使い、必ず検証を通します。

## libc が包んでいる

C から `write()` を呼ぶとき、直接 `syscall` 命令を書いているわけではありません。libc の薄いラッパ関数が間に入ります。

```c
ssize_t write(int fd, const void *buf, size_t n) {
    long ret = do_syscall(1, fd, buf, n);
    if (ret < 0) { errno = -ret; return -1; }
    return ret;
}
```

libc がやっていること：

- 引数をシステムコールの規約に合わせて並べ替える
- 負の戻り値を `errno` に移し、`-1` を返す（C の慣習に合わせる）
- 移植性を提供する（アーキテクチャごとの違いを吸収）

`printf` はさらに上の層です。書式を展開し、**バッファに溜め**、いっぱいになるか改行が来たときに初めて `write` を呼びます。

<Callout type="warn" title="バッファリングが原因の混乱">
  標準出力が端末なら行単位、パイプやファイルなら**ブロック単位**でバッファされます。

```bash
./a.out            # 出力がすぐ見える
./a.out | cat      # 4KB 溜まるまで出てこない
```
  プログラムがクラッシュすると、バッファに残った出力は失われます。
  「ログの最後の数行が出ていない」原因はたいていこれです。
  `fflush(stdout)` か、`setvbuf` でバッファリングを切ることで対処します。
</Callout>

## どれくらい遅いのか

システムコール 1 回のコストは、おおよそ 100〜500 ナノ秒です。関数呼び出しの 100 倍以上。

さらに、KPTI（Meltdown 対策）が有効だとページテーブルの切り替えが加わり、さらに数倍になります。

**だから、システムコールの回数を減らすことが最適化の王道です。**

| 悪い | 良い |
| --- | --- |
| 1 バイトずつ `write` | バッファに溜めてまとめて `write` |
| ループの中で `gettimeofday` | 1 回取ってから使い回す |
| ファイルごとに `open`/`close` | 開いたまま使い回す |
| 1 つずつ `send` | `writev` でまとめて送る |

## vDSO

`gettimeofday` や `clock_gettime` は、非常に高い頻度で呼ばれます。しかし実際にやることは「カーネルが持っている時刻を読む」だけで、特権が必要な操作ではありません。

そこで **vDSO**（virtual Dynamic Shared Object）という仕組みがあります。カーネルが、各プロセスのアドレス空間に小さな共有ライブラリをマップします。その中に時刻取得の実装が入っており、**カーネルに入らずに答えを返します**。

```bash
ldd /bin/ls | head -1
# linux-vdso.so.1 (0x00007ffd...)
```

ディスク上に存在しないのに `ldd` に出てくるのは、これがカーネル由来だからです。

結果として、`clock_gettime` は数十ナノ秒で返ります。システムコールとして呼ぶより 10 倍近く速いことになります。

## 観察する

```bash
strace ./a.out                      # 全システムコールを表示
strace -c ./a.out                   # 回数と時間を集計
strace -f -e trace=openat ./a.out   # 特定のものだけ（子プロセスも追う）
strace -p 1234                      # 実行中のプロセスに接続
```

`strace -c` の出力は、最適化の出発点として非常に有用です。

```
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 45.23    0.004521           4      1024           read
 30.11    0.003010           3       892           write
```

`read` が 1024 回も呼ばれているなら、バッファサイズを見直す余地があります。

macOS では `dtruss`（SIP の無効化が必要）、Windows では Process Monitor が同等です。

<Callout type="tip" title="strace は遅い">
  `strace` は `ptrace` を使っており、**システムコールごとに 2 回の停止が発生します**。
  対象は数十倍遅くなります。タイミングに依存する問題の調査には向きません。
  オーバーヘッドの小さい観測が必要なら、eBPF ベースの道具（`bpftrace`、`perf trace`）を使います。
</Callout>

## 制限する

プログラムが呼べるシステムコールを制限できます。**seccomp** です。

```c
// この時点以降、read / write / exit / sigreturn 以外を呼ぶと即座に殺される
prctl(PR_SET_SECCOMP, SECCOMP_MODE_STRICT);
```

より柔軟な **seccomp-bpf** では、番号や引数の値に応じてフィルタを書けます。

これは**攻撃面を減らす**ための仕組みです。脆弱性を突かれてコードを実行されても、`execve` が禁止されていればシェルを起動できません。

Docker、Chrome のサンドボックス、systemd のサービス制限（`SystemCallFilter=`）などで使われています。

## システムコールの数

Linux には 300 以上のシステムコールがあります。よく使うものはごく一部です。

| 分類 | 例 |
| --- | --- |
| ファイル | `open`, `read`, `write`, `close`, `lseek`, `stat` |
| プロセス | `fork`, `execve`, `exit`, `wait4`, `kill` |
| メモリ | `mmap`, `munmap`, `brk`, `mprotect` |
| ネットワーク | `socket`, `bind`, `listen`, `accept`, `connect` |
| 同期 | `futex` |
| 多重化 | `select`, `poll`, `epoll_wait` |

```bash
cat /usr/include/asm/unistd_64.h      # 番号の一覧
man 2 syscalls                        # 全体の説明
```

## io_uring

システムコールのコストを根本的に減らす新しい方式が **io_uring** です。

ユーザ空間とカーネルの間に**共有のリングバッファ**を置き、そこにリクエストを書き込むだけで I/O を依頼します。**システムコールを呼ばずに**複数の I/O を投入でき、完了も同じリングから受け取ります。

高負荷の I/O 処理で、従来方式より大幅な性能向上が得られます。一方で、実装が複雑で脆弱性も複数報告されており、環境によっては無効化されています。

## まとめ

- システムコールは、ユーザ空間からカーネルに入る唯一の入口
- 飛び先はカーネルが固定している。だから安全
- カーネルは引数、特にポインタを必ず検証する
- libc は薄いラッパ。`printf` はさらにバッファリングを挟む
- コストは関数呼び出しの 100 倍以上。回数を減らすのが最適化の基本
- vDSO は、カーネルに入らずに済ませる仕組み
- `strace -c` で回数と時間を集計できる
- seccomp で呼べるシステムコールを制限し、攻撃面を減らせる
