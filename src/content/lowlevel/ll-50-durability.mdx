## 「保存しました」はどこまでか

第 48 回で、`write` が返ってもディスクに書かれたとは限らない、だから `fsync` が要る、と書きました。この回ではもう一段掘ります。

データがプログラムから媒体に届くまでには、少なくとも 4 つの段があります。

```
  ┌─────────────────────────┐
  │ ① アプリのバッファ         │  printf、BufferedWriter、Python の file オブジェクト
  └───────────┬─────────────┘
              │ fflush / flush                   ← ここまではプロセスのメモリ
  ┌───────────┴─────────────┐
  │ ② ページキャッシュ          │  カーネルのメモリ（第 48 回）
  └───────────┬─────────────┘
              │ fsync / fdatasync / 時間が経つと自動で
  ┌───────────┴─────────────┐
  │ ③ デバイスの書き込みキャッシュ │  SSD や HDD の中の DRAM
  └───────────┬─────────────┘
              │ フラッシュ命令 / FUA
  ┌───────────┴─────────────┐
  │ ④ 媒体                   │  NAND や磁気ディスク。ここで初めて電源断に耐える
  └─────────────────────────┘
```

それぞれの段で、失われる条件が違います。

| データがいる場所 | プロセスが落ちると | OS が落ちると | 電源が落ちると |
| --- | --- | --- | --- |
| ① アプリのバッファ | **消える** | 消える | 消える |
| ② ページキャッシュ | 残る | **消える** | 消える |
| ③ デバイスのキャッシュ | 残る | 残る | **消える**（電源保護が無ければ） |
| ④ 媒体 | 残る | 残る | 残る |

「保存しました」と表示してよいのは、**想定する故障に対して、データが十分下の段まで届いたとき**です。

## ① と ② の境目: flush は fsync ではない

言語の標準ライブラリは、`write` を毎回呼ぶと遅いので、プロセスの中にバッファを持ちます。`flush` はこのバッファを `write` で吐き出すだけで、**② のページキャッシュに入れたところで終わります**。

```python
f = open("data", "w")
f.write("important")
f.flush()               # ② まで。OS が落ちれば消える
os.fsync(f.fileno())    # ③ を越えて ④ まで（後述の条件付き）
```

プロセスが `kill -9` で落ちても ② にあるデータは残ります。カーネルがいずれ書き出すからです。守りたいのが「プロセスのクラッシュ」だけなら `flush` で足り、「OS のクラッシュや電源断」なら `fsync` が要る。**何から守るのかで、呼ぶべきものが変わります。**

## ② はいつ書き出されるのか

`fsync` を呼ばなかったデータも、放っておけばいずれディスクに書かれます。その「いずれ」は、カーネルのパラメータで決まっています。

```
$ cat /proc/sys/vm/dirty_expire_centisecs
3000
$ cat /proc/sys/vm/dirty_writeback_centisecs
1500
$ cat /proc/sys/vm/dirty_background_ratio /proc/sys/vm/dirty_ratio
10
20
```

| パラメータ | 既定値 | 意味 |
| --- | --- | --- |
| `dirty_expire_centisecs` | 3000（30 秒） | これより古いダーティページは書き出しの対象になる |
| `dirty_writeback_centisecs` | 1500（15 秒） | 書き出しのスレッドが起きる間隔 |
| `dirty_background_ratio` | 10% | ダーティページがこれを超えると、裏で書き出しを始める |
| `dirty_ratio` | 20% | これを超えると、**`write` を呼んだプロセス自身が書き出しを待たされる** |

つまり、`fsync` しないデータは、**OS が落ちると最大で数十秒ぶん失われうる** ということです。

<Callout type="warn" title="write が突然遅くなる">
  普段は一瞬で返る `write` が、大量に書いている最中に急に数百ミリ秒止まることがあります。
  ダーティページが `dirty_ratio` に達し、書いたプロセスが書き出しに付き合わされているのが典型的な原因です。
  `/proc/meminfo` の `Dirty` と `Writeback` を見ると、溜まり具合が分かります。
</Callout>

## fsync、fdatasync、O_SYNC

② から下へ押し出す方法は、いくつかあります。

| 方法 | 何を書き出すか | 使いどころ |
| --- | --- | --- |
| `fsync(fd)` | データと、inode の情報（大きさ、時刻など）すべて | 基本 |
| `fdatasync(fd)` | データと、**読み出しに必要な** inode の情報だけ | 更新時刻の書き込みを省きたいとき |
| `open` に `O_SYNC` | 毎回の `write` が `fsync` 相当になる | ログのように書くたびに確定させたいとき |
| `open` に `O_DSYNC` | 毎回の `write` が `fdatasync` 相当になる | 同上で、少し軽く |

`fdatasync` が省けるのは、たとえば最終更新時刻です。ファイルの大きさが変わった場合は、それが無いと読み戻せないので書き出されます。データベースが追記しないように事前に領域を確保しておくのは、**大きさを変えずに書けば、`fdatasync` が inode に触らずに済む** からでもあります。

なお、Linux の `sync_file_range` は名前から永続化の道具に見えますが、メタデータを書かず、デバイスのキャッシュも空にしないため、それだけでは永続性を保証しません（[man7: sync_file_range(2)](https://man7.org/linux/man-pages/man2/sync_file_range.2.html)）。

## ③ デバイスも嘘をつく

`fsync` がページキャッシュを書き出しても、データはまだ **③ デバイスの中の DRAM** にいるかもしれません。SSD も HDD も、書き込みを速く返すために内部にキャッシュを持っています。

```
$ cat /sys/block/*/queue/write_cache
write back        ← デバイスが揮発性のキャッシュを持っている
write through     ← 持っていない、または無効
```

`write back` のデバイスに対しては、Linux の `fsync` は、データを送ったあとに **キャッシュを媒体に書き出せ** という命令（フラッシュ）を出すか、書き込み自体に **キャッシュを素通りさせる** 印（FUA、Force Unit Access）を付けます。これで ④ まで届きます。

逆に、電源が落ちてもキャッシュの中身を書き切るだけのコンデンサを積んだ SSD（**電源喪失保護**、PLP）は、キャッシュにあるデータを失わないと保証できるので、フラッシュの命令をすぐに完了できます。データセンター向けの SSD が `fsync` で速いのはこのためです。

<Callout type="warn" title="macOS の fsync はデバイスのキャッシュを空にしない">
  macOS の `fsync` は、データをホストからドライブへ送るところまでしか保証しません。
  ドライブの中のキャッシュまで書き出させるには、`fcntl(fd, F_FULLFSYNC)` を使います
  （[Apple: fsync(2)](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/fsync.2.html)）。
  はるかに遅いのですが、データベースのように書き込み順序を厳密に守りたいものは、こちらを使う必要があります。
  **同じ `fsync` という名前でも、OS によって届く段が違います。**
</Callout>

## 途中まで書かれる

ここまでは「届いたか、届いていないか」の話でした。実際にはもう 1 つ、**半分だけ届く** という状態があります。

ディスクが原子的に書けるのは、多くの場合 **セクタ**（論理ブロック。512 バイトや 4KB）単位です。

```
$ cat /sys/block/*/queue/logical_block_size
512
```

一方、ファイルシステムのブロックは 4KB、PostgreSQL のページは 8KB です。8KB のページを書いている途中で電源が落ちると、**前半は新しく、後半は古い** ページがディスクに残りえます。これを **torn write**（ちぎれた書き込み）と呼びます。

```
書こうとしたページ:   [ 新 新 新 新 | 新 新 新 新 ]
ディスクに残ったもの:  [ 新 新 新 新 | 古 古 古 古 ]   どちらの版でもない
```

PostgreSQL は、チェックポイントの後にページを初めて変更するとき、**ページ全体の写しを WAL に書いておく** ことで対処しています（`full_page_writes`）。ページがちぎれても、写しから丸ごと復元できます（[PostgreSQL Wiki: Full page writes](https://wiki.postgresql.org/wiki/Full_page_writes)）。

追記型のログなら、各レコードに **長さとチェックサム** を付けるのが定石です。クラッシュ後に読み直し、チェックサムが合わない末尾は「書きかけ」として捨てます。

## 順序は保証されない

もう 1 つの落とし穴が、**書いた順に届くとは限らない** ことです。

ページキャッシュは、ダーティページを都合のよい順に書き出します。デバイスも、内部で並べ替えます。`fsync` を挟まずに A、B の順で書いても、電源断のあとに **B だけがディスクにある** 状態がありえます。

### ext4 の空ファイル事件

これが大規模に表面化したのが、2009 年の ext4 です。多くのアプリケーションは、設定ファイルを次のように置き換えていました。

```c
fd = open("config.new", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write(fd, buf, len);
close(fd);                       // fsync していない
rename("config.new", "config");
```

ext4 は **遅延割り当て**（書き出す直前までブロックの場所を決めない）を採用していたため、`rename` によるディレクトリの書き換えが先にディスクに届き、データの書き出しはまだ、という状態が長く続きました。その間にクラッシュすると、**`config` が 0 バイトのファイルになる** という事故が多発しました（[LWN: Ts'o: Delayed allocation and the zero-length file problem](https://lwn.net/Articles/323169/)）。

ext4 は、`rename` で既存のファイルを置き換える形や、`O_TRUNC` で開いたファイルを閉じる形を検出したら、データを先に書き出す `auto_da_alloc` という救済を入れました（[man7: ext4(5)](https://man7.org/linux/man-pages/man5/ext4.5.html)）。ただしこれは **壊れたアプリケーションのための特別扱い** であり、他のファイルシステムでも同じ保証があるわけではありません。

### 正しい置き換え方

順序を保証する道具は、`fsync` しかありません。**`fsync` は「ここより前の書き込みが届くまで先に進まない」という壁** として使います。

```c
fd = open("config.tmp", O_WRONLY | O_CREAT | O_TRUNC, 0644);
write(fd, buf, len);
fsync(fd);                       // 1. 中身を先に確定させる
close(fd);
rename("config.tmp", "config");  // 2. 名前を付け替える（原子的、第 49 回）
dfd = open(".", O_RDONLY | O_DIRECTORY);
fsync(dfd);                      // 3. 付け替えたディレクトリを確定させる（第 48 回）
```

1 が無ければ、空ファイルの事件が起きます。3 が無ければ、電源断のあとに古い名前に戻っているかもしれません。**クラッシュの後に見えるのは、古いファイルか新しいファイルのどちらか** という保証は、この 3 手が揃って初めて成り立ちます。

<Callout type="tip" title="言語のライブラリが隠していること">
  Python の `os.replace` や Go の `os.Rename` は、2 の `rename` だけです。
  1 と 3 は自分で書く必要があります。
  「設定を安全に保存する」関数を用意しているライブラリは、中でこの 3 手をやっています。
</Callout>

## fsync が失敗したら

第 48 回で、fsyncgate に触れました。`fsync` がエラーを返したとき、Linux はそのページのダーティの印を消してしまうので、**もう一度 `fsync` しても成功が返り、データは失われたまま** になる、という問題です。

その後、2 つの変化がありました。

**カーネル側。** Linux 4.13 で `errseq_t` という仕組みが入り、書き出しのエラーが、そのファイルを開いている **すべての fd の `fsync`** に報告されるようになりました（[LWN: fs: introduce new writeback error reporting](https://lwn.net/Articles/724232/)）。以前は、先に `fsync` を呼んだ誰か 1 人だけがエラーを受け取り、他の fd では見逃されることがありました。ただし、失敗したページを再試行してくれるわけではありません。

**データベース側。** PostgreSQL は、`fsync` の失敗を再試行するのをやめ、**即座に PANIC で停止し、再起動時に WAL から復元する** ようにしました。2019 年 2 月の 11.2、10.7 などに入っています（[PostgreSQL 11.2 等のリリース告知](https://www.postgresql.org/about/news/postgresql-112-107-9612-9516-and-9421-released-1920/)）。

教訓は、**`fsync` の失敗は回復可能なエラーではない** ということです。そのデータは失われたものとして扱い、確実に残っている別の記録（ログ）から作り直す。そのために、第 51 回で見るジャーナルや、第 66 回で見るデータベースの WAL が存在します。

## まとめ

- データは、アプリのバッファ、ページキャッシュ、デバイスのキャッシュ、媒体の 4 段を通る。どの故障から守るかで、必要な段が決まる
- `flush` はページキャッシュまで。OS の停止や電源断から守るには `fsync` が要る
- `fsync` しないデータは、既定で最大数十秒ぶんページキャッシュに留まる。溜まりすぎると `write` が止まる
- `fdatasync` は読み出しに不要なメタデータを省く。`sync_file_range` は永続化の保証にならない
- デバイスにも揮発性のキャッシュがある。Linux の `fsync` はフラッシュや FUA で越えるが、macOS では `F_FULLFSYNC` が要る
- 原子的に書けるのはセクタ単位。それより大きいページは途中でちぎれうる
- 書いた順に届く保証はない。`fsync` を壁として使い、「書く → fsync → rename → ディレクトリを fsync」で置き換える
- `fsync` の失敗は再試行で直らない。ログから作り直す前提で設計する

次は、ファイルシステム自身が、書き込みの途中で電源が落ちても壊れないための仕組みを見ます。
