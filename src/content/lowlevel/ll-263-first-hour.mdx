## 速くする前にすること

第 261 回で何を最大にするのかを、第 262 回で負荷をかける側がどう振る舞うのかを見ました。ここからは、実際にサーバーの前に座ったときの話です。

競技が始まると、参加者の手元にあるのは、起動しているサーバーが数台と、マニュアルと、ベンチマーカーを走らせるボタンだけです。アプリケーションのコードはサーバーの上にあり、nginx や MySQL の設定はサーバーの `/etc` の下にあります。何がどこにあり、何を変えたら何が変わるのかは、まだ分かりません。

この状態で、いきなりインデックスを張り始めることもできます。けれど上位のチームは、最初の 1 時間近くを**改善のための足場づくり**に使います。この回の問いは、**その 1 時間で何を作り、何を確かめておくのか**です。

| 作るもの・確かめるもの | 目的 |
| --- | --- |
| コードと設定をリポジトリに取り込む | 何を変えたのかを、後から必ずたどれるようにする |
| 1 つのコマンドで配る | 変更を試す手間と、手で配るときの間違いをなくす |
| 実際に効いている値を確かめる | 「変えたつもり」で測り続ける事故を防ぐ |
| 初回の点数と、そのばらつきを記録する | 後の変更が効いたのかを判断する基準を持つ |
| マニュアルとコードを読む | 点数の定義、猶予、禁止事項を把握する |

## 上位チームの初動

まず、上位のチームが最初の 1 時間をどう使っているかを見ます。

ISUCON12 と ISUCON13 で優勝した NaruseJun は、初動の分担がほぼ決まっていると話しています（[gihyo.jp のインタビュー](https://gihyo.jp/article/2022/10/isucon12-champinterview-narusejun)）。

> この3人になってからは、初動に関しては、私がドキュメントの読解、takashiがリポジトリの準備・チェック、nginxの設定確認など、sekaiさんはAnsibleの設定および各種計測ツールの準備、という形でほぼ決まっていますね。

ISUCON13 の参加記では、この分担で「大体10時40分くらいには、実際の改善が開始できるような状態になっていました」と書かれています（[ISUCON13で優勝しました(チーム NaruseJun)](https://zenn.dev/tohutohu/articles/923bdf5dcd73af)）。競技開始は 10 時なので、足場づくりに 40 分を使っていることになります。11 時の時点のスコアは 5,261 で、最終スコアは 468,006 でした。

ISUCON11 予選を 1 位で通過した shallowverse の記録では、10 時から 11 時の欄に「全員でマニュアルを音読しつつ，Ansibleでサーバ側の基本的な設定をしました．」とあり、初期スコアは 3,200 点でした（[ISUCON11予選を1位通過した](https://www.y1r.org/posts/20210831-isucon11-qualify)）。

ISUCON11 本選で優勝した fujiwara組は、役割をもう少し長い時間で分けています。fujiwara 氏がインフラの初期設定、モニタリング、複数台構成などの「足回りを整備」し、その間にほかの 2 人が大きめのアプリケーションの改造に取りかかる、という方針でした（[ISUCON11で優勝しました](https://sfujiwara.hatenablog.com/entry/isucon11-final)）。

細部は違いますが、共通しているのは次の 3 つの仕事を**並行して**進めていることです。

| 仕事 | 中身 |
| --- | --- |
| 取り込みと配る仕組み | サーバーのコードと設定をリポジトリに入れ、配るコマンドを用意する |
| 計測の準備 | アクセスログ、スロークエリログ、プロファイラを有効にし、結果を集める（第 263〜265 回） |
| 読解 | マニュアルとアプリケーションのコードを読み、点数の定義と制約を把握する |

1 人のチームなら、これを順番にこなすことになります。どの順でも、この 3 つが揃うまでは、改善の結果を正しく判断できません。

## リポジトリに何を入れるか

最初の仕事は、サーバーの上にあるものをリポジトリに取り込むことです。NaruseJun の ISUCON13 のリポジトリについて、参加記は次のように説明しています（[ISUCON13で優勝しました(チーム NaruseJun)](https://zenn.dev/tohutohu/articles/923bdf5dcd73af)）。

> リポジトリにはGoのアプリケーションコードと全言語共通のあれこれと環境変数のenv.sh及びミドルウェアの設定を入れています。

そして「ミドルウェアの設定変更もリポジトリのコードを変更しデプロイすることで反映しています」。サーバーに直接ログインして `/etc/nginx/nginx.conf` を書き換えることはしない、ということです。

取り込む対象を、一般的な Web アプリケーションのサーバーで整理すると次のようになります。

| 対象 | 典型的な場所（Ubuntu の場合） | 取り込む理由 |
| --- | --- | --- |
| アプリケーションのコード | ホームディレクトリの下 | 改善の大半はここで行う |
| 環境変数 | `env.sh` など、systemd の unit が読むファイル | データベースの接続先、台数を増やすときの切り替え |
| systemd の unit | `/etc/systemd/system/` | 起動の方法、再起動時の挙動、ファイルディスクリプタの上限 |
| nginx の設定 | `/etc/nginx/` | ログの形式、静的ファイルの配信、上流との接続 |
| MySQL の設定 | `/etc/mysql/` | スロークエリログ、バッファの大きさ |
| カーネルのパラメータ | `/etc/sysctl.d/` | 接続の待ち行列、ポートの範囲 |
| データベースのスキーマ | 初期化のスクリプトや SQL ファイル | インデックスの追加はここに書く |

ISUCON14 の講評によれば、この回の `POST /api/initialize` はテーブルを作り直す方式で、講評は「`webapp/sql/1-schema.sql` の末尾に以下のように追記をしてインデックスを貼ることで」と、インデックスの追加先をスキーマのファイルとして示しています（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。データベースに直接 `ALTER TABLE` を打つと、次の初期化で消えてしまう回もあるのです。

### 手元で動かさない、という選択

NaruseJun は、手元に開発環境を作らないと書いています。

> ただし、手元でコードのビルドを行ったりローカルの開発環境を準備することはせず、基本的にベンチマークによって動作確認などは行っています。

ビルドできない書き間違いも「デプロイ時に発覚する感じ」だそうです。8 時間の競技では、手元の環境を本番と同じにする手間より、配って試す手間を小さくする方が得だという判断です。その前提として、**配る操作が 1 つのコマンドで、速く、失敗しにくい**ことが必要になります。

## 1 つのコマンドで配る

配る仕組みは、チームごとに形は違っても中身はほぼ同じです。

shallowverse は「お手製deploy script」として、「git pull して systemctl restart ... をコマンド一発でやります．」と書き、「nginxのアクセスログの削除も併せて行っています．」と続けています。NaruseJun は、`make deploy` で既定のブランチを、`make deploy BRANCH=hoge` でブランチを指定して配れるようにしています。そして「ブランチをデプロイして計測したあとにmasterへのマージを行い」ます。

配るコマンドがやることを整理すると、次のようになります。

1. 配る版を決める（ブランチ、コミット）
2. コードをビルドする
3. 設定ファイルを所定の場所へ置く
4. 設定の文法を確かめる（`nginx -t` など）
5. サービスを再起動する
6. ログを空にする（前の計測の結果と混ざらないように）
7. **実際に効いている値を表示する**

7 番目は見落とされがちですが、この回の実測で最も役に立ったのはこれでした。

## 実測：取り込んで、配って、確かめる

手元の Docker で MySQL と nginx を 1 つずつ動かし、競技のサーバーに見立てて、取り込みから配るまでを組みました。本物のサーバーでは `sudo cp` と `systemctl restart` に当たる操作を、ここでは `docker cp` と `docker restart` で代用しています。

環境は Apple M1 Pro / macOS 26.2、Docker 29.4.0、イメージは `mysql:8.4`（MySQL 8.4.13）と `nginx:latest`（nginx 1.31.8）です。

### 取り込む

まず、動いているサーバーから設定をそのままコピーして、最初のコミットにします。

```bash
docker cp tune-262-mysql:/etc/mysql/conf.d mysql/
docker cp tune-262-nginx:/etc/nginx/nginx.conf nginx/
docker cp tune-262-nginx:/etc/nginx/conf.d nginx/
git init -b main && git add -A && git commit -m "サーバーの設定をそのまま取り込む"
```

```text
$ git ls-files
deploy.sh
nginx/conf.d/default.conf
nginx/nginx.conf
```

`mysql/conf.d` は空のディレクトリだったので、Git には何も入りませんでした。MySQL の設定は、このイメージでは `/etc/my.cnf` にあります。**取り込んだつもりのディレクトリが空だった、ということ自体が一つの情報**です。どのファイルが実際に読まれているのかを、この時点で確かめておくべきでした。

### 配って、確かめる

次に、スロークエリログをすべてのクエリについて取る設定（第 265 回で使います）と、nginx のアクセスログを JSON で出す設定（第 264 回で使います）を足しました。MySQL の設定は、Ubuntu の MySQL パッケージで使われる `mysql.conf.d` というディレクトリに置きました。ISUCON のサーバーは Ubuntu なので、その習慣のとおりです。

```ini
# mysql/mysql.conf.d/isucon.cnf
[mysqld]
slow_query_log      = 1
slow_query_log_file = /var/lib/mysql/slow.log
long_query_time     = 0
```

配るスクリプトの最後には、MySQL と nginx に「いま何が効いているか」を問い合わせる行を入れてあります。

```bash
echo "--- 実際に効いている値"
docker exec tune-262-mysql mysql -uroot -proot -N -e \
  "SELECT @@slow_query_log, @@long_query_time, @@slow_query_log_file"
docker exec tune-262-nginx nginx -T | grep -E '^\s*(log_format|access_log)'
```

配った結果です。

```text
$ time ./deploy.sh
deploy 7cf51e2 (main)
2026/11/12 00:52:18 [notice] 46#46: signal process started
mysqld is alive
--- 実際に効いている値
0	10.000000	/var/lib/mysql/35524935fa37-slow.log
    log_format  main  '$remote_addr - $remote_user [$time_local] "$request" '
    log_format json escape=json '{"time":"$time_iso8601","method":"$request_method","uri":"$request_uri",'
    access_log  /var/log/nginx/access.json  json;
./deploy.sh  0.37s user 0.29s system 6% cpu 9.417 total
```

nginx は新しい形式でログを書くようになりました。一方、MySQL の `slow_query_log` は 0、`long_query_time` は既定の 10 秒のままです。ファイルは置かれ、再起動もしたのに、**設定は効いていません**。

理由は、MySQL がどのファイルを読むかにあります。`mysqld --verbose --help` は、読む設定ファイルの順番を表示します。

```text
$ mysqld --verbose --help | grep -A1 "Default options are read"
Default options are read from the following files in the given order:
/etc/my.cnf /etc/mysql/my.cnf /usr/etc/my.cnf ~/.my.cnf
```

このイメージの `/etc/my.cnf` の最後は `!includedir /etc/mysql/conf.d/` で、`/etc/mysql/mysql.conf.d/` はどこからも読み込まれていませんでした。`my_print_defaults mysqld` は、設定ファイルを読んだ結果として `mysqld` に渡る引数を並べるので、ここに自分の設定が出てこなければ、そのファイルは読まれていません。

```text
$ my_print_defaults mysqld
--host-cache-size=0
--skip-name-resolve
--datadir=/var/lib/mysql
--socket=/var/run/mysqld/mysqld.sock
--secure-file-priv=/var/lib/mysql-files
--user=mysql
--pid-file=/var/run/mysqld/mysqld.pid
```

ファイルを `conf.d` に移して配り直すと、値が変わりました。

```text
$ time ./deploy.sh
deploy 545819d (main)
mysqld is alive
--- 実際に効いている値
1	0.000000	/var/lib/mysql/slow.log
    ...
./deploy.sh  0.31s user 0.25s system 9% cpu 6.108 total

$ my_print_defaults mysqld | tail -3
--slow_query_log=1
--slow_query_log_file=/var/lib/mysql/slow.log
--long_query_time=0
```

nginx に 2 件の要求を送り、MySQL に 1 つクエリを投げて、ログが期待どおりに出ていることも確かめました。

```text
{"time":"2026-11-12T00:52:48+00:00","method":"GET","uri":"/","status":200,"body_bytes":896,"reqtime":0.000}
{"time":"2026-11-12T00:52:48+00:00","method":"GET","uri":"/nothing","status":404,"body_bytes":153,"reqtime":0.000}
```

もし最後の確認の行がなければ、スロークエリログが空のまま「スロークエリは無い」と判断したり、既定の 10 秒より遅いクエリだけを見て「データベースは問題ない」と結論したりしていたかもしれません。

<Callout type="tip" title="効いている値を、どこから来たかと一緒に見る">
  MySQL 8.0 以降の `performance_schema.variables_info` には、変数の値がどこから設定されたかが入っています。文書は `VARIABLE_PATH` を「If the variable was set from an option file, VARIABLE_PATH is the path name of that file. Otherwise, the value is the empty string.」と説明しています（[MySQL 8.4 Reference Manual: The variables_info Table](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-variables-info-table.html)）。
  nginx の `nginx -T` は、`-t` と同じく設定を検査したうえで、「additionally dump configuration files to standard output」、つまり読み込んだ設定ファイルをすべて書き出します（[nginx: Command-line parameters](https://nginx.org/en/docs/switches.html)）。`include` で読まれていないファイルは、ここに出てきません。
  どちらも、「置いたファイル」ではなく「読まれた結果」を見る方法です。
</Callout>

### ブランチを配って戻す

配るスクリプトを、指定した版を `git archive` で一時ディレクトリに取り出してから配る形にし、確認の行も `variables_info` から値の出どころを出すように変えました。そのうえで、`innodb_buffer_pool_size` を 256 MB にする設定ファイル `buffer.cnf` を足したブランチを作り、ブランチを配ってから既定のブランチに戻す、という操作を試しました。

最初の版のスクリプトは、リポジトリにあるファイルをサーバーへ**コピーするだけ**でした。その動きを `CLEAN=0` として残し、次の順で配りました。

```text
### 1  既定のブランチを配る
deploy a42a65d (main) clean=1
innodb_buffer_pool_size	134217728
long_query_time	0.000000	/etc/mysql/conf.d/isucon.cnf
slow_query_log	ON	/etc/mysql/conf.d/isucon.cnf

### 2  ブランチを配る（コピーするだけ）
deploy 167b9d6 (try-buffer-pool) clean=0
innodb_buffer_pool_size	268435456	/etc/mysql/conf.d/buffer.cnf

### 3  既定のブランチに戻す（コピーするだけ）
deploy a42a65d (main) clean=0
innodb_buffer_pool_size	268435456	/etc/mysql/conf.d/buffer.cnf
$ ls /etc/mysql/conf.d
buffer.cnf
isucon.cnf

### 4  既定のブランチに戻す（配る前に conf.d を空にする）
deploy a42a65d (main) clean=1
innodb_buffer_pool_size	134217728
$ ls /etc/mysql/conf.d
isucon.cnf
```

3 番目で、既定のブランチに戻したのに、バッファプールは 256 MB のままでした。既定のブランチには `buffer.cnf` が無いので、コピーされるファイルもありません。けれど、ブランチを配ったときにサーバーへ置かれた `buffer.cnf` は、誰も消さないので残り続けます。`VARIABLE_PATH` が、その残ったファイルを指しています。

これは、**リポジトリから消したファイルが、サーバーからは消えない**という問題です。コピーで配る仕組みは、足すことしかできません。4 番目のように、配る先のディレクトリをリポジトリと同じ中身に揃える（先に空にしてから置く、`rsync --delete` を使う、など）必要があります。

この問題は、ブランチを何本も試してから戻すとき、つまり競技の後半で効いてきます。「元に戻したのに点数が戻らない」「再起動したら挙動が変わった」という形で現れ、原因を探すのに時間がかかります。

### 配るのにかかる時間

配るスクリプトの実行時間は、1 回目の確認で 9.4 秒、2 回目で 6.1 秒でした。ほとんどは MySQL の再起動を待つ時間です。マシンがほかの処理で特に混んでいた時間帯には、同じスクリプトが 35.6 秒かかりました。

8 時間の競技で 1 回の変更ごとに配って測るなら、配る時間はそのまま回数に効きます。設定を変えていないときは MySQL を再起動しない、変更のあったサービスだけを再起動する、といった工夫は、ここで回収できます。ただし、再起動を省くことは「再起動しても同じように動くか」を確かめる機会を減らすことでもあります。その確認は第 279 回の再起動試験で改めて行います。

## 初回の点数を記録する

足場ができたら、何も変えずにベンチマーカーを走らせ、点数を記録します。これが後のすべての変更の基準になります。

記録するのは点数だけではありません。どの版で走らせたのか（コミット）、ベンチマーカーのログ、アクセスログとスロークエリログとプロファイルの結果を、まとめて残します。NaruseJun は、そのための道具 pprotein を作って使っていて、参加記では「/initialize の最後にフックを挟むことで自動で計測を開始し、Web上からpprof,alp,slpの結果をインタラクティブに見ることのできるツールです」と説明しています（[ISUCON13で優勝しました(チーム NaruseJun)](https://zenn.dev/tohutohu/articles/923bdf5dcd73af)）。ベンチマーカーは走るたびに必ず初期化を呼ぶので、そこを合図にすれば、計測の開始を忘れることがありません。この仕組みは第 266 回で扱います。

### 何もしなくても、点数は揺れる

初回の点数を 1 回だけ取って基準にすると、後の判断を誤ることがあります。同じ版でも、走らせるたびに点数は変わるからです。

第 261 回の実験の店で、何も変えずに 15 秒の負荷走行を 9 回繰り返しました。

```text
requests=1353 (90 req/s) errors=0 purchases=351 revenue=35100 score=35100 PASS
requests=1358 (91 req/s) errors=0 purchases=351 revenue=35100 score=35100 PASS
requests=1313 (88 req/s) errors=0 purchases=338 revenue=33800 score=33800 PASS
requests=1342 (89 req/s) errors=0 purchases=346 revenue=34600 score=34600 PASS
requests=1348 (90 req/s) errors=0 purchases=351 revenue=35100 score=35100 PASS
requests=1348 (90 req/s) errors=0 purchases=348 revenue=34800 score=34800 PASS
requests=1355 (90 req/s) errors=0 purchases=352 revenue=35200 score=35200 PASS
requests=1349 (90 req/s) errors=0 purchases=351 revenue=35100 score=35100 PASS
requests=1328 (89 req/s) errors=0 purchases=344 revenue=34400 score=34400 PASS
```

最小 33,800、最大 35,200、中央値 35,100 です。幅は中央値の約 4% あります。計測した時間帯はロードアベレージが 60〜140 と非常に高く、ほかの処理の影響を受けやすい状態でした。この条件では、**4% 未満の差は、1 回ずつの比較では変更の効果と見分けられません**。

ISUCON の作問者も、点数のばらつきを気にかけています。ISUCON9 予選の講評は「分析や実装に多くの時間が使えるようベンチマーク試行によってスコアがバラつかないよう安定させることも意識しておりました」と書いています（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。一方、ISUCON14 では初期実装のマッチングがランダムだったため、講評によれば「ランダム性を除いたマッチングアルゴリズムに変更すると、それまでかなりぶれていたベンチマークスコアもかなり安定したのではないでしょうか」（[ISUCON14 問題の解説と講評](https://isucon.net/archives/58869617.html)）。アプリケーションの作りそのものが、点数のばらつきの原因になることもあるのです。

初回のベンチマークは、可能なら 2〜3 回走らせて、ばらつきの幅を知っておくのが安全です。その幅より小さな改善は、何度か走らせて傾向を見るか、点数ではなくアクセスログやプロファイルの数字で効果を確かめます。

### 1 回に 1 つずつ変える

ばらつきを知っていても、一度にいくつもの変更を入れると、どれが効いたのか、どれが壊したのかが分からなくなります。shallowverse の記録には、午後に「色々一気にmergeしすぎて，複数台構成に切り替えたあたりでFAILするようになった．」とあり、手で `git bisect` をして原因の変更を探し、戻すまでに約 1 時間を使っています（[ISUCON11予選を1位通過した](https://www.y1r.org/posts/20210831-isucon11-qualify)）。

ブランチ単位で配れるようにしておくのは、変更を 1 つずつ試すためです。1 つ配り、測り、点数と計測結果を記録してからマージする。この手順の手間を小さくするのが、最初の 1 時間で作る足場の役割です。

## マニュアルとコードを読む

足場づくりと並行して、マニュアルを読みます。読む目的は、第 261 回で見た採点の決まりを、その回の問題について具体的に把握することです。

| 読むところ | 例 |
| --- | --- |
| 点数の定義 | ISUCON14 の「移動距離の合計 × 0.1 ＋ 移動距離の合計 ＋ ライド完了数 × 5」 |
| 減点と FAIL の条件 | ISUCON14 の「200件以上のワーニング」、クリティカルエラーの一覧 |
| 反映の猶予 | ISUCON14 の座標は過去 3 秒以内であればよい。ISUCON13 のアイコンのハッシュは更新から 2 秒以内に反映 |
| タイムアウト | 初期化は 30 秒、通知の取得は 60 秒、それ以外は 10 秒（ISUCON14） |
| 変えてはいけないもの | URI、レスポンスの構造、追試で使う設定やポート |
| 負荷を調整する値 | ISUCON9 予選の `campaign`、ISUCON11 予選の `dropProbability`、ISUCON14 の `retry_after_ms` |

反映の猶予は、第 271 回で扱う「許される古さ」の上限そのものです。ISUCON13 の講評も、アイコンのハッシュをキャッシュするなら「iconが更新されてから2秒以内にicon_hashを反映すること」という条件を確認するよう促しています（[ISUCON13 問題の解説と講評](https://isucon.net/archives/58001272.html)）。ISUCON14 の当日マニュアルは、`GET /api/app/nearby-chairs` で返す椅子の座標について「過去3秒以内に `POST /api/chair/coordinate` で送信された座標に一致する必要があります」と定めていました（[ISUCON14 当日マニュアル](https://github.com/isucon/isucon14/blob/main/docs/manual.md)）。この 3 秒が分かっていれば、座標の書き込みをまとめて後回しにできる、という判断が最初から立ちます。

ただし、最初の 1 時間ですべてを理解する必要はありません。shallowverse は、最初の通読で「マニュアルのグラフに関する説明が複雑でよく分からず，結局その部分は読み飛ばしました．」と書いています。そして午後に、点数の付け方を 2 回読み直し、そのたびに方針を変えています。**最初に全体をざっと押さえ、点数が伸び悩んだら点数の節に戻る**、という読み方で十分です。

ISUCON9 予選の講評は、最後の謝辞の中に「マニュアル確認しましょう」という一言を紛れ込ませています（[ISUCON9 予選問題の解説と講評](https://isucon.net/archives/53789931.html)）。読み飛ばした部分に答えが書いてあることは、それだけよくあるということでしょう。

コードを読む担当は、エンドポイントの一覧と、それぞれがどのテーブルに何回問い合わせているかの見当を付けておくと、後で計測の結果を読むときに役立ちます。ただし、ここで直し始めないことです。直す順番は、計測で決めます。

## 事前に用意しておくもの

最初の 1 時間を短くする一番の方法は、競技の前に準備しておくことです。

**チートシート。** NaruseJun は、毎回の経験をチートシートにまとめて更新しています。インタビューでは、その中身を「初動」「改善」「ブラウザチェック確認」の 3 つに分けて書いていると話し、sekai 氏は、チートシートを更新していくにつれて「その時間が短縮され、今は、ほぼすぐに手を動かすところに入れるようになっています」と振り返っています（[gihyo.jp のインタビュー](https://gihyo.jp/article/2022/10/isucon12-champinterview-narusejun)）。

**テンプレートと構成管理。** 配るスクリプト、`Makefile`、計測ツールの導入と設定、カーネルや MySQL の定番の設定を、Ansible などでまとめて流し込めるようにしておきます。shallowverse は、Ansible、配るスクリプト、スロークエリログを一発で有効にするスクリプト、ログの解析結果を Slack に流すスクリプトを事前に用意していて、スロークエリログの設定を一発で行う理由を「本番焦っているときにslowlogの設定をするのはミスりがちなので，あると便利．」と書いています。

**素振り。** 過去の問題を本番と同じ手順で解く練習です。NaruseJun の ISUCON13 の参加記には、本番の 1 週間前に集まって「初動→改善いくつか→再起動試験の手順を確認しました」とあり、そこで出た改善点をテンプレートのリポジトリや pprotein に反映してから当日を迎えています。過去の問題を手元で動かせることが、第 261 回で見た「題材として再現できる」性質の実用面です。

<Callout type="warn" title="計測の道具そのものを守る">
  NaruseJun の ISUCON13 の参加記には、開始前に設定を間違えてチートシートが公開状態になっていて、そこに載っていた計測ツールのドメインを急いで変えた、という話が出てきます。参加記は「来年はTailscaleとかWARPとか使ったほうがいいんでしょうね。」と続けています。
  計測の道具は、アプリケーションの内部（プロファイル、クエリ、URI）を外から見えるようにするものです。本番の環境で同じ道具を使うなら、認証のない管理画面やプロファイラのエンドポイントを公開しないことは、性能の話以前の前提です。
</Callout>

## 本番での最初の 1 時間

競技を離れても、「知らないサービスの性能を見てほしい」と頼まれたときの最初の 1 時間は、ほぼ同じ形になります。

**動いているものと、リポジトリにあるものは一致しているか。** 本番のサーバーで、誰かが手で設定を変えたまま、リポジトリや構成管理に反映していないことはよくあります。実測で見た「リポジトリから消したのにサーバーに残ったファイル」は、その一つの形です。構成管理の道具で差分を確かめる、実際に効いている値（`SHOW VARIABLES`、`nginx -T`、`systemctl cat`、`sysctl -a`）を取り出してリポジトリの値と比べる、といった作業が最初に来ます。

**変更を安全に試して、戻せるか。** 本番では、配るコマンドは CI/CD のパイプラインになり、ブランチ単位の配備はステージング環境やカナリアリリースになります。どの形でも、1 つの変更を配り、測り、だめなら戻せることが前提です。

**基準となる数字はあるか。** 変更の前の応答時間、エラー率、スループット、資源の使用率を、ばらつきの幅とともに把握しておきます。本番の負荷は時間帯や曜日で変わるので、ISUCON よりもばらつきはずっと大きくなります。比べるなら、同じ時間帯どうし、あるいは同時に動く 2 つの版どうしで比べます。

**何が「良くなった」なのかは決まっているか。** 第 261 回で見たとおり、目的関数と制約を先に決めます。マニュアルの代わりに、SLO、ビジネスの指標、仕様書、そして過去の障害の記録を読みます。

## 次の回へ

足場ができたら、計測を始めます。次の第 264 回では、この回で JSON 形式にした nginx のアクセスログを集計し、どのエンドポイントにどれだけの時間がかかっているのかを、URI をまとめる方法とともに見ます。

## まとめ

- 上位チームは最初の 40 分〜1 時間を、取り込みと配る仕組み、計測の準備、マニュアルとコードの読解に使い、それを分担して並行で進める
- アプリケーションのコード、環境変数、systemd の unit、nginx・MySQL・カーネルの設定、スキーマをリポジトリに入れ、設定の変更もリポジトリを変えて配ることで反映する
- 配るコマンドは、版の指定、ビルド、設定の配置、文法の検査、再起動、ログの消去までを 1 回で行い、最後に実際に効いている値を表示させる
- 実測では、Ubuntu の習慣で `mysql.conf.d` に置いた MySQL の設定が、`conf.d` しか読まないイメージでは一切効かなかった。配った後の確認の行で、それがすぐに分かった
- 読まれた結果を見るには、`my_print_defaults`、`mysqld --verbose --help`、`performance_schema.variables_info` の `VARIABLE_PATH`、`nginx -T` を使う
- コピーするだけの配り方は、リポジトリから消したファイルをサーバーから消さない。ブランチを配ってから戻すと、ブランチの設定が残り続けた。配る先をリポジトリと同じ中身に揃える
- 何も変えずに 9 回走らせた点数は 33,800〜35,200 で、幅は約 4% だった。ばらつきの幅より小さな改善は、1 回ずつの比較では判断できない
- 一度に多くの変更を入れると、FAIL の原因を探すのに時間を取られる。ブランチ単位で配り、1 つずつ測ってからマージする
- マニュアルからは、点数の定義、減点と FAIL、反映の猶予、タイムアウト、変えてはいけないもの、負荷を調整する値を拾う。全部を最初に理解する必要はなく、伸び悩んだら点数の節に戻る
- チートシート、テンプレート、構成管理、過去の問題での素振りが、最初の 1 時間を短くする
- 本番でも、動いているものとリポジトリの一致、安全に試して戻せる仕組み、ばらつきを含めた基準の数字、目的関数の確認が、最初の 1 時間の仕事になる
