## 同じプロセスの中に、別の言語を呼び込む

Python から画像処理ライブラリを呼ぶ。Go から暗号ライブラリを呼ぶ。Node.js からデータベースのクライアントを呼ぶ。

いずれも、**その言語では書かれていないコードを、同じプロセスの中で実行しています**。この仕組みを **FFI**（Foreign Function Interface）と呼びます。

理由は 3 つあります。

- **既存の資産を使いたい**。数十年かけて枯れた C のライブラリを、書き直したくない
- **速度が要る**。数値計算、暗号、圧縮、動画のデコード
- **OS の機能に触りたい**。システムコールのラッパは C で提供されている

<Callout type="note" title="別プロセスで動かすのとは違う">
  HTTP や gRPC で別プロセスに投げるのも「別の言語の機能を使う」ことですが、
  **FFI は同じプロセスの中**です。

  だから速い。関数呼び出しとほぼ同じコストで済みます。
  そして、**だから危険**でもあります。相手が壊れると、自分も一緒に落ちます。
</Callout>

## なぜ C ABI が共通語なのか

Python から Rust を呼ぶとき、Go から C++ を呼ぶとき。どんな組み合わせでも、**間に立つのは C の呼び出し規約**です。

理由は、C ABI が**最も小さい共通部分**だからです。

第 5 章で見たとおり、ABI が決めているのは「引数をどのレジスタに置くか」「戻り値はどこか」「誰がレジスタを守るか」といった、**機械語のレベルの取り決め**です。ここには言語の機能が一切入っていません。

- クラスも、例外も、ジェネリクスも、所有権も出てこない
- どの言語も「C のように振る舞う関数」なら出力できる

```rust
// Rust から C ABI の関数を公開する
#[no_mangle]
pub extern "C" fn add(a: i32, b: i32) -> i32 { a + b }
```

`extern "C"` が「C の規約で呼べるようにせよ」という指示、`#[no_mangle]` が「名前を修飾するな」という指示です。第 5 章で見た名前修飾（name mangling）を止めています。

<Callout type="tip" title="C++ 同士でも ABI は揃わない">
  皮肉なことに、**C++ は C++ 同士でも ABI が安定しません**。
  コンパイラやバージョンが違うと、名前修飾も例外の実装も標準ライブラリのレイアウトも変わります。

  だから C++ のライブラリを配布するときも、**境界は C の関数にする**のが定石です。
  言語が豊かになるほど、境界は貧しくしなければならない。
</Callout>

## 呼ぶ側の仕組み

### 1. 静的リンク・動的リンク

C から C を呼ぶ場合は、第 5 章でみたリンクそのものです。ヘッダで宣言し、リンク時に解決します。

### 2. 実行時に探す

言語のランタイムが `dlopen` と `dlsym` を使って、実行時にライブラリを読み込み、シンボルを引きます。

```c
void *handle = dlopen("libfoo.so", RTLD_LAZY);
int (*add)(int, int) = dlsym(handle, "add");
int result = add(1, 2);
```

**Python の `ctypes` はこれをそのままやっています。**

```python
import ctypes
lib = ctypes.CDLL("./libfoo.so")
lib.add.argtypes = [ctypes.c_int, ctypes.c_int]
lib.add.restype = ctypes.c_int
print(lib.add(1, 2))
```

`argtypes` と `restype` を指定しているのは、**Python がその関数の型を知らない**からです。C のライブラリにはヘッダの情報が残っていません。シンボル名とアドレスしかない。

だから、**型を人間が書いて教える**必要があります。間違えれば、引数が別のレジスタから読まれ、見当違いの値が渡ります。

<Callout type="warn" title="型を間違えると即座には落ちない">
  `c_int` と書くべきところを `c_long` と書いても、多くの場合そのまま動きます。
  値が小さいうちは上位ビットが 0 だからです。

  **境界を越えた値だけが壊れる。** 第 4 章で見た「ページ境界を越えないと検出されない」
  のと同じ構造で、テストをすり抜けます。
</Callout>

### 3. 言語ごとの専用機構

| 言語 | 仕組み | 特徴 |
| --- | --- | --- |
| Go | **cgo** | C のコードを Go のソースに直接書ける。C コンパイラが必要 |
| Python | ctypes / cffi / C API / **PyO3** | C API は最も速いが、Python のバージョンに依存する |
| Java | JNI / **Panama（FFM API）** | JNI は冗長。Panama は JDK 22 で正式化された後継 |
| Node.js | **N-API** | V8 の内部に依存しない安定 ABI |
| Rust | `extern "C"` / bindgen | ヘッダから束縛を自動生成できる |

**ヘッダから自動生成する**方向（bindgen、cgo、cffi の API モード）と、**手で書く**方向（ctypes）があります。前者のほうが型の食い違いを防げます。

## 境界で壊れるもの

ここからが本題です。FFI の難しさは、呼ぶこと自体ではなく、**境界を越えるときに合わせなければならないものの多さ**にあります。

### 構造体のレイアウト

第 1 章で見たアラインメントとパディングが、そのまま問題になります。

```c
struct Point { char tag; int x; int y; };   // 12 バイト（パディング込み）
```

呼ぶ側がこれを「1 + 4 + 4 = 9 バイト」だと思って組み立てると、**すべてのフィールドがずれます**。

さらに、`#pragma pack` の有無、コンパイラ、ビット幅（第 1 章の LP64 / LLP64）でも変わります。

### 文字列

| 言語 | 表現 |
| --- | --- |
| C | **NUL 終端**のバイト列。長さは持たない |
| Go / Rust | ポインタ + **長さ** |
| Java / C# / JS | UTF-16、長さ付き、不変 |
| Python | 内部表現が可変（Latin-1 / UCS-2 / UCS-4） |

C に文字列を渡すには、**NUL 終端のコピーを作る**必要があります。そして、そのコピーを**いつ解放するか**という問題が生まれます。

第 1 章で見た文字コードの違いも、ここで効いてきます。UTF-8 を前提にしている C のライブラリに、UTF-16 の文字列をそのまま渡せば壊れます。

### 所有権：誰が確保し、誰が解放するのか

**最も事故が多い箇所です。**

```c
char *result = library_function();   // ライブラリが malloc したものを返す
// これは誰が free するのか？
```

規約は 3 通りあり得ます。

| 規約 | 呼ぶ側がすること |
| --- | --- |
| 呼ぶ側が解放する | ライブラリと同じアロケータで `free` する |
| **専用の解放関数を呼ぶ** | `library_free(result)` を呼ぶ |
| ライブラリが持ち続ける | 何もしない。次の呼び出しで無効になることがある |

**ドキュメントを読むしかありません。** 間違えれば、メモリリークか、二重解放か、解放済み領域の参照になります。

<Callout type="warn" title="アロケータが違うと free できない">
  Windows では、DLL ごとに別の C ランタイムがリンクされていることがあります。
  **A の malloc で確保したものを B の free に渡すと壊れます。**

  これが「専用の解放関数を用意する」という規約が広く使われる理由です。
</Callout>

### GC との衝突

GC を持つ言語では、さらに厄介になります。

**問題 1：オブジェクトが移動する。**

多くの GC は、断片化を避けるためにオブジェクトを移動させます（コピー GC、世代別 GC）。C にポインタを渡した直後に GC が走ると、**渡したアドレスは無効になります**。

対策は、GC に「これは動かすな」と伝えることです（ピン留め、pinning）。

**問題 2：生きているのに回収される。**

```go
data := make([]byte, 100)
C.process(unsafe.Pointer(&data[0]))   // Go 側から見ると data はもう使われていない
```

C 側が非同期に使い続けている間に、Go の GC が `data` を回収するかもしれません。**GC は C 側のポインタを知りません。**

対策は、呼び出しが終わるまで参照を保持することです。Go なら `runtime.KeepAlive`、あるいは `runtime.AddCleanup` でライフサイクルを結びつけます。

**問題 3：コールバックで戻ってくる。**

C から言語側の関数を呼び返すとき、**関数ポインタしか渡せません**。クロージャや、GC 管理下のオブジェクトへの参照は渡せない。

そこで、**ハンドル**（整数の ID）を経由します。言語側でテーブルを持ち、C には ID だけを渡す。Go の `cgo.NewHandle` がこれです。

### スレッド

- Python の **GIL**（第 6 章）：C の関数を呼ぶ前に GIL を解放しないと、その間ほかのスレッドが止まる。解放したなら、戻ってきたときに取り直す必要がある
- Go の **goroutine**：goroutine のスタックは小さく、可変長。C はそれを前提にしていないので、**専用のシステムスタックに切り替える**必要がある
- **TLS**（スレッドローカル記憶域）：言語ランタイムが使うレジスタ（Go の `g` レジスタなど）を C が壊すことがある
- C 側が作ったスレッドから言語側に呼び返すには、**そのスレッドをランタイムに登録**する必要がある（JNI の `AttachCurrentThread`）

### エラー

**例外は境界を越えられません。** C++ の例外が C の関数を通過すると、多くの場合そこで終了します。Rust の panic も同様で、`extern "C"` の境界を越える panic は未定義動作でした（現在は中断するよう定められています）。

したがって、**境界では必ずエラーコードに変換する**必要があります。

## FFI は、segfault との戦いになる

ここまでの項目は、どれか 1 つでも間違えると、**第 4 章で見たセグメンテーションフォールト**になります。

そして、状況が普通より悪い。

| | 通常のバグ | FFI 越しのバグ |
| --- | --- | --- |
| 落ちる範囲 | そのコード | **ホストプロセス全体** |
| スタックトレース | 出る | **境界で途切れる** |
| デバッガ | 効く | 言語のデバッガは C 側を見られない |
| Sanitizer | 効く | 言語ランタイムごとビルドし直す必要がある |
| 再現性 | まだまし | GC やスレッドのタイミング次第 |

**Python のスクリプトが `Segmentation fault` とだけ出して死ぬ**という経験は、ほぼこれです。Python のコードには何も問題がなく、C の境界で壊れている。

<Callout type="warn" title="安全な言語を使っていても、安全ではなくなる">
  Rust も Go も Java も、メモリ安全を保証します。
  **しかし FFI の境界を越えた先は、その保証の外です。**

  Rust が `unsafe` ブロックを要求するのは、まさにここを明示するためです。
  「安全でない箇所がどこか」がコード上で分かることに価値があります。

  逆に言えば、**FFI を使った時点で、そのプロセスの安全性は C のレベルまで落ちます。**
</Callout>

## 呼び出しそのもののコスト

FFI は「関数呼び出しとほぼ同じ」と書きましたが、言語によっては前後に処理が入ります。

**Go の cgo** が典型です。呼び出しのたびに、

1. goroutine のスタックから、**OS スレッドのシステムスタックに切り替える**
2. ランタイムに「この goroutine はしばらく Go の外に出る」と通知する（スケジューラが他を動かせるように）
3. C の関数を呼ぶ
4. 戻ってきて、状態を復元する

この前後の処理が、**単純な関数呼び出しの数十倍**のコストになります。

そのため、**細かい呼び出しをループで繰り返すのが最悪のパターン**です。境界をまたぐ回数を減らし、1 回でまとまった量を渡すのが定石になります。第 7 章で見た「システムコールの回数を減らす」のと、まったく同じ話です。

<Callout type="tip" title="cgo を使わずに C を呼ぶという選択肢">
  Go には、cgo を使わずに `dlopen` と自前のトランポリンで C の関数を呼ぶ手法もあります
  （purego など）。

  C コンパイラが不要になるので、**クロスコンパイルが簡単になる**という大きな利点があります。
  cgo を有効にすると、対象プラットフォームごとに C のツールチェインが必要になり、
  「Go はクロスコンパイルが簡単」という利点が失われるためです。
</Callout>

## ビルドとデプロイの問題

見落とされがちですが、実務ではここが一番効きます。

- **C コンパイラが必要になる**。CI にも、開発環境にも
- **クロスコンパイルが難しくなる**。ターゲットごとのツールチェインが要る
- **動的ライブラリの配布が必要**。バージョンの不一致（第 5 章）が起きる
- **静的リンクすれば配布は楽になる**が、ライセンスとバイナリサイズの問題が出る

「1 バイナリを置くだけで動く」という利点は、FFI を使った時点で危うくなります。

## 呼ばないという選択

境界の面倒をすべて避ける方法があります。**別プロセスにする**ことです。

```
FFI:        同じプロセス。速い。落ちたら一緒に死ぬ
別プロセス:  IPC が必要。遅い。落ちても生き残る
```

第 6 章で見た「プロセスを分けることの意味」そのものです。分離と速度の交換です。

Chrome がレンダリングをプロセスごとに分け、PostgreSQL が接続ごとにプロセスを使うのと同じ判断が、ここでも使えます。

**そして、その中間を狙ったものが次に出てきます。** 同じプロセスの中にいながら、壊れても外に波及しない実行環境。それが WebAssembly です。

## まとめ

- FFI は「同じプロセスの中で、別の言語の関数を呼ぶ」仕組み
- 共通語は C ABI。最も小さい共通部分だから
- 境界では、構造体レイアウト、文字列表現、所有権、GC、スレッド、エラーの 6 つを合わせる必要がある
- どれかを間違えると、**ホストプロセス全体が segfault で落ちる**
- スタックトレースは境界で途切れ、デバッガも Sanitizer も効きにくい
- 安全な言語を使っていても、FFI の先は安全ではない
- 呼び出しそのものにもコストがある。境界をまたぐ回数を減らす
- ビルドとデプロイの面倒も増える

次は、この問題に対して**まったく別の方向から出てきた答え**を見ます。ブラウザの中で生まれた命令セットが、なぜ FFI の解になりつつあるのか。
