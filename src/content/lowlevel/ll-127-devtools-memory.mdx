## 閉じたはずの画面が残る

1 枚のページの中で画面を切り替えるアプリケーション（SPA）を長く開いていると、だんだん重くなることがあります。タブを開き直すと直る。典型的なメモリリークの症状です。

JavaScript には GC があり、第 26 回で見たとおり、**GC ルートから辿れないもの**は自動で回収されます。逆に言えば、辿れるものは決して回収されません。GC のある言語でのリークとは、「もう使わないのに、どこかから辿れてしまうもの」が溜まっていくことです。解放し忘れではなく、**参照の消し忘れ**です。

この回では、Chrome の DevTools の Memory パネルを使って、その「どこか」を突き止める方法を見ます。題材として、一覧画面を開いて閉じるだけの小さなページを用意しました。

```js
const rowCache = new Map()

class ListView {
  constructor(n) {
    this.root = document.createElement('section')
    for (let i = 0; i < n; i++) {
      const row = document.createElement('div')
      row.className = 'row'
      row.textContent = `item ${opened}-${i}`
      this.root.appendChild(row)
      rowCache.set(`${opened}-${i}`, row)          // 行の要素をキャッシュする
    }
    this.payload = new Array(20000).fill(opened)  // 画面が持つデータの代わり
    this.onResize = () => { this.root.dataset.w = String(innerWidth) }
    window.addEventListener('resize', this.onResize)
  }
  close() {
    this.root.remove()
    window.removeEventListener('resize', this.onResize)
  }
}
```

上は cache 版の形です。1 回開くと 200 行の `div` を作り、閉じると `section` ごと DOM から外します。このページに、漏らし方を変えた 5 つの版を用意しました。

| 版 | `rowCache` に行を入れる | `close()` でリスナを外す |
| --- | --- | --- |
| fixed | 入れない | 外す |
| cache | 入れる | 外す |
| listener | 入れない | 外さない |
| leak | 入れる | 外さない |
| weakref | `WeakRef` で包んで入れる | 外す |

計測は Apple M1 Pro / macOS 26.2 の Chrome 155.0.8059.85（headless）で、Playwright から Chrome DevTools Protocol（DevTools が裏で使っている命令の口）を叩いて行いました。DevTools の画面で行う操作と、取れるデータは同じです。

## どのメモリを見ているのか

最初に区別しておくべきことがあります。ページが使うメモリは 1 か所ではありません。

- **JS ヒープ**：V8 が管理する JavaScript のオブジェクト。配列、文字列、クロージャ
- **DOM**：要素やテキストノード。Blink（Chrome の描画エンジン）が自分のヒープで管理する
- **その他**：デコード済みの画像、GPU のテクスチャ（第 121 回）、ネットワークのバッファ

Chrome のタスクマネージャ（`Shift+Esc`）は、この違いを列で分けています。文書は「The Memory footprint column represents OS memory. DOM nodes are stored in OS memory.」「The JavaScript Memory column represents the JS heap.」と説明しています（[Fix memory problems](https://developer.chrome.com/docs/devtools/memory-problems)）。

この区別が実際に効いてくる例を、cache 版で見ます。開いて閉じるを 30 回繰り返し、強制的に GC してから、DevTools の Performance パネルのカウンタと同じ値（JS ヒープの使用量、DOM ノード数、イベントリスナ数）を読みました。

```text
版          回数   JS ヒープ   DOM ノード   リスナ
fixed        0    0.59 MB        16        0
            30    0.66 MB        16        0
cache        0    0.59 MB        16        0
            30    0.98 MB     12046        0
listener     0    0.59 MB        16        0
            30    2.96 MB     12046       30
leak         0    0.59 MB        16        0
            30    3.27 MB     12046       30
```

cache 版では、DOM ノードが 12,030 個増えています（30 回 × (`section` 1 + `div` 200 + テキスト 200)）。ところが JS ヒープは 0.39 MB しか増えていません。同じ時点のヒープスナップショット（後述）では、到達できるものの合計が 0.91 MB から 3.00 MB へ増え、そのうち Blink の側のオブジェクトが 1.83 MB を占めていました。**JS ヒープの数字だけを見ていると、DOM のリークを小さく見積もります。** DOM ノード数のカウンタを必ず並べて見てください。

Performance パネルでメモリを記録すると、この 2 つが線で出ます。文書は「Here you can see memory usage broken down by JS heap (same as HEAP graph in the Overview pane), documents, DOM nodes, listeners, and GPU memory.」と書いています（[Fix memory problems](https://developer.chrome.com/docs/devtools/memory-problems)）。

<Callout type="tip" title="記録の最初と最後で GC を押す">
  JS ヒープの線は、GC が走るまで上がり続けるのが普通です。上がっていること自体はリークの証拠になりません。見るべきは、**GC の直後の値が、操作を繰り返すたびに上がっていくか**です。文書も「It's a good practice to start and end your recording with a forced garbage collection.」と勧めています（[Fix memory problems](https://developer.chrome.com/docs/devtools/memory-problems)）。上の表の値も、すべて GC を強制した直後に読んでいます。

  同じ操作を 1 回だけ行って比べるのも危険です。初回だけ走る準備（コードのコンパイル、キャッシュの用意）が混ざります。**同じ操作を 10 回、20 回と繰り返して、回数に比例して増えるか**を見ます。上の表では DOM ノードが 10 回ごとにきっちり 4,010 個ずつ増えていました。
</Callout>

## ヒープスナップショットの中身

増えていることが分かったら、次は「何が、なぜ残っているのか」です。Memory パネルの Heap snapshot は、その瞬間のヒープを丸ごと書き出します。中身は**グラフ**です。

- 頂点：オブジェクト。JavaScript のオブジェクトに加えて、DOM の要素や Blink の内部の構造も入る
- 辺：参照。「`ListView` の `root` プロパティが `<section>` を指す」のように、名前の付いた矢印

leak 版を 30 回開いて閉じたあとのスナップショットは 4.9 MB の JSON で、頂点が 56,252 個ありました。この中から、残ってはいけないものを探します。手がかりになるのが、各オブジェクトに付く 2 つの大きさです。

| 列 | 意味 |
| --- | --- |
| Shallow size | そのオブジェクト自身が占める大きさ |
| Retained size | そのオブジェクトを消したら、一緒に回収できるようになるものの合計 |

文書の定義は、Shallow size が「This is the size of memory that is held by the object itself.」、Retained size が「This is the size of memory that is freed once the object itself is deleted along with its dependent objects that were made unreachable from GC roots.」です（[Memory terminology](https://developer.chrome.com/docs/devtools/memory-problems/memory-101)）。

`ListView` のオブジェクトの Shallow size は 24 バイトしかありません。プロパティを 3 つ持つだけだからです。しかし、それが指す `payload` の配列と `section` の木を巻き添えにしているなら、Retained size は桁違いに大きくなります。**リークを探すときに並べ替える列は、Retained size です。**

## 誰が誰を「支配」しているか

Retained size は、「消したら届かなくなるもの」を数えます。ここで注意が要るのは、**別の経路でも届くものは数えない**ことです。

この関係を整理したのが**支配木**（dominator tree）です。GC ルートから X へのどの経路も必ず A を通るとき、A は X を支配する、と言います。A を消せば X には届かなくなるので、X は A の Retained size に入ります。文書は「Dominator objects are comprised of a tree structure because each object has exactly one immediate dominator.」と説明しています（[Memory terminology](https://developer.chrome.com/docs/devtools/memory-problems/memory-101)）。

下の SIM は、例のページを 1 画面ぶんに縮めたグラフです。`close()` で何を外すかを選び、1 手ずつ進めてください。

<HeapRetainers client:visible />

「何も外さない」を選ぶと、閉じたあとの `ListView` の Retained size は 80,048 バイトにとどまります。`section` と `div` は、`ListView` を消しても `rowCache` から届いてしまうので、`ListView` の取り分に入らないからです。「キャッシュだけ消す」にすると、`section` から下が `ListView` からしか届かなくなり、その分が `ListView` の Retained size に加わります。

実際のスナップショットでも同じことが起きていました。30 回分のスナップショットから、weak（弱い参照）の辺を除いて支配木を自分で計算した値です（DevTools はさらに細かく辺を選り分けるので、画面の値とは少しずれることがあります）。

```text
                       listener 版        leak 版
ListView  Shallow            24             24
          Retained      136,152         80,048
<section> Retained       56,104            104
<section> の直接の支配者    ListView      (GC roots)
rowCache  Retained          280        229,924
```

listener 版では、1 画面ぶんの `ListView` を消せば、配列（約 80 KB）と `section` の木（56 KB）がまとめて消えます。1 回あたり 136 KB を握っている犯人として、Retained size の大きい順に並べるだけで `ListView` が浮かびます。

ところが leak 版では、同じ `ListView` が 80 KB しか握っていないことになり、`section` は 104 バイトです。**2 つの経路から握られているものは、どちらの Retained size にも入りません。** そのため、原因が 2 つあるリークでは、それぞれの原因を 1 つずつ消しても Retained size の数字はあまり動かず、両方を消して初めて一気に減る、ということが起きます。Retained size が小さいからといって無関係だとは言えません。

<Callout type="note" title="Distance 列">
  Summary ビューには、GC ルートからの距離を示す Distance という列もあります。文書は「Distance shows the distance to the root using the shortest simple path of nodes.」と書いています（[Record heap snapshots](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots)）。同じ種類のオブジェクトの大半が同じ距離にあるのに、いくつかだけが遠いなら、それは予定外の経路で握られている候補です。
</Callout>

## Retainers を読む

「誰が握っているか」を具体的に教えてくれるのが、オブジェクトを選んだときに下に出る **Retainers** の欄です。文書は「The Retainers section at the bottom of the Memory panel shows objects that point to the object selected in the view.」と書いています（[Record heap snapshots](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots)）。

Retainers は、選んだオブジェクトから矢印を逆向きに辿って GC ルートまで遡ります。listener 版のスナップショットで、残っている `section` から GC ルートまでの最短の経路を辿ると、次のようになりました（Blink の内部の名前は一部省いています）。

```text
(GC roots)
 └ system / NativeContext                ページの JavaScript 全体の文脈
   └ global_proxy_object → Window
     └ blink::EventTargetData            window に登録されたリスナの一覧
       └ RegisteredEventListener → V8EventListener
         └ (closure) onResize
           └ context → system / Context  クロージャが閉じ込めた変数の入れ物
             └ this → ListView
               └ root → <section>
```

**window のリスナ一覧 → アロー関数 → その関数が閉じ込めた `this` → `ListView` → `root`**。`removeEventListener` を忘れたことが、そのまま経路として読めます。アロー関数は自分の `this` を持たず、外側の `this` を変数のように閉じ込めます。そのため、関数を 1 つ握られると、それを作ったオブジェクト全体が握られます。

cache 版では、経路はこうなりました。

```text
(GC roots)
 └ system / NativeContext
   └ script_context_table → system / Context
     └ rowCache → Map
       └ table → <div class="row">
         └ [6] → <section>
```

`Map` の中身から `div` へ、そして `div` から親の `section` へ辿っています。DOM の要素は親や兄弟への参照を持っているので、**行を 1 つ握るだけで、木全体が残ります**。cache 版の `rowCache` の Retained size は 2,009,108 バイトでした。

<Callout type="warn" title="経路の途中の名前は、エンジンの内部">
  `system / Context` や `blink::EventTargetData` は、ソースコードには出てこないエンジンの内部の構造です。版によって名前も段数も変わります。読むときは、**自分のコードに出てくる名前（変数名、プロパティ名、クラス名）が経路のどこに出てくるか**に注目します。上の経路なら `rowCache`、`onResize`、`this`、`root` です。
</Callout>

## Detached な DOM

`section` のように、DOM の木から外されたのに JavaScript から届く要素を、DevTools は **Detached** と呼びます。文書は「A node is said to be "detached" when it's removed from the DOM tree but some JavaScript still references it.」と定義し、探し方として「Type Detached in the Class filter input box to search for detached DOM trees.」と書いています（[Fix memory problems](https://developer.chrome.com/docs/devtools/memory-problems)）。

スナップショットの各頂点には、この判定の印が付いています。30 回分の結果は次のとおりでした。

```text
版         Detached の印     その中身
listener        30          <section> 30
cache         6030          <section> 30、<div class="row"> 6000
leak          6030          同上
fixed            0
```

listener 版にも、`section` の下には 6,000 個の `div` が残っています。しかし印が付いたのは 30 個の `section` だけで、`div` には付いていませんでした。cache 版で `div` に印が付いたのは、`rowCache` が `div` を直接握っていたからだと読めます。どちらの場合も、印の付いた要素を開けば、その下の木が見えます。

Memory パネルには、JavaScript から握られている切り離された要素だけを一覧にする **Detached elements** という種類の記録もあります。文書は「The Detached elements profile shows you detached elements that persist because they are referenced by JavaScript code.」と説明しています（[Fix memory problems](https://developer.chrome.com/docs/devtools/memory-problems)）。

## よくある 4 つの握り方

Retainers を何度か読むと、同じ形に何度も出会います。

| 握っているもの | 典型的な形 | 外し方 |
| --- | --- | --- |
| イベントリスナ | `window` や `document` など長生きするものに登録し、外し忘れる | `removeEventListener`。または `addEventListener` の `signal` に `AbortController` の `signal` を渡し、閉じるときに `abort()` |
| クロージャ | コールバックやアロー関数が、外側の大きなオブジェクトを閉じ込める | 閉じ込めるものを小さくする。必要な値だけを先に取り出してから関数を作る |
| タイマ | `setInterval` のコールバックが画面を参照し続ける | 閉じるときに `clearInterval` |
| キャッシュ | モジュールの変数に置いた `Map` や配列に、要素や画面のオブジェクトを入れる | 上限を決めて古いものを捨てる。キーが要素なら `WeakMap` |

`signal` については、MDN が「The listener will be removed when the abort() method of the AbortController which owns the AbortSignal is called.」と書いています（[addEventListener](https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/addEventListener)）。1 つの画面がリスナを何個も登録する場合でも、`abort()` 1 回でまとめて外せます。

どれにも共通しているのは、**短命なもの（画面）を、長生きするもの（`window`、モジュールの変数、タイマ）から指している**ことです。長生きするものから短命なものへの矢印を作るときには、それをいつ消すかを同時に決めておきます。

## 弱い参照：WeakMap と WeakRef

「GC の邪魔をしない参照」も用意されています。`WeakMap` は、キーを弱く持つ辞書です。MDN は「an object's presence as a key in a WeakMap does not prevent the object from being garbage collected.」と書いています（[WeakMap](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WeakMap)）。要素に付けたい情報を、要素をキーにして持つ用途に向いています。要素が消えれば、情報も一緒に消えます。

例のページのキャッシュは文字列をキーにしているので、`WeakMap` は使えません。そこで値を `WeakRef` で包んだのが weakref 版です。

```text
版         回数   JS ヒープ   DOM ノード
weakref      0    0.59 MB        16
            10    0.76 MB        16
            20    0.85 MB        16
            30    0.98 MB        16
```

DOM ノードは 16 のまま増えず、要素は回収されています。ところが **JS ヒープは cache 版と同じだけ増えています**。中身の消えた `WeakRef` と、そのキーの文字列が `Map` に 6,000 件残っているからです。弱い参照は、指す先を回収させてくれますが、入れ物の項目までは消してくれません。

項目を消す方法として、オブジェクトが回収されたときに呼ばれる `FinalizationRegistry` がありますが、V8 の解説は「avoid writing code that depends on the garbage collector cleaning up a WeakRef or calling a finalizer at any predictable time — it can’t be done!」と強く注意しています（[Weak references and finalizers](https://v8.dev/features/weak-references)）。呼ばれる時期は決まっておらず、呼ばれないこともあります。後片付けの補助には使えても、それに頼った設計にはしないのが無難です。

## スナップショットを比べる

ここまでは 1 枚のスナップショットを読みました。実際のアプリケーションでは、何万もあるオブジェクトの中から怪しいものを見つけるのが一苦労です。そこで 2 枚を比べます。

Comparison ビューは「Differences between two snapshots.」、つまり 2 枚の差分を、コンストラクタの名前ごとの増減として見せます（[Record heap snapshots](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots)）。項目を開くと、追加されたインスタンスと削除されたインスタンスが分かれて出ます。スナップショットの各オブジェクトには ID が付いているので、ここでは 10 回開いた後（2 枚目）と 30 回開いた後（3 枚目）を、その ID で突き合わせて同じ集計をしました。

```text
leak 版  2 枚目 → 3 枚目     新しく現れた 19,805 個、消えた 3,591 個
  4000  <div class="row">
  4000  blink::UniqueElementData
  4000  Text
    20  ListView
    20  <section>

fixed 版 2 枚目 → 3 枚目     新しく現れた 3,622 個、消えた 3,589 個
  （上位は文字列、数値、描画の内部の構造。画面の部品はない）
```

20 回ぶん開いたので、`ListView` と `section` が 20 個、`div` が 20 × 200 = 4,000 個。**増えた個数が操作の回数のちょうど倍数になっているもの**がリークの候補です。fixed 版にも 3,622 個の新しいオブジェクトがありますが、ほぼ同じ数が消えており、中身は計測のたびに作り直される内部の値です。

さらに絞り込む定番の手順が **3 スナップショット法**です。1 枚目を取り、操作してから 2 枚目、もう一度操作してから 3 枚目を取る。そして「1 枚目と 2 枚目のあいだに作られ、3 枚目でもまだ生きているもの」だけを見ます。一時的に作ってすぐ捨てるものが除かれます。

```text
leak 版                 fixed 版
 9628 生き残り           1515 生き残り
 2000 <div class="row">   498 system / FunctionTemplateInfo
 2000 Text                383 (string)
 2000 UniqueElementData   229 system / AccessorPair
                          202 (code)
```

fixed 版にも 1,515 個の生き残りがあります。初回の操作で一度だけ作られる、関数の雛形やコンパイル済みのコードです。これらは 2 回目以降は増えません。生き残りがあること自体ではなく、**操作の回数に比例して生き残るもの**を探します。

## 割り当てを記録する

スナップショットは「今、何が残っているか」の写真です。「どこで作られたか」を知りたいときは、時間に沿って割り当てを記録する方式を使います。

- **Allocation instrumentation on timeline**：記録中の割り当てを時刻つきで残す。文書は時間軸に出る青い棒について「Those blue bars represent new memory allocations. Those new memory allocations are your candidates for memory leaks.」と書いており、棒の区間を選ぶと、その間に作られたオブジェクトだけに絞り込める
- **Allocation sampling**：割り当てを一定の量ごとに抜き取り、関数ごとに集計する。文書は「Use the Allocation sampling profile type in the Memory panel to view memory allocation by JavaScript function.」と書いている（どちらも [Fix memory problems](https://developer.chrome.com/docs/devtools/memory-problems)）

Allocation sampling は、第 239 回で見た CPU のサンプリングプロファイラのメモリ版です。leak 版を 30 回開いて閉じる間、1 KiB ごとに抜き取って集計すると、記録の終わりに生きていた割り当てはこうなりました。

```text
2,559,456  ListView        （leak.html 14 行目、コンストラクタ）
  213,928  set             （Map.prototype.set）
   10,408  (V8 API)
```

コンストラクタの中の `new Array(20000)` と、`rowCache.set` が上位に来ています。抜き取りなので値は推定ですが、負荷が小さく、本番に近い操作でも記録できます。一方、DOM の要素は JS ヒープの外で作られるため、ここには小さくしか現れません。DOM の増え方は、カウンタとスナップショットの側で見ます。

## 調べる順番

1. Performance パネル（またはタスクマネージャ）で、同じ操作を 10 回、20 回と繰り返し、GC の直後の JS ヒープと DOM ノード数が回数に比例して増えるかを見る
2. 増えるなら、操作の前後でヒープスナップショットを取り、Comparison ビューで「回数の倍数で増えたもの」を探す
3. 候補を選び、Retained size の大きいものから Retainers を開いて、自分のコードの名前が出てくるところまで遡る
4. DOM が残っているなら、Class filter に `Detached` と入れて、切り離された木を探す
5. 経路を断つ修正をして、1 に戻って増えなくなったことを確かめる

修正したら必ず測り直します。この回の leak 版のように原因が 2 つあると、片方を直しても数字が大きくは変わらず、「効かなかった」と誤解しがちです。

## まとめ

- GC のある言語のリークは、使わないものが GC ルートから辿れてしまうこと。参照の消し忘れが原因
- JS ヒープと DOM は別の場所で数えられる。DOM が漏れても JS ヒープの数字はあまり動かないことがあるので、DOM ノード数を並べて見る
- Shallow size は自分の大きさ、Retained size は自分を消せば一緒に消えるものの合計。リークは Retained size で探す
- 2 つの経路から握られているものは、どちらの Retained size にも入らない。原因が複数あるリークでは数字が小さく見える
- Retainers を GC ルートまで遡り、自分のコードの名前が出てくる場所で原因を読む。長生きするもの（`window`、モジュールの変数、タイマ）から短命なものへの矢印が典型
- DOM の要素は親と兄弟を指しているので、1 つ握ると木全体が残る
- 弱い参照は指す先を回収させるが、入れ物の項目は残る。FinalizationRegistry が呼ばれる時期は保証されない
- 比べるときは、操作の回数の倍数で増えたものを探す。3 スナップショット法で一時的なものを除く
