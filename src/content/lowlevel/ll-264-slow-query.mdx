## エンドポイントの次は SQL

第 263 回では、nginx のアクセスログを alp で集計し、時間の合計で並べた表の上位に、商品の一覧とコメント一覧が来ることを確かめました。どちらもデータベースを引くエンドポイントです。けれどアクセスログには、その時間がどの SQL に使われたのかは書かれていません。

この回では、データベースの側の記録を見ます。MySQL の**スロークエリログ**です。名前は「遅いクエリの記録」ですが、ISUCON の上位チームはこれを**すべてのクエリの記録**として使います。その理由と、集計の道具である pt-query-digest の読み方、そして集計が隠してしまうものを、第 263 回と同じアプリケーションに負荷をかけて確かめます。

## スロークエリログの 1 件

MySQL の文書は、スロークエリログを次のように定義しています（[MySQL 8.0 Reference Manual: The Slow Query Log](https://dev.mysql.com/doc/refman/8.0/en/slow-query-log.html)）。

> The slow query log consists of SQL statements that take more than `long_query_time` seconds to execute and require at least `min_examined_row_limit` rows to be examined.

実行に `long_query_time` 秒より長くかかり、かつ `min_examined_row_limit` 行以上を調べた SQL が記録されます。文書には「The minimum and default values of `long_query_time` are 0 and 10, respectively.」とあり、既定では 10 秒です。`min_examined_row_limit` は、今回の MySQL では 0（行数で絞らない）でした。

記録の 1 件は次のような形です。今回の実測で取ったものから 1 件を抜き出しました。

```text
# Time: 2026-11-12T00:57:28.303737Z
# User@Host: root[root] @  [192.168.215.1]  Id:    18
# Query_time: 0.015894  Lock_time: 0.000003 Rows_sent: 3  Rows_examined: 3
SET timestamp=1794445048;
SELECT id, user_id, body, created_at FROM comments WHERE item_id = 22952 ORDER BY created_at DESC LIMIT 10;
```

| 項目 | 意味 |
| --- | --- |
| `Query_time` | 実行にかかった秒数（マイクロ秒単位） |
| `Lock_time` | ロックの獲得にかかった秒数 |
| `Rows_sent` | クライアントに返した行の数 |
| `Rows_examined` | サーバーが調べた行の数 |

`Rows_sent` と `Rows_examined` は、文書ではそれぞれ「The number of rows sent to the client.」「The number of rows examined by the server layer (not counting any processing internal to storage engines).」と説明されています。後者は MySQL のサーバー層が受け取った行の数で、InnoDB の中で読み飛ばした行は含まれません。

`Query_time` の扱いにも 1 つ注意があります。文書には「The time to acquire the initial locks is not counted as execution time.」とあります。最初のロックを待った時間は `Query_time` に入らず、`Lock_time` の側に出ます。

## すべてのクエリを記録する

### 速いクエリも積もる

ISUCON9 本選で優勝した白金動物園の mirakui さんは、次のように書いています（[チーム白金動物園として ISUCON 9 本選で優勝しました](https://blog.mirakui.com/entry/2019/10/14/011554)）。

> 今回、MySQL のスローログは `long_query_time = 0` にして、常に全部のクエリを出させていました。遅いクエリについ目が行ってしまいがちですが、ISUCON のような高トラフィック環境下では、10 ms もかからないようなクエリでも、量があることでアプリケーションの負荷になることがあります。スロークエリというのはインデックス張ったりしてわりと早めに減らせてしまうので、スロークエリだけを見ていると「あーもう DB ネックじゃなくなったね」という誤解をすることがあります（予選のときにこの思考になってしまってた）。今回は速いクエリに注目していたことで、大量に呼ばれているクエリに気づきやすくなりました。

`long_query_time` を 1 秒や 0.1 秒にすると、記録されるのは 1 回が遅いクエリだけになります。第 263 回で、アクセスログを合計で並べる理由を「取り返せる時間の大きさ」と書きました。クエリも同じで、1 回 0.5 ミリ秒のクエリでも 10 万回呼ばれれば 50 秒です。それを見落とさないために、閾値を 0 にしてすべてを記録します。

### 設定は接続のたびに写し取られる

設定は、MySQL の起動時のオプション（`my.cnf` や `--long-query-time=0`）でも、動いているサーバーへの `SET GLOBAL` でも変えられます。ここに 1 つ落とし穴があります。

今回の実測は、MySQL 8.0.46 を Docker で動かし、`--slow-query-log=1 --long-query-time=10` で起動したところから始めました。アプリケーションを起動して負荷をかけている途中で、`long_query_time` を 0 に変えます。

```text
mysql> SET GLOBAL long_query_time=0;
mysql> SELECT @@global.long_query_time;
0.000000

$ ./lg -base http://127.0.0.1:8264 -c 8 -d 5s
requests=664 errors=0 rps=132.8
$ grep -c '^# Query_time' slow.log
0
```

5 秒間に 664 件の要求を処理したのに、スロークエリログには 1 件も書かれませんでした。アプリケーションを起動し直してから同じ負荷をかけると、今度は 15,581 件が書かれました。

```text
$ ./lg -base http://127.0.0.1:8264 -c 8 -d 5s
requests=1379 errors=0 rps=275.8
$ grep -c '^# Query_time' slow.log
15581
```

理由は、`long_query_time` に「全体の値」と「接続ごとの値」の 2 つがあるからです。MySQL の文書は「The client's session variables are initialized at connect time using the current values of the corresponding global variables.」と説明しています（[MySQL 8.0 Reference Manual: Using System Variables](https://dev.mysql.com/doc/refman/8.0/en/using-system-variables.html)）。接続ごとの値は**接続した瞬間に**全体の値から写し取られます。Go の `database/sql` のように接続を使い回すアプリケーションは、`SET GLOBAL` の前に張った接続を使い続けるので、古い値の 10 秒のままでした。

`SET GLOBAL` で変えたときは、アプリケーションを再起動するか、接続を張り直させる必要があります。もう 1 つ、`SET GLOBAL` で変えた値は MySQL の再起動で元に戻ります（第 278 回）。競技でも本番でも、恒久的に使う設定は設定ファイルに書きます。

## pt-query-digest

### 実測の条件

第 263 回と同じアプリケーション（商品 50,000 行、利用者 1,000 行、コメント 200,000 行、インデックスは主キーだけ）を、スロークエリログを有効にした MySQL につなぎ、16 並列の閉ループで 30 秒間負荷をかけました。今回は nginx を挟まず、アプリケーションに直接要求を送っています。環境は Apple M1 Pro / macOS 26.2、OrbStack の Docker、Go 1.24.6 です。同じ機械で他の重い処理も動いていたため、秒数の絶対値は揺れます。

```text
$ ./lg -base http://127.0.0.1:8264 -c 16 -d 30s
requests=5035 errors=0 rps=167.8
```

30 秒間のスロークエリログは 13,704,303 バイト、59,091 件になりました。これを人が読むことはできないので、集計します。

### フィンガープリントでまとめる

[pt-query-digest](https://docs.percona.com/percona-toolkit/pt-query-digest.html) は Percona Toolkit に含まれるスロークエリログの集計ツールです。今回は 3.7.2 を Docker のイメージ（`percona/percona-toolkit`）で動かしました。

```bash
docker run --rm -v $PWD:/w:ro percona/percona-toolkit pt-query-digest /w/slow.log
```

alp が URI をまとめたように、pt-query-digest は SQL を**フィンガープリント**でまとめます。文書の説明は次のとおりです。

> A query fingerprint is the abstracted form of a query, which makes it possible to group similar queries together. Abstracting a query removes literal values, normalizes whitespace, and so on.

`WHERE id = 452` と `WHERE id = 589` は、どちらも `where id = ?` になり、同じ組に入ります。文書が挙げる変換には、ほかに「Strip comments.」「Lowercase the entire query.」「Replace all literals inside of IN() and VALUES() lists with a single placeholder, regardless of cardinality.」などがあります。`IN (1,2,3)` と `IN (1,2,3,4)` も同じ組です。そして、集計の考え方を SQL で書くと次のようになる、と説明しています。

```sql
SELECT WORST(query BY Query_time), SUM(Query_time), ...
FROM /path/to/slow.log
GROUP BY FINGERPRINT(query)
ORDER BY SUM(Query_time) DESC
LIMIT 10
```

既定の並び順は `Query_time` の**合計**です。第 263 回で alp を合計で並べたのと同じ考え方が、最初から採られています。

約 5 万 9 千件の SQL が 11 種類にまとまりました。`5.52x concurrency` は、実行時間の合計と時間の幅から計算したおおよその同時実行数で、実際に 166 秒 ÷ 30 秒はほぼ 5.5 です。平均して 5.5 本のクエリが同時に走っていたことになります。

注目すべきは最後の 2 行の対比です。返した行は合わせて 39,160 行なのに、調べた行は 1 億 5,543 万行です。返した 1 行のために、平均して約 4,000 行を調べています。

表示する組の数は `--limit` で決まり、既定値は `95%:20` です。文書の説明では、時間の大きい方から全体の 95% に当たる組か 20 組の、先に達した方までを出します。残りは MISC の行にまとめられます。

1 位はコメント一覧のクエリで、データベースの時間の 51.6% を使っています。第 263 回のアクセスログでもコメント一覧は合計の 2 位でした。一覧（`SELECT items`）は 2 位で 19.0% です。

### 比で見当を付ける

返した行数に対する調べた行数の比は、インデックスが足りているかどうかの手早い目安になります。ISUCON13 で優勝した NaruseJun の tohutohu さんは、スロークエリの集計を見るときの基準を次のように書いています（[ISUCON13で優勝しました](https://zenn.dev/tohutohu/articles/923bdf5dcd73af)）。

> こちらも多くの場合はSumを見ますが、最序盤などインデックスを追加したい場合はRow Sent/Row Examinedの比を見ています。適切にインデックスが設定されている場合はこの比が5倍以下くらいになりますが、インデックスがない場合は100倍とかになるので適切なインデックスを考えて設定します。

今回のコメント一覧は、195,520 ÷ 4.11 でおよそ 47,600 倍でした。主キーで 1 行を引く `SELECT users` は、調べた行も返した行も 1 行で、比は 1 倍です。

ただし、比は目安です。次のような場合は、比が大きくても正常、または比が小さくても問題があります。

- **集計のクエリ。** `COUNT(*)` や `SUM` は、多くの行を調べて 1 行を返すのが仕事です。比が大きいのは当然で、問題はその集計を毎回やり直していることの方です（第 273 回）。
- **`LIMIT` で早く止まるクエリ。** 部分一致の検索（`LIKE '%chair%' LIMIT 50`）は、条件に合う行が早く 50 件見つかれば、そこで読むのをやめます。今回の検索のクエリは比が 50 倍前後でしたが、条件に合う行が少ない語で検索されると、表の全体を読みます。
- **返す行がそもそも多すぎるクエリ。** 1 万行を返して、アプリケーションの側で 10 行だけ使っているなら、比は 1 倍でも無駄です。`Rows sent` の大きさそのものも見ます。

## performance_schema

### ログを書かずに集計する

スロークエリログはファイルに 1 件ずつ書くので、すべてを記録すると、それ自体が負担になります（第 265 回で測ります）。MySQL には、文の実行をサーバーの中で集計しておく仕組みもあります。**performance_schema** の `events_statements_summary_by_digest` 表です。ISUCON14 に参加した matsuu さんは、「nginxはnjsを用いてjson形式のログを吐き、MySQLは performance_schema からスロークエリーを取得する形となりました。」と書いています（[DuckDB+Evidenceを駆使してISUCON14で21位になった話](https://matsuu.hatenablog.com/entry/2024/12/14/184649)）。

この表は、pt-query-digest のフィンガープリントと同じ考え方で SQL を正規化した**ダイジェスト**ごとに、回数・時間・行数を足し合わせています。MySQL の文書は正規化について、「Literal values are converted to parameter markers.」「Comments are removed and whitespace is adjusted.」と書いています（[MySQL 8.0 Reference Manual: Performance Schema Statement Digests and Sampling](https://dev.mysql.com/doc/refman/8.0/en/performance-schema-statement-digests.html)）。今回の MySQL では、performance_schema は特に設定しなくても有効になっていました（`@@performance_schema` が 1）。

次の SQL で、時間の合計が大きい順に並べます。時間の列はピコ秒単位なので、10 の 12 乗で割って秒にしています。

```sql
SELECT LEFT(DIGEST_TEXT, 60) AS digest_text,
       COUNT_STAR AS calls,
       ROUND(SUM_TIMER_WAIT / 1e12, 2) AS total_s,
       ROUND(AVG_TIMER_WAIT / 1e9, 3) AS avg_ms,
       SUM_ROWS_EXAMINED AS examined,
       SUM_ROWS_SENT AS sent,
       ROUND(SUM_ROWS_EXAMINED / NULLIF(SUM_ROWS_SENT, 0), 1) AS ratio
FROM performance_schema.events_statements_summary_by_digest
WHERE SCHEMA_NAME = 'shop'
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 8;
```

### プリペアドステートメントは数えられていなかった

さきほどの 30 秒の負荷の後にこの SQL を流すと、結果は**空**でした。表全体を見ても、`SCHEMA_NAME` が NULL の 4 種類・8 回しか入っていません。文の種類ごとの集計表（`events_statements_summary_global_by_event_name`）を見ると、理由が分かりました。

```text
+----------------------------+------------+--------+
| EVENT_NAME                 | COUNT_STAR | s      |
+----------------------------+------------+--------+
| statement/com/Execute      |      32597 | 250.41 |
| statement/sql/insert       |        251 |  37.62 |
| statement/com/Close stmt   |      32597 |  28.14 |
| statement/com/Prepare      |      31605 |  25.03 |
...
```

アプリケーションの SELECT は、すべてプリペアドステートメントの実行（`statement/com/Execute`）として数えられていて、ダイジェストの表には現れていませんでした。手元の MySQL 8.0.46 では、サーバー側のプリペアドステートメントで実行された文はダイジェストごとの集計に載らなかった、ということです。

Go の MySQL ドライバには、`?` の位置に値を埋め込んだ SQL 文字列をクライアントの側で作って送る `interpolateParams` という設定があります。README は「This reduces the number of roundtrips, since the driver has to prepare a statement, execute it with given parameters and close the statement again with `interpolateParams=false`.」と説明しています（[go-sql-driver/mysql](https://github.com/go-sql-driver/mysql#interpolateparams)）。接続の文字列に `interpolateParams=true` を足してアプリケーションを起動し直し、もう一度 30 秒の負荷をかけてから同じ SQL を流しました。

```text
+--------------------------------------------------------------+-------+---------+---------+-----------+-------+---------+
| digest_text                                                  | calls | total_s | avg_ms  | examined  | sent  | ratio   |
+--------------------------------------------------------------+-------+---------+---------+-----------+-------+---------+
```

### 回数の多さは、呼び方の問題

`SELECT users` の 1 回 0.2 ミリ秒を、インデックスで速くする余地はほとんどありません。主キーで 1 行を引いているからです。減らせるのは**回数**です。一覧のエンドポイントは 20 件の商品を返すために、出品者を 1 件ずつ 20 回引いています。いわゆる N+1 です（第 267 回）。

ISUCON13 で 2 位になった織時屋（traP）の記録にも、同じ型の判断があります（[ISUCON13で2位になりました(織時屋)](https://trap.jp/post/2049/)）。

> slow queryでthemes, users, iconsへの単純SELECTクエリがそれぞれ5万件ほど飛んでおり、user timeでトップなので@tokiがキャッシュする

1 回ずつは速い「単純 SELECT」が、回数のせいで最上位にいる。直し方はインデックスではなく、キャッシュ（第 269 回）や、まとめて引くこと（第 267 回）です。

ただし、スロークエリログには「その 96,276 回が、どの要求から何回ずつ呼ばれたのか」は書かれていません。1 件の要求が 20 回呼んでいるのか、2 万件の要求が 1 回ずつ呼んでいるのかで、直し方は変わります。この区別を付ける方法は第 265 回で扱います。

### フィンガープリントが隠すもの

フィンガープリントは、リテラルの値を `?` に置き換えてまとめます。だからこそ数万件のログを数行に要約できるのですが、**値によって計画が変わるクエリでは、性質の違う実行を 1 行に混ぜてしまいます**。平均の 20 ミリ秒は、0.3 ミリ秒の実行と 27 ミリ秒の実行の加重平均で、どちらの実行の姿でもありません。

この種のクエリを見分ける手掛かりは、報告の中にあります。

- **最小と最大の差が桁で違う**（調べた行数 20 と 49,800）
- **実行時間の分布の山が 2 つある**
- **V/M（ばらつきの指標）が大きい**（今回は 0.01 と小さく出ていて、これだけでは気付けませんでした）

気付いたら、報告の末尾の実例だけでなく、遅い側と速い側の実例を両方 `EXPLAIN` にかけます。一覧の直し方（`OFFSET` を使わずに、前のページの最後のキーから続きを取る）は第 273 回で扱います。

## 書き込みの時間

インデックスを張った後の 1 位は `INSERT comments` で、1 回平均 58 ミリ秒でした。調べた行数は 0 行で、行を探す費用はありません。

MySQL 8.0 の既定の設定（`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`）では、トランザクションをコミットするたびに、InnoDB のログとバイナリログをディスクへ同期します。試しに、この 2 つを `SET GLOBAL` で緩めた状態（`2` と `0`）と元の状態で 15 秒ずつ負荷をかけ、performance_schema で `INSERT` の平均を見ました。

| 同期を緩めた（`2`、`0`） | 237 | 6.542 ms |

## 本番で使うとき

**`long_query_time = 0` の費用。** すべてのクエリを書くと、ログの量は要求の数に比例します。今回、インデックスを張った後の 30 秒間のログは 29,236,213 バイト（120,577 件）でした。1 時間続ければ約 3.5 GB です。ISUCON11 本選で優勝した fujiwara組の sfujiwara さんは、終盤の改善として「最後にダメ押しで今までずっと有効にしていた MySQL の slow query log を無効化して更に数字を伸ばした」と書いています（[ISUCON11で優勝しました](https://sfujiwara.hatenablog.com/entry/isucon11-final)）。費用の大きさは第 265 回で測り、止め忘れの扱いは第 278 回で扱います。

本番では、閾値を数百ミリ秒程度にして遅いものだけをログに書き、回数の多い速いクエリは performance_schema の集計で見る、という分担が現実的です。performance_schema の表はサーバーのメモリ上の集計なので、ファイルの書き込みは増えません。定期的に読み出して差分を取れば、時間ごとの推移も作れます。

**ログに残る値。** スロークエリログは、リテラルの値を含む SQL をそのまま書きます。利用者のメールアドレスで検索するクエリなら、そのアドレスがログに残ります。ログの保存先と保存期間は、アクセスログと同じく、何が書かれうるかで決めます。performance_schema のダイジェストは、リテラルを `?` に置き換えた形で持ちます。

**補足の項目。** MySQL 8.0.14 からは `log_slow_extra` を有効にすると、送受信したバイト数（`Bytes_sent` など）、行の読み方ごとの回数（`Read_key`、`Read_rnd_next` など）、並べ替えの回数と行数（`Sort_rows` など）、作った一時表の数（`Created_tmp_disk_tables` など）がファイルに追加されます（[MySQL 8.0 Reference Manual: The Slow Query Log](https://dev.mysql.com/doc/refman/8.0/en/slow-query-log.html)）。表を頭から読んだのか、並べ替えにディスクの一時表を使ったのかなど、`Rows_examined` だけでは分からない費用の手掛かりになります。

**ログの切り替え。** ベンチマークや計測期間ごとにログを分けたいときは、ファイルの名前を変えてからログを切り替えさせます。MySQL の文書は「rename the current log file first before flushing it. At flush time, the server opens the new log file with the original name.」と説明しています（[MySQL 8.0 Reference Manual: Server Log Maintenance](https://dev.mysql.com/doc/refman/8.0/en/log-file-maintenance.html)）。切り替えは `FLUSH LOGS` 文や `mysqladmin flush-logs` で行います。動いている MySQL が開いているファイルを外から空にすると、MySQL は前に書いていた位置から書き続けることがあり、先頭が空白（NUL）で埋まったファイルになります。手元の実験でも、30 秒ぶんのログが実際の内容の 2 倍の大きさになりました。

## 次の回へ

この回では、データベースの時間をどの SQL が使っているかを集計しました。けれど、`SELECT users` の 96,276 回がどの要求から来たのか、データベースの外（アプリケーションとの往復や、アプリケーション自身の処理）でどれだけ時間を使っているのかは、スロークエリログには書かれていません。次の第 265 回では、リクエスト ID を使ってアクセスログとスロークエリログを 1 件ずつ結び、プロファイルと合わせて、1 件の要求の時間がどこで使われているのかを見ます。

## まとめ

- スロークエリログは、`long_query_time` 秒より長くかかった SQL を、実行時間・ロック時間・返した行数・調べた行数とともに記録する
- 閾値を 0 にしてすべてのクエリを記録すると、1 回は速いが回数の多いクエリも見える。遅いクエリだけを見ていると、データベースが空いたと誤解しやすい
- `long_query_time` の接続ごとの値は、接続した瞬間に全体の値から写される。`SET GLOBAL` の後は、接続を張り直すまで効かない
- pt-query-digest は、リテラルを `?` に置き換えたフィンガープリントで SQL をまとめ、既定で実行時間の合計の順に並べる
- 返した行数に対する調べた行数の比は、インデックスの過不足の手早い目安。ただし集計、`LIMIT` で止まる検索、返す行が多すぎるクエリでは読み替える
- performance_schema の `events_statements_summary_by_digest` は、ログを書かずに同じ集計をサーバーの中で持つ。手元の MySQL 8.0.46 では、サーバー側のプリペアドステートメントで実行された文はこの表に載らなかった
- 同じ実行でも、スロークエリログと performance_schema で時間の値は一致しない。順位を読み、絶対値は同じ道具の中で比べる
- 遅いクエリを直すと、回数の多い速いクエリが上位に浮かぶ。直すべきは 1 回の速さではなく回数で、手はインデックスではなく呼び方の変更
- フィンガープリントは値の違いを捨てる。値によって実行計画が変わるクエリは、最小と最大の差や分布の山の数で見分け、両側の実例を `EXPLAIN` にかける
- 調べた行数が 0 でも遅い書き込みは、コミット時のディスクへの同期を待っていることがある。インデックスでは直らない
- 本番では、ファイルのログは閾値を上げて遅いものだけにし、回数の多いクエリは performance_schema で見る。ログにはリテラルの値が残る
