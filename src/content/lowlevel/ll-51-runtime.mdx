## 1 行の裏にいる 4 人

```bash
docker run --rm alpine:3.20 echo hello
```

この 1 行で、コンテナが作られ、`echo` が動き、コンテナが消えます。これを 1 つのプログラムがやっているわけではありません。**役割の違う 4 つのプログラムが、順にバトンを渡しています。**

```
 docker（CLI）        コマンドを解釈して、API を呼ぶだけ
    │  HTTP（/var/run/docker.sock）
    ▼
 dockerd              Docker の API、ネットワーク、ボリューム、ビルド
    │  gRPC
    ▼
 containerd           イメージの取得と展開、コンテナの管理
    │  fork / exec
    ▼
 containerd-shim      コンテナ 1 つにつき 1 つ。最後まで残る
    │  fork / exec
    ▼
 runc                 名前空間と cgroup を作り、execve して消える
    │
    ▼
 echo hello           コンテナの中の PID 1
```

`docker` コマンド自体は、デーモンに HTTP でリクエストを送るクライアントにすぎません。`docker ps` が他のターミナルで起動したコンテナも表示できるのは、状態を持っているのが `dockerd` のほうだからです。

## なぜ分かれているのか

最初期の Docker は、これらを 1 つのデーモンで行っていました。分割が進んだのは、**それぞれを別の用途で使いたい人がいた**からです。

| 層 | 使う人 |
| --- | --- |
| dockerd | 開発者の手元。ビルド、Compose、ネットワークの管理まで欲しい |
| containerd | Kubernetes。イメージの取得とコンテナの管理だけで十分 |
| runc | あらゆるコンテナ実行環境。「名前空間を作って起動する」部分だけ欲しい |

Kubernetes のノードでは、多くの場合 dockerd はいません。kubelet が containerd を直接呼びます。**コンテナを動かすのに Docker は必須ではない**、ということです。

層の間の約束事は、OCI（Open Container Initiative）が仕様として決めています。前回のイメージの形式が **OCI Image Spec**、今回の runc が従う起動の約束が **OCI Runtime Spec** です。

## runc が受け取るもの

containerd は、前回見た層を overlayfs で重ねて 1 つのディレクトリを作り、そこに `config.json` を添えて runc に渡します。この組を **bundle** と呼びます。Runtime Spec では、bundle は `config.json` と、そこから参照されるルートファイルシステムからなると定められています（[OCI Runtime Spec: bundle](https://github.com/opencontainers/runtime-spec/blob/main/bundle.md)）。

```
bundle/
├── config.json     何を、どの名前空間で、どの制限で起動するか
└── rootfs/         overlayfs で重ねた / （イメージの層 + 書き込み層）
```

`config.json` の中身は、第 49 回で見た仕組みをそのまま JSON にしたものです。

```json
{
  "process": {
    "args": ["echo", "hello"],
    "env": ["PATH=/usr/local/sbin:..."],
    "cwd": "/",
    "user": { "uid": 0, "gid": 0 },
    "capabilities": { "bounding": ["CAP_CHOWN", "CAP_KILL", "..."] }
  },
  "root": { "path": "rootfs", "readonly": false },
  "linux": {
    "namespaces": [
      { "type": "pid" }, { "type": "mount" }, { "type": "network" },
      { "type": "uts" }, { "type": "ipc" }, { "type": "cgroup" }
    ],
    "resources": { "memory": { "limit": 536870912 }, "cpu": { "quota": 50000, "period": 100000 } },
    "seccomp": { "defaultAction": "SCMP_ACT_ERRNO", "syscalls": ["..."] }
  }
}
```

`docker run -m 512m --cpus 0.5` と書いたものは、`resources` の数字になって runc まで届きます。**Docker のオプションの大半は、最終的にこの JSON のどこかに落ちる**と考えると、見通しがよくなります。

runc がすることは、順番に並べるとこうなります。

1. `clone` で子プロセスを作る。このとき名前空間のフラグを渡す（第 31 回・第 49 回）
2. 子を cgroup に入れ、メモリや CPU の上限を書き込む
3. 子の中で、rootfs を `/` に据える（`pivot_root`）。`/proc` や `/dev` をマウントする
4. capability を削り、seccomp のフィルタを設定する（第 58 回）
5. `execve` で `echo` に置き換わる

最後の `execve` で、runc の子プロセスは `echo` そのものになります。第 30 回で見た **fork して exec する** 流れと同じです。違うのは、fork と exec の間に、見える範囲と使える量を制限する手順が挟まっていることだけです。

## runc は消え、shim が残る

runc は、コンテナのプロセスを起動したら **終了します**。常駐しません。

では、起動したプロセスの親は誰になるのか。手元の Docker Desktop の Linux VM で、ホスト側の PID 名前空間からプロセスの親子関係を見てみます。

```bash
$ docker run --rm --pid=host alpine:3.20 ps -o pid,ppid,args
  PID  PPID  COMMAND
  260   133  /usr/bin/containerd --config /etc/containerd/containerd.toml
  276   133  /usr/local/bin/dockerd --config-file /run/config/docker/daemon.json
26754     1  /usr/bin/containerd-shim-runc-v2 -namespace moby -id d2d2e141c3a2...
26855 26791  postgres
26791     1  /usr/bin/containerd-shim-runc-v2 -namespace moby -id fa80e4cf8a4f...
68414     1  /usr/bin/containerd-shim-runc-v2 -namespace moby -id 97bcbe305f98...
68437 68414  ps -o pid,ppid,args
```

いくつかのことが分かります。

- コンテナのプロセス（`postgres` や、この `ps` 自身）の親は `containerd-shim-runc-v2` である
- shim の親は containerd ではなく、PID 1 である。shim は containerd から切り離されて動いている
- runc はどこにもいない

**shim は、コンテナのプロセスの親として残り続けるための小さなプログラム**です。containerd の文書では、shim は containerd から命令を受け、fork / exec で runc を起動し、コンテナの終了をイベントとして報告し、入出力を受け渡すものとされています（[containerd: Runtime v2](https://github.com/containerd/containerd/blob/main/docs/runtime-v2.md)）。

親として残る理由は、第 30 回の **回収** です。

- コンテナのプロセスが終了したとき、その終了ステータスを `wait` で受け取る親が要る
- 標準出力と標準エラーを受け取り、`docker logs` に流す誰かが要る

これを containerd 自身が親として担うと、**containerd を再起動したとき、全コンテナが道連れになります**。shim を挟めば、containerd や dockerd を更新のために止めても、コンテナは動き続けます。shim が 1 コンテナにつき 1 つあるのは、この切り離しのためです。

<Callout type="note" title="shim の名前はランタイムの名前から決まる">
  containerd は、`io.containerd.runc.v2` のようなランタイム名から、
  `containerd-shim-runc-v2` という実行ファイル名を組み立てて起動します（同じ文書）。
  名前を変えれば、runc 以外のランタイムにも差し替えられます。この回の後半で使います。
</Callout>

## PID 1 は特別扱いされる

runc が `execve` した結果、アプリケーションはコンテナの中で **PID 1** になります。第 49 回の PID 名前空間のためです。

普通の Linux で PID 1 は init（systemd など）の席です。カーネルは PID 1 を特別に扱います。その扱いが、アプリケーションを PID 1 にしたとき、2 つの問題を起こします。

### 問題 1: シグナルが効かない

第 41 回で見たとおり、シグナルには **既定の動作** があります。SIGTERM の既定の動作は「終了」です。ハンドラを登録していないプロセスに SIGTERM を送れば、終了します。

ところが PID 1 は例外です。**名前空間の PID 1 は、ハンドラを登録していないシグナルを、同じ名前空間の中から送られても無視します**。init がうっかり殺されるとシステム全体が止まるので、カーネルが守っているのです。

コンテナの中から確かめてみます。

```bash
$ docker run --rm alpine:3.20 sh -c 'kill -TERM 1; kill -KILL 1; echo "PID 1 はまだ生きている"'
PID 1 はまだ生きている
```

`sh` は PID 1 で、SIGTERM のハンドラを持っていません。SIGTERM も、名前空間の中から送った SIGKILL も、無視されました。

`docker stop` は、まず SIGTERM を送り、既定で 10 秒待ってから SIGKILL を送ります。アプリケーションが SIGTERM のハンドラを持っていないと、SIGTERM は無視され、**毎回 10 秒待たされたうえで強制終了**されます。後片付けの処理も走りません。

<Callout type="tip" title="ホストからの SIGKILL は効く">
  カーネルが無視するのは、同じ名前空間の中から送られたシグナルです。
  親の名前空間（ホスト）から送られた SIGKILL と SIGSTOP は、PID 1 でも止められません。
  10 秒後の SIGKILL が最終的に効くのはこのためです。
</Callout>

### 問題 2: ゾンビが溜まる

第 30 回で、親が先に死んだ孤児は PID 1 に引き取られ、PID 1 が `wait` で回収する、と書きました。コンテナの中では、**アプリケーションがこの役を押し付けられます**。

アプリケーションが子プロセスを作り（シェルスクリプトを呼ぶ、ヘッドレスブラウザを起動するなど）、その子がさらに孫を作って先に終わると、孫はアプリケーションに引き取られます。アプリケーションは自分が親になった覚えのないプロセスを `wait` しないので、ゾンビとして残り続けます。

### 対策: 小さな init を PID 1 に置く

両方の問題を同時に解決するのが、**PID 1 の仕事だけをする小さなプログラム**を挟むことです。

```bash
$ docker run --rm --init alpine:3.20 ps -o pid,comm
PID   COMMAND
    1 docker-init
    7 ps
```

`--init` を付けると、`docker-init`（中身は tini）が PID 1 になり、アプリケーションはその子になります。tini は、受け取ったシグナルを子に転送し、孤児を回収し、子が終了したらその終了ステータスで自分も終了します。アプリケーションは PID 1 ではなくなるので、シグナルの既定動作が普通に効きます。

## exec 形式と shell 形式

Dockerfile の `CMD` と `ENTRYPOINT` には、書き方が 2 つあります。この違いも PID 1 に効きます。

```dockerfile
CMD ["node", "server.js"]     # exec 形式
CMD node server.js            # shell 形式
```

| 形式 | config.json の `args` | PID 1 になるもの |
| --- | --- | --- |
| exec 形式 | `["node", "server.js"]` | `node` |
| shell 形式 | `["/bin/sh", "-c", "node server.js"]` | `/bin/sh`（ただしシェルによる） |

shell 形式では、PID 1 がシェルになることがあります。シェルは SIGTERM を子に転送しないので、`docker stop` のシグナルが `node` に届きません。exec 形式を使うのが基本です。

<Callout type="warn" title="起動スクリプトを挟むときは exec で置き換える">
  環境変数の準備などのために、起動スクリプトを挟むことがあります。
  その最後は、`exec` で本体に置き換わるように書きます。

```sh
#!/bin/sh
set -e
export DATABASE_URL="..."
exec node server.js    # シェルが node に置き換わり、node が PID 1 になる
```
  `exec` を付け忘れると、シェルが PID 1 に居座り、シグナルが本体に届きません。
</Callout>

## runc 以外のランタイム

shim の名前を差し替えれば、runc 以外の実行方法を選べます。第 49 回で名前だけ出したものが、ここに入ります。

| ランタイム | 何をするか | 分離の強さ |
| --- | --- | --- |
| **runc** | 名前空間 + cgroup。既定 | カーネルを共有 |
| **crun** | runc と同じ仕様を C で実装。起動が速く、メモリが少ない | 同上 |
| **gVisor**（runsc） | システムコールをユーザ空間のカーネルで受け、ホストのカーネルに届く数を減らす | 中間 |
| **Kata Containers** | コンテナごとに軽量 VM を起動し、その中で動かす | VM 相当 |
| **runwasi** | コンテナの代わりに Wasm モジュールを Wasm ランタイムで動かす | Wasm のサンドボックス |

どれも containerd から見れば **同じ形の shim** です。イメージの取得、層の展開、ログの受け渡しは共通で、最後に「何で動かすか」だけが違います。

**runwasi** は containerd のサブプロジェクトで、Wasm のワークロードを、containerd から直接、あるいは Kubernetes の kubelet 経由で動かすためのものです（[containerd/runwasi](https://github.com/containerd/runwasi)）。第 45 回の Wasm ランタイム（Wasmtime、WasmEdge など）を shim の中に組み込み、`io.containerd.wasmtime.v1` のようなランタイム名で呼び出します。イメージの層に入っているのが Linux の実行ファイルではなく `.wasm` ファイルで、runc の代わりに Wasm ランタイムがそれを実行する、という違いです。

<Callout type="note" title="Docker Desktop の Wasm 機能は非推奨">
  Docker Desktop は、こうした Wasm 用の shim を同梱して `docker run --runtime=io.containerd.wasmtime.v1`
  のように使える機能を提供していました。しかし現在、この機能は非推奨で、
  将来の版で削除されると公式文書に明記されています（[Docker Docs: Wasm workloads](https://docs.docker.com/desktop/features/wasm/)）。
  containerd と runwasi を直接使う道は残っています。
</Callout>

## macOS や Windows では、どこで動いているのか

ここまでの話はすべて Linux のカーネルの機能です。macOS には名前空間も cgroup もありません。

では Mac の Docker Desktop は何をしているのかというと、**Linux の仮想マシンを 1 台起動し、その中で dockerd と containerd を動かしています**。`docker` コマンドだけが macOS 側にあり、VM の中の dockerd にソケット越しに話しかけています。

```bash
$ docker info --format '{{.OperatingSystem}} / {{.KernelVersion}}'
Docker Desktop / 6.12.72-linuxkit
```

カーネルのバージョンが Linux のものになっています。上の `ps` で見えた PID 1 の `/initd` も、この VM の init です。

```
 macOS
 ├── docker（CLI）
 └── Linux VM（Docker Desktop が起動）
     ├── dockerd / containerd
     └── containerd-shim ─ コンテナ
```

**Mac で動かすコンテナは、仮想マシンの中のコンテナ**です。第 49 回の 2 つの分離が、両方とも使われています。ファイル共有が遅い、ポートの見え方が Linux と違う、といった Mac 特有の問題は、この VM の境界から来ています（第 54 回）。

## まとめ

- `docker run` の裏では、CLI → dockerd → containerd → shim → runc と順にバトンが渡る
- runc は、bundle（config.json + rootfs）を受け取り、clone、cgroup、pivot_root、seccomp、execve の順に進めて終了する。この約束が OCI Runtime Spec
- shim はコンテナのプロセスの親として残り、終了ステータスの回収と入出力を担う。これにより containerd を止めてもコンテナは止まらない
- 名前空間の PID 1 は、ハンドラのないシグナルを無視し、孤児の回収を押し付けられる。`--init`（tini）で解決する
- `CMD` は exec 形式で書き、起動スクリプトの最後は `exec` で本体に置き換える
- shim を差し替えると、crun、gVisor、Kata、runwasi などに実行方法を変えられる
- Mac や Windows の Docker Desktop は、Linux VM の中でコンテナを動かしている

次は、このイメージを自分で作る側に回ります。Dockerfile の 1 行が、どう層になり、どうキャッシュされるのかを見ます。
