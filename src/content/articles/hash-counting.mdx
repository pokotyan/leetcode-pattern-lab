## 「あるかどうか」を毎回確認するのは、実はとても重い

こんな問題を考えます。

> `nums = [2, 7, 11, 15]` から、足すと `target = 9` になる2つの数字を探してください。ただし今回は、配列がソートされているとは限りません。

Two Pointers の記事で見た問題とよく似ていますが、**ソートされていない**というのが違いです。ソートされていない配列に対して、Two Pointers はそのままでは使えません（両端から寄せる根拠だった「単調性」が無いからです）。

素直に考えると、また二重ループに戻ってしまいます。`nums[i]` を1つ選んで、残りの要素の中から `target - nums[i]` になる値を探す。「探す」という部分を配列に対してそのまま行うと、毎回配列の先頭から末尾まで見て回ることになり、これが O(N) かかります。全体では O(N²) です。

## 発想：探す代わりに、先に置いておく

ここで欲しいのは、「この値はすでに配列の中にあるか？」を、**配列を端から端まで見なくても**答えられる仕組みです。それを実現するのがハッシュテーブル（Python では辞書 `dict` や集合 `set`）です。ハッシュテーブルへの追加・検索は、平均するとどちらも O(1) で済みます。

`nums = [2, 7, 11, 15]`、`target = 9` を例に、配列を1回だけ順番に見ながら考えてみます。

1. `i=0`：`nums[0] = 2`。あと `9 - 2 = 7` があれば target になります。でも、まだ何も辞書に入っていないので、`7` はまだ見つかりません。**とりあえず `2` を辞書に記録しておきます。**
2. `i=1`：`nums[1] = 7`。あと `9 - 7 = 2` があれば target です。**辞書を見ると、さっき記録した `2` がちょうどあります。** これで答えが見つかりました。

「先に見た値を辞書に置いておき、後から来た値がその相手を探しに来る」という順番になっているのがポイントです。これなら配列を1回なめるだけで済むので、O(N) で解けます。

```python
def two_sum(nums, target):
    seen = {}                      # 値 -> index
    for i, num in enumerate(nums):
        need = target - num
        if need in seen:
            return [seen[need], i]  # 探していた相手が過去に見つかっていた
        seen[num] = i               # 今の値も、将来の相手のために記録しておく
    return []
```

<Callout type="tip" title="なぜ「先に探して、後で記録する」順番なのか">
  もし「先に記録してから探す」順番にしてしまうと、`nums = [3, 3]`、`target = 6` のような入力で、`nums[0]` 自身を `nums[0]` の相手として見つけてしまいます（同じ要素を2回使うのは反則です）。
  「まず探してから、自分を記録する」という順番にしておけば、**自分より前にある要素としか一致しない**ので、この問題は自然に起きません。
</Callout>

## カウントの道具としてのハッシュテーブル

ハッシュテーブルのもう1つの得意技が、「何かの出現回数を数える」ことです。Python では `dict` を自分で使う書き方と、`collections.Counter` を使う書き方があります。

```python
from collections import Counter

count = Counter(["a", "b", "a", "c", "b", "a"])
# Counter({'a': 3, 'b': 2, 'c': 1})
```

`Valid Anagram`（2つの文字列が同じ文字の並べ替えかどうか）は、両方の文字列で文字のカウントを取って、それが完全に一致するかどうかを見るだけで解けます。`Group Anagrams` では、「ソートした文字列」や「26文字それぞれの出現回数をタプルにしたもの」を**キー**として使い、同じキーを持つ単語同士を辞書でグルーピングします。「何をキーにすれば、同じグループのものが同じキーになるか」を考えるのがこのタイプの問題のコツです。

## 集合で O(N) にする：Longest Consecutive Sequence

ここまでよりも一段難しい問題を見てみます。

> `nums = [100, 4, 200, 1, 3, 2]` から、連続する整数の列（順番はバラバラでもよい）のうち、一番長いものの長さを求めてください。

この例では `1, 2, 3, 4` が連続しているので答えは `4` です。

一番素直な方法は、配列をソートしてから連続する部分を数えることです。これなら O(N log N) で解けますが、実はソートすら要りません。**集合を使えば O(N) で解けます。**

考え方のポイントは、「**列の先頭になる値からだけ**数え始める」ということです。たとえば `4` は、`1, 2, 3, 4` という列の途中にあります。もし `4` から「4はあるか、5はあるか、6はあるか……」と数え始めてしまうと、後で `1` から数え始めたときにもう一度同じ列を数えることになり、無駄です。

ある値 `x` が「列の先頭」かどうかは、**`x - 1` が集合の中に無いかどうか**で判定できます。`x - 1` があるなら、`x` はその列の途中の値だということなので、スキップします。`x - 1` が無いなら、`x` はどこにも属さない新しい列の先頭なので、そこから `x+1`、`x+2`、……と集合にある限り伸ばしていきます。

```python
def longest_consecutive(nums):
    num_set = set(nums)
    best = 0
    for x in num_set:
        if x - 1 in num_set:
            continue          # x は列の途中。起点は他にある
        # x が列の先頭のときだけ、ここから伸ばす
        length = 1
        while x + length in num_set:
            length += 1
        best = max(best, length)
    return best
```

<Callout type="tip" title="なぜこれで O(N) だと言えるのか">
  「先頭からしか伸ばさない」という制約のおかげで、**どの数字も、生涯で高々1回しか `while` ループの中で調べられません。** 途中の値からは絶対に伸ばし始めないからです。
  一見すると `for` の中に `while` があるので重そうに見えますが、全体を通した `while` の実行回数の合計は、配列の要素数を超えません。この「全体で見ると各要素は定数回しか触られない」という考え方は、他の問題の計算量を見積もるときにもよく使います。
</Callout>

## この型の計算量

| 用途 | 時間 | 空間 |
| --- | --- | --- |
| 存在判定（Two Sum など） | O(N) | O(N) |
| カウント（Counter など） | O(N) | O(K)（K は種類数） |
| Longest Consecutive Sequence | O(N) | O(N) |

平均計算量が O(1) であることが前提になっている点には注意してください。最悪計算量（ハッシュの衝突が起きまくる場合）は O(N) になり得ますが、実際の面接ではほぼ平均計算量で評価して構いません。

## 「これはハッシュテーブルだ」と気づくためのサイン

- 「**存在するかどうか**を素早く判定したい」
- 「**出現回数**を数えたい」「**グループ分け**したい」
- 配列の要素の**順序は答えに関係ない**（関係あるなら、順序を保つ別の構造を検討します）
- 二重ループの内側が「探す」だけの処理になっている → ハッシュテーブルで置き換えられないか疑う

<Callout type="warn" title="ハッシュ化できないものはキーにできない">
  Python では、リストのような「中身を変更できる（mutable な）」オブジェクトは、辞書のキーや集合の要素にはできません。キーにしたい場合はタプルに変換してください（`tuple(sorted(word))` のように）。地味にハマりやすいポイントです。
</Callout>
