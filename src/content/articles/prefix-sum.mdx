## 「区間の和を何度も聞かれる」と、何が困るのか

こんな場面を考えてみてください。

> `nums = [3, 1, 4, 1, 5, 9]` があります。「index 1 から 4 までの合計は？」「index 0 から 2 までの合計は？」というクエリが、次々とたくさん飛んできます。

素直に答えるなら、クエリのたびに `sum(nums[l:r+1])` を呼べばいいはずです。でもこれは、1回のクエリに O(N) かかります。クエリが Q 回来るなら、全部で O(NQ) です。N も Q も大きい問題では、これでは間に合いません。

前の記事の Sliding Window は「端から順番に1つずつずらす」場合には強い味方でしたが、**今回のように「index 1〜4」「index 0〜2」のように、あちこち飛び回って区間を聞かれる**場合には向いていません。窓を毎回ゼロから作り直すことになってしまうからです。

## 発想：先に「ここまでの合計」を全部計算しておく

ここで使うのが累積和です。考え方はとてもシンプルです。**クエリが来るたびに毎回計算するのをやめて、先に「配列の先頭から i 番目までの合計」を全部計算して、配列として持っておく**のです。

`nums = [3, 1, 4, 1, 5, 9]` に対して、`prefix[i]` を「`nums` の先頭から `i` 番目の直前までの合計」と定義してみます。

| i | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| prefix[i] | 0 | 3 | 4 | 8 | 9 | 14 | 23 |

`prefix` の長さが `nums` より1つ長いことに注目してください。`prefix[0] = 0` は「まだ何も足していない」という状態を表す番兵です。これがあることで、あとの計算がとてもきれいになります。

区間 `[l, r]` の合計を求めたいときは、こう考えます。

> `prefix[r+1]` は「先頭から r 番目まで」の合計、`prefix[l]` は「先頭から l-1 番目まで」の合計です。この2つを引き算すれば、`nums[l]` から `nums[r]` までだけがちょうど残ります。

つまり `nums[l] + ... + nums[r] = prefix[r+1] - prefix[l]` です。実際に `l=1, r=4` で確かめてみましょう。`prefix[5] - prefix[1] = 14 - 3 = 11`。手で足すと `1 + 4 + 1 + 5 = 11` で、確かに一致します。

```python
def build_prefix(nums):
    prefix = [0]
    for x in nums:
        prefix.append(prefix[-1] + x)
    return prefix

def range_sum(prefix, l, r):
    # nums[l] から nums[r] までの合計
    return prefix[r + 1] - prefix[l]
```

`prefix` を作るのに O(N) かかりますが、これは**最初に1回だけ**です。作ってしまえば、どんなクエリが何回来ても、1回あたり O(1) の引き算で答えられます。

<Callout type="tip" title="Sliding Window との使い分け">
  「区間の端から端まで、順番に1つずつずらしながら見ていきたい」なら Sliding Window のほうが、追加の配列を作らないぶん軽量です。
  「あちこちの区間について、何度も自由に問い合わせたい」なら累積和のほうが向いています。**どちらも「毎回ゼロから計算し直す無駄をなくす」という同じ発想の、違う形**だと捉えておくと覚えやすいです。
</Callout>

## 累積和とハッシュテーブルを組み合わせる

ここからが本題です。累積和の本当の強さは、単に区間クエリに答えるだけでなく、**ハッシュテーブルと組み合わせて「条件を満たす部分配列の個数」を数える**場面で発揮されます。

> `nums` から、合計がちょうど `k` になる連続する部分配列が何個あるか数えてください。ただし `nums` には負の数が含まれることもあります。

まず、なぜ Sliding Window が使えないのかを確認しておきます。Sliding Window がうまくいくのは「窓を伸ばすと合計が単調に増える」という前提があるときでした。負の数が混ざっていると、窓を伸ばしても合計が増えたり減ったりするので、「縮めるべきかどうか」を判断できません。だからこの問題には累積和を使います。

考え方はこうです。左から `right` まで見たときの累積和を `cur` とします。もし**過去のどこかの累積和が `cur - k` だった**なら、その位置から `right` までの区間の合計は、ちょうど `k` になります。なぜなら、区間の合計は「今の累積和」から「区間の直前までの累積和」を引いたものだからです。

具体例で見てみます。`nums = [1, 2, 3]`、`k = 3` としましょう。累積和を左から計算していくと `1, 3, 6` と変化します。

- `right=0`：`cur = 1`。`cur - k = 1 - 3 = -2`。過去に -2 という累積和は無いので該当なし
- `right=1`：`cur = 3`。`cur - k = 0`。**過去に累積和0（何も足していない状態）があった**ので、そこから今までの区間 `[0,1]`、つまり `[1, 2]` が合計3になっている。カウント+1
- `right=2`：`cur = 6`。`cur - k = 3`。**過去に累積和3（`right=1` のとき）があった**ので、そこから今までの区間、つまり `[3]` が合計3になっている。カウント+1

最終的に2個見つかります。「過去のどの累積和が何回出たか」を効率よく調べるために、ハッシュテーブルを使います。

```python
def subarray_sum(nums, k):
    count = 0
    cur = 0
    seen = {0: 1}          # 累積和 -> 出現回数（まだ何も足してない=0 が1回）
    for num in nums:
        cur += num
        # cur - k がこれまでに出ていれば、そこから今までが合計kの部分配列
        count += seen.get(cur - k, 0)
        seen[cur] = seen.get(cur, 0) + 1
    return count
```

<Callout type="warn" title="seen = {0: 1} を忘れると、先頭からの区間を数え損ねます">
  さきほどの例で `right=1` のとき、なぜ `cur - k = 0` が「見つかった」ことになったか思い出してください。これは、**まだ何も足していない状態（累積和0）を、あらかじめ1回分カウントしておいた**からです。
  もし `seen = {}` から始めてしまうと、「配列の先頭からぴったり k になる区間」を1つ見逃してしまいます。この初期値は、地味ですが忘れるとテストケースの一部だけ落ちる、という形でバグが出るので要注意です。
</Callout>

## この型の計算量

| 用途 | 時間 | 空間 |
| --- | --- | --- |
| 累積和の構築 | O(N) | O(N) |
| 構築後の1回のクエリ | O(1) | — |
| 累積和 + ハッシュテーブル | O(N) | O(N) |

累積和を作るところは一度だけ O(N)、そのあとのクエリはすべて O(1) というのが、累積和の一番の強みです。

## 「これは累積和だ」と気づくためのサイン

- 「連続する部分配列の合計」について、**何度も問い合わせる**（1回だけなら愚直に足せばいい場合もあります）
- 「合計がちょうど k になる部分配列は何個？」という、**個数を数える**問題
- 配列に**負の数が混ざっていて**、Sliding Window の「単調に増える」という前提が崩れている
- 二次元配列で「長方形領域の合計」を求めたい（この場合は縦横2方向の累積和を組み合わせます）
