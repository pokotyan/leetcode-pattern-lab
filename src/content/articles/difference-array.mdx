## この記事を読む前に押さえておく型

- **累積和**：この記事の型は、累積和とちょうど逆向きの操作です。「差分を並べたものを累積和すると元に戻る」という関係そのものが根拠になっているので、累積和を先に体に入れておかないと、なぜ復元できるのかが分かりません

## まず、困っている状況を体験してみます

次の問題を考えます。

> 座席が `n = 5` 席ある飛行機に、予約が3件入りました。予約はそれぞれ「何席目から何席目までに、何人ぶん」という形で来ます。
> `[1, 2, 10]` は「1席目から2席目までに10人」、`[2, 3, 20]` は「2席目から3席目までに20人」、`[2, 5, 25]` は「2席目から5席目までに25人」です。
> 最終的に各座席が何人ぶん予約されているかを返してください。

素直に考えれば、予約を1件ずつ取り出して、その区間の座席を1つずつ回して足していけば終わりです。

```python
for first, last, seats in bookings:
    for i in range(first - 1, last):
        ans[i] += seats            # 区間の長さぶんループする
```

これで答えは確実に出ます。手元の例なら、足し算は合計で `2 + 2 + 4 = 8` 回です。何も問題ないように見えます。

問題は入力が大きくなったときです。この問題の制約では、座席数 `n` も予約件数もそれぞれ最大 20,000 件あります。予約1件が全席を覆っていた場合、内側のループは毎回 20,000 回まわります。つまり最悪で `20,000 × 20,000 = 4億回`。1秒間に1億回が目安なので、**4秒**ほどかかる計算です。制限時間を超えます。

ここで一度立ち止まって、何が無駄なのかを考えてみます。`[2, 5, 25]` という予約に対して、2席目、3席目、4席目、5席目と、同じ `+25` を4回書いています。**同じ値を、同じ回数だけ、律儀に書き写している**わけです。この繰り返しをやめられれば、計算は一気に軽くなります。

## 発想を変える：値そのものではなく「変わり目」だけを書く

累積和の記事で、「先に累積和を作っておけば、区間の和が引き算1回で出せる」という話をしました。あれは **配列 → 累積和** という向きの変換でした。

差分配列は、これをちょうど逆向きに使います。**先に「隣との差」だけを並べた配列を作っておき、最後に一度だけ累積和を取って元の配列に戻す**という考え方です。

なぜこれで区間の加算が速くなるのでしょうか。「区間 `[l, r]` に `v` を足す」という操作を、差の世界で見てみます。

- 区間の内側では、隣との差は**変わりません**。3席目と4席目が両方 `+25` されるなら、その2つの差は元のままです
- 変わるのは**区間の入口と出口だけ**です。`l` の位置で値が `v` だけ跳ね上がり、`r` の次の位置で `v` だけ元に戻ります

つまり、区間がどれだけ長くても、差の世界で書き換える必要があるのは**たった2マス**です。

```python
diff[l] += v        # ここから v だけ高くなる
diff[r + 1] -= v    # ここで元の高さに戻る
```

そして最後に `diff` の累積和を取れば、すべての予約を反映した本当の配列が出てきます。加算が M 件あっても書き込みは `2M` 回、復元が `N` 回なので、全体で **O(M + N)** です。さきほどの4億回が、4万回まで落ちます。

```python
def corp_flight_bookings(bookings, n):
    diff = [0] * (n + 1)
    for first, last, seats in bookings:
        diff[first - 1] += seats      # ここから seats 人増える
        diff[last] -= seats           # ここで元に戻す
    ans = []
    cur = 0
    for i in range(n):
        cur += diff[i]                # 差分を積み上げると実際の値になる
        ans.append(cur)
    return ans
```

## なぜ累積和を取ると元に戻るのか、数字で確かめます

「差だけ記録して、あとで足し上げれば戻る」と言われても、最初は納得しづらいところです。さきほどの例で実際に追いかけてみます。

予約は `[1,2,10]`、`[2,3,20]`、`[2,5,25]` の3件、`n = 5` です。`diff` は長さ6（`n + 1`）で、全部 0 から始めます。

1. `[1, 2, 10]`：座席1から増えるので `diff[0] += 10`。座席2を過ぎたら戻るので `diff[2] -= 10`。この時点で `diff = [10, 0, -10, 0, 0, 0]`
2. `[2, 3, 20]`：`diff[1] += 20`、`diff[3] -= 20`。`diff = [10, 20, -10, -20, 0, 0]`
3. `[2, 5, 25]`：`diff[1] += 25`、`diff[5] -= 25`。`diff = [10, 45, -10, -20, 0, -25]`

ここまで、書き込みは6回だけです。では左から足し上げていきます。

| i | diff[i] | 足し上げた cur | 意味 |
| --- | --- | --- | --- |
| 0 | 10 | 10 | 座席1は10人 |
| 1 | 45 | 55 | 座席2で20人と25人が加わって55人 |
| 2 | -10 | 45 | 座席3では1件目が抜けて45人 |
| 3 | -20 | 25 | 座席4では2件目も抜けて25人 |
| 4 | 0 | 25 | 座席5は変化なしで25人 |

答えは `[10, 55, 45, 25, 25]` です。素直に全部のマスへ足していったときと、ぴったり同じ結果になりました。

`cur` の正体は「その位置までの差を全部足した値」、つまり**その位置の高さ**です。差を足し上げれば高さに戻る、というのは階段を1段ずつ登るのと同じで、各段の高さの差を順に足していけば、いま何段目にいるかが分かります。

<Callout type="warn" title="番兵の1マスと、閉区間・半開区間の取り違え">
  差分配列のバグは、ほぼすべて**マイナスを書く位置**から出ます。

  - 問題文の区間が `[l, r]` の**閉区間**（r 番目も含む）なら、戻すのは `r + 1` の位置です。`diff[r] -= v` と書くと、r 番目だけ加算が漏れます
  - 半開区間 `[l, r)` で与えられる問題（Car Pooling の降車地点がこれです）なら、そのまま `diff[r] -= v` が正解です
  - 配列の長さは元の長さより**1つ長く**取ります。区間が末尾まで届いていると `r + 1` が配列の外に出てしまうためです。この余分な1マスは最後の復元で読まないので、値が入ったままでも答えには影響しません

  どちらの区間なのかは問題ごとに違います。書き始める前に、入力例1つを手で追って `r` 番目が含まれるかどうかを必ず確認してください。
</Callout>

## 上限の判定にそのまま使う：Car Pooling

差分配列は、答えの配列を返す問題だけの道具ではありません。**復元の途中で条件を確認する**という使い方が、そのまま別の問題になります。

> 定員 `capacity` の車で相乗りをします。各便は「`num` 人が地点 `start` で乗り、地点 `end` で降りる」という形で与えられます。車は一方向にしか進みません。全員を運べるなら `True`、どこかで定員を超えるなら `False` を返してください。

「各地点で車内に何人いるか」が分かれば判定できます。そして車内人数は、**地点ごとの乗り降りの増減を足し上げたもの**です。これは差分配列そのものです。

この問題では、乗客が乗っているのは `start` 以上 `end` 未満の区間です。`end` の地点ではもう降りているので、`diff[end] -= num` がそのまま正しくなります（さきほどの座席の問題と `-1` の位置が違うのは、この区間の取り方の違いによるものです）。

```python
def car_pooling(trips, capacity):
    diff = [0] * 1001
    for num, start, end in trips:
        diff[start] += num        # start で num 人乗る
        diff[end] -= num          # end で num 人降りる
    cur = 0
    for x in diff:
        cur += x                  # その地点にいる人数
        if cur > capacity:
            return False
    return True
```

配列の長さを 1001 に固定しているのは、この問題の制約で地点の番号が 1000 までと決まっているからです。地点の種類が決まっている問題では、入力を見ずに固定長で確保してしまうのが手軽です。

<CarPooling client:visible />

「降車と乗車が同じ地点」という入力を選んでみてください。地点5で3人が降りて2人が乗るとき、`diff[5]` には `-2 + 3` が両方書き込まれ、その地点の人数は正しく入れ替わります。**同じマスに複数の増減が重なっても、足し算なので順番を気にする必要がありません。** これが差分配列が扱いやすい理由の1つです。

<Callout type="tip" title="地点の番号が大きいときは座標圧縮">
  Car Pooling では地点が 1000 までと決まっていましたが、地点の番号が 10<sup>9</sup> まであるような問題では、固定長の配列は作れません。
  その場合は「実際に登場する地点だけを集めて、小さい番号に振り直す」という前処理（座標圧縮）をしてから差分配列を作るか、区間をイベントとして並べて処理する型に切り替えます。後者が次の記事で扱う内容です。
</Callout>

## この型の計算量

| やり方 | 時間 | 空間 | 内訳 |
| --- | --- | --- | --- |
| 素直に区間を回す | O(M × L) | O(N) | M は加算の件数、L は区間の長さ。区間が長いと破綻する |
| 差分配列 | O(M + N) | O(N) | 書き込みが 2M 回、復元が N 回 |
| 差分配列（座標圧縮つき） | O(M log M + M) | O(M) | 登場する地点のソートが支配的 |

注意したいのは、差分配列は**加算をすべて受け取り終えてから、最後に一度だけ復元する**型だという点です。「加算」と「値の問い合わせ」が交互に来る問題には使えません。その場合は、区間更新と区間取得の両方が O(log N) でできる構造（セグメント木や BIT）が必要になります。これは後の記事で扱います。

## 「これは差分配列だ」と気づくためのサイン

- 「**区間 `[l, r]` に一律で `v` を足す**」という操作が、何度も繰り返される
- 更新がすべて先に来て、**問い合わせは最後の1回だけ**（途中経過を聞かれない）
- 「予約」「乗車と降車」「イベントの開始と終了」「ある期間だけ有効」といった言葉が出てくる
- 素直に実装すると `件数 × 区間の長さ` になり、制約を掛け算すると1億を大きく超える
- 求めたいのが「各位置の最終的な値」や「どこかで上限を超えるか」である

<Callout type="warn" title="二次元にも同じ発想が使えます">
  グリッドの矩形領域に一律で加算する問題では、差分配列を二次元に広げます。矩形 `(r1, c1)` から `(r2, c2)` への加算は、四隅の4マスを書き換えるだけで表せます。

  ```python
  diff[r1][c1]         += v
  diff[r1][c2 + 1]     -= v
  diff[r2 + 1][c1]     -= v
  diff[r2 + 1][c2 + 1] += v
  ```

  最後に行方向と列方向へ順に累積和を取ると復元できます。符号が4つとも違うので、入力例を1つ手で追って確認してから提出してください。
</Callout>
