## なぜ BFS では最短距離が求まらなくなるのか

グラフ探索の記事で、「重みの無いグラフなら、BFS が最短距離を保証する」と説明しました。BFS がうまくいくのは、**キューに入れる順番が、そのまま距離の近い順になっている**からでした。

ところが、辺に**重み**（コスト）がついたグラフだと、これが崩れます。たとえば `A → B` に重み4の辺、`A → C` に重み1の辺、`C → B` に重み1の辺があるとします。BFS の感覚では「`A → B` は1歩だから近い」と思ってしまいますが、実際には `A → C → B` と2歩でも合計コストは2で、直接行くより安く済みます。**「歩数が少ない」と「コストが小さい」は、重みがあると一致しなくなる**わけです。

## ヒープで「一番近い未確定ノード」を選び続ける

BFS の代わりに使うのがダイクストラ法です。考え方の骨格は BFS とよく似ています。**「まだ確定していないノードの中で、一番近いものから確定させていく」**というものです。ただし「近い順」をキューではなく、**ヒープ（優先度付きキュー）**で管理します。ヒープを使えば、「今わかっている中で一番小さいコストのもの」を効率よく取り出せるからです（ヒープについては別の記事で扱いますが、ここでは「一番小さいものをすぐ取り出せる箱」とだけ理解しておけば十分です）。

> 重み付き有向グラフが与えられます。ノード `k` から出発して、すべてのノードに信号が届くまでにかかる時間（最も時間がかかったノードまでの距離）を求めてください。届かないノードがあれば `-1` を返します。

手順はこうです。

1. 始点の距離を0、それ以外を無限大として初期化する
2. ヒープから、**まだ確定していない中で一番距離が小さいノード**を取り出す
3. そのノードを確定させ、そこから出ている辺をたどって、隣のノードの距離が縮まるなら更新する（これを「緩和」と呼びます）
4. ヒープが空になるまで2〜3を繰り返す

```python
import heapq

def network_delay_time(times, n, k):
    graph = [[] for _ in range(n + 1)]
    for u, v, w in times:
        graph[u].append((v, w))
    dist = [float("inf")] * (n + 1)
    dist[k] = 0
    heap = [(0, k)]                    # (距離, ノード)
    while heap:
        d, u = heapq.heappop(heap)      # 未確定の中で最も近いものを取り出す
        if d > dist[u]:
            continue                     # 既にもっと良い記録がある。古い情報は無視
        for v, w in graph[u]:
            nd = d + w
            if nd < dist[v]:
                dist[v] = nd             # 緩和：もっと近い道が見つかった
                heapq.heappush(heap, (nd, v))
    m = max(dist[1:])
    return m if m < float("inf") else -1
```

「遠回りが最短になる」のプリセットで試してみてください。ノード1からノード2への直接の辺は重み4ですが、ノード3を経由すると `1 + 1 = 2` で、直接行くより安く済みます。ダイクストラ法は、この「遠回りしたほうが実は近い」パターンを自然に見つけ出します。

<Callout type="warn" title="ヒープに同じノードが複数回入ることがあります">
  コードを見ると、一度ヒープに入れたノードの距離をあとから更新する処理はしていません。同じノードについて、古い（大きい）距離のエントリと、新しい（小さい）距離のエントリが両方ヒープに残ることがあります。
  そこで `if d > dist[u]: continue` というチェックが必要です。**古いエントリが先に出てきても、すでにもっと良い記録があるなら無視する**ことで、正しさを保っています。この1行を忘れると、確定済みのノードをもう一度処理してしまい、結果は変わらないものの無駄な計算が増えます（正しさそのものは保たれますが、計算量が悪化します）。
</Callout>

## なぜ「確定させたノードは、もう更新されない」と言えるのか

ダイクストラ法の正しさは、**「ヒープから取り出す順番が、常に距離の小さい順になっている」**という一点に支えられています。ヒープから取り出された時点のノードは、その時点で「他のどの未確定ノードよりも記録が小さい」ことが保証されています。

もしこのノードの記録があとで縮まるとしたら、それは「今より短い経路が、他の未確定ノードを経由して見つかる」ということですが、辺の重みはすべて0以上なので、他のノードを経由すればするほど距離は増える一方です。**確定させた時点の記録より小さくなることは、理屈のうえであり得ません。** これが、確定したノードを二度と処理し直さなくてよい理由です。

<Callout type="warn" title="負の重みがあると、この理屈が壊れます">
  「経由すればするほど距離は増える」という前提は、辺の重みがすべて0以上だからこそ成り立ちます。負の重みの辺があると、確定させたはずのノードの記録が後から縮む可能性が出てくるため、ダイクストラ法は使えません。負の重みを扱いたい場合はベルマンフォード法という別のアルゴリズムを使いますが、コーディング面接で実装を求められることはまずありません。「負の重みがあると使えない」という制約を知っていれば十分です。
</Callout>

## この型の計算量

| 実装 | 時間 | 空間 |
| --- | --- | --- |
| ヒープを使う場合 | O(E log N) | O(N + E) |
| ヒープを使わない場合（密なグラフ向け） | O(N²) | O(N²) |

疎なグラフ（辺の数が少ない）ならヒープを使う方法が有利で、密なグラフ（辺の数がノード数の2乗に近い）なら、ヒープなしで全ノードを毎回線形に探す方法のほうが速くなることもあります。ただし面接で問われるのはほぼ疎グラフのケースなので、まずはヒープを使う形を確実に書けるようにしておいてください。

## 「これはダイクストラ法だ」と気づくためのサイン

- 「**重み付き**グラフ」で「**最短の**コスト・時間・距離」を求める
- すべての重みが**0以上**（負の数を含まない）
- 「確率の掛け算で最大を求めよ」のような、和ではなく**別の演算で最適値を追跡する**問題（`Path with Maximum Probability` のように、優先度の取り方を変えるだけで同じ骨格が使えます）
- 「あと k 回まで乗り継げる」のように、**状態を拡張**したダイクストラ（`Cheapest Flights Within K Stops`）
