## 状態が1つでは足りないとき

前の記事で見た一次元 DP は、`dp(i)` のように**1つの変数**だけを状態にしていました。ここからは、`dp(i, j)` のように**2つの変数の組み合わせ**を状態にする問題を見ていきます。

発想そのものは一次元 DP と何も変わりません。「何を状態にするか」「遷移式は何か」を決めるだけです。ただ、状態が2次元になった分、表（グリッド）としてイメージすると理解しやすくなります。

## グリッド上を移動する：Unique Paths

> `m × n` のグリッドがあります。左上のマスからスタートして、右か下にしか進めないロボットが、右下のマスまで行く道のりは何通りありますか。

あるマス `(i, j)` に注目してみます。ロボットは右か下にしか進めないので、`(i, j)` に来る方法は、**「上のマス `(i-1, j)` から来る」か「左のマス `(i, j-1)` から来る」の、2通りしかありません。** つまり `(i, j)` までの道のりの数は、この2つのマスまでの道のりの数を**足したもの**です。

一番上の行と一番左の列は、まっすぐ進むしかないので、必ず1通りです。ここが計算の出発点（初期条件）になります。

```python
def unique_paths(m, n):
    # dp[i][j]: (0,0) から (i,j) までの道のりの数
    dp = [[1] * n for _ in range(m)]   # 一番上の行と一番左の列は必ず1通り
    for i in range(1, m):
        for j in range(1, n):
            dp[i][j] = dp[i - 1][j] + dp[i][j - 1]  # 上から来るか、左から来るか
    return dp[-1][-1]
```

<UniquePathsGrid client:visible />

グリッドが左上から右下に向かって、1マスずつ数字で埋まっていく様子を見てください。それぞれのマスは、**すぐ上とすぐ左のマスの値を足すだけ**で求まっています。これが二次元 DP の一番シンプルな形です。

<Callout type="tip" title="行き先の数だけ、足し算する項が増えます">
  もし「右・下」に加えて「右下斜め」にも進めるロボットなら、遷移式は `dp[i][j] = dp[i-1][j] + dp[i][j-1] + dp[i-1][j-1]` と、足し算する項が1つ増えるだけです。「そのマスに来る方法が何通りあるか」を数え上げる、という考え方は変わりません。
</Callout>

## 文字列を2本扱う：Longest Common Subsequence

もう1つの典型的な二次元 DP を見てみます。今度はグリッドではなく、**2つの文字列**を扱います。

> 2つの文字列 `text1` と `text2` が与えられます。両方に共通して（順序を保ったまま、連続していなくてもよい）現れる、最長の部分列の長さを求めてください。

ここで `dp(i, j)` を「`text1` の最初の `i` 文字」と「`text2` の最初の `j` 文字」から作れる、最長共通部分列の長さ、と定義します。2つの文字列の「どこまで見たか」を、それぞれ別の軸として持つわけです。

新しい文字 `text1[i-1]` と `text2[j-1]` を追加で見たとき、何が起きるでしょうか。

- **2つの文字が一致する**なら、その文字を共通部分列に使えます。斜め上の `dp(i-1, j-1)` に、この一致した1文字ぶんを足します
- **一致しない**なら、今回追加した文字のどちらか一方（あるいは両方）は使えません。「`text1` 側を1文字諦めた場合（`dp(i-1, j)`）」と「`text2` 側を1文字諦めた場合（`dp(i, j-1)`）」のうち、**大きいほう**を採用します

```python
def longest_common_subsequence(text1, text2):
    m, n = len(text1), len(text2)
    dp = [[0] * (n + 1) for _ in range(m + 1)]
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            if text1[i - 1] == text2[j - 1]:
                dp[i][j] = dp[i - 1][j - 1] + 1   # 文字が一致。斜め上から+1
            else:
                dp[i][j] = max(dp[i - 1][j], dp[i][j - 1])  # 一致しない。上か左の良い方
    return dp[m][n]
```

<LongestCommonSubsequence client:visible />

`abcde` と `ace` の例で見てみると、`a`、`c`、`e` が一致するたびに、**表の中で斜め方向に値が1ずつ増えていく**のが確認できます。一致しないマスでは、上と左のうち大きいほうがそのまま引き継がれています。

<Callout type="warn" title="dp のサイズが (m+1) × (n+1) になる理由">
  `dp[0][j]` や `dp[i][0]` は、「片方の文字列が0文字（空文字列）のときの答え」を表しています。空文字列との共通部分列は当然0なので、これが初期条件になります。**この「0文字のとき」の行と列を用意しておくおかげで、`i=1`、`j=1` から場合分け無しで同じ式を使い回せます。** これは累積和の記事で見た「`prefix[0] = 0` という番兵」と同じ発想です。
</Callout>

## Edit Distance も同じ型です

`Edit Distance`（片方の文字列を、もう片方に変換するための最小編集回数を求める）も、`dp(i, j)` の定義こそ違いますが、骨格は `Longest Common Subsequence` とそっくりです。文字が一致すれば斜め上からそのまま引き継ぎ、一致しなければ「置換」「削除」「挿入」の3つの操作それぞれに対応する `dp(i-1, j-1)`、`dp(i-1, j)`、`dp(i, j-1)` の中から一番コストの低いものを選び、+1します。**「2つの文字列を、それぞれどこまで使ったか」を軸にする**という考え方が身につけば、この手の問題は初見でも構造が見えるようになります。

## ナップサック型：容量という軸を持つ

もう1つのパターンとして、`Partition Equal Subset Sum` のような「重さの制約の中で、何を選ぶか」という問題があります。ここでは `dp(i, w)` を「最初の `i` 個の中から選んで、重さ `w` 以下におさまるか（または最大価値はいくらか）」と定義します。**「何番目まで見たか」と「今使った容量」**の2つを軸にするという点で、これも二次元 DP の仲間です。

## この型の計算量

| 問題 | 時間 | 空間 |
| --- | --- | --- |
| Unique Paths | O(M · N) | O(M · N)（直前の行だけ持てば O(N) に削減可） |
| Longest Common Subsequence | O(M · N) | O(M · N)（同上） |
| ナップサック型 | O(N · W) | O(N · W)（同上） |

二次元 DP でも、「今の行の計算に、**直前の行だけ**あれば十分」というケースがほとんどです。その場合、空間計算量は1つ前の行を持つだけの O(N) まで削減できます。

## 「これは二次元 DP だ」と気づくためのサイン

- 「グリッド上を移動する」「格子状の盤面」
- **2つの文字列（または配列）**を比較しながら答えを求める
- 「何番目まで」に加えて、**容量・残り予算・使った回数**のような、もう1つの軸がある
- 一次元 DP を試して、遷移式を立てるのに情報が1つ足りないと感じたとき
