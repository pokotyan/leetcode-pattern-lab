## 知っている二分探索は、実はごく一部です

学校や入門書で最初に習う二分探索は、だいたいこんな形だったはずです。

> ソート済みの配列から、値 `x` が入っている位置を返してください。見つからなければ `-1`。

真ん中を見て、探している値より大きければ左半分、小さければ右半分……というやつです。これはこれで大事な基礎ですが、正直に言うと、**Medium で出るのはここではありません。** 実際に出てくるのは、こんな問題です。

- 値 `x` が配列の中に**複数ある**とき、その**一番最初の位置**を返してください
- `x` 以上の値の中で、**一番小さい**要素を返してください
- ある条件を満たす**最小の速度**を求めてください（配列すら与えられません）

「真ん中と比較して、大きいか小さいかで半分に絞る」という発想のままでは、これらは解けません。二分探索を、**「値を探す道具」ではなく「境界を探す道具」**として捉え直す必要があります。

## 二分探索の正体：境界を探すゲーム

こう考えてみてください。あなたの前に、`False, False, False, True, True, True` のように、**あるところを境にきっちり2つに分かれる**一列の答えが並んでいます。あなたの仕事は、その境目（最初に `True` になる位置）を見つけることです。

一列ぜんぶを端から確認すれば見つかりますが、それでは O(N) かかります。もし「今見ている位置が `True` か `False` か」を確認する方法さえあれば、**毎回半分ずつ候補を捨てながら**境目に迫っていけます。これが二分探索の正体です。配列である必要すらなく、`True`/`False` を判定できる条件さえあれば使えます。

## ok / ng 方式で書く

二分探索は理屈は簡単なのに、実装すると `mid + 1` か `mid` か、`<` か `<=` か、といった細かいところでよくバグります。これを避けるための、覚えやすい書き方を紹介します。

「探索範囲」を `lo`、`hi` で管理する代わりに、**「条件を満たすと分かっている候補 `ok`」と「条件を満たさないと分かっている候補 `ng`」**という2つの変数で管理します。

```python
ok, ng = 条件を必ず満たす値, 条件を必ず満たさない値
while abs(ok - ng) > 1:
    mid = (ok + ng) // 2
    if condition(mid):
        ok = mid
    else:
        ng = mid
return ok        # 条件を満たす限界
```

覚えることはこの3つだけです。

1. `ok` と `ng` の初期値には、**絶対に条件を満たす値／絶対に満たさない値**を置きます。配列の範囲外の番兵で構いません
2. ループの継続条件は `abs(ok - ng) > 1`。2つが隣り合ったら終わりです
3. 最後に返すのは `ok`

`abs()` を使っているのは、`ok` と `ng` のどちらが大きいかを毎回気にしなくて済むようにするためです。`ok` が右にあるケースと左にあるケースの両方を、同じコードでカバーできます。

### 実際に手を動かして、下界（lower bound）を求めてみます

「条件」を `nums[i] >= x` に決めると、この条件を初めて満たす位置（＝ `x` 以上の値が現れる最初の index）が求まります。これを下界（lower bound）と呼びます。

`nums = [1, 3, 3, 4, 4, 4, 4, 19]`、`x = 4` で、実際に手を動かしてみます。配列に届かない範囲を番兵として、`ok = 8`（配列の外だが「必ず成立」扱い）、`ng = -1`（これも範囲外で「必ず不成立」扱い）から始めます。

1. `mid = (8 + (-1)) // 2 = 3`。`nums[3] = 4 >= 4` は成立するので `ok = 3`
2. `mid = (3 + (-1)) // 2 = 1`。`nums[1] = 3 >= 4` は成立しないので `ng = 1`
3. `mid = (3 + 1) // 2 = 2`。`nums[2] = 3 >= 4` は成立しないので `ng = 2`
4. `ok = 3`、`ng = 2` は隣り合ったので終了。答えは `ok = 3`

```python
def lower_bound(nums, x):
    # 条件 P(i): nums[i] >= x
    ok, ng = len(nums), -1     # ok は範囲外だが「必ず成立」扱い
    while abs(ok - ng) > 1:
        mid = (ok + ng) // 2
        if nums[mid] >= x:
            ok = mid
        else:
            ng = mid
    return ok
```

<LowerBoundOkNg client:visible />

セルの下に表示される `T` / `F` は、その位置が条件 `nums[i] >= x` を満たすかどうかです。`F` が並んだあとに `T` が並ぶという、きれいな一列になっているのがわかります。この単調な並びがあるからこそ、境界が一意に決まります。

配列を見ると `4` が4つ並んでいますが、答えは**最初に4が現れる index 3**です。素直に `nums[mid] == x` で探す普通の二分探索では、こういう「複数ある中の最初」を求めることができません。

<Callout type="tip" title="上界（upper bound）も、まったく同じ形で書けます">
  条件を `nums[i] <= x` に変えて、`ok, ng = 0, len(nums)` から始めれば、条件を満たす**最大**の index（上界）が求まります。ループの中身は1文字も変えなくてよく、条件式と番兵の位置を入れ替えるだけです。
</Callout>

<Callout type="warn" title="ng は和製英語です">
  英語話者との面接では `ok` / `ng` ではなく、`ok` / `no`、あるいは `good` / `bad` という言い方を使うようにしてください。
</Callout>

## 単調に見えないときも、実は使える：回転ソート配列

ここまでは配列全体がきれいに単調でした。では、こういう配列ならどうでしょうか。

> `[4, 5, 6, 7, 0, 1, 2]` — もともと `[0,1,2,4,5,6,7]` だった配列を、途中でぐるっと回転させたものです。この中から `target = 0` を探してください。

パッと見ると、途中で数字が大きい方から小さい方へガクッと落ちていて、全体としては単調ではありません。二分探索は使えないように思えます。

ここで少し視点を変えてみます。`mid` で配列を2つに割ったとき、**その2つの半分のうち、少なくともどちらか片方は必ず普通にソートされています。** 実際に `[4, 5, 6, 7, 0, 1, 2]` を `mid = 3`（値7）で割ると、左半分 `[4, 5, 6, 7]` は完全にソートされていて、右半分 `[0, 1, 2]` にだけ「谷」が残っています。

つまり、判定の手順は2段階に分かれます。

1. `nums[lo] <= nums[mid]` かどうかで、**左右どちらの半分がソート済みか**を判定する
2. ソート済みと分かった側に対して、「target はその範囲に入るか？」を確認する。入るならそちらへ、入らないなら反対側へ進む

「ソートされていない側」について判断しようとすると条件が複雑になりますが、**確実に言える側だけで判断する**のがこの問題のコツです。

```python
def search(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[lo] <= nums[mid]:               # 左半分がソート済み
            if nums[lo] <= target < nums[mid]:
                hi = mid - 1                    # 答えは左半分
            else:
                lo = mid + 1
        else:                                   # 右半分がソート済み
            if nums[mid] < target <= nums[hi]:
                lo = mid + 1                    # 答えは右半分
            else:
                hi = mid - 1
    return -1
```

<Callout type="warn" title="等号の位置に注意してください">
  `nums[lo] <= nums[mid]` の等号は、要素がちょうど1つ（`lo == mid`）のときに左半分を正しく「ソート済み」と判定するために必要です。
  また `nums[lo] <= target < nums[mid]` は、左が閉区間、右が開区間になっています。`nums[mid]` はすでに一致しないと確認済みだからです。ここを雑に `<=` にしてしまうと、要素数が2のときに落ちます。
</Callout>

## ここからが本題：答えそのものを二分探索する

ここまでは「配列の中の位置」を探していましたが、実は二分探索は**配列が無くても**使えます。ここが Medium で一番差がつくポイントです。

> `piles` という山からバナナを食べます。1時間に最大 `k` 本まで食べられます（食べ残しがあっても、その山はその時間で終わりにします）。`h` 時間以内に全部の山を食べ切れる、**最小の `k`** を求めてください。

`k` を1から順番に試していけば答えは見つかりますが、`k` の上限は 10<sup>9</sup> にもなるので、1つずつ試すのは論外です。

ここで、こう考えてみます。「`k` を大きくすればするほど、食べ切るのにかかる時間は短くなる（または変わらない）」というのは、直感的に明らかです。つまり、`k` を横に並べたとき、「間に合うかどうか」は `False, False, ..., True, True` という単調な並びになっているはずです。

| k | 1 | 2 | 3 | ... | 答え | ... | max(piles) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| h時間で間に合うか | F | F | F | ... | **T** | T | T |

これは、さっきの lower bound とまったく同じ形の問題です。「配列の値」の代わりに「`k` という候補の数字」に対して、同じ ok / ng のロジックをそのまま当てはめられます。

```python
def min_eating_speed(piles, h):
    def hours(k):          # 速度 k での所要時間
        return sum((p + k - 1) // k for p in piles)

    # 条件 P(k): hours(k) <= h
    ok, ng = max(piles), 0   # ok は必ず成立 / ng は不成立
    while abs(ok - ng) > 1:
        mid = (ok + ng) // 2
        if hours(mid) <= h:
            ok = mid
        else:
            ng = mid
    return ok
```

<KokoEatingBananas client:visible />

横軸が「配列の中身」ではなく「速度 `k` の候補」になっている点に注目してください。**探している対象が「入力データ」から「答えの候補」に変わっただけで、やっていることは lower bound とまったく同じ**です。この「答えの決めうち」というパターンに気づけると、二分探索が使える場面が一気に広がります。

<Callout type="tip" title="答えの決めうちが使えるかどうかの2つの条件">
  次の2つが両方成り立つとき、この型が使えます。

  1. 答えの候補に**順序**がある（ほとんどの場合、数値です）
  2. 「候補 `x` が条件を満たすかどうか」を、**その `x` だけを見て単独で判定できる**（他の候補の答えを必要としない）

  そのうえで、判定関数が `F...FT...T`（または `T...TF...F`）という単調な形になっていることも確認してください。ここが崩れていると、二分探索をしても間違った答えが返ってきます。
</Callout>

計算量は「二分探索の実行回数 × 1回の判定にかかるコスト」で決まります。Koko の例では、判定関数 `hours()` が O(N) かかるので、全体では O(N log(max(piles))) です。「二分探索だから O(log N)」とだけ答えてしまうと、判定関数のコストを忘れていることになるので注意してください。

## 「これは二分探索だ」と気づくためのサイン

- 「**ソート済み**の配列」＋「**O(log N) で**」
- 「最小の〜を求めよ」「最大の〜を求めよ」で、**候補が数値**かつ範囲がとても広い（10<sup>9</sup> など）
- 「〜できる最小の速度／時間／容量」
- 「判定は簡単にできるが、最適な値を直接求めるのは難しい」という構造の問題

<Callout type="warn" title="オーバーフローと無限ループに注意">
  - `mid = (lo + hi) // 2` は Python では問題になりませんが、C++ や Java では `lo + (hi - lo) // 2` と書くのが安全です
  - `while lo <= hi` 形式で、うっかり `lo = mid` と書くと無限ループになります。必ず `mid ± 1` で動かしてください
  - ok / ng 方式なら `ok = mid` / `ng = mid` とそのまま書いて大丈夫です。`abs(ok - ng) > 1` が終了を保証してくれます
</Callout>
