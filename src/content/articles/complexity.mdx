## O記法は「だいたいの伸び方」を表す道具です

`O(N)` や `O(N²)` という記法を見ると身構えてしまうかもしれませんが、これは**「入力サイズ N を大きくしたとき、処理時間（またはメモリ）がどんな形で増えていくか」**を表しているだけです。

たとえば、配列を1回だけ端から端まで見るコードは `O(N)` です。N が2倍になれば、かかる時間もだいたい2倍になります。二重ループで全ペアを見るコードは `O(N²)` です。N が2倍になると、かかる時間はだいたい4倍になります。**「正確に何秒か」ではなく、「Nを増やしたときの伸び方の形」**を表現しているのが O記法だと捉えてください。

## なぜ「最悪」の場合で考えるのか

同じアルゴリズムでも、入力によって速かったり遅かったりします。配列から特定の値を探す線形探索は、運が良ければ（探している値が先頭にあれば）一瞬で終わりますが、運が悪ければ（末尾にある、または存在しない）配列全部を見ることになります。

面接やアルゴリズムの設計で計算量を語るとき、基本的には**最悪計算量**（一番運が悪いときにどれだけかかるか）を使います。理由はシンプルで、**「これ以上は絶対に遅くならない」という保証がないと、安心して使えない**からです。平均的には速くても、特定の入力でいきなり遅くなるアルゴリズムは、本番で痛い目を見ます。

<Callout type="tip" title="定数倍や小さい項は無視してよい理由">
  `O(2N)` や `O(N + 10)` は、どちらも `O(N)` として扱います。N が十分に大きくなると、係数の2倍や、足し算された10という定数は、全体の伸び方にほとんど影響しなくなるからです。**Nが小さいうちの細かい差ではなく、Nが大きくなったときの支配的な項**に注目するのが O記法の考え方です。
</Callout>

## よく出てくる計算量の形と、その導き方

計算量は、コードの構造から直接導けます。パターンを知っておくと、コードを見ただけで見積もりができるようになります。

### ループの入れ子

```python
for i in range(n):
    for j in range(n):
        ...   # O(1) の処理
```

外側のループが N 回、その中で内側のループがさらに N 回まわるので、中の処理は合計 `N × N = N²` 回実行されます。これが `O(N²)` の根拠です。3重に入れ子になれば `O(N³)` になります。「ループが何重か」を数えるだけで、だいたいの見積もりができます。

<Callout type="warn" title="入れ子になっていても O(N²) とは限らない">
  Sliding Window の記事で見たように、`for` の中に `while` があっても、**内側のポインタが全体を通して高々 N 回しか動かない**なら、合計では `O(N)` です。「見た目が入れ子かどうか」ではなく、**「内側の処理が、外側のループ全体を通して合計何回実行されるか」**を数えるのが正しい見積もり方です。
</Callout>

### 再帰：分岐の数と深さ

再帰関数の計算量は、**「1回の呼び出しで何回自分自身を呼ぶか（分岐数）」**と**「再帰がどれだけ深く続くか（深さ）」**の2つから見積もります。

素朴なフィボナッチ数の再帰（`fib(n) = fib(n-1) + fib(n-2)`）は、1回の呼び出しで2回自分を呼びます。深さは `n` です。分岐が2つ、深さが `n` の木を思い浮かべると、末端の数は `2ⁿ` 個に近くなります。これが `O(2ⁿ)` という、とても重い計算量の正体です（DPの記事で見た通り、これはメモ化で `O(N)` まで落とせます）。

### 分割統治：O(N log N) はどこから来るのか

マージソートのような「問題を半分に割って、それぞれ再帰的に解いて、最後に統合する」アルゴリズムは `O(N log N)` になります。これも分解して考えます。

- 「半分に割る」を繰り返すと、何回で1個まで小さくなるか？　これが `log N` 回です（N を2で割り続けて1になるまでの回数）
- 「統合する」処理は、各階層で合計 `N` 個の要素を扱います

つまり、**「`log N` 段の階層があり、各階層で `O(N)` の作業をする」**ので、全体で `O(N log N)` になります。二分探索の `O(log N)` は「統合の作業が無い」バージョンだと考えると、関係が見えやすくなります。

## 空間計算量：見落としがちな2つのポイント

計算量というと時間ばかりに目が行きがちですが、空間計算量（使うメモリの量）にも同じくらい注意が必要です。

**1つ目は、出力そのものをカウントするかどうかです。** 「すべての部分集合を返す」問題では、答え自体が `O(2ⁿ)` 個あるので、それを格納する配列だけで `O(2ⁿ)` の空間を使います。これは答えの性質上避けられないので、通常「追加でどれだけメモリを使うか」を議論します。

**2つ目は、再帰のコールスタックです。** 再帰関数を呼ぶたびに、その分の情報がスタックに積まれます。木の記事で見たように、二分木に対する DFS の再帰は、木の高さの分だけスタックが積まれるので `O(H)` の空間を使います。**「配列やハッシュテーブルを使っていないから空間計算量は O(1) だ」と思い込むと、再帰のスタック分を見落とします。**

<Callout type="warn" title="再帰の深さがそのまま空間計算量になる">
  グリッドの記事で見た `Number of Islands` の DFS を思い出してください。グリッドがすべて陸だと、再帰は最大で `H × W` 段まで深くなり得ます。これは実質的に `O(N)` の追加空間を使っていることになります。反復（ループ）で書き直せばスタックの心配は無くなりますが、それでも自分でスタックを持てば同じだけのメモリを使います。「再帰を使わなければメモリを使わない」わけではないことに注意してください。
</Callout>

## ならし計算量：動的配列の `append` はなぜ平均 O(1) なのか

Python のリストへの `append()` は「平均 O(1)」と言われますが、実は**すべての `append` が O(1) というわけではありません。**

動的配列は、内部で確保している容量がいっぱいになると、新しく2倍の大きさの配列を確保し、既存の要素を全部コピーし直します。このコピーは `O(N)` かかる、重い操作です。「じゃあ `append` は遅いのでは？」と思うかもしれませんが、ここで**ならし計算量**という考え方が登場します。

容量を2倍に増やす方式では、この「重い `append`」が起きるのは、要素数が `1, 2, 4, 8, 16...` に達したときだけです。N 回の `append` の中で、コピーにかかった合計のコストを数えると、`1 + 2 + 4 + ... + N ≈ 2N` 程度にしかなりません。これを N 回の `append` で割ると、1回あたり平均 `O(1)` になります。**「たまに重い処理が起きるが、それを含めて全体を平均すると軽い」**というのが、ならし計算量の考え方です。

## 制約から解法を逆算する

ここまでの内容を踏まえて、最初の記事でも触れた「制約から解法を逆算する」表をもう一度見てみます。今度は、**なぜその計算量が境界線になるのか**まで含めて読めるはずです。

| 入力サイズ N | 通る計算量の目安 | この記事で見た根拠 |
| --- | --- | --- |
| N ≤ 20 | O(2<sup>N</sup>) | 再帰の分岐数が2、深さがNの木 |
| N ≤ 500 | O(N<sup>3</sup>) | 3重の入れ子ループ |
| N ≤ 5,000 | O(N<sup>2</sup>) | 2重の入れ子ループ |
| N ≤ 10<sup>5</sup> | O(N log N) | ソート、分割統治 |
| N ≤ 10<sup>6</sup> | O(N) | 1回のループ、ポインタが戻らない探索 |

制約を見た瞬間に「これは二重ループでは無理だ」とわかるのは、単なる暗記ではなく、**「二重ループは O(N²) になる」という導出を理解しているから**です。表を丸暗記するより、この記事で見た「なぜその計算量になるのか」を体に入れておくほうが、初見の問題にも応用が効きます。
