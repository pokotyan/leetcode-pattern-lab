## 正直に言うと、センスの問題ではありません

LeetCode の Medium 問題を見て「思いつかない…」と落ち込んだことがあるかもしれません。でも安心してください。それはあなたの地頭が悪いからではなく、**単純にその解き方をまだ知らないだけ**、というケースがほとんどです。

コーディング面接で出る問題の中には、正直に言うと**知らなければ一生かかっても思いつかない解き方**が一定数あります。逆に言えば、その解き方さえ知っていれば、初めて見る問題でも「あ、これはあの型だ」とピンとくるようになります。

だからこの教材では、1問1問を個別に丸暗記していくのではなく、**同じ道具で解ける問題をまとめて、ひとつの「型」として身につける**という進め方をします。型が頭の中の引き出しに入っていれば、初見の問題でも「これは両端から縮めていくやつだ」「これは条件を満たす限界を探すやつだ」と当たりがつくようになります。

この教材を最後まで読んだとき、次のことができるようになっているのがゴールです。

- 初めて見る Medium 問題でも、**方針が15分以内に立つ**
- 選んだ解法について、**なぜその計算量になるのかを自分の言葉で説明できる**
- 「なぜ他のやり方ではなく、これを選んだのか」を、トレードオフとして説明できる

## 記事はぜんぶ同じ形をしています

迷わず読み進められるように、どの記事も次の順番で構成してあります。

1. **その型が何に困っているときの道具なのか** — 具体的な数字を使って、まず感覚をつかみます
2. **最小限のコード** — ここだけは覚えてしまってよい骨格です
3. **1手ずつ動かせるシミュレーター** — いまコードのどの行が、変数のどこを動かしているのかを目で追えます
4. **ハマりどころ** — 実際によくある間違いを、先に知っておきます
5. **練習問題** — 記事の冒頭に並んでいる LeetCode の問題を、自分の手で解いてみます

<Callout type="tip" title="シミュレーターは、実際に触ってみてください">
  再生ボタンを押すと自動で1手ずつ進みます。`←` `→` キーで1手ずつ、`Space`
  キーで再生・一時停止もできます。**大事なのは、入力欄の数字や文字列を自分で書き換えてみることです。**
  空の配列、要素が1個だけ、全部同じ値……こういう「意地悪な入力」を試してみると、コードのどの部分がそれを支えているのかが見えてきます。
</Callout>

## 何から読めばいいか

上から順番に読んでいけば、必要な知識は先に出てくるようになっています。時間があまり取れない場合のために、優先度もつけておきます。

| 優先度 | 分野 | なぜ優先か |
| --- | --- | --- |
| 最優先 | 配列・文字列（Two Pointers / Sliding Window） | Medium で一番よく出ます。覚えるコストの割に効果が大きいです |
| 高 | ハッシュテーブル | 二重ループを O(N) に変える基本の道具。他の型と組み合わせてもよく出ます |
| 高 | 二分探索 | 「答えそのものを探す」型まで含めると、使える場面がとても広いです |
| 高 | グラフ（BFS / DFS） | グリッドの問題まで含めると、Medium でかなり出てきます |
| 中 | 木、スタック、ヒープ | 覚えることは少ないのに、覚えれば確実に得点源になります |
| 中 | 再帰・バックトラック | 全探索の「書き方の型」がほぼ決まっています |
| 後回しでもOK | 動的計画法 | 一番習得に時間がかかります。まずは基本の形だけ押さえれば十分です |

## 解けない問題に出会ったとき

解けなくても、まったく問題ありません。そこで焦って解答をすぐ見てしまうのが一番もったいないです。まずは**最低20分は自分の頭で考えてみましょう。**

考えるときのコツは3つです。

- 紙に図を書いてみる（頭の中だけで完結させようとしない）
- 極端に小さい入力（要素が1個、空っぽ）ならどうなるか考えてみる
- 問題文の制約を見て「これは O(N²) じゃ通らなそうだ」と逆算してみる

そして解答を読んだあとは、**その倍の時間を復習に使ってください。** 「なるほど、わかった」で終わらせず、次の3つを自分に聞いてみましょう。

- そもそも自分はなぜ解けなかったのか（知らなかっただけなのか、気づけなかっただけなのか）
- どこまでは自力で正しく考えられていたのか
- 次に似た問題を見たとき、何がきっかけでこの解き方を思い出せばいいのか

このうち一番大事なのは3つ目です。型を身につけるというのは、結局のところ**「この特徴を見たらこの解き方」という組み合わせを、自分の中に作っていくこと**に他なりません。

<Callout type="warn" title="解答の丸写しは、実はあまり効きません">
  解答のコードをそのまま書き写しても、「頭の中のイメージをコードに変換する」練習にはなりません。解説を読み終えたら一度画面を閉じ、何も見ずにもう一度自分の手で書いてみてください。最初はうまく書けなくて当たり前です。
</Callout>

## 問題文の数字を、ただの飾りだと思わない

問題文についている制約、たとえば `1 <= nums.length <= 10^5` のような1行は、実は**「この計算量で解いてくださいね」という、こっそりしたヒント**になっています。

目安として、コンピュータは1秒間におよそ 10<sup>8</sup>（1億）回くらいの単純な操作をこなせると考えてください。この数字をもとに、入力サイズ N から通る計算量を逆算できます。

| 入力サイズ N | 通る計算量の目安 | よく出てくる解法 |
| --- | --- | --- |
| N ≤ 10 | O(N!) や O(2<sup>N</sup>) | すべての並び方、すべての組み合わせを試す |
| N ≤ 20 | O(2<sup>N</sup>) | bit を使った全探索 |
| N ≤ 500 | O(N<sup>3</sup>) | 三重ループ |
| N ≤ 5,000 | O(N<sup>2</sup>) | 二重ループ |
| N ≤ 10<sup>5</sup> | O(N log N) | ソート、二分探索、ヒープ |
| N ≤ 10<sup>6</sup> | O(N) | Two Pointers、Sliding Window、累積和 |

たとえば `1 <= nums.length <= 10^5` と書いてあったとします。この瞬間に、「二重ループ（O(N²)）はまず通らないな」とわかります。つまり、**「何を使えばいいか」を考える前に、「何が使えないか」が先にわかる**わけです。これも立派な解法の絞り込みです。問題を読み始めた時点で、もう解法選びは始まっています。
