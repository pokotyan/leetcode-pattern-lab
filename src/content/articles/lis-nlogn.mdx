## この記事を読む前に押さえておく型

- **動的計画法（一次元）**：まず O(N²) の素直な DP を書けることが出発点です。「`dp[i]` を `i` 番目で終わる増加列の長さ」と決める状態の立て方を知らないと、この記事で削っているものが何なのか分かりません
- **二分探索**：この型の O(N log N) は、内側のループを丸ごと二分探索に置き換えることで出てきます。しかも探すのは「値そのもの」ではなく「条件を満たす最初の位置」なので、`ok` / `ng` 方式で下界を求める形をそのまま使います。ここが曖昧だと、この記事の後半は読めません

## まず、困っている状況を体験してみます

> 配列 `nums = [10, 9, 2, 5, 3, 7, 101, 18]` から、いくつか要素を取り除いて（順番は変えずに）、値が増加していく列を作ります。作れる最長の列の長さを求めてください。

答えは `[2, 3, 7, 101]` の4です。まず素直な DP を書いてみます。

`dp[i]` を「`i` 番目の要素で**終わる**増加列の、最長の長さ」と決めます。`i` 番目を列の最後に置くとき、その手前は「`i` より前にあって、値が `nums[i]` より小さい」どれかです。その中で一番長いものにつなげればよいので、

```python
def length_of_lis_n2(nums):
    dp = [1] * len(nums)
    for i in range(len(nums)):
        for j in range(i):
            if nums[j] < nums[i]:
                dp[i] = max(dp[i], dp[j] + 1)
    return max(dp)
```

これで正しく解けます。ただし、`i` ごとに手前を全部見直すので O(N²) です。この問題の制約は N が 2,500 なので実は通りますが、同じ形で N が 10 万まで来る問題（Russian Doll Envelopes など）では 100 億回になり、まったく歯が立ちません。

無駄はどこにあるのでしょうか。内側のループがやっているのは、**「値が `nums[i]` より小さいものの中で、`dp` が最大のものを探す」**という検索です。この検索を、毎回ゼロから舐め直しているのが重いのです。

## 発想を変える：長さごとに「一番小さい末尾」だけを覚えておく

ここで、持つ情報をがらりと変えます。各要素についての `dp` を覚えるのをやめて、代わりに次の配列を持ちます。

> `tails[k]` ＝ 長さ `k + 1` の増加列を作れるときの、**末尾の値として一番小さいもの**

なぜ「一番小さい末尾」なのでしょうか。増加列を今後も伸ばしていきたいとき、末尾は小さいほど有利だからです。長さ3の増加列が `[2, 5, 7]` と `[2, 3, 100]` の2通り作れるなら、今後の伸ばしやすさでは末尾 7 のほうが 100 より明らかに得です。同じ長さなら、末尾が最小のものだけを覚えておけば十分です。

この `tails` には、とても便利な性質があります。**必ず増加順に並びます。** 長さ4の列の末尾が、長さ3の列の末尾以下になることはありえません（長さ4の列から最後の1個を取り除けば長さ3の列になり、その末尾は元の末尾より小さいからです）。

増加順に並んでいるということは、**二分探索が使えます。** ここが O(N²) を O(N log N) に落とす本体です。

新しい値 `x` が来たときにやることは2つだけです。

1. `tails` の中から、**`x` 以上が最初に現れる位置**を二分探索で探す
2. その位置が `tails` の末尾より後（＝ `x` がどの末尾よりも大きい）なら、`x` を**追加**して長さを1つ伸ばす。そうでなければ、その位置を `x` で**置き換える**

```python
def length_of_lis(nums):
    tails = []                        # tails[k] = 長さ k+1 の増加列の、最小の末尾
    for x in nums:
        # 条件 P(i): tails[i] >= x を最初に満たす位置を探す
        ok, ng = len(tails), -1
        while abs(ok - ng) > 1:
            mid = (ok + ng) // 2
            if tails[mid] >= x:
                ok = mid
            else:
                ng = mid
        if ok == len(tails):
            tails.append(x)           # どの末尾より大きい → 長さを1つ伸ばせる
        else:
            tails[ok] = x             # 同じ長さを、より小さい末尾で作り直す
    return len(tails)
```

二分探索の部分は、二分探索の記事で書いた下界（lower bound）そのままです。`ok` の初期値を `len(tails)`（範囲外だが「必ず成立」扱い）に置くことで、「どの末尾よりも大きい」ケースが自然に `ok == len(tails)` として出てきます。

## なぜこれで正しい長さが出るのか、数字で確かめます

`[10, 9, 2, 5, 3, 7, 101, 18]` を順に処理します。

| 来た値 | 二分探索の結果 | 操作 | tails |
| --- | --- | --- | --- |
| 10 | 空なので位置0（末尾） | 追加 | [10] |
| 9 | 10 は 9 以上なので位置0 | 置き換え | [9] |
| 2 | 位置0 | 置き換え | [2] |
| 5 | どれより大きいので末尾 | 追加 | [2, 5] |
| 3 | 5 が 3 以上なので位置1 | 置き換え | [2, 3] |
| 7 | どれより大きいので末尾 | 追加 | [2, 3, 7] |
| 101 | 末尾 | 追加 | [2, 3, 7, 101] |
| 18 | 101 が 18 以上なので位置3 | 置き換え | [2, 3, 7, 18] |

最終的な `tails` の長さは4で、これが答えです。

ここで、多くの人が引っかかる点を先回りしておきます。**最後の `tails` は `[2, 3, 7, 18]` ですが、これは実際の最長増加部分列ではありません。** 元の配列で 18 は 101 より後ろにあるので、`[2, 3, 7, 18]` は確かに増加列として成立していますが、いつもそうとは限りません。置き換えの操作は「将来のために末尾を小さくしておく」という予約のようなもので、途中の `tails` は必ずしも実在する1本の列を表していないからです。

**保証されているのは長さだけです。** 実際の列そのものを復元したい場合は、各要素がどの位置に入ったかを別に記録して、あとから逆にたどる必要があります。

<Callout type="warn" title="置き換えで長さが減らない理由と、狭義・広義の切り替え">
  「置き換えたら短くなるのでは」と不安になるかもしれませんが、置き換えは `tails` の**長さを変えません**。すでにある位置の値を、より小さい値で上書きするだけです。長さが増えるのは末尾に追加したときだけなので、`len(tails)` は一度も減りません。

  もう1つ、条件の等号には注意が必要です。

  - **狭義単調増加**（同じ値を含めない。`1 < 2 < 3`）：探すのは「`x` **以上**が最初に現れる位置」。上のコードの `tails[mid] >= x` です
  - **広義単調増加**（同じ値を許す。`1 <= 2 <= 2`）：探すのは「`x` **より大きい**値が最初に現れる位置」。条件を `tails[mid] > x` に変えます

  問題文の「strictly increasing」「non-decreasing」を読み飛ばすと、この1文字でずれます。シミュレーターで「同じ値を含む」の入力を選ぶと、同じ値が来たときに追加ではなく置き換えになる様子が見えます。
</Callout>

## ソートで二次元を一次元に落とす：Russian Doll Envelopes

LIS が本当に効いてくるのは、一見すると LIS に見えない問題です。

> 封筒が `[[w, h], ...]` の形で与えられます。幅も高さも**厳密に大きい**封筒の中には、小さい封筒を入れられます。最大で何枚を入れ子にできますか。

条件が幅と高さの2つあるので、そのままでは増加列になりません。そこで片方を先に固定してしまいます。**幅で昇順にソートすれば、幅の条件はもう気にしなくてよくなり、残るのは高さについての最長増加部分列だけです。**

ただし、ここに落とし穴があります。幅が同じ封筒どうしは入れ子にできません。幅の昇順に並べただけだと、幅が同じで高さが増えている組（たとえば `(1,1), (1,2), (1,3)`）が、高さの増加列として数えられてしまいます。

これを防ぐのが、**同じ幅のときは高さを降順に並べる**という一手です。高さが降順に並んでいれば、その中から増加する列を選ぶことはできません。ソートの基準だけで、条件違反の組み合わせを構造的に排除しているわけです。

```python
def max_envelopes(envelopes):
    envelopes.sort(key=lambda e: (e[0], -e[1]))   # 幅は昇順、同じ幅なら高さは降順
    tails = []
    for _, h in envelopes:
        ok, ng = len(tails), -1                   # tails[i] >= h の最初の位置
        while abs(ok - ng) > 1:
            mid = (ok + ng) // 2
            if tails[mid] >= h:
                ok = mid
            else:
                ng = mid
        if ok == len(tails):
            tails.append(h)
        else:
            tails[ok] = h
    return len(tails)
```

「同じ幅が3枚」という入力を選んでみてください。`(1,1), (1,2), (1,3), (2,4)` は、高さの降順ソートによって `(1,3), (1,2), (1,1), (2,4)` の順に並びます。高さの列は `[3, 2, 1, 4]` となり、増加列は `[3, 4]` か `[1, 4]` の長さ2です。もし高さを昇順に並べてしまっていたら `[1, 2, 3, 4]` となり、幅がすべて1の封筒を3枚重ねる、という誤った答え4が出ていました。

<Callout type="tip" title="「ソートで条件を1つ消す」は発展問題の定番です">
  2つ以上の条件が絡む問題で、片方をソートで固定して残りを一次元の問題に落とす、という手口は繰り返し出てきます。

  - Russian Doll Envelopes：幅でソートして、高さの LIS に落とす
  - Maximum Height by Stacking Cuboids：各直方体の辺を揃えてからソートし、LIS 型の DP に落とす
  - 区間の問題（前の記事）：開始時刻でソートして、比べる相手を直前の1つに絞る

  共通しているのは、**「ソートした後に何が保証されるか」を言葉にできるかどうか**です。ここを説明できないままソートすると、同値のときの順序で答えが変わってしまいます。
</Callout>

## この型の計算量

| やり方 | 時間 | 空間 | 内訳 |
| --- | --- | --- | --- |
| 素直な DP | O(N²) | O(N) | 各 i について手前を全部見る |
| tails + 二分探索 | **O(N log N)** | O(N) | N 個それぞれに1回の二分探索 |
| Russian Doll Envelopes | O(N log N) | O(N) | ソート O(N log N) + LIS O(N log N) |

なお、LIS の**個数**を数える問題（Number of Longest Increasing Subsequence）や、実際の列そのものを復元する問題では、この形をそのまま使えません。長さだけを求める問題かどうかを最初に確認してください。

## 「これは LIS だ」と気づくためのサイン

- 「**部分列**」（subsequence。連続でなくてよい）＋「増加する／減少する」
- 「並べ替えずに、いくつか取り除いて条件を満たす最長のものを作る」
- 2つの属性があって、「両方とも大きい」という入れ子の条件が付いている（ソートで一次元化を疑う）
- 「山型（増えてから減る）の最長」→ 左からの LIS と右からの LIS を両方求める
- 素直な DP が O(N²) になり、N が 10<sup>5</sup> 規模である

<Callout type="warn" title="「連続」なのか「部分列」なのかを最初に確認してください">
  「連続部分配列（subarray）」と「部分列（subsequence）」は別物です。連続なら Sliding Window や累積和の出番で、連続でないなら DP か、この記事の型です。
  問題文の subarray / substring / subsequence を見落とすと、まったく違う型で解き始めてしまいます。英語の問題文では、ここは必ず明示されています。
</Callout>
