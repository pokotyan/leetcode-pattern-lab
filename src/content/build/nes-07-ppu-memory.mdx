## 2KB で 1 画面を表す

画面は 256 × 240 ピクセルです。1 ピクセルに 1 バイト使うと 61KB。ファミコンの RAM は 2KB しかありません。**まったく足りません。**

そこで、**画面をタイルの並びとして表現します**。

```
256 ÷ 8 = 32 タイル（横）
240 ÷ 8 = 30 タイル（縦）
32 × 30 = 960 タイル
```

各タイルに「どの絵柄を使うか」の番号（1 バイト）を持てば、**960 バイト**で 1 画面が表せます。

**絵柄そのもの（タイルの中身）は別に置きます。** 256 種類のタイルを、繰り返し使い回す、という設計です。

<Callout type="tip" title="この構造は今も生きている">
  同じタイルを何度も使うことで、データ量を劇的に減らす。
  タイルマップと呼ばれるこの手法は、
  2D ゲームエンジンでも、地図アプリのタイル配信でも、今も使われています。

  第 3 章で読んだキャッシュと同じで、**繰り返しがあるなら、実体は 1 つでよい**。
</Callout>

## PPU のメモリ空間

PPU は CPU とは**別のアドレス空間**を持ちます。16KB です。

| アドレス | 大きさ | 内容 |
| --- | --- | --- |
| `$0000`〜`$0FFF` | 4KB | **パターンテーブル 0**（タイルの絵柄 256 個） |
| `$1000`〜`$1FFF` | 4KB | **パターンテーブル 1**（さらに 256 個） |
| `$2000`〜`$23FF` | 1KB | **ネームテーブル 0**（どのタイルをどこに置くか） |
| `$2400`〜`$27FF` | 1KB | ネームテーブル 1 |
| `$2800`〜`$2BFF` | 1KB | ネームテーブル 2 |
| `$2C00`〜`$2FFF` | 1KB | ネームテーブル 3 |
| `$3000`〜`$3EFF` | | `$2000`〜`$2EFF` のミラー |
| `$3F00`〜`$3F1F` | 32 バイト | **パレット** |
| `$3F20`〜`$3FFF` | | パレットのミラー |

パターンテーブルは、通常**カートリッジの CHR ROM** が接続されています。ネームテーブルは、本体の 2KB の VRAM です。

## タイルの中身：2 ビットプレーン

1 タイルは 8 × 8 ピクセル。各ピクセルは **4 色のうち 1 つ**（2 ビット）です。

素直に考えると、8 × 8 × 2 ビット = 16 バイト。実際 16 バイトです。しかし、**並べ方が独特**です。

```
バイト 0〜7   : 各ピクセルの下位ビット（ビットプレーン 0）
バイト 8〜15  : 各ピクセルの上位ビット（ビットプレーン 1）
```

1 ピクセルの 2 ビットが、**16 バイト離れた 2 箇所に分かれて置かれています**。

```
オフセット 0:  0 1 1 0 0 1 1 0     ← 1 行目の下位ビット
オフセット 8:  0 0 1 1 1 1 0 0     ← 1 行目の上位ビット
               ─────────────
色番号:        0 1 3 2 2 3 1 0
```

<Callout type="note" title="なぜ分けるのか">
  回路の都合です。PPU は 1 ピクセルずつシフトレジスタから取り出して描画します。
  2 つのプレーンをそれぞれ独立したシフトレジスタに入れておけば、
  **毎サイクル 1 ビットずつ取り出して合成するだけ**で済みます。

  ピクセル単位でインターリーブされていると、2 ビットずつ取り出す必要があり、
  回路が複雑になります。

  **データの配置が、それを処理する回路の形で決まっている**例です。
</Callout>

```ts
// src/nes/tile.ts
/** 16 バイトのタイルを、8x8 の色番号（0〜3）に展開する */
export function decodeTile(chr: Uint8Array, tileIndex: number, base = 0): number[][] {
  const offset = base + tileIndex * 16
  const rows: number[][] = []

  for (let row = 0; row < 8; row++) {
    const lo = chr[offset + row]!
    const hi = chr[offset + row + 8]!
    const line: number[] = []
    for (let col = 0; col < 8; col++) {
      const bit = 7 - col                        // 左端が bit7
      line.push(((lo >> bit) & 1) | (((hi >> bit) & 1) << 1))
    }
    rows.push(line)
  }
  return rows
}
```

**左端が bit7** です。文字列の左から読むのと同じ向きになるように配置されています。

## ネームテーブル

1KB のうち、内訳はこうです。

```
$2000〜$23BF   960 バイト   タイル番号（32 × 30）
$23C0〜$23FF    64 バイト   属性テーブル
```

タイル番号の部分は素直です。`(row * 32 + col)` 番目のバイトが、その位置のタイル番号。

## 属性テーブル：色をどう決めるか

タイルの色番号は 0〜3 の 4 段階です。しかし、実際の色は 4 色だけではありません。

**どのパレットを使うか**を、別に指定します。パレットは 4 組あり、それぞれ 3 色 + 共通の背景色を持ちます。

問題は、**その指定を 64 バイトに収める**ことです。960 タイルそれぞれにパレット番号（2 ビット）を持たせると 240 バイト必要で、入りません。

そこで、**粒度を粗くします**。

```
1 バイト = 4 × 4 タイル（32 × 32 ピクセル）を担当
その中を 2 × 2 タイルの 4 区画に分け、各区画に 2 ビット
```

```
 バイトのビット配置
 ┌─────────┬─────────┐
 │ bit 1-0 │ bit 3-2 │    左上 / 右上
 ├─────────┼─────────┤
 │ bit 5-4 │ bit 7-6 │    左下 / 右下
 └─────────┴─────────┘
```

```ts
export function paletteFor(attrTable: Uint8Array, tileX: number, tileY: number): number {
  const index = (tileY >> 2) * 8 + (tileX >> 2)        // どのバイトか
  const byte = attrTable[index]!
  const quadrant = ((tileY >> 1) & 1) * 2 + ((tileX >> 1) & 1)   // どの区画か
  return (byte >> (quadrant * 2)) & 3
}
```

<Callout type="warn" title="これが「色替えの制約」として見える">
  **隣り合う 2 × 2 タイル（16 × 16 ピクセル）は、同じパレットしか使えません。**

  ファミコンのゲームで、キャラクタの色が 16 ピクセル単位で切り替わっているように見えたり、
  背景の色数が少なく見えたりするのは、この制約によるものです。

  **メモリを節約するための設計が、そのまま見た目の特徴になっています。**
</Callout>

## ネームテーブルのミラーリング

ネームテーブルは 4 つぶん（4KB）のアドレス空間がありますが、**本体の VRAM は 2KB しかありません**。

そこで、2 つが別の 2 つのミラーになります。どう対応させるかは、**カートリッジが決めます**（第 4 回の iNES フラグ 6）。

| モード | 対応 | 向いているスクロール |
| --- | --- | --- |
| **水平ミラーリング** | NT0=NT1、NT2=NT3 | **縦スクロール** |
| **垂直ミラーリング** | NT0=NT2、NT1=NT3 | **横スクロール** |
| 4 画面 | 全部独立（追加 RAM が必要） | 両方向 |

名前と効果が逆に感じられますが、**「どちら向きに並べて配置されるか」**を指しています。垂直ミラーリングでは、NT0 と NT1 が横に並ぶので、横スクロールが自然にできます。

```ts
export function mirrorNametable(addr: number, mode: 'horizontal' | 'vertical'): number {
  const a = (addr - 0x2000) & 0x0fff
  const table = a >> 10            // どのネームテーブルか（0〜3）
  const offset = a & 0x03ff        // その中の位置

  if (mode === 'horizontal') return ((table >> 1) * 0x400) + offset    // 0,0,1,1
  return ((table & 1) * 0x400) + offset                                 // 0,1,0,1
}
```

## パレット

`$3F00`〜`$3F1F` の 32 バイトです。

| アドレス | 内容 |
| --- | --- |
| `$3F00` | **共通の背景色** |
| `$3F01`〜`$3F03` | 背景パレット 0 の 3 色 |
| `$3F05`〜`$3F07` | 背景パレット 1 |
| ... | |
| `$3F11`〜`$3F13` | スプライトパレット 0 |
| ... | |

各バイトは **NES の 64 色から 1 つを選ぶ番号**です。RGB ではありません。実際の色は、エミュレータ側が変換表を持ちます。

<Callout type="warn" title="$3F10 は $3F00 のミラー">
  `$3F10`、`$3F14`、`$3F18`、`$3F1C` は、
  それぞれ `$3F00`、`$3F04`、`$3F08`、`$3F0C` のミラーです。

  スプライトパレットの「色 0」は透明として扱われるので、
  実体を持つ必要がないためです。
  **ここを実装しないと、背景色が変わらないゲームが出ます。**
</Callout>

## テストを書く

```ts
// src/nes/tile.check.ts
import { strict as assert } from 'node:assert'
import { decodeTile, paletteFor, mirrorNametable } from './tile'

// 2 ビットプレーンの合成
{
  const chr = new Uint8Array(16)
  for (let r = 0; r < 4; r++) chr[r] = 0xff          // 上 4 行の下位ビット
  for (let r = 4; r < 8; r++) chr[r + 8] = 0xff      // 下 4 行の上位ビット

  const tile = decodeTile(chr, 0)
  assert.equal(tile[0]![0], 1, '下位だけ → 色 1')
  assert.equal(tile[7]![0], 2, '上位だけ → 色 2')

  chr[0] = 0xff; chr[8] = 0xff
  assert.equal(decodeTile(chr, 0)[0]![0], 3, '両方 → 色 3')
  console.log('ok   2 ビットプレーンの合成')
}

// ビット順
{
  const chr = new Uint8Array(16)
  chr[0] = 0b10000000
  assert.equal(decodeTile(chr, 0)[0]![0], 1, '左端は bit7')
  assert.equal(decodeTile(chr, 0)[0]![7], 0)

  chr[0] = 0b00000001
  assert.equal(decodeTile(chr, 0)[0]![7], 1, '右端は bit0')
  console.log('ok   ビット順（左端が MSB）')
}

// 属性テーブル
{
  const attr = new Uint8Array(64)
  attr[0] = 0b11_10_01_00       // 右下=3 左下=2 右上=1 左上=0
  assert.equal(paletteFor(attr, 0, 0), 0, '左上')
  assert.equal(paletteFor(attr, 2, 0), 1, '右上')
  assert.equal(paletteFor(attr, 0, 2), 2, '左下')
  assert.equal(paletteFor(attr, 2, 2), 3, '右下')
  assert.equal(paletteFor(attr, 1, 1), 0, '同じ 2×2 区画は同じパレット')

  attr[1] = 0b00_00_00_10
  assert.equal(paletteFor(attr, 4, 0), 2, 'タイル 4 からは次のバイト')
  console.log('ok   属性テーブル')
}

// ミラーリング
{
  assert.equal(mirrorNametable(0x2000, 'horizontal'), 0x000)
  assert.equal(mirrorNametable(0x2400, 'horizontal'), 0x000, '水平では NT1 = NT0')
  assert.equal(mirrorNametable(0x2800, 'horizontal'), 0x400)

  assert.equal(mirrorNametable(0x2400, 'vertical'), 0x400)
  assert.equal(mirrorNametable(0x2800, 'vertical'), 0x000, '垂直では NT2 = NT0')
  console.log('ok   ネームテーブルのミラーリング')
}

console.log('\n全部通りました')
```

## タイルを絵として見る

実際の ROM から取り出して、端末に表示してみます。

```ts
const CHARS = [' ', '░', '▒', '█']

export function renderTile(chr: Uint8Array, index: number): string {
  return decodeTile(chr, index)
    .map((row) => row.map((c) => CHARS[c]).join(''))
    .join('\n')
}

console.log(renderTile(rom.chr, 0x00))
```

マリオの ROM で試すと、文字やキャラクタの一部が見えます。**ここで何かが見えたら、パターンテーブルの読み方は合っています。**

<Callout type="tip" title="中間成果物を目で見る">
  エミュレータ開発では、「画面が出るまで何も確認できない」状態が続きがちです。
  タイルを端末に文字で描くだけでも、**進んでいる実感と、確実な検証**が得られます。

  第 8 章で読んだ「測ってから直す」と同じで、
  **見えないものはデバッグできません**。
</Callout>

## 演習

1. **パターンテーブル全体を表示する**。256 タイルを 16 × 16 に並べて出力してください
2. **ネームテーブルを表示する**。タイル番号を 32 × 30 の表で出します
3. **属性テーブルを可視化する**。どの領域がどのパレットを使うかを図にしてください
4. **パレットのミラーを実装する**。`$3F10` への書き込みが `$3F00` に反映されることを確認します
5. **CHR RAM の ROM を扱う**。CHR バンク数が 0 の ROM で、書き込みができることを確かめてください
