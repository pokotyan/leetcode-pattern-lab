## 検索は「探していない」

検索エンジンに言葉を入れると、数億件の文書から0.2秒で結果が返ってきます。ここで最初に捨てるべき思い込みが、**「全文書を順に調べている」**という発想です。

仮に1文書の走査が 1 マイクロ秒で済んだとしても、1 億文書なら 100 秒かかります。そもそも間に合いません。

実際には、検索のときには**文書を1件も読んでいません。** 読んでいるのは、あらかじめ作っておいた**索引**だけです。

## 転置インデックス：辞書の向きをひっくり返す

普通に文書を保管すると、こういう形になります。

```
文書1 → [検索, エンジン, 仕組み]
文書2 → [データベース, 索引]
文書3 → [検索, 索引, 高速]
```

この向きのままでは、「検索」という語を含む文書を探すのに全部見るしかありません。そこで、**向きをひっくり返します。**

```
検索       → [1, 3]
エンジン   → [1]
仕組み     → [1]
データベース → [2]
索引       → [2, 3]
高速       → [3]
```

これが転置インデックス（inverted index）です。各語に紐づく文書 ID の並びを **posting list** と呼びます。

この形にしておけば、「検索」を含む文書は辞書を1回引くだけで分かります。**ハッシュテーブルの記事でやった「探しながら覚える」の、規模を大きくしたもの**だと考えて差し支えありません。

<Callout type="tip" title="索引を作るコストはどこへ行ったのか">
  転置インデックスを作る作業そのものは、全文書を読む必要があるので O(総単語数) かかります。消えたわけではなく、**検索時から事前計算へ移した**だけです。

  これは累積和とまったく同じ取引です。「先に O(N) 払っておいて、問い合わせを O(1) にする」。検索は問い合わせが何億回も来るので、この取引が圧倒的に得になります。

  逆に言えば、**問い合わせが1回しか来ないなら索引は損**です。1回だけの検索なら grep のほうが速い、というのはそのまま正しい判断になります。
</Callout>

## 複数の語で検索する：posting list の突き合わせ

「検索 エンジン」のように2語で検索したときは、**両方の posting list に出てくる文書**を探します。

ここで posting list が**文書 ID の昇順に並べてある**ことが効きます。ソート済みの2つの配列から共通部分を取り出すのは、Two Pointers そのものです。

```python
def intersect(a, b):
    res = []
    i = j = 0
    while i < len(a) and j < len(b):
        if a[i] == b[j]:
            res.append(a[i])        # 両方に出てくる文書
            i += 1
            j += 1
        elif a[i] < b[j]:
            i += 1                  # 小さいほうだけ進める
        else:
            j += 1
    return res
```

<PostingIntersect client:visible />

全組み合わせを試すと `len(a) × len(b)` ですが、ソート済みなら `len(a) + len(b)` で済みます。**索引を「ソートして保管する」という設計判断が、検索時の計算量を決めている**わけです。

実際のエンジンでは、短い posting list から処理する、スキップポインタを持たせて飛ばす、といった工夫が加わりますが、骨格はこの突き合わせです。

## 順番はどう決まるのか：TF-IDF

該当する文書が1万件見つかったとして、どれを上に出すべきでしょうか。ここからがランキングの話です。

最初に思いつくのは、**検索語がたくさん出てくる文書ほど関係が深いだろう**という考えです。これが TF（term frequency、単語の出現頻度）です。

ただし、これだけでは困ります。「の」「する」のような語は、どの文書にも大量に出てきます。TF だけで順位を決めると、中身と関係なく長い文書が上に来てしまいます。

そこで、**その語が珍しいかどうか**で重みをつけます。これが IDF（inverse document frequency）です。

```
idf(語) = log(全文書数 / その語を含む文書数)
```

- 「の」は全文書に出てくる → `log(1) = 0` → 重みゼロ
- 「転置インデックス」が1万件中10件にしか出てこない → `log(1000)` → 重みが大きい

**珍しい語ほど、その文書を特徴づけている**という判断です。TF-IDF は、この2つを掛け合わせたものです。

<Callout type="tip" title="なぜ log を使うのか">
  文書数の比をそのまま使うと、100 万件中1件しかない語の重みが 100 万になり、ほかの要素が全部かき消されます。

  `log` を通すと、比が 10 倍になっても重みは一定量しか増えません（`log(1000)` は `log(100)` の 1.5 倍にしかなりません）。**「珍しさ」の効きを穏やかにするための圧縮**です。

  数列のノートで見た通り、`log` は「桁数」に近い量です。「その語がどれくらいの桁で珍しいか」を重みにしている、と読むと腑に落ちます。
</Callout>

## BM25：TF-IDF の実用版

TF-IDF には、実際に使うと困る点が2つあります。

**1つ目：出現回数が線形に効きすぎる。** 検索語が 100 回出てくる文書は、10 回の文書より 10 倍関係が深いでしょうか。おそらく違います。5 回も 10 回も「その話題について書いてある」という点では同じで、**どこかで頭打ちになるべき**です。

**2つ目：長い文書が有利になる。** 長ければ、それだけ語が多く含まれます。文書の長さで割り引く必要があります。

この2つを式に組み込んだのが BM25 です。Elasticsearch や OpenSearch が既定で使っているスコアリングは、これです。

```python
import math

def bm25(docs, query, k1=1.5, b=0.75):
    N = len(docs)
    avgdl = sum(len(d) for d in docs) / N
    scores = [0.0] * N
    for term in query:
        n_q = sum(1 for d in docs if term in d)   # その語を含む文書数
        if n_q == 0:
            continue
        idf = math.log((N - n_q + 0.5) / (n_q + 0.5) + 1)
        for i, d in enumerate(docs):
            f = d.count(term)                     # 文書内の出現回数
            if f == 0:
                continue
            norm = f * (k1 + 1) / (f + k1 * (1 - b + b * len(d) / avgdl))
            scores[i] += idf * norm
    return scores
```

<Bm25Score client:visible />

式は複雑に見えますが、読むべきところは3箇所だけです。

| 部分 | 役割 | 動かすとどうなるか |
| --- | --- | --- |
| `idf` | 珍しい語を重くする | 変えない（語ごとに決まる） |
| `k1`（既定 1.2〜2.0） | 出現回数の頭打ちの位置 | 小さくすると、少ない出現回数ですぐ頭打ちになる |
| `b`（既定 0.75） | 文書長による割り引きの強さ | 0 にすると長さを無視、1 にすると長さで完全に割る |

`norm` の部分は、`f` が大きくなると `k1 + 1` に近づいて**それ以上増えなくなります**。これが「頭打ち」の正体です。「出現回数の飽和」というプリセットで、tf が 1 → 2 → 6 と増えたときの増分がどう鈍るかを確認してみてください。

<Callout type="warn" title="「なぜこの順番なのか」と聞かれたとき">
  検索結果の順位について説明を求められたら、確認する順番はこうなります。

  1. **そもそもヒットしているか**（転置インデックスに語があるか。形態素解析や n-gram の切り方で、期待した語になっていないことが多い）
  2. **idf が効いているか**（ありふれた語だけでヒットしていないか）
  3. **文書長の割り引き**（`b` が効きすぎて、長い正解文書が沈んでいないか）
  4. **フィールドごとの重み**（タイトルと本文で重みが違う設定になっていることが多い）

  実務で「検索結果がおかしい」と言われる原因は、スコアの計算式より**1番目の分割の問題**であることが圧倒的に多いです。スコアを疑う前に、その語が索引にどう入っているかを確認してください。
</Callout>

## サジェストは別の道具

検索窓に文字を打つたびに出てくる候補は、BM25 とは別の仕組みです。ここで必要なのは「**この接頭辞で始まる語**」を高速に引くことなので、トライ木の出番です。

トライのノートで見た通り、接頭辞での絞り込みは**打った文字数ぶんの手数**で終わり、登録語数には依存しません。そこから候補を数件選ぶところで、ヒープを使って Top-K を取ります。

`Design Search Autocomplete System` は、この2つを組み合わせるだけの問題です。実務の検索システムの、いちばん小さい縮図になっています。
