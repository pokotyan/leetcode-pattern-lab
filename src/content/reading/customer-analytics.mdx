## 新しい設計はいらない

顧客データを扱う製品の代表が CDP（Customer Data Platform）です。CDP Institute は CDP を「software that creates and maintains a persistent, unified customer record that is accessible to other systems（永続的で統合された顧客の記録を作って保ち、ほかのシステムから使えるようにするソフトウェア）」と定義しています（[CDP Institute: What is a CDP?](https://www.cdpinstitute.org/learning-center/what-is-a-cdp/)）。その画面に並ぶ「売上の上位 1 割の顧客」「最近来ていない優良顧客」「月ごとの継続率」といった集計は、製品を入れるかどうかとは別に、ここまでの回で作った表から組み立てられます。

この回で使うのは次の 2 つだけです。

- 注文のファクト `fct_orders`（1 行 = 注文 1 件。顧客のキー、注文日、金額を持つ）
- 顧客のディメンション `dim_customer`（<a href={`${import.meta.env.BASE_URL}reading/dwh-dimension-tables/`}>ディメンションテーブルの設計</a>）

いずれの集計も、注文の粒度から顧客の粒度へ粗くする操作です。<a href={`${import.meta.env.BASE_URL}reading/dwh-principles/`}>粒度は粗くできるが細かくは戻せない</a>ので、顧客ごとの要約だけを持って注文を捨てると、後から別の切り口で集計し直せなくなります。要約は、注文のファクトを残したうえで足すものです。

## 実験に使ったデータ

DuckDB 1.4.3 で、顧客 2 万人が 2024 年の各月に初回購入し、その後は月ごとに確率 0.35 × 0.9^(経過月) で買いに来る、という注文を作りました。1 回の金額は顧客ごとの係数で大きく偏らせています。結果は 2024-01-01〜2025-12-28 の注文 72,369 件です。作り方は乱数によるもので、実在の購買の分布を表すものではありません。

## デシル分析

顧客を購入額の多い順に 10 等分し、各段（デシル）が売上の何割を占めるかを見ます。SQL の `NTILE(10)` は、並べた行を 10 個のなるべく同じ大きさの組に分けて、1 から 10 の番号を振る関数です。

```sql
WITH t AS (
  SELECT customer_id, sum(amount) AS m FROM fct_orders
  WHERE order_date BETWEEN DATE '2025-01-01' AND DATE '2025-12-31' GROUP BY 1
), d AS (SELECT *, NTILE(10) OVER (ORDER BY m DESC) AS decile FROM t)
SELECT decile, count(*) AS customers, sum(m) AS sales,
       round(100.0 * sum(m) / sum(sum(m)) OVER (), 1) AS share_pct,
       round(100.0 * sum(sum(m)) OVER (ORDER BY decile) / sum(sum(m)) OVER (), 1) AS cum_pct
FROM d GROUP BY decile ORDER BY decile;
```

```text
┌────────┬───────────┬──────────┬───────────┬─────────┐
│ decile │ customers │  sales   │ share_pct │ cum_pct │
├────────┼───────────┼──────────┼───────────┼─────────┤
│      1 │      1468 │ 62130382 │      36.1 │    36.1 │
│      2 │      1468 │ 32869768 │      19.1 │    55.2 │
│      3 │      1468 │ 22686572 │      13.2 │    68.4 │
│      4 │      1468 │ 16626179 │       9.7 │    78.1 │
│      5 │      1468 │ 12254843 │       7.1 │    85.2 │
│      6 │      1468 │  9068904 │       5.3 │    90.4 │
│      7 │      1468 │  6599028 │       3.8 │    94.3 │
│      8 │      1468 │  4754167 │       2.8 │    97.0 │
│      9 │      1467 │  3241631 │       1.9 │    98.9 │
│     10 │      1467 │  1837951 │       1.1 │   100.0 │
└────────┴───────────┴──────────┴───────────┴─────────┘
```

2025 年に買った 14,678 人のうち、上位 2 つのデシル（上位 2 割）で売上の 55.2% を占めています。売上が一部の顧客にどれだけ偏っているかを、1 枚の表で読めるのがデシル分析です。14,678 は 10 で割り切れないので、`NTILE` は上の段から 1 人ずつ多く割り当てています（1〜8 段が 1,468 人、9・10 段が 1,467 人）。

限界は、金額しか見ていないことです。1 回だけ大きく買った顧客と、毎月少しずつ買い続ける顧客が同じ段に入ります。

## RFM 分析

顧客を 3 つの値で評価します。Optimove の解説は、それぞれを次のように定義しています（[Optimove: RFM Segmentation](https://www.optimove.com/resources/learning-center/rfm-segmentation)）。

- **Recency**：「How much time has elapsed since a customer’s last activity or transaction with the brand?（最後の取引からどれだけ経ったか）」
- **Frequency**：「How often has a customer transacted …during a particular period of time?（一定期間に何回取引したか）」
- **Monetary**：「how much a customer has spent with the brand during a particular period of time（一定期間にいくら使ったか）」

それぞれを何段かに分けて点を付け、組み合わせで顧客を分けます。段の数は資料によって違い、Optimove は 4 段（3 段も可）を勧め、それより多い段数は勧めていません（同上）。ここではシミュレーターに合わせて 5 段にし、5 を最もよい点にします。

```sql
WITH base AS (
  SELECT customer_id, DATE '2025-12-31' - max(order_date) AS r, count(*) AS f, sum(amount) AS m
  FROM fct_orders WHERE order_date BETWEEN DATE '2025-01-01' AND DATE '2025-12-31' GROUP BY 1
), s AS (
  SELECT *, 6 - NTILE(5) OVER (ORDER BY r ASC)  AS rs,
            6 - NTILE(5) OVER (ORDER BY f DESC) AS fs,
            6 - NTILE(5) OVER (ORDER BY m DESC) AS ms FROM base
)
SELECT rs, fs, ms, count(*) AS customers FROM s GROUP BY ALL ORDER BY customers DESC LIMIT 5;
```

```text
┌───────┬───────┬───────┬───────────┐
│  rs   │  fs   │  ms   │ customers │
├───────┼───────┼───────┼───────────┤
│     1 │     1 │     1 │       879 │
│     2 │     2 │     1 │       521 │
│     1 │     1 │     2 │       511 │
│     5 │     5 │     5 │       507 │
│     1 │     1 │     3 │       474 │
└───────┴───────┴───────┴───────────┘
```

最も多いのは 111（最近来ておらず、回数も金額も少ない）、その次の 4 番目に 555（最近よく来て、たくさん使う）が並びます。点の組み合わせは 5 × 5 × 5 = 125 通りあるので、実務では「R と F がともに高い」「R が低く F が高い」のように、いくつかの区分にまとめて名前を付けます。

### 同じ値が多いと、段の境目が値と関係なく切られる

`NTILE` は行の数で等分するので、同じ値の顧客が段の境目をまたぐと、同じ値なのに別の点が付きます。回数（F）の分布を見ると、それがはっきり出ます。

```text
┌───────┬───────────┬───────────┬───────────┐
│   f   │ customers │ min_score │ max_score │
├───────┼───────────┼───────────┼───────────┤
│     1 │      6852 │         1 │         3 │
│     2 │      4635 │         3 │         4 │
│     3 │      2165 │         4 │         5 │
│     4 │       784 │         5 │         5 │
└───────┴───────────┴───────────┴───────────┘
```

1 回しか買っていない 6,852 人に、1 点から 3 点までが付いています。どの顧客が何点になるかは、同じ値の中での並び順で決まり、業務上の意味はありません。回数のように値の種類が少ない軸では、`NTILE` ではなく「1 回は 1 点、2 回は 2 点、5 回以上は 5 点」のように境目を値で決めるほうが説明しやすくなります。

## CPM 分析

CPM（Customer Portfolio Management）分析は、日本の通信販売で使われてきた顧客の分け方です。富士フイルムビジネスイノベーションの解説は、「新規購買からの日数」「累計購買金額」「離反期間」などの指標を基に、顧客を 10 のセグメントに分類し、長期的な顧客育成や LTV（顧客生涯価値）の向上に用いる手法、と説明しています（[富士フイルムビジネスイノベーション: CPM分析とは](https://www.fujifilm.com/fb/ja/solutions/columns/marketing-5696)）。10 の区分は、育ち具合の 5 段階（新規・育成・継続・特売・優良）と、いま買っているか（現役）離れたか（離反）の掛け合わせです（同上）。

RFM との違いについて、同じ解説は、RFM 分析では現在の顧客セグメントが変わると継続的な働きかけができなくなり、その弱点を補うのが CPM 分析だ、としています（同上）。育成の段階という「積み上がるもの」と、現役か離反かという「いまの状態」を分けて持つので、「優良だったが離れた」顧客を「最初から来ない」顧客と区別できます。

どの段階をどの基準で分けるか（何日買わなければ離反か、いくら以上で優良か）は、業務で決めるものです。基準の値を SQL のあちこちに書き込まず、1 か所（変数や設定の表）にまとめておくと、「優良顧客」が資料によって違う意味になるのを防げます。

## コホート分析

同じ月に初めて買った顧客を 1 つの組（コホート）にし、その後の各月に何割が買いに来たかを追います。

```sql
WITH first AS (SELECT customer_id, date_trunc('month', min(order_date)) AS cohort FROM fct_orders GROUP BY 1),
act AS (SELECT DISTINCT customer_id, date_trunc('month', order_date) AS m FROM fct_orders),
size AS (SELECT cohort, count(*) AS n FROM first GROUP BY 1),
ret AS (
  SELECT f.cohort, date_diff('month', f.cohort, a.m) AS k, count(*) AS active
  FROM act a JOIN first f USING (customer_id) GROUP BY 1, 2
)
SELECT ... -- 経過月 k を列に並べ替える（PIVOT）
```

```text
┌─────────┬───────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
│ cohort  │   n   │   m0   │   m1   │   m2   │   m3   │   m4   │   m5   │   m6   │
├─────────┼───────┼────────┼────────┼────────┼────────┼────────┼────────┼────────┤
│ 2024-01 │  1667 │  100.0 │   30.5 │   28.0 │   27.4 │   21.5 │   20.2 │   19.0 │
│ 2024-02 │  1728 │  100.0 │   31.4 │   27.3 │   24.2 │   22.9 │   21.1 │   18.6 │
│ 2024-03 │  1659 │  100.0 │   30.0 │   28.0 │   24.7 │   23.0 │   20.0 │   19.7 │
│ 2024-04 │  1651 │  100.0 │   31.2 │   27.6 │   25.7 │   24.2 │   20.7 │   19.4 │
└─────────┴───────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┘
```

行がコホート、列が初回からの経過月です。翌月に約 3 割が戻り、6 か月後には約 2 割になります。コホートを縦に並べると、施策を変えた月の前後で継続率が変わったかを比べられます。

表を縦長にした `ret`（コホート × 経過月 × 人数）は、<a href={`${import.meta.env.BASE_URL}reading/wide-long/`}>縦持ち</a>の形です。経過月を列に並べるのは見せるときだけにして、保存する表は縦長にしておくと、経過月がいくつ増えても表の形が変わりません。

<Callout type="warn" title="観測していない月を、離れたと読まない">
  新しいコホートほど、観測できた月が短くなります。このデータは 2025-12 で終わっているので、2024-12 のコホートは 12 か月後まで、2024-11 は 13 か月後までしか値がありません。表の右下が空いているのは、まだ時間が経っていないだけです。同じ理由で、「2 回目を買った人の割合」のような指標は、直近のコホートほど低く出ます。比べるときは「初回から 90 日以内に 2 回目」のように、観測する期間をそろえます。
</Callout>

## 点数や区分をどこに置くか

RFM の点や CPM の区分は、どの表のどこに持つべきでしょうか。選択肢は 4 つあります。

| 置き方 | 向いている場面 |
| --- | --- |
| 1. 毎回、問い合わせで計算する | 定義を試している段階。表が増えず、基準を変えるのも簡単 |
| 2. 顧客のディメンションの属性にする | 多くのダッシュボードで、絞り込みやグループ化に繰り返し使う |
| 3. 顧客のキーだけの表に保存する | 施策ごとに抽出した顧客の集まりを、後で何度も使う |
| 4. 時点ごとに記録する | 区分の移り変わり（先月は優良、今月は離反）を追う |

2 について、Kimball Group は予測分析の入力として、顧客の恒久的なキーを主キーにし、その分析のために用意した印・回数・金額を持つ表を例に挙げています。そのうえで、それらの値が「stable and regularly used for query filtering and grouping beyond predictive analysis（予測分析以外でも、安定して、絞り込みとグループ化に繰り返し使われる）」なら、顧客ディメンションの恒久的な属性にしてよい、としています（[Kimball Group: Design Tip #172](https://www.kimballgroup.com/2015/02/design-tip-172-leverage-dimensional-model-predictive-analytics/)）。

3 は、Kimball が行動調査グループ（behavior study group）と呼ぶ型です。「a simple table, called a _study group_, consisting only of the customers' durable keys（顧客の恒久的なキーだけでできた単純な表）」を作っておけば、顧客ディメンションを持つどのスキーマにも絞り込みとして使え、複数のグループの積・和・差から新しいグループも作れる、とされています（[Kimball Group: Behavior Study Groups](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/behavior-study-group/)）。CDP の「セグメント」機能が保存しているのは、この表にあたります。

4 は、<a href={`${import.meta.env.BASE_URL}reading/dwh-fact-tables/`}>ファクトテーブルの設計</a>で見た定期スナップショットそのものです。1 行 = 顧客 1 人 × 1 か月で、月末の区分と点数を記録し、過去の行は書き換えません。

```sql
-- 1 行 = 顧客 1 人 × 1 か月（月末時点）
CREATE TABLE fct_customer_segment_monthly (
  month_key    INTEGER NOT NULL,   -- YYYYMM
  customer_key INTEGER NOT NULL,
  cpm_segment  VARCHAR NOT NULL,
  rfm_cell     VARCHAR
);
```

区分は、その時点の注文と基準から計算した結果です。後から基準日を過去に戻して計算し直すことはできても、そのときの基準（当時の「優良」の金額）や、遅れて届いた注文・取消の反映までは再現できません。**区分の移り変わりを見たくなる日が来そうなら、要件が固まる前から月末の記録だけは貯め始めておく**のが安全です。

<Callout type="note" title="基準日を固定する">
  `current_date` を使った集計は、流すたびに結果が変わります。この回の SQL が `DATE '2025-12-31'` のように基準日を書いているのは、同じ数字を後から再現できるようにするためです。実務では基準日を引数として受け取る形にします。
</Callout>

## まとめ

| 集計 | 必要な粒度 | 分かること | 注意 |
| --- | --- | --- | --- |
| デシル | 顧客 | 売上の偏り | 金額しか見ない |
| RFM | 顧客 | いまの顧客の状態 | 同じ値が多い軸では NTILE の境目が恣意的になる |
| CPM | 顧客 | 育成の段階と、現役か離反か | 基準は業務で決め、1 か所にまとめる |
| コホート | 顧客 × 月 | 継続率と、その変化 | 観測期間の短い直近のコホートを読み違えない |
| 区分の移り変わり | 顧客 × 月 | 施策の効果 | 月末の記録を貯めておかないと、後から作れない |

どれも、注文のファクトと顧客のディメンションという、ここまでに作った表の上で書けました。新しく作ったのは、顧客 1 人 1 行の要約と、顧客 × 月の記録だけです。粒度をそろえて持っておけば、名前の付いた分析手法はその上の問い合わせとして後から足せる、というのがこのカテゴリの結論です。
