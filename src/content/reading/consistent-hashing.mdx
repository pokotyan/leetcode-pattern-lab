## 1台に収まらなくなったとき

キャッシュの設計の記事では、「容量がいっぱいになったとき何を捨てるか」を扱いました。LRU と LFU です。

台数が増えると、その手前にもう1つ問いが生まれます。

> **このキーは、どのサーバーに置くのか**

読むときも書くときも同じ答えが出ないといけません。さもないと、書いたサーバーと読みに行くサーバーが食い違い、キャッシュが当たらなくなります。

素直な方法は、ハッシュを台数で割ることです。

```python
node = nodes[hash(key) % len(nodes)]
```

キーが決まれば行き先が一意に決まり、分布も均等です。何も問題がないように見えます。

## 台数が変わった瞬間に壊れる

問題は、**台数が変わったとき**に起きます。

サーバーを 3 台から 4 台に増やすと、`% 3` が `% 4` に変わります。すると、**ほとんどすべてのキーの行き先が変わります。**

| キーのハッシュ | 3台のとき | 4台のとき |
| --- | --- | --- |
| 10 | 10 % 3 = 1 | 10 % 4 = 2 |
| 11 | 11 % 3 = 2 | 11 % 4 = 3 |
| 12 | 12 % 3 = 0 | 12 % 4 = 0 |
| 13 | 13 % 3 = 1 | 13 % 4 = 1 |

3 台から 4 台では、およそ **4 分の 3 のキーが移動**します。キャッシュなら、その瞬間にほぼ全件がミスになり、背後のデータベースに一斉にアクセスが飛びます。これは実際にサービスを落とす規模の負荷になります。

保存が目的のデータベースなら、さらに深刻です。大部分のデータを**物理的に別のサーバーへ移す**必要があります。

欲しいのは、次の性質です。

> ノードを 1 台増やしたとき、**移動するキーは全体の 1/N 程度で済む**

## 発想を変える：キーもノードも同じ円の上に置く

ハッシュ値を「どのノードか」ではなく、**円周上の位置**として使います。

1. ハッシュ値の取りうる範囲（たとえば 0 から 2<sup>32</sup>−1）を、**円**だと考える
2. **ノード**をハッシュして、円の上に配置する
3. **キー**もハッシュして、円の上に配置する
4. キーの位置から**時計回りに進み、最初に出会ったノード**が担当する

```python
import bisect

class HashRing:
    def __init__(self, nodes, vnodes=1):
        self.ring = []                       # (位置, ノード名) を位置順に保つ
        for n in nodes:
            for i in range(vnodes):
                self.ring.append((hash_ring(f"{n}#{i}"), n))
        self.ring.sort()

    def node_for(self, key):
        pos = hash_ring(key)
        i = bisect.bisect_left(self.ring, (pos, ''))   # pos 以上で最初の点
        if i == len(self.ring):
            i = 0                            # 一周して先頭に戻る
        return self.ring[i][1]
```

<ConsistentHashing client:visible />

ノード D を追加したとき、**担当が変わるのは D の直前の区間にいたキーだけ**です。それ以外のキーは、時計回りで最初に出会うノードが変わらないので、そのまま動きません。シミュレーターの最後に、余りで決める方式との比較が出ます。

<Callout type="tip" title="bisect が出てくるところ">
  `node_for` の中身は、「位置順に並んだ配列から、`pos` 以上で最初の要素を探す」という操作です。二分探索の記事でやった**下界（lower bound）そのもの**です。

  見つからなかった場合（`pos` がリング上の最後のノードより後ろ）に `i = 0` として先頭へ戻しているのが、「円である」ことを表現している唯一の部分です。**データ構造としてはただのソート済み配列で、円なのは解釈だけ**です。

  ノード数が数百程度なら、二分探索は O(log N) = 10 回程度です。キーを引くたびに走りますが、無視できるコストです。
</Callout>

## そのままでは偏る：仮想ノード

素朴に実装すると、すぐ問題が出ます。**ノードが円周上に均等に並ばない**のです。

ハッシュはランダムに散らばるので、3 台なら円周を 3 等分してはくれません。ある区間が極端に長くなり、そのノードだけが全体の半分を担当する、といったことが普通に起きます。

さらに、ノードが 1 台落ちると、**その区間を丸ごと隣の 1 台が引き受けます。** 負荷が 2 倍になり、そこも落ちる、という連鎖が起きえます。

対策は単純です。**1 台のノードを、円の上に何十〜何百点も置きます。**

```python
for i in range(vnodes):
    self.ring.append((hash_ring(f"{n}#{i}"), n))   # A#0, A#1, A#2, ...
```

これが仮想ノード（virtual node）です。1 台が円周上のあちこちに小さな区間をたくさん持つ形になるので、

- 区間の長さの偏りが**平均化される**（大数の法則）
- ノードが落ちたとき、その負荷は**残りの全ノードに分散する**（1 台に集中しない）

シミュレーターの「仮想ノード3点」で、同じノードが複数の位置に現れる様子を確認できます。実際のシステムでは 100〜300 点程度を使うのが普通です。

<Callout type="warn" title="ハッシュだけでは解決しない偏り：ホットキー">
  仮想ノードで解決するのは**キーの個数**の偏りだけです。特定のキーへのアクセスが極端に多い場合（人気商品の在庫、有名人のプロフィール）、そのキーを持つノードだけが過負荷になります。これがホットキー問題です。

  ハッシュの工夫では解決しません。別の手を打ちます。

  - **そのキーだけ複数ノードに複製する**（読み取り専用なら効く）
  - **キーに接尾辞を付けて分割する**（`item123#0` 〜 `item123#9` に分け、読むときは全部を集める）
  - **手前にローカルキャッシュを置く**（アプリ側のメモリで吸収する）

  「分散したのに1台が重い」という症状を見たら、まず**キーの個数ではなくアクセス回数の分布**を確認してください。
</Callout>

## Sharding：同じ話を保存側で

キャッシュではなくデータベースを分割するとき、同じ問題が「シャーディング」という名前で出てきます。分け方の選択肢は主に 3 つです。

| 方式 | 決め方 | 得意なこと | 苦手なこと |
| --- | --- | --- | --- |
| **ハッシュ** | `hash(key)` で決める | 均等に散らばる | 範囲検索ができない（連続するキーが別のノードへ行く） |
| **範囲** | キーの範囲で区切る（a〜f は 1 号機） | 範囲検索が1ノードで済む | 偏りやすい。時系列 ID だと常に末尾のノードに書き込みが集中する |
| **ディレクトリ** | 対応表を別に持つ | 自由に移動できる | 対応表が単一障害点になる |

**範囲で分けたときの「末尾集中」**は、実務でよく踏みます。ID が時刻順に増えていくと、新しいデータは常に最後のシャードに入るので、書き込みが 1 台に集まります。対策として、キーの先頭にハッシュ由来の接頭辞を付けて散らす（salting）ことがよく行われます。

<Callout type="tip" title="分割したあとに困ること">
  分割そのものより、**分割したあとにできなくなること**のほうが設計上は重要です。

  - **複数シャードにまたがる結合（JOIN）** が、1 回のクエリでできなくなる
  - **複数シャードにまたがるトランザクション**が、単純にはできなくなる（この話は分散トランザクションの記事で扱います）
  - **一意性の保証**（ユニーク制約）が、シャードをまたぐと効かない
  - **集計**が、全シャードに問い合わせて足し合わせる形になる

  だから、**「何をキーにして分けるか」が設計のほぼすべて**になります。一緒に取り出すデータが同じシャードに載るようにキーを選べば、上の問題の多くは起きません。逆にここを間違えると、あとから直すのは全データの移動を伴います。
</Callout>

## まとめ

- 台数で割る方式は、台数が変わると**ほぼ全キーが移動**する
- キーとノードを同じ円に置き、時計回りで担当を決めると、移動は **1/N 程度**で済む
- 担当ノードを引く操作は、ソート済み配列に対する**下界の二分探索**
- 素朴な配置は偏るので、**仮想ノード**で 1 台を多数の点に分ける
- アクセス回数の偏り（ホットキー）は、ハッシュでは解決しない
- 保存側で同じ問題を扱うのがシャーディング。**分割キーの選択がすべてを決める**
