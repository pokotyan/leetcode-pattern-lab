## 2 つの整数で部分木を表す

<a href={`${import.meta.env.BASE_URL}reading/tree-path-enumeration/`}>経路列挙</a>は、根からの道のりを文字列で持つことで再帰をなくしました。入れ子集合（nested set）は、同じことを 2 つの整数で行います。SQL の著述家 Joe Celko が著書（『Joe Celko's Trees and Hierarchies in SQL for Smarties』）などで広めた方式で、SQL で木を扱う方法として古くから知られています。

番号の振り方は次のとおりです。根から深さ優先で木をたどり、カウンタを 1 つずつ進めながら、ノードに**入るとき**の番号を `lft`、**出るとき**の番号を `rgt` に書きます。

```text
商品 [1, 20]
├─ 家電 [2, 11]
│   ├─ PC [3, 8]
│   │   ├─ ノート [4, 5]
│   │   └─ デスク [6, 7]
│   └─ カメラ [9, 10]
└─ 食品 [12, 19]
    └─ 飲料 [13, 18]
        ├─ お茶 [14, 15]
        └─ 水 [16, 17]
```

深さ優先でたどるので、あるノードに入ってから出るまでの間に、その子孫すべてに入って出ます。つまり、**子孫の区間は必ず先祖の区間の内側に収まり**、兄弟どうしの区間は重なりません。木の形が、区間の包含関係として番号に写っています。

- 子孫：`lft` が自分の区間 `[lft, rgt]` に入る行
- 先祖：自分の `lft` を区間に含む行
- 葉：`rgt = lft + 1`
- 部分木の大きさ：`(rgt - lft + 1) / 2`

<NestedSet client:visible />

木の下に描いた帯の図は、各ノードの区間 `[lft, rgt]` を数直線の上に、深さごとの段に分けて並べたものです。下の目盛りが番号で、帯の左端が `lft`、右端が `rgt` にあたります。子の帯は必ず親の帯の真下に収まっています。「葉を追加」や「部分木を移動」を選ぶと、帯がまとめて右や左へずれていく様子が見えます。表の `8 → 10` のような表示は、その手順で書き換わった値です。

## 実験の準備

<a href={`${import.meta.env.BASE_URL}reading/tree-tables/`}>4 つの方式の比較</a>と同じ、10 分岐・深さ 5 の 111,111 ノードの木を PostgreSQL 17.11 に作りました。番号は「ゼロ埋めした経路の辞書順」で行きがけ順を求め、`lft = 2 × 行きがけ順 − 深さ − 1`、`rgt = lft + 2 × 部分木の大きさ − 1` で計算しています。

```sql
CREATE TABLE ns (id int PRIMARY KEY, lft int NOT NULL, rgt int NOT NULL, name text NOT NULL);
CREATE INDEX ns_lft ON ns(lft);
CREATE INDEX ns_rgt ON ns(rgt);
```

```text
 id  |  lft   |  rgt   |  name
-----+--------+--------+---------
   1 |      1 | 222222 | node1
   2 |      2 |  22223 | node2
  12 |      3 |   2224 | node12
 112 |      4 |    225 | node112
  11 | 200000 | 222221 | node11
```

根の区間は `[1, 222222]` で、ちょうどノード数の 2 倍です。表の大きさは索引 2 本込みで 13 MB でした。

## 子孫：BETWEEN 1 回

id 2（11,111 ノード）の子孫を数えます。

```sql
SELECT count(*) FROM ns c JOIN ns p ON c.lft BETWEEN p.lft AND p.rgt WHERE p.id = 2;
```

```text
   ->  Nested Loop (actual rows=11111 loops=1)
         ->  Index Scan using ns_pkey on ns p (actual rows=1 loops=1)
               Index Cond: (id = 2)
         ->  Index Only Scan using ns_lft on ns c (actual rows=11111 loops=1)
               Index Cond: ((lft >= p.lft) AND (lft <= p.rgt))
   Buffers: shared hit=55
 Execution Time: 1.026 ms
```

主キーで親の区間を読み、`lft` の索引を `[2, 22223]` の範囲で走査するだけです。1 回目の測定は 2.083 ms、2 回目は 1.026 ms・55 ブロックでした。隣接リストの再帰（182 ブロック）よりも、経路列挙の前方一致（78 ブロック）よりも少ない読み取りで済んでいます。整数の比較だけなので、索引の幅も小さく済みます。

## 先祖：索引の片側しか使えない

先祖は「自分の `lft` を区間に含む行」、つまり `a.lft <= c.lft AND c.lft <= a.rgt` です。木の左端に近い葉（id 11112）では速く終わります。

```text
=== 先祖: 入れ子集合（id 11112）
         ->  Index Scan using ns_lft on ns a (actual rows=6 loops=1)
               Index Cond: (lft <= c.lft)
               Buffers: shared hit=4
 Execution Time: 0.036 ms
```

ところが、同じ問い合わせを木の右端の葉（id 111111）で実行すると、結果が大きく変わります。

```text
=== 入れ子集合: 先祖（右端の葉 111111）
   ->  Nested Loop (actual rows=6 loops=1)
         Buffers: shared hit=744 read=273
         ->  Index Scan using ns_lft on ns a (actual rows=6 loops=1)
               Index Cond: (lft <= c.lft)
               Filter: (c.lft <= rgt)
               Rows Removed by Filter: 111105
 Execution Time: 10.949 ms
```

先祖 6 行を得るために、**111,105 行を読んで捨てています**。B-tree の索引は 1 つの列の範囲しか絞れないので、`lft <= c.lft` の側は索引で絞れても、`rgt >= c.lft` は読んだ行を 1 つずつ確かめるしかありません。右端の葉では「自分より左にあるすべてのノード」、つまりほぼ全行が `lft <= c.lft` を満たします。

対策の 1 つは、区間そのものに索引を張ることです。PostgreSQL の範囲型と GiST 索引を使うと、「この点を含む区間」を索引で直接引けます。追加で測りました（`BEGIN` 〜 `ROLLBACK` の中で索引を作って測っています）。

```sql
CREATE INDEX ns_range ON ns USING gist (int4range(lft, rgt, '[]'));
SELECT count(*) FROM ns a JOIN ns c ON int4range(a.lft, a.rgt, '[]') @> c.lft WHERE c.id = 111111;
```

```text
         ->  Bitmap Heap Scan on ns a (actual rows=6 loops=1)
               Recheck Cond: (int4range(lft, rgt, '[]'::text) @> c.lft)
               ->  Bitmap Index Scan on ns_range (actual rows=6 loops=1)
                     Index Cond: (int4range(lft, rgt, '[]'::text) @> c.lft)
   Buffers: shared hit=11 read=3
 Execution Time: 1.339 ms
```

読んだブロックは 1,017 から 14 に減りました。入れ子集合の読み取りの速さは「区間の問い合わせを索引で引けること」に支えられていて、B-tree だけでは子孫の側にしか効かない、という点は押さえておく必要があります。

## 葉の追加：右側の番号がすべてずれる

ここからが入れ子集合の弱点です。id 112（左寄りのノード）の最後の子として葉を 1 つ足します。新しい葉は親の `rgt` の位置に `[rgt, rgt + 1]` を使うので、その位置以降の番号をすべて 2 ずつ右へずらし、隙間を開けてから入れます。

```sql
UPDATE ns SET rgt = rgt + 2 WHERE rgt >= (SELECT rgt FROM ns WHERE id = 112);
UPDATE ns SET lft = lft + 2 WHERE lft >  (SELECT rgt - 2 FROM ns WHERE id = 112);
INSERT INTO ns SELECT 200000, rgt - 2, rgt - 1, 'new' FROM ns WHERE id = 112;
```

```text
UPDATE 111001
Time: 705.625 ms
UPDATE 110997
Time: 717.534 ms
INSERT 0 1
```

**1 行を足すために、11 万行の rgt と、11 万行の lft を書き換え**、それぞれ 0.7 秒かかりました。隣接リスト・経路列挙・閉包テーブルでは、同じ操作がそれぞれ 1 行・1 行・6 行の書き込みです。同じ追加を木の右端（id 11111 の下）で行うと、結果は逆になります。

```text
UPDATE 5
UPDATE 0
```

右側にノードがほとんどないので、書き換えるのは先祖 5 行の `rgt` だけです。入れ子集合の書き込みの重さは「足す位置より右に何ノードあるか」で決まり、木の左に足すほど重くなります。

## 部分木の移動：4 段階の付け替え

部分木の移動は、追加よりさらに手間がかかります。番号の区間を切り取って別の場所に差し込むので、一般には次の 4 段階を踏みます。ステップ実行の「部分木を移動」はこの順に進みます。

1. 移す部分木の番号を負にして、いったん数直線の外へ退避する
2. 抜けた幅 w の穴を詰める（右側の番号を w だけ左へ）
3. 移動先の親の `rgt` の位置に、幅 w の穴を開ける（そこより右の番号を w だけ右へ）
4. 退避した部分木を、穴の位置へずらして戻す

id 12（1,111 ノード）を id 11 の下へ移し、値が変わった行を数えました。移動後に「12 の区間が 11 の区間の内側にあるか」「番号が重複していないか」「1 から 222222 まで隙間がないか」も確かめています。

```text
=== 入れ子集合: 部分木の移動で値が変わった行数
DO
Time: 1418.608 ms (00:01.419)
 changed
---------
  111110

 moved_inside | numbers_unique | no_gaps
--------------+----------------+---------
 t            | t              | t
```

1,111 ノードを移すために、**根以外の全行（111,110 行）の番号が変わりました**。id 12 は木の左端に近く、id 11 は右端にあるので、その間にあるノードがすべて一度は左へ、または右へずれたためです。隣接リストなら `UPDATE 1`、経路列挙なら部分木の 1,111 行で済む操作です。

## 並行して書くと、互いに待つ

番号の付け直しは、書き込みの量だけでなく、並行性にも響きます。2 つのトランザクションが木の離れた場所にそれぞれ葉を足す、という状況を作りました。A は id 112 の下に足して、コミットせずに 3 秒保持します。その間に B が、木の反対側の id 11111 の下に足します。B には `lock_timeout = '1s'` を設定しています。

```text
--- 入れ子集合: A が 112 の下に追加（未コミットのまま 3 秒保持）
--- B が離れた枝 11111 の下に追加（lock_timeout 1s）
ERROR:  canceling statement due to lock timeout
CONTEXT:  while updating tuple (707,102) in relation "ns"
Time: 1004.492 ms (00:01.004)

--- 隣接リスト: 同じ組み合わせ
Time: 0.785 ms
```

B が書き換えるのは先祖 5 行の `rgt` だけですが、その中には根（と id 11 などの上位のノード）が含まれます。A は 11 万行を書き換えていて、根の行のロックも持っています。どこに足しても根の `rgt` は必ず変わるので、**入れ子集合への書き込みは、木のどこであっても互いに直列になります**。隣接リストでは、2 つの INSERT は別々の行なので待ち合いません。

<Callout type="warn" title="番号の隙間を空けておく工夫">
  番号を 1 刻みでなく 100 刻みなどで振っておき、隙間に新しいノードを入れて付け直しを減らす工夫があります。番号を有理数や浮動小数点数にして、2 つの番号の間に必ず新しい番号を作れるようにする派生（入れ子区間など）も提案されています。ただし隙間はいずれ尽き、そのときは全体の付け直しになります。書き込みが多い木の問題を根本から解く方法ではありません。
</Callout>

## 親と深さを出すのが面倒

入れ子集合の表には、親が誰かも、深さがいくつかも直接は書いてありません。

- 親：自分を区間に含む行のうち、`lft` が最大のもの（いちばん内側の先祖）
- 深さ：自分を区間に含む行の数 − 1
- 直下の子だけ：子孫のうち、間に別の先祖を挟まないもの

どれも先祖や子孫を一度集めてから絞る問い合わせになり、隣接リストの「`parent_id` を見るだけ」「`WHERE parent_id = ?`」に比べて書くのも読むのも重くなります。実務では、`parent_id` や `depth` の列を併せて持つことがよくあります。その場合は、番号を付け直すたびにそれらとの整合も保つ必要があります。

## 長所と短所

| 観点 | 入れ子集合 |
| --- | --- |
| 子孫を取る | BETWEEN 1 回。整数の範囲走査で、4 方式の中でも読む量が少ない |
| 先祖を取る | B-tree だけでは片側しか絞れず、右寄りのノードで遅い。区間型の索引で解消できる |
| 親・直下の子・深さ | 表に直接ない。問い合わせが複雑になる |
| 葉の追加 | 足す位置より右のノードを全部書き換える |
| 部分木の移動 | 4 段階の付け替え。最悪でほぼ全行 |
| 並行書き込み | 根の行を必ず書き換えるので、木全体で直列になる |
| 参照整合性 | 番号の正しさを DB は守らない。区間が重なる・交差する行を作れる |

向いているのは、**読むことがほとんどで、変わるときはまとめて作り直せる木**です。商品カテゴリや地域区分のようなマスタを夜間のバッチで作り直し、日中はひたすら読む、という使い方なら、付け直しの重さは問題になりません。逆に、ユーザーの操作で頻繁にノードが増えたり動いたりする木（コメントのスレッド、組織図の編集画面など）には向きません。

次回の<a href={`${import.meta.env.BASE_URL}reading/tree-closure-table/`}>閉包テーブル</a>は、番号を詰める代わりに「先祖と子孫のすべての組」を別の表に持ちます。読み取りは入れ子集合と同じく 1 回の索引で済み、書き込みは木全体ではなく、触ったノードの深さと部分木の大きさにだけ比例します。
