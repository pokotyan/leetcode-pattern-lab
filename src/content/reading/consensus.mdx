## 3台に同じ数字を書きたいだけなのに

サーバーを 3 台に増やしました。どれに聞いても同じ答えが返ってきてほしい。それだけです。

ところが、次のどれも実際に起こります。

- 1 台目に書き込んだ直後、2 台目に複製する前にプロセスが落ちる
- ネットワークが切れて、1 台目と 2 台目が互いに見えなくなる
- 3 台目からの応答が遅い。落ちているのか、単に遅いのかが**区別できない**

最後が特に厄介です。分散システムでは、**「落ちている」と「遅い」を確実に見分ける方法がありません。** 応答が無いとき、相手が死んだのか、返事が途中で詰まっているのかは分かりません。

この前提のもとで「全員が同じ答えを持つ」を実現するのが、分散合意の問題です。

## CAP：3つのうち2つしか選べない

考えを整理するための枠組みが CAP です。次の 3 つを同時には満たせない、という主張です。

| | 意味 |
| --- | --- |
| **C**onsistency | どのノードに聞いても、最新の同じ値が返る |
| **A**vailability | どのノードも、必ず応答を返す |
| **P**artition tolerance | ネットワークが分断されても動き続ける |

ここで大事なのは、**P は選択肢ではない**ということです。ネットワークは必ず切れます。ケーブルは抜けるし、スイッチは壊れるし、クラウドのゾーンは落ちます。分散システムを作る以上、P は前提として受け入れるしかありません。

したがって実際の選択は、**分断が起きている最中に C と A のどちらを取るか**になります。

- **CP を選ぶ**：分断された側は「答えられません」とエラーを返す。古い値を返すくらいなら止まる。銀行口座、在庫数、設定情報
- **AP を選ぶ**：分断された側も手元の値で答える。古いかもしれないが、返す。SNS のタイムライン、閲覧数、レコメンド

<Callout type="warn" title="CAP は「常に2つしか選べない」という意味ではありません">
  よくある誤解が、「うちは AP システムだから一貫性は無い」という言い方です。

  CAP が言っているのは、**ネットワークが分断されている最中の話**だけです。正常時は C も A も両方成り立ちます。分断は年に数回、数分間といった頻度で起きるもので、そのわずかな時間にどちらを優先するかを決めておく、という話です。

  また、C と A は 0 か 1 かではありません。実際のシステムは「この操作は強い一貫性、この操作は結果整合で十分」と**操作ごとに使い分けます。** 決済は CP、通知の既読フラグは AP、といった具合です。

  CAP は設計の出発点を整理する道具であって、システムに貼るラベルではありません。
</Callout>

## Quorum：なぜ「過半数」なのか

複数ノードで値を決めるとき、**何台の同意があれば確定してよい**のでしょうか。

全台の同意を求めると、1 台落ちただけで何も決まらなくなります。1 台でよいことにすると、別の 1 台が違う値を持ってしまいます。

答えは**過半数**です。理由は、数学ノードの鳩の巣原理そのものです。

> 全体が N 台のとき、過半数（`N/2` より多い）の集合を 2 つ取ると、**必ず 1 台以上が両方に属する**

2 つの集合の大きさの合計が N を超えるので、重ならないことはありえません。5 台なら、3 台の集合を 2 つ取ると、合計 6 > 5 なので必ず共有があります。

この「必ず重なる」が効くのは、**読み書きの整合を保証する**ときです。

- 書き込みを `W` 台に、読み取りを `R` 台に対して行う
- `W + R > N` なら、読み取り側の集合は**必ず最新を持つノードを 1 台以上含む**
- その中で最も新しい値を採用すれば、古い値を読むことはない

| N | W | R | W + R > N か | 性質 |
| --- | --- | --- | --- | --- |
| 3 | 2 | 2 | 4 > 3 ○ | 標準的な設定。1台落ちても動く |
| 3 | 3 | 1 | 4 > 3 ○ | 読みが速い。書き込みは1台落ちると止まる |
| 3 | 1 | 3 | 4 > 3 ○ | 書きが速い。読みは1台落ちると止まる |
| 3 | 1 | 1 | 2 > 3 × | 速いが、古い値を読みうる（結果整合） |

Cassandra や DynamoDB で `W` と `R` を設定できるのは、この表のどこに立つかを選ばせているからです。

## Raft：leader を1人決めてしまう

過半数で決められると分かっても、**誰が提案するのか**という問題が残ります。全員が勝手に提案すると、衝突の解決が複雑になります（これを正面から解いたのが Paxos で、正しいけれど理解も実装も難しいことで有名です）。

Raft の割り切りはこうです。

> **まず leader を 1 人選ぶ。** 以後、書き込みの提案は leader だけが行う

これで、合意の問題が「**leader を選ぶ**」と「**leader の指示を複製する**」の 2 つに分かれます。どちらも過半数で決めます。

選挙の手順は次の通りです。

1. leader からの定期連絡が途絶えたノードが、**任期（term）を 1 つ上げて立候補**する
2. 全ノードに投票を依頼する
3. 各ノードは、**1 つの任期につき 1 票だけ**投じる
4. 過半数を得た候補が leader になる

```python
def on_election_timeout(self):
    self.term += 1                       # 任期を1つ進める
    self.state = 'candidate'
    self.voted_for = self.id
    votes = 1                            # まず自分の1票
    for peer in self.peers:
        if peer.request_vote(self.term, self.id):
            votes += 1
    if votes > self.cluster_size // 2:   # 過半数を取れたか
        self.state = 'leader'

def request_vote(self, term, candidate_id):
    if term < self.term:
        return False                     # 古い任期からの依頼は拒否
    if term > self.term:
        self.term = term
        self.voted_for = None            # 新しい任期なので投票権が戻る
    if self.voted_for is None:
        self.voted_for = candidate_id
        return True                      # 1つの任期で投票できるのは1回だけ
    return False
```

<Callout type="tip" title="「1任期1票」と「過半数」で二重 leader が防げる">
  2 人が同時に leader になってしまうと、それぞれが別の値を書き込んで壊れます。これを防いでいるのが、次の 2 つの組み合わせです。

  - 各ノードは 1 つの任期につき 1 票しか投じない
  - leader になるには過半数が要る

  同じ任期で 2 人が過半数を集めるには、合計で N を超える票が必要です。ところが票は N 票しかありません。**だから同じ任期に leader は 2 人以上存在できません。** ここでも鳩の巣原理が効いています。

  「票が割れる」のプリセットでは、2 人が同時に立候補して誰も過半数に届かない状況（split vote）が起きます。Raft はこれを、**各ノードの待ち時間をランダムにずらす**ことで解決します。次の任期では、たいてい 1 人だけが先に立候補するので決まります。確率に頼った、単純だが実用的な解決です。
</Callout>

<Callout type="warn" title="ノード数は奇数にする">
  「2台停止で決まらない」のプリセットが示す通り、5 台のうち 2 台が落ちても残り 3 台で過半数を満たせるので動きます。3 台落ちると止まります。

  ここで、**偶数台にする意味がほとんどない**ことに注意してください。

  | 台数 | 過半数 | 耐えられる故障 |
  | --- | --- | --- |
  | 3 | 2 | 1 台 |
  | 4 | 3 | 1 台 |
  | 5 | 3 | 2 台 |
  | 6 | 4 | 2 台 |

  4 台は 3 台と同じ耐障害性しかないのに、合意に必要な台数が 1 つ増えるぶん遅くなります。**etcd や ZooKeeper で「3 台か 5 台」と言われるのは、この表が理由**です。
</Callout>

## Gossip：全員に聞かなくてよい情報の広め方

合意が必要ない情報もあります。「どのノードが生きているか」「クラスタに新しいノードが加わった」といったメンバー情報です。多少遅れて伝わっても構いません。

そこで使われるのが Gossip プロトコルです。

> 各ノードが定期的に、**ランダムに選んだ数台**に自分の知っていることを伝える。伝えられた側も、また別の数台に伝える

噂話が広まるのと同じです。中央の管理者がいないので、単一障害点がありません。

伝播の速さは、確率の見積もりで押さえられます。1 ラウンドで知っているノード数がおよそ倍になるので、**全体に行き渡るまで O(log N) ラウンド**です。1,000 ノードでも 10 ラウンド程度で済みます。

グラフ探索のノードで見た BFS の層と同じ構造ですが、辺が固定ではなく**毎回ランダムに選ばれる**点が違います。そのおかげで、一部のノードが落ちても伝播が止まりません。

| | Raft などの合意 | Gossip |
| --- | --- | --- |
| 保証 | 全員が同じ値で合意する | いつかは全員に伝わる（結果整合） |
| 速さ | 過半数の往復が必要 | 遅いが、止まらない |
| 中央 | leader がいる | いない |
| 使いどころ | 書き込みの順序、設定値 | メンバー情報、障害検知、統計 |

## まとめ

- 分散システムでは「落ちている」と「遅い」を区別できない。ここがすべての出発点
- P は前提。実際の選択は**分断中に C と A のどちらを取るか**
- 過半数どうしは必ず重なる。だから **`W + R > N`** で最新の値に必ず触れられる
- Raft は leader を 1 人決めることで、合意の問題を 2 つに分ける
- 「1 任期 1 票 + 過半数」で、同じ任期に leader が 2 人現れることはない
- ノード数は奇数にする。偶数は遅くなるだけ
- 合意が要らない情報は Gossip で広める。O(log N) ラウンドで行き渡る
