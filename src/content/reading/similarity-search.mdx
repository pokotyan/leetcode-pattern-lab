## 「意味が近い」をどう計算するか

BM25 は語の一致で順位を決めていました。強力ですが、限界があります。

> 「犬の飼い方」で検索した人に、「イヌの育て方」という記事を出したい

語としては一文字も一致しません。転置インデックスでは、この2つは無関係な文書です。

必要なのは、**語そのものではなく意味を突き合わせる**仕組みです。そのために、単語や文書を**ベクトル（数の並び）**に変換します。これが embedding（埋め込み）です。

```
"犬"   → [0.21, -0.44, 0.87, ...]   （数百〜数千次元）
"イヌ" → [0.19, -0.41, 0.90, ...]
"株価" → [-0.62, 0.13, -0.05, ...]
```

似た意味の語が、**近い場所に置かれる**ようにベクトルを作ります。そうすれば「意味が近い」は「ベクトルが近い」という幾何の問題に変わります。

<Callout type="tip" title="ベクトルはどこから来るのか">
  この記事では「意味を表すベクトルが与えられている」ところから始めます。作り方は大きく2系統あります。

  - **共起から作る**：「同じ文脈に出てくる語は意味が近い」という前提で、周辺語の統計からベクトルを決める（word2vec など）
  - **タスクを解かせて副産物として得る**：大量の文章で「次の語を当てる」訓練をすると、その途中の表現が意味を捉えたベクトルになる（Transformer 系のモデル）

  Transformer の中身（attention の仕組み）はこの教材の範囲を超えますが、**出力として得られるのはただのベクトルで、そのあとの検索の仕組みは以下とまったく同じ**です。「AI 検索」と呼ばれているものの後半は、ここに書いてあることでできています。
</Callout>

## 近さの測り方：コサイン類似度

2 つのベクトルが「近い」とは何でしょうか。幾何のノートで見たユークリッド距離が素直ですが、意味の比較では**別の測り方**を使うのが普通です。

```
cos(a, b) = (a と b の内積) / (a の長さ × b の長さ)
```

内積を、それぞれの長さで割っています。割ることで**長さの影響が消え、向きだけが残ります。**

なぜ長さを無視したいかというと、文書の長さや語の出現回数がベクトルの長さに出てしまうからです。「犬」について 100 語書いた文書と 1,000 語書いた文書は、**向きは同じで長さだけが違う**はずです。この 2 つを別物と扱いたくありません。

値は −1 から 1 の範囲で、1 に近いほど同じ向きです。

```python
import heapq, math

def top_k_similar(query, docs, k):
    heap = []                                  # (類似度, id) の最小ヒープ
    for i, v in enumerate(docs):
        dot = sum(a * b for a, b in zip(query, v))
        norm = math.sqrt(sum(a * a for a in query)) * math.sqrt(sum(b * b for b in v))
        cos = dot / norm                       # 長さで割るので、向きだけが効く
        if len(heap) < k:
            heapq.heappush(heap, (cos, i))
        elif cos > heap[0][0]:
            heapq.heapreplace(heap, (cos, i))  # いまの最下位を追い出す
    return sorted(heap, reverse=True)
```

「長さより向き」のプリセットでは、原点から遠い B より、向きの揃った D のほうが上位に来ます。**距離で測っていたら逆になる**場面です。

後半のヒープの使い方は、Top-K の記事そのままです。候補が 1,000 万件あっても、保持するのは k 件だけで済みます。

<Callout type="warn" title="正規化してあるなら、内積だけで足ります">
  実務のベクトル検索では、保管する前にすべてのベクトルを**長さ 1 に正規化**しておくのが定石です。そうすると分母が常に 1 になるので、

  ```
  cos(a, b) = a と b の内積
  ```

  となり、割り算も平方根も消えます。1,000 万件との比較で平方根を 1,000 万回計算するのと、しないのとでは大きな差になります。

  幾何のノートで「距離は 2 乗のまま比べる」と書いたのと同じ発想です。**比較しかしないなら、順序を変えない変形はすべて省いてよい**というのは、性能を考えるときの基本的な手筋です。
</Callout>

## 全件比較をやめる：近似最近傍（ANN）

ここで現実的な問題にぶつかります。候補が 1,000 万件、次元が 768 だとすると、1 回の検索で **77 億回の掛け算**が必要です。ヒープを使っても、全件との内積計算そのものは避けられません。

そこで、**正確さを少し諦めます。**

> 本当に一番近いものを必ず見つける代わりに、**たいていの場合に十分近いものを、ずっと速く見つける**

これが近似最近傍（Approximate Nearest Neighbor、ANN）です。代表的な考え方を2つ挙げます。

### LSH：近いものが同じバケツに落ちるハッシュ

普通のハッシュは、少しでも違う入力をまったく別の値に飛ばします（だからこそ衝突が珍しい）。LSH（Locality Sensitive Hashing）は、その逆を狙います。

> **近いベクトルほど、同じハッシュ値になりやすい**ように設計する

コサイン類似度の場合、作り方は驚くほど単純です。ランダムな向きの平面を 1 枚引いて、**ベクトルがその平面のどちら側にあるか**を 1 ビットとして記録します。これを何十本か繰り返せば、ビット列ができます。

向きの近い 2 つのベクトルは、ランダムな平面で切られても**たいてい同じ側に落ちます**。だから似たビット列になります。

検索時は、クエリと同じバケツ（同じビット列）に入っているものだけを比較します。全件との比較が、候補の絞り込みに変わります。

<Callout type="tip" title="ハッシュを何本使うかは、確率で決める">
  1 枚の平面で同じ側に落ちる確率は、2 つのベクトルのなす角を θ として `1 − θ/π` です。角度が近いほど 1 に近づきます。

  ビットを `b` 本使うと、全ビットが一致する確率は `(1 − θ/π)^b` になります。`b` を大きくすると精度は上がりますが、**本当に近いものまで取りこぼす**確率も上がります。

  そこで、ビット列を `L` 組つくって「どれか 1 組でも一致すれば候補にする」という形にします。取りこぼす確率は `(1 − p^b)^L` まで下がります。

  **`b` と `L` をいくつにするかは、許容できる取りこぼし率から逆算します。** 確率と期待値のノートでやった「機会の数 × 1 回あたりの確率」の見積もりが、そのまま設計のパラメータ決定になります。
</Callout>

### グラフを使う方法（HNSW）

現在の実装で主流なのは、ベクトルどうしを「近いもの同士」でつないだグラフを作り、**そのグラフをたどって近づいていく**やり方です。

1. 適当なノードから始める
2. 隣接ノードのうち、クエリに最も近いものへ移る
3. それ以上近づけなくなったら終了

これはグラフ探索であり、**貪欲に「今より良い隣」へ進む**という骨格です。多層構造（粗いグラフから細かいグラフへ降りる）にすることで、スキップリストのように速く目的地へ近づけます。

FAISS、pgvector、各種ベクトルデータベースで使われているのは、おおむねこの系統です。

## 推薦：行列を埋める問題として

検索と並んで、ベクトルが活躍するのが推薦です。

ユーザーと商品の関係は、大きな表として書けます。

| | 商品A | 商品B | 商品C |
| --- | --- | --- | --- |
| ユーザー1 | 5 | ? | 3 |
| ユーザー2 | ? | 4 | ? |
| ユーザー3 | 2 | ? | ? |

この表の **`?` を埋める**のが推薦です。ほとんどのマスが空いているのが普通で（誰も全商品を買わない）、埋めるには何らかの仮定が要ります。

Matrix Factorization（行列分解）の仮定はこうです。

> この大きな表は、**ユーザーの特徴ベクトル**と**商品の特徴ベクトル**の内積で近似できる

ユーザー `u` と商品 `i` の評価を `p_u · q_i` と書き、既知のマスとの誤差が最小になるように `p` と `q` を学習します。次元数を数十に絞ることで、「似た好みのユーザーは近いベクトルになる」という構造が自然に現れます。

学習が終われば、**推薦も検索と同じ「近いベクトルを探す問題」**になります。ユーザーのベクトルに近い商品ベクトルを、ANN で引いてくればよいだけです。

<Callout type="tip" title="Learning to Rank：最後に並べ替える層">
  実際の検索・推薦システムは、たいてい2段構えです。

  1. **候補の絞り込み（recall）**：BM25 や ANN で、数百〜数千件まで一気に絞る。速さが最優先
  2. **並べ替え（ranking）**：絞った候補に対して、重いモデルで丁寧に順位をつける

  2 段目で使われるのが Learning to Rank です。「クリックされたか」「滞在時間」などの正解データから、**順位そのものを機械学習で決めます。** 特徴量には BM25 スコア、コサイン類似度、新しさ、人気度などが並びます。

  つまり、この記事とひとつ前の記事で扱ったスコアは、**最終的な順位そのものではなく、機械学習モデルへの入力**になっていることが多いわけです。「なぜこの順番か」を説明しづらくなる原因でもあります。
</Callout>

## まとめ

| やりたいこと | 手段 | 代償 |
| --- | --- | --- |
| 語の一致で探す | 転置インデックス + BM25 | 表記ゆれ・言い換えに弱い |
| 意味で探す | embedding + コサイン類似度 | ベクトルを作るコスト、全件比較の重さ |
| 全件比較を避ける | LSH / グラフ（HNSW） | 取りこぼしが起きる（近似） |
| 空欄を埋める | 行列分解 | 学習データが要る、新規ユーザーに弱い |
| 最後の並べ替え | Learning to Rank | 説明性が下がる |

実務のシステムは、これらのどれか1つではなく**組み合わせ**で動いています。語の一致と意味の近さを両方使って候補を集め、最後に機械学習で並べ替える、という構成が典型です。
