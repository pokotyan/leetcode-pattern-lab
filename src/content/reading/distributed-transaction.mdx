## 1台のデータベースなら簡単だった

口座 A から口座 B へ 1 万円を移す処理を考えます。1 台のデータベースに両方の口座があるなら、こう書くだけです。

```sql
BEGIN;
  UPDATE accounts SET balance = balance - 10000 WHERE id = 'A';
  UPDATE accounts SET balance = balance + 10000 WHERE id = 'B';
COMMIT;
```

途中で落ちても、データベースが巻き戻してくれます。「両方成功するか、両方何も起きないか」のどちらかしかありません。

ところが、マイクロサービスに分けた瞬間に、これが書けなくなります。口座サービス、決済サービス、通知サービスがそれぞれ別のデータベースを持っているからです。**1 つの `BEGIN` で囲める範囲が、サービスの中で閉じてしまいます。**

## 2PC：全員に「準備できたか」を聞いてから確定させる

素直な解決が Two-Phase Commit（2PC）です。調整役（coordinator）を 1 人立てて、2 段階で進めます。

**第1段階（prepare）**：調整役が全参加者に「この処理、確定できますか」と聞く。各参加者は、確定できる状態まで準備してロックを取り、「はい」か「いいえ」を返す

**第2段階（commit / abort）**：全員が「はい」なら、調整役が「確定してください」と伝える。1 人でも「いいえ」なら、全員に「取り消してください」と伝える

これで「全員成功か、全員取り消し」が実現します。理屈は明快です。

<Callout type="warn" title="2PC の致命的な弱点：調整役が落ちると止まる">
  第1段階で「はい」と答えた参加者は、**確定も取り消しもできない状態でロックを握ったまま待ちます。** 自分だけの判断で確定すると、ほかが取り消していた場合に不整合になるからです。

  ここで調整役が落ちると、参加者は**待ち続けるしかありません。** ロックは握られたまま、そのデータに触る処理はすべて止まります。これをブロッキングと呼びます。

  さらに悪いことに、分散システムでは「調整役が落ちた」のか「返事が遅いだけ」なのかを区別できません（分散合意の記事で見た通りです）。勝手にタイムアウトで打ち切ると、調整役が生きていた場合に食い違います。

  この性質のため、**2PC はマイクロサービス間ではほとんど使われません。** 使われるのは、1 つのデータベースクラスタの内部（複数シャードにまたがる更新）のように、参加者が近くて信頼できる範囲に限られます。
</Callout>

## Saga：確定してしまってから、必要なら打ち消す

もう1つの方針は、**足並みを揃えるのを諦める**ことです。

> 各段階は、その場で**確定してしまう**。あとで失敗が分かったら、**打ち消す操作を新たに実行する**

打ち消す操作を補償トランザクション（compensating transaction）と呼びます。重要なのは、これが**巻き戻しではない**という点です。

| 元の操作 | 補償 |
| --- | --- |
| 在庫を 1 減らす | 在庫を 1 増やす |
| 1 万円を引き落とす | 1 万円を返金する |
| 配送を手配する | 配送をキャンセルする |
| メールを送る | **打ち消せない**（取り消しのメールを送るしかない） |

```python
def run_saga(steps, ctx):
    done = []
    for step in steps:
        try:
            step.action(ctx)          # 進める
            done.append(step)
        except Exception:
            for s in reversed(done):  # 成功した分だけ、逆順に取り消す
                s.compensate(ctx)
            return 'failed'
    return 'committed'
```

<SagaRollback client:visible />

コードの形を見てください。**成功したものを積み上げ、失敗したら逆順に取り出して打ち消す。** バックトラックの記事でやった「選ぶ → 再帰 → 取り消す」と同じ骨格です。違いは、取り消しがメモリ上の `path.pop()` ではなく、**別のサービスへの新しいリクエスト**になっている点です。

<Callout type="warn" title="補償では「なかったこと」にはできません">
  データベースのロールバックは、本当に何も起きなかった状態に戻します。補償は違います。

  - 注文が作られ、そのあと取り消された、という**履歴が残る**
  - 返金までの間、ユーザーの残高は減ったままになる（**一時的に不整合が見える**）
  - 発送通知メールは取り消せない。「先ほどのメールは誤りでした」を送ることしかできない

  つまり Saga を選ぶということは、**中間状態が外から見える**ことを受け入れるということです。これは技術の問題というより、業務として許容できるかの問題になります。

  だから設計では、「補償可能な順に並べる」という工夫が効きます。**取り消せない操作（メール送信、外部への通知）を最後に持ってくる**だけで、失敗時の被害が大きく変わります。
</Callout>

## Saga をどう駆動するか

進行を管理する方法が 2 通りあります。

| | オーケストレーション | コレオグラフィ |
| --- | --- | --- |
| 進め方 | 中央の Saga 実行役が、各サービスを順に呼ぶ | 各サービスがイベントを発行し、次のサービスがそれを拾って動く |
| 流れの把握 | 1 箇所を読めば分かる | 全サービスを追わないと分からない |
| 結合 | 実行役が全サービスを知っている | サービス同士は互いを知らない |
| 向いている規模 | 段階が多い、複雑な流れ | 段階が少ない、単純な流れ |

実務では、**まずオーケストレーションで始めるほうが安全**です。コレオグラフィは疎結合で美しいのですが、「いま注文はどこまで進んでいるのか」を調べるのに全サービスのログを突き合わせることになり、障害対応が非常に苦しくなります。

## Eventual Consistency：いつかは揃う

Saga を採用すると、システムは**結果整合（eventual consistency）**になります。

> 新しい更新が止まれば、**いつかは**すべてのノードが同じ値に落ち着く

「いつかは」の部分が曲者です。保証されているのは収束することだけで、**いつ収束するかは保証されていません。** 数ミリ秒のこともあれば、障害時には数時間かかることもあります。

実務で問題になるのは、たいてい次の形です。

- ユーザーが自分で書き込んだ直後に読み直すと、古い値が見える（**自分の書き込みが見えない**）
- 一覧画面と詳細画面で、違う値が表示される
- 更新の順序が入れ替わって届き、古い値が新しい値を上書きする

対策として、次のようなものがあります。

- **Read your writes**：書き込んだ本人には、しばらく primary から読ませる
- **バージョン番号やタイムスタンプ**：古い更新を無視する（更新の順序を守る）
- **画面上の表現**：「反映まで数分かかります」と明示して、そもそも期待させない

3 番目は技術ではありませんが、結果整合を採用したシステムでは**最も効く対策**であることが多いです。

## 選び方

| 状況 | 選択 |
| --- | --- |
| 1 つの DB の中で済む | 普通のトランザクション |
| 同じ DB クラスタの複数シャード | 2PC（DB が内部で面倒を見てくれる） |
| 複数のマイクロサービス | Saga |
| 厳密な整合が業務上必須（会計の締めなど） | そもそもサービスを分けない、という判断もある |

最後の行が実は重要です。**「このデータとこのデータは、絶対に食い違ってはいけない」という関係があるなら、それらを別サービスに分けないほうがよい**ことがあります。サービス境界の設計は、トランザクション境界の設計でもあります。

## まとめ

- サービスを分けると、1 つの `BEGIN` で囲める範囲がサービス内に閉じる
- 2PC は「全員成功か全員取り消し」を実現するが、**調整役が落ちるとロックを握ったまま止まる**
- Saga は各段階をその場で確定し、失敗したら**逆順に補償**する。バックトラックと同じ骨格
- 補償は巻き戻しではない。**中間状態が外から見える**ことを受け入れる設計
- 取り消せない操作は、できるだけ後ろに置く
- 結果整合は「いつかは揃う」だけで、いつ揃うかは保証されない
