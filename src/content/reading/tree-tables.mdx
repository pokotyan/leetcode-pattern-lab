## 表は平らで、木は平らではない

商品カテゴリ、組織図、コメントの返信のスレッド、フォルダとファイル。業務のデータには木の形をしたものがよく出てきます。一方、リレーショナルデータベースの表は行の集合で、行と行の間に「親子」という構造はありません。木を表に載せるには、親子の関係をどこかの列の値として書き込む必要があります。

その書き込み方に、名前のついた方式が 4 つあります。<a href={`${import.meta.env.BASE_URL}reading/schema-map/`}>テーブル設計の型の地図</a>で挙げた型のうち、最も比べがいのある組です。

| 方式 | 各行（または別の表）に書くもの | 例: ノート PC（id 7）の行 |
| --- | --- | --- |
| 隣接リスト | 親の id | `parent_id = 4` |
| 経路列挙 | 根から自分までの経路 | `path = '/1/2/4/7/'` |
| 入れ子集合 | 深さ優先でたどったときの入りと出の番号 | `lft = 4, rgt = 5` |
| 閉包テーブル | すべての「先祖・子孫」の組（別の表） | `(1,7,3) (2,7,2) (4,7,1) (7,7,0)` |

木に対してよく行う操作は、おおむね次の 5 つです。

- **子孫を取る**: このカテゴリの下にある商品をすべて
- **先祖を取る**: パンくずリスト（商品 > 家電 > PC > ノート）
- **葉を追加する**: カテゴリを 1 つ増やす
- **部分木を移動する**: 組織変更で、部署を丸ごと別の本部の下へ
- **部分木を削除する**

方式の違いは、この 5 つのうちどれを安くし、どれを高くするかの違いです。

## 同じ操作を 4 つの方式で

10 ノードの小さな木で、選んだ操作に何文を流し、何行を読み、何行を書くかを並べました。操作と対象を変えて、数字がどう入れ替わるかを見てください。各方式の回では、同じ操作を 1 手ずつ実行して、表のどの行が読まれ書き換えられるかを追えます。

<HierarchyCompare client:visible />

大まかな傾向は次のとおりです。

| 操作 | 隣接リスト | 経路列挙 | 入れ子集合 | 閉包テーブル |
| --- | --- | --- | --- | --- |
| 子孫を取る | 深さの段数だけ再帰 | 前方一致の範囲 1 回 | 区間の範囲 1 回 | 主キーの範囲 1 回 |
| 先祖を取る | 深さの段数だけ主キー検索 | 経路を分けて主キー検索 | 索引の片側を走査して絞る | 索引で 1 回 |
| 葉を追加 | 1 行 | 1 行 | 右側のすべての行を書き換える | 深さ + 1 行 |
| 部分木を移動 | 1 行 | 部分木の行数 | 移動元と移動先の間のすべての行 | 部分木 × 先祖の直積 |
| 外部キーで親子を守れるか | 守れる | 守れない | 守れない | 守れる（2 列とも） |

## 11 万ノードで測る

10 ノードでは差が見えにくいので、各ノードが 10 個の子を持つ深さ 5 の木（1 + 10 + 100 + 1,000 + 10,000 + 100,000 = 111,111 ノード）を、4 つの方式でそれぞれ表にしました。環境は手元の Mac の Docker 上の PostgreSQL 17.11 です。

```sql
-- 10 分岐 × 深さ 5 = 111,111 ノード。id は幅優先の連番
CREATE TABLE base AS
WITH RECURSIVE t(id, parent_id, depth) AS (
  SELECT 1, NULL::int, 0
  UNION ALL
  SELECT (t.id - 1) * 10 + k + 1, t.id, t.depth + 1
  FROM t, generate_series(1, 10) k
  WHERE t.depth < 5
)
SELECT id, parent_id, depth, 'node' || id AS name FROM t;
```

各方式の表と索引は次のとおりです。

```sql
-- 隣接リスト
CREATE TABLE adj (id int PRIMARY KEY, parent_id int REFERENCES adj(id), name text NOT NULL);
CREATE INDEX adj_parent ON adj(parent_id);
-- 経路列挙（'/1/2/12/'）。前方一致を索引で引けるよう text_pattern_ops で作る
CREATE TABLE pe (id int PRIMARY KEY, path text NOT NULL, name text NOT NULL);
CREATE INDEX pe_path ON pe(path text_pattern_ops);
-- 入れ子集合
CREATE TABLE ns (id int PRIMARY KEY, lft int NOT NULL, rgt int NOT NULL, name text NOT NULL);
CREATE INDEX ns_lft ON ns(lft);
CREATE INDEX ns_rgt ON ns(rgt);
-- 閉包テーブル（ノード本体は ct_node）
CREATE TABLE ct (ancestor int NOT NULL REFERENCES ct_node(id),
                 descendant int NOT NULL REFERENCES ct_node(id),
                 depth int NOT NULL, PRIMARY KEY (ancestor, descendant));
CREATE INDEX ct_desc ON ct(descendant);
```

### 大きさ

```text
    t    |   n    | pg_size_pretty
---------+--------+----------------
 ct_node | 111111 | 7296 kB
 adj     | 111111 | 9184 kB
 ns      | 111111 | 13 MB
 pe      | 111111 | 14 MB
 ct      | 654321 | 57 MB
```

閉包テーブルは、ノード 1 つにつき「深さ + 1」行の組を持つので、この木では 654,321 行になりました。索引を含めて 57 MB と、隣接リストの 6 倍ほどです。深い木ほどこの比は大きくなります。

### 読み取り

ノード 2 の子孫（自分を含めて 11,111 行）と、深さ 5 の葉 11112 の先祖（6 行）を、`EXPLAIN (ANALYZE, BUFFERS)` で測りました。値は 2 回目の実行のもので、バッファはすべて共有バッファ上のヒット（ディスクを読んでいない）です。

| 方式 | 子孫の取り方 | 子孫: 時間 / バッファ | 先祖: 時間 / バッファ |
| --- | --- | --- | --- |
| 隣接リスト | WITH RECURSIVE で 5 段 | 6.923 ms / 182 | 0.027 ms / 18 |
| 経路列挙 | `path LIKE '/1/2/%'` | 1.196 ms / 78 | 0.049 ms / 20（経路を分けて主キーで引く） |
| 入れ子集合 | `lft BETWEEN 2 AND 22223` | 1.026 ms / 55 | 0.036 ms / 4 |
| 閉包テーブル | `ancestor = 2` | 0.820 ms / 37 | 0.027 ms / 3 |

子孫は、隣接リストだけが再帰になり、残りの 3 つは索引の範囲を 1 回走査するだけで済みます。先祖はどの方式でも 1 ms を大きく下回りますが、この表には 2 つの例外が隠れています。

- **経路列挙で先祖を素朴に書くと遅い。** `c.path LIKE a.path || '%'`（相手の経路が自分の経路の前置きになっている行）と書くと、索引が使えず全行を読みます。8.720 ms / 80 バッファでした。経路の文字列を `/` で分けて主キーで引けば 0.049 ms です。
- **入れ子集合の先祖は、ノードの位置で大きく変わる。** 上の 0.036 ms は左端に近い葉の値です。右端の葉 111111 で測ると、`lft <= 自分の lft` の側しか索引で絞れないため、111,105 行を読んで捨て、10.949 ms / 1,017 バッファかかりました。

### 書き込み

それぞれトランザクションの中で実行し、件数を見てからロールバックしました。

| 操作 | 隣接リスト | 経路列挙 | 入れ子集合 | 閉包テーブル |
| --- | --- | --- | --- | --- |
| ノード 112 の下に葉を追加 | 1 行 | 1 行 | 111,001 行 + 110,997 行を更新（各 0.7 秒）+ 1 行 | 1 + 5 行 |
| 右端のノード 11111 の下に葉を追加 | — | — | 5 行 + 0 行を更新 + 1 行 | — |
| 部分木 12（1,111 ノード）をノード 11 の下へ移動 | 1 行 | 1,111 行（12 ms） | 111,110 行（1.4 秒） | 2,222 行削除 + 2,222 行挿入 |
| 部分木 12 を削除 | 1,111 行（13 ms） | 1,111 行（1.8 ms） | 測っていない | 6,543 行（39 ms）+ ノード本体 |

入れ子集合の書き込みの重さは、番号を振り直す範囲で決まります。木の左寄りに葉を 1 つ足すと、その右にあるほぼすべての行の番号がずれます。右端に足せば 5 行で済みます。同じ「葉を 1 つ足す」でも、場所によって書き換える行数が 4 万倍以上違います。

書き換える行が多いことは、時間だけでなく並行性にも響きます。入れ子集合で 2 つのトランザクションが別々の枝に葉を足すと、どちらも根の行の rgt を書き換えるので、後の方が待たされます。詳しくは<a href={`${import.meta.env.BASE_URL}reading/tree-nested-set/`}>入れ子集合</a>の回で実験します。

## DB 製品の組み込み型

方式を自分で組み立てる代わりに、DB が木のための型を用意していることもあります。

**PostgreSQL の ltree** は、経路列挙を型として提供する拡張です。`1.2.12.112` のような「ラベルをドットでつないだ経路」を 1 つの値として持ち、`@>`（左が右の先祖か、または等しいか）と `<@`（左が右の子孫か、または等しいか）の演算子に GiST 索引が効きます（[PostgreSQL: ltree](https://www.postgresql.org/docs/17/ltree.html)）。同じ 11 万ノードで試すと、子孫 11,111 行が 1.981 ms、先祖 6 行が 0.054 ms でした。詳しくは<a href={`${import.meta.env.BASE_URL}reading/tree-path-enumeration/`}>経路列挙</a>の回で扱います。

**SQL Server の hierarchyid** は、木の中の位置を表すコンパクトな型です。Microsoft の文書によると、比較は深さ優先の順で、hierarchyid の索引では部分木の行が互いに近くに並びます。一方で、この型の列は木であることを自動では保証せず、「親子の関係は外部キーのようには強制されない」ため、親を消すと子が存在しない親を指したまま残りうると明記されています（[Microsoft Learn: Hierarchical Data (SQL Server)](https://learn.microsoft.com/en-us/sql/relational-databases/hierarchical-data-sql-server)）。同じ文書は親子の方式（隣接リスト）と比べて、部分木の問い合わせは hierarchyid のほうがかなり速く、葉でない部分木の移動は遅い、とまとめています。移動で書き換わるのは部分木のノード数ぶんの行です。これは経路列挙と同じ性質で、hierarchyid が経路を圧縮して持つ型だと分かります。

<Callout type="tip" title="組み込み型も、どれかの方式の実装である">
  ltree も hierarchyid も、中身は「根からの経路を値として持つ」方式です。部分木の取得は速く、移動は部分木の大きさに比例し、親子の参照整合性は別に守る必要がある、という経路列挙の性質をそのまま引き継いでいます。
</Callout>

## どれを選ぶか

1 つの方式がすべての操作で勝つことはありません。どの操作をどれだけ行うかで選びます。

- **まず隣接リスト**。書き込みは常に 1 行で、外部キーで親子を守れ、循環以外の壊れ方をしません。WITH RECURSIVE が使える DB なら、子孫の取得も 1 文で書けます。木が浅く（数段）、子孫の取得がたまにしか起きないなら、これで足ります。
- **子孫の取得が多く、移動がまれなら経路列挙**。パンくずリストも経路の文字列からすぐ作れます。PostgreSQL なら ltree を使えます。
- **読み取りが圧倒的に多く、木がほとんど変わらないなら入れ子集合**。子孫の数を `(rgt - lft - 1) / 2` で行を読まずに求められるのも利点です。ただし追加・移動が重く、並行して書き込むと競合します。
- **読み書きの両方があり、記憶域に余裕があるなら閉包テーブル**。子孫・先祖ともに索引 1 回で、外部キーで整合性も守れます。代わりに行数がノード数 ×（平均の深さ + 1）になります。

実務では組み合わせもよく使われます。親の id を正とし、そこから閉包テーブルや経路を作って検索用に持つ、という形です。隣接リストは壊れにくく、ほかの方式はそこから作り直せます。
