## まず、困っている状況を体験してみます

データベースに 1 億件のユーザー ID が入っています。アクセスのたびに、こう問い合わせが来ます。

> この ID は登録されていますか？

登録されていない ID の問い合わせが大量に来るとします（存在しない ID での総当たりや、キャッシュミス）。そのたびにディスクを読みに行くのは無駄です。**読む前に「無い」と分かれば、アクセスそのものを省けます。**

素直な方法は、全 ID をメモリ上の集合に入れておくことです。

```python
if user_id in known_ids:      # O(1) で判定できる
    ...
```

計算量は申し分ありません。問題は**容量**です。ID が平均 30 バイトなら、1 億件で 3 GB。Python の集合はオブジェクトの overhead が乗るので、実際にはさらに膨らみます。1 台のサーバーのメモリに載せるには大きすぎます。

## 発想を変える：要素を捨てて、ビットだけ残す

ここで、思い切った割り切りをします。

> **要素そのものは保存しない。** ハッシュが指す場所にビットを立てるだけにする

手順はこうです。

1. `m` ビットの配列を用意する（全部 0）
2. 要素を追加するとき、`k` 本のハッシュ関数でそれぞれ位置を計算し、**そのビットを 1 にする**
3. 問い合わせのとき、同じ `k` 箇所を見る
   - **1 つでも 0 があれば** → その要素は**絶対に入っていない**
   - **全部 1 なら** → **たぶん入っている**

```python
class BloomFilter:
    def __init__(self, m, k):
        self.bits = [0] * m          # m ビットの配列
        self.m = m
        self.k = k                   # ハッシュ関数の本数

    def _positions(self, key):
        h1, h2 = hash1(key), hash2(key)
        return [(h1 + i * h2) % self.m for i in range(self.k)]

    def add(self, key):
        for p in self._positions(key):
            self.bits[p] = 1         # 立てるだけ。決して消さない

    def might_contain(self, key):
        # 1つでも 0 があれば「絶対に無い」
        # 全部 1 なら「たぶん有る」
        return all(self.bits[p] for p in self._positions(key))
```

## 答えが片側だけ確実、という非対称さ

ここがこのデータ構造の本質です。

| 実際 | Bloom Filter の答え | 起こりうるか |
| --- | --- | --- |
| 入っている | たぶん有る | 常にこう答える（**見落としは絶対にない**） |
| 入っている | 無い | **起こらない** |
| 入っていない | 無い | たいていこう答える |
| 入っていない | たぶん有る | **起こる**（偽陽性） |

「入っているのに無いと言う」（偽陰性）は**原理的に起こりません。** 追加したときに立てたビットは二度と 0 に戻らないからです。

この非対称さが、使いどころを決めます。**「無い」と言われたら信じてよく、「有る」と言われたら確認が要る**という使い方に限れば、誤りが実害にならないからです。

<Callout type="warn" title="「たぶん有る」を「有る」として扱ってはいけない">
  Bloom Filter を使った設計でいちばん危険なのは、`might_contain` が True を返したときに、そのまま「存在する」として処理を進めてしまうことです。

  正しい使い方は必ずこの形になります。

  ```python
  if not bloom.might_contain(key):
      return None              # 確実に無いので、ここで終わり
  return db.get(key)           # 有るかもしれないので、本体に聞く
  ```

  **本体への確認が省けるのは「無い」と言われたときだけ**です。偽陽性が起きた場合は、無駄に 1 回ディスクを読むだけで、答えは正しく返ります。性能の問題であって、正しさの問題にはなりません。

  文字列照合のノートでローリングハッシュについて「ハッシュが一致しても本体を突き合わせる」と書きました。構造はまったく同じです。違うのは、Bloom Filter は**本体を持っていないので自分では確認できず**、確認を下の層（データベース）に委ねている点です。
</Callout>

## どれくらい小さくなるのか

偽陽性率を `p`、要素数を `n`、ビット数を `m` とすると、ハッシュの本数を最適に選んだときの関係はこうなります。

```
m / n ≈ -1.44 × log2(p)
```

1 要素あたり何ビット必要かを表にすると、こうなります。

| 目標の偽陽性率 | 1 要素あたりのビット数 | 1 億件での容量 |
| --- | --- | --- |
| 10%（1/10） | 約 4.8 ビット | 約 60 MB |
| 1%（1/100） | 約 9.6 ビット | 約 120 MB |
| 0.1%（1/1000） | 約 14.4 ビット | 約 180 MB |

3 GB が **120 MB** になりました。しかも、**要素の長さに依存しません。** ID が 30 バイトでも 300 バイトでも、1 要素あたり 9.6 ビットのままです。長いものを扱うほど有利になります。

<Callout type="tip" title="ハッシュの本数 k はどう決めるか">
  `k` が小さすぎると、少ないビットだけで判定するので偶然の一致が増えます。逆に `k` が大きすぎると、1 要素の追加で立つビットが多くなり、**配列がすぐ埋まって**やはり偽陽性が増えます。

  最適値は次の式で与えられます。

  ```
  k = (m / n) × ln 2 ≈ 0.693 × (m / n)
  ```

  1 要素あたり 9.6 ビットなら `k ≈ 7` 本です。このとき、ビット配列のちょうど**半分が 1 になる**ことが知られています。「半分埋まったところが最も効率がよい」と覚えておくと、感覚が合います。

  確率と期待値のノートでやった「機会の数 × 1 回あたりの確率」の見積もりが、そのまま設計パラメータの決定に使われている例です。

  なお実装上は、独立なハッシュ関数を `k` 本用意する必要はありません。2 本から `h1 + i × h2` の形で作れば、性能上ほぼ同等であることが知られています（上のコードもこの形です）。
</Callout>

## 削除ができない

Bloom Filter の最大の制約が、**要素を削除できない**ことです。

ビットを 0 に戻そうとすると、**そのビットを共有しているほかの要素まで「無い」ことになってしまいます。** 偽陰性が生まれ、片側だけ確実という性質が壊れます。

対策は 2 つあります。

- **Counting Bloom Filter**：ビットの代わりに小さなカウンタ（4 ビット程度）を置き、追加で +1、削除で −1 する。容量は 4 倍になる
- **Cuckoo Filter**：要素の指紋（短いハッシュ値）を保存し、削除に対応する。偽陽性率が同程度なら Bloom Filter より小さくできることが多い

もっと単純な運用として、**定期的に全部作り直す**という方法もよく使われます。追加しかされない用途（すでに処理した ID の記録など）なら、そもそも削除が要りません。

## 実際にどこで使われているか

| 場面 | 何を判定しているか |
| --- | --- |
| LSM-tree（RocksDB、Cassandra） | 各 SSTable に持たせ、「このファイルにキーは無い」と分かればディスクを読まない |
| CDN・キャッシュ | 「1 回しかアクセスされていない URL」をキャッシュに入れない判定 |
| 分散システム | すでに処理したメッセージ ID かどうかの粗い判定（確実な重複排除は別途必要） |
| ウェブブラウザ | 危険な URL のリストを、全件持たずに手元で 1 次判定する |
| データベース結合 | 結合相手に存在しない行を、転送する前に落とす |

共通しているのは、**「無い」と分かったときに重い処理を丸ごと省ける**という構造です。次の記事で扱うデータベースの索引でも、この形が出てきます。

## まとめ

- 要素を保存せず、ハッシュが指すビットだけを立てる
- **偽陰性は原理的に起きない。** 偽陽性だけが起きる
- だから「無い」は信じてよく、「有る」は本体への確認が要る
- 1 要素あたり 10 ビット程度で偽陽性率 1%。要素の長さに依存しない
- 削除はできない。必要なら Counting Bloom Filter や Cuckoo Filter を使う
