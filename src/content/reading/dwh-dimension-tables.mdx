## 出来事を説明する側の表

前回の<a href={`${import.meta.env.BASE_URL}reading/dwh-fact-tables/`}>ファクトテーブルの設計</a>では、出来事や測定値を記録する表を扱いました。ファクトの行は、日付のキー、商品のキー、顧客のキーと、金額や数量といった数値でできています。「どの商品か」「どの地域の顧客か」といった説明は、キーの先にあるディメンションテーブルが持ちます。

Microsoft の解説は、ディメンションテーブルを「業務にかかわる実体、つまりモデル化する“もの”を表す」表とし、その列は「絞り込みとグループ化に使う」ものだとしています（[Microsoft Learn: Understand star schema](https://learn.microsoft.com/en-us/power-bi/guidance/star-schema)）。集計するのはファクトの数値で、ディメンションの列は集計しません。

この回では、ディメンションテーブルを作るときに必ず出てくる判断を順に見ていきます。中心になるのは「属性が変わったとき、過去の集計をどうするか」です。

## 代理キーと自然キー

ディメンションには 2 種類のキーを持たせます。

- **自然キー**（natural key、業務キー）：業務システムが持っている ID。顧客番号 `C-0042` や社員番号など
- **代理キー**（surrogate key）：ディメンションの中だけで使う、意味を持たない番号

Kimball Group は、代理キーを「these dimension surrogate keys are simple integers, assigned in sequence, starting with the value 1（1 から順に振る単純な整数）」とし、主キーは「cannot be the operational system's natural key（業務システムの自然キーであってはならない）」と書いています（[Kimball Group: Dimension Surrogate Keys](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/dimension-surrogate-key/)）。

業務の ID があるのに、わざわざ別の番号を振る理由として、Microsoft は次の 4 つを挙げています（[Microsoft Fabric: Dimension tables](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-dimension-tables)）。

- 複数の業務システムの ID を混ぜても衝突しない
- 複数列でできた業務キーを 1 列にまとめられる
- 後で見る SCD Type 2 で、同じ顧客の複数の版を区別できる
- 小さな整数型を選べば、行数の多いファクトの幅を抑えられる

代理キーの値には意味を持たせません。ただし日付だけは例外で、Microsoft は日付ディメンションの代理キーを `YYYYMMDD` 形式の整数にすることを「the only exception (alongside the time dimension)（時刻のディメンションと並ぶ唯一の例外）」としています（同上）。`20250105` のように読めて、数としての並びが日付の並びと一致するためです。

<Callout type="warn" title="代理キーを振り直さない">
  代理キーを自動で振っているディメンションを、空にして作り直してはいけません。Microsoft は「you should never perform a truncate and full reload of it（切り詰めて全件を読み込み直すことは決してしてはならない）」とし、理由を「it would invalidate the data loaded into fact tables（ファクトに読み込んだデータが無効になる）」と書いています（[Microsoft Fabric: Load tables](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-load-tables)）。作り直すと同じ顧客に別の番号が振られ、ファクトの側に残っている古い番号が別人を指してしまいます。
</Callout>

## 属性が変わったとき：SCD

顧客が東京から大阪へ転居したとします。1 月に東京で買った売上は、地域別の集計で東京に数えるべきでしょうか、大阪に数えるべきでしょうか。どちらが正しいかは業務によって決まります。データウェアハウスの側でできるのは、どちらの答えを出す設計にするかを意識して選ぶことです。

この「時間とともにゆっくり変わるディメンションの属性」の扱い方を、Kimball の一派は SCD（Slowly Changing Dimension）と呼び、型に番号を振っています。業務システムの表で変わる値を残す方法としては<a href={`${import.meta.env.BASE_URL}reading/temporal-tables/`}>時間とともに変わる値を残す</a>で扱いました。ここでは分析の側から、**ファクトがどの版を指すか**に注目します。

下のシミュレーターは、顧客 A の転居を Type 1（上書き）と Type 2（版を足す）で記録し、地域別売上を出し直します。

### Type 1：上書き

属性を新しい値で上書きします。Kimball は、Type 1 の属性は常に最新の値を表すので「this technique destroys history（この方法は履歴を壊す）」とし、変更に合わせて集計済みのファクトテーブルを再計算する必要がある、と注意しています（[Kimball Group: Type 1](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/type-1/)）。

過去の値に意味がない属性（メールアドレスや氏名の表記の誤り）には、これで十分です。Microsoft も Type 1 は「should be used for most changing attributes, like customer name, email address（顧客名やメールアドレスなど、変わる属性の大半に使うべき）」としています（[Microsoft Fabric: Dimension tables](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-dimension-tables)）。

ただし、上書きした属性で過去の売上を切ると、数字が変わります。Microsoft は営業担当者の担当地域を例に、上書き後は「It's as if that salesperson was always assigned to the new sales region（その担当者が最初から新しい地域にいたかのようになる）」と書いています（同上）。

### Type 2：版を足す

変わるたびに新しい行を足し、古い行には有効期間の終わりを書きます。Kimball は、Type 2 では主キーを自然キーより細かくする必要があり、変更のたびに新しい代理キーを振ること、そして少なくとも「row effective date」「row expiration date」「current row indicator（有効開始日、有効終了日、現在の行の印）」の 3 列を足すことを挙げています（[Kimball Group: Type 2](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/type-2/)）。

ここで大事なのは、ファクトの粒度が変わることです。Microsoft は「the granularity of related fact tables isn't at the salesperson level, but rather the *salesperson version* level（関連するファクトの粒度は営業担当者ではなく、営業担当者の版になる）」と書いています（[Microsoft Fabric: Dimension tables](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-dimension-tables)）。ファクトを読み込むときに「売れた日に有効だった版」の代理キーを引いて入れておくので、後から集計しても売れた時点の地域で数えられます。

### 実験：Type 1 と Type 2 で上半期の数字はどう変わるか

DuckDB 1.4.3 で、顧客 10 万人（地域 8 つ）と 2025 年の販売 100 万行を作りました。顧客の 10 人に 1 人が 2025-07-01 に隣の地域へ移ります。Type 1 は顧客 1 人 1 行で転居後の地域だけを持ち、Type 2 は移った顧客に 2 つの版を持たせます。ファクトは読み込み時に、Type 2 では売れた日に有効だった版のキーを引きます。

```sql
CREATE TABLE fct_sales_t2 AS
SELECT s.sale_date, d.customer_key, s.amount
FROM src_sales s JOIN dim_customer_t2 d
  ON d.customer_id = s.customer_id AND s.sale_date >= d.valid_from AND s.sale_date < d.valid_to;
```

```text
┌─────────────────┬─────────┐
│        t        │    n    │
├─────────────────┼─────────┤
│ dim_customer_t1 │  100000 │
│ dim_customer_t2 │  110000 │
│ fct_sales_t1    │ 1000000 │
│ fct_sales_t2    │ 1000000 │
└─────────────────┴─────────┘
```

同じ「2025 年 1〜6 月の地域別売上」を、6 月末に出した場合と、12 月末に出し直した場合で比べます（R0〜R2 の 3 地域だけを表示）。

```text
--- 6 月末に出した数字（移る前の地域で数える）
│ R0      │ 312436975 │
│ R1      │ 309554498 │
│ R2      │ 314297523 │
--- 12 月末に Type 1 で出し直す
│ R0      │ 250033710 │
│ R1      │ 371957763 │
│ R2      │ 250542195 │
--- 12 月末に Type 2 で出し直す
│ R0      │ 312436975 │
│ R1      │ 309554498 │
│ R2      │ 314297523 │
```

Type 1 では、終わったはずの上半期の数字が 12 月末に変わりました。この作り方では偶数の地域の顧客だけが奇数の地域へ移るので、R0 と R2 が減り、R1 が増えています。Type 2 では 6 月末と同じ数字が出ます。

Type 2 でも「いまの地域で過去を見たい」という問いには答えられます。ファクトが指す版から自然キー（`customer_id`）をたどり、現在の版に寄せて集計します。

```sql
SELECT cur.region, sum(f.amount) AS h1_sales
FROM fct_sales_t2 f
JOIN dim_customer_t2 v   ON v.customer_key = f.customer_key
JOIN dim_customer_t2 cur ON cur.customer_id = v.customer_id AND cur.is_current
WHERE f.sale_date < DATE '2025-07-01' GROUP BY 1 ORDER BY 1 LIMIT 3;
```

```text
│ R0      │ 250033710 │
│ R1      │ 371957763 │
│ R2      │ 250542195 │
```

Type 1 と同じ数字になりました。**Type 2 で持っておけば両方の問いに答えられ、Type 1 で持つと一方にしか答えられません。** 代わりに、ディメンションの行は 10 万から 11 万に増え、問い合わせを書く人は版という考え方を知っている必要があります。Microsoft は版の多すぎる表は分析者を混乱させるとして、「Try to avoid having too many SCD type 2 changes on a dimension table（1 つのディメンションに Type 2 の変更が多くなりすぎないようにする）」と書き、版を見分けるために「Lynn Tsoflias (Australia)」のような版の名前の列を持つことを勧めています（[Microsoft Fabric: Dimension tables](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-dimension-tables)）。

### そのほかの型

Kimball の一覧には、ほかにも番号の付いた型があります。

| 型 | 内容 | 出典 |
| --- | --- | --- |
| Type 0 | 元の値を保ち、変えない。「the dimension attribute value never changes, so facts are always grouped by this original value（値は変わらず、ファクトは常に元の値でまとめられる）」。生年月日や最初の契約日など | [Type 0](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/type-0/) |
| Type 3 | 古い値を残すための列を足す。「add a new attribute in the dimension to preserve the old attribute value（古い値を保つ属性を足す）」。直前の値だけを並べて比べたいとき | [Type 3](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/type-3/) |
| Type 4 | 頻繁に変わる属性の群を、ミニディメンションという別の表に切り出す。「used when a group of attributes in a dimension rapidly changes」。ファクトには元のディメンションとミニディメンションの両方のキーを持たせる | [Type 4](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/type-4/) |
| Type 6 | Type 2 の版の行に、同じ属性の「いまの値」（Type 1）も埋め込む。「builds on the type 2 technique by also embedding current type 1 versions of the same attributes」 | [Type 6](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/type-6/) |

Type 6 は、上の実験で自己結合して求めた「いまの地域」を、あらかじめ各版の行に列として持っておく形です。結合が 1 回減る代わりに、地域が変わるたびに同じ顧客の全部の版の行を書き換えます。

Microsoft は Type 3 を「isn't commonly used（あまり使われない）」としています。また、頻繁に変わる属性（たとえば価格）はディメンションに置かず、ファクトの数値として持つことを勧めています（[Microsoft Fabric: Dimension tables](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-dimension-tables)）。1 つのディメンションの中で、列ごとに Type 1 と Type 2 を使い分けることもできます。

## 日付ディメンション

ほとんどのファクトが日付を持つので、日付ディメンションはどのスタースキーマにもあります。業務システムには「日付の表」がないので、データウェアハウスの側で生成します（[Microsoft Fabric: Dimension tables](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-dimension-tables)）。1 日 1 行で、年・四半期・月・曜日・会計年度・祝日の印・週番号など、絞り込みとグループ化に使う列を持たせます。

```sql
-- DuckDB の例。2015〜2035 年を 1 日 1 行で作る
CREATE TABLE dim_date AS
SELECT CAST(strftime(d, '%Y%m%d') AS INTEGER) AS date_key,
       CAST(d AS DATE)                         AS full_date,
       year(d) AS year, quarter(d) AS quarter, month(d) AS month,
       strftime(d, '%Y-%m')                    AS year_month,
       dayofweek(d) NOT IN (0, 6)              AS is_weekday
FROM range(DATE '2015-01-01', DATE '2036-01-01', INTERVAL 1 DAY) t(d);
```

```text
┌──────────────┬───────────────┬───────────────┐
│ count_star() │ min(date_key) │ max(date_key) │
├──────────────┼───────────────┼───────────────┤
│         7670 │      20150101 │      20351231 │
└──────────────┴───────────────┴───────────────┘
```

21 年分でも 7,670 行です。ファクトに比べれば無視できる大きさなので、使いそうな列は遠慮なく足せます。

時刻は別にします。Microsoft は「A date dimension shouldn't include a grain that extends to time of day（日付ディメンションの粒度を時刻まで細かくしない）」とし、時刻の分析が要るなら日付と時刻の 2 つのディメンションを持つよう勧めています（同上）。1 分単位の時刻の表なら 1,440 行で済み、日付と掛け合わせた巨大な表を作らずに済みます。

## 何度も引く・まとめる・ファクトに置く

ここからは、名前の付いた小さな型を見ます。

### 適合ディメンション

複数のファクトで共有するディメンションです。Kimball は、別々のディメンションの属性が同じ列名と同じ値の範囲を持つとき、それらは「conform（適合する）」とし、これを全社的なデータウェアハウスの統合の本質としています（[Kimball Group: Conformed Dimensions](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/conformed-dimension/)）。売上のファクトと在庫のファクトが同じ `dim_product` と `dim_date` を使っていれば、「商品別に売上と在庫を並べる」という問いにそのまま答えられます。部門ごとに別々の商品の表を作ると、同じ「商品カテゴリ」が部門によって違う意味になり、数字が合わなくなります。

### 役割を演じるディメンション

1 つのファクトから、同じディメンションを何度も引く形です。Kimball は「A single physical dimension can be referenced multiple times in a fact table, with each reference linking to a logically distinct role（1 つの物理的なディメンションを、ファクトから論理的に異なる役割として何度も参照できる）」と書き、それぞれの外部キーが日付ディメンションの別のビューを指すようにすることを勧めています（[Kimball Group: Role-Playing Dimensions](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/role-playing-dimension/)）。

```sql
-- 注文日と出荷日で、同じ dim_date を 2 回引く
SELECT od.year AS order_year, sd.year AS ship_year, sum(f.amount)
FROM fct_order_items f
JOIN dim_date od ON od.date_key = f.order_date_key
JOIN dim_date sd ON sd.date_key = f.ship_date_key
GROUP BY 1, 2;
```

表の実体は 1 つで、どの列で結合するかによって役割が決まります。

### ジャンクディメンション

注文の状態、支払方法、ギフト包装の有無のように、値の種類が少ない印がたくさんあるとき、1 つずつディメンションにするとファクトのキーが増えます。Kimball は、業務の処理はこうした「miscellaneous, low-cardinality flags and indicators（雑多な、値の種類の少ない印）」を多く生むとし、それらを 1 つのジャンクディメンションにまとめることを勧めています（[Kimball Group: Junk Dimensions](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/junk-dimension/)）。

中身の作り方は資料によって違います。Kimball は「should only contain the combination of values that actually occur in the source data（実際にデータに現れた組み合わせだけを持つ）」とし、Microsoft は「typically stores the Cartesian product of all dimension attribute values（すべての値の直積を持つのが普通）」としています（[Microsoft Fabric: Dimension tables](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-dimension-tables)）。印の組み合わせが少なければ直積で前もって作れて読み込みが単純になり、多ければ現れたものだけにして表を小さく保ちます。

### 退化ディメンション

注文番号のように、ファクトと同じ粒度で、説明する属性を何も持たないものです。Kimball は「a dimension is defined that has no content except for its primary key（主キーのほかに中身のないディメンション）」があるとき、それを対応する表なしでファクトに置くと書いています（[Kimball Group: Degenerate Dimensions](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/degenerate-dimension/)）。注文番号の列だけの表を別に作っても、結合が増えるだけで得るものがありません。

### 値が分からないときの行

ファクトを読み込むときに、ディメンションに対応する行が見つからないことがあります。Microsoft は、欠損・不明・該当なし・誤りを表す特別な行を前もって入れておく例を示しています（`0` が欠損、`-1` が不明など。[Microsoft Fabric: Dimension tables](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-dimension-tables)）。こうしておくと、ファクトのキーを NULL にせずに済み、内部結合で行が消えることもありません。

## 正規化するか

ディメンションは原則として正規化しません。Microsoft は「It's almost always the case that dimension tables should be *denormalized*（ディメンションはほぼ常に非正規化すべき）」とし、ディメンションはファクトに比べて小さいので、重複して持つ費用より問い合わせの速さと使いやすさの利点が上回る、と書いています（[Microsoft Fabric: Dimension tables](https://learn.microsoft.com/en-us/fabric/data-warehouse/dimensional-modeling-dimension-tables)）。商品のディメンションに、分類名や部門名まで平らに持たせます。

例外として正規化した形（スノーフレーク）を選ぶ条件も挙がっています。ディメンションが極端に大きい、分類の粒度で記録したファクト（分類ごとの予算など）とつなぐキーが要る、上位の階層で履歴を追う必要がある、という場合です（同上）。この選択は次回の<a href={`${import.meta.env.BASE_URL}reading/dwh-schema-shapes/`}>スキーマの形と選び方</a>で、表全体の形として比べます。

## まとめ

- ディメンションには、業務の ID（自然キー）とは別に、意味を持たない代理キーを振る。日付だけは `YYYYMMDD` の整数でよい
- 属性が変わったときの扱いは選ぶもの。上書き（Type 1）は過去の集計を変え、版を足す（Type 2）はファクトの粒度を「版」にする。実験では、Type 1 で出し直した上半期の数字が変わり、Type 2 では変わらなかった
- Type 2 で持っておけば、自然キーで現在の版に寄せることで「いまの属性で過去を見る」問いにも答えられる
- 日付ディメンションは自分で作り、時刻とは分ける
- 共有するディメンションは定義をそろえる（適合）。同じディメンションを役割を変えて何度も引く。小さな印はジャンクディメンションにまとめ、注文番号のようなものはファクトに置く
